用命名空间标签约束 Pod

容器安全上下文是清单作者主动写的；Pod Security Admission（PSA）则在 API Server 接收 Pod 时，拿它和预定义的 Pod 安全标准比对。标准分三级：privileged 不设限制，baseline 挡住已知的提权手段（特权容器、hostNetwork、hostPath 等），restricted 在此基础上要求按加固最佳实践来写。每个命名空间通过标签为三种模式各选一个级别：

  • enforce：违规的 Pod 直接被拒绝；
  • warn：放行，但给客户端返回警告；
  • audit：放行，在审计日志的事件里加注解。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，kubectl v1.30.0，containerd 1.7.18）。这个集群没有给 API Server 配置 PSA 的 AdmissionConfiguration，也就是说集群级默认是 privileged，一切约束都来自命名空间标签。实验用了几个独立的 namespace，文中统一写成 notes-lab-*。

三种模式各自给出什么

先建一个「拒绝 baseline 违规、对 restricted 违规只提醒」的命名空间，这是从宽松策略过渡时常见的写法：

apiVersion: v1
kind: Namespace
metadata:
  name: notes-lab
  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/enforce-version: v1.31
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/warn-version: v1.31
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/audit-version: v1.31

然后提交一个最普通的 nginx Pod，不写任何 securityContext：

apiVersion: v1
kind: Pod
metadata:
  name: nginx-plain
spec:
  containers:
    - name: nginx
      image: nginx:alpine
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
$ kubectl -n notes-lab apply -f nginx-plain.yaml
Warning: would violate PodSecurity "restricted:v1.31": allowPrivilegeEscalation != false (container "nginx" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "nginx" must set securityContext.capabilities.drop=["ALL"]), runAsNonRoot != true (pod or container "nginx" must set securityContext.runAsNonRoot=true), seccompProfile (pod or container "nginx" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
pod/nginx-plain created

它满足 baseline，所以被创建了；同时 warn 模式把不满足 restricted 的四项逐条列了出来，括号里直接写着该设哪个字段。这四项正好就是 restricted 对一个普通 Pod 的全部额外要求：allowPrivilegeEscalation: false、capabilities.drop: ["ALL"]、runAsNonRoot: true、seccompProfile.type: RuntimeDefault（或 Localhost）。各字段的含义见容器安全上下文，这里不重复。

再提交一个违反 baseline 的 Pod（hostNetwork: true 加 privileged: true）：

$ kubectl -n notes-lab apply -f nginx-privileged.yaml
Error from server (Forbidden): error when creating "nginx-privileged.yaml": pods "nginx-privileged" is forbidden: violates PodSecurity "baseline:v1.31": host namespaces (hostNetwork=true), privileged (container "nginx" must not set securityContext.privileged=true)

两处细节：被拒绝的请求只带 enforce 的错误，没有附上 restricted 的警告。这是有意为之：PSA 源码（1.31 的 admission.go）在计算 warn 结果前有一句 if response.Allowed，注释写着避免给一个已经要被拒绝的请求再加警告。另外，措辞上，warn 是 would violate，enforce 是 violates，在 CI 日志里 grep 时可以据此区分。

audit 去了哪里

audit 模式的结果写在审计事件的注解 pod-security.kubernetes.io/audit-violations 里，不在 Pod 对象上，也不是 kubectl get events 能看到的 Event。为了确认这一点，单独建了一个只设 audit=restricted 的命名空间，提交同一个 nginx-plain：

$ kubectl -n notes-lab-audit apply -f nginx-plain.yaml -v=6
pod/nginx-plain created
I1012 16:03:01.005239 1298106 apply.go:541] Running apply post-processor function

客户端一句警告都没有，Pod 的注解里也没有任何 pod-security 开头的键。审计注解要靠 API Server 的审计日志才能看到，而这个集群的 kube-apiserver 启动参数里没有任何 --audit-log-*、--audit-policy-file 或 --audit-webhook-*，审计没有开启，所以这次实验没法展示 audit 注解的实际内容。按官方文档，它的值和 warn 的文案是同一种格式（would violate PodSecurity "restricted:latest": ...）。

实际意义是：只配 audit 而不配 warn，开发者提交时什么都不会察觉。想让人看到，就同时配 warn。

restricted 下让 nginx 真正跑起来

换一个 enforce: restricted 的命名空间，nginx-plain 直接被拒，错误内容和上面的警告一模一样，只是开头变成了 violates。照着提示补齐四个字段：

apiVersion: v1
kind: Pod
metadata:
  name: nginx-step1
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: nginx
      image: nginx:alpine
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
      resources:
        requests:
          cpu: 10m
          memory: 16Mi

PSA 放行了，但 Pod 起不来：

NAME          READY   STATUS                       RESTARTS   AGE
nginx-step1   0/1     CreateContainerConfigError   0          20s
Warning  Failed     3s (x4 over 19s)  kubelet            Error: container has runAsNonRoot and image will run as root (pod: "nginx-step1_notes-lab-restricted(...)", container: nginx)

这条错误来自 kubelet，不是 PSA。PSA 只检查清单里写了什么，runAsNonRoot: true 只是一个声明；真正检查镜像会以哪个用户运行的是 kubelet。官方 nginx 镜像默认以 root 启动 master 进程，所以被拦下。通过了准入不代表能跑，这是从 baseline 迁到 restricted 时最先碰到的一类问题。

接着在 Pod 级加 runAsUser: 101（alpine 版 nginx 镜像里 nginx 用户的 UID），容器启动了，但马上退出：

nginx: [emerg] mkdir() "/var/cache/nginx/client_temp" failed (13: Permission denied)

非 root 用户不能写镜像里属于 root 的缓存目录。给 /var/cache/nginx 和 /run（pid 文件所在）各挂一个 emptyDir，再试：

nginx: [emerg] bind() to 0.0.0.0:80 failed (13: Permission denied)

80 是特权端口。restricted 唯一允许加回的 capability 恰好是 NET_BIND_SERVICE，可是加上 add: ["NET_BIND_SERVICE"] 后 PSA 照样放行，报错却一字不变：对非 root 进程，这样加回的 capability 并不生效，原因见容器安全上下文。可行的办法有两个：让 nginx 改听 1024 以上的端口，或者在 Pod 的 securityContext.sysctls 里把 net.ipv4.ip_unprivileged_port_start 调低，这个 sysctl 在 baseline 和 restricted 下都允许设置。

这里选前一种，让 nginx 监听 8080，用 ConfigMap 覆盖默认的 default.conf：

apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-8080
data:
  default.conf: |
    server {
      listen 8080;
      location / {
        root /usr/share/nginx/html;
      }
    }
---
apiVersion: v1
kind: Pod
metadata:
  name: nginx-restricted
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 101
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: nginx
      image: nginx:alpine
      ports:
        - containerPort: 8080
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: conf
          mountPath: /etc/nginx/conf.d
        - name: cache
          mountPath: /var/cache/nginx
        - name: run
          mountPath: /run
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
  volumes:
    - name: conf
      configMap:
        name: nginx-8080
    - name: cache
      emptyDir: {}
    - name: run
      emptyDir: {}
$ kubectl -n notes-lab-restricted get pod nginx-restricted
NAME               READY   STATUS    RESTARTS   AGE
nginx-restricted   1/1     Running   0          16s
$ kubectl -n notes-lab-restricted exec nginx-restricted -- sh -c "id; wget -qO- http://127.0.0.1:8080 | grep title"
uid=101(nginx) gid=101(nginx) groups=101(nginx)
<title>Welcome to nginx!</title>

从「通过 PSA」到「真正 Running」，多出来的三步（指定 UID、可写目录、非特权端口）都和 PSA 无关，是镜像本身默认以 root 运行造成的。生产中更常见的做法是直接换用以非 root 用户构建的镜像。

kubectl debug 也要过 PSA

临时调试容器（ephemeral container）同样受检。在这个命名空间里直接 kubectl debug：

$ kubectl -n notes-lab-restricted debug nginx-restricted --image=busybox:1.36 -- sleep 30
Defaulting debug container name to debugger-kdk2g.
Error from server (Forbidden): pods "nginx-restricted" is forbidden: violates PodSecurity "restricted:v1.31": allowPrivilegeEscalation != false (container "debugger-kdk2g" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "debugger-kdk2g" must set securityContext.capabilities.drop=["ALL"])

这里只报了两项，因为 runAsNonRoot 和 seccompProfile 写在 Pod 级，调试容器继承了。加上 --profile=restricted，kubectl 会自动补齐字段：

$ kubectl -n notes-lab-restricted debug nginx-restricted --image=busybox:1.36 --profile=restricted -- sleep 30
Defaulting debug container name to debugger-6jz7d.
$ kubectl -n notes-lab-restricted get pod nginx-restricted -o jsonpath="{.spec.ephemeralContainers[*].securityContext}"
{"allowPrivilegeEscalation":false,"capabilities":{"drop":["ALL"]},"runAsNonRoot":true,"seccompProfile":{"type":"RuntimeDefault"}}

更多用法见 kubectl debug。

Deployment 被接受，Pod 却一个都没有

enforce 只作用于 Pod 本身；对 Deployment、Job 这类带 Pod 模板的工作负载，PSA 只做 warn 和 audit。在 restricted 命名空间里提交一个模板不合规的 Deployment：

$ kubectl -n notes-lab-restricted apply -f deploy-plain.yaml
Warning: would violate PodSecurity "restricted:v1.31": allowPrivilegeEscalation != false (container "nginx" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "nginx" must set securityContext.capabilities.drop=["ALL"]), runAsNonRoot != true (pod or container "nginx" must set securityContext.runAsNonRoot=true), seccompProfile (pod or container "nginx" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
deployment.apps/web created

注意这个命名空间只设了 enforce，没设 warn，Deployment 照样收到了警告。原因在 1.31 源码 api/helpers.go 的 PolicyToEvaluate：没有 warn 标签、而 enforce 比默认的 warn 级别更严时，warn 自动取 enforce 的级别和版本。而 warn 模式本来就作用于工作负载，于是 Deployment 收到了警告。同一个命名空间里直接提交的 Pod 没有警告，是因为请求被拒绝了，前面提到的 if response.Allowed 跳过了 warn。created 之后就安静了，看上去一切正常：

$ kubectl -n notes-lab-restricted get deploy web
NAME   READY   UP-TO-DATE   AVAILABLE   AGE
web    0/2     0            0           14s
$ kubectl -n notes-lab-restricted rollout status deploy/web --timeout=10s
Waiting for deployment "web" rollout to finish: 0 out of 2 new replicas have been updated...
error: timed out waiting for the condition

ReplicaSet 是创建出来了，Pod 却是 0 个。原因在 ReplicaSet 的事件里，不在 Deployment 上：

$ kubectl -n notes-lab-restricted describe rs -l app=web
...
  Warning  FailedCreate  7s               replicaset-controller  Error creating: pods "web-76848fd7c8-2mf5t" is forbidden: violates PodSecurity "restricted:v1.31": allowPrivilegeEscalation != false (container "nginx" must set securityContext.allowPrivilegeEscalation=false), ...
  Warning  FailedCreate  6s               replicaset-controller  Error creating: pods "web-76848fd7c8-d6q4b" is forbidden: violates PodSecurity "restricted:v1.31": ...
  ...
  Warning  FailedCreate  1s (x2 over 4s)  replicaset-controller  (combined from similar events): Error creating: pods "web-76848fd7c8-fshww" is forbidden: ...

7 秒内出现了十来条 FailedCreate，控制器一直在重试。Deployment 的 status 里也能找到线索，ReplicaFailure 条件带着同一段错误：

Progressing=True NewReplicaSetCreated: Created new replica set "web-76848fd7c8"
Available=False MinimumReplicasUnavailable: Deployment does not have minimum availability.
ReplicaFailure=True FailedCreate: pods "web-76848fd7c8-2mf5t" is forbidden: violates PodSecurity "restricted:v1.31": ...

所以 Deployment 一直 0/N、又找不到任何 Pod 时，先 kubectl describe rs 看 FailedCreate。apply 时那条 Warning: 不会让命令失败，输出照样是 created，在 CI 里很容易被忽略。kubectl 有一个全局参数 --warnings-as-errors，按说明会把服务端警告当成错误、以非零退出码结束，可以在流水线里用它把这类清单提前拦下（这次实验没有测这个参数）。

给已有命名空间收紧策略

已经跑着工作负载的命名空间，直接加 enforce: restricted 会怎样？准备一个不带任何 PSA 标签的命名空间，里面放三类违规负载：一个普通 nginx Pod、一个 capabilities.add: ["SYS_ADMIN"] 的 busybox、一个两副本的 nginx Deployment。

先用 --dry-run=server 预演，这一步不会真的改标签：

$ kubectl label --dry-run=server --overwrite ns notes-lab-existing pod-security.kubernetes.io/enforce=baseline
Warning: existing pods in namespace "notes-lab-existing" violate the new PodSecurity enforce level "baseline:latest"
Warning: tool-sysadmin: non-default capabilities
namespace/notes-lab-existing labeled (server dry run)
$ kubectl label --dry-run=server --overwrite ns notes-lab-existing pod-security.kubernetes.io/enforce=restricted
Warning: existing pods in namespace "notes-lab-existing" violate the new PodSecurity enforce level "restricted:latest"
Warning: nginx-plain (and 3 other pods): allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile
namespace/notes-lab-existing labeled (server dry run)

几个值得注意的地方：

  • 没写 enforce-version 时，提示里的版本是 latest；
  • baseline 只点名了加了 SYS_ADMIN 的那个 Pod，其余三个 Pod 已经满足 baseline；
  • restricted 下四个 Pod 的违规类别相同，被合并成一行 nginx-plain (and 3 other pods)。要看清每个 Pod 具体差什么，得逐个 dry-run 提交它们的清单。

真正打标签时顺手钉了 enforce-version=v1.31，所以提示里的版本变成 restricted:v1.31，末尾也没有了 (server dry run)。等 20 秒再看，四个 Pod 都还在：

$ kubectl label --overwrite ns notes-lab-existing pod-security.kubernetes.io/enforce=restricted pod-security.kubernetes.io/enforce-version=v1.31
Warning: existing pods in namespace "notes-lab-existing" violate the new PodSecurity enforce level "restricted:v1.31"
Warning: nginx-plain (and 3 other pods): allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile
namespace/notes-lab-existing labeled
$ kubectl -n notes-lab-existing get pod
NAME                   READY   STATUS    RESTARTS   AGE
nginx-plain            1/1     Running   0          53s
tool-sysadmin          1/1     Running   0          53s
web-76848fd7c8-489hv   1/1     Running   0          52s
web-76848fd7c8-x9qn4   1/1     Running   0          52s

PSA 只在创建和更新时检查，不会驱逐已经在运行的 Pod。问题会在 Pod 被替换时出现。删掉 Deployment 的一个 Pod（模拟节点故障或驱逐）：

$ kubectl -n notes-lab-existing delete pod web-76848fd7c8-489hv
pod "web-76848fd7c8-489hv" deleted
$ kubectl -n notes-lab-existing get deploy web
NAME   READY   UP-TO-DATE   AVAILABLE   AGE
web    1/2     1            1           63s
$ kubectl -n notes-lab-existing get events --field-selector reason=FailedCreate -o custom-columns=TIME:.lastTimestamp,COUNT:.count,MSG:.message
TIME                   COUNT   MSG
2026-10-12T08:01:19Z   1       Error creating: pods "web-76848fd7c8-9jbth" is forbidden: violates PodSecurity "restricted:v1.31": allowPrivilegeEscalation != fa
...
2026-10-12T08:01:24Z   6       (combined from similar events): Error creating: pods "web-76848fd7c8-j7v7b" is forbidden: violates PodSecurity "restricted:v1.31"

副本从 2 掉到 1，补不回来了。这就是「打完标签当时什么都没发生，过几天服务少了副本」的来由：故障出现在下一次节点维护、驱逐或滚动更新时，而不是改标签的那一刻。

已有 Pod 的更新也会受影响，但不是所有更新都检查。按官方文档，元数据更新（改 seccomp、AppArmor 相关注解除外）以及对 activeDeadlineSeconds、tolerations 的更新都豁免；1.31 源码里的 isSignificantPodUpdate 只在容器数量变化、镜像变化或新增临时容器时才重新评估。所以加标签可以，改镜像就不行：

$ kubectl -n notes-lab-existing label pod nginx-plain tier=demo
pod/nginx-plain labeled
$ kubectl -n notes-lab-existing set image pod/nginx-plain nginx=nginx:1.27
error: failed to patch image update to pod template: pods "nginx-plain" is forbidden: violates PodSecurity "restricted:v1.31": allowPrivilegeEscalation != false (container "nginx" must set securityContext.allowPrivilegeEscalation=false), ...

稳妥的顺序是：先只加 warn 和 audit，观察一段时间、改完清单，再用 dry-run 确认没有违规 Pod，最后加 enforce。

版本固定

<mode>-version 把策略固定在某个 Kubernetes 小版本当时的定义上。restricted 的各项检查是逐步加入的，比如 capabilities 必须 drop ALL 从 v1.22 起，runAsUser 不能为 0 从 v1.23 起。拿一个满足其余条件、只是没有 drop ALL 的 Pod 测试：

$ kubectl label --overwrite ns notes-lab-version pod-security.kubernetes.io/enforce-version=v1.21
namespace/notes-lab-version labeled
$ kubectl -n notes-lab-version apply -f nocaps.yaml
pod/nocaps created
$ kubectl -n notes-lab-version delete pod nocaps
pod "nocaps" deleted
$ kubectl label --overwrite ns notes-lab-version pod-security.kubernetes.io/enforce-version=v1.22
namespace/notes-lab-version labeled
$ kubectl -n notes-lab-version apply -f nocaps.yaml
Error from server (Forbidden): error when creating "nocaps.yaml": pods "nocaps" is forbidden: violates PodSecurity "restricted:v1.22": unrestricted capabilities (container "c" must set securityContext.capabilities.drop=["ALL"])

同样是 restricted，钉在 v1.21 时放行，钉在 v1.22 时拒绝。v1.23 的 runAsUser 检查也一样：runAsNonRoot: true 加 runAsUser: 0 这种自相矛盾的 Pod，在 v1.22 下能通过 PSA，然后被 kubelet 以 container's runAsUser breaks non-root policy 拦在 CreateContainerConfigError；把版本改成 v1.23 时，dry-run 会提示 uid0: runAsUser=0，新提交的 Pod 也直接被拒。

用 latest 意味着集群升级后自动用上新加的检查，原本能创建的 Pod 可能在升级后突然被拒；钉住版本则把这件事变成一次主动的、可以先 dry-run 的标签变更。

标签值写错时，Namespace 本身就改不进去：

$ kubectl label --overwrite ns notes-lab-version pod-security.kubernetes.io/enforce-version=1.22
The Namespace "notes-lab-version" is invalid: metadata.labels[pod-security.kubernetes.io/enforce-version]: Invalid value: "1.22": must be "latest" or "v1.x"
$ kubectl label --overwrite ns notes-lab-version pod-security.kubernetes.io/enforce=restricted-typo pod-security.kubernetes.io/enforce-version=v1.21
The Namespace "notes-lab-version" is invalid: metadata.labels[pod-security.kubernetes.io/enforce]: Invalid value: "restricted-typo": must be one of privileged, baseline, restricted

两次都是整条 label 命令失败，同一条命令里合法的 enforce-version=v1.21 也没有生效，之后提交 Pod 时报的仍是 restricted:v1.22。不过高于集群版本的值不会被拒：在这个 v1.31 集群上设置 v1.40 能成功，拒绝信息显示为 restricted:v1.40。PSA 源码 policy/registry.go 会把高于内置最高版本的值截到最高版本（if r.maxVersion.Older(lv.Version) { lv.Version = r.maxVersion }），所以钉一个未来版本实际等于 latest：集群升级后新加的检查会悄悄生效，起不到钉版本的作用。

清理

kubectl delete namespace notes-lab notes-lab-audit notes-lab-restricted notes-lab-existing notes-lab-version

PSA 只管 Pod 字段，管不了谁能创建 Pod（那是 RBAC）、镜像里有什么、Pod 之间能不能通信（那是 NetworkPolicy）。另一个局限是命名空间标签只能整体设置级别，做不到「这个 Deployment 可以例外」；豁免只能在集群级的 AdmissionConfiguration 里按用户、RuntimeClass 或命名空间配置。需要更细的规则时，得换用 ValidatingAdmissionPolicy 或 Kyverno、Gatekeeper 这类策略引擎。
