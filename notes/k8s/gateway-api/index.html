把入口与路由分开

Ingress把入口规则写在一个对象中。Gateway API 将入口能力表达为 GatewayClass 和 Gateway，把 HTTP 匹配与转发规则表达为 HTTPRoute。创建这些 API 对象本身不会接通流量；集群还必须安装支持 Gateway API 的控制器，并具备可访问的数据平面。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico）。Gateway API 控制器是集群里已经装好的 Traefik v3.7.9，它的 Service 是 traefik/traefik（LoadBalancer）。实验放在单独的 notes-lab namespace，跨命名空间的实验再加一个 notes-lab-b。负载均衡 IP 用 <lb-ip> 代替。

先看清控制器接受什么

动手前先只读地看三样东西：CRD 版本、GatewayClass、控制器自己的配置。

kubectl get crd -o 'custom-columns=NAME:.metadata.name,BUNDLE:.metadata.annotations.gateway\.networking\.k8s\.io/bundle-version,CHANNEL:.metadata.annotations.gateway\.networking\.k8s\.io/channel' | grep gateway.networking
kubectl get gatewayclass -o wide
backendtlspolicies.gateway.networking.k8s.io            v1.5.0   standard
gatewayclasses.gateway.networking.k8s.io                v1.5.0   standard
gateways.gateway.networking.k8s.io                      v1.5.0   standard
grpcroutes.gateway.networking.k8s.io                    v1.5.0   standard
httproutes.gateway.networking.k8s.io                    v1.5.0   standard
listenersets.gateway.networking.k8s.io                  v1.5.0   standard
referencegrants.gateway.networking.k8s.io               v1.5.0   standard
tlsroutes.gateway.networking.k8s.io                     v1.5.0   standard

NAME                  CONTROLLER                            ACCEPTED   AGE   DESCRIPTION
cloud-provider-kind   kind.sigs.k8s.io/gateway-controller   True       60d   cloud-provider-kind gateway API
traefik               traefik.io/gateway-controller         True       57d

装的是 v1.5.0 的 Standard channel，没有 TCPRoute、UDPRoute 这类 Experimental 资源。集群里有两个 GatewayClass，gatewayClassName 选哪个，流量就由哪个控制器接管，这里用 traefik。顺带一提，Traefik v3.7 的文档写的是支持 Gateway API v1.6.3，比集群里的 CRD 新一个小版本；下面用到的都是 v1.5 已有的字段，v1.6 新增的功能这次没有测。

关键的是 Traefik 的启动参数：

kubectl -n traefik get deploy traefik -o jsonpath='{range .spec.template.spec.containers[0].args[*]}{@}{"\n"}{end}'
kubectl -n traefik get svc traefik -o jsonpath='{range .spec.ports[*]}{.name} {.port}->{.targetPort}{"\n"}{end}'
--entryPoints.web.address=:8000/tcp
--entryPoints.websecure.address=:8443/tcp
...
--providers.kubernetesgateway
--providers.kubernetesgateway.statusaddress.service.name=traefik
--providers.kubernetesgateway.statusaddress.service.namespace=traefik

web 80->web
websecure 443->websecure

两点信息：kubernetesgateway provider 没有配 namespaces，按文档就是监听所有命名空间，所以在自己的 namespace 里建 Gateway 也会被它处理；HTTP 入口点 web 监听的是容器里的 8000 端口，Service 再把 80 映射过去。后面第一个坑就出在这里。statusaddress.service 则让 Traefik 把这个 Service 的负载均衡地址抄到每个 Gateway 的 status.addresses。

准备后端

两个 Service 分别指向两个 traefik/whoami Deployment，用 --name 让响应里带上自己是谁，后面数流量时一眼就能分清：

apiVersion: apps/v1
kind: Deployment
metadata: {name: web-v1}
spec:
  replicas: 1
  selector: {matchLabels: {app: web, version: v1}}
  template:
    metadata: {labels: {app: web, version: v1}}
    spec:
      containers:
      - name: whoami
        image: traefik/whoami:v1.10.2
        args: ["--name=web-v1"]
        ports: [{containerPort: 80}]
        resources: {requests: {cpu: 10m, memory: 16Mi}, limits: {memory: 32Mi}}
---
apiVersion: v1
kind: Service
metadata: {name: web-v1}
spec:
  selector: {app: web, version: v1}
  ports: [{port: 80, targetPort: 80}]

web-v2 把上面的 v1 全换成 v2 即可。再加一个从集群内部发请求用的 client Pod：

apiVersion: v1
kind: Pod
metadata: {name: client}
spec:
  containers:
  - name: curl
    image: curlimages/curl:latest
    command: ["sleep", "7200"]
    resources: {requests: {cpu: 10m, memory: 16Mi}, limits: {memory: 64Mi}}

三段放进同一个 apps.yaml，用 --- 分隔：

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f apps.yaml
kubectl -n notes-lab wait --for=condition=Ready pod --all --timeout=180s

后面的 Gateway 和 HTTPRoute 都用 kubectl -n notes-lab apply -f <文件> 提交。metadata 里自己写了 namespace 的文件（后文的 ReferenceGrant 和 team-b 路由）直接 kubectl apply -f <文件>，不要加 -n。

Gateway：监听端口要对上入口点

第一版 Gateway 按直觉写了 80 端口：

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: {name: lab-gw}
spec:
  gatewayClassName: traefik
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    hostname: "*.gw.notes.test"
kubectl -n notes-lab get gateway lab-gw
kubectl -n notes-lab get gateway lab-gw -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}---listeners attachedRoutes={.status.listeners[0].attachedRoutes}---{"\n"}{range .status.listeners[*].conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'

（端口为 80 的第一次查询用的是不带 attachedRoutes 的版本，所以下面第一段输出里只有 ---listeners---。）

NAME     CLASS     ADDRESS      PROGRAMMED   AGE
lab-gw   traefik   <lb-ip>                   5s

Accepted=False ListenersNotValid: All Listeners must be valid
---listeners---
Accepted=False PortUnavailable: Cannot find entryPoint for Gateway: no matching entryPoint for port 80 and protocol "HTTP"

Traefik 不会为 Gateway 新开端口，它只会把 listener 挂到端口相同的已有入口点上。这里要写的是入口点的 8000，而不是 Service 对外的 80。值得注意的是 ADDRESS 一栏照样显示了地址：地址来自 statusaddress 配置，Gateway 是否可用跟它无关，要看的是 PROGRAMMED 列，这里是空的。Traefik 日志里也有同一句 ERR Gateway Not Accepted ... no matching entryPoint for port 80。

把 port 改成 8000 后：

NAME     CLASS     ADDRESS      PROGRAMMED   AGE
lab-gw   traefik   <lb-ip>      True         16s

Accepted=True Accepted: Gateway successfully scheduled
Programmed=True Programmed: Gateway successfully scheduled
---listeners attachedRoutes=0---
Accepted=True Accepted: No error found
ResolvedRefs=True ResolvedRefs: No error found
Programmed=True Programmed: No error found

Gateway 有两层条件：Gateway 自身的 Accepted、Programmed，以及每个 listener 各自的 Accepted、ResolvedRefs、Programmed。listener 层的 attachedRoutes 是现在挂上来的路由数，后面排查时很有用。

这个 Gateway 和集群里已有的 traefik/traefik-gateway 共用 8000 这个入口点，Traefik 靠 Host 区分请求。listener 已经限定为通配域名 *.gw.notes.test，下面的路由里仍然写上 hostnames，是为了让每条路由的匹配范围一眼就能看出来。

HTTPRoute：路径和请求头匹配

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: app}
spec:
  parentRefs:
  - name: lab-gw
  hostnames: ["app.gw.notes.test"]
  rules:
  - matches:
    - path: {type: PathPrefix, value: /v2}
    - headers:
      - name: X-Canary
        value: "true"
    backendRefs:
    - name: web-v2
      port: 80
  - matches:
    - path: {type: PathPrefix, value: /}
    backendRefs:
    - name: web-v1
      port: 80

第一条规则下有两个 match，它们是「或」的关系：路径以 /v2 开头，或者带 X-Canary: true，都走 web-v2。同一个 match 里写多个条件才是「且」。

kubectl get httproute 只列出主机名，看不出路由有没有生效，状态要单独取：

kubectl -n notes-lab get httproute app
kubectl -n notes-lab get httproute app -o jsonpath='{range .status.parents[*]}parent={.parentRef.name} controller={.controllerName}{"\n"}{range .conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}{end}'
NAME   HOSTNAMES               AGE
app    ["app.gw.notes.test"]   4s

parent=lab-gw controller=traefik.io/gateway-controller
Accepted=True Accepted:
ResolvedRefs=True ResolvedRefs:

HTTPRoute 的状态按 parent 分组，每个 parent 下各有 Accepted（是否挂上了这个 Gateway）和 ResolvedRefs（backendRefs 是否都能解析）。路由挂上后，Gateway listener 的 attachedRoutes 从 0 变成了 1。

怎么把请求送到 Traefik

status.addresses 里的地址在这个环境里从宿主机连不上：

$ curl -sS -m 5 -H "Host: app.gw.notes.test" http://<lb-ip>/
curl: (7) Failed to connect to <lb-ip> port 80 after 0 ms: Could not connect to server

这个 LoadBalancer IP 从宿主机连不上，原因这次没有追。所以下面换两种方式访问：从集群内的 client Pod 直接请求 traefik.traefik.svc，或者在宿主机上对 Traefik 的 Service 做端口转发。不要把这种地址不通归咎于 HTTPRoute 写错，先确认路由状态都是 True，再单独查网络这一层。

集群内请求：

kubectl -n notes-lab exec client -- curl -s -H 'Host: app.gw.notes.test' http://traefik.traefik.svc.cluster.local/v2/hello

把几种请求的结果放在一起（只保留 whoami 输出里的 Name 等行）：

# Host: app.gw.notes.test，路径 /
Name: web-v1
# 路径 /v2/hello
Name: web-v2
GET /v2/hello HTTP/1.1
# 路径 /，带 X-Canary: true
Name: web-v2
X-Canary: true
# 路径 /，带 X-Canary: yes
Name: web-v1
# 路径 /v2x
Name: web-v1
# Host: other.gw.notes.test（listener 通配能覆盖，但没有路由声明它）
404

两处容易想错的地方：

  • 请求头匹配默认是 Exact，值必须一字不差，yes 不等于 true。
  • PathPrefix: /v2 按路径段匹配，/v2/hello 命中，/v2x 不命中，落到了 / 规则上。规范原文是 /abc、/abc/、/abc/def 都匹配前缀 /abc，/abcd 不匹配。

有一个请求没有返回：从 client 请求 traefik.traefik.svc.cluster.local:8000，curl 加上 -m 5 后报的是 Connection timed out after 5001 milliseconds。8000 是 Traefik 容器的端口，Service 并没有暴露它；Gateway 里写 8000，客户端访问的却是 Service 的 80，两边的端口不是一回事。

宿主机上的端口转发：

kubectl -n traefik port-forward svc/traefik 28471:80
Forwarding from 127.0.0.1:28471 -> 8000
Forwarding from [::1]:28471 -> 8000
$ curl -s -H 'Host: app.gw.notes.test' http://127.0.0.1:28471/v2 | grep Name
Name: web-v2
$ curl -s -H 'Host: app.gw.notes.test' http://127.0.0.1:28471/ | grep Name
Name: web-v1

转发目标显示的是 -> 8000，port-forward 把 Service 的 80 解析成了 Pod 的目标端口，正好印证上面的端口对应关系。

权重分流：数一数到底分了多少

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: split}
spec:
  parentRefs:
  - name: lab-gw
  hostnames: ["split.gw.notes.test"]
  rules:
  - backendRefs:
    - name: web-v1
      port: 80
      weight: 80
    - name: web-v2
      port: 80
      weight: 20

连续发 200 个请求，统计响应来自谁：

kubectl -n notes-lab exec client -- sh -c 'for i in $(seq 1 200); do curl -s -H "Host: split.gw.notes.test" http://traefik.traefik.svc.cluster.local/ | grep ^Name; done | sort | uniq -c'
160 Name: web-v1
 40 Name: web-v2

不多不少正好 160 比 40。再看 20 个请求的先后顺序：

v1 v1 v1 v1 v2 v1 v1 v1 v1 v2 v1 v1 v1 v1 v2 v1 v1 v1 v1 v2

这次单客户端顺序请求、单个 Traefik 副本的测试里，结果表现为固定的 4:1 交替，每 5 个请求里有 1 个去 v2。推测这是 Traefik 加权轮询（WRR）的正常表现，不是随机抽样；多副本、并发请求下会不会这么整齐，没有测。规范本身只要求比例约等于 weight / 所有权重之和，权重是相对值，加起来不必等于 100。

把权重改成 web-v1: 0、web-v2: 1：

kubectl -n notes-lab patch httproute split --type=json -p '[{"op":"replace","path":"/spec/rules/0/backendRefs/0/weight","value":0},{"op":"replace","path":"/spec/rules/0/backendRefs/1/weight","value":1}]'

50 个请求全部到了 web-v2；规范对 0 的定义是这一项不应收到流量。再把 web-v2 也改成 0：

kubectl -n notes-lab patch httproute split --type=json -p '[{"op":"replace","path":"/spec/rules/0/backendRefs/1/weight","value":0}]'
no available server

HTTP 503

此时路由的 Accepted 和 ResolvedRefs 仍然都是 True。从状态上看不出任何问题，这只是一个合法但没有可用后端的配置，排查时要回头看权重。

故障一：backendRef 指向不存在的 Service

新建一条路由 missing，主机名 missing.gw.notes.test，后端写成一个不存在的 web-v3：

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: missing}
spec:
  parentRefs:
  - name: lab-gw
  hostnames: ["missing.gw.notes.test"]
  rules:
  - backendRefs:
    - name: web-v3
      port: 80
Accepted=True Accepted:
ResolvedRefs=False BackendNotFound: Cannot load HTTPBackendRef notes-lab/web-v3: getting service: service "web-v3" not found

HTTP 500

Accepted=True 说明路由已经挂到 Gateway 上，Gateway 的 attachedRoutes 也把它算了进去；问题在后端解析这一步。规范要求：一条规则的 backendRefs 全部无效、且没有过滤器时，匹配到的请求必须返回 500。Traefik 照此返回了空响应体的 500。

用 describe 看也是同样的信息，但最后一行是 Events: <none>：

      Message:               Cannot load HTTPBackendRef notes-lab/web-v3: getting service: service "web-v3" not found
      Observed Generation:   1
      Reason:                BackendNotFound
      Status:                False
      Type:                  ResolvedRefs
    Controller Name:         traefik.io/gateway-controller
...
Events:       <none>

后来补测了一次：端口写错的 Gateway、missing 和正常的 app 路由，describe 的 Events 都是 <none>，kubectl get events 里也只有 Pod、ReplicaSet、Deployment 的事件。至少在这个版本的 Traefik 上，Gateway 和路由的问题只写在 status 和 Traefik 日志里，不产生 Events，习惯看 Events 排错的话，在这里什么也看不到。

和它对照的是 Service 存在、但没有就绪 Pod 的情况。把 web-v2 缩到 0 副本再访问 /v2：

kubectl -n notes-lab scale deploy web-v2 --replicas=0
kubectl -n notes-lab exec client -- curl -s -w '\nHTTP %{http_code}\n' -H 'Host: app.gw.notes.test' http://traefik.traefik.svc.cluster.local/v2
no available server

HTTP 503

状态依旧全是 True。后端没有就绪端点时返回 503，符合规范里 SHOULD 返回 503 的要求。测完恢复副本：

kubectl -n notes-lab scale deploy web-v2 --replicas=1
现象HTTPRoute 状态响应
Service 不存在ResolvedRefs=False / BackendNotFound500，空响应体
跨命名空间缺授权（见下节）ResolvedRefs=False / RefNotPermitted500
Service 无可用端点，或权重全为 0全部 True503 no available server

看到 500 先查路由状态。在 Traefik 上，看到 503 先查后端端点和权重；权重全为 0 时返回 503 是 Traefik 的行为，规范并没有规定这种情况的状态码。

故障二：跨命名空间引用后端，缺 ReferenceGrant

再建一个命名空间 notes-lab-b，部署 web-b：Deployment 和 Service 照 web-v1 的模板改名得到，--name 改成 web-b。

kubectl create namespace notes-lab-b
until kubectl -n notes-lab-b get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab-b apply -f app-b.yaml

然后在 notes-lab 新建路由 xns，主机名 xns.gw.notes.test，后端引用 notes-lab-b 里的 web-b：

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: xns}
spec:
  parentRefs:
  - name: lab-gw
  hostnames: ["xns.gw.notes.test"]
  rules:
  - backendRefs:
    - name: web-b
      namespace: notes-lab-b
      port: 80
Accepted=True Accepted:
ResolvedRefs=False RefNotPermitted: Cannot load HTTPBackendRef core/Service/notes-lab-b/web-b: missing ReferenceGrant

HTTP 500

引用别的命名空间的对象，需要对方命名空间的所有者明确同意。授权对象 ReferenceGrant 要建在被引用的那一边，也就是 notes-lab-b：

apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-lab-routes
  namespace: notes-lab-b
spec:
  from:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    namespace: notes-lab
  to:
  - group: ""
    kind: Service
    name: web-b
ResolvedRefs=True ResolvedRefs:
Name: web-b
GET / HTTP/1.1
HTTP 200

from 只能精确到 group、kind 和 namespace，不能指定某一条路由的名字；to 里可以收窄到某个 Service 名，不写 name 则放行该命名空间的所有 Service。实验里写的是 v1beta1。v1.5.0 的 CRD 同时提供 v1（存储版本仍是 v1beta1），官方文档的示例也已改用 v1，按理写 v1 也能用，但这次没有测。

授权可以随时收回。删掉这个 ReferenceGrant 后，几秒内路由状态变回 ResolvedRefs=False RefNotPermitted，请求也重新返回 500。

故障三：路由没挂上

下面两条路由都能创建成功，kubectl get httproute 里也和正常路由一样列出来，但流量就是到不了：

# 主机名和 listener 的 *.gw.notes.test 不相交
  parentRefs:
  - name: lab-gw
  hostnames: ["app.other.test"]

两者都是 Accepted=False，原因不同：一个是主机名没有交集，一个是 sectionName 找不到同名 listener（我们的 listener 叫 http）。ResolvedRefs 却是 True，后端没有问题。两个主机名的请求都返回 404。此时 Gateway 的 attachedRoutes 是 4（app、split、missing、xns），没有把这两条算进去。另一方面，missing 的后端根本不存在，早在它刚创建时 attachedRoutes 就已经是 3，把它算了进去。所以 attachedRoutes 只反映挂没挂上，不代表这些路由都能正常转发。

allowedRoutes：Gateway 决定谁能挂上来

让 notes-lab-b 里的路由挂到 notes-lab 的 Gateway 上：

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: team-b
  namespace: notes-lab-b
spec:
  parentRefs:
  - name: lab-gw
    namespace: notes-lab
  hostnames: ["b.gw.notes.test"]
  rules:
  - backendRefs:
    - name: web-b
      port: 80
Accepted=False NotAllowedByListeners:
ResolvedRefs=True ResolvedRefs:
404

Gateway 里没写 allowedRoutes，但读回来的 spec 已经被填上了默认值：

{"namespaces":{"from":"Same"}}

默认只允许同一命名空间的路由挂载。这和上一节的 ReferenceGrant 是两回事：ReferenceGrant 管的是「路由能不能引用别处的 Service」，由 Service 一侧授权；allowedRoutes 管的是「路由能不能挂到这个 Gateway」，由 Gateway 一侧决定。

按命名空间标签放行。每个命名空间都自带 kubernetes.io/metadata.name 标签，可以直接拿来选：

allowedRoutes:
  namespaces:
    from: Selector
    selector:
      matchLabels:
        kubernetes.io/metadata.name: notes-lab-b

team-b 立刻变成 Accepted=True，b.gw.notes.test 返回了 web-b。但同时出了一个意外：

# notes-lab 里原来正常的 app 路由
Accepted=False NotAllowedByListeners:
ResolvedRefs=True ResolvedRefs:
404
attachedRoutes=1

from: Selector 只放行选中的命名空间，Gateway 自己所在的命名空间不在其中，也被挡在了外面。原来的 4 条路由一起掉线，attachedRoutes 只剩 1。在共享 Gateway 上收紧或放开 allowedRoutes 时，这一步最容易误伤已有业务。把两个命名空间都写进选择器：

selector:
  matchExpressions:
  - key: kubernetes.io/metadata.name
    operator: In
    values: [notes-lab, notes-lab-b]
attachedRoutes=5
Name: web-v1
Name: web-b

排查顺序

  1. Gateway 的 PROGRAMMED 是否为 True；不是，就看 listener 条件。在 Traefik 上最常见的是 PortUnavailable，listener 端口没有对上入口点。ADDRESS 有值不说明任何问题。
  2. HTTPRoute 每个 parent 的 Accepted。为 False 时看 reason：NotAllowedByListeners 查 Gateway 的 allowedRoutes，NoMatchingListenerHostname 查主机名，NoMatchingParent 查 sectionName 和 port。
  3. ResolvedRefs。BackendNotFound 查 Service 名和命名空间，RefNotPermitted 去被引用的命名空间里补 ReferenceGrant。
  4. 状态全是 True 仍返回 503，查后端端点和权重。
  5. 最后才是网络：请求打到了哪个地址和端口，Host 头写对没有。

这次实验中 Traefik 没有为 Gateway 和路由产生 Events，上面这些信息都在 status 里，用 -o yaml 或 jsonpath 看，不要只看 describe 的末尾。

清理

kubectl delete namespace notes-lab notes-lab-b

Gateway、HTTPRoute、ReferenceGrant 都是命名空间级对象，随命名空间一起删除；GatewayClass 是集群级的，属于控制器安装的一部分，实验不要动它。Traefik 自带的中间件可以挂在路由上做改写和鉴权，见 Traefik Middleware。
