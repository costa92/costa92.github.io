控制器如何维持期望状态

Kubernetes 控制器反复比较对象的 spec 与集群当前状态，并通过 API 发起调整。Deployment 声明期望副本数，ReplicaSet 负责维持对应 Pod 数量。删除一个受管理的 Pod，只会删除那个实例；控制器随后创建替代 Pod。这是「调谐循环」最直观的例子。

几件相关的事前面已经测过，这篇不重复：删一个受管 Pod 马上补回、直接改受管 Pod 的镜像控制器视而不见、generation 与 observedGeneration 的关系，见概念和术语；ownerReferences、改标签让 Pod 脱离或被收养、级联删除，见 API 对象与控制器关系；控制器管理器在哪里运行、靠 Lease 选主，见集群组件。

这一篇只盯着循环本身：它什么时候被唤醒、一次调谐读的是什么、失败后多久重试、人和控制器同时改一个对象时谁说了算。

下文输出来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，Calico CNI，kubectl 客户端 v1.30.0）。实验放在单独的 namespace 里，命令和输出中统一写作 notes-lab；控制器管理器的 Pod 名简化为 kube-controller-manager-control-plane。文中引用的源码都是 v1.31.0 标签下的版本。

准备：一个 Deployment，再加一道配额保险

保存为 web.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      terminationGracePeriodSeconds: 5
      containers:
        - name: nginx
          image: nginx:alpine
          resources:
            requests:
              cpu: 10m
              memory: 16Mi

后面有一个实验要把副本数瞬间改到 10。为了让这个 namespace 无论如何不超过 6 个 Pod，先放一个配额：

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab create quota cap6 --hard=pods=6
kubectl -n notes-lab apply -f web.yaml
kubectl -n notes-lab rollout status deploy/web --timeout=120s

这道保险本身后来也成了实验的一部分：控制器想多建 Pod 时撞上它，会留下清楚的痕迹。

怎么看见控制器的每一次调谐

kind 用 kubeadm 起的控制器管理器没调日志级别，但 ReplicaSet 控制器每处理完一次就打一行 Finished syncing（replica_set.go 第 679 行，用的是不带级别的 logger.Info），时间精确到微秒，还带耗时：

kubectl -n kube-system logs kube-controller-manager-control-plane --since=1m | grep 'notes-lab/web-'
I1013 10:41:14.473934       1 replica_set.go:679] "Finished syncing" logger="replicaset-controller" kind="ReplicaSet" key="notes-lab/web-78b89f5d44" duration="36.493782ms"
I1013 10:41:14.490313       1 replica_set.go:679] "Finished syncing" logger="replicaset-controller" kind="ReplicaSet" key="notes-lab/web-78b89f5d44" duration="16.339986ms"
I1013 10:41:14.490371       1 replica_set.go:679] "Finished syncing" logger="replicaset-controller" kind="ReplicaSet" key="notes-lab/web-78b89f5d44" duration="32.562µs"

同步失败时，紧跟着还有一行 E... 开头的 Unhandled Error。这一行太长，后文用一个小脚本只保留时间、sync/ERROR 和耗时或错误原因，保存为 rslog.sh，参数是起始时间和截止时刻：

kubectl -n kube-system logs kube-controller-manager-control-plane --since-time="$1" \
 | grep 'notes-lab/web-' \
 | awk -v until="$2" '{t=$2; if (substr(t,1,8)>until) exit; if ($1 ~ /^E/) {match($0,/pods \\"[^\\]*\\" is forbidden: exceeded quota: [a-z0-9]*/); print t, "ERROR", substr($0,RSTART,RLENGTH)} else {match($0,/duration="[^"]*"/); print t, "sync", substr($0,RSTART+10,RLENGTH-11)}}'

托管集群通常看不到控制器管理器的日志，那时只能靠下文用到的 --watch 加时间戳和 Events。

删一个 Pod，控制器被叫醒了 11 次

10:41:14 删掉一个 Pod，这一秒多里 ReplicaSet 控制器的同步记录：

$ bash rslog.sh 2026-10-13T10:41:10Z 10:41:16
10:41:14.473934 sync 36.493782ms
10:41:14.490313 sync 16.339986ms
10:41:14.490371 sync 32.562µs
10:41:14.501670 sync 51.736µs
10:41:14.598483 sync 41.525µs
10:41:14.696340 sync 38.494µs
10:41:14.914595 sync 55.764µs
10:41:15.410525 sync 7.862069ms
10:41:15.410591 sync 34.461µs
10:41:15.425615 sync 58.033µs
10:41:15.431570 sync 28.403µs

一次删除换来 11 次同步。旧 Pod 进入 Terminating、新 Pod 被创建、被调度、容器启动、变成 Ready、旧 Pod 最终消失，每一次 Pod 对象变化都会把所属 ReplicaSet 的 key 放进工作队列。耗时几十毫秒的那几次真正调了 API（第一次创建替补 Pod，后面几次写 status）；几十微秒的那些只是重新数了一遍，发现没有差额，状态也没变，什么都没做。

这就是调谐的基本形态：事件只负责把控制器叫醒，叫醒之后它不关心是什么事件，只拿缓存里的当前状态和 spec 比。下面几个实验分别从不同角度验证这句话，以及它的边界。

水平触发：看状态，不看事件

「水平触发（level-triggered）」的意思是控制器对「现在是什么样」作出反应，而不是对「刚发生了什么」作出反应。一个推论常被这样表述：如果副本数在很短时间内从 3 改到 10 又改到 2，控制器只会看到最终的 2，不会先建 7 个再删 8 个。实测下来，这句话只对了一半。

12 毫秒内连改两次，控制器照样按 10 动手

为了让两次修改尽量贴近，用 kubectl proxy 加一个 curl 进程连发两个 PATCH，复用同一条连接：

kubectl proxy --port=18081 &
U=http://127.0.0.1:18081/apis/apps/v1/namespaces/notes-lab/deployments/web
H='Content-Type: application/merge-patch+json'
curl -s -o /dev/null -w 'patch1 replicas=10 done %{time_total}s\n' -X PATCH -H "$H" -d '{"spec":{"replicas":10}}' $U \
  --next -s -o /dev/null -w 'patch2 replicas=2  done %{time_total}s\n' -X PATCH -H "$H" -d '{"spec":{"replicas":2}}' $U
10:42:59.511
patch1 replicas=10 done 0.014647s
patch2 replicas=2  done 0.012036s
10:42:59.545

另开三个 --watch 分别记录 Deployment、ReplicaSet 和 Pod，每行前面加上本地收到的时间。保存为 tw.sh，第一个参数是输出文件，其余原样传给 kubectl get：

out=$1; shift
kubectl -n notes-lab get "$@" --watch 2>&1 \
  | while IFS= read -r line; do printf '%s %s\n' "$(date -u +%T.%N | cut -c1-12)" "$line"; done > "$out"

Pod 那一路额外加了 --output-watch-events，所以每行带 ADDED/MODIFIED/DELETED。（--output-watch-events 和 custom-columns 一起用时列会错位，所以 Deployment 和 ReplicaSet 两路没加。）三路分别是：

bash tw.sh dep.txt deploy web -o custom-columns=GEN:.metadata.generation,OBS:.status.observedGeneration,SPEC:.spec.replicas,CUR:.status.replicas &
bash tw.sh rs.txt rs -o custom-columns=NAME:.metadata.name,SPEC:.spec.replicas,CUR:.status.replicas,READY:.status.readyReplicas &
bash tw.sh pods.txt pod -l app=web --output-watch-events &

后台跑的这几个进程，结束时按自己记下的 PID 逐个 kill，不要按命令行模式批量结束 kubectl，同一台机器上可能还有别人的 watch。

Deployment 一侧（列依次是 generation、observedGeneration、spec.replicas、status.replicas）：

10:42:56.541 4     4     3      3
10:42:59.533 5     4     10     3
10:42:59.543 6     4     2      3
10:42:59.579 6     6     2      3

Deployment 的 observedGeneration 从 4 直接跳到 6，从没出现过 5。但这不等于第 5 版被跳过了：下面会看到，它在第 5 版写入后的 10 毫秒之内已经把 ReplicaSet 改成了 10。也就是说，它处理了第 5 版，只是没有记下 observedGeneration=5。推测是处理第 5 版的那一轮最后写 status 时，手里的 resourceVersion 已经被第 6 版的写入淘汰，更新冲突失败，下一轮处理第 6 版时才写成功；这次没有抓到冲突的日志。ReplicaSet 一侧，spec.replicas 先变成 10，紧接着又变成 2：

第一次同步耗时 90 毫秒，倒推它大约在 10:42:59.540 开始，读到的正是 replicas: 10。它在这一次里建出 3 个 Pod，然后撞上 cap6。等它结束，spec.replicas 早就是 2 了，下一次同步（10:42:59.631 开始）读到 2，删掉 4 个：

10:42:59.668 MODIFIED   web-78b89f5d44-w4q6n   0/1     Terminating         0          0s

三个刚建的 Pod 活了不到 0.1 秒，还顺带删掉了一个跑了 11 秒的老 Pod nw58j，因为目标是 2 而原来有 3 个。之前用两条 kubectl scale 前后执行（间隔是两次 kubectl 启动的时间），结果一模一样：建 3 个、4 次 FailedCreate、删 4 个。

所以「水平触发」保证的是：下一次调谐一定从最新状态出发，中间值造成的偏差会被纠正；它不保证中间值不被执行。一次同步开始时读的是缓存快照，同步过程中 spec 再怎么变，这一轮也照旧做完。没有 cap6，这一轮会真的去建 7 个 Pod。

合并发生在哪里

合并确实存在，规则在 client-go 工作队列的 Add 里（util/workqueue/queue.go），分两种情况：

  • key 还在队列里排队、没被取走时，再次 Add 直接去重，队列里始终只有一份；
  • key 已经出队、正在处理时，再次 Add 只给它记一个 dirty 标记，不会重复入队；处理完调用 Done 时发现有标记，再入队一次。不管处理期间来了多少事件，结果都只是「之后再同步一次」。同一个 key 也不会被两个 worker 同时处理。

上面那 90 毫秒里，3 个新 Pod 各自产生了好几次更新，ReplicaSet 的 spec 也从 10 变成了 2，可接下来只跑了一次同步，而不是十几次，这是第二种情况。中间值 10 之所以被执行，是因为 spec.replicas 变成 2 的时候，key 已经出队，正在按 10 处理；这次 Add 只留下一个 dirty 标记。如果 key 出队得再晚一点，在变成 2 时还在排队，出队后读到的就会是 2，10 就真被跳过了。能不能跳过中间值，取决于事件落在哪个时间窗口里，不是一个可以依赖的保证。

换句话说，事件会被合并成「需要再看一次」这一个标记，标记背后的内容由下一次同步现读。这才是水平触发在实现上的样子。

暂停的 Deployment：三次改动，只有一次发布

想让中间状态真正被跳过，靠的不是手速，而是让控制器在这段时间里不对模板变化动手，spec.paused 就是这个开关。上一个实验把副本数留在了 2，先恢复到 3（这一步当时没有保存输出，属于补记）：

kubectl -n notes-lab scale deploy web --replicas=3
kubectl -n notes-lab rollout status deploy/web
kubectl -n notes-lab rollout pause deploy/web
kubectl -n notes-lab set image deploy/web nginx=nginx:1.27; sleep 3
kubectl -n notes-lab set env deploy/web MODE=a; sleep 3
kubectl -n notes-lab set env deploy/web MODE=b
$ kubectl -n notes-lab get deploy web -o jsonpath='{.metadata.generation} {.status.observedGeneration} {.spec.paused}{"\n"}'
11 11 true
$ kubectl -n notes-lab get deploy web -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'
Available=True MinimumReplicasAvailable: Deployment has minimum availability.
Progressing=Unknown DeploymentPaused: Deployment is paused
$ kubectl -n notes-lab get rs
NAME             DESIRED   CURRENT   READY   AGE
web-78b89f5d44   3         3         3       3m43s

observedGeneration 追上了 generation：控制器每一版都「看到」了，只是选择不创建新 ReplicaSet。syncDeployment 里遇到 d.Spec.Paused 就只走 sync()，它只处理扩缩和清理旧 ReplicaSet，不做滚动（pkg/controller/deployment/deployment_controller.go、sync.go）。所以暂停期间扩缩照常生效：

$ kubectl -n notes-lab scale deploy web --replicas=4; sleep 3; kubectl -n notes-lab get rs; kubectl -n notes-lab get deploy web
deployment.apps/web scaled
NAME             DESIRED   CURRENT   READY   AGE
web-78b89f5d44   4         4         4       4m3s
NAME   READY   UP-TO-DATE   AVAILABLE   AGE
web    4/4     0            4           4m3s

UP-TO-DATE 是 0：4 个 Pod 全是旧模板。这时候用 rollout status 等发布完成会一直等下去，而且不会提示 Deployment 被暂停了：

$ timeout 8 kubectl -n notes-lab rollout status deploy/web; echo exit=$?
Waiting for deployment "web" rollout to finish: 0 out of 3 new replicas have been updated...
exit=124

（这条输出是扩到 4 之前抓的，所以写的是 3。）CI 里如果有人在发布前忘了 resume，症状就是这里的超时，要看的是 Progressing 条件里的 DeploymentPaused。

恢复之后只出现了一个新 ReplicaSet，模板是三次修改叠加后的结果：

$ kubectl -n notes-lab rollout resume deploy/web
deployment.apps/web resumed

和控制器对着干

直接缩 ReplicaSet：13 毫秒被改回，但已经删了 2 个

Deployment 那篇用 Events 看到过这件事，当时只有秒级精度。用 watch 重看一次：

$ kubectl -n notes-lab scale rs/web-b77b9f77 --replicas=1
10:45:23.992
replicaset.apps/web-b77b9f77 scaled

  2. 按 Deployment 模板算出哈希，准备创建同名 ReplicaSet，结果名字已被占用，而占用者的模板不同。这就是 sync.go 里处理的哈希冲突：collisionCount 加 1，用新的计数重新算哈希，得到 web-59646575b8。

为什么不是失败 1 次就停，也不是 7 次全打出去？manageReplicas 把创建分批交给 slowStartBatch：第一批 1 个，整批成功就翻倍，2、4、8……；某一批里有任何失败，等这一批全部返回后放弃剩下的（pkg/controller/replicaset/replica_set.go，初始批大小 SlowStartInitialBatchSize = 1 在 pkg/controller/controller_utils.go）。差 7 个时：第 1 批 1 个成功，第 2 批 2 个成功，第 3 批 4 个并发发出，这时配额已满，4 个全部被拒，剩下 0 个。正好对上 3 成功 4 失败。

源码注释说明了用意：如果同步开始时配额就已经满了，每次同步注定失败的请求数是 min(N, 1)，也就是 1 个，避免成百个 Pod 一起去撞配额，顺带避免事件刷屏。另一个上限是 BurstReplicas = 500，单次同步最多建或删 500 个，这个规模在小集群里碰不到。

下一节换一个更紧的配额，看到的是另一种组合：差 5 个、只剩 2 个名额时，第 1 批 1 个成功，第 2 批 1 成功 1 失败，于是这次同步只有 1 次 FailedCreate；之后每次重试都从批大小 1 开始，每次恰好失败 1 次。

4 条 SuccessfulCreate 加 21 次 FailedCreate，正好 25 次，和令牌桶容量一致；11:11:32 建出的 ctrv8、s8989、tchxn 三个 Pod 都没有 SuccessfulCreate 事件，同一时段控制器日志里这个 ReplicaSet 失败了 31 次，也只记下 21 次。

所以排查长时间卡住的控制器，Events 不是完整记录：没有新事件不代表没在失败，甚至不代表没有创建成功。ReplicaSet 的 status.conditions、对象本身和控制器日志更可信。

控制器立刻知道缺 5 个（概念和术语里测过，Terminating 的 Pod 不计入副本数），但配额不这么算：5 个 Terminating 加 1 个新的就是 6，第一时间只补上了 fs2zf，接下来 0.5 秒里同步失败了 19 次。旧 Pod 的状态变成 Completed 之后才陆续腾出名额：3 个 Completed，紧接着补 3 个；再 2 个 Completed，补最后 1 个。这和 v1.31 配额计数的规则一致（pkg/quota/v1/evaluator/core/pods.go 的 QuotaV1Pod）：phase 为 Succeeded 或 Failed 的 Pod 不计入；带 deletionTimestamp 的 Pod，要等到 deletionTimestamp 再过一个宽限期才不计入。deletionTimestamp 本身已经是「删除时刻加宽限期」，所以后一条最多要等约 2 倍宽限期。这里旧 Pod 先走到了终止阶段，所以没等满。这个例子里容器 1 秒内就退出了，只耽误了 0.6 秒；如果应用要用满 30 秒的优雅终止期，配额又刚好卡着副本数，滚动更新或批量删除时就会出现这样一段「控制器想补、配额不让」的空窗。配额的写法见资源策略。

没有事件时，控制器多久看一次

如果调谐完全依赖事件，事件丢了怎么办？教科书式的回答是 informer 的定期 resync：每隔一段时间把缓存里的所有对象当作「更新」再派发一遍。在这个集群上，这个间隔长得多：

  • 控制器管理器的启动参数里没有 --min-resync-period，默认值是 12 小时（staging/src/k8s.io/controller-manager/config/v1alpha1/defaults.go）。
  • 共享 informer 的实际 resync 周期是这个值乘以 1 到 2 之间的随机数，也就是 12 到 24 小时，故意错开以免所有控制器同时 LIST（cmd/kube-controller-manager/app/controllermanager.go 的 ResyncPeriod）。
  • resync 不重新请求 API Server，只是把本地缓存重放一遍。重放的 Pod 更新会被 updatePod 丢掉（resourceVersion 没变就直接返回，replica_set.go 第 430 行附近）；重放的 ReplicaSet 更新则不做这个判断，updateRS 每次都入队，注释里专门写了理由：让「创建 Pod 失败过、又没有 Pod 可以触发事件」的 ReplicaSet 不至于永远停住。也就是说，上一节那种卡在退避里的 ReplicaSet，最坏情况下还有这道 12 到 24 小时的兜底，只是远比 1000 秒的退避上限晚，实际起作用的是退避。

实验里能直接看到的是反面：10:48:01.271 到 10:50:45.124 之间，这个 ReplicaSet 一次同步都没有，控制器既不轮询，也没有短周期 resync；它被叫醒，只能因为事件或者退避到期。12 小时的 resync 本身这次没有观察到。

那 watch 断了、删除事件丢了怎么办？ReplicaSet 控制器靠的是另一套机制，「expectations」：它记下自己发出了几个创建、哪些删除，在 informer 看到对应事件前不会再动手，以免重复创建；如果一直等不到，5 分钟后（ExpectationsTimeout，controller_utils.go）视为过期。过期只是让下一次同步不再被它挡住，SatisfiedExpectations 返回 true，它本身不会把 key 放进队列，还得靠某个事件或退避到期来触发。前面「修好配额等了 5 分 14 秒」恰好也是 5 分钟出头，但那是退避的 327.68 秒，和这个超时无关：那次失败发生在创建请求被拒绝时，控制器已经把没建成的 Pod 从 expectations 里减掉了。再加上 informer 自身断线后会重新 LIST，状态还是会被找回来。这部分这次没有制造出来，属于读源码得到的推测。

排查顺序

副本数不对、或者改了 Deployment 迟迟没反应时：

  1. kubectl get deploy 看 generation 和 observedGeneration：不相等说明 Deployment 控制器还没处理到这一版；相等再往下看。
  2. spec.paused 是不是 true，Progressing 条件是不是 DeploymentPaused。暂停时扩缩照常，模板变化不发布，rollout status 会一直等。
  3. ReplicaSet 的 DESIRED 和 CURRENT 差多少，status.conditions 里有没有 ReplicaFailure。缺的 Pod 根本不存在时，原因在 ReplicaSet 上，不在 Pod 上。
  4. Events 里找 FailedCreate，但不要因为没有新事件就认为没在失败：同一对象的事件有限流，长时间的故障后期往往一条都不记。
  5. 原因已经修好但副本不补，多半是卡在指数退避里。等最多 1000 秒，或者对 ReplicaSet 做一次无害的更新（加个注解）把它叫醒。
  6. 有人手工改过 ReplicaSet？status.collisionCount 不为空、修订号莫名多出一个，都是线索。

清理

kubectl delete namespace notes-lab
kubectl get namespace notes-lab
