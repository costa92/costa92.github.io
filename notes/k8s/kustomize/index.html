Kustomize 环境配置

同一应用在开发和生产环境通常只差副本数、镜像标签、资源限制和几项配置。Kustomize 从一组基础清单（base）出发，每个环境写一个 overlay 描述差异，渲染出最终清单，不需要复制整份 Deployment。kubectl 内置了它：kubectl kustomize <目录> 只渲染，kubectl apply -k <目录> 渲染后直接提交。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18），实验放在单独的 notes-lab namespace。机器上有两个 Kustomize：kubectl v1.30.0 内置的 v5.0.4，以及单独安装的 kustomize 命令 v4.5.4。大部分渲染结果两者逐字相同，不同的地方会单独指出。

目录和清单

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kustom-demo/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
├── exp/              # 每个对照实验一个子目录，如 smp-typo、json-index、nohash
│   └── <实验名>/kustomization.yaml   # 都以 resources: [../../base] 引用 base
└── overlays/
    ├── dev/
    │   └── kustomization.yaml
    └── prod/
        ├── kustomization.yaml
        └── resources-patch.yaml

base 里的 Deployment 故意放了两个容器（nginx 和一个 sidecar），后面演示补丁怎么作用在容器列表上：

# base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
          envFrom:
            - configMapRef:
                name: web-config
          resources:
            requests:
              cpu: 10m
              memory: 32Mi
        - name: sidecar
          image: busybox:1.36
          command: ["sh", "-c", "sleep 3600"]
          resources:
            requests:
              cpu: 10m
              memory: 16Mi

base/service.yaml 是一个按 app: web 选择 Pod 的 ClusterIP Service，端口 80。base/kustomization.yaml 把两者列为资源，并用生成器产生 Deployment 引用的 ConfigMap：

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
configMapGenerator:
  - name: web-config
    literals:
      - LOG_LEVEL=info

两个 overlay：

# overlays/dev/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
namePrefix: dev-
commonLabels:
  env: dev
configMapGenerator:
  - name: web-config
    behavior: merge
    literals:
      - LOG_LEVEL=debug
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
namePrefix: prod-
commonLabels:
  env: prod
replicas:
  - name: web
    count: 3
images:
  - name: nginx
    newTag: alpine
patches:
  - path: resources-patch.yaml
# overlays/prod/resources-patch.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  template:
    spec:
      containers:
        - name: nginx
          resources:
            limits:
              memory: 128Mi

从这份 diff 能读出几件事：

  • namePrefix 改了所有对象的名字，也改了 Deployment 里对 ConfigMap 的引用（configMapRef），但没有改 app: web 这个标签和选择器，后面会看到这带来的问题。
  • commonLabels 不只加到 metadata.labels，还加进了 Service 的 selector、Deployment 的 spec.selector.matchLabels 和 Pod 模板标签。官方文档对这个字段的描述就是「labels to add to all resources and selectors」。
  • prod 的 ConfigMap 后缀 hf678c7m2b 和 base 一模一样。它的数据和 base 相同，只是多了前缀和 env: prod 标签，后缀没变；dev 改了数据，后缀就变成了 47668c6k28。从这组结果看，后缀跟着数据走，namePrefix 和 commonLabels 不影响它。
  • 补丁只给 nginx 容器加了 limits，sidecar 原样保留，下一节展开。

同一个 prod overlay（newTag: alpine 的最终版本）用独立的 kustomize build（v4.5.4）渲染，与 kubectl kustomize（v5.0.4）的输出 diff 结果为空。

补丁：按名字合并 vs 按下标定位

patches 字段下可以写两种补丁：像上面那样写成一个「半截」Kubernetes 对象，是策略合并补丁（strategic merge patch，SMP）；写成 op/path/value 列表，是 JSON 6902 补丁。两者在处理容器列表时差别很大。

SMP：容器列表按 name 合并

SMP 知道 Pod 的 containers 列表以 name 为合并键，所以 prod 的补丁只写了 name: nginx 和一个 limits，渲染结果里 nginx 的其余字段和整个 sidecar 都还在（见上面的 diff）。

方便的同时也有坑：名字写错不会报错。把补丁里的 nginx 拼成 ngnix：

      containers:
      - name: ngnix
        resources:
          limits:
            memory: 128Mi
      - envFrom:
        - configMapRef:
            name: web-config-hf678c7m2b
        image: nginx:1.27
        name: nginx
...

Kustomize 找不到同名容器，就把补丁当成一个新容器插到列表开头，渲染照样成功，退出码 0。直到提交给 API Server 才暴露：

kubectl -n notes-lab apply -k exp/smp-typo --dry-run=server
configmap/web-config-hf678c7m2b created (server dry run)
service/web created (server dry run)
The Deployment "web" is invalid: spec.template.spec.containers[0].image: Required value

报错说的是 containers[0] 缺镜像，和「容器名写错」看起来毫不相关。看到这种报错，先去渲染结果里数一下容器个数。

要用 SMP 删掉一个列表元素，用 $patch: delete：

patches:
  - patch: |-
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: web
      spec:
        template:
          spec:
            containers:
              - name: sidecar
                $patch: delete

渲染结果里只剩 nginx 一个容器。

JSON 6902：路径里的下标和整列表替换

JSON 6902 补丁不认识合并键，只认路径。用 replace 替换整个 containers：

patches:
  - target:
      kind: Deployment
      name: web
    patch: |-
      - op: replace
        path: /spec/template/spec/containers
        value:
          - name: nginx
            image: nginx:1.27
            resources:
              limits:
                memory: 128Mi
spec:
  containers:
  - image: nginx:1.27
    name: nginx
    resources:
      limits:
        memory: 128Mi

sidecar 没了，nginx 原来的 ports、envFrom、requests 也全没了。replace 就是整体替换，本意只是加个 limit 的话，这样写会把列表里其他内容一起抹掉。

用下标定位单个元素则是另一个坑。想给 nginx 加 limit，却以为它是第二个容器：

- op: add
  path: /spec/template/spec/containers/1/resources/limits
  value:
    memory: 128Mi
- command:
  - sh
  - -c
  - sleep 3600
  image: busybox:1.36
  name: sidecar
  resources:
    limits:
      memory: 128Mi
    requests:
      cpu: 10m
      memory: 16Mi

limit 加到了 sidecar 上，同样没有任何报错。base 里容器顺序一变，按下标写的补丁就会悄悄改到别的容器上。JSON 6902 有一个 test 操作可以当保险：先断言下标 1 的容器名是 nginx，不成立就整个失败：

- op: test
  path: /spec/template/spec/containers/1/name
  value: nginx
- op: add
  path: /spec/template/spec/containers/1/resources/limits
  value:
    memory: 128Mi
error: testing value /spec/template/spec/containers/1/name failed: test failed

v4.5.4 的报错只是开头从 error: 变成 Error:，内容相同。对 Deployment 这类内置类型，改容器字段优先用 SMP；只有 SMP 表达不了的操作（比如改列表里某个没有合并键的元素）才用 JSON 6902，并且带上 test。

旧字段的弃用提示

老教程里常见 patchesStrategicMerge: 和 patchesJson6902:。用 patchesStrategicMerge 引用同一个补丁文件，kubectl 内置的 v5.0.4 会提示：

# Warning: 'patchesStrategicMerge' is deprecated. Please use 'patches' instead. Run 'kustomize edit fix' to update your Kustomization automatically.

v4.5.4 渲染同一目录没有任何提示，退出码同样是 0。这条警告走的是标准错误：把标准输出重定向到 /dev/null 后它照样打印，而 2>/dev/null 时渲染结果第一行就是 apiVersion: v1，所以 kubectl kustomize ... > out.yaml 不会把警告混进清单。commonLabels 其实从 v5.0.0 起也已弃用（见 kubectl.docs.kubernetes.io 的 commonLabels 页面；上游较新的源码注释为「Use the Labels field instead」，较新版本渲染时会打印 'commonLabels' is deprecated. Please use 'labels' instead.），但这次用的 v5.0.4 没有打印这条提示，不能拿「没警告」当作还能放心用的依据。

常见错误：补丁目标找不到

overlay 里写了 namePrefix: dev-，补丁的 metadata.name 很容易顺手写成加了前缀的 dev-web：

namePrefix: dev-
patches:
  - patch: |-
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: dev-web
      spec:
        replicas: 2
error: no matches for Id Deployment.v1.apps/dev-web.[noNs]; failed to find unique target for patch Deployment.v1.apps/dev-web.[noNs]

两个版本报的是同一句话（v4.5.4 开头是 Error:）。Id 的格式是 类型.版本.组/名字.[命名空间]，[noNs] 表示没有命名空间。补丁匹配的是变换前的名字，也就是 base 里的 web；把补丁改回 name: web 就能渲染。把补丁的 apiVersion 写成 apps/v1beta1 也是同一句报错，只是 Id 变成 Deployment.v1beta1.apps/web.[noNs]；逐段对照 Id 就能找出是哪一段不匹配。base 对象带 namespace 而补丁没写的情况这次没有测，推测会落在 Id 的最后一段。

configMapGenerator：改数据就触发滚动更新

把 dev 部署上去：

kubectl -n notes-lab apply -k kustom-demo/overlays/dev
kubectl -n notes-lab rollout status deploy/dev-web --timeout=120s
kubectl -n notes-lab exec deploy/dev-web -c nginx -- printenv LOG_LEVEL

service/dev-web created
deployment.apps/dev-web created
...

debug

然后把 dev overlay 里的 LOG_LEVEL=debug 改成 warn，先 kubectl diff -k 看会变什么（只保留了有意义的行）：

-            name: dev-web-config-47668c6k28
+            name: dev-web-config-dfk4bdbtkk

+  LOG_LEVEL: warn

数据一变，生成的是一个新名字的 ConfigMap；Deployment 的 Pod 模板里引用的名字跟着变，模板变了，Deployment 控制器就会发起滚动更新。记录时间：

旧 ConfigMap 不会被删掉：

NAME                                 DESIRED   CURRENT   READY   AGE
replicaset.apps/dev-web-5c4444b99d   0         0         0       20s
replicaset.apps/dev-web-75c9457dfb   1         1         1       8s

NAME                                  DATA   AGE
configmap/dev-web-config-47668c6k28   1      21s

这其实是好事：旧 ReplicaSet 还引用着旧 ConfigMap，回滚时 Pod 能拿回旧配置。代价是每改一次数据就留下一个 ConfigMap，需要定期清理。kubectl apply 本身不会删除清单里已经不存在的对象，见 kubectl 批量清单管理。

关掉哈希后缀会怎样

对照组：另建一个 overlay，namePrefix: nohash-，加上

generatorOptions:
  disableNameSuffixHash: true

部署后同样把 LOG_LEVEL 从 debug 改成 warn 再 apply：

configmap/nohash-web-config configured
service/nohash-web unchanged
deployment.apps/nohash-web unchanged

ConfigMap 被原地更新，Deployment unchanged，没有新的 ReplicaSet。逐个 Pod 看环境变量：

pod/dev-web-75c9457dfb-zkpcm warn
pod/nohash-web-cdb74c45b-5lhpv debug

nohash-web 的 Pod 仍然是 debug：通过 envFrom 注入的环境变量只在容器启动时读取一次，ConfigMap 改了，正在运行的容器不会感知。要生效只能手动 kubectl rollout restart。这正是哈希后缀存在的理由，官方文档的说法是「This ensures that a new ConfigMap or Secret is generated when the contents are changed」。ConfigMap 以卷挂载时的更新行为另有规律，见 Namespace、ConfigMap 与 Secret。

namePrefix 不碰选择器：两个应用互相串台

上面这个对照实验顺带撞上了一个更隐蔽的问题。最初我用的是 kubectl exec deploy/nohash-web -- printenv LOG_LEVEL，它输出了 warn，看起来像是配置已经生效。实际上：

NAME                         READY   STATUS    RESTARTS   AGE   APP   ENV
dev-web-75c9457dfb-zkpcm     2/2     Running   0          43s   web   dev
nohash-web-cdb74c45b-5lhpv   2/2     Running   0          23s   web

nohash overlay 没写 commonLabels，它的 Deployment 和 Service 选择器就是 base 里的 app=web，而 dev 的 Pod 也带着 app=web。kubectl exec deploy/nohash-web 按 Deployment 的选择器挑 Pod，挑中的是 dev 的 Pod。Service 也一样：

NAME               SVC      PODS
dev-web-gvltd      <none>   dev-web-75c9457dfb-zkpcm
nohash-web-xbkmk   <none>   dev-web-75c9457dfb-zkpcm,nohash-web-cdb74c45b-5lhpv

nohash-web 这个 Service 的 EndpointSlice 里同时有两个应用的 Pod，流量会被分到 dev 那边去。namePrefix 只改名字和名字引用，标签和选择器原封不动。同一个 namespace 里从同一个 base 部署多份时，必须让每一份的选择器不同。本文 dev overlay 用 commonLabels 做到了这一点（dev 的选择器是 app=web,env=dev，所以 dev 的 Service 没有串进 nohash 的 Pod）；新写的 kustomization 用 labels 加 includeSelectors: true 达到同样效果，它会同时加到选择器和 Pod 模板上。

commonLabels 与不可变的 selector

commonLabels 会进选择器，带来的另一面是：对已经存在的 Deployment 再加一个 commonLabels，apply 会失败。在 dev overlay 里加一行 team: web：

kubectl -n notes-lab apply -k kustom-demo/overlays/dev
configmap/dev-web-config-dfk4bdbtkk configured
service/dev-web configured
The Deployment "dev-web" is invalid: spec.selector: Invalid value: v1.LabelSelector{MatchLabels:map[string]string{"app":"web", "env":"dev", "team":"web"}, MatchExpressions:[]v1.LabelSelectorRequirement(nil)}: field is immutable

apps/v1 的 Deployment 创建后 spec.selector 不能改。更糟的是这次 apply 只失败了一半：kubectl apply -k 把渲染出的对象逐个提交，不是一个事务，某个对象被拒绝时，前面已经成功的对象不会回滚。所以 ConfigMap 和 Service 已经更新，Deployment 被 API Server 拒绝、保持原样。看 Service：

{"app":"web","env":"dev","team":"web"}
null

Service 的选择器已经要求 team=web，而现有 Pod 没有这个标签（Deployment 没更新成功），EndpointSlice 里一个端点都没有，这个 Service 从这一刻起不再转发任何流量。坏掉的是 Service，不是 Deployment，生产环境里这就是一次故障。

只想给对象加标签、不碰选择器，用 labels 字段：

labels:
  - pairs:
      team: web
    includeSelectors: false
    includeTemplates: true

渲染结果里 team: web 出现在各对象的 metadata.labels 和 Pod 模板标签里，Service 的 selector 和 Deployment 的 matchLabels 仍是 app: web, env: dev。apply 后 Service 选择器恢复成 {"app":"web","env":"dev"}，EndpointSlice 重新有了端点（只改模板标签，Deployment 做了一次正常的滚动更新）。

这里两个版本有差别：includeTemplates 是 v4.5.4 不认识的字段，独立的 kustomize build 直接报错：

Error: json: unknown field "includeTemplates"

去掉这个字段后，两个版本渲染同一份 kustomization 的完整输出 diff 为空，但 team: web 只加在 Deployment 的 metadata.labels 上，不进 Pod 模板。如果团队里有人用旧版 kustomize 二进制，同一份 kustomization 可能在他那里渲染失败。

出了这种事，先从 overlay 里撤掉这个标签再 apply 一次，Service 的选择器就恢复了，Deployment 本来就没变。只有确实需要换选择器时，才删掉 Deployment 重建（会中断服务），选择器没有原地修改的办法。

images：按镜像名字面匹配

prod overlay 里的 images 把 nginx:1.27 换成了 nginx:alpine，部署后核对：

NAME       READY   UP-TO-DATE   AVAILABLE   AGE     CONTAINERS      IMAGES                      SELECTOR
dev-web    1/1     1            1           2m23s   nginx,sidecar   nginx:1.27,busybox:1.36     app=web,env=dev
prod-web   3/3     3            3           12s     nginx,sidecar   nginx:alpine,busybox:1.36   app=web,env=prod
prod-web-566867d7bb-bq65l nginx:alpine 128Mi
prod-web-566867d7bb-h9mmf nginx:alpine 128Mi
prod-web-566867d7bb-v9s6m nginx:alpine 128Mi

name 匹配的是镜像名本身，不看标签。但「同一个镜像」的不同写法 Kustomize 不会当成一回事。准备一个 Pod，四个容器用四种写法：

initContainers:
  - name: init
    image: docker.io/library/nginx:1.27
containers:
  - name: a
    image: nginx:1.27
  - name: b
    image: nginx
  - name: c
    image: my-registry.example.com/nginx:1.27
images:
  - name: nginx
    newName: registry.example.com/mirror/nginx
    newTag: "1.27.3"
- image: registry.example.com/mirror/nginx:1.27.3
  name: a
- image: registry.example.com/mirror/nginx:1.27.3
  name: b
- image: my-registry.example.com/nginx:1.27
  name: c
- image: docker.io/library/nginx:1.27
  name: init

nginx:1.27 和不带标签的 nginx 都被替换了；另一个仓库的 my-registry.example.com/nginx 没被误伤；但 docker.io/library/nginx:1.27 也没被替换，尽管容器运行时把它和 nginx:1.27 当成同一个镜像。再加一条 name: docker.io/library/nginx 之后，init 容器也换成了镜像仓库地址，说明 images 同样覆盖 initContainers，问题只出在名字的写法上。base 里镜像写法不统一时，替换完要 grep 一遍渲染结果里所有 image:。

清理

kubectl -n notes-lab delete -k kustom-demo/overlays/dev
kubectl -n notes-lab delete -k kustom-demo/overlays/prod
kubectl delete namespace notes-lab

delete -k 按当前渲染结果删除，生成器之前留下的旧名字 ConfigMap 不在其中。重新建一次 dev，把 LOG_LEVEL 从 warn 改回 debug 再 apply，留下两个 ConfigMap，然后执行 delete -k：

configmap "dev-web-config-47668c6k28" deleted
service "dev-web" deleted
deployment.apps "dev-web" deleted
NAME                                  DATA   AGE
configmap/dev-web-config-dfk4bdbtkk   1      23s
configmap/kube-root-ca.crt            1      23s

旧的 dfk4bdbtkk 留了下来，需要另外删，或者直接删整个 namespace。

几条经验：

  • 提交前先 kubectl kustomize 或 kubectl diff -k，SMP 写错容器名、JSON 补丁下标指错，渲染阶段都不会报错。
  • 同一 namespace 从同一 base 部署多份，用 labels 加 includeSelectors: true 区分选择器（commonLabels 已弃用）；Deployment 一旦建好，就别再往进选择器的标签里加东西，后加的标签设 includeSelectors: false。
  • 保留 ConfigMap 的哈希后缀，让配置变更走正常的滚动更新和回滚。

多人或多个工具同时改同一对象时的字段归属问题，见 Server-Side Apply 字段所有权。Kustomize 和 Helm 都能组织清单：环境之间只差少量字段时 Kustomize 更直接，需要参数化模板和版本化发布时再考虑 Helm。
