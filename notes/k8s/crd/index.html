CRD 与自定义资源

CustomResourceDefinition（CRD）让 API Server 接受一种新的资源类型。创建 CRD 后，可以像管理内置资源一样用 kubectl get、apply、delete 管理它的实例。但 CRD 本身不执行任何业务逻辑：它只负责注册 API、校验字段、存储对象，真正去「做事」的是另外编写的控制器，见 Operator 模式和调谐循环。这一篇只看 API Server 这一侧：一个 CRD 到底帮你挡住了什么、放过了什么。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，kubectl 客户端 v1.30.0），实例放在单独的 notes-lab namespace 里。CRD 是集群级资源，删除 CRD 会连带删除该类型的全部实例，所以只在自己有完整权限的实验集群里做，组名也选一个不会和别人冲突的 notes-lab.example。

定义一个 Widget

一个 CRD 里把这篇要测的东西都放进去：必填字段、枚举、正则、默认值、CEL 规则、不可变字段、一段允许任意内容的子树，再加上 status 子资源和自定义列。保存为 widget-crd.yaml：

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: widgets.notes-lab.example
spec:
  group: notes-lab.example
  scope: Namespaced
  names:
    plural: widgets
    singular: widget
    kind: Widget
    shortNames: [wdg]
  versions:
    - name: v1
      served: true
      storage: true
      subresources:
        status: {}
      additionalPrinterColumns:
        - name: Color
          type: string
          jsonPath: .spec.color
        - name: Replicas
          type: integer
          jsonPath: .spec.replicas
        - name: Phase
          type: string
          jsonPath: .status.phase
        - name: Age
          type: date
          jsonPath: .metadata.creationTimestamp
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: [color]
              x-kubernetes-validations:
                - rule: "self.replicas <= self.maxReplicas"
                  message: "replicas must not exceed maxReplicas"
              properties:
                color:
                  type: string
                  enum: [red, green, blue]
                owner:
                  type: string
                  pattern: '^[a-z][a-z0-9-]{1,15}$'
                replicas:
                  type: integer
                  minimum: 0
                  default: 1
                maxReplicas:
                  type: integer
                  default: 3
                storageSize:
                  type: string
                  x-kubernetes-validations:
                    - rule: "self == oldSelf"
                      message: "storageSize is immutable"
                labels:
                  type: object
                  x-kubernetes-preserve-unknown-fields: true
            status:
              type: object
              properties:
                phase:
                  type: string
                observedGeneration:
                  type: integer
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl apply -f widget-crd.yaml
kubectl wait --for=condition=Established crd/widgets.notes-lab.example --timeout=60s
kubectl api-resources --api-group=notes-lab.example
customresourcedefinition.apiextensions.k8s.io/widgets.notes-lab.example created
customresourcedefinition.apiextensions.k8s.io/widgets.notes-lab.example condition met
NAME      SHORTNAMES   APIVERSION             NAMESPACED   KIND
widgets   wdg          notes-lab.example/v1   true         Widget

CRD 自己的 conditions 里，NamesAccepted 表示复数名、短名没有和已有资源冲突，Established 表示 API 已经可以服务：

NamesAccepted=True NoConflicts
Established=True InitialNamesAccepted

Established 之后，explain 还要等几秒

wait 一返回，紧接着执行 kubectl explain，第一次失败了：

$ kubectl -n notes-lab explain widget.spec
error: couldn't find resource for "notes-lab.example/v1, Resource=widgets"

4 秒后再执行就正常了：

FIELD: spec <Object>


DESCRIPTION:
    <empty>
FIELDS:
  color	<string> -required-
  enum: red, green, blue
    <no description>

  labels	<Object>
    <no description>

  maxReplicas	<integer>
    <no description>

  owner	<string>
    <no description>

  replicas	<integer>
    <no description>

  storageSize	<string>
    <no description>

Established 说明 REST 端点能用了，而 explain 读的是 API Server 发布的 OpenAPI 文档。推测是这份文档异步更新，比 REST 端点晚了几秒；同一时刻 api-resources 已经能列出 widgets。所以脚本里如果紧跟着跑 explain 或依赖 OpenAPI 的客户端校验，要留出重试。另一个可见的细节是满屏的 <no description>：schema 里每个字段都可以写 description，explain 就是团队成员看这个 API 的文档，值得补上。

schema 校验：报错原文

先创建一个合法实例 demo，保存为 w-ok.yaml：

apiVersion: notes-lab.example/v1
kind: Widget
metadata:
  name: demo
spec:
  color: red
  owner: team-a
  storageSize: 1Gi
kubectl -n notes-lab apply -f w-ok.yaml

再故意准备三个不合法的版本 w-bad1.yaml～w-bad3.yaml（结构同上，只改 spec），逐个 kubectl -n notes-lab apply -f。w-bad1.yaml 缺必填字段 color，spec 里只有 owner: team-a：

The Widget "bad1" is invalid: 
* spec.color: Required value
* <nil>: Invalid value: "null": some validation rules were not checked because the object was invalid; correct the existing errors to complete validation

w-bad2.yaml 一次写错三处（color: purple、owner: Team_A、replicas: -1）：

The Widget "bad2" is invalid: 
* spec.color: Unsupported value: "purple": supported values: "red", "green", "blue"
* spec.owner: Invalid value: "Team_A": spec.owner in body should match '^[a-z][a-z0-9-]{1,15}$'
* spec.replicas: Invalid value: -1: spec.replicas in body should be greater than or equal to 0
* <nil>: Invalid value: "null": some validation rules were not checked because the object was invalid; correct the existing errors to complete validation

w-bad3.yaml 写了 color: blue，但把整数写成了字符串 replicas: "2"：

The Widget "bad3" is invalid: 
* spec.replicas: Invalid value: "string": spec.replicas in body must be of type integer: "string"
* <nil>: Invalid value: "null": some validation rules were not checked because the object was invalid; correct the existing errors to complete validation

几点值得留意：

  • OpenAPI 层面的错误会一次全部列出，不用改一处提交一次。
  • 每条结尾那句 some validation rules were not checked 说的是 CEL 规则（x-kubernetes-validations）：基础 schema 不通过时，CEL 规则根本没有执行。修完这些错误后再提交，可能还会冒出新的 CEL 错误。
  • YAML 里给整数加了引号就是字符串，CRD 不会帮你转换类型。

默认值

demo 提交时只写了三个字段，kubectl -n notes-lab get widget demo -o yaml 读回来是这样：

spec:
  color: red
  maxReplicas: 3
  owner: team-a
  replicas: 1
  storageSize: 1Gi

replicas 和 maxReplicas 被补上了 schema 里的 default。上面那条 self.replicas <= self.maxReplicas 规则也因此能正常执行：两个字段都有默认值，规则里直接访问不会出错。没有默认值时会怎样，后面 CEL 一节会看到。

按官方文档，默认值在三个时机应用：请求进入 API Server 时、从 etcd 读出时、变更型准入 webhook 修改对象之后。从 etcd 读出时补的默认值不会自动写回 etcd，要等下一次更新才持久化。这意味着给已有 CRD 新增一个带默认值的字段，旧对象读出来也会带上它。

未知字段：strict、warn 和 false

把 color 拼成 colour，同时在允许任意内容的 labels 下面塞一些 schema 里没有的嵌套字段，保存为 w-prune.yaml：

apiVersion: notes-lab.example/v1
kind: Widget
metadata:
  name: prune
spec:
  color: green
  colour: green
  labels:
    team: a
    nested:
      anything: goes

kubectl -n notes-lab apply -f w-prune.yaml，kubectl 1.30 默认的 --validate=strict 直接拒绝：

Error from server (BadRequest): error when creating "w-prune.yaml": Widget in version "v1" cannot be handled as a Widget: strict decoding error: unknown field "spec.colour"

换成 --validate=warn，只打一行警告，对象照样创建：

$ kubectl -n notes-lab apply -f w-prune.yaml --validate=warn
Warning: unknown field "spec.colour"
widget.notes-lab.example/prune created

读回来，colour 已经不见了，labels 下面的任意内容原样保留：

{"color":"green","labels":{"nested":{"anything":"goes"},"team":"a"},"maxReplicas":3,"replicas":1}

删掉重建，用 --validate=false，结果相同，而且连警告都没有：

widget.notes-lab.example "prune" deleted
widget.notes-lab.example/prune created
{"color":"green","labels":{"nested":{"anything":"goes"},"team":"a"},"maxReplicas":3,"replicas":1}

这就是 pruning：apiextensions.k8s.io/v1 的 CRD 默认剪掉 schema 里没声明的字段，只有标了 x-kubernetes-preserve-unknown-fields: true 的子树例外。剪枝是服务端行为，strict 只是让服务端在剪之前先报错。所以如果你的 CI 或某个工具用的是 --validate=false，拼错的字段会被静默丢弃，对象创建成功，控制器读到的是默认值，从现象上看就是「配置没生效」。按官方文档，请求里不指定 fieldValidation 时服务端默认是 Warn，只在响应头里带一条警告；很多程序化客户端（比如用 client-go 写的控制器）不会把这条警告展示出来，效果同样是静默剪掉。

还有一个容易误导的痕迹：客户端 apply 的 last-applied-configuration 注解里，colour 还在：

{"apiVersion":"notes-lab.example/v1","kind":"Widget","metadata":{"annotations":{},"name":"prune","namespace":"notes-lab"},"spec":{"color":"green","colour":"green","labels":{"nested":{"anything":"goes"},"team":"a"}}}

看注解会以为字段生效了，判断字段是否真的存下来，要看对象本身的 spec。x-kubernetes-preserve-unknown-fields 则要慎用：那棵子树里不会再有任何类型或拼写检查。

status 子资源与 generation

CRD 里开了 subresources.status，status 就有了独立的写入入口。下面每一步之后都读一次 generation、resourceVersion 和 status。

起点（此前对 spec 做过几次修改，generation 已经是 4）：

gen=4 rv=10945711 status=

通过主资源写 status，kubectl 回报 no change，什么都没写进去：

$ kubectl -n notes-lab patch widget demo --type=merge -p '{"status":{"phase":"Ready"}}'
widget.notes-lab.example/demo patched (no change)

通过 --subresource=status 写，resourceVersion 变了，generation 不变：

$ kubectl -n notes-lab patch widget demo --subresource=status --type=merge -p '{"status":{"phase":"Ready","observedGeneration":3}}'
widget.notes-lab.example/demo patched
gen=4 rv=10945826 status={"observedGeneration":3,"phase":"Ready"}

反过来，通过 status 子资源夹带一个 spec 修改，patched 照样打印，但只有 status 生效，color 还是 red：

$ kubectl -n notes-lab patch widget demo --subresource=status --type=merge -p '{"spec":{"color":"blue"},"status":{"phase":"Degraded"}}'
widget.notes-lab.example/demo patched
gen=4 rv=10945827 status={"observedGeneration":3,"phase":"Degraded"}
red

从主资源改 spec，generation 才加一；只改 label，generation 不变：

$ kubectl -n notes-lab patch widget demo --type=merge -p '{"spec":{"color":"blue"}}'
gen=5 rv=10945828 status={"observedGeneration":3,"phase":"Degraded"}
$ kubectl -n notes-lab patch widget demo --type=merge -p '{"metadata":{"labels":{"tier":"demo"}}}'
gen=5 rv=10945829 status={"observedGeneration":3,"phase":"Degraded"}

这正是控制器需要的分工：用户只能改 spec，控制器只写 status，互不覆盖；按官方文档，generation 对 .metadata 和 .status 以外的所有变化递增，在这个 CRD 里就是 spec 变化，控制器处理完把 status.observedGeneration 写成当前 generation，外部就能用 observedGeneration == generation 判断「最新的期望已经被处理过」。上面 status 里的值是手写模拟的，此时 3 ≠ 5，说明控制器还没跟上。把它补成 5：

gen=5 rv=10945913 status={"observedGeneration":5,"phase":"Ready"}

两个容易踩的点：一是对 status 的错误写入不会报错，主资源会静默忽略 status、status 子资源会静默忽略 spec，只看 patched 会误以为改成功了；二是给控制器配 RBAC 时，status 是单独的资源 widgets/status，只给 widgets 的 update 权限写不了 status。

自定义列

additionalPrinterColumns 决定 kubectl get 显示哪些列，Phase 列直接读 .status.phase，没有 status 的对象显示为空：

NAME    COLOR   REPLICAS   PHASE   AGE
demo    blue    5          Ready   51s
prune   green   1                  27s

没配自定义列时，kubectl get 只有 NAME 和 AGE 两列，后面的 Gadget 就是例子。列也可以设 priority: 1，那样只在 -o wide 时出现。

CEL 校验规则

x-kubernetes-validations 用 CEL 表达式表达 OpenAPI 写不出来的约束，比如字段之间的关系。demo 的 maxReplicas 默认是 3，把 replicas 改成 5：

The Widget "demo" is invalid: spec: Invalid value: "object": replicas must not exceed maxReplicas

两个字段一起改就通过。错误挂在 spec 上，因为规则写在 spec 这一层，self 就是 spec 对象。

写错的规则在 CRD 创建时就被拒绝

另建一个最小的 Gadget CRD（gadget-crd.yaml，下面是最终改对后的完整版本）：

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: gadgets.notes-lab.example
spec:
  group: notes-lab.example
  scope: Namespaced
  names: {plural: gadgets, singular: gadget, kind: Gadget}
  versions:
    - name: v1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              x-kubernetes-validations:
                - rule: "!has(self.min) || !has(self.max) || self.min <= self.max"
              properties:
                min: {type: integer}
                max: {type: integer}

第一次故意把规则写成 self.min <= self.mx，再 kubectl apply -f gadget-crd.yaml：

The CustomResourceDefinition "gadgets.notes-lab.example" is invalid: spec.validation.openAPIV3Schema.properties[spec].x-kubernetes-validations[0].rule: Invalid value: apiextensions.ValidationRule{Rule:"self.min <= self.mx", Message:"", MessageExpression:"", Reason:(*apiextensions.FieldValueErrorReason)(nil), FieldPath:"", OptionalOldSelf:(*bool)(nil)}: compilation failed: ERROR: <input>:1:17: undefined field 'mx'
 | self.min <= self.mx
 | ................^

CEL 规则在 CRD 写入时就按 schema 做类型检查，引用不存在的字段会被直接指出位置。

可选字段要先 has()

把规则改成 self.min <= self.max 重新 apply，再提交一个只有 min、没有 max 的对象：

printf "apiVersion: notes-lab.example/v1\nkind: Gadget\nmetadata:\n  name: g1\nspec:\n  min: 1\n" | kubectl -n notes-lab apply -f -
The Gadget "g1" is invalid: spec: Invalid value: "object": no such key: max evaluating rule: self.min <= self.max

编译能过，运行时却失败：max 是可选字段且没有默认值，对象里不存在它。Widget 那条规则没出这个问题，是因为两个字段都有默认值。可选字段的规则要先判断是否存在：

- rule: "!has(self.min) || !has(self.max) || self.min <= self.max"

改完以后只写 min 能创建，min: 5, max: 2 仍被拒绝：

printf "apiVersion: notes-lab.example/v1\nkind: Gadget\nmetadata:\n  name: g2\nspec:\n  min: 5\n  max: 2\n" | kubectl -n notes-lab apply -f -
gadget.notes-lab.example/g1 created
The Gadget "g2" is invalid: spec: Invalid value: "object": failed rule: !has(self.min) || !has(self.max) || self.min <= self.max

这条规则没写 message，违反时报错就直接是 failed rule: <表达式>，对使用者不太友好，正式的 CRD 最好都写上。

转换规则 oldSelf：拦得住修改，拦不住删除

规则里引用了 oldSelf 就是转换规则，比较更新前后的值。storageSize 上的 self == oldSelf 意在让它不可变，试着改：

The Widget "demo" is invalid: spec.storageSize: Invalid value: "string": storageSize is immutable

但先把字段删掉，再写一个新值，两步都成功了：

$ kubectl -n notes-lab patch widget demo --type=merge -p '{"spec":{"storageSize":null}}'
widget.notes-lab.example/demo patched
$ kubectl -n notes-lab patch widget demo --type=merge -p '{"spec":{"storageSize":"5Gi"}}'
widget.notes-lab.example/demo patched

1Gi 绕一圈变成了 5Gi，所谓的不可变形同虚设。原因是转换规则只在旧值和新值都存在时才执行：删除字段时没有新值，重新设置时没有旧值，两次都跳过了。官方文档的做法是在父对象上再加一条规则，禁止删除已经设置过的字段：

spec:
  x-kubernetes-validations:
    - rule: "self.replicas <= self.maxReplicas"
      message: "replicas must not exceed maxReplicas"
    - rule: "!has(oldSelf.storageSize) || has(self.storageSize)"
      message: "storageSize cannot be removed once set"

更新 CRD 后，删除和修改都被拦住：

The Widget "demo" is invalid: spec: Invalid value: "object": storageSize cannot be removed once set
The Widget "demo" is invalid: spec.storageSize: Invalid value: "string": storageSize is immutable

这条规则同样引用了 oldSelf，创建时不会执行，所以新建一个带 storageSize: 2Gi 的 fresh 不受影响，正常创建。如果业务上要求字段「创建时必须给出、之后不能变」，还要在 required 里列上它。另一种写法是在规则上设 optionalOldSelf: true，让转换规则在没有旧值时也执行（oldSelf 变成 CEL 的 optional 类型）；按官方文档，这个字段依赖下面要讲的校验棘轮特性，没开启时 CRD API 里没有它。本文没有实测这种写法。

收紧 schema 后，旧对象怎么办

demo 此时是 blue。把枚举改成只允许 [red, green] 再应用 CRD，旧对象读出来没有变化：

NAME   COLOR   REPLICAS   PHASE   AGE
demo   blue    5          Ready   84s

修改它的其他字段也没被拒绝，哪怕请求里原样带着 color: blue：

$ kubectl -n notes-lab patch widget demo --type=merge -p '{"spec":{"replicas":4}}'
widget.notes-lab.example/demo patched
$ kubectl -n notes-lab patch widget demo --type=merge -p '{"spec":{"color":"blue","owner":"team-b"}}'
widget.notes-lab.example/demo patched
{"color":"blue","maxReplicas":5,"owner":"team-b","replicas":4,"storageSize":"5Gi"}

而新建一个 blue 的对象会被拒绝：

* spec.color: Unsupported value: "blue": supported values: "red", "green"

这是校验棘轮（validation ratcheting）：更新时，没有变化的非法值不再报错，只有新写入或被修改的值要满足新 schema。按官方文档，这个特性 v1.30 起默认开启，v1.33 GA。官方文档也列了例外，比如引用 oldSelf 的转换规则从不走棘轮，修改 required 列表引起的错误也不走棘轮（这两点本文没有实测）。棘轮让收紧 schema 不会让存量对象一下子全都无法更新，但也意味着存量的非法数据会一直留着，API Server 不会帮你迁移。要清理，得自己找出这些对象逐个改掉。

删除 CRD 时，实例去哪了

给 demo 加一个没有任何控制器负责的 finalizer，然后删除 CRD，不等待：

kubectl -n notes-lab patch widget demo --type=merge -p '{"metadata":{"finalizers":["notes-lab.example/cleanup"]}}'
kubectl delete crd widgets.notes-lab.example --wait=false

5 秒后，CRD 还在，多了一个 Terminating condition：

deletionTimestamp=2026-10-12T07:50:07Z
NamesAccepted=True NoConflicts: no conflicts found
Established=True InitialNamesAccepted: the initial names have been accepted
Terminating=True InstanceDeletionInProgress: CustomResource deletion is in progress

没有 finalizer 的 fresh 和 prune 已经被删掉了，只剩 demo，它带着 deletionTimestamp 等 finalizer 被移除：

NAME   COLOR   REPLICAS   PHASE   AGE
demo   blue    4          Ready   101s
2026-10-12T07:50:07Z ["notes-lab.example/cleanup"]

这期间想再创建一个 Widget：

Error from server (MethodNotAllowed): error when creating "STDIN": create not allowed while custom resource definition is terminating

CRD 删除前，它的 finalizers 是空的；删除之后才出现 customresourcecleanup.apiextensions.k8s.io，由它负责先删完所有实例再放行 CRD。手动移除 demo 的 finalizer 后，4 秒内 CRD 和对象都消失了，资源类型也随之不存在：

Error from server (NotFound): Unable to list "notes-lab.example/v1, Resource=widgets": the server could not find the requested resource (get widgets.notes-lab.example)

现实里，这个 finalizer 通常属于某个 Operator。如果先卸载了 Operator 再删 CRD，就会停在这里：CRD 一直 Terminating，实例一直等一个永远不会来的清理。正确顺序是先删实例、等控制器清理完，再卸载控制器和 CRD。手动移除 finalizer 能解开僵局，但控制器本该清理的外部资源也就没人管了。

重建 CRD，数据不会回来

另一个 Gadget CRD 下有一个实例 g1。删除 CRD（没有 finalizer，0.24 秒就返回了），立刻用同一份 YAML 重建：

$ kubectl delete crd gadgets.notes-lab.example
customresourcedefinition.apiextensions.k8s.io "gadgets.notes-lab.example" deleted
$ kubectl apply -f gadget-crd.yaml
customresourcedefinition.apiextensions.k8s.io/gadgets.notes-lab.example created

kubectl -n notes-lab get gadgets 返回 No resources found。删 CRD 就是删数据，kubectl delete -f 一个包含 CRD 的目录、Helm 卸载一个带 CRD 的 chart 时都要想清楚这一点。

排查速查

现象原因
no matches for kind "Widget" in version "notes-lab.example/v2" / ensure CRDs are installed firstCRD 没装，或这个版本没有声明/served: false
explain 报 couldn't find resource，但 api-resources 已能列出推测是 OpenAPI 发布有几秒延迟
strict decoding error: unknown field字段拼错或 schema 没声明；--validate=false 时会被静默剪掉
some validation rules were not checked基础 schema 有错，CEL 规则还没执行
no such key: xxx evaluating ruleCEL 访问了不存在的可选字段，先用 has()
status 写入后没变化，patched (no change)开了 status 子资源，要用 --subresource=status
CRD 长时间 Terminating，InstanceDeletionInProgress有实例的 finalizer 没人处理

只靠 CRD 做不到的事

整个实验里，demo 的 status 都是手写的，replicas 改成 5 也不会多出任何 Pod。CRD 能做的是让非法的期望进不来、让 spec 和 status 各归其主；根据 spec 创建资源、回写 status、在删除时清理外部资源，都是控制器的事。

控制器怎么写、怎么用 observedGeneration 和 finalizer，接着看 Operator 模式；控制器为什么要做成反复对比期望与现状的循环，见调谐循环。

清理

kubectl delete crd widgets.notes-lab.example gadgets.notes-lab.example --ignore-not-found
kubectl get crd | grep notes-lab   # 应无输出
kubectl delete namespace notes-lab
