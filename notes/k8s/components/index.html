Kubernetes 集群组件

集群通常由控制平面与工作节点构成。kubectl 向 API Server 提交对象；控制器把 Deployment 展开成 Pod；调度器为新 Pod 选择节点；节点上的 kubelet 请求容器运行时启动容器；kube-proxy 把 Service 翻译成节点上的转发规则。这些组件之间不直接互相调用，都只和 API Server 打交道，各自监听自己关心的对象，干完活再把结果写回去。

位置组件职责
控制平面kube-apiserver处理 API 请求，做认证、鉴权、准入，是唯一直接读写 etcd 的组件
控制平面etcd保存集群数据，需要备份与访问保护
控制平面kube-scheduler为还没有 nodeName 的 Pod 选择节点
控制平面kube-controller-manager运行 Deployment、ReplicaSet、Node 等控制器，协调实际与期望状态
工作节点kubelet使分配到本节点的 Pod 按规格运行并上报状态，也负责静态 Pod
工作节点容器运行时通过 CRI 运行容器，例如 containerd
工作节点kube-proxy在使用 kube-proxy 的集群中维护 Service 转发规则

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），实验放在单独的 notes-lab namespace 里。为便于阅读，节点名简化成了 control-plane、worker、worker2，各类 IP 用 <pod-ip>、<cluster-ip>、<apiserver-ip> 之类的占位符代替。kind 的节点是 Docker 容器，所以文中用 docker exec <节点> ... 进入节点；在虚拟机或物理机上，换成 SSH 登录节点执行同样的命令即可。

调度器和控制器管理器靠 Lease 选主

--leader-elect=true 表示同一时刻只有一个实例真正干活，即使控制平面有多台。谁在干活记录在 kube-system 的 Lease 里：

这和 kube-scheduler 的默认参数一致：--leader-elect-lease-duration 15s、--leader-elect-renew-deadline 10s、--leader-elect-retry-period 2s。TRANSITIONS 是领导权换手的次数，单控制平面的集群里，换手只可能是同一台机器上的进程重启后重新抢锁。

这个集群的 kube-scheduler 重启了 183 次、kube-controller-manager 重启了 224 次，换手次数（177、215）和重启次数基本对得上。查上一个实例怎么退出的：

控制器管理器的上一次退出也一样，最后一行是 "leaderelection lost"，退出码都是 1。这不是程序崩溃，而是设计如此：在 renew-deadline（10 秒）内续不上租约，组件就主动退出，避免出现两个实例同时调度、同时操作对象的情况；退出后 kubelet 把静态 Pod 重新拉起，控制平面节点的 kubelet 日志里能看到 back-off 10s restarting failed container=kube-scheduler。续约失败的直接原因是请求 API Server 超时（Client.Timeout exceeded）；为什么 API Server 当时响应不过来，这次没有直接测到，推测和这台机器磁盘慢、etcd 写入延迟高有关。所以看到这两个组件重启次数很高，先查 --previous 日志里有没有 leaderelection lost，有的话该去查 API Server 和 etcd，而不是调度器本身。

节点的心跳同样是 Lease，放在 kube-node-lease 里，每个节点一个。连续查 worker 的 Lease：

kube-proxy：Service 变成每个节点上的 iptables 规则

这个集群的 kube-proxy 是 iptables 模式（kube-system/kube-proxy ConfigMap 里 mode: iptables）。给 Deployment 建一个 Service，然后去 worker2 上看规则：

kubectl -n notes-lab expose deploy web --port=80

-A KUBE-SEP-C3WCY5MRIKW4KZX5 -p tcp -m comment --comment "notes-lab/web" -m tcp -j DNAT --to-destination <pod-ip-2>:80

后端地址来自 EndpointSlice。所以 Service 不通、而 iptables 里找不到对应的 SEP 时，先查 EndpointSlice 里有没有 ready 的端点，见 Service。

按事件来源定位故障

下面故意制造几种故障。思路都一样：看最后一条事件是哪个组件发的，问题就在那个组件负责的阶段，或者在它下一个本该出现却没出现的组件那里。

调度器：FailedScheduling

Pod 要求一个不存在的节点标签：

apiVersion: v1
kind: Pod
metadata:
  name: pick-node
spec:
  nodeSelector:
    notes-lab.io/disk: ssd
  containers:
    - name: nginx
      image: nginx:alpine
      resources:
        requests:
          cpu: 20m
          memory: 32Mi
$ kubectl -n notes-lab get pod pick-node -o wide
NAME        READY   STATUS    RESTARTS   AGE   IP       NODE     NOMINATED NODE   READINESS GATES
pick-node   0/1     Pending   0          8s    <none>   <none>   <none>           <none>
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  8s    default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) didn't match Pod's node affinity/selector. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

NODE 为 <none>、事件来自 default-scheduler，说明卡在调度阶段，kubelet 还没参与。消息逐个节点说明了淘汰原因：控制平面有污点，两个 worker 不匹配 nodeSelector。同样的信息也写在 Pod 的 PodScheduled 条件里（"reason":"Unschedulable","status":"False"）。最后一句 preemption 是说即使驱逐低优先级 Pod 也腾不出合适的节点。

06:06:25.827 给 worker2 打上标签：

kubectl label node worker2 notes-lab.io/disk=ssd
CREATED                EVENTTIME                     CONTROLLER          REASON             NOTE
2026-10-13T06:06:13Z   2026-10-13T06:06:13.163201Z   default-scheduler   FailedScheduling   0/3 nodes are available: ...
2026-10-13T06:06:25Z   2026-10-13T06:06:25.858855Z   default-scheduler   Scheduled          Successfully assigned notes-lab/pick-node to worker2
2026-10-13T06:06:27Z   <nil>                         kubelet             Pulled             Container image "nginx:alpine" already present on machine
2026-10-13T06:06:27Z   <nil>                         kubelet             Created            Created container nginx
2026-10-13T06:06:27Z   <nil>                         kubelet             Started            Started container nginx

打标签到 Scheduled 只隔了约 31 毫秒。调度器不是定时轮询，它 watch 了 Node 对象，节点标签变化会让不可调度的 Pod 重新进入调度队列。调度规则本身见调度和污点与容忍。

跳过调度器：nodeName 写错

spec.nodeName 本来是调度器写的字段，如果在清单里直接写死，调度器就不会处理这个 Pod。对比一个写对节点名、一个写成不存在的 worker9 的 Pod：

apiVersion: v1
kind: Pod
metadata:
  name: direct
spec:
  nodeName: worker   # 另一个 Pod ghost-node 写的是 worker9
  containers:
    - name: nginx
      image: nginx:alpine
      resources:
        requests:
          cpu: 20m
          memory: 32Mi

30 秒后：

NAME         READY   STATUS    RESTARTS   AGE   IP          NODE
direct       1/1     Running   0          30s   <pod-ip>    worker
ghost-node   0/1     Pending   0          30s   <none>      worker9

direct 的事件里只有 kubelet 的 Pulled/Created/Started，没有 Scheduled，调度器完全没有经手。调度器不检查，不等于没人检查：kubelet 收到 Pod 后还有自己的准入检查。另建一个 nodeName: worker、却请求 200 核 CPU 的 direct-big：

apiVersion: v1
kind: Pod
metadata:
  name: direct-big
spec:
  nodeName: worker
  containers:
    - name: nginx
      image: nginx:alpine
      resources:
        requests:
          cpu: "200"
          memory: 32Mi
NAME         READY   STATUS     RESTARTS   AGE   IP       NODE     NOMINATED NODE   READINESS GATES
direct-big   0/1     OutOfcpu   0          56s   <none>   worker   <none>           <none>
Status:           Failed
Reason:           OutOfcpu
Message:          Pod was rejected: Node didn't have enough resource: cpu, requested: 200000, used: 560, capacity: 28000
Events:
  Type     Reason    Age   From     Message
  ----     ------    ----  ----     -------
  Warning  OutOfcpu  56s   kubelet  Node didn't have enough resource: cpu, requested: 200000, used: 560, capacity: 28000

经过调度器的 Pod 资源不够时会停在 Pending 等待；绕过调度器的 Pod 被 kubelet 直接判为 Failed（内存不够应是 OutOfmemory，未实测），不会自己恢复，也不会换节点。报错里的 capacity: 28000（单位是 millicore）实际是节点的 allocatable，即可分配给 Pod 的量，不是物理核数。

ghost-node 更麻烦：

Node:             worker9/
Status:           Pending
Events:                      <none>
{"phase":"Pending","qosClass":"Burstable"}

一条事件都没有，status 里连 conditions 都没有。调度器认为它已经有节点了，不归自己管；没有哪个 kubelet 叫 worker9，也就没人认领。

但它也不会一直挂着。单独重跑一次，06:14:07 创建后每 2 秒查一次 phase：

06:14:07 Pending
06:14:09 Pending
06:14:11 Pending
...
06:14:59 Pending
06:15:01 Pending
06:15:03 Error from server (NotFound): pods "ghost-node" not found

Pod 在约 54 秒后自己消失了，2 秒一次的轮询里看到的一直是 Pending，也没有任何事件。删掉它的是控制器管理器里的 Pod 垃圾回收控制器：

kubectl -n kube-system logs kube-controller-manager-control-plane --since=5m | grep ghost-node
I1013 06:15:01.613870       1 gc_controller.go:342] "PodGC is force deleting Pod" logger="pod-garbage-collector-controller" pod="notes-lab/ghost-node"
I1013 06:15:01.617435       1 gc_controller.go:258] "Forced deletion of orphaned Pod succeeded" logger="pod-garbage-collector-controller" pod="notes-lab/ghost-node"

PodGC 把绑定到不存在节点上的 Pod 当作孤儿强制删除，删除不留事件。按 1.31 的源码，它在删除前会先把 phase 置为 Failed，并加上 DisruptionTarget 条件（reason 为 DeletionByPodGC），然后以宽限期 0 删除；日志里两步只隔约 4 毫秒，所以轮询看不到中间状态。

为什么是 54 秒：源码里孤儿 Pod 的隔离时间是常量 quarantineTime = 40 秒，PodGC 的扫描周期 gcCheckPeriod 是 20 秒，所以删除时间会落在创建后 40 到 60 秒之间。这两个值都没有对应的启动参数；--terminated-pod-gc-threshold 只管已终止的 Pod，和这里无关。第一轮实验里 ghost-node 06:06:39 创建、06:07:22 去删时已经 NotFound，也落在这个区间里。

这类问题的现场很短：Pending、Events 为空、NODE 列却有值，要尽快核对节点名是否真实存在（kubectl get nodes）；如果 Pod「过一会儿自己没了」，去控制器管理器日志里搜 Pod 名。如果它属于某个 Deployment，推测控制器会按同一个模板再建一个，表现为 Pod 不断换名字（这次没有测）。

控制器管理器：Pod 根本没被创建

给 namespace 加一个最多 2 个 Pod 的配额，再把 Deployment 扩到 4：

kubectl -n notes-lab create quota pods-cap --hard=pods=2
kubectl -n notes-lab scale deploy web --replicas=4
$ kubectl -n notes-lab get deploy web

web-668945bdf5-bltvs   1/1     Running   0          10s
web-668945bdf5-l5lf2   1/1     Running   0          2m28s

缺的两个 Pod 不是 Pending，而是根本不存在，describe pod 无从查起。事件挂在 ReplicaSet 上：

2026-10-13T06:07:25Z   replicaset-controller   ReplicaSet   FailedCreate        Error creating: pods "web-668945bdf5-n5t45" is forbidden: exceeded quota: pods-cap, requested: pods=1, used: pods=2, limited: pods=2
...
2026-10-13T06:07:26Z   <none>                  ReplicaSet   FailedCreate        (combined from similar events): Error creating: pods "web-668945bdf5-fpxmm" is forbidden: exceeded quota: pods-cap, requested: pods=1, used: pods=2, limited: pods=2

拒绝发生在 API Server 的准入阶段（ResourceQuota 准入插件），报告者是 replicaset-controller，因为是它发起的创建请求。手工创建 Pod 撞上同一个配额，错误直接回到终端：

Error from server (Forbidden): pods "extra" is forbidden: exceeded quota: pods-cap, requested: pods=1, used: pods=2, limited: pods=2

区别在于：经过控制器创建的对象，错误只会出现在控制器的事件里，kubectl apply 本身显示成功。06:07:42 删掉配额，06:07:49 ReplicaSet 补齐了两个 Pod，控制器在后台持续重试，不需要人工触发；中间这 7 秒推测是控制器工作队列的重试退避。配额的用法见资源策略。

kubelet 和控制器的分工：容器退出与 Pod 被删

最后对比两个看起来相似的动作。06:08:04 同时做两件事：在一个 Pod 里 kill 1 结束 nginx 主进程，直接删除另一个 Pod：

kubectl -n notes-lab exec web-668945bdf5-bltvs -- kill 1
kubectl -n notes-lab delete pod web-668945bdf5-l5lf2 --wait=false
NAME                   READY   STATUS    RESTARTS     AGE   NODE
web-668945bdf5-2tqb9   1/1     Running   0            8s    worker2
web-668945bdf5-bltvs   1/1     Running   1 (8s ago)   47s   worker

被 kill 的 Pod 名字没变，RESTARTS 变成 1：

    Last State:     Terminated
      Reason:       Completed
      Exit Code:    0
...
  Normal  Scheduled  52s                default-scheduler  Successfully assigned notes-lab/web-668945bdf5-bltvs to worker
  Normal  Pulled     11s (x2 over 51s)  kubelet            Container image "nginx:alpine" already present on machine

  Normal  Started    9s (x2 over 50s)   kubelet            Started container nginx

Scheduled 只有一次，Created/Started 变成 x2：这是 kubelet 在原节点、原 Pod 里按 restartPolicy: Always 把容器重新拉起，控制平面没有参与。nginx 收到 SIGTERM 是正常退出，所以退出码是 0、原因是 Completed，但仍然会被重启。

被删除的那个 Pod 则换了名字，走了一遍完整链路：

2026-10-13T06:08:04Z   replicaset-controller   web-668945bdf5         SuccessfulCreate    Created pod: web-668945bdf5-2tqb9
2026-10-13T06:08:04Z   default-scheduler       web-668945bdf5-2tqb9   Scheduled           Successfully assigned notes-lab/web-668945bdf5-2tqb9 to worker2
2026-10-13T06:08:04Z   kubelet                 web-668945bdf5-l5lf2   Killing             Stopping container nginx
2026-10-13T06:08:08Z   kubelet                 web-668945bdf5-2tqb9   Pulled              Container image "nginx:alpine" already present on machine

旧 Pod 由 kubelet 停止容器（Killing），新 Pod 由 replicaset-controller 创建、调度器分配、kubelet 启动。容器级别的故障由节点上的 kubelet 自愈，Pod 级别的缺失由控制器补齐。这也意味着节点整个宕掉时，kubelet 没了，只能等控制器把 Pod 重建到别的节点上。协调循环的细节见调和循环。

排查顺序

现象最后出现的事件来源先查什么
apply 直接报错无（API Server 同步返回）错误信息本身：校验、RBAC、准入、配额
Deployment 副本不够，Pod 不存在replicaset-controller FailedCreatekubectl describe rs，常见是配额、PSA、准入 Webhook
Pending，NODE 为空default-scheduler FailedScheduling事件里逐节点的淘汰原因
Pending，NODE 有值，没有事件；40–60 秒后 Pod 自己消失无（PodGC 删除不留事件）节点名不存在，Pod 被 PodGC 当孤儿删掉；kubectl get nodes 核对，控制器管理器日志里搜 Pod 名
Pending，NODE 有值，没有事件；Pod 一直不消失无节点存在但 kubelet 没在跑（PodGC 不会删），去该节点看 kubelet 状态和日志
写死 nodeName，Pod 直接 Failed（OutOfcpu/OutOfmemory）kubelet节点剩余资源，或去掉 nodeName 交给调度器
ContainerCreating / ImagePullBackOff / CrashLoopBackOffkubelet事件、logs --previous，再到节点 journalctl -u kubelet
Pod 正常，Service 不通无EndpointSlice，节点上的 kube-proxy 规则
很多 Pod 同时异常，或调度器/控制器反复重启—/readyz?verbose、组件 --previous 日志、Lease 换手次数

更完整的排查流程见故障排查，多控制平面的部署见高可用。
