容器安全上下文

RBAC 管的是一个身份能对 Kubernetes API 做什么；securityContext 管的是容器里的进程在节点内核面前有多大权限：以哪个 UID/GID 运行、带哪些 Linux capabilities、能不能写根文件系统、能不能通过 setuid 程序提权、受不受 seccomp 过滤。两者作用在不同层面，一个也替代不了另一个。

这些字段写在 YAML 里看起来都差不多，实际效果差别很大，有些还和直觉相反。下面每个字段都在集群里跑一遍，用 id、ls -l 和 /proc/<pid>/status 看进程实际拿到了什么权限。环境是一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），实验放在单独的 notes-lab namespace 里，Pod IP 用 <pod-ip> 代替。

用户、组与卷的属组

先跑一个什么都不设的 busybox 作为对照，再跑一个设了三个 ID 字段的 Pod，两者都挂一个 emptyDir 到 /data：

apiVersion: v1
kind: Pod
metadata:
  name: ids
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      volumeMounts:
        - name: data
          mountPath: /data
      resources:
        requests: {cpu: 10m, memory: 16Mi}
  volumes:
    - name: data
      emptyDir: {}

对照组就是镜像默认的 root：

$ kubectl -n notes-lab exec baseline -- id
uid=0(root) gid=0(root) groups=0(root),10(wheel)
$ kubectl -n notes-lab exec baseline -- sh -c "ls -ld /data; touch /data/f; ls -l /data/f"
drwxrwxrwx    2 root     root          4096 Oct 12 07:53 /data
-rw-r--r--    1 root     root             0 Oct 12 07:53 /data/f

设了 ID 的 Pod：

$ kubectl -n notes-lab exec ids -- id
uid=1000 gid=3000 groups=2000,3000
$ kubectl -n notes-lab exec ids -- sh -c "ls -ld /data; touch /data/f; ls -l /data/f; ps -o pid,user,group,args"
drwxrwsrwx    2 root     2000          4096 Oct 12 07:53 /data
-rw-r--r--    1 1000     2000             0 Oct 12 07:53 /data/f
PID   USER     GROUP    COMMAND
    1 1000     3000     sleep 3600
   19 1000     3000     ps -o pid,user,group,args

三个字段各管一件事：

  • runAsUser: 1000 决定进程 UID，PID 1 和 exec 进去的进程都是 1000。
  • runAsGroup: 3000 决定主组，进程的 GROUP 列是 3000。
  • fsGroup: 2000 不改主组，而是作为附加组加进来（groups=2000,3000），同时 kubelet 把卷目录的属组改成 2000，并设置了 setgid 位，就是 drwxrwsrwx 里那个 s。所以在 /data 下新建的文件属组是 2000，而不是进程主组 3000。

对比一下在卷外面新建文件：

$ kubectl -n notes-lab exec ids -- sh -c "touch /tmp/x; ls -l /tmp/x; touch /etc/x"
-rw-r--r--    1 1000     3000             0 Oct 12 07:53 /tmp/x
touch: /etc/x: Permission denied
command terminated with exit code 1

/tmp/x 的属组是 3000，只有卷里的文件才继承 2000。这就是 fsGroup 的用途：多个 UID 不同的容器，或者 Pod 重建后换了 UID，都能靠同一个附加组访问同一个卷。注意新文件的权限是 0644，同组的其他 UID 只能读、不能写，要组内可写还得应用自己调 umask 或 chmod。/etc/x 写不进去是普通的文件权限问题，进程不是 root 了，跟后面要讲的只读根文件系统无关。

fsGroup 只对支持属主管理的卷类型生效（emptyDir、多数块存储 PV 等），hostPath 这类不会被改属组。对大卷来说，kubelet 默认每次挂载都递归 chown/chmod 整个卷，文件多时会拖慢 Pod 启动；fsGroupChangePolicy: OnRootMismatch 让它只在卷根目录的属主和权限不符时才递归处理。这个字段对 emptyDir、Secret、ConfigMap 这类临时卷不起作用。

只设 runAsUser 时，主组是 root

如果只写 runAsUser、不写 runAsGroup：

$ kubectl -n notes-lab run uid-only --image=busybox:1.36 --restart=Never --overrides='{"spec":{"securityContext":{"runAsUser":1000}}}' -- sh -c "id; touch /tmp/a; ls -l /tmp/a"
$ kubectl -n notes-lab logs uid-only
uid=1000 gid=0(root) groups=0(root)
-rw-r--r--    1 1000     root             0 Oct 12 07:54 /tmp/a

UID 换掉了，主组却还是 0。官方文档也写明了：省略 runAsGroup 时，容器的主组 ID 是 root(0)。进程不是 root 用户，但仍属于 root 组，能读写所有对 root 组开放的文件。只想「降成非 root」时，runAsUser 和 runAsGroup 要一起写。

不过这条规则有个例外。后面用 curl 镜像做实验时，只设了 runAsUser: 100，结果是：

$ kubectl -n notes-lab exec nonroot-named-uid -- id
uid=100(curl_user) gid=101(curl_group) groups=101(curl_group)

主组变成了 101。curl 镜像的 /etc/passwd 里有 UID 100 这个用户，主组是 101，运行时按这条记录补上了主组；busybox 镜像里没有 UID 1000 的记录，于是落回 0。所以 gid 是不是 0，取决于镜像里有没有这个 UID 的 passwd 记录，两种镜像结果不一样。显式写上 runAsGroup 就不受镜像影响了。

runAsNonRoot：kubelet 在启动前检查

runAsNonRoot: true 不改变进程用哪个 UID 运行，它只是让 kubelet 在创建容器前检查一下：最终 UID 是 0 就拒绝启动。用四个 Pod 覆盖几种情况，模板如下，只换镜像和 securityContext：

apiVersion: v1
kind: Pod
metadata:
  name: nonroot-named
spec:
  containers:
    - name: app
      image: curlimages/curl:latest
      imagePullPolicy: IfNotPresent
      command: ["sleep", "3600"]
      securityContext:
        runAsNonRoot: true
      resources:
        requests: {cpu: 10m, memory: 16Mi}
Pod镜像镜像 USERsecurityContext
nonroot-busyboxbusybox:1.36未设置（root）runAsNonRoot: true
nonroot-namedcurlimages/curlcurl_user（用户名）runAsNonRoot: true
nonroot-named-uidcurlimages/curlcurl_userrunAsNonRoot: true + runAsUser: 100
nonroot-uid0busybox:1.36未设置runAsNonRoot: true + runAsUser: 0
NAME                READY   STATUS                       RESTARTS   AGE
nonroot-busybox     0/1     CreateContainerConfigError   0          15s
nonroot-named       0/1     CreateContainerConfigError   0          15s
nonroot-named-uid   1/1     Running                      0          15s
nonroot-uid0        0/1     CreateContainerConfigError   0          15s

三个失败的 Pod 状态都是 CreateContainerConfigError，RESTARTS 是 0。容器根本没创建出来，不存在「重启」，Pod phase 也一直停在 Pending。区分原因要看事件里的消息，三种情况的措辞各不相同：

$ kubectl -n notes-lab get events --field-selector involvedObject.name=nonroot-busybox,type=Warning -o custom-columns=REASON:.reason,MESSAGE:.message
REASON   MESSAGE
Failed   Error: container has runAsNonRoot and image will run as root (pod: "...", container: app)

$ kubectl -n notes-lab get events --field-selector involvedObject.name=nonroot-named,type=Warning -o custom-columns=REASON:.reason,MESSAGE:.message
REASON   MESSAGE
Failed   Error: container has runAsNonRoot and image has non-numeric user (curl_user), cannot verify user is non-root (pod: "...", container: app)

$ kubectl -n notes-lab get events --field-selector involvedObject.name=nonroot-uid0,type=Warning -o custom-columns=REASON:.reason,MESSAGE:.message
REASON   MESSAGE
Failed   Error: container's runAsUser breaks non-root policy (pod: "...", container: app)
  • image will run as root：镜像没声明 USER，或者声明的就是 root，而 Pod 也没指定 runAsUser。
  • image has non-numeric user (curl_user)：最容易让人困惑的一种。curl 镜像明明不是 root，照样被拒。原因是 kubelet 只能看到镜像配置里的字符串 curl_user，不会进镜像查 /etc/passwd，无法确认它对应的 UID 不是 0，所以按失败处理。解决办法是在镜像里写数字形式的 USER 100，或者在 Pod 里补一个 runAsUser，也就是第三个 Pod 的写法。
  • runAsUser breaks non-root policy：两个字段自相矛盾。API Server 不会拦截这种组合，Pod 照样创建成功，要到 kubelet 启动容器时才报错。

kubelet 会一直重试，事件计数在增长，但只要配置不改，结果都一样：

COUNT    REASON      LAST
<none>   Scheduled   <nil>
4        Pulled      2026-10-12T07:54:27Z
4        Failed      2026-10-12T07:54:27Z

readOnlyRootFilesystem：nginx 缺哪些可写目录

只读根文件系统能防住「往镜像目录里写个 webshell」这类攻击，代价是很多镜像默认要往根文件系统写东西。直接给官方 nginx 镜像打开：

apiVersion: v1
kind: Pod
metadata:
  name: ro-nginx
spec:
  containers:
    - name: nginx
      image: nginx:alpine
      securityContext:
        readOnlyRootFilesystem: true
      resources:
        requests: {cpu: 10m, memory: 32Mi}

网页目录依然写不进去，只有两个挂载点可写。看 /proc/mounts 更直接，根文件系统是 ro 挂载的 overlay，两个卷是 rw（overlay 的 lowerdir 一长串路径这里省略了）：

overlay / overlay ro,relatime,lowerdir=...,upperdir=...,workdir=...,uuid=on,nouserxattr 0 0
tmpfs /run tmpfs rw,relatime,size=1024k,inode64,noswap 0 0
/dev/sda /var/cache/nginx ext4 rw,relatime 0 0

/run 下还多了个 secrets 目录。ServiceAccount token 挂在 /var/run/secrets/kubernetes.io/serviceaccount，Alpine 里 /var/run 是指向 /run 的链接，推测这个目录就是 token 挂载点留下的；这次没有进一步确认 token 文件在 emptyDir 盖上之后是否仍可读，依赖 token 的应用要自己验证一下。

换成别的应用，思路一样：开启只读后看日志里的 EROFS 报错，把报错路径一个个换成卷。可写卷要尽量少、尽量窄，整个 / 都换成可写卷就失去意义了。emptyDir 的介质和容量上限见 emptyDir。

capabilities：root 和非 root 看到的不一样

Linux 把 root 的特权拆成了几十个 capability。在 /proc/<pid>/status 里，CapEff 是当前生效的集合，CapBnd 是上限（bounding set），之后再怎么 exec 也拿不到这之外的 capability。四个 Pod 对比，分别是：root 默认、root 加 drop: ["ALL"]、UID 1000 默认、UID 1000 加 drop ALL + add NET_BIND_SERVICE + allowPrivilegeEscalation: false：

$ kubectl -n notes-lab exec cap-root-default -- grep -E '^(Cap|NoNewPrivs|Seccomp)' /proc/self/status
CapInh:	0000000000000000
CapPrm:	00000000a80425fb
CapEff:	00000000a80425fb
CapBnd:	00000000a80425fb
CapAmb:	0000000000000000
NoNewPrivs:	0
Seccomp:	0
Seccomp_filters:	0

用 capsh 解码这个掩码，就是 containerd 默认给容器的 14 个 capability：

$ capsh --decode=00000000a80425fb
0x00000000a80425fb=cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap

drop: ["ALL"] 之后五个集合全是 0。root 依然是 UID 0，但已经改不了文件属主了：

$ kubectl -n notes-lab exec cap-root-dropall -- sh -c "id; touch /tmp/f; chown 1000 /tmp/f; ls -l /tmp/f"
uid=0(root) gid=0(root) groups=0(root),10(wheel)
chown: /tmp/f: Operation not permitted
-rw-r--r--    1 root     root             0 Oct 12 07:56 /tmp/f

同样的命令在 cap-root-default 里能成功，文件属主变成了 1000。「是不是 root」和「有没有特权」是两回事，后者由 capability 决定。

非 root 的两个 Pod：

$ kubectl -n notes-lab exec cap-user-default -- grep -E '^(Cap|NoNewPrivs|Seccomp)' /proc/self/status
CapInh:	0000000000000000
CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	00000000a80425fb
CapAmb:	0000000000000000
NoNewPrivs:	0
Seccomp:	0
Seccomp_filters:	0

$ kubectl -n notes-lab exec cap-user-bind -- grep -E '^(Cap|NoNewPrivs|Seccomp)' /proc/self/status
CapInh:	0000000000000000
CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000000000400
CapAmb:	0000000000000000
NoNewPrivs:	1
Seccomp:	0
Seccomp_filters:	0

非 root 进程默认 CapEff 就是 0，默认的 14 个只留在 bounding set 里。第二个 Pod 显式 add 了 NET_BIND_SERVICE（0x400），可它只出现在 CapBnd 里，CapEff 和 CapPrm 仍然是 0。exec 进去的是新进程，为了排除这个因素，又看了 PID 1，结果一样：

$ kubectl -n notes-lab exec cap-user-bind -- grep -E "^Cap(Prm|Eff|Bnd)" /proc/1/status
CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000000000400

实际去绑 80 端口：

$ kubectl -n notes-lab exec cap-user-bind -- timeout 2 nc -l -p 80
nc: bind: Permission denied
command terminated with exit code 1
$ kubectl -n notes-lab exec cap-user-bind -- timeout 2 nc -l -p 8080; echo exit=$?
punt!
command terminated with exit code 143
exit=143

80 端口绑不上；8080 正常监听，2 秒后被 timeout 用 SIGTERM 结束（143 = 128 + 15，punt! 是 busybox nc 收到信号时打印的）。也就是说，非 root 容器 add: ["NET_BIND_SERVICE"] 不会生效。这是 Kubernetes 本身的限制，不是这套环境的特例：按内核规则，非 root 进程在 execve 一个不带 file capability 的程序时，permitted 和 effective 集合会被清空，只有 ambient 集合里的 capability 能保留下来；而 Pod API 里没有设置 ambient capabilities 的字段，上面 CapAmb 一直是 0。这个问题在 kubernetes/kubernetes#56374 里讨论了多年，对应的 KEP-2763 也还没有落地。有点讽刺的是，Pod Security 的 restricted 级别明确允许 add: ["NET_BIND_SERVICE"]，可对它要求的非 root 进程来说，这一项加了也没用。

80 端口有两种能实际测通的做法。

一是保留 UID 0，但只给一个 capability：

securityContext:
  runAsUser: 0
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]
    add: ["NET_BIND_SERVICE"]
$ kubectl -n notes-lab exec bind-root-mincap -- grep -E "^Cap(Prm|Eff|Bnd)" /proc/1/status
CapPrm:	0000000000000400
CapEff:	0000000000000400
CapBnd:	0000000000000400
$ kubectl -n notes-lab exec bind-root-mincap -- timeout 2 nc -l -p 80; echo exit=$?
punt!
command terminated with exit code 143
exit=143
$ kubectl -n notes-lab exec bind-root-mincap -- sh -c "touch /tmp/f; chown 1000 /tmp/f"
chown: /tmp/f: Operation not permitted
command terminated with exit code 1

root 进程的 add 是生效的，80 端口能绑，其他特权（比如 chown）都没有。但它仍然是 UID 0，过不了 runAsNonRoot，Pod Security 的 restricted 级别也不允许。

二是让非 root 进程本来就能绑低端口。端口特权的门槛是网络命名空间里的 net.ipv4.ip_unprivileged_port_start。它的默认值取决于容器运行时：containerd 1.7 不改它，保持内核默认的 1024；containerd 2.x 的 CRI 配置 enable_unprivileged_ports 默认为 true，会把它设成 0，那样非 root 进程本来就能绑 80，上面这个失败也就不会出现。这个集群用的是 1.7：

$ kubectl -n notes-lab exec cap-root-default -- sysctl net.ipv4.ip_unprivileged_port_start
net.ipv4.ip_unprivileged_port_start = 1024

它从 Kubernetes 1.22 起属于安全 sysctl，可以直接在 Pod 级设置，作用范围只是这个 Pod 自己的网络命名空间：

spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
    sysctls:
      - name: net.ipv4.ip_unprivileged_port_start
        value: "80"
$ kubectl -n notes-lab exec bind-sysctl -- sh -c "id; grep CapEff /proc/1/status; sysctl net.ipv4.ip_unprivileged_port_start"
uid=1000 gid=1000 groups=1000
CapEff:	0000000000000000
net.ipv4.ip_unprivileged_port_start = 80
$ kubectl -n notes-lab exec bind-sysctl -- timeout 2 nc -l -p 80; echo exit=$?
punt!
command terminated with exit code 143
exit=143
$ kubectl -n notes-lab exec bind-sysctl -- timeout 2 nc -l -p 79; echo exit=$?
nc: bind: Permission denied
command terminated with exit code 1
exit=1

capability 全是 0，80 能绑，79 不行，门槛正好落在设置的值上。当然，最省事的做法还是让应用监听 8080 这类高端口，再由 Service 的 port: 80 转到 targetPort: 8080。

allowPrivilegeEscalation：setuid 程序还管不管用

allowPrivilegeEscalation: false 对应的是进程的 no_new_privs 标志，上面 NoNewPrivs: 1 那一行就是它。不设置时默认是 true，也就是 NoNewPrivs: 0。这个标志的作用是 exec 时不再授予新权限，最典型的就是 setuid 位失效。

要看到效果，需要一个属主是 root、带 setuid 位的程序。用 C 写一个只打印真实 UID 和有效 UID 的小程序，静态编译：

#include <stdio.h>
#include <unistd.h>
int main(void) {
    printf("ruid=%d euid=%d\n", getuid(), geteuid());
    return 0;
}

每个 Pod 里放两个容器，共享一个 emptyDir：helper 是默认的 root，负责把程序设成 root:root 4755；app 以 UID 1000 运行，执行这个程序。两个 Pod 只差 app 的 allowPrivilegeEscalation：

- name: app
  image: busybox:1.36
  command: ["sleep", "3600"]
  securityContext:
    runAsUser: 1000
    allowPrivilegeEscalation: true   # 另一个 Pod 里是 false
  volumeMounts: [{name: shared, mountPath: /shared}]
$ kubectl -n notes-lab cp suidcheck ape-true:/shared/suidcheck -c helper
$ kubectl -n notes-lab exec ape-true -c helper -- sh -c 'chown 0:0 /shared/suidcheck; chmod 4755 /shared/suidcheck; ls -l /shared/suidcheck'
-rwsr-xr-x    1 root     root        816984 Oct 12 07:58 /shared/suidcheck
$ kubectl -n notes-lab exec ape-true -c app -- sh -c 'grep NoNewPrivs /proc/self/status; /shared/suidcheck'
NoNewPrivs:	0
ruid=1000 euid=0
$ kubectl -n notes-lab exec ape-false -c app -- sh -c 'grep NoNewPrivs /proc/self/status; /shared/suidcheck'
NoNewPrivs:	1
ruid=1000 euid=1000

允许提权时，UID 1000 的进程执行这个程序后有效 UID 变成了 0；禁止后 setuid 位被忽略，仍然是 1000。

这个实验说明 runAsUser: 1000 本身挡不住提权，而它的前提——同一 Pod 里有能往共享卷写 setuid 程序的 root 容器——本身就是风险。除此之外，如果镜像里本来就带属主为 root 的 setuid 程序（传统发行版里的 su、passwd 通常就是），非 root 容器也能借它拿到 root。allowPrivilegeEscalation: false 堵的就是这条路。另外，容器设了 privileged: true 或带 CAP_SYS_ADMIN 时，提权实际上总是允许的，allowPrivilegeEscalation: false 不能和这两者同时设置。

Pod 级与容器级：谁覆盖谁

securityContext 在两个位置都能写。Pod 级的设置作用于所有容器；容器级的设置只作用于当前容器，两边都写了同一个字段时，容器级优先：

apiVersion: v1
kind: Pod
metadata:
  name: precedence
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
    runAsNonRoot: true
  containers:
    - name: inherit
      image: busybox:1.36
      command: ["sleep", "3600"]
    - name: override
      image: busybox:1.36
      command: ["sleep", "3600"]
      securityContext:
        runAsUser: 2000
$ kubectl -n notes-lab exec precedence -c inherit -- id
uid=1000 gid=1000 groups=1000
$ kubectl -n notes-lab exec precedence -c override -- id
uid=2000 gid=1000 groups=1000

覆盖是逐字段的：override 只换掉了 UID，runAsGroup 仍然继承 Pod 级的 1000。seccomp 也一样，Pod 级设 RuntimeDefault、某个容器设 Unconfined，那个容器就脱离了过滤：

$ kubectl -n notes-lab exec seccomp-mix -c inherit -- grep "^Seccomp:" /proc/1/status
Seccomp:	2
$ kubectl -n notes-lab exec seccomp-mix -c override -- grep "^Seccomp:" /proc/1/status
Seccomp:	0

两个位置能写的字段并不相同。runAsUser、runAsGroup、runAsNonRoot、seccompProfile 两边都有；fsGroup、sysctls、supplementalGroups 只能写在 Pod 级，因为它们作用于卷或整个 Pod 的命名空间；capabilities、readOnlyRootFilesystem、allowPrivilegeEscalation、privileged 只能写在容器级。写错位置时，API Server 会直接拒绝：

$ kubectl -n notes-lab apply -f bad-level.yaml
Error from server (BadRequest): error when creating "bad-level.yaml": Pod in version "v1" cannot be handled as a Pod: strict decoding error: unknown field "spec.containers[0].securityContext.fsGroup", unknown field "spec.securityContext.capabilities", unknown field "spec.securityContext.readOnlyRootFilesystem"

但如果加了 --validate=false，字段会被悄悄丢掉，Pod 照样创建：

$ kubectl -n notes-lab apply -f bad-level.yaml --validate=false
pod/bad-level created
$ kubectl -n notes-lab get pod bad-level -o jsonpath="{.spec.securityContext} {.spec.containers[0].securityContext}"
{} {}
$ kubectl -n notes-lab exec bad-level -- sh -c "id; grep CapEff /proc/1/status; touch /etc/x && echo rootfs-writable"
uid=0(root) gid=0(root) groups=0(root),10(wheel)
CapEff:	00000000a80425fb
rootfs-writable

两个 securityContext 都是空的，容器以 root 运行，带着全部默认 capability，根文件系统可写，YAML 里写的限制一条都没生效。部署脚本里如果为了绕过某个校验报错加了 --validate=false，安全相关的字段最好部署后再确认一遍是否还在。

seccomp：RuntimeDefault 与 Unconfined

seccomp 过滤的是系统调用。前面所有没设 seccomp 的 Pod，/proc/1/status 里都是 Seccomp: 0，也就是完全没有过滤。这是上游的默认行为：官方文档写明，kubelet 没开启 seccompDefault 时，未指定 profile 的 Pod 默认是 Unconfined。这个开关 v1.27 起已是 GA，但默认仍然关闭。节点 kubelet 配置文件里也没有这一项（它也可能通过命令行参数开启，所以真正的证据是上面的 Seccomp: 0）：

$ docker exec <worker-node> grep -i seccomp /var/lib/kubelet/config.yaml; echo "grep-exit=$?"
grep-exit=1

所以「不写就是运行时默认 profile」这个印象是错的，除非节点上专门开启了 seccompDefault。两个 root busybox，只差 Pod 级 seccompProfile.type：

spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault   # 另一个 Pod 里是 Unconfined
$ kubectl -n notes-lab exec seccomp-unconfined -- grep -E '^Seccomp' /proc/1/status
Seccomp:	0
Seccomp_filters:	0
$ kubectl -n notes-lab exec seccomp-runtimedefault -- grep -E '^Seccomp' /proc/1/status
Seccomp:	2
Seccomp_filters:	1

Seccomp: 2 表示 filter 模式，已经加载了一个过滤器。用 unshare -U 尝试创建一个新的 user namespace：

$ kubectl -n notes-lab exec seccomp-unconfined -- unshare -U id
uid=65534(nobody) gid=65534(nobody) groups=65534(nobody),65534(nobody)
$ kubectl -n notes-lab exec seccomp-runtimedefault -- unshare -U id
unshare: unshare(0x10000000): Operation not permitted
command terminated with exit code 1

Unconfined 下成功进入了新的 user namespace，因为没有建立 UID 映射，显示为 nobody；RuntimeDefault 下 unshare(CLONE_NEWUSER)（0x10000000）这个系统调用直接返回了 EPERM。两个 Pod 的用户和 capability 完全相同，差别只能来自 seccomp。

作为对照，unshare -m（新的 mount namespace）在两边都失败，报错完全一样：

$ kubectl -n notes-lab exec seccomp-unconfined -- unshare -m sh -c 'echo mount-ns-ok'
unshare: unshare(0x20000): Operation not permitted
command terminated with exit code 1
$ kubectl -n notes-lab exec seccomp-runtimedefault -- unshare -m sh -c 'echo mount-ns-ok'
unshare: unshare(0x20000): Operation not permitted
command terminated with exit code 1

但两边是被不同的层拒绝的。containerd 1.7 的默认 profile（contrib/seccomp/seccomp_default.go）默认动作是返回错误，unshare 只在容器带 CAP_SYS_ADMIN 时才加入放行列表，而且不区分 flag，所以 RuntimeDefault 下的两次 unshare 都是 seccomp 直接拒绝的。Unconfined 下没有过滤，unshare -U 能成功；unshare -m 需要 CAP_SYS_ADMIN，默认的 14 个 capability 里没有它，是内核的 capability 检查拒绝的。同样是 Operation not permitted，可能来自 seccomp，也可能来自 capability。要分清是哪一层拒绝的，就像这里一样，只改一个变量对比。

组合起来：非 root 的只读 nginx 监听 80

把上面的结论合在一起，官方 nginx 镜像不用改，也能在 restricted 级别下监听 80 端口。镜像里的 nginx 用户 UID 是 101：

apiVersion: v1
kind: Pod
metadata:
  name: hardened-nginx
spec:
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 101
    runAsGroup: 101
    seccompProfile:
      type: RuntimeDefault
    sysctls:
      - name: net.ipv4.ip_unprivileged_port_start
        value: "80"
  containers:
    - name: nginx
      image: nginx:alpine
      ports:
        - containerPort: 80
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: cache
          mountPath: /var/cache/nginx
        - name: run
          mountPath: /run
      resources:
        requests: {cpu: 10m, memory: 32Mi}
        limits: {memory: 64Mi}
  volumes:
    - name: cache
      emptyDir: {}
    - name: run
      emptyDir:
        medium: Memory
        sizeLimit: 1Mi

先给 namespace 打上 pod-security.kubernetes.io/enforce=restricted 标签，再创建这个 Pod，它能通过准入并正常启动：

$ kubectl -n notes-lab exec hardened-nginx -- sh -c "id; grep -E \"^(CapEff|NoNewPrivs|Seccomp):\" /proc/1/status; ps -o pid,user,args"
uid=101(nginx) gid=101(nginx) groups=101(nginx)
CapEff:	0000000000000000
NoNewPrivs:	1
Seccomp:	2
PID   USER     COMMAND
    1 nginx    nginx: master process nginx -g daemon off;
   27 nginx    nginx: worker process
   28 nginx    nginx: worker process
...

从另一个同样受限的 curl Pod 访问它，返回 200：

$ kubectl -n notes-lab run probe --image=curlimages/curl:latest --image-pull-policy=IfNotPresent --restart=Never --rm -i --overrides='{"spec":{"securityContext":{"runAsNonRoot":true,"runAsUser":100,"seccompProfile":{"type":"RuntimeDefault"}},"containers":[{"name":"probe","image":"curlimages/curl:latest","imagePullPolicy":"IfNotPresent","args":["-s","-o","/dev/null","-w","%{http_code}\n","http://<pod-ip>:80/"],"securityContext":{"allowPrivilegeEscalation":false,"capabilities":{"drop":["ALL"]}}}]}}'
If you don't see a command prompt, try pressing enter.
200
pod "probe" deleted

日志里多了一条警告，可以忽略：

nginx: [warn] the "user" directive makes sense only if the master process runs with super-user privileges, ignored in /etc/nginx/nginx.conf:2

master 进程本来就不是 root，配置里的 user nginx; 没有作用。另外 ps 里 worker 进程有 28 个：nginx 的 worker_processes auto 按节点可见的 CPU 数计算，不看 cgroup 配额；镜像入口脚本 30-tune-worker-processes.sh 会读配额，但它默认不启用。实际部署时可以在配置里写死 worker 数。

作为对照，最早那个只设了 runAsNonRoot 的 busybox，在这个 namespace 里连创建都会被拒：

Error from server (Forbidden): error when creating "nr1.yaml": pods "nonroot-busybox" is forbidden: violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "app" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "app" must set securityContext.capabilities.drop=["ALL"]), seccompProfile (pod or container "app" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")

securityContext 是在每个 Pod 里写的，写不写、写得对不对，全靠写 YAML 的人。Pod Security Admission 在 namespace 层面强制检查，没写够的 Pod 直接拒绝。级别划分和标签用法见 Pod Security Admission。

清理
