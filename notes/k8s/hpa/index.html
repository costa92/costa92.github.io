HPA 水平扩缩容

HorizontalPodAutoscaler（HPA）定期读取指标，算出目标副本数，再改写 Deployment 的 spec.replicas。它不会调大单个 Pod 的 CPU，也不会一有流量就立刻扩容。用 CPU 利用率做指标时，百分比是相对于容器 CPU request 算的，所以 request 必须写。

这一篇不讲排查清单（见 HPA 不扩容排查），只看机制：施压之后每一步扩容发生在什么时候、为什么是这个副本数，撤压之后为什么要等一段时间才缩回去，以及 <unknown> 是怎么来的。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），已经装好 Metrics Server，实验放在单独的 notes-lab namespace 里。时间都是 UTC。

准备一个真正吃 CPU 的服务

空闲的 nginx 几乎不耗 CPU，单次请求也撑不起持续负载。这里用 busybox 自带的 httpd 加一个 CGI 脚本：每个请求在 shell 里空转 3 万次循环再返回，CPU 消耗和请求量成正比，也不用额外拉镜像。

apiVersion: v1
kind: ConfigMap
metadata:
  name: burn-cgi
data:
  burn: |
    #!/bin/sh
    i=0
    while [ $i -lt 30000 ]; do i=$((i+1)); done
    echo "Content-Type: text/plain"
    echo
    echo "ok $(hostname)"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: burn
spec:
  replicas: 1
  selector:
    matchLabels:
      app: burn
  template:
    metadata:
      labels:
        app: burn
    spec:
      containers:
        - name: web
          image: busybox:1.36
          command: ["httpd", "-f", "-p", "8080", "-h", "/www"]
          ports:
            - containerPort: 8080
          readinessProbe:
            tcpSocket:
              port: 8080
            periodSeconds: 2
          resources:
            requests:
              cpu: 100m
              memory: 16Mi
            limits:
              cpu: 200m
              memory: 64Mi
          volumeMounts:
            - name: cgi
              mountPath: /www/cgi-bin
      volumes:
        - name: cgi
          configMap:
            name: burn-cgi
            defaultMode: 0755   # CGI 脚本要有执行权限
---
apiVersion: v1
kind: Service
metadata:
  name: burn
spec:
  selector:
    app: burn
  ports:
    - port: 80
      targetPort: 8080

CPU limit 设成 request 的两倍，这个选择后面会影响扩容步长。先测一次请求：

$ kubectl -n notes-lab run t --image=busybox:1.36 --restart=Never --rm -i -- sh -c 'time wget -qO- http://burn/cgi-bin/burn'
ok burn-5c877494c8-8s85p
real	0m 0.27s

HPA 和它被补全的默认行为

目标是平均 CPU 利用率 50%，最多 5 个副本。缩容稳定窗口默认是 300 秒，为了在几分钟内看到完整过程，第一轮先改成 60 秒，后面再换回默认值对比：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: burn
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: burn
  minReplicas: 1
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60

提交后读回来，behavior 里没写的部分已经被补上了：

$ kubectl -n notes-lab get hpa burn -o yaml
spec:
  behavior:
    scaleDown:
      policies:
      - periodSeconds: 15
        type: Percent
        value: 100
      selectPolicy: Max
      stabilizationWindowSeconds: 60
    scaleUp:
      policies:
      - periodSeconds: 15
        type: Pods
        value: 4
      - periodSeconds: 15
        type: Percent
        value: 100
      selectPolicy: Max
      stabilizationWindowSeconds: 0

意思是：扩容没有稳定窗口，每 15 秒最多加 4 个 Pod 或翻一倍（取较大者）；缩容每 15 秒最多减掉 100%，也就是一步就能缩到 minReplicas。

刚创建的 HPA 会短暂显示 <unknown>：

03:46:17 horizontalpodautoscaler.autoscaling/burn created
NAME   REFERENCE         TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
burn   Deployment/burn   cpu: <unknown>/50%   1         5         0          0s

16 秒后变成 cpu: 1%/50%，Conditions 里 ScalingActive 为 True / ValidMetricFound。控制器默认每 15 秒同步一次，第一次同步之前没有数据，这种 <unknown> 不用管。长时间不消失的那种在最后一节。

扩容时间线

起一个负载 Pod，里面 4 个循环并发请求 burn：

kubectl -n notes-lab run load --image=busybox:1.36 --restart=Never -- \
  sh -c 'for n in 1 2 3 4; do (while true; do wget -qO- http://burn/cgi-bin/burn >/dev/null; done) & done; wait'

另开一个循环，每 5 秒记录一次 HPA 状态和 Deployment 副本：

while true; do
  echo "$(date -u +%T) cpu=$(kubectl -n notes-lab get hpa burn -o jsonpath='{.status.currentMetrics[0].resource.current.averageUtilization}% desired={.status.desiredReplicas}') \
$(kubectl -n notes-lab get deploy burn -o jsonpath='spec={.spec.replicas} ready={.status.readyReplicas}')"
  sleep 5
done

负载容器 03:47:59 开始运行。记录如下（略去重复行）：

03:48:17 cpu=1% desired=1 spec=1 ready=1
03:48:24 cpu=161% desired=4 spec=4 ready=1
03:48:37 cpu=201% desired=4 spec=4 ready=3
03:48:42 cpu=201% desired=4 spec=4 ready=4
03:48:54 cpu=192% desired=4 spec=4 ready=4
03:49:05 cpu=192% desired=4 spec=4 ready=4
03:49:10 cpu=140% desired=5 spec=5 ready=4
03:49:17 cpu=140% desired=5 spec=5 ready=5
03:49:43 cpu=125% desired=5 spec=5 ready=5

对应的 HPA 事件：

TIME                   REASON              MSG
2026-10-12T03:48:19Z   SuccessfulRescale   New size: 4; reason: cpu resource utilization (percentage of request) above target
2026-10-12T03:49:09Z   SuccessfulRescale   New size: 5; reason: cpu resource utilization (percentage of request) above target

逐步拆开看。

第一步：施压 20 秒后，1 → 4。 官方给出的公式是：

期望副本数 = ceil( 当前副本数 × 当前指标值 / 目标值 )

当时唯一的 Pod 利用率 161%，ceil(1 × 161 / 50) = ceil(3.22) = 4。扩容策略允许这一步加到 5（+4 个 Pod），所以 4 是公式算出来的，不是被策略截断的。

这里能看出 CPU limit 的影响。limit 是 request 的 2 倍，单个 Pod 的利用率最多到 200%，日志里也确实停在 201%、200%。不管真实压力有多大，从 1 个副本出发，第一步最多只能算出 ceil(1 × 200 / 50) = 4。limit 越贴近 request，HPA 能看到的压力上限越低，扩容就要分更多步走。

中间的停顿：4 个 Pod 都就绪了，利用率还显示 201%，却 30 多秒没有继续扩。 按公式 ceil(4 × 201 / 50) = 17，应该直接到上限 5。原因在于这 201% 只来自老 Pod。03:48:54 的 kubectl top 只列出了 3 个 Pod，新 Pod 的指标还没采到：

NAME                    CPU(cores)   MEMORY(bytes)
burn-5c877494c8-8s85p   192m         1Mi
burn-5c877494c8-9np2d   98m          0Mi
burn-5c877494c8-scvtb   120m         2Mi

可这时 TARGETS 的 192% 正好等于老 Pod 一个的用量（192m / 100m），已经采到的两个新 Pod 也没算进去。按 HPA 控制器的规则（文档和 v1.31 源码 replica_calculator.go 一致），新 Pod 在这一刻分成两种：

  • 缺指标：Metrics Server 还没有它的数据，比如上面没列出来的第四个 Pod。
  • 视为未就绪：有数据，但 Pod 还在 CPU 初始化期内（--horizontal-pod-autoscaler-cpu-initialization-period，默认 5 分钟），并且这条样本的采集时间早于「Pod 变为 Ready 的时刻 + 采样窗口」，说明样本里混有启动阶段的用量，于是被丢掉。另一个参数 --horizontal-pod-autoscaler-initial-readiness-delay（默认 30 秒）处理的是刚启动时 Ready 状态来回跳的情况，这里用不上。

两种 Pod 都先排除，只用剩下的 Pod 算平均值，所以 status 里显示的是 192%、201% 这种只代表老 Pod 的数。要扩容时，控制器再把这两种 Pod 都按 0% 补回去重算：1 个 201% 加 3 个 0%，平均约 50%，落在默认 10% 的容忍度以内，所以不动。文档特别说明，status 报告的是没有做这层修正的原始平均值，所以看 TARGETS 会以为该继续扩。控制器内部每一步怎么算的没法直接看到，以上是按源码规则对日志的解释。

第二步：再过 50 秒，4 → 5。 新 Pod 有了指标，平均 140%，ceil(4 × 140 / 50) = 12，被 maxReplicas 截到 5。此时 Conditions：

ScalingLimited  True    TooManyReplicas   the desired replica count is more than the maximum replica count

5 个副本时平均利用率还有 120% 左右，压力明显超过容量。TooManyReplicas 持续为 True，说明上限设小了，或者该优化单个请求的开销，HPA 自己解决不了。

同样的负载一共跑了三轮。从负载 Pod 开始运行（第二轮取它变为 Ready 的时刻）到第一次扩容，分别是 20 秒、35 秒（03:52:39 → 03:53:14）和 22 秒；第一次到第二次扩容分别隔了 50、46、48 秒。三轮的步数和副本数完全一样。第一步的时间差，推测来自负载开始的时刻与 Metrics Server 采样、HPA 15 秒同步周期之间的相位不同。所以「施压后多久扩容」只能给一个范围，这个环境里是 20～35 秒。

缩容：指标先滞后，再等稳定窗口

60 秒窗口

03:50:25 前后删掉负载 Pod（容器具体什么时候停下没有精确记录）：

03:50:30 cpu=121% desired=5 spec=5 ready=5
03:50:46 cpu=112% desired=5 spec=5 ready=5
03:51:01 cpu=48% desired=5 spec=5 ready=5
03:51:12 cpu=1% desired=5 spec=5 ready=5
03:51:53 cpu=1% desired=5 spec=5 ready=5
03:52:00 cpu=1% desired=1 spec=1 ready=1
2026-10-12T03:51:57Z   SuccessfulRescale   New size: 1; reason: All metrics below target

这 90 秒分两段。

前 35～45 秒，HPA 看到的还是旧指标。 删掉负载半分钟后，HPA 看到的还是 112%。不过这一轮不能完全归到指标上：负载 Pod 的 PID 1 是 sh -c，不处理 SIGTERM，虽然用了 --grace-period=0 --force，容器实际在什么时刻停下没有记录。

为了分清楚，第三轮让负载脚本到点自己退出（容器 finishedAt 为 04:17:36），同时每 5 秒读一次 Metrics API 的原始数据（kubectl get --raw /apis/metrics.k8s.io/v1beta1/namespaces/notes-lab/pods），里面有每个 Pod 的样本时间戳 timestamp 和采样窗口 window：

04:17:48 cpu=107% | 2jpf9:75034304n@04:17:42/18.19s ... kcwpt:55853833n@04:17:43/15.236s
04:18:01 cpu=79%  | 2jpf9:218088n@04:17:56/13.898s cpbpk:61543810n@04:17:45/19.299s ...
04:18:11 cpu=13%  | (同上)
04:18:28 cpu=1%   | 2jpf9:194471n@04:18:07/10.454s cpbpk:187411n@04:18:03/18.398s ...

这一次负载确定在 04:17:36 停了：

  • Metrics Server 那边，各 Pod 到 04:17:52～04:18:03 才出现空闲样本（0.2m 左右），比负载停止晚 16～27 秒。每个 Pod 的样本时间戳各不相同，窗口在 10～27 秒之间，晚停的那部分时间还在窗口里。
  • HPA 那边又晚一点，要等下一次同步才读到新样本：先是 79%（那次同步用的样本窗口跨过了停止时刻，5 个 Pod 的样本都还带着负载的尾巴），然后 13%，04:18:28 才到 1%，离负载停止 52 秒。

所以即使负载干净利落地停下，这个环境里也有约 50 秒的指标滞后。第一轮的 35～45 秒和这个量级一致，但当时的负载停止时刻不精确，那一轮的数字只能当参考。

剩下的约 60 秒是稳定窗口。 03:51:01 那次同步看到 48%，比值 48 / 50 = 0.96，偏离 1 不到默认容忍度 0.1，按规则直接保持当前副本数 5。之后每次同步的建议值都是 1，但缩容时 HPA 会取窗口内所有建议值中的最大值。03:51:00 左右那个 5 过期之后，才在 03:51:57 缩到 1。缩容策略允许一次减 100%，指标又是从 48% 直接跳到 1%，中间没有留下 2、3 这样的建议值，所以 5 直接到 1。

第三轮的指标中间经过了一个 13%（ceil(5 × 13 / 50) = 2），同样的 60 秒窗口下就缩了两步：04:18:56 New size: 2，04:19:11 New size: 1。

默认 300 秒窗口

把 behavior.scaleDown 删掉，恢复默认值，重新施压 86 秒（03:52:39～03:54:05）。撤压约 80 秒后的 Conditions：

Metrics:                                               ( current / target )
  resource cpu on pods  (as a percentage of request):  1% (1m) / 50%
Conditions:
  Type            Status  Reason               Message
  ----            ------  ------               -------
  AbleToScale     True    ScaleDownStabilized  recent recommendations were higher than current one, applying the highest recent recommendation

利用率 1%，desiredReplicas 还是 5。status.desiredReplicas 已经是经过稳定窗口处理后的值，不是公式直接算出来的那个数。前后的记录：

03:54:31 cpu=89% desired=5 spec=5 ready=5
03:54:46 cpu=17% desired=5 spec=5 ready=5
03:55:02 cpu=1% desired=5 spec=5 ready=5
   ……（约 4 分半钟保持不变）
03:59:29 cpu=1% desired=5 spec=5 ready=5
03:59:35 cpu=1% desired=2 spec=2 ready=2
03:59:50 cpu=1% desired=1 spec=1 ready=1
2026-10-12T03:59:31Z   SuccessfulRescale   New size: 2; reason: All metrics below target
2026-10-12T03:59:45Z   SuccessfulRescale   New size: 1; reason: All metrics below target

这一次缩了两步：5 → 2 → 1，中间隔 14 秒，正好约等于一个同步周期。把撤压后几次同步的建议值排出来，就能对上：

同步时刻（约）看到的利用率当次建议值300 秒后过期
03:54:3089%ceil(5×89/50)=9 → 截到 503:59:30
03:54:4517%ceil(5×17/50)=203:59:45
03:55:00 起1%1—

03:59:30 时，最后一个 5 移出窗口，窗口内最大值变成 2；再过 15 秒，2 也过期，只剩 1。这和第三轮 60 秒窗口下的两步缩容是同一回事，只是窗口长度不同。

看到这里就能理解：缩容稳定窗口不是「指标低于目标后再等 N 秒」，而是「取过去 N 秒内建议值的最大值」。撤压后最后一个高建议值出现在什么时候，加上 N 秒，就是缩容时刻。

手动 scale 为什么能顶住约 5 分钟

HPA 运行期间把 Deployment 手动扩到 3：

04:02:20 deployment.apps/burn scaled
04:02:21 spec=3 ready=1 desired=1
04:02:31 spec=3 ready=3 desired=3

CPU 一直是 1%，HPA 却没有马上缩回去，Conditions 同样是 ScaleDownStabilized，直到 04:07:45 才 New size: 1，距手动扩容 5 分 25 秒。稳定窗口里记的是 HPA 每次自己算出的建议值，不是手动设的副本数。那么「建议 3」是哪来的？推测是这样：手动加出来的 2 个 Pod 已经 Running、但 Metrics Server 还没采到它们时，属于「缺指标」。按 v1.31 源码，缩容方向上缺指标的 Pod 按 request 的 max(100%, 目标值) 也就是 100% 补值，平均变成 (1 + 100 + 100) / 3 ≈ 67%，比值约 1.34。原始比值（0.02）要缩容，补值后的比值却要扩容，方向反了，这时控制器按规则直接返回当前副本数 3，于是窗口里留下了一条「建议 3」，又保留了 300 秒。还处于 Pending 的 Pod 不算缺指标，算未就绪，缩容时直接排除。04:07:45 距手动扩容 5 分 25 秒，比 300 秒多出的二十几秒，大致对得上新 Pod 从启动到有指标的时间，但每次同步的建议值没法直接看到。

实际影响是：手动 scale 在默认配置下能「顶住」约 5 分钟，然后被 HPA 改回去。临时救火可以这么做，但它不是可靠的覆盖手段；要长期改副本范围，应该改 HPA 的 minReplicas。

缺少 CPU request 时的 <unknown>

准备两个 Deployment：nores 只有一个 nginx 容器，完全不写 resources；sidecar 有两个容器，web 写了 cpu: 50m，日志代理容器 log-agent 没写。

containers:
  - name: web
    image: nginx:alpine
    resources:
      requests:
        cpu: 50m
  - name: log-agent
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
kubectl -n notes-lab autoscale deployment nores --cpu-percent=50 --min=1 --max=3
kubectl -n notes-lab autoscale deployment sidecar --cpu-percent=50 --min=1 --max=3

46 秒后两个都是 <unknown>：

NAME      REFERENCE            TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
burn      Deployment/burn      cpu: 1%/50%          1         5         1          14m
nores     Deployment/nores     cpu: <unknown>/50%   1         3         1          46s
sidecar   Deployment/sidecar   cpu: <unknown>/50%   1         3         1          46s

sidecar 的事件按时间先后变了三次：

Warning  FailedGetResourceMetric  31s  horizontal-pod-autoscaler  failed to get cpu utilization: unable to get metrics for resource cpu: no metrics returned from resource metrics API
Warning  FailedGetResourceMetric  16s  horizontal-pod-autoscaler  failed to get cpu utilization: did not receive metrics for targeted pods (pods might be unready)
Warning  FailedGetResourceMetric  0s   horizontal-pod-autoscaler  failed to get cpu utilization: missing request for cpu in container log-agent of Pod sidecar-77c5794767-bbvfv

前两条出现在 Pod 刚启动、Metrics Server 还没采到它的时候，过一两个同步周期就没了。第三条才是真正的原因，并且会一直重复，Conditions 里也写着：

ScalingActive  False   FailedGetResourceMetric  the HPA was unable to compute the replica count: failed to get cpu utilization: missing request for cpu in container log-agent of Pod sidecar-77c5794767-bbvfv

两点值得记住：

  • 只要有一个容器缺 request，整个 Pod 的利用率就算不出来。 web 明明写了 50m，HPA 照样放弃。这和官方文档一致：Pod 中有容器没设对应的 request，这个 Pod 的 CPU 利用率就无定义，HPA 对该指标不采取任何动作。sidecar 和注入式代理最容易漏这一项。这条规则针对的是 type: Resource 指标，按整个 Pod 算，原生 sidecar（restartPolicy: Always 的 init 容器）也算在内。如果只想按某一个容器算，可以改用 type: ContainerResource，这时只需要那个容器有 request。
  • 这时 Metrics Server 是好的。 同一时刻 kubectl top pod -l app=sidecar --containers 能正常列出 web 和 log-agent 的用量。top 有数而 HPA 是 <unknown>，先查 request，不要去重装 Metrics Server。

给 log-agent 补上 request：

kubectl -n notes-lab set resources deploy/sidecar -c log-agent --requests=cpu=10m

修改会触发滚动更新。52 秒后 TARGETS 变成 cpu: 0%/50%。滚动更新期间，rollout status 有一段时间一直停在 1 old replicas are pending termination。推测是 sleep 作为 PID 1 不处理 SIGTERM，旧 Pod 要等满默认 30 秒的宽限期才退出，这一点这次没有单独计时。滚动更新的过程见 Deployment。

<unknown> 的其他来源（Metrics API 不可用、目标被设为 0 副本、多指标里有一个读取失败）以及「期望副本涨了但 Pod 起不来」的情况，放在 HPA 不扩容排查 里。

小结

这次实验里能直接量到的几个数：

  • 施压后 20～35 秒第一次扩容，再过 46～50 秒第二次。按控制器规则，新 Pod 在有指标之前、初始化期内的样本作废之前，扩容时都按 0% 计算，所以第二次要等它们的有效指标出现，这是根据源码的推测。
  • CPU limit 决定了单个 Pod 利用率的上限（这里是 200%），也就决定了每一步最多能扩多少。
  • 负载确定停止后，HPA 约 50 秒才看到 1%（第三轮实测），然后才开始计算稳定窗口；窗口取的是这段时间内建议值的最大值，所以缩容可能分几步完成。
  • 手动 scale 出来的副本，在默认窗口下约 5 分钟后被 HPA 改回去。
  • 使用 Resource 类型的 CPU 指标时，Pod 里任何一个容器缺 CPU request，HPA 都是 <unknown>；判断真正原因要看最后一直重复的那条事件，开头几条可能只是指标还没采到。

清理

kubectl delete namespace notes-lab

request 和 limit 的含义见探针与资源管理，它们如何决定 Pod 的 QoS 等级见 QoS。
