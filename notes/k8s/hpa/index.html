HPA 水平扩缩容

HorizontalPodAutoscaler（HPA）定期读取指标，算出目标副本数，再改写 Deployment 的 spec.replicas。它不会调大单个 Pod 的 CPU，也不会一有流量就立刻扩容。用 CPU 利用率做指标时，百分比是相对于容器 CPU request 算的，所以 request 必须写。

前半部分看机制：施压之后每一步扩容发生在什么时候、为什么是这个副本数，撤压之后为什么要等一段时间才缩回去，以及 <unknown> 是怎么来的。后半部分是排查：故意把 HPA 弄坏，记录每种故障下 Conditions、事件和副本字段各显示什么。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），已经装好 Metrics Server，实验放在单独的 notes-lab namespace 里。时间都是 UTC。

准备一个真正吃 CPU 的服务

空闲的 nginx 几乎不耗 CPU，单次请求也撑不起持续负载。这里用 busybox 自带的 httpd 加一个 CGI 脚本：每个请求在 shell 里空转 3 万次循环再返回，CPU 消耗和请求量成正比，也不用额外拉镜像。

apiVersion: v1
kind: ConfigMap
metadata:
  name: burn-cgi
data:
  burn: |
    #!/bin/sh
    i=0
    while [ $i -lt 30000 ]; do i=$((i+1)); done
    echo "Content-Type: text/plain"
    echo
    echo "ok $(hostname)"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: burn
spec:
  replicas: 1
  selector:
    matchLabels:
      app: burn
  template:
    metadata:
      labels:
        app: burn
    spec:
      containers:
        - name: web
          image: busybox:1.36
          command: ["httpd", "-f", "-p", "8080", "-h", "/www"]
          ports:
            - containerPort: 8080
          readinessProbe:
            tcpSocket:
              port: 8080
            periodSeconds: 2
          resources:
            requests:
              cpu: 100m
              memory: 16Mi
            limits:
              cpu: 200m
              memory: 64Mi
          volumeMounts:
            - name: cgi
              mountPath: /www/cgi-bin
      volumes:
        - name: cgi
          configMap:
            name: burn-cgi
            defaultMode: 0755   # CGI 脚本要有执行权限
---
apiVersion: v1
kind: Service
metadata:
  name: burn
spec:
  selector:
    app: burn
  ports:
    - port: 80
      targetPort: 8080

CPU limit 设成 request 的两倍，这个选择后面会影响扩容步长。先测一次请求：

$ kubectl -n notes-lab run t --image=busybox:1.36 --restart=Never --rm -i -- sh -c 'time wget -qO- http://burn/cgi-bin/burn'
ok burn-5c877494c8-8s85p
real	0m 0.27s

HPA 和它被补全的默认行为

目标是平均 CPU 利用率 50%，最多 5 个副本。缩容稳定窗口默认是 300 秒，为了在几分钟内看到完整过程，第一轮先改成 60 秒，后面再换回默认值对比：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: burn
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: burn
  minReplicas: 1
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60

提交后读回来，behavior 里没写的部分已经被补上了：

$ kubectl -n notes-lab get hpa burn -o yaml
spec:
  behavior:
    scaleDown:
      policies:
      - periodSeconds: 15
        type: Percent
        value: 100
      selectPolicy: Max
      stabilizationWindowSeconds: 60
    scaleUp:
      policies:
      - periodSeconds: 15
        type: Pods
        value: 4
      - periodSeconds: 15
        type: Percent
        value: 100
      selectPolicy: Max
      stabilizationWindowSeconds: 0

意思是：扩容没有稳定窗口，每 15 秒最多加 4 个 Pod 或翻一倍（取较大者）；缩容每 15 秒最多减掉 100%，也就是一步就能缩到 minReplicas。

刚创建的 HPA 会短暂显示 <unknown>：

03:46:17 horizontalpodautoscaler.autoscaling/burn created
NAME   REFERENCE         TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
burn   Deployment/burn   cpu: <unknown>/50%   1         5         0          0s

16 秒后变成 cpu: 1%/50%，Conditions 里 ScalingActive 为 True / ValidMetricFound。控制器默认每 15 秒同步一次，第一次同步之前没有数据，这种 <unknown> 不用管。长时间不消失的那种在最后一节。

扩容时间线

起一个负载 Pod，里面 4 个循环并发请求 burn：

kubectl -n notes-lab run load --image=busybox:1.36 --restart=Never -- \
  sh -c 'for n in 1 2 3 4; do (while true; do wget -qO- http://burn/cgi-bin/burn >/dev/null; done) & done; wait'

另开一个循环，每 5 秒记录一次 HPA 状态和 Deployment 副本：

while true; do
  echo "$(date -u +%T) cpu=$(kubectl -n notes-lab get hpa burn -o jsonpath='{.status.currentMetrics[0].resource.current.averageUtilization}% desired={.status.desiredReplicas}') \
$(kubectl -n notes-lab get deploy burn -o jsonpath='spec={.spec.replicas} ready={.status.readyReplicas}')"
  sleep 5
done

负载容器 03:47:59 开始运行。记录如下（略去重复行）：

03:48:17 cpu=1% desired=1 spec=1 ready=1
03:48:24 cpu=161% desired=4 spec=4 ready=1
03:48:37 cpu=201% desired=4 spec=4 ready=3
03:48:42 cpu=201% desired=4 spec=4 ready=4
03:48:54 cpu=192% desired=4 spec=4 ready=4
03:49:05 cpu=192% desired=4 spec=4 ready=4
03:49:10 cpu=140% desired=5 spec=5 ready=4
03:49:17 cpu=140% desired=5 spec=5 ready=5
03:49:43 cpu=125% desired=5 spec=5 ready=5

对应的 HPA 事件：

TIME                   REASON              MSG
2026-10-12T03:48:19Z   SuccessfulRescale   New size: 4; reason: cpu resource utilization (percentage of request) above target
2026-10-12T03:49:09Z   SuccessfulRescale   New size: 5; reason: cpu resource utilization (percentage of request) above target

逐步拆开看。

第一步：施压 20 秒后，1 → 4。 官方给出的公式是：

期望副本数 = ceil( 当前副本数 × 当前指标值 / 目标值 )

当时唯一的 Pod 利用率 161%，ceil(1 × 161 / 50) = ceil(3.22) = 4。扩容策略允许这一步加到 5（+4 个 Pod），所以 4 是公式算出来的，不是被策略截断的。

这里能看出 CPU limit 的影响。limit 是 request 的 2 倍，单个 Pod 的利用率最多到 200%，日志里也确实停在 201%、200%。不管真实压力有多大，从 1 个副本出发，第一步最多只能算出 ceil(1 × 200 / 50) = 4。limit 越贴近 request，HPA 能看到的压力上限越低，扩容就要分更多步走。

中间的停顿：4 个 Pod 都就绪了，利用率还显示 201%，却 30 多秒没有继续扩。 按公式 ceil(4 × 201 / 50) = 17，应该直接到上限 5。原因在于这 201% 只来自老 Pod。03:48:54 的 kubectl top 只列出了 3 个 Pod，新 Pod 的指标还没采到：

NAME                    CPU(cores)   MEMORY(bytes)
burn-5c877494c8-8s85p   192m         1Mi
burn-5c877494c8-9np2d   98m          0Mi
burn-5c877494c8-scvtb   120m         2Mi

可这时 TARGETS 的 192% 正好等于老 Pod 一个的用量（192m / 100m），已经采到的两个新 Pod 也没算进去。按 HPA 控制器的规则（文档和 v1.31 源码 replica_calculator.go 一致），新 Pod 在这一刻分成两种：

  • 缺指标：Metrics Server 还没有它的数据，比如上面没列出来的第四个 Pod。
  • 视为未就绪：有数据，但 Pod 还在 CPU 初始化期内（--horizontal-pod-autoscaler-cpu-initialization-period，默认 5 分钟），并且这条样本的采集时间早于「Pod 变为 Ready 的时刻 + 采样窗口」，说明样本里混有启动阶段的用量，于是被丢掉。另一个参数 --horizontal-pod-autoscaler-initial-readiness-delay（默认 30 秒）处理的是刚启动时 Ready 状态来回跳的情况，这里用不上。

两种 Pod 都先排除，只用剩下的 Pod 算平均值，所以 status 里显示的是 192%、201% 这种只代表老 Pod 的数。要扩容时，控制器再把这两种 Pod 都按 0% 补回去重算：1 个 201% 加 3 个 0%，平均约 50%，落在默认 10% 的容忍度以内，所以不动。文档特别说明，status 报告的是没有做这层修正的原始平均值，所以看 TARGETS 会以为该继续扩。控制器内部每一步怎么算的没法直接看到，以上是按源码规则对日志的解释。

第二步：再过 50 秒，4 → 5。 新 Pod 有了指标，平均 140%，ceil(4 × 140 / 50) = 12，被 maxReplicas 截到 5。此时 Conditions：

ScalingLimited  True    TooManyReplicas   the desired replica count is more than the maximum replica count

5 个副本时平均利用率还有 120% 左右，压力明显超过容量。TooManyReplicas 持续为 True，说明上限设小了，或者该优化单个请求的开销，HPA 自己解决不了。

同样的负载一共跑了三轮。从负载 Pod 开始运行（第二轮取它变为 Ready 的时刻）到第一次扩容，分别是 20 秒、35 秒（03:52:39 → 03:53:14）和 22 秒；第一次到第二次扩容分别隔了 50、46、48 秒。三轮的步数和副本数完全一样。第一步的时间差，推测来自负载开始的时刻与 Metrics Server 采样、HPA 15 秒同步周期之间的相位不同。所以「施压后多久扩容」只能给一个范围，这个环境里是 20～35 秒。

缩容：指标先滞后，再等稳定窗口

60 秒窗口

03:50:25 前后删掉负载 Pod（容器具体什么时候停下没有精确记录）：

03:50:30 cpu=121% desired=5 spec=5 ready=5
03:50:46 cpu=112% desired=5 spec=5 ready=5
03:51:01 cpu=48% desired=5 spec=5 ready=5
03:51:12 cpu=1% desired=5 spec=5 ready=5
03:51:53 cpu=1% desired=5 spec=5 ready=5
03:52:00 cpu=1% desired=1 spec=1 ready=1
2026-10-12T03:51:57Z   SuccessfulRescale   New size: 1; reason: All metrics below target

这 90 秒分两段。

前 35～45 秒，HPA 看到的还是旧指标。 删掉负载半分钟后，HPA 看到的还是 112%。不过这一轮不能完全归到指标上：负载 Pod 的 PID 1 是 sh -c，不处理 SIGTERM，虽然用了 --grace-period=0 --force，容器实际在什么时刻停下没有记录。

为了分清楚，第三轮让负载脚本到点自己退出（容器 finishedAt 为 04:17:36），同时每 5 秒读一次 Metrics API 的原始数据（kubectl get --raw /apis/metrics.k8s.io/v1beta1/namespaces/notes-lab/pods），里面有每个 Pod 的样本时间戳 timestamp 和采样窗口 window：

04:17:48 cpu=107% | 2jpf9:75034304n@04:17:42/18.19s ... kcwpt:55853833n@04:17:43/15.236s
04:18:01 cpu=79%  | 2jpf9:218088n@04:17:56/13.898s cpbpk:61543810n@04:17:45/19.299s ...
04:18:11 cpu=13%  | (同上)
04:18:28 cpu=1%   | 2jpf9:194471n@04:18:07/10.454s cpbpk:187411n@04:18:03/18.398s ...

这一次负载确定在 04:17:36 停了：

  • Metrics Server 那边，各 Pod 到 04:17:52～04:18:03 才出现空闲样本（0.2m 左右），比负载停止晚 16～27 秒。每个 Pod 的样本时间戳各不相同，窗口在 10～27 秒之间，晚停的那部分时间还在窗口里。
  • HPA 那边又晚一点，要等下一次同步才读到新样本：先是 79%（那次同步用的样本窗口跨过了停止时刻，5 个 Pod 的样本都还带着负载的尾巴），然后 13%，04:18:28 才到 1%，离负载停止 52 秒。

所以即使负载干净利落地停下，这个环境里也有约 50 秒的指标滞后。第一轮的 35～45 秒和这个量级一致，但当时的负载停止时刻不精确，那一轮的数字只能当参考。

剩下的约 60 秒是稳定窗口。 03:51:01 那次同步看到 48%，比值 48 / 50 = 0.96，偏离 1 不到默认容忍度 0.1，按规则直接保持当前副本数 5。之后每次同步的建议值都是 1，但缩容时 HPA 会取窗口内所有建议值中的最大值。03:51:00 左右那个 5 过期之后，才在 03:51:57 缩到 1。缩容策略允许一次减 100%，指标又是从 48% 直接跳到 1%，中间没有留下 2、3 这样的建议值，所以 5 直接到 1。

第三轮的指标中间经过了一个 13%（ceil(5 × 13 / 50) = 2），同样的 60 秒窗口下就缩了两步：04:18:56 New size: 2，04:19:11 New size: 1。

默认 300 秒窗口

把 behavior.scaleDown 删掉，恢复默认值，重新施压 86 秒（03:52:39～03:54:05）。撤压约 80 秒后的 Conditions：

Metrics:                                               ( current / target )
  resource cpu on pods  (as a percentage of request):  1% (1m) / 50%
Conditions:
  Type            Status  Reason               Message
  ----            ------  ------               -------
  AbleToScale     True    ScaleDownStabilized  recent recommendations were higher than current one, applying the highest recent recommendation

利用率 1%，desiredReplicas 还是 5。status.desiredReplicas 已经是经过稳定窗口处理后的值，不是公式直接算出来的那个数。前后的记录：

03:54:31 cpu=89% desired=5 spec=5 ready=5
03:54:46 cpu=17% desired=5 spec=5 ready=5
03:55:02 cpu=1% desired=5 spec=5 ready=5
   ……（约 4 分半钟保持不变）
03:59:29 cpu=1% desired=5 spec=5 ready=5
03:59:35 cpu=1% desired=2 spec=2 ready=2
03:59:50 cpu=1% desired=1 spec=1 ready=1
2026-10-12T03:59:31Z   SuccessfulRescale   New size: 2; reason: All metrics below target
2026-10-12T03:59:45Z   SuccessfulRescale   New size: 1; reason: All metrics below target

这一次缩了两步：5 → 2 → 1，中间隔 14 秒，正好约等于一个同步周期。把撤压后几次同步的建议值排出来，就能对上：

同步时刻（约）看到的利用率当次建议值300 秒后过期
03:54:3089%ceil(5×89/50)=9 → 截到 503:59:30
03:54:4517%ceil(5×17/50)=203:59:45
03:55:00 起1%1—

03:59:30 时，最后一个 5 移出窗口，窗口内最大值变成 2；再过 15 秒，2 也过期，只剩 1。这和第三轮 60 秒窗口下的两步缩容是同一回事，只是窗口长度不同。

看到这里就能理解：缩容稳定窗口不是「指标低于目标后再等 N 秒」，而是「取过去 N 秒内建议值的最大值」。撤压后最后一个高建议值出现在什么时候，加上 N 秒，就是缩容时刻。

手动 scale 为什么能顶住约 5 分钟

HPA 运行期间把 Deployment 手动扩到 3：

04:02:20 deployment.apps/burn scaled
04:02:21 spec=3 ready=1 desired=1
04:02:31 spec=3 ready=3 desired=3

CPU 一直是 1%，HPA 却没有马上缩回去，Conditions 同样是 ScaleDownStabilized，直到 04:07:45 才 New size: 1，距手动扩容 5 分 25 秒。稳定窗口里记的是 HPA 每次自己算出的建议值，不是手动设的副本数。那么「建议 3」是哪来的？推测是这样：手动加出来的 2 个 Pod 已经 Running、但 Metrics Server 还没采到它们时，属于「缺指标」。按 v1.31 源码，缩容方向上缺指标的 Pod 按 request 的 max(100%, 目标值) 也就是 100% 补值，平均变成 (1 + 100 + 100) / 3 ≈ 67%，比值约 1.34。原始比值（0.02）要缩容，补值后的比值却要扩容，方向反了，这时控制器按规则直接返回当前副本数 3，于是窗口里留下了一条「建议 3」，又保留了 300 秒。还处于 Pending 的 Pod 不算缺指标，算未就绪，缩容时直接排除。04:07:45 距手动扩容 5 分 25 秒，比 300 秒多出的二十几秒，大致对得上新 Pod 从启动到有指标的时间，但每次同步的建议值没法直接看到。

实际影响是：手动 scale 在默认配置下能「顶住」约 5 分钟，然后被 HPA 改回去。临时救火可以这么做，但它不是可靠的覆盖手段；要长期改副本范围，应该改 HPA 的 minReplicas。

缺少 CPU request 时的 <unknown>

准备两个 Deployment：nores 只有一个 nginx 容器，完全不写 resources；sidecar 有两个容器，web 写了 cpu: 50m，日志代理容器 log-agent 没写。

containers:
  - name: web
    image: nginx:alpine
    resources:
      requests:
        cpu: 50m
  - name: log-agent
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
kubectl -n notes-lab autoscale deployment nores --cpu-percent=50 --min=1 --max=3
kubectl -n notes-lab autoscale deployment sidecar --cpu-percent=50 --min=1 --max=3

46 秒后两个都是 <unknown>：

NAME      REFERENCE            TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
burn      Deployment/burn      cpu: 1%/50%          1         5         1          14m
nores     Deployment/nores     cpu: <unknown>/50%   1         3         1          46s
sidecar   Deployment/sidecar   cpu: <unknown>/50%   1         3         1          46s

sidecar 的事件按时间先后变了三次：

Warning  FailedGetResourceMetric  31s  horizontal-pod-autoscaler  failed to get cpu utilization: unable to get metrics for resource cpu: no metrics returned from resource metrics API
Warning  FailedGetResourceMetric  16s  horizontal-pod-autoscaler  failed to get cpu utilization: did not receive metrics for targeted pods (pods might be unready)
Warning  FailedGetResourceMetric  0s   horizontal-pod-autoscaler  failed to get cpu utilization: missing request for cpu in container log-agent of Pod sidecar-77c5794767-bbvfv

前两条出现在 Pod 刚启动、Metrics Server 还没采到它的时候，过一两个同步周期就没了。第三条才是真正的原因，并且会一直重复，Conditions 里也写着：

ScalingActive  False   FailedGetResourceMetric  the HPA was unable to compute the replica count: failed to get cpu utilization: missing request for cpu in container log-agent of Pod sidecar-77c5794767-bbvfv

两点值得记住：

  • 只要有一个容器缺 request，整个 Pod 的利用率就算不出来。 web 明明写了 50m，HPA 照样放弃。这和官方文档一致：Pod 中有容器没设对应的 request，这个 Pod 的 CPU 利用率就无定义，HPA 对该指标不采取任何动作。sidecar 和注入式代理最容易漏这一项。这条规则针对的是 type: Resource 指标，按整个 Pod 算，原生 sidecar（restartPolicy: Always 的 init 容器）也算在内。如果只想按某一个容器算，可以改用 type: ContainerResource，这时只需要那个容器有 request。
  • 这时 Metrics Server 是好的。 同一时刻 kubectl top pod -l app=sidecar --containers 能正常列出 web 和 log-agent 的用量。top 有数而 HPA 是 <unknown>，先查 request，不要去重装 Metrics Server。

给 log-agent 补上 request：

kubectl -n notes-lab set resources deploy/sidecar -c log-agent --requests=cpu=10m

修改会触发滚动更新。52 秒后 TARGETS 变成 cpu: 0%/50%。滚动更新期间，rollout status 有一段时间一直停在 1 old replicas are pending termination。推测是 sleep 作为 PID 1 不处理 SIGTERM，旧 Pod 要等满默认 30 秒的宽限期才退出，这一点这次没有单独计时。滚动更新的过程见 Deployment。

<unknown> 的其他来源（Metrics API 不可用、目标被设为 0 副本、多指标里有一个读取失败）以及「期望副本涨了但 Pod 起不来」的情况，放在下面的排查部分。

小结

这次实验里能直接量到的几个数：

  • 施压后 20～35 秒第一次扩容，再过 46～50 秒第二次。按控制器规则，新 Pod 在有指标之前、初始化期内的样本作废之前，扩容时都按 0% 计算，所以第二次要等它们的有效指标出现，这是根据源码的推测。
  • CPU limit 决定了单个 Pod 利用率的上限（这里是 200%），也就决定了每一步最多能扩多少。
  • 负载确定停止后，HPA 约 50 秒才看到 1%（第三轮实测），然后才开始计算稳定窗口；窗口取的是这段时间内建议值的最大值，所以缩容可能分几步完成。
  • 手动 scale 出来的副本，在默认窗口下约 5 分钟后被 HPA 改回去。
  • 使用 Resource 类型的 CPU 指标时，Pod 里任何一个容器缺 CPU request，HPA 都是 <unknown>；判断真正原因要看最后一直重复的那条事件，开头几条可能只是指标还没采到。

不扩容排查：先分清是哪一种

前面看的是正常情况下扩缩的时间线。这一部分反过来，专门把 HPA 弄坏，看它坏的时候都留下了什么线索。

看到 Pod 数没涨，先分清是哪一种：HPA 没有提高期望副本数，还是期望副本已经提高了，新 Pod 却没跑起来。前一种去看 HPA 自己的 Conditions 和事件，后一种去看 ReplicaSet 和 Pod 的事件。HPA 只负责改 spec.replicas，改完之后的事它不管，也基本不报错。

排查实验的准备

排查部分是另一次运行（2026-10-13），环境同上，两个工作节点是 worker、worker2。被扩缩的还是上面的 burn，把前面的清单保存为 burn.yaml：

第一站：Metrics API 本身

HPA 的 CPU 指标来自 metrics.k8s.io，由 Metrics Server 提供。先确认这条链路是通的，只读两条命令：

$ kubectl get apiservice v1beta1.metrics.k8s.io
NAME                     SERVICE                      AVAILABLE   AGE
v1beta1.metrics.k8s.io   kube-system/metrics-server   True        57d
$ kubectl get apiservice v1beta1.metrics.k8s.io -o jsonpath="{range .status.conditions[*]}{.type}={.status} {.reason}: {.message}{\"\n\"}{end}"
Available=True Passed: all checks passed

AVAILABLE 为 False 时，message 里会写聚合层连不上 Metrics Server 的原因，这时整个集群里用 Resource / ContainerResource 指标的 HPA 都会是 <unknown>，kubectl top 也会失败；走 custom/external metrics API 的指标不经过 Metrics Server，不受这一条影响。再直接读一个 namespace 的原始数据：

kubectl get --raw /apis/metrics.k8s.io/v1beta1/namespaces/notes-lab/pods

namespace 刚建好、还没有 Pod 时，返回的是一个空列表。有一个细节要注意：对一个根本不存在的 namespace 发同样的请求，返回也一模一样，不报错：

{"kind":"PodMetricsList","apiVersion":"metrics.k8s.io/v1beta1","metadata":{},"items":[]}

所以 items 为空不能说明 Metrics Server 坏了，先确认 namespace 名有没有拼错、里面有没有在跑的 Pod。部署好服务后再读一次，每个容器都有自己的数（这是后面实验进行中的读数，nores、sidecar 是下一节创建的）：

$ kubectl get --raw /apis/metrics.k8s.io/v1beta1/namespaces/notes-lab/pods | python3 -m json.tool | grep -E "\"name\"|cpu"
                "name": "burn-5c877494c8-q5kcd",
                    "name": "web",
                        "cpu": "191129n",
                "name": "nores-7d494d6f7-6kfpf",
                    "name": "nginx",
                        "cpu": "0",
                "name": "sidecar-6fd465ddb9-kjvgk",
                    "name": "log-agent",
                        "cpu": "24337n",
                    "name": "web",
                        "cpu": "0",

单位 n 是纳核，191129n 约等于 0.19m。这个集群的 Metrics Server 参数里有 --metric-resolution=15s，也就是每 15 秒向 kubelet 采一次。这一层通了，后面的 <unknown> 就不该再怀疑 Metrics Server。

group "" 指的是核心组，也就是 v1。看到 FailedGetScale，逐字核对 scaleTargetRef 的三个字段。

容器缺 CPU request：ScalingActive=False FailedGetResourceMetric

这一种在上文已经复现过，这次运行用的也是 nores 和 sidecar 两个 Deployment（nores 用 kubectl -n notes-lab create deployment nores --image=nginx:alpine 创建；sidecar 的 log-agent 命令换成了 trap 'exit 0' TERM; while true; do sleep 1; done，同样没写 request）。这里只补两处上文没有展开的地方。

第一处是 -o yaml 里的状态。describe 会把字段排版好，原始 status 能看到两个容易误读的值：

- lastTransitionTime: "2026-10-13T07:04:10Z"
  message: 'the HPA was unable to compute the replica count: failed to get cpu utilization:
    missing request for cpu in container nginx of Pod nores-7d494d6f7-6kfpf'
  reason: FailedGetResourceMetric
  status: "False"
  type: ScalingActive

- type: ""

desiredReplicas: 0 不是 HPA 想把服务缩到 0，只是这一轮没算出结果；AbleToScale 仍是 True，Deployment 也一直是 1 个副本。拿 desiredReplicas 写告警的话，这种情况会误报。同一时刻 kubectl top pod -l app=nores 正常输出 0m，再次说明指标链路是好的，缺的是 request。

第二处是修法。多容器 Pod 里只有 sidecar 缺 request 时，除了给 sidecar 补上，还可以让 HPA 只看主容器，改用 ContainerResource（v1.30 起 GA）：

  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: sidecar
  minReplicas: 1
  maxReplicas: 3
  metrics:

      containerResource:
        name: cpu
        container: web
        target:
          type: Utilization
          averageUtilization: 50

log-agent 依旧没有 request，HPA 已经能算了。这种改法只动 HPA，不触发 Deployment 的滚动更新。代价是 sidecar 的 CPU 不再参与决策，日志代理自己被打满时 HPA 看不到。

补充：刚滚动更新完的几十秒

后面做调度实验时，先给 burn 加了反亲和规则，触发了一次滚动更新，新 Pod 07:17 刚过时起来。负载 07:17:24 开始，HPA 却连着 45 秒算不出指标：

观测到的是：从 07:17:23 到 07:18:04 共约 45 秒，ScalingActive 一直是 FailedGetResourceMetric，事件写着 1 invalid out of 1，之后自己恢复。失败从 07:17:23 开始，比负载早一秒，和旧 Pod 进入 Terminating 的时间吻合，所以这段空窗和负载无关，是滚动更新带来的。

原因没有直接测到，下面是按 v1.31 源码 replica_calculator.go 的推测。groupPods 会忽略带删除时间戳的 Pod，正在删除的旧 Pod 先被排除，只剩一个新 Pod。新 Pod 又可能因为「缺指标」或「视为未就绪」不被采用，两种情况的规则和扩容时间线里讲的一样（--horizontal-pod-autoscaler-initial-readiness-delay 只对启动已超过 5 分钟初始化期的 Pod 生效，这里的新 Pod 用不上）。

不管是哪一种，剩下可用的样本是 0 个，就报 did not receive metrics for targeted pods。这条事件和缺 request 的那条不同，会自己消失，但单副本服务在发布后马上遇到流量高峰时，HPA 会有这么一段完全不动的时间。

有指标，期望副本仍不变

容忍度：高于目标 7% 不扩容

HPA 算的是比值 当前值 / 目标值，比值离 1.0 不超过容忍度时不做任何动作。v1.31 的默认容忍度是 0.1，只能通过 kube-controller-manager 的 --horizontal-pod-autoscaler-tolerance 全局修改；单个 HPA 的容忍度是 v1.33 才引入的（特性门控 HPAConfigurableTolerance：v1.33 alpha，v1.35 beta 但默认关闭，v1.37 GA），字段在 behavior.scaleUp.tolerance 和 behavior.scaleDown.tolerance，两个方向分别设置，v1.31 的 API 里还没有。

这个效果要让负载稳定在一个固定水平才看得清。负载 Pod 只用一个循环串行请求，每次请求后睡 0.3 秒，跑 170 秒后自己退出：

kubectl -n notes-lab apply -f hpa-burn.yaml
kubectl -n notes-lab delete pod load --ignore-not-found
kubectl -n notes-lab run load --image=busybox:1.36 --restart=Never -- sh -c \
  'end=$(($(date +%s)+170)); while [ $(date +%s) -lt $end ]; do wget -qO- http://burn/cgi-bin/burn >/dev/null; sleep 0.3; done; echo done $(date -u +%T)'

HPA 先把目标设成 300%，保证不会扩容，等利用率稳定在 72%～73%；07:08:15 左右改成 68%，07:09:00 左右再改成 60%：

这 45 秒里比值是 73 / 68 ≈ 1.07，在 0.9～1.1 之内，HPA 认为”已经够接近目标”，Events 一条都没有。改到 60% 后比值变成 1.22，下一次同步就 ceil(1 × 73 / 60) = 2，扩到 2。

容忍度按比值算，和副本数无关：目标 50% 时，平均利用率要超过 55% 才会扩容。如果服务常年停在”略高于目标”，HPA 不会报任何东西，把目标值调低一点，或者接受这个余量。

稳定窗口：缩容晚一分钟

稳定窗口的机制上文已经测过，这次运行里同样的结论又出现了一遍：扩到 2 个副本后串行负载被平摊，07:09:48 负载退出，这个 HPA 设的是 60 秒窗口。39% 和 32% 时还不该缩（ceil(2 × 32 / 60) = ceil(1.07) = 2），到 18% 时当次建议值才变成 1，AbleToScale 随即变成 ScaleDownStabilized，意思是窗口里还留着更高的建议值；最后一个”建议 2”大约出现在 07:09:5x，60 秒后过期，07:10:51 事件 New size: 1。

判断缩容”卡住”时先找这个 Reason：只要是 ScaleDownStabilized，就是窗口在起作用，不是故障。

  Normal  SuccessfulRescale  3m5s                 horizontal-pod-autoscaler  New size: 1; reason: All metrics below target
  Normal  SuccessfulRescale  49s (x2 over 4m50s)  horizontal-pod-autoscaler  New size: 2; reason: cpu resource utilization (percentage of request) above target

167% 对应 ceil(2 × 167 / 50) = 7，被截到 2，ScalingLimited 是唯一的提示，没有 Warning 事件。还有一个读事件的小坑：New size: 2 显示 x2 over 4m50s，是这一次扩容和前面容忍度实验那次扩容被合并成了一条，Age 显示的是最近一次。按时间排查时，用 get events --sort-by=.lastTimestamp 看绝对时间更稳妥。

TooManyReplicas 持续为 True，说明压力超出了 HPA 被允许的范围，要么调大上限，要么降低单个请求的开销。但接下来两个实验会看到，这个 Condition 也会在上限并不是真正瓶颈时亮起。

期望副本涨了，Pod 却没跑起来

ResourceQuota：Pod 根本没被创建

负载还在跑，在 namespace 里加一个只允许总共 300m CPU request 的配额，再把 maxReplicas 放开到 5：

kubectl -n notes-lab create quota cpu-cap --hard=requests.cpu=300m
kubectl -n notes-lab patch hpa burn --type=merge -p '{"spec":{"maxReplicas":5}}'
07:14:05 cpu=167%/50% cur=2 desired=2 AbleToScale=ReadyForNewScale ScalingActive=ValidMetricFound ScalingLimited=TooManyReplicas  spec=2 status=2 ready=2
07:14:10 cpu=173%/50% cur=2 desired=5 AbleToScale=SucceededRescale ScalingActive=ValidMetricFound ScalingLimited=TooManyReplicas  spec=5 status=3 ready=3
07:14:26 cpu=165%/50% cur=5 desired=5 AbleToScale=ReadyForNewScale ScalingActive=ValidMetricFound ScalingLimited=TooManyReplicas  spec=5 status=3 ready=3

HPA 把副本改到 5 之后，Deployment 只有 3 个 Pod（每个 100m，正好用满 300m）。HPA 这边一切”正常”：

burn   Deployment/burn   cpu: 155%/50%   1         5         5          7m47s

  ScalingLimited  True    TooManyReplicas   the desired replica count is more than the maximum replica count

get hpa 的 REPLICAS 是 5，describe hpa 说 5 current，可集群里只有 3 个 Pod，而且一个 Pending 的都没有，因为另外两个根本没被创建出来。原因只在 ReplicaSet 的事件里：

2026-10-13T07:14:07Z   burn-5c877494c8            FailedCreate                   Error creating: pods "burn-5c877494c8-4f9dv" is forbidden: exceeded quota: cpu-cap, requested: requests.cpu=100m, used: requests.cpu=300m, limited: requests.cpu=300m

Deployment 的 Conditions 里也有：

Available=False MinimumReplicasUnavailable: Deployment does not have minimum availability.
ReplicaFailure=True FailedCreate: pods "burn-5c877494c8-vn9lz" is forbidden: exceeded quota: cpu-cap, requested: requests.cpu=100m, used: requests.cpu=300m, limited: requests.cpu=300m

5 current 是怎么来的？看 scale 子资源：

$ kubectl get --raw /apis/apps/v1/namespaces/notes-lab/deployments/burn/scale
{"kind":"Scale","apiVersion":"autoscaling/v1","metadata":{...},"spec":{"replicas":5},"status":{"replicas":3,"selector":"app=burn"}}

status.replicas 明明是 3，HPA 的 currentReplicas 却是 5。v1.31 的控制器源码（horizontal.go）里是 currentReplicas := scale.Spec.Replicas，它拿的是期望值，不是实际存在的 Pod 数。所以 HPA 的”current”只代表”我上次设成了多少”，判断 Pod 是否真的到位，要看 Deployment 的 READY 或 status.replicas。

不过计算新副本数时用的不是这个 5。按 v1.31 replica_calculator.go 的 GetResourceReplicas，没有缺指标、未就绪的 Pod 时，新副本数是 ceil(比值 × 有指标的就绪 Pod 数)，也就是实际存在的 3 个 Pod：ceil(3 × 155 / 50) = ceil(9.3) = 10。currentReplicas（scale.Spec.Replicas）用来和上下限比较、作为不需要调整时直接返回的值，并写进 status。

10 超过上限 5，所以 ScalingLimited 还是 TooManyReplicas。只看 HPA 会以为”上限太小，再调大”，其实调多大都没用，配额才是瓶颈。

另一个副作用出现在负载停止后：07:16:22 HPA 缩到 2，07:16:37 缩到 1，ReplicaSet 那 2 个一直创建失败的副本也随之不再需要。HPA 自己的事件里只有几条 SuccessfulRescale，看不出配额拦过它，事后复盘要去翻 ReplicaSet 的事件（事件默认只保留一小时左右）。配额的配置见LimitRange 与 ResourceQuota。

调度失败：Pod Pending

去掉配额，给 burn 加一条必须满足的 Pod 反亲和，要求同一节点上不能有两个 burn。保存为 antiaff-patch.yaml：

spec:
  template:
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: burn
              topologyKey: kubernetes.io/hostname
kubectl -n notes-lab delete pod load --ignore-not-found
kubectl -n notes-lab delete quota cpu-cap
kubectl -n notes-lab patch deploy burn --patch-file antiaff-patch.yaml
kubectl -n notes-lab rollout status deploy/burn
# 和上一节相同的 4 并发负载，150 秒后自动退出
kubectl -n notes-lab run load --image=busybox:1.36 --restart=Never -- sh -c \
  'end=$(($(date +%s)+150)); for n in 1 2 3 4; do (while [ $(date +%s) -lt $end ]; do wget -qO- http://burn/cgi-bin/burn >/dev/null; done) & done; wait; echo done $(date -u +%T)'

集群里能跑业务的只有两个工作节点，施压后 HPA 扩到 5：

（REPLICAS 显示 4 是设计如此：setStatus 写入的 currentReplicas 是本轮同步开始时读到的值，这一轮 HPA 正是从 4 改到 5，所以要到下一轮才显示 5。）这次和配额不一样：5 个 Pod 都被创建了，status.replicas 也是 5，3 个停在 Pending。原因在 Pod 的事件里：

Warning  FailedScheduling  49s   default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) didn't match pod anti-affinity rules. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

这条消息按节点逐个列出被排除的理由：control-plane 有污点，两个 worker 不满足反亲和。如果是资源不够，这里会换成 Insufficient cpu 一类的提示。HPA 侧又是一片”正常”，只有 ScalingLimited=TooManyReplicas：

  ScalingLimited  True    TooManyReplicas   the desired replica count is more than the maximum replica count

kubectl top pod -l app=burn 只列出 2 个 Running 的 Pod，各 157m、190m，扩出来的 3 个副本一点负载都没分到。

ResourceQuota 拦截调度失败
Pod 是否存在不存在存在，Pending

HPA 在两种情况下都不会报错。所以只要 HPA 显示已经扩了、服务却还是扛不住，就去比对 Deployment 的 READY 和 HPA 的 REPLICAS，两者不一致时，往下一层看 ReplicaSet 和 Pod 的事件。调度规则见 Pod 亲和与反亲和 和污点与容忍。

排查顺序

把上面的实验串起来，遇到”HPA 不扩容”时按这个顺序看，每一步只需要一两条命令：

  1. kubectl describe hpa，看 Conditions 里哪一行是 False：
    • AbleToScale=False FailedGetScale：scaleTargetRef 的名字、kind 或 apiVersion 不对。
    • ScalingActive=False ScalingDisabled：目标副本是 0，HPA 主动停了。
    • ScalingActive=False FailedGetResourceMetric：读最后一直重复的那条事件。missing request 是缺 request；did not receive metrics 在新 Pod 刚起来时会出现，持续不消失才去查 Metrics Server（get apiservice、get --raw）。
  2. 三行都是 True/正常，比较当前值和目标值：比值在 0.9～1.1 内是容忍度；Reason 是 ScaleDownStabilized 是稳定窗口；ScalingLimited=TooManyReplicas 是到了上限，但还要做第 3 步。
  3. 比较 HPA 的 REPLICAS 和 Deployment 的 READY。HPA 的 current 是 spec.replicas，不代表 Pod 已经存在：少了 Pod 看 ReplicaSet 的 FailedCreate（配额、准入），有 Pending 看 Pod 的 FailedScheduling，Running 但不 Ready 看探针，见 Pod 与容器。

不要在 HPA 运行期间反复 kubectl scale 同一个 Deployment，也不要把固定的 spec.replicas 留在反复 apply 的清单里，两者都会和 HPA 互相覆盖。手动 scale 能撑多久见上文手动 scale 为什么能顶住约 5 分钟。

清理

kubectl delete namespace notes-lab
