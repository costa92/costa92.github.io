Helm 说成功，只代表它等到的那几件事成功了

Helm 入门已经讲过 Release 的生命周期：三种预览方式、values 优先级、不传 values 时升级沿用什么、被 API Server 拒绝的半途失败、不加 --wait 时坏镜像也被标成 deployed、--rollback-on-failure 回到哪个修订、pending-upgrade 和历史只留 10 个。这些这里不再重复。这一篇关心的是升级之后：怎么确认改动真的到了用户手里，出问题时回滚会把集群带回什么样子。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0），客户端是 Helm v4.3.0：

version.BuildInfo{Version:"v4.3.0", GitCommit:"bec5b06ed841fe5269972d864d5177944fd5970f", GitTreeState:"clean", GoVersion:"go1.27.1", KubeClientVersion:"v1.37"}

实验放在单独的 notes-lab namespace 里。请求从集群内一个 curlimages/curl 的 Pod 发出：

kubectl create namespace notes-lab
kubectl -n notes-lab run client --image=curlimages/curl:latest \
  --overrides='{"spec":{"containers":[{"name":"client","image":"curlimages/curl:latest","command":["sleep","3600"],"resources":{"requests":{"cpu":"10m","memory":"16Mi"}}}]}}'

容器命令是 sleep 3600，一小时后容器退出重启，kubectl cp 进去的 /tmp 脚本随之丢失：19:32 那次就报了 sh: can't open '/tmp/loop.sh'，重新拷贝后才继续。自己做的话改成 sleep infinity 更省事。

时区要留意：Helm 和本机 date 的输出是 UTC+8，容器里的时间（client 的流量日志、nginx 日志）和 Kubernetes 事件的时间戳是 UTC，08:47 对应 16:47。

实验用的 Chart

在编写 Helm Chart 的 web-chart 基础上加了四样东西，为的是让「版本」在请求里看得见：

  • templates/configmap.yaml：nginx 配置，/healthz 固定返回 ok，其他路径返回 {{ .Values.message }} pod=$hostname；
  • Deployment 挂载这个 ConfigMap，加上 readinessProbe，路径取 .Values.readinessPath（默认 /healthz），每 2 秒探一次；
  • templates/tests/test-message.yaml：一个 helm.sh/hook: test 的 Pod，对 Service 请求 6 次，响应里不含当前 message 就退出 1；
  • templates/job.yaml：migration.enabled=true 时创建一个 sleep 若干秒的 Job，名字带 {{ .Release.Revision }}，模拟数据库迁移。

这就是 Chart 0.2.0。实验过程中 Chart 又改了几版，命令里的 ./web-chart 在不同时间指向不同版本：

  • 0.2.1：Pod 模板加 checksum/config 注解（见下一节）；
  • 0.2.2：容器加 lifecycle.preStop.sleep.seconds: 5；
  • 0.3.0（目录 ./web-chart-0.3.0）：message 默认值改为 hello from chart 0.3.0，新增 banner.header/banner.text，nginx 配置里多一行 add_header {{ .Values.banner.header }} {{ .Values.banner.text | quote }};；
  • ./web-chart-noprestop：0.3.0 删掉 lifecycle 那 4 行，其余不变；
  • ./web-chart-strict：0.3.0 的 values.schema.json 顶层加 "additionalProperties": false，并补上 message、readinessPath、migration、banner 的定义。

--wait 之所以秒回，是因为它等的是资源「就绪」：Deployment 的 Pod 模板没变，本来就是就绪的，ConfigMap 创建出来就算好。Helm 不知道 nginx 需要重启。常见的修法是在 Pod 模板里放一个配置内容的哈希，配置一变，模板跟着变，Deployment 就会滚动更新（这就是 Chart 0.2.1）：

template:
  metadata:
    annotations:
      checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}

就绪探针路径写错，照样通过

把 readinessPath 改成一个不存在的 /nope，满以为 --wait 会超时，结果升级成功，3 个新 Pod 都是 1/1：

$ date +%T; helm upgrade web ./web-chart-0.3.0 -n notes-lab --reuse-values --set readinessPath=/nope --set message="hello v5" --wait --timeout 45s; echo exit=$?; date +%T

...
REVISION: 12
DESCRIPTION: Upgrade complete
...
exit=0
19:32:07
$ kubectl -n notes-lab exec client -- curl -s -o /dev/null -w "%{http_code}\n" http://web-web-chart/nope
200

nginx 的 location / 兜住了所有路径，/nope 也返回 200。大部分 Web 框架都有类似的兜底路由（前端单页应用的 index.html 回退最典型），探针路径拼错不会报错，只是让探针失去了意义：以后应用真的坏了，它也照样「就绪」。上线前值得手动请求一个肯定不存在的路径，看它是不是真的返回 404。修订 12 的这个 /nope 后面还会再出现一次。

就绪对 Helm 的意义也就到这里：Helm 4 的 --wait（watcher 策略）用 kstatus 判断资源是否 Current，对 Deployment 来说就是新副本数到位并且 Available，而 Available 取决于就绪探针。探针测的是什么，Helm 就相信什么。

升级时的流量

用下面的脚本在 client Pod 里每 0.1 秒请求一次 Service，记下 curl 的退出码和响应：

end=$(( $(date +%s) + $1 ))
while [ $(date +%s) -lt $end ]; do
  out=$(curl -s -m 1 -o /tmp/b -w "%{http_code}" http://web-web-chart/ 2>&1); rc=$?
  echo "$(date +%T) rc=$rc code=$out $(cat /tmp/b 2>/dev/null)"; rm -f /tmp/b
  sleep 0.1
done

$1 是持续的秒数。脚本先拷进 Pod，在后台运行，同时在本机执行升级，日志重定向到本机文件：

kubectl -n notes-lab cp loop.sh client:/tmp/loop.sh
kubectl -n notes-lab exec client -- sh /tmp/loop.sh 45 > traffic1.log 2>&1 &
sleep 3
helm upgrade ...
wait

第一次是升级到加了配置哈希的 Chart 0.2.1，3 个 Pod 逐个替换，--wait 用了 25 秒：

两点：

  • Helm 返回时最后一个旧 Pod 还在 Terminating。--wait 等的是新副本可用，不等旧 Pod 退干净。
  • 405 个请求里 4 个失败，rc=7 是连接被拒。把失败时间和事件对上，每一次都紧跟在一个旧 Pod 被停止之后：
2026-10-12T08:47:06Z   Killing             web-web-chart-75b76c7467-59kpq   Stopping container web

同时，从 08:47:07 到 08:47:24 这十几秒里，v1 和 v2 的响应交替出现。滚动更新期间新旧版本同时在线，接口不兼容的改动在这段时间里会出问题，和 Helm 无关。

Pod 被删除后，容器收到 SIGTERM 和它从 Service 的后端里摘掉是两条并行的路径，后者要经过 EndpointSlice 和各节点的转发规则更新。推测失败就发生在这个窗口里：请求还被转到正在退出的 Pod，而 nginx 已经不再接受连接（这次没有抓转发规则的变化，只有时间上的对应）。常规做法是加一个 preStop 先等几秒（Chart 0.2.2 加的 sleep: seconds: 5），详见 优雅终止。

另外单独删过一个带 preStop 的 Pod，同时请求 Service 和它的 Pod IP：删除后 5 秒内直连 Pod IP 全部成功，之后才被拒，经过 Service 的请求一个都没失败。删除 Pod 时摘流量与停进程的先后关系，优雅终止有更细的实验，这里不展开。

preStop 从下一次升级才开始起作用

一共做了 7 次带流量的滚动更新，按「被替换掉的旧 Pod 有没有 preStop」排列：

时间修订旧 Pod 来自旧 Pod 有 preStop请求数失败
16:473修订 2（Chart 0.2.0）无4054
16:484修订 3（Chart 0.2.1）无4556
19:3515修订 14（Chart 0.3.0）有5550
19:3616修订 15有4560
19:3717修订 16（去掉 preStop）无4505
19:3818修订 17无4503
19:3919修订 18有4510

修订 4 本身就是加 preStop 的那次升级，但它照样失败了 6 次，因为被停掉的是修订 3 的 Pod，它们的 spec 里没有 preStop。修订 16 反过来：这次升级去掉了 preStop，被替换的修订 15 的 Pod 还带着它，0 失败；到下一次（修订 17）才开始出错。终止行为由要被删的那个 Pod 的 spec 决定，所以加优雅终止的那一次发布本身并不受保护，验证效果要看再下一次。

后 5 次是在同一天晚些时候做的，中间集群的 API Server 有一段时间不可用，那段时间没有采集任何数据，恢复后才继续实验；这 5 次的结果和前两次的规律一致。样本只有 7 次、每次 450 个左右请求，失败次数会随时机波动，表里只能说明「有没有 preStop」的差别，不能当作失败率。

–wait-for-jobs

打开 migration（sleep 25），先只用 --wait，再加上 --wait-for-jobs：

$ date +%T; helm upgrade web ./web-chart-0.3.0 -n notes-lab --reuse-values --set migration.enabled=true --set migration.sleepSeconds=25 --wait --timeout 2m | sed -n 5,7p; date +%T; kubectl -n notes-lab get jobs
19:30:44
STATUS: deployed
REVISION: 10
DESCRIPTION: Upgrade complete
19:30:45
NAME                       STATUS    COMPLETIONS   DURATION   AGE
web-web-chart-migrate-10   Running   0/1           1s         1s
$ date +%T; helm upgrade web ./web-chart-0.3.0 -n notes-lab --reuse-values --wait --wait-for-jobs --timeout 2m | sed -n 5,7p; date +%T; kubectl -n notes-lab get jobs
19:30:45
STATUS: deployed
REVISION: 11
DESCRIPTION: Upgrade complete
19:31:24
NAME                       STATUS     COMPLETIONS   DURATION   AGE
web-web-chart-migrate-11   Complete   1/1           37s        38s

只加 --wait 时，Job 刚创建 1 秒 Helm 就返回了：Helm 4 的 watcher 只等 Job 开始运行，不等它跑完；加了 --wait-for-jobs 才等到 Complete（39 秒）。

这组输出里还藏着一个问题：修订 10 的 migrate-10 刚跑了 1 秒，修订 11 一升级就把它删了，因为新清单里只有 migrate-11。事件里 migrate-10 只有一条 SuccessfulCreate，没有完成记录。名字带修订号的 Job，每次升级都会删掉上一个，不管它跑没跑完。在 Release 清单里放迁移 Job，必须配合 --wait-for-jobs，或者改用 pre-upgrade hook（hook 不属于清单，Helm 会等它完成才继续）。hook 方式这次没有实测。

–reuse-values 遇上新版 Chart 的默认值

Chart 0.3.0 做了两处改动：message 的默认值从 hello v1 改成 hello from chart 0.3.0，新增了一个配置项 banner，模板里读 .Values.banner.header。当时 Release 的用户 values 只有 replicaCount: 3。四种写法用 --dry-run=server 渲染对比：

$ helm upgrade web ./web-chart-0.3.0 -n notes-lab --reuse-values --dry-run=server 2>&1 | head -3
Error: UPGRADE FAILED: web-chart/templates/deployment.yaml:15:28
  executing "web-chart/templates/deployment.yaml" at <include (print $.Template.BasePath "/configmap.yaml") .>:
    error calling include:
$ helm upgrade web ./web-chart-0.3.0 -n notes-lab --reuse-values --dry-run=server 2>&1 | tail -2
  executing "web-chart/templates/configmap.yaml" at <.Values.banner.header>:
    nil pointer evaluating interface {}.header
$ helm upgrade web ./web-chart-0.3.0 -n notes-lab --reset-values --dry-run=server | grep -E "replicas:|X-Chart|return 200 \"hello"
        add_header X-Chart "0.3.0";
        return 200 "hello from chart 0.3.0 pod=$hostname\n";
  replicas: 1
$ helm upgrade web ./web-chart-0.3.0 -n notes-lab --reset-then-reuse-values --dry-run=server | grep -E "replicas:|X-Chart|return 200 \"hello"
        add_header X-Chart "0.3.0";
        return 200 "hello from chart 0.3.0 pod=$hostname\n";
  replicas: 3
$ helm upgrade web ./web-chart-0.3.0 -n notes-lab --dry-run=server | grep -E "replicas:|X-Chart|return 200 \"hello"
        add_header X-Chart "0.3.0";
        return 200 "hello from chart 0.3.0 pod=$hostname\n";
  replicas: 3
  • --reuse-values 沿用的是上一个修订的完整 values，包括旧 Chart 的默认值，新 Chart 的 values.yaml 被整个忽略。新增的 banner 不存在，模板直接 nil pointer 报错。这还算好的：如果新模板用的是顶层键加默认值，比如 {{ .Values.bannerText | default "x" | quote }}，就不会报错，只会悄悄用上模板里的兜底值（见下面的本地验证）。
  • --reset-values 只用新 Chart 默认值，用户设过的 replicaCount: 3 丢了，副本数退回 1。
  • --reset-then-reuse-values 先取新 Chart 默认值，再叠上上次的用户 values，banner 有了，replicaCount 也保住了。
  • 什么都不加、也不传任何 values 时，结果和 --reset-then-reuse-values 一样。

在本地用 helm template 模拟 --reuse-values 的效果：把 0.3.0 的 values.yaml 换成旧版 0.2.2 的，分别用两种写法渲染。v-top 用顶层键 .Values.bannerText | default "x"，v-nested 用 .Values.banner.text | default "x"：

$ helm template web ./v-top --show-only templates/configmap.yaml | grep add_header
        add_header X-Chart "x";
$ helm template web ./v-nested 2>&1 | head -6
Error: web-chart/templates/deployment.yaml:15:28
  executing "web-chart/templates/deployment.yaml" at <include (print $.Template.BasePath "/configmap.yaml") .>:
    error calling include:
web-chart/templates/configmap.yaml:13:37
  executing "web-chart/templates/configmap.yaml" at <.Values.banner.text>:
    nil pointer evaluating interface {}.text

default 救不了两层取值：banner 不存在时，取 .text 那一步就已经 nil pointer 了。顶层键则静默得到 "x"，新版本的默认值 0.3.0 没有生效，也没有任何提示。

还要注意：四种写法里，凡是成功渲染的，message 都变成了新默认值 hello from chart 0.3.0。用户从没设过的值，会跟着 Chart 默认值一起变，helm get values 里看不到这一项，只有清单 diff 能看出来。实际升级后：

$ kubectl -n notes-lab exec client -- curl -si http://web-web-chart/ | grep -E "X-Chart|hello"
X-Chart: 0.3.0
hello from chart 0.3.0 pod=web-web-chart-f5c774d77-rnrd5

手动改过的字段：Helm 4 直接报冲突

线上常见的情形是有人临时 kubectl scale 或 kubectl edit 了一下。Helm 4 新装的 Release 用服务端应用（helm get metadata 里写着 APPLY_METHOD: server-side apply），这和 Helm 3 的三方合并处理方式完全不同。先对 web 做三处手动修改：

$ kubectl -n notes-lab scale deploy web-web-chart --replicas=2
deployment.apps/web-web-chart scaled
$ kubectl -n notes-lab set env deploy/web-web-chart DEBUG=1
deployment.apps/web-web-chart env updated
$ kubectl -n notes-lab label deploy web-web-chart notes-lab.io/owner=ops
deployment.apps/web-web-chart labeled
$ kubectl -n notes-lab get deploy web-web-chart -o jsonpath="{range .metadata.managedFields[*]}{.manager} {.operation} {.subresource}{\"\n\"}{end}"
helm Apply 
kubectl Update scale
kube-controller-manager Update status
kubectl-set Update 
kubectl-label Update

replicas 本来归 helm 管，kubectl scale 通过 scale 子资源改了它的值，所有权随之转给了 kubectl。这时回滚到当前修订、或者做一次不改副本数的升级，都失败了：

$ helm rollback web 5 -n notes-lab --wait --timeout 2m; echo exit=$?

$ helm upgrade web ./web-chart -n notes-lab --reuse-values --wait --timeout 2m; echo exit=$?
level=WARN msg="upgrade failed" name=web error="conflict occurred while applying object notes-lab/web-web-chart apps/v1, Kind=Deployment: Apply failed with 1 conflict: conflict with \"kubectl\" with subresource \"scale\" using apps/v1: .spec.replicas"
Error: UPGRADE FAILED: conflict occurred while applying object notes-lab/web-web-chart apps/v1, Kind=Deployment: Apply failed with 1 conflict: conflict with "kubectl" with subresource "scale" using apps/v1: .spec.replicas

用 kubectl patch 改 Chart 里写了的内存 limit，再升级，也是一样：

$ kubectl -n notes-lab patch deploy web-web-chart --type=json -p '[{"op":"replace","path":"/spec/template/spec/containers/0/resources/limits/memory","value":"128Mi"}]'
deployment.apps/web-web-chart patched
$ helm upgrade web ./web-chart-0.3.0 -n notes-lab --reuse-values --wait --timeout 2m 2>&1 | tail -1

注意「回滚失败」这件事本身：线上出了问题想回滚，却因为有人之前手动扩过容而回滚不了。加 --force-conflicts 才能把字段夺回来（下面用的是 upgrade；helm rollback --help 里也有 --force-conflicts，这次没有测）：

$ helm upgrade web ./web-chart -n notes-lab --reuse-values --force-conflicts --wait --timeout 3m | sed -n 1,7p; echo exit=$?
Release "web" has been upgraded. Happy Helming!
...
REVISION: 8
DESCRIPTION: Upgrade complete
exit=0
$ kubectl -n notes-lab get deploy web-web-chart -o jsonpath="replicas={.spec.replicas} env={.spec.template.spec.containers[0].env} label={.metadata.labels.notes-lab\.io/owner}{\"\n\"}"
replicas=3 env=[{"name":"DEBUG","value":"1"}] label=ops
$ kubectl -n notes-lab get deploy web-web-chart -o jsonpath="{range .metadata.managedFields[*]}{.manager} {.operation} {.subresource}{\"\n\"}{end}"
helm Apply 
kubectl-set Update 
kubectl-label Update 
kube-controller-manager Update status

副本数回到 3，kubectl 从 managedFields 里消失了；但 Chart 里没写的 DEBUG 环境变量和那个标签都留着，服务端应用只管自己声明过的字段。顺带一提，失败的两个修订在历史里的状态不一样：

6       	Mon Oct 12 19:27:04 2026	failed    	web-chart-0.2.0	1.27       	Rollback "web" failed: conflict occurred ...
7       	Mon Oct 12 19:27:12 2026	superseded	web-chart-0.2.2	1.27       	Upgrade "web" failed: conflict occurred ...

作为对比，在 Helm 4 里用 --server-side=false 装一个客户端应用的 Release csa（2 个副本），做同样的三处修改，再不带任何改动升级：

$ helm get metadata csa -n notes-lab | grep APPLY
APPLY_METHOD: client-side apply
$ helm upgrade csa ./web-chart -n notes-lab --reuse-values --wait --timeout 2m | sed -n 1,7p; echo exit=$?
Release "csa" has been upgraded. Happy Helming!
...
REVISION: 2
DESCRIPTION: Upgrade complete
exit=0
$ kubectl -n notes-lab get deploy csa-web-chart -o jsonpath="replicas={.spec.replicas} env={.spec.template.spec.containers[0].env} label={.metadata.labels.notes-lab\.io/owner}{\"\n\"}"
replicas=2 env=[{"name":"DEBUG","value":"1"}] label=ops

客户端应用（Helm 3 一直用的三方合并）不报错，直接把副本数从 1 改回 Chart 里的 2，其余两处同样保留。两种方式对「Chart 没写的字段」处理一样，区别在「Chart 写了、又被人改过的字段」：三方合并静默覆盖，服务端应用拒绝并要求显式 --force-conflicts。哪个 Release 用哪种方式，见 Helm 入门里的 apply_method 字段，从 Helm 3 迁移来的和 Helm 4 新装的可能并存。

副本数由 HPA 管理的 Deployment，Chart 里本来就不该写 replicas；否则在服务端应用下，HPA 每次改副本数都会抢走这个字段的所有权，推测下一次 Helm 升级会遇到同样的冲突（这一点没有实测）。

让 values 里的拼写错误报出来

把 message 拼成 mesage，Helm 不会有任何提示，渲染结果里还是旧值：

$ helm upgrade web ./web-chart-0.3.0 -n notes-lab --reuse-values --set mesage="hello v6" --dry-run=server | grep -E "return 200 \"hello"
        return 200 "hello v5 pod=$hostname\n";

真执行的话，这是一次「成功」且 Pod 都就绪的升级，只是什么都没变。前面的 helm test 也抓不到：它比对的期望值同样取自 .Values.message，仍是 hello v5，和实际响应一致，测试照样通过。测试和应用读的是同一份 values，values 本身写错了，两边一起错。能拦住的是在 values.schema.json 顶层加 "additionalProperties": false，并把所有合法的键都列进 properties（就是上面的 ./web-chart-strict）：

$ helm upgrade web ./web-chart-strict -n notes-lab --reuse-values --set mesage="hello v6" --dry-run=server 2>&1 | head -4
Error: UPGRADE FAILED: values don't meet the specifications of the schema(s) in the following chart(s):
web-chart:
- at '': additional properties 'mesage' not allowed

代价是每加一个配置项都得同步改 schema，不然合法的值也会被拒。

清理

helm uninstall web -n notes-lab --wait
kubectl delete namespace notes-lab --wait

小结

  • --wait 等的是资源就绪，而就绪由探针决定。ConfigMap 变了 Pod 不重建、探针路径被兜底路由吃掉，Helm 都会报成功。升级后跑一个检查真实响应的 helm test，按它的退出码判定，测试失败不会改变 Release 状态。
  • 升级失败、旧 Pod 还在服务，不等于集群回到了旧版本：共享的 ConfigMap 可能已经是新的坏配置，旧 Pod 一重启就会崩。
  • 回滚生成新修订，恢复目标修订的全部 values 和原样清单：当时的错误配置会回来，已删除的 Job 会重新执行。回滚前先 helm get values/manifest --revision 看清目标。
  • Chart 升级了版本就别用 --reuse-values，用 --reset-then-reuse-values，或者每次完整传 values 文件；用户没设过的值会随新默认值一起变。
  • Helm 4 服务端应用下，被 kubectl scale/edit/patch 改过的 Chart 字段会让升级和回滚都报冲突，需要 --force-conflicts；Helm 3 方式的 Release 会静默覆盖。
  • 滚动更新时终止的 Pod 会让少量请求连接被拒，本次实验中被替换的旧 Pod 带 preStop 的 3 次都是 0 失败；preStop 只对之后的发布生效。
