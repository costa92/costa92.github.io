集群 DNS 故障定位

Pod 访问 whoami 失败时，报错可能来自三个完全不同的层面：名字没解析出来、解析出来了但 Service 没有后端、解析和后端都没问题但网络不通。只看「访问不了」分不出是哪一层，得先弄清楚 Pod 里的一个名字是怎么变成 DNS 查询的，再去看每一层失败时的报错长什么样。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，CoreDNS v1.11.1，CNI 为 Calico，kube-proxy 为 iptables 模式），实验放在单独的 notes-lab namespace 里。集群 DNS 的 Service IP 写成 <dns-ip>，其他 Service IP 写成 <cluster-ip>，Pod IP 写成 <pod-ip>。

实验用到的后端是一个两副本的 traefik/whoami Deployment，外加三个 Service：

  • whoami：普通 ClusterIP，选择器正确；
  • whoami-hl：同样的选择器，但 clusterIP: None（headless）；
  • noep：选择器故意写成 app: whoami-typo，匹配不到任何 Pod。
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done

客户端 Pod 比较多，区别在镜像的 C 库和 DNS 配置。dnslog 是下文自建的带日志 CoreDNS：

Pod镜像C 库dnsPolicynameserver
bbbusybox:1.36glibcClusterFirst<dns-ip>
cfcurlimages/curlmuslClusterFirst<dns-ip>
cndbusybox:1.36glibcClusterFirst + dnsConfig（ndots:2）<dns-ip>
dfltnginx:1.27glibcDefault<node-dns>
npnginx:1.27glibcClusterFirst，带 role=client 标签<dns-ip>
cfixcurlimages/curlmuslNone，只留三个集群搜索域<dns-ip>
ldeb / ldeb1nginx:1.27glibcNone，ndots:5 / ndots:1<dnslog-ip>
lbbbusybox:1.36glibcNone，ndots:5<dnslog-ip>
lcu / lcu1curlimages/curlmuslNone，ndots:5 / ndots:1<dnslog-ip>

先看 resolv.conf

ClusterFirst：默认值

不写 dnsPolicy 的 Pod 用的是 ClusterFirst：

$ kubectl -n notes-lab exec bb -- cat /etc/resolv.conf
search notes-lab.svc.cluster.local svc.cluster.local cluster.local localdomain
nameserver <dns-ip>
options ndots:5
$ kubectl -n notes-lab get pod bb -o jsonpath='{.spec.dnsPolicy}'
ClusterFirst

前三个搜索域是 kubelet 按 Pod 所在 namespace 生成的，nameserver 指向 kube-system/kube-dns 这个 Service。第四个 localdomain 不是 Kubernetes 加的，而是从节点的 /etc/resolv.conf 继承来的：

$ docker exec worker cat /etc/resolv.conf
nameserver <node-dns>
search localdomain
options ndots:0

kind 节点本身是 Docker 容器，这一行又来自宿主机。也就是说，宿主机网络配置里的一个搜索域，最终出现在了每个 Pod 里。后面会看到它在名字拼错时让每次查询多等 3 秒。

ndots:5 的意思是：名字里的点少于 5 个，就先依次拼上搜索域去查，都失败了才把名字原样查一次。点数达到 ndots 时，两种 C 库的做法不一样：glibc 先原样查，失败了再走搜索域；musl 只原样查，不再走搜索域。以末尾 . 结尾的名字两者都只原样查。后面调低 ndots 那一节会看到这个差别的后果。

Default：节点的配置

Default 这个名字有误导性，它并不是默认值，而是「照搬节点的 resolv.conf」：

$ kubectl -n notes-lab exec dflt -- cat /etc/resolv.conf
search localdomain
nameserver <node-dns>
options ndots:0

这个 Pod 完全绕开了集群 DNS，查 Service 名一律失败，查公网域名正常：

-- whoami.notes-lab.svc.cluster.local
command terminated with exit code 2
exit=2
-- kubernetes.default
command terminated with exit code 2
exit=2
-- example.com
<public-ip>     STREAM example.com

getent 的退出码 2 表示「找不到」。如果某个 Pod 能上网却解析不了任何 Service 名，先看它的 dnsPolicy 是不是被写成了 Default。

None 与 dnsConfig

dnsPolicy: None 时，resolv.conf 完全由 dnsConfig 决定，nameservers 至少要有一个。其他策略下 dnsConfig 是追加合并：

spec:
  dnsPolicy: ClusterFirst
  dnsConfig:
    searches: ["example.internal"]
    options:
      - name: ndots
        value: "2"
      - name: timeout
        value: "2"
search notes-lab.svc.cluster.local svc.cluster.local cluster.local localdomain example.internal
nameserver <dns-ip>
options ndots:2 timeout:2

搜索域追加在末尾；同名的 ndots 被替换成了 2，没有出现两条 ndots。

一个名字到底发出几次查询

kube-system 里的 CoreDNS 没有启用 log 插件（Corefile 里和日志相关的只有 errors，没有 log），看不到每条查询。为了不改系统组件，我在实验 namespace 里另起了一个只做转发、带查询日志的 CoreDNS：

apiVersion: v1
kind: ConfigMap
metadata:
  name: dnslog
data:
  Corefile: |
    .:53 {
        log . "{type} {name} {rcode}"
        errors
        forward . <dns-ip>
    }

用同一个 registry.k8s.io/coredns/coredns:v1.11.1 镜像跑成 Pod，客户端 Pod 用 dnsPolicy: None 指向它，搜索域和 ndots 照抄上面 ClusterFirst 的值：

spec:
  dnsPolicy: "None"
  dnsConfig:
    nameservers: ["<dnslog-ip>"]
    searches:
      - notes-lab.svc.cluster.local
      - svc.cluster.local
      - cluster.local
      - localdomain
    options:
      - name: ndots
        value: "5"

这个代理自己不开缓存，客户端每发一个包都会在日志里留一行。它只负责记录和转发，答案仍然来自集群 CoreDNS（kubernetes 插件，外加 cache 30），所以日志里的查询条数反映的是客户端的行为；耗时则多了一跳，也会受到集群 CoreDNS 30 秒缓存的影响。客户端主要用 nginx:1.27（Debian，glibc 2.36）里的 getent。

短名：一次命中

getent ahostsv4 只查 IPv4，最干净：

$ kubectl -n notes-lab exec ldeb -- getent ahostsv4 whoami
<cluster-ip>   STREAM whoami.notes-lab.svc.cluster.local
--- dnslog 新增查询:
A whoami.notes-lab.svc.cluster.local. NOERROR

第一个搜索域就是本 namespace，同 namespace 的短名一次命中。getent ahosts（A 和 AAAA 都要）是两条：

AAAA whoami.notes-lab.svc.cluster.local. NOERROR
A whoami.notes-lab.svc.cluster.local. NOERROR

名字越完整，查询反而越多

带上 namespace，名字里有一个点：

$ kubectl -n notes-lab exec ldeb -- getent ahostsv4 whoami.notes-lab
--- dnslog 新增查询:
A whoami.notes-lab.notes-lab.svc.cluster.local. NXDOMAIN
A whoami.notes-lab.svc.cluster.local. NOERROR

写成完整的服务域名，四个点，仍然少于 5：

$ kubectl -n notes-lab exec ldeb -- getent ahostsv4 whoami.notes-lab.svc.cluster.local
--- dnslog 新增查询:
A whoami.notes-lab.svc.cluster.local.notes-lab.svc.cluster.local. NXDOMAIN
A whoami.notes-lab.svc.cluster.local.svc.cluster.local. NXDOMAIN
A whoami.notes-lab.svc.cluster.local.cluster.local. NXDOMAIN
A whoami.notes-lab.svc.cluster.local.localdomain. NXDOMAIN
A whoami.notes-lab.svc.cluster.local. NOERROR

把四个搜索域全试一遍才原样查，5 次。末尾加一个点，才是真正的「完整域名」：

$ kubectl -n notes-lab exec ldeb -- getent ahostsv4 whoami.notes-lab.svc.cluster.local.
--- dnslog 新增查询:
A whoami.notes-lab.svc.cluster.local. NOERROR

访问集群外的域名代价最大。example.com 只有一个点，A 和 AAAA 各走一遍搜索域：

$ kubectl -n notes-lab exec ldeb -- getent ahosts example.com
--- dnslog 新增查询:
AAAA example.com.notes-lab.svc.cluster.local. NXDOMAIN
A example.com.notes-lab.svc.cluster.local. NXDOMAIN
A example.com.svc.cluster.local. NXDOMAIN
AAAA example.com.svc.cluster.local. NXDOMAIN
AAAA example.com.cluster.local. NXDOMAIN
A example.com.cluster.local. NXDOMAIN

AAAA example.com.localdomain. NXDOMAIN
A example.com. NOERROR
AAAA example.com. NOERROR

10 次查询里只有最后 2 次有用。换成 alpine 系的 curlimages/curl（musl libc）结果一样，也是 10 次，只是 A/AAAA 的先后顺序不同。

写法（ndots:5，4 个搜索域）只查 AA + AAAA
whoami12
whoami.notes-lab24
whoami.notes-lab.svc.cluster.local510
whoami.notes-lab.svc.cluster.local.12

getent hosts 和 getent ahosts 不一样

getent hosts whoami 多出了好几条：

$ kubectl -n notes-lab exec ldeb -- getent hosts whoami
<cluster-ip>   whoami.notes-lab.svc.cluster.local
--- dnslog 新增查询:
AAAA whoami.notes-lab.svc.cluster.local. NOERROR
AAAA whoami.svc.cluster.local. NXDOMAIN
AAAA whoami.cluster.local. NXDOMAIN
AAAA whoami.localdomain. NXDOMAIN
AAAA whoami. SERVFAIL
AAAA whoami. SERVFAIL
A whoami.notes-lab.svc.cluster.local. NOERROR

getent hosts 先只查 IPv6。Service 只有 IPv4，第一个 AAAA 返回 NOERROR 但没有记录，于是它把整个搜索列表走完、再原样查 whoami.，全部落空后才退回去查 A。7 次查询拿到一个本可以 1 次拿到的答案。测解析时用 getent ahosts（和 curl、大多数程序一样走 getaddrinfo），它反映的才是应用实际的行为。

调低 ndots 的代价

把 ndots 改成 1 再测：

$ kubectl -n notes-lab exec ldeb1 -- getent ahosts example.com
--- dnslog 新增查询:
A example.com. NOERROR
AAAA example.com. NOERROR

外部域名从 10 次降到 2 次。但 whoami.notes-lab 这种带一个点的集群内写法就出问题了。glibc（ldeb1）先原样查，失败了再走搜索域：

$ kubectl -n notes-lab exec ldeb1 -- getent ahostsv4 whoami.notes-lab
--- dnslog 新增查询:
A whoami.notes-lab. NXDOMAIN
A whoami.notes-lab.notes-lab.svc.cluster.local. NXDOMAIN
A whoami.notes-lab.svc.cluster.local. NOERROR

musl（lcu1，同样 ndots:1）只原样查一次，直接失败，curl 也一样：

$ kubectl -n notes-lab exec lcu1 -- getent ahostsv4 whoami.notes-lab
command terminated with exit code 2
(exit=2)
--- dnslog 新增查询:
A whoami.notes-lab. NXDOMAIN
$ kubectl -n notes-lab exec lcu1 -- curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://whoami.notes-lab/
000
curl: (6) Could not resolve host: whoami.notes-lab
command terminated with exit code 6
(exit=6)
--- dnslog 新增查询:
AAAA whoami.notes-lab. NXDOMAIN
A whoami.notes-lab. NXDOMAIN

短名 whoami 没有点，在 musl 的 ndots:1 下仍然走搜索域，一次命中。所以在 alpine 系镜像里调低 ndots，凡是「服务名.namespace」这类写法会直接解析失败，而不只是多几次查询。

glibc 的第一条 whoami.notes-lab. 不属于 cluster.local，CoreDNS 会把它转发给上游，集群内部的服务名就这样流到了集群外。如果第二段恰好是一个真实的公网顶级域，上游还会给出一个「成功」的错误答案，StatefulSet 那篇就碰到了 web 这个顶级域返回 127.0.53.53 的情况。所以调 ndots 之前，先确认业务代码里集群内的名字都写成短名或带末尾点的完整域名。对确定是外部的域名，在代码或配置里加末尾点，效果和调 ndots 一样，还不影响别的名字。

nslookup 的结果不能直接当结论

官方 DNS 调试文档的第一步是 nslookup kubernetes.default，文档里的客户端是用 dnsutils.yaml 部署的 registry.k8s.io/e2e-test-images/agnhost:2.39。换成很多人顺手用的 busybox:1.36 跑这条命令：

$ kubectl -n notes-lab exec cnd -- nslookup kubernetes.default
Server:		<dns-ip>
Address:	<dns-ip>:53

** server can't find kubernetes.default: NXDOMAIN

** server can't find kubernetes.default: NXDOMAIN

command terminated with exit code 1

集群 DNS 并没有坏，同一个 Pod 里查完整域名是正常的：

$ kubectl -n notes-lab exec cnd -- nslookup kubernetes.default.svc.cluster.local.
Name:	kubernetes.default.svc.cluster.local
Address: <kubernetes-ip>

busybox 的 nslookup 自己实现了查询逻辑：名字里只要有点就原样查询，不走搜索域，也不管 ndots（源码分析见 StatefulSet 一篇）。日志里看得很清楚，whoami.notes-lab 只被原样查了，A、AAAA 各两次：

$ kubectl -n notes-lab exec lbb -- nslookup whoami.notes-lab
** server can't find whoami.notes-lab: NXDOMAIN

** server can't find whoami.notes-lab: NXDOMAIN

command terminated with exit code 1
--- dnslog 新增查询:
A whoami.notes-lab. NXDOMAIN
A whoami.notes-lab. NXDOMAIN
AAAA whoami.notes-lab. NXDOMAIN
AAAA whoami.notes-lab. NXDOMAIN

而同一个 Pod 里的 busybox wget 走 C 库解析器，同一个名字可以访问：

$ kubectl -n notes-lab exec lbb -- wget -qO /dev/null -S -T 3 http://whoami.notes-lab/
  HTTP/1.1 200 OK
--- dnslog 新增查询:
AAAA whoami.notes-lab.notes-lab.svc.cluster.local. NXDOMAIN
A whoami.notes-lab.notes-lab.svc.cluster.local. NXDOMAIN
A whoami.notes-lab.svc.cluster.local. NOERROR
AAAA whoami.notes-lab.svc.cluster.local. NOERROR

更隐蔽的是短名。busybox nslookup whoami 会走搜索域，而且把每个搜索域的 A、AAAA 并发发出去，把所有失败都打印出来。答案明明查到了，退出码却是 1：

$ kubectl -n notes-lab exec lbb -- nslookup whoami
** server can't find whoami.cluster.local: NXDOMAIN

** server can't find whoami.svc.cluster.local: NXDOMAIN

Name:	whoami.notes-lab.svc.cluster.local
Address: <cluster-ip>

** server can't find whoami.svc.cluster.local: NXDOMAIN

** server can't find whoami.cluster.local: NXDOMAIN

** server can't find whoami.localdomain: NXDOMAIN


** server can't find whoami.localdomain: NXDOMAIN

command terminated with exit code 1

在脚本里写 nslookup whoami && ... 判断 DNS 是否就绪，会永远判定失败。用 busybox 排查时有两条规则：要么查带末尾点的完整域名，要么换一个带 getent 的镜像用 getent ahosts，或者直接用 wget 验证。

名字拼错，为什么要等好几秒

  • 前三个搜索域在同一毫秒内全部返回，它们属于 cluster.local，CoreDNS 的 kubernetes 插件本地就能回答。
  • .localdomain 用了约 3.1 秒。 它不归集群管，CoreDNS 转发给节点的上游 DNS，上游过了 3 秒才回 NXDOMAIN。单独测一次也是这样：t1-1791789013.localdomain. 耗时 3181ms，而 cluster.local 下的名字只要 1～2ms。上游为什么这么慢没有测到，推测和宿主机的解析器配置有关。
  • 原样查询 typo-xxx. 返回 SERVFAIL，之后 musl 又在 2.5 秒时重发了一轮，直到 5 秒超时。 去掉 localdomain（dnsPolicy: None 只留三个集群搜索域）后，同样的测试稳定在 5.0 秒：
== cfix
typo-1791789169-1 exit=6 5.005501s
typo-1791789174-2 exit=6 5.006167s
typo-1791789179-3 exit=6 5.005428s

glibc 对 SERVFAIL 的处理不同，不会等满超时。Debian 镜像里的 curl 查一个新的拼错名字，只花了 localdomain 那 3 秒：

$ kubectl -n notes-lab exec ldeb -- bash -c "n=typo-$(date +%s); echo $n; curl -s -m 15 -o /dev/null -w \"exit=%{exitcode} %{time_total}s\n\" http://$n/"
typo-1791789027
exit=6 3.037512s

这几个数字和这个环境强相关（节点继承来的搜索域、上游对单标签名字回 SERVFAIL），换个集群不一定一样。但现象是通用的：名字拼错时不一定立刻失败，可能先卡几秒，表现得像 DNS 超时。看到「解析慢」时，先确认名字本身是否存在，不要直接去调 CoreDNS。

三种「没有后端」：DNS 给的答案不一样

情况DNS 结果curl 报错
ClusterIP Service，选择器匹配不到 Pod（noep）返回 ClusterIPFailed to connect ... after 0 ms，立即失败
Service 不存在（nosuchsvc）所有搜索域 NXDOMAINCould not resolve host，可能等几秒
headless Service，副本缩到 0，或 Pod 存在但未就绪（默认配置）NXDOMAIN同上

ClusterIP 无后端：能解析，连接被拒

noep 的 EndpointSlice 是空的，但 DNS 照样返回 ClusterIP：

$ kubectl -n notes-lab get endpointslice
NAME              ADDRESSTYPE   PORTS     ENDPOINTS                        AGE
noep-kscvf        IPv4          <unset>   <unset>                          47s
whoami-hl-8dxhr   IPv4          80        <pod-ip-1>,<pod-ip-2>            49s
whoami-q2r9c      IPv4          80        <pod-ip-1>,<pod-ip-2>            51s
$ kubectl -n notes-lab exec ldeb -- getent ahostsv4 noep
<cluster-ip>    STREAM noep.notes-lab.svc.cluster.local
<cluster-ip>    DGRAM  
<cluster-ip>    RAW    
exit=0
$ kubectl -n notes-lab logs dnslog --timestamps --since=3m | grep noep    # 节选：只保留本次 getent 对应的一行
2026-10-12T07:05:11.280736310Z [INFO] A noep.notes-lab.svc.cluster.local. NOERROR

连接 0 毫秒就失败，原因在节点的 iptables 里，kube-proxy 给没有后端的 Service 装了一条 REJECT：

$ docker exec worker2 iptables-save | grep 'notes-lab/noep'
-A KUBE-SERVICES -d <cluster-ip>/32 -p tcp -m comment --comment "notes-lab/noep has no endpoints" -m tcp --dport 80 -j REJECT --reject-with icmp-port-unreachable

所以「能解析 + 连接立刻被拒」基本可以排除 DNS，直接去查 Service 的选择器、Pod 标签和就绪状态，见 探针与资源管理。

headless Service：A 记录就是 Pod IP

有后端时，headless Service 的 A 记录直接是所有就绪 Pod 的 IP，不经过 ClusterIP：

$ kubectl -n notes-lab exec cnd -- nslookup -type=a whoami-hl.notes-lab.svc.cluster.local.
Name:	whoami-hl.notes-lab.svc.cluster.local
Address: <pod-ip-2>
Name:	whoami-hl.notes-lab.svc.cluster.local
Address: <pod-ip-1>

SRV 记录只为有名字的端口生成。端口没起名时查 _http._tcp.whoami-hl... 是 NXDOMAIN；给端口加上 name: http 后：

_http._tcp.whoami-hl.notes-lab.svc.cluster.local	service = 0 50 80 <a-b-c-d>.whoami-hl.notes-lab.svc.cluster.local
_http._tcp.whoami-hl.notes-lab.svc.cluster.local	service = 0 50 80 <e-f-g-h>.whoami-hl.notes-lab.svc.cluster.local

把 Deployment 缩到 0 再查。普通 Service 还在返回 ClusterIP，headless Service 变成了 NXDOMAIN：

Name:	whoami.notes-lab.svc.cluster.local
Address: <cluster-ip>

** server can't find whoami-hl.notes-lab.svc.cluster.local.: NXDOMAIN

在客户端看来，这和 Service 根本不存在完全一样，日志里也是把搜索域走完再原样查：

$ kubectl -n notes-lab exec ldeb -- getent ahostsv4 whoami-hl
command terminated with exit code 2
--- dnslog 新增查询:
A whoami-hl.notes-lab.svc.cluster.local. NXDOMAIN
A whoami-hl.svc.cluster.local. NXDOMAIN
A whoami-hl.cluster.local. NXDOMAIN
A whoami-hl.localdomain. NXDOMAIN
A whoami-hl. SERVFAIL
A whoami-hl. SERVFAIL

缩到 0 是「根本没有 Pod」。Pod 存在但没就绪时又怎样？另起一个就绪探针故意失败的 nginx Pod nr（Running 但 0/1），给它配两个 headless Service：nr-hl 用默认配置，nr-hl-pub 加上 publishNotReadyAddresses: true：

$ kubectl -n notes-lab get pod nr
NAME   READY   STATUS    RESTARTS   AGE
nr     0/1     Running   0          38s
$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=nr-hl -o jsonpath='{range .items[*].endpoints[*]}nr-hl {.targetRef.name} ready={.conditions.ready}{"\n"}{end}'
nr-hl nr ready=false
$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=nr-hl-pub -o jsonpath='{range .items[*].endpoints[*]}nr-hl-pub {.targetRef.name} ready={.conditions.ready}{"\n"}{end}'
nr-hl-pub nr ready=true
$ kubectl -n notes-lab exec ldeb1 -- getent ahostsv4 nr-hl.notes-lab.svc.cluster.local.
command terminated with exit code 2
(exit=2)
--- dnslog 新增查询:
A nr-hl.notes-lab.svc.cluster.local. NXDOMAIN
$ kubectl -n notes-lab exec ldeb1 -- getent ahostsv4 nr-hl-pub.notes-lab.svc.cluster.local.
<pod-ip>  STREAM nr-hl-pub.notes-lab.svc.cluster.local
(exit=0)
--- dnslog 新增查询:
A nr-hl-pub.notes-lab.svc.cluster.local. NOERROR

（中间两行是两个 Service 的 EndpointSlice 里 nr 的 ready 条件。）默认配置下，未就绪的 Pod 在 EndpointSlice 里是 ready=false，DNS 里看不到它，结果同样是 NXDOMAIN；开了 publishNotReadyAddresses 后，EndpointSlice 把它标成 ready=true，DNS 立刻返回了它的 IP。

所以 headless Service 报 NXDOMAIN 时，先 kubectl get service 确认它存不存在，存在的话再看 EndpointSlice 里有没有就绪地址、Service 是否开了 publishNotReadyAddresses；不要急着怀疑 CoreDNS。StatefulSet 用的也是 headless Service，推测其 Pod 未就绪时也会出现同样的 NXDOMAIN，这次没有用 StatefulSet 单独验证。

NetworkPolicy 拦住了 DNS

给客户端 Pod（标签 role=client）加一条出站策略，只放行到 whoami 的 80 端口。很多人写出站白名单时只想到业务端口：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: client-egress
spec:
  podSelector:
    matchLabels: {role: client}
  policyTypes: [Egress]
  egress:
    - to:
        - podSelector:
            matchLabels: {app: whoami}
      ports:
        - {protocol: TCP, port: 80}

策略生效前 curl http://whoami/ 返回 200。生效后：

curl: (28) Resolving timed out after 15000 milliseconds
000 14.999502s
command terminated with exit code 28
exit=2

real	0m20.021s
200 0.000411s

三行结果分别是：curl 卡在解析阶段直到 15 秒上限；getent ahostsv4 whoami 20 秒后返回「找不到」；直接用 ClusterIP 访问，0.4 毫秒返回 200。业务流量是通的，只有到 DNS 的 UDP/TCP 53 被拦了。报错是 Resolving timed out，不是 Could not resolve host：前者是 DNS 服务器没有回应，后者是服务器回答了「没有这个名字」。getent 的 20 秒，推测是 glibc 默认 timeout:5、attempts:2 在多次查询上累加出来的，这次没有逐包验证。

补一条放行 DNS 的策略。注意选的是 CoreDNS Pod，不是 kube-dns 的 ClusterIP，NetworkPolicy 匹配的是 Pod：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
spec:
  podSelector:
    matchLabels: {role: client}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - {protocol: UDP, port: 53}
        - {protocol: TCP, port: 53}
200 0.001082s
curl: (28) Connection timed out after 15000 milliseconds
000 14.999320s

whoami 恢复了。example.com 现在能解析，但卡在了连接阶段，因为出站白名单里没有它。从 Resolving timed out 变成 Connection timed out，说明问题已经从 DNS 移到了下一层。策略写法见 NetworkPolicy。

排查顺序

把上面的现象串起来，一个服务名访问不了时，按这个顺序查：

  1. 在出问题的 Pod 里测，不要在宿主机或别的 Pod 里测。 宿主机不用集群 DNS；别的 Pod 可能 dnsPolicy、NetworkPolicy 都不同。先 cat /etc/resolv.conf，确认 nameserver 是集群 DNS、搜索域里有本 namespace。
  2. 用完整域名加末尾点、用 getent ahosts 测。 getent ahosts whoami.notes-lab.svc.cluster.local. 能解析，说明 DNS 服务本身没问题，再去看短名、ndots 和搜索域；用 busybox nslookup 时别看退出码，也别查带点的短名。
  3. 看报错属于哪一类。 Resolving timed out 或长时间无响应：DNS 包没回来，查 NetworkPolicy、CoreDNS 是否在运行。Could not resolve host 或 NXDOMAIN：服务器回答了没有这个名字，查名字拼写、namespace、Service 是否存在，headless Service 还要看有没有就绪 Pod。能解析但连接立刻被拒：Service 没有后端，查 EndpointSlice。能解析但连接超时：查 targetPort、容器监听地址和 NetworkPolicy。
  4. 最后才看 CoreDNS。
kubectl -n kube-system get service kube-dns
kubectl -n kube-system get endpointslice -l kubernetes.io/service-name=kube-dns
kubectl -n kube-system get pods -l k8s-app=kube-dns -o wide
kubectl -n kube-system get configmap coredns -o jsonpath='{.data.Corefile}'
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=50
NAME             ADDRESSTYPE   PORTS        ENDPOINTS                       AGE
kube-dns-7p7m6   IPv4          9153,53,53   <coredns-ip-1>,<coredns-ip-2>   60d

DNS 的 Service 名叫 kube-dns，后端实际是 CoreDNS，标签在不同发行版里可能不同。这个集群的 Corefile 没有 log 插件，CoreDNS 日志里只有错误，看不到每条查询，实验期间两个 CoreDNS Pod 一行日志都没有输出。想看查询明细，又不方便改系统组件时，可以像上面那样在自己的 namespace 里起一个带 log 的 CoreDNS 做转发，让问题 Pod 用 dnsPolicy: None 指过去。

清理

kubectl delete namespace notes-lab
