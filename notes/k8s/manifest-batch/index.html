用一个目录管理一组资源

kubectl 常用命令里讲过单个文件的 apply、create 和 last-applied-configuration 注解。一组相互依赖的对象（ConfigMap 和读它的 Pod、Deployment 和它的 Service）放进同一个目录，用 -f 目录/ 一次提交，可以少敲文件名，也少漏文件。但「一次提交一个目录」并不是一个原子操作，它有自己的处理顺序、文件筛选规则和删除边界，这一篇逐个实测。

下文输出来自一个三节点 kind 集群（Kubernetes v1.31.0，kubectl 客户端 v1.30.0），资源放在 实验命名空间 notes-lab 里，Cluster IP 用 <cluster-ip> 代替；kube-api-access- 后缀、ApplySet ID、/tmp/LIVE-* 路径都是随机值，以自己的输出为准。先建好 namespace：

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done

目录和清单

batch-demo/01-configmap.yaml：

apiVersion: v1
kind: ConfigMap
metadata:
  name: batch-demo
  labels:
    app.kubernetes.io/part-of: batch-demo
data:
  message: hello-from-directory

batch-demo/02-pod.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: batch-demo
  labels:
    app.kubernetes.io/part-of: batch-demo
spec:
  containers:
    - name: reader
      image: busybox:1.36
      command: ["sh", "-c", "cat /etc/demo/message; echo; sleep 3600"]
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
      volumeMounts:
        - name: settings
          mountPath: /etc/demo
          readOnly: true
  volumes:
    - name: settings
      configMap:
        name: batch-demo

两份清单都打了 app.kubernetes.io/part-of: batch-demo，后面按标签清理时要用。

后文陆续用到的其他文件都很短，要点如下，照着写就能复现：

  • batch-demo/extra/03-service.yaml：Service batch-demo，带 part-of 标签，selector 也是 app.kubernetes.io/part-of: batch-demo，端口 80。
  • batch-demo/04-extra.json、batch-demo/05-extra.yml：ConfigMap from-json、from-yml，带 part-of 标签，各带一个 data 键（format: json、format: yml）。
  • batch-demo/notes.txt：ConfigMap from-txt，不带标签。
  • teammate.yaml（放在目录外）：ConfigMap teammate-config，带 part-of 标签，模拟「别人的对象碰巧打了同一个标签」。
  • order-demo/：namespace.yaml 是 Namespace notes-lab-order；deployment.yaml（1 副本 nginx:alpine，名为 web，selector 为 app: web）和 service.yaml（web，selector 为 app: web，端口 80）都写了 namespace: notes-lab-order，不带 part-of 标签。
  • aset/a.yaml、aset/b.yaml：ConfigMap aset-a、aset-b，各带一个 data 键（k: a、k: b），不带标签。
  • ns-mismatch.yaml：ConfigMap ns-mismatch，写了 namespace: notes-lab-other。
  • dirbad/、multi/、sort-demo/ 里都是最小 ConfigMap，不带标签；sort-demo/ 里对象名是 sort- 加小写文件名，如 B.yaml 对应 sort-b。

除了 order-demo/ 和 ns-mismatch.yaml，这些文件都不写 namespace 字段。清单里没写 namespace，统一在命令行用 -n notes-lab 指定；如果清单里写了 namespace，又在命令行给了另一个，kubectl 会直接拒绝，不会悄悄选一个：

$ kubectl -n notes-lab apply -f ns-mismatch.yaml --dry-run=client
error: the namespace from the provided object "notes-lab-other" does not match the namespace "notes-lab". You must pass '--namespace=notes-lab-other' to perform this operation.

预览、应用、核对

对象还不存在时，get -f 会对目录里的每个对象报一次 NotFound，退出码为 1：

$ kubectl -n notes-lab get -f batch-demo/
Error from server (NotFound): configmaps "batch-demo" not found
Error from server (NotFound): pods "batch-demo" not found

--dry-run=server 让 API Server 把两个对象都走一遍校验和准入：

$ kubectl -n notes-lab apply -f batch-demo/ --dry-run=server
configmap/batch-demo created (server dry run)
pod/batch-demo created (server dry run)

注意 Pod 引用的 ConfigMap 此时并不存在，dry-run 照样通过：API Server 不检查对象之间的引用，ConfigMap 缺失要等 Pod 真正调度到节点、kubelet 挂载卷时才会暴露。dry-run 通过只说明每个对象单独合法。

正式提交、核对、看日志：

$ kubectl -n notes-lab apply -f batch-demo/
configmap/batch-demo created
pod/batch-demo created
$ kubectl -n notes-lab get -f batch-demo/
NAME                   DATA   AGE
configmap/batch-demo   1      0s

NAME             READY   STATUS              RESTARTS   AGE
pod/batch-demo   0/1     ContainerCreating   0          0s
$ kubectl -n notes-lab wait --for=condition=Ready pod/batch-demo --timeout=120s && kubectl -n notes-lab logs batch-demo
pod/batch-demo condition met
hello-from-directory

get -f 只列目录里声明的对象，不会把 namespace 里的其他东西带出来，适合用来核对「这一组」的状态。

diff 的三种退出码

kubectl diff 本身的原理（交给服务端做一次试合并，再和线上对象比较）见 kubectl 常用命令，这里只看对目录用时的退出码。刚 apply 完、没有改动时：

$ kubectl -n notes-lab diff -f batch-demo/; echo "diff exit=$?"
diff exit=0

把 ConfigMap 的 message 改成 hello-v2：

$ kubectl -n notes-lab diff -f batch-demo/; echo "diff exit=$?"
diff -u -N /tmp/LIVE-3184281781/v1.ConfigMap.notes-lab.batch-demo /tmp/MERGED-252728610/v1.ConfigMap.notes-lab.batch-demo
--- /tmp/LIVE-3184281781/v1.ConfigMap.notes-lab.batch-demo	2026-10-13 18:39:25.197663115 +0800
+++ /tmp/MERGED-252728610/v1.ConfigMap.notes-lab.batch-demo	2026-10-13 18:39:25.197663115 +0800
@@ -1,6 +1,6 @@
 apiVersion: v1
 data:
-  message: hello-from-directory
+  message: hello-v2
 kind: ConfigMap
 metadata:
   annotations:
diff exit=1

在保留这处改动的同时，再把 Pod 的 CPU request 从 10m 改成 20m。Pod 创建后 resources 不能原地修改（InPlacePodVerticalScaling 在 v1.31 是默认关闭的 alpha 特性），服务端试合并直接失败：

$ kubectl -n notes-lab diff -f batch-demo/; echo "diff exit=$?"
The Pod "batch-demo" is invalid: spec: Forbidden: pod updates may not change fields other than `spec.containers[*].image`,`spec.initContainers[*].image`,`spec.activeDeadlineSeconds`,`spec.tolerations` (only additions to existing tolerations),`spec.terminationGracePeriodSeconds` (allow it to be set to 1 if it was previously negative)
  core.PodSpec{
...
- 					s"cpu":    {i: resource.int64Amount{value: 10, scale: -3}, s: "10m", Format: "DecimalSI"},
+ 					s"cpu":    {i: resource.int64Amount{value: 20, scale: -3}, s: "20m", Format: "DecimalSI"},
...
diff exit=2

退出码 2 符合官方定义（0 无差异，1 有差异，大于 1 表示 kubectl 或 diff 本身出错）。值得注意的是输出里没有 ConfigMap 那段 diff：任何一个对象出错，diff 就中止，已经算出的差异也不输出。CI 里拿 diff 做门禁时，退出码大于 1 要当作「未知」处理，不能当作「有差异」去继续发布。

把 Pod 改回 10m，apply 新的 ConfigMap。apply 后约 66 秒查看时，挂载进去的文件已经是新值（具体什么时候生效没有测）；按官方说明，这个延迟最长可达 kubelet 同步周期加上缓存传播的时间。日志还是旧的，因为程序只在启动时读一次：

$ date '+%T'; kubectl -n notes-lab exec batch-demo -- cat /etc/demo/message; echo; kubectl -n notes-lab logs batch-demo
18:40:38
hello-v2
hello-from-directory

Pod 每次都显示 configured

接着反复 apply 同一个目录，ConfigMap 显示 unchanged，Pod 却每次都是 configured：

$ kubectl -n notes-lab apply -f batch-demo/
configmap/batch-demo unchanged
pod/batch-demo configured

用 -v=8 看发出去的补丁，只有几条 $setElementOrder 指令，没有任何字段改动，同时 diff 返回 0：

$ kubectl -n notes-lab apply -f batch-demo/02-pod.yaml -v=8 2>&1 | grep 'Request Body' | sed 's/^.*Request Body: //'; kubectl -n notes-lab diff -f batch-demo/; echo "diff exit=$?"
{"spec":{"$setElementOrder/containers":[{"name":"reader"}],"$setElementOrder/volumes":[{"name":"settings"}],"containers":[{"$setElementOrder/volumeMounts":[{"mountPath":"/etc/demo"}],"name":"reader"}]}}
diff exit=0

线上 Pod 的卷和挂载点比清单多一项，是准入阶段自动注入的 ServiceAccount token：

$ kubectl -n notes-lab get pod batch-demo -o jsonpath='{.spec.volumes[*].name}{"\n"}{.spec.containers[0].volumeMounts[*].mountPath}{"\n"}'
settings kube-api-access-znntb
/etc/demo /var/run/secrets/kubernetes.io/serviceaccount

推测是客户端 apply 计算三方合并时，因为列表元素数量不同，总要生成一个保持顺序的补丁，于是 kubectl 认为「有补丁就是 configured」。所以 configured 不能当作「真的改了东西」的依据，要判断是否有变化，看 diff 的退出码。

目录里哪些文件会被读

子目录：没有 -R 就跳过

在 batch-demo/extra/ 下再放一个 Service：

$ find batch-demo -type f | sort
batch-demo/01-configmap.yaml
batch-demo/02-pod.yaml
batch-demo/extra/03-service.yaml
$ kubectl -n notes-lab apply -f batch-demo/
configmap/batch-demo unchanged
pod/batch-demo configured
$ kubectl -n notes-lab get svc
No resources found in notes-lab namespace.
$ kubectl -n notes-lab apply -R -f batch-demo/
configmap/batch-demo unchanged
pod/batch-demo configured
service/batch-demo created

没有任何提示，子目录被静默忽略。get 和 delete 也一样：get -f batch-demo/ 只列出 ConfigMap 和 Pod，加 -R 才带上 Service（delete 的情况见后文）。diff 没有单独测，它和其他命令用的是同一套文件遍历逻辑，推断行为相同。目录一旦分层，这几条命令都要记得加 -R，否则删除时会漏掉（后面会看到）。

扩展名：只认 .yaml、.yml、.json

往目录里加四个文件：README.md、内容是合法 ConfigMap 的 notes.txt、JSON 格式的 04-extra.json、.yml 后缀的 05-extra.yml：

$ ls batch-demo
01-configmap.yaml
02-pod.yaml
04-extra.json
05-extra.yml
README.md
extra
notes.txt
$ kubectl -n notes-lab apply -f batch-demo/
configmap/batch-demo unchanged
pod/batch-demo configured
configmap/from-json created
configmap/from-yml created

.json 和 .yml 被读了，README.md 和 notes.txt 被跳过，同样没有提示。所以在清单目录里放说明文档是安全的。但这个过滤只在遍历目录时生效，把 .txt 文件直接点名给 -f，照样会提交：

$ kubectl -n notes-lab apply -f batch-demo/notes.txt
configmap/from-txt created

验证完随后删掉了 from-txt（kubectl -n notes-lab delete cm from-txt）。

坏文件会挡住谁

语法错误：只影响它所在的文件

目录 dirbad/ 里有 a.yaml、b.yaml、c.yaml 三个 ConfigMap，b.yaml 的 data: 前面多了一个空格：

$ kubectl -n notes-lab apply -f dirbad/
configmap/dir-a created
configmap/dir-c created
error: error parsing dirbad/b.yaml: error converting YAML to JSON: yaml: line 4: did not find expected key

排在后面的 c.yaml 照样提交了，坏文件的报错留到最后输出，退出码为 1。

多文档文件：坏文档之后的全部丢掉

把三个 ConfigMap 用 --- 写进同一个 multi/all.yaml，第二个文档同样多一个空格：

$ cat -n multi/all.yaml
     1	apiVersion: v1
     2	kind: ConfigMap
     3	metadata:
     4	  name: multi-a
     5	data:
     6	  k: a
     7	---
     8	apiVersion: v1
     9	kind: ConfigMap
    10	metadata:
    11	  name: multi-b
    12	 data:
    13	  k: b
    14	---
    15	apiVersion: v1
    16	kind: ConfigMap
    17	metadata:
    18	  name: multi-c
    19	data:
    20	  k: c
$ kubectl -n notes-lab apply -f multi/all.yaml
configmap/multi-a created
error: error parsing multi/all.yaml: error converting YAML to JSON: yaml: line 4: did not find expected key
$ kubectl -n notes-lab get cm -o name | grep multi
configmap/multi-a

这次结果不一样：multi-a 提交了，multi-c 没有。解析器读到坏文档就放弃了整个文件的剩余部分。另外报错里的 line 4 是相对于第二个文档的行号，文件里对应的是第 11、12 行附近，不能直接拿去跳转。

如果第二个文档的 YAML 合法、只是内容不合法，比如名字写成 Multi_B。先删掉上一轮留下的 multi-a，再提交：

$ kubectl -n notes-lab delete cm multi-a
configmap "multi-a" deleted
$ kubectl -n notes-lab apply -f multi/all.yaml
configmap/multi-a created
configmap/multi-c created
The ConfigMap "Multi_B" is invalid: metadata.name: Invalid value: "Multi_B": a lowercase RFC 1123 subdomain must consist of lower case alphanumeric characters, '-' or '.', and must start and end with an alphanumeric character (e.g. 'example.com', regex used for validation is '[a-z0-9]([-a-z0-9]*[a-z0-9])?(\.[a-z0-9]([-a-z0-9]*[a-z0-9])?)*')

这时三个文档都解析成功，被服务端拒绝的只有 Multi_B 自己，后面的 multi-c 不受影响。

归纳一下：客户端解析错误以文件为单位中断，服务端拒绝以对象为单位。无论哪种，都没有回滚，已经成功的对象留在集群里，一次 apply -f 目录/ 的结果可能是「部分成功」。

文件顺序：Namespace 排在后面

目录里的文件按名字的字节序处理，没有按资源类型排序：数字在前，大写字母排在小写前面；加 -R 时子目录按自己的名字参与排序。另做的一个小实验里，1.yaml、B.yaml、a.yaml、m/x.yaml、z.yaml 的提交顺序正是这样：

$ kubectl -n notes-lab apply -R -f sort-demo/ --dry-run=server
configmap/sort-1 created (server dry run)
configmap/sort-b created (server dry run)
configmap/sort-a created (server dry run)
configmap/sort-x created (server dry run)
configmap/sort-z created (server dry run)

用一个「自然命名」的目录验证，三个文件都属于一个尚不存在的 namespace notes-lab-order：

$ ls order-demo
deployment.yaml
namespace.yaml
service.yaml

先 dry-run：

$ kubectl apply -f order-demo/ --dry-run=server
namespace/notes-lab-order created (server dry run)
Error from server (NotFound): error when creating "order-demo/deployment.yaml": namespaces "notes-lab-order" not found
Error from server (NotFound): error when creating "order-demo/service.yaml": namespaces "notes-lab-order" not found

dry-run 不会真的创建 namespace，所以里面的对象全部失败。diff 更彻底，第一个对象出错就整体中止，退出码 2：

$ kubectl diff -f order-demo/; echo "diff exit=$?"
Error from server (NotFound): namespaces "notes-lab-order" not found
diff exit=2

也就是说，一个「新建 namespace 加若干资源」的目录，第一次部署前用 --dry-run=server 或 diff 预检注定失败，这种失败不代表清单有错。

正式提交：

$ kubectl apply -f order-demo/
namespace/notes-lab-order created
service/web created
Error from server (NotFound): error when creating "order-demo/deployment.yaml": namespaces "notes-lab-order" not found

deployment.yaml 排在 namespace.yaml 前面，提交时 namespace 还不存在，失败；service.yaml 排在后面，成功了。报错统一打印在最后，不看清楚的话容易以为是 Service 之后出了问题。

紧接着第二次执行，这时 namespace 已经存在，Deployment 才被创建：

$ kubectl apply -f order-demo/
deployment.apps/web created
namespace/notes-lab-order unchanged
service/web unchanged

之后又跑了第三次，加 -v=6 看请求顺序（三个对象此时都已存在，这次没有任何创建），确认处理顺序就是文件名顺序：

$ kubectl apply -f order-demo/ -v=6 2>&1 | grep -E 'GET .*/(namespaces|deployments|services)/' | sed -E 's/^.*(GET [^ ]+).*/\1/; s#https://[^/]+#https://<apiserver>#'
GET https://<apiserver>/apis/apps/v1/namespaces/notes-lab-order/deployments/web
GET https://<apiserver>/api/v1/namespaces/notes-lab-order
GET https://<apiserver>/api/v1/namespaces/notes-lab-order/services/web

所以再执行一次能「修好」，但第一次的退出码是 1，流水线会判失败。正确做法是用文件名控制顺序，比如 00-namespace.yaml；CRD 和使用它的自定义资源也是同样的道理。

删除：delete -f 和 –ignore-not-found

delete -f 同样按文件顺序删除：

$ kubectl delete -f order-demo/
deployment.apps "web" deleted
namespace "notes-lab-order" deleted
service "web" deleted

再执行一次，每个对象一条 NotFound，退出码 1；清理脚本需要可以重复执行时，加 --ignore-not-found：

$ kubectl delete -f order-demo/
Error from server (NotFound): error when deleting "order-demo/deployment.yaml": deployments.apps "web" not found
Error from server (NotFound): error when deleting "order-demo/namespace.yaml": namespaces "notes-lab-order" not found
Error from server (NotFound): error when deleting "order-demo/service.yaml": services "web" not found
$ kubectl delete -f order-demo/ --ignore-not-found; echo "exit=$?"
exit=0

移走文件，对象还在

回到 batch-demo。此时集群里有它的 ConfigMap、Pod、Service，以及 from-json、from-yml 两个 ConfigMap。把 05-extra.yml 移出目录，再 apply：

$ kubectl -n notes-lab apply -R -f batch-demo/
configmap/batch-demo unchanged
pod/batch-demo configured
configmap/from-json unchanged
service/batch-demo unchanged
$ kubectl -n notes-lab get cm -l app.kubernetes.io/part-of=batch-demo
NAME         DATA   AGE
batch-demo   1      2m51s
from-json    1      54s
from-yml     1      54s
$ kubectl -n notes-lab diff -R -f batch-demo/; echo "diff exit=$?"
diff exit=0

from-yml 成了孤儿：目录里没有它，集群里还在，而且 diff 返回 0，看不出任何异样。apply 只管「目录里有的对象」，它不知道上一次提交过什么。

–prune -l：按标签删掉不在目录里的对象

--prune 会删除「匹配选择器、带 last-applied-configuration 注解、但不在本次清单里」的对象。kubectl diff 也支持 --prune，先预览会删什么（ConfigMap 的完整内容一大段，这里只保留头部）：

$ kubectl -n notes-lab diff -R -f batch-demo/ --prune -l app.kubernetes.io/part-of=batch-demo; echo "diff exit=$?"
W1013 18:42:16.141672 2155515 prune.go:71] Deprecated: kubectl apply will no longer prune non-namespaced resources by default when used with the --namespace flag in a future release. To preserve the current behaviour, list the resources you want to target explicitly in the --prune-allowlist flag.
diff -u -N /tmp/LIVE-2102057160/v1.ConfigMap.notes-lab.from-yml /tmp/MERGED-2260197012/v1.ConfigMap.notes-lab.from-yml
--- /tmp/LIVE-2102057160/v1.ConfigMap.notes-lab.from-yml	2026-10-13 18:42:17.344320229 +0800
+++ /tmp/MERGED-2260197012/v1.ConfigMap.notes-lab.from-yml	1970-01-01 07:30:00.000000000 +0730
@@ -1,32 +0,0 @@
-apiVersion: v1
-data:
-  format: yml
...
diff exit=1

预览里要删的只有孤儿 from-yml。为了看清 prune 的实际范围，预览之后又在 namespace 里放了两个带同样标签、但不属于这个目录的 ConfigMap：一个用 kubectl create 建再打标签（没有 last-applied 注解），一个是另一份文件 teammate.yaml 用 apply 建的：

$ kubectl -n notes-lab create configmap made-by-create --from-literal=k=v && kubectl -n notes-lab label cm made-by-create app.kubernetes.io/part-of=batch-demo
configmap/made-by-create created
configmap/made-by-create labeled
$ kubectl -n notes-lab apply -f teammate.yaml
configmap/teammate-config created

然后真正执行 prune：

$ kubectl -n notes-lab apply -R -f batch-demo/ --prune -l app.kubernetes.io/part-of=batch-demo
configmap/batch-demo unchanged
pod/batch-demo configured
configmap/from-json unchanged
service/batch-demo unchanged
W1013 18:42:17.745140 2155791 prune.go:71] Deprecated: kubectl apply will no longer prune non-namespaced resources by default when used with the --namespace flag in a future release. To preserve the current behaviour, list the resources you want to target explicitly in the --prune-allowlist flag.
configmap/from-yml pruned
configmap/teammate-config pruned
$ kubectl -n notes-lab get cm -l app.kubernetes.io/part-of=batch-demo
NAME             DATA   AGE
batch-demo       1      3m4s
from-json        1      67s
made-by-create   1      2s

对比预览：预览时还没有 teammate-config，所以 diff 里看不到它；执行时它已经在了，于是被误删。孤儿 from-yml 删掉了，但别人用 apply 建的 teammate-config 也一起被删了，只因为它碰巧带着同一个标签；made-by-create 逃过一劫，仅仅因为它没有 last-applied 注解。这就是这种模式的问题：kubectl 并不记得「哪些对象属于这个目录」，只能靠「标签 + 注解」去猜。还要注意两点：

  • 那条 Deprecated 警告说的是：带 --namespace 时，默认的 prune 白名单目前还会扫描集群级资源（如 Namespace、PersistentVolume），以后会改掉。官方文档建议同时用 --prune-allowlist 写明要清理的类型，比如 --prune-allowlist=core/v1/ConfigMap。
  • 官方文档还提醒，prune 只能对清单的根目录执行。对子目录执行时，其他子目录里带同样标签的对象都会被当作孤儿删掉。

这种基于白名单的 prune 从 kubectl v1.5 起至今仍是 alpha（v1.30 的 kubectl apply --help 里写着 Alpha Disclaimer: the --prune functionality is not yet complete），截至当前官方文档也仍是 alpha，官方的定位是由 ApplySet 取代它。

ApplySet：用一个父对象记录成员

ApplySet 从 kubectl v1.27 开始以 alpha 提供，需要设置环境变量 KUBECTL_APPLYSET=true，不设的话 v1.30 不认这个参数：

$ kubectl -n notes-lab apply --prune --applyset=aset-demo -f aset/
error: unknown flag: --applyset
See 'kubectl apply --help' for usage.
$ KUBECTL_APPLYSET=true kubectl -n notes-lab apply --prune --applyset=aset-demo -f aset/
configmap/aset-a created
configmap/aset-b created

aset/ 里有 a.yaml、b.yaml 两个 ConfigMap。kubectl 默认建了一个名为 aset-demo 的 Secret 做父对象，在父对象上记下 ID 和包含的资源类型，再给每个成员打上对应的标签：

$ kubectl -n notes-lab get secret aset-demo -o jsonpath='{.metadata.labels}{"\n"}{.metadata.annotations}{"\n"}'
{"applyset.kubernetes.io/id":"applyset-NU_ZSZjcmueGU8U7VvjXyaqGJOA7VkK8kqnlurvBLmo-v1"}
{"applyset.kubernetes.io/additional-namespaces":"","applyset.kubernetes.io/contains-group-kinds":"ConfigMap","applyset.kubernetes.io/tooling":"kubectl/v1.30.0"}
$ kubectl -n notes-lab get cm aset-a --show-labels
NAME     DATA   AGE   LABELS
aset-a   1      0s    applyset.kubernetes.io/part-of=applyset-NU_ZSZjcmueGU8U7VvjXyaqGJOA7VkK8kqnlurvBLmo-v1

删掉 b.yaml 后再执行，aset-b 被清理；同一 namespace 里由别人 apply 的 teammate-config 不带这个 ApplySet 标签，没有被碰：

$ KUBECTL_APPLYSET=true kubectl -n notes-lab apply --prune --applyset=aset-demo -f aset/
configmap/aset-a unchanged
configmap/aset-b pruned
$ kubectl -n notes-lab apply -f teammate.yaml
configmap/teammate-config created
$ KUBECTL_APPLYSET=true kubectl -n notes-lab apply --prune --applyset=aset-demo -f aset/
configmap/aset-a unchanged
$ kubectl -n notes-lab get cm teammate-config
NAME              DATA   AGE
teammate-config   1      0s

范围由 ApplySet 自己的成员标签决定，所以不能再叠加标签选择器：

$ KUBECTL_APPLYSET=true kubectl -n notes-lab apply --prune --applyset=aset-demo -f aset/ -l app=x
error: --selector is incompatible with --applyset

ApplySet 仍是 alpha，官方文档明确说后续版本可能有不兼容的改动；每个对象最多属于一个 ApplySet，多个目录要各用一个名字。父对象 Secret 不要随手删，推测删掉后 kubectl 就无从得知原来的成员（这一点没有实测）。如果需要在生产里长期按目录同步，Kustomize 渲染加上 Argo CD、Flux 这类 GitOps 工具会更稳妥；多个工具改同一对象的字段归属问题见 Server-Side Apply。

按标签批量清理，以及 all 的范围

prune 之后，namespace 里带 part-of=batch-demo 的对象有 Pod、Service、四个 ConfigMap（batch-demo、from-json、made-by-create，以及 ApplySet 一节重新 apply 的 teammate-config），再加一个随后创建并打上同样标签的 Secret batch-demo-token：

$ kubectl -n notes-lab create secret generic batch-demo-token --from-literal=t=x && kubectl -n notes-lab label secret batch-demo-token app.kubernetes.io/part-of=batch-demo
secret/batch-demo-token created
secret/batch-demo-token labeled

先用 delete -f 删目录里的对象，故意不加 -R：

$ kubectl -n notes-lab delete -f batch-demo/
configmap "batch-demo" deleted
pod "batch-demo" deleted
configmap "from-json" deleted
$ kubectl -n notes-lab get all,cm,secret -l app.kubernetes.io/part-of=batch-demo
NAME                 TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
service/batch-demo   ClusterIP   <cluster-ip>    <none>        80/TCP    2m6s

NAME                        DATA   AGE
configmap/made-by-create    1      53s
configmap/teammate-config   1      36s

NAME                      TYPE     DATA   AGE
secret/batch-demo-token   Opaque   1      31s

extra/ 里的 Service 留了下来，这正是前面说的「分层目录忘了 -R」。剩下的对象按标签清理，很多人会写 delete all：

$ kubectl -n notes-lab delete all -l app.kubernetes.io/part-of=batch-demo
service "batch-demo" deleted
$ kubectl -n notes-lab get all,cm,secret -l app.kubernetes.io/part-of=batch-demo
NAME                        DATA   AGE
configmap/made-by-create    1      59s
configmap/teammate-config   1      42s

NAME                      TYPE     DATA   AGE
secret/batch-demo-token   Opaque   1      37s

all 不是「所有资源」，而是一个资源类别，成员由各资源自己声明。在这个集群上它包含：

$ kubectl api-resources --categories=all -o name
pods
replicationcontrollers
services
daemonsets.apps
deployments.apps
replicasets.apps
statefulsets.apps
horizontalpodautoscalers.autoscaling
cronjobs.batch
jobs.batch

ConfigMap、Secret、PersistentVolumeClaim、Ingress、ServiceAccount、Role 都不在里面。要把它们也删掉，得显式列出类型：

$ kubectl -n notes-lab delete all,cm,secret -l app.kubernetes.io/part-of=batch-demo
configmap "made-by-create" deleted
configmap "teammate-config" deleted
secret "batch-demo-token" deleted
$ kubectl -n notes-lab get all,cm,secret -l app.kubernetes.io/part-of=batch-demo
No resources found in notes-lab namespace.

按标签批量删除之所以可行，前提是每个清单都一致地打了同一个标签；推荐用 app.kubernetes.io/part-of、app.kubernetes.io/name 这类公共标签，规则见 标签与选择器。反过来，teammate-config 的例子也说明：标签只是约定，任何人都能打，按标签删除之前先用同样的选择器 get 一遍，确认清单。

清理

kubectl delete namespace notes-lab --wait
kubectl get namespace notes-lab
# Error from server (NotFound): namespaces "notes-lab" not found

ApplySet 的父 Secret 和其他实验对象都在这个 namespace 里，会一起删除。
