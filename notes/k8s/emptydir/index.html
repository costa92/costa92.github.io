emptyDir：和 Pod 同寿命的目录

emptyDir 在 Pod 被分配到节点时创建，一开始是空的，Pod 里的所有容器（包括 init 容器）都可以挂载它，挂载路径可以各不相同。容器崩溃不会让 Pod 离开节点，卷里的数据还在；Pod 从节点上删除，卷也随之删除。要在 Pod 重建后保留数据，需要 PVC，见持久卷与存储声明，那一篇也测了 local-path 卷的容量为什么不受限，这里不再重复。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，节点内核 7.0，cgroup v2），实验放在单独的 notes-lab namespace。节点名简化成 control-plane、worker、worker2。所有 Pod 都用 nodeSelector 固定在 worker 上，方便到节点里看卷目录。文中时间是 UTC。

这一篇关心的是 emptyDir 本身：它在哪、能活多久、两种介质（磁盘和内存）写满时分别发生什么。

init 容器写、主容器读

一个 Pod 三个容器：init 写配置，app 读配置并在收到信号文件后以退出码 3 崩溃，sidecar 以只读方式把同一个卷挂到另一个路径：

apiVersion: v1
kind: Pod
metadata:
  name: share
spec:
  nodeSelector:
    kubernetes.io/hostname: worker
  initContainers:
    - name: init
      image: busybox:1.36
      command: ["sh", "-c", "echo \"init wrote at $(date +%T)\" > /work/config; echo \"init ran at $(date +%T)\" >> /work/init.log"]
      volumeMounts:
        - name: work
          mountPath: /work
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo \"app start $(date +%T)\" >> /work/app.log; cat /work/config; while [ ! -f /work/crash ]; do sleep 1; done; rm /work/crash; echo crashing; exit 3"]
      volumeMounts:
        - name: work
          mountPath: /work
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 32Mi}
    - name: sidecar
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]
      volumeMounts:
        - name: work
          mountPath: /data
          readOnly: true
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 32Mi}
  volumes:
    - name: work
      emptyDir: {}
kubectl create namespace notes-lab
# 等 default ServiceAccount 出现再建 Pod，原因见 Pod 与容器一篇
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f share.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/share --timeout=120s
kubectl -n notes-lab logs share -c app
kubectl -n notes-lab exec share -c sidecar -- cat /data/config /data/init.log /data/app.log
kubectl -n notes-lab exec share -c sidecar -- sh -c "echo x > /data/try"
init wrote at 01:19:00
init wrote at 01:19:00
init ran at 01:19:00
app start 01:19:09
sh: can't create /data/try: Read-only file system
command terminated with exit code 1

第一行是 app 的日志，它读到了 init 容器留下的文件。init 容器 01:19:00 已经写完，app 01:19:09 才启动，中间隔了 9 秒（时间花在哪一步这次没细查），文件一直在卷里等着。这是 init 容器准备配置、下载数据最常见的交接方式：init 容器的文件系统随它退出就没了，只有写进卷的东西能留给后面的容器。

sidecar 把卷挂在 /data，看到的是同一份文件；readOnly: true 只作用于这一个挂载，写入被拒绝，app 那边照样可写。

容器崩溃：卷里的数据还在，根文件系统没了

先让 app 在卷里和自己的根文件系统里各写一个文件，再触发崩溃：

kubectl -n notes-lab exec share -c app -- sh -c "echo before-crash \$(date +%T) > /work/marker; touch /tmp/in-rootfs"
kubectl -n notes-lab exec share -c app -- touch /work/crash

8 秒后：

NAME    READY   STATUS    RESTARTS     AGE
share   2/2     Running   1 (9s ago)   46s
kubectl -n notes-lab logs share -c app --previous
kubectl -n notes-lab logs share -c app
kubectl -n notes-lab exec share -c app -- sh -c "cat /work/marker /work/init.log /work/app.log; ls /tmp/in-rootfs"
init wrote at 01:19:00
crashing
init wrote at 01:19:00
before-crash 01:19:23
init ran at 01:19:00
app start 01:19:09
app start 01:19:27
ls: /tmp/in-rootfs: No such file or directory
command terminated with exit code 1

逐行看：

  • --previous 是崩溃前的实例，最后一行是 crashing；当前实例重新读到了配置。
  • /work/marker 还在，app.log 里有两次启动记录（01:19:09 和 01:19:27），卷跨过了容器重启。
  • /tmp/in-rootfs 没了。它写在容器的可写层里，重启后是一个新容器，可写层是新的。
  • init.log 只有一行。容器重启不会重跑 init 容器，init 容器只在 Pod 启动时跑一遍。如果 init 准备的文件被主容器删了或改坏了，重启主容器拿不回来，只能重建 Pod。

容器状态里记下了这次退出：

kubectl -n notes-lab get pod share -o jsonpath='{range .status.containerStatuses[*]}{.name} restarts={.restartCount} lastExit={.lastState.terminated.exitCode}{"\n"}{end}'
app restarts=1 lastExit=3
sidecar restarts=0 lastExit=

sidecar 没受影响。崩溃日志用 --previous 看的原因，见 Pod 与容器。

在节点上它就是一个目录

卷的位置是 /var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir/<卷名>。Pod 的 uid 用 kubectl get pod share -o jsonpath='{.metadata.uid}' 取，然后到节点里看（kind 节点就是一个 Docker 容器）：

docker exec <worker 的节点容器> ls -la /var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir/work
docker exec <worker 的节点容器> df -h /var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir/work
total 24
drwxrwxrwx 2 root root 4096 Oct 13 01:19 .
drwxr-xr-x 3 root root 4096 Oct 13 01:18 ..
-rw-r--r-- 1 root root   38 Oct 13 01:19 app.log
-rw-r--r-- 1 root root   23 Oct 13 01:19 config
-rw-r--r-- 1 root root   21 Oct 13 01:19 init.log
-rw-r--r-- 1 root root   22 Oct 13 01:19 marker
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda        916G  367G  503G  43% /var

两个细节：

  • 目录权限是 drwxrwxrwx（0777），所以不同 UID 运行的容器都能往里写。当前的官方文档介绍了用 emptyDir.mode 字段改这个权限，但它对应的特性门控 EmptyDirVolumeMode 要到 v1.37 才以 alpha 出现、默认关闭；v1.31 的 EmptyDirVolumeSource 里根本没有这个字段，本集群用不了。
  • 它和 kubelet 目录在同一个文件系统上。容器里 df 看到的也是整块盘：
kubectl -n notes-lab exec share -c app -- sh -c 'df -h /work; grep /work /proc/mounts'
Filesystem                Size      Used Available Use% Mounted on
/dev/sda                915.8G    366.3G    503.0G  42% /work
/dev/sda /work ext4 rw,relatime 0 0

/proc/mounts 里卷是从节点 bind mount 进来的 ext4，不是容器根文件系统那种 overlay。所以磁盘介质的 emptyDir 写多了，挤占的是节点磁盘，和镜像、日志共用一份空间；sizeLimit 也不会让 df 的数字变小，后面会看到它是怎么生效的。

kubectl -n notes-lab delete pod share --grace-period=1
docker exec <worker 的节点容器> ls /var/lib/kubelet/pods/<旧 uid>
kubectl -n notes-lab apply -f share.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/share --timeout=120s
kubectl -n notes-lab get pod share -o jsonpath='{.metadata.uid}{"\n"}'
kubectl -n notes-lab exec share -c app -- sh -c "ls -l /work; cat /work/init.log"
3ccd462b-3d2b-4661-a95e-73c66e8be792

同名 Pod，uid 变了（第一行），卷是新的：marker 不见了，init.log 也只有新的一行 01:19:52，init 容器重新跑了一遍。旧 Pod 的目录在节点上的清理比 kubectl delete 返回略晚：01:19:49 delete 返回后马上看，/var/lib/kubelet/pods/<旧 uid>/ 还在：

containers
etc-hosts
plugins
volumes

到 01:20:00 再看，已经整个没了：

docker exec <worker 的节点容器> ls /var/lib/kubelet/pods/<旧 uid>/volumes/kubernetes.io~empty-dir/
docker exec <worker 的节点容器> ls -d /var/lib/kubelet/pods/<旧 uid>
ls: cannot access '/var/lib/kubelet/pods/fc71c13c-1dfb-4c79-af6a-65a87a02fa13/volumes/kubernetes.io~empty-dir/': No such file or directory
ls: cannot access '/var/lib/kubelet/pods/fc71c13c-1dfb-4c79-af6a-65a87a02fa13': No such file or directory

Deployment 滚动更新、节点驱逐、重新调度，本质上都是删旧 Pod、建新 Pod，结果都是这样。emptyDir 适合放能丢的东西：缓存、中间结果、容器间交接的文件。

medium: Memory：写满了不是报错，是 OOM

medium: Memory 把卷换成 tmpfs。给容器 64Mi 的内存 limit，不写 sizeLimit：

apiVersion: v1
kind: Pod
metadata:
  name: mem
spec:
  nodeSelector:
    kubernetes.io/hostname: worker
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]
      volumeMounts:
        - name: cache
          mountPath: /cache
      resources:
        requests: {cpu: 10m, memory: 64Mi}
        limits: {memory: 64Mi}
  volumes:
    - name: cache
      emptyDir:
        medium: Memory
kubectl -n notes-lab exec mem -- sh -c "df -h /cache; grep /cache /proc/mounts; cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/memory.current"
Filesystem                Size      Used Available Use% Mounted on
tmpfs                    64.0M         0     64.0M   0% /cache
tmpfs /cache tmpfs rw,relatime,size=65536k,inode64,noswap 0 0
67108864
1777664

tmpfs 的大小是 64M，正好等于 Pod 的内存 limit。kubelet 挂 tmpfs 时取的大小是「节点可分配内存、Pod 内存 limit、sizeLimit」三者中最小的那个。这条规则来自 kubelet 的 calculateEmptyDirMemorySize。官方卷文档只写了「不指定大小时为节点可分配内存」，那是 Pod 没设内存 limit 的情况；资源管理文档的说法是不设 sizeLimit 时内存卷「may consume up to that pod’s memory limit」，和这里一致：每个容器都设了 limit，所以是 64M。由此也可知，sizeLimit 设得大于等于 Pod 内存 limit 不起作用。

写 40Mi，看容器的内存账：

kubectl -n notes-lab exec mem -- sh -c "dd if=/dev/zero of=/cache/a bs=1M count=40; cat /sys/fs/cgroup/memory.current; grep -E \"^(anon|file|shmem) \" /sys/fs/cgroup/memory.stat"
40+0 records in
40+0 records out
41943040 bytes (40.0MB) copied, 0.007758 seconds, 5.0GB/s
44769280
anon 614400
file 41988096
shmem 41943040

memory.current 从 1.7MiB 涨到 42.7MiB，shmem 正好是 40MiB，算在这个容器的内存里。kubectl top 这时还拿不到这个刚建的 Pod 的数据（podmetrics ... not found），要靠 cgroup 文件看。

再写 30Mi，总量 70Mi，超过 tmpfs 大小，也超过内存 limit。直觉上 tmpfs 先满，dd 应该报 No space left on device：

kubectl -n notes-lab exec mem -- sh -c "dd if=/dev/zero of=/cache/b bs=1M count=30; echo dd-exit=\$?; df -h /cache; cat /sys/fs/cgroup/memory.current /sys/fs/cgroup/memory.events"
kubectl -n notes-lab get pod mem

实际是：

command terminated with exit code 137
NAME   READY   STATUS      RESTARTS   AGE
mem    0/1     OOMKilled   0          23s

先到的是内存 limit：容器里还有 sh、sleep、dd 自己的内存，tmpfs 还没写满 64M，cgroup 就已经到顶，OOM killer 出手。exec 里的 dd 被杀，后面的命令都没来得及执行。节点上的文件显示第二个文件只写进去 21.6MiB：

docker exec <worker 的节点容器> ls -l /var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir/cache
-rw-r--r-- 1 root root 41943040 Oct 13 01:20 a
-rw-r--r-- 1 root root 22675456 Oct 13 01:20 b

重启救不回来

真正的麻烦在后面。10 多秒后：

NAME   READY   STATUS              RESTARTS     AGE
mem    0/1     RunContainerError   2 (2s ago)   40s
Last State:     Terminated
  Reason:       StartError
  Message:      failed to create containerd task: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: container init was OOM-killed (memory limit too low?): unknown
  Exit Code:    128

新容器连启动都做不到，container init was OOM-killed。原因在 Pod 级的 cgroup 里。先在节点上按 uid 找到 Pod 的 cgroup 目录（uid 里的 - 换成 _），再读它的内存统计：

docker exec <worker 的节点容器> sh -c 'find /sys/fs/cgroup -maxdepth 5 -type d -name "*<pod_uid>*"'
# /sys/fs/cgroup/kubelet.slice/kubelet-kubepods.slice/kubelet-kubepods-burstable.slice/kubelet-kubepods-burstable-pod<pod_uid>.slice
docker exec <worker 的节点容器> sh -c 'cd <上面的目录>; ls -d */; echo max=$(cat memory.max) current=$(cat memory.current); grep -E "^(anon|shmem) " memory.stat; cat memory.events'
max=67108864 current=65064960
anon 4096
shmem 64618496
low 0
high 0
max 102
oom 3
oom_kill 6
oom_group_kill 1

Pod 的 cgroup 上限也是 64Mi（单容器 Pod，等于容器 limit），而 tmpfs 里的 61.6MiB 文件还占着，挂在 Pod 这一级。文件不删，这部分内存就回收不了；新容器一启动，Pod cgroup 立刻到顶。两分钟后状态是：

NAME   READY   STATUS             RESTARTS      AGE
mem    0/1     CrashLoopBackOff   4 (24s ago)   2m14s
2026-10-13T01:22:14Z   4        Failed      Error: failed to create containerd task: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: container init was OOM-killed (memory limit too low?): unknown

kubectl exec 进不去（容器不存在），也就没法在 Pod 里删文件。这个 Pod 只能删掉重建，删 Pod 会释放 tmpfs。前面说「emptyDir 数据跨容器重启保留」，在这里反过来成了故障：内存卷把 limit 吃满后，重启只会无限循环。官方文档也提醒过，内存卷里的文件不会被系统自动删除，内存压力下这部分也回收不了。

排查时的线索：Reason: StartError、container init was OOM-killed，并且 Pod 挂了 medium: Memory 的卷。单看 CrashLoopBackOff 会以为是程序的问题。

给内存卷加 sizeLimit

同样 64Mi 的 limit，加上 sizeLimit: 16Mi：

volumes:
  - name: cache
    emptyDir:
      medium: Memory
      sizeLimit: 16Mi

（清单是把 mem 的名字换成 mem-limited、加上这一行，其余不变。）

kubectl -n notes-lab exec mem-limited -- sh -c "df -h /cache; grep /cache /proc/mounts"
Filesystem                Size      Used Available Use% Mounted on
tmpfs                    16.0M         0     16.0M   0% /cache
tmpfs /cache tmpfs rw,relatime,size=16384k,inode64,noswap 0 0

tmpfs 变成了 16M。再写 30Mi：

kubectl -n notes-lab exec mem-limited -- sh -c "dd if=/dev/zero of=/cache/a bs=1M count=30; echo dd-exit=\$?; ls -l /cache; cat /sys/fs/cgroup/memory.current"
kubectl -n notes-lab get pod mem-limited
dd: error writing '/cache/a': No space left on device
17+0 records in
16+0 records out
16777216 bytes (16.0MB) copied, 0.003884 seconds, 4.0GB/s
dd-exit=1
total 16384
-rw-r--r--    1 root     root      16777216 Oct 13 01:22 a
18857984
NAME          READY   STATUS    RESTARTS   AGE
mem-limited   1/1     Running   0          4s

这次是应用能处理的 ENOSPC，容器内存 18.0MiB，离 64Mi 还远，Pod 照常运行。tmpfs 写满在 16M 上（等于 sizeLimit，没有超过），6 分钟后这个 Pod 仍是 Running、RESTARTS 0，kubelet 没有驱逐它。原因是 kubelet 的 emptyDir 超限驱逐要求用量严格大于 sizeLimit，而 tmpfs 本身就把用量封顶在 sizeLimit，永远到不了「大于」。

所以用内存卷时，sizeLimit 要设，并且要明显小于内存 limit，给进程自己的内存留出空间。这样写满时得到的是写入错误，而不是 OOM 加启动循环。

磁盘 emptyDir 的 sizeLimit：先写进去，后驱逐

磁盘介质的 sizeLimit 不是文件系统配额。设 sizeLimit: 20Mi，容器内存 limit 给到 128Mi（原因见下一节）：

apiVersion: v1
kind: Pod
metadata:
  name: disk
spec:
  nodeSelector:
    kubernetes.io/hostname: worker
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]
      volumeMounts:
        - name: scratch
          mountPath: /scratch
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 128Mi}
  volumes:
    - name: scratch
      emptyDir:
        sizeLimit: 20Mi

写 40Mi，然后每秒查一次 Pod 状态：

date -u +%T.%N; kubectl -n notes-lab exec disk-a -- sh -c 'dd if=/dev/zero of=/scratch/big bs=1M count=40; echo dd-exit=$?; ls -l /scratch; date +%T'
for i in $(seq 1 90); do
  s=$(kubectl -n notes-lab get pod disk-a -o jsonpath='{.status.phase} {.status.reason}' 2>&1)
  echo "$(date -u +%T) $s"
  case "$s" in *Evicted*|*Failed*) break;; esac
  sleep 1
done

（上面的清单是模板：这一组 Pod 用 sed 把 name: disk 换成 disk-a 到 disk-d 分别提交，其余不变。最早那个叫 disk 的 Pod 内存 limit 是 32Mi，见下一节。）

41943040 bytes (40.0MB) copied, 0.041161 seconds, 971.8MB/s
dd-exit=0

-rw-r--r--    1 root     root      41943040 Oct 13 01:24 big
01:24:07

两倍于 sizeLimit 的数据全部写入成功，没有任何报错。20 秒后：

2026-10-13T01:24:27Z   Evicted     Usage of EmptyDir volume "scratch" exceeds the limit "20Mi". 
2026-10-13T01:24:27Z   Killing     Stopping container app
01:24:34 Running 
01:24:35 Failed Evicted

kubelet 发现用量超限，驱逐整个 Pod，phase 变成 Failed、reason Evicted，消息直接点出是哪个卷超了：

Usage of EmptyDir volume "scratch" exceeds the limit "20Mi".

同样的操作又做了三次，从写完到 Evicted 事件的间隔：

Pod写完Evicted间隔
disk-a01:24:06.901:24:27约 20 秒
disk-b01:24:49.801:25:26约 36 秒
disk-c01:25:42.701:26:22约 39 秒
disk-d01:27:15.901:28:52约 96 秒

最快 20 秒，最慢 96 秒。原因是 kubelet 不在写入路径上拦截，而是定期扫描每个 emptyDir 目录算用量，驱逐管理器再拿这个数和 sizeLimit 比。通过 API Server 的节点代理读 kubelet 的实际配置：

kubectl get --raw /api/v1/nodes/<worker>/proxy/configz | python3 -c 'import json,sys; c=json.load(sys.stdin)["kubeletconfig"]; [print(k, c.get(k)) for k in ["evictionHard","evictionPressureTransitionPeriod","volumeStatsAggPeriod","localStorageCapacityIsolation"]]'
evictionHard {'imagefs.available': '0%', 'nodefs.available': '0%', 'nodefs.inodesFree': '0%'}
evictionPressureTransitionPeriod 5m0s
volumeStatsAggPeriod 1m0s
localStorageCapacityIsolation True

kubelet 源码里，每个 Pod 的卷用量统计用 wait.JitterUntil(..., volumeStatsAggPeriod, 1.0, ...) 循环执行，抖动因子 1.0 意味着每次间隔在 1～2 分钟之间随机；驱逐管理器每 10 秒（evictionMonitoringPeriod）拿最新的统计值和 sizeLimit 比一次。还有一步：fsResourceAnalyzer 用 wait.Forever(..., calcPeriod) 每分钟（无抖动）扫一次 Pod 列表，给新 Pod 建统计器；统计器一建好先立刻算一次，之后才按 1～2 分钟带抖动的周期算。所以最坏情况大约是 2 分 10 秒，实测的 20～96 秒都落在这个范围内。表里也能看出这个每分钟一次的节拍：disk-a、b、c 的驱逐时间是 01:24:27、01:25:26、01:26:22，几乎每分钟同一秒，正是新 Pod 被发现、立刻统计、超限就驱逐；disk-d 慢到 96 秒，推测是它的第一次统计赶在写入之前完成（Pod 01:27:15 启动，写入在 01:27:15.9），超限只能等下一个带抖动的周期才被发现。evictionPressureTransitionPeriod 管的是节点压力状态的退出，和 emptyDir 超限驱逐无关。（kind 把 evictionHard 全设成 0%，节点压力驱逐基本关掉了，但 emptyDir 超限驱逐不受影响，localStorageCapacityIsolation 为 true 时就生效。）

这意味着两件事：

  • sizeLimit 挡不住突发写入。 在被发现之前，Pod 可以写远超限制的数据。这里只写了 40Mi，如果是一个失控的进程，一两分钟能写很多 GB，挤占整个节点的磁盘。
  • 被驱逐的 Pod 不会自己消失。 四个 Pod 都留在列表里，STATUS 显示的还是 ContainerStatusUnknown 而不是 Evicted：
NAME          READY   STATUS                   RESTARTS   AGE
disk-a        0/1     ContainerStatusUnknown   1          5m10s
disk-b        0/1     ContainerStatusUnknown   1          4m23s
disk-c        0/1     ContainerStatusUnknown   1          3m30s
disk-d        0/1     ContainerStatusUnknown   1          2m17s

kubectl get pod 的 STATUS 列优先显示容器的终止原因，其次才是 pod.status.reason，所以 Evicted 被盖住了，要看 .status.reason 或事件才知道是被驱逐的。RESTARTS 的 1 也不是容器真的又崩了一次：lastState 里写的是 The container could not be located when the pod was deleted. The container used to be Running，是 kubelet 找不到被杀掉的容器时补记的一条状态：

{"terminated":{"exitCode":137,"finishedAt":null,"message":"The container could not be located when the pod was deleted.  The container used to be Running","reason":"ContainerStatusUnknown","startedAt":null}}

裸 Pod 被驱逐后没有人重建；由 Deployment 管理时，控制器会建一个新 Pod，新 Pod 拿到的是空卷。如果应用每次启动都往卷里写同样多的东西，就会「驱逐、重建、再驱逐」。

意外：写磁盘卷也会 OOM

上一节的内存 limit 给了 128Mi，是因为第一次用 32Mi 的 limit 做这个实验时，dd 先被杀了：

command terminated with exit code 137
{"terminated":{"containerID":"containerd://7ca7de7c3c44323e668a1b37459f4f6050ab3d57cab830234a09ab9d8f43f076","exitCode":137,"finishedAt":"2026-10-13T01:23:04Z","reason":"OOMKilled","startedAt":"2026-10-13T01:23:04Z"}}

为了排除 sizeLimit 的干扰，换成不带 sizeLimit 的 emptyDir: {}、内存 limit 32Mi 的 Pod disk-oom，再写 40Mi：

kubectl -n notes-lab exec disk-oom -- sh -c 'rm -f /scratch/big; dd if=/dev/zero of=/scratch/big bs=1M count=40 2>&1|tail -1; echo dd-exit=$?; cat /sys/fs/cgroup/memory.events | grep oom_kill'

又是 exit code 137，容器 lastState 为 OOMKilled。写的是磁盘，不是 tmpfs。等容器重启后看，被杀前写进去了约 28.8MiB：

kubectl -n notes-lab exec disk-oom -- sh -c 'ls -l /scratch; cat /sys/fs/cgroup/memory.current; grep -E "^(anon|file|file_dirty|file_writeback) " /sys/fs/cgroup/memory.stat'
total 29536
-rw-r--r--    1 root     root      30244864 Oct 13 01:29 big
3612672
anon 147456
file 1560576
file_dirty 12288
file_writeback 0

文件留在了磁盘上。这里的 3.4MiB 是新容器自己的 cgroup，旧容器留下的页缓存不在新容器的 cgroup 里（推测转记到了 Pod 那一级，Pod 级 cgroup 这次没读），所以这个数说明不了什么。能说明问题的是：新容器能正常启动，说明这些页缓存可以回收（推测是写回磁盘后被回收）。这和 tmpfs 那次的死循环完全不同。

换成绕过页缓存的写法就没问题：

kubectl -n notes-lab exec disk-oom -- sh -c 'rm -f /scratch/big; dd if=/dev/zero of=/scratch/big bs=1M count=40 oflag=direct 2>&1|tail -1; echo dd-exit=$?'
kubectl -n notes-lab exec disk-oom -- sh -c 'rm -f /scratch/big; for i in $(seq 1 40); do dd if=/dev/zero of=/scratch/big bs=1M count=1 seek=$((i-1)) conv=notrunc,fsync 2>/dev/null; done; echo loop-exit=$?; ls -l /scratch/big'
41943040 bytes (40.0MB) copied, 1.954818 seconds, 20.5MB/s
dd-exit=0
loop-exit=0
-rw-r--r--    1 root     root      41943040 Oct 13 01:29 /scratch/big

oflag=direct 和每写 1MiB 就 fsync 一次的循环都写完了 40MiB，进程没被杀。作为对照，紧接着在同一个容器里再做一次普通的 40Mi 写入，又是 command terminated with exit code 137；5 秒后查 restartCount 仍是 1，但紧接着的 exec 报 container not found，容器多半也被杀了，只是状态还没更新，这一次的细节没有再追。

普通写文件产生的页缓存要算进容器的内存。推测是在 32Mi 这么小的 limit 下，脏页产生得比写回快，内核来不及回收，就在 cgroup 里触发了 OOM。这一点只在这个环境（内核 7.0、cgroup v2）上测了，换内核或存储结果可能不同。实际意义是：一个只设了几十 Mi 内存 limit、却要往卷里写大文件的容器，可能因为写文件被 OOMKilled，看 memory.stat 里 file、file_dirty 的大小能帮助确认。

排查时看哪里

  • 容器重启后文件还在、Pod 重建后文件没了：正常，这是 emptyDir 的寿命。看 Pod uid 有没有变就知道是哪一种。
  • StartError，container init was OOM-killed，Pod 挂了内存卷：tmpfs 把 limit 占满了，只能删 Pod；预防办法是给内存卷设一个明显小于 limit 的 sizeLimit。
  • 写内存卷报 No space left on device：碰到了 tmpfs 的大小，即 sizeLimit。tmpfs 大小等于 Pod 内存 limit 时，先到的是 OOM，见不到这个错误。
  • Pod Failed、Evicted，消息为 Usage of EmptyDir volume ... exceeds the limit：磁盘卷超了 sizeLimit。超限后最长可能要两分钟左右才会被驱逐，kubectl get pod 的 STATUS 列可能显示 ContainerStatusUnknown。
  • 写磁盘卷时 OOMKilled：检查内存 limit 是否小到装不下写文件产生的页缓存。

需要在节点上看卷内容时，到 /var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir/ 下找，只读查看即可，不要在那里改文件。

清理

kubectl -n notes-lab delete pod --all --grace-period=1
kubectl delete namespace notes-lab

被驱逐的 Pod 也要手动删。sizeLimit 之外，限制 Pod 整体本地存储用量还可以设容器的 resources.limits.ephemeral-storage，它会把可写层、日志和 emptyDir 加在一起算，本文没有测。Pod 级别的资源配置见探针与资源管理，OOMKilled 和 QoS 的关系见 QoS。
