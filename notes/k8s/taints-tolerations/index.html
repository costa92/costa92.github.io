污点与容忍

nodeSelector 和节点亲和是 Pod 挑节点；污点（taint）反过来，是节点排斥 Pod。Pod 上的容忍（toleration）只是解除这种排斥，不会把 Pod 吸引到带污点的节点上，最终落在哪里仍由调度器的其他规则决定。这一篇把三种污点效果、容忍的匹配规则、节点故障时的自动驱逐逐个跑一遍。

给节点加污点、停掉节点，都会影响节点上所有人的 Pod，所以这次没有用平时那个共享集群，而是单独起了一个用完即删的三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 是 kind 自带的 kindnet）。节点名简化成 control-plane、worker、worker2，Pod IP 用 <pod-ip> 代替，实验 namespace 实际叫 notes-lab-taints，和节点名一样简化成 notes-lab，事件消息里的也一并替换了。输出里的时间有两种：date +%T 打印的是本机时间（UTC+8），事件和 timeAdded 是 UTC，两者差 8 小时。

# kind.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
kind create cluster --name notes-lab-taints --image kindest/node:v1.31.0 --config kind.yaml
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done

kind 生成的节点全名是 notes-lab-taints-control-plane、notes-lab-taints-worker、notes-lab-taints-worker2，下文的命令和输出都用简化名，照着做时要换回全名。

NAME            TAINTS
control-plane   [map[effect:NoSchedule key:node-role.kubernetes.io/control-plane]]
worker          <none>
worker2         <none>

control-plane 上的 NoSchedule 污点是 kubeadm 装集群时加的，普通 Pod 因此不会调度到控制平面。

每个 Pod 天生带着两条容忍

先建一个什么都没写的 Pod：

apiVersion: v1
kind: Pod
metadata:
  name: plain
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
kubectl -n notes-lab get pod plain \
  -o jsonpath='{range .spec.tolerations[*]}{.key}{"\t"}{.operator}{"\t"}{.effect}{"\t"}{.tolerationSeconds}{"\n"}{end}'
node.kubernetes.io/not-ready	Exists	NoExecute	300
node.kubernetes.io/unreachable	Exists	NoExecute	300

YAML 里一条容忍都没有，存进 API Server 的对象却多了两条。这是 DefaultTolerationSeconds 准入插件补的：节点 NotReady 或失联时，Pod 还能在上面待 300 秒，过后才会被驱逐。后面「节点挂了」一节会实测这 300 秒。

如果自己写了其中一条，插件只补缺的那条，不覆盖你写的。给另一个 Pod 写上 unreachable 容忍 60 秒：

tolerations:
  - key: node.kubernetes.io/unreachable
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 60
node.kubernetes.io/unreachable	Exists	NoExecute	60
node.kubernetes.io/not-ready	Exists	NoExecute	300

NoSchedule：挡住新 Pod，不动老 Pod

先跑一个 4 副本的 Deployment web（busybox sleep infinity），两个 worker 各分到两个。然后给 worker 加污点：

kubectl taint node worker dedicated=lab:NoSchedule

再用 nodeSelector: kubernetes.io/hostname: worker 把一个没有容忍的 Pod 钉到 worker，它就只能 Pending：

FailedScheduling   0/3 nodes are available: 1 node(s) didn't match Pod's node affinity/selector, 1 node(s) had untolerated taint {dedicated: lab}, 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

三个节点各有一个原因：worker2 不匹配 nodeSelector，worker 有未容忍的 {dedicated: lab}，control-plane 有未容忍的控制平面污点。消息里的污点只写了 key: value，没写 effect。每个节点只记第一个失败原因，这一点在调度那篇里已经拆过。

容忍怎么才算匹配

worker 上还是 dedicated=lab:NoSchedule。准备六个都钉在节点上的 Pod，只有容忍写法不同：

Pod容忍结果
equal-wrong-value{key: dedicated, operator: Equal, value: prod, effect: NoSchedule}Pending
equal-right{key: dedicated, operator: Equal, value: lab, effect: NoSchedule}Running
exists-key{key: dedicated, operator: Exists}Running
wrong-effect{key: dedicated, operator: Equal, value: lab, effect: NoExecute}Pending
equal-no-effect{key: dedicated, operator: Equal, value: lab}Running
exists-all-cp（钉到 control-plane）- operator: ExistsRunning
NAME                READY   STATUS    RESTARTS   AGE   IP         NODE            NOMINATED NODE   READINESS GATES
equal-wrong-value   0/1     Pending   0          22s   <none>     <none>          <none>           <none>
equal-right         1/1     Running   0          21s   <pod-ip>   worker          <none>           <none>
exists-key          1/1     Running   0          20s   <pod-ip>   worker          <none>           <none>
wrong-effect        0/1     Pending   0          18s   <none>     <none>          <none>           <none>
equal-no-effect     1/1     Running   0          15s   <pod-ip>   worker          <none>           <none>
exists-all-cp       1/1     Running   0          11s   <pod-ip>   control-plane   <none>           <none>

规则归纳起来是：key 要相同；Equal 还要求 value 相同，Exists 不看 value；effect 留空表示匹配这个 key 的所有 effect，写了就必须相同。wrong-effect 的 key 和 value 都对，只是 effect 写成了 NoExecute，照样不算数。

排查时要留意：equal-wrong-value 和 wrong-effect 的 FailedScheduling 消息和上一节那个完全没写容忍的 Pod 一字不差，都是 had untolerated taint {dedicated: lab}。调度器只告诉你哪个污点没被容忍，不会说你的容忍差在哪儿，只能自己拿 kubectl get node -o jsonpath='{.spec.taints}' 和 Pod 的 .spec.tolerations 逐字段对。

Exists 带上 value 会直接被 API Server 拒绝，连对象都创建不出来：

The Pod "exists-with-value" is invalid: spec.tolerations[0].operator: Invalid value: core.Toleration{Key:"dedicated", Operator:"Exists", Value:"lab", Effect:"", TolerationSeconds:(*int64)(nil)}: value must be empty when `operator` is 'Exists'

空 key 加 Exists：什么都容忍，也包括节点故障

exists-all-cp 只写了一行 operator: Exists，连控制平面污点都容忍了。再看它的容忍列表：

Exists

只有自己写的那一条，准入插件没有再补那两条 300 秒的容忍：插件发现已有容忍能覆盖 not-ready / unreachable，就不再添加。代价是这种 Pod 在节点失联后永远不会被驱逐，下面停节点的实验里能看到它一直留在原地。除了确实需要每个节点都跑一份的系统组件，业务 Pod 不应该这么写。

容忍不等于「去那里」

用一个 6 副本的 Deployment tolerant，模板里只加 dedicated=lab:NoSchedule 的容忍：

NAME                       NODE
tolerant-dc555894b-btmhr   worker
tolerant-dc555894b-g29s8   worker2
tolerant-dc555894b-gbbvb   worker
tolerant-dc555894b-q8s2c   worker2
tolerant-dc555894b-x5xlk   worker
tolerant-dc555894b-xv4nf   worker2

一边三个。容忍让 worker 重新成为候选，但 worker2 本来就是候选，调度器照常打散。想做「专用节点」，要两样同时上：污点把别人挡在外面，节点亲和把自己拉进来。给 worker 打上标签 notes-lab.io/dedicated=lab，再往模板里加一条 required 节点亲和：

kubectl label node worker notes-lab.io/dedicated=lab
kubectl -n notes-lab patch deploy tolerant --type=merge -p '{"spec":{"template":{"spec":{"affinity":{"nodeAffinity":{"requiredDuringSchedulingIgnoredDuringExecution":{"nodeSelectorTerms":[{"matchExpressions":[{"key":"notes-lab.io/dedicated","operator":"In","values":["lab"]}]}]}}}}}}}'

PreferNoSchedule：软排斥，这次一个都没去

把 worker 的污点换成 dedicated=lab:PreferNoSchedule，把 web 先缩到 0 再扩到 10 个副本，统计落点：

10 worker2

官方文档对 PreferNoSchedule 的说法是「尽量避开，但不保证」。在这个两 worker 都很空的集群上，「尽量」的效果非常强，10 个副本一个都没去 worker，压过了默认的打散倾向。推测是污点打分在这里占了上风：v1.31 default_plugins.go 里打分插件的权重是 TaintToleration 3、PodTopologySpread 2、NodeResourcesFit 1，另外，扩容前 12:29:31 已有一个钉在 worker 上、没写 requests 的 pin-worker，NodeResourcesFit 打分会给没写 requests 的 Pod 计一个非零默认值，也可能让 worker 稍微吃亏。这次没有逐项看调度器的打分。节点资源紧张时 Pod 会不会被放到有这种污点的节点上，这次没有实测。

它确实只是软约束：用 nodeSelector 把没有容忍的 Pod 钉到 worker，直接就跑起来了：

NAME         READY   STATUS    RESTARTS   AGE   IP         NODE     NOMINATED NODE   READINESS GATES
pin-worker   1/1     Running   0          3s    <pod-ip>   worker   <none>           <none>

同样的 Pod 遇到 NoSchedule 时只能 Pending。

NoExecute：赶走已经在跑的 Pod

前两种效果只管调度，NoExecute 会驱逐节点上已经在跑、且不容忍它的 Pod。先撤掉上一节的软污点（kubectl taint node worker dedicated=lab:PreferNoSchedule-，12:30:15），再用 nodeSelector: kubernetes.io/hostname: worker 在 worker 上钉四个裸 Pod：

Pod容忍 dedicated=lab:NoExecute
ne-none无
ne-forever有，不写 tolerationSeconds
ne-30s有，tolerationSeconds: 30
ne-90s有，tolerationSeconds: 90

后台开一个带本机时间的 watch：

kubectl -n notes-lab get pod -l '!app' -w --output-watch-events \
  -o 'custom-columns=EVENT:.type,NAME:.object.metadata.name,PHASE:.object.status.phase,DEL:.object.metadata.deletionTimestamp' \
  | while IFS= read -r l; do echo "$(date +%T) $l"; done &

然后在 12:30:51 加污点，50 秒后（12:31:41）撤掉：

kubectl taint node worker dedicated=lab:NoExecute
# 50 秒后
kubectl taint node worker dedicated=lab:NoExecute-

watch 的记录（DEL 是 deletionTimestamp）：

12:31:00 MODIFIED   ne-none      Failed    2026-10-13T04:30:53Z

TIME                   POD      REASON                 MESSAGE
2026-10-13T04:30:51Z   ne-none  TaintManagerEviction   Marking for deletion Pod notes-lab/ne-none

  • ne-none 在加污点的同一秒被标记删除。
  • ne-30s 在 04:31:21 被标记，正好是加污点后 30 秒。准确地说，倒计时从控制器处理到这个污点时开始（v1.31 源码里取的是处理时的当前时间，不是污点的 timeAdded），两者通常只差一两秒。

DisruptionTarget True DeletionByTaintManager Taint manager: deleting due to NoExecute taint 2026-10-13T04:35:23Z

cordon 对应的污点与 DaemonSet

kubectl cordon 只是把节点的 spec.unschedulable 设为 true，随后节点上会自动多出一个对应的污点（由控制平面根据这个字段加上）：

control-plane   <none>    [map[effect:NoSchedule key:node-role.kubernetes.io/control-plane]]
worker          true      [map[effect:NoSchedule key:node.kubernetes.io/unschedulable timeAdded:2026-10-13T04:32:48Z]]
worker2         <none>    <none>

看完后 kubectl uncordon worker、删掉这个 DaemonSet。web 的 4 个副本因为是在 cordon 期间扩出来的，全都留在 worker2 上，正好给下一节用。

节点挂了：60 秒和 300 秒

现在验证开头那两条 300 秒的容忍。worker2 上有：

  • web 的 4 个副本（上一节 cordon 期间扩出来的），用的是自动补上的 300 秒容忍；
  • unreach-60s，自己写了 unreachable 容忍 60 秒；
  • tolerate-all，只写了 operator: Exists。

04:39:23352 sweb 的 4 个 Pod 被标记删除（NoExecute 后 300 s）
04:39:27356 sDeployment 在 worker 上补建 4 个 Pod

几点值得记住：

  • 业务真正开始恢复是在停机后约 6 分钟，而不是 5 分钟。前面还有 45 秒是节点控制器在等心跳：v1.31 的 --node-monitor-grace-period 默认 40 秒（v1.32 起改为 50 秒），这个集群没改，再加上检查周期，实测 45 秒才判定失联；之后又过了 7 秒才加 NoExecute。这 7 秒推测是因为节点控制器在这一轮检查里拿的还是更新前的 Ready 状态，NoExecute 污点要等下一轮（默认每 5 秒一次）才加上，没有用日志核实。
  • 被标记删除的 Pod 一直卡在 Terminating。节点上的 kubelet 已经不在了，没人能确认容器停没停，所以 API 里这些 Pod 一直留着，直到节点回来。Deployment 不等它们消失，看到 deletionTimestamp 就补新副本；如果是 StatefulSet，同名 Pod 要等旧的真正删掉才能重建，会一直卡住（这次没有测 StatefulSet）。如果确认节点已经关机、短时间回不来，可以手动给它加 node.kubernetes.io/out-of-service 污点（非优雅节点关机处理，v1.28 GA），让控制平面强制清理这些 Pod，这一步这次也没有实测。
  • 想让关键服务更快切走，可以像 unreach-60s 那样把 unreachable / not-ready 的 tolerationSeconds 调小；调太小的话，网络抖一下也会触发重建。
  • tolerate-all 自始至终没被标记删除。

小结

effect对新 Pod对已在跑的 Pod实测
NoSchedule无匹配容忍则不能调度不驱逐老 Pod 原地不动，钉过去的新 Pod Pending
PreferNoSchedule尽量避开不驱逐空闲集群里 10 个副本一个都没去；nodeSelector 钉过去照样能跑
NoExecute无匹配容忍则不能调度无容忍立即驱逐，有 tolerationSeconds 则倒数后驱逐倒数精确到秒；倒数中撤掉污点会取消驱逐

清理时先删 Pod，再把污点和标签去掉（键名后加 -）：

kubectl delete namespace notes-lab
kubectl taint node worker dedicated-   # 去掉这个 key 的所有污点，不管 effect
kubectl label node worker notes-lab.io/dedicated-

这次用的是一次性集群，最后直接 kind delete cluster 删掉了。
