为什么两个工具修改同一对象会冲突

批量清单管理用的是普通 kubectl apply，也就是客户端应用：kubectl 把上次应用的清单存进 last-applied-configuration 注解，下次在本地做三方合并。Server-Side Apply（SSA）把这件事挪到了 API Server：每个字段归哪个「字段管理者」（field manager）管，记录在 metadata.managedFields 里。一个管理者想把另一个管理者持有的字段改成不同的值，用 Apply 提交的请求会被拒绝，这样意外覆盖会变成一个明确的错误。字段所有权是协作机制，不代替 RBAC。

Helm 4 默认用 SSA，手动 kubectl scale 之后 helm upgrade、helm rollback 报冲突的完整过程，在 Helm 升级与回滚的「手动改过的字段」一节里已经实测过，这里不再重复，只看 SSA 本身的规则。

下文输出来自一个三节点 kind 集群（Kubernetes v1.31.0），kubectl 客户端是 v1.30.0，实验放在单独的 notes-lab namespace 里。为了只看所有权，Pod 都是 busybox:1.36 跑 sleep，请求 10m CPU、16Mi 内存。

下面反复用到一条命令，列出对象上每个管理者的名字、操作类型、子资源和时间：

kubectl -n notes-lab get deploy ssa -o jsonpath='{range .metadata.managedFields[*]}{.manager} {.operation} {.subresource} {.time}{"\n"}{end}'

后文对 csa、ho 等其他 Deployment 和 ConfigMap 用的是同一条命令，换掉资源类型和名字即可。

同一份清单，两种 apply 留下的记录

准备一个 Deployment 清单，名字分别替换成 csa 和 ssa：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: ssa
  labels:
    app: ssa
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ssa
  template:
    metadata:
      labels:
        app: ssa
    spec:
      containers:
        - name: app
          image: busybox:1.36
          command: ["sh", "-c"]
          args: ["sleep 3600"]
          env:
            - name: MODE
              value: blue
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              memory: 32Mi
kubectl -n notes-lab apply -f csa.yaml
kubectl -n notes-lab apply --server-side -f ssa.yaml
deployment.apps/csa created
deployment.apps/ssa serverside-applied

两边的管理者（--- 上面是 csa，下面是 ssa）：

kubectl-client-side-apply Update  2026-10-13T03:22:20Z
kube-controller-manager Update status 2026-10-13T03:22:21Z
---
kubectl Apply  2026-10-13T03:22:20Z
kube-controller-manager Update status 2026-10-13T03:22:21Z

客户端 apply 在服务端看来只是一次普通的写入，操作类型是 Update，管理者名叫 kubectl-client-side-apply；--server-side 的操作类型是 Apply，默认管理者名就是 kubectl。kube-controller-manager 那一条是 Deployment 控制器写 status 子资源留下的。

csa 带着 last-applied-configuration 注解，ssa 只有控制器加的 revision 注解：

{"deployment.kubernetes.io/revision":"1"}

更值得看的是两个管理者各自拥有哪些字段。用 jq 取出第一条记录（各自的 apply 管理者）在 spec 和容器下的键：

kubectl -n notes-lab get deploy csa -o json --show-managed-fields | jq -c '.metadata.managedFields[0].fieldsV1 | {metadata: ."f:metadata", spec_keys: (."f:spec"|keys), container_keys: (."f:spec"."f:template"."f:spec"."f:containers"."k:{\"name\":\"app\"}"|keys)}'
kubectl -n notes-lab get deploy ssa -o json --show-managed-fields | jq -c '.metadata.managedFields[0].fieldsV1 | {spec_keys: (."f:spec"|keys), container_keys: (."f:spec"."f:template"."f:spec"."f:containers"."k:{\"name\":\"app\"}"|keys)}'
{"metadata":{"f:annotations":{".":{},"f:kubectl.kubernetes.io/last-applied-configuration":{}},"f:labels":{".":{},"f:app":{}}},"spec_keys":["f:progressDeadlineSeconds","f:replicas","f:revisionHistoryLimit","f:selector","f:strategy","f:template"],"container_keys":[".","f:args","f:command","f:env","f:image","f:imagePullPolicy","f:name","f:resources","f:terminationMessagePath","f:terminationMessagePolicy"]}
{"spec_keys":["f:replicas","f:selector","f:template"],"container_keys":[".","f:args","f:command","f:env","f:image","f:name","f:resources"]}

第一行是 kubectl-client-side-apply：除了清单里写的字段，它还拥有 progressDeadlineSeconds、revisionHistoryLimit、strategy、imagePullPolicy、terminationMessagePath 这些 API Server 补上的默认值。Update 是按「这次请求让哪些字段出现或变化」记账的，创建时默认值也算在它头上。第二行是 SSA 的 kubectl，只拥有清单里声明过的字段，这正是 SSA 的意图：你声明什么，就只管什么。

完整的 fieldsV1 长这样（节选 kubectl 一条）：

f:spec:
  f:replicas: {}
  f:selector: {}
  f:template:
    f:metadata:
      f:labels:
        f:app: {}
    f:spec:
      f:containers:
        k:{"name":"app"}:
          .: {}
          f:args: {}
          f:command: {}
          f:env:
            k:{"name":"MODE"}:
              .: {}
              f:name: {}
              f:value: {}

k:{"name":"app"} 表示 containers 是按 name 做键的列表，每个元素单独记账。{} 只表示「这一项作为叶子被拥有」，单看它分不出是标量（如 f:replicas）还是被当作整体的结构。args、selector 不再往下拆，是因为 OpenAPI 里把 args 标成了 atomic 列表、把 LabelSelector 标成了 atomic 结构：

{"mapType":"atomic"}

这是 LabelSelector 的 x-kubernetes-map-type，args 的类型在后面「列表」一节查。

命令式命令各自叫什么

对 ssa 依次做几种常见的手动修改：

KUBE_EDITOR="sed -i s/value:\ blue/value:\ green/" kubectl -n notes-lab edit deploy ssa
kubectl -n notes-lab scale deploy ssa --replicas=3
kubectl -n notes-lab patch deploy ssa -p '{"spec":{"template":{"spec":{"containers":[{"name":"app","resources":{"limits":{"memory":"48Mi"}}}]}}}}'
kubectl -n notes-lab label deploy ssa notes-lab.io/owner=ops
kubectl -n notes-lab set image deploy/ssa app=busybox:1.37
kubectl -n notes-lab set image deploy/ssa app=busybox:1.36
kubectl Apply  2026-10-13T03:22:20Z
kubectl Update scale 
kubectl-edit Update  2026-10-13T03:22:42Z
kubectl-label Update  2026-10-13T03:22:42Z
kubectl-patch Update  2026-10-13T03:22:52Z
kube-controller-manager Update status 2026-10-13T03:22:53Z
kubectl-set Update  2026-10-13T03:22:53Z

除了 scale，每个子命令都有自己的管理者名（kubectl-edit、kubectl-patch、kubectl-label、kubectl-set）。这些是 kubectl 给各子命令的 --field-manager 参数设的默认值，请求里显式带上了。scale 没有这个参数，请求里不带管理者名，API Server 就从 User-Agent 的前缀推断出 kubectl，恰好和 SSA 的默认名字撞上。不过它的操作类型和子资源不同，是另一条记录。这条记录的 time 是空的，原因没有深究。

把每条记录拥有的叶子字段列出来（paths(type=="object" and length==0) 取出所有 {} 叶子，下面的输出省略了 kubectl Apply 和控制器两条）：

for i in 0 1 2 3 4 5 6; do
  kubectl -n notes-lab get deploy ssa -o json --show-managed-fields | jq -r --argjson i $i '.metadata.managedFields[$i] // empty | "\(.manager) \(.operation) \(.subresource // ""): " + ([.fieldsV1 | paths(type=="object" and length==0)] | map(map(select(. != "."))|join("/")) | join("  "))'
done
kubectl Update scale: f:spec/f:replicas
kubectl-edit Update : f:spec/f:template/f:spec/f:containers/k:{"name":"app"}/f:env/k:{"name":"MODE"}/f:value
kubectl-label Update : f:metadata/f:labels/f:notes-lab.io/owner
kubectl-patch Update : f:spec/f:template/f:spec/f:containers/k:{"name":"app"}/f:resources/f:limits/f:memory
kubectl-set Update : f:spec/f:template/f:spec/f:containers/k:{"name":"app"}/f:image

谁改了值，所有权就转给谁，原来的 kubectl 那条里对应的字段消失了。注意 image：第二次 set image 把值改回了清单里的 1.36，但所有权没有还给 kubectl，仍然在 kubectl-set 手里。值回去了，账没回去。

顺带一个和 SSA 无关、但这次真撞上的坑。第一次写 patch 时用的是 --type=merge：

The Deployment "ssa" is invalid: spec.template.spec.containers[0].image: Required value

JSON Merge Patch 不认识列表的键，containers 整个被替换成了只有 name 和 resources 的那一项，于是缺了 image。去掉 --type=merge、用默认的 strategic merge patch 才按 name 合并。

冲突：先用 dry-run 看，再决定要不要 force

现在原样再 apply 一次 ssa.yaml。先加 --dry-run=server，让 API Server 完整走一遍合并和冲突检查，但不落盘：

kubectl -n notes-lab apply --server-side -f ssa.yaml --dry-run=server
error: Apply failed with 3 conflicts: conflicts with "kubectl" with subresource "scale" using apps/v1:
- .spec.replicas
conflicts with "kubectl-edit" using apps/v1:
- .spec.template.spec.containers[name="app"].env[name="MODE"].value
conflicts with "kubectl-patch" using apps/v1:
- .spec.template.spec.containers[name="app"].resources.limits.memory
Please review the fields above--they currently have other managers. Here
are the ways you can resolve this warning:
* If you intend to manage all of these fields, please re-run the apply
  command with the `--force-conflicts` flag.
* If you do not intend to manage all of the fields, please edit your
  manifest to remove references to the fields that should keep their
  current managers.
* You may co-own fields by updating your manifest to match the existing
  value; in this case, you'll become the manager if the other manager(s)
  stop managing the field (remove it from their configuration).
See https://kubernetes.io/docs/reference/using-api/server-side-apply/#conflicts

几个细节：

  • 冲突报告按管理者分组，列出了具体字段路径，列表元素用 [name="app"] 这种键来定位。
  • 管理者名同样叫 kubectl，scale 那条照样和 Apply 冲突。区分管理者看的不只是名字。
  • image 没有出现在冲突里：kubectl-set 持有的值和清单里一样都是 1.36，值相同就不算冲突，这次 apply 成功的话两者会共同拥有它。
  • label 也不冲突，清单里根本没写 notes-lab.io/owner。

去掉 --dry-run 结果一样，退出码 1，对象上 replicas=3 MODE=green limit=48Mi 原封不动。--dry-run=server 加上 --force-conflicts 还能预演强制的结果，-o jsonpath 打印返回的对象：

2 kubectl/Apply/ kubectl-label/Update/ kubectl-set/Update/ kube-controller-manager/Update/status

预演结果里副本数回到 2，scale、kubectl-edit、kubectl-patch 三条记录都没了；再查真实对象，副本数还是 3，七条记录都在。确认无误后真正执行：

deployment.apps/ssa serverside-applied
kubectl Apply  2026-10-13T03:23:12Z
kubectl-label Update  2026-10-13T03:22:42Z
kubectl-set Update  2026-10-13T03:22:53Z
kube-controller-manager Update status 2026-10-13T03:23:12Z
replicas=2 MODE=blue limit=32Mi image=busybox:1.36 labels={"app":"ssa","notes-lab.io/owner":"ops"}

被抢走字段的管理者如果什么都不剩，整条记录会被删掉；kubectl-set 还和 kubectl 共有 image，kubectl-label 的标签清单没提，所以这两条留着，那个标签也留着。--force-conflicts 只抢清单里写了的字段。

共享所有权，以及删掉字段什么时候真的会删

用一个 ConfigMap 和两个管理者 team-a、team-b 把规则逐条走一遍。team-a 先应用三个键：

apiVersion: v1
kind: ConfigMap
metadata:
  name: shared
data:
  color: blue
  size: s
  mode: x
configmap/shared serverside-applied
team-a Apply: f:color f:mode f:size
data={"color":"blue","mode":"x","size":"s"}

每一步之后都用下面这个函数打印两类信息：每个管理者一行「管理者 操作: 拥有的 data 键」，最后一行是当前的 data：

cmf() {
  kubectl -n notes-lab get cm shared -o json --show-managed-fields | jq -r '.metadata.managedFields[] | "\(.manager) \(.operation): " + ((.fieldsV1."f:data" // {}) | keys | join(" "))'
  kubectl -n notes-lab get cm shared -o jsonpath='data={.data}{"\n"}'
}

team-b 想把 color 改成 red，冲突：

error: Apply failed with 1 conflict: conflict with "team-a": .data.color

team-b 改成提交相同的 color: blue，成功，color 变成两者共有：

configmap/shared serverside-applied
team-b Apply: f:color
team-a Apply: f:color f:mode f:size
data={"color":"blue","mode":"x","size":"s"}

共有之后，谁都不能单方面改它。team-a 想把 color 改成 green：

error: Apply failed with 1 conflict: conflict with "team-b": .data.color

接着 team-a 从自己的清单里删掉 color（只剩 size、mode）再应用。值没有被删，因为 team-b 还拥有它，team-a 只是放弃了所有权：

configmap/shared serverside-applied
team-b Apply: f:color
team-a Apply: f:mode f:size
data={"color":"blue","mode":"x","size":"s"}

team-b 再应用一份没有 data 的清单，此时它是 color 唯一的所有者，color 被删掉；team-b 不再拥有任何字段，它的记录也一起消失：

configmap/shared serverside-applied
team-a Apply: f:mode f:size
data={"mode":"x","size":"s"}

team-a 删掉 size，同理直接删除：

team-a Apply: f:mode
data={"mode":"x"}

所以「从清单里删掉一个字段」有两种结果：只有你拥有它时字段被删除（有默认值的字段会回到默认值，下面 replicas 就是这种情况）；还有别人拥有时，只是你的名字从记录里去掉。这也是两个管理者之间转移所有权的标准做法：先提交相同的值变成共有，再由原所有者从清单里删掉它。

Update 不做字段冲突检查

字段冲突只发生在 Apply 上（和 resourceVersion 不匹配导致的那种 409 冲突是两回事）。kubectl patch、edit、scale 这类 Update 操作会直接覆盖，并静默接管所有权。继续用上面的 ConfigMap，先 patch 一个相同的值：

configmap/shared patched (no change)
team-a Apply: f:mode
data={"mode":"x"}

值没变，所有权也不动。改成不同的值：

configmap/shared patched
kubectl-patch Update: f:mode
data={"mode":"y"}

team-a 一声提示都没收到就丢了 mode。这时 team-a 从清单里删掉 mode 再应用，mode: y 依然留在对象上，因为它已经不归 team-a 管了：

configmap/shared serverside-applied
kubectl-patch Update: f:mode
data={"mode":"y"}

这是排查「清单里明明删了，线上怎么还在」时该先查的情况：看 managedFields 里这个字段现在归谁。反过来，如果清单里留着这个字段，下次 apply 就会撞上和 kubectl-patch 的冲突，这时候冲突反而是好事，说明有人绕过流水线改过线上。

两条流水线共用一个管理者名

对 Apply 来说，管理者名决定了这是谁的意图：同名的两次 Apply 会被当作同一份配置的新旧版本。两条流水线都不传 --field-manager，就都叫 kubectl。第一条应用：

data:
  color: blue
  owner: pipeline-1

第二条应用只有 color: red 的清单：

configmap/same-mgr serverside-applied
configmap/same-mgr serverside-applied
{"color":"red"}
kubectl Apply  2026-10-13T03:23:50Z

没有冲突，color 被改成 red；更糟的是 owner 被删了。对 SSA 来说这是同一个管理者更新了自己的配置，新配置里没有 owner，它又是唯一所有者，于是删除。CI、Operator、手工操作要用不同的 --field-manager，冲突检测才有意义。

列表：按键合并还是整体替换

列表怎么合并由 OpenAPI 里的 x-kubernetes-list-type 决定。直接从集群的 OpenAPI v3 里查容器和 PodSpec 的列表字段：

kubectl get --raw /openapi/v3/apis/apps/v1 > openapi-apps.json
jq -c '.components.schemas["io.k8s.api.core.v1.Container"].properties | to_entries[] | select(.value.type=="array") | {field: .key, listType: .value["x-kubernetes-list-type"], keys: .value["x-kubernetes-list-map-keys"]}' openapi-apps.json
{"field":"args","listType":"atomic","keys":null}
{"field":"command","listType":"atomic","keys":null}
{"field":"env","listType":"map","keys":["name"]}
{"field":"envFrom","listType":"atomic","keys":null}
{"field":"ports","listType":"map","keys":["containerPort","protocol"]}
{"field":"resizePolicy","listType":"atomic","keys":null}
{"field":"volumeDevices","listType":"map","keys":["devicePath"]}
{"field":"volumeMounts","listType":"map","keys":["mountPath"]}

PodSpec 里同样查了一遍，containers、initContainers、volumes 是按 name 的 map，topologySpreadConstraints 按 topologyKey+whenUnsatisfiable，而 tolerations 和 readinessGates 是 atomic：

{"field":"containers","listType":"map","keys":["name"]}
{"field":"tolerations","listType":"atomic","keys":null}

map 类型的列表里，不同管理者可以各管各的元素；atomic 列表整个归一个管理者，任何改动都是替换整个列表。模拟一个「注入 sidecar」的工具 injector，和主清单的管理者 base 同时管一个 Deployment。base 的清单就是前面那份（名字换成 lst、replicas: 1），在 Pod 模板的 spec 末尾加一条容忍：

tolerations:
  - key: notes-lab.io/a
    operator: Exists
    effect: NoSchedule
kubectl -n notes-lab apply --server-side --field-manager=base -f lst-base.yaml

injector 只提交它关心的部分（lst-side.yaml）：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: lst
spec:
  template:
    spec:
      containers:
        - name: app
          env:
            - name: EXTRA
              value: "1"
        - name: sidecar
          image: busybox:1.36
          command: ["sh", "-c", "sleep 3600"]
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
kubectl -n notes-lab apply --server-side --field-manager=injector -f lst-side.yaml

这份清单连 selector 都没有，单独看不是合法的 Deployment，但 SSA 只要求合并后的结果合法，应用成功：

deployment.apps/lst serverside-applied
app: env=[{"name":"MODE","value":"blue"},{"name":"EXTRA","value":"1"}] args=["sleep 3600"]
sidecar: env= args=

containers 按 name 合并多了一个 sidecar，app 容器的 env 也按 name 合并，MODE 和 EXTRA 并存。injector 的记录里只有它自己提交的那些字段。

如果 injector 还想给 app 改 args（在 lst-side.yaml 的 app 容器里加一行 args: ["sleep 7200"]）：

error: Apply failed with 1 conflict: conflict with "base": .spec.template.spec.containers[name="app"].args

冲突报在整个 .args 上，而不是某个元素。容忍度更值得注意。injector 只想「再加一条」容忍，在 lst-side.yaml 末尾追加：

tolerations:
  - key: notes-lab.io/b
    operator: Exists
    effect: NoSchedule
error: Apply failed with 1 conflict: conflict with "base": .spec.template.spec.tolerations

用 --force-conflicts --dry-run=server 预演一下强制的后果：

kubectl -n notes-lab apply --server-side --field-manager=injector --force-conflicts --dry-run=server -f lst-side-tol.yaml -o jsonpath='{.spec.template.spec.tolerations}{"\n"}'
[{"effect":"NoSchedule","key":"notes-lab.io/b","operator":"Exists"}]

base 的 notes-lab.io/a 不见了。atomic 列表没有「追加」这回事，强制等于整体替换。对象本身没动，仍然是 notes-lab.io/a。多个工具都要往 tolerations、args、command 里写东西时，没法靠 SSA 自动合并，只能约定由一方管理整个列表。

从客户端 apply 迁移到服务端 apply

回到最开始用客户端 apply 创建的 csa。不带 --field-manager，直接用 --server-side 应用一份把 MODE 改成 green 的清单：

deployment.apps/csa serverside-applied
kubectl-last-applied Apply  
kubectl Apply  2026-10-13T03:24:30Z
kube-controller-manager Update status 2026-10-13T03:22:36Z

MODE 是 kubectl-client-side-apply 的字段，值也变了，却没有冲突。这一条 kubectl apply --server-side 背后其实分了几步，一部分在 API Server，一部分在 kubectl（以下按 kubectl v1.30 和 apiserver 的源码梳理，没有逐个请求抓包）：

  1. kubectl 发出 SSA 请求，管理者 kubectl。API Server 的字段管理器里有一段专门处理迁移的逻辑，只在管理者名正好是 kubectl 时生效：和 last-applied-configuration 注解里记录的字段发生的冲突会被放行。所以 MODE 从 blue 改成 green 不报错。同样只对 kubectl 这个名字，API Server 会在每次 SSA 后把注解内容同步成这次应用的配置。
  2. 请求成功后，kubectl 再用管理者 kubectl-last-applied 单独 apply 一次只含这个注解的对象，让注解有一个 Apply 类型的所有者，后面不会被当成没人管的字段删掉。
  3. kubectl 再用一个 JSON Patch 改写 managedFields，把 kubectl-client-side-apply 拥有的全部字段（包括那些默认值字段）并入 kubectl 的记录，删掉 kubectl-client-side-apply 那条。
  4. 最后 kubectl 把原来的 SSA 请求再发一次。这时 kubectl 名下多出来的默认值字段不在清单里，于是从它的记录里去掉；没人拥有的默认值字段被删除后又由 API Server 重新填上默认值。

结果就是 kubectl-client-side-apply 那条消失，多了一条 kubectl-last-applied。看看两条各管什么：

{"manager":"kubectl-last-applied","metadata":{"f:annotations":{"f:kubectl.kubernetes.io/last-applied-configuration":{}}},"spec_keys":[]}
{"manager":"kubectl","metadata":{"f:labels":{"f:app":{}}},"spec_keys":["f:replicas","f:selector","f:template"]}

kubectl-last-applied 只持有 last-applied-configuration 注解，注解内容已经是新清单（节选："env":[{"name":"MODE","value":"green"}]）。kubectl 最终只拥有清单里写过的字段，原来记在客户端 apply 名下的 strategy、revisionHistoryLimit 等默认值字段不再有人拥有。

迁移之后，从清单里删掉整个 env 再 --server-side 应用，env 被删除：

deployment.apps/csa serverside-applied
env=

再退回客户端 apply 也行，因为注解一直被同步着。先用带 env 的清单做一次普通 kubectl apply，env 回来了；再用不带 env 的清单做一次，三方合并照常把它删掉：

deployment.apps/csa configured
env=
kubectl Apply  2026-10-13T03:24:43Z
kube-controller-manager Update status 2026-10-13T03:24:44Z
kubectl-client-side-apply Update  2026-10-13T03:24:44Z

只是对象上会同时留着 kubectl Apply 和 kubectl-client-side-apply 两条记录，两种方式来回切换以后，所有权会越来越难读。

第 1、2 步和服务端的注解同步只认 kubectl 这个名字；第 3 步不看名字，会把所有拥有该注解的 Update 记录并入当前的 --field-manager。另建一个用客户端 apply 创建的 csa2，用 --field-manager=ci 做同样的修改：

error: Apply failed with 1 conflict: conflict with "kubectl-client-side-apply" using apps/v1: .spec.template.spec.containers[name="app"].env[name="MODE"].value

这个冲突是第 1 步报的：服务端不会为 ci 放行。打算让 CI 用自定义管理者名接管老对象，要么第一次提交时值保持不变，要么明确用 --force-conflicts。按 kubectl 源码，请求成功后第 3 步会把 kubectl-client-side-apply 的整条记录并入 ci，而不只是共有几个字段；由于第 2 步不对 ci 执行，注解此后归 ci 所有却不在它的清单里，推测在第 4 步重发时会被删掉。这两点这次都没有实测。另外，官方文档提醒：迁移时 kubectl 是靠 last-applied-configuration 注解判断哪些字段属于客户端 apply 的，客户端 apply 之后被 kubectl scale 之类改过的字段不在其中，--server-side 时照样会冲突。这一点这次没有单独复现。

before-first-apply

managedFields 可以用一次非 Apply 的 patch 写成 [{}] 整体清空（官方文档记载的做法，正常情况下不该这么做）。清空 csa2 之后，再查管理者，什么都没有输出。这时用 ci 提交不同的 MODE：

error: Apply failed with 1 conflict: conflict with "before-first-apply" using apps/v1: .spec.template.spec.containers[name="app"].env[name="MODE"].value

对象上没有任何所有权记录时，API Server 把已有的字段都算在一个叫 before-first-apply 的管理者头上，这样第一次 SSA 也不会悄悄覆盖。提交相同的值则成功，之后的记录里只有 ci 和控制器，看不到 before-first-apply：

deployment.apps/csa2 serverside-applied
ci Apply  2026-10-13T03:25:09Z
kube-controller-manager Update status 2026-10-13T03:25:09Z

按 apiserver 源码，before-first-apply 其实是作为一条 Update 记录保存了的。消失的原因推测在 kubectl 这一侧：csa2 是客户端 apply 建的，带着 last-applied-configuration 注解，于是 before-first-apply 成了「拥有该注解的 Update 记录」，被前面迁移的第 3 步整条并入了 ci。这个推测没有单独验证。

在日志或报错里看到 before-first-apply，说明这个对象之前没有 managedFields，比如被人清空过。还有一点：清空之后、第一次 Apply 之前，普通的 Update 也不会被记账。上面清空用的那次 patch 本身没有留下 kubectl-patch 记录，等了 3 秒再查也还是空的。按 apiserver 源码，对象一旦没有 managedFields，Update 就跳过所有权追踪，直到下一次 Apply。

把 replicas 交给 HPA

副本数由 HPA 管的 Deployment，清单里不该再写 replicas。但「直接删掉」有坑。先看最简单的情况：清单里 replicas: 2，kubectl 是唯一所有者，然后从清单里删掉这一行：

deployment.apps/naive serverside-applied
replicas=2
8d7
<   replicas: 2
deployment.apps/naive serverside-applied
replicas=1

字段被删除后回到默认值 1。线上 10 个副本的服务这样改一次清单，会被直接缩到 1 个。

再上一个真的 HPA，清单里仍写着 replicas: 2（Deployment 名为 rep）：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: rep
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: rep
  minReplicas: 3
  maxReplicas: 3
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 80
kubectl -n notes-lab apply --server-side -f rep.yaml
kubectl -n notes-lab apply --server-side -f hpa.yaml

HPA 的 CPU 指标此时还是 <unknown>，但它照样把副本数拉到了下限（事件原因是 Current number of replicas below Spec.MinReplicas）。30 秒后：

replicas=3
kubectl Apply  2026-10-13T03:25:46Z
kube-controller-manager Update scale 
kube-controller-manager Update status 2026-10-13T03:26:06Z

HPA 控制器以 kube-controller-manager 的身份通过 scale 子资源写副本数，所有权随之转过去。这时 CI 原样应用清单，报冲突：

error: Apply failed with 1 conflict: conflict with "kube-controller-manager" with subresource "scale" using apps/v1: .spec.replicas

如果流水线为了「让部署能过」默认加了 --force-conflicts，就会和 HPA 来回拉锯。11:26:24 强制应用后每 3 秒查一次副本数：

11:26:24
deployment.apps/rep serverside-applied
11:26:25 replicas=2
11:26:28 replicas=2
11:26:31 replicas=2
11:26:34 replicas=2
11:26:37 replicas=3
11:26:40 replicas=3
FIRST                  LAST                   COUNT   REASON
2026-10-13T03:26:05Z   2026-10-13T03:26:37Z   2       SuccessfulRescale

副本数被压回 2 约 13 秒后，HPA 又改回 3，事件计数变成 2。这段时间取决于 HPA 的同步周期，默认 15 秒（这个集群的 kube-controller-manager 没有设 --horizontal-pod-autoscaler-sync-period），13 秒落在一个周期之内。只有清单里的值和 HPA 算出来的期望值不同时（这里是低于 minReplicas），每次部署才会这样拉扯一次；两者恰好相等时，按前面共享所有权的规则，apply 不会冲突，只会和 HPA 共有这个字段。

这个冲突其实是好信号：它说明 HPA 已经拿到了 replicas，此时从清单里删掉这一行是安全的，因为 kubectl 已经不是它的所有者了：

8d7
<   replicas: 2
deployment.apps/rep serverside-applied
replicas=3
{"manager":"kubectl","subresource":null,"replicas":false}
{"manager":"kube-controller-manager","subresource":"scale","replicas":true}
{"manager":"kube-controller-manager","subresource":"status","replicas":false}

危险的是 HPA 还没写过 replicas 的那段时间，比如 HPA 刚建好、副本数正好在范围内。官方文档给的做法是先用一个临时管理者提交只含 replicas 的清单，让它和 kubectl 共有这个字段，然后再删：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: ho
spec:
  replicas: 3
kubectl -n notes-lab apply --server-side -f ho.yaml                     # 主清单，replicas: 3
kubectl -n notes-lab apply --server-side --field-manager=handover-to-hpa -f ho-handover.yaml
kubectl -n notes-lab apply --server-side -f ho-norep.yaml               # 主清单删掉 replicas

官方文档的示例命令还加了 --validate=false，这次没加，只含 replicas 的清单也通过了。前两条命令之后：

deployment.apps/ho serverside-applied
handover-to-hpa Apply  
kubectl Apply  2026-10-13T03:27:36Z

handover-to-hpa 和前面 kubectl-last-applied 的 time 都是空的。按 apiserver 源码，Apply 没有改变对象时不会更新时间戳，这两次提交的值都和对象上已有的一样。

第三条命令之后：

deployment.apps/ho serverside-applied
replicas=3
{"manager":"handover-to-hpa","replicas":true}
{"manager":"kubectl","replicas":false}
{"manager":"kube-controller-manager","replicas":false}

主清单删掉 replicas 后，副本数保持 3，所有权留在 handover-to-hpa 手里。按文档的说法，HPA 下次改副本数时会接管这个字段，临时管理者不再拥有任何字段，记录随之自动删除。ho 没有配 HPA，这一步没有验证。HPA 本身的排查见 HPA 和 HPA 排查。

小结

  • managedFields 记录的是「谁、用什么操作、通过哪个子资源」，管理者名相同但操作或子资源不同，就是两条记录，彼此照样冲突。
  • 冲突只发生在 Apply 上；edit、patch、scale 和控制器的写入会静默接管字段。值改回去，所有权也不会自动还回去。
  • 从清单里删字段：唯一所有者时删除或回到默认值，共有时只是放弃所有权。replicas 回到 1 是最危险的一种。
  • 不同的流水线要用不同的 --field-manager，否则彼此覆盖、互删字段都不会报错。
  • args、command、tolerations 是 atomic 列表，只能整体归一个管理者；containers、env、volumes 按键合并。
  • 有疑问先 --dry-run=server，带不带 --force-conflicts 都能预演结果。--force-conflicts 只该在确认要接管字段时用，不该写进流水线的默认参数。

参考：Server-Side Apply、Declarative Management of Kubernetes Objects Using Configuration Files、ObjectMeta（managedFields）、Horizontal Pod Autoscaling。
