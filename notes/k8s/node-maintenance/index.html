节点维护与安全排空

升级内核、换硬盘、升级 kubelet 之前，要先把节点上的 Pod 挪走。标准动作是两步：kubectl cordon 让节点不再接新 Pod，kubectl drain 把已有 Pod 逐个驱逐，控制器再到别的节点上补副本。维护完 kubectl uncordon 恢复调度。这一篇把每一步实际做了什么、会在哪里卡住都跑一遍。

cordon 和 drain 会影响节点上所有人的 Pod，所以这次没有动平时那个共享集群，而是单独起了一个用完即删的三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 是 kind 自带的 kindnet）。注意 kubectl 客户端是 v1.30.0，drain 的逻辑都在客户端里，不同版本的提示文字可能略有差别。节点名简化成 control-plane、worker、worker2，Pod IP 用 <pod-ip> 代替，实验放在 notes-lab namespace。

维护前先看清目标节点上有什么：

kubectl get pods -A -o wide --field-selector spec.nodeName=worker

kube-system kube-proxy-vcfth         1/1     Running   0          34m   <node-ip>   worker   <none>           <none>
notes-lab   bare                     1/1     Running   0          22s   <pod-ip>    worker   <none>           <none>
notes-lab   cache-5fb4b7884d-2ksh9   1/1     Running   0          18s   <pod-ip>    worker   <none>           <none>

notes-lab   web-695d7c566b-nt9xj     1/1     Running   0          21s   <pod-ip>    worker   <none>           <none>

这几个 Pod 是故意凑齐的 drain 常见障碍：

  • kindnet、kube-proxy：DaemonSet 管理的系统 Pod；
  • bare：直接创建的裸 Pod，没有控制器；
  • cache：1 副本 Deployment，挂了一个 emptyDir，并用 nodeSelector 钉在 worker 上；
  • web：4 副本的普通 Deployment，两个 worker 各两个。

cordon：只挡新 Pod

kubectl cordon worker
kubectl get nodes
kubectl get node worker -o jsonpath='unschedulable={.spec.unschedulable} taints={.spec.taints}{"\n"}'

control-plane   Ready                      control-plane   35m   v1.31.0
worker          Ready,SchedulingDisabled   <none>          34m   v1.31.0
worker2         Ready                      <none>          34m   v1.31.0
unschedulable=true taints=[{"effect":"NoSchedule","key":"node.kubernetes.io/unschedulable","timeAdded":"2026-10-13T04:43:50Z"}]

cordon 改的是节点的 spec.unschedulable，节点上随即出现一个 node.kubernetes.io/unschedulable:NoSchedule 污点。它是 NoSchedule，不是 NoExecute，所以 worker 上的 Pod 一个都没动。把 web 扩到 6 个副本，新增的两个（04:43:52 和 04:43:55 创建）都去了 worker2。不过扩容前 worker 上已有 4 个、worker2 只有 2 个，默认打散本来也会偏向 worker2，单看这次扩容分不出是不是 cordon 的作用，确证见下文 cache 的 FailedScheduling（1 node(s) were unschedulable）：

drain 的三道关卡

把 web 缩回 4 副本（kubectl -n notes-lab scale deploy/web --replicas=4，这条命令的输出没有留档），uncordon 之后，直接 drain：

kubectl drain worker
node/worker cordoned
error: unable to drain node "worker" due to error:[cannot delete DaemonSet-managed Pods (use --ignore-daemonsets to ignore): kube-system/kindnet-vjr94, kube-system/kube-proxy-vcfth, cannot delete cannot delete Pods that declare no controller (use --force to override): notes-lab/bare, cannot delete Pods with local storage (use --delete-emptydir-data to override): notes-lab/cache-5fb4b7884d-2ksh9], continuing command...
There are pending nodes to be drained:
 worker
cannot delete DaemonSet-managed Pods (use --ignore-daemonsets to ignore): kube-system/kindnet-vjr94, kube-system/kube-proxy-vcfth
cannot delete cannot delete Pods that declare no controller (use --force to override): notes-lab/bare
cannot delete Pods with local storage (use --delete-emptydir-data to override): notes-lab/cache-5fb4b7884d-2ksh9
exit=1

三类障碍一次全列出来了，每类后面都写了对应的参数。cannot delete cannot delete 这个重复是 kubectl 自己的提示文字，不是复制错了。两件事要注意：

  • 第一行就是 node/worker cordoned。drain 先 cordon，再检查，检查不过就退出，但不会撤销 cordon。之后 kubectl get nodes 看到的还是 Ready,SchedulingDisabled。drain 失败后记得自己判断要不要 uncordon。
  • 检查不过时一个 Pod 都没驱逐。同一时刻的 Pod 列表里，web、cache、bare 全都还在 worker 上 Running。检查是在驱逐前统一做的，不会出现「赶走一半再报错」。

逐个加参数，报错一类一类消失：

$ kubectl drain worker --ignore-daemonsets
node/worker already cordoned
error: unable to drain node "worker" due to error:[cannot delete cannot delete Pods that declare no controller (use --force to override): notes-lab/bare, cannot delete Pods with local storage (use --delete-emptydir-data to override): notes-lab/cache-5fb4b7884d-2ksh9], continuing command...

$ kubectl drain worker --ignore-daemonsets --delete-emptydir-data
node/worker already cordoned
error: unable to drain node "worker" due to error:cannot delete cannot delete Pods that declare no controller (use --force to override): notes-lab/bare, continuing command...

三个参数各自放过了什么：

  • --ignore-daemonsets：跳过 DaemonSet 的 Pod，不驱逐它们。就算驱逐了，DaemonSet 控制器也会马上在原节点补回来，因为它的 Pod 容忍 unschedulable 污点。
  • --delete-emptydir-data：允许驱逐带 emptyDir 的 Pod。emptyDir 跟着 Pod 走，Pod 删了数据就没了，换到别的节点是一个空目录。这个参数就是让你确认「这些数据可以丢」。
  • --force：允许处理没有控制器的 Pod。裸 Pod 被赶走以后，没有任何东西会重建它。

drain 就是一个客户端脚本，整个过程是：读节点、列出节点上的 Pod、查每个 Pod 的属主（这里查的是两个 DaemonSet）、对每个要处理的 Pod 并发 POST 一个 eviction 子资源，然后大约每秒 GET 一次，直到 404 才算这个 Pod 走完（kubectl v1.30 源码里轮询间隔写死为 1 秒，v1.31 相同）。即使用了 --force，裸 Pod 走的也是 Eviction API，而不是直接 DELETE。Eviction 成功返回 201（官方文档写的是 200，上面的请求日志里实测是 201），和直接调 Eviction API 时一样，见 PDB。

服务端的分工是：API Server 处理 eviction 请求，检查 PDB，允许的话先给 Pod 加一个 DisruptionTarget condition，再删除它（设置 deletionTimestamp）；kubelet 只是看到 Pod 被删除，像普通删除一样走优雅终止。kubelet 并不知道这是一次 drain。

这几个 Pod 的宽限期都是 1 秒，Killing 事件都在 12:44:20（事件里记的是 UTC 04:44:20），对象却到 12:44:29 才消失，整个 drain 用了约 11 秒。多出的几秒耗在 kubelet 停容器到 API 里的对象被删掉之间，这次没有测具体耗在哪一步。

1 node(s) were unschedulable 就是被 cordon 的 worker，它又是唯一满足 nodeSelector 的节点。drain 只负责把 Pod 赶走，不检查替代 Pod 有没有地方去。所以 drain 之前要先排查用 nodeSelector、节点亲和或本地 PV 绑在这台节点上的工作负载，drain 之后要看一眼有没有 Pending。

uncordon：Pending 的会回来，Running 的不会

kubectl uncordon worker
# 30 秒后
kubectl -n notes-lab get pod -o wide
NAME                     READY   STATUS    RESTARTS   AGE    IP         NODE      NOMINATED NODE   READINESS GATES

web-695d7c566b-szvvr     1/1     Running   0          65s    <pod-ip>   worker2   <none>           <none>

一直 Pending 的 cache 在 30 秒内已经在 worker 上 Running，web 的 4 个副本全留在 worker2。调度只在 Pod 创建时发生一次，Kubernetes 不会因为节点恢复就把运行中的 Pod 挪回去。滚动维护多台节点时，最后一台维护完，负载往往全挤在先维护的那几台上。想重新均衡，可以等下一次发布，或者对 Deployment 做一次 kubectl rollout restart（会重建全部 Pod）。

drain 会等优雅终止

准备一个收到 SIGTERM 后还要忙 15 秒的 Pod，宽限期 30 秒：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: slow
spec:
  replicas: 1
  selector:
    matchLabels: {app: slow}
  template:
    metadata:
      labels: {app: slow}
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: app
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              trap 'echo "got TERM $(date +%T)"; sleep 15; echo "bye $(date +%T)"; exit 0' TERM
              echo "start $(date +%T)"
              while true; do sleep 1; done

先 kubectl cordon worker2，apply 之后 Pod 只能落在 worker 上，再 kubectl uncordon worker2。一边 logs -f，一边 drain，每行加上本机时间：

12:45:46 node/worker cordoned
12:45:46 Warning: ignoring DaemonSet-managed Pods: kube-system/kindnet-vjr94, kube-system/kube-proxy-vcfth
12:45:46 evicting pod notes-lab/slow-6466db86d6-9v6d8
12:46:05 pod/slow-6466db86d6-9v6d8 evicted
12:46:05 node/worker drained
start 04:45:43
got TERM 04:45:46
bye 04:46:01

容器里打印的是 UTC 时间。drain 一发出驱逐，容器就收到了 SIGTERM，程序按自己的节奏干完 15 秒的收尾才退出，drain 一直等到 Pod 对象消失（12:46:05）才往下走。Eviction 用的是 Pod 自己的 terminationGracePeriodSeconds。

--grace-period 可以覆盖它。重新布置一遍：kubectl uncordon worker、kubectl cordon worker2、kubectl -n notes-lab rollout restart deploy/slow，新 Pod 落到 worker 后 kubectl uncordon worker2。然后 --grace-period=5：

12:46:23 node/worker cordoned
12:46:23 evicting pod notes-lab/slow-6f7dc98767-vw87z
12:46:39 pod/slow-6f7dc98767-vw87z evicted
12:46:39 node/worker drained
start 04:46:18
got TERM 04:46:24

这次日志里没有 bye，Pod 对象也比上一次早消失（SIGTERM 后 15 秒，上一次是 19 秒），说明收尾没跑完，推测是 5 秒到期后被 SIGKILL 杀掉了。drain 一共用了 16 秒，比 5 秒的宽限期多出约 10 秒，这次没有测具体耗在哪一步（前一次是 bye 之后约 4 秒对象消失）。维护窗口很紧时可以用这个参数压缩时间，代价是应用来不及做完收尾。SIGTERM 和宽限期的细节见优雅终止。

PDB 卡住 drain

上一节 drain 完，worker 还处在 cordon 状态，先 kubectl uncordon worker。然后建一个 2 副本的 Deployment guarded，配一个 minAvailable: 2 的 PDB，也就是一个都不许自愿中断：

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: guarded
spec:
  minAvailable: 2
  selector:
    matchLabels: {app: guarded}
NAME      MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
guarded   2               N/A               0                     8s

两个副本一个在 worker，一个在 worker2。drain worker，加 --timeout=40s：

  • 按官方文档，PDB 不允许时 Eviction API 返回 429（实测响应见 PDB），drain 把它当成「稍后再试」，每次被拒后等 5 秒再试（kubectl v1.30 源码里写死的 5 * time.Second，v1.31 相同）。40 秒里一共试了 9 次。
  • 不加 --timeout 就会一直重试下去。kubectl drain --help 里写的是 --timeout=0s: ... zero means infinite。在流水线里跑 drain，一定要设超时，否则一个配错的 PDB 就能把整条维护流程挂住，而且屏幕上只有不断重复的这一行。
  • 超时退出后节点仍是 Ready,SchedulingDisabled，Pod 仍在原地 Running。

–disable-eviction：绕过预算

drain 超时退出后，worker 上还是那一个副本，ALLOWED DISRUPTIONS 为 0。改用 --disable-eviction 再 drain 一次：

两种方式在 Pod 上留下的痕迹

用普通 drain 驱逐一个 slow Pod，在终止中途读它的 conditions：

DisruptionTarget True EvictionByEvictionAPI Eviction API: evicting
PodReadyToStartContainers True  
Initialized True  
Ready True  
ContainersReady True  
PodScheduled True

走 Eviction API 的 Pod 多了一个 DisruptionTarget condition，reason 是 EvictionByEvictionAPI。按官方文档「Pod disruption conditions」，这个 condition 只在五种情况下添加：调度器抢占（PreemptionByScheduler）、污点驱逐（DeletionByTaintManager）、Eviction API（EvictionByEvictionAPI）、PodGC 清理（DeletionByPodGC）、kubelet 因节点压力、节点关机或为系统关键 Pod 抢占而终止 Pod（TerminationByKubelet），用户直接 DELETE 不在其中，所以 --disable-eviction 删掉的 Pod 按文档不会带它（这一点这次没有拿到可靠的对照输出）。污点与容忍里节点失联被驱逐的 Pod，reason 就是 DeletionByTaintManager。Job 的 podFailurePolicy 可以根据这个 condition 区分「被中断」和「自己失败」；排查 Pod 为什么消失时，只要对象还没从 API 里消失，也可以先看这个字段。

小结

步骤实测行为
cordon设 spec.unschedulable，节点上自动出现 unschedulable:NoSchedule 污点；已有 Pod 不动
drain 预检先 cordon 再检查；DaemonSet、裸 Pod、emptyDir 三类问题一次列全；检查不过一个都不驱逐，也不撤销 cordon
drain 驱逐并发 POST eviction，每秒 GET 一次直到 404；遵守 Pod 的宽限期，--grace-period 可覆盖
遇到 PDB每 5 秒重试，默认无限；--timeout 到点退出；条件满足后自动继续
--disable-eviction改成 DELETE，绕过 PDB；按文档 Pod 上不会有 DisruptionTarget
uncordonPending 的 Pod 会调度回来，运行中的 Pod 不会回迁

这次用的是一次性集群，做完直接 kind delete cluster 删掉了。在真实集群上，维护后记得 kubectl uncordon <node>，并核对各工作负载的就绪副本数和 PDB 的 ALLOWED DISRUPTIONS。
