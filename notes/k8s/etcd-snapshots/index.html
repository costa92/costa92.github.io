etcd 保存的是整个集群的关键状态

高可用拓扑区分了堆叠式和外部 etcd。CSI 卷快照则面向应用 PVC。etcd 快照保存 Kubernetes API 对象状态，不能代替应用数据库或 PVC 的备份；反过来，仅有应用数据也无法完整恢复控制平面。

本页只针对自己管理的 kubeadm 集群，托管服务（EKS、GKE 等）的 etcd 对用户不可见，不适用。恢复会直接改写集群状态，所以下面所有操作都是在一个用完即删的单节点 kind 集群里做的（Kubernetes v1.31.0，kubeadm 部署的堆叠式 etcd 3.5.15，节点名简化为 control-plane，节点 IP 用 <node-ip> 代替）。kind 节点就是一个跑着 kubelet 的容器，目录布局和 kubeadm 完全一致，下文的路径可以直接对照真实控制平面节点；它做不到的事情在最后单独说明。

从静态 Pod 清单找端点和证书

kubeadm 把 etcd 作为静态 Pod 运行，参数全部写在 /etc/kubernetes/manifests/etcd.yaml。不用猜证书路径，直接读清单：

cat /etc/kubernetes/manifests/etcd.yaml
  - --advertise-client-urls=https://<node-ip>:2379
  - --cert-file=/etc/kubernetes/pki/etcd/server.crt
  - --client-cert-auth=true
  - --data-dir=/var/lib/etcd
  - --initial-advertise-peer-urls=https://<node-ip>:2380
  - --initial-cluster=<node-name>=https://<node-ip>:2380
  - --key-file=/etc/kubernetes/pki/etcd/server.key
  - --listen-client-urls=https://127.0.0.1:2379,https://<node-ip>:2379
  - --listen-peer-urls=https://<node-ip>:2380
  - --name=<node-name>
  - --peer-trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt
  - --trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt
  image: registry.k8s.io/etcd:3.5.15-0
- hostPath:
    path: /etc/kubernetes/pki/etcd
- hostPath:
    path: /var/lib/etcd

（输出只保留了相关的行。）几条信息后面都会用到：

  • 客户端端口 2379 在 127.0.0.1 和节点 IP 上都监听，2380 只监听节点 IP，是成员之间用的 peer 端口。
  • --client-cert-auth=true：客户端必须出示由 ca.crt 签发的证书，只给 CA 不够。
  • 数据目录是 hostPath /var/lib/etcd，恢复时要改的就是这一项。
  • --name、--initial-cluster、--initial-advertise-peer-urls 是恢复时要传给 etcdutl 的成员参数。单节点时 --initial-cluster 只有自己一项。

API Server 用的是另一套客户端证书，在 kube-apiserver.yaml 里：

- --etcd-cafile=/etc/kubernetes/pki/etcd/ca.crt
- --etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt
- --etcd-keyfile=/etc/kubernetes/pki/apiserver-etcd-client.key
- --etcd-servers=https://127.0.0.1:2379

这里的 --etcd-servers 就是恢复后 API Server 要连的地址；如果恢复出的 etcd 端点变了，要同步改这个参数。

etcd 镜像里有 etcdctl，没有 etcdutl

kubeadm 用的 registry.k8s.io/etcd:3.5.15-0 镜像里，/usr/local/bin 下只有 etcd、etcdctl 及其 3.4 旧版本和迁移脚本，不带 etcdutl：

$ kubectl -n kube-system exec etcd-control-plane -- etcdctl version
etcdctl version: 3.5.15
API version: 3.5
$ kubectl -n kube-system exec etcd-control-plane -- etcdutl version
error: Internal error occurred: ... exec: "etcdutl": executable file not found in $PATH: unknown

kubectl exec 跑 etcdctl 做健康检查很方便，但快照文件会落在容器的文件系统里，还得另想办法取出来，etcdutl 也没有。所以实际做备份时，更省事的办法是在控制平面节点上装一份和服务端版本一致的 etcd 客户端，版本号以清单里的镜像 tag 为准：

ETCD_VER=v3.5.15
curl -sSLO https://github.com/etcd-io/etcd/releases/download/${ETCD_VER}/etcd-${ETCD_VER}-linux-amd64.tar.gz
curl -sSL https://github.com/etcd-io/etcd/releases/download/${ETCD_VER}/SHA256SUMS | grep linux-amd64.tar.gz
sha256sum etcd-${ETCD_VER}-linux-amd64.tar.gz   # 两行哈希必须一致
tar xzf etcd-${ETCD_VER}-linux-amd64.tar.gz
install -m 0755 etcd-${ETCD_VER}-linux-amd64/etcdctl etcd-${ETCD_VER}-linux-amd64/etcdutl /usr/local/bin/

实测时两个哈希都是 3f6b48d8c2844699f2b19c1880508ecf63e1489769ed37ebb97495d5cd848a89。下文的命令都在节点上执行。

证书或端点写错时会发生什么

先故意写错，看错误长什么样。这一步很值得在演练里做一遍，因为结果和直觉不同。

不带证书：snapshot save 一直挂着

etcdctl --endpoints=https://127.0.0.1:2379 snapshot save /var/backups/etcd/nocert.db
{"level":"info","ts":"2026-10-13T06:51:17.206702Z","caller":"snapshot/v3_snapshot.go:65","msg":"created temporary db file","path":"/var/backups/etcd/nocert.db.part"}

打印完这一行就再也没有输出了。两分多钟后它还在：

7746       02:11 etcdctl --endpoints=https://127.0.0.1:2379 snapshot save /var/backups/etcd/nocert.db

手动 kill 掉以后，目录里留下一个 0 字节的 .part 文件：

Terminated

real	2m11.457s
exit=143
nocert.db.part

只带 --cacert、不带客户端证书，也一样挂住。这时候客户端看不到原因，要去 etcd 那边看日志：

kubectl -n kube-system logs etcd-control-plane --since=3m | grep 'rejected connection'
{"level":"warn","ts":"2026-10-13T06:53:28.718360Z","caller":"embed/config_logging.go:170","msg":"rejected connection on client endpoint","remote-addr":"127.0.0.1:50276","server-name":"","error":"tls: client didn't provide a certificate"}
{"level":"warn","ts":"2026-10-13T06:53:29.720830Z","caller":"embed/config_logging.go:170","msg":"rejected connection on client endpoint","remote-addr":"127.0.0.1:43426","server-name":"","error":"tls: client didn't provide a certificate"}
{"level":"warn","ts":"2026-10-13T06:53:31.367991Z","caller":"embed/config_logging.go:170","msg":"rejected connection on client endpoint","remote-addr":"127.0.0.1:43438","server-name":"","error":"tls: client didn't provide a certificate"}

客户端在不停重连，间隔从 1 秒逐渐拉长。如果备份放在 cron 里跑，这种挂起不会报错退出，只会让任务一直不结束，还在备份目录留下空的 .part。加上 --command-timeout 之后它会按时失败，并把原因打出来：

etcdctl --endpoints=https://127.0.0.1:2379 --command-timeout=5s snapshot save /var/backups/etcd/nocert.db
{"level":"error","ts":"2026-10-13T06:54:02.349523Z","logger":"client","caller":"v3@v3.5.15/retry_interceptor.go:130","msg":"streamer failed to create ClientStream","error":"rpc error: code = DeadlineExceeded desc = latest balancer error: last connection error: connection error: desc = \"transport: authentication handshake failed: tls: failed to verify certificate: x509: certificate signed by unknown authority\"", ...}
Error: context deadline exceeded

real	0m5.008s
exit=5

同样只带 CA 时，endpoint health 不加任何参数也在 5.01 秒后失败（etcdctl 的 --command-timeout 默认是 5 秒），snapshot save 却没有受这个默认值约束。写备份脚本时 --command-timeout 要显式加上（这次实测 5 秒就足够让失败暴露；真实集群的快照越大越慢，超时要按快照大小留够余量）。

端点写错时的三种报错

证书都给对，只改 --endpoints，每次都带 --command-timeout=5s，最终都是 context deadline exceeded，区别在前面那行 last connection error：

写成客户端看到的原因etcd 日志
http://127.0.0.1:2379（漏了 s）error reading server preface: read tcp ... connection reset by peertls: first record does not look like a TLS handshake
https://127.0.0.1:2380（peer 端口）dial tcp 127.0.0.1:2380: connect: connection refused无
https://127.0.0.1:12379（端口写错）dial tcp 127.0.0.1:12379: connect: connection refused无

2380 那一行容易误判：它不是「peer 端口不接受客户端请求」，而是 peer 端口压根没在 127.0.0.1 上监听，和端口写错是同一种拒绝。另外，https://localhost:2379 是能通的，kubeadm 签发的 server 证书里包含 localhost。

保存快照

上一节的错误演示都是在没有设置任何 ETCDCTL_* 环境变量的 shell 里做的。从这里开始，先把端点和证书导出成环境变量，etcdctl 会按 ETCDCTL_<参数名> 读取它们，后面的命令就不用每次写一长串。证书取自 etcd 静态 Pod 自己的 server 证书（和 kubernetes.io 文档的示例一致；kubeadm 还在同一目录生成了 healthcheck-client.crt，也可以用）：

export ETCDCTL_API=3
export ETCDCTL_ENDPOINTS=https://127.0.0.1:2379
export ETCDCTL_CACERT=/etc/kubernetes/pki/etcd/ca.crt
export ETCDCTL_CERT=/etc/kubernetes/pki/etcd/server.crt
export ETCDCTL_KEY=/etc/kubernetes/pki/etcd/server.key

mkdir -p /var/backups/etcd
etcdctl --command-timeout=60s snapshot save /var/backups/etcd/snap-1.db

--command-timeout=60s 是推荐写法。实测时这几个值是直接写成命令行参数的，也没有带 --command-timeout，下面的输出来自那次执行。

{"level":"info","ts":"2026-10-13T06:55:50.512764Z","caller":"snapshot/v3_snapshot.go:65","msg":"created temporary db file","path":"/var/backups/etcd/snap-1.db.part"}
{"level":"info","ts":"2026-10-13T06:55:50.517552Z","logger":"client","caller":"v3@v3.5.15/maintenance.go:212","msg":"opened snapshot stream; downloading"}
{"level":"info","ts":"2026-10-13T06:55:52.511695Z","logger":"client","caller":"v3@v3.5.15/maintenance.go:220","msg":"completed snapshot read; closing"}
Snapshot saved at /var/backups/etcd/snap-1.db

etcdctl 先写 .part，传完才改名，所以只要看到最终文件名，就说明传输本身结束了。文件大小和数据目录对比一下：

-rw------- 1 root root 1466400 Oct 13 06:55 snap-1.db
1.4M	/var/lib/etcd/member/snap/db
-rw------- 1 root root 16801792 Oct 13 06:55 db

数据目录里的 db 文件 ls 显示 16 MB，du 只有 1.4 MB，是 bbolt 预分配的稀疏文件；快照只包含实际数据，1.4 MB。估算备份空间时看 du 或 endpoint status 里的 DB SIZE，不要看 ls。

用 etcdutl 看快照状态

etcdutl --write-out=table snapshot status /var/backups/etcd/snap-1.db
+--------+----------+------------+------------+
|  HASH  | REVISION | TOTAL KEYS | TOTAL SIZE |
+--------+----------+------------+------------+
| b130fc |      956 |        966 |     1.5 MB |
+--------+----------+------------+------------+

旧写法 etcdctl snapshot status 在 3.5 里还能用，但会先打印一行弃用提示。kubernetes.io 的「Operating etcd clusters for Kubernetes」写明它自 3.5 起弃用、计划在 3.6 移除；同一页也说明 etcdctl snapshot restore 同样已弃用，应改用 etcdutl snapshot restore：

Deprecated: Use `etcdutl snapshot status` instead.

REVISION 是 etcd 的全局修订号，Kubernetes 对象的 resourceVersion 就取自它。快照前最后改动的 Deployment resourceVersion 是 948，快照的 revision 是 956，对得上（中间那几次写入推测是 Lease 续约之类的后台写入，没有逐个核对）。这个对应关系在恢复后会再用到。不过这只是观察实现细节，写客户端程序时应当把 resourceVersion 当作不透明值，只用来原样传回 API Server，不要比较大小或做算术。

快照文件坏了，status 不一定发现

这是这次实验里最意外的结果。拿 snap-1.db 做两个坏文件：一个截掉后半段，一个在 1 MB 偏移处写入 4 个 0xff 字节：

head -c 700000 snap-1.db > truncated.db
cp snap-1.db flipped.db
printf '\xff\xff\xff\xff' | dd of=flipped.db bs=1 seek=1000000 conv=notrunc status=none

截断的文件，snapshot status 直接 panic：

panic: assertion failed: Page expected to be: 351, but self identifies as 0

goroutine 137 [running]:
go.etcd.io/bbolt._assert(...)
	go.etcd.io/bbolt@v1.3.10/db.go:1387
...
exit=2

改了 4 个字节的文件，snapshot status 正常返回，revision 和 key 数量都和原文件一样，只有 HASH 列变了：

+----------+----------+------------+------------+
|   HASH   | REVISION | TOTAL KEYS | TOTAL SIZE |
+----------+----------+------------+------------+
| 96ccd91a |      956 |        966 |     1.5 MB |
+----------+----------+------------+------------+
exit=0

HASH 是按库内 KV 数据现算的，它本身不知道「正确值」是多少，除非你保存快照时把它记下来对比。真正能发现问题的是 snapshot restore：

$ etcdutl snapshot restore truncated.db --data-dir /var/lib/etcd-restore-trunc
Error: snapshot missing hash but --skip-hash-check=false
$ etcdutl snapshot restore flipped.db --data-dir /var/lib/etcd-restore-flip
Error: expected sha256 [171 38 69 176 ...], got [128 190 215 207 ...]

etcdctl snapshot save 生成的文件末尾附带一个 32 字节的 SHA-256，restore 时会校验。从恢复出的目录也能看出来：member/snap/db 是 1466368 字节，正好比快照文件少 32 字节。截断的文件丢了这个尾巴，所以报 missing hash；--skip-hash-check 只该用于直接从数据目录拷出来的 db 文件（官方恢复文档也是这么说的），不能拿来「绕过」这个错误。

还有一个小坑：校验失败的那次 restore 已经建好了 /var/lib/etcd-restore-flip/member/snap/db，失败后没有清理。下次往同一目录恢复会报目录非空，记得先删掉。

所以「快照能用」至少要做到：

  1. 保存后立刻记录 sha256sum，复制到异地后再算一遍对比；
  2. 定期把快照真的 restore 到一个临时目录，这是 etcdutl 里唯一会校验内嵌哈希的步骤。

恢复：证明它是某个时间点的状态

为了让恢复结果一眼可辨，快照前后各做一组改动：

2026-10-13T06:56:54Z	info	membership/cluster.go:421	added member	{"cluster-id": "2c890c77148f919d", "local-member-id": "0", "added-peer-id": "2e3a9eb00162239a", "added-peer-peer-urls": ["https://<node-ip>:2380"]}
2026-10-13T06:56:55Z	info	snapshot/v3_snapshot.go:293	restored snapshot	{"path": "/var/backups/etcd/snap-1.db", "wal-dir": "/var/lib/etcd-from-snap-1/member/wal", ...}

--name 和 --initial-advertise-peer-urls 取本节点 etcd.yaml 里的值。--initial-cluster 要分情况：单节点时直接取清单里的值；多成员时不能照抄各节点的清单，因为 kubeadm 是逐个 join 控制平面的，每个节点 etcd.yaml 里的 --initial-cluster 只包含它加入时已有的成员，互不相同。应在故障前（或从任一健康成员）用 etcdctl member list 拼出完整的 名字=peer地址 列表，所有成员用同一份列表和同一个 --initial-cluster-token。restore 会丢掉快照里原有的成员信息（日志里的 Trimming membership information），按这几个参数重新生成成员和集群 ID。如果全用默认值，恢复出来的成员 peer 地址是 http://localhost:2380：

added member	{"cluster-id": "cdf818194e3a8c32", "local-member-id": "0", "added-peer-id": "8e9e05c52164694d", "added-peer-peer-urls": ["http://localhost:2380"]}

单节点也许还能起来，但成员列表里记着一个错误的地址，以后加成员时会出问题；多成员集群必须每个成员用自己的 --name、同一份完整的 --initial-cluster 和同一个 token 分别恢复，而且所有成员必须用同一个快照文件；每个成员的 --initial-advertise-peer-urls 必须和它在 --initial-cluster 里那一项的地址完全一致。

成员列表要在平时就记录下来（比如每次备份时把 etcdctl member list 的输出和快照存在一起），真到所有控制平面都坏掉时就查不到了。如果没记，还有一个退路：最后一个加入的控制平面节点，它的 etcd.yaml 里的 --initial-cluster 通常就是完整列表（前提是之后没有再增删成员）。从 member list 换算成 --initial-cluster 的格式是 name=peerURL，用逗号连接。下面是一个三成员的示意（名字和地址是虚构的，地址取自 RFC 5737 文档保留网段，换算命令只在这段文本上试过，没有在多成员集群上跑过）：

$ etcdctl member list
2e3a9eb00162239a, started, cp1, https://192.0.2.11:2380, https://192.0.2.11:2379, false
5b1c0e7a9d2f4410, started, cp2, https://192.0.2.12:2380, https://192.0.2.12:2379, false
8f6d2c3b1a0e9977, started, cp3, https://192.0.2.13:2380, https://192.0.2.13:2379, false
$ etcdctl member list | awk -F', ' '{printf "%s%s=%s", (NR>1?",":""), $3, $4} END{print ""}'
cp1=https://192.0.2.11:2380,cp2=https://192.0.2.12:2380,cp3=https://192.0.2.13:2380

某个成员配置了多个 peer 地址时，第 4 列里会有多个地址，要手工核对。

目标目录必须不存在或为空，往已有目录恢复会被拒绝：

Error: data-dir "/var/lib/etcd-from-snap-1" not empty or could not be read

这是好事，它防止了把正在用的 /var/lib/etcd 覆盖掉。恢复到新目录、保留旧目录，回退时只要把清单改回去。

注意 etcdutl snapshot restore 写到新目录是纯离线的文件操作，不连接 etcd，也不影响正在运行的集群，所以这一步可以提前做，也可以在停 API Server 之后做。官方顺序「停 API Server → 恢复 etcd → 启动 API Server」里的「恢复」，指的是让 etcd 切换到这个新数据目录，也就是下面第三步。

第二步：停掉 API Server

官方文档的要求是先停所有 API Server，再恢复所有 etcd 成员，最后再启动 API Server。kubeadm 下停静态 Pod 的方法是把清单移出 manifests 目录：

mv /etc/kubernetes/manifests/kube-apiserver.yaml /root/

06:57:05 移走，06:57:39 检查时容器已经没有了；中间没有轮询，实际停下的时间更早。脚本里要等 crictl ps --name kube-apiserver 为空再继续，不能移完就动 etcd。

第三步：让 etcd 使用新目录

先把原清单备份到 manifests 目录之外。kubelet 会把 /etc/kubernetes/manifests 下的文件都当作静态 Pod 清单来解析，备份文件如果留在这个目录里，可能被当成第二个 etcd 静态 Pod。然后只改 etcd-data 这个卷的 hostPath，容器内路径和 --data-dir 都不用动：

cp /etc/kubernetes/manifests/etcd.yaml /root/etcd.yaml.orig
sed -i 's#      path: /var/lib/etcd$#      path: /var/lib/etcd-from-snap-1#' /etc/kubernetes/manifests/etcd.yaml
diff /root/etcd.yaml.orig /etc/kubernetes/manifests/etcd.yaml
88c88
<       path: /var/lib/etcd
---
>       path: /var/lib/etcd-from-snap-1

06:57:55 保存清单，06:58:07 新的 etcd 容器起来。这时 API Server 还停着，可以先直接用 etcdctl 核对：

etcdctl --write-out=table endpoint status

别让数据目录和 kubeadm 配置脱节

这一小节的步骤在实验里都没有执行（实验最后直接删掉了整个集群），命令是按上文实测过的同类操作写出来的。

只改 hostPath 有一个后患：kubeadm 把 etcd 数据目录记在 kube-system/kubeadm-config ConfigMap 的 ClusterConfiguration 里（etcd.local.dataDir，默认 /var/lib/etcd），清单里的 hostPath 改了，这个值不会跟着变。推测（按 kubeadm 会依据 ClusterConfiguration 重新生成静态 Pod 清单来推断，没有实测）：之后执行 kubeadm upgrade 等会重写 etcd.yaml 的操作时，hostPath 可能被改回 /var/lib/etcd，etcd 就切回了恢复前的旧数据；同样按实现推断，kubeadm upgrade 升级前备份 etcd 时，复制的也是 etcd.local.dataDir 指向的目录，备份到的会是旧数据。处理办法有三种：

  • 推荐：在第四步启动 API Server 之前、API Server 还停着的时候，把新目录换到原来的位置，旧目录改名保留作回退。先把 etcd.yaml 移出 manifests 目录，等 etcd 容器真正退出再动目录：etcd 还在跑时执行 mv，它持有的文件句柄不变，会继续往改名后的目录里写数据。

    mv /etc/kubernetes/manifests/etcd.yaml /root/etcd.yaml.restored
while crictl ps --name '^etcd$' -q | grep -q .; do sleep 2; done
mv /var/lib/etcd /var/lib/etcd.before-restore-$(date +%Y%m%d)
mv /var/lib/etcd-from-snap-1 /var/lib/etcd
cp /root/etcd.yaml.orig /etc/kubernetes/manifests/etcd.yaml
# etcd 起来后确认成员 ID 是 restore 生成的那个（实验里是 2e3a9eb00162239a）
etcdctl --write-out=table endpoint status

  • 更省事：一开始就不恢复到新目录。停 API Server 后先停 etcd（同样移走 etcd.yaml 并用上面的循环等它退出），把 /var/lib/etcd 改名保留，然后直接 etcdutl snapshot restore ... --data-dir /var/lib/etcd，再原样放回清单。hostPath 和 dataDir 都不用改。代价是 etcd 必须先停，restore 不能提前离线做好。

  • 改配置：保留新目录，用 kubectl -n kube-system edit configmap kubeadm-config 把 ClusterConfiguration 里的 etcd.local.dataDir 改成新路径，让 kubeadm 以后生成的清单和现状一致。ClusterConfiguration 是全集群共用的一份，所以多控制平面时每个节点上的新目录路径都必须一致。

恢复之后的副作用

API 层面看起来已经回到过去了，但节点和各个组件不一定跟上。

节点上的孤儿容器还在跑

API 里只剩 2 个 Pod，节点上却还是 4 个沙箱，app-after 和第三个 app 副本的容器照常运行：

07:01:56
POD ID              CREATED             STATE               NAME                        NAMESPACE                  ATTEMPT             RUNTIME
8727148c61970       5 minutes ago       Ready               app-7545867f49-tvbrm        notes-lab                  0                   (default)
f70dbd912392c       5 minutes ago       Ready               app-after-5dc5d6858-ktblq   notes-lab                  0                   (default)
7f9229b136bf1       6 minutes ago       Ready               app-7545867f49-hrvdw        notes-lab                  0                   (default)
64dfb56d02e1a       6 minutes ago       Ready               app-7545867f49-p4djv        notes-lab                  0                   (default)

每 10 秒查一次，到 07:05:30，也就是 API Server 恢复将近 4 分钟之后，这两个孤儿依然是 Ready，kubelet 日志里也没有任何相关记录。真实业务里，这意味着「已经不存在」的工作负载还在处理请求、写数据库。重启这个节点的 kubelet 后情况立刻变了：

07:05:37
07:05:37 ready-sandboxes=4
07:05:42 ready-sandboxes=2
2026-10-13T07:05:39Z   Killing             app-7545867f49-tvbrm
2026-10-13T07:05:39Z   Killing             app-after-5dc5d6858-ktblq

kubelet 为什么一直没发现，这次没有直接测到，以下是推测：kubelet 里的 reflector 在 API Server 回来后，会从它记下的 resourceVersion（约 1001）续上 watch，而不是重新 List；这两个 Pod 是随快照「回到过去」而消失的，etcd 里从来没有产生过它们的删除事件，续上的 watch 自然也收不到。加了 --mark-compacted 之后，从旧 resourceVersion 续 watch 会得到 410 Gone，reflector 只能重新 List，才会发现 Pod 已经不在了（下文第二轮的结果和这个推测一致，但同样没有直接抓到 410）。

controller-manager 和 scheduler 自己重启了

NAME                                                   RESTARTS   LAST_FINISHED          REASON
kube-controller-manager-control-plane                  1          2026-10-13T06:57:17Z   Error
kube-scheduler-control-plane                           1          2026-10-13T06:57:19Z   Error
E1013 06:57:17.512886       1 controllermanager.go:340] "leaderelection lost"

API Server 停掉 12 秒后，这两个组件续不上 leader 租约，直接退出，由 kubelet 重新拉起，于是带着全新的缓存连上恢复后的 API Server。kubernetes.io 文档里也写了「恢复期间关键组件会丢失 leader lock 并自行重启」。之后把 app 扩到 3 副本，controller-manager 正常创建了新 Pod。不过这个「自动重启」取决于 API Server 停了多久，文档的建议仍然是恢复后主动重启 kube-scheduler、kube-controller-manager 和所有节点的 kubelet，不要依赖巧合。kubelet 不参与选主，不会自己重启，上一节的孤儿就是证据。

resourceVersion 倒退，编号会被复用

恢复后 etcd 的 revision 是 957（比快照多 1，推测是启动后的一次内部写入，没有查是哪个 key）。几十秒后，namespace 的 List resourceVersion 已经走到：

07:02:13
list resourceVersion: 999

999 在恢复之前是 app-after Deployment 的 resourceVersion。也就是说，同一个编号先后代表了两个完全不同的状态。任何缓存了旧 resourceVersion 的客户端（informer、Operator、自己写的 watch 程序），都可能把新事件当成已经见过的旧事件。

用 –bump-revision 和 –mark-compacted 避开倒退

etcd v3.5 的恢复文档专门针对这种情况给了两个参数：--bump-revision 让恢复后的 revision 加上一个足够大的数，保证不会倒退；--mark-compacted 把这个点标记为已压缩，让所有旧 watch 被终止、客户端被迫重新 List。etcdutl 3.5.15 已经支持：

--bump-revision uint                   How much to increase the latest revision after restore
--mark-compacted                       Mark the latest revision after restore as the point of scheduled compaction (required if --bump-revision > 0, disallowed otherwise)

第二轮实验用同样的流程，快照 snap-2.db（revision 1444）之后新建了 Deployment app-after2，恢复时加上这两个参数：

etcdutl snapshot restore /var/backups/etcd/snap-2.db --data-dir /var/lib/etcd-from-snap-2 \
  --name control-plane --initial-cluster control-plane=https://<node-ip>:2380 \
  --initial-cluster-token etcd-restore-2 --initial-advertise-peer-urls https://<node-ip>:2380 \
  --bump-revision 1000000000 --mark-compacted
2026-10-13T07:07:41Z	info	snapshot/v3_snapshot.go:356	bumping latest revision	{"latest-revision": 1444, "bump-amount": 1000000000, "new-latest-revision": 1000001444}
2026-10-13T07:07:41Z	info	snapshot/v3_snapshot.go:373	marking revision compacted	{"revision": 1000001444}

恢复后新建对象的 resourceVersion 从十亿开始，旧编号不会再出现：

marker-post-restore-2 rv=1000001611

这一轮恢复期间没有再重启 kubelet。API Server 07:14:46 就绪后，孤儿 app-after2 在 07:16:12 收到 Killing 事件，07:16:45 沙箱变为 NotReady，前后 86 秒，kubelet 自己清理掉了。（Killing 到停止隔了 30 多秒，推测是 busybox 的 sleep 作为 1 号进程不处理 SIGTERM，等满了默认的 30 秒宽限期。）

这个结果与上一节的推测一致，但不能证明因果，两轮之间至少有三个混杂因素：

  • 第二轮开始前，kubelet 已经在第一轮末尾（07:05:37）重启过一次，两轮面对的 kubelet 状态不同；
  • API Server 停机时长不同：第一轮约 4.5 分钟（06:57:05 到 07:01:37），第二轮约 7 分钟（07:07:42 到 07:14:41）；
  • 07:16:12 的清理时刻，正好和 kubelet 处理 etcd 静态 Pod 的 mirror pod 撞在一起（07:16:09 日志 "Trying to delete pod" pod="kube-system/etcd-..."，07:16:12 记录 etcd Pod 的启动耗时），清理可能是被这次处理顺带触发的。

两轮也各只做了一次。能放心给出的建议是：恢复 Kubernetes 用的 etcd 时，带上 --bump-revision 和 --mark-compacted，并且仍然重启所有节点的 kubelet 以及 controller-manager、scheduler。bump 的数值要大于从快照到恢复之间可能产生的写入数（每次写入 revision 加 1）。etcd 文档的估算是：假设每秒写入少于 1500 次、快照不超过一周，加 10 亿就够了。

单节点实验没覆盖的部分

  • 多成员集群：kind 单节点只有一个 etcd 成员。三成员的堆叠式集群需要先停掉所有控制平面节点上的 API Server，用同一个快照、同一份由 etcdctl member list 拼出的完整 --initial-cluster、同一个 token、各自的 --name 和 peer 地址分别恢复每个成员，再一起启动。这个顺序这里没有实测，以 etcd 恢复文档为准。
  • 外部 etcd：etcd 不是静态 Pod 时，数据目录和启动参数在 systemd unit 或其他配置里，「改 hostPath」那一步要换成改对应的配置。
  • 快照大小和耗时：实验集群的快照只有 1.5 MB，保存用了 2 秒。生产集群通常大得多，--command-timeout 和磁盘空间要按实际大小定。
  • 加密数据：如果 API Server 配置了 Secret 静态加密，恢复后还需要原来的加密密钥配置才能读出 Secret，快照里不包含这个文件。

检查清单

  1. 从 etcd.yaml 读端点和证书，客户端工具版本与 etcd 一致，etcdutl 要另外安装。
  2. snapshot save 一定加 --command-timeout，并检查是否残留 .part。
  3. 保存后记录 sha256sum 和 etcdutl snapshot status 的输出；status 能读出来不代表文件没坏。
  4. 定期把快照 restore 到临时目录，这是 etcdutl 里唯一校验内嵌哈希的步骤。
  5. 恢复：停所有 API Server → restore 到新目录（--name、peer 地址取本节点清单；--initial-cluster 单节点取清单值，多成员用 etcdctl member list 拼出的完整列表，所有成员同一份列表、同一个 token；带 --bump-revision 和 --mark-compacted）→ 改 etcd-data 的 hostPath → 核对 key → 启动 API Server → 重启所有节点的 kubelet 以及 controller-manager、scheduler → 检查节点上有没有 API 里已不存在的容器 → 把新目录换回 /var/lib/etcd、旧目录改名保留（或同步修改 kubeadm-config 里的 etcd.local.dataDir）。
  6. 快照文件里有集群的全部 Secret，权限、加密和存放位置按最高敏感级别处理，不要放进 Git 或公开对象存储。
  7. 异地备份的不只是快照：/etc/kubernetes/pki（etcd CA 和 server/peer 证书）以及 API Server 使用的 EncryptionConfiguration 文件也要一并备份。节点整机丢失时，没有这些文件，拿着快照也无法以原来的证书和加密配置重建控制平面。

证书过期同样会让 etcdctl 连不上，续期方法见 kubeadm 证书管理；升级控制平面前先做一次快照，流程见 kubeadm 升级。
