kubeconfig 多集群管理

kubectl 通过 kubeconfig 找到 API Server 和身份凭据。一个 context 把三样东西绑在一起：集群（API Server 地址和 CA）、用户（凭据）和默认 namespace。多集群操作最容易出错的地方不是命令语法，而是把正确的命令发到错误的 context，或者用错了身份。

context 的基本操作，比如给 context 设 namespace、--minify 只看当前 context，在 kubectl 常用命令 里讲过；context 指向连不上的地址时报什么错、按 context 名字拦截写入，在 本地实验环境 里用假 context 演示过。这一篇往下挖几件那两篇没碰的事：同一个集群配两种权限不同的身份，多个 kubeconfig 文件合并时到底谁说了算，kubectl config 改写时写进了哪个文件，以及凭据怎么泄露。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，CNI 为 Calico），客户端是 kubectl v1.30.0。kind 生成的 context 名统一写成 kind-lab，API Server 地址写成 <apiserver>。实验全程没有碰 ~/.kube/config，所有改动都落在临时目录里的几个 kubeconfig 文件上，用 KUBECONFIG=... 指过去；实验 namespace 叫 notes-lab。

这条 get nodes 是只读的，用的还是日常 kubeconfig；从下一节起，所有 kubectl 命令都只作用于临时文件。

$ kubectl --context kind-lab get nodes
NAME            STATUS   ROLES           AGE   VERSION
control-plane   Ready    control-plane   61d   v1.31.0
worker          Ready    <none>          61d   v1.31.0
worker2         Ready    <none>          61d   v1.31.0

拆出一份私有副本

先从日常的 kubeconfig 里拆出 kind 集群那一项：

umask 077
kubectl config view --minify --flatten --context kind-lab > a.kubeconfig
chmod 600 a.kubeconfig

--flatten 会把证书和私钥以 base64 内联进文件，这份文件就等于集群管理员的钥匙，所以先 umask 077 再写，权限是 600：

$ ls -l a.kubeconfig
-rw------- 1 user user 5686 Oct 13 18:39 a.kubeconfig
$ KUBECONFIG=a.kubeconfig kubectl config view
apiVersion: v1
clusters:
- cluster:
    certificate-authority-data: DATA+OMITTED
    server: https://<apiserver>
  name: kind-lab
contexts:
- context:
    cluster: kind-lab
    user: kind-lab
  name: kind-lab
current-context: kind-lab
kind: Config
preferences: {}
users:
- name: kind-lab
  user:
    client-certificate-data: DATA+OMITTED
    client-key-data: DATA+OMITTED

不带 --raw 的 config view 会把证书、私钥显示成 DATA+OMITTED，token 显示成 REDACTED，这个输出可以贴出来。kind 用的是客户端证书认证，证书本身不是秘密，可以单独解出来看身份和有效期：

$ KUBECONFIG=a.kubeconfig kubectl config view --raw -o jsonpath="{.users[0].user.client-certificate-data}" | base64 -d | openssl x509 -noout -subject -issuer -startdate -enddate
subject=O=kubeadm:cluster-admins, CN=kubernetes-admin
issuer=CN=kubernetes
notBefore=Aug 13 06:34:32 2026 GMT
notAfter=Aug 13 06:39:32 2027 GMT

O=kubeadm:cluster-admins 是这张证书所属的组，有效期一年。这个组的权限来自 kubeadm 建的一条 ClusterRoleBinding：

$ KUBECONFIG=a.kubeconfig kubectl get clusterrolebinding kubeadm:cluster-admins -o wide
NAME                     ROLE                        AGE   USERS   GROUPS                   SERVICEACCOUNTS
kubeadm:cluster-admins   ClusterRole/cluster-admin   61d           kubeadm:cluster-admins

这两点后文讲泄露时还会用到。

同一个集群，两个身份

context 里的「用户」一栏决定你以谁的身份说话。给同一个集群再配一个只读身份：一个 ServiceAccount，加一个只允许 get/list Pod 的 Role。

export KUBECONFIG=a.kubeconfig
kubectl create namespace notes-lab
until kubectl -n notes-lab get sa default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab create serviceaccount notes-lab-reader
kubectl -n notes-lab create role pod-reader --verb=get,list --resource=pods
kubectl -n notes-lab create rolebinding notes-lab-reader --role=pod-reader --serviceaccount=notes-lab:notes-lab-reader
kubectl -n notes-lab run web --image=nginx:alpine --restart=Never

短期 token：最短 10 分钟

kubectl create token 通过 TokenRequest API 签发一个有时效的 token。想要 5 分钟的被拒绝了：

$ kubectl -n notes-lab create token notes-lab-reader --duration=5m
error: failed to create token: TokenRequest.authentication.k8s.io "" is invalid: spec.expirationSeconds: Invalid value: 300: may not specify a duration less than 10 minutes

改成 --duration=10m，直接写进一个 600 权限的文件，不在终端上打印。token 是 JWT，中间那段是不加密的 claims，看一眼不会泄露凭据（签名部分才是关键，这里没输出）：

kubectl -n notes-lab create token notes-lab-reader --duration=10m > reader.token
cut -d. -f2 reader.token | tr "_-" "/+" | base64 -d 2>/dev/null | python3 -m json.tool
{
    "aud": [
        "https://kubernetes.default.svc.cluster.local"
    ],
    "exp": 1791888609,
    "iat": 1791888009,
    "iss": "https://kubernetes.default.svc.cluster.local",
    "jti": "eb5cccaa-caf0-4df4-9edd-3789efc465d5",
    "kubernetes.io": {
        "namespace": "notes-lab",
        "serviceaccount": {
            "name": "notes-lab-reader",
            "uid": "396b1de9-0880-4947-b781-05e8c3829518"
        }
    },
    "nbf": 1791888009,
    "sub": "system:serviceaccount:notes-lab:notes-lab-reader"
}

exp - iat 正好 600 秒，签发于 18:40:09，应在 18:50:09 失效。jti 是这个 token 的唯一编号，下面 whoami 里会再看到它。

一份只有用户和 context 的文件

把这个 token 做成单独的 reader.kubeconfig，里面只放用户和 context，集群仍然引用 a.kubeconfig 里那个 kind-lab：

export KUBECONFIG=reader.kubeconfig
kubectl config set-credentials notes-lab-reader --token="$(cat reader.token)"
kubectl config set-context a-reader --cluster=kind-lab --user=notes-lab-reader --namespace=notes-lab
kubectl config use-context a-reader
$ KUBECONFIG=reader.kubeconfig kubectl config view
apiVersion: v1
clusters: null
contexts:
- context:
    cluster: kind-lab
    namespace: notes-lab
    user: notes-lab-reader
  name: a-reader
current-context: a-reader
kind: Config
preferences: {}
users:
- name: notes-lab-reader
  user:
    token: REDACTED

单独用这个文件时，第一个坑出现了：

$ KUBECONFIG=reader.kubeconfig kubectl get pods
E1013 18:40:16.194153 2140409 memcache.go:265] couldn't get current server API group list: Get "http://localhost:8080/api?timeout=32s": dial tcp 127.0.0.1:8080: connect: connection refused
...
The connection to the server localhost:8080 was refused - did you specify the right host or port?

context 引用的集群在这份文件里不存在，kubectl 没有报「cluster 不存在」，而是退回了默认地址 http://localhost:8080。看到 localhost:8080，基本可以断定 kubectl 根本没读到有效的集群配置：要么 KUBECONFIG 指错了文件，要么 context 引用的 cluster 名不存在，要么没有 current-context（后文会再碰到一次）。

把两个文件一起放进 KUBECONFIG，引用就接上了。管理员和只读身份是同一个集群上的两个 context：

$ export KUBECONFIG=a.kubeconfig:reader.kubeconfig
$ kubectl auth whoami
ATTRIBUTE   VALUE
Username    kubernetes-admin
Groups      [kubeadm:cluster-admins system:authenticated]
$ kubectl --context a-reader auth whoami
ATTRIBUTE                                           VALUE
Username                                            system:serviceaccount:notes-lab:notes-lab-reader
UID                                                 396b1de9-0880-4947-b781-05e8c3829518
Groups                                              [system:serviceaccounts system:serviceaccounts:notes-lab system:authenticated]
Extra: authentication.kubernetes.io/credential-id   [JTI=eb5cccaa-caf0-4df4-9edd-3789efc465d5]

kubectl auth whoami 背后是 SelfSubjectReview API，官方文档标注它从 v1.28 起 Stable，问的是「API Server 认为我是谁」，比看 context 名字可靠得多。只读身份那一行的 JTI 和 token 里的 jti 对得上，能确认用的就是刚签发的那个 token。

can-i –list：RBAC 说可以，不等于真能做

$ kubectl --context a-reader auth can-i --list
Resources                                       Non-Resource URLs                      Resource Names   Verbs
selfsubjectreviews.authentication.k8s.io        []                                     []               [create]
selfsubjectaccessreviews.authorization.k8s.io   []                                     []               [create]
selfsubjectrulesreviews.authorization.k8s.io    []                                     []               [create]
globalnetworkpolicies.projectcalico.org         []                                     []               [get list watch create update patch delete deletecollection]
networkpolicies.projectcalico.org               []                                     []               [get list watch create update patch delete deletecollection]
pods                                            []                                     []               [get list]
                                                [/.well-known/openid-configuration/]   []               [get]
...
                                                [/version]                             []               [get]

pods [get list] 是我们给的；前三行和下面的非资源 URL 是所有已认证用户都有的。意外的是中间两行：一个只读 ServiceAccount，居然对 Calico 的 networkpolicies 和 globalnetworkpolicies 拥有全部动词。顺着 ClusterRoleBinding 找来源：

calico-tiered-policy-passthrough -> calico-tiered-policy-passthrough subject: system:authenticated
system:basic-user -> system:basic-user subject: system:authenticated
system:discovery -> system:discovery subject: system:authenticated
system:public-info-viewer -> system:public-info-viewer subject: system:authenticated
system:service-account-issuer-discovery -> system:service-account-issuer-discovery subject: system:serviceaccounts

Calico 的 operator 建了一个 calico-tiered-policy-passthrough ClusterRole，绑给了 system:authenticated，也就是所有登录用户。看它的属主和规则（节选）：

$ KUBECONFIG=a.kubeconfig kubectl get clusterrole calico-tiered-policy-passthrough -o yaml
...
  ownerReferences:
  - apiVersion: operator.tigera.io/v1
    blockOwnerDeletion: true
    controller: true
    kind: APIServer
    name: default
rules:
- apiGroups:
  - projectcalico.org
  resources:
  - networkpolicies
  - globalnetworkpolicies
  verbs:
  - get
  - list
  - watch
  - create
  - update
  - patch
  - delete
  - deletecollection

真去用的时候：

$ kubectl --context a-reader get networkpolicies.projectcalico.org
Error from server (Forbidden): networkpolicies.projectcalico.org is forbidden: operation on Calico tiered policy is forbidden
$ kubectl --context a-reader auth can-i create networkpolicies.projectcalico.org
yes
$ kubectl --context a-reader auth can-i create networkpolicies.networking.k8s.io
no

can-i 回答 yes，实际请求却被拒绝。Calico 的文档「Configure RBAC for tiered policies」解释了这层关系：本集群通过 operator 的 APIServer CR 装了 Calico API Server（前面那个 ClusterRole 的 ownerReference 就指向 APIServer/default），projectcalico.org 的策略由它以扩展 API Server 的方式提供，权限按 tier 来管，规则写在 tier.networkpolicies、tier.globalnetworkpolicies 这类伪资源上，再用 resourceNames 限定到某个 tier（如 default.*）；访问某个 tier 里的策略，还需要对这个 tier 本身有 get 权限。calico-tiered-policy-passthrough 推测只是让请求通过 Kubernetes 这一层 RBAC，真正的判断在 tier 上（文档没有提到这个 ClusterRole，这是从名字和报错推断的）。文档也直接写了：kubectl auth can-i 不能用来检查 tiered policy 的 RBAC。要让这个只读身份真正能读 default tier 的策略，需要再授予 tiers 的 get（resourceNames: ["default"]）和 tier.networkpolicies 的 get、list（resourceNames: ["default.*"]），这一步本文没有实测。所以 can-i --list 适合用来发现「一个身份比你以为的多了什么」，但不能当作最终结论；装了聚合 API 的集群尤其如此。

只读身份的边界和预期一致：

$ kubectl --context a-reader auth can-i delete pods
no
$ kubectl --context a-reader get pods -n default
Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:notes-lab:notes-lab-reader" cannot list resource "pods" in API group "" in the namespace "default"
$ kubectl --context a-reader delete pod web
Error from server (Forbidden): pods "web" is forbidden: User "system:serviceaccount:notes-lab:notes-lab-reader" cannot delete resource "pods" in API group "" in the namespace "notes-lab"

Forbidden 的报错把用户名、动词、资源和 namespace 都写全了，这四项正好对应一条 Role 规则，对着改就行。有一个报错例外：

$ timeout 10 kubectl --context a-reader get pods -w
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          4m10s
Error from server (Forbidden): unknown (get pods)
$ kubectl --context a-reader auth can-i watch pods
no

-w 先 list 出了当前的 Pod，接着发起 watch 时被拒，报错是语焉不详的 unknown (get pods)，看不出缺的是哪个动词。Role 里只给了 get,list，没给 watch。只读角色要支持 -w 和各种控制器式的客户端，三个动词要一起给。权限模型本身见 RBAC。

多个文件合并：谁说了算

上面 a.kubeconfig:reader.kubeconfig 的 current-context 是管理员那个，换个顺序就变了：

$ export KUBECONFIG=a.kubeconfig:reader.kubeconfig
$ kubectl config current-context
kind-lab
$ export KUBECONFIG=reader.kubeconfig:a.kubeconfig
$ kubectl config current-context; kubectl auth whoami
a-reader
ATTRIBUTE                                           VALUE
Username                                            system:serviceaccount:notes-lab:notes-lab-reader
...

同样两个文件，只是顺序不同，不带 --context 的命令就换了身份。为了看清同名条目怎么处理，再造两个互相冲突的文件（地址用文档专用网段 192.0.2.0/24，不会真连上）：

# b1.kubeconfig
apiVersion: v1
kind: Config
clusters:
- name: shared
  cluster:
    server: https://192.0.2.11:6443
contexts:
- name: dup
  context:
    cluster: shared
    user: u1
- name: only-in-b1
  context:
    cluster: shared
    user: u1
current-context: only-in-b1
users:
- name: u1
  user:
    token: placeholder-b1
# b2.kubeconfig
apiVersion: v1
kind: Config
clusters:
- name: shared
  cluster:
    server: https://192.0.2.22:6443
    insecure-skip-tls-verify: true
contexts:
- name: dup
  context:
    cluster: shared
    user: u2
    namespace: from-b2
- name: only-in-b2
  context:
    cluster: shared
    user: u2
current-context: only-in-b2
users:
- name: u2
  user:
    token: placeholder-b2
$ export KUBECONFIG=b1.kubeconfig:b2.kubeconfig
$ kubectl config get-contexts; kubectl config current-context
CURRENT   NAME         CLUSTER   AUTHINFO   NAMESPACE
          dup          shared    u1         
*         only-in-b1   shared    u1         
          only-in-b2   shared    u2         
only-in-b1
$ kubectl config view --minify --context dup
apiVersion: v1
clusters:
- cluster:
    server: https://192.0.2.11:6443
  name: shared
contexts:
- context:
    cluster: shared
    user: u1
  name: dup
current-context: dup
kind: Config
preferences: {}
users:
- name: u1
  user:
    token: REDACTED

三条规律：

  • current-context 取第一个设置了它的文件。
  • 同名条目整条取第一个文件的，不按字段合并。 b2 里的 dup 有 namespace: from-b2，b1 里的没有；合并结果没有 namespace。同名 cluster shared 也一样，b2 里的 insecure-skip-tls-verify 没有被并进来。
  • 不重名的条目全部保留。

把顺序倒过来，dup 就换成 b2 的那一整条，连带指向了另一个地址：

$ export KUBECONFIG=b2.kubeconfig:b1.kubeconfig
$ kubectl config get-contexts; kubectl config view --minify --context dup -o jsonpath="{.clusters[0].cluster.server}"
CURRENT   NAME         CLUSTER   AUTHINFO   NAMESPACE
          dup          shared    u2         from-b2
          only-in-b1   shared    u1         
*         only-in-b2   shared    u2         
https://192.0.2.22:6443

这和官方文档的描述一致：第一个设置某个值或 map key 的文件胜出，之后的文件里同名条目即使有不冲突的字段也会被丢弃。实际中最常见的冲突是 cluster 和 user 名：很多工具生成的 kubeconfig 用 default、admin 这类通用名字，几份文件一合并，context 名都不一样，指向的 cluster 或 user 却悄悄变成了排在前面那份文件里的。合并后用 --minify --context <名字> 看一眼实际的 server 和 user，比只看 get-contexts 可靠。

改写落到哪个文件

kubectl config 的子命令会改文件。合并模式下它们写到哪里，逐个试，先把顺序换回 b1 在前：

$ export KUBECONFIG=b1.kubeconfig:b2.kubeconfig
$ kubectl config use-context only-in-b2; grep -H current-context b1.kubeconfig b2.kubeconfig
Switched to context "only-in-b2".
b1.kubeconfig:current-context: only-in-b2
b2.kubeconfig:current-context: only-in-b2
$ kubectl config set-context --current --namespace=ns-set
Context "only-in-b2" modified.
$ kubectl config set-context brand-new --cluster=shared --user=u2; grep -l brand-new b1.kubeconfig b2.kubeconfig
Context "brand-new" created.
b1.kubeconfig
$ kubectl config set-context dup --namespace=edited
Context "dup" modified.

改完后分别单独看两个文件：

$ KUBECONFIG=b1.kubeconfig kubectl config get-contexts; echo; KUBECONFIG=b2.kubeconfig kubectl config get-contexts
CURRENT   NAME         CLUSTER   AUTHINFO   NAMESPACE
          brand-new    shared    u2         
          dup          shared    u1         edited
          only-in-b1   shared    u1         

CURRENT   NAME         CLUSTER   AUTHINFO   NAMESPACE
          dup          shared    u2         from-b2
*         only-in-b2   shared    u2         ns-set
  • use-context 把 current-context 写进了 b1（b2 本来就是 only-in-b2，没变）。
  • 修改已有条目，写回定义它的那个文件：only-in-b2 的 namespace 改在 b2 里，dup 改的是 b1 里那条胜出的，b2 里被遮住的 dup 原样不动。
  • 新建条目也写进了 b1。

client-go 的 PathOptions.GetDefaultFilename 给出了这个「默认文件」的规则：KUBECONFIG 只有一个文件时就是它；有多个时，取列表里第一个存在的文件；链里的文件都不存在时，创建列表中的最后一个。current-context 和新条目都写到这个默认文件，已有条目则写回它的来源文件。

问题在于改写后的文件单独拿出来已经不自洽了。b1 的 current-context 指向一个只在 b2 里存在的 context，brand-new 引用的 user u2 也只在 b2 里：

$ KUBECONFIG=b1.kubeconfig kubectl config current-context; KUBECONFIG=b1.kubeconfig kubectl get pods
only-in-b2
Error in configuration: context was not found for specified context: only-in-b2
$ KUBECONFIG=b1.kubeconfig kubectl --context brand-new get pods --request-timeout=2s
Please enter Username: error: EOF

第二条最出人意料：找不到 user，kubectl 没有报错，而是进入交互模式要用户名（这里标准输入是空的，所以立刻 EOF）。在脚本或 CI 里，它就表现为一条卡住不动的命令。

unset current-context 在合并模式下不生效

$ export KUBECONFIG=b1.kubeconfig:b2.kubeconfig
$ kubectl config unset current-context; grep -H current-context b1.kubeconfig b2.kubeconfig; kubectl config current-context
Property "current-context" unset.
b1.kubeconfig:current-context: ""
b2.kubeconfig:current-context: only-in-b2
only-in-b2

unset 只把第一个文件的 current-context 清成空字符串，而空字符串不算「设置了」，合并时继续往后找，b2 的 only-in-b2 又顶上来了。想用「没有默认 context，强迫每条命令写 --context」这种做法，要保证列表里每个文件都没有 current-context。单独看 b1 时，没有 current-context 的后果和前面缺 cluster 一样，退回 localhost:8080：

$ KUBECONFIG=b1.kubeconfig kubectl config current-context; KUBECONFIG=b1.kubeconfig kubectl get pods
error: current-context is not set
E1013 18:41:26.597520 2149491 memcache.go:265] couldn't get current server API group list: Get "http://localhost:8080/api?timeout=32s": dial tcp 127.0.0.1:8080: connect: connection refused
...

命令行参数的优先级

kubeconfig 只提供默认值，命令行参数层层覆盖：

  • --kubeconfig 覆盖 KUBECONFIG，而且只读这一个文件、不合并：

    $ KUBECONFIG=a.kubeconfig kubectl --kubeconfig b2.kubeconfig config get-contexts -o name
dup
only-in-b2

    -o name 只输出名字，适合给脚本或补全用。

  • --context 覆盖 current-context，写错名字会直接报错，不会退回默认值：

    $ export KUBECONFIG=a.kubeconfig:reader.kubeconfig
$ kubectl --context nope get pods
Error in configuration: context was not found for specified context: nope

  • --user、--cluster 还能覆盖 context 里的单个字段。下面这条命令（仍是 KUBECONFIG=a.kubeconfig:reader.kubeconfig）名义上用的是只读 context，实际身份是管理员：

    $ kubectl --context a-reader --user kind-lab auth whoami
ATTRIBUTE   VALUE
Username    kubernetes-admin
Groups      [kubeadm:cluster-admins system:authenticated]

  • -n 覆盖 context 的 namespace。只读身份只在 notes-lab 有权限，-n kube-system 就没了：

    $ kubectl --context a-reader -n kube-system auth can-i list pods
no

所以「当前 context 是只读的」并不能保证命令是只读的，命令行上的 --user 能把它整个换掉。

rename-context 和 unset

kind 的 context 名是 kind-<集群名>，几个集群放在一起很难一眼区分。可以改名：

$ export KUBECONFIG=a.kubeconfig:reader.kubeconfig
$ kubectl config rename-context kind-lab a-admin; kubectl config get-contexts; grep -H current-context a.kubeconfig reader.kubeconfig
Context "kind-lab" renamed to "a-admin".
CURRENT   NAME       CLUSTER    AUTHINFO           NAMESPACE
*         a-admin    kind-lab   kind-lab           
          a-reader   kind-lab   notes-lab-reader   notes-lab
a.kubeconfig:current-context: a-admin
reader.kubeconfig:current-context: a-reader

改名时 current-context 跟着改了。只改 context 名，cluster 和 user 的名字不动，所以 a-reader 对 kind-lab 的引用不受影响。注意 kind 删除集群时按 kind-<集群名> 清理 kubeconfig，改过名的 context 推测不会被清掉，需要手动删。

unset 用点号路径删掉单个字段。删掉只读 context 的 namespace，命令就落到 default，权限立刻不够了：

$ kubectl config unset contexts.a-reader.namespace; kubectl --context a-reader get pods
Property "contexts.a-reader.namespace" unset.
Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:notes-lab:notes-lab-reader" cannot list resource "pods" in API group "" in the namespace "default"
$ kubectl config set-context a-reader --namespace=notes-lab; kubectl --context a-reader get pods
Context "a-reader" modified.
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          89s

写入前核对：看地址，不看名字

本地实验环境 里的检查函数按 context 名字放行 kind-*。名字是最不可靠的一项：任何人都能 rename-context，合并时同名条目还会被顶替。造一个冒名的 context，把 b2 的 only-in-b2 改名成和真集群一模一样的 kind-lab，再放到 KUBECONFIG 的最前面。改名只动 b2 的一份拷贝 c.kubeconfig（拷贝时 b2 已经被前面的实验改过，所以 context 上带着 ns-set）：

cp b2.kubeconfig c.kubeconfig
chmod 600 c.kubeconfig
$ KUBECONFIG=c.kubeconfig kubectl config rename-context only-in-b2 kind-lab
Context "only-in-b2" renamed to "kind-lab".

下面的检查改为核对 context 解析出来的 API Server 地址，通过后再用 auth whoami 打出 API Server 眼中的身份。把这段函数保存为 guard.sh：

# 允许写入的 API Server 地址，按自己的环境填写
KGUARD_ALLOW="https://<apiserver>"

kguard() {
  local ctx ns server user
  ctx=${KCTX:-$(kubectl config current-context)} || return 1
  ns=$(kubectl config view --minify --context "$ctx" -o jsonpath='{..namespace}')
  server=$(kubectl config view --minify --context "$ctx" -o jsonpath='{.clusters[0].cluster.server}')
  echo "→ context=$ctx namespace=${ns:-default} server=$server" >&2
  case " $KGUARD_ALLOW " in
    *" $server "*) ;;
    *) echo "拒绝：$server 不在允许列表里" >&2; return 1 ;;
  esac
  user=$(kubectl --context "$ctx" auth whoami -o jsonpath='{.status.userInfo.username}') || return 1
  echo "→ user=$user" >&2
}

kw() { kguard && kubectl ${KCTX:+--context=$KCTX} "$@"; }

写入命令用 kw 代替 kubectl。三种情况：

$ export KUBECONFIG=a.kubeconfig:reader.kubeconfig; source guard.sh
$ kw -n notes-lab create configmap via-admin --from-literal=k=v
→ context=a-admin namespace=default server=https://<apiserver>
→ user=kubernetes-admin
configmap/via-admin created

$ KCTX=a-reader kw create configmap via-reader --from-literal=k=v
→ context=a-reader namespace=notes-lab server=https://<apiserver>
→ user=system:serviceaccount:notes-lab:notes-lab-reader
error: failed to create configmap: configmaps is forbidden: User "system:serviceaccount:notes-lab:notes-lab-reader" cannot create resource "configmaps" in API group "" in the namespace "notes-lab"

$ export KUBECONFIG=c.kubeconfig:a.kubeconfig:reader.kubeconfig
$ kubectl config get-contexts
CURRENT   NAME       CLUSTER    AUTHINFO           NAMESPACE
          a-admin    kind-lab   kind-lab           
          a-reader   kind-lab   notes-lab-reader   notes-lab
          dup        shared     u2                 from-b2
*         kind-lab   shared     u2                 ns-set
$ kw -n notes-lab create configmap lookalike --from-literal=k=v
→ context=kind-lab namespace=ns-set server=https://192.0.2.22:6443
拒绝：https://192.0.2.22:6443 不在允许列表里

第三种情况下，名字叫 kind-lab、排在 current-context 位置上的 context 其实指向另一个地址，按名字放行的检查会被骗过去，按地址的检查拦住了它。第二种说明 auth whoami 那一行的价值：同一个地址，打出来的身份不同，写入的结果也不同。

这个检查还有两处看不到的东西。一是第一条输出里显示的是 namespace=default，因为它读的是 context 上的 namespace，看不到命令参数里的 -n notes-lab；二是它同样看不到 --user 这类覆盖参数。要可靠，就约定写入命令一律通过 kw 并显式带 --context 和 -n。另外，API Server 地址也不是绝对唯一的，kind 集群重建后端口会变，本机端口也可能被别的集群复用，所以允许列表要跟着集群生命周期维护。

exec 凭据插件

kind 的 kubeconfig 用的是内联的客户端证书（前面 config view 里的 client-certificate-data / client-key-data）。云厂商的托管集群更常见的是 exec 凭据插件：kubeconfig 里不放凭据，而是写一条命令，kubectl 每次需要凭据时执行它，从标准输出读一个 ExecCredential JSON。为了看清这个机制，写一个最小的插件，把前面那个只读 token 包一层。第一次把它保存为和 kubeconfig 同目录的 token-plugin.sh，读的是同目录下的 reader.token：

#!/bin/sh
# 演示用 exec 凭据插件：从文件读 token，按 ExecCredential 格式输出
echo "plugin called at $(date +%T), KUBERNETES_EXEC_INFO=$KUBERNETES_EXEC_INFO" >> "$(dirname "$0")/plugin.log"
printf '{"apiVersion":"client.authentication.k8s.io/v1","kind":"ExecCredential","status":{"token":"%s"}}\n' "$(cat "$(dirname "$0")/reader.token")"
chmod 700 token-plugin.sh   # 至少要有执行权限；它会读出 token，所以只给自己

用绝对路径配置：

export KUBECONFIG=exec.kubeconfig
kubectl config set-credentials reader-exec --exec-api-version=client.authentication.k8s.io/v1 \
  --exec-command="$PWD/token-plugin.sh" --exec-env=DEMO_SECRET=not-really-secret --exec-interactive-mode=Never
kubectl config set-context a-exec --cluster=kind-lab --user=reader-exec --namespace=notes-lab
$ export KUBECONFIG=a.kubeconfig:exec.kubeconfig
$ kubectl --context a-exec auth whoami
Unable to connect to the server: getting credentials: exec: executable token-plugin.sh not found

It looks like you are trying to use a client-go credential plugin that is not installed.

To learn more about this feature, consult the documentation available at:
      https://kubernetes.io/docs/reference/access-authn-authz/authentication/#client-go-credential-plugins
$ grep -n "command:" exec.kubeconfig
18:      command: token-plugin.sh

原因在 client-go 的 clientcmd/loader.go 里。kubectl 把用户写回文件前，会调用 RelativizePathWithNoBacksteps，把其中的文件路径改写成相对 kubeconfig 所在目录的路径；插件和 kubeconfig 同目录，结果就是一个不带斜杠的裸文件名 token-plugin.sh。读取时，GetAuthInfoFileReferences 只把含路径分隔符的 exec.command 当作文件路径、按 kubeconfig 目录解析（源码注释是 Only resolve exec command if it isn’t PATH based），不带斜杠的名字原样交给执行器，于是去 PATH 里找，找不到就报 not found。传 --exec-command=./token-plugin.sh 同样会被改写成裸名字，kubectl config set 又改不了 exec 下的字段。对策有两个：把插件放进 kubeconfig 目录下的子目录，存下来的是 bin/token-plugin.sh，带斜杠，能按目录解析；或者把插件放进 PATH，直接用命令名配置。这里用第一种，把插件挪到 bin/。挪进子目录后，脚本里找 plugin.log 和 reader.token 的路径要多加一层 ../（这两个文件仍在 kubeconfig 所在目录，$(dirname "$0")/../ 依赖插件就放在 bin/ 下），然后用新路径重新配置：

mkdir bin
sed 's#"$(dirname "$0")/reader.token"#"$(dirname "$0")/../reader.token"#; s#"$(dirname "$0")/plugin.log"#"$(dirname "$0")/../plugin.log"#' token-plugin.sh > bin/token-plugin.sh
chmod 700 bin/token-plugin.sh && rm token-plugin.sh
export KUBECONFIG=exec.kubeconfig
kubectl config set-credentials reader-exec --exec-command="$PWD/bin/token-plugin.sh"
grep -n "command:" exec.kubeconfig    # 18:      command: bin/token-plugin.sh
$ export KUBECONFIG=a.kubeconfig:exec.kubeconfig
$ kubectl --context a-exec auth whoami; kubectl --context a-exec get pods; cat plugin.log
ATTRIBUTE                                           VALUE
Username                                            system:serviceaccount:notes-lab:notes-lab-reader
...
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          2m43s
plugin called at 18:42:40, KUBERNETES_EXEC_INFO={"kind":"ExecCredential","apiVersion":"client.authentication.k8s.io/v1","spec":{"interactive":false}}

plugin called at 18:42:40, KUBERNETES_EXEC_INFO={"kind":"ExecCredential","apiVersion":"client.authentication.k8s.io/v1","spec":{"interactive":false}}

两条 kubectl 命令，插件被调用了两次。插件输出里没有 expirationTimestamp，按文档，凭据只缓存到进程退出或收到 401，每个 kubectl 进程都要重新执行一次插件。KUBERNETES_EXEC_INFO 里的 interactive: false 来自 interactiveMode: Never，插件据此判断能不能向用户要输入（比如弹浏览器登录）。

再看 config view 怎么显示这个用户：

$ KUBECONFIG=exec.kubeconfig kubectl config view

- name: reader-exec
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1
      args: null
      command: token-plugin.sh
      env:
      - name: DEMO_SECRET
        value: not-really-secret
      interactiveMode: Never

（这是挪目录之前的输出。）exec 的 env 和 args 不会被打码。有些插件的配置习惯把 client secret、访问密钥放在 env 里，这种 kubeconfig 即使不加 --raw，config view 的输出也会把它们原样带出来。

exec 机制也是官方文档那句「只使用可信来源的 kubeconfig」的原因：kubeconfig 里的 command 会在你的机器上以你的身份执行。拿到别人给的 kubeconfig，先看一遍里面有没有 exec、command 指向哪里。

token 到期之后

token 的 exp 是 18:50:09。下面这个脚本等到 18:49:40 后，用只读 context 跑 8 次 get pods，每次之间 sleep 10（kubectl 本身只花不到 1 秒，所以输出的时间戳正好相隔 10 秒）：

export KUBECONFIG=a.kubeconfig:reader.kubeconfig:exec.kubeconfig
while [ "$(date +%H%M%S)" -lt 184940 ]; do sleep 5; done   # 按自己 token 的 exp 减 30 秒填
for i in 1 2 3 4 5 6 7 8; do
  echo "== $(date '+%T')"
  kubectl --context a-reader get pods 2>&1
  sleep 10
done > expiry.log 2>&1

8 次跑完是 18:50:51，token 仍然有效。于是又手动起了一个同样每 10 秒一次、遇到 Unauthorized 就停的循环，它的第一次请求在 18:51:14：

export KUBECONFIG=a.kubeconfig:reader.kubeconfig
for i in $(seq 1 30); do echo "== $(date '+%T')"; out=$(kubectl --context a-reader get pods 2>&1); echo "$out"; echo "$out" | grep -q Unauthorized && break; sleep 10; done | tee expiry2.log | tail -8

两段输出拼在一起：

== 18:49:41
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          9m44s
== 18:49:51
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          9m54s
== 18:50:01
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          10m
== 18:50:11
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          10m

== 18:50:51
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          10m
== 18:51:14
error: You must be logged in to the server (Unauthorized)

过了 exp 之后 token 又多用了至少 42 秒。由于两段循环之间有个空档，实测的失效点只能确定落在 exp 之后 (42s, 65s] 这个区间。这和源码对得上：v1.31 的 pkg/serviceaccount/claims.go 用 go-jose 的 Claims.Validate 校验 exp，而 go-jose v2 的 Validate 默认带 DefaultLeeway，也就是 1 分钟的时钟偏差余量，所以 token 要到 exp + 60s（18:51:09）才会被判过期。另外，kube-apiserver 会把认证成功的结果缓存 10 秒（pkg/kubeapiserver/options/authentication.go 里 TokenSuccessCacheTTL 默认 10 * time.Second，在 pkg/kubeapiserver/authenticator/config.go 里包在 token 认证器外层），一个快到 exp + 60s 时成功过的 token，最多还能再多用 10 秒。所以「10 分钟 token」实际能用 11 分钟左右，不要拿 exp 卡秒级的安全边界。

过期后报的是 Unauthorized（401），和前面权限不够时的 Forbidden（403）是两回事：401 是「不认识你」，凭据过期、被吊销、根本不对都是这个；403 是「认识你，但你没这个权限」。auth whoami 在过期后也只会报同一句 401，看不出原因，这时先确认 token 的签发时间和有效期：

$ export KUBECONFIG=a.kubeconfig:reader.kubeconfig
$ kubectl --context a-reader auth whoami; kubectl --context a-reader auth can-i get pods
error: You must be logged in to the server (Unauthorized)
error: You must be logged in to the server (Unauthorized)

走 exec 插件的那个 context 用的是同一个 token，也失败了。先清空插件日志再跑一次，插件在一条命令里被调用了两次：

$ : > plugin.log
$ export KUBECONFIG=a.kubeconfig:exec.kubeconfig
$ kubectl --context a-exec get pods; cat plugin.log
error: You must be logged in to the server (Unauthorized)
plugin called at 18:51:27, KUBERNETES_EXEC_INFO={"kind":"ExecCredential","apiVersion":"client.authentication.k8s.io/v1","spec":{"interactive":false}}

plugin called at 18:51:27, KUBERNETES_EXEC_INFO={"kind":"ExecCredential","apiVersion":"client.authentication.k8s.io/v1","spec":{"interactive":false}}

之前成功时是一条命令一次，这里收到 401 后又执行了一次插件，推测就是文档说的「收到 401 时丢弃缓存的凭据」后重新取了一次。真实的插件在这一步会去刷新 token，所以云厂商的 exec 插件一般感觉不到过期；静态 token 写死在 kubeconfig 里就只能手工换。

不等过期，也能让 token 提前失效。重新签一个 10 分钟的 token，写回 reader.kubeconfig，确认可用后删掉 ServiceAccount：

KUBECONFIG=a.kubeconfig kubectl -n notes-lab create token notes-lab-reader --duration=10m > reader.token
KUBECONFIG=reader.kubeconfig kubectl config set-credentials notes-lab-reader --token="$(cat reader.token)" >/dev/null
$ export KUBECONFIG=a.kubeconfig:reader.kubeconfig
$ kubectl --context a-reader get pods
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          11m
$ kubectl --context a-admin -n notes-lab delete serviceaccount notes-lab-reader; kubectl --context a-reader get pods; sleep 15; date +%T; kubectl --context a-reader get pods
serviceaccount "notes-lab-reader" deleted
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          11m
18:51:49
error: You must be logged in to the server (Unauthorized)

删除后紧接着的那条请求仍然成功了，15 秒后再请求已是 401。最可能的原因是上面那个 10 秒的认证成功缓存（推测）：删除前那次 get pods 用同一个 token 认证成功，结果被缓存，删除后的请求直接命中缓存，没有再去检查 ServiceAccount 是否存在。另一种可能是 claims.go 查 ServiceAccount 时读的是 informer 缓存，删除事件还没同步过来；这次的数据分不出是哪一种。再建一个同名的 ServiceAccount，旧 token 依然无效，因为 token 里绑定的是旧对象的 UID（前面 claims 里的 uid），新对象的 UID 已经变了：

$ kubectl --context a-admin -n notes-lab create serviceaccount notes-lab-reader; sleep 12; kubectl --context a-reader get pods; kubectl --context a-admin -n notes-lab get sa notes-lab-reader -o jsonpath="{.metadata.uid}"
serviceaccount/notes-lab-reader created
error: You must be logged in to the server (Unauthorized)
541176e9-26d0-41db-a39a-e18cdfed6515

新对象的 UID 是 541176e9-...，token 里记的还是 396b1de9-...。

这也是 create token 签发的 token 比客户端证书好处理的地方：泄露了可以删对象作废，最坏也就是等它过期。

别把 –raw 贴进工单

kubectl config view --raw（或者直接 cat ~/.kube/config）的输出里有什么，按本文这几种用户逐项说，这里不贴实际内容：

  • 客户端证书的私钥（client-key-data）。kind 这张是 kubeadm:cluster-admins 组的证书，相当于整个集群的管理员，有效期到 2027 年 8 月。官方文档明确写着 Kubernetes 不支持证书吊销，签出去的证书在过期前一直有效；泄露后能做的只有轮换签发它的 CA，或者在 RBAC 里删掉这个组的绑定。后一条之所以可行，是因为 kubeadm 的 admin.conf 用的是 kubeadm:cluster-admins 组，权限来自一条普通的 ClusterRoleBinding；而 super-admin.conf 里那张 system:masters 证书会绕过授权层，泄露了连这一招都没有。
  • bearer token（token）。像本文这种 create token 签发的短期 token，泄露窗口就是剩余有效期；而旧式的 Secret 型 ServiceAccount token 本身没有 exp，只能删 Secret 来作废；不过自 v1.30 起（LegacyServiceAccountTokenCleanUp 进入 GA），自动生成的这类 token 长期不用（默认一年）会被控制器标记为失效，再过一段时间被清理。
  • exec 插件的 env 和 args，上一节看到即使不加 --raw 也会显示。
  • API Server 地址、集群和用户名。不算凭据，但会暴露内部域名、IP 和集群规划。

需要别人帮忙看 kubeconfig 时，贴 kubectl config view --minify（不加 --raw、不加 --flatten），并且检查一遍 exec 部分。

文件权限方面，kubectl 对宽松的权限不会提示。拷一份只含占位 token 的 b2，改成所有人可读，照样静默读取：

$ cp b2.kubeconfig loose.kubeconfig; chmod 644 loose.kubeconfig
$ ls -l loose.kubeconfig; KUBECONFIG=loose.kubeconfig kubectl config get-contexts -o name
-rw-r--r-- 1 user user 405 Oct 13 18:41 loose.kubeconfig
dup
only-in-b2

所以权限要自己把关：带凭据的 kubeconfig 用 600，导出前先 umask 077，用完删掉 --flatten 导出的副本。

清理

export KUBECONFIG=a.kubeconfig
kubectl delete namespace notes-lab --wait
rm -f a.kubeconfig reader.kubeconfig reader.token exec.kubeconfig b1.kubeconfig b2.kubeconfig c.kubeconfig loose.kubeconfig plugin.log
rm -rf bin
unset KUBECONFIG

ServiceAccount、Role、RoleBinding 都在 namespace 里，删 namespace 时一起删掉；ServiceAccount 被删后，用它签发的 token 也就不能再用了。临时 kubeconfig 里 a.kubeconfig 带着管理员私钥，一定要删。
