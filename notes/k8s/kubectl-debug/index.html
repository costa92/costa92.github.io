应用镜像没有 shell 时怎么办

在 kubectl 常用命令 里，kubectl exec 是进容器排查的首选。但越来越多的镜像基于 distroless 或 scratch 构建，里面只有一个静态二进制，sh、ls、ps 都没有。kubectl debug 的做法是往正在运行的 Pod 里加一个临时容器（ephemeral container），用你自己选的工具镜像，和应用容器共享网络，必要时还能共享进程视图。应用镜像不用改，Pod 也不用重建。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），kubectl 客户端是 v1.30.0。实验放在单独的 notes-lab namespace 里。为便于阅读，节点名简化成了 worker，Pod IP 用 <pod-ip> 代替。客户端版本在这一篇里很重要，后面会看到，--profile 的默认值随 kubectl 版本变过。

一个真正没有 shell 的 Pod

目标镜像用 traefik/whoami:v1.10.2，它是从 scratch 构建的，镜像里只有 /whoami 这个二进制，监听 80 端口，收到 HTTP 请求就回显主机名和 IP。

apiVersion: v1
kind: Pod
metadata:
  name: app
  labels:
    app: app
spec:
  containers:
    - name: whoami
      image: traefik/whoami:v1.10.2
      ports:
        - containerPort: 80
      resources:
        requests:
          cpu: 20m
          memory: 16Mi
        limits:
          memory: 32Mi

exec 进不去，ls 也一样：

$ kubectl -n notes-lab exec app -- sh
error: Internal error occurred: Internal error occurred: error executing command in container: failed to exec in container: failed to start exec "00e79815e62e...": OCI runtime exec failed: exec failed: unable to start container process: exec: "sh": executable file not found in $PATH: unknown

报错的关键是最后的 executable file not found in $PATH。这是镜像里没有这个程序，和 Pod 健康与否无关，Pod 此时是 1/1 Running。

加一个临时容器：不带 –target

先不指定目标容器。为了让输出能留档，这里没用 -it，而是让调试容器跑一串命令就退出，再用 kubectl logs -c 读它的输出：

kubectl -n notes-lab debug app --image=busybox:1.36 --container=dbg-notarget -- \
  sh -c "hostname; echo ---; ps; echo ---; netstat -tln; echo ---; wget -qO- http://localhost:80 | head -3; echo ---; ls /proc/1/root/ 2>&1 | head"
kubectl -n notes-lab logs app -c dbg-notarget

这一组输出把「共享什么、不共享什么」分得很清楚：

  • 网络是共享的。netstat 看到了 whoami 监听的 :::80，wget localhost:80 拿到了 whoami 的回显。临时容器和应用容器在同一个网络命名空间里，所以排查 DNS、连通性、端口监听，不需要 --target。
  • 进程不共享。ps 里只有调试容器自己的 sh 和 ps，PID 1 是 sh，看不到 /whoami。/proc/1/root/ 列出的 bin、home、lib 也是 busybox 自己的根文件系统。

所以在这种模式下 ps 里看不到应用进程，不能据此判断应用已经退出了。

加上 –target：进入应用的进程命名空间

kubectl -n notes-lab debug app --image=busybox:1.36 --target=whoami --container=dbg-target -- \
  sh -c 'ps; echo ---; ls -l /proc/1/exe; echo ---; ls /proc/1/root/; echo ---; cat /proc/1/cmdline | tr "\0" " "; echo; echo ---; id; ls /proc/1/root/ >/dev/null && echo root-ok'
kubectl -n notes-lab logs app -c dbg-target

这次 PID 1 是 /whoami，调试容器加入了目标容器的 PID 命名空间。更有用的是 /proc/1/root/：它现在列出的是 whoami 镜像的根文件系统（只有 whoami 二进制和几个目录），这就是在无 shell 镜像里查看配置文件、证书的入口，比如 cat /proc/1/root/etc/...。调试容器自己的 / 仍然是 busybox，工具照常可用。

kubectl 打印的那句提示是说，进程命名空间共享依赖容器运行时支持。containerd 1.7 下实测是支持的。

临时容器加上去就删不掉

两次调试之后看 Pod 的 spec。临时容器在 spec.ephemeralContainers 里，带了 --target 的那个多一个 targetContainerName：

$ kubectl -n notes-lab get pod app -o yaml
  ephemeralContainers:
  - command:
    - sh
    - -c
    - hostname; echo ---; ps; echo ---; netstat -tln; echo ---; wget -qO- http://localhost:80
      | head -3; echo ---; ls /proc/1/root/ 2>&1 | head
    image: busybox:1.36
    imagePullPolicy: IfNotPresent
    name: dbg-notarget
    resources: {}
    terminationMessagePath: /dev/termination-log
    terminationMessagePolicy: File
  - command:
    ...
    name: dbg-target
    resources: {}
    targetContainerName: whoami

describe 里有一个单独的 Ephemeral Containers: 段，状态、退出码和普通容器一样：

Ephemeral Containers:
  dbg-notarget:
    Container ID:  containerd://dedae91b5505...
    Image:         busybox:1.36
    ...
    State:          Terminated
      Reason:       Completed
      Exit Code:    0
      Started:      Mon, 12 Oct 2026 16:33:11 +0800
      Finished:     Mon, 12 Oct 2026 16:33:12 +0800
    Ready:          False
    Restart Count:  0

而 kubectl get pod 完全看不出来。实验后期这个 Pod 身上已经挂了 8 个临时容器，get pod 显示的仍然是 1/1 Running、重启 0 次。

接下来试着把它们弄掉。直接 patch Pod 删第一个：

$ kubectl -n notes-lab patch pod app --type=json -p '[{"op":"remove","path":"/spec/ephemeralContainers/0"}]'
The Pod "app" is invalid: spec: Forbidden: pod updates may not change fields other than `spec.containers[*].image`,`spec.initContainers[*].image`,`spec.activeDeadlineSeconds`,`spec.tolerations` (only additions to existing tolerations),`spec.terminationGracePeriodSeconds` (allow it to be set to 1 if it was previously negative)

普通的 Pod 更新压根不能动这个字段。临时容器要通过专门的 ephemeralcontainers 子资源写入（kubectl debug 就是 PATCH .../pods/app/ephemeralcontainers），也正因为如此，用 kubectl edit 加不了临时容器。那就走子资源：用 kubectl get pod app -o json 导出整个 Pod，删掉 spec.ephemeralContainers 里的第一项，存成 remove-one.json，再整体提交给 ephemeralcontainers 子资源：

$ kubectl replace --raw /api/v1/namespaces/notes-lab/pods/app/ephemeralcontainers -f remove-one.json
The Pod "app" is invalid: spec.ephemeralContainers: Forbidden: existing ephemeral containers "dbg-target" may not be removed

这次被明确拒绝：已有的临时容器不能删除。另外用同样的方法单独发了一个请求，对象是后文 PodSecurity 一节用到的 app-psa 这个 Pod：在它的列表末尾追加一个带 ports 和 resources 的临时容器，也被拒：

The Pod "app-psa" is invalid: 
* spec.ephemeralContainers[1].ports: Forbidden: cannot be set for an Ephemeral Container
* spec.ephemeralContainers[1].resources: Forbidden: cannot be set for an Ephemeral Container

临时容器不能声明端口、探针和资源。它占用的 CPU 和内存不计入任何 request，也就没有任何保证。推测它和应用容器跑在同一个 Pod cgroup 里、共用 Pod 的内存上限（这里的 whoami 只有 32Mi），在调试容器里跑占内存的工具，可能把应用一起拖进 OOM，这次没有验证。

重名：退出码 0，什么都没发生

用一个已经存在的名字再调试一次：

$ kubectl -n notes-lab debug app --image=busybox:1.36 --container=dbg-target -- true; echo "exit=$?"
exit=0

没有报错，退出码是 0，但 Pod 里没有新容器，dbg-target 的命令也还是原来那条。开 -v=6 能看到 kubectl 确实发出了 PATCH .../pods/app/ephemeralcontainers，服务端回的是 200 OK；-v=8 打出的请求体里，dbg-target 在 $setElementOrder 中出现了两次。推测是策略合并补丁按 name 合并后服务端认为没有变化，这一点没有再往下追。实际影响是：脚本里固定用 --container=xxx 反复调试，第二次起会静默失效，不指定 --container 让 kubectl 自动生成 debugger-xxxxx 名字更稳。

不重启，也连不回去

交互式的用法才是日常最常见的。退出 shell 时 kubectl 会打印一行提示：

$ kubectl -n notes-lab debug -it app --image=busybox:1.36 --target=whoami --container=dbg-tty -- sh
Targeting container "whoami". If you don't see processes from this container it may be because the container runtime doesn't support this feature.
If you don't see a command prompt, try pressing enter.
/ # hostname
app
/ # ps -o pid,args
PID   COMMAND
    1 /whoami
  163 sh
  176 ps -o pid,args
/ # exit
Session ended, the ephemeral container will not be restarted but may be reattached using 'kubectl attach app -c dbg-tty -i -t' if it is still running

exit 结束的是容器的主进程，容器随之退出（Completed，退出码 0），之后 attach 就只剩报错：

$ kubectl -n notes-lab attach app -c dbg-tty -i -t
If you don't see a command prompt, try pressing enter.
error: Internal error occurred: unable to upgrade connection: container dbg-tty not found in pod app_notes-lab

报错写的是 not found，而不是「已退出」，容易让人以为名字敲错了。exit 之后这个容器就没用了，想继续调试只能再加一个新的临时容器。

还有个小坑：不带 -t、只用 -i 从管道喂命令时，这次实验里命令输出没有回显到终端（只打印了 Targeting container 和 If you don't see a command prompt 两行提示），输出全进了容器日志（kubectl logs app -c dbg-i 里能看到）。命令是在 4 秒后才送进去的，也确实执行了，原因未查明。要在脚本里拿结果，像前面那样不带 -i、事后读 logs -c 更可靠。

–profile：六种配置实际给了什么

kubectl debug 用 --profile 决定调试容器的 securityContext。对同一个 Pod 分别用六种配置各加一个临时容器，读出 spec 里实际写入的内容：

p-legacy	
p-general	{"capabilities":{"add":["SYS_PTRACE"]}}
p-baseline	
p-restricted	{"allowPrivilegeEscalation":false,"capabilities":{"drop":["ALL"]},"runAsNonRoot":true,"seccompProfile":{"type":"RuntimeDefault"}}
p-netadmin	{"capabilities":{"add":["NET_ADMIN","NET_RAW"]}}
p-sysadmin	{"privileged":true}

每个容器里跑 grep CapEff /proc/self/status，并试着建一块 dummy 网卡（ip link add dummy0 type dummy）：

profileCapEff相对 containerd 默认多出的能力建网卡/dev 条目数
legacy00000000a80425fb无Operation not permitted16
general00000000a80c25fbSYS_PTRACEOperation not permitted16
baseline00000000a80425fb无Operation not permitted16
netadmin00000000a80435fbNET_ADMIN成功16
sysadmin000001ffffffffff全部成功253
restricted没有启动———

a80425fb 是 containerd 给容器的默认能力集（CHOWN、DAC_OVERRIDE、NET_RAW、SYS_CHROOT 等 14 项）。netadmin 虽然在 spec 里写了 NET_ADMIN 和 NET_RAW，但 NET_RAW 本来就在默认集里，所以实际只多了一位。sysadmin 是特权容器，能力全开，还能看到宿主机的全部设备节点。

legacy 和 baseline 在临时容器场景下结果完全一样。按 kubectl 源码，baseline 会先清空调试容器的 securityContext，而 legacy 本来就什么都不设，区别要到 --copy-to 和节点调试时才显现。

restricted 那个没有启动：

p-restricted	{"waiting":{"message":"container has runAsNonRoot and image will run as root (pod: \"app_notes-lab(9a6f38f2-...)\", container: p-restricted)","reason":"CreateContainerConfigError"}}

restricted 只设了 runAsNonRoot: true，没设具体用户；busybox 镜像默认是 root，于是 kubelet 拒绝创建。这个容器停在 CreateContainerConfigError，几分钟后再看仍然是 restartCount=0，不会重试，只能另起一个。后面 PodSecurity 那节会看到它在什么条件下能跑起来。

SYS_PTRACE 到底管什么

从上面的表看，general 只比 legacy 多一个 SYS_PTRACE，而在 app 这个 Pod 里，legacy 也能 ps、也能读 /proc/1/root。这是因为调试容器和 whoami 都以 root 运行，UID 相同，内核的 ptrace 访问检查直接放行。

让应用换个 UID 跑就不一样了。只在容器级设置 runAsUser: 65532，再加一个演示用的环境变量：

- name: whoami
  image: traefik/whoami:v1.10.2
  args: ["--port", "8080"]
  env:
    - name: DEMO_TOKEN
      value: "not-a-real-secret"
  securityContext:
    runAsUser: 65532

baseline（legacy 结果相同）：

uid=0(root) gid=0(root) groups=0(root),10(wheel)
PID   USER     COMMAND
    1 65532    /whoami --port 8080
ls: /proc/1/root/: Permission denied
sh: can't open /proc/1/environ: Permission denied

general：

uid=0(root) gid=0(root) groups=0(root),10(wheel)
PID   USER     COMMAND
    1 65532    /whoami --port 8080
dev
etc
DEMO_TOKEN=not-a-real-secret

调试容器是 root，却读不到一个普通用户进程的根文件系统和环境变量：UID 不同时，访问 /proc/<pid>/root、environ 需要 CAP_SYS_PTRACE。ps 两边都能用，因为 /proc/<pid>/cmdline 对所有人可读。所以当你看到 Permission denied 时，先看目标进程的 UID 和调试容器的 profile，换成 --profile=general 通常就能解决。

另一面是：general 下环境变量里的密钥一眼可见。谁有权更新 pods/ephemeralcontainers 子资源，谁就能读到 Pod 里的这些东西。生产集群应该像对待 pods/exec 一样收紧这个权限，见 RBAC。

Pod 级 securityContext 会被继承

如果把 runAsUser: 65532 写在 Pod 级 spec.securityContext 里，结果又不同。同样的命令，legacy 下：

uid=65532 gid=0(root) groups=0(root)
PID   USER     COMMAND
    1 65532    /whoami --port 8080
   17 65532    sh -c id; ps -o pid,user,args | head -3; ls /proc/1/root/ 2>&1 | head -2; tr "\0" "\n" < /proc/1/environ 2>&1 | grep -E "DEMO|denied"
dev
etc
DEMO_TOKEN=not-a-real-secret

调试容器自己也变成了 65532。Pod 级的 securityContext 对临时容器同样生效，于是两边 UID 相同，不需要 SYS_PTRACE 也能看到全部内容；反过来，需要 root 才能做的事（比如装包、改网络）在这种 Pod 里调试容器也做不了。

–copy-to：复制一个 Pod 来改

临时容器只能「加」，不能改已有容器。要换命令、换镜像，就得用 --copy-to 复制出一个新 Pod，原 Pod 不受影响。

share-processes 的默认值和帮助文档不一致

帮助里写着 --share-processes=true。照这个理解，复制出来的 Pod 应该共享进程命名空间：

kubectl -n notes-lab debug app --copy-to=app-copy --image=busybox:1.36 --container=dbg -- sleep 3600
shareProcessNamespace=
containers=whoami dbg
ephemeral=
labels=
PID   USER     TIME  COMMAND
    1 root      0:00 sleep 3600
   13 root      0:00 ps

shareProcessNamespace 是空的，dbg 容器里看不到 whoami。把参数显式写出来（--share-processes=true），或者改用 --profile=general，结果才符合预期：

shareProcessNamespace=true dbg.securityContext=
PID   USER     TIME  COMMAND
    1 65535     0:00 /pause
    7 root      0:00 /whoami
   23 root      0:00 sleep 3600
   35 root      0:00 ps

查了 kubectl v1.30 的源码：复制 Pod 时只有在命令行显式传了 --share-processes 才会设置这个字段（change ShareProcessNamespace configuration only when commanded explicitly）；general、baseline、restricted、netadmin、sysadmin 这几个 profile 会主动打开它，唯独 legacy「对复制出的 Pod 什么都不做」。帮助里的 =true 只是变量初值。

共享进程命名空间后，PID 1 变成了 pause 容器，应用进程不再是 PID 1。前面那种 /proc/1/root 的写法要换成 /proc/$(pidof whoami)/root。

同一组输出里还能看到另外两件事：复制品没有任何标签，所以不会被原来的 Service 选中，不会接到线上流量；原 Pod 上的临时容器也不会被复制过去。v1.30 源码中，去标签和 profile 无关，复制时 metadata 只带上了 annotations。

给 CrashLoopBackOff 的 Pod 换个命令

模拟一个启动时找不到配置文件就退出的程序，带一个存活探针：

- name: app
  image: busybox:1.36
  command: ["sh", "-c", "test -f /etc/app/app.conf || { echo 'fatal: /etc/app/app.conf not found' >&2; exit 2; }; sleep 3600"]
  livenessProbe:
    exec:
      command: ["true"]
NAME    READY   STATUS             RESTARTS      AGE
crash   0/1     CrashLoopBackOff   2 (23s ago)   58s

这种 Pod 恰恰是临时容器帮不上忙的场景。带 --target 加一个调试容器：

dbg {"waiting":{"message":"invalid target container: container \"7d13fb27cef6...\" is not running - in state CONTAINER_EXITED","reason":"RunContainerError"}}

目标容器这一刻正处于退出状态，进程命名空间无从加入，调试容器启动失败，而且不会重试。不带 --target 推测能起来，但应用进程本来就活不过一秒，能看的也只有网络环境，这次没有试。

正确的做法是复制一份，把应用容器的命令换成 sleep，让它活下来再进去看。--container 指向已有的容器名、后面跟命令时，修改的就是这个容器的命令：

kubectl -n notes-lab debug crash --copy-to=crash-debug --container=app -- sleep 3600
NAME          READY   STATUS             RESTARTS      AGE
crash         0/1     CrashLoopBackOff   3 (36s ago)   95s
crash-debug   1/1     Running            0             3s
$ kubectl -n notes-lab exec crash-debug -c app -- ls -la /etc/app
ls: /etc/app: No such file or directory

原 Pod 继续崩溃，复制品稳定运行，可以在和原容器相同的镜像、环境变量、挂载下慢慢排查。

但要注意存活探针。legacy 下复制品保留了原来的探针：

command=["sleep","3600"]
livenessProbe={"exec":{"command":["true"]},"failureThreshold":3,"periodSeconds":10,"successThreshold":1,"timeoutSeconds":1}
labels=

这次的探针是 true，无论如何都能通过。如果原来的探针是对应用端口发 HTTP 请求，改成 sleep 之后探针必然失败，复制品会被 kubelet 反复重启（这一点是推测，这次没有专门复现）。用 --profile=general 复制时，探针被去掉了。v1.30 源码中，只有 general 和 baseline 会去掉存活探针，restricted、netadmin、sysadmin 都会保留。新版本改了这套逻辑：从 1.31 起，复制时先保留原 Pod 的标签，再交给 profile 去掉，并新增了 --keep-labels、--keep-annotations、--keep-liveness、--keep-readiness、--keep-startup、--keep-init-containers。在 1.33 和 1.36 的源码里，legacy 之外的所有 profile 都会去掉标签、注解和探针，legacy 只去标签。下面是 v1.30 客户端用 general 复制的结果：

livenessProbe=
shareProcessNamespace=true
securityContext={"capabilities":{"add":["SYS_PTRACE"]}}

用 –set-image 换镜像

把镜像标签写错，Pod 卡在 ErrImagePull，然后复制一份并修正镜像：

kubectl -n notes-lab debug badimg --copy-to=badimg-fixed --set-image=whoami=traefik/whoami:v1.10.2
NAME           IMAGE                         READY
badimg         traefik/whoami:v1.10.2-typo   false
badimg-fixed   traefik/whoami:v1.10.2        true

--set-image 的语法和 kubectl set image 一样，容器名=镜像。更常见的用法是把无 shell 的镜像整个换成带工具的：--set-image='*=busybox:1.36'。这里有个坑：

NAME          READY   STATUS             RESTARTS      AGE
badimg-star   0/1     CrashLoopBackOff   1 (21s ago)   26s

原 Pod 没写 command，换镜像后跑的是 busybox 镜像默认的 sh，没有终端输入就立刻退出，复制品自己也进了 CrashLoopBackOff。要么给它一个不会退出的命令，要么附加上去交互。按 v1.30 源码，只加 -it 时 kubectl 不报错，但也不会附加：只有 --set-image 时复制出的 Pod 没有调试容器名，附加这一步被直接跳过，留下的仍是一个反复崩溃的复制品。要用 --container 指定附加到哪个容器。按源码推出来的写法如下，这条命令这次没有实际运行：

kubectl -n notes-lab debug badimg -it --copy-to=badimg-sh --set-image='*=busybox:1.36' --container=whoami -- sh

PodSecurity restricted 的 namespace

给 namespace 打上 pod-security.kubernetes.io/enforce=restricted。打标签时 API Server 会检查已有 Pod 并给出警告：

Warning: existing pods in namespace "notes-lab" violate the new PodSecurity enforce level "restricted:v1.31"
Warning: app-nonroot: allowPrivilegeEscalation != false, unrestricted capabilities
Warning: app: privileged, allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile

app-nonroot 创建时是完全符合 restricted 的（Pod 级 runAsNonRoot、runAsUser、seccompProfile，容器级 drop: ["ALL"]、allowPrivilegeEscalation: false）。它现在不合规，原因是之前在它身上用 legacy 和 general 加过两个临时容器。app 被标成 privileged，是因为那个 sysadmin 调试容器。临时容器删不掉，调试过一次的 Pod 永久带着这些安全字段，这类 Pod 要等下一次滚动更新才能「洗白」。已经运行的 Pod 不会因为这个警告被驱逐，enforce 只拦截新的请求。

再新建一个合规的 Pod app-psa（配置同 app-nonroot），依次尝试各个 profile：

Error from server (Forbidden): pods "app-psa" is forbidden: violates PodSecurity "restricted:v1.31": allowPrivilegeEscalation != false (container "psa-legacy" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "psa-legacy" must set securityContext.capabilities.drop=["ALL"])
Error from server (Forbidden): pods "app-psa" is forbidden: violates PodSecurity "restricted:v1.31": allowPrivilegeEscalation != false (container "psa-general" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "psa-general" must set securityContext.capabilities.drop=["ALL"]; container "psa-general" must not include "SYS_PTRACE" in securityContext.capabilities.add)

baseline 和 netadmin 也是同样的 Forbidden。PodSecurity 准入会检查 ephemeralcontainers 子资源的更新，被拒时什么都不会写进 Pod。所测的五种 profile 里只有 restricted 能过（sysadmin 没有在这个 Pod 上试），而这次它真的跑起来了：

uid=65532 gid=0(root) groups=0(root)
CapEff:	0000000000000000
PID   USER     COMMAND
    1 65532    /whoami --port 8080

前面在 app 上 restricted 失败，是因为 app 没有设置 runAsUser，busybox 默认以 root 运行；app-psa 在 Pod 级设了 runAsUser: 65532，临时容器继承过来，runAsNonRoot 的检查就通过了。在 restricted namespace 里调试，能力为零、非 root，能做的基本只剩看网络和读同 UID 进程的文件；--copy-to 产生的复制品是普通 Pod，创建时同样要过所在 namespace 的 PodSecurity 检查，这次没有单独测。PodSecurity 的细节见 Pod Security Admission 和 安全上下文。

节点调试：kubectl debug node

kubectl debug node/<节点> 会在当前 namespace 里创建一个普通 Pod，调度到指定节点。仍在 restricted 的 namespace 里执行，直接被拒，报错正好列出了它要什么：

Creating debugging pod node-debugger-worker-7zzpq with container debugger on node worker.
Error from server (Forbidden): pods "node-debugger-worker-7zzpq" is forbidden: violates PodSecurity "restricted:v1.31": host namespaces (hostNetwork=true, hostPID=true, hostIPC=true), allowPrivilegeEscalation != false (container "debugger" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "debugger" must set securityContext.capabilities.drop=["ALL"]), restricted volume types (volume "host-root" uses restricted volume type "hostPath"), runAsNonRoot != true (pod or container "debugger" must set securityContext.runAsNonRoot=true), seccompProfile (pod or container "debugger" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")

去掉标签后，用 general 看一眼节点，只做只读操作。注意节点的 / 是以读写方式挂进来的，在 /host 下误删、误改都会直接作用到节点上：

  sh -c 'echo hostname=$(hostname); ls /host/etc/kubernetes /host/etc/kubernetes/manifests; echo ---; chroot /host crictl ps --name whoami -o table; echo ---; ps | grep -c . ; grep CapEff /proc/self/status'

节点的根文件系统挂在 /host，Pod 使用宿主机的网络、PID、IPC 命名空间，所以 hostname 是节点名，ps 能看到节点上的全部 146 行进程。worker 节点的 manifests 目录是空的，静态 Pod 只在控制平面节点上。chroot /host crictl ps 借用节点自己的 crictl 看到了三个 whoami 容器。它的能力集和普通容器一样，不是特权容器；这次 chroot 能成功，是因为默认能力集里有 SYS_CHROOT，而官方文档提醒过非特权时 chroot 和部分进程信息可能失败，需要完整权限时用 --profile=sysadmin。

这个 Pod 的 restartPolicy 是 Never，命令结束后不会自己消失，用完要手动删：

kubectl -n notes-lab get pod -o name | grep node-debugger | xargs kubectl -n notes-lab delete

小结

  • 看网络不需要 --target；看进程和应用的文件需要 --target，入口是 /proc/<pid>/root。应用以其他 UID 运行时，还要 --profile=general 提供的 SYS_PTRACE。
  • kubectl 1.30 到 1.35 的默认 profile 是 legacy，其中 1.32 到 1.35 在使用 legacy 时会打印废弃警告（以上来自源码）。从 1.36 起默认改为 general，--copy-to 默认就会共享进程，帮助和行为不一致的问题也随之消失。kubernetes.io 的调试页面目前仍写着默认是 legacy，已经过时。用旧客户端时，legacy 下 --copy-to 不共享进程、不去探针，最好每次都显式写 --profile。
  • 临时容器删不掉、不重启、get pod 里看不见，还会永久影响 Pod 的 PodSecurity 合规性。生产上把它当成一次性的、会留痕的操作。
  • 应用起不来（CrashLoopBackOff、镜像错误）时用 --copy-to 改命令或换镜像，复制品没有标签、不接流量，用完删掉。

清理

kubectl delete namespace notes-lab

临时容器没有单独的清理方式，删 Pod 是唯一的办法；由控制器管理的 Pod，滚动重启一次即可。更系统的排查路径见 故障排查。
