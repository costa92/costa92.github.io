删除 Pod 时发生了什么

Pod 生命周期里只简单提到了删除宽限期，这篇专门看终止过程。官方文档描述的顺序是：API Server 给 Pod 设置 deletionTimestamp，Pod 进入 Terminating；kubelet 看到后先执行 preStop 钩子（如果配置了），再向容器发送 SIGTERM；terminationGracePeriodSeconds 用完进程还没退出，就发 SIGKILL。同时，EndpointSlice 控制器把这个端点标成 terminating，Service 不再把新流量分给它。

这几步里哪些是串行的、哪些是并行的，各花多长时间，下面逐个测出来。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico，kube-proxy 默认配置），实验放在单独的 notes-lab namespace 里。节点名简化成 worker、worker2，时间都是 UTC。实验期间这个集群上同时跑着别的负载，API Server 偶尔报 etcdserver: request timed out，所以下文里涉及 API 状态同步的几个延迟偏大，不要当成基准值。

一次删除的完整时间线

实验 Pod 的主进程是一个处理 SIGTERM 的 shell 循环：收到 TERM 后删掉就绪文件、花 3 秒「收尾」再退出。preStop 睡 5 秒，开始和结束各往 PID 1 的标准输出写一行，这样它会出现在容器日志里，kubectl logs --timestamps 能给每一行打上纳秒级时间戳。再配一个 Service 选中它。

保存为 term-seq.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: term-seq
  labels:
    app: seq
spec:
  terminationGracePeriodSeconds: 30
  containers:
    - name: app
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          trap 'echo "TERM received"; rm -f /tmp/ready; env sleep 3; echo "cleanup done, exit 0"; exit 0' TERM
          touch /tmp/ready
          echo "started"
          while true; do sleep 1 & wait $!; done
      readinessProbe:
        exec:
          command: ["cat", "/tmp/ready"]
        periodSeconds: 1
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "echo 'preStop start' > /proc/1/fd/1; sleep 5; echo 'preStop end' > /proc/1/fd/1"]
      ports:
        - containerPort: 8080
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
---
apiVersion: v1
kind: Service
metadata:
  name: seq
spec:
  selector:
    app: seq
  ports:
    - port: 80
      targetPort: 8080

主循环写成 sleep 1 & wait $! 而不是 sleep 1，是因为 shell 在前台命令结束前不会执行 trap；用 wait 等后台进程，信号到达时 wait 会立即返回。trap 里的 env sleep 3 是踩坑后的写法，见文末「一个没弄清的现象」。

删除前开三个观察者：kubectl logs -f --timestamps 跟日志；kubectl get pod -w 打印 deletionTimestamp、Ready 条件和容器状态；再每 0.3 秒左右查一次 EndpointSlice 的端点条件（用 -w 加 jsonpath 盯 EndpointSlice 时，第一次尝试没打印出任何更新，所以改成了轮询）。

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f term-seq.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/term-seq --timeout=120s

# 观察者 1：容器日志，带纳秒时间戳
kubectl -n notes-lab logs -f --timestamps term-seq > logs.txt &
# 给每行输出加本机时间（下面几处 watch 都用它）
ts(){ while IFS= read -r l; do printf '%s %s\n' "$(date -u +%T.%3N)" "$l"; done; }

# 观察者 2：Pod 的 deletionTimestamp、Ready 条件、容器状态
kubectl -n notes-lab get pod term-seq -w -o jsonpath='deletionTimestamp={.metadata.deletionTimestamp} grace={.metadata.deletionGracePeriodSeconds} ready={.status.conditions[?(@.type=="Ready")].status} state={.status.containerStatuses[0].state}{"\n"}' | ts > pod.txt &
# 观察者 3：轮询 EndpointSlice 的端点条件，行首加本机时间
while true; do
  printf '%s %s\n' "$(date -u +%T.%3N)" "$(kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=seq -o json \
    | jq -c '[.items[] | {eps:[.endpoints[]? | {n:.targetRef.name, c:.conditions}]}]')"
  sleep 0.3
done > eps.txt &

date -u +%T.%3N; kubectl -n notes-lab delete pod term-seq; date -u +%T.%3N
kill %1 %2 %3
uniq -f1 eps.txt    # 跳过时间列去重，只看变化

从这张表能读出几件事：

  • deletionTimestamp 不是删除发生的时间，而是 API Server 估算的「删除时间 + 宽限期」，这里是 07:08:46 + 30 秒 = 07:09:16。到最后一刻，kubelet 确认容器已经停掉，再以宽限期 0 发起最终删除，这时 watch 看到的值被改写成了 deletionTimestamp=2026-10-12T07:08:46Z grace=0。
  • 摘流量和 preStop 是并行开始的。删除后 0.2 秒内 EndpointSlice 就把端点标成 ready=false，几乎和 preStop start 同时。这说明「先摘流量、再停进程」并不是 Kubernetes 保证的顺序，两条线各走各的；preStop 能起到的作用，只是推迟 SIGTERM 的到来。
  • SIGTERM 紧跟在 preStop 之后，间隔不到 5 毫秒。preStop 用掉的 5 秒算在 30 秒宽限期里面。严格说，kubelet 的宽限期是从它开始停止容器（即执行 preStop）时才计时的，不是从 API 收到删除请求时；deletionTimestamp 只是 API Server 按「收到请求的时间 + 宽限期」算出的估计值。这次 kubelet 0.1 秒内就接手了，两者差别不大，下一节会看到集群繁忙时差出 2 秒的例子。
  • ready 和 serving 是两回事。terminating 的端点 ready 恒为 false，这是官方为了兼容 1.26 之前的行为定下的；serving 则继续跟着就绪探针走。preStop 期间探针照常运行、照常成功，所以 serving 一直是 true；主进程删掉 /tmp/ready 之后，serving 才变成 false。不过主进程删文件后 3.4 秒就退出了，和探针第 3 次失败（failureThreshold 默认 3）差不多同时，所以这次分不清 serving=false 是探针失败还是容器退出触发的，只能说发生在两者之后。官方文档的说法是，普通流量看 ready；如果需要在 Pod 终止期间继续把流量排空给它，看的是 serving。
  • 进程退出到 Pod 对象消失又过了 9 秒多。这段时间 kubelet 要把状态上报 API、清理沙箱和网络，然后才发起最终删除。之前三次跑同样的实验，这个间隔分别是 8.9、8.0 和 10.3 秒。考虑到实验时集群负载较高，推测正常情况下会短一些；kubectl delete 默认等对象真正消失才返回，所以它的耗时比进程实际退出要长。

进程怎么响应 SIGTERM，决定了它要等多久

探针与资源管理里已经看到，以 sh 为 PID 1 又不设 trap 的容器会无视 SIGTERM，只能等满宽限期被 SIGKILL。这里把四种常见情况放在一起删除，宽限期都设为 10 秒：

Pod容器里的 PID 1
sig-ignoresh -c "while true; do sleep 1; done"，没有 trap
sig-trap同样的 shell，加了 trap 'echo TERM received; exit 0' TERM
sig-gotraefik/whoami，一个 Go 写的 HTTP 服务
sig-nginxnginx:alpine

先看 PID 1 登记了哪些信号处理函数。/proc/1/status 里的 SigCgt 是一个位图，第 n 位（从 1 数）为 1 表示信号 n 被捕获，SIGTERM 是 15 号信号，对应掩码 0x4000：

$ kubectl -n notes-lab exec sig-ignore -- grep -E 'SigIgn|SigCgt' /proc/1/status
SigIgn:	0000000000000004
SigCgt:	0000000000010002
$ kubectl -n notes-lab exec sig-trap -- grep -E 'SigIgn|SigCgt' /proc/1/status
SigIgn:	0000000000000004
SigCgt:	0000000000014002
$ kubectl -n notes-lab exec sig-nginx -- grep -E 'SigIgn|SigCgt' /proc/1/status
SigIgn:	0000000040001000
SigCgt:	0000000018016a07

sig-ignore 的 0x10002 只捕获了 SIGINT 和 SIGCHLD；加上 trap 后变成 0x14002，多出来的正是 0x4000。nginx 也捕获了 SIGTERM；它的 SigIgn 是 0x40001000，即主动忽略了 13 号信号 SIGPIPE（0x1000）和 31 号信号（0x40000000），两个 shell 的 0x4 则是忽略了 3 号 SIGQUIT。Linux 对 PID 1 有特殊保护：没有登记处理函数的信号，内核不会执行默认动作（终止进程），而是直接丢弃。所以 sig-ignore 收到 SIGTERM 什么也不会发生。这个检查方法对排查很有用：不确定一个镜像能不能被优雅停止时，exec 进去看一眼 SigCgt 的第 15 位就知道。whoami 是 scratch 镜像，没有 ps、grep 这类工具，这里没法用同样的办法看。

用一个 watch 记录每个 Pod 的状态变化，再并行删除四个 Pod：

for p in sig-ignore sig-trap sig-go sig-nginx; do kubectl -n notes-lab delete pod $p --wait=false & done

sig-go 的退出码 2 是个意外。whoami 收到 SIGTERM 后立刻就退出了，并没有拖延，但 reason 是 Error。原因在 Go 运行时：whoami v1.10.2 的 app.go 没有引入 os/signal，直接 log.Fatal(http.ListenAndServe(...))；Go 运行时自己为 SIGTERM 注册了处理函数（所以 PID 1 的保护不起作用），信号没被程序接管时，runtime/signal_unix.go 的 dieFromSignal 会恢复默认动作、再给自己发一次信号，想以「被信号杀死」的方式退出。可进程是 PID 1，内核把这次信号丢掉了，运行时最后只能 exit(2)，源码注释写的就是 just exit with the wrong status。Go 1.27 把这里改成了 exit(128 + sig)（对照 go1.26.0 和 go1.27.1 两个 tag 的源码，1.27 的发布说明里没有提），用 1.27 编译的程序遇到同样情况会以 143 退出。实际影响是：滚动更新一个没处理 SIGTERM 的 Go 服务，旧容器的状态会显示 Error、退出码 2，这不代表程序出了故障。

还要注意，sig-go 这种「立即退出」也不等于优雅。下一节会看到，正是这种进程在滚动更新时会丢请求。

preStop 比宽限期还长

preStop 的时间算在宽限期里，那 preStop 自己超时了会怎样？两个 Pod，宽限期都是 10 秒，preStop 是一个每秒打印一行、要跑 30 秒的循环：

lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "i=0; while [ $i -lt 30 ]; do i=$((i+1)); echo preStop $i > /proc/1/fd/1; sleep 1; done"]

long-prestop-trap 的主进程处理 SIGTERM，long-prestop-ignore 的不处理。07:14:43 左右同时删除，deletionTimestamp 都是 07:14:53。

不处理 SIGTERM 的那个：

2026-10-12T07:14:45.227086971Z preStop 2
...
2026-10-12T07:14:53.227958218Z preStop 10
2026-10-12T07:14:54.228068735Z preStop 11
2026-10-12T07:14:55.228253736Z preStop 12

事件：

2026-10-12T07:14:43Z   long-prestop-trap     Killing             Stopping container app
2026-10-12T07:14:44Z   long-prestop-ignore   Killing             Stopping container app
2026-10-12T07:14:53Z   long-prestop-trap     FailedPreStopHook   PreStopHook failed
2026-10-12T07:14:56Z   long-prestop-ignore   FailedPreStopHook   PreStopHook failed

两者合起来看：

  • kubelet 只等 preStop 到宽限期用完（第 10 秒），然后不管它跑没跑完，直接发 SIGTERM。官方文档对此的描述是，preStop 超过宽限期后，kubelet 会一次性再延长 2 秒；在 kubelet 代码里，这体现为扣掉 preStop 用时后剩余宽限期不足最小值时，按最小值 2 秒处理。
  • FailedPreStopHook 事件并不是在超时那一刻记下的：long-prestop-ignore 的宽限期在 07:14:54 左右用完，事件却记在 07:14:56，正好是容器被 SIGKILL、钩子进程随之结束的时候；long-prestop-trap 的事件记在 07:14:53，也是主进程退出的那一秒。可见事件是在钩子的 exec 进程死掉时记录的。
  • 主进程处理 SIGTERM 的，收到信号就退出了，整个容器随之结束，剩下的 preStop 也跟着没了。
  • 主进程不处理 SIGTERM 的，preStop 又多跑了两行（第 11、12 行），也就是那 2 秒延长，之后被 SIGKILL。总耗时约 12 秒，而不是 10 秒。

所以 preStop 写得太长，代价是主进程收尾的时间被挤掉：在这个例子里，处理 SIGTERM 的程序只剩下 2 秒的延长期，来不及做完的工作就会被 SIGKILL 打断。规划时应该满足：preStop 时长 + 程序收尾时长 < terminationGracePeriodSeconds，并留出余量。FailedPreStopHook 事件的消息只有一句 PreStopHook failed，不说原因，超时和下面这种「命令不存在」看起来完全一样。

精简镜像里的 exec preStop

很多文章的建议是加一个 preStop: exec: command: ["sleep", "5"]。拿 whoami 试一下：

lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]

删除后 Pod 只用了 9.5 秒就消失了，事件里同样只有 FailedPreStopHook PreStopHook failed，要到节点上的 kubelet 日志里才看得到原因：

"PreStop hook failed" err="rpc error: code = Unknown desc = failed to exec in container: failed to start exec \"894319427b51cb63c9635b56a9abb2bd2c73e1df578317cd2fd9f66cb332ea21\": OCI runtime exec failed: exec failed: unable to start container process: exec: \"sleep\": executable file not found in $PATH: unknown"

whoami 是从 scratch 构建的镜像，里面没有 sleep，也没有 shell。exec 类型的钩子是在容器内执行命令，命令不存在钩子就失败，kubelet 随即发 SIGTERM，等于没有配。对这类镜像，用内置的 sleep 动作：

lifecycle:
  preStop:
    sleep:
      seconds: 5

它由 kubelet 自己计时，不依赖镜像里有什么。这个字段由特性门控 PodLifecycleSleepAction 控制，v1.29 alpha，v1.30 起 beta 并默认开启，v1.34 GA。在这个 v1.31 集群上它被正常接受，下一节的实验用的就是它。

滚动更新时到底丢不丢请求

前面看到摘流量和发 SIGTERM 是并行的。如果进程收到 SIGTERM 立即退出，而各节点上的 kube-proxy 还没来得及把这个端点从转发规则里去掉，发往它的新连接就会失败。下面直接数失败次数。

加上 5 秒的 preStop

只改一处：

kubectl -n notes-lab patch deploy web --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/lifecycle","value":{"preStop":{"sleep":{"seconds":5}}}}]'

07:21:25.281 {"n":"web-5749dd5c8b-mpfqj","del":"2026-10-12T07:21:55Z","ready":"True","st":"running","fin":null,"code":null}
07:21:44.124 {"n":"web-5749dd5c8b-mpfqj","del":"2026-10-12T07:21:55Z","ready":"False","st":"terminated","fin":"2026-10-12T07:21:30Z","code":2}

这 5 秒里旧 Pod 仍然在监听，在转发规则更新前到达的连接照样能被处理，等 SIGTERM 到来时已经没有新流量了。preStop 的作用就是这一点：它不是为程序收尾准备的，而是给流量摘除的传播留时间。

这个实验的边界也要说清楚：

  • 客户端每个请求都新建连接。HTTP keep-alive 长连接、gRPC 这种复用连接的客户端，即使转发规则更新了，已经建立的连接仍然连着旧 Pod，这时需要程序在收到 SIGTERM 后主动关闭空闲连接、处理完在途请求再退出（Go 里就是 http.Server.Shutdown）。这种情况这里没有测。
  • 5 秒对这个空闲的 3 节点集群足够；节点多、经过外部负载均衡器或 Ingress 时，传播时间会更长，需要按实际环境测。
  • whoami 自己不做优雅关闭，请求都很短才没出问题。处理慢请求的服务，还需要 preStop 之后有足够的收尾时间，记得一起算进宽限期。

kubectl delete 的 –grace-period 和 –force

三个忽略 SIGTERM 的 Pod del-gp3、del-gp0、del-force，terminationGracePeriodSeconds 都是 30，用不同参数删除。每个都是这样（只改名字）：

apiVersion: v1
kind: Pod
metadata:
  name: del-gp3
  labels: {exp: del}
spec:
  terminationGracePeriodSeconds: 30
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo started; while true; do sleep 1; done"]
      resources: {requests: {cpu: 10m, memory: 16Mi}}

节点上的容器状态用 docker exec <节点容器> crictl ps -a --label io.kubernetes.pod.name=del-force 查看（kind 的节点就是 Docker 容器）。

--grace-period=3 覆盖了 Pod 自己的 30 秒：

$ kubectl -n notes-lab delete pod del-gp3 --grace-period=3
07:23:51.274
pod "del-gp3" deleted
07:24:02.787

命令 11.5 秒后返回：3 秒宽限期加上前面看到的 kubelet 清理和上报时间。

--grace-period=0 不带 --force，删除后立刻看 Pod：

07:24:02.792
pod "del-gp0" deleted
07:24:03.167
2026-10-12T07:24:03Z 1

实测 deletionGracePeriodSeconds 是 1，不是 0。官方文档写明，用 kubectl 时必须同时加 --force 和 --grace-period=0 才是强制删除；单独写 --grace-period=0，kubectl 会把它换成 1 秒（kubectl 源码里有一行注释说明这种转换），走的是正常删除流程。

API 对象在 07:24:56 消失，容器到 07:24:59.8 才被 SIGKILL，中间差了将近 4 秒。官方文档的说法是，强制删除时 API Server 不等 kubelet 确认，节点上的 Pod 仍会得到一个很短的宽限期（small grace period）再被杀掉；kubelet 代码里的最小宽限期是 2 秒。这个容器忽略 SIGTERM，所以等这 2 秒过去被 SIGKILL，退出码 137，再加上 kubelet 发现删除的时间，合起来约 4 秒。这次节点正常，kubelet 几秒内就清理掉了；如果节点失联，kubelet 看不到删除，容器会一直运行下去，警告里的 may continue to run on the cluster indefinitely 说的就是这种情况。

对普通 Deployment 的 Pod，这几秒的重叠无伤大雅。对 StatefulSet 就危险了：强制删除后，控制器马上会创建同名的新 Pod，而旧容器可能还在写同一份数据。所以 --force 只应该用在确认节点已经不存在、或容器确实已经停止的情况下，不要拿它当「删得快一点」的开关。想加快删除，用 --grace-period=N 就够了。

一个没弄清的现象

第一节的实验最初在 trap 里写的是普通的 sleep 3，结果三次运行中，从 TERM received 到 cleanup done 分别只用了 0.69 秒、3.2 秒和 0.76 秒。单独用 kubectl exec 给 PID 1 发 SIGTERM 复现：

2026-10-12T07:05:39.296850428Z TERM
2026-10-12T07:05:39.459035498Z after-sleep

trap 里的 sleep 3 只睡了 0.16 秒。把 trap 改成先 env sleep 3、再 sleep 3：

2026-10-12T07:06:36.839600244Z TERM
2026-10-12T07:06:39.841143582Z after-env-sleep
2026-10-12T07:06:42.841241548Z after-plain-sleep

两次都睡满了 3 秒。看起来是 busybox sh 在 trap 里执行的第一个 sleep 会被提前打断（多数时候只睡了 0.16～0.76 秒），而 env sleep 会以独立进程的方式运行。推测 busybox 把 sleep 当作 NOFORK applet 在 shell 进程内执行，被主循环里后台 sleep 1 退出时产生的 SIGCHLD 打断了；这一点没有验证。如果你用 busybox shell 写 trap 来模拟「收尾」，要注意这个问题，否则会误以为程序很快就退出了。

小结

  • deletionTimestamp 是 API Server 估算的「删除时间 + 宽限期」；kubelet 从开始停止容器时计算宽限期，preStop 的时间也包含在内，集群繁忙时实际结束时间会比 deletionTimestamp 晚。
  • EndpointSlice 标记 terminating（ready=false）和执行 preStop 几乎同时开始，Kubernetes 不保证「先摘流量再停进程」。
  • 进程收到 SIGTERM 立即退出，滚动更新时会有约 2 秒的连接失败（本次实测每轮 239～308 个请求）；加上 5 秒的 preStop sleep 后降到 0。
  • PID 1 不处理 SIGTERM 就只能等满宽限期被 SIGKILL（137）；没有自己处理 SIGTERM 的 Go 程序作为 PID 1 会立即退出，但退出码是 2（Go 1.27 起为 143），reason 是 Error。
  • preStop 超过宽限期时，kubelet 只额外给 2 秒，然后发 SIGKILL；exec 钩子在精简镜像里会因为找不到命令而失败，改用 sleep 动作。
  • --grace-period=0 不加 --force 会被当作 1 秒；--force 只删除 API 对象，不等容器真正停止。

和发布相关的还有 PDB：它限制的是同时被自愿驱逐的 Pod 数量，管不到单个连接是否处理完。Deployment 的滚动策略见 Deployment，Service 与 EndpointSlice 的关系见 Service。
