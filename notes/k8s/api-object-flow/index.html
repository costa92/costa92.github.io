一份清单不会直接变成容器

概念和术语列出了常见对象，集群组件说明了组件职责。这一篇把它们连起来，看一个无状态 Web 服务从 Deployment 到 Pod、从 Service 到后端地址，中间到底靠什么关联，以及删掉或改掉其中一环会发生什么。

用户清单 ──apply──> API Server 中的 Deployment
                          │ Deployment 控制器
                          ▼
                       ReplicaSet
                          │ ReplicaSet 控制器
                          ▼
                          Pod ──调度器选节点──> kubelet 启动容器

Service ──标签选择──> Pod
   │
   └── EndpointSlice 记录后端地址与就绪信息

图里其实有两种关系。Deployment → ReplicaSet → Pod 和 Service → EndpointSlice 是归属，写在从属对象的 metadata.ownerReferences 里，垃圾回收按它工作；Service → Pod 只是标签选择，Service 不是 Pod 的所有者。下面的实验会把这两种关系分别拆开看。

下文输出来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，Calico CNI，kube-proxy 为 iptables 模式）。实验放在单独的 namespace 里，命令和输出中统一写作 notes-lab；节点名简化为 worker、worker2，Pod IP 和 ClusterIP 用占位符代替。

准备：一个 Deployment 加一个 Service

保存为 web.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
          resources:
            requests:
              cpu: 20m
              memory: 32Mi
            limits:
              memory: 64Mi
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f web.yaml
kubectl -n notes-lab rollout status deploy/web --timeout=120s
kubectl -n notes-lab get deploy,rs,pod,svc,endpointslice -o wide --show-labels
NAME                  READY   UP-TO-DATE   AVAILABLE   AGE   ...   SELECTOR   LABELS
deployment.apps/web   2/2     2            2           4s    ...   app=web    <none>

NAME                             DESIRED   CURRENT   READY   AGE   ...   SELECTOR                               LABELS
replicaset.apps/web-668945bdf5   2         2         2       4s    ...   app=web,pod-template-hash=668945bdf5   app=web,pod-template-hash=668945bdf5

NAME                       READY   STATUS    RESTARTS   AGE   ...   LABELS
pod/web-668945bdf5-jlcsx   1/1     Running   0          4s    ...   app=web,pod-template-hash=668945bdf5
pod/web-668945bdf5-xjvs7   1/1     Running   0          4s    ...   app=web,pod-template-hash=668945bdf5

NAME          TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE   SELECTOR   LABELS
service/web   ClusterIP   <cluster-ip>   <none>        80/TCP    4s    app=web    <none>

NAME                                       ADDRESSTYPE   PORTS   ENDPOINTS              AGE   LABELS
endpointslice.discovery.k8s.io/web-v4mcp   IPv4          80      <pod-ip-1>,<pod-ip-2>  4s    endpointslice.kubernetes.io/managed-by=endpointslice-controller.k8s.io,kubernetes.io/service-name=web

（-o wide 多出的 IP、NODE、CONTAINERS 等列用 ... 省略了。）先注意 SELECTOR 列：清单里只写了 app=web，但 ReplicaSet 的选择器多了一个 pod-template-hash=668945bdf5。这个哈希由 Deployment 控制器根据 Pod 模板算出，同时写进 ReplicaSet 名字、ReplicaSet 选择器和 Pod 标签。后面几个实验的结果都和这个多出来的标签有关。

ownerReferences：用 uid 串起来的链

用 JSONPath 把每个对象自己的 uid 和它指向的所有者打出来（JSONPath 的写法见 kubectl JSONPath）：

OR='{.metadata.name}{"  uid="}{.metadata.uid}{"\n  owner: "}{range .metadata.ownerReferences[*]}{.kind}/{.name} uid={.uid} controller={.controller} blockOwnerDeletion={.blockOwnerDeletion}{end}{"\n"}'
kubectl -n notes-lab get deploy web -o jsonpath="$OR"
kubectl -n notes-lab get rs -o jsonpath="{range .items[*]}$OR{end}"
kubectl -n notes-lab get pod -o jsonpath="{range .items[*]}$OR{end}"
web  uid=e890f77a-8c95-4aa0-92d8-9f6b8184dbb6
  owner: 
web-668945bdf5  uid=ce675569-b123-414e-bb0c-9a6f0f163b47
  owner: Deployment/web uid=e890f77a-8c95-4aa0-92d8-9f6b8184dbb6 controller=true blockOwnerDeletion=true
web-668945bdf5-jlcsx  uid=cafb4bdb-69dd-4b94-896b-903a4ec98b5e
  owner: ReplicaSet/web-668945bdf5 uid=ce675569-b123-414e-bb0c-9a6f0f163b47 controller=true blockOwnerDeletion=true
web-668945bdf5-xjvs7  uid=9c8f171d-a30b-4183-9495-fc345eeff46e
  owner: ReplicaSet/web-668945bdf5 uid=ce675569-b123-414e-bb0c-9a6f0f163b47 controller=true blockOwnerDeletion=true

Pod 的所有者 uid 等于 ReplicaSet 的 uid，ReplicaSet 的所有者 uid 等于 Deployment 的 uid，Deployment 自己没有所有者。Service 那条链同样如此：

kubectl -n notes-lab get svc web -o jsonpath="$OR"
kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=web -o jsonpath="{range .items[*]}$OR{end}"
web  uid=32300c80-9608-4669-82c0-5f0cb5433162
  owner: 
web-v4mcp  uid=b5099f8a-06a1-4b47-a2d8-a02688509ba9
  owner: Service/web uid=32300c80-9608-4669-82c0-5f0cb5433162 controller=true blockOwnerDeletion=true

EndpointSlice 归 Service 所有，而 Pod 的 ownerReferences 里完全没有 Service。在对象数据里能看到的 Service 与 Pod 之间的联系，只有 EndpointSlice 中每个端点的 targetRef：

kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=web \
  -o jsonpath='{range .items[*].endpoints[*]}{.targetRef.name} ready={.conditions.ready} node={.nodeName}{"\n"}{end}'
web-668945bdf5-xjvs7 ready=true node=worker
web-668945bdf5-jlcsx ready=true node=worker2

后文查端点时用的是同一条命令，只是去掉了 node={.nodeName} 这一段。

uid 对不上，就等于没有所有者

所有者是按 uid 认的，不是按名字。验证方法：建一个 ConfigMap，再建两个 Pod，ownerReferences 都指向这个 ConfigMap 的名字，一个填真实 uid，一个填全零 uid：

kubectl -n notes-lab create configmap owner-cm --from-literal=k=v
CMUID=$(kubectl -n notes-lab get cm owner-cm -o jsonpath='{.metadata.uid}')
cat > dangling.yaml <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: right-uid
  ownerReferences:
    - apiVersion: v1
      kind: ConfigMap
      name: owner-cm
      uid: $CMUID
spec:
  containers:
    - name: c
      image: busybox:1.36
      command: ["sleep", "3600"]
---
apiVersion: v1
kind: Pod
metadata:
  name: wrong-uid
  ownerReferences:
    - apiVersion: v1
      kind: ConfigMap
      name: owner-cm
      uid: 00000000-0000-0000-0000-000000000000
spec:
  containers:
    - name: c
      image: busybox:1.36
      command: ["sleep", "3600"]
EOF

这次 $CMUID 展开后是 b361a247-40c3-414b-984c-c1e9f915c9e1。

$ kubectl -n notes-lab apply -f dangling.yaml
pod/right-uid created
pod/wrong-uid created
$ kubectl -n notes-lab get pod right-uid wrong-uid      # 3 秒后
NAME        READY   STATUS    RESTARTS   AGE
right-uid   1/1     Running   0          3s
Error from server (NotFound): pods "wrong-uid" not found

wrong-uid 的所有者名字是对的，但 uid 在集群里找不到，垃圾回收器把它当成所有者已不存在的从属对象，3 秒内就删掉了，事件里只留下一条 Scheduled。接着删除 ConfigMap，right-uid 也随之进入 Terminating：

$ kubectl -n notes-lab delete configmap owner-cm; sleep 2; kubectl -n notes-lab get pod right-uid
configmap "owner-cm" deleted
NAME        READY   STATUS        RESTARTS   AGE
right-uid   1/1     Terminating   0          16s

这也说明 ownerReferences 不限于内置控制器之间：任何同 namespace 的对象都能当所有者，Operator 就是靠这个让自定义资源删除时带走它创建的对象。官方文档另有限制：跨 namespace 的所有者引用不被允许，namespace 级对象可以指向集群级所有者，反过来不行。

改标签：脱离与收养

把 Pod 从 ReplicaSet 里拉出来

kubectl -n notes-lab label pod web-668945bdf5-jlcsx app=debug --overwrite
kubectl -n notes-lab get pod -L app,pod-template-hash -o wide
NAME                   READY   STATUS    RESTARTS   AGE   ...   NODE      ...   APP     POD-TEMPLATE-HASH
web-668945bdf5-6qt45   1/1     Running   0          3s    ...   worker2   ...   web     668945bdf5
web-668945bdf5-jlcsx   1/1     Running   0          18s   ...   worker2   ...   debug   668945bdf5
web-668945bdf5-xjvs7   1/1     Running   0          18s   ...   worker    ...   web     668945bdf5

被改了标签的 jlcsx 仍在运行，但已经不属于任何人：

$ kubectl -n notes-lab get pod web-668945bdf5-jlcsx -o jsonpath='{.metadata.ownerReferences}{"\n"}'

ReplicaSet 发现选择器只匹配到 1 个 Pod，立刻补了一个 6qt45，ReplicaSet 依然显示 2/2。Service 的选择器也是 app=web，所以 jlcsx 同时退出了 EndpointSlice：

web-668945bdf5-xjvs7 ready=true
web-668945bdf5-6qt45 ready=true

这正是官方文档推荐的隔离调试手法：Pod 留着保存现场，不再接流量，副本数由控制器补齐。要注意它的名字仍带着 web-668945bdf5- 前缀，pod-template-hash 标签也还在，看名字会误以为它还归 ReplicaSet 管，判断归属要看 ownerReferences。

改回去：多出来的那个被删掉

调试完把标签改回 app=web，ReplicaSet 重新收养 jlcsx，此时它手下有 3 个 Pod，比期望多一个：

$ kubectl -n notes-lab label pod web-668945bdf5-jlcsx app=web --overwrite
pod/web-668945bdf5-jlcsx labeled
$ kubectl -n notes-lab get pod -L app -o wide
NAME                   READY   STATUS    RESTARTS   AGE   ...   NODE      ...   APP
web-668945bdf5-jlcsx   1/1     Running   0          27s   ...   worker2   ...   web
web-668945bdf5-xjvs7   1/1     Running   0          27s   ...   worker    ...   web
kubectl -n notes-lab get events --field-selector involvedObject.kind=ReplicaSet \
  --sort-by=.lastTimestamp -o custom-columns=TIME:.lastTimestamp,REASON:.reason,MSG:.message
TIME                   REASON             MSG
2026-10-13T06:04:14Z   SuccessfulCreate   Created pod: web-668945bdf5-jlcsx
2026-10-13T06:04:14Z   SuccessfulCreate   Created pod: web-668945bdf5-xjvs7
2026-10-13T06:04:29Z   SuccessfulCreate   Created pod: web-668945bdf5-6qt45
2026-10-13T06:04:38Z   SuccessfulDelete   Deleted pod: web-668945bdf5-6qt45

被删的是刚补上的 6qt45，不是改回来的 jlcsx。这和官方文档列出的缩容排序一致：worker2 上有两个副本，优先删那里的；同节点的两个里，创建时间较新的先删（文档说明创建时间按对数尺度分桶比较）。换句话说，把调试过的 Pod 改回去，它很可能会留下来继续接流量，如果容器里留着调试时改过的东西，这里要小心。

只改 pod-template-hash：脱离 ReplicaSet，却还在 Service 里

两个选择器不一样，ReplicaSet 看 app 和 pod-template-hash，Service 只看 app。只改哈希标签：

kubectl -n notes-lab label pod web-668945bdf5-xjvs7 pod-template-hash=manual --overwrite
kubectl -n notes-lab get pod -L app,pod-template-hash
NAME                   READY   STATUS    RESTARTS   AGE   APP   POD-TEMPLATE-HASH
web-668945bdf5-cnrs4   1/1     Running   0          4s    web   668945bdf5
web-668945bdf5-jlcsx   1/1     Running   0          38s   web   668945bdf5
web-668945bdf5-xjvs7   1/1     Running   0          38s   web   manual
web-668945bdf5-xjvs7 ready=true
web-668945bdf5-jlcsx ready=true
web-668945bdf5-cnrs4 ready=true

ReplicaSet 补了一个新 Pod，Service 后端却变成了 3 个。再把 Deployment 缩到 0：

$ kubectl -n notes-lab scale deploy web --replicas=0
deployment.apps/web scaled
$ kubectl -n notes-lab get deploy,rs,pod
NAME                  READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/web   0/0     0            0           49s

NAME                             DESIRED   CURRENT   READY   AGE
replicaset.apps/web-668945bdf5   0         0         0       49s

NAME                       READY   STATUS    RESTARTS   AGE
pod/web-668945bdf5-xjvs7   1/1     Running   0          49s

起一个客户端 Pod 从集群内发请求：

$ kubectl -n notes-lab run client --image=curlimages/curl:latest --restart=Never --command -- sleep 3600
pod/client created
$ kubectl -n notes-lab wait --for=condition=Ready pod/client --timeout=60s
pod/client condition met
$ kubectl -n notes-lab exec client -- curl -s -o /dev/null -w '%{http_code}\n' http://web
200

Deployment 显示 0/0，Service 却仍然返回 200，流量全落在一个没人管理的 Pod 上，它不会随下次发布更新，节点故障后也不会被重建。排查「明明缩容了还有流量」「发布后还有旧版本响应」时，用 Service 的选择器查一遍 Pod，再逐个看 ownerReferences 是否为空。

孤儿 Pod 要手工删，然后把副本扩回 2，后面的实验从这个状态继续：

$ kubectl -n notes-lab delete pod web-668945bdf5-xjvs7 --wait=false
pod "web-668945bdf5-xjvs7" deleted
$ kubectl -n notes-lab scale deploy web --replicas=2
deployment.apps/web scaled
$ kubectl -n notes-lab rollout status deploy/web --timeout=60s
Waiting for deployment "web" rollout to finish: 0 of 2 updated replicas are available...
Waiting for deployment "web" rollout to finish: 1 of 2 updated replicas are available...
deployment "web" successfully rolled out

故障一：Service 选择器什么都没匹配上

用 kubectl create service 生成清单，再用 sed 把选择器改成 app=wbe，模拟少打一个字母：

kubectl -n notes-lab create service clusterip web-typo --tcp=80:80 --dry-run=client -o yaml \
  | sed 's/app: web-typo/app: wbe/' | kubectl -n notes-lab apply -f -

create service 生成的清单里，Service 自己的标签和选择器都是 app: web-typo，sed 把两处一起改了，所以下面 EndpointSlice 的标签里也会出现 app: wbe（EndpointSlice 会复制 Service 的标签）。

$ kubectl -n notes-lab get svc web-typo -o wide
NAME       TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE   SELECTOR
web-typo   ClusterIP   <cluster-ip>   <none>        80/TCP    3s    app=wbe
$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=web-typo -o yaml
...
- addressType: IPv4
  apiVersion: discovery.k8s.io/v1
  endpoints: null
  kind: EndpointSlice
  metadata:
    ...
    labels:
      app: wbe
      endpointslice.kubernetes.io/managed-by: endpointslice-controller.k8s.io
      kubernetes.io/service-name: web-typo
    ...
    ownerReferences:
    - apiVersion: v1
      blockOwnerDeletion: true
      controller: true
      kind: Service
      name: web-typo
      uid: 8d7d2a2d-d9ab-47f4-8da8-793bde909157
  ports: null

EndpointSlice 照样创建出来了，归属 Service，只是 endpoints 和 ports 都是 null。describe svc 也只有一行 Endpoints: <none>，没有任何 Warning 事件，API 层面一切「正常」。从客户端看：

$ kubectl -n notes-lab exec client -- curl -sS -m 5 http://web-typo
curl: (7) Failed to connect to web-typo:80 after 0 ms: Could not connect to server
command terminated with exit code 7

先排除 DNS。在 curlimages/curl 里直接 nslookup web-typo，最后打印的是 ** server can't find web-typo.localdomain: NXDOMAIN。这并不是没解析到：Pod 的 /etc/resolv.conf 里 search 列表最后一项是 localdomain，nslookup 把短名逐个拼上 search 域去试，最后显示的是最后一次失败的结果。用完整域名查就清楚了（这是另一轮重建的 web-typo）：

$ kubectl -n notes-lab exec client -- nslookup web-typo.notes-lab.svc.cluster.local
Server:		<dns-ip>
Address:	<dns-ip>:53


Name:	web-typo.notes-lab.svc.cluster.local
Address: <cluster-ip>

DNS 没问题，失败发生在连接阶段。kind 的节点是 docker 容器，容器名就是节点名，可以从 client Pod 的 nodeName 取到，进去看 kube-proxy 写的规则：

$ docker exec $(kubectl -n notes-lab get pod client -o jsonpath='{.spec.nodeName}') iptables-save | grep 'web-typo'
-A KUBE-SERVICES -d <cluster-ip>/32 -p tcp -m comment --comment "notes-lab/web-typo:80-80 has no endpoints" -m tcp --dport 80 -j REJECT --reject-with icmp-port-unreachable

没有端点的 Service，kube-proxy 在 iptables 模式下会写一条 REJECT，回 ICMP port unreachable，所以 curl 通常 0 ms 就失败。但不要把「0 ms 被拒」当成唯一特征。第二轮里先删掉了同名的 web-typo，7 秒后立即用同一条命令重建，紧接着连续三次 curl 都是 5 秒超时：

$ kubectl -n notes-lab exec client -- curl -sS -m 5 -o /dev/null -w 'dns=%{time_namelookup}s connect=%{time_connect}s total=%{time_total}s\n' http://web-typo
dns=0.000423s connect=0.000000s total=5.001661s
curl: (28) Connection timed out after 5001 milliseconds
command terminated with exit code 28

重建约 25 秒后再试，又恢复成 0 ms 失败；再过 9 秒查到上面那条 REJECT 规则已存在。超时那几次没有同时抓规则，所以无法确认当时规则在不在。随后又建了 web-typo2、web-typo3 两个同样没有端点的 Service，规则都在创建的同一秒就出现了，推测超时和 kube-proxy 同步规则的时机有关，但没有坐实。另有一次在 3139 ms 后才失败（第一次用完整域名请求时）。还有一次 1058 ms 后才失败，发生在 web-typo3 上，当时同一轮循环已经查到规则存在，同步时机的推测解释不了它，原因不明。结论是：失败方式只能作参考，判断有没有后端要看 EndpointSlice，再用 Service 的选择器去查 Pod：

kubectl -n notes-lab get svc web-typo -o jsonpath='{.spec.selector}'
kubectl -n notes-lab get pod -l app=wbe

把选择器改对后，2 秒内端点就填上了，请求返回 200：

$ kubectl -n notes-lab patch svc web-typo -p '{"spec":{"selector":{"app":"web"}}}'
service/web-typo patched
$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=web-typo -o jsonpath='{range .items[*].endpoints[*]}{.targetRef.name} ready={.conditions.ready}{"\n"}{end}'
web-668945bdf5-jcb82 ready=true
web-668945bdf5-lf7z8 ready=true
$ kubectl -n notes-lab exec client -- curl -s -o /dev/null -w '%{http_code}\n' http://web-typo
200

故障二：一个「临时」Pod 带着业务标签

反过来的情况更隐蔽：选择器匹配到了不该匹配的 Pod。实际执行时这一节排在后文 orphan 实验之后，所以 Pod 名是 24rgg、g48c8，而不是上一节的 jcb82、lf7z8，具体名字以你的环境为准。用 busybox 起一个调试 Pod，顺手打上 app=web：

kubectl -n notes-lab run stray --image=busybox:1.36 --labels=app=web --command -- sleep 3600
kubectl -n notes-lab get pod -l app=web -L pod-template-hash
NAME                   READY   STATUS    RESTARTS   AGE   POD-TEMPLATE-HASH
stray                  1/1     Running   0          2s    
web-668945bdf5-24rgg   1/1     Running   0          30s   668945bdf5
web-668945bdf5-g48c8   1/1     Running   0          30s   668945bdf5

它没有 pod-template-hash，ReplicaSet 不会收养它（ownerReferences 为空），但 Service 只看 app=web，于是它进了 EndpointSlice，而且是 ready=true（没配就绪探针，容器起来就算就绪）：

web-668945bdf5-g48c8 ready=true
web-668945bdf5-24rgg ready=true
stray ready=true

busybox 不监听 80 端口。从客户端连续请求 9 次，只统计状态码：

for i in $(seq 1 9); do
  kubectl -n notes-lab exec client -- curl -sS -m 2 -o /dev/null -w '%{http_code}\n' http://web 2>&1 | head -1
done | sort | uniq -c
3 000
6 200

大约三分之一的请求失败（000 表示 curl 没拿到 HTTP 响应）。第二轮重做时把错误信息也打出来，失败那次是：

code=000 ip=
curl: (7) Failed to connect to web:80 after 0 ms: Could not connect to server

直接 curl 这个 Pod 的 IP，报错一模一样：

$ kubectl -n notes-lab exec client -- curl -sS -m 2 http://$(kubectl -n notes-lab get pod stray -o jsonpath='{.status.podIP}'):80
curl: (7) Failed to connect to <pod-ip>:80 after 0 ms: Could not connect to server
command terminated with exit code 7

注意这和上一节「Service 没有端点」的报错文字完全相同，通常是 0 ms 的 Could not connect to server。区别在比例：没有端点时每次都失败，混进一个坏端点时只有一部分失败。看 EndpointSlice 里每个端点的 targetRef.name，很快就能发现混进来的那个。另外，第二轮里 stray Ready 后立刻查 EndpointSlice，它还没出现，8 秒后再查才有，EndpointSlice 的更新有短暂延迟。

如果标签打得更「全」，连 pod-template-hash 一起带上，结局是另一种。以下是第二轮的记录，先删掉 stray，再从 ReplicaSet 取当前的哈希（这次取到的是 668945bdf5，命令里直接写了这个值）：

kubectl -n notes-lab delete pod stray --wait=false
HASH=$(kubectl -n notes-lab get rs -l app=web -o jsonpath='{.items[0].metadata.labels.pod-template-hash}')
$ kubectl -n notes-lab run stray2 --image=nginx:alpine --labels=app=web,pod-template-hash=668945bdf5; kubectl -n notes-lab get pod stray2 -o jsonpath='{.status.phase} node={.spec.nodeName}{"\n"}'; sleep 2; kubectl -n notes-lab get pod stray2
pod/stray2 created
Pending node=worker
Error from server (NotFound): pods "stray2" not found
$ kubectl -n notes-lab get events --sort-by=.lastTimestamp -o custom-columns=TIME:.lastTimestamp,OBJ:.involvedObject.name,REASON:.reason,MSG:.message | grep -E 'stray2'
<nil>                  stray2                 Scheduled           Successfully assigned notes-lab/stray2 to worker
2026-10-13T06:16:30Z   web-668945bdf5         SuccessfulDelete    Deleted pod: stray2

SuccessfulDelete 来自 ReplicaSet web-668945bdf5，时间和创建 stray2 同一秒。由此推断：ReplicaSet 先收养了这个没有控制者的 Pod，发现副本多了一个，又把它删了。被删的偏偏是它而不是另外两个 Running 的 Pod，推测和它当时的 Pending 状态有关：官方文档的缩容排序第一条是「Pending (and unschedulable) pods are scaled down first」。不过 stray2 当时已经调度到了 worker，是否落在这一条里，这次没法确认。文档对此也有明确提醒：裸 Pod 不要带能匹配 ReplicaSet 选择器的标签，ReplicaSet 会收养不是从自己模板创建的 Pod。

删除：三种级联策略

orphan：留下 ReplicaSet，再被新 Deployment 收养

orphan 这一节换一个只打印名字、uid 和所有者的模板：

OR='{.metadata.name}{"  uid="}{.metadata.uid}{"\n  owner: "}{range .metadata.ownerReferences[*]}{.kind}/{.name} uid={.uid}{end}{"\n"}'
$ kubectl -n notes-lab delete deploy web --cascade=orphan
deployment.apps "web" deleted
$ kubectl -n notes-lab get rs,pod -l app=web -o jsonpath="{range .items[*]}$OR{end}"
web-668945bdf5  uid=ce675569-b123-414e-bb0c-9a6f0f163b47
  owner: 
web-668945bdf5-jcb82  uid=0984c842-db6a-47f7-817b-8688015de5e8
  owner: ReplicaSet/web-668945bdf5 uid=ce675569-b123-414e-bb0c-9a6f0f163b47
web-668945bdf5-lf7z8  uid=15003422-b5b1-4f3b-b095-06dc0fd24b60
  owner: ReplicaSet/web-668945bdf5 uid=ce675569-b123-414e-bb0c-9a6f0f163b47

只断开了 Deployment 和 ReplicaSet 之间这一环，ReplicaSet 到 Pod 的归属原样保留。孤儿 ReplicaSet 也不是一个死对象，把它的两个 Pod 都删掉：

$ kubectl -n notes-lab delete pod -l app=web --wait=false | head -1; sleep 3; kubectl -n notes-lab get pod -l app=web
pod "web-668945bdf5-jcb82" deleted
NAME                   READY   STATUS              RESTARTS   AGE
web-668945bdf5-24rgg   0/1     ContainerCreating   0          3s
web-668945bdf5-g48c8   0/1     ContainerCreating   0          3s
web-668945bdf5-jcb82   0/1     Completed           0          41s

-l app=web 匹配到 jcb82 和 lf7z8 两个 Pod，两个都删了，只是 head -1 只留下了第一行输出。3 秒后 lf7z8 已经从列表里消失，jcb82 还停在 Completed 等待移除；ReplicaSet 补了 24rgg、g48c8 两个新 Pod，没有 Deployment 也照样维持副本数。

重新 apply 原来的 web.yaml，得到一个新的 Deployment（uid f3a87606-...，原来是 e890f77a-...）：

$ kubectl -n notes-lab apply -f web.yaml
deployment.apps/web created
service/web unchanged
$ kubectl -n notes-lab get rs,pod -l app=web -o jsonpath="{range .items[*]}$OR{end}"
web-668945bdf5  uid=ce675569-b123-414e-bb0c-9a6f0f163b47
  owner: Deployment/web uid=f3a87606-2982-4b08-af75-29514f6d6279
web-668945bdf5-24rgg  uid=d0e4ddc2-83c2-46c5-acf0-9d806f05dad9
  owner: ReplicaSet/web-668945bdf5 uid=ce675569-b123-414e-bb0c-9a6f0f163b47
web-668945bdf5-g48c8  uid=960dd0e2-231d-4107-9aa7-564ef340b2d6
  owner: ReplicaSet/web-668945bdf5 uid=ce675569-b123-414e-bb0c-9a6f0f163b47

ReplicaSet 的 uid 没变，所有者换成了新 Deployment 的 uid；两个 Pod 的 uid 也和 apply 之前一样，没有重启。Deployment 的事件里没有新增任何 ScalingReplicaSet，收养是静默完成的。

如果重新创建时改了模板，旧 ReplicaSet 会被收养成历史版本，然后正常滚动更新。把 web.yaml 里的镜像换成 nginx:1.27 另存为 web-127.yaml，再做一次 orphan 删除后 apply：

$ kubectl -n notes-lab delete deploy web --cascade=orphan
deployment.apps "web" deleted
$ kubectl -n notes-lab apply -f web-127.yaml
deployment.apps/web created
service/web unchanged
$ kubectl -n notes-lab get events --field-selector involvedObject.kind=Deployment --sort-by=.lastTimestamp -o custom-columns=TIME:.lastTimestamp,REASON:.reason,MSG:.message | tail -5
...
2026-10-13T06:06:51Z   ScalingReplicaSet   Scaled up replica set web-66674c4d66 to 1
2026-10-13T06:06:54Z   ScalingReplicaSet   Scaled down replica set web-668945bdf5 to 1 from 2
2026-10-13T06:06:54Z   ScalingReplicaSet   Scaled up replica set web-66674c4d66 to 2 from 1
2026-10-13T06:06:58Z   ScalingReplicaSet   Scaled down replica set web-668945bdf5 to 0 from 1
$ kubectl -n notes-lab get rs -o 'custom-columns=NAME:.metadata.name,DESIRED:.spec.replicas,IMAGE:.spec.template.spec.containers[0].image,OWNER_UID:.metadata.ownerReferences[0].uid,REVISION:.metadata.annotations.deployment\.kubernetes\.io/revision'
NAME             DESIRED   IMAGE          OWNER_UID                              REVISION

rollout history 里能看到 revision 1 和 2，可以回滚到旧版本。所以 --cascade=orphan 适合「要删掉并重建 Deployment 对象本身，但不想动正在运行的 Pod」的场景，比如把对象交给另一套部署工具管理。前提是新对象的 selector 与旧的一致；selector 不一致时旧 ReplicaSet 按理不会被匹配到，推测会继续以孤儿身份运行（这次没有测）。

foreground 与 background：Deployment 什么时候消失

为了让删除过程看得见，换一个 Pod 退出较慢的 Deployment，保存为 slow.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: slow
spec:
  replicas: 2
  selector:
    matchLabels:
      app: slow
  template:
    metadata:
      labels:
        app: slow
    spec:
      terminationGracePeriodSeconds: 20
      containers:
        - name: nginx
          image: nginx:alpine
          lifecycle:
            preStop:
              exec:
                command: ["sleep", "8"]
          resources:
            requests:
              cpu: 20m
              memory: 32Mi
            limits:
              memory: 64Mi

删除时加 --wait=false，然后用下面的 poll.sh 每秒查一次 Deployment 和 ReplicaSet 的 deletionTimestamp、finalizers，以及 Pod 状态：

kc(){ kubectl -n notes-lab "$@"; }
for i in $(seq 1 $1); do
  d=$(kc get deploy slow -o jsonpath='{.metadata.deletionTimestamp}{" "}{.metadata.finalizers}' 2>/dev/null || echo gone); [ -z "$d" ] && d=gone
  rs=$(kc get rs -l app=slow -o jsonpath='{range .items[*]}{.metadata.deletionTimestamp}{" "}{.metadata.finalizers}{end}' 2>/dev/null); n=$(kc get rs -l app=slow --no-headers 2>/dev/null | wc -l)
  p=$(kc get pod -l app=slow --no-headers 2>/dev/null | awk '{print $3}' | sort | uniq -c | xargs)
  echo "$(date -u +%T) deploy=[$d] rs($n)=[$rs] pods=[$p]"
  sleep 1
done

--cascade=foreground：

$ kubectl -n notes-lab delete deploy slow --cascade=foreground --wait=false; bash poll.sh 16
deployment.apps "slow" deleted
06:07:21 deploy=[2026-10-13T06:07:21Z ["foregroundDeletion"]] rs(1)=[2026-10-13T06:07:21Z ["foregroundDeletion"]] pods=[2 Terminating]
06:07:22 deploy=[2026-10-13T06:07:21Z ["foregroundDeletion"]] rs(1)=[2026-10-13T06:07:21Z ["foregroundDeletion"]] pods=[2 Terminating]
...
06:07:30 deploy=[2026-10-13T06:07:21Z ["foregroundDeletion"]] rs(1)=[2026-10-13T06:07:21Z ["foregroundDeletion"]] pods=[2 Terminating]
06:07:31 deploy=[2026-10-13T06:07:21Z ["foregroundDeletion"]] rs(1)=[2026-10-13T06:07:21Z ["foregroundDeletion"]] pods=[2 Completed]
06:07:32 deploy=[gone] rs(0)=[] pods=[]

--cascade=background（kubectl delete 的默认值）。先重新 apply -f slow.yaml 等它就绪，再删：

$ kubectl -n notes-lab delete deploy slow --cascade=background --wait=false; bash poll.sh 14
deployment.apps "slow" deleted
06:07:47 deploy=[gone] rs(0)=[] pods=[2 Terminating]
06:07:48 deploy=[gone] rs(0)=[] pods=[2 Terminating]
...
06:07:58 deploy=[gone] rs(0)=[] pods=[2 Terminating]
06:07:59 deploy=[gone] rs(0)=[] pods=[1 Completed]
06:08:00 deploy=[gone] rs(0)=[] pods=[]

Pod 的退出时间两次差不多（10～13 秒，主要是 preStop 的 8 秒），区别在于 Deployment 和 ReplicaSet 何时从 API 中消失：

  • foreground：两者都被打上 deletionTimestamp 和 foregroundDeletion finalizer，一直留到 Pod 全部删除才消失。finalizer 是逐层传下去的，ReplicaSet 也在等它自己的 Pod。能挡住所有者删除的，只有 ownerReferences 里 blockOwnerDeletion=true 的从属对象；控制器创建的 ReplicaSet 和 Pod 都带着这个字段（见开头的输出），所以这里会等。
  • background：第一秒 Deployment 和 ReplicaSet 就查不到了，Pod 还在 Terminating，由垃圾回收器在后台清理。

脚本里如果删完 Deployment 紧接着用同名重建，background 下 Pod 可能还没退干净，新旧 Pod 会短暂共存；需要「彻底删完再继续」时用 foreground 并等待命令返回。

删 Service 不会动 Pod

这一节和下一节来自第二轮实验：新建了一个同名 namespace 重做，在里面 apply 同一份 web.yaml，所以输出是 created，Pod 名和 uid 与前文不同。

$ kubectl -n notes-lab apply -f web.yaml

Deployment 立刻按同一模板重建了 ReplicaSet，名字完全相同（哈希没变），但 uid 变了，是一个新对象。旧 Pod 被级联删除、新 Pod 还在创建，READY 一度为 0。第一轮做同样的操作结果一样。这不是滚动更新，没有任何 maxUnavailable 保护。想重启 Pod 用 kubectl rollout restart，不要删 ReplicaSet。

排查顺序

把上面的现象串起来，请求失败时可以沿两条链分别检查：

  1. 对象被接受了吗：kubectl get deploy，apply 成功只说明 API Server 收下了对象，READY 才说明控制器做到了。
  2. 副本归谁管：Pod 的 ownerReferences 指向哪个 ReplicaSet、uid 是否对得上；ownerReferences 为空的 Pod 是孤儿，不随发布更新。
  3. 后端有谁：EndpointSlice 是否为空，每个端点的 targetRef.name 是否都是预期的 Pod。空的就核对选择器拼写；多出来的就找带同样标签的「临时」Pod。
  4. 请求怎么失败：每次都失败，先看 EndpointSlice 是否为空；部分请求间歇性失败，先看是否混进了不该在里面的端点。两种情况下 curl 的报错可能一模一样，不要只凭报错文字判断；EndpointSlice 正常时再去看网络路径。

标签的设计原则见标签与选择器，控制器如何反复调谐见调谐循环，Deployment 的更新策略见 Deployment。

清理

kubectl delete namespace notes-lab
