Headless Service 与 Pod DNS

普通 Service 提供一个虚拟 IP，kube-proxy 把发往它的连接转给某个后端，客户端不必关心有几个 Pod。Headless Service 写 clusterIP: None，不分配虚拟 IP，也就没有转发这一层：集群 DNS 直接把后端 Pod 的地址交给客户端，连谁、怎么重试，由客户端自己决定。数据库、消息队列这类需要认出每个副本的应用常用它，StatefulSet 也靠它给每个 Pod 一个固定的域名。

「A 记录是一组 Pod IP」「缩到 0 或 Pod 未就绪时是 NXDOMAIN」在 DNS 排查里已经测过，StatefulSet 的 pod-0.svc 记录和 busybox nslookup 查带点短名的坑在 StatefulSet 里也写过，这里不重复。这一篇看的是这些记录具体长什么样：SRV 里的端口和目标名从哪来、没有 StatefulSet 时怎样给 Pod 起名、按 IP 拼出来的名字在这个集群里能不能用，以及 Pod 换了 IP 之后 DNS 要多久才跟上。

下文输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，CoreDNS v1.11.1（镜像 registry.k8s.io/coredns/coredns:v1.11.1），CNI 为 Calico，kube-proxy 为 iptables 模式，这两项是集群的已知配置，本文没有单独测），实验放在单独的 notes-lab namespace 里。集群 DNS 的 Service IP 写作 <dns-ip>，ClusterIP 写作 <cluster-ip>，Pod IP 按用途写成 <pod-a>、<db-0-ip> 这样的占位符；IP 拼成的域名同理写成 <pod-a-dashed>（实际是 a-b-c-d 这种把 IP 里的点换成横线的形式）。10.20.0.x、10.99.99.99 是我故意编的、集群里不存在的地址。

用 dig 而不是 busybox nslookup

busybox 的 nslookup 能查 A 和 SRV，但不显示 TTL，也不显示 SRV 应答里附带的 A 记录，下面关于缓存的实验没法用它做。节点上没有缓存 netshoot 之类带 dig 的镜像，我用已缓存的 alpine/socat 镜像（基于 Alpine）起一个 Pod，临时装上 bind-tools，10 秒左右装完：

apiVersion: v1
kind: Pod
metadata:
  name: dig
spec:
  containers:
    - name: dig
      image: alpine/socat:latest
      imagePullPolicy: IfNotPresent
      command: ["sh", "-c", "sleep 3600"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 64Mi}
$ kubectl -n notes-lab exec dig -- sh -c 'time apk add --no-cache bind-tools 2>&1 | tail -3; dig -v'
real	0m 10.57s
user	0m 0.21s
sys	0m 0.06s
DiG 9.20.29

这需要 Pod 能访问 Alpine 的软件源。busybox 客户端是 kubectl -n notes-lab run bb --image=busybox:1.36 --restart=Never -- sleep 600（实际运行时用 --overrides 另加了 10m CPU / 16Mi 的 requests）。拿后文用到的 ext-hl 作对比，看它在 busybox 1.36 里的样子：地址都在，TTL 没有。

$ kubectl -n notes-lab exec bb -- nslookup ext-hl.notes-lab.svc.cluster.local
Server:		<dns-ip>

同一组 Pod，两种 Service

后端是两副本的 traefik/whoami，它会在响应里打印 hostname，能看出请求落到了哪个 Pod。同一个选择器配两个 Service：web-hl 是 headless，web-vip 是普通 ClusterIP。两个 Service 都多开了一个 admin 端口，Service 端口 8080，targetPort 指向容器的 http（80），后面会看到这个映射在 headless 下的下场。保存为 web.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.10.2
          ports:
            - name: http
              containerPort: 80
          resources:
            requests: {cpu: 10m, memory: 16Mi}
            limits: {memory: 32Mi}
---
apiVersion: v1
kind: Service
metadata:
  name: web-hl
spec:
  clusterIP: None
  selector:
    app: web
  ports:
    - name: http
      port: 80
      targetPort: http
    - name: admin
      port: 8080
      targetPort: http
---
apiVersion: v1
kind: Service
metadata:
  name: web-vip
spec:
  selector:
    app: web
  ports:
    - name: http
      port: 80
      targetPort: http
    - name: admin
      port: 8080
      targetPort: http
kubectl -n notes-lab apply -f web.yaml
kubectl -n notes-lab rollout status deploy/web --timeout=90s
kubectl -n notes-lab get svc
kubectl -n notes-lab get endpointslice
NAME      TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)           AGE
web-hl    ClusterIP   None           <none>        80/TCP,8080/TCP   10s
web-vip   ClusterIP   <cluster-ip>   <none>        80/TCP,8080/TCP   9s
NAME            ADDRESSTYPE   PORTS   ENDPOINTS                        AGE
web-hl-4hjt4    IPv4          80,80   <pod-a>,<pod-b>   9s
web-vip-vppwp   IPv4          80,80   <pod-a>,<pod-b>   8s

TYPE 一栏两个都是 ClusterIP，区别只在 CLUSTER-IP 是不是 None。两个 Service 的 EndpointSlice 内容一样，PORTS 都是 80,80：两个端口都解析到了容器的 80。

A 记录：一个虚拟 IP，还是一组 Pod IP

$ kubectl -n notes-lab exec dig -- dig +noall +answer +comments web-hl.notes-lab.svc.cluster.local A
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12171
;; flags: qr aa rd; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1
;; ANSWER SECTION:
web-hl.notes-lab.svc.cluster.local. 30	IN A <pod-a>
web-hl.notes-lab.svc.cluster.local. 30	IN A <pod-b>

$ kubectl -n notes-lab exec dig -- dig +noall +answer web-vip.notes-lab.svc.cluster.local A
web-vip.notes-lab.svc.cluster.local. 30 IN A <cluster-ip>

（第一段省略了 dig 关于 .local 和 EDNS 的几行提示。）aa 表示这是 CoreDNS 作为 cluster.local 权威给出的答案。TTL 是 30 秒，来自这个集群 Corefile 里 kubernetes 插件的 ttl 30；CoreDNS 插件文档写的默认值是 5 秒，所以别的集群可能不一样，先看 kubectl -n kube-system get cm coredns。

连续查 4 次，两个地址的顺序会变：

<pod-b> <pod-a> 
<pod-b> <pod-a> 
<pod-b> <pod-a> 
<pod-a> <pod-b>

Corefile 里启用了 loadbalance 插件，它会打乱 A 记录的顺序。很多客户端只取第一个地址，这就是 headless 下唯一的「负载均衡」，而且它只在发起查询时起作用，客户端拿到地址后一直连同一个，流量就不会再分散。

kube-proxy 也完全不管 headless Service。在节点上数规则，web-hl 一条都没有，web-vip 则有（此时 Deployment 已经缩到 0，所以是 REJECT 规则）：

$ docker exec <集群名>-worker2 iptables-save | grep -c 'notes-lab/web-hl'
0
$ docker exec <集群名>-worker2 iptables-save | grep 'notes-lab/web-vip' | head -3
-A KUBE-SERVICES -d <cluster-ip>/32 -p tcp -m comment --comment "notes-lab/web-vip:http has no endpoints" -m tcp --dport 80 -j REJECT --reject-with icmp-port-unreachable
-A KUBE-SERVICES -d <cluster-ip>/32 -p tcp -m comment --comment "notes-lab/web-vip:admin has no endpoints" -m tcp --dport 8080 -j REJECT --reject-with icmp-port-unreachable

SRV 记录：端口号是 Pod 的，不是 Service 的

SRV 记录的名字是 _端口名._协议.服务名...，只有起了名字的端口才有。先看两个 Service 的 http 端口：

$ kubectl -n notes-lab exec dig -- dig +noall +answer +additional SRV _http._tcp.web-hl.notes-lab.svc.cluster.local
_http._tcp.web-hl.notes-lab.svc.cluster.local.	30 IN SRV 0 50 80 <pod-a-dashed>.web-hl.notes-lab.svc.cluster.local.
_http._tcp.web-hl.notes-lab.svc.cluster.local.	30 IN SRV 0 50 80 <pod-b-dashed>.web-hl.notes-lab.svc.cluster.local.
<pod-b-dashed>.web-hl.notes-lab.svc.cluster.local. 30 IN A <pod-b>
<pod-a-dashed>.web-hl.notes-lab.svc.cluster.local. 30	IN A <pod-a>

$ kubectl -n notes-lab exec dig -- dig +noall +answer +additional SRV _http._tcp.web-vip.notes-lab.svc.cluster.local
_http._tcp.web-vip.notes-lab.svc.cluster.local. 30 IN SRV 0 100 80 web-vip.notes-lab.svc.cluster.local.
web-vip.notes-lab.svc.cluster.local. 30 IN A <cluster-ip>

SRV 的四个字段依次是优先级、权重、端口、目标。headless Service 每个 Pod 一条，目标是 Pod 的域名；因为这两个 Pod 没有设置 hostname，CoreDNS 用 IP 换成横线的形式当名字，并在附加段里顺带给出它们的 A 记录，客户端一次查询就能拿到端口和地址。ClusterIP Service 只有一条，目标是 Service 自己。

再查 admin 端口，差别就出来了：

$ kubectl -n notes-lab exec dig -- dig +noall +answer SRV _admin._tcp.web-hl.notes-lab.svc.cluster.local
_admin._tcp.web-hl.notes-lab.svc.cluster.local. 30 IN SRV 0 50 80 <pod-a-dashed>.web-hl.notes-lab.svc.cluster.local.
_admin._tcp.web-hl.notes-lab.svc.cluster.local. 30 IN SRV 0 50 80 <pod-b-dashed>.web-hl.notes-lab.svc.cluster.local.

（命令实际带了 +additional，附加段与上面相同，这里省略。）headless Service 的 admin SRV 里端口是 80，不是 Service 上写的 8080。ClusterIP 一侧我当时没有单独查 _admin._tcp.web-vip，而是直接查了不带 _端口._协议 前缀的 Service 名。这是 CoreDNS 的扩展用法，Kubernetes DNS 规范里没有：它把所有端口的 SRV 一起返回。两边都用这种方式查，对比如下：

$ kubectl -n notes-lab exec dig -- dig +noall +answer SRV web-hl.notes-lab.svc.cluster.local
web-hl.notes-lab.svc.cluster.local. 30	IN SRV 0 25 80 <pod-a-dashed>.web-hl.notes-lab.svc.cluster.local.
web-hl.notes-lab.svc.cluster.local. 30	IN SRV 0 25 80 <pod-b-dashed>.web-hl.notes-lab.svc.cluster.local.
$ kubectl -n notes-lab exec dig -- dig +noall +answer SRV web-vip.notes-lab.svc.cluster.local
web-vip.notes-lab.svc.cluster.local. 30 IN SRV	0 50 80 web-vip.notes-lab.svc.cluster.local.
web-vip.notes-lab.svc.cluster.local. 30 IN SRV	0 50 8080 web-vip.notes-lab.svc.cluster.local.

ClusterIP Service 列出了 80 和 8080 两个端口。headless Service 只有端口 80 的记录，而且权重是 25。CoreDNS v1.11.1 的 plugin/backend_lookup.go 在 SRV() 里先按全部 4 条（2 个端点 × 2 个端口，每条 100）算权重，100×100/400 = 25；之后 isDuplicate 把目标和端口都相同的记录去掉（源码注释原话是 “we may drop duplicate SRV records latter on”）。两个端口都是 Pod 的 80，所以只剩 2 条，权重加起来是 50 而不是 100。headless 的记录来自 EndpointSlice，而 EndpointSlice 里存的是解析后的目标端口：

$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=web-hl -o jsonpath='{.items[0].ports}'
[{"name":"http","port":80,"protocol":"TCP"},{"name":"admin","port":80,"protocol":"TCP"}]

故障：headless Service 上的端口映射不生效

这在客户端上表现为：同样的 名字:8080，ClusterIP 能通，headless 连接被拒：

$ kubectl -n notes-lab exec dig -- wget -qO- -T 3 http://web-vip:8080/ | grep Hostname
Hostname: web-56d67c887-qgdtf
$ kubectl -n notes-lab exec dig -- wget -qO- -T 3 http://web-hl:8080/
wget: can't connect to remote host (<pod-b>): Connection refused
command terminated with exit code 1
$ kubectl -n notes-lab exec dig -- wget -qO- -T 3 http://web-hl:80/ | grep Hostname
Hostname: web-56d67c887-g5d9w

web-hl 解析出来就是 Pod IP，连接直接发到 Pod 的 8080，那里没有进程监听。8080→80 的映射是 kube-proxy 在虚拟 IP 上做的，headless 没有虚拟 IP，这一层就不存在。所以 headless Service 上写 port 和 targetPort 不一样基本没有意义；客户端要么连容器真正监听的端口，要么查 SRV 拿端口。报错里括号中的 IP 是 Pod IP 而不是 ClusterIP，这是判断「我连的其实是 headless」的线索。

给每个 Pod 一个名字

StatefulSet：SRV 的目标变成 Pod 名

StatefulSet db（2 副本）配一个 headless Service db-hl，serviceName: db-hl。每个 Pod 的记录在 StatefulSet 里测过，这里只看它和上面的差别。用到的清单如下：

apiVersion: v1
kind: Service
metadata:
  name: db-hl
spec:
  clusterIP: None
  selector:
    app: db
  ports:
    - name: http
      port: 80
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db-hl
  replicas: 2
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.10.2
          ports:
            - name: http
              containerPort: 80
          resources:
            requests: {cpu: 10m, memory: 16Mi}
            limits: {memory: 32Mi}

SRV 目标从 IP 横线名变成了 db-0、db-1：

$ kubectl -n notes-lab exec dig -- dig +noall +answer SRV _http._tcp.db-hl.notes-lab.svc.cluster.local
_http._tcp.db-hl.notes-lab.svc.cluster.local. 30 IN SRV 0 50 80 db-0.db-hl.notes-lab.svc.cluster.local.
_http._tcp.db-hl.notes-lab.svc.cluster.local. 30 IN SRV 0 50 80 db-1.db-hl.notes-lab.svc.cluster.local.

原因在 EndpointSlice 的 hostname 字段，StatefulSet 的 Pod 会被填上自己的名字：

$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=db-hl \
    -o jsonpath='{range .items[*].endpoints[*]}{.targetRef.name} hostname={.hostname}{"\n"}{end}'
db-0 hostname=db-0
db-1 hostname=db-1

普通 Pod：hostname + subdomain

不用 StatefulSet 也能得到同样的效果。Pod 的 spec.hostname 和 spec.subdomain 两个字段，subdomain 写成 headless Service 的名字，这个 Pod 又被该 Service 选中，就会有 <hostname>.<subdomain>.<namespace>.svc.cluster.local。我建了两个带 app: web 标签的 Pod：solo 写对了，typo 把 subdomain 写成了 web-headless：

apiVersion: v1
kind: Pod
metadata:
  name: solo
  labels:
    app: web
spec:
  hostname: solo
  subdomain: web-hl          # typo 这个 Pod 写成了 web-headless
  containers:
    - name: whoami
      image: traefik/whoami:v1.10.2
      ports:
        - name: http
          containerPort: 80
$ kubectl -n notes-lab exec dig -- dig +noall +answer solo.web-hl.notes-lab.svc.cluster.local
solo.web-hl.notes-lab.svc.cluster.local. 30 IN	A <solo-ip>
$ kubectl -n notes-lab exec dig -- dig +noall +answer SRV _http._tcp.web-hl.notes-lab.svc.cluster.local
_http._tcp.web-hl.notes-lab.svc.cluster.local.	30 IN SRV 0 33 80 <pod-a-dashed>.web-hl.notes-lab.svc.cluster.local.
_http._tcp.web-hl.notes-lab.svc.cluster.local.	30 IN SRV 0 33 80 solo.web-hl.notes-lab.svc.cluster.local.
_http._tcp.web-hl.notes-lab.svc.cluster.local.	30 IN SRV 0 33 80 <typo-dashed>.web-hl.notes-lab.svc.cluster.local.
$ kubectl -n notes-lab exec dig -- dig +noall +answer web-hl.notes-lab.svc.cluster.local
web-hl.notes-lab.svc.cluster.local. 30	IN A <pod-a>
web-hl.notes-lab.svc.cluster.local. 30	IN A <typo-ip>
web-hl.notes-lab.svc.cluster.local. 30	IN A <solo-ip>

（此时 Deployment 已缩到 1 副本，所以只剩一个 <pod-a>。）solo 的名字能解析，用这个名字访问，whoami 报出的 hostname 也是 solo：

$ kubectl -n notes-lab exec dig -- wget -qO- http://solo.web-hl/ | head -3
Hostname: solo
IP: 127.0.0.1
IP: ::1

故障：subdomain 写错，Pod 在名单里，名字却查不到

typo 是这个实验里最容易误判的情况：它的 IP 好好地出现在 web-hl 的 A 记录里，流量也能打到它，但它自己的名字查不到，写错的那个名字、改正后的名字都查不到：

$ kubectl -n notes-lab exec dig -- dig +noall +comments typo.web-headless.notes-lab.svc.cluster.local | grep status
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 13305
$ kubectl -n notes-lab exec dig -- dig +noall +comments typo.web-hl.notes-lab.svc.cluster.local | grep status
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 7115
$ kubectl -n notes-lab exec dig -- wget -qO- http://typo.web-hl/
wget: bad address 'typo.web-hl'
command terminated with exit code 1

在 SRV 里它也露了馅，目标是 IP 横线名而不是 typo。直接的证据在 EndpointSlice：

$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=web-hl \
    -o jsonpath='{range .items[*].endpoints[*]}{.targetRef.name} hostname={.hostname} ready={.conditions.ready}{"\n"}{end}'
web-56d67c887-g5d9w hostname= ready=true
solo hostname=solo ready=true
typo hostname= ready=true

控制器只在 Pod 的 subdomain 等于 Service 名时才给端点填 hostname，typo 是 ready=true 但 hostname 为空。同一个 Pod 被 ClusterIP 的 web-vip 选中时，三个端点的 hostname 全是空的。所以「Pod 名字查不到」先看这个字段：空的，就去核对 Pod 的 subdomain 和 Service 名是否一字不差、在不在同一个 namespace。subdomain 属于 Pod spec，创建后不能改，只能删掉重建。

意外：subdomain 指向普通 Service，CoreDNS 也给了记录

官方文档的说法是：存在一个与 subdomain 同名的 headless Service 时，DNS 才返回这个 Pod 完整主机名的记录。我顺手试了反例，起一个 hostname: vipsub、subdomain: web-vip 的 Pod（清单同上面的 solo，只改了名字、hostname 和 subdomain），web-vip 是有 ClusterIP 的普通 Service：

$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=web-vip \
    -o jsonpath='{range .items[*].endpoints[*]}{.targetRef.name} hostname={.hostname}{"\n"}{end}'
web-56d67c887-g5d9w hostname=
solo hostname=
vipsub hostname=vipsub
$ kubectl -n notes-lab exec dig -- dig +noall +comments +answer vipsub.web-vip.notes-lab.svc.cluster.local | grep -E 'status|IN'
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 46994
vipsub.web-vip.notes-lab.svc.cluster.local. 30	IN A <vipsub-ip>

EndpointSlice 控制器照样填了 hostname，CoreDNS 照样应答。同样，<pod-a-dashed>.web-vip... 这种横线名在普通 Service 下也能解析出 Pod IP，而 web-vip 本身的 A 和 SRV 记录仍然只给虚拟 IP：

$ kubectl -n notes-lab exec dig -- dig +noall +answer web-vip.notes-lab.svc.cluster.local
web-vip.notes-lab.svc.cluster.local. 30 IN A <cluster-ip>
$ kubectl -n notes-lab exec dig -- dig +noall +answer <pod-a-dashed>.web-vip.notes-lab.svc.cluster.local

代码里能找到原因。EndpointSlice 控制器只比较 Pod 的 subdomain 和 Service 名，相同就填 hostname，不管 Service 是不是 headless。CoreDNS v1.11.1 的 plugin/kubernetes/kubernetes.go 里，findServices 的判断是 if svc.Headless() || r.endpoint != ""：只要查询名里带了端点这一段（vipsub.、a-b-c-d.），就去 EndpointSlice 里找，同样不要求 headless。不过 Kubernetes 文档只承诺 headless Service 下有这些记录，换一种 DNS 实现或者换个 CoreDNS 版本，未必还是这样。要给 Pod 起名，还是按文档用 headless Service。

按 IP 拼出来的名字：pods insecure 不做任何校验

还有一类名字和 Service 无关：<IP 横线形式>.<namespace>.pod.cluster.local。文档把它归为早期 kube-dns 的行为，CoreDNS 是否提供取决于 kubernetes 插件的 pods 选项。只读查看 kubectl -n kube-system get cm coredns -o yaml，这个集群的 Corefile 里是：

kubernetes cluster.local in-addr.arpa ip6.arpa {
   pods insecure
   fallthrough in-addr.arpa ip6.arpa
   ttl 30
}

insecure 按 CoreDNS 文档的说法是「直接用请求里的 IP 返回 A 记录，不去查 Kubernetes」。实测确实如此，一个不存在的 IP 也能解析，换个 namespace 也照样给：

$ kubectl -n notes-lab exec dig -- dig +noall +answer <pod-b-dashed>.notes-lab.pod.cluster.local
<pod-b-dashed>.notes-lab.pod.cluster.local. 30	IN A <pod-b>
--- nonexistent IP, same ns
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 64300
10-99-99-99.notes-lab.pod.cluster.local. 30 IN	A 10.99.99.99
--- real pod IP, wrong namespace
<pod-b-dashed>.kube-system.pod.cluster.local. 30 IN A <pod-b>
--- nonexistent namespace
--- service-scoped dashed name, IP not an endpoint
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 28633

--- nonexistent namespace 下面是空的，单独查状态是 NXDOMAIN，default namespace 则正常返回：

$ kubectl -n notes-lab exec dig -- dig +noall +comments <pod-b-dashed>.no-such-ns.pod.cluster.local | grep status
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 19271
$ kubectl -n notes-lab exec dig -- dig +short <pod-b-dashed>.default.pod.cluster.local
<pod-b>

也就是说，它只检查 namespace 存在，IP 是什么就回什么。文档没提 namespace 这一层，但 CoreDNS v1.11.1 的 findPods 一开头就是 if !k.namespaceExposed(namespace) { return nil, errNoItems }，namespace 不存在就是 NXDOMAIN，接下来把横线换回点，直接当 IP 返回。这类名字等于把 IP 换了个写法，不能证明「这个 IP 属于某个 Pod」，也不会随 Pod 重建而更新。CoreDNS 文档说，pods 选项本来就是为了直连 Pod 时方便使用 SSL 证书；它同时提醒，insecure 模式如果和通配符证书一起被恶意利用，就会被滥用。也就是说，有一张 *.<ns>.pod.cluster.local 的证书，再配合 insecure，任何 IP 都能冒充成这个名字。对比之下，Service 下的横线名 10-99-99-99.web-hl... 是 NXDOMAIN：Service 范围内的名字只对真实端点有效。如果 Corefile 写的是 pods verified，按文档会先确认同 namespace 里存在这个 IP 的 Pod，这次没有测。

反向解析时，Pod IP 会同时返回它所属的每个 Service 下的横线名，普通 Service 也算：

$ kubectl -n notes-lab exec dig -- dig +noall +answer -x <pod-b>
<pod-b-reversed>.in-addr.arpa. 30	IN	PTR	<pod-b-dashed>.web-hl.notes-lab.svc.cluster.local.
<pod-b-reversed>.in-addr.arpa. 30	IN	PTR	<pod-b-dashed>.web-vip.notes-lab.svc.cluster.local.

Pod 换了 IP，DNS 多久跟上

headless 把 Pod IP 直接交给了客户端，IP 一变，客户端拿到的就是缓存里的旧值。CoreDNS 自己有 cache 30，记录 TTL 也是 30 秒，下面按秒测三种情况。

dig Pod 里跑一个循环，每秒查一次，打印时间、响应码、剩余 TTL 和地址：

i=0; while [ $i -lt 75 ]; do
  r=$(dig +noall +comments +answer db-0.db-hl.notes-lab.svc.cluster.local 2>/dev/null \
      | tr '\t' ' ' | grep -E 'status:| IN ' \
      | sed -E 's/.*status: ([A-Z]+),.*/\1/; s/db-0\.db-hl\.[^ ]* //' | tr '\n' ' ')
  echo "$(date -u +%T) $r"; i=$((i+1)); sleep 1
done

（tr '\t' ' ' 不能省。dig 输出的字段之间有时是空格、有时是制表符，我第一次用 / IN A / 去匹配，TTL 降到个位数附近的几秒全被当成了空结果，差点得出「有十秒查不到记录」的错误结论。）

没有选择器：手工维护 EndpointSlice

pg-z.ext-hl.notes-lab.svc.cluster.local. 30 IN	A 10.20.0.99
$ kubectl -n notes-lab exec dig -- dig +short ext-hl.notes-lab.svc.cluster.local | sort
10.20.0.11
10.20.0.13

pg-z 马上能查到了，可同一时刻查 ext-hl 还是只有两个地址，缺 10.20.0.99，过一会儿再查就是三个。推测是之前那次 ext-hl 查询的结果还在缓存里，pg-z 的那次则恰好落到了没有缓存它的副本上；查询每次随机落到哪个副本，这次没有核实。改了 EndpointSlice 之后，立即验证看到的不一定是新结果。

SRV 的名字取自 EndpointSlice 的端口名

再把 ext-hl-1 的端口名从 pg 改成 postgres，Service 上的端口名仍然是 pg：

$ kubectl -n notes-lab exec dig -- dig +noall +answer SRV _pg._tcp.ext-hl.notes-lab.svc.cluster.local
_pg._tcp.ext-hl.notes-lab.svc.cluster.local. 30 IN SRV	0 100 5432 pg-z.ext-hl.notes-lab.svc.cluster.local.
$ kubectl -n notes-lab exec dig -- dig +noall +answer SRV _postgres._tcp.ext-hl.notes-lab.svc.cluster.local
_postgres._tcp.ext-hl.notes-lab.svc.cluster.local. 30 IN SRV 0 50 5432 pg-a.ext-hl.notes-lab.svc.cluster.local.
_postgres._tcp.ext-hl.notes-lab.svc.cluster.local. 30 IN SRV 0 50 5432 10-20-0-13.ext-hl.notes-lab.svc.cluster.local.

_pg._tcp 只剩 ext-hl-nolabel 里的 pg-z，另外两个地址跑到了一个 Service 上根本没有定义的 _postgres._tcp 下。CoreDNS 生成 SRV 时用的是 EndpointSlice 的端口名。A 记录不受影响，三个地址都在，所以只用 A 记录的客户端发现不了这个问题，按 SRV 发现成员的客户端会少一部分节点。手写 EndpointSlice 时，端口名要和 Service 保持一致。

对比：ExternalName

ExternalName Service 既不分配 IP，也不选 Pod，DNS 只返回一条 CNAME：

$ kubectl -n notes-lab create service externalname alias --external-name=ext-hl.notes-lab.svc.cluster.local
service/alias created
$ kubectl -n notes-lab exec dig -- dig +noall +answer alias.notes-lab.svc.cluster.local
alias.notes-lab.svc.cluster.local. 30 IN CNAME	ext-hl.notes-lab.svc.cluster.local.
ext-hl.notes-lab.svc.cluster.local. 30	IN A 10.20.0.13
ext-hl.notes-lab.svc.cluster.local. 30	IN A 10.20.0.11
ext-hl.notes-lab.svc.cluster.local. 30	IN A 10.20.0.99

目标恰好是集群内的名字，CoreDNS 顺手把 CNAME 也解析了。它适合给一个已经有域名的东西起别名；后端只有 IP 时，用上面的无选择器 headless Service。

排查清单

  1. 连接被拒，报错里是 Pod IP：连的是 headless Service，端口映射不生效，换成容器实际监听的端口，或查 SRV。
  2. Service 名能查到，Pod 名查不到：看 EndpointSlice 端点的 hostname。空的，就核对 Pod 的 subdomain 和 Service 名；StatefulSet 则核对 serviceName 对应的 Service 是否存在。
  3. 地址刚变或刚扩容，DNS 结果不对：先看 TTL（dig 才看得到）。CoreDNS 会缓存正向答案和 NXDOMAIN，这个集群里都是 30 秒，两个 CoreDNS 副本的结果可能不同，等一个 TTL 再下结论。
  4. 手工 EndpointSlice 不生效：标签 kubernetes.io/service-name 有没有，端口名和 Service 是否一致，conditions.ready 是不是 false。
  5. <ip>.<ns>.pod.cluster.local 能解析：在 pods insecure 下这不说明任何事情，别拿它判断 Pod 是否存在。

清理

kubectl delete namespace notes-lab
