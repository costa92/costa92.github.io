NetworkPolicy 网络隔离

Service 给后端提供了稳定入口，但不管谁能访问后端。NetworkPolicy 用 Pod 和 Namespace 的标签描述「允许哪些流量」，真正执行规则的是网络插件：API Server 只负责保存对象，CNI 不支持 NetworkPolicy 时，kubectl apply 照样成功，流量却一点不受影响。所以 kubectl get networkpolicy 能列出对象，并不能证明隔离已经生效，要用真实连接去验证。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18），CNI 是 Calico v3.32.1，数据面用的是 iptables 模式（FelixConfiguration 里 bpfEnabled: false、nftablesMode: Disabled）。实验放在 notes-lab namespace，跨 namespace 的测试另建了 notes-lab-b。节点名简化为 worker、worker2，Pod IP 用 <web-ip> 之类的占位符代替。

准备：一个服务端，两个客户端

服务端是一个 nginx，客户端是两个只有标签不同的 busybox：

apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  containers:
    - name: nginx
      image: nginx:alpine
      ports:
        - containerPort: 80
---
apiVersion: v1
kind: Pod
metadata:
  name: client
  labels:
    role: client
spec:
  containers:
    - name: sh
      image: busybox:1.36
      command: ["sleep", "3600"]
---
apiVersion: v1
kind: Pod
metadata:
  name: other
  labels:
    role: other
spec:
  containers:
    - name: sh
      image: busybox:1.36
      command: ["sleep", "3600"]
kubectl create namespace notes-lab
kubectl -n notes-lab apply -f pods.yaml
kubectl -n notes-lab create service clusterip web --tcp=80:80
kubectl -n notes-lab wait --for=condition=Ready pod --all --timeout=180s
WEB_IP=$(kubectl -n notes-lab get pod web -o jsonpath='{.status.podIP}')

web 落在 worker，两个客户端都在 worker2，测试流量会跨节点。没有任何策略时，两个客户端都能访问 web。另外先记下一个基线：访问 web 上一个没有进程监听的端口 81，会立刻得到拒绝：

$ kubectl -n notes-lab exec client -- sh -c "time wget -qO- -T 5 http://<web-ip>:81"
wget: can't connect to remote host (<web-ip>): Connection refused
Command exited with non-zero status 1
real	0m 0.00s

这个 Connection refused 是 web 的内核回的 RST：包到达了 Pod，只是端口上没人监听。后面会用到这个对照。

默认拒绝入站

podSelector: {} 选中 namespace 里的所有 Pod，policyTypes 里有 Ingress 却不写任何 ingress 规则，效果就是「这些 Pod 的入站全部拒绝」：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes:
    - Ingress

应用后，按 Service 名、按 Pod IP、从哪个客户端访问都一样，全部卡满 5 秒超时：

$ kubectl -n notes-lab exec client -- sh -c "time wget -qO- -T 5 http://<web-ip>"
wget: download timed out
Command exited with non-zero status 1
real	0m 5.00s

最值得注意的是端口 81。刚才它是 0 秒返回的 Connection refused，现在变成了：

$ kubectl -n notes-lab exec client -- sh -c "time wget -qO- -T 5 http://<web-ip>:81"
wget: download timed out
Command exited with non-zero status 1
real	0m 5.00s

为什么是超时而不是拒绝

被策略拦下的包是被静默丢弃的，客户端发出的 SYN 收不到任何回应，只能等到自己的超时。在 web 所在节点上看 Calico 为这个 Pod 的网卡生成的 iptables 链（节选）。kind 的节点就是 docker 容器，容器名形如 <集群名>-worker，下面简写为 worker：

$ docker exec worker sh -c "iptables-save -t filter | grep -E '^-A cali-tw-calif6452de636f '"
-A cali-tw-calif6452de636f ... -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
-A cali-tw-calif6452de636f ... -m conntrack --ctstate INVALID -j DROP
...
-A cali-tw-calif6452de636f ... -m mark --mark 0x0/0x20000 -j cali-pi-_HrHfYwkdbK-Ei7cTvSV
-A cali-tw-calif6452de636f ... -m comment --comment "Return if policy accepted" -m mark --mark 0x10000/0x10000 -j RETURN
-A cali-tw-calif6452de636f ... -m mark --mark 0x0/0x20000 -j NFLOG --nflog-prefix "DPI|default" --nflog-group 1 --nflog-size 80
-A cali-tw-calif6452de636f ... -m comment --comment "End of tier default. Drop if no policies passed packet" -m mark --mark 0x0/0x20000 -j DROP

cali-tw-<网卡> 是发往该 Pod 的流量要过的链（tw 即 to workload）。没被任何策略放行的包落到最后的 DROP，而不是 REJECT，这就是客户端只能看到超时的原因。包在到达 Pod 之前就被丢了，所以无论端口上有没有进程，表现都一样。

这给排查提供了一个很实用的信号：

  • Connection refused：直连 Pod IP 时，说明包到了目标 Pod，是应用没在这个端口监听，或者监听地址不对，和 NetworkPolicy 无关；
  • 超时：包在半路被丢了，NetworkPolicy 是嫌疑之一，但网络不通、路由问题也会表现成超时，需要再排除。

这是 Calico 的默认行为，不是 NetworkPolicy 的规定。本集群 Calico 使用默认的 iptablesFilterDenyAction: Drop（nftables 模式对应 nftablesFilterDenyAction）；改成 Reject 或换用别的 CNI 时，被拦的连接也可能返回拒绝，换了环境要重新验证。

按 podSelector 放行

在默认拒绝之上，只给 role=client 开放 web 的 TCP 80：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-allow-client
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              role: client
      ports:
        - protocol: TCP
          port: 80
$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://web | grep title
<title>Welcome to nginx!</title>
$ kubectl -n notes-lab exec other -- wget -qO- -T 3 http://web
wget: download timed out
command terminated with exit code 1
$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://<web-ip>:81
wget: download timed out
command terminated with exit code 1

client 通了，other 仍然超时；client 访问 81 也超时，因为规则限定了端口 80。

kubectl get networkpolicy 的 POD-SELECTOR 列显示的是策略作用于谁，<none> 表示空选择器，也就是全部 Pod：

NAME                   POD-SELECTOR   AGE
default-deny-ingress   <none>         61s
web-allow-client       app=web        14s

多条策略取并集

NetworkPolicy 没有顺序，也没有「拒绝」规则。同一个 Pod 被多条策略选中时，允许的流量是各条策略允许范围的并集。默认拒绝那条策略什么都不允许，它的作用只是让所有 Pod 进入「被隔离」状态。

再加一条策略放行 role=other，这次故意不写 ports：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-allow-other
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              role: other

两个客户端分别访问 80 和 81：

$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://<web-ip>:80 | grep title
<title>Welcome to nginx!</title>
$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://<web-ip>:81 | grep title
wget: download timed out
command terminated with exit code 1
$ kubectl -n notes-lab exec other -- wget -qO- -T 3 http://<web-ip>:80 | grep title
<title>Welcome to nginx!</title>
$ kubectl -n notes-lab exec other -- wget -qO- -T 3 http://<web-ip>:81 | grep title
wget: can't connect to remote host (<web-ip>): Connection refused
command terminated with exit code 1

四个结果正好对应两条策略的并集：

来源端口 80端口 81
client（只命中 web-allow-client，限 80）通超时，被策略丢弃
other（只命中 web-allow-other，不限端口）通拒绝，策略放行了，但没人监听

other 访问 81 得到的是 Connection refused，又一次印证上一节的判断：能收到拒绝，说明策略这一关已经过了。

默认拒绝出站：先坏掉的是 DNS

给 client 加一条只有 Egress 类型、没有规则的策略：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: client-deny-egress
spec:
  podSelector:
    matchLabels:
      role: client
  policyTypes:
    - Egress
$ kubectl -n notes-lab exec client -- sh -c "time nslookup web.notes-lab.svc.cluster.local"
;; connection timed out; no servers could be reached

Command exited with non-zero status 1
real	0m 5.00s
$ kubectl -n notes-lab exec client -- sh -c "time wget -qO- -T 5 http://web"
wget: bad address 'web'
Command exited with non-zero status 1
real	0m 20.02s

第二条输出容易误导：bad address 看起来像域名写错了，其实是发往 DNS 的 UDP 53 被拦了。而且 wget -T 5 管不到域名解析这一步，命令实际卡了 20 秒。推测这是解析器按 resolv.conf 里的 search 域（ndots:5 下短名 web 会依次拼上几个后缀）逐个查询、每次都等到超时累加出来的，这次没有逐条抓包确认。排查出站策略时，先用 nslookup 单独测解析，再用 Pod IP 测连通，把两件事分开。DNS 本身的排查见 DNS 排查。

放行 DNS：按 Pod 选，不要按 Service IP

Pod 的 /etc/resolv.conf 里写的是 kube-dns Service 的 ClusterIP，直觉上会写一条 ipBlock 放行这个地址：

egress:
  - to:
      - ipBlock:
          cidr: <kube-dns-ip>/32
    ports:
      - protocol: UDP
        port: 53
      - protocol: TCP
        port: 53

应用后解析依旧失败：

$ kubectl -n notes-lab exec client -- sh -c "time nslookup web.notes-lab.svc.cluster.local"
;; connection timed out; no servers could be reached

Command exited with non-zero status 1
real	0m 5.00s

官方文档本来就说 ipBlock 应该用于集群外部的 IP，Pod IP 是临时且不可预测的。推测这里失败的原因是：到 Service IP 的包先被 kube-proxy 做了 DNAT，目的地址换成了 CoreDNS Pod 的 IP，Calico 判断策略时看到的已经不是 ClusterIP。官方文档对此的说法是，地址改写发生在策略处理之前还是之后「没有定义」，不同插件和 Service 实现可能不同。旁证是下一节的 client-allow-web：它用 podSelector 选中 web，客户端经 Service 名（也就是 ClusterIP）访问 http://web 照样放行，说明策略匹配的是 DNAT 之后的 Pod。所以更可靠的写法是直接选中 CoreDNS 的 Pod：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: client-allow-dns
spec:
  podSelector:
    matchLabels:
      role: client
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53

kubernetes.io/metadata.name 是 Kubernetes 自动给每个 namespace 打上的标签，值就是 namespace 名，不用自己维护。TCP 53 也要放开，响应过大时 DNS 会改走 TCP。

$ kubectl -n notes-lab exec client -- sh -c "time nslookup web.notes-lab.svc.cluster.local"
real	0m 0.00s
Server:		<kube-dns-ip>
Address:	<kube-dns-ip>:53

Name:	web.notes-lab.svc.cluster.local
Address: <cluster-ip>

$ kubectl -n notes-lab exec client -- sh -c "time wget -qO- -T 5 http://web"
wget: download timed out
Command exited with non-zero status 1
real	0m 5.01s

解析好了，报错也从 bad address 变成了 download timed out：现在卡住的是 client 到 web 的出站。

两端都要放行

再给 client 放行到 app=web 的 TCP 80 出站，请求就通了。这时如果删掉 web 那一侧的 web-allow-client：

$ kubectl -n notes-lab delete networkpolicy web-allow-client
networkpolicy.networking.k8s.io "web-allow-client" deleted
$ kubectl -n notes-lab exec client -- wget -qO- -T 5 http://web
wget: download timed out
command terminated with exit code 1

client 的出站允许了，web 的入站不允许，连接照样建立不起来。一条连接要成功，源 Pod 的出站策略和目标 Pod 的入站策略都得放行（任一侧没有被隔离，则这一侧默认放行）。重新应用 web-allow-client 后恢复正常。

namespaceSelector 与 podSelector：差一个短横线

这是 NetworkPolicy 最容易写错的地方。下面两段只差 podSelector 前面的一个 -：

写法 A：一个元素，两个条件同时满足（AND）写法 B：两个元素，满足任一即可（OR）
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: notes-lab-b
        podSelector:
          matchLabels:
            role: client
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: notes-lab-b
      - podSelector:
          matchLabels:
            role: client

为了把区别测出来，另建 namespace notes-lab-b，放两个同样带 role=client、role=other 标签的 Pod，分别叫 b-client、b-other（pods-b.yaml）：

apiVersion: v1
kind: Pod
metadata:
  name: b-client
  namespace: notes-lab-b
  labels:
    role: client
spec:
  containers:
    - name: sh
      image: busybox:1.36
      command: ["sleep", "3600"]
---
apiVersion: v1
kind: Pod
metadata:
  name: b-other
  namespace: notes-lab-b
  labels:
    role: other
spec:
  containers:
    - name: sh
      image: busybox:1.36
      command: ["sleep", "3600"]

保留 default-deny-ingress，作用于 web 的只有这一条测试策略，再用下面的 matrix.sh 从四个客户端依次访问 web 的 Pod IP，每行输出 namespace、Pod 名和结果：

WEB_IP=$(kubectl -n notes-lab get pod web -o jsonpath='{.status.podIP}')
for p in "notes-lab client" "notes-lab other" "notes-lab-b b-client" "notes-lab-b b-other"; do
  set -- $p
  if kubectl -n $1 exec $2 -- wget -qO- -T 3 http://$WEB_IP >/dev/null 2>&1; then r=OK; else r=TIMEOUT; fi
  printf "%-13s %-9s %s\n" "$1" "$2" "$r"
done

kubectl describe 会把解析结果写出来。写法 A 只有一个 From，两个选择器在同一块里：

Allowing ingress traffic:
  To Port: <any> (traffic allowed to all ports)
  From:
    NamespaceSelector: kubernetes.io/metadata.name=notes-lab-b
    PodSelector: role=client
notes-lab     client    TIMEOUT
notes-lab     other     TIMEOUT
notes-lab-b   b-client  OK
notes-lab-b   b-other   TIMEOUT

只有「notes-lab-b 里的 role=client」能进来。写法 B 变成两个 From：

Allowing ingress traffic:
  To Port: <any> (traffic allowed to all ports)
  From:
    NamespaceSelector: kubernetes.io/metadata.name=notes-lab-b
  From:
    PodSelector: role=client
notes-lab     client    OK
notes-lab     other     TIMEOUT
notes-lab-b   b-client  OK
notes-lab-b   b-other   OK

notes-lab-b 里的所有 Pod 都放进来了，b-other 也不例外；另外本 namespace 的 client 也被放行，因为第二个元素是一个单独的 podSelector。

还有一个相关细节：不带 namespaceSelector 的 podSelector 只匹配策略所在 namespace 的 Pod。只保留前面的 web-allow-client（from 里只有 podSelector: role=client）时：

notes-lab     client    OK
notes-lab     other     TIMEOUT
notes-lab-b   b-client  TIMEOUT
notes-lab-b   b-other   TIMEOUT

b-client 的标签同样是 role=client，但它在另一个 namespace，进不来。想放行「所有 namespace 里的 role=client」，要在同一个元素里写 namespaceSelector: {} 加 podSelector。

拿不准时，看 kubectl describe networkpolicy 输出里有几个 From，比盯着 YAML 缩进可靠。

已建立的连接会不会被切断

先清空 namespace 里的策略，在 web 里用 nc 监听 9000 端口，把收到的内容写进文件；other 每秒发一行当前时间，用的始终是同一条 TCP 连接：

kubectl -n notes-lab exec web -- sh -c "nohup nc -l -p 9000 > /tmp/recv.log 2>&1 &"
kubectl -n notes-lab exec other -- env W=$WEB_IP sh -c \
  "nohup sh -c \"while true; do date +%T; sleep 1; done | nc \$W 9000\" > /tmp/send.log 2>&1 &"

连接建立后，在 06:04:57（UTC）应用 default-deny-ingress。3 秒后从 other 发起一个新的 HTTP 请求，被拦了：

$ kubectl -n notes-lab exec other -- wget -qO- -T 3 http://<web-ip>
wget: download timed out
command terminated with exit code 1

而那条老连接上的数据一直在进来。06:05:54 看接收端：

$ kubectl -n notes-lab exec web -- tail -5 /tmp/recv.log
06:05:49
06:05:50
06:05:51
06:05:52
06:05:53

从 06:04:13 到 06:05:53 共 101 行，策略生效前后没有中断。对应的是前面那段 iptables 链的第一条：--ctstate RELATED,ESTABLISHED -j ACCEPT。推测 conntrack 里已有的连接在这里就被放行，走不到后面的策略判断；这次没有单独查看 conntrack 表来确认。

这条连接一旦断开就回不来了。作为对照，没有任何策略时从 other 连 9000 是立即成功的（重建 Pod 后补测，先在 web 里执行 nohup nc -l -p 9000 > /tmp/recv2.log & 监听，web 收到了 hello）：

$ kubectl -n notes-lab exec other -- sh -c "echo hello | time nc -w 5 <web-ip> 9000"
real	0m 0.00s
$ kubectl -n notes-lab exec web -- cat /tmp/recv2.log
hello

回到默认拒绝的状态，停掉发送端、重新监听，再从 other 连 9000：

$ kubectl -n notes-lab exec other -- sh -c "time nc -w 5 <web-ip> 9000 < /dev/null"
Command exited with non-zero status 1
real	0m 5.00s

结果是 5 秒超时而不是 refused，本身就说明包被丢了。

这意味着收紧策略之后，长连接（数据库连接池、gRPC、WebSocket）会继续工作，直到它们因为重启或重连而断开，那时才会失败。「改完策略测一下没问题」不能证明策略对长连接正确，故障可能在几小时后的某次重连时才出现。官方文档明确说，策略变化是否影响已有连接由具体实现决定，这里观察到的只是 Calico iptables 模式下的行为。

反方向也测了一次：在默认拒绝状态下，other 连续发起 1 秒超时的请求，每次记下完成时间和结果：

kubectl -n notes-lab exec other -- sh -c 'nohup sh -c "for i in \$(seq 1 60); do
  if wget -qO- -T 1 http://'"$WEB_IP"' >/dev/null 2>&1; then echo \$(date +%T) OK; else echo \$(date +%T) FAIL; fi
done" > /tmp/probe.log 2>&1 &'

06:06:25.02 应用 web-allow-other，日志里 06:06:26 先有一次 FAIL，紧接着同一秒出现第一次 OK。探测只有秒级精度，能说的是新策略在约 2 秒内生效。

排查顺序

结合上面的实验，访问不通时可以按这个顺序看：

  1. 报错是 Connection refused 还是超时。直连 Pod IP 时，前者说明包已经到了目标 Pod，先查应用的端口和监听地址；经 Service 访问时，refused 还可能是 Service 没有可用 endpoint，被 kube-proxy 直接 REJECT。
  2. 报错是 bad address，或者解析超时，先查出站策略有没有放行到 CoreDNS Pod 的 UDP/TCP 53。
  3. 用 Pod IP 直连，排除 DNS；对源 Pod 和目标 Pod 分别列出选中它们的策略，出站和入站都要放行。
  4. 用 kubectl describe networkpolicy 核对 From/To 的个数和选择器内容，再用 kubectl get pod --show-labels、kubectl get ns --show-labels 确认标签真的匹配。
  5. 以上都对，再去节点上看 CNI 的规则。Calico 的入站链是 cali-tw-<网卡名>，数据包走向见 CNI 网络路径。

清理

kubectl delete namespace notes-lab notes-lab-b --wait

NetworkPolicy 是 namespace 级对象，随 namespace 一起删除。

参考：Network Policies、Declare Network Policy。
