编写自己的 Helm Chart

Helm 入门讲的是 Release 的一生：安装、三种预览方式、values 的优先级、失败的升级、历史和卸载。这一篇换到 Chart 作者这一边，不用 helm create 的脚手架，从几个文件手写一个 Chart，重点放在模板写错时会发生什么：哪些错误渲染时就报，哪些一路通过 helm lint，直到 API Server 才被拒绝，哪些根本不报错，只是悄悄渲染出另一个结果。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0），客户端是 Helm v4.3.0，实验放在单独的 notes-lab namespace 里（创建方法见实验环境），Service 的 IP 用 <cluster-ip> 代替。下面每个错误都是在 Chart 的一个副本上单独改出来的，改完即丢，命令里统一写成 ./web-chart。

Chart 的文件

最终的目录：

web-chart/
├── Chart.yaml
├── values.yaml
├── values.schema.json
└── templates/
    ├── _helpers.tpl
    ├── deployment.yaml
    ├── service.yaml
    └── NOTES.txt

Chart.yaml：

apiVersion: v2
name: web-chart
description: 一个仅供实验的 Nginx Chart
type: application
version: 0.1.0
appVersion: "1.27"

version 是 Chart 包自己的版本，每改一次模板都该升；appVersion 是被打包的应用版本，本身不会影响镜像，下面的模板让它在 image.tag 留空时充当默认标签。values.yaml：

replicaCount: 1

image:
  repository: nginx
  tag: ""          # 留空时使用 Chart.appVersion
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80

podLabels: {}

env: {}

resources:
  requests:
    cpu: 10m
    memory: 32Mi
  limits:
    memory: 64Mi

_helpers.tpl：命名模板

以下划线开头的文件不会被当成清单输出，适合放 define 定义的命名模板：

{{/* 资源名：<release>-<chart>，超过 63 字符截断 */}}
{{- define "web-chart.fullname" -}}
{{- printf "%s-%s" .Release.Name .Chart.Name | trunc 63 | trimSuffix "-" -}}
{{- end -}}

{{- define "web-chart.selectorLabels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end -}}

{{- define "web-chart.labels" -}}
{{ include "web-chart.selectorLabels" . }}
helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version }}
app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end -}}

模板名是全局的：父 Chart 和所有子 Chart 的模板编译在一起，同名的后加载者覆盖前者，所以名字一律带上 Chart 名前缀。selectorLabels 和 labels 分成两个，是有意为之，后面「selector 里放了会变的标签」一节会看到原因。

trunc 63 是因为 Service 等资源名不能超过 63 个字符。Helm 自己限制 Release 名最长 53 个字符：

Error: release name check failed: release name "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa": invalid release name, must match regex ^[a-z0-9]([-a-z0-9]*[a-z0-9])?(\.[a-z0-9]([-a-z0-9]*[a-z0-9])?)*$ and the length must not be longer than 53

53 个字符的 Release 名加上 -web-chart 正好是 63，这个 Chart 名之下截断不会真正发生；Chart 名更长，或者像脚手架那样再拼别的后缀时，trunc 才起作用。

deployment.yaml 和 service.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "web-chart.fullname" . }}
  labels:
    {{- include "web-chart.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      {{- include "web-chart.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "web-chart.selectorLabels" . | nindent 8 }}
        {{- with .Values.podLabels }}
        {{- toYaml . | nindent 8 }}
        {{- end }}
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - name: http
              containerPort: 80
          {{- with .Values.env }}
          env:
            {{- range $k, $v := . }}
            - name: {{ $k }}
              value: {{ $v | quote }}
            {{- end }}
          {{- end }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
apiVersion: v1
kind: Service
metadata:
  name: {{ include "web-chart.fullname" . }}
  labels:
    {{- include "web-chart.labels" . | nindent 4 }}
spec:
  type: {{ .Values.service.type }}
  selector:
    {{- include "web-chart.selectorLabels" . | nindent 4 }}
  ports:
    - name: http
      port: {{ .Values.service.port }}
      targetPort: http

插入多行内容的固定写法是 {{- ... | nindent N }}：左边的 {{- 吃掉这一行行首的缩进和上一行的换行，nindent 再补回一个换行，并把每一行缩进 N 格。with 在值为空（{}、""、0、false、nil）时跳过整块，所以 podLabels 和 env 没设置时，模板里不会留下空的 env:。

toYaml 会把 map 的键按字母排序，limits 跑到了 requests 前面，和 values.yaml 里的顺序不同，这不影响语义。

NOTES.txt

templates/NOTES.txt 也是模板，安装、升级结束后打印出来，用来告诉使用者怎么访问：

{{ .Release.Name }} 已{{ if .Release.IsInstall }}安装{{ else }}升级{{ end }}（第 {{ .Release.Revision }} 个修订），镜像 {{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}。

在集群内访问：
  http://{{ include "web-chart.fullname" . }}.{{ .Release.Namespace }}.svc:{{ .Values.service.port }}
{{- if ne .Values.service.type "ClusterIP" }}

Service 类型是 {{ .Values.service.type }}，注意它会对集群外暴露。
{{- end }}

$ kubectl -n notes-lab run curl --image=curlimages/curl:latest --restart=Never --rm -i --quiet -- curl -s -o /dev/null -w '%{http_code}\n' http://web-web-chart.notes-lab.svc:80

改成 NodePort 升级一次，IsInstall 变成 false，条件块也出现了：

$ helm upgrade web ./web-chart -n notes-lab --reuse-values --set service.type=NodePort --wait --timeout 2m
...
REVISION: 2

在集群内访问：
  http://web-web-chart.notes-lab.svc:80

Service 类型是 NodePort，注意它会对集群外暴露。

每个修订的 NOTES 都存在 Release 记录里，helm get notes web -n notes-lab --revision 1 还能看到第一次安装时那份。

.Release.Revision、.Release.IsUpgrade 这些值依赖集群里的 Release 记录，helm template 不连集群，只能给出固定的假设值。用一个临时 ConfigMap 把内置对象打印出来对比：

release: {{ printf "name=%s ns=%s rev=%d install=%t upgrade=%t service=%s" .Release.Name .Release.Namespace .Release.Revision .Release.IsInstall .Release.IsUpgrade .Release.Service | quote }}
chart: {{ printf "%s %s app=%s" .Chart.Name .Chart.Version .Chart.AppVersion | quote }}
template: {{ .Template.Name | quote }}
$ helm template web ./web-chart
  release: "name=web ns=default rev=1 install=true upgrade=false service=Helm"
  chart: "web-chart 0.1.0 app=1.27"
  template: "web-chart/templates/tpl.yaml"

$ helm template web ./web-chart -n notes-lab
  release: "name=web ns=notes-lab rev=1 install=true upgrade=false service=Helm"

$ helm upgrade web ./web-chart -n notes-lab --reuse-values --dry-run=client
  release: "name=web ns=notes-lab rev=5 install=false upgrade=true service=Helm"

helm template 永远是「第 1 个修订、全新安装」；不加 -n 时，namespace 取 kubeconfig 当前 context 里设置的 namespace，这里的 context 没有设置，所以是 default。用一份 kubeconfig 副本把 context 的 namespace 设成 foo-ns 再试：

$ KUBECONFIG=kubeconfig-copy helm template web ./web-chart --show-only templates/tpl.yaml | grep release:
  release: "name=web ns=foo-ns rev=1 install=true upgrade=false service=Helm"

第三条命令里的 rev=5，是因为做这个对比时 Release 已经有 4 个修订（后文「selector 里放了会变的标签」一节的一次失败升级和一次回滚），下一次升级就是第 5 个。模板里按 IsUpgrade 分支的逻辑，要用 --dry-run 才预览得到（helm template 也有 --is-upgrade 参数可以模拟，这次没测）。

缩进写错：两种完全不同的结局

真正非法的 YAML：渲染时就报错

把 labels 下的 nindent 4 写成 indent 4：

labels:
  {{- include "web-chart.labels" . | indent 4 }}
$ helm template web ./web-chart --show-only templates/deployment.yaml
Error: YAML parse error on web-chart/templates/deployment.yaml: error converting YAML to JSON: yaml: line 5: mapping values are not allowed in this context

Use --debug flag to render out invalid YAML

按提示加 --debug，Helm 会把出错的渲染结果原样打印出来：

# Source: web-chart/templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-web-chart
  labels:    app.kubernetes.io/name: web-chart
    app.kubernetes.io/instance: web
    helm.sh/chart: web-chart-0.1.0

{{- 已经把换行吃掉了，indent 不补换行，第一行标签就接在了 labels: 后面。报错的行号从 apiVersion 那一行数起，# Source 注释不算。这种错误 helm lint 也能发现：

[ERROR] templates/deployment.yaml: unable to parse YAML: error converting YAML to JSON: yaml: line 5: mapping values are not allowed in this context

-}} 也一样，它吃掉的是右边的换行和下一行的缩进：

b: "2"
{{- if true -}}
c: "3"
{{- end }}

渲染出来是 b: "2"c: "3"（cat -A 看到的原样），报 yaml: line 8: did not find expected key。反过来，{{ if }} 和 {{ end }} 不加 -，只会在原位置留下一行只有空格的空行，YAML 里无害，只是难看。

合法但错位的 YAML：template 和 lint 都放行

更麻烦的是另一种写法，toYaml 后面忘了 nindent：

resources:
  {{ toYaml .Values.resources }}

helm template 没有报错，输出是这样的：

          resources:
            limits:
  memory: 64Mi
requests:
  cpu: 10m
  memory: 32Mi

toYaml 的第一行跟在模板里写好的 12 格缩进后面，其余各行从第 0 列开始。helm lint 也通过：

==> Linting ./web-chart
[INFO] Chart.yaml: icon is recommended

1 chart(s) linted, 0 chart(s) failed

原因是这段文本恰好仍是合法 YAML，只是结构变了。用 Python 解析渲染结果：

$ helm template web ./web-chart --show-only templates/deployment.yaml | python3 -c 'import sys,yaml,json; d=yaml.safe_load(sys.stdin); print(list(d.keys())); print(json.dumps(d["spec"].get("memory"))); print(d["spec"]["template"]["spec"]["containers"][0]["resources"])'
['apiVersion', 'kind', 'metadata', 'spec', 'requests']
"64Mi"
{'limits': None}

limits 成了空值；缩进 2 格的 memory: 64Mi 被当成了 Deployment spec 下的一个键；requests 跑到了文档的顶层。真正安装时才被拒绝（这一节和下一节的两次失败安装，实际是在前文正式安装 web 之前做的，每次做完都 helm uninstall web 清掉，所以能复用同一个名字）：

$ helm install web ./web-chart -n notes-lab
Error: INSTALLATION FAILED: server-side apply failed for object notes-lab/web-web-chart apps/v1, Kind=Deployment: failed to create typed patch object (notes-lab/web-web-chart; apps/v1, Kind=Deployment): .requests: field not declared in schema
$ helm list -n notes-lab
NAME	NAMESPACE           	REVISION	UPDATED                                	STATUS	CHART          	APP VERSION
web 	notes-lab	1       	2026-10-12 16:33:20.648748058 +0800 +08	failed	web-chart-0.1.0	1.27
$ kubectl -n notes-lab get deploy,svc
NAME                    TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
service/web-web-chart   ClusterIP   <cluster-ip>    <none>        80/TCP    9s

Release 记成了 failed，Service 照样建好了，不会自动撤回，这一点和Helm 入门里失败的升级一样。后文 w-i-tpl 那次，出错的 ConfigMap 按安装顺序排在 Deployment 和 Service 之前，另外两个资源也照样建出来了，可见这和先后顺序无关；推测 Helm 是把所有资源都提交一遍，最后再汇总报错。查看之后先卸载：

$ helm uninstall web -n notes-lab
release "web" uninstalled

Helm 4 默认用服务端应用，这条错误只报了第一个未知字段 .requests；把同样的渲染结果交给 kubectl apply --dry-run=server，两个错位的字段都列了出来：

$ helm template web ./web-chart | kubectl -n notes-lab apply --dry-run=server -f -
service/web-web-chart created (server dry run)
Error from server (BadRequest): error when creating "STDIN": Deployment in version "v1" cannot be handled as a Deployment: strict decoding error: unknown field "requests", unknown field "spec.memory"

如果错位后的字段名碰巧在上一层也合法，API Server 也不会拒绝，渲染结果就这样装进去了。所以 helm template 不报错只能说明模板语法没问题，还得看一眼渲染结果，或者交给 API Server 校验一遍。

类型：quote 和数字标签

env 的值没加 quote

把模板里的 value: {{ $v | quote }} 换成 value: {{ $v }}，传入：

env:
  LISTEN_PORT: 8080
  DEBUG: true
env:
  - name: DEBUG
    value: true
  - name: LISTEN_PORT
    value: 8080

（range 遍历 map 时也按键排序，DEBUG 排在前面。）helm lint --strict 通过，--dry-run=server 也不报错（它不让 API Server 校验对象，见 Helm 入门）。真正安装时：

Error: INSTALLATION FAILED: server-side apply failed for object notes-lab/web-web-chart apps/v1, Kind=Deployment: failed to create typed patch object (notes-lab/web-web-chart; apps/v1, Kind=Deployment): errors:
  .spec.template.spec.containers[name="web"].env[name="DEBUG"].value: expected string, got &value.valueUnstructured{Value:true}
  .spec.template.spec.containers[name="web"].env[name="LISTEN_PORT"].value: expected string, got &value.valueUnstructured{Value:8080}

环境变量的值、注解的值、ConfigMap 的 data 都必须是字符串。这次同样建好了 Service，做完 helm uninstall web 清掉。加上 quote 后渲染成 value: "true"、value: "8080"。凡是 Kubernetes 要求字符串、而用户可能填数字或布尔值的位置，模板里都加 quote。

image.tag: 1.20 变成了 nginx:1.2

镜像标签的问题出在 values 这一侧，模板加不加 quote 都救不回来：

$ cat tag-float.yaml
image:
  tag: 1.20
$ helm template web ./web-chart -f tag-float.yaml --show-only templates/deployment.yaml | grep image:
          image: "nginx:1.2"
$ helm template web ./web-chart --set image.tag=1.20 --show-only templates/deployment.yaml | grep image:
          image: "nginx:1.20"

values 文件里不加引号的 1.20 被 YAML 解析成浮点数 1.2，末尾的 0 在进入模板之前就没了；同样的值用 --set 传，结果是 1.20。长数字更离谱，用时间戳当标签：

$ cat tag-int.yaml
image:
  tag: 20261012153000
$ helm template web ./web-chart -f tag-int.yaml --show-only templates/deployment.yaml | grep image:
          image: "nginx:2.0261012153e+13"

replicaCount: 20261012153000 也一样渲染成 replicas: 2.0261012153e+13。推测原因是 Helm 把 values 文件解析成 JSON 兼容的结构，数字一律成了 float64，模板输出时大数用科学计数法打印；--set 走的是另一套解析，所以前面的 1.20 没有变。values 里看起来像数字的字符串，必须自己加引号。这类错误光靠模板防不住，要靠下面的 schema。

default、required 和缺失的嵌套值

这一节和下一节的函数实验，都在 Chart 副本的 templates/ 下新建一个临时 ConfigMap 模板（文件名就是报错里出现的 defaults.yaml、probe.yaml、probe-dig.yaml、probe-paren.yaml、req.yaml、tpl.yaml；tpl.yaml 由 include/template 和作用域几个实验轮流改写，后文对作用域错误做真实安装时，同样的内容另存成了 scope.yaml），每个实验一个文件，片段里只列出不同的那部分，文件头都是：

apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ include "web-chart.fullname" . }}-<用途>
data:

default 会吞掉 0 和 false

default 判断的是「空」，不是「没设置」。serviceLinks 是为这个实验虚构的开关，故意不写进 values.yaml：

replicas: {{ .Values.replicaCount | default 1 | quote }}
serviceLinks: {{ .Values.serviceLinks | default true | quote }}
serviceLinksHasKey: {{ hasKey .Values "serviceLinks" | ternary .Values.serviceLinks true | quote }}
$ helm template web ./web-chart --set replicaCount=0 --set serviceLinks=false --show-only templates/defaults.yaml
...
data:
  replicas: "1"
  serviceLinks: "true"
  serviceLinksHasKey: "false"

用户明确要 0 个副本、关闭某个开关，default 都把它改回了默认值。布尔开关和可以为 0 的数字不要用 default，要么把默认值写进 values.yaml，要么像第三行那样用 hasKey 判断键是否存在。

required：缺值时给出可读的报错

为了让 .Values.ingress.host 本身不触发下文的 nil pointer，副本的 values.yaml 末尾加了一行 ingress: {}：

domain: {{ required "ingress.host 必须设置，例如 --set ingress.host=web.example.com" .Values.ingress.host | quote }}
$ helm template web ./web-chart --show-only templates/req.yaml
Error: execution error at (web-chart/templates/req.yaml:6:13): ingress.host 必须设置，例如 --set ingress.host=web.example.com

--set ingress.host=（空字符串）同样报错。但 helm lint 对它网开一面，加了 --strict 也只是一条警告，退出码是 0：

$ helm lint ./web-chart --strict; echo exit=$?
level=WARN msg="missing required value" message="ingress.host 必须设置，例如 --set ingress.host=web.example.com"
==> Linting ./web-chart
[INFO] Chart.yaml: icon is recommended

1 chart(s) linted, 0 chart(s) failed
exit=0

lint 检查的是 Chart 本身，按设计允许「使用者必须传值」的 Chart 通过。CI 里想确认一份具体的 values 能用，应该跑 helm template -f <那份 values>，而不是只跑 lint。

nil pointer：访问不存在的嵌套键

values.yaml 里没有 probe，模板却直接取 .Values.probe.http.path：

path: {{ .Values.probe.http.path | default "/" | quote }}
$ helm template web ./web-chart --show-only templates/probe.yaml
Error: web-chart/templates/probe.yaml:6:18
  executing "web-chart/templates/probe.yaml" at <.Values.probe.http.path>:
    nil pointer evaluating interface {}.http
$ helm template web ./web-chart --set probe.enabled=true --show-only templates/probe.yaml
Error: web-chart/templates/probe.yaml:6:18
  executing "web-chart/templates/probe.yaml" at <.Values.probe.http.path>:
    nil pointer evaluating interface {}.path

两点要注意：报错里的字段名是「在 nil 上取的那个字段」，.http 说明 probe 不存在，.path 说明 probe 在、http 不在，要往前看一级；后面接的 default 来不及生效，取值这一步就失败了。两种安全写法：

dig: {{ dig "http" "path" "/" (.Values.probe | default dict) | quote }}
paren: {{ ((.Values.probe).http).path | default "/" | quote }}

不传、传 --set probe.http.path=/healthz、传 --set probe=null 三种情况下，两种写法的结果都一样（"/"、"/healthz"、"/"）。类型不对时两者都会失败。把两种写法分别放进两个 Chart 副本，用 --set probe.http=abc 让 http 成为字符串（--show-only 只是过滤输出，所有模板仍会渲染，所以要分开放）：

$ helm template web ./web-chart --set probe.http=abc --show-only templates/probe-dig.yaml
Error: template: web-chart/templates/probe-dig.yaml:6:11: executing "web-chart/templates/probe-dig.yaml" at <dig "http" "path" "/" (.Values.probe | default dict)>: error calling dig: interface conversion: interface {} is string, not map[string]interface {}
$ helm template web ./web-chart --set probe.http=abc --show-only templates/probe-paren.yaml
Error: web-chart/templates/probe-paren.yaml:6:20
  executing "web-chart/templates/probe-paren.yaml" at <.Values.probe>:
    can't evaluate field path in type string

括号写法的报错直接说出了在哪个字段上碰到了字符串，dig 只说类型转换失败。dig 和括号写法只能防住「键不存在」，防不住「键的类型不对」，后者要靠后面的 schema。

更根本的办法是在 values.yaml 里把嵌套结构写全（哪怕值为空），读者一看就知道 Chart 支持哪些键。

include、template 和作用域

template 不能接管道

把 include 换成 template，其余不变：

labels:
  {{- template "web-chart.labels" . | nindent 4 }}
Error: web-chart/templates/tpl.yaml:6:48
  executing "web-chart/templates/tpl.yaml" at <4>:
    wrong type for value; expected string; got common.Values

这个报错乍看莫名其妙。template 是一个动作而不是函数，它的语法是 template "名字" 管道，于是 . | nindent 4 整个成了传进模板的参数，相当于 nindent 4 .，把 values 对象当成字符串去缩进。去掉管道写成 {{ template "web-chart.labels" . }} 能渲染通过，但输出无法缩进：

  labels:
    app.kubernetes.io/name: web-chart
app.kubernetes.io/instance: web
helm.sh/chart: web-chart-0.1.0
app.kubernetes.io/version: "1.27"
app.kubernetes.io/managed-by: Helm

只有第一行在 labels 下面，其余标签掉到了顶层，又是一份「合法但错位」的 YAML，helm template 同样不报错。include 是函数，返回字符串，可以接 nindent，所以 Chart 里一律用 include。

with 和 range 里的点

with 和 range 会把 . 换成当前元素：

data:
  {{- with .Values.service }}
  port: {{ .port | quote }}
  owner: {{ .Release.Name }}
  {{- end }}
Error: web-chart/templates/tpl.yaml:8:20
  executing "web-chart/templates/tpl.yaml" at <.Release.Name>:
    nil pointer evaluating interface {}.Name

块里的 . 是 .Values.service，它下面没有 Release。根作用域要用 $，改成 {{ $.Release.Name }} 后渲染出 owner: web。在 range 里调用命名模板时更容易踩到，因为习惯性地传了 .：

{{- range $k, $v := .Values.env }}
{{ $k }}: {{ include "web-chart.fullname" . }}
{{- end }}
Error: web-chart/templates/tpl.yaml:7:15
  executing "web-chart/templates/tpl.yaml" at <include "web-chart.fullname" .>:
    error calling include:
web-chart/templates/_helpers.tpl:3:27
  executing "web-chart.fullname" at <.Release.Name>:
    can't evaluate field Release in type bool

报错指向的是 _helpers.tpl，真正写错的却是调用方。type bool 是因为 env 按键排序后第一个是 DEBUG: true，. 成了这个布尔值。在 range 里调用命名模板要传 $。

values.schema.json

前面的浮点标签，以及 Service 类型写错（Helm 入门里要到 API Server 才被拒绝）这类错误，都可以在渲染之前就拦下来。在 Chart 根目录放一个 values.schema.json：

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["image", "service"],
  "properties": {
    "replicaCount": { "type": "integer", "minimum": 0, "maximum": 5 },
    "image": {
      "type": "object",
      "required": ["repository"],
      "properties": {
        "repository": { "type": "string", "minLength": 1 },
        "tag": { "type": "string" },
        "pullPolicy": { "enum": ["Always", "IfNotPresent", "Never"] }
      }
    },
    "service": {
      "type": "object",
      "properties": {
        "type": { "enum": ["ClusterIP", "NodePort", "LoadBalancer"] },
        "port": { "type": "integer", "minimum": 1, "maximum": 65535 }
      }
    },
    "env": {
      "type": "object",
      "additionalProperties": { "type": ["string", "number", "boolean"] }
    },
    "podLabels": { "type": "object", "additionalProperties": { "type": "string" } },
    "resources": { "type": "object" }
  }
}

（实际文件是格式化后的同样内容。）Helm 文档的示例用的是 draft-07，这里写 2020-12，Helm 4.3 同样接受。

$ helm template web ./web-chart -f tag-float.yaml
Error: values don't meet the specifications of the schema(s) in the following chart(s):
web-chart:
- at '/image/tag': got number, want string

$ helm template web ./web-chart --set replicaCount=10 --set service.type=Foo
Error: values don't meet the specifications of the schema(s) in the following chart(s):
web-chart:
- at '/service/type': value must be one of 'ClusterIP', 'NodePort', 'LoadBalancer'
- at '/replicaCount': maximum: got 10, want 5

$ helm template web ./web-chart --set image.repository=
Error: values don't meet the specifications of the schema(s) in the following chart(s):
web-chart:
- at '/image/repository': minLength: got 0, want 1

所有不符合的地方一次列全。1.20 被解析成浮点数这件事，到了 schema 这里就变成了明确的 got number, want string。--set replicaCount=3 通过；--set-string replicaCount=3 被拒（got string, want integer），因为 --set 会把纯数字转成整数。lint 也会做 schema 校验：helm lint ./web-chart --set service.type=Foo 报了两条 [ERROR]，一条在 values.yaml，一条在 templates/。

拼错的键：默认静默忽略

replicaCount 拼成 replicas，没有任何提示，副本数还是 1：

$ helm template web ./web-chart --set replicas=3 --show-only templates/deployment.yaml | grep replicas
  replicas: 1

在 schema 顶层加 "additionalProperties": false 就能拦住，但它校验的是合并后的全部 values，包括 Chart 自己的默认值。在一个还没声明 podLabels、resources 的版本上试：

$ helm template web ./web-chart --set replicas=3
Error: values don't meet the specifications of the schema(s) in the following chart(s):
web-chart:
- at '': additional properties 'podLabels', 'replicas', 'resources' not allowed

$ helm template web ./web-chart --set global.env=dev
Error: values don't meet the specifications of the schema(s) in the following chart(s):
web-chart:
- at '': additional properties 'global', 'podLabels', 'resources' not allowed

拼错的 replicas 被抓到了，同时也暴露出 schema 漏写了两个合法的键。第二条更值得注意：global 是 Helm 父子 Chart 之间共享值的约定键，以后这个 Chart 被当成子 Chart，或者自己引入子 Chart，顶层的 additionalProperties: false 会拒绝 global 和子 Chart 的那一段 values（后一种情况是推测，这次没有实测）。所以本文最终的 Chart 只在 env、podLabels 这些叶子对象上限制类型，没有在顶层禁止额外的键。子 Chart 见 Helm Chart 依赖与锁定。

NOTES.txt 写错会挡住升级

NOTES.txt 不是清单，但同样会被渲染。在末尾加一行 入口：{{ .Values.ingress.host }}（values 里没有 ingress）：

$ helm upgrade web ./web-chart -n notes-lab --reuse-values
Error: UPGRADE FAILED: web-chart/templates/NOTES.txt:9:19
  executing "web-chart/templates/NOTES.txt" at <.Values.ingress.host>:
    nil pointer evaluating interface {}.host
$ helm history web -n notes-lab
REVISION	UPDATED                 	STATUS    	CHART          	APP VERSION	DESCRIPTION     
1       	Mon Oct 12 16:35:42 2026	superseded	web-chart-0.1.0	1.27       	Install complete
2       	Mon Oct 12 16:36:56 2026	deployed  	web-chart-0.1.0	1.27       	Upgrade complete

一行提示文字写错，整次升级就做不了。好在它和其他渲染错误一样，发生在提交任何资源之前，历史里没有多出 failed 的修订。helm template 和 helm lint 都能报出这个错误。

selector 里放了会变的标签

最后一个错误模板和 lint 都查不出来，要到改 Chart 时才暴露。把 app.kubernetes.io/version 从 labels 挪进 selectorLabels（看起来只是「多一个标签更精确」），升级已有的 Release：

$ helm upgrade web ./web-chart -n notes-lab --reuse-values --wait --timeout 1m
Error: UPGRADE FAILED: server-side apply failed for object notes-lab/web-web-chart apps/v1, Kind=Deployment: Deployment.apps "web-web-chart" is invalid: spec.selector: Invalid value: v1.LabelSelector{MatchLabels:map[string]string{"app.kubernetes.io/instance":"web", "app.kubernetes.io/name":"web-chart", "app.kubernetes.io/version":"1.27"}, MatchExpressions:[]v1.LabelSelectorRequirement(nil)}: field is immutable

Deployment 的 spec.selector 创建后不可修改，修订 3 记为 failed。但 Service 的 selector 是可以改的，它已经被更新了：

$ kubectl -n notes-lab get svc web-web-chart -o jsonpath='{.spec.selector}'
{"app.kubernetes.io/instance":"web","app.kubernetes.io/name":"web-chart","app.kubernetes.io/version":"1.27"}
$ kubectl -n notes-lab get pod --show-labels
NAME                             READY   STATUS    RESTARTS   AGE     LABELS
web-web-chart-5795c958c7-6g7pl   1/1     Running   0          2m16s   app.kubernetes.io/instance=web,app.kubernetes.io/name=web-chart,pod-template-hash=5795c958c7,tier=frontend

Deployment 没变，Pod 上没有 version 标签，新的 Service selector 选不中它。升级失败后马上（08:37:46 UTC）查的那一次，EndpointSlice 里还列着这个 Pod，约 25 秒后（08:38:11）再查已是 endpoints=null。两次查询之间从集群内访问 Service 已经失败：

$ kubectl -n notes-lab run curl --image=curlimages/curl:latest --restart=Never --rm -i --quiet -- curl -s -m 5 -o /dev/null -w '%{http_code}\n' http://web-web-chart.notes-lab.svc:80; echo exit=$?
000
pod notes-lab/curl terminated (Error)
exit=7

也就是说，这次升级「失败」了，但服务已经断了。回滚到修订 2 后 Service 的 selector 恢复原样，访问重新返回 200。selector 只放 name 和 instance 这种在 Release 一生里不会变的标签，版本号、Chart 版本这类标签放进 labels，这是 _helpers.tpl 把两者分开的原因。

lint 能查什么

把上面的情况汇总一下：

错误helm templatehelm lint真正安装
indent/-}} 产生非法 YAML报错报错报错，不留修订（-}} 这一例没装，推测相同）
toYaml 少了 nindent、template 无法缩进（合法但错位）通过通过API Server 拒绝出错的对象，Release failed，其余资源已建好
env 值未加 quote通过通过（--strict 也是）API Server 拒绝
1.20 变成 1.2（无 schema）通过，结果错通过没有实测；有 schema 时渲染前就报错
required 缺值报错只警告，退出码 0报错，不留修订
nil 嵌套取值、作用域写错、NOTES.txt 出错报错报错报错，不留修订
selector 改了通过通过Deployment 被拒，Service 已改

表中除注明的格子外都实测过（lint 一列里 -}}、template 无法缩进、作用域错误和无 schema 的 1.20，是事后在本地补跑的 helm lint，结果与表中一致）。用 template 无法缩进的那个 ConfigMap、缺失的嵌套值、with 里的 .Release、缺值的 required 各做一个 Chart 副本，分别安装：

$ helm install w-i-tpl ./web-chart -n notes-lab
Error: INSTALLATION FAILED: server-side apply failed for object notes-lab/w-i-tpl-web-chart-tpl /v1, Kind=ConfigMap: failed to create typed patch object (notes-lab/w-i-tpl-web-chart-tpl; /v1, Kind=ConfigMap): .app.kubernetes.io/instance: field not declared in schema
$ helm install w-i-nil ./web-chart -n notes-lab
Error: INSTALLATION FAILED: web-chart/templates/probe.yaml:6:18
  executing "web-chart/templates/probe.yaml" at <.Values.probe.http.path>:
    nil pointer evaluating interface {}.http
$ helm install w-i-scope ./web-chart -n notes-lab
Error: INSTALLATION FAILED: web-chart/templates/scope.yaml:8:20
  executing "web-chart/templates/scope.yaml" at <.Release.Name>:
    nil pointer evaluating interface {}.Name
$ helm install w-i-req ./web-chart -n notes-lab
Error: INSTALLATION FAILED: execution error at (web-chart/templates/req.yaml:6:13): ingress.host 必须设置，例如 --set ingress.host=web.example.com
$ helm list -n notes-lab
NAME   	NAMESPACE           	REVISION	UPDATED                                	STATUS	CHART          	APP VERSION
w-i-tpl	notes-lab	1       	2026-10-12 16:45:27.667157457 +0800 +08	failed	web-chart-0.1.0	1.27

后三个是渲染期错误，没有留下 Release。第一个通过了渲染，Release 记为 failed，同一 Release 的 Deployment 和 Service 已经建好，只有出错的 ConfigMap 没有建出来。

lint 主要查的是「模板能不能渲染、渲染出来是不是合法 YAML、values 是否符合 schema」，它不知道 Kubernetes 的字段定义。在 CI 里更有用的组合是：helm lint 加上 helm template -f <各环境 values> | kubectl apply --dry-run=server -f -，后者会让 API Server 按真实的字段定义校验一遍（需要能连集群）。这次实测中，它把 env 的类型错误报成了 cannot unmarshal bool into Go struct field EnvVar.spec.template.spec.containers.env.value of type string。两边列出的错误条数并不固定：缩进错位那次，Helm 只报了 .requests，kubectl 列出了两个未知字段；env 这次反过来，kubectl 只报了第一个布尔值，Helm 的服务端应用把 DEBUG 和 LISTEN_PORT 两条都列了出来。所以别指望一次报全，修一个再跑一次。selector 这类和已有对象有关的问题，只有对着现有 Release 做一次真实升级（例如在预发环境）才会出现，升级流程见 Helm 升级验证与回滚。

清理

helm uninstall web -n notes-lab
kubectl delete namespace notes-lab

小结

  • 插入多行内容一律 {{- include ... | nindent N }} 或 {{- toYaml ... | nindent N }}；indent 和 -}} 用错会产生非法 YAML，少了 nindent 则可能产生合法但错位的 YAML，后者只有 API Server 能发现。
  • 字符串字段加 quote；values 里像数字的版本号自己加引号，再用 schema 的 "type": "string" 兜底。
  • default 会把 0、false 当成空值；required 在 lint 里只是警告；嵌套取值用 dig 或 ((.a).b).c，报错里的字段名要往前看一级。
  • 命名模板带 Chart 名前缀，用 include 而不是 template；with/range 里取根对象用 $。
  • selector 只放不会变的标签，否则升级时 Deployment 被拒、Service 却已经被改。
