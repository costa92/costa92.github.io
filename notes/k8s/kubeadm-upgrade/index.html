第 61 / 66 节 · 集群搭建

先确认集群归谁管

这份清单只适用于自己用 kubeadm 管理的集群。托管 Kubernetes 服务的控制平面由云厂商升级，步骤完全不同。起点见 kubeadm 安装部署 和 kubeadm 高可用拓扑。

为了不只停留在纸面，这次专门建了一个一次性的 kind 集群（kind v0.24.0，节点镜像 kindest/node:v1.31.0，一个控制平面加一个 worker，containerd 1.7.18，CNI 是 kind 自带的 kindnet），在节点里真的跑了两轮升级：先在 v1.31 内升补丁版本 v1.31.0 → v1.31.14，再跨一个 minor 升到 v1.32.13。节点名简化为 control-plane 和 worker，节点 IP 写成 <node-ip>。

kind 节点本身是容器，里面的 kubeadm、kubelet、kubectl 是直接放在 /usr/bin 下的二进制，没有 apt 包，systemd 管 kubelet。所以这次用的办法是从 dl.k8s.io 下载官方二进制、校验后替换。真实主机上应该走包管理器，这一点放在后面「kind 和真实主机的差别」里单独说。

实验过程中宿主机磁盘很慢，有一段时间严重过载。下文第 6 节的几个问题都是在宿主机过载时出现的，不代表正常升级会这样；第 7 节是过载缓解后的一轮，可以对照着看。

1. 盘点：先把「现在是什么样」记下来

升级前要留下可对比的基线：版本、静态 Pod 镜像、附加组件版本、证书有效期。下面这些输出在升级结束后会再看一遍。

kubectl get nodes -o wide
kubectl version
grep -H image: /etc/kubernetes/manifests/*.yaml        # 在控制平面节点上
kubeadm certs check-expiration                         # 在控制平面节点上
kubectl get pdb -A

附加组件当时是 CoreDNS v1.11.1、kube-proxy v1.31.0。另外记下 kubeadm-config 里的 kubernetesVersion: v1.31.0，后面会看到 apply 中途失败时它已经先被改掉了。

还有一个容易漏的点：管理机上的 kubectl 自己也有版本约束。我宿主机上的 kubectl 是 v1.30.0，版本偏差策略只允许 kubectl 和 kube-apiserver 相差一个 minor，升到 v1.32 后它就超出支持范围了，所以实验一开始就换成了 v1.31.14 的 kubectl（同时兼容 v1.30～v1.32）。

为了观察升级对业务和 API 的影响，在集群里放了一个两副本的 Deployment（busybox httpd）、一个 Service 和一个 minAvailable: 1 的 PDB，并开了两个探测：

  • 宿主机每秒请求一次 apiserver 的 /readyz，记录 HTTP 状态码（000 表示连不上）；
  • 每个节点上每秒 curl 一次 Service 的 ClusterIP，检验各节点上 kube-proxy 的规则是否还能把流量送到后端。

每一轮 apply 之前都要做一次 etcd 快照，并且把快照拷到控制平面节点之外。这次实验里我只在第二轮（v1.31.14 → v1.32.13）之前做了，第一轮补丁升级之前漏做了，而那一轮恰好把 etcd 从 3.5.15 升到了 3.5.24。第二轮实际执行的命令是借 etcd 容器里自带的 etcdctl：

E=$(crictl ps --name etcd -q)
crictl exec $E etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/healthcheck-client.crt \
  --key=/etc/kubernetes/pki/etcd/healthcheck-client.key \
  snapshot save /var/lib/etcd/pre-1.32.db
Snapshot saved at /var/lib/etcd/pre-1.32.db
...
-rw-------  1 root root 3723296 Oct 13 09:13 pre-1.32.db

快照写到 /var/lib/etcd 下，是因为这个目录以 hostPath 挂进了 etcd 容器，文件能直接落到节点上。但这个位置并不安全：它和 etcd 数据在同一块盘上，节点或磁盘出问题时会和数据一起丢。实际操作时应该马上拷到别的机器，并做一次校验。etcd 镜像里没有 etcdutl，需要在节点上装一份与服务端同版本的 etcd 客户端，再执行下面的命令（这次实验没有执行这一步，安装方法和校验能发现什么、不能发现什么，见 etcd 快照）：

etcdutl snapshot status /var/lib/etcd/pre-1.32.db -w table

2. 拿到目标版本的二进制

在 kind 里，从 dl.k8s.io 下载对应版本的二进制和 .sha256，逐个校验：

# 下载：每个版本目录里放 kubeadm、kubelet、kubectl 及对应的 .sha256
for v in v1.31.14 v1.32.13; do
  mkdir -p $v
  for b in kubeadm kubelet kubectl; do
    curl -sSL -o $v/$b        https://dl.k8s.io/release/$v/bin/linux/amd64/$b
    curl -sSL -o $v/$b.sha256 https://dl.k8s.io/release/$v/bin/linux/amd64/$b.sha256
  done
done
# v1.33.13 只下载了 kubeadm，用来验证跳 minor 的报错

# 校验
for f in v1.31.14/kubeadm v1.31.14/kubelet v1.31.14/kubectl v1.32.13/kubeadm v1.32.13/kubelet v1.32.13/kubectl v1.33.13/kubeadm; do
  echo "$(cat $f.sha256)  $f" | sha256sum --check
done
v1.31.14/kubeadm: OK
v1.31.14/kubelet: OK
v1.31.14/kubectl: OK
v1.32.13/kubeadm: OK
v1.32.13/kubelet: OK
v1.32.13/kubectl: OK
v1.33.13/kubeadm: OK

各 minor 的最新补丁版本可以从 https://dl.k8s.io/release/stable-1.32.txt 这类地址查到，当时分别是 v1.31.14、v1.32.13、v1.33.13。原来的三个二进制先复制到备份目录再替换。kubeadm、kubelet 不要一起换：kubeadm 先换，kubelet 要等这个节点排空之后再换。

3. 版本规则：一次只能跨一个 minor

官方升级文档写得很明确：不支持跳过 minor 版本升级。kubeadm 本身也会检查。拿 v1.33.13 的 kubeadm 去看 v1.31.0 的集群，直接拒绝：

$ /opt/bins/v1.33.13/kubeadm upgrade plan
[preflight] Running pre-flight checks.
[upgrade/config] Reading configuration from the "kubeadm-config" ConfigMap in namespace "kube-system"...
[upgrade/config] Use 'kubeadm init phase upload-config --config your-config-file' to re-upload it.
[upgrade/init config] FATAL: this version of kubeadm only supports deploying clusters with the control plane version >= 1.32.0. Current version: v1.31.0

反过来，用旧 kubeadm 去升更高的 minor 也不行。v1.31.14 的 kubeadm 被要求升到 v1.32.13 时：

[upgrade/version] FATAL: the --version argument is invalid due to these fatal errors:

	- Specified version to upgrade to "v1.32.13" is at least one minor release higher than the kubeadm minor release (32 > 31). Such an upgrade is not supported

所以 kubeadm 的 minor 必须等于目标版本的 minor，而目标版本最多比当前控制平面高一个 minor。从 v1.31 去 v1.33，就得 v1.31 → v1.32 → v1.33 走两轮完整流程，每一轮都包括所有节点的 kubelet。

kubeadm 之外，各组件之间的版本偏差策略（Version Skew Policy）决定了升级顺序：

组件相对 kube-apiserver
kube-controller-manager、kube-scheduler不能比 apiserver 新，最多旧一个 minor
kubelet不能比 apiserver 新，最多旧三个 minor
kube-proxy不能比 apiserver 新，最多旧三个 minor
kubectl上下一个 minor

kubelet 不能比 apiserver 新，所以先升控制平面，后升 kubelet，顺序不能反。另外官方说明 kubelet 的 minor 升级不支持原地进行，必须先排空节点。这次的 v1.33 只下载了 kubeadm，没有去验证「kubelet 比 apiserver 新」时的实际报错。

4. plan 和 dry-run

换上 v1.31.14 的 kubeadm 后，在第一个控制平面节点上执行：

几点值得留意：

  • remote version is much newer: v1.37.1; falling back to: stable-1.31：kubeadm 会联网查最新版本，发现远超自己能处理的范围就回退到本 minor。离线环境里这一步查不到，最好直接指定版本。
  • 补丁升级不只是换控制平面镜像，etcd 从 3.5.15 升到了 3.5.24，CoreDNS 从 v1.11.1 升到了 v1.11.3。附加组件和 etcd 的变化要在 plan 阶段看清楚，不能当成「小版本随便升」。
  • kubelet 单独列出来，说明 apply 不会碰任何节点上的 kubelet。

第二轮换上 v1.32.13 的 kubeadm 再 plan，CoreDNS 和 etcd 反而不变（v1.11.3、3.5.24-0），只有控制平面和 kube-proxy 升级。可见附加组件的版本跟着 kubeadm 走，每个版本要各看各的 plan，没法类推。

--dry-run 不改集群，但会打印将要执行的每一步：

kubeadm upgrade apply v1.31.14 --dry-run --yes

v1.31.14 的 dry-run 两秒结束，输出 4675 行，大部分是它「假装」发给 API 的请求。过滤掉 [dryrun] 开头的行，主干是这些：

[upgrade/health] Would create the Job with the prefix "upgrade-health-check" in namespace "kube-system" and wait until it completes
[upgrade/prepull] Would pull the required images (like 'kubeadm config images pull')
[upgrade/apply] Upgrading your Static Pod-hosted control plane to version "v1.31.14" (timeout: 5m0s)...
[upload-config] Storing the configuration used in ConfigMap "kubeadm-config" in the "kube-system" Namespace
[kubelet-start] Writing kubelet configuration to file "/etc/kubernetes/tmp/kubeadm-upgrade-dryrun4113264781/config.yaml"
[addons] Applied essential addon: CoreDNS
[addons] Applied essential addon: kube-proxy
[upgrade/successful] Finished dryrunning successfully!

dry-run 并不完全「无痕」：它在 /etc/kubernetes/tmp/ 下留了两个目录（kubeadm-upgrade-dryrun*、kubeadm-kubelet-config*），静态 Pod 清单没有变化。

5. 预拉镜像，别把下载时间算进维护窗口

apply 会先拉镜像。为了把下载和真正的切换分开，先单独拉：

kubeadm config images pull --kubernetes-version v1.31.14
[config/images] Pulled registry.k8s.io/kube-apiserver:v1.31.14
[config/images] Pulled registry.k8s.io/kube-controller-manager:v1.31.14
[config/images] Pulled registry.k8s.io/kube-scheduler:v1.31.14
[config/images] Pulled registry.k8s.io/kube-proxy:v1.31.14
[config/images] Pulled registry.k8s.io/coredns/coredns:v1.11.3
[config/images] Pulled registry.k8s.io/pause:3.10
[config/images] Pulled registry.k8s.io/etcd:3.5.24-0

real	4m53.031s

v1.32.13 那一轮只有 4 个新镜像，却花了 8 分 5 秒。这台机器磁盘慢，解压占了不少时间；网络和磁盘都会让这一步变得不可预测，所以要放到维护窗口之前做。

这条命令只在控制平面节点上拉，worker 上的 kube-proxy 新镜像不会被预拉。第一轮我没在 worker 上预拉，kube-proxy 滚动到 worker 时现场拉镜像；后面 CoreDNS 被调度到 worker 时也一样，Pulling 到 Pulled 花了 32 秒。第二轮在 worker 上提前执行了 crictl pull registry.k8s.io/kube-proxy:v1.32.13（35 秒）。

6. apply：第一次没有成功

健康检查 Job 15 秒超时

第一次执行 kubeadm upgrade apply v1.31.14 --yes 时宿主机严重过载，19 秒后直接失败：

[upgrade] Running cluster health checks
[upgrade/health] FATAL: [preflight] Some fatal errors occurred:
	[ERROR CreateJob]: Job "upgrade-health-check-hf7fq" in the namespace "kube-system" did not complete in 15s: no condition of type Complete
[preflight] If you know what you are doing, you can make a check non-fatal with `--ignore-preflight-errors=...`

kubeadm 的集群健康检查不只是调 API：它在 kube-system 里建一个 Job，用 pause 镜像跑一个容器，要求 15 秒内完成。看这个 Job 的时间戳：

NAME                         CREATED                START                  DONE                   TTL   DEADLINE
upgrade-health-check-hf7fq   2026-10-13T08:40:24Z   2026-10-13T08:40:40Z   2026-10-13T08:40:52Z   20    20
NAME                               CREATED                NODE
upgrade-health-check-hf7fq-zsfl7   2026-10-13T08:40:40Z   worker

Job 08:40:24 创建，Pod 到 08:40:40 才被 Job 控制器创建出来，中间隔了 16 秒，15 秒的超时在 Pod 出现之前就已经到了。所以这个检查同时考验了 controller-manager、调度器、某个节点上的 kubelet 和镜像（pause 必须已经在节点上或能拉到）。它失败时，别急着加 --ignore-preflight-errors，先看 Job 卡在哪一步：没创建出 Pod，看 controller-manager；Pod Pending，看调度和节点；容器起不来，看镜像和运行时。这次是在宿主机过载时撞上的，过载缓解后同样的检查就过了。

不过它并不只在过载时才会失败。第二轮换上 v1.32.13 的 kubeadm 执行 plan 时，又撞上了一次同样的 15 秒超时，而这次 Pod 并不慢：

NAME                                 CREATED                START                  DONE
upgrade-health-check-1791882130721   2026-10-13T09:02:10Z   2026-10-13T09:02:11Z   2026-10-13T09:02:27Z

Job 创建后 1 秒 Pod 就建出来了（事件里 09:02:14 容器已启动），但 Job 过了约 16 秒才被标记完成，刚好超过 15 秒。紧接着重跑一次 plan 就通过了。这时盯着 Pod 看，pause 容器 09:02:50 启动并在同一秒退出，Pod 状态到 09:02:55 才显示 terminated、09:02:57 才变成 Succeeded。容器早就退出了，慢在状态逐级上报和 Job 控制器的处理上，15 秒的余量并不宽裕。

apply 中途失败：控制平面升完了，附加组件没升

8. 节点：排空、upgrade node、kubelet、解除封锁

下面两段是按 v1.32 官方页面（Upgrading kubeadm clusters、Upgrading Linux nodes）核对过的完整步骤，以 Debian 系为例。切软件源和 apt/yum 这几行属于官方流程，本次在 kind 里没有逐字执行，而是用替换二进制代替。每升一个 minor，每个节点都要把这些步骤完整做一遍；升到下一个 minor 时，要按那个版本的官方页面重新核对一次。

第一个控制平面节点，每一轮：

# 1. 切软件源到目标 minor（仅跨 minor 时需要，见文末「软件包」）
sed -i 's#/v1.31/#/v1.32/#' /etc/apt/sources.list.d/kubernetes.list
# 2. 升级 kubeadm 包
apt-mark unhold kubeadm && apt-get update && apt-get install -y kubeadm='1.32.x-*' && apt-mark hold kubeadm
kubeadm version
# 3. 查看计划（apply 之前先做 etcd 快照，见第 1 节）
kubeadm upgrade plan
# 4. 升级控制平面
kubeadm upgrade apply v1.32.x
# 5. 按需升级 CNI 插件（官方原文：Manually upgrade your CNI provider plugin）
# 6. 排空（在管理机上）
kubectl drain <cp-node> --ignore-daemonsets
# 7. 升级 kubelet、kubectl 并重启
apt-mark unhold kubelet kubectl && apt-get update && apt-get install -y kubelet='1.32.x-*' kubectl='1.32.x-*' && apt-mark hold kubelet kubectl
systemctl daemon-reload && systemctl restart kubelet
# 8. 解除封锁（在管理机上）
kubectl uncordon <cp-node>

其余控制平面节点相同，只是第 3、4 步换成 kubeadm upgrade node。RHEL 系把 apt 那几行换成 yum install -y kubeadm-'1.32.x-*' --disableexcludes=kubernetes（kubelet、kubectl 同理）。

worker 节点的顺序是：升级 kubeadm → kubeadm upgrade node → drain → 升级 kubelet 和 kubectl → uncordon。

# 在该节点上：切软件源（跨 minor 时），apt/yum 升级 kubeadm（kind 中为替换二进制），然后
kubeadm upgrade node
# 在管理机上
kubectl drain <node> --ignore-daemonsets
# 在该节点上：apt/yum 升级 kubelet、kubectl（kind 中为替换二进制），然后
systemctl daemon-reload && systemctl restart kubelet
# 在管理机上
kubectl uncordon <node>

kubeadm upgrade node 在 worker 上只更新 kubelet 配置文件，不重启 kubelet，所以放在 drain 前后都可以。这次实际执行时，我是先 drain，再换 kubeadm、执行 kubeadm upgrade node，然后换 kubelet、kubectl 并重启，最后 uncordon，和官方顺序不完全一样。控制平面节点在 apply 之后同样是 drain → 升级 kubelet、kubectl → uncordon。

实验里 drain worker 时多加了两个参数：--delete-emptydir-data --timeout=60s（之后几次是 120s、180s）。

  • --delete-emptydir-data：节点上有 Pod 使用 emptyDir 时，drain 默认拒绝执行，因为 Pod 被驱逐后 emptyDir 里的数据会被删除、无法找回。加上这个参数，等于确认这些数据可以丢，比如缓存、临时文件。如果 emptyDir 里有还没落盘的业务数据，要先处理好再加。这次其实用不上：第一次 drain 控制平面时没有加这个参数也通过了，被驱逐的 CoreDNS 和 local-path-provisioner 都没有因 emptyDir 被拒；我在后面几次是预防性加的。
  • --timeout：drain 默认会一直等下去。被 PDB 挡住时，加上超时能让它按时退出并报错，脚本可以据此停下来，否则维护窗口会被无声地耗掉。下面「PDB 卡住排空」就是靠 60 秒超时暴露出来的。

每个节点做完都要过一道门槛再动下一台：节点 Ready；kubectl get nodes 里的版本正确；uncordon 确实成功，节点不再显示 SchedulingDisabled；该回到这台节点的业务 Pod 已经调度回来并 Ready。官方的说法是 worker 要「一次一台或几台」（one node at a time or few nodes at a time）地升级。第 7 节的 Forbidden 就是反例：uncordon 那一下失败了，如果脚本不检查就直接去 drain 下一台，集群会同时少掉两个节点的容量。

v1.32.13 之后目录合计 379M。etcd 备份是整个数据目录的拷贝（125M，含 WAL），而同一时刻 etcdctl snapshot save 出来的快照只有 3.7MB。而且每执行一次 apply 就多一份，包括那次 etcd 被跳过的重跑。etcd 数据量大的集群里，/etc/kubernetes 所在分区的剩余空间也要列入升级前检查。这份目录拷贝能帮助回退，但不能替代经过恢复演练的快照。

回退条件

控制平面、网络或存储验收失败时，停止升级后续节点。apply 自己在某个静态 Pod 起不来时会回滚该组件，但它不会回滚已经写进 kubeadm-config 的版本、已经续签的证书和已经升级的附加组件。从上面半升级的状态就能看出来。把 kubeadm 包降级回去不等于回滚：etcd 已经是新版本、数据也可能已被新版 apiserver 写过。真正的回退路径是预先演练过的 etcd 快照恢复加配置备份，见 etcd 快照。

kind 和真实主机的差别

  • 软件包。 真实主机上通过 pkgs.k8s.io 的软件源安装，这个源是按 minor 版本划分的，v1.31 的源里没有 v1.32 的包。升 minor 时要注意三点：每个节点都要切，worker 也不例外；在升级 kubeadm 之前切，否则 apt/yum 找不到目标版本；补丁升级（如 v1.31.0 → v1.31.14）不用切，同一个源里就有。Debian 系把 /etc/apt/sources.list.d/kubernetes.list 里的 v1.31 改成 v1.32，RHEL 系改 /etc/yum.repos.d/kubernetes.repo。官方文档中 kubeadm 的写法，Debian 系是 apt-mark unhold kubeadm && apt-get update && apt-get install -y kubeadm='1.32.x-*' && apt-mark hold kubeadm，RHEL 系是 yum install -y kubeadm-'1.32.x-*' --disableexcludes=kubernetes（软件源里通常排除了这几个包，防止被普通 yum update 意外升级，所以安装时要临时解除），kubelet、kubectl 同理。这次在 kind 里是直接替换二进制，包管理的这部分没有实测。旧的 apt.kubernetes.io / yum.kubernetes.io 源已经冻结，装不到新版本。
  • kubelet 服务。 kind 改过 kubelet 的 systemd 单元（RestartSec=1s 等），重启和恢复比常规主机快，真实环境的时间会不一样。
  • CNI。 kind 用 kindnet，这次升级没有碰 CNI。生产集群的 Calico、Cilium 等有自己的版本兼容矩阵，要在升级前单独核对，并且通常单独升级。
  • 规模。 一主一从放大了一些问题（PDB 卡住、CoreDNS 同时被驱逐、单控制平面中断），也掩盖了一些问题（多控制平面的 upgrade node、负载均衡摘除节点）。上面的耗时只说明这台机器上的情况，不能直接拿来估算维护窗口。
