StorageClass 决定如何供给存储

持久卷与存储声明一篇已经测过 PVC 从 Pending 到 Bound、数据在 Pod 重建后仍在、以及 Retain 的 PV 怎么挂回去。这一篇换个角度，只看 StorageClass 本身：PVC 里的类名怎么写、类上的 volumeBindingMode、reclaimPolicy、allowVolumeExpansion 各自在什么时候起作用，以及哪些行为其实是供给器决定的，而不是 Kubernetes。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18），实验放在单独的 notes-lab namespace。节点名简化成 control-plane、worker、worker2。StorageClass 是集群级对象，集群自带的 standard 只读不改；需要改字段的实验，另建了一个名为 notes-lab-storageclass-retain 的类（实验对象都以 notes-lab- 开头，便于清理），用完删掉。

先把现有的类读清楚

kubectl get storageclass
kubectl get storageclass standard -o yaml
NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
standard (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  60d
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
  name: standard
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer

（省略了 last-applied-configuration 等元数据。）几个值得注意的地方：

  • (default) 来自注解 storageclass.kubernetes.io/is-default-class: "true"，不是某个 spec 字段。官方文档说，如果有多个类都带这个注解，不写类名的 PVC 会用最新创建的那个。允许多个默认类只是为了迁移时平滑过渡，平时应该只留一个。
  • YAML 里根本没有 allowVolumeExpansion，kubectl get 显示成 false。字段缺省就是不允许扩容。
  • provisioner: rancher.io/local-path 只是一个名字。Kubernetes 不会校验它，谁监听这个名字，谁来建卷。所以从别的集群抄来的 StorageClass，provisioner 名字对不上时，PVC 只会一直等。

local-path 供给器的具体行为由 local-path-storage namespace 里的一个 ConfigMap 决定：

kubectl -n local-path-storage get configmap local-path-config -o yaml
data:
  config.json: |-
    {
            "nodePathMap":[
            {
                    "node":"DEFAULT_PATH_FOR_NON_LISTED_NODES",
                    "paths":["/var/local-path-provisioner"]
            }
            ]
    }
  helperPod.yaml: |-
    apiVersion: v1
    kind: Pod
    metadata:
      name: helper-pod
    spec:
      containers:
      - name: helper-pod
        image: docker.io/kindest/local-path-helper:v20230510-486859a6
        imagePullPolicy: IfNotPresent
  setup: |-
    #!/bin/sh
    set -eu
    mkdir -m 0777 -p "$VOL_DIR"
  teardown: |-
    #!/bin/sh
    set -eu
    rm -rf "$VOL_DIR"

所谓「供给一个卷」，就是派一个 helper Pod 到目标节点执行 setup 脚本，mkdir -m 0777；「删除卷」就是执行 teardown，rm -rf。后面看到的现象，大部分都能从这几行里找到原因。供给器本身的版本是 kindest/local-path-provisioner:v20241108-5c6d2daf。

PVC 里类名的三种写法

同时创建三个 PVC，只有 storageClassName 不同（保存为 pvcs.yaml）：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: no-class          # 不写 storageClassName
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 16Mi
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: empty-class
spec:
  storageClassName: ""    # 显式写空字符串
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 16Mi
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: bad-class
spec:
  storageClassName: fast-ssd   # 集群里没有这个类
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 16Mi
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f pvcs.yaml
kubectl -n notes-lab get pvc

40 秒后，三个都是 Pending：

NAME          STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
bad-class     Pending                                      fast-ssd       <unset>                 40s
empty-class   Pending                                                     <unset>                 40s
no-class      Pending                                      standard       <unset>                 40s

外表一样，事件完全不同：

kubectl -n notes-lab get events --sort-by=.lastTimestamp \
  -o custom-columns=TIME:.lastTimestamp,OBJ:.involvedObject.name,REASON:.reason,MSG:.message
TIME                   OBJ           REASON                 MSG
2026-10-13T05:19:11Z   bad-class     ProvisioningFailed     storageclass.storage.k8s.io "fast-ssd" not found
2026-10-13T05:19:11Z   empty-class   FailedBinding          no persistent volumes available for this claim and no storage class is set
2026-10-13T05:19:11Z   no-class      WaitForFirstConsumer   waiting for first consumer to be created before binding
  • 不写：DefaultStorageClass 准入插件在创建时把 standard 填了进去，之后就固定了。WaitForFirstConsumer 是正常的等待，下一节会让它绑定。
  • 写空字符串：明确表示「不要类」，也就关掉了动态供给。它只能绑定同样没有类的 PV，集群里没有，于是 FailedBinding。注意这个事件是 Normal 级别，不是 Warning，很容易被忽略。
  • 写错：ProvisioningFailed，直接说出类不存在。这次 PVC 一创建就有了这条事件（x3 over 40s，第一次出现在创建时）；在持久卷一篇里，同样的事件等了一分半，推测是那次碰上了 controller-manager 重启。

空字符串的用途是「我要一块管理员手工建好的卷」。建一个不带类的静态 PV 验证一下（集群级对象，需要相应权限；保存为 static-pv.yaml）：

apiVersion: v1
kind: PersistentVolume
metadata:
  name: notes-lab-storageclass-static
spec:
  capacity:
    storage: 16Mi
  accessModes: ["ReadWriteOnce"]
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /tmp/notes-lab-storageclass-static
kubectl apply -f static-pv.yaml
kubectl get pv notes-lab-storageclass-static
kubectl -n notes-lab get pvc

20 秒内 empty-class 就绑上了它，bad-class 没有去抢：

NAME          STATUS    VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
bad-class     Pending                                                                        fast-ssd       <unset>                 111s
empty-class   Bound     notes-lab-storageclass-static              16Mi       RWO                           <unset>                 111s
no-class      Bound     pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e   16Mi       RWO            standard       <unset>                 111s

（no-class 此时已经被下一节的 Pod 用上了。）PV 的匹配首先看类名是否相同："" 只配 ""，standard 只配 standard。官方示例里用 volumeName 预绑定 PV 时也会显式写 storageClassName: ""，注释是「否则会被设成默认类」，原因就在这里：不写类名，准入插件会填上默认类，再去找这个 PV 就对不上了。

还有一个本文没有实测的区别：集群里暂时没有默认类时，不写类名的 PVC 会保持「未设置」，等管理员设好默认类后，控制平面会回头给它补上；而写了 "" 的 PVC 不会被补。本集群一直有默认类，又不能改 standard，所以没有复现。

WaitForFirstConsumer：卷跟着第一个 Pod 走

给 no-class 起一个 Pod，不加任何节点约束（保存为 first.yaml）：

apiVersion: v1
kind: Pod
metadata:
  name: first
spec:
  terminationGracePeriodSeconds: 1
  containers:
    - name: c
      image: busybox:1.36
      command: ["sh", "-c", "echo \"$(hostname) $(date +%T)\" >> /data/log; cat /data/log; sleep 3600"]
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: no-class

Pod 05:19:37 提交，05:19:46 就绪，这次建卷只用了 6 秒（持久卷一篇那次用了 38 秒，那时集群更忙）。调度器选中 worker2 后，把节点名写进了 PVC 的注解（输出截取了相关部分）：

kubectl -n notes-lab get pvc no-class -o jsonpath='{.metadata.annotations}{"\n"}'
"volume.kubernetes.io/selected-node":"worker2","volume.kubernetes.io/storage-provisioner":"rancher.io/local-path"

供给器读到这个注解，才知道去哪台节点建目录。建出来的 PV 带着反向的约束：

PV=$(kubectl -n notes-lab get pvc no-class -o jsonpath='{.spec.volumeName}')
kubectl get pv $PV -o jsonpath='{.spec.nodeAffinity}{"\n"}{.spec.persistentVolumeReclaimPolicy}{"\n"}{.spec.hostPath.path}{"\n"}'
{"required":{"nodeSelectorTerms":[{"matchExpressions":[{"key":"kubernetes.io/hostname","operator":"In","values":["worker2"]}]}]}}
Delete
/var/local-path-provisioner/pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e_notes-lab_no-class

三行分别是 PV 的 nodeAffinity、继承自类的回收策略、节点上的目录。从这一刻起，任何想用这个 PVC 的 Pod 都只能去 worker2。再起一个 Pod second，清单和 first 相同，只改名字并加上节点选择：

metadata:
  name: second
spec:
  nodeSelector:
    kubernetes.io/hostname: worker
  # 其余与 first 相同，仍挂 claimName: no-class

15 秒后：

NAME     READY   STATUS    RESTARTS   AGE   IP       NODE     NOMINATED NODE   READINESS GATES
second   0/1     Pending   0          15s   <none>   <none>   <none>           <none>
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  15s   default-scheduler  0/3 nodes are available: 1 node(s) didn't match Pod's node affinity/selector. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

报错只提 nodeSelector，不提卷，3 个节点也只解释了 1 个。推测这是 v1.31.0 调度器 VolumeBinding 插件 v1.27 起引入的一个优化（v1.31.0 仍在）造成的：它在 PreFilter 阶段先按 PV 的 nodeAffinity 把候选节点缩成 worker2，worker2 又不满足 nodeSelector，报错里就只剩这一条；依据见 StatefulSet 一篇。这个优化后来被撤回（回移到 v1.31.3），新版本上的报错应该会逐个节点给出原因，本文只在 v1.31.0 上看过。排查时看到带 PVC 的 Pod 报 didn't match Pod's node affinity/selector，要把 PV 的 nodeAffinity 也拿出来对一下。

这也说明了 WaitForFirstConsumer 的意义：第一个 Pod 的调度约束（节点选择、亲和性、资源）决定卷建在哪里。如果让卷先建好、再调度 Pod，卷可能落在 Pod 去不了的节点上。官方文档还提醒，这个模式下不要用 nodeName 指定节点，nodeName 会绕过调度器，调度器不写 selected-node 注解，PVC 就会一直 Pending；要固定节点，用 kubernetes.io/hostname 的 nodeSelector。

自建一个 Retain + Immediate 的类

回收策略、绑定时机不能原地改（见下一节），standard 又不动，所以另建一个类。provisioner 照抄 standard：

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: notes-lab-storageclass-retain
provisioner: rancher.io/local-path
reclaimPolicy: Retain
volumeBindingMode: Immediate
allowVolumeExpansion: true
NAME                            PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
notes-lab-storageclass-retain   rancher.io/local-path   Retain          Immediate              true                   0s
standard (default)              rancher.io/local-path   Delete          WaitForFirstConsumer   false                  60d

用这个类创建 PVC imm。Immediate 的意思是 PVC 一创建就供给、绑定，不等 Pod。30 秒后：

NAME   STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS                    VOLUMEATTRIBUTESCLASS   AGE
imm    Pending                                      notes-lab-storageclass-retain   <unset>                 30s
Events:
  Type     Reason                Age                From                                     Message
  ----     ------                ----               ----                                     -------
  Normal   Provisioning          15s (x2 over 30s)  rancher.io/local-path_local-path-provisioner-...  External provisioner is provisioning volume for claim "notes-lab/imm"
  Warning  ProvisioningFailed    15s (x2 over 30s)  rancher.io/local-path_local-path-provisioner-...  failed to provision volume with StorageClass "notes-lab-storageclass-retain": configuration error, no node was specified
  Normal   ExternalProvisioning  4s (x3 over 30s)   persistentvolume-controller                       Waiting for a volume to be created either by the external provisioner 'rancher.io/local-path' or manually by the system administrator. If volume creation is delayed, please verify that the provisioner is running and correctly registered.

供给器确实立刻开始干活了，但失败：no node was specified。local-path 的卷是某台节点上的目录，它必须知道是哪台节点。上游源码 provisioner.go 里，节点取自 opts.SelectedNode，也就是调度器写的 selected-node 注解；非共享文件系统模式下它为空，就直接返回这个错误。Immediate 模式下调度器还没参与，没有注解，供给器就无从下手。供给器日志里每隔 15～30 秒重试一次，每次都是同样的错：

E1013 05:20:45.547232       1 controller.go:957] error syncing claim "ede67e26-db4e-4dcb-872a-95c6d02c8424": failed to provision volume with StorageClass "notes-lab-storageclass-retain": configuration error, no node was specified
E1013 05:21:00.548056       1 controller.go:957] error syncing claim "ede67e26-db4e-4dcb-872a-95c6d02c8424": failed to provision volume with StorageClass "notes-lab-storageclass-retain": configuration error, no node was specified
E1013 05:21:30.549036       1 controller.go:957] error syncing claim "ede67e26-db4e-4dcb-872a-95c6d02c8424": failed to provision volume with StorageClass "notes-lab-storageclass-retain": configuration error, no node was specified

这时候起一个 Pod immpod（清单同 first，只把名字改成 immpod、claimName 改成 imm）也救不了它，反而形成死锁：

Warning  FailedScheduling  20s   default-scheduler  0/3 nodes are available: pod has unbound immediate PersistentVolumeClaims. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

调度器的逻辑是：Immediate 模式的 PVC 应该已经绑好了，没绑好就不调度，等着；供给器那边在等调度器给节点。两边互相等。

为了确认原因确实是缺注解，手工把注解补上：

kubectl -n notes-lab annotate pvc imm volume.kubernetes.io/selected-node=worker
2026-10-13T05:21:45Z   imm           Provisioning            External provisioner is provisioning volume for claim "notes-lab/imm"
2026-10-13T05:21:51Z   imm           ProvisioningSucceeded   Successfully provisioned volume pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424
2026-10-13T05:21:56Z   immpod        Pulled                  Container image "busybox:1.36" already present on machine
2026-10-13T05:21:57Z   immpod        Started                 Started container c

05:21:45 打上注解，6 秒后卷建好，PVC 绑定，一直 Pending 的 Pod 随后被调度到 worker。这说明卡点就在节点信息上。但这只是验证手段，不是用法：手工指定节点等于替调度器做决定，节点资源、污点都没人检查。结论：本集群这种 nodePathMap 配置的 local-path，只能用 WaitForFirstConsumer。local-path 的 README 另外提到 sharedFileSystemPath 模式（所有节点挂同一个共享文件系统），那种模式可以用 Immediate，本文没有测。官方文档对 Immediate 的说明也提到，对于不是所有节点都能访问的存储，Immediate 模式会在不了解 Pod 调度需求的情况下供给卷，可能导致 Pod 无法调度；云盘这类按可用区划分的存储也有同样的问题，只是程度轻一些（本文没有在云盘上实测）。

这块卷的 PV 继承了新类的回收策略：

PV2=$(kubectl -n notes-lab get pvc imm -o jsonpath='{.spec.volumeName}')
kubectl get pv $PV2 -o 'custom-columns=NAME:.metadata.name,CLASS:.spec.storageClassName,RECLAIM:.spec.persistentVolumeReclaimPolicy,NODE:.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]'
NAME                                       CLASS                           RECLAIM   NODE
pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424   notes-lab-storageclass-retain   Retain    worker

类的字段能不能改

kubectl patch storageclass notes-lab-storageclass-retain -p '{"reclaimPolicy":"Delete"}'
kubectl patch storageclass notes-lab-storageclass-retain -p '{"allowVolumeExpansion":false}'
The StorageClass "notes-lab-storageclass-retain" is invalid: reclaimPolicy: Forbidden: updates to reclaimPolicy are forbidden.
storageclass.storage.k8s.io/notes-lab-storageclass-retain patched

reclaimPolicy 创建后不能改（按 API 的校验规则，provisioner、parameters、volumeBindingMode 也不可变，本文没有逐个试），allowVolumeExpansion 可以随时开关。这条实验是在第二次建这个类时做的（第一次建的类已在回收实验中删掉，见后文），类名和其余字段相同，只把绑定模式换成了 WaitForFirstConsumer。

要改不可变字段，只能删掉类再按同名重建。删除 StorageClass 时 API 没有阻拦，已经存在的 PV 和 PVC 仍然记着类名。后面回收一节会看到，在本集群的 local-path 上，类删掉之后旧 PV 的清理照样能完成；换成别的供给器是否如此，没有验证。

扩容：请求被接受，然后就没有然后了

先在 standard 的 PVC 上试，把 16Mi 改成 32Mi：

kubectl -n notes-lab patch pvc no-class -p '{"spec":{"resources":{"requests":{"storage":"32Mi"}}}}'
Error from server (Forbidden): persistentvolumeclaims "no-class" is forbidden: only dynamically provisioned pvc can be resized and the storageclass that provisions the pvc must support resize

standard 没有 allowVolumeExpansion，准入阶段就拒绝了，PVC 不变。这是好的失败：立刻、明确。

换到 allowVolumeExpansion: true 的 imm 上，同样的 patch 被接受了：

kubectl -n notes-lab patch pvc imm -p '{"spec":{"resources":{"requests":{"storage":"32Mi"}}}}'
persistentvolumeclaim/imm patched

30 秒后：

kubectl -n notes-lab get pvc imm -o jsonpath='{.spec.resources.requests.storage} {.status.capacity.storage}{"\n"}'
kubectl -n notes-lab describe pvc imm | sed -n '/^Events/,$p'

（下面只保留了 describe 事件里与扩容相关的一行。）

32Mi 16Mi
  Warning  ExternalExpanding      30s                 volume_expand                                                                                      waiting for an external controller to expand this PVC

第一列是 spec.resources.requests.storage，第二列是 status.capacity.storage。申请已经是 32Mi，实际容量仍是 16Mi，PV 的 capacity 也还是 16Mi。Kubernetes 的扩容控制器发现这个卷不归内置插件管，就留下一条 ExternalExpanding，等外部的 resizer 来处理。可是 local-path 供给器只管建和删，不提供扩容，没有任何组件会来接手。patch（05:22:22）后 69 秒再看，状态没变，这条事件仍只有一次。

StorageClass 上的 allowVolumeExpansion: true 只是一个许可，它不代表驱动真的会扩容。 这个开关是集群管理员自己填的，填错了没有任何校验。现实中更常见的是 CSI 驱动支持扩容，这时会有 external-resizer sidecar 接手，PVC 上会出现 Resizing、FileSystemResizePending 之类的条件；本文没有支持扩容的驱动，没有实测。

想撤回这次扩容请求也不行：

kubectl -n notes-lab patch pvc imm -p '{"spec":{"resources":{"requests":{"storage":"16Mi"}}}}'
The PersistentVolumeClaim "imm" is invalid: spec.resources.requests.storage: Forbidden: field can not be less than previous value

在 v1.31.0 默认配置下，requests.storage 只能往大改。官方文档描述的「扩容失败后改成比上次请求小的值重试」依赖 RecoverVolumeExpansionFailure 特性门控，它在 1.31 默认关闭；即使开启，新值也必须严格大于 status.capacity，这里 16Mi 等于当前容量，同样不满足。本文没有开启门控验证。所以这个 PVC 就带着一个永远完不成的 32Mi 申请，直到被删除。如果有监控按 requests 和 capacity 是否一致来报警，会一直报。

顺带一提，容量申请在 local-path 上本来就不起约束作用：往这个 16Mi 的卷里 dd 写入 48M 照样成功，节点上的目录占了 49M，权限是 setup 脚本给的 drwxrwxrwx，原因见持久卷一篇的容量实验。

回收策略：谁来删节点上的目录

Delete：5 秒，目录一起没

no-class 来自 standard，回收策略是 Delete。删掉 Pod 和 PVC：

05:23:15
persistentvolumeclaim "no-class" deleted
05:23:15
05:23:21
Error from server (NotFound): persistentvolumes "pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e" not found

供给器日志显示它又派了一个 helper Pod 去 worker2 执行 teardown：

time="2026-10-13T05:23:15Z" level=info msg="Deleting volume pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e at worker2:/var/local-path-provisioner/pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e_notes-lab_no-class" 
time="2026-10-13T05:23:15Z" level=info msg="create the helper pod helper-pod-delete-pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e into local-path-storage" 
time="2026-10-13T05:23:20Z" level=info msg="Volume pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e has been deleted on worker2:/var/local-path-provisioner/pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e_notes-lab_no-class"

删除前后各在节点上执行一次 docker exec <worker2 的节点容器> ls /var/local-path-provisioner/：删除前列出 pvc-a63388ea-..._notes-lab_no-class，删除后输出为空。顺序是先删数据，再删 PV 对象：PV 对象一消失，节点上的数据就已经没了。官方文档说，不写 reclaimPolicy 时默认就是 Delete。

Retain：PV 留下，数据留下，收尾归你

删掉 imm 的 Pod 和 PVC：

NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM           STORAGECLASS                    VOLUMEATTRIBUTESCLASS   REASON   AGE
pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424   16Mi       RWO            Retain           Released   notes-lab/imm   notes-lab-storageclass-retain   <unset>                          2m

Released 的定义是「claim 已删除，但对应的存储资源还没被集群回收」。节点 worker 上的目录还在。Released 的 PV 怎样重新挂给新 PVC，持久卷一篇已经演示过，这里只看怎么收尾。有两条路，结果截然不同。

路线一：把 PV 改成 Delete，让供给器来删。 这次先把 StorageClass notes-lab-storageclass-retain 删了，故意让 PV 指向一个已不存在的类，然后：

kubectl patch pv pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424 \
  -p '{"spec":{"persistentVolumeReclaimPolicy":"Delete"}}'
I1013 05:23:56.771073       1 controller.go:1471] delete "pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424": started
time="2026-10-13T05:23:56Z" level=info msg="Deleting volume pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424 at worker:/var/local-path-provisioner/pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424_notes-lab_imm" 
time="2026-10-13T05:24:02Z" level=info msg="Volume pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424 has been deleted on worker:/var/local-path-provisioner/pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424_notes-lab_imm" 
I1013 05:24:02.791417       1 controller.go:1536] delete "pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424": succeeded

改完立刻触发，6 秒后 PV 和节点目录都没了。类已经被删了，删除照样完成，这是本集群 local-path 配置下的实测结果。看上游源码，Delete 会按 PV 上记的类名选配置：ConfigMap 里没有 storageClassConfigs（本集群就是）时直接用全局配置，不读 StorageClass；配置了 storageClassConfigs 而类名不在其中时，会报 BUG: Got request for unexpected storage class。其他驱动（比如 CSI）删卷时是否需要类，本文没有测，推测各不相同。

路线二：直接删 PV 对象。 这是更符合直觉、也更容易出事的做法。重建一个同名的 Retain 类（这次用 WaitForFirstConsumer），新建 PVC keep（同 imm，只改名字）和 Pod keeper（同 first，名字改成 keeper、claimName 改成 keep）。keeper 被调度到 worker2，写入一行 keeper 05:24:54 后删掉 Pod 和 PVC，PV 变成 Released，然后：

kubectl delete pv pvc-6422019d-ba03-444d-889c-6a2a0e45a35b
05:25:05
persistentvolume "pvc-6422019d-ba03-444d-889c-6a2a0e45a35b" deleted

20 秒后到节点 worker2 上看（kind 的节点就是 Docker 容器）：

docker exec <worker2 的节点容器> ls /var/local-path-provisioner/
docker exec <worker2 的节点容器> sh -c 'cat /var/local-path-provisioner/*_notes-lab_keep/log'
pvc-6422019d-ba03-444d-889c-6a2a0e45a35b_notes-lab_keep
keeper 05:24:54

目录和数据原样留着。供给器日志里查这个卷的 ID 的删除记录：

kubectl -n local-path-storage logs deploy/local-path-provisioner --since=2m \
  | grep 6422019d-ba03-444d-889c-6a2a0e45a35b | grep -v Event | grep -i delet

grep 无输出。去掉最后一个 grep 只按 ID 计数（--since=1m），有 8 行日志，但上面的删除过滤一条都没匹配到：供给器没有执行删除。

PV 对象没了，kubectl get pv 也显示 No resources found，从 Kubernetes 里已经看不到这块数据的任何线索。这和官方文档对 Retain 手工回收的描述一致：删除 PV 后，底层存储资源依然存在，需要手工清理数据、手工删除存储资源。在 local-path 上，「手工」意味着登录节点删目录；本实验最后就是这样清掉的：

docker exec <worker2 的节点容器> rm -rf /var/local-path-provisioner/pvc-6422019d-..._notes-lab_keep

换成云盘，留下的就是一块继续计费、没人认领的盘（推测，本文没有在云上实测）。所以 Retain 卷要退役时，先决定数据还要不要：要，就先备份或挂到新 PVC；不要，就把 PV 改成 Delete，让供给器按正规流程删，而不是直接 kubectl delete pv。

排查时看哪里

PVC Pending 时，先看 kubectl describe pvc 的事件：

事件含义
WaitForFirstConsumer正常，等第一个使用它的 Pod
FailedBinding ... no storage class is set（Normal）写了 storageClassName: ""，又没有无类的 PV
ProvisioningFailed ... storageclass ... not found类名写错。PVC 上的类名不能改，要么删掉重建，要么补建同名的类
ProvisioningFailed ... no node was specified节点本地存储用了 Immediate，换成 WaitForFirstConsumer 的类
ExternalProvisioning 一直重复，且既没有 Provisioning 也没有 ProvisioningFailed没人认领这个 provisioner 名字，或供给器没在运行

Pod Pending、PVC 已经 Bound 时，把 PV 的 nodeAffinity 和 Pod 的节点约束放在一起看。扩容后 requests 和 capacity 一直对不上，先确认驱动是否真的支持扩容，allowVolumeExpansion 只是许可。Retain 的 PV 删除前，先想好由谁清理底层数据。

清理

kubectl -n notes-lab delete pod --all
kubectl -n notes-lab delete pvc --all
kubectl delete pv notes-lab-storageclass-static   # Retain 的静态 PV，PVC 删后停在 Released
kubectl get pv                                  # 尤其留意 Retain 的 Released PV
kubectl delete storageclass notes-lab-storageclass-retain
kubectl delete namespace notes-lab

本次实验结束后，kubectl get pv 为空，三个节点的 /var/local-path-provisioner/ 下都没有本实验留下的目录。
