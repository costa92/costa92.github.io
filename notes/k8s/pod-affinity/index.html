Pod 亲和与反亲和

Pod 调度与节点选择 讲的 nodeSelector、节点亲和性看的是节点标签。Pod 间亲和与反亲和看的是节点上已经有哪些 Pod：「如果某个拓扑域里已经运行着匹配规则 Y 的 Pod，那么这个 Pod 应该（反亲和则是不应该）放进这个域」。拓扑域由 topologyKey 指定，它是一个节点标签的键，值相同的节点属于同一个域：kubernetes.io/hostname 就是一个节点一个域，topology.kubernetes.io/zone 就是一个可用区一个域。

规则同样分两种：requiredDuringSchedulingIgnoredDuringExecution 是过滤条件，不满足就不能调度；preferredDuringSchedulingIgnoredDuringExecution 只参与打分。过滤和打分的基本流程、FailedScheduling 消息的读法在调度那篇已经拆过，这里不再重复。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0），节点名简化成 control-plane、worker、worker2。control-plane 带 kubeadm 默认的 NoSchedule 污点，所以真正可调度的只有两个 worker，这一点会反复出现在实验结果里。实验用的节点标签加了 notes-lab.io/ 前缀，做完全部删除；Pod 都很小（requests 10m CPU / 16Mi 内存）。除了 web-anti 和 web-mlk 两个 Deployment，其余实验 Pod 都加了 terminationGracePeriodSeconds: 0 以便快速删除重来，下文 YAML 为了简洁省略了这一行。

硬反亲和：两个节点放不下三个副本

最常见的用法是「同一个 Deployment 的副本不要挤在一个节点上」。保存为 anti-req.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-anti
spec:
  replicas: 3
  selector:
    matchLabels: {app: web-anti}
  template:
    metadata:
      labels: {app: web-anti}
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels: {app: web-anti}
              topologyKey: kubernetes.io/hostname
      containers:
        - name: app
          image: busybox:1.36
          command: ["sleep", "3600"]
          resources:
            requests: {cpu: 10m, memory: 16Mi}
kubectl create namespace notes-lab
kubectl -n notes-lab apply -f anti-req.yaml
kubectl -n notes-lab get pod -o wide
NAME                        READY   STATUS    RESTARTS   AGE   NODE
web-anti-5684d4b9b7-cgjr5   0/1     Pending   0          12s   <none>
web-anti-5684d4b9b7-vpwjh   1/1     Running   0          12s   worker2
web-anti-5684d4b9b7-wtgmf   1/1     Running   0          12s   worker
Warning  FailedScheduling  12s   default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) didn't match pod anti-affinity rules. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

两个 worker 各有一个副本，第三个无处可去。消息里的 didn't match pod anti-affinity rules 指的是这个 Pod 自己的反亲和规则没被满足；后面会看到另一种措辞，指的是别人的规则。抢占那一段是 2 No preemption victims found，说明调度器认为驱逐一些 Pod 有可能让反亲和成立，只是这次没有找到优先级比它低的 Pod。对比后面硬亲和失败时的 3 Preemption is not helpful：缺一个目标 Pod，驱逐谁也变不出来。

副本占满所有拓扑域时，默认滚动更新可能卡住

把副本数降到 2，正好一个节点一个，看起来没问题了。接着做一次普通的滚动更新：

kubectl -n notes-lab scale deploy web-anti --replicas=2
kubectl -n notes-lab set env deploy/web-anti VERSION=v2     # 04:36:10
kubectl -n notes-lab rollout status deploy/web-anti --timeout=5s
kubectl -n notes-lab get rs
Waiting for deployment "web-anti" rollout to finish: 1 out of 2 new replicas have been updated...
error: timed out waiting for the condition
NAME                  DESIRED   CURRENT   READY   AGE
web-anti-5684d4b9b7   2         2         2       58s
web-anti-6bc4996849   1         1         0       35s

新 ReplicaSet 的第一个 Pod 一直 Pending，事件和上面一字不差。原因在默认策略：

{"rollingUpdate":{"maxSurge":"25%","maxUnavailable":"25%"},"type":"RollingUpdate"}

2 副本时 maxSurge 25% 向上取整是 1，maxUnavailable 25% 向下取整是 0。控制器必须先多起一个新 Pod，等它就绪才能删旧的；而新 Pod 带着同样的 app: web-anti 标签，反亲和把它挡在两个都有旧副本的节点之外。新的起不来，旧的不能删，滚动更新就停在这里，不会自己恢复。

卡死的条件是两个同时成立：每个拓扑域里都已有旧副本（没有空域给多出来的新 Pod），并且 maxUnavailable 取整后为 0。默认 25% 向下取整，副本数 ≤ 3 时才是 0；副本数为 4 及以上时 maxUnavailable 至少为 1，控制器可以先删旧 Pod 腾位置，滚动不会卡死，只是每一轮都要等旧 Pod 终止（本次只测了 2 副本）。

解决办法之一是允许先删后建：

kubectl -n notes-lab patch deploy web-anti \
  -p '{"spec":{"strategy":{"rollingUpdate":{"maxSurge":0,"maxUnavailable":1}}}}'   # 04:36:50

这次能走完，但用了 74 秒（04:36:50 到 04:38:04）。按事件时间排开（调度器的事件只填 eventTime，kubelet 和控制器的事件只填 firstTimestamp，所以要两列一起看）：

kubectl -n notes-lab get events \
  -o custom-columns=ETIME:.eventTime,FIRST:.firstTimestamp,OBJ:.involvedObject.name,REASON:.reason
<nil>                         2026-10-13T04:36:50Z   web-anti-5684d4b9b7-vpwjh   Killing
2026-10-13T04:37:23.237911Z   <nil>                  web-anti-6bc4996849-hlh9r   Scheduled
<nil>                         2026-10-13T04:37:25Z   web-anti-5684d4b9b7-wtgmf   Killing
2026-10-13T04:37:25.343110Z   <nil>                  web-anti-6bc4996849-dzmnh   FailedScheduling
2026-10-13T04:38:00.757751Z   <nil>                  web-anti-6bc4996849-dzmnh   Scheduled

旧 Pod 04:36:50 开始停止，新 Pod 直到 04:37:23 才被调度到同一个节点，中间隔了 33 秒；第二轮是 04:37:25 到 04:38:00，35 秒。sleep 作为 1 号进程不处理 SIGTERM，要等满默认的 30 秒宽限期才被杀掉。两轮间隔都略大于 30 秒，和「旧 Pod 处于 Terminating 期间仍然算作节点上的匹配 Pod，直到对象真正删掉」相符（推测，没有直接看调度器缓存）。所以在硬反亲和下，旧 Pod 的优雅终止时间会直接加到每一轮滚动的耗时上。

更好的办法是下文的 matchLabelKeys，让每个版本只和自己版本的 Pod 互斥。

软反亲和：尽量打散，不会 Pending

改成 preferredDuringSchedulingIgnoredDuringExecution 后，规则只影响打分。为了排除 Deployment 自带的打散效果（调度器默认的拓扑分布约束只对属于 Service、ReplicaSet、StatefulSet 等的 Pod 生效），这里用裸 Pod：每轮依次创建 4 个带相同标签的 Pod，间隔 2 秒，记下落点，删掉再来。带软反亲和的写法：

apiVersion: v1
kind: Pod
metadata:
  name: spread-1
  labels: {app: spread}
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels: {app: spread}
            topologyKey: kubernetes.io/hostname
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}

对照组 solo-* 去掉整个 affinity。各跑三轮：

轮次无亲和（solo）软反亲和（spread）
1worker2 ×3，worker ×12 / 2，顺序 worker、worker2、worker、worker2
2worker2 ×3，worker ×12 / 2，顺序 worker2、worker、worker2、worker
3worker2 ×2，worker ×22 / 2，顺序 worker2、worker、worker、worker2

没有亲和时，裸 Pod 的落点由资源均衡类打分决定，三轮里有两轮是 3:1。软反亲和三轮都是 2:2，而且前两个 Pod 一定分开。第 3 个 Pod 到来时两个节点上各有一个匹配 Pod，反亲和对两边扣分相同，等于没有偏好，第 3 轮它就和第 2 个落在了同一个节点，再由第 4 个补到另一边。软反亲和管的是「避开匹配 Pod 更多的域」，不是精确均分；要稳定的均匀分布，用拓扑分布约束。

weight 只在多条规则之间有意义

调度那篇实测过，只有一条 preferred 节点亲和时，weight 写 1 和 100 没有区别。Pod 间亲和的 weight 也主要用来在多条规则冲突时比大小。先用 nodeName 固定两个 Pod：db 在 worker，batch 在 worker2。新 Pod 同时想避开两者，但只能选一个节点：

affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100        # 避开 db
        podAffinityTerm:
          labelSelector: {matchLabels: {app: db}}
          topologyKey: kubernetes.io/hostname
      - weight: 10         # 避开 batch
        podAffinityTerm:
          labelSelector: {matchLabels: {app: batch}}
          topologyKey: kubernetes.io/hostname

三组权重各跑三次，结果完全一致：

w-db1-batch2      worker
w-db10-batch100   worker
w-db100-batch10   worker2

避开 db 的权重大，就去 worker2（和 batch 挤）；反过来就去 worker。1 对 2 和 10 对 100 效果相同。按 v1.31 InterPodAffinity 插件的实现，各节点的原始得分做的是最小–最大归一化：(得分 − 最低分) × 100 / (最高分 − 最低分)，和 NodeAffinity 只按最高分等比缩放不同。归一化后最高的节点是 100、最低的是 0；只有两个候选节点时结果永远是 100 和 0，所以这组实验只说明了「两个节点时只看大小顺序」，节点更多时权重的具体数值会不会影响结果，本次没有测。

硬亲和：目标 Pod 不存在就 Pending

反过来，让 web 必须和 app: cache 的 Pod 在同一节点。保存为 web-near-cache.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: web
  labels: {app: web}
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels: {app: cache}
          topologyKey: kubernetes.io/hostname
  containers:
    - name: app
      image: nginx:alpine
      resources:
        requests: {cpu: 10m, memory: 16Mi}

先只提交 web（04:40:07）：

NAME   READY   STATUS    RESTARTS   AGE   IP       NODE
web    0/1     Pending   0          8s    <none>   <none>
Warning  FailedScheduling  8s    default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) didn't match pod affinity rules. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

8 秒后再提交一个普通的 cache Pod，保存为 cache.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: cache
  labels: {app: cache}
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}
kubectl -n notes-lab apply -f cache.yaml
kubectl -n notes-lab get events \
  -o custom-columns=ETIME:.eventTime,OBJ:.involvedObject.name,REASON:.reason
2026-10-13T04:40:07.676647Z   web                         FailedScheduling
2026-10-13T04:40:15.803615Z   cache                       Scheduled
2026-10-13T04:40:15.804887Z   web                         Scheduled

两条 Scheduled 消息里的目标节点都是 worker。cache 被调度后 1.3 毫秒，Pending 的 web 就被放到了同一个节点。这时两者都还是 ContainerCreating，cache 根本没运行：亲和匹配的是已经分配到节点的 Pod，不关心它是否 Ready。所以硬亲和保证不了「web 启动时 cache 已经可用」，启动顺序和依赖要靠应用自己的重试或探针。

自亲和的第一个 Pod 是特例

如果一组 Pod 都要求「和带 app: group 的 Pod 在一起」，而它们自己就带 app: group，按上面的逻辑第一个 Pod 永远找不到目标，整组就死锁了。调度器为此留了一个特例：集群里没有任何其他 Pod 匹配这条规则（命名空间和选择器都算），这个 Pod 自己匹配自己的规则，并且选中的节点带有所有要求的 topologyKey 标签时，它可以被调度。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: group
spec:
  replicas: 3
  selector:
    matchLabels: {app: group}
  template:
    metadata:
      labels: {app: group}
    spec:
      affinity:
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels: {app: group}
              topologyKey: kubernetes.io/hostname
      containers:
        - name: app
          image: busybox:1.36
          command: ["sleep", "3600"]
          resources:
            requests: {cpu: 10m, memory: 16Mi}

跑了两次，3 个副本每次都全部落在同一个节点（两次都是 worker）：

NAME                    STATUS    NODE
group-ff7d8988d-7w4p7   Pending   worker
group-ff7d8988d-8p269   Pending   worker
group-ff7d8988d-lfssr   Pending   worker

（这里的 Pending 是 phase，节点已经分配，容器还在创建。）前面的 web 就不满足这个特例：它的标签是 app: web，不匹配自己要求的 app: cache，于是只能等。另外要注意，硬的自亲和意味着整组永远挤在第一个 Pod 所在的拓扑域里，节点放不下时剩下的副本会 Pending，而不是换个地方。

命名空间范围：默认只看自己的 namespace

亲和项默认只在待调度 Pod 所在的 namespace 里找匹配的 Pod。在另一个 namespace notes-lab-b（打上标签 notes-lab.io/team=cache）里放一个 cache，它落在 worker2。先删掉上一节留在 notes-lab 里的 web 和 cache，否则 ns-default 会直接找到本 namespace 的那个 cache：

kubectl -n notes-lab delete pod web cache
kubectl create namespace notes-lab-b
kubectl label namespace notes-lab-b notes-lab.io/team=cache
until kubectl -n notes-lab-b get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab-b apply -f cache.yaml

然后在 notes-lab 里提交四个只有范围不同的 Pod，亲和规则仍是 app: cache + kubernetes.io/hostname：

Pod范围字段结果
ns-default不写Pending，didn't match pod affinity rules
ns-listnamespaces: ["notes-lab-b"]worker2
ns-selectornamespaceSelector: {matchLabels: {notes-lab.io/team: cache}}worker2
ns-allnamespaceSelector: {}worker2

ns-list 的写法，字段和 labelSelector、topologyKey 同级：

- labelSelector:
    matchLabels: {app: cache}
  topologyKey: kubernetes.io/hostname
  namespaces: ["notes-lab-b"]
NAME          NODE
ns-all        worker2
ns-default    <none>
ns-list       worker2
ns-selector   worker2

几条规则：namespaces 和 namespaceSelector 都不写时只看本 namespace；namespaceSelector: {}（空对象）匹配所有 namespace，和不写是两回事；两个字段同时写时取并集（API 参考里的说法，本次没有测）。ns-default 的失败消息和「目标根本不存在」时完全一样，消息不会提示「别的 namespace 里有匹配的 Pod」。目标服务和调用方分属不同 namespace 时，这是最容易漏的一项。

topologyKey：节点缺标签时，反亲和会悄悄失效

topologyKey 不必是主机名。给两个 worker 都打上同一个临时 zone 标签，模拟「两台机器在同一个可用区」：

kubectl label node worker worker2 notes-lab.io/zone=a

把前面的 web-anti 改名为 zone-anti，topologyKey 换成 notes-lab.io/zone，副本数 2：

NAME                         STATUS    NODE
zone-anti-7c96586b66-jcvgd   Pending   <none>
zone-anti-7c96586b66-qhgx8   Pending   worker
Warning  FailedScheduling  8s    default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) didn't match pod anti-affinity rules. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

worker2 上明明一个 zone-anti 都没有，第二个副本还是进不去：两个节点同属 zone=a，反亲和按域比较，不按节点。04:46:38 把 worker2 改成 zone=b，同一秒内 Pending 的副本就被调度了（04:46:38.98 Scheduled），节点标签变化会触发重试。

接下来是这次最值得记住的现象。把 worker2 上的 zone 标签删掉，再扩到 4 个副本：

kubectl label node worker2 notes-lab.io/zone-
kubectl -n notes-lab scale deploy zone-anti --replicas=4

worker                             Ready    <none>          60d   v1.31.0   a

NAME                         STATUS    NODE
zone-anti-7c96586b66-b7jdn   Running   worker2
zone-anti-7c96586b66-gq72r   Running   worker2
zone-anti-7c96586b66-jcvgd   Running   worker2
zone-anti-7c96586b66-qhgx8   Running   worker

没有任何 Pending，3 个副本叠在了没有 zone 标签的 worker2 上。没有这个标签的节点不属于任何 zone 域，反亲和对它不起约束。官方文档对此只有一句提醒：反亲和要求每个节点都带有 topologyKey 对应的标签，否则「可能导致意外行为」。实际效果是规则形同虚设，而且没有任何事件或告警。新加入的节点池忘了打 zone 标签，就会发生这种事。和拓扑分布约束对照着看更清楚：DoNotSchedule 的分布约束会直接跳过缺标签的节点（消息里带 missing required label），表现是节点闲着不接 Pod；硬反亲和则相反，缺标签的节点不受约束，表现是 Pod 叠在一起。

硬亲和方向正好相反，缺标签的节点是进不去的。先把副本数缩回 2（kubectl -n notes-lab scale deploy/zone-anti --replicas=2），此时 worker（zone=a）和 worker2（无标签）上各有一个 zone-anti Pod。再提交一个要求按 zone 亲和 app: zone-anti 的 Pod，连试三次：

zf-1   worker
zf-2   worker
zf-3   worker

三次都在 worker。尽管 worker2 上也有匹配的 Pod，它不在任何 zone 里，不算「同一个域」。

IgnoredDuringExecution：调度之后的变化不会驱逐 Pod

规则只在调度那一刻检查。先清掉前面的工作负载，重新创建 cache 和 web：

kubectl -n notes-lab delete deploy zone-anti
kubectl -n notes-lab delete pod --all --wait
kubectl -n notes-lab apply -f cache.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/cache --timeout=120s
kubectl -n notes-lab apply -f web-near-cache.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/web --timeout=120s

这次两者都在 worker2 上。04:45:27 把 cache 的标签改掉：

kubectl -n notes-lab label pod cache app=cache-retired --overwrite

45 秒后再提交一个和 web 一模一样的 web2：

NAME    APP             STATUS    RESTARTS   NODE
cache   cache-retired   Running   0          worker2
web     web             Running   0          worker2
web2    web             Pending   <none>     <none>

web 的亲和条件已经不成立了，它照常运行，没有重启；新来的 web2 才按新状态判断，找不到目标而 Pending。反亲和也一样：下一节的实验里，把同节点上的一个 Pod 改成被禁止的标签，60 秒内两边都没被动过。想在条件变化后把 Pod 重新排布，Kubernetes 本身不会做，需要手动删 Pod 或用 descheduler 一类的组件（后者本次没有测）。

反亲和是对称的：别人的规则也会挡住你

一个 Pod 没写任何亲和规则，也可能因为反亲和 Pending。先创建 loner，用 nodeSelector 固定在 worker，并声明「不和 app: noisy 的 Pod 在同一节点」：

apiVersion: v1
kind: Pod
metadata:
  name: loner
  labels: {app: loner}
spec:
  nodeSelector:
    kubernetes.io/hostname: worker
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels: {app: noisy}
          topologyKey: kubernetes.io/hostname
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}

再提交三个只带 app: noisy 标签、没有任何亲和规则的 Pod，外加一个 noisy-pinned，它用 nodeSelector 指定了 worker：

NAME           STATUS    NODE
loner          Pending   worker
noisy-1        Pending   worker2
noisy-2        Pending   worker2
noisy-3        Pending   worker2
noisy-pinned   Pending   <none>

（前四个已分配节点，phase 为 Pending 是因为容器还在创建。）三个 noisy 都落在 worker2，但前面的对照组显示裸 Pod 本来就常偏向 worker2，这一点单独说明不了什么。真正的证据是 noisy-pinned：它只能去 worker，结果无处可去：

Warning  FailedScheduling  6s    default-scheduler  0/3 nodes are available: 1 node(s) didn't match Pod's node affinity/selector, 1 node(s) didn't satisfy existing pods anti-affinity rules, 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }. preemption: 0/3 nodes are available: 1 No preemption victims found for incoming pod, 2 Preemption is not helpful for scheduling.

注意措辞变成了 didn't satisfy existing pods anti-affinity rules：拒绝它的是节点上已有 Pod 的规则。排查一个没写亲和却 Pending 的 Pod，看到这句就该去查目标节点上谁带着 podAntiAffinity：

kubectl get pod -A --field-selector spec.nodeName=worker \
  -o jsonpath='{range .items[?(@.spec.affinity.podAntiAffinity)]}{.metadata.namespace}/{.metadata.name}{"\n"}{end}'

这条命令里的存在性过滤 ?(@.spec.affinity.podAntiAffinity) 本次没有在这个场景下运行过，写法见 kubectl JSONPath。

过滤阶段只有已有 Pod 的硬反亲和是对称的，它们的硬亲和不会挡住新 Pod。打分阶段则不止于此：按 v1.31 InterPodAffinity 插件的打分实现，已有 Pod 的硬亲和（按 hardPodAffinityWeight 计，默认 1）以及 preferred 亲和、反亲和，仍会给新 Pod 在对应节点上加分或减分。这部分本次没有单独测。官方概念页「Ignored Fields」一节的说法是已有 Pod 的 preferred 亲和、反亲和不参与新 Pod 的调度，和 v1.31 源码不一致，这里以源码为准。

接着做上一节提到的 IgnoredDuringExecution 测试：在 worker 上起一个 quiet（标签 app: quiet），就绪后 04:42:32 把它改成 app: noisy。60 秒后：

NAME           APP     STATUS    RESTARTS   NODE
loner          loner   Running   0          worker
noisy-pinned   noisy   Pending   <none>     <none>
quiet          noisy   Running   0          worker

loner 的规则已经被违反，两边都没被驱逐；noisy-pinned 照样被挡着。04:43:40 删除 loner：

2026-10-13T04:42:06.950653Z   noisy-pinned                FailedScheduling
2026-10-13T04:43:49.970110Z   noisy-pinned                Scheduled

阻挡它的 Pod 一删，noisy-pinned 就被调度了，不需要重建。不过中间隔了约 9 秒，不像打节点标签时那样在 1 秒内反应。事件会被聚合成系列，eventTime 只记第一次出现的时间（describe 里 x2 over 5s 这类计数就是聚合的表现），所以看不出删除前最后一次重试发生在什么时候，也就判断不了它当时是否处于退避中。这 9 秒的原因本次没有查明。

matchLabelKeys 与 mismatchLabelKeys

这两个字段在 v1.31 是 beta，默认开启。在本集群的 apiserver 指标里可以确认：

kubectl get --raw /metrics | grep 'kubernetes_feature_enabled{name="MatchLabelKeysInPodAffinity"'
kubernetes_feature_enabled{name="MatchLabelKeysInPodAffinity",stage="BETA"} 1

matchLabelKeys：按版本互斥，解决滚动更新卡死

matchLabelKeys 列出一些标签键，apiserver 在创建 Pod 时取出 Pod 自身这些标签的值，合并进 labelSelector。配合 Deployment 给每个版本打的 pod-template-hash，就能让反亲和只在同一版本内生效：

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels: {app: web-mlk}
        matchLabelKeys: ["pod-template-hash"]
        topologyKey: kubernetes.io/hostname

看创建出来的 Pod，选择器已经被改写了：

kubectl -n notes-lab get pod <pod> -o jsonpath='{.spec.affinity.podAntiAffinity}'
{
    "requiredDuringSchedulingIgnoredDuringExecution": [
        {
            "labelSelector": {
                "matchExpressions": [
                    {
                        "key": "pod-template-hash",
                        "operator": "In",
                        "values": [
                            "776fb66bff"
                        ]
                    }
                ],
                "matchLabels": {
                    "app": "web-mlk"
                }
            },
            "matchLabelKeys": [
                "pod-template-hash"
            ],
            "topologyKey": "kubernetes.io/hostname"
        }
    ]
}

同样 2 副本、同样默认的 25%/25% 策略，04:47:40 触发滚动更新，04:47:46 就报告完成：

NAME                       HASH         STATUS    NODE
web-mlk-776fb66bff-6t7ff   776fb66bff   Running   worker
web-mlk-776fb66bff-vsglc   776fb66bff   Running   worker2
web-mlk-7fb5bbf9c-2w9fc    7fb5bbf9c    Running   worker2
web-mlk-7fb5bbf9c-x6n9n    7fb5bbf9c    Running   worker

新旧版本可以在同一节点上短暂共存（旧的两个此时正在 Terminating），新版本两个副本之间仍然互相分开。和前面 web-anti 卡住、改策略后还要 74 秒相比，差别很明显。代价是滚动过程中某个节点会同时跑新旧两个副本，反亲和在这段时间里不是严格的「一个节点一个」。

改写发生在 apiserver 创建 Pod 时，所以之后直接修改 Pod 上的这个标签，已经合并进去的选择器不会跟着变，官方文档也提醒不要对会被直接修改的标签使用这个字段。

mismatchLabelKeys：不同租户不共享节点

mismatchLabelKeys 合并进去的是 NotIn。每个 Pod 都带 tenant 标签，并写同一条反亲和：

metadata:
  labels: {tenant: a}
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchExpressions:
              - {key: tenant, operator: Exists}
          mismatchLabelKeys: ["tenant"]
          topologyKey: kubernetes.io/hostname

依次提交 a-1、a-2、b-1、b-2、c-1，每个间隔 3 秒：

NAME   TENANT   STATUS    NODE
a-1    a        Running   worker
a-2    a        Running   worker2
b-1    b        Pending   <none>
b-2    b        Pending   <none>
c-1    c        Pending   <none>

c-1 合并后的选择器是「有 tenant 标签且 tenant 不是 c」：

{"matchExpressions":[{"key":"tenant","operator":"Exists"},{"key":"tenant","operator":"NotIn","values":["c"]}]}

规则本身工作正常，问题在于租户 a 的两个 Pod 分别落在了两个节点上（为什么这样分没有单独测；前面的裸 Pod 对照组反而偏向 worker2），把仅有的两个节点都「占」成了 a 的地盘，后来的租户全部 Pending。04:48:52 删掉 a-2 后，b-1、b-2 一起进了 worker2（同租户可以共处），c-1 仍然 Pending。光靠 mismatchLabelKeys 只能保证隔离，不能保证每个租户都有位置。官方示例另外配了一条 matchLabelKeys: [tenant] 的硬亲和，文档给的用途是让租户的 Pod 落到正确的节点池；按它的语义，这条亲和也会把同一租户的 Pod 收拢到同一个域里，避免一个租户摊满所有域（这是我的理解，本次没有测）。即使这样，拓扑域的数量仍然要不少于租户数，否则总有租户 Pending。labelSelector 里的 tenant Exists 也不能省：没有它，选择器会匹配到同一 namespace 里所有不带 tenant 标签的 Pod；如果再配了 namespaceSelector 把范围扩到其他 namespace，DaemonSet 之类不带 tenant 标签的 Pod 也会被算进来。

两个写错就被拒绝的地方

API 校验会挡掉一些错误，用 --dry-run=server 就能看到：

The Pod "no-topo" is invalid: 
* spec.affinity.podAffinity.requiredDuringSchedulingIgnoredDuringExecution[0].topologyKey: Required value: can not be empty
The Pod "mlk-conflict" is invalid: 
* spec.affinity.podAffinity.requiredDuringSchedulingIgnoredDuringExecution[0][0]: Invalid value: "app": exists in both matchLabelKeys and labelSelector
* spec.affinity.podAffinity.requiredDuringSchedulingIgnoredDuringExecution[0].matchLabelKeys[0]: Invalid value: "app": exists in both matchLabelKeys and mismatchLabelKeys

topologyKey 不能为空；同一个键不能既出现在 matchLabelKeys 又出现在 labelSelector 或 mismatchLabelKeys 里。但前面那些真正麻烦的情况，比如 namespace 范围写漏、节点缺 topologyKey 标签，都能通过校验。

排查清单

现象消息或线索先查什么
副本 Pendingdidn't match pod anti-affinity rules副本数是否超过拓扑域数量；topologyKey 是否太粗（zone 而非节点）
滚动更新卡住新 RS 的 Pod 报上面那条硬反亲和 + 每个域都有旧副本 + maxUnavailable 取整为 0（默认 25% 时副本数 ≤ 3）；改用 matchLabelKeys: [pod-template-hash]

另外，官方文档提醒 Pod 间亲和计算量较大，不建议在几百个节点以上的集群里大量使用。只是想把副本打散时，拓扑分布约束通常是更直接的选择；按节点属性选位置则用节点亲和性，排斥则用污点与容忍。
