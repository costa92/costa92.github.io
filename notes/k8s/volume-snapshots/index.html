快照不是给所有 PVC 自动提供的功能

PV、PVC 与 StorageClass解释了 PVC 如何获得底层卷。卷快照多了三块拼图，缺一块都不行：

  • snapshot.storage.k8s.io 下的三个 CRD：VolumeSnapshot、VolumeSnapshotContent、VolumeSnapshotClass。它们不属于核心 API，按官方文档的说法，CRD 和控制器应由 Kubernetes 发行版负责安装。
  • 部署在控制平面的 snapshot-controller，负责创建、绑定、删除 VolumeSnapshotContent。
  • 和 CSI 驱动部署在一起的 csi-snapshotter sidecar，它盯着 VolumeSnapshotContent，再去调用驱动的 CreateSnapshot / DeleteSnapshot。

这也意味着快照只对 CSI 卷有效。

先检查：一个装不了快照的集群长什么样

我日常用的实验集群是三节点 kind（Kubernetes v1.31.0，containerd 1.7.18，Calico），默认 StorageClass standard 来自 local-path-provisioner。动手之前先只读检查一遍：

kubectl api-resources | grep -i snapshot
kubectl get csidrivers
kubectl get storageclass standard \
  -o custom-columns=NAME:.metadata.name,PROVISIONER:.provisioner,BINDING:.volumeBindingMode,RECLAIM:.reclaimPolicy
$ kubectl api-resources | grep -i snapshot
$ kubectl get csidrivers
NAME            ATTACHREQUIRED   PODINFOONMOUNT   STORAGECAPACITY   TOKENREQUESTS   REQUIRESREPUBLISH   MODES       AGE
csi.tigera.io   true             true             false             <unset>         false               Ephemeral   61d
NAME       PROVISIONER             BINDING                RECLAIM
standard   rancher.io/local-path   WaitForFirstConsumer   Delete

三项都不满足：

  • api-resources 里没有任何 snapshot 资源，CRD 没装，kubectl get volumesnapshotclass 直接报 the server doesn't have a resource type "volumesnapshotclass"。
  • 唯一的 CSIDriver csi.tigera.io 是 Calico 自带的，MODES 只有 Ephemeral，它不提供持久卷，跟快照没关系。别看到列表里有 CSI 驱动就以为能做快照。
  • standard 的 provisioner 是 rancher.io/local-path，不是 CSI 驱动。

最后一点可以用一个实际的 PVC 再确认。在 notes-lab 里建一个 1Gi、StorageClass 为 standard 的 PVC，再用一个 busybox Pod 挂上它（standard 是 WaitForFirstConsumer，没有 Pod 用它就不会绑定）：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: demo-data
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: standard
  resources:
    requests:
      storage: 1Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: writer
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh","-c","sleep 3600"]
    resources: {requests: {cpu: 10m, memory: 16Mi}}
    volumeMounts: [{name: data, mountPath: /data}]
  volumes:
  - name: data
    persistentVolumeClaim: {claimName: demo-data}
kubectl create namespace notes-lab
kubectl -n notes-lab apply -f shared-pvc.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/writer --timeout=180s

然后看它的 PV：

PV=$(kubectl -n notes-lab get pvc demo-data -o jsonpath='{.spec.volumeName}')
kubectl get pv "$PV" -o jsonpath='csi.driver=[{.spec.csi.driver}] hostPath={.spec.hostPath.path}{"\n"}'
csi.driver=[] hostPath=/var/local-path-provisioner/<pvc-dir>

.spec.csi.driver 是空的，卷是一个节点上的 hostPath 目录。这种卷就算以后装上 CRD 也做不了快照。此时硬提交一个 VolumeSnapshot，连 API 都对不上：

$ kubectl -n notes-lab apply -f demo-snapshot.yaml
error: resource mapping not found for name: "demo-snapshot" namespace: "" from "demo-snapshot.yaml": no matches for kind "VolumeSnapshot" in version "snapshot.storage.k8s.io/v1"
ensure CRDs are installed first

检查到这一步，应该停下来：要么换一个支持快照的 CSI 驱动，要么接受这个集群不做卷快照。不要往共享集群里随手装 CRD。

搭一个能做快照的一次性集群

下面的实验都在一个单节点的一次性 kind 集群（kind v0.24.0，kindest/node:v1.31.0）上做，装的是上游的 hostpath CSI 驱动。这个驱动是给测试用的，把数据放在节点本地目录里，不能用于生产。

先建集群，kubeconfig 写到单独的文件里，不碰默认的 ~/.kube/config，再让当前终端指向它：

kind create cluster --name notes-lab-snap --image kindest/node:v1.31.0 \
  --kubeconfig ./notes-lab-snap.kubeconfig
export KUBECONFIG=$PWD/notes-lab-snap.kubeconfig
kubectl config current-context    # 应输出 kind-notes-lab-snap

从这里开始，所有命令都针对这个新集群的 context kind-notes-lab-snap。换了终端要重新 export KUBECONFIG，否则 CRD 会被装进别的集群。

用到的版本：

组件版本来源
快照 CRDv8.2.0kubernetes-csi/external-snapshotter 的 client/config/crd/
snapshot-controllerv8.2.0同仓库 deploy/kubernetes/snapshot-controller/
csi-driver-host-pathv1.17.0（插件镜像实际是 hostpathplugin:v1.16.1）deploy/kubernetes-1.31/deploy.sh

第一步只装 CRD：

git clone --depth 1 -b v8.2.0 https://github.com/kubernetes-csi/external-snapshotter.git
cd external-snapshotter
kubectl kustomize client/config/crd | kubectl create -f -
kubectl create namespace notes-lab

在这里停一下，先做下一节「CRD 装了、控制器没装」的实验，再装控制器：

kubectl -n kube-system kustomize deploy/kubernetes/snapshot-controller | kubectl create -f -
kubectl -n kube-system set image deploy/snapshot-controller \
  snapshot-controller=registry.k8s.io/sig-storage/snapshot-controller:v8.2.0

第二条命令是因为 v8.2.0 这个 tag 里 setup-snapshot-controller.yaml 写的镜像仍是 snapshot-controller:v8.0.1，要和 CRD 版本对齐（我实际是在 apply 前直接改了清单里的镜像，效果相同）。最后装 hostpath 驱动：

cd ..
git clone --depth 1 -b v1.17.0 https://github.com/kubernetes-csi/csi-driver-host-path.git
cd csi-driver-host-path
deploy/kubernetes-1.31/deploy.sh
kubectl apply -f examples/csi-storageclass.yaml

deploy/kubernetes-1.31 是指向 kubernetes-1.30 的符号链接。hostpath 驱动 v1.17.0 的清单里，csi-snapshotter sidecar 用的也是 v8.2.0。部署脚本会装 CSIDriver、带 8 个容器的 csi-hostpathplugin StatefulSet 和一个 VolumeSnapshotClass，但不会创建 StorageClass，所以要另外 apply 仓库里的 examples/csi-storageclass.yaml（csi-hostpath-sc，volumeBindingMode: Immediate）。镜像全部来自 registry.k8s.io，这次 10 个镜像在节点里并行拉取，用了不到 4 分钟。

装完以后再跑一遍检查：

$ kubectl get csidrivers
NAME                  ATTACHREQUIRED   PODINFOONMOUNT   STORAGECAPACITY   TOKENREQUESTS   REQUIRESREPUBLISH   MODES                  AGE
hostpath.csi.k8s.io   true             true             false             <unset>         false               Persistent,Ephemeral   3m1s
$ kubectl get volumesnapshotclass
NAME                     DRIVER                DELETIONPOLICY   AGE
csi-hostpath-snapclass   hostpath.csi.k8s.io   Delete           2m59s

MODES 里有了 Persistent，快照类的 DRIVER 和它一致，这才算具备条件。

CRD 装了、控制器没装：对象建得出来，但什么都不会发生

这一步故意插在 CRD 和控制器之间做：只装了 CRD，就提交一个 VolumeSnapshot。它引用的 PVC demo-data 和快照类这时都还不存在：

apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: early-snap
  namespace: notes-lab
spec:
  volumeSnapshotClassName: csi-hostpath-snapclass
  source:
    persistentVolumeClaimName: demo-data
$ kubectl apply -f early-snap.yaml
volumesnapshot.snapshot.storage.k8s.io/early-snap created
$ kubectl -n notes-lab get volumesnapshot early-snap
NAME         READYTOUSE   SOURCEPVC   SOURCESNAPSHOTCONTENT   RESTORESIZE   SNAPSHOTCLASS            SNAPSHOTCONTENT   CREATIONTIME   AGE
early-snap                demo-data                                         csi-hostpath-snapclass                                    20s
$ kubectl -n notes-lab get volumesnapshot early-snap -o jsonpath='status=[{.status}] finalizers=[{.metadata.finalizers}]{"\n"}'
status=[] finalizers=[]

API Server 照单全收，因为 CRD 只校验字段格式，不检查引用的 PVC 和类存不存在。READYTOUSE 是空的，不是 false：status 整个没有，finalizer 也没有，describe 里 Events: <none>。快照对象完全没有 status、没有事件，就说明没有任何控制器在处理它。

控制器起来后，这个对象马上有了反应：

Status:
  Error:
    Message:     Failed to create snapshot content with error snapshot controller failed to update early-snap on API server: cannot get claim from snapshot
    Time:        2026-10-13T11:42:11Z
  Ready To Use:  false
Events:
  Type     Reason                         Age   From                 Message
  ----     ------                         ----  ----                 -------
  Warning  SnapshotContentCreationFailed  39s   snapshot-controller  Failed to create snapshot content with error snapshot controller failed to update early-snap on API server: cannot get claim from snapshot

cannot get claim from snapshot 指的是源 PVC 找不到。看完这条事件，我在创建 demo-data 之前把 early-snap 删掉了。删除命令没有记进实验记录，具体时间不详。

后面「控制器中途停掉」一节还会在集群正常运转时把控制器缩到 0 副本，再验证一次。

快照与恢复

写入可识别的数据

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: demo-data
  namespace: notes-lab
spec:
  storageClassName: csi-hostpath-sc
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: writer
  namespace: notes-lab
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 36000"]
    resources: {requests: {cpu: 10m, memory: 16Mi}}
    volumeMounts: [{name: data, mountPath: /data}]
  volumes:
  - name: data
    persistentVolumeClaim: {claimName: demo-data}

这次 PV 里有了 CSI 驱动：

driver=hostpath.csi.k8s.io handle=4fa86f46-c6fb-11f1-9524-5a4bc721600a

写一个带时间的标记文件和一个 50MB 的随机文件，记下校验和：

kubectl -n notes-lab exec writer -- sh -c 'echo "before-snapshot $(date -u +%T)" > /data/marker.txt; dd if=/dev/urandom of=/data/blob.bin bs=1M count=50 2>/dev/null; sync; md5sum /data/blob.bin; cat /data/marker.txt'
8ddbbfd9dc7e664c5046fd72bb1fb843  /data/blob.bin
before-snapshot 11:43:43

创建快照，看它何时可用

apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: demo-snapshot
  namespace: notes-lab
spec:
  volumeSnapshotClassName: csi-hostpath-snapclass
  source:
    persistentVolumeClaimName: demo-data

apply 之后每半秒查一次 readyToUse 和绑定的 content：

11:43:55.894 ready= content=
11:43:56.530 ready=false content=snapcontent-a4e2450d-d9c1-4d05-a7c3-0bd07e4da579
11:43:57.118 ready=false content=snapcontent-a4e2450d-d9c1-4d05-a7c3-0bd07e4da579
11:43:57.725 ready=true content=snapcontent-a4e2450d-d9c1-4d05-a7c3-0bd07e4da579

经历了三个状态：先是没有 status，然后控制器建好 VolumeSnapshotContent 并绑定（ready=false），最后驱动做完快照（ready=true）。在 hostpath 上不到 2 秒，云盘一类的后端可能慢得多。恢复之前一定要等 READYTOUSE 为 true，对象创建成功不代表快照已经可用。

紧接着往源卷追加一行，用来区分快照前后的数据：

before-snapshot 11:43:43
after-snapshot 11:43:57

VolumeSnapshot 和 VolumeSnapshotContent

$ kubectl -n notes-lab get volumesnapshot demo-snapshot
NAME            READYTOUSE   SOURCEPVC   SOURCESNAPSHOTCONTENT   RESTORESIZE   SNAPSHOTCLASS            SNAPSHOTCONTENT                                    CREATIONTIME   AGE
demo-snapshot   true         demo-data                           1Gi           csi-hostpath-snapclass   snapcontent-a4e2450d-d9c1-4d05-a7c3-0bd07e4da579   1s             2s
$ kubectl get volumesnapshotcontent
NAME                                               READYTOUSE   RESTORESIZE   DELETIONPOLICY   DRIVER                VOLUMESNAPSHOTCLASS      VOLUMESNAPSHOT   VOLUMESNAPSHOTNAMESPACE   AGE
snapcontent-a4e2450d-d9c1-4d05-a7c3-0bd07e4da579   true         1073741824    Delete           hostpath.csi.k8s.io   csi-hostpath-snapclass   demo-snapshot    notes-lab                 2s

这两个对象的关系和 PVC / PV 一样：VolumeSnapshot 是命名空间里的申请，VolumeSnapshotContent 是集群级别的实体，名字就是 snapcontent- 加上 VolumeSnapshot 的 UID。content 的关键字段：

spec:
  deletionPolicy: Delete
  driver: hostpath.csi.k8s.io
  source:
    volumeHandle: 4fa86f46-c6fb-11f1-9524-5a4bc721600a
  sourceVolumeMode: Filesystem
  volumeSnapshotClassName: csi-hostpath-snapclass
  volumeSnapshotRef:
    apiVersion: snapshot.storage.k8s.io/v1
    kind: VolumeSnapshot
    name: demo-snapshot
    namespace: notes-lab
    resourceVersion: "1164"
    uid: a4e2450d-d9c1-4d05-a7c3-0bd07e4da579
status:
  creationTime: 1791891836331528419
  readyToUse: true
  restoreSize: 1073741824
  snapshotHandle: 5f4f3c4d-c6fb-11f1-9524-5a4bc721600a

source.volumeHandle 是源卷在驱动里的 ID，status.snapshotHandle 是存储系统里那份快照的 ID。restoreSize 是 1Gi，即源卷的容量，而不是实际写入的 50MB。

hostpath 驱动把快照存到了哪里，可以直接进驱动容器看：

$ kubectl exec csi-hostpathplugin-0 -c hostpath -- ls -la /csi-data-dir/
drwxr-xr-x 2 root root     4096 Oct 13 11:43 4fa86f46-c6fb-11f1-9524-5a4bc721600a
-rw-r--r-- 1 root root 52437189 Oct 13 11:43 5f4f3c4d-c6fb-11f1-9524-5a4bc721600a.snap
-rw------- 1 root root     1028 Oct 13 11:43 state.json
$ kubectl exec csi-hostpathplugin-0 -c hostpath -- tar -tzvf /csi-data-dir/5f4f3c4d-c6fb-11f1-9524-5a4bc721600a.snap
drwxr-xr-x root/root         0 2026-10-13 11:43 ./
-rw-r--r-- root/root  52428800 2026-10-13 11:43 ./blob.bin
-rw-r--r-- root/root        25 2026-10-13 11:43 ./marker.txt

所谓快照，在这个驱动里就是把卷目录打成一个 tar 包，和源卷放在同一块节点磁盘上。marker.txt 是 25 字节，只有第一行。云厂商的块存储快照实现各不相同，有的是增量、有的会复制到对象存储，但道理是一样的：快照放在哪、和源卷是否共享故障域，由存储系统决定，Kubernetes 管不了。

恢复到新的 PVC

恢复不是把快照写回原卷，而是新建一个 PVC，用 dataSource 指向快照：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: restored-data
  namespace: notes-lab
spec:
  storageClassName: csi-hostpath-sc
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
  dataSource:
    name: demo-snapshot
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io

同时建了三个，只有容量不同：restored-data 1Gi、restored-big 2Gi、restored-small 500Mi。

NAME             STATUS    VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS      VOLUMEATTRIBUTESCLASS   AGE
demo-data        Bound     pvc-afcaf15e-2f9c-41dd-854e-0545916165a4   1Gi        RWO            csi-hostpath-sc   <unset>                 58s
restored-big     Bound     pvc-d39d2575-e97b-4139-b792-bf37dd2e5e14   2Gi        RWO            csi-hostpath-sc   <unset>                 8s
restored-data    Bound     pvc-2bb4f007-f725-4e42-aeb0-f55c979abc28   1Gi        RWO            csi-hostpath-sc   <unset>                 8s
restored-small   Pending                                                                        csi-hostpath-sc   <unset>                 8s

比快照小的那个卡在 Pending，原因写在 PVC 事件里，由 external-provisioner 报出：

Warning  ProvisioningFailed    8s (x4 over 15s)  hostpath.csi.k8s.io_csi-hostpathplugin-0_e0409720-99f5-4669-8974-f491cea285c0  failed to provision volume with StorageClass "csi-hostpath-sc": error getting handle for DataSource Type VolumeSnapshot by Name demo-snapshot: requested volume size 524288000 is less than the size 1073741824 for the source snapshot demo-snapshot

所以恢复的容量至少要等于快照的 RESTORESIZE，可以更大。挂上一个 Pod 读两个恢复卷：

apiVersion: v1
kind: Pod
metadata:
  name: reader
  namespace: notes-lab
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 36000"]
    resources: {requests: {cpu: 10m, memory: 16Mi}}
    volumeMounts:
    - {name: r1, mountPath: /restored}
    - {name: r2, mountPath: /restored-big}
  volumes:
  - name: r1
    persistentVolumeClaim: {claimName: restored-data}
  - name: r2
    persistentVolumeClaim: {claimName: restored-big}
kubectl -n notes-lab exec reader -- sh -c 'cat /restored/marker.txt; md5sum /restored/blob.bin; cat /restored-big/marker.txt'
before-snapshot 11:43:43
8ddbbfd9dc7e664c5046fd72bb1fb843  /restored/blob.bin
before-snapshot 11:43:43

校验和与源文件一致，11:43:57 写入的 after-snapshot 两个卷里都没有，快照只包含创建那一刻的数据。2Gi 的卷在 PV 上显示为 2Gi，但 hostpath 驱动并不限制目录大小，容器里 df 看到的是整块节点磁盘，所以这里没法验证「恢复到更大的卷后文件系统是否跟着扩容」。在真实块存储上，这取决于驱动是否在恢复后扩展文件系统，要按驱动文档核对。

这次的 csi-hostpath-sc 是 Immediate，PVC 建好就开始恢复。如果 StorageClass 是 WaitForFirstConsumer，恢复的 PVC 会先停在 Pending，等第一个使用它的 Pod 调度后才供给，这时 Pending 是正常的。

跨命名空间恢复：一个不报错的坑

快照在 notes-lab，想在另一个命名空间里恢复：

kubectl create namespace notes-lab-other

第一个 PVC xns-plain 就是上面的 restored-data 换了名字，namespace 改成 notes-lab-other，仍用 dataSource。dataSource 没有 namespace 字段，只会在 PVC 自己的命名空间里找：

Warning  ProvisioningFailed    3s (x4 over 10s)  hostpath.csi.k8s.io_csi-hostpathplugin-0_e0409720-99f5-4669-8974-f491cea285c0  failed to provision volume with StorageClass "csi-hostpath-sc": error getting handle for DataSource Type VolumeSnapshot by Name demo-snapshot: error getting snapshot demo-snapshot from api server: volumesnapshots.snapshot.storage.k8s.io "demo-snapshot" not found

PVC 停在 Pending，报错写得很清楚。真正的坑在另一种写法，dataSourceRef 支持写 namespace：

dataSourceRef:
  name: demo-snapshot
  namespace: notes-lab
  kind: VolumeSnapshot
  apiGroup: snapshot.storage.k8s.io
NAME        STATUS    VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS      VOLUMEATTRIBUTESCLASS   AGE
xns-plain   Pending                                                                        csi-hostpath-sc   <unset>                 10s
xns-ref     Bound     pvc-9b2277c8-7401-4058-bf01-acfca5a1881a   1Gi        RWO            csi-hostpath-sc   <unset>                 10s

xns-ref 立刻 Bound，事件里是 ProvisioningSucceeded，看上去恢复成功了。查一下它的 spec，再用一个一次性 Pod xns-check 挂上它、列出目录内容：

kubectl -n notes-lab-other run xns-check --image=busybox:1.36 --restart=Never --overrides='{"spec":{"containers":[{"name":"c","image":"busybox:1.36","command":["ls","-la","/data"],"volumeMounts":[{"name":"d","mountPath":"/data"}]}],"volumes":[{"name":"d","persistentVolumeClaim":{"claimName":"xns-ref"}}]}}'

后文的 inuse-check、gone-check 也是这种写法，只换了 claimName 和 command。

$ kubectl -n notes-lab-other get pvc xns-ref -o jsonpath='dataSource={.spec.dataSource} dataSourceRef={.spec.dataSourceRef}{"\n"}'
dataSource= dataSourceRef=
$ kubectl -n notes-lab-other logs xns-check
total 8
drwxr-xr-x    2 root     root          4096 Oct 13 11:44 .
drwxr-xr-x    1 root     root          4096 Oct 13 11:45 ..

dataSourceRef 被 API Server 整个丢掉了，得到的是一个空卷，apply 时没有任何警告。原因是跨命名空间数据源（CrossNamespaceVolumeDataSource）在 v1.31 还是 Alpha，默认关闭：

kubernetes_feature_enabled{name="AnyVolumeDataSource",stage="BETA"} 1
kubernetes_feature_enabled{name="CrossNamespaceVolumeDataSource",stage="ALPHA"} 0

按官方文档，要用这个功能，需要在 kube-apiserver、kube-controller-manager 上同时打开 AnyVolumeDataSource 和 CrossNamespaceVolumeDataSource，csi-provisioner 也要打开后者，并且在快照所在的命名空间建 Gateway API 的 ReferenceGrant。门控关闭时字段被静默丢弃，这是本次实测到的行为，和 v1.31 源码 pkg/api/persistentvolumeclaim/util.go 一致：门控关闭、dataSourceRef.namespace 非空（且不是更新一个已在使用该字段的旧 PVC）时，整个 dataSourceRef 被置为 nil。这和文档里「dataSourceRef never ignores values」的说法形成反差：那句讲的是非法取值会报错，而门控关闭时根本轮不到校验，字段在进入校验前就被去掉了。

提交前可以用服务端 dry-run 看 API Server 最终会存下什么：

$ kubectl apply --dry-run=server -f xns-ref.yaml -o jsonpath='{.spec.dataSourceRef}{"|"}{.spec.dataSource}{"\n"}'
|

竖线两边都是空的，说明 dataSourceRef 和 dataSource 都没留下。实际影响是：自动化脚本只检查 PVC 是否 Bound，会把一个空卷当成恢复成功。恢复后一定要读一遍数据核对。

快照一个正在写的卷

快照不要求先停 Pod，但这不代表正在写的数据会被完整地拍下来。实验时我在 writer 里放了一个模拟事务的后台循环，每笔先写 BEGIN，等 1 秒再写 COMMIT。下面这条启动命令是示意：实际运行的那条没有记进实验记录。

# 示意：在 writer 里后台运行一个两步写入的循环
kubectl -n notes-lab exec writer -- sh -c 'nohup sh -c "i=0; while true; do i=\$((i+1)); echo \"BEGIN txn \$i\" >> /data/journal.log; sleep 1; echo \"COMMIT txn \$i\" >> /data/journal.log; sleep 0.1; done" >/dev/null 2>&1 &'

循环运行期间创建快照 inuse-snap（写法同 demo-snapshot），就绪后看源卷，再把它恢复成 inuse-restore（写法同 restored-data），用 inuse-check Pod 执行 tail -3 /data/journal.log：

$ kubectl -n notes-lab exec writer -- tail -2 /data/journal.log
BEGIN txn 6
COMMIT txn 6
$ kubectl -n notes-lab logs inuse-check
BEGIN txn 5
COMMIT txn 5
BEGIN txn 6

恢复出来的卷里，第 6 笔只有 BEGIN，没有 COMMIT。能下的结论只有一条：在这种 tar 实现下，快照不保证一致。

这跟驱动怎么做快照有关。hostpath 驱动的 CreateSnapshot（pkg/hostpath/controllerserver.go）调用 tar 把卷目录逐个文件打包，打包期间应用还在写，不同文件甚至同一文件的不同部分可能来自不同时刻，连崩溃一致都不保证。块存储驱动通常在块层面截取同一时刻，给出崩溃一致（crash-consistent）的快照，相当于那一刻拔掉电源后磁盘上的样子；这一点是推测，这次没有在块存储上验证。

即便快照是原子的，也只能做到崩溃一致。数据库能靠自己的日志从这种状态恢复，前提是快照是原子的；应用还留在内存缓冲、没有落盘的数据不会进快照。要得到应用一致的快照，需要先让应用停写或刷盘（例如数据库的备份模式、fsfreeze），或者用带钩子的备份工具。Kubernetes 的快照 API 本身不管这一层。

几种常见的失败

没写快照类、写错类名、驱动不匹配

apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: wrong-driver-class
driver: ebs.csi.aws.com
deletionPolicy: Delete

同时提交三个快照：snap-no-class 不写 volumeSnapshotClassName，snap-missing-class 写一个不存在的类，snap-wrong-driver 用上面这个驱动不匹配的类。15 秒后：

NAME                 READYTOUSE   SOURCEPVC   SOURCESNAPSHOTCONTENT   RESTORESIZE   SNAPSHOTCLASS        SNAPSHOTCONTENT                                    CREATIONTIME   AGE
snap-no-class                     demo-data                                                                                                                                15s
snap-missing-class                demo-data                                         does-not-exist                                                                         15s
snap-wrong-driver    false        demo-data                                         wrong-driver-class   snapcontent-d67d1c3c-3f5b-416e-9b84-9b899e61cc62                  15s

前两个在事件里直接给出原因：

Warning  SetDefaultSnapshotClassFailed  15s   snapshot-controller  Failed to set default snapshot class with error cannot find default snapshot class
Warning  GetSnapshotClassFailed  15s   snapshot-controller  Failed to get snapshot class with error volumesnapshotclass.snapshot.storage.k8s.io "does-not-exist" not found

驱动不匹配的最隐蔽。控制器不检查 PVC 的驱动和快照类的驱动是否一致，照样建了 content，然后只留下一条 Normal 事件：

Normal  CreatingSnapshot  15s   snapshot-controller  Waiting for a snapshot notes-lab/snap-wrong-driver to be created by the CSI driver.

集群里没有 ebs.csi.aws.com 的 sidecar 来接这个 content，它的 status 一直是空的，等多久都一样。看到 READYTOUSE=false 且停在 Waiting for a snapshot ... to be created by the CSI driver，先对比 kubectl get pv <pv> -o jsonpath='{.spec.csi.driver}' 和快照类的 DRIVER 列。

不写类名时，控制器会去找默认快照类，这里一个都没有，所以失败；默认类的用法放到后面 Retain 一节之后再做。

external-snapshotter 从 v8.0 起，VolumeSnapshot 和 VolumeSnapshotContent 的校验改由 CRD 里的 CEL 规则完成，校验 webhook 被弃用（v8.0 中它只剩「每个驱动至多一个默认类」这一项检查），到 v8.2 正式移除。CEL 规则会拦下这类请求，例如快照源不能改、两种源只能二选一：

The VolumeSnapshot "demo-snapshot" is invalid: spec.source.persistentVolumeClaimName: Invalid value: "string": persistentVolumeClaimName is immutable
The VolumeSnapshot "bad-both" is invalid: spec.source: Invalid value: "object": exactly one of volumeSnapshotContentName and persistentVolumeClaimName must be set

快照没完成时删除源 PVC

snap-wrong-driver 永远完成不了，这时删除源 PVC demo-data（先删掉挂载它的 writer）：

NAME        STATUS        VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS      VOLUMEATTRIBUTESCLASS   AGE
demo-data   Terminating   pvc-afcaf15e-2f9c-41dd-854e-0545916165a4   1Gi        RWO            csi-hostpath-sc   <unset>                 4m14s
deletionTimestamp=2026-10-13T11:47:33Z finalizers=["snapshot.storage.kubernetes.io/pvc-as-source-protection"]

PVC 被 pvc-as-source-protection finalizer 挡住，这是官方文档说的保护：正在作为快照源的 PVC，要等快照就绪或放弃后才会真正删除。

想解开时又碰到第二层：删除 snap-wrong-driver 本身也卡住了。它的 content 带着 volumesnapshotcontent-bound-protection finalizer 和 volumesnapshot-being-deleted: yes 注解，等着驱动来删后端快照，而那个驱动根本不存在。只有在确认存储上没有对应快照时（这里 snapshotHandle 从未生成），才能手工去掉 content 的 finalizer：

kubectl patch volumesnapshotcontent snapcontent-d67d1c3c-3f5b-416e-9b84-9b899e61cc62 \
  --type=merge -p '{"metadata":{"finalizers":null}}'

content 和快照随即消失，PVC 却还是 Terminating。控制器日志说明了原因：另外两个失败的快照也引用着它。

I1013 11:48:33.570658       1 snapshot_controller.go:1053] Keeping PVC notes-lab/demo-data, it is used by snapshot notes-lab/snap-no-class

删掉那两个以后 PVC 仍然没有被释放。实测给 PVC 加注解不会触发释放，给一个引用它的正常快照加注解，它就立刻被处理了；推测控制器不监听 PVC 事件，只在处理快照时顺带检查 PVC 的 finalizer：

kubectl -n notes-lab annotate vs demo-snapshot notes-lab.io/poke=1
I1013 11:49:42.304409       1 snapshot_controller.go:1058] isPVCBeingUsed: no snapshot is being created from PVC notes-lab/demo-data
I1013 11:49:42.304411       1 snapshot_controller.go:1086] checkandRemovePVCFinalizer[demo-snapshot]: Remove Finalizer for PVC demo-data as it is not used by snapshots in creation
I1013 11:49:42.312355       1 snapshot_controller.go:1025] Removed protection finalizer from persistent volume claim demo-data

snapshot-controller 的 --resync-period 默认 15 分钟，推测不做任何操作，等一次全量重新同步后也会释放，这次没有等到验证。结论是：PVC 卡在 Terminating 时，先查有没有未就绪的快照（包括早就失败、被遗忘的）在引用它。

源 PVC 删了，快照还能用

源 PVC 删除后，按 Delete 回收策略，PV 和源卷目录 4fa86f46-... 都没了，但 demo-snapshot 仍是 true，.snap 文件还在。从它再恢复一个 after-source-gone，再用 gone-check Pod 执行 cat /data/marker.txt：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: after-source-gone
  namespace: notes-lab
spec:
  storageClassName: csi-hostpath-sc
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
  dataSource:
    name: demo-snapshot
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
NAME                STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS      VOLUMEATTRIBUTESCLASS   AGE
after-source-gone   Bound    pvc-c27be4db-56b8-46a4-8f2f-eab9e1403f91   1Gi        RWO            csi-hostpath-sc   <unset>                 11s
before-snapshot 11:43:43

快照的生命周期独立于源卷，删除源卷不会连带删除快照。这在 hostpath 上成立；有些存储系统要求快照存在时源卷不能删，以驱动文档为准。

控制器中途停掉

这一组实际是在上面的恢复和删源 PVC 之后做的，这时 demo-data 已经删掉，所以快照源用的是恢复出来的 restored-data：

apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: noctrl-snap
  namespace: notes-lab
spec:
  volumeSnapshotClassName: csi-hostpath-snapclass
  source:
    persistentVolumeClaimName: restored-data
kubectl -n kube-system scale deploy snapshot-controller --replicas=0
kubectl -n notes-lab apply -f noctrl-snap.yaml        # 11:50:29
kubectl -n kube-system scale deploy snapshot-controller --replicas=2   # 11:50:59

11:50:29 提交 noctrl-snap，30 秒后它照样是 status=[]、Events: <none>；11:50:59 恢复成 2 副本，11:51:21 它变成了 readyToUse=true。控制器缺席期间提交的对象不会丢，控制器回来后会补做。

deletionPolicy：Delete 和 Retain

删除 VolumeSnapshot 时，content 和后端快照的去留由 deletionPolicy 决定（快照类里设置，复制到 content 上）。

Delete：删掉 noctrl-snap 后，它的 content 立即消失，/csi-data-dir 下对应 67691036-... 的文件数为 0。

Retain：新建一个 deletionPolicy: Retain 的类 hostpath-retain，用它给 restored-data 做快照 retain-snap：

apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: hostpath-retain
driver: hostpath.csi.k8s.io
deletionPolicy: Retain
---
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: retain-snap
  namespace: notes-lab
spec:
  volumeSnapshotClassName: hostpath-retain
  source:
    persistentVolumeClaimName: restored-data

就绪后删掉快照：

$ kubectl -n notes-lab delete vs retain-snap
volumesnapshot.snapshot.storage.k8s.io "retain-snap" deleted
$ kubectl get vsc snapcontent-dfb5bbd2-1783-405b-8632-5e2bb2b4c174
NAME                                               READYTOUSE   RESTORESIZE   DELETIONPOLICY   DRIVER                VOLUMESNAPSHOTCLASS   VOLUMESNAPSHOT   VOLUMESNAPSHOTNAMESPACE   AGE
snapcontent-dfb5bbd2-1783-405b-8632-5e2bb2b4c174   true         1073741824    Retain           hostpath.csi.k8s.io   hostpath-retain       retain-snap      notes-lab                 14s
-rw-r--r-- 1 root root 52437189 Oct 13 11:51 /csi-data-dir/7a1a52d1-c6fc-11f1-9524-5a4bc721600a.snap

content 和后端文件都留着。再手工删 content，后端文件依然在：

volumesnapshotcontent.snapshot.storage.k8s.io "snapcontent-dfb5bbd2-1783-405b-8632-5e2bb2b4c174" deleted
-rw-r--r-- 1 root root 52437189 Oct 13 11:51 /csi-data-dir/7a1a52d1-c6fc-11f1-9524-5a4bc721600a.snap

到这一步，Kubernetes 里已经没有任何对象指向这份快照，但它仍在占用存储，在云上还会持续计费。Retain 适合「快照对象删了，数据还得留」的场景，代价是要自己管理这些孤儿快照。

只要记得 snapshotHandle，可以把它重新导入集群，即预置（pre-provisioned）快照，content 和快照互相引用：

apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotContent
metadata:
  name: imported-content
spec:
  deletionPolicy: Delete
  driver: hostpath.csi.k8s.io
  source:
    snapshotHandle: 7a1a52d1-c6fc-11f1-9524-5a4bc721600a
  sourceVolumeMode: Filesystem
  volumeSnapshotRef:
    name: imported-snap
    namespace: notes-lab
---
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: imported-snap
  namespace: notes-lab
spec:
  source:
    volumeSnapshotContentName: imported-content
NAME            READYTOUSE   SOURCEPVC   SOURCESNAPSHOTCONTENT   RESTORESIZE   SNAPSHOTCLASS   SNAPSHOTCONTENT    CREATIONTIME   AGE
imported-snap   true                     imported-content        1Gi                           imported-content   29s            1s

导入时把 deletionPolicy 写成了 Delete，所以删除 imported-snap 后，content 和 7a1a52d1-...snap 文件都被清理掉了。

默认快照类

前面 snap-no-class 失败是因为没有默认类。控制器会找带 snapshot.storage.kubernetes.io/is-default-class: "true" 注解、驱动与 PVC 一致的快照类。11:52 给 csi-hostpath-snapclass 加上注解，不写类名的快照 default-snap（源 PVC 为 restored-data）就自动用上了它：

kubectl annotate volumesnapshotclass csi-hostpath-snapclass snapshot.storage.kubernetes.io/is-default-class=true

紧接着把同一驱动的 hostpath-retain 也标成默认，再提交一个不写类名的 default-snap2：

kubectl annotate volumesnapshotclass hostpath-retain snapshot.storage.kubernetes.io/is-default-class=true
Warning  SetDefaultSnapshotClassFailed  8s    snapshot-controller  Failed to set default snapshot class with error 2 default snapshot classes were found

同一个驱动有两个默认类，控制器不知道该用哪个，直接失败。做完要把注解去掉（实验时我是直接删掉了整个集群，下面两条命令没有实际执行）：

kubectl annotate volumesnapshotclass csi-hostpath-snapclass snapshot.storage.kubernetes.io/is-default-class-
kubectl annotate volumesnapshotclass hostpath-retain snapshot.storage.kubernetes.io/is-default-class-

快照不等于备份

把这次看到的几点放在一起：

  • hostpath 的快照和源卷在同一块磁盘上，磁盘或节点坏了，两者一起丢。云盘快照可能存到别处，但仍在同一个存储系统、同一个账号下，误删账号资源或区域故障时不一定能幸免。
  • 快照只包含卷里的数据。Deployment、Service、Secret 这些对象不在里面，恢复后还要有办法重建它们。
  • 快照最多做到崩溃一致，而且要以驱动能原子截取为前提（hostpath 这种逐文件打包的连这一点都做不到），应用一致要靠应用自己配合。
  • Retain 留下的孤儿快照、驱动不匹配卡住的 content，都不会自己报警。

快照适合在升级、迁移、批量改数据前留一个快速回退点，恢复也快。灾难恢复仍然需要跨故障域的备份：导出到另一个存储系统，并定期真正做一次恢复演练。

清理

共享集群上只做了第一节的检查，删除 notes-lab 即可，里面的 demo-data PVC 和 writer Pod 会随之删掉：

kubectl delete namespace notes-lab

如果是在一个长期使用的集群上做了后面这些快照实验，要按下面的顺序清理，因为快照类和 content 是集群级对象，删命名空间带不走：

kubectl -n notes-lab delete pod reader inuse-check gone-check --ignore-not-found
kubectl -n notes-lab delete pvc --all
kubectl -n notes-lab delete volumesnapshot --all
kubectl get volumesnapshotcontent        # 确认 Retain 策略没有留下孤儿 content
kubectl delete volumesnapshotclass wrong-driver-class hostpath-retain
kubectl delete namespace notes-lab notes-lab-other

先删使用恢复卷的 Pod，再删 PVC，最后删快照。删快照前先看一眼类的 deletionPolicy，避免以为删干净了，后端其实还留着。这次用的是一次性集群，不用逐个清理，直接整个删掉：

kind delete cluster --name notes-lab-snap --kubeconfig ./notes-lab-snap.kubeconfig

PVC 本身的用法见 PVC 实验。
