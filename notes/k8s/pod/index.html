Pod：容器的运行单元

Pod 是 Kubernetes 可调度的最小单元。一个 Pod 可以包含多个容器，它们共享网络命名空间，同一 Pod 内的容器可以通过 localhost 互相访问；文件则不共享，需要显式挂载同一个卷。日常业务一般交给 Deployment 管理 Pod，这一篇先直接创建单个 Pod，把它的生命周期和常见状态看清楚。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），实验放在单独的 notes-lab namespace 里。为便于阅读，节点名简化成了 worker、worker2，Pod IP 用 <pod-ip> 代替。

创建并观察

保存为 pod.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: web-pod
  labels:
    app: web-pod
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80
      resources:
        requests:
          cpu: 50m
          memory: 64Mi
        limits:
          memory: 128Mi
kubectl create namespace notes-lab
kubectl -n notes-lab apply -f pod.yaml
kubectl -n notes-lab get pod web-pod -o wide

第一次提交就碰到一个小插曲：

Error from server (Forbidden): pods "web-pod" is forbidden: error looking up service account notes-lab/default: serviceaccount "default" not found

namespace 刚创建时，它的 default ServiceAccount 由控制器异步补上，中间有一个很短的空窗。手工操作几乎碰不到，但脚本里「建 namespace 后立刻 apply」就会撞上。稳妥的做法是先等 ServiceAccount 出现：

until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done

ContainerCreating 不一定是在拉镜像

重新提交后，Pod 在 ContainerCreating 停了好几分钟。看事件：

kubectl -n notes-lab describe pod web-pod
Events:
  Type    Reason     Age    From               Message
  ----    ------     ----   ----               -------
  Normal  Scheduled  4m30s  default-scheduler  Successfully assigned notes-lab/web-pod to worker2
  Normal  Pulling    3m6s   kubelet            Pulling image "nginx:1.27"
  Normal  Pulled     20s    kubelet            Successfully pulled image "nginx:1.27" in 2m45.663s (2m45.663s including waiting). Image size: 72406859 bytes.
  Normal  Created    16s    kubelet            Created container nginx
  Normal  Started    15s    kubelet            Started container nginx

describe 里的 Age 是相对时间，不好算间隔。换成带绝对时间的事件列表：

kubectl -n notes-lab get events --field-selector involvedObject.name=web-pod \
  --sort-by=.lastTimestamp -o custom-columns=TIME:.lastTimestamp,REASON:.reason
TIME                   REASON
2026-10-12T03:25:39Z   Scheduled
2026-10-12T03:27:03Z   Pulling
2026-10-12T03:29:49Z   Pulled
2026-10-12T03:29:53Z   Created
2026-10-12T03:29:54Z   Started

这几分钟分成了两段：

  • 调度到开始拉镜像，隔了 84 秒。拉镜像之前，kubelet 要先通过 CRI 让 containerd 创建 Pod 沙箱（pause 容器加网络命名空间），containerd 再调用 CNI 插件分配 IP、配置网卡。查节点上 containerd 的日志，RunPodSandbox 03:25:40 开始，03:27:03 才返回；其中 Calico 在 03:25:45 开始分配 IP，到 03:27:02 才写完 endpoint，绝大部分时间耗在这一步。为什么这么慢这次没有直接测到，推测和集群刚重启两分钟有关：Calico 要通过 API Server 读写数据，而控制平面还在恢复。
  • 拉镜像用了 2 分 45 秒。Pulled 消息里的 including waiting 和总耗时相同，说明没有在排队等其他镜像，时间基本都花在下载这 72 MB 上。

所以看到 ContainerCreating 时，先看 Events 停在哪一步。停在 Scheduled 之后、还没出现 Pulling，多半卡在沙箱、网络或卷挂载阶段，留意有没有 FailedCreatePodSandBox、FailedMount 事件，没有的话再去看节点上的 containerd 和 CNI 日志；停在 Pulling，才是镜像本身慢。

端口转发

kubectl -n notes-lab port-forward pod/web-pod 8080:80
Forwarding from 127.0.0.1:8080 -> 80
Forwarding from [::1]:8080 -> 80

另开一个终端执行 curl http://localhost:8080，能看到 Nginx 的欢迎页。Forwarding from 这一行表示本地端口已经开始监听，到 Pod 的连接要等第一个请求进来才建立。第一次测试时，转发放到后台 3 秒后还没打印这一行，curl 直接连接失败；后来再测，209 毫秒就打印出来了。脚本里不要用固定的 sleep，应该等这一行出现再继续。端口转发只用于本地调试，不是生产入口。

三种常见的异常状态

故意制造三种故障，看每种状态下 Kubernetes 给出的信息。

镜像拉不下来：ErrImagePull → ImagePullBackOff

kubectl -n notes-lab run bad-image --image=nginx:1.27-typo --restart=Never
kubectl -n notes-lab describe pod bad-image
Normal   Pulling    27s (x3 over 67s)  kubelet  Pulling image "nginx:1.27-typo"
Warning  Failed     25s (x3 over 66s)  kubelet  Failed to pull image "nginx:1.27-typo": rpc error: code = NotFound desc = failed to pull and unpack image "docker.io/library/nginx:1.27-typo": failed to resolve reference "docker.io/library/nginx:1.27-typo": docker.io/library/nginx:1.27-typo: not found
Warning  Failed     25s (x3 over 66s)  kubelet  Error: ErrImagePull
Normal   BackOff    14s (x3 over 65s)  kubelet  Back-off pulling image "nginx:1.27-typo"
Warning  Failed     14s (x3 over 65s)  kubelet  Error: ImagePullBackOff

ErrImagePull 是单次拉取失败，ImagePullBackOff 是 kubelet 在两次重试之间退避等待，两者会交替出现。真正有用的是 Failed to pull image 那一行里的错误：仓库存在、标签不存在时，报的是这里的 NotFound。如果把仓库名写错，比如 nginxx-typo-repo:1.27，报错就变成了：

failed to resolve reference "docker.io/library/nginxx-typo-repo:1.27": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed

Docker Hub 对不存在的仓库和无权访问的私有仓库给出同一种回复，所以看到 pull access denied 时，先逐字核对镜像名，确认无误再去查 imagePullSecrets。如果报的是超时，那就是网络问题。

容器反复退出：CrashLoopBackOff

用 busybox 模拟一个启动就因为找不到配置文件而退出的程序：

apiVersion: v1
kind: Pod
metadata:
  name: crash-pod
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo loading config; echo 'config /etc/app.conf not found' >&2; exit 1"]

一分多钟后：

NAME        READY   STATUS             RESTARTS      AGE
crash-pod   0/1     CrashLoopBackOff   2 (31s ago)   76s

describe 里最有价值的是 Last State，它记录了上一次退出的原因和退出码：

Last State:     Terminated
  Reason:       Error
  Exit Code:    1
  Started:      Mon, 12 Oct 2026 11:31:27 +0800
  Finished:     Mon, 12 Oct 2026 11:31:27 +0800
Restart Count:  2

Started 和 Finished 是同一秒，说明程序刚启动就退出了，问题出在启动阶段，比如配置、参数、依赖或权限，而不是运行到一半才出错。退出码 1 是程序自己返回的；如果看到 137 并且 Reason 是 OOMKilled，那是超出内存 limit 被杀了。

另外，STATUS 列不是 Pod 的 phase。容器反复崩溃期间，STATUS 在 Error 和 CrashLoopBackOff 之间来回切换，但 phase 一直是 Running：

$ kubectl -n notes-lab get pod crash-pod -o jsonpath='{.status.phase}'
Running

看日志时，logs 和 logs --previous 的区别取决于容器当前的状态。为了分清每次运行，把命令改成先打印启动时间、活 8 秒再退出：

command: ["sh", "-c", "echo \"start $(date +%T)\"; sleep 8; echo 'config /etc/app.conf not found' >&2; exit 1"]

容器正在退避等待时，两条命令返回的都是最近一次退出的那个实例：

$ kubectl -n notes-lab logs crash-pod
start 03:38:48
config /etc/app.conf not found
$ kubectl -n notes-lab logs crash-pod --previous
start 03:38:48
config /etc/app.conf not found

容器重新跑起来、还没崩溃时，两者就分开了：不带参数看到的是当前实例（03:39:24 启动，还没走到报错那一步），--previous 看到的是上一个：

$ kubectl -n notes-lab logs crash-pod
start 03:39:24
$ kubectl -n notes-lab logs crash-pod --previous
start 03:38:48
config /etc/app.conf not found

所以排查崩溃原因，一律用 --previous，不用管当前碰巧处在哪个阶段。容器还没重启过时没有上一个实例，这条命令会报 previous terminated container ... not found。

状态字段里还能看到当前的退避时间：

{"waiting":{"message":"back-off 20s restarting failed container=app ...","reason":"CrashLoopBackOff"}}

退避从 10 秒开始，每次翻倍，最长 5 分钟；容器正常运行满 10 分钟后，退避计时清零。

Running 但不 Ready

给 nginx 配一个它不提供的就绪探针路径：

readinessProbe:
  httpGet:
    path: /healthz
    port: 80
  periodSeconds: 5
NAME        READY   STATUS    RESTARTS   AGE
not-ready   0/1     Running   0          31s
Warning  Unhealthy  24s (x2 over 25s)  kubelet  Readiness probe failed: Get "http://<pod-ip>:80/healthz": dial tcp <pod-ip>:80: connect: connection refused
Warning  Unhealthy  5s (x5 over 23s)   kubelet  Readiness probe failed: HTTP probe failed with statuscode: 404

按官方定义，phase 为 Running 表示 Pod 已经绑定到节点、所有容器都已创建，并且至少有一个容器正在运行、启动或重启。它并不代表能接流量。给这个 Pod 打上标签 app=not-ready，再创建一个同名 Service（kubectl create service 默认按 app=<名称> 选择 Pod），然后看 EndpointSlice：

kubectl -n notes-lab label pod not-ready app=not-ready
kubectl -n notes-lab create service clusterip not-ready --tcp=80:80
kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=not-ready \
  -o jsonpath='{range .items[*].endpoints[*]}{.targetRef.name} ready={.conditions.ready}{"\n"}{end}'
not-ready ready=false

Pod 被登记进来了，但标记为 ready=false；在旧的 Endpoints 对象里，它出现在 notReadyAddresses，而不是 addresses。Service 不会把流量转给它。

两种失败信息的含义也不一样：最初两次是 connection refused，nginx 还没开始监听，启动头一两秒出现这种情况是正常的，就绪探针失败也不会重启容器，不用处理；之后变成 404，端口通了，但路径不对，这是探针配置本身写错了。如果 connection refused 一直不消失，就该检查探针端口和应用的监听地址。探针的细节见探针与资源管理。

同一 Pod 里的两个容器

验证开头那句「共享网络、不共享文件」：

apiVersion: v1
kind: Pod
metadata:
  name: two-containers
spec:
  containers:
    - name: web
      image: nginx:alpine
    - name: probe
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]
kubectl -n notes-lab exec two-containers -c probe -- wget -qO- http://localhost:80
kubectl -n notes-lab exec two-containers -c probe -- ls /usr/share/nginx/html
kubectl -n notes-lab exec two-containers -c web -- hostname
kubectl -n notes-lab exec two-containers -c probe -- hostname
<title>Welcome to nginx!</title>
ls: /usr/share/nginx/html: No such file or directory
two-containers
two-containers

probe 容器通过 localhost:80 访问到了 web 容器里的 nginx，说明两者共享同一个网络命名空间；也正因为如此，同一 Pod 内的两个容器不能监听同一个端口。两个容器的 hostname 都是 Pod 名，这是另一件事：Pod 内的容器还共享 UTS 命名空间。

但 probe 看不到 nginx 镜像里的网页目录，每个容器的根文件系统仍然来自各自的镜像。要共享文件，需要在两个容器里挂载同一个卷，见 emptyDir。

清理

kubectl -n notes-lab delete pod web-pod
kubectl -n notes-lab get pod web-pod
# Error from server (NotFound): pods "web-pod" not found

kubectl delete namespace notes-lab

直接创建的 Pod 删除后就没了，没有任何控制器会重建它，节点故障时也一样。下一篇用 Deployment 维护副本；初始化容器和终止流程见 Pod 生命周期。
