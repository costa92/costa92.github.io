从最外层的症状往里查

单个对象的排查，前面几篇分别讲过：探针、Service、Ingress、调度、DNS。真实故障往往不是一个错误，而是几个错误叠在一起，修好一个，症状只是换了个样子。这一篇把它们串起来：部署一个应用，故意在不同层埋下错误，然后只从用户能看到的症状出发，按「Ingress → Service → Pod → 容器」的顺序一层层往里查，查到底再回到外层确认。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），Ingress 控制器是 Traefik v3.7.9，IngressClass 名为 traefik。实验放在单独的 notes-lab namespace 里。节点名简化成 worker、worker2，Pod IP、ClusterIP 和负载均衡地址分别用 <pod-ip>、<cluster-ip>、<lb-ip> 代替。

动手之前先确认 kubectl 指向的是哪个集群，排查错环境比任何故障都浪费时间：

kubectl config current-context
kubectl get nodes

埋了错误的应用

应用用 traefik/whoami，它把收到的请求原样回显，回显内容里带 Pod 名，便于确认流量落到了哪里。保存为 app-broken.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop
spec:
  replicas: 2
  selector:
    matchLabels:
      app: shop
  template:
    metadata:
      labels:
        app: shop
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.10.2-typo
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 8080
            periodSeconds: 5
          resources:
            requests:
              cpu: 50m
              memory: 64Gi
            limits:
              memory: 64Gi
---
apiVersion: v1
kind: Service
metadata:
  name: shop
spec:
  selector:
    app: shpo
  ports:
    - port: 80
      targetPort: 8080
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
spec:
  ingressClassName: traefik
  rules:
    - host: troubleshoot.notes-lab.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: shop-svc
                port:
                  number: 80

里面有六处错误：镜像标签不存在、内存请求 64Gi、就绪探针端口写成 8080、Service 选择器拼成 shpo、Service 的 targetPort 写成 8080、Ingress 指向不存在的 shop-svc。先不看答案，假装这是别人交给你的清单。

kubectl create namespace notes-lab
kubectl -n notes-lab apply -f app-broken.yaml
deployment.apps/shop created
service/shop created
ingress.networking.k8s.io/shop created

API Server 全部接受，一个警告都没有。这些字段在语法上都合法：引用一个不存在的 Service、选择一个没有 Pod 的标签、请求一个没有节点能满足的内存量，都不会在提交时被拒绝。错误只会在后面运行时一层层暴露出来。

集群外访问 Ingress，这里用端口转发连到 Traefik 的 Service，再用 Host 头指定域名，省得改 hosts：

kubectl -n traefik port-forward svc/traefik 18080:80 &
curl -i -H "Host: troubleshoot.notes-lab.local" http://127.0.0.1:18080/

第一层：Ingress，404

HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Mon, 12 Oct 2026 08:33:31 GMT
Content-Length: 19

404 page not found

这个 404 本身几乎不提供信息。换一个根本没有配置过的域名再请求一次：

$ curl -s -i -H "Host: no-such-host.notes-lab.local" http://127.0.0.1:18080/
HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Mon, 12 Oct 2026 08:33:35 GMT
Content-Length: 19

404 page not found

一模一样。对 Traefik 来说，「这条 Ingress 规则因为后端有问题没能生效」和「压根没有这个域名的规则」在客户端看来没有区别，都是没匹配到路由。所以拿到 404 时，不能从响应里判断问题在哪，得去看 Ingress 对象：

kubectl -n notes-lab get ingress shop
kubectl -n notes-lab describe ingress shop
NAME   CLASS     HOSTS                          ADDRESS      PORTS   AGE
shop   traefik   troubleshoot.notes-lab.local   <lb-ip>      80      11s
Rules:
  Host                          Path  Backends
  ----                          ----  --------
  troubleshoot.notes-lab.local  
                                /   shop-svc:80 (<error: endpoints "shop-svc" not found>)
Annotations:                    <none>
Events:                         <none>

两点值得注意。第一，ADDRESS 已经有值，这只说明控制器认领了这条 Ingress 并回写了状态，不代表路由能用。第二，Events 是空的，Traefik 不会把这类错误写成 Kubernetes 事件。真正指出问题的是 Backends 那一列：shop-svc 的 endpoints 找不到。控制器自己的日志说得更直白：

2026-10-12T08:33:29Z ERR Cannot create service error="service not found" ingress=shop namespace=notes-lab providerName=kubernetes serviceName=shop-svc servicePort=&ServiceBackendPort{Name:,Number:80,}

修正后端名：

kubectl -n notes-lab patch ingress shop --type=json \
  -p='[{"op":"replace","path":"/spec/rules/0/http/paths/0/backend/service/name","value":"shop"}]'

后端端口写错，describe 不会告诉你

顺带试了另一种 Ingress 错误：Service 名对了，端口写成 Service 上并不存在的 8080（这一步是在全部修好之后单独做的）。客户端同样是 404 page not found，但 describe 的输出看起来完全正常，后面还列出了两个 Pod 地址：

Rules:
  Host                          Path  Backends
  ----                          ----  --------
  troubleshoot.notes-lab.local  
                                /   shop:8080 (<pod-ip-1>:80,<pod-ip-2>:80)
Annotations:                    <none>

kubectl 按端口号去 Service 上找端口名，找不到也不报错，会退回未命名端口；本例 Service 端口没命名，所以照样列出了地址。这种情况只有控制器日志能看出来：

2026-10-12T08:39:02Z ERR Cannot create service error="service port not found" ingress=shop namespace=notes-lab providerName=kubernetes serviceName=shop servicePort=&ServiceBackendPort{Name:,Number:8080,}

所以 Ingress 返回 404 而 describe 又挑不出毛病时，下一步就是看 Ingress 控制器的日志，按 namespace 和 Ingress 名过滤。更多 Ingress 本身的规则见 Ingress。

第二层：Service，503

修正后端名后再请求：

HTTP/1.1 503 Service Unavailable
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Mon, 12 Oct 2026 08:33:49 GMT
Content-Length: 20

no available server

状态码变了，说明请求已经越过 Ingress 规则，到了「找后端」这一步。describe ingress 里后端的括号也从错误变成了 <none>：

/   shop:80 (<none>)

这里有个与控制器配置相关的细节：这个集群的 Traefik 开了 --providers.kubernetesingress.allowEmptyServices=true。按 Traefik 文档，这个选项允许为没有可用 endpoint 的 Service 建路由，请求到达后返回 503；它默认是 false；文档只写了开启后返回 503，没写关闭时的响应。默认配置下同样的场景会是什么响应，这次没有测，换一个控制器（比如 ingress-nginx）文案和状态码也可能不同。不要死记某个状态码对应某个原因，用它判断「请求走到了哪一层」就够了。

no available server 指向 Service 没有可用后端：

kubectl -n notes-lab describe svc shop
Selector:          app=shpo
Type:              ClusterIP
IP Family Policy:  SingleStack
IP Families:       IPv4
IP:                <cluster-ip>
IPs:               <cluster-ip>
Port:              <unset>  80/TCP
TargetPort:        8080/TCP
Endpoints:         <none>
Session Affinity:  None
Events:            <none>

Endpoints: <none> 有两种可能：选择器选不中任何 Pod，或者选中了但没有一个 Ready。把选择器和 Pod 标签摆在一起比：

$ kubectl -n notes-lab get pods --show-labels
NAME                   READY   STATUS    RESTARTS   AGE   LABELS
shop-7d966c5d8-2pc9c   0/1     Pending   0          29s   app=shop,pod-template-hash=7d966c5d8
shop-7d966c5d8-hb6hk   0/1     Pending   0          29s   app=shop,pod-template-hash=7d966c5d8
$ kubectl -n notes-lab get pods -l app=shpo
No resources found in notes-lab namespace.

用 Service 的选择器原样去查 Pod，查不到，就是选择器的问题。这一步同样没有任何事件。修正：

kubectl -n notes-lab patch svc shop -p '{"spec":{"selector":{"app":"shop"}}}'
Selector:          app=shop
Endpoints:         <none>

选择器对了，Endpoints 还是空，curl 依旧 503。这时候问题已经不在 Service：两个 Pod 都是 Pending，连 IP 都没有，自然进不了 endpoints。往里走一层。

第三层：Pod Pending

kubectl -n notes-lab describe pod -l app=shop
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  40s   default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient memory. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

这条消息按节点逐一交代了排除原因：控制平面节点有污点，Pod 不容忍；两个 worker 内存不够。后半句是抢占的评估结果：即便驱逐低优先级 Pod 也腾不出 64Gi。对照节点的可分配量：

$ kubectl get nodes -o custom-columns=NAME:.metadata.name,MEM:.status.allocatable.memory,CPU:.status.allocatable.cpu
NAME            MEM          CPU
control-plane   64329524Ki   28
worker          64329524Ki   28
worker2         64329524Ki   28

64329524Ki 约合 61.3Gi，比请求的 64Gi 小，没有任何节点能放下。调度器比较的是 requests 和节点的可分配量减去已有 Pod 的请求总和，与节点实际用了多少内存无关。调度规则的细节见调度。把资源改回合理的值：

kubectl -n notes-lab set resources deploy/shop -c whoami \
  --requests=cpu=50m,memory=64Mi --limits=memory=128Mi

修了配置，旧 Pod 却没走

25 秒后再看：

NAME                    READY   STATUS             RESTARTS   AGE   IP          NODE      NOMINATED NODE   READINESS GATES
shop-6b45866445-tzk2s   0/1     ImagePullBackOff   0          25s   <pod-ip>    worker2   <none>           <none>
shop-7d966c5d8-2pc9c    0/1     Pending            0          72s   <none>      <none>    <none>           <none>
shop-7d966c5d8-hb6hk    0/1     Pending            0          72s   <none>      <none>    <none>           <none>
NAME              DESIRED   CURRENT   READY   AGE
shop-6b45866445   1         1         0       25s
shop-7d966c5d8    2         2         0       72s

两个 Pending 的旧 Pod 还在，新 ReplicaSet 只起了一个 Pod。这是滚动更新的默认策略在起作用：

$ kubectl -n notes-lab get deploy shop -o jsonpath='{.spec.strategy}'
{"rollingUpdate":{"maxSurge":"25%","maxUnavailable":"25%"},"type":"RollingUpdate"}

按 Deployment 文档，maxSurge 的百分比向上取整，maxUnavailable 向下取整。2 个副本时，maxSurge 是 1，maxUnavailable 是 0：总数最多 3 个 Pod，可用的 Pod 至少要有 2 个。旧 Pod 本来就不可用，为什么不先删掉？Deployment 控制器其实会优先清理不可用的旧 Pod，但能删几个有上限：Pod 总数减去最少可用数，再减去新 ReplicaSet 里还没可用的 Pod 数。这时是 3 - 2 - 1 = 0，一个都不能删。新 Pod 卡住，滚动更新也就卡住：

$ kubectl -n notes-lab rollout status deploy/shop --timeout=10s
Waiting for deployment "shop" rollout to finish: 1 out of 2 new replicas have been updated...
error: timed out waiting for the condition

修了一处，看到的却是新旧两版 Pod 混在一起、各坏各的。这时用 pod-template-hash 标签分开看，只关心最新那个 ReplicaSet 的 Pod。滚动更新本身见 Deployment。

第四层：ImagePullBackOff

kubectl -n notes-lab describe pod -l pod-template-hash=6b45866445
Events:
  Type     Reason     Age                From               Message
  ----     ------     ----               ----               -------
  Normal   Scheduled  40s                default-scheduler  Successfully assigned notes-lab/shop-6b45866445-tzk2s to worker2
  Normal   Pulling    22s (x2 over 37s)  kubelet            Pulling image "traefik/whoami:v1.10.2-typo"
  Warning  Failed     18s (x2 over 35s)  kubelet            Failed to pull image "traefik/whoami:v1.10.2-typo": rpc error: code = NotFound desc = failed to pull and unpack image "docker.io/traefik/whoami:v1.10.2-typo": failed to resolve reference "docker.io/traefik/whoami:v1.10.2-typo": docker.io/traefik/whoami:v1.10.2-typo: not found
  Warning  Failed     18s (x2 over 35s)  kubelet            Error: ErrImagePull
  Normal   BackOff    4s (x2 over 34s)   kubelet            Back-off pulling image "traefik/whoami:v1.10.2-typo"
  Warning  Failed     4s (x2 over 34s)   kubelet            Error: ImagePullBackOff

NotFound 说明仓库存在而标签不存在；仓库名写错、私有仓库没配 imagePullSecrets 时报的是另一种错误，见 Pod 与容器。

这个阶段有一个容易看走眼的地方。Pod 调度成功后拿到了 IP，这时看 EndpointSlice：

$ kubectl -n notes-lab get endpointslice -o wide
NAME         ADDRESSTYPE   PORTS   ENDPOINTS         AGE
shop-kr9v2   IPv4          8080    <pod-ip>          87s

ENDPOINTS 列有地址了，看上去后端已经就位。但 curl 仍然是 503。把每个 endpoint 的就绪状态打出来：

$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=shop \
    -o jsonpath='{range .items[*].endpoints[*]}{.targetRef.name} {.addresses[0]} ready={.conditions.ready}{"\n"}{end}'
shop-6b45866445-tzk2s <pod-ip> ready=false

kubectl get endpointslice 的默认列会列出未就绪的地址，只有 conditions.ready 才说明能不能接流量。describe svc 的 Endpoints 行只显示就绪地址，这时是空的。判断后端是否可用，看后两者，不要看前者。

修正镜像标签：

kubectl -n notes-lab set image deploy/shop whoami=traefik/whoami:v1.10.2

第五层：Running 但 0/1

30 秒后，ReplicaSet 变成了三个：

NAME                    READY   STATUS             RESTARTS   AGE    IP         NODE      NOMINATED NODE   READINESS GATES
shop-6b45866445-tzk2s   0/1     ImagePullBackOff   0          79s    <pod-ip>   worker2   <none>           <none>
shop-7d966c5d8-hb6hk    0/1     Pending            0          2m6s   <none>     <none>    <none>           <none>
shop-d6498f8bb-8v6jx    0/1     Running            0          30s    <pod-ip>   worker    <none>           <none>
NAME              DESIRED   CURRENT   READY   AGE
shop-6b45866445   1         1         0       79s
shop-7d966c5d8    1         1         0       2m6s
shop-d6498f8bb    1         1         0       31s

三个版本各一个 Pod，而且都不 Ready。注意最早那个 ReplicaSet shop-7d966c5d8 从 2 变成了 1：这次没有任何 Pod 变成 Ready，一个 Pending 的旧 Pod 照样被删了。还是上面那个上限：改镜像后又创建了新的 ReplicaSet，刚创建时它的副本数是 0，没有未可用的 Pod，上限变成 3 - 2 - 0 = 1，于是控制器先删掉一个不可用的旧 Pod，再把新 ReplicaSet 扩到 1。

最新的那个 Pod 已经 Running，问题换成了就绪探针：

Normal   Started    31s               kubelet            Started container whoami
Warning  Unhealthy  4s (x8 over 31s)  kubelet            Readiness probe failed: Get "http://<pod-ip>:8080/": dial tcp <pod-ip>:8080: connect: connection refused

connection refused 持续了 8 次没有消失，说明不是启动慢，而是那个端口上就没有进程在听。容器到底在听哪个端口，最直接的证据是它自己的日志：

$ kubectl -n notes-lab logs -l pod-template-hash=d6498f8bb
2026/10/12 08:35:04 Starting up on port 80

应用在 80 上，探针打 8080。就绪探针失败不会重启容器，RESTARTS 一直是 0，所以这种错误不会以 CrashLoopBackOff 的形式引起注意，Pod 只是安静地停在 0/1。如果写错的是存活探针，容器就会被反复重启。探针的语义见探针与资源管理。

kubectl -n notes-lab patch deploy shop --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/port","value":80}]'
kubectl -n notes-lab rollout status deploy/shop --timeout=90s
Waiting for deployment "shop" rollout to finish: 0 out of 2 new replicas have been updated...
Waiting for deployment "shop" rollout to finish: 1 out of 2 new replicas have been updated...
Waiting for deployment "shop" rollout to finish: 1 old replicas are pending termination...
deployment "shop" successfully rolled out

新 Pod 一 Ready，滚动更新就能推进，三个旧版本的 Pod 也随之被清掉。

回到外层：502

Pod 层全部正常了，回到最外面重新请求：

HTTP/1.1 502 Bad Gateway
Date: Mon, 12 Oct 2026 08:36:36 GMT
Content-Length: 11

Bad Gateway

又换了一个状态码。502 表示代理找到了后端，但连上去失败了。EndpointSlice 这次两个地址都是 ready=true，问题出在 describe svc 的这两行：

TargetPort:        8080/TCP
Endpoints:         <pod-ip-1>:8080,<pod-ip-2>:8080

Endpoints 列出的是「Pod IP:targetPort」，而容器声明的端口是 80：

$ kubectl -n notes-lab get pod -l app=shop -o jsonpath='{.items[0].spec.containers[0].ports}'
[{"containerPort":80,"protocol":"TCP"}]

就绪探针改对了，探针直接打 Pod 的 80，所以 Pod 是 Ready 的；Service 的 targetPort 是另一个字段，不会跟着变。两处端口互不校验，一个对一个错时就是这个样子：endpoints 完全就绪，流量却进不去。

Traefik 的访问日志里还有个细节：这次请求的 "ServiceURL":"http://<pod-ip-1>:8080"、"OriginStatus":502。Traefik 是直接连 Pod IP 的，并不经过 Service 的 ClusterIP。也就是说，在默认配置下（没有开启 nativeLB，nativeLBByDefault 为 false），这条链路上 kube-proxy 不参与，Service 只是 Traefik 用来查 endpoints 的索引。从集群内部用一个临时 Pod 分别访问 Service 和 Pod 的 80 端口，可以把问题钉死在 targetPort 上：

$ kubectl -n notes-lab run tmp-curl --rm -i --restart=Never --image=curlimages/curl:latest -- \
    sh -c 'curl -sS -m 3 http://shop/ ; echo; curl -sS -m 3 http://<pod-ip-2>:80/ | head -3'
curl: (7) Failed to connect to shop:80 after 0 ms: Could not connect to server

Hostname: shop-85ddcd7dd6-mx58d
IP: 127.0.0.1
IP: ::1

走 Service 连不上，直连 Pod 的 80 正常。修正 targetPort：

kubectl -n notes-lab patch svc shop --type=json \
  -p='[{"op":"replace","path":"/spec/ports/0/targetPort","value":80}]'

这里碰到一个没能解释的现象。第一次改 targetPort 是 08:37:46。3 秒后（08:37:49）用 describe svc 看，Endpoints 行还是 :8080；8 秒后（08:37:54）同时看 EndpointSlice 和 Endpoints，端口都还是 8080，curl 仍然 502；13 秒后（08:37:59）两者才都变成 80：

为了量清楚，又把 targetPort 来回改了一次。用一个小循环：记下 patch 的时间，然后每 0.5 秒读一次 EndpointSlice 的端口、顺便 curl 一次，端口变成目标值就停：

want=80   # 目标 targetPort：先设 8080 跑一次，再设 80 跑一次
echo "patch targetPort=$want at $(date -u +%T.%3N)"
kubectl -n notes-lab patch svc shop --type=json \
  -p="[{\"op\":\"replace\",\"path\":\"/spec/ports/0/targetPort\",\"value\":$want}]"
for i in $(seq 1 60); do
  p=$(kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=shop -o jsonpath='{.items[0].ports[0].port}')
  c=$(curl -s -o /dev/null -w "%{http_code}" -H "Host: troubleshoot.notes-lab.local" http://127.0.0.1:18080/)
  echo "$(date -u +%T.%3N) slicePort=$p http=$c"
  [ "$p" = "$want" ] && break; sleep 0.5
done

先改成 8080、再改回 80，这次都在 1 秒内生效：

patch targetPort=8080 at 08:38:46.271
service/shop patched
08:38:46.364 slicePort=8080 http=502
patch targetPort=80 at 08:38:51.376
service/shop patched
08:38:52.240 slicePort=80 http=200

第一次那 8 到 13 秒的延迟没能复现，原因没有测到。Endpoints 和 EndpointSlice 是两个控制器分别维护的，却同时滞后，推测是 kube-controller-manager 当时整体处理延迟，而不是某一个控制器的问题。实际的启示是：改完 Service 后，先确认 EndpointSlice 的端口已经变了，再去判断修复有没有生效，不然可能把一次正确的修复误判成无效。EndpointSlice 一更新，Traefik 那边几乎同时就恢复了 200。

症状 → 第一条命令

下表只收这次实际观察到的情况：

看到的症状第一条命令看什么
Ingress 返回 404kubectl describe ingress <名称>Backends 列有没有 <error: ...>；看着正常就查控制器日志里的 ERR
Ingress 返回 503（本例 Traefik 文案 no available server）kubectl describe svc <名称>Endpoints 是否为空；为空再用 Service 的 Selector 原样 get pods -l
Ingress 返回 502kubectl describe svc <名称>Endpoints 里的端口和容器实际监听的端口是否一致
Endpoints 为空但选择器能选中 Podkubectl get pods -o widePod 是 Pending、ImagePullBackOff 还是 Running 0/1
Pendingkubectl describe podFailedScheduling 消息里逐类节点的排除原因
ImagePullBackOffkubectl describe podFailed to pull image 那行：not found 是标签不存在；其他报错见 Pod 与容器
Running 但 0/1kubectl describe pod + kubectl logsReadiness probe failed 的具体错误；日志里应用实际监听的端口
修了配置，旧 Pod 还在kubectl get rs是否有多个 ReplicaSet 并存、新 RS 的 Pod 是否 Ready
get endpointslice 有地址，流量仍不通get endpointslice -o jsonpath=...conditions.ready地址是 ready=false 还是 true

规律是：外层的状态码只用来判断请求走到了哪一层，原因要到那一层的对象上去找；每修一处，回到最外层重新请求一次，看症状是否变成了下一层的样子。
