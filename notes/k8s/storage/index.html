把数据留在 Pod 生命周期之外

容器可写层随容器消失；emptyDir 与 Pod 同寿命。需要在 Pod 重建后保留数据时，由 PersistentVolumeClaim（PVC）申请存储，再挂载到 Pod。PersistentVolume（PV）代表实际的一块存储；StorageClass 决定 PV 怎么被动态创建出来。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18），实验放在单独的 notes-lab namespace。节点名简化成 control-plane、worker、worker2，Pod IP 用 <pod-ip> 代替。集群唯一的 StorageClass 是 kind 自带的 standard：

NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
standard (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  60d

它是 local-path-provisioner（镜像 kindest/local-path-provisioner:v20241108-5c6d2daf），所谓「卷」就是某个节点上的一个目录。这决定了下面很多现象，换成云盘或 NFS 结果会不一样，文中会分开说。StorageClass 本身的字段（类名怎么写、绑定时机、回收策略、扩容开关）放在后半部分，见先把现有的类读清楚。

PVC 先停在 Pending

只申请 16Mi，不写 storageClassName：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: demo-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 16Mi
kubectl -n notes-lab apply -f pvc.yaml
kubectl -n notes-lab get pvc demo-data
kubectl -n notes-lab describe pvc demo-data

20 秒后：

NAME        STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
demo-data   Pending                                      standard       <unset>                 22s
Events:
  Type    Reason                Age                From                         Message
  ----    ------                ----               ----                         -------
  Normal  WaitForFirstConsumer  15s (x2 over 28s)  persistentvolume-controller  waiting for first consumer to be created before binding

两点值得看：

  • STORAGECLASS 列已经是 standard，清单里并没写。这是 DefaultStorageClass 准入插件在创建时补上的，补上之后就固定了。
  • Pending 是正常状态，事件 WaitForFirstConsumer 写得很清楚：没有 Pod 用它之前，不创建卷。此时集群里也没有对应的 PV。

为什么要等？local-path 的卷只存在于某一个节点上。如果先建卷再调度，卷可能落在 Pod 去不了的节点上。等调度器替 Pod 选好节点，再在那台节点上建目录，两者自然一致。看到 Pending 的 PVC 先看事件，是这条就不用处理。官方文档还提醒，这个模式下不要用 nodeName 指定节点，nodeName 会绕过调度器，调度器不写 selected-node 注解，PVC 就会一直 Pending；要固定节点，用 kubernetes.io/hostname 的 nodeSelector。

第一个 Pod 触发供给

apiVersion: v1
kind: Pod
metadata:
  name: writer
spec:
  containers:
    - name: c
      image: busybox:1.36
      command: ["sh", "-c", "test -f /data/marker || echo \"written by $(hostname) at $(date +%T)\" > /data/marker; cat /data/marker; sleep 3600"]
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: demo-data

Pod 06:57:02 提交，06:57:56 Ready，用了 54 秒。按时间排的事件（节点名已简化）：

2026-10-12T06:57:43Z   demo-data   ProvisioningSucceeded   rancher.io/local-path_local-path-provisioner-ccc7bf7fc-wqgh2_a0a2aa4e-3df1-4092-a742-0e9fc599938f   Successfully provisioned volume pvc-21f71a43-f04b-4841-8b27-d655e68e0ba5

顺序是：调度器选中 worker2，把节点名写进 PVC 的注解 volume.kubernetes.io/selected-node，供给器看到注解才开始干活（06:57:05），38 秒后 PV 建好，PVC 绑定，kubelet 才能挂载、启动容器。镜像早就在节点上，54 秒几乎都花在了建卷上。

建一个目录要 38 秒，是因为 local-path 不在自己的进程里建目录，而是往目标节点派一个 helper Pod 去执行 mkdir。供给器日志：

time="2026-10-12T06:57:05Z" level=info msg="create the helper pod helper-pod-create-pvc-21f71a43-f04b-4841-8b27-d655e68e0ba5 into local-path-storage" 
time="2026-10-12T06:57:41Z" level=info msg="Volume pvc-21f71a43-f04b-4841-8b27-d655e68e0ba5 has been created on worker2:/var/local-path-provisioner/pvc-21f71a43-f04b-4841-8b27-d655e68e0ba5_notes-lab_demo-data"

local-path-storage namespace 的事件显示 helper Pod 06:57:26 才启动，比创建晚了 21 秒。这段时间里没有沙箱相关的事件可看，推测是在等沙箱和网络就绪，没有直接测到。也就是说，用 local-path 时，每个新 PVC 的首次启动都要多付一个 Pod 的启动开销；集群忙的时候这段会更长。ExternalProvisioning 那条事件里「please verify that the provisioner is running」的提示，在供给慢的时候也会出现，不代表供给器坏了，要以后面有没有 ProvisioningSucceeded 或 ProvisioningFailed 为准。

再看自动生成的 PV（只保留 spec）：

spec:
  accessModes:
  - ReadWriteOnce
  capacity:
    storage: 16Mi
  claimRef:
    apiVersion: v1
    kind: PersistentVolumeClaim
    name: demo-data
    namespace: notes-lab
    resourceVersion: "10932784"
    uid: 21f71a43-f04b-4841-8b27-d655e68e0ba5
  hostPath:
    path: /var/local-path-provisioner/pvc-21f71a43-f04b-4841-8b27-d655e68e0ba5_notes-lab_demo-data
    type: DirectoryOrCreate
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values:
          - worker2
  persistentVolumeReclaimPolicy: Delete
  storageClassName: standard
  volumeMode: Filesystem
  • PV 名 pvc-<uid> 里的 uid 就是 PVC 的 uid，claimRef 反向指回 PVC，两边一一对应。
  • hostPath 是 worker2 上的目录，nodeAffinity 要求用它的 Pod 必须在 worker2。后面访问模式一节会碰到这个约束的后果。
  • persistentVolumeReclaimPolicy: Delete 从 StorageClass 继承而来，决定 PVC 删除后 PV 的去向。

PVC 上还多了一个 finalizer：

["kubernetes.io/pvc-protection"]

它在删除那一节会起作用。

删除 Pod，数据还在

kubectl -n notes-lab exec writer -- cat /data/marker
kubectl -n notes-lab delete pod writer
kubectl -n notes-lab apply -f writer.yaml
kubectl -n notes-lab exec writer -- cat /data/marker
written by writer at 06:57:56

重建的 Pod 06:59:20 才提交，读到的仍是 06:57:56 第一次写的内容，test -f 发现文件已存在，没有覆盖。新 Pod 也回到了 worker2，这是 PV 的 nodeAffinity 决定的，不是巧合。直接到节点上看，就是一个普通文件：

docker exec <worker2 的节点容器> cat /var/local-path-provisioner/pvc-21f71a43-..._notes-lab_demo-data/marker
written by writer at 06:57:56

插一句：kubectl delete pod writer 用了 57 秒才返回（06:58:23 到 06:59:20）。容器的 PID 1 是 sh，推测它没有处理 SIGTERM，kubelet 只能等 30 秒的默认宽限期结束再强杀；多出来的 27 秒原因没有确认。这和存储无关，原因和改法见优雅终止；后面的实验删 Pod 时都加了 --grace-period=1。

16Mi 只是申请，不是上限

在 Pod 里看挂载点的大小：

kubectl -n notes-lab exec writer -- df -h /data
Filesystem                Size      Used Available Use% Mounted on
/dev/sda                915.8G    729.5G    139.7G  84% /data

显示的是整块宿主机磁盘。往 16Mi 的卷里写 64M：

kubectl -n notes-lab exec writer -- dd if=/dev/zero of=/data/big bs=1M count=64
kubectl -n notes-lab exec writer -- du -sh /data
kubectl -n notes-lab get pvc demo-data -o jsonpath='{.status.capacity.storage}'
64+0 records in
64+0 records out
67108864 bytes (64.0MB) copied, 0.443900 seconds, 144.2MB/s
64.0M	/data
16Mi

写入成功，PVC 仍然报告容量 16Mi。local-path 的卷只是一个目录，没有任何配额机制，requests.storage 只用来匹配和记账。一个 Pod 写满了卷，其实是写满了节点磁盘，会连带同节点上的其他 Pod 和 kubelet 本身。

Kubernetes 本身不保证容量被强制执行，官方文档对绑定的说法是「至少得到申请的大小，可能更大」。云盘类的 CSI 驱动通常会真的创建一块对应大小的盘（不足云厂商最小规格时会向上取整，比如 1Gi），写满就是 No space left on device；本地目录类的存储则要另想办法（比如有项目配额的文件系统）。本文只测了 local-path。

访问模式

ReadWriteOnce 不等于只能一个 Pod

writer 还在运行时，再起一个挂同一 PVC 的 reader，不指定节点，它往 marker 里追加一行：

NAME     READY   STATUS    RESTARTS   AGE   IP          NODE      NOMINATED NODE   READINESS GATES
reader   1/1     Running   0          16s   <pod-ip>    worker2   <none>           <none>
writer   1/1     Running   0          61s   <pod-ip>    worker2   <none>           <none>
written by writer at 06:57:56
reader reader was here

reader 的命令是 echo "reader $(hostname) was here" >> /data/marker; sleep 3600。两个 Pod 同时读写同一个 RWO 卷，没有任何报错。官方定义里 ReadWriteOnce 约束的是节点：卷只能被一个节点以读写方式挂载，同一节点上的多个 Pod 都可以用。两个进程同时写同一个文件，要靠应用自己协调。

那跨节点呢？给第三个 Pod 加上 nodeSelector: kubernetes.io/hostname: worker：

NAME                READY   STATUS    RESTARTS   AGE   IP       NODE     NOMINATED NODE   READINESS GATES
reader-other-node   0/1     Pending   0          10s   <none>   <none>   <none>           <none>
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  12s   default-scheduler  0/3 nodes are available: 1 node(s) didn't match Pod's node affinity/selector. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

它在调度阶段就被挡住了，挡它的是 PV 的 nodeAffinity，不是访问模式，卷根本没机会被第二个节点挂载。所以在 local-path 上测不出 RWO 对跨节点挂载的限制；用网络存储才能看到 attach 阶段的冲突，这一点本文没有实测。这条报错只提 nodeSelector，不提卷，3 个节点也只解释了 1 个。推测这是 v1.31.0 调度器 VolumeBinding 插件 v1.27 起引入的一个优化（v1.31.0 仍在）造成的：它在 PreFilter 阶段先按 PV 的 nodeAffinity 把候选节点缩成 worker2，worker2 又不满足 nodeSelector，报错里就只剩这一条；依据见 StatefulSet 一篇。这个优化后来被撤回（回移到 v1.31.3），新版本上的报错应该会逐个节点给出原因，本文只在 v1.31.0 上看过。排查时看到带 PVC 的 Pod 报 didn't match Pod's node affinity/selector，要把 PV 的 nodeAffinity 也拿出来对一下。

ReadWriteOncePod：调度器认，供给器不认

要求「整个集群只允许一个 Pod」时用 ReadWriteOncePod。把访问模式换掉，新建 solo-data，先后起两个 Pod solo-a、solo-b：

NAME     READY   STATUS    RESTARTS   AGE     IP                NODE                         NOMINATED NODE   READINESS GATES
solo-a   0/1     Pending   0          2m31s   <none>            <none>                       <none>           <none>
solo-b   0/1     Pending   0          16s     <none>            <none>                       <none>           <none>

两个都没起来，原因各不相同。solo-b 的事件：

Warning  FailedScheduling  15s   default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node has pod using PersistentVolumeClaim with the same name and ReadWriteOncePod access mode. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

调度器知道 solo-a 已经占了这个 RWOP 卷（尽管 solo-a 自己还没跑起来），直接拒绝 solo-b。RWOP 的限制在调度阶段就生效。

solo-a 的问题在卷本身。它的 describe 里 Events 是 <none>，status 里只有 phase，连 PodScheduled 条件都没有：

{"phase":"Pending","qosClass":"Burstable"}

原因要去 PVC 上找：

Warning  ProvisioningFailed    100s (x3 over 2m25s)  rancher.io/local-path_local-path-provisioner-ccc7bf7fc-wqgh2_a0a2aa4e-3df1-4092-a742-0e9fc599938f  failed to provision volume with StorageClass "standard": Only support ReadWriteOnce access mode

这个版本的 local-path 只接受 ReadWriteOnce。调度器已经为 solo-a 选了节点（PVC 注解 selected-node 是 worker），然后停在等卷建好的那一步；卷永远建不出来，Pod 就一直挂着，13 分钟后依然如此，Pod 上始终没有事件。正常情况下，调度器的 VolumeBinding 插件等卷绑定最多 600 秒（bindTimeoutSeconds 默认值），超时后会给 Pod 记一条 FailedScheduling 再重新调度。这次没看到，推测和实验期间 kube-scheduler 至少重启过两次有关（07:04 前后和 07:07 前后，这个集群的控制平面本来就不稳定）：重启会清掉调度器内存里的状态，600 秒重新计时。

后来控制平面平稳时（kube-scheduler 没再重启）重做了一遍，只起 solo-a。07:23:43 提交，07:33:44 Pod 上终于出现了一条事件，正好 600 秒：

2026-10-12T07:33:44.113892Z   solo-a      running PreBind plugin "VolumeBinding": binding volumes: context deadline exceeded

这条信息只说超时，不说为什么，原因仍然要去 PVC 的 ProvisioningFailed 里找。这是一个很容易漏看的场景：Pod Pending 却没有事件时，去看它引用的 PVC 的事件。官方文档也说明 RWOP 只支持 CSI 卷，local-path 不是 CSI 驱动。

故障一：StorageClass 名字写错

把 storageClassName 写成一个不存在的 fast-ssd：

NAME        STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
typo-data   Pending                                      fast-ssd       <unset>                 19s
Events:        <none>

和正常的 WaitForFirstConsumer 相比，外表都是 Pending，区别在事件：这里一开始什么都没有。再起一个使用它的 Pod，30 多秒后调度器先报错：

0/3 nodes are available: pod has unbound immediate PersistentVolumeClaims. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

immediate 这个词有误导性。调度器判断是否延迟绑定时，StorageClass 不存在就返回「不延迟」，于是把这个 PVC 当成 Immediate 模式，要求它先绑定好才能调度，报「有未绑定的 Immediate 模式 PVC」。PVC 上的事件直到 07:05:43 才出现，距创建（07:04:07）一分半：

2026-10-12T07:05:43Z   typo-data           ProvisioningFailed      storageclass.storage.k8s.io "fast-ssd" not found

这条才说出了真正的原因。PV 控制器默认 15 秒重新同步一次，解释不了 96 秒的延迟；推测是因为 kube-controller-manager 恰好在 07:04:29 重启，要重新选主、同步缓存之后才处理这个 PVC。所以 PVC 刚创建、事件为空时，先用 kubectl get storageclass 核对名字，不要干等。

想直接改成正确的类名是不行的：

kubectl -n notes-lab patch pvc typo-data -p '{"spec":{"storageClassName":"standard"}}'
The PersistentVolumeClaim "typo-data" is invalid: spec: Forbidden: spec is immutable after creation except resources.requests and volumeAttributesClassName for bound claims

PVC 的 spec 创建后基本不可改，只能删掉重建。如果 PVC 由 StatefulSet 的 volumeClaimTemplates 生成，模板本身也不能改（v1.31 中这个字段不可变）。做法是 kubectl delete sts <名称> --cascade=orphan 只删 StatefulSet、保留 Pod，再用新模板重建 StatefulSet；已经存在的同名 PVC 不会被替换，用错的 PVC 要先删掉，新模板才会对它生效，见 StatefulSet。

故障二：删除仍在使用的 PVC

writer 还在运行时删除 demo-data：

kubectl -n notes-lab delete pvc demo-data --wait=false
kubectl -n notes-lab get pvc demo-data
NAME        STATUS        VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
demo-data   Terminating   pvc-21f71a43-f04b-4841-8b27-d655e68e0ba5   16Mi       RWO            standard       <unset>                 12m
2026-10-12T07:08:42Z ["kubernetes.io/pvc-protection"]
NAME     READY   STATUS    RESTARTS   AGE
writer   1/1     Running   0          9m38s
written by writer at 06:57:56
reader reader was here

delete 立刻返回了 deleted，但 PVC 只是打上了 deletionTimestamp，因为 pvc-protection finalizer 还在，对象不会真正消失。writer 照常运行，数据照常可读。不加 --wait=false 的话，kubectl delete 默认会等到 finalizer 去掉才返回，看起来像命令挂了。

这时再起一个用它的新 Pod，会被调度器拒绝：

0/3 nodes are available: persistentvolumeclaim "demo-data" is being deleted. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

这是 Deployment 滚动更新时可能碰到的情况：有人删了 PVC，老 Pod 还在跑，一切正常；直到老 Pod 被替换，新 Pod 起不来。看到 is being deleted，去查谁删了 PVC。在 finalizer 去掉之前，PVC 救不回来，deletionTimestamp 不能撤销；能做的是先把数据从仍在运行的 Pod 里拷出来。

删掉最后一个使用它的 Pod：

07:09:26
pod "writer" deleted
07:09:40
pvc gone 07:09:42
pv gone 07:10:27
host dir removed

Pod 07:09:40 删完，PVC 2 秒内消失。由于回收策略是 Delete，供给器随即删除 PV 和节点上的目录，又是通过一个 helper Pod，用了 45 秒。最后 worker2 的 /var/local-path-provisioner/ 下已经没有这个目录，数据彻底没了。

还有一个和文档字面不一致的观察。官方说明里「有 Pod 对象在使用该 PVC」就算 in active use；但在上一节，typo-pod 一直 Pending、没被调度到任何节点，删除 typo-data 后约 40 秒内 PVC 就没了，并没有被它挡住。调度器的事件依次是：

0/3 nodes are available: pod has unbound immediate PersistentVolumeClaims. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.
0/3 nodes are available: persistentvolumeclaim "typo-data" is being deleted. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.
0/3 nodes are available: persistentvolumeclaim "typo-data" not found. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

这和源码一致：pvc_protection_controller.go 的 podUsesPVC 只检查 spec.nodeName 不为空的 Pod。注释给的理由是 kubelet 只会看到已调度的 Pod，而且不会启动引用了带 deletionTimestamp 的 PVC 的 Pod，所以未调度的 Pod 不会再用到这个卷。

回收策略：Delete 与 Retain

上面已经看到 Delete 的效果：PVC 一删，PV 和数据一起没。动态供给的 PV 默认继承 StorageClass 的 Delete，对数据库这类数据，常见的做法是在 PV 上改成 Retain。PV 是集群级对象，下面的操作需要相应权限：

PV=$(kubectl -n notes-lab get pvc keep-data -o jsonpath='{.spec.volumeName}')
kubectl patch pv $PV -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'

keep-data 是新建的 PVC，由 Pod keeper 写入 written by keeper at 07:11:39。删掉 Pod 和 PVC 后：

NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM                         STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pvc-db992e6c-00c0-47de-92ad-7db37c62dbfc   16Mi       RWO            Retain           Released   notes-lab/keep-data   standard       <unset>                          56s

PV 留下了，状态 Released，CLAIM 列还记着原来的 PVC。节点上的数据也在（这次卷在 worker 上）：

written by keeper at 07:11:39

但同名 PVC 重建后不会自动拿回它。用同一份清单重新创建 keep-data 和 keeper：

written by keeper at 07:12:51
NAME        STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
keep-data   Bound    pvc-27d88013-8923-4427-9d69-2fdead8b42ba   16Mi       RWO            standard       <unset>                 29s
pvc-27d88013-8923-4427-9d69-2fdead8b42ba   16Mi       RWO            Delete           Bound      notes-lab/keep-data   standard       <unset>                          9s
pvc-db992e6c-00c0-47de-92ad-7db37c62dbfc   16Mi       RWO            Retain           Released   notes-lab/keep-data   standard       <unset>                          86s

新 PVC 拿到了一块新卷，marker 是新写的 07:12:51，Pod 看到的是空目录。旧 PV 的 claimRef 里记的是旧 PVC 的 uid（db992e6c-...），新 PVC 的 uid 是 27d88013-...，名字相同也不算同一个。如果没注意到这一点，会以为「数据丢了」，其实旧数据还躺在另一个 PV 里。

要挂回旧数据，用 volumeName 指定那个 PV：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: restore-data
spec:
  volumeName: pvc-db992e6c-00c0-47de-92ad-7db37c62dbfc
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 16Mi

直接提交还不行：

Warning  FailedBinding  10s (x2 over 11s)  persistentvolume-controller  volume "pvc-db992e6c-00c0-47de-92ad-7db37c62dbfc" already bound to a different claim.

Released 的 PV 仍被旧 claimRef 占着。这里的做法是直接去掉 claimRef，PV 变为 Available：

kubectl patch pv pvc-db992e6c-00c0-47de-92ad-7db37c62dbfc --type=json \
  -p '[{"op":"remove","path":"/spec/claimRef"}]'
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pvc-db992e6c-00c0-47de-92ad-7db37c62dbfc   16Mi       RWO            Retain           Available           standard       <unset>                          2m28s

约 20 秒内，restore-data 变成 Bound。挂载它的 Pod 叫 restorer，读到的却是 keeper 当初写的内容，并且自动落在 worker：

NAME       READY   STATUS    RESTARTS   AGE   IP          NODE     NOMINATED NODE   READINESS GATES
restorer   1/1     Running   0          32s   <pod-ip>    worker   <none>           <none>
written by keeper at 07:11:39

去掉 claimRef 有个风险：Available 的 PV 会被任何匹配的 PVC 拿走，不一定是你的 restore-data。更稳妥的是把 claimRef 直接改成新 PVC 的名字和 namespace（不写 uid），PV 就只预留给它：

kubectl patch pv <pv-name> --type=merge \
  -p '{"spec":{"claimRef":{"name":"restore-data","namespace":"notes-lab","uid":null,"resourceVersion":null}}}'

这条命令本文没有实测。官方文档给的手工回收步骤是删除 PV、清理数据、按同样的存储定义新建 PV，前提都是先确认旧数据就是你想要的。Retain 的代价是必须有人来收尾：PV 不会自己消失，local-path 的目录也一直占着节点磁盘。实验最后把这个 PV 改回 Delete 再删 PVC，供给器同样清掉了节点上的目录。

StorageClass：先把现有的类读清楚

前面一直在用集群自带的 standard，下面换个角度，只看 StorageClass 本身：PVC 里的类名怎么写、类上的 volumeBindingMode、reclaimPolicy、allowVolumeExpansion 各自在什么时候起作用，以及哪些行为其实是供给器决定的，而不是 Kubernetes。

这部分是另一次运行（2026-10-13），环境同上。StorageClass 是集群级对象，集群自带的 standard 只读不改；需要改字段的实验，另建了一个名为 notes-lab-storageclass-retain 的类（实验对象都以 notes-lab- 开头，便于清理），用完删掉。

kubectl get storageclass
kubectl get storageclass standard -o yaml
NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
standard (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  60d
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
  name: standard
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer

（省略了 last-applied-configuration 等元数据。）几个值得注意的地方：

  • (default) 来自注解 storageclass.kubernetes.io/is-default-class: "true"，不是某个 spec 字段。官方文档说，如果有多个类都带这个注解，不写类名的 PVC 会用最新创建的那个。允许多个默认类只是为了迁移时平滑过渡，平时应该只留一个。
  • YAML 里根本没有 allowVolumeExpansion，kubectl get 显示成 false。字段缺省就是不允许扩容。
  • provisioner: rancher.io/local-path 只是一个名字。Kubernetes 不会校验它，谁监听这个名字，谁来建卷。所以从别的集群抄来的 StorageClass，provisioner 名字对不上时，PVC 只会一直等。

local-path 供给器的具体行为由 local-path-storage namespace 里的一个 ConfigMap 决定：

kubectl -n local-path-storage get configmap local-path-config -o yaml
data:
  config.json: |-
    {
            "nodePathMap":[
            {
                    "node":"DEFAULT_PATH_FOR_NON_LISTED_NODES",
                    "paths":["/var/local-path-provisioner"]
            }
            ]
    }
  helperPod.yaml: |-
    apiVersion: v1
    kind: Pod
    metadata:
      name: helper-pod
    spec:
      containers:
      - name: helper-pod
        image: docker.io/kindest/local-path-helper:v20230510-486859a6
        imagePullPolicy: IfNotPresent
  setup: |-
    #!/bin/sh
    set -eu
    mkdir -m 0777 -p "$VOL_DIR"
  teardown: |-
    #!/bin/sh
    set -eu
    rm -rf "$VOL_DIR"

所谓「供给一个卷」，就是派一个 helper Pod 到目标节点执行 setup 脚本，mkdir -m 0777；「删除卷」就是执行 teardown，rm -rf。后面看到的现象，大部分都能从这几行里找到原因。供给器本身的版本是 kindest/local-path-provisioner:v20241108-5c6d2daf。

PVC 里类名的三种写法

同时创建三个 PVC，只有 storageClassName 不同（保存为 pvcs.yaml）：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: no-class          # 不写 storageClassName
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 16Mi
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: empty-class
spec:
  storageClassName: ""    # 显式写空字符串
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 16Mi
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: bad-class

until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done

kubectl -n notes-lab get pvc

  • 写空字符串：明确表示「不要类」，也就关掉了动态供给。它只能绑定同样没有类的 PV，集群里没有，于是 FailedBinding。注意这个事件是 Normal 级别，不是 Warning，很容易被忽略。

（no-class 此时已经被下一节的 Pod 用上了。）PV 的匹配首先看类名是否相同："" 只配 ""，standard 只配 standard。官方示例里用 volumeName 预绑定 PV 时也会显式写 storageClassName: ""，注释是「否则会被设成默认类」，原因就在这里：不写类名，准入插件会填上默认类，再去找这个 PV 就对不上了。

让 no-class 绑定

给 no-class 起一个 Pod，不加任何节点约束（保存为 first.yaml，后面几个 Pod 都照它改名字和 claimName）：

apiVersion: v1
kind: Pod

  name: first
spec:
  terminationGracePeriodSeconds: 1
  containers:
    - name: c
      image: busybox:1.36
      command: ["sh", "-c", "echo \"$(hostname) $(date +%T)\" >> /data/log; cat /data/log; sleep 3600"]
      resources:
        requests:
          cpu: 10m

05:21:45 打上注解，6 秒后卷建好，PVC 绑定，一直 Pending 的 Pod 随后被调度到 worker。这说明卡点就在节点信息上。但这只是验证手段，不是用法：手工指定节点等于替调度器做决定，节点资源、污点都没人检查。结论：本集群这种 nodePathMap 配置的 local-path，只能用 WaitForFirstConsumer。local-path 的 README 另外提到 sharedFileSystemPath 模式（所有节点挂同一个共享文件系统），那种模式可以用 Immediate，本文没有测。官方文档对 Immediate 的说明也提到，对于不是所有节点都能访问的存储，Immediate 模式会在不了解 Pod 调度需求的情况下供给卷，可能导致 Pod 无法调度；云盘这类按可用区划分的存储也有同样的问题，只是程度轻一些（本文没有在云盘上实测）。

类的字段能不能改

kubectl patch storageclass notes-lab-storageclass-retain -p '{"reclaimPolicy":"Delete"}'
kubectl patch storageclass notes-lab-storageclass-retain -p '{"allowVolumeExpansion":false}'

storageclass.storage.k8s.io/notes-lab-storageclass-retain patched

reclaimPolicy 创建后不能改（按 API 的校验规则，provisioner、parameters、volumeBindingMode 也不可变，本文没有逐个试），allowVolumeExpansion 可以随时开关。这条实验是在第二次建这个类时做的（第一次建的类已在回收实验中删掉，见后文），类名和其余字段相同，只把绑定模式换成了 WaitForFirstConsumer。

要改不可变字段，只能删掉类再按同名重建。删除 StorageClass 时 API 没有阻拦，已经存在的 PV 和 PVC 仍然记着类名。后面回收一节会看到，在本集群的 local-path 上，类删掉之后旧 PV 的清理照样能完成；换成别的供给器是否如此，没有验证。

32Mi 16Mi
  Warning  ExternalExpanding      30s                 volume_expand                                                                                      waiting for an external controller to expand this PVC

第一列是 spec.resources.requests.storage，第二列是 status.capacity.storage。申请已经是 32Mi，实际容量仍是 16Mi，PV 的 capacity 也还是 16Mi。Kubernetes 的扩容控制器发现这个卷不归内置插件管，就留下一条 ExternalExpanding，等外部的 resizer 来处理。可是 local-path 供给器只管建和删，不提供扩容，没有任何组件会来接手。patch（05:22:22）后 69 秒再看，状态没变，这条事件仍只有一次。

StorageClass 上的 allowVolumeExpansion: true 只是一个许可，它不代表驱动真的会扩容。 这个开关是集群管理员自己填的，填错了没有任何校验。现实中更常见的是 CSI 驱动支持扩容，这时会有 external-resizer sidecar 接手，PVC 上会出现 Resizing、FileSystemResizePending 之类的条件；本文没有支持扩容的驱动，没有实测。

想撤回这次扩容请求也不行：

kubectl -n notes-lab patch pvc imm -p '{"spec":{"resources":{"requests":{"storage":"16Mi"}}}}'
The PersistentVolumeClaim "imm" is invalid: spec.resources.requests.storage: Forbidden: field can not be less than previous value

在 v1.31.0 默认配置下，requests.storage 只能往大改。官方文档描述的「扩容失败后改成比上次请求小的值重试」依赖 RecoverVolumeExpansionFailure 特性门控，它在 1.31 默认关闭；即使开启，新值也必须严格大于 status.capacity，这里 16Mi 等于当前容量，同样不满足。本文没有开启门控验证。所以这个 PVC 就带着一个永远完不成的 32Mi 申请，直到被删除。如果有监控按 requests 和 capacity 是否一致来报警，会一直报。

顺带一提，容量申请在 local-path 上本来就不起约束作用：往这个 16Mi 的卷里 dd 写入 48M 照样成功，节点上的目录占了 49M，权限是 setup 脚本给的 drwxrwxrwx，原因见上文 16Mi 只是申请，不是上限。

Retain 卷退役：谁来删节点上的目录

Delete：这次 5 秒，目录一起没

no-class 来自 standard，回收策略是 Delete。删掉 Pod 和 PVC（上文故障二那次运行里，PVC 消失后 PV 和目录用了 45 秒才删完，这次只用了 5 秒左右）：

05:23:15
persistentvolumeclaim "no-class" deleted
05:23:15
05:23:21
Error from server (NotFound): persistentvolumes "pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e" not found

供给器日志显示它又派了一个 helper Pod 去 worker2 执行 teardown：

time="2026-10-13T05:23:15Z" level=info msg="Deleting volume pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e at worker2:/var/local-path-provisioner/pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e_notes-lab_no-class" 
time="2026-10-13T05:23:15Z" level=info msg="create the helper pod helper-pod-delete-pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e into local-path-storage" 
time="2026-10-13T05:23:20Z" level=info msg="Volume pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e has been deleted on worker2:/var/local-path-provisioner/pvc-a63388ea-bd52-4c6c-90d8-88c42c458e5e_notes-lab_no-class"

删除前后各在节点上执行一次 docker exec <worker2 的节点容器> ls /var/local-path-provisioner/：删除前列出 pvc-a63388ea-..._notes-lab_no-class，删除后输出为空。顺序是先删数据，再删 PV 对象：PV 对象一消失，节点上的数据就已经没了。官方文档说，不写 reclaimPolicy 时默认就是 Delete。

Retain：PV 留下，数据留下，收尾归你

删掉 imm 的 Pod 和 PVC：

NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM           STORAGECLASS                    VOLUMEATTRIBUTESCLASS   REASON   AGE
pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424   16Mi       RWO            Retain           Released   notes-lab/imm   notes-lab-storageclass-retain   <unset>                          2m

Released 的定义是「claim 已删除，但对应的存储资源还没被集群回收」。节点 worker 上的目录还在。Released 的 PV 怎样重新挂给新 PVC，上文已经演示过，这里只看怎么收尾。有两条路，结果截然不同。

路线一：把 PV 改成 Delete，让供给器来删。 这次先把 StorageClass notes-lab-storageclass-retain 删了，故意让 PV 指向一个已不存在的类，然后：

kubectl patch pv pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424 \
  -p '{"spec":{"persistentVolumeReclaimPolicy":"Delete"}}'
I1013 05:23:56.771073       1 controller.go:1471] delete "pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424": started
time="2026-10-13T05:23:56Z" level=info msg="Deleting volume pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424 at worker:/var/local-path-provisioner/pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424_notes-lab_imm" 
time="2026-10-13T05:24:02Z" level=info msg="Volume pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424 has been deleted on worker:/var/local-path-provisioner/pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424_notes-lab_imm" 
I1013 05:24:02.791417       1 controller.go:1536] delete "pvc-ede67e26-db4e-4dcb-872a-95c6d02c8424": succeeded

改完立刻触发，6 秒后 PV 和节点目录都没了。类已经被删了，删除照样完成，这是本集群 local-path 配置下的实测结果。看上游源码，Delete 会按 PV 上记的类名选配置：ConfigMap 里没有 storageClassConfigs（本集群就是）时直接用全局配置，不读 StorageClass；配置了 storageClassConfigs 而类名不在其中时，会报 BUG: Got request for unexpected storage class。其他驱动（比如 CSI）删卷时是否需要类，本文没有测，推测各不相同。

路线二：直接删 PV 对象。 这是更符合直觉、也更容易出事的做法。重建一个同名的 Retain 类（这次用 WaitForFirstConsumer），新建 PVC keep（同 imm，只改名字）和 Pod keeper（同 first，名字改成 keeper、claimName 改成 keep）。keeper 被调度到 worker2，写入一行 keeper 05:24:54 后删掉 Pod 和 PVC，PV 变成 Released，然后：

kubectl delete pv pvc-6422019d-ba03-444d-889c-6a2a0e45a35b
05:25:05
persistentvolume "pvc-6422019d-ba03-444d-889c-6a2a0e45a35b" deleted

20 秒后到节点 worker2 上看（kind 的节点就是 Docker 容器）：

docker exec <worker2 的节点容器> ls /var/local-path-provisioner/
docker exec <worker2 的节点容器> sh -c 'cat /var/local-path-provisioner/*_notes-lab_keep/log'
pvc-6422019d-ba03-444d-889c-6a2a0e45a35b_notes-lab_keep
keeper 05:24:54

目录和数据原样留着。供给器日志里查这个卷的 ID 的删除记录：

kubectl -n local-path-storage logs deploy/local-path-provisioner --since=2m \
  | grep 6422019d-ba03-444d-889c-6a2a0e45a35b | grep -v Event | grep -i delet

grep 无输出。去掉最后一个 grep 只按 ID 计数（--since=1m），有 8 行日志，但上面的删除过滤一条都没匹配到：供给器没有执行删除。

PV 对象没了，kubectl get pv 也显示 No resources found，从 Kubernetes 里已经看不到这块数据的任何线索。这和官方文档对 Retain 手工回收的描述一致：删除 PV 后，底层存储资源依然存在，需要手工清理数据、手工删除存储资源。在 local-path 上，「手工」意味着登录节点删目录；本实验最后就是这样清掉的：

docker exec <worker2 的节点容器> rm -rf /var/local-path-provisioner/pvc-6422019d-..._notes-lab_keep

换成云盘，留下的就是一块继续计费、没人认领的盘（推测，本文没有在云上实测）。所以 Retain 卷要退役时，先决定数据还要不要：要，就先备份或挂到新 PVC；不要，就把 PV 改成 Delete，让供给器按正规流程删，而不是直接 kubectl delete pv。

排查时看哪里

PVC Pending 时，先看 kubectl describe pvc 的事件：

事件含义
WaitForFirstConsumer正常，等第一个使用它的 Pod
事件为空刚创建时可能还没处理到，先用 kubectl get storageclass 核对类名，不要干等
FailedBinding ... no storage class is set（Normal）写了 storageClassName: ""，又没有无类的 PV
ProvisioningFailed ... storageclass ... not found类名写错。PVC 上的类名不能改，要么删掉重建，要么补建同名的类
ProvisioningFailed ... Only support ReadWriteOnce access mode供给器不支持这个访问模式
ProvisioningFailed ... no node was specified节点本地存储用了 Immediate，换成 WaitForFirstConsumer 的类
ExternalProvisioning 一直重复，且既没有 Provisioning 也没有 ProvisioningFailed没人认领这个 provisioner 名字，或供给器没在运行

其他几种情况：

  • Pod Pending 但没有事件：去看它引用的 PVC 的事件。调度器在等卷时，通常要 600 秒超时后 Pod 上才会出现 FailedScheduling。
  • Pod Pending、PVC 已经 Bound：把 PV 的 nodeAffinity 和 Pod 的节点约束放在一起看。
  • is being deleted：PVC 已被删除，只是被 finalizer 留着，找出是谁删的，先抢救数据。
  • PVC 重建后数据「没了」：查有没有 Released 的旧 PV。
  • 扩容后 requests 和 capacity 一直对不上：先确认驱动是否真的支持扩容，allowVolumeExpansion 只是许可。
  • Retain 的 PV 删除前，先想好由谁清理底层数据。

另外，PVC 创建后能改的只有 resources.requests，而且只能往大改：PVC 要已经 Bound，StorageClass 还要设了 allowVolumeExpansion: true。本集群的 standard 是 false，扩容这条路走不通，报错见扩容一节。

local-path 适合实验和单机场景：卷绑死在一个节点上，容量不受限，节点没了数据就没了。它也不支持快照，备份思路见卷快照；只需要 Pod 内临时共享文件时，用 emptyDir 即可。每个副本要有自己的 PVC 时用 StatefulSet。

清理

先删 Pod，再删 PVC，最后确认没有遗留的 PV（尤其是改过 Retain 的）和实验用的 StorageClass：

kubectl -n notes-lab delete pod --all
kubectl -n notes-lab delete pvc --all
kubectl delete pv notes-lab-storageclass-static   # Retain 的静态 PV，PVC 删后停在 Released
kubectl get pv                                  # 尤其留意 Retain 的 Released PV
kubectl delete storageclass notes-lab-storageclass-retain
kubectl delete namespace notes-lab

StorageClass 那次运行结束后，kubectl get pv 为空，三个节点的 /var/local-path-provisioner/ 下都没有实验留下的目录。
