Ingress：按主机名和路径转发

Ingress 描述 HTTP(S) 路由规则：请求的 Host 和路径匹配到哪条规则，就转给哪个 Service。但单独创建 Ingress 不会接收流量，集群里必须有一个 Ingress 控制器读取这些对象，并把它们翻译成自己的路由配置。所以 Ingress 的行为有一半由 Kubernetes 规范决定，另一半取决于控制器怎么翻译。这一篇的几个实验，正好碰到了两者不一致的地方。先完成 Service 实验。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0），控制器是用 Helm 装的 Traefik v3.7.9，实验放在单独的 notes-lab namespace 里。Traefik 的 Service 是 LoadBalancer 类型，但这台机器上访问不到它的外部 IP，所以请求都发到节点的 NodePort，下文写作 <node-ip>:<nodeport>；Pod IP 用 <pod-ip> 代替。NodePort 从 Traefik 的 Service 上查：

kubectl -n traefik get svc traefik
NAME      TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)                      AGE
traefik   LoadBalancer   <cluster-ip>   <lb-ip>       80:30825/TCP,443:31471/TCP   56d

80:30825 里的 30825 就是 HTTP 入口的 NodePort，节点 IP 用 kubectl get node -o wide 查。

准备后端

两个 Deployment 都用 traefik/whoami，它会在响应里打印自己的名字，用来分辨请求落到了哪个后端：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-v1
spec:
  replicas: 1
  selector:
    matchLabels: {app: web-v1}
  template:
    metadata:
      labels: {app: web-v1}
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.10.2
          args: ["--name", "web-v1"]
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: web-v1
spec:
  selector: {app: web-v1}
  ports:
    - name: http
      port: 80
      targetPort: 80

web-v2 照抄一份，把名字都换成 web-v2。把两份内容保存为 backends.yaml：

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f backends.yaml
kubectl -n notes-lab rollout status deploy/web-v1
kubectl -n notes-lab rollout status deploy/web-v2

先看集群里有哪些 IngressClass

kubectl get ingressclass -o custom-columns=NAME:.metadata.name,CONTROLLER:.spec.controller,DEFAULT:.metadata.annotations.ingressclass\\.kubernetes\\.io/is-default-class,CREATED:.metadata.creationTimestamp
NAME                  CONTROLLER                            DEFAULT   CREATED
cloud-provider-kind   kind.sigs.k8s.io/ingress-controller   true      2026-08-14T04:44:52Z
traefik               traefik.io/ingress-controller         true      2026-08-17T02:54:35Z

这个集群有两个 IngressClass，而且都标成了默认：一个是 kind 的 cloud-provider-kind 带的，一个是 Traefik 的 Helm chart 装的。这种情况在装过多个控制器的实验集群里并不少见。

不写 ingressClassName

官方文档里有一段警告：集群中有多个默认 IngressClass 时，准入控制器会拒绝创建没有指定 ingressClassName 的 Ingress。实际试一下，不写 ingressClassName：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: no-class
spec:
  rules:
    - host: noclass.notes-lab.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-v1
                port:
                  number: 80
$ kubectl -n notes-lab apply -f noclass.yaml
ingress.networking.k8s.io/no-class created
$ kubectl -n notes-lab get ingress no-class -o jsonpath='{.spec.ingressClassName}'
traefik

没有被拒绝，字段被自动填成了 traefik。翻 DefaultIngressClass 准入插件的源码（plugin/pkg/admission/network/defaultingressclass/admission.go）：v1.24 及更早的版本遇到多个默认类会拒绝创建；从 v1.25 起（PR #110974），getDefaultClass 把所有默认类按创建时间排序，取最新的那个，创建时间相同再按名字升序。它只打一条 choosing the newest 日志，而且是 V(4) 级别，API Server 要开 -v=4 才看得到，平时完全无感。traefik 比 cloud-provider-kind 晚三天创建，所以选中了它。文档里那段警告描述的是 v1.24 及以前的行为。

这个默认值是在创建时写进对象的。之后谁再装一个控制器并标成默认，新建的 Ingress 会跟着换类，已有的不受影响。依赖「最新的默认类」很容易在某天悄悄变掉，所以清单里最好显式写上 ingressClassName。

用 --resolve 或 -H 'Host: ...' 让请求带上规则里的主机名：

curl -H 'Host: noclass.notes-lab.test' http://<node-ip>:<nodeport>/
Name: web-v1
Hostname: web-v1-5dbbf56c97-twm42
RemoteAddr: <traefik-pod-ip>:52338
GET / HTTP/1.1
Host: noclass.notes-lab.test
X-Forwarded-For: <node-ip>
X-Forwarded-Host: noclass.notes-lab.test
X-Forwarded-Proto: http
X-Forwarded-Server: traefik-64778566cf-g95kw

后端看到的 Host 还是原始主机名；RemoteAddr 是 Traefik Pod 的地址，因为连接是 Traefik 发起的。X-Forwarded-For 里也不是真正的客户端，而是节点地址：请求经 NodePort 进来时被 kube-proxy 做了 SNAT。想让后端拿到真实客户端 IP，要在 Traefik 的 Service 上设置 externalTrafficPolicy: Local 之类的配置，这里没有测。

ingressClassName 写错

把类名写成集群里不存在的 nginx，保存为 wrongclass.yaml：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: wrong-class
spec:
  ingressClassName: nginx
  rules:
    - host: wrongclass.notes-lab.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-v1
                port:
                  number: 80
$ kubectl -n notes-lab apply -f wrongclass.yaml
ingress.networking.k8s.io/wrong-class created
$ kubectl -n notes-lab get ingress wrong-class
NAME          CLASS   HOSTS                       ADDRESS   PORTS   AGE
wrong-class   nginx   wrongclass.notes-lab.test             80      5s
$ curl -H 'Host: wrongclass.notes-lab.test' http://<node-ip>:<nodeport>/
404 page not found

API Server 不检查这个 IngressClass 是否存在，照样创建成功；Traefik 只处理属于自己的类，于是直接忽略它。这时 describe 看起来一切正常，后端甚至已经解析出了 Pod 地址：

Ingress Class:    nginx
Rules:
  Host                       Path  Backends
  ----                       ----  --------
  wrongclass.notes-lab.test
                             /   web-v1:80 (<pod-ip>:80)
Events:                      <none>

Backends 那一列是 kubectl 自己去查 Service 和 Endpoints 拼出来的，和有没有控制器在处理这个 Ingress 无关。真正的线索是 ADDRESS 一直为空：Traefik 接管一个 Ingress 后，会把自己的入口地址写进 status.loadBalancer（它的日志里能看到 Updated ingress status）。没人写，就说明没有控制器认领它。

把类名改回 traefik：

kubectl -n notes-lab patch ingress wrong-class --type=merge -p '{"spec":{"ingressClassName":"traefik"}}'

patch 返回后不到 1 秒，第二次 curl 就拿到了 200，ADDRESS 也随即出现。顺带一提，这里 ADDRESS 填的是 Traefik Service 的 LoadBalancer IP，可这台机器上访问 <lb-ip> 根本连不上。ADDRESS 只表示控制器认领了这个 Ingress，不代表这个地址能访问。

pathType：规范怎么写，Traefik 怎么做

按 Kubernetes 规范，Prefix 按 / 分隔的路径段匹配：/app 能匹配 /app、/app/、/app/x，但不匹配 /application；Prefix 的 /docs/ 会忽略末尾斜杠，也能匹配 /docs。多条规则同时命中时，路径最长的优先，长度相同时 Exact 优先于 Prefix。ImplementationSpecific 交给控制器自行解释。

用一个 Ingress 把这几种情况放在一起：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: paths
spec:
  ingressClassName: traefik
  rules:
    - host: paths.notes-lab.test
      http:
        paths:
          - path: /app
            pathType: Prefix
            backend:
              service: {name: web-v1, port: {number: 80}}
          - path: /app/admin
            pathType: Exact
            backend:
              service: {name: web-v2, port: {number: 80}}
          - path: /docs/
            pathType: Prefix
            backend:
              service: {name: web-v2, port: {number: 80}}
          - path: /img
            pathType: ImplementationSpecific
            backend:
              service: {name: web-v2, port: {number: 80}}

逐个请求，打印状态码和命中的后端：

请求路径           结果               按规范应为
/app               200 web-v1
/app/x             200 web-v1
/application       200 web-v1         404（不是同一路径段）
/APP               404                路径区分大小写，符合
/app/admin         200 web-v1         web-v2（Exact 应胜出）
/app/admin/        200 web-v1         web-v1，符合
/docs              404                web-v2（Prefix 忽略末尾斜杠）
/docs/a            200 web-v2
/docsx             404
/img               200 web-v2
/imgs              200 web-v2         由控制器决定

和规范对不上的有三处。原因要看 Traefik 把这些规则翻译成了什么。Traefik 的 API 面板（--api.insecure，8080 端口）能列出所有路由，我用 port-forward 只读地查了一下：

kubectl -n traefik port-forward deploy/traefik 18080:8080
curl -s http://127.0.0.1:18080/api/http/routers

用 jq 整理成「优先级、规则、后端 Service」三列：

curl -s http://127.0.0.1:18080/api/http/routers | jq -r '.[] | "\(.priority) \(.rule) -> \(.service)"'
50 Host("paths.notes-lab.test") && Path("/app/admin") -> notes-lab-web-v2-80
50 Host("paths.notes-lab.test") && PathPrefix("/app") -> notes-lab-web-v1-80
52 Host("paths.notes-lab.test") && PathPrefix("/docs/") -> notes-lab-web-v2-80
50 Host("paths.notes-lab.test") && PathPrefix("/img") -> notes-lab-web-v2-80

这份输出是重建实验环境后重新抓的，同样的清单下 /app/admin 连续 6 次仍然全部落到 web-v1。

两件事一目了然：

  • Prefix 被翻译成了 PathPrefix，而 Traefik 的 PathPrefix 是纯字符串前缀，所以 /application 也算以 /app 开头，/docs 却不以 /docs/ 开头。Traefik 的 Kubernetes Ingress provider 有一个 strictPrefixMatching 选项，文档写明它的作用是让前缀匹配严格遵守 Ingress 规范，默认值是 false。我没有修改控制器启动参数去验证，只能照文档说开启后应符合规范。ImplementationSpecific 同样翻译成 PathPrefix，/imgs 也能命中。
  • 路由优先级默认等于规则字符串的长度。PathPrefix("/app") 和 Path("/app/admin") 恰好都是 18 个字符，整条规则都是 50，打成了平手。Traefik 文档只说明了不同 provider 之间平手时怎么处理，没说同一 provider 内平手的顺序。

平手的后果是结果不可预测。我往这个 Ingress 里再加一条 Exact 规则 /app/settings，Traefik 重新加载配置后，/app/admin 连续 8 次请求全部落到了 web-v2，而加之前的 6 次全是 web-v1。/app/admin 那两条规则一个字没动，结果却反过来了。原因我没有直接测到，推测和排序方式有关：Traefik v3.7.9 的 pkg/muxer/http/mux.go 用不稳定的 sort.Sort 给路由排序，只比较 priority 和 provider 优先级，同一 provider 内优先级相同的路由谁在前没有保证，路由表一变，顺序就可能变。

要让 Exact 稳定胜出，可以把它拆到单独的 Ingress，用 Traefik 的注解显式提高优先级：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: paths-exact
  annotations:
    traefik.ingress.kubernetes.io/router.priority: "100"
spec:
  ingressClassName: traefik
  rules:
    - host: paths.notes-lab.test
      http:
        paths:
          - path: /app/admin
            pathType: Exact
            backend:
              service: {name: web-v2, port: {number: 80}}
/app/admin   Name: web-v2
/app/admin/  Name: web-v1
/app/x       Name: web-v1

这个注解作用于整个 Ingress 生成的所有路由，所以只有需要特殊优先级的规则才单独拆出来。换控制器时，路径匹配是最容易出问题的地方，迁移前应逐条用 curl 验证，而不是只看 YAML。

主机名匹配

下面是规则部分的示意，省略了 http.paths 和后端的写法，完整格式同上一节：

rules:
  - host: "*.wild.notes-lab.test"
    # → web-v2
  - host: api.wild.notes-lab.test
    # → web-v1
  - http:            # 不写 host
      paths:
        - path: /notes-lab-nohost
          # → web-v1
Host 请求头                        路径                 结果
noclass.notes-lab.test             /                    200 web-v1
NOCLASS.Notes-Lab.TEST             /                    200 web-v1
noclass.notes-lab.test:8080        /                    200 web-v1
noclass.notes-lab.test.            /                    200 web-v1
a.wild.notes-lab.test              /                    200 web-v2
api.wild.notes-lab.test            /                    200 web-v1
a.b.wild.notes-lab.test            /                    404
wild.notes-lab.test                /                    404
whatever.example                   /notes-lab-nohost    200 web-v1
  • 主机名不区分大小写，Host 头里带端口、末尾带点都不影响匹配。
  • 通配符 *.wild.notes-lab.test 只覆盖一层 DNS 标签：a.b.wild... 和 wild... 本身都不匹配，这一点 Traefik 和规范一致。
  • api.wild... 同时匹配精确规则和通配符规则，结果走了精确规则。不过这是靠长度：精确规则 50，通配符规则 48。换一个和通配符等长的精确主机就不一样了。单独建一个 Ingress，*.wild.notes-lab.test 指向 web-v2，b.wild.notes-lab.test 指向 web-v1：
48 Host("b.wild.notes-lab.test") && PathPrefix("/") -> notes-lab-web-v1-80
48 Host("*.wild.notes-lab.test") && PathPrefix("/") -> notes-lab-web-v2-80

请求 Host: b.wild.notes-lab.test 8 次，全部落到了 web-v2，也就是通配符规则胜出。Kubernetes 文档没有规定精确主机和通配符同时命中时谁优先，大多数人会默认精确的优先，这里并不成立。原因和上面 /app/admin 的情况一样：优先级相同时，谁先被匹配取决于路由的排序，没有保证，精确主机需要靠 router.priority 注解兜底。

  • 不写 host 的规则匹配任意主机名。在共享的控制器上，这种规则配上 / 会接住所有没被别人匹配的请求，实验时我特意用了一个不会冲突的路径。

后端写错时返回什么

Ingress 能匹配到，但后端有问题，Traefik 返回的状态码各不相同。先建两个有问题的 Service，再在一个 Ingress 里放五条规则，各自制造一种错误：

apiVersion: v1
kind: Service
metadata:
  name: web-badtarget
spec:
  selector: {app: web-v1}
  ports:
    - name: http
      port: 80
      targetPort: 8080   # whoami 只监听 80
---
apiVersion: v1
kind: Service
metadata:
  name: web-empty
spec:
  selector: {app: nobody}   # 选不到任何 Pod
  ports:
    - name: http
      port: 80
      targetPort: 80
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: broken
spec:
  ingressClassName: traefik
  rules:
    - host: wrongport.notes-lab.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: {name: web-v1, port: {number: 8080}}
    - host: noservice.notes-lab.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: {name: web-v3, port: {number: 80}}
    - host: badtarget.notes-lab.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: {name: web-badtarget, port: {number: 80}}
    - host: empty.notes-lab.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: {name: web-empty, port: {number: 80}}
    - host: portname.notes-lab.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: {name: web-v1, port: {name: web}}
主机后端问题返回
wrongportService 存在，但没有 8080 这个端口404 page not found
portname按端口名 web 引用，Service 的端口名是 http404 page not found
noserviceService web-v3 不存在404 page not found
badtargetService 端口存在，targetPort: 8080，容器没在监听502 Bad Gateway
emptyService 存在，selector 选不到任何 Pod503 no available server

前三种的 404，和主机名写错、类名写错时一模一样。 原因在 Traefik 日志里：

kubectl -n traefik logs deploy/traefik | grep notes-lab
ERR Cannot create service error="service port not found" ingress=broken namespace=notes-lab serviceName=web-v1 servicePort=&ServiceBackendPort{Name:,Number:8080,}
ERR Cannot create service error="service not found" ingress=broken namespace=notes-lab serviceName=web-v3 servicePort=&ServiceBackendPort{Name:,Number:80,}
ERR Cannot create service error="service port not found" ingress=broken namespace=notes-lab serviceName=web-v1 servicePort=&ServiceBackendPort{Name:web,Number:0,}

Traefik 建不出后端，就干脆不生成这条路由，请求没有匹配到任何路由，自然是 404。这三行错误每隔几秒就会重复一次，在日志里很显眼。另外两条规则在同一个 Ingress 里照常生效，坏掉的只是这一条 path，不会连累整个 Ingress。

不看控制器日志的话，describe 也有提示，只是不太明显：

wrongport.notes-lab.test   /   web-v1:8080 ()
noservice.notes-lab.test   /   web-v3:80 (<error: endpoints "web-v3" not found>)
badtarget.notes-lab.test   /   web-badtarget:80 (<pod-ip>:8080)
empty.notes-lab.test       /   web-empty:80 (<none>)
portname.notes-lab.test    /   web-v1:web ()

括号里为空的 ()，表示 Service 上找不到这个端口；<none> 表示端口对上了，但没有就绪的 Pod。badtarget 这一行看起来完全正常，因为 Endpoints 只记录 targetPort，不会检查容器是否真的在监听。它要靠访问日志区分（集群开了 JSON 格式的访问日志）：

RequestHost                DownstreamStatus  RouterName                         ServiceAddr
wrongport.notes-lab.test   404               -                                  -
badtarget.notes-lab.test   502               notes-lab-broken-badtarget-...     <pod-ip>:8080
empty.notes-lab.test       503               notes-lab-broken-empty-...         -

RouterName 为空，说明请求根本没匹配到路由，问题出在规则或后端引用上；有路由、有 ServiceAddr、返回 502，说明 Traefik 已经连到 Pod，是 Pod 那一侧拒绝了连接。

503 这一种和控制器配置有关。这个集群的 Traefik 带了 --providers.kubernetesingress.allowEmptyServices=true，按 Traefik 文档，这个选项让没有任何可用 endpoint 的 Service 也能生成路由并返回 503，而默认值是 false。默认配置下，空 Service 也会像前三种一样直接 404，这一点我没有在这个集群上验证。

排查顺序可以归纳成：先看 kubectl get ingress 的 ADDRESS 是否为空（有没有控制器认领），再看 describe 里 Backends 的括号（端口和 endpoint），最后看控制器日志和访问日志（路由是否生成、连的是哪个地址）。

清理与后续

kubectl delete namespace notes-lab

Ingress API 已经冻结，Kubernetes 项目现在推荐用 Gateway API；Ingress 本身仍是 GA，目前没有移除计划。这一篇里路径匹配、优先级都要靠控制器的注解和启动参数来补，Gateway API 则把这些写进了规范。旧版 Ingress NGINX 控制器已停止维护，不要把它作为新集群的默认选择。需要在路由上加请求或响应处理，见 Traefik Middleware。
