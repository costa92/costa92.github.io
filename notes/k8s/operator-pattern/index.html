CRD 只定义接口，Operator 才执行动作

CRD 那一篇只看 API Server 这一侧：schema 校验、默认值、status 子资源和 generation，结论是 CRD 只负责存对象，不会替你做任何事。调谐循环看的是内置控制器怎样把实际状态拉回期望。Operator 把两者接起来：用自定义资源表达意图，再写一个控制器持续读它、操作别的对象、把结果写回 status。

光讲设计容易把草稿说成组件，所以这一篇真的写了一个能跑的控制器，但要先说清楚它是什么：一个约 110 行的 bash 脚本，用 kubectl 和 jq 每 3 秒轮询一次，从宿主机上用一个专用 ServiceAccount 的 token 访问 API Server。没有 informer 缓存、没有工作队列、没有 leader election，只用来把 Operator 的几个关键机制逐个跑出真实输出。它不是生产组件，最后一节对照 controller-runtime 列出它缺的东西。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，kubectl 客户端 v1.30.0，jq 1.8.1），实验放在单独的 namespace 里，输出中统一写成 notes-lab；API Server 地址写成 <api-server>。控制器日志用的是本地时间（UTC+8）。

接口：一个 Backup 资源

备份对象只有两个 spec 字段：要备份的 ConfigMap 名 source，以及保留几份备份 retain。没有定时表达式，每次 spec 变化就算一次「请求备份」。status 由控制器写：Ready 条件、observedGeneration、最近一次的 Job 名。CRD 的 schema、校验和 status 子资源的细节 CRD 那一篇已经测过，这里只列和控制器有关的部分：

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backups.notes-lab.io
spec:
  group: notes-lab.io
  scope: Namespaced
  names: {plural: backups, singular: backup, kind: Backup}
  versions:
    - name: v1
      served: true
      storage: true
      subresources:
        status: {}
      additionalPrinterColumns:
        - {name: Source, type: string, jsonPath: .spec.source}
        - {name: Retain, type: integer, jsonPath: .spec.retain}
        - {name: Ready, type: string, jsonPath: '.status.conditions[?(@.type=="Ready")].status'}
        - {name: Reason, type: string, jsonPath: '.status.conditions[?(@.type=="Ready")].reason'}
        - {name: Age, type: date, jsonPath: .metadata.creationTimestamp}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: [source]
              properties:
                source: {type: string, minLength: 1}
                retain: {type: integer, minimum: 1, maximum: 5, default: 2}
            status:
              type: object
              properties:
                observedGeneration: {type: integer}
                lastJob: {type: string}
                conditions:
                  type: array
                  items:
                    type: object
                    required: [type, status]
                    properties:
                      type: {type: string}
                      status: {type: string, enum: ["True", "False", "Unknown"]}
                      reason: {type: string}
                      message: {type: string}
                      observedGeneration: {type: integer}
                      lastTransitionTime: {type: string, format: date-time}

「备份」本身做得很简单：Job 把源 ConfigMap 挂成只读卷，打印文件列表和整个目录 tar 包的 md5。它没有把数据写到任何存储里，所以这个 Operator 证明的是控制逻辑，不是数据可恢复。真实的备份系统还要回答备份写到哪、怎么校验、怎么恢复，这些不是靠一个 Ready=True 能说明的。

另有一个 GC 管不到的东西，用来让 finalizer 有事可做：namespace 里一个共享的 ConfigMap backup-catalog，每个 Backup 成功后控制器在里面登记一行。它被多个 Backup 共用，不能挂 ownerReferences 给某一个，删除 Backup 时只能由控制器自己去删那一行。

一次调谐做什么

步骤控制器动作可核对的结果
删除中删目录登记项，再摘掉自己的 finalizer对象消失，目录里没有残留
首次见到先挂 finalizer，本轮结束metadata.finalizers 出现 notes-lab.io/backup-cleanup
校验依赖源 ConfigMap 不存在就写 Ready=False/SourceNotFound，不建 Job不会出现一个永远卡在挂载的 Pod
比较期望的 Job 名是 <backup>-g<generation>，不存在才创建重启、重复调谐、双实例都不会多建
报告把 Job 的 Complete/Failed 翻译成 Ready 条件，写 observedGenerationobservedGeneration == generation 表示最新 spec 已处理
清理按 generation 排序，只保留最新 retain 个 Job旧 Job 及其 Pod 被删除

权限：先设计，再证明

控制器只管一个 namespace，所以用 Role 就够了，不需要 ClusterRole。按上表逐条推出需要的动词：

apiVersion: v1
kind: ServiceAccount
metadata:
  name: backup-controller
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: backup-controller
rules:
  - apiGroups: ["notes-lab.io"]
    resources: ["backups"]
    verbs: ["get", "list", "watch", "patch"]      # patch 用于增删 finalizer
  - apiGroups: ["notes-lab.io"]
    resources: ["backups/status"]
    verbs: ["get", "patch"]                       # get 是 kubectl 客户端要的，见下文
  - apiGroups: ["batch"]
    resources: ["jobs"]
    verbs: ["get", "list", "create", "delete"]
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get"]
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["backup-catalog"]
    verbs: ["patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: backup-controller
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: backup-controller
subjects:
  - kind: ServiceAccount
    name: backup-controller

几处刻意的取舍：控制器不 update、不 create、不 delete Backup，那是用户的事；它不碰 Pod，Job 的 Pod 由 Job 控制器建、由垃圾回收删；ConfigMap 只能读，唯一能改的是 resourceNames 限定的 backup-catalog。resourceNames 对 create 不起作用（创建时还没有名字），所以目录 ConfigMap 由管理员预先建好。RBAC 本身的规则见 RBAC。

准备实验环境

以下是实验的完整准备步骤，后文所有实验都在这之上进行。把上面的 CRD 存为 backup-crd.yaml，ServiceAccount、Role 和 RoleBinding 存为 rbac.yaml，再建好源 ConfigMap、目录 ConfigMap 和第一个 Backup：

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl apply -f backup-crd.yaml
kubectl wait --for=condition=Established crd/backups.notes-lab.io --timeout=30s
kubectl -n notes-lab apply -f rbac.yaml
kubectl -n notes-lab create configmap app-config \
  --from-literal=db.url=postgres://db:5432/app --from-literal=feature.flags=a,b
kubectl -n notes-lab create configmap backup-catalog
kubectl -n notes-lab apply -f - <<'EOF'
apiVersion: notes-lab.io/v1
kind: Backup
metadata:
  name: app-config
spec:
  source: app-config
  retain: 2
EOF

控制器从宿主机运行，用 kubectl create token 签一个短期 token，拼成一个独立的 kubeconfig。<api-server> 和 ca.crt 都从你自己（管理员）的 kubeconfig 里取：API Server 地址是当前集群条目的 server 字段（kubectl cluster-info 第一行也会打印），CA 证书是同一条目里 base64 编码的 certificate-authority-data：

CLUSTER=$(kubectl config view --minify -o jsonpath='{.clusters[0].name}')
SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')   # 即 <api-server>
kubectl config view --raw --minify -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' \
  | base64 -d > ca.crt
kubectl -n notes-lab create token backup-controller --duration=2h > token
TOKEN=$(cat token)
kubectl config set-cluster lab --kubeconfig=sa.kubeconfig --server="$SERVER" \
  --certificate-authority=ca.crt --embed-certs
kubectl config set-credentials backup-controller --kubeconfig=sa.kubeconfig --token="$TOKEN"
kubectl config set-context lab --kubeconfig=sa.kubeconfig --cluster=lab \
  --user=backup-controller --namespace=notes-lab
kubectl config use-context lab --kubeconfig=sa.kubeconfig
alias sa='kubectl --kubeconfig sa.kubeconfig -n notes-lab'
$ sa auth whoami
ATTRIBUTE                                           VALUE
Username                                            system:serviceaccount:notes-lab:backup-controller
Groups                                              [system:serviceaccounts system:serviceaccounts:notes-lab system:authenticated]

坑一：can-i ... /status 查的不是子资源

最初我用的是 sa auth can-i patch backups.notes-lab.io/status。为了演示权限缺失，先从 Role 里删掉了 backups/status 那条规则，再查，结果仍然是 yes：

$ kubectl -n notes-lab patch role backup-controller --type=json -p '[{"op":"remove","path":"/rules/1"}]'
role.rbac.authorization.k8s.io/backup-controller patched
$ sa auth can-i patch backups.notes-lab.io/status
yes

can-i 的参数是 VERB TYPE[/NAME]，斜杠后面会被当成对象名，这条命令问的是「能不能 patch 一个名叫 status 的 Backup」，Role 里对 backups 有 patch，所以是 yes。查子资源必须用 --subresource：

$ sa auth can-i patch backups.notes-lab.io --subresource=status
no

configmaps/backup-catalog 那一行恰好是想查对象名，所以写法是对的。用 can-i 做权限证明时，写成斜杠形式的子资源检查会给出一个看起来令人安心、实际答非所问的 yes。

坑二：kubectl patch status 还要 get 权限

这时（Role 里还只有坑一删掉 status 规则后的状态）启动控制器，这是整组实验的第一次运行，脚本见下一节，启动方式是 NS=notes-lab KCFG=sa.kubeconfig ./controller.sh。它挂上了 finalizer、建出了 Job，写 status 时被拒绝：

18:49:35 controller started ns=notes-lab interval=3s
18:49:35 finalizer added to app-config
18:49:38 created job app-config-g1
Error from server (Forbidden): backups.notes-lab.io "app-config" is forbidden: User "system:serviceaccount:notes-lab:backup-controller" cannot get resource "backups/status" in API group "notes-lab.io" in the namespace "notes-lab"
18:49:45 catalog app-config -> job=app-config-g1 completed=2026-10-13T10:49:42Z
Error from server (Forbidden): backups.notes-lab.io "app-config" is forbidden: User "system:serviceaccount:notes-lab:backup-controller" cannot get resource "backups/status" in API group "notes-lab.io" in the namespace "notes-lab"

这是预期中的 Forbidden，但报的动词是 get，不是 patch。停掉控制器，把规则加回来、只给 patch：

$ kubectl -n notes-lab patch role backup-controller --type=json -p '[{"op":"add","path":"/rules/1","value":{"apiGroups":["notes-lab.io"],"resources":["backups/status"],"verbs":["patch"]}}]'
role.rbac.authorization.k8s.io/backup-controller patched

can-i 已经是 yes，kubectl 照样失败；-v=6 能看到原因，kubectl 在发 PATCH 之前先 GET 了一次对象：

$ sa auth can-i patch backups.notes-lab.io --subresource=status
yes
$ sa patch backup app-config --subresource=status --type=merge -p '{"status":{"lastJob":"manual-test"}}' -v=6 2>&1 | grep -E 'GET|PATCH|Error'
I1013 18:50:07.364605 2286245 round_trippers.go:553] GET https://<api-server>/apis/notes-lab.io/v1/namespaces/notes-lab/backups/app-config/status 403 Forbidden in 2 milliseconds
Error from server (Forbidden): backups.notes-lab.io "app-config" is forbidden: User "system:serviceaccount:notes-lab:backup-controller" cannot get resource "backups/status" in API group "notes-lab.io" in the namespace "notes-lab"

用同一个 token 直接发 PATCH 请求，服务端只看 patch 权限，返回 200：

$ curl -s --cacert ca.crt -H "Authorization: Bearer $TOKEN" -X PATCH \
    -H 'Content-Type: application/merge-patch+json' \
    https://<api-server>/apis/notes-lab.io/v1/namespaces/notes-lab/backups/app-config/status \
    -d '{"status":{"lastJob":"manual-test"}}' -o /dev/null -w '%{http_code}\n'
200

这次测试在 status 里留下了 lastJob: manual-test。脚本从不读 status.lastJob，第一次写 status 时就会把它覆盖，所以清不清都可以，这里清空只是为了让 status 只反映控制器自己的输出。原实验当时并没有用下面的命令清理（而是直接置空了 status，命令没有留下记录），这一段是第二轮在新 namespace 里补测的：

$ kubectl -n notes-lab patch backup app-config --subresource=status --type=merge -p '{"status":{"lastJob":"manual-test"}}'
backup.notes-lab.io/app-config patched
$ kubectl -n notes-lab get backup app-config -o jsonpath='{.status}{"\n"}'
{"lastJob":"manual-test"}
$ kubectl -n notes-lab patch backup app-config --subresource=status --type=merge -p '{"status":null}'
backup.notes-lab.io/app-config patched
$ kubectl -n notes-lab get backup app-config -o jsonpath='status={.status}{"\n"}'
status=

所以「最小权限」要按实际用的客户端来算。用 Go 客户端直接发 PATCH 的控制器只需 patch；用 kubectl 写的脚本还得给 get。上面 Role 里 backups/status 的 get 就是这么来的；configmaps 和 backups 本来就有 get，所以另外两处 kubectl patch 没出问题。

坑三：can-i --list 里多出来的权限

auth can-i --list 列出的不只有自己写的 Role，还有通过用户组继承的规则。这个集群的 CNI 是 Calico，所以多了几行 Calico 的资源；默认 kind 集群用的是 kindnet，不会出现这几行：

$ kubectl -n notes-lab auth can-i --list --as=system:serviceaccount:notes-lab:backup-controller

jobs.batch                                      []                                     []                 [get list create delete]
globalnetworkpolicies.projectcalico.org         []                                     []                 [get list watch create update patch delete deletecollection]

（输出删掉了 selfsubjectreviews 和一串 /healthz、/version 之类的非资源 URL；它是在删掉 status 规则前抓的，所以 status 这里还是只有 patch。）

来源是 Calico 安装时建的一个绑定给 system:authenticated 组的 ClusterRole：

$ kubectl get clusterrolebinding calico-tiered-policy-passthrough -o jsonpath='{.roleRef.name} {.subjects}{"\n"}'
calico-tiered-policy-passthrough [{"apiGroup":"rbac.authorization.k8s.io","kind":"Group","name":"system:authenticated"}]
$ sa get networkpolicies.projectcalico.org
Error from server (Forbidden): networkpolicies.projectcalico.org is forbidden: operation on Calico tiered policy is forbidden

实际调用被拒了，报错说明 Calico 的 API 服务自己又按 tier 做了一层检查，RBAC 这一层只是放行。这件事和 Operator 本身无关，但它说明审查一个 Operator 的权限时，不能只读它自带的 Role 文件，要用 can-i --list --as=<它的 ServiceAccount> 看最终生效的集合，再逐项判断。

控制器脚本

修好权限后的完整脚本，NS 和 KCFG 由环境变量传入：

#!/usr/bin/env bash
# 最小 Backup 控制器：轮询 + kubectl + jq。只用于演示，不是生产组件。
set -u
NS=${NS:?}
KCFG=${KCFG:?}
INTERVAL=${INTERVAL:-3}
FIN=notes-lab.io/backup-cleanup
kc() { kubectl --kubeconfig "$KCFG" -n "$NS" "$@"; }
log() { echo "$(date +%T) $*"; }

# 只在 Ready 条件或 observedGeneration 真的变化时才写 status
set_status() { # obj status reason message job
  local obj=$1 st=$2 reason=$3 msg=$4 job=$5 name gen want
  name=$(jq -r .metadata.name <<<"$obj"); gen=$(jq -r .metadata.generation <<<"$obj")
  want=$(jq -c --arg st "$st" --arg r "$reason" --arg m "$msg" --arg j "$job" \
      --argjson g "$gen" --arg now "$(date -u +%FT%TZ)" '
    ((.status.conditions // []) | map(select(.type=="Ready")) | .[0]) as $old
    | {observedGeneration: $g, lastJob: $j,
       conditions: [{type: "Ready", status: $st, reason: $r, message: $m, observedGeneration: $g,
         lastTransitionTime: (if $old != null and $old.status == $st then $old.lastTransitionTime else $now end)}]}' <<<"$obj")
  if [ "$(jq -S -c '.status // {}' <<<"$obj")" = "$(jq -S -c . <<<"$want")" ]; then return; fi
  kc patch backup "$name" --subresource=status --type=merge -p "{\"status\":$want}" >/dev/null \
    && log "status $name gen=$gen Ready=$st reason=$reason"
}

reconcile() {
  local obj=$1 name uid gen src retain rv job jobjson
  name=$(jq -r .metadata.name <<<"$obj"); uid=$(jq -r .metadata.uid <<<"$obj")
  gen=$(jq -r .metadata.generation <<<"$obj"); rv=$(jq -r .metadata.resourceVersion <<<"$obj")
  src=$(jq -r .spec.source <<<"$obj"); retain=$(jq -r '.spec.retain // 2' <<<"$obj")
  local fins; fins=$(jq -c '.metadata.finalizers // []' <<<"$obj")

  # 1. 删除中：先清理 GC 管不到的东西（目录里的登记项），再摘掉 finalizer
  if [ "$(jq -r '.metadata.deletionTimestamp // ""' <<<"$obj")" != "" ]; then
    if jq -e --arg f "$FIN" 'index($f)' <<<"$fins" >/dev/null; then
      kc patch configmap backup-catalog --type=merge -p "{\"data\":{\"$name\":null}}" >/dev/null || return
      local rest; rest=$(jq -c --arg f "$FIN" 'map(select(. != $f))' <<<"$fins")
      kc patch backup "$name" --type=merge \
        -p "{\"metadata\":{\"resourceVersion\":\"$rv\",\"finalizers\":$rest}}" >/dev/null \
        && log "cleanup $name: catalog entry removed, finalizer released"
    fi
    return
  fi

  # 2. 先挂上 finalizer，再做任何有副作用的事
  if ! jq -e --arg f "$FIN" 'index($f)' <<<"$fins" >/dev/null; then
    kc patch backup "$name" --type=merge \
      -p "{\"metadata\":{\"resourceVersion\":\"$rv\",\"finalizers\":$(jq -c --arg f "$FIN" '. + [$f]' <<<"$fins")}}" >/dev/null \
      && log "finalizer added to $name"
    return   # 下一轮用新的 resourceVersion 继续
  fi

  # 3. 校验依赖：源 ConfigMap 不存在就报告，不建 Job
  local err
  if ! err=$(kc get configmap "$src" -o name 2>&1 >/dev/null); then
    if grep -q NotFound <<<"$err"; then
      set_status "$obj" False SourceNotFound "configmap $src not found" ""
    else
      log "ERROR get configmap $src: $err"
    fi
    return
  fi

  # 4. 每个 generation 一个 Job，名字确定 => 重启/重复调谐不会多建
  job="$name-g$gen"
  if ! jobjson=$(kc get job "$job" -o json 2>/dev/null); then
    jq -n --arg job "$job" --arg name "$name" --arg uid "$uid" --arg gen "$gen" --arg src "$src" '
    {apiVersion: "batch/v1", kind: "Job",
     metadata: {name: $job,
       labels: {"notes-lab.io/backup": $name, "notes-lab.io/generation": $gen},
       ownerReferences: [{apiVersion: "notes-lab.io/v1", kind: "Backup", name: $name, uid: $uid,
                          controller: true, blockOwnerDeletion: true}]},
     spec: {backoffLimit: 0, activeDeadlineSeconds: 60,
       template: {spec: {restartPolicy: "Never",
         containers: [{name: "backup", image: "busybox:1.36",
           command: ["sh", "-c", "cd /src && echo \"files: $(ls | tr \"\\n\" \" \")\" && tar cf - . | md5sum"],
           resources: {requests: {cpu: "10m", memory: "16Mi"}, limits: {memory: "32Mi"}},
           volumeMounts: [{name: "src", mountPath: "/src", readOnly: true}]}],
         volumes: [{name: "src", configMap: {name: $src}}]}}}}' \
    | kc create -f - >/dev/null && log "created job $job" || { log "ERROR create job $job"; return; }
    set_status "$obj" False JobRunning "job $job created" "$job"
    return
  fi

  # 5. 把 Job 结果翻译成 Backup 的 Ready 条件
  if jq -e '.status.conditions // [] | any(.type=="Complete" and .status=="True")' <<<"$jobjson" >/dev/null; then
    local done_at; done_at=$(jq -r .status.completionTime <<<"$jobjson")
    local entry="job=$job completed=$done_at"
    if [ "$(kc get configmap backup-catalog -o json | jq -r --arg n "$name" '.data[$n] // ""')" != "$entry" ]; then
      kc patch configmap backup-catalog --type=merge -p "{\"data\":{\"$name\":\"$entry\"}}" >/dev/null \
        && log "catalog $name -> $entry"
    fi
    set_status "$obj" True Succeeded "job $job completed at $done_at" "$job"
  elif jq -e '.status.conditions // [] | any(.type=="Failed" and .status=="True")' <<<"$jobjson" >/dev/null; then
    set_status "$obj" False JobFailed "$(jq -r '.status.conditions[]|select(.type=="Failed")|.reason' <<<"$jobjson")" "$job"
  else
    set_status "$obj" False JobRunning "job $job running" "$job"
  fi

  # 6. 只保留最新 retain 个 Job
  kc get jobs -l "notes-lab.io/backup=$name" -o json \
    | jq -r --argjson keep "$retain" '.items | sort_by(.metadata.labels["notes-lab.io/generation"]|tonumber) | reverse | .[$keep:][] | .metadata.name' \
    | while read -r old; do
        kc delete job "$old" --wait=false >/dev/null && log "pruned job $old (retain=$retain)"
      done
}

log "controller started ns=$NS interval=${INTERVAL}s"
while true; do
  # stderr 不并进 list：有 warning 时 jq 仍能解析，错误直接进日志
  if list=$(kc get backups -o json); then
    while read -r obj; do [ -n "$obj" ] && reconcile "$obj"; done < <(jq -c '.items[]' <<<"$list")
  else
    log "ERROR list backups (see stderr above)"
  fi
  sleep "$INTERVAL"
done

几个设计点值得单独说：

  • 增删 finalizer 时带上 resourceVersion。merge patch 里写了 metadata.resourceVersion，API Server 会做乐观并发检查，对象在读和写之间被别人改过就返回 Conflict，而不是用旧的 finalizer 列表覆盖新的。
  • 挂 finalizer 之后本轮就返回，下一轮拿着新的 resourceVersion 再继续。先有 finalizer 再建 Job，保证「建了外部副作用却没机会清理」的窗口不存在。
  • Job 名由 generation 决定。这是幂等的核心，后面重启和双实例实验都靠它。
  • status 用 merge patch 整体替换 conditions 数组。只有一个条件时这样最简单；条件多了以后应该按 type 合并，否则会互相覆盖。

内容完全相同的 patch 被 API Server 当成了空操作，没有产生新版本，所以 watch 这个对象的人不会收到事件。代价只是每轮多一次请求；但如果 status 里放了每次都变的东西，比如「最后调谐时间」，每一轮就都是一次真实写入和一次 watch 事件，控制器还会被自己写 status 触发的事件再次唤醒。

blockOwnerDeletion: true 这次创建成功，但控制器并没有 backups/finalizers 的 update 权限。创建成功本身说明这个集群没有启用 OwnerReferencesPermissionEnforcement 准入插件，API Server 的启动参数也能印证（只读查询）：

按官方文档，这个插件有两条规则：一是修改对象的 ownerReferences 需要对该对象（这里是依赖方 Job）有 delete 权限，本文的 Role 对 jobs 已有 delete；二是设置 blockOwnerDeletion 需要对 owner 的 finalizers 子资源有 update 权限。在启用了它的集群里，同样的 Role 应该会创建失败，需要再给 backups/finalizers 的 update；这一点这次没有测到。

{"t":"10:54:34","type":"MODIFIED","rv":"11162298","gen":4,"ready":"Succeeded","del":null,"fin":["notes-lab.io/backup-cleanup"]}

{"t":"10:54:41","type":"MODIFIED","rv":"11162332","gen":5,"ready":"Succeeded","del":"2026-10-13T10:54:40Z","fin":["notes-lab.io/backup-cleanup"]}
{"t":"10:54:43","type":"DELETED","rv":"11162337","gen":5,"ready":"Succeeded","del":"2026-10-13T10:54:40Z","fin":["notes-lab.io/backup-cleanup"]}

能读出几件事。app-config 此前经历了 3 代（创建、retain 改 3、retain 改回 2），所以 ADDED 时是 gen:3；10:54:30 的 gen:4 就是上面那次 retain:3 的 patch，控制器随即建出 app-config-g4：

  • watch 的第一个事件是 ADDED，带着当前完整对象，之后每次变更（包括控制器自己写 status）都是一个 MODIFIED。informer 就是建立在「先 list、再从那个 resourceVersion 开始 watch」上的，我的脚本没用 watch，代价是每 3 秒完整 list 一次。
  • 前台删除时 API Server 加上了 foregroundDeletion finalizer，1 秒内依赖的 Job 删完，它就被摘掉了，剩下我们自己的 finalizer，再等 2 秒控制器摘掉，对象才 DELETED。
  • 设置 deletionTimestamp 时 generation 从 4 变成了 5，spec 并没有变。所以「generation 变了就该做一次新备份」这个假设在删除时并不成立；这个脚本在删除分支里先判断 deletionTimestamp 并直接返回，才没有为第 5 代再建一个 Job。
  • DELETED 事件里 ready 仍是 Succeeded。对象在被删时，status 不会自动变成「正在删除」，要看 deletionTimestamp。

控制器不在时删除：卡住

停掉控制器，删除 settings。20 秒后它还在：

$ date +%T; kubectl -n notes-lab delete backup settings --wait=false
18:53:36
backup.notes-lab.io "settings" deleted
$ date +%T; kubectl -n notes-lab get backup settings -o jsonpath='deletionTimestamp={.metadata.deletionTimestamp} finalizers={.metadata.finalizers}{"\n"}'
18:53:56
deletionTimestamp=2026-10-13T10:53:36Z finalizers=["notes-lab.io/backup-cleanup"]
$ kubectl -n notes-lab get backups
NAME         SOURCE       RETAIN   READY   REASON      AGE
app-config   app-config   2        True    Succeeded   4m21s
settings     settings     1        True    Succeeded   99s
$ kubectl -n notes-lab get jobs,pods | grep -E 'NAME|settings'
NAME                      STATUS     COMPLETIONS   DURATION   AGE
job.batch/settings-g2     Complete   1/1           3s         60s
NAME                      READY   STATUS      RESTARTS   AGE
pod/settings-g2-bxzrv     0/1     Completed   0          60s

三处容易误判的地方：

  • kubectl delete 打印了 deleted，对象却还在。这行字只表示删除请求被接受了。
  • kubectl get backups 没有显示 Terminating，settings 看起来和 app-config 一样健康，Ready=True。Pod 的 STATUS 列和 Namespace 的 STATUS 会显示 Terminating，自定义资源只显示 CRD 里定义的列。排查「删不掉」要直接看 deletionTimestamp 和 finalizers；如果自己写 CRD，可以考虑加一个 .metadata.deletionTimestamp 的打印列。
  • Job 和 Pod 也还在。默认的 background 级联是「owner 先消失，GC 再删依赖」，owner 被 finalizer 挡住，依赖也就一直留着。

不带 --wait=false 的删除会一直挂着，用 timeout 15 包一层，15 秒后被杀掉，退出码 124：

$ timeout 15 kubectl -n notes-lab delete backup settings; echo exit=$?
backup.notes-lab.io "settings" deleted
exit=124

这正是卸载 Operator 时的典型事故：先删了控制器，再删它的对象（或 CRD，见 CRD 那一篇删除 CRD 的实验），就停在这里。手动摘掉 finalizer 能解开：

$ date +%T; kubectl -n notes-lab patch backup settings --type=json -p '[{"op":"remove","path":"/metadata/finalizers"}]'
18:54:11
backup.notes-lab.io/settings patched
$ date +%T; kubectl -n notes-lab get backup settings; kubectl -n notes-lab get jobs,pods | grep -E 'NAME|settings'
18:54:15
Error from server (NotFound): backups.notes-lab.io "settings" not found
NAME                      STATUS     COMPLETIONS   DURATION   AGE
NAME                      READY   STATUS      RESTARTS   AGE

这条 JSON patch 删掉的是整个 finalizers 字段，对象上如果还有别的组件挂的 finalizer，也一并被清掉了。这里只有一个所以无所谓；生产环境应只删自己那一项，并用 test 先确认下标对应的确实是它。补测时给对象挂了两个 finalizer，删除后按下标移除：

$ kubectl -n notes-lab patch backup app-config --type=merge -p '{"metadata":{"finalizers":["example.com/other","notes-lab.io/backup-cleanup"]}}'
backup.notes-lab.io/app-config patched
$ kubectl -n notes-lab delete backup app-config --wait=false
backup.notes-lab.io "app-config" deleted
$ kubectl -n notes-lab patch backup app-config --type=json -p '[{"op":"test","path":"/metadata/finalizers/0","value":"notes-lab.io/backup-cleanup"},{"op":"remove","path":"/metadata/finalizers/0"}]'
The request is invalid: the server rejected our request due to an error in our request
$ kubectl -n notes-lab patch backup app-config --type=json -p '[{"op":"test","path":"/metadata/finalizers/1","value":"notes-lab.io/backup-cleanup"},{"op":"remove","path":"/metadata/finalizers/1"}]'
backup.notes-lab.io/app-config patched
$ kubectl -n notes-lab get backup app-config -o jsonpath='deletionTimestamp={.metadata.deletionTimestamp} finalizers={.metadata.finalizers}{"\n"}'
deletionTimestamp=2026-10-13T11:03:57Z finalizers=["example.com/other"]

下标写错时 test 失败，整个 patch 被拒绝，不会误删别人的 finalizer；对象继续等 example.com/other 的主人处理。

回到 settings：对象和 Job、Pod 都没了，但 finalizer 本来要做的事没人做，目录里留下了一条孤儿记录。等控制器最后把 app-config 正常删完，目录里只剩这一条：

$ kubectl -n notes-lab get configmap backup-catalog -o jsonpath='{.data}{"\n"}'
{"settings":"job=settings-g2 completed=2026-10-13T10:52:59Z"}

官方文档对此的建议是：不要为了让删除继续就手动移除 finalizer，除非你清楚它的用途、并且用别的方式完成了它要做的清理。放到 Operator 设计里，就是要在文档里写明每个 finalizer 负责清理什么、控制器长期不在时人工清理的步骤。卸载时先删对象、等控制器清理完，再删控制器和 CRD（CRD 被卡住的情形见 CRD 那一篇）。

和真正的控制器框架比

上面每一项机制都是手搓的，生产环境的 Operator 一般用 controller-runtime（Kubebuilder 和 Operator SDK 的 Go 项目都基于它）。下表左列是这次实测的脚本行为，右列是框架按其文档提供的机制，右列我没有在这次实验里运行验证：

问题这个脚本controller-runtime / client-go
如何得知变化每 3 秒完整 list 一次所有 Backup 和相关 Jobinformer：list 一次后 watch，本地缓存对象，读请求走缓存
子对象变化靠下一轮轮询发现 Job 完成可以 watch 拥有的对象（Owns），Job 变化时把它的 owner 放进队列
重复事件、并发单线程顺序处理，没有队列workqueue 对同一个 key 去重，且同一个 key 不会被并发处理
出错后打印错误，下一轮（3 秒后）重试按 key 指数退避重新入队，叠加整体令牌桶限速
多副本没有，双实例只靠确定性名字防住了重复创建基于 Lease 的 leader election；manager 选项默认 LeaseDuration 15 秒、RenewDeadline 10 秒、RetryPeriod 2 秒
写 status、finalizerkubectl merge patch，finalizer 带 resourceVersionclient 的 Status().Update/Patch，controllerutil 提供增删 finalizer、设置 controller 引用的辅助函数
权限手写 Role，kubectl 需要额外的 getKubebuilder 项目用 // +kubebuilder:rbac 注释，由 controller-gen 生成 RBAC 清单，仍需人工审查最终权限

框架解决的是规模和可靠性：缓存省掉了反复 list 的开销，队列和退避让一个坏对象不至于拖住其他对象，leader election 解决了上面双实例实验里的分歧问题。它不替你做的，是这篇大部分篇幅讨论的设计决定：status 里报告什么、什么算一次新请求、finalizer 负责清理什么、依赖缺失时怎么表现、什么时候可以清理旧产物。这些决定用 shell 和用 Go 都得自己想清楚。

评审一个 Operator 时看什么

按这次实验踩到的点，评审一个现成的 Operator 可以逐项问：

  • 用 kubectl auth can-i --list --as=system:serviceaccount:<ns>:<sa> 看最终生效的权限，子资源用 --subresource 查，别用斜杠。
  • status 里有没有 observedGeneration？Ready 条件在 spec 刚改完时会不会给出旧结论？
  • 子对象名字是不是由输入确定的？控制器重启或多副本时会不会重复创建？
  • 每个 finalizer 清理什么？控制器卸载或长期宕机时，文档里有没有人工处理步骤？
  • 依赖缺失时，错误是写在用户提交的对象上，还是只出现在某个 Pod 的事件里？
  • 清理旧产物的规则会不会在新产物成功前就删掉旧的？

清理

kubectl delete crd backups.notes-lab.io --wait
kubectl delete namespace notes-lab --wait
kubectl get crd backups.notes-lab.io
# Error from server (NotFound): customresourcedefinitions.apiextensions.k8s.io "backups.notes-lab.io" not found

删 CRD 前要确认已经没有带 finalizer 的实例，否则 CRD 会卡在 Terminating（原因同上）。这次的权限只用了 Role 和 RoleBinding，随 namespace 一起删除，没有创建任何 ClusterRole。
