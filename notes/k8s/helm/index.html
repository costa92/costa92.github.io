Helm：管理一组 Kubernetes 清单

Helm 把模板和默认参数打包成 Chart，装进集群后形成一个 Release。每次 install、upgrade、rollback 都会给 Release 记一个新的修订号（revision）。适合用它管理的是由多份清单组成、还要按环境调参数的应用。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0），客户端是 Helm v4.3.0：

version.BuildInfo{Version:"v4.3.0", GitCommit:"bec5b06ed841fe5269972d864d5177944fd5970f", GitTreeState:"clean", GoVersion:"go1.27.1", KubeClientVersion:"v1.37"}

实验放在单独的 notes-lab namespace 里，Service 的 IP 用 <cluster-ip> 代替。网上多数 Helm 教程是按 Helm 3 写的，Helm 4 有几处变化会影响下面的命令和输出，遇到时会单独指出。这一篇只讲 Release 的生命周期；Chart 怎么写见编写 Helm Chart，子 Chart 见 Helm Chart 依赖与锁定，生产升级的检查流程见 Helm 升级验证与回滚。

准备一个 Chart

helm create demo

脚手架生成了 Deployment、Service、ServiceAccount，以及默认关闭的 HPA、Ingress、HTTPRoute 模板。先别急着装，看一眼镜像会渲染成什么：

helm template web ./demo --show-only templates/deployment.yaml | grep image:
image: "nginx:1.16.0"

模板里写的是 {{ .Values.image.tag | default .Chart.AppVersion }}，values.yaml 里 tag 为空，于是用了 Chart.yaml 的 appVersion: "1.16.0"。nginx 1.16.0 是 2019 年的版本，直接装就得先去拉一个老镜像。这里把 values.yaml 改成集群里已缓存的 nginx:alpine，顺便补上资源请求：

image:
  repository: nginx
  pullPolicy: IfNotPresent
  tag: "alpine"
# ...
resources:
  requests:
    cpu: 20m
    memory: 32Mi
$ helm lint ./demo
==> Linting ./demo
[INFO] Chart.yaml: icon is recommended

1 chart(s) linted, 0 chart(s) failed

appVersion 没改，所以后面所有输出的 APP VERSION 列都还是 1.16.0，和实际跑的镜像对不上。这一列只是 Chart 作者写的说明，判断线上版本要看 Deployment 里的 image。

安装，以及 Release 存在哪里

kubectl create namespace notes-lab
helm install web ./demo -n notes-lab --wait --timeout 2m
helm list -n notes-lab
NAME: web
LAST DEPLOYED: Mon Oct 12 15:48:50 2026
NAMESPACE: notes-lab
STATUS: deployed
REVISION: 1
DESCRIPTION: Install complete
...
NAME  NAMESPACE   REVISION  UPDATED                                STATUS    CHART       APP VERSION
web   notes-lab   1         2026-10-12 15:48:50.58349442 +0800 +08 deployed  demo-0.1.0  1.16.0

Helm 没有服务端组件，Release 的状态默认存成 Release 所在 namespace 里的 Secret（可以用 HELM_DRIVER 换成 ConfigMap 或 SQL）：

$ kubectl -n notes-lab get secret --show-labels
NAME                        TYPE                 DATA   AGE   LABELS
sh.helm.release.v1.web.v1   helm.sh/release.v1   1      7s    modifiedAt=1791791336,name=web,owner=helm,status=deployed,version=1

一个修订对应一个 Secret，名字是 sh.helm.release.v1.<release>.v<revision>，类型 helm.sh/release.v1，状态写在标签上。它的 release 字段要解两层 base64：外层是 Secret 本身的编码，解开后是以 H4sI 开头的字符串，这是 gzip 数据（1f 8b）再做一次 base64 的样子：

$ kubectl -n notes-lab get secret sh.helm.release.v1.web.v1 -o jsonpath="{.data.release}" | base64 -d | base64 -d | head -c 4 | xxd
00000000: 1f8b 0800                                ....

再 gunzip 就是一份 JSON：

kubectl -n notes-lab get secret sh.helm.release.v1.web.v1 -o jsonpath="{.data.release}" \
  | base64 -d | base64 -d | gunzip \
  | jq '{name,namespace,version,info: (.info|{status,description,first_deployed}), apply_method, chart: .chart.metadata.version, config, manifest_bytes: (.manifest|length)}'
{
  "name": "web",
  "namespace": "notes-lab",
  "version": 1,
  "info": {
    "status": "deployed",
    "description": "Install complete",
    "first_deployed": "2026-10-12T15:48:50.58349442+08:00"
  },
  "apply_method": "ssa",
  "chart": "0.1.0",
  "config": null,
  "manifest_bytes": 2008
}

几个字段值得认一下：

  • manifest 是这次渲染出的完整清单，helm get manifest 读的就是它；
  • config 是用户传入的 values，这次没传，所以是 null；
  • chart 里存了整个 Chart，包括全部模板文件（.chart.templates[].name 能列出 deployment.yaml、NOTES.txt 在内的 9 个文件）。整个 Release JSON 解压后 21028 字节，Secret 的 .data.release 字段 11744 字节，其中大头是 chart，而且每个修订都存一份；
  • apply_method: "ssa" 是 Helm 4 的新字段。新安装的 Release 默认用服务端应用（Server-Side Apply），从 Helm 3 升级过来的老 Release 继续用客户端应用，可以用 --server-side 显式指定。

在 Deployment 的 managedFields 里也能看到这一点，字段管理者是 helm，操作类型是 Apply；同时 Helm 给每个资源打上了归属标记，后面讲资源冲突时会用到：

$ kubectl -n notes-lab get deploy web-demo -o jsonpath="{range .metadata.managedFields[*]}{.manager} {.operation}{\"\n\"}{end}"
helm Apply
kube-controller-manager Update
$ kubectl -n notes-lab get deploy web-demo -o jsonpath="{.metadata.annotations}{\"\n\"}{.metadata.labels}"
{"deployment.kubernetes.io/revision":"1","meta.helm.sh/release-name":"web","meta.helm.sh/release-namespace":"notes-lab"}
{"app.kubernetes.io/instance":"web","app.kubernetes.io/managed-by":"Helm","app.kubernetes.io/name":"demo","app.kubernetes.io/version":"1.16.0","helm.sh/chart":"demo-0.1.0"}

预览：template、dry-run=client、dry-run=server

三种预览方式离集群的远近不同。为了看出区别，临时往 Chart 里加一个模板 templates/env-info.yaml，读取集群版本，并用 lookup 查询本 Release 已有的 Service：

apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ include "demo.fullname" . }}-env-info
data:
  kubeVersion: {{ .Capabilities.KubeVersion.Version | quote }}
  existingClusterIP: {{ dig "spec" "clusterIP" "none" (lookup "v1" "Service" .Release.Namespace (include "demo.fullname" .)) | quote }}

Release web 已经装好，它的 Service 是存在的。三种方式渲染出的结果：

$ helm template web ./demo --show-only templates/env-info.yaml
  kubeVersion: "v1.37.0"
  existingClusterIP: "none"

$ helm upgrade web ./demo -n notes-lab --dry-run=client --reuse-values
  kubeVersion: "v1.31.0"
  existingClusterIP: "none"

$ helm upgrade web ./demo -n notes-lab --dry-run=server --reuse-values
  kubeVersion: "v1.31.0"
  existingClusterIP: "<cluster-ip>"

（只截取了 data 部分。这三次对比做完后就删掉了 env-info.yaml，后面的实验里没有它。）

  • helm template 完全不连集群，.Capabilities.KubeVersion 填的是 Helm 自带的默认值 v1.37.0，和 helm version 里的 KubeClientVersion 一致，而集群实际是 v1.31.0。依赖版本判断（比如按集群版本选 API 版本）的 Chart，用 helm template 预览可能和真实安装不一样；
  • --dry-run=client 拿到了真实的集群版本，但 lookup 仍然返回空。帮助里说 client 模式「avoids cluster connections」，实测它至少连了集群读取版本信息，和帮助的说法对不上；
  • 只有 --dry-run=server 的 lookup 真正查到了现有 Service。

不过 server 模式也只管渲染，不会把对象交给 API Server 校验。把 Service 类型设成一个不存在的值 Foo，三种方式都照常输出 type: Foo，--dry-run=server 也没报错。下一节真正执行时才被拒绝。

Helm 本身没有 diff 命令，helm diff 是第三方插件，这次环境没装：

$ helm diff
Error: unknown command "diff" for "helm"
Run 'helm --help' for usage.

不想装插件的话，可以用 helm get manifest 导出当前清单，和 helm template 的输出做文本比对；也可以把渲染结果交给 kubectl diff -f - 做服务端比对。这两种方法这次都没有实测。

values 的优先级

两个覆盖文件：

# values-a.yaml
replicaCount: 2
podLabels:
  team: a
  tier: web
tolerations:
  - key: notes-lab.io/a
    operator: Exists
# values-b.yaml
replicaCount: 3
podLabels:
  tier: frontend
tolerations:
  - key: notes-lab.io/b
    operator: Exists

按不同顺序传入，只看 Deployment 里相关的几行：

$ helm template web ./demo -f values-a.yaml -f values-b.yaml --show-only templates/deployment.yaml | grep -E "replicas:|team:|tier:|key:"
  replicas: 3
        team: a
        tier: frontend
        - key: notes-lab.io/b
$ helm template web ./demo -f values-b.yaml -f values-a.yaml --show-only templates/deployment.yaml | grep -E "replicas:|team:|tier:|key:"
  replicas: 2
        team: a
        tier: web
        - key: notes-lab.io/a

多个 -f 后面的覆盖前面的，但覆盖方式分两种：map 是逐键合并，team: a 只在 a 里有，两种顺序下都保留了下来；列表是整体替换，tolerations 不会拼成两项，只剩后一个文件里的那一项。往列表里「追加一项」的写法在 values 里不存在，要么把整个列表写全，要么改模板。

--set 的优先级高于所有 -f，和它在命令行里的位置无关：

$ helm template web ./demo -f values-a.yaml -f values-b.yaml --set replicaCount=1 --set podLabels.tier=api --show-only templates/deployment.yaml | grep -E "replicas:|team:|tier:|key:"
  replicas: 1
        team: a
        tier: api
        - key: notes-lab.io/b
$ helm template web ./demo --set replicaCount=1 -f values-b.yaml --show-only templates/deployment.yaml | grep -E "replicas:"
  replicas: 1

官方文档说，把某个键设成 null 可以把它从 Chart 的默认值里删掉。实测和文档一致，不在默认值里的键不会被删：

$ helm template web ./demo --set image.pullPolicy=null --show-only templates/deployment.yaml | grep -E "imagePullPolicy"
          imagePullPolicy: 
$ helm template web ./demo -f values-a.yaml --set podLabels.team=null --show-only templates/deployment.yaml | grep -E "team:|tier:"
        team: null
        tier: web

image.pullPolicy 是 Chart 默认值，被删掉后渲染成空。podLabels.team 来自另一个用户文件 values-a.yaml，null 没有删除它，而是被当成字面值写进了标签。要去掉其他 values 文件里的键，只能改那个文件。

helm upgrade web ./demo -n notes-lab -f values-a.yaml --wait --timeout 2m
helm get values web -n notes-lab

helm get values 只显示用户传入的部分，加 --all 才会把 Chart 默认值一起列出。接下来连续做两次升级，一次什么 values 都不传，一次只传一个 --set：

$ helm upgrade web ./demo -n notes-lab --wait --timeout 2m
REVISION: 3
$ helm get values web -n notes-lab; kubectl -n notes-lab get deploy web-demo
USER-SUPPLIED VALUES:
podLabels:
  team: a
  tier: web
replicaCount: 2
tolerations:
- key: notes-lab.io/a
  operator: Exists
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
web-demo   2/2     2            2           78s

$ helm upgrade web ./demo -n notes-lab --set podLabels.tier=api --wait --timeout 2m
REVISION: 4
$ helm get values web -n notes-lab; kubectl -n notes-lab get deploy web-demo
USER-SUPPLIED VALUES:
podLabels:
  tier: api
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
web-demo   1/1     1            1           92s

不传任何 values 时，Helm 沿用了上一个修订的 values，副本数还是 2；一旦传了 --set podLabels.tier=api，上次的 -f values-a.yaml 就整个作废，副本数悄悄退回到 Chart 默认的 1。只想改一个参数时，要么每次把全部 -f 带上，要么加 --reuse-values（在上次的 values 上叠加本次修改）。--reuse-values 有个副作用：它连上次的 Chart 默认值也一起沿用，新版 Chart 在 values.yaml 里加的默认值不会生效；需要新默认值时用 --reset-then-reuse-values。这一点这次没有实测。生产上更稳的做法是前者，values 文件放进版本库，每次升级都完整传入。

失败的升级

被 API Server 拒绝：失败了，但改动已经生效一半

用上一节没被拦住的非法 Service 类型真正执行一次：

$ helm upgrade web ./demo -n notes-lab --reuse-values --set service.type=Foo
level=WARN msg="upgrade failed" name=web error="server-side apply failed for object notes-lab/web-demo /v1, Kind=Service: Service \"web-demo\" is invalid: spec.type: Unsupported value: \"Foo\": supported values: \"ClusterIP\", \"ExternalName\", \"LoadBalancer\", \"NodePort\""
Error: UPGRADE FAILED: server-side apply failed for object notes-lab/web-demo /v1, Kind=Service: Service "web-demo" is invalid: spec.type: Unsupported value: "Foo": supported values: "ClusterIP", "ExternalName", "LoadBalancer", "NodePort"

修订 5 被记为 failed，修订 4 仍然是 deployed。helm status 显示的却是最新的修订 5：

NAME: web
LAST DEPLOYED: Mon Oct 12 15:50:47 2026
NAMESPACE: notes-lab
STATUS: failed
REVISION: 5
DESCRIPTION: Upgrade "web" failed: server-side apply failed for object notes-lab/web-demo /v1, Kind=Service: Service "web-demo" is invalid: spec.type: Unsupported value: "Foo": supported values: "ClusterIP", "ExternalName", "LoadBalancer", "NodePort"

失败不等于什么都没改。再试一次，同时把副本数改成 3：

$ helm upgrade web ./demo -n notes-lab --reuse-values --set replicaCount=3 --set service.type=Foo
Error: UPGRADE FAILED: server-side apply failed for object notes-lab/web-demo /v1, Kind=Service: Service "web-demo" is invalid: spec.type: Unsupported value: "Foo": supported values: "ClusterIP", "ExternalName", "LoadBalancer", "NodePort"
$ kubectl -n notes-lab get deploy web-demo
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
web-demo   1/3     1            1           2m5s

Service 被拒绝了，Deployment 的副本数却已经改成了 3，几秒后变成 3/3。按 Helm 的安装顺序，Service 排在 Deployment 前面，可见一个资源失败并没有让后面的资源停下。Helm 没有事务：它逐个提交资源，某个资源出错时先记下错误，继续处理剩下的，最后再一起报错。失败的那个不会生效，其余已提交的不会自动撤回。Release 状态写着 failed，集群却处在新旧混合的状态。修复的办法是回滚到一个已知正常的修订：

$ helm rollback web 4 -n notes-lab --wait --timeout 2m
Rollback was a success! Happy Helming!
$ helm history web -n notes-lab
REVISION  UPDATED                   STATUS      CHART       APP VERSION  DESCRIPTION
1         Mon Oct 12 15:48:50 2026  superseded  demo-0.1.0  1.16.0       Install complete
2         Mon Oct 12 15:49:37 2026  superseded  demo-0.1.0  1.16.0       Upgrade complete
3         Mon Oct 12 15:50:07 2026  superseded  demo-0.1.0  1.16.0       Upgrade complete
4         Mon Oct 12 15:50:08 2026  superseded  demo-0.1.0  1.16.0       Upgrade complete
5         Mon Oct 12 15:50:47 2026  failed      demo-0.1.0  1.16.0       Upgrade "web" failed: server-side apply fa
6         Mon Oct 12 15:50:55 2026  failed      demo-0.1.0  1.16.0       Upgrade "web" failed: server-side apply fa
7         Mon Oct 12 15:51:07 2026  deployed    demo-0.1.0  1.16.0       Rollback to 4
$ kubectl -n notes-lab get deploy web-demo
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
web-demo   1/1     1            1           2m24s

回滚不会改写历史，而是用修订 4 的内容生成一个新修订 7，描述是 Rollback to 4。

镜像写错：不加 –wait，Helm 说成功

把镜像标签改成不存在的 alpine-typo，不加 --wait：

$ helm upgrade web ./demo -n notes-lab --reuse-values --set image.tag=alpine-typo
STATUS: deployed
REVISION: 8
DESCRIPTION: Upgrade complete

约 20 秒后：

$ helm status web -n notes-lab
...
STATUS: deployed
REVISION: 8
DESCRIPTION: Upgrade complete
RESOURCES:
...
==> v1/Pod(related)
NAME                        READY   STATUS             RESTARTS   AGE
web-demo-56558f6ccd-w2g9d   1/1     Running            0          90s
web-demo-769b567cc9-lsght   0/1     ImagePullBackOff   0          20s

不加 --wait 时，Helm 只等 hook，资源被 API Server 接受就算成功（--wait 帮助里写明，不带这个参数时的默认策略是 hookOnly）。修订 8 被标成了 deployed，新 Pod 却在 ImagePullBackOff；旧 Pod 还在跑，是 Deployment 滚动更新的保护，跟 Helm 无关。另外，Helm 4 的 helm status 默认就列出资源和相关 Pod，Helm 3 里的 --show-resources 参数已经删掉，传它会报 unknown flag。

加上 --wait，Helm 会一直等到资源就绪或超时：

$ date +%T; helm upgrade web ./demo -n notes-lab --reuse-values --set image.tag=alpine-typo2 --wait --timeout 60s; echo "exit=$?"; date +%T
15:51:46
level=WARN msg="upgrade failed" name=web error="resource Deployment/notes-lab/web-demo not ready. status: InProgress, message: Pending termination: 1\ncontext deadline exceeded"
Error: UPGRADE FAILED: resource Deployment/notes-lab/web-demo not ready. status: InProgress, message: Pending termination: 1
context deadline exceeded
exit=1
15:52:47

正好等满 60 秒后失败。status: InProgress, message: Pending termination: 1 是 Helm 4 换用 kstatus 判断就绪后的输出格式，意思是还有 1 个旧副本没被替换下来，滚动更新卡住了。真正的原因要去看新 Pod 的事件。

–rollback-on-failure 会回到哪个修订

Helm 4 把 --atomic 改名为 --rollback-on-failure，旧参数还能用，但会打印警告：

Flag --atomic has been deprecated, use --rollback-on-failure instead

它的帮助写的是失败后回滚到「上一个成功的 release」，而且会自动开启 --wait。此时上一个 deployed 的修订是 8，也就是镜像写错、不加 --wait 被误标成功的那个：

$ helm upgrade web ./demo -n notes-lab --reuse-values --set image.tag=alpine-typo3 --rollback-on-failure --timeout 45s
Error: UPGRADE FAILED: an error occurred while rolling back the release. original upgrade error: resource Deployment/notes-lab/web-demo not ready. status: InProgress, message: Pending termination: 1
context deadline exceeded: release web failed: resource Deployment/notes-lab/web-demo not ready. status: InProgress, message: Pending termination: 1
context deadline exceeded
$ helm get values web -n notes-lab --revision 11
USER-SUPPLIED VALUES:
image:
  tag: alpine-typo
podLabels:
  tier: api
$ kubectl -n notes-lab get deploy web-demo -o jsonpath="{.spec.template.spec.containers[0].image}"
nginx:alpine-typo

升级失败（修订 10）后，Helm 自动回滚到了修订 8，回滚本身也等不到就绪，于是修订 11 也是 failed，Deployment 停在 nginx:alpine-typo。--rollback-on-failure 只认 Release 记录里的状态，而一个不加 --wait 装上去的修订，即使应用起不来也是 deployed。

手动 helm rollback web 7 回到正常版本（生成修订 12）后再试同样的错误升级，这次就回滚成功了：

$ helm upgrade web ./demo -n notes-lab --reuse-values --set image.tag=alpine-typo4 --rollback-on-failure --timeout 45s
Error: UPGRADE FAILED: release web failed, and has been rolled back due to rollback-on-failure being set: resource Deployment/notes-lab/web-demo not ready. status: InProgress, message: Pending termination: 1
context deadline exceeded
$ helm history web -n notes-lab
...
12        Mon Oct 12 15:54:31 2026  superseded  demo-0.1.0  1.16.0       Rollback to 7
13        Mon Oct 12 15:54:37 2026  failed      demo-0.1.0  1.16.0       Upgrade "web" failed: resource Deployment/notes-lab/web-demo not re
14        Mon Oct 12 15:55:24 2026  deployed    demo-0.1.0  1.16.0       Rollback to 12
$ kubectl -n notes-lab get deploy web-demo -o jsonpath="{.spec.template.spec.containers[0].image}"
nginx:alpine

结论很直接：要依赖自动回滚，每次升级都得带 --wait，否则历史里的 deployed 不可信。

升级进程被中断：pending-upgrade

CI 任务被取消、终端断开，都可能让 Helm 进程在升级途中退出。用 kill -9 模拟：带 --wait 发起一次错误镜像的升级，5 秒后杀掉进程。

$ helm history web -n notes-lab | tail -2
16        Mon Oct 12 15:55:52 2026  deployed         demo-0.1.0  1.16.0       Rollback to 14
17        Mon Oct 12 15:56:30 2026  pending-upgrade  demo-0.1.0  1.16.0       Preparing upgrade
$ helm upgrade web ./demo -n notes-lab --reuse-values --set image.tag=alpine
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress

修订 17 停在 pending-upgrade，没有任何进程会再去更新它，26 秒后再看还是这样。对应的 Secret 标签也是 status=pending-upgrade。之后的 upgrade 一律被拒，报的却是「另一个操作正在进行」，很容易让人以为是别人在发布，一直干等。这时清单其实已经提交了，Deployment 用的是 nginx:alpine-typo6，新 Pod 在 ImagePullBackOff。

helm rollback 不受这个锁的限制，回滚到最后一个正常修订就能恢复：

$ helm rollback web 16 -n notes-lab --wait --timeout 90s
Rollback was a success! Happy Helming!
$ helm history web -n notes-lab | tail -4
15        Mon Oct 12 15:55:42 2026  superseded       demo-0.1.0  1.16.0       Upgrade complete
16        Mon Oct 12 15:55:52 2026  superseded       demo-0.1.0  1.16.0       Rollback to 14
17        Mon Oct 12 15:56:30 2026  pending-upgrade  demo-0.1.0  1.16.0       Preparing upgrade
18        Mon Oct 12 15:57:06 2026  deployed         demo-0.1.0  1.16.0       Rollback to 16

修订 17 在历史里永远保留 pending-upgrade，但不再挡路，下一次 helm upgrade 正常生成了修订 19。动手回滚前，先确认确实没有其他 Helm 进程在跑，例如 CI 里有没有同一个 Release 的任务。

上面那份历史里修订 15 显示 Upgrade complete，是第一次模拟时留下的：那次 kill 只杀掉了包装命令的 shell，真正的 helm 进程还活着。推测它在我回滚（修订 16）把镜像改回正确值之后等到了 Deployment 就绪，于是把自己这次「错误镜像的升级」标成了成功，有一段时间历史里同时出现了两个 deployed。这也说明 Release 记录反映的是 Helm 进程看到的过程，不是对集群状态的独立判断。

历史只保留 10 个修订

经过这一轮折腾，Secret 只剩 10 个：

$ kubectl -n notes-lab get secret -l owner=helm,name=web -o custom-columns=NAME:.metadata.name,STATUS:.metadata.labels.status --sort-by=.metadata.creationTimestamp
NAME                         STATUS
sh.helm.release.v1.web.v10   failed
sh.helm.release.v1.web.v11   failed
sh.helm.release.v1.web.v12   superseded
sh.helm.release.v1.web.v13   failed
sh.helm.release.v1.web.v14   superseded
sh.helm.release.v1.web.v15   superseded
sh.helm.release.v1.web.v16   superseded
sh.helm.release.v1.web.v17   pending-upgrade
sh.helm.release.v1.web.v18   superseded
sh.helm.release.v1.web.v19   deployed
$ helm rollback web 4 -n notes-lab
Error: release has no 4 version

helm upgrade 的 --history-max 默认是 10，超出的旧修订从最老的开始连同 Secret 一起删掉，只有当前 deployed 的那个修订会被保留。删掉 namespace 后在新建的 notes-lab 里重新装 web 来验证：修订 1 是正常安装，随后用 --history-max 3 做 4 次镜像写错的升级，都失败了：

helm install web ./demo -n notes-lab --wait --timeout 90s
for t in typo1 typo2 typo3 typo4; do
  helm upgrade web ./demo -n notes-lab --history-max 3 --set image.tag=$t --wait --timeout 20s
done
$ helm history web -n notes-lab
REVISION  UPDATED                   STATUS    CHART       APP VERSION  DESCRIPTION
1         Mon Oct 12 16:07:07 2026  deployed  demo-0.1.0  1.16.0       Install complete
4         Mon Oct 12 16:07:58 2026  failed    demo-0.1.0  1.16.0       Upgrade "web" failed: resource Deployment/no
5         Mon Oct 12 16:08:19 2026  failed    demo-0.1.0  1.16.0       Upgrade "web" failed: resource Deployment/no

失败的修订 2、3 被删了，deployed 的修订 1 留了下来，所以连续失败不会把能回滚的版本删掉。但「保留」认的是状态：如果当前 deployed 的是一次不加 --wait、实际起不来的升级，按源码逻辑推断，留下来的就是这个坏版本，更早的好版本照样会被删掉（这一点没有实测）。

集群里已有同名资源

用 kubectl 先建一个 Service，名字恰好和 Chart 要创建的一样，然后安装 Release other：

$ kubectl -n notes-lab create service clusterip other-demo --tcp=80:80
service/other-demo created
$ helm install other ./demo -n notes-lab
Error: INSTALLATION FAILED: unable to continue with install: Service "other-demo" in namespace "notes-lab" exists and cannot be imported into the current release: invalid ownership metadata; label validation error: missing key "app.kubernetes.io/managed-by": must be set to "Helm"; annotation validation error: missing key "meta.helm.sh/release-name": must be set to "other"; annotation validation error: missing key "meta.helm.sh/release-namespace": must be set to "notes-lab"

Helm 靠上文那一个标签加两个注解判断资源归谁。不属于任何 Release 的资源，报 missing key；属于另一个 Release 的，报的是值不匹配。用 fullnameOverride 让新 Release web2 的资源和 web 撞名：

$ helm install web2 ./demo -n notes-lab --set fullnameOverride=web-demo
Error: INSTALLATION FAILED: unable to continue with install: ServiceAccount "web-demo" in namespace "notes-lab" exists and cannot be imported into the current release: invalid ownership metadata; annotation validation error: key "meta.helm.sh/release-name" must equal "web2": current value is "web"

第一种情况下，事后查 owner=helm 的 Secret 和带 app.kubernetes.io/instance=other 标签的资源都是空的：归属检查发生在创建任何东西之前，失败不会留下 Release 记录。

确认这个 Service 确实应该交给 Helm 管，可以加 --take-ownership，跳过归属检查。但在 Helm 4 下，它还会撞上服务端应用的字段冲突：

$ helm install other ./demo -n notes-lab --take-ownership
Error: INSTALLATION FAILED: conflict occurred while applying object notes-lab/other-demo /v1, Kind=Service: Apply failed with 3 conflicts: conflicts with "kubectl-create" using v1:
- .spec.selector
- .spec.ports[port=80,protocol="TCP"].name
- .spec.ports[port=80,protocol="TCP"].targetPort
$ helm history other -n notes-lab
REVISION  UPDATED                   STATUS  CHART       APP VERSION  DESCRIPTION
1         Mon Oct 12 15:58:30 2026  failed  demo-0.1.0  1.16.0       Release "other" failed: conflict occurred while applying
$ kubectl -n notes-lab get deploy,sa -l app.kubernetes.io/instance=other
NAME                         READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/other-demo   0/1     0            0           1s

NAME                        SECRETS   AGE
serviceaccount/other-demo   0         4s

kubectl create 写入的 selector、端口名和 targetPort 这三个字段，字段管理者是 kubectl-create，Helm 要改成自己的值，服务端应用拒绝了。和上面不同，这次失败留下了一个 failed 的 Release，还有已经建好的 ServiceAccount 和 Deployment。直接重试会报 cannot reuse a name that is still in use，要先 helm uninstall other，再加上 --force-conflicts 强制接管冲突字段：

$ helm install other ./demo -n notes-lab --take-ownership --force-conflicts --wait --timeout 90s
STATUS: deployed
REVISION: 1
$ kubectl -n notes-lab get svc other-demo -o jsonpath="{.spec.selector}{\"\n\"}{.metadata.annotations}{\"\n\"}"
{"app.kubernetes.io/instance":"other","app.kubernetes.io/name":"demo"}
{"meta.helm.sh/release-name":"other","meta.helm.sh/release-namespace":"notes-lab"}

接管之后，原来的 selector {"app":"other-demo"} 被整个换成了 Chart 里的值。如果原先有别的 Pod 靠这个 selector 接流量，现在就断了。

还有一个更容易忽略的后果，出现在卸载时。前面那次失败安装后执行 helm uninstall other，Helm 删掉了它建的 ServiceAccount 和 Deployment，保留了 Service，因为 Service 当时还没被接管：

level=WARN msg="skipping delete of resource not owned by this release" kind=Service name=other-demo namespace=notes-lab release=other
1 resource(s) were not deleted because they are not owned by this release:
[Service] other-demo

接管成功之后再卸载，Service 就跟着 Release 一起被删了：

$ helm uninstall other -n notes-lab
release "other" uninstalled
$ kubectl -n notes-lab get svc other-demo
Error from server (NotFound): services "other-demo" not found

卸载

helm uninstall web -n notes-lab --keep-history
helm list -n notes-lab
NAME  NAMESPACE   REVISION  UPDATED                                 STATUS       CHART       APP VERSION
web   notes-lab   19        2026-10-12 15:57:18.88095511 +0800 +08  uninstalled  demo-0.1.0  1.16.0

--keep-history 会删掉全部资源，但保留 Release 的 Secret，最新修订 19 被标为 uninstalled。这时还能 helm rollback web 19 恢复：回滚后 Deployment 重新出现，生成了修订 20 Rollback to 19。

注意上面是不带任何过滤参数的 helm list，已卸载的 Release 也显示出来了。这是 Helm 4 的一处改动：Helm 3 的 helm list 默认只列 deployed 和 failed，Helm 4 默认列出所有状态，-a/--all 参数也删掉了（传了会报 unknown flag），想看部分状态要用 --deployed、--failed、--pending、--uninstalled 等过滤。用 Helm 3 写的脚本如果靠 helm list 判断「是否有正在运行的 Release」，在 Helm 4 下会把已卸载、pending-upgrade 等状态的也算进去。

不带 --keep-history 的 helm uninstall 会连同 Secret 一起清掉，之后 kubectl -n notes-lab get secret -l owner=helm 返回 No resources found。

kubectl delete namespace notes-lab

小结

  • Release 状态就是 namespace 里的 helm.sh/release.v1 Secret，每个修订一个，默认只留 10 个（当前 deployed 的那个总会保留）；helm list、history、rollback 都只是在读写它们。
  • helm template 不连集群，--dry-run=server 能做 lookup，但三者都不会让 API Server 校验对象。
  • -f 后者覆盖前者，map 合并、列表替换；--set 永远最高；升级时一旦传了新 values，上次的就不再沿用。
  • 升级失败不回滚已提交的资源；不加 --wait 的升级只要被 API Server 接受就算成功，这会让 --rollback-on-failure 回到一个坏版本。
  • 卡在 pending-upgrade 时，确认没有别的 Helm 进程在跑，再用 helm rollback 解锁。
