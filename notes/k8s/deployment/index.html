Deployment：管理副本和版本

Deployment 描述一个无状态应用要跑几个副本、每个副本长什么样（Pod 模板），但它自己不创建 Pod：它为每个版本的模板建一个 ReplicaSet，由 ReplicaSet 去维持 Pod 数量。发布新版本时，Deployment 新建一个 ReplicaSet，按更新策略一边扩新的、一边缩旧的。这一篇把这个过程逐秒记录下来，再故意把发布弄坏两次，看卡住时集群里是什么样子。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），实验放在单独的 notes-lab namespace 里。节点名简化成了 worker、worker2，Pod IP 用 <pod-ip> 代替。

准备

保存为 deployment.yaml。镜像用 nginx:alpine，版本号放在环境变量 APP_VERSION 里，改它就能触发一次发布，不用每次都去拉新镜像。就绪探针的 initialDelaySeconds: 5 是故意的：让新 Pod 慢一点就绪，滚动更新的每一步才看得清。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-web
  labels:
    app: demo-web
spec:
  replicas: 4
  selector:
    matchLabels:
      app: demo-web
  template:
    metadata:
      labels:
        app: demo-web
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
          env:
            - name: APP_VERSION
              value: "v1"
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 2
          resources:
            requests:
              cpu: 20m
              memory: 32Mi
            limits:
              memory: 64Mi
kubectl create namespace notes-lab
kubectl -n notes-lab apply -f deployment.yaml
kubectl -n notes-lab rollout status deployment/demo-web
kubectl -n notes-lab get deploy,rs -l app=demo-web
NAME                       READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/demo-web   4/4     4            4           20s

NAME                                  DESIRED   CURRENT   READY   AGE
replicaset.apps/demo-web-6f86b6f6c9   4         4         4       20s

ReplicaSet 名字后缀 6f86b6f6c9 是 Pod 模板的哈希，同时以 pod-template-hash 标签打在 ReplicaSet 的选择器和它的每个 Pod 上，新旧两批 Pod 就靠这个标签区分。三层对象之间靠 ownerReferences 串起来：

$ kubectl -n notes-lab get pod demo-web-6f86b6f6c9-4rqgt -o jsonpath='{.metadata.ownerReferences}'
[{"apiVersion":"apps/v1","blockOwnerDeletion":true,"controller":true,"kind":"ReplicaSet","name":"demo-web-6f86b6f6c9","uid":"a706a35d-..."}]
$ kubectl -n notes-lab get rs demo-web-6f86b6f6c9 -o jsonpath='{.metadata.ownerReferences}'
[{"apiVersion":"apps/v1","blockOwnerDeletion":true,"controller":true,"kind":"Deployment","name":"demo-web","uid":"a2daf5f1-..."}]

别直接改 ReplicaSet

官方文档有一句「Do not manage ReplicaSets owned by a Deployment」。试一下把 ReplicaSet 直接缩到 2：

kubectl -n notes-lab scale rs/demo-web-6f86b6f6c9 --replicas=2

随即再看，DESIRED 已经回到 4，看起来像什么都没发生。但事件记录了全过程：

2026-10-12T04:25:46Z   demo-web-6f86b6f6c9         SuccessfulDelete    Deleted pod: demo-web-6f86b6f6c9-4rqgt
2026-10-12T04:25:46Z   demo-web                    ScalingReplicaSet   Scaled up replica set demo-web-6f86b6f6c9 to 4 from 2
2026-10-12T04:25:46Z   demo-web-6f86b6f6c9         SuccessfulDelete    Deleted pod: demo-web-6f86b6f6c9-f6ch7
2026-10-12T04:25:50Z   demo-web-6f86b6f6c9         SuccessfulCreate    Created pod: demo-web-6f86b6f6c9-5wjqg
2026-10-12T04:25:50Z   demo-web-6f86b6f6c9         SuccessfulCreate    Created pod: demo-web-6f86b6f6c9-w9mvl

ReplicaSet 控制器先执行了缩容，真的删掉了两个 Pod；Deployment 控制器同一秒把副本数改回 4，ReplicaSet 再补建两个新 Pod：

NAME                        READY   STATUS              RESTARTS   AGE
demo-web-6f86b6f6c9-5wjqg   0/1     ContainerCreating   0          4s
demo-web-6f86b6f6c9-bkmhq   1/1     Running             0          35s
demo-web-6f86b6f6c9-lgs9r   1/1     Running             0          35s
demo-web-6f86b6f6c9-w9mvl   0/1     ContainerCreating   0          4s

所以这条命令不是「无效」，而是白白重启了一半副本，有十几秒只剩 2 个 Pod 在服务。补建比删除晚了 4 秒，这次没有深究，推测是 ReplicaSet 控制器要先确认删除生效才会再次计算差额。直接删除单个 Pod 后控制器怎么补齐，见控制器调谐循环。

滚动更新逐秒记录

rollout status 只报告「几个已更新、几个可用」，看不出新旧 Pod 此刻各有几个、哪些在终止。下面这个脚本每秒打印一行：未处于终止中的 Pod 数（active）、Ready 的 Pod 数，以及按模板哈希前 4 位分组的状态：

while true; do
  kubectl -n notes-lab get pods -l app=demo-web -o json | jq -r --arg t "$(date -u +%T)" '
   [.items[] | {h: .metadata.labels["pod-template-hash"][0:4],
     s: (if .metadata.deletionTimestamp then "term"
         elif ([.status.conditions[]?|select(.type=="Ready" and .status=="True")]|length)>0 then "ready"
         else "notready" end)}] as $p
   | ($p|map(select(.s!="term"))|length) as $act | ($p|map(select(.s=="ready"))|length) as $rdy
   | "\($t)  active=\($act) ready=\($rdy)  " + ($p | group_by(.h)
       | map("\(.[0].h)[" + ([group_by(.s)[] | "\(.[0].s)=\(length)"] | join(",")) + "]") | join(" "))'
  sleep 1
done

默认策略是 maxSurge: 25%、maxUnavailable: 25%，progressDeadlineSeconds: 600，revisionHistoryLimit: 10，这几个值都可以在新建的 Deployment 上直接查到。4 个副本时，25% 正好是 1 个。

第一秒控制器就同时用掉了两个额度：新 ReplicaSet 扩到 1（用掉 maxSurge），旧的缩到 3（用掉 maxUnavailable）。紧接着又把新的扩到 2，因为此时总数 5 = 4 + 1，仍在上限之内。之后的节奏完全由新 Pod 什么时候 Ready 决定：04:26:22 创建的 Pod 到 04:26:34 才 Ready，12 秒里有 5 秒是 initialDelaySeconds，其余是建沙箱、启动容器和第一次探测。新 Pod 每 Ready 一个，就腾出一个旧 Pod 的额度。整个过程 active 最多 5、ready 最少 3，正好是 replicas ± 1。

term 那一列也值得注意：旧 Pod 被删除后还要好几秒才真正消失，这段时间它已不算副本，却还在进程退出的路上。它在退出前是否还会收到请求，见优雅终止与流量排空。

发布卡住：镜像标签写错

把 progressDeadlineSeconds 调到 60 秒、策略恢复默认，然后发布一个不存在的标签：

kubectl -n notes-lab patch deployment demo-web -p '{"spec":{"progressDeadlineSeconds":60,"strategy":{"rollingUpdate":{"maxSurge":"25%","maxUnavailable":"25%"}}}}'
kubectl -n notes-lab expose deployment demo-web --port=80
kubectl -n notes-lab set image deployment/demo-web nginx=nginx:1.27-typo
kubectl -n notes-lab rollout status deployment/demo-web
Waiting for deployment "demo-web" rollout to finish: 1 out of 4 new replicas have been updated...
Waiting for deployment "demo-web" rollout to finish: 1 out of 4 new replicas have been updated...
Waiting for deployment "demo-web" rollout to finish: 2 out of 4 new replicas have been updated...
error: deployment "demo-web" exceeded its progress deadline

命令 04:29:20 发出，64 秒后 rollout status 以退出码 1 结束，CI 里可以直接靠这个退出码判失败。逐秒记录从 04:29:23 起就再没变过：

04:29:23  active=5 ready=3  5b8f[notready=2] 5f48[ready=3,term=1]
...
04:30:58  active=5 ready=3  5b8f[notready=2] 5f48[ready=3]

控制器用完两个额度（新的扩到 2、旧的缩到 3）后就停住了：新 Pod 永远不会 Ready，它没有额度再删旧 Pod。

$ kubectl -n notes-lab get deploy,rs -l app=demo-web
NAME                       READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/demo-web   3/4     2            3           5m48s

NAME                                  DESIRED   CURRENT   READY   AGE
replicaset.apps/demo-web-5b8fb5d9dd   2         2         0       106s
replicaset.apps/demo-web-5f4896c4b    3         3         3       2m41s
...
$ kubectl -n notes-lab get pods -l app=demo-web
NAME                        READY   STATUS             RESTARTS   AGE
demo-web-5b8fb5d9dd-99k95   0/1     ImagePullBackOff   0          106s
demo-web-5b8fb5d9dd-jptsk   0/1     ImagePullBackOff   0          104s
demo-web-5f4896c4b-862pq    1/1     Running            0          2m40s
demo-web-5f4896c4b-948bs    1/1     Running            0          2m40s
demo-web-5f4896c4b-hkj67    1/1     Running            0          2m27s

流量这时由 3 个旧 Pod 承担，Service 的 EndpointSlice 里新 Pod 是 ready=false：

demo-web-5f4896c4b-862pq ready=true
demo-web-5f4896c4b-hkj67 ready=true
demo-web-5f4896c4b-948bs ready=true
demo-web-5b8fb5d9dd-99k95 ready=false
demo-web-5b8fb5d9dd-jptsk ready=false

也就是说，坏版本没有造成中断，只是少了 maxUnavailable 那一份容量，而且会一直这样少下去。再看 Deployment 的两个 condition：

Available	True	MinimumReplicasAvailable	2026-10-12T04:26:01Z	Deployment has minimum availability.
Progressing	False	ProgressDeadlineExceeded	2026-10-12T04:30:24Z	ReplicaSet "demo-web-5b8fb5d9dd" has timed out progressing.

Available 仍然是 True，因为 3 个可用副本满足 4 − 1 的最低要求。只监控 Available 的告警会完全错过这次失败，要看的是 Progressing 变成 False 且 reason 为 ProgressDeadlineExceeded。超时之后 Kubernetes 什么也不做：不回滚、不删除坏 Pod，只报告这个状态，回不回滚由人或上层工具决定。时间也对得上：最后一次进展是 04:29:23 新 ReplicaSet 扩到 2，60 秒后的 04:30:24 被判超时。

至于为什么卡，describe deployment 只说新 ReplicaSet 有 2 个副本不可用，原因要到 Pod 上找：

$ kubectl -n notes-lab get pods -l app=demo-web,pod-template-hash=5b8fb5d9dd \
    -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.containerStatuses[0].state.waiting.reason}{"\t"}{.status.containerStatuses[0].state.waiting.message}{"\n"}{end}'
demo-web-5b8fb5d9dd-99k95	ImagePullBackOff	Back-off pulling image "nginx:1.27-typo"
demo-web-5b8fb5d9dd-jptsk	ImagePullBackOff	Back-off pulling image "nginx:1.27-typo"

镜像拉取错误的完整排查见 Pod 与容器。

发布历史与回滚

前面每次发布后都紧跟着给 Deployment 打了 kubernetes.io/change-cause 注解，rollout history 的 CHANGE-CAUSE 列就是从这里复制的。上文的发布命令块里没有逐条写出这一步，照着做时每次发布后补一行，比如：

kubectl -n notes-lab annotate deployment/demo-web kubernetes.io/change-cause='image nginx:alpine, env v2' --overwrite

不打注解的话，CHANGE-CAUSE 列都是 <none>。打了注解后的历史是这样：

$ kubectl -n notes-lab rollout history deployment/demo-web
REVISION  CHANGE-CAUSE
1         <none>
2         APP_VERSION=v2 (default 25%/25%)
3         APP_VERSION=v3 (maxSurge=0,maxUnavailable=1)
4         APP_VERSION=v4 (maxSurge=2,maxUnavailable=0)
5         image nginx:1.27-typo

历史并不单独存放，每个修订就是一个旧 ReplicaSet，修订号写在它的注解里。修订 4 的完整模板：

kubectl -n notes-lab rollout history deployment/demo-web --revision=4

从卡住的镜像发布回滚：

$ kubectl -n notes-lab rollout undo deployment/demo-web
deployment.apps/demo-web rolled back
$ kubectl -n notes-lab get pods -l app=demo-web
NAME                       READY   STATUS    RESTARTS   AGE
demo-web-5f4896c4b-862pq   1/1     Running   0          2m59s
demo-web-5f4896c4b-948bs   1/1     Running   0          2m59s
demo-web-5f4896c4b-hkj67   1/1     Running   0          2m46s
demo-web-5f4896c4b-kpxd5   1/1     Running   0          9s

只用了 11 秒，因为回滚就是把旧 ReplicaSet 5f4896c4b 重新扩回 4，那 3 个一直在服务的旧 Pod 原样保留，只补了 1 个。修订号的变化有点反直觉：

REVISION  CHANGE-CAUSE
1         <none>
2         APP_VERSION=v2 (default 25%/25%)
3         APP_VERSION=v3 (maxSurge=0,maxUnavailable=1)
5         image nginx:1.27-typo
6         APP_VERSION=v4 (maxSurge=2,maxUnavailable=0)

修订 4 消失了，变成了 6。回滚不会退回到某个编号，而是把那个旧模板当作一次新发布，用的还是原来那个 ReplicaSet，所以它拿到新的最大修订号。按编号回滚前要先看清当前编号，后文会演示。

change-cause 会过期

回滚后 Deployment 上的 change-cause 注解被换成了修订 4 当时的文字。接着用最初的 deployment.yaml 执行 kubectl apply：live 对象上的 APP_VERSION 是 v4，文件里是 v1，于是又发生一次发布，回到了修订 1 的模板（ReplicaSet 6f86b6f6c9 被重新启用，变成修订 7）。但历史是这样记的：

6         APP_VERSION=v4 (maxSurge=2,maxUnavailable=0)
7         APP_VERSION=v4 (maxSurge=2,maxUnavailable=0)

修订 7 实际是 v1，CHANGE-CAUSE 却写着 v4。这个注解会从 Deployment 同步到当前的新 ReplicaSet，之后那个 ReplicaSet 不再是「新」的，就不再改动。所以前面「先 set env、再 annotate」也能记对；而这次 6f86b6f6c9 重新成为新 ReplicaSet，拿到的就是 Deployment 上此刻那条 v4 的说明。后面几次发布全都没改注解，历史里连着五行一模一样的说明，基本没法用。要么每次发布都更新它，要么干脆把版本信息放进 Pod 模板的标签或镜像标签里，用 --revision=N 看实际内容。

这次 apply 还说明了另一件事：用 kubectl rollout undo 或 set image 改过线上之后，如果 Git 里的清单没改，下一次 apply 会悄悄把它改回去，并且是一次真正的发布。

哪些改动会触发发布

规则只有一条：当且仅当 .spec.template 变化时才发布。逐项改了一遍，每次记下修订号、ReplicaSet 数和当前有副本的 ReplicaSet：

$ kubectl -n notes-lab scale deployment/demo-web --replicas=3
revision=7 rs=5 current-rs=demo-web-6f86b6f6c9
$ kubectl -n notes-lab annotate deployment/demo-web team=web
$ kubectl -n notes-lab label deployment/demo-web tier=frontend
revision=7 rs=5 current-rs=demo-web-6f86b6f6c9
$ kubectl -n notes-lab patch deployment demo-web -p '{"spec":{"minReadySeconds":3,"progressDeadlineSeconds":120,"revisionHistoryLimit":5}}'
revision=7 rs=5 current-rs=demo-web-6f86b6f6c9
$ kubectl -n notes-lab patch deployment demo-web -p '{"spec":{"template":{"metadata":{"annotations":{"note":"hello"}}}}}'
revision=8 rs=6 current-rs=demo-web-7c49768996
$ kubectl -n notes-lab set resources deployment/demo-web -c nginx --requests=cpu=30m
revision=9 rs=6 current-rs=demo-web-7df7b6b9cb
$ kubectl -n notes-lab rollout restart deployment/demo-web
revision=10 rs=6 current-rs=demo-web-568657878b
改动发布？
scale 改副本数否
Deployment 自身的 label / annotation否
strategy、minReadySeconds、progressDeadlineSeconds、revisionHistoryLimit否（前面改策略时修订号同样没变）
内容不变的 apply（输出 unchanged）否
Pod 模板上的 annotation是
容器的 resources、env、image、探针是
rollout restart是

rollout restart 并没有特殊机制，它只是往模板里写了一个时间戳注解，让模板变了：

{"kubectl.kubernetes.io/restartedAt":"2026-10-12T12:34:21+08:00","note":"hello"}

修改 revisionHistoryLimit: 5 之后，ReplicaSet 数停在了 6 个：5 个旧的加当前的，修订 2、3 对应的 ReplicaSet 被自动删掉，从历史里消失。默认保留 10 个，历史不是无限的。

还有一个改不了的字段。想给选择器加一个标签：

$ kubectl -n notes-lab patch deployment demo-web -p '{"spec":{"selector":{"matchLabels":{"app":"demo-web","track":"stable"}},"template":{"metadata":{"labels":{"app":"demo-web","track":"stable"}}}}}'
The Deployment "demo-web" is invalid: spec.selector: Invalid value: v1.LabelSelector{MatchLabels:map[string]string{"app":"demo-web", "track":"stable"}, MatchExpressions:[]v1.LabelSelectorRequirement(nil)}: field is immutable

apps/v1 里 Deployment 的选择器创建后不可修改，模板标签可以加，但选择器只能删掉 Deployment 重建（或新建一个同标签的 Deployment 再切流量）。选择器怎样匹配 Pod 见标签与选择器。

回到滚动更新：3 个副本时默认策略不会少副本

文档规定 maxSurge 的百分比向上取整，maxUnavailable 向下取整。上一节已经把副本数调到 3、设了 minReadySeconds: 3，策略仍是默认的 25%/25%，再执行一次 kubectl -n notes-lab rollout restart deployment/demo-web：

04:39:59  active=3 ready=3  5686[ready=3]
04:40:00  active=4 ready=3  5686[ready=3] 74f7[notready=1]
...
04:40:08  active=4 ready=4  5686[ready=3] 74f7[ready=1]
04:40:09  active=4 ready=4  5686[ready=3] 74f7[ready=1]
04:40:10  active=4 ready=4  5686[ready=3] 74f7[ready=1]
04:40:12  active=3 ready=3  5686[ready=2,term=1] 74f7[ready=1]

3 × 25% = 0.75，maxSurge 取 1，maxUnavailable 取 0，所以默认策略在 3 副本时等价于「先加一个、再删一个」，ready 始终 ≥3。04:40:08 新 Pod 已经 Ready，旧 Pod 却到 04:40:12 才被删，中间这几秒就是 minReadySeconds：Pod Ready 后还要持续 3 秒不出问题才算 available，控制器只认 available。

发布卡住：就绪探针写错

另一种更隐蔽：镜像没问题，容器正常运行，只是就绪探针路径写成了应用不提供的 /healthz。为了少等，先把期限调到 45 秒：

kubectl -n notes-lab patch deployment demo-web -p '{"spec":{"progressDeadlineSeconds":45}}'
kubectl -n notes-lab patch deployment demo-web --type=json \
  -p '[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/healthz"}]'
kubectl -n notes-lab annotate deployment/demo-web kubernetes.io/change-cause='readiness path /healthz' --overwrite

此时副本数是 3，默认策略只会多建 1 个新 Pod：

NAME                            READY   STATUS    RESTARTS   AGE
pod/demo-web-654d69949d-6m9dh   0/1     Running   0          2m33s
pod/demo-web-74f7b478b4-4wpl4   1/1     Running   0          3m24s
pod/demo-web-74f7b478b4-6k9h5   1/1     Running   0          3m39s
pod/demo-web-74f7b478b4-86vwt   1/1     Running   0          3m8s

STATUS 是 Running，RESTARTS 是 0，get pods 看不出任何报错，原因只在事件里（下面的 describe 比上面的 get pods 晚一分多钟采集，所以 Age 对不上）：

Normal   Started    3m46s                kubelet            Started container nginx
Warning  Unhealthy  3m (x22 over 3m42s)  kubelet            Readiness probe failed: HTTP probe failed with statuscode: 404

这次 3 个旧副本一个都没少，用户完全无感。危险在于它可能被当成「发布还在进行」一直挂着。

一次没有超时的发布

第一次做这个实验时，progressDeadlineSeconds 设的是 45 秒，可 rollout status 等了将近三分钟还没退出。看 condition：

04:43:45
45
Available	True	MinimumReplicasAvailable	2026-10-12T04:26:01Z	2026-10-12T04:26:01Z	Deployment has minimum availability.
Progressing	True	NewReplicaSetAvailable	2026-10-12T04:40:46Z	2026-10-12T04:31:16Z	ReplicaSet "demo-web-74f7b478b4" has successfully progressed.

新 ReplicaSet 早在 04:41:06 就建好了，Progressing 却还停在上一次发布成功的状态，提到的还是旧 ReplicaSet。翻 v1.31 的控制器源码，判断是否超时的 DeploymentTimedOut 里有一段：如果 Progressing 的 reason 是 NewReplicaSetAvailable，直接返回不超时。源码注释描述的正是这种场景：新 ReplicaSet 创建后触发的那次同步，用的是还没带上「已创建新 ReplicaSet」condition 的缓存副本；注释的预期是后续同步会让 condition 追上来。

能不能追上，取决于 DeploymentProgressing：它拿新算出的计数（updated、ready、available、待缩容的旧副本）和上一次写进 status 的值比较，有一项变好才刷新 condition。上一次写入的是刚发布完成的 updatedReplicas=3，这次新 ReplicaSet 只有 1 个 Pod，1 不比 3 大；这个 Pod 又始终不 Ready，其他几项也没变好。于是 condition 一直不刷新，超时检查也就一直被跳过。

随后每次先 rollout undo 回到正常版本，再重做了三次：两次复用这个 ReplicaSet（一次不带 annotate、一次带），一次把路径换成 /healthz2 新建 ReplicaSet（期限顺手改成 46 秒）。三次 condition 都在 2 秒内变成 ReplicaSetUpdated 或 NewReplicaSetCreated，到期后按时变成 ProgressDeadlineExceeded。最后一次：

04:47:30
True NewReplicaSetCreated 2026-10-12T04:47:24Z Created new replica set "demo-web-67699587b6"
04:48:25
False ProgressDeadlineExceeded 2026-10-12T04:48:11Z ReplicaSet "demo-web-67699587b6" has timed out progressing.

第一次为什么没刷新，没能复现，也没找到直接证据，推测是创建 ReplicaSet 后写入「NewReplicaSetCreated」的那次状态更新没有成功（比如和紧随其后的 kubectl annotate 冲突），之后的同步又没有任何计数变化可以触发更新。不管原因，结论是：别把「发布失败」的判断完全交给 progressDeadlineSeconds，CI 里给 rollout status 再加一个 --timeout 兜底。

按修订号回滚

最后一次重做之后，发布仍卡在 /healthz2。这时想用编号回到最初的 v1：

$ kubectl -n notes-lab rollout undo deployment/demo-web --to-revision=1
error: unable to find specified revision 1 in history

修订 1 的 ReplicaSet 早在前面那次 apply 时被重新启用、编号成了 7，之后又经过多次回滚重做，修订号整体一直在往上涨。不确定回滚到哪个修订时，可以先用 --dry-run=server 看会得到什么模板：

$ kubectl -n notes-lab rollout undo deployment/demo-web --to-revision=9 --dry-run=server \
    -o jsonpath='{.spec.template.spec.containers[0].resources.requests}'
{"cpu":"30m","memory":"32Mi"}

刚回滚完，rollout status 可能误报失败

确认无误后执行 kubectl -n notes-lab rollout undo deployment/demo-web --to-revision=9，紧接着跑 rollout status：

deployment.apps/demo-web rolled back
Waiting for deployment spec update to be observed...
Waiting for deployment spec update to be observed...
error: deployment "demo-web" exceeded its progress deadline

回滚其实正在正常进行，几秒后再跑一次，rollout status 等了约 40 秒后报告 successfully rolled out。第一次读到的是还没被刷新的 ProgressDeadlineExceeded。同样是从超时状态回滚，前面镜像那次和几次重做之间的回滚都没遇到。原因没有直接测到，有两种推测：

  • 时序：rollout status 看到 observedGeneration 已追上，但 condition 还没写回。不过 v1.31 的 syncRolloutStatus 是在同一次状态写入里同时更新这两者的，这种可能性较低。
  • 和上一节同一个比较逻辑：这次回到的修订 9（7df7b6b9cb）当时是 0 个 Pod，第一次同步只是把它扩上去，计数没有任何一项变好，condition 就保持 ProgressDeadlineExceeded；而其他几次回到的 ReplicaSet 手上都有 Ready 的 Pod，一同步 updated 计数就立刻变大，算作有进展。

不管哪种，脚本里回滚后如果马上判断成败，要容忍这一次误报，或者稍等再查。

清理

kubectl delete namespace notes-lab

滚动更新只保证副本数在 maxSurge/maxUnavailable 范围内变化；节点维护时驱逐 Pod 不走这套规则，要靠 PodDisruptionBudget 保护。下一篇用 Service 给这组 Pod 一个稳定入口。
