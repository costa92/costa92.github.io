Downward API 与 Pod 元数据

应用有时需要知道自己在哪个 Pod、命名空间或节点上运行，或者自己被分到了多少 CPU。Downward API 可以把受支持的自身字段作为环境变量或卷文件交给容器，不必为此授予访问 Kubernetes API 的权限。它和 ConfigMap、Secret 的注入方式（环境变量、整卷、subPath）几乎一样，区别在数据来源：这里来自当前 Pod 和容器本身。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），实验放在单独的 notes-lab namespace 里。节点名简化成了 worker，Pod IP 和节点 IP 分别用 <pod-ip>、<host-ip> 代替。

一个 Pod 读出所有字段

实验 Pod 有两个容器：app 设了 requests 和 limits，sidecar 什么资源都没设，用来对照「没有 limit 时读到什么」。app 的环境变量把 fieldRef 能引用的字段几乎都列了一遍，再用 resourceFieldRef 读自己和 sidecar 的资源值。保存为 dapi-demo.yaml（中间重复的 resourceFieldRef 条目省略了一部分）：

apiVersion: v1
kind: Pod
metadata:
  name: dapi-demo
  labels:
    app: dapi-demo
    track: stable
  annotations:
    notes-lab.io/owner: team-a
spec:
  containers:
    - name: app
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          last=""
          while true; do
            now="env=$TRACK vol=$(grep track /etc/podinfo/labels) sub=$(grep track /etc/sub/labels)"
            [ "$now" != "$last" ] && echo "$(date -u +%T) $now" && last="$now"
            sleep 1
          done
      env:
        - name: POD_NAME
          valueFrom: {fieldRef: {fieldPath: metadata.name}}
        - name: POD_NAMESPACE
          valueFrom: {fieldRef: {fieldPath: metadata.namespace}}
        - name: POD_UID
          valueFrom: {fieldRef: {fieldPath: metadata.uid}}
        - name: NODE_NAME
          valueFrom: {fieldRef: {fieldPath: spec.nodeName}}
        - name: SA_NAME
          valueFrom: {fieldRef: {fieldPath: spec.serviceAccountName}}
        - name: POD_IP
          valueFrom: {fieldRef: {fieldPath: status.podIP}}
        - name: POD_IPS
          valueFrom: {fieldRef: {fieldPath: status.podIPs}}
        - name: HOST_IP
          valueFrom: {fieldRef: {fieldPath: status.hostIP}}
        - name: TRACK
          valueFrom: {fieldRef: {fieldPath: "metadata.labels['track']"}}
        - name: OWNER
          valueFrom: {fieldRef: {fieldPath: "metadata.annotations['notes-lab.io/owner']"}}
        - name: MISSING_LABEL
          valueFrom: {fieldRef: {fieldPath: "metadata.labels['no-such-key']"}}
        - name: CPU_LIMIT
          valueFrom: {resourceFieldRef: {resource: limits.cpu}}
        - name: CPU_LIMIT_M
          valueFrom: {resourceFieldRef: {resource: limits.cpu, divisor: 1m}}
        - name: MEM_REQUEST
          valueFrom: {resourceFieldRef: {resource: requests.memory}}
        - name: MEM_REQUEST_MI
          valueFrom: {resourceFieldRef: {resource: requests.memory, divisor: 1Mi}}
        - name: SIDE_CPU_LIMIT
          valueFrom: {resourceFieldRef: {containerName: sidecar, resource: limits.cpu}}
        - name: SIDE_MEM_LIMIT
          valueFrom: {resourceFieldRef: {containerName: sidecar, resource: limits.memory}}
        # CPU_REQUEST / CPU_REQUEST_M / MEM_LIMIT_MI / SIDE_CPU_LIMIT_M / SIDE_CPU_REQUEST_M 同理
      resources:
        requests: {cpu: 50m, memory: 32Mi}
        limits: {cpu: 200m, memory: 64Mi}
      volumeMounts:
        - name: podinfo
          mountPath: /etc/podinfo
        - name: podinfo
          mountPath: /etc/sub/labels
          subPath: labels
    - name: sidecar
      image: busybox:1.36
      command: ["sleep", "3600"]
  volumes:
    - name: podinfo
      downwardAPI:
        items:
          - path: labels
            fieldRef: {fieldPath: metadata.labels}
          - path: annotations
            fieldRef: {fieldPath: metadata.annotations}
          - path: name
            fieldRef: {fieldPath: metadata.name}
          - path: cpu_limit_m
            resourceFieldRef: {containerName: app, resource: limits.cpu, divisor: 1m}
kubectl create namespace notes-lab
kubectl -n notes-lab apply -f dapi-demo.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/dapi-demo --timeout=120s
kubectl -n notes-lab exec dapi-demo -c app -- sh -c 'env | sort | grep -E "^(POD_|NODE_|SA_|HOST_|TRACK|OWNER|MISSING|CPU_|MEM_|SIDE_)"'
CPU_LIMIT=1
CPU_LIMIT_M=200
CPU_REQUEST=1
CPU_REQUEST_M=50
HOST_IP=<host-ip>
MEM_LIMIT_MI=64
MEM_REQUEST=33554432
MEM_REQUEST_MI=32
MISSING_LABEL=
NODE_NAME=worker
OWNER=team-a
POD_IP=<pod-ip>
POD_IPS=<pod-ip>
POD_NAME=dapi-demo
POD_NAMESPACE=notes-lab
POD_UID=1bab05aa-a373-4e0a-849f-3690c68ddaaa
SA_NAME=default
SIDE_CPU_LIMIT=28
SIDE_CPU_LIMIT_M=28000
SIDE_CPU_REQUEST_M=0
SIDE_MEM_LIMIT=65873432576
TRACK=stable

fieldRef 这一组没什么意外，和 kubectl get pod -o jsonpath 读到的 uid、节点名、IP 一一对应。POD_IPS 是单栈集群，所以只有一个地址；双栈时这里是逗号分隔的两个。值得留意的是下面几处。

不存在的标签键：变量被设成空字符串

metadata.labels['no-such-key'] 引用了一个不存在的键，Pod 照常启动，MISSING_LABEL 出现在了 env 输出里，值为空：

$ kubectl -n notes-lab exec dapi-demo -c app -- sh -c 'env | grep -c MISSING_LABEL; echo "[${MISSING_LABEL-unset}]"'
1
[]

不带冒号的 ${MISSING_LABEL-unset} 没有走默认值，说明变量确实被设置了，只是为空。这和 ConfigMap 的 optional: true 不一样，那边键缺失时变量根本不会被设置。应用里如果用「变量是否存在」判断有没有配置，这里会误判，应该判断是否为空。

CPU 不加 divisor 会向上取整

app 的 CPU limit 是 200m、request 是 50m，不写 divisor 时读到的都是 1。divisor 默认是 1，也就是以「核」为单位。kubelet 换算时做的是向上取整：pkg/api/v1/resource/helpers.go 里按 math.Ceil(值 / divisor) 计算，0.2 核和 0.05 核都变成了 1。这个规则对卷文件和内存同样适用。写上 divisor: 1m 才拿到 200 和 50。

这在实际中很容易踩：程序按 CPU_LIMIT 设置工作线程数时，200m 和 1 核会得到同样的结果。按 CPU 调线程数（比如 Go 的 GOMAXPROCS），应该用 divisor: 1m 读毫核，再自己决定怎么取整。

内存默认以字节为单位，MEM_REQUEST=33554432 就是 32Mi，写 divisor: 1Mi 后变成 32；如果 request 不是 1Mi 的整数倍，同样会被向上取整。CPU 的 divisor 只能是 1m 或 1，后面复现了写成 10m 时的报错。

没设 limit：读到的是节点 allocatable

sidecar 没有设 limits，SIDE_CPU_LIMIT=28、SIDE_MEM_LIMIT=65873432576。对照它所在节点：

$ kubectl get node worker -o jsonpath='capacity: cpu={.status.capacity.cpu} memory={.status.capacity.memory}{"\n"}allocatable: cpu={.status.allocatable.cpu} memory={.status.allocatable.memory}{"\n"}'
capacity: cpu=28 memory=64329524Ki
allocatable: cpu=28 memory=64329524Ki

64329524Ki × 1024 = 65873432576 字节，正好对上。官方文档写明：容器没有设置 CPU 和内存 limit 时，Downward API 返回节点的最大可分配值（node allocatable）。kind 节点没有配置资源预留，所以 allocatable 和 capacity 相同；生产节点一般会预留一部分给系统和 kubelet，读到的会比物理规格小。

这意味着「读 limit 来决定开多少线程、用多大缓存」的程序，在没设 limit 的 Pod 里会以为自己独占整台机器。request 则没有这个回退，没设就是 0（SIDE_CPU_REQUEST_M=0）。

卷里的文件

$ kubectl -n notes-lab exec dapi-demo -c app -- sh -c 'ls -la /etc/podinfo/; mount | grep -E "podinfo|/etc/sub"'
total 4
drwxrwxrwt    3 root     root           160 Oct 13 01:34 .

lrwxrwxrwx    1 root     root            18 Oct 13 01:34 annotations -> ..data/annotations
lrwxrwxrwx    1 root     root            18 Oct 13 01:34 cpu_limit_m -> ..data/cpu_limit_m
lrwxrwxrwx    1 root     root            13 Oct 13 01:34 labels -> ..data/labels
lrwxrwxrwx    1 root     root            11 Oct 13 01:34 name -> ..data/name
tmpfs on /etc/podinfo type tmpfs (ro,relatime,size=64329524k,inode64,noswap)
tmpfs on /etc/sub/labels type tmpfs (ro,relatime,size=64329524k,inode64,noswap)

结构和 ConfigMap 卷相同：每个文件是符号链接，经过 ..data 指向一个带时间戳的目录，更新时 kubelet 写好新目录再切换 ..data。不同的是它挂在只读的 tmpfs 上（ConfigMap 卷在节点磁盘上）。tmpfs 的 size=64329524k 恰好等于节点 allocatable 内存（kind 节点没有资源预留，也等于 capacity）。原因在 kubelet 源码里：downwardAPI 卷内部包了一个 medium: Memory 的 emptyDir（downwardapi.go 里的 wrappedVolumeSpec），而 empty_dir.go 的 calculateEmptyDirMemorySize 用 Pod 的内存 limit 作为 tmpfs 大小，Pod 没有内存上限时退回节点 allocatable。这个 Pod 的 sidecar 没设内存 limit，Pod 整体就没有上限；配置那篇 里 Secret 卷的 tmpfs 大小等于 Pod 的内存 limit，是同一套逻辑。这个行为受 SizeMemoryBackedVolumes 特性门控制，在 v1.31 是 Beta、默认开启。

文件内容是 key="value" 每行一条：

== labels
app="dapi-demo"
track="stable"
== annotations
cni.projectcalico.org/containerID="858a8f61e8a8..."
cni.projectcalico.org/podIP="<pod-ip>/32"
cni.projectcalico.org/podIPs="<pod-ip>/32"
kubectl.kubernetes.io/last-applied-configuration="{\"apiVersion\":\"v1\",\"kind\":\"Pod\", ...（整份 Pod 定义）"
kubernetes.io/config.seen="2026-10-13T01:34:15.132993679Z"
kubernetes.io/config.source="api"
notes-lab.io/owner="team-a"
== name
dapi-demo
== cpu_limit_m
200

annotations 文件里只有一条是我写的。Calico 写进去的 Pod IP、kubelet 加的 config.seen/config.source，还有 kubectl apply 留下的 last-applied-configuration（整份 Pod 定义转成的 JSON，占了这个 4086 字节文件的绝大部分），全都在。应用按行解析时别假设只有自己的注解，grep owner 也会误中 last-applied-configuration 那一行（它里面含有 notes-lab.io/owner），要匹配完整的 notes-lab.io/owner=。只需要一两个注解的话，用 metadata.annotations['<key>'] 单独投射成文件更干净。

改标签之后：只有整卷文件会变

同一个标签 track 用三种方式读：环境变量 TRACK、整卷文件 /etc/podinfo/labels、subPath 单独挂载的 /etc/sub/labels。容器每秒读一次，有变化才打印带时间的一行。为了让计时干净，单独用一个小 Pod 来测，保存为 watch-demo.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: watch-demo
  labels:
    track: stable
spec:
  containers:
    - name: app
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          last=""
          while true; do
            now="env=$TRACK vol=$(grep track /etc/podinfo/labels) sub=$(grep track /etc/sub/labels)"
            [ "$now" != "$last" ] && echo "$(date -u +%T) $now" && last="$now"
            sleep 1
          done
      env:
        - name: TRACK
          valueFrom: {fieldRef: {fieldPath: "metadata.labels['track']"}}
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 32Mi}
      volumeMounts:
        - {name: podinfo, mountPath: /etc/podinfo}
        - {name: podinfo, mountPath: /etc/sub/labels, subPath: labels}
  volumes:
    - name: podinfo
      downwardAPI:
        items:
          - path: labels
            fieldRef: {fieldPath: metadata.labels}

每隔十几秒改一次标签，改之前打印时间：

date -u +%T.%N; kubectl -n notes-lab label pod watch-demo track=v2 --overwrite

四次 label 分别在 02:53:06.21、02:53:18.36、02:53:30.45、02:53:43.16 发出，容器日志：

$ kubectl -n notes-lab logs watch-demo
02:52:53 env=stable vol=track="stable" sub=track="stable"
02:53:07 env=stable vol=track="v2" sub=track="stable"
02:53:18 env=stable vol=track="v3" sub=track="stable"
02:53:31 env=stable vol=track="v4" sub=track="stable"
02:53:44 env=stable vol=track="v5" sub=track="stable"

每次都在 1–2 秒内落地，也就是容器下一次采样就读到了；日志时间只精确到秒，没法测得更细。环境变量和 subPath 文件从头到尾都是 stable。

这和 ConfigMap 卷差别很大：配置那篇 里同一个集群的 ConfigMap 卷要 52–63 秒才更新，配置那篇推测是在等 kubelet 下一轮周期性 Pod 同步。Downward API 快，是因为改标签改的就是 Pod 对象本身：kubelet watch 到 Pod 更新会马上对这个 Pod 执行一次 syncPod，而 volume_manager.go 的 WaitForAttachAndMount 在每次 syncPod 时都会调用 ReprocessPod（源码注释写的是 “Atomically updating volumes, like Downward API, depend on this”），downwardapi.go 的 RequiresRemount 又返回 true，于是卷当场按新的 Pod 对象重写。改注解同样是更新 Pod 对象，注解文件和配置那篇里「改 Pod 注解能立刻刷新 ConfigMap 卷」走的都是这条路径；实测中把 notes-lab.io/owner 改成 team-c 后，OWNER 环境变量仍是 team-a。

subPath 不更新，官方文档对 downwardAPI 卷有明确说明：以 subPath 挂载的容器收不到字段变化。原因和 ConfigMap 一样，subPath 在容器创建时绑定到当时那个时间戳目录里的文件，之后 ..data 怎么切都和它无关。

容器重启后两者都拿到新值

和 ConfigMap 一样，环境变量和 subPath 在容器重新创建时重新解析，Pod 内的容器重启也算，不必删 Pod，细节和 subPath 重启时可能出现的 StartError 见 配置那篇。这里用一个每 20 秒退出一次、restartPolicy: Always 的容器验证：02:47:34 启动时读到 stable，02:47:35 把标签改成 canary，下一次重启（02:47:56）三处就都是新值了：

02:47:56 env=canary vol=track="canary" sub=track="canary"

之后又改了一次标签，几次重启中 Warning 事件只有 BackOff，没有挂载失败。

注入方式改 Pod 标签/注解后何时读到新值
环境变量 fieldRef不变容器重新创建时
整卷挂载本次实测 1–2 秒内更新立即；应用还得自己重新读文件
subPath 挂载不变容器重新创建时

字段写错时会怎样

按官方文档，字段分三类：metadata.name、namespace、uid 以及 metadata.labels['<KEY>']、metadata.annotations['<KEY>'] 两种方式都能用；spec.nodeName、spec.serviceAccountName、status.hostIP(s)、status.podIP(s) 只能做环境变量；整个 metadata.labels、metadata.annotations 只能做卷文件。故意写错七处，用 --dry-run=server 让 API Server 校验而不真正创建：

kubectl -n notes-lab apply --dry-run=server -f bad-labels-env.yaml

整个 labels 当环境变量（fieldPath: metadata.labels）：

The Pod "bad-labels-env" is invalid: spec.containers[0].env[0].valueFrom.fieldRef.fieldPath: Unsupported value: "metadata.labels": supported values: "metadata.name", "metadata.namespace", "metadata.uid", "spec.nodeName", "spec.serviceAccountName", "status.hostIP", "status.hostIPs", "status.podIP", "status.podIPs"

报错列出的「支持值」里没有 metadata.labels['<KEY>']，但前面 TRACK 已经证明带下标的写法可以做环境变量，别被这个列表误导。原因在校验代码：validateObjectFieldSelector 先用 SplitMaybeSubscriptedPath 把带下标的路径拆成 metadata.labels 加键名，再单独判断，列表里自然只有不带下标的字段。

Pod IP 放进卷（卷的 fieldRef: {fieldPath: status.podIP}）：

The Pod "bad-podip-vol" is invalid: 
* spec.volumes[0].downwardAPI.fieldRef.fieldPath: Unsupported value: "status.podIP": supported values: "metadata.annotations", "metadata.labels", "metadata.name", "metadata.namespace", "metadata.uid"
* spec.containers[0].volumeMounts[0].name: Not found: "podinfo"

卷里的 resourceFieldRef 没写 containerName：

The Pod "bad-res-vol" is invalid: 
* spec.volumes[0].downwardAPI.resourceFieldRef.containerName: Required value
* spec.containers[0].volumeMounts[0].name: Not found: "podinfo"

后两例的第二条 volumeMounts[0].name: Not found 是连带错误：卷本身校验失败，挂载它的 volumeMounts 就找不到卷了，真正要修的是第一条。环境变量里的 containerName 可以省略，默认是当前容器；卷不属于任何容器，所以必须写。

CPU 的 divisor 写成 10m：

The Pod "bad-divisor" is invalid: spec.containers[0].env[0].valueFrom.resourceFieldRef.divisor: Invalid value: "limits.cpu": only divisor's values 1m and 1 are supported with the cpu resource

字段路径指向 divisor，但 Invalid value 显示的却是 limits.cpu，不是我写的 10m：校验代码调用 field.Invalid(..., rName, ...) 时传入的是资源名而不是 divisor 的值。看报错时以后半句为准。

字段名大小写写错（spec.nodename）和下标没加引号（metadata.labels[track]）：

The Pod "bad-typo" is invalid: spec.containers[0].env[0].valueFrom.fieldRef.fieldPath: Invalid value: "spec.nodename": error converting fieldPath: field label not supported: spec.nodename
The Pod "bad-label-key" is invalid: spec.containers[0].env[0].valueFrom.fieldRef.fieldPath: Invalid value: "metadata.labels[track]": error converting fieldPath: field label not supported: metadata.labels[track]

字段路径区分大小写，标签键必须写成 metadata.labels['track']，YAML 里整个值要再用双引号包起来。

唯一通过校验的错误：containerName 写错

第七个文件把环境变量里的 containerName 写成了不存在的 nope，--dry-run=server 却通过了：

pod/bad-container created (server dry run)

真正创建后，25 秒时：

NAME            READY   STATUS                       RESTARTS   AGE
bad-container   0/1     CreateContainerConfigError   0          25s
TYPE      REASON      COUNT    MSG
Normal    Scheduled   <none>   Successfully assigned notes-lab/bad-container to worker2
Normal    Pulled      4        Container image "busybox:1.36" already present on machine
Warning   Failed      4        Error: container nope not found

API Server 不检查环境变量里的 containerName 是否真的存在，错误推迟到 kubelet 生成容器配置时才暴露，状态是 CreateContainerConfigError，和 ConfigMap 引用缺失时一样，见 配置那篇。也就是说，CI 里只靠 --dry-run=server 发现不了这类拼写错误；改容器名时要顺手搜一遍 containerName。

小结

  • 只关心「我是谁、在哪」：用环境变量，简单，启动后也不会变。
  • 要感知标签、注解的变化：用整卷挂载并让应用重新读文件，实测 1–2 秒内更新；不要用 subPath。
  • 读资源值：CPU 一律写 divisor: 1m；容器没设 limit 时读到的是节点 allocatable，资源限制的设置见 探针与资源管理。
  • Downward API 只暴露上面列出的字段，要读其他 Pod 或对象，得用 ServiceAccount 访问 API，见 ServiceAccount 与 RBAC。

清理

kubectl delete namespace notes-lab
