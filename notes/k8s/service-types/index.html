Service 类型与 NodePort

ClusterIP Service 只在集群内部可达，选择器、EndpointSlice、iptables 随机分发这些基础在那一篇里已经测过。这一篇看另外几种类型：NodePort 在每个节点上开一个端口，LoadBalancer 在 NodePort 之上再请求一个外部入口，ExternalName 只是一条 DNS 别名。另外几个和对外暴露有关的字段，externalTrafficPolicy、internalTrafficPolicy、sessionAffinity，也一起实测。需要直接拿到每个 Pod 地址的场景看 Headless Service，HTTP 路由看 Ingress。

类型结果使用前提
ClusterIP集群内部虚拟 IP默认类型
NodePortClusterIP 之外，每个节点再开一个端口转发到后端客户端能到达节点网络
LoadBalancerNodePort 之外，再请求一个外部负载均衡入口集群里有负载均衡实现（云厂商控制器、MetalLB、cloud-provider-kind 等）
ExternalName集群 DNS 返回一条 CNAME不分配 ClusterIP，不做任何转发

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico，kube-proxy 为 iptables 模式；集群里用 Helm 在 traefik namespace 装了 Traefik，带一个 LoadBalancer 类型的 Service 和 IngressClass traefik）。kind 的节点是宿主机上的 Docker 容器，宿主机通过一块 Docker 网桥直接连到各节点的 IP。节点名简化成 control-plane、worker、worker2；节点 IP 写作 <worker-ip>、<worker2-ip>、<control-plane-ip>，宿主机在这块网桥上的地址写作 <host-bridge-ip>，其他 IP 也都换成了占位符。实验 namespace 在文中统一写作 notes-lab。

实验准备

关键是让「有后端的节点」和「没有后端的节点」分得开：whoami 后端用 nodeSelector 固定在 worker 上，两个客户端 Pod 分别放在 worker 和 worker2。whoami 会在响应里打印 Hostname（Pod 名）和 RemoteAddr（它看到的 TCP 对端地址），后面判断源 IP 全靠它。保存为 base.yaml，节点名按自己的集群改：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      nodeSelector:
        kubernetes.io/hostname: <集群名>-worker
      containers:
        - name: whoami
          image: traefik/whoami:v1.10.2
          ports:
            - name: http
              containerPort: 80
          resources:
            requests:
              cpu: 20m
              memory: 32Mi
            limits:
              memory: 64Mi
---
apiVersion: v1
kind: Pod
metadata:
  name: client-w2
spec:
  nodeSelector:
    kubernetes.io/hostname: <集群名>-worker2
  containers:
    - name: curl
      image: curlimages/curl:latest
      command: ["sleep", "3600"]
---
# client-w1 与 client-w2 相同，只是 nodeSelector 指向 worker
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f base.yaml
kubectl -n notes-lab get pod -o wide
NAME                   READY   STATUS    RESTARTS   AGE   IP                NODE
client-w1              1/1     Running   0          38s   <client-w1-ip>    worker
client-w2              1/1     Running   0          40s   <client-w2-ip>    worker2
web-849d9b5bd4-h4tvn   1/1     Running   0          40s   <h4tvn-ip>        worker

NodePort：端口怎么分配

两个 NodePort Service，一个让系统自动分配，一个手工指定 nodePort: 31987：

apiVersion: v1
kind: Service
metadata:
  name: web-np
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - name: http
      port: 80
      targetPort: http
---
apiVersion: v1
kind: Service
metadata:
  name: web-fixed
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - name: http
      port: 80
      targetPort: http
      nodePort: 31987
NAME        TYPE       CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
web-fixed   NodePort   <cluster-ip>   <none>        80:31987/TCP   1s
web-np      NodePort   <cluster-ip>   <none>        80:31926/TCP   2s

80:31926 冒号前是 Service 端口，后面是分到的节点端口。NodePort 并没有取代 ClusterIP，web-np 照样有一个 ClusterIP，kubectl get svc web-np -o yaml 里还能看到默认补上的两个字段：

externalTrafficPolicy: Cluster
internalTrafficPolicy: Cluster

三种分配失败

再故意建三个 Service，分别抢已占用的 31987、用范围外的 29999、用另一个 namespace 里 traefik 已经占着的 30825（自己复现时，换成你集群里任何已被占用的 nodePort）：

The Service "web-fixed2" is invalid: spec.ports[0].nodePort: Invalid value: 31987: provided port is already allocated
The Service "web-low" is invalid: spec.ports[0].nodePort: Invalid value: 29999: provided port is not in the valid range. The range of valid ports is 30000-32767
The Service "web-tr" is invalid: spec.ports[0].nodePort: Invalid value: 30825: provided port is already allocated

几点信息：

  • 校验发生在 API Server，对象根本创建不出来，不会出现「Service 建好了但端口不通」的中间状态。
  • 第三条说明 NodePort 是整个集群的资源，跨 namespace 也会冲突。报错里只说 already allocated，不告诉你被谁占了，要自己查：kubectl get svc -A | grep 30825。
  • 范围由 API Server 的 --service-node-port-range 决定。这个集群的 kube-apiserver 没有设置该参数，报错里的 30000-32767 就是默认值。

手工指定端口最怕和自动分配撞车。官方文档的做法是把范围切成两段：默认范围下 30000-30085 是静态段，自动分配优先使用 30086-32767，上段用完才会占静态段。所以要手工固定端口，挑 30000-30085 里的值冲突风险最小（这条是文档内容，这次没有把动态段耗尽去验证）。

NodePort：从哪里能访问

从宿主机访问，没有后端的节点也行

节点 IP 用 docker inspect 查：

docker inspect -f '{{.Name}} {{range .NetworkSettings.Networks}}{{.IPAddress}} gw={{.Gateway}}{{end}}' \
  <集群名>-worker <集群名>-worker2 <集群名>-control-plane
/worker <worker-ip> gw=<host-bridge-ip>
/worker2 <worker2-ip> gw=<host-bridge-ip>
/control-plane <control-plane-ip> gw=<host-bridge-ip>

在宿主机上分别请求三个节点的 31926：

$ curl -s -m 5 http://<worker-ip>:31926/ | grep -E 'Hostname|RemoteAddr'
Hostname: web-849d9b5bd4-h4tvn
RemoteAddr: <worker-ip>:25155
$ curl -s -m 5 http://<worker2-ip>:31926/ | grep -E 'Hostname|RemoteAddr'
Hostname: web-849d9b5bd4-h4tvn
RemoteAddr: <worker2-ip>:34615
$ curl -s -m 5 http://<control-plane-ip>:31926/ | grep -E 'Hostname|RemoteAddr'
Hostname: web-849d9b5bd4-h4tvn
RemoteAddr: <control-plane-ip>:16237

三个节点都能通，包括没有 whoami Pod 的 worker2 和控制平面节点。kube-proxy 在每个节点上都为 NodePort 装了规则，打到哪个节点都会被转给唯一的后端。

更值得注意的是 RemoteAddr：whoami 看到的源地址不是宿主机 <host-bridge-ip>，而是接收请求的那个节点的 IP。连请求本来就落在后端所在节点 worker 上时，源地址也被改成了 <worker-ip>。节点上的规则解释了原因：

docker exec <集群名>-worker2 iptables-save -t nat | grep 'notes-lab/web-np'
-A KUBE-EXT-U26NTG6KVUAZ4QZZ -m comment --comment "masquerade traffic for notes-lab/web-np:http external destinations" -j KUBE-MARK-MASQ
-A KUBE-NODEPORTS -d 127.0.0.0/8 -p tcp -m comment --comment "notes-lab/web-np:http" -m tcp --dport 31926 -m nfacct --nfacct-name  localhost_nps_accepted_pkts -j KUBE-EXT-U26NTG6KVUAZ4QZZ
-A KUBE-NODEPORTS -p tcp -m comment --comment "notes-lab/web-np:http" -m tcp --dport 31926 -j KUBE-EXT-U26NTG6KVUAZ4QZZ

externalTrafficPolicy: Cluster 下，所有从 NodePort 进来的流量都先打上 KUBE-MARK-MASQ，再在 POSTROUTING 做 SNAT；请求即使正好落在后端所在的节点上也一样会被改写。好处是任何节点都能转发、回包一定原路返回；代价是后端拿不到真实客户端 IP。按 IP 限流、记录访问日志、做白名单的应用，在这种模式下看到的全是节点 IP。

节点上并没有进程在监听这个端口

$ docker exec <集群名>-worker2 sh -c 'ss -ltnp | grep 31926; echo rc=$?'
rc=1

ss 里找不到 31926。iptables 模式下 NodePort 只是 nat 表里的一条匹配规则，内核在 PREROUTING 阶段就把包改写了，不需要任何用户态进程监听。所以用 ss/netstat 检查「NodePort 有没有起来」是查不到的，要看 iptables-save。上面第二条规则还表明节点自己的 127.0.0.1 也能访问 NodePort，实测 docker exec <集群名>-worker2 curl http://127.0.0.1:31926/ 同样返回了 whoami。v1.31 的官方文档（Virtual IPs and Service Proxies）只说 iptables 模式支持 localhost 上的 NodePort，nftables 和 ipvs 模式都不支持。kube-proxy 源码（pkg/proxy/iptables/proxier.go，注释引用了 issue 90259）里能看到，这依赖把内核参数 route_localnet 设为 1，而它有安全隐患，可以用 --iptables-localhost-nodeports=false 关掉。nftables 模式对应的 alpha 特性门控 KubeProxyNFTablesLocalhostNodePorts 要到 v1.37 才出现，和本文的 v1.31 无关。

从集群内的 Pod 访问

在 worker2 上的 client-w2 里，分别访问本节点 IP、worker 的 IP 和 Service 名：

Hostname: web-849d9b5bd4-h4tvn
RemoteAddr: <worker2-ip>:18691
Hostname: web-849d9b5bd4-h4tvn
RemoteAddr: <worker-ip>:13599
Hostname: web-849d9b5bd4-h4tvn
RemoteAddr: <client-w2-ip>:53110

走 NodePort 时源地址被换成了节点 IP，走 ClusterIP（http://web-np/）时 whoami 看到的是 Pod 自己的 IP。集群内部访问应当用 Service 名，绕一圈 NodePort 不但多一跳，还丢了源地址。

kind 的节点 IP 在宿主机上能直接访问，是 Docker 网桥带来的便利。换到云主机或物理机，节点 IP 是否对客户端可达、安全组和防火墙是否放行 30000-32767，都要另外确认，NodePort 本身管不到这一层。

externalTrafficPolicy：Cluster 和 Local

把 web-np 改成 Local：

kubectl -n notes-lab patch svc web-np -p '{"spec":{"externalTrafficPolicy":"Local"}}'

再从宿主机请求三个节点，同时打印耗时：

$ curl -sS -m 5 -w 'time=%{time_total}\n' http://<worker-ip>:31926/ | grep -E 'Hostname|RemoteAddr|time=|curl'
Hostname: web-849d9b5bd4-h4tvn
RemoteAddr: <host-bridge-ip>:42854
User-Agent: curl/8.18.0
time=0.000482
$ curl -sS -m 5 -w 'time=%{time_total}\n' http://<worker2-ip>:31926/ | grep -E 'Hostname|RemoteAddr|time=|curl'
curl: (28) Connection timed out after 5002 milliseconds
time=5.002129
$ curl -sS -m 5 -w 'time=%{time_total}\n' http://<control-plane-ip>:31926/ | grep -E 'Hostname|RemoteAddr|time=|curl'
curl: (28) Connection timed out after 5002 milliseconds
time=5.002461

两个变化：

  1. 打到有后端的 worker，whoami 终于看到了宿主机的真实地址 <host-bridge-ip>。
  2. 打到没有后端的 worker2 和控制平面，连接超时，不是被拒绝。

规则说明了超时的来源：

-A KUBE-EXTERNAL-SERVICES -p tcp -m comment --comment "notes-lab/web-np:http has no local endpoints" -m addrtype --dst-type LOCAL -m tcp --dport 31926 -j DROP
-A KUBE-EXT-U26NTG6KVUAZ4QZZ -s <pod-cidr> -m comment --comment "pod traffic for notes-lab/web-np:http external destinations" -j KUBE-SVC-U26NTG6KVUAZ4QZZ
-A KUBE-EXT-U26NTG6KVUAZ4QZZ -m comment --comment "masquerade LOCAL traffic for notes-lab/web-np:http external destinations" -m addrtype --src-type LOCAL -j KUBE-MARK-MASQ
-A KUBE-EXT-U26NTG6KVUAZ4QZZ -m comment --comment "route LOCAL traffic for notes-lab/web-np:http external destinations" -m addrtype --src-type LOCAL -j KUBE-SVC-U26NTG6KVUAZ4QZZ

本节点没有端点时，kube-proxy 装的是 DROP，包被静默丢弃，客户端只能等到超时。对比 Service 那篇里「完全没有端点」时的 REJECT，那种情况 curl 不到 1 毫秒就失败。所以NodePort 在部分节点上超时、在部分节点上正常，第一个怀疑对象就是 externalTrafficPolicy: Local 加上后端没有覆盖所有节点。

规则里还有一个例外：源地址在 Pod 网段（<pod-cidr>）内的流量直接进 KUBE-SVC，按集群范围分发。实测从 worker2 上的 client-w2 访问 worker2 自己的 NodePort，在 Local 下照样成功：

Hostname: web-849d9b5bd4-h4tvn
RemoteAddr: <client-w2-ip>:59942
Hostname: web-849d9b5bd4-h4tvn
RemoteAddr: <worker2-ip>:28831

第一行是访问 <worker2-ip>:31926，第二行是访问 <worker-ip>:31926。也就是说，在集群内的 Pod 里测 Local 是测不出「某些节点不通」的，要从集群外测。第二行的源地址变成了 <worker2-ip>，那是 Pod 访问集群外地址时在 worker2 上被做了 SNAT，推测是 Calico 的 natOutgoing，这次没有单独确认。

Cluster（默认）Local
哪些节点能接所有节点只有运行着就绪后端的节点
后端看到的源 IP接收请求的节点 IP客户端真实 IP
打到没有后端的节点多转一跳到别的节点DROP，客户端超时

Local 只在前面有一层「知道该把流量发给哪些节点」的东西时才好用，这就是 LoadBalancer 的健康检查端口。

LoadBalancer

kind 里有没有负载均衡实现

先只读地看一眼集群里已有的 LoadBalancer，traefik：

NAME      TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)                      AGE
traefik   LoadBalancer   <cluster-ip>   <lb-ip>       80:30825/TCP,443:31471/TCP   57d

它有 EXTERNAL-IP，status 里还带着 ipMode: Proxy，metadata 里有 service.kubernetes.io/load-balancer-cleanup 这个 finalizer：

status:
  loadBalancer:
    ingress:
    - ip: <lb-ip>
      ipMode: Proxy

这两样都是负载均衡控制器写进去的，看上去集群里有一个实现。可是再查下去：

  • kube-system 和其他 namespace 里没有 MetalLB 之类的 Pod，也没有相关 CRD；
  • 宿主机上装着 cloud-provider-kind（kind 官方的 LoadBalancer 实现，在集群外以进程方式运行，为每个 LoadBalancer 起一个代理容器），但进程没在运行，docker ps -a 里也没有它的代理容器；
  • docker network inspect 列出这块网桥上的容器，只有三个节点，没有谁持有 <lb-ip>；
  • 从宿主机 curl -m 3 http://<lb-ip>/，3 秒超时（exit 28）。

推测这个 IP 是 cloud-provider-kind 以前运行时写入的（它用代理容器实现 LoadBalancer，ipMode: Proxy 与此相符，但这次没有直接证据），控制器停掉后没人清理，status 就一直留着一个已经不通的地址。EXTERNAL-IP 有值不代表入口可用，它只是某个控制器曾经写过的状态。排查 LoadBalancer 不通时，要去确认分配这个 IP 的组件现在还在不在。

自己建一个，看会发生什么

建一个 externalTrafficPolicy: Local 的 LoadBalancer：

apiVersion: v1
kind: Service
metadata:
  name: web-lb
spec:
  type: LoadBalancer
  externalTrafficPolicy: Local
  selector:
    app: web
  ports:
    - name: http
      port: 80
      targetPort: http

20 秒后：

NAME     TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
web-lb   LoadBalancer   <cluster-ip>   <pending>     80:32335/TCP   22s
nodePort=32335 hc=32036 status={"loadBalancer":{}}
No resources found in notes-lab namespace.

没有任何控制器处理它，EXTERNAL-IP 停在 <pending>，kubectl get events 也是空的，没有一条报错告诉你「没有负载均衡实现」。在自建集群里看到 <pending> 一直不变，又找不到相关事件，基本就是这个原因。

但 Kubernetes 自己负责的那部分已经做完了：分配了 ClusterIP 和 NodePort 32335，NodePort 照常可用。还多了一个 healthCheckNodePort: 32036。前面那个同样是 Local 的 NodePort Service 没有这个字段，它只在 LoadBalancer 加 Local 时才分配。kube-proxy 在每个节点的这个端口上回答健康检查：

$ curl -s -m 5 -w '\nhttp=%{http_code}\n' http://<worker-ip>:32036/healthz
{
	"service": {
		"namespace": "notes-lab",
		"name": "web-lb"
	},
	"localEndpoints": 1,
	"serviceProxyHealthy": true
}
http=200
$ curl -s -m 5 -w '\nhttp=%{http_code}\n' http://<worker2-ip>:32036/healthz
{
	"service": {
		"namespace": "notes-lab",
		"name": "web-lb"
	},
	"localEndpoints": 0,
	"serviceProxyHealthy": true
}
http=503

有本地端点的 worker 返回 200，没有的 worker2 返回 503。外部负载均衡器按这个结果只把流量发给 worker，就避开了上一节「打到没有后端的节点被 DROP」的问题，这也是 Local 通常搭配 LoadBalancer 使用的原因。客户端源 IP 能否保留，还要看负载均衡器本身是否透传源地址：直接转发数据包的 LB 能保留；七层代理或 TCP 代理型的 LB（自己终结连接再重新发起）会让后端看到 LB 的地址，Local 也救不回来。

allocateLoadBalancerNodePorts: false

有些负载均衡实现直接把流量发到 Pod IP，用不到 NodePort。这时可以关掉 NodePort 分配。先在已有的 web-lb 上改：

$ kubectl -n notes-lab patch svc web-lb -p '{"spec":{"allocateLoadBalancerNodePorts":false}}'
service/web-lb patched
$ kubectl -n notes-lab get svc web-lb
NAME     TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
web-lb   LoadBalancer   <cluster-ip>   <pending>     80:32335/TCP   32s

32335 还在。官方文档写明，对已经分配了 NodePort 的 Service 改成 false，已有端口不会自动回收，要手工删掉每个端口上的 nodePort 字段。删掉重建，一开始就带上这个字段：

NAME     TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
web-lb   LoadBalancer   <cluster-ip>   <pending>     80/TCP    1s
nodePort=[] hc=31917

PORT(S) 里没有 NodePort 了，但 healthCheckNodePort 仍然分配了 31917。这个开关只管 Service 端口对应的 NodePort，不管健康检查端口。

再把它的 type 改成 NodePort，系统立即补分配了一个端口（80:30640/TCP），allocateLoadBalancerNodePorts 和 healthCheckNodePort 两个字段都被清掉了，externalTrafficPolicy: Local 则保留了下来。

ExternalName：只是一条 CNAME

apiVersion: v1
kind: Service
metadata:
  name: alias
spec:
  type: ExternalName
  externalName: web-np.notes-lab.svc.cluster.local
  ports:
    - port: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: tr-alias
spec:
  type: ExternalName
  externalName: traefik.traefik.svc.cluster.local
---
apiVersion: v1
kind: Service
metadata:
  name: ext
spec:
  type: ExternalName
  externalName: example.com
NAME       TYPE           CLUSTER-IP   EXTERNAL-IP                          PORT(S)    AGE
alias      ExternalName   <none>       web-np.notes-lab.svc.cluster.local   8080/TCP   1s
tr-alias   ExternalName   <none>       traefik.traefik.svc.cluster.local    <none>     1s
ext        ExternalName   <none>       example.com                          <none>     0s

没有 ClusterIP，kubectl get endpointslice -l kubernetes.io/service-name=alias 返回 No resources found，kube-proxy 也就没有任何规则可装。它在 DNS 里的样子：

$ kubectl -n notes-lab exec client-w2 -- nslookup alias.notes-lab.svc.cluster.local
Server:		<dns-ip>
Address:	<dns-ip>:53


alias.notes-lab.svc.cluster.local	canonical name = web-np.notes-lab.svc.cluster.local
Name:	web-np.notes-lab.svc.cluster.local
Address: <cluster-ip>

CoreDNS 返回 CNAME，客户端再按 CNAME 解析到目标的地址，后面的连接直接发往目标，ExternalName 本身不在数据路径上。由此带来两个容易踩的坑。

端口不会被映射

alias 的 ports 里写了 8080，但这只是个摆设：

Hostname: web-849d9b5bd4-h4tvn
Host: alias
curl: (28) Connection timed out after 5001 milliseconds
rc=28

curl http://alias/（80 端口）成功，curl http://alias:8080/ 超时。8080 被原样发到 web-np 的 ClusterIP 上，而 web-np 只有 80 端口的规则。推测这个包没有任何规则接手、ClusterIP 上也没有真实主机回应，所以只能等到超时。ExternalName 不做端口转换，客户端必须直接用目标的端口。

Host 头和 TLS 证书对不上

上面 whoami 的输出里已经能看到 Host: alias：客户端用的是别名，HTTP 请求里的 Host 头也就是别名。whoami 不看 Host，所以没出问题。换成按 Host 路由的目标就不一样了。在实验 namespace 里给 traefik 加一条只匹配 web.notes-lab.test 的 Ingress，后端是 web-np：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: traefik
  rules:
    - host: web.notes-lab.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-np
                port:
                  number: 80

然后通过 tr-alias 访问，一次用默认的 Host 头，一次手工指定：

kubectl -n notes-lab exec client-w2 -- curl -s -m 5 -o /dev/null -w 'no Host override: %{http_code}\n' http://tr-alias/
kubectl -n notes-lab exec client-w2 -- curl -s -m 5 -H 'Host: web.notes-lab.test' http://tr-alias/ | grep -E 'Hostname|^Host:|X-Forwarded-Host'
no Host override: 404
Hostname: web-849d9b5bd4-h4tvn
Host: web.notes-lab.test
X-Forwarded-Host: web.notes-lab.test

不改 Host 头，traefik 收到的是 Host: tr-alias，没有路由匹配，返回 404；手工加上 -H "Host: web.notes-lab.test" 才走到后端。

指向公网域名时问题更明显：

$ kubectl -n notes-lab exec client-w2 -- nslookup ext.notes-lab.svc.cluster.local
...
ext.notes-lab.svc.cluster.local	canonical name = example.com
Name:	example.com
Address: <example-ip-1>
...
$ kubectl -n notes-lab exec client-w2 -- curl -s -m 8 -o /dev/null -w 'http://ext/ http=%{http_code}\n' http://ext/
http://ext/ http=403
$ kubectl -n notes-lab exec client-w2 -- curl -sS -m 8 -o /dev/null -w 'https://ext/ http=%{http_code}\n' https://ext/
curl: (35) TLS connect error: error:0A000410:SSL routines::ssl/tls alert handshake failure
https://ext/ http=000
command terminated with exit code 35

作为对照，在同一个 Pod 里：

https://example.com/ http=200
http://ext/ + Host: example.com http=200

网络是通的。HTTP 返回 403 是因为对方的 CDN 不认识 Host: ext；HTTPS 在握手阶段就失败了：客户端在 SNI 里发的是 ext，推测服务端找不到对应的站点配置，直接用 handshake failure 告警终止了握手。即使握手成功，证书上的域名也不会是 ext，客户端校验照样失败。所以 ExternalName 适合数据库、消息队列这类不看主机名的协议；HTTP(S) 要么让客户端直接用真实域名，要么在集群里放一个会改写 Host 的代理。

官方文档还提到一点：externalName 填 IPv4 地址能通过校验，但它会被当成一个由数字组成的域名，不会被解析成 IP。要把 Service 指向固定 IP，用不带选择器的 Service 配合手工维护的 EndpointSlice。

internalTrafficPolicy: Local

externalTrafficPolicy 管从 NodePort、LoadBalancer 进来的流量；集群内部访问 ClusterIP 的流量由 internalTrafficPolicy 管：

apiVersion: v1
kind: Service
metadata:
  name: web-itp
spec:
  internalTrafficPolicy: Local
  selector:
    app: web
  ports:
    - name: http
      port: 80
      targetPort: http
$ kubectl -n notes-lab exec client-w1 -- curl -sS -m 5 -w 'time=%{time_total}\n' http://web-itp/ | grep -E 'Hostname|time='
Hostname: web-849d9b5bd4-h4tvn
time=0.000780
$ kubectl -n notes-lab exec client-w2 -- curl -sS -m 5 -w 'time=%{time_total}\n' http://web-itp/
time=5.001242
curl: (28) Connection timed out after 5001 milliseconds
command terminated with exit code 28

同一个 Service 名，worker 上的客户端正常，worker2 上的客户端超时。worker2 上的规则：

-A KUBE-SERVICES -d <cluster-ip>/32 -p tcp -m comment --comment "notes-lab/web-itp:http has no local endpoints" -m tcp --dport 80 -j DROP

又是 DROP，和 Service 整体没有端点时的 REJECT 不同。Service、EndpointSlice 看起来都正常，只有部分节点上的客户端超时，这类故障很难从对象状态上看出来。它适合每个节点都有后端的场景，比如 DaemonSet 形式的节点本地代理或日志收集器；后端不能保证覆盖所有节点时，不要用。

sessionAffinity: ClientIP

把 web 扩到 3 个副本，建一个带会话亲和的 Service，超时设成 30 秒方便观察：

apiVersion: v1
kind: Service
metadata:
  name: web-aff
spec:
  selector:
    app: web
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 30
  ports:
    - name: http
      port: 80
      targetPort: http

在 client-w2 里分别对没有亲和的 web-np 和 web-aff 各发 30 次请求：

$ kubectl -n notes-lab exec client-w2 -- sh -c 'for i in $(seq 1 30); do curl -s http://web-np/ | grep Hostname; done' | sort | uniq -c
     13 Hostname: web-849d9b5bd4-4pj4k
      9 Hostname: web-849d9b5bd4-h4tvn
      8 Hostname: web-849d9b5bd4-qmdsh
$ kubectl -n notes-lab exec client-w2 -- sh -c 'for i in $(seq 1 30); do curl -s http://web-aff/ | grep Hostname; done' | sort | uniq -c
     30 Hostname: web-849d9b5bd4-qmdsh

每次 curl 都是新连接，没有亲和时三个 Pod 都分到了，有亲和时 30 次全落在同一个 Pod。实现方式是 iptables 的 recent 模块，按源 IP 记住上次选中的端点：

-A KUBE-SEP-KKK6CXNR3IUBWEO7 -p tcp -m comment --comment "notes-lab/web-aff:http" -m recent --set --name KUBE-SEP-KKK6CXNR3IUBWEO7 --mask 255.255.255.255 --rsource -m tcp -j DNAT --to-destination <pod-ip-a>:80
-A KUBE-SVC-KRL3RTAHIWMG3CQR -m comment --comment "notes-lab/web-aff:http -> <pod-ip-a>:80" -m recent --rcheck --seconds 30 --reap --name KUBE-SEP-KKK6CXNR3IUBWEO7 --mask 255.255.255.255 --rsource -j KUBE-SEP-KKK6CXNR3IUBWEO7

--rcheck --seconds 30 就是 timeoutSeconds：这个源 IP 30 秒内来过，就直接跳到上次那个端点。每隔 32 秒发一次请求，超过超时时间：

03:37:41 Hostname: web-849d9b5bd4-qmdsh
03:38:13 Hostname: web-849d9b5bd4-qmdsh
03:38:45 Hostname: web-849d9b5bd4-h4tvn
03:39:17 Hostname: web-849d9b5bd4-h4tvn
03:39:49 Hostname: web-849d9b5bd4-4pj4k
03:40:21 Hostname: web-849d9b5bd4-4pj4k

6 次里换了两次后端。过期后重新随机选择，可能选到别的 Pod，也可能刚好还是原来那个，所以并不是每次都换。默认的 timeoutSeconds 是 10800 秒（3 小时）。

使用时注意两点：

  • 亲和的键是 kube-proxy 看到的源 IP。客户端如果在 NAT 网关或七层代理后面，大量用户会共用同一个源 IP，被压到同一个 Pod 上。
  • 它只是「尽量回到同一个 Pod」，Pod 被删除或重建后会话照样会换后端。需要严格会话保持的应用，状态应当放到 Pod 之外。

清理

kubectl delete namespace notes-lab

namespace 删除后，其中 Service 占用的 NodePort（包括手工指定的 31987）都会释放。Service 的基本机制见 Service 与服务发现；终止中的端点在 Local 策略下的特殊处理见 优雅终止。
