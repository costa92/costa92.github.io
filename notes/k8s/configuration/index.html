第 18 / 63 节 · 配置与运维

将资源与配置分开

本系列在 本地实验环境 中创建了 notes-lab Namespace。Namespace 用来组织有命名空间的对象，也可以配合 RBAC 和配额管理团队资源；它本身不是完整的安全隔离边界。ConfigMap 和 Secret 都属于某个 Namespace，Pod 只能引用同一 Namespace 里的配置：configMapKeyRef 只有 name、key、optional 三个字段，没有 namespace。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），实验放在单独的 notes-lab namespace 里，所有配置值都是演示用的占位值。节点名简化成了 worker、worker2。

先看一个容易忽略的细节：kubectl get all 并不是「全部」。实验结束前，这个 namespace 里有两个 Pod、五个 ConfigMap 和一个 Secret，get all 只列出了 Pod：

$ kubectl -n notes-lab get all
NAME              READY   STATUS    RESTARTS   AGE
pod/cm-demo       1/1     Running   0          21m
pod/frozen-demo   1/1     Running   0          15s
---
$ kubectl -n notes-lab get configmaps,secrets
NAME                         DATA   AGE
configmap/absent-settings    1      6m18s
configmap/app-settings       2      21m
configmap/frozen-settings    1      3m52s
configmap/kube-root-ca.crt   1      21m
configmap/no-such-settings   1      8m2s

NAME                      TYPE     DATA   AGE
secret/demo-credentials   Opaque   1      4m29s

kube-root-ca.crt 不是我创建的，每个 namespace 建好后控制器都会自动放一份集群 CA 证书进来，供 Pod 校验 API Server 用。

同一份 ConfigMap，三种注入方式

创建一个有两个键的 ConfigMap：

kubectl -n notes-lab create configmap app-settings \
  --from-literal=APP_MODE=v1 --from-literal=LOG_LEVEL=info

然后让一个 Pod 用三种方式读同一个键 APP_MODE：环境变量、整卷挂载到 /etc/app、用 subPath 单独挂一个文件到 /etc/sub/APP_MODE。容器每秒读一次三处的值，有变化才打印一行带时间的日志，这样更新什么时候到达容器，日志里一目了然。保存为 cm-demo.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: cm-demo
spec:
  containers:
    - name: app
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          last=""
          while true; do
            now="env=$APP_MODE vol=$(cat /etc/app/APP_MODE) sub=$(cat /etc/sub/APP_MODE)"
            [ "$now" != "$last" ] && echo "$(date -u +%T) $now" && last="$now"
            sleep 1
          done
      env:
        - name: APP_MODE
          valueFrom:
            configMapKeyRef:
              name: app-settings
              key: APP_MODE
      volumeMounts:
        - name: settings
          mountPath: /etc/app
        - name: settings
          mountPath: /etc/sub/APP_MODE
          subPath: APP_MODE
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 32Mi}
  volumes:
    - name: settings
      configMap:
        name: app-settings
$ kubectl -n notes-lab apply -f cm-demo.yaml && kubectl -n notes-lab wait --for=condition=Ready pod/cm-demo --timeout=120s && kubectl -n notes-lab logs cm-demo
pod/cm-demo created
pod/cm-demo condition met
04:54:58 env=v1 vol=v1 sub=v1

整卷挂载的目录结构值得看一眼，后面的更新行为都和它有关：

$ kubectl -n notes-lab exec cm-demo -- ls -la /etc/app/
drwxrwxrwx    3 root     root          4096 Oct 12 04:54 .
drwxr-xr-x    1 root     root          4096 Oct 12 04:54 ..
drwxr-xr-x    2 root     root          4096 Oct 12 04:54 ..2026_10_12_04_54_30.32765340
lrwxrwxrwx    1 root     root            30 Oct 12 04:54 ..data -> ..2026_10_12_04_54_30.32765340
lrwxrwxrwx    1 root     root            15 Oct 12 04:54 APP_MODE -> ..data/APP_MODE
lrwxrwxrwx    1 root     root            16 Oct 12 04:54 LOG_LEVEL -> ..data/LOG_LEVEL

每个键是一个符号链接，经过 ..data 指向一个带时间戳的目录。kubelet 更新时先写一个新的时间戳目录，再把 ..data 换过去，读文件的程序不会读到写了一半的内容。subPath 则不同：它在容器启动时把 APP_MODE 解析到当时那个时间戳目录里的具体文件，再单独 bind mount 进来，之后 ..data 怎么切换都和它无关。

更新要多久才能到达容器

把 APP_MODE 连续改了四次，每次记下执行 patch 的时间：

date -u +%T; kubectl -n notes-lab patch configmap app-settings --type=merge -p '{"data":{"APP_MODE":"v2"}}'

四次 patch 分别在 04:55:18、04:56:26、04:57:37、04:58:36 发出，容器日志：

$ kubectl -n notes-lab logs cm-demo
04:54:58 env=v1 vol=v1 sub=v1
04:56:12 env=v1 vol=v2 sub=v1
04:57:29 env=v1 vol=v3 sub=v1
04:58:29 env=v1 vol=v4 sub=v1
04:59:38 env=v1 vol=v5 sub=v1
patch 时间卷文件变化时间延迟
04:55:1804:56:1254 秒
04:56:2604:57:2963 秒
04:57:3704:58:2952 秒
04:58:3604:59:3862 秒

三列里只有卷在变。环境变量从头到尾是 v1，subPath 挂载的文件也一直是 v1。

延迟稳定在一分钟左右，而这个集群 kubelet 的配置是：

$ kubectl get --raw /api/v1/nodes/worker/proxy/configz | python3 -c "import json,sys; c=json.load(sys.stdin)[\"kubeletconfig\"]; print({k:c.get(k) for k in [\"syncFrequency\",\"configMapAndSecretChangeDetectionStrategy\"]})"
{'syncFrequency': '1m0s', 'configMapAndSecretChangeDetectionStrategy': 'Watch'}

检测策略是 Watch，kubelet 本地的 ConfigMap 缓存几乎是实时的，但官方文档说明 kubelet 在每次周期性同步 Pod 时检查挂载的 ConfigMap 是否需要刷新（改注解等事件也会触发一次同步），总延迟最长可达「同步周期 + 缓存传播延迟」。四次延迟在 52–63 秒之间，落地时刻（56:12、57:29、58:29、59:38）的间隔是 60–77 秒，都在 1 分钟的 syncFrequency 附近。我推测这次的延迟基本都花在等下一轮 Pod 同步上，缓存本身没有拖慢；间隔不是整 60 秒，推测是 kubelet 给同步周期加了随机抖动。如果 kubelet 用的是 TTL 缓存策略，还要再加上缓存的 TTL。

所以「改完 ConfigMap 等几秒看看」是不够的，至少要按一到两分钟准备。

改注解可以立即触发刷新

文档提到，更新 Pod 的任意注解会触发一次立即同步。试一下：

$ date -u +%T; kubectl -n notes-lab patch configmap app-settings --type=merge -p '{"data":{"APP_MODE":"v6"}}'; kubectl -n notes-lab annotate pod cm-demo notes-lab/touch=$(date +%s) --overwrite; date -u +%T
05:00:08
configmap/app-settings patched
pod/cm-demo annotated
05:00:13
$ kubectl -n notes-lab logs cm-demo --since=30s
05:00:14 env=v1 vol=v6 sub=v1

注解在 05:00:13 打完，文件 05:00:14 就变了（中间的 5 秒是两条 kubectl 命令自己的耗时）。这适合调试时用；生产里更常见的做法是把配置内容的哈希写进 Deployment 的 Pod 模板注解，让配置变更直接触发滚动更新，见 Deployment。

容器重启会读到新值，但第一次重启失败了

环境变量和 subPath 是在创建容器时解析的。那么不重建 Pod、只让容器重启，能不能拿到新值？用一个跑 20 秒就退出的容器验证，restartPolicy: Always 让 kubelet 不断重启它。env、volumeMounts（只保留 subPath 那一条）、volumes 和 cm-demo 相同，只改了下面两处：

metadata:
  name: restart-demo
spec:
  restartPolicy: Always
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo \"$(date -u +%T) env=$APP_MODE sub=$(cat /etc/sub/APP_MODE)\"; sleep 20"]

容器 05:00:40 启动，读到 v6；05:00:42 把 ConfigMap 改成 v7。50 秒后：

$ kubectl -n notes-lab get pod restart-demo; kubectl -n notes-lab logs restart-demo
NAME           READY   STATUS    RESTARTS      AGE
restart-demo   1/1     Running   2 (21s ago)   57s
05:01:29 env=v7 sub=v7

重启后的容器里，环境变量和 subPath 文件都是 v7。所以准确的说法是：这两种方式要等容器重新创建才会读到新值，Pod 内的容器重启也算，不一定要删 Pod。这和文档里「subPath 收不到更新」并不矛盾：文档说的是运行中的容器看不到变化；v1.19 的 PR #89629 之后，容器重启时 kubelet 会重新解析 subPath，所以新容器能拿到新值。

但 RESTARTS 是 2，只跑了 50 秒的 Pod 不该重启两次。describe 里记下了中间那次失败：

Last State:     Terminated
  Reason:       StartError
  Message:      failed to create containerd task: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: error during container init: error mounting "/var/lib/kubelet/pods/3f6a0a67-9499-422d-b26e-dbba376c376f/volume-subpaths/settings/app/0" to rootfs at "/etc/sub/APP_MODE": mount /var/lib/kubelet/pods/3f6a0a67-9499-422d-b26e-dbba376c376f/volume-subpaths/settings/app/0:/etc/sub/APP_MODE (via /proc/self/fd/6), flags: 0x5001: no such file or directory: unknown
  Exit Code:    128
  Started:      Thu, 01 Jan 1970 07:30:00 +0730
  Finished:     Mon, 12 Oct 2026 13:01:11 +0800

容器在 05:01:11 重启时，runc 挂载 subPath 失败，报 no such file or directory，进程根本没启动，所以 Started 是 1970 年的零值。kubelet 退避后再试一次就成功了。之后我又用新 Pod 重复了三次「启动后改 ConfigMap、等容器重启」，这个错误都没再出现，四次里出现一次。

这次没有到节点上核对挂载点，但现象和一个已知问题完全对得上（kubernetes#68211）：subPath 挂载绑定的是某个时间戳目录里的文件，ConfigMap 更新后 kubelet 切换 ..data 并删掉旧时间戳目录，volume-subpaths 下的 bind mount 就指向了一个已经不存在的文件，容器重启时挂载报 no such file or directory。v1.19 合入的 PR #89629 让重试时重新准备 subPath，所以下一次启动能恢复，和本次看到的「失败一次、退避后成功」一致。推测触发条件是「重启前已经有一次卷更新删掉了旧目录」，而不是重启恰好撞上切换的那一刻；另外三次没出现，可能是容器重启时卷还没轮到更新。在更老的版本上，据 issue 里的描述，容器会一直起不来，只能删 Pod。

小结三种方式的更新行为：

注入方式ConfigMap 更新后何时读到新值
环境变量 env / envFrom不变容器重新创建时
整卷挂载文件最终更新，本次实测约 1 分钟kubelet 下一次同步 Pod 时；应用还得自己重新读文件
subPath 挂载不变容器重新创建时

这些规则对 Secret 同样适用。Secret 卷的轮换和应用重新加载，见 Secret 轮换与应用重新加载。

引用不存在时 Pod 卡在哪里

故意写错三种引用，三个 Pod 都用同一个 busybox 容器，启动时打印 APP_MODE 并列出 /etc/app：

command: ["sh", "-c", "echo APP_MODE=${APP_MODE:-<unset>}; ls /etc/app 2>&1; sleep 3600"]

差别只在引用部分：

# missing-cm：环境变量引用不存在的 ConfigMap
      env:
        - name: APP_MODE
          valueFrom:
            configMapKeyRef:
              name: no-such-settings
              key: APP_MODE
              optional: false
# missing-key：ConfigMap 存在，键不存在
      env:
        - name: APP_MODE
          valueFrom:
            configMapKeyRef:
              name: app-settings
              key: NO_SUCH_KEY
              optional: false
# missing-vol：卷引用不存在的 ConfigMap
      volumeMounts:
        - name: settings
          mountPath: /etc/app
  volumes:
    - name: settings
      configMap:
        name: no-such-settings
        optional: false

同样是「ConfigMap 不存在」，状态却不一样：

  • 环境变量引用失败发生在生成容器配置这一步，状态是 CreateContainerConfigError，事件原因是 Failed。
  • 卷引用失败发生在挂载卷这一步，比创建容器还早，所以状态停在 ContainerCreating，事件原因是 FailedMount。这和镜像慢、网络慢时看到的状态一样，必须看事件才能区分，参考 Pod 与容器 里对 ContainerCreating 的分析。

键不存在时，消息会写明键名和 namespace/名称，拼写错误一眼就能看出来。

这类错误不需要删 Pod。05:07:45 补建了 no-such-settings：

missing-cm 和 missing-vol 的容器分别在 05:08:00 和 05:08:04 自己启动了，kubelet 一直在重试。missing-key 引用的键仍然不存在，所以还卡着。

optional: true 改变了什么

把三处引用都改成 optional: true：opt-cm 和 opt-vol 引用一个不存在的 absent-settings，opt-key 仍引用 app-settings 里不存在的 NO_SUCH_KEY。opt-vol 的卷定义：

卷里的文件在 05:10:35 出现，晚了 66 秒，走的还是前面那套周期同步；环境变量依旧没有设置，要等容器重新创建。

optional: true 的代价是：配置缺失时 Pod 照常 Running，错误被推迟到应用自己读配置时才暴露。只有程序本身对缺失配置有默认值时才适合用它。

Secret：base64 只是编码

用一个演示值创建 Secret：

$ kubectl -n notes-lab create secret generic demo-credentials --from-literal=API_TOKEN=example-only-token
secret/demo-credentials created
$ kubectl -n notes-lab get secret demo-credentials -o yaml | grep -v -E 'uid|resourceVersion|creationTimestamp'
apiVersion: v1
data:
  API_TOKEN: ZXhhbXBsZS1vbmx5LXRva2Vu
kind: Secret
metadata:
  name: demo-credentials
  namespace: notes-lab
type: Opaque
$ kubectl -n notes-lab get secret demo-credentials -o jsonpath='{.data.API_TOKEN}' | base64 -d
example-only-token

-o yaml 输出里滤掉了 uid 等几个元数据字段。data 里的值一条 base64 -d 就还原了，能 get 这个 Secret 的人就能读到原文。kubectl describe secret 只显示长度（API_TOKEN: 18 bytes），这只是展示上的克制，不是保护。

确认这个集群有没有开启静态加密

API 里看到的是 base64，那 etcd 里存的是什么，取决于有没有开启静态加密（encryption at rest）。开启后，etcd 里的 Secret 值会以 k8s:enc:<provider>:v1: 开头（例如 k8s:enc:aescbc:v1:），后面跟密文；没有这个前缀、直接能看到原文，就说明没开。在 control-plane 上用 etcdctl 只读地取出这个演示 Secret 的记录：

$ kubectl -n kube-system exec etcd-control-plane -- etcdctl --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key get /registry/secrets/notes-lab/demo-credentials --print-value-only | strings | grep -E 'k8s|example|API_TOKEN|Opaque'
0{"f:data":{".":{},"f:API_TOKEN":{}},"f:type":{}}B
	API_TOKEN
example-only-token
Opaque

没有 k8s:enc: 前缀，值就是原文 example-only-token，连 base64 都没有：etcd 里存的是 protobuf 序列化后的对象，base64 只出现在 API 的 JSON/YAML 表示里，用来装二进制数据。结论是这个 kind 集群没有开启静态加密，这也是 Kubernetes 的默认状态，拿到 etcd 数据或备份的人就能读到所有 Secret。开启方法见 Encrypting Confidential Data at Rest，配置后可以用同样的 etcdctl 命令检查前缀，确认确实生效。

Secret 和 ConfigMap 挂成卷时，落地方式也不一样。下一节的 frozen-demo Pod 里各挂了一个，ConfigMap 挂到 /etc/app，Secret 以 readOnly: true 挂到 /etc/secret：

volumes:
  - name: settings
    configMap:
      name: frozen-settings
  - name: creds
    secret:
      secretName: demo-credentials
$ kubectl -n notes-lab exec frozen-demo -- sh -c 'mount | grep -E "/etc/(app|secret)"'
/dev/sda on /etc/app type ext4 (ro,relatime)
tmpfs on /etc/secret type tmpfs (ro,relatime,size=32768k,inode64,noswap)

ConfigMap 卷在节点磁盘上，Secret 卷在 tmpfs（内存）里，不会写到节点的持久存储。tmpfs 的 size=32768k 和这个 Pod 的内存 limit 32Mi 相同，推测 kubelet 是按 limit 设定 tmpfs 大小的。

只把 Secret 交给需要的容器、RBAC 权限怎么收，见 Secret 安全边界与轮换 和 ServiceAccount 与 RBAC。

immutable：改不了，只能删了重建

apiVersion: v1
kind: ConfigMap
metadata:
  name: frozen-settings
immutable: true
data:
  APP_MODE: v1
$ kubectl -n notes-lab apply -f frozen.yaml; kubectl -n notes-lab patch configmap frozen-settings --type=merge -p '{"data":{"APP_MODE":"v2"}}'; kubectl -n notes-lab patch configmap frozen-settings --type=merge -p '{"immutable":false}'; kubectl -n notes-lab label configmap frozen-settings team=demo
configmap/frozen-settings created
The ConfigMap "frozen-settings" is invalid: data: Forbidden: field is immutable when `immutable` is set
The ConfigMap "frozen-settings" is invalid: immutable: Forbidden: field is immutable when `immutable` is set
configmap/frozen-settings labeled

改 data 被拒，想把 immutable 改回 false 也被拒；但改标签这类元数据是可以的。唯一能换内容的办法是删掉再建一个同名的。

那正在用它的 Pod 会怎样？让一个 Pod 挂载 frozen-settings（就是上面查 tmpfs 的那个 Pod），05:11:55 删掉 ConfigMap，用 APP_MODE: v2 重建：

$ date -u +%T; kubectl -n notes-lab logs frozen-demo; kubectl -n notes-lab get pod frozen-demo
05:14:25
05:11:48 cm=v1 secret=18B
NAME          READY   STATUS    RESTARTS   AGE
frozen-demo   1/1     Running   0          2m45s

两分半钟后文件还是 v1，而前面普通 ConfigMap 一分钟左右就更新了。05:14:33 改了 Pod 注解，20 秒后仍是 v1，立即同步的办法对它也不起作用。删掉 Pod 重建，才读到 v2：

05:15:39 cm=v2 secret=18B

官方文档的说法是：kubelet 不再 watch 标记为 immutable 的 ConfigMap，已有的 Pod 还保持着指向被删除那份的挂载点，建议重建这些 Pod。好处是 ConfigMap 很多的集群里能减轻 API Server 的负担，也避免误改配置一下子影响所有 Pod。实际用法通常是给名称带上版本或内容哈希（如 app-settings-v2），改配置就建新对象，并修改 Deployment 的引用触发滚动更新。

清理

kubectl delete namespace notes-lab
