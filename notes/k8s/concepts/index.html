Kubernetes 概念和术语

Kubernetes（K8s）管理的是期望状态：你不下达“启动两个容器”的命令，而是提交一个写着“我要两个副本”的对象；控制器（持续运行的程序，每类对象都有对应的控制器）不断比较期望和实际，不一致就调整。这一篇在集群上验证：期望写在哪里、实际状态由谁写、控制器管什么、不管什么。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，kubectl v1.30.0，containerd 1.7.18，CNI 为 Calico），实验放在单独的 notes-lab namespace 里，ClusterIP 用 <cluster-ip> 代替，脚本打印的是本地时间（UTC+8）。

常用对象一览

所有对象都存放在 API Server 里。API Server 是集群的入口，kubectl 和各个控制器都只和它打交道，它把对象存进 etcd（集群的键值数据库）。各组件的职责见集群组件。

对象解决的问题实践
Node运行 Pod 的机器集群组件
容器镜像打包程序和依赖镜像构建
Pod一个或多个紧密协作的容器，调度的最小单元Pod 与容器
控制器把实际状态推向期望状态控制器调谐循环
ReplicaSet让匹配选择器的 Pod 数等于期望副本数Deployment
Deployment管理 ReplicaSet，负责副本与滚动更新Deployment
Label / Selector对象上的键值对，以及按它筛选对象的条件标签与选择器
Service为变化中的 Pod 提供稳定入口Service
Headless Service通过 DNS 发现每个后端 PodHeadless Service
Ingress按域名或路径转发 HTTP(S)Ingress
Namespace把对象分组，名字只在组内唯一配置与命名空间
Downward API把 Pod 元数据提供给容器Downward API
ConfigMap / Secret配置与镜像分开配置与命名空间
Job / CronJob一次性或定时任务批处理任务

一个 Deployment 的链条是：Deployment 创建 ReplicaSet，ReplicaSet 创建 Pod，调度器（kube-scheduler，为 Pod 选节点）把 Pod 分到某个 Node，Node 上的 kubelet（每个节点上的代理，负责启停容器）启动容器。请求路径通常是：客户端 → Ingress 控制器 → Service → Pod。

先问集群：有哪些对象、对象有哪些字段

对象类型不用死记，kubectl api-resources 会列出 API Server 认识的全部类型。资源按 API 组划分，Pod、Service 这些最早的类型在组名为空的核心组，清单里写 apiVersion: v1；Deployment 在 apps 组：

$ kubectl api-resources --api-group=apps
NAME                  SHORTNAMES   APIVERSION   NAMESPACED   KIND
controllerrevisions                apps/v1      true         ControllerRevision
daemonsets            ds           apps/v1      true         DaemonSet
deployments           deploy       apps/v1      true         Deployment
replicasets           rs           apps/v1      true         ReplicaSet
statefulsets          sts          apps/v1      true         StatefulSet

NAMESPACED 一列说明对象是否属于某个 namespace。核心组里 Pod、Service、ConfigMap、PVC 属于 namespace，Node、Namespace、PV 是集群级的。这个集群装了 cert-manager、Argo CD 等组件，不加过滤时共列出 109 种 namespace 级、80 种集群级资源，大部分来自 CRD，所以用到时查就行。

-n 写错时 kubectl 很宽容：集群级对象直接忽略 -n，namespace 级对象查一个不存在的 namespace 只说“没有资源”，退出码还是 0。脚本靠退出码判断，namespace 名写错了也发现不了：

$ kubectl get pods -n does-not-exist; echo "exit=$?"
No resources found in does-not-exist namespace.
exit=0

查字段用 kubectl explain，内容来自 API Server 发布的 OpenAPI 文档，和集群版本一致。kubectl explain deployment 里，spec 是 “Specification of the desired behavior”，status 是 “Most recently observed status”：期望和观察从定义上就分开了。kubectl explain deployment.spec.selector 里有一句 “It must match the pod template’s labels”，违反它的后果见新手错误一节。

读懂一个对象

保存为 web.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              memory: 128Mi
  • apiVersion 和 kind 指明对象类型；metadata.name 是对象名，同一 namespace 内同类对象不能重名。
  • spec 是期望状态；status 由集群报告，不写进清单。
  • selector.matchLabels 必须与 Pod 模板（template，ReplicaSet 照着它创建 Pod）的标签匹配；Service 也通过标签选择后端。
  • replicas: 2 表示期望两个 Pod；resources.requests 是给调度器看的资源预留，见探针与资源管理。

看 status 追上 spec

提交后每 0.5 秒读一次几个字段：metadata.generation（GEN）、status.observedGeneration（OBS）、spec.replicas（SPEC）、status.replicas（CUR）、status.updatedReplicas（UPD）、status.readyReplicas（READY）。保存为 watch.sh，参数是采样次数：

kc(){ kubectl -n notes-lab "$@"; }
printf "%-12s %-4s %-4s %-5s %-5s %-5s %-5s\n" TIME GEN OBS SPEC CUR UPD READY
for i in $(seq 1 ${1:-30}); do
  kc get deploy web -o jsonpath='{.metadata.generation} {.status.observedGeneration} {.spec.replicas} {.status.replicas} {.status.updatedReplicas} {.status.readyReplicas}' 2>/dev/null | { read g o s c u rd; printf "%-12s %-4s %-4s %-5s %-5s %-5s %-5s\n" $(date +%T.%3N) "$g" "${o:--}" "$s" "${c:--}" "${u:--}" "${rd:--}"; }
  sleep 0.5
done
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done

status 不归你写

在清单里写上 status 会怎样？保存为 withstatus.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-status
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web-status
  template:
    metadata:
      labels:
        app: web-status
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
status:
  replicas: 5
  readyReplicas: 5
$ kubectl -n notes-lab apply -f withstatus.yaml; kubectl -n notes-lab get deploy web-status -o jsonpath="{.status}{\"\n\"}"; sleep 5; kubectl -n notes-lab get deploy web-status -o jsonpath="{.status.replicas} {.status.readyReplicas}{\"\n\"}"
deployment.apps/web-status created
{"conditions":[{"lastTransitionTime":"2026-10-13T06:16:07Z","lastUpdateTime":"2026-10-13T06:16:07Z","message":"Deployment does not have minimum availability.","reason":"MinimumReplicasUnavailable","status":"False","type":"Available"},{"lastTransitionTime":"2026-10-13T06:16:07Z","lastUpdateTime":"2026-10-13T06:16:07Z","message":"ReplicaSet \"web-status-5ffc6dd4cc\" is progressing.","reason":"ReplicaSetUpdated","status":"True","type":"Progressing"}],"observedGeneration":1,"replicas":1,"unavailableReplicas":1,"updatedReplicas":1}

没有报错，replicas: 5 也没有出现。单看实验分不清是 API Server 丢弃还是被控制器覆盖；v1.31 源码 pkg/registry/apps/deployment/strategy.go 的 PrepareForCreate 里有 deployment.Status = apps.DeploymentStatus{}，创建请求里的 status 会被直接清空。

控制器管数量，不管内容

这一节的输出来自另一轮实验，web 是 3 个副本、镜像 nginx:alpine。跟做时先对齐：

kubectl -n notes-lab delete deploy web-status
kubectl -n notes-lab scale deploy web --replicas=3
kubectl -n notes-lab rollout status deploy/web

Pod 名的随机后缀每次都不同，下面命令里的 Pod 名要换成自己的。

裸 Pod：删了就没了

$ kubectl -n notes-lab run bare --image=nginx:alpine --labels=app=bare --restart=Never; kubectl -n notes-lab wait --for=condition=Ready pod/bare --timeout=60s

pod/bare condition met
$ kubectl -n notes-lab get pod bare -o 'jsonpath={.metadata.ownerReferences}'; echo '<- ownerReferences(空)'
<- ownerReferences(空)
$ kubectl -n notes-lab delete pod bare; sleep 5; kubectl -n notes-lab get pod bare; kubectl -n notes-lab get pod -l app=bare
pod "bare" deleted
Error from server (NotFound): pods "bare" not found
No resources found in notes-lab namespace.

ownerReferences 记录对象归谁管，受管 Pod 的这一项指向 ReplicaSet；裸 Pod 为空，没有控制器为它负责，删除、节点故障、驱逐后都不会回来。

直接改受管 Pod：控制器视而不见

Service：按标签找 Pod

Pod 会被替换，IP 跟着变，Service 只靠标签选择器找后端。这一节回到“读懂一个对象”那一轮：web 2 个副本，先把镜像改成 nginx:1.27，10 秒后改回 nginx:alpine，再过 8 秒创建 Service。跟做时：

kubectl -n notes-lab scale deploy web --replicas=2
kubectl -n notes-lab set image deploy/web nginx=nginx:1.27; sleep 10
kubectl -n notes-lab set image deploy/web nginx=nginx:alpine; sleep 8

保存为 svc.yaml：

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
$ kubectl -n notes-lab apply -f svc.yaml
service/web created
$ kubectl -n notes-lab get svc web
NAME   TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
web    ClusterIP   <cluster-ip>    <none>        80/TCP    0s

EndpointSlice 是 Service 的后端列表，由控制器维护：登记所有匹配的 Pod，用 conditions.ready 标出是否就绪；kube-proxy（每个节点上把 Service 翻译成转发规则的组件，见集群组件）通常只把流量转给就绪的端点：

$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=web -o 'jsonpath={range .items[*].endpoints[*]}{.targetRef.name} ready={.conditions.ready}{"\n"}{end}'
web-cbff8bdb4-sgxdp ready=true
web-cbff8bdb4-zbzmx ready=true
web-785cd9fb7-4tlmh ready=false

web-785cd9fb7-4tlmh 属于旧 ReplicaSet（nginx:1.27 那版），ready=false。当时没记录它的 terminating 条件，推测它正在终止；11 秒后再查，它已不在列表里。

从另一个 Pod 里访问，同一 namespace 内用短名字 web 就行：

$ kubectl -n notes-lab run client --image=busybox:1.36 --restart=Never -- sleep 3600
pod/client created
$ kubectl -n notes-lab wait --for=condition=Ready pod/client --timeout=60s
pod/client condition met
$ kubectl -n notes-lab exec client -- wget -qO- -T 5 http://web | grep -i "<title>"
<title>Welcome to nginx!</title>

Pod 的 DNS 搜索域带着自己的 namespace，web 被补全成 web.notes-lab.svc.cluster.local，跨 namespace 要写 web.<namespace>。选择器写错时 Service 照样创建，只是后端为空，见 API 对象与控制器关系；更多见 Service、Service 类型 和 DNS 排查。

新手常见错误

以下都是故意复现的。输出来自 3 个副本的那一轮，先 kubectl -n notes-lab scale deploy web --replicas=3 对齐。

namespace 写错：NotFound

对象明明在，get 却说找不到：

$ kubectl get deploy web; echo "exit=$?"
Error from server (NotFound): deployments.apps "web" not found
exit=1
$ kubectl get deploy web -n notes-lab
NAME   READY   UP-TO-DATE   AVAILABLE   AGE
web    3/3     3            3           3m25s

不带 -n 时用的是当前上下文（kubeconfig 里“集群 + 用户 + 默认 namespace”的组合）的 namespace，没配就是 default，可用 kubectl config view --minify -o jsonpath="{.contexts[0].context.namespace}" 查看，这次输出为空。不知道对象在哪个 namespace，就按名字全局搜：

$ kubectl get deploy -A --field-selector metadata.name=web
NAMESPACE                   NAME   READY   UP-TO-DATE   AVAILABLE   AGE
notes-lab                   web    3/3     3            3           3m25s

共享集群上还会列出其他 namespace 里同名的 web（上面只保留了本实验的一行）。

选择器和模板标签不一致：提交即被拒

把 web.yaml 的模板标签改成 app: web-v2，选择器仍是 app: web，名字改成 web-mismatch：

sed 's/^        app: web$/        app: web-v2/' web.yaml | sed 's/name: web$/name: web-mismatch/' > mismatch.yaml
$ kubectl -n notes-lab apply -f mismatch.yaml
The Deployment "web-mismatch" is invalid: spec.template.metadata.labels: Invalid value: map[string]string{"app":"web-v2"}: `selector` does not match template `labels`

这就是 explain 里那句话的执行结果。

想改 Deployment 的选择器：field is immutable

把已存在的 web 的选择器和模板标签一起改成 app: web2，两者一致也不行：

sed 's/^      app: web$/      app: web2/; s/^        app: web$/        app: web2/' web.yaml > reselect.yaml
$ kubectl -n notes-lab apply -f reselect.yaml
The Deployment "web" is invalid: spec.selector: Invalid value: v1.LabelSelector{MatchLabels:map[string]string{"app":"web2"}, MatchExpressions:[]v1.LabelSelectorRequirement(nil)}: field is immutable

Deployment 选择器创建后不可修改，只能新建再删旧的，所以选择器要用稳定的标签，版本号之类放到模板的其他标签里。

apiVersion 照抄旧教程

sed 's#apps/v1#apps/v1beta1#; s/name: web$/name: web-old/' web.yaml > oldapi.yaml
$ kubectl -n notes-lab apply -f oldapi.yaml
error: resource mapping not found for name: "web-old" namespace: "" from "oldapi.yaml": no matches for kind "Deployment" in version "apps/v1beta1"
ensure CRDs are installed first

集群不提供 apps/v1beta1。“ensure CRDs are installed first” 在这里是误导，该用 kubectl api-resources 查当前的 APIVERSION。

学习路线

从本地实验环境开始，依次学习镜像、Pod、Deployment、标签、探针与资源管理、Service 和 Ingress。随后看配置、批处理、Helm Chart、存储与访问控制；遇到异常可查故障排查。进阶章节从 kubectl 开始，逐步练习节点工作负载、维护预算、网络隔离、调度、自动扩缩容和环境配置。集群搭建章节进一步介绍高可用拓扑、多集群上下文与可观测性。

想了解由谁执行这些操作，先读集群组件；想看 Deployment、ReplicaSet、Pod、Service、EndpointSlice 之间靠什么关联，读 API 对象与控制器关系；本篇“删 Pod 被补回”背后的机制，在控制器调谐循环里展开。

运行前用 kubectl config current-context 核对集群，别在共享或生产集群上练习。本篇的清理：

kubectl delete namespace notes-lab --wait
kubectl get namespace notes-lab
# Error from server (NotFound): namespaces "notes-lab" not found
