第 65 / 66 节 · 集群搭建

从 Kubernetes 状态走向可观测性

kubectl get 和 Events 能告诉我们 Kubernetes 对象发生了什么，应用日志记录程序输出，Metrics Server 与 HPA关注短期 CPU、内存等资源指标。它们还不足以解释一次跨服务请求为什么慢。OpenTelemetry（OTel）提供采集链路追踪、指标和日志的通用模型与工具，通常需要应用埋点、Collector 和后端存储配合。

信号回答的问题常见内容
Traces一次请求经过了哪些步骤，耗时在哪trace、span、父子关系、属性
Metrics一段时间内趋势如何请求量、错误率、延迟分布
Logs某时刻程序记录了什么错误文本、字段、关联 ID

三种信号可以通过 trace ID 等上下文关联，但安装 Collector 本身不会让没有埋点的应用自动产出完整调用链。

先建立 Kubernetes 排查基线

在实验集群执行只读命令：

kubectl config current-context
kubectl -n k8s-lab get pods -o wide
kubectl -n k8s-lab get events --sort-by=.lastTimestamp
kubectl -n k8s-lab top pods

kubectl top 需要 Metrics API；若 Metrics Server 未安装，它报错不代表应用没有日志或追踪数据。查看指定 Pod 的应用输出可运行 kubectl -n k8s-lab logs POD_NAME，先把 POD_NAME 换成实际名称。

读懂 Collector 流水线

Collector 从 receiver 收到数据，经过可选 processor，最后由 exporter 发往调试输出或可观测性后端。下面是配置结构示意，不是完整的 Kubernetes 部署清单：

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318
processors:
  batch: {}
exporters:
  debug: {}
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]

service.pipelines.traces 才真正启用上述组件；仅在顶层声明 receiver/exporter 不会启动链路。这个示例只接收并输出 traces，没有配置指标、日志或持久化后端。0.0.0.0 会监听所有容器网络接口，部署时要限制访问范围并按环境配置认证与 TLS。

安装对应发行版的 Collector 后，可用其 validate --config=... 命令验证配置；组件是否可用取决于该发行版。下一步再选应用语言的 OTel SDK、确定 OTLP 端点、部署 Collector、接入可查询的后端，并用一次实际请求验证 trace 是否贯通。

详见 OpenTelemetry 信号与 Collector 配置。
