第 62 / 63 节 · 集群搭建

kubectl 看得到什么，看不到什么

kubectl get、describe 和 Events 告诉我们 Kubernetes 对象发生了什么，kubectl logs 给出容器的标准输出，kubectl top 给出 Metrics Server 采到的短期 CPU 和内存。一次请求为什么慢、慢在哪一跳、同一时刻哪个服务报了什么错，这些问题它们答不上来。OpenTelemetry（OTel）为链路追踪、指标和日志定义了统一的数据模型和传输协议 OTLP，并提供 Collector 来接收、加工和转发这些数据。应用要先用 SDK 埋点，数据才会产生；光装一个 Collector，没有埋点的应用不会自动产出调用链。

信号回答的问题常见内容
Traces一次请求经过了哪些步骤，耗时在哪trace、span、父子关系、属性
Metrics一段时间内趋势如何请求量、错误率、延迟分布
Logs某时刻程序记录了什么错误文本、字段、关联 ID

这篇不接任何存储后端，只用 Collector 的 debug exporter 把收到的数据打印到它自己的标准输出，再用 kubectl logs 查看。这样能把「数据进没进 Collector、经过处理后长什么样」看得清清楚楚，也方便复现各种出错的情况。

下文输出来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico，已装 metrics-server），Collector 用的是 otel/opentelemetry-collector-contrib:0.114.0，实验放在单独的 notes-lab namespace。节点名简化成 worker，Pod IP 用 <pod-ip> 代替。

先看 kubectl 自己能给出什么

实验做到一半（Collector 已经收发过几轮数据，也拒绝过好几个错误请求）时，看一眼 kubectl 能提供的信息：

kubectl -n notes-lab top pods
kubectl -n notes-lab get events --sort-by=.lastTimestamp \
  -o custom-columns=TIME:.lastTimestamp,OBJ:.involvedObject.name,REASON:.reason | tail -8
echo "client log lines: $(kubectl -n notes-lab logs client | wc -l)"

实际执行时三条命令之间用 echo --- 隔开，下面输出里的 --- 就是它打印的：

NAME                            CPU(cores)   MEMORY(bytes)   
client                          0m           8Mi             
otel-collector-dbf58864-7c72h   1m           34Mi            
---
2026-10-13T10:54:24Z   otel-collector                    ScalingReplicaSet

client log lines: 0
  • top 只有容器级的 CPU 和内存，没有请求量、错误率、延迟。
  • Events 只记录 Kubernetes 组件对对象做了什么：调度、拉镜像、启动、删除，应用自己的请求错误不在里面。就在这之前的十几秒里，Collector 拒绝了 6 个错误请求（端口协议错位、404、415、400，见后文），Events 里一条都没有。Events 默认也只保留一小时（kube-apiserver --event-ttl 默认 1h0m0s）。
  • 发请求的 client Pod 日志是空的，curl 的输出返回给了 kubectl exec，没有写进容器标准输出。即便应用打了日志，kubectl logs 也只能一个 Pod 一个 Pod 地看，多个服务的日志靠时间戳人工对齐。

OTel 补的就是这块：让应用主动上报带上下文的数据，再集中处理。

部署一个最小的 Collector

Collector 的配置分四块：receivers 接收数据，processors 加工，exporters 发出去，service.pipelines 把它们按信号类型串成流水线。只在顶层声明了的组件，没被任何 pipeline 引用的话，不会启动。

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318
processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 200
    spike_limit_mib: 50
  batch: {}
exporters:
  debug:
    verbosity: detailed
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [debug]
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [debug]
    logs:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [debug]

想亲手复现下一节「监听 localhost」的坑，先把 grpc、http 下面的 endpoint 两行删掉，写成 grpc: {}、http: {} 部署一次，再换回这份配置。

几个键值按 0.114.0 的组件文档核对过：

  • memory_limiter 检查的是进程堆内存，check_interval 默认是 0s，必须显式设置（文档建议 1s）；软限制等于 limit_mib - spike_limit_mib。文档建议把它放在 pipeline 的第一个。
  • batch 默认每 200ms 或攒够 8192 条发一批，应当放在 memory_limiter 之后。
  • debug exporter 的 verbosity 可选 basic（默认）、normal、detailed，只有 detailed 会打印完整字段。

把配置放进 ConfigMap，用 Deployment 跑一个副本，再建一个 Service 暴露 4317（gRPC）和 4318（HTTP）：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: otel-collector
spec:
  replicas: 1
  selector:
    matchLabels:
      app: otel-collector
  template:
    metadata:
      labels:
        app: otel-collector
    spec:
      containers:
        - name: collector
          image: otel/opentelemetry-collector-contrib:0.114.0
          args: ["--config=/conf/config.yaml"]
          ports:
            - name: otlp-grpc
              containerPort: 4317
            - name: otlp-http
              containerPort: 4318
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              memory: 256Mi
          volumeMounts:
            - name: conf
              mountPath: /conf
      volumes:
        - name: conf
          configMap:
            name: otel-collector-conf
---
apiVersion: v1
kind: Service
metadata:
  name: otel-collector
spec:
  selector:
    app: otel-collector
  ports:
    - name: otlp-grpc
      port: 4317
    - name: otlp-http
      port: 4318

发数据的客户端是一个常驻的 curl Pod，和上面两个对象放在同一个 collector.yaml 里：

---
apiVersion: v1
kind: Pod
metadata:
  name: client
  labels:
    app: client
spec:
  containers:
    - name: curl
      image: curlimages/curl:latest
      command: ["sleep", "7200"]
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
        limits:
          memory: 64Mi
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab create configmap otel-collector-conf --from-file=config.yaml
kubectl -n notes-lab apply -f collector.yaml
kubectl -n notes-lab rollout status deploy/otel-collector

后面每次改配置，都是重新生成 ConfigMap 再重启 Deployment：

kubectl -n notes-lab create configmap otel-collector-conf --from-file=config.yaml \
  --dry-run=client -o yaml | kubectl -n notes-lab apply -f -
kubectl -n notes-lab rollout restart deploy/otel-collector

第一个坑：不写 endpoint，Pod 正常但连不上

最开始我把 receiver 写成了很多入门示例里的样子：

receivers:
  otlp:
    protocols:
      grpc: {}
      http: {}

Pod 很快变成 Running，日志最后一行是 Everything is ready。往 Service 发请求却连不上：

$ kubectl -n notes-lab exec client -- curl -sS -m 5 -X POST http://otel-collector:4318/v1/traces -H "Content-Type: application/json" -d "{}"
curl: (7) Failed to connect to otel-collector:4318 after 0 ms: Could not connect to server
command terminated with exit code 7

原因就在启动日志里：

2026-10-13T10:54:10.727Z	info	otlpreceiver@v0.114.0/otlp.go:112	Starting GRPC server	{"kind": "receiver", "name": "otlp", "data_type": "logs", "endpoint": "localhost:4317"}
2026-10-13T10:54:10.727Z	info	otlpreceiver@v0.114.0/otlp.go:169	Starting HTTP server	{"kind": "receiver", "name": "otlp", "data_type": "logs", "endpoint": "localhost:4318"}
2026-10-13T10:54:10.727Z	info	service@v0.114.0/service.go:261	Everything is ready. Begin running and processing data.

这个版本的 OTLP receiver 默认只监听 localhost，同一 Pod 之外的流量进不来。按 Collector 的 CHANGELOG：v0.94.0 加入了特性开关 component.UseLocalHostAsDefaultHost；v0.104.0 起默认启用，OTLP receiver 的默认地址从 0.0.0.0 改成 localhost，CHANGELOG 里还特别提醒这可能让容器环境（比如 Kubernetes）里的 receiver 失效；v0.110.0 这个开关变为 stable，v0.112.0 把它移除了。所以 0.104 以前的教程里 grpc: {} 能直接用，换到新版本就连不上。v0.114.0 的 receiver README 里还写着这个开关「will become the default in a future release」，这句已经过时了，以实际启动日志为准。而 Kubernetes 这边一切正常，因为没配就绪探针，EndpointSlice 里这个 Pod 是就绪的：

otel-collector-6678fb4495-pz726 ready=true

所以 Service 照常把流量转给它，连接在 Pod 里被拒绝。改成 0.0.0.0:4317 / 0.0.0.0:4318 后，启动日志里的 endpoint 变了，同时多出一条警告：

2026-10-13T10:54:25.676Z	warn	internal@v0.114.0/warning.go:40	Using the 0.0.0.0 address exposes this server to every network interface, which may facilitate Denial of Service attacks.	{"kind": "receiver", "name": "otlp", "data_type": "metrics", "documentation": "https://github.com/open-telemetry/opentelemetry-collector/blob/main/docs/security-best-practices.md#safeguards-against-denial-of-service-attacks"}
2026-10-13T10:54:25.677Z	info	otlpreceiver@v0.114.0/otlp.go:112	Starting GRPC server	{"kind": "receiver", "name": "otlp", "data_type": "metrics", "endpoint": "0.0.0.0:4317"}

在 Pod 里监听 0.0.0.0 是让 Service 能转发进来的必要条件，但这也意味着集群内任何能访问到这个端口的 Pod 都能写数据，生产环境要配合 NetworkPolicy、认证和 TLS 来限制访问。

用 curl 发送三种信号

OTLP/HTTP 接受 JSON，路径分别是 /v1/traces、/v1/metrics、/v1/logs。手写 JSON 能让每个字段都看得见。OTLP 的数据是三层嵌套：最外层 resourceSpans 按「谁产生的数据」分组，resource.attributes 描述产生方本身（这里只有 service.name，后面 k8sattributes 补的 Pod 信息也加在这一层）；中间层 scopeSpans 按埋点库分组，scope.name 是埋点库的名字；最里层 spans 才是一个个 span。span 的 kind 是枚举值，2 表示 SERVER（处理收到的请求），3 表示 CLIENT（向外发起的调用，比如查数据库）。指标和日志的结构相同，只是换成 resourceMetrics → scopeMetrics → metrics 和 resourceLogs → scopeLogs → logRecords。下面这条 trace 有两个 span：一个服务端 span POST /checkout，和它的子 span SELECT orders（parentSpanId 指向前者）：

NOW=$(date +%s%N); S1=$((NOW-120000000))
cat > trace.json <<EOF
{"resourceSpans":[{"resource":{"attributes":[{"key":"service.name","value":{"stringValue":"checkout"}}]},
 "scopeSpans":[{"scope":{"name":"manual-curl"},"spans":[
  {"traceId":"5b8efff798038103d269b633813fc60c","spanId":"eee19b7ec3c1b174","name":"POST /checkout","kind":2,
   "startTimeUnixNano":"$S1","endTimeUnixNano":"$NOW",
   "attributes":[{"key":"http.response.status_code","value":{"intValue":"200"}}]},
  {"traceId":"5b8efff798038103d269b633813fc60c","spanId":"eee19b7ec3c1b175","parentSpanId":"eee19b7ec3c1b174","name":"SELECT orders","kind":3,
   "startTimeUnixNano":"$((S1+10000000))","endTimeUnixNano":"$((S1+100000000))",
   "attributes":[{"key":"db.system","value":{"stringValue":"postgresql"}}]}
 ]}]}]}
EOF

指标是一个累计计数器 http.server.request.count，值为 42；日志是一条 ERROR，并且带上了同一个 traceId 和 spanId。在同一个 shell 里接着生成（沿用上面的 $NOW）：

cat > metrics.json <<EOF
{"resourceMetrics":[{"resource":{"attributes":[{"key":"service.name","value":{"stringValue":"checkout"}}]},
 "scopeMetrics":[{"scope":{"name":"manual-curl"},"metrics":[
  {"name":"http.server.request.count","unit":"1","sum":{"aggregationTemporality":2,"isMonotonic":true,
   "dataPoints":[{"asInt":"42","startTimeUnixNano":"$((NOW-60000000000))","timeUnixNano":"$NOW",
   "attributes":[{"key":"http.route","value":{"stringValue":"/checkout"}}]}]}}
 ]}]}]}
EOF
cat > logs.json <<EOF
{"resourceLogs":[{"resource":{"attributes":[{"key":"service.name","value":{"stringValue":"checkout"}}]},
 "scopeLogs":[{"scope":{"name":"manual-curl"},"logRecords":[
  {"timeUnixNano":"$NOW","severityNumber":17,"severityText":"ERROR",
   "body":{"stringValue":"payment gateway timeout after 3s"},
   "traceId":"5b8efff798038103d269b633813fc60c","spanId":"eee19b7ec3c1b174",
   "attributes":[{"key":"order.id","value":{"stringValue":"A-1001"}}]}
 ]}]}]}
EOF

把三个文件拷进 client Pod，按路径依次发送：

for f in trace metrics logs; do kubectl -n notes-lab cp $f.json client:/tmp/$f.json; done
for p in traces:trace metrics:metrics logs:logs; do
  ep=${p%%:*}; f=${p##*:}; echo "--> /v1/$ep"
  kubectl -n notes-lab exec client -- curl -sS -w " HTTP %{http_code}\n" -X POST \
    http://otel-collector:4318/v1/$ep -H "Content-Type: application/json" --data-binary @/tmp/$f.json
done
--> /v1/traces
{"partialSuccess":{}} HTTP 200
--> /v1/metrics
{"partialSuccess":{}} HTTP 200
--> /v1/logs
{"partialSuccess":{}} HTTP 200

对照这三段，三种信号的差别就具体了：

  • Trace 是一组共享 Trace ID 的 span，靠 Parent ID 连成树。子 span 的起止时间落在父 span 之内，能看出 120ms 里有 90ms 花在数据库上。
  • Metric 是一个带时间窗口的数值。Cumulative 表示 42 是从 StartTimestamp 起累计的总数，而不是这一分钟的增量；后端算速率时依赖这个语义。
  • Log 是某个时刻的一条记录。它带着 Trace ID 和 Span ID，后端就能从这条错误日志跳到对应的那次请求。三种信号能互相关联，靠的就是这种上下文，而不是时间戳碰运气。

还有一个小细节：我没填 observedTimeUnixNano，Collector 也没有补，于是显示成了 1970 年。用 SDK 时这个字段由 SDK 填写；手写数据或用某些日志采集器时，后端如果按观测时间排序，就会出现这种怪时间。

端口、协议和路径错位时的报错

应用接 Collector 时，最常见的配置错误是端口和协议对不上：SDK 用 gRPC 却指向 4318，或者用 HTTP 却指向 4317。用 curl 把几种错位都试了一遍。以下命令在 client Pod 内执行，即每条前面加 kubectl -n notes-lab exec client --：

$ curl -sS -X POST http://otel-collector:4317/v1/traces -H "Content-Type: application/json" --data-binary @/tmp/trace.json
curl: (1) Received HTTP/0.9 when not allowed

$ curl -sS -i -X POST http://otel-collector:4317/v1/traces -H "Content-Type: application/json" --data-binary @/tmp/trace.json --http2-prior-knowledge
HTTP/2 415 
content-type: application/grpc
grpc-status: 3
grpc-message: invalid gRPC request content-type "application/json"

$ curl -sS -X POST http://otel-collector:4318/opentelemetry.proto.collector.trace.v1.TraceService/Export -H "Content-Type: application/grpc" --http2-prior-knowledge -d x
curl: (16) Remote peer returned unexpected data while we expected SETTINGS frame.  Perhaps, peer does not support HTTP/2 properly.

$ curl -sS -X POST http://otel-collector:4318/v1/trace -H "Content-Type: application/json" --data-binary @/tmp/trace.json
404 page not found

$ curl -sS -w " HTTP %{http_code}\n" -X POST http://otel-collector:4318/v1/traces -H "Content-Type: text/plain" --data-binary @/tmp/trace.json
415 unsupported media type, supported: [application/json, application/x-protobuf] HTTP 415
现象原因
HTTP/1.1 打到 4317，报 HTTP/0.94317 只说 HTTP/2（gRPC），回来的字节 curl 解析不了
HTTP/2 打到 4317，grpc-message: invalid gRPC request content-type协议对了，但这是 gRPC 服务，不认 JSON
HTTP/2 直连 4318，等不到 SETTINGS 帧4318 是 HTTP/1.1 服务，gRPC 客户端握手失败
404 page not found路径写错，少了一个 s
415 unsupported media typeContent-Type 只能是 application/json 或 application/x-protobuf

最隐蔽的一种是返回 200 但什么都没收到。把指标的 JSON 发到 /v1/traces：

{"partialSuccess":{}} HTTP 200

Collector 日志里在这之后没有任何新输出。/v1/traces 按 trace 的格式解析，不认识的 resourceMetrics 字段被忽略，等于收到了一个空请求。客户端看到 200 就认为发送成功了。字段格式错误则会被拒绝，比如 traceId 不是 32 位十六进制：

{"code":3,"message":"readSpan.traceId: parse trace_id:invalid length for ID, error found in #10 byte of ...|eId\":\"abc\",\"spanId\":|..., ..."} HTTP 400

这几种错误都只出现在客户端的响应里，Collector 的日志（info 级别）和 Kubernetes Events 里都没有记录。应用侧要把 exporter 的错误打出来，否则只会看到「后端没数据」。

k8sattributes：给数据补上 Pod 信息

应用上报的数据里通常只有 service.name，不知道自己跑在哪个 Pod、哪个节点。contrib 版 Collector 里的 k8sattributes processor 会 watch API Server，在本地缓存里维护一份 Pod 列表；数据到达时，按连接的来源 IP 在这份缓存里查出对应的 Pod，把它的元数据补进 resource 属性：

processors:
  k8sattributes:
    auth_type: serviceAccount
    filter:
      namespace: notes-lab
    extract:
      metadata:
        - k8s.namespace.name
        - k8s.pod.name
        - k8s.node.name
    pod_association:
      - sources:
          - from: connection
service:
  pipelines:
    logs:
      receivers: [otlp]
      processors: [memory_limiter, k8sattributes, batch]
      exporters: [debug]

这里只画出了 logs pipeline，实验中 traces、metrics 两条 pipeline 也一样把 k8sattributes 插在 memory_limiter 和 batch 之间。

extract.metadata 不写的话，默认提取 k8s.namespace.name、k8s.pod.name、k8s.pod.uid、k8s.pod.start_time、k8s.deployment.name、k8s.node.name 六个字段，其中 k8s.deployment.name 需要额外读 ReplicaSet。这里只取了三个字段。

没有 RBAC：Pod 照样 Ready，数据照样通过

先用 namespace 的 default ServiceAccount 直接跑。Collector 正常启动，但日志被 client-go 的报错刷屏：

W1013 10:55:22.838566       1 reflector.go:561] k8s.io/client-go@v0.31.2/tools/cache/reflector.go:243: failed to list *v1.Pod: pods is forbidden: User "system:serviceaccount:notes-lab:default" cannot list resource "pods" in API group "" in the namespace "notes-lab"

这时发一条日志，返回 200，输出里只多了一个 k8s.pod.ip，它直接取自连接的来源地址，不需要查 API：

Resource attributes:
     -> service.name: Str(checkout)
     -> k8s.pod.ip: Str(<pod-ip>)

也就是说，权限不够时 processor 不会报错拦截，数据会少几个属性继续往下走。如果只看后端，很难发现。

namespaced Role 够用吗

报错里说的是 in the namespace "notes-lab"，因为配置了 filter.namespace，processor 只 watch 这一个 namespace 的 Pod。那么在 namespace 内建一个 Role 就够了：

apiVersion: v1
kind: ServiceAccount
metadata:
  name: otel-collector
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: otel-collector-pods
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: otel-collector-pods
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: otel-collector-pods
subjects:
  - kind: ServiceAccount
    name: otel-collector
kubectl -n notes-lab apply -f rbac-role.yaml
kubectl -n notes-lab set serviceaccount deploy/otel-collector otel-collector

新 Pod 的日志里 forbidden 计数为 0，再发一条日志：

Resource attributes:
     -> service.name: Str(checkout)
     -> k8s.pod.ip: Str(<pod-ip>)
     -> k8s.node.name: Str(worker)
     -> k8s.pod.name: Str(client)
     -> k8s.namespace.name: Str(notes-lab)

去掉 filter.namespace、保留同一个 Role，报错立刻变成了集群范围：

W1013 10:56:03.456086       1 reflector.go:561] k8s.io/client-go@v0.31.2/tools/cache/reflector.go:243: failed to list *v1.Pod: pods is forbidden: User "system:serviceaccount:notes-lab:otel-collector" cannot list resource "pods" in API group "" at the cluster scope

不加 filter 时 processor 要 list 全集群的 Pod，只能用 ClusterRole + ClusterRoleBinding。ClusterRoleBinding 的 subject 必须写明 ServiceAccount 所在的 namespace。保存为 rbac-cluster.yaml：

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: notes-lab-observability-pods
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: notes-lab-observability-pods
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: notes-lab-observability-pods
subjects:
  - kind: ServiceAccount
    name: otel-collector
    namespace: notes-lab
kubectl apply -f rbac-cluster.yaml

apply 之后没有重启 Collector，5 秒后新日志里已经没有 forbidden，再发数据 k8s.pod.name 就补上了。client-go 的 informer 会自己退避重试，权限到位后自动恢复。验证完我立刻删掉了这两个集群级对象：

kubectl delete -f rbac-cluster.yaml

官方文档说，集群范围部署时需要对 pods 和 namespaces 都有 get/watch/list 权限；用 namespace filter 时只查这个 namespace 的 Pod 和 ReplicaSet，但也就取不到 node、namespace 对象上的标签和注解了。这次两种方式都只给了 pods 权限，也都成功补上了属性，推测是因为提取的字段里没用到 namespace 对象的元数据（k8s.namespace.name 直接取自 Pod 本身）。RBAC 本身见 RBAC。

放在 batch 后面，属性全丢

先把 filter.namespace: notes-lab 加回去（ClusterRole 已删，只剩 namespaced Role），再把三条 pipeline 的 processors 顺序都改成 [memory_limiter, batch, k8sattributes]，其余配置和带 filter 的那一版相同。权限不变，再发一次：

Resource attributes:
     -> service.name: Str(checkout)
ScopeLogs #0

这次连 k8s.pod.ip 都没有了，也没有任何报错。from: connection 依赖请求的连接信息，而 batch 把多次请求的数据攒在一起再往下发，这时连接上下文已经没了。文档的要求是 k8sattributes 必须放在任何批处理或尾部采样之前。所以 memory_limiter → k8sattributes → batch 这个顺序不是随便排的。

配置写错：Collector 直接拒绝启动

Collector 对配置的检查很严格，写错键名、写错枚举值、引用了未定义的组件，都会直接退出。可以在发布前用镜像自带的 validate 子命令检查。我用同一个镜像跑一个一次性 Pod，把待检查的配置放进 ConfigMap bad-conf，对几份故意写错的配置分别执行：

kubectl -n notes-lab create configmap bad-conf --from-file=config.yaml=bad.yaml
kubectl -n notes-lab run validate --image=otel/opentelemetry-collector-contrib:0.114.0 --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"validate","image":"otel/opentelemetry-collector-contrib:0.114.0","args":["validate","--config=/conf/config.yaml"],"volumeMounts":[{"name":"c","mountPath":"/conf"}]}],"volumes":[{"name":"c","configMap":{"name":"bad-conf"}}]}}'
kubectl -n notes-lab wait --for=jsonpath='{.status.phase}'=Failed pod/validate --timeout=60s
kubectl -n notes-lab get pod validate -o jsonpath='{.status.phase} exit={.status.containerStatuses[0].state.terminated.exitCode}{"\n"}'
kubectl -n notes-lab logs validate

换下一份配置前，先删掉 validate Pod，再用 --dry-run=client -o yaml | kubectl apply -f - 更新 bad-conf。

把 limit_mib 写成 limit_mb：

Failed exit=1
Error: failed to get config: cannot unmarshal the configuration: decoding failed due to the following error(s):

error decoding 'processors': error reading configuration for "memory_limiter": decoding failed due to the following error(s):

'' has invalid keys: limit_mb

pipeline 里引用了没定义的 attributes processor：

Failed exit=1
Error: service::pipelines::traces: references processor "attributes" which is not configured

verbosity 写成 verbose。报错说的是 metrics level，和 debug exporter 的字面意思对不上，但定位到了出错的组件和键：

Error: failed to get config: cannot unmarshal the configuration: decoding failed due to the following error(s):

error decoding 'exporters': error reading configuration for "debug": decoding failed due to the following error(s):

error decoding 'verbosity': unknown metrics level "verbose"

删掉 memory_limiter 的 check_interval：

Error: processors::memory_limiter: 'check_interval' must be greater than zero

正确的配置返回 Succeeded exit=0，没有任何输出；检查正确配置时，wait 那一行要改成等 =Succeeded，否则会一直等到超时。

不做校验、直接把 limit_mb 那份推上去会怎样？新 Pod 进入 CrashLoopBackOff，而 Deployment 的滚动更新卡住，旧 Pod 继续服务：

NAME                              READY   STATUS             RESTARTS      AGE
otel-collector-67d7b877-d525w     0/1     CrashLoopBackOff   2 (21s ago)   40s
otel-collector-6d4776484b-pcdj5   1/1     Running            0             2m21s
Waiting for deployment "otel-collector" rollout to finish: 1 old replicas are pending termination...
error: timed out waiting for the condition

这时往 Service 发数据仍然返回 200，由旧 Pod 接收。新 Pod 起不来，滚动更新就不会继续删旧 Pod，这是 Deployment 滚动更新的保护。但要注意，ConfigMap 已经是坏的了，旧 Pod 一旦因为别的原因重启，也会起不来。validate 能查出键名、类型和引用错误，查不出「监听 localhost」「后端地址不存在」这类运行时问题，下面这份配置就能通过校验。

后端不可达：重试、队列满、丢数据

把 traces 的出口换成一个指向不存在地址的 OTLP exporter，并且故意把队列调得很小，让现象在几十秒内出现：

exporters:
  otlp/backend:
    endpoint: no-such-backend:4317
    tls:
      insecure: true
    timeout: 2s
    retry_on_failure:
      enabled: true
      initial_interval: 1s
      max_interval: 4s
      max_elapsed_time: 20s
    sending_queue:
      enabled: true
      num_consumers: 1
      queue_size: 2
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter]
      exporters: [otlp/backend]

这里特意去掉了 batch，原因见本节末尾的对照实验。

连发 6 个 trace 请求（每个 2 个 span）：

kubectl -n notes-lab exec client -- sh -c 'for i in 1 2 3 4 5 6; do
  curl -sS -m 5 -w " #$i HTTP %{http_code}\n" -X POST http://otel-collector:4318/v1/traces \
    -H Content-Type:application/json --data-binary @/tmp/trace.json; done'
{"partialSuccess":{}} #1 HTTP 200
{"partialSuccess":{}} #2 HTTP 200
{"partialSuccess":{}} #3 HTTP 200
{"code":14,"message":"sending queue is full"} #4 HTTP 503
{"code":14,"message":"sending queue is full"} #5 HTTP 503
{"code":14,"message":"sending queue is full"} #6 HTTP 503

一个请求正被唯一的消费者拿着重试，队列里还能放两个，所以前三个被接受，后三个直接收到 503。Collector 日志按时间顺序是这样的（节选，去掉了堆栈）：

2026-10-13T11:00:32.241Z	info	internal/retry_sender.go:126	Exporting failed. Will retry the request after interval.	{"kind": "exporter", "data_type": "traces", "name": "otlp/backend", "error": "rpc error: code = Unavailable desc = connection error: desc = \"transport: Error while dialing: dial tcp: lookup no-such-backend on <cluster-dns-ip>:53: server misbehaving\"", "interval": "805.339066ms"}
2026-10-13T11:00:32.251Z	error	internal/base_exporter.go:130	Exporting failed. Rejecting data.	{"kind": "exporter", "data_type": "traces", "name": "otlp/backend", "error": "sending queue is full", "rejected_items": 2}
2026-10-13T11:00:35.377Z	info	internal/retry_sender.go:126	Exporting failed. Will retry the request after interval.	{"kind": "exporter", "data_type": "traces", "name": "otlp/backend", "error": "rpc error: code = Unavailable ...", "interval": "4.947092936s"}
2026-10-13T11:00:49.202Z	error	internal/queue_sender.go:92	Exporting failed. Dropping data.	{"kind": "exporter", "data_type": "traces", "name": "otlp/backend", "error": "no more retries left: rpc error: code = Unavailable ...", "dropped_items": 2}

Will retry 的间隔从 0.8 秒涨到 5 秒左右，带随机抖动；17 秒后第一批数据用完了重试时间，被 Dropping data 丢弃，之后另外两批依次在 11:01:08 和 11:01:25 被丢弃。DNS 这里报的是 server misbehaving 而不是常见的 no such host，推测和这个集群 CoreDNS 的上游转发有关，排查时把它当作「名字解析失败」即可。

Collector 自己的内部指标监听在 Pod 内的 localhost:8888，用 port-forward 读出来，账目很清楚：

kubectl -n notes-lab port-forward deploy/otel-collector 18888:8888 &
curl -s localhost:18888/metrics | grep -E '^otelcol_(exporter|receiver)_[a-z_]+\{' | grep -v _bucket \
  | sed -E 's/service_instance_id="[^"]+",//; s/service_version="[^"]+",?//; s/service_name="otelcol-contrib",?//'

末尾的 sed 去掉了每行都相同的 service_* 标签，方便阅读。port-forward 绑定的是当时那个 Pod，每次 rollout restart 换了新 Pod 之后，要先结束旧的 port-forward 再重新执行一次。

otelcol_exporter_enqueue_failed_spans{exporter="otlp/backend",} 6
otelcol_exporter_queue_capacity{exporter="otlp/backend",} 2
otelcol_exporter_queue_size{data_type="traces",exporter="otlp/backend",} 0
otelcol_exporter_send_failed_spans{exporter="otlp/backend",} 6
otelcol_exporter_sent_spans{exporter="otlp/backend",} 0
otelcol_receiver_accepted_spans{receiver="otlp",transport="http"} 6
otelcol_receiver_refused_spans{receiver="otlp",transport="http"} 6

12 个 span，6 个在入口就被拒（客户端知道），6 个被接受后重试失败丢弃（客户端不知道），成功发出 0 个。客户端拿到 200 只代表数据进了 Collector 的内存队列，不代表到了后端。 默认值比这里宽松得多：retry_on_failure 默认 initial_interval: 5s、max_interval: 30s、max_elapsed_time: 300s，sending_queue 默认 num_consumers: 10、queue_size: 1000，而且这个队列在内存里，Collector 重启时队列里的数据也就没了。生产环境里，otelcol_exporter_send_failed_* 和 otelcol_exporter_queue_size 接近 queue_capacity 都值得告警。

加上 batch 再试一次

同一份配置，只把 traces pipeline 的 processors 改成 [memory_limiter, batch]，重新部署后同样发 6 个请求，每个之间隔 0.5 秒，让它们落进不同的批次：

kubectl -n notes-lab exec client -- sh -c 'for i in 1 2 3 4 5 6; do
  curl -sS -m 5 -w " #$i HTTP %{http_code}\n" -X POST http://otel-collector:4318/v1/traces \
    -H Content-Type:application/json --data-binary @/tmp/trace.json; sleep 0.5; done'
{"partialSuccess":{}} #1 HTTP 200
{"partialSuccess":{}} #2 HTTP 200
{"partialSuccess":{}} #3 HTTP 200
{"partialSuccess":{}} #4 HTTP 200
{"partialSuccess":{}} #5 HTTP 200
{"partialSuccess":{}} #6 HTTP 200

6 个全是 200，但 Collector 内部照样在丢。日志里有 3 条这样的记录：

2026-10-13T11:15:31.223Z	error	internal/base_exporter.go:130	Exporting failed. Rejecting data.	{"kind": "exporter", "data_type": "traces", "name": "otlp/backend", "error": "sending queue is full", "rejected_items": 2}

重新 port-forward 后读指标（同样用 sed 去掉了 service_* 标签）：

curl -s localhost:18888/metrics \
  | grep -E '^otelcol_(exporter_enqueue_failed|exporter_sent|receiver_accepted|receiver_refused)_spans' \
  | sed -E 's/service_instance_id="[^"]+",//; s/service_version="[^"]+",?//; s/service_name="otelcol-contrib",?//'
otelcol_exporter_enqueue_failed_spans{exporter="otlp/backend",} 6
otelcol_receiver_accepted_spans{receiver="otlp",transport="http"} 12
otelcol_receiver_refused_spans{receiver="otlp",transport="http"} 0

receiver 记的是 12 个全部接受、0 个拒绝，被拒的 6 个只在 exporter 的指标和 Collector 日志里看得到。进了队列的另外 6 个最后怎样，本轮读完指标（发送后约 12 秒）就结束了实验，没等到结果。batch 收下数据就向 receiver 返回成功，之后再异步往 exporter 送，exporter 的「队列满」传不回客户端。所以有 batch 时，只看客户端返回码或 receiver 的指标，都发现不了后端的问题。

memory_limiter 拒收数据

触发 memory_limiter 不需要压测，把上限调得比 Collector 空闲时的堆还小就行。把 limit_mib 设为 12、spike_limit_mib 设为 4（软限制 8 MiB）：

2026-10-13T11:01:41.565Z	warn	memorylimiter@v0.114.0/memorylimiter.go:184	Memory usage is above hard limit. Forcing a GC.	{"kind": "processor", "name": "memory_limiter", "pipeline": "logs", "cur_mem_mib": 50}
2026-10-13T11:01:41.568Z	info	memorylimiter@v0.114.0/memorylimiter.go:173	Memory usage after GC.	{"kind": "processor", "name": "memory_limiter", "pipeline": "logs", "cur_mem_mib": 38}
2026-10-13T11:01:41.568Z	warn	memorylimiter@v0.114.0/memorylimiter.go:210	Memory usage is above soft limit. Refusing data.	{"kind": "processor", "name": "memory_limiter", "pipeline": "logs", "cur_mem_mib": 38}

一条数据都还没收，contrib 版 Collector 的堆在 GC 后也有 38 MiB。此后每秒都强制 GC 一次，堆停在 38 MiB 降不下来。这时发数据：

{"code":14,"message":"data refused due to high memory usage"} HTTP 503

超过软限制时拒收，超过硬限制时额外强制 GC。返回的是可重试的错误（gRPC code 14，即 Unavailable），发送方可以据此稍后重试，这正是把它放在 pipeline 第一位的用意：在内存吃紧时把压力推回发送方，而不是被 OOMKilled 后丢掉所有数据。

上限要和容器的内存 limit 一起算。文档说进程总内存通常比 limit_mib 高约 50 MiB，前面用的 limit_mib: 200 配上 256Mi 的 limit 就已经贴边了。limit_percentage 按 cgroup 的内存限制取百分比，比写死 MiB 更不容易和 limit 对不上；两者同时写时 limit_mib 优先。

清理

kubectl delete namespace notes-lab
kubectl get clusterrole,clusterrolebinding | grep notes-lab

实验用到的 ClusterRole 和 ClusterRoleBinding 在验证完 k8sattributes 后就已删除，删掉 namespace 后，ServiceAccount、Role、ConfigMap 和 Pod 都随之清理。

回头看，Collector 的数据流本身很直白：receiver 收、processor 改、exporter 发。容易出问题的是各环节之间的衔接，而且很多故障都不报错：监听在 localhost 上 Pod 照样 Ready，发错路径照样返回 200，k8sattributes 没权限或者排错了位置就悄悄少几个属性，后端挂了客户端照样拿到 200。所以接入时要看的是数据最终长什么样、发出去了多少，以及 Collector 自己的 otelcol_* 指标。Kubernetes 自身组件（kube-apiserver、kubelet）也能通过 OTLP 输出 trace，见下方参考链接。
