Secret 给了你什么，没给你什么

Namespace、ConfigMap 与 Secret 已经实测过 Secret 的基本形态：data 只是 base64 编码，一条 base64 -d 就还原；describe 只显示字节数；Secret 卷挂在 tmpfs 上；immutable: true 之后改值、改回 false 都会被拒；etcd 里的值在没开静态加密时就是原文。这些不再重复。

这一篇关心的是另一类问题：除了直接 get 之外，还有哪些路径能读到 Secret；把 Secret 只挂给一个容器，到底隔离到什么程度。

下文输出都来自一个三节点 kind 集群（Server Version: v1.31.0，CNI 为 Calico），实验放在单独的 notes-lab namespace 里，敏感值一律是 example-only-not-real 这样的演示值。

仅使用演示值。不要把真实密钥写进清单、终端历史、Git 仓库或文章截图。

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab create secret generic demo-token \
  --from-literal=token=example-only-not-real \
  --from-literal=user=demo-user

谁能读到它

建三个 ServiceAccount，各给一种权限：

for sa in pod-viewer pod-creator secret-lister; do
  kubectl -n notes-lab create sa $sa
done
kubectl -n notes-lab create role pod-viewer    --verb=get,list --resource=pods
kubectl -n notes-lab create role pod-creator   --verb=create   --resource=pods
kubectl -n notes-lab create role secret-lister --verb=list     --resource=secrets
for r in pod-viewer pod-creator secret-lister; do
  kubectl -n notes-lab create rolebinding $r --role=$r --serviceaccount=notes-lab:$r
done

权限矩阵：

$ for sa in pod-viewer pod-creator secret-lister; do
    printf "%-14s get-secrets=%s list-secrets=%s create-pods=%s pods-log=%s pods-exec=%s\n" $sa \
      "$(kubectl -n notes-lab auth can-i get secrets --as=system:serviceaccount:notes-lab:$sa)" \
      "$(kubectl -n notes-lab auth can-i list secrets --as=system:serviceaccount:notes-lab:$sa)" \
      "$(kubectl -n notes-lab auth can-i create pods --as=system:serviceaccount:notes-lab:$sa)" \
      "$(kubectl -n notes-lab auth can-i get pods --subresource=log --as=system:serviceaccount:notes-lab:$sa)" \
      "$(kubectl -n notes-lab auth can-i create pods --subresource=exec --as=system:serviceaccount:notes-lab:$sa)"
  done
pod-viewer     get-secrets=no list-secrets=no create-pods=no pods-log=no pods-exec=no
pod-creator    get-secrets=no list-secrets=no create-pods=yes pods-log=no pods-exec=no
secret-lister  get-secrets=no list-secrets=yes create-pods=no pods-log=no pods-exec=no

写这张表时踩了一个坑。最初写的是 kubectl auth can-i get pods/log，结果 pod-viewer 一栏给出了 yes，pod-creator 的 create pods/exec 也是 yes。原因是 can-i 的参数按 VERB TYPE[/NAME] 解析，pods/log 被理解成「名为 log 的 pod」，检查的其实是 get pods。所以只有本来就有 get pods（或 create pods）权限的主体才会得到这个误导性的 yes，没有的照样是 no，不容易察觉。检查子资源要写 --subresource=log、--subresource=exec。

没有 Secret 权限的主体读不到

$ kubectl -n notes-lab get secret demo-token --as=system:serviceaccount:notes-lab:pod-viewer
Error from server (Forbidden): secrets "demo-token" is forbidden: User "system:serviceaccount:notes-lab:pod-viewer" cannot get resource "secrets" in API group "" in the namespace "notes-lab"

只给 list 不给 get 也挡不住内容，RBAC 那篇已经用 ConfigMap 演示过 list 返回完整对象。换成 Secret 结果一样，get 被拒，list 照样能拿到值：

$ kubectl -n notes-lab get secrets --as=system:serviceaccount:notes-lab:secret-lister \
    -o jsonpath='{.items[*].data.token}' | base64 -d
example-only-not-real

能创建 Pod 就能读 Secret

pod-creator 对 Secret 没有 get，也没有 list，但它能创建 Pod。把目标 Secret 挂进自己创建的 Pod，再读文件就行：

# reader.yaml
apiVersion: v1
kind: Pod
metadata:
  name: mount-reader
spec:
  restartPolicy: Never
  containers:
    - name: reader
      image: busybox:1.36
      command: ["sh", "-c", "cat /mnt/secret/token; echo"]
      volumeMounts:
        - name: s
          mountPath: /mnt/secret
          readOnly: true
  volumes:
    - name: s
      secret:
        secretName: demo-token

第一次用 apply -f 提交失败了：

$ kubectl -n notes-lab apply -f reader.yaml --as=system:serviceaccount:notes-lab:pod-creator
Error from server (Forbidden): error when retrieving current configuration of:
...
from server for: "reader.yaml": pods "mount-reader" is forbidden: User "system:serviceaccount:notes-lab:pod-creator" cannot get resource "pods" in API group "" in the namespace "notes-lab"

apply 要先 get 现有对象来计算差异，而 pod-creator 只有 create。换成 create -f 就过了：

$ kubectl -n notes-lab create -f reader.yaml --as=system:serviceaccount:notes-lab:pod-creator
pod/mount-reader created
$ kubectl -n notes-lab wait --for=jsonpath='{.status.phase}'=Succeeded pod/mount-reader --timeout=60s
pod/mount-reader condition met
$ kubectl -n notes-lab logs mount-reader
example-only-not-real

pod-creator 自己没有 pods/log 权限，这里的日志是用管理员身份看的。不过这不影响结论：Pod 里的程序已经读到了值，接下来是写到日志还是发到别处，都由创建 Pod 的人决定。这是设计如此，挂载 Secret 时 kubelet 不检查 Pod 的创建者能不能读这个 Secret。官方文档原话是：anyone who is authorized to create a Pod in a namespace can use that access to read any Secret in that namespace; this includes indirect access such as the ability to create a Deployment。所以审视 Secret 的读取权限时，要把能在这个 namespace 创建 Pod、Deployment、Job 的主体都算进去。

按容器挂载能隔离到什么程度

Secret 卷和 env 都在容器级别声明。下面这个 Pod（保存为 demo.yaml） 只给 needs-token 挂卷、注入环境变量，no-token 什么都不给：

# demo.yaml
apiVersion: v1
kind: Pod
metadata:
  name: secret-demo
spec:
  securityContext:
    fsGroup: 2000
  containers:
    - name: needs-token
      image: busybox:1.36
      command: ["sleep", "3600"]
      env:
        - name: TOKEN_ENV
          valueFrom:
            secretKeyRef: {name: demo-token, key: token}
      volumeMounts:
        - name: cred
          mountPath: /run/credentials
          readOnly: true
    - name: no-token
      image: busybox:1.36
      command: ["sleep", "3600"]
  volumes:
    - name: cred
      secret:
        secretName: demo-token
        defaultMode: 0400
        items:
          - {key: token, path: token}
kubectl -n notes-lab apply -f demo.yaml && kubectl -n notes-lab wait --for=condition=Ready pod/secret-demo --timeout=120s
$ kubectl -n notes-lab exec secret-demo -c needs-token -- cat /run/credentials/token
example-only-not-real

$ kubectl -n notes-lab exec secret-demo -c no-token -- sh -c 'ls /run/credentials; env | grep -c TOKEN_ENV'
ls: /run/credentials: No such file or directory
0

挂载范围确实是按容器划分的。但这只是挂载范围，不是进程隔离，下面会看到。

defaultMode 0400 加上 fsGroup 后实际变为 0440

卷里的 token 是一个指向 ..data/token 的符号链接（kubelet 用它做原子更新），要用 ls -lL 跟到真实文件才能看到权限：

$ kubectl -n notes-lab exec secret-demo -c needs-token -- ls -l /run/credentials/
lrwxrwxrwx    1 root     2000            12 ... token -> ..data/token
$ kubectl -n notes-lab exec secret-demo -c needs-token -- ls -lL /run/credentials/token
-r--r-----    1 root     2000            21 ... /run/credentials/token

写的是 0400，实际是 -r--r-----，也就是 0440：设了 fsGroup 之后，kubelet 把文件属组改成 2000，并给属组补上了读权限。

而且上面这个容器以 root 运行，root 不受文件权限限制，所以这个例子其实演示不出权限起了什么作用。改成非 root 用户（runAsUser: 1000、runAsGroup: 3000）再测两种情况。不设 fsGroup 时：

# nofsgroup.yaml
apiVersion: v1
kind: Pod
metadata:
  name: nofsgroup-demo
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      securityContext: {runAsUser: 1000, runAsGroup: 3000}
      volumeMounts:
        - {name: cred, mountPath: /run/credentials, readOnly: true}
  volumes:
    - name: cred
      secret:
        secretName: demo-token
        defaultMode: 0400
kubectl -n notes-lab apply -f nofsgroup.yaml && kubectl -n notes-lab wait --for=condition=Ready pod/nofsgroup-demo --timeout=120s

文件保持 root:root 0400，非 root 进程读不了：

$ kubectl -n notes-lab exec nofsgroup-demo -c app -- sh -c 'id; ls -lL /run/credentials/token; cat /run/credentials/token'
uid=1000 gid=3000 groups=3000
-r--------    1 root     root            21 ... /run/credentials/token
cat: can't open '/run/credentials/token': Permission denied

设了 fsGroup: 2000 后，文件变成 root:2000 0440。但 fsGroup 是 Pod 级字段，会作为附加组加给 Pod 里的每一个容器。用两个不同 uid 的容器挂同一个卷来验证：

# nonroot.yaml
apiVersion: v1
kind: Pod
metadata:
  name: nonroot-demo
spec:
  securityContext:
    fsGroup: 2000
  containers:
    - name: owner-group
      image: busybox:1.36
      command: ["sleep", "3600"]
      securityContext: {runAsUser: 1000, runAsGroup: 3000}
      volumeMounts:
        - {name: cred, mountPath: /run/credentials, readOnly: true}
    - name: other-group
      image: busybox:1.36
      command: ["sleep", "3600"]
      securityContext: {runAsUser: 1001, runAsGroup: 3001}
      volumeMounts:
        - {name: cred, mountPath: /run/credentials, readOnly: true}
  volumes:
    - name: cred
      secret:
        secretName: demo-token
        defaultMode: 0400
kubectl -n notes-lab apply -f nonroot.yaml && kubectl -n notes-lab wait --for=condition=Ready pod/nonroot-demo --timeout=120s

两个容器都读得到：

$ for c in owner-group other-group; do echo "== $c"; kubectl -n notes-lab exec nonroot-demo -c $c -- \
    sh -c 'id; ls -lL /run/credentials/token; cat /run/credentials/token; echo'; done
== owner-group
uid=1000 gid=3000 groups=2000,3000
-r--r-----    1 root     2000            21 ... /run/credentials/token
example-only-not-real
== other-group
uid=1001 gid=3001 groups=2000,3001
-r--r-----    1 root     2000            21 ... /run/credentials/token
example-only-not-real

结论是：fsGroup 解决的是「非 root 进程读得到挂载的文件」，不能区分同一个 Pod 里的容器。要让某个容器读不到，就别给它挂这个卷。非 root 运行的配置见 SecurityContext。

环境变量与文件

同样的值，通过 env 注入的话，在容器里一条命令就能打出来：

$ kubectl -n notes-lab exec secret-demo -c needs-token -- sh -c 'echo $TOKEN_ENV'
example-only-not-real

问题不在于 env 能被读到（文件也能被读到），而在于几点差别：

  • 环境变量跟着进程走，子进程会继承；同 uid 的进程（包括 kubectl exec 进去的 shell）都能读到，没法像文件那样单独设属组和权限位；
  • 环境变量容易被意外带出去，比如启动时打印全部配置的日志、带环境信息的崩溃转储、错误上报；
  • 环境变量在容器启动时取值，运行中的容器看不到 Secret 的更新。官方文档（ConfigMap 一节）的说法是 ConfigMaps consumed as environment variables are not updated automatically and require a pod restart。kubelet 每次启动容器都会重新生成环境变量，Secret 轮换里实测过：容器原地重启后拿到的就是新值，不必重建 Pod，但不能指望靠容器重启来完成轮换。

kubectl describe pod 不会打印值，只显示来源：

$ kubectl -n notes-lab describe pod secret-demo | grep -A1 Environment
    Environment:
      TOKEN_ENV:  <set to the key 'token' in secret 'demo-token'>  Optional: false

敏感值能用文件就用文件。

shareProcessNamespace 会打穿按容器的隔离

前面 no-token 看不到 needs-token 的任何东西，前提是两个容器各有独立的 PID 命名空间。开启 shareProcessNamespace: true 之后情况就变了。shared.yaml 和 secret-demo 基本一样，只多了一个字段，去掉了 fsGroup：

# shared.yaml
apiVersion: v1
kind: Pod
metadata:
  name: shared-ns-demo
spec:
  shareProcessNamespace: true
  containers:
    - name: needs-token
      image: busybox:1.36
      command: ["sleep", "3600"]
      env:
        - name: TOKEN_ENV
          valueFrom:
            secretKeyRef: {name: demo-token, key: token}
      volumeMounts:
        - {name: cred, mountPath: /run/credentials, readOnly: true}
    - name: no-token
      image: busybox:1.36
      command: ["sleep", "3600"]
  volumes:
    - name: cred
      secret:
        secretName: demo-token
        defaultMode: 0400
        items:
          - {key: token, path: token}

在 no-token 里能看到整个 Pod 的进程：

kubectl -n notes-lab apply -f shared.yaml && kubectl -n notes-lab wait --for=condition=Ready pod/shared-ns-demo --timeout=120s
$ kubectl -n notes-lab exec shared-ns-demo -c no-token -- ps
PID   USER     TIME  COMMAND
    1 65535     0:00 /pause
    7 root      0:00 sleep 3600
   19 root      0:00 sleep 3600
   31 root      0:00 ps

能读到挂载文件的 pid 7 就是 needs-token。no-token 自己没有挂卷，却能通过 /proc/7/root 读到对方的文件，通过 /proc/7/environ 读到对方的环境变量：

$ kubectl -n notes-lab exec shared-ns-demo -c no-token -- sh -c 'ls /run/credentials 2>&1
    for p in $(pgrep sleep); do echo "pid $p:"; cat /proc/$p/root/run/credentials/token 2>&1; echo
      tr "\0" "\n" < /proc/$p/environ 2>&1 | grep TOKEN_ENV; done'
ls: /run/credentials: No such file or directory
pid 7:
example-only-not-real
TOKEN_ENV=example-only-not-real
pid 19:
cat: can't open '/proc/19/root/run/credentials/token': No such file or directory

pid 19 是 no-token 自己的 sleep，它没有这个挂载，所以找不到文件，这是正常的。

官方文档在 Share Process Namespace 里写得很明确：Container filesystems are visible to other containers in the pod through the /proc/$pid/root link. This makes debugging easier, but it also means that filesystem secrets are protected only by filesystem permissions.

这里两个容器都以 root 运行。复制 shared.yaml 为 shared-nonroot.yaml，只改两处：metadata.name 改成 shared-ns-nonroot，no-token 容器加上

securityContext:
  runAsUser: 1001
kubectl -n notes-lab apply -f shared-nonroot.yaml && kubectl -n notes-lab wait --for=condition=Ready pod/shared-ns-nonroot --timeout=120s

两条路径都被拒：

$ kubectl -n notes-lab exec shared-ns-nonroot -c no-token -- sh -c 'id; ps
    for p in $(pgrep sleep); do echo "pid $p:"; cat /proc/$p/root/run/credentials/token 2>&1; echo
      tr "\0" "\n" < /proc/$p/environ 2>&1 | grep -E "TOKEN_ENV|denied"; done'
uid=1001 gid=0(root) groups=0(root)
PID   USER     TIME  COMMAND
    1 65535     0:00 /pause
    7 root      0:00 sleep 3600
   19 1001      0:00 sleep 3600
...
pid 7:
cat: can't open '/proc/7/root/run/credentials/token': Permission denied

sh: can't open /proc/7/environ: Permission denied
pid 19:
cat: can't open '/proc/19/root/run/credentials/token': No such file or directory

被拒的原因，这个实验区分不出来，两种都有可能：一是普通文件权限，token 是 root:root 0400，uid 1001 本来就读不了；二是内核对 /proc/<pid>/root 和 /proc/<pid>/environ 的 ptrace 访问检查，uid 不同又没有 CAP_SYS_PTRACE 就会被拒。只有一条证据单独指向后者：root 容器去读 pause 进程（uid 65535）的 /proc/1/environ 时也被拒了（sh: can't open /proc/1/environ: Permission denied），root 不受文件权限限制，这次拦住它的推测是 ptrace 检查。无论是哪一种，结论都一样：必须共享进程命名空间时（比如为了调试 sidecar），让各容器用不同的非 root uid 运行，Secret 才还有一层保护。

更新与大小

Secret 卷更新后，kubelet 会把新值同步到文件，但有延迟；subPath 挂载的不会更新；应用还得重新读取文件才会用上新值。这些时序和轮换策略见 Secret 轮换。不再变化的 Secret 可以设 immutable: true，效果和 ConfigMap 一样，见 configuration 那篇。

单个 Secret 有 1MiB 的大小上限。生成一个 1048577 字节（1MiB 加 1 字节）的文件放进去：

$ head -c 1048577 /dev/zero | tr '\0' 'a' > big.txt
$ kubectl -n notes-lab create secret generic big-demo --from-file=blob=big.txt
error: failed to create secret Secret "big-demo" is invalid: data: Too long: must have at most 1048576 bytes

Secret 里不要放大文件或二进制资产，那些应该走卷或对象存储。证书和私钥照常放，用 kubernetes.io/tls 类型的 Secret。

集群怎么存它

官方文档的说法是：Kubernetes Secrets are, by default, stored unencrypted in the API server’s underlying data store (etcd). 在这个集群上 etcd 的实际内容，configuration 那篇已经用 etcdctl 只读检查过：存的是 protobuf 序列化后的对象，值是原文。

不进 etcd 也有办法初步判断：静态加密要靠 kube-apiserver 的 --encryption-provider-config 参数开启，看它的启动参数就行：

$ kubectl -n kube-system get pods -l component=kube-apiserver \
    -o jsonpath='{range .items[*].spec.containers[*].command[*]}{@}{"\n"}{end}' | grep -i encryption \
  || echo "NO --encryption-provider-config flag present"
NO --encryption-provider-config flag present

apiserver 的启动参数里没有 --encryption-provider-config，可以推断没有启用静态加密。这个方法只适用于 apiserver 以静态 Pod 运行、能看到它的集群（kubeadm、kind 这类）；托管集群的控制平面由云厂商运行，看不到 apiserver Pod，这个方法用不了，要看厂商控制台或文档里的加密选项。生产环境应该开启静态加密，最好使用 KMS provider，不要把加密密钥直接写在 provider 配置文件里，开启方法见 Encrypting Confidential Data at Rest。

如果不希望 Secret 原文出现在 Git 仓库里，社区有两类工具：一类把加密后的密文提交进仓库，由集群内的控制器解密（如 Sealed Secrets）；另一类从外部密钥管理系统同步到集群（如 External Secrets Operator）。它们管的是密文怎么入库、密钥从哪里来，同步进集群后仍然是普通的 Secret，本文测到的边界照样存在：能创建 Pod 就能读，list 能拿到值，共享进程命名空间会让其他容器看到。

小结

收紧 Secret 的读取权限，要看三类主体：有 get 的，有 list/watch 的，以及能在这个 namespace 创建 Pod 或工作负载的。在 Pod 内部，按容器挂载是有效的边界，但 fsGroup 会作用到所有容器，shareProcessNamespace 会让其他容器经 /proc/<pid>/root 看到文件，到最后只剩文件权限和 uid 在起作用。敏感值用文件而不是环境变量，以非 root 运行，并确认集群开启了静态加密。
