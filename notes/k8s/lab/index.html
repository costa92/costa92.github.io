本地实验环境

这个专栏里的实验都跑在本机的 kind 集群上：Kubernetes v1.31.0，一个控制平面加两个 worker，每篇的资源都放在单独的 notes-lab namespace 里。这一篇把这套环境从零搭一遍，顺带记录搭建时实际碰到的几个坑。专栏自己用的那个集群和这里一样是 kind 建的 v1.31.0 三节点集群，区别是它额外装了下面这些组件。各篇笔记里只写了版本，没有安装步骤，这里也只搭最基础的部分；想完全对齐，需要按官方文档自己装：

组件专栏集群里的版本官方安装文档
Calico（替换 kindnet）v3.32.1，Tigera operator v1.42.3Calico 在 kind 上的快速入门
metrics-serverv0.8.1，带 --kubelet-insecure-tlsmetrics-server README
Traefikv3.7.9，Helm chart traefik-41.1.0Traefik Helm chart
Gateway API CRDv1.5.0，Standard channelInstalling Gateway API

不装 Calico 时用的是 kind 自带的 kindnet，NetworkPolicy 相关笔记的结果可能对不上，原因见下文「CNI：kindnet」一节。

kind（Kubernetes in Docker）把每个节点做成一个 Docker 容器，容器里跑 systemd、containerd 和 kubelet，再用 kubeadm 拉起集群。和另外两个常见选择比：minikube 默认是单节点，多节点和各种附加组件靠 --nodes、minikube addons 打开，适合入门；k3d 跑的是 k3s，组件做过裁剪，启动快、占用小，但和上游 kubeadm 集群在细节上有差异。专栏要观察调度、节点维护、拓扑分布这类多节点行为，又希望组件尽量接近上游，所以选了 kind。多节点的 kubeadm 裸机安装见 kubeadm 安装部署。

下文的输出来自一台 Linux 主机（28 核、61 GiB 内存，Docker 29.9.0，Docker 使用 containerd 镜像存储），这次实验建的集群叫 notes-lab-env，用完即删。节点 IP 用 <node-ip> 一类占位符代替。本篇保留了完整的节点名 notes-lab-env-worker；其他笔记把节点名简写成 control-plane、worker、worker2，读者自己集群里的实际名字是 <集群名>-worker 这种形式。

前提

  • 需要一个容器运行时。本文用的是 Docker；kind 也能自动识别 podman 和 nerdctl，但它们默认以 rootless 模式运行，kind 文档说需要额外配置，这里没有试。
  • 资源：本文实测三节点集群跑起来后合计约 1.3 GiB 内存，kindest/node 镜像在本地占用约 1.5 GB 磁盘（数据见后文「集群占多少资源」）。
  • 只在 Linux 上验证过。Docker Desktop（macOS、Windows）没有验证，下文从宿主机直连节点 IP 的做法在那里大概率不通。

安装 kind 和 kubectl

下面的安装命令这次没有重新执行（本机已经装好），是按官方文档整理的，固定到本文用的版本。

kind v0.24.0（Linux x86_64）。二进制按 kind 快速入门 的地址下载；快速入门没有写校验步骤，GitHub release 页面为每个二进制附带了一个 .sha256sum 文件：

curl -Lo kind https://kind.sigs.k8s.io/dl/v0.24.0/kind-linux-amd64
curl -Lo kind.sha256sum https://github.com/kubernetes-sigs/kind/releases/download/v0.24.0/kind-linux-amd64.sha256sum
echo "$(cut -d' ' -f1 kind.sha256sum)  kind" | sha256sum --check
chmod +x kind && sudo mv kind /usr/local/bin/kind

装了 Go 的话，也可以用 go install sigs.k8s.io/kind@v0.24.0。本文用的二进制和 release 里的校验和一致：

$ cat kind-linux-amd64.sha256sum && sha256sum --check kind-linux-amd64.sha256sum
b89aada5a39d620da3fcd16435b7f28d858927dd53f92cbac77686b0588b600d  kind-linux-amd64
kind-linux-amd64: OK

kubectl 按 Install kubectl on Linux 安装，二进制和校验文件要下同一个版本：

curl -LO https://dl.k8s.io/release/v1.31.0/bin/linux/amd64/kubectl
curl -LO https://dl.k8s.io/release/v1.31.0/bin/linux/amd64/kubectl.sha256
echo "$(cat kubectl.sha256)  kubectl" | sha256sum --check
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl

kubectl 和集群的版本相差不能超过一个小版本。本机实际用的是 v1.30.0 的客户端，在这个范围内。确认 kind 版本：

$ kind --version
kind version 0.24.0

用配置文件建集群

命令行参数只能决定集群名和节点镜像，节点数量、端口映射都要写在配置文件里。保存为 kind-config.yaml：

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    image: kindest/node:v1.31.0
    extraPortMappings:
      - containerPort: 30080
        hostPort: 30080
        listenAddress: "127.0.0.1"
        protocol: TCP
  - role: worker
    image: kindest/node:v1.31.0
  - role: worker
    image: kindest/node:v1.31.0

extraPortMappings 的作用后面单独说。

为什么要固定节点镜像

不写 image 时，kind 用的是它自己这个版本内置的默认镜像；换一个 kind 版本，集群的 Kubernetes 版本就跟着变了。每个 kind 版本的 release notes 会列出为它构建的节点镜像，v0.24.0 列的是：

v1.31.0: kindest/node:v1.31.0@sha256:53df588e04085fd41ae12de0c3fe4c72f7013bba32a20e7325357a1ac94ba865

写上 kindest/node:v1.31.0，至少把 Kubernetes 版本钉住了。但只写标签还不够，本机这份镜像的摘要和上面那行对不上：

$ docker image inspect kindest/node:v1.31.0 --format '{{json .RepoDigests}}'
["kindest/node@sha256:25a3504b2b340954595fa7a6ed1575ef2edadf5abd83c0776a4308b64bf47c93"]

再直接查 Docker Hub，v1.31.0 这个标签现在指向的也是 25a3504b…，不是 release notes 里的 53df588e…。也就是说，同名标签在发布之后被重新推送过（是谁、因为什么推的，这次没有查到；一个旁证是这份镜像里的 kindnet 镜像标签是 v20241108，晚于 v0.24.0 的发布时间 2024 年 8 月）。release notes 里写得很明确：要保证用的是为这个 kind 版本构建的镜像，必须带 @sha256 摘要。想让别人逐字节复现，就把配置里的 image 写成上面那行带摘要的形式。这次实验和专栏的集群都只按标签固定，用的是本机已缓存的 25a3504b…。

创建，并留意机器负载

kind 默认把新集群的连接信息合并进 ~/.kube/config，并切换当前上下文。为了不碰日常用的 kubeconfig，这里用 --kubeconfig 写到单独的文件，后面的命令都通过 KUBECONFIG 环境变量指向它：

export KUBECONFIG=$PWD/kubeconfig
kind create cluster --name notes-lab-env --config kind-config.yaml --kubeconfig "$KUBECONFIG"

建集群时要同时启动三个节点容器、在里面跑 kubeadm，是一段磁盘 IO 密集的过程。这台机器磁盘偏慢，以前建集群时负载冲到过 100 以上，所以先看一眼 uptime，负载高就等它降下来再建。这次开始时负载不高：

命令返回了，节点还没 Ready

kind create cluster 返回之后立刻查节点：

$ kubectl get nodes -o wide
NAME                          STATUS     ROLES           AGE   VERSION   INTERNAL-IP   EXTERNAL-IP   OS-IMAGE                         KERNEL-VERSION     CONTAINER-RUNTIME
notes-lab-env-control-plane   NotReady   control-plane   44s   v1.31.0   <cp-ip>       <none>        Debian GNU/Linux 12 (bookworm)   7.0.0-38-generic   containerd://1.7.18
notes-lab-env-worker          NotReady   <none>          8s    v1.31.0   <worker-ip>   <none>        Debian GNU/Linux 12 (bookworm)   7.0.0-38-generic   containerd://1.7.18
notes-lab-env-worker2         NotReady   <none>          7s    v1.31.0   <worker2-ip>  <none>        Debian GNU/Linux 12 (bookworm)   7.0.0-38-generic   containerd://1.7.18

三个节点都是 NotReady，CoreDNS 还在 Pending，两个 worker 上的 kindnet 和 kube-proxy 在 ContainerCreating。kind 默认不等节点就绪（--wait 参数也只等控制平面节点，不管 worker），节点名的规则是 <集群名>-control-plane、<集群名>-worker、<集群名>-worker2，同时也是 Docker 容器名。脚本里接着建资源之前，自己等一下：

$ kubectl wait --for=condition=Ready node --all --timeout=300s
node/notes-lab-env-control-plane condition met
node/notes-lab-env-worker condition met
node/notes-lab-env-worker2 condition met

real	0m14.726s

污点的变化也值得看一眼。17:54:32 查的时候，三个节点上都挂着 node.kubernetes.io/not-ready 的 NoSchedule 污点；等待期间 worker2 上反而新加了一个 NoExecute 的同名污点（timeAdded 是 09:54:50Z，UTC），节点全部 Ready 之后再查时还在，几秒后再查才消失。推测是节点生命周期控制器在 worker2 短暂未就绪时补打的 NoExecute，状态同步有延迟，这次没有从控制器日志上核实。此时 CoreDNS 和 local-path-provisioner 仍在 ContainerCreating。脚本里马上要调度 Pod 的话，把 kubectl -n kube-system rollout status deploy/coredns 也加上更稳。

$ kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
NAME                          TAINTS
notes-lab-env-control-plane   [map[effect:NoSchedule key:node-role.kubernetes.io/control-plane]]
notes-lab-env-worker          <none>
notes-lab-env-worker2         [map[effect:NoExecute key:node.kubernetes.io/not-ready timeAdded:2026-10-13T09:54:50Z]]

控制平面上的 NoSchedule 污点是永久的，普通 Pod 只会落到两个 worker 上。

cluster-info 和上下文

$ kubectl cluster-info
Kubernetes control plane is running at https://127.0.0.1:39291
CoreDNS is running at https://127.0.0.1:39291/api/v1/namespaces/kube-system/services/kube-dns:dns/proxy

API Server 被映射到宿主机 127.0.0.1 的一个随机端口，只有本机能访问。kind 生成的上下文名固定是 kind-<集群名>：

$ kubectl config get-contexts; kubectl config current-context
CURRENT   NAME                 CLUSTER              AUTHINFO             NAMESPACE
*         kind-notes-lab-env   kind-notes-lab-env   kind-notes-lab-env   
kind-notes-lab-env

实验 namespace

kubectl create namespace notes-lab
until kubectl -n notes-lab get sa default >/dev/null 2>&1; do sleep 1; done
kubectl config set-context --current --namespace=notes-lab

中间那行是在等 namespace 的 default ServiceAccount，它由控制器异步创建，刚建好 namespace 就立刻创建 Pod 会被拒绝，见 Pod 与容器。设置之后，namespace 是记在上下文上的：

CURRENT   NAME                 CLUSTER              AUTHINFO             NAMESPACE
*         kind-notes-lab-env   kind-notes-lab-env   kind-notes-lab-env   notes-lab
$ kubectl config view --minify -o jsonpath='{..namespace}'
notes-lab

其他笔记的命令都显式写了 -n notes-lab，即使上下文没设 namespace 也不会写到 default 里去。

上下文指错了会怎样

本机往往不止一个集群，最怕的是以为在实验集群，实际在别的集群上执行了写入。为了不碰真实集群，下面在实验用的 kubeconfig 里加了几个假的上下文来演示。

连不上：报错，但可能要等很久

先加一个指向不可达地址的上下文（192.0.2.10 属于文档专用地址段，不会有主机应答），模拟一个 VPN 没连上的远端集群：

kubectl config set-cluster fake-prod --server=https://192.0.2.10:6443 --insecure-skip-tls-verify=true
kubectl config set-credentials fake-admin --token=placeholder
kubectl config set-context fake-prod --cluster=fake-prod --user=fake-admin --namespace=default
kubectl config use-context fake-prod

地址可达、只是端口上没有服务时（比如本机的 kind 集群容器已经停了，127.0.0.1 上那个端口没人监听），报错是瞬间的。再加一个指向本机空闲端口的上下文：

kubectl config set-cluster fake-stopped --server=https://127.0.0.1:39999 --insecure-skip-tls-verify=true
kubectl config set-context fake-stopped --cluster=fake-stopped --user=fake-admin
kubectl --context fake-stopped get nodes

所以 i/o timeout 多半指向网络或地址本身（VPN、防火墙、IP 写错），connection refused 指向「地址对、服务不在」，在 kind 上通常是节点容器停了，docker ps -a 就能看到。

连得上：成功执行，只是写到了别处

真正危险的是第二种：上下文能连上，命令也成功了，只是目标不对。先切回实验集群的上下文（前面一直停在 fake-prod 上），再用同一个 kind 集群建一个不带 namespace 的上下文，模拟「切到了另一个上下文却没注意」：

kubectl config use-context kind-notes-lab-env
kubectl config set-context lab-default-ns --cluster=kind-notes-lab-env --user=kind-notes-lab-env
$ kubectl --context lab-default-ns create configmap where-am-i --from-literal=k=v
configmap/where-am-i created
$ kubectl get configmap where-am-i
Error from server (NotFound): configmaps "where-am-i" not found
$ kubectl get configmap where-am-i -n default
NAME         DATA   AGE
where-am-i   1      4s

创建成功，没有任何提示，对象落进了 default。演示完记得删掉它，以及这个临时上下文和前面的 fake-stopped：

kubectl -n default delete configmap where-am-i
kubectl config delete-context lab-default-ns
kubectl config delete-context fake-stopped
kubectl config delete-cluster fake-stopped

换成另一个集群也是同样的效果：kubectl 只认当前上下文，不知道你心里想的是哪个集群。

写入前的检查

最直接的办法是每条写入命令都显式带 --context kind-<集群名> 和 -n notes-lab。跑脚本前，也可以先过一道检查：

lab_guard() {
  local ctx ns
  ctx=$(kubectl config current-context) || return 1
  ns=$(kubectl config view --minify -o jsonpath='{..namespace}')
  case "$ctx" in
    kind-*) ;;
    *) echo "拒绝：当前上下文是 $ctx，不是 kind 集群" >&2; return 1 ;;
  esac
  [ "$ns" = notes-lab ] || { echo "拒绝：当前 namespace 是 '${ns:-default}'" >&2; return 1; }
  echo "ok: $ctx / $ns"
}

把它存成 guard.sh，在几个上下文之间来回切换验证：

source guard.sh
lab_guard
kubectl config use-context fake-prod >/dev/null; lab_guard; echo exit=$?
kubectl config use-context lab-default-ns >/dev/null; lab_guard; echo exit=$?
kubectl config use-context kind-notes-lab-env >/dev/null; lab_guard
ok: kind-notes-lab-env / notes-lab
拒绝：当前上下文是 fake-prod，不是 kind 集群
exit=1
拒绝：当前上下文是 lab-default-ns，不是 kind 集群
exit=1
ok: kind-notes-lab-env / notes-lab

lab-default-ns 是因为上下文名不以 kind- 开头被拦下的，namespace 那条分支这次没有被触发。显式带 --context 的命令不读当前上下文，也就不经过这道检查。它只看上下文名字，挡得住误切到远端集群，挡不住一个恰好叫 kind-xxx 的别的 kind 集群；本机有多个 kind 集群时，把 kind-* 换成精确的上下文名。另外，像本文这样给实验集群单独一个 kubeconfig 文件，日常的 ~/.kube/config 里根本没有它，两边不会互相串。

kind 默认带了什么

CNI：kindnet

$ kubectl get ds -n kube-system
NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR            AGE
kindnet      3         3         1       3            1           kubernetes.io/os=linux   19s
kube-proxy   3         3         1       3            1           kubernetes.io/os=linux   23s

kind 自带的 CNI 是 kindnet（镜像 kindest/kindnetd:v20241108-5c6d2daf），每个节点分一个 /24（控制平面 10.244.0.0/24，两个 worker 是 10.244.1.0/24、10.244.2.0/24），节点上的 CNI 配置是 ptp 加 host-local 地址分配。容易记错的一点：老版本的 kind 不执行 NetworkPolicy，而 v0.24.0 的 release notes 写明从这个版本起通过 kube-network-policies 开箱支持 NetworkPolicy，这次没有在默认 CNI 上测试策略效果。专栏的集群换成了 Calico，NetworkPolicy 那几篇的输出是 Calico 下的；在 kindnet 上照做，策略是否生效、被拦时是超时还是拒绝，都可能和文中不一样。换 CNI 的做法是在配置里加 networking.disableDefaultCNI: true 再自己装，kind 文档称之为「power user feature with limited support」，即支持有限的高级用法，同时说明 Calico 等常见 CNI 的 manifest 已知可用；这次没有演示。数据包怎么走见 CNI 网络路径排查。

默认 StorageClass：standard（local-path）

$ kubectl get storageclass
NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
standard (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  17s

WaitForFirstConsumer 意味着只建 PVC 不会马上出卷。先只提交一个 100Mi 的 PVC，保存为 pvc-only.yaml：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 100Mi
kubectl -n notes-lab apply -f pvc-only.yaml
sleep 20
kubectl -n notes-lab get pvc data
kubectl -n notes-lab get events --field-selector involvedObject.name=data \
  -o custom-columns=REASON:.reason,COUNT:.count,MSG:.message

20 秒后它仍然是 Pending：

NAME   STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
data   Pending                                      standard       <unset>                 20s
REASON                  COUNT   MSG
WaitForFirstConsumer    4       waiting for first consumer to be created before binding

（事件按名字筛选，COUNT 里混进了之前一个同名 PVC 的事件，只看 REASON 即可。）这不是故障。再创建一个挂载它的 Pod writer（pvc.yaml 是上面的 PVC 加下面这个 Pod，用 --- 隔开）：

apiVersion: v1
kind: Pod
metadata:
  name: writer
spec:
  containers:
    - name: w
      image: busybox:1.36
      command: ["sh", "-c", "echo saved > /data/f && sleep 3600"]
      volumeMounts:
        - {name: d, mountPath: /data}
  volumes:
    - name: d
      persistentVolumeClaim: {claimName: data}
kubectl -n notes-lab apply -f pvc.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/writer --timeout=120s
kubectl -n notes-lab get pvc data
persistentvolumeclaim/data unchanged
pod/writer created
pod/writer condition met
NAME   STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
data   Bound    pvc-908c63fc-d6cd-4987-9ce2-493e418e60cd   100Mi      RWO            standard       <unset>                 36s

Pod 调度到哪个节点，卷就建在哪个节点的 /var/local-path-provisioner/ 下，PVC 随即 Bound。卷数据存在节点容器里，删集群就没了。细节见 PV、PVC 与 StorageClass。

没有 metrics-server

$ kubectl top nodes
error: Metrics API not available

kind 不带 metrics-server，kubectl top 和 HPA 都用不了。专栏的集群是预先装好的。自己装的话用官方 manifest：

kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.7.2/components.yaml

在 kind 上直接这么装，Pod 一直 Running 但 0/1，就绪探针返回 500，日志里是证书校验失败：

E1013 10:04:03.563959       1 scraper.go:149] "Failed to scrape node" err="Get \"https://<worker2-ip>:10250/metrics/resource\": tls: failed to verify certificate: x509: cannot validate certificate for <worker2-ip> because it doesn't contain any IP SANs" node="notes-lab-env-worker2"
I1013 10:04:04.250789       1 server.go:191] "Failed probe" probe="metric-storage-ready" err="no metrics to serve"

原因在 kubelet 的服务证书。看一个节点上的证书：

$ docker exec notes-lab-env-worker openssl x509 -in /var/lib/kubelet/pki/kubelet.crt -noout -subject -issuer -ext subjectAltName
subject=CN = notes-lab-env-worker@1791885260
issuer=CN = notes-lab-env-worker-ca@1791885260
X509v3 Subject Alternative Name: 
    DNS:notes-lab-env-worker

这是 kubelet 启动时自签的证书，签发者是它自己的 CA 而不是集群 CA，SAN 里也只有主机名、没有 IP；而 metrics-server 按 InternalIP 去连 kubelet。metrics-server 的 README 要求 kubelet 证书由集群 CA 签发，否则就加 --kubelet-insecure-tls 跳过校验，并注明这个参数仅用于测试。本地实验集群里加上它：

kubectl -n kube-system patch deployment metrics-server --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

滚动更新完成后 20 秒，top 就有数据了：

NAME                          CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%   
notes-lab-env-control-plane   49m          0%     839Mi           1%        
notes-lab-env-worker          19m          0%     182Mi           0%        
notes-lab-env-worker2         16m          0%     293Mi           0%

百分比几乎都是 0，因为每个节点报告的容量是整台宿主机：

NAME                          CPU   MEM
notes-lab-env-control-plane   28    64329524Ki
notes-lab-env-worker          28    64329524Ki
notes-lab-env-worker2         28    64329524Ki

三个节点共享同一台机器的 CPU 和内存，各自都声称拥有全部。所以在 kind 上做调度、驱逐相关的实验时，「节点资源不足」很难自然出现，需要靠 Pod 的 requests 或 kubelet 参数人为制造；专栏里 QoS、探针与资源管理 的实验都是在 Pod 级 limit 上做的。

从宿主机访问 NodePort：extraPortMappings

kind 节点是容器，NodePort 开在容器里，宿主机默认够不到 localhost:<nodePort>。配置里那段 extraPortMappings 就是让 Docker 把宿主机的 127.0.0.1:30080 转发到控制平面容器的 30080：

$ docker port notes-lab-env-control-plane
6443/tcp -> 127.0.0.1:39291
30080/tcp -> 127.0.0.1:30080

用两个 busybox httpd 副本加一个固定 nodePort: 30080 的 Service 测试，每个副本返回自己的 Pod 名：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
        - name: httpd
          image: busybox:1.36
          command: ["sh", "-c", "mkdir -p /www && echo \"hello from $(hostname)\" > /www/index.html && exec httpd -f -p 8080 -h /www"]
          ports:
            - containerPort: 8080
          resources:
            requests: {cpu: 10m, memory: 16Mi}
            limits: {memory: 32Mi}
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: NodePort
  selector: {app: web}
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080
$ for i in 1 2 3 4; do curl -s --max-time 3 http://127.0.0.1:30080/; done
hello from web-547ddf4469-mhrm7
hello from web-547ddf4469-2bsp2
hello from web-547ddf4469-mhrm7
hello from web-547ddf4469-mhrm7

两个 Pod 都在 worker 上，请求先进控制平面容器，再由 kube-proxy 转给任意一个副本，所以映射只要开在一个节点上就够了。

映射是建集群时写进 Docker 容器的，之后改不了。把 Service 的 nodePort 改成 30081：

$ curl -sS --max-time 3 http://127.0.0.1:30081/
curl: (7) Failed to connect to 127.0.0.1 port 30081 after 0 ms: Could not connect to server
$ curl -sS --max-time 3 http://127.0.0.1:30080/
curl: (56) Recv failure: 连接被对方重置

两种失败不一样：30081 在宿主机上根本没人监听，立即拒绝；30080 的 Docker 端口转发还在，连接建立了，但容器里已经没有 30080 的 NodePort，连接被重置。所以要预先想好哪些端口需要从宿主机访问，Service 里用固定的 nodePort 对上。

在 Linux 上还有一条路：节点容器的 IP 在 Docker 网桥上，宿主机能直接访问，curl http://<worker-ip>:30081/ 是通的。Docker Desktop（macOS、Windows）的容器跑在虚拟机里，这条路一般走不通，这次没有在那两个平台上验证。Service 的几种类型见 Service 类型。

端口被占用：集群直接建不起来

hostPort 选了一个被占用的端口时，整个 kind create cluster 会失败。本机 80 端口已经被另一个容器占着，把配置改成 hostPort: 80、listenAddress: "0.0.0.0" 再建：

 ✗ Preparing nodes 📦 📦 📦 
Deleted nodes: ["notes-lab-env-control-plane" "notes-lab-env-worker2" "notes-lab-env-worker"]
ERROR: failed to create cluster: command "docker run --name notes-lab-env-control-plane ... --publish=0.0.0.0:80:30080/TCP --publish=127.0.0.1:39783:6443/TCP -e KUBECONFIG=/etc/kubernetes/admin.conf kindest/node:v1.31.0" failed with error: exit status 125

docker: Error response from daemon: failed to set up container networking: driver failed programming external connectivity on endpoint notes-lab-env-control-plane (74f0b3cf...): Bind for 0.0.0.0:80 failed: port is already allocated

real	0m49.735s

kind 会自动删掉已经建出来的节点容器，也不会写 kubeconfig，失败之后可以直接改配置重来。建之前用 ss -ltn 或 docker ps --format '{{.Names}} {{.Ports}}' 查一下端口。

把本地镜像放进节点：kind load

节点里的 containerd 和宿主机的 Docker 是两套镜像存储，宿主机上 docker build 出来的镜像，节点看不到。先在宿主机上构建一个演示镜像，build/Dockerfile 只有两行：

FROM busybox:1.36
RUN echo lab-demo > /hello.txt
docker build -t notes-lab/lab-demo:v1 build/

kind load docker-image 把它导入每个节点：

$ time kind load docker-image notes-lab/lab-demo:v1 --name notes-lab-env
Image: "notes-lab/lab-demo:v1" with ID "sha256:9a5dd46d2004d359d1e9220182c8e515c193a3df86205d1406e65572838f11bc" not yet present on node "notes-lab-env-worker2", loading...
Image: "notes-lab/lab-demo:v1" with ID "sha256:9a5dd46d2004d359d1e9220182c8e515c193a3df86205d1406e65572838f11bc" not yet present on node "notes-lab-env-control-plane", loading...
Image: "notes-lab/lab-demo:v1" with ID "sha256:9a5dd46d2004d359d1e9220182c8e515c193a3df86205d1406e65572838f11bc" not yet present on node "notes-lab-env-worker", loading...

real	0m9.794s

本地构建的镜像没问题。但想把宿主机上从 Docker Hub 拉来的 busybox:1.36 也导进去、省掉节点上的下载时，失败了：

$ time kind load docker-image busybox:1.36 --name notes-lab-env
ERROR: failed to load image: command "docker exec --privileged -i notes-lab-env-control-plane ctr --namespace=k8s.io images import --all-platforms --digests --snapshotter=overlayfs -" failed with error: exit status 1

Command Output: ctr: content digest sha256:71b0cbca78cef3413c843ed16136b822b6deefc6dea540f0f77b0e39eb991dc5: not found

real	1m8.077s

busybox:1.36 在宿主机上是一个多平台镜像索引，而 kind 导入时带了 --all-platforms。推测是宿主机 Docker（用的 containerd 镜像存储）只下载了 amd64 那一份的内容，导出的包里缺了其他平台引用的内容，导入时就找不到；这次没有逐层核实。改用 docker save --platform linux/amd64 加 kind load image-archive 也没完全成功，worker 上报 mismatched image rootfs and manifest layers。对这类公共小镜像，最省事的是让节点自己拉：两个副本拉 busybox 各用了 11 到 12 秒。kind load 的完整实验（镜像拉取策略、同标签改内容）见镜像与拉取策略。

集群占多少资源

装好 metrics-server、跑着三个小 Pod 时：

$ docker stats --no-stream --format 'table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}\t{{.PIDs}}' notes-lab-env-control-plane notes-lab-env-worker notes-lab-env-worker2
NAME                          CPU %     MEM USAGE / LIMIT     PIDS
notes-lab-env-control-plane   3.65%     864.9MiB / 61.35GiB   440
notes-lab-env-worker          1.20%     190.3MiB / 61.35GiB   157
notes-lab-env-worker2         2.19%     313.5MiB / 61.35GiB   222

三个节点合计约 1.3 GiB 内存，大头是控制平面（etcd、API Server、控制器）。磁盘方面，三个节点共用一份 1.49 GB 的 kindest/node 镜像，每个容器自己的可写层这时只有几百 KB 到几 MB；节点里拉的镜像和 local-path 卷放在容器的匿名卷里，会随实验累积。

这次没有碰到 inotify 上限导致的 too many open files。本机的这两个值：

$ sysctl fs.inotify.max_user_instances fs.inotify.max_user_watches
fs.inotify.max_user_instances = 1024
fs.inotify.max_user_watches = 524288

kind 的已知问题文档里提到，Ubuntu 的默认值是 max_user_watches=8192、max_user_instances=128，不够建多节点的集群，建议调到 max_user_watches=524288、max_user_instances=512。

删除集群

$ kind get clusters
notes-lab-env
$ time kind delete cluster --name notes-lab-env --kubeconfig kubeconfig
Deleting cluster "notes-lab-env" ...
Deleted nodes: ["notes-lab-env-worker2" "notes-lab-env-control-plane" "notes-lab-env-worker"]

real	0m6.577s

（kind get clusters 的输出里还有本机另一个集群，这里略去。）删除只用了 6.6 秒，同时会把 kind-notes-lab-env 上下文从 kubeconfig 里删掉；手工加的 fake-prod 留着，要自己清：

$ kubectl config delete-context fake-prod; kubectl config delete-cluster fake-prod; kubectl config delete-user fake-admin; kubectl config get-contexts
deleted context fake-prod from <scratch>/kubeconfig
deleted cluster fake-prod from <scratch>/kubeconfig
deleted user fake-admin from <scratch>/kubeconfig
CURRENT   NAME   CLUSTER   AUTHINFO   NAMESPACE

确认节点容器没有残留：

$ docker ps -a | grep notes-lab-env; echo grep-exit=$?
grep-exit=1

只想清掉某一篇的实验资源、保留集群时，删 namespace 就够了：kubectl delete namespace notes-lab --wait。本机内存紧张时，可以 docker stop 掉三个节点容器，用的时候再 docker start，这次没有测重启后的恢复时间。Pod 与容器里那次 84 秒的沙箱创建发生在专栏集群重启两分钟后，推测和控制平面还在恢复有关。
