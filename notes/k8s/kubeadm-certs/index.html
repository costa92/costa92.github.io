第 62 / 66 节 · 集群搭建

先盘点，再安排更新

kubeadm 升级检查清单管的是版本，证书到期是另一条时间线：kubeadm 签发的组件证书默认一年有效，集群如果一年没升级、也没人手动续期，到期那天控制平面组件之间就会互相拒绝连接。本篇只讨论 kubeadm 管理的自建控制平面；托管 Kubernetes 服务、外部 CA 或自行替换 PKI 的集群，按实际提供方的流程处理。

续期会改动控制平面证书，下面的实验没有在任何正在使用的集群上做，而是专门建了一个用完即删的 kind 集群（kind 底层就是 kubeadm，节点里能直接执行 kubeadm 命令）：Kubernetes v1.31.0，一个控制平面节点加一个 worker，containerd 1.7.18。文中节点名简化成 control-plane、worker，两台节点的 IP 分别用 <control-plane-ip>、<worker-ip> 代替。命令按真实节点的写法给出，需要在控制平面节点上以 root 执行。

check-expiration：看什么，不看什么

sudo kubeadm certs check-expiration

集群刚创建一分钟时的输出：

CERTIFICATE                EXPIRES                  RESIDUAL TIME   CERTIFICATE AUTHORITY   EXTERNALLY MANAGED
admin.conf                 Oct 13, 2027 08:00 UTC   364d            ca                      no      
apiserver                  Oct 13, 2027 08:00 UTC   364d            ca                      no      
apiserver-etcd-client      Oct 13, 2027 08:00 UTC   364d            etcd-ca                 no      
apiserver-kubelet-client   Oct 13, 2027 08:00 UTC   364d            ca                      no      
controller-manager.conf    Oct 13, 2027 08:00 UTC   364d            ca                      no      
etcd-healthcheck-client    Oct 13, 2027 08:00 UTC   364d            etcd-ca                 no

front-proxy-client         Oct 13, 2027 08:00 UTC   364d            front-proxy-ca          no

CERTIFICATE AUTHORITY   EXPIRES                  RESIDUAL TIME   EXTERNALLY MANAGED
ca                      Oct 10, 2036 08:00 UTC   9y              no      
etcd-ca                 Oct 10, 2036 08:00 UTC   9y              no      
front-proxy-ca          Oct 10, 2036 08:00 UTC   9y              no

几列的含义：

  • CERTIFICATE：/etc/kubernetes/pki 下的证书，加上 admin.conf、super-admin.conf、controller-manager.conf、scheduler.conf 这几个 kubeconfig 里内嵌的客户端证书。
  • EXPIRES / RESIDUAL TIME：到期时间和剩余时间。组件证书一年，三个 CA 十年。kubeadm certs renew 只续组件证书，不续 CA；CA 到期是另一个问题，kubeadm 不提供开箱即用的 CA 轮换。
  • CERTIFICATE AUTHORITY：由哪个 CA 签发。三套 CA 互相独立，etcd 相关的四张证书挂在 etcd-ca 下。
  • EXTERNALLY MANAGED：yes 表示 kubeadm 认为这张证书不归它管，后面单独复现。

表里没有 kubelet.conf，这是有意的，后面一节专门讲。

check-expiration 读的是磁盘上的文件。想看证书的完整信息，直接用 openssl：

sudo openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout \
  -subject -issuer -serial -startdate -enddate -ext subjectAltName,extendedKeyUsage
subject=CN = kube-apiserver
issuer=CN = kubernetes
serial=42DCF5DB7C991540
notBefore=Oct 13 07:55:50 2026 GMT
notAfter=Oct 13 08:00:50 2027 GMT
X509v3 Extended Key Usage: 
    TLS Web Server Authentication
X509v3 Subject Alternative Name: 
    DNS:kubernetes, DNS:kubernetes.default, DNS:kubernetes.default.svc, DNS:kubernetes.default.svc.cluster.local, DNS:localhost, DNS:control-plane, IP Address:<service-ip>, IP Address:<control-plane-ip>, IP Address:127.0.0.1

两个细节：

  • notBefore 比集群创建时间（08:00:50）早了整整 5 分钟，notAfter 则是创建时间加一年。后面看到 controller-manager 给 kubelet 签的证书也一样往前推了 5 分钟。推测是为了容忍节点间的时钟偏差：新加入的节点时钟稍慢，也不会因为证书「尚未生效」而连不上。
  • SAN 列表决定客户端能用哪些地址访问 API Server。通过负载均衡器的域名或新 IP 访问时报 x509: certificate is valid for ..., not ...，就是这里缺了条目。kubeadm certs renew 的输出里有一行 Reading configuration from the cluster，但官方文档说明，续期时 CN、O 和 SAN 这些属性以现有证书为准，不参考 kubeadm-config ConfigMap 里的值，所以靠 renew 补不了 SAN；文档同时建议让 ConfigMap 和实际证书保持一致，免得日后混淆。

高可用集群要逐台控制平面节点检查，每台节点的证书是各自签发的，只看一台说明不了其他节点。不要把输出里的证书内容或私钥复制到工单与文章中。

看懂检查结果

发现下一步
某证书剩余时间短查它属于哪个组件，备份 /etc/kubernetes 和 etcd 后安排续期
EXTERNALLY MANAGED=yes走外部 CA 的签发流程；kubeadm 在这种情况下不会替你续
CA 剩余时间短renew 解决不了，需要按官方的 CA 手动轮换流程处理
想找的证书不在表里先确认它是否归 kubeadm 管（kubelet、Ingress、业务证书都不归），不要据此认定永不过期

不在清单里的：kubelet 证书

每个节点的 kubelet 有两张证书：访问 API Server 用的客户端证书，以及 API Server 调 kubelet（kubectl logs、exec）时 kubelet 出示的服务端证书。它们都在 /var/lib/kubelet/pki：

sudo ls -l /var/lib/kubelet/pki
sudo grep -nE 'client-certificate|client-key' /etc/kubernetes/kubelet.conf
sudo grep -n rotate /var/lib/kubelet/config.yaml

worker 上的目录：

-rw------- 1 root root 1131 Oct 13 08:01 kubelet-client-2026-10-13-08-01-36.pem
lrwxrwxrwx 1 root root   59 Oct 13 08:01 kubelet-client-current.pem -> /var/lib/kubelet/pki/kubelet-client-2026-10-13-08-01-36.pem
-rw-r--r-- 1 root root 2363 Oct 13 08:01 kubelet.crt
-rw------- 1 root root 1679 Oct 13 08:01 kubelet.key

control-plane 上的目录长得一样，但客户端证书的来历不同：

-rw------- 1 root root 2855 Oct 13 08:00 kubelet-client-2026-10-13-08-00-52.pem
lrwxrwxrwx 1 root root   59 Oct 13 08:00 kubelet-client-current.pem -> /var/lib/kubelet/pki/kubelet-client-2026-10-13-08-00-52.pem
-rw-r--r-- 1 root root 2417 Oct 13 08:00 kubelet.crt
-rw------- 1 root root 1679 Oct 13 08:00 kubelet.key

这张证书的 notBefore 是 07:55:50，和 apiserver.crt 完全相同，下面的 CSR 列表里也没有来自 control-plane 的请求：它是 kubeadm init 用本地 CA 直接签好写进去的，没有走 CSR。worker 的那张才是 TLS bootstrap 申请来的。

下面两段 grep 输出来自 control-plane（worker 上的 kubelet.conf 同样指向这个软链接）：

18:    client-certificate: /var/lib/kubelet/pki/kubelet-client-current.pem
19:    client-key: /var/lib/kubelet/pki/kubelet-client-current.pem
47:rotateCertificates: true

kubelet.conf 不内嵌证书，而是指向 kubelet-client-current.pem 这个软链接；kubeadm 打开了 rotateCertificates，kubelet 自己负责续期。这就是 check-expiration 不列它的原因。worker 加入集群时，kubelet 先用 bootstrap token 提交 CSR，由 controller-manager 自动批准：

NAME        AGE   SIGNERNAME                                    REQUESTOR                 REQUESTEDDURATION   CONDITION
csr-rgqb7   48s   kubernetes.io/kube-apiserver-client-kubelet   system:bootstrap:<token-id>   <none>              Approved,Issued
csr-x6pq7   50s   kubernetes.io/kube-apiserver-client-kubelet   system:bootstrap:<token-id>   <none>              Approved,Issued

两条 CSR 解开来，subject 都是 O=system:nodes, CN=system:node:worker，相隔 2 秒；落盘的只有后一张（文件名里的 08-01-36）。为什么提交了两次这次没有深究。

亲眼看一次客户端证书轮换

一年才轮换一次，没法等。办法是用集群 CA 给 worker 签一张只有 6 分钟有效期、身份相同的客户端证书，把软链接指过去再重启 kubelet。

仅限一次性实验集群
这个实验要把控制平面的 ca.key 拷到别处签证书，等于把整个集群的信任根带离了控制平面。生产集群不要这样做。

# 在拿到 ca.crt / ca.key 副本的机器上签发
openssl req -new -newkey rsa:2048 -nodes -keyout kc.key \
  -subj '/O=system:nodes/CN=system:node:worker' -out kc.csr
printf 'extendedKeyUsage=clientAuth\n' > kc.ext
openssl x509 -req -in kc.csr -CA ca.crt -CAkey ca.key -extfile kc.ext \
  -not_before $(date -u -d '-1 min' +%Y%m%d%H%M%SZ) \
  -not_after  $(date -u -d '+5 min' +%Y%m%d%H%M%SZ) -out kc.crt
cat kc.crt kc.key > kubelet-client-short.pem
# 拷到 worker 的 /var/lib/kubelet/pki/ 后（拷贝方式示意，未逐字记录）：
cd /var/lib/kubelet/pki
chmod 600 kubelet-client-short.pem
ln -sfn /var/lib/kubelet/pki/kubelet-client-short.pem kubelet-client-current.pem
systemctl restart kubelet

如果轮换没有按预期发生，恢复办法是把软链接指回原来的 pem，再重启 kubelet（示意，本次轮换成功，没有执行）：

ln -sfn /var/lib/kubelet/pki/kubelet-client-2026-10-13-08-01-36.pem /var/lib/kubelet/pki/kubelet-client-current.pem
systemctl restart kubelet

签出来的短证书：

subject=O=system:nodes, CN=system:node:worker
notBefore=Oct 13 08:12:46 2026 GMT
notAfter=Oct 13 08:18:46 2026 GMT

08:13:46 重启 kubelet，之后不做任何操作。kubelet 日志：

Oct 13 08:13:46 worker kubelet[952]: I1013 08:13:46.401049     952 server.go:929] "Client rotation is on, will bootstrap in background"
Oct 13 08:13:46 worker kubelet[952]: I1013 08:13:46.401845     952 certificate_store.go:130] Loading cert/key pair from "/var/lib/kubelet/pki/kubelet-client-current.pem".
Oct 13 08:18:06 worker kubelet[952]: I1013 08:18:06.417183     952 transport.go:147] "Certificate rotation detected, shutting down client connections to start using new credentials"
-rw------- 1 root root 1131 Oct 13 08:01 kubelet-client-2026-10-13-08-01-36.pem
-rw------- 1 root root 1131 Oct 13 08:18 kubelet-client-2026-10-13-08-18-05.pem
lrwxrwxrwx 1 root root   59 Oct 13 08:18 kubelet-client-current.pem -> /var/lib/kubelet/pki/kubelet-client-2026-10-13-08-18-05.pem
-rw------- 1 1000 1000 2884 Oct 13 08:13 kubelet-client-short.pem
csr-66b6s   26s     kubernetes.io/kube-apiserver-client-kubelet   system:node:worker   <none>              Approved,Issued

新证书 08:18:05 落盘，这时旧证书 360 秒的寿命还剩 41 秒，约 11%。官方文档说轮换发生在剩余寿命 30% 到 10% 之间的某个时刻，实测落在区间内。注意几点：

  • 这次提交 CSR 的是 system:node:worker，用的是当前证书的身份，不再需要 bootstrap token；同样被自动批准。
  • 轮换只是换文件、改软链接，然后断开旧连接重新建立，kubelet 不需要重启。
  • 新证书有效期一年（notAfter=Oct 13 08:13:05 2027 GMT），旧文件留在目录里不会删除。
  • 前提是旧证书还没过期。如果节点关机超过一年，或者轮换一直失败，证书过期后 kubelet 就无法再用它申请新证书，要按官方排障文档「Kubelet client certificate rotation fails」手工修复。

服务端证书：Ready 不等于 kubectl logs 能用

默认情况下 kubelet.crt 是 kubelet 启动时自己生成的自签名证书：

subject=CN = worker@1791878494
issuer=CN = worker-ca@1791878494
notBefore=Oct 13 07:01:34 2026 GMT
notAfter=Oct 13 07:01:34 2027 GMT

kubeadm 的默认配置没有让 API Server 校验 kubelet 的服务端证书，所以平时没人在意。想让它由集群 CA 签发，官方给的流程分两处改：

  1. kubectl -n kube-system edit configmap kubelet-config，在其中的 KubeletConfiguration 里加 serverTLSBootstrap: true。新加入的节点和以后的 kubeadm upgrade 都从这里取 kubelet 配置。
  2. 每个已有节点在 /var/lib/kubelet/config.yaml 里加同一行，然后 systemctl restart kubelet。官方的「Reconfiguring a kubeadm cluster」页面给的另一种做法是不手改文件，在节点上执行 kubeadm upgrade node phase kubelet-config，把 ConfigMap 的最新内容下载到本地 config.yaml，再重启 kubelet；一次处理一个节点。

只改本地文件也能立刻生效，这次实验就是这么做的（只改了 worker 的 config.yaml，没动 ConfigMap）。但只改本地是留不住的，reconfigure 文档的原文是：

During kubeadm upgrade, kubeadm downloads the KubeletConfiguration from the kubelet-config ConfigMap and overwrite the contents of /var/lib/kubelet/config.yaml.

也就是说，下次 kubeadm upgrade 后这一行就没了。本次没有实测升级。

在 worker 上改完重启 kubelet，立刻出现一条待批准的 CSR：

NAME        AGE   SIGNERNAME                                    REQUESTOR            REQUESTEDDURATION   CONDITION
csr-cbdcj   7s    kubernetes.io/kubelet-serving                 system:node:worker   <none>              Pending

controller-manager 内置的批准器不会自动批准 kubernetes.io/kubelet-serving 这类 CSR（kubelet 可以在 SAN 里填任意地址，自动批准不安全）。CSR 一直 Pending 的这段时间，节点状态完全正常，但凡是要连 kubelet 10250 端口的操作都失败了：

NAME                            STATUS   ROLES           AGE   VERSION
control-plane                   Ready    control-plane   12m   v1.31.0
worker                          Ready    <none>          11m   v1.31.0
$ kubectl -n kube-system logs kube-proxy-7rnk2 --tail=1
Error from server: Get "https://<worker-ip>:10250/containerLogs/kube-system/kube-proxy-7rnk2/kube-proxy?tailLines=1": remote error: tls: internal error

客户端只看到一个含糊的 tls: internal error，原因要去 worker 的 kubelet 日志里找：

Oct 13 08:13:22 worker kubelet[858]: I1013 08:13:22.251181     858 ???:1] "http: TLS handshake error from <control-plane-ip>:39008: no serving certificate available for the kubelet"

kubelet 一旦打开 serverTLSBootstrap，就不再用原来的自签名证书，在拿到签好的证书之前，它没有任何证书可以出示。批准前先核对 CSR 里申请的身份和 SAN 是不是这台节点自己的：

kubectl get csr csr-cbdcj -o jsonpath='{.spec.request}' | base64 -d | openssl req -noout -text | grep -A1 -E 'Subject:|Alternative'
kubectl certificate approve csr-cbdcj
        Subject: O=system:nodes, CN=system:node:worker
--
                X509v3 Subject Alternative Name: 
                    DNS:worker, IP Address:<worker-ip>

批准后几秒，目录里多了 kubelet-server-current.pem 软链接，10250 端口出示的证书变成了 issuer=CN=kubernetes，kubectl logs 恢复。serving 证书同样会在快到期时重新提交 CSR，每次都要有人或控制器批准；打开这个选项前，先想好谁来批。

所以节点 Ready 只能说明 kubelet 到 API Server 这条路通，不代表反方向也通。

renew all 之后，运行中的组件用的是哪张证书

续期前先备份整个 /etc/kubernetes，里面有私钥，备份目录的权限要跟原目录一样严。etcd 数据另做快照，做法见 etcd 快照。实验里备份到了 /root/k8s-backup，下面写成带日期的形式（示意，未逐字记录）：

sudo cp -a /etc/kubernetes /root/k8s-backup-$(date +%F)
sudo kubeadm certs renew all
certificate embedded in the kubeconfig file for the admin to use and for kubeadm itself renewed
certificate for serving the Kubernetes API renewed
certificate the apiserver uses to access etcd renewed
certificate for the API server to connect to kubelet renewed
certificate embedded in the kubeconfig file for the controller manager to use renewed
certificate for liveness probes to healthcheck etcd renewed
certificate for etcd nodes to communicate with each other renewed
certificate for serving etcd renewed
certificate for the front proxy client renewed
certificate embedded in the kubeconfig file for the scheduler manager to use renewed
certificate embedded in the kubeconfig file for the super-admin renewed

Done renewing certificates. You must restart the kube-apiserver, kube-controller-manager, kube-scheduler and etcd, so that they can use the new certificates.

最后一行要求重启四个组件。原本的计划是证明「不重启，API Server 仍在出示旧证书」：续期前后各比一次磁盘上 apiserver.crt 和 6443 端口实际出示的证书的序列号。

echo | openssl s_client -connect 127.0.0.1:6443 2>/dev/null | openssl x509 -noout -serial -enddate
sudo openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -serial -enddate

两条命令放进一个小脚本里，前缀标明来源。续期前：

running: serial=42DCF5DB7C991540 notAfter=Oct 13 08:00:50 2027 GMT 
on-disk: serial=42DCF5DB7C991540 notAfter=Oct 13 08:00:50 2027 GMT

08:02:45 执行 renew all，没有重启任何组件，紧接着再查：

running: serial=37622D0F68DFC892 notAfter=Oct 13 08:02:45 2027 GMT 
on-disk: serial=37622D0F68DFC892 notAfter=Oct 13 08:02:45 2027 GMT

结果和预期相反：API Server 已经在出示新证书了。它的日志说明了原因，启动时为服务端证书注册了一个监视文件的控制器：

I1013 08:01:13.553803       1 dynamic_serving_content.go:135] "Starting controller" name="serving-cert::/etc/kubernetes/pki/apiserver.crt::/etc/kubernetes/pki/apiserver.key"
I1013 08:01:13.553975       1 dynamic_serving_content.go:135] "Starting controller" name="aggregator-proxy-cert::/etc/kubernetes/pki/front-proxy-client.crt::/etc/kubernetes/pki/front-proxy-client.key"

而在 renew 写文件的那一刻，它还读到了写了一半的文件：

E1013 08:02:45.292872       1 dynamic_serving_content.go:221] "Unhandled Error" err="key failed with : missing content for serving cert \"serving-cert::/etc/kubernetes/pki/apiserver.crt::/etc/kubernetes/pki/apiserver.key\"" logger="UnhandledError"
E1013 08:02:45.650264       1 dynamic_serving_content.go:221] "Unhandled Error" err="key failed with : tls: private key does not match public key" logger="UnhandledError"

推测是证书和私钥分两次写入，中间状态下二者不匹配；从结果看，控制器报错后没有采用残缺的文件，等文件写完整后加载了新证书。续期后看到这两行不用慌。

etcd 也一样，2379 端口出示的已经是新证书，和续期前备份目录 /root/k8s-backup 里的旧证书序列号不同：

etcd running: serial=144C3CD21A544C9C
etcd on-disk: serial=144C3CD21A544C9C
etcd backup : serial=0DD8A6BB5CEB84E8

续期后 20 秒左右，kubectl logs 还报过一次 write tcp ...->...:10250: use of closed network connection，重试就好了。推测是 API Server 发现 apiserver-kubelet-client 证书换了，主动关掉了到 kubelet 的旧连接，和上面 kubelet 轮换时「shutting down client connections」是同一种机制，这一点没有直接验证。

那为什么还要重启？官方文档的原话是动态重载「currently not supported for all components and certificates」。这次测到会热加载的是 API Server 和 etcd 的服务端证书。controller-manager 和 scheduler 用的是 kubeconfig 里内嵌的客户端证书，推测只在启动时读一次；它们手里的旧证书不会被吊销，照样能用，但会在原来的日期到期。不重启，一年后的同一天仍然会出事。外面没法直接看到这两个进程手里拿的是哪张客户端证书，所以这条没有测出来，按文档重启最稳妥。

重启静态 Pod

控制平面组件是 kubelet 直接管理的静态 Pod，kubectl delete pod 删掉的只是 API Server 里的镜像对象，进程不会重启。做法是把 manifest 临时移出目录，等容器停掉再移回来。一次只移一个组件，确认它恢复后再处理下一个；临时目录用 /root/manifests-aside/ 这类持久目录，不要用 /tmp，有些发行版的 /tmp 是 tmpfs，万一中途节点重启，manifest 就没了：

sudo mkdir -p /root/manifests-aside
sudo mv /etc/kubernetes/manifests/kube-apiserver.yaml /root/manifests-aside/
# 等 crictl ps --name kube-apiserver 不再有输出
sudo mv /root/manifests-aside/kube-apiserver.yaml /etc/kubernetes/manifests/

（实验节点是一次性的 kind 容器，当时临时目录用的是 /tmp，计时结果不受影响。）

计时结果：

官方文档说要等 20 秒（kubelet 的 fileCheckFrequency），实测 kubelet 一两秒内就发现了 manifest 被移走，推测除了定时轮询，kubelet 还监听了这个目录的文件变化。但不要依赖固定等待时间：确认旧容器真的没了再移回去，否则 kubelet 可能根本没察觉文件被移走过。新容器的 POD ID 换了，说明是重建而不是原地重启。

单控制平面集群重启 API Server 和 etcd 期间，API 会短暂不可用。高可用集群逐台节点续期、逐台重启，一台恢复后再处理下一台。

admin.conf 和 super-admin.conf

续期后对比一下自己手里的 kubeconfig 和节点上的 admin.conf、super-admin.conf：

my kubeconfig : subject=O=kubeadm:cluster-admins, CN=kubernetes-admin serial=5A596EDF4D37A511 notAfter=Oct 13 08:00:50 2027 GMT 
admin.conf: subject=O = kubeadm:cluster-admins, CN = kubernetes-admin serial=2C050EDBBD8C8EB5 notAfter=Oct 13 08:02:45 2027 GMT 
super-admin.conf: subject=O = system:masters, CN = kubernetes-super-admin serial=687487C66A04D678 notAfter=Oct 13 08:02:45 2027 GMT

renew 只改节点上的文件。拷到 $HOME/.kube/config、CI 系统或同事电脑上的那些副本还是旧证书，而且照样能用，续期之后用旧 kubeconfig 执行 kubectl auth whoami 一切正常，因为旧证书没过期、CA 也没变。这正是它危险的地方：续期当天什么都不会坏，旧副本会在原来的到期日突然失效。续期后要主动更新副本：

sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

两个文件的身份不同。admin.conf 属于 kubeadm:cluster-admins 组，靠一个 ClusterRoleBinding 获得 cluster-admin 权限：

NAME                     ROLE                        AGE     USERS   GROUPS                   SERVICEACCOUNTS
kubeadm:cluster-admins   ClusterRole/cluster-admin   3m40s           kubeadm:cluster-admins

super-admin.conf 是 kubeadm v1.29 起拆出来的，属于 system:masters 组，直接绕过 RBAC 授权，绑定被误删了也照样能用，是留给紧急情况的。日常不要用它，也不要分发；它的证书同样一年到期，renew all 会一并续期。

证书过期时看到什么

不能为了演示去拨节点时钟，下面用两张故意签得很短的证书模拟。

客户端证书过期。用集群 CA 签一张 3 分钟有效期、CN 为 notes-lab-shortlived 的客户端证书，写进一个单独的 kubeconfig。简化后的命令如下（-not_before/-not_after 需要 OpenSSL 3.4 及以上；client.ext 这一步是示意，实验里签发的证书没有加 EKU 扩展，同样能通过认证）：

# 在一次性环境里操作，ca.key 用完即删
openssl req -new -newkey rsa:2048 -nodes -keyout short.key \
  -subj '/CN=notes-lab-shortlived' -out short.csr
printf 'extendedKeyUsage=clientAuth\n' > client.ext
openssl x509 -req -in short.csr -CA ca.crt -CAkey ca.key -extfile client.ext \
  -not_before $(date -u -d '-1 min' +%Y%m%d%H%M%SZ) \
  -not_after  $(date -u -d '+2 min' +%Y%m%d%H%M%SZ) -out short.crt
# 构造 kubeconfig（示意，实验里是直接写的 YAML，内容等价）
kubectl --kubeconfig short.kubeconfig config set-cluster lab \
  --server https://<apiserver>:6443 --certificate-authority ca.crt
kubectl --kubeconfig short.kubeconfig config set-credentials short \
  --client-certificate short.crt --client-key short.key
kubectl --kubeconfig short.kubeconfig config set-context short --cluster lab --user short
kubectl --kubeconfig short.kubeconfig config use-context short
kubectl --kubeconfig short.kubeconfig auth whoami

有效期内：

ATTRIBUTE   VALUE
Username    notes-lab-shortlived
Groups      [system:authenticated]

到期 6 秒后：

08:07:26
error: You must be logged in to the server (Unauthorized)
error: You must be logged in to the server (Unauthorized)

kubectl 只说 401，不提证书。原因在 API Server 的日志里：

E1013 08:07:26.649796       1 authentication.go:73] "Unable to authenticate the request" err="[x509: certificate has expired or is not yet valid: current time 2026-10-13T08:07:26Z is after 2026-10-13T08:07:20Z, verifying certificate SN=288671046601627334219465353328182594739880327215, SKID=DB:A0:30:5E:E0:B3:A2:F2:62:B7:C6:5C:AA:C7:FE:26:9B:6D:25:59, AKID=A3:D3:C4:90:53:7E:E0:FF:32:F3:54:9C:23:93:99:45:A3:50:23:65 failed: x509: certificate has expired or is not yet valid: current time 2026-10-13T08:07:26Z is after 2026-10-13T08:07:20Z]"

API Server 对过期的客户端证书不会在 TLS 握手阶段拒绝，而是把请求当作认证失败处理。所以拿着过期的 kubeconfig，看到的是 Unauthorized，很容易误判成 RBAC 或 token 问题。这时候先解出 client-certificate-data 看 notAfter。

**服务端证书过期。**另签一张 5 分钟前就已过期、SAN 为 127.0.0.1 的服务端证书，用 openssl s_server 在本地端口上出示，让 kubectl 去连。kubectl 没有任何凭据时会交互式地要用户名，所以随便给一个 --token。简化命令（s_server 那一行是示意，未逐字记录）：

printf 'subjectAltName=IP:127.0.0.1\nextendedKeyUsage=serverAuth\n' > srv.ext
openssl req -new -newkey rsa:2048 -nodes -keyout srv.key -subj '/CN=expired-apiserver' -out srv.csr
openssl x509 -req -in srv.csr -CA ca.crt -CAkey ca.key -extfile srv.ext \
  -not_before $(date -u -d '-10 min' +%Y%m%d%H%M%SZ) \
  -not_after  $(date -u -d '-5 min' +%Y%m%d%H%M%SZ) -out srv.crt
openssl s_server -accept 127.0.0.1:16443 -cert srv.crt -key srv.key -www &   # 示意
kubectl --kubeconfig /dev/null --server https://127.0.0.1:16443 \
  --certificate-authority ca.crt --token dummy get nodes
kill %1   # 停掉 s_server（示意）

输出的最后一行：

Unable to connect to the server: tls: failed to verify certificate: x509: certificate has expired or is not yet valid: current time 2026-10-13T16:05:39+08:00 is after 2026-10-13T08:00:27Z

这一次报错直接出现在 kubectl 这边，信息也明确。apiserver.crt 过期时，客户端看到的应该就是这一行，前面还会有几行 memcache.go 的同样报错。两种情况可以这样区分：报 Unauthorized 是你的证书有问题，报 failed to verify certificate 是服务端的证书有问题。

真实集群里证书全部过期时，控制平面组件之间也无法互相认证，kubectl 可能完全不可用，这时要在控制平面节点上用 kubeadm certs renew 处理文件，再重启静态 Pod。签发只依赖本地的 CA 私钥，但 renew 的输出里有一行 Reading configuration from the cluster，API Server 已经不可用时它会怎样，这次没有实测。

外部 CA：EXTERNALLY MANAGED=yes

kubeadm 判断「外部 CA 模式」的依据很简单：/etc/kubernetes/pki 下有 ca.crt、没有 ca.key，其他证书和 kubeconfig 都已就位。在实验集群上把 ca.key 临时移走，就能看到这种状态。

仅限一次性集群，生产环境不要做
移走期间 kubeadm 无法签发任何 ca 证书。推测此时如果 controller-manager 重启，它找不到 CSR 签名用的私钥，可能起不来；这一点没有实测。

mv /etc/kubernetes/pki/ca.key /root/ca.key.aside
kubeadm certs check-expiration

判断是按 CA 分别做的：只有 ca 签发的那几张变成了 yes，etcd-ca 和 front-proxy-ca 的私钥还在，它们签的证书仍然归 kubeadm 管。这时分别续一张：

$ kubeadm certs renew apiserver
Detected external ca, certificate for serving the Kubernetes API can't be renewed
$ kubeadm certs renew etcd-server
certificate for serving etcd renewed

注意第一条：证书没有续上，命令的退出码却是 0，和第二条成功续期时一样。如果用脚本或定时任务跑 renew，只看退出码会以为成功了。续期之后一定要再跑一遍 check-expiration，确认 EXPIRES 真的变了。外部 CA 模式下，这些证书要用 kubeadm certs generate-csr 生成 CSR，交给外部 CA 签发后放回原位。实验做完立刻恢复，再确认一遍：

mv /root/ca.key.aside /etc/kubernetes/pki/ca.key
kubeadm certs check-expiration
apiserver                  Oct 13, 2027 08:02 UTC   364d            ca                      no      
ca                      Oct 10, 2036 08:00 UTC   9y              no

ca.key 放回去之后，这些行又变回了 no。

kubeadm upgrade 会顺带续期

官方文档写明，kubeadm upgrade apply 和 kubeadm upgrade node 在升级控制平面时会续期所有证书；如果集群至少每年升级一次，证书就不会过期。要关掉这个行为，传 --certificate-renewal=false。这次没有在实验集群上做升级，升级流程见 kubeadm 升级检查清单。反过来说，如果你的集群因为种种原因长期不升级，就得有人每年手动续期，最好用 check-expiration 加监控提前告警。

续期前的核对清单

  1. 确认证书由 kubeadm、外部 CA 还是其他系统签发（看 EXTERNALLY MANAGED），并确认 Kubernetes 与 kubeadm 版本。
  2. 备份 /etc/kubernetes（含私钥，注意访问权限）并保存一份可恢复的 etcd 快照，参考 etcd 快照。
  3. 每台控制平面节点执行 kubeadm certs renew all，之后重跑 check-expiration，确认日期确实变了，不要只看退出码。
  4. 逐个重启 kube-apiserver、kube-controller-manager、kube-scheduler、etcd 的静态 Pod，确认旧容器已经消失再放回 manifest。是否真的重启过，用 crictl ps 看 CREATED 时间和 POD ID 有没有变；API Server 会热加载服务端证书，openssl s_client 看到新序列号只能说明新证书已生效，证明不了组件重启过。
  5. 更新所有 admin.conf 的副本；super-admin.conf 留在节点上，不分发。
  6. kubelet 证书单独检查：/var/lib/kubelet/pki 下软链接指向的证书是否在有效期内；打开了 serverTLSBootstrap 的话，确认有人或控制器在批准 serving CSR。
