标签把对象关联起来

Label 是对象上的键值对，例如 app.kubernetes.io/name: web、env: prod。它的用途是筛选和关联：Deployment 靠它认领 Pod，Service 靠它找后端，kubectl get -l 靠它过滤。Annotation 也是键值对，但不能用来筛选，适合存放给人或工具看的补充信息。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，kubectl 客户端 v1.30.0，CNI 为 Calico），实验放在单独的 notes-lab namespace 里。节点名简化成了 worker、worker2，Pod IP 用 <pod-ip> 代替。Deployment 的选择器为什么不能改，Deployment 笔记里已经实测过；Service 选择器写错、选择器过宽误匹配，见 Service 笔记。这里不再重复。

标签的格式：哪些写得进去

先建一个 busybox Pod 当靶子，然后逐条试边界：

kubectl -n notes-lab run lbl --image=busybox:1.36 --restart=Never -- sleep 3600

键：名字 63 字符，前缀 253 字符

键分两段，前缀/名字，前缀可省略。名字部分 63 个字符可以，64 个就被拒绝：

$ kubectl -n notes-lab label pod lbl aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa=ok
pod/lbl labeled
$ kubectl -n notes-lab label pod lbl aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa=ok
The Pod "lbl" is invalid: metadata.labels: Invalid value: "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa": name part must be no more than 63 characters

前缀必须是 DNS 子域名，总长不超过 253。用三段 63 个 a 加一段 61 个 b（中间三个点，合计 253 字符）能写进去；最后一段多一个字符就报错（下面把那串前缀缩写了）：

The Pod "lbl" is invalid: metadata.labels: Invalid value: "<254 字符的前缀>/x": prefix part must be no more than 253 characters

前缀不能有大写，因为 DNS 子域名只接受小写；名字部分则可以有大写。一个键里也只能有一个 /：

$ kubectl -n notes-lab label pod lbl Example.COM/x=1
The Pod "lbl" is invalid: metadata.labels: Invalid value: "Example.COM/x": prefix part a lowercase RFC 1123 subdomain must consist of lower case alphanumeric characters, '-' or '.', and must start and end with an alphanumeric character (e.g. 'example.com', regex used for validation is '[a-z0-9]([-a-z0-9]*[a-z0-9])?(\.[a-z0-9]([-a-z0-9]*[a-z0-9])?)*')
$ kubectl -n notes-lab label pod lbl a/b/c=1
The Pod "lbl" is invalid: metadata.labels: Invalid value: "a/b/c": a qualified name must consist of alphanumeric characters, '-', '_' or '.', and must start and end with an alphanumeric character (e.g. 'MyName',  or 'my.name',  or '123-abc', regex used for validation is '([A-Za-z0-9][-A-Za-z0-9_.]*)?[A-Za-z0-9]') with an optional DNS subdomain prefix and '/' (e.g. 'example.com/MyName')
$ kubectl -n notes-lab label pod lbl _k=1
The Pod "lbl" is invalid: metadata.labels: Invalid value: "_k": name part must consist of alphanumeric characters, '-', '_' or '.', and must start and end with an alphanumeric character (e.g. 'MyName',  or 'my.name',  or '123-abc', regex used for validation is '([A-Za-z0-9][-A-Za-z0-9_.]*)?[A-Za-z0-9]')

kubernetes.io/ 和 k8s.io/ 前缀保留给 Kubernetes 核心组件，自己的标签用自己的域名做前缀，或者不带前缀。

值：可以为空，但不能有空格和中文

值同样最多 63 个字符，允许空字符串；不为空时必须以字母或数字开头和结尾，中间只能是字母、数字、-、_、.：

$ kubectl -n notes-lab label pod lbl empty=
pod/lbl labeled
$ kubectl -n notes-lab label pod lbl v=a_b.c-D9
pod/lbl labeled
$ kubectl -n notes-lab label pod lbl 'v=has space'
error: invalid label value: "v=has space": a valid label must be an empty string or consist of alphanumeric characters, '-', '_' or '.', and must start and end with an alphanumeric character (e.g. 'MyValue',  or 'my_value',  or '12345', regex used for validation is '(([A-Za-z0-9][-A-Za-z0-9_.]*)?[A-Za-z0-9])?')
$ kubectl -n notes-lab label pod lbl v=-dash
error: invalid label value: "v=-dash": a valid label must be an empty string or consist of alphanumeric characters, '-', '_' or '.', and must start and end with an alphanumeric character (e.g. 'MyValue',  or 'my_value',  or '12345', regex used for validation is '(([A-Za-z0-9][-A-Za-z0-9_.]*)?[A-Za-z0-9])?')
$ kubectl -n notes-lab label pod lbl 'k=中文'
error: invalid label value: "k=中文": a valid label must be an empty string or consist of alphanumeric characters, '-', '_' or '.', and must start and end with an alphanumeric character (e.g. 'MyValue',  or 'my_value',  or '12345', regex used for validation is '(([A-Za-z0-9][-A-Za-z0-9_.]*)?[A-Za-z0-9])?')

注意两种报错的开头不一样：键错了是 The Pod "lbl" is invalid，由 API Server 拒绝；值错了是 error: invalid label value，kubectl 在本地就拦下了，请求根本没发出去。换成 kubectl patch 绕过 kubectl 的检查，服务端照样拒绝，只是报错格式变成了 API Server 的：

$ kubectl -n notes-lab patch pod lbl -p '{"metadata":{"labels":{"v":"has space"}}}'
The Pod "lbl" is invalid: metadata.labels: Invalid value: "has space": a valid label must be an empty string or consist of alphanumeric characters, '-', '_' or '.', and must start and end with an alphanumeric character (e.g. 'MyValue',  or 'my_value',  or '12345', regex used for validation is '(([A-Za-z0-9][-A-Za-z0-9_.]*)?[A-Za-z0-9])?')

所以用 Helm 模板或脚本拼标签值时（比如把分支名 feature/login 或带 + 的版本号塞进标签），报错会在 apply 时才出现，而且是 metadata.labels: Invalid value。版本号、提交说明这类自由文本放注解更合适。

空值标签在选择时算「有这个键」：

$ kubectl -n notes-lab get pod -l empty -o name
pod/lbl
$ kubectl -n notes-lab get pod -l empty= -o name
pod/lbl
$ kubectl -n notes-lab get pod -l Empty -o name

最后一条什么都没返回：键区分大小写。

改已有的值要加 –overwrite

$ kubectl -n notes-lab label pod lbl v=other
error: 'v' already has a value (a_b.c-D9), and --overwrite is false
$ kubectl -n notes-lab label pod lbl v=other --overwrite
pod/lbl labeled
$ kubectl -n notes-lab label pod lbl v=other --overwrite
pod/lbl not labeled
$ kubectl -n notes-lab label pod lbl nothere-
label "nothere" not found.
pod/lbl not labeled

--overwrite 是防止误改的保险：新增标签不需要它，改已有键的值必须加。值没变时输出 not labeled；删除不存在的键（key-）只打印一行提示。这两种情况的退出码另外测过，都是 0，所以脚本里不能靠退出码判断标签有没有真的改动。

选择器：等值与集合

建 5 个只跑 sleep 的 Pod，标签各不相同，p5 故意不带 env：

kubectl -n notes-lab run p1 --image=busybox:1.36 --restart=Never --labels=env=dev,tier=web -- sleep 3600
kubectl -n notes-lab run p2 --image=busybox:1.36 --restart=Never --labels=env=staging,tier=web -- sleep 3600
kubectl -n notes-lab run p3 --image=busybox:1.36 --restart=Never --labels=env=prod,tier=web,canary=true -- sleep 3600
kubectl -n notes-lab run p4 --image=busybox:1.36 --restart=Never --labels=env=prod,tier=db -- sleep 3600
kubectl -n notes-lab run p5 --image=busybox:1.36 --restart=Never --labels=tier=cache -- sleep 3600

--show-labels 把所有标签挤在一列里，-L 把指定的键单独列出来，对比起来清楚得多：

$ kubectl -n notes-lab get pod -L env,tier,canary
NAME   READY   STATUS    RESTARTS   AGE    ENV       TIER    CANARY
p1     1/1     Running   0          114s   dev       web     
p2     1/1     Running   0          113s   staging   web     
p3     1/1     Running   0          112s   prod      web     true
p4     1/1     Running   0          110s   prod      db      
p5     1/1     Running   0          109s             cache

各种写法的匹配结果：

选择器匹配到说明
env=prodp3 p4等值
env!=prodp1 p2 p5没有 env 键的 p5 也算「不等于」
env in (dev,staging)p1 p2集合
env notin (prod)p1 p2 p5同样包含没有该键的对象
!envp5不存在该键
canaryp3存在该键，不看值
env=prod,tier=webp3逗号是 AND
env in (prod),!canaryp4两种写法可以混用
env in (prod,dev),tier notin (db)p1 p3

!= 和 notin 把 p5 也选进来，最容易让人意外：想用 env!=prod 找「非生产环境的 Pod」，结果混进了根本没标环境的东西。

$ kubectl -n notes-lab get pod -l env!=prod
NAME   READY   STATUS    RESTARTS   AGE
p1     1/1     Running   0          115s
p2     1/1     Running   0          114s
p5     1/1     Running   0          110s

要排除没有该键的对象，先加一个「存在」条件。另起三个 Pod 验证：q1 是 env=dev，q2 是 env=prod，q3 不带 env：

$ kubectl -n notes-lab get pod -l env!=prod -o name
pod/q1
pod/q3
$ kubectl -n notes-lab get pod -l 'env,env!=prod' -o name
pod/q1

选择器没有 OR。写 || 时，解析器把 prod||env 当成了一个值，然后按值的格式报错；集合写法少了括号也会报错：

$ kubectl -n notes-lab get pod -l 'env=prod||env=dev'
Error from server (BadRequest): Unable to find "/v1, Resource=pods" that match label selector "env=prod||env=dev", field selector "": unable to parse requirement: values[0][env]: Invalid value: "prod||env": a valid label must be an empty string or consist of alphanumeric characters, '-', '_' or '.', and must start and end with an alphanumeric character (e.g. 'MyValue',  or 'my_value',  or '12345', regex used for validation is '(([A-Za-z0-9][-A-Za-z0-9_.]*)?[A-Za-z0-9])?')
$ kubectl -n notes-lab get pod -l 'env in dev'
Error from server (BadRequest): Unable to find "/v1, Resource=pods" that match label selector "env in dev", field selector "": unable to parse requirement: found 'dev' expected: '('

要「prod 或 dev」，用 env in (prod,dev)。同一个键写两个等值条件 env=prod,env=dev 不报错，只是什么都匹配不到。

集合写法一定要加引号。在 zsh 里不加引号，括号会被当成通配符，命令根本到不了 kubectl（这次是在 zsh 的 eval 里跑的，所以报错前缀是 (eval):1:）：

$ kubectl -n notes-lab get pod -l env in (dev,staging)
(eval):1: no matches found: (dev,staging)

重复写 -l，只有最后一个生效

一开始用 -l env=prod -l tier=db 测，只返回了 p4，看起来像是两个条件取 AND。但这组数据分不出来，因为单独 tier=db 也只有 p4。把顺序换一下：

$ kubectl -n notes-lab get pod -l tier=web -l env=prod
NAME   READY   STATUS    RESTARTS   AGE
p3     1/1     Running   0          2m6s
p4     1/1     Running   0          2m4s
$ kubectl -n notes-lab get pod -l env=prod -l tier=web
NAME   READY   STATUS    RESTARTS   AGE
p1     1/1     Running   0          2m9s
p2     1/1     Running   0          2m8s
p3     1/1     Running   0          2m7s

结果分别等于单独的 env=prod 和单独的 tier=web：后一个 -l 直接覆盖了前一个，没有任何提示。kubectl 参考文档里 -l 的类型是 string，而 -L 是 strings、明确写了可以重复，两者行为不同。多个条件要写在同一个 -l 里，用逗号分隔。

注解：放什么都行，但不能筛选

注解的值没有字符限制，空格、中文、JSON 都可以：

$ kubectl -n notes-lab annotate pod p1 'notes-lab.io/note=这是 一段 带空格和中文的说明, 还有 {json: true}'
pod/p1 annotated
$ kubectl -n notes-lab get pod p1 -o jsonpath='{.metadata.annotations}'
{"cni.projectcalico.org/containerID":"e4abcc23…","cni.projectcalico.org/podIP":"<pod-ip>/32","cni.projectcalico.org/podIPs":"<pod-ip>/32","notes-lab.io/note":"这是 一段 带空格和中文的说明, 还有 {json: true}"}

注解的键和标签的键规则相同，bad key 这样带空格的键同样会被拒绝。另外，这个 Pod 上已经有 Calico 写入的三条注解，后面算大小时会用到。

注解没法用来选对象。-l 不认注解，不报错，只是返回空；字段选择器则直接报不支持：

$ kubectl -n notes-lab get pod -l notes-lab.io/note -o name
$ kubectl -n notes-lab get pod --field-selector metadata.annotations.notes-lab.io/note=x
Error from server (BadRequest): Unable to find "/v1, Resource=pods" that match label selector "", field selector "metadata.annotations.notes-lab.io/note=x": field label not supported: metadata.annotations.notes-lab.io/note

256 KiB 是所有注解合计

官方文档写的是：一个对象上所有注解的键和值加起来不能超过 256 KiB。先生成两个 patch 文件：

python3 -c "import json;print(json.dumps({'metadata':{'annotations':{'notes-lab.io/blob-a':'x'*200000}}}))" > a200k.json
python3 -c "import json;print(json.dumps({'metadata':{'annotations':{'notes-lab.io/blob-b':'y'*62000}}}))" > b62k.json

先写入 200000 字节的那条，再写入 62000 字节的：

$ kubectl -n notes-lab patch pod p2 --type=merge --patch-file a200k.json
pod/p2 patched
$ kubectl -n notes-lab patch pod p2 --type=merge --patch-file b62k.json
The Pod "p2" is invalid: metadata.annotations: Too long: must have at most 262144 bytes

两条单独都远小于上限，合起来 262000 字节，再加上 Calico 那三条注解，就超过了 262144。第二条改成 60000 字节就能写进去，这时统计各注解长度：

{'cni.projectcalico.org/containerID': 64, 'cni.projectcalico.org/podIP': 18, 'cni.projectcalico.org/podIPs': 18, 'notes-lab.io/blob-a': 200000, 'notes-lab.io/blob-b': 60000} 260226

键加值合计 260226 字节，离上限只剩 1.9 KB。这时如果 CNI、服务网格或 kubectl apply 再往对象上加注解，就会被拒。kubectl apply 会把整份清单存进 kubectl.kubernetes.io/last-applied-configuration 注解，清单里本身带着大注解时，等于占了两份额度；这一点这次没有单独测，是根据这个注解的存储方式推测的。

大注解还有一个更早的限制：命令行。kubectl annotate 的值直接放在参数里，Linux 对单个参数有长度上限（约 128 KiB），超过时连 kubectl 都启动不了。下面是中文 locale 下的报错，英文环境里是 argument list too long；kc 是实验时包装 kubectl 的 shell 函数：

$ kubectl -n notes-lab annotate pod p3 notes-lab.io/big=$(python3 -c "print(\"z\"*140000)")
kc: 参数列表过长: kubectl

120000 字节可以写进去。更大的内容应该用 --patch-file，或者干脆放进 ConfigMap。注解适合放一条说明、一个链接、一小段配置，存大数据并不合适。

字段选择器

字段选择器按对象字段过滤，但只支持每种资源事先登记的少数几个字段。Pod 支持 metadata.name、metadata.namespace、spec.nodeName、spec.restartPolicy、spec.schedulerName、spec.serviceAccountName、spec.hostNetwork、status.phase、status.podIP、status.nominatedNodeName。文档的列表里还有 status.podIPs，它能通过校验，但在 1.31 中不生效（据源码推断，未实测）：

$ kubectl -n notes-lab get pod --field-selector status.phase=Running,spec.nodeName!=worker2 -o wide
NAME   READY   STATUS    RESTARTS   AGE   IP          NODE     NOMINATED NODE   READINESS GATES
p1     1/1     Running   0          13m   <pod-ip>    worker   <none>           <none>

不在名单里的字段，哪怕是 metadata.labels、容器镜像这种很常用的，也会直接报错：

$ kubectl -n notes-lab get pod --field-selector metadata.labels.env=prod
Error from server (BadRequest): Unable to find "/v1, Resource=pods" that match label selector "", field selector "metadata.labels.env=prod": field label not supported: metadata.labels.env
$ kubectl -n notes-lab get pod --field-selector spec.containers.image=busybox:1.36
Error from server (BadRequest): Unable to find "/v1, Resource=pods" that match label selector "", field selector "spec.containers.image=busybox:1.36": field label not supported: spec.containers.image

字段选择器只有 =、==、!=，不支持集合写法；值区分大小写，写成小写 running 不报错，但什么也匹配不到：

$ kubectl -n notes-lab get pod --field-selector 'status.phase in (Running)'
Error from server (BadRequest): Unable to find "/v1, Resource=pods" that match label selector "", field selector "status.phase in (Running)": invalid selector: 'status.phase in (Running)'; can't understand 'status.phase in (Running)'
$ kubectl -n notes-lab get pod --field-selector status.phase=running
No resources found in notes-lab namespace.

它可以和 -l 一起用，两者取交集：

$ kubectl -n notes-lab get pod -l tier=web --field-selector status.phase=Running,metadata.name!=p1
NAME   READY   STATUS    RESTARTS   AGE
p2     1/1     Running   0          13m
p3     1/1     Running   0          13m

按镜像筛 Pod 这类需求，字段选择器做不到，只能先 get 再用 jsonpath 或 jq 在客户端过滤，见 kubectl JSONPath。

推荐标签 app.kubernetes.io/*

Kubernetes 建议在所有对象上使用一组共享前缀的标签：name（应用名）、instance（这一份部署的唯一名）、version、component、part-of（所属的上层应用）、managed-by（管理工具）。这些都只是约定，核心组件并不强制要求。下面这个 Deployment 用了其中五个，managed-by 留给 Helm 这类工具去写：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app.kubernetes.io/name: web
    app.kubernetes.io/instance: web-a
    app.kubernetes.io/part-of: shop
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: web
      app.kubernetes.io/instance: web-a
  template:
    metadata:
      labels:
        app.kubernetes.io/name: web
        app.kubernetes.io/instance: web-a
        app.kubernetes.io/version: "1.27"
        app.kubernetes.io/component: frontend
        app.kubernetes.io/part-of: shop
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
          ports:
            - name: http
              containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app.kubernetes.io/name: web
    app.kubernetes.io/instance: web-a
  ports:
    - port: 80
      targetPort: http

选择器只用了 name 和 instance，这两个在应用生命周期里不会变。version 每次发布都会变，放进选择器就等于把它冻住了，因为 Deployment 的选择器创建后不可修改（报错见 Deployment 笔记）。version 只放在模板标签里，供查询和展示。

按推荐标签查询：

$ kubectl -n notes-lab get pod -L app.kubernetes.io/instance,app.kubernetes.io/version,app.kubernetes.io/component
NAME                  READY   STATUS    RESTARTS   AGE    INSTANCE   VERSION   COMPONENT
web-9c6ccbcb6-bhf8t   1/1     Running   0          3m4s   web-a      1.27      frontend
web-9c6ccbcb6-mzphs   1/1     Running   0          3m3s   web-a      1.27      frontend
$ kubectl -n notes-lab get deploy,rs,svc -l app.kubernetes.io/part-of=shop
NAME                  READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/web   2/2     2            2           43m

NAME                            DESIRED   CURRENT   READY   AGE
replicaset.apps/web-9c6ccbcb6   2         2         2       3m6s

（Deployment 的 AGE 是 43m、ReplicaSet 只有 3m，推测是实验期间宿主机过载、控制平面中断了一段时间造成的：controller-manager 恢复后才创建出 ReplicaSet。和标签本身无关。）

查询里写了 svc，结果却没有 Service。原因是 Service 的 metadata.labels 是空的，它只有 spec.selector。选择器决定它选中谁，标签决定它能被谁选中，两者互不影响。ReplicaSet 能被查出来，是因为它的标签是从 Pod 模板复制过来的。想用 part-of=shop 一次列出整个应用，Service、ConfigMap 这些对象也得自己打上标签。

改标签把 Pod 移出 Deployment

把 Pod 的标签改掉让它脱离 ReplicaSet、留下来调试，以及改回去后被重新收养、多出来的一个被删掉，这两步在 API 对象与控制器关系里已经实测过，这里只看移出之后再删 Deployment 会怎样。

删 Deployment，孤儿 Pod 还在

把 bhf8t 的 instance 改成 debug 移出去，然后删除 Deployment：

$ kubectl -n notes-lab label pod web-9c6ccbcb6-bhf8t app.kubernetes.io/instance=debug --overwrite
pod/web-9c6ccbcb6-bhf8t labeled
$ kubectl -n notes-lab delete deployment web
deployment.apps "web" deleted
$ kubectl -n notes-lab get deploy,rs,pod --show-labels
NAME                      READY   STATUS    RESTARTS   AGE     LABELS
pod/web-9c6ccbcb6-bhf8t   1/1     Running   0          3m58s   app.kubernetes.io/component=frontend,app.kubernetes.io/instance=debug,app.kubernetes.io/name=web,app.kubernetes.io/part-of=shop,app.kubernetes.io/version=1.27,pod-template-hash=9c6ccbcb6

Deployment、ReplicaSet 和它管的 Pod 都被级联删除了，只有这个孤儿还在运行。它的 instance=debug 不在任何 Service 的选择器里，所以不接流量，但 nginx 仍在运行、能响应本地请求，继续占着资源：

$ kubectl -n notes-lab exec web-9c6ccbcb6-bhf8t -- wget -qO- -T 3 http://127.0.0.1/ | grep -o '<title>.*</title>'
<title>Welcome to nginx!</title>

级联删除顺着 ownerReferences 走，孤儿已经没有 owner，所以不会被删。它会一直占着资源，直到有人手动删除。隔离出来的 Pod 用完要记得清理。jsonpath 没法表达「字段不存在」，找出没有 owner 的 Pod 可以用 jq：

kubectl -n notes-lab get pod -o json | jq -r '.items[]|select(.metadata.ownerReferences==null)|.metadata.name'

提交时就会被拒的写法

Deployment 的模板标签必须满足它自己的选择器，否则 API Server 直接拒收：

spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: bad
  template:
    metadata:
      labels:
        app.kubernetes.io/name: bad-typo
$ kubectl -n notes-lab apply -f bad.yaml
The Deployment "bad" is invalid: spec.template.metadata.labels: Invalid value: map[string]string{"app.kubernetes.io/name":"bad-typo"}: `selector` does not match template `labels`

这个错误好查，因为提交时就报出来了。Service 就没这么幸运：它和 Pod 之间没有这种校验。把选择器里的 web-a 写成 web-A，Service 照样创建成功，只是 EndpointSlice 是空的：

$ kubectl -n notes-lab apply -f svc-typo.yaml
service/web-typo created
$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=web-typo
NAME             ADDRESSTYPE   PORTS     ENDPOINTS   AGE
web-typo-j6jfk   IPv4          <unset>   <unset>     1s

标签值区分大小写，这一类问题的排查顺序见 Service 笔记。

排查时先看什么

  1. 怀疑选择器没选中：把 Service 或控制器的选择器原样复制到 kubectl get pod -l '<selector>' 里跑一遍，结果为空就是标签对不上。
  2. 用 -L key1,key2 把相关键单独列成列，比在 --show-labels 的长串里找差异快得多。
  3. 用了 != 或 notin：记得它们会选中没有该键的对象。
  4. 多个条件写进同一个 -l，用逗号分隔，不要重复写 -l。
  5. 判断一个 Pod 归谁管，看 ownerReferences，不要看 Pod 的名字。

清理

kubectl delete namespace notes-lab
kubectl get namespace notes-lab
# Error from server (NotFound): namespaces "notes-lab" not found
