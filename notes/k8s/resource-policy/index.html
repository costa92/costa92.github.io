LimitRange 与 ResourceQuota

LimitRange 约束单个容器、单个 Pod 或单个 PVC 的资源配置，也能给没写 request/limit 的容器补上默认值；ResourceQuota 约束一个 namespace 里资源的总量。两者都在 API Server 的准入阶段起作用，常一起使用：默认值让每个新 Pod 都有明确的资源声明，配额再限制总占用。

系列里其他几篇已经碰过这两个对象：QoS 测了「只写 default 的 LimitRange 把什么都没写的 Pod 变成 Guaranteed」，kubectl 发现只写 max 时服务端会把 default/defaultRequest 也填上，集群组件和调谐循环看了配额挡住 ReplicaSet 创建 Pod 时的 FailedCreate 和退避。这一篇不再重复这些，而是把两个策略本身的规则逐条测一遍。

下文输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，StorageClass standard 为 local-path），实验放在单独的 notes-lab namespace 里，时间均为 UTC。单独创建的测试 Pod 都用下面这份清单，只有一个名为 app 的容器，每次只改 metadata.name 和 resources，下文直接写出每个 Pod 的 resources（{} 表示什么都不写）：

apiVersion: v1
kind: Pod
metadata:
  name: none
spec:
  terminationGracePeriodSeconds: 1
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources: {}

terminationGracePeriodSeconds: 1 是为了删 Pod 时不必等满 30 秒（sleep 不处理 SIGTERM）。大部分 LimitRange 测试用 --dry-run=server：它会完整走一遍准入（包括 LimitRanger 的改写），但不落盘，-o jsonpath 能直接看到改写后的结果。

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f pod.yaml --dry-run=server -o jsonpath='{.spec.containers[0].resources}{"\n"}'

下面各节按顺序在同一个 namespace 里做，每节开头写了要先删掉的上一节对象；不删的话，残留的 LimitRange 或配额会改变后面的结果。

LimitRange 的默认值怎么推出来

只写 defaultRequest：不会推出 limit

apiVersion: v1
kind: LimitRange
metadata:
  name: req-only
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 50m
        memory: 32Mi
kubectl -n notes-lab apply -f lr-req-only.yaml
$ kubectl -n notes-lab describe limitrange req-only
Type        Resource  Min  Max  Default Request  Default Limit  Max Limit/Request Ratio
----        --------  ---  ---  ---------------  -------------  -----------------------
Container   memory    -    -    32Mi             -              -
Container   cpu       -    -    50m              -              -

什么都没写的 Pod 只拿到 request，没有 limit：

{"requests":{"cpu":"50m","memory":"32Mi"}}

推导是单向的。读 v1.31 的 SetDefaults_LimitRangeItem（pkg/apis/core/v1/defaults.go），服务端保存 type: Container 的 LimitRange 时按这个顺序补字段：没写 default 就取 max；没写 defaultRequest 就取 default；还没有就取 min。从来没有「从 defaultRequest 推出 default」这一步。所以只写 defaultRequest 的 LimitRange 不会给容器加任何上限。

容器自己写了 limit：request 跟 limit，不跟 defaultRequest

还是这个 req-only，提交两个只写了 CPU limit 的 Pod：

# resources: {"limits":{"cpu":"20m"}}
{"limits":{"cpu":"20m"},"requests":{"cpu":"20m","memory":"32Mi"}}
# resources: {"limits":{"cpu":"300m"}}
{"limits":{"cpu":"300m"},"requests":{"cpu":"300m","memory":"32Mi"}}

CPU request 等于各自的 limit，既不是 defaultRequest 的 50m，也没有因为 20m 小于 50m 而报错；内存没写，才用上 defaultRequest 的 32Mi。先删掉 req-only，换成同时写了 default 和 defaultRequest 的 LimitRange（kubectl -n notes-lab delete limitrange req-only，再 apply 下面这份），结果一样：

apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 50m
        memory: 32Mi
      default:
        cpu: 100m
        memory: 64Mi
# resources: {}
{"limits":{"cpu":"100m","memory":"64Mi"},"requests":{"cpu":"50m","memory":"32Mi"}}
# resources: {"limits":{"cpu":"300m","memory":"128Mi"}}
{"limits":{"cpu":"300m","memory":"128Mi"},"requests":{"cpu":"300m","memory":"128Mi"}}
# resources: {"requests":{"cpu":"20m"}}
{"limits":{"cpu":"100m","memory":"64Mi"},"requests":{"cpu":"20m","memory":"32Mi"}}

原因是两层默认值的先后：Pod 进 API Server 先过类型默认值，「只写 limit 的资源，request 复制 limit」在这一步就做完了（探针与资源测过这条）；轮到 LimitRanger 时 request 已经有值，它只补缺失的字段（mergeContainerResources 里 if !found 才写入）。

request 写得比默认 limit 大：422，不是 403

# resources: {"requests":{"cpu":"150m","memory":"100Mi"}}
The Pod "req-big" is invalid: 
* spec.containers[0].resources.requests: Invalid value: "100Mi": must be less than or equal to memory limit of 64Mi
* spec.containers[0].resources.requests: Invalid value: "150m": must be less than or equal to cpu limit of 100m

用户只写了 request，LimitRanger 补上 100m/64Mi 的默认 limit，结果 request 大于 limit，被之后的对象校验拦下。报错里出现的 limit of 64Mi 是清单里根本没有的数字，第一次看到很容易摸不着头脑。官方文档对此有明确说明：LimitRange 不检查它注入的默认值是否和容器已有的值一致。文档对后果的描述是 Pod「will not be schedulable」，实测并不会等到调度：创建请求当场就返回 422，Pod 对象根本没有生成。遇到这种报错，先 kubectl describe limitrange 看默认 limit。

min、max 和 maxLimitRequestRatio

先删掉上一节的 defaults，再 apply 下面的 bounds：

kubectl -n notes-lab delete limitrange defaults
apiVersion: v1
kind: LimitRange
metadata:
  name: bounds
spec:
  limits:
    - type: Container
      min:
        cpu: 10m
        memory: 8Mi
      max:
        cpu: 200m
        memory: 128Mi
      maxLimitRequestRatio:
        cpu: "4"

读回来，default 和 defaultRequest 都被填成了 max（这就是 kubectl 那篇看到的现象，规则见上一节）：

$ kubectl -n notes-lab describe limitrange bounds
Type        Resource  Min  Max    Default Request  Default Limit  Max Limit/Request Ratio
----        --------  ---  ---    ---------------  -------------  -----------------------
Container   cpu       10m  200m   200m             200m           4
Container   memory    8Mi  128Mi  128Mi            128Mi          -

四种违规的原样报错：

# resources: {"limits":{"cpu":"500m","memory":"256Mi"}}
Error from server (Forbidden): error when creating "STDIN": pods "too-big" is forbidden: [maximum cpu usage per Container is 200m, but limit is 500m, maximum memory usage per Container is 128Mi, but limit is 256Mi]
# resources: {"requests":{"cpu":"5m","memory":"4Mi"}}
Error from server (Forbidden): error when creating "STDIN": pods "too-small" is forbidden: [minimum cpu usage per Container is 10m, but request is 5m, minimum memory usage per Container is 8Mi, but request is 4Mi, cpu max limit to request ratio per Container is 4, but provided ratio is 40.000000]
# resources: {"requests":{"cpu":"20m"},"limits":{"cpu":"200m"}}
Error from server (Forbidden): error when creating "STDIN": pods "ratio" is forbidden: cpu max limit to request ratio per Container is 4, but provided ratio is 10.000000
# resources: {"requests":{"cpu":"20m"}}
Error from server (Forbidden): error when creating "STDIN": pods "req-only" is forbidden: cpu max limit to request ratio per Container is 4, but provided ratio is 10.000000
  • max 比较的是 limit，min 比较的是 request，报错里写得很清楚（but limit is / but request is）。
  • too-small 多出一条比例违规：它没写 limit，被注入默认 limit 200m，200m / 5m = 40。
  • 最后一个最容易踩：只写了 requests.cpu: 20m，一个合法的、看起来很保守的 request，被拒的原因却是比例。默认 limit 取了 max 的 200m，200m / 20m = 10 超过 4。用户手里的清单里没有任何 limit，报错却在说 limit 和 request 的比例。有比例约束时，request 的下限是 limit / ratio；容器没写 limit 时，limit 被注入为 max，下限才等于 max / ratio（这里是 200m / 4 = 50m），比 min 写的 10m 高得多。

把 request 提到 50m 就能过，limit 依然注入为 200m：

# resources: {"requests":{"cpu":"50m"},"limits":{"cpu":"200m"}}
{"limits":{"cpu":"200m","memory":"128Mi"},"requests":{"cpu":"50m","memory":"128Mi"}}

type: Pod 只管有 limit 的那部分

type: Pod 约束的是 Pod 里所有容器加起来的量，不提供默认值。这一节保留 bounds，再加一个 per-pod：

apiVersion: v1
kind: LimitRange
metadata:
  name: per-pod
spec:
  limits:
    - type: Pod
      max:
        cpu: 300m
        memory: 200Mi
$ kubectl -n notes-lab get limitrange per-pod -o jsonpath='{.spec.limits[0]}{"\n"}'
{"max":{"cpu":"300m","memory":"200Mi"},"type":"Pod"}

两容器的测试 Pod 在基础清单上再加一个容器，两个容器分别叫 a 和 b：

containers:
  - name: a
    image: busybox:1.36
    command: ["sleep", "3600"]
    resources: {}
  - name: b
    image: busybox:1.36
    command: ["sleep", "3600"]
    resources: {}

和 bounds 同时存在时，两个容器都不写资源：每个容器被 bounds 注入 200m/128Mi，加起来超过 Pod 上限：

Error from server (Forbidden): error when creating "STDIN": pods "two-default" is forbidden: [maximum cpu usage per Pod is 300m, but limit is 400m, maximum memory usage per Pod is 200Mi, but limit is 256Mi]

两容器分别写 100m 和 150m 的 limit，总共 250m，可以通过。

接着删掉 bounds（kubectl -n notes-lab delete limitrange bounds），只留 per-pod，结果出乎意料。容器 a 什么都不写，容器 b 写 limits: {cpu: 100m, memory: 64Mi}：

pod/two-nolimit created (server dry run)
a {}
b {"limits":{"cpu":"100m","memory":"64Mi"},"requests":{"cpu":"100m","memory":"64Mi"}}

通过了。容器 a 没有任何上限，Pod 实际能用的资源不受 300m 约束。而两个容器都不写时才会被拒：

Error from server (Forbidden): error when creating "STDIN": pods "none-at-all" is forbidden: [maximum cpu usage per Pod is 300m.  No limit is specified, maximum memory usage per Pod is 200Mi.  No limit is specified]

v1.31 的 podLimits()（plugin/pkg/admission/limitranger/admission.go）只把写了 limit 的容器加起来；只要有一个容器有 limit，总和就有值，max 只和这个总和比较，没写 limit 的容器被直接忽略。只有所有容器都没写、总和里没有这项资源时，才报 No limit is specified。init 容器也会参与：普通 init 容器（以及它之前已启动的 sidecar 累计量）的 limit 取最大值，再和普通容器加 sidecar 的总和比较取大，这次没有测带 init 容器的 Pod。所以 type: Pod 的 max 不能单独用来兜底，要配合 type: Container 的 default 让每个容器都有 limit。

PersistentVolumeClaim：只有 min/max

先删掉 per-pod，再 apply 下面的 pvc-size。pvc-size 和 data-ok 这个 PVC 之后一直留着，它们不影响 Pod：

kubectl -n notes-lab delete limitrange per-pod
apiVersion: v1
kind: LimitRange
metadata:
  name: pvc-size
spec:
  limits:
    - type: PersistentVolumeClaim
      min:
        storage: 100Mi
      max:
        storage: 1Gi
$ kubectl -n notes-lab get limitrange pvc-size -o jsonpath='{.spec.limits[0]}{"\n"}'
{"max":{"storage":"1Gi"},"min":{"storage":"100Mi"},"type":"PersistentVolumeClaim"}

和 Container 类型不同，max 没有被复制成默认值，服务端的默认值补全只针对 Container。用 standard StorageClass 申请三种大小，清单如下，data-big、data-tiny 只把名字和 storage 换成 2Gi、50Mi：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-ok
spec:
  storageClassName: standard
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 500Mi
Error from server (Forbidden): error when creating "STDIN": persistentvolumeclaims "data-big" is forbidden: maximum storage usage per PersistentVolumeClaim is 1Gi, but request is 2Gi
Error from server (Forbidden): error when creating "STDIN": persistentvolumeclaims "data-tiny" is forbidden: minimum storage usage per PersistentVolumeClaim is 100Mi, but request is 50Mi
persistentvolumeclaim/data-ok created
NAME      STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
data-ok   Pending                                      standard       <unset>                 0s

Pending 是因为 local-path 的绑定模式是 WaitForFirstConsumer，要等有 Pod 用它才分配卷，和 LimitRange 无关（见 StorageClass）。拒绝发生在 PVC 对象创建时，比动态供给早，不会留下半成品的 PV。

只在创建时生效

上一节开头已经删掉了 per-pod，先确认 namespace 里只剩 pvc-size：

$ kubectl -n notes-lab get limitrange
NAME       CREATED AT
pvc-size   2026-10-13T11:25:23Z

然后建两样东西：一个 limits: {cpu: 500m, memory: 64Mi} 的 Pod big-before，一个什么资源都不写的 Deployment web（kubectl create deployment web --image=busybox:1.36 -- sleep 3600，它的容器名是 busybox）。然后再 apply 上面的 bounds（单容器最多 200m）：

NAME                  STATUS    RES
big-before            Running   map[limits:map[cpu:500m memory:64Mi] requests:map[cpu:500m memory:64Mi]]
web-b6cbccd96-vsmbg   Running   map[]

big-before 明明违反了新的 max，仍然在跑；web 的 Pod 也没有被补上默认值。之后给 big-before 加标签、加注解也都成功：

pod/big-before labeled
pod/big-before annotated

LimitRanger 的源码对 Pod 的更新请求直接跳过（SupportsAttributes 里 Pod + Update 返回 false），注释给的理由是：容器列表在创建后不可变，改写或校验它们没有意义。

rollout restart 让 Deployment 新建 Pod，新 Pod 才拿到默认值；但 Deployment 自己的模板还是空的，默认值只写进了 Pod：

$ kubectl -n notes-lab get pod -l app=web -o 'custom-columns=NAME:.metadata.name,STATUS:.status.phase,RES:.spec.containers[0].resources'
NAME                   STATUS    RES
web-568b587945-844fr   Running   map[limits:map[cpu:200m memory:128Mi] requests:map[cpu:200m memory:128Mi]]
web-b6cbccd96-vsmbg    Running   map[]
$ kubectl -n notes-lab get deploy web -o jsonpath='{.spec.template.spec.containers[0].resources}{"\n"}'
{}

（旧 Pod 还在列表里，是因为 sleep 不处理 SIGTERM，要等满 30 秒宽限期。）新 Pod 上有 kubernetes.io/limit-ranger 注解，记录了哪些字段是 LimitRanger 填的：

{...,"kubernetes.io/limit-ranger":"LimitRanger plugin set: cpu, memory request for container busybox; cpu, memory limit for container busybox"}

故障：加了 LimitRange 之后，下一次发布卡住

这也意味着：LimitRange 上线那一刻什么都不会坏，坏在之后第一次发布。把 Deployment 的 CPU limit 改成 500m：

$ kubectl -n notes-lab set resources deployment web --limits=cpu=500m,memory=64Mi
deployment.apps/web resource requirements updated

修改 Deployment 本身被接受了，LimitRange 只检查 Pod 和 PVC。8 秒后：

NAME                  READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/web   1/1     0            1           23s

想在发布前发现这种问题，对 Pod 清单跑一次 kubectl apply --dry-run=server，对 Deployment 跑没用，它不会触发 Pod 的准入。重试节奏见调谐循环。做完这一节，回滚 Deployment 并删掉 bounds：

kubectl -n notes-lab rollout undo deployment web
kubectl -n notes-lab delete limitrange bounds

回滚回到的是 rollout restart 那个版本，它的 ReplicaSet web-568b587945 一直在跑，所以不会新建 Pod。web 的 Pod 仍是被 bounds 注入了 200m/128Mi 的那个，后面算配额时还会用到这个数。

一个 namespace 里有两个 LimitRange

文档对这种情况只有一句：两个以上 LimitRange 时，应用哪个默认值是不确定的。实测一下。两个 LimitRange 的默认值故意错开，aa-platform 不写内存 limit，zz-team 不写内存 request：

apiVersion: v1
kind: LimitRange
metadata:
  name: zz-team
spec:
  limits:
    - type: Container
      default: {cpu: 150m, memory: 96Mi}
      defaultRequest: {cpu: 80m}
---
apiVersion: v1
kind: LimitRange
metadata:
  name: aa-platform
spec:
  limits:
    - type: Container
      default: {cpu: 100m}
      defaultRequest: {cpu: 50m, memory: 16Mi}

服务端补全后，zz-team 的内存 request 被填成了 96Mi：

aa-platform {"default":{"cpu":"100m"},"defaultRequest":{"cpu":"50m","memory":"16Mi"},"type":"Container"}
zz-team {"default":{"cpu":"150m","memory":"96Mi"},"defaultRequest":{"cpu":"80m","memory":"96Mi"},"type":"Container"}

头 5 次 dry-run 加 1 次真实创建，结果全是 zz-team 的值。如果只测到这里，很容易得出「按名字倒序」之类的结论。又跑了 20 次：

# pod.yaml 为基础清单，resources: {}
for i in $(seq 1 20); do
  kubectl -n notes-lab apply -f pod.yaml --dry-run=server -o jsonpath='{.spec.containers[0].resources}{"\n"}'
done | sort | uniq -c
 6 {"limits":{"cpu":"100m","memory":"96Mi"},"requests":{"cpu":"50m","memory":"16Mi"}}
14 {"limits":{"cpu":"150m","memory":"96Mi"},"requests":{"cpu":"80m","memory":"96Mi"}}

两种结果都出现了，而且第一种是拼出来的：CPU 和内存 request 来自 aa-platform，内存 limit 来自 zz-team（aa-platform 没有这一项）。同一份清单两次提交，可能一次拿到 96Mi 的内存 request，一次拿到 16Mi。

和源码对得上：LimitRanger 从 informer 缓存里列出 namespace 下所有 LimitRange，逐个合并默认值，每个字段只在还没有值时才写入，所以先处理的那个按字段胜出，后一个补空缺。缓存列表的顺序没有保证，这次观察到的 14:6 只是这 20 次的结果，不代表任何稳定比例。校验也是逐个 LimitRange 执行的，任何一个不满足都会拒绝；但被校验的值来自上面不确定的合并结果。所以如果某个 LimitRange 里有 maxLimitRequestRatio 这类依赖 limit 和 request 的约束，同一份清单可能时而通过、时而被拒（这次两个 LimitRange 都没写约束，没有实测这一点）。结论很简单：默认值只放在一个 LimitRange 里，其他 LimitRange 只写约束。

做完删掉这两个 LimitRange 和真实创建的那个 Pod（m-real，拿到的是 zz-team 的 80m/96Mi）：

kubectl -n notes-lab delete limitrange aa-platform zz-team
kubectl -n notes-lab delete pod m-real --wait=false

ResourceQuota：计算资源

apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute
spec:
  hard:
    requests.cpu: 300m
    limits.memory: 256Mi

配额可以比已有用量还小

此时 namespace 里有三个 Pod：big-before（500m/64Mi）、web（200m/128Mi）和刚被删除、还在终止中的 m-real（80m/96Mi），CPU request 合计 780m，正在终止的 m-real 也被计入了。namespace 里的 LimitRange 只剩 pvc-size。11:26:41.55 创建配额，第一次读到 status.used 只隔了 30 毫秒：

11:26:41.552439555
{"limits.memory":"288Mi","requests.cpu":"780m"} 11:26:41.582756843
$ kubectl -n notes-lab describe quota compute
Resource       Used   Hard
--------       ----   ----
limits.memory  288Mi  256Mi
requests.cpu   780m   300m

Used 大于 Hard，配额创建照样成功，现有 Pod 也不受影响，和 LimitRange 一样只在准入时检查。效果是从此 namespace 里任何新 Pod 都进不来，直到用量降到 Hard 以下。

exceeded quota 和 must specify 是两种拒绝

# resources: {"requests":{"cpu":"10m"},"limits":{"memory":"16Mi"}}
Error from server (Forbidden): error when creating "STDIN": pods "newbie" is forbidden: exceeded quota: compute, requested: requests.cpu=10m, used: requests.cpu=700m, limited: requests.cpu=300m
# resources: {}
Error from server (Forbidden): error when creating "STDIN": pods "nores" is forbidden: failed quota: compute: must specify limits.memory for: app; requests.cpu for: app
# resources: {"requests":{"cpu":"10m"}}
Error from server (Forbidden): error when creating "STDIN": pods "half" is forbidden: failed quota: compute: must specify limits.memory for: app

（这几次提交时 m-real 已经删除完毕，所以 used 是 700m，而不是上文的 780m。）

  • exceeded quota 是总量不够，报错只列超出的那一项：newbie 的内存 limit 16Mi 放得下，所以只提了 CPU。
  • failed quota: ... must specify 是 Pod 根本没声明配额要管的资源，和总量无关，哪怕配额全空也会拒。这条只针对 CPU 和内存：配额里出现 cpu、memory、requests.cpu、requests.memory、limits.cpu、limits.memory 中的哪个，Pod 的每个容器就必须声明对应的值（v1.31 pkg/quota/v1/evaluator/core/pods.go 的 validationSet 只有这 6 个键，源码注释特意写明不再往里加 ephemeral-storage 等资源），并且精确到 request/limit：配额管 requests.cpu 就要 request，管 limits.memory 就要 limit，half 写了 CPU request 仍因缺内存 limit 被拒。报错按容器名列出缺什么，多容器 Pod 能直接看出是哪个容器。

用 LimitRange 默认值解决 must specify

删掉 big-before 腾出用量（kubectl -n notes-lab delete pod big-before --wait=false，删除过程的计时见下一小节），再 apply 前面那个 defaults LimitRange（默认 request 50m/32Mi，默认 limit 100m/64Mi），重新提交什么都没写的 nores：

{"limits.memory":"128Mi","requests.cpu":"200m"} rv=11168607
pod/nores created
{"limits.memory":"192Mi","requests.cpu":"250m"} rv=11168636
$ kubectl -n notes-lab get pod nores -o jsonpath='{.spec.containers[0].resources}{"\n"}'
{"limits":{"cpu":"100m","memory":"64Mi"},"requests":{"cpu":"50m","memory":"32Mi"}}

同一个空清单，这次被接受，配额按注入后的值计了 50m 和 64Mi。这说明 LimitRanger 的改写发生在配额检查之前：它是修改型准入插件，ResourceQuota 是校验型，修改型全部跑完才轮到校验型。官方文档也正是推荐用 LimitRange 给配额 namespace 补默认值。

Used 由谁、在什么时候更新

上面 nores 创建前后，紧接着读到的 Used 已经加上了 50m，没有任何延迟。删除方向则要等。11:26:58.15 删除 big-before（宽限期 1 秒），每 0.26 秒读一次 Pod 状态和配额：

delete-start 11:26:58.148477907
pod "big-before" deleted
11:26:58.190880529 Running del=2026-10-13T11:26:59Z used={"limits.memory":"192Mi","requests.cpu":"700m"}
...
11:27:00.314947767 Running del=2026-10-13T11:26:59Z used={"limits.memory":"192Mi","requests.cpu":"700m"}
11:27:00.579481525 Failed del=2026-10-13T11:26:59Z used={"limits.memory":"192Mi","requests.cpu":"700m"}
11:27:00.842529640 Failed del=2026-10-13T11:26:59Z used={"limits.memory":"192Mi","requests.cpu":"700m"}
11:27:01.100212546 Error from server (NotFound): pods "big-before" not found used={"limits.memory":"128Mi","requests.cpu":"200m"}

用量在删除后约 3 秒才降下来，但这 3 秒主要花在 Pod 终止上：Pod 在 11:27:00.58 变成 Failed，大约 0.5 秒后（下一次采样之后的那次）用量就降了。不过用量下降那次采样时 Pod 已经 NotFound，这次分不清触发重算的是 Failed 还是对象删除。按 v1.31 的 QuotaV1Pod，phase 为 Succeeded/Failed 的 Pod 不计入配额，Succeeded 这一半由下文 Job 一节证实；还在 Terminating 的 Pod 怎么算，见调谐循环「Terminating 的 Pod 仍占配额」一节。配额对象的 managedFields 说明了是谁写的：

$ kubectl -n notes-lab get quota compute --show-managed-fields -o jsonpath='{range .metadata.managedFields[*]}{.manager} {.operation} {.subresource} {.time}{"\n"}{end}'
kubectl-client-side-apply Update  2026-10-13T11:26:41Z
kube-controller-manager Update status 2026-10-13T11:27:01Z
kube-apiserver Update status 2026-10-13T11:27:12Z

11:27:01 那次（删除后用量下降）是 kube-controller-manager 写的，11:27:12 那次（创建 nores）是 kube-apiserver 写的。也就是说：加用量由准入插件在创建请求里同步完成，先写配额状态，再放行对象（按设计这能防止并发创建超额，本次没有测并发）；减用量靠控制器管理器里的配额控制器，它监听 Pod 删除和状态变化后重算，平时还有一个全量重算周期，控制器管理器参数 --resource-quota-sync-period 默认 5 分钟（这个集群没有覆盖它；5 分钟的全量周期这次没有等着测）。修改 spec.hard 后，status.hard 也由配额控制器更新，不是 API Server：ResourceQuota 的更新策略 PrepareForUpdate 会保留旧 status，控制器发现 spec.hard 和 status.hard 不一致，把这个配额放进 missingUsageQueue 优先重算。后来在一个新建的、只有一个配额 cap（kubectl -n notes-lab create quota cap --hard=pods=3）的 namespace 里补测了一次，把 pods 从 3 改到 5：

patch 11:38:16.238282858
returned: spec=5 status.hard=3
11:38:16.281361365 status.hard=5
kubectl-create Update  2026-10-13T11:38:11Z {"f:spec":{"f:hard":{}}}
kube-controller-manager Update status 2026-10-13T11:38:16Z {"f:status":{"f:hard":{".":{},"f:pods":{}},"f:used":{".":{},"f:pods":{}}}}
kubectl-patch Update  2026-10-13T11:38:16Z {"f:spec":{"f:hard":{"f:pods":{}}}}

patch 返回的对象里 status.hard 还是 3，43 毫秒后读到 5，managedFields 里写 status.hard 的是 kube-controller-manager。

所以 kubectl describe quota 里的 Used 可能短暂偏高，不会偏低：刚删掉 Pod 时立刻重试创建，可能还会被拒，等几秒再试。Terminating 的 Pod 在宽限期内仍计入配额，调谐循环那篇测过批量删除时的这段空窗。

对象数量配额

compute 配额和 defaults LimitRange 保留，Pod 仍是 web 和 nores，再加一个计数配额：

apiVersion: v1
kind: ResourceQuota
metadata:
  name: objects
spec:
  hard:
    pods: "4"
    count/configmaps: "2"
    services.nodeports: "0"

刚建好，ConfigMap 就已经用掉 1 个：

每个 namespace 都有一个由控制器自动创建的 kube-root-ca.crt（Pod 用来校验 API Server 证书），它也算数。把 count/configmaps 设成 1 的话，用户一个都建不了。

services.nodeports: 0 禁止 NodePort，ClusterIP 不受影响。LoadBalancer 默认也会分配 NodePort，同样被拒；显式关掉 NodePort 分配就能通过：

error: failed to create LoadBalancer service: services "lb" is forbidden: exceeded quota: objects, requested: services.nodeports=1, used: services.nodeports=0, limited: services.nodeports=0
spec:
  type: LoadBalancer
  allocateLoadBalancerNodePorts: false

（在 kind 里这只是演示配额的计数方式，LoadBalancer 能否在不分配 NodePort 时正常工作取决于具体的负载均衡实现，见 Service 类型。）

Job：完成的 Pod 不占配额

还是上面的 objects（pods: 4）和 compute（requests.cpu: 300m），defaults LimitRange 也还在，namespace 里已有 2 个运行中的 Pod（web 和 nores），CPU request 合计 250m。跑一个串行 3 次的 Job，每个 Pod 睡 3 秒，资源由 defaults 注入（request 50m）：

apiVersion: batch/v1
kind: Job
metadata:
  name: batch
spec:
  completions: 3
  parallelism: 1
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: task
          image: busybox:1.36
          command: ["sh", "-c", "sleep 3"]

每秒记一次两个配额的用量和 Job 的 Pod（名字只留后缀）：

作用域：只管一部分 Pod

BestEffort 和 NotBestEffort

真实场景里常见的需求是：允许少量不声明资源的临时 Pod，其余必须声明。先删掉上一节的 Job、两个配额和 defaults，此时还剩 web、nores 两个 Pod，再建两个带作用域的配额：

kubectl -n notes-lab delete job batch
kubectl -n notes-lab delete quota compute objects
kubectl -n notes-lab delete limitrange defaults
apiVersion: v1
kind: ResourceQuota
metadata:
  name: besteffort
spec:
  hard:
    pods: "1"
  scopes: ["BestEffort"]
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: not-besteffort
spec:
  hard:
    pods: "3"
    requests.cpu: 300m
    limits.memory: 256Mi
  scopes: ["NotBestEffort"]

describe 会把作用域的含义直接写出来：

Scopes:     BestEffort
 * Matches all pods that do not have resource requirements set. These pods have a best effort quality of service.
Resource  Used  Hard
--------  ----  ----
pods      0     1
pod/be1 created
Error from server (Forbidden): error when creating "STDIN": pods "be2" is forbidden: exceeded quota: besteffort, requested: pods=1, used: pods=1, limited: pods=1
Error from server (Forbidden): error when creating "STDIN": pods "mem-only" is forbidden: failed quota: not-besteffort: must specify limits.memory for: app; requests.cpu for: app
pod/burst1 created
  • 第一个 BestEffort Pod 进来，第二个被 besteffort 拒。
  • mem-only 只写了 requests.memory: 16Mi，已经不是 BestEffort，于是归 not-besteffort 管，又因为缺 CPU request 和内存 limit 被 must specify 拒绝。只写一项资源，反而要满足更严的那个配额。
  • burst1（CPU request 20m、内存 limit 32Mi）满足要求。

QoS 的判定规则见 QoS。BestEffort 作用域只能配 pods，试图给它配 requests.cpu 会在创建配额时被拒：

The ResourceQuota "bad-scope" is invalid: spec.scopes: Invalid value: []core.ResourceQuotaScope{"BestEffort"}: unsupported scope applied to resource

道理也直接：BestEffort 的 Pod 没有 request，限制它们的 CPU request 总和没有意义。

按 PriorityClass 限制

先删掉上一小节的两个配额和 be1、burst1 两个 Pod：

kubectl -n notes-lab delete pod be1 burst1 --wait=false
kubectl -n notes-lab delete quota besteffort not-besteffort

另一种作用域用 scopeSelector 按 PriorityClass 选 Pod，用来防止某个 namespace 把高优先级用满。实验里临时建了一个 PriorityClass（做完即删），这里写作 high：

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high
value: 1000
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: high-priority
spec:
  hard:
    pods: "1"
  scopeSelector:
    matchExpressions:
      - scopeName: PriorityClass
        operator: In
        values: ["high"]
pod/hp1 created
Error from server (Forbidden): error when creating "STDIN": pods "hp2" is forbidden: exceeded quota: high-priority, requested: pods=1, used: pods=1, limited: pods=1
pod/normal created

hp1、hp2 是在基础清单的 spec 下加了 priorityClassName: high、不写资源的 Pod：

spec:
  priorityClassName: high

两个 priorityClassName: high 的 Pod 只进来一个，没设优先级的 normal 不受这个配额约束。

看到拒绝时怎么判断是谁

报错片段来源先看什么
maximum ... per Container is / minimum ... but request isLimitRange（403）kubectl describe limitrange 的 Min/Max
max limit to request ratio ... provided ratio isLimitRange（403）清单没写 limit 时，是不是注入了默认 limit
per Pod is 300m. No limit is specifiedPod 类型 LimitRange每个容器都需要 limit，或加 Container 默认值
Invalid value: ... must be less than or equal to ... limit of对象校验（422）request 大于 LimitRange 注入的默认 limit
exceeded quota: <名字>, requested: ..., used: ..., limited: ...ResourceQuotakubectl describe quota，刚删过 Pod 就等几秒
failed quota: <名字>: must specify ...ResourceQuota补资源声明，或用 LimitRange 默认值

通过 Deployment、Job 创建的 Pod，这些报错不会出现在 kubectl apply 的输出里，只在 ReplicaSet/Job 的事件和 status.conditions 里。

清理

kubectl delete namespace notes-lab
kubectl delete priorityclass high

删除 namespace 会连同其中的 LimitRange、ResourceQuota、Pod、PVC 一起删除；PriorityClass 是集群级对象，要单独删。
