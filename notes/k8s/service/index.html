Service：稳定地找到 Pod

Deployment 中的 Pod 会重建，IP 会变。Service 用标签选择器圈定一组 Pod，给它们一个固定的虚拟 IP（ClusterIP）和 DNS 名称；控制器持续把匹配的 Pod 地址写进 EndpointSlice，各节点上的 kube-proxy 再把发往 ClusterIP 的连接转给其中一个后端。先完成 Deployment 实验。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico，kube-proxy 为 iptables 模式），实验放在单独的 notes-lab namespace 里。节点名简化成 worker、worker2。IP 换成了占位符：Pod IP 按 Pod 名的随机后缀命名，例如 demo-web-68d89579c4-psvk8 的 IP 记作 <psvk8-ip>，方便和 iptables 规则、EndpointSlice 对上号；Service 的虚拟 IP 写作 <cluster-ip>。

搭一个能分辨后端的服务

后端用 traefik/whoami，它会在响应里打印自己的 hostname，也就是 Pod 名，这样每个请求落到哪个 Pod 一眼就能看出来。保存为 deploy.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: demo-web
  template:
    metadata:
      labels:
        app: demo-web
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.10.2
          ports:
            - name: http
              containerPort: 80
          resources:
            requests:
              cpu: 20m
              memory: 32Mi
            limits:
              memory: 64Mi

Service 保存为 service.yaml。targetPort 这里写的是容器端口的名字 http，不是数字，后面会看到这个选择的影响：

apiVersion: v1
kind: Service
metadata:
  name: demo-web
spec:
  type: ClusterIP
  selector:
    app: demo-web
  ports:
    - name: http
      port: 80
      targetPort: http
      protocol: TCP

再起两个客户端 Pod：client 用 curlimages/curl，bb 用 busybox:1.36。

kubectl -n notes-lab apply -f deploy.yaml -f service.yaml
kubectl -n notes-lab run client --image=curlimages/curl:latest --restart=Never --command -- sleep 3600
kubectl -n notes-lab run bb --image=busybox:1.36 --restart=Never --command -- sleep 3600
kubectl -n notes-lab get pod -o wide
kubectl -n notes-lab get svc demo-web
NAME                        READY   STATUS    RESTARTS   AGE   IP            NODE
client                      1/1     Running   0          17s   <client-ip>   worker2
demo-web-68d89579c4-9lpkf   1/1     Running   0          17s   <9lpkf-ip>    worker2
demo-web-68d89579c4-psvk8   1/1     Running   0          17s   <psvk8-ip>    worker
demo-web-68d89579c4-ztgts   1/1     Running   0          17s   <ztgts-ip>    worker2
NAME       TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
demo-web   ClusterIP   <cluster-ip>   <none>        80/TCP    17s

没写 type 时默认就是 ClusterIP；NodePort、LoadBalancer 等对外暴露的类型见 Service 类型。

EndpointSlice：Service 的后端名单

Service 对象本身不保存 Pod 列表。EndpointSlice 控制器按选择器找 Pod，结果写进带 kubernetes.io/service-name 标签的 EndpointSlice：

kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=demo-web -o yaml
endpoints:
- addresses:
  - <psvk8-ip>
  conditions:
    ready: true
    serving: true
    terminating: false
  nodeName: worker
  targetRef:
    kind: Pod
    name: demo-web-68d89579c4-psvk8
...（另外两个 Pod 结构相同）
metadata:
  generateName: demo-web-
  labels:
    endpointslice.kubernetes.io/managed-by: endpointslice-controller.k8s.io
    kubernetes.io/service-name: demo-web
  ownerReferences:
  - kind: Service
    name: demo-web
ports:
- name: http
  port: 80
  protocol: TCP

几个值得注意的地方：

  • ports 里已经是数字 80 了。Service 写的是端口名 http，控制器去 Pod 的容器端口里查到 http 对应 80，把解析后的结果写进来。官方文档提到，正因为按名字解析，同一个 Service 下不同版本的 Pod 可以把同名端口放在不同的数字上。
  • 每个端点带 nodeName 和 targetRef，排查时能直接对应到具体 Pod 和节点。
  • ownerReferences 指向 Service，删掉 Service，这些 EndpointSlice 会被一起回收。

DNS：短名是怎么补全的

在 client 里看 DNS 配置：

$ kubectl -n notes-lab exec client -- cat /etc/resolv.conf
search notes-lab.svc.cluster.local svc.cluster.local cluster.local localdomain
nameserver <dns-ip>
options ndots:5

nameserver 是 CoreDNS 的 Service IP。ndots:5 的意思是：名字里的点少于 5 个，就先依次拼上 search 里的后缀去查。所以在同一个 namespace 里写 demo-web，第一次尝试的就是 demo-web.notes-lab.svc.cluster.local，直接命中。跨 namespace 时要带上 namespace：在另一个 namespace notes-lab-b 里起一个 curl Pod，curl http://demo-web.notes-lab/ 返回 200，它拼上的是第二个后缀 svc.cluster.local；同一个 Pod 里只写 demo-web，第一次 3 秒超时报 Resolving timed out，放宽超时后 5 秒报 Could not resolve host: demo-web。短名只在本 namespace 内有效，而且失败得并不快，为什么要等 5 秒这次没有细查，推测和 localdomain 这类后缀要转发到上游 DNS 有关。最后那个 localdomain 不是 Kubernetes 加的，推测是从节点的 resolv.conf 继承来的，具体内容因环境而异。

用 busybox 风格的 nslookup 查短名时，输出容易误读：

$ kubectl -n notes-lab exec client -- nslookup demo-web
Server:		<dns-ip>
Address:	<dns-ip>:53

** server can't find demo-web.cluster.local: NXDOMAIN

** server can't find demo-web.svc.cluster.local: NXDOMAIN

Name:	demo-web.notes-lab.svc.cluster.local
Address: <cluster-ip>

** server can't find demo-web.localdomain: NXDOMAIN
...
command terminated with exit code 1

答案其实已经查到了，但这个 nslookup 会把每个搜索后缀都查一遍，只要有一个 NXDOMAIN，退出码就是 1。脚本里用它的退出码判断「DNS 坏了」会误判；用完整域名 demo-web.notes-lab.svc.cluster.local 查就是干净的单条结果。DNS 本身的排查见 DNS 排查。

另一种服务发现方式是环境变量。bb 是在 demo-web 创建之后才启动的，它的环境里有：

$ kubectl -n notes-lab exec bb -- env | grep ^DEMO_WEB | sort
DEMO_WEB_PORT=tcp://<cluster-ip>:80
DEMO_WEB_PORT_80_TCP=tcp://<cluster-ip>:80
DEMO_WEB_PORT_80_TCP_ADDR=<cluster-ip>
DEMO_WEB_PORT_80_TCP_PORT=80
DEMO_WEB_PORT_80_TCP_PROTO=tcp
DEMO_WEB_SERVICE_HOST=<cluster-ip>
DEMO_WEB_SERVICE_PORT=80
DEMO_WEB_SERVICE_PORT_HTTP=80

而后面那几个 web-* Service 是在 bb 之后创建的，bb 里一个 WEB_ 开头的变量都没有。环境变量只在容器启动时注入一次，所以官方文档要求「Service 必须先于客户端 Pod 创建」。实际使用中还是以 DNS 为准。

负载怎样分发

每个新连接随机选一个后端

在 client 里发 60 次请求，每次 curl 都是一个新的 TCP 连接：

kubectl -n notes-lab exec client -- sh -c \
  'for i in $(seq 1 60); do curl -s http://demo-web/ | grep Hostname; done' | sort | uniq -c
21 Hostname: demo-web-68d89579c4-9lpkf
20 Hostname: demo-web-68d89579c4-psvk8
19 Hostname: demo-web-68d89579c4-ztgts

分得很匀。规则可以直接在节点上看到。kind 的节点是 Docker 容器，名字是 <集群名>-worker2 这种形式，用 docker ps --format '{{.Names}}' 可以列出来，然后 docker exec 进去只读查看：

docker exec <集群名>-worker2 iptables-save -t nat | grep 'notes-lab/demo-web'
-A KUBE-SERVICES -d <cluster-ip>/32 -p tcp ... --dport 80 -j KUBE-SVC-4S37L7VAW4B2436R
-A KUBE-SVC-4S37L7VAW4B2436R ... -> <psvk8-ip>:80" -m statistic --mode random --probability 0.33333333349 -j KUBE-SEP-W42DAUOKUFAPMZ65
-A KUBE-SVC-4S37L7VAW4B2436R ... -> <ztgts-ip>:80" -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-F6GTYTZYCFSXZJ6A
-A KUBE-SVC-4S37L7VAW4B2436R ... -> <9lpkf-ip>:80" -j KUBE-SEP-SQANAFWZQUYEVCU4
-A KUBE-SEP-W42DAUOKUFAPMZ65 -p tcp ... -j DNAT --to-destination <psvk8-ip>:80

三条规则依次以 1/3、剩下的 1/2、剩下的全部命中，每个后端的概率都是 1/3。KUBE-SEP-* 链做 DNAT，把目标地址从 ClusterIP 改写成 Pod IP。也就是说，在 iptables 模式下 ClusterIP 不对应任何一块网卡，它只是这些 iptables 规则的匹配条件。

同一个连接上的请求不会换后端

一个 curl 进程在同一条命令里请求多个 URL 时，会复用同一个 keep-alive 连接。加 -v 能看到复用过程：

$ kubectl -n notes-lab exec client -- curl -sv http://demo-web/ http://demo-web/ 2>&1 | grep -E '^\*|Hostname'
* Established connection to demo-web (<cluster-ip> port 80) from <client-ip> port 34860
Hostname: demo-web-68d89579c4-psvk8
* Reusing existing http: connection with host demo-web
Hostname: demo-web-68d89579c4-psvk8

换成不带 -v 的统计：一条命令请求 5 个 URL，5 次全落在 psvk8；再把「一条命令请求 3 个 URL」跑三次：

3 Hostname: demo-web-68d89579c4-9lpkf

3 Hostname: demo-web-68d89579c4-psvk8

3 Hostname: demo-web-68d89579c4-ztgts

三次分别落在三个不同的 Pod，但每次内部都不换。kube-proxy 只在建立连接时选一次后端，之后这条连接上的所有请求都跟着走。由此推测，用 HTTP/2、gRPC 或连接池的客户端，长连接建好后流量会固定在少数几个 Pod 上，扩容出来的新 Pod 可能长时间分不到流量；这次没有测 gRPC，但按上面的机制，这类问题要在客户端或七层代理那一层解决。

port-forward 不经过负载均衡

kubectl -n notes-lab port-forward service/demo-web 8080:80
for i in $(seq 1 10); do curl -s http://127.0.0.1:8080/ | grep Hostname; done | sort | uniq -c
10 Hostname: demo-web-68d89579c4-9lpkf

10 次全是同一个 Pod。kubectl port-forward service/... 只是借 Service 的选择器挑出一个 Pod，然后直接转发到它，不经过 ClusterIP 和 kube-proxy。kubectl 的文档还写明，选中的 Pod 终止时转发会话就结束，需要重新执行命令（这一点这次没有复现）。用它验证「Service 的负载均衡是否正常」是测不出来的，要在集群内的 Pod 里测。

ClusterIP ping 不通是正常的

$ kubectl -n notes-lab exec bb -- ping -c 2 -W 2 <cluster-ip>
2 packets transmitted, 0 packets received, 100% packet loss
$ kubectl -n notes-lab exec bb -- ping -c 2 -W 2 <psvk8-ip>
2 packets transmitted, 2 packets received, 0% packet loss
$ kubectl -n notes-lab exec bb -- wget -qO- -T 3 http://<cluster-ip>/ | head -1
Hostname: demo-web-68d89579c4-ztgts

上面的规则只匹配 -p tcp --dport 80，ICMP 没有任何规则接手，ClusterIP 上也没有真实的主机来回应，所以 ping 必然丢包，而 HTTP 照常可用。排查时不要拿 ping ClusterIP 判断 Service 是否可用。顺带一提，curlimages/curl 镜像以非 root 运行，在里面 ping 会直接报 permission denied (are you root?)，所以这里换用了 busybox。

Pod 被替换时名单怎么变

上面这些测试做完之后，开一个循环每 0.5 秒读一次 EndpointSlice，然后删掉 worker 上的 psvk8（03:46:38.803 发出删除），把每次变化的内容摘出来：

03:46:39.334
demo-web-68d89579c4-9lpkf <9lpkf-ip> ready=true serving=true terminating=false
demo-web-68d89579c4-psvk8 <psvk8-ip> ready=false serving=true terminating=true
demo-web-68d89579c4-ztgts <ztgts-ip> ready=true serving=true terminating=false

03:46:44.248
demo-web-68d89579c4-9lpkf <9lpkf-ip> ready=true serving=true terminating=false
demo-web-68d89579c4-ztgts <ztgts-ip> ready=true serving=true terminating=false

03:46:47.630
demo-web-68d89579c4-9lpkf <9lpkf-ip> ready=true serving=true terminating=false
demo-web-68d89579c4-cd6g7 <cd6g7-ip> ready=true serving=true terminating=false
demo-web-68d89579c4-ztgts <ztgts-ip> ready=true serving=true terminating=false

删除发出后半秒内，旧 Pod 就被标成 ready=false terminating=true，只要还有就绪的端点，kube-proxy 就不会把新连接分给它。它在名单里又留了约 5 秒才被移除，推测是等容器真正退出（这次没有单独测容器的退出时间）。serving=true 表示它此时还能处理请求。按官方文档，这个行为在 v1.28 稳定：流量策略为 Local（例如 externalTrafficPolicy: Local）时，如果节点上的本地端点全部处于终止中，kube-proxy 会退而把流量转给这些终止中的端点，所以「终止中的 Pod 一定不接流量」并不绝对。细节见 优雅终止。替补 Pod cd6g7 拿到了新 IP <cd6g7-ip>，删除发出后约 9 秒出现在名单里。整个过程中 kubectl get svc demo-web 的 ClusterIP 一直是 <cluster-ip>，客户端不需要知道后端换了人。

五种常见故障

故意建几个有问题的 Service，后端仍然是上面那三个 demo-web Pod：

apiVersion: v1
kind: Service
metadata:
  name: web-typo        # 选择器把 - 写成了 _
spec:
  selector:
    app: demo_web
  ports:
    - port: 80
      targetPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: web-badport     # 容器监听 80，targetPort 写成 8080
spec:
  selector:
    app: demo-web
  ports:
    - port: 80
      targetPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: web-badname     # Pod 里没有叫 web 的端口
spec:
  selector:
    app: demo-web
  ports:
    - port: 80
      targetPort: web

客户端看到的错误一模一样

$ kubectl -n notes-lab exec client -- curl -sS -m 5 http://web-typo/
curl: (7) Failed to connect to web-typo:80 after 0 ms: Could not connect to server
$ kubectl -n notes-lab exec client -- curl -sS -m 5 http://web-badport/
curl: (7) Failed to connect to web-badport:80 after 0 ms: Could not connect to server
$ kubectl -n notes-lab exec client -- curl -sS -m 5 http://web-badname/
curl: (7) Failed to connect to web-badname:80 after 0 ms: Could not connect to server

三种错误原因不同，但客户端拿到的都是立即的连接拒绝，耗时都不到 1 毫秒，从客户端这边分不出是哪种。DNS 三个都能解析，Service 本身也都存在。区别要到 EndpointSlice 里找：

$ kubectl -n notes-lab get endpointslice
NAME                ADDRESSTYPE   PORTS     ENDPOINTS                          AGE
demo-web-v7b4p      IPv4          80        <9lpkf-ip>,<ztgts-ip>,<cd6g7-ip>   118s
web-badname-sz8nq   IPv4          <unset>   <ztgts-ip>,<cd6g7-ip>,<9lpkf-ip>   3s
web-badport-gvlcz   IPv4          8080      <ztgts-ip>,<9lpkf-ip>,<cd6g7-ip>   3s
web-typo-q6mgg      IPv4          <unset>   <unset>                            4s

选择器写错（web-typo）：ENDPOINTS 是空的，一个 Pod 都没选中。kubectl describe svc web-typo 里显示 Endpoints: <none>。这时把 Service 的 Selector 和 kubectl get pod --show-labels 逐字对比，标签的值区分 - 和 _、也区分大小写。

targetPort 写错（web-badport）：名单是满的，端口是 8080。describe 里是 Endpoints: <cd6g7-ip>:8080,...，看起来一切正常。这种情况在 EndpointSlice 层面看不出错，要绕过 Service 直接连 Pod IP 加 targetPort 验证：

$ kubectl -n notes-lab exec client -- curl -sS -m 3 http://<cd6g7-ip>:8080/
curl: (7) Failed to connect to <cd6g7-ip>:8080 after 0 ms: Could not connect to server

直连也失败，说明问题在「Pod 里那个端口没有进程监听」，再对照容器的 containerPort 和应用实际监听的端口。

命名端口不存在（web-badname）：这个最容易看走眼。kubectl get endpointslice 的 ENDPOINTS 列列出了三个 IP，只有 PORTS 是 <unset>。用 jsonpath 看，ports 字段是 null；kubectl describe svc web-badname 和 kubectl get endpoints 都显示 <none>。Pod 被选中了，但端口名解析不出来，这些地址等于不可用。

kube-proxy 的规则印证了这一点。这类规则在 filter 表里，用前面的 -t nat 是找不到的（实测 nat 表 grep 结果为空）：

docker exec <集群名>-worker2 iptables-save -t filter | grep 'has no endpoints'
-A KUBE-SERVICES -d <web-badname-ip>/32 -p tcp -m comment --comment "notes-lab/web-badname has no endpoints" -m tcp --dport 80 -j REJECT --reject-with icmp-port-unreachable
-A KUBE-SERVICES -d <web-typo-ip>/32 -p tcp -m comment --comment "notes-lab/web-typo has no endpoints" -m tcp --dport 80 -j REJECT --reject-with icmp-port-unreachable

没有可用后端的 Service，kube-proxy 会装一条 REJECT 规则，这就是 curl 立即失败、而不是等到超时的原因。web-badport 则是正常的 DNAT 链，包被转到 Pod 的 8080 上，再被 Pod 的内核拒绝。所以：EndpointSlice 有地址、PORTS 有值时，去查 Pod 的端口；ENDPOINTS 空或 PORTS 是 <unset> 时，查选择器和端口名。

Pod 未就绪：在名单里，但不接流量

再加两个带 app=demo-web 标签的 Pod：not-ready 是一个 whoami，但就绪探针检查一个不存在的端口 9999，所以永远 0/1；stray 是一个只跑 sleep 的 busybox，没有声明任何端口，却是 1/1 Ready，模拟「别的东西碰巧用了同一个标签」：

apiVersion: v1
kind: Pod
metadata:
  name: not-ready
  labels:
    app: demo-web
spec:
  containers:
    - name: whoami
      image: traefik/whoami:v1.10.2
      ports:
        - name: http
          containerPort: 80
      readinessProbe:
        tcpSocket:
          port: 9999
        periodSeconds: 3
---
apiVersion: v1
kind: Pod
metadata:
  name: stray
  labels:
    app: demo-web
spec:
  containers:
    - name: sh
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]
$ kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=demo-web \
    -o jsonpath='{range .items[*].endpoints[*]}{.targetRef.name} ready={.conditions.ready}{"\n"}{end}'
stray ready=true
demo-web-68d89579c4-9lpkf ready=true
demo-web-68d89579c4-ztgts ready=true
demo-web-68d89579c4-cd6g7 ready=true
not-ready ready=false

not-ready 被登记了但标成 ready=false。发 40 个请求，它一次也没有分到：

14 Hostname: demo-web-68d89579c4-9lpkf
17 Hostname: demo-web-68d89579c4-cd6g7
 9 Hostname: demo-web-68d89579c4-ztgts

所以「Pod 是 Running、Service 也选中了它，但就是没流量」，先看 READY 列和 EndpointSlice 里的 ready。探针怎么配见探针与资源管理。

标签误匹配：命名端口挡住了一次事故

上面的结果里还有一件出乎意料的事：stray 是 ready=true，可 40 个请求没有一个失败。看 EndpointSlice 列表就明白了：

NAME             ADDRESSTYPE   PORTS     ENDPOINTS                                       AGE
demo-web-6xccs   IPv4          <unset>   <stray-ip>                                      19s
demo-web-v7b4p   IPv4          80        <9lpkf-ip>,<ztgts-ip>,<cd6g7-ip> + 1 more...    2m40s

demo-web 多了一个 EndpointSlice，里面只有 stray（<stray-ip>），端口是 <unset>。stray 没有叫 http 的端口，控制器把它单独放进一个端口为空的分片，kube-proxy 不会往这里转发流量。

换一个用数字 targetPort: 80 的 Service web-num，选择器同样是 app=demo-web：

kubectl -n notes-lab create service clusterip web-num --tcp=80:80 --dry-run=client -o yaml \
  | sed 's/app: web-num/app: demo-web/' | kubectl -n notes-lab apply -f -

这次 stray 进了正常的名单，40 个请求里有 14 个失败：

14 FAIL
13 Hostname: demo-web-68d89579c4-9lpkf
 5 Hostname: demo-web-68d89579c4-cd6g7
 8 Hostname: demo-web-68d89579c4-ztgts

理论上是 1/4 失败，抽样结果 14/40 在随机波动范围内。这正是线上最难查的那种症状：部分请求连接被拒，重试几次又好了。根因是选择器太宽，圈进了不该圈的 Pod。排查方法是用 Service 的选择器反查 Pod，看有没有混进来的：

kubectl -n notes-lab get pod -l app=demo-web -o wide --show-labels

预防方法有两个：选择器多带一个标签（比如再加上 app.kubernetes.io/component），以及像 demo-web 那样用命名的 targetPort。后者能挡住「误匹配的 Pod 没有这个端口名」这类情况，但如果误匹配的 Pod 恰好也有同名端口就挡不住了，不能替代精确的选择器。

排查顺序

把上面的结果整理成一条从外到内的路径：

  1. kubectl get svc 确认 Service 存在、端口对；在集群内的 Pod 里用完整域名测 DNS。
  2. kubectl get endpointslice -l kubernetes.io/service-name=<svc>：ENDPOINTS 为空查选择器；PORTS 为 <unset> 查端口名；有多个分片时逐个看。
  3. 看各端点的 ready，对照 kubectl get pod 的 READY 列。
  4. 名单正常但仍失败，在客户端 Pod 里绕过 Service 直连 <pod-ip>:<targetPort>，失败就是 Pod 端口或应用的问题。
  5. 只有部分请求失败，用选择器反查 Pod，找混进来的后端。

清理

kubectl delete namespace notes-lab

删除 namespace 会连同其中的 Service、EndpointSlice 和 Pod 一起删掉。需要直接拿到每个 Pod 的地址时，看 Headless Service；HTTP 路由看 Ingress；包从 Pod 到 Pod 的完整路径见 CNI 网络路径。
