Pod 调度与节点选择

调度器为还没有指定节点的 Pod 选择运行位置，分两步：先过滤，排除资源不够、带着 Pod 不容忍的污点、或者不满足硬约束的节点；再对剩下的候选节点打分，选分数最高的那个。过滤后一个节点都不剩，Pod 就停在 Pending，调度器会在集群发生变化时再试。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），节点名简化成 control-plane、worker、worker2。三个节点的可分配资源都是 28 核 CPU、约 61 GiB 内存；control-plane 带有 kubeadm 默认的 node-role.kubernetes.io/control-plane:NoSchedule 污点，普通 Pod 不会被调度上去。实验用的节点标签统一加了 notes-lab.io/ 前缀，做完全部删除。

nodeSelector：标签对不上就一直 Pending

nodeSelector 是最直接的硬约束：节点必须带有全部指定的标签。先在还没有任何节点带这个标签的时候提交 Pod，看失败是什么样子。保存为 sel-demo.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: sel-demo
spec:
  nodeSelector:
    notes-lab.io/pool: lab
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
kubectl create namespace notes-lab
kubectl -n notes-lab apply -f sel-demo.yaml
kubectl -n notes-lab get pod sel-demo -o wide
kubectl -n notes-lab describe pod sel-demo
NAME       READY   STATUS    RESTARTS   AGE   IP       NODE     NOMINATED NODE   READINESS GATES
sel-demo   0/1     Pending   0          5s    <none>   <none>   <none>           <none>
Conditions:
  Type           Status
  PodScheduled   False
...
Node-Selectors:              notes-lab.io/pool=lab
...
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  6s    default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) didn't match Pod's node affinity/selector. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

NODE 为 <none>、PodScheduled 为 False，说明问题出在调度阶段，还没轮到 kubelet。这条消息分三段读：

  • 0/3 nodes are available：集群里 3 个节点，过滤后剩 0 个。
  • 1 node(s) had untolerated taint {...}：control-plane 因为污点被排除；2 node(s) didn't match Pod's node affinity/selector：两个 worker 因为标签不匹配被排除。1 + 2 正好是 3。
  • preemption: ... 3 Preemption is not helpful：调度器还评估过能不能通过驱逐低优先级 Pod 腾出位置，结论是没用，因为这两类原因都不是资源问题，驱逐谁都改变不了。

每个节点只记第一个失败的插件

注意计数：control-plane 既没有这个标签，也不容忍那个污点，两个条件都不满足，却只被记在污点一栏，所以总数是 1 + 2 = 3，而不是 4。原因在调度器的实现里：过滤阶段对每个节点按顺序执行过滤插件，碰到第一个拒绝的插件就返回（v1.31 RunFilterPlugins）。默认插件顺序是 NodeUnschedulable → NodeName → TaintToleration → NodeAffinity → NodePorts → NodeResourcesFit……（default_plugins.go），污点检查排在节点亲和性前面，control-plane 在 TaintToleration 这一步就被拒了，根本轮不到检查标签。

排查时要记住：消息里没出现的原因，不等于那个节点在这一项上是满足的。给 Pod 加上容忍之后，它很可能接着报 didn't match Pod's node affinity/selector。污点本身的用法见污点与容忍。

补上标签，Pending 的 Pod 自己会被调度

再用同样的配置提交一个 sel-demo2（把 metadata.name 改掉再 apply 一次），现在就有两个 Pending 的 Pod。给 worker2 打标签，然后看事件：

kubectl label node worker2 notes-lab.io/pool=lab    # 03:48:32 执行
kubectl -n notes-lab get events --sort-by=.lastTimestamp \
  -o custom-columns=LAST:.lastTimestamp,OBJ:.involvedObject.name,REASON:.reason
LAST                   OBJ         REASON
2026-10-12T03:47:48Z   sel-demo    FailedScheduling
2026-10-12T03:48:23Z   sel-demo2   FailedScheduling
2026-10-12T03:48:33Z   sel-demo    Scheduled
2026-10-12T03:48:33Z   sel-demo2   Scheduled

打标签后 1 秒内，两个分别等了约 10 秒和四十多秒的 Pod 都被分配到 worker2，不需要删掉重建。调度器会在节点变化时重新尝试那些不可调度的 Pod。

标签删了，Pod 不会被赶走

反过来，在两个 Pod 运行时删掉 worker2 上的标签：

kubectl label node worker2 notes-lab.io/pool-   # 03:48:54
kubectl -n notes-lab get pod -o wide           # 03:49:15
NAME        READY   STATUS    RESTARTS   AGE   NODE
sel-demo    1/1     Running   0          87s   worker2
sel-demo2   1/1     Running   0          54s   worker2

两个 Pod 照常运行。nodeSelector 和下面的 requiredDuringSchedulingIgnoredDuringExecution 一样，只在调度那一刻检查，名字里的 IgnoredDuringExecution 就是这个意思。想让节点主动赶走不符合条件的 Pod，要用 NoExecute 污点。

既然调度靠节点标签，标签键最好选 kubelet 自己改不了的。官方建议隔离用的标签放在 node-restriction.kubernetes.io/ 前缀下，配合 NodeRestriction 准入插件，防止被攻破的节点给自己贴标签，把工作负载吸过去。

requests 太大：Insufficient cpu / memory

调度器比较的是节点可分配量减去已调度 Pod 的 requests 总和，不是节点当前的实际使用率。故意提交四个 requests 超标的 Pod：

Podrequests.cpurequests.memory
big-cpu3264Mi
big-mem100m80Gi
big-both3280Gi
fit-282864Mi
big-cpu   0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient cpu. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.
big-mem   0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient memory. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.
big-both  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient cpu, 2 Insufficient memory. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.
fit-28    0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient cpu. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

几个值得注意的地方：

  • big-both 的计数是 1 + 2 + 2 = 5，比节点数还多。每个节点仍然只记第一个拒绝它的插件，但 NodeResourcesFit 这一个插件返回的状态里可以带多个原因（Insufficient cpu 和 Insufficient memory 同时出现），而消息是按原因计数的。所以这里要理解成「几个节点缺 CPU、几个节点缺内存」，不能直接加起来对节点总数。

  • fit-28 请求的 28 核正好等于节点的可分配量，照样失败。原因是节点上已经有别的 Pod 占了 requests：

    kubectl describe node worker | sed -n '/Allocated resources/,/Events/p'
    Resource           Requests     Limits
--------           --------     ------
cpu                600m (2%)    3100m (11%)
memory             1056Mi (1%)  4896Mi (7%)

    这个节点实际很空闲，但 28 − 0.6 = 27.4 核才是新 Pod 能申请的上限。看 requests 一栏，不要看 kubectl top。

  • 抢占那一段从 3 Preemption is not helpful 变成了 2 No preemption victims found：资源不足属于驱逐别的 Pod 有可能解决的问题，所以调度器会在每个 worker 上找优先级比新 Pod 低的 Pod；这次没有找到：新 Pod 没设 PriorityClass，优先级是默认的 0，节点上没有比它更低的 Pod，于是报了这一句。不过前三个 Pod 的请求本身就超过了节点的可分配量，就算把节点上的 Pod 全部驱逐也放不下，抢占对它们本来就没有意义。只有 fit-28 这种「节点总量够、被别人的 requests 占了」的情况，配上更高优先级的 PriorityClass，才有可能靠抢占调度上去。本实验没有测抢占。

这种 Pod 不会自己好起来，只有调小 requests 或者加节点。requests 和 limits 的设置见探针与资源管理。

nodeAffinity：required 与 preferred

nodeSelector 只能做「标签等于某值」的精确匹配。节点亲和性支持 In、NotIn、Exists、Gt 等运算符，还分硬约束和软偏好两种。实验前给两个 worker 打标签：

kubectl label node worker  notes-lab.io/zone=a
kubectl label node worker2 notes-lab.io/zone=c notes-lab.io/disk=ssd

required：同一个 term 里是 AND，多个 term 之间是 OR

aff-and 把两个条件写在同一个 matchExpressions 里，要求「zone 是 a 或 b」并且「disk 是 ssd」。保存为 aff-and.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: aff-and
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: notes-lab.io/zone
                operator: In
                values: ["a", "b"]
              - key: notes-lab.io/disk
                operator: In
                values: ["ssd"]
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}

aff-or.yaml 把同样两个条件拆成两个 nodeSelectorTerms：

apiVersion: v1
kind: Pod
metadata:
  name: aff-or
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: notes-lab.io/zone
                operator: In
                values: ["a", "b"]
          - matchExpressions:
              - key: notes-lab.io/disk
                operator: In
                values: ["ssd"]
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}
kubectl -n notes-lab apply -f aff-and.yaml -f aff-or.yaml
kubectl -n notes-lab get pod -o wide
NAME      READY   STATUS    RESTARTS   AGE   NODE
aff-and   0/1     Pending   0          7s    <none>
aff-or    1/1     Running   0          6s    worker

worker 只有 zone=a，worker2 只有 disk=ssd，没有节点两样都满足，所以 aff-and 一直 Pending；aff-or 两个节点都符合，最终落在 worker。缩进写错一层，语义就从 AND 变成 OR，而 YAML 依然合法，kubectl apply 不会有任何提示。

aff-and 的 FailedScheduling 消息和前面 nodeSelector 那次一字不差，仍然是 didn't match Pod's node affinity/selector。消息不会告诉你哪一条表达式没满足，要自己拿 kubectl get nodes -L notes-lab.io/zone,notes-lab.io/disk 对着规则逐条核对。同时写了 nodeSelector 和 nodeAffinity 时，两者都要满足。

preferred：这次压过了默认打散，weight 写 1 也一样

软偏好只参与打分，不参与过滤。用 4 副本的 Deployment 对比几种写法。完整的 pref-w1.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: pref-w1
spec:
  replicas: 4
  selector:
    matchLabels: {app: pref-w1}
  template:
    metadata:
      labels: {app: pref-w1}
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 1
              preference:
                matchExpressions:
                  - key: notes-lab.io/zone
                    operator: In
                    values: ["c"]
      containers:
        - name: app
          image: busybox:1.36
          command: ["sleep", "3600"]
          resources:
            requests: {cpu: 10m, memory: 16Mi}

其余几个只改名字和 weight/values：pref-c 把 weight 改成 100，baseline 去掉整个 affinity，pref-none 把 values 改成 ["zzz"]、副本数改成 2。每次只跑一个 Deployment，删干净再跑下一个。

Deployment亲和性workerworker2
baseline无22
pref-c偏好 zone=c，weight 10004
pref-w1偏好 zone=c，weight 104

没有亲和性时，4 个 Pod 被均匀分到两个 worker 上。这种打散来自默认就开启的打分插件：PodTopologySpread 的系统默认软约束（按主机名和可用区打散同一个控制器的 Pod），加上 NodeResourcesBalancedAllocation 等资源均衡类打分。加了偏好之后，在这个 4 副本、Pod 很小的场景里，4 个全部落到了 worker2，打散没有压过偏好。副本数更多、节点更多时结果会不会变，这次没有测。

weight 改成 1 结果也一样。官方文档说调度器把节点满足的各条偏好的 weight 累加起来，按字面理解 weight 1 应该很弱。但看 v1.31 的实现：NodeAffinity 插件的 Score 确实是把匹配上的 weight 加起来，随后的 NormalizeScore 调用 DefaultNormalizeScore(100)，把各节点得分按最高分等比缩放到 0–100，再乘以插件权重 2 参与汇总。只有一条偏好时，匹配的节点总是被缩放成 100 分，weight 写 1 还是 100 没有区别；weight 只在多条 preferred 规则之间比较相对大小。如果目标是「尽量分散，同时略微倾向某类节点」，靠调小 weight 达不到，要配合拓扑分布约束。

最后，偏好一个根本不存在的值（zone=zzz），Pod 照常调度，两个副本分在两个 worker 上。这就是 preferred 和 required 的根本区别：偏好落空不会导致 Pending。

nodeName：绕过调度器

spec.nodeName 直接指定节点，调度器不再处理这个 Pod，由那个节点上的 kubelet 接手。做两个测试，一个指向 control-plane，一个指向不存在的节点：

apiVersion: v1
kind: Pod
metadata:
  name: nn-cp
spec:
  nodeName: control-plane    # 另一个 Pod nn-ghost 写成 no-such-node
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
NAME       READY   STATUS              RESTARTS   AGE   NODE
nn-cp      0/1     ContainerCreating   0          17s   control-plane
nn-ghost   0/1     Pending             0          15s   no-such-node

nn-cp 很快跑在了 control-plane 上，尽管那里有 NoSchedule 污点。它的事件里只有 kubelet 的 Pulling、Pulled、Created、Started，没有 default-scheduler 发出的 Scheduled：NoSchedule 是给调度器看的，绕过调度器也就绕过了它。

不过绕过的只是调度器，kubelet 在启动 Pod 前还有自己的准入检查（v1.31 pkg/kubelet/lifecycle/predicate.go）：资源是否放得下，放不下 Pod 会直接失败，原因是 OutOfcpu、OutOfmemory 这类；nodeSelector 和 required 节点亲和性是否匹配；端口是否冲突；污点只检查 NoExecute，代码注释写的就是 kubelet 只关心 NoExecute 污点。所以 nodeName 能越过 NoSchedule，越不过 NoExecute，也越不过资源和标签约束，只是失败从 Pending 变成了 Pod 直接 Failed。这几种 kubelet 拒绝的情况本次没有复现。

nn-ghost 指向一个不存在的节点，状态是 Pending，NODE 列却填着 no-such-node，而且一条事件都没有：没有调度器会为它报 FailedScheduling，也没有 kubelet 认领它。它在 50 秒时还在，60 秒时已经 NotFound，被自动删除了。官方文档的说法是这种 Pod「不会运行，某些情况下可能被自动删除」；推测这里是 kube-controller-manager 里的 PodGC 在工作：按 Pod 生命周期 文档，PodGC 会清理绑定到不存在节点的孤儿 Pod，删除前先把它标成 Failed 并加上 DisruptionTarget 条件。v1.31 源码里 PodGC 每 20 秒检查一次（gcCheckPeriod），节点不存在要先等 40 秒隔离期（quarantineTime），某一轮检查发现节点不存在（创建后 0–20 秒）才开始计隔离期，期满后还要等下一轮检查才真正删除，所以 Pod 会在创建后约 40 到 80 秒之间被删，和观察到的 50–60 秒吻合。删除前那一刻的状态本次没有抓到。

所以 nodeName 写错的表现和标签不匹配完全不同：前者没有任何事件，Pod 过一会儿凭空消失；后者有清楚的 FailedScheduling。日常调度不要用 nodeName，它是给自定义调度器和特殊场景用的。

怎么选

机制适用情况实测要点
nodeSelector精确匹配少量节点标签不匹配就 Pending；补标签后自动调度；删标签不驱逐
节点亲和性 required需要 In/NotIn/Exists 等集合匹配term 之间 OR，term 内 AND；失败消息不指明哪条表达式
节点亲和性 preferred软偏好只有一条偏好时 weight 1 和 100 效果一样；本次 4 副本实验中压过了默认打散
Pod 亲和与反亲和根据其他 Pod 的位置放置依赖拓扑域标签
污点与容忍节点排斥不合适的 Pod容忍只解除排斥，不保证调度到该节点
nodeName跳过调度器无视 NoSchedule 污点，但 kubelet 仍检查资源、标签和 NoExecute；节点名写错没有事件，Pod 会被清理

排查 Pending 的顺序：describe 里先看 NODE 是否为空、有没有 FailedScheduling；有就逐段拆 0/N nodes are available，注意每个节点只记第一个拒绝它的插件；没有事件却显示了节点名，就去核对 nodeName。

清理

kubectl delete namespace notes-lab
kubectl label node control-plane worker worker2 notes-lab.io/pool- notes-lab.io/zone- notes-lab.io/disk-
