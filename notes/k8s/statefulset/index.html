有稳定身份的 Pod

Deployment 的副本可以互相替换，名字带随机后缀，挂的是同一份卷模板。StatefulSet 给每个副本一个固定序号：Pod 叫 web-0、web-1，删掉重建还叫这个名字；通过 volumeClaimTemplates，每个序号有自己的一个 PVC；配合 Headless Service，每个序号还有一条固定的 DNS 记录。它只负责「身份」和「顺序」，数据库的复制、选主、备份仍然是应用自己的事。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），实验放在单独的 notes-lab namespace。默认 StorageClass standard 是 rancher 的 local-path provisioner，volumeBindingMode: WaitForFirstConsumer、回收策略 Delete，卷就是节点本地磁盘上的一个目录。节点名简化为 control-plane、worker、worker2，Pod IP 用 <pod-ip> 之类的占位符代替。PV、PVC 和 StorageClass 本身的概念见持久卷和 StorageClass，这里不重复。

实验用的 StatefulSet

保存为 web.yaml。容器启动时如果卷里还没有 index.html，就写一行「主机名 + 首次写入时间」，已有则不动，这样一眼能看出卷是不是原来那块。就绪探针延迟 5 秒，preStop 睡 3 秒，让创建和终止的顺序在时间线上拉开：

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  clusterIP: None
  selector:
    app: web
  ports:
    - name: http
      port: 80
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: web
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      terminationGracePeriodSeconds: 10
      containers:
        - name: nginx
          image: nginx:alpine
          command:
            - sh
            - -c
            - |
              f=/usr/share/nginx/html/index.html
              [ -f $f ] || echo "$(hostname) first written $(date +%T)" > $f
              exec nginx -g 'daemon off;'
          ports:
            - containerPort: 80
              name: http
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 2
          lifecycle:
            preStop:
              exec:
                command: ["sleep", "3"]
          resources:
            requests:
              cpu: 20m
              memory: 32Mi
            limits:
              memory: 64Mi
          volumeMounts:
            - name: data
              mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 16Mi
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f web.yaml
kubectl -n notes-lab rollout status sts/web --timeout=180s
Waiting for 3 pods to be ready...
Waiting for 2 pods to be ready...
Waiting for 1 pods to be ready...
partitioned roll out complete: 3 new pods have been updated...

没有设置分区，rollout status 的结尾也写着 partitioned roll out complete，这只是 StatefulSet 版本的固定措辞，不用在意。

逐个创建：后一个等前一个 Ready

每个 Pod 的创建时间和变为 Ready 的时间：

kubectl -n notes-lab get pods -l app=web -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}created={.metadata.creationTimestamp}{"\t"}ready={.status.conditions[?(@.type=="Ready")].lastTransitionTime}{"\t"}{.spec.nodeName}{"\n"}{end}'
web-0	created=2026-10-12T04:54:38Z	ready=2026-10-12T04:56:09Z	worker
web-1	created=2026-10-12T04:56:09Z	ready=2026-10-12T04:56:32Z	worker2
web-2	created=2026-10-12T04:56:32Z	ready=2026-10-12T04:57:24Z	worker

web-1 的创建时间和 web-0 变成 Ready 是同一秒，web-2 和 web-1 也一样。这就是默认的 podManagementPolicy: OrderedReady：序号 N 的 Pod 要等 0 到 N-1 全部 Running 且 Ready 之后才会创建。三副本一共花了 2 分 46 秒。

时间花在哪，看事件（节选 web-0 那一段）：

kubectl -n notes-lab get events --sort-by=.lastTimestamp \
  -o custom-columns=TIME:.lastTimestamp,OBJ:.involvedObject.name,REASON:.reason,MSG:.message
TIME                   OBJ          REASON                  MSG
2026-10-12T04:54:38Z   web          SuccessfulCreate        create Claim data-web-0 Pod web-0 in StatefulSet web success
2026-10-12T04:54:40Z   web          SuccessfulCreate        create Pod web-0 in StatefulSet web successful
2026-10-12T04:54:40Z   data-web-0   WaitForPodScheduled     waiting for pod web-0 to be scheduled
2026-10-12T04:54:46Z   data-web-0   Provisioning            External provisioner is provisioning volume for claim "notes-lab/data-web-0"
2026-10-12T04:55:54Z   data-web-0   ProvisioningSucceeded   Successfully provisioned volume pvc-516b640d-d3a2-499c-abac-63e77039d820
2026-10-12T04:55:56Z   web-0        Scheduled               Successfully assigned notes-lab/web-0 to worker
2026-10-12T04:56:01Z   web-0        Pulled                  Container image "nginx:alpine" already present on machine
2026-10-12T04:56:03Z   web-0        Started                 Started container nginx

几个值得注意的地方：

  • PVC 比 Pod 先创建。 控制器先建 data-web-0，再建 web-0。PVC 名字的规则是「模板名-Pod 名」，所以是 data-web-0，不是两个 Pod 共用一个 data。
  • 大头是卷的供给。 从 Provisioning 到 ProvisioningSucceeded 用了 68 秒，镜像已经在节点上，容器启动只用了几秒。local-path 供给卷的方式是在目标节点上起一个 helper Pod 去建目录，local-path-storage 里的事件显示这个 helper Pod 从镜像就绪到容器创建隔了四十多秒。为什么这么慢这次没有深挖，推测和同一时段集群里还有其他实验在建 Pod 有关；web-1 的同一段只用了 12 秒。
  • Scheduled 晚于 ProvisioningSucceeded。 在 WaitForFirstConsumer 模式下，调度器先给 Pod 选好节点，provisioner 再在那个节点上建卷，所以 PVC 的第一条事件是 WaitForPodScheduled。

下文的时间线都用下面这个 watch.sh 记录：每秒查一次 Pod，只在状态变化时打印一行，terminating 表示 Pod 已经带上了 deletionTimestamp。用法是 L=web bash watch.sh 60（标签值、持续秒数）：

L=${L:-web}; prev=""
end=$(( $(date +%s) + $1 ))
while [ $(date +%s) -lt $end ]; do
  cur=$(kubectl -n notes-lab get pods -l app=$L --no-headers -o custom-columns=N:.metadata.name,R:.status.containerStatuses[0].ready,DEL:.metadata.deletionTimestamp 2>/dev/null | awk '{d=($3=="<none>")?"":" terminating"; printf "%s(ready=%s%s) ", $1,$2,d}')
  [ "$cur" != "$prev" ] && echo "$(date -u +%T) $cur" && prev="$cur"
  sleep 1
done

换成 Parallel

想把现有的 web 改成并行，直接被拒绝：

kubectl -n notes-lab patch sts web -p '{"spec":{"podManagementPolicy":"Parallel"}}'
The StatefulSet "web" is invalid: spec: Forbidden: updates to statefulset spec for fields other than 'replicas', 'ordinals', 'template', 'updateStrategy', 'persistentVolumeClaimRetentionPolicy' and 'minReadySeconds' are forbidden

podManagementPolicy、serviceName、volumeClaimTemplates 都不在这个白名单里，建好之后改不了，只能删掉 StatefulSet 重建（PVC 默认会留下，见后文）。所以复制同一份清单另建一个 par：Service 名、StatefulSet 名、serviceName、选择器和 Pod 标签里的 web 全部换成 par，再加上 podManagementPolicy: Parallel，其余不变：

sed -e 's/name: web$/name: par/' -e 's/app: web/app: par/' -e 's/serviceName: web/serviceName: par/' \
  -e 's/^  replicas: 3/  replicas: 3\n  podManagementPolicy: Parallel/' web.yaml > par.yaml
kubectl -n notes-lab apply -f par.yaml
L=par bash watch.sh 100

改完后 StatefulSet 头部是这样：

metadata:
  name: par
spec:
  serviceName: par
  replicas: 3
  podManagementPolicy: Parallel
  selector:
    matchLabels:
      app: par

为了把同时运行的 Pod 控制在 6 个以内，这一步之前先把 web 缩到了 1。

05:05:38 par-0(ready=<none>) par-1(ready=<none>) par-2(ready=false)
05:05:39 par-0(ready=false) par-1(ready=false) par-2(ready=false)
05:05:48 par-0(ready=true) par-1(ready=false) par-2(ready=true)
05:05:50 par-0(ready=true) par-1(ready=true) par-2(ready=true)
par-0	created=2026-10-12T05:05:04Z	ready=2026-10-12T05:05:46Z	worker2
par-1	created=2026-10-12T05:05:04Z	ready=2026-10-12T05:05:49Z	worker

三个 Pod 同一秒创建，三块卷同时供给，45 秒全部就绪，而 OrderedReady 用了 2 分 46 秒。就绪顺序是 par-0、par-2、par-1，不再按序号。Parallel 只影响扩缩容时的创建和删除；名字、PVC、DNS 这些身份保证不变。应用如果要求 0 号先起来当主节点，再让其他副本加入，就不能用它。

倒序终止

把 web 从 3 缩到 1：

kubectl -n notes-lab scale sts web --replicas=1
05:02:02
statefulset.apps/web scaled
05:02:02 web-0(ready=true) web-1(ready=true) web-2(ready=true terminating)
05:02:09 web-0(ready=true) web-1(ready=true terminating)
05:02:16 web-0(ready=true)

序号大的先走，web-2 彻底消失后才开始删 web-1，每个间隔 7 秒左右。Parallel 的 par 缩到 0 则是同时删：

05:06:49
statefulset.apps/par scaled
05:06:49 par-0(ready=true) par-1(ready=true) par-2(ready=true terminating)
05:06:50 par-0(ready=true terminating) par-1(ready=true terminating) par-2(ready=true terminating)
05:06:57 par-0(ready=false terminating) par-1(ready=false terminating) par-2(ready=true terminating)
05:06:58 par-2(ready=false terminating)
05:06:59

另外，kubectl delete sts 直接删除 StatefulSet 时，官方文档说明不保证终止顺序；需要有序退出，应该先缩到 0 再删。

稳定的 DNS 名，不稳定的 IP

在同一个 namespace 起一个 busybox 当客户端：

kubectl -n notes-lab run dns --image=busybox:1.36 --restart=Never -- sleep 3600
kubectl -n notes-lab exec dns -- nslookup web
Name:	web.notes-lab.svc.cluster.local
Address: <web-0-ip>
Name:	web.notes-lab.svc.cluster.local
Address: <web-2-ip>
Name:	web.notes-lab.svc.cluster.local
Address: <web-1-ip>

这里节选了答案部分，原始输出前后还有几行 ** server can't find web.cluster.local: NXDOMAIN、web.svc.cluster.local、web.localdomain 之类的报错：不带点的 web 被逐个拼上搜索域去查，只有 web.notes-lab.svc.cluster.local 查到了。查 Service 名，返回的是三个 Pod 的 IP，没有虚拟 IP，这是 Headless Service 的行为。StatefulSet 额外给每个 Pod 一条 <pod 名>.<serviceName> 的记录。Pod 自己也知道这个完整域名：

$ kubectl -n notes-lab exec web-1 -- hostname
web-1
$ kubectl -n notes-lab exec web-1 -- hostname -f
web-1.web.notes-lab.svc.cluster.local
$ kubectl -n notes-lab exec dns -- wget -qO- http://web-1.web
web-1 first written 04:56:26

一个误导人的 nslookup 结果

但用 busybox 的 nslookup 查短名 web-0.web，结果很奇怪：

$ kubectl -n notes-lab exec dns -- nslookup web-0.web
Server:		<dns-ip>
Address:	<dns-ip>:53

Non-authoritative answer:
Name:	web-0.web
Address: 127.0.53.53

同一个 Pod 里 ping web-0.web 却解析到了正确的 Pod IP，而 nslookup web-0.web.notes-lab 返回 NXDOMAIN：

PING web-0.web (<web-0-ip>): 56 data bytes
64 bytes from <web-0-ip>: seq=0 ttl=63 time=0.032 ms
** server can't find web-0.web.notes-lab: NXDOMAIN

Pod 的 /etc/resolv.conf 是：

search notes-lab.svc.cluster.local svc.cluster.local cluster.local localdomain
nameserver <dns-ip>
options ndots:5

按 ndots:5，web-0.web 只有一个点，本该先拼搜索域。但 busybox 1.36 的 nslookup 自己实现了查询逻辑，源码 networking/nslookup.c 的 add_query_with_search() 里有一句 strchr(dname, '.')：名字里只要有点，就原样查询，完全不用搜索域，不管 ndots 是多少。web-0.web.notes-lab 同理，原样发出去自然是 NXDOMAIN。ping 走的是 C 库解析器，遵守 ndots，所以正常。

那 127.0.53.53 是谁给的？web-0.web 原样查询，CoreDNS 不负责这个后缀，转发给了上游。而 .web 是一个真实存在、已经委派的顶级域：

$ kubectl -n notes-lab exec dns -- nslookup -type=ns web.
Non-authoritative answer:
web	nameserver = ac1.nstld.com
web	nameserver = ac4.nstld.com
web	nameserver = ac2.nstld.com
web	nameserver = ac3.nstld.com
$ kubectl -n notes-lab exec dns -- nslookup -type=txt anything-123.web
Non-authoritative answer:
anything-123.web	text = "Your DNS configuration needs immediate attention see https://icann.org/namecollision"
$ kubectl -n notes-lab exec dns -- nslookup -type=a zzz-not-exist.web
Non-authoritative answer:
Name:	zzz-not-exist.web
Address: 127.0.53.53

这个顶级域目前处于 ICANN 名称冲突的「受控中断」阶段，任意名字都返回 127.0.53.53，TXT 记录提示去看 icann.org/namecollision。答案来自 .web 注册局的权威服务器，等这个顶级域正式启用后，结果可能会变成别的、甚至是公网上某台真实主机的地址。

所以真正的坑是：Service 名恰好和某个顶级域同名（web、app、dev 都是），客户端又用了一个绕过搜索域的解析器去查带点的短名，查询就漏到了公网 DNS，拿回一个看似有效的地址。排查时看到 127.0.53.53 就该想到这一点。查 StatefulSet 的 Pod 记录时，用完整域名最省事：

$ kubectl -n notes-lab exec dns -- nslookup web-0.web.notes-lab.svc.cluster.local
Name:	web-0.web.notes-lab.svc.cluster.local
Address: <web-0-ip>

更多 DNS 排查思路见 DNS 排查。

删除 Pod 后：名字和数据不变，IP 变了

先往 web-0 的卷里追加一行，记下 UID、IP 和节点：

$ kubectl -n notes-lab exec web-0 -- sh -c 'echo edited-by-hand >> /usr/share/nginx/html/index.html; cat /usr/share/nginx/html/index.html'
web-0 first written 04:56:03
edited-by-hand
NAME    UID                                    IP               NODE
web-0   0ac93e41-1c95-402e-9e15-4ca7b25a0850   <old-ip>         worker

然后删除它：

kubectl -n notes-lab delete pod web-0
kubectl -n notes-lab wait --for=condition=Ready pod/web-0 --timeout=120s
05:01:05
pod "web-0" deleted
pod/web-0 condition met
05:01:33
NAME    UID                                    IP               NODE
web-0   9852b1a3-f759-4ba5-9779-cb7910aa84ea   <new-ip>         worker
web-0 first written 04:56:03
edited-by-hand

UID 变了，说明是一个全新的 Pod 对象；名字没变，首次写入时间和手工追加的那一行都还在，说明挂回了同一个 data-web-0。Pod IP 换了一个，DNS 记录随之更新，再查 web-0.web.notes-lab.svc.cluster.local 得到的是新 IP。所以客户端应该连 DNS 名，而不是缓存 Pod IP。

新 Pod 的创建时间是 05:01:19，比删除命令晚了 14 秒：同名的旧 Pod 彻底终止后，控制器才会创建新的，同一时刻不会有两个 web-0。这里的 14 秒比缩容时每个 Pod 约 7 秒长，原因这次没有测，preStop 的 3 秒是算在 10 秒优雅终止期之内的。

local-path 卷把 Pod 钉在节点上

重建后的 web-0 回到了原来的 worker，这不是巧合。看 data-web-0 背后的 PV：

PV=$(kubectl -n notes-lab get pvc data-web-0 -o jsonpath='{.spec.volumeName}')
kubectl get pv $PV -o jsonpath='{.spec.persistentVolumeReclaimPolicy}{"\n"}{.spec.hostPath.path}{"\n"}{.spec.nodeAffinity}{"\n"}'
Delete
/var/local-path-provisioner/pvc-516b640d-d3a2-499c-abac-63e77039d820_notes-lab_data-web-0
{"required":{"nodeSelectorTerms":[{"matchExpressions":[{"key":"kubernetes.io/hostname","operator":"In","values":["worker"]}]}]}}

卷就是 worker 上的一个 hostPath 目录，PV 上带着 nodeAffinity，要求使用它的 Pod 必须在 worker 上。只要这个 PVC 在，web-0 就只能调度到 worker。节点挂了，Pod 也就起不来，数据不会跟着漂移。云盘类的 CSI 卷通常按可用区约束，不会绑死到某一台机器，这是 local-path 这类本地卷特有的限制。

故意让 Pod 去别的节点挂这块卷，看会报什么错。先把 web 缩到 1（data-web-2 留着，见下一节），再用一个指定 worker2 的 Pod 去挂 data-web-2，它的 PV 在 worker 上：

apiVersion: v1
kind: Pod
metadata:
  name: peek
spec:
  nodeSelector:
    kubernetes.io/hostname: worker2
  containers:
    - name: c
      image: busybox:1.36
      command: ["sh", "-c", "cat /data/index.html; sleep 3600"]
      volumeMounts:
        - name: d
          mountPath: /data
  volumes:
    - name: d
      persistentVolumeClaim:
        claimName: data-web-2
NAME   READY   STATUS    RESTARTS   AGE
peek   0/1     Pending   0          8s
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  8s    default-scheduler  0/3 nodes are available: 1 node(s) didn't match Pod's node affinity/selector. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

这条报错容易让人误判：它只提到 nodeSelector，没提卷，计数也对不上（3 个节点只解释了 1 个）。原因在调度器的 VolumeBinding 插件：从 v1.27 起（PR #109877），它在 PreFilter 阶段就按已绑定本地 PV 的 nodeAffinity 把候选节点缩成 worker 一个，worker 又不满足 nodeSelector，于是报错里只剩这一条原因。这个优化后来因为节点 hostname 标签和节点名不一致时会调度错误而被撤回（PR #125398 进了 v1.32.0，回移到 v1.31.3），所以在更新的版本上，同样的场景应该会看到逐个节点的原因，包括 volume node affinity conflict；本文只在 v1.31.0 上实测过。实际排查时，看到 Pending 的 Pod 带着 PVC，就去查对应 PV 的 nodeAffinity，和 Pod 的节点约束对一下。

去掉 nodeSelector 重新提交，Pod 被调度到 worker，读到的是 web-2 当初写的内容：

NAME   NODE
peek   worker
web-2 first written 04:57:18

上面缩容到 1 之后，PVC 一个没少：

再扩回 3。PVC 都还在，不需要再供给，两个 Pod 16 秒就全部就绪，比首次创建快得多：

05:04:02 web-0(ready=true) web-1(ready=<none>)
05:04:03 web-0(ready=true) web-1(ready=false)

web-1 和 web-2 读到的仍是最初写入的内容：

web-1 first written 04:56:26
web-2 first written 04:57:18

这由 persistentVolumeClaimRetentionPolicy 决定。没写这个字段，API Server 会填上默认值：

kubectl -n notes-lab get sts web -o jsonpath='{.spec.podManagementPolicy} {.spec.persistentVolumeClaimRetentionPolicy} {.spec.updateStrategy}{"\n"}'
OrderedReady {"whenDeleted":"Retain","whenScaled":"Retain"} {"rollingUpdate":{"partition":0},"type":"RollingUpdate"}
  • whenScaled: Retain：缩容时保留被缩掉序号的 PVC，下次扩容原样挂回。
  • whenDeleted: Retain：删除 StatefulSet 时保留全部 PVC。

把 whenScaled 改成 Delete（这个字段在白名单里，可以直接改），再从 3 缩到 2：

kubectl -n notes-lab patch sts web -p '{"spec":{"persistentVolumeClaimRetentionPolicy":{"whenScaled":"Delete"}}}'
kubectl -n notes-lab scale sts web --replicas=2
kubectl -n notes-lab get pvc
NAME         STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
data-web-0   Bound    pvc-516b640d-d3a2-499c-abac-63e77039d820   16Mi       RWO            standard       <unset>                 18m
data-web-1   Bound    pvc-fb584ed9-5977-434b-b748-c0d17c91b150   16Mi       RWO            standard       <unset>                 16m

data-web-2 跟着 web-2 一起被删掉了。它背后的 PV 先变成 Released，因为 StorageClass 的回收策略是 Delete，两分钟内再查，PV 已经不存在，按 local-path 的做法节点上的目录也会被 provisioner 删掉，数据就没了：

NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM                  STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pvc-aac63eeb-a577-43a9-bccd-c6a77d6a6af2   16Mi       RWO            Delete           Released   notes-lab/data-web-2   standard       <unset>                          15m
Error from server (NotFound): persistentvolumes "pvc-aac63eeb-a577-43a9-bccd-c6a77d6a6af2" not found

按官方文档，whenScaled: Delete 只在缩容时生效，平时删 Pod 重建不会删 PVC；控制器做法是先把要缩掉的 PVC 的 owner 设成对应 Pod，等 Pod 删完再由垃圾回收删 PVC。保留默认值更安全：缩容是常见操作，误缩一次就丢数据的代价太高。这个字段 1.27 起为 beta 并默认开启，1.32 GA，本集群 v1.31 上已经可用。

最后用 kubectl delete sts web 删除 StatefulSet，whenDeleted 仍是 Retain，data-web-0、data-web-1 都还在，需要手工删。

坏更新卡住，回滚也解不开

更新策略默认是 RollingUpdate，从序号最大的 Pod 开始，一次一个，等更新后的 Pod Running 且 Ready，再更新前一个。把就绪探针的路径改成一个 nginx 不存在的 /healthz，模拟一个起不来的新版本：

kubectl -n notes-lab patch sts web --type=json \
  -p '[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/healthz"}]'
05:07:46
statefulset.apps/web patched
05:07:46 web-0(ready=true) web-1(ready=true) web-2(ready=true terminating)
05:07:53 web-0(ready=true) web-1(ready=true) web-2(ready=false terminating)
05:07:54 web-0(ready=true) web-1(ready=true) web-2(ready=false)

之后 70 秒没有任何变化。一分多钟后看状态：

$ kubectl -n notes-lab rollout status sts/web --timeout=20s
Waiting for 1 pods to be ready...
error: timed out waiting for the condition
NAME    READY   STATUS    RESTARTS   AGE    CONTROLLER-REVISION-HASH
web-0   1/1     Running   0          8m8s   web-6f6c986dc4
web-1   1/1     Running   0          2m4s   web-6f6c986dc4
web-2   0/1     Running   0          94s    web-65d45dc8b
current=web-6f6c986dc4 update=web-65d45dc8b ready=2 updated=1
  Warning  Unhealthy  43s (x22 over 85s)  kubelet            Readiness probe failed: HTTP probe failed with statuscode: 404

只有 web-2 换成了新版本（controller-revision-hash 不同），它一直不 Ready，web-1 和 web-0 就一直不动。这是好事：坏版本只影响了一个副本。判断卡在哪里，看三样东西：currentRevision 和 updateRevision 不同说明更新没完成；各 Pod 的 controller-revision-hash 标签说明谁已经换了；不 Ready 的那个 Pod 的事件说明为什么。

直觉上回滚模板就行：

kubectl -n notes-lab rollout undo sts/web
05:09:31
statefulset.apps/web rolled back
05:09:32 web-0(ready=true) web-1(ready=true) web-2(ready=false)
NAME    READY   STATUS    RESTARTS   AGE     CONTROLLER-REVISION-HASH
web-0   1/1     Running   0          8m53s   web-6f6c986dc4
web-1   1/1     Running   0          2m49s   web-6f6c986dc4
web-2   0/1     Running   0          2m19s   web-65d45dc8b
current=web-6f6c986dc4 update=web-6f6c986dc4

updateRevision 已经回到旧版本，可 web-2 还是坏的那个版本，40 多秒后仍然没被替换。官方文档把这种情况叫 Forced rollback，原因是一个已知问题（kubernetes#67250）：在 OrderedReady 下，控制器会一直等这个坏 Pod 变成 Ready（永远不会），然后才去把它改回正确配置。解决办法是回滚模板之后，手工删掉已经用坏配置跑起来的 Pod：

05:10:17
pod "web-2" deleted
05:10:17 web-0(ready=true) web-1(ready=true) web-2(ready=false terminating)
05:10:26 web-0(ready=true) web-1(ready=true) web-2(ready=false)
05:10:35 web-0(ready=true) web-1(ready=true) web-2(ready=true)
NAME    READY   STATUS    RESTARTS   AGE     CONTROLLER-REVISION-HASH

web-1   1/1     Running   0          3m24s   web-6f6c986dc4
web-2   1/1     Running   0          22s     web-6f6c986dc4

顺带一提，改坏探针之前，ControllerRevision 只有一份，序号是 1：

NAME             CONTROLLER             REVISION   AGE
web-6f6c986dc4   statefulset.apps/web   1          13m

回滚之后，同一个 web-6f6c986dc4 的序号变成了 3，undo 并不新建一份修订，而是把旧修订的序号往上提：

web-65d45dc8b    statefulset.apps/web   2          2m31s
web-6f6c986dc4   statefulset.apps/web   3          15m

分区滚动更新

rollingUpdate.partition 设为 N 时，只有序号大于等于 N 的 Pod 会更新。设 partition: 2，再给模板加一个环境变量当作新版本：

kubectl -n notes-lab patch sts web -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":2}}}}'
kubectl -n notes-lab set env sts/web VERSION=v2

05:11:03 web-0(ready=true) web-1(ready=true)

05:11:13 web-0(ready=true) web-1(ready=true) web-2(ready=true)

只有 web-2 拿到了 VERSION=v2，rollout status 也认为这次分区更新已经完成。这就是金丝雀：先让一个副本跑新版本，观察没问题再放开。

分区以下的 Pod 被删掉会怎样？删除 web-0：

常见坑：serviceName 指向的 Service 不存在

serviceName 只是一个名字，StatefulSet 不会帮你创建这个 Service，也不检查它是否存在。建一个 serviceName: db-headless 但没有对应 Service 的 StatefulSet：

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db-headless
  replicas: 1
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
        - name: c
          image: busybox:1.36
          command: ["sleep", "3600"]
statefulset.apps/db created
pod/db-0 condition met
Error from server (NotFound): services "db-headless" not found
db-0.db-headless.notes-lab.svc.cluster.local
Server:		<dns-ip>
Address:	<dns-ip>:53

** server can't find db-0.db-headless.notes-lab.svc.cluster.local: NXDOMAIN

Pod 正常 Ready，hostname -f 也报出了完整域名，看起来一切正常，但别的 Pod 解析这个名字得到 NXDOMAIN。集群应用（比如按 db-0.db-headless 找主节点的副本）会在这里连不上。补上选择器为 app: db 的 Headless Service（kubectl create service 默认选择器是 app: <名称>，这里用 sed 改成 app: db），几秒后就能解析：

kubectl -n notes-lab create service clusterip db-headless --clusterip=None --tcp=80:80 -o yaml --dry-run=client \
  | sed 's/app: db-headless/app: db/' | kubectl -n notes-lab apply -f -
kubectl -n notes-lab get svc db-headless -o jsonpath='{.spec.selector}{"\n"}'
service/db-headless created
{"app":"db"}
Name:	db-0.db-headless.notes-lab.svc.cluster.local
Address: <db-0-ip>

还有一个相关的情况：Pod 不 Ready 时，它的 DNS 记录也没有。给 db 加一个永远失败的就绪探针，db-0 重建后：

kubectl -n notes-lab patch sts db --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/readinessProbe","value":{"exec":{"command":["false"]},"periodSeconds":2}}]'
kubectl -n notes-lab get endpointslice -l kubernetes.io/service-name=db-headless \
  -o jsonpath='{range .items[*].endpoints[*]}{.hostname} ready={.conditions.ready}{"\n"}{end}'
NAME   READY   STATUS    RESTARTS   AGE
db-0   0/1     Running   0          11s
** server can't find db-0.db-headless.notes-lab.svc.cluster.local: NXDOMAIN
db-0 ready=false

EndpointSlice 里有 db-0，但 ready=false，DNS 就不发布它的记录。有些集群软件需要在就绪之前先通过 DNS 互相发现（比如组建集群后才算就绪），这时可以给 Headless Service 设置 publishNotReadyAddresses: true：

kubectl -n notes-lab patch svc db-headless -p '{"spec":{"publishNotReadyAddresses":true}}'
Name:	db-0.db-headless.notes-lab.svc.cluster.local
Address: <db-0-ip>

代价是客户端可能连到还没准备好的副本，最好只给集群内部互相发现用的那个 Service 打开，对外提供服务的 Service 保持默认。
