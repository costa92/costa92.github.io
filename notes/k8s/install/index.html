用 kubeadm 引导集群

kubeadm 只负责把一台已经装好容器运行时和 kubelet 的机器变成控制平面或工作节点：生成证书、写静态 Pod 清单、签发令牌、让新节点完成 TLS 引导。容器运行时、软件包、CNI 插件、负载均衡入口都不归它管。日常练习用本地实验环境就够了，这一篇专门看 kubeadm 本身做了什么。

实验没有用真实虚拟机，而是用一个一控一工的 kind 集群（node 镜像 kindest/node:v1.31.0，kubeadm v1.31.0，containerd 1.7.18）当作两台「主机」：kind 的节点容器里已经装好了 containerd、kubelet 和 kubeadm，kind 创建集群时自己就是调用 kubeadm init 和 kubeadm join。我在这个基础上把工作节点 kubeadm reset 掉，再手工预检、手工加入。节点里的命令是通过 docker exec 进容器执行的，下文省掉了这个前缀；节点名简化为 control-plane、worker，节点 IP 用 <cp-ip>、<worker-ip> 代替，令牌用 <token> 代替（kind 内置的 abcdef.0123456789abcdef 是公开的固定值，保留原样）。

注意
下文出现的 --discovery-token-unsafe-skip-ca-verification、kubelet 的 failSwapOn: false、--ignore-preflight-errors 跳过预检，都只是为了在 kind 容器里做实验，真实主机不要照抄。

真实主机上的安装步骤

未在本次实验中执行
这一节是给真实主机准备的完整流程。本次实验没有在宿主机上装包、执行 init，内容整理自 v1.31 版官方文档 Installing kubeadm、Container Runtimes、Creating a cluster with kubeadm，以及各 CNI 项目自己的文档。后面几节的实测会回过头验证其中一部分：预检查什么、join 怎么失败、没有 CNI 时什么样。

以 Debian/Ubuntu、containerd、Kubernetes v1.31 为例。下面的命令除特别说明外，每台节点都要执行。

1. 系统准备

每台机器的主机名、MAC 地址和 product_uuid（sudo cat /sys/class/dmi/id/product_uuid）必须唯一，克隆出来的虚拟机尤其要检查。

关闭 swap（kubelet 默认检测到 swap 就拒绝启动），并注释掉 /etc/fstab 里的 swap 行，让它重启后也不会回来：

sudo swapoff -a
sudo sed -i '/\sswap\s/ s/^/#/' /etc/fstab
swapon --show   # 没有输出说明已关闭

Ubuntu 默认装出来的 swap 通常就是 fstab 里的 /swap.img 这一行。有些系统的 swap 不在 fstab 里，而是由 systemd 的 swap 单元（systemctl list-units --type swap 能看到）或 zram 之类的服务启用，这种要把对应单元 mask 掉，否则重启后又会回来。

也可以保留 swap，在 kubelet 配置里写 failSwapOn: false。NodeSwap 特性 1.28 进入 beta，从 1.30 起默认开启；但默认的 swapBehavior: NoSwap 仍然不让工作负载用 swap，真要让 Pod 用，要把它设成 LimitedSwap，而且只支持 cgroup v2。

打开 IPv4 转发并立即生效：

cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.ipv4.ip_forward = 1
EOF
sudo sysctl --system
sysctl net.ipv4.ip_forward

旧教程里的 modprobe br_netfilter 加 net.bridge.bridge-nf-call-iptables = 1，v1.31 的 Container Runtimes 文档已经不再列出，kubeadm 从 v1.30 起也不在预检里检查（见下文）。但这不等于都不需要了：Flannel 的 README 明确写着它需要 br_netfilter 模块才能正常启动，而 kubeadm 从 1.30 起不再检查这个模块。用 Flannel 这类网桥型 CNI 时，按 v1.29 版 Container Runtimes 文档的写法加上模块和 sysctl，并写进 /etc/modules-load.d/，让模块开机自动加载：

cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay
sudo modprobe br_netfilter

cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system

其他 CNI 需不需要，看它自己的文档。

节点之间要放行这些端口（见 Ports and Protocols）：

节点端口用途
控制平面6443/tcpAPI Server，所有节点和客户端都要能访问
控制平面2379-2380/tcpetcd
控制平面10259/tcp、10257/tcpscheduler、controller-manager，只需本机访问
所有节点10250/tcpkubelet API，控制平面要能访问
工作节点10256/tcpkube-proxy
工作节点30000-32767/tcpNodePort Service

CNI 还有自己的端口，比如 Flannel 默认的 VXLAN 后端走 8472/udp，同样要在节点之间放行。

2. 安装 containerd

可以用发行版自带的包（Debian/Ubuntu 上 sudo apt-get install -y containerd），也可以按 Docker 文档配好它的 apt 源，装 containerd.io 包。按 containerd 文档，containerd.io 包里带了 runc，但不带 CNI 插件。

装好后生成默认配置：

sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml

把 runc 的 cgroup 驱动改成 systemd。kubeadm 从 v1.22 起在未指定时默认给 kubelet 配 systemd，而文档要求容器运行时和 kubelet 的 cgroup 驱动一致，否则 kubelet 会失败。

config default 生成的文件里已经有 SystemdCgroup = false 这一行，要做的是把它改成 true，不要把下面的 TOML 段整段追加到文件末尾，那样同一个表头会出现两次，按 TOML 规范这是不合法的配置：

sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
grep -n SystemdCgroup /etc/containerd/config.toml   # 应该只看到一行 SystemdCgroup = true

这一行所在的表头随 containerd 大版本不同，用来核对改的位置对不对：

# containerd 1.x
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
  SystemdCgroup = true

# containerd 2.x
[plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.runc.options]
  SystemdCgroup = true

如果没有重新生成配置，而是保留了包自带的 config.toml（典型是 Docker 源的 containerd.io），要确认 cri 不在 disabled_plugins 里。改完重启：

sudo systemctl restart containerd

配置里还指定了 pause 镜像。kubeadm v1.31 默认用 registry.k8s.io/pause:3.10，按 v1.31 的 kubeadm 源码，两者不一致时它会在预检的拉镜像阶段打一条警告：detected that the sandbox image ... of the container runtime is inconsistent with that used by kubeadm。按提示改成同一个版本，再重启 containerd。键名同样随大版本不同：

# containerd 1.x
[plugins."io.containerd.grpc.v1.cri"]
  sandbox_image = "registry.k8s.io/pause:3.10"

# containerd 2.x
[plugins.'io.containerd.cri.v1.images'.pinned_images]
  sandbox = 'registry.k8s.io/pause:3.10'

3. 安装 kubeadm、kubelet、kubectl

网上很多教程还在用 apt.kubernetes.io、yum.kubernetes.io（或者 packages.cloud.google.com 下的 kubernetes-el7-x86_64）。官方文档写明这两个旧仓库从 2023 年 9 月 13 日起已经废弃并冻结，之后发布的版本只能从 pkgs.k8s.io 安装；按冻结公告后来补充的时间线，旧仓库已在 2024 年 3 月 4 日移除，现在照旧教程配源根本装不上。新仓库还有一个容易忽略的变化：每个小版本一个仓库，URL 里带着小版本号，装 v1.31 就只能拿到 1.31.x：

sudo apt-get update
sudo apt-get install -y apt-transport-https ca-certificates curl gpg
sudo mkdir -p -m 755 /etc/apt/keyrings
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.31/deb/Release.key \
  | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.31/deb/ /' \
  | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
sudo systemctl enable --now kubelet

kubelet 这时会每隔几秒重启一次，因为它在等 kubeadm init 或 join 生成配置，属于正常现象。

apt-mark hold 防止日常 apt upgrade 把 kubelet 顺手升到别的版本，升级要走 kubeadm upgrade 的流程。想升到下一个小版本时，要先改 kubernetes.list 里的 v1.31，否则 apt 根本看不到新版本。RHEL 系的 .repo 文件同理：baseurl=https://pkgs.k8s.io/core:/stable:/v1.31/rpm/，并用 exclude=kubelet kubeadm kubectl cri-tools kubernetes-cni 把这几个包排除在系统升级之外，安装时加 --disableexcludes=kubernetes。旧教程里关闭 gpgcheck、固定一个早已过期的小版本，都不该照抄。

4. 初始化控制平面（只在第一台控制平面执行）

先选好 CNI，再按它的要求定 Pod 网段：

sudo kubeadm init --pod-network-cidr=<CNI 要求的网段> \
  [--control-plane-endpoint=<名字或 VIP>:6443] \
  [--kubernetes-version=v1.31.0]
  • --pod-network-cidr：用 Flannel 时填 10.244.0.0/16。Pod 网段不能和宿主机所在的任何网段重叠，文档原话是重叠就很可能出问题。
  • --control-plane-endpoint：将来要扩成多控制平面，现在就带上，指向一个 DNS 名或负载均衡 VIP；不带它初始化的单控制平面集群，文档说明事后改成高可用不受 kubeadm 支持。细节见高可用。
  • --kubernetes-version：可选，不写时 kubeadm 会联网查稳定版本（下文实测能看到这一步）。

init 成功后，按输出的提示给普通用户配置 kubectl：

mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

如果是 root 用户，也可以直接：

export KUBECONFIG=/etc/kubernetes/admin.conf

admin.conf 带的是集群管理员证书，不要分发给别人；init 还会生成权限更高的 super-admin.conf，文档建议把它移到安全的位置保存。

5. 安装 CNI

下文实验里用的 kindnet 是 kind 自带的，只在 kind 里有，真实集群要自己选。两个常见的选择：

  • Flannel：默认 Pod 网段 10.244.0.0/16，和上面的 --pod-network-cidr 对应。按 Flannel README 安装：kubectl apply -f https://github.com/flannel-io/flannel/releases/latest/download/kube-flannel.yml；网段不是 10.244.0.0/16 时，要先下载清单改掉其中的网段。

  • Calico：按 Calico Quickstart 用 Tigera operator 安装，分两步，<version> 换成页面上当前的版本号：

    kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/<version>/manifests/tigera-operator.yaml
curl -LO https://raw.githubusercontent.com/projectcalico/calico/<version>/manifests/custom-resources.yaml
# 按需修改其中的 cidr 后
kubectl create -f custom-resources.yaml

    custom-resources.yaml 里的默认 IP 池是 192.168.0.0/16，很容易和办公室或家用局域网重叠。重叠时把 init 的 --pod-network-cidr 和这个文件里的 cidr 改成同一个不冲突的网段，再执行最后一步。

一个集群只装一种 Pod 网络插件。装完等 CoreDNS 变成 Running，再去加工作节点。

6. 加入工作节点

先确认工作节点能访问控制平面的 6443、控制平面能访问工作节点的 10250，CNI 的端口也已放行，然后在工作节点执行 init 输出的那条命令：

sudo kubeadm join <控制平面地址>:6443 --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash>

令牌默认 24 小时过期，过期后在控制平面用 kubeadm token create --print-join-command 重新生成。最后在控制平面 kubectl get nodes 确认节点 Ready。

kind 给 kubeadm 传了什么

kind 把渲染好的配置放在节点的 /kind/kubeadm.conf。控制平面节点上的内容（删掉了 provider-id 等无关行）：

cat /kind/kubeadm.conf
apiServer:
  certSANs:
  - localhost
  - 127.0.0.1
  extraArgs:
    runtime-config: ""
apiVersion: kubeadm.k8s.io/v1beta3
clusterName: notes-lab-install
controlPlaneEndpoint: control-plane:6443
...
kind: ClusterConfiguration
kubernetesVersion: v1.31.0
networking:
  podSubnet: 10.244.0.0/16
  serviceSubnet: 10.96.0.0/16
---
apiVersion: kubeadm.k8s.io/v1beta3
bootstrapTokens:
- token: abcdef.0123456789abcdef
kind: InitConfiguration
localAPIEndpoint:
  advertiseAddress: <cp-ip>
  bindPort: 6443
nodeRegistration:
  criSocket: unix:///run/containerd/containerd.sock
...
skipPhases:
- preflight
---
...

  bootstrapToken:
    apiServerEndpoint: control-plane:6443
    token: abcdef.0123456789abcdef
    unsafeSkipCAVerification: true

...

- preflight
---

cgroupRoot: /kubelet
...

...

和 kubeadm config print init-defaults 打印的默认值对比：

apiVersion: kubeadm.k8s.io/v1beta4
bootstrapTokens:
- groups:
  - system:bootstrappers:kubeadm:default-node-token
  token: abcdef.0123456789abcdef
  ttl: 24h0m0s
...
localAPIEndpoint:
  advertiseAddress: 1.2.3.4
  bindPort: 6443
nodeRegistration:
  criSocket: unix:///var/run/containerd/containerd.sock
...
timeouts:
  controlPlaneComponentHealthCheck: 4m0s
  discovery: 5m0s
...
caCertificateValidityPeriod: 87600h0m0s
certificateValidityPeriod: 8760h0m0s
...
kind: ClusterConfiguration
kubernetesVersion: 1.31.0
networking:
  dnsDomain: cluster.local
  serviceSubnet: 10.96.0.0/12

几处值得记住的差别：

  • kind 跳过了预检（skipPhases: [preflight]）。下面会看到容器里过不了内核配置检查，推测这是跳过它的主要原因。
  • kind 的 join 不校验 CA（unsafeSkipCAVerification: true），在本机容器网络里无所谓，真实环境应该用 --discovery-token-ca-cert-hash。
  • 默认不设 podSubnet。很多 CNI（比如 Flannel，以及这里的 kindnet）要求它，所以 kubeadm init 要不要带 --pod-network-cidr，取决于先选好的 CNI。默认 Service 网段是 /12，kind 改成了 /16。
  • kubelet 配了 failSwapOn: false。宿主机开着 2 GB swap，kubelet 仍然能起来，靠的就是这一行。
  • API 版本：v1.31 引入了 v1beta4，而这个节点上 kind 写的还是 v1beta3。拿这份配置跑 kubeadm 时会看到废弃提示：
W1013 09:37:41.972368    1643 common.go:101] your configuration file uses a deprecated API spec: "kubeadm.k8s.io/v1beta3" (kind: "ClusterConfiguration"). Please use 'kubeadm config migrate --old-config old.yaml --new-config new.yaml', which will write the new, similar spec using a newer API version.

默认值里的令牌 ttl: 24h0m0s、证书有效期一年（CA 十年），分别对应下文的令牌过期和证书管理。

预检：在重置后的节点上逐项触发

先把工作节点重置：

kubeadm reset -f

它打出的提示放到最后一节说。重置后在 worker 上跑一次控制平面的预检：

kubeadm init phase preflight
I1013 09:32:53.006695     707 version.go:261] remote version is much newer: v1.37.1; falling back to: stable-1.31
[preflight] Running pre-flight checks
	[WARNING Swap]: swap is supported for cgroup v2 only. The kubelet must be properly configured to use swap. Please refer to https://kubernetes.io/docs/concepts/architecture/nodes/#swap-memory, or disable swap on the node
	[WARNING FileExisting-socat]: socat not found in system path
[preflight] The system verification failed. Printing the output from the verification:
...
error execution phase preflight: [preflight] Some fatal errors occurred:
	[ERROR SystemVerification]: failed to parse kernel config: unable to load kernel module: "configs", output: "modprobe: FATAL: Module configs not found in directory /lib/modules/7.0.0-38-generic\n", err: exit status 1
[preflight] If you know what you are doing, you can make a check non-fatal with `--ignore-preflight-errors=...`

逐行看：

  • 第一行：没指定 --kubernetes-version 时，kubeadm 会联网查 stable 版本，发现远端已经是 v1.37.1，比自己新太多，于是退回 stable-1.31。离线环境或想固定版本时，kubeadm init 可以带 --kubernetes-version v1.31.0；但 kubeadm init phase preflight 不接受这个参数（实测报 unknown flag: --kubernetes-version），只能通过 --config 文件里的 kubernetesVersion 固定。
  • WARNING Swap：只是警告，因为 kubelet 是否容忍 swap 由它自己的配置决定，kubeadm 不拦。
  • WARNING FileExisting-socat：kubectl port-forward 依赖 socat，缺了只影响端口转发。
  • ERROR SystemVerification：容器里读不到宿主机的内核配置。这是 kind 环境特有的，也是 kind 跳过预检的原因；在真实主机上一般不会出现。后面除特别说明外，实验都加上 --ignore-preflight-errors=SystemVerification 把它降成警告。

ip_forward

把 worker 网络命名空间里的转发关掉（节点是容器，不影响宿主机），再预检一次。一开始我用的是 kubeadm join phase preflight control-plane:6443 ...，结果没有报错。查了 v1.31 的 kubeadm 源码 cmd/kubeadm/app/preflight/checks.go：join 时只有 API Server 地址是 IP 字面量，才会加上 IPv4 检查；写的是主机名就跳过。换成 IP（这一条没有加 --ignore-preflight-errors，所以 SystemVerification 也一起报成了错误）：

sysctl -w net.ipv4.ip_forward=0
kubeadm join phase preflight <cp-ip>:6443 --token abcdef.0123456789abcdef \
  --discovery-token-unsafe-skip-ca-verification
error execution phase preflight: [preflight] Some fatal errors occurred:
	[ERROR SystemVerification]: failed to parse kernel config: ...
	[ERROR FileContent--proc-sys-net-ipv4-ip_forward]: /proc/sys/net/ipv4/ip_forward contents are not set to 1

同样关掉转发后，kubeadm init phase preflight 也报了同一个 FileContent--proc-sys-net-ipv4-ip_forward。init 这边的条件宽得多：serviceSubnet、podSubnet 只要有一个是 IPv4 网段，或者 advertise 地址是 IPv4，就会加这项检查，默认配置下 init 基本总会检查 ip_forward。

具体的 sysctl 检查项写在 checks_linux.go 的 addIPv4Checks 里。对比 v1.29 和 v1.30 的源码，v1.29 还同时检查 /proc/sys/net/bridge/bridge-nf-call-iptables 和 ip_forward，v1.30 起只剩 ip_forward。所以在 v1.31 上用主机名 join 的节点，就算忘了开转发，预检也会放行，问题要等 Pod 网络不通时才暴露。

端口被占用

在正在运行的控制平面上跑预检，相当于「在一台已经装过的机器上再 init 一次」：

kubeadm init phase preflight --config /kind/kubeadm.conf --ignore-preflight-errors=SystemVerification
error execution phase preflight: [preflight] Some fatal errors occurred:
	[ERROR Port-6443]: Port 6443 is in use
	[ERROR Port-10259]: Port 10259 is in use
	[ERROR Port-10257]: Port 10257 is in use
	[ERROR FileAvailable--etc-kubernetes-manifests-kube-apiserver.yaml]: /etc/kubernetes/manifests/kube-apiserver.yaml already exists
	[ERROR FileAvailable--etc-kubernetes-manifests-kube-controller-manager.yaml]: /etc/kubernetes/manifests/kube-controller-manager.yaml already exists

容器运行时没起来

把 worker 上的 containerd 停掉，再跑 join 预检：

systemctl stop containerd
kubeadm join phase preflight <cp-ip>:6443 --token abcdef.0123456789abcdef \
  --discovery-token-unsafe-skip-ca-verification \
  --cri-socket unix:///run/containerd/containerd.sock --ignore-preflight-errors=SystemVerification
[preflight] Running pre-flight checks
W1013 09:37:50.861455    1234 checks.go:1080] [preflight] WARNING: Couldn't create the interface used for talking to the container runtime: failed to create new CRI runtime service: validate service connection: validate CRI v1 runtime API for endpoint "unix:///run/containerd/containerd.sock": rpc error: code = Unavailable desc = connection error: desc = "transport: Error while dialing: dial unix /run/containerd/containerd.sock: connect: no such file or directory"
	[WARNING Swap]: ...
	[WARNING FileExisting-socat]: socat not found in system path
...
[preflight] Reading configuration from the cluster...

出乎意料：运行时不可用在 v1.31 的预检里只是一条警告，预检继续往下走、开始读集群配置了，不带 --cri-socket 让它自动探测也一样。这一条混在一串 WARNING 里很容易被扫过去，这次没有让 join 真正跑下去，推测它会在后面等待 kubelet 健康检查的阶段失败。所以预检输出里的 Couldn't create the interface used for talking to the container runtime 要当成错误对待，先 systemctl status containerd，再用 crictl info 确认 CRI 插件可用。实验完把 containerd 重新启动。

加入节点：令牌和 CA 哈希

在控制平面生成一条新的 join 命令：

kubeadm token create --print-join-command
kubeadm join control-plane:6443 --token <token> --discovery-token-ca-cert-hash sha256:4129c298cd64d55c80d22312cac22660008870b7f1c295597e73655b1ced2538

--discovery-token-ca-cert-hash 是集群 CA 公钥的 SHA-256。节点第一次连 API Server 时还不信任它，只能匿名读 kube-public/cluster-info 这个 ConfigMap；令牌用来验证这份 ConfigMap 的签名（证明它来自持有令牌的集群），哈希用来钉住其中的 CA（证明没有被中间人换掉）。哈希也可以自己从 CA 证书算出来，和上面那条一致：

openssl x509 -pubkey -in /etc/kubernetes/pki/ca.crt \
  | openssl rsa -pubin -outform der 2>/dev/null \
  | openssl dgst -sha256 -hex | sed 's/^.* //'
4129c298cd64d55c80d22312cac22660008870b7f1c295597e73655b1ced2538

哈希写错

把哈希换成全 0：

error execution phase preflight: couldn't validate the identity of the API Server: cluster CA found in cluster-info ConfigMap is invalid: none of the public keys "sha256:4129c298cd64d55c80d22312cac22660008870b7f1c295597e73655b1ced2538" are pinned

立刻失败，错误里直接给出了集群 CA 的真实哈希。这在复制粘贴截断时很好用；但如果你不确定连的是不是自己的集群，不要把错误里的哈希抄回去重试，应该回控制平面重新算。

令牌被删或已过期

先建一个令牌、马上删掉，再拿它 join：

kubeadm token create zzzzzz.0123456789abcdef --ttl 1m
kubeadm token delete zzzzzz
kubeadm join control-plane:6443 --token zzzzzz.0123456789abcdef \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --ignore-preflight-errors=SystemVerification --v=1
I1013 09:38:43.691083    1368 token.go:228] [discovery] Retrying due to error: could not find a JWS signature in the cluster-info ConfigMap for token ID "zzzzzz"
I1013 09:38:48.690968    1368 token.go:228] [discovery] Retrying due to error: could not find a JWS signature in the cluster-info ConfigMap for token ID "zzzzzz"
I1013 09:38:53.714178    1368 token.go:228] [discovery] Retrying due to error: could not find a JWS signature in the cluster-info ConfigMap for token ID "zzzzzz"

每 5 秒重试一次，并不立刻失败。cluster-info 里按令牌 ID 存着签名，键名是 jws-kubeconfig-<令牌 ID>，令牌没了签名也就没了。

过期的令牌也一样。建一个 --ttl 1m 的令牌 yyyyyy，09:41:05 到期；09:41:22 再看，kubeadm token list 里已经没有它，对应的 Secret 也被删了，cluster-info 里的签名只剩两个：

Error from server (NotFound): secrets "bootstrap-token-yyyyyy" not found

"jws-kubeconfig-abcdef
"jws-kubeconfig-<id>

麻烦的是不加 --v=1 时这段重试什么都不打印，命令会一直安静地等到发现超时。默认超时是 5 分钟（源码里的 DiscoveryTimeout 常量），本次没有等满。为了看到最终报错，我写了一份 v1beta4 的 JoinConfiguration，把 timeouts.discovery 改成 30 秒：

apiVersion: kubeadm.k8s.io/v1beta4
kind: JoinConfiguration
discovery:
  bootstrapToken:
    apiServerEndpoint: control-plane:6443
    token: yyyyyy.0123456789abcdef
    caCertHashes:
    - sha256:4129c298cd64d55c80d22312cac22660008870b7f1c295597e73655b1ced2538
timeouts:
  discovery: 30s

这时 worker 已经加入了集群，完整的 join 会先因为文件已存在而失败，所以只跑预检阶段，并用 --ignore-preflight-errors=all 放过这些错误：

kubeadm join phase preflight --config join-expired.yaml --ignore-preflight-errors=all

30 秒后报错：

error execution phase preflight: couldn't validate the identity of the API Server: failed to request the cluster-info ConfigMap: client rate limiter Wait returned an error: context deadline exceeded

最终报错只说超时，完全没提令牌。看到 join 卡在 Reading configuration from the cluster 之前或报这条错，先在控制平面 kubeadm token list 确认令牌还在；令牌默认 24 小时过期，隔天再加节点就要重新 token create。

没有 CNI 时

这个集群创建时加了 networking.disableDefaultCNI: true，kind 不装它默认的 kindnet。kubeadm 跑完，两个节点都是 NotReady：

原因写在节点的 Ready 条件里：

cni plugin not initialized 的意思是 containerd 在 /etc/cni/net.d 里找不到网络配置。此时 kube-system 里的 Pod 分成了两类：

NAME                                       READY   STATUS              RESTARTS   AGE   IP         NODE
coredns-6f6b679f8f-698r6                   0/1     Pending             0          13s   <none>     <none>

控制平面组件和 kube-proxy 都用宿主机网络，不需要 CNI，所以能跑；CoreDNS 需要 Pod 网络，一直 Pending。它甚至没被调度，原因是节点 NotReady 期间带着 node.kubernetes.io/not-ready:NoSchedule 污点：

Warning  FailedScheduling  13s   default-scheduler  0/1 nodes are available: 1 node(s) had untolerated taint {node.kubernetes.io/not-ready: }. preemption: 0/1 nodes are available: 1 Preemption is not helpful for scheduling.

kind 的 node 镜像里自带 kindnet 的清单 /kind/manifests/default-cni.yaml 和镜像 docker.io/kindest/kindnetd:v20241108-5c6d2daf，不用联网拉取。清单里 POD_SUBNET 的值是模板占位符 {{ .PodSubnet }}，替换成 10.244.0.0/16 后 apply：

clusterrole.rbac.authorization.k8s.io/kindnet created
clusterrolebinding.rbac.authorization.k8s.io/kindnet created
serviceaccount/kindnet created
daemonset.apps/kindnet created

	"plugins": [
	{

kubeadm reset 留下了什么

开头第一次 reset worker 时，没有先 drain，也没有删节点对象。输出里有一条警告：

W1013 09:32:43.802491     577 cleanupnode.go:105] [reset] Failed to remove containers: failed to stop running pod 23954f4726027f0bb2e41522be9280d47774f6d0084a4ffef48d795b442d5766: rpc error: code = DeadlineExceeded desc = failed to stop sandbox container "23954f4726027f0bb2e41522be9280d47774f6d0084a4ffef48d795b442d5766" in "SANDBOX_READY" state: wait sandbox container "23954f4726027f0bb2e41522be9280d47774f6d0084a4ffef48d795b442d5766": context deadline exceeded

reset 之后 crictl ps -a 里还剩一个已退出的 kube-proxy 容器。当时宿主机资源很紧：节点里看到的 swap（与宿主机共用）2 GB 几乎用满，09:34 前后 kubectl 访问 API Server 还出现过 connection reset by peer。推测停沙箱超时与此有关。更值得注意的是 API 里的 Node 对象还在：

NAME            STATUS     ROLES           AGE   VERSION
control-plane   NotReady   control-plane   66s   v1.31.0
worker          NotReady   <none>          44s   v1.31.0

reset 只清本机，不会通知集群。后来手工 join 时，worker 直接沿用了这个旧 Node 对象（AGE 是 8 分钟而不是几秒）。

官方文档 Remove the node 一节给的顺序是：drain → 在节点上 kubeadm reset → 手工清 iptables/IPVS → kubectl delete node。第二次实验我把 delete node 提前到了 reset 之前，这是我自己调整的顺序，不是文档的写法：

kubectl drain worker --delete-emptydir-data --ignore-daemonsets
kubectl delete node worker
kubeadm reset -f

这次 reset 没有警告，容器也清干净了。不过两次 reset 的条件不止顺序一个变量，这个对比证明不了「改顺序」起了作用：第一次停沙箱超时，推测和当时资源紧张有关。

两次 reset 都会打这一段：

The reset process does not clean CNI configuration. To do so, you must remove /etc/cni/net.d

The reset process does not reset or clean up iptables rules or IPVS tables.
If you wish to reset iptables, you must do so manually by using the "iptables" command.

If your cluster was setup to utilize IPVS, run ipvsadm --clear (or similar)
to reset your system's IPVS tables.

The reset process does not clean your kubeconfig files and you must remove them manually.
Please, check the contents of the $HOME/.kube/config file.

逐项核对，确实都还在。iptables-save 里仍有 80 行带 KUBE 的规则，nat 表里的链一个不少，/etc/cni/net.d 下还是 kindnet 的配置：

:KUBE-MARK-MASQ - [0:0]
:KUBE-NODEPORTS - [0:0]
:KUBE-POSTROUTING - [0:0]

这些残留如果不清，这台机器换个 CNI 重新加入时，containerd 会先读到旧的 conflist，旧的 Service 规则也会继续把流量往不存在的 Pod 上转。按文档手工清掉（kindnet 的 IP 分配状态在 /run/cni-ipam-state，也一并删掉）：

  && iptables -t nat -X && iptables -t mangle -X
rm -rf /etc/cni/net.d/* /run/cni-ipam-state

之后 KUBE 规则数和 /etc/cni/net.d 下的文件数都是 0。用 IPVS 模式的 kube-proxy 还要 ipvsadm --clear。

kubeconfig 的残留在控制平面上看。实验里先复制了一份 admin.conf（容器里是 root，所以没用文档那三行里的 sudo cp -i 和 chown）：

mkdir -p $HOME/.kube && cp /etc/kubernetes/admin.conf $HOME/.kube/config

reset 控制平面之后，这个文件原样留着，里面还指向已经不存在的 API Server：

-rw------- 1 root root 5699 Oct 13 09:44 /root/.kube/config
...
    server: https://control-plane:6443
The connection to the server control-plane:6443 was refused - did you specify the right host or port?

这里还有一个小坑：在 kind 节点里直接跑 kubectl，报的却是 localhost:8080 连不上，因为 kind 的节点镜像设置了环境变量 KUBECONFIG=/etc/kubernetes/admin.conf，$HOME/.kube/config 根本没被读；reset 删掉 admin.conf 后，kubectl 找不到任何配置，就退回了默认的 localhost:8080。在真实主机上看到 localhost:8080，同样说明 kubectl 没读到 kubeconfig，先查 KUBECONFIG 和 $HOME/.kube/config。

admin.conf 是集群管理员凭据，只放在可信的管理机上；控制平面节点下线时，记得把复制出去的副本也删掉。

小结

  • 装包用 pkgs.k8s.io 的小版本仓库，apt-mark hold 锁版本；containerd 设 SystemdCgroup = true，开 ip_forward；Pod 网段按 CNI 定，且不能和宿主机网段重叠。
  • 预检的 WARNING 不全是小事：运行时不可用在 v1.31 只是警告；用主机名 join 时 ip_forward 根本不检查；bridge-nf-call-iptables 从 v1.30 起不再检查。
  • join 失败先分清是哈希（立刻报错，并给出真实哈希）还是令牌（默默重试，最后只报超时）。
  • 节点 NotReady 且信息里有 cni plugin not initialized，就是还没装 CNI；CoreDNS 会因 not-ready 污点停在 Pending。
  • 下线节点按文档的 drain → reset → 清 iptables/IPVS → delete node 的顺序，另外手工删 /etc/cni/net.d 和 kubeconfig。
