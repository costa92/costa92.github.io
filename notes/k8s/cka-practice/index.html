用本站笔记准备 CKA 实操

CKA 是在命令行里完成任务的实操考试。这一页做两件事：一是按官方大纲的领域把本站笔记排成一条练习路线；二是自己按考试的节奏做几道小题，看看时间到底花在哪里。题目都是自己出的，不来自任何真实考试题库。

当前大纲：v1.35

2026-10-13 查看了 cncf/curriculum 仓库：CKA 的大纲文件是 CKA_Curriculum_v1.35.pdf，最后一次提交是 2026-03-03（提交信息 CKA exam curriculum v1.35）。同一天 Linux Foundation 的 CKA 页面写的是：考试基于 Kubernetes v1.35，时长 2 小时，含一次重考和两次模拟器机会。

领域和权重（PDF 与 LF 页面一致）：

权重领域大纲里的条目（摘要）
30%故障排查集群与节点、集群组件、资源使用监控、容器输出流、Service 与网络
25%集群架构、安装与配置RBAC、基础设施准备、kubeadm 建集群、集群生命周期、高可用控制平面、Helm 与 Kustomize、CNI/CSI/CRI 等扩展接口、CRD 与 Operator
20%服务与网络Pod 间连通性、NetworkPolicy、ClusterIP/NodePort/LoadBalancer 与 endpoints、Gateway API、Ingress、CoreDNS
15%工作负载与调度滚动更新与回滚、ConfigMap 与 Secret、工作负载自动扩缩容、自愈部署、Pod 准入与调度（limits、节点亲和等）
10%存储StorageClass 与动态供给、卷类型/访问模式/回收策略、PV 与 PVC

大纲每隔一段时间会随 Kubernetes 版本更新，报名前请以上面两个页面为准。考场的具体环境（终端、可查阅的文档范围、题目数量等）这里不做描述，以官方的考生手册为准。

下文的练习在一个三节点 kind 集群上完成（Kubernetes v1.31.0，比考试版本旧四个小版本；containerd 1.7.18，CNI 为 Calico，装了 metrics-server，默认 StorageClass 是 local-path），全部放在单独的 notes-lab namespace 里。节点名简化为 worker、worker2，IP 用 <pod-ip>、<cluster-ip> 代替。

八道限时小题

先说清楚耗时的含义：下面的耗时是从第一条命令到验证通过的墙钟时间，命令是事先想好的，故障也是我自己埋的，所以它反映的是 rollout、调度、拉起 Pod 这些「等待」占多少时间，不代表考场上读题加排查的时间。真正有参考价值的是每题里浪费时间的那一步。

为了少打字，下面的命令都假设已经定义了：

kc(){ kubectl -n notes-lab "$@"; }

题 1：建 Deployment 并暴露 Service，用 curl 验证（11 秒，绕开空输出又花了约 22 秒）

kc create deployment web --image=nginx:1.27 --replicas=2 --port=80
kc expose deployment web --port=80 --target-port=80
kc rollout status deployment/web --timeout=120s
kc get deploy,svc,endpointslice -o wide
NAME                  READY   UP-TO-DATE   AVAILABLE   AGE   CONTAINERS   IMAGES       SELECTOR
deployment.apps/web   2/2     2            2           3s    nginx        nginx:1.27   app=web

NAME          TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE   SELECTOR
service/web   ClusterIP   <cluster-ip>    <none>        80/TCP    3s    app=web

NAME                                       ADDRESSTYPE   PORTS   ENDPOINTS             AGE
endpointslice.discovery.k8s.io/web-875x2   IPv4          80      <pod-ip>,<pod-ip>     3s

建好并 rollout 完成只用了约 3 秒。然后用一个临时 Pod 去 curl，到这里一共 11 秒，结果什么都没打印出来：

$ kc run t1 --rm -i --restart=Never --image=curlimages/curl:latest -- curl -s -o /dev/null -w '%{http_code}\n' http://web
If you don't see a command prompt, try pressing enter.
pod "t1" deleted

重跑一次还是一样。换成不带 --rm -i、跑完再看日志，就拿到了 200：

$ kc run t1b --restart=Never --image=curlimages/curl:latest -- curl -s -o /dev/null -w '%{http_code}\n' http://web
pod/t1b created
$ kc wait --for=jsonpath='{.status.phase}'=Succeeded pod/t1b --timeout=60s
pod/t1b condition met
$ kc logs t1b
200

再在命令前加 sleep 3，--rm -i 也能看到输出了：

$ kc run t1c --rm -i --restart=Never --image=curlimages/curl:latest -- sh -c 'sleep 3; curl -s -o /dev/null -w "%{http_code}\n" http://web'
If you don't see a command prompt, try pressing enter.
200
pod "t1c" deleted

所以问题不在 Service，而在 kubectl run -i 的 attach 时机：curl 几十毫秒就跑完了，kubectl 还没 attach 上，输出就错过了（这是根据加 sleep 前后的差别推断的，没有去看 kubectl 的源码）。验证类命令跑得很快时，要么先 sleep 一下，要么老老实实 logs。最省事的是保留一个长期运行的客户端 Pod，后面统统 kc exec，题 3 就是这么做的。

题 2：修好一个不工作的 Deployment（62 秒，三层故障）

下面的清单埋了三个错误，一次只暴露一个：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: nginx
          image: nginx:1.27-alpne
          resources:
            requests:
              cpu: "64"
              memory: 64Mi
---
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api
  ports:
    - port: 80
      targetPort: 8080

第一层：Pending。 镜像标签写错了，但 Pod 根本没走到拉镜像那一步：

$ kc apply -f broken.yaml
deployment.apps/api created
service/api created
$ kc get pods -l app=api
NAME                  READY   STATUS    RESTARTS   AGE
api-67dbd6478-lk6cw   0/1     Pending   0          8s
api-67dbd6478-zf29t   0/1     Pending   0          8s
$ kc describe pod -l app=api | sed -n '/Events:/,$p'
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  8s    default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient cpu. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

这条消息要拆开读：控制平面节点因为污点被排除，两个 worker 是 Insufficient cpu。请求了 64 核，哪个节点都放不下。

kc set resources deployment api -c nginx --requests=cpu=50m,memory=64Mi

第二层：ErrImagePull。 改完 15 秒后：

$ kc get pods -l app=api
NAME                   READY   STATUS         RESTARTS   AGE
api-55df847dfc-qmjlz   0/1     ErrImagePull   0          15s
api-67dbd6478-lk6cw    0/1     Pending        0          27s
api-67dbd6478-zf29t    0/1     Pending        0          27s
$ kc get events --field-selector reason=Failed --sort-by=.lastTimestamp | tail -3
11s         Warning   Failed   pod/api-55df847dfc-qmjlz   Failed to pull image "nginx:1.27-alpne": rpc error: code = NotFound desc = failed to pull and unpack image "docker.io/library/nginx:1.27-alpne": failed to resolve reference "docker.io/library/nginx:1.27-alpne": docker.io/library/nginx:1.27-alpne: not found
11s         Warning   Failed   pod/api-55df847dfc-qmjlz   Error: ErrImagePull
10s         Warning   Failed   pod/api-55df847dfc-qmjlz   Error: ImagePullBackOff

注意旧的两个 Pending Pod 还在，新 ReplicaSet 只起了一个 Pod。这是滚动更新的默认参数造成的：maxSurge 和 maxUnavailable 默认都是 25%，2 个副本时前者向上取整为 1、后者向下取整为 0，所以只能先多起 1 个新 Pod，新 Pod 不可用就一直卡在这里。看到新旧 Pod 混在一起时不用慌，修好模板后控制器会自己收尾。

kc set image deployment/api nginx=nginx:1.27
kc rollout status deployment/api --timeout=120s

第三层：新 Pod 都 Running 了，curl 还是失败。

$ kc get endpointslice -l kubernetes.io/service-name=api
NAME        ADDRESSTYPE   PORTS   ENDPOINTS                         AGE
api-wzxw9   IPv4          8080    <pod-ip>,<pod-ip>,<pod-ip>        40s
$ kc run t2 --rm -i --restart=Never --image=curlimages/curl:latest -- sh -c 'sleep 2; curl -sS -m 3 http://api || true'
If you don't see a command prompt, try pressing enter.
curl: (7) Failed to connect to api:80 after 0 ms: Could not connect to server
pod "t2" deleted

EndpointSlice 不是空的，说明选择器没问题；线索是 PORTS 列的 8080，而 nginx 监听 80。（这里列出了三个地址，其中一个是还在 Terminating 的那个镜像拉取失败的 Pod，get endpointslice 的默认输出不区分就绪状态。）再查一下 Deployment：

$ kc get svc api -o jsonpath='{.spec.ports[0].targetPort}{"\n"}'
8080
$ kc get deploy api -o jsonpath='{.spec.template.spec.containers[0].ports}{"\n"}'

容器根本没声明 ports，第一处输出是空行，但这不影响流量：真正决定转发到哪个端口的是 Service 的 targetPort，它必须等于进程实际监听的端口。curl 0 毫秒就报 Could not connect，失败得很快，推测是连接被直接拒绝（8080 上没有进程监听）；这和题 3 里被 NetworkPolicy 拦截时等满超时才失败，是两种很容易区分的表现。

$ kc patch svc api --type=json -p '[{"op":"replace","path":"/spec/ports/0/targetPort","value":80}]'
service/api patched
$ kc get endpointslice -l kubernetes.io/service-name=api
NAME        ADDRESSTYPE   PORTS   ENDPOINTS             AGE
api-wzxw9   IPv4          80      <pod-ip>,<pod-ip>     59s

再 curl 就是 200 了。三层故障各有一条决定性的信息：FailedScheduling 的 Insufficient cpu、Failed to pull image 的 not found、EndpointSlice 的端口号。

题 3：NetworkPolicy 只允许带标签的客户端访问（33 秒）

准备两个长期运行的客户端，一个带 role=client，一个不带。加策略前两个都能访问：

kc run client --image=curlimages/curl:latest --labels=role=client -- sleep 3600
kc run other --image=curlimages/curl:latest -- sleep 3600
$ for p in client other; do echo -n "$p: "; kc exec $p -- curl -s -o /dev/null -w '%{http_code}\n' -m 3 http://web; done
client: 200
other: 200

NetworkPolicy 没有 kubectl create 子命令，只能写 YAML：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-allow-client
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              role: client
      ports:
        - protocol: TCP
          port: 80
$ kc apply -f np-web.yaml
networkpolicy.networking.k8s.io/web-allow-client created
$ for p in client other; do echo -n "$p: "; kc exec $p -- curl -sS -o /dev/null -w '%{http_code}\n' -m 3 http://web; done
client: 200
other: curl: (28) Connection timed out after 3001 milliseconds
000
command terminated with exit code 28

被拦截的表现是超时，不是拒绝，没有任何回应。推测是 Calico 直接把包丢掉了，这次没有在节点上抓包确认。

接着做一个常见的错误：再给客户端加一条只允许访问 web 的出站策略，忘了放行 DNS。

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: client-egress
spec:
  podSelector:
    matchLabels:
      role: client
  policyTypes:
    - Egress
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: web
      ports:
        - protocol: TCP
          port: 80
$ kc exec client -- curl -sS -o /dev/null -w '%{http_code}\n' -m 5 http://web
000
curl: (28) Resolving timed out after 5001 milliseconds
command terminated with exit code 28
$ kc exec client -- curl -sS -o /dev/null -w '%{http_code}\n' -m 5 http://<cluster-ip>
200

报错从 Connection timed out 变成了 Resolving timed out，卡在域名解析。直接用 ClusterIP 访问是通的：在这个 Calico 集群上，允许 app=web 的 Pod 就足以放行经过 Service 的流量，策略按 DNAT 之后的 Pod 地址匹配。补上到 CoreDNS 的 53 端口（UDP 和 TCP 都要）：

- to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
  ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
$ kc exec client -- curl -sS -o /dev/null -w '%{http_code}\n' -m 5 http://web
200
$ kc exec client -- curl -sS -o /dev/null -w '%{http_code}\n' -m 5 http://api
curl: (28) Connection timed out after 5001 milliseconds
000
command terminated with exit code 28

访问 api 超时是预期的：这条出站策略只放行了 app=web 的 80 端口和 DNS，api 的 Pod 不在其中。

namespaceSelector 和 podSelector 写在同一个 - 下面是「与」，分成两个 - 就变成「或」，这个缩进是 NetworkPolicy 最容易写错的地方。kubernetes.io/metadata.name 是每个 namespace 自动带的标签，k8s-app=kube-dns 是先 get pods --show-labels 查出来的，CoreDNS Service 的 targetPort 也是 53，所以按 Pod 端口写 53 是对的。更多细节见 NetworkPolicy。

题 4：用 dry-run 和 explain 快速写清单（16 秒）

要求：Pod cfg 用 busybox:1.36 跑 sleep 3600，请求 50m CPU、32Mi 内存，把 ConfigMap app-cfg 的全部键注入环境变量，同时挂到 /etc/app。

第一反应是让 kubectl run 直接带上资源请求：

$ kc run cfg --image=busybox:1.36 --requests=cpu=50m --dry-run=client -o yaml -- sleep 3600
error: unknown flag: --requests
See 'kubectl run --help' for usage.

这个参数在新版 kubectl 里已经没有了（这次用的客户端是 v1.30.0），旧教程里还常能看到。能生成的只有骨架：

$ kc run cfg --image=busybox:1.36 --dry-run=client -o yaml -- sleep 3600
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: null
  labels:
    run: cfg
  name: cfg
  namespace: notes-lab
spec:
  containers:
  - args:
    - sleep
    - "3600"
    image: busybox:1.36
    name: cfg
    resources: {}
  dnsPolicy: ClusterFirst
  restartPolicy: Always
status: {}

两个细节：-- 后面的内容进了 args 而不是 command（要覆盖镜像的 ENTRYPOINT 得加 --command；busybox 没有 ENTRYPOINT，这里用 args 也能跑）；用了 -n 时输出里会带上 namespace。

剩下的字段名不用背，用 explain 查：

$ kc explain pod.spec.containers.envFrom --recursive
...
FIELDS:
  configMapRef	<ConfigMapEnvSource>
    name	<string>
    optional	<boolean>
  prefix	<string>
  secretRef	<SecretEnvSource>
    name	<string>
    optional	<boolean>
$ kc explain pod.spec.containers.volumeMounts | grep -E '^  [a-zA-Z]+'
  mountPath	<string> -required-
  mountPropagation	<string>
  name	<string> -required-
  readOnly	<boolean>
  recursiveReadOnly	<string>
  subPath	<string>
  subPathExpr	<string>

补完后的清单：

apiVersion: v1
kind: Pod
metadata:
  labels:
    run: cfg
  name: cfg
spec:
  containers:
  - args:
    - sleep
    - "3600"
    image: busybox:1.36
    name: cfg
    resources:
      requests:
        cpu: 50m
        memory: 32Mi
    envFrom:
    - configMapRef:
        name: app-cfg
    volumeMounts:
    - name: cfg
      mountPath: /etc/app
  volumes:
  - name: cfg
    configMap:
      name: app-cfg

ConfigMap 用 kc create configmap app-cfg --from-literal=MODE=exam --from-literal=app.conf='listen 80' 建。验证（第一条是一次组合命令，最后的 1 是环境变量里含 app.conf 的行数）：

$ kc exec cfg -- sh -c 'echo MODE=$MODE; ls /etc/app; cat /etc/app/app.conf; echo; env | grep -c app.conf'
MODE=exam
MODE
app.conf
listen 80
1
$ kc exec cfg -- env | grep -E 'MODE|app.conf'
MODE=exam
app.conf=listen 80

app.conf 带点号能被注入并不奇怪：旧版 kubelet 用来检查的正则是 [-._a-zA-Z][-._a-zA-Z0-9]*，本来就允许点号。真正的意外在后面：explain envFrom 只说键必须是 C_IDENTIFIER、非法键会记事件；官方的 ConfigMap 任务页更进一步，说非法键会被跳过，并举了 1badkey 的例子。专门建一个带数字开头键的 ConfigMap，再用 dry-run 生成 Pod、jq 补上 envFrom 后提交：

kc create configmap bad-keys --from-literal=1bad=x --from-literal=good-key.v1=y
kc run envtest --image=busybox:1.36 --restart=Never --dry-run=client -o json -- sh -c 'env | grep -E "bad|good"; sleep 5' \
  | jq '.spec.containers[0].envFrom=[{configMapRef:{name:"bad-keys"}}]' | kc apply -f -

1bad 照样被注入了，事件里也没有任何警告：

$ kc logs envtest
good-key.v1=y
1bad=x
$ kc get events --field-selector involvedObject.name=envtest -o custom-columns=TYPE:.type,REASON:.reason,MSG:.message
TYPE     REASON      MSG
Normal   Scheduled   Successfully assigned notes-lab/envtest to worker2
Normal   Pulled      Container image "busybox:1.36" already present on machine
Normal   Created     Created container envtest
Normal   Started     Started container envtest

API Server 和 kubelet 的 RelaxedEnvironmentVariableValidation 特性门控都显示为关闭（stage="ALPHA"} 0；这个门控在 1.30–1.31 是 alpha，默认关闭），所以不是门控的作用。对比 release-1.29 和 release-1.30 的 pkg/kubelet/kubelet_pods.go 可以看到原因：v1.30 起 kubelet 不再过滤 envFrom 里的非法键，IsEnvVarName 检查和 InvalidEnvironmentVariableNames 事件整段被删掉了，这和门控无关。kubernetes.io 的 ConfigMap 任务页里还是旧说法。

题 5：JSONPath 和 custom-columns 查询

第一条命令就栽了：

$ kc get pods -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,IMAGE:.spec.containers[*].image,IP:.status.podIP --sort-by=.metadata.creationTimestamp
(eval):1: no matches found: custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,IMAGE:.spec.containers[*].image,IP:.status.podIP

这台机器的 shell 是 zsh，[*] 被当成通配符，找不到匹配文件就直接报错，kubectl 根本没被执行。同样的命令在 bash 里能跑：bash 找不到匹配时会把原字符串原样传下去（但如果当前目录恰好有能匹配的文件名，bash 也会把它替换掉）。后面查控制平面组件时我又犯了一次同样的错。凡是带 [ 的 JSONPath，一律加引号：

下面这条是加上引号后补跑的，所以列表里已经有了后面用到的 burner：

$ kc get pods -o 'custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,IMAGE:.spec.containers[*].image' --sort-by=.metadata.creationTimestamp
NAME                   NODE      IMAGE
web-555d94684b-9bfzc   worker    nginx:1.27
web-555d94684b-9rtlp   worker2   nginx:1.27
api-79cf89564b-fzjdr   worker2   nginx:1.27
api-79cf89564b-dgw9f   worker    nginx:1.27
burner                 worker2   busybox:1.36

{.items[*].metadata.name} 输出的是空格分隔的一行；要一行一个，用 range：

$ kc get pods -l app=web -o jsonpath='{.items[*].metadata.name}'
web-555d94684b-9bfzc web-555d94684b-9rtlp
$ kc get pods -l app=web -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.containerStatuses[0].restartCount}{"\n"}{end}'
web-555d94684b-9bfzc	0
web-555d94684b-9rtlp	0

另一类常见题是「把 CPU 用量最高的 Pod 名写进文件」。第一次跑时所有 Pod 都是 0m：

$ kc top pod --sort-by=cpu
NAME                   CPU(cores)   MEMORY(bytes)   
api-79cf89564b-dgw9f   0m           21Mi            
api-79cf89564b-fzjdr   0m           21Mi            
cfg                    0m           1Mi             
web-555d94684b-9bfzc   0m           29Mi            
web-555d94684b-9rtlp   0m           28Mi

这时 head -1 取到的只是并列里排第一的那个，答案没有意义。起一个 CPU limit 为 100m 的死循环 Pod burner：

kc run burner --image=busybox:1.36 --restart=Never --overrides='{"spec":{"containers":[{"name":"burner","image":"busybox:1.36","command":["sh","-c","timeout 150 sh -c \"while :; do :; done\""],"resources":{"requests":{"cpu":"50m"},"limits":{"cpu":"100m"}}}]}}'

它在创建后 29 秒内出现在 top 里（刚创建时还是 ContainerCreating，13 秒时已经 Running）。推测剩下的等待是 metrics-server 采样周期造成的，这次没有单独测：

$ kc top pod --sort-by=cpu
NAME                   CPU(cores)   MEMORY(bytes)   
burner                 90m          2Mi             
api-79cf89564b-dgw9f   0m           21Mi            
...
$ kc top pod --sort-by=cpu --no-headers | head -1 | awk '{print $1}' > top-pod.txt; cat top-pod.txt
burner

刚创建的 Pod 在 top 里查不到时，等半分钟再看，不要以为命令写错了。更多查询写法见 kubectl JSONPath 查询。

题 6：PVC 与动态供给（10 秒）

$ kubectl get sc standard
NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
standard (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  60d

清单 pvc.yaml 里是一个 PVC 和一个挂载它、往里写时间的 Pod：

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: standard
  resources:
    requests:
      storage: 100Mi
---
apiVersion: v1
kind: Pod
metadata:
  name: writer
spec:
  containers:
    - name: w
      image: busybox:1.36
      command: ["sh", "-c", "date > /data/at.txt; sleep 3600"]
      volumeMounts:
        - name: d
          mountPath: /data
  volumes:
    - name: d
      persistentVolumeClaim:
        claimName: data

先只提交其中的 PVC（--- 之前的前 10 行）：

head -10 pvc.yaml | kc apply -f -
$ kc get pvc data
NAME   STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
data   Pending                                      standard       <unset>                 0s
$ kc describe pvc data | sed -n '/Events/,$p'
Events:
  Type    Reason                Age   From                         Message
  ----    ------                ----  ----                         -------
  Normal  WaitForFirstConsumer  1s    persistentvolume-controller  waiting for first consumer to be created before binding

Pending 在这里是正常的：WaitForFirstConsumer 要等有 Pod 用它、调度器选定节点后才创建 PV。再提交整个文件，把 Pod 也建出来：

$ kc apply -f pvc.yaml
persistentvolumeclaim/data unchanged
pod/writer created
$ kc wait --for=condition=Ready pod/writer --timeout=90s
pod/writer condition met
$ kc get pvc data
NAME   STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
data   Bound    pvc-df9780cf-03bd-48ff-8385-fef20ebf6681   100Mi      RWO            standard       <unset>                 10s
$ kc exec writer -- cat /data/at.txt
Tue Oct 13 06:17:41 UTC 2026

所以排查 PVC Pending，先看 StorageClass 的 VOLUMEBINDINGMODE，再看 Events；如果是 Immediate 却一直 Pending，才是供给器的问题。删除 namespace 后，PV 先变成 Released，因为回收策略是 Delete，几秒后就被删掉了。见 PV、PVC 与 StorageClass。

题 7：RBAC，只允许改 Deployment（28 秒）

kc create serviceaccount deployer
kc create role deploy-mgr --verb=get,list,watch,update,patch --resource=deployments

绑定时少写了 namespace：

$ kc create rolebinding deploy-mgr --role=deploy-mgr --serviceaccount=deployer
error: serviceaccount must be <namespace>:<name>

--serviceaccount 必须写成 <namespace>:<name>，哪怕已经用 -n 指定了 namespace。改成 --serviceaccount=notes-lab:deployer 后检查权限：

$ kc auth can-i patch deployments --as=system:serviceaccount:notes-lab:deployer
yes
$ kc auth can-i create deployments --as=system:serviceaccount:notes-lab:deployer
no
$ kc auth can-i patch deployments/scale --as=system:serviceaccount:notes-lab:deployer
yes
$ kc scale deployment web --replicas=1 --as=system:serviceaccount:notes-lab:deployer
Error from server (Forbidden): deployments.apps "web" is forbidden: User "system:serviceaccount:notes-lab:deployer" cannot patch resource "deployments/scale" in API group "apps" in the namespace "notes-lab"

can-i 说可以，真去 scale 却被拒了。加 -v=8 看 kubectl 实际发出的请求：

Request Body: {"kind":"SelfSubjectAccessReview","apiVersion":"authorization.k8s.io/v1","metadata":{"creationTimestamp":null},"spec":{"resourceAttributes":{"namespace":"notes-lab","verb":"patch","group":"apps","resource":"deployments","name":"scale"}},"status":{"allowed":false}}

deployments/scale 被解析成了「名为 scale 的 Deployment」，问的根本不是子资源。用 get deployments/does-not-exist 这种不存在的名字去问，同样返回 yes，因为 Role 没有限制 resourceNames。查子资源要用 --subresource：

$ kc auth can-i patch deployments --subresource=scale --as=system:serviceaccount:notes-lab:deployer
no

给 Role 补上 deployments/scale 规则：

kc patch role deploy-mgr --type=json -p '[{"op":"add","path":"/rules/-","value":{"apiGroups":["apps"],"resources":["deployments/scale"],"verbs":["get","patch","update"]}}]'

之后这条命令返回 yes，scale 也成功了。kubectl scale 走的是 scale 子资源，所以只给 deployments 的 patch 不够。见 ServiceAccount 与 RBAC。

题 8：滚动更新与回滚（14 秒）

kc scale deployment web --replicas=2
kc set image deployment/web nginx=nginx:alpine
kc annotate deployment/web kubernetes.io/change-cause='image nginx:alpine'
kc rollout status deployment/web
kc rollout history deployment/web
kc rollout undo deployment/web --to-revision=1
kc rollout history deployment/web
REVISION  CHANGE-CAUSE
1         <none>
2         image nginx:alpine

deployment.apps/web rolled back
...
REVISION  CHANGE-CAUSE
2         image nginx:alpine
3         <none>

回滚到 revision 1 之后，历史里的 1 不见了，变成了 3。回滚不是「回到旧编号」，而是把旧模板重新作为最新的 revision；题目要求「回滚后写出当前 revision 号」时，答案是 3 而不是 1。最后用 jsonpath 确认镜像已经回到 nginx:1.27。滚动更新的细节见 Deployment。

集群组件：只做只读检查

节点级操作没有做，但控制平面是否健康可以只读地看：

$ kubectl get --raw='/readyz?verbose' | tail -5
[+]autoregister-completion ok
[+]poststarthook/apiservice-openapi-controller ok
[+]poststarthook/apiservice-openapiv3-controller ok
[+]shutdown ok
readyz check passed

kubeadm 集群的控制平面组件是 kube-system 里的静态 Pod，可以用 kubectl -n kube-system get pods -l tier=control-plane 列出；组件起不来时要去节点上看 kubelet 日志和 /etc/kubernetes/manifests，见集群组件和常见故障排查。

这次最耽误时间的几件事

  • kubectl run --rm -i 跑太快的命令会丢输出，以为 Service 坏了，其实是没 attach 上。
  • zsh 把 [*] 当通配符，同一个错犯了两次。JSONPath 一律加引号。
  • auth can-i ... deployments/scale 问的是名为 scale 的对象，子资源要用 --subresource。
  • v1.30 的 kubectl run 已经没有 --requests，资源请求要在 dry-run 生成的 YAML 里补，或者对 Deployment 用 kubectl set resources。
  • top 结果全是 0m 时，「最高的那个」没有意义；新 Pod 要等半分钟才有数据。

清理

kubectl delete namespace notes-lab --wait
kubectl get pv | grep notes-lab   # 刚删完时 PV 可能还是 Released，几秒后才消失
