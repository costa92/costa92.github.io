Pod 从提交到 Ready 经过哪些关口

Pod 与容器已经看过单容器 Pod 的 phase、CrashLoopBackOff 和 logs --previous。这一篇把 Pod 内部的启动链条拆开看：init 容器按顺序跑完，应用容器才启动；还可以把 init 容器声明成 sidecar（1.28 引入时是 alpha，需要打开特性门；1.29 升为 beta 并默认开启），让它一直运行下去；容器启动和停止时各有一个钩子。每一步落在状态的哪个字段上，失败时怎么体现，下面逐个测。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），镜像全部用本地已缓存的 busybox:1.36，时间都是 UTC。实验 namespace 在输出里统一写成 notes-lab，节点名简化成 worker、worker2，containerd 容器 ID 截断。实验期间宿主机上还跑着别的负载（load average 在 10 到 14 之间），所以下面看到的「容器之间隔了 5 秒」这类间隔偏大，只能看先后顺序，不要当成基准值。

phase 只有一个，condition 有五个

phase 是一个粗粒度的总结：Pending、Running、Succeeded、Failed、Unknown。更细的进度记录在 status.conditions 里。在 1.31 上，kubelet 维护的 condition 有五个：

  • PodScheduled：已经调度到节点。
  • PodReadyToStartContainers：沙箱建好、网络配好、卷挂好，可以开始拉镜像建容器了。它在 1.31 是 beta 特性，默认开启，早期叫 PodHasNetwork。
  • Initialized：所有 init 容器都成功结束。
  • ContainersReady：所有容器都就绪。
  • Ready：Pod 可以接流量，Service 会把它加入端点。

用一个两个 init 容器加一个应用容器的 Pod，看这五个 condition 依次在什么时候变成 True。每个 init 容器打印开始和结束时间、睡 4 秒；应用容器启动 5 秒后才创建就绪文件，这样 ContainersReady 和应用启动能错开。保存为 phases.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: phases
spec:
  initContainers:
    - name: init-a
      image: busybox:1.36
      command: ["sh", "-c", "echo \"init-a start $(date +%T)\"; sleep 4; echo \"init-a done $(date +%T)\""]
    - name: init-b
      image: busybox:1.36
      command: ["sh", "-c", "echo \"init-b start $(date +%T)\"; sleep 4; echo \"init-b done $(date +%T)\""]
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo \"app start $(date +%T)\"; sleep 5; touch /tmp/ready; sleep 3600"]
      readinessProbe:
        exec:
          command: ["cat", "/tmp/ready"]
        periodSeconds: 1
      resources:
        requests: {cpu: 10m, memory: 16Mi}
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f phases.yaml
kubectl -n notes-lab get pod phases -w

提交时间是 03:22:07，STATUS 列的变化：

NAME     READY   STATUS    RESTARTS   AGE
phases   0/1     Pending   0          1s
phases   0/1     Init:0/2   0          1s
phases   0/1     Init:0/2   0          10s
phases   0/1     Init:0/2   0          13s
phases   0/1     Init:1/2   0          22s
phases   0/1     Init:1/2   0          24s
phases   0/1     PodInitializing   0          30s
phases   0/1     Running           0          30s
phases   1/1     Running           0          36s

Init:1/2 表示两个 init 容器完成了一个；PodInitializing 表示 init 全部完成、应用容器还没起来。再把 condition 按转换时间排序，和容器的起止时间放在一起：

kubectl -n notes-lab get pod phases \
  -o jsonpath='{range .status.conditions[*]}{.lastTransitionTime}  {.type}={.status}{"\n"}{end}' | sort
2026-10-13T03:22:07Z  PodScheduled=True
2026-10-13T03:22:20Z  PodReadyToStartContainers=True
2026-10-13T03:22:36Z  Initialized=True
2026-10-13T03:22:42Z  ContainersReady=True
2026-10-13T03:22:42Z  Ready=True
init-a 2026-10-13T03:22:19Z -> 2026-10-13T03:22:23Z Completed
init-b 2026-10-13T03:22:29Z -> 2026-10-13T03:22:33Z Completed
app started=2026-10-13T03:22:37Z ready=true

对照起来就是一条串行的链：

时间发生了什么
03:22:07调度完成，PodScheduled=True
03:22:17第一条 Pulled 事件，说明沙箱此时已经建好
03:22:19–20init-a 开始；PodReadyToStartContainers=True 写入
03:22:23init-a 结束
03:22:29–33init-b 运行，前一个结束之后它才开始
03:22:36Initialized=True
03:22:37应用容器启动
03:22:42就绪文件出现、探针通过，ContainersReady 和 Ready 同时为 True

几个值得注意的地方：

  • init 期间 phase 一直是 Pending，虽然 init 容器明明在跑。STATUS 列的 Init:0/2 是 kubectl get 的展示列（由 API Server 的 printPod 生成），不是 phase。后面 init 反复失败的 Pod 同样停在 Pending。
  • 调度到沙箱就绪不超过 10 秒，condition 晚写了约 3 秒。 第一条 Pulled 事件出现在 03:22:17，拉镜像之前沙箱必须已经建好；而 PodReadyToStartContainers 的转换时间是 03:22:20，比实际就绪晚了约 3 秒。这段时间里 Pod 没有任何容器，事件列表里也只有一条 Scheduled。十几分钟后（03:35）在同一集群重复一次，condition 在调度后 11 秒写入，init 容器之间也同样隔了 5–6 秒。从 init-a 结束（03:22:23）到 init-b 的 Pulled 事件（03:22:28）中间 kubelet 没有留下任何事件，这次没有深究，推测和宿主机负载有关，换一个空闲集群应该会短得多。
  • lastTransitionTime 只精确到秒，而且是 kubelet 同步状态时写的，所以 PodReadyToStartContainers 的时间可能比第一个 init 容器的 startedAt 还晚一秒（第二次测量就是 03:35:45 对 03:35:44），不要拿它做精确计时。
  • 应用容器 03:22:37 就在运行了，但 Ready 要等到 03:22:42。这 5 秒里 Pod 是 Running 而 0/1，事件里留下一条 Readiness probe failed: cat: can't open '/tmp/ready'。

kubectl wait --for=condition=Ready 等的就是最后一个 condition。脚本里如果只想等 init 跑完（比如要去看应用容器的第一行日志），可以等 condition=Initialized。

init 容器失败：Always 与 Never 结局不同

模拟一个数据库迁移步骤连不上数据库。同一份清单只改 restartPolicy，分别建 init-fail-always（Always，也是默认值）和 init-fail-never（Never）：

apiVersion: v1
kind: Pod
metadata:
  name: init-fail-always
spec:
  restartPolicy: Always
  initContainers:
    - name: migrate
      image: busybox:1.36
      command: ["sh", "-c", "echo \"migrate run $(date +%T)\"; echo 'db not reachable' >&2; exit 1"]
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}

同时 watch 两个 Pod（kubectl get pod a b -w 会报 you may only watch a single resource or type of resource at a time，所以直接 watch 整个 namespace）：

NAME               READY   STATUS        RESTARTS   AGE
init-fail-always   0/1     Init:0/1      0          4s
init-fail-never    0/1     Init:0/1      0          4s
init-fail-always   0/1     Init:Error    0          12s
init-fail-never    0/1     Init:Error    0          14s
init-fail-always   0/1     Init:0/1      1 (9s ago)   15s
init-fail-always   0/1     Init:Error    1 (9s ago)   15s
init-fail-always   0/1     Init:CrashLoopBackOff   1 (18s ago)   31s
init-fail-always   0/1     Init:Error              2 (20s ago)   33s
init-fail-always   0/1     Init:CrashLoopBackOff   2 (16s ago)   47s
init-fail-always   0/1     Init:0/1                3 (36s ago)   67s
init-fail-always   0/1     Init:Error              3 (38s ago)   69s

（输出里删掉了几行重复状态。）Always 的 Pod 在 Init:Error 和 Init:CrashLoopBackOff 之间循环，重启次数不断增加，退避规则和普通容器一样，从 10 秒开始翻倍；Never 的 Pod 停在 Init:Error，再也不动了。两者的状态字段差别更大：

$ kubectl -n notes-lab get pod init-fail-always -o jsonpath=...
phase=Pending reason=
PodReadyToStartContainers=True
Initialized=False ContainersNotInitialized
Ready=False ContainersNotReady
ContainersReady=False ContainersNotReady
PodScheduled=True
init: 3 {"terminated":{"containerID":"containerd://1dcc1e46...","exitCode":1,"finishedAt":"2026-10-13T03:25:32Z","reason":"Error","startedAt":"2026-10-13T03:25:32Z"}}
app: {"waiting":{"reason":"PodInitializing"}}

$ kubectl -n notes-lab get pod init-fail-never -o jsonpath=...
phase=Failed reason=
PodReadyToStartContainers=False
Initialized=False ContainersNotInitialized
Ready=False PodFailed
ContainersReady=False PodFailed
PodScheduled=True
init: 0 {"terminated":{"containerID":"containerd://bdc537bf...","exitCode":1,"finishedAt":"2026-10-13T03:24:38Z","reason":"Error","startedAt":"2026-10-13T03:24:38Z"}}
app: {"waiting":{"reason":"PodInitializing"}}
  • Always：phase 仍是 Pending。一个 init 容器重启了几十次的 Pod，phase 依然显示「还没开始」，按 phase 做告警的话会漏掉它，要看 initContainerStatuses[].restartCount。
  • Never：phase 直接变成 Failed，Ready 的原因写成 PodFailed，沙箱也被回收了（PodReadyToStartContainers=False）。官方文档的表述是，restartPolicy: Never 的 Pod 在启动阶段 init 容器失败，整个 Pod 被视为失败。Job 的 Pod 常用 Never，这时 init 失败会直接算作一次 Pod 失败，计入 Job 的 backoffLimit。
  • 两种情况下应用容器都停在 waiting: PodInitializing，从来没有被创建过。这时去看它的日志只会得到：
Error from server (BadRequest): container "app" in pod "init-fail-always" is waiting to start: PodInitializing

看到这个报错，就该把 -c 换成 init 容器的名字。init 容器处于退避等待时，logs -c migrate 和 logs -c migrate --previous 返回的都是最近一次失败的那份：

migrate run 03:25:32
db not reachable
migrate run 03:25:32
db not reachable

这和 Pod 与容器里普通容器的规律一致：容器正在退避时，当前实例就是最近一次退出的那个。

还有一个事件计数上的小坑：init-fail-always 的事件列表里 Created container migrate 的 COUNT 是 4、时间是最后一次的 03:25:32，前几次的时间都被合并掉了。要还原每次重试的时间，得看 init 容器自己打印的日志，或者在故障发生时就 watch。

init 容器什么时候会重跑

init 容器跑完就结束了，那么后面应用容器崩溃重启时，init 会不会再跑一遍？用一个 emptyDir 记录 init 的执行历史：init 每次运行往 /work/history 追加一行，应用容器启动时把这个文件打印出来，在发现 /tmp/crash 后以退出码 1 退出。保存为 rerun.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: rerun
spec:
  volumes:
    - name: work
      emptyDir: {}
  initContainers:
    - name: init
      image: busybox:1.36
      command: ["sh", "-c", "echo \"init ran $(date +%T)\" | tee -a /work/history"]
      volumeMounts:
        - {name: work, mountPath: /work}
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo \"app start $(date +%T)\"; cat /work/history; while [ ! -f /tmp/crash ]; do sleep 1; done; exit 1"]
      volumeMounts:
        - {name: work, mountPath: /work}
      resources:
        requests: {cpu: 10m, memory: 16Mi}

最初的版本用 kubectl exec ... -- kill 1 让 sleep 3600 的应用退出，结果 RESTARTS 一直是 0：没有 trap 的 shell 作为 PID 1 会忽略 SIGTERM（见优雅终止），所以改成了用文件触发退出。

应用容器重启：init 不重跑

kubectl -n notes-lab exec rerun -c app -- touch /tmp/crash   # 03:27:12
NAME    READY   STATUS    RESTARTS      AGE
rerun   1/1     Running   1 (12s ago)   19s
init restarts=0 finished=2026-10-13T03:27:09Z
app restarts=1 last=Error/1
$ kubectl -n notes-lab logs rerun -c app
app start 03:27:16
init ran 03:27:09

应用容器重启了一次，新实例 03:27:16 启动，但历史文件里只有一行，init 的 finishedAt 也没变。kubelet 只重启退出的那个容器，init 已经完成的记录还在，不会重来。

沙箱被重建：init 全部重跑

官方文档列出的 init 重跑原因之一是 Pod 的基础设施容器（也就是沙箱里的 pause 容器）被重启。下面用 crictl 只停掉这个 Pod 的沙箱来模拟。

注意
这是直接在节点上操作容器运行时，绕过了 Kubernetes。只在随时可以重建的 kind 实验集群里这样做，不要在共享或生产节点上执行。

kind 的节点就是一个 Docker 容器，容器名和节点名相同，所以先查出 Pod 在哪个节点上，再 docker exec 进去：

kubectl -n notes-lab get pod rerun -o wide            # NODE 列就是节点容器名
docker exec <节点容器> crictl pods --namespace notes-lab --name rerun
docker exec <节点容器> crictl stopp <沙箱 ID>      # 03:27:36
POD ID              CREATED              STATE               NAME                NAMESPACE                 ATTEMPT             RUNTIME
5ff84bb6c075e       23 seconds ago       Ready               rerun               notes-lab                 0                   (default)

（略去了一行前一个同名 Pod 留下的 NotReady 沙箱。）

crictl stopp 自己报了 context deadline exceeded（crictl 默认超时较短），但沙箱确实停了。之后的事件：

2026-10-13T03:27:50Z   2        Pulled           Container image "busybox:1.36" already present on machine
2026-10-13T03:27:53Z   2        Created          Created container init
2026-10-13T03:27:54Z   2        Started          Started container init
2026-10-13T03:27:57Z   3        Pulled           Container image "busybox:1.36" already present on machine
2026-10-13T03:28:01Z   3        Created          Created container app
2026-10-13T03:28:01Z   3        Started          Started container app
uid=13ad7c6f-b1c6-47c9-8d01-d15aaf75d8df

$ kubectl -n notes-lab logs rerun -c app

顺序要看清：BackOff（03:27:39）出现在 SandboxChanged（03:27:40）之前。停沙箱时，运行时会把沙箱里的容器一起停掉，应用容器这次的退出码 137 就来自 crictl stopp 这一步，而不是 kubelet 发现沙箱变化后去杀的。kubelet 先看到的是「应用容器又退出了」：它在 03:27:12 已经崩溃过一次，这次重启要退避，于是先记了一条 BackOff；下一轮同步才发现沙箱没了，记下 SandboxChanged，重建沙箱，再从第一个 init 容器开始重新走一遍。

20 秒后再看节点上的沙箱，多了一个 ATTEMPT 为 1 的新沙箱，旧的变成 NotReady：

POD ID              CREATED             STATE               NAME                NAMESPACE                 ATTEMPT             RUNTIME
9a0e019e07ad8       12 seconds ago      Ready               rerun               notes-lab                 1                   (default)
5ff84bb6c075e       51 seconds ago      NotReady            rerun               notes-lab                 0                   (default)

Pod 的 UID 没变，所以 emptyDir 还在，历史文件里多了第二行。

这就是文档要求 init 容器幂等的原因：init 写进 emptyDir 的东西，第二次运行时可能已经存在。比如 init 用 mkdir 建目录而没有加 -p，或者对数据库执行不带 IF NOT EXISTS 的建表，在沙箱重建后就会失败，Pod 卡在 Init:CrashLoopBackOff，而第一次部署时一切正常。推测节点重启而 Pod 没被驱逐时也会走同样的路径，但这次没有测；而且这只适用于 restartPolicy 不是 Never 的 Pod，Never 的 Pod 在第一个沙箱之后不会再重建沙箱。

sidecar：带 restartPolicy: Always 的 init 容器

给 init 容器写上 restartPolicy: Always，它就成了 sidecar：按 init 的顺序启动，但不需要退出，而是和应用容器一起一直运行。这个能力由 SidecarContainers 特性门控制，1.29 起默认开启，在 1.31 上不需要任何额外配置。

下面这个 Pod 把普通 init 和 sidecar 交错排列：setup（普通）→ proxy（sidecar）→ logagent（sidecar）→ migrate（普通）→ 应用 app。每个容器都打印启动时间；sidecar 和应用收到 SIGTERM 时打印一行，应用收到后还要花 4 秒收尾。保存为 sidecar.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: sidecar
spec:
  terminationGracePeriodSeconds: 30
  initContainers:
    - name: setup
      image: busybox:1.36
      command: ["sh", "-c", "echo \"setup $(date +%T)\"; sleep 3"]
    - name: proxy
      image: busybox:1.36
      restartPolicy: Always
      command: ["sh", "-c", "trap 'echo \"proxy TERM $(date +%T)\"; exit 0' TERM; echo \"proxy start $(date +%T)\"; while true; do sleep 1 & wait $!; done"]
    - name: logagent
      image: busybox:1.36
      restartPolicy: Always
      command: ["sh", "-c", "trap 'echo \"logagent TERM $(date +%T)\"; exit 0' TERM; echo \"logagent start $(date +%T)\"; while true; do sleep 1 & wait $!; done"]
    - name: migrate
      image: busybox:1.36
      command: ["sh", "-c", "echo \"migrate $(date +%T)\"; sleep 3"]
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "trap 'echo \"app TERM $(date +%T)\"; env sleep 4; echo \"app exit $(date +%T)\"; exit 0' TERM; echo \"app start $(date +%T)\"; while true; do sleep 1 & wait $!; done"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}

主循环写成 sleep 1 & wait $!、trap 里用 env sleep，原因见优雅终止。

启动顺序

  • sidecar 不需要「完成」。Initialized 在 03:28:51 变成 True 时，proxy 和 logagent 都还在运行；对 sidecar 来说，「启动了」就算过了这一关。
  • READY 列的分母是 3：两个 sidecar 加一个应用容器，普通 init 不算。Init:2/4 那一刻显示 1/3，说明 proxy 已经被算作就绪的容器。sidecar 如果配了 readinessProbe，它的结果会影响 Pod 的 Ready。

用 startupProbe 让后面的容器等 sidecar 真正就绪

「启动了」只表示进程在跑。代理类 sidecar 往往要几秒才开始监听，这时可以给 sidecar 配 startupProbe，kubelet 会等探针通过才启动下一个容器。下面的 proxy 8 秒后才创建 /tmp/up，保存为 sidecar-probe.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: sidecar-probe
spec:
  initContainers:
    - name: proxy
      image: busybox:1.36
      restartPolicy: Always
      command: ["sh", "-c", "echo \"proxy start $(date +%T)\"; sleep 8; touch /tmp/up; echo \"proxy up $(date +%T)\"; sleep 3600"]
      startupProbe:
        exec:
          command: ["cat", "/tmp/up"]
        periodSeconds: 1
        failureThreshold: 30
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo \"app start $(date +%T)\"; sleep 3600"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}
proxy start 03:30:34
proxy up 03:30:42
app start 03:30:44
2026-10-13T03:30:42Z  Initialized=True

Initialized 正好在 proxy up 那一秒变成 True，应用容器在那之后才启动。没有 startupProbe 时，下一个容器会在 sidecar 进程启动后立刻开始（上一节里就是 init 容器 migrate），第一批请求可能打到一个还没监听的代理上。

关闭顺序

删除 Pod 前，对 app、proxy、logagent 各开一个 kubectl logs -f --timestamps 跟着日志：

for c in app proxy logagent; do kubectl -n notes-lab logs -f --timestamps sidecar -c $c > sc-$c.log & done
kubectl -n notes-lab delete pod sidecar     # 03:30:07.283 发出，03:30:15.799 返回
2026-10-13T03:30:07.381010675Z app TERM 03:30:07
2026-10-13T03:30:11.451657306Z app exit 03:30:11
2026-10-13T03:30:12.592045139Z logagent TERM 03:30:12
2026-10-13T03:30:13.309723377Z proxy TERM 03:30:13

（三份日志按时间合并，略去了各自的启动行。）

  1. 删除请求发出后约 0.1 秒，应用容器收到 SIGTERM；此时两个 sidecar 都没有收到信号。
  2. 应用 4 秒后退出（03:30:11.45）。
  3. 1.1 秒后 logagent 收到 SIGTERM，再过 0.7 秒才轮到 proxy。

也就是先停应用，应用完全退出后再按清单的倒序停 sidecar，后启动的先停。这正好是代理类 sidecar 需要的：应用在收尾阶段还能通过代理发请求、通过日志 sidecar 送出最后的日志。官方文档的描述与此一致。需要注意的是这几步共用同一个 terminationGracePeriodSeconds，应用收尾用掉的时间，sidecar 就少了。

第一次测试时 trap 里用的是内置 sleep 4，应用 0.9 秒就退出了（busybox 的老问题，见优雅终止文末），但那一次 sidecar 的顺序同样是 logagent 先于 proxy。

sidecar 崩溃：STATUS 显示 Init:Error，但应用在正常运行

sidecar 退出后总会被重启，不受 Pod 的 restartPolicy 影响。下面的 Pod 是 restartPolicy: Never，sidecar agent 每次运行 5 秒后以退出码 1 退出：

apiVersion: v1
kind: Pod
metadata:
  name: sidecar-crash
spec:
  restartPolicy: Never
  initContainers:
    - name: agent
      image: busybox:1.36
      restartPolicy: Always
      command: ["sh", "-c", "echo \"agent start $(date +%T)\"; sleep 5; echo 'agent crashed' >&2; exit 1"]
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo \"app start $(date +%T)\"; sleep 3600"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}

一分钟后：

NAME            READY   STATUS       RESTARTS   AGE
sidecar-crash   1/2     Init:Error   2          60s
phase=Running
agent restarts=2 state={"terminated":{...,"exitCode":1,"finishedAt":"2026-10-13T03:31:10Z","reason":"Error","startedAt":"2026-10-13T03:31:05Z"}}
app restarts=0 state={"running":{"startedAt":"2026-10-13T03:30:36Z"}}

Never 只管应用容器，sidecar 已经重启了两次并进入退避。更容易误导人的是 STATUS 列：显示 Init:Error，看起来像是 Pod 还没初始化完，实际上 phase 是 Running，应用容器从 03:30:36 起一直在跑、从未重启。这一列是 API Server 端按 v1.31 的 printPod 拼出来的：遍历 init 容器时，一个处于 terminated 状态的 sidecar 会让 STATUS 被设成 Init: 加退出原因；之后虽然因为 Initialized=True 还会再看一遍应用容器，但只有应用容器处于 waiting 或 terminated 时才会覆盖这个值，正在运行的应用容器只会让 READY 加一。所以只要 sidecar 恰好处在两次重启之间，STATUS 就是 Init:Error。看到 sidecar Pod 显示 Init: 开头的状态时，先看 READY 列和 containerStatuses，确认应用容器本身是不是好的，再去查 sidecar 的 logs -c <sidecar> --previous。

postStart：会阻塞后面的容器，失败会杀掉容器

postStart 钩子在容器创建后立即触发，和容器的主进程同时运行，不保证谁先谁后。下面的 Pod 有两个容器，first 的 postStart 睡 6 秒，所有步骤都往共享卷里的同一个文件追加一行：

apiVersion: v1
kind: Pod
metadata:
  name: poststart
spec:
  volumes:
    - name: log
      emptyDir: {}
  containers:
    - name: first
      image: busybox:1.36
      command: ["sh", "-c", "echo \"first main $(date +%T)\" >> /log/seq; sleep 3600"]
      volumeMounts: [{name: log, mountPath: /log}]
      lifecycle:
        postStart:
          exec:
            command: ["sh", "-c", "echo \"first postStart begin $(date +%T)\" >> /log/seq; sleep 6; echo \"first postStart end $(date +%T)\" >> /log/seq"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}
    - name: second
      image: busybox:1.36
      command: ["sh", "-c", "echo \"second main $(date +%T)\" >> /log/seq; sleep 3600"]
      volumeMounts: [{name: log, mountPath: /log}]
NAME        READY   STATUS              RESTARTS   AGE

poststart   0/2     ContainerCreating   0          8s
poststart   2/2     Running             0          18s
$ kubectl -n notes-lab exec poststart -c second -- cat /log/seq

first postStart end 03:32:04
second main 03:32:05

  • first 的主进程和钩子在同一秒开始，所以钩子里不能假设主进程已经在监听端口，也不能假设它还没开始。
  • 钩子运行的 6 秒里，Pod 一直显示 ContainerCreating，first 的主进程其实早就在跑了。
  • second 要等 first 的 postStart 结束才被创建（03:32:04 钩子结束，03:32:04 才出现 second 的 Pulled）。kubelet 按顺序启动容器，并且同步等待每个容器的 postStart。一个慢钩子会拖慢同一 Pod 里排在后面的所有容器。

postStart 失败

把钩子换成一个注册失败的命令：

apiVersion: v1
kind: Pod
metadata:
  name: poststart-fail
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo \"app main $(date +%T)\"; sleep 3600"]
      lifecycle:
        postStart:
          exec:
            command: ["sh", "-c", "echo 'cannot register to config center' >&2; exit 1"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}

32 秒后：

NAME             READY   STATUS              RESTARTS   AGE
poststart-fail   0/1     ContainerCreating   0          32s
TIME                   COUNT    TYPE      REASON                MSG
2026-10-13T03:31:59Z   1        Normal    Created               Created container app
2026-10-13T03:32:00Z   1        Normal    Started               Started container app
2026-10-13T03:32:00Z   1        Warning   FailedPostStartHook   PostStartHook failed
2026-10-13T03:32:00Z   1        Normal    Killing               FailedPostStartHook

钩子在 03:32:00 失败，同一秒就发出了 Killing，但半分钟后容器状态仍是 ContainerCreating，RESTARTS 是 0，logs --previous 报 previous terminated container "app" ... not found，state 里也只有 {"waiting":{"reason":"ContainerCreating"}}，没有任何错误信息，这时能看到的只有 FailedPostStartHook 事件。再过半分钟多：

NAME             READY   STATUS               RESTARTS   AGE
poststart-fail   0/1     PostStartHookError   0          69s
TIME                   COUNT    TYPE      REASON                MSG
2026-10-13T03:32:34Z   2        Normal    Pulled                Container image "busybox:1.36" already present on machine
2026-10-13T03:32:35Z   2        Normal    Created               Created container app
2026-10-13T03:32:35Z   2        Normal    Started               Started container app
2026-10-13T03:32:35Z   2        Warning   FailedPostStartHook   PostStartHook failed
2026-10-13T03:32:35Z   2        Normal    Killing               FailedPostStartHook

now={"waiting":{"message":"Exec lifecycle hook ([sh -c echo 'cannot register to config center' \u003e\u00262; exit 1]) for Container \"app\" in Pod \"poststart-fail_notes-lab(a760cfb1-...)\" failed - error: command 'sh -c echo 'cannot register to config center' \u003e\u00262; exit 1' exited with 1: cannot register to config center\n, message: \"cannot register to config center\\n\"","reason":"PostStartHookError"}}

两个发现：

  1. 「杀掉容器」走的是正常的终止流程，带宽限期。 第一个实例 03:32:00 启动、03:32:30 才结束，退出码 137：作为 PID 1 的 sh 不处理 SIGTERM，等满默认的 30 秒宽限期后被 SIGKILL。把 terminationGracePeriodSeconds 改成 5 再测，同样的过程变成 03:34:49 启动、03:34:54 结束。也就是说 postStart 失败后的「杀掉」就是普通的终止：先 SIGTERM，宽限期到了才 SIGKILL。这里用满了整个宽限期，只是因为这个 sh 忽略 SIGTERM；能正确处理 SIGTERM 的程序会更快退出。在它退出之前，容器处于「已经失败但还没死」的状态，Pod 看起来一直卡在 ContainerCreating。
  2. 钩子的输出不在事件里。 事件只写了固定的 PostStartHook failed，钩子打印的 cannot register to config center 出现在容器状态的 state.waiting.message 中。这是 kubelet 有意为之：v1.31 的 kuberuntime_container.go 在记录这条事件的地方注释写着 do not record the message in the event so that secrets won't leak from the server，preStop 失败的事件 PreStopHook failed 也一样。排查 postStart 失败时可以看 kubectl get pod -o jsonpath='{.status.containerStatuses[0].state.waiting.message}'，但这条消息要等第一个实例被杀掉之后才会出现；在那之前只能看到 FailedPostStartHook 事件，具体原因要等。

69 秒时看到的其实已经是第二轮：事件计数变成了 2，第二个实例 03:32:35 启动，钩子又失败，又进入了 30 秒的宽限期。state.waiting 里的 PostStartHookError 和 RESTARTS 仍为 0 都是这个中间状态的样子：lastState 已经记下了第一个实例的退出，restartCount 还没跟上。到 2 分 21 秒时 RESTARTS 变成 2、状态进入 CrashLoopBackOff；宽限期 5 秒那次也是先看到 lastState、过一会儿 restartCount 才变成 1。为什么计数会滞后这次没有查源码，看重启次数时知道有这种中间状态就行。

preStop

preStop 是删除时的对应钩子：kubelet 先执行 preStop，结束后才向主进程发 SIGTERM，两者共用 terminationGracePeriodSeconds。它和 EndpointSlice 摘除、SIGTERM、SIGKILL 之间的时间线，以及滚动更新时有无 preStop 的失败请求数，已经在优雅终止与流量排空里逐项测过，这里不重复。上面 sidecar 的关闭顺序可以和那篇放在一起看：sidecar 的 SIGTERM 排在应用完全退出之后，应用的 preStop 和收尾时间都会推迟 sidecar 的终止。

把退出原因写进状态：terminationMessage

容器退出时，kubelet 会读取 terminationMessagePath（默认 /dev/termination-log）指向的文件，把内容放进 state.terminated.message。这样即使日志已经随容器一起被清理，或者日志系统里混了太多输出，kubectl describe 和监控系统也能直接拿到一句退出原因。三个对比，保存为 termmsg.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: tm-file
spec:
  restartPolicy: Never
  containers:
    - name: app
      image: busybox:1.36
      terminationMessagePath: /tmp/why
      command: ["sh", "-c", "echo 'loading...'; echo 'config key DB_URL missing' > /tmp/why; exit 2"]
---
apiVersion: v1
kind: Pod
metadata:
  name: tm-default
spec:
  restartPolicy: Never
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo 'loading...'; echo 'panic: DB_URL missing' >&2; exit 3"]
---
apiVersion: v1
kind: Pod
metadata:
  name: tm-fallback
spec:
  restartPolicy: Never
  containers:
    - name: app
      image: busybox:1.36
      terminationMessagePolicy: FallbackToLogsOnError
      command: ["sh", "-c", "echo 'loading...'; echo 'panic: DB_URL missing' >&2; exit 3"]

三个 Pod 都是 restartPolicy: Never，退出后：

tm-file: exit=2 reason=Error message=config key DB_URL missing

tm-default: exit=3 reason=Error message=
tm-fallback: exit=3 reason=Error message=loading...
panic: DB_URL missing

$ kubectl -n notes-lab describe pod tm-fallback
    State:      Terminated
      Reason:   Error
      Message:  loading...
panic: DB_URL missing

      Exit Code:    3
  • 默认策略 File 只认文件。程序只往 stderr 打了错误，message= 后面就是空的。
  • FallbackToLogsOnError 在文件为空且容器以错误退出时，取日志的最后一段（上限 2048 字节或 80 行，取较小者），stdout 和 stderr 都会包含进来，所以 loading... 也在里面。对没法改代码的程序，这一行配置就能让 describe 直接显示崩溃原因。
  • 自定义路径要在 Pod 创建时就确定，创建后不能修改。单条消息超过 4096 字节会被截断，同一个 Pod 内所有容器（含 init 容器）的终止消息合计不超过 12 KiB，按容器数平分，比如 12 个容器时每个只有 1024 字节。

小结

  • condition 的顺序是 PodScheduled → PodReadyToStartContainers → Initialized → ContainersReady → Ready。init 期间 phase 一直是 Pending，init 卡住时不要只看 phase。
  • init 失败：restartPolicy: Always 无限重试，phase 保持 Pending；Never 直接让 Pod 进入 Failed。
  • 应用容器重启不会重跑 init；沙箱重建（事件 SandboxChanged）会让所有 init 从头再跑一遍，emptyDir 里的旧数据还在，init 必须幂等。
  • sidecar 按清单顺序启动，启动（或 startupProbe 通过）即放行后面的容器；删除时等应用退出后倒序停止；崩溃时无视 restartPolicy: Never 照样重启，STATUS 会显示 Init:Error，但应用可能完全正常。
  • postStart 会阻塞同一 Pod 里排在后面的容器；失败后容器走普通的终止流程（SIGTERM，宽限期到了再 SIGKILL），不处理 SIGTERM 的进程会拖满整个宽限期；错误详情不在事件里，要等第一个实例被杀后才出现在 state.waiting.message 中。
  • 程序退出前写 /dev/termination-log，或者设置 FallbackToLogsOnError，退出原因就会出现在 Pod 状态里。

清理

kubectl delete namespace notes-lab
