让副本分散到不同节点

Pod 亲和与反亲和 能表达“靠近”或“避开”其他 Pod；拓扑分布约束直接描述同类 Pod 在节点或可用区之间允许有多大数量差。它只影响调度，不能保证节点故障后的服务可用性；服务副本、容量和 PodDisruptionBudget 仍需分别设计。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0；containerd 1.7.18、CNI 为 Calico 是这个集群的已知配置，本篇没有单独核对），节点名简化成 control-plane、worker、worker2，实验放在单独的 notes-lab namespace 里。control-plane 带 kubeadm 默认的 node-role.kubernetes.io/control-plane:NoSchedule 污点，可调度的只有两个 worker。kind 节点没有 topology.kubernetes.io/zone 标签，为了模拟两个可用区，给两个 worker 临时打上 notes-lab.io/zone=a 和 notes-lab.io/zone=b，实验结束后删除。调度器怎么过滤、怎么读 0/3 nodes are available 这类消息，见 Pod 调度与节点选择，这里不再重复。

kubectl label node worker  notes-lab.io/zone=a
kubectl label node worker2 notes-lab.io/zone=b

skew 怎么算

一条约束的核心是四个字段：

  • topologyKey：按哪个节点标签划分拓扑域，标签值相同的节点属于同一个域。
  • labelSelector：数哪些 Pod。每个域里有多少个匹配这个选择器的 Pod，就是这个域的计数。
  • maxSkew：把待调度 Pod 放进某个域之后，「该域计数 − 所有合格域里的最小计数」不能超过这个值。
  • whenUnsatisfiable：DoNotSchedule（默认）是硬约束，找不到满足的节点就 Pending；ScheduleAnyway 只在打分时偏向偏差小的节点。

关键在「所有合格域里的最小计数」：哪些域算合格，由 nodeAffinityPolicy 和 nodeTaintsPolicy 决定，而它们的默认值并不对称。下面第一个实验就栽在这里。

按主机名打散：第 3 个副本 Pending

旧版本这篇笔记的示例是 2 副本、按 kubernetes.io/hostname 打散，在这个集群上确实成功了。把副本数改成 3，保存为 host-spread.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: host-spread
spec:
  replicas: 3
  selector:
    matchLabels: {app: host-spread}
  template:
    metadata:
      labels: {app: host-spread}
    spec:
      terminationGracePeriodSeconds: 0
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels: {app: host-spread}
      containers:
        - name: app
          image: busybox:1.36
          command: ["sleep", "3600"]
          resources:
            requests: {cpu: 10m, memory: 16Mi}
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f host-spread.yaml
kubectl -n notes-lab get pods -l app=host-spread -o wide
NAME                           READY   STATUS    RESTARTS   AGE   NODE
host-spread-75ff4d448d-2q42l   1/1     Running   0          8s    worker
host-spread-75ff4d448d-4zx99   0/1     Pending   0          8s    <none>
host-spread-75ff4d448d-cdbtz   1/1     Running   0          8s    worker2

两个 worker 各一个，第 3 个一直 Pending。资源显然够，事件是这样的：

Warning  FailedScheduling  11s   default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) didn't match pod topology spread constraints. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

两个 worker 都因为分布约束被拒。按上面的公式算一下：nodeTaintsPolicy 不写时等同于 Ignore，即计算 skew 时不看污点，control-plane 也是一个合格的拓扑域，里面的计数永远是 0（Pod 根本上不去）。于是最小计数恒为 0，第 3 个 Pod 放到任何一个 worker 上，该域计数都变成 2，2 − 0 = 2 > 1。control-plane 本身则在污点过滤那一步就被排除了，所以三个节点都不行。

按主机名打散时，只要集群里有满足 Pod 节点亲和、带拓扑键，却因为污点上不去、身上也没有匹配 Pod 的节点，硬约束就会把副本数卡在「可用节点数 × maxSkew」上，这是官方文档 Known limitations 里那句「Pods matched on tainted nodes are respected」（Issue 80921）的一个具体表现。因资源不足等其他过滤条件上不去的节点，按源码推测同理，本次未测。被 nodeSelector/节点亲和排除的节点则不受影响，默认 nodeAffinityPolicy: Honor 不会把它们算进来（见下一节）。2 副本能跑，只是因为恰好每个 worker 一个，没碰到上限。

nodeTaintsPolicy: Honor

在约束里加一行，让计算 skew 时也遵守污点：只有没有污点、或者 Pod 容忍了污点的节点才算合格域。

- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: DoNotSchedule
  nodeTaintsPolicy: Honor
  labelSelector:
    matchLabels: {app: host-spread}

删掉旧 Deployment 重新 apply，3 个副本全部调度成功；再扩到 5：

kubectl -n notes-lab scale deploy host-spread --replicas=5
kubectl -n notes-lab get pods -l app=host-spread -o wide
NAME                           READY   STATUS    RESTARTS   AGE   NODE
host-spread-7667558445-bz4kp   1/1     Running   0          16s   worker
host-spread-7667558445-d2m4v   1/1     Running   0          16s   worker
host-spread-7667558445-h79cj   1/1     Running   0          8s    worker2
host-spread-7667558445-t52mc   1/1     Running   0          8s    worker
host-spread-7667558445-zkf55   1/1     Running   0          16s   worker2

3 比 2，偏差 1，符合约束。control-plane 不再参与计算。

ScheduleAnyway 不会 Pending

把第一份配置（不带 nodeTaintsPolicy）的 whenUnsatisfiable 改成 ScheduleAnyway，3 个副本立即全部调度，扩到 6 个后是 3 比 3：

NAME                           READY   STATUS    RESTARTS   AGE   NODE
host-spread-8447c9df65-24qjv   1/1     Running   0          16s   worker2
host-spread-8447c9df65-5x7nh   1/1     Running   0          8s    worker2
host-spread-8447c9df65-7c7qb   1/1     Running   0          8s    worker
host-spread-8447c9df65-cwxz2   1/1     Running   0          16s   worker2
host-spread-8447c9df65-jqdzl   1/1     Running   0          16s   worker
host-spread-8447c9df65-srwkk   1/1     Running   0          8s    worker

软约束只参与打分，而打分只针对通过过滤的节点：control-plane 在污点过滤那一步就被排除，根本不参与打分。按主机名打散时，每个候选节点的得分只取决于它自己身上已有多少匹配的 Pod，再在候选节点之间归一化，打分阶段没有「全局最小值」，所以 Pod 不会无处可去。这次刚好均匀，但这只是打分的结果，节点资源或其他打分插件的权重变化时，ScheduleAnyway 不保证任何偏差上限。

nodeAffinityPolicy：默认是 Honor

和污点相反，节点亲和性默认是被遵守的：Pod 写了 nodeSelector 或 nodeAffinity 时，不匹配的节点不计入 skew。用一个只允许去 zone a 的 Deployment 验证，保存为 zone-a-only.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: zone-a-only
spec:
  replicas: 3
  selector:
    matchLabels: {app: zone-a-only}
  template:
    metadata:
      labels: {app: zone-a-only}
    spec:
      terminationGracePeriodSeconds: 0
      nodeSelector:
        notes-lab.io/zone: a
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: notes-lab.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels: {app: zone-a-only}
      containers:
        - name: app
          image: busybox:1.36
          command: ["sleep", "3600"]
          resources:
            requests: {cpu: 10m, memory: 16Mi}
NAME                           READY   STATUS              RESTARTS   AGE   NODE
zone-a-only-77c9895668-4fgx2   0/1     ContainerCreating   0          8s    worker
zone-a-only-77c9895668-k6dzk   0/1     ContainerCreating   0          8s    worker
zone-a-only-77c9895668-t7jdr   0/1     ContainerCreating   0          8s    worker

3 个全在 worker，没有违反约束：zone b 被 nodeSelector 排除，合格域只剩 a 一个，单个域没有偏差可言。在约束里加上 nodeAffinityPolicy: Ignore 再跑一次：

NAME                           READY   STATUS    RESTARTS   AGE   NODE
zone-a-only-76f6cb7fdf-226j2   1/1     Running   0          8s    worker
zone-a-only-76f6cb7fdf-ps7zb   0/1     Pending   0          8s    <none>
zone-a-only-76f6cb7fdf-vtvg5   0/1     Pending   0          8s    <none>
Warning  FailedScheduling  8s    default-scheduler  0/3 nodes are available: 1 node(s) didn't match Pod's node affinity/selector, 1 node(s) didn't match pod topology spread constraints, 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }. preemption: 0/3 nodes are available: 1 No preemption victims found for incoming pod, 2 Preemption is not helpful for scheduling.

现在 zone b 也算合格域，计数恒为 0，zone a 放第 2 个就是 2 − 0 > 1。消息里三个节点各占一个原因：worker2 不匹配 nodeSelector，worker 违反分布约束，control-plane 有污点。

两个策略合起来记：nodeAffinityPolicy 默认 Honor，nodeTaintsPolicy 默认 Ignore。两个字段在 v1.26 起为 beta 并默认开启（特性门控 NodeInclusionPolicyInPodTopologySpread），v1.31 里仍是 beta；按当前官方文档，两者在 v1.33 GA。集群里有专用节点池、带污点的 GPU 节点或者控制平面节点时，按主机名或可用区做硬打散，基本都应该显式写上 nodeTaintsPolicy: Honor。

labelSelector 必须选中自己

labelSelector 数的是匹配选择器的 Pod，和这条约束写在谁身上无关。故意写错：先用一个 Deployment other 在 zone a 放 2 个 app=other 的 Pod，再部署 4 副本的 web，它的约束误写成数 app=other：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 4
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      terminationGracePeriodSeconds: 0
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: notes-lab.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels: {app: other}   # 写错：没有匹配自己的 Pod
      containers:
        - name: app
          image: busybox:1.36
          command: ["sleep", "3600"]
          resources:
            requests: {cpu: 10m, memory: 16Mi}
kubectl -n notes-lab get pods -o wide -L app
NAME                     READY   STATUS              RESTARTS   AGE   NODE      APP
other-74c65bf67b-cqnhz   1/1     Running             0          14s   worker    other
other-74c65bf67b-jv9pk   1/1     Running             0          14s   worker    other
web-758bc78b4b-c5246     0/1     ContainerCreating   0          8s    worker2   web
web-758bc78b4b-gvlnf     0/1     ContainerCreating   0          8s    worker2   web
web-758bc78b4b-m8vjh     0/1     ContainerCreating   0          8s    worker2   web
web-758bc78b4b-vlxpr     0/1     ContainerCreating   0          8s    worker2   web

4 个 web 全部挤在 worker2。对 web 来说，计数是 zone a 有 2 个（other）、zone b 有 0 个，而它自己不匹配选择器，放到哪里都不会改变计数。所以放 zone b 永远是 0 − 0，放 zone a 永远是 2 − 0，2 > 1，zone a 被过滤，只剩 b。约束「满足」了，web 自己的分布却是 0 比 4。

kubectl apply 对这种写法没有任何提示。只有完全不写 labelSelector 时，API Server 才给出警告。下面是对一个不带 labelSelector 的裸 Pod 做 kubectl apply --dry-run=server 的输出：

Warning: spec.topologySpreadConstraints[0].labelSelector: a null labelSelector results in matching no pod

写约束时，labelSelector 最好直接照抄 Pod 模板的标签（通常和 Deployment 的 spec.selector 一致）。排查分布不均时，先拿约束里的选择器去 kubectl get pods -l ... -o wide 数一遍，看数到的是不是你以为的那批 Pod。

节点缺少拓扑标签

DoNotSchedule 约束下，没有 topologyKey 标签的节点会被直接跳过。只给 worker 打一个 notes-lab.io/rack=r1，worker2 不打，然后部署 4 副本、按 notes-lab.io/rack 打散的 rack（结构同上，topologyKey 换成 notes-lab.io/rack）：

NAME                    READY   STATUS              RESTARTS   AGE   NODE
rack-867b8b48cc-l6g7m   0/1     ContainerCreating   0          8s    worker
rack-867b8b48cc-m4nf9   0/1     ContainerCreating   0          8s    worker
rack-867b8b48cc-sdwj7   0/1     ContainerCreating   0          8s    worker
rack-867b8b48cc-t2dqg   0/1     ContainerCreating   0          8s    worker

4 个都在 worker：只有一个域，偏差为 0，worker2 根本不是候选。要看到它为什么被排除，单独提交一个 Pod rack-pin：标签为 app=rack-pin，用 nodeSelector 钉到 worker2，约束同样按 notes-lab.io/rack 打散、选择器是自己的 app=rack-pin：

Warning  FailedScheduling  5s    default-scheduler  0/3 nodes are available: 1 node(s) didn't match Pod's node affinity/selector, 1 node(s) didn't match pod topology spread constraints (missing required label), 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

(missing required label) 就是这个原因的标志。实际集群里更常见的情况是新加的节点池忘了打 zone 标签，或者标签键拼错了，这批节点会被所有带硬分布约束的工作负载默默绕开，资源闲着、别的节点却越来越挤。Pod 写了多条约束时，节点要同时带齐所有 topologyKey 才会被考虑。

minDomains：域不够就当最小值为 0

minDomains 要求合格域至少有这么多个；不够时，调度器把「最小计数」当成 0 来算 skew。它在 v1.30 已经 GA，v1.31 直接可用，且只能和 DoNotSchedule 一起用。在 zone 约束上加 minDomains: 3，而集群只有 a、b 两个 zone，部署 3 副本：

topologySpreadConstraints:
  - maxSkew: 1
    minDomains: 3
    topologyKey: notes-lab.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels: {app: mindom}
NAME                      READY   STATUS              RESTARTS   AGE   NODE
mindom-7b6cd8b498-472qr   0/1     ContainerCreating   0          8s    worker
mindom-7b6cd8b498-k26l7   0/1     Pending             0          8s    <none>
mindom-7b6cd8b498-mhd5q   0/1     ContainerCreating   0          8s    worker2
Warning  FailedScheduling  12s               default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) didn't match pod topology spread constraints. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

每个 zone 1 个之后，第 3 个放哪都是 2 − 0 = 2。同一份配置删掉 minDomains 再部署，3 个副本全部调度（worker 1 个、worker2 2 个）。注意消息和前面 control-plane 污点那次一模一样，看不出是 minDomains 造成的，只能回头核对约束和合格域的数量。

minDomains 的用途是在跨区集群里给「至少分到几个区」兜底：区不够时宁可 Pending，配合能感知分布约束的集群自动扩缩容去补节点。小集群里随手写上，效果就是副本数被卡在「域数 × maxSkew」。和 ScheduleAnyway 组合会被直接拒绝：

The Deployment "mindom" is invalid: spec.template.spec.topologySpreadConstraints[0].minDomains: Invalid value: 3: can only use minDomains if whenUnsatisfiable=DoNotSchedule, not ScheduleAnyway

滚动更新：新旧 Pod 混在一起算

Deployment 滚动更新期间，新旧两个 ReplicaSet 的 Pod 带着同样的 app 标签，约束会把它们一起数。为了让效果明显，v1 故意用 nodeSelector 把 4 个副本全放在 zone a（默认 nodeAffinityPolicy: Honor，合格域只有 a，不违反约束），然后 v2 去掉 nodeSelector，看新 Pod 落在哪里。保存为 roll.yaml：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: roll
spec:
  replicas: 4
  selector:
    matchLabels: {app: roll}
  template:
    metadata:
      labels: {app: roll}
    spec:
      terminationGracePeriodSeconds: 0
      nodeSelector:
        notes-lab.io/zone: a
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: notes-lab.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels: {app: roll}
      containers:
        - name: app
          image: busybox:1.36
          command: ["sleep", "3600"]
          resources:
            requests: {cpu: 10m, memory: 16Mi}
kubectl -n notes-lab apply -f roll.yaml
kubectl -n notes-lab rollout status deploy roll --timeout=120s
kubectl -n notes-lab patch deploy roll --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/nodeSelector"}]'
kubectl -n notes-lab rollout status deploy roll --timeout=180s
kubectl -n notes-lab get pods -l app=roll \
  -o custom-columns=NAME:.metadata.name,HASH:.metadata.labels.pod-template-hash,NODE:.spec.nodeName,PHASE:.status.phase

roll-545957c444-l7b9s   545957c444   worker2   Running
roll-545957c444-prfrm   545957c444   worker2   Running

1 比 3，偏差 2，比约束允许的大。删掉重做一次，结果还是 1 比 3。原因是新 Pod 调度时，还在 zone a 上的旧 Pod 也算在计数里：第一批新 Pod 调度时，zone a 上还有 3 到 4 个旧 Pod（调度器不计已标记删除的 Pod，而旧 ReplicaSet 在同一秒从 4 缩到了 3，确切是几个属于推测），b 是 0，只能进 b；等旧 Pod 陆续删光，b 已经多出来了，而已经运行的 Pod 不会被挪动。每一步调度都满足约束，最终结果却不满足。

matchLabelKeys 解决的就是这个问题：列在里面的标签键，会取待调度 Pod 自己的值，和 labelSelector 做 AND。Deployment 控制器给每个版本的 Pod 打了不同的 pod-template-hash，用它就能只数同版本的 Pod：

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: notes-lab.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels: {app: roll}
    matchLabelKeys:
      - pod-template-hash

同样的 v1 → v2 过程：

NAME                   HASH        NODE      PHASE
roll-8cbdf4688-4lb44   8cbdf4688   worker2   Running
roll-8cbdf4688-4q9z7   8cbdf4688   worker2   Running
roll-8cbdf4688-6xck8   8cbdf4688   worker    Running
roll-8cbdf4688-dwds6   8cbdf4688   worker    Running

2 比 2。查看运行中的 Pod，存进去的约束还是原样，labelSelector 里没有被并入 pod-template-hash：

[{"labelSelector":{"matchLabels":{"app":"roll"}},"matchLabelKeys":["pod-template-hash"],"maxSkew":1,"topologyKey":"notes-lab.io/zone","whenUnsatisfiable":"DoNotSchedule"}]

v1.31 里 matchLabelKeys 是 beta 并默认开启（v1.27 起，特性门控 MatchLabelKeysInPodTopologySpread），由调度器在计算时取值。从 v1.34 起改为由 kube-apiserver 在创建 Pod 时把对应键值显式并入 labelSelector，可以通过关闭 kube-apiserver 的特性门控 MatchLabelKeysInPodTopologySpreadSelectorMerge 回到旧行为，所以在 v1.34 及以后的集群上看到的 Pod 规格会不一样。同一个键不能同时出现在 matchLabelKeys 和 labelSelector 里，也不能在没有 labelSelector 时单独使用。

只在调度时生效

约束只在 Pod 被调度的那一刻检查，之后集群怎么变，已经运行的 Pod 都不会动。这一节紧接 rack-pin 之后做，接着上面 rack 的场景：4 个副本都在 worker（rack r1）时，给 worker2 打上 notes-lab.io/rack=r2：

kubectl label node worker2 notes-lab.io/rack=r2
# 45 秒后
kubectl -n notes-lab get pods -l app=rack -o wide
NAME                    READY   STATUS    RESTARTS   AGE   NODE
rack-867b8b48cc-l6g7m   1/1     Running   0          69s   worker
rack-867b8b48cc-m4nf9   1/1     Running   0          69s   worker
rack-867b8b48cc-sdwj7   1/1     Running   0          69s   worker
rack-867b8b48cc-t2dqg   1/1     Running   0          69s   worker

现在是两个域、4 比 0，远超 maxSkew: 1，但没有任何 Pod 被驱逐或迁移。扩到 6 个，新增的 2 个都去了 worker2，变成 4 比 2，新 Pod 是按约束放的，旧的不平衡还留着。

缩容同样不看约束。从这个 4 比 2 缩到 3，做了两次，结果完全不同：

  • 第一次在扩容后十几秒就缩容，worker2 上两个新 Pod 还没启动（事件显示缩容在 04:39:40，它们的容器 04:39:52 才 Created）。它们的 phase 还是 Pending，ReplicaSet 按 phase 排序时先删 Pending 的，两个新 Pod 加一个 worker 上的被删掉，剩下 3 比 0。
  • 第二次先删掉 Deployment，按同样步骤重新造出 4 比 2，等 rollout status 完成、6 个都就绪后再缩，删掉的是 worker 上的 3 个，剩下 1 比 2。
NAME                    READY   STATUS    RESTARTS   AGE   NODE
rack-867b8b48cc-dwgd9   1/1     Running   0          13s   worker2
rack-867b8b48cc-lz79k   1/1     Running   0          13s   worker2
rack-867b8b48cc-x9w9g   1/1     Running   0          34s   worker

第二次看起来像是「顺手平衡」了，其实是 ReplicaSet 自己的删除排序（v1.31 controller_utils.go 的 ActivePodsWithRanks）：依次是未调度的先删、phase 为 Pending 的先于 Running、未就绪的先于就绪，再看 pod-deletion-cost 注解，然后优先删所在节点上同一 Deployment 的活跃 Pod 较多的（计数用 IsPodActive，不要求就绪），再往后依次比较就绪时长（对数分桶）、重启次数、创建时间。它比较的是节点，并不知道约束里的 topologyKey；按 zone 打散、一个 zone 里有多个节点时，这个排序就帮不上忙，这种情况本次没有测。官方文档的说法是缩容可能导致分布不均，需要再平衡时用 Descheduler 这类工具；也可以手动删掉多出来那一侧的 Pod，让控制器重建时按约束重新调度。
