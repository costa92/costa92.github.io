“副本没增加”先分成两类

HPA 水平扩缩容那篇看的是正常情况下扩缩的时间线。这一篇反过来，专门把 HPA 弄坏，看它坏的时候都留下了什么线索。

看到 Pod 数没涨，先分清是哪一种：HPA 没有提高期望副本数，还是期望副本已经提高了，新 Pod 却没跑起来。前一种去看 HPA 自己的 Conditions 和事件，后一种去看 ReplicaSet 和 Pod 的事件。HPA 只负责改 spec.replicas，改完之后的事它不管，也基本不报错。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico，一个 control-plane 加 worker、worker2 两个工作节点），装好了 Metrics Server，实验放在单独的 notes-lab namespace 里。时间都是 UTC。

被扩缩的服务和 HPA 水平扩缩容里的 burn 相同：busybox httpd 加一个 CGI 脚本，每个请求空转一段循环，CPU request 100m、limit 200m。保存为 burn.yaml：

apiVersion: v1
kind: ConfigMap
metadata:
  name: burn-cgi
data:
  burn: |
    #!/bin/sh
    i=0
    while [ $i -lt 30000 ]; do i=$((i+1)); done
    echo "Content-Type: text/plain"
    echo
    echo "ok $(hostname)"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: burn
spec:
  replicas: 1
  selector:
    matchLabels:
      app: burn
  template:
    metadata:
      labels:
        app: burn
    spec:
      containers:
        - name: web
          image: busybox:1.36
          command: ["httpd", "-f", "-p", "8080", "-h", "/www"]
          ports:
            - containerPort: 8080
          readinessProbe:
            tcpSocket:
              port: 8080
            periodSeconds: 2
          resources:
            requests:
              cpu: 100m
              memory: 16Mi
            limits:
              cpu: 200m
              memory: 64Mi
          volumeMounts:
            - name: cgi
              mountPath: /www/cgi-bin
      volumes:
        - name: cgi
          configMap:
            name: burn-cgi
            defaultMode: 0755   # CGI 脚本要有执行权限
---
apiVersion: v1
kind: Service
metadata:
  name: burn
spec:
  selector:
    app: burn
  ports:
    - port: 80
      targetPort: 8080
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f burn.yaml
kubectl -n notes-lab rollout status deploy/burn

为了能逐秒对照，另开一个循环每 5 秒打印一行 HPA 和 Deployment 的状态：

while true; do
  echo "$(date -u +%T) $(kubectl -n notes-lab get hpa burn -o jsonpath='cpu={.status.currentMetrics[0].resource.current.averageUtilization}%/{.spec.metrics[0].resource.target.averageUtilization}% cur={.status.currentReplicas} desired={.status.desiredReplicas} {range .status.conditions[*]}{.type}={.reason} {end}') $(kubectl -n notes-lab get deploy burn -o jsonpath='spec={.spec.replicas} status={.status.replicas} ready={.status.readyReplicas}')"
  sleep 5
done

burn 的 HPA 到”有指标，期望副本仍不变”一节才创建（kubectl -n notes-lab apply -f hpa-burn.yaml），之前的几个实验都用别的 HPA。它用 autoscaling/v2，最多 3 个副本，缩容稳定窗口缩短到 60 秒，目标先写成 300%，后面的实验再按需修改：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: burn
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: burn
  minReplicas: 1
  maxReplicas: 3
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 300
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60

cur 是 HPA 认为的当前副本数，desired 是它算出的期望副本数，后面三列是 Deployment 的 spec.replicas、实际存在的 Pod 数和就绪数。后面几个故障的关键，就在这几列对不上的地方。

第一站：Metrics API 本身

HPA 的 CPU 指标来自 metrics.k8s.io，由 Metrics Server 提供。先确认这条链路是通的，只读两条命令：

$ kubectl get apiservice v1beta1.metrics.k8s.io
NAME                     SERVICE                      AVAILABLE   AGE
v1beta1.metrics.k8s.io   kube-system/metrics-server   True        57d
$ kubectl get apiservice v1beta1.metrics.k8s.io -o jsonpath="{range .status.conditions[*]}{.type}={.status} {.reason}: {.message}{\"\n\"}{end}"
Available=True Passed: all checks passed

AVAILABLE 为 False 时，message 里会写聚合层连不上 Metrics Server 的原因，这时整个集群里用 Resource / ContainerResource 指标的 HPA 都会是 <unknown>，kubectl top 也会失败；走 custom/external metrics API 的指标不经过 Metrics Server，不受这一条影响。再直接读一个 namespace 的原始数据：

kubectl get --raw /apis/metrics.k8s.io/v1beta1/namespaces/notes-lab/pods

namespace 刚建好、还没有 Pod 时，返回的是一个空列表。有一个细节要注意：对一个根本不存在的 namespace 发同样的请求，返回也一模一样，不报错：

{"kind":"PodMetricsList","apiVersion":"metrics.k8s.io/v1beta1","metadata":{},"items":[]}

所以 items 为空不能说明 Metrics Server 坏了，先确认 namespace 名有没有拼错、里面有没有在跑的 Pod。部署好服务后再读一次，每个容器都有自己的数（这是后面实验进行中的读数，nores、sidecar 是下一节创建的）：

$ kubectl get --raw /apis/metrics.k8s.io/v1beta1/namespaces/notes-lab/pods | python3 -m json.tool | grep -E "\"name\"|cpu"
                "name": "burn-5c877494c8-q5kcd",
                    "name": "web",
                        "cpu": "191129n",
                "name": "nores-7d494d6f7-6kfpf",
                    "name": "nginx",
                        "cpu": "0",
                "name": "sidecar-6fd465ddb9-kjvgk",
                    "name": "log-agent",
                        "cpu": "24337n",
                    "name": "web",
                        "cpu": "0",

单位 n 是纳核，191129n 约等于 0.19m。这个集群的 Metrics Server 参数里有 --metric-resolution=15s，也就是每 15 秒向 kubelet 采一次。这一层通了，后面的 <unknown> 就不该再怀疑 Metrics Server。

<unknown> 的三种来源

TARGETS 显示 <unknown> 是最常见的”不扩容”现象，但它只说明这一轮没算出指标，原因要看 Conditions 里哪一行是 False。下面三种情况 get hpa 看起来一样，Conditions 完全不同。

scaleTargetRef 写错：AbleToScale=False

把目标名 burn 错写成 brun：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: burn-typo
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: brun
  minReplicas: 1
  maxReplicas: 3
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
NAME        REFERENCE         TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
burn-typo   Deployment/brun   cpu: <unknown>/50%   1         3         0          40s
Deployment pods:                                       0 current / 0 desired
Conditions:
  Type         Status  Reason          Message
  ----         ------  ------          -------
  AbleToScale  False   FailedGetScale  the HPA controller was unable to get the target's current scale: deployments/scale.apps "brun" not found
Events:
  Type     Reason          Age                From                       Message
  ----     ------          ----               ----                       -------
  Warning  FailedGetScale  10s (x2 over 25s)  horizontal-pod-autoscaler  deployments/scale.apps "brun" not found

REPLICAS 是 0，Conditions 只有 AbleToScale 一行，ScalingActive 都没出现：控制器拿不到目标的 scale 子资源，后面的指标读取根本没开始。kubectl apply 不会校验目标存不存在，HPA 照样创建成功。

把名字改对、apiVersion 写成 v1（Deployment 实际在 apps/v1），报错换了一种：

AbleToScale  False   FailedGetScale  the HPA controller was unable to get the target's current scale: no matches for kind "Deployment" in group ""

group "" 指的是核心组，也就是 v1。看到 FailedGetScale，逐字核对 scaleTargetRef 的三个字段。

容器缺 CPU request：ScalingActive=False FailedGetResourceMetric

这一种在 HPA 水平扩缩容里已经复现过（nores 单容器不写 resources，sidecar 的日志容器没写 request）。这里只补两处那篇没有展开的地方。实验对象同样是两个：nores 用 kubectl create deployment nores --image=nginx:alpine 创建，完全不写 resources；sidecar 保存为 sidecar.yaml，web 写了 request，log-agent 没写：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: sidecar
spec:
  replicas: 1
  selector:
    matchLabels:
      app: sidecar
  template:
    metadata:
      labels:
        app: sidecar
    spec:
      containers:
        - name: web
          image: nginx:alpine
          resources:
            requests:
              cpu: 50m
        - name: log-agent
          image: busybox:1.36
          command: ["sh", "-c", "trap 'exit 0' TERM; while true; do sleep 1; done"]
kubectl -n notes-lab create deployment nores --image=nginx:alpine
kubectl -n notes-lab apply -f sidecar.yaml
kubectl -n notes-lab autoscale deployment nores --cpu-percent=50 --min=1 --max=3
kubectl -n notes-lab autoscale deployment sidecar --cpu-percent=50 --min=1 --max=3

第一处是 -o yaml 里的状态。describe 会把字段排版好，原始 status 能看到两个容易误读的值：

- lastTransitionTime: "2026-10-13T07:04:10Z"
  message: 'the HPA was unable to compute the replica count: failed to get cpu utilization:
    missing request for cpu in container nginx of Pod nores-7d494d6f7-6kfpf'
  reason: FailedGetResourceMetric
  status: "False"
  type: ScalingActive
currentMetrics:
- type: ""
currentReplicas: 1
desiredReplicas: 0

desiredReplicas: 0 不是 HPA 想把服务缩到 0，只是这一轮没算出结果；AbleToScale 仍是 True，Deployment 也一直是 1 个副本。拿 desiredReplicas 写告警的话，这种情况会误报。同一时刻 kubectl top pod -l app=nores 正常输出 0m，再次说明指标链路是好的，缺的是 request。

第二处是修法。多容器 Pod 里只有 sidecar 缺 request 时，除了给 sidecar 补上，还可以让 HPA 只看主容器，改用 ContainerResource（v1.30 起 GA）：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: sidecar
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: sidecar
  minReplicas: 1
  maxReplicas: 3
  metrics:
    - type: ContainerResource
      containerResource:
        name: cpu
        container: web
        target:
          type: Utilization
          averageUtilization: 50

kubectl apply 后 40 秒：

NAME      REFERENCE            TARGETS       MINPODS   MAXPODS   REPLICAS   AGE
sidecar   Deployment/sidecar   cpu: 0%/50%   1         3         1          2m1s
Metrics:                                                                  ( current / target )
  resource cpu of container "web" on pods  (as a percentage of request):  0% (0) / 50%
...
  ScalingActive   True    ValidMetricFound     the HPA was able to successfully calculate a replica count from cpu container resource utilization (percentage of request)

log-agent 依旧没有 request，HPA 已经能算了。这种改法只动 HPA，不触发 Deployment 的滚动更新。代价是 sidecar 的 CPU 不再参与决策，日志代理自己被打满时 HPA 看不到。

目标被缩到 0：ScalingActive=False ScalingDisabled

接着上一步，HPA 已经能正常读到 sidecar 的指标，这时把 Deployment 手动缩到 0：

kubectl -n notes-lab scale deploy sidecar --replicas=0

35 秒后：

NAME      REFERENCE            TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
sidecar   Deployment/sidecar   cpu: <unknown>/50%   1         3         0          2m42s
Deployment pods:                                                          0 current / 0 desired
Conditions:
  Type            Status  Reason              Message
  ----            ------  ------              -------
  AbleToScale     True    SucceededGetScale   the HPA controller was able to get the target's current scale
  ScalingActive   False   ScalingDisabled     scaling is disabled since the replica count of the target is zero
  ScalingLimited  False   DesiredWithinRange  the desired count is within the acceptable range
（事件段略）

minReplicas 是 1，HPA 却没有把它拉回 1，也没有新增事件（按 v1.31 源码 horizontal.go，副本为 0 的这个分支只设置 Condition，不记事件）。这是有意的设计：目标副本为 0 被当成”有人手动停用”，HPA 自己也跟着停下，直到有人把副本改回非 0。上线前为了维护临时缩到 0 的服务，恢复时如果忘了这一点，会以为 HPA 失灵。

补充：刚滚动更新完的几十秒

后面做调度实验时，先给 burn 加了反亲和规则，触发了一次滚动更新，新 Pod 07:17 刚过时起来。负载 07:17:24 开始，HPA 却连着 45 秒算不出指标：

07:17:18 cpu=1%/50% cur=1 desired=1 AbleToScale=ReadyForNewScale ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=1 status=1 ready=1
07:17:23 cpu=%/50% cur=1 desired=1 AbleToScale=SucceededGetScale ScalingActive=FailedGetResourceMetric ScalingLimited=DesiredWithinRange  spec=1 status=1 ready=1
07:18:04 cpu=%/50% cur=1 desired=1 AbleToScale=SucceededGetScale ScalingActive=FailedGetResourceMetric ScalingLimited=DesiredWithinRange  spec=1 status=1 ready=1
07:18:09 cpu=200%/50% cur=1 desired=4 AbleToScale=SucceededRescale ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=4 status=4 ready=1
Warning  FailedGetResourceMetric       53s (x3 over 83s)      horizontal-pod-autoscaler  failed to get cpu utilization: did not receive metrics for targeted pods (pods might be unready)
Warning  FailedComputeMetricsReplicas  53s (x3 over 83s)      horizontal-pod-autoscaler  invalid metrics (1 invalid out of 1), first error is: failed to get cpu resource metric value: failed to get cpu utilization: did not receive metrics for targeted pods (pods might be unready)

观测到的是：从 07:17:23 到 07:18:04 共约 45 秒，ScalingActive 一直是 FailedGetResourceMetric，事件写着 1 invalid out of 1，之后自己恢复。失败从 07:17:23 开始，比负载早一秒，和旧 Pod 进入 Terminating 的时间吻合，所以这段空窗和负载无关，是滚动更新带来的。

原因没有直接测到，下面是按 v1.31 源码 replica_calculator.go 的推测。groupPods 会忽略带删除时间戳的 Pod，正在删除的旧 Pod 先被排除，只剩一个新 Pod。新 Pod 又可能因为两种原因不被采用：

  • 还没有样本：Metrics Server 每 15 秒采一次，新 Pod 刚起来时还没有它的数据。
  • 被当成未就绪：Pod 启动后 --horizontal-pod-autoscaler-cpu-initialization-period（默认 5 分钟）内，如果样本的采集时间早于”变为 Ready 的时刻 + 采样窗口”，这条样本会被丢掉。另一个参数 --horizontal-pod-autoscaler-initial-readiness-delay（默认 30 秒）只对启动已超过这 5 分钟的 Pod 生效，这里的新 Pod 用不上。

不管是哪一种，剩下可用的样本是 0 个，就报 did not receive metrics for targeted pods。这条事件和缺 request 的那条不同，会自己消失，但单副本服务在发布后马上遇到流量高峰时，HPA 会有这么一段完全不动的时间。

有指标，期望副本仍不变

容忍度：高于目标 7% 不扩容

HPA 算的是比值 当前值 / 目标值，比值离 1.0 不超过容忍度时不做任何动作。v1.31 的默认容忍度是 0.1，只能通过 kube-controller-manager 的 --horizontal-pod-autoscaler-tolerance 全局修改；单个 HPA 的容忍度是 v1.33 才引入的（特性门控 HPAConfigurableTolerance：v1.33 alpha，v1.35 beta 但默认关闭，v1.37 GA），字段在 behavior.scaleUp.tolerance 和 behavior.scaleDown.tolerance，两个方向分别设置，v1.31 的 API 里还没有。

这个效果要让负载稳定在一个固定水平才看得清。负载 Pod 只用一个循环串行请求，每次请求后睡 0.3 秒，跑 170 秒后自己退出：

kubectl -n notes-lab apply -f hpa-burn.yaml
kubectl -n notes-lab delete pod load --ignore-not-found
kubectl -n notes-lab run load --image=busybox:1.36 --restart=Never -- sh -c \
  'end=$(($(date +%s)+170)); while [ $(date +%s) -lt $end ]; do wget -qO- http://burn/cgi-bin/burn >/dev/null; sleep 0.3; done; echo done $(date -u +%T)'

HPA 先把目标设成 300%，保证不会扩容，等利用率稳定在 72%～73%；07:08:15 左右改成 68%，07:09:00 左右再改成 60%：

kubectl -n notes-lab patch hpa burn --type=json \
  -p '[{"op":"replace","path":"/spec/metrics/0/resource/target/averageUtilization","value":68}]'
# 45 秒后
kubectl -n notes-lab patch hpa burn --type=json \
  -p '[{"op":"replace","path":"/spec/metrics/0/resource/target/averageUtilization","value":60}]'
07:08:12 cpu=73%/300% cur=1 desired=1 AbleToScale=ReadyForNewScale ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=1 status=1 ready=1
07:08:17 cpu=73%/68% cur=1 desired=1 AbleToScale=ReadyForNewScale ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=1 status=1 ready=1
07:08:58 cpu=73%/68% cur=1 desired=1 AbleToScale=ReadyForNewScale ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=1 status=1 ready=1
07:09:03 cpu=73%/60% cur=1 desired=1 AbleToScale=ReadyForNewScale ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=1 status=1 ready=1
07:09:08 cpu=71%/60% cur=1 desired=2 AbleToScale=SucceededRescale ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=2 status=2 ready=1

目标 68% 时，describe 里清清楚楚写着当前值高于目标，三条 Condition 却全是”正常”：

Metrics:                                               ( current / target )
  resource cpu on pods  (as a percentage of request):  73% (73m) / 68%
...
Deployment pods:       1 current / 1 desired
Conditions:
  Type            Status  Reason              Message
  ----            ------  ------              -------
  AbleToScale     True    ReadyForNewScale    recommended size matches current size
  ScalingActive   True    ValidMetricFound    the HPA was able to successfully calculate a replica count from cpu resource utilization (percentage of request)
  ScalingLimited  False   DesiredWithinRange  the desired count is within the acceptable range
Events:           <none>

这 45 秒里比值是 73 / 68 ≈ 1.07，在 0.9～1.1 之内，HPA 认为”已经够接近目标”，Events 一条都没有。改到 60% 后比值变成 1.22，下一次同步就 ceil(1 × 73 / 60) = 2，扩到 2。

容忍度按比值算，和副本数无关：目标 50% 时，平均利用率要超过 55% 才会扩容。如果服务常年停在”略高于目标”，HPA 不会报任何东西，把目标值调低一点，或者接受这个余量。

稳定窗口：缩容晚一分钟

同一轮里，扩到 2 个副本后串行负载被平摊（总 CPU 没变，每个 Pod 只剩 30% 多），07:09:48 负载退出。这个 HPA 设了 behavior.scaleDown.stabilizationWindowSeconds: 60：

07:09:38 cpu=39%/60% cur=2 desired=2 AbleToScale=ReadyForNewScale ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=2 status=2 ready=2
07:09:53 cpu=32%/60% cur=2 desired=2 AbleToScale=ReadyForNewScale ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=2 status=2 ready=2
07:10:09 cpu=18%/60% cur=2 desired=2 AbleToScale=ScaleDownStabilized ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=2 status=2 ready=2
07:10:24 cpu=1%/60% cur=2 desired=2 AbleToScale=ScaleDownStabilized ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=2 status=2 ready=2
07:10:49 cpu=1%/60% cur=2 desired=2 AbleToScale=ScaleDownStabilized ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=2 status=2 ready=2
07:10:54 cpu=1%/60% cur=2 desired=1 AbleToScale=SucceededRescale ScalingActive=ValidMetricFound ScalingLimited=DesiredWithinRange  spec=1 status=1 ready=1

39% 和 32% 时还不该缩：ceil(2 × 32 / 60) = ceil(1.07) = 2。到 18% 时当次建议值才变成 1，AbleToScale 随即变成 ScaleDownStabilized，意思是窗口里还留着更高的建议值。最后一个”建议 2”大约出现在 07:09:5x，60 秒后过期，07:10:51 事件 New size: 1。

判断缩容”卡住”时先找这个 Reason：只要是 ScaleDownStabilized，就是窗口在起作用，不是故障。默认窗口是 300 秒，窗口取的是建议值的最大值，具体怎么推算缩容时刻见 HPA 水平扩缩容。

期望副本到顶：ScalingLimited=TooManyReplicas

换成 4 个并发循环的重负载（150 秒后自动退出），maxReplicas 设成 2：

期望副本涨了，Pod 却没跑起来

get hpa 的 REPLICAS 是 5，describe hpa 说 5 current，可集群里只有 3 个 Pod，而且一个 Pending 的都没有，因为另外两个根本没被创建出来。原因只在 ReplicaSet 的事件里：

2026-10-13T07:14:07Z   burn-5c877494c8            FailedCreate                   Error creating: pods "burn-5c877494c8-4f9dv" is forbidden: exceeded quota: cpu-cap, requested: requests.cpu=100m, used: requests.cpu=300m, limited: requests.cpu=300m

5 current 是怎么来的？看 scale 子资源：

$ kubectl get --raw /apis/apps/v1/namespaces/notes-lab/deployments/burn/scale
{"kind":"Scale","apiVersion":"autoscaling/v1","metadata":{...},"spec":{"replicas":5},"status":{"replicas":3,"selector":"app=burn"}}

status.replicas 明明是 3，HPA 的 currentReplicas 却是 5。v1.31 的控制器源码（horizontal.go）里是 currentReplicas := scale.Spec.Replicas，它拿的是期望值，不是实际存在的 Pod 数。所以 HPA 的”current”只代表”我上次设成了多少”，判断 Pod 是否真的到位，要看 Deployment 的 READY 或 status.replicas。

不过计算新副本数时用的不是这个 5。按 v1.31 replica_calculator.go 的 GetResourceReplicas，没有缺指标、未就绪的 Pod 时，新副本数是 ceil(比值 × 有指标的就绪 Pod 数)，也就是实际存在的 3 个 Pod：ceil(3 × 155 / 50) = ceil(9.3) = 10。currentReplicas（scale.Spec.Replicas）用来和上下限比较、作为不需要调整时直接返回的值，并写进 status。

10 超过上限 5，所以 ScalingLimited 还是 TooManyReplicas。只看 HPA 会以为”上限太小，再调大”，其实调多大都没用，配额才是瓶颈。

另一个副作用出现在负载停止后：07:16:22 HPA 缩到 2，07:16:37 缩到 1，ReplicaSet 那 2 个一直创建失败的副本也随之不再需要。HPA 自己的事件里只有几条 SuccessfulRescale，看不出配额拦过它，事后复盘要去翻 ReplicaSet 的事件（事件默认只保留一小时左右）。配额的配置见LimitRange 与 ResourceQuota。

调度失败：Pod Pending

去掉配额，给 burn 加一条必须满足的 Pod 反亲和，要求同一节点上不能有两个 burn。保存为 antiaff-patch.yaml：

spec:
  template:
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: burn
              topologyKey: kubernetes.io/hostname
kubectl -n notes-lab delete pod load --ignore-not-found
kubectl -n notes-lab delete quota cpu-cap
kubectl -n notes-lab patch deploy burn --patch-file antiaff-patch.yaml
kubectl -n notes-lab rollout status deploy/burn
# 和上一节相同的 4 并发负载，150 秒后自动退出
kubectl -n notes-lab run load --image=busybox:1.36 --restart=Never -- sh -c \

这条消息按节点逐个列出被排除的理由：control-plane 有污点，两个 worker 不满足反亲和。如果是资源不够，这里会换成 Insufficient cpu 一类的提示。HPA 侧又是一片”正常”，只有 ScalingLimited=TooManyReplicas：

排查顺序

把上面的实验串起来，遇到”HPA 不扩容”时按这个顺序看，每一步只需要一两条命令：

  1. kubectl describe hpa，看 Conditions 里哪一行是 False：
    • AbleToScale=False FailedGetScale：scaleTargetRef 的名字、kind 或 apiVersion 不对。
    • ScalingActive=False ScalingDisabled：目标副本是 0，HPA 主动停了。
    • ScalingActive=False FailedGetResourceMetric：读最后一直重复的那条事件。missing request 是缺 request；did not receive metrics 在新 Pod 刚起来时会出现，持续不消失才去查 Metrics Server（get apiservice、get --raw）。
  2. 三行都是 True/正常，比较当前值和目标值：比值在 0.9～1.1 内是容忍度；Reason 是 ScaleDownStabilized 是稳定窗口；ScalingLimited=TooManyReplicas 是到了上限，但还要做第 3 步。
  3. 比较 HPA 的 REPLICAS 和 Deployment 的 READY。HPA 的 current 是 spec.replicas，不代表 Pod 已经存在：少了 Pod 看 ReplicaSet 的 FailedCreate（配额、准入），有 Pending 看 Pod 的 FailedScheduling，Running 但不 Ready 看探针，见 Pod 与容器。

不要在 HPA 运行期间反复 kubectl scale 同一个 Deployment，也不要把固定的 spec.replicas 留在反复 apply 的清单里，两者都会和 HPA 互相覆盖。手动 scale 能撑多久见 HPA 水平扩缩容。

清理
