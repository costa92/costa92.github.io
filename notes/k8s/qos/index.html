QoS 是从资源配置里推出来的

Pod 的 QoS 类别（Quality of Service）不是一个可以填写的字段，而是 API Server 在创建 Pod 时根据各容器的 CPU、内存 requests/limits 算出来、写进 status.qosClass 的结果。requests 和 limits 本身的含义、内存超限 OOMKilled、CPU 限额节流这些基础内容已经在探针与资源管理里实测过，这一篇只看 QoS：边界情况怎么判、创建后能不能变、在节点上落成了什么。

类别条件
Guaranteed每个容器都设置了 CPU 和内存的 request 与 limit，且两者相等
Burstable不满足 Guaranteed，但至少有一个容器设置了 CPU 或内存的 request/limit
BestEffort所有容器都没有 CPU、内存的 request/limit

下文输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，节点为 cgroup v2，内存容量约 61 GiB），实验放在单独的 notes-lab namespace 里，namespace 中没有 LimitRange 和 ResourceQuota。节点名简化为 worker，时间均为 UTC。

判定边界

一次创建六个 Pod，全部用 busybox 跑 sleep，固定在同一个节点上方便后面看 cgroup：

Pod资源配置
qos-grequests = limits = 100m / 32Mi
qos-brequests 50m / 16Mi，limits 100m / 64Mi
qos-be什么都不写
multi-one-bare容器 app 同 qos-g；另一个容器 sidecar 什么都不写
init-bare主容器同 qos-g；init 容器什么都不写
cpu-only只写 CPU：requests = limits = 100m，不写内存

apply 之后约 15 秒查：

NAME             QOS          STATUS
cpu-only         Burstable    Pending
init-bare        Burstable    Pending
multi-one-bare   Burstable    Pending
qos-b            Burstable    Running
qos-be           BestEffort   Pending
qos-g            Guaranteed   Running

几个值得记住的结论：

  • Pod 还在 Pending，qosClass 就已经有值了。它不是 kubelet 跑起来之后才算的。用 --dry-run=server 也能直接拿到，适合在提交前确认：

    kubectl -n notes-lab apply -f edge.yaml --dry-run=server \
  -o jsonpath='{range .items[*]}{.metadata.name} {.status.qosClass} {.spec.containers[0].resources.requests}{"\n"}{end}'

  • 一个容器拖累整个 Pod。multi-one-bare 里 app 容器完全符合 Guaranteed，但 sidecar 没写资源，整个 Pod 就是 Burstable。给业务容器配好了资源，注入的 sidecar 没配，是 Pod 达不到 Guaranteed 最常见的原因。

  • init 容器也算。init-bare 的 init 容器早就运行结束了，Pod 仍然是 Burstable。上游 v1.31 的 ComputePodQOS 把 InitContainers 和 Containers 放在一起遍历，任何一个容器缺少 CPU 或内存 limit，就不可能是 Guaranteed。

  • 只写 CPU 不算 Guaranteed。cpu-only 的 CPU request 和 limit 完全相等，但没有内存，所以是 Burstable。

再用 server 端 dry-run 看另外几种组合（清单见下方折叠块）：init 容器和主容器各自 requests = limits 但数值不同；Guaranteed 配置额外加一个 ephemeral-storage request；只给 CPU 写了 request，limits 写了 CPU 和内存：

init-guaranteed Guaranteed {"cpu":"100m","memory":"32Mi"}
g-plus-storage Guaranteed {"cpu":"100m","ephemeral-storage":"100Mi","memory":"32Mi"}
limits-partial-req Burstable {"cpu":"50m","memory":"32Mi"}
edge.yaml
apiVersion: v1
kind: Pod
metadata:
  name: init-guaranteed
spec:
  nodeSelector: {kubernetes.io/hostname: worker}
  initContainers:
    - name: init
      image: busybox:1.36
      command: ["sh", "-c", "echo init done"]
      resources:
        requests: {cpu: 200m, memory: 64Mi}
        limits: {cpu: 200m, memory: 64Mi}
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: {cpu: 100m, memory: 32Mi}
        limits: {cpu: 100m, memory: 32Mi}
---
apiVersion: v1
kind: Pod
metadata:
  name: g-plus-storage
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: {cpu: 100m, memory: 32Mi, ephemeral-storage: 100Mi}
        limits: {cpu: 100m, memory: 32Mi}
---
apiVersion: v1
kind: Pod
metadata:
  name: limits-partial-req
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: {cpu: 50m}
        limits: {cpu: 100m, memory: 32Mi}
---
apiVersion: v1
kind: Pod
metadata:
  name: unschedulable
spec:
  nodeSelector: {notes-lab.io/no-such-node: "true"}
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      resources:
        requests: {cpu: 100m, memory: 32Mi}
        limits: {cpu: 100m, memory: 32Mi}

最后一个 unschedulable 用了一个不存在的节点标签，dry-run 结果同样是 Guaranteed，输出里略去了。

  • 只要每个容器自己 requests = limits，容器之间数值不同没关系。
  • ephemeral-storage 不参与 QoS 判定，只看 CPU 和内存。
  • limits-partial-req 的内存 request 是 API Server 从 limit 复制过来的 32Mi，但 CPU request 写了 50m，没被覆盖，于是是 Burstable。也就是说，「只写 limits 会变成 Guaranteed」只对完全没写 request 的资源成立，写了一部分 request 就按写的算。

一个意外：LimitRange 把「什么都没写」变成了 Guaranteed

很多人知道 LimitRange 会给容器注入默认值，但容易忽略注入之后 QoS 会变成什么。在 namespace 里建一个只写了 default（默认 limit）的 LimitRange：

apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
spec:
  limits:
    - type: Container
      default: {cpu: 100m, memory: 64Mi}
$ kubectl -n notes-lab describe limitrange defaults
Type        Resource  Min  Max  Default Request  Default Limit  Max Limit/Request Ratio
----        --------  ---  ---  ---------------  -------------  -----------------------
Container   memory    -    -    64Mi             64Mi           -
Container   cpu       -    -    100m             100m           -

没写 defaultRequest，Default Request 一栏却也有值：没有指定默认 request 时，默认 request 取默认 limit。然后分别创建一个什么都不写的 Pod 和一个只写了 requests.cpu: 10m 的 Pod：

kubectl -n notes-lab apply -f lr.yaml
kubectl -n notes-lab run no-res --image=busybox:1.36 --restart=Never -- sleep 3600
kubectl -n notes-lab run req-only --image=busybox:1.36 --restart=Never --overrides='{"spec":{"containers":[{"name":"req-only","image":"busybox:1.36","command":["sleep","3600"],"resources":{"requests":{"cpu":"10m"}}}]}}'
kubectl -n notes-lab get pod no-res req-only -o jsonpath='{range .items[*]}{.metadata.name} {.status.qosClass} {.spec.containers[0].resources}{"\n"}{end}'
no-res Guaranteed {"limits":{"cpu":"100m","memory":"64Mi"},"requests":{"cpu":"100m","memory":"64Mi"}}
req-only Burstable {"limits":{"cpu":"100m","memory":"64Mi"},"requests":{"cpu":"10m","memory":"64Mi"}}

清单里一个字段都没写的 no-res 成了 Guaranteed，还被加上了 64Mi 的内存上限。如果应用实际需要更多内存，它会在这个 namespace 里莫名其妙地 OOMKilled。排查时看 Pod 上的注解就知道是谁动的手：

$ kubectl -n notes-lab get pod no-res -o jsonpath='{.metadata.annotations}'
{"kubernetes.io/limit-ranger":"LimitRanger plugin set: cpu, memory request for container no-res; cpu, memory limit for container no-res"}

LimitRange 的其他用法见资源配额与限制范围。

创建之后改不了

想把 qos-b 的 requests 调到和 limits 一样，让它变成 Guaranteed：

kubectl -n notes-lab patch pod qos-b \
  -p '{"spec":{"containers":[{"name":"app","resources":{"requests":{"cpu":"100m","memory":"64Mi"}}}]}}'
The Pod "qos-b" is invalid: 
* metadata: Invalid value: "Burstable": Pod QoS is immutable
* spec: Forbidden: pod updates may not change fields other than `spec.containers[*].image`,`spec.initContainers[*].image`,`spec.activeDeadlineSeconds`,`spec.tolerations` (only additions to existing tolerations),`spec.terminationGracePeriodSeconds` (allow it to be set to 1 if it was previously negative)

这里有两条独立的拒绝理由：一条是 Pod 的 resources 本来就不允许原地修改；另一条专门检查 QoS 是否会变化。第二条意味着即使开启了原地调整资源（In-place Pod Resize），也只能在原 QoS 类别的规则内调整：Guaranteed 调完必须仍然相等，Burstable 不能把 CPU 和内存同时调成相等，BestEffort 不能新增资源。

本集群 v1.31 上这个特性还是 alpha，没有开启。kubelet 和 API Server 的 metrics 里都能查到特性门控的状态：

$ kubectl get --raw /metrics | grep 'kubernetes_feature_enabled{name="InPlacePodVerticalScaling"'
kubernetes_feature_enabled{name="InPlacePodVerticalScaling",stage="ALPHA"} 0

所以在 v1.31 上想换 QoS，唯一的办法是改工作负载模板，让控制器用新配置重建 Pod。原地调整资源从 v1.35 起是 GA。

不要去写 status.qosClass

既然 QoS 存在 status 里，那直接改 status 子资源呢？这一步本来只是想证明「改了也没用」，结果出乎意料：

kubectl -n notes-lab patch pod qos-b --subresource=status -p '{"status":{"qosClass":"Guaranteed"}}'

01:20:02 打完补丁，API Server 接受了，get pod 显示 Guaranteed。接下来 Pod 的事件：

FIRST                  LAST                   COUNT    REASON           MSG
2026-10-13T01:20:07Z   2026-10-13T01:20:07Z   1        Killing          Stopping container app
2026-10-13T01:20:41Z   2026-10-13T01:20:41Z   1        SandboxChanged   Pod sandbox changed, it will be killed and re-created.
2026-10-13T01:18:58Z   2026-10-13T01:20:43Z   2        Pulled           Container image "busybox:1.36" already present on machine
2026-10-13T01:19:04Z   2026-10-13T01:20:43Z   2        Created          Created container app
2026-10-13T01:19:05Z   2026-10-13T01:20:44Z   2        Started          Started container app

5 秒后 kubelet 开始停止容器（Killing），34 秒后重建了 Pod 沙箱。中间这段推测是 sleep 作为 PID 1 不处理 SIGTERM、等满了默认 30 秒的宽限期。重建后的容器 oom_score_adj 变成了 Guaranteed 的 -997，在节点上被放进了 Guaranteed 的 cgroup 位置（见下一节），而 spec 里的资源还是 Burstable 的配置。

原因可以在上游代码里找到：v1.31 的 GetPodQOS 在 status.qosClass 非空时直接返回它，只有为空时才根据 spec 计算，kubelet 决定 cgroup 和 OOM 分数时走的就是这个函数。QoS 一变，Pod cgroup 的路径也就变了；v1.31 kubelet.go 的 SyncPod 里有一段 if !pcm.Exists(pod) && !firstSync { kl.killPod(...) }，新路径下的 Pod cgroup 不存在、又不是第一次同步，于是整个 Pod 被杀掉重建，正好对应事件里的 Killing 和 SandboxChanged。

想改回去也不行。01:24:01 把 qos-b 的 status 补回 Burstable，8 秒后 kubelet 又把它写成了 Guaranteed：

$ kubectl -n notes-lab get pod qos-b --show-managed-fields -o jsonpath='{range .metadata.managedFields[*]}{.manager} {.operation} {.subresource} {.time}{"\n"}{end}'
kubectl-client-side-apply Update  2026-10-13T01:18:48Z
calico Update status 2026-10-13T01:20:42Z
kubelet Update status 2026-10-13T01:24:09Z

$ kubectl -n notes-lab get pod qos-b -o jsonpath='{.status.qosClass} restarts={.status.containerStatuses[0].restartCount}'; kubectl -n notes-lab exec qos-b -- cat /proc/1/oom_score_adj
Guaranteed restarts=1
-997

这次没有触发重建，restarts 仍是 1，oom_score_adj 仍是 -997。为什么这次 kubelet 坚持用它自己的值、没有像第一次那样跟着补丁走，我没有查清，推测和 kubelet 本地缓存的状态与补丁到达的先后有关。

在另一个新建的 Pod qos-b2 上重复写 Guaranteed：第一次补丁约 5 秒后被 kubelet 改回了 Burstable，第二次被采纳，同样触发了 Killing 和 SandboxChanged，重建后 oom_score_adj 也是 -997。三次写 Guaranteed 被采纳了两次，一次写回 Burstable 失败。

结论：status.qosClass 是给人看的结果，不是配置入口。一般用户没有 pods/status 的写权限，碰不到这个问题；但自己写控制器、或者给了某个组件 pods/status 的 patch 权限时要知道，一旦写错，Pod 会被重建，之后补丁也改不回来，只能删掉 Pod 重建。排查时以 spec 为准。

到节点上看：cgroup 层级

kubelet 用 QoS 决定 Pod 的 cgroup 放在哪一层。kind 节点就是一个 Docker 容器，可以只读地进去看（worker 指 kind 的工作节点容器，实际名字是 <集群名>-worker）。普通节点上这棵树在 /sys/fs/cgroup/kubepods.slice/；kind 给 kubelet 配了 cgroupRoot: /kubelet，所以多了一层：

$ docker exec worker sh -c 'cd /sys/fs/cgroup/kubelet.slice/kubelet-kubepods.slice; ls -d */'
kubelet-kubepods-besteffort.slice/
kubelet-kubepods-burstable.slice/
kubelet-kubepods-pod1fc63e50_87d3_4fa6_89c5_e92557c3c02b.slice/
kubelet-kubepods-pod5ce0a1d6_77fb_42f1_bf31_6b69ead77935.slice/

结构是：Guaranteed 的 Pod 直接挂在 kubepods 下面；Burstable 和 BestEffort 各有一个中间层 kubepods-burstable.slice、kubepods-besteffort.slice，Pod 挂在里面。目录名里的就是 Pod UID（- 换成了 _）。上面第一个是 qos-b，此时它已经因为上一节的 status 补丁被当成 Guaranteed 重建了；第二个是 qos-g。

逐层读 cpu.weight、cpu.max、memory.max。用的是下面这个小脚本，通过标准输入交给节点上的 sh，不在节点上留文件：

# cg.sh：参数是 Pod UID（- 换成 _）
cd /sys/fs/cgroup/kubelet.slice/kubelet-kubepods.slice
show(){ printf "%-60s cpu.weight=%-5s cpu.max=%-14s memory.max=%s\n" "$1" "$(cat $1/cpu.weight)" "$(cat $1/cpu.max | tr ' ' '/')" "$(cat $1/memory.max)"; }
show .
show kubelet-kubepods-burstable.slice
show kubelet-kubepods-besteffort.slice
for u in "$@"; do
  for d in $(find . -maxdepth 2 -type d -name "*pod${u}.slice"); do
    show "$d"
    for c in $d/cri-containerd-*.scope; do show "$c"; done
  done
done
docker exec -i worker sh -s <uid1> <uid2> ... < cg.sh

（脚本对每个目录打印三个文件，cpu.max 的空格换成了 /；参数是 qos-g、qos-b、qos-be、multi-one-bare 的 UID，输出略去了 qos-b 的几行）：

pod5ce0a1d6 是 qos-g，pod7e687d28 是 qos-be，pod69e0205d 是 multi-one-bare。每个 Pod 目录下的 cri-containerd-*.scope 是容器，其中 cpu.weight=1、没有上限的那个是 pause 容器或没写资源的容器。

几处对照：

  • CPU 份额来自 requests。cgroup v2 的 cpu.weight 由 requests 换算而来：100m 的 qos-g 是 4，50m 的 qos-b 是 2，BestEffort 是最低的 1。按 cgroup v1 的 shares（毫核 × 1024 / 1000）再换算成 v2 weight（1 + (shares - 2) × 9999 / 262142）计算，结果和读到的值一致；顶层 kubepods 的 1094 对应节点的可分配 CPU：

    $ kubectl get node worker -o jsonpath='{.status.capacity.cpu} {.status.allocatable.cpu}'
28 28

    28 核即 28672 shares，换算出来正好是 1094。

  • CPU 和内存上限来自 limits。qos-g 在 Pod 层和容器层都是 cpu.max=10000/100000（0.1 核）、memory.max=33554432（32Mi）。

  • 多容器 Pod 的 Pod 层上限是 max。multi-one-bare 里 app 容器自己有 32Mi 上限，但因为 sidecar 没有 limit，Pod 层的 memory.max、cpu.max 都是 max，Pod 整体没有上限。

  • BestEffort 那一层没有任何上限，只是 cpu.weight 最低。

qos-b 被 status 补丁「升级」之后，旧的 Burstable 目录并没有立刻消失：

$ docker exec worker sh -c 'ls -d /sys/fs/cgroup/kubelet.slice/kubelet-kubepods.slice/*1fc63e50* /sys/fs/cgroup/kubelet.slice/kubelet-kubepods.slice/*/*1fc63e50* 2>&1'

旧目录里已经没有进程，容器都在新目录里；两个目录的 cpu.weight 和 memory.max 都按 spec 算（2 和 64Mi），只有位置跟着 status 走。这个空目录一直留到 Pod 删除后才和新目录一起被清理掉。

oom_score_adj：内核 OOM 时先杀谁

节点内存真的耗尽、kubelet 来不及驱逐时，由内核的 OOM killer 挑进程杀。kubelet 按 QoS 给每个容器设置 oom_score_adj，在容器里读 PID 1 的值：

for p in qos-g qos-b qos-be cpu-only init-bare; do
  echo "$p $(kubectl -n notes-lab exec $p -c app -- cat /proc/1/oom_score_adj)"
done
for c in app sidecar; do
  echo "multi-one-bare/$c $(kubectl -n notes-lab exec multi-one-bare -c $c -- cat /proc/1/oom_score_adj)"
done
qos-g -997
qos-b -997
qos-be 1000
cpu-only 999
init-bare 999
multi-one-bare/app 999
multi-one-bare/sidecar 999

（qos-b 的 -997 是 status 补丁造成的，按 spec 它应该和其他 Burstable 一样。）

  • Guaranteed 是 -997，BestEffort 是 1000，几乎是两个极端。
  • Burstable 的值是 1000 - 1000 × 该容器自己的内存 request / 节点内存容量。官方文档写下限是 2，v1.31 的 pkg/kubelet/qos/policy.go 里下限实际是 1000 + guaranteedOOMScoreAdj = 3；算出 1000 时减 1 变成 999。几十 MiB 的 request 相对 61 GiB 的节点小到可以忽略，所以都是 999；cpu-only 没有内存 request，算出来是 1000，变成 999。
  • 用哪个公式由 Pod 的 QoS 决定，不看容器自己配得完不完整。multi-one-bare 里 app 容器资源配得和 Guaranteed 一样，也只拿到 999，没有得到 -997；sidecar 没有内存 request，同样是 999。

为了验证公式，再建一个 requests.memory: 256Mi 的 Burstable Pod：

$ kubectl -n notes-lab exec b-256 -- cat /proc/1/oom_score_adj
996

节点 capacity.memory 是 64329524Ki，1000 - 1000 × 256Mi / 64329524Ki 取整正好是 996。在内存大的节点上，Burstable Pod 之间的差别非常小，内核选择谁主要还是看谁实际占的内存多（oom_score 本身按内存占比计算，oom_score_adj 是加在上面的修正）。

QoS 不决定的事

节点有空闲 CPU 时，BestEffort 并不慢

cpu.weight 只在 CPU 争用时起作用。在 qos-g（limit 0.1 核）和 qos-be（weight 1，无上限）里同时跑 20 秒死循环，前后在节点上读 Pod 层的 cpu.stat：

date -u +%T
for p in qos-g qos-be; do
  kubectl -n notes-lab exec $p -- sh -c 'b=$(date +%s); timeout 20 sh -c "while :; do :; done"; echo "$(hostname) busy loop done after $(($(date +%s)-b))s"' &
done; wait
date -u +%T

前后两次 cpu.stat 用下面的 cpustat.sh 在节点上读 Pod 层目录（参数是 qos-g 和 qos-be 的 UID）：

Guaranteed 照样会 OOMKilled

同样分配 100M 内存：

$ kubectl -n notes-lab exec qos-be -- sh -c 'cat /sys/fs/cgroup/memory.max; dd if=/dev/zero of=/dev/null bs=100M count=1; cat /sys/fs/cgroup/memory.peak'
max
104857600 bytes (100.0MB) copied, 0.022600 seconds, 4.3GB/s
107503616

$ kubectl -n notes-lab exec qos-g -- sh -c 'cat /sys/fs/cgroup/memory.max; dd if=/dev/zero of=/dev/null bs=100M count=1'
33554432
command terminated with exit code 137
$ kubectl -n notes-lab get pod qos-g -o jsonpath='{.status.qosClass} restarts={.status.containerStatuses[0].restartCount} last={.status.containerStatuses[0].lastState.terminated.reason}'
Guaranteed restarts=1 last=OOMKilled

BestEffort 没有上限，100M 随便用；Guaranteed 超过自己 32Mi 的 limit 就被内核杀掉，容器重启。-997 的 oom_score_adj 只影响节点整体内存耗尽时的挑选，对容器自己 cgroup 内的超限没有任何保护。

驱逐顺序不是按 QoS 排的

kubelet 在节点内存压力下挑选驱逐对象，按官方文档依次看三件事，内存用量是否超过 requests、Pod 优先级、用量超出 requests 多少，并明确写了 kubelet 不使用 QoS 类别来决定驱逐顺序。之所以常被说成「先 BestEffort、再 Burstable、最后 Guaranteed」，是因为 BestEffort 的 requests 为 0，只要用了内存就算超出；Guaranteed 的用量被 limit = request 封住，不可能超出。QoS 只是对驱逐顺序的一个近似估计。磁盘压力（DiskPressure）下更是和 QoS 无关，因为 QoS 不考虑 ephemeral-storage。

这部分我没有在集群上复现：制造节点内存压力会影响同一集群上的其他工作负载，所以只做了容器级别的 OOM。

排查清单

  • Pod 的 QoS 和预期不同：先 kubectl get pod -o yaml 看最终的 resources，而不是看自己的清单。重点看三处：有没有没写资源的容器（包括 init 容器和注入的 sidecar），有没有只写了 CPU 或只写了内存，以及 kubernetes.io/limit-ranger 注解是否存在。
  • 没写资源却被 OOMKilled：查 namespace 里的 LimitRange，它的默认 limit 可能很小。
  • 想改 QoS：v1.31 上不能原地改，报 Pod QoS is immutable；改 Deployment 等模板，让 Pod 重建。开启原地调整资源后也一样不能跨 QoS 类别。
  • status 和 spec 对不上：以 spec 为准，检查是否有组件写过 pods/status（kubectl get pod --show-managed-fields 能看到 status 最后由谁更新）。

清理

kubectl delete namespace notes-lab
