容器镜像如何进入集群

镜像包含程序、依赖和启动配置；Pod 引用镜像后，由节点上的容器运行时负责获取并启动它。镜像名通常写成 仓库/名称:标签，例如 nginx:1.27。标签可以被重新指向另一份内容，摘要（digest）不能，这个区别在本地实验里也会直接暴露出来。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，kind v0.24.0），实验放在单独的 notes-lab namespace 里。kind 的节点名形如 <集群名>-worker，文中简化为 control-plane、worker、worker2。环境准备见本地实验环境。

关键的一点：kind 的每个节点是一个 Docker 容器，里面跑着自己的 containerd。宿主机上 docker build 出来的镜像在宿主机 Docker 里，节点的 containerd 看不到它。

构建一个能分辨版本的小镜像

为了后面能分清「到底跑的是哪一份内容」，镜像里放一个写着版本号的页面，用 busybox 自带的 httpd 提供出来：

FROM busybox:1.36
ARG VERSION=dev
RUN mkdir /www && echo "images-demo $VERSION" > /www/index.html
EXPOSE 8080
CMD ["httpd", "-f", "-p", "8080", "-h", "/www"]
docker build --build-arg VERSION=v1 -t notes-lab/images-demo:v1 .
docker build --build-arg VERSION=v2 -t notes-lab/images-demo:v2 .
docker tag notes-lab/images-demo:v1 notes-lab/images-demo:latest
docker images notes-lab/images-demo
IMAGE                          ID             DISK USAGE   CONTENT SIZE   EXTRA
notes-lab/images-demo:latest   b83eb61e6b51       6.78MB         2.21MB
notes-lab/images-demo:v1       b83eb61e6b51       6.78MB         2.21MB
notes-lab/images-demo:v2       c2143b87a49a       6.78MB         2.21MB

latest 和 v1 是同一个 ID，只是两个名字。

只 build 不导入：ErrImagePull

先不导入，直接用这个镜像起 Pod：

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab run before-load --image=notes-lab/images-demo:v1 --restart=Never
kubectl -n notes-lab describe pod before-load
Normal   Scheduled  25s               default-scheduler  Successfully assigned notes-lab/before-load to worker
Normal   BackOff    22s               kubelet            Back-off pulling image "notes-lab/images-demo:v1"
Warning  Failed     22s               kubelet            Error: ImagePullBackOff
Normal   Pulling    8s (x2 over 24s)  kubelet            Pulling image "notes-lab/images-demo:v1"
Warning  Failed     6s (x2 over 22s)  kubelet            Failed to pull image "notes-lab/images-demo:v1": failed to pull and unpack image "docker.io/notes-lab/images-demo:v1": failed to resolve reference "docker.io/notes-lab/images-demo:v1": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed
Warning  Failed     6s (x2 over 22s)  kubelet            Error: ErrImagePull

两个细节：

  • 镜像名里没写仓库地址，运行时把它补全成了 docker.io/notes-lab/images-demo:v1，然后真的去 Docker Hub 找。报错是 pull access denied，和写错公共镜像名时一模一样，看报错本身分辨不出是「镜像只在宿主机上」还是「名字写错了」。
  • 这个 Pod 的 imagePullPolicy 是 IfNotPresent（标签不是 latest 时的默认值），节点上没有，所以它去拉了。

用 kind load 导入节点

kind load docker-image notes-lab/images-demo:v1 --name <集群名>
Image: "notes-lab/images-demo:v1" with ID "sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab" not yet present on node "worker", loading...
Image: "notes-lab/images-demo:v1" with ID "sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab" not yet present on node "control-plane", loading...
Image: "notes-lab/images-demo:v1" with ID "sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab" not yet present on node "worker2", loading...

real	0m22.153s

kind load 做的事情相当于 docker save 后在每个节点里执行 containerd 的导入，默认导入所有节点，3 个节点用了 22 秒。用节点里的 crictl 核对：

docker exec <集群名>-worker crictl images | grep notes-lab
docker.io/notes-lab/images-demo                             v1                   dd004fd152c16       2.21MB

注意 IMAGE ID 和宿主机 Docker 显示的不一样：宿主机是 b83eb61e…，节点里是 dd004fd1…。用 crictl images --digests 能看到两者的关系，b83eb61e… 出现在 DIGEST 列，是镜像清单（这里是 OCI image index）的摘要；IMAGE ID 是镜像配置的摘要：

IMAGE                                                       TAG                  DIGEST              IMAGE ID            SIZE
docker.io/notes-lab/images-demo                             latest               b83eb61e6b51d       dd004fd152c16       2.21MB
docker.io/notes-lab/images-demo                             v1                   b83eb61e6b51d       dd004fd152c16       2.21MB

（宿主机 Docker 用的是 containerd 镜像存储，所以 docker images 显示的 ID 是清单摘要；用传统存储的 Docker 显示的是配置 ID，两边会一致。）

minikube 对应的命令是 minikube image load notes-lab/images-demo:v1，原理相同。

导入后不用删 Pod

刚才那个 before-load 没有删，导入完成后它自己起来了：

kubectl -n notes-lab get events --field-selector involvedObject.name=before-load --sort-by=.lastTimestamp \
  -o custom-columns=FIRST:.firstTimestamp,LAST:.lastTimestamp,COUNT:.count,REASON:.reason
FIRST                  LAST                   COUNT    REASON
2026-10-13T06:49:58Z   2026-10-13T06:50:42Z   3        Pulling
2026-10-13T06:50:00Z   2026-10-13T06:50:45Z   3        Failed
2026-10-13T06:50:56Z   2026-10-13T06:50:56Z   1        Pulled
2026-10-13T06:50:57Z   2026-10-13T06:50:57Z   1        Started
Normal   Pulled     27s                kubelet            Container image "notes-lab/images-demo:v1" already present on machine

kubelet 在退避等待结束后重试，这次策略 IfNotPresent 发现镜像已经在节点上，就不拉了。所以 ImagePullBackOff 不是终态，把镜像补上之后等下一次重试即可；退避越久，等得越久，下面会量这个间隔。

imagePullPolicy 的默认值

官方文档的规则是：不写 imagePullPolicy 时，标签为 :latest 或干脆不写标签，默认 Always；写了摘要或写了其他标签，默认 IfNotPresent。这个值在对象创建时就写死，之后改镜像标签也不会跟着变。

把 :latest 也导入所有节点，然后起两个 Pod，一个用 :latest，一个用 :v1，都不写策略：

kind load docker-image notes-lab/images-demo:latest --name <集群名>
kubectl -n notes-lab run tag-latest --image=notes-lab/images-demo:latest --restart=Never
kubectl -n notes-lab run tag-v1 --image=notes-lab/images-demo:v1 --restart=Never
kubectl -n notes-lab get pod tag-latest tag-v1 \
  -o custom-columns=NAME:.metadata.name,IMAGE:.spec.containers[0].image,POLICY:.spec.containers[0].imagePullPolicy
NAME         IMAGE                          POLICY
tag-latest   notes-lab/images-demo:latest   Always
tag-v1       notes-lab/images-demo:v1       IfNotPresent

约 20 秒后：

NAME         READY   STATUS             RESTARTS   AGE
tag-latest   0/1     ImagePullBackOff   0          19s
tag-v1       1/1     Running            0          19s
Warning  Failed     1s (x2 over 16s)  kubelet            Failed to pull image "notes-lab/images-demo:latest": failed to pull and unpack image "docker.io/notes-lab/images-demo:latest": failed to resolve reference "docker.io/notes-lab/images-demo:latest": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed

两个镜像在每个节点上都有，而且是同一个镜像。tag-latest 失败只因为策略是 Always：每次启动容器都要问一次仓库，仓库里根本没有这个镜像。本地实验镜像不要打 latest 标签，或者显式写 imagePullPolicy: IfNotPresent。

Never：哪个节点没有镜像就在哪个节点失败

v2 只导入 worker：

kind load docker-image notes-lab/images-demo:v2 --name <集群名> --nodes <集群名>-worker
== worker
docker.io/notes-lab/images-demo                             latest               dd004fd152c16       2.21MB
docker.io/notes-lab/images-demo                             v1                   dd004fd152c16       2.21MB
docker.io/notes-lab/images-demo                             v2                   08eaf62b43566       2.21MB
== worker2
docker.io/notes-lab/images-demo                          latest               dd004fd152c16       2.21MB
docker.io/notes-lab/images-demo                          v1                   dd004fd152c16       2.21MB

两个 imagePullPolicy: Never 的 Pod，用 nodeName 分别固定到两个节点：

apiVersion: v1
kind: Pod
metadata:
  name: never-worker2
spec:
  nodeName: <集群名>-worker2
  containers:
    - name: app
      image: notes-lab/images-demo:v2
      imagePullPolicy: Never
      resources:
        requests: {cpu: 10m, memory: 16Mi}

（never-worker 相同，只是 nodeName 换成 worker。两个 Pod 写在同一个 never.yaml 里，用 --- 分隔。）

kubectl -n notes-lab apply -f never.yaml
NAME            READY   STATUS              RESTARTS   AGE
never-worker    1/1     Running             0          20s
never-worker2   0/1     ErrImageNeverPull   0          20s
Warning  ErrImageNeverPull  6s (x4 over 18s)  kubelet  Container image "notes-lab/images-demo:v2" is not present with pull policy of Never
Warning  Failed             6s (x4 over 18s)  kubelet  Error: ErrImageNeverPull

ErrImageNeverPull 的报错很直白，比 pull access denied 好排查得多：它明确告诉你「这台节点上没有」，而不会去外网绕一圈。本地实验里用 Never 的好处就在这里，代价是每个可能被调度到的节点都得导入。

这里用 nodeName 是为了确定性地落到指定节点。正常调度时，调度器的 ImageLocality 打分会稍微偏向已有镜像的节点，但它只是打分项之一，不保证一定选中，所以只导入部分节点的做法迟早会撞上这个错误。何况 v1.31 的 image_locality.go 里 minThreshold 是 23MB，这个镜像只有约 2MB，这一项得分为 0，等于完全不起作用。

两个和拉取失败不同的现象：

  • 重试不退避。从 worker2 的 kubelet 日志里取出每次报 ErrImageNeverPull 的时间：

    06:52:21
06:52:21
06:52:22
06:52:33
06:52:45
06:53:00
06:53:11
06:53:22

    首轮连发 3 次，之后间隔 11 到 15 秒，没有翻倍。ErrImageNeverPull 不走镜像拉取的指数退避，它只是让这次 Pod 同步出错；kubelet v1.31 的 pkg/kubelet/pod_workers.go 在同步出错后用 wait.Jitter(backOffPeriod, 0.5) 重新排队，backOffPeriod 是 10 秒，所以间隔落在 10 到 15 秒。

  • 补上镜像后自己恢复。06:53 给 worker2 也导入 v2，没有动 Pod：

拉取退避到底等多久

tag-latest 放着不管，跑了 11 分钟。describe 的事件里只能看到这些：

Normal   Pulling    10m (x4 over 11m)    kubelet            Pulling image "notes-lab/images-demo:latest"
Warning  Failed     10m (x4 over 11m)    kubelet            Error: ErrImagePull
Warning  Failed     9m53s (x6 over 11m)  kubelet            Error: ImagePullBackOff
Normal   BackOff    86s (x43 over 11m)   kubelet            Back-off pulling image "notes-lab/images-demo:latest"

看上去最后一次拉取是 10 分钟前，之后只有 BackOff。先确认 Pod 在哪个节点，再去那个节点上看 kubelet 日志：

kubectl -n notes-lab get pod tag-latest -o wide
NAME         READY   STATUS             RESTARTS   AGE   IP                NODE                         NOMINATED NODE   READINESS GATES
tag-latest   0/1     ImagePullBackOff   0          19s   <pod-ip>          worker                       <none>           <none>

（这是 Pod 刚创建时的输出，节点之后不会变。）日志和事件对不上：

docker exec <集群名>-worker journalctl -u kubelet --no-pager \
  | grep 'pod="notes-lab/tag-latest"' | grep 'with ErrImagePull' | awk '{print $3}'
06:51:51
06:52:06
06:52:34
06:53:23
06:54:56
06:57:50
07:02:56

一共拉了 7 次，相邻间隔是 15、28、49、93、174、306 秒：15 秒起约每次翻倍，最后封顶约 300 秒。kubelet 的理论退避从 10 秒开始翻倍（10、20、40……），实测每段都多出几秒，是退避到期后要等下一次 Pod 同步才会真正重试。官方文档写的上限也是 300 秒（5 分钟）。中间密集出现的 BackOff 事件（43 次）只是 kubelet 每次同步时发现「还在退避期」，并没有真正去拉。

事件里 Pulling 停在 4 次，后 3 次拉取没有出现在事件里。原因在 kubelet 发事件用的 client-go（v0.31，tools/record/events_cache.go）：它对同一个 source + object 有一个 spam filter，令牌桶容量 25（defaultSpamBurst），之后每 300 秒补 1 个（defaultSpamQPS = 1/300）。超出的事件直接在本地丢弃，但计数在丢弃之前已经在本地累加，下一条放行的事件会带上累加后的计数。所以 BackOff 显示 x43，LAST 却停在 07:02:02：

2026-10-13T06:51:51Z   2026-10-13T07:02:02Z   43       BackOff

也就是说，事件里的时间和计数都可能落后于实际。一个 Pod 的事件发到 25 条以后，最多 5 分钟才更新一次；需要精确时间就看节点上的 kubelet 日志。另一个推论：镜像修好后最坏要等 5 分钟才会被下一次重试拾起，赶时间就直接删掉 Pod 重建。

用摘要固定版本

官方推荐用 镜像名@sha256:<摘要> 固定内容。先看节点上记录的摘要，以及 Pod 状态里上报的 imageID：

kubectl -n notes-lab get pod tag-v1 never-worker \
  -o custom-columns=NAME:.metadata.name,IMAGE:.status.containerStatuses[0].image,IMAGEID:.status.containerStatuses[0].imageID
NAME           IMAGE                                    IMAGEID
tag-v1         docker.io/notes-lab/images-demo:latest   docker.io/library/import-2026-10-13@sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab
never-worker   docker.io/notes-lab/images-demo:v2       docker.io/library/import-2026-10-13@sha256:c2143b87a49a041e15977c6bd35c130010fc7615cab7a65fb3f4b37237066721

这一段有两处出乎意料：

  • tag-v1 的 spec 写的是 :v1，状态里的 image 却是 :latest。因为节点上 v1 和 latest 指向同一个镜像，运行时上报的是这个镜像的某一个标签，不一定是你写的那个。判断 Pod 实际跑的是什么，看 imageID 的摘要，不要看 status.image 的标签。

  • imageID 里的仓库名是 import-2026-10-13，不是 notes-lab/images-demo。crictl inspecti 显示，导入的镜像只有这样一条摘要记录：

    "repoDigests": [
  "docker.io/library/import-2026-10-13@sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab"
],

这直接影响摘要引用。用这个摘要在 worker 上起 Pod（用 nodeName 固定到已导入镜像的节点）：

kubectl -n notes-lab run by-digest \
  --image=notes-lab/images-demo@sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab \
  --image-pull-policy=IfNotPresent --restart=Never \
  --overrides='{"spec":{"nodeName":"<集群名>-worker"}}'
Warning  Failed   16s               kubelet  Failed to pull image "notes-lab/images-demo@sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab": failed to pull and unpack image "docker.io/notes-lab/images-demo@sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab": failed to resolve reference "docker.io/notes-lab/images-demo@sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed

  --overrides='{"spec":{"nodeName":"<集群名>-worker"}}'
Warning  Failed   8s    kubelet  Failed to pull image "docker.io/library/import-2026-10-13@sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab": failed to pull and unpack image "docker.io/library/import-2026-10-13@sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab": failed to resolve reference "docker.io/library/import-2026-10-13@sha256:b83eb61e6b51d9937d54bc07ec2e2d695e6554df0175c43b5ca98720463dd5ab": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed

这个名字来自 kind 的导入命令 ctr images import --all-platforms --digests：--digests 会为每个导入的清单额外建一条 import-<日期>@sha256:<摘要> 记录，节点的 ctr images ls 里看到的正是不带 docker.io/library/ 前缀的这个名字。至于运行时按摘要查找时为什么认不出这条记录，这次没有追到源码，推测是查找时用的规范化名字与它对不上。

对照组是从 Docker Hub 正常拉下来、worker 上已有的 busybox:1.36，它的摘要记录在真实的仓库名下：

"docker.io/library/busybox@sha256:73aaf090f3d85aa34ee199857f03fa3a95c8ede2ffd4cc2cdb5b94e566b11662"
kubectl -n notes-lab run busybox-digest \
  --image=busybox@sha256:73aaf090f3d85aa34ee199857f03fa3a95c8ede2ffd4cc2cdb5b94e566b11662 \
  --restart=Never --overrides='{"spec":{"nodeName":"<集群名>-worker"}}' -- sleep 3600
kubectl -n notes-lab get pod busybox-digest -o custom-columns=NAME:.metadata.name,POLICY:.spec.containers[0].imagePullPolicy,\
STATUS:.status.phase,IMAGE:.status.containerStatuses[0].image,IMAGEID:.status.containerStatuses[0].imageID
NAME             POLICY         STATUS    IMAGE                            IMAGEID
busybox-digest   IfNotPresent   Running   docker.io/library/busybox:1.36   docker.io/library/busybox@sha256:73aaf090f3d85aa34ee199857f03fa3a95c8ede2ffd4cc2cdb5b94e566b11662
Normal  Pulled   11s   kubelet  Container image "busybox@sha256:73aaf090f3d85aa34ee199857f03fa3a95c8ede2ffd4cc2cdb5b94e566b11662" already present on machine

没写策略，按摘要引用默认就是 IfNotPresent，本地命中，没有联网。结论：摘要固定适用于经过镜像仓库分发的镜像；kind load 导入的镜像在这套环境里只能按标签引用。想在本地集群里也用摘要，需要搭一个本地镜像仓库，推上去再拉。

同一个标签换了内容

最常见的坑：改了代码，重新构建，还用原来的标签。本节从头重新构建并重跑（我是在一个新的 namespace 里重跑的，镜像 ID 因此和前文不同：宿主机上 v1 这次是 656d66…，前文是 b83eb61e…；内容没变，节点上的配置 ID 仍是 dd004fd1…）。接着前文做的话，先删掉旧的 tag-v1，重新构建 v1 并打上 latest，导入所有节点，再在 worker2 上起一个 tag-v1：

kubectl -n notes-lab delete pod tag-v1
docker build --build-arg VERSION=v1 -t notes-lab/images-demo:v1 .
docker tag notes-lab/images-demo:v1 notes-lab/images-demo:latest
kind load docker-image notes-lab/images-demo:v1 notes-lab/images-demo:latest --name <集群名>
kubectl -n notes-lab run tag-v1 --image=notes-lab/images-demo:v1 --restart=Never \
  --overrides='{"spec":{"nodeName":"<集群名>-worker2"}}'

然后改内容重新构建，仍然打 v1，只导入 worker：

docker build --build-arg VERSION=v1-rebuilt -t notes-lab/images-demo:v1 .
kind load docker-image notes-lab/images-demo:v1 --name <集群名> --nodes <集群名>-worker
IMAGE                          ID             DISK USAGE   CONTENT SIZE   EXTRA
notes-lab/images-demo:latest   656d66b09d0c       6.78MB         2.21MB
notes-lab/images-demo:v1       2598ea9f7d73       6.78MB         2.21MB

现在两个节点上的 v1 已经不是同一个镜像：

== worker
docker.io/notes-lab/images-demo                             latest               dd004fd152c16       2.21MB
docker.io/notes-lab/images-demo                             v1                   dbcc93cda5c0f       2.21MB
== worker2
docker.io/notes-lab/images-demo                          latest               dd004fd152c16       2.21MB
docker.io/notes-lab/images-demo                          v1                   dd004fd152c16       2.21MB

在两个节点上各起一个 v1 的 Pod，同样用 nodeName 固定：

for n in worker worker2; do
  kubectl -n notes-lab run v1-on-$n --image=notes-lab/images-demo:v1 --restart=Never \
    --overrides="{\"spec\":{\"nodeName\":\"<集群名>-$n\"}}"
done
for p in v1-on-worker v1-on-worker2 tag-v1; do
  echo -n "$p: "; kubectl -n notes-lab exec $p -- wget -qO- http://localhost:8080/
done
v1-on-worker: images-demo v1-rebuilt
v1-on-worker2: images-demo v1
tag-v1: images-demo v1

三个 Pod 的 spec 一模一样都是 notes-lab/images-demo:v1，跑的内容却不一样。spec 看不出区别，能分辨的只有 imageID：

NAME            SPEC                       IMAGEID
v1-on-worker    notes-lab/images-demo:v1   docker.io/library/import-2026-10-13@sha256:2598ea9f7d734f20162d4f97dd2882e7ccb58e5169095a1f5b5e7a6f84469e85
v1-on-worker2   notes-lab/images-demo:v1   docker.io/library/import-2026-10-13@sha256:656d66b09d0cc762301f5c5508ce7523cebe6802ca3d8da5d276d6aae199575f
tag-v1          notes-lab/images-demo:v1   docker.io/library/import-2026-10-13@sha256:656d66b09d0cc762301f5c5508ce7523cebe6802ca3d8da5d276d6aae199575f

再把新的 v1 导入所有节点，已经在跑的容器不受影响，仍是旧内容：

kind load docker-image notes-lab/images-demo:v1 --name <集群名>
v1-on-worker2: images-demo v1
tag-v1: images-demo v1

删掉 v1-on-worker2 按同样的命令重建，才拿到新内容：

kubectl -n notes-lab delete pod v1-on-worker2
kubectl -n notes-lab run v1-on-worker2 --image=notes-lab/images-demo:v1 --restart=Never \
  --overrides='{"spec":{"nodeName":"<集群名>-worker2"}}'
kubectl -n notes-lab exec v1-on-worker2 -- wget -qO- http://localhost:8080/
images-demo v1-rebuilt

也就是说，同标签覆盖之后，集群里新旧版本并存，哪个 Pod 跑哪份取决于它在哪个节点、什么时候创建。用 Deployment 时情况更糟：只改镜像内容不改 Pod 模板，Deployment 不会触发滚动更新（见 Deployment）。改了内容就换一个新标签，比如 v1.0.1，并更新 Pod 模板。

策略在创建时就定了

接着用这个重建好的 v1-on-worker2 验证前面那条规则「imagePullPolicy 创建后不会跟着标签变」。它用 :v1 创建，策略是 IfNotPresent；把镜像改成 :latest（Pod 的 image 字段允许原地修改）：

kubectl -n notes-lab get pod v1-on-worker2 \
  -o custom-columns=NAME:.metadata.name,IMAGE:.spec.containers[0].image,POLICY:.spec.containers[0].imagePullPolicy
kubectl -n notes-lab set image pod/v1-on-worker2 v1-on-worker2=notes-lab/images-demo:latest
NAME            IMAGE                      POLICY
v1-on-worker2   notes-lab/images-demo:v1   IfNotPresent
pod/v1-on-worker2 image updated

45 秒后：

NAME            IMAGE                          POLICY         RESTARTS   READY
v1-on-worker2   notes-lab/images-demo:latest   IfNotPresent   1          true
images-demo v1
Normal  Pulled   52s                kubelet  Container image "notes-lab/images-demo:v1" already present on machine
Normal  Killing  45s                kubelet  Container v1-on-worker2 definition changed, will be restarted
Normal  Pulled   14s                kubelet  Container image "notes-lab/images-demo:latest" already present on machine
Normal  Created  13s (x2 over 51s)  kubelet  Created container v1-on-worker2
Normal  Started  13s (x2 over 51s)  kubelet  Started container v1-on-worker2

镜像已经是 :latest，策略仍是 IfNotPresent，所以它直接用了节点上的 latest 正常起来，页面也变回了 latest 指向的旧内容；而前面新建的 tag-latest 因为默认 Always 一直起不来。同一个镜像名，新建和原地修改的结果不同。

另外 Killing 到重新创建隔了 32 秒（事件时间 07:13:28 到 07:14:00）：busybox httpd 作为 1 号进程不处理 SIGTERM，要等 30 秒的宽限期到期被 SIGKILL。这和镜像无关，但改镜像时会看到，见优雅终止。

附带一个现象：每次 kind load 都打印 not yet present on node，哪怕刚刚导入过同一个镜像。kind v0.24.0 的判断方法是拿宿主机 docker image inspect 的 .Id 去和节点上 crictl inspecti 的 status.id 比较（pkg/cmd/kind/load/docker-image/docker-image.go 和 pkg/cluster/nodeutils/util.go）。在使用 containerd 镜像存储的 Docker 上，前者是清单摘要（2598ea…），后者是配置摘要（dbcc93…），两者永远不相等，所以每次都重新导入。这不影响结果，只是多花时间。

排查顺序

「先看 Events」仍是第一步，但要记得上面量到的：事件的时间和计数可能落后，需要确认最近一次拉取何时发生、报了什么，以节点上的 kubelet 日志为准。

镜像相关的失败按这几步走：

  1. 报错是 ErrImageNeverPull：这台节点上没有镜像。docker exec <节点> crictl images 核对，用 kind load 补上即可，Pod 不用删。
  2. 报错是 pull access denied：先逐字核对镜像名，确认运行时补全后的完整名字（docker.io/...）；再看 imagePullPolicy，本地镜像配上 Always（包括 :latest 的默认值）一定会走到这一步；最后才是私有仓库凭据 imagePullSecrets。
  3. 镜像起来了但行为不对：比较 Pod 的 imageID 和节点上 crictl images --digests 的结果，确认跑的是哪一份内容。

清理

kubectl delete namespace notes-lab --wait
for n in control-plane worker worker2; do
  for t in latest v1 v2; do
    docker exec <集群名>-$n crictl rmi docker.io/notes-lab/images-demo:$t   # 没导入过的标签会报 no such image，可忽略
  done
done
docker rmi notes-lab/images-demo:v1 notes-lab/images-demo:v2 notes-lab/images-demo:latest

crictl rmi 只删掉了带标签的记录，节点上 ctr -n k8s.io images ls 里仍留着 import-2026-10-13@sha256:… 这几条导入时生成的记录，要用 docker exec <节点> ctr -n k8s.io images rm import-2026-10-13@sha256:<摘要> 单独删。长期使用 kind load 的集群，这类记录会越积越多。
