DaemonSet 与节点工作负载

Deployment 关心「总共跑几个副本」，DaemonSet 关心「每个符合条件的节点上跑一个」。日志采集、节点监控、CNI 和 kube-proxy 这类节点级组件都用它。副本数没有 replicas 字段可填，完全由符合条件的节点决定：节点加入、标签变化，控制器都会跟着增删 Pod。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），节点名简化成 control-plane、worker、worker2，实验放在单独的 notes-lab namespace 里，Pod IP 用 <pod-ip> 代替。

默认落在哪些节点

先准备一个最小的节点代理，启动时打印版本号、启动时间和所在节点，后面用它区分新旧 Pod。保存为 agent.yaml：

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
spec:
  selector:
    matchLabels:
      app: node-agent
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      terminationGracePeriodSeconds: 2
      containers:
        - name: agent
          image: busybox:1.36
          command: ["sh", "-c", "echo \"v1 start $(date +%T) on $NODE\"; while true; do sleep 30; done"]
          env:
            - name: NODE
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              memory: 32Mi
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f agent.yaml
kubectl -n notes-lab rollout status ds/node-agent --timeout=120s
kubectl -n notes-lab get ds node-agent
kubectl -n notes-lab get pods -l app=node-agent -o wide
daemon set "node-agent" successfully rolled out
NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
node-agent   2         2         2       2            2           <none>          15s
NAME               READY   STATUS    RESTARTS   AGE   IP          NODE      ...
node-agent-vvn7g   1/1     Running   0          15s   <pod-ip>    worker2
node-agent-w78lh   1/1     Running   0          15s   <pod-ip>    worker

集群有三个节点，DESIRED 却是 2。控制平面节点被跳过了，原因在它的污点上：

kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
NAME            TAINTS
control-plane   [map[effect:NoSchedule key:node-role.kubernetes.io/control-plane]]
worker          <none>
worker2         <none>

DaemonSet 并不会无视污点。Pod 模板没有容忍这个 NoSchedule 污点，控制器在计算「符合条件的节点」时就把它排除了，所以 DESIRED 直接是 2，而不是 3 个里有 1 个 Pending。describe ds 的事件里也只有两条 SuccessfulCreate，没有任何关于控制平面的提示——被污点挡掉的节点不会产生报错，要自己对照 kubectl get nodes 才能发现少了谁。

想让代理也跑到控制平面上，给 Pod 模板加一条容忍（只改自己的 Pod，不动节点）：

spec:
  template:
    spec:
      tolerations:
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
kubectl -n notes-lab patch ds node-agent --patch-file tol-patch.yaml

用一个每秒轮询一次的小脚本记录 Pod 列表的变化，只在列表变化时打印。列依次是名字、节点、phase、ready、deletionTimestamp、controller-revision-hash 标签，保存为 watch.sh，用法是 bash watch.sh <秒数> [标签选择器]：

N=$1; SEL=${2:-app=node-agent}; prev=""
for i in $(seq 1 $N); do
  cur=$(kubectl -n notes-lab get pods -l $SEL --no-headers -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,PHASE:.status.phase,READY:.status.containerStatuses[0].ready,DEL:.metadata.deletionTimestamp,HASH:.metadata.labels.controller-revision-hash 2>&1 | sort -k2)
  if [ "$cur" != "$prev" ]; then echo "--- $(date -u +%T)"; echo "$cur"; prev="$cur"; fi
  sleep 1
done

实际运行时我还在 sort 前用 sed 去掉了节点名前缀，所以输出里是简化后的节点名。因为只在变化时打印，两帧之间发生了什么、谁先谁后是看不到的。下面是 bash watch.sh 40 的节选，patch 发生在 01:19:01：

node-agent-vvn7g   worker2         Running   true    <none>   646c7bb897
node-agent-w78lh   worker          Running   true    <none>   646c7bb897
--- 01:19:18
node-agent-9swq4   control-plane   Running   true   <none>                 5d66bb45cd
node-agent-vvn7g   worker2         Running   true   <none>                 646c7bb897
node-agent-w78lh   worker          Running   true   2026-10-13T01:19:20Z   646c7bb897
--- 01:19:26
node-agent-9swq4   control-plane   Running   true    <none>   5d66bb45cd
node-agent-vvn7g   worker2         Running   true    <none>   646c7bb897
node-agent-mk5r6   worker          Pending   false   <none>   5d66bb45cd
...
--- 01:19:37
node-agent-9swq4   control-plane   Running   true   <none>   5d66bb45cd
node-agent-8z547   worker2         Running   true   <none>   5d66bb45cd

deletionTimestamp 一列要这样读：它不是发出删除的时刻，而是「删除时刻 + 宽限期」，也就是 kubelet 最晚要强制杀掉容器的时间。这里宽限期是 2 秒，所以 01:19:18 那一帧里 w78lh 显示的是 01:19:20。

两件事同时发生了：控制平面上马上补了一个新 Pod；两个工作节点上原本好好的 Pod 也被逐个替换。加容忍改的是 Pod 模板，模板一变就是一个新的 revision（hash 从 646c7bb897 变成 5d66bb45cd），已有的 Pod 都要按更新策略滚一遍。生产环境里「只是想让代理多覆盖一个节点」，也会触发全量滚动，这一点要心里有数。

控制器替 Pod 加了什么

看一个 DaemonSet Pod 的容忍和亲和。下面这组命令是在上一节加容忍之前跑的（01:18:44，patch 在 01:19:01）；加完容忍后再查，会多出一条 control-plane 容忍，共 7 条：

P=$(kubectl -n notes-lab get pod -l app=node-agent -o jsonpath='{.items[0].metadata.name}')
kubectl -n notes-lab get pod $P -o jsonpath='{range .spec.tolerations[*]}{.key}{"\t"}{.operator}{"\t"}{.effect}{"\n"}{end}'
kubectl -n notes-lab get pod $P -o jsonpath='{.spec.affinity}'
node.kubernetes.io/not-ready	Exists	NoExecute
node.kubernetes.io/unreachable	Exists	NoExecute
node.kubernetes.io/disk-pressure	Exists	NoSchedule
node.kubernetes.io/memory-pressure	Exists	NoSchedule
node.kubernetes.io/pid-pressure	Exists	NoSchedule
node.kubernetes.io/unschedulable	Exists	NoSchedule
---
{"nodeAffinity":{"requiredDuringSchedulingIgnoredDuringExecution":{"nodeSelectorTerms":[{"matchFields":[{"key":"metadata.name","operator":"In","values":["worker2"]}]}]}}}

当时模板里一条容忍都没写，控制器自己补了 6 条：

  • not-ready / unreachable 是 NoExecute，没有 tolerationSeconds。普通 Pod 默认只容忍这两个污点 300 秒，之后会被驱逐；DaemonSet Pod 无限期容忍，节点失联也不会被赶走——反正赶走了也没地方去。
  • 三个 pressure 和 unschedulable 是 NoSchedule。unschedulable 这一条意味着节点被 cordon 之后，DaemonSet Pod 照样能调度上去；kubectl drain 不驱逐 DaemonSet Pod、要求显式加 --ignore-daemonsets，也和这一点有关，见节点维护。
  • 官方文档列的第 7 条 network-unavailable 这里没有，它只加给 hostNetwork: true 的 Pod。

注意这份默认清单里没有控制平面污点，所以上一节必须自己加。

亲和那一行是 DaemonSet 的调度方式：控制器为每个目标节点创建一个 Pod，并写上 matchFields: metadata.name In [节点名]，把它钉死在这个节点上，之后再由默认调度器完成绑定。轮询脚本里能看到这个过程——新 Pod 刚出现时 NODE 是 <none>，一秒后才有节点名：

--- 01:23:09
labeled-agent-xlvkx   <none>   Pending   <none>   <none>   86dcdffc6
--- 01:23:10
labeled-agent-xlvkx   worker   Pending   false   <none>   86dcdffc6

走默认调度器意味着资源、端口这些调度检查对 DaemonSet Pod 一样生效，后面 hostPort 的故障就是这么来的。

节点标签增删时 Pod 的去留

再建一个只跑在带 notes-lab.io/agent=on 标签节点上的 DaemonSet。容器里用 trap 捕获 SIGTERM，被删除时会打一行日志。保存为 labeled.yaml：

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: labeled-agent
spec:
  selector:
    matchLabels:
      app: labeled-agent
  template:
    metadata:
      labels:
        app: labeled-agent
    spec:
      terminationGracePeriodSeconds: 2
      nodeSelector:
        notes-lab.io/agent: "on"
      containers:
        - name: agent
          image: busybox:1.36
          command: ["sh", "-c", "trap 'echo got SIGTERM; exit 0' TERM; while true; do sleep 1; done"]
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              memory: 32Mi
kubectl -n notes-lab apply -f labeled.yaml
kubectl -n notes-lab get ds labeled-agent

刚创建时没有节点匹配，DESIRED 是 0，事件为空，看起来什么都没发生：

NAME            DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR           AGE
labeled-agent   0         0         0       0            0           notes-lab.io/agent=on   6s
Events:            <none>

kubectl label node worker notes-lab.io/agent=on

01:23:30 再把标签去掉，同时用 logs -f 在后台盯着容器输出：

标签去掉两秒后控制器就删除了 Pod，走的是正常的优雅终止，容器收到了 SIGTERM。

这和普通 Pod 不一样。字段名 requiredDuringSchedulingIgnoredDuringExecution 后半截的 IgnoredDuringExecution 说的就是（nodeSelector 语义相同）：调度后节点标签变了，已经在跑的 Pod 不受影响。为了对照，准备一个同样 nodeSelector 的裸 Pod，保存为 plain.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: plain-pod
spec:
  terminationGracePeriodSeconds: 2
  nodeSelector:
    notes-lab.io/agent: "on"
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
        limits:
          memory: 32Mi

给 worker2 打上标签，让裸 Pod 和 DaemonSet 的 Pod 都落到 worker2，再去掉标签：

kubectl label node worker2 notes-lab.io/agent=on
kubectl -n notes-lab apply -f plain.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/plain-pod --timeout=60s
kubectl -n notes-lab wait --for=condition=Ready pod -l app=labeled-agent --timeout=60s
kubectl -n notes-lab get pod -o wide
kubectl label node worker2 notes-lab.io/agent-
sleep 15; kubectl -n notes-lab get pod -o wide

去标签之前（node-agent 的三行略去）：

NAME                  READY   STATUS    RESTARTS   AGE     IP          NODE
labeled-agent-pmwf2   1/1     Running   0          7s      <pod-ip>    worker2
plain-pod             1/1     Running   0          7s      <pod-ip>    worker2

去掉 worker2 的标签，15 秒后（node-agent 的三行略去）：

NAME               READY   STATUS    RESTARTS   AGE     IP          NODE
plain-pod          1/1     Running   0          22s     <pod-ip>    worker2

裸 Pod 还在，DaemonSet 的 Pod 已经没了。删除它的不是调度器，而是 DaemonSet 控制器：它在每次同步时重新计算「哪些节点该有 Pod」，对不再符合条件的节点直接删除 Pod。这是普通的删除，不走 Eviction API，PodDisruptionBudget 也拦不住。所以给节点改标签之前，先查一下有没有 DaemonSet 依赖这个标签，否则可能一条命令就把某个节点上的日志采集或网络代理撤掉了。

模板里的 required 节点亲和在 Pod 上被替换

把 nodeSelector 换成「除了标了 off 的节点都跑」，保存为 affinity-patch.yaml：

spec:
  template:
    spec:
      nodeSelector: null
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: notes-lab.io/agent
                    operator: NotIn
                    values: ["off"]
kubectl -n notes-lab patch ds labeled-agent --patch-file affinity-patch.yaml

两个工作节点都没有这个标签，NotIn 成立，DESIRED 变成 2（控制平面仍被污点挡掉）。然而看新 Pod 的亲和：

worker
{"nodeAffinity":{"requiredDuringSchedulingIgnoredDuringExecution":{"nodeSelectorTerms":[{"matchFields":[{"key":"metadata.name","operator":"In","values":["worker"]}]}]}}}

自己写的 NotIn 表达式在 Pod 上完全找不到，requiredDuringSchedulingIgnoredDuringExecution 被控制器换成了只有节点名的那一条。官方文档也是这么写的：模板里的节点亲和用于控制器挑选节点，在创建出的 Pod 上会被替换。被替换的只是 required 这部分；preferred 亲和和 nodeSelector 按源码会原样保留在 Pod 上，这次没有单独验证。所以排查「为什么某节点没有 DaemonSet Pod」时，去看 DaemonSet 的模板，而不是看 Pod 的 spec.affinity。

给 worker2 打上 notes-lab.io/agent=off，10 秒内它上面的 Pod 就被删除了，DESIRED 降到 1：

NAME            DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
labeled-agent   1         1         1       1            1           <none>          107s

三种更新方式

RollingUpdate + maxUnavailable：先删后建

默认的更新策略是：

{"rollingUpdate":{"maxSurge":0,"maxUnavailable":1},"type":"RollingUpdate"}

前面加容忍那次滚动就是用的这个默认值。把 worker 上旧 Pod w78lh 和新 Pod mk5r6 的事件对起来，旧 Pod 的最后一条：

2026-10-13T01:19:18Z   Killing     Stopping container agent

新 Pod：

2026-10-13T01:19:27Z   Pulled      Container image "busybox:1.36" already present on machine
2026-10-13T01:19:28Z   Created     Created container agent
2026-10-13T01:19:28Z   Started     Started container agent

旧 Pod 01:19:18 开始停止。这个程序不理 SIGTERM（见本节最后一段），容器要到 2 秒宽限期满、01:19:20 左右才被杀掉；新 Pod 01:19:28 启动，从旧容器真正退出算起，worker 上大约 8 秒没有代理在跑。镜像已经在节点上，推测这 8 秒主要花在旧 Pod 收尾和新 Pod 创建沙箱上，各占多少没有单独测。

新 Pod 是什么时候建出来的？轮询里 01:19:24 这一帧：

--- 01:19:24
node-agent-9swq4   control-plane   Running   true     <none>                 5d66bb45cd
node-agent-vvn7g   worker2         Running   true     <none>                 646c7bb897
node-agent-w78lh   worker          Failed    false    2026-10-13T01:19:20Z   646c7bb897
node-agent-mk5r6   worker          Pending   <none>   <none>                 5d66bb45cd

旧 Pod w78lh 对象还在，但已经进入终态 Failed，新 Pod mk5r6 就建出来了；01:19:34 的 worker2 上也是同样的情形。控制器等的不是旧 Pod 对象消失，而是它带着 deletionTimestamp 进入终态（Failed / Succeeded），这时它就不再算作这个节点上的 Pod（对照 v1.31 源码中 getNodesToDaemonPods 的过滤逻辑）。对日志采集这类组件，这个空窗意味着可能漏掉一小段日志（推测，取决于采集器是否从文件断点续读）。

轮询里还有一个细节：被替换的旧 Pod 最后的 phase 是 Failed，而上一节带 trap 的 Pod 是 Succeeded。这个代理的 shell 作为 PID 1 没有处理 SIGTERM，推测是等满 2 秒宽限期后被 SIGKILL 才退出，所以记为失败。真实的节点代理要正确处理 SIGTERM，否则每次滚动都要等满宽限期。

RollingUpdate + maxSurge：先建后删

kubectl -n notes-lab patch ds node-agent --type merge \
  -p '{"spec":{"updateStrategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":1,"maxUnavailable":0}}}}'

然后把启动日志改成 v2。这次我连着执行了两条命令，先加了个环境变量，再 patch 了 command：

kubectl -n notes-lab set env ds/node-agent VERSION=v2
kubectl -n notes-lab patch ds node-agent --type json \
  -p '[{"op":"replace","path":"/spec/template/spec/containers/0/command/2","value":"echo \"v2 start $(date +%T) on $NODE\"; while true; do sleep 30; done"}]'
bash watch.sh 45

node-agent-mk5r6   worker          Running   true     2026-10-13T01:20:21Z   5d66bb45cd

（为便于阅读，后两段只保留了 worker 的两行。）

worker2 的新 Pod bnjcc 直到 01:20:20 才创建，因为 maxSurge: 1 是整个 DaemonSet 共用的额度，不是每个节点各一个：此前这个额度一直被 worker 上的 surge Pod htfnr 占着，01:20:20 worker 的旧 Pod mk5r6 开始删除、额度释放，控制器才轮到 worker2。同一帧里还能看到 surge 模式下控制器不等旧 Pod 终止：bnjcc 创建时，正在删除的 wrfqz 还是 Running：

--- 01:20:20
node-agent-bnjcc   <none>                             Pending   <none>   <none>                 7cd7d9487d
node-agent-9swq4   control-plane   Running   true     <none>                 5d66bb45cd
node-agent-8z547   worker2         Running   true     <none>                 5d66bb45cd
node-agent-wrfqz   worker2         Running   true     2026-10-13T01:20:10Z   85788c4f7
node-agent-htfnr   worker          Running   true     <none>                 7cd7d9487d
node-agent-mk5r6   worker          Running   true     2026-10-13T01:20:21Z   5d66bb45cd
  • worker 上新 Pod htfnr 01:20:19 就绪，旧 Pod mk5r6 01:20:20 才开始删除。有一秒钟同一节点上跑着两个代理，没有空窗。worker2 上更干净：旧 Pod 8z547 一直 Running，直到 01:20:28 新 Pod bnjcc 就绪的那一帧才被打上删除标记。官方更新文档里「更新过程中每个节点最多一个 Pod」那句话，只在 maxSurge: 0 时成立。
  • 意外的是 wrfqz：第一条命令生成了 revision 3（hash 85788c4f7），控制器立刻在 worker2 上起了一个 surge Pod；紧接着第二条命令（两条都在 01:20:07 执行）生成 revision 4，这个 Pod 在 01:20:08 还是 Pending 时就被打上了 deletionTimestamp。但它的容器照样启动了：轮询里它从 01:20:17 到 01:20:22 的几帧都是 Running true，01:20:24 才变成 Failed。也就是说，中间版本的容器真的跑起来并且 Ready 了，至少约 5 秒。多处修改最好合并成一次 apply，否则控制器会为每个中间版本动手。

三个节点依次替换，整个过程在 01:20:42 结束。

OnDelete：改模板不动 Pod

kubectl -n notes-lab patch ds node-agent --type merge -p '{"spec":{"updateStrategy":{"type":"OnDelete","rollingUpdate":null}}}'

这一步在下一节的 rollout undo --to-revision=2（01:21:21）之后做，此时三个 Pod 已经回滚到 v1。01:21:56 把模板改成 v3：

kubectl -n notes-lab patch ds node-agent --type json \
  -p '[{"op":"replace","path":"/spec/template/spec/containers/0/command/2","value":"echo \"v3 start $(date +%T) on $NODE\"; while true; do sleep 30; done"}]'
sleep 20
kubectl -n notes-lab get ds node-agent
kubectl -n notes-lab rollout status ds/node-agent --timeout=5s

20 秒后：

NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
node-agent   3         3         3       0            3           <none>          3m47s
error: rollout status is only available for RollingUpdate strategy type

UP-TO-DATE 为 0，三个 Pod 都还是旧版本；rollout status 在 OnDelete 下直接不可用。只有手动删掉的 Pod 才会按新模板重建：

kubectl -n notes-lab delete pod node-agent-vkqxs
2026-10-13T01:22:21Z   node-agent-vkqxs   Killing            Stopping container agent
2026-10-13T01:22:25Z   node-agent         SuccessfulCreate   (combined from similar events): Created pod: node-agent-ltf7q
2026-10-13T01:22:28Z   node-agent-ltf7q   Started            Started container agent
NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
node-agent   3         3         3       1            3           <none>          4m14s
[pod/node-agent-6r9k2/agent] v1 start 01:21:43 on worker2
[pod/node-agent-ltf7q/agent] v3 start 01:22:28 on worker
[pod/node-agent-vtrt7/agent] v1 start 01:21:24 on control-plane

删除 01:22:21 发出。程序不理 SIGTERM，旧容器要到宽限期满、01:22:23 左右才被杀掉；新 Pod 01:22:25 创建，01:22:28 启动，从旧容器退出算起 worker 上约 5 秒没有代理。和前面 maxUnavailable 的滚动一样，控制器要等旧 Pod 进入终态才在这个节点上补新的。宽限期越长、程序越不理 SIGTERM，这个空窗就越长。

OnDelete 适合想自己控制每个节点何时升级的场景，比如先挑一台节点验证，或者配合节点重启一起做。代价是版本状态全靠 UP-TO-DATE 列自己盯。

ControllerRevision 与回滚

DaemonSet 没有 ReplicaSet 这一层，历史版本存在 ControllerRevision 对象里，Pod 上的 controller-revision-hash 标签就对应它的名字：

kubectl -n notes-lab get controllerrevision
kubectl -n notes-lab rollout history ds/node-agent --revision=3
NAME                    CONTROLLER                  REVISION   AGE
node-agent-5d66bb45cd   daemonset.apps/node-agent   2          2m13s
node-agent-646c7bb897   daemonset.apps/node-agent   1          2m47s
node-agent-7cd7d9487d   daemonset.apps/node-agent   4          69s
node-agent-85788c4f7    daemonset.apps/node-agent   3          69s
daemonset.apps/node-agent with revision #3
Pod Template:
  Labels:	app=node-agent
  Containers:
   agent:
    Image:	busybox:1.36
    ...
    Command:
      sh
      -c
      echo "v1 start $(date +%T) on $NODE"; while true; do sleep 30; done
    ...
    Environment:
      NODE:	 (v1:spec.nodeName)
      VERSION:	v2
    ...
  Tolerations:	node-role.kubernetes.io/control-plane:NoSchedule op=Exists

revision 3 正是上面那个只加了环境变量、还没改 command 的中间版本，它和其他版本一样被保留了下来。保留数量由 spec.revisionHistoryLimit 控制，默认 10。

回到 revision 2：

kubectl -n notes-lab rollout undo ds/node-agent --to-revision=2
NAME                    CONTROLLER                  REVISION   AGE
node-agent-5d66bb45cd   daemonset.apps/node-agent   5          2m45s
node-agent-646c7bb897   daemonset.apps/node-agent   1          3m19s
node-agent-7cd7d9487d   daemonset.apps/node-agent   4          101s
node-agent-85788c4f7    daemonset.apps/node-agent   3          101s

没有新建对象，原来的 node-agent-5d66bb45cd 编号从 2 变成了 5，revision 2 从历史里消失。回滚就是「把模板改成旧版本的内容」，同样走滚动更新，三个 Pod 都换成了 v1。之后再想回到「回滚前的上一个版本」，要按新的编号找，别凭记忆填 --to-revision。

故障一：坏镜像让滚动更新停住

先从 OnDelete 切回 RollingUpdate：

kubectl -n notes-lab patch ds node-agent --type merge \
  -p '{"spec":{"updateStrategy":{"type":"RollingUpdate","rollingUpdate":{"maxUnavailable":1,"maxSurge":0}}}}'
kubectl -n notes-lab rollout status ds/node-agent --timeout=120s
kubectl -n notes-lab logs -l app=node-agent --prefix

切换本身不改 Pod 模板，但另外两个还停在 v1 的 Pod 立刻按 RollingUpdate 被换成了 v3：

Waiting for daemon set "node-agent" rollout to finish: 2 out of 3 new pods have been updated...
Waiting for daemon set "node-agent" rollout to finish: 2 out of 3 new pods have been updated...
Waiting for daemon set "node-agent" rollout to finish: 2 of 3 updated pods are available...
daemon set "node-agent" successfully rolled out
[pod/node-agent-xc58w/agent] v3 start 01:25:24 on control-plane
[pod/node-agent-bmv59/agent] v3 start 01:25:10 on worker2
[pod/node-agent-ltf7q/agent] v3 start 01:22:28 on worker

OnDelete 期间攒下的未更新 Pod，会在切回 RollingUpdate 的那一刻一起开始滚动。然后故意写错镜像标签：

kubectl -n notes-lab set image ds/node-agent agent=busybox:1.36-typo

45 秒后：

NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
node-agent   3         3         2       1            2           <none>          7m40s
NAME               READY   STATUS         RESTARTS   AGE   IP          NODE
node-agent-bmv59   1/1     Running        0          67s   <pod-ip>    worker2
node-agent-gbcm5   0/1     ErrImagePull   0          39s   <pod-ip>    worker
node-agent-xc58w   1/1     Running        0          50s   <pod-ip>    control-plane
Waiting for daemon set "node-agent" rollout to finish: 1 out of 3 new pods have been updated...
error: timed out waiting for the condition

控制器删掉了 worker 上的旧 Pod，新 Pod 拉不到镜像，因为 maxUnavailable: 1 已经用完，它不会再动另外两个节点。读这张表：UP-TO-DATE 1 说明只换了一台，READY 2 比 DESIRED 3 少一个，再到 -o wide 里找那个不 Ready 的 Pod 在哪个节点。损失被限制在一个节点上，但这个节点的代理是真没了，不会自己恢复。

修复就是再改一次模板，回滚最快：

kubectl -n notes-lab rollout undo ds/node-agent
daemon set "node-agent" successfully rolled out
NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
node-agent   3         3         3       3            3           <none>          8m27s
[pod/node-agent-bmv59/agent] v3 start 01:25:10 on worker2
[pod/node-agent-kjw82/agent] v3 start 01:26:52 on worker
[pod/node-agent-xc58w/agent] v3 start 01:25:24 on control-plane

worker2 和 control-plane 上的 Pod 名字和启动时间都没变，只有 worker 换了新 Pod。回滚的目标版本和它们现在的版本 hash 相同，控制器不会去重建它们。不带 --to-revision 时 undo 回到上一个版本，这里正是坏镜像之前的 v3。

故障二：hostPort 遇上 maxSurge

节点代理经常要用 hostPort 或 hostNetwork 暴露端口。下面这个 DaemonSet 占用节点的 39481 端口，更新策略是 maxSurge: 1, maxUnavailable: 0，保存为 hostport.yaml：

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: port-a
spec:
  selector:
    matchLabels:
      app: port-a
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: port-a
    spec:
      terminationGracePeriodSeconds: 2
      containers:
        - name: web
          image: nginx:alpine
          ports:
            - containerPort: 80
              hostPort: 39481
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              memory: 32Mi
kubectl -n notes-lab apply -f hostport.yaml
kubectl -n notes-lab rollout status ds/port-a --timeout=90s

两个工作节点上的 Pod 正常运行后，随便改一个环境变量触发更新：

kubectl -n notes-lab set env ds/port-a VERSION=v2
NAME     DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
port-a   2         2         2       0            2           <none>          116s
NAME           READY   STATUS    RESTARTS   AGE    IP         NODE
port-a-84qgn   0/1     Pending   0          26s    <none>     <none>
port-a-llt4q   1/1     Running   0          111s   <pod-ip>   worker2
port-a-m6f26   1/1     Running   0          112s   <pod-ip>   worker
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  34s   default-scheduler  0/3 nodes are available: 1 node(s) didn't have free ports for the requested pod ports. preemption: 0/3 nodes are available: 1 No preemption victims found for incoming pod, 2 Preemption is not helpful for scheduling.

surge Pod 要和旧 Pod 在同一节点上同时存在，端口却已经被旧 Pod 占着，调度器放不下它；旧 Pod 又要等新 Pod 就绪才会删除。两边互相等，又过了 40 秒仍是同样状态，rollout status 超时。这里不会有任何 Pod 崩溃，旧版本照常服务，只是更新永远不会前进，比坏镜像更难察觉。

消息里的「0/3 nodes … 1 node(s) didn’t have free ports」也值得留意：只有一个节点给出了端口冲突的原因。因为这个 Pod 被 matchFields 钉在一个节点上，另外两个节点从一开始就不在考虑范围内（推测它们对应后半句的「2 Preemption is not helpful」）。看到 DaemonSet Pod 的 FailedScheduling，只需关心它被钉住的那一个节点。

改回先删后建，更新立刻继续，34 秒走完：

kubectl -n notes-lab patch ds port-a --type merge \
  -p '{"spec":{"updateStrategy":{"rollingUpdate":{"maxSurge":0,"maxUnavailable":1}}}}'
daemon set "port-a" successfully rolled out
NAME           READY   STATUS    RESTARTS   AGE   IP         NODE
port-a-fchpr   1/1     Running   0          11s   <pod-ip>   worker
port-a-xr4jx   1/1     Running   0          25s   <pod-ip>   worker2

结论：用了 hostPort 的 DaemonSet 不能用 maxSurge，只能接受每个节点一小段空窗。这次只测了 hostPort。hostNetwork: true 的情况推测要分两种：如果容器声明了 ports，调度器同样会做端口检查，结果应该和这里一样卡在 Pending；如果没声明，新 Pod 能调度上去，但会在绑定已被占用的端口时启动失败。

同一个端口被两个 DaemonSet 抢，是同一类问题的另一种样子。把上面的清单换个名字 port-b 再部署一份：

sed 's/port-a/port-b/g' hostport.yaml > hostport-b.yaml
kubectl -n notes-lab apply -f hostport-b.yaml
NAME     DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
port-a   2         2         2       2            2           <none>          4m2s
port-b   2         2         0       2            0           <none>          20s

port-b 的两个 Pod 都 Pending，报同样的 didn't have free ports。注意 CURRENT 是 2：Pending、还没绑定节点的 Pod 也算进了 CURRENT。判断 DaemonSet 是否健康要看 READY / AVAILABLE 和 DESIRED 是否相等，CURRENT 等于 DESIRED 说明不了什么。

清理

kubectl label node worker2 notes-lab.io/agent-
kubectl delete namespace notes-lab

节点标签不属于任何 namespace，删 namespace 不会带走它，要单独去掉。

DaemonSet 的落点同时受污点、nodeSelector 和节点亲和影响，规则细节见 Pod 调度和污点与容忍；需要稳定身份和存储的副本型工作负载见 StatefulSet。
