先确定故障停在哪一层

应用访问 http://web 看似只发一个请求，实际要走三段：DNS 把名字解析成 Service 的 ClusterIP，kube-proxy 写在节点上的规则把 ClusterIP 换成某个后端 Pod IP，最后由 CNI 插件铺好的路由把包送到那个 Pod。Service 和 DNS 排查分别讲过前两段。不要把所有「网络不通」都归因于 CNI：下面复现的四种故障里，两种是 NetworkPolicy 写法的问题（策略由 CNI 执行，但 CNI 本身工作正常），另外两种是 Service 配置错误，与 CNI 无关。

下文的输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico，kube-proxy 为 iptables 模式），实验放在单独的 notes-lab namespace 里。节点名简化成 control-plane、worker、worker2；Pod IP、节点 IP、ClusterIP 用 <client-ip>、<worker-ip>、<cluster-ip> 这类占位符代替。

实验环境

先确认集群用的是什么 CNI、kube-proxy 跑在哪种模式，后面看到的路由和规则才对得上号。这个集群的 Calico 组件在 calico-system 下，不在 kube-system，按固定名称去 kube-system 找是找不到的：

kubectl get pods -A -o wide | grep -Ei "calico|coredns|kube-proxy"
kubectl -n kube-system get cm kube-proxy -o jsonpath='{.data.config\.conf}' | grep -E '^mode|clusterCIDR'
...

calico-system  calico-node-sblhg                         1/1  Running  41             60d  ...  worker

Calico 的地址池配置决定了跨节点流量走不走隧道：

$ kubectl get ippools.crd.projectcalico.org default-ipv4-ippool -o jsonpath='{.spec}'
{"allowedUses":["Workload","Tunnel"],"assignmentMode":"Automatic","blockSize":26,"cidr":"192.168.0.0/16","ipipMode":"Never","natOutgoing":true,"nodeSelector":"all()","vxlanMode":"CrossSubnet"}

vxlanMode: CrossSubnet 表示只有跨子网的节点之间才做 VXLAN 封装。kind 的三个节点在同一个 Docker 网段里，所以按这个配置，节点间应该是直接路由，后面的路由表会印证这一点。

把下面的清单保存为 lab.yaml。实验对象：一个两副本的 web（traefik/whoami，会在响应里回显自己的 Hostname 和对端地址），用 Pod 反亲和让两个副本分到 worker 和 worker2；一个固定在 worker 上的 busybox 客户端；一个普通的 ClusterIP Service。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: web
              topologyKey: kubernetes.io/hostname
      containers:
        - name: whoami
          image: traefik/whoami:v1.10.2
          ports:
            - containerPort: 80
          resources:
            requests: {cpu: 20m, memory: 32Mi}
            limits: {memory: 64Mi}
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
---
apiVersion: v1
kind: Pod
metadata:
  name: client
  labels:
    app: client
spec:
  nodeSelector:
    kubernetes.io/hostname: worker   # 换成你的节点名
  containers:
    - name: sh
      image: busybox:1.36
      command: ["sh", "-c", "sleep 36000"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 32Mi}
kubectl create namespace notes-lab
kubectl -n notes-lab apply -f lab.yaml
kubectl -n notes-lab wait --for=condition=Ready pod --all --timeout=180s

web-78b9f97946-kn48l   1/1     Running   0          4s    <web-a-ip>    worker

web-a 和客户端在同一节点，web-b 在另一个节点，这样同节点和跨节点路径可以分开看。

第一层：Pod IP 是否可达

Pod 里看到的网络

kubectl -n notes-lab exec client -- ip addr show eth0
kubectl -n notes-lab exec client -- ip route
2: eth0@if478: <BROADCAST,MULTICAST,UP,LOWER_UP,M-DOWN> mtu 1450 qdisc noqueue qlen 1000
    link/ether fe:a2:81:cf:f2:14 brd ff:ff:ff:ff:ff:ff
    inet <client-ip>/32 scope global eth0
...
default via 169.254.1.1 dev eth0 
169.254.1.1 dev eth0 scope link

和常见的「Pod 在一个 /24 网段里、网关是网桥」不一样，Calico 给 Pod 的是 /32 地址，默认网关是一个并不存在的 169.254.1.1。Pod 里不存在「同网段直连」，任何目的地址都要先交给这个网关。eth0@if478 说明这块网卡是 veth 的一端，对端是节点上编号 478 的接口。按编号找接口名可以用 docker exec worker ip -o link | grep '^478:'，找到名字后查看它：

$ docker exec worker ip -o link show cali60537bb0411
478: cali60537bb0411@if2: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1450 ... link/ether ee:ee:ee:ee:ee:ee brd ff:ff:ff:ff:ff:ff link-netns cni-f8e1d211-...
$ docker exec worker cat /proc/sys/net/ipv4/conf/cali60537bb0411/proxy_arp
1

kind 的节点本身是 Docker 容器，所以可以用 docker exec <节点> 只读地查看节点网络。节点侧的 cali* 接口开着 proxy_arp，MAC 统一是 ee:ee:ee:ee:ee:ee。Pod 向 169.254.1.1 发 ARP 请求时，由这个接口代答。刚启动、还没发过流量时，ip neigh 的输出是空的，下文访问过其他 Pod 之后再看。

另外注意 Pod 网卡的 MTU 是 1450，而节点自己的 eth0 是 1500：

$ docker exec worker ip link show eth0
2: eth0@if58: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP mode DEFAULT group default 
$ docker exec worker ip -o link show vxlan.calico
5: vxlan.calico: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1450 ...

MTU 没有手工配置，是 Calico 自动探测的：operator 的 Installation 对象里 spec.calicoNetwork.mtu 为空，status.mtu 是 1450。

$ kubectl get installation default -o jsonpath='{.spec.calicoNetwork.mtu}{"|"}{.status.mtu}{"\n"}'
|1450

Calico 文档给的 IPv4 VXLAN 头部是 50 字节，1500 − 50 = 1450，正好是这里的值。CrossSubnet 下 VXLAN 是启用的（只是同子网的节点之间不用），推测 Calico 就是按 VXLAN 的开销自动探测出 1450，再统一用在所有 Pod 网卡上，哪怕本集群的节点间流量实际不封装。

节点上的路由

$ docker exec worker ip route | grep 192.168
blackhole <worker-block>/26 proto 80 
<web-a-ip> dev calib5519a774fd scope link metric 1024 
<client-ip> dev cali60537bb0411 scope link metric 1024 
...
<control-plane-block>/26 via <control-plane-ip> dev eth0 proto 80 onlink 
<worker2-block>/26 via <worker2-ip> dev eth0 proto 80 onlink 
$ docker exec worker2 ip route | grep 192.168
<worker-block>/26 via <worker-ip> dev eth0 proto 80 onlink 
<control-plane-block>/26 via <control-plane-ip> dev eth0 proto 80 onlink 
blackhole <worker2-block>/26 proto 80 
...
<web-b-ip> dev calif73f77523ff scope link metric 1024 
...

这几行就是 Calico 在节点上铺的全部路径：

  • 本节点每个 Pod 一条 /32 路由，指向它的 cali* 接口。
  • 其他节点的地址块（blockSize: 26，每块 64 个地址）各一条路由，下一跳直接是对方节点的 IP、出口是 eth0。节点上虽然有 vxlan.calico 设备，但没有路由指向它，印证了 CrossSubnet 下同子网不封装。
  • 本节点自己的地址块有一条 blackhole：块内没有分配出去的地址直接丢弃，不会被默认路由发到别处。

同节点与跨节点

kubectl -n notes-lab exec client -- wget -qO- -T 3 http://<web-a-ip>/ | grep -E "Hostname|IP: 192|RemoteAddr"
kubectl -n notes-lab exec client -- wget -qO- -T 3 http://<web-b-ip>/ | grep -E "Hostname|IP: 192|RemoteAddr"
Hostname: web-78b9f97946-kn48l
IP: <web-a-ip>
RemoteAddr: <client-ip>:59806
Hostname: web-78b9f97946-6kcns
IP: <web-b-ip>
RemoteAddr: <client-ip>:46554

（IP: 192 用来从 whoami 列出的多个地址里只留下 Pod 网段那一行，换成你集群的 Pod 网段前缀。）两边看到的 RemoteAddr 都是客户端的 Pod IP，跨节点也没有做源地址转换，这正是 Kubernetes 网络模型要求的「Pod 之间不经 NAT 直接通信」。

现在再看邻居表，刚才的空表里多了网关这一条：

$ kubectl -n notes-lab exec client -- ip neigh
169.254.1.1 dev eth0 lladdr ee:ee:ee:ee:ee:ee ref 1 used 0/0/0 probes 4 REACHABLE

MAC 正是节点侧 cali* 接口的 ee:ee:ee:ee:ee:ee。路径差别用 traceroute 看得更清楚：

$ kubectl -n notes-lab exec client -- traceroute -n -w 2 -m 5 <web-a-ip>
 1  <worker-ip>  0.005 ms  0.002 ms  0.003 ms
 2  <web-a-ip>  0.002 ms  0.002 ms  0.002 ms
$ kubectl -n notes-lab exec client -- traceroute -n -w 2 -m 5 <web-b-ip>
 1  <worker-ip>  0.004 ms  0.002 ms  0.001 ms
 2  <worker2-ip>  0.002 ms  0.002 ms  0.002 ms
 3  <web-b-ip>  0.002 ms  0.002 ms  0.002 ms

同节点两跳（本节点 → 目标 Pod），跨节点三跳，中间正是路由表里那个下一跳 <worker2-ip>。ping 的 TTL 也对得上：同节点回包 ttl=63，跨节点 ttl=62。

所以第一层要分开测同节点和跨节点。同节点通只能说明 veth 和本机路由正常；跨节点不通时，顺着 traceroute 停下的那一跳，去查对方节点的路由、节点间防火墙和 calico-node 的状态。

第二层：Service 到后端

$ kubectl -n notes-lab get svc web -o wide
NAME   TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE   SELECTOR
web    ClusterIP   <cluster-ip>   <none>        80/TCP    22s   app=web
$ kubectl -n notes-lab get endpointslices -l kubernetes.io/service-name=web
NAME        ADDRESSTYPE   PORTS   ENDPOINTS                 AGE
web-nk2nh   IPv4          80      <web-b-ip>,<web-a-ip>     22s

ClusterIP 不属于任何网卡，它只存在于每个节点的 iptables 规则里。按 namespace/Service 名过滤 nat 表，就能看到这个 Service 的全部转发规则：

docker exec worker iptables-save -t nat | grep "notes-lab/web"
-A KUBE-SEP-EDYWJHADPYGS77FK -s <web-a-ip>/32 -m comment --comment "notes-lab/web" -j KUBE-MARK-MASQ
-A KUBE-SEP-EDYWJHADPYGS77FK -p tcp -m comment --comment "notes-lab/web" -m tcp -j DNAT --to-destination <web-a-ip>:80
-A KUBE-SEP-NXZFC6CW4AYHBYUW -s <web-b-ip>/32 -m comment --comment "notes-lab/web" -j KUBE-MARK-MASQ
-A KUBE-SEP-NXZFC6CW4AYHBYUW -p tcp -m comment --comment "notes-lab/web" -m tcp -j DNAT --to-destination <web-b-ip>:80
-A KUBE-SERVICES -d <cluster-ip>/32 -p tcp -m comment --comment "notes-lab/web cluster IP" -m tcp --dport 80 -j KUBE-SVC-SNIOZU3EQWEFVC7N
-A KUBE-SVC-SNIOZU3EQWEFVC7N ! -s 192.168.0.0/16 -d <cluster-ip>/32 -p tcp -m comment --comment "notes-lab/web cluster IP" -m tcp --dport 80 -j KUBE-MARK-MASQ
-A KUBE-SVC-SNIOZU3EQWEFVC7N -m comment --comment "notes-lab/web -> <web-a-ip>:80" -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-EDYWJHADPYGS77FK
-A KUBE-SVC-SNIOZU3EQWEFVC7N -m comment --comment "notes-lab/web -> <web-b-ip>:80" -j KUBE-SEP-NXZFC6CW4AYHBYUW

这是 iptables-save 的原始顺序，按包的走向要从后四行倒着读：目的地址是 ClusterIP:80 的包跳进 KUBE-SVC-* 链；第一条后端以 0.5 的概率命中，没命中就落到第二条；KUBE-SEP-* 链做 DNAT，把目的地址改成具体的 Pod IP:端口。之后的路就回到第一层，由 Calico 的路由送达。来源不在 Pod 网段（! -s 192.168.0.0/16）的包会被打上 MASQ 标记做源地址转换。每个 KUBE-SEP-* 链里的 -s <后端自己的 IP> 那条是 hairpin 规则：Pod 经 Service 访问、恰好被分到自己时，如果不做源地址转换，回包的源和目的都是它自己，会在 Pod 内部直接投递，不经过节点上的反向 DNAT，连接对不上。普通的 Pod 之间互访两条都不命中，源 IP 保留，所以经 Service 访问时 RemoteAddr 仍是客户端的 Pod IP：

$ kubectl -n notes-lab exec client -- sh -c 'wget -qO- -T 3 http://web/ | grep RemoteAddr'
RemoteAddr: <client-ip>:43686

「随机」指的是每个新连接独立抽签，不是轮询。连续 6 次请求，5 次落在同一个后端：

$ kubectl -n notes-lab exec client -- sh -c 'for i in 1 2 3 4 5 6; do wget -qO- -T 3 http://web/ | grep Hostname; done'
Hostname: web-78b9f97946-6kcns
Hostname: web-78b9f97946-6kcns
Hostname: web-78b9f97946-6kcns
Hostname: web-78b9f97946-kn48l
Hostname: web-78b9f97946-6kcns
Hostname: web-78b9f97946-6kcns

还有一个常被误判的现象：ping 不通 ClusterIP 是正常的。

$ kubectl -n notes-lab exec client -- ping -c 2 -W 2 <cluster-ip>
2 packets transmitted, 0 packets received, 100% packet loss
command terminated with exit code 1

上面的规则只匹配 -p tcp --dport 80，ICMP 包不会被 DNAT，也没有哪块网卡持有这个地址。iptables 模式下判断 Service 通不通，要用它真正暴露的协议和端口去连，不能用 ping。

第三层：名称到 ClusterIP

$ kubectl -n notes-lab exec client -- cat /etc/resolv.conf
search notes-lab.svc.cluster.local svc.cluster.local cluster.local localdomain
nameserver <dns-ip>
options ndots:5
$ kubectl -n kube-system get endpointslices -l kubernetes.io/service-name=kube-dns
NAME             ADDRESSTYPE   PORTS        ENDPOINTS                     AGE
kube-dns-7p7m6   IPv4          9153,53,53   <coredns-1>,<coredns-2>       60d

nameserver 本身也是一个 ClusterIP（kube-dns Service），所以 DNS 查询同样走第二层的 DNAT 和第一层的路由，最后到达 control-plane 上的两个 CoreDNS Pod。DNS 坏了，可能是 CoreDNS 本身的问题，也可能是通往 CoreDNS 的网络路径被挡住了，后面第二个故障就是后者。

用 busybox 排查 DNS 有个坑：解析成功了，nslookup 也可能返回退出码 1。

$ kubectl -n notes-lab exec client -- nslookup web
Server:		<dns-ip>
Address:	<dns-ip>:53


** server can't find web.cluster.local: NXDOMAIN

** server can't find web.cluster.local: NXDOMAIN

Name:	web.notes-lab.svc.cluster.local
Address: <cluster-ip>

** server can't find web.svc.cluster.local: NXDOMAIN

** server can't find web.svc.cluster.local: NXDOMAIN

** server can't find web.localdomain: NXDOMAIN

** server can't find web.localdomain: NXDOMAIN

command terminated with exit code 1

busybox 的 nslookup 有自己的一套逻辑，不走 libc 解析器：名字里不带点时，它给每个 search 域都拼一遍去查，并且 A 和 AAAA 各查一次，所以每个不存在的后缀会出现两遍 NXDOMAIN；只要有一个回复的 rcode 不为 0，退出码就是 1。名字里带点时，它原样查询，不拼 search 域，也不看 ndots：

$ kubectl -n notes-lab exec client -- nslookup web.notes-lab
Server:		<dns-ip>
Address:	<dns-ip>:53

** server can't find web.notes-lab: NXDOMAIN

** server can't find web.notes-lab: NXDOMAIN

command terminated with exit code 1
$ kubectl -n notes-lab exec client -- nslookup web.notes-lab.svc.cluster.local; echo exit=$?
Server:		<dns-ip>
Address:	<dns-ip>:53


Name:	web.notes-lab.svc.cluster.local
Address: <cluster-ip>

exit=0

ndots:5 只对 libc 解析器起作用：名字里的点少于 5 个时先拼 search 域，按这个规则，应用里写 web.notes-lab 会命中 web.notes-lab.svc.cluster.local（这一点本次没有单独测），busybox nslookup 却直接报 NXDOMAIN。所以用 busybox 测 DNS，要么查完整域名，要么看输出里有没有 Name:/Address:，不能只看退出码。同一个容器里的 wget http://web/ 走的是 libc 解析，前面已经证明能按短名访问。

三层都通的状态记下来，下面逐个弄坏。

故障一：NetworkPolicy 挡住入站，DNS 照常

给 web 加一条只声明 Ingress、不写任何放行规则的策略，等于对 web 默认拒绝所有入站。保存为 web-deny-ingress.yaml：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-deny-ingress
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
    - Ingress
kubectl -n notes-lab apply -f web-deny-ingress.yaml
$ kubectl -n notes-lab exec client -- nslookup web.notes-lab.svc.cluster.local
...
Name:	web.notes-lab.svc.cluster.local
Address: <cluster-ip>

$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://web/
wget: download timed out
command terminated with exit code 1
$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://<web-b-ip>/
wget: download timed out
command terminated with exit code 1
$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://<web-a-ip>/
wget: download timed out
command terminated with exit code 1
$ kubectl -n notes-lab get endpointslices -l kubernetes.io/service-name=web
NAME        ADDRESSTYPE   PORTS   ENDPOINTS                 AGE
web-nk2nh   IPv4          80      <web-b-ip>,<web-a-ip>     63s

这一组输出的特征：

  • DNS 正常，EndpointSlice 两个后端都在，第二、三层看起来都没问题。
  • 直接打 Pod IP 也失败，而且同节点、跨节点一起失败。路由坏了通常只影响跨节点，同节点也不通，就该先怀疑策略。
  • 失败方式是超时，不是拒绝。策略丢包时不回任何东西，客户端只能干等到超时。

策略在节点上的落点可以只读地确认。Calico 把每个 NetworkPolicy 编译成 iptables 链，注释里带着 namespace 和策略名：

$ docker exec worker2 iptables-save -t filter | grep notes-lab
-A cali-pi-_GZlz4BiKCVD4yAYzF8u -m comment --comment "cali:9p2Cs5k_KsD_OlIU" -m comment --comment "KubernetesNetworkPolicy notes-lab/web-deny-ingress ingress"
...

只取这条策略链自己的规则，结果只有这一行注释，没有任何放行规则：

$ docker exec worker2 iptables-save -t filter | grep -E '^-A cali-pi-_GZlz4BiKCVD4yAYzF8u '
-A cali-pi-_GZlz4BiKCVD4yAYzF8u -m comment --comment "cali:9p2Cs5k_KsD_OlIU" -m comment --comment "KubernetesNetworkPolicy notes-lab/web-deny-ingress ingress"

再看 web-b 那块 cali* 接口（calif73f77523ff，来自上面 worker2 的路由表）的入站链 cali-tw-<接口名>：

$ docker exec worker2 iptables-save -t filter | grep -E "^-A cali-tw-calif73f77523ff"
-A cali-tw-calif73f77523ff ... -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
...
-A cali-tw-calif73f77523ff ... -m comment --comment "Start of tier default" -j MARK --set-xmark 0x0/0x20000
-A cali-tw-calif73f77523ff ... -m mark --mark 0x0/0x20000 -j cali-pi-_GZlz4BiKCVD4yAYzF8u
-A cali-tw-calif73f77523ff ... -m comment --comment "Return if policy accepted" -m mark --mark 0x10000/0x10000 -j RETURN
...
-A cali-tw-calif73f77523ff ... -m comment --comment "End of tier default. Drop if no policies passed packet" -m mark --mark 0x0/0x20000 -j DROP
...

包进入策略链，没有规则给它打上「已接受」标记，返回后命中 Drop if no policies passed packet，这就是超时的来源。

修复是再加一条放行策略（web-allow-client.yaml）。NetworkPolicy 之间是并集关系，后加的这条不需要删掉默认拒绝：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-allow-client
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: client
      ports:
        - port: 80
kubectl -n notes-lab apply -f web-allow-client.yaml
$ kubectl -n notes-lab exec client -- sh -c 'wget -qO- -T 3 http://web/ | grep Hostname'
Hostname: web-78b9f97946-kn48l
$ kubectl -n notes-lab exec client -- ping -c 2 -W 2 <web-b-ip>
2 packets transmitted, 0 packets received, 100% packet loss
command terminated with exit code 1

HTTP 恢复了，ping 依然不通。放行规则只开了 TCP 80（port 不写协议时默认 TCP），ICMP 不在其中。在有 NetworkPolicy 的 namespace 里，ping 不通既不能说明网络断了，ping 通了也不能说明业务端口能连，测试一律用业务协议和端口。

进入下一个故障前删掉这两条策略：

kubectl -n notes-lab delete networkpolicy web-deny-ingress web-allow-client

故障二：出站策略忘了放行 DNS

反过来，在客户端这边做出站限制，只允许访问 web 的 80 端口，保存为 client-egress.yaml：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: client-egress
spec:
  podSelector:
    matchLabels:
      app: client
  policyTypes:
    - Egress
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: web
      ports:
        - port: 80
kubectl -n notes-lab apply -f client-egress.yaml
$ kubectl -n notes-lab exec client -- nslookup -timeout=2 web.notes-lab.svc.cluster.local
;; connection timed out; no servers could be reached

command terminated with exit code 1
$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://web/
wget: bad address 'web'
command terminated with exit code 1
$ kubectl -n notes-lab exec client -- sh -c 'wget -qO- -T 3 http://<cluster-ip>/ | grep Hostname'
Hostname: web-78b9f97946-kn48l

按名字访问报 bad address，看上去像 DNS 坏了，但 CoreDNS 好好的，是去往 CoreDNS 的 UDP 53 被出站策略丢了。用 ClusterIP 直接访问却是通的。规则里写的是 podSelector: app=web，而客户端发出的包目的地址原本是 ClusterIP，说明在这个集群里，出站策略看到的是 DNAT 之后的 Pod 地址。这只是本集群（Calico 加 iptables 模式 kube-proxy）的实测结果；官方文档在 ipBlock 一节说明，地址改写发生在策略处理之前还是之后没有定义，不同组合的行为可能不同。

「按名字失败、按 ClusterIP 成功」是区分 DNS 问题和转发问题最快的办法。修复是在 client-egress.yaml 的 egress 列表末尾补上 DNS 这一项，再 kubectl -n notes-lab apply -f client-egress.yaml：

- to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
  ports:
    - port: 53
      protocol: UDP
    - port: 53
      protocol: TCP
$ kubectl -n notes-lab exec client -- nslookup -timeout=2 web.notes-lab.svc.cluster.local
...
Name:	web.notes-lab.svc.cluster.local
Address: <cluster-ip>

$ kubectl -n notes-lab exec client -- sh -c 'wget -qO- -T 3 http://web/ | grep Hostname'
Hostname: web-78b9f97946-6kcns

namespaceSelector 和 podSelector 写在同一个 to 元素里是「且」的关系：kube-system 里带 k8s-app=kube-dns 标签的 Pod。拆成两个元素就变成「或」，放行范围会大得多。策略写法见 NetworkPolicy。

进入下一个故障前删掉这条策略。补上 DNS 的版本和第一版同名，kubectl apply 只是更新了同一个对象，所以删一次就够了：

kubectl -n notes-lab delete networkpolicy client-egress

故障三：targetPort 写错，端点在但被拒绝

保存为 web-badport.yaml：

apiVersion: v1
kind: Service
metadata:
  name: web-badport
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080   # 容器实际监听 80
kubectl -n notes-lab apply -f web-badport.yaml
$ kubectl -n notes-lab get endpointslices -l kubernetes.io/service-name=web-badport
NAME                ADDRESSTYPE   PORTS   ENDPOINTS                 AGE
web-badport-22stv   IPv4          8080    <web-a-ip>,<web-b-ip>     2s
$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://web-badport/
wget: can't connect to remote host (<cluster-ip>): Connection refused
command terminated with exit code 1
$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://<web-b-ip>:8080/
wget: can't connect to remote host (<web-b-ip>): Connection refused
command terminated with exit code 1

EndpointSlice 里后端齐全，Pod 也都 Ready，只看「有没有端点」会觉得一切正常。要看的是 PORTS 列：8080。节点规则也如实地 DNAT 到 8080：

$ docker exec worker iptables-save -t nat | grep "notes-lab/web-badport" | grep DNAT
-A KUBE-SEP-DQBKX6RH2QWKODXK -p tcp -m comment --comment "notes-lab/web-badport" -m tcp -j DNAT --to-destination <web-b-ip>:8080
-A KUBE-SEP-RODMZDWT5JUWISS4 -p tcp -m comment --comment "notes-lab/web-badport" -m tcp -j DNAT --to-destination <web-a-ip>:8080

包确实送到了 Pod，是 Pod 的内核发现 8080 没有进程监听，回了 RST，于是报 Connection refused。Kubernetes 不会拿 targetPort 去和容器声明的 containerPort 比对：Pod 上明明只声明了 80，Service 照样被接受，EndpointSlice 照样生成。

定位方法是用 EndpointSlice 里的「Pod IP:端口」原样去连（上面第三条命令）。同样被拒绝，就是端口不对，与 Service 无关；能连上，再回头查 Service 和 kube-proxy。

故障四：选择器不匹配，没有端点也是 Connection refused

保存为 web-badsel.yaml：

apiVersion: v1
kind: Service
metadata:
  name: web-badsel
spec:
  selector:
    app: web-v2      # 实际 Pod 的标签是 app=web
  ports:
    - port: 80
      targetPort: 80
kubectl -n notes-lab apply -f web-badsel.yaml
$ kubectl -n notes-lab get endpointslices -l kubernetes.io/service-name=web-badsel
NAME               ADDRESSTYPE   PORTS     ENDPOINTS   AGE
web-badsel-pd52b   IPv4          <unset>   <unset>     2s
$ kubectl -n notes-lab exec client -- wget -qO- -T 3 http://web-badsel/
wget: can't connect to remote host (<cluster-ip>): Connection refused
command terminated with exit code 1

报错和故障三一字不差，但原因完全不同：这次连接根本没有到达任何 Pod。kube-proxy 给没有端点的 Service 在 filter 表里写了一条 REJECT 规则，拒绝是节点自己回的：

$ docker exec worker iptables-save | grep "notes-lab/web-badsel"
-A KUBE-SERVICES -d <cluster-ip>/32 -p tcp -m comment --comment "notes-lab/web-badsel has no endpoints" -m tcp --dport 80 -j REJECT --reject-with icmp-port-unreachable

对照选择器和 Pod 标签，问题一眼可见：

$ kubectl -n notes-lab describe svc web-badsel | grep -E 'Selector|Endpoints'
Selector:          app=web-v2
Endpoints:         <none>
$ kubectl -n notes-lab get pods --show-labels
NAME                   READY   STATUS    RESTARTS   AGE     LABELS
client                 1/1     Running   0          2m26s   app=client
web-78b9f97946-6kcns   1/1     Running   0          2m26s   app=web,pod-template-hash=78b9f97946
web-78b9f97946-kn48l   1/1     Running   0          2m26s   app=web,pod-template-hash=78b9f97946

Pod 都在，只是没有一个带 app=web-v2。如果端点存在但全部 ready=false（探针没过），表现也是没有可用后端，排查方法见 Pod 与容器里「Running 但不 Ready」一节。

把几种症状放在一起

保留故障三、四的两个 Service，再把故障一的默认拒绝策略加回去（web-deny-ingress.yaml 就是故障一的第一份清单）：

kubectl -n notes-lab apply -f web-deny-ingress.yaml

同一个客户端依次访问三个 Service，-T 5 限定最多等 5 秒：

$ kubectl -n notes-lab exec client -- sh -c 'for u in http://web/ http://web-badport/ http://web-badsel/; do echo == $u; time wget -qO /dev/null -T 5 $u; done'
== http://web/
wget: download timed out
Command exited with non-zero status 1
real	0m 5.00s
...
== http://web-badport/
wget: download timed out
Command exited with non-zero status 1
real	0m 5.00s
...
== http://web-badsel/
wget: can't connect to remote host (<cluster-ip>): Connection refused
Command exited with non-zero status 1
real	0m 1.00s
...

前两个都等满了 5 秒；web-badsel 的拒绝在 1.00s 时返回，busybox time 的精度不足以说明这 1 秒具体花在哪，这里只能说它比超时快得多。

有一个意外：web-badport 原本是 Connection refused，加上策略后变成了超时。策略在 Pod 网卡前就把包丢了，包到不了 Pod 的内核，也就没有 RST 回来，端口错误被策略盖住了。而 web-badsel 的 REJECT 发生在客户端所在节点的 filter 表里，包还没走到 Pod 网卡就被拒绝了，所以不受 web 上的策略影响。

据此可以整理出一张判断表：

现象先查本次复现的原因
bad address，按 ClusterIP 能通DNS 路径：CoreDNS 端点、出站策略是否放行 53出站策略漏了 DNS
超时，同节点和跨节点 Pod IP 都不通NetworkPolicy入站默认拒绝
超时，只有跨节点不通节点路由、节点间防火墙、calico-node本次未复现
Connection refused，EndpointSlice 有后端EndpointSlice 的端口列，直接连「Pod IP:端口」targetPort 写错
Connection refused，EndpointSlice 为空Service 选择器与 Pod 标签、就绪状态选择器不匹配

超时说明包被静默丢弃了，往策略和路由上查；被拒绝说明有人明确回了拒绝，要么是 Pod 上没有进程监听，要么是 kube-proxy 发现 Service 没有端点。只是这条规律有前提：前面那个被策略盖住的 web-badport 就说明，多个问题叠在一起时，看到的只是最外层的那一个，修完一层要重新测一遍。

Pod 拿不到 IP 的情况

上面都假定 Pod 已经有 IP。如果 Pod 停在 ContainerCreating、kubectl get pod -o wide 的 IP 列为空，那是 CNI 在创建沙箱时就失败了，看 Events 里有没有 FailedCreatePodSandBox，再看对应节点上 CNI 组件（这里是 calico-system 下的 calico-node）是否 Running。这类故障需要动节点，本次实验没有复现；一个相关的实测案例见 Pod 与容器，Calico 分配 IP 花了一分多钟，Pod 一直停在 ContainerCreating。排查时不要先重装 CNI，重装会改变所有节点的网络状态，还会把原始错误一并抹掉。

网络工具不在应用镜像里时，可以用临时调试容器在目标 Pod 的网络命名空间里执行同样的 ip route、wget，不用为了排查去改镜像。更一般的故障排查顺序见故障排查。

清理

不用先删策略，直接删 namespace。下面是另一次重做时的记录：namespace 里留着 web Service 和 web-deny-ingress 策略，删除前 worker2 上有 15 行规则带这个 namespace 的名字，删除后两个 worker 上都是 0：

$ docker exec worker2 iptables-save | grep -c notes-lab
15
$ kubectl delete namespace notes-lab --wait
namespace "notes-lab" deleted
$ docker exec worker iptables-save | grep -c notes-lab
0
$ docker exec worker2 iptables-save | grep -c notes-lab
0

也就是说，kube-proxy 写的 Service 规则和 Calico 编译出的策略链都随 namespace 一起清掉了。
