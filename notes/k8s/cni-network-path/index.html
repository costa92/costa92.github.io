第 48 / 66 节 · 进阶实践

先确定故障停在哪一层

应用访问 http://demo-web 看似只发一个请求，实际涉及 DNS 名称解析、Service 到后端的转发，以及 Pod 之间的网络路径。Service和DNS 排查分别讲过前两层；CNI 插件通常参与创建 Pod 网络接口和配置 Pod 网络。不要把所有“网络不通”都归因于 CNI，不同插件的转发和策略实现也不同。

本页是只读定位流程，不要求安装或替换网络插件。先选一个自己有权排查的实验 Pod，把命令里的名称替换为实际对象：

kubectl config current-context
kubectl -n k8s-lab get pods -o wide
kubectl -n k8s-lab get pod replace-with-pod -o jsonpath='{.status.podIP}{"\n"}{.spec.nodeName}{"\n"}'
kubectl -n k8s-lab describe pod replace-with-pod

若 Pod 没有 IP 且一直处于 ContainerCreating，看 Events 是否出现 FailedCreatePodSandBox、IP 分配或网络插件错误。此时检查节点是否 Ready、运行时是否正常，以及该集群实际使用的 CNI 组件状态；组件可能由 DaemonSet、Deployment 或节点服务管理，不能仅凭固定名称推断：

kubectl get nodes -o wide
kubectl -n kube-system get daemonsets,deployments,pods -o wide

不要在排查时先重装 CNI。重装会改变全节点的网络状态，且可能掩盖原始错误。

有 Pod IP 后继续缩小范围

如果 Pod 已取得 IP，按下列顺序查：

  1. Pod 到 Pod IP：从具备网络工具的实验容器访问目标 Pod IP。若只在跨节点失败，重点查节点间路由、封装、防火墙和所用 CNI 的健康状态；同节点成功不证明跨节点路径正常。
  2. Service 到后端：kubectl -n k8s-lab get service demo-web，再运行 kubectl -n k8s-lab get endpointslices -l kubernetes.io/service-name=demo-web。后端为空时，先查 Service 选择器、Pod 标签和就绪状态。
  3. 名称到 Service：在测试容器中解析 demo-web.k8s-lab.svc.cluster.local。若直接访问 Service 地址成功而按名称失败，重点查 DNS，而不是先更换 CNI。

这些检查要基于Service 实验中实际存在于 k8s-lab 的 demo-web；原实验清单未写命名空间，应用 Deployment 和 Service 时要明确使用 -n k8s-lab。网络工具不在应用镜像内时，可参考 临时调试容器，避免为排查而修改生产镜像。若 NetworkPolicy 已生效，也要检查它是否允许测试流量；策略效果由网络插件能力决定。

路径示意： 应用名称 → 集群 DNS → Service 地址 → EndpointSlice 中的就绪后端 → Pod IP → 节点网络。这用于定位，不表示所有集群都按同一种数据平面实现 Service 转发或 Pod 路由。要深入到 eBPF、iptables、隧道和路由表，必须先确认所用 CNI 及其版本。
