kubectl 常用命令

kubectl 是 Kubernetes API 的命令行客户端，每条命令最后都会变成一次或几次 HTTP 请求。这一篇不罗列命令，而是用几个临时 Pod 把常用命令逐个跑一遍，重点看两类事：同一类命令之间到底差在哪；哪些写错了不报错，却给出一个看起来正常的结果。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），客户端是 kubectl v1.30.0，实验放在单独的 notes-lab namespace 里。为便于阅读，节点名简化成 worker、worker2，Pod IP、Cluster IP、API Server 地址分别用 <pod-ip>、<cluster-ip>、<apiserver> 代替。JSONPath、kubectl debug、Server-Side Apply 和标签各有单独的笔记，这里只在用到时链接过去。

先确认命令会发到哪里

命令发到哪个集群由 kubeconfig 的 current-context 决定，发到哪个 namespace 由 context 上的 namespace 字段决定，没设就是 default。练习改 context 时不要直接动 ~/.kube/config，先导出一份只含当前 context 的副本，用 KUBECONFIG 指过去：

kubectl config view --minify --flatten > /tmp/kubeconfig-lab   # --flatten 会把证书一起导出，用完删掉
export KUBECONFIG=/tmp/kubeconfig-lab
kubectl config get-contexts
kubectl config view --minify
CURRENT   NAME                      CLUSTER                   AUTHINFO                  NAMESPACE
*         kind-lab                  kind-lab                  kind-lab                  
apiVersion: v1
clusters:
- cluster:
    certificate-authority-data: DATA+OMITTED
    server: https://<apiserver>
  name: kind-lab
contexts:
- context:
    cluster: kind-lab
    user: kind-lab
  name: kind-lab
current-context: kind-lab
kind: Config
preferences: {}
users:
- name: kind-lab
  user:
    client-certificate-data: DATA+OMITTED
    client-key-data: DATA+OMITTED

--minify 只显示当前 context 用到的那一组 cluster/user，比翻整份 kubeconfig 快得多；不加 --flatten 时证书显示为 DATA+OMITTED，可以放心贴出来。NAMESPACE 一列为空，所以此时 kubectl get pods 查的是 default。给当前 context 设上 namespace 后，不带 -n 的命令就都落到实验 namespace 里，-n 仍然可以临时覆盖（这一段是在实验后半段做的，所以列出的是后文 Deployment 的 Pod）：

$ kubectl config set-context --current --namespace=notes-lab
Context "kind-lab" modified.
$ kubectl get pods
NAME                   READY   STATUS    RESTARTS   AGE
app-6bb8f765c9-mrt7q   1/1     Running   0          2m23s
$ kubectl get pods -n default
No resources found in default namespace.

错误一：namespace 拼错，get 不报错

把 namespace 故意拼成 notes-lab-kubetcl（t 和 c 换了位置）：

$ kubectl config set-context --current --namespace=notes-lab-kubetcl; kubectl get pods
Context "kind-lab" modified.
No resources found in notes-lab-kubetcl namespace.

set-context 不检查 namespace 是否存在，get 也只说「没有资源」，和一个真的空 namespace 无法区分。加 -v=6 看实际请求：

$ kubectl get pods -v=6 2>&1 | grep round_trippers
I1013 16:05:22.645741  867892 round_trippers.go:553] GET https://<apiserver>/api/v1/namespaces/notes-lab-kubetcl/pods?limit=500 200 OK in 2 milliseconds

API Server 对不存在的 namespace 做 list 返回的是 200 OK 和空列表，不是 404。能揭穿它的有两个办法：直接 kubectl get ns <名字>，或者做一次写操作，创建时才会报 namespace 不存在：

$ kubectl run x --image=busybox:1.36 --restart=Never -- sleep 10
Error from server (NotFound): namespaces "notes-lab-kubetcl" not found

试完把 context 的 namespace 改回来，后文的命令都显式带 -n notes-lab：

kubectl config set-context --current --namespace=notes-lab

所以「No resources found」时，第一反应应该是核对输出里那个 namespace 名，而不是怀疑对象被删了。-v=6 会把每个请求的方法、URL、状态码和耗时打出来，后文还会多次用到它。

实验对象

建三个 Pod：inspect-demo 每 5 秒打印一行带序号和时间的日志，方便区分日志参数；web、web2 是两个 nginx，标签有意设得不一样：

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab run inspect-demo --image=busybox:1.36 --restart=Never \
  --labels=app=inspect-demo,tier=debug \
  -- sh -c 'i=0; while true; do echo tick $i $(date +%T); i=$((i+1)); sleep 5; done'
kubectl -n notes-lab run web  --image=nginx:alpine --labels=app=web,tier=frontend
kubectl -n notes-lab run web2 --image=nginx:alpine --labels=app=web,tier=frontend,env=staging
kubectl -n notes-lab wait --for=condition=Ready pod --all --timeout=120s
kubectl -n notes-lab create service clusterip web --tcp=80:80   # 按 app=web 选中 web 和 web2

等 default ServiceAccount 的原因见 Pod 与容器；整个实验环境的准备见本地实验环境。

默认输出时 kubectl 请求的是 as=Table，列名和每列的值由 API Server 算好返回；-o yaml、-o name 请求的才是完整对象。

筛选：标签选择器和字段选择器

$ kubectl -n notes-lab get pods -l app=web
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          15s
web2   1/1     Running   0          15s
$ kubectl -n notes-lab get pods -l "app=web,env!=staging"
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          15s
$ kubectl -n notes-lab get pods -l "tier in (debug,frontend),!env"
NAME           READY   STATUS    RESTARTS   AGE
inspect-demo   1/1     Running   0          15s
web            1/1     Running   0          15s

逗号是「且」；!env 表示「没有 env 这个键」，env!=staging 则连没有 env 的对象也算进去。标签的格式限制和集合写法的细节见标签与选择器。

--field-selector 按对象字段筛，但每种资源只支持服务端事先登记的几个字段，名单因资源而异；Pod 支持哪些字段、不支持时怎么报错，见标签与选择器里的字段选择器一节。这里只看一下 Service。Service 在这个版本上除了 metadata.name、metadata.namespace，只认 spec.clusterIP 和 spec.type，端口就不行：

$ kubectl -n notes-lab get svc --field-selector spec.type=ClusterIP
NAME   TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
web    ClusterIP   <cluster-ip>   <none>        80/TCP    1s
$ kubectl -n notes-lab get svc --field-selector spec.ports.port=80
Error from server (BadRequest): Unable to find "/v1, Resource=services" that match label selector "", field selector "spec.ports.port=80": field label not supported: spec.ports.port

Pod、Service 这类核心资源遇到不支持的字段报的是 field label not supported（官方文档里 Ingress 的例子报的是另一种措辞 is not a known field selector）。要按镜像、端口这类字段筛，只能拿回列表在客户端过滤，见 kubectl JSONPath。

错误二：zsh 把方括号当成了通配符

想试试 Pod 能不能按镜像筛，在 zsh 里直接这么写：

$ kubectl -n notes-lab get pods --field-selector spec.containers[0].image=nginx:alpine
(eval):1: no matches found: spec.containers[0].image=nginx:alpine

（这条是在脚本里通过 eval 执行时的输出；在交互式 zsh 里显示为 zsh: no matches found: ...。）

这条报错不是 kubectl 给的，命令根本没执行：zsh 把 [0] 当作文件名通配，找不到匹配的文件就直接报错（bash 默认会把原样字符串传下去，所以同样的命令在 bash 里能跑）。判断方法很简单，看报错前缀：kubectl 的服务端错误通常以 Error from server 开头，客户端错误通常以 error: 开头，而这里是 shell 自己的格式。加上引号后，才拿到真正的答案：

$ kubectl -n notes-lab get pods --field-selector 'spec.containers[0].image=nginx:alpine'
Error from server (BadRequest): Unable to find "/v1, Resource=pods" that match label selector "", field selector "spec.containers[0].image=nginx:alpine": field label not supported: spec.containers[0].image

凡是带 []、{}、*、? 的参数（JSONPath、--sort-by、字段选择器）都应该加单引号。

get -o yaml 是对象本身，115 行里一个事件都没有；默认还隐藏了 managedFields，加 --show-managed-fields 会涨到 201 行。describe 则是 kubectl 在客户端拼出来的报告：把对象字段重排成人好读的样子，再额外查一次事件。-v=6 能看到这次额外的查询：

$ kubectl -n notes-lab describe pod web2 -v=6 2>&1 | grep -E "GET https"
I1013 16:00:54.664572  834702 round_trippers.go:553] GET https://<apiserver>/api/v1/namespaces/notes-lab/pods/web2 200 OK in 2 milliseconds
I1013 16:00:54.665858  834702 round_trippers.go:553] GET https://<apiserver>/api/v1/namespaces/notes-lab/pods/web2 200 OK in 0 milliseconds
I1013 16:00:54.667304  834702 round_trippers.go:553] GET https://<apiserver>/api/v1/namespaces/notes-lab/events?fieldSelector=involvedObject.name%3Dweb2%2CinvolvedObject.namespace%3Dnotes-lab%2CinvolvedObject.uid%3Dd3ff9502-8a67-4be5-8260-b80d84032a0d&limit=500 200 OK in 0 milliseconds

事件按 involvedObject 的名字、namespace 和 uid 过滤。所以删掉再重建的同名 Pod，describe 只显示新对象的事件；想看前一个对象留下的事件，要用 kubectl get events --field-selector involvedObject.name=<名字>，它不带 uid 条件。事件有保留期（kube-apiserver 的 --event-ttl 默认 1 小时），describe 里 Events 为空不代表什么都没发生过。

要写进脚本或拿去对比的，用 get -o yaml/json；要排查「为什么不动」，先看 describe 的 Events 和 Last State，具体例子见 Pod 与容器。

describe 会按前缀匹配

$ kubectl -n notes-lab describe pod we | grep -E "^Name:"
Name:             web
Name:             web2
$ kubectl -n notes-lab describe pod web | grep -E "^Name:"
Name:             web
$ kubectl -n notes-lab get pod we
Error from server (NotFound): pods "we" not found

get 要求名字完全一致，describe 在找不到同名对象时会把所有以该字符串开头的对象都描述一遍。名字恰好存在时只给那一个，所以 describe pod web 没有带上 web2。少敲几个字母时这很方便，但在 Pod 名带随机后缀的 Deployment 里，describe pod app 会一次吐出所有副本，读的时候要看清 Name:。

explain：查字段定义

explain 查的是字段定义，不需要任何对象存在，数据来自 API Server 发布的 OpenAPI：

$ kubectl explain deploy.spec.strategy --recursive
GROUP:      apps
KIND:       Deployment
VERSION:    v1

FIELD: strategy <DeploymentStrategy>


DESCRIPTION:
    The deployment strategy to use to replace existing pods with new ones.
    DeploymentStrategy describes how to replace existing pods with new ones.
    
FIELDS:
  rollingUpdate	<RollingUpdateDeployment>
    maxSurge	<IntOrString>
    maxUnavailable	<IntOrString>
  type	<string>
  enum: Recreate, RollingUpdate
$ kubectl explain pod.spec.container
KIND:       Pod
VERSION:    v1

error: field "container" does not exist

路径里用的是 YAML 字段名 containers（列表不用写下标），不是类型名。不加 --recursive 时会打印字段说明，默认值通常写在说明里，比如 imagePullPolicy 的说明写着标签为 :latest 时默认 Always，否则 IfNotPresent。

logs：用带时间的日志区分各个参数

inspect-demo 每 5 秒打印一行，下面在 08:01:00（UTC）执行：

$ date -u +%T; kubectl -n notes-lab logs inspect-demo --tail=3
08:01:00
tick 5 08:00:47
tick 6 08:00:52
tick 7 08:00:57
$ kubectl -n notes-lab logs inspect-demo --since=12s
tick 6 08:00:52
tick 7 08:00:57
$ kubectl -n notes-lab logs inspect-demo --since=12s --timestamps
2026-10-13T08:00:52.632790113Z tick 6 08:00:52
2026-10-13T08:00:57.634189945Z tick 7 08:00:57

--tail 按行数截，--since 按时间截，依据的是容器运行时记录的写入时间，--timestamps 会把这个时间打在每行前面。应用自己不打时间戳时，--timestamps 是判断「这行日志是什么时候写的」唯一的依据。

-f 会一直跟下去，在脚本里一定要配超时：

$ timeout 12 kubectl -n notes-lab logs -f inspect-demo --tail=1; echo "timeout exit=$?"
tick 7 08:00:57
tick 8 08:01:02
tick 9 08:01:07
timeout exit=124

--tail=1 先补出最后一行，然后新行实时追加；124 是 timeout 杀掉进程时的退出码，不是 kubectl 的错误。容器还没重启过时，--previous 会报 previous terminated container "inspect-demo" in pod "inspect-demo" not found；它和不带参数的 logs 什么时候返回不同的实例，见 Pod 与容器 里的 CrashLoopBackOff 实验。

多容器 Pod：-c 和默认容器

再建一个 Pod，里面一个 nginx（web），一个每 10 秒打印一行的 busybox（sidecar），保存为 two.yaml 后 kubectl -n notes-lab apply -f two.yaml：

apiVersion: v1
kind: Pod
metadata:
  name: two
  labels:
    app: two
spec:
  containers:
    - name: web
      image: nginx:alpine
    - name: sidecar
      image: busybox:1.36
      command: ["sh", "-c", "while true; do echo sidecar $(date +%T); sleep 10; done"]
$ kubectl -n notes-lab logs two --tail=1
Defaulted container "web" out of: web, sidecar
2026/10/13 08:01:21 [notice] 1#1: start worker process 63
$ kubectl -n notes-lab logs two -c sidecar --tail=1
sidecar 08:01:23
$ kubectl -n notes-lab logs two --all-containers --tail=1
2026/10/13 08:01:21 [notice] 1#1: start worker process 63
sidecar 08:01:23

不带 -c 时 kubectl 选第一个容器，并在 stderr 打一行 Defaulted container。这行提示很容易被忽略：要找的日志在 sidecar 里，看到的却是 nginx 的，第一反应往往是「怎么没日志」。想换默认容器，可以给 Pod 加注解 kubectl.kubernetes.io/default-container，之后不带 -c 读的就是它，提示也不再出现：

$ kubectl -n notes-lab annotate pod two kubectl.kubernetes.io/default-container=sidecar
pod/two annotated
$ kubectl -n notes-lab logs two --tail=1
sidecar 08:01:23

实际使用时这个注解应该写在 Deployment 的 Pod 模板里，而不是事后加到某个 Pod 上。按标签一次看多个 Pod 时，用 --prefix 区分每行来自哪里：

$ kubectl -n notes-lab logs -l app=web --tail=1 --prefix
[pod/web/web] 2026/10/13 08:00:25 [notice] 1#1: start worker process 63
[pod/web2/web2] 2026/10/13 08:00:22 [notice] 1#1: start worker process 63

exec：退出码会传回来

$ kubectl -n notes-lab exec inspect-demo -- ps
PID   USER     TIME  COMMAND
    1 root      0:00 sh -c i=0; while true; do echo tick $i $(date +%T); i=$((i+1)); sleep 5; done
   26 root      0:00 ps
$ kubectl -n notes-lab exec inspect-demo -- sh -c "exit 3"

这条命令之后 $? 是 3：容器里命令的退出码会原样变成 kubectl 的退出码，脚本可以直接拿 exec 做检查。-- 用来分隔 kubectl 自己的参数和要执行的命令，不写的旧格式还能用，但会提示 kubectl exec [POD] [COMMAND] is DEPRECATED。

exec 只能运行镜像里已经有的程序，nginx:alpine 里没有 bash：

$ kubectl -n notes-lab exec web -- bash
error: Internal error occurred: Internal error occurred: error executing command in container: failed to exec in container: failed to start exec "392299c52d3e7fcc59556ac1ded4533cad8f1209d7b2e00b75e782d22c51825e": OCI runtime exec failed: exec failed: unable to start container process: exec: "bash": executable file not found in $PATH: unknown

报错里的 executable file not found in $PATH 说明 Pod 和连接都没问题，只是镜像里没有这个程序，换成 sh 即可；连 sh 都没有的镜像，要用临时容器，见 kubectl debug。

port-forward

错误三：本地端口被占用，转发却「成功」了

后台起一个转发，然后用 curl 测试：

$ kubectl -n notes-lab port-forward svc/web 18080:80 > pf.log 2>&1 &
$ cat pf.log; curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18080/
Forwarding from [::1]:18080 -> 80
404

nginx 的首页怎么会是 404？线索在 pf.log：正常情况下有 IPv4 和 IPv6 两行 Forwarding from，这里只有 [::1] 一行。查本机监听：

$ ss -ltnp | grep 18080
LISTEN 0      4096            127.0.0.1:18080      0.0.0.0:*                                              
LISTEN 0      4096                [::1]:18080         [::]:*    users:(("kubectl",pid=838594,fd=8))       
$ curl -s -i http://127.0.0.1:18080/ | head -5
HTTP/1.1 404 Not Found
Cache-Control: must-revalidate,no-cache,no-store
Content-Type: text/html;charset=iso-8859-1
Content-Length: 496
Server: Jetty(9.4.54.v20240208)

127.0.0.1:18080 早就被本机另一个程序（一个 Jetty 服务）占了。kubectl 默认同时监听 localhost 的 IPv4 和 IPv6，只要有一个绑定成功就不算失败，于是只拿到了 [::1]；curl 访问 127.0.0.1 时打到的是 Jetty。直接访问 http://[::1]:18080/ 则返回 200。

你的机器上多半没有这样一个程序，可以用 Python 先占住一个端口来复现。下面是另起一轮、对一个名为 app 的 nginx Service 补测的，端口换成了 18081：

$ python3 -m http.server 18081 --bind 127.0.0.1 > py.log 2>&1 &
$ kubectl -n notes-lab port-forward svc/app 18081:80 > pf3.log 2>&1 & sleep 2; cat pf3.log
Forwarding from [::1]:18081 -> 80
$ curl -s -i http://127.0.0.1:18081/ | grep -iE "^(HTTP|Server)"
HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.14.4
$ curl -s -i "http://[::1]:18081/" | grep -iE "^(HTTP|Server)"
HTTP/1.1 200 OK
Server: nginx/1.31.3

这次两边都返回 200，只看状态码根本发现不了问题，Python 返回的是一个目录列表。可靠的判断依据是响应头里的 Server:，它告诉你到底是谁在回答；再配合 pf.log 里少了的那行 Forwarding from 127.0.0.1。复现完用 kill %1 %2（或按 PID）结束这两个后台进程。

先结束第一个 port-forward：kill %1，或者用 ps -o pid,cmd -C kubectl 找到它的 PID 再 kill <pid>。然后用 --address 127.0.0.1 只监听 IPv4，冲突会立刻变成报错：

$ timeout 5 kubectl -n notes-lab port-forward --address 127.0.0.1 svc/web 18080:80; echo "exit=$?"
Unable to listen on port 18080: Listeners failed to create with the following errors: [unable to create listener: Error listen tcp4 127.0.0.1:18080: bind: address already in use]
error: unable to listen on any of the requested ports: [{18080 80}]
exit=1

更省事的是本地端口留空，让系统分配一个空闲端口，从输出里读出来（下文的 36621 是这次分到的端口，换成你自己 pf2.log 里的那个）：

$ kubectl -n notes-lab port-forward svc/web :80 > pf2.log 2>&1 &
$ cat pf2.log
Forwarding from 127.0.0.1:36621 -> 80
Forwarding from [::1]:36621 -> 80
$ curl -s http://127.0.0.1:36621/ | grep -o '<title>.*</title>'
<title>Welcome to nginx!</title>

转发到 Service 也只连一个 Pod

把 web、web2 的首页分别改成各自的主机名，再对比 port-forward 和集群内访问 Service：

for p in web web2; do kubectl -n notes-lab exec $p -- sh -c 'hostname > /usr/share/nginx/html/index.html'; done
$ for i in 1 2 3 4 5 6; do curl -s http://127.0.0.1:36621/; done | sort | uniq -c
      6 web2
$ kubectl -n notes-lab run curl --image=curlimages/curl:latest --restart=Never --rm -i --quiet -- sh -c "for i in 1 2 3 4 5 6; do curl -s http://web/; done" | sort | uniq -c
      5 web
      1 web2

port-forward svc/web 只在启动时借 Service 的选择器挑一个 Pod，之后所有连接都发给它，不经过 kube-proxy，也就没有负载均衡。这个 Pod 一没，转发就断了。删掉 web2 后：

$ kubectl -n notes-lab delete pod web2 --wait=false
pod "web2" deleted
$ curl -s -m 3 http://127.0.0.1:36621/; echo "curl exit=$?"
curl exit=52
$ cat pf2.log
...
Handling connection for 36621
E1013 16:02:22.761080  841342 portforward.go:413] an error occurred forwarding 36621 -> 80: error forwarding port 80 to pod 05afdb9adb75f9e498ce034e21c7348a18a5b4cc1f0b996c5f29b63465497797, uid : failed to execute portforward in network namespace "/var/run/netns/cni-1d329cf0-8ff2-ec62-7701-5c633fb9d8d3": failed to connect to localhost:80 inside namespace "05afdb9adb75f9e498ce034e21c7348a18a5b4cc1f0b996c5f29b63465497797", IPv4: dial tcp4 127.0.0.1:80: connect: connection refused IPv6 dial tcp6 [::1]:80: connect: connection refused 
error: lost connection to pod

报错里的 failed to connect to localhost:80 inside namespace 说明了转发的实际路径：节点上的容器运行时进入 Pod 的网络命名空间，连那里的 localhost:80。Service 后面明明还有一个健康的 web，kubectl 也不会切过去，而是直接退出。所以 port-forward 适合临时调试一个具体的 Pod，验证 Service 的负载均衡要在集群里测。

后台的 port-forward 用完要按 PID 结束。先用 ps -o pid,cmd -C kubectl 找到它，再 kill <pid>。不要用 pkill -f port-forward，它可能误杀其他项目正在用的转发。

create 不能重复执行，apply 可以

$ kubectl -n notes-lab create -f app-v1.yaml
deployment.apps/app created
$ kubectl -n notes-lab create -f app-v1.yaml
Error from server (AlreadyExists): error when creating "app-v1.yaml": deployments.apps "app" already exists

create 的语义是「新建」，对象已存在就失败，所以重复执行的脚本里不能用它。现在对这个由 create 建出来的对象执行 apply：

$ kubectl -n notes-lab apply -f app-v1.yaml
Warning: resource deployments/app is missing the kubectl.kubernetes.io/last-applied-configuration annotation which is required by kubectl apply. kubectl apply should only be used on resources created declaratively by either kubectl create --save-config or kubectl apply. The missing annotation will be patched automatically.
deployment.apps/app configured

apply 依赖注解 kubectl.kubernetes.io/last-applied-configuration，create 建的对象没有这个注解（此前它只有控制器加的 deployment.kubernetes.io/revision），所以 apply 警告一句后自动补上。补上的内容就是这次提交的清单本身：

$ kubectl -n notes-lab get deploy app -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}' | python3 -m json.tool
{
    "apiVersion": "apps/v1",
    "kind": "Deployment",
    "metadata": {
        "annotations": {},
        "labels": {
            "app": "app",
            "team": "a"
        },
        "name": "app",
        "namespace": "notes-lab"
    },
    "spec": {
        "replicas": 1,
...

apply 只删「上次是我写的」字段

先用命令式命令加一个标签 owner=manual，再 apply 删掉了 team 的 v2：

$ kubectl -n notes-lab label deploy app owner=manual
deployment.apps/app labeled
$ kubectl -n notes-lab get deploy app --show-labels
NAME   READY   UP-TO-DATE   AVAILABLE   AGE   LABELS
app    1/1     1            1           5s    app=app,owner=manual,team=a
$ kubectl -n notes-lab diff -f app-v2.yaml; echo "diff exit=$?"
...
@@ -10,7 +10,6 @@
   labels:
     app: app
     owner: manual
-    team: a
   name: app
   namespace: notes-lab
   resourceVersion: "11139016"
diff exit=1
$ kubectl -n notes-lab apply -f app-v2.yaml
deployment.apps/app configured
$ kubectl -n notes-lab get deploy app --show-labels
NAME   READY   UP-TO-DATE   AVAILABLE   AGE   LABELS
app    1/1     1            1           5s    app=app,owner=manual

v2 里既没有 team 也没有 owner，结果 team 被删了，owner 留着。区别就在 last-applied 注解：team 在上一次 apply 的清单里，从清单里消失就表示「我不要它了」；owner 从来不在注解里，apply 认为它归别人管，不碰。

反过来，如果对象是 create 出来的，第一次 apply 之前没有注解可比，从清单里删掉的字段就不会被清理。用 ConfigMap 验证一下，cm-v1.yaml 有 a、b 两个键，cm-v2.yaml 只有 a：

# cm-v1.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cfg
data:
  a: "1"
  b: "2"
---
# cm-v2.yaml：同上，去掉 b 这一行
$ kubectl -n notes-lab create -f cm-v1.yaml
configmap/cfg created
$ kubectl -n notes-lab apply -f cm-v2.yaml 2>&1 | tail -1
configmap/cfg configured
$ kubectl -n notes-lab get cm cfg -o jsonpath='{.data}{"\n"}'
{"a":"1","b":"2"}
$ kubectl -n notes-lab delete cm cfg; kubectl -n notes-lab apply -f cm-v1.yaml; kubectl -n notes-lab apply -f cm-v2.yaml; kubectl -n notes-lab get cm cfg -o jsonpath='{.data}{"\n"}'
configmap "cfg" deleted
configmap/cfg created
configmap/cfg configured
{"a":"1"}

同样两份文件，先 create 再 apply，b 留了下来，而且单靠从清单里删掉已经清不掉了，因为新的注解里也没有 b；全程用 apply，b 被正常删除。要清掉残留的 b，可以先把它写回清单 apply 一次，让它进入注解，再从清单里删掉 apply；或者直接改线上对象：

$ kubectl -n notes-lab apply -f cm-v1.yaml; kubectl -n notes-lab apply -f cm-v2.yaml; kubectl -n notes-lab get cm cfg -o jsonpath='{.data}{"\n"}'
configmap/cfg configured
configmap/cfg configured
{"a":"1"}
$ kubectl -n notes-lab patch cm cfg --type=json -p '[{"op":"remove","path":"/data/b"}]'
configmap/cfg patched

（后一条是在另一轮「先 create 再 apply」之后执行的，执行后 .data 同样只剩 {"a":"1"}；用 edit 删掉这一行效果相同。）这就是官方文档说不支持混用 apply 和 create/replace 的原因。确实需要先用 create 的话，加 --save-config 让它也写上这个注解。

edit 的改动会被下一次 apply 改回去

edit 会打开编辑器修改线上对象，下面用 sed 代替编辑器，把副本数改成 2：

$ KUBE_EDITOR="sed -i 's/^  replicas: 1/  replicas: 2/'" kubectl -n notes-lab edit deploy app
deployment.apps/app edited
$ kubectl -n notes-lab get deploy app -o jsonpath='spec.replicas={.spec.replicas}{"\n"}'; kubectl -n notes-lab get deploy app -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}' | grep -o '"replicas":[0-9]'
spec.replicas=2
"replicas":1
$ kubectl -n notes-lab diff -f app-v2.yaml | grep -E "^[-+] "
-  generation: 4
+  generation: 5
-  replicas: 2
+  replicas: 1
$ kubectl -n notes-lab apply -f app-v2.yaml
deployment.apps/app configured
$ kubectl -n notes-lab get deploy app -o jsonpath='spec.replicas={.spec.replicas}{"\n"}'
spec.replicas=1

edit 只改线上对象，不更新 last-applied 注解，也不会改你的 YAML 文件。下一次 apply 发现清单里写着 replicas: 1，和线上的 2 不同，就改回去。和上面 owner 标签的区别在于：replicas 出现在清单里，归清单管；owner 不在清单里，所以保留。线上应急用 edit 或 scale 改了某个字段，事后一定要同步回 YAML，否则下一次发布会悄悄撤销。退出编辑器时没有改动，会提示 Edit cancelled, no changes made.。

–dry-run=client 和 –dry-run=server

--dry-run=client 只在本地组装对象，--dry-run=server 把请求完整地交给 API Server 走一遍校验和准入，只是最后不写入 etcd。同一个错误，两种 dry-run 给出不同的结论。

校验错误：bad-sel.yaml 由 app-v1.yaml 改两处得到，名字换成 bad-sel，selector 写成 app: app-typo，和模板标签 app: app 对不上：

sed -e 's/name: app$/name: bad-sel/' -e 's/^      app: app$/      app: app-typo/' app-v1.yaml > bad-sel.yaml
$ kubectl -n notes-lab apply -f bad-sel.yaml --dry-run=client
deployment.apps/bad-sel created (dry run)
$ kubectl -n notes-lab apply -f bad-sel.yaml --dry-run=server
The Deployment "bad-sel" is invalid: spec.template.metadata.labels: Invalid value: map[string]string{"app":"app"}: `selector` does not match template `labels`

准入拒绝：在 namespace 里 apply 一个 LimitRange，限制单个容器 CPU limit 不超过 200m：

apiVersion: v1
kind: LimitRange
metadata:
  name: cpu-cap
spec:
  limits:
    - type: Container
      max:
        cpu: 200m

再提交一个 limit 为 500m 的 Pod：

$ kubectl -n notes-lab run big --image=busybox:1.36 --restart=Never --overrides='{"spec":{"containers":[{"name":"big","image":"busybox:1.36","args":["sleep","60"],"resources":{"limits":{"cpu":"500m"}}}]}}' --dry-run=client
pod/big created (dry run)
$ kubectl -n notes-lab run big --image=busybox:1.36 --restart=Never --overrides='{"spec":{"containers":[{"name":"big","image":"busybox:1.36","args":["sleep","60"],"resources":{"limits":{"cpu":"500m"}}}]}}' --dry-run=server
Error from server (Forbidden): pods "big" is forbidden: maximum cpu usage per Container is 200m, but limit is 500m

字段名拼错：typo.yaml 是把 app-v1.yaml 里的 replicas 写成 replica（sed 's/^ replicas: 1/ replica: 1/' app-v1.yaml > typo.yaml），client 模式同样放行，server 模式才报 strict decoding error: unknown field "spec.replica"（这条报错还把整个补丁打了出来，很长，这里只摘关键部分）。

client 模式也会访问 API Server（读 OpenAPI、查对象是否存在），但从不发出写请求；server 模式多了一个带 dryRun=All 的 POST。字段校验靠的是 fieldValidation=Strict 这个参数，由服务端执行，没有这个 POST 就没人查。所以 --dry-run=client 只适合配合 -o yaml 生成清单，要确认「这份清单能不能提交成功」，用 --dry-run=server 或 kubectl diff。

做完把 LimitRange 删掉：

kubectl -n notes-lab delete limitrange cpu-cap

不删的话会影响之后创建的 Pod。它只写了 max，但另起一轮补测时读回来发现，服务端把 default 和 defaultRequest 也都填成了 200m，没声明资源的容器会被注入这两个值：

$ kubectl -n notes-lab get limitrange cpu-cap -o jsonpath='{.spec.limits[0]}{"\n"}'
{"default":{"cpu":"200m"},"defaultRequest":{"cpu":"200m"},"max":{"cpu":"200m"},"type":"Container"}
$ kubectl -n notes-lab run lr-test --image=busybox:1.36 --restart=Never --dry-run=server -o jsonpath="{.spec.containers[0].resources}{\"\n\"}" -- sleep 10
{"limits":{"cpu":"200m"},"requests":{"cpu":"200m"}}

delete：deleted 不等于已经没了

先把前面用完的 web 和 two 删掉，再用同一条命令建两个 Pod d1、d2 用于后面的对比：

kubectl -n notes-lab delete pod web two --wait=false
for p in d1 d2; do kubectl -n notes-lab run $p --image=busybox:1.36 --restart=Never -- sh -c 'while true; do sleep 1; done'; done

inspect-demo 的主进程是一个 sh 循环，先默认删除它：

$ date +%T; time kubectl -n notes-lab delete pod inspect-demo; date +%T
16:03:38
pod "inspect-demo" deleted
  0.05s user 0.01s system 0% cpu 32.576 total
16:04:11

用了 32.6 秒。默认宽限期是 30 秒，kubelet 先发 SIGTERM，期限到了再 SIGKILL。这里几乎等满了 30 秒，推测是因为作为 PID 1 的 sh 没有给 SIGTERM 设处理函数，内核不会替 PID 1 执行默认的终止动作，只能等 SIGKILL（这次没有在容器里单独验证信号处理）。优雅退出的细节见 优雅终止。

--wait=false 立即返回，同样打印 deleted，但对象其实还在：

$ time kubectl -n notes-lab delete pod d1 --wait=false; kubectl -n notes-lab get pod d1
pod "d1" deleted
  0.04s user 0.01s system 173% cpu 0.028 total
NAME   READY   STATUS        RESTARTS   AGE
d1     1/1     Terminating   0          44s
$ kubectl -n notes-lab get pod d1 -o jsonpath='{.metadata.deletionTimestamp} {.metadata.deletionGracePeriodSeconds}{"\n"}'
2026-10-13T08:04:45Z 30

deleted 的意思是「删除请求已被接受」。对象被打上 deletionTimestamp，状态显示为 Terminating，要等 kubelet 停掉容器后才真正消失。脚本如果紧接着要用同名对象重建，必须用默认的 --wait=true，或者 kubectl wait --for=delete。

--grace-period=1 把宽限期缩短到 1 秒，但整条命令仍然用了 4.8 秒，推测多出来的几秒是 kubelet 停容器、回报状态，以及 API Server 最终删除对象的时间（没有逐段计时）：

$ time kubectl -n notes-lab delete pod d2 --grace-period=1
pod "d2" deleted
  0.04s user 0.02s system 1% cpu 4.810 total

--now 等同于 --grace-period=1。--grace-period=0 --force 会跳过等待直接从 API 删除对象，节点上的容器可能还在运行，只在节点已经失联、Pod 卡在 Terminating 时考虑。

–sort-by：自然排序，拼错字段要看对象个数

这一节在上面的 delete 之后执行：此时 inspect-demo、d1、d2、web、two、web2 都已删除，namespace 里只剩 Deployment app 的 1 个 Pod（web、two 在 delete 一节开头删掉，web2 在 port-forward 一节删掉）。如果你的 namespace 里还有别的 Pod，给下面的 get 都加上 -l app=app，只看这一组。

字段写错时，默认表格输出会打印 No resources found、退出码 0，换成 -o name 才报出真正的错误，原因和源码位置见 kubectl JSONPath。这里补充一个那篇没有覆盖的情况：列表里只有一个对象时，默认表格输出完全不受拼错的排序字段影响。下面把 podIP 写成 podIp，Deployment 先是 1 个副本，再扩到 3 个：

$ kubectl -n notes-lab get pods --sort-by=.status.podIp
NAME                   READY   STATUS    RESTARTS   AGE
app-6bb8f765c9-mrt7q   1/1     Running   0          2m56s
$ kubectl -n notes-lab scale deploy app --replicas=3; kubectl -n notes-lab rollout status deploy app --timeout=60s
deployment.apps/app scaled
Waiting for deployment "app" rollout to finish: 1 of 3 updated replicas are available...
Waiting for deployment "app" rollout to finish: 2 of 3 updated replicas are available...
deployment "app" successfully rolled out
$ kubectl -n notes-lab get pods --sort-by=.status.podIp; echo "exit=$?"
No resources found in notes-lab namespace.
exit=0

kubectl v1.30 的 SortingPrinter.PrintObj 对默认表格和 -o wide 拿到的 Table，只在 len(table.Rows) > 1 时才调用 NewTableSorter 去解析排序字段，一行时直接原样打印，字段写没写对根本不检查。-o name、-o json、-o jsonpath 拿到的是对象列表，走的是 SortObjects，只有一个对象也会报错。下面是另起一轮、只有 1 个副本时补测的：

$ kubectl -n notes-lab get pods -l app=app --sort-by=.status.podIp -o name
error: couldn't find any field with path "{.status.podIp}" in the list of objects
$ kubectl -n notes-lab get pods -l app=app --sort-by=.status.podIp -o jsonpath='{.items[*].metadata.name}'
error: couldn't find any field with path "{.status.podIp}" in the list of objects

所以一条带 --sort-by 的表格命令在测试环境只有一个副本时能跑通，到了多副本的环境就变成「No resources found」。写进脚本之前，先用 -o name 或 -o jsonpath 跑一次，确认排序字段是对的。

字段写对时：

$ kubectl -n notes-lab get pods --sort-by=.status.podIP -o custom-columns=NAME:.metadata.name,IP:.status.podIP
NAME                   IP
app-6bb8f765c9-85g8n   <pod-net>.107.7
app-6bb8f765c9-7g7fq   <pod-net>.107.46
app-6bb8f765c9-mrt7q   <pod-net>.209.201

（IP 前两段用 <pod-net> 代替。）注意 .7 排在 .46 前面：逐字符比较的话 4 小于 7，结果会相反。kubectl 对字符串用的是 sortorder.NaturalLess，即自然排序，字符串里的连续数字按数值比较。

清理

kubectl delete namespace notes-lab --wait
kubectl get namespace notes-lab
# Error from server (NotFound): namespaces "notes-lab" not found
rm /tmp/kubeconfig-lab && unset KUBECONFIG

删除 namespace 会连同里面的 Pod、Deployment、Service、LimitRange 一起删掉。那份 kubeconfig 副本是用 --flatten 导出的，里面有客户端证书和私钥，用完一定要删。

回头看，这次碰到的几个坑有一个共同点：命令没有报错，退出码是 0，只是结果不对。namespace 拼错时是空列表，排序字段拼错时也是空列表，本地端口被占时转发到了别的程序，先 create 后 apply 时被删的字段留了下来。遇到「看起来正常但不对」的结果，-v=6 看实际请求、换成 -o name / -o json 看有没有被吞掉的错误，比反复重跑同一条命令有用。整体排查思路见故障排查。
