PodDisruptionBudget 与维护窗口

按官方文档，维护节点时 kubectl drain 并不直接删 Pod，而是对每个 Pod 调用 Eviction API（DaemonSet 管理的 Pod 要配合 --ignore-daemonsets 跳过，静态 Pod 的 mirror Pod 不会被驱逐；加 --disable-eviction 则改成直接删除，绕过 PDB）。PodDisruptionBudget（PDB）就是在 Eviction 这个入口上把关：它给一组 Pod 定一个自愿中断的预算，至少保留多少个健康 Pod，或者最多允许多少个不健康。节点宕机、内核 OOM 这类非自愿中断，它管不了。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico）。这个集群还跑着别的东西，所以没有 cordon 或 drain 节点，而是对自己 namespace 里的 Pod 直接发 Eviction 请求。按官方文档，drain 做的也是同一件事，另外还会先 cordon 节点、遇到 429 时重试，流程见节点维护与安全排空。

实验环境

一个 3 副本的 nginx Deployment，保存为 web.yaml。就绪探针请求 /index.html，之后只要删掉这个文件，就能让某个 Pod 变成 Running 但不 Ready：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      terminationGracePeriodSeconds: 5
      containers:
        - name: nginx
          image: nginx:alpine
          readinessProbe:
            httpGet:
              path: /index.html
              port: 80
            periodSeconds: 2
            failureThreshold: 1
          resources:
            requests:
              cpu: 10m
              memory: 32Mi
            limits:
              memory: 64Mi

驱逐有两种发法。一是用 kubectl 把 Eviction 对象 POST 到 Pod 的 eviction 子资源：

cat > ev.json <<'EOF'
{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"<pod>"}}
EOF
kubectl create --raw /api/v1/namespaces/notes-lab/pods/<pod>/eviction -f ev.json

kubectl 只打印一行错误摘要。想看完整的响应体，就在集群里放一个 curl Pod，给它的 ServiceAccount 绑定一个只允许 create pods/eviction 的 Role。保存为 evictor.yaml：

apiVersion: v1
kind: ServiceAccount
metadata:
  name: evictor
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: evictor
rules:
  - apiGroups: [""]
    resources: ["pods/eviction"]
    verbs: ["create"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: evictor
subjects:
  - kind: ServiceAccount
    name: evictor
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: evictor
---
apiVersion: v1
kind: Pod
metadata:
  name: evictor
spec:
  serviceAccountName: evictor
  containers:
    - name: curl
      image: curlimages/curl:latest
      command: ["sleep", "3600"]
      resources:
        requests:
          cpu: 10m
          memory: 16Mi
        limits:
          memory: 32Mi

本地的脚本 evict.sh，参数是要驱逐的 Pod 名：

SA=/var/run/secrets/kubernetes.io/serviceaccount
NS=$(cat $SA/namespace)
curl -sS --cacert $SA/ca.crt -H "Authorization: Bearer $(cat $SA/token)" \
  -H 'Content-Type: application/json' -w '\nHTTP %{http_code}\n' \
  -X POST https://kubernetes.default.svc/api/v1/namespaces/$NS/pods/$1/eviction \
  -d "{\"apiVersion\":\"policy/v1\",\"kind\":\"Eviction\",\"metadata\":{\"name\":\"$1\"}}"

需要看响应头时，在 curl -sS 后面加 -i。把这些都装起来：

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f web.yaml -f evictor.yaml
kubectl -n notes-lab rollout status deploy/web
kubectl -n notes-lab wait --for=condition=Ready pod/evictor
kubectl -n notes-lab cp evict.sh evictor:/tmp/evict.sh
kubectl -n notes-lab exec evictor -- sh /tmp/evict.sh <pod>

本地的 evict.sh 没有可执行位（-rw-rw-r--），拷进去也一样，直接 exec ... /tmp/evict.sh 会报 permission denied，所以用 sh /tmp/evict.sh 调用；也可以拷贝前先 chmod +x。

状态字段怎么读

先建一个 minAvailable: 2 的 PDB：

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: web
$ kubectl -n notes-lab get pdb web
NAME   MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web    2               N/A               1                     5s
$ kubectl -n notes-lab get pdb web -o jsonpath='{.status}' | python3 -m json.tool
{
    "conditions": [
        {
            "lastTransitionTime": "2026-10-12T06:57:32Z",
            "message": "",
            "observedGeneration": 1,
            "reason": "SufficientPods",
            "status": "True",
            "type": "DisruptionAllowed"
        }
    ],
    "currentHealthy": 3,
    "desiredHealthy": 2,
    "disruptionsAllowed": 1,
    "expectedPods": 3,
    "observedGeneration": 1
}

四个数的关系：disruptionsAllowed = currentHealthy - desiredHealthy（不小于 0），desiredHealthy 是预算要求的最少健康数。currentHealthy 是选中的 Pod 里 Ready condition 为 True 的数量，但 v1.31 源码里的 countHealthyPods 还会跳过两类 Pod：已经带 deletionTimestamp（正在删除）的，以及刚被驱逐、记在 status.disruptedPods 里等待删除的。所以一个仍显示 1/1 的 Terminating Pod 不算健康，后面选择器写错那一节的输出里就有这样一个。expectedPods 分两种算法：整数 minAvailable 时就是选中的 Pod 数；百分比或 maxUnavailable 时取所属控制器（Deployment 等）的期望副本数。

连续驱逐两次

驱逐第一个 Pod，成功；紧接着驱逐第二个，被拒：

$ kubectl create --raw /api/v1/namespaces/notes-lab/pods/web-74d74755df-4rst7/eviction -f ev.json
{"kind":"Status","apiVersion":"v1","metadata":{},"status":"Success","code":201}

$ kubectl create --raw /api/v1/namespaces/notes-lab/pods/web-74d74755df-ckrf8/eviction -f ev.json
Error from server (TooManyRequests): Cannot evict pod as it would violate the pod's disruption budget.

成功时返回的是 201。官方文档写的是驱逐允许时返回 200 OK，这个集群上无论是 Status 里的 code，还是 curl 拿到的 HTTP 状态码，实际都是 201（下面 curl 的输出也一样）。原因在 apiserver：v1.31 的 eviction 处理返回的是一个只填了 status: Success 的 Status 对象，通用的 create handler（staging/src/k8s.io/apiserver/pkg/endpoints/handlers/create.go）发现它的 Code 为 0，就默认填成 201 Created。脚本判断成功与否，用 2xx 判断更稳妥。

被拒之后马上看 PDB 状态：

status:
  conditions:
  - lastTransitionTime: "2026-10-12T06:58:18Z"
    message: ""
    observedGeneration: 1
    reason: InsufficientPods
    status: "False"
    type: DisruptionAllowed
  currentHealthy: 2
  desiredHealthy: 2
  disruptionsAllowed: 0
  expectedPods: 4
  observedGeneration: 1

expectedPods 变成了 4：被驱逐的 Pod 还在 Terminating，Deployment 补的新 Pod 已经创建，两个都匹配选择器。这里是整数 minAvailable，expectedPods 就是选中的 Pod 数，所以替换期间会短暂多出一个；而 Terminating 的那个不计入 currentHealthy。真正决定放不放行的是 currentHealthy 和 desiredHealthy，替换 Pod 变成 Ready 之后，disruptionsAllowed 才回到 1。

minAvailable 等于副本数：所有驱逐都会被拒

把 PDB 改成 minAvailable: 3，与副本数相同：

NAME   MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web    3               N/A               0                     2m30s

ALLOWED DISRUPTIONS 恒为 0，任何一个 Pod 都驱逐不了。对 drain 来说，这意味着节点永远排不空。maxUnavailable: 0 按定义也是同样效果（这次没有单独测）。官方文档把它作为单实例有状态应用的一种做法：维护前由运维和应用负责人沟通，删掉 PDB，维护完再建回来。但这种配置如果被无意中留下，就成了 drain 卡死的常见原因。

用 curl Pod 再驱逐一次，evict.sh 里加上 -i 看响应头：

HTTP 429

有两点值得注意。第一，这种「预算用完」（disruptionsAllowed 为 0）的 429 没有 Retry-After 头，调用方要自己决定隔多久重试。v1.31 的源码（pkg/registry/core/pod/storage/eviction.go 的 checkAndDecrement）里还有另一种 429：PDB 的 status.observedGeneration 小于 metadata.generation，即控制器还没处理完最新的 spec 时，会返回带 Retry-After: 10 的 429，cause 是 The disruption budget web is still being processed by the server.。这次试了三次「改完 PDB 立刻驱逐」，控制器每次都抢先处理完了，没有复现出来。第二，details.causes 里写明了是哪个 PDB、要求几个健康 Pod、当前有几个，kubectl 的一行摘要把这些都省掉了。drain 卡住时想知道是哪个预算在拦，这条 message 最直接。另外，429 也可能是 API 限流造成的，靠 reason: DisruptionBudget 区分。

kubectl delete 不受预算约束

就在驱逐被拒的同一个 Pod 上，直接删除：

$ kubectl -n notes-lab delete pod web-74d74755df-bbtt6
pod "web-74d74755df-bbtt6" deleted
$ kubectl -n notes-lab get pods -l app=web; kubectl -n notes-lab get pdb web
NAME                   READY   STATUS              RESTARTS   AGE
web-74d74755df-t86jw   1/1     Running             0          3m30s
web-74d74755df-x5tqp   0/1     ContainerCreating   0          13s
web-74d74755df-zwzjb   1/1     Running             0          88s
NAME   MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web    3               N/A               0                     2m44s

删除成功，健康 Pod 只剩 2 个，低于 PDB 要求的 3 个。PDB 只在 Eviction 子资源上生效，DELETE 请求根本不经过它。所以「PDB 能保护我的服务」的前提是：执行中断的工具走的是 Eviction API。按官方文档，drain 走的是这个入口（--disable-eviction 除外）；手工 kubectl delete、直接 delete Pod 的脚本则不经过 PDB。

滚动更新也不看 PDB

在 ALLOWED DISRUPTIONS 为 0 的状态下执行 kubectl rollout restart deploy/web：

deployment.apps/web restarted
...
Waiting for deployment "web" rollout to finish: 1 old replicas are pending termination...
deployment "web" successfully rolled out
NAME                   READY   STATUS        RESTARTS   AGE
web-64f5bd4f7d-6667h   1/1     Running       0          63s
web-64f5bd4f7d-xt8mw   1/1     Running       0          51s
web-64f5bd4f7d-zl5wt   1/1     Running       0          23s
web-74d74755df-t86jw   0/1     Terminating   0          4m46s
NAME   MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE

三个旧 Pod 全部被换掉，滚动更新照常完成。Deployment 控制器删旧 Pod 用的是普通删除，可用性由它自己的 maxUnavailable/maxSurge 控制。3 副本时默认的 25% 换算下来是 maxUnavailable 0、maxSurge 1，所以这次更新本身就没让健康数低于 3，但这和 PDB 无关。滚动参数见 Deployment。

minAvailable 与 maxUnavailable、百分比取整

同一组 Pod，依次套上六种写法（每次只保留一个 PDB），记录状态。副本数为 5 时：

MIN MAXU HEALTHY DESIRED ALLOWED EXPECTED
2     <none>   5     2     3     5
<none>   1     5     4     1     5
50%   <none>   5     3     2     5
<none>   50%   5     2     3     5
34%   <none>   5     2     3     5
<none>   34%   5     3     2     5

缩到 3 副本后重来一遍：

2     <none>   3     2     1     3
<none>   1     3     2     1     3
50%   <none>   3     2     1     3
<none>   50%   3     1     2     3
34%   <none>   3     2     1     3
<none>   34%   3     1     2     3

几个结论：

  • 整数 minAvailable 不随副本数变。minAvailable: 2 在 5 副本时允许中断 3 个，在 3 副本时只允许 1 个；maxUnavailable: 1 则始终允许 1 个。服务会扩缩容时，maxUnavailable 的行为更符合直觉。
  • 两种百分比都向上取整。5 × 50% = 2.5：minAvailable: 50% 要求 3 个健康，maxUnavailable: 50% 允许 3 个不可用（于是只要求 2 个健康）。3 × 34% = 1.02：两种写法都取整到 2。
  • 所以 minAvailable: X% 和 maxUnavailable: (100-X)% 并不等价，maxUnavailable 的百分比也可能被突破。3 副本、maxUnavailable: 34% 时允许 2 个同时中断，实际不可用比例是 67%。官方文档对此也有说明：只有 1 个副本时，maxUnavailable 的任何百分比都会放行这唯一的副本。
  • 百分比和 maxUnavailable 需要从 Deployment、StatefulSet 等控制器（或带 scale 子资源的自定义资源）读出期望副本数，这时 expectedPods 来自控制器的副本数，和前面整数 minAvailable 时按选中 Pod 数计算不同。

还有一个小坑：第一次跑这张表时，每个 PDB 创建后只隔 3 秒就去读，其中两个 34% 的 PDB 读到的数字全是 0，其余几行正常。推测是控制器还没来得及写 status。这时的 0 和真正的「预算用完」看起来一样，而且按前文「被拒时的完整响应」引用的源码，这段时间里驱逐会收到带 Retry-After: 10 的 429。脚本里应该等 .status.observedGeneration 等于 .metadata.generation 再读状态。

未就绪 Pod：unhealthyPodEvictionPolicy

PDB 的预算是按健康 Pod 算的，可节点维护时最想先清走的，往往正是那个 Running 但不 Ready 的 Pod。unhealthyPodEvictionPolicy 决定这类 Pod 能不能被驱逐，默认值是 IfHealthyBudget。

IfHealthyBudget：健康数不足时，连坏的也不让动

minAvailable: 3，删掉其中一个 Pod 的 index.html 让它不 Ready：

NAME                   READY   STATUS    RESTARTS   AGE
web-64f5bd4f7d-6667h   0/1     Running   0          9m40s
web-64f5bd4f7d-xt8mw   1/1     Running   0          9m28s
web-64f5bd4f7d-zl5wt   1/1     Running   0          9m
POLICY   HEALTHY   DESIRED   ALLOWED
<none>   2         3         0

驱逐那个不健康的 6667h：

{
  "kind": "Status",
  "apiVersion": "v1",
  "metadata": {},
  "status": "Failure",
  "message": "Cannot evict pod as it would violate the pod's disruption budget.",
  "reason": "TooManyRequests",
  "details": {
    "causes": [
      {
        "reason": "DisruptionBudget",
        "message": "The disruption budget web needs 3 healthy pods and has 2 currently"
      }
    ]
  },
  "code": 429
}
HTTP 429

驱逐它并不会让健康数变少，但仍然被拒。IfHealthyBudget 的规则是：Running 但未就绪的 Pod，只有在 currentHealthy >= desiredHealthy 时才能驱逐。现在 2 < 3，应用已经处于「被中断」状态，所以连这个坏 Pod 也不让动。如果这个 Pod 永远不会就绪（比如配置错误），drain 就会一直卡在它身上。

把预算放宽到 minAvailable: 2，健康数刚好达标：

POLICY   HEALTHY   DESIRED   ALLOWED
<none>   2         2         0

这时 ALLOWED 同样是 0，驱逐健康 Pod 返回 429，驱逐那个不健康的 Pod 却成功了：

$ kubectl -n notes-lab exec evictor -- sh /tmp/evict.sh web-64f5bd4f7d-xt8mw | tail -6
      }
    ]
  },
  "code": 429
}
HTTP 429
$ kubectl -n notes-lab exec evictor -- sh /tmp/evict.sh web-64f5bd4f7d-6667h | tail -3
  "code": 201
}
HTTP 201

所以 disruptionsAllowed: 0 并不等于「什么都驱逐不了」，未就绪 Pod 走的是另一套判断。

AlwaysAllow：未就绪 Pod 随时可驱逐

web-64f5bd4f7d-xt8mw   0/1     Terminating   0          10m
web-64f5bd4f7d-zl5wt   1/1     Running       0          10m
web-64f5bd4f7d-zsv7n   1/1     Running       0          39s

官方文档把两种策略当作取舍来讲，没有给统一推荐：IfHealthyBudget 让已经受损的应用里那些还在启动的 Pod 有机会变健康，代价是 CrashLoopBackOff 或一直不报 Ready 的 Pod 会挡住 drain；AlwaysAllow 让运维能直接清掉这些坏 Pod，代价是它们可能永远没机会恢复。对无状态服务，一个不能接流量的 Pod 被驱逐也不损失可用性，我倾向于用 AlwaysAllow。Pending、Succeeded、Failed 阶段的 Pod 无论哪种策略都可以驱逐。

两个让 PDB 失效的配置错误

选择器写错：ALLOWED 为 0，却什么都没保护

把标签 app: web 误写成 app: wbe：

NAME   MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web    2               N/A               0                     8s

只看这一行，ALLOWED DISRUPTIONS 是 0，像是在严格保护。连续驱逐三个 web Pod：

Total: 0 和 NoPods 事件说明它一个 Pod 都没匹配上。检查 PDB 时，要看 expectedPods（Total）是否等于副本数，不能只看 ALLOWED DISRUPTIONS。

空选择器与重叠的 PDB：500

在 policy/v1 中，selector: {} 匹配 namespace 里的所有 Pod。再加一个这样的 PDB，和原来的 web 并存：

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: everything
spec:
  maxUnavailable: 1
  selector: {}
NAME         MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
everything   N/A             1                 2                     7s
web          2               N/A               1                     7s

这时驱逐任意一个 web Pod：

  "apiVersion": "v1",

HTTP 500
Error from server: This pod has more than one PodDisruptionBudget, which the eviction subresource does not support.

一个 Pod 被两个 PDB 选中，Eviction API 直接返回 500。和 429 不同，它不是「稍后再试」的意思，重试多少次都一样，必须修改选择器。

everything 本身也有问题。它不光选中了 3 个 web Pod，还选中了那个没有控制器的 curl Pod，控制器给出了警告：

Warning  UnmanagedPods  6s (x2 over 7s)  controllermanager  Pods selected by this PodDisruptionBudget (selector: &LabelSelector{MatchLabels:map[string]string{},MatchExpressions:[]LabelSelectorRequirement{},}) were found to be unmanaged. As a result, the status of the PDB cannot be calculated correctly, which may result in undefined behavior. To account for these pods please set ".spec.minAvailable" field of the PDB to an integer value.
HEALTHY   DESIRED   ALLOWED   EXPECTED
4         2         2         3

算出来的数字也对不上：expectedPods 只按 Deployment 的 3 个副本算，currentHealthy 却把裸 Pod 也算了进去，得到 4。结果 maxUnavailable: 1 的 PDB 显示允许中断 2 个。官方文档的限制写得很明确：选中的 Pod 没有受支持的控制器时，只能用整数 minAvailable，不能用 maxUnavailable，也不能用百分比。

小结

  • PDB 只拦 Eviction API。按官方文档，drain 默认走 Eviction API，因而受它约束；kubectl delete 和 Deployment 滚动更新都不受它约束。
  • 被拒返回 429，details.causes 里写明了哪个预算、要求几个、当前几个；一个 Pod 匹配多个 PDB 时返回 500，重试也没用。成功时这个集群返回的是 201。
  • minAvailable 是绝对下限，maxUnavailable 随副本数伸缩；两种百分比都向上取整，maxUnavailable 的百分比可能被突破。
  • minAvailable 等于副本数或 maxUnavailable: 0 会让 drain 永远卡住；默认的 IfHealthyBudget 下，健康数不足时连未就绪 Pod 也驱逐不了，无状态服务可以考虑 AlwaysAllow。
  • 检查 PDB 时先看 Total/expectedPods 是否等于副本数，选择器写错的 PDB 在 get pdb 里看起来和严格保护一模一样。

驱逐成功之后，Pod 照常走优雅终止流程（preStop、SIGTERM、terminationGracePeriodSeconds），见优雅终止。

清理

kubectl delete namespace notes-lab
