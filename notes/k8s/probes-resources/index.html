三种探针，两类资源设置

探针回答三个不同的问题：startupProbe 问「启动完了没有」，readinessProbe 问「现在能不能接流量」，livenessProbe 问「是不是该重启了」。资源设置也分两层：requests 是调度器用来找节点的账面数字，limits 是内核在运行时强制执行的上限，内存超限会被杀，CPU 超限只会被限速。

探针失败后的效果
startupProbe成功之前，存活和就绪探针都不执行；失败次数达到阈值时重启容器
readinessProbePod 在 EndpointSlice 里被标为未就绪，Service 不再转发流量；不重启
livenessProbe连续失败达到 failureThreshold 时，kubelet 杀掉并重启容器

就绪探针失败时 Pod 是什么样子、connection refused 和 404 两种报错各说明什么，已经在 Pod 与容器 里复现过，这里不再重复，重点放在「多久重启」和「资源超限时到底发生了什么」。

下文输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，节点为 cgroup v2；kind 节点共用宿主机内核，版本 7.0.0；每个节点可分配 28 核 CPU），实验放在单独的 notes-lab namespace 里。节点名简化为 worker、worker2，Pod IP 用 <pod-ip> 代替，时间均为 UTC。

存活探针：从失败到重启到底要多久

直觉上，periodSeconds: 5、failureThreshold: 3 意味着出问题后 15 秒左右重启。用一个能精确控制「何时变不健康」的 Pod 来量：容器启动 20 秒后删掉 /tmp/healthy，存活和就绪探针都检查这个文件。

apiVersion: v1
kind: Pod
metadata:
  name: live-timing
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "touch /tmp/healthy; echo \"start $(date +%T)\"; sleep 20; rm /tmp/healthy; echo \"removed $(date +%T)\"; sleep 3600"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 32Mi}
      readinessProbe:
        exec:
          command: ["test", "-f", "/tmp/healthy"]
        periodSeconds: 2
        failureThreshold: 1
      livenessProbe:
        exec:
          command: ["test", "-f", "/tmp/healthy"]
        periodSeconds: 5
        failureThreshold: 3
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f live-timing.yaml
kubectl -n notes-lab get events --field-selector involvedObject.name=live-timing \
  --sort-by=.lastTimestamp -o custom-columns=FIRST:.firstTimestamp,LAST:.lastTimestamp,COUNT:.count,REASON:.reason,MSG:.message
kubectl -n notes-lab get pod live-timing \
  -o jsonpath='{.status.containerStatuses[0].lastState}{"\n"}{.status.containerStatuses[0].state}{"\n"}'

另开一个终端每秒记录一次 ready 和 restartCount：

while true; do
  echo "$(date -u +%T) $(kubectl -n notes-lab get pod live-timing \
    -o jsonpath='{.status.containerStatuses[0].ready} {.status.containerStatuses[0].restartCount}')"
  sleep 1
done | uniq -f1
03:46:10 true 0
03:46:31 false 0
03:47:17 true 1

再把日志、事件和容器状态拼在一起：

$ kubectl -n notes-lab logs live-timing --previous
start 03:46:10
removed 03:46:30

FIRST                  LAST                   COUNT   REASON      MSG
2026-10-12T03:46:33Z   2026-10-12T03:46:43Z   3       Unhealthy   Liveness probe failed:
2026-10-12T03:46:43Z   2026-10-12T03:46:43Z   1       Killing     Container app failed liveness probe, will be restarted
2026-10-12T03:46:30Z   2026-10-12T03:47:00Z   18      Unhealthy   Readiness probe failed:

{"terminated":{"containerID":"containerd://0bb2...","exitCode":137,"finishedAt":"2026-10-12T03:47:13Z","reason":"Error","startedAt":"2026-10-12T03:46:08Z"}}
{"running":{"startedAt":"2026-10-12T03:47:16Z"}}

时间线是这样的：

时刻事件距文件删除
03:46:30删除 /tmp/healthy0 s
03:46:31轮询看到 ready=false1 s
03:46:33 / 38 / 43存活探针第 1、2、3 次失败3–13 s
03:46:43Killing13 s
03:47:13容器真正退出，退出码 13743 s
03:47:16新容器启动46 s

两个值得注意的地方：

  • 探测的部分比 15 秒短。第一次失败出现在删除后 3 秒，这只是探测周期的相位碰巧对上了；从第一次失败到第三次失败是 2 × 5 = 10 秒。所以「发现故障」的时间落在 (failureThreshold-1) × periodSeconds 到 failureThreshold × periodSeconds 之间。就绪探针周期是 2 秒、阈值 1，1 秒内 Pod 就变成了 Ready=false（如果有 Service 选中它，EndpointSlice 会随之把它标为未就绪），比存活探针早得多，这正是两者分工的意义：先停流量，确认真坏了再重启。这次没有建 Service，流量摘除那一步没有直接观察。
  • 真正的大头是 30 秒的终止宽限期。Killing 之后 kubelet 先发 SIGTERM，等 terminationGracePeriodSeconds（默认 30 秒）再发 SIGKILL。这个容器的 PID 1 是 sh，没有为 SIGTERM 注册处理函数，而 Linux 不会对 PID 1 执行信号的默认动作，所以 SIGTERM 被直接忽略，只能等满 30 秒被 SIGKILL，退出码 137 = 128 + 9。

为了确认 30 秒确实是被宽限期吃掉的，同样的 Pod 改成处理 SIGTERM（命令里加 trap 'echo "got TERM $(date +%T)"; exit 0' TERM，并把最后的 sleep 3600 改成 sleep 3600 & wait，否则 shell 要等前台 sleep 结束才执行 trap）：

start 03:47:35
removed 03:47:55
got TERM 03:48:07

{"terminated":{"containerID":"containerd://42f7...","exitCode":0,"finishedAt":"2026-10-12T03:48:07Z","reason":"Completed","startedAt":"2026-10-12T03:47:35Z"}}
{"running":{"startedAt":"2026-10-12T03:48:11Z"}}

从删除文件到新容器启动只用了 16 秒，退出码变成了 0，reason 是 Completed。这也说明两件事：

  1. 被存活探针杀掉的容器，退出码可能是 137，也可能是 0，取决于程序怎么响应 SIGTERM。所以 137 不能直接等同于 OOM，要看 reason 字段（见下文）。
  2. 估算存活探针的恢复时间，要把 terminationGracePeriodSeconds 和程序处理 SIGTERM 的速度算进去，不只是 periodSeconds × failureThreshold。探针本身也有一个 terminationGracePeriodSeconds 字段（v1.28 GA），可以只为探针触发的重启单独设置一个更短的宽限期；它只能写在存活探针和启动探针上，写在就绪探针上会被 API Server 拒绝。

这次的事件里还有两条容易让人误会的记录：

Readiness probe errored: rpc error: code = NotFound desc = failed to exec in container: failed to load task: no running task found: ...
Readiness probe errored: rpc error: code = Unknown desc = failed to exec in container: container is in CONTAINER_EXITED state

这是容器已经退出、新容器还没起来的那几秒里，就绪探针照常执行、找不到进程而报的错。重启期间看到它们不用额外排查。

慢启动应用被存活探针杀死

存活探针最常见的事故，是应用本身没问题，只是启动慢，结果每次都在启动完成前被杀掉。用 busybox 模拟一个启动要 40 秒、之后才监听 8080 的程序，只配存活探针（为了让循环快一点，宽限期设为 5 秒）：

apiVersion: v1
kind: Pod
metadata:
  name: slow-start
spec:
  terminationGracePeriodSeconds: 5
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo \"booting $(date +%T)\"; sleep 40; mkdir -p /www; echo ok > /www/index.html; echo \"listening $(date +%T)\"; exec httpd -f -p 8080 -h /www"]
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 32Mi}
      livenessProbe:
        httpGet:
          path: /
          port: 8080
        periodSeconds: 5
        failureThreshold: 3
FIRST                  REASON      MSG
2026-10-12T03:47:45Z   Started     Started container app
2026-10-12T03:47:45Z   Unhealthy   Liveness probe failed: Get "http://<pod-ip>:8080/": dial tcp <pod-ip>:8080: connect: connection refused
2026-10-12T03:47:55Z   Killing     Container app failed liveness probe, will be restarted

（FIRST 是每类事件第一次出现的时间。）

没有设置 initialDelaySeconds，第一次探测在容器启动的同一秒就发出了，10 秒后第三次失败、容器被杀。日志里永远只有 booting，看不到 listening。约两分钟后：

NAME         READY   STATUS             RESTARTS     AGE
slow-start   0/1     CrashLoopBackOff   4 (6s ago)   2m2s
{"waiting":{"message":"back-off 40s restarting failed container=app ...","reason":"CrashLoopBackOff"}}

程序一行错误都没有，却进入了 CrashLoopBackOff，退避时间也照常翻倍。排查时如果只看 logs --previous，会发现日志「正常」，容易误以为是程序崩了没留日志；真正的线索在 Events 里的 Killing ... failed liveness probe，以及 Last State 的 Finished 总是在启动后 10 多秒。

还有一个反直觉的现象：两次重启之间，kubectl get pod 显示的是 1/1 Running：

NAME         READY   STATUS    RESTARTS      AGE
slow-start   1/1     Running   4 (22s ago)   118s

这时程序根本还没开始监听。原因是这个 Pod 没有配置就绪探针，没有就绪探针的容器一启动就被视为 Ready，如果有 Service 选中它，它就会接到流量。存活探针不会影响 Ready 状态，它只管重启。

用 startupProbe 修好

不改存活探针，只加一个 startupProbe，给启动阶段 2 × 30 = 60 秒的预算：

startupProbe:
  httpGet:
    path: /
    port: 8080
  periodSeconds: 2
  failureThreshold: 30
$ kubectl -n notes-lab logs slow-start-fixed
booting 03:48:40
listening 03:49:20

FIRST                  LAST                   COUNT   REASON      MSG
2026-10-12T03:48:41Z   2026-10-12T03:49:19Z   20      Unhealthy   Startup probe failed: Get "http://<pod-ip>:8080/": dial tcp <pod-ip>:8080: connect: connection refused

$ kubectl -n notes-lab get pod slow-start-fixed -o jsonpath='{range .status.conditions[*]}{.type} {.lastTransitionTime}{"\n"}{end}'
...
Ready 2026-10-12T03:49:21Z
ContainersReady 2026-10-12T03:49:21Z

$ kubectl -n notes-lab get pod slow-start-fixed
NAME               READY   STATUS    RESTARTS   AGE
slow-start-fixed   1/1     Running   0          47s

启动探针失败了 20 次，没有一次存活探针失败的事件：startupProbe 成功之前，kubelet 不执行存活和就绪探针。03:49:20 开始监听，下一次启动探针成功，03:49:21 Pod 变为 Ready，RESTARTS 一直是 0。启动阶段的 Startup probe failed 事件是预期内的，只要没有超过阈值就不会重启。

failureThreshold × periodSeconds 应该覆盖应用最慢一次启动的时间，再留些余量；之后存活探针仍然可以用较短的周期，出问题时不必等很久。用 initialDelaySeconds 也能绕过去，但它是固定延迟：设短了照样被杀，设长了每次启动都要白等，而 startupProbe 是一旦就绪就交接。

内存超限：OOMKilled 与退出码 137

给 Pod 设 64Mi 内存上限，主进程只是 sleep，再用 kubectl exec 跑 dd 申请一块缓冲区（dd 会按 bs 一次性分配内存）：

apiVersion: v1
kind: Pod
metadata:
  name: oom-demo
spec:
  restartPolicy: Never
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]
      resources:
        requests: {cpu: 10m, memory: 64Mi}
        limits: {memory: 64Mi}

先看容器里看到的 cgroup：

$ kubectl -n notes-lab exec oom-demo -- cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/memory.oom.group
67108864
1

memory.max 就是 64Mi 换算成的字节数。申请 40M 没问题：

$ kubectl -n notes-lab exec oom-demo -- sh -c 'dd if=/dev/zero of=/dev/null bs=40M count=1; cat /sys/fs/cgroup/memory.peak'
41943040 bytes (40.0MB) copied, 0.010022 seconds, 3.9GB/s
43892736

峰值约 42 MiB，没有触发 OOM。换成 100M：

$ kubectl -n notes-lab exec oom-demo -- dd if=/dev/zero of=/dev/null bs=100M count=1
command terminated with exit code 137

$ kubectl -n notes-lab get pod oom-demo
NAME       READY   STATUS      RESTARTS   AGE
oom-demo   0/1     OOMKilled   0          17s
State:          Terminated
  Reason:       OOMKilled
  Exit Code:    137
  Started:      Mon, 12 Oct 2026 11:48:45 +0800
  Finished:     Mon, 12 Oct 2026 11:48:56 +0800

这里有个意外：超限的是 exec 进去的 dd，但整个容器都没了，连只占几百 KB 的 PID 1 sleep 也一起被杀；因为 restartPolicy: Never，容器不会重启，Pod 进入 Failed。原因就是上面那个 memory.oom.group = 1：这个设置让内核在 OOM 时杀掉 cgroup 里的所有进程，而不是只挑最大的那个。从 v1.28 开始，kubelet 在 cgroup v2 节点上会为容器设置它（CHANGELOG-1.28，#117793）。cgroup v1 节点、v1.28 之前的版本，或者 v1.32 起 kubelet 配置了 singleProcessOOMKill: true，都会回到只杀单个进程；本集群是 v1.31，没有这个开关。所以在这样的集群上，进容器跑一条吃内存的调试命令，可能会把业务进程一起带走。

还有两个排查时要知道的点：

  • Pod 的事件里没有 OOM 记录。这个 Pod 的事件只有 Scheduled、Pulled、Created、Started，OOM 只体现在容器状态的 Reason: OOMKilled 上，要看 describe pod 里的 State / Last State。kubelet 可能会在 Node 对象上记一条 SystemOOM 事件，但本集群里查询为空。
  • 区分 OOM 和其他 137。前面被存活探针杀掉的容器也是 137，但 reason 是 Error；只有 reason 为 OOMKilled 才是内存超限。

另外，describe pod 里的时间是本地时区（+0800），get events 的时间戳是 UTC，对时间线时别搞混。

三种 QoS 类别怎么判定、对应的 cgroup 和 OOM 分数，见 Pod QoS 类别：判定边界、cgroup 与 OOM 分数。

CPU 超限：不会被杀，只会变慢

在同一个节点上建两个 Pod，一个 limits.cpu: 100m，一个不设 CPU limit，其他一样（requests 都是 100m）：

apiVersion: v1
kind: Pod
metadata:
  name: cpu-limited
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]
      resources:
        requests: {cpu: 100m, memory: 16Mi}
        limits: {cpu: 100m, memory: 32Mi}
$ kubectl -n notes-lab exec cpu-limited -- cat /sys/fs/cgroup/cpu.max
10000 100000
$ kubectl -n notes-lab exec cpu-free -- cat /sys/fs/cgroup/cpu.max
max 100000

10000 100000 的意思是每 100 ms 的周期里最多用 10 ms CPU，正好是 0.1 核。用完配额后，这个 cgroup 的进程要等下一个周期才能继续跑，这就是节流（throttling）。

在两个 Pod 里跑同样的 shell 计数循环（数到 100 万），同时记录 cpu.stat：

for p in cpu-free cpu-limited; do
  echo "== $p"
  kubectl -n notes-lab exec $p -- sh -c '
    b=$(grep -E "nr_periods|nr_throttled " /sys/fs/cgroup/cpu.stat | tr "\n" " ")
    time sh -c "i=0; while [ \$i -lt 1000000 ]; do i=\$((i+1)); done"
    echo "before: $b"
    echo "after:  $(grep -E "nr_periods|nr_throttled " /sys/fs/cgroup/cpu.stat | tr "\n" " ")"' 2>&1
done
== cpu-free
real	0m 0.82s
user	0m 0.81s
sys	0m 0.00s
before: nr_periods 0 nr_throttled 0
after:  nr_periods 0 nr_throttled 0
== cpu-limited
real	0m 8.78s
user	0m 0.87s
sys	0m 0.00s
before: nr_periods 25 nr_throttled 18
after:  nr_periods 113 nr_throttled 105

两边消耗的 CPU 时间（user）几乎一样，都是 0.8 秒多，但受限的那个花了 8.78 秒墙钟时间，约为 10 倍，和 100m 的配额对得上。期间经过了 88 个周期，其中 87 个被节流。程序没有任何报错、没有重启，只是慢。线上表现通常是延迟升高、超时，而不是崩溃，所以 CPU limit 设得太紧的问题更隐蔽。

cpu.stat 里还有个 throttled_usec，这一段只增加了约 1.58 秒，明显少于墙钟时间里被耽误的约 7.9 秒，我没有查清它在这个内核上的统计口径，判断是否被节流时用 nr_throttled / nr_periods 的比例更直观。还有一个细节：cpu-limited 刚启动不久、还没跑计数时，nr_periods / nr_throttled 就已经是 5 / 2，推测是容器启动和 exec 带来的短暂 CPU 突发撞上了配额。上面 before 里的 25 / 18 也不是从零开始，推测包含了这之前几次 exec 的消耗。

让两个 Pod 各在后台跑一个 75 秒的死循环，用 metrics-server 看：

for p in cpu-free cpu-limited; do
  kubectl -n notes-lab exec $p -- sh -c 'timeout 75 sh -c "while :; do :; done" >/dev/null 2>&1 &'
done
sleep 60   # metrics-server 的读数要等一个采样窗口才稳定，立刻看会偏低
kubectl -n notes-lab top pod
$ kubectl -n notes-lab top pod
NAME          CPU(cores)   MEMORY(bytes)
cpu-free      1000m        0Mi
cpu-limited   101m         0Mi

不设 limit 的那个吃满了一个核（单线程循环最多就是 1 核），受限的稳定在 100m 左右。注意死循环开始后 27 秒查的那一次显示的是 563m 和 33m，metrics-server 的数据是一个时间窗口内的平均值，刚开始负载时读数偏低，要多等一会儿再看。kubectl top 只能告诉你用到了 limit，判断是不是在被节流还得看 cpu.stat。

requests 决定能不能调度

调度器只看 requests 的账面数字，不看节点实际用了多少。每个节点可分配 28 核，申请 30 核：

resources:
  requests: {cpu: "30", memory: 16Mi}
NAME          READY   STATUS    RESTARTS   AGE
big-request   0/1     Pending   0          2s

FailedScheduling   0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient cpu. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

这条消息按节点逐个给出了原因：控制平面节点因为污点被排除，两个工作节点都是 Insufficient cpu。后半句是抢占的结论：即使驱逐低优先级 Pod 也腾不出 30 核。实际环境中更常见的是 requests 累加超过节点剩余可分配量，而节点的实际 CPU 使用率可能很低，这时 kubectl top node 看起来很空闲，Pod 却调度不上去。要看的是 kubectl describe node 里的 Allocated resources，它统计的是 requests 之和。

反过来，只写 limits 不写 requests 时：

resources:
  limits: {cpu: 150m, memory: 48Mi}
$ kubectl -n notes-lab get pod limits-only -o jsonpath='{.spec.containers[0].resources}{"\n"}{.status.qosClass}{"\n"}'
{"limits":{"cpu":"150m","memory":"48Mi"},"requests":{"cpu":"150m","memory":"48Mi"}}
Guaranteed

API Server 把 limits 复制成了 requests，Pod 因此成了 Guaranteed。这意味着只写 limits 的 Pod 调度时按 limits 占用节点资源，limits 写得宽松，节点就会被「占满」得很快。namespace 里即使有 LimitRange 设置了默认 request，结果不变：只写 limit 时 request 仍等于 limit，原因见资源配额与限制范围。

清理

kubectl delete namespace notes-lab

小结

  • 存活探针从故障到容器重启的时间 ≈ 发现故障（不超过 periodSeconds × failureThreshold）+ 终止宽限期 + 重启。PID 1 不处理 SIGTERM 时，宽限期会吃满，本次实测为 46 秒，处理 SIGTERM 后为 16 秒。
  • 应用启动比存活探针的容忍时间长，就会无错误地进入 CrashLoopBackOff；用 startupProbe 给启动阶段单独的预算。
  • 没有就绪探针的容器一启动就是 Ready，不管应用有没有在监听。
  • 退出码 137 只说明进程被 SIGKILL，reason: OOMKilled 才是内存超限；Pod 的事件里看不到 OOM。v1.28 起的 cgroup v2 节点上，一个进程超限会带走整个容器。
  • CPU limit 用节流来执行，表现为变慢而不是报错，看 cpu.stat 的 nr_throttled。
  • 调度只看 requests；只写 limits 时 requests 会被设为与 limits 相同。
