给工作负载最小必要权限

ServiceAccount 是 Pod 在 Kubernetes API 面前的身份；Role 描述某个 namespace 内允许对哪些资源做哪些动作；RoleBinding 把角色授予主体。RBAC 的规则只有「允许」，没有「拒绝」，一个主体最终的权限是所有绑定的并集。给应用访问 API 的权限时，先列清楚它要读写什么，再一条条授予，不要直接绑 cluster-admin。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0，kubectl 客户端 v1.30.0），API Server 的授权模式是 --authorization-mode=Node,RBAC。实验放在单独的 notes-lab namespace 里，节点名简化成 worker，API Server 地址用 <apiserver> 代替。操作者是 kubeadm 的管理员账号，所以可以用 --as 模拟其他身份；普通用户没有 impersonate 权限时，带 --as 的命令本身会被拒绝。

从一个只读 Role 开始

保存为 rbac.yaml：

apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-reader
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-reader-pods
subjects:
  - kind: ServiceAccount
    name: app-reader
    namespace: notes-lab
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab apply -f rbac.yaml -f web.yaml

web.yaml 是一个用来被查看、看日志、exec 的 nginx Pod，容器名是 nginx：

apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: nginx
      image: nginx:alpine
      resources:
        requests: {cpu: 20m, memory: 32Mi}
        limits: {memory: 64Mi}

用 can-i 列一张权限表

ServiceAccount 的用户名固定是 system:serviceaccount:<namespace>:<名称>。用它挨个问：

SA=system:serviceaccount:notes-lab:app-reader
for a in "get pods" "list pods" "watch pods" "delete pods" "create pods" \
         "get pods/log" "create pods/exec" "get pods/exec" "list secrets" "list services"; do
  printf "%-18s %s\n" "$a" "$(kubectl -n notes-lab auth can-i $a --as=$SA)"
done
kubectl auth can-i list pods -n default --as=$SA
get pods           yes
list pods          yes
watch pods         yes
delete pods        no
create pods        no
get pods/log       yes
create pods/exec   no
get pods/exec      yes
list secrets       no
list services      no
list pods -n default no

前面几行符合预期，但 get pods/log 和 get pods/exec 竟然是 yes，Role 里明明没写这两个子资源。加 -v=8 看 kubectl 实际发出的 SelfSubjectAccessReview：

Request Body: {"kind":"SelfSubjectAccessReview",...,"spec":{"resourceAttributes":{"namespace":"notes-lab","verb":"get","resource":"pods","name":"log"}},...}

kubectl 把 pods/log 按 类型/名称 解析成了「名叫 log 的 Pod」，问的其实是 get pods，当然是 yes。查子资源要用 --subresource：

kubectl -n notes-lab auth can-i get pods --subresource=log --as=$SA
kubectl -n notes-lab auth can-i create pods --subresource=exec --as=$SA
kubectl -n notes-lab auth can-i get pods --subresource=exec --as=$SA
no
no
no

这个坑很隐蔽：权限表看起来放行了，真正调用时却是 403。写 can-i 检查脚本时，子资源一律用 --subresource。

拿这个身份真正去操作，结果和修正后的表一致：

$ kubectl -n notes-lab get pods --as=$SA
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          25s
$ kubectl -n notes-lab logs web --as=$SA
Error from server (Forbidden): pods "web" is forbidden: User "system:serviceaccount:notes-lab:app-reader" cannot get resource "pods/log" in API group "" in the namespace "notes-lab"
$ kubectl -n notes-lab exec web --as=$SA -- hostname
Error from server (Forbidden): pods "web" is forbidden: User "system:serviceaccount:notes-lab:app-reader" cannot create resource "pods/exec" in API group "" in the namespace "notes-lab"
$ kubectl -n notes-lab delete pod web --as=$SA
Error from server (Forbidden): pods "web" is forbidden: User "system:serviceaccount:notes-lab:app-reader" cannot delete resource "pods" in API group "" in the namespace "notes-lab"

这条错误信息把授权判断用到的五个要素都列了出来：用户、动词（get）、资源（pods/log）、API 组（"" 即核心组）和 namespace。补规则时照着它写就行。

Pod 用自己的 token 调 API

kubectl --as 只是模拟，工作负载真正拿到的是挂进容器的 token。起一个用 app-reader 身份运行的 curl 容器：

apiVersion: v1
kind: Pod
metadata:
  name: api-client
spec:
  serviceAccountName: app-reader
  containers:
    - name: curl
      image: curlimages/curl:latest
      command: ["sleep", "3600"]
kubectl -n notes-lab apply -f api-client.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/api-client

在容器里用挂载的 CA 和 token 访问 API：

kubectl -n notes-lab exec api-client -- sh -c '
D=/var/run/secrets/kubernetes.io/serviceaccount; TOKEN=$(cat $D/token); NS=$(cat $D/namespace)

$ curl -sS --cacert .../ca.crt -H "Authorization: Bearer bad.token.value" https://kubernetes.default.svc/api/v1/namespaces/notes-lab/pods

  "code": 401

应用里排查 API 调用失败，先看状态码和 message 里的 User：

  • 401 Unauthorized：认证没过，API Server 不认这个 token（伪造、过期、绑定的 Pod 已删除）。这时和 RBAC 无关，改 Role 没用。
  • 403 且 User 是 system:anonymous：请求根本没带 token。常见原因是代码没读 token 文件，或者 Pod 关掉了自动挂载（见后文）。
  • 403 且 User 是自己的 ServiceAccount：身份对了，缺权限，按 message 里的动词、资源、namespace 补规则。

改了权限要不要重启 Pod

不用。在 api-client 里循环访问 ConfigMap 列表，中途加一个 RoleBinding、再删掉：

[05:01:38.679] before: 403
rolebinding.rbac.authorization.k8s.io/app-reader-view created
[05:01:39.066] after:  200
rolebinding.rbac.authorization.k8s.io "app-reader-view" deleted
[05:01:39.283] removed: 403

授权是每个请求单独判断的，绑定变更几乎立即生效：授权器读的是本地 informer 缓存，这里实测在约 0.4 秒内完成了放行和撤销，token 不需要换。

get、list、watch 是三个独立的动词

很多人把「读」当成一个权限，实际上 get（按名字取单个对象）、list（取集合）、watch（订阅变更）在 RBAC 里互不包含。准备两个 ConfigMap，再建两个只差一个动词的 Role：

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: cm-get-only
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: cm-list-only
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["list"]

分别绑给 cm-getter 和 cm-lister 两个 ServiceAccount（RoleBinding 写法同上，略），再准备两个 ConfigMap：

kubectl -n notes-lab create configmap app-config --from-literal=db_host=db.internal --from-literal=log_level=info
kubectl -n notes-lab create configmap other-config --from-literal=feature_x=on
G=system:serviceaccount:notes-lab:cm-getter
S=system:serviceaccount:notes-lab:cm-lister

只有 get 的身份：

$ kubectl -n notes-lab get cm app-config --as=$G
NAME         DATA   AGE
app-config   2      6s
$ kubectl -n notes-lab get cm --as=$G
Error from server (Forbidden): configmaps is forbidden: User "system:serviceaccount:notes-lab:cm-getter" cannot list resource "configmaps" in API group "" in the namespace "notes-lab"
$ kubectl -n notes-lab get cm app-config --watch --as=$G
NAME         DATA   AGE
app-config   2      6s
Error from server (Forbidden): unknown (get configmaps)

--watch 先成功打印了一次，然后报了一个几乎看不出原因的 unknown (get configmaps)。加 -v=6 才看清楚，kubectl 先发了一个 GET 取对象，再发一个带 watch=true 的请求，被拒的是第二个：

GET https://<apiserver>/api/v1/namespaces/notes-lab/configmaps/app-config 200 OK in 4 milliseconds
GET https://<apiserver>/api/v1/namespaces/notes-lab/configmaps?fieldSelector=metadata.name%3Dapp-config&resourceVersion=0&watch=true 403 Forbidden in 0 milliseconds

同样是 HTTP GET，带 watch=true 的集合请求在 RBAC 里算 watch 动词。控制器、informer 一类的程序启动时都会先 list 再 watch，只给 get 的话会卡在这一步。

只有 list 的身份正好反过来：

$ kubectl -n notes-lab get cm app-config --as=$S
Error from server (Forbidden): configmaps "app-config" is forbidden: User "system:serviceaccount:notes-lab:cm-lister" cannot get resource "configmaps" in API group "" in the namespace "notes-lab"
$ kubectl -n notes-lab get cm --as=$S -o jsonpath='{range .items[*]}{.metadata.name}: {.data}{"\n"}{end}'
app-config: {"db_host":"db.internal","log_level":"info"}
kube-root-ca.crt: {"ca.crt":"-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n"}
other-config: {"feature_x":"on"}

按名字取 app-config 被拒，可是 list 返回的是完整对象，data 一字不少。也就是说「给 list 不给 get」挡不住任何内容。对 Secret 来说这一点尤其要紧：给了 list secrets，就等于能读到这个 namespace 里所有 Secret 的值。Secret 的其他注意事项见 Secret 安全边界与轮换。

resourceNames：只允许操作指定名字的对象

只允许改 app-config 这一个 ConfigMap，把常用动词都写上：

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-config-only
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["app-config"]
    verbs: ["get", "list", "watch", "update", "patch", "create", "delete"]

绑给 ServiceAccount app-config-editor，并设 E=system:serviceaccount:notes-lab:app-config-editor。

$ kubectl -n notes-lab get cm app-config --as=$E
NAME         DATA   AGE
app-config   2      30s
$ kubectl -n notes-lab get cm other-config --as=$E
Error from server (Forbidden): configmaps "other-config" is forbidden: User "system:serviceaccount:notes-lab:app-config-editor" cannot get resource "configmaps" in API group "" in the namespace "notes-lab"
$ kubectl -n notes-lab patch cm app-config -p '{"data":{"log_level":"debug"}}' --as=$E
configmap/app-config patched
$ kubectl -n notes-lab patch cm other-config -p '{"data":{"feature_x":"off"}}' --as=$E
Error from server (Forbidden): configmaps "other-config" is forbidden: User "system:serviceaccount:notes-lab:app-config-editor" cannot get resource "configmaps" in API group "" in the namespace "notes-lab"
$ kubectl -n notes-lab get cm --as=$E
Error from server (Forbidden): configmaps is forbidden: User "system:serviceaccount:notes-lab:app-config-editor" cannot list resource "configmaps" in API group "" in the namespace "notes-lab"
$ kubectl -n notes-lab get cm --field-selector metadata.name=app-config --as=$E
NAME         DATA   AGE
app-config   2      31s
$ kubectl -n notes-lab delete cm app-config --as=$E
configmap "app-config" deleted
$ kubectl -n notes-lab create cm app-config --from-literal=log_level=warn --as=$E
error: failed to create configmap: configmaps is forbidden: User "system:serviceaccount:notes-lab:app-config-editor" cannot create resource "configmaps" in API group "" in the namespace "notes-lab"

这一组输出里有三个值得记住的地方：

  1. patch 别的对象，报的是 cannot get。kubectl 的 patch 会先 GET 一次对象，被拒在了这一步，所以错误里的动词不一定是你执行的那个命令。-v=6 能看到请求停在第一个 GET 上：

    GET https://<apiserver>/api/v1/namespaces/notes-lab/configmaps/other-config 403 Forbidden in 4 milliseconds
Error from server (Forbidden): configmaps "other-config" is forbidden: User "system:serviceaccount:notes-lab:app-config-editor" cannot get resource "configmaps" in API group "" in the namespace "notes-lab"

  2. list 要带字段选择器。规则写了 list，但不带条件的 get cm 仍然被拒；加上 --field-selector metadata.name=app-config，请求范围和 resourceNames 对上了才放行。

  3. 能删不能建。create 请求在授权时对象还没有名字，resourceNames 对它无效，所以这个身份把 app-config 删掉之后再也建不回来。需要「删了重建」语义的程序，create 得单独写一条不带 resourceNames 的规则；否则就别删，原地 update/patch。这个限制只针对顶层资源的 create，子资源上 resourceNames 照常有效，比如可以只允许 exec 进某个指定的 Pod。

子资源要单独授权

kubectl logs 访问的是 pods/log，kubectl exec 访问的是 pods/exec，对 pods 的权限不会自动覆盖它们。前面的错误信息已经说明：logs 要 get pods/log，exec 报的是 cannot create resource "pods/exec"。

先故意只给 exec 写 get，看看会怎样（绑定名 app-reader-debug，主体仍是 app-reader）：

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-debugger
rules:
  - apiGroups: [""]
    resources: ["pods/log"]
    verbs: ["get"]
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["get"]
$ kubectl -n notes-lab logs web --as=$SA --tail=1
2026/10/12 04:55:06 [notice] 1#1: start worker process 63
$ kubectl -n notes-lab exec web --as=$SA -- hostname
web

只有 get pods/exec，exec 却成功了。用 -v=6 看请求方法：

GET https://<apiserver>/api/v1/namespaces/notes-lab/pods/web/exec?command=hostname&container=nginx&stderr=true&stdout=true 101 Switching Protocols in 4 milliseconds
web

kubectl v1.30 的 exec 默认先走 WebSocket，握手是一个 HTTP GET，对应 RBAC 的 get 动词。关掉 WebSocket 强制走旧的 SPDY 协议，请求变成 POST，就要 create 了：

$ KUBECTL_REMOTE_COMMAND_WEBSOCKETS=false kubectl -n notes-lab exec web --as=$SA -v=6 -- hostname
POST https://<apiserver>/api/v1/namespaces/notes-lab/pods/web/exec?command=hostname&container=nginx&stderr=true&stdout=true 403 Forbidden in 4 milliseconds
Error from server (Forbidden): pods "web" is forbidden: User "system:serviceaccount:notes-lab:app-reader" cannot create resource "pods/exec" in API group "" in the namespace "notes-lab"

回头再看最开始那次失败，删掉 pod-debugger 的绑定重新执行，-v=6 里能看到 GET 先失败（没有拿到 101），kubectl 随即回退到 POST，最后打印的是 POST 的错误：

GET https://<apiserver>/api/v1/namespaces/notes-lab/pods/web/exec?command=hostname&container=nginx&stderr=true&stdout=true  in 3 milliseconds
POST https://<apiserver>/api/v1/namespaces/notes-lab/pods/web/exec?command=hostname&container=nginx&stderr=true&stdout=true 403 Forbidden in 2 milliseconds
Error from server (Forbidden): pods "web" is forbidden: User "system:serviceaccount:notes-lab:app-reader" cannot create resource "pods/exec" in API group "" in the namespace "notes-lab"

所以错误信息里的 create 只反映了回退后的那次请求。

按文档的写法把 exec 规则改成 create（其余不变）：

- apiGroups: [""]
  resources: ["pods/exec"]
  verbs: ["create"]
GET https://<apiserver>/api/v1/namespaces/notes-lab/pods/web/exec?command=hostname&container=nginx&stderr=true&stdout=true  in 2 milliseconds
POST https://<apiserver>/api/v1/namespaces/notes-lab/pods/web/exec?command=hostname&container=nginx&stderr=true&stdout=true 101 Switching Protocols in 19 milliseconds
web

WebSocket 的 GET 失败，回退到 POST 后成功，命令能跑，只是多了一次往返。

这个「只要 get 就能 exec」的缺口是 v1.34 及以前的行为。v1.35 加了特性门控 AuthorizePodWebsocketUpgradeCreatePermission（Beta，默认开启），对 pods/exec、pods/attach、pods/portforward 的 WebSocket 升级请求也检查 create，和 SPDY 一致。这一点来自官方 changelog 和特性门控说明，本文的 v1.31 集群上没法验证。所以：授予 exec 权限一律写 create，新老版本都能用；审计 v1.34 及以前的集群时，pods/exec 上的 get 也要当作 exec 权限看待。另外，上面的协议选择只测了 kubectl v1.30，其他客户端未必相同。

RoleBinding 引用 ClusterRole

ClusterRole 本身没有 namespace，但用 RoleBinding 引用它时，授予的权限只在 RoleBinding 所在的 namespace 里有效。这是复用内置角色最常见的方式（下面设 V=system:serviceaccount:notes-lab:viewer）：

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: viewer-view
subjects:
  - kind: ServiceAccount
    name: viewer
    namespace: notes-lab
roleRef:
  kind: ClusterRole
  name: view
  apiGroup: rbac.authorization.k8s.io
notes-lab        list pods: yes
kube-system      list pods: no
default          list pods: no
list deployments.apps                         yes
list configmaps                               yes
list secrets                                  no
get pods --subresource=log                    yes
create pods --subresource=exec                no
list rolebindings.rbac.authorization.k8s.io   no
create configmaps                             no
Warning: resource 'namespaces' is not namespace scoped

list namespaces                               yes
Warning: resource 'nodes' is not namespace scoped

view 只读、不含 Secret，也看不到 Role 和 RoleBinding，和官方文档的描述一致；跨出 notes-lab 就全是 no。

奇怪的是 list namespaces 显示 yes。view 里确实有 namespaces 的读权限，但 namespace 是集群级资源，can-i 带着 -n 发出的检查请求在真实 API 调用里并不存在。实际调用一下：

$ kubectl auth can-i list namespaces --as=$V
Warning: resource 'namespaces' is not namespace scoped

no
$ kubectl get namespaces --as=$V
Error from server (Forbidden): namespaces is forbidden: User "system:serviceaccount:notes-lab:viewer" cannot list resource "namespaces" in API group "" at the cluster scope
$ kubectl get namespace notes-lab --as=$V
NAME             STATUS   AGE
notes-lab   Active   5m13s

列出所有 namespace 被拒（at the cluster scope），但读取 notes-lab 这个 namespace 对象本身成功了。从结果推测，读取单个 namespace 时授权器把它当作「在该 namespace 内」的请求，于是 notes-lab 里的 RoleBinding 生效。去掉 -n 也不行，Warning 照样出现：没写 -n 时 kubectl 用的是 kubeconfig 当前 context 的 namespace（没设时为 default，这里就是没设）。用 -v=8 看三种写法发出的检查请求：

$ kubectl auth can-i list namespaces --as=$V -v=8 | ...
"resourceAttributes":{"namespace":"default","verb":"list","resource":"namespaces"}
$ kubectl auth can-i list namespaces -n notes-lab --as=$V -v=8 | ...
"resourceAttributes":{"namespace":"notes-lab","verb":"list","resource":"namespaces"}
$ kubectl auth can-i list namespaces -A --as=$V -v=8 | ...
"resourceAttributes":{"verb":"list","resource":"namespaces"}

只要请求里带了 namespace，kubectl 就打印那条 Warning。前面不带 -n 得到 no，只是因为 viewer 在 default 里没有绑定，并不是问对了；换一个在 default 有绑定的身份，同样会得到错误的 yes。真正和实际调用一致的是 -A，它不带 namespace：

$ kubectl auth can-i list namespaces -A --as=$V
no

所以对集群级资源，用 can-i ... -A 来问；看到 not namespace scoped 的 Warning，就说明这次的结果不可信。

要把一个 ClusterRole 授予所有 namespace，才用 ClusterRoleBinding。这次实验没有创建任何集群级绑定。

几种不报错但不生效的配置

apiGroups 写错

Deployment 在 apps 组，下面这条规则写成了核心组 ""（Role 名 deploy-manager，绑给 ServiceAccount deployer，设 D=system:serviceaccount:notes-lab:deployer）：

rules:
  - apiGroups: [""]
    resources: ["deployments"]
    verbs: ["get", "list", "update", "patch"]

apply 正常通过，权限却没有：

$ kubectl -n notes-lab auth can-i list deployments.apps --as=$D
no
$ kubectl -n notes-lab get deployments --as=$D
Error from server (Forbidden): deployments.apps is forbidden: User "system:serviceaccount:notes-lab:deployer" cannot list resource "deployments" in API group "apps" in the namespace "notes-lab"
$ kubectl -n notes-lab auth can-i --list --as=$D
Resources                                       Non-Resource URLs                      Resource Names   Verbs
selfsubjectreviews.authentication.k8s.io        []                                     []               [create]
selfsubjectaccessreviews.authorization.k8s.io   []                                     []               [create]
selfsubjectrulesreviews.authorization.k8s.io    []                                     []               [create]
deployments                                     []                                     []               [get list update patch]
...

RBAC 不校验资源是否真的存在于某个组里。can-i --list 里的线索是 deployments 后面没有 .apps 后缀，说明规则落在了核心组；错误信息里的 in API group "apps" 则直接告诉你应该写哪个组。不确定时用 kubectl api-resources 查 APIVERSION 列。

--list 的输出里还有几条 selfsubject* 和一串 /healthz、/version 之类的非资源 URL，它们来自集群对所有已认证用户的默认绑定（system:basic-user、system:discovery 等），每个 ServiceAccount 都有。这个集群里还多出了 Calico 的 globalnetworkpolicies 等条目，来自 Calico 自带的一个绑给 system:authenticated 的 ClusterRoleBinding，别的集群未必有。

roleRef 名字拼错

roleRef: {kind: Role, name: pods-reader, apiGroup: rbac.authorization.k8s.io}
rolebinding.rbac.authorization.k8s.io/typo-role created
$ kubectl -n notes-lab auth can-i list pods --as=$D
no - RBAC: role.rbac.authorization.k8s.io "pods-reader" not found
$ kubectl -n notes-lab get rolebinding typo-role -o wide
NAME        ROLE               AGE   USERS   GROUPS   SERVICEACCOUNTS
typo-role   Role/pods-reader   28s                    notes-lab/deployer

引用不存在的 Role，绑定照样能建，get 看上去也一切正常。好在 can-i 的 no 后面附带了原因，直接指出 Role 找不到。发现写错了想就地改，会碰到第二个限制：

$ kubectl -n notes-lab patch rolebinding typo-role --type=json -p '[{"op":"replace","path":"/roleRef/name","value":"pod-reader"}]'
The RoleBinding "typo-role" is invalid: roleRef: Invalid value: rbac.RoleRef{APIGroup:"rbac.authorization.k8s.io", Kind:"Role", Name:"pod-reader"}: cannot change roleRef

roleRef 创建后不可修改，只能删掉重建。官方给的理由是：这样可以放心地把某个绑定的 update 权限交给别人维护成员列表，而对方没法借机把角色换成更大的。

ServiceAccount 主体漏写 namespace

subjects:
  - kind: ServiceAccount
    name: deployer

本以为会被拒，结果在 RoleBinding 里创建成功，而且生效了：

rolebinding.rbac.authorization.k8s.io/bad-subject created
$ kubectl -n notes-lab auth can-i list pods --as=$D -v=8 2>&1 | grep 'Response Body' | grep -oE 'RBAC: allowed by [^}]*'
RBAC: allowed by RoleBinding \"bad-subject/notes-lab\" of Role \"pod-reader\" to ServiceAccount \"deployer/notes-lab\""

RoleBinding 里省略的 namespace 被当成了绑定自己所在的 namespace。同样的写法放进 ClusterRoleBinding 就不行，用服务端 dry-run 验证（不会真正创建）：

$ kubectl create clusterrolebinding notes-lab-dryrun --clusterrole=view --serviceaccount=notes-lab:deployer --dry-run=client -o yaml \
    | sed '/namespace:/d' | kubectl apply --dry-run=server -f -
The ClusterRoleBinding "notes-lab-dryrun" is invalid: subjects[0].namespace: Required value

省略能用，但不建议依赖它：清单被拷到另一个 namespace 应用时，主体会悄悄变成那个 namespace 里的同名 ServiceAccount。显式写上 namespace 更不容易出错。

不需要 API 的 Pod：关掉 token 挂载

默认情况下每个 Pod 都会挂上 ServiceAccount token，哪怕它从不访问 API。容器被攻破时，这个 token 就是现成的凭据。automountServiceAccountToken 可以写在 ServiceAccount 上，也可以写在 Pod 上。测三种组合：

apiVersion: v1
kind: ServiceAccount
metadata:
  name: no-token
automountServiceAccountToken: false
---
# pod-off：用 default SA，Pod 上写 automountServiceAccountToken: false
# sa-off：用 no-token SA，Pod 上不写
# sa-off-pod-on：用 no-token SA，Pod 上写 automountServiceAccountToken: true
== pod-off
ls: /var/run/secrets/kubernetes.io/serviceaccount: No such file or directory
command terminated with exit code 1
volumes: 
== sa-off
ls: /var/run/secrets/kubernetes.io/serviceaccount: No such file or directory
command terminated with exit code 1
volumes: 
== sa-off-pod-on
ca.crt
namespace
token
volumes: kube-api-access-959xs

两边都关掉时，Pod 里连 kube-api-access-* 卷都没有注入；ServiceAccount 上关了、Pod 上显式打开，以 Pod 为准。所以 ServiceAccount 上的 false 只是默认值，能创建 Pod 的人可以在 Pod 里覆盖它。没有 token 的 Pod 去访问 API，就是前面那个 system:anonymous 的 403。容器进程本身的权限由安全上下文控制，namespace 级的 Pod 约束见 Pod Security Admission。

挂进 Pod 的 token 什么时候过期

看 api-client 被注入的卷：

$ kubectl -n notes-lab get pod api-client -o jsonpath='{.spec.volumes[0]}' | python3 -m json.tool
{
    "name": "kube-api-access-k5f29",
    "projected": {
        "defaultMode": 420,
        "sources": [
            {
                "serviceAccountToken": {
                    "expirationSeconds": 3607,
                    "path": "token"
                }
            },
            {
                "configMap": {
                    "items": [
                        {
                            "key": "ca.crt",
                            "path": "ca.crt"
                        }
                    ],
                    "name": "kube-root-ca.crt"
                }
            },
            {
                "downwardAPI": {
                    "items": [
                        {
                            "fieldRef": {
                                "apiVersion": "v1",
                                "fieldPath": "metadata.namespace"
                            },
                            "path": "namespace"
                        }
                    ]
                }
            }
        ]
    }
}

token、CA 证书、namespace 三个文件分别来自 TokenRequest、kube-root-ca.crt 这个 ConfigMap 和 Downward API，合成一个投射卷。expirationSeconds 写的是 3607 秒，约一小时。但解开 token 的 JWT 载荷看（节选）：

{
 "aud": [
  "https://kubernetes.default.svc.cluster.local"
 ],
 "exp": 1823316955,
 "iat": 1791780955,
 "iss": "https://kubernetes.default.svc.cluster.local",
 "kubernetes.io": {
  "namespace": "notes-lab",
  "node": {
   "name": "worker",
   ...
  },
  "pod": {
   "name": "api-client",
   "uid": "a7e44ade-0bb0-46bb-ada8-6821d25bf344"
  },
  "serviceaccount": {
   "name": "app-reader",
   ...
  },
  "warnafter": 1791784562
 },
 "nbf": 1791780955,
 "sub": "system:serviceaccount:notes-lab:app-reader"
}
iat 2026-10-12 04:55:55 exp 2027-10-12 04:55:55 lifetime_s 31536000

实际有效期是 31536000 秒，整整一年。warnafter 比 iat 晚 3607 秒，才是那个「一小时」。这是 API Server 的 --service-account-extend-token-expiration（默认开启）在起作用：自动注入的 token 被延长到最多一年，好让还没学会重新读取 token 文件的老客户端不至于一小时后突然失效。kubelet 会在 token 存活超过 TTL 的 80% 或超过 24 小时时去换新的，应用要做的是每次请求（或定期）重新读文件，而不是启动时读一次缓存到底。

手工签发的 token 不享受这个延长：

$ kubectl -n notes-lab create token app-reader --duration=5m
error: failed to create token: TokenRequest.authentication.k8s.io "" is invalid: spec.expirationSeconds: Invalid value: 300: may not specify a duration less than 10 minutes
--duration=10m:
iat 2026-10-12 04:58:35 exp 2026-10-12 05:08:35 lifetime 600 s no-pod-binding
--duration=1h:
iat 2026-10-12 04:58:35 exp 2026-10-12 05:58:35 lifetime 3600 s no-pod-binding
--duration=48h:
iat 2026-10-12 04:58:35 exp 2026-10-14 04:58:35 lifetime 172800 s no-pod-binding

最短 10 分钟；本集群没有设置 --service-account-max-token-expiration，所以 48 小时也照给，设了上限的集群会被截断。这些 token 都没有绑定到任何 Pod。

一年的有效期听起来吓人，但 Pod 里的 token 绑定了 Pod 的 uid。把 token 拷出来，在集群外用 curl 访问，然后删掉 Pod 再试：

[04:57:51] token from pod, pod alive:
HTTP 200
[04:57:51] delete pod
pod "api-client" deleted
[04:58:28] same token after pod deleted:
{
  "kind": "Status",
  "apiVersion": "v1",
  "metadata": {},
  "status": "Failure",
  "message": "Unauthorized",
  "reason": "Unauthorized",
  "code": 401
}HTTP 401

Pod 一删，token 立即变成 401。所以一年只在 Pod 活着时才有意义，而 kubectl create token 签出的 token 不绑定 Pod，泄露后只能等它到期或删掉 ServiceAccount，时长要按需给短。

清理

kubectl delete namespace notes-lab

Role、RoleBinding、ServiceAccount 都是 namespace 级对象，随 namespace 一起删除。如果实验里建过 ClusterRole 或 ClusterRoleBinding，要单独删。
