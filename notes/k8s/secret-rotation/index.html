更新 Secret 不等于完成轮换

Secret 的安全使用边界讲了谁能读到 Secret、环境变量和文件的暴露面差别、immutable 与 1MiB 限制。这一篇只讨论一件事：凭据换了之后，应用什么时候真正用上新值。这中间有三段延迟，每一段都可能让你误以为「已经轮换完了」：

  1. API 里的 Secret 改了，kubelet 要过一段时间才把新内容写进 Pod 的卷；
  2. 卷里的文件变了，应用如果只在启动时读一次，内存里仍然是旧值；
  3. 应用用上新值了，但对端（数据库、上游服务）是否接受新凭据、旧凭据什么时候作废，是另一套时序。

下文输出都来自一个三节点 kind 集群（Kubernetes v1.31.0，containerd 1.7.18，CNI 为 Calico），实验放在单独的 notes-lab namespace 里。节点名简化为 worker、worker2。Pod 里打印的时间是 UTC。凭据一律是 v1-demo、v2-demo 这类演示标记，不要把真实密钥写进命令行。

一个 Pod，三种拿法

先建 namespace 和 Secret，再让同一个 Pod 用三种方式拿到同一个 key：整卷挂载、subPath 挂成单个文件、secretKeyRef 注入环境变量。容器里每 0.2 秒读一遍三处的值，有变化才打印一行：

kubectl create namespace notes-lab
until kubectl -n notes-lab get serviceaccount default >/dev/null 2>&1; do sleep 1; done
kubectl -n notes-lab create secret generic rotation-demo --from-literal=token=v1-demo
apiVersion: v1
kind: Pod
metadata:
  name: watcher
spec:
  containers:
    - name: w
      image: busybox:1.36
      env:
        - name: TOKEN_ENV
          valueFrom:
            secretKeyRef: {name: rotation-demo, key: token}
      command:
        - sh
        - -c
        - |
          last=""
          while true; do
            cur="vol=$(cat /run/cred/token) subPath=$(cat /etc/app/token) env=$TOKEN_ENV"
            if [ "$cur" != "$last" ]; then echo "$(date +%T) $cur"; last="$cur"; fi
            sleep 0.2
          done
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 32Mi}
      volumeMounts:
        - name: cred
          mountPath: /run/cred
          readOnly: true
        - name: cred
          mountPath: /etc/app/token
          subPath: token
          readOnly: true
  volumes:
    - name: cred
      secret:
        secretName: rotation-demo

卷里的文件多久才变

用 merge patch 把 token 依次改成 v2-demo … v7-demo，每次改完就在宿主机上反复 exec cat，直到读到新值为止；两次修改之间隔开不同的秒数，避免总是落在同一个相位上：

11:38:43 vol=v7-demo subPath=v1-demo env=v1-demo

6 次延迟分别是 81、38、60、34、68、51 秒；subPath 和 env 始终是 v1-demo。这和 ConfigMap 的实测是同一套机制，那篇已经展开过，这里各用一句话带过：

  • 节点 kubelet 生效配置（configz）是 syncFrequency = 1m0s、configMapAndSecretChangeDetectionStrategy = Watch，缓存几乎实时，延迟主要花在等下一轮 Pod 同步上。本篇相邻两次更新的间隔是 77、80、70、83、85 秒，结合 kubelet v1.31 pod_workers.go 里的 workerResyncIntervalJitterFactor = 0.5，推测每个 Pod 每 60 到 90 秒同步一次，所以要准备等最多一分半钟；6 个样本不能当作上限保证。
  • 改完 Secret 立刻给 Pod 打一个无关注解（kubectl annotate pod watcher --overwrite notes-lab.io/poke=8），会触发一次立即同步，3 次都在同一秒内就变了。这只适合排障时确认「是不是只是还没同步」。
  • subPath 在容器创建时绑定当时的那个真实文件，环境变量在容器创建时取值，运行中都不会变。

文件是怎么换掉的：监听要放在目录上

卷里的 token 是 token -> ..data/token 的符号链接，kubelet 每次更新时新建一个时间戳目录，再把 ..data 原子地切过去（机制见 ConfigMap 那篇）。本篇关心的是：应用如果用 inotify 或 fsnotify 做热加载，能收到什么事件。

这一节是之后在一个全新的 namespace 里单独跑的，所以时间戳和前后几节对不上。除了上面的 watcher，再起一个去掉 subPath 挂载的 watcher-nosub（只删掉 /etc/app/token 那个 volumeMount，循环里也不再读它）。沿用前面的环境的话，先删掉旧 Pod、把 token 重置为 v1：

kubectl -n notes-lab delete pod watcher
kubectl -n notes-lab patch secret rotation-demo --type=merge -p '{"stringData":{"token":"v1-demo"}}'
kubectl -n notes-lab apply -f watcher.yaml -f watcher-nosub.yaml

v1 时先对照 inode：watcher 里卷路径解析出的文件和 subPath 挂载的文件是同一个 inode：

$ kubectl -n notes-lab exec watcher -- sh -c 'stat -L -c "%i %n" /run/cred/token /etc/app/token'
3 /run/cred/token
3 /etc/app/token
$ kubectl -n notes-lab exec watcher-nosub -- sh -c 'stat -L -c "%i %n" /run/cred/token'
3 /run/cred/token

在两个 Pod 里都用 busybox 的 inotifyd 同时监听文件路径和目录，然后改成 v2-demo，并打注解触发同步：

kubectl -n notes-lab exec watcher -- sh -c 'inotifyd - /run/cred/token:cDMx > /tmp/ino-file.log 2>&1 & inotifyd - /run/cred:nyDMd > /tmp/ino-dir.log 2>&1 & sleep 1; echo started'
# watcher-nosub 里执行同一条
kubectl -n notes-lab patch secret rotation-demo --type=merge -p '{"stringData":{"token":"v2-demo"}}'
kubectl -n notes-lab annotate pod watcher watcher-nosub --overwrite notes-lab.io/poke=2

3 秒后：

== watcher-nosub file watch
D	/run/cred/token
x	/run/cred/token
== watcher-nosub dir watch

y	/run/cred	..data

   37 root      0:00 inotifyd - /run/cred nyDMd

目录上的事件依次是：创建新时间戳目录、创建临时链接 ..data_tmp、把它 rename 成 ..data、删除旧目录。文件路径上的监听，两个 Pod 结果不同：

  • watcher-nosub 只收到 D（被删除）和 x（监听失效），随后监听文件的那个 inotifyd 退出，进程列表里只剩监听目录的 37 号。前面那个 watcher 在改到 v11（第 10 次更新）之后才建立监听，下一次更新时同样只收到 D 和 x。
  • watcher 一个事件都没收到，36 号监听进程还在。更新后再看 inode，卷路径已经指向新文件，subPath 那边还是 3：
$ kubectl -n notes-lab exec watcher -- sh -c 'stat -L -c "%i %n" /run/cred/token /etc/app/token'
7 /run/cred/token
3 /etc/app/token

推测是 subPath 的 bind mount 一直占着 inode 3，旧目录删掉后这个文件也没有真正释放，所以既没有「修改」，也没有「删除」。

结论：不用 subPath 时，只监听文件只会收到 D/x，然后监听作废；同一容器里还用 subPath 挂着同一个 key 时，可能一个事件都收不到。两种情况都没有 c（内容修改）事件。所以热加载要监听目录（看 ..data 的 rename），或者收到删除事件后重新解析路径、重建监听；只监听文件、等「修改」事件的写法永远等不到。

subPath 和环境变量

运行中的容器里，这两种方式都不会变。容器原地重启（restartPolicy: Always，进程退出后由 kubelet 拉起）时能拿到新的环境变量；subPath 能不能拿到新值，要看重启那一刻卷是否已经同步。用一个每次启动打印三处的值、30 秒后自己退出的容器来测，kubelet 会把它原地拉起：

完整清单 restarter.yaml
apiVersion: v1
kind: Pod
metadata:
  name: restarter
spec:
  restartPolicy: Always
  containers:
    - name: app
      image: busybox:1.36
      # 每次容器启动打印一次三种来源的值，30 秒后退出，由 kubelet 原地重启容器
      command: ["sh", "-c", "echo \"$(date +%T) start vol=$(cat /run/cred/token) subPath=$(cat /etc/app/token) env=$TOKEN_ENV\"; sleep 30"]
      env:
        - name: TOKEN_ENV
          valueFrom:
            secretKeyRef: {name: rotation-demo, key: token}
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 32Mi}
      volumeMounts:
        - {name: cred, mountPath: /run/cred, readOnly: true}
        - {name: cred, mountPath: /etc/app/token, subPath: token, readOnly: true}
  volumes:
    - name: cred
      secret: {secretName: rotation-demo}

不需要额外命令触发重启，容器每 30 秒自己退出一次。此时 token 是 v5-demo，等第一次启动后改成 v6-demo：

kubectl -n notes-lab apply -f restarter.yaml
kubectl -n notes-lab wait --for=condition=Ready pod/restarter --timeout=60s
kubectl -n notes-lab patch secret rotation-demo --type=merge -p '{"stringData":{"token":"v6-demo"}}'
kubectl -n notes-lab logs restarter --previous; kubectl -n notes-lab logs restarter

这次 11:58:15 改成 v6-demo，第一次重启时卷还没同步：

  [log] 11:58:43 start vol=v5-demo subPath=v5-demo env=v6-demo
11:58:44 running container sees: vol=v6-demo subPath=v5-demo env=v6-demo  restarts=1

环境变量是新的，subPath 是旧的，并且在这个容器的整个生命周期里都停在 v5；到 11:59:26 下一次重启时三处才都是 v6。这个时机不可控，所以用了 subPath 或环境变量的 Secret，轮换时仍以滚动重建 Pod 为准。ConfigMap 那篇还碰到过容器重启时 subPath 挂载直接失败的情况。

文件变了，应用未必用上

前面的 watcher 每次都重新 cat，所以文件一变它就「用上」了。真实应用多数在启动时读一次配置。用两个 busybox httpd 做对比，CGI 都返回自己当前在用的 token：

  • static-app：启动时 T=$(cat /run/cred/token)，把值写死进 CGI 脚本，之后只用内存里这份；
  • live-app：CGI 脚本里是 $(cat /run/cred/token)，每个请求都重新读文件。
完整清单 apps.yaml（static-app 与 live-app）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: static-app
spec:
  replicas: 1
  selector:
    matchLabels: {app: static-app}
  template:
    metadata:
      labels: {app: static-app}
    spec:
      containers:
        - name: app
          image: busybox:1.36
          # 启动时读一次凭据，之后一直用内存里的值
          command:
            - sh
            - -c
            - |
              T=$(cat /run/cred/token)
              mkdir -p /www/cgi-bin
              printf '#!/bin/sh\necho "Content-Type: text/plain"\necho\necho "%s started=%s using=%s"\n' "$HOSTNAME" "$(date +%T)" "$T" > /www/cgi-bin/t
              chmod +x /www/cgi-bin/t
              exec httpd -f -p 8080 -h /www
          ports: [{containerPort: 8080}]
          resources:
            requests: {cpu: 10m, memory: 16Mi}
            limits: {memory: 32Mi}
          volumeMounts:
            - {name: cred, mountPath: /run/cred, readOnly: true}
      volumes:
        - name: cred
          secret: {secretName: rotation-demo}
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: live-app
spec:
  replicas: 1
  selector:
    matchLabels: {app: live-app}
  template:
    metadata:
      labels: {app: live-app}
    spec:
      containers:
        - name: app
          image: busybox:1.36
          # 每个请求都重新读文件
          command:
            - sh
            - -c
            - |
              mkdir -p /www/cgi-bin
              printf '#!/bin/sh\necho "Content-Type: text/plain"\necho\necho "%s started=%s using=$(cat /run/cred/token)"\n' "$HOSTNAME" "$(date +%T)" > /www/cgi-bin/t
              chmod +x /www/cgi-bin/t
              exec httpd -f -p 8080 -h /www
          ports: [{containerPort: 8080}]
          resources:
            requests: {cpu: 10m, memory: 16Mi}
            limits: {memory: 32Mi}
          volumeMounts:
            - {name: cred, mountPath: /run/cred, readOnly: true}
      volumes:
        - name: cred
          secret: {secretName: rotation-demo}

滚动重启

kubectl -n notes-lab rollout restart deploy/static-app
11:43:54.597 kubectl rollout restart deploy/static-app
deployment.apps/static-app restarted
11:43:54.719 static-app-9dfd4c597-4z797 started=11:41:27 using=v1-demo
11:43:55.288 static-app-9dfd4c597-4z797 started=11:41:27 using=v1-demo
11:43:55.873 static-app-9dfd4c597-4z797 started=11:41:27 using=v1-demo
11:43:56.445 static-app-57699dc76-zs2bh started=11:43:55 using=v2-demo
first v2 response after 1.9s

1.9 秒后请求就落到了新 Pod 上。这么快是因为 busybox 镜像已经在节点上、也没有配就绪探针；真实服务要加上拉镜像、启动和就绪探针的时间，多副本时还要按 maxSurge/maxUnavailable 逐批替换。rollout restart 的原理是往 Pod 模板里写一个注解：

{"kubectl.kubernetes.io/restartedAt":"2026-10-13T19:43:54+08:00"}

新 Pod 在创建时读取 Secret，所以拿到的是当时 API 里的值（kubelet 的 watch 缓存可能有很短的滞后），不受前面那 60 到 90 秒同步周期的影响。

用 checksum 注解把轮换绑进发布

rollout restart 要人记得去执行。另一种常见做法是把 Secret 内容的哈希写进 Pod 模板的注解，内容一变哈希就变，模板变了 Deployment 自然滚动。Helm 里一般写成 checksum/secret: {{ include (print $.Template.BasePath "/secret.yaml") . | sha256sum }}，见 Helm Chart。这里用 kubectl 手工模拟同样的步骤：

sum=$(kubectl -n notes-lab get secret rotation-demo -o jsonpath='{.data}' | sha256sum | cut -c1-16)
kubectl -n notes-lab patch deploy static-app -p \
  "{\"spec\":{\"template\":{\"metadata\":{\"annotations\":{\"checksum/rotation-demo\":\"$sum\"}}}}}"

依次执行三次：首次写入、Secret 没变时重复执行、改 Secret 之后再执行：

哈希不变时 patched (no change)，不产生新的 ReplicaSet；哈希一变就多出一个 ReplicaSet，新 Pod 用上了 v3。单独 kubectl patch secret 不会触发滚动，前面 static-app 那段就是例子：11:41:40 patch 之后，直到 11:43:54 手动 rollout restart，一直是同一个 ReplicaSet static-app-9dfd4c597（restart 后列出的 RS 里它的 AGE 是 2m29s）在服务。所以第 3 步必须由同一个发布流程重新计算哈希、更新 Deployment。这个办法只对「Secret 和 Deployment 走同一条发布管道」的情况有效；如果 Secret 由外部系统直接写进集群，模板里的哈希不会自己变。

双凭据轮换：先加新的，再删旧的

上面只看了「使用方」。轮换真正容易出事的地方，是使用方和校验方的切换时间对不上。搭一个最小模型：

  • auth-server：挂载 Secret auth-server-tokens，其中 tokens 每行一个可接受的令牌，每个请求都重新读文件；
  • client：挂载 Secret client-cred，启动时读一次自己的令牌，之后每 2 秒请求一次 auth-server。
# auth-server 的 CGI：令牌在列表里就返回 accepted，否则 401
t="${QUERY_STRING#token=}"
if grep -qxF "$t" /run/accepted/tokens; then
  printf 'Content-Type: text/plain\n\naccepted %s\n' "$t"
else
  printf 'Status: 401 Unauthorized\nContent-Type: text/plain\n\nrejected %s\n' "$t"
fi
完整清单 dual.yaml（auth-server 与 client）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: auth-server
spec:
  replicas: 1
  selector:
    matchLabels: {app: auth-server}
  template:
    metadata:
      labels: {app: auth-server}
    spec:
      containers:
        - name: server
          image: busybox:1.36
          # 每个请求重新读取 /run/accepted/tokens（每行一个可接受的令牌）
          command:
            - sh
            - -c
            - |
              mkdir -p /www/cgi-bin
              cat > /www/cgi-bin/check <<'CGI'
              #!/bin/sh
              t="${QUERY_STRING#token=}"
              if grep -qxF "$t" /run/accepted/tokens; then
                printf 'Content-Type: text/plain\n\naccepted %s\n' "$t"
              else
                printf 'Status: 401 Unauthorized\nContent-Type: text/plain\n\nrejected %s\n' "$t"
              fi
              CGI
              chmod +x /www/cgi-bin/check
              exec httpd -f -p 8080 -h /www
          ports: [{containerPort: 8080}]
          resources:
            requests: {cpu: 10m, memory: 16Mi}
            limits: {memory: 32Mi}
          volumeMounts:
            - {name: accepted, mountPath: /run/accepted, readOnly: true}
      volumes:
        - name: accepted
          secret: {secretName: auth-server-tokens}
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: client
spec:
  replicas: 1
  selector:
    matchLabels: {app: client}
  template:
    metadata:
      labels: {app: client}
    spec:
      containers:
        - name: client
          image: busybox:1.36
          # 启动时读一次自己的令牌，之后每 2 秒调用一次 auth-server
          command:
            - sh
            - -c
            - |
              T=$(cat /run/cred/token)
              while true; do
                r=$(wget -qO- "http://auth-server:8080/cgi-bin/check?token=$T" 2>&1)
                echo "$(date +%T) $HOSTNAME token=$T -> $r"
                sleep 2
              done
          resources:
            requests: {cpu: 10m, memory: 16Mi}
            limits: {memory: 32Mi}
          volumeMounts:
            - {name: cred, mountPath: /run/cred, readOnly: true}
      volumes:
        - name: cred
          secret: {secretName: client-cred}
kubectl -n notes-lab create secret generic auth-server-tokens --from-literal=tokens=v1-demo
kubectl -n notes-lab create secret generic client-cred --from-literal=token=v1-demo
kubectl -n notes-lab apply -f dual.yaml
kubectl -n notes-lab expose deploy auth-server --port=8080
11:44:44 client-f774c9458-xrrxr token=v1-demo -> accepted v1-demo

错误做法：两边同时换

服务端只接受 v2，客户端也换成 v2 并滚动重启，三条命令几乎同时执行：

kubectl -n notes-lab patch secret auth-server-tokens --type=merge -p '{"stringData":{"tokens":"v2-demo"}}'
kubectl -n notes-lab patch secret client-cred --type=merge -p '{"stringData":{"token":"v2-demo"}}'
kubectl -n notes-lab rollout restart deploy/client

客户端是新 Pod，立即拿到 v2；服务端是老 Pod，要等卷同步：

11:45:04 一步到位：server 只接受 v2，client 改成 v2 并重启
11:45:06 server file: v1-demo
...
11:45:55 server file: v1-demo
11:45:58 server file: v2-demo
11:45:05 client-64bfcf4878-x75dq token=v2-demo -> wget: server returned error: HTTP/1.1 401 Unauthorized
11:45:07 client-64bfcf4878-x75dq token=v2-demo -> wget: server returned error: HTTP/1.1 401 Unauthorized
...
11:45:55 client-64bfcf4878-x75dq token=v2-demo -> wget: server returned error: HTTP/1.1 401 Unauthorized
11:45:57 client-64bfcf4878-x75dq token=v2-demo -> wget: server returned error: HTTP/1.1 401 Unauthorized
11:45:59 client-64bfcf4878-x75dq token=v2-demo -> accepted v2-demo

从 11:45:05 到 11:45:57，连续 27 次请求全是 401，持续 54 秒。两边的 Secret 在 API 里是同时改的，但「新 Pod 立即读到」和「老 Pod 要等同步」的速度差，直接变成了一段故障窗口。如果服务端也是启动时只读一次，这个窗口会一直持续到服务端重启为止。

正确做法：三步

# 1. 服务端同时接受新旧两个
kubectl -n notes-lab patch secret auth-server-tokens --type=merge -p '{"stringData":{"tokens":"v2-demo\nv3-demo"}}'
#    等服务端确实读到了 v3（看文件，或者用 v3 发一次测试请求）
# 2. 客户端换成新的并滚动重启
kubectl -n notes-lab patch secret client-cred --type=merge -p '{"stringData":{"token":"v3-demo"}}'
kubectl -n notes-lab rollout restart deploy/client
# 3. 所有客户端都换完后，服务端移除旧的
kubectl -n notes-lab patch secret auth-server-tokens --type=merge -p '{"stringData":{"tokens":"v3-demo"}}'
11:48:37 第 1 步：server 同时接受 v2 和 v3
secret/auth-server-tokens patched
11:48:48 server 文件已变为: v2-demo,v3-demo
11:48:48 第 2 步：client 换成 v3 并滚动重启
...
deployment "client" successfully rolled out
11:48:55 第 3 步：server 移除 v2
secret/auth-server-tokens patched
11:49:59 server 文件已变为: v3-demo
wget: server returned error: HTTP/1.1 401 Unauthorized
command terminated with exit code 1
accepted v3-demo

最后两行是第 3 步完成后分别用 v2 和 v3 测试：旧令牌已被拒绝，新令牌可用。新客户端 Pod 的日志里一次 401 也没有：

$ kubectl -n notes-lab logs deploy/client | grep -c accepted; kubectl -n notes-lab logs deploy/client | grep -c 401
41
0

关键在第 1 步之后的那个「等」：不能 patch 完就进入第 2 步，要确认服务端真的已经接受新令牌。这次第 1 步等了 11 秒，第 3 步等了 64 秒，正好又是一次 0 到 90 秒之间的随机等待。真实系统里，「服务端」可能是数据库的用户表、云厂商的 API Key 列表，第 1 步就对应「签发新凭据、旧凭据暂不吊销」；能否同时持有两份有效凭据，取决于对端系统，这一点在选型时就要确认。

删除仍被挂载的 Secret

11:50:23 删除 rotation-demo，此时 watcher 和 static-app 都挂着它。100 秒后：

$ kubectl -n notes-lab exec watcher -- sh -c 'cat /run/cred/token; echo; cat /etc/app/token; echo; echo env=$TOKEN_ENV'
v3-demo
v1-demo
env=v1-demo
$ kubectl -n notes-lab exec watcher -- ls -la /run/cred/
drwxr-xr-x    2 root     root            60 Oct 13 11:44 ..2026_10_13_11_44_58.2002317777
lrwxrwxrwx    1 root     root            32 Oct 13 11:44 ..data -> ..2026_10_13_11_44_58.2002317777
lrwxrwxrwx    1 root     root            12 Oct 13 11:30 token -> ..data/token

已经在跑的 Pod 不受影响：文件保留删除前的最后一版，Pod 也一直是 Running。kubelet 会反复重试挂载并报警告，64 秒内 8 条，远多于每分钟一次的周期同步。推测是失败操作的指数退避：从 0.5 秒起逐次翻倍，8 次约 63.5 秒，和这里的时间跨度对得上：

FIRST                  LAST                   COUNT   MSG
2026-10-13T11:51:21Z   2026-10-13T11:52:25Z   8       MountVolume.SetUp failed for volume "cred" : secret "rotation-demo" not found

新 Pod 就起不来了。此时对 static-app 做一次滚动重启，再单独创建一个只用 secretKeyRef 环境变量的 Pod env-only：

完整清单 env-only.yaml
apiVersion: v1
kind: Pod
metadata:
  name: env-only
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo token=$TOKEN_ENV; sleep 3600"]
      env:
        - name: TOKEN_ENV
          valueFrom:
            secretKeyRef: {name: rotation-demo, key: token}
      resources:
        requests: {cpu: 10m, memory: 16Mi}
        limits: {memory: 32Mi}
kubectl -n notes-lab rollout restart deploy/static-app
kubectl -n notes-lab apply -f env-only.yaml
NAME                          READY   STATUS                       RESTARTS   AGE
env-only                      0/1     CreateContainerConfigError   0          46s
static-app-64f8c6c558-lvzv7   0/1     ContainerCreating            0          46s
static-app-747c779f68-5pmht   1/1     Running                      0          8m46s

卷引用停在 ContainerCreating，事件是 FailedMount ... secret "rotation-demo" not found；环境变量引用停在 CreateContainerConfigError，事件是 Error: secret "rotation-demo" not found。两种状态怎么区分，ConfigMap 那篇对比过，这里不再展开。

好在 Deployment 的滚动更新要等新 Pod 就绪才会缩掉旧 ReplicaSet，旧 Pod static-app-747c779f68-5pmht 一直在服务，请求没有中断。这里只有 1 个副本，默认 maxUnavailable 是 25%，向下取整后为 0，所以不会先删旧 Pod；多副本时，滚动一开始就会先删掉 maxUnavailable 个旧 Pod，新 Pod 起不来，这部分容量就一直缺着。如果这时节点故障或旧 Pod 被驱逐，重建出来的 Pod 也会卡在同一个地方，服务就真的中断了。

11:53:12 用同样的名字重新创建 Secret（值为 v4-demo），kubelet 的重试很快接上：

11:53:12 重新创建 Secret (v4-demo)
secret/rotation-demo created
11:53:19 static-app rollout complete (+6s)
11:53:24 env-only Ready (+11s)

一直挂着它的 watcher 也在 11:53:29 把卷更新成了新 Secret 的内容：

11:53:29 vol=v4-demo subPath=v1-demo env=v1-demo

所以「先删旧 Secret、再建新 Secret」这种轮换方式，中间的空档里任何新建的 Pod 都起不来。要换 Secret 的名字（比如带版本号的 db-cred-v2），顺序应该是先建新的，改 Deployment 引用并滚动完成，再删旧的。官方文档也说明：默认情况下 Secret 是必需的，非 optional 的 Secret 都可用之前，Pod 的任何容器都不会启动；把卷或 secretKeyRef 标成 optional: true 可以让 Pod 在 Secret 缺失时照常启动，但那意味着应用要自己处理「没有凭据」的情况。

外部密钥系统同步过来的 Secret

如果集群装了 External Secrets Operator（需要先按官方 Helm chart 安装），Secret 的值来自外部密钥系统，由 ExternalSecret 按 refreshInterval 定期拉取并写入集群里的 Secret。只用 namespace 级对象就能演示：一个使用 Fake provider 的 SecretStore（值直接写在 spec 里），加一个 refreshInterval: 15s 的 ExternalSecret。Fake provider 只用于测试，apply 时会给出 Warning: store fake-store isn't currently maintained 的警告；下面的 apiVersion 是 external-secrets.io/v1，较老的 ESO 版本要写 v1beta1：

apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: fake-store
spec:
  provider:
    fake:
      data:
        - key: /demo/api-token
          value: ext-v1-demo
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: api-token
spec:
  refreshInterval: 15s
  secretStoreRef:
    name: fake-store
    kind: SecretStore
  target:
    name: api-token
  data:
    - secretKey: token
      remoteRef:
        key: /demo/api-token
NAME                                           STORETYPE     STORE        REFRESH INTERVAL   STATUS         READY
externalsecret.external-secrets.io/api-token   SecretStore   fake-store   15s                SecretSynced   True

改 SecretStore 里的值来模拟外部系统轮换，看集群里的 Secret 多久跟上：

kubectl -n notes-lab patch secretstore fake-store --type=json \
  -p '[{"op":"replace","path":"/spec/provider/fake/data/0/value","value":"ext-v2-demo"}]'
11:54:03 外部源改为 ext-v2-demo
11:54:17 Secret api-token 变为 ext-v2-demo (+13.4s)
11:54:25 外部源改为 ext-v3-demo
11:54:32 Secret api-token 变为 ext-v3-demo (+7.0s)
11:54:44 外部源改为 ext-v4-demo
11:54:47 Secret api-token 变为 ext-v4-demo (+3.3s)

都在 15 秒以内。把 refreshInterval 调成 1h 后再改外部值：

kubectl -n notes-lab patch externalsecret api-token --type=merge -p '{"spec":{"refreshInterval":"1h"}}'

20 秒内 Secret 不变；给 ExternalSecret 加一个 force-sync 注解，立即同步：

11:55:18 refreshInterval=1h，外部源改为 ext-v5-demo
11:55:38 20s 后 Secret 值: ext-v4-demo
externalsecret.external-secrets.io/api-token annotated
11:55:38 加 force-sync 注解后 Secret 变为 ext-v5-demo (+0.0s)
kubectl -n notes-lab annotate externalsecret api-token force-sync=$(date +%s) --overwrite

这只解决了「外部系统 → 集群里的 Secret」这一段。从 Secret 到卷文件的 0 到 90 秒、应用是否重新读文件、双凭据过渡，前面那些问题一个都不会少。端到端的最坏延迟，大致是 refreshInterval 加上 kubelet 的同步等待，再加上应用自己的重新加载机制。

小结

  • 整卷挂载的 Secret 会更新，但要等 kubelet 下一次同步这个 Pod。默认配置下这次测得 34 到 81 秒，推测上限在 90 秒左右；subPath 和环境变量在容器的整个生命周期里都不会变。
  • 文件是通过切换 ..data 符号链接原子替换的。做热加载的应用要监听目录，只监听文件收不到修改事件。
  • 应用只在启动时读一次凭据的话，文件变了也没有用，要靠滚动重启，或者在模板里加 checksum 注解，把 Secret 变更绑进发布流程。
  • 校验方和使用方同时切换会出现故障窗口，这次测到 54 秒的 401。应该先让校验方同时接受新旧两份、确认生效，再切使用方，最后撤销旧凭据。
  • 删除仍被引用的 Secret 时，运行中的 Pod 不受影响，新 Pod 会卡在 FailedMount 或 CreateContainerConfigError。换名字要先建后删。

谁能读取或修改这些 Secret，按 ServiceAccount 与 RBAC 收紧；Deployment 滚动的节奏见 Deployment。

kubectl delete namespace notes-lab
