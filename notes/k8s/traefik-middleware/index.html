路由规则之外再处理请求

Ingress 实验只处理了「请求转给谁」。Traefik 的 Middleware 是它自己的 CRD（middlewares.traefik.io），挂在路由上，在请求到达后端之前改写请求、直接返回响应，或者在响应回来时加头。挂载方式有两种：普通 Ingress 用注解 traefik.ingress.kubernetes.io/router.middlewares，Traefik 自己的 IngressRoute 用 middlewares: 字段。这一篇先用一个响应头确认链路，再把几个常用中间件逐个跑一遍，最后故意写错引用，看 Traefik 怎么处理。

下文的输出来自一个三节点 kind 集群（Kubernetes v1.31.0），控制器是集群里已经装好的 Traefik v3.7.9（namespace traefik，IngressClass traefik）。实验放在单独的 notes-lab namespace，跨命名空间的实验再加一个 notes-lab-b。Pod IP 用 <client-ip>、<traefik-pod-ip> 这类占位符代替。

先确认控制器读哪些 provider

CRD 装了不代表 Traefik 在读它，要看启动参数（只读）：

kubectl -n traefik get deploy traefik -o jsonpath='{range .spec.template.spec.containers[0].args[*]}{@}{"\n"}{end}'
--entryPoints.metrics.address=:9100/tcp
--entryPoints.traefik.address=:8080/tcp
--entryPoints.web.address=:8000/tcp
--entryPoints.websecure.address=:8443/tcp
--api.dashboard=true
--api.insecure=true
...
--providers.kubernetescrd
--providers.kubernetescrd.allowEmptyServices=true
--providers.kubernetesingress
--providers.kubernetesingress.allowEmptyServices=true
...
--log.level=INFO
--accesslog=true
--accesslog.format=json

三点和本文有关：

  • kubernetescrd 和 kubernetesingress 两个 provider 都开着。前者读 Middleware、IngressRoute，后者读 Ingress；Ingress 注解里引用 Middleware，就是跨 provider 引用。
  • 没有 --providers.kubernetescrd.allowCrossNamespace，按文档它默认是 false。后面专门测它。
  • --api.insecure=true 让 Traefik 在 8080 入口点上开放了 API 和 dashboard，不需要认证。这在实验集群里很方便，下面用它只读地查路由状态；生产环境不应该这样开。Traefik 文档的做法是关掉 insecure，建一个路由指向内部服务 api@internal（Kubernetes 上就是一个 IngressRoute，services 写 kind: TraefikService、name: api@internal），再挂上 basicAuth 之类的认证中间件；或者干脆不对外暴露，只在需要时用 kubectl port-forward 到本地访问。

CRD 里有哪些中间件，kubectl explain 直接能列出来：

kubectl explain middleware.spec --api-version=traefik.io/v1alpha1

basicAuth	<Object>

...
headers	<Object>

ipAllowList	<Object>

...
rateLimit	<Object>
redirectRegex	<Object>
redirectScheme	<Object>
...
stripPrefix	<Object>
stripPrefixRegex	<Object>

v3 把 ipWhiteList 改名为 ipAllowList，但 CRD 里旧字段还在，描述是 Deprecated: please use IPAllowList instead.。旧写法还能不能用，后面也会测。

第一个中间件：用响应头确认链路

一个 Middleware 加两个 Ingress，一个挂中间件、一个不挂，作为对照：

apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: lab-headers}
spec:
  headers:
    customResponseHeaders:
      X-Lab-Middleware: enabled
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: with-mw
  annotations:
    traefik.ingress.kubernetes.io/router.middlewares: notes-lab-lab-headers@kubernetescrd
spec:
  ingressClassName: traefik
  rules:
  - host: mw.notes-lab.test
    http:
      paths:
      - {path: /, pathType: Prefix, backend: {service: {name: whoami, port: {number: 80}}}}
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: plain
spec:
  ingressClassName: traefik
  rules:
  - host: plain.notes-lab.test
    http:
      paths:
      - {path: /, pathType: Prefix, backend: {service: {name: whoami, port: {number: 80}}}}

保存为 step1.yaml 并提交：

kubectl -n notes-lab apply -f step1.yaml

注解的值是 <Middleware 所在 namespace>-<Middleware 名称>@kubernetescrd。前半段是 Traefik 内部给这个中间件起的名字，@kubernetescrd 指明它来自 CRD provider。多个中间件用逗号分隔。

kubectl -n notes-lab exec client -- curl -si -H 'Host: mw.notes-lab.test' http://traefik.traefik.svc.cluster.local/
HTTP/1.1 200 OK
Content-Length: 519
Content-Type: text/plain; charset=utf-8
Date: Tue, 13 Oct 2026 11:26:08 GMT
X-Lab-Middleware: enabled

Name: whoami
Hostname: whoami-78bb5899bd-z4fcd
...
RemoteAddr: <traefik-pod-ip>:47738
GET / HTTP/1.1
Host: mw.notes-lab.test
...
X-Forwarded-For: <client-ip>
X-Forwarded-Host: mw.notes-lab.test
X-Forwarded-Port: 80
X-Forwarded-Proto: http

对照的 plain.notes-lab.test 返回的头里只有 Content-Length、Content-Type、Date，没有 X-Lab-Middleware。注意 X-Forwarded-For 和 X-Real-Ip 是 client Pod 自己的 IP：从 Pod 经 ClusterIP 访问 Traefik 没有被 SNAT，这和 Ingress 篇里走 NodePort 时看到节点地址不一样，后面的 ipAllowList 依赖这一点。

Traefik 把 Ingress 翻译成了什么路由、挂了哪些中间件，可以通过它的 API 查（这个集群开了 api.insecure，8080 端口直接可读）。先拿到 Traefik Pod 的 IP，再从 client 请求，返回的 JSON 在本机用 jq 挑几个字段：

TRAEFIK_POD_IP=$(kubectl -n traefik get pod -l app.kubernetes.io/name=traefik -o jsonpath='{.items[0].status.podIP}')
kubectl -n notes-lab exec client -- curl -s "http://$TRAEFIK_POD_IP:8080/api/http/routers?search=with-mw" \
  | jq -c '.[] | {name, entryPoints, rule, middlewares, status}'
{"name":"notes-lab-with-mw-mw-notes-lab-test@kubernetes","entryPoints":["metrics","web"],"rule":"Host(\"mw.notes-lab.test\") && PathPrefix(\"/\")","middlewares":["notes-lab-lab-headers@kubernetescrd"],"status":"enabled"}
{"name":"websecure-notes-lab-with-mw-mw-notes-lab-test@kubernetes","entryPoints":["websecure"],"rule":"Host(\"mw.notes-lab.test\") && PathPrefix(\"/\")","middlewares":["notes-lab-lab-headers@kubernetescrd"],"status":"enabled"}

一个 Ingress 生成了两个路由，分别挂在 HTTP（web）和 HTTPS（websecure）入口点上，中间件两边都挂了。路由名后缀是 @kubernetes，中间件后缀是 @kubernetescrd，两个来源不同。HTTP 那条的 entryPoints 里还有 metrics：Ingress 没写 traefik.ingress.kubernetes.io/router.entrypoints 注解时，这个集群里的路由同时挂到了 web 和用来暴露 Prometheus 指标的 metrics（9100 端口）上，websecure 则单独生成了一条 TLS 路由。不想让业务路由出现在指标端口上，就用这个注解限定，比如 router.entrypoints: web。后面几种故障里，多数会在这里的 status 和 error 字段留下痕迹，但不是全部，见后文。下文的 <traefik-pod-ip> 就是这里的 $TRAEFIK_POD_IP。

ipAllowList 一节单独提交。

stripPrefix：去掉路径前缀

apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: strip-api}
spec:
  stripPrefix:
    prefixes: ["/api"]

Ingress 的 path 是 /api（Prefix）。看 whoami 收到的请求行：

# 请求 /api/users?id=1
GET /users?id=1 HTTP/1.1
X-Forwarded-Prefix: /api
# 请求 /api
GET / HTTP/1.1
X-Forwarded-Prefix: /api
# 请求 /apiv2
GET /v2 HTTP/1.1
X-Forwarded-Prefix: /api

前两条符合预期：前缀去掉了，查询串保留，剥掉的部分放进 X-Forwarded-Prefix，后端要生成绝对链接时可以用它拼回去。路径剩空时补成了 /。

第三条是个坑。按 Kubernetes 规范，Prefix 类型的 /api 是按路径段匹配的，不应该匹配 /apiv2；但 Ingress 篇已经测到 Traefik 把它当字符串前缀处理，这里请求照样进来了，stripPrefix 也按字符串剥掉了 /api，后端收到的是 /v2。如果后端恰好有 /v2 这个路径，就会被意外访问到。要严格按段匹配，Traefik v3.7 的 Kubernetes Ingress provider 有一个 strictPrefixMatching 选项（默认 false，写在控制器的 providers.kubernetesIngress 配置里，对所有 Ingress 生效），打开后 /api 只匹配 /api、/api/ 和 /api/...；也可以改用 IngressRoute，规则写成 Path(`/api`) || PathPrefix(`/api/`)。这两种这次都没有测。

redirectScheme 和 redirectRegex：重定向，以及顺序的影响

apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: to-https}
spec:
  redirectScheme:
    scheme: https
    permanent: true
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: old-to-new}
spec:
  redirectRegex:
    regex: ^http://([^/]+)/old/(.*)
    replacement: http://${1}/new/${2}

先按 old-to-new,to-https 的顺序挂到一个 Ingress 上（就是上面 redirect 这个 Ingress），分别发 HTTP GET、POST 和 HTTPS 请求。HTTPS 入口点用的是 Traefik 的默认自签证书，所以要加 -k：

kubectl -n notes-lab exec client -- curl -si -H 'Host: redirect.notes-lab.test' http://traefik.traefik.svc.cluster.local/old/page | grep -iE '^(HTTP|Location)'
kubectl -n notes-lab exec client -- curl -si -X POST -H 'Host: redirect.notes-lab.test' http://traefik.traefik.svc.cluster.local/hello | grep -iE '^(HTTP|Location)'
kubectl -n notes-lab exec client -- curl -sik -H 'Host: redirect.notes-lab.test' https://traefik.traefik.svc.cluster.local/hello | grep -iE '^(HTTP|Location|Name)'
# GET /old/page
HTTP/1.1 302 Found
Location: http://redirect.notes-lab.test/new/page
# GET /hello
HTTP/1.1 301 Moved Permanently
Location: https://redirect.notes-lab.test/hello
# POST /hello
HTTP/1.1 308 Permanent Redirect
Location: https://redirect.notes-lab.test/hello
# 走 HTTPS 入口点 GET /hello
HTTP/2 200

几个细节：

  • redirectRegex 没写 permanent，返回 302；redirectScheme 写了 permanent: true，GET 返回 301，POST 返回 308。Traefik 的文档没有写具体状态码，这是实测结果。308 要求客户端保持原方法和请求体重发，301 则允许浏览器把 POST 改成 GET。
  • 请求已经是 HTTPS 时 redirectScheme 不动作，直接转给后端。
  • /old/page 被第一个中间件直接回了 302，第二个中间件根本没执行，所以 Location 还是 http://。客户端要再跳一次才到 HTTPS。

把注解顺序反过来，变成 to-https,old-to-new：

kubectl -n notes-lab annotate ingress redirect --overwrite \
  traefik.ingress.kubernetes.io/router.middlewares=notes-lab-to-https@kubernetescrd,notes-lab-old-to-new@kubernetescrd
# HTTP GET /old/page
HTTP/1.1 301 Moved Permanently
Location: https://redirect.notes-lab.test/old/page
# HTTPS GET /old/page
HTTP/2 200

HTTP 请求先被升到 HTTPS，路径没变；可升过去以后，HTTPS 上的 /old/page 直接 200，没有再跳 /new/page。原因是正则写的是 ^http://，而 redirectRegex 匹配的是包含协议的完整 URL，HTTPS 请求的 URL 以 https:// 开头，匹配不上。所以无论哪个顺序，这组配置都有一条路径没处理对；正则里写成 ^https?:// 才能两边都覆盖。

basicAuth：Secret 的两种写法

apiVersion: v1
kind: Secret
metadata: {name: lab-users}
type: Opaque
stringData:
  users: |
    labuser:$apr1$MzKHePyU$m81zaAgDGMAKy57MJPR6o.
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: lab-auth}
spec:
  basicAuth:
    secret: lab-users
    headerField: X-Auth-User
    removeHeader: true

users 里每行是 用户名:哈希，哈希支持 MD5、SHA1、BCrypt。没有 htpasswd 时可以用 openssl passwd -apr1 labpass 生成 MD5（apr1）格式，上面这串就是这样生成的，密码是 labpass，只用于实验。

# 不带凭据
HTTP/1.1 401 Unauthorized
Content-Type: text/plain
Www-Authenticate: Basic realm="traefik"
# 密码错误
401
# -u labuser:labpass，whoami 收到的头
Name: whoami
X-Auth-User: labuser

realm 默认是 traefik。认证通过后，后端通过 headerField 拿到用户名；removeHeader: true 让 Authorization 头在转给后端前被删掉，whoami 的输出里确实没有它，后端不会再看到用户密码。

另一种写法是 kubernetes.io/basic-auth 类型的 Secret，只放 username 和 password 两个键。后面的故障实验里用它补建了一个 Secret，labuser:labpass 认证通过。这种 Secret 里的密码是明文（只是 base64 编码），文档也提醒它比哈希方式更不安全。

rateLimit：令牌桶，实测数一数

apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: lab-ratelimit}
spec:
  rateLimit:
    average: 5
    burst: 10

按文档，这是一个令牌桶：桶容量为 burst，以 average / period（period 默认 1 秒）的速度补充，超出的请求被拒。不写 sourceCriterion 时按请求的远端地址分桶。

先连续不停地发 30 个请求：

kubectl -n notes-lab exec client -- sh -c 'for i in $(seq 1 30); do curl -s -o /dev/null -w "%{http_code} " -H "Host: rl.notes-lab.test" http://traefik.traefik.svc.cluster.local/; done; echo'
200 200 200 200 200 200 200 200 200 200 429 429 429 429 429 429 429 429 429 429 429 429 429 429 429 200 429 429 429 429

前 10 个正好是 burst，桶空之后返回 429，中间那一个 200 是这段时间里补充进来的一个令牌。被拒的响应长这样：

HTTP/1.1 429 Too Many Requests
Retry-After: 1
X-Retry-In: 150.024237ms
Date: Tue, 13 Oct 2026 11:27:19 GMT
Content-Length: 17

Too Many Requests

X-Retry-In 告诉客户端还要等多久才有下一个令牌，比 Retry-After 的整秒精确。

再控制发送速度，每次间隔几秒等桶回满：

不间断（1 秒内发完）600s1248
每次 sleep 0.05，约 10 个/秒10010s5743
每次 sleep 0.1，约 6 个/秒6010s600
每次 sleep 0.25，约 3.75 个/秒308s300

按令牌桶算，约 10 个/秒发 10 秒，理论放行量是 10 + 5×10 = 60 个，实测 57 个。差的 3 个推测是计时误差：date +%s 只精确到秒，实际发送时间可能不到 10 秒。约 6 个/秒那一行虽然超过了 5，但 10 秒里多出的约 10 个请求刚好被 10 个令牌的余量吃掉，全部通过；推测再持续久一点就会开始出现 429，这次没有测。所以 burst 不只是「瞬时峰值」，它也决定了略超速率的流量能撑多久。

这里只有一个 Traefik 副本。按 RateLimit 文档，不配 redis 时限流用的是内存存储，只对单个 Traefik 实例有效；要让多个副本共享同一个限额，需要配置 CRD 里的 redis 字段。多副本的情况这次没有测。另外按远端地址分桶意味着：如果客户端都经过同一个 SNAT 出口进来，它们会共用一个桶。

ipAllowList：Traefik 认为客户端是谁

先查 client Pod 的 IP：

kubectl -n notes-lab get pod client -o jsonpath='{.status.podIP}'

把它填进白名单，保存为 step3.yaml，用 kubectl -n notes-lab apply -f step3.yaml 提交：

    traefik.ingress.kubernetes.io/router.middlewares: notes-lab-only-client@kubernetescrd

从 client 访问：

换一个客户端：在宿主机上对 Traefik 的 Service 做端口转发，从宿主机请求。

kubectl -n traefik port-forward svc/traefik 28472:80 &

curl -si -H 'Host: allow.notes-lab.test' http://127.0.0.1:28472/
HTTP/1.1 403 Forbidden
Date: Tue, 13 Oct 2026 11:28:43 GMT

Forbidden

被拒是 403，可以用 rejectStatusCode 改。拒绝的原因从没挂中间件的 plain 路由上看得很清楚：

$ curl -s -H 'Host: plain.notes-lab.test' http://127.0.0.1:28472/ | grep -E '^(RemoteAddr|X-Forwarded-For|X-Real-Ip)'
RemoteAddr: <traefik-pod-ip>:47738
X-Forwarded-For: 127.0.0.1
X-Real-Ip: 127.0.0.1

port-forward 是在 Traefik Pod 的网络命名空间里从 127.0.0.1 发起连接的，所以 Traefik 眼里客户端是 127.0.0.1。用端口转发调试带 ipAllowList 的路由时，403 很可能只是这个原因。调试完用 kill $PF_PID 结束这一个转发进程。

能不能伪造 X-Forwarded-For 绕过？先要分清：不设 ipStrategy 时，ipAllowList 比对的是 TCP 连接的远端地址，根本不看这个头，所以伪造了也没用，这一点说明不了 Traefik 怎么处理 XFF。要看 XFF 本身，得让中间件去读它。准备三个中间件，用一个 IngressRoute 分别挂到三个主机名上（Ingress 注解写法也一样，这里图省事）。allow.notes-lab.test 这个主机名上面的 allow Ingress 已经用过，进这一节之前先把它删掉，免得两条路由抢同一个 Host（这一步是示意，实测时这一节是在新建的 namespace 里做的，没有残留的 allow）：

kubectl -n notes-lab delete ingress allow

中间件和 IngressRoute 保存为 xff.yaml，用 kubectl -n notes-lab apply -f xff.yaml 提交：

apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: only-client}          # allow.notes-lab.test
spec:
  ipAllowList:
    sourceRange: ["<client-ip>/32"]
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: only-client-depth1}   # depth1.notes-lab.test
spec:
  ipAllowList:
    sourceRange: ["<client-ip>/32"]
    ipStrategy: {depth: 1}
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: only-fake-depth1}     # fake.notes-lab.test
spec:
  ipAllowList:
    sourceRange: ["203.0.113.7/32"]
    ipStrategy: {depth: 1}
---
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata: {name: xff}
spec:
  entryPoints: [web]
  routes:
  - match: Host(`allow.notes-lab.test`)
    kind: Rule
    middlewares: [{name: only-client}]
    services: [{name: whoami, port: 80}]
  - match: Host(`depth1.notes-lab.test`)
    kind: Rule
    middlewares: [{name: only-client-depth1}]
    services: [{name: whoami, port: 80}]
  - match: Host(`fake.notes-lab.test`)
    kind: Rule
    middlewares: [{name: only-fake-depth1}]
    services: [{name: whoami, port: 80}]

请求的写法（以 depth1 带伪造头为例，其余五次只换 Host 和是否带头）：

kubectl -n notes-lab exec client -- curl -s -o /dev/null -w '%{http_code}\n' \
  -H 'Host: depth1.notes-lab.test' -H 'X-Forwarded-For: 203.0.113.7' http://traefik.traefik.svc.cluster.local/

depth: 1 表示取 X-Forwarded-For 从右数第 1 个地址。每个主机名各请求两次，一次不带头，一次带 X-Forwarded-For: 203.0.113.7：

主机白名单ipStrategy不带 XFF带伪造 XFF
allow<client-ip>无（远端地址）200200
depth1<client-ip>depth: 1403403
fake203.0.113.7depth: 1403403

关键是 depth1 这一行。如果 Traefik 先把 XFF 改写成真实地址再交给中间件，depth: 1 应该取到 <client-ip> 并放行；实际两次都是 403。fake 一行也是 403，伪造值同样没有被读到。也就是说，入口点没有配置 forwardedHeaders.trustedIPs 时，实测中间件读不到客户端带来的 X-Forwarded-For（与这个头在中间件之前被删掉一致），而 XFF 里取不到地址时请求被拒绝，这也是实测结果。ipAllowList 文档对后一半有说明：上一跳的地址要到代理的最后阶段才追加进 X-Forwarded-For，那时已经过了白名单检查，所以无法用来匹配 sourceRange；depth 超过头里的地址个数时，客户端 IP 为空。后端收到的头是这样：

$ kubectl -n notes-lab exec client -- curl -s -H 'Host: plain.notes-lab.test' -H 'X-Forwarded-For: 203.0.113.7' http://traefik.traefik.svc.cluster.local/ | grep -E '^(X-Forwarded-For|X-Real-Ip)'
X-Forwarded-For: <client-ip>
X-Real-Ip: <client-ip>

后端看到的 <client-ip> 就是转发阶段追加的那一跳，中间件阶段还没有。实际后果是：没有可信代理时别给 ipAllowList 配 depth，否则白名单会拒掉所有人。rateLimit 的 sourceCriterion.ipStrategy 用的是同一套取地址逻辑，推测配了 depth 也会取不到地址，这次没有测。前面确实有一层可信代理（云负载均衡等）时，才需要配置 trustedIPs 并调整 depth；这种场景这次没有搭。

在 IngressRoute 上挂中间件，以及顺序

IngressRoute 是 Traefik 自己的路由 CRD，中间件直接写在每条 route 下面。准备两个设置同一组头的中间件，一个写 a、一个写 b，再用 chain 把它们打包：

apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: hdr-a}
spec:
  headers:
    customRequestHeaders: {X-Req-Order: a}
    customResponseHeaders: {X-Resp-Order: a}
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: hdr-b}
spec:
  headers:
    customRequestHeaders: {X-Req-Order: b}
    customResponseHeaders: {X-Resp-Order: b}
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: a-then-b}
spec:
  chain:
    middlewares:
    - name: hdr-a
    - name: hdr-b
---
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata: {name: order}
spec:
  entryPoints: [web]
  routes:
  - match: Host(`ab.notes-lab.test`)
    kind: Rule
    middlewares:
    - name: hdr-a
    - name: hdr-b
    services:
    - {name: whoami, port: 80}
  - match: Host(`ba.notes-lab.test`)
    kind: Rule
    middlewares:
    - name: hdr-b
    - name: hdr-a
    services:
    - {name: whoami, port: 80}
  - match: Host(`chain.notes-lab.test`)
    kind: Rule
    middlewares:
    - name: a-then-b
    services:
    - {name: whoami, port: 80}

IngressRoute 里同一 namespace 的中间件只写名字，不用拼 <ns>- 前缀和 @kubernetescrd。

kubectl -n notes-lab exec client -- curl -si -H 'Host: ab.notes-lab.test' http://traefik.traefik.svc.cluster.local/ | grep -E '^(HTTP|X-Resp-Order|X-Req-Order)'

X-Resp-Order 是响应头，X-Req-Order 出自 whoami 打印的请求头：

# ab：hdr-a, hdr-b
HTTP/1.1 200 OK
X-Resp-Order: a
X-Req-Order: b
# ba：hdr-b, hdr-a
HTTP/1.1 200 OK
X-Resp-Order: b
X-Req-Order: a
# chain：a-then-b
HTTP/1.1 200 OK
X-Resp-Order: a
X-Req-Order: b

同一个头，请求方向和响应方向是相反的两个赢家：

  • 请求头：列表里最后一个生效。请求按 a → b 的顺序穿过中间件，b 后写，覆盖了 a。
  • 响应头：列表里第一个生效。响应按 b → a 的顺序回来，a 最后写。

中间件像一层层洋葱，列表第一个在最外层。这和重定向实验里「第一个中间件直接返回，后面的不执行」是同一个模型。chain 的行为和直接把两个名字按同样顺序写在路由上一致，它的用处是把一组固定搭配（比如认证 + 限流 + 安全头）定义一次，在多个路由里复用。

在 Traefik API 里，这三条 route 各自生成了一个路由，middlewares 字段原样记录了顺序。路由名里的那串哈希由 Traefik 生成，换一个环境会不一样，按 rule 对照即可：

{"name":"notes-lab-order-4caae0e4441643731784@kubernetescrd","rule":"Host(`chain.notes-lab.test`)","middlewares":["notes-lab-a-then-b@kubernetescrd"],"status":"enabled"}
{"name":"notes-lab-order-5ecd62553c67becbaf8a@kubernetescrd","rule":"Host(`ab.notes-lab.test`)","middlewares":["notes-lab-hdr-a@kubernetescrd","notes-lab-hdr-b@kubernetescrd"],"status":"enabled"}
{"name":"notes-lab-order-c7d793208e15b43c4531@kubernetescrd","rule":"Host(`ba.notes-lab.test`)","middlewares":["notes-lab-hdr-b@kubernetescrd","notes-lab-hdr-a@kubernetescrd"],"status":"enabled"}

写错引用时：整条路由下线

直觉上，中间件引用写错，最多是「中间件没生效、请求照常转发」。在下面实测的几类错误里（注解格式写错、中间件被删除、IngressRoute 跨命名空间引用、Secret 不存在），都不是这样：整条路由直接下线。用 Ingress 注解跨命名空间引用则是成功的，见下文。

注解漏写后缀或前缀

# no-provider：漏了 @kubernetescrd
traefik.ingress.kubernetes.io/router.middlewares: notes-lab-lab-headers
# no-ns：漏了 namespace 前缀
traefik.ingress.kubernetes.io/router.middlewares: lab-headers@kubernetescrd

两个 Ingress 分别用 noprovider.、nons.notes-lab.test，后端都是正常的 whoami：

HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff

两个都是 404，和主机名写错一模一样。Traefik API 里路由被标成了 disabled：

{"name":"notes-lab-no-ns-nons-notes-lab-test@kubernetes","middlewares":["lab-headers@kubernetescrd"],"status":"disabled","error":["middleware \"lab-headers@kubernetescrd\" does not exist"]}
{"name":"notes-lab-no-provider-noprovider-notes-lab-test@kubernetes","middlewares":["notes-lab-lab-headers@kubernetes"],"status":"disabled","error":["middleware \"notes-lab-lab-headers@kubernetes\" does not exist"]}

注意第二行：漏写后缀时，Traefik 并不是去所有 provider 里找，而是自动补上了 Ingress 自己的 provider，变成 @kubernetes，而 Ingress provider 下面没有这个中间件。日志里是同样的错误，每个入口点（web、websecure、metrics）各报一遍，而且会反复出现：

kubectl -n traefik logs deploy/traefik --since=5m | grep notes-lab
2026-10-13T11:29:37Z ERR error="middleware \"notes-lab-lab-headers@kubernetes\" does not exist" entryPointName=web routerName=notes-lab-no-provider-noprovider-notes-lab-test@kubernetes
2026-10-13T11:29:39Z ERR error="middleware \"lab-headers@kubernetescrd\" does not exist" entryPointName=web routerName=notes-lab-no-ns-nons-notes-lab-test@kubernetes

（日志默认带终端颜色控制符，这里去掉了。）Kubernetes 这一侧完全看不出问题：kubectl get ingress 照样有 ADDRESS，describe 里后端也有 endpoint，Events 是 <none>：

NAME          CLASS     HOSTS                       ADDRESS    PORTS   AGE
no-provider   traefik   noprovider.notes-lab.test   <lb-ip>    80      15s
no-ns         traefik   nons.notes-lab.test         <lb-ip>    80      15s

同样的事也发生在删除中间件时：把正在被 with-mw 引用的 lab-headers 删掉，4 秒后再请求 mw.notes-lab.test，返回 404 Not Found。中间件和路由之间没有任何删除保护，删一个「只是加个头」的中间件，就能让引用它的路由全部下线。

单看这条路由，这种失败方式对安全类中间件是好事：认证或白名单写错，结果是 404，而不是绕过认证放行。但这有个前提，就是同一个 Host 上没有别的路由能接住这个请求，后面的 Secret 实验会演示前提不成立时的情况。另一个代价是排查时 404 会把人引向 Host、IngressClass，所以看到 404 而 Ingress 本身看起来正常时，先查 Traefik API 里路由的 status，或者在日志里搜 does not exist。

跨命名空间引用

换一个更能说明风险的例子：notes-lab-b 团队有一个中间件，用 customRequestHeaders 给自己的后端注入访问凭据（这里是一串假的 token）。notes-lab 里的人分别用 Ingress 注解和 IngressRoute 去引用它：

kubectl create namespace notes-lab-b
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata: {name: inject-token, namespace: notes-lab-b}
spec:
  headers:
    customRequestHeaders:
      Authorization: "Bearer fake-token-of-team-b"
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: borrow-token
  namespace: notes-lab
  annotations:
    traefik.ingress.kubernetes.io/router.middlewares: notes-lab-b-inject-token@kubernetescrd
spec:
  ingressClassName: traefik
  rules:
  - host: borrow.notes-lab.test
    http:
      paths:
      - {path: /, pathType: Prefix, backend: {service: {name: whoami, port: {number: 80}}}}
---
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata: {name: borrow-ir, namespace: notes-lab}
spec:
  entryPoints: [web]
  routes:
  - match: Host(`borrow-ir.notes-lab.test`)
    kind: Rule
    middlewares:
    - name: inject-token
      namespace: notes-lab-b
    services: [{name: whoami, port: 80}]

这份文件里每个对象都写了 namespace，直接 kubectl apply -f，不要加 -n。

$ kubectl -n notes-lab exec client -- curl -s -w 'HTTP %{http_code}\n' -H 'Host: borrow.notes-lab.test' http://traefik.traefik.svc.cluster.local/ | grep -E '^(Name|Authorization|HTTP)'
Name: whoami
Authorization: Bearer fake-token-of-team-b
HTTP 200
$ kubectl -n notes-lab exec client -- curl -s -w 'HTTP %{http_code}\n' -H 'Host: borrow-ir.notes-lab.test' http://traefik.traefik.svc.cluster.local/ | grep -E '^(Name|Authorization|HTTP)'
HTTP 404

两种写法结果相反。IngressRoute 被拒绝，日志说得很清楚：

2026-10-13T11:39:53Z ERR Failed to create middleware keys error="invalid reference to middleware inject-token: allowCrossNamespace is disabled, cross-namespace are disallowed" ingress=borrow-ir namespace=notes-lab providerName=kubernetescrd

Traefik API 的路由列表里干脆没有 borrow-ir 这条路由，不是 disabled，而是根本没生成，所以也查不到 status 和 error，只能看日志。

Ingress 注解却顺利用上了另一个 namespace 的中间件，notes-lab 自己的后端（这里是 whoami）收到了 notes-lab-b 的凭据，Traefik API 里这条路由是正常的 enabled：

{"name":"notes-lab-borrow-token-borrow-notes-lab-test@kubernetes","middlewares":["notes-lab-b-inject-token@kubernetescrd"],"status":"enabled","error":null}

文档对 allowCrossNamespace 的描述是「允许 IngressRoute 引用其他命名空间的资源」；Ingress 注解能不能引用其他 namespace 的中间件，文档没有说明，以上为实测。也就是说，在这个配置下，任何能在自己 namespace 里建 Ingress 的人，都能把别的 namespace 的中间件挂到自己的路由上，allowCrossNamespace: false 挡不住。Kubernetes Ingress provider 有一个相关的选项 crossProviderNamespaces，按文档它限定哪些 namespace 的 Ingress 可以使用 router.middlewares 这类跨 provider 引用的注解，不设置时全部允许。它按 Ingress 所在的 namespace 限制，而不是按被引用中间件所在的 namespace。由此推论：把 notes-lab 排除在这个列表之外，会拒掉 notes-lab 里所有的 @kubernetescrd 引用，包括引用它自己 namespace 里的中间件；对一个 namespace 来说只能全开或全关，做不到「只允许引用同 namespace 的中间件」。这一点和它能不能堵住上面的用法，这次都没有测。

顺带一提，<ns>-<name> 这种拼法本身有歧义：namespace notes-lab 里名为 b-inject-token 的中间件，拼出来的名字也是 notes-lab-b-inject-token。两者同时存在时 Traefik 会怎么处理，这次没有测。

basicAuth 引用的 Secret 不存在

kind: Middleware
metadata: {name: auth-missing}
spec:
  basicAuth:
    secret: no-such-secret
---
apiVersion: traefik.io/v1alpha1
kind: Middleware

metadata: {name: fail2}
spec:
  entryPoints: [web]

请求 authmissing.notes-lab.test 返回 404 Not Found。日志里先是中间件构建失败，再是路由找不到中间件：

2026-10-13T11:30:31Z ERR Error while reading basic auth middleware error="secret 'notes-lab/no-such-secret' not found" middlewareName=notes-lab-auth-missing providerName=kubernetescrd
2026-10-13T11:30:33Z ERR error="middleware \"notes-lab-auth-missing@kubernetescrd\" does not exist" entryPointName=web routerName=notes-lab-fail2-f82cb922c41068b2f270@kubernetescrd

kubectl apply 时没有任何报错，Middleware 对象正常创建，只是 Traefik 不把它载入，Traefik API 的中间件列表里也找不到它。路由的 error 里只有「middleware does not exist」，看不出真正的原因是 Secret 不存在，这一点只有日志里有。补建这个 Secret（这次用 kubernetes.io/basic-auth 类型）：

kubectl -n notes-lab create secret generic no-such-secret --type=kubernetes.io/basic-auth \
  --from-literal=username=labuser --from-literal=password=labpass
11:30:48 401

Secret 在 11:30:48 创建，同一秒内的请求已经变成 401，带上 labuser:labpass 返回 200。Traefik 监听 Secret 的变化，不需要重建 Middleware 或路由。

HTTP 200

不带任何凭据，/admin/users 直接到了后端。两条路由的状态：

{"name":"notes-lab-admin-f0cb6c3b892bd23254f9@kubernetescrd","rule":"Host(`site.notes-lab.test`) && PathPrefix(`/admin`)","priority":51,"middlewares":["notes-lab-admin-auth@kubernetescrd"],"status":"disabled","error":["middleware \"notes-lab-admin-auth@kubernetescrd\" does not exist"]}
{"name":"notes-lab-site-fallback-1bb4ef99e89eb6d8a989@kubernetescrd","rule":"Host(`site.notes-lab.test`)","priority":27,"middlewares":null,"status":"enabled","error":null}

正常情况下 /admin 路由的优先级更高（Traefik 默认按规则长度算，51 对 27），会先匹配。它下线以后，请求就落到了兜底路由上，认证被整个绕过。补建 Secret（第一条命令是示意写法，实测时是先用 openssl passwd -apr1 生成哈希，再把结果填进 --from-literal）：

kubectl -n notes-lab create secret generic admin-users \
  --from-literal=users="labuser:$(openssl passwd -apr1 labpass)"
kubectl -n notes-lab exec client -- curl -s -o /dev/null -w 'HTTP %{http_code}\n' \
  -H 'Host: site.notes-lab.test' http://traefik.traefik.svc.cluster.local/admin/users
kubectl -n notes-lab exec client -- curl -s -o /dev/null -w 'HTTP %{http_code}\n' \
  -H 'Host: site.notes-lab.test' http://traefik.traefik.svc.cluster.local/
secret/admin-users created
HTTP 401
HTTP 200

/admin/users 变回 401，/ 仍是 200。所以「引用写错就 404」只对单条路由成立；只要同一个 Host 上还有更宽的路由（兜底的 /、另一个 Ingress 里的同名主机），受保护路径就可能悄悄变成公开的。上线认证类中间件后，至少要用不带凭据的请求验证一次受保护路径返回的是 401。

旧名字 ipWhiteList

用 v2 的写法 ipWhiteList 建一个只放行 127.0.0.1/32 的中间件，从 client 请求返回 403 Forbidden，说明它照常生效。Traefik API 里它的类型是 ipwhitelist，日志里有一条提醒：

2026-10-13T11:30:33Z WRN Middleware "notes-lab-old-whitelist@kubernetescrd" of type IPWhiteList is deprecated, please use IPAllowList instead.

在 v3.7.9 上旧名字还能用，只是告警。迁移文档说 v3 只是改了名、配置不变，把字段名换成 ipAllowList 即可。

排查顺序

  1. 请求 404，但 Ingress 有 ADDRESS、后端有 endpoint：去 Traefik API 看这个路由在不在、status 是不是 disabled，或者在日志里搜 does not exist、cross-namespace、secret ... not found。本文测到的几类中间件引用错误都会让整条路由下线；跨命名空间被拒时路由根本不出现，Secret 不存在时 error 里看不到真正原因，这两种要看日志。受保护路径如果返回的是 200 而不是 404，检查同一 Host 上是否有兜底路由接走了请求。
  2. 路由正常，但响应不对：对照 API 里路由的 middlewares 列表顺序。请求方向从前往后执行，响应方向从后往前；提前返回的中间件（重定向、认证失败、限流、白名单）会让后面的都不执行。
  3. 白名单、限流结果奇怪：先确认 Traefik 认为的客户端地址，用一个不挂中间件的 whoami 路由看 X-Real-Ip。port-forward 进来的是 127.0.0.1，经 SNAT 进来的是节点地址。

清理

kubectl delete namespace notes-lab notes-lab-b

没有改动 traefik namespace 里的任何东西，也没有动 CRD 和 IngressClass。同一个 Traefik 作为 Gateway API 控制器时的路由写法见 Gateway API HTTPRoute 入门。
