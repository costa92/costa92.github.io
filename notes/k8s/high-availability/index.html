kubeadm 高可用拓扑

单控制平面安装适合学习引导流程，但 API Server 和 etcd 都只有一份，那台机器一停，整个集群就没法改了。kubeadm 的高可用方案是让多个控制平面节点躲在一个稳定的负载均衡入口后面，同时让 etcd 有足够成员形成多数派。加多少个工作节点都解决不了控制平面的单点问题。

两种官方拓扑

拓扑etcd 放在哪最少机器主要取舍
堆叠式（stacked）每个控制平面节点上跑一个 etcd 成员3 台kubeadm 默认；机器少，但停一台就同时少一个 API Server 和一个 etcd 成员
外部 etcd独立的 etcd 主机3 台控制平面 + 3 台 etcd控制平面和数据层的故障互不牵连，机器翻倍，运维多一套

官方文档对堆叠式有一句很关键的描述：每个控制平面节点上的 etcd 成员只和本节点的 kube-apiserver 通信；外部 etcd 拓扑下，每台 etcd 主机则与所有控制平面的 kube-apiserver 通信。这句话决定了后面故障演练里看到的很多现象。

下面的实验用的是一个临时的 kind 集群（kind v0.24.0，节点镜像 kindest/node:v1.31.0，etcd 3.5.15，CNI 是 kind 自带的 kindnet）：3 个控制平面节点、没有工作节点，属于堆叠式拓扑。前面的负载均衡器是 kind 自动创建的一个 haproxy 容器；真实环境一般用 keepalived + haproxy、硬件负载均衡或云厂商的 LB。kind 会给节点容器加上集群名前缀：下面用 --name ha-lab 建集群，容器名就是 ha-lab-control-plane、ha-lab-control-plane2、ha-lab-control-plane3 和 ha-lab-external-load-balancer。可复制的命令里写的是完整容器名；输出里为了好读去掉了前缀，写作 control-plane、external-load-balancer 等。容器 IP 和宿主机端口用 <cp1-ip>、<lb-port> 这类占位符代替。时间方面，15:xx 格式的（脚本和 date 输出）是 UTC+8，07:xx 格式的（组件日志、Kubernetes 对象里的时间戳）是 UTC，两者差 8 小时。实验结束后集群已删除。

# kind.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: control-plane
  - role: control-plane
kind create cluster --name ha-lab --image kindest/node:v1.31.0 --config kind.yaml --kubeconfig ./kubeconfig
kubectl --kubeconfig ./kubeconfig create namespace notes-lab

# 下文的 <cp1-ip>、<cp2-ip>、<cp3-ip>、<lb-ip> 分别是这几个容器在 kind 网络里的 IP
docker inspect -f '{{.Name}} {{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' \
  ha-lab-control-plane ha-lab-control-plane2 ha-lab-control-plane3 ha-lab-external-load-balancer

这台实验机的 Docker 数据目录在机械硬盘上，建集群用了 3 分 55 秒，下文的各种恢复时间也会比 SSD 上长，绝对值只能作参考。

入口：负载均衡器和 controlPlaneEndpoint

kind 生成的 haproxy 配置如下（节选）。haproxy 镜像里没有 cat，docker exec ... cat 会报 executable file not found，可以用 docker cp 导出：

docker cp ha-lab-external-load-balancer:/usr/local/etc/haproxy/haproxy.cfg - | tar -xO
defaults
  log global
  mode tcp
  option dontlognull
  # TODO: tune these
  timeout connect 5000
  timeout client 50000
  timeout server 50000

frontend control-plane
  bind *:6443
  
  default_backend kube-apiservers

backend kube-apiservers
  option httpchk GET /healthz
  # TODO: we should be verifying (!)
  
  server control-plane control-plane:6443 check check-ssl verify none resolvers docker resolve-prefer ipv4
  server control-plane2 control-plane2:6443 check check-ssl verify none resolvers docker resolve-prefer ipv4
  server control-plane3 control-plane3:6443 check check-ssl verify none resolvers docker resolve-prefer ipv4

两点值得注意：

  • mode tcp：负载均衡器只转发 TCP，TLS 由每个 API Server 自己终结。客户端证书认证要靠这一点，LB 不能把 TLS 拆掉。
  • 健康检查是 GET /healthz，而不是单纯的 TCP 端口探测。官方文档里云上 LB 的健康检查写的是 TCP 检查 6443 端口；HTTP 检查更严格，后面会看到它在 etcd 出问题时的效果。

kubeadm 把这个入口写进了 ClusterConfiguration：

kubectl --kubeconfig ./kubeconfig -n kube-system get cm kubeadm-config -o jsonpath='{.data.ClusterConfiguration}'
apiServer:
  certSANs:
  - localhost
  - 127.0.0.1
...
controlPlaneEndpoint: external-load-balancer:6443
...
etcd:
  local:
    dataDir: /var/lib/etcd

etcd.local 说明是堆叠式。宿主机上拿到的 kubeconfig 指向 LB 映射出来的端口 server: https://127.0.0.1:<lb-port>。再看节点上各组件的 kubeconfig 分别连到哪里：

for f in admin.conf kubelet.conf controller-manager.conf scheduler.conf; do
  echo -n "$f: "; docker exec ha-lab-control-plane2 grep server: /etc/kubernetes/$f
done
admin.conf:     server: https://external-load-balancer:6443
kubelet.conf:     server: https://external-load-balancer:6443
controller-manager.conf:     server: https://<cp2-ip>:6443
scheduler.conf:     server: https://<cp2-ip>:6443

kubelet 和管理员走 LB；本机的 controller-manager 和 scheduler 直接连本机 API Server。API Server 连 etcd 也只连本机：

docker exec ha-lab-control-plane2 grep -E 'etcd-servers' /etc/kubernetes/manifests/kube-apiserver.yaml
- --etcd-servers=https://127.0.0.1:2379

这就是文档里那句「只和本节点通信」的具体形态。

证书 SAN：用 LB 的 IP 访问会被拒

每个 API Server 证书的 SAN 里有 LB 的主机名，但没有 LB 的 IP：

docker exec ha-lab-control-plane3 openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -ext subjectAltName
X509v3 Subject Alternative Name: 
    DNS:kubernetes, DNS:kubernetes.default, DNS:kubernetes.default.svc, DNS:kubernetes.default.svc.cluster.local, DNS:localhost, DNS:control-plane3, DNS:external-load-balancer, IP Address:10.96.0.1, IP Address:<cp3-ip>, IP Address:127.0.0.1

把 kubeconfig 的 server 改成 LB 的容器 IP https://<lb-ip>:6443 试一下：

sed 's#server: https://127.0.0.1:<lb-port>#server: https://<lb-ip>:6443#' kubeconfig > kubeconfig-lbip
kubectl --kubeconfig ./kubeconfig-lbip get ns kube-system

E1013 15:36:10.482594  517926 memcache.go:265] couldn't get current server API group list: Get "https://<lb-ip>:6443/api?timeout=32s": tls: failed to verify certificate: x509: certificate is valid for 10.96.0.1, <cp1-ip>, 127.0.0.1, not <lb-ip>
E1013 15:36:10.484731  517926 memcache.go:265] couldn't get current server API group list: Get "https://<lb-ip>:6443/api?timeout=32s": tls: failed to verify certificate: x509: certificate is valid for 10.96.0.1, <cp3-ip>, 127.0.0.1, not <lb-ip>

这个报错顺带证明了 LB 是 TCP 透传：几次重试轮流落到了 control-plane3 和 control-plane 上，客户端看到的是后端各自的证书（当时 control-plane2 已停，所以只有两台）。客户端用来访问的每一个名字和 IP 都必须在 SAN 里，所以 controlPlaneEndpoint 要在 kubeadm init 时就定好；官方也建议用能解析的 DNS 名，并且 LB 的地址要始终和 controlPlaneEndpoint 一致。事后要加名字只能重新签发 API Server 证书；证书的日常检查见 kubeadm 证书到期检查。

etcd：三个成员与多数派

这次实验从 etcd 官方 Release 下载了 v3.5.15 的 etcdctl，用同一 Release 的 SHA256SUMS 校验过，拷进三个节点容器，用 kubeadm 生成的 healthcheck 客户端证书访问。其实 registry.k8s.io/etcd 镜像本身就带 etcdctl（但不带 etcdutl），kubectl -n kube-system exec etcd-<节点名> -- etcdctl ... 的用法在 etcd 快照里实测过。不过 API Server 不可用时 kubectl exec 也用不了，失去多数派的演练里还是得在节点上直接跑。

curl -LO https://github.com/etcd-io/etcd/releases/download/v3.5.15/etcd-v3.5.15-linux-amd64.tar.gz
curl -LO https://github.com/etcd-io/etcd/releases/download/v3.5.15/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS      # etcd-v3.5.15-linux-amd64.tar.gz: OK
tar -xzf etcd-v3.5.15-linux-amd64.tar.gz --strip-components=1 etcd-v3.5.15-linux-amd64/etcdctl
for n in "" 2 3; do
  docker cp etcdctl ha-lab-control-plane$n:/usr/local/bin/etcdctl
  docker cp ectl.sh ha-lab-control-plane$n:/usr/local/bin/ectl
done

ectl.sh 只是给 etcdctl 套上证书参数：

#!/bin/sh
exec etcdctl --cacert /etc/kubernetes/pki/etcd/ca.crt \
  --cert /etc/kubernetes/pki/etcd/healthcheck-client.crt \
  --key /etc/kubernetes/pki/etcd/healthcheck-client.key "$@"
EP=https://<cp1-ip>:2379,https://<cp2-ip>:2379,https://<cp3-ip>:2379
docker exec ha-lab-control-plane ectl --endpoints $EP member list -w table
docker exec ha-lab-control-plane ectl --endpoints $EP endpoint status -w table

scheduler 和 controller-manager：靠 Lease 选主

三个节点都跑着 kube-scheduler 和 kube-controller-manager，但同一时刻只有一个在干活，谁是 leader 记录在 kube-system 的 Lease 对象里：

kubectl --kubeconfig ./kubeconfig -n kube-system get lease kube-scheduler kube-controller-manager \
  -o custom-columns=NAME:.metadata.name,HOLDER:.spec.holderIdentity,DURATION:.spec.leaseDurationSeconds,TRANSITIONS:.spec.leaseTransitions,RENEW:.spec.renewTime
NAME                      HOLDER                                               DURATION   TRANSITIONS   RENEW
kube-scheduler            control-plane_24621221-e52b-4e13-ba47-4953114afa45   15         0             2026-10-13T07:26:56.023092Z
kube-controller-manager   control-plane_518a55fa-be15-49f0-98cd-79219093195f   15         0             2026-10-13T07:26:55.575013Z

两个 leader 和 etcd leader 恰好都在第一个节点 control-plane 上。默认参数是：租约 15 秒（--leader-elect-lease-duration）、leader 必须在 10 秒内续约成功否则主动退出（--leader-elect-renew-deadline）、每 2 秒尝试一次（--leader-elect-retry-period）。

故障演练

演练期间，宿主机上一直跑着下面这个脚本，经 LB 循环做三件事：读 namespace/kube-system、在 notes-lab 里新建一个 ConfigMap、查两个 Lease 的持有者。每个请求超时 4 秒，每轮之后睡 1 秒，所以请求失败时两行之间会隔十来秒：

#!/bin/bash
# usage: probe.sh <kubeconfig> <logfile>
KC=$1; LOG=$2; i=0
while [ ! -f $LOG.stop ]; do
  i=$((i+1)); t=$(date '+%H:%M:%S.%1N')
  r=$(timeout 6 kubectl --kubeconfig $KC --request-timeout=4s get ns kube-system -o name 2>&1 | tail -1 | cut -c1-160)
  w=$(timeout 6 kubectl --kubeconfig $KC --request-timeout=4s -n notes-lab create configmap probe-$i --from-literal=t=$t -o name 2>&1 | tail -1 | cut -c1-160)
  h=$(timeout 6 kubectl --kubeconfig $KC --request-timeout=4s -n kube-system get lease kube-scheduler kube-controller-manager -o jsonpath='{range .items[*]}{.spec.holderIdentity}{" "}{end}' 2>&1 | sed -E 's/_[0-9a-f-]{36}//g' | tail -1 | cut -c1-120)
  echo "$t | R: $r | W: $w | L: $h" >> $LOG
  sleep 1
done

每行格式是 时间 | R: 读 | W: 写 | L: scheduler 和 controller-manager 的持有者，时间戳是这一轮开始的时刻，错误信息被截断到 160 个字符。

停一台 follower：几乎无感

先停 control-plane2（docker stop ha-lab-control-plane2），它既不是 etcd leader，也不持有 Lease。docker stop 在 15:27:30.7 发出，15:27:46.4 返回（节点容器里跑着 systemd，停止要等一会儿）。

15:27:43.4 | R: namespace/kube-system | W: configmap/probe-5 | L: control-plane control-plane 
15:27:47.6 | R: namespace/kube-system | W: configmap/probe-6 | L: control-plane control-plane 
15:27:49.5 | R: namespace/kube-system | W: configmap/probe-7 | L: control-plane control-plane 
15:27:51.1 | R: namespace/kube-system | W: configmap/probe-8 | L: control-plane control-plane

读写一次都没失败。这一阶段只有一次 Lease 查询失败，发生在 stop 发出约 3 秒后、节点容器还在关闭的时候：

15:27:33.9 | R: namespace/kube-system | W: configmap/probe-3 | L: control-plane error: client rate limiter Wait returned an error: rate: Wait(n=1) would exceed context deadl

这条请求在 4 秒超时内没拿到结果，原因没有细查。可能是请求恰好落在正在关闭的 control-plane2 上；另一个可能和慢盘有关：故障注入之前，haproxy 在 07:27:22 因 /healthz 检查超时（Layer7 timeout）把 control-plane3 摘掉过一次，07:27:32 又加回来，说明这台机器上 API Server 偶尔就会响应很慢。两者都是推测。

haproxy 的日志显示它在 07:27:38 把 control-plane2 摘掉：

kubectl --kubeconfig ./kubeconfig get nodes

从发出 stop 到 Ready 变成 Unknown 大约 40 秒，与 v1.31 中 --node-monitor-grace-period 的默认值 40s 吻合（较新版本的文档里这个默认值已经是 50s）。

15:28:31.6 执行 docker start，15:29:12 检查时这个 etcd 成员已经恢复健康，并追上了日志（三个成员 raft index 都是 1448）；haproxy 在 07:29:16 把它重新加回后端。从启动到重新接流量大约 45 秒。

停掉 leader 所在的节点：etcd 秒切，Lease 要等十几秒

这次停 control-plane（docker stop ha-lab-control-plane），它同时是 etcd leader 和两个 Lease 的持有者。docker stop 在 15:29:27.2 发出。etcd 选主几乎是瞬间完成的，control-plane3 的 etcd 日志：

docker exec ha-lab-control-plane3 sh -c 'crictl logs $(crictl ps -q --name etcd) 2>&1' \
  | grep -E 'lost leader|elected leader|became leader|became candidate|is starting a new election'
{"level":"info","ts":"2026-10-13T07:29:27.640885Z","logger":"raft","caller":"etcdserver/zap_raft.go:77","msg":"d59766ecfc7dbb16 is starting a new election at term 2"}
{"level":"info","ts":"2026-10-13T07:29:27.640891Z","logger":"raft","caller":"etcdserver/zap_raft.go:77","msg":"d59766ecfc7dbb16 became candidate at term 3"}
{"level":"info","ts":"2026-10-13T07:29:27.640914Z","logger":"raft","caller":"etcdserver/zap_raft.go:77","msg":"raft.node: d59766ecfc7dbb16 lost leader 8d38bec195c4fc71 at term 3"}
{"level":"info","ts":"2026-10-13T07:29:28.409739Z","logger":"raft","caller":"etcdserver/zap_raft.go:77","msg":"d59766ecfc7dbb16 became leader at term 3"}

从发起选举到选出新 leader 不到 0.8 秒，term 从 2 变成 3。kind v0.24.0 的节点镜像设置了 STOPSIGNAL SIGRTMIN+3，docker stop 的信号先发给容器里的 systemd，再由 systemd 依次停掉 kubelet、containerd 和其中的容器，etcd 在这个过程中被正常终止。etcd 3.5 源码里写明 leader 停止时会把 leadership 移交给某个 peer（”When stopping leader, Stop transfers its leadership to one of its peers”）。时间上也对得上：stop 发出后 0.43 秒，control-plane3 就开始了选举，比 1 秒的最小选举超时还短，不像是等心跳超时触发的。所以推测这次是主动移交，日志里没有直接看到移交记录。断电、断网这类来不及移交的情况，按 etcd 文档要等大约一个选举超时才能选出新 leader。etcd 默认心跳间隔 100ms、选举超时 1000ms，kubeadm 生成的 etcd 静态 Pod 不覆盖这两个参数。

Lease 就慢得多（下面是探测脚本的记录，然后用前面那条 get lease 命令查 acquireTime）：

controller-manager 在 stop 发出后约 17 秒被 control-plane3 接管，scheduler 约 19 秒。停机前最后一次查到的续约时间是 07:29:25.13，controller-manager 新的 acquireTime 是 07:29:44.48，相隔约 19 秒：候选者要看到 Lease 超过 15 秒没有续约才会去抢，之后还有每 2 秒一次的重试。07:29:25.13 之后旧持有者有没有再续约过没有记录，所以 19 秒只是上限。这里旧持有者是随节点容器一起被停掉的，没有主动释放 Lease，候选者只能等它过期。空窗期里新建的 Pod 没人调度，控制器也停着，已经在跑的工作负载不受影响。

API 这边只有一次失败，发生在 control-plane 的 API Server 正在关闭、haproxy 还没把它摘掉（07:29:33 才摘）的那几秒：

15:29:28.4 | R: namespace/kube-system | W: configmap/probe-54 | L: control-plane control-plane 
15:29:32.1 | R: error: client rate limiter Wait returned an error: context deadline exceeded - error from a previous attempt: EOF | W: configmap/probe-55 | L: control-plane control-plane 
15:29:37.4 | R: namespace/kube-system | W: configmap/probe-56 | L: control-plane control-plane

新连接被 haproxy 转给了正在关闭的那个后端，连接被对端关掉（EOF），kubectl 重试到超时还是失败；下一次请求换了后端就正常了。客户端带重试的话这类失败通常能吸收掉，一次性的脚本则会直接报错。

再停一台：失去多数派

control-plane 还停着，接着在 15:30:17.4 再停 control-plane2（docker stop ha-lab-control-plane2），只剩 control-plane3 一个 etcd 成员，1/3 不是多数派。

剩下的这个成员没有 leader，线性一致读直接超时；而指定 --consistency=s（serializable）的读由本地成员直接回答，不经过共识，能返回结果，但可能是旧数据：

$ docker exec ha-lab-control-plane3 ectl --endpoints https://<cp3-ip>:2379 endpoint status -w table
| https://<cp3-ip>:2379 | d59766ecfc7dbb16 |  3.5.15 |  2.5 MB |     false |      false |         3 |       1633 |               1633 | etcdserver: no leader |
$ docker exec ha-lab-control-plane3 ectl --endpoints https://<cp3-ip>:2379 get /registry/namespaces/kube-system --keys-only
Error: context deadline exceeded
$ docker exec ha-lab-control-plane3 ectl --endpoints https://<cp3-ip>:2379 get /registry/namespaces/kube-system --keys-only --consistency=s
/registry/namespaces/kube-system

Kubernetes 的客户端经 LB 访问时，看到的不是 etcd 的错误，而是连接直接被关掉：

$ time kubectl --kubeconfig ./kubeconfig -n notes-lab create configmap via-lb --from-literal=a=b
error: failed to create configmap: Post "https://127.0.0.1:<lb-port>/api/v1/namespaces/notes-lab/configmaps?fieldManager=kubectl-create&fieldValidation=Strict": EOF

real	0m0.018s

原因在 haproxy 日志里：control-plane3 的 API Server 进程还活着，但它的 /healthz 依赖 etcd，检查超时，于是 kind 的这个 haproxy 把最后一个后端也摘了：

docker logs --since 3m ha-lab-external-load-balancer 2>&1 | tail -6
[WARNING] 285/073029 (55) : Server kube-apiservers/control-plane3 is DOWN, reason: Layer7 timeout, check duration: 2001ms. 0 active and 0 backup servers left. 4 sessions active, 0 requeued, 0 remaining in queue.
[ALERT] 285/073029 (55) : backend 'kube-apiservers' has no server available!

绕过 LB 直接连 control-plane3 的 API Server，才能看到真正的错误。kind 把每个控制平面节点的 6443 也映射到了宿主机端口，用 docker port 查出来，再用 sed 生成一份 kubeconfig（证书 SAN 里有 127.0.0.1，可以直接用）：

docker port ha-lab-control-plane3 6443      # 输出形如 127.0.0.1:<cp3-port>
sed 's#server: https://127.0.0.1:<lb-port>#server: https://127.0.0.1:<cp3-port>#' kubeconfig > kubeconfig-cp3

读和写的报法不一样：

$ time kubectl --kubeconfig ./kubeconfig-cp3 get ns kube-system
Error from server: etcdserver: request timed out

real	0m7.402s
$ time kubectl --kubeconfig ./kubeconfig-cp3 get --raw '/api/v1/namespaces?resourceVersion=0'
Error from server (TooManyRequests): storage is (re)initializing

real	0m10.036s
$ time kubectl --kubeconfig ./kubeconfig-cp3 get --raw '/api/v1/namespaces?resourceVersion=0&limit=1'
Error from server: etcdserver: request timed out

real	0m12.960s
$ time kubectl --kubeconfig ./kubeconfig-cp3 -n notes-lab create configmap during-quorum-loss --from-literal=a=b
error: failed to create configmap: Internal error occurred: resource quota evaluation timed out

real	0m10.026s
  • 普通的 get 是要求最新数据的读，API Server 去 etcd 做线性一致读，etcd 没有 leader，等到超时。
  • resourceVersion=0 本来允许 API Server 直接从自己的 watch cache 返回（可能是旧数据），但两次都失败了：第一次等了 10 秒才返回 429 storage is (re)initializing；第二次在 15:31:43 加了 limit=1，等了 12.96 秒，报的是 etcdserver: request timed out。按 v1.31 源码可以给出一个推测的解释：ResilientWatchCacheInitialization 在 v1.31 是 Beta、默认开启，watch cache 未就绪时 cacher.go 的 GetList 立即返回 429，并带 Retry-After: 1；client-go 遇到这种响应默认最多重试 10 次（request.go 里 maxRetries: 10），每次等 1 秒，合起来正好约 10 秒，最后把 429 交给用户。第二次带了 limit 且没有 label/field selector，符合 shouldDelegateListOnNotReadyCache 的条件，缓存未就绪时请求被直接委派给 etcd，于是和普通读一样超时。普通 get 用了 7.4 秒，也和 etcd 的请求超时 ReqTimeout = 5s + 2×选举超时（默认 1s）= 7s 吻合。要验证可以在同样的状态下加 -v=6 重跑，看 kubectl 是否打印出 10 次重试。不管机制如何，结论是一样的：失去多数派时，别指望「至少还能从缓存读」。
  • 写请求更早就卡住了：创建 ConfigMap 先要经过 ResourceQuota 准入检查，这一步要读 etcd，10 秒后超时，报的是 resource quota evaluation timed out，请求根本没走到真正写入那一步。看到这条报错别去查配额配置，先查 etcd。

/readyz 和 /livez 都把 etcd 标成失败：

kubectl --kubeconfig ./kubeconfig-cp3 get --raw='/readyz?verbose'
kubectl --kubeconfig ./kubeconfig-cp3 get --raw='/livez?verbose'
Error from server (InternalError): an error on the server ("[+]ping ok\n[+]log ok\n[-]etcd failed: reason withheld\n[-]etcd-readiness failed: reason withheld\n[+]informer-sync ok\n ... \n[-]shutdown failed: reason withheld\nreadyz check failed") has prevented the request from succeeding
Error from server (InternalError): an error on the server ("[+]ping ok\n[+]log ok\n[-]etcd failed: reason withheld\n ... \nlivez check failed") has prevented the request from succeeding

后面几件事是连锁反应：

  • control-plane3 上的 controller-manager 和 scheduler 续约失败，在 07:30:28 左右先后退出，与失去多数派后约 10 秒的 renew deadline 吻合（crictl ps -a 找到已退出的那个 controller-manager 容器 ID，再看它的日志）：
docker exec ha-lab-control-plane3 crictl ps -a --name kube-controller-manager
docker exec ha-lab-control-plane3 crictl logs <已退出的容器 ID> 2>&1 | tail -4
I1013 07:30:28.661661       1 leaderelection.go:297] failed to renew lease kube-system/kube-controller-manager: timed out waiting for the condition
E1013 07:30:28.661710       1 controllermanager.go:340] "leaderelection lost"
  • control-plane3 的 API Server 容器在 07:31:56 正常退出（exitCode: 0）后被重启。上面那次 /readyz 是 07:31:38 查的，里面已经有 [-]shutdown failed，说明当时 API Server 已经收到终止信号、进入关闭流程，比退出早了 18 秒。静态 Pod 里的存活探针是每 10 秒检查一次 /livez、连续失败 8 次判定失败，/livez 又包含 etcd 检查；这些都支持「kubelet 因存活探针失败重启了它」，但 kubelet 日志里没有找到直接记录，仍是推测。失去多数派时重启 API Server 毫无帮助，只会多出一段启动时间。

从第一次请求失败（15:30:18）开始，这段时间里经 LB 的每一次读写都失败。

恢复：先回来一台就够，但还有余震

15:32:38.9 启动 control-plane2。15:33:16.3 检查时两个成员已恢复多数派，选出了 term 4 的 leader；15:33:19.4 经 LB 的读写恢复。整个不可用时间约 3 分钟。

15:33:08.3 | R: error: client rate limiter Wait returned an error: context deadline exceeded - error from a previous attempt: EOF | W: error: failed to create configmap: Post "https://127.0.0.1:<lb-port>/api/v1/namespaces/notes-lab/configmaps?fieldManage | L: 
15:33:19.4 | R: namespace/kube-system | W: configmap/probe-104 | L: control-plane3 control-plane3

15:33:30.8 再启动 control-plane，15:34:39 检查时三个成员已全部健康，haproxy 在 07:35:00 把三个后端全部加回。中间有一段余震：control-plane3 的 API Server 在这期间重启了 3 次。第一次是 07:31:56 正常退出后被拉起（07:31:59 启动的那个实例何时退出没有记录）；07:33:09.76 启动的已经是第二次重启后的实例，它在 07:34:10.57 以退出码 255 崩溃：

F1013 07:34:10.569367       1 hooks.go:210] PostStartHook "start-service-ip-repair-controllers" failed: unable to perform initial IP and Port allocation check

在 v1.31 的 storage_core.go 里，这个 PostStartHook 要等 ClusterIP 和 NodePort 两个修复循环各完成第一轮，最多等 time.After(time.Minute)，超时就返回这条错误，整个 API Server 随之退出。这个实例从启动到崩溃约 60 秒，撞上的正是这个 1 分钟上限。可多数派在它启动后最迟约 7 秒就已经恢复：15:33:16.3 检查时已有 leader，这个实例自己 07:33:15 的日志里也已经出现 etcdserver: leader changed：

E1013 07:33:15.256918       1 reflector.go:158] "Unhandled Error" err="k8s.io/client-go/informers/factory.go:160: Failed to watch *v1.RoleBinding: failed to list *v1.RoleBinding: etcdserver: leader changed" logger="UnhandledError"

修复循环为什么在剩下 50 多秒里还没完成，根因没有查明。同一时段经 LB 的写请求又失败了一次：

15:34:19.1 | R: namespace/kube-system | W: error: failed to create configmap: the server was unable to return a response in the time allotted, but may still be processing the request (post configmaps) | L:

Lease 在恢复期间也换了好几手：按 LeaderElection 事件，control-plane3 在 07:33:36 先拿到了两个 Lease；最后两个都落到 control-plane2，acquireTime 分别是 controller-manager 07:34:03.4、scheduler 07:34:29.6。其中 controller-manager 的易主早于 07:34:10 那次 API Server 崩溃，这几次易主的具体原因没有逐个查。恢复后各组件的重启次数：

control-plane 和 control-plane2 的计数主要来自整个节点容器的 docker stop / docker start（control-plane2 停过两次，control-plane 一次），说明不了问题。全程没停过的 control-plane3 才有参考价值：它的 etcd 重启 0 次，API Server 3 次，controller-manager 和 scheduler 各 2 次，重启的都是依赖 etcd 的组件。多数派恢复之后，这些组件又花了一分多钟才逐个恢复正常。重启对多数派损失本身没有任何修复作用，排查时要先看 etcd，再看其余组件。恢复时间里有多少是这台机器的慢盘造成的没有测，推测在 SSD 上会短一些。

kubeconfig 直连某一台：高可用白做

最后验证一个容易被忽视的问题：有人为了「绕开 LB 少一跳」，把 kubeconfig 的 server 写成某台控制平面的地址。三台都恢复后，用同样的 sed 方法生成一个指向 control-plane2 宿主机端口的 kubeconfig-cp2，然后 docker stop ha-lab-control-plane2：

$ time kubectl --kubeconfig ./kubeconfig-cp2 get ns kube-system
The connection to the server 127.0.0.1:<cp2-port> was refused - did you specify the right host or port?

real	0m0.021s
$ time kubectl --kubeconfig ./kubeconfig get ns kube-system
NAME          STATUS   AGE
kube-system   Active   12m

real	0m0.191s

集群好好的，走 LB 的请求 0.19 秒就返回了，但直连的客户端立即失败。CI 流水线、外部系统、各种 Operator 的 kubeconfig 都要用 controlPlaneEndpoint，否则高可用只对一部分客户端生效。节点上的 kubelet.conf 指向 LB 也是这个原因。

建设前检查

  1. 先定 controlPlaneEndpoint（推荐 DNS 名加端口），在 kubeadm init 时就写进去；所有客户端用到的名字和 IP 都要进 API Server 证书的 SAN。LB 本身也要高可用，否则它就是新的单点。
  2. LB 用 TCP 转发，不要终结 TLS。本实验中 kind 的 haproxy 用 HTTP /healthz 做检查，etcd 失去多数派时所有后端都被摘掉，客户端只看到 EOF，看不到 etcd 的错误；排查时要直接连某台 API Server 才能看到真正的原因。换成别的 LB，表现取决于它的健康检查方式（kubeadm 文档写的是对 6443 端口做 TCP 检查），以及所有后端都不健康时它是照样转发（fail-open）还是拒绝连接（fail-close）。
  3. 堆叠式至少 3 个控制平面，外部 etcd 至少 3 台控制平面加 3 台 etcd；etcd 成员数用奇数。
  4. 部署后真的演练一次：停一台，确认读写不断、Lease 在十几秒内迁移；再看 etcdctl endpoint status 里 leader 和 raft index 是否一致。
  5. 准备好 etcd 快照和恢复流程，失去多数派且成员回不来时只能靠它。

已有的单控制平面集群，如果初始化时没有设置 controlPlaneEndpoint，不能靠多 kubeadm join 几台控制平面就变成高可用：入口、证书 SAN 和 etcd 拓扑都要在初始化时考虑进去。升级多控制平面集群的顺序见 kubeadm 升级。
