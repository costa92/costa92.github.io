父 Chart 如何管理子 Chart

编写 Helm Chart写了一个 Nginx Chart web-chart。这一篇把它当成子 Chart，再配一个只渲染 ConfigMap 的小 Chart cache，由父 Chart shop 在 Chart.yaml 里声明依赖。这种只负责把几个子 Chart 组合起来的父 Chart，通常叫伞形 Chart（umbrella chart）。

下文的输出来自 Helm v4.3.0，大部分实验只在本地渲染；最后一节装进一个三节点 kind 集群（Kubernetes v1.31.0），放在单独的 notes-lab namespace 里（kubectl create namespace notes-lab），节点名简化为 worker、worker2，Pod 和 Service 的 IP 用占位符代替。Release 的安装、升级和 values 优先级见 Helm 入门，这里不再重复。

目录和依赖声明

lab/
├── web-chart/          # 上一篇的 Chart，原样复制
├── cache/
│   ├── Chart.yaml
│   ├── values.yaml
│   └── templates/configmap.yaml
└── shop/
    ├── Chart.yaml
    ├── values.yaml
    └── templates/

cache/Chart.yaml 的 version 一开始是 0.1.0，模板只有一个 ConfigMap：

apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-{{ .Chart.Name }}
data:
  maxMemory: {{ .Values.maxMemory | quote }}

shop/Chart.yaml 的第一版：

apiVersion: v2
name: shop
description: 伞形 Chart：web + cache
type: application
version: 0.1.0
dependencies:
  - name: web-chart
    version: "~0.1.0"
    repository: file://../web-chart
  - name: cache
    version: "~0.1.0"
    repository: file://../cache

repository: file:// 后面是相对于父 Chart 目录的路径。name 必须和子 Chart 自己 Chart.yaml 里的 name 一致。

dependency list、update、build

刚写完依赖时，charts/ 目录还不存在：

$ helm dependency list ./shop
NAME     	VERSION	REPOSITORY         	STATUS 
web-chart	~0.1.0 	file://../web-chart	missing
cache    	~0.1.0 	file://../cache    	missing

$ helm template demo ./shop
Error: an error occurred while checking for chart dependencies. You may need to run 'helm dependency build' to fetch missing dependencies: found in Chart.yaml, but missing in charts/ directory: web-chart, cache

helm install 报同样的错误，只是前面多了 INSTALLATION FAILED:。Helm 渲染时只看 charts/ 目录，不会自己顺着 repository 去取。

$ helm dependency update ./shop
Saving 2 charts
Deleting outdated charts
$ ls -l shop/charts
total 8
-rw-rw-r-- 1 user user  425 Oct 12 16:43 cache-0.1.0.tgz
-rw-rw-r-- 1 user user 1824 Oct 12 16:43 web-chart-0.1.0.tgz
$ cat shop/Chart.lock
dependencies:
- name: web-chart
  repository: file://../web-chart
  version: 0.1.0
- name: cache
  repository: file://../cache
  version: 0.1.0
digest: sha256:1fd8264c94b31c463807a37421e8211f82b1c430a8559b93eff5069cccc50f51
generated: "2026-10-12T16:43:37.351040054+08:00"
$ helm dependency list ./shop
NAME     	VERSION	REPOSITORY         	STATUS
web-chart	~0.1.0 	file://../web-chart	ok    
cache    	~0.1.0 	file://../cache    	ok

update 做了两件事：按 version 约束解析出具体版本，写进 Chart.lock；再把子 Chart 打成 .tgz 放进 charts/。即使是 file:// 依赖，charts/ 里放的也是打包后的副本，而不是指向源目录的链接。渲染结果里子 Chart 的模板路径是 shop/charts/<子 Chart>/templates/...：

$ helm template demo ./shop | grep -E "^# Source|^kind|^  name:"
# Source: shop/charts/cache/templates/configmap.yaml
kind: ConfigMap
  name: demo-cache
# Source: shop/charts/web-chart/templates/service.yaml
kind: Service
  name: demo-web-chart
# Source: shop/charts/web-chart/templates/deployment.yaml
kind: Deployment
  name: demo-web-chart

build 则是「按 Chart.lock 重建 charts/」，不重新解析版本。两者的差别在后面几节会一一看到。

Chart.lock 锁住了什么

锁的是版本号，不是内容

把 cache/values.yaml 里的 maxMemory: 64mb 改成 128mb，子 Chart 的 version 不变，然后跑 build：

$ sha256sum shop/charts/*.tgz; grep digest shop/Chart.lock
7ba94a56e1135e51860857136417a534a343173fbc2b303bf6f1346acddb9c85  shop/charts/cache-0.1.0.tgz
f8ea425dbdea21b69c41843192272727015faa74137fee9257c6c9914ca27c57  shop/charts/web-chart-0.1.0.tgz
digest: sha256:1fd8264c94b31c463807a37421e8211f82b1c430a8559b93eff5069cccc50f51
$ helm dependency build ./shop
Saving 2 charts
Deleting outdated charts
$ sha256sum shop/charts/*.tgz; grep -E "digest|generated" shop/Chart.lock
6535875b6e127fb4d2d9db8614d3a09a75248d619fca4eae780fa2231ce21dea  shop/charts/cache-0.1.0.tgz
f8ea425dbdea21b69c41843192272727015faa74137fee9257c6c9914ca27c57  shop/charts/web-chart-0.1.0.tgz
digest: sha256:1fd8264c94b31c463807a37421e8211f82b1c430a8559b93eff5069cccc50f51
generated: "2026-10-12T16:43:37.351040054+08:00"
$ helm template demo ./shop --show-only charts/cache/templates/configmap.yaml
...
data:
  maxMemory: "128mb"

build 从源目录重新打包，cache 的 tgz 变了，渲染出 128mb；Chart.lock 一个字都没变。没改过的 web-chart 重新打出来的 tgz 哈希和之前完全相同。锁文件里只有名字、仓库和版本号，没有任何子 Chart 内容的校验和，远程仓库的依赖也一样：同一个版本号在仓库里被重新发布成别的内容，锁文件同样察觉不到。file:// 只是最容易踩到的情形，同一份 Chart.lock 在两个人手上可以打出内容不同的包，取决于各自的 ../cache 目录是什么状态。想让锁文件真正起作用，子 Chart 每次改动都要升 version。

子 Chart 升了版本，约束没跟上

把 cache 的 version 升到 0.2.0，父 Chart 的约束还是 ~0.1.0：

$ helm dependency list ./shop
NAME     	VERSION	REPOSITORY         	STATUS
web-chart	~0.1.0 	file://../web-chart	ok    
cache    	~0.1.0 	file://../cache    	ok    

$ helm dependency build ./shop
Saving 2 charts
Save error occurred:  can't get a valid version for dependency cache
Error: can't get a valid version for dependency cache
$ helm dependency update ./shop
Error: can't get a valid version for 1 subchart(s): "cache" (repository "file://../cache", version "~0.1.0"). Make sure a matching chart version exists in the repo, or change the version constraint in Chart.yaml
$ ls shop/charts
cache-0.1.0.tgz
web-chart-0.1.0.tgz

list 只比较 charts/ 里的包和约束，所以仍然是 ok。build、update 都失败（build 退出码为 1），charts/ 里留着旧的 cache-0.1.0.tgz。file:// 目录里只有一个版本，约束对不上就没有别的候选。

改了 Chart.yaml，没跑 update

再把父 Chart 中 cache 的约束改成 ~0.2.0，不跑 update，Chart.lock 还是旧的：

$ helm dependency list ./shop
NAME     	VERSION	REPOSITORY         	STATUS       
web-chart	~0.1.0 	file://../web-chart	ok           
cache    	~0.2.0 	file://../cache    	wrong version

$ helm template demo ./shop --show-only charts/cache/templates/configmap.yaml
---
# Source: shop/charts/cache/templates/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: demo-cache
data:
  maxMemory: "128mb"

$ helm lint ./shop
==> Linting ./shop
[INFO] Chart.yaml: icon is recommended

1 chart(s) linted, 0 chart(s) failed
$ helm install demo ./shop -n notes-lab --dry-run=client | head -8
NAME: demo
LAST DEPLOYED: Mon Oct 12 16:44:10 2026
NAMESPACE: notes-lab
STATUS: pending-install
REVISION: 1
DESCRIPTION: Dry run complete
TEST SUITE: None
HOOKS:

list 标出了 wrong version，但 template、lint、install --dry-run 全部照常，用的是 charts/ 里那份版本不符的 0.1.0。渲染和安装只检查 charts/ 里「有没有」这个子 Chart，不检查版本是否满足约束。只有 build 会拒绝：

$ helm dependency build ./shop
Error: the lock file (Chart.lock) is out of sync with the dependencies file (Chart.yaml). Please update the dependencies with 'helm dependency update'

update 之后锁文件和 charts/ 才一起换成 0.2.0，digest 也变了：

$ helm dependency update ./shop
Saving 2 charts
Deleting outdated charts
$ ls shop/charts; cat shop/Chart.lock
cache-0.2.0.tgz
web-chart-0.1.0.tgz
dependencies:
- name: web-chart
  repository: file://../web-chart
  version: 0.1.0
- name: cache
  repository: file://../cache
  version: 0.2.0
digest: sha256:613cdee3e121d521d1062ef584c3d8a94d4d966347c2e9f04c58d0b7cfc5f59a
generated: "2026-10-12T16:44:10.595324158+08:00"

digest 用来判断锁文件是否过期。Helm 源码里它由 resolver.HashReq 计算：把 Chart.yaml 里依赖的全部字段和锁文件里的依赖列表一起序列化后取 sha256。所以不只是版本约束，依赖声明里任何一个字段变了都会让锁文件过期。在锁文件已同步（build 正常）的 shop 上，用一个小脚本每次只改 Chart.yaml 的一个字段，跑 build，再还原并确认 build 恢复正常：

echo "baseline: $(helm dependency build ./shop 2>&1 | tail -1)"
try(){ echo "--- $1"; sed -i "$2" shop/Chart.yaml; diff shop-Chart.yaml.orig shop/Chart.yaml | grep '^>'; helm dependency build ./shop 2>&1 | tail -1; cp shop-Chart.yaml.orig shop/Chart.yaml; echo "restore: $(helm dependency build ./shop 2>&1 | tail -1)"; }
try repository 's#repository: file://../cache#repository: file://../cache/#'
try condition 's/condition: cache.enabled/condition: cache.on/'
try tags 's/tags: \[backend\]/tags: [backend, db]/'
try alias 's/alias: admin/alias: admin2/'
try import-values 's/parent: imported/parent: imported2/'
baseline: Deleting outdated charts
--- repository
>     repository: file://../cache/
Error: the lock file (Chart.lock) is out of sync with the dependencies file (Chart.yaml). Please update the dependencies with 'helm dependency update'
restore: Deleting outdated charts
--- condition
>     condition: cache.on
Error: the lock file (Chart.lock) is out of sync with the dependencies file (Chart.yaml). Please update the dependencies with 'helm dependency update'
restore: Deleting outdated charts
--- tags
>     tags: [backend, db]
Error: the lock file (Chart.lock) is out of sync with the dependencies file (Chart.yaml). Please update the dependencies with 'helm dependency update'
restore: Deleting outdated charts
--- alias
>     alias: admin2
Error: the lock file (Chart.lock) is out of sync with the dependencies file (Chart.yaml). Please update the dependencies with 'helm dependency update'
restore: Deleting outdated charts
--- import-values
>         parent: imported2
Error: the lock file (Chart.lock) is out of sync with the dependencies file (Chart.yaml). Please update the dependencies with 'helm dependency update'
restore: Deleting outdated charts

（这里用的是后文加了 alias、condition、tags、import-values 的 shop；Deleting outdated charts 是 build 成功时的最后一行。）repository 末尾多一个 /、只改 condition、tags、alias 或 import-values，都不影响解析出的版本，但锁文件一律过期，要重新 update。另一个方向，手工改锁文件里的版本号、不动 Chart.yaml，build 同样报 out of sync（见后文远程仓库一节）。另外，update 解析结果不变时不会重写锁文件，连跑两次 generated 时间都没动，所以锁文件出现在 diff 里就说明解析结果真的变了。

charts/ 里的其他东西

charts/ 目录里放解包后的目录也可以：

$ ls -F shop/charts
cache/
web-chart-0.1.0.tgz
$ helm dependency list ./shop
NAME     	VERSION	REPOSITORY         	STATUS  
web-chart	~0.1.0 	file://../web-chart	ok      
cache    	~0.2.0 	file://../cache    	unpacked

渲染结果与打包时相同。更需要留意的是没在 Chart.yaml 里声明的 Chart：复制一份 cache 改名为 extra 放进 charts/：

$ helm dependency list ./shop
NAME     	VERSION	REPOSITORY         	STATUS  
web-chart	~0.1.0 	file://../web-chart	ok      
cache    	~0.2.0 	file://../cache    	unpacked

WARNING: "shop/charts/extra" is not in Chart.yaml.
$ helm template demo ./shop | grep -E "^# Source|  name:"
# Source: shop/charts/cache/templates/configmap.yaml
  name: demo-cache
# Source: shop/charts/extra/templates/configmap.yaml
  name: demo-extra
# Source: shop/charts/web-chart/templates/service.yaml
  name: demo-web-chart
# Source: shop/charts/web-chart/templates/deployment.yaml
  name: demo-web-chart

只有 list 给了一条警告，template 一声不吭地把 extra 也渲染了。charts/ 下的东西都会被当成子 Chart，而 update/build 只清理它认识的旧包（Deleting outdated charts），所以本地残留的目录可能随着 helm package 一起进了发布包。.gitignore 掉 charts/*.tgz 只防得住打包文件，防不住这种残留目录；可靠的做法是 CI 从干净的克隆重新 build 再打包。

版本范围

file:// 只有一个版本，看不出范围怎么选。在本机起一个临时的 Chart 仓库，把 cache 打成五个版本（每个版本的 maxMemory 改成 v<版本号>，方便事后认出是哪个包）：

mkdir -p repo pkgsrc
for v in 0.1.0 0.1.5 0.2.0 0.3.0-rc.1 1.0.0; do
  rm -rf pkgsrc/cache; cp -r cache pkgsrc/cache
  sed -i "s/^version: .*/version: $v/" pkgsrc/cache/Chart.yaml
  sed -i "s/^maxMemory: .*/maxMemory: v$v/" pkgsrc/cache/values.yaml
  helm package pkgsrc/cache -d repo >/dev/null
done
helm repo index repo --url http://127.0.0.1:8879

# 另开一个终端，在 repo 目录里起 HTTP 服务
cd repo && python3 -m http.server 8879 --bind 127.0.0.1

再写一个只依赖 cache 的 Chart ranges（values.yaml 为 {}），ranges/Chart.yaml：

apiVersion: v2
name: ranges
version: 0.1.0
dependencies:
  - name: cache
    version: "~0.1.0"
    repository: http://127.0.0.1:8879

逐个修改约束并 update，Chart.lock 里解析出的版本：

约束解析结果
~0.1.00.1.5
^0.1.00.1.5
0.1.x0.1.5
^0.20.2.0
>=0.2.01.0.0
>=0.2.0 <1.0.00.2.0
>=0.3.0-0 <1.0.00.3.0-rc.1
*1.0.0
~1.2.0报错

几个容易想错的地方：

  • ^0.1.0 没有选 0.2.0。Helm 文档说 ^1.2.3 等价于 >=1.2.3 <2.0.0，但主版本为 0 时，^ 只允许补丁版本变化，效果和 ~ 一样。
  • >=0.2.0 <1.0.0 跳过了 0.3.0-rc.1，预发布版本默认不参与匹配；约束里自己带上预发布标记（>=0.3.0-0）才会被选中。
  • >=0.2.0 和 * 会一路跟到 1.0.0，跨主版本也照升不误。
$ helm dependency update ./ranges
Error: can't get a valid version for 1 subchart(s): "cache" (repository "http://127.0.0.1:8879", version "~1.2.0"). Make sure a matching chart version exists in the repo, or change the version constraint in Chart.yaml

仓库发布了新版本：build 不动，update 跟进

约束 ~0.1.0，锁在 0.1.5。这时用同样的方法再打一个 0.1.6 放进 repo/、重新 helm repo index，删掉 charts/ 后先跑 build：

$ rm -rf ranges/charts; helm dependency build ./ranges; ls ranges/charts
Error: no repository definition for http://127.0.0.1:8879. Please add the missing repos via 'helm repo add'
ls: cannot access 'ranges/charts': No such file or directory

这是没想到的一点：同一个直接写 URL 的仓库，update 能用（输出里是 Getting updates for unmanaged Helm repositories...），build 却要求先 helm repo add。加上之后：

$ helm repo add labrepo http://127.0.0.1:8879
"labrepo" has been added to your repositories
$ rm -rf ranges/charts; helm dependency build ./ranges; ls ranges/charts; tar xzOf ranges/charts/cache-0.1.5.tgz cache/values.yaml
...
Saving 1 charts
Downloading cache from repo http://127.0.0.1:8879
Deleting outdated charts
cache-0.1.5.tgz
maxMemory: v0.1.5
$ helm dependency update ./ranges; ls ranges/charts; grep -A3 "^dependencies" ranges/Chart.lock
...
Saving 1 charts
Downloading cache from repo http://127.0.0.1:8879
Deleting outdated charts
cache-0.1.6.tgz
dependencies:
- name: cache
  repository: http://127.0.0.1:8879
  version: 0.1.6

build 严格按锁文件取回 0.1.5，update 在约束范围内取了最新的 0.1.6 并改写锁文件。想退回 0.1.5，手工改锁文件是不行的：

$ sed -i "s/  version: 0.1.6/  version: 0.1.5/" ranges/Chart.lock; grep -E "version|digest" ranges/Chart.lock
  version: 0.1.5
digest: sha256:5421517fd22e032b8886cfafa256b8a5f1ae6a9835b92d6f5c7303eaaff9d4b9
$ helm dependency build ./ranges; ls ranges/charts
Error: the lock file (Chart.lock) is out of sync with the dependencies file (Chart.yaml). Please update the dependencies with 'helm dependency update'
cache-0.1.6.tgz

要固定在某个版本，就把 Chart.yaml 里的约束写成那个版本再 update。CI 里用 build，升级依赖时在本地跑 update 并审阅 Chart.lock 的 diff，就是这个分工。

condition 和 tags

把 shop 改成三个依赖：web-chart 用 alias 装两份（web 和 admin，下一节细说），都打上 frontend 标签；cache 打上 backend 标签。每个依赖同时有 condition：

dependencies:
  - name: web-chart
    alias: web
    version: "~0.1.0"
    repository: file://../web-chart
    condition: web.enabled
    tags: [frontend]
  - name: web-chart
    alias: admin
    version: "~0.1.0"
    repository: file://../web-chart
    condition: admin.enabled
    tags: [frontend]
  - name: cache
    version: "~0.2.0"
    repository: file://../cache
    condition: cache.enabled
    tags: [backend]

shop/values.yaml：

tags:
  frontend: true
  backend: true

web: {}

admin:
  enabled: false

cache: {}

注意 web.enabled 和 cache.enabled 在 values 里不存在，只有 admin.enabled: false。用不同参数渲染，看哪些子 Chart 出现在结果里：

参数渲染出的子 Chart
（默认）cache web
--set tags.frontend=falsecache
--set tags.frontend=false --set web.enabled=truecache web
--set admin.enabled=trueadmin cache web
--set tags.backend=falseweb
--set tags.backend=false --set cache.enabled=truecache web
--set cache.enabled=false --set tags.backend=trueweb

规则可以从表里读出来：condition 指向的值存在时，它说了算，tags 被忽略（第 3、6、7 行）；condition 的值不存在时才看 tags（第 2、5 行）。admin 默认不出现，是因为 admin.enabled: false 盖过了 frontend: true。这和 Helm 文档「Conditions (when set in values) always override tags」一致。

一个实用的推论：想让 tags 能整体开关一组子 Chart，就不要给 xxx.enabled 写默认值，否则 tags 永远不起作用。这既包括父 Chart 的 values.yaml，也包括子 Chart 自己的 values.yaml：condition 是在合并子 Chart 默认值之后求值的。在 cache 的 values.yaml 里加一行 enabled: true 再试：

$ helm template demo ./shop --set tags.backend=false | grep -E "^# Source" | cut -d/ -f3 | sort -u | tr "\n" " "; echo
cache parent-view.yaml web

tags.backend=false 没能关掉 cache。（这次是在实验目录的副本上做的，schema 里也放行了 enabled。）

condition 的值必须是布尔

$ helm template demo ./shop --set web.enabled=yes ...
level=WARN msg="returned non-bool value" path=web.enabled chart=web
cache web
$ helm template demo ./shop --set web.enabled=yes --set tags.frontend=false ...
level=WARN msg="returned non-bool value" path=web.enabled chart=web
cache
$ helm template demo ./shop --set-string web.enabled=false ...
level=WARN msg="returned non-bool value" path=web.enabled chart=web
cache web

（命令后面接的是同一段 grep/cut 管道，省略了。）值不是布尔时，Helm 只打一条警告，然后当作 condition 没设置，转去看 tags。最后一行最容易出事：字符串 "false" 没有关掉 web。values 文件里写成 enabled: "false"（带引号）也一样，同样只有一条警告，web 照样被渲染。

import-values：子 Chart 把值交给父 Chart

方向反过来，子 Chart 也能把值「导出」给父 Chart。cache/values.yaml 加一段 exports：

exports:
  connection:
    cacheHost: cache-from-child
    cachePort: 6379

父 Chart 的依赖里用两种写法导入：

import-values:
  - connection
  - child: exports.connection
    parent: imported

第一次写的时候把 child 指向了一个标量 maxMemory，只得到一条警告，值没有导入：

level=WARN msg="ImportValues missing table from chart" chart=cache error="\"maxMemory\" is not a table"

child 必须指向一个 map。改正后：

$ helm template demo ./shop --show-only templates/parent-view.yaml
...
data:
  valuesKeys: "admin,cache,cacheHost,cachePort,global,imported,tags,web"
  webReplicas: "2"
  webImageRepo: "nginx"
  cacheMaxMemory: "128mb"
  globalEnv: "dev"
  globalRegion: "<unset>"
  cacheHost: "cache-from-child"
  cachePort: "6379"
  imported: "{\"cacheHost\":\"cache-from-child\",\"cachePort\":6379}"
  childHelperInParent: "app.kubernetes.io/name: shop;app.kubernetes.io/instance: demo"

（最后一行来自后文「同名模板」一节加的调用，这里先不管。）

简写 - connection 会到子 Chart 的 exports 下找 connection，把里面的键直接铺到父 Chart 的顶层；child/parent 写法则把子 Chart 任意路径下的 map 放到父 Chart 指定的键下。

和父 Chart 自己的值冲突时，父 Chart 赢。Helm 文档 import-values 一节的 myimports 示例写的是相反的结果：父 Chart 的 myint: 0、mybool: false 被子 Chart 的 999、true 覆盖。照抄那个示例（父 Chart values.yaml 里 myimports 有 myint: 0、mybool: false、mystring，子 Chart 的 default.data 是 myint: 999、mybool: true），用一个 ConfigMap 打印 .Values.myimports：

$ helm dependency update ./docex/parent && helm template x ./docex/parent
...
data:
  myimports: "{\"mybool\":false,\"myint\":0,\"mystring\":\"helm rocks!\"}"

Helm 4.3 上父 Chart 的值保留了下来，与文档示例不符，这里以实测为准。回到 shop：shop/values.yaml 顶层加一行 cacheHost: from-parent-values：

$ helm template demo ./shop --show-only templates/parent-view.yaml | grep cacheHost
...
  cacheHost: "from-parent-values"
$ helm template demo ./shop --set cacheHost=from-set --show-only templates/parent-view.yaml | grep cacheHost
...
  cacheHost: "from-set"

这一节最意外的结果是：用户去覆盖子 Chart 的导出值，导入的结果并不跟着变。删掉上面那行之后：

$ helm template demo ./shop --set cache.exports.connection.cacheHost=from-set-child --show-only templates/parent-view.yaml | grep -E "^  (cacheHost|imported):"
  cacheHost: "cache-from-child"
  imported: "{\"cacheHost\":\"cache-from-child\",\"cachePort\":6379}"
$ cat override-exports.yaml; helm template demo ./shop -f override-exports.yaml --show-only templates/parent-view.yaml | grep -E "^  (cacheHost|imported):"
cache:
  exports:
    connection:
      cacheHost: from-file-child
  cacheHost: "cache-from-child"
  imported: "{\"cacheHost\":\"cache-from-child\",\"cachePort\":6379}"

--set 和 -f 都一样：导入用的是子 Chart 包里自带的默认值。这次实测的结论是，import-values 适合导出子 Chart 的固定信息（端口、约定的名字）；会随部署变化的值，直接在父 Chart 里定义，再传给子 Chart。

父子 schema 怎么配合

子 Chart 的 schema 校验父 Chart 传下去的值

web-chart 带着上一篇的 values.schema.json（image.tag 必须是字符串，replicaCount 最大 5）。通过父 Chart 传入错误的值：

$ cat bad-child.yaml; helm template demo ./shop -f bad-child.yaml
web:
  image:
    tag: 1.20
admin:
  enabled: true
  replicaCount: 9
Error: values don't meet the specifications of the schema(s) in the following chart(s):
web:
- at '/image/tag': got number, want string
admin:
- at '/replicaCount': maximum: got 9, want 5

同一份 schema 对两个 alias 分别校验，报错按 alias 分组，路径是相对子 Chart 的（/image/tag，而不是 /web/image/tag）。父 Chart 绕不过子 Chart 的限制。但被禁用的子 Chart 不校验：

$ helm template demo ./shop --set admin.enabled=false --set admin.replicaCount=9 | grep -E "^# Source" | cut -d/ -f3 | sort -u | tr "\n" " "; echo
cache parent-view.yaml web

父 schema 顶层 additionalProperties: false

上一篇留了一个没验证的推测：父 Chart 的 schema 在顶层写 "additionalProperties": false，会拒绝子 Chart 的那一段 values。给 shop 加一个只声明 tags 的 schema：

$ cat shop/values.schema.json; helm template demo ./shop
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "tags": { "type": "object" }
  }
}
Error: values don't meet the specifications of the schema(s) in the following chart(s):
shop:
- at '': additional properties 'global', 'cachePort', 'imported', 'cacheHost', 'web', 'admin', 'cache' not allowed

推测成立，而且范围比预想的大：被拒的不只是子 Chart 段（web、admin、cache）和 global，还有 import-values 导入进来的 cacheHost、cachePort、imported。父 Chart 的 schema 校验的是合并、导入之后的完整 values。把这些键都声明进 properties 后渲染通过，拼错的键照样能拦住：

$ helm template demo ./shop --set webb.replicaCount=3
Error: values don't meet the specifications of the schema(s) in the following chart(s):
shop:
- at '': additional properties 'webb' not allowed

template 和 lint 看到的 values 不一样

在父 schema 里给 web 加 "required": ["image"]。image 只在子 Chart 的默认值里，父 Chart 的 values.yaml 没写。helm template 通过了（印证上面「父 schema 看到的是合并后的 values」），helm lint 却失败：

$ helm lint ./shop
==> Linting ./shop
[INFO] Chart.yaml: icon is recommended
[ERROR] values.yaml: - at '/web': missing property 'image'


Error: 1 chart(s) linted, 1 chart(s) failed

报错位置写的是 values.yaml：lint 这一项只拿父 Chart 自己的 values.yaml 对父 schema，不合并子 Chart 的默认值。父 schema 里对子 Chart 段的 required，lint 和真正渲染的结论可能相反；子 Chart 段的约束最好留给子 Chart 自己的 schema。

严格的子 Chart schema 会拒绝 enabled 和 global

反过来，给 cache 写一个顶层 "additionalProperties": false 的 schema，声明 maxMemory、exports、global。单独渲染 cache 通过，放进 shop 也通过，直到有人用 condition 去开它：

$ helm template demo ./shop --set cache.enabled=true
Error: values don't meet the specifications of the schema(s) in the following chart(s):
cache:
- at '': additional properties 'enabled' not allowed

condition 的键 cache.enabled 在父 Chart 的 cache: 段里，于是也进了子 Chart 的 values。再在副本上把 cache 默认值里的 global、父 Chart values.yaml 里的 global 都删掉，schema 里也不声明 global（cache 的 values.yaml 用的是原版，前面 tags 一节加的 enabled: true 不在里面，渲染时也没有传 cache.enabled）：

$ grep -c global rr/shop/values.yaml rr/cache/values.yaml rr/cache/values.schema.json; helm dependency build ./rr/shop >/dev/null; helm template demo ./rr/shop
rr/cache/values.schema.json:0
rr/shop/values.yaml:0
rr/cache/values.yaml:0
Error: values don't meet the specifications of the schema(s) in the following chart(s):
cache:
- at '': additional properties 'global' not allowed
$ helm template t ./rr/cache
...
  valuesKeys: "exports,maxMemory"

（rr/ 是实验目录的副本，两个模板里引用 global 的行也删掉了。）三个文件里都没有 global，作为子 Chart 渲染时它仍然出现在 values 里：Helm 总会给子 Chart 注入 global，哪怕是空的。单独渲染 cache 时就没有这个键。所以一个可能被当作子 Chart 使用的 Chart，顶层禁止额外键时至少要放行 global 和它自己的开关键（常见的 enabled）。

同名模板：父 Chart 悄悄改掉子 Chart 的名字

上一篇说过命名模板是全局的。实测一下：在 shop/templates/_helpers.tpl 里定义一个和子 Chart 同名的模板：

{{- define "web-chart.fullname" -}}
from-parent-{{ .Chart.Name }}
{{- end -}}

父 Chart 的 parent-view.yaml 里顺便调用子 Chart 的 web-chart.selectorLabels：

$ helm template demo ./shop --set admin.enabled=true | grep -E "^# Source|^  name:|childHelperInParent"
# Source: shop/charts/cache/templates/configmap.yaml
  name: demo-cache
# Source: shop/templates/parent-view.yaml
  name: demo-parent-view
  childHelperInParent: "app.kubernetes.io/name: shop;app.kubernetes.io/instance: demo"
# Source: shop/charts/admin/templates/service.yaml
  name: from-parent-admin
# Source: shop/charts/web/templates/service.yaml
  name: from-parent-web
# Source: shop/charts/admin/templates/deployment.yaml
  name: from-parent-admin
# Source: shop/charts/web/templates/deployment.yaml
  name: from-parent-web

父 Chart 的定义覆盖了子 Chart 自己的，子 Chart 渲染出的 Service、Deployment 名全变了；连跑 10 次结果都一样，不是随机的。helm lint 对重名没有任何提示。另一方面，父 Chart 可以直接 include 子 Chart 的命名模板，但用的是调用方的上下文，所以 .Chart.Name 是 shop。

再把父 Chart 的这个定义移走，改放在兄弟子 Chart cache 的 _helpers.tpl 里，5 次渲染 web 的 Service 名都是 from-cache-web。兄弟 Chart 之间也会互相覆盖。顺序来自 Helm 源码 pkg/engine/engine.go 的 sortTemplates：模板按路径层级排序后整体倒序（sort.Reverse(byPathLen)），层级深的先解析，同一层按路径字母序倒序，同名 define 以最后解析的为准。父 Chart 的模板路径最浅，最后解析，所以总是赢；charts/cache 和 charts/web 同层，cache 字母序靠前、解析在后，所以也赢了。结论是命名模板一律带上本 Chart 的名字作前缀，不在别的 Chart 里重复定义。

--dependency-update（install、upgrade、template 都有）只在 charts/ 缺包时才起作用：源码 pkg/cmd/install.go 里，它在 CheckDependencies 失败后才触发，调用的是 Manager.Update()，也就是 helm dependency update 的逻辑。所以 charts/ 齐全时，即使锁文件已经过期，它什么也不做，渲染照旧用 charts/ 里的包；charts/ 缺包时，它按约束重新解析并改写锁文件。实测：把 cache 的约束改成 >=0.2.0 让锁文件过期、删掉 charts/，再跑 helm template --dependency-update，渲染成功，Chart.lock 被改写成新的 digest 和 generated 时间；而锁文件与 Chart.yaml 不一致时，helm dependency build 会报 out of sync 并停下。

所以 CI 里要做两件事：Chart.lock 必须提交进仓库，没有锁文件时 build 也会退回到 update 去解析版本；部署前显式跑 helm dependency build，让过期的锁文件直接失败，而不是靠 --dependency-update。

清理

helm uninstall demo -n notes-lab --wait
kubectl delete namespace notes-lab
helm repo remove labrepo
# 回到起 http.server 的终端按 Ctrl+C 停掉临时仓库

小结

  • update 按约束解析版本、写 Chart.lock；build 只按锁文件重建 charts/。list 能看出 missing、wrong version、unpacked，但 template、lint、install 只检查 charts/ 里有没有，不检查版本对不对。
  • Chart.lock 的 digest 覆盖 Chart.yaml 依赖声明的全部字段（包括 condition、tags）和锁定结果，任何一边变了 build 都会拒绝；但锁文件里没有任何依赖的内容校验和，子 Chart 改了内容不升版本，锁文件察觉不到，file:// 依赖最容易踩到。
  • ^0.x 只允许补丁版本变化；预发布版本要在约束里显式写出才会被选中；build 要求仓库已 helm repo add，update 不要求。
  • condition 的值存在时压过 tags，不存在时才看 tags；非布尔值（包括字符串 "false"）只警告并被忽略。
  • alias 改的是子 Chart 的名字本身：模板路径、.Chart.Name、helm.sh/chart 标签都跟着变。
  • 子 Chart 只看得到自己那段和 global；父 Chart 看得到子 Chart 合并后的默认值。import-values 导入的是子 Chart 包里的默认值，用户覆盖不跟着走。
  • 父 schema 顶层 additionalProperties: false 会拒绝子 Chart 段、global 和导入的键；子 schema 顶层这么写，要放行 global 和 enabled。
  • 同名命名模板会被父 Chart 或兄弟 Chart 静默覆盖，lint 不报。
