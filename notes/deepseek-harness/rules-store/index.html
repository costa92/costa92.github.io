第 23 / 36 节 · 发布规则实战

重启后规则存储打不开，守卫随之消失，2.3 又被部署了一次。起因是跳过校验写进去的一条规则：阈值写成了字符串，本进程里照常拦截。

上一篇的规则引擎把历史放在内存里，引擎一重载就清零。这一篇把规则和历史存下来，并让规则可以修改、回滚，也可以由模型生成。

这次把规则改成数据，和部署历史一起存进 dsh 自带的 storage-domain，修改时追加版本，回滚时改指针，再逐个看存储层没有承诺的地方。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 工具刚返回时，规则读不到这次结果，三次部署都放行；
  • 不 flush 就关宿主，排队的 2 条写入失败；
  • 跳过校验写入的坏规则，重启后让守卫消失；
  • 两个宿主共用 single 布局目录，关掉后规则丢失。

规则改成数据，模型只能填三个字段

第 21 篇的规则是一个 evaluate 函数。函数没法让模型生成，也不好让人逐版本对比。这一篇把规则写成一段数据，用 zod 定义它的形状：

export const ruleSpecSchema = z.object({
  id: z.string().regex(/^[a-z][a-z0-9-]*$/),
  kind: z.literal('failed-in-window'),
  threshold: z.number().int().min(1),
  windowHours: z.number().positive(),
}).strict()

kind 目前只有一种，“时间窗口内失败 N 次”。引擎按 kind 解释数据，模型能填的只有 id、阈值和窗口。

存储用 storage-domain。它在存储后端之上提供声明了 schema 的键值表（打开时按 schema 校验已存记录），读取同步取自内存，写入要先持久化才返回（packages/storage/storage-domain/README.zh.md）。“读取是同步的”正好满足第 21 篇的限制：守卫是同步函数，规则要用的数据必须能同步读到。

一个领域里放三张表：

表键值
revisions<规则 id>_<版本号>规则数据、修改说明、时间，写入后不改不删
active<规则 id>当前生效的版本号；没有这条记录就是停用
events递增序号一次部署的服务、版本、结果、时间

后端用 storage-json，整个领域默认存成一个 JSON 文件。插件在 apply 里打开领域，注册 tools/result 监听器记历史、注册守卫拦部署，再以 ctx.ruleStore 提供修改规则的接口。

宿主是一个 Cordis 根上下文，挂 dsh-system-prompt、dsh-tools 和存储三件套，部署直接调 ctx.tools.execute()（packages/core/tools/src/index.ts:1348），不经过 agent 循环；“重启”是把整个根上下文销毁，再用同一个目录新建一个。

图：守卫同步读内存里的规则和历史，tools/result 把部署结果排进写入链落盘。

重启之后规则还在

先写入第 1 版规则“同一版本 24 小时内失败 2 次就拦”，并让它生效。合成发布平台上 2.3 版本每次都部署失败，连发三次：

== 1. 规则和历史存进 storage-domain，重启后还在 ==
第 1 次 deploy(2.3) -> 执行 failed
第 2 次 deploy(2.3) -> 执行 failed
第 3 次 deploy(2.3) -> 拒绝 [same-version-failed@1] payment-api 2.3 在 24 小时内已失败 2 次
磁盘上：release_rules.json，revisions 1 条，active 1 条，events 2 条
重启后：生效规则 same-version-failed@1，历史 2 条
重启后 deploy(2.3) -> 拒绝 [same-version-failed@1] payment-api 2.3 在 24 小时内已失败 2 次
平台共执行 2 次

第三次被守卫拦下，平台只执行了两次。关掉宿主前先等历史写完，文件里有一个版本、一个生效指针、两条历史。重启后规则和历史都还在，同一个版本仍然被拦。

输出里没有打印的一步：脚本之后又用 v2.3 试了一次，也被拦（脚本断言，未打印）。守卫把版本号前的 v 去掉再比较，记历史用的是平台返回值里规范化后的版本，第 21 篇说的两处不一致这里都处理了。

修改追加版本，回滚只改指针

修改规则时不动原记录，追加第 2 版“放宽到 4 次”，再把生效指针指过去。回滚就是把指针指回第 1 版：

== 2. 修改规则、回滚 ==
改用第 2 版后 deploy(2.3) -> 执行 failed
回滚后：版本 1, 2，生效 same-version-failed@1
回滚后 deploy(2.3) -> 拒绝 [same-version-failed@1] payment-api 2.3 在 24 小时内已失败 3 次

第 2 版生效时，失败 2 次的 2.3 放行了，平台第三次失败。指针指回第 1 版后，同一个版本又被拦下，两个版本都还在表里。

守卫每次调用都直接读 active 和 revisions 两张表，指针一改，下一次调用就按新版本判断，不需要监听变更事件再重建规则。

工具刚返回，结果还读不到

第 1 步能拦下第三次，靠的是一个“排队中”的缓冲。把它关掉（countPending=false）再跑一次，再换成 agent 循环对照：

== 3. 工具刚返回，这次结果还读不到 ==
countPending=false：三次结果 执行/执行/执行，每次返回后规则看到的历史 0/0/0，平台执行 3 次
countPending=true：三次结果 执行/执行/拒绝，每次返回后规则看到的历史 1/2/2，平台执行 2 次
agent 循环 countPending=false，同一条回复连发 3 次，模型请求耗时 200ms：执行/执行/执行
agent 循环 countPending=false，分 3 轮各发 1 次，模型请求耗时 0ms：执行/执行/执行
agent 循环 countPending=false，分 3 轮各发 1 次，模型请求耗时 200ms：执行/执行/拒绝
agent 循环 countPending=true，同一条回复连发 3 次，模型请求耗时 0ms：执行/执行/拒绝

不算排队中的记录时，每次部署返回后规则看到的历史都是 0 条，三次都放行了。

storage-domain 的 put 先等后端落盘，再改内存（packages/storage/storage-domain/src/domain.ts:307-311）。

落盘本身要经过几次文件系统往返：storage-json 写临时文件、fsync、改名、再 fsync 目录（packages/storage/storage-json/src/atomic.ts）。

另一边，tools/result 是 emit 通知（tools/src/index.ts:191），execute() 调完监听器就返回，监听器返回 promise 也不会等（:1674-1682），所以监听器只能把写入排进队列。ctx.tools.execute() 返回时，这次结果还在写，紧接着的下一次调用读到的是旧的内存。

demo 的 record() 在排队前先把记录放进一个内存缓冲，写入完成后再移除；规则计算历史时把缓冲里的也算上。事件键也要在这时同步分配，写入链上的记录还没进内存，按表的 size 算键会重复。

读不到的窗口有多宽，取决于调用有多密。后四行换成真实的 agent 循环和脚本化模型：关掉缓冲时，同一条回复里连发 3 次，三次都放行。工具不声明 isConcurrencySafe 就按 exclusive 一个接一个跑（tools/src/index.ts:1282-1290），调用之间没有模型请求，情况和脚本一样。

分 3 轮发也不一定安全：模型请求瞬间返回时，三次照样全放行；每次请求耗时 200ms，第三次才被拦下。打开缓冲后，同一条回复里的第三次也被拦下，不再依赖调用之间有多少空档。

关宿主时排队的写入会丢

第 1 步关宿主前调了 flush()，等所有历史写完。不等，部署完立刻销毁宿主：

== 4. 关宿主时还在排队的写入 ==
不 flush 直接关：写入失败 2 条，StorageError: unit 'release_rules' is closed
重启后历史 1 条；deploy(2.3) -> 执行 failed
监听器直接返回 rejected promise：deploy(2.4) -> 执行 succeeded；dsh 只记 1 条 warn：tool "deploy_release" (call-18): tools/result observer failed: unit closed

三次部署产生三条历史，只有第一条落了盘，另外两条报 unit 'release_rules' is closed（来自存储单元，不是领域）。重启后历史只有 1 条，2.3 又能部署了。demo 断言了写入失败 2 条、重启后历史 1 条。

**未实测：**按源码，Cordis 卸载时同一层的 disposer 同时启动，领域和后端的关闭同时开始，存储单元立刻标成已关闭、只等正在写的第 1 条，后两条轮到时单元已关。

规则插件要自己负责“关之前写完”。第 4 步最后一行是对照：监听器直接返回 rejected promise，工具结果照常是 执行 succeeded，dsh 只记一条 warn 日志（tools/src/index.ts:1671-1673、:1680），失败到不了工具结果里。

demo 因此把失败的写入收进 writeErrors，关宿主前调用 flush()。

跳过校验的坏规则，重启后让守卫消失

规则变成数据后，模型就可以提出新规则。假设模型给的阈值是字符串 '2'：

== 5. 模型生成的规则不校验就写进去 ==
先校验：propose 被拒 -> threshold: Invalid input: expected number, received string
不校验：写入成功，本进程里三次 -> 执行/执行/拒绝
重启：规则存储没起来 -> invalid-record，revisions/same-version-failed_1 不符合 schema
ctx.ruleStore 存在吗：false；deploy(2.3) -> 执行 failed，平台执行 1 次

propose() 默认先用 zod 校验，这条规则被拒。跳过校验（trustProposals: true），写入照样成功，本进程里规则也照常工作，JavaScript 把 failures >= '2' 当数字比较了。

storage-domain 的 put 不做 schema 校验（storage-domain/src/domain.ts:307-311），所以写入成功；校验只在打开领域时对每条已存记录做一次（packages/storage/storage-domain/src/index.ts:126）。

问题留到了重启。打开领域时这条记录不合 schema，整个 open 报 invalid-record，领域里的所有规则和历史都读不出来。规则插件起不来，ctx.ruleStore 不存在，守卫也没有注册。宿主的其余部分照常运行，2.3 又被部署了一次。

坏记录挪走了，指针还指着它

storage-domain 为这种情况留了一个选项：领域声明 invalidRecords: 'backup-and-skip'，打开时把不合 schema 的记录挪到一边、记一条错误日志，继续打开（storage-domain/src/index.ts:131-138）。它要求后端能单独挪动一条记录。

single 布局没有这个能力（packages/storage/storage-domain/src/spec.ts:64-65，storage-domain/src/index.ts:131），要配 per-record 布局，每条记录一个文件。第 6 步先在 single 布局上声明它试一次，再换 per-record：

== 6. per-record + backup-and-skip：坏记录挪走，其余照常 ==
single + backup-and-skip 重启 -> invalid-record，revisions/same-version-failed_1 不符合 schema
per-record 下写入带 @ 的键 -> per-record key 'same-version-failed@1' is not path-safe
重启成功；revisions 目录：same-version-failed_1.json.bak.<时间>
生效指针还在：same-version-failed@1，历史 1 条
deploy(2.4) -> 拒绝 [same-version-failed@1] 规则版本缺失

第一行是 single 布局：声明了 backup-and-skip 也没有任何提示，重启照旧整个报 invalid-record。

第二行顺带试了一下键：single 布局里什么键都行，per-record 布局把键当成文件名，只接受 [a-zA-Z0-9_-]，后端约定里写明了这一点（packages/storage/storage/src/backend.ts:96-98）。所以 demo 的版本键用 _，不用 @，换布局前要先检查键。

重启后领域正常打开，坏的第 1 版被改名成 .bak.<时间>，但 active 表里的指针还指着它。demo 的守卫遇到“指针指向的版本不存在”时直接拒绝，所以连 2.4 都部署不了。

backup-and-skip 的说明里写的是给“可丢弃的派生数据”用的（storage-domain/src/spec.ts:60-61）。规则不是派生数据：挪走一条规则，引擎要么当它不存在而放行，要么像 demo 这样全部拒绝。无论哪种，都不如在写入前校验。

两个宿主共用目录，single 布局丢了规则

最后一个场景：运维在一个宿主里加规则，agent 在另一个宿主里部署，两个宿主指向同一个存储目录。

== 7. 两个宿主共用一个目录 ==
single：另一个宿主里连发三次 2.3，平台执行 3 次
single：domain/changed 运维宿主收到 revisions+active 2 条，agent 宿主收到 events 3 条
single：两边都关掉再打开：生效规则 []，历史 3 条
per-record：另一个宿主里连发三次 2.3，平台执行 3 次
per-record：domain/changed 运维宿主收到 revisions+active 2 条，agent 宿主收到 events 3 条
per-record：两边都关掉再打开：生效规则 [same-version-failed@1]，历史 3 条

两种布局下，agent 那边的守卫都看不到另一个宿主刚加的规则，三次部署都放行了。领域只在 open 时从磁盘读一次（storage-domain/src/index.ts:119），之后的读取都来自本宿主的内存，不会重新读文件。

domain/changed 事件也帮不上忙：运维宿主只收到自己写的 revisions、active，agent 宿主只收到自己的 events。事件只在发出它的根上下文里分发，同一进程里的两个根上下文彼此都收不到。

关掉再打开后，single 布局下的规则没了：每次写入都把这个单元打开时载入、之后只在本宿主里更新的全部状态序列化成一个文件，再整体替换（packages/storage/storage-json/src/single-unit.ts:140-141）。agent 那边的状态里没有规则，它写第一条历史时就把运维写的规则覆盖了。

atomic.ts 开头的注释写明了这个前提：一个单元文件在每个进程里只有一个写入方，后写覆盖是正确的。demo 的两个宿主在同一进程里各开一个后端，同样违反了这个前提。

per-record 布局每条记录一个文件（packages/storage/storage-json/src/per-record-unit.ts:221），两边写的是不同的文件，规则和历史都留下了。

这对 Agent 意味着什么

规则写成数据后，模型能生成，人也能逐版本对比，但 storage-domain 的写入不校验，坏数据要到下次打开才暴露，而且会让整个领域打不开，所以要在写入前校验。修改时追加版本，旧版本不改不删，回滚只写 active 表里的一条记录，不用恢复数据，也不会在回滚时再写坏一次。

写完才能读到，规则引擎要把正在写的记录也算进去，否则连续的工具调用之间会漏拦；同一条模型回复里的多个部署调用之间没有空档，最容易漏。

关宿主前要等写入完成，否则排队的历史会丢。存储起不来时守卫跟着插件消失，部署会被直接放行。

一个目录只给一个宿主写。本例两个宿主共用目录时，single 布局关掉后规则丢失，per-record 保留了规则，但两边都看不到对方刚写的修改。

本文的验证范围

实测部分是两个文件：规则存储插件 rule-store.ts 和驱动脚本 rules-store-demo.ts。

脚本挂载真实的 dsh-system-prompt、dsh-tools、dsh-storage、dsh-storage-json 和 dsh-storage-domain，部署大多直接调 ctx.tools.execute()。

第 3 步另挂 dsh-llm、dsh-session、dsh-session-projection、dsh-agent、dsh-agent-loop，用脚本化模型跑 agent 循环，模型请求耗时由脚本控制。

发布平台是合成的；“重启”是在同一个进程里销毁 Cordis 根上下文再重建，“两个宿主”也是同一个进程里的两个根上下文，各自挂一套存储插件。数据写在系统临时目录，脚本退出时删除。本机为 Linux，其他平台未验证。

主要结论都有断言：

  • 重启后规则仍拦下 2.3 和 v2.3，平台执行 2 次，历史 2 条；
  • 第 2 版生效时放行、回滚后拒绝，版本 1、2 都在；
  • 不算排队中的记录时三次都放行，算上时第三次被拦；
  • agent 循环里关掉缓冲时，同一条回复连发、模型请求 0ms 的分轮发都全放行，请求 200ms 时第三次被拦；打开缓冲后同一条回复的第三次被拦；
  • 不 flush 直接关宿主写入失败 2 条，重启后历史 1 条；监听器返回 rejected promise 时工具结果照常，只有 1 条 warn；
  • 校验拒绝字符串阈值；不校验时写入成功，重启报 invalid-record，规则存储不存在，部署被执行；
  • single 布局声明 backup-and-skip 重启仍报 invalid-record；per-record 拒绝带 @ 的键；backup-and-skip 下重启成功、坏版本被改名、部署被拒；
  • 两个宿主共用目录时另一边三次都放行，各宿主只收到自己写入的 domain/changed，single 布局关掉后规则丢失、per-record 保留，历史都是 3 条。

另外做了变异检查。以下 7 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • 规则不算排队中的记录；
  • 第 1 步关宿主前不 flush；
  • 去掉回滚；
  • 第 4 步关宿主前先 flush；
  • propose() 忽略 trustProposals，总是校验；
  • per-record 领域去掉 backup-and-skip；
  • 指针指向的版本不存在时放行。

连续 5 次运行，以及 4 个进程并发运行，输出都一致。
