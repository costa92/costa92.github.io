第 7 / 36 节 · Cordis 运行机制

脱敏插件卸下后，查询结果里的 token 以明文 tok_live_9f3a 返回。Cordis 有五种事件分发模式，只有 parallel 会等全部监听器跑完再集中报错。

第 4、5 篇讲完了插件的注册和依赖，插件之间怎么协作还没讲。查询结果要脱敏，冻结窗口要拦截查询，审计要记录每次调用，这些都不该写进查询插件本身。Cordis 的事件系统为此给了五种分发模式。

这次给发布查询挂几个旁路：waterfall 做脱敏，bail 做冻结窗口检查，emit / parallel / serial 做审计和通知，查询插件本身一行不动。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • waterfall 按洋葱序执行，不调 next() 就否决内层；
  • emit 一个监听器抛错，后面的监听器不再执行；
  • parallel 全部跑完，把 2 个失败聚成 AggregateError；
  • 卸下脱敏插件，token 以明文返回。

五种模式，只有 parallel 集中处理异常

DispatchMode 只列了五个值（vendor/cordis/src/events.ts:32），对应 EventsService 上五个方法：

模式监听器返回值异常
emit（同步）丢弃冒泡，后续不执行
parallel（异步）丢弃跑完后聚合成 AggregateError
serial（异步）逐个 await，遇中止值即返回reject，后续不执行
bail（同步）同 serial，但不 await抛出，后续不执行
waterfall（同步）环绕包装，见下文沿调用栈冒泡

表中 serial、bail、waterfall 三行的“异常”列由后文第 8 步实测。

分发方法的返回值：emit 无返回值，parallel 返回 Promise<void>，serial 返回 Promise<首个中止值 | undefined>，bail 返回首个中止值，waterfall 返回最外层监听器的返回值。serial 与 bail 无人中止时返回 undefined（第 9 步实测）。

集中处理错误的只有 parallel（:183）：用 Promise.allSettled 等所有监听器跑完，再把失败项聚成一个 AggregateError 抛出。其余四种不做集中处理，第一个监听器抛错后，后面的监听器都不再执行。

图：同一批监听器换个分发方法，返回值处理、短路行为和异常兜底都不同。

下面各节在同一个发布查询场景里把五种模式逐个跑一遍。脚本仍然只用 vendor Cordis，不启动 dsh，不调模型。数据是合成的，那个 tok_live_9f3a 是假 token，用来演示脱敏。

脚本位于 scratch-plugin/events-demo/events-demo.ts（获取与运行命令见文末“本文的验证范围”）。各节只贴对应步骤的监听器，事件类型声明、调用与断言从略，完整脚本见示例仓库。

waterfall 是洋葱，不是流水线

看名字容易以为是“上一个监听器的返回值传给下一个”，源码（:234）是另一回事：

waterfall(...args: any[]) {
  const cbs = this.dispatch('waterfall', args)
  const inner = args.pop()
  const next = () => {
    const cb = cbs.shift() ?? inner
    return cb(...args)
  }
  args.push(next)
  return next()
}

调用方传进来的最后一个实参是内置行为（实际干活的那段逻辑），它被换成了 next。监听器的签名是 (...args, next)，形态和 Koa 中间件一样：

  • 进入时从外到内，返回时从内到外。想改写结果，代码要写在 next() 之后。
  • 不调用 next() 就直接返回，等于否决：内层监听器和内置行为都不会执行。
  • 监听器返回 undefined，最终结果就是 undefined（return next() 原样返回，第 9 步实测）。这里没有 bail 那种中止判定，也没有“跳过空值用上一个”的兜底。

dsh 的工具调用准入也走 waterfall：tools/pre-execute 的内置行为是 () => Promise.resolve({ kind: 'allow' })（按源码，未实测；packages/core/tools/src/index.ts:1482）。

权限插件挂进这条链，就能在工具执行前拒绝或转人工审批（按源码，未实测）；模型输出流、系统提示词也是这样的 waterfall 扩展点，如 llm/stream（按源码，未实测；packages/llm/llm/src/index.ts:1118）。

docs/cordis-primer.zh.md 的速查表把 waterfall 写成“监听器按注册顺序观察”，容易误读成线性流水线，以同一文档中的“Cordis Waterfall 语义”一节和 vendor/cordis/src/events.ts:234 的实现为准。

图：进入从外到内，返回从内到外；脱敏写在 next() 之后，否决则根本不调 next()。

脱敏在返回时改写，否决直接跳过内层

第 1 步由两个插件各挂一个 release/query 中间件，先注册的 redact 在外层：

const redact = root.plugin({ name: 'redact', apply(ctx: Context) {
  ctx.on('release/query', (_q, next) => {
    log('  redact: enter')
    const records = next()
    log('  redact: exit, rewriting token')
    return records.map(r => ({ ...r, token: 'REDACTED' }))
  })
} })
const trace = root.plugin({ name: 'trace', apply(ctx: Context) {
  ctx.on('release/query', (_q, next) => {
    log('  trace: enter')
    const records = next()
    log(`  trace: exit, ${records.length} record(s)`)
    return records
  })
} })
const inner = () => { log('  inner: read DB'); return DB }
let result = root.waterfall('release/query', query, inner)

输出：

1. waterfall: onion order, redaction happens on the way out
  redact: enter
  trace: enter
  inner: read DB
  trace: exit, 1 record(s)
  redact: exit, rewriting token
  result=[{"id":"demo-001","version":"1.4.0","token":"REDACTED"}]

进入顺序是 redact → trace → 内置行为，返回顺序反过来，是洋葱序。脱敏写在 next() 之后，所以它看到的是内层已经取好的完整数据，改写后再交给调用方。两个中间件分属两个插件，彼此不知道对方存在。

第 2 步再挂一个用 prepend 注册、不调 next() 的 veto：

const veto = root.plugin({ name: 'veto', apply(ctx: Context) {
  ctx.on('release/query', () => { log('  veto: refuse, not calling next()'); return [] }, true)
} })
result = root.waterfall('release/query', query, inner)
await veto.dispose()

输出：

2. waterfall: a middleware that never calls next() vetoes the rest
  veto: refuse, not calling next()
  result=[]

veto 用 prepend 注册到最外层，不调 next 直接返回空数组，redact、trace 和读库的内置行为一个都没执行。

工具准入 tools/pre-execute 用的是同一种形态（按源码，未实测），实测见第 9 篇。

bail 只把三个值算作“没处理”

bail 和 serial 的中止判定共用一个函数（:13）：

export function isBailed(value: any) {
  return value !== null && value !== false && value !== undefined
}

只有 null、false、undefined 算“没处理，继续问下一个”，其他值都算中止值，作为分发结果返回，包括 0、空字符串和 NaN。

第 10 步把这几个值逐个放在第一个监听器里返回，看第二个监听器还跑不跑：

10. isBailed on edge values
  null      -> continue, result="next"
  false     -> continue, result="next"
  undefined -> continue, result="next"
  0         -> stop, result=0
  ''        -> stop, result=""
  NaN       -> stop, result=NaN

分界在第四行：从 0 起，第二个监听器不再执行，bail 把 0、""、NaN 原样当结果返回。

写“冻结窗口检查”这类监听器时，不想拦截就必须返回这三个值之一；返回 0 或 '' 表达“没有问题”，会让整条链在这里停住。

dsh 里的斜杠命令用的就是这个协议：把 ctx.bail(...) === true 当作“某个监听器认领了这个输入 token”，没认领的监听器必须返回 undefined（按源码，未实测；packages/client/ui-commands/src/client/service.ts:183）。

第 3 步给 release/freeze 挂三个检查：

const freeze = root.plugin({ name: 'freeze', apply(ctx: Context) {
  ctx.on('release/freeze', () => { log('  window-check: not frozen -> return false'); return false })
  ctx.on('release/freeze', q => { log('  policy-check: frozen -> return reason'); return `frozen for ${q.service}` })
  ctx.on('release/freeze', () => { log('  never reached'); return 'late' })
} })

输出：

3. bail: isBailed treats only null/false/undefined as "not handled"
  window-check: not frozen -> return false
  policy-check: frozen -> return reason
  bail result="frozen for payment-api"

第一个监听器返回 false，被判为“没处理”，继续问下一个；第二个返回字符串，分发停在这里并把它当结果返回，第三个没被调用。

emit 抛错即中断，parallel 跑完再报，serial 逐个等

第 4 步用 emit 分发，第二个监听器抛错：

const listeners = root.plugin({ name: 'listeners', apply(ctx: Context) {
  ctx.on('release/queried', () => { log('  audit-log wrote a line'); return 'ignored' })
  ctx.on('release/queried', () => { throw new Error('metrics down') })
  ctx.on('release/queried', () => { log('  never reached') })
} })

输出：

4. emit: return values dropped, synchronous, one throw stops the rest
  audit-log wrote a line
  caught: metrics down

第一个监听器返回的 'ignored' 被 emit 丢掉；第二个抛出的异常 emit 不兜，直接冒泡到调用处，第三个监听器没执行。

做审计、埋点这类“不能互相影响”的事，用 emit 要自己在监听器里兜住异常。async 监听器的 reject 不会被 emit 等待。

第 11 步挂一个直接 reject 的 async 监听器，并临时监听 unhandledRejection：

11. emit with an async listener that rejects
  emit returned without throwing
  unhandledRejection: async listener failed

emit 正常返回，调用处什么都没收到，错误只出现在进程级的 unhandledRejection。

第 5 步换成 parallel，三个 async 监听器里两个失败：

const par = root.plugin({ name: 'par', apply(ctx: Context) {
  ctx.on('release/audit', async () => { log('  audit A ok'); })
  ctx.on('release/audit', async () => { throw new Error('audit B failed') })
  ctx.on('release/audit', async () => { throw new Error('audit C failed') })
} })

输出：

5. parallel: all listeners run, failures come back aggregated
  audit A ok
  AggregateError with 2: audit B failed, audit C failed

三个监听器都跑了（A 成功，B、C 失败），最后抛出一个带两个子错误的 AggregateError。五种模式里只有 parallel 保证全部跑完，并把失败集中报给调用方。

第 6 步用 serial 发通知：

const ser = root.plugin({ name: 'ser', apply(ctx: Context) {
  ctx.on('release/notify', async () => { log('  notify slack -> undefined'); })
  ctx.on('release/notify', async () => { log('  notify oncall -> "sent"'); return 'sent' })
  ctx.on('release/notify', async () => { log('  never reached'); return 'x' })
} })

输出：

6. serial: awaits each listener, stops at the first bail value
  notify slack -> undefined
  notify oncall -> "sent"
  serial result="sent"

第一个返回 undefined 继续，第二个返回 'sent' 停住。serial 和 bail 的唯一区别是会 await 每个监听器。

脱敏插件一卸下，token 就是明文

ctx.on 注册的监听器就是第 4 篇讲的可撤销副作用（vendor/cordis/src/events.ts:256）：

return this.ctx.fiber.effect(() => {
  hooks[method]({ ctx: this.ctx, callback, ...options })
  return () => this.unregister(hooks, callback)
}, label)

插件卸载时监听器自动摘掉，作者不用自己收集 disposer。执行顺序只看注册：prepend 为真就 unshift，否则 push（:255），没有优先级数字，先注册的先执行。

第 7 步卸掉 redact 插件，再跑一次同样的查询：

await redact.dispose()
result = root.waterfall('release/query', query, inner)
log(`  result=${JSON.stringify(result)}`)

输出：

7. listeners are effects: dispose the plugin, the middleware is gone
  trace: enter
  inner: read DB
  trace: exit, 1 record(s)
  result=[{"id":"demo-001","version":"1.4.0","token":"tok_live_9f3a"}]

token 以明文返回。监听器是 effect，随插件一起消失，waterfall 链上少了一层，内置行为的原始数据直接回到调用方。token 会不会外泄，取决于脱敏插件还挂没挂着。

其余三种抛错即中断，无人中止返回 undefined

第 8 步给 serial、bail、waterfall 各挂两个监听器，第一个抛错，第二个只记录自己跑过；waterfall 的内置行为同样记录：

8. serial / bail / waterfall when a listener throws
  serial rejected: serial boom
  bail threw: bail boom
  waterfall threw: waterfall boom
  later listeners / inner ran: []

最后一行是空表：三种模式都在第一个抛错处停下，第二个监听器和 waterfall 的内置行为都没执行。serial 返回的 Promise 被 reject，另两种同步抛出异常，都没有 parallel 那样的集中处理。

第 9 步让监听器都不中止：serial 的返回 undefined，bail 的返回 null，waterfall 的调了 next() 却不 return：

9. nobody bails, a middleware returns undefined
  serial=undefined, bail=undefined, waterfall=undefined (inner returned "inner value")

前两个是预期的“无人认领”。waterfall 那一项看括号：内置行为返回了 "inner value"，结果仍是 undefined，中间件忘了 return 就会吞掉内层结果。

这对 Agent 意味着什么

脱敏插件没改查询代码一行，就在查询外面套了一层并改写了结果，挂在 waterfall 上的能力都能这样被插件包住。

冻结窗口检查这类由第一个认领的监听器决定结果的场景，适合 bail。需要包住内置行为、在返回时改写结果，用 waterfall。审计、通知要求每个监听器都跑完且互不影响，用 parallel。

旁路通知别用 emit 裸跑。一个监听器抛异常会连累后面的，异常还会冒泡到业务调用处；async 监听器失败则直接成了未处理 rejection。

本文的验证范围

实测部分是 events-demo.ts，只用 vendor Cordis（4.0.2），没有启动 dsh 的 CLI 或 Web 进程，也没有调用模型；数据与 token 都是合成的；脚本用 tsx 运行，未单独跑类型检查。

表格里的五种模式行为来自 events.ts 实现；其中各模式的返回值、中止判定和异常行为都由本次输出直接支持。

主要结论都有断言：

  • waterfall 的执行顺序为 redact → trace → 内置行为 → trace → redact，结果里的 token 为 REDACTED；
  • prepend 注册、不调 next() 的监听器让 waterfall 结果为空数组；
  • bail 的结果为第二个监听器返回的 frozen for payment-api；
  • emit 遇到抛错的监听器，异常 metrics down 冒泡到调用处；
  • parallel 抛出 AggregateError，含 2 个子错误；
  • serial 的结果为 'sent'；
  • 卸载脱敏插件后，waterfall 结果里的 token 为原始值 tok_live_9f3a；全程没有输出过 never reached；
  • serial、bail、waterfall 的首个监听器抛错时，分别 reject、throw、throw，后续监听器与内置行为都未执行；
  • 无人中止时 serial、bail 返回 undefined；waterfall 中间件不 return 时结果为 undefined；
  • isBailed 对 null、false、undefined 放行，对 0、''、NaN 中止；
  • emit 遇 async 监听器 reject 时正常返回，错误出现在 unhandledRejection。

同一脚本在同一环境下连续运行 3 次，输出完全一致。
