第 34 / 36 节 · 扩展与外部接入

部署工具声明了 1 秒超时，平台 2.5 秒后才上线。超时之后模型原样重试，平台收到了三次部署。

第 29 篇把冒烟检查放到了后台，部署本身仍是一次同步的工具调用。平台慢时它可能卡上几十秒，模型等不到结果，又可能原样再调一次。

dsh 基础组合（base bundle）里有两个 guard 插件，一个给工具调用设超时，一个在模型反复做同一个调用时提醒它。它们在 packages/guard 下，下称 guard 插件，与第 9、21 篇按参数拒绝调用的守卫不是一回事。

下面用合成发布平台对照工具超时和实际上线的时间，再让模型重复调用同一个部署工具，检查提醒何时介入、能否拦下部署。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 部署工具 1 秒超时报错，平台 2.5 秒时照样上线；
  • 不理 signal 的工具等满 2.5 秒，部署成功也报超时；
  • 原样连调三次部署，平台收到三次，提醒在第 4 次请求才出现；
  • 交替参数、递增计数、中间插人类消息，都不触发提醒。

两个插件默认启用，限时写在工具自己的定义上

超时和重复提醒各由一个插件负责：

  • 超时插件 dsh-tool-call-timeout-policy，挂在 tools/execute。 工具声明了 timeoutMs 就把一个到点即中止的 signal 换到 exec 上，等工具结束后把结果换成超时错误。
  • 重复提醒插件 dsh-repeat-tool-reminder，挂在 tools/post-execute。 数同一个 agent 连续多少次用相同参数调同一个工具，到阈值就往下一次请求里加一段提醒。

两者都在基础组合里（packages/bundle/base/cordis.patch.yml:387-388,441-445），提醒的阈值配成 [3, 5, 8]。

超时插件不需要配置，限时写在工具自己的定义上：ToolDefinition.timeoutMs，注释写明声明它就等于承诺“把 exec.signal 转给一个能配合取消的实现”（packages/core/tools/src/index.ts:242-249）。

随附工具里只有网页工具声明了 timeoutMs。demo 第 6 步挂上 tool-fs、tool-bash、tool-web（网页工具的配置照基础组合），读出各自的定义：

== 6. 随附工具声明的 timeoutMs ==
  bash=undefined  read=undefined  write=undefined  edit=undefined  web_fetch=30000  web_search=60000

bash、read、write、edit 都是 undefined，不走这个插件的限时，和 README 的说法一致（packages/guard/timeout-policy/README.zh.md:42,123）；web_fetch 和 web_search 分别是 30 秒和 60 秒。

demo 在一个进程里挂 agent 循环和这两个插件，阈值照基础组合的配置，模型换成脚本化模型。部署工具这样写，平台请求一发出就开始部署，工具只是在等确认：

const deploy = defineTool({
  name: 'deploy_release',
  parameters: { service: { type: 'string', required: true }, version: { type: 'string', required: true } },
  timeoutMs: 1000,
  async execute(args, exec) {
    const done = rollout(args.version)
    await Promise.race([done, new Promise((_resolve, reject) => {
      exec.signal.addEventListener('abort', () => { reject(new Error('deploy wait aborted')) }, { once: true })
    })])
    return `${args.service} ${args.version} 已上线`
  },
  // ……description、output 略
})

超时只是不再等

跑一下转发 signal 的部署工具：

== 1. 转发 signal 的部署工具：1 秒超时，平台照样上线 ==
  工具结果 | Error: tool call timed out after 1000ms
  日志里的 error | {"name":"ToolTimeoutError","code":"TOOL_TIMEOUT"}
  这一轮用时 1.0 秒；此刻平台：请求 ["2.5"]，已上线 []
  2.5 秒后平台：已上线 ["2.5"]

模型看到的是一行 Error: tool call timed out after 1000ms，会话日志的 tool/result 里还多一个结构化的 error，代码是 TOOL_TIMEOUT（packages/guard/timeout-policy/src/index.ts:41-48）。这一轮 1 秒就结束了。

整个超时插件是一个 tools/execute 包装（timeout-policy/src/index.ts:55-81）。它从注册表读出工具的 timeoutMs，没有就原样放行；有就用 deadline() 造一个融合了上游取消和定时器的信号，换到 exec.signal 上，等 next() 返回。

如果是自己的定时器先到，就把工具返回的东西整个换成一条超时错误（:73-75）。但平台那边部署已经开始，工具只是放弃了等待，1.5 秒后版本 2.5 照样上线。

超时插件只负责“通知”：README 的已知限制第一条就是“协作式，绝不是硬终止”（timeout-policy/README.zh.md:122），dsh-timeout 库的注释也写明，它只通过 abort signal 发通知，停下工作由各个能力自己负责（packages/util/timeout/src/index.ts:1-5）。

对部署这类有副作用的工具，“超时”说明的是“不知道结果”，不是“没有发生”。错误文字里没有这层意思。

不理 signal 的工具等满全程，成功也报超时

第二个部署工具同样声明 timeoutMs: 1000，但没有把 exec.signal 接进去；另一个看板工具没有声明超时，要 2.5 秒才返回：

== 2. 不理 signal 的部署工具和没声明超时的工具 ==
  deploy_release_legacy（声明 1000ms，不理 signal）| 用时 2.5 秒 | Error: tool call timed out after 1000ms
    平台此刻已上线 ["2.5","2.6"]
    超时插件收到的原始结果 | Error: tool call aborted
  read_dashboard（没声明）                     | 用时 2.5 秒 | error rate 0.1%

再看 deploy_release_legacy 这一行：

  • 声明的 1 秒没有缩短等待。 定时器 1 秒时中止了信号，工具没理会，包装停在 await next() 里等它自己结束（timeout-policy/src/index.ts:68），这一轮仍接近 2.5 秒。
  • 部署成功了，模型收到的却是超时。 工具最后返回了“已上线”，但包装只看定时器有没有先到（:73），先到就整个替换，不看工具返回的是什么。平台上版本 2.6 已经上线，模型读到的是一条错误。

即使没有这层替换，模型也拿不到“已上线”。demo 在超时包装里面挂了一个只记录不改动的 tools/execute 监听器，“原始结果”那一行就是它记下的：注册表发现信号已中止，已经把成功结果改成了 Error: tool call aborted（packages/core/tools/src/index.ts:1558-1562）。

用户中断和超时撞在一起时，看谁先到：

== 7. 用户中断和超时，谁先到算谁 ==
  500ms 时用户中断 deploy_release_legacy | 用时 2.5 秒 | Error: tool call aborted | 原始结果 Error: tool call aborted
  1500ms 时用户中断 deploy_release_legacy | 用时 2.5 秒 | Error: tool call timed out after 1000ms | 原始结果 Error: tool call aborted

两行的用时都是 2.5 秒，中断和超时一样停不下不理 signal 的工具。0.5 秒中断时定时器还没到，模型看到的是 aborted；1.5 秒中断时定时器已经在 1 秒触发，结果仍被换成超时。包装只问“自己的定时器有没有触发”（timeout-policy/src/index.ts:73），不管之后有没有用户中断。

read_dashboard 没声明 timeoutMs，包装直接放行（timeout-policy/src/index.ts:59），等满 2.5 秒拿到原结果。没有全局默认超时，README 把这列为第二条限制（packages/guard/timeout-policy/README.zh.md:123）。

超时后原样重试，平台收到三次部署

模型拿到超时错误后，最自然的反应是再试一次，脚本化模型就连续三次用同样的参数调 deploy_release：

== 3. 超时后原样重试 ==
  第 1 次部署 | Error: tool call timed out after 1000ms
  第 2 次部署 | Error: tool call timed out after 1000ms
  第 3 次部署 | Error: tool call timed out after 1000ms
  第 4 次模型请求里出现提醒 | You are repeating the exact same tool call with identical arguments.
  平台收到的部署请求 ["2.7","2.7","2.7"]

平台收到了三次版本 2.7 的部署。重复提醒确实出现了，但在第 4 次模型请求里，也就是第三次部署已经发出去之后。

阈值 3 数的就是第 3 次调用本身，而提醒挂在 tools/post-execute，只能随这次调用的结果进入下一次请求（packages/guard/repeat-tool-reminder/src/index.ts:181-188,213-224）；插件又从不拒绝调用。

源码注释解释了为什么在 post-execute 计数：被拒的调用也会流经这个钩子，而插件要打破的就是模型反复撞同一个被拒调用的循环。

第 8 步用一个总被 tools/pre-execute 拒绝的回滚工具验证了前半句（节选）：

rollback_release 被 pre-execute 拒绝 3 次 | Error: rollback needs the duty lead | 提醒在第 4 次请求 | 工具体执行 0 次

工具体一次都没执行，提醒照样在第 4 次请求出现，被拒的调用和执行过的一样计数。

提醒从不拦调用

换一个没有副作用的工具，用同样的参数查 9 次发布状态，偶数次故意把参数的键顺序倒过来写成 { version, service }：

== 4. 同样的参数查 9 次状态：提醒不拦调用 ==
  第 4 次请求 | You are repeating the exact same tool call with identical arguments.
  第 6 次请求 | - consecutive_calls: 5 ⏎ - arguments: {"service":"payment-api","version":"2.7"}
  第 9 次请求 | - consecutive_calls: 8 ⏎ - arguments: {"service":"payment-api","version":"2.7"}
  check_status 实际执行 9 次

第 3 次之后给一段温和的提醒，第 5、8 次之后给详细版：点出工具名、连续次数和规范化后的参数，并说“不要再用这组参数调用”（:63-79）。判断“相同”时，参数先按键深度排序再序列化（:89-105），键顺序不同的两种写法算同一个调用。

参数超过 argumentsPreviewChars（基础组合配的是 500）时，提醒里只引前一段，判断仍用完整参数（:113-121）。同一步里并发的相同调用也逐个计数。第 8 步的另外两行（节选，demo 用“……”省略了引文中段）：

参数 651 字，第 5 次后的提醒里 | - arguments: {"note":"灰度灰度灰度灰度灰度灰度灰度灰度灰度……… (+151 more chars)
同一步并发 3 个相同的 check_status → 提醒在第 2 次请求

第一行的引文恰好 500 字，后面标出省略了 151 字，第 5 次照样算重复。第二行里，一个模型响应带了 3 个相同调用，三个调用在同一步里各计一次，第 2 次请求就收到了提醒。

提醒以 plugin 来源的消息附在这次工具结果之后（:203-206,213-224；packages/core/agent-loop/src/tool-calls.ts:156-157），不改结果，也不拒绝调用：第 9 次照样执行。

README 开头就写明“提醒只是建议，绝不会阻止或延迟合理的重复调用”（packages/guard/repeat-tool-reminder/README.zh.md:12）。阈值只有 [3, 5, 8] 这三个点，第 8 次之后不再有新提醒。

交替、计数、插话都不算重复

三种常见的循环都不会触发：

== 5. 不算重复的几种循环 ==
  2.7 与 2.8 交替查 6 次         → 提醒 0 条
  参数里多一个递增的 attempt，6 次 → 提醒 0 条
  查 2 次、人插一句、再查 2 次    → 提醒 0 条

对同一个 agent，插件比较上一次被跟踪调用和这一次的工具名、规范化参数：完全相同就计数加一，否则从 1 重新数（repeat-tool-reminder/src/index.ts:194-198）。

  • 两组参数交替。 每次都和上一次不同，计数一直是 1。周期为 2 的循环完全看不见，周期更长的也一样。
  • 参数里带一个递增的字段。 任何一个值变了，就不是“相同调用”。模型自己加的 attempt、时间戳、随机 id，都会让检测失效。
  • 中间插一条人类消息。 某一步的新消息里只要有 user 来源的，这个 agent 的链条就清空（:229-232）。所以“查 2 次、人说继续、再查 2 次”累计 4 次也不会提醒。

plugin 来源的消息不清空链条。第 8 步的 check_job 在第 2 次调用时模拟后台任务往会话里发一条通知（节选）：

check_job 连调 3 次，第 3 次请求里夹着后台任务的 plugin 通知 → 提醒在第 4 次请求

通知进了第 3 次请求，第 3 次调用仍接着前两次计数。

include 和 exclude 配置可以只跟踪部分工具，或者让某些工具对链条“透明”，既不计数也不打断（:28-43,175-179）。基础组合没有配这两项，所有工具都被跟踪。第 9 步各起一个宿主，把 check_status 和记进度的 note_progress 交替调用：

== 9. include / exclude ==
  默认配置，查 / 记 交替 5 次 → 提醒 0 条
  exclude: ['note_*']，同一序列 → 提醒在第 6 次请求
  include: ['check_*']，记 3 次 → 提醒 0 条

默认配置下交替打断了链条；排除 note_* 后，三次 check_status 连成一条，第 5 个调用之后出现提醒；只跟踪 check_* 时，note_progress 连调 3 次也不计数。

图：超时包装 1 秒后中止 signal，部署照样上线；重复提醒第 3 次调用后计到阈值，随结果进下一次请求。

这对 Agent 意味着什么

超时之后结果是未知，不是失败。超时插件只能请工具停下，停不停、停在哪一步，由工具决定。demo 里部署超时后，平台上 2.5 照样上线，超时错误的文字里没有这层提示。

声明 timeoutMs 等于承诺会配合取消。不接 exec.signal 的工具，声明的时限不会缩短等待，只会把成功的结果改成超时错误。旧代码接进来之前，要么先接好取消，要么别声明。

重复提醒在调用执行之后才计数。第一条提醒进入第 4 次模型请求时，第三次调用已经执行完了；脚本化模型收到提醒后，仍把 check_status 调到了第 9 次。插件只提示、不拒绝，不能代替轮数上限或业务层面的去重。

它只认工具名和参数完全相同的连续调用；交替参数、递增计数，或中间插一条人类消息，都不会触发提醒。

本文的验证范围

实测部分是 guard-demo.ts。它在一个进程里挂 Cordis、agent 循环、dsh-tool-call-timeout-policy 和 dsh-repeat-tool-reminder（阈值 [3, 5, 8]、引用上限 500，与基础组合的配置相同），没有启动 dsh 的 CLI 或 Web 进程。

第 6 步另起一个宿主挂 tool-fs、tool-bash、tool-web，底层的文件、shell、网页服务用空对象占位，只读工具定义、不调用；第 9 步为每种配置各起一个宿主。

模型换成脚本化模型，按剧本调工具，同一步的多个调用放在一个响应里；发布平台是合成的，上线用 2.5 秒的定时器模拟；拒绝回滚的是 demo 自己挂的 tools/pre-execute 监听器，后台任务通知由 demo 的工具直接注入；会话只在内存。

主要结论都有断言：

  • 转发 signal 的部署工具：结果为超时错误，日志里 error 为 ToolTimeoutError/TOOL_TIMEOUT，这一轮不到 2 秒，此刻平台未上线，再过 2.5 秒平台已上线；
  • 不理 signal 的部署工具：脚本要求这一轮至少耗时 2.45 秒（给 2.5 秒定时器留 50 毫秒余量），结果为超时错误，超时插件收到的原始结果为 Error: tool call aborted，平台已上线；没声明超时的工具使用同样的耗时断言，结果原样；
  • 原样调 3 次部署：提醒只出现在第 4 次模型请求里，平台收到 3 次部署；
