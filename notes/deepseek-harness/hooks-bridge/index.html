第 29 / 36 节 · 扩展与外部接入

同一份 hooks.json 搬进 dsh，退出码 2 能拦下部署，另有 7 种写法没拦住，其中 3 种按 Claude Code 文档本该生效。

第 27 篇把外部工具通过 MCP 接进来，这一篇接的是另一类现成配置。很多团队已经给 Claude Code 写了 hooks：工具运行前拦危险命令，运行后检查结果，收尾前要求补测试。dsh-hooks-claude-code 让这份 hooks.json 不用改就能被 dsh 加载运行，但行为并不完全一致。

这次给发布值班 agent 挂一份 hooks.json，用 PreToolUse 在冻结窗口里拦部署，用 PostToolUse 检查部署结果，用 Stop 要求收尾前跑冒烟检查；再把第 21 篇的规则引擎挂上去，看 hook 与守卫谁先谁后，哪些写法在 dsh 里不生效。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 退出码 2 拦下部署，另有 7 种写法在 dsh 里照样放行；
  • hook 返回 ask 时，后注册的冻结插件没有运行，部署执行；
  • PostToolUse 拦下失败结果，规则引擎一条没记，2.3 失败 3 次；
  • stop_hook_active 为 false；拦 10 次后脚本取消。

接上 hooks.json 后，退出码 2 拦下部署

桥接启动时读一次 configPath 指定的配置（packages/hooks/hooks-claude-code/src/index.ts:100-115），只运行 7 个事件上的 command 类型 hook，其余忽略。

7 个事件是 SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、Stop、SubagentStart、SubagentStop（packages/hooks/hooks-claude-code/src/config.ts:11-19）。

其余类型如 http、prompt 会跳过并打警告（:97-101、hooks-claude-code/src/index.ts:109-111）。

demo 的所有 hook 都指向同一个脚本 release-hook.mjs，按参数换行为。命令里的 ${CLAUDE_PLUGIN_ROOT} 在读配置时替换成桥接配置的 pluginRoot（hooks-claude-code/src/config.ts:57-62）：

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "deploy_release",
        "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/release-hook.mjs\" freeze" }]
      }
    ]
  }
}

freeze 模式照 Claude Code 文档的写法：往 stderr 写原因，退出码 2。

== 1. PreToolUse：退出码 2 拦下部署 ==
部署 2.4：报错「Error: 发布冻结中，2.4 等窗口结束再部署」
平台执行 0 次
hook 从 stdin 收到的字段：session_id, transcript_path, cwd, hook_event_name, tool_name, tool_input, tool_use_id
  tool_input = {"service":"payment-api","version":"2.4"}，transcript_path = ""
  hook 的工作目录是会话工作区：true；宿主的 RELEASE_API_TOKEN 在 hook 进程里：absent
  宿主的 DSH_DEMO_MARKER 在 hook 进程里：absent
会话日志记下 hook/result：{"point":"PreToolUse","decision":"block","exitCode":2,"stderrSummary":"发布冻结中，2.4 等窗口结束再部署"}

前两行是预期的拦截，反常在后面：transcript_path 是空字符串，宿主的令牌也没进 hook 进程。

桥接在 tools/pre-execute 这个 waterfall 事件上注册监听器：deny 或 block 变成拒绝，ask 变成审批请求，其余交给下一个监听器（hooks-claude-code/src/index.ts:237-243）。模型看到的报错和第 21 篇守卫拒绝时一样，带 Error: 前缀。

hook 从 stdin 收到的字段名照 Claude Code 的 schema，但少了几个，没有 Claude Code 的 permission_mode、effort 等字段（按 Claude Code 文档，未实测）。

transcript_path 固定为空字符串（hooks-claude-code/src/index.ts:320-329），是因为持久化层不暴露日志路径，会话日志默认用 Zstandard 压缩，hook 脚本读不了（按 README，未实测）。

hook 在会话工作区里运行，工作目录取会话的 cwd，CLAUDE_PROJECT_DIR 默认也设成它（hooks-claude-code/src/index.ts:146-150）。

命令经 dsh-shell 执行器启动，子进程环境去掉了名字匹配 /KEY|PASSWORD|SECRET|TOKEN/i 的变量（packages/subprocess/subprocess/src/index.ts:47、:66-70），桥接的配置项里也没有 env，hook 要调发布平台的 API，令牌得从别处读。

DSH_* 变量也会从子进程环境去掉（清洗在 packages/subprocess/subprocess-local/src/spawn.ts:45 应用）：名字不像凭据的 DSH_DEMO_MARKER 同样没进 hook 进程。

每次运行都在会话日志里留一对记录：hook/invoked 记事件点和 matcher，hook/result 记解码出的决定、退出码、截断后的 stderr 和耗时（packages/hooks/hook-protocol/src/events.ts:75-104）。这两种事件只进日志，不发给模型。

这些写法拦不住部署

demo 用同一个部署请求试了 7 种写法，每种单独起一个宿主、只挂这一个 hook，结果都是平台照样部署：

== 2. 这些写法都没拦住：部署照样执行 ==
退出码 1：payment-api 2.4 succeeded（记为 pass，退出码 1）
JSON 写 deny、退出码 1：payment-api 2.4 succeeded（记为 pass，退出码 1）
顶层 {"decision":"deny"}：payment-api 2.4 succeeded（记为 pass，退出码 0）
hookSpecificOutput 缺 hookEventName：payment-api 2.4 succeeded（记为 pass，退出码 0）
hook 超时（timeout: 1 秒）：payment-api 2.4 succeeded（记为 pass，没有退出码）
matcher 写成 "deploy_release, rollback_release"：payment-api 2.4 succeeded（没有 hook 记录）
{"continue":false}：payment-api 2.4 succeeded（记为 stop，退出码 0）
对照，顶层 {"decision":"block"}：报错「Error: 发布冻结中」，平台执行 0 次

前 7 行都是 succeeded，只有最后一行对照组拦下了部署。这 7 种写法由共享的解码器 dsh-hook-protocol 和桥接处理，和 Claude Code 文档对照如下（按 Claude Code 文档，未实测）：

写法dsh 的处理Claude Code 文档
退出码 1非阻塞失败一样
JSON 写 deny、退出码 1不解析 JSONdeny 会拦下
顶层 decision: "deny"当作无效已弃用，旧值只有 approve / block
缺 hookEventName丢弃事件字段要求必须有，缺失后果没明说
超时非阻塞失败一样，不拦
matcher 含逗号、空格当正则按字面列表匹配
continue: false只记为 stopClaude 停止处理

dsh 一侧只有退出码 2 算拦截，退出码 0 才解析 stdout，顶层 decision 只认 approve / block，缺 hookEventName 就丢弃事件字段（packages/hooks/hook-protocol/src/codec.ts:38-40、:66-69、:72-86、:122-124）。

超时的进程被杀、退出码为空（packages/hooks/hook-protocol/src/runner.ts:91）；matcher 只有 [A-Za-z0-9_|] 按字面匹配（packages/hooks/hook-protocol/src/matcher.ts:18、:61-64）。

continue: false 只写进日志，没有运行级效果（hooks-claude-code/src/index.ts:188）。

Claude Code 在任何退出码下都读 JSON；顶层 decision 的旧值 approve / block 分别映射成 allow / deny，deny 不是合法旧值（按 Claude Code 文档，未实测）。

缺 hookEventName 若判为 schema 校验失败，Claude Code 按非阻塞错误处理，工具照常执行。matcher 把 -、空格、, 也当字面列表字符；continue: false 优先于其他决定字段（按 Claude Code 文档，未实测）。

表中“JSON 写 deny、退出码 1”、matcher、continue: false 三行，在 Claude Code 里生效（按 Claude Code 文档，未实测），搬到 dsh 就不生效。三种都不报错，只在 hook/result 里留下一条 pass 或 stop，matcher 写法连记录都没有。

其中 continue: false 写在桥接 README 的已知限制里，另外两种没写；运行时三种都不打警告。

**未实测：**按源码，dsh 桥接的默认超时是 600 秒（hooks-claude-code/src/index.ts:75），执行器的上限也是 600 秒（packages/shell/bash-local/src/index.ts:107-108、:149-153），不设 timeout 的检查脚本卡住时，部署要等 10 分钟后放行。

会话日志里的 decision 只反映解码结果，不反映效果：pass 表示这个 hook 没给出能识别的决定；stop 只表示 hook 要求停下，运行没有停（hook-protocol/src/events.ts:99）。审计时想知道“这次部署有没有被 hook 拦过”，要看同一次调用的工具结果，不能只看 hook/result。

hook 与原生插件按注册顺序生效

hook 的 PreToolUse 是 tools/pre-execute 上的监听器；第 21 篇的规则引擎用守卫 ctx.tools.guard。工具流水线先跑 pre-execute waterfall，返回 ask 就去审批，放行才跑守卫（packages/core/tools/src/index.ts:1482-1496）。

平台上 2.3 每次部署失败，demo 连续部署三次：

== 3. 和第 21 篇守卫、其他 pre-execute 插件的先后 ==
hook 返回 ask，连续部署 2.3 三次：平台执行 2 次，审批人收到 3 次请求、都批准了
  审批理由：hook 要求人工确认 2.3
  第 3 次：报错「Error: [same-version-failed-twice] payment-api 2.3 在 24 小时内已失败 2 次，停止重试」
hook 返回 allow，同样三次：平台执行 2 次，第 3 次：报错「Error: [same-version-failed-twice] payment-api 2.3 在 24 小时内已失败 2 次，停止重试」
冻结插件在 hooks 桥接之后注册：payment-api 2.4 succeeded，平台执行 1 次
冻结插件在 hooks 桥接之前注册：报错「Error: freeze-window 插件：发布冻结中」，hook 运行 0 次
hook 返回 deny：报错「Error: hook 拒绝 2.4」；后注册的 pre-execute 插件运行 0 次（hook 返回 allow 时 1 次）
同一事件配 allow、ask、deny 三个 hook：依次运行 allow、ask、deny，结果 报错「Error: hook 拒绝 2.4」，审批请求 0 次
配 ask、allow 两个：结果 payment-api 2.4 succeeded，审批请求 1 次
同一条命令配两次、各占 300 毫秒：运行 2 次，第二个比第一个晚开始 300 毫秒以上：true

前四行里，ask 的理由原样交给审批人，审批人批准后守卫照样拒绝，和第 27 篇的审批一样，hook 绕不过守卫。allow 也不是预先批准，桥接对 allow 只调用 next() 交给后面的监听器（hooks-claude-code/src/index.ts:242），守卫照常执行。

waterfall 按注册顺序调用，前一个监听器不调 next()，后面的就轮不到（vendor/cordis/src/events.ts:234-243；注册默认 push 到末尾，:255）。所以 hook 返回 ask 时，后注册的 pre-execute 插件不再运行。

demo 写了一个冻结窗口插件，对所有部署返回 deny：

  • 它注册在 hooks 桥接之后时，hook 返回 ask，审批人批准，部署执行。冻结插件没有被调用。
  • 它注册在前面时，冻结插件直接拒绝，hook 根本没运行。

同样两个插件，结果取决于加载顺序。输出第 7 行：hook 返回 deny 时，桥接同样不调 next()，后注册的计数插件一次也没运行（hooks-claude-code/src/index.ts:240）。

Claude Code 里，匹配同一次 PreToolUse 的多个 hook 并行运行，结论按 deny > defer > ask > allow 取最严格的（按 Claude Code 文档，未实测）。

dsh 桥接在自己内部按配置顺序串行运行、不去重（:151-184），结论也按这个优先级合并（packages/hooks/hook-protocol/src/merge.ts:35-42，没有 defer）。

输出最后三行：allow、ask、deny 依次运行，合并成 deny，审批一次也没问；ask 加 allow 合并成 ask。同一条命令配两次就运行两次，第二个等第一个结束才开始。桥接和其他原生插件之间不合并决定，按 waterfall 顺序执行：前面的监听器不调 next()，后面的就不运行。

守卫不受影响，因为它在 waterfall 之后运行，只能拒绝。要拦截的规则，写成守卫比写成 pre-execute 监听器可靠。

图：部署依次经过 pre-execute waterfall、审批、守卫和 PostToolUse；底栏是放行写法与 Stop 循环。

PostToolUse 改了结果，规则引擎漏记了失败

PostToolUse 在工具运行之后触发，demo 的检查脚本看到结果里有 failed，就返回 {"decision":"block","reason":"…先查原因再重试"}，想让模型别再重试；部署成功时返回一条 additionalContext：

== 4. PostToolUse：部署已经执行，hook 只能改结果 ==
连续部署 2.3 三次，每次：报错「2.3 部署失败，先查原因再重试」
平台执行 3 次，规则历史 0 条，第 3 次守卫没有拦
部署 2.4：payment-api 2.4 succeeded；模型下一次请求里多了一条插件消息：2.4 已上线，记得 10 分钟后看错误率
后面再注册一个 post-execute 插件（对 2.4 返回 block）：
  部署 2.3：报错「2.3 部署失败，先查原因再重试」，后面的插件运行 0 次
  部署 2.4：报错「值班规则：2.4 先灰度」，后面的插件运行 1 次；hook 的附加消息仍在：2.4 已上线，记得 10 分钟后看错误率

第二行平台执行 3 次，三次部署都发生了，hook 拦下的只是结果。桥接把 block 映射成 post-execute 的 block 决定（hooks-claude-code/src/index.ts:250-252），工具流水线用 hook 的理由替换原结果，并标成报错（tools/src/index.ts:1757-1764）。

模型看到的是 hook 的一句话，看不到 payment-api 2.3 failed。

第 21 篇的引擎在 tools/result 上记部署历史，报错的结果一律不记。tools/result 收到的是 post-execute 之后的最终结果（tools/src/index.ts:185-191），hook 把失败结果改成了报错，引擎就一条也记不下来。

第 3 步同样三次部署，第三次被守卫拦下；这里第三次照样执行，平台上 2.3 失败了 3 次。hook 本想阻止重试，却让规则引擎漏记了失败，守卫没有记录可依，拦不下第三次。

additionalContext 作为一条来源为 hooks-claude-code 的用户消息，放进模型的下一次请求（hooks-claude-code/src/index.ts:191-195、:255-263）。

最后三行在桥接之后又注册了一个 post-execute 插件。hook 返回 block 时直接返回，不调 next()，后面的插件没运行（:250-252）。hook 没拦时，桥接先调 next()，让后面的插件先做决定，再把自己的消息加上去：2.4 被后面的插件拦下，hook 的附加消息仍然到了模型。

Stop 连拦 10 次，直到 demo 取消

Stop hook 在模型准备结束一轮时触发（agent/turn-stopping）。它返回 block 时，桥接调用 agent.steer() 塞一条消息，让模型再走一步（hooks-claude-code/src/index.ts:269-276）。

demo 的第一个脚本自己用标记文件计数，前两次拦下：

== 5. Stop：强制继续没有上限 ==
hook 自己计数、拦两次：模型请求 4 次（部署本身 2 次）
  模型收到的引导：还没跑冒烟检查（第 1 次拦下） / 还没跑冒烟检查（第 2 次拦下）
  三次 Stop 的 stop_hook_active：false, false, false
按 stop_hook_active 自我限制的 hook：Stop 运行 10 次、模型请求 12 次后由 demo 取消，轮次结束原因 {"kind":"aborted","reason":{"kind":"user"}}

“部署本身 2 次”指不拦时这次对话只要 2 次模型请求，多出的 2 次来自两次强制继续。

dsh 桥接把 stop_hook_active 写死为 false（hooks-claude-code/src/index.ts:343-345）。

在 Claude Code 里，这个字段告诉 hook“这一轮已经因为 Stop hook 继续过”，官方建议 hook 检查这个值（或读 transcript），避免在一个永远满足不了的条件上反复拦截；最直接的写法是看到 true 就放行（按 Claude Code 文档，未实测）。

第二个脚本就按这个建议写：stop_hook_active 不是 true 才拦。在 dsh 里它每次都拦，模型被一次次推着继续。demo 在第 12 次模型请求时取消了 agent；更长轮次会怎样，没有继续实测。

Claude Code 连续强制继续 8 次后会忽略下一次拦截、结束这一轮，上限可以用 CLAUDE_CODE_STOP_HOOK_BLOCK_CAP 调（按 Claude Code 文档，未实测）。

dsh 桥接没有实现 Stop 次数上限，源码里留着 TODO(stop-loop-guard)（按源码，未实测；hooks-claude-code/src/index.ts:268）。本次每多一次强制继续，就多一次完整的模型请求。

dsh 上的 Stop hook 要自己设退出条件。demo 用标记文件计数，拦两次后放行。

PTC 子调用照样触发 hook，updatedInput 不生效

第 6 步补两种情况：

== 6. PTC 程序里的子调用、updatedInput ==
PTC 程序里调 deploy_release：程序拿到 caught: 发布冻结中，2.4 等窗口结束再部署，平台执行 0 次
  hook 收到 tool_name = deploy_release，tool_use_id = call-1:ptc:1
hook 放行并要求把版本改成 2.5：payment-api 2.4 succeeded，平台收到 2.4
  logger：hooks-claude-code: PreToolUse hook requested updatedInput, which is not yet honored (ignored)

第 25 篇的 PTC 模式下，程序里的 tools.deploy_release(...) 同样触发了 PreToolUse，tool_name 是原名，tool_use_id 是子调用编号 call-1:ptc:1。hook 的拒绝成了程序里的异常，被 catch 住了，和第 25 篇守卫的拒绝一样。

hook 放行并要求把版本改成 2.5，平台收到的仍是 2.4；桥接只在 logger 里打一条 warn（hooks-claude-code/src/index.ts:174-176）。靠 updatedInput 改参数的 hook，搬到 dsh 就不改了，部署按原参数执行。

这对 Agent 意味着什么

同一份 hooks.json 在 dsh 里只跑一个子集：7 个事件、command 类型，stdin 缺 transcript。“JSON 写 deny、退出码 1”、逗号分隔的 matcher、continue: false 这三种写法在 dsh 里静默放行，迁移前要在 dsh 上逐个实跑拦截型 hook。

会话日志里的 hook/result 也不等于拦截结果，pass 和 stop 背后部署都可能已经发生。审计有没有拦住，要对照平台侧是否真的执行（PostToolUse 改成报错时部署已经发生），不能只看 hook/result 里的 decision。

hook 与原生插件之间按加载顺序生效。在 pre-execute 上先注册的插件先表态，hook 的 ask 可以让后面插件的 deny 失效，必须拦住的规则放进守卫。PostToolUse 拦不住副作用，还可能改掉别人依赖的结果：靠 tools/result 记账的插件看到的是 hook 改过之后的结果。

Stop hook 要自己限次：本次 stop_hook_active 一直为 false，连拦 10 次时桥接也没有主动结束。

本文的验证范围

实测部分有三个文件：

  • release-hook.mjs：一个 command hook 脚本，按参数切换行为，把收到的 stdin、工作目录和能否读到令牌记进账本；
  • release-rules.ts：第 21 篇的规则引擎，与第 27 篇相同；
  • hooks-demo.ts：驱动脚本，挂载真实的 dsh-hooks-claude-code、dsh-bash-local、dsh-subprocess-local、dsh-tools、dsh-user-approval、会话存储与 agent 循环。hook 是真实启动的 Node 子进程。

模型和审批人是脚本化的，发布平台是本地注册的合成工具，时钟固定。每个场景启动一个新宿主和一份新的 hooks.json。第 6 步的 PTC 宿主另挂 dsh-ptc-runtime-node 和本地沙箱。

主要结论都有断言：

  • 退出码 2 时的报错文字、平台执行 0 次、stdin 的字段列表、transcript_path 为空、hook 的工作目录、读不到令牌和 DSH_DEMO_MARKER、日志里的一对 hook/* 事件及其决定和退出码；
  • 7 种写法下部署都执行了，以及各自在日志里的记录；对照组的顶层 block 拦下了部署；
  • ask 与 allow 两种情况下平台执行 2 次、第 3 次的拒绝文字、审批人收到 3 次请求；冻结插件两种注册顺序下的结果，以及 hook 运行次数；hook 返回 deny 时后注册插件运行 0 次、allow 时 1 次；三个 hook 的运行顺序与合并结果、审批次数；同一命令配两次运行 2 次且相隔 300 毫秒以上；
  • PostToolUse 三次的报错文字、平台执行 3 次、规则历史 0 条、成功部署后模型请求里的附加消息；后注册的 post-execute 插件在 hook 拦下时运行 0 次、没拦时运行 1 次且附加消息仍在；
  • Stop 自计数时的模型请求次数和引导文字、stop_hook_active 全为 false、按文档建议写的 hook 一直拦到第 12 次模型请求被取消；
  • PTC 子调用的拒绝文字、平台执行 0 次、hook 收到的 tool_name 与 tool_use_id；updatedInput 下平台收到 2.4、logger 的警告原文。

输出里的 Stop 运行次数和轮次结束原因只打印，未设置断言。

另外做了变异检查。以下 5 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • freeze 模式的退出码从 2 改成 3；
  • 超时那一种写法去掉 timeout: 1；
  • 冻结插件改到 hooks 桥接之前注册；
  • 按文档建议写的 Stop hook 改成只在字段缺失时拦截；
  • PostToolUse 检查脚本把 block 改成 approve。

连续 5 次运行，以及 4 个进程并发运行，输出都一致。本机实测一次运行约 11 秒，其中超时那一种写法固定等 1 秒。
