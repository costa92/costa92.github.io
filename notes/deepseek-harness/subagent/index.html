第 20 / 36 节 · Agent 编排

父 agent 在 setup 里拉黑了回滚工具，自己看不到；它派出去的子 agent 看得到，回滚照样执行。一次派 10 个后台子 agent，第 9、10 个直接被拒。

第 18 篇的 goal 让一个会话连续跑很多轮，但干活的始终是一个 agent。本篇换个做法：用 packages/subagent 让父 agent 给每个服务派一个子 agent 去查发布记录，自己只负责汇总。

这次给 3 个服务各派一个子 agent，比较后台与前台、spawn 与 fork；再给父 agent 拉黑回滚工具，最后一次派 10 个。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 默认的 subagent 派出即返回，结果靠结束通知送回；
  • fork 子 agent 看得到之前的轮次，看不到当前这一轮；
  • 父 agent 在 setup 里拉黑的工具，子 agent 照样能调；
  • 可继续的后台子 agent 同时最多 8 个，第 9、10 个被拒。

委派要挂服务、后端、委派工具和控制工具四类包

packages/subagent 下有 10 个包，本篇直接挂载其中 5 个：

  • dsh-subagent 提供 ctx.subagents：按名字注册的提供方表、一次性运行（one-shot）、可继续子 agent（continuable）的管理，以及列出子会话的 listChildren()。
  • dsh-subagent-spawn-in-process 和 dsh-subagent-fork-in-process 是两个进程内后端。spawn 起一个全新的子 agent，fork 起一个带着父会话历史的子 agent。两者共用 dsh-subagent-in-process-driver 里的驱动代码。
  • dsh-tool-subagent 把委派做成模型能调的工具。一个实例对应一个提供方和一个工具名。
  • dsh-tool-subagent-control 提供 send_message 和 interrupt_agent，用于和可继续子 agent 通信。

除这 5 个和驱动包外，其余 4 个是进程外后端（ACP、Codex、Claude Code、另一个 dsh 实例），本篇没有用到；控制工具包里还有一个单独加载的 list_agents，本篇也没用。

基础组合（base bundle）挂了两个委派工具（packages/bundle/base/cordis.patch.yml:356-374）：

  • subagent 走 spawn，backgroundMode: continuable，默认在后台运行。
  • subagent_fork 走 fork，backgroundMode: one-shot，默认在前台等结果。

demo 按这两行配置挂载，另加一个带 toolFilter 的 subagent_safe，后文“setup 里拉黑的工具，子 agent 照样能调”一节会用到。

图：父 agent 并发派出子 agent，子 agent 加入父 agent 的 preset，结果经通知或前台返回收回。

默认的 subagent 工具派出去就返回

脚本化模型在父 agent 的一条回复里同时调 3 次 subagent，每个服务一次，子 agent 各查一个服务，查询有 40、200、360 毫秒不等的延迟：

== 1. 默认的 subagent：派出去就返回，结果靠通知送回 ==
subagent -> started subagent <order-api>
subagent -> started subagent <payment-api>
subagent -> started subagent <user-api>
通知首行：Background subagent <order-api> finished and will do no further work unless you send it more.
  结尾文本：order-api: demo-007 succeeded
  结尾文本：payment-api: demo-003 failed, rolled back
  结尾文本：user-api: demo-011 succeeded
子 agent 查询最多同时 3 个在跑；父 agent 共 4 轮，其中 3 轮由通知唤醒
还活着的子 agent 0 个；留下的子会话：continuable/inactive, continuable/inactive, continuable/inactive
子 agent 收到的任务消息 2 段；第 2 段开头：Your parent agent id is "patrol". Before you finish, send your result to…

前三行是派发的返回值，每个只有一行 started subagent；结果要看通知首行之后的三行结尾文本。尖括号里的服务名是脚本替换的，dsh 原文是子会话的 UUID，没有尖括号。

3 次调用在同一步里并发执行：subagent 工具声明了 isConcurrencySafe: () => true（packages/subagent/tool-subagent/src/index.ts:471）。

agent 循环会把同一条回复里的这类调用放进一个并发组，默认最多同时 10 个（packages/core/agent-loop/src/constants.ts:6）。

后台模式下，工具调用 startContinuable()，子 agent 的收件箱接下任务就返回（tool-subagent/src/index.ts:528-537），不等它开始跑。父 agent 拿到的只是一行 started subagent <id>，脚本化模型接着回复一句，这一轮就结束了，不等结果。

子 agent 跑完以后，由运行时给父 agent 投一条通知。通知的来源类型是 subagent-settled，首行说明子 agent 怎么结束的，后面附上它最后一条回复里的文字（packages/subagent/subagent/src/continuation-messages.ts:106-160）。

父 agent 空闲时，通知作为 followup 排队并开启新的一轮；正在跑时，以 steer 方式并进当前这一轮；父 agent 正在关闭时只写入、不唤醒（packages/subagent/subagent/src/continuation-activation.ts:871-881、:334-346）。

本例 3 条通知到达时父 agent 都已空闲，分别唤醒了 3 轮，加上最初那一轮共 4 轮。换一个父 agent，派出子 agent 后在同一轮里再调一个等 600 毫秒的工具：

== 2. 父 agent 还在跑时，结束通知并进当前这一轮 ==
父 agent 日志：turn/start -> user/message(user) -> tool/result -> tool/result -> user/message(subagent-settled) -> turn/end
父 agent 共 1 轮，模型请求 3 次

通知出现在唯一一对 turn/start、turn/end 之间，没有另开一轮。轮数取决于通知到达时父 agent 在不在跑。

父 agent 要在“收齐 3 份”之后再汇总，得由模型自己记着派出去了几个、收到了几个。

子 agent 回收后，子会话留下且可继续

子 agent 结束的条件是：没有正在进行的工作、收件箱为空、它自己派出的子 agent 都已回收。满足后，管理器先刷盘，再释放子 agent、归还名额，最后才给父 agent 投通知（subagent/src/continuation-activation.ts:742、:842-864）。

脚本另开一个父 agent relay 派一个后台子 agent，在释放和通知两个时刻各记一笔，然后用 send_message 把它叫回来：

== 3. 回收顺序，以及用 send_message 叫回已回收的子 agent ==
释放子 agent（此时盘上已有它的最后一条事件 seq 17：true）
父 agent 收到通知（此时子 agent 还在注册表：false）
send_message -> message delivered to agent <order-api>
子 agent 被叫回后的第一次请求（去掉系统消息）：
  user: 查 order-apiYour parent agent id is…
  user: Current runtime context. This snap…
  assistant:
  user: order-api: demo-007 succeeded
  assistant: order-api: demo-007 succeeded
  user: Agent relay sent a message: 再查一次
父 agent 收到 2 条结束通知，结尾文本：order-api: demo-007 succeeded / order-api: demo-007 succeeded

前两行对应顺序：释放时盘上已有最后一条事件，通知到达时注册表里已经没有它。

子 agent 从注册表消失时，通知可能还没进父 agent 的日志，所以脚本按通知条数等待。3 条通知都到齐之后检查：注册表里已经没有子 agent，3 个子会话还留在持久化里，listChildren() 列出它们是 continuable、inactive。

“可继续”的意思是之后还能用 send_message 给它发消息，管理器会从日志把它恢复出来再投递。叫回后的第一次请求带着上一次的任务和查询结果，最后一条是父 agent 转来的“再查一次”，查完又投了一条通知。

挂了 send_message 时，可继续子 agent 的任务后面会追加一段说明（subagent/src/continuation.ts:178-181），第 1 步末行就是：要它结束前用 send_message 把结果发给父 agent。本例的脚本化子 agent 没照做，结果只通过通知送回。

要一次汇总，就让它在前台跑

同样 3 个服务，这次每个调用都带 run_in_background: false：

== 4. run_in_background: false：同一步拿齐 3 份结果，子 agent 随即回收 ==
subagent -> order-api: demo-007 succeeded
subagent -> payment-api: demo-003 failed, rolled back
subagent -> user-api: demo-011 succeeded
查询最多同时 3 个；父 agent 这一轮发了 2 次请求；还活着的子 agent 0 个
  子会话 check order-api mode=one-shot activity=inactive parent=sweep depth=1 origin=subagent
  子会话 check payment-api mode=one-shot activity=inactive parent=sweep depth=1 origin=subagent
  子会话 check user-api mode=one-shot activity=inactive parent=sweep depth=1 origin=subagent
前台子 agent 收到的任务消息各 1、1、1 段，没有 send_message 说明

3 个子 agent 仍然并发，父 agent 在同一步拿齐 3 份结果，下一次请求直接汇总。这一轮父 agent 只发了 2 次模型请求：一次派活，一次汇总。

run_in_background: false 让调用改走一次性的前台路径（tool-subagent/src/index.ts:304、:564-568），即使这个工具实例配置的是 continuable。

前台调用在拿到结果后立刻 dispose 子 agent（settleForegroundRun，tool-subagent/src/index.ts:208-238）。回收的是内存里的 agent，会话本身留着。

子会话的头部记录了它从哪来：parentSession 指向父会话，origin 是 subagent，delegationDepth 是父 agent 的深度加 1（packages/subagent/subagent/src/child-agent.ts:51 计算，:139-157 写入头部）。

后台模式不占住父 agent，代价是要多跑几轮、自己对账。前台模式一次拿齐结果，父 agent 等待期间做不了别的事。

fork 看得到之前的轮次，看不到当前这一轮

父 agent 先和人聊一轮：“本次发布版本 v2.3，涉及 3 个服务”。第二轮人说“payment-api 刚回滚过，重点看它”，父 agent 同时用 subagent_fork 和 subagent 各派一个子 agent，任务都是“查 payment-api”。

脚本记下两个子 agent 第一次请求里的消息：

== 5. fork 看得到之前的轮次，看不到当前这一轮 ==
fork check 的第一次请求：
  user: 本次发布版本 v2.3，涉及 3 个服务
  assistant: 记下了：v2.3，3 个服务。
  user: 查 payment-api
  user: Current runtime context. This snap…
spawn check 的第一次请求：
  user: 查 payment-api
  user: Current runtime context. This snap…

spawn 出来的子 agent 只看到任务本身。fork 出来的子 agent 多了第一轮的对话，但看不到第二轮里人说的“重点看它”。

fork 后端截取父会话日志到最后一个 turn/end 为止（packages/subagent/subagent-fork-in-process/src/index.ts:48-55）。当前这一轮还没结束，日志不平衡，没法作为子会话的种子回放，所以被整段排除。

subagent_fork 的工具描述里对模型说明了这一点：“it does not see the current in-flight turn”（tool-subagent/src/index.ts:256-257）。

实际用的时候，人在当前这一轮里交代的要求，父 agent 要自己写进任务文字里，fork 不会替它带过去。

setup 里拉黑的工具，子 agent 照样能调

本节准备了两个父 agent，都拉黑了全局工具 rollback_release，只是拉黑的位置不同：

  • 一个在宿主创建会话时的 setup 里，对 agent 自己的作用域调 restrict({ deny })。第 17 篇讲过，这是给单个会话加限制的做法之一。
  • 另一个挂在一个 preset 上，preset 的行里写了 restrict: { deny: [rollback_release] }。

两个父 agent 各派子 agent 去回滚：

== 6. 子 agent 能用哪些工具 ==
父 agent（setup 里 deny）：rollback_release 看不到
  用 subagent 派的子 agent：看得到，收到 -> payment-api rolled back
  用 subagent_safe 派的子 agent：看不到，收到 -> Error: unknown tool "rollback_release"
父 agent（preset 里 deny）：rollback_release 看不到
  用 subagent 派的子 agent：看不到，收到 -> Error: unknown tool "rollback_release"
子 agent 的运行时说明：You are a delegated subagent: your permission scope was fixed wh…
子 agent 工具表里有 subagent：true，再派一层 -> Error: subagent depth 2 exceeds maxDepth 1
父 agent（preset 行在 agent/created 里 allow）：工具 lookup_release, subagent
  用 subagent 派的子 agent：工具 lookup_release, subagent，收到 -> Error: unknown tool "rollback_release"
父 agent：沙箱覆盖 workspace-write，审批策略 ask；调 risky_op -> unavailable
  子会话日志里的策略事件：sandbox/mode workspace-write source=delegation；approval/policy never source=delegation
  子 agent 调 risky_op -> rejected

在 setup 里拉黑的那个父 agent 自己看不到回滚工具，它派出去的子 agent 却看得到，回滚也执行了。脚本断言 rollback_release 真的被调用了一次。

agent 循环创建 agent 时，作用域从循环自己的上下文派生（packages/core/agent-loop/src/index.ts:552、:628），子 agent 的作用域因此不挂在父 agent 的作用域下面。

派生发生在 agent 构造时（packages/core/agent-loop/src/agent.ts:104）。子 agent 的工具作用域和父 agent 仅一处关联：加入父 agent 的 preset（subagent/src/child-agent.ts:205）。所以 preset 里的限制会跟过去，父 agent 自身作用域的不会。

设计笔记（2026-07-12-subagent-persona-tool-filter-and-depth.zh.md）明确说了这是有意的：注册作用域是扁平的，“生命周期所有权不意味着可见性继承”；“可见性不是授权”，“这些控制有意不解决安全隔离或父到子的非升权问题”。

子 agent 的运行时上下文里另有一段说明：“your permission scope was fixed when you were started and cannot be widened”。这段话管的是审批和沙箱，工具列表不在它的范围内。

委派时，父 agent 的显式沙箱覆盖设置会被复制到子会话，审批策略在挂了审批服务时固定为 never（subagent/src/child-agent.ts:246-277）；Auto、Full access 权限预设也会复制（按源码，未实测）。

输出最后三行是另一个父 agent：挂上审批和沙箱策略服务，父会话显式把沙箱设为 workspace-write，审批保持 ask。子会话日志里多了两条 source=delegation 的策略事件，子 agent 请求审批直接得到 rejected。

父 agent 同样请求审批，得到的是 unavailable：脚本没挂任何应答方。

要让子 agent 也用不了回滚，可以用下面的办法，demo 都验证过：

  • 把限制写进 preset。子 agent 加入同一个 preset，限制随之生效。
  • 在委派工具上配 toolFilter，例如 subagent_safe 配的 { deny: ['rollback_release'] }。它在子 agent 创建时对子 agent 的作用域调 restrict()（subagent/src/child-agent.ts:218），对这个工具派出的所有子 agent 都生效。

第 17 篇在 preset 行里监听 agent/created 加的白名单，也会跟到子 agent：子 agent 加入 preset 后，同样会在 preset 的作用域里触发 agent/created。输出倒数第 5、4 行，父 agent 所在 preset 只放行两个工具，子 agent 的工具表也只有这两个，调回滚被拦。

脚本化子 agent 调了一个不在自己列表里的工具，这是故意的：返回 unknown tool，说明被过滤的工具连执行也被拦下，不只是不展示给模型。

第 7 行是深度限制。子 agent 的工具列表里仍然有 subagent，调用时才被拒。

委派工具不配 maxDepth 时，读宿主设置 subagent.maxDepth，默认 1（packages/subagent/subagent/src/index.ts:200、:248-251），也就是只允许一层子 agent。设计笔记里写的默认值是 3，与现在的代码不一致，以代码为准。

一次派 10 个，第 9、10 个被拒

最后让父 agent 一次派 10 个后台子 agent，子 agent 的查询全部卡住，直到脚本放行：

== 7. 一次派 10 个：第 9、10 个被拒 ==
成功 8 个，失败 2 个；此时还活着的子 agent 8 个
第 9 个 -> Error: subagent limit reached (active child limit: 8)
池满时，前台一次性子 agent -> order-api: demo-007 succeeded；还活着的可继续子 agent 8 个
放行后：还活着的子 agent 0 个，wide 收到 8 条结束通知
子 agent 再派 8 个孙 agent：成功 7 个，失败 1 个；此时还活着的子孙 8 个
  失败的那个 -> Error: subagent limit reached (active child limit: 8)

第 2 行是第 9 个的报错，原文分号后还有一句建议，脚本只打印了分号前的部分。

可继续子 agent 有一个容量池，默认 8 个（subagent/src/index.ts:201）。占满后新的派发直接报错 ACTIVATION_LIMIT_REACHED。报错会作为错误结果返回给模型，错误文本里建议它等已有的子 agent 结束，或者用现有的 agent 完成工作。

池满时再派一个前台一次性子 agent，照常拿到结果：一次性子 agent 不占这个池。

容量池按“不是可继续子 agent 的父 agent”分配，通常就是顶层 agent，同一条可继续父子链上的子孙共用这 8 个名额（subagent/src/continuation-activation.ts:605-611、:488-489）。

最后两行用另配 maxDepth: 2 的 subagent_deep：顶层 agent 派 1 个可继续子 agent，它再派 8 个孙 agent，只成功 7 个。子 agent 自己占了顶层的 1 个名额，孙 agent 没有另起一个池。

这对 Agent 意味着什么

需要约束一个会话能用哪些工具时，限制要写在子 agent 也会继承的地方：写进 preset，或者配在委派工具的 toolFilter 上。只在父 agent 自己的作用域里加的限制，到子 agent 那里就没有了。

父 agent 在 setup 里拉黑的工具，子 agent 照样能调，所以工具过滤算不上安全边界，绝不能执行的操作，不能只靠父 agent 这一层过滤来挡。

默认的后台模式适合互相独立、不急着要结果的任务；“查完再汇总”更适合前台模式，或者由模型在后台模式下自己对账。fork 不会带上当前这一轮，用户在这一轮里刚说的要求，要写进任务文字里交给子 agent。

可继续（continuable）的后台子 agent 同时最多 8 个，委派默认只能一层。服务一多，派之前就要数一数，分批派，或者调大 maxActiveSubagents。

本文的验证范围

实测部分是 subagent-demo.ts：挂载真实的 dsh-subagent、spawn 和 fork 两个后端、dsh-tool-subagent（三个实例）、dsh-tool-subagent-control、dsh-agent-loop。

demo 还挂载真实的 dsh-tools、dsh-system-prompt、dsh-agent-presets、JSONL 持久化和 SQLite 会话查询（都写在临时目录），以及 dsh-session-checkpoint-policy，没有启动 dsh 的 CLI 或 Web 进程。

dsh-sandbox-policy 和 dsh-user-approval 在第 6 步中途才挂上，前面各步的输出不受它们影响。

模型是脚本化模型，父 agent 每一轮的动作是预先写好的，子 agent 按任务文字决定调哪个工具；发布数据是合成的。

主要结论都有断言：

  • 后台派发返回的是 started subagent <id> 一行，3 条通知的结尾文本和父 agent 的轮数；
  • 可继续子 agent 任务后的 send_message 说明，前台子 agent 没有；
  • 父 agent 在跑时通知落在同一轮里，父 agent 的请求次数；
  • 释放时盘上已有最后一条事件、通知时子 agent 已不在注册表，send_message 叫回后的请求内容和第 2 条通知；
  • 前台派发的并发数、父 agent 的请求次数；
  • 两种模式下子 agent 都已释放，子会话的模式和状态，以及前台子会话头部的父会话、深度和来源；
  • fork 子 agent 看得到第一轮、看不到第二轮，spawn 子 agent 两轮都看不到；
  • 两个父 agent 和三个子 agent 能否看到回滚工具，以及回滚只真正执行了一次；
  • 运行时说明的开头，子 agent 工具表里仍有 subagent，以及二层委派的报错；
  • agent/created 白名单下父子两边的工具表，子会话的两条委派策略事件和审批结果；
  • 10 个里恰好第 9、10 个失败，池满时前台一次性派发成功，放行后 8 条通知到齐；
  • 两层委派时 8 个孙 agent 恰好第 8 个失败。

另外做了变异检查。以下 8 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • subagent 上加 toolFilter 拉黑回滚工具；
  • 去掉 patrol preset 里的 restrict；
  • subagent 的深度上限改成 2；
  • SubagentRuntime 的 maxActiveSubagents 改成 10；
  • subagent_fork 改走 spawn；
  • 第 4 步一次派 3 个改回后台；
  • 池满时那次前台派发改回后台；
  • subagent_deep 的深度上限改成 1。

连续 5 次运行，以及 4 个进程并发运行，输出都一致。
