第 25 / 36 节 · 发布规则实战

候选规则在 9 次部署上回放，放宽窗口的第 2 版少失败 4 次，也误拦了 1 次成功部署。送去审批时，应答者收到的请求里没有调用参数。

上一篇从会话日志里挖出了候选规则，存成了新版本但没有生效。这一篇是规则进化的最后一步，候选先在固定数据集上回放评测，经人确认后才生效；每一版规则的来源、评测结果和审批结果都能查回去。

这次写一个回放评测函数，把日志里的部署按时间重放一遍，统计候选规则“少失败几次、误拦几次成功部署”；再写一个 activate_rule 工具，它的 tools/pre-execute 监听器先算评测，再返回 ask，走 dsh 的审批服务交给人决定。最后把版本表、评测表和会话日志里的审批事件拼成规则谱系。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 第 2 版回放少失败 4 次、误拦成功 1 次，审批被拒；
  • 应答者收到 5 个字段，不带调用参数，要按 callId 回日志查；
  • 被拒时模型只收到一句固定的话，没有错误码和原因；
  • 卸掉审批服务后，模型收到的错误就是 ask 的 reason。

回放评测显示放宽窗口会误拦成功部署

数据还是三天值班的会话日志，比第 23 篇多了一个版本：2.5 第 1 天失败两次，第 2 天平台恢复，部署成功：

== 1. 数据：三天值班，2.3 每天失败，2.5 第 1 天失败两次、第 2 天成功 ==
数据集 12-8d9fa519：12 次调用，执行 9 次（失败 8、成功 1），被规则拒绝 3 次

输出里的 12-8d9fa519 是数据集的标识：挖掘模块沿用第 23 篇，读回的记录就是数据集，用记录数加事件编号的哈希标识它。

接着让三个版本的规则在这份数据集上各回放一遍：

== 2. 回放评测：同一份数据集，三个版本的规则 ==
 24 小时内失败 2 次：少失败 0 次，误拦成功 0 次
168 小时内失败 2 次：少失败 4 次，误拦成功 1 次
168 小时内失败 3 次：少失败 3 次，误拦成功 0 次
  • 第 1 版（24 小时内失败 2 次）是现在生效的规则，在这份数据上什么也没拦住：日志里的 9 次部署本来就是它放行的。
  • 第 2 版是第 23 篇的候选，窗口放宽到 7 天，能少 4 次失败，但会误拦 2.5 第 2 天那次成功部署：前一天的两次失败还在窗口里。
  • 第 3 版把阈值提到 3 次，少失败 3 次，不误拦。

回放按平台时间把“执行”过的部署逐条过一遍规则：规则会拦的，按它原本的结果计为“少失败”或“误拦成功”，并且不再进入后面的历史；规则放行的，保留原结果。

回放依赖的前提都是 demo 的简化：

  • 被拦的部署不会换一种方式再发；
  • 没被拦的部署，结果和日志里一样；
  • 日志里被现行规则拒绝的调用没有结果，不参与回放。候选如果在某处比现行规则宽松，会放行这些调用，回放看不到（第 3 版就会放行第 1 天的第三次 2.3）。

真实情况里，被拦之后 agent 可能改版本号、改服务，结果也可能不同。回放的数字是在这些前提下的估计，不是保证。

图：pre-execute 先回放评测、写评测表，再返回 ask 交审批；第 2 版被拒，第 3 版生效。

启用走审批，请求里没有调用参数

activate_rule 的 pre-execute 监听器算完评测写进评测表，再返回 { kind: 'ask', reason }。工具流水线收到 ask，交给审批服务（packages/core/tools/src/index.ts:1698-1738），审批服务再发给应答者，即 approval/request 上的监听器。

demo 的应答者是脚本化的审批人：回放里有误拦就拒绝，没有就批准。评审会话里，脚本化模型先申请启用第 2 版，被拒后提交阈值为 3 的第 3 版，再申请启用：

== 3. 启用走 dsh 的审批：pre-execute 返回 ask ==
应答者收到 [agent, callId, reason, signal, toolName]
  按 callId 回会话日志查到参数：{"ruleId":"same-version-failed","revision":2}
  reason：启用 same-version-failed@2：数据集 12-8d9fa519 的 9 次部署回放，少失败 4 次、误拦成功 1 次
  决定：rejected
应答者收到 [agent, callId, reason, signal, toolName]
  按 callId 回会话日志查到参数：{"ruleId":"same-version-failed","revision":3}
  reason：启用 same-version-failed@3：数据集 12-8d9fa519 的 9 次部署回放，少失败 3 次、误拦成功 0 次
  决定：allowed-once
工具结果 1：失败 Error: the user rejected tool "activate_rule"
工具结果 2：成功 已保存为候选 same-version-failed@3，未生效
工具结果 3：成功 已启用 same-version-failed@3

应答者收到的字段只有 agent、callId、reason、signal、toolName（packages/interaction/user-approval/src/types.ts:63-74），请求里没有调用参数。

同进程的应答者可以拿 callId 去 req.agent.session 的日志里找 tool/call 事件，读出参数，第 3 步输出的第二行就是这样查到的。

请求里能直接展示给人的文字只有 reason。要启用哪一版、评测结果如何，最好由宿主自己算好写进去，不要用模型在对话里的转述。

被拒的那次，模型收到的是 Error: the user rejected tool "activate_rule"，没有错误码，也没有拒绝原因。demo 里模型接着提第 3 版是脚本安排的，真实模型要靠别的途径知道“误拦”才是问题。

谱系靠版本表、评测表和日志拼出来

规则的来源、评测结果和审批结果分散在三个地方：规则存储里的版本表和评测表，以及评审会话日志里的审批事件。

审批服务在会话里追加 approval/asked（含 callId、reason）和 approval/decided（packages/interaction/user-approval/src/index.ts:218-225）。评测表的键也含 callId，两边按它对上：

== 4. 规则的谱系：版本表、评测表和会话日志拼起来 ==
@1 24 小时/2 次：人工录入：同一版本 24 小时内失败 2 次就拦；证据 0 条
@2 168 小时/2 次：第 23 篇的候选：窗口放宽到 7 天；证据 6 条
   评测 rule-review#call-13：少失败 4、误拦 1；审批 rule-review#11 -> rejected
@3 168 小时/3 次：阈值提到 3 次，避免误拦平台抖动；证据 6 条
   评测 rule-review#call-15：少失败 3、误拦 0；审批 rule-review#23 -> allowed-once
当前生效：same-version-failed@3
日志里 approval/decided 的字段：[id, outcome]

第 2 版带着第 23 篇的 6 条证据，评测后被拒；第 3 版评测通过后批准，成为生效版本。rule-review#11、#23 是审批请求在日志里的位置，和第 23 篇的证据编号一样可以回查。

评测表的键是 <会话 id>#<callId>，因为 callId 跨会话不保证唯一；同一会话里是否会重复，本篇的单进程 demo 没有遇到（按源码，未实测）。

第 4 步最后一行是日志里 approval/decided 的全部字段：只有 id 和 outcome，不记审批人是谁，要追责得由应答者自己另行记录。

评测在返回 ask 之前就写入，没到审批人手里的调用也会留下一条评测，谱系里找不到对应审批事件时显示 -。

谱系不单独存表，由版本表、评测表和会话日志拼出来。审计事件已经在日志里，再抄一份就多了一个会不一致的副本。代价是会话日志也要长期保留。

第 4 天再部署，2.3 被拦、2.5 照常上线

第 3 版生效后，直接调用部署工具（不经过模型）再发一次两个版本：

== 5. 生效之后：第 4 天再部署 ==
deploy(2.3) -> 拒绝 [same-version-failed@3] payment-api 2.3 在 168 小时内已失败 6 次
deploy(2.5) -> 执行 {"service":"payment-api","version":"2.5","outcome":"succeeded"}

2.3 在 7 天内已失败 6 次，被第 3 版拦下；2.5 只在第 1 天失败过两次，没到 3 次，照常部署成功。输出里去掉了随时钟变化的 at 字段。守卫的判断和回放一致：两处按同一条规则计数，都是窗口内失败次数达到阈值就拦（demo 里是两份相同的写法，不是同一个函数）。

卸掉审批服务，模型收到的是 reason 本身

审批服务在场时，先让应答者依次给出几种结果，再把会话策略改成 never，最后在最外层挂一个直接 allow 的 pre-execute 监听器：

== 6. 审批服务在场：应答者的几种结果、never 策略、前置 allow ==
应答者返回 cancelled -> 失败 Error: approval for tool "activate_rule" was cancelled（问了应答者 1 次）
应答者返回 unavailable -> 失败 Error: tool "activate_rule" requires approval, but no approval channel is available（问了应答者 1 次）
应答者抛错 -> 失败 Error: tool "activate_rule" requires approval, but no approval channel is available（问了应答者 1 次）
应答者返回未知值 'maybe' -> 失败 Error: tool "activate_rule" requires approval, but no approval channel is available（问了应答者 1 次）
会话策略改成 never -> 失败 Error: the user rejected tool "activate_rule"（问了应答者 0 次）
最外层再挂一个直接 allow 的监听器 -> 成功 已启用 same-version-failed@3（问了应答者 0 次）
  评测表条数没变：true

前四行里只有 cancelled 有自己的理由；应答者返回 unavailable、抛错、返回未知值，模型收到的是同一句“no approval channel is available”（tools/src/index.ts:1694-1696）。

never 策略不问应答者，模型收到的和人拒绝一字不差，分不出是人拒了还是策略拒了。最外层的 allow 让本篇的 ask 根本没执行：应答者没被问，评测表也没多一条，第 9 篇实测过的 waterfall 绕过在这里同样成立。

最后试两种审批不在场的情况：

== 7. 审批不在场 ==
不经过 agent 直接调 activate_rule：
  拒绝 tool "activate_rule" requires approval, but the call has no agent to route it through
卸掉审批服务后经 agent 调 activate_rule，模型收到：
  Error: 启用 same-version-failed@1：数据集 12-8d9fa519 的 9 次部署回放，少失败 0 次、误拦成功 0 次
生效仍是：same-version-failed@3

不经过 agent 直接调用时，流水线不调审批服务，直接拒绝（tools/src/index.ts:1711），理由里写明调用没有 agent 可走审批；这次调用不会留下审批事件，但本篇的 pre-execute 已经写了一条评测。

卸掉审批服务后，再经 agent 申请回滚到第 1 版，也被拒绝了，规则没有变。但模型收到的错误文字是 ask 的 reason 本身，也就是那句评测摘要。

流水线在没有审批服务时用 ask.reason ?? '...requires approval (not yet supported)' 作为拒绝理由（tools/src/index.ts:1703-1706）：给了 reason，默认那句“需要审批”就不出现了。模型看到一句评测说明加 Error: 前缀，看不出这是没有审批通道。

这对 Agent 意味着什么

评测要在固定数据集上做，并写明前提。本篇的数据集有标识，评测结果和它绑定；回放只是在“被拦不重试、结果不变”前提下的估计。

审批请求不带调用参数，能直接展示给人的文字只有 reason，要启用什么、评测结果如何，都该由宿主算好写进去。没有审批服务时，reason 会原样变成拒绝理由，所以它还得能单独当拒绝理由读。

人拒绝时模型只收到一句固定的话，never 策略下也是同一句，被拒的原因要另想办法让模型知道。审批监听器要挂在 pre-execute 的最外层：更外层的监听器直接 allow，本篇的 ask 和评测都不会执行，应答者也不会被问到。

谱系靠日志拼：版本表存规则和证据，评测表存评测，审批记录留在会话日志里，按会话和 callId 对上。

本文的验证范围

实测部分是 rules-review-demo.ts，配合规则存储 rule-store.ts（沿用第 22–23 篇，加了评测表）、日志挖掘 log-miner.ts（沿用第 23 篇）和回放评测与启用 evaluate.ts。

脚本挂载真实的会话存储与 JSONL 持久化、dsh-session-query-sqlite、工具流水线、agent 循环、存储三件套和 dsh-user-approval。模型和审批人都是脚本化的：模型每一步调哪个工具是预先写好的，审批人按 reason 里有没有误拦决定。发布平台和时钟是合成的。日志和数据写在系统临时目录，脚本退出时删除。

前几篇的脚本化模型按“最后一条消息来自用户”判断新一轮，审批服务注入的运行时上下文让它失效，本篇改成按“最近一条用户消息之后还没有回复”判断。

主要结论都有断言：

  • 数据集 12 次调用、执行 9 次；三个版本的回放结果依次是 0/0、4/1、3/0；
  • 应答者收到两次请求，第一次的字段与按 callId 查到的参数、第 2 版被拒、第 3 版被批准，生效版本为第 3 版；
  • 第 4 步时评测表有两条，审批结果依次是 rejected、allowed-once，approval/decided 的字段只有 id、outcome；
  • 第 4 天 2.3 被第 3 版拦下，2.5 部署成功；
  • 应答者返回 cancelled、unavailable、抛错、未知值时模型收到的四句话，每次都问了应答者；
  • never 策略下模型收到的与人拒绝相同、应答者未被问；最外层 allow 让启用成功、应答者未被问、评测表条数不变；
  • 卸掉审批服务后申请启用失败，生效版本不变。

另外做了变异检查。以下 6 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • 审批人一律批准；
  • pre-execute 返回 allow 而不是 ask；
  • ask 不带 reason；
  • 回放时忽略时间窗口；
  • 不写评测表；
  • 规则存储的守卫不再拒绝（数据集在第 1 步就变了）。

连续 5 次运行，以及 4 个进程并发运行，输出都一致。

完整代码：GitHub 示例仓库，固定到提交 ad4082d。

前提是 dsh 仓库已 pnpm install 并完成构建（各包导出指向构建后的 lib/）。

在 dsh 仓库根目录获取并运行：

mkdir -p scratch-plugin
git clone https://github.com/costa92/deepseek-harness-demo.git scratch-plugin/deepseek-harness-demo
git -C scratch-plugin/deepseek-harness-demo checkout --detach ad4082d
cp -R scratch-plugin/deepseek-harness-demo/rules-review-demo scratch-plugin/rules-review-demo
