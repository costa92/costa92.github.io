第 19 / 36 节 · Agent 编排

巡检目标列了 5 个服务，模型只查了 2 个就调 update_goal 标记完成，没有任何东西拦它。一条人类消息之后，会话能自动续跑 5 轮，完成与否全凭模型自己说。

第 16 篇看到，一轮对话里模型可以一直调工具，循环没有步数上限。本篇看一轮结束以后由谁开下一轮：packages/goal 给会话挂一个持久的目标，由续行驱动器在 agent 空闲时自动开新的一轮，直到目标完成、受阻或用完轮数。

这次给会话一个目标“巡检 5 个服务最近一次发布，找出失败的”，看它怎么一轮一轮跑完；再让模型只查 2 个服务就宣布完成、在第 1 轮就报受阻、一直不收尾；最后在巡检中途关掉进程，看恢复后会不会自己接着跑。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 一条人类消息之后，驱动器自动续跑了 5 轮；
  • 只查 2 个服务就标记完成，照样被接受；
  • 受阻门槛只看轮次编号，第 3 轮首次报受阻也被接受；
  • 恢复后目标仍是 active，续行关闭，要人说“继续”。

goal 只存状态，续跑靠驱动器

goal 组有四个包，本篇用到其中三个：

  • dsh-goal 提供 ctx.goals，每个会话最多一个当前目标。它只存状态，不调度工作。每次变更都往会话日志追加一条 goal/change，日志是唯一的持久存储。
  • dsh-tool-goal 给模型三个工具：get_goal、create_goal、update_goal。
  • dsh-goal-round-driver 是续行驱动器：agent 空闲、目标是 active、续行已启用（armed）、轮数还有剩余时，往收件箱里排一条 <goal_round> 提示，开下一轮。

第四个包 dsh-command-goal 是给人用的 /goal 命令，本篇未用。基础组合（base bundle）的宿主层挂了 dsh-goal、驱动器和 /goal 命令，tool-goal 也在（按源码，未实测；packages/bundle/base/cordis.patch.yml:299-306、:423-424）。

Web 组合把 tool-goal 和 command-goal 两行都关掉（packages/bundle/web-app/cordis.patch.yml:440-444），改由 standard 等 preset 提供（按源码，未实测）。

目标有四个持久阶段：active、paused、blocked、complete。另有一个只在进程内的开关 activation，取值 armed 或 disarmed，决定驱动器能不能自动开下一轮。它不写日志，这一点在“恢复后目标还在，续行开关没了”一节会用到。

一条人类消息，自动跑了 5 轮

脚本给会话发一条人类消息“巡检一下所有服务最近一次发布”。脚本化模型在这一轮里调 create_goal，给出目标和 max_goal_rounds: 8。

之后每一轮查一个服务，第 5 轮查完最后一个，先 get_goal 拿到 id 和 revision，再 update_goal 标记完成：

== 1. 巡检：一条人类消息，之后自动续跑 ==
第 1 轮的续跑提示（节选）：
  <goal_round>
  Objective: "巡检 5 个服务最近一次发布，找出失败的"
  Round: 1/8
  ……共 587 个字符
lookup_release -> order-api: demo-007 succeeded
lookup_release -> payment-api: demo-003 failed, rolled back
lookup_release -> user-api: demo-011 succeeded
lookup_release -> search-api: demo-005 succeeded
lookup_release -> notify-api: demo-009 succeeded
人类 1 条消息，轮次 6 个，其中 goal round 1,2,3,4,5
结束：phase=complete rounds=5/8 activation=disarmed
complete 之后，tool-goal 给模型追加一条收尾提示：
  The goal is marked complete and this autonomous run is ending.
另一会话：驱动器排进第 1 轮的同时，插进一条插件消息
  第 1 轮 goal 消息排队 2 次，领取顺序：user, goal round 1, plugin, goal round 1, plugin
  日志里的消息：user, plugin, goal round 1, plugin
  结束：phase=complete rounds=1/8 activation=disarmed

一条人类消息之后跑了 6 轮：人类那一轮创建目标，后面 5 轮全是驱动器开的。

驱动器的触发点是 agent/status 变成 idle（packages/goal/goal-round-driver/src/index.ts:258-260）。每次空闲，它检查目标，排一条 goal 来源的用户消息（:192），提示词由 prompt.ts 渲染：目标、Round: 当前/上限，后面是一段固定的工作指令。

goal 消息在 agent/pre-step 里还要过一道校验：必须是驱动器刚预留的那一条，目标的 id、revision 和轮次编号都对得上，否则拒绝这一步。

第 16 篇提到，驱动器拒绝前会把同一步领到的其他消息放回收件箱（restoreOtherClaimed，goal-round-driver/src/index.ts:379），就发生在这里。

输出最后四行是另一个会话：驱动器刚排进第 1 轮，脚本就插进一条插件消息。两条被同一步领走，goal 消息被拒，插件消息放回后先跑了一轮；驱动器再排一次第 1 轮，所以排队 2 次。

roundsStarted 只在 goal 消息进入步骤（记成 user/message）时加一，被拒的那次不算：日志里只有一条第 1 轮，结束时是 rounds=1/8。

第 5 轮里模型标记完成后，tool-goal 用 deferContext 追加一条 <goal_complete> 提示（packages/goal/tool-goal/src/index.ts:321），要求模型写一段收尾说明、不再调工具。

脚本断言了这条消息来自 tool-goal 插件。目标变成 complete 以后，驱动器不再开新的一轮，脚本里的模型回复也正好用完。

图：人类那一轮创建目标并启用续行，agent 每次空闲驱动器就排一条 goal round，直到完成、受阻或轮数用完。

只查了 2 个服务就宣布完成

同样的目标，这次模型第 2 轮查完 payment-api 就调 update_goal complete：

== 2. 只查了 2 个服务就宣布完成 ==
查过的服务：order-api, payment-api（清单共 5 个）
update_goal complete 被接受：phase=complete rounds=2/8 activation=disarmed

第 2 行显示 complete 被接受了。权限检查只确认调用来自人类直接消息，或者来自当前这一轮 goal round，也就是 goal 消息的 id、revision、轮次编号和当前目标一致（packages/goal/tool-goal/src/authority.ts:111 起）。

权限检查通过后，update_goal 直接调 ctx.goals.complete()，服务层只核对 revision 和阶段能不能转换（packages/goal/goal/src/index.ts:391）。两处都不涉及证据。README 的已知限制直说“没有独立评估器”，完成与否由调用方决定。

约束完成的只有提示词里一句“Before claiming completion, gather evidence that the whole objective is achieved”，和工具指引里的“Mark complete only when the objective is actually achieved”。

受阻门槛看的是轮次编号

tool-goal 有一个配置 blockedAfterConsecutiveRounds，默认 3。工具指引对模型说的是：同一个受阻条件连续持续 3 轮以后才能标记 blocked。

脚本让模型第 1 轮报受阻，第 2 轮不报，第 3 轮再报：

== 3. 报告受阻：门槛看的是轮次编号 ==
第 1 轮报受阻 -> Error: blocked requires at least 3 consecutive goal rounds; current round is 1
第 2 轮没有报受阻
第 3 轮再报一次 -> 接受（中间第 2 轮没报，谈不上连续）
  phase=blocked rounds=3/8 activation=disarmed reason=model-reported
另一会话前两轮都不报，第 3 轮第一次报 -> 接受
  phase=blocked rounds=3/8 activation=disarmed reason=model-reported
人类那一轮直接要求标记受阻 -> 接受：phase=blocked rounds=0/8 activation=disarmed reason=model-reported

机械检查就是这一个条件（tool-goal/src/index.ts:306-313）：

if (args.action === 'blocked' && authority.kind === 'goal-round'
  && authority.goal.roundsStarted < resolved.blockedAfterConsecutiveRounds) {
  throw new HarnessError(
    `blocked requires at least ${resolved.blockedAfterConsecutiveRounds} consecutive goal rounds; `
    + `current round is ${authority.goal.roundsStarted}`,
    'GOAL_TOOL_BLOCK_THRESHOLD',
  )
}

比较的是当前轮次编号，不是“连续报了几次受阻”。条件里的 authority.kind === 'goal-round' 表示门槛只管驱动器开的轮次；人类直接要求停下时，可以在任何一轮标记受阻：输出末行，人类那一轮里模型建完目标就报受阻，rounds=0/8 也被接受。

只要到了第 3 轮，模型第一次报受阻也会被接受，脚本用另一个会话验证了这一点。“同一个条件是否持续”由模型自己判断，tool-goal README 在已知限制里写明了（packages/goal/tool-goal/README.zh.md:150）。受阻原因以代码 model-reported 写进日志。

轮数上限由模型给出

目标创建时带一个轮数上限。驱动器每次开新一轮前检查：roundsStarted 已经达到上限，就把目标标记为受阻，代码 round-limit（goal-round-driver/src/index.ts:166-172）。

让模型一直不收尾，上限设为 3：

== 4. 模型一直不收尾：轮数上限 ==
max_goal_rounds 由模型在 create_goal 里给出，这里是 3
第 3 轮后：phase=blocked rounds=3/3 activation=disarmed reason=round-limit
  Goal reached its configured limit of 3 rounds.

上限是 create_goal 的可选参数 max_goal_rounds，由模型填写。服务端只要求它是正的安全整数（goal/src/index.ts:199），没有上界（按源码，未实测）。不填时用部署配置 defaultMaxGoalRounds，默认 256，基础组合没有改它（按源码，未实测）。

第 16 篇说过，一轮里的步数也没有上限。README 同样写明：上限只数轮数，不计 token、费用和时间。

恢复后目标还在，续行开关没了

第 12 篇看过会话在崩溃后怎么恢复，这里接上 JSONL 持久化，并和基础组合一样挂上 session-checkpoint-policy（bundle/base/cordis.patch.yml:398-399），在第 2 轮查 payment-api 的工具执行中途销毁整个 Context，再在新的 Context 里恢复同一个会话：

== 5. 巡检到一半销毁 Context，恢复后不会自己续跑 ==
卡在第 2 轮查 payment-api：phase=active rounds=2/8 activation=armed
  此时盘上的日志已有第 1、2 轮的 goal 消息（checkpoint 插件在模型请求前刷了盘）
从第 1 轮结束处 fork：phase=active rounds=1/8 activation=disarmed
  插件消息让 fork 跑完一轮再空闲：goal round 仍是 1
新 Context 恢复会话：phase=active rounds=2/8 activation=disarmed，agent 状态 idle
  第 2 轮的 lookup_release 结果被补写为：
    The tool call was interrupted after it was recorded, but no result was durably recorded.
插件消息那一轮，模型 update_goal resume -> Error: this goal operation requires a direct human turn on a top-level agent
插件消息让 agent 跑完一轮再空闲：模型请求 3 次，goal round 仍是 1,2
人类说“继续”，模型 update_goal resume 之后：goal round 1,2,3,4,5,6
  结束：phase=complete rounds=6/8 activation=disarmed；被中断的第 2 轮计入轮数
子进程不挂 checkpoint 插件，卡在第 2 轮时：phase=active rounds=2/8 activation=armed
  SIGKILL 后在本进程恢复：phase=active rounds=1/8 activation=disarmed，日志里只有第 1 轮

先看前两行：卡住时，脚本直接读盘上的日志，断言第 1、2 轮的 goal 消息都已落盘；括号里那句是脚本打印的说明，不是断言。

fork 那两行是趁卡住时，按 session-controller 的写法从第 1 轮结束处 fork 出一个会话。fork 出来的目标同样是 disarmed，跑完一轮插件消息也没开新的 goal round。

恢复后，目标还是 active，轮数也在，因为它们都从日志回放出来。第 12 篇讲过的补写也发生了：第 2 轮那次 lookup_release 没有结果落盘，恢复时被补成一段“调用中断、结果未知”的说明。

activation 变成了 disarmed。它只存在内存里，新 Context 里的初始值就是 disarmed，goal 服务还会在每个 agent/created 上再关一次（goal/src/index.ts:484-493；:255-257）。

只看“恢复后模型没收到请求”还不够：恢复出来的 agent 直接是 idle，不会产生空闲事件，驱动器这时根本没被唤起。

脚本于是发一条插件来源的消息，让 agent 跑完一轮、重新进入空闲。模型在这一轮里试着 update_goal resume，被拒：要求人类直接发起的一轮。驱动器被唤起了，但目标是 disarmed，它在 drive() 里直接返回（goal-round-driver/src/index.ts:165），没有开新的 goal round。

人类消息“继续”发出后，模型调 update_goal resume。resume 要求这一轮里有人类直接发的消息（tool-goal/src/authority.ts:80-84），插件消息那一轮已经验证过，模型自己恢复不了。

之后又跑了 4 轮，把剩下的服务查完。脚本化模型在第 3 轮重查了 payment-api，这是脚本的安排，不是 dsh 替它重试。被中断的第 2 轮已经算进了轮数，所以总共用了 6 轮。

最后两行换成真杀进程：同一脚本起一个子进程，不挂 checkpoint 插件，卡在第 2 轮时 SIGKILL。恢复后只剩 rounds=1/8，第 2 轮的 goal 消息没落盘，少算了一轮。

这对 Agent 意味着什么

实测只查了 2 个服务就标完成，照样被接受，dsh 把完成的判断交给了模型。巡检这类有明确清单的目标，得由使用方自己对照清单检查完成证据，dsh 不做这一步。

轮数上限也握在模型手里：max_goal_rounds 由模型在 create_goal 里给出，设为 3 时，第 3 轮后目标以 round-limit 受阻，续行随之关闭。

会话恢复之后，目标不会自己继续，要人类说一声“继续”，模型才能 update_goal resume。定时巡检这类无人值守的场景，重启后由谁来恢复，要事先考虑进去。

本文的验证范围

实测脚本 goal-demo.ts 挂载真实的 dsh-goal、dsh-tool-goal、dsh-goal-round-driver、dsh-agent-loop、dsh-tools、dsh-system-prompt、会话投影、JSONL 持久化（临时目录）和 dsh-session-checkpoint-policy。

模型是脚本化模型，每一轮的动作是预先写好的；发布数据是合成的。恢复场景（第 5 步）的主线是在同一个 Node 进程里销毁整个 Context 后重建；真杀进程的对照是子进程被 SIGKILL，再由父进程恢复。

主要结论都有断言：

  • 各场景的阶段、轮数、续行状态和受阻代码；
  • goal round 编号序列和轮次数；
  • 查过的服务；
  • 第 1 轮受阻被拒的错误文本，以及第 3 轮首次报受阻被接受；
  • 第 1 轮提示词的开头和收尾提示的来源；
  • 插话时 goal 消息的排队次数、领取顺序、日志顺序和轮数；
  • 人类那一轮标记受阻被接受，插件消息那一轮 resume 被拒的错误文本；
  • fork 出的目标状态与 goal round，SIGKILL 后恢复的轮数与日志；
  • 中断时盘上已有的 goal 轮次、恢复后补写的工具结果；
  • 恢复后经过一次空闲仍没有新的 goal round。

断言之外，有一个示例脚本不含的手动变体（按文中命令复现不了）：去掉 dsh-session-checkpoint-policy 再跑，“第 1、2 轮都已落盘”的断言失败，盘上只有第 1 轮；销毁 Context 时还会再刷一次盘，所以恢复后仍能看到第 2 轮。

行为与文中不符时脚本以非零退出码结束。连续 5 次运行，输出都一致。
