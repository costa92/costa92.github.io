第 15 / 36 节 · 能力、工具与会话

值班会话里搜 demo-003，搜出 3 个会话；搜句子里的“回滚”，一个也搜不到。搜出的会话里还有一个从没提过 demo-003，命中来自 fork 时继承的日志。

前几篇都在看一个会话内部：日志怎么写、崩溃后怎么补、上下文满了怎么压缩。会话多了以后，问题变成另一种：demo-003 出事那天，值班同事在哪几个会话里讨论过它？哪个会话是从哪个会话 fork 出来的？

这次先用真实的 agent 循环写出 5 个会话，其中 3 个是 fork，再在一个全新的 Context 里只凭磁盘上的日志，用 ctx.sessionQuery（packages/session-query）跨会话搜出“所有提到 demo-003 的会话”，并追踪它们的谱系。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 搜 demo-003 命中 3 个会话，其中 1 个只靠 fork 继承的日志；
  • 搜“回滚”“健康检查”0 命中，整段“已自动回滚”命中 3 个；
  • 删掉根会话日志后，谱系标为 complete: false；
  • readSession() 读 fork 子会话一律抛错，活着的也一样。

全文搜索来自单独挂载的 SQLite 后端

跨会话查询集中在 ctx.sessionQuery 这一个服务上，按第 8 篇讲的 seam 模式拆开：

  • dsh-session-query 是 Service Definition。精确读取、列表过滤、谱系追踪、事件关系这些不依赖搜索引擎的功能，直接在这一层实现；
  • 全文搜索 searchSessions()、searchEvents() 是抽象方法，由后端实现。仓库里的实现是 dsh-session-query-sqlite，用 Node 自带的 node:sqlite 建一个 FTS5 索引。

插件默认 openAt: startup，启动时就打开索引；基础组合（base bundle）把它改成了 path: ':memory:'、openAt: never，全文搜索默认关闭（packages/bundle/base/cordis.patch.yml:136-140）。

脚本第 6 步按同样的配置挂一个查询后端：

6. the base bundle config: search refused, exact reads and lineage still served
  base/cordis.patch.yml: - id: session-query-sqlite | name: '@deepseek-ai/dsh-session-query-sqlite' | config: | path: ':memory:' | openAt: never
  rows naming dsh-tool-session-query in the same file: 0
  searchSessions -> SESSION_QUERY_SEARCH_DISABLED; searchEvents -> SESSION_QUERY_SEARCH_DISABLED
  readSurface(oncall-payment-rca): inheritedEventCount=16; traceSession(oncall-order-idle): ancestors ["oncall-order"] complete=true

看第 3 行：两个搜索调用都以 SESSION_QUERY_SEARCH_DISABLED 失败，精确读取和谱系追踪照常返回（两个会话的来历见“fork 子会话因继承的日志被一起搜出”）。按配置里的注释，Web 侧栏的搜索这时只匹配标题和工作区名（按源码，未实测）。

部署方要用内容搜索，得在 profile 里把 openAt 改成 first-search 或 startup，并给一个持久的 path（按源码，未实测）。实测脚本不走基础组合，直接挂插件并给一个文件路径，用的是插件默认的 startup。

同一族里的 dsh-tool-session-query 给模型提供搜索、追踪、读取会话历史的工具，按工作区授权；第 6 步的第 2 行显示它不在基础组合里。

索引是专用的派生数据库，和会话日志分开存放。建索引时 live 优先：进程里活着的会话用内存里的版本，其余的从持久化读取，第 10 步有实测。

进索引的文本由 extractSessionEventText()（packages/session-query/session-query/src/extraction.ts:15）决定：用户和助手消息、工具调用名和参数、工具结果（含错误名和错误码）、待办事项，以及出错、中断等轮次结束状态；推理块、request/header 等结构事件不进。

图：搜索前对账磁盘、增量更新 FTS5 索引，命中可溯至工具调用；谱系读会话头部 parentSession。

fork 子会话因继承的日志被一起搜出

脚本第一段用脚本化模型跑出 5 个值班会话：

  • oncall-payment：查 payment-api，工具返回 demo-003 失败、已自动回滚；
  • oncall-order：查 order-api，和 demo-003 无关；
  • oncall-payment-rca：从 oncall-payment fork，追问回滚后要不要重新发布；
  • oncall-payment-review：从 oncall-payment-rca 再 fork，让它写复盘；
  • oncall-order-idle：从 oncall-order fork 之后什么也没做，第 5 步要用。

同一段还写了 3 个会话留给后面的步骤：工具结果被剪枝的 oncall-search-api，以及分属两个工作区的 ws-a-deploy、ws-b-deploy，内容都不含 demo-003 和“回滚”。

fork 的做法和第 12 篇一样，照 session-controller 的方式把父日志到最后一个 turn/end 作为种子。然后关掉 Context，换一个新的，只挂持久化和 SQLite 查询后端：

1. which sessions mention demo-003?
  oncall-payment-rca     best seq 23 assistant/message own       "先修复健康检查，再重新发布 demo-003。"
  oncall-payment-review  best seq 23 assistant/message inherited "先修复健康检查，再重新发布 demo-003。"
  oncall-payment         best seq 13 assistant/message own       "demo-003 在灰度阶段健康检查失败，已自动回滚。"

每行是一个会话：searchSessions() 按会话分组，每个会话只返回匹配最强的一条事件（bestMatch），附一段按字符截断的摘录。

三个会话被搜出来，oncall-order 没有。第二行的 oncall-payment-review 自己从没提过 demo-003，它的最佳命中 seq 23，是 fork 时从父会话复制过来的那条助手消息。fork 子会话的日志开头是父日志截至最后一个 turn/end 的副本（第 12 篇），索引也就照样收录。

“own / inherited”这一列是脚本自己算的：用 readSurface() 拿到每个会话的 inheritedEventCount，命中的 seq 小于它就是继承来的。搜索接口本身不做这个区分。

事件过滤条件只有 seq、时间、类型、surface 和文本几类，没有“只看自己写的事件”这一项（按源码，未实测；packages/session-query/session-query/src/types.ts:215-219）。要回答“谁自己讨论过 demo-003”，调用方得自己过滤。

中文词在句子里不是 token

再搜几个中文词：

2. Chinese words inside a sentence are not tokens
  searchSessions("回滚"        ) -> 0 session(s)
  searchSessions("健康检查"      ) -> 0 session(s)
  searchSessions("已自动回滚"     ) -> 3 session(s)
  searchSessions("灰度阶段健康检查失败") -> 3 session(s)
  filterEvents(oncall-payment, text "回滚") -> seqs [10,13] (tool/result, assistant/message)

“回滚”和“健康检查”明明出现在好几条消息里，却一个会话都搜不到；搜“已自动回滚”或“灰度阶段健康检查失败”这种整段，反而能命中。

FTS5 建表时用的是 tokenize = 'unicode61'（packages/session-query/session-query-sqlite/src/schema.ts:135）。unicode61 按空白和标点切分 token，汉字被当作普通的字母字符。

一句“demo-003 在灰度阶段健康检查失败，已自动回滚。”切出来的 token 是 demo、003、在灰度阶段健康检查失败、已自动回滚，两个标点之间的一整串汉字就是一个 token。

查询文本又会被整体加上引号，当作一个字面短语（quoteFtsData()，packages/session-query/session-query-sqlite/src/query.ts:223），所以只有和某个完整 token 对上才能命中。

“灰度阶段健康检查失败”能命中，是因为工具结果里这段前面是全角冒号（failed：灰度阶段…），在那里恰好是一个独立 token。

按 token 匹配、不按子串匹配，README 写得很明确：“结果匹配 token 与短语，而非任意子字符串”。

设计记录（.agents/notes/archived/feature/2026-07-10-sqlite-session-query-provider.md:32、:51）说明了为什么不用 FTS5 的 trigram 分词器：它不支持少于三个字符的查询，如两个字母的 AI，而且记录里测得的索引约是 unicode61 的 2.1 倍。

记录里承认的代价是 AI 匹配不到 BRAID，整份记录没有讨论中文。对英文来说，这只是“搜不到词的一部分”；对中文来说，却变成了“除非恰好输入两个标点之间的整段原文，否则搜不到”。

换成 trigram 也不能完全解决。

脚本第 7 步绕过 dsh，直接用 node:sqlite 建一张 trigram 表，放进同一句话：

7. the trigram tokenizer (probed directly in node:sqlite) still misses a two-character word
  "回滚" -> 0  "健康检查" -> 1  "自动回滚" -> 1

看“回滚”那一项：两个字不够一个三元组，照样 0 命中；四个字的“健康检查”“自动回滚”才能命中。这次探测只说明分词器本身的行为，dsh 的后端没有 trigram 选项。

第 2 步输出的最后一行是 README 给的替代方案：filterEvents() 的 text 子句对提取出的文本做字面子串扫描，不区分大小写。它找到了 tool/result 和助手消息两条。代价是它只能在一个会话内扫描，要跨会话就得调用方自己遍历所有会话。

搜 demo-003 能命中，是因为连字符是分隔符，demo 和 003 各是一个 token，而且它们前后都有空格或标点。发布单号、服务名这类 ASCII 标识，比中文描述更容易搜到。

根会话日志删掉后，谱系标成不完整

接着追踪谱系，再删掉根会话的日志：

3. lineage: who forked from whom
  oncall-payment (complete=true)
  └─ oncall-payment-rca
    └─ oncall-payment-review
  traceSession(oncall-payment-review): ancestors ["oncall-payment-rca","oncall-payment"] root=oncall-payment
  after deleting oncall-payment's log: complete=false unresolvedParentId=oncall-payment
  searchSessions("demo-003") now -> ["oncall-payment-rca","oncall-payment-review"]

前四行是 traceSession()（packages/session-query/session-query/src/index.ts:327）给出的谱系。它不需要搜索后端，靠每个会话头部记录的 parentSession 拼出：从目标往上是由近及远的祖先链，往下是递归嵌套的后代树。

脚本接着删掉了根会话 oncall-payment 的日志目录。再追踪叶子，结果变成 complete: false，并给出第一个找不到的父会话 id。类型定义里，complete: true 带 root，complete: false 带 unresolvedParentId，二者互斥，调用方不会把一条断掉的链误当成完整的。

最后一行说明索引会跟着磁盘同步：同一个查询服务实例，再搜 demo-003 时，被删掉的会话不再出现。

第 9 步换成新增内容：在另一个 Context 里恢复 oncall-order 并写入 demo-042：

9. reconciliation picks up content written after the first search
  searchSessions("demo-042") -> 0 session(s)
  another context resumes oncall-order and writes demo-042; the same query service now -> ["oncall-order"]

看最后一行：写入发生在首次搜索之后，查询服务没有重建，新内容照样被搜出。README 把这一步叫作对账：每次搜索先列出持久化快照，逐会话比较修订号，只读取新增或变化的日志，在一个事务里更新索引（按 README，未实测）。

一条命中能追回它回答的那次调用

再从 oncall-payment-rca 里的一条命中往回追：

4. from a hit to its neighbourhood: the tool result and the call it answers
  searchEvents(oncall-payment-rca, "failed") -> seq 10 tool/result surface=current
  traceEvent: sourceEventSeqs [9] derivedEventSeqs []
  readEvent window: 9 tool/call | 10 tool/result | 11 step/end

第一行的 searchEvents() 在单个会话内搜。每条命中带着 surface 字段，取值 current、shadowed 或 log-only，这是用和模型历史相同的 foldSurface() 算出来的。第 13 篇里被剪枝遮住的原始内容也能搜到。

第 8 步把剪枝阈值调到 60 个码点：

8. content hidden from the model by pruning is still searchable, marked shadowed
  searchEvents(oncall-search-api, "rollback-window") -> seq 10 tool/result shadowed
  searchEvents(oncall-search-api, "demo-120") -> seq 13 assistant/message current, seq 17 tool/result current, seq 10 tool/result shadowed

看第 1 行：rollback-window 只在被剪掉的中间出现，仍能搜到，命中的是 seq 10 的原始结果，标为 shadowed。demo-120 在开头，剪后的 seq 17 标为 current。被摘要遮住的内容同样标为 shadowed（按源码，未实测）。

traceEvent() 读的是第 12 篇提到的 sourceEventSeqs：这条 tool/result 引用的来源是 seq 9 的 tool/call。

脚本让 readEvent() 取目标事件前后各一条原始事件，前后各能取多少条受配置 readWindowMax（默认 50）限制。从搜索命中到“这个结果是哪次调用返回的”，靠这两个接口就能走通。

readSession() 读不了任何 fork

最后用 readSession() 读每个会话，读到 fork 子会话时直接抛错：

5. readSession() cannot read any persisted fork
  readSession(oncall-order): 16 events
  readSession(oncall-payment-rca): seeded session constructor seed must equal its inherited prefix
  readSession(oncall-order-idle) (forked, never used): seeded session constructor seed must equal its inherited prefix
  readSurface(oncall-payment-rca): 7 surface events, inheritedEventCount=16

普通会话读得出来，fork 子会话全部失败，包括 fork 之后一句话都没说的 oncall-order-idle。同一个会话，readSurface() 能正常读。

readSession() 校验时把整份日志交给 Session.create() 回放一遍（session-query/src/index.ts:184）。create() 以 'snapshot' 模式构造会话（packages/core/session/src/index.ts:517）。

'snapshot' 模式对 fork 的约束是种子必须恰好等于继承前缀（:608-609），这对刚 fork 出来、还没开始跑的会话成立。落盘的 fork 子会话至少还有一条 session/end-seed {inherited: true} 标记，日志一定比继承前缀长，所以必然失败。

同一个类还有 Session.fromRestore()（:535），专门从存储恢复。

agent 恢复会话时带着 eventState 调用 sessions.prepare()，走的就是 fromRestore()，持久化相关的测试读 fork 会话也用它（packages/core/agent-loop/src/index.ts:913，core/session/src/index.ts:1015）。

恢复走的路径和 readSession() 不同，所以 agent 恢复 fork 子会话不受这条校验影响（按源码，未实测），readSession() 却读不了。仓库里没有生产代码调用 readSession()，测试里也没有覆盖 fork 会话的用例。

readSession() 仍是 ctx.sessionQuery 的公开方法，dsh-tool-cordis 的 API 目录（packages/extensions/tool-cordis/src/api-catalog.ts:1990）也收录了它的签名，自己写插件调用它的，遇到 fork 会话会失败。

README 说 readSession 经 Session.create 回放，是为了“复用恢复的校验”（packages/session-query/session-query/README.md:115）。

ctx.sessionQuery 读的是 live 优先的语料，第 10 步在查询所在的进程里建了两个活着的会话：

10. a live session is searched from memory; a live fork fails readSession() too
  unflushed event in oncall-live: on disk false; searchSessions("demo-077") -> ["oncall-live"]; record {"live":true,"persisted":false}
  readSession(oncall-order-live-fork) (live, never flushed): seeded session constructor seed must equal its inherited prefix

看第 1 行：没刷盘的 oncall-live 在磁盘上不存在，却能被搜到，记录标为 live。第 2 行是刚 fork、一次都没刷盘的会话，readSession() 以同一条错误失败，活着的 fork 也读不了。

给模型的查询工具只看同一工作区

dsh-tool-session-query 用调用它的 agent 判断权限：目标会话的 cwd 必须和调用者完全相同（packages/session-query/tool-session-query/src/workspace-access.ts:96）。

第 11 步挂上这个插件，用两个 agent 通过 ctx.tools.execute() 调用：

11. tool-session-query: the caller agent's cwd decides what the model may see
  ws-a-caller   session_search({"query":"demo-201"}) -> Session search results (1): ["ws-a-deploy"]
  ws-a-caller   session_trace({"session_id":"ws-b-deploy"}) -> SESSION_QUERY_TOOL_UNAUTHORIZED: session target is outside the caller workspace
  no-cwd-caller session_search({"query":"demo-003"}) -> SESSION_QUERY_TOOL_UNAUTHORIZED: cross-session search is unavailable because the caller session has no workspace
  no-cwd-caller session_trace({"session_id":"oncall-order"}) -> SESSION_QUERY_TOOL_UNAUTHORIZED: session target is outside the caller workspace

看后两行：no-cwd-caller 和 oncall-* 都没有 cwd，却连跨会话搜索都被拒绝，没有工作区的调用者只能查自己。ws-a-caller 搜 demo-201 只拿到同一工作区的 ws-a-deploy，追踪 ws-b-deploy 被拒。

这对 Agent 意味着什么

默认的 unicode61 分词下，中文句子几乎只能整段匹配，要让中文内容可检索，得留英文或编号锚点。发布单号、服务名、错误码这类 ASCII 标识是可靠的检索入口，写工具输出和提示词时值得保留。

按中文词检索，只能扫描或换后端。已知会话时可以用 filterEvents() 的子串扫描，实测它的 text 子句能在单个会话里找到“回滚”。

给模型开查询工具之前，先把工作区定下来。实测没有 cwd 的会话调用 session_search 直接被拒，同一工作区的会话才互相可见，按项目目录启动会话，模型才查得到以前的工作。

fork 越多，同一段话被跨会话搜出的次数越多，结果得按继承前缀去重。给人看时，可以只保留 seq 不小于 inheritedEventCount 的命中。
