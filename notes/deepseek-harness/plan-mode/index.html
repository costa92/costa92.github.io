第 36 / 36 节 · 扩展与外部接入

值班会话用 /plan 进了计划模式，模型第一步就调了部署工具。平台收到 2.7 并上线，没有拒绝，也没有一条提醒。

第 34 篇看到，写在全局 AGENTS.md 里的“部署前必须审批”可能被仓库指令整份挤掉，只写成文字的规则靠不住。计划模式是另一种写成文字的约束：要求 agent 先出计划，经人批准再动手。

这次让值班 agent 收到“发布 payment-api”时先进计划模式，出一份发布计划，经值班负责人批准再部署，看计划模式激活时模型调部署工具会怎样、计划怎么提交和批准、和守卫与审批怎么叠加，以及重启后计划状态还在不在。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 计划模式下调部署工具照样执行，平台收到 2.7，没有提醒；
  • 批准计划后，同一条回复里的部署仍按计划模式处理；
  • 审批策略切到 never，计划评审照样问人；
  • 回复期间发的 /plan off 同进程下一步生效，重启后丢失。

计划模式只是一段提示词

dsh-plan-mode 在基础组合（base bundle）里默认挂载，唯一的配置是一段英文引导（packages/bundle/base/cordis.patch.yml:308-322）。引导禁止编辑或写文件、改配置，也禁止以其他方式执行计划；准备好后要调 exit_plan_mode 提交完整计划。

插件本身只注册了五样东西（packages/plan/plan-mode/src/index.ts:192-361）：

注册项作用
agent/pre-step 监听在步骤开始前写入待生效的切换
plan:policy 提示词段计划模式激活时渲染引导
plan 会话投影从日志折叠出计划状态
/plan 命令进入或离开计划模式
exit_plan_mode 工具提交计划，经人评审后离开

表里没有 tools/pre-execute 监听，也没有守卫。文件开头的注释写明，沙箱模式和审批策略各自施加限制，不读也不写计划状态（plan-mode/src/index.ts:5-7）。

README 也说得直接：引导控制规划行为，“但每个工具仍然可用”，需要强制限制时请用沙箱模式与审批提示（packages/plan/plan-mode/README.zh.md:12,185）。

exit_plan_mode 在计划模式之外也保持注册，进入或离开只改变提示词段，不改变工具目录（plan-mode/src/index.ts:15-17）。第 17 篇的 preset 用 restrict 把工具从目录里拿掉；计划模式为了请求缓存稳定，一个工具都不拿。

demo 在一个进程里挂 agent 循环、命令服务、用户提问服务和 plan-mode，引导文本从基础组合的配置文件里原样读出，模型换成脚本化模型。宿主组合的关键几行：

await ctx.plugin(CommandRuntime)
await ctx.plugin(UserQuestionService)
await ctx.plugin(PlanModeController, { section: SECTION })
ctx.tools.register(deployRelease)

部署工具在计划模式下照样执行

人发 /plan 先出 payment-api 2.7 的发布计划，脚本化模型第一步就调部署工具：

== 1. 计划模式下，模型直接调部署工具 ==
  /plan 的回执 | Plan mode on. Use /plan off to leave.
  第 1 次请求 | 系统提示含计划引导：true，工具目录 ["deploy_release","exit_plan_mode"]
  deploy_release 的结果 | payment-api 2.7 已上线
  平台收到的部署 ["2.7"]，这一轮 plan-mode 发出的提醒 0 条

看第三、四行：部署正常返回，平台收到了 2.7。部署走的是普通的工具流水线，模型没听引导，plan-mode 也没有任何一环插在流水线里，结果和没开计划模式时一样。

会话空闲时发 /plan，计划状态立即写入日志（plan-mode/src/index.ts:414-434），命令里带的文字再通过 agent.steer() 作为一条用户消息开出这一轮（:253-262）。所以第一次请求就带着引导，工具目录里部署工具和 exit_plan_mode 并列。

用文字回计划、人说“照这个做”，计划模式都不结束

模型也可能不调部署工具，直接用文字回一份计划，再等人点头：

== 2. 不提交计划就结束一轮 ==
  模型用文字回了一份计划 | 这一轮请求 1 次，结束后计划状态 {"active":true}
  人回“可以，照这个做” | 请求仍含计划引导：true，部署结果 payment-api 2.8 已上线
  两轮下来：plan-mode 提醒 0 条，计划状态 {"active":true}

模型不提交计划，这一轮照常结束，没有任何机制催它提交。离开计划模式只有两条路：exit_plan_mode 经评审批准，或人发 /plan off（plan-mode/src/index.ts:236-251,347）。

人回“可以，照这个做”，模型接着部署 2.8，同样执行成功。基础组合的引导专门写了“用户在对话中的同意不批准任何东西，也不结束计划模式”（base/cordis.patch.yml:312）。这句话管的是模型怎么理解，工具层照样放行。

计划要走 exit_plan_mode，批准后下一步才离开

换一个会话，先 /plan，再让模型按规矩提交计划。前两次提交时还没有人接评审，第二步起才挂上脚本化的评审人：

== 3. 用 exit_plan_mode 提交计划：没人应答、标题不对、打回、批准 ==
  /plan（空闲时）| Plan mode on. Use /plan off to leave.
  没人应答评审     | Error: no user-questions answerer accepted the request
  计划用 ## 开头   | Error: exit_plan_mode requires a non-empty markdown plan starting with a # heading
  应答者收到       | header=Plan review，选项 ["Approve","Keep planning"]，intent=plan-review，detail 首行 # payment-api 2.8 发布计划
  打回并附意见     | Error: The user chose to keep planning; their feedback: 先确认 2.7 的回滚方案
  批准             | Plan approved — plan mode exited; carry out the plan starting with your next step.
  批准后的日志     | tool/result → step/end → plan/mode {"active":false} → step/start
  批准后的下一次请求 | 含计划引导：false，工具目录不变：true，plan-mode 提醒 0 条
  部署 2.8         | payment-api 2.8 已上线；计划状态 {"active":false}

从“批准后的日志”那一行看，计划状态在下一步开始前才切换，不是在工具返回时。

  • 没有应答者。 评审走的是用户提问服务 ctx.userQuestions，不是审批服务（plan-mode/src/index.ts:298-318）。服务在、却没人应答时，模型收到的是提问服务的原话（packages/interaction/user-questions/src/index.ts:130-133），里面没提计划模式。
  • 标题只认一级。 计划必须以 # 开头（plan-mode/src/index.ts:295-297），## 发布计划 被拒。
  • 打回。 评审人选 Keep planning 或填了自由文本，模型收到一条带意见原文的错误，计划模式不变（:336-343）。

第 7 步另开一个会话，测评审没得到回答的情况：第一次评审时评审人关掉评审、回到输入框（应答者以 ASK_CANCELLED 拒绝），第二次评审还没回答时 plan-mode 被重载：

== 7. 评审没有得到回答：关掉评审改为发言、评审期间 plan-mode 重载 ==
  评审人关掉评审改为发言 | Error: The user dismissed the plan review to speak instead; stay in plan mode, stop here, and wait for their message.
  评审期间 plan-mode 重载 | Error: the plan-mode service was reloaded while the plan was under review; present the plan again
  这一轮后计划状态 {"active":true}，最后一次请求含计划引导：true

第二行里评审人其实点了批准，结果仍是错误：旧实例已经没有 pre-step 监听来写入“离开”，只能让模型重新提交（plan-mode/src/index.ts:331-335）。两种情况计划模式都不变。

批准时，工具只把“离开”记成进程内的待生效选择，返回 { approved: true }（plan-mode/src/index.ts:347-348）。

下一步开始前的 agent/pre-step 监听才把 plan/mode {"active":false} 写进日志（:192-209,437-449），所以这次请求里引导消失了，工具目录不变。

批准不产生切换通知，因为工具结果已经告诉了模型（plan-mode/src/index.ts:206-208）。人用 /plan 切换时才有通知，见“回复期间的 /plan off，重启后就丢了”。

同一条回复里先提交再部署，部署仍算在计划中

既然 plan-mode 不拦工具，值班组可以自己加一道守卫：部署前读 ctx.planMode.get()，计划模式激活就拒绝：

ctx.tools.guard((exec) => {
  if (exec.name !== 'deploy_release' || exec.agent === undefined) return undefined
  // demo 里还把读到的状态记下来，此处略
  return ctx.planMode.get(exec.agent).active ? '计划模式下不部署，先用 exit_plan_mode 提交计划' : undefined
})

模型先直接部署，再在同一条回复里连发 exit_plan_mode 和部署：

== 4. 自己加一道守卫：计划模式下不许部署 ==
  计划模式中直接部署          | Error: 计划模式下不部署，先用 exit_plan_mode 提交计划
  同一条回复里先提交再部署    | exit_plan_mode：Plan approved；deploy_release：Error: 计划模式下不部署，先用 exit_plan_mode 提交计划
    守卫此刻读到的计划状态 {"active":true,"pending":false}
  下一步再部署                | payment-api 2.9 已上线（守卫读到 {"active":false}）
  平台收到的部署 ["2.9"]

看第二、三行：计划已批准，同一批里的部署却被拒了，守卫读到的仍是 active: true。

get() 返回的 active 是日志里已记录的状态，pending 是待生效选择的目标值（plan-mode/src/index.ts:392-396）。"pending":false 的意思是“有一个待生效的切换，目标是离开”，不是“没有待生效的切换”。

批准后的状态要到下一步开始前才写入，这一批剩下的调用仍在计划模式下。README 把这写成有意为之：批准后“当前这批工具调用剩余部分仍保留计划引导”（plan-mode/README.zh.md:93）。基础组合的引导也要求 exit_plan_mode 是这条回复里唯一、最后一个工具调用（base/cordis.patch.yml:322）。

“部署工具在计划模式下照样执行”一节测过，plan-mode 自己不拦部署；没有这道守卫，同一批里的部署就没有别的东西拦。守卫只能拒绝、不能放行（第 9 篇），适合用来兜底。

审批批了守卫照拒，never 也拦不住计划评审

第 24 篇的做法是让部署在 tools/pre-execute 返回 ask，经 dsh 的审批服务问人。上面那道守卫保留，再挂上审批服务：

== 5. 叠加审批：部署要人批，再切到 danger-full-access 预设 ==
  计划模式中部署 | 审批人被问 1 次（deploy_release：部署生产要值班负责人批准），批准；结果 Error: 计划模式下不部署，先用 exit_plan_mode 提交计划
  切到 danger-full-access 预设写入 | permission/preset {"preset":"danger-full-access"}；sandbox/mode {"mode":"danger-full-access"}；approval/policy {"policy":"never"}
  审批策略 never | 计划评审照样问人 1 次：Plan approved
                 | 退出计划后部署：审批人被问 0 次，结果 Error: the user rejected tool "deploy_release"
  平台收到的部署 []

审批人批准了，部署仍被守卫拒绝：工具流水线先跑 tools/pre-execute，遇到 ask 就去问审批服务，得到放行后才轮到守卫（packages/core/tools/src/index.ts:1482-1496）。

审批请求只带工具名、callId 和原因（packages/interaction/user-approval/src/index.ts:104-125），不带计划状态，审批人批准时并不知道会话正在计划模式里。

权限预设把沙箱模式和审批策略绑定，基础组合里 danger-full-access 配 never（base/cordis.patch.yml:236-248）。demo 挂上服务切过去，日志依次多出输出里的三条事件（packages/interaction/permission-presets/src/index.ts:402-416）。

策略为 never 时的拒绝与第 30 篇相同：审批服务不问任何人，直接返回“拒绝”（user-approval/src/index.ts:268）；模型收到的却是“the user rejected”（packages/core/tools/src/index.ts:1724-1726），审批人被问 0 次。

计划评审不受影响：它走用户提问服务，never 只管审批服务的请求，评审照样弹给人。无人值守、没有应答者时，模型就停在“计划要走 exit_plan_mode，批准后下一步才离开”里那条 no user-questions answerer 错误上。

回复期间的 /plan off，重启后就丢了

最后一个场景：模型正在回复时，人发 /plan off。先在同一进程里接着聊，再换一个会话做同样的操作，然后重启宿主、恢复会话：

== 6. 轮中选的 /plan off：同进程下一步生效，重启后丢失 ==
  模型回复期间人发 /plan off | Leaving plan mode (applies from the next step).
    这一轮结束后 | 计划状态 {"active":true,"pending":false}，界面投影 {"active":true,"pending":true}
  同一进程，人发“继续” | 含计划引导：false，plan-mode 通知 ["The user switched this session back to the default mode."]
  另一个会话同样操作后重启宿主 | 重启前：计划状态 {"active":true,"pending":false}，界面投影 {"active":true,"pending":true}
    恢复会话后 | 计划状态 {"active":true}，界面投影 {"active":true,"pending":true}
    人发“继续” | 含计划引导：true，这一轮后计划状态 {"active":true}，界面投影 {"active":true,"pending":true}

看最后两行：重启后 /plan off 没了，计划模式还在，界面投影却一直显示“待生效”。计划状态里的 pending 是 get() 返回的待生效目标值，界面投影里的 pending 是“有一个成功的 /plan 选择与当前状态不同”。

轮次进行中的选择只存进一个进程内的 WeakMap，等下一步开始前写入（plan-mode/src/index.ts:182,419-422）。这次选择发生在最后一次请求期间，这一轮之后再没有步骤，所以一直没写进日志。

同一进程里人再发一句“继续”，新一轮的第一步就把它写入，还附上一条切换通知（plan-mode/src/index.ts:452-463）。进程在这之前退出，选择就丢了。README 的已知限制写了这一条，并说“UI 必须重新应用它”（plan-mode/README.zh.md:186）。

界面投影的 pending 从日志里的 command/run、command/done 折叠出来（plan-mode/src/index.ts:138-148,159-162），命令事件已经落盘，于是重启后仍是 true。

已经写入日志的计划状态会随会话恢复：第二个会话进入计划模式时写的 plan/mode 还在，恢复后第一次请求就带着引导。README 说该状态“能在重启后保留”（plan-mode/README.zh.md:67），对已记录的状态成立，对待生效的选择不成立。

fork 同理。第 8 步把第 7 步那个仍在计划模式的会话，按最后一个 turn/end 之前的日志 fork 出一个新会话：

== 8. fork 继承已记录的计划状态 ==
  fork 出的会话 | 计划状态 {"active":true}；新开的会话 | 计划状态 {"active":false}
  fork 出的会话第一次请求 | 含计划引导：true

计划状态从日志里的 plan/mode 折叠出来，fork 带着这段日志，也就带着计划模式；新开的会话从未激活开始（plan-mode/README.zh.md:187）。

图：/plan 只给请求加一段引导，部署照常过工具流水线；exit_plan_mode 批准后，下一步开始前切换。

这对 Agent 意味着什么

计划模式只改变模型看到的文字，工具目录、工具流水线都不变，模型不听引导时，部署照样上线。本篇实测里，计划模式下挡住部署的是守卫。

批准要到下一步才生效。批准和同一条回复里的其他调用处在同一批，状态还没切换：守卫按计划状态拦截时，这批部署会被拒；不拦截时，这批部署在计划模式下已经执行。让 exit_plan_mode 单独成一条回复，是引导里写明的要求。

计划评审由用户提问服务处理，和审批服务互不知情：审批人看不到会话在计划模式里，never 策略也挡不住计划评审弹给人。无人值守的组合里要确认两条通道各自有没有应答者。

轮次中途选的 /plan off 只在进程内排队，进程退出就丢，界面投影却一直显示待生效。需要确定离开计划模式时，要等到下一步开始、日志里出现 plan/mode。

本文的验证范围

实测部分是 plan-mode-demo.ts。它在一个进程里挂 Cordis、agent 循环、JSONL 会话持久化与检查点策略、dsh-commands、dsh-user-questions 和 dsh-plan-mode。引导文本从基础组合配置文件原样读取；叠加审批时再挂 dsh-user-approval（策略 ask）。

没有启动 dsh 的 CLI 或 Web 进程；模型、计划评审人和审批人都是脚本化的；发布平台是合成的；“部署要审批”和“计划模式下不许部署”分别是 demo 自己写的 pre-execute 监听和守卫。

切预设用 dsh-permission-presets 服务（预设表照抄基础组合），它要求的 bash 执行器用一个只带 sandboxMode 的对象占位。

关掉评审由应答者以 ASK_CANCELLED 拒绝模拟，重载是销毁 plan-mode 的插件实例再重新挂载；重启用同一进程内销毁 Context 再重新组装模拟；fork 按日志前缀建新会话。

主要结论都有断言：

  • /plan 回执原文；两次请求的系统提示都含基础组合的引导；工具目录为 deploy_release 和 exit_plan_mode；部署结果为已上线，平台收到 2.7；没有 plan-mode 来源的消息；
  • 文字回计划那一轮只有 1 次请求；两轮请求都含引导，部署 2.8 执行成功；计划状态为 {"active":true}；日志里只有进入时的 1 条 plan/mode；
  • 没有应答者、计划以 ## 开头两种错误原文；评审人共收到 2 次评审，标题、选项、intent 与计划原文；打回与批准的结果原文；
  • 批准后日志依次为 tool/result、step/end、plan/mode {"active":false}、step/start；批准前的请求都含引导，之后那次不含且工具目录不变；部署 2.8 执行成功，计划状态为 {"active":false}；
  • 直接部署和同一批里的部署都被守卫拒绝，exit_plan_mode 已批准；守卫三次读到的状态依次为 {"active":true}、{"active":true,"pending":false}、{"active":false}；平台只收到一次 2.9；
  • 审批人只被问 1 次、原因原文，批准后仍被守卫拒绝；切预设写入的三条事件；策略 never 下计划评审问了 1 次并批准，审批人没再被问，部署结果为 the user rejected 原文，平台没有收到部署；
  • /plan off 回执原文；同一进程下一轮不含引导、切换通知原文、计划状态为 {"active":false}；重启前后的计划状态与界面投影如输出所示，恢复后第一次请求含引导；
  • 关掉评审、评审期间重载两种错误原文，计划状态为 {"active":true}，最后一次请求含引导，两次评审都被应答；
  • fork 出的会话计划状态为 {"active":true}、第一次请求含引导，新开的会话为 {"active":false}。

另外做了变异检查。以下 5 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • 批准后立即写入 plan/mode，不等下一步开始前；
  • 引导段不看计划状态，始终渲染；
  • 去掉计划必须以 # 开头的检查；
  • 投影不再记录成功的 /plan 选择；
  • demo 不切换到 danger-full-access 预设。

连续 5 次运行，以及 4 个进程并发运行，输出都一致。本机实测一次运行约 1 秒。
