第 17 / 36 节 · Agent 编排

模型连续 25 次调工具，循环跑了 26 步，中间没有上限拦它，第 26 次请求带了 52 条消息。README 举例的 turn-stopping 只在最后一步之后触发了一次。

第 11 到 15 篇分别看了会话日志、恢复、压缩、查询和溢出落盘。本篇转到发起请求、执行工具的 agent 循环。

这次给循环的主要钩子挂上记录用的监听器，逐条记下一次“payment-api 最近一次发布怎么样？”从提问到回答经过的钩子和日志事件；再比较 steer、followup 怎么进入轮次，以及 turn-stopping 在哪一步触发。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 一次“查询 → 回答”分两步，每次请求都从日志重新派生；
  • steer 进同一轮的第 2 步，followup 开第 2 轮；
  • 连调 25 次工具跑了 26 步，turn-stopping 只触发 1 次；
  • pre-step 拒绝时，这一步领走的 steer 消息丢失。

一次查询至少两步

循环的公开约定在 packages/core/agent，唯一的实现是 packages/core/agent-loop 里的 ReactLoopAgent（packages/core/agent-loop/src/agent.ts）。它有两层单位：

  • 轮次（turn）：用户的一条消息开一轮，到模型不再需要继续为止；
  • 步骤（step）：一次模型调用，加上这次调用发出的所有工具调用。

本节“至少两步”只针对模型先调工具、再读结果回答的案例。官方架构文档还定义了零步骤轮次：首次领取的输入在 agent/pre-step 被拒绝或改写为空，日志仍记 turn/start 和 turn/end，中间没有 step/start（按官方架构文档，未实测）。因此不能用“轮次总会调用一次模型”去读会话日志。

一轮里的步骤循环写在 turn() 里（agent.ts:287-321）。去掉原注释（骨架里的中文注释为新加）、各关键点之前的取消检查 signal.throwIfAborted()、空批次的提前结束和 finally 里的收尾后，骨架是：

while (true) {
  const decision = await this.preStep(target, { turn, step })
  if (decision.kind === 'reject') { turnEnds = { kind: 'blocked' }; return false }
  this.session.append('step/start', { turn, step })
  const stepEnd = await this.step(decision)     // 调了工具且结果没标 concludesTurn 时返回 null
  if (turnEnds === null || turnEnds.kind !== 'max-tokens') turnEnds = stepEnd
  this.session.append('step/end', { turn, step })
  if (turnEnds && this.inbox.nextStep.length === 0) {
    await this.dispatch.serial('agent/turn-stopping', { turn, signal })
  }
  if (turnEnds && this.inbox.nextStep.length === 0) break
  target = 'next-step'
}

step() 在模型回了纯文本时返回 completed，撞上输出上限时返回 max-tokens；调了工具就执行工具，结果没有标记 concludesTurn 时返回 null（:488、:485、:493）。

null 表示轮次还没完，于是进入下一步，把工具结果交给模型。所以一次“查询 → 回答”至少是两步：第一步模型决定调工具，第二步模型读到结果后回答。

图：每步先领收件箱、过 agent/pre-step，再从日志派生请求；调了工具就再来一步。

消息和工具调用先落日志

脚本挂载 dsh-agent-loop、工具运行时和系统提示词，用脚本化模型：第一次请求返回一个 lookup_release 调用，第二次返回回答。

脚本在每个主要钩子上挂一个只记录、不修改的监听器，同时订阅 session/event（输出里 ~ 是实时状态事件，[hook] 是钩子，其余是写进会话日志的事件及其 seq）：

1. one turn, "query -> answer": every hook and every logged event in order
  seq  0 agent/inbox/spliced
    ~ agent/status running
  seq  1 turn/start
  seq  2 agent/inbox/spliced
    [hook] system-prompt/assemble
    [hook] agent/pre-step (step 1)
  seq  3 step/start step 1
    [hook] agent/request
  seq  4 system/message
  seq  5 user/message "payment-api 最近一次发布怎么样？"
  seq  6 request/header
  seq  7 request/context
    [hook] llm/stream
  seq  8 assistant/message
  seq  9 tool/call
    [hook] tools/pre-execute lookup_release
    [hook] tools/post-execute lookup_release
  seq 10 tool/result
  seq 11 step/end step 1
    [hook] system-prompt/assemble
    [hook] agent/pre-step (step 2)
  seq 12 step/start step 2
    [hook] agent/request
    [hook] llm/stream
  seq 13 assistant/message
  seq 14 step/end step 2
    [hook] agent/turn-stopping
  seq 15 turn/end(completed)
    ~ agent/status idle

从上往下看这几处顺序：

  • 收件箱也在日志里。 用户消息先作为 agent/inbox/spliced 写进日志（seq 0），轮次开始后被领取，又记一条 splice（seq 2）；收件箱是从这些事件折叠出的持久投影，进程被杀后照样能恢复（第 10 步）。
  • 每一步都重新组装系统提示词，然后才进 agent/pre-step。pre-step 是 waterfall，可以改写这一步要进入的消息，也可以直接拒绝这一步。
  • step/start 先于 agent/request，而系统提示词和用户消息在 agent/request 之后才写进日志，即 seq 4、5；在这期间取消，两者都不提交（第 6 步）。第二步没有新的 system/message，提示词变了才会重写（第 7 步）。
  • tool/call 先写日志，再走工具流水线。 第 9 篇讲的守卫和执行都发生在 seq 9 之后，结果在 seq 10 才落日志；并行执行时结果也按模型给出的顺序依次提交（第 8 步；packages/core/agent-loop/src/tool-calls.ts:146-160）。
  • agent/turn-stopping 只在最后一步之后出现一次。 第一步调了工具，轮次还没结束，不会触发它。

取消、改提示词、并行调用都按日志顺序提交

第 6 步在 agent/request 的监听器里直接取消这一轮：

6. cancel inside agent/request: the step started, but no system prompt or user message was committed
  turn/start > step/start 1 > step/end > turn/end(aborted)
  system/message or user/message in the log: false; inbox pending: 0

看第 1 行：step/start 已经写了，系统提示词和用户消息都没进日志，这一步空着结束。领走的用户消息也没回到收件箱，cancel() 默认会清空它（见“取消会清空收件箱，也会补齐没执行的工具结果”）。

第 7 步挂一段每次组装都会变的提示词：

7. a prompt that changes between steps is re-committed at step 2
  system/message: seq 4 (step 1, "append"), seq 13 (step 2, {"op":"replace","startSeq":4,"endSeq":4})

第 2 步写了一条新的 system/message，用 replace 遮住 seq 4 那条。提示词不变时不重写，变了就在这一步重写一次。

第 8 步让模型在一条消息里发两个可以并行的调用，第一个慢、第二个快：

8. two parallel-safe calls in one message: the slow first call is still committed first
  finished executing: fast-api, slow-api
  log: tool/call p-1 > tool/call p-2 > tool/result p-1 > tool/result p-2

看最后一行：fast-api 先执行完，日志里仍是 p-1 的结果在前。并行只影响执行，提交按模型给出的顺序。

每次请求都从日志重新派生

再看两次请求本身的内容：

2. the second request is derived from the log, not kept in memory
  request 1: 2 messages [system user], 1 tool schema(s)
  request 2: 4 messages [system user assistant user]
  request keys: messages, model, provider, sessionId, signal, tools
  request 2 messages deep-equal session.deriveMessages(): true; every message frozen: true
  last message of request 2: role user, blocks [tool-result]

看第 4 行，deep-equal 为 true：循环不在内存里维护一份“对话历史”。每次请求前，buildRequest() 调 session.deriveMessages() 从日志派生消息列表（agent-loop/src/agent.ts:604），这就是第 11 篇讲的 surface 投影。

脚本把第二次请求的消息和轮次结束后派生历史的前 4 条逐字（JSON）比较，完全相同。构造请求时，源码逐条深冻结派生出的消息，并冻结数组（:604-610），脚本检查了数组和每条消息都已冻结，下游监听器没法原地修改。

请求对象里没有单独的 system 字段，系统提示词是消息列表里的第一条 system 消息。工具结果放在一条 user 消息的 tool-result 块里，没有单独的 tool 角色。

从日志派生，也是第 12 篇崩溃恢复成立的前提：请求里的消息列表只依赖日志，换一个进程读同一份日志，派生出的历史是一样的。模型路由和工具 schema 由当次的提示词组装与 agent/request 决定，变化时才记进 request/header。

官方架构文档把这几项职责分开：core/system-prompt 组装提示词片段和工具 schema，core/agent-loop 驱动轮次，llm/llm 提供模型适配器。脚本记录了 system-prompt/assemble 与 llm/stream 的先后，但没有比较不同 profile 的组装结果（按官方架构文档，未实测）。

第 9 步连问 4 轮，第 3 轮前注册一个新工具，第 4 轮在 agent/request 里换成 mock-large：

9. request/header is rewritten only when the envelope changes
  turn 1: request/header ["initial"]
  turn 2: request/header []
  turn 3: request/header ["change"]
  turn 4: request/header ["change"]

第 2 轮信封没变，一条都不写；工具变了、模型变了，各记一条 change（agent-loop/src/agent.ts:572-582）。

steer 进下一步，followup 开新一轮

Agent 接口有三种投递消息的方法（接口见 packages/core/agent/src/runtime-types.ts:222-241，实现见 agent-loop/src/agent.ts:137-147）：

方法进入哪个队列是否唤醒循环
followup()next-turn是
steer()next-step是
inject()next-step否

运行中 steer 和 inject 走同一个队列，都在下一个步骤边界被领取；区别在空闲时，inject 不会开新一轮。当前活动已被取消时，唤醒类消息会改投 next-turn（:131-132）。

脚本让工具执行时卡在一个闸门上，趁这个时候先 steer 一句“顺便也看看 order-api”，再 followup 一句“order-api 呢？”，然后放开闸门：

3. steer vs followup while a tool is running
  steer    "顺便也看看 order-api" -> seq 16, turn 1 step 2 (same turn, next step)
  followup "order-api 呢？"        -> seq 23, turn 2 step 1 (a new turn)
  turn 1: completed; turn 2: completed

steer 的消息在同一轮的第 2 步进入，和工具结果一起交给模型；followup 的消息要等第 1 轮结束，才作为第 2 轮的第一条消息。

每轮第一步领取全部 next-step 消息再加一条 next-turn 消息，之后的步骤只领取 next-step（agent-loop/src/agent.ts:245、packages/core/agent-loop/src/inbox.ts:109-114）。

一轮正常结束后如果还有待处理的消息，同一个驱动直接开下一轮（agent-loop/src/agent.ts:345）。

实际用起来，steer 会改变当前这一轮的走向，模型在回答之前就看到了补充要求；followup 不打断当前这一轮，模型要等给出完整回答之后才看到这个新问题。

排队的 followup 也记在日志里。第 10 步在子进程里让第一轮的工具卡住，再排一个 followup，然后 kill -9，换一个 Context 恢复：

10. the inbox is in the log: kill -9 with a queued followup, then resume in a new context
  child killed while lookup_release hung (SIGKILL); "order-api 呢？" was queued behind it
  right after resume: next-turn inbox ["order-api 呢？"]; turn/end(interrupted)
  300ms later: status idle, model calls 0; the restored message waits for a wake-up
  after a new followup: user messages ["payment-api 最近一次发布怎么样？","order-api 呢？","还在吗？"]; turn/end(interrupted), turn/end(completed), turn/end(completed)

看第 2、3 行：恢复后“order-api 呢？”回到了收件箱，循环却没有自己醒来，300ms 里一次模型也没调。直到新的 followup 把它唤醒，才依次开了第 2、3 轮。

没有步数上限

让脚本化模型一直调工具，不挂任何限制：

4. a model that keeps calling tools: nothing stops the turn by default
  26 steps, 25 tool calls in turn 1; agent/turn-stopping fired 1 time(s), after the last step
  every step re-sends the whole history: the 26th request carried 52 messages

脚本化模型连续 25 次调工具，第 26 次才回答。循环跑了 26 步，中间没有上限拦它。每一步都把完整历史重新发一遍，第 26 次请求带了 52 条消息：系统提示词、用户问题，加上 25 对工具调用和结果。

26 次请求累计发送了 702 条消息（2 + 4 + … + 52），累计输入量大致随步数的平方增长。上下文快满时第 13 篇的压缩会缩短历史，但它不结束轮次。

第 11 步另起一个挂了压缩、窗口 2000 token 的 Context，让模型连调 12 次工具：

11. compaction inside a turn does not end it
  0 prunes, 2 summaries; first summary during step 7
  turn 1: 13 steps, completed

看最后一行：第 7 步里就写了摘要，轮次照样跑满 13 步，以 completed 结束。

仓库里和“防止转圈”相近的实现都不是步数上限：

  • 基础组合（base bundle）默认启用的 repeat-tool-reminder，在同一工具以相同参数连续重复 3、5、8 次时提醒模型，只提醒、不阻止，本文 25 次调用参数各不相同，挂上它也不会触发（按源码，未实测）；
  • tool-jobs 的 maxConsecutiveWakes（默认 3），限制的是后台任务唤醒开出的轮数。

README 举例的 turn-stopping 拦不住工具调用

README 的“已知限制”写明没有内置轮次预算（packages/core/agent-loop/README.zh.md:200）：“工具调用或 steering 会让当前轮次继续；限制失控轮次的策略必须从既有生命周期扩展点（如 agent/turn-stopping）执行取消。”它举的 turn-stopping 对这两种来源都管不全。

对工具调用它无效：实测 26 步里只在最后一步后触发一次，此时模型已自己停下。骨架里只有 turnEnds 非空且 next-step 队列为空时才触发（agent-loop/src/agent.ts:316）；前者指本步回了纯文本、撞上 max-tokens 或工具结果标了 concludesTurn，普通调工具步返回 null。

第 12 步让回答撞上输出上限：

12. an answer cut at the output cap ends the turn as max-tokens
  turn/start > step/start 1 > user/message > assistant/message > step/end > turn/end(max-tokens); turn-stopping 1

轮次以 max-tokens 结束，turn-stopping 照样触发一次，和回了纯文本时一样。

对 steer 只部分有效：监听器自己在 turn-stopping 里 steer 让轮次续跑（如 Claude Code 的 Stop hook）时，可以在那里不再 steer，也可以计数或取消（按源码，未实测）。第 13 步的监听器第一次触发时 steer 一句：

13. a turn-stopping listener that steers keeps the turn going
  turn/start > step/start 1 > user/message > assistant/message > step/end > step/start 2 > user/message > assistant/message > step/end > turn/end(completed); turn-stopping 2

轮次多跑了一步，turn-stopping 触发 2 次。其他来源在步骤结束前排进 next-step 的 steer 会直接开下一步，不经过它，第 14 步的第 2 行就是这样。

同一钩子的类型注释（agent/src/runtime-types.ts:365-374）说得更全：turn-stopping 是让监听器“不同意停”的地方，可以 steer 一条消息让轮次继续；反向控制，即提前结束工具循环，靠工具结果上的 concludesTurn 标记，且该标记不会越过已经进入 next-step 的上下文或 steer。

Claude Code 兼容层的 Stop hook 就是正方向的用法：hook 返回阻止时，在 turn-stopping 里 steer 一条消息，强制再跑一步（按源码，未实测）。

Stop hook 的实现留了 TODO(stop-loop-guard)（packages/hooks/hooks-claude-code/src/index.ts:268，Codex 兼容层 packages/hooks/hooks-codex/src/index.ts:256 也有一个）：连续强制继续的次数尚无上限（按源码，未实测）。

要拦工具循环，“执行取消”得挂在每一步都会经过的扩展点上，“三种停法都留下一个模型没回应的工具结果”一节实测了这种做法。

三种停法都留下一个模型没回应的工具结果

再分别用三种办法拦它（日志结尾一行跳过了收件箱的 splice 事件）：

5. three ways to stop it: reject the step, cancel from a hook, or conclude from inside the tool
  agent/pre-step rejects step 4 -> turn 1: blocked; 3 model calls; turn-stopping 0
    log ends tool/result > step/end > turn/end: the step-3 tool result is never answered
    steered during step 3, claimed by the rejected step 4: ["先停一下，汇总已经查到的"]
    afterwards in history: false; still pending: false; event before turn/end: agent/inbox/spliced
  agent.cancel() in agent/pre-step at step 4 -> turn 1: aborted (hook: step budget); 3 model calls; turn-stopping 0
    log ends tool/result > step/end > turn/end
  tool calls exec.concludeTurn() -> turn 1: completed; 1 model call; turn-stopping 1
    log ends tool/result > step/end > turn/end: the model never saw the result

第一种是在 agent/pre-step 里拒绝：超过 3 步就返回 { kind: 'reject' }，第 4 步没有开始，轮次以 blocked 结束，模型只被调用了 3 次，turn-stopping 一次也没触发。代价是日志停在第 3 步的工具结果上，模型没有机会看到它、也没有给出回答。

第二种是在钩子里取消：同样在 agent/pre-step 里判断步数，但不拒绝，改为对 payload.agent 调用 cancel({ kind: 'hook', reason: 'step budget' })。

AgentCancelCause 专设了 hook 一种（packages/core/session/src/types.ts:191）。

waterfall 返回后的 signal.throwIfAborted() 让这一步来不及开始，轮次以 aborted 结束，取消原因记在 turn/end 里。这就是 README 说的“执行取消”。

第三种是工具自己结束轮次：工具在执行时调用 exec.concludeTurn()（packages/core/tools/src/index.ts:417），结果带上 concludesTurn，这一步就以 completed 结束（agent-loop/src/agent.ts:493）。

模型只被调用 1 次，工具结果写进日志，但模型同样没看到。轮次算正常结束，turn-stopping 照常触发。

这个标记挡不住已经排进下一步的内容。第 14 步让同一个结束轮次的工具，一次在 post-execute 附带 additionalContexts，一次在执行时被 steer：

14. concludeTurn() does not end the turn when context or a steer is waiting
  with additionalContexts: turn/start > step/start 1 > user/message > assistant/message > tool/call > tool/result > step/end > step/start 2 > user/message > assistant/message > step/end > turn/end(completed); turn-stopping 1
  with a steer during the tool: turn/start > step/start 1 > user/message > assistant/message > tool/call > tool/result > step/end > step/start 2 > user/message > assistant/message > step/end > turn/end(completed); turn-stopping 1

两种都多跑了一步，turn-stopping 只在第 2 步后触发 1 次。只有成功的结果能带 concludesTurn（按源码，未实测）。

pre-step 拒绝时，领走的 steer 消息丢了

脚本还在第 3 次工具调用执行时 steer 了一句“先停一下，汇总已经查到的”。这条消息被第 4 步领取，随后第 4 步被拒绝。结果它既没有进历史，也不在收件箱里，日志里只留下一条领取它的 agent/inbox/spliced。

preStep() 先用 inbox.claim() 把这一步的消息移出收件箱（agent-loop/src/agent.ts:245），再跑 agent/pre-step waterfall（:250），拒绝时直接返回，领走的消息没有放回去。

丢消息的行为和 steer() 的接口注释对不上，那里写的是“被拒绝的步骤会把 steering 留在收件箱里，等下次唤醒”（agent/src/runtime-types.ts:227-228）。

仓库里的 goal-round-driver 在拒绝前会用 agent.inbox.prepend() 把其他领到的消息放回收件箱（packages/goal/goal-round-driver/src/index.ts:127-135）。

第 15 步按这个做法再跑一次，第 3 次工具调用时再排一个 followup：

15. reject step 4, but put the claimed steer back first; a followup queued meanwhile
  turn/start > step/start 1 > step/start 2 > step/start 3 > turn/end(blocked); status idle
    still queued: next-step ["先停一下，汇总已经查到的"], next-turn ["另外 order-api 呢？"]
  after followup "继续": turn/end(blocked), turn/end(completed), turn/end(completed)
    turn 2's request ends with: assistant[tool-call] user[tool-result] user["先停一下，汇总已经查到的"] user["另外 order-api 呢？"]

看第 2 行：steer 回到了 next-step，followup 还在 next-turn，循环却停在 idle，没有自己开下一轮。第 2 轮要等新的 followup 唤醒，它的请求末尾先是第 3 步那个没人回应过的工具结果，再是放回去的 steer 和排队的 followup。

取消会清空收件箱，也会补齐没执行的工具结果

第 16 步在两个时机取消：模型流式输出到一半时，以及两个串行工具调用的第一个刚进 tools/pre-execute 时：

16. cancel mid-stream, and cancel while the first of two calls runs
  turn/start > step/start 1 > user/message > assistant/message > step/end > turn/end(aborted)
    assistant/message interrupted=true: "payment-api 最近一次发布 demo-003"
  two exclusive calls, cancel in tc-1's pre-execute: tc-1 ABORTED_BEFORE_DISPATCH, tc-2 ABORTED_BEFORE_DISPATCH; turn/end(aborted)

流式途中取消，已收到的半句话以 interrupted 的 assistant/message 写进日志。工具调用途中取消，两个调用都得到 ABORTED_BEFORE_DISPATCH 的合成结果：第一个的本体没开始执行，第二个根本没派发（agent-loop/src/tool-calls.ts:250-260）。

第 17 步在工具执行时排一个 followup，再调 cancel()：

17. cancel() clears queued messages unless keepInbox is set
  keepInbox false: turn/start > turn/end(aborted); pending 0
  keepInbox true : turn/start > turn/end(aborted); pending 1

不带 keepInbox 时排队的消息被清空（agent-loop/src/agent.ts:149-153）；带上它，消息留在收件箱里，但同样不会自己开下一轮。

这对 Agent 意味着什么

实测默认不限制一轮的步数，连调 25 次工具跑了 26 步，中间没有任何上限拦它，turn-stopping 只在最后一步之后触发了一次，靠它拦不住工具循环。步数上限得自己的部署来加：在 agent/pre-step 里按 step 取消或拒绝，都在第 4 步开始前停了下来。拒绝时，这一步领走的 steer 消息会丢，既不进历史，也不在收件箱里。

进程重启或步骤被拒绝后，排队的消息不会自己跑。实测恢复后的收件箱、拒绝前放回的 steer、带 keepInbox 取消后留下的消息，都要等一条新消息唤醒循环，需要自动继续就得自己补一次唤醒。

插话时想让模型在这一轮的回答里考虑新信息，用 steer，它会改变正在进行的工作；只是排一个新问题，用 followup，它不打断当前这一轮。

本文的验证范围

实测部分是一个脚本 agent-loop-demo.ts：挂载真实的 dsh-agent-loop、dsh-tools、dsh-system-prompt 和会话投影，模型是脚本化模型。发布数据是合成的。

主 Context 没有挂持久化（会话只在内存里）。第 10 步另用 JSONL 持久化，被杀的一方是子进程；第 11 步另起一个挂了 token 估算、剪枝器和 dsh-compaction-basic 的 Context。

主要结论都有断言：

  • 事件骨架与钩子的相对顺序，模型调用次数与 turn-stopping 次数；
  • 第二次请求的消息与派生历史一致，数组和每条消息都已冻结；
  • steer 和 followup 各落在哪一轮哪一步；
  • 失控轮次的步数、turn-stopping 次数与第 26 次请求的 52 条消息；
  • 三种停法的结束原因、模型调用次数、turn-stopping 次数与日志结尾；
  • 被拒绝的步骤领走的消息既不在历史里，也不在收件箱里；
  • 在 agent/request 里取消时这一轮只有 start、end 两对事件；提示词变化时第 2 步以 replace 重写；
  • 并行调用执行完成顺序与日志提交顺序；request/header 在 4 轮里依次为 initial、无、change、change；
  • 恢复后的收件箱内容，新 followup 之后 3 轮的用户消息与结束原因；挂压缩的轮次 13 步、completed；
  • max-tokens 结束原因，turn-stopping 里 steer 后的步数与触发次数，concludeTurn() 遇到上下文或 steer 时的步数；
  • 放回的消息与排队的 followup 在拒绝后仍待处理，第 2 轮请求末尾的 4 条消息；
  • 流式途中取消得到 interrupted 的消息，两个调用都是 ABORTED_BEFORE_DISPATCH，keepInbox 两种取值下的待处理数。

行为与文中不符时脚本以非零退出码结束。连续 5 次运行，输出都一致。
