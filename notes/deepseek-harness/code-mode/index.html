第 26 / 36 节 · 发布规则实战

程序里连发三次部署，第三次被守卫拦下，拒绝以异常的形式到了程序里。另一段程序用 catch 吞掉异常，三次都被拒，模型只收到“已尝试 3 次”，run_code 照样成功。

第 24 篇的审批、第 21 篇的守卫都按一次调用一个结果设计。dsh 的 Code Mode 叫 PTC 模式（Programmatic Tool Calling）：模型写 TypeScript 交给 run_code，由程序调 tools.deploy_release(...)。本篇把第 21 篇的规则引擎原样放进去，看守卫、审批、日志是否管用。

这次宿主把 dsh-tools 的 mode 设成 ptc，挂上 PTC 进程运行时 dsh-ptc-runtime-node；脚本化模型只写程序，部署都在程序里发生。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 程序里第三次部署被守卫拦下，拒绝成了可被 catch 吞掉的异常；
  • 部署记在 tool/ptc-dispatch 里，第 23 篇的挖掘模块读不到；
  • 工具声明可并发后，PTC 和原生模式并发三次部署，全部执行；
  • 审批迟到超过 500 毫秒的程序预算，审批记为 cancelled，部署未执行。

PTC 模式下模型只拿到 run_code

基础组合（base bundle）默认用原生模式。要进 PTC 模式，可以在 dsh-tools 的配置里写 mode: ptc；Web 端临时用环境变量 DSH_TOOLS_MODE 切整个进程（按源码，未实测；packages/bundle/web-app/cordis.patch.yml:34-38）。

随附的 ptc preset 则只让自己的 agent 进 PTC 模式（按源码，未实测；packages/preset/agent-presets/presets/ptc/agent.cordis.yml:280）。

demo 在 dsh-tools 配置里写 mode: ptc，下面的错误原文是一行，按子句拆开显示：

== 1. PTC 模式：模型只拿到 run_code，工具变成程序里的 SDK ==
发给模型的工具 schema：run_code
系统提示里的 SDK 声明：`deploy_release: {`、`declare class ToolCallError`、`declare const tools`
直接调 deploy_release，模型收到：
  Error: unknown tool "deploy_release"
  only `run_code` is callable directly
  — call `deploy_release` from inside a `run_code` program instead
pre-execute 监听器收到 0 次调用

请求里的工具 schema 只剩 run_code。其他工具变成系统提示里的一段 TypeScript 声明：参数类型、输出类型，以及失败时抛出的 ToolCallError。

模型照原生习惯直接调 deploy_release，会在策略流水线之前被拒：demo 挂的 pre-execute 监听器一次也没收到（packages/core/tools/src/index.ts:1379-1385、:1430-1450）。

错误文字里特意带上了正确的做法。注释说，只给一句“未知工具”，模型会以为部署坏了，不会去改正自己（:1439-1442）。

执行 run_code 时，程序跑在一个全新的 Node 子进程里，受会话的文件沙箱约束（第 20 篇的 workflow 用的是同一个运行时）。程序每调一次 tools.xxx，子进程就通过控制通道请宿主执行，宿主把它当成一次子调用，交给注册表。

图：子进程里的工具调用回宿主过 pre-execute、审批和守卫，记进 tool/ptc-dispatch。

子调用照样过守卫，拒绝变成程序里的异常

宿主为子调用生成新的调用编号 <run_code 的 callId>:ptc:<n>，带上父调用的令牌 parent，然后交给和原生调用相同的调度器（packages/core/tools/src/ptc.ts:537-548、:615）。

调度器的准备阶段依次跑 tools/pre-execute、审批和守卫（tools/src/index.ts:1482-1508），结束时发 tools/result（:1666-1685）。所以第 21 篇的规则引擎一行不改，也能管住程序里的部署。

脚本化模型写一段“失败就重试”的程序，连发三次 payment-api 2.3：

== 2. 程序里重试：子调用照样过守卫，拒绝变成程序里的异常 ==
模型收到：
  1: failed
  2: failed
  3: ToolCallError(deploy_release)
     [same-version-failed-twice] payment-api 2.3 在 24 小时内已失败 2 次，停止重试
平台执行 2 次，规则引擎的历史 2 条（tools/result 对子调用也触发）
程序把异常吞掉时，模型收到：已尝试 3 次（这次 3 次都被拒，平台仍是 2 次）

第三次被守卫拦下，平台只执行了两次；引擎的历史是两条，说明 tools/result 对子调用也触发了。

但拒绝到了程序里只是普通异常：宿主把子调用的失败文字抛给程序（tools/src/ptc.ts:668），程序拿到的是 ToolCallError。第一段程序把它打印出来，模型才看到拒绝理由。第二段程序写了 try { ... } catch {}，三次部署都被拒，模型只收到程序返回的“已尝试 3 次”，run_code 本身也是成功。

run_code 的说明里，只有程序打印或返回的内容才是输出（:52）。守卫仍然拦住了部署，但“被拦了”这件事能不能传到模型，取决于模型写的程序。

部署改记在 tool/ptc-dispatch 里

第 23 篇的挖掘模块按 tool/call 和 tool/result 配对找部署。PTC 模式下，这两种事件只记模型直接发出的调用（run_code，以及被模式拒掉的直接调用）。

程序里的子调用记在另外两种事件里：开始时追加 tool/ptc-dispatch-start，结束时追加 tool/ptc-dispatch（tools/src/ptc.ts:605-611、:579-591）。

用第 23 篇的 readDeploys 读值班会话的日志：

== 3. 会话日志：部署记在 tool/ptc-dispatch 里，第 23 篇的挖掘模块读不到 ==
tool/call：deploy_release、run_code、run_code；tool/ptc-dispatch：6 条
tool/ptc-dispatch 的字段：arguments, content, isError, name, parentCallId, rootCallId, subCallId
readDeploys 读回 1 条：oncall#11 error（直接调用被拒的那次）
presentationMeta 被调用：PTC 的 6 次子调用 0 次；原生模式部署 1 次，1 次
  原生 tool/result.meta = {"service":"inventory-api","version":"1.0","outcome":"succeeded"}

值班会话里，程序发出了 6 次部署（执行 2 次、被守卫拒 4 次），readDeploys 一条也没读到；它读回的唯一一条是第 1 步那次被模式拒掉的直接调用。

tool/ptc-dispatch 里有参数、渲染后的文字和 isError，没有 meta。第 23 篇靠 presentationMeta 把结构化结果带进日志，但 tool/ptc-dispatch 的写入本身就不带 meta（:579-591）。

最后两行显示，6 次子调用一次也没执行 presentationMeta，原生模式同一个工具执行 1 次，meta 也写进了日志。子调用带 parent，源码在这里跳过了 presentationMeta（tools/src/index.ts:1815）。

挖掘模块要支持 PTC 模式，得另外读 tool/ptc-dispatch，而且只能从渲染文字里解析结果。

tool/ptc-dispatch-start 和 tool/ptc-dispatch 只进日志，不进模型上下文（packages/core/tools/src/types.ts:37-38、:52-53）。模型下一轮看到的，仍然只有程序的输出。

拒绝的错误码只进日志，程序拿不到

pre-execute 的 deny 带 info 时，日志会多出 error 字段吗？demo 在两种模式下各试了一次：

== 4. 拒绝带错误码：日志里有，模型和程序都拿不到 ==
原生：模型收到 Error: 9.9 已冻结
  tool/result.error = {"name":"ReleaseFrozen","code":"RELEASE_FROZEN"}
PTC：程序里的异常只有 name, toolName, message
  tool/ptc-dispatch.error = {"name":"ReleaseFrozen","code":"RELEASE_FROZEN"}

原生模式下，tool/result 多了 error 字段（packages/core/agent-loop/src/tool-calls.ts:285）。

PTC 模式下，错误码记进了 tool/ptc-dispatch.error（tools/src/ptc.ts:589），但程序拿到的异常上，可枚举的字段只有 name 和 toolName，另有 message，没有错误码：宿主只把失败文字传给程序（:665-668 的注释写明了这一点）。

程序拿不到错误码，要区分“被规则拒绝”和“平台出错”只能比对文字。两种模式下，模型看到的都只是一句文字，错误码只进日志。

工具声明可并发时守卫拦不住

程序可以用 Promise.all / Promise.allSettled 同时发多个调用。SDK 说明里写着：可并发的调用同时执行，会改东西的调用单独执行（packages/core/tools/src/ts-types.ts:258）。

哪些调用“可并发”，看工具定义里的 isConcurrencySafe，没声明就按独占处理（tools/src/index.ts:1282-1291）。

同一段程序，用 Promise.allSettled 并发发三次 order-api 2.3，工具分别不声明和声明 isConcurrencySafe：

== 5. Promise.all 并发三次：工具声明可并发，守卫就拦不住 ==
不声明（默认独占）：failed, failed, 被拒；平台执行 2 次；守卫判断时的历史条数 0, 1, 2
声明 isConcurrencySafe：failed, failed, failed；平台执行 3 次；守卫判断时的历史条数 0, 0, 0
原生模式一条消息 3 个调用，不声明：failed, failed, 被拒；平台执行 2 次；守卫判断时的历史条数 0, 1, 2
原生模式一条消息 3 个调用，声明 isConcurrencySafe：failed, failed, failed；平台执行 3 次；守卫判断时的历史条数 0, 0, 0

前两行是 PTC：独占时三次依次执行，第三次被拦；声明可并发后三次全部执行。demo 在规则引擎的守卫前面挂了一个守卫，记下每次判断时引擎的历史条数：并发时三次都是 0。

准备阶段（pre-execute 和守卫）在一条有序通道里逐个执行（tools/src/ptc.ts:486-503、:612-621），可并发的调用一旦启动工具主体，通道就准备下一个；规则引擎的历史靠 tools/result 更新，要等工具主体结束并提交才有。

isConcurrencySafe 是工具作者对“能不能并发”的声明。它只该给只读工具；一个会改东西的工具声明了它，依赖历史的守卫就失效了。

后两行是原生模式：模型一条消息发 3 个 tool-call，同样按这个声明分组（agent-loop/src/tool-calls.ts:89、:205）。声明可并发时守卫看到的历史也是 0，三次都放行，和 PTC 一样漏拦。

审批参数不在 tool/call 里，等待也算超时

第 24 篇的应答者按 callId 回会话日志，在 tool/call 里找调用参数。

子调用的审批请求带的是子调用编号，在 tool/call 里按它找参数就失效了：

== 6. 审批：子调用的 callId 不在 tool/call 里；等审批的时间算进程序超时 ==
应答者收到 callId=call-15:ptc:1
  tool/call 里查：没有；tool/ptc-dispatch-start 里查：{"service":"billing-api","version":"1.0"}
  批准，部署执行：succeeded
审批人 1.5 秒后才批准，run_code 的 timeoutMs 是 500：
  模型收到：Error: code run failed (timeout): execution deadline reached (500ms)
  两次审批的结果：allowed-once、cancelled；批准到达后平台执行 0 次
不传 timeoutMs，审批人 125 秒后才批准：
  模型收到：Error: code run failed (timeout): execution deadline reached (120000ms)
  这次审批的结果：cancelled；批准到达后平台执行 0 次

call-15:ptc:1 在 tool/call 里找不到，要去 tool/ptc-dispatch-start 里按 subCallId 找。tool/ptc-dispatch-start 在准备阶段之前就已追加（tools/src/ptc.ts:605-615），所以应答者收到请求时参数已经在日志里。

第二次，审批人 1.5 秒后才回答，而这次 run_code 的时间预算只有 500 毫秒。程序的截止时间包含等子调用和等审批的时间（:113 的参数说明）。

到点后运行时停掉程序，宿主随即中止所有子调用共用的 signal（:547、:706），审批请求带的就是这个 signal（tools/src/index.ts:1720）。

审批服务看到它被中止，记为 cancelled，迟到的批准被丢弃（packages/interaction/user-approval/src/index.ts:287-298），子调用以中止结果结束（tools/src/index.ts:1490-1491），部署没有执行。

第三次不传 timeoutMs，审批人 125 秒后才批准：程序在 120 秒时超时（packages/ptc-runtime/ptc-runtime-node/src/index.ts:54 的默认值），审批同样记为 cancelled。

程序抛错时前面的部署已经生效

最后一种情况：程序先部署，再做一次检查，检查失败就抛错。

== 7. 程序抛错：前面的部署已经生效，结果却是一条错误 ==
模型收到的第一行：Error: code run failed (exception): Error: smoke check failed
  接着 5 行堆栈（含宿主上的文件路径），然后是：
  Captured output:
  deployed 4.0
  File sandbox: workspace-write; enforcement: full.
平台执行 1 次（user-api 4.0），规则引擎的历史 1 条

run_code 的结果是一条错误，但 user-api 4.0 已经部署了。程序没有事务：已完成的子调用不会回滚，失败的程序也不会自动重跑。run_code 的说明里有一句相关的提醒，写在沙箱提权部分：先前的操作可能已经完成，重试前先检查（tools/src/ptc.ts:124）。

规则引擎记下了这次部署，因为它观察的是子调用自己的 tools/result，不看 run_code 的结果。

错误文字里带着程序抛出的 Error 的完整堆栈（packages/ptc-runtime/ptc-runtime-node/src/bootstrap.ts:221 取的是 error.stack），其中有宿主上运行时文件的绝对路径。

错误文字会进模型上下文，也会写进会话日志，demo 的输出里只打印了行数。

这对 Agent 意味着什么

子调用和原生调用走同一条准备阶段，pre-execute、审批、守卫都生效，可拒绝变成了程序里的异常，被 catch 住就没了，能不能到模型取决于程序怎么写。需要模型一定看到的约束，不能只靠守卫的拒绝文字。

PTC 模式下的工具调用不在 tool/call / tool/result 里，也没有 meta，按日志做统计、挖规则、查审批参数的代码，都要多读 tool/ptc-dispatch 这两种事件。原生和 PTC 模式下，deny 带的 info 都会写进日志，但模型只看到文字，PTC 程序也拿不到错误码。

依赖历史的守卫在并发下看不到还没返回的结果，会改东西的工具不要声明 isConcurrencySafe。

程序的时间预算要算上人工审批：等审批超时，整个程序失败，部署也没有执行。程序中途失败时，已完成的子调用不会回滚（见“程序抛错时前面的部署已经生效”）。

本文的验证范围

实测部分是 code-mode-demo.ts，配合发布规则引擎 release-rules.ts（代码与第 21 篇相同，挂载时配了去掉 v 前缀的规范化）和日志读取 log-miner.ts（第 23 篇的 readDeploys，去掉了异常分组部分）。

脚本挂载真实的 dsh-tools（mode: ptc）、dsh-ptc-runtime-node、本地沙箱与沙箱策略（workspace-write）、本地子进程与文件系统、会话存储与 JSONL 持久化、dsh-session-query-sqlite、agent 循环和 dsh-user-approval。

模型和审批人是脚本化的：模型每一步写什么程序是预先写好的，审批人按设定的延迟批准。发布平台是合成的，时钟固定。日志写在系统临时目录，脚本退出时删除。本机为 Linux。

主要结论都有断言：

  • 发给模型的工具只有 run_code，系统提示里有 SDK 声明，直接调用被拒，pre-execute 监听器收到 0 次；
  • 程序里第三次部署被守卫拒绝，拒绝以 ToolCallError 到达程序；吞掉异常后模型只看到返回值；平台执行 2 次，引擎历史 2 条；
  • 值班会话有 6 条 tool/ptc-dispatch，第一条的字段里没有 meta（写入代码本身就不写这一项）；readDeploys 只读回直接调用那一条；子调用执行 presentationMeta 0 次，原生模式 1 次且 meta 进了日志；
  • deny 带 info 时，原生的 tool/result.error 和 PTC 的 tool/ptc-dispatch.error 都有错误码，程序里的异常没有；
  • 并发三次（PTC 的 Promise.allSettled 和原生一条消息 3 个调用）：独占时第三次被拒、守卫看到的历史依次 0、1、2；声明可并发时三次都执行、历史都是 0；
  • 子调用的审批请求 callId 是 call-15:ptc:1，只能在 tool/ptc-dispatch-start 里查到参数；审批迟到时程序超时（设 500 毫秒和默认 120 秒各一次）、审批记为 cancelled、部署未执行；
  • 程序抛错时，前面的部署已执行，引擎历史 1 条。

另外做了变异检查。以下 7 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • dsh-tools 用原生模式；
  • 规则引擎的守卫不再拒绝；
  • 规则引擎不再从 tools/result 记历史；
  • 部署工具总是声明可并发；
  • deny 不带 info；
  • 慢审批那次 run_code 不设 timeoutMs；
  • 审批人立即批准。
