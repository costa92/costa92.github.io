第 6 / 36 节 · Cordis 运行机制

插件一行不改，把文件版数据源换成平台版，apply 自动重跑，查到的记录从 demo-001 变成 plat-77。只用 ctx.set 改服务的值，插件不会重载，apply 一次都不重跑。

第 4 篇结尾预告要把临时的 Toolbox 换成 releases 服务。第 3 篇的 release-lookup 直接读 releases.json，要接真实的发布平台，是不是得改插件？

这次给 release-lookup 准备文件版和平台版两个 releases 数据源，插件代码不动，只换挂载的提供方，看插件怎么反应。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 数据源未提供时，插件停在 PENDING，apply 不执行；
  • 同一作用域再注册同名服务，直接报 has been registered；
  • 在原提供方上 ctx.set 改值，插件不重载；
  • 换一个提供方插件，依赖方完整重载，apply 第二次执行。

构造 Service 就完成注册

Service 在构造函数里就把自己注册了进去（vendor/cordis/src/service.ts:42）：

constructor(protected ctx: Context, name: string) {
  name ??= this.constructor['provide'] as string
  ...
  self.ctx = ctx
  self.name = name
  defineProperty(self, symbols.tracker, tracker)

  self.ctx.reflect.provide(name, self, this[symbols.check])
  return self
}

所以 new FileReleases(ctx) 这一行，服务就已经对外可见了，不需要另写一句注册。名字由构造参数给出，也可以省略参数、改用类上的静态 provide 字段（按源码，未实测；vendor/cordis/src/service.ts:43）。

第 4 篇留下的问题也在这段里：defineProperty(self, symbols.tracker, tracker) 给服务实例挂上 tracker。

读取服务属性时，getTraceable 会把 tracker 中的 ctx 换成调用方的 ctx，所以服务内部的 this.ctx.effect 记在调用方插件的 Fiber 上，不记在服务自己名下。后文第 7 步直接读到了这个替换。

ctx.releases 也不是用 Object.defineProperty 挂上去的属性。Context 是一个 Proxy，读属性时走一个 handler（vendor/cordis/src/reflect.ts:135 起），沿 Fiber 链逐级查找实现，并检查 isolate 标签。

在插件上下文里查不到、链上也没有祖先 Fiber 持有该服务时，它会直接抛错而不是返回 undefined，错误信息形如 cannot get property "x" without inject（第 8 步实测）。

根上下文例外（:152）：不做 inject 检查，按非严格模式读取，查不到返回 undefined，脚本里的 root.releases 就是这样读到的。服务对谁可见由 Fiber 和 inject 决定，不是全局变量，后文几步都建立在这一点上。

注册由 provide() 实现（:277）。注册动作本身是一个 effect（第 4 篇的机制），提供方插件卸载时自动注销；同一个 isolate 作用域里同名服务只能有一个，重复注册抛错。

inject 只有硬依赖一档

inject 可以写数组，也可以写对象（vendor/cordis/src/registry.ts:71）：

if (Array.isArray(inject)) {
  for (const name of inject) {
    result[name] = null
  }
} else if (Reflect.has(inject, symbols.checkProto)) {
  Object.assign(result, resolve(Object.getPrototypeOf(inject)))
  for (const name of Object.keys(inject)) {
    result[name] = inject[name] ?? null
  }
} else {
  // 纯对象：同上的循环
}

几种写法归一化成同一张表，键是服务名，值是该服务的 intercept 配置。后文第 7 步的插件用的就是对象写法 inject: { releases: {} }。

这个版本的源码里没有 required / optional 两档语义：只要写进 inject，就是硬依赖，缺了插件就不跑。

想做“有则用、无则降级”，可以用 ctx.inject(['releases'], ctx => {...}) 挂一个带依赖的子插件，也可以用 ctx.get(name) 在运行时自己探测，它不要求声明依赖，服务不在就返回 undefined（第 5 步实测）。

ctx.inject 挂的子插件在服务在时激活，不在时退回 PENDING、它登记的副作用被撤销（:300，第 12 步实测）。

ctx.get 的第二个参数 strict 默认为 true，传 false 会把提供方尚未激活的实现一并返回，不是一种“更宽松的探测”（vendor/cordis/src/reflect.ts:237，第 11 步实测）。

依赖判定只看提供方 uid

插件该不该激活，由 Fiber 的 _refresh() 算一个字符串决定（vendor/cordis/src/fiber.ts:611）：

_refresh() {
  let epoch: string | boolean = false
  epoch = ''
  for (const name of Object.keys(this.inject)) {
    const impl = this._store[name]
    if (!impl) {
      epoch = INACTIVE
      break
    }
    epoch += ':' + impl.fiber.uid
  }
  this._setEpoch(epoch)
}

_refresh() 遍历所有依赖：缺任何一个，epoch 变成 INACTIVE，状态回到 PENDING（FiberState 六个状态见 :147）；全都在，epoch 就是各提供方 Fiber uid 拼成的串。

_setEpoch()（:625）拿新旧 epoch 比：相同就什么都不做；从 INACTIVE 变为有效则重载插件；否则先卸载。

epoch 里编码的是提供方 Fiber 的 uid，不是服务的值。换一个提供方插件，uid 变了，依赖方完整重载；在原提供方里改服务的值，uid 没变，依赖方毫无察觉。

图：_refresh() 缺依赖即 INACTIVE；齐全则拼接提供方 uid，交 _setEpoch() 比较。

改值走的是 set()（vendor/cordis/src/reflect.ts:254），它只动 impl.value，并且限制只有提供它的那个 Fiber 能改（第 9 步实测）：

if (impl.fiber !== this.ctx.fiber) {
  throw new Error(`cannot set property "${name}" in multiple fibers`)
}
impl.value = value

数据源未到插件不跑，同名数据源不能并存

脚本仍然只用 vendor 里的 Cordis，不启动 dsh、不调模型。Releases 是抽象基类，规定 origin 和 list() 两个成员；FileReleases 返回内置记录，PlatformReleases 模拟来自发布平台，返回另一条数据。

release-lookup 只写 inject: ['releases']，两次运行用的是同一份插件代码。

脚本位于 scratch-plugin/service-demo/service-demo.ts（获取与运行命令见文末“本文的验证范围”）。正文只贴三个数据源类和插件的定义，步骤驱动代码与断言从略，完整脚本见示例仓库：

const log = (msg: string) => { console.log(msg) }

export interface Release { id: string; service: string; version: string; status: 'succeeded' | 'failed' }

/** Contract both data sources implement; the plugin only knows this shape. */
abstract class Releases extends Service {
  constructor(ctx: Context) { super(ctx, 'releases') }
  abstract origin: string
  abstract list(service: string): Promise<Release[]>
}

/** Source A: records shipped with the demo, stands in for releases.json. */
class FileReleases extends Releases {
  origin = 'file'
  records: Release[] = [{ id: 'demo-001', service: 'payment-api', version: '1.4.0', status: 'succeeded' }]
  async list(service: string) { return this.records.filter(r => r.service === service) }
}

/** Source B: stands in for a release platform API; same contract, different data. */
class PlatformReleases extends Releases {
  origin = 'platform'
  async list(service: string) {
    return [{ id: 'plat-77', service, version: '2.0.1', status: 'failed' as const }]
  }
}

const applied: string[] = []
const releaseLookup = { name: 'release-lookup', inject: ['releases'], async apply(ctx: Context) {
  log(`  apply() ran, origin=${ctx.releases.origin}`)
  const records = await ctx.releases.list('payment-api')
  log(`  lookup_release -> ${JSON.stringify(records)}`)
  applied.push(...records.map(r => r.id))
} }

脚本先加载插件、再挂文件版数据源，输出的第 1、2 步：

1. plugin loads before any releases service
  state=0 (0=PENDING)
2. provide the file-backed source
  apply() ran, origin=file
  lookup_release -> [{"id":"demo-001","service":"payment-api","version":"1.4.0","status":"succeeded"}]
  state=2 (2=ACTIVE)

和第 4 篇一样，数据源不在，插件就停在 PENDING，apply 一行不执行。FileReleases 一挂上，插件自动激活并查到文件里的 demo-001。

第 3 步在同一作用域再挂一个 PlatformReleases：

3. register a second releases service in the same scope
  service "releases" has been registered at <FileReleases>

第二个 releases 提供方注册失败，同名服务不能并存。报错里的 <FileReleases> 是已经占用该名字的提供方的 Fiber 名，这句错误来自重复检查（vendor/cordis/src/reflect.ts:289）。要让两份实现同时存在，得用 ctx.isolate() 分作用域，见第 10 步。

换提供方完整重载，改值不重载

第 4 步不换提供方，只在文件版的 Fiber 上用 ctx.set 换一个值：

const patched = Object.create(Object.getPrototypeOf(root.releases) as object) as Releases
Object.assign(patched, root.releases, { origin: 'file(updated)' })
fileFiber.ctx.set('releases', patched)

输出：

4. ctx.set on the live service: change value, keep the provider fiber
  plugin state=2, ctx.releases.origin=file(updated)
  (no new apply() line above)
  reference held before set: origin=file

改值后 ctx.releases.origin 立刻变成新值，插件状态一直是 2（ACTIVE），也没有新的 apply() ran 输出，插件没有重载。对应 set() 只改 impl.value、不触发通知，epoch 里的提供方 uid 没变。

最后一行里，set 之前存下的引用读到的仍是 file，Cordis 不会替插件换掉旧引用。所以插件应每次经 ctx.releases 读取，不在 apply 里缓存服务对象。

Object.create 看着别扭，是因为构造 Service 子类就会注册服务。直接写 new FileReleases(root) 会立刻撞上 service "releases" has been registered at <FileReleases>，就是第 3 步那条报错。要拿一个“同类但不注册”的值，只能绕开构造函数。

第 5 步先卸载文件版，再挂平台版：

5. swap the provider: dispose file source, then load platform source
  after dispose state=0 (0=PENDING), ctx.get("releases")=undefined
  apply() ran, origin=platform
  lookup_release -> [{"id":"plat-77","service":"payment-api","version":"2.0.1","status":"failed"}]
  state=2 (2=ACTIVE)

换提供方则是完整重载。卸载文件版的瞬间，插件退回 PENDING，ctx.get 也返回 undefined；装上平台版后重新激活，apply 第二次执行，同一行 ctx.releases.list() 查到的变成 plat-77。

第 6 步不声明依赖，直接用 ctx.get 读：

6. read without inject
  ctx.get("releases").origin=platform

ctx.get('releases') 不走 Proxy 的 inject 检查，不声明依赖也能读，直接从 store 取当前实现（vendor/cordis/src/reflect.ts:233）。可选依赖可以这样探测，但服务消失时没有状态机处理，调用方得自己判断。

图：左边两步走完整重载，右边只换 impl.value；两条路都让 ctx.releases 变了，插件的反应相反。

服务的可见和可改都由 Fiber 判定

前面几处源码结论由第 7–13 步逐条实跑，这几步在平台版已挂上之后进行：

7. this.ctx inside the service, read through a consumer
  provider fiber=<PlatformReleases>, service this.ctx.fiber=<probe>
8. read ctx.releases without declaring inject
  cannot get property "releases" without inject
9. ctx.set from a consumer fiber
  cannot set property "releases" in multiple fibers

第 7 步看 provider fiber 那一行：服务由 PlatformReleases 提供，probe 插件经 ctx.releases 读到的 this.ctx 却属于 probe。服务内部登记的 effect 因此记在调用方名下。

第 8 步的插件没写 inject，读 ctx.releases 直接抛错，不是返回 undefined。第 9 步由消费方 release-lookup 调 set，被拒；只有提供方能改值。

第 10、11 步分别测隔离作用域里的同名服务和 get 的 strict 参数：

10. same name in an isolated scope
  root origin=platform, isolated origin=file
11. get(name) vs get(name, false) while the provider is still loading
  provider state during apply=1 (1=LOADING): get=undefined, get(false)={"v":1}
  after apply state=2: get={"v":1}

第 10 步在 root.isolate('releases') 里再挂 FileReleases，没有撞上第 3 步的报错，两个作用域各读到自己的实现。

第 11 步的提供方在 apply 里先 ctx.provide('draft', ...) 再等待。此时它处于 LOADING，默认 get 读不到，get(name, false) 已能拿到值；apply 结束后两者一致。

第 12 步先卸载 release-lookup，免得它的输出混进来，再让 host 插件用 ctx.inject(['releases'], ...) 挂子插件，然后卸载平台版、换上文件版：

12. ctx.inject child follows the provider
  child up, origin=platform
  child down
  after provider dispose: host state=2, child state=0
  child up, origin=file
  after new provider: child state=2
13. dispose root
  child down

after provider dispose 那一行里，提供方消失后，host 仍是 2（ACTIVE），只有子插件退回 0（PENDING）、撤销副作用。新提供方一到，子插件自动重建，读到 file。

这对 Agent 意味着什么

把 releases 从文件版换成平台版，release-lookup 的代码不用动，换的只是挂哪个插件。

换提供方等于让依赖方完整重启；只想换数据就用 ctx.set，插件不会重载，apply 也不重跑。

同一作用域里同名服务只能有一个，第二个提供方直接注册失败，报错会指出已占用该名字的提供方，要并存得用 isolate 分作用域。

可选依赖可以用 ctx.inject 隔离，数据源不在时只有子插件停下，主插件保持 ACTIVE，其余能力照常提供。

本文的验证范围

实测部分是 service-demo.ts，只用 vendor Cordis（4.0.2），没有启动 dsh 的 CLI 或 Web 进程，也没有调用模型；数据是合成的演示数据。状态码和错误信息来自本次运行输出；脚本用 tsx 运行，未单独跑类型检查。

主要结论都有断言：

  • 数据源未提供时插件状态为 PENDING，FileReleases 挂上后为 ACTIVE，查到 demo-001；
  • 同一作用域再挂 PlatformReleases，等待它时抛出含 has been registered 的错误；
  • 在原提供方上 ctx.set 后 ctx.releases.origin 为 file(updated)，apply 没有再次执行；
  • 卸载文件版后插件为 PENDING，挂上平台版后为 ACTIVE，apply 第二次执行并查到 plat-77；
  • set 前存下的引用仍读到 file；卸载文件版后 ctx.get('releases') 为 undefined；
  • ctx.get('releases') 读到的 origin 为 platform；
  • 经消费方读服务，服务的 this.ctx.fiber 是消费方 probe；
  • 不写 inject 读 ctx.releases 抛 without inject；消费方 set 抛 in multiple fibers；
  • isolate 作用域里挂第二个 releases 不报错，两边各读到 platform 与 file；
  • 提供方 LOADING 时 get 为 undefined、get(name, false) 有值；
  • 提供方卸载后 ctx.inject 子插件为 PENDING、宿主仍 ACTIVE，新提供方到来后子插件回到 ACTIVE。

同一脚本在同一环境下连续运行 3 次，输出完全一致。
