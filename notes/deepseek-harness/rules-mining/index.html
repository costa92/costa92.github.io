第 24 / 36 节 · 发布规则实战

三天值班下来，2.3 执行失败了 6 次：规则每天都拦下一次部署，但窗口只有 24 小时，第二天同一个版本又能部署两次。

上一篇把规则存了下来，可以修改、回滚，也可以由模型生成。这一篇从值班 agent 的会话日志里找出现有规则没管住的失败发布，让模型据此提一条候选规则，并附上指回日志的证据。

这次写一个日志挖掘模块，通过 ctx.sessionQuery 读回所有会话里的 deploy_release 调用；再给一个评审会话两个工具，list_anomalies 列出异常，propose_rule 提交候选规则。候选存成规则的新版本，不改生效指针，评测和确认留给下一篇。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 结构化返回值不进日志，只能靠 presentationMeta 带进去；
  • 24 小时窗口下，2.3 三天里被部署 6 次；
  • 被规则拒绝与平台超时，在日志里字段完全相同；
  • 写错的规则和证据被拒，候选存下但不生效。

结构化结果只能靠 meta 进日志

挖日志之前，先看日志里有什么。一次工具调用在会话日志里是两条事件（packages/core/session/src/types.ts:341-365）：

事件字段内容
tool/callcallId、name、arguments原始参数字符串
tool/resultmessage渲染给模型的内容
tool/resulterror结果带 info 时才写
tool/resultmetapresentationMeta 的返回值

message 即 output.render 的结果，meta 本来是给界面回放用的（error 的写入见 packages/core/agent-loop/src/tool-calls.ts:285）。

工具 execute 返回的结构化值本身不进日志。要事后按字段统计，只能让工具把字段放进 meta：

output: {
  schema: { /* service、version、outcome、at */ },
  render: (_args, value) => [{ type: 'text', text: `${value.service} ${value.version} ${value.outcome}` }],
  // 会话日志只存 render 出来的文字；想事后按字段挖，就得把字段放进 meta。
  presentationMeta: (_args, value) => ({ ...value }),
},

presentationMeta 只在没有 parent 的调用上执行（packages/core/tools/src/index.ts:1815，条件是 exec.parent === undefined），而且只在成功时执行。

Code Mode（run_code）里通过 SDK 发起的子调用带 parent（:323-332）。第 1 步在一个单独的对照宿主里，直接调一次部署，再在 run_code 里调一次：

== 1. 对照宿主：Code Mode 里的子调用不生成 meta ==
直接调 deploy_release：tool/result data 字段 [message, meta, step, turn]，presentationMeta 执行 1 次
在 run_code 里调 tools.deploy_release：tool/call 只有 run_code，子调用记成 1 条 tool/ptc-dispatch
  tool/ptc-dispatch 字段 [arguments, content, isError, name, parentCallId, rootCallId, subCallId]
  run_code 的 tool/result data 字段 [message, step, turn]，presentationMeta 执行 0 次

最后一行里，run_code 的结果没有 meta，presentationMeta 一次也没执行；子调用只记成一条 tool/ptc-dispatch，字段里也没有 meta。模型改用 Code Mode 部署，日志里就没有可挖的字段。

workflow 启动的子 agent 里，工具调用是它自己循环里的顶层调用，会生成 meta（按源码，未实测）。

图：值班日志留下 tool/call 与 tool/result，另一个宿主读回分组，评审会话提交候选第 2 版。

被拒与报错在日志里字段相同

宿主挂真实的会话存储、JSONL 持久化、agent 循环，以及上一篇的规则存储，生效的是第 1 版规则“同一版本 24 小时内失败 2 次就拦”。每天开一个值班会话，脚本化模型收到“发布 payment-api 2.3，失败就重试”，连发三次部署，第三次写成 v2.3。

每天结束后把时钟拨快 25 小时，第三天还发布一次会超时的 order-api：

== 2. 三天值班：规则每天拦一次，同一版本每天照样失败两次 ==
第 1 天：规则引擎记下的历史累计 2 条
第 2 天：规则引擎记下的历史累计 4 条
第 3 天：规则引擎记下的历史累计 6 条

历史每天只增加 2 条：每天执行两次、第三次被拦，这些调用都留在三个值班会话的日志里。

换一个宿主，挂上 dsh-session-query-sqlite，只从磁盘上的日志读。挖掘模块用 listSessions() 列出会话，readSession() 读出每个会话的全部事件，把 tool/call 的 callId 和 tool/result 消息里 tool-result 块的 toolCallId 对上：

== 3. 换一个宿主，从会话日志里读回部署 ==
读到 10 次 deploy_release：执行 6，被规则拒绝 3，其他错误 1
  executed data 字段 [message, meta, step, turn]  文字 "payment-api 2.3 failed"
  denied   data 字段 [message, step, turn]  文字 "Error: [same-version-failed@1] payment-api 2"
  error    data 字段 [message, step, turn]  文字 "Error: platform timeout"
  tool/call 里的参数是模型原样给的字符串：{"service":"payment-api","version":"v2.3"}
  对照宿主 抛 HarnessError：data 字段 [error, message, step, turn]  error {"name":"HarnessError","code":"PLATFORM_DOWN"}
  对照宿主 deny 带 info：data 字段 [error, message, step, turn]  error {"name":"ReleaseRuleDenied","code":"LEDGER_FREEZE"}

拒绝那一行的文字只截取了前 44 个字符，完整的拒绝理由是 Error: [same-version-failed@1] payment-api 2.3 在 24 小时内已失败 2 次。

执行成功的结果带 meta，服务、版本、结果、平台时间都在里面。被规则拒绝和平台超时两种失败，data 的字段完全一样，都只有 message、step、turn，没有 error。

第 21 篇说过，守卫拒绝的结果只有 message、没有 info（tools/src/index.ts:1496-1506）。agent 循环只在有 info 时写 error 字段，meta 也只在成功时生成。

error 那一行是工具抛普通 Error（平台超时），同样没有 error 字段。最后两行来自对照宿主：工具抛 HarnessError，或 pre-execute 用 deny 拒绝并带 info（:644-650、:589-593），data 里就多出 error，带着 name 和 code。

挖掘模块只能按文字区分：dsh 给失败结果统一加 Error: 前缀（:1503、:1883），后面紧跟 [规则 id@版本] 的算被拒，其余算其他错误。方括号这一段是本系列规则引擎自己拼的消息格式，换一个守卫就不成立。

tool/call 那一行是第三次调用的参数，日志里存的是模型给的 v2.3。这次调用被守卫拒绝，没有 meta；能和 2.3 合并计数，是因为规则引擎在拒绝文字里写的是规范化后的 2.3。统计执行过的部署用 meta 里平台返回的版本，统计被拒的用拒绝文字里的版本，都不能用原始参数。

异常附上 6 条可回查的证据

本 demo 把“执行且失败”的记录按服务和版本分组，全部时间内的失败次数超过生效规则的阈值，就算规则没管住（不看窗口，也不看当时规则是否已生效）；被拒次数按拒绝文字里的服务和版本计数：

== 4. 找出规则没管住的版本 ==
payment-api 2.3：执行失败 6 次、被拒 3 次，分布在 3 个会话，首尾相隔 50 小时
  当前规则窗口 24 小时；证据是这 6 次失败的 tool/result 事件：
    oncall-day1#10, oncall-day1#15, oncall-day2#10
    oncall-day2#15, oncall-day3#10, oncall-day3#15

2.3 在 3 个会话里执行失败 6 次，首尾相隔 50 小时，远超 24 小时的窗口。证据是这 6 次失败对应的 tool/result 事件，写成 <会话 id>#<seq>。

会话日志只追加，seq 从 0 开始连续编号；readSession 把日志重放进 Session.create（packages/session-query/session-query/src/index.ts:184-191）。第 4 步后半段检查这个编号靠不靠得住，fork 和压缩在对照宿主里试：

readEvent 逐条取回 6 条证据：6 条是 tool/result，toolCallId 与读回时一致
删掉 oncall-day1 日志第 6 行后 readSession -> SESSION_QUERY_CORRUPT_SESSION: invalid committed event at line 5: released v2 row 4 has seq gap (expected 4, got 5)
对照宿主 probe#11（一次原生部署）：fork 出的 probe-fork#11 是同一次调用 true
  手动压缩后日志追加 compaction/start, compaction/summary, user/message, compaction/end
  probe#11 仍是这次调用 true，probe 日志里这次调用的 tool/result 共 1 条
  readSession(probe-fork) -> Error: seeded session constructor seed must equal its inherited prefix
  另起宿主从磁盘读 probe-fork -> 同样报错
  对照宿主上跑 readDeploys -> Error: seeded session constructor seed must equal its inherited prefix

“删掉第 6 行”那一行说明改写会被发现：读日志时 seq 必须连续，缺一行就报 SESSION_QUERY_CORRUPT_SESSION，报错来自日志解码，还没走到 Session.create。

日志没被改写时，6 条证据逐条 readEvent 取回，toolCallId 都对得上。

fork 出的分支和手动压缩后的原会话里，同一个编号仍指向同一次调用，压缩只在日志末尾追加四条事件。反常的是 fork：readSession 读分支直接报错，另起宿主从磁盘读也一样，挖掘模块遍历会话时整个中断。

要挖带分支的日志，得先跳过或单独处理 fork 出的会话。

规则引擎自己的历史表里也有这 6 次失败，但只有服务、版本、结果和时间。日志里还有被拒的 3 次，以及每次调用所在的对话。候选规则附的证据应该指向人能打开看的对话。

模型给的规则和证据都要校验

评审会话里，脚本化模型先调 list_anomalies 拿到上面的异常和证据，再调 propose_rule 提交候选。propose_rule 用 zod 校验规则数据，还要求证据编号是日志里真实存在、确实执行失败的部署。

脚本让模型先犯两次错：

== 5. 让模型据此提候选规则 ==
提交 1：拒绝 Error: 规则不合法：windowHours Invalid input: expected number, received string
提交 2：拒绝 Error: 证据不成立：oncall-day1#3, oncall-day9#12 不是一次执行失败的部署
提交 3：通过 已保存为候选 same-version-failed@2，未生效

第 1 次把窗口写成 '7d'，zod 拒绝。第 2 次规则合法，但证据里的 oncall-day1#3 不是部署结果，oncall-day9 这个会话根本不存在，也被拒绝。拒绝理由作为工具错误结果回到模型，脚本安排的下一步是重新提交。第 3 次窗口改成 168 小时，附上 6 条真实证据，通过。

模型虽然读了 list_anomalies 的输出，交回来的编号仍是它自己生成的文字，可能抄错，也可能编造，证据检查省不掉。

候选存成第 2 版，生效的仍是第 1 版

候选存成规则的第 2 版，生效指针仍然指向第 1 版：

== 6. 候选只是存下来，还没生效 ==
版本 1, 2；生效 same-version-failed@1；候选 2
候选第 2 版：窗口 168 小时，附 6 条证据
第 4 天 deploy(2.3) -> 执行 failed（生效的仍是第 1 版）
试算：指针临时指向第 2 版，同一天再部署 2.3 -> 拒绝 [same-version-failed@2] payment-api 2.3 在 168 小时内已失败 7 次

第 4 天直接调用工具再部署 2.3（不经过模型，也不写会话日志），按第 1 版规则判断，前一天的失败已经出了 24 小时窗口，放行，又失败了一次。

最后一行是试算：把指针临时指向第 2 版、同一天再部署，168 小时窗口里已有 7 次失败，被拦下；试算完指针改回第 1 版。第 2 版是否该生效，要先拿历史数据评测，再由人确认。

这对 Agent 意味着什么

工具返回值不进日志，只有 meta 能带字段，而且只在没有 parent 的成功调用上有，Code Mode 的子调用就没有。需要事后统计的工具，从一开始就该把关键字段放进 presentationMeta。

被规则拒绝和普通报错在日志里字段相同，只能按文字前缀区分；对照宿主里 deny 带上 info，日志就多出 error.code，拒绝最好带一个错误码。合并版本时也别用模型给的参数：tool/call 里是模型的原话，v2.3 和 2.3 要靠平台返回值或规则引擎写进拒绝文字的规范化版本才能合到一起。

证据编号在 fork 和压缩后仍指向原调用，但 readSession 读 fork 出的会话会报错，遍历全部会话的挖掘会整个中断，挖之前要先处理 fork 出的会话。

模型提的规则数据要校验形状，证据编号要与日志中执行失败的调用核对，候选只追加版本，不动生效指针。

本文的验证范围

实测部分是三个文件：规则存储 rule-store.ts、日志挖掘 log-miner.ts、驱动脚本 rules-mining-demo.ts。

rule-store.ts 沿用第 22 篇，版本记录加了 evidence 字段，新增 revision() 和 candidates()，其余配置项本篇没有用到；“候选”定义为版本号大于生效版本的修订，这是 demo 的约定。

脚本挂载真实的 dsh-llm、dsh-session、dsh-session-projection、dsh-session-persistence-jsonl、dsh-session-checkpoint-policy、dsh-session-query-sqlite。

另外还挂载真实的 dsh-system-prompt、dsh-tools、dsh-agent、dsh-agent-loop，以及存储三件套 dsh-storage、dsh-storage-json、dsh-storage-domain，没有启动 dsh 的 CLI 或 Web 进程。

对照宿主用单独的日志目录，dsh-tools 设成 both 模式，另挂 dsh-token-meter、dsh-compaction-basic 和第 20 篇的 PTC 运行时（沙箱、子进程、文件系统、dsh-ptc-runtime-node）；压缩用 compactNow 手动触发，摘要由脚本化模型给出。

模型是脚本化模型，每一轮调哪个工具、传什么参数是预先写好的，其中评审会话的证据编号取自 list_anomalies 的返回；发布平台和时钟是合成的，“三天”是在同一个进程里拨时钟。日志和数据写在系统临时目录，脚本退出时删除。

主要结论都有断言：

  • 直接调用的结果有 meta、presentationMeta 执行 1 次；run_code 只有 1 条 tool/ptc-dispatch，结果和子调用都没有 meta，执行 0 次；
  • 读回 10 次调用，执行 6、被拒 3、其他错误 1；被拒和其他错误的 data 字段相同，且没有 error；
  • 抛 HarnessError、deny 带 info 时 data 有 error，name 与 code 如输出；
  • 只找出一个异常，失败 6 次、被拒 3 次、3 个会话、相隔 50 小时；
  • 6 条证据 readEvent 取回后 toolCallId 一致；删一行后 readSession 报错；
  • fork 和压缩后编号仍指向原调用、原会话里这次调用只有 1 条结果；readSession 读 fork 出的会话报错，从磁盘读相同，readDeploys 随之报同样的错；
  • 三次提交依次因规则不合法、证据不成立被拒，第三次通过；
  • 候选是第 2 版、证据与异常一致、生效的仍是第 1 版，第 4 天部署被执行；指针临时指向第 2 版时同一天的部署被拒。

另外做了变异检查。以下 6 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • 部署工具去掉 presentationMeta；
  • 挖掘模块不再按文字识别被拒；
  • 挖掘模块只读第一个会话；
