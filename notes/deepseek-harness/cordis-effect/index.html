第 5 / 36 节 · Cordis 运行机制

卸载插件后，它的 3 项注册（工具、定时器、缓存）按注册的逆序撤销，事件监听也一并摘掉；依赖的服务消失时，插件不报废，退回 PENDING 等待。

第 3 篇（发布记录查询插件实战）的测试里有一条用例：插件卸载后，lookup_release 工具随之注销。插件代码里没有写任何注销逻辑，只调用了一次 ctx.tools.register()，注销是 Cordis 做的。

这次把 release-lookup 缩成只用 Cordis 的最小版本，除了工具，还注册缓存、定时器和事件监听，逐一检查插件卸载与依赖消失后留下了什么。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 依赖服务未就绪时，插件停在 PENDING，apply 不执行；
  • 卸载后缓存、定时器、工具按注册逆序撤销，监听器不再收到事件；
  • 服务内部登记的工具 effect，随调用方插件卸载而撤销；
  • 依赖服务被卸载，插件退回 PENDING，而不是 DISPOSED。

副作用记在各自的 Fiber 名下

Cordis 核心只有九个源文件，共 2694 行。插件生命周期涉及 Context、Fiber 和 Effect：

  • Context 是服务容器。ctx.tools、ctx.llm 这类属性读取都经过一个 Proxy 解析到对应服务（vendor/cordis/src/context.ts:74 创建 Proxy，解析逻辑在 vendor/cordis/src/reflect.ts:135）。
  • Fiber 是“一次插件应用”的运行实例，持有配置、依赖快照、状态和这次运行的全部副作用（vendor/cordis/src/fiber.ts）。ctx.plugin(x) 返回以它为原型的 thenable 包装，读属性就是读 Fiber（vendor/cordis/src/registry.ts:330-335，第 7 篇细讲）。
  • Effect 是一个带撤销函数的副作用。ctx.effect(execute) 立即执行 execute，把它返回的 disposer 收集起来，卸载时统一调用。

每个插件拿到的 ctx 都是父 Context 的子对象，上面挂着自己的 fiber。

// vendor/cordis/src/fiber.ts
this.ctx = this.context = parent.extend({ fiber: this })

所以插件里调用的 ctx.effect()、ctx.on() 都能找到“当前属于哪个 Fiber”，副作用记在这个 Fiber 名下。

图：对象关系。每个插件的 ctx 派生自父 Context，副作用挂在各自的 Fiber 下。

卸载某个 Fiber，只会拆掉它名下的那一枝。

依赖未到，Fiber 停在 PENDING

FiberState 是一个 const enum，编译后是数字：

值状态源码注释含义
0PENDING等待所需服务
1LOADING插件回调正在执行
2ACTIVE已加载并在提供能力
3FAILED回调或配置抛错
4DISPOSED已移除，不能重启
5UNLOADINGdisposer 正在执行

PENDING 排在最前。插件声明了 inject: ['tools']，而 tools 服务还没出现时，Fiber 不报错，停在 PENDING 等待。dsh 的加载顺序因此靠依赖声明表达，不用手写启动序列。

状态之间怎么转移，要看 _setEpoch()、_reload()、_unload() 和 _getState()。Fiber 把各依赖服务提供方 Fiber 的 uid 拼成一个 epoch 字符串，缺任何一个依赖就是 INACTIVE；epoch 变化驱动加载和卸载：

图：状态转移依据 fiber.ts 的 _setEpoch、_reload、_unload 与 _getState。

后面案例的第 5 步走的就是 ACTIVE → UNLOADING → PENDING 这条路径。

effect 按注册逆序撤销

effect() 的实现约 150 行，大部分在处理异步和并发卸载，下面只摘主干：

// vendor/cordis/src/fiber.ts（节选）
effect(execute: () => Effect, label = 'anonymous'): any {
  this.assertActive()
  if (this.state === FiberState.UNLOADING) {
    throw new CordisError('INACTIVE_EFFECT')
  }

  const disposables: Disposable[] = []
  let disposing = false
  let disposalTask: void | Promise<void>
  const dispose = () => {
    if (disposing) return disposalTask
    disposing = true
    let task!: void | Promise<void>
    for (const disposable of disposables.splice(0).reverse()) {
      // ...依次执行，遇到 Promise 就串起来
    }
    return disposalTask = task
  }
  // ...
}

这段代码对副作用注册和撤销的限制如下：

  1. 已卸载或正在卸载的 Fiber 不能再注册副作用，抛 INACTIVE_EFFECT。这防止卸载过程中又“长出”新资源。
  2. disposer 按注册的逆序执行（.reverse()）。后建的资源先拆，和栈一样。
  3. disposer 只执行一次。disposing 标志让重复调用直接返回同一个任务。

第 1、3 条分别由后文案例第 8、7 步实测。

把 effect() 和 Fiber 卸载连起来看，一个副作用从注册到撤销的流程如下：

图：effect 内部串行逆序撤销；Fiber 卸载时各项副作用按逆序启动、并发等待。

execute 的返回值可以是四种形状（vendor/cordis/src/fiber.ts:83）：一个 disposer、一个 yield 多个 disposer 的同步生成器；返回 disposer 的 Promise 或异步生成器也可以（按源码，未实测）。生成器适合“一个副作用由几步组成”的场景，每 yield 一个就登记一个撤销动作。

dsh 自己的插件就这样用。goal-round-driver 在同一个生成器 effect 里注册了 10 个事件监听，最后 yield 一个等待调度任务收尾的 async disposer（按源码，未实测；packages/goal/goal-round-driver/src/index.ts:245）。

源码注释说明了顺序的用意：这个 disposer 在监听之后登记，撤销时最先执行，等它 settle 之后才摘掉监听，收尾期间 step fence 一直在。案例第 9 步按同样写法复现，结果与注释不符，见后文。

// One composite effect keeps the step fence installed until this
// plugin's own scheduling tasks settle.
ctx.effect(function* () {
  ctx.on('agent/error', ...)
  ctx.on('agent/disposed', ...)
  ctx.on('agent/created', ...)
  ctx.on('agent/status', ...)
  // ...另有 6 个监听
  // Yielded after listener registration, so this close runs first and the
  // composite effect removes listeners only after its promise settles.
  yield async () => { /* 等待调度任务 settle */ }
})

docs/cordis-primer.zh.md 把这条总结为实践规则：每个注册都应有对应的 disposer；teardown 顺序有要求时，把相关工作放在同一个 effect 里。

release-lookup 卸载后什么都不剩

读源码只能得到“应该如此”。下面的脚本把第 3 篇的 release-lookup 缩成 Cordis 层面的最小版本，不加载 dsh 的 ToolRuntime，只用 vendor 里的 Cordis：

  • Toolbox 服务模拟 ctx.tools，register() 用 ctx.effect 登记工具；
  • release-lookup 插件注册工具，开一个缓存定时器，再监听 release/changed 事件。

脚本位于 scratch-plugin/effect-demo/effect-demo.ts（获取与运行命令见文末“本文的验证范围”）。正文只贴 Toolbox 和插件的定义，步骤驱动代码与断言从略，完整脚本见示例仓库：

/** Minimal stand-in for ctx.tools: a name → description map. */
class Toolbox extends Service {
  tools = new Map<string, string>()
  constructor(ctx: Context) { super(ctx, 'toolbox') }
  register(name: string, description: string) {
    return this.ctx.effect(() => {
      this.tools.set(name, description)
      log(`  + tool ${name}`)
      return () => { this.tools.delete(name); log(`  - tool ${name}`) }
    }, `toolbox.register("${name}")`)
  }
}

const seen: string[] = []
const releaseLookup = { name: 'release-lookup', inject: ['toolbox'], apply(ctx: Context) {
  ctx.toolbox.register('lookup_release', 'query release history')
  ctx.effect(function* () {
    const timer = setInterval(() => {}, 60_000)
    log('  + cache timer')
    yield () => { clearInterval(timer); log('  - cache timer') }
    log('  + cache map')
    yield () => { log('  - cache map') }
  }, 'release cache')
  ctx.on('release/changed', id => { seen.push(id); log(`  release changed: ${id}`) })
} }

插件用了 { name, inject, apply } 对象形式。dsh 的插件文件用 export const name + export function apply，导出的模块同样相当于对象形式。

脚本先加载插件、再提供 Toolbox，输出的第 1、2 步：

1. load plugin before toolbox exists
  state=0 (0=PENDING)
2. provide toolbox
  + tool lookup_release
  + cache timer
  + cache map
  state=2 (2=ACTIVE) tools=lookup_release
  release changed: demo-003

第 1 步里，插件先于 Toolbox 加载却没有报错，state=0 之前也没有任何 + 行，apply 没有执行，依赖没到就一直等着。第 2 步 Toolbox 提供后，插件自动进入 ACTIVE，三项注册依次完成。

自动激活不靠脚本编排，脚本里没有任何“等 Toolbox 好了再加载插件”的代码。最后一行 release changed: demo-003 来自脚本随后发出的一次 release/changed，说明监听器也已挂上。

第 3 步卸载 release-lookup，再发一次 release/changed：

3. dispose release-lookup
  - cache map
  - cache timer
  - tool lookup_release
  tools=[]
  (no listener output above)

三行 - 的顺序与第 2 步的 + 正好相反，插件代码里却没有写任何注销逻辑。之后再发 release/changed，监听器没有输出，ctx.on 同样是可撤销的副作用。

逆序分两层。缓存和定时器在同一个生成器 effect 内，由 disposables.splice(0).reverse() 严格串行撤销。

工具和这个缓存 effect 是 Fiber 上的两项独立副作用，由 _unload() 按 _disposables.clear() 返回的逆序启动。本例的 disposer 都是同步函数，所以输出严格有序；异步时的情形见第 10 步。

注册归调用方，依赖消失就退回等待

第 3 步里的工具撤销值得单独看。工具是在 Toolbox 服务内部用 this.ctx.effect 登记的，却随 release-lookup 卸载被撤销，没有等到 Toolbox 卸载，说明这个 effect 记在了调用方插件的 Fiber 名下。

dsh 里 ctx.tools.register() 不需要插件手动注销，同样因为副作用记在发起注册的插件名下。背后的机制在服务调用链的上下文追踪，第 5 篇讲 Service 时展开。

第 4 步对已卸载 Fiber 的 ctx 再调一次 effect：

4. effect on disposed fiber
  Error: INACTIVE_EFFECT

调用抛出 code 为 INACTIVE_EFFECT 的错误，对应 assertActive()，卸载后不能再注册。

第 5 步重新加载插件，再卸载它依赖的 Toolbox：

const again = root.plugin(releaseLookup)
await again
await toolboxFiber.dispose()
log(`  dependent state=${again.state} (0=PENDING)`)

输出：

5. dispose toolbox while a new plugin depends on it
  + tool lookup_release
  + cache timer
  + cache map
  - cache map
  - cache timer
  - tool lookup_release
  dependent state=0 (0=PENDING)

依赖消失后，插件的三项注册全部撤销，状态回到 0（PENDING），不是 4（DISPOSED）。激活状态随依赖的有无切换，这就是“响应式依赖”。

第 6 步再提供一次 Toolbox：

6. provide toolbox again
  + tool lookup_release
  + cache timer
  + cache map
  dependent state=2 (2=ACTIVE) tools=lookup_release

同一个 again Fiber 重新执行 apply，三项注册再次完成，状态回到 2（ACTIVE），脚本没有重新调用 root.plugin。驱动它的是 _setEpoch（vendor/cordis/src/fiber.ts:625-638）。

异步撤销只在同一个 effect 内保序

第 7、8 步分别验证前面的第 3 条和第 1 条：同一个 disposer 连调两次；在 disposer 里再调 ctx.effect：

7. call one disposer twice
  disposer ran 1 time(s)
8. effect while the fiber is unloading
  state=5 (5=UNLOADING)
  Error: INACTIVE_EFFECT

第 7 步计数停在 1，第二次调用没有再执行撤销。第 8 步的 disposer 运行时 Fiber 处于 5（UNLOADING），此时注册同样被拒。

第 9 步复现 goal-round-driver 的写法：生成器里先 ctx.on 挂监听，最后 yield 一个 async disposer，它开头 emit 一次事件。bare-on 照原样不 yield 监听，yield-on 把 ctx.on 的返回值也 yield 进去：

9. async disposer yielded last in a generator effect
  bare-on: async disposer start, emit bare-on
  bare-on: async disposer end
  yield-on: async disposer start, emit yield-on
  listener still on: yield-on
  yield-on: async disposer end

bare-on 和注释对不上：async disposer 一开始 emit，监听已经没有输出，并没有“等它 settle 之后才摘掉监听”。

生成器 effect 只收集 yield 出来的 disposer（_execute 里的 safeCollect），没 yield 的 ctx.on 是 Fiber 上另一项更晚登记的副作用，卸载时先被撤销。

只有 yield-on 在收尾期间还收得到事件。

第 10 步在同一个插件里用两个独立 effect 各登记一个 async disposer：A 等 10ms、先登记，B 等 50ms、后登记：

10. two async effects on one fiber unload concurrently
  B(50ms) start
  A(10ms) start
  A(10ms) end
  B(50ms) end

B 后登记先启动，符合逆序；但 A 没等 B 结束就开始，还先结束。_unload() 用 Promise.all 并发等待，逆序只管启动，不管完成。有顺序依赖的异步撤销要 yield 进同一个 effect。

这对 Agent 意味着什么

插件卸载时，它注册的工具、定时器和监听器按逆序全部撤销，不会留下“幽灵工具”让模型继续调用。

依赖的服务被卸载时，插件同样撤掉全部注册、回到 PENDING，等服务重新出现再自动恢复。

卸载途中或卸载之后再注册副作用，会直接抛 INACTIVE_EFFECT，插件移除后不会又长出新资源。

收尾时 async disposer 如果还要响应事件，监听必须 yield 进同一个生成器，只用 ctx.on 挂的监听会先被摘掉。

本文的验证范围

实测部分是 effect-demo.ts，只用 vendor Cordis（4.0.2），没有启动 dsh 的 CLI 或 Web 进程，也没有调用模型；运行环境为 Node v22.22.0，脚本用 tsx 运行，未单独跑类型检查。状态码依据 FiberState 源码与本次输出。

脚本最初把插件写成 Object.assign(fn, { name: ... })，运行时报 Cannot assign to read only property 'name' of function：函数自带的 name 属性只读，因此改用对象形式。

主要结论都有断言：

  • 插件先于 Toolbox 加载时状态为 PENDING，Toolbox 提供后为 ACTIVE；
  • 卸载 release-lookup 后工具表为空，之后再发 release/changed，监听器只收到过卸载前的 demo-003；
  • 对已卸载 Fiber 的 ctx 调用 effect 抛出 code 为 INACTIVE_EFFECT 的错误；
  • 卸载 Toolbox 后，依赖它的插件回到 PENDING；再提供 Toolbox，同一 Fiber 回到 ACTIVE、工具恢复；
  • 同一个 disposer 调两次只执行一次；UNLOADING 期间调用 effect 抛 INACTIVE_EFFECT；
  • 生成器里没 yield 的监听在 async disposer 开始前已摘除，yield 的监听收尾期间仍在；
  • 两个独立 async disposer 逆序启动、并发完成（后启动的 A 先结束）。

同一脚本在同一环境下连续运行 3 次，输出完全一致。
