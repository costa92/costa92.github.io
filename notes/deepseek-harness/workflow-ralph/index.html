第 21 / 36 节 · Agent 编排

3 个子 agent 里一个模型请求失败，结果只剩 null，run 仍报 completed；给 agent() 多写一个 effort 选项，整个 run 直接失败。

第 19 篇的子 agent 派几个、派给谁，都由模型在对话里一次次决定。本篇看 packages/workflow 给出的另两种做法：让模型写一段编排脚本一次跑完，或者用部署方写死的循环一轮一轮推进。

这次拿同一个“巡检 3 个服务最近一次发布”，先让模型写成 workflow 脚本并行派 3 个子 agent，其中一个的模型请求失败；再用 ralph 固定循环跑 3 轮。然后看两种写法在子 agent 出错、报告不合格、超出上限时怎么表现；最后让子 agent 在 workflow 里再开 workflow，看深度上限管不管得住。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • workflow 的子 agent 失败只得到 null，run 仍报成功；
  • 给 agent() 多写一个选项，整个 run 失败；
  • Ralph 凭一句“都查过了”就算完成；
  • workflow 嵌套越过深度上限，子 agent 到了第 4 层。

四个包，Ralph 默认关着

packages/workflow 下有 4 个包：

  • dsh-workflow 定义 ctx.workflowEngine 这个接口：启动请求、运行句柄、结果和 workflow/* 事件。每个上下文只有一个引擎。
  • dsh-workflow-ptc 是引擎的实现，脚本里的每个 agent() 通过 ctx.subagents 起一个子 agent。
  • dsh-tool-workflow 给模型一个 workflow 工具，参数是脚本、meta 和 args。
  • dsh-tool-ralph 给模型一个 ralph 工具，参数只有目标和可选的轮数上限。循环脚本是写死在包里的。

workflow-ptc 把脚本交给 PTC 运行时（dsh-ptc-runtime-node，本系列还没有单独讲过），在一个单独的 Node 进程里执行，进程受调用会话的沙箱策略约束（packages/workflow/workflow-ptc/src/index.ts:166），下文第 1 步实测了本机上的效果。

基础组合（base bundle）里挂了 PTC 运行时、workflow-ptc 和 tool-workflow（packages/bundle/base/cordis.patch.yml:376-385）。tool-ralph 那一行是 disabled: true，打开时轮数上限配成 64（:433-438）。

demo 按这套挂载，把 ralph 打开，上限设成 5 轮。

两个工具都附带一段系统提示，要求只在用户明确要求时才用（packages/workflow/tool-workflow/src/index.ts:211-215，packages/workflow/tool-ralph/src/index.ts:405-409）：

  • workflow： 用户要 workflow 或大规模多 agent 编排时；
  • Ralph： 用户明确要 Ralph 循环或“每轮全新 agent 迭代”时。

图：workflow 与 ralph 在 PTC 进程跑脚本，经 ctx.subagents 起子 agent。

模型写的 workflow 里子 agent 失败，run 仍是 completed

脚本化的父 agent 调 workflow，脚本用 parallel() 给 3 个服务各派一个子 agent，其中查 payment-api 的那个子 agent，模型请求直接抛错：

== 1. 模型写的 workflow：一个子 agent 失败，整个 run 仍是 completed ==
脚本：
  const results = await parallel(args.services.map(s => () => agent('查 ' + s, { label: s })))
  return { results, globals: [typeof setTimeout, typeof require, typeof fetch, typeof process] }
工具结果首行：workflow "release-patrol" completed (3 agents).，isError=false
results：["order-api: demo-007 succeeded",null,"user-api: demo-011 succeeded"]
脚本里 setTimeout/require/fetch/process：undefined / undefined / undefined / undefined
父会话日志里的 tool-workflow/agent-end（除 runId）：seq 1 ["outcome"] completed；seq 2 ["outcome"] failed；seq 3 ["outcome"] completed
脚本里 agent.constructor('return process')() -> typeof pid = number
  写工作区外的文件 -> EROFS，宿主上存在：false
  写工作区内的文件 -> ok，宿主上存在：true

失败的子 agent 在结果里只是一个 null。agent() 等到子 agent 结束：结束原因不是 completed，或者传了 schema 却没拿到结构化结果，都返回 null，不抛错（packages/workflow/workflow-ptc/src/runtime.ts:207-222）。

parallel() 和 pipeline() 遇到普通异常，也和 agent() 一样把这一项变成 null，其他项照常返回。写错选项、超出总数上限、run 被取消则会终止整个脚本，下文第 2 步都实测了；基础设施故障同样如此（按源码，未实测；:296-307、:325-339、:196-206）。

脚本正常 return，整个 run 就是 completed，返回普通结果“completed (3 agents)”并附上返回值。3 个里包括失败的那一个。run 开始以后，workflow 工具只在结束原因不是 completed 时报错（tool-workflow/src/index.ts:179-192、:303-308）。

失败的原因没有传回来，模型看到的只有一个 null；父会话日志也只记 outcome: failed（tool-workflow/src/index.ts:106-115），见输出里 agent-end 那一行：每条记录除了编号只有 outcome 一个字段。

脚本如果只拼接非空结果，汇总里会直接少掉 payment-api，而它恰恰是发布失败的那个服务（demo 特意让它的子 agent 出错）。

工具描述写明：agent() “Resolves null when the child fails (filter with .filter(Boolean))”（tool-workflow/src/index.ts:142）。照括号里的建议滤掉 null，失败的服务会从结果里无声消失。

要不要检查 null、怎么处理，都由模型生成的脚本决定。

setTimeout 那一行显示的是脚本的运行环境。

除了 JSON、Promise 这类 JS 内置对象，宿主只注入了 agent、parallel、pipeline、phase、log 和 args（workflow-ptc/src/runtime.ts:83-98），没有提供定时器、require、fetch 和 process。

按设计，读写文件、联网都交给子 agent 去做。不过 vm 上下文不是安全边界：最后三行是另一个脚本，借宿主注入的 agent 函数拿到了 process。

管住这个进程的是 PTC 的沙箱。本机是 Linux，工作区外的文件写不进去（EROFS），工作区内照常写入；其他平台上由各自的沙箱实现约束这个进程（按源码，未实测）。

写错一个选项，整个 run 失败

同一个脚本，只是给 agent() 多传了一个 effort: 'high'：

== 2. 同一个脚本写错一个 agent() 选项：整个 run 失败 ==
isError=true：workflow run failed: …
  …agent() option "effort" is deferred and not supported by this engine
后面还跟着 10 行调用栈，第 1 行：at WorkflowExecution.readAgentOptions (dsh-workflow-guest.js:887:47)
meta.name 为空 -> isError=true：Error: invalid meta: meta.name must be a non-empty string（没有起脚本进程：true）
maxTotalAgents 2、parallel 3 个 -> stopReason=error agentsStarted=2
  WorkflowError: this run reached its total agent cap (2)
子 agent 卡住时取消 run -> stopReason=cancelled error=workflow run cancelled: demo cancel

报错的是 effort 这个选项：agent() 只接受 label、phase、schema、provider、model 五个选项。调用栈来自执行脚本的那个 Node 进程，行数随版本变化，demo 只断言了首行之后都是调用栈。

effort、isolation、agentType 是 Claude Code 动态工作流里有、这里延后实现的选项，会被明确拒绝（workflow-ptc/src/runtime.ts:33-35、:252-258）。

写错选项属于致命错误，parallel() 不会把它变成 null，会直接终止整个脚本（:304）。

后四行是其他三种情况，后两种直接调引擎：meta 不合法在开跑前就报错，没有起脚本进程；parallel() 里第 3 个子 agent 超出总数上限，整个 run 以 error 结束；子 agent 卡住时取消，run 以 cancelled 结束。

子 agent 出了问题，run 照样报成功；脚本里一个拼写错误，整个 run 却失败。子系统文档（docs/subsystems/workflow.zh.md）给的理由是：拼错的选项必须明确报错，不能看上去像一次普通的子 agent 失败。

Ralph 是固定循环，每轮一个新 agent

同一个巡检目标交给 ralph，maxRounds: 4。脚本化的 worker 不做实际查询，每轮直接交一份预先写好的报告：前两轮报 continue（摘要写“查完了 order-api”等），第 3 轮报 complete，证据只有一句“都查过了”。

跑一下这个循环：

== 3. ralph：固定循环，每轮一个全新子 agent，只交接一份报告 ==
工具结果首行：Ralph worker reported completion after 3 rounds.
最终报告：status=complete evidence=["都查过了"]
共 3 个 worker，各自第一次请求的消息数：3, 3, 3
第 2 轮收到的交接：{"status":"continue","summary":"查完了 order-api","evidence":["order-api: demo-007 …
worker 的工具表里有 ralph：true，有 workflow：true
worker 第三条消息的开头：Current runtime context. This snapshot s…

首行说 worker 在第 3 轮报告完成，最终证据只有一句“都查过了”。Ralph 自己就是一段 workflow 脚本，写死在 tool-ralph 里（tool-ralph/src/index.ts:88-175）。

每一轮调一次 agent()，要求子 agent 按固定 schema 交一份结构化报告：状态、摘要、证据、下一步、阻塞原因。子 agent 通过 structured_output 工具提交这份报告。

每个 worker 都是全新的 spawn 子 agent，第一次请求里只有 3 条消息：系统提示、这一轮的任务，以及运行时上下文（输出末行）。

任务文字里写着不可变的目标、当前轮次，以及上一轮的报告原文（:152-160）。第 2 轮收到的就是第 1 轮那份 JSON。两轮之间传递的只有这份报告，更多的状态要靠共享工作区。

“完成”的判定和第 18 篇的 goal 一样，由 worker 自己说了算。固定脚本只检查报告的格式：摘要和每条证据、下一步都必须非空、不带首尾空白，blocker 不能带首尾空白，整份报告不超过 maxHandoffChars（:102-122、:142-145）。下一节第 4 步测了摘要多一个空格和报告超长两种。

complete 还必须至少有一条证据、没有下一步、阻塞为空（:129-133）。“都查过了”满足这些条件，所以被接受。工具的结果文本也写明了这一点：是“worker reported completion”，不是验证过的完成。

worker 的工具表里仍然有 ralph 和 workflow。任务文字里有一句“Do not call the ralph tool”，但这只是提示，没有从结构上禁止。设计笔记（2026-07-16-harness-level-loop.zh.md）自己也写了：“提示词指导不是强制执行”。

Ralph 出错就停，失败的一轮不重试

接着让第 2 轮的 worker 模型请求失败、让 worker 交一份证据为空的 complete、让父 agent 要 50 轮，再试几种报告和配置：

== 4. ralph 的其他结局：出错、报告不合格、受阻、轮数用完、超上限 ==
第 2 轮出错 -> isError=true：Error: Ralph round 2 child failed before producing a structured report.
  下一行：Last successful handoff:，后面是第 1 轮的报告；这次一共起了 2 个 worker
完成但证据为空 -> isError=true：
  …a complete Ralph report needs evidence, no nextSteps, and an empty blocker
maxRounds 50 -> isError=true：Error: Ralph maxRounds 50 exceeds the deployment ceiling 5
摘要末尾多一个空格 -> isError=true：
  …Ralph round report summary must be non-empty and normalized
第 2 轮报 blocked -> isError=false：Ralph worker reported a blocker after 2 rounds.
每轮都 continue、maxRounds 2 -> isError=false：Ralph reached its 2 rounds limit; the worker reported work remaining.
不配 maxRounds 的 ralph，maxRounds 300 -> Error: Ralph maxRounds 300 exceeds the deployment ceiling 256
maxHandoffChars 200、报告 322 字符 -> isError=true：
  …Ralph round report exceeds maxHandoffChars (322 > 200)

和 workflow 不同，Ralph 的固定脚本会检查 null：某一轮的子 agent 失败，循环立即停下，返回 round-failed（:166-168）。

工具把它变成错误，并附上最后一份有效交接（:383-390、:463）。

失败的一轮不会重试：第 2 轮出错的那次一共只起了 2 个 worker。如果是基础设施故障导致子 agent 的结果直接 reject，run 以 error 结束，报错里不带交接（按源码，未实测）。

报告不合格时，脚本自己抛错，run 以 error 结束，工具同样报错：证据为空、摘要带空格、超过 maxHandoffChars 都是这样。

blocked 和轮数用完不算出错：isError=false，首行分别写“reported a blocker”和“reached its 2 rounds limit”。

轮数上限由部署配置给出：模型传的值不能超过它，不传就取上限（基础组合配 64；包默认 256，脚本换了一份不配 maxRounds 的 ralph 验证），超过就在开跑前拒绝（:206-215）。解析后的轮数同时作为这次 run 的子 agent 总数上限传给引擎（:450）。

workflow 里套 workflow，深度上限管不到

第 19 篇测过，subagent 工具默认只允许一层子 agent。workflow 的子 agent 工具表里有 workflow，于是让它再开一个 workflow，一层套一层，套 3 次，最里面那个再用 subagent 派一个：

== 5. 深度：subagent 工具只许一层，workflow 里套 workflow 不受这个限制 ==
各层子 agent 的 delegationDepth：1 -> 2 -> 3 -> 4
第 4 层用 subagent 再派一个 -> Error: subagent depth 5 exceeds maxDepth 1
这次嵌套一共起了 4 个执行脚本的进程
preset 行 restrict { deny: [workflow] }：父 agent 工具 lookup_release, ralph, subagent
  它的 workflow 里的子 agent 再开 workflow -> Error: unknown tool "workflow"

子 agent 的深度照常加 1，记在会话头部，一直到了第 4 层。只有最后那次 subagent 调用被深度上限拒掉，前面 4 层都是 workflow 开出来的。

workflow 引擎起子 agent 时既不传 maxDepth，也不带 toolFilter（packages/workflow/workflow-ptc/src/host.ts:200-211）。

第 19 篇讲过，深度上限的默认值 1 是 subagent 工具在调用时读宿主设置、填进请求的；请求里不带 maxDepth，服务只把深度加 1，不做比较（packages/subagent/subagent/src/child-agent.ts:50-58）。

设计笔记（2026-07-05-dynamic-workflows.zh.md）把“嵌套 workflow()”列为延后功能，指的是脚本里没有这个钩子。子 agent 调 workflow 工具再开一个 run，走的是另一条路，不受这条延后规定管。

每个新的 run 各自起一个执行脚本的 Node 进程：4 层嵌套是 4 个 run，脚本数到 4 个进程。每个 run 也有自己的子 agent 总数上限，默认 1000（按源码，未实测）。

要挡住嵌套，得把限制写进子 agent 会继承的地方。最后两行，父 agent 所在 preset 拉黑了 workflow，引擎起的子 agent 加入同一个 preset，再开 workflow 就是 unknown tool。

workflow 靠模型自觉，Ralph 靠部署方写死

workflowralph
编排由谁写模型每次现写脚本部署方写死
子 agent 间传什么脚本变量，随意上一轮的结构化报告
一个子 agent 失败变 null，run 仍 completed停下报错，附上一份交接
用法写错整个 run 失败模型碰不到脚本
完成由谁判定脚本 return 就算worker 自报，只查格式
上限并发数、总数、单次项数部署配置的轮数
基础组合开着关着

workflow 上限有三项：并发数默认 min(16, max(1, availableParallelism() - 2))，随逻辑核数变化；总数 1000（按源码，未实测）；每次 parallel()/pipeline() 4096 项（workflow-ptc/src/index.ts:105-111、:141-143）。

直接调引擎试并发数和项数：

== 6. workflow 的并发与单次项数上限 ==
本机 availableParallelism() = 28；parallel 20 个子 agent，同时在跑最多 16 个，最后拿到 20 份结果
parallel 4096 项 -> stopReason=completed value=4096
parallel 4097 项 -> stopReason=error：WorkflowError: parallel() received 4097 items — over the per-call cap (4096)

本机 28 个逻辑核，并发封顶 16；项数 4096 能过，4097 整个 run 报错。

这对 Agent 意味着什么

workflow 结果里的 null 就是失败，只是不知道原因。只看“completed (3 agents)”会以为全部成功，所以要逐项检查：汇总前先数一数有几个 null，至少在结果里说明哪几项没查成。

Ralph 的循环凭一句“都查过了”就能结束，它的“完成”要自己验证，需要的话在报告之外再对照清单检查一遍。

本例中子 agent 在 workflow 里一路开到第 4 层，只有最后那次 subagent 调用被拒。子 agent 的工具表里只要还有 workflow，就不能指望深度上限限制嵌套；实测在 preset 里拉黑 workflow 才挡住。

本文的验证范围

实测部分是 workflow-demo.ts。它挂载真实的 dsh-workflow-ptc、dsh-tool-workflow、dsh-tool-ralph、dsh-ptc-runtime-node、本地沙箱与沙箱策略（workspace-write，工作区在临时目录）、本地子进程与文件系统。

还挂载真实的 dsh-subagent 和 spawn 后端、dsh-tool-subagent、dsh-agent-presets、dsh-agent-loop、dsh-tools、dsh-system-prompt。

workflow 脚本真的在 PTC 起的 Node 进程里执行，没有启动 dsh 的 CLI 或 Web 进程。数进程时，脚本包了一层 ctx.subprocess.spawn 计数。

模型是脚本化模型，父 agent 每一轮调哪个工具、传什么脚本是预先写好的；子 agent 按任务文字决定动作，Ralph worker 的报告也是预先写好的；发布数据是合成的。

主要结论都有断言：

  • workflow 的工具结果首行、isError、返回值里的 null，以及脚本里 4 个全局都不存在；
  • agent-end 记录只有 outcome，脚本拿到 process、工作区外写入 EROFS 且宿主上没有文件、工作区内写入成功；
  • 写错选项时的错误首行，以及后面全是调用栈；
  • meta 不合法的报错且没起进程，超出总数上限和取消时的 stopReason 与报错；
  • Ralph 的结果首行、最终证据、3 个 worker 的任务开头、各自第一次请求只有 3 条消息（system、user、user）、第 2 轮收到的交接等于第 1 轮的报告、worker 工具表里有 ralph 和 workflow；
  • worker 第三条消息是运行时上下文；
  • Ralph 第 2 轮失败的报错、附带的交接和 worker 数，证据为空、摘要带空格、报告超长被拒，超出上限被拒，blocked 与轮数用完的首行，包默认上限 256；
  • 嵌套时各层深度是 1、2、3、4，第 5 层的报错，进程数 4，preset 拉黑后的 unknown tool；
  • 并发峰值等于 min(16, max(1, availableParallelism() - 2))，4096 项通过、4097 项报错。

另外做了变异检查。以下 7 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • 让 payment-api 的子 agent 不再失败；
  • 把 effort 换成合法的 label；
  • 把“都查过了”的证据删掉；
  • Ralph 的部署上限改成 100；
  • subagent 的深度上限改成 5；
  • worker 报告的摘要末尾多一个空格；
  • preset 的 restrict 不再拉黑 workflow。

连续 5 次运行，以及 4 个进程并发运行，输出都一致。
