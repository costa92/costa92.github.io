第 28 / 36 节 · 扩展与外部接入

经 MCP 接入后，平台上的 2.3 失败了 3 次，规则引擎的历史是 0 条。服务器回复前崩溃时，部署已经成功，模型拿到的只有 Connection closed。

前面各篇的 deploy_release 都是宿主里用 defineTool 注册的本地工具。真实的发布平台更可能以 MCP（Model Context Protocol）服务器的形式提供，由 agent 作为客户端接入。

这次把合成发布平台放进一个手写的本地 MCP 服务器，用 dsh-mcp-client 接入，再把第 21 篇的规则引擎和第 24 篇的审批挂上去，看 MCP 工具在注册表里长什么样、规则和审批还管不管用、服务器崩溃和重连时会发生什么。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 规则引擎按工具名和结果字段认部署，两处都对不上，历史 0 条；
  • 版本号传成数字，守卫放行，dsh 不校验参数，部署照样执行；
  • 服务器回复前崩溃，部署已执行，模型只看到 Connection closed；
  • 重连预算耗尽后，工具被移出注册表。

接入后，模型只拿到名字、描述和参数

服务器没有用 SDK，是一个约 60 行的脚本：从标准输入逐行读 JSON-RPC 请求，回答 initialize、tools/list、tools/call 和 ping，其余请求回 -32601。

服务器声明一个 deploy_release 工具，带 inputSchema、outputSchema 和 annotations（destructiveHint: true），初始化时返回一句 instructions。每次启动、每个请求、每次部署都记进一个账本文件，demo 从账本核对平台上实际发生了什么。

接入后看注册表和模型拿到了什么：

== 1. 接入后，注册表和模型看到什么 ==
模型拿到的工具：mcp__release__deploy_release
工具 schema 的字段：description, name, parameters
parameters 与服务器的 inputSchema 相同：true
服务器声明的 annotations（destructiveHint）和 outputSchema 没有交给模型
服务器另报两个名字不合规的工具 deploy.release 和 deploy_x…x（67 个字符）：
  mcp__release__deploy_release（28 个字符）
  mcp__release__deploy_release_f9785fed4e72（41 个字符）
  mcp__release__deploy_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxx_af0824b90844（64 个字符）
只挂审批服务、不配 ask 规则：审批请求 0 次，部署直接执行：payment-api 2.4 succeeded
工具定义的 isConcurrencySafe：undefined；一条消息两个调用（每个 300 毫秒），服务器上：deploy → reply → deploy → reply

工具名加了服务器前缀，公开名是 mcp__<serverName>__<原名>，serverName 取自本地配置，不用服务器自报的名字（packages/mcp/mcp-client/src/tools.ts:81-87）。服务器收到的仍是原名 deploy_release。

输出第 5 到 8 行是另一台宿主，服务器多报了两个名字不合规的工具。deploy.release 的点换成了 _，后面还接了 _ 和 12 位哈希，不会和合规的 deploy_release 撞名；超长的名字截到 51 个字符再接哈希，总长 64（:81-87）。

dsh 的工具定义只取 name、description、inputSchema、outputSchema 和 execution.taskSupport（:131-141），annotations 就丢了。输出第 4 行是 demo 写死的文字，实测断言的是 schema 只有三个字段。

dsh 的 ToolDefinition 没有“只读”“有破坏性”这类字段（packages/core/tools/src/index.ts:216-282）。倒数第二行：宿主挂了审批服务但没配 ask 规则，标了 destructiveHint 的部署没有触发审批，直接执行了。

和 readOnlyHint 沾边的只有调度用的 isConcurrencySafe（:263），桥接也不设。最后一行：一条消息里的两个部署，服务器上是一个回复完才收到下一个，按独占调度。

outputSchema 由 SDK 用来校验 structuredContent，dsh 把它放进结果 schema；发给模型的只有 name、description、parameters（mcp-client/src/tools.ts:250-266、tools/src/index.ts:1261-1263）。

图：带前缀的工具名先审批再过守卫，不校验参数；客户端用原名调用，结果在 structuredContent 里。

接一台服务器起两个进程，说明原样进系统提示

同一次运行的第 1 步接着输出系统提示、进程、环境变量和说明长度上限：

系统提示里多了一段，服务器给的 instructions 原样拼在后面：
  ### MCP server: release
  Always look up the latest release before deploying.
一次连接启动服务器进程 2 次：start → server/discover → start → initialize → tools/list
宿主进程有 RELEASE_API_TOKEN，服务器进程里：absent、absent
宿主进程有 DSH_DEMO_MARKER，服务器进程里：absent、absent
maxInstructionBytes 设成 10：
  connection attempt failed: Error: mcp-client(release): server instructions exceed maxInstructionBytes (10)
  connection failed; retrying in 20ms (attempt 1/3)
  connection attempt failed: Error: mcp-client(release): server instructions exceed maxInstructionBytes (10)
  connection failed; retrying in 40ms (attempt 2/3)
  connection attempt failed: Error: mcp-client(release): server instructions exceed maxInstructionBytes (10)
  connection failed; retrying in 80ms (attempt 3/3)
  connection attempt failed: Error: mcp-client(release): server instructions exceed maxInstructionBytes (10)
  giving up after 3 consecutive failed reconnect attempts
  服务器进程启动 8 次，注册的 MCP 工具 0 个

连接成功后，服务器的 instructions 去掉末尾空白、加上一行标题（packages/mcp/mcp-client/src/connection.ts:318-319）。

带标题的 instructions 作为 mcp:<serverName> 段放进系统提示（packages/mcp/mcp-client/src/server-context.ts:32-38）。服务器写进系统提示的内容，只受长度限制。

长度上限默认 32,768 字节（含标题，maxInstructionBytes 可调，mcp-client/src/connection.ts:49）。输出后半段把上限设成 10 字节：每次连接都因说明超长失败，进入重连退避（:320-322、:324-331）。4 次尝试起了 8 个进程，预算耗尽后放弃，工具一个也没注册。

一次连接启动两个进程，起因是 dsh 把 SDK 的版本协商设为 auto（mcp-client/src/connection.ts:262）。

SDK（@modelcontextprotocol/client 2.0.0）在 stdio 下先起一个一次性的兄弟进程，发 server/discover 探测协议版本，探完回收，再启动正式的服务器进程（SDK dist/index.mjs 中的 negotiateStdioViaSibling）。

dsh 的 README 也写了一次连接会启动两个进程（packages/mcp/mcp-client/README.zh.md:28）。服务器启动时有副作用（写锁文件、连数据库、发通知）的话，每次连接都会做两遍。

子进程环境以 scrubbedParentEnv() 为基础，再合并配置里的 env（packages/mcp/mcp-client/src/transport.ts:21-23），凭据形的环境变量传不过去。

scrubbedParentEnv() 去掉名字匹配 /KEY|PASSWORD|SECRET|TOKEN/i 的变量和所有 DSH_* 变量（packages/subprocess/subprocess/src/index.ts:47、:66-70）。名字不像凭据的 DSH_DEMO_MARKER 也没传过去。

服务器需要的令牌要在配置的 env 里显式传，第 4 步显式传入后读到了。

规则引擎认不出 MCP 部署

第 21 篇的规则引擎在 tools/result 上记部署结果，由守卫按历史拦截，在 post-execute 追加告警。它要认出一次部署，工具名得等于 deployTool（默认 deploy_release），参数里的 service、version 得是字符串，结果值里得有 outcome 字段。

本篇把平台上的 2.3 设成每次都失败，让模型连续部署三次：

== 2. 第 21 篇的规则引擎：连续部署 2.3 三次 ==
默认配置（认 deploy_release）：平台执行 3 次，规则历史 0 条
deployTool 改成 MCP 名：平台执行 3 次，规则历史 0 条
  结果值的字段是 content、structuredContent，引擎读 value.outcome 读不到
再从 structuredContent 读结果：平台执行 2 次，规则历史 2 条
  第 3 次：报错「Error: [same-version-failed-twice] payment-api 2.3 在 24 小时内已失败 2 次，停止重试」
  审批人收到 3 次请求、都批准了；第 3 次批准后才被守卫拒绝
第 23 篇的 readDeploys 读这台宿主的日志：按 deploy_release 读回 0 条；按 MCP 名读回 3 条（executed、executed、error）
  读回的记录里 service/version/outcome：都没有，tool/result 没有 meta：true

第一种配置下，名字对不上，记录和守卫两个钩子都跳过这个工具（告警钩子本来只看 lookup_release）。

改名还不够：MCP 工具结果是 { content, structuredContent }（mcp-client/src/tools.ts:301-306），结构化字段在 structuredContent 里，引擎读 value.outcome 得到 undefined，一条历史也记不下。两种配置下规则都没报错，也没拦住第三次部署。

为此本篇给引擎加了一个配置项 outcomeOf，默认仍读 value.outcome，MCP 场景改成读 structuredContent.outcome，改动 3 行代码。之后第三次部署被守卫拒绝，拒绝理由原样到达模型，和本地工具一样。

审批也生效：demo 照第 24 篇，在 tools/pre-execute 上对 MCP 部署返回 ask，脚本化的审批人三次都收到请求。审批先于守卫（第 25 篇；守卫在全部 pre-execute 监听器之后执行，tools/src/index.ts:706-708），所以第三次是审批人批准后才被守卫拒绝，部署没有执行。

按名字和结果字段识别工具的插件，接 MCP 时都要重新对一遍。

第三种配置的宿主还把会话日志写进 JSONL，输出最后两行是第 23 篇的 readDeploys 读回的结果。按原名读回 0 条；改成 MCP 名能读回 3 条，但服务、版本、结果都是空的。MCP 工具的输出定义没有 presentationMeta（mcp-client/src/tools.ts:250-266），日志里只有渲染出的文字。

参数不经 dsh 校验

本地工具用 defineTool 注册时，参数在 execute 入口按 schema 校验，不合规就抛 ToolArgsError（packages/core/tools/src/schema.ts:585-587）。

MCP 桥接的 execute 只把非对象参数换成 {}，其余原样发给服务器（mcp-client/src/tools.ts:286-287），参数合不合 inputSchema 由服务器决定。

demo 在同一个宿主里再注册一个本地的 deploy_release，两边都在规则已记下两次失败之后，收到 version 为数字 2.3 的调用：

== 3. 参数不经 dsh 校验：version 传成数字 2.3 ==
本地 deploy_release：报错「Error: invalid arguments: "version" must be a string」，执行 0 次
MCP 工具：守卫放行，服务器把它转成 "2.3" 部署，结果 payment-api 2.3 failed
规则历史仍是 2 条，平台上 2.3 已失败 3 次

MCP 工具这边，守卫放行是因为 version 不是字符串，引擎读不出键就不判断（第 21 篇说过，守卫看到的是模型给的原始参数）。本地的 deploy_release 不是这台宿主配置的 deployTool，守卫根本不看它，挡住它的是参数校验。

MCP 工具没有参数校验这一道，服务器又不校验类型，第三次失败部署照样发生。这次结果的参数同样读不出来，规则历史没有增加。

要堵住，可以让服务器严格按 inputSchema 校验，也可以让引擎把非字符串的版本号规范化后再判断。前者要改平台，后者只改宿主。

报错的部署可能已经执行

重连策略默认 500 毫秒起步、每次翻倍、上限 30 秒、每次故障最多 10 次（mcp-client/src/connection.ts:41-46）。demo 缩短为 20 毫秒起步、上限 1 秒、最多 3 次。

服务器部署 2.6 时先记账，再在回复之前退出：

== 4. 服务器在回复前崩溃，之后重连 ==
env 里显式传入后，服务器进程里：present、present
部署 2.6：报错「Error: Connection closed」
  平台账本里这次部署已经执行：2.6 succeeded；规则历史 0 条
紧接着再部署：报错「Error: Not connected」
重连日志：
  connection lost; reconnecting in 20ms (attempt 1/3)
  reconnected and re-synced tools (attempt 1/3)
重连后工具换成新一代定义，再部署：payment-api 2.4 succeeded
服务器进程累计启动 4 次

2.6 已经部署成功，模型拿到的却是 Connection closed，报错不等于没执行。服务器的操作没有幂等键的话，模型重试就是第二次部署。这台宿主挂了读 structuredContent 的规则引擎，历史仍是 0 条：引擎不记报错的结果。

断开期间工具还在：连接断开只把当前连接置空、安排重连（mcp-client/src/connection.ts:180-185），旧的工具定义留在注册表里。它们捕获的还是旧一代 client（mcp-client/src/tools.ts:138-141），调用得到 SDK 的 Not connected。

重连成功后重新拉取工具列表，整批换成新一代定义（mcp-client/src/connection.ts:323、mcp-client/src/tools.ts:145-151）。重连是新起的服务器进程，服务器放在内存里的状态不会保留；这次重连又启动了两个进程，累计 4 次。

第 4 步后半段，平台再次崩溃：

平台起不来，1 秒内再崩溃一次：
  connection lost; reconnecting in 40ms (attempt 2/3)
  connection failed; retrying in 80ms (attempt 3/3)
  giving up after 3 consecutive failed reconnect attempts
工具被移出注册表；模型下一次请求的工具列表：[]
再调：报错「Error: unknown tool "mcp__release__deploy_release"」
放弃后等 1.5 秒（超过重连上限 1 秒）：服务器进程启动次数 8 → 8，工具仍不在注册表里
logger 默认缓冲（不设级别）里留下的重连记录：reconnected and re-synced tools (attempt 1/3)；giving up after 3 consecutive failed reconnect attempts

连接保持达到 maxDelayMs 才算这次故障结束，下一次断开重新计数（mcp-client/src/connection.ts:220-222），一次故障共用一份预算。本例第二次崩溃时计数没有清零，日志从 attempt 2/3 接着数，只再试了 2 次就放弃。

源码注释说明了用意：让“能连上但很快又崩”的服务器也会耗尽预算，不会无限重启（:7-13）。

放弃时注销这台服务器的全部工具（mcp-client/src/connection.ts:225-235），模型下一次请求里没有这个工具，调用得到 unknown tool（tools/src/index.ts:503）。

系统提示里它的 instructions 段也一并清空（mcp-client/src/connection.ts:231）。放弃后等 1.5 秒，服务器进程一次也没再启动，工具也没回来。放弃日志的后半句 demo 没打印，提示要重载插件或重启宿主才会再连（按源码，未实测；:233）。

重连过程只写进 logger，不进会话日志：重试记 warn，重连成功记 info，放弃记 error（mcp-client/src/connection.ts:233、:238、:342）。

最后一行读的是 logger 自带的缓冲，它没设级别，按默认阈值过滤（vendor/cordis/src/logger.ts:155）：两条“reconnecting”都没留下，只剩“reconnected”和“giving up”。要看到重试过程，得像 demo 这样另挂一个收 warn 的 exporter。

PTC 程序拿到完整结果，超时报错时部署已执行

第 5 步补了三种情况，各用一台新宿主：

== 5. PTC 程序调 MCP 工具、服务器改工具列表、调用超时 ==
PTC 程序里调 mcp__release__deploy_release，程序拿到的值：
  {"content":[{"type":"text","text":"payment-api 2.4 succeeded"}],"structuredContent":{"service":"payment-api","version":"2.4","outcome":"succeeded"}}
服务器在第一次部署后发 tools/list_changed：工具 mcp__release__deploy_release → 下一次模型请求里 mcp__release__deploy_release, mcp__release__rollback_release
  服务器进程启动 2 次，tools/list 收到 2 次
toolCallTimeoutMs 设成 100，服务器 300 毫秒后才回：报错「Error: Request timed out」
  平台账本：deploy 2.8 → reply 2.8

第 25 篇的 PTC 模式下，程序调 MCP 工具拿到的是完整结果，content 和 structuredContent 两块都在，和第 2 步规则引擎看到的结果值相同。

服务器声明了 listChanged，第一次部署后多出 rollback_release 并发通知。客户端在同一个连接里当场重新拉取列表，进程还是 2 次启动，下一次模型请求就带上了新工具（mcp-client/src/connection.ts:263-269）。

调用超时同样是报错但已执行。超时只让客户端不再等（mcp-client/src/connection.ts:370），模型收到 Request timed out，平台上的 2.8 已部署，服务器随后也回了结果。

这对 Agent 意味着什么

守卫和审批挂在工具流水线上，对 MCP 工具照样生效。但工具名多了 mcp__<serverName>__ 前缀，结构化结果在 structuredContent 里，按名字和字段识别工具的插件都要重新对一遍。本例的规则引擎两处都对不上，既没报错，也没拦住部署。

dsh 不按 inputSchema 校验 MCP 工具的参数，校验落在服务器身上，守卫要自己处理类型不对的参数，或者确认服务器会校验。服务器的风险标注模型也看不到：拿到的 schema 只有三个字段，annotations 不在其中，破坏性操作要不要审批，得由宿主自己按工具名配置。

连接在回复前断开或调用超时时，客户端报错，但本篇两种情况下部署都已经执行。报错的调用不能当作没发生。

接入一台服务器后，它的进程每次连接都启动两次（一次用来探测协议版本），它的 instructions 原样进系统提示。

本文的验证范围

实测部分是 mcp-client-demo.ts，挂载真实的 dsh-mcp-client、dsh-tools、dsh-user-approval、会话存储与 agent 循环。

MCP stdio 服务器是手写的 release-mcp-server.mjs，规则引擎用第 21 篇的 release-rules.ts（加了 outcomeOf 配置项）。

模型和审批人是脚本化的，发布平台是合成的，时钟固定。每个场景启动一个新宿主和一个新账本。重连策略缩短了延迟。重连日志来自 demo 挂的一个收所有级别的 exporter。

服务器的额外行为（多报名字不合规的工具、改工具列表）由配置的 env 打开，2.8 版本延迟 300 毫秒回复。第 2 步第三种配置的宿主另挂 JSONL 持久化，由 dsh-session-query-sqlite 读回；第 5 步的 PTC 宿主挂 dsh-ptc-runtime-node 和本地沙箱。

主要结论都有断言：

  • 模型拿到的工具名、schema 只有三个字段、parameters 与服务器的 inputSchema 相同（输出里“annotations（destructiveHint）和 outputSchema 没有交给模型”那一行是写死的文字，断言的是 schema 只有三个字段）；
  • 不合规的名字带 12 位哈希、超长名字总长 64；只挂审批服务时审批 0 次；isConcurrencySafe 未设，两个调用在服务器上依次执行；
  • 系统提示里的服务器段落、一次连接的账本顺序（两次启动）、未显式传入时服务器读不到 RELEASE_API_TOKEN 和 DSH_DEMO_MARKER；说明超长时 4 次连接失败、起 8 个进程、放弃、没有工具；
  • 规则引擎三种配置下的平台执行次数和历史条数、第三次的拒绝文字、审批人收到的三个 callId；readDeploys 按原名读回 0 条、按 MCP 名读回 3 条且没有服务、版本、结果；
  • 数字版本号：本地工具的报错文字、本地执行 0 次、MCP 工具部署成功执行且结果为 failed、历史仍为 2 条；
  • 崩溃那次的报错与账本里的部署、规则历史 0 条、断开期间的 Not connected、重连日志、重连后部署成功、进程累计启动 4 次；
  • 第二次崩溃后的三条重连日志、工具列表为空、unknown tool 报错；放弃后 1.5 秒内没有新进程；logger 自带缓冲里只有两条重连记录；
  • PTC 程序拿到的值、list_changed 后的工具列表和启动次数、超时的报错与账本里的部署。

另外做了变异检查。以下 7 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • 第 1 步在 env 里显式传入令牌；
  • 第 2 步第三种配置去掉 outcomeOf；
  • 第 2 步第三种配置的宿主不挂审批；
  • 服务器在 version 不是字符串时返回 isError；
  • 服务器先退出再记账；
  • 关闭自动重连；
  • 重连延迟和稳定窗口都缩短到 1 毫秒。

连续 5 次运行，以及 4 个进程并发运行，输出都一致。本机实测一次运行约 4.5 秒，其中 1.5 秒是放弃后的等待。
