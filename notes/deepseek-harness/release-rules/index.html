第 22 / 36 节 · 发布规则实战

同一版本失败两次后，守卫拦下了第三次部署；把版本写成 v2.3，规则没认出来，平台第三次部署了同一个失败版本。

从这一篇起进入实战：用前面讲过的扩展点，给发布值班 agent 加一个风险规则引擎。第一条规则是“同一版本 24 小时内失败两次，就不许再部署”。

这次写一个 release-rules 服务：从工具结果里攒发布历史，用守卫拦下违规的部署，用 post-execute 给查询结果追加告警。脚本化的 agent 连着重试失败版本，看第三次有没有被拦；把被拒也记成失败，看窗口会不会续上；查状态看告警；换个写法绕一次；把规则和引擎分别卸载、重载，看历史还在不在；最后拨时钟、试 async 守卫。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 2.3 失败两次后，第三次部署被守卫拦下；
  • 被拒调用的结果里没有错误码，只有 message；
  • 版本写成 v2.3，规则放行，平台照样部署；
  • async 守卫让所有工具都报错，拒绝理由丢失。

引擎挂在流水线的三个位置

第 9 篇把一次工具调用拆成了七个阶段。规则引擎用到其中三个，源码都在 packages/core/tools/src/index.ts：

位置用途能做什么
tools/result记历史只能观察最终结果
守卫 ctx.tools.guard()拦截类规则同步返回拒绝理由，不能放行
tools/post-execute告警类规则接受结果，附上 additionalContexts

三个位置在源码里依次对应（:191；:713、:1116-1122；:599-602）。

拦截用守卫，不用 tools/pre-execute，理由第 9 篇实测过：pre-execute 是 waterfall，前面的监听器直接返回 allow 就能跳过后面的策略，守卫则在整条 waterfall 放行之后才执行，只能拒绝（:1482-1506）。

引擎本身是一个 Cordis Service，挂在 ctx.releaseRules 上。三个钩子都在构造函数里注册，跟着服务的生命周期走。规则是普通对象：

export interface ReleaseRule {
  readonly id: string
  readonly severity: 'block' | 'warn'
  /** Returns a finding message when the rule fires. Must be synchronous: guards cannot await. */
  evaluate(input: RuleInput): string | undefined
}

每条规则包成一个小插件，在 apply 里用 ctx.effect(() => ctx.releaseRules.register(rule)) 注册。第 4 篇讲过，这样插件卸载时注册自动撤销。

evaluate 必须是同步的，因为守卫是同步函数。规则要用的数据必须能同步读到（通常放在内存里），不能在守卫里去查发布平台。

第一条规则就几行：

evaluate({ service, version, history, now }) {
  const failures = history.filter(e => e.service === service && e.version === version
    && e.outcome === 'failed' && now - e.at < 24 * 3600_000)
  return failures.length >= 2
    ? `${service} ${version} 在 24 小时内已失败 ${failures.length} 次，停止重试`
    : undefined
},

图：守卫命中即拒绝；放行后工具执行，tools/result 记历史，post-execute 追加告警。

失败两次，第三次被拦下

合成的发布平台上，payment-api 的 2.3 版本每次都部署失败。脚本化的 agent 收到“失败就重试”，连着调了三次 deploy_release，之后再调两个会抛错的工具作对照：

== 1. 同一版本部署失败两次，第三次被规则拦下 ==
第 1 次 deploy_release -> payment-api 2.3 failed
第 2 次 deploy_release -> payment-api 2.3 failed
第 3 次 deploy_release -> isError=true
  Error: [same-version-failed-twice] payment-api 2.3 在 24 小时内已失败 2 次，停止重试
平台实际执行了 2 次；规则引擎记下的历史 2 条
被拒调用的结果里带错误码吗：没有，只有 message
工具体抛普通 Error：{"message":"platform down"}
工具体抛 HarnessError：{"message":"platform down","info":{"name":"HarnessError","code":"PLATFORM_DOWN"}}

第三次在守卫那里被拒，工具体没有执行，平台只部署了两次。模型收到的是一条错误结果，内容就是规则给的理由。

“带错误码吗”那一行的现象，第 9 篇已经见过（code=-）；这里它决定了历史该怎么记。守卫拒绝时，结果里只有一句 message（:1505）。

最后两行是对照：工具体抛普通 Error，结果同样只有 message；抛 HarnessError 才带 info.code（:644-650、:1879-1887）。所以在 tools/result 里，被规则拒绝的调用和抛普通错误的调用没有结构化字段可以区分。

如果把工具报错也记成部署失败，被拒的重试也会算进失败次数。另起一个宿主给引擎打开 recordErrors，换 refund-api 重演一遍，时钟单独拨动：

== 2. 把被拒的调用也记成失败：窗口被一直续上 ==
第 0 小时：三次调用，平台执行 2 次，历史 3 条
第 23 小时：再试两次，被拒 2 次，历史 5 条
第 25 小时：Error: [same-version-failed-twice] refund-api 2.3 在 24 小时内已失败 2 次，停止重试
平台一共执行 2 次

到第 25 小时，第 0 小时的三条失败已经出了窗口，第 23 小时被拒的两次又凑够两条，版本照样被拦，平台却始终只执行过 2 次。只要窗口里还有两次被拒的重试，这个版本就一直被拦。

demo 让部署工具把“部署失败”当成正常数据返回，即 { outcome: 'failed' }，不抛错；记录器默认只看成功返回的值，工具报错一律不记。

另一种办法是在 tools/pre-execute 里用 deny 拒绝，它可以带 info（按源码，未实测；:589-593）。但 pre-execute 是 waterfall，前面的监听器返回 allow 就能跳过这条拒绝，不像守卫那样只能拒绝。

告警追加在工具结果之后，不改结果本身

第二条规则是告警类：某个服务最近一次发布失败，查询它的时候提醒一句。agent 调 lookup_release，看它下一次请求里的最后两条消息：

== 3. 查询时追加告警：工具结果后面多一条插件消息 ==
  user/tool: payment-api: 2.3 failed
  user/plugin: release-rules 告警：[last-release-failed] payment-api 最近一次发布 2.3 失败
会话日志里这条告警的来源：{"kind":"plugin","plugin":"release-rules"}

user/plugin 那一行就是告警。post-execute 监听器接受原结果，另外返回一条 additionalContexts。模型在工具结果后面收到一条来源为 plugin 的用户消息，会话日志里也记下了这条消息和它的来源。

工具结果仍是平台返回的原文，会话日志里能分清哪句是平台说的、哪句是规则加的。

版本写成 v2.3，规则就认不出来

合成发布平台接受 2.3 和 v2.3 两种写法，工具体里会先去掉前面的 v。agent 换成 v2.3 再部署一次：

== 4. 版本写成 v2.3：规则没认出来，平台照样部署 ==
deploy_release(v2.3) -> payment-api 2.3 failed；平台执行次数 +1
引擎按工具体同样的写法规范化后，2.3、v2.3、v2.3 三次：第 3 次被拦
  Error: [same-version-failed-twice] payment-api 2.3 在 24 小时内已失败 2 次，停止重试

规则按原样比较 version，v2.3 和历史里的 2.3 对不上，守卫放行，平台第三次部署了同一个失败版本。

守卫拿到的是模型给的原始参数。流水线在 pre-execute 之前只把参数做一次 JSON 快照并冻结（:1419-1423），工具体里去掉 v 是工具的私有逻辑，改写后的参数不会交给守卫。demo 引擎也没有配规范化，规则按原字符串比较 version。

问题和 schema 校验的时机无关：v2.3 是合法字符串，校验提前也照样通过。守卫看到的参数没经过 schema 校验（packages/core/tools/src/schema.ts:585-588），第 9 篇已经用 service=123 实测过。

修法是让引擎用和工具体一样的规则规范化参数。demo 给引擎配了 normalize，去掉版本号前面的 v，在另一个宿主里连续三次 2.3、v2.3、v2.3，第三次被拦。

规范化逻辑最好和工具体共用同一个函数，否则工具一改写法，规则又会漏。demo 里两处是各写一份的（引擎还多做了 service.trim()），生产代码应抽成一个共享函数。

记录一侧也可以不用原始参数，直接取工具返回值里平台规范化后的 service/version；demo 为了演示问题，两侧都用的是原始参数。

历史只在引擎内存里，重载就清零，窗口按引擎时钟算

规则是插件，可以单独加载和卸载；引擎也是插件。分别试一下：

== 5. 卸载规则、重载引擎 ==
已注册的规则：same-version-failed-twice, last-release-failed, hot-rule
卸载 hot-rule 之后：same-version-failed-twice, last-release-failed
重载前，引擎对 payment-api 2.3 的判断：same-version-failed-twice
引擎卸载后，两条规则插件的状态：0, 0（0 = 等待依赖）
卸载期间（旧实例上挂着必拦、必告警规则）：deploy_release(2.3) -> payment-api 2.3 failed，平台执行 +1，查询告警 0 条，旧实例历史 3 条（卸载前 3）

“卸载期间”那一行说明钩子跟着引擎走：demo 往已卸载的旧实例上直接注册了必拦、必告警两条规则，部署照样执行，查询没有告警，旧实例的历史也没变。守卫和两个监听器登记在引擎的 Fiber 名下，随引擎一起撤销了。

卸载一条规则的插件，它就从注册表里消失，其他规则不受影响。

卸载引擎时，两条规则插件依赖 releaseRules，回到了等待状态（FiberState 0）。引擎重新加载后，它们自动重新执行 apply，又注册回来了，第 5 篇讲过这种依赖驱动的重启。

第 5 步后半段接着查询、部署、再查询，最后另建一个宿主模拟进程重启：

引擎重新加载：规则自动回来了 same-version-failed-twice, last-release-failed，历史 0 条
重载后先查询：告警 0 条
deploy_release(2.3) -> payment-api 2.3 failed（重载前会被拦下，现在规则没有触发）
部署失败一次后再查询：告警 1 条 release-rules 告警：[last-release-failed] payment-api 最近一次发布 2.3 失败
新宿主（相当于进程重启）：部署前历史 0 条，deploy_release(2.3) -> payment-api 2.3 failed

“重载后先查询：告警 0 条”这一行，payment-api 刚失败过好几次，查询却没有提醒。历史只在引擎实例的内存里，重载后是 0 条，同一个失败了好几次的版本又能部署了。

再失败一次后告警恰好 1 条，重建的监听器只有一份。新宿主的历史同样从 0 开始，进程重启也是这样。下一篇要解决的就是这个：把规则和历史持久化。

窗口也由引擎自己算。在配了 normalize 的那个宿主里把引擎的时钟拨快 25 小时，再部署一次 2.3：

== 6. 24 小时窗口：时钟拨快 25 小时后放行 ==
deploy_release(2.3) -> payment-api 2.3 failed（25 小时前的 2 次失败都已出了窗口）

输出只有一行：25 小时前的 2 次失败都已出了窗口，部署放行。时钟是注入给引擎的函数，demo 里可以随意拨动。窗口的起点是引擎记录历史、观察到结果的时刻，不是平台上的部署时间。

async 守卫让所有工具报错

写规则时很容易想在守卫里顺手查一下外部系统，demo 把一个 async 函数强转成守卫注册上去：

== 7. 守卫写成 async ==
lookup_release(order-api) -> Error: tool result must be losslessly JSON-serializable
deploy_release(order-api 1.0) -> Error: tool result must be losslessly JSON-serializable
  平台执行次数没变：true
去掉这个守卫后 lookup_release(order-api) -> order-api: no deployment

前两行里两个工具都失败了，报错看不出原因。注册在根上下文的守卫对所有工具生效，引擎自己的守卫也是每次调用都进来，靠工具名提前返回。

async 函数返回的是 Promise，不是 undefined，逐个守卫检查时就被当成了拒绝理由（tools/src/index.ts:749-755）。流水线把它原样放进 error.message（:1505）。

物化结果时 Promise 无法 JSON 快照，:638 抛出 TypeError；这个异常被 prepareExecution 的 catch 接住（:1513-1514），变成一条以 TypeError 为 message 的错误结果，拒绝理由本身就丢了。

TypeScript 的类型会挡住这种写法。第 8 步去掉强转，用 tsc --noEmit 检查两个探针文件，一个注册 async 守卫，一个注册同步守卫：

== 8. 去掉强转，让 tsc 检查 async 守卫 ==
async-guard.ts(4,29): error TS2322: Type 'Promise<undefined>' is not assignable to type 'string'.
sync-guard.ts 的报错：0 条

报错只落在 async 探针上：ToolGuard 要求返回 string | undefined（:713），Promise<undefined> 过不了类型检查。demo 是用 as unknown as ToolGuard 强转进去的；用 JavaScript 写插件，或者随手一个 as any，就会碰上（按源码，未实测）。

这对 Agent 意味着什么

第 7 步的 async 守卫让 lookup_release 和 deploy_release 都报错，平台一次也没执行，所以守卫里的规则得是同步的，需要的数据提前放进内存。守卫看到的又是模型给的原始参数，模型换一种写法，规则就可能漏过去，规则和工具体要用同一套参数规范化。

被规则拒绝、工具抛普通 Error 的结果都只有 message，把报错也记成失败，重试会一直续上窗口。demo 把部署失败当返回值 { outcome: 'failed' }，只记成功返回的值，平台执行 2 次，历史也是 2 条。

demo 引擎的历史放在内存里，引擎一重载就清零，历史得持久化。清零是引擎的实现，不是 dsh 的行为。

本文的验证范围

实测部分是两个文件：规则引擎 release-rules.ts 和驱动脚本 rules-demo.ts。脚本挂载真实的 dsh-llm、dsh-tools、dsh-agent、dsh-agent-loop、dsh-system-prompt、会话存储和会话投影，没有启动 dsh 的 CLI 或 Web 进程。

模型是脚本化模型，每一轮调哪个工具、传什么参数是预先写好的；发布平台和它的数据是合成的，时钟由脚本控制。

主要结论都有断言：

  • 三次部署的结果、平台执行次数、历史条数，以及被拒结果没有 info；普通 Error 只有 message、HarnessError 带 info；
  • 打开 recordErrors 后，第 23 小时两次被拒、第 25 小时仍被拒，平台只执行 2 次，历史 6 条；
  • 告警消息的位置、内容和来源；
  • v2.3 绕过规则，以及规范化后被拦；
  • 卸载、重载 hot-rule 后的规则列表，引擎卸载后规则插件的状态；
  • 卸载期间旧实例上的规则不拦、不告警、不记历史；
  • 重载后历史 0 条、规则列表恢复、查询无告警、同一版本部署放行、再查询告警恰好 1 条，新宿主历史为 0；
