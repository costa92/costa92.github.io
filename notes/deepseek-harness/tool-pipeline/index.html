第 10 / 36 节 · 能力、工具与会话

给 lookup_release 加了一条“不指定服务名就不许查”的规则，另一个插件前置一个放行监听器，3 条发布记录全出来了。同一规则换成守卫，照样拦得住。

上一篇看了 ctx.tools 的两头：注册时模型能看到什么，返回时输出要过哪道 schema 检查。这一篇看中间：模型发起一次调用，到工具体执行、结果回到模型，经过哪些关卡，每一关能做什么、不能做什么。

沿着这次调用经过的关卡，看前置监听器为什么能放行全量查询，以及守卫为什么还能拦住它。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 前置 allow-all 绕过 pre-execute 策略，绕不过守卫；
  • 守卫收到的 service=123 没有经过 schema 校验；
  • 守卫放行后，tools/execute 仍能整体换掉参数；
  • 被拒的调用照样经过 post-execute，监听器抛错则不经过。

一次调用经过七个阶段

docs/tool-execution-pipeline.zh.md 用一张流程图描述了整条工具流水线，开头一段话概括了顺序：

tools/pre-execute waterfall（瀑布式事件）首先运行，随后是单调守卫，然后运行 tools/execute 和 tools/post-execute waterfall；这三个 waterfall 可以改写一次调用。由定义自身控制的 finalizeContent 和 tools/result 在此之后运行。

在每个阶段挂一个只记录、不干预的监听器，调一次 lookup_release：

1. one call, every stage
  service=payment-api: ok content="2 record(s): demo-001,demo-003"
    stages: pre-execute -> guard -> execute> -> body -> <execute -> post-execute -> finalizeContent -> result

看 stages: 一行：execute> 和 <execute 包在 body 两边，是第 6 篇讲的 waterfall 洋葱形状，外层监听器调 next() 才会进到工具体，next() 返回后还能再处理结果。

阶段形式能做什么
tools/pre-executewaterfall放行、拒绝、取消、要求审批
guard同步函数拒绝或弃权，不能放行
tools/executewaterfall，包住工具体超时、重试、计量、替换结果
工具体execute()干活，返回规范值
tools/post-executewaterfall接受、替换值或内容、拦截、追加上下文
finalizeContent工具定义上的回调最后改一次给模型的内容
tools/resultemit只能观察冻结后的结果

图：红色虚线是拒绝与抛错。被拒的调用绕过工具体但仍进入 post-execute，监听器抛错则直接进入收尾。

三个 waterfall 的签名都在 packages/core/tools/src/index.ts 的事件声明里，其中 tools/execute 的注释说监听器在 exec 上只能换 exec.signal，实测并没有拦住别的字段（见第 8 步）。决策类型是封闭的联合类型（:589 起）：

export type PreToolDecision =
  | { kind: 'allow' }
  | { kind: 'deny'; reason: string; info?: ToolErrorInfo }
  | { kind: 'cancel' }
  | { kind: 'ask'; reason?: string }

export type PostToolDecision =
  | { kind: 'accept'; content?: ContentBlock[]; value?: never; additionalContexts?: UserMessage[] }
  | { kind: 'accept'; value: JsonValue; content?: never; additionalContexts?: UserMessage[] }
  | { kind: 'block'; feedback: ContentBlock[]; additionalContexts?: UserMessage[] }

pre-execute 没有“改写参数”这个选项。注释给的理由是参数在这之前已经写进会话日志、展示给用户了，再改就对不上。

写在 pre-execute 的规则会被前置监听器绕过

先用最直接的办法：挂一个 tools/pre-execute 监听器，service 不是非空字符串就返回 deny。

为了演示全量查询，本文用的是 lookup_release 的简化版：service 参数可选，省略时返回所有服务的记录，数据是内存里的三条合成记录。第 3 篇的正式版本把 service 设成了必填，工具体里也检查了空字符串。那是工具体自己查参数，这一篇把规则放到工具外面。

const policy = root.on('tools/pre-execute', (exec, next): Promise<PreToolDecision> => {
  const reason = exec.name === 'lookup_release' ? denyFullScan(exec.arguments) : undefined
  return reason ? Promise.resolve({ kind: 'deny', reason }) : next()
})

再挂一个无条件放行、不调 next() 的监听器，一次默认追加，一次前置：

2. a full-scan policy written as a pre-execute listener
  no service: isError code=- text="Error: lookup_release requires an explicit service name"
    stages: pre-execute -> post-execute -> finalizeContent -> result
  no service + allow-all appended: isError code=- text="Error: lookup_release requires an explicit service name"
    stages: pre-execute -> post-execute -> finalizeContent -> result
  no service + allow-all prepended: ok content="3 record(s): demo-001,demo-003,demo-007"
    stages: allow-all -> guard -> execute> -> body -> <execute -> post-execute -> finalizeContent -> result

第一行不传 service，调用被拒。第二行默认追加（append）的 allow-all 排在策略里层，策略直接 deny、不调 next()，allow-all 没被调用。

第三行用 ctx.on(name, listener, true) 前置（prepend）之后，allow-all 变成最外层，直接返回 allow，策略所在的里层没被调用，3 条记录全出来了。

pre-execute 又是开放的扩展点，任何插件都能往上挂，也都能 prepend。Claude Code 的 hook 桥接就挂在这里，把 PreToolUse hook 的结果翻译成 PreToolDecision（按源码，未实测；packages/hooks/hooks-claude-code/src/index.ts:237）。

一条安全规则放在这里，它能不能生效，取决于别的插件的挂载顺序和写法。

守卫只能拒绝，不能放行

ctx.tools.guard() 是为这种情况准备的（tools/src/index.ts:1116）。守卫的类型是一个同步函数（:713）：

export type ToolGuard = (execution: Readonly<ToolExecution>) => string | undefined

返回字符串就是拒绝理由，返回 undefined 是弃权。没有“放行”这个返回值。它的执行位置在 prepareExecution() 里（:1496）：

const denialReason = decision.kind === 'allow' ? this.guardReason(exec) : decision.reason

pre-execute 整条 waterfall 跑完、结论是 allow，才轮到守卫。guardReason()（:1125）先查全局层，再沿 agent 作用域链逐层查，第一个返回理由的守卫生效。守卫在 pre-execute 之后执行，只要有一个拒绝，调用就被拒，没有监听器能把它改回放行。

同一条规则换成守卫，prepended 的 allow-all 照样挂着：

3. the same policy as a monotonic guard
  no service + allow-all prepended: isError code=- text="Error: lookup_release requires an explicit service name"
    stages: allow-all -> guard -> post-execute -> finalizeContent -> result
  service=123 (never schema-checked yet): isError code=- text="Error: lookup_release requires an explicit service name"
    stages: allow-all -> guard -> post-execute -> finalizeContent -> result
  service="   ": isError code=- text="Error: lookup_release requires an explicit service name"
    stages: allow-all -> guard -> post-execute -> finalizeContent -> result

第一个用例里，allow-all 返回了 allow，守卫还是拒绝了。

仓库里目前只有一处用 tools.guard()：子 agent 的结构化输出（packages/subagent/subagent-in-process-driver/src/structured.ts:109）。结构化结果一旦记录，本轮后续的工具调用都不该再执行。旁边的注释写了守卫的定位：

Guards run after the whole pre-execute waterfall and compose monotonically (deny or abstain, never allow), so a later prepended listener cannot resurrect dispatch.

“单调”指守卫只会让允许的集合变小。

守卫也可以挂在 agent 作用域上。第 9 步挂三层守卫：全局只拦 g，agent-A 拦 g 和 a，它的子作用域 agent-A/sub 全拦（节选，省略了 stages 行）：

9. guards along the scope chain: global first, then farthest scope first
  no agent, payment-api: ok content="2 record(s): demo-001,demo-003"
  agent-A, payment-api: ok content="2 record(s): demo-001,demo-003"
  agent-A/sub, payment-api: isError code=- text="Error: sub-agent guard"
  agent-A/sub, a: isError code=- text="Error: agent-A guard"
  agent-A/sub, g: isError code=- text="Error: global guard"

看最后两行的拒绝理由：同一个子 agent 的调用，a 由父作用域的守卫先拒，g 由全局守卫先拒。子作用域的守卫不影响父 agent 和不带 agent 的调用。

守卫看到的参数未经 schema 校验

第 3 步的第二、三个用例里，service=123 和空白字符串都原样进到了守卫，守卫收到的参数没有经过 schema 校验。

参数校验发生在 defineTool 包出来的 execute() 里（packages/core/tools/src/schema.ts:585 起），在工具体内部。pre-execute 和守卫拿到的只是快照过、冻结过的原始参数，守卫里的 denyFullScan 必须先判断类型，不能直接调用 service.trim()。

被拒的调用照样经过 post-execute

对比第 2、3 步的阶段序列：被拒的调用跳过了 execute 和工具体，但照样经过 post-execute、finalizeContent 和 tools/result。

prepareExecution() 把拒绝包装成 post-result，送进后半段工具流水线（tools/src/index.ts:1498 起）。

post-execute 上的监听器因此看得到每一次拒绝，比如 hook 桥接的 PostToolUse，或者统计拒绝次数的插件。tools/result 的观察者拿到的也是完整的调用记录，不会漏掉被拒的那部分。

要求审批（ask）走的是同一条路。当前组合里没有挂 ctx.approval 服务，所以 serviceAsk()（:1698）直接把它转成 deny：

4. ask with no approval service mounted
  service=payment-api: isError code=- text="Error: production payment data"
    stages: pre-execute -> post-execute -> finalizeContent -> result

模型看到的错误文本就是 ask 里写的 reason（:1705 的 ask.reason ?? ...），所以写 reason 时要想到，它可能直接成为模型读到的拒绝理由。

挂上审批服务后，ask 才会去问人。真实的 dsh-user-approval 要求处于打开的回合里（按源码，未实测），第 10 步先不写 reason，再改挂一个按预设结果回答的审批桩，分别试不带 agent 的调用和审批人的四种回答（节选，省略了 stages 行）：

10. ask: default reason, no agent, and the four approval outcomes
  ask without reason, no approval service: isError code=- text="Error: tool \"lookup_release\" requires approval (not yet supported)"
  approval service, but no agent: isError code=- text="Error: tool \"lookup_release\" requires approval, but the call has no agent to route it through"
  agent-A, approver says allowed-once: ok content="2 record(s): demo-001,demo-003"
  agent-A, approver says rejected: isError code=- text="Error: the user rejected tool \"lookup_release\""
  agent-A, approver says cancelled: isError code=- text="Error: approval for tool \"lookup_release\" was cancelled"
  agent-A, approver says unavailable: isError code=- text="Error: tool \"lookup_release\" requires approval, but no approval channel is available"

第 1 行省略 reason 时模型看到的是默认文本。第 2 行挂了审批服务，但调用不带 agent，审批桩一次都没被问到就转成了 deny。

后四行只有 allowed-once 放行，三种不放行各有各的文本，模型能分清是人拒绝了还是没有审批通道。这时审批人看到的理由才是 ask 里写的 reason。

环绕层超时只能通知工具体停下

tools/execute 包在工具体外面，基础组合（base bundle）里的超时插件 dsh-tool-call-timeout-policy 就挂在这里（packages/guard/timeout-policy/src/index.ts:56）。下文称它为 guard 插件，与 ctx.tools.guard 的守卫无关。

guard 插件默认启用（packages/bundle/base/cordis.patch.yml:387），读工具声明的 timeoutMs，把一个带截止时间的 signal 换到 exec.signal 上，调 next()，超时后把结果替换成 TOOL_TIMEOUT：

5. around: timeout-policy wraps tools/execute
  body takes 200ms, timeoutMs=50: isError code=TOOL_TIMEOUT text="Error: tool call timed out after 50ms"
    stages: pre-execute -> guard -> execute> -> body -> <execute -> post-execute -> finalizeContent -> result
    elapsed ~50ms
  same, but the body ignores exec.signal: isError code=TOOL_TIMEOUT text="Error: tool call timed out after 50ms"
    stages: pre-execute -> guard -> execute> -> body -> <execute -> post-execute -> finalizeContent -> result
    elapsed ~200ms

看两行 elapsed：两次都是 TOOL_TIMEOUT，但后一次耗时是前一次的四倍（约 50ms 对约 200ms）。第一次工具体监听了 exec.signal，50ms 时收到 abort 就结束了；第二次工具体不理会 signal，外层一直等它跑满 200ms 才返回，结果仍被替换成 TOOL_TIMEOUT。

ToolDefinition.execute 的注释写明了这份契约：registry “does not abandon this promise, but it cannot hard-kill same-process code”。超时只通过 signal 通知工具该停，停不停由工具体决定。工具不配合时，超时策略只能改写最终结果，调用不会提前结束。

timeoutMs 的注释（tools/src/index.ts:246）也写明，声明这个字段即表示 “this tool forwards exec.signal to a cooperative implementation”。

守卫放行之后，环绕层还能换掉参数

tools/execute 的注释说包装层只能换 exec.signal，“call identity remains immutable”。第 8 步重新挂上第 3 步的全量查询守卫，再挂一个 tools/execute 监听器，分三次改 exec：

8. tools/execute: the contract says swap exec.signal only
  mutate exec.arguments.service: isError code=- text="Error: Cannot assign to read only property 'service' of object '#<Object>'"
    stages: pre-execute -> guard -> finalizeContent -> result
  guard passes payment-api, then reassign exec.arguments = {}: ok content="3 record(s): demo-001,demo-003,demo-007"
    stages: pre-execute -> guard -> execute> -> body -> <execute -> post-execute -> finalizeContent -> result
  reassign exec.name: isError code=UNKNOWN_TOOL text="Error: unknown tool \"no_such_tool\""
    stages: pre-execute -> guard -> execute> -> <execute -> post-execute -> finalizeContent -> result

第 1 行改参数里的字段，参数对象是冻结的，赋值抛错，调用失败。第 2 行把整个 arguments 换成 {}，守卫已经按 payment-api 放行，工具体收到的却是空参数，3 条记录全出来了。

第 3 行换 name 同样生效，分派按新名字找工具，得到 UNKNOWN_TOOL。冻结只管到参数对象内部，exec 自身的字段没有锁住，“只能换 signal”只是约定，运行时不检查。

后置层替换的值会再校验一次

tools/post-execute 拿到的是工具体的结果，可以接受、替换或者拦截。第 6 步依次换成合规的值、换成不合 schema 的值、直接拦截（节选，省略了每次调用后打印的 stages 行）：

6. post-execute: replaced values are validated again
  redact ids: ok content="2 record(s): "
  replace with an off-schema value: isError code=INVALID_TOOL_OUTPUT text="Error: tool \"lookup_release\" returned invalid output: \"value.count\" must be an integer"
  block after the body ran: isError code=- text="release data is frozen during the incident"

第一行把 ids 清空后返回新的 value，模型看到的内容是按新值重新 render 出来的。第二行替换成 count: 'two'，被 output schema 拦下，错误码和第 8 篇工具体直接返回脏数据时一样，因为替换值走的是同一个 createSuccessResult()（tools/src/index.ts:1779）：

const replaced = this.createSuccessResult(exec, tool, decision.value)

第 8 篇说 output schema 是出口闸门，post-execute 替换后的值同样要过这道闸门，策略层改结果也得守同一份契约。环绕层 tools/execute 换掉的成功值也是一样（normalizeDispatchResult()，tools/src/index.ts:1835）。

第 11 步在 next() 返回后把 value 换成 count: 'two'：

11. a value swapped in tools/execute is validated too
  around layer swaps the value: isError code=INVALID_TOOL_OUTPUT text="Error: tool \"lookup_release\" returned invalid output: \"value.count\" must be an integer"
    stages: pre-execute -> guard -> execute> -> body -> <execute -> finalizeContent -> result

错误码同样是 INVALID_TOOL_OUTPUT，但 stages 里这次没有 post-execute：环绕层的校验失败算工具流水线失败，直接成了最终结果。

第 6 步输出的第三行是 block：工具体已经执行过了，结果被整个替换成 feedback 的文本。它前面没有 Error: 前缀，模型看到的就是 feedback 的原文。查询已经发生、结果却不该给模型看时用它，比如事故期间冻结发布数据。

监听器抛错就是失败，而不是跳过

最后看策略插件自己出问题的情况，比如它依赖的外部服务不可用：

7. a throwing listener fails the call, it does not skip the policy
  pre-execute throws: isError code=- text="Error: policy service unreachable"
    stages: pre-execute -> finalizeContent -> result

调用失败，工具体没有执行，是 fail closed。阶段序列里连 post-execute 也没有，因为 prepareExecution() 的 catch 分支（:1514）生成的是 final-result，不是 post-result：

} catch (error: unknown) {
  return next({ kind: 'final-result', exec, result: toolErrorResult(error) })
}

环绕分派那一段的注释（:1572）写得更一般：

Tool and unknown-tool failures still receive post-execute; pipeline failures are already final.

工具体抛错、工具不存在，这些属于“调用本身的结果”，仍然交给 post-execute 处理；工具流水线里的监听器抛错，直接生成最终结果。第 12 步对照了前两种：

12. tool failures still reach post-execute
  the body throws: isError code=- text="Error: release platform returned 502"
    stages: pre-execute -> guard -> execute> -> body -> <execute -> post-execute -> finalizeContent -> result
  unknown tool: isError code=UNKNOWN_TOOL text="Error: unknown tool \"no_such_tool\""
    stages: pre-execute -> guard -> execute> -> <execute -> post-execute -> result

两行的 stages 里都有 post-execute。不存在的工具也照样走完 pre-execute 和守卫，只是没有工具体；它没有工具定义，所以也没有 finalizeContent。

finalizeContent 的注释（:233）写了它会覆盖 “pipeline failures that bypass tools/post-execute”，所以第 7 步的阶段序列里 finalizeContent 和 result 还在。

调用方取消是另一类结果。第 13 步分别在 pre-execute 里和工具体运行中 abort 调用方的 signal，后一次工具体不理 signal、照常返回成功值：

13. caller cancellation: before dispatch, and after the body started
  caller aborts during pre-execute: isError code=ABORTED_BEFORE_DISPATCH text="Error: tool call aborted before dispatch"
    stages: pre-execute -> guard -> post-execute -> finalizeContent -> result
  caller aborts while the body runs: isError code=ABORTED text="Error: tool call aborted"
    stages: pre-execute -> guard -> execute> -> body -> <execute -> post-execute -> finalizeContent -> result

看两行的错误码：工具体还没开始，得到 ABORTED_BEFORE_DISPATCH，stages 里没有 body；工具体已经跑完并返回成功，结果仍被换成 ABORTED。

这对 Agent 意味着什么

不许全量查询这类不可绕过的禁止规则，用 tools.guard() 写：同步、只能拒绝，前置的 allow-all 也改不成放行。但守卫之后还有环绕层，第 8 步里 tools/execute 监听器在守卫之后整体换掉了参数，3 条记录照样全出来。

可协商的策略放在 pre-execute，就得接受外层监听器可能先做决定，第 2 步里前置的 allow-all 就让全量查询放行了。要人确认的用 ask，返回前先确认组合里挂了 ctx.approval，否则等于 deny。

超时包在 tools/execute 上，工具体不理 signal 时拦不住耗时；脱敏、冻结这类结果处理放 post-execute，替换的值要过 output schema。守卫拿到的参数没有经过 schema 校验，service=123 原样进到守卫，写规则时要先判断参数类型。

本文的验证范围

实测部分是一个脚本 pipeline-demo.ts，挂载真实的 dsh-system-prompt、dsh-tools、dsh-tool-call-timeout-policy 和 dsh-scope，不启动 agent 循环，直接调用 ctx.tools.execute()，没有启动 CLI/Web。

第 9、10 步的 agent 是只带 id 的普通对象；第 10 步的审批服务是按预设结果回答的桩，没有用 dsh-user-approval。

lookup_release 是简化版（service 可选、内存数据），不是第 3 篇的正式插件。本机跑通，输出即文中所引，阶段序列来自每个阶段挂的记录监听器。

主要结论都有断言：

  • 只记录的监听器下，一次调用依次经过全部阶段；
  • pre-execute 策略拒绝不带 service 的调用，追加的 allow-all 不改变结果，前置的 allow-all 让全量查询返回 3 条记录；
  • 同一规则写成守卫后，前置 allow-all 下仍被拒，service=123 和空白字符串同样被拒，阶段序列跳过工具体；
  • 未挂审批服务时，ask 以它的 reason 被拒；
  • 两次超时都返回 TOOL_TIMEOUT，配合 signal 的工具体在 150ms 内结束，不理 signal 的至少等满 195ms；
  • post-execute 替换的值按新值渲染，不合 schema 的替换得到 INVALID_TOOL_OUTPUT，block 返回 feedback 原文；
  • pre-execute 监听器抛错时调用失败，阶段序列里没有 post-execute；
  • tools/execute 里改冻结参数的字段抛错；守卫放行后整体换成 {} 返回 3 条记录，换 name 得到 UNKNOWN_TOOL；
  • 三层守卫下，五次调用依次得到放行、放行、sub、agent-A、全局守卫的拒绝；
  • ask 省略 reason 得默认文本，有审批服务无 agent 时审批桩未被调用，四种审批结果各得对应文本；
  • 环绕层换成不合 schema 的值得到 INVALID_TOOL_OUTPUT，且不经过 post-execute；
  • 工具体抛错与工具不存在都经过 post-execute，阶段序列与文中一致；
  • 分派前取消得到 ABORTED_BEFORE_DISPATCH 且没有执行工具体，工具体运行中取消得到 ABORTED。

行为与文中不符时脚本以非零退出码结束。连续 3 次运行，输出都一致。
