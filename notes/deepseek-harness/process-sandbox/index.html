第 11 / 36 节 · 能力、工具与会话

中文 locale 下，沙箱拦住了写报告的命令，判定结果是 denied=false：模型收到的输出从 5 行缩到 3 行，拒绝标记和提权提示都没了。

上一篇的守卫管的是“这次调用该不该发起”。放行之后，一条 shell 命令在机器上做了什么，守卫就看不到了。这一篇看最底下那一层：dsh 的进程沙箱如何限制子进程能碰哪些文件。

这次跑一条“筛选发布日志”的 shell 命令 grep ERROR logs/payment-api-1.4.2.log > reports/payment-api-errors.txt，从工作区里的日志筛出错误行，写成一份报告，看它在各种模式下碰到什么边界。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • workspace-write 拦工作区外写入，/tmp 写入不留在宿主上；
  • 最严格的 read-only 下，仍能读工作区外文件、连宿主 TCP 端口；
  • 中文 locale 下同一次拒绝被判为 denied=false；
  • runner 链清空时受限模式拒跑，danger-full-access 照跑。

进程沙箱拆成四个包

这里又是第 8 篇讲过的 seam 结构：

包注册为职责
dsh-sandbox—（定义）抽象、模式词汇、提权规则
dsh-sandbox-localctx.sandbox按平台选 runner 包装 argv
dsh-sandbox-policyctx.sandboxPolicy默认模式、工作区根、会话切换
dsh-bash-sandboxctx.shellspawn 前交给 sandbox 包装

dsh-sandbox 定义的抽象是 SandboxProvider；dsh-bash-sandbox 继承本地 bash 执行器，spawn 前先把 argv 交给 ctx.sandbox 包装。seam 只有一个方法（packages/sandbox/sandbox/src/index.ts:176）：

abstract confine(argv: readonly string[], policy: SandboxPolicy, signal?: AbortSignal): Promise<ConfinedArgv>

confine() 接收准备 spawn 的 argv，返回包装后的 argv，调用方改用它去 spawn。策略作为参数传入，provider 不保存它。源码注释（:62）给的理由：两个消费方可能同时用不同策略限制子进程，一次获批的提权重试也就是一次策略更宽的新调用。

基础组合（base bundle）把它们接起来（packages/bundle/base/cordis.patch.yml:212），默认模式是 workspace-write：

- id: sandbox
  name: '@deepseek-ai/dsh-sandbox-local'
- id: sandbox-policy
  name: '@deepseek-ai/dsh-sandbox-policy'
  config:
    mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
    workspaceRoot: !!js process.cwd()
- id: bash-sandbox
  name: '@deepseek-ai/dsh-bash-sandbox'
  disabled: !!js process.platform === 'win32'
  # …

三种模式只描述文件写入：read-only 只允许 /dev/null 这类必需的写入口，workspace-write 可以写工作区和临时区域，danger-full-access 完全不经过沙箱。

图：受限模式交给后端包装，结束后从 stderr 推断是否被拒；danger-full-access 不经过沙箱。

bwrap 把宿主根目录只读挂载

实测脚本先直接调用 ctx.sandbox.confine()，看它把筛日志的命令变成了什么：

1. the provider wraps argv; the policy travels with each call
  runner=bwrap enforcement=full denialSignatures=["read-only file system"]
  argv: bwrap --ro-bind / / --dev /dev --unshare-pid --proc /proc --die-with-parent --tmpfs /tmp --bind <ws> <ws> -- bash -c grep ERROR logs/payment-api-1.4.2.log > reports/payment-api-errors.txt

argv: 一行里的 <ws> 是脚本在 HOME 下新建的工作区目录。这一串参数来自 bwrapProfileArgs()（packages/sandbox/sandbox-local/src/profiles.ts:16）：

  • --ro-bind / /：整个宿主根目录只读挂进来；
  • --dev /dev、--unshare-pid --proc /proc：新的 /dev，私有 PID 命名空间里的 /proc；
  • workspace-write 才加的两项：--tmpfs /tmp 给一个空的临时 /tmp，--bind <ws> <ws> 把工作区以可写方式挂回原路径。

合起来，bwrap 下的 workspace-write 是宿主文件系统只读，只有工作区可写且能留下结果；/tmp 虽然可写，但只是随命令销毁的 tmpfs。

用哪个 runner 按平台决定（packages/sandbox/sandbox-local/src/index.ts:159）：

const PLATFORM_CHAINS: Record<string, readonly SelectedRunner['runner'][]> = {
  linux: ['bwrap', 'landlock'],
  darwin: ['seatbelt'],
  // …
  win32: ['windows-acl'],
}

Linux 有两个候选，按顺序逐个做功能探测（bwrap 的探测是用 read-only profile 跑一次 true），第一个通过的被选中、后面的不再探测。

本机的 bubblewrap 是 0.9.0，探测通过，报告 enforcement=full。

选择结果在 provider 的生命周期内只算一次（sandbox-local/src/index.ts:496）。第 1 步接着另起一个 provider，用测试钩子让 bwrap 探测先失败，再把它“修好”，最后重载插件：

cache: bwrap probe fails            -> SANDBOX_UNAVAILABLE
cache: bwrap fixed, same provider   -> SANDBOX_UNAVAILABLE (bwrap probed 1 time)
cache: provider plugin reloaded     -> runner=bwrap

看中间一行：bwrap 已经能用了，同一个 provider 仍然报 SANDBOX_UNAVAILABLE，探测只跑过 1 次。装好或修好 bwrap 之后，要重载沙箱插件才会生效。

read-only 模式能读不能写

demo 里 sandbox-policy 以 read-only 挂载。read-only 是插件自身的 schema 默认值（packages/sandbox/sandbox-policy/src/index.ts:113），基础组合把它覆盖成了 workspace-write。

输出标签里的 deployment default 因此指的是 demo 自己的部署，不是基础组合的默认值。

先数错误行，再生成报告：

2. read-only (the deployment default): reads pass, the report write is refused
  [read-only] grep -c ERROR logs/payment-api-1.4.2.log
    exit=0 denied=false
  [read-only] grep ERROR logs/payment-api-1.4.2.log > reports/payment-api-errors.txt
    exit=1 denied=true stderr="bash: line 1: reports/payment-api-errors.txt: Read-only file system"
  model sees:
    | [stderr]
    | bash: line 1: reports/payment-api-errors.txt: Read-only file system
    | [sandbox: file access denied under read-only mode]
    | [sandbox: escalation available — retry this exact command once with sandbox_permissions (the narrowest wider mode that suffices) + justification; the approval prompt asks the user]
    | [exit code: 1]

前两行里读日志没问题，后两行里重定向写报告被内核拒绝，脚本断言了报告文件确实不存在。

model sees 是通过 ctx.tools.execute() 调用 bash 工具拿到的文本，即模型实际读到的内容：stderr 原文，加两行标记。第一行告诉模型这是策略拒绝，不是命令写错了；第二行告诉它可以带上 sandbox_permissions 和一句理由重试。

bash 工具的描述（packages/shell/tool-bash/src/index.ts:77）也在教模型认这个标记：

a blocked file operation is reported as [sandbox: file access denied under <mode> mode] — a policy denial, not a bug in the command; do not retry another way.

记住这两行标记，第 5 步它们会消失。

工作区外写不进，/tmp 写了也不留

同一条命令换成 workspace-write，再试着改工作区旁边的部署配置，最后往 /tmp 写一个文件：

3. workspace-write: inside the workspace yes, beside it no, /tmp is private
  [workspace-write] grep ERROR logs/payment-api-1.4.2.log > reports/payment-api-errors.txt
    exit=0 denied=false
  [workspace-write] echo tampered > <outside>/deploy.env
    exit=1 denied=true stderr="bash: line 1: <outside>/deploy.env: Read-only file system"
  [workspace-write] echo scratch > /tmp/dsh-sandbox-demo-probe && cat /tmp/dsh-sandbox-demo-probe
    exit=0 denied=false
    host sees /tmp/dsh-sandbox-demo-probe? false

第一条命令生成了报告，两行错误都在；<outside> 是和工作区同级的另一个目录，改写被拒，文件内容没变。

/tmp 那一行，沙箱里写成功、也读得回来，命令结束后宿主上却没有这个文件，因为 bwrap 给的是一个随命令销毁的 tmpfs。

bash-sandbox 的 README 里有一张表列了各后端的差别：Landlock 下是宿主 /tmp，Seatbelt 下是 /private/tmp 加每用户临时目录，写到 /tmp 的文件能不能留给下一步用，因后端而异（按 README，未实测）。

模式不管读和网络

模式词汇的定义（sandbox/src/index.ts:24）如下：

read-only permits only required sinks such as /dev/null; workspace-write also permits the workspace and a backend-defined temp area; danger-full-access bypasses confinement. Network and process visibility are outside this vocabulary.

实测边界外的读和网络：

4. what the modes do not cover: reads, network; processes are hidden by bwrap only
  [read-only] cat <outside>/deploy.env
    exit=0 denied=false
  [read-only] exec 3<>/dev/tcp/127.0.0.1/<port> && echo connected
    exit=0 denied=false
  [read-only] ps -e --no-headers | wc -l
    exit=0 denied=false
    processes visible inside: 4

在最严格的 read-only 下：

  • 工作区外的 deploy.env 照样能读出来（文件内容是 demo 造的假 token）；
  • 脚本在宿主 127.0.0.1 上开了一个 TCP 端口，沙箱里的 bash 连得上；
  • ps 只看到 4 个进程。这来自 bwrap 的 --unshare-pid，模式本身没有承诺；Landlock 的授权参数和 Seatbelt 的 profile 里都没有对应的设置（按源码，未实测；sandbox-local/src/profiles.ts:30、:51）。

bwrap 参数里没有 --unshare-net，也没有限制读取的挂载。实测只证明工作区外的演示文件可读、宿主本机端口可连；没有读取真实凭证，也没有测试向外网发送内容。只靠写入限制，不能把读取范围或网络访问视为已隔离。

“被拒绝”是从 stderr 猜出来的

第 2 步的 denied=true 来自 bash-sandbox 在命令结束后做的分类（packages/shell/bash-sandbox/src/index.ts:119），先看是不是 runner 自己挂了，再看是不是拒绝：

const runnerFailure = classifyRunnerFailure(result.exitCode, result.stderr.text, facts.runnerFailureRules)
if (runnerFailure !== undefined) {
  throw new SandboxUnavailableError(mode, runnerFailure.detail)
}
return { ...result, sandbox: { mode, denied: classifyDenial(result, facts.denialSignatures), enforcement: facts.enforcement } }

classifyDenial 最后落到 matchesSignature()（packages/sandbox/sandbox/src/diagnostics.ts:96）：

export function matchesSignature(exitCode: number | null, stderr: string, signatures: readonly string[]): boolean {
  if (exitCode === null || exitCode === 0) return false
  const lowered = stderr.toLowerCase()
  return signatures.some(signature => lowered.includes(signature.toLowerCase()))
}

退出码非零，且 stderr 里包含后端的拒绝签名，就算被拒。

bwrap 的签名只有一条英文短语 read-only file system（sandbox-local/src/index.ts:206），Landlock 是 permission denied，Seatbelt 是 operation not permitted（按源码，未实测）。

可 stderr 是 bash 和各个命令按当前 locale 打印的。

中文 locale 下，拒绝标记和提权提示消失

脚本开头把 LC_ALL 设成了 C，第 5 步把它换成 zh_CN.UTF-8 再跑同一条命令：

5. "denied" is inferred from stderr text
  [read-only] grep ERROR logs/payment-api-1.4.2.log > reports/payment-api-errors.txt
    exit=1 denied=false stderr="bash: 行 1: reports/payment-api-errors.txt: 只读文件系统"
  model sees:
    | [stderr]
    | bash: 行 1: reports/payment-api-errors.txt: 只读文件系统
    | [exit code: 1]
  [read-only] echo "error: Read-only file system (from our own CLI)" >&2; exit 1
    exit=1 denied=true stderr="error: Read-only file system (from our own CLI)"

看第一条命令：写入同样被拦住了，文件没有生成，沙箱本身没有失效。但“只读文件系统”不包含 read-only file system，于是 denied=false。模型看到的只剩一个普通的失败，没有拒绝标记，也没有提权提示，不知道这是策略拒绝，也不知道可以请求用户批准。

第 5 步的 model sees 是在工具层测的：bash 工具不接受 env 参数，子进程的 locale 继承自 dsh 进程本身。demo 在调用前把进程的 LC_ALL 改成中文来模拟“在中文终端里启动 dsh”。

dsh 的 bash 执行器只给子进程补了 NO_COLOR、TERM、PAGER、GIT_PAGER 4 个变量，没有统一 locale（packages/shell/bash-local/src/index.ts:27）。

仓库调 git 时带了 LC_ALL: 'C'（packages/deliverables/workspace-changes/src/git.ts:69），bash 工具这条路径没有。

反过来也会误判：第二条命令自己往 stderr 打印了这个短语然后退出 1，没有任何文件操作，也被归为拒绝。bash-sandbox 的 README 在“已知限制”里写了这类问题：拒绝是从 stderr 推断的，包含相同特征的应用错误可能被归为拒绝；拒绝信息不在保留的 stderr 尾部里时也可能漏判。locale 这种漏法文档里没有提。

第 8 篇的 tool-fs 走 ctx.fs 的沙箱实现时，拒绝由进程内的栅栏直接返回结构化错误码 FS_SANDBOX_DENIED，不需要猜。bash 跑在外部进程里，跨平台的 seam 只拿得到退出码和 stderr，是否被拒只能从这两样推断。

没有 runner 就不跑

为了模拟主机上没有可用 runner，demo 另起一个 Context，用包自带的测试钩子 internals.chain = [] 把 runner 链清空：

6. fail closed: no usable runner, no unconfined fallback
  read-only -> SANDBOX_UNAVAILABLE: sandbox mode "read-only" is requested but no sandbox backend is usable on this host
  danger-full-access -> exit=0 sandbox={"mode":"danger-full-access","denied":false} (provider never consulted)

read-only 下直接抛 SANDBOX_UNAVAILABLE，脚本断言了命令里的 touch 没有执行。

SandboxUnavailableError（sandbox/src/index.ts:131）的错误文本后半句是 “refusing to run the command unconfined”，然后列出各平台该装什么。这是 fail closed：限制不了就不执行，不会退回到不受限的执行。

同一个 Context 里，danger-full-access 却照样执行成功了。这个模式在 bash-sandbox 里是一个提前返回（bash-sandbox/src/index.ts:92），不问 provider，沙箱不可用也不影响它。

要管住的是能把模式改成 danger-full-access 的几个入口：部署默认值、会话切换，以及“提权一次只管一次调用”里的审批。

另一条 fail closed 路径是单独跑出来的：把链强制设成只有 Landlock 时，本机的 landlock-run 启动器没有编译出来，调用同样以 SANDBOX_UNAVAILABLE 失败，错误末尾附了 Runner failure: ... ENOENT。

单一候选不做探测，失败发生在执行时，结果仍然是不执行。

提权一次只管一次调用

第 2 步的提示让模型带上 sandbox_permissions 重试。先直接在工具层试：

7. escalation: one call, one approval, strictly wider only
  via tool, no approval service -> "sandbox escalation to \"workspace-write\" requires approval, but no approval service is composed"

demo 这里没有挂审批服务，提权直接失败，命令没有执行。基础组合里挂的是 dsh-user-approval（base/cordis.patch.yml:232），它自己不弹确认，请求交给部署挂的应答器（approval/request 监听器）来回答。

审批逻辑本身是一个独立函数 approveEscalation()（packages/sandbox/sandbox/src/escalation.ts:153），demo 给它一个假的审批者，记录它被问了几次：

read-only -> read-only       : granted read-only
workspace-write -> read-only : refused: sandbox escalation to "read-only" is not strictly wider than this call's current "workspace-write" mode
read-only -> workspace-write : granted workspace-write
read-only -> workspace-write, user rejects: refused: the user rejected escalating this command to "workspace-write"
approval prompt reason: "escalate sandbox to workspace-write: save the error summary into the workspace"

四种请求，审批者只被问了两次（脚本断言了次数）：

  • 请求当前模式，直接放行，不打扰用户；
  • 请求更窄的模式，直接拒绝。阶梯是一张封闭的表（:28），read-only 能升到另外两档，workspace-write 只能升到 danger-full-access；
  • 严格更宽的请求才会问用户，理由原样放进审批提示；
  • 用户拒绝，就抛错，命令不执行。

接着挂上 dsh-user-approval 和一个脚本化的应答器（每次都批准一次）。先不经过 agent 直接调工具，再让脚本化模型在真实 agent 循环里连发三次 bash：

via tool, approval service composed, no agent -> "sandbox escalation to \"workspace-write\" requires approval, but the call has no agent to route it through"
real agent loop, dsh-user-approval + a scripted answerer that allows once:
  call 1 bash                       -> [sandbox: file access denied under read-only mode]
  call 2 bash + sandbox_permissions -> (no output)
  call 3 bash (same command again)  -> [sandbox: file access denied under read-only mode]
  answerer asked 1 time; session log: approval/asked, approval/decided(allowed-once)

第一行不太符合直觉：审批服务挂上了，但调用没有 agent，提权仍然失败（sandbox/src/escalation.ts:165）。第 9 篇里 ask 在没有 agent 时等于 deny，是同一个设计。

agent 循环里，第 1 次被拒并带着提权提示；第 2 次带上 sandbox_permissions，应答器被问 1 次、批准，报告写成了（(no output) 是因为输出都重定向进了文件）。

第 3 次原样重跑同一条命令，又回到 read-only 被拒。获批的模式只合进那一次调用的策略，下一次调用重新解析会话的常驻策略（tool-bash/src/index.ts:336）。会话日志里留下一对 approval/asked、approval/decided 作审计。

会话模式切换是一条日志事件，重启后仍生效

提权是一次性的。要让整个会话换模式，走的是 setSandboxMode()（sandbox-policy/src/session-mode.ts:53）：往会话日志追加一条 sandbox/mode 事件，ctx.sandboxPolicy 解析策略时读这条事件的投影。

第 8 步在第 7 步的会话上切到 workspace-write，关掉宿主，从同一目录的 JSONL 日志恢复会话，再写一次报告：

8. a session mode switch is one event in the log and survives a restart
  log line: {"type":"sandbox/mode","data":{"mode":"workspace-write"}}
  after restart: overrideOf(session)=workspace-write default=read-only
  bash after restart -> "(no output)", report lines=2

看 after restart 一行：部署默认值还是 read-only，会话的覆盖值从日志回放回来了。写报告直接成功，应答器没有再被问，脚本断言了它的计数仍是 1。

后台任务的 runner 失败被记成 killed

bash 带 run_in_background 时命令交给 ctx.jobs，结果从任务输出里读。bash-sandbox 在进程结束时同样做一次分类（bash-sandbox/src/index.ts:159）。

第 9 步先在 read-only 下后台写报告，再在一个只剩 Landlock 档的 Context 里后台跑 touch。本机没编译 landlock-run，runner 本身起不来：

9. background jobs: the same denial and runner-failure markers, in the job output
  [read-only, bwrap] started background job bash-1; status=completed detail="exit code: 1"
    | [stderr]
    | bash: line 1: reports/payment-api-errors.txt: Read-only file system
    | [sandbox: file access denied under read-only mode]
    | [sandbox: escalation available — retry this exact command once with sandbox_permissions (the narrowest wider mode that suffices) + justification; the approval prompt asks the user]
  [read-only, landlock launcher missing] started background job bash-1; status=killed detail="killed before exit"
    | [stderr]
    | subprocess failed before reporting an outcome: Error: spawn ~/code/harness-fresh/deepseek-harness/native/system/packages/linux-x64/bin/landlock-run ENOENT
    | [sandbox: the sandbox runner itself failed under read-only mode — the command did not run; this is a sandbox problem, not a command failure]

第一个任务的拒绝标记、提权提示和前台一致，状态是 completed，exit code: 1。

第二个任务的状态是 killed、killed before exit，其实没有谁杀它：启动器不存在，spawn 报 ENOENT，命令没跑。输出里的标记说对了，是 runner 失败，状态栏记错了。

源码知道这个缺口，tool-bash/src/background.ts:19 的 TODO 写明 runner 失败目前借用了无信号的 kill。

只看任务状态做重试或告警的消费方，会把“沙箱坏了”当成“任务被杀”。

这对 Agent 意味着什么

三种模式只约束文件写入。实测 read-only 能读取工作区外的演示文件、连接宿主本机端口；真实凭证与外网传输没有测过。若要隔离敏感文件和网络，还需另行限制并验证。

写入由内核拦截，中文 locale 下照样拦住了；“被拒绝”的判定靠 stderr 字符串匹配，换了语言就漏判。中文环境下，模型收不到拒绝标记和提权提示，收到的只是普通失败；demo 在 LC_ALL=C 下，同一次拒绝被正确识别。

受限模式在沙箱不可用时会拒绝执行，danger-full-access 却不经过沙箱，沙箱不可用时照样执行。部署时的 DSH_PERMISSION_MODE、会话日志里的 sandbox/mode 和提权审批，是需要管住的入口；会话切换写一条事件就生效，重启后还在，不经过审批。

本文的验证范围

实测部分是一个脚本 sandbox-demo.ts，挂载真实的 dsh-sandbox-local、dsh-sandbox-policy、dsh-bash-sandbox、dsh-subprocess-local、dsh-tool-bash。

脚本还挂载 dsh-system-prompt、dsh-tools、dsh-shell-env、dsh-session-projection、dsh-jobs-local、dsh-tool-jobs。

第 7、8 步另起宿主，挂真实的 agent 循环、dsh-user-approval、JSONL 会话持久化和脚本化模型，没有启动 CLI/Web。应答器是脚本化的，每次都批准一次，代替 CLI/Web 里的人工确认。

执行器层直接调用 ctx.shell.run()，模型视角通过 ctx.tools.execute() 调用 bash 工具。本机是 Linux，内核 6.8，bubblewrap 0.9.0。

/tmp 下的“工作区外”目录在 tmpfs 覆盖后不存在，往里写只报 No such file or directory，碰不到只读边界，所以 demo 把它建在 HOME 下。

read-only 模式不挂 tmpfs，同一写入报 Read-only file system；这一对照于 2026-09-28 用同样的 bwrap 参数单独补跑，强制只用 Landlock 时的 ENOENT 也是单独跑的，两者都不在示例脚本里。

运行需要可用的 bubblewrap（bwrap --ro-bind / / --dev /dev --unshare-pid --proc /proc --die-with-parent -- true 能成功，这就是 dsh 自己的探测命令）。

第 5 步需要 Bash 实际把只读文件系统错误输出成中文。即使 locale -a 已列出中文 locale，也不保证这一点：2026-10-02 的一次 Debian 容器复跑中，locale 已生成，Bash 仍输出英文；换用装有中文语言包的 Ubuntu 容器后才走到中文对照。

示例脚本遇到英文 Read-only file system 就打印“locale not installed”的提示并跳过该对照，即使其他断言通过仍以 0 退出。复现时要看第 5 步是否出现 denied=false、只读文件系统 和 model sees，不能只看退出码。

主要结论都有断言：

  • 本机选中的 runner 是 bwrap；探测失败的结论被缓存，修好后同一 provider 仍不可用、bwrap 只探测 1 次，重载插件后恢复；
  • read-only 下读日志成功，重定向写报告被判为拒绝，报告文件不存在；
  • workspace-write 下报告生成且含 2 行，写工作区外被判为拒绝且 deploy.env 内容不变，/tmp 写入成功但宿主上没有这个文件；
  • read-only 下能读出工作区外的文件、能连上宿主的 TCP 端口，沙箱里看到的进程少于 10 个；
  • Bash 实际输出中文错误时，同一次拒绝 denied=false，模型看到的文本里没有 [sandbox: 标记；自己打印英文拒绝短语的失败命令被判为拒绝；
  • runner 链清空时 read-only 调用被拒且 touch 没有执行，danger-full-access 照样执行；
  • 未挂审批服务时经工具提权失败；四种请求里审批者只被问两次；
  • 挂了审批服务但调用没有 agent 时提权失败；agent 循环里应答器只被问 1 次，获批那次写入成功，下一次同样的命令被拒，日志里有一对审批事件；
  • sandbox/mode 在日志里只有一条，重启恢复后覆盖值仍是 workspace-write，写报告成功且不再询问；
  • 后台任务的输出带拒绝标记，状态 completed；runner 失败的后台任务状态为 killed，输出带 runner 失败标记，touch 没有执行。

除第 5 步允许跳过中文对照外，已执行的断言不通过时脚本以非零退出码结束。此前连续 3 次运行，输出都一致；2026-10-02 在有中文错误输出的 Ubuntu 容器中复跑，第 5 步也通过。
