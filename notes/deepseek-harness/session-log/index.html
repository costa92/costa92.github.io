第 12 / 36 节 · 能力、工具与会话

一次查询，会话日志写下 16 条事件；模型看到的 5 条消息都由其中 5 条算出，没有单独存储。

沙箱的模式切换是写进会话日志的一条事件，不在别处另存状态（本文第 8 步实测）。dsh 对整个会话都这么做：一个会话的全部交互记成一份只追加的事件日志，模型的消息历史、UI 上的各种状态，都从这份日志算出来。

这次让 lookup_release 跑一次真实的 agent 循环，然后只读落盘的日志文件，还原这次查询的完整轨迹。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 一问一答加一次工具调用，写下 16 条事件；
  • 只读 JSONL 文件，离线算出的 surface 与运行中一致；
  • 重启后旧字节是新文件的前缀，历史和投影从日志重放；
  • 未标 ignorable 的未知事件让整份日志拒绝解读。

一次查询写下 16 条事件

docs/subsystems/session.zh.md 开头一段给了定位：

Session 是一份由类型化 SessionEvent 组成的仅追加日志，是 agent（智能体）完整交互历史的唯一真源。LLM（大语言模型）消息历史从日志派生而来，从不单独存储；回放即从同一组事件重新派生。

实测脚本挂载真实的 dsh-agent-loop、dsh-tools 和 JSONL 持久化，模型换成脚本化模型：第一次请求返回“调用 lookup_release”，第二次返回一句结论。持久化选了 compression: 'none'，默认是 zstd 压缩，关掉之后日志就是能直接读的文本。

问一句“payment-api 最近一次发布怎么样？”，然后打开磁盘上的文件：

1. one query through the real agent loop, persisted as JSONL
  file: <root>/_no-cwd/oncall-demo/session.v3.jsonl
  header: version=3 id=oncall-demo
    0 agent/inbox/spliced
    1 turn/start
    2 agent/inbox/spliced
    3 step/start
  * 4 system/message
  * 5 user/message         payment-api 最近一次发布怎么样？
    6 request/header       initial tools=[lookup_release]
    7 request/context
  * 8 assistant/message    call lookup_release({"service":"payment-api"})
    9 tool/call            lookup_release {"service":"payment-api"}
  *10 tool/result          1 record(s): demo-003 failed
   11 step/end
   12 step/start
  *13 assistant/message    payment-api 最近一次发布 demo-003 失败。
   14 step/end
   15 turn/end             completed

文件第一行是会话头（格式版本 3、会话 id），之后每行一个事件，seq 从 0 连续递增。_no-cwd 是因为 demo 的会话没有工作目录，正常会话会放在按 cwd 命名的项目目录下。

一问一答，加一次工具调用，写下了 16 条事件。里面有：

  • 轮次和步骤的边界（turn/*、step/*）；
  • 输入队列的变化（agent/inbox/spliced）；
  • 这次请求用的配置和工具（request/header、request/context）；
  • 一条单独的 tool/call 记录；
  • 前面标了 * 的 5 条消息事件。

图：事件追加进 JSONL，经 surface 派生历史、apply 折叠投影。

模型历史是算出来的

标 * 的是四种“产生消息”的事件类型（packages/core/session/src/types.ts:417 的 SurfaceEventType）：system/message、user/message、assistant/message、tool/result。

只有这四种事件带 surfaceOp 字段，声明自己怎么进入模型可见的有序列表，源码里叫 surface：

2. the model history is derived, not stored
  16 events -> surface [4,5,8,10,13] -> 5 messages: system, user, assistant, user, assistant
  foldSurface over the parsed file -> [4,5,8,10,13]

看第一行：surface 上是 seq 4、5、8、10、13 这 5 个事件，deriveMessages()（packages/core/session/src/index.ts:841）把每个事件投影成一条消息。

规则在 deriveEventMessage()（packages/core/session/src/surface.ts:119），源码注释写得很直接：

Intentionally non-exhaustive: only message-producing events derive history; turn/step boundaries, failed attempts, and errors are trace/replay data.

对照输出看两处：

  • tool/result 投影出来是一条 user 角色的消息，里面放 tool-result 块，所以角色序列是 system、user、assistant、user、assistant；
  • seq 9 的 tool/call 和 seq 8 的 assistant 消息里的 tool-call 块内容相同，但它不在 surface 上，是只进日志的执行记录。

第二行输出是另一种验证：脚本把 JSONL 文件逐行 JSON.parse，把事件数组交给导出的纯函数 foldSurface()（:544），得到的节点序号和运行中会话的 surface 完全一致。

拿到这个文件的进程不需要运行中的 dsh，就能算出模型当时看到的是哪几条事件；再对它们调用 deriveEventMessage() 就得到消息内容。

surface 不直接等于“所有消息事件”：压缩靠 replace 用新节点遮住一段旧节点，见第 13 篇。

屏幕上逐字出现的内容，也不等于每个字都已写进日志。官方架构文档把 agent/assistant-stream 定为进程内实时事件；一次尝试结束后，完整的紧凑流才随 assistant/message 或仅用于日志的 assistant/attempt 提交。

若进程在提交前硬中断，日志里没有那段持久的尝试流（按官方架构文档，未实测）。所以本文从文件还原的是已提交的历史，不能据此还原 UI 曾短暂显示的每个片段。

只读文件就能还原轨迹

按 seq 顺序把日志读一遍，就能还原这次查询的经过。脚本只用解析后的 JSON，挑出关心的事件：

3. rebuild the query trajectory from the file alone
  user asked              "payment-api 最近一次发布怎么样？"
  request header seq 6: initial tools=[lookup_release]
  step 1: model called     lookup_release {"service":"payment-api"}
  step 1: tool returned    "1 record(s): demo-003 failed"
  step 2: model answered   "payment-api 最近一次发布 demo-003 失败。"
  turn 1: ended          completed

request/header 记录了这次请求的调用配置和组装好的工具 schema，所以事后能回答“模型当时能调哪些工具、每个工具的参数长什么样”。

request/header 只在三种时机追加快照（docs/subsystems/session.zh.md）：

  • agent 循环实例开始（reason initial 或 resume）；
  • 请求内容变化（change）；
  • 开启新的消息序列（series，比如跟随一次 surface 替换）。

同一序列里的后续步骤和重试沿用最新的一份，所以这一轮有两次模型请求，却只有 seq 6 一条。

第 7 步在另一个会话里连问四轮：第二、三轮之间注册一个新工具 rollback_release，第三、四轮之间手工追加一条 replace 的 user/message，把前三轮的消息换成一句摘要（压缩就是这么替换 surface 的）：

7. request/header: appended at start, on change, and on a new series only
  turn 1: seq 7 initial tools=[lookup_release]
  turn 3: seq 25 change tools=[lookup_release,rollback_release]
  turn 4: seq 36 series tools=[lookup_release,rollback_release]

没有 turn 2 这一行：工具没变，第二轮不追加快照。第三轮工具多了一个，追加 change；第四轮请求内容没变，但 surface 被替换过，追加 series。

系统提示词不在 request/header 里，它是 surface 上的第 0 号节点 system/message（seq 4）。提示词变了就替换或追加一个系统节点，请求头不动（按源码，未实测）。

只追加，重启后文件只会变长

脚本接着关掉整个 Context，再用同一个根目录启动一个新的，恢复同一个会话后问第二个问题：

4. append-only: restart and ask again, the file only grows
  bytes 4560 -> 8592, old bytes are a prefix: true
  events 16 -> 31, seq contiguous: true
  request/header snapshots: seq 6 initial tools=[lookup_release]; seq 22 resume tools=[lookup_release]
  first new event: seq 16 session/end-seed

看第一行的 true：重启后的写入没有碰旧文件的任何字节，新事件全部接在末尾。

第 11 步用 strace -f -e trace=write,fsync,fdatasync,link 跑一个子进程，同样问一轮、重启、再问一轮，只保留会话目录下的调用：

11. every append is written, then fsync-ed, before it counts (strace)
  write  oncall-demo/session.v3.jsonl.<rand>.tmp 4467 bytes
  fsync  oncall-demo/session.v3.jsonl.<rand>.tmp
  link   oncall-demo/session.v3.jsonl.<rand>.tmp
  fsync  oncall-demo
  write  oncall-demo/session.v3.jsonl 68 bytes
  fsync  oncall-demo/session.v3.jsonl
  write  oncall-demo/session.v3.jsonl 2088 bytes
  fsync  oncall-demo/session.v3.jsonl

看第三、四行：第一批事件先写进临时文件并 fsync，再 link 成正式文件名，然后对目录 fsync。之后每批都是一次 write 紧跟一次同一文件的 fsync，脚本断言了每个 write 后面都是它。

这与 JSONL 后端 README 描述的写入方式一致：每批事件追加若干行，fsync 之后 append 才算完成。README 还说写入或同步失败时把文件截回之前的长度，“已提交事件绝不重写”（按 README，未实测）。

重启后新增的第一条事件是 session/end-seed，它是恢复时由 Session 构造函数追加的边界标记：之前的内容属于一个已经结束的生命周期。第二个请求头的 reason 也从 initial 变成了 resume。这两个细节和崩溃修复、fork 有关，是第 12 篇的内容。

历史和投影都从日志重放出来

历史既然是从日志算出来的，重启恢复就不需要任何额外的快照：

5. restart = replay: history and projections come back from the log
  restored history equals the pre-restart history: true
  releaseQueries projection after restart + turn 2: ["payment-api","order-api"]

看第一行：比较对象是重启前后 deriveMessages() 的 JSON 序列化结果，重启后没有任何额外的恢复步骤，历史就一字不差。

第二行是会话投影（session projection）。模型历史只是日志的一种派生结果，UI 需要的状态是另一种。

dsh-session-projection 提供了一个注册表，领域插件往里注册“折叠单元”：给一个初始状态和一个纯函数 apply(state, event)，框架对每个已提交的事件调用它。demo 注册了一个最简单的单元，按顺序记录查过哪些服务（节选，省略了 stateSchema，完整脚本见示例仓库）：

const releaseQueries: ProjectionDefinition<'releaseQueries'> = {
  key: 'releaseQueries',
  stateVersion: 1,
  init: () => [],
  apply: (state, event) => event.type === 'tool/call' && event.data.name === 'lookup_release'
    ? [...state, (JSON.parse(event.data.arguments) as { service: string }).service]
    : state,
}

["payment-api","order-api"] 这个列表没有保存在任何地方。第一个元素来自重启前的那一轮，它能出现，是因为注册表把恢复后的完整日志又折叠了一遍。

投影文档（docs/subsystems/session-projection.zh.md）规定：apply 必须同步、必须是纯函数，不关心的事件要返回同一个引用；注册表只订阅一次 session/event（packages/session/session-projection/src/index.ts:220），领域插件自己不持有订阅。

读不懂就拒绝

新版本的插件可能写出旧版本不认识的事件。脚本复制一份日志，在末尾手工追加一条 release/audit 事件，分别在不带和带 ignorable: true 两种情况下读取：

6. a reader refuses events it does not understand, unless marked ignorable
  ignorable=false: session "oncall-demo" contains event type "release/audit" (seq 31) unknown to this harness and not marked ignorable; refusing to interpret the log
  ignorable=true: read 32 events, last=release/audit

没有标记的，整份日志拒绝解读，前面 31 条正常事件也不给读；标了 ignorable 的，照常读出。

检查在 validateStoredEvents()（packages/session/session-persistence/src/storage-contract.ts:75），判断条件只有一行：类型不在 KNOWN_SESSION_EVENT_TYPES 里，且没有 ignorable: true。

为什么默认是拒绝而不是跳过？SessionEvent 类型上 ignorable 字段的注释（session/src/types.ts:478）给了理由：

Absent means required: a reader meeting an unrecognized type without this marker MUST refuse to reconstruct the session instead of silently dropping the event, because an unrecognized required event may change how the rest of the log is interpreted. … defaulting to required means a forgotten marker over-refuses (an inconvenience) rather than silently resuming a gutted session.

一条不认识的事件可能改变后面事件的含义，比如某个新插件用它声明“从这里往前的某段历史作废”。跳过它，读出来的历史就是错的，而且没人知道。

第 6 步的未知事件是手工追加的。第 8、9 步换成插件的正常写法：在第 7 步的会话上先切一次沙箱模式，再以仓库外插件的身份调用 Session.append() 写一条 release/audit，关掉宿主后用同一版本的 dsh 重新打开：

8. a sandbox mode switch is one more line in the same file
  last line: {"type":"sandbox/mode","seq":40,"time":<ms>,"data":{"mode":"workspace-write"}}
  files under the root: 4 -> 4; overrideOf(session) = workspace-write
9. an out-of-repo plugin appends its own event type: written fine, unreadable after restart
  append accepted at seq 41; last line on disk: {"type":"release/audit","seq":41,"time":<ms>,"data":{"note":"payment-api 1.4.2 rolled back"}}
  same dsh, reopen: session "header-demo" contains event type "release/audit" (seq 41) unknown to this harness and not marked ignorable; refusing to interpret the log

第 8 步的模式切换就是文件末尾多出一行，根目录下的文件数没变。第 9 步里写入被接受了，同一版本的 dsh 重开时却整份拒绝，和第 6 步一样。

读方认识的类型来自一份生成的静态清单，注释写明仓库外插件的事件“by construction”不在其中（packages/core/session/src/known-event-types.ts:8）。append() 也没有设置 ignorable 的入口（session/src/index.ts:719）。

写入时不拦，读取时才拒，插件作者要到下次重启才会发现。

默认的 zstd 压缩，撕裂的尾帧只丢解不开的部分

前面的步骤都关了压缩。默认的 zstd 格式是一个头帧加每批一帧。第 10 步用默认格式跑两轮（中间重启），再在副本上模拟两种写到一半的崩溃：只丢最后 4 字节的校验和，或把最后一帧截掉一半：

10. zstd (the default): a torn last frame gives up only what it cannot decode
  two turns across a restart: 4 zstd frames (header + one per append batch), 31 events
  drop the 4-byte checksum: zstd -t exit 1
    read 31 events, last=turn/end; resumed 32 events, zstd -t exit 0; one more turn 41 events, zstd -t exit 0
  cut the last frame in half: zstd -t exit 1
    read 17 events, last=session/end-seed; resumed 17 events, zstd -t exit 1; one more turn 26 events, zstd -t exit 0

看最后一行：截掉一半时，第二轮的 14 条事件全丢，前面的 17 条完好；恢复后文件仍然过不了 zstd -t，要等下一批新事件写入前才截掉残帧。只丢校验和时，一条事件都没少。

这对 Agent 意味着什么

模型为什么调了某个工具、当时能看到哪些工具、工具返回了什么，都在日志里按顺序排着，排查时照顺序翻日志即可。工具集随插件动态变化时，request/header 能把“当时的工具列表”也找回来。

需要的状态写成投影，不用另存，重启后从日志重新折叠就能恢复，第 5 步的查询列表就是这样回来的。

往日志里加新事件类型之前，得先想好旧读方怎么处理。第 6 步里，一条未标 ignorable 的未知事件让前面 31 条正常事件也读不出来；第 9 步里，插件用 append() 写的自定义事件写入时不报错，重开时整份被拒。

本文的验证范围

实测部分是一个脚本 session-demo.ts，挂载真实的 dsh-agent-loop、dsh-session、dsh-session-persistence-jsonl（compression: 'none'）和 dsh-session-projection。

脚本另外挂载 dsh-llm、dsh-system-prompt、dsh-tools、dsh-agent。模型是脚本化模型，回复写死在脚本里，不调用真实的 DeepSeek。没有启动 CLI/Web。

日志内容、surface、派生历史、重启恢复和读方拒绝都来自本机运行。第 6 步的 release/audit 事件是在日志副本末尾手工追加的，第 9 步的是经 Session.append() 写入的。

第 7 步的 surface 替换是手工追加的一条 replace 事件，没有挂压缩插件；第 7、8 步的宿主另挂 dsh-sandbox-policy。第 10 步用默认的 zstd 压缩，撕裂是在副本上截断文件模拟的。第 11 步需要本机有 strace，没有时脚本打印提示后跳过。

主要结论都有断言：

  • 一次查询写下的 16 条事件类型及顺序；
  • surface 节点是 [4,5,8,10,13]，派生消息的角色是 system、user、assistant、user、assistant；对文件离线 foldSurface() 得到同样的节点；
  • 只读文件还原出的查询轨迹；
  • 重启后旧文件是新文件的字节前缀，seq 连续，新增的第一条事件是 session/end-seed；
  • 重启前后派生历史的 JSON 相同，投影结果是 ["payment-api","order-api"]；
  • 未标 ignorable 的未知事件让读取失败，标了之后照常读出；
  • request/header 只有 initial、change、series 三条，工具没变的那一轮没有；
  • 模式切换后文件最后一行是 sandbox/mode，根目录下文件数不变；
  • append() 写的自定义事件在同版本重开时被拒；
  • zstd 尾帧撕裂后能读出的事件数分别为 31 和 17，下一批写入后文件通过 zstd -t；
  • strace 里每个 write 之后紧跟同一文件的 fsync。

行为与文中不符时脚本以非零退出码结束。连续 3 次运行，输出都一致。
