第 16 / 36 节 · 能力、工具与会话

工具一次返回 2000 行发布日志，模型只看到 49999 字节的首尾预览和通知，三条失败记录全在被省掉的中间。会话日志里也只剩预览和一个路径，文件满 30 天后，路径还在，文件没了。

第 13 篇的剪枝器（dsh-compaction-tool-result-pruner）只改模型看到的那一份历史，日志里的工具结果一个字不动。本篇的 spill（溢出落盘）不一样：工具结果太大时，它在结果作为 tool/result 写进会话日志之前就把内容换掉，模型和日志拿到的都是同一份首尾预览，外加一个指向完整文件的路径。

这次让一个工具一次返回 2000 行发布日志（122889 字节），失败记录只出现在中间，然后看模型拿到了什么、日志里留下了什么、模型能不能自己读回来，以及 fork、重启、过期之后这个路径还能不能用。最后拿用户附件的存储做对照。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 12 万字节的结果，模型和日志都只拿到 49999 字节的预览加通知；
  • 预览接缝没有省略标记，拼出一行畸形记录；
  • 模型按路径 read，能读回中间的三条失败记录；
  • 文件过期被清理后，继承的路径读出 FS_NOT_FOUND。

spill 拆成三个包，只有一个方法

spill 按第 8 篇的 seam（可替换能力）拆成三个包：

  • dsh-spill 定义 ctx.spillStore，只有一个方法 saveText()：存一段文本，返回定位信息 locator、精确字节数和一句给模型的取回提示 retrievalHint；
  • dsh-spill-local 是本地文件系统实现，locator 就是文件路径；
  • dsh-spill-policy 决定什么时候 spill，并把工具结果换成预览加通知。

基础组合（base bundle）挂了 spill-local 和 spill-policy（dsh-spill 只是抽象服务定义，由后端继承），策略的上限是 maxInlineBytes: 50000（packages/bundle/base/cordis.patch.yml:390-396）。

spill-local 未配置，用默认值：根目录是构造时在系统临时目录下创建的私有目录 dsh-spill-XXXXXX（每进程一个，权限 0700），清理期 30 天（packages/spill/spill-local/src/store.ts:37；packages/spill/spill-local/src/index.ts:68）。

策略挂在 tools/post-execute 这个 waterfall 上（packages/spill/spill-policy/src/index.ts:185），先让下游监听器处理完，再决定要不要换：

const decision = await next()
// Skip `read` to avoid a read → spill → read again loop.
if (decision.kind !== 'accept' || Object.hasOwn(decision, 'value')
  || exec.parent !== undefined || exec.name === 'read') return decision

只处理被接受的、没有替换值的、非嵌套调用的纯文本结果；read 工具的结果跳过，否则模型读 spill 文件得到的内容又会被 spill 一次。超过上限才动手。

图：完整内容只写进 spill 文件，模型和会话日志拿到同一份首尾预览加路径；fork 继承路径，文件过期后路径失效。

12 万字节进来，模型看到 49999 字节

让工具返回 2000 行、122889 字节的日志（输出里 <tmp> 是脚本的临时目录，<rand> 是文件名里的随机前缀，打印时遮掉以便每次输出一致）：

1. a 2000-line tool result is over maxInlineBytes: the full text goes to a file
  tool output 122889 bytes -> model sees 49999 bytes (cap 50000)
  notice: "(Omitted 73103 bytes. Full formatted result stored at: <tmp>/spill/session-6da900528adc/<rand>-fetch_deploy_log.txt. Use read with offset/limit, or grep this path to search within it.)"
  spill file spill/session-6da900528adc/<rand>-fetch_deploy_log.txt: 122889 bytes, identical to the tool output: true
  failed releases in the spill file: demo-1001 demo-1002 demo-1003; in what the model sees: []
  preview 49786 bytes + blank line 2 bytes + notice 211 bytes = 49999
  preview seam, rows 409-411: "demo-0409 payment-api 1.408.0 success canary=ok duration=40s" | "demo-0410 payment-api 1.409.0 success canary=ok durati success canary=ok duration=40s" | "demo-1600 payment-api 1.1599.0 success canary=ok duration=41s"
  session log on disk: 57512 bytes, contains "demo-1001": false, contains the locator: true, absolute: true

先看第 1 行：模型看到的是 49999 字节，没有超过 50000。做法是先给通知预留位置（spill-policy/src/index.ts:166-169）：

const reserve = Buffer.byteLength(formatSpillNotice({ kind: 'exact', count: totalBytes }, ref), 'utf8') + 2
const previewBudget = Math.max(0, cap - reserve)
const { text: previewText, omitted } = preview(text, previewBudget)
const notice = formatSpillNotice(omitted, ref)

预留按“省略了全部字节”估算通知长度，实际省略数的位数不会更多，通知只会更短或等长，所以预览加通知不会超限。剩下的预算一半给头、一半给尾（:97-98），由 dsh-output-retention 的 TextRetainer 按 UTF-8 字节截取。输出第 5 行：预览 49786 字节，空行 2 字节，通知 211 字节。

预留之后仍放不下时，策略保留原结果（:179）。第 9 步把上限调到 100 字节：

9. maxInlineBytes 100: even the notice does not fit, so the original result stays
  model sees the full 122889 bytes: true; spill files written anyway: 1

看这一行：模型拿到完整的 122889 字节，spill 目录里却多了一个没人引用的文件，源码注释称它是无害的孤儿，清理推迟（:177）。

预览接缝没有标记，拼出一行畸形记录

三个失败记录 demo-1001 到 demo-1003 都在被省掉的中间，模型一条也看不到。这点和第 13 篇的剪枝结果相同，接缝处却不一样。

剪枝器会在头尾之间插一行 [... tool result middle pruned ...]；spill 的预览没有任何标记，头部按字节在第 410 行中间截断，紧接着就是尾部的开头。尾部从第 1599 行中间开始，下一行就是完整的 demo-1600。

于是预览里出现了一行拼接出来的记录：前半截是 demo-0410，后半截是 demo-1599 的结尾。第 411 到 1598 行整整 1188 行消失，文本里看不出它们原来在哪。除了这行拼接出来的畸形记录，模型能得到的线索就只有末尾通知里的“省略了 73103 字节”。

spill 之后，第 13 篇的剪枝器还可能再剪一次。第 10 步用默认配置的剪枝器处理这份 49999 字节的结果：

10. the default pruner on a spilled preview: the notice survives in the kept tail
  49999 chars -> 5159 chars; ends with the whole notice: true; notice starts 4948 chars in

看这一行：剪完剩 5159 个字符，通知从第 4948 个字符开始，整段落在保留的 1024 字符尾部里，路径还在。

日志里也只剩预览

第 1 步输出的最后一行是和第 13 篇最大的不同。会话日志文件只有 57512 字节，里面搜不到 demo-1001，只有预览和那个路径，路径是宿主机上的绝对路径。

README 里说“成功的替换只改变面向模型的副本，绝不改变规范的程序化结果”，这里的程序化结果指工具返回的结构化值；会话日志记下的 tool/result 是面向模型的文本（packages/core/session/src/types.ts:343 起），所以日志里也只有预览。

完整内容只存在 spill 文件里。第 14 篇的全文搜索（基础组合默认关闭）索引的也是日志。

第 6 步给同一个进程挂上 SQLite 后端再搜：

6. spilled text is not in the log, so full-text search cannot find it
  searchSessions("demo-0001") -> ["oncall-payment-fork@66 tool/result","oncall-payment@10 tool/result"]
  searchSessions("demo-1500") -> []
  searchSessions("demo-1001") -> ["oncall-payment@23 tool/result","oncall-payment-fork@23 tool/result"]

看 demo-1500 那一行：它只在被省掉的中间，搜不到。demo-1001 搜得到，命中的却是第 2 步 read 读回来的那条 tool/result，fork 子会话继承了同一条。

模型按提示自己读回来

脚本化模型照通知里的提示，用 read 读中段：

2. the model follows the hint and reads the middle back with read
  | <path><tmp>/spill/session-6da900528adc/<rand>-fetch_deploy_log.txt</path>
  | <type>file</type>
  | <content>
  | 1000: demo-1000 payment-api 1.999.0 success canary=ok duration=53s
  | 1001: demo-1001 payment-api 1.1000.0 failed  canary=ok duration=54s
  | 1002: demo-1002 payment-api 1.1001.0 failed  canary=ok duration=55s
  | 1003: demo-1003 payment-api 1.1002.0 failed  canary=ok duration=56s
  | 1004: demo-1004 payment-api 1.1003.0 success canary=ok duration=40s

第 1001 到 1003 行正是三条失败记录。通知里的 retrievalHint 是本地后端写死的一句话（spill-local/src/index.ts:159）：用 read 带 offset/limit 读，或者 grep 这个路径。

第 2 步用挂载的 dsh-tool-fs 的 read 只读第 1000 行起的 5 行，远低于上限。第 7 步让它一次读 2000 行：

7. read is exempt: a read result over the cap stays inline
  read(offset 1, limit 2000) -> 55604 bytes inline, spill notice: false, new spill files: 0

看这一行：读回 55604 字节，超过 50000 的上限，照样整段留在结果里，也没有产生新的 spill 文件。

按路径读回能走通，前提是模型的 read 和 spill 后端看到的是同一个文件系统。spill-local 的 README 把它列为已知限制：远程或虚拟部署需要另一个 SpillStore 后端。

基础组合的 ctx.fs 是 dsh-fs-sandbox（bundle/base/cordis.patch.yml:504-505），它的 README 写明只限制写入和编辑、保留本地文件系统的读取行为。

第 8 步换成同样的组合，工作区设为 <tmp>/ws，spill 文件在工作区外：

8. with dsh-fs-sandbox (workspace-write, workspace <tmp>/ws), the spill file under the temp dir
  read  -> ok: "2: demo-0002 order-api 1.1.0 success canary=ok duration=41s"
  write -> ok: "<path><tmp>/spill/session-2df23b3019d5/<rand>-fetch_deploy_log.txt</path>\n<type>file</type>\n<content>\nUpdated "

看 write 那一行：读取没被拦，写入也成功了，spill 文件被改成一行 overwritten。spill 根目录在系统临时目录下，workspace-write 模式对这里放行，sandbox-policy 给模型的提示也写明部分平台临时区可写（packages/sandbox/sandbox-policy/src/index.ts:47）。

读取方面，bash 的进程沙箱同样不限制（第 10 篇）；spill-local README 的开发备注还提醒：将来如果加工作区隔离，必须显式放行 spill 路径。

fork 继承的是路径，不是文件

再 fork 一个子会话，让它自己也 spill 一次：

3. fork: the child inherits the parent locator; its own spills go to its own directory
  inherited locator: spill/session-6da900528adc/<rand>-fetch_deploy_log.txt  (session-6da900528adc = sha256("oncall-payment"))
  child's own spill: spill/session-2df23b3019d5/<rand>-fetch_deploy_log.txt  (session-2df23b3019d5 = sha256("oncall-payment-fork"))

两行的目录名不同：spill 文件按所属会话分目录，目录名是会话 id 的 sha256 取前 12 位，文件名前加 12 位随机十六进制，以 wx 和 0o600 排他写入（spill-local/src/store.ts:79-80,110,115）。

文件名猜不到，没法预先放一个同名符号链接。会话目录却是固定的，第 11 步在根目录里预先放了一个指向别处的会话目录链接：

11. the private root is the guard: a symlink planted inside it does redirect writes
  locator spill/session-f43918ee5ef2/<rand>-fetch_deploy_log.txt -> real path <tmp>/elsewhere/<rand>-fetch_deploy_log.txt
  spill root mode 700; files in <tmp>/elsewhere: 1

看第 1 行：spill 照样写了进去，真实路径落在 <tmp>/elsewhere。代码不检查会话目录是不是链接，挡住重定向的是 0700 的根目录：其他本地用户没法往里放东西。

fork 的子会话，日志开头是父日志的副本（第 12 篇），路径原样保留，指向父会话目录。文件不复制，也不改归属；子会话之后 spill 的内容写到自己的目录。SpillOwner 的类型注释（packages/spill/spill/src/types.ts:31-36）写明了这一设计，于是同一个文件可能被多个会话的日志引用，却只按一个时间戳过期。

30 天后，路径还在，文件没了

脚本把父会话那个 spill 文件的修改时间改到 31 天前，关掉 Context 再启动一个新的：

4. restart after 31 days: the startup sweep deletes the old file, the log still points at it
  parent spill file exists: false; child spill file exists: true
  read(inherited locator) -> FS_NOT_FOUND: "Error: cannot read \"<tmp>/spill/session-6da900528adc/<rand>-fetch_deploy_log.txt\": not found"

第 1 行显示，父会话的文件被删了，子会话自己那份还在。

spill-local 激活后会尝试清理一次：扫描配置的根目录和系统临时目录下以前留下的默认根目录，删除 mtime 严格早于截止时间的普通文件，再修剪空目录（判断在 packages/spill/spill-local/src/cleanup.ts:256，根目录收集在 :418-431）。

接着恢复 fork 子会话，让模型再读一次继承来的路径：FS_NOT_FOUND。日志里的预览和路径都还在，路径指向的文件已经没了。

配置注释（spill-local/src/index.ts:44-46）说明这是有意的：恢复或 fork 出来的会话可能还引用旧路径，所以保留到过期为止。过期以后，spill 接口没有取回、刷新或续期的方法，日志里也没有全文的备份。

  • 清理只在 spill-local 插件激活时跑（spill-local/src/index.ts:95-101）：进程启动时一次，插件重新加载时也一次（按源码，未实测）。运行中途才过期的文件要等下一次激活才会回收（按 README，未实测）；
  • 默认根目录在插件构造时创建，每个进程一个，从没 spill 过也会建，进程退出后留在原地，见下面的第 12 步；
  • 日志里存的是宿主机上的绝对路径（第 1 步），把会话日志拷到另一台机器，路径就会失效。

第 12 步把 TMPDIR 指到 <tmp>/tmpbase，先后起 4 个进程，都不配 root：

12. default roots across processes (TMPDIR pointed at <tmp>/tmpbase)
  process 1, no spill: created <tmpbase>/dsh-spill-XXXXXX, still there after exit: true, entries: 0
  process 2: root 1 held one 31-day-old file -> root 1 exists: false; process 2 root exists: true
  process 3: root 2 holds a fresh file -> root 2 exists: true; root 3 (empty) exists after exit: true
  process 4: root 3 exists: false; default roots left: 2 (root 2: true, process 4's own: true)

后三行是每次激活时的清理：只放了过期文件的根目录 1 被删掉，放了新文件的根目录 2 保留，进程 3 留下的空根目录在进程 4 启动时被删。

附件按内容寻址、读取时校验，spill 文件改了也照读

同样是“大内容放在日志外面，日志里只记引用”，用户附加的文件和图片由 dsh-attachment-local 保存，策略几乎完全相反：

5. a spill file has no digest; an attachment does
  edited spill file, read -> ok: "1: demo-0001 order-api 1.0.0 failed  canary=ok duration=40s"
  attachment: sha256:54fc11ccf3a2… 122889 bytes, saved twice -> same id: true
  stored under dsh-home/attachments/v1/files/…
  edited attachment, readFileStream -> ATTACHMENT_CORRUPT: Stored file attachment failed integrity verification.
    bytes handed to the caller before the error: 122889
    stop after the first chunk (65536 bytes): no error

先看第 1 行：脚本改了子会话 spill 文件的第一行，把 success 改成 failed，read 照常返回改过的内容，没有任何报错。spill 文件没有记录摘要，读取时也不校验。

再把同样的 122889 字节作为附件存两次，得到同一个 attachmentId：id 就是内容的 sha256（packages/attachment/attachment-local/src/file-store.ts:95-97），相同内容只存一份。

代码里没有自动删除已存对象的逻辑（按源码，未实测），README 概述写明存储对象“永远不会被自动删除”。

存储位置是 <DSH_HOME>/attachments/v1，不在临时目录；对象写好后权限改成只读 0o400（packages/attachment/attachment-local/src/index.ts:176；packages/attachment/attachment-local/src/store.ts:291）。

脚本改了存储的文件内容，readFileStream() 边读边把数据交给调用方，读完再按字节数和 sha256 校验（attachment-local/src/file-store.ts:178-180），不符就以 ATTACHMENT_CORRUPT 失败。

只要把流读完，篡改一定会被报出来。看最后两行：报错前调用方已经收到了全部 122889 字节；只读第一块 65536 字节就停下，没有任何报错。

用户交给会话的附件要一直可读，被改过要能发现。spill 把工具输出的溢出部分当作可以过期的缓存，可它替换掉的是日志里唯一的那份记录，文件过期后，这段工具输出就找不回来了。

这对 Agent 意味着什么

预览只保留头尾，接缝处没有标记，中间的内容模型要主动 read 才看得到，所以工具输出最好把汇总行、错误计数放在开头或结尾，别指望模型去读中间。spill 在剪枝之前就生效。

实测中完整结果只在 spill 文件里，文件改到 31 天前、重建 Context 后被删除，日志里没有备份，继承的路径读出 FS_NOT_FOUND。需要审计或复盘的输出，得在 spill 之外另存一份。

在基础组合的 dsh-fs-sandbox（workspace-write）下，模型用 write 就改掉了临时目录里的 spill 文件，读的时候又不校验，所以 spill 文件只能当缓存，不能当证据。

spill 上限和剪枝器的单位不同：预览加通知按 UTF-8 字节计，停在 49999 字节；剪枝器按字符计（第 10 步）。两者比较时要换算。

本文的验证范围

实测脚本 spill-demo.ts 挂载真实的 dsh-agent-loop、JSONL 持久化、dsh-fs-local 和 dsh-tool-fs，及 maxInlineBytes: 50000 的 dsh-spill-policy 和默认清理期的 dsh-spill-local（根目录改到临时目录便于观察），用脚本化模型。

第 5 步额外挂载 dsh-attachment-local，dshHome 配置指向临时目录。发布日志是合成数据。

和基础组合的差异：除第 8 步换成 dsh-fs-sandbox 和 workspace-write 的 dsh-sandbox-policy 外，ctx.fs 用的是 dsh-fs-local，spill 目录在工作目录内。“31 天”是改文件修改时间模拟的，“重启”是在同一进程里销毁并重建 Context。

第 6 步挂 dsh-session-query-sqlite，第 10 步单独挂默认配置的剪枝器，第 12 步以子进程运行、只挂 dsh-spill-local。

主要结论都有断言：

  • 模型看到的结果不超过 50000 字节，spill 文件与工具输出完全相同；
  • 三条失败记录都在 spill 文件里、不在预览里，通知里的省略字节数等于全文减预览；
  • 接缝处恰好有一行残缺记录；会话日志里没有 demo-1001、有 spill 路径；
  • read 按路径读回的中段含三条失败记录；
  • 父、子会话的 spill 目录名分别是各自会话 id 的哈希，子会话日志原样带着父会话的路径；
  • 改到 31 天前的文件在重建 Context 后被删除、子会话的文件还在，再读继承的路径得到 FS_NOT_FOUND；
  • 改过的 spill 文件照常读出；同一内容存两次附件得到同一个 id，改过的附件读取时以 ATTACHMENT_CORRUPT 失败；
  • 预览 49786 字节、通知 211 字节，二者以空行相接；接缝在第 410 行，下一行是 demo-1600；日志里的路径是绝对路径；
  • 改过的附件报错前已交出全部字节，只读第一块就停下不报错；
  • 中间独有的 demo-1500 搜不到，demo-1001 只命中 read 读回的两条 tool/result；
  • read 读回超过 50000 字节时不产生 spill 通知和新文件；
  • dsh-fs-sandbox 下读、写 spill 文件都成功；
  • 上限 100 字节时模型拿到完整结果，spill 文件照样写出；
  • 默认剪枝器剪完后以完整通知结尾；
  • 根目录里的会话目录链接把 spill 写到链接目标；
  • 4 个进程的默认根目录互不相同，过期文件所在和空的旧根目录被删，含新文件的保留。

行为与文中不符时脚本以非零退出码结束。连续 5 次运行，输出都一致。

完整代码：GitHub 示例仓库，固定到提交 ad4082d。

前提是 dsh 仓库已 pnpm install 并完成构建（各包导出指向构建后的 lib/）。还须在默认 /tmp 或仅本人可写的 TMPDIR 下运行，否则第 4 步的清理会被跳过、断言失败。

跳过条件是：POSIX 上，根目录能被其他本地用户改写，或它的祖先目录能被其他用户写且没有粘滞位时，整个根目录会被跳过（spill-local/src/index.ts:43-44，spill-local/src/cleanup.ts:46-91）。

mkdir -p scratch-plugin
