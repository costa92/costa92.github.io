第 31 / 36 节 · 扩展与外部接入

从脚本里让值班 agent 部署 payment-api 2.4，审批没人应答，工具被拒，部署账本 0 行，headless 退出码 0。

第 24 篇留下一个问题：规则启用走 dsh 的审批服务，应答者是同进程里的 approval/request 监听器；跨进程的审批客户端能否按 callId 取到会话日志里的参数，当时没有实测。前面各篇的 demo 大多在同一进程里调 agent，实际的自动化却多半在进程外：CI 步骤跑一条命令，调度器定时发任务，另一个服务把 agent 当子进程用。

这次从脚本里驱动发布值班 agent，走 dsh 的两条路：dsh --profile headless 一次跑一个任务就退出，SDK 则常驻一个 dsh --profile sdk 子进程、在 stdio 上跑 JSON-RPC。先看一次性任务的输出和退出码，再看部署需要审批时，审批请求能不能到达进程外的客户端、客户端能不能回答。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 部署审批没人应答，工具被拒，headless 仍退出 0；
  • SDK 收到 approval/asked，仍得到 unavailable；
  • 模型出错时 run() 照常返回，finalResponse 为空串；
  • 新 SDK 进程不能沿用同一个会话，headless 能接上。

模型和工具用 --patch 挂进子进程

前面的 demo 直接 ctx.plugin()。这次 agent 跑在 dsh 子进程里，模型、工具和审批门要从命令行挂进去。

dsh 启动器接受任意个 --patch 文件，叠加在 profile 的组合之上（apps/cli/src/profile-boot.ts:186-213）。补丁里 insert 的插件名以 ./ 或 ../ 开头时，按补丁文件所在目录解析（packages/boot/app-boot/src/index.ts:319-330）：

# duty.cordis.patch.yml
- id: agent-default-model
  config:
    provider: scripted
    model: mock

- insert:
    - id: duty-demo
      name: './duty-plugin.ts'

duty-plugin.ts 注册一个脚本化模型 scripted，以及 read_releases、deploy_release 两个工具。部署执行时，子进程往工作目录的 deploys.jsonl 追加一行，父进程事后读这个账本。

另有一个 tools/pre-execute 监听器，让每次部署都返回 ask，和第 24 篇的写法相同：

ctx.on('tools/pre-execute', async (exec, next) => {
  if (exec.name !== 'deploy_release') return next()
  const args = exec.arguments as { service: string; version: string }
  return { kind: 'ask', reason: `部署 ${args.service} ${args.version} 需要值班人确认` }
})

headless 用 agent-default-model 的选择建 agent（packages/bundle/headless/src/index.ts:332-333）。SDK 的 provider 和 model 由客户端在 initialize 时传入（demo 传的是 scripted/mock）。

provider 没有已注册的适配器时，SDK 服务器直接报错（packages/sdk/server/src/server.ts:150-153）。demo 传一个没注册的 nope，run() 抛出 no adapter registered for provider "nope"（第 4 步输出）。

只有 deepseek-official 例外，会自动挂官方适配器（按源码，未实测）。

demo 从源码启动 dsh，即 node --import tsx/esm apps/cli/src/bin.ts。SDK 那边另叠一层 sdk-source.cordis.patch.yml，由脚本自己叠上。

headless 的退出码只看最后一轮

dsh --profile headless "<任务>" 建一个 agent，把任务作为用户消息提交，等 agent 空闲后从会话日志里取最后一条助手文字写到 stdout。模型的推理过程流式写到 stderr。

跑一次查询，让模型故障一次，再让最后一步只回空文字：

== 1. headless：一次性任务的输出与退出码 ==
查询 payment-api → 退出码 0
  stdout | 已完成：payment-api 最近一次发布 2.2，状态 succeeded
  stderr | dsh: reasoning:
  stderr | 按剧本回答
模型故障 → 退出码 1
  stdout | （空行）
  stderr | dsh: UNKNOWN: scripted provider is down
最后一步只回空文字 → 退出码 0
  stdout | 先查一下发布记录
  stderr | dsh: reasoning:
  stderr | 按剧本回答

最后一轮的 turn/end 原因是 completed 时退出码为 0，其他情况为 1；原因是 error 时，stderr 多一行 dsh: <code>: <message>（headless/src/index.ts:360-380），模型故障那次的 stderr 就是这一行。

模型出错时 stdout 仍有一个空行，脚本判断成败要看退出码，不能只看 stdout 是否为空。默认模式下推理进 stderr，把 stderr 收进 CI 日志时，模型的推理文字也会一起留下。

第三次运行的最后一步只回了空文字，stdout 却是前一步工具调用前的那句“先查一下发布记录”：headless 跳过空文字往前找（headless/src/index.ts:88-94）。SDK 在同样情况下给空串，见第 4 步。

部署被拒，退出码还是 0

headless 叠加在基础组合（base bundle）dsh-base 之上，其中有审批服务 dsh-user-approval，默认策略是 ask（packages/bundle/base/cordis.patch.yml:231-234）。

ask 把请求交给已挂载的应答者，一个都没有时结果是 unavailable（packages/interaction/user-approval/src/index.ts:273-285）。Web 界面的应答者由浏览器端提供，headless 里没有。

工具流水线把 unavailable 变成一次拒绝，理由是固定文字（packages/core/tools/src/index.ts:1732-1735）：

== 2. headless 部署：审批没人应答 ==
部署 payment-api 2.4 → 退出码 0
  stdout | 没有执行：Error: tool "deploy_release" requires approval, but no approval channel is available
  stderr | dsh: reasoning:
  stderr | 按剧本回答
部署账本：0 行
--json → 退出码 0，12 个事件：session status status tool_call tool_result status status thinking text status status final
  tool_result | {"type":"tool_result","callId":"call-1","status":"error","result":"Error: tool \"deploy_release\" requires approval, but no approval channel is available"}
  turn_end    | {"kind":"completed"}

对照“退出码 0”和“部署账本：0 行”两行：部署没执行，退出码仍是 0。工具被拒只是一次失败的工具结果，模型拿到结果后回了一句话，这一轮正常结束。退出码只反映这一轮有没有正常结束，不反映任务有没有做成。

stdout 里能看到报错原文，是因为脚本化模型把工具结果照念了一遍；真实模型的措辞不可依赖，不要 grep stdout 判断成败。

--json 把这次运行投影成按行 JSON 事件，但投影只处理轮次、步骤、助手消息和工具调用几类事件（packages/bundle/headless/src/json-stream.ts:259-313）。审批的问与答写进了会话日志，事件流里没有。

只看 --json 的话，只能从 tool_result 的 status: "error" 和结果文字推断部署被拒；要看审批本身，得去读 DSH_HOME 下这个会话的日志。

改成 never 自动拒绝，理由却写成“用户拒绝”

无人值守时，更合适的写法是让审批直接拒绝，别等一个不存在的应答者。审批服务的 never 策略就是做这个的（user-approval/src/index.ts:268）。

基础组合里切到 never 的现成开关是 DSH_PERMISSION_MODE=danger-full-access，但这个环境变量同时把沙箱切到完全放开（base/cordis.patch.yml:218,234），本节最后一段输出会看到。

只改审批行的 policy，拒绝能生效，但权限预设服务发现“沙箱 workspace-write、审批 never”对不上任何预设。

权限预设服务因此报 composed sandbox and approval defaults match no preset，这一行插件没有激活，stderr 多出一条警告（packages/interaction/permission-presets/src/index.ts:217-221）。

demo 的 ci.cordis.patch.yml 在权限预设表里加一个 ci 权限预设并设为默认。按 id 打的补丁会整体替换这一行的 config，不做合并（vendor/include/src/index.ts:120-123），所以基础组合原有的三个权限预设也要照抄一遍，否则它们就从预设表里消失了：

- id: permission
  config:
    presets:
      read-only:
        sandbox: read-only
        approval: ask
      workspace-write:
        sandbox: workspace-write
        approval: ask
      danger-full-access:
        sandbox: danger-full-access
        approval: never
      ci:
        sandbox: workspace-write
        approval: never
    defaultPreset: ci

叠加这个补丁后再部署一次（第 2 步输出接下来的一段）：

叠加 ci.cordis.patch.yml 后部署 → 退出码 0
  stdout | 没有执行：Error: the user rejected tool "deploy_release"
  stderr | dsh: reasoning:
  stderr | 按剧本回答
  会话日志 | permission/preset=ci sandbox/mode=workspace-write approval/policy=never；审批 asked → decided:rejected

部署被拒的理由变成 the user rejected tool "deploy_release"（core/tools/src/index.ts:1724-1727），可这次没有人被问过。

最后一行是 demo 从 DSH_HOME 读出的这个会话日志：日志里照样有一对 approval/asked 和 approval/decided: rejected（user-approval/src/index.ts:218-226），看起来和有人审过一样。退出码依旧是 0。

权限预设服务在新会话的日志里写下预设、沙箱和审批策略，就是上面那行的前三项（permission-presets/src/index.ts:432-447）。审批服务先读会话自己的 approval/policy，读不到才用配置（user-approval/src/index.ts:236-238），所以 ci 补丁只管新会话。

第 2 步接着用 --session-id 跨补丁接会话：

叠加 ci 补丁接上不带补丁时建的会话 → 退出码 0
  stdout | 没有执行：Error: tool "deploy_release" requires approval, but no approval channel is available
  stderr | dsh: reasoning:
  stderr | 按剧本回答
不带补丁接上 ci 下建的会话 → 退出码 0
  stdout | 没有执行：Error: the user rejected tool "deploy_release"
  stderr | dsh: reasoning:
  stderr | 按剧本回答

叠着 ci 补丁接上第一次部署时建的会话，得到的仍是 unavailable；不带补丁接上 ci 下建的会话，仍是自动拒绝。审批策略跟着会话走，不跟着这次启动的补丁走。

最后换成 DSH_PERMISSION_MODE=danger-full-access 部署一次：

DSH_PERMISSION_MODE=danger-full-access 下部署 → 退出码 0
  stdout | 没有执行：Error: the user rejected tool "deploy_release"
  stderr | dsh: reasoning:
  stderr | 按剧本回答
  会话日志 | permission/preset=danger-full-access sandbox/mode=danger-full-access approval/policy=never；审批 asked → decided:rejected

拒绝原文和 ci 一样。“会话日志”那行里，沙箱记成了 danger-full-access，审批放开的同时沙箱也放开了。

--session-id 能接上对话，换个工作目录就接不上

每次 headless 调用默认新建一个 session-<uuid> 会话，--json 的第一个事件报告这个 id，下一次调用带 --session-id 就接着这段对话：

== 3. --session-id：下一个进程接着这段对话 ==
上一节 --json 报告的会话：session-<uuid>
同一目录 --session-id → 退出码 0
  stdout | 收到：你好（这是本会话第 2 条用户消息）
  stderr | dsh: reasoning:
  stderr | 按剧本回答
不存在的 id → 退出码 1
  stdout | （空行）
  stderr | dsh: session "session-nope" does not exist; omit --session-id to start a new Session
换一个工作目录 → 退出码 1
  stdout | （空行）
  stderr | dsh: session "session-<uuid>" was recorded in "<work>", not "<other>"

“第 2 条用户消息”是脚本化模型数出来的：它看到了上一个进程里的那条部署请求。

接续前，runner 会查会话日志，会话不存在、记录的工作目录和当前不同都拒绝。会话没有记录工作目录、是子 agent 或 fork 出来的、运行在某个 agent preset 下，同样拒绝（按源码，未实测；headless/src/index.ts:211-230,245-293）。

工作目录的检查是精确的字符串比较，CI 里每次检出到不同路径时，上一次的会话就接不上。

SDK 把审批请求送到客户端，客户端却答不了

SDK 的协议只有 3 个请求：initialize、session/prompt、shutdown。另有 4 种从服务器发往客户端的通知（packages/sdk/protocol/README.zh.md 的方法表）。

服务器把运行时里每个会话的每条日志事件都作为 session.event 转发，不做过滤（sdk/server/src/server.ts:95-98），审批的 approval/asked 和 approval/decided 也在其中。

客户端 DeepSeekHarness.run() 提交一条消息，等到这条消息的入队回执，再一直收通知直到 agent 空闲（packages/sdk/client/src/api.ts:113-115,176-224）：

== 4. SDK：审批请求传到了客户端，但客户端答不了 ==
部署 payment-api 2.4
  运行中收到 approval/asked | {"toolName":"deploy_release","callId":"call-1","reason":"部署 payment-api 2.4 需要值班人确认"}
  approval/decided          | unavailable
  finalResponse             | 没有执行：Error: tool "deploy_release" requires approval, but no approval channel is available
  RunResult 的字段          | sessionId, finalResponse, events, notifications
模型故障
  run() 正常返回，finalResponse | ""
  turn/end.reason               | {"kind":"error","error":{"message":"scripted provider is down","code":"UNKNOWN"}}
最后一步只回空文字，finalResponse | ""
SDK 进程还开着 duty-1 时 headless --session-id duty-1 → 退出码 1
  stdout | （空行）
  stderr | dsh: session "duty-1" is already owned by an active write handle
provider 没有注册适配器 | JsonRpcResponseError: no adapter registered for provider "nope"
新 SDK 进程用同一个 sessionId | JsonRpcResponseError: session "duty-1" already exists
headless --session-id duty-1 → 退出码 0
  stdout | 收到：接着查（这是本会话第 3 条用户消息）
  stderr | dsh: reasoning:
  stderr | 按剧本回答

审批请求在运行中就到了客户端：approval/asked 在审批决定之前发出，带 callId 和理由（事件里另有一个 id，输出里省略了），不带工具参数。

参数在审批之前已经写进了 tool/call 事件（packages/core/agent-loop/src/tool-calls.ts:168,263-265），服务器同样会转发，按 callId 就能找到。

可协议里没有回答 approval/asked 的请求，子进程里又没有应答者，于是立即判为 unavailable。第 24 篇问的参数能按 callId 取到，审批决定却送不回子进程。

两份 README 的“已知限制”都写明，服务器发往客户端的请求只是传输层为未来审批流程预留：协议 README 说服务器从不发送，客户端 README 说协议两端都未实现。

run() 也不报告成败。模型出错时它照常返回，finalResponse 是空字符串，RunResult 里没有状态字段。

finalResponse 取的是这段区间里最后一条助手消息（sdk/client/src/api.ts:300-310），要知道这一轮是否出错，得自己在 events 里找最后一个 turn/end 的 reason。

最后一条助手消息没有文字时，finalResponse 也是空串：输出里“最后一步只回空文字”那次就是 ""，同样的任务 headless 输出的是前一步的文字。

SDK 服务器收到本进程里没见过的 sessionId 时总是新建 agent（sdk/server/src/server.ts:259-288），所以新 SDK 进程不能沿用同一个会话。

新建时会话日志已在磁盘上，持久化层拒绝重复创建（packages/session/session-persistence-jsonl/src/index.ts:317-319）。同一个 duty-1，headless 用 --session-id 能接上，模型看到了 SDK 进程里的两条用户消息。

前提是 SDK 进程已经关掉。它还开着 duty-1 时，headless 接这个会话退出 1，报 already owned by an active write handle：会话目录有一把跨进程的写锁，由持有会话的进程占着（session-persistence-jsonl/src/index.ts:864-874）。

应答者挂在子进程里，决定来自外面

审批的应答者只能是同进程的 approval/request 监听器。要让进程外的客户端做决定，就在子进程里挂一个应答者，由它把问题转出去、把答案带回来。demo 用共享目录做中转：应答者等 <sessionId>.<callId>.answer 文件，读完即删，超时就当审批通道不可用：

ctx.on('approval/request', async (request, next) => {
  if (request.callId === undefined) return next()
  const file = join(config.dir, `${request.agent.session.id}.${request.callId}.answer`)
  for (let waited = 0; waited < (config.timeoutMs ?? 5000); waited += 20) {
    if (request.signal?.aborted === true) return 'cancelled'
    if (existsSync(file)) {
      const answer = readFileSync(file, 'utf8').trim()
      rmSync(file)
      return answer === 'allow' ? 'allowed-once' : 'rejected'
    }
    await sleep(20)
  }
  rmSync(file, { force: true })
  return 'unavailable'
})

父进程在 onNotification 里从 tool/call 事件记下每个工具调用的参数，键是会话 id 加 callId，原因见下。

收到 approval/asked 时，父进程按同一个键找到参数，交给值班人的规则决定。

规则是：2.3 在黑名单里，拒绝；2.5 不回答，模拟人不在；其他批准。脚本把应答者的超时设成 1 秒：

== 5. 审批桥：子进程里挂应答者，答案由客户端写文件 ==
  approval/asked call-1 | 参数 {"service":"payment-api","version":"2.4"} → allow
部署 2.4：allowed-once | 已完成：payment-api 2.4 已部署
  approval/asked call-2 | 参数 {"service":"payment-api","version":"2.3"} → reject
部署 2.3：rejected | 没有执行：Error: the user rejected tool "deploy_release"
  approval/asked call-3 | 参数 {"service":"payment-api","version":"2.5"} → 不回答
部署 2.5：unavailable | 没有执行：Error: tool "deploy_release" requires approval, but no approval channel is available
部署账本：{"service":"payment-api","version":"2.4"}

三种结果都按预期出现在会话事件的 approval/decided 里，账本里只有 2.4。

  • 文件名带上 sessionId。callId 由模型给出，不保证跨会话唯一，同一会话里也可能重复：本文的脚本化模型按进程编号，换进程接上会话后又从 call-1 开始。
  • 答案读完就删。应答者拿不到 approval/asked 的 id（监听器收到的只有 agent、工具名、callId、理由和 signal），只能按会话和 callId 找文件；旧答案留在目录里，就会被下一次同名调用读到，变成没问就批准。demo 读完即删、超时返回前再清一次，但超时之后才写进来的答案还是会留下，见第 6 步。
  • 超时是必须的。应答者不返回，这次工具调用就一直挂着。demo 超时后返回 unavailable，模型看到的是“没有审批通道”。
  • 谁能写这个目录，谁就能批准部署。demo 用 mkdtemp 建目录，答案先写临时文件再改名（按 demo 代码，未实测）。

第 6 步先把超时设成 10 分钟、不回答；再用 1 秒超时让 duty-4 的部署落空，之后才写答案：

== 6. 应答者的超时：不设超时整轮挂住，超时后才到的答案留给下一次 ==
不设超时，没人回答：3 秒后 run() still pending，已收到的事件 approval/asked
超时 1 秒，没人回答：unavailable
超时后才写的答案留在目录里：duty-4.call-1.answer
新 headless 进程接上 duty-4 再部署 2.6（没人被问） → 退出码 0
  stdout | 已完成：payment-api 2.6 已部署
  stderr | dsh: reasoning:
  stderr | 按剧本回答
部署账本：{"service":"payment-api","version":"2.4"} {"service":"payment-api","version":"2.6"}

看第一行：3 秒后 run() 还没返回，只收到 approval/asked，没有 approval/decided，也没有 turn/end，整轮停在审批上。

后半段是过期答案：答案写在超时之后，没人再读，留在目录里。新的 headless 进程接上 duty-4 再部署 2.6，脚本化模型从 call-1 重新编号，应答者读到这份旧答案，部署在没人被问的情况下执行，账本多了 2.6。

ACP profile 自带把审批交给客户端的桥

dsh 的 ACP profile 自带一座审批桥：它的 approval/request 监听器把请求转成 ACP 的 session/request_permission 发给客户端。

桥按客户端的选项返回 allowed-once、rejected 或 cancelled（packages/acp/acp/src/index.ts:155-173）。

第 7 步用 dsh --profile acp 起子进程，叠上 duty 补丁和把 ACP 默认模型换成 scripted 的 acp.cordis.patch.yml，脚本手写换行分隔的 JSON-RPC 客户端。2.4 过 1.5 秒才批准，2.3 拒绝，2.5 不回答、改发 session/cancel：

== 7. ACP profile：审批转成 session/request_permission ==
  session/request_permission | toolCallId call-1，选项 allow-once / reject-once
部署 2.4，1.5 秒后选 allow-once → stopReason end_turn
部署 2.3，选 reject-once → stopReason end_turn
部署 2.5，不回答、发 session/cancel → stopReason cancelled
关闭 stdin 后子进程退出码 0，会话日志里的 approval/decided：allowed-once, rejected, cancelled
部署账本：{"service":"payment-api","version":"2.4"} {"service":"payment-api","version":"2.6"} {"service":"payment-api","version":"2.4"}

看第一行：请求带着 toolCallId，选项只有一次性的批准和拒绝。客户端过 1.5 秒才回答，桥照样等着，它本身不设超时。

2.5 那次没人回答，客户端取消这一轮，stopReason 是 cancelled，日志里的决定也是 cancelled：审批服务收到 signal 中止就返回（user-approval/src/index.ts:286-299）。账本最后一行是这次批准的 2.4。

图：部署停在审批上，approval/asked 写进日志并转给 SDK 客户端，由同进程的应答者或审批桥决定。

这对 Agent 意味着什么

部署被拒、工具报错时，只要模型正常回一句话收尾，headless 就退出 0。CI 要判断部署是否真的发生，得看工具结果或外部账本。

没有应答者时的 unavailable 只是兜底，无人值守要显式拒绝审批：像 ci.cordis.patch.yml 那样另配一个审批为 never 的权限预设并设为默认。它只管新会话，拒绝写作“用户拒绝”，别当成有人审过。

SDK 客户端能看到审批请求，协议里却没有回答审批的方法。需要进程外审批时，应答者得挂在子进程里，由它向外取答案；应答者必须带超时，超时后到的答案要作废，否则会变成没问就批准。ACP profile 自带这座桥，客户端可以直接批准、拒绝或取消。

run() 的成败要自己判断：RunResult 没有状态字段，模型出错时 finalResponse 为空、调用不抛错，要查最后一个 turn/end。

跨进程接续会话走 headless。SDK 每个新进程都要新 sessionId；headless 的 --session-id 能接上两者留下的会话，至少要共用 DSH_HOME、工作目录字符串完全一致，CI 每次检出到不同路径时就接不上。

本文的验证范围

实测部分是 headless-sdk-demo.ts 和挂进子进程的两个插件。父进程用 spawnSync 起真实的 dsh --profile headless 进程，用 @deepseek-ai/dsh-sdk-client 的 DeepSeekHarness 起真实的 dsh --profile sdk 子进程。

两者都从源码启动，组合的是 dsh-base（SDK 从源码启动时按 sdk-source 补丁关掉 typert-loader）。第 7 步另起一个 dsh --profile acp 子进程，由脚本手写的 JSON-RPC 客户端驱动。

模型换成脚本化模型，发布平台是合成的，审批桥用共享目录中转。所有子进程共用脚本创建的一个临时 DSH_HOME 和一个工作目录（换目录那次用另一个临时目录），跨进程接续会话靠的就是共用 DSH_HOME；脚本退出时删除。“只改 policy 时权限预设不激活”那一处是手动跑过一次，没有写进 demo。

主要结论都有断言：

  • headless 的 stdout、stderr 原文和退出码，模型出错时 stdout 为一个空行，最后一步只回空文字时 stdout 是前一步的文字；
  • 部署被拒时退出码 0、账本为空，--json 没有审批事件、tool_result 为 error、turn_end 为 completed；ci 权限预设下的拒绝原文、会话日志里的预设三项和 asked → decided:rejected；
  • 跨补丁接会话时审批跟着会话走的两种结果；danger-full-access 下的拒绝原文和日志里的沙箱 danger-full-access；
  • --session-id 接上时模型看到第 2 条用户消息，不存在的 id 和换目录都退出 1；
  • SDK 运行中收到的 approval/asked 内容、approval/decided 为 unavailable、finalResponse 原文；模型出错和最后一步只回空文字时 run() 都返回空字符串，前者 turn/end 为 error；
  • SDK 进程持有 duty-1 时 headless 接它退出 1；未注册 provider 的报错原文；新 SDK 进程报 session "duty-1" already exists；headless 接上 duty-1 后模型看到第 3 条用户消息；
  • 审批桥三种结果依次为 allowed-once、rejected、unavailable，不回答的那次至少等了 1 秒，账本只有 2.4，答案目录最后为空；
  • 不设超时时 3 秒后 run() 未返回、只收到 approval/asked；过期答案让新进程的部署在没人被问时执行，账本多了 2.6；
  • ACP 的三次部署：1.5 秒后批准为 end_turn，日志里的决定依次为 allowed-once、rejected、cancelled，子进程退出 0，账本多了一条 2.4。

另外做了变异检查。以下 6 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • 部署不再返回 ask；
  • ci 权限预设的审批改回 ask；
  • 审批桥超时改为返回 rejected；
  • 脚本化模型不再抛错，改为回一句空话；
  • 父进程写答案文件时去掉 sessionId；
  • 审批桥读完答案不再删除文件。

连续 5 次运行，以及 4 个进程并发运行，输出都一致。本机实测一次运行约 27 秒，大部分时间花在启动 dsh 子进程和定时等待上。
