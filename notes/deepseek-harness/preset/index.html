第 18 / 36 节 · Agent 编排

直接用值班 preset 建的会话只有 2 个工具；空会话切换到同一个 preset 后有 4 个，宿主的 host_shell、host_fetch 都在，加入时设的白名单没生效。

第 16 篇看完了 agent 循环：循环不带人设也不带工具，模型看到什么全看挂载的插件。第 8 篇讲工具注册表时说过，一个“发布值班”preset 就是一组作用域注册加一组 restrict，而 restrict 落在哪一层作用域，决定了它能不能当白名单。本篇把它做出来，看区别落在哪里。

这次写一个 release-oncall preset，带自己的人设、两个值班工具和一份 runbook，和一个通用 preset 同时跑在一个进程里；再试几种把宿主工具挡在外面的写法，看每种落在哪个作用域；最后改 preset 目录里的文件，看新旧会话各拿到哪个版本。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 两个 preset 同跑一个进程，工具和人设各会话独立；
  • preset 行在常驻作用域 restrict，只能拉黑名单；
  • 切换进来的会话，agent/created 里下的白名单没生效；
  • 只改 runbook、不碰组装文件，新会话仍读到旧版本。

preset 是一个目录，挂载一次，多个会话共用

本篇涉及 packages/preset 下的 agent-presets 和 persona 两个包。一个 preset 就是一个目录，目录名是 id，里面必须有一份 agent.cordis.yml，可选一份 preset.yml 放显示名和描述。

agent.cordis.yml 的格式就是第 7 篇讲的插件树：一行一个插件。案例的值班 preset 长这样（<demo> 是示例目录）：

- id: persona
  name: '@deepseek-ai/dsh-persona'
  config:
    prefix: 你是发布值班助手，只查发布记录和执行回滚，不改代码。
- id: oncall
  name: <demo>/oncall-rows.ts
  config:
    tools: [lookup_release, rollback_release]
    runbook: <presets>/release-oncall/runbook.md

oncall-rows.ts 是案例自己写的插件行：按 tools 注册工具，启用时读一次 runbook 文件注册成一段提示词，另有两个可选字段 restrict 和 allowOnJoin，后文“宿主工具的 restrict 写在常驻作用域只能拉黑名单”一节再用。

新建会话从 preset 组装的入口是 AgentPresets.mount(agentCtx, id)（packages/preset/agent-presets/src/index.ts:443-456）；子 agent 走 composeFrom()，空会话换 preset 走 select()。

mount 的注释要求在 agent 工厂的 setup 钩子里调用，因为此时 agent 还没发布，组装失败会让整个创建回滚。案例的宿主就是这么建会话的：

const { agent } = await ctx.agents.create({
  sessionId: SessionId(id),
  agentOptions: { provider: 'mock', model: 'mock' },
  setup: async (agentCtx: Context) => {
    await ctx.agentPresets.mount(agentCtx, presetId)
    if (agentMask !== undefined) agentCtx.tools.restrict(agentMask)
  },
})

mount 先由 ensureStanding()（:776-824）保证这个 preset 在进程里有一份常驻挂载：以 { agentPreset: id } 为 key 建一个作用域，把 agent.cordis.yml 的所有行挂进去。

再用 bindScopeParent 把这个常驻作用域设成 agent 作用域的父作用域。工具、提示词段落这些按作用域分层的注册表沿父链往上查，agent 就看到了 preset 的注册。

同一个 preset 只挂一次，后来的会话只是认父。ensureStanding 按 id 缓存一个 promise（:410-420），两个会话同时第一次用同一个 preset 也只挂一份，下文第 2 步会验证。

坏的 preset 带着原因列在名单里

案例的根目录里放了三个 preset，其中 deploy-bot 引用了一个不存在的包：

== 1. 名单：坏的 preset 带着原因列出来 ==
release-oncall  发布值班  ok
deploy-bot      -  broken: row "deploy" names a plugin that cannot be resolved: @deepseek-ai/dsh-tool-deploy
general         -  ok
开 deploy-bot 会话 -> agent-preset/invalid，没有留下半个会话
不关 includeShippedRoot 时，名单前面多出 4 个随附 preset：standard, ptc, minimal, cordis

前三行是名单：每次 list() 都重新扫描根目录，不缓存。坏的 preset 也不跳过，带着原因留在名单里。

健康检查只看文件：YAML 能否解析、是不是插件行列表、行里的包能否找到。找包时，挂了 pluginPackages 服务就问它（:266-273），没挂就沿 harness 基址往上找 node_modules 里的目录（packages/preset/agent-presets/src/discovery.ts:112，案例走这条）。

健康检查不 import 任何插件，所以包在、但 apply 时抛错的插件，到首个会话挂载时才暴露（按源码，未实测）。

用坏 preset 开会话时，resolveMountable()（agent-presets/src/index.ts:397-407）在挂载前就拒绝，错误码 agent-preset/invalid，脚本断言 agent 注册表的会话数未变。

最后一行说的是名单的根目录顺序（:181-185）：随包交付的根在最前，配置的根居中，$DSH_HOME/.agent-presets 在最后，同名时靠前的赢（按源码，未实测）。

includeShippedRoot 和 includeUserRoot 默认都是 true。只配了自己的根目录时，standard、cordis 等随附 preset 仍能按 id 选到，它们带着 bash、文件读写和子 agent 工具；要只用自己的 preset，这两个开关都得显式关掉（按源码，未实测）。

两个会话各有工具和人设

s1 用值班 preset，s2 不指定，走插件配置 default 指定的 general：

== 2. 同一进程里的两个会话 ==
s1 release-oncall 工具：host_shell, lookup_release, rollback_release
s2 general        工具：host_shell, read_notes
全局视图          工具：host_shell
s1 系统提示：
  deployment:persona-prefix「你是发布值班助手，只查发布记录和执行回滚，不改代码。」
  oncall:runbook「回滚前先确认上一个成功版本。」
s2 系统提示：
  deployment:persona-prefix「你是通用编码助手。」
s3 也选 release-oncall：常驻挂载仍是 1 份
r1、r2 同时首次选 oncall-race：常驻挂载 1 份
dsh-persona 挂到全局层 -> prompt section "deployment:persona-prefix" is already registered (for a per-agent override, register through that agent's `agent.ctx` instead)

两个会话的工具和提示词互不相干。人设的替换靠同名遮蔽：宿主的 dsh-system-prompt 在全局层注册了名为 deployment:persona-prefix 的段落，案例配成“你是通用编码助手。”

dsh-persona 行在 preset 的作用域里注册同名段落，组装时作用域里的同名段落优先（packages/core/system-prompt/src/index.ts:576）。dsh-persona 只能挂在作用域里。输出最后一行是另起一个宿主把它挂到全局层：和宿主那条注册撞名，直接抛错。

倒数第 2 行是 r1、r2 用 Promise.all 同时首次选一个新 preset，常驻挂载仍只有 1 份。

每个会话的工具列表里都有 host_shell。它是案例的宿主在全局层注册的工具，不属于任何 preset。

宿主工具的 restrict 写在常驻作用域只能拉黑名单

图：会话的工具来自全局、常驻作用域、agent 三层，白名单只能落在 agent 作用域。

工具注册表对一个 agent 的视图由三部分拼成（packages/core/tools/src/index.ts:1158-1199）：全局层的工具，加上父链上各层的工具，最后是 agent 自己这一层的注册。

前两部分统称“继承来的”，要经过链上每一层（包括 agent 自己这层）restriction 的过滤；只有 agent 自己这层的注册不受过滤（:1180；:1184-1189）。

对加入 preset 的会话来说，preset 注册的工具在常驻作用域，属于“继承来的”，和宿主的全局工具归为一类，这就是第 8 篇预告的作用域区别。案例的 oncall-rows.ts 有两个相关字段：

  • restrict 在插件启用时原样传给 ctx.tools.restrict()，这个调用落在常驻作用域；
  • allowOnJoin 监听 agent/created，对新加入的 agent 调 agent.ctx.tools.restrict({ allow })，落在 agent 自己的作用域。

agent/created 按作用域投递（packages/core/scope/src/scoped-events.generated.ts:12），常驻挂载的监听器能收到加入它的 agent 的这个事件。

const { restrict, allowOnJoin } = config
if (restrict !== undefined) ctx.effect(() => ctx.tools.restrict(restrict))
if (allowOnJoin !== undefined) {
  ctx.on('agent/created', ({ agent }) => { agent.ctx.tools.restrict({ allow: allowOnJoin }) })
}

复制出几个值班 preset，各用一种写法，再加一个由宿主在 setup 里做白名单的对照：

== 3. 想把宿主工具挡在值班 preset 外面 ==
s1 调 host_shell -> host_shell ran
preset 行 restrict { deny: [host_shell] } -> lookup_release, rollback_release
  s4 调 host_shell -> Error: unknown tool "host_shell"
preset 行 restrict { allow: [] }          -> (空)，preset 自己的两个工具也没了
preset 行 restrict { allow: [lookup_release, rollback_release] } -> agent-preset/invalid：
  tools.restrict() names unknown global tools "lookup_release", "rollback_release"; known global tools: host_shell
宿主在 setup 里对 agent 作用域 allow 同样两个名字 -> lookup_release, rollback_release
preset 行监听 agent/created，对 agent 作用域 allow -> lookup_release, rollback_release
宿主后来又注册 host_fetch：
  preset 行 deny 版          -> host_fetch, lookup_release, rollback_release
  setup 里 allow 版          -> lookup_release, rollback_release
  agent/created 里 allow 版  -> lookup_release, rollback_release

首行是基线，没有 restrict 时 s1 调宿主的 host_shell，工具执行了。

  • 常驻作用域的 deny 挡住了 host_shell，挡不住后来注册的 host_fetch。 它是黑名单，只挡写进去的名字；被拒的调用返回的错误和工具不存在时一样。
  • 常驻作用域的 allow 写空会滤掉 preset 自己的工具，写上自己的工具名则挂载失败。 preset 的工具在常驻作用域里，对 agent 属于继承，写空时一并被滤掉；restrict() 要求名字是已知的全局工具（tools/src/index.ts:1094-1098）。从常驻作用域看，这两个工具是自己注册的，不在名单里。
  • agent 作用域的 allow 两种位置都正确，后来的 host_fetch 也进不来。 从 agent 看，preset 的工具是继承来的，可以写进白名单。子 agent 限制工具集用的也是 agent 作用域（packages/subagent/subagent/src/child-agent.ts:218）。

脚本还记录了脚本化模型每次收到的请求：s1 的请求带着 host_shell，deny 版的请求不带；各会话提示词组装出的工具列表也和注册表视图一致。

preset 文件本身能做白名单，但得绕到 agent 作用域上去做，在插件启用时直接调 restrict() 只能拉黑名单。agent/created 这条路还有一个缺口，“切换进来的会话，加入时设的白名单没生效”一节的切换会碰到。

**未实测：**按源码，dsh 自己靠宿主层不注册模型工具兜底：Web 组合的 patch（packages/bundle/web-app/cordis.patch.yml:377 起）把基础组合（base bundle）里 16 行 @deepseek-ai/dsh-tool-* 禁掉 15 行，剩下一行不注册工具。

切换进来的会话，加入时设的白名单没生效

再把空会话切到带 allowOnJoin 的 oncall-join，并试着切换一个已经跑过的会话：

== 4. 切换 preset ==
空会话 s8 切到 oncall-join -> host_fetch, host_shell, lookup_release, rollback_release
  直接用 oncall-join 建的 s7 只有两个工具；切换进来的没有收到 agent/created，白名单没生效
  日志记下 agent-preset/selected {"agentPreset":"oncall-join"}
s1 已经跑过一轮，再切 -> agent-preset/locked：session "s1" has already started; its agent preset is fixed
s11 在 setup 里 allow [read_notes]，切到 release-oncall -> (空)
  不撤旧的，再下 allow [lookup_release, rollback_release] -> (空)
  撤掉旧的 allow -> lookup_release, rollback_release
空会话 s12 切到 oncall-own -> agent-preset/invalid，日志里 agent-preset/selected 0 条，仍在 general

切换不再发 agent/created（recompose() 只发 tools/change）。s8 创建时加入默认 general，其 agent/created 只投给 general 的监听器；切到 oncall-join 后，该 preset 的 allowOnJoin 没见过 s8，于是它继承宿主全部工具。

宿主在 setup 里下的白名单也只在创建时执行一次。s11 在 setup 里只放行 general 的 read_notes，切到值班 preset 后一个工具都不剩：旧白名单还在，新 preset 的工具全被滤掉。

第 4 行被拒：select() 按会话排队逐个执行，每次切换前都会重新检查会话是否空白（agent-presets/src/index.ts:724-757）。

判断依据是会话投影 turnBoundary：有进行中的轮次，或已完成的轮次数大于 0，就拒绝（:743-751）。理由写在 README 里：对话中途换工具，日志里已记下的工具调用在新组装里可能没有对应的工具。

切换本身是把 agent 的父作用域改认另一个常驻挂载，成功后发一次 tools/change（:696），再往会话日志追加 agent-preset/selected（:755）。先切换、后记日志，所以挂载失败时日志里不会留下没生效的记录。

输出末行 s12 切到挂载会失败的 oncall-own，被拒后日志里没有 agent-preset/selected，会话仍在 general。

能切换 preset 的部署，白名单要能在切换后换一份。同一作用域上的多条 restriction 取交集（tools/src/index.ts:740-746）：s11 只追加新的 allow，结果仍是空；用 setup 里保存的撤销函数撤掉旧的，值班工具才回来。

只改 runbook，新会话还拿旧版本

值班会话的 runbook 是 preset 目录里的一个普通文件。先只改它，再只 touch agent.cordis.yml：

== 5. 改 preset 目录里的文件 ==
只改 runbook.md，新会话 s9 看到：回滚前先确认上一个成功版本。（常驻挂载 1 份）
再 touch agent.cordis.yml，新会话 s10 看到：回滚前先确认上一个成功版本，并在群里通知。
  s1 仍是：回滚前先确认上一个成功版本。（常驻挂载变成 2 份，旧的一份不回收）
带 dsh-skill-filesystem 的 preset，每代各建一个会话并读一次 skill 目录：
  第一代：chokidar 监听器 1 个，原生 fs.watch 句柄 1 个
  touch 后第二代：chokidar 监听器 2 个，原生 fs.watch 句柄 1 个

s9 还是旧文本，因为常驻挂载按“代际”管理。每一代记下挂载时 agent.cordis.yml 的修改时间和大小，新会话进来时重新 stat 一次，两者都没变就复用当前这一代（agent-presets/src/index.ts:785-786、:848-850）。

改了 runbook，组装文件的 stamp 没变，新会话 s9 拿到的还是旧的那一代，看到的是旧 runbook。touch 一下组装文件（脚本用 utimes 把修改时间往后拨 60 秒，避开时间精度的影响），下一个会话 s10 触发新一代挂载，插件行重新执行，读到了新 runbook。

已经加入的会话留在自己的那一代，s1 看到的一直是旧文本。旧的一代不回收，ensureStanding 里留着 TODO（:787）：没有计数，不知道最后一个会话什么时候离开。

README 的已知限制写到了代价：dsh-skill-filesystem 默认监听自己的根目录，每改一次组装文件再建会话，就多一套活着的文件监听。

最后三行是另一个 preset oncall-skills，只挂这一行。第二代挂上后，chokidar 监听器从 1 个变成 2 个，第一代的没有关；原生 fs.watch 句柄仍是 1 个，两代监听的是同一个目录，句柄数没有翻倍。

同一个限制也适用于 preset 自带的 skill 目录和其他资产（按 README，未实测）。README 写明 stamp 只看 agent.cordis.yml，旁边文件的修改要等组装文件本身变化或者进程重启，才会到新会话。

这对 Agent 意味着什么

想让值班会话只有值班工具，白名单要落在 agent 作用域，对它 restrict({ allow })，可以写在宿主的 setup 里，也可以由 preset 行在 agent/created 里做。preset 行在启用时直接调的 deny 是黑名单，只挡得住当时已知的名字，宿主以后新加的工具会直接出现在值班会话里。

允许切换 preset 时，agent/created 和 setup 里下的白名单都不会跟着切换：前者让切换进来的会话拿到宿主全部工具，后者把新 preset 的工具滤光。要保存撤销函数，切换后撤旧下新。

只配了自己的根目录，不等于名单里只有自己的 preset。不关 includeShippedRoot，名单前面就多出 standard、ptc、minimal、cordis 4 个随附 preset。

runbook 这类被插件在启用时读取的文件，改完之后新会话不会自动拿到，要碰一下 agent.cordis.yml。每触发一次新代际都会多留一份挂载，频繁修改的场景要把这个开销算进去。

本文的验证范围

实测部分是一个脚本 preset-demo.ts：挂载真实的 dsh-agent-presets、dsh-persona、dsh-tools、dsh-system-prompt、dsh-agent-loop、dsh-skill、dsh-skill-filesystem 和会话投影。

preset 目录建在临时目录里，模型是脚本化模型，会话只在内存。

dsh-persona 的包名行按 ctx.baseUrl 解析，案例把基址设在装有它的 apps/cli；dsh 启动时基址在 profile 目录，包由 pluginPackages 服务解析（按源码，未实测）。

oncall-rows.ts 是案例自己的插件行，restrict 和 allowOnJoin 都是它自己的配置项，dsh 随附的插件里没有这样的配置。案例关掉了宿主的 harness 身份段落，输出里也滤掉了空段落，只是为了让输出短一些。

数 chokidar 监听器时，脚本包了一层 chokidar.watch 计数创建与关闭；原生句柄数来自 process.getActiveResourcesInfo()。

主要结论都有断言：

  • 名单各行的健康状态，坏 preset 以 agent-preset/invalid 拒绝且会话数不变，随附 preset 的 id；
  • 两个会话的工具与提示词段落，常驻挂载份数；
  • 各种 restrict 写法的工具列表与错误，s1 调 host_shell 的结果，脚本化模型收到的请求所带的工具；
  • 提示词组装出的工具列表与注册表视图一致；
  • 并发首次选同一 preset 时的常驻挂载份数，dsh-persona 挂到全局层的报错；
  • 切换记下的 agent-preset/selected、切换后的工具列表（白名单缺口），以及已开始会话的 agent-preset/locked；
  • setup 白名单切换后的工具列表、追加与撤销后的工具列表，挂载失败的切换不写日志；
  • 改 runbook 与 touch 组装文件前后各会话读到的 runbook，以及常驻挂载份数；
  • 两代 dsh-skill-filesystem 的 chokidar 监听器数与原生监听句柄数。

行为与文中不符时脚本以非零退出码结束。连续 5 次运行，输出都一致。
