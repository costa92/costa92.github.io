第 9 / 36 节 · 能力、工具与会话

工具代码没改，ctx.fs 换成 fs-sandbox 后，模型看到的 write 参数从 2 个变成 4 个。输出 schema 加严后，上游多一个字段，整次调用失败。

第 4–7 篇读的都是 Cordis 的框架层机制，dsh 在它上面搭了八十多个服务。从这一篇起进入 dsh 自己的代码，先看一个结构问题：**这么多服务，哪些可以换、哪些不能换，换的时候谁不用动。**dsh 文档有现成的分类表，这里对照读其中两个：可以整体替换的 seam ctx.fs，不可替换的 core ctx.tools。

这次把 ctx.fs 的 provider 从 fs-local 换成 fs-sandbox，看 tool-fs 不改代码时模型看到的参数怎么变；再给 lookup_release 的输出 schema 加 additionalProperties: false，看上游多一个字段时会怎样。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 没有 ctx.fs provider 时，文件工具一个都不注册；
  • 换成 fs-sandbox 后，write 多出两个提权参数；
  • 不带 output 契约的工具，注册直接抛错；
  • 输出多一个未声明字段，调用返回 INVALID_TOOL_OUTPUT。

82 个服务只分三种角色

docs/capability-seams.zh.md 末尾有一张表，列出每个 ctx.* 服务的角色、所属包、实现包和直接消费方。角色只有三种，类型定义在生成脚本里（scripts/gen-doc-graphs.ts:34）：

mode: 'core' | 'seam' | 'bundle'

按表统计：

49 core
32 seam
 1 bundle

唯一的 bundle 是 ctx.agentLoop。seam 的定义见架构文档（docs/architecture.zh.md:135）：

一个 seam 是一项可替换能力，包含三种角色：声明接口的 Service Definition、实现它的 Service Provider，以及使用它的 Consumer（通常是面向模型的工具）。

seam 按结构划分：接口和实现分开、可以有多个实现的服务才是 seam，和服务重不重要无关。core 服务只有一份实现，由所属包自己提供。

第 5 篇把发布数据源抽成 releases 服务，让文件版和模拟平台版可以互换，就是手写了一个最小的 seam。dsh 里的 seam 是同一个套路，下面的 ctx.fs 把三种角色拆成了独立的 npm 包（文档也说明一个包可以同时承担多个角色）。

换掉 ctx.fs，模型看到的参数变了

ctx.fs 的三种角色分在五个包里：

角色包做什么
Definitiondsh-fs抽象类 FileSystem，只声明接口和事件
Providerdsh-fs-localLocalFileSystem，直接读写本机磁盘
Providerdsh-fs-sandboxSandboxedFileSystem，按沙箱模式拦截写入
Providerdsh-fs-ssh远端文件系统
Consumerdsh-tool-fs面向模型的 read / write / edit 工具

Definition 是一个抽象 Service（packages/fs/fs/src/index.ts:86），服务名在构造函数里写死：

export abstract class FileSystem extends Service {
  constructor(ctx: Context) {
    super(ctx, 'fs')
  }

两个本地 Provider 是继承关系，SandboxedFileSystem 继承 LocalFileSystem（packages/fs/fs-local/src/index.ts:66、packages/fs/fs-sandbox/src/index.ts:55），ctx.fs 取的是当前挂载的那一个。

Consumer 那边只声明依赖，不指定用哪个实现（packages/fs/tool-fs/src/index.ts）：

/** Services required by the filesystem tool suite. */
export const inject = ['tools', 'fs', 'systemPrompt']

tool-fs 的模块注释说，这个包拥有 schema、校验、读取窗口和格式化，“never a concrete provider”。

fs-sandbox 的类注释则把替换方式写成了一句话（fs-sandbox/src/index.ts:49）：代替 dsh-fs-local 加载，再配一个 ctx.sandboxPolicy，“is the whole swap”。

照着做一遍这个 swap。先只挂 tool-fs，再挂 fs-local，然后卸掉 fs-local 换成 fs-sandbox（read-only 模式），全程不碰 tool-fs（节选，省略了第 2 步的 model sees 一行）：

1. seam: tool-fs consumes ctx.fs, it never picks a provider
  without any ctx.fs provider: tools=(none)
  + fs-local: tools=edit,read,write sandboxMode=undefined
  write params: file_path,content
  write via fs-local -> isError=false
2. swap the provider, keep the consumer
  fs-local disposed: tools=(none)
  + fs-sandbox(read-only): tools=edit,read,write sandboxMode=read-only
  write params: file_path,content,sandbox_permissions,justification
  write via fs-sandbox -> isError=true code=FS_SANDBOX_DENIED

先看 tools= 几行。没有 provider 时，tool-fs 在 inject 里要的 fs 不满足，插件停在 PENDING，read / write / edit 一个都没注册，模型不会看到“调了必失败”的工具，这是第 5 篇讲的响应式依赖。

换 provider 时 consumer 跟着重启了一次：fs-local 卸载那一刻工具全部消失，fs-sandbox 挂上后又重新出现。tool-fs 的代码没改，但它被卸载又重新 apply 了一遍。

再看 write params。挂 fs-sandbox 之后，同样的代码让 write 多了 sandbox_permissions 和 justification 两个参数，由 tool-fs 的沙箱适配决定（packages/fs/tool-fs/src/sandbox.ts:44）：

const defaultMode = ctx.fs.sandboxMode
this.escalationModes = defaultMode === undefined ? [] : ESCALATION_TARGETS

sandboxMode 是 Definition 上的一个 getter，基类和 fs-local 返回 undefined，fs-sandbox 覆盖成部署的默认模式。consumer 在 apply 时读 sandboxMode，只有后端会拦截时才向模型暴露提权参数。被拒绝时，返回给模型的文本里带着提权提示。

第 2 步输出节选，模型收到的拒绝文本，demo 把它截到 160 个字符打印：

model sees: [{"type":"text","text":"Error: [sandbox: file access denied under read-only mode]\n[sandbox: escalation available — retry this exact operation once with sandbox

\n 之后的 escalation available 是提权提示。

提示说的“retry once”要经过审批。真实的 dsh-user-approval 要求处于打开的回合里（按源码，未实测），第 8 步改挂一个只会批准的审批桩，带上 sandbox_permissions: 'workspace-write' 重试同一次写入，再不带提权写一次：

8. fs-sandbox escalation: one approved wider retry
  approval asked: write: escalate sandbox to workspace-write: save the on-call note
  escalated write -> isError=false
  next write without escalation -> isError=true code=FS_SANDBOX_DENIED

approval asked 一行是审批人看到的理由，模型写的 justification 原样带在里面。批准只对这一次调用生效，下一次不带提权的写入又被拒。

seam 保证换实现不用改 consumer 的代码，但不保证对模型没影响。能力不同的后端通过 Definition 上的只读属性把差异告诉 consumer，由 consumer 决定怎么呈现给模型。

图：tool-fs 只依赖接口，换上 fs-sandbox 后自己重启一次，模型看到的 write 参数从两个变成四个。

ctx.tools 只有一条工具流水线

回到能力表，ctx.tools 那一行的角色是 core，实现包一栏是空的，说明写的是：

注册能力，负责 PTC mode 传输，并让调用依次经过策略前处理、单调守卫、环绕分派、策略后处理和最终结果观测。

实现只有一个类 ToolRuntime（packages/core/tools/src/index.ts:789），构造时把自己接到系统提示词上（:834）：

constructor(ctx: Context, config: Config = {}) {
  super(ctx, 'tools')
  ...
  ctx.systemPrompt.tools(context => this.wireSchemas(context.scope))

ctx.tools 管的是所有工具共用的那条工具流水线，包括守卫、审批路由、输出校验，以及超时这类环绕插件的挂载点，所以不做成 seam。fs 的不同实现可以对同一个接口给出不同行为；工具流水线如果有两个实现，同一个工具在不同部署里的安全语义就不一样了。

dsh 让工具流水线只有一份，扩展点做成事件（tools/pre-execute、tools/execute、tools/post-execute），要改行为就挂监听，不换实现。工具流水线留到第 9 篇，这篇只看注册和结果这两头。

注册工具时 output 契约必填

第 3 篇的插件已经声明了 output，因为不写就注册不进去，register() 一上来就检查它（tools/src/index.ts:1043）：

register(definition: ToolDefinition): () => void {
  const name = definition.name
  const output = (definition as Partial<ToolDefinition>).output
  if (output === undefined || typeof output !== 'object'
    || typeof output.render !== 'function'
    || (output.presentationMeta !== undefined && typeof output.presentationMeta !== 'function')) {
    throw new TypeError(`tool "${name}" must declare output { schema, render, presentationMeta? }`)
  }
  assertSupportedJsonSchema(output.schema)

实测：

3. core: ctx.tools refuses a tool without an output contract
  TypeError: tool "no_output" must declare output { schema, render, presentationMeta? }

注册直接抛出 TypeError。output 由两部分组成：schema 描述工具体返回的规范值（canonical value），render 把这个值投影成模型看到的内容块。类型定义里 ToolDefinition.output 的注释是 “Mandatory canonical output declaration”。

仓库自己的测试夹具也绕不开，testing.ts 专门提供了一个 defineContentToolFixture，并注明产品工具必须声明领域 DTO，不能这么偷懒。

模型只看得到三个字段

ToolDefinition 上的字段不少：timeoutMs、isConcurrencySafe、finalizeContent、presentCall、output……进模型上下文的由 schemaOf()（tools/src/index.ts:1262）决定，它按白名单只取三个字段：

private schemaOf(definition: ToolDefinition, detachParameters: boolean): ToolSchema {
  const { name, description, parameters } = definition
  ...
  return { name, description, parameters: detached }
}

给测试工具设了 timeoutMs: 5000 和完整的 output schema，schemas() 投影出来是：

4. what the model sees: schemas() keeps only name/description/parameters
  schema keys: name,description,parameters

timeoutMs 和 output schema 都不在键里。timeoutMs 的注释写明 “it is NEVER sent to the model”，isConcurrencySafe 写的是 “never model-visible”。

schemas() 只是投影，发给模型的是 agent 循环组装的请求。第 10 步挂上真实的 agent 循环和一个脚本化模型，工具额外带上 isConcurrencySafe，模型第一次回复调 lookup_release，工具执行完时再注册一个 late_tool（节选）：

10. a real agent step: what the model request carries
  request 1 tools: lookup_release; lookup_release keys: name,description,parameters
  request 2 tools: late_tool,lookup_release

看 keys:：请求里的工具仍只有三个键，timeoutMs、isConcurrencySafe 都没进请求。第二次请求多了 late_tool，说明 agent 循环每一步都重新组装一次工具列表，回合中途注册的工具下一步就可见。

原生工具调用模式下，模型看到的是 render 的输出，看不到 schema。output schema 只在 PTC 模式（模型写一段代码去调工具）下给模型：sdkSchemas()（tools/src/index.ts:1245）生成 SDK 类型声明时会带上 output。

第 11 步另起一个 mode: 'ptc' 的 ToolRuntime，挂上 PTC 运行时，注册同一个 lookup_release，再组装一次系统提示词：

11. PTC mode: the SDK declaration carries the output shape
  model tools: run_code
  system prompt SDK declares:
    interface ToolOutputMap {
      lookup_release: {
        records: ({
          id: string;
          service: string;
          version: string;
          status: "succeeded" | "failed";
        })[];
      };
    }

模型能直接调的只剩 run_code，lookup_release 的输出 schema 被译成 TypeScript 类型写进系统提示词，模型写代码时靠它知道返回值的形状。

原生工具调用模式下，模型读的是 description 和 parameters，output.schema 只有运行时用。想让模型理解返回值，要靠 render 渲染出的内容，在 schema 里写注释没用。

output schema 是出口闸门

工具体返回之后，createSuccessResult()（tools/src/index.ts:1802）依次快照成无损 JSON、按 output.schema 校验、冻结、调用 render：

const detached = snapshotToolValue(tool.name, candidate)
const violations = validateJsonSchemaValue(tool.output.schema, detached, 'value')
if (violations.length > 0) throw new ToolOutputError(tool.name, violations)
const value = deepFreeze(detached)
let rendered: ContentBlock[]
try {
  rendered = tool.output.render(exec.arguments, value)

校验在 render 之前，失败就不渲染。

用一个简化版的 lookup_release 验证：发布记录的 schema 里 additionalProperties: false，数据源先返回干净记录，再模拟上游接口某天开始多返回一个审批人邮箱 approver：

5. output schema is enforced on every successful value
  clean source -> isError=false content=[{"type":"text","text":"1 record(s)"}] value={"records":[{"id":"demo-003","service":"payment-api","version":"1.4.2","status":"failed"}]}
  leaky source -> isError=true code=INVALID_TOOL_OUTPUT
  model sees: [{"type":"text","text":"Error: tool \"lookup_release\" returned invalid output: \"value.records[0].approver\" is not a declared property (additionalProperties: false)"}]

clean source 一行里，value 是完整记录，content 只有 1 record(s)。模型拿到的是 content，value 留在执行现场，给策略层和嵌套调用用。

ToolExecutionSuccess.value 的注释是 “deliberately omitted from durable events”。第 10 步的最后一行在整份会话事件里查了一遍：

session events contain the value's "demo-003"? false; contain the rendered "1 record(s)"? true

记录 id demo-003 只在 value 里，事件里没有；render 出来的 1 record(s) 在。会话日志存的是模型看到的内容，规范值不在里面。

leaky source 一行里，多出来的字段让整次调用失败，model sees 的错误文本里有字段名 approver，没有邮箱本身。上游数据形状一变，工具就报错，没声明过的字段进不了上下文。

第 3 篇在工具体里另校验了整个数据文件（validateJsonSchemaValue(..., raw)），管的是读进来的数据（第 3 篇发布时的版本上这层校验未生效，见本文的验证范围）；registry 这道闸门管的是返回给模型的数据。工具体里的校验，作者随时可以删掉；registry 的输出校验不归工具作者管。

作用域内同名注册遮蔽全局

同一个 ToolRuntime 服务多个 agent。注册可以是全局的，也可以挂在某个 agent 的作用域上，作用域内的同名注册会遮蔽全局的那个。restrict() 则能让某个 agent 看不到某些全局工具（tools/src/index.ts:1077）。

作用域由 dsh-scope 的 createScope(ctx, key) 创建，返回的 context 继承调用方的依赖 API，须在声明 inject: ['tools'] 的插件里创建，否则读 ctx.tools 报 cannot get property "tools" without inject。

在 agent-A 的作用域里注册一个描述不同的 lookup_release，再 deny 掉 edit：

6. scope: an agent-scoped registration shadows the global one
  global view : global release lookup
  agent-A view: on-call preset: production only
  agent-A tools=lookup_release,read,write
  global  tools=edit,lookup_release,read,write
  agent-A calls edit -> isError=true code=UNKNOWN_TOOL

被 restrict 掉的工具，agent-A 调用时拿到 UNKNOWN_TOOL，和工具不存在时一样，不会暴露“这个工具有，但你没权限”。

restrict() 还有几条硬性检查（tools/src/index.ts:1077-1098）。第 9 步把三种错误用法各试一次（节选，错误信息截到第一个冒号或分号）：

9. restrict() hard checks, and tools/change is not scope-filtered
  root.restrict({ deny: [edit] }) -> tools.restrict() requires a scoped context (agent.ctx)
  scoped.restrict({}) -> tools.restrict({}) is a no-op
  scoped.restrict({ deny: [nope] }) -> tools.restrict() names unknown global tool "nope"

三种都直接抛错，不静默忽略：在全局 context 上 restrict 会影响所有 agent，allow 和 deny 都不传被当成配置 bug，名字必须是已知的全局工具。

第 17 篇的 preset 会用到这里，一个“发布值班” preset 就是一组作用域注册加一组 restrict。restrict 落在哪一层作用域，决定了它能不能当白名单，第 17 篇再展开。

作用域一卸载，注册和屏蔽自动撤销

register() 和 restrict() 最后都走 this.layers.effect(this.ctx, ...)，返回撤销函数。用的是第 4 篇讲的 effect：登记在调用方的 Fiber 上，Fiber 卸载时自动撤销。

把 agent-A 的作用域 dispose 掉：

7. registrations are effects of the registering fiber
  scope disposed: tools/change fired 2x, agent-A view=global release lookup, agent-A tools=edit,lookup_release,read,write

看 fired 2x 和 agent-A tools=：作用域里做过一次 register、一次 restrict，dispose 之后 tools/change 触发了两次，agent-A 的视图回到全局：lookup_release 恢复成全局描述，edit 回来了，没写一行反注册代码。

tools/change 的注释说明它是不按作用域过滤的广播：一个作用域的工具集变了，所有监听者都能收到。第 9 步在 agent-B 的作用域上挂监听，让 agent-A 注册一个作用域工具（节选）：

agent-A registers a scoped tool -> agent-B listener fired 1x, agent-B view=global release lookup

agent-B 的视图没变，它的监听器照样触发了一次。监听方要自己判断这次变化和自己有没有关系。

这对 Agent 意味着什么

一项能力放哪，先看它需不需要多个实现。需要，就按 seam 拆成 Definition / Provider / Consumer 三个包，差异通过 Definition 上的只读属性暴露；不需要就是 core，扩展靠事件。

模型只看到工具的 name、description、parameters 和 render 的结果，这几处要写好。原生工具调用模式下 output.schema 不给模型看，它管的是运行时的出口检查。

output schema 要写严，additionalProperties: false 等于给每个工具加了一道防泄漏闸门。上游数据多一个字段，调用会失败，但没审过的数据不会进上下文。

本文的验证范围

实测部分是 tools-demo.ts，挂载真实的 dsh-system-prompt、dsh-tools、dsh-tool-fs、dsh-fs-local、dsh-fs-sandbox、dsh-sandbox-policy、dsh-session-projection 和 dsh-scope。

第 1–9 步直接调用 ctx.tools.execute()，不启动 agent 循环；第 10 步挂真实的 dsh-agent-loop，模型是按脚本回放的假模型；第 11 步另挂 dsh-ptc-runtime-node 及其依赖，只组装系统提示词，不执行程序。全程没有启动 dsh 的 CLI 或 Web 进程，没有调用真实模型。

第 8 步的审批服务是一个只会批准的桩，没有用 dsh-user-approval。lookup_release 在第 5 步里是一个简化版本，数据源是内存数组，approver 字段是为演示构造的。

第 3 篇 release-tool.ts 最初的版本丢掉了 validateJsonSchemaValue 返回的违规列表，那层校验实际没生效；示例仓库后来的提交 60f6f89（晚于第 3 篇发布时固定的 fb00e26）已改为有违规就报错，本文固定的 ad4082d 包含这次修复。

缺少 inject: ['tools'] 时访问 ctx.tools 的报错来自编写 demo 时的一次运行，不在输出块里，也没有断言。

主要结论都有断言：

  • 没有 ctx.fs provider 时工具列表为空；挂 fs-local 后 sandboxMode 为 undefined，write 参数为 file_path,content，写入成功；
  • 换成 fs-sandbox（read-only）后工具仍是 edit,read,write，sandboxMode 为 read-only，write 参数多出 sandbox_permissions,justification，写入返回 FS_SANDBOX_DENIED；
  • 注册不带 output 的工具抛错；
  • schemas() 投影出的键只有 name、description、parameters；
  • 干净数据调用成功；多一个 approver 字段时错误码为 INVALID_TOOL_OUTPUT，返回给模型的内容里不含邮箱；
  • agent-A 作用域里 lookup_release 的描述被遮蔽，全局描述不变；agent-A 看不到 edit，调用时错误码为 UNKNOWN_TOOL；
  • 作用域卸载后 tools/change 触发 2 次，agent-A 的描述和工具列表回到全局；
  • 带 sandbox_permissions 的写入触发一次审批并成功，下一次不带提权的写入仍返回 FS_SANDBOX_DENIED；
  • 全局 restrict、空 restrict、未知工具名三种用法都抛错；agent-A 注册作用域工具时 agent-B 的监听器触发 1 次；
  • agent 循环的请求里工具只有三个键、不含 5000，第二次请求含回合中途注册的 late_tool；会话事件不含 demo-003、含 1 record(s)；
  • PTC 模式下模型只拿到 run_code，系统提示词的 ToolOutputMap 含 records 的字段类型。

行为与文中不符时脚本以非零退出码结束。连续 3 次运行，输出都一致。
