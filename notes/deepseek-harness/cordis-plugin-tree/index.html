第 8 / 36 节 · Cordis 运行机制

一个通知插件挂两次，registry 里只有 1 个条目，底下是 2 个 Fiber。改其中一份配置，插件先 dispose 再 apply，是完整重启，不是打补丁。

第 4–6 篇讲了插件的副作用、服务依赖和事件分发，看的都是单个插件，dsh 启动时加载的却是一棵树。比如同一个通知插件要同时服务 staging 和 production，两套配置、两条 Redis 连接；同一类服务要按 preset 或 entry 各用一份，互不可见；改一行代码要能热重载，不用重启整个进程。

这三个需求在 Cordis 里分别对应 registry 的“一插件多 Fiber”、ctx.isolate() 的符号作用域，和 hmr 插件的一次 registry.delete + 重挂。下面把三者读完并各跑一遍。

这次让同一个通知插件以 staging / production 两份配置挂载，再在两个 isolate 里各注册一个同名 store，最后不靠文件监听复刻一次 HMR 换代。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • 同一插件挂两次，registry 1 个条目、2 个 Fiber；
  • fiber.update 先 dispose 后 apply，uid 不变；
  • 吞掉 internal/update 不调 next()，可以拦下重启；
  • 两个 isolate 注册同名 store，各读到 memory、disk。

一个插件可以挂多个 Fiber

ctx.plugin 不是 Context 上的方法，是 mixin 转发过去的（vendor/cordis/src/reflect.ts:221）：

this.mixin('registry', ['inject', 'plugin'])

实现在 registry 里（vendor/cordis/src/registry.ts:316）。它先把插件归一化成一个 callback：函数直接用，{ apply } 对象取 apply，class 本身就是函数。这个 callback 就是 registry 的唯一键。

有了键，registry 再拿或建一个 Plugin.Runtime，最后 new 一个 Fiber。Runtime 的字段注释（:139）写明了两者的关系：

/** Every live fiber of this plugin (one per `ctx.plugin()` call). */
fibers: DisposableList<Fiber>

一个 runtime 对应一个插件，一个 Fiber 对应一次挂载。“同一插件两份配置”因此不需要额外机制，调两次就行：

1. one plugin, two configs -> one runtime, two fibers
  apply: channel=#staging retries=1 (fiber uid=1)
  apply: channel=#prod retries=5 (fiber uid=2)
  registry entries=1 fibers of notifier=2

registry.size 是 1，runtime.fibers 是 2。后面的 HMR 靠的就是这个一对多关系：热重载要遍历 runtime.fibers 才能把每个实例都换掉。

图：registry 键为归一化 callback，runtime 下两次 plugin() 生成两个 Fiber。

Fiber 保留原始配置，重挂时用的就是它

Fiber 上并排放着两个字段（vendor/cordis/src/fiber.ts:189）：

/** The validated plugin config (updated by `update()`). */
public config: any
/** The raw plugin config, re-resolved before each activation. */
public _config: any

构造时只存 raw，this.config 在每次重载里重算，走的是 _resolveConfig（构造、重算、定义依次见 :229、:655、:641）：

private _resolveConfig(config: any) {
  config = this.context.waterfall(this, 'internal/config', config, () => config)
  return this.runtime ? resolveConfig(this.runtime, config) : config
}

先过 internal/config 这条 waterfall（第 6 篇讲的洋葱中间件），loader 用它做配置里的表达式插值（按源码，未实测）；再过 schema 校验。

校验接的是 Standard Schema V1，不是 Cordis 自家 API（vendor/cordis/src/registry.ts:104 的 Config?: StandardSchemaV1<any, T>）。

所以 Config = Schema.object(...) 在这个版本里不是框架约定，schemastery 只是恰好满足这个接口的一个库。第 6 步的 v2 用的就是手写的 { '~standard': { validate } } 对象，没引 schemastery，校验照样生效。

保留 raw，是为了每次重载都从原始配置重新解析一遍。插件升级后 schema 变了，旧的 raw 配置会按新 schema 重新校验，第 6 步里 v2 的 Config 给两份旧配置都补上了默认的 timeoutMs=3000。HMR 重挂时传的也是 raw 配置，新版本的默认值就是这样补进来的。

update() 不是打补丁，是完整重启

fiber.update() 的实现（vendor/cordis/src/fiber.ts:736）：

update(config: any, noSave = false) {
  this.assertActive()
  this._config = config
  if (this.state !== FiberState.ACTIVE) { ... }
  config = this._resolveConfig(config)
  this.context.waterfall(this, 'internal/update', config, noSave, () => {
    this.config = config
    this._error = undefined
    return this.restart()
  })
}

restart()（:718）把 epoch（第 5 篇讲的那个依赖串）置为 INACTIVE 再刷新，等于一次完整的卸载加重载。整个方法里没有 diff 或 patch。

第 2 步对 prod 的 Fiber 调 update，把 retries 改成 9：

2. update(config) is a full restart, not a patch
  dispose: channel=#prod
  apply: channel=#prod retries=9 (fiber uid=2)
  staging untouched? channel=#staging still active: true

先 dispose 再 apply，插件在 ctx.effect 里注册的清理逻辑照常执行。Fiber uid 仍是 2，重启的是同一个 Fiber，没有换新的。同 runtime 的另一个 Fiber（staging）没受影响。

fiber.update 这条路径上没有“只更新配置不重启”的分支，要跳过重启只能从 internal/update 拦。

internal/update 监听器可以拦下重启

restart() 没有直接调用，被包在 internal/update 的 waterfall 里，源码注释写了原因（:728）：

so update hooks (and HMR) can veto or replace the restart

按第 6 篇讲的 waterfall 语义，监听器不调 next()，里层就不会执行。internal/update 的里层正是 restart()。

普通的 ctx.on('internal/update') 只会收到本插件自己 Fiber 的 update（vendor/cordis/src/events.ts:140-146，见第 8 步）；要拦别的插件，得像 demo 那样传 { global: true, prepend: true }：

ctx.on('internal/update', function () {
  vetoed++
  log(`  internal/update seen for <${this.name}>, swallowing it (no next() call)`)
}, { global: true, prepend: true })

输出：

3. a listener on internal/update can veto the restart
  internal/update seen for <notifier>, swallowing it (no next() call)
  (no apply/dispose printed above -> the restart was vetoed)

监听器收到了 notifier 的 update，之后没有任何 apply 或 dispose 输出，这次重启被否决了。

loader 里的 Group 插件用的是前一种，只接管自己的 update（vendor/loader/src/config/group.ts:81）：

ctx.on('internal/update', (config) => { this.update(config) })

第 8 步验证了这种不带 global 的写法：self-guard 挂一个本地监听器，先更新另一个插件 other，再更新它自己：

8. internal/update without global only sees its own fiber
  apply: other v=1
  apply: other v=2
  local listener saw <self-guard>, swallowing it
  listener saw: [self-guard]; applied: [self-guard:1, other:1, other:2]

other 照常重启到 v=2，监听器没收到它的 update；只有 self-guard 自己那次被收到并吞掉，applied 里没有 self-guard:2。

一个 group 是配置树上的一个子节点，它的 config 是一串 entry。config 变了不该重启 group 自己，那会把整棵子树拆掉重建（按源码，未实测）。

group 按 id 遍历新旧 entry 列表：新表里没有的 remove，有的一律走 create（:48），由 Entry 自己再算一次字段 diff 决定要不要动（按源码，未实测）。

配置热更新分两层：上层做 diff 决定动谁（按源码，未实测），被动到的那个 Fiber 一律整体重启。entry 层的 diff 只在 Fiber 已启动、且 config 字段变了（或自己是 group）时，才往下调 fiber.update（按源码，未实测；vendor/loader/src/config/entry.ts:98）。

被否决的那次 update，_config 在进 waterfall 之前就已经写进去了。重启没发生，原始配置却换了，下一次因为别的原因重载时，生效的是新配置。第 6 步的输出里能直接看到这一点。

isolate 让同名服务分成两个世界

ctx.isolate() 只有三行（vendor/cordis/src/context.ts:121）：

isolate(name: string, label?: symbol) {
  const shadow = Object.create(this[symbols.isolate])
  shadow[name] = label ?? Symbol(name)
  return this.extend({ [symbols.isolate]: shadow })
}

ctx[symbols.isolate] 是一张 服务名 → symbol 的表，用原型链串成作用域链。isolate 以当前表为原型建新表，给这个服务名换一个新 symbol，然后 extend 出子 Context，父 Context 不受影响。

换个 symbol 就能隔离，因为服务实现存在一张以 symbol 为键的全局扁平表里（vendor/cordis/src/reflect.ts:209），查找逻辑是（:237）：

_getImpl(name: string, strict = true) {
  const key = this.ctx[symbols.isolate][name]
  const impl = key && this.store[key]
  ...
}

查找时先取本 Context 为这个服务名登记的 symbol，再拿它去全局表里取实现。注册同理（:287），provide 之前还会在 root 上兜底建一个默认 symbol（:286），没 isolate 过的 Context 都落在它上面。

提供方写入的 symbol 和消费方读出的 symbol 是同一个，才能匹配，隔离就是让两者不同。实现表又是全局扁平字典，所以 isolate 只管正常查找路径，不能当安全边界用。

两个 realm（作用域）各注册一个同名服务，再从 root 读一次（第 4、5 步）：

4. isolate: same service name, two realms
  reader-A sees store.read()=memory
  reader-B sees store.read()=disk
  same symbol? false
5. the isolate boundary: root has no store at all
  root.reflect.get('store') -> undefined
  but walking root.reflect.store -> memory, disk

reader-A、reader-B 两行说明两个 store 服务同时存在且互不冲突（同一个 realm 里重复注册才会抛 has been registered）。

没 isolate 过的 root 两个都看不见：它的 store symbol 是 provide 在 root 上兜底建的那一个，存在，但底下没挂任何实现。脚本用的是非严格模式 root.reflect.get('store', false)，连未激活的实现也会返回，结果仍是 undefined。

最后一行露出了隔离的边界：root 不走查找，直接遍历 root.reflect.store 这张表，两个 realm 的实现 memory、disk 都拿到了。

图：提供方按自身 symbol 写入全局实现表，消费方按同一 symbol 读出，两个 realm 互不可见。

isolate(name, label) 的第二个参数是共享作用域用的。第 7 步用同一个 label 开两个 Context，在 C 里注册 MemStore，从 D 里读：

7. isolate with the same label: two contexts, one realm
  reader-D sees store.read()=memory
  same symbol? true

D 读到了 C 注册的 memory，两边 symbol 相同，是同一个 realm。

loader 把这两种用法映射成了 YAML 里的两种写法（按源码，未实测；vendor/loader/src/config/isolate.ts:81、:84）：

  • isolate: { foo: true } 走 LocalRealm，是 entry 私有的 realm；
  • isolate: { foo: myLabel } 走按 label 缓存的 GlobalRealm，同 label 的 entry 共享。

dsh 的 preset 用 isolate 给 plan mode、compaction、workflow engine 这类状态开 entry 私有的 realm（按源码，未实测；packages/preset/agent-presets/presets/standard/agent.cordis.yml:108、:141、:172）。

HMR 按原始配置重挂，被否决的配置此时生效

vendor 目录里有完整的 @deepseek-ai/cordis-plugin-hmr（1.0.17，427 行），dsh 自己还在它之上 fork 了一套 @deepseek-ai/dsh-hmr（packages/boot/hmr/src/index.ts，590 行），加了串行化、重入检测和 profile 配置监听（按源码，未实测）。

剥掉文件监听、依赖分析、缓存清理和回滚，“换掉插件”的动作就是下面这段（vendor/hmr/src/index.ts:353）：

const reload = (plugin: any, runtime: Plugin.Runtime) => {
  if (!runtime) return
  for (const oldFiber of runtime.fibers) {
    const fiber = oldFiber.parent.registry.plugin(plugin, oldFiber._config, this.getOuterStack)
    fiber.entry = oldFiber.entry
    if (fiber.entry) fiber.entry.fiber = fiber
  }
}
// 下面两句在 :368 / :375，位于 for (const [plugin, { filename, runtime }] of reloads) 循环里，各自带 try/catch
this.ctx.registry.delete(plugin)
reload(attempts[filename], runtime)

reload 用到了前面几节的内容：

  • 遍历 runtime.fibers，因为一个插件可能挂了多份（第 1 步）；
  • 取 oldFiber._config 而不是 config，raw 配置会按新版本的 schema 重新校验（下面 v2 补上的 timeoutMs）；
  • 在 oldFiber.parent 上重挂，父 Context 决定了 isolate 与 intercept 作用域（intercept 见第 5 篇），换新实现不该换 realm；
  • registry.delete(plugin) 会把旧 runtime 的所有 Fiber 一起 dispose（vendor/cordis/src/registry.ts:258）。

上面几步在核心 Cordis 上就能复刻，不需要文件监听：

6. HMR core: delete the plugin, remount every fiber from its own _config
  dispose: channel=#staging
  dispose: channel=#prod
  v2 apply: channel=#staging retries=1 timeoutMs=3000 (fiber uid=8)
  v2 apply: channel=#prod retries=99 timeoutMs=3000 (fiber uid=9)
  remounted 2 fiber(s), each keeping its own config and parent context

两行 v2 apply 说明两个实例各自带着自己的配置回来了，旧 raw 配置里没有的 timeoutMs 由 v2 的 Config 补上。

prod 是 retries=99，正是第 3 步里被否决的那次 update 写进 _config 的值，当时没重启，这次重挂时生效了。uid 换成 8 和 9，说明这是两个新 Fiber，不是 restart。

插件自己调 ctx.fiber.dispose() 时，loader 会把 disabled: true 写回配置文件，HMR 卸载旧插件时则不能写（按源码，未实测）。loader 用一行判断把两者分开（vendor/loader/src/index.ts:140）：

if (!ctx.registry.has(fiber.runtime!.callback)) return

registry 里还有这个 callback，说明是插件自己关掉了自己；已经被 delete 掉了，说明是 HMR 在换代码（按源码，未实测）。

在包装对象上 update，真 Fiber 仍记着旧配置

ctx.plugin() 返回的是包了一层的 thenable，不是 Fiber 本身（vendor/cordis/src/registry.ts:331）：

const fiber = new Fiber(...)
const wrapped = Object.create(fiber) as Fiber & PromiseLike<Fiber>
wrapped.then = (onFulfilled, onRejected) => fiber.await().then(onFulfilled, onRejected)
return wrapped

用 Object.create(fiber) 包装，读属性会沿原型链落到真 Fiber 上，但写属性只会写在包装层。

update() 里第一件事就是 this._config = config，在包装对象上调用它，改到的是包装层的 _config，真 Fiber 的仍是旧值。config（vendor/cordis/src/fiber.ts:655）同样只写在包装层。

第 9 步在包装对象上 update({ v: 2 })，再照 HMR 的做法从 runtime.fibers 重挂：

9. update() on the wrapper returned by plugin()
  apply {"v":1}
  dispose {"v":1}
  after await wrapper, v2 applied yet? false
  apply {"v":2}
  real fiber _config={"v":1} config={"v":1} state=ACTIVE
  wrapper own props: _config, config, state, inertia
  dispose {"v":2}
  apply {"v":1}
  remounted from runtime.fibers with {"v":1}
  dispose {"v":1}

apply {"v":2} 说明插件确实用新配置重跑了：副作用列表 _disposables 和 _runner 是真 Fiber 上的共享对象（:203、:209），卸载和重跑照样发生。

但真 Fiber 的 _config、config 仍是 {"v":1}。restart 一路写入的 state、inertia 也成了包装层的自有属性（:583、:632），真 Fiber 看起来一直是 ACTIVE。

await 包装对象时 then 等的是真 Fiber（vendor/cordis/src/registry.ts:333），它的 inertia 是空的，所以 await 在旧实例卸载后、apply {"v":2} 之前就返回了。

runtime.fibers 里存的是真 Fiber，HMR 从它身上取 _config，重挂时拿到的是旧配置 {"v":1}，这次 update 就丢了。最后一行 dispose 来自脚本结尾卸载 root。

loader 的 entry 存的是 .ctx.fiber，也就是真 Fiber（vendor/loader/src/config/entry.ts:188），dsh 自己的 hmr 也取 .ctx.fiber（packages/boot/hmr/src/index.ts:524）。

vendor 的 hmr 则把包装对象直接写进 entry.fiber（vendor/hmr/src/index.ts:358），前面引用的正是这段。

源码里没有相关注释，看不出 vendor hmr 的写法是有意设计还是疏漏。自己写脚本操作 Fiber 时按 .ctx.fiber 取就行，demo 也是这样取的。

profile 先叠配置，Fiber 后保存实例

前面的实验从 ctx.plugin() 开始，没有回答 dsh 启动时是谁构造这棵树。官方架构文档给出的顺序是：profile 列出的组合包、profile 自己的 cordis.patch.yml、home 级补丁，最后才是 --patch。

补丁按 id 找配置项，替换的是整个 config；这与上文 fiber.update() 的“先卸载再重挂”是两个不同阶段（按官方架构文档，未实测）。

要核对一台机器实际装出了什么，文档给的入口是 dsh --profile web --dump-config。本文只在纯 Cordis 脚本里验证了 Fiber 的行为，没有运行这条 dsh 命令，也没有验证 profile 叠加后的 HMR。

这对 Agent 意味着什么

一个 agent 同时连 staging 和 production 的通知通道，在这套架构里就是对同一个插件调两次 plugin()，同一能力挂多份是常规用法，多实例逻辑不用写进插件内部。

估算配置改动的代价要按整体重启算：一次配置更新会先 dispose 再 apply，插件注册的清理逻辑全部执行；internal/update 监听器不调 next() 可以拦下这次重启。

isolate 管的是服务查找的作用域，不是权限边界。实测中两个 realm 的同名 store 经正常查找互不可见，但遍历实现表就能全拿到。要并存同名服务就开 isolate，要隔离不可信插件得另想办法。

本文的验证范围

实测部分是 tree-demo.ts，只依赖 vendor Cordis（4.0.2），没有启动 dsh 的 CLI 或 Web 进程，也没有调用模型；脚本用 tsx 运行，未单独跑类型检查，输出即文中所引。

主要结论都有断言：

  • 同一插件挂两次后，其 runtime 下有 2 个 Fiber；
  • update() 之后 prod 的 Fiber uid 仍是 2，apply 依次收到 #staging:1、#prod:5、#prod:9；
  • 挂上吞掉 internal/update 的监听器后再 update()，apply 没有再次执行；
  • 两个 realm 的读者分别读到 memory 和 disk，两边的 store symbol 不同；
  • root 上以非严格模式读 store 得到 undefined；
  • root 遍历 reflect.store 拿到 memory、disk 两个实现；
  • 删掉插件再按各自 _config 重挂后，apply 收到 v2 #staging:1:3000 和 v2 #prod:99:3000；
  • 同一 label 的两个 Context 共用 symbol，D 读到 C 注册的 memory；
  • 不带 global 的监听器只收到 self-guard 自己的 update，other 照常重启；
  • 包装对象 update 后 await 返回时 v2 尚未 apply，真 Fiber _config、config 仍为 {"v":1}、状态 ACTIVE，state 是包装层自有属性，按 runtime.fibers 重挂收到 v1。

同一脚本在同一环境下连续运行 3 次，输出完全一致。
