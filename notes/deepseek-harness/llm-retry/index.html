maxRetries 设成 2，一轮里重试了 4 次：预算按步清零。提供方要求等 60 秒时，normal 模式一次也不重试，这一轮直接结束。

前面各篇的模型都是脚本化的，除第 13 篇故意制造的上下文超限外从不出错。真实的提供方会限流、超时、在流到一半时断开。这一篇看模型请求失败之后，dsh 怎么处理。

这次写一个会按剧本失败的脚本化模型，给发布值班 agent 挂上 dsh-llm-retry 和 dsh-token-meter，逐一看限流、中途断流、未知错误和认证失败时，本轮怎么结束、日志里留下什么、token 怎么计。

源码为本机 DeepSeek Harness 0.1.6-alpha.2，commit ddefc45fbc。

实测结论

  • maxRetries 为 2 时，两步各失败 2 次，一轮共重试 4 次；
  • 调用块流出后断流，失败那次不执行，重试后平台只部署 1 次；
  • normal 模式对普通 Error 和要求等 60 秒的 429 不重试；
  • always 模式遇到 401 连续排了 7 次重试，直到用户取消。

没挂重试时，一次 429 就结束这一轮

重试是一个单独的插件，不在模型服务里。基础组合（base bundle）的配置里默认挂了它（按源码，未实测；packages/bundle/base/cordis.patch.yml:91-92），自己组装宿主时要记得挂。

先看不挂会怎样：

== 1. 没挂 llm-retry：一次 429 就结束这一轮 ==
本轮结束：error RATE_LIMIT（429 too many requests）；whenIdle 正常返回
日志：assistant/attempt
用户再说一句，模型收到：system/plugin、user/user「发布 payment-api 2.5」、user/user「再试一次」

看第一行：本轮以 error 结束，whenIdle 却正常返回。

适配器抛出的错误被模型服务转成一个 reason 为 error 的 finish 块（packages/llm/llm/src/index.ts:1128-1136）。

agent 循环把这次尝试记成 assistant/attempt，没有监听器要求重试时就抛出错误，本轮以 error 结束，并追加 turn/end（packages/core/agent-loop/src/agent.ts:444-463、:340）。

whenIdle() 不抛错，调用方要自己看 turn/end 的原因才知道这轮失败了。用户接着说“再试一次”，模型收到的是两条连续的用户消息，中间没有回复。失败那一轮的用户消息还在历史里，没有被撤回。

图：失败尝试记为 assistant/attempt，重试时记 llm/retry 等事件，再重发同一份消息。

挂上重试后，两次 429 仍能成功

挂上 dsh-llm-retry 后，同样的限流会被重试。重试策略归提供方适配器所有，在注册路由时读一次（packages/llm/llm/src/index.ts:439-441）。

默认是 normal 模式：对 RATE_LIMIT、SERVER、TIMEOUT、TRANSPORT 和空响应最多重试 5 次，退避从 500 毫秒到 10 秒，10% 抖动（packages/llm/llm/src/retry-policy.ts:14-23）。

demo 为了输出可复现，把策略改成最多 2 次、20 毫秒起步、上限 200 毫秒、不加抖动，重试列表只保留 RATE_LIMIT 和 TRANSPORT：

== 2. 挂上 llm-retry：两次 429 后成功 ==
本轮结束：completed
日志：assistant/attempt、llm/retry、llm/retry-started、assistant/attempt、
      llm/retry、llm/retry-started、assistant/message
llm/retry：第 1 次等 20 毫秒（RATE_LIMIT），第 2 次等 40 毫秒（RATE_LIMIT）
3 次请求的消息完全相同：true
token 用量：输入 100、输出 5（失败的两次没有上报用量）

日志那两行里，每次失败后都跟着一对 llm/retry 和 llm/retry-started。重试挂在 agent 循环的 agent/request-error waterfall 上（agent-loop/src/agent.ts:450-462），没有包在模型服务外面。

插件先追加一条 llm/retry，记下第几次、等多久、失败原因，等待结束后再追加 llm/retry-started，然后让循环重跑这一步（packages/llm/llm-retry/src/index.ts:188-191）。先写日志再等待，取消时日志里不会少一次“计划中”的重试（见第 6 步）。

三次请求的 messages 序列化后完全相同，重试是同一份历史的重放。这一节失败的两次没有流出任何内容；已流出部分内容的情况见“调用块流出后断流，失败那次不执行”。

失败尝试只记成不进入模型历史的 assistant/attempt（packages/core/session/src/types.ts:330-335）；重试事件、延迟、提供方错误和失败的部分输出都不会到达模型（按 README，未实测）。

重试预算 maxRetries 按每一步算

把 maxRetries 设为 2，跑两种连续失败：

== 3. 预算：maxRetries 是每一步的，不是每一轮的 ==
maxRetries = 2，连续 3 次 429：重试 2 次后，本轮结束：error RATE_LIMIT（429 too many requests）
两步各失败 2 次：重试记录 步1#1 步1#2 步2#1 步2#2，本轮结束：completed
同时挂压缩插件，同一步里 429、429、上下文超长：llm/retry 2 条（第 1 步），压缩 1 次，本轮结束：completed

预算用尽后，本轮以最后一次的错误结束。但计数存在会话投影里，按提供方和策略分开，遇到 step/start 或 turn/end 就清零（llm-retry/src/index.ts:131-136）。第二个例子里，第一步调部署工具，第二步写回答，两步各失败两次，一轮里一共重试了 4 次，都在预算内。

每一步发一次模型请求（重试仍在同一步内），同一条回复里的多个工具调用在同一步执行，最后写回答也占一步。

在默认 normal 策略、只有 llm-retry 负责恢复的前提下，一轮能跑完时请求次数最多是步数乘以 6（按源码，未实测）。

还挂了压缩这类自带预算的恢复插件时，预算相加。第三行的宿主另挂了 dsh-compaction-basic：同一步里两次 429 用完了 llm-retry 的 2 次，接着的上下文超长不在它的重试列表里，交给压缩插件压缩后重试。

这一步一共重试了 3 次。压缩插件的次数另算（maxOverflowRetries，默认 1，packages/compaction/compaction-basic/src/config.ts:93），估请求上限时要加上。

调用块流出后断流，失败那次不执行

这次模型把 deploy_release 的调用完整流出之后，连接才断开。

== 4. 调用块已经流出来，连接断了 ==
失败那次的流记在 assistant/attempt 里：
  block-start、deploy_release({"service":"payment-api","version":"2.5"})、block-end、usage、finish
失败那次没有执行；重试请求的消息与失败那次相同：true
重试后平台执行 1 次，tool/call 1 条
token 用量：输入 300、输出 45（失败那次的 100/20 也算进去了）
参数流到一半就断开：失败那次的流 block-start、deploy_release({"service":"payment-)、finish
  重试后平台执行 1 次，tool/call 1 条

看 block-start 开头的一行和下一行：失败那次流出了完整的调用块，却没有执行。重试请求的消息与失败那次相同，模型看不到自己上次流出的调用；重试后（demo 里由脚本）重新发出调用，平台只部署了一次。

最后两行是另一种断法：参数只流出一半，失败那次的流里只有半截参数。结果相同，失败那次不执行，平台只部署 1 次。

循环只在流正常结束、追加了 assistant/message 之后才执行工具调用（agent-loop/src/agent.ts:487-489）；流以错误结束时，整次尝试只记成 assistant/attempt（session/src/types.ts:330-335）。

失败那次的流完整留在日志里，包括调用块和用量。token 计量也算进累计：llm/retry-started 会关闭上一次尝试的计数槽，重试的用量另外累加（packages/llm/token-meter/src/usage-projection.ts:123-126）。输入 300 是三次请求各 100，输出 45 是 20 + 20 + 5。

token-meter 记的是流里上报过的用量，失败请求只要上报过就会计入；提供方在失败前没有上报用量的，比如第 2 步的 429，就不计。

token-meter 从日志里的 assistant/message 和 assistant/attempt 取最后一个用量样本，折叠成会话投影（usage-projection.ts:82-86、:118-148）。demo 读的是内存里的这份投影。

normal 模式不重试普通 Error 和超长等待

normal 和 always 两种模式，各遇到一次普通 Error 和一次要求等 60 秒的 429：

== 5. 哪些失败会重试 ==
normal：普通 Error -> 不重试，本轮 error UNKNOWN
normal：429 且要求等 60 秒 -> 不重试，本轮 error RATE_LIMIT
always：普通 Error -> 重试，等 20 毫秒，本轮 completed
always：429 且要求等 60 秒 -> 重试，等 20 毫秒，本轮 completed
normal：带 code 的普通 Error -> 记为 UNKNOWN，不重试，本轮 error UNKNOWN
normal：failure.code 与 code 一致 -> 记为 TRANSPORT，重试，本轮 completed
normal：failure.code 与 code 不一致 -> 记为 UNKNOWN，不重试，本轮 error UNKNOWN
always + 压缩插件，上下文超长：压缩 1 次，llm/retry 0 条，本轮 completed

先看普通 Error。第 5 步里不带 code 的普通 Error 被记为 UNKNOWN，本轮直接以 error 结束。

第 5 到 7 行换了三种错误对象：普通 Error 自带 code: 'ECONNRESET'，仍记为 UNKNOWN；failure.code 和 code 都是 TRANSPORT 时才被认下并重试；两者不一致又回到 UNKNOWN。

模型服务只认 dsh 自己的错误类型和这种两处一致的错误码（packages/llm/llm/src/adapter-failure.ts:16-27、:105-107）。

UNKNOWN 不在 normal 模式的重试列表里（llm-retry/src/index.ts:215-217）。自己写适配器时，网络错误要包成 LlmError 并给出 TRANSPORT、TIMEOUT 这类错误码，否则一次 socket hang up 就会结束本轮。

再看 Retry-After。提供方要求等待的时间在 maxDelayMs 以内时，插件照它等；超过上限时，normal 模式直接交给下游，不重试（:227-235）。默认上限是 10 秒，提供方说“60 秒后再来”，这一轮就结束了。

always 模式对这两种都重试：它不看错误码，Retry-After 超过上限时改用本地退避。

最后一行是 always 模式加上压缩插件：上下文超长时，它先交给排在后面的压缩插件，压缩后要求重试，llm-retry 就照办，自己不记 llm/retry（:199-214）。

always 模式遇到认证失败会一直重试

always 模式不看错误码，等一会儿能恢复的错误和永远不会恢复的错误都照样重试：

== 6. always 模式遇到认证失败：直到用户取消 ==
401 连续 7 次，排了 7 次重试，等待 20/40/80/160/200/200/200 毫秒
第 7 次请求发出时用户取消：llm/retry-started 6 条，最后一次重试在等待中被中止
本轮结束：aborted（user）
always 策略写上 maxRetries: 2，解析后只剩：mode, initialDelayMs, maxDelayMs, jitterRatio
按它跑，401 连续 12 次，排了 12 次重试，本轮结束：aborted（user）
  前 4 次等待在 20/40/80/160 毫秒的 ±10% 内：true；之后 8 次都在 180–200 毫秒之间：true

看第一行：API key 错了，重试不会有任何结果，always 模式会按退避一直请求下去，直到成功、取消或插件卸载。

demo 在第 7 次请求发出时用 setTimeout(..., 0) 安排 agent.cancel({ kind: 'user' })。取消在这次请求失败、第 7 次重试进入等待之后才生效，该次重试在等待中被中止（llm/retry 7 条、llm/retry-started 6 条），本轮以 aborted 结束。

7 次重试已经超过 normal 默认的 5 次。后三行想给 always 模式设上限：配置里写 maxRetries: 2，解析后这一项被丢掉（packages/llm/llm/src/retry-policy.ts:186-191），照样重试了 12 次才被取消。

这次用默认的 10% 抖动：退避到顶以后，8 次等待都落在 maxDelayMs 的 0.9 到 1 倍之间。抖动本是上下对称的，超过上限的部分被截掉（llm-retry/src/index.ts:59-64）。没人取消，它就一直以这个间隔请求下去。

真实适配器读 Retry-After，默认策略 5 次重试约等 15 秒

前面的错误都是脚本化模型直接抛的。第 7 步换成真实的 dsh-llm-deepseek 适配器，baseURL 指向本地一个 HTTP 服务，服务依次回 429（带 Retry-After: 0.05）、500、401：

== 7. 真实的 llm-deepseek 适配器：HTTP 429/500/401 映射成什么 ==
服务端收到 3 个请求：POST /v1/messages
  llm/retry 第 1 次：RATE_LIMIT（HTTP 429，Retry-After 50 毫秒），等 50 毫秒
  llm/retry 第 2 次：SERVER（HTTP 500），等 40 毫秒
  本轮结束：error AUTH（invalid api key）

看第一条 llm/retry：适配器把 429 映射成 RATE_LIMIT，并把 Retry-After 的 0.05 秒换算成 50 毫秒，插件照它等。

500 映射成 SERVER，按本地退避等 40 毫秒；401 映射成 AUTH，不在重试列表里，本轮结束（packages/llm/llm-deepseek/src/protocols/messages/transport.ts:22-44）。

第 8 步不给策略，用 dsh 的默认值，连续 5 次 429 后成功：

== 8. 默认策略：连续 5 次 429 实际等了多久 ==
llm/retry 5 条，每次等待都在 500/1000/2000/4000/8000 毫秒的 ±10% 内：true，本轮结束：completed
等待合计在 13.95–17.05 秒之间：true；整轮耗时不少于等待合计：true

默认策略下，5 次重试的等待合计约 15.5 秒，这一轮要多等这么久才出结果。每步都可能碰上，界面或调用方的超时要留出这段时间。

这对 Agent 意味着什么

流以错误结束时整次尝试作废，已经流出的工具调用不会执行，重试后由模型重新发出调用，所以重试本身不会让同一个调用执行两次。

maxRetries 的计数在每一步开始时清零：设成 2 时，两步各失败 2 次，一轮共重试 4 次，仍在预算内。

normal 模式遇到两种失败会直接放弃：普通 Error 记为 UNKNOWN，不重试，所以适配器要给错误码；提供方要求的等待超过 maxDelayMs 时也不重试。always 模式对认证失败这种永久错误也会一直重试，用它就得配上取消。

没挂重试时，whenIdle() 不抛错，要看 turn/end 才知道这一轮失败了，失败那一轮的用户消息留在历史里。

本文的验证范围

实测部分是 llm-retry-demo.ts。它挂载真实的 dsh-llm、dsh-llm-retry、dsh-token-meter、会话存储与投影、dsh-tools 和 agent 循环。

模型提供方是脚本化模型：每次请求按剧本返回文字、发出工具调用，或抛出指定错误码的 LlmError、普通 Error。重试策略由这个适配器提供，最多 2 次、20 毫秒起步、上限 200 毫秒、不加抖动，重试列表只保留 RATE_LIMIT 和 TRANSPORT，与默认值不同。发布平台是合成的。会话只在内存里。

第 3、5 步另挂了 dsh-compaction-basic，脚本化模型直接回摘要。第 7 步改挂真实的 dsh-llm-deepseek，baseURL 指向本地 HTTP 服务，API key 是假的，DSH_HOME 指向临时目录。第 8 步用 dsh 的默认策略。

主要结论都有断言：

  • 不挂重试时一次 429 结束本轮，下一轮请求里有两条连续的用户消息；
  • 两次 429 后成功，日志事件顺序、等待 20/40 毫秒、三次请求相同、token 用量 100/5；
  • 连续 3 次 429 在重试 2 次后结束；两步各失败 2 次时重试 4 次、本轮完成；同时挂压缩插件时，同一步里 2 次 llm-retry 加 1 次压缩后完成；
  • 调用块流出后断流，失败那次的流里有调用块，重试请求的消息与失败那次相同，部署只执行 1 次，token 用量 300/45；参数流到一半断开时同样只部署 1 次；
  • normal 模式对普通 Error 和超上限的 Retry-After 不重试，always 模式都重试；带 code 的普通 Error 和 failure/code 不一致的错误记为 UNKNOWN，两者一致时记为 TRANSPORT 并重试；always 模式把上下文超长交给压缩插件，不记 llm/retry；
  • always 模式下认证失败 7 次、排了 7 次重试、llm/retry-started 6 条，取消后本轮以 aborted（user） 结束；写上 maxRetries 被丢掉，照样重试 12 次，到顶后的等待在 180–200 毫秒之间；
  • 真实适配器把 429/500/401 映射成 RATE_LIMIT/SERVER/AUTH，429 的等待取自 Retry-After；
  • 默认策略 5 次等待都在 500 到 8000 毫秒的 ±10% 内，合计在 13.95–17.05 秒之间。

另外做了变异检查。以下 7 处改动各自单独做，每一处都会让脚本以非零退出码结束：

  • 第 2 步不挂 llm-retry；
  • 重试列表去掉 TRANSPORT；
  • maxRetries 改成 3；
  • 普通 Error 改成带 TRANSPORT 的 LlmError；
  • 第 5 步要求等 60 秒的 429 去掉 Retry-After；
  • 断流发生在上报用量之前；
  • 第 5 次请求后就取消。

连续 5 次运行，以及 4 个进程并发运行，输出都一致。带随机抖动的两步只打印范围检查的结果，不打印具体毫秒数。
