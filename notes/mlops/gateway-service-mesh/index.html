第 13 / 25 节 · 服务与部署

第 11 篇用 KServe 把模型服务标准化了：一份 InferenceService 替代了 Deployment、Service、Ingress、HPA 和模型下载逻辑，推理契约统一成 /v1/models/<name>:predict。但有两件事它一概不管——外部流量怎么安全地进到这个端点，以及集群里的其他服务凭什么能调它。

第 10 篇 §4 留了一句欠条：”生产环境还要在这一层补上 TLS、认证、超时、请求体大小限制和 rate limit。”这一篇来还。顺带把另一层窗户纸捅破：第 11 篇为了在 KinD 上有个 ingress controller 装了 istiod，但那只是让 KServe 生成的 Ingress 有人认领，装了 istiod 不等于用上了服务网格——数据面根本没有 sidecar，mTLS、流量切分、遥测一个都没启用。

1. 两个词解决的不是同一个问题

网关（Gateway）管**南北向（north-south）流量：外部请求进入集群这一跳。网格（Service Mesh）管东西向（east-west）**流量：集群内部服务之间的调用。它们不是替代关系，也不是”网格更高级所以可以省掉网关”。

    Internet
       │
       ▼
┌─────────────┐
│  AWS NLB    │  云负载均衡：把流量送进集群
└──────┬──────┘
       │  ── 南北向：TLS / 限流 / 认证 / 体积上限
┌──────▼──────┐
│   Traefik   │  入口网关
└──────┬──────┘
       │
┌──────▼───────────────────────────────┐
│  intent-mlops namespace              │
│                                      │
│  [sidecar]intent-api                 │
│       │  ── 东西向：mTLS / 熔断 /    │
│       │        权重切分 / 授权       │
│  [sidecar]feature-service            │
│  [sidecar]intent-classifier(KServe)  │
└──────────────────────────────────────┘

职责切开看：

能力归网关归网格
TLS 终止、证书签发✅内部 mTLS 另算
host/path 路由✅—
外部认证、限流、IP 白名单✅—
请求体大小限制✅—
服务间 mTLS（零信任）✗✅
服务间授权（谁能调谁）✗✅
重试、超时、熔断、离群摘除粗粒度✅ 细粒度
按权重/Header 切分流量到版本有限✅
无侵入的端到端遥测只有入口那一跳✅ 每一跳

一句话的边界：如果你只有一个单体推理服务，外部请求进来、预测、返回，中间没有服务互调，那你不需要服务网格。 装它买到的能力有一半用不上，代价却一分不少。这个系列一贯的姿态是先说清什么时候不该上——第 4 节会给判据。

2. 把网关这层补齐

第 10 篇的 Ingress 是最小形态：一个 host、一条 path、指向 intent-api Service。生产要补的东西都在这一层，不在 Flask 里。

为什么不在应用里做？ 限流写在 Flask 里，意味着恶意流量已经吃掉了 TCP 连接、gunicorn 线程和 JSON 解析的 CPU 才被判定为”超限”；写在网关，它在进程之外就被拒了。而且以后加了 feature-service、KServe 端点，每个服务各写一套逻辑，阈值必然漂移。网关策略是 Git 里的声明式清单，git log 说得清谁改的；藏在业务代码中间的 if count > 20 没人 review。

Traefik v3 用 Middleware CRD 表达这些能力。仓库里 deploy/gateway/traefik-middleware.yaml 给了 6 个，先摘两个最能说明问题的：

apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata:
  name: intent-api-ratelimit
  namespace: intent-mlops
spec:
  rateLimit:
    average: 20            # 每来源每秒平均 20 请求
    burst: 40
    period: 1s
    sourceCriterion:
      ipStrategy:
        depth: 1           # Traefik 前面有 1 层可信代理（NLB）
---
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata:
  name: intent-api-buffering
  namespace: intent-mlops
spec:
  buffering:
    maxRequestBodyBytes: 65536      # 超大 body 在网关就 413，不进 worker
    memRequestBodyBytes: 65536
    maxResponseBodyBytes: 1048576

另外四个是 ipAllowList（v3 的名字，v2 叫 ipWhiteList）、inFlightReq（每来源并发上限）、headers（HSTS 等安全响应头），以及 retry——最后这个要当心：重试对推理这种非幂等成本的请求要谨慎，后端已经过载时盲目重试等于自己 DDoS 自己，所以它默认没有挂进下面的 annotation 链，需要时再加，并且必须配合 inFlightReq 一起用。

挂载方式：annotation，不是 IngressRoute

第 10 篇明确选了原生 Ingress 而不是 Traefik 私有的 IngressRoute，理由是可移植性。代价是：Middleware 只能通过 annotation 挂到 router 上，引用格式为 <middleware 命名空间>-<middleware 名>@kubernetescrd，多个用逗号分隔，从左到右依次执行：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: intent-api
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
    traefik.ingress.kubernetes.io/router.entrypoints: websecure
    traefik.ingress.kubernetes.io/router.middlewares: >-
      intent-mlops-intent-api-ipallowlist@kubernetescrd,
      intent-mlops-intent-api-ratelimit@kubernetescrd,
      intent-mlops-intent-api-buffering@kubernetescrd,
      intent-mlops-intent-api-inflight@kubernetescrd,
      intent-mlops-intent-api-secheaders@kubernetescrd
spec:
  ingressClassName: traefik
  tls:
    - hosts: [intent-api.example.com]
      secretName: intent-api-tls        # 由 cert-manager 填充
  # rules 段与第 10 篇的 base/ingress.yaml 完全相同，此处省略

顺序按”越便宜越靠前”排：IP 白名单是一次网段比较，限流是一次计数，buffering 要读 body——把最贵的放最后，被前面拦掉的请求根本不会走到它。@kubernetescrd 后缀表示这个 middleware 来自 Kubernetes CRD 而非文件配置；漏掉后缀或写错命名空间前缀，Traefik 会静默地找不到它——router 照常工作，只是策略一条没生效。所以下面这条验证不能省。

TLS 证书交给 cert-manager：加 cert-manager.io/cluster-issuer annotation，它会把签发好的证书写进 spec.tls.secretName。第 11 篇为 KServe webhook 装的那套 cert-manager 在这里复用，不用装第二遍。

但上面这份 Ingress 有三个前置状态，缺一个就得不到预期结果，而且都不会明确报错：

前置现状怎么补
websecure entryPoint第 10 篇的 helm install traefik 是默认安装，只有 web（80）helm upgrade traefik traefik/traefik -n traefik --set ports.websecure.expose.default=true
letsencrypt-prod ClusterIssuer第 11 篇只装了 cert-manager 本体，没建 issuer按 cert-manager 文档建一个 ACME ClusterIssuer；本地/内网环境改用 selfsigned
intent-api.example.com 能解析占位域名，不存在换成你自己的域名并把 A 记录指向 Traefik 的 LoadBalancer 地址（kubectl get svc -n traefik）

没有真实域名时，Middleware 部分仍可验证——把 host 换成 nip.io 之类的泛解析域名，或者直接 kubectl port-forward 到 Traefik 再用 curl -H 'Host: ...' 打，限流和请求体上限照样生效，只是走 HTTP 不走 TLS。

光有 Middleware 清单等于没有

这是本篇最该记住的一条工程教训：traefik-middleware.yaml 单独 apply 是完全无效的。Middleware 只是一堆待引用的策略对象，不挂到某个 router 上就永远不会被执行——而挂载动作发生在 Ingress 的 annotation 里。仓库最初就踩了这个坑：Middleware 写得很完整，deploy/base/ingress.yaml 却一个 annotation 都没有，Argo CD 又只同步 deploy/base。结果是清单齐全、apply 全绿、kubectl get middleware 有五条，而线上 /predict 无限流、无体积上限、无 TLS。

所以仓库里现在有一层 deploy/overlays/production，把三件事收进同一个收敛面：

deploy/overlays/production/
├── kustomization.yaml     # base + gateway + ../../monitoring
└── ingress-patch.yaml     # 给 Ingress 补 middlewares / entrypoints / TLS

Argo CD 的 Application 也从 deploy/base 改成指向这个 overlay。判断标准很简单：如果某份清单不在任何一个 Application 的 path 之下，它在生产里就不存在。 网关策略、mTLS、监控规则全都属于最容易犯这个错的一类——它们不像 Deployment 那样”没生效就没服务”，而是没生效也一切正常，直到出事。

# 先看渲染结果里 annotation 有没有真的落到 Ingress 上
kustomize build example/deploy/overlays/production | grep -A6 'kind: Ingress'

kubectl apply -k example/deploy/overlays/production
kubectl get middleware -n intent-mlops
kubectl describe ingress intent-api -n intent-mlops   # 确认 annotation 在
kubectl get certificate -n intent-mlops               # READY=True 才算签发成功

# 限流真的生效了吗——连打 60 次应该看到 429
for i in $(seq 60); do curl -s -o /dev/null -w '%{http_code}\n' \
  https://intent-api.example.com/healthz; done | sort | uniq -c

最后那条 curl 循环不是可选的验收步骤。kubectl get middleware 返回五个对象，只证明对象存在；只有真的打出 429，才证明策略挂上了。这两件事之间隔着一个 annotation，而它出错时不报错。

两件事不在 Middleware 里，找错地方会浪费半天：超时配在 entryPoint（Helm values 的 ports.websecure.transport.respondingTimeouts）和后端 ServersTransport 上；OIDC/JWT 认证在社区版只有 forwardAuth（把请求转给一个鉴权服务），完整的 JWT 校验得靠商业版或自己接。

还有个隐蔽的坑：ipStrategy.depth 必须等于 Traefik 前面可信代理的实际层数。写成 0 时所有请求的来源 IP 都是负载均衡器的地址，限流会把全世界算成同一个客户端——要么第一秒全局 429，要么单个攻击者永远打不满配额。

3. 网格在模型服务上到底买到了什么

假设你已经越过了”只有一个服务”的阶段：intent-api 要调 feature-service 取在线特征（第 16 篇），KServe 上还挂着别的模型端点，批量任务也在调推理。这时候网格的三件事开始有真实收益。

前提是 sidecar 注入——这才是”用上网格”和”装了 istiod”的分界线：

kubectl label namespace intent-mlops istio-injection=enabled --overwrite
kubectl rollout restart deployment/intent-api -n intent-mlops
kubectl get pod -n intent-mlops -o \
  jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[*].name}{"\n"}{end}'

每个 Pod 里出现 istio-proxy 这个容器，才算数。

3.1 mTLS：堵住”集群内谁都能 curl 你的推理端点”

动手前先解决一个冲突。 本篇前半段的入口是 Traefik（deploy/base/ingress.yaml 写的是 ingressClassName: traefik），而下面这套 mesh 清单的授权策略只放行 Istio ingress gateway 的身份。两者直接叠加会得到一个很难查的结果：清单全部合法、Pod 全部健康、kubectl get authorizationpolicy 一切正常，而所有外部请求被 sidecar 以 403 拒掉。

入口只能有一个，先选定再往下走：

选择要改什么
改用 Istio ingress gateway把 ingress.yaml 换成 Gateway + VirtualService，本篇前半段的 Traefik Middleware 不再适用（限流等能力改用 Istio 的对应配置）
保留 Traefik（本系列默认）把 Traefik 的 Pod 纳入网格，并把授权策略里的 principal 改成它真实的 ServiceAccount（kubectl get sa -n traefik 确认名字）；或对该端口用 PERMISSIVE 并配 NetworkPolicy 只放行 Traefik

还有一个更基础的前提：没有 sidecar 注入，下面所有策略都是废纸。PeerAuthentication 和 AuthorizationPolicy 的执行者是 sidecar，没注入就没有执行者，东西向调用直接绕过，而这一切不会有任何报错。所以注入状态必须进 GitOps（kubectl label ns intent-mlops istio-injection=enabled 要写在清单里而不是敲在终端上），否则你以为开了零信任，实际什么都没开。

默认的 Kubernetes 网络模型是平的：任何命名空间的任何 Pod，只要知道 intent-api.intent-mlops.svc.cluster.local，就能直接发 POST。NetworkPolicy 能按 IP/标签拦一层，但无法回答”对面到底是谁”——IP 会漂移，标签是调用方自己贴的。Istio 用 mTLS 给每个工作负载发一张基于 ServiceAccount 的证书身份，PeerAuthentication 强制 STRICT 后，明文请求在 sidecar 就被拒，应用永远看不到：

apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: intent-mlops
spec:
  mtls:
    mode: STRICT

有了可验证的身份，AuthorizationPolicy 才能写出真正的最小权限——默认拒绝，然后按 principal 放行：

apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: intent-api-allow-callers
  namespace: intent-mlops
spec:
  selector:
    matchLabels: {app: intent-api}
  action: ALLOW
  rules:
    - from:
        - source:
            principals: [cluster.local/ns/istio-system/sa/istio-ingressgateway-service-account]
      to:
        - operation: {methods: ["POST"], paths: ["/predict"]}
    - from:
        - source:
            principals: [cluster.local/ns/monitoring/sa/prometheus]
      to:
        - operation: {methods: ["GET"], paths: ["/metrics"]}

一条容易搞反的规则：只要有任何一条 ALLOW 策略选中了这个工作负载，没被匹配上的请求就已经默认被拒。仓库里那份额外的空 rules: [] 策略语义上冗余，留着只是让”默认拒绝”在清单里显式可见，并防住有人误删允许列表后服务变成全开。另外 kubelet 的 /healthz /readyz 探针不需要放行，Istio 会重写探针路径让它绕过 sidecar 的授权过滤器——不知道这点的人常因为探针 403 而误以为策略写错了。

这直接接上第 20 篇讲的模型窃取攻击面：/predict 返回 confidence，是反推模型边界最有价值的泄露维度。网关的限流管住外部高频探测，AuthorizationPolicy 管住另一半——集群内一个被攻陷的无关服务，能不能不限速地把你的模型抽干。这两层缺一不可，它们防的不是同一个攻击者。

3.2 流量切分：第 15 篇那套判据的执行机构

第 15 篇给出了 canary 放量的完整判据——5xx 率、p95 延迟、PSI、低置信度比例、人工纠正率，写成了 gate.py 里的 decide()，返回 promote / hold / rollback。但那一篇只回答了”什么时候该放量”，没回答”流量到底怎么切“。VirtualService 就是那个缺失的执行机构。

先用 DestinationRule 把同一个 Service 后面的 Pod 切成 subset：

apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: intent-api
  namespace: intent-mlops
spec:
  host: intent-api.intent-mlops.svc.cluster.local
  trafficPolicy:
    tls: {mode: ISTIO_MUTUAL}
    outlierDetection: {consecutive5xxErrors: 5, interval: 10s, baseEjectionTime: 30s}
  subsets:
    - name: stable
      labels: {version: stable}
    - name: canary
      labels: {version: canary}

outlierDetection 是连续 5 次 5xx 就把该副本踢出负载池。注意 subset 是标签选择器，不是 Deployment：base/deployment.yaml 的 Pod 只有 app: intent-api 一个标签，直接 apply 上面这份，两个 subset 都解析到零个端点，服务 100% 不可用而清单本身完全合法。真实用法是给现有 Deployment 的 pod 模板补 version: stable，再起一份带 version: canary 的 Deployment，两者共用同一个 intent-api Service（Service 的 selector 只认 app 标签，两边都会被选中）。这是整套清单里最容易翻车的一处，所以仓库里把它补全了 —— deploy/mesh/canary-deployment.yaml 是可直接 apply 的 canary 副本，配套的 patch 命令写在文件头部：

# 1) 给稳定版打标签（一次性）
kubectl patch deployment intent-api -n intent-mlops --type strategic-merge \
  -p '{"spec":{"template":{"metadata":{"labels":{"version":"stable"}}}}}'

# 2) 起 canary（先把镜像 digest 换成待验证版本）
kubectl apply -f deploy/mesh/canary-deployment.yaml

# 3) 确认两个 subset 都有端点，再动权重
istioctl proxy-config endpoint deploy/istio-ingressgateway.istio-system \
  | grep intent-api

第 3 步不能省：先确认端点非空再调权重，否则你会把流量切给一个空集合，而 kubectl get vs 一切正常。

然后 VirtualService 按权重分流：

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: intent-api
  namespace: intent-mlops
spec:
  hosts: [intent-api.intent-mlops.svc.cluster.local]
  http:
    - name: weighted-canary
      timeout: 2s
      retries:
        attempts: 2
        perTryTimeout: 800ms
        retryOn: gateway-error,connect-failure,refused-stream
      route:
        - destination: {host: intent-api.intent-mlops.svc.cluster.local, subset: stable, port: {number: 80}}
          weight: 95
        - destination: {host: intent-api.intent-mlops.svc.cluster.local, subset: canary, port: {number: 80}}
          weight: 5

两边这样挂上钩：gate.py 返回 promote，就把权重从 95/5 改成 75/25，接着 50/50、0/100；返回 rollback，直接改回 100/0。改的是 Git 里的这份 YAML，由 Argo CD 收敛（第 15 篇的 GitOps 约定），不是谁上去 kubectl edit。权重必须和为 100。

apply 完必须验证权重真的下发到了数据面，而不是只躺在 etcd 里：

kubectl apply -f deploy/mesh/destinationrule.yaml
kubectl apply -f deploy/mesh/virtualservice.yaml

istioctl proxy-config route deploy/intent-api -n intent-mlops --name 80 -o json \
  | jq '.[].virtualHosts[].routes[].route.weightedClusters'

# subset 有没有真实端点——空数组就是 version 标签没打
istioctl proxy-config endpoint deploy/intent-api -n intent-mlops \
  --cluster 'outbound|80|canary|intent-api.intent-mlops.svc.cluster.local'

retries 这段有前提：/predict 幂等无副作用，重试安全；哪天这个端点开始写反馈表（第 18 篇），就得删掉，否则一次超时会产生两条记录。

3.3 可观测性：补上第 19 篇点名的那个缺口

这是网格对本系列最有价值的一条接缝。

第 19 篇已经指出了这条 SLI 的口径问题——intent_api_prediction_seconds 只包住 predict_proba，度量的是模型推理耗时而非用户感受到的请求延迟——并给出了出路：”在入口那一层取指标”。这里补上怎么取。

sidecar 自动产出的指标就是答案，零应用改动：

  • istio_requests_total{response_code, source_workload, destination_workload} —— 按调用方和被调方拆分的请求计数，直接算成功率；
  • istio_request_duration_milliseconds_bucket —— 端到端延迟直方图，口径是 Envoy 收到请求到发出响应，包含所有 HTTP 开销；
  • istio_request_bytes / istio_response_bytes —— 请求响应体积。

用它重写第 19 篇那条延迟 SLI，口径就成立了：

histogram_quantile(0.95,
  sum by (le) (
    rate(istio_request_duration_milliseconds_bucket{
      destination_workload="intent-api",
      reporter="destination"
    }[5m])
  )
)

三个必须说清的点。第一，reporter 决定你站在谁的角度看——destination 是服务端视角（不含调用方到 sidecar 的网络），source 是调用方视角（更贴近用户体感，但把网络抖动也算进来）。两个都合法，但 SLO 文档里必须写死是哪一个，这正是第 19 篇强调的”先把口径钉死”。第二，这套指标只覆盖被网格纳管的那一跳，用户到 Traefik 之间那段仍要从网关取。第三，标签由 Envoy 自动打，不用在应用里维护，但服务数一多指标基数会显著膨胀——这是网格的成本之一。

保留 intent_api_prediction_seconds 仍然有意义：它和 istio_request_duration_milliseconds 的差值，就是纯 HTTP 开销。这个差值突然变大，说明问题不在模型而在序列化或网络，排查方向从第一分钟就分岔了。

4. 代价，以及什么时候不该上

网格不是免费的。诚实的清单：

  • 每个 Pod 多一个 sidecar：约 50–100 MiB 内存和一点 CPU。20 个服务各 3 副本，就是 3–6 GiB 内存花在代理上。
  • 延迟：每次调用多两跳本地代理，通常 2–5 ms。对承诺 p95 ≤ 150 ms 的意图分类不致命，对个位数毫秒的服务是硬伤。
  • 控制面运维：istiod 要监控、要升级，Istio 的 minor 节奏很快，跨版本升级要走 revision 金丝雀。这是持续工作量，不是装完就结束。
  • 调试链路变长：一个 503 可能来自应用、客户端 sidecar、服务端 sidecar、outlierDetection 踢了副本，或一条写错的 AuthorizationPolicy。没有 istioctl proxy-config / istioctl analyze 的肌肉记忆，排查时间会明显变长。
  • 故障半径：一条写错的 VirtualService 能让整个命名空间 503。

该上的判据（满足两条以上再认真考虑）：服务之间有真实互调且调用关系在增长；合规要求集群内零信任而不只是边界防护；需要按权重/Header 做细粒度渐进发布且网关层做不到；多团队共用集群，需要不依赖各团队自觉的统一遥测与策略。

替代方案（大多数团队应该先试这些）：

  • 网关层做 canary：Traefik 的加权服务能按比例分流，够用且不引入 sidecar；
  • KServe 自带 canaryTrafficPercent：InferenceService 上一个字段就能按比例切给 canary 版本——模型服务全在 KServe 上的话，先用它；
  • NetworkPolicy + 应用层 token：覆盖相当一部分”限制谁能调谁”的诉求，代价远低于网格；
  • 只装 Istio 的 ingress gateway、不注入 sidecar：拿到网关能力，不承担数据面成本——这正是第 11 篇 KinD 环境的状态。

先把网关这层做扎实，再考虑网格。 第 2 节那些 Middleware 挡掉的问题，在早期出现得频繁得多。

5. Gateway API：知道它，但这个系列先不用

Ingress 的表达力早就不够了——没有原生的权重、Header 匹配、跨命名空间引用，扩展全塞在 annotation 里，每家 controller 互不兼容（本篇的 traefik.ingress.kubernetes.io/... 就是典型）。社区的答案是 Gateway API：把入口拆成 GatewayClass（谁来实现）/ Gateway（监听什么）/ HTTPRoute（怎么路由）三层，权重和 Header 匹配是规范里的一等字段而不是 annotation。Traefik 和 Istio 都已支持，Istio 甚至把它作为推荐的入口配置方式。

本系列继续用 Ingress + Middleware，两条理由：生态成熟度——Gateway API 的核心 HTTP 部分已稳定，但限流、认证、请求体限制这些生产必需的策略仍依赖各实现的扩展或 experimental 通道，换过去只是把 annotation 换成另一套非标准字段，可移植性并没真正兑现；版本基线——附录 D 锁定的是 Traefik 3.x 和一套已验证的清单，教学路径上再引入一组 CRD 会让”哪里出错了”更难回答。

结论：新项目没有历史包袱，值得直接从 Gateway API 起步；已有 Ingress 资产的，等实际需要它的能力（比如权重切分）时再迁，不必为新而新。

仍然缺少什么

这一篇之后，流量从公网进来的每一跳都有了策略：TLS 在网关终止、限流和体积上限在网关执行、服务间强制 mTLS、调用关系被显式授权、放量权重可以被 Git 管理、端到端延迟终于有了正确口径的指标。

但这些全都只作用在请求路径上。它们不知道请求里的那句话有没有被正确分类，不知道进模型的特征今天是不是全变成了空值，不知道这个模型是谁批准上线的。权重能切到 5%，可”切到 5% 之后看什么、什么时候回滚”，靠的是第 15 篇的判据；判据依赖的指标是否可信，取决于第 13 篇的数据质量门禁有没有拦住脏数据。网关和网格把管道修好了，管道里流的东西对不对，是接下来八篇的事。
