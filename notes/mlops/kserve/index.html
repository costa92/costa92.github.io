第 12 / 25 节 · 服务与部署

使用原生 Kubernetes 部署一个模型并不困难，困难的是长期管理几十种模型：每个团队都在重复编写 Deployment、Service、Ingress、HPA、模型下载和健康检查。

KServe 把这些通用能力收敛为模型领域的声明式 API。

本文固定使用 KServe 0.18.0，目标 Kubernetes/EKS 为 1.34.x。KServe 0.18 要求 Kubernetes 1.32+；示例选择 Standard mode，不依赖 Knative 的 scale-to-zero 与 revision 流量。入口只需一个普通 IngressClass：生产沿用附录 D 的 Traefik 3.x，本地演示用 Istio 等任意 controller 都可以。注意这里的 Istio 只是被当成 ingress controller 用，不等于启用了服务网格——两者的区别、以及网关和网格各自该管什么，见第 12 篇。完整版本矩阵与安装顺序见附录 D。

1. 核心对象

  • InferenceService：声明模型格式、存储位置、资源和扩缩容意图；
  • ServingRuntime / ClusterServingRuntime：定义使用什么容器加载某类模型；
  • Storage Initializer：把 S3 等位置的模型放入运行环境；
  • Predictor：执行在线推理。

一个概念性示例：

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: intent-classifier
spec:
  predictor:
    model:
      modelFormat:
        name: sklearn
      storageUri: s3://example-models/intent/1/
      resources:
        requests:
          cpu: 250m
          memory: 512Mi
        limits:
          cpu: "1"
          memory: 1Gi

具体字段和受支持模型格式应以当前 KServe 版本为准。模型必须按对应 runtime 期望的格式保存，不能假设任意 joblib 文件都能被内置 runtime 加载。

本项目本地训练输出是 artifacts/intent-model.joblib。发布步骤应把经过 checksum 验证的制品以 runtime 期望的 model.joblib 名称写入不可变 storageUri 目录。但在改文件名之前，先把版本这件事说清楚。

本示例工程不能直接用 KServe 0.18 的内置 sklearn runtime。 内置 runtime 的镜像把 scikit-learn 钉在 ~=1.5.1（即 >=1.5.1,<1.6），而 example/pyproject.toml 声明的是 scikit-learn>=1.6,<2。joblib 制品本质上是 pickle，跨 sklearn 大版本反序列化不受任何兼容性保证——运气好报 InconsistentVersionWarning，运气不好在 load 时直接抛异常，或者更糟：加载成功但估计器内部属性被静默错误重建。

摆在面前的是两条路，选哪条取决于你更看重什么：

  • 把训练端降到 1.5.x，与内置 runtime 对齐。 好处是零额外镜像、直接用 modelFormat: {name: sklearn}。代价是你的训练依赖版本从此由 KServe 的发布节奏决定——升 KServe 就得动训练环境，反过来也一样。
  • 保持 1.6，构建自定义 ServingRuntime。 本系列选这条。用与训练完全相同的依赖锁构建一个 serving 镜像，注册成自己的 ClusterServingRuntime，storageUri 指向的制品由这个 runtime 加载。代价是多一个镜像要维护，收益是训练端和 serving 端的 sklearn 版本由同一份锁文件保证一致，而不是靠”希望它们碰巧兼容”。

选第二条的理由和本节开头那句是同一个：不能只改文件名后假设兼容。 文件名对上了只说明 runtime 找得到文件，说明不了它读得懂文件。这个约束已记进附录 D 的版本表。

下文第 3 节的 InferenceService 清单为了讲清字段仍写 modelFormat: {name: sklearn}；真按本系列的选择走，要把它换成 runtime: <你的自定义 runtime 名>。

2. 本地快速验证：从空集群到控制面就绪

生产集群按附录 D 的顺序装（先 CRD 与 controller，再业务清单，全部固定版本、GitOps 推进）。为了在动手前先把 InferenceService 的行为看清楚，可以在一台开发机上用 KinD 拉起一个一次性集群，跑通同一套控制面。这里的版本与生产基线对齐：KServe v0.18.0、Standard mode。

集群 context 提醒：这一节会新建一个独立的 KinD 集群，kind create cluster 会把 kubeconfig 的 current-context 切成 kind-kserve-lab。第 06 篇装的 MLflow 在别的集群里（kind-mlops-labs 或你的 EKS），第 14 篇的 Argo Workflow 也假定和 MLflow 同集群。本篇跑完后要回到那条线，先切回去：

kubectl config get-contexts                 # 看清楚有哪些
kubectl config use-context kind-mlops-labs  # 或 arn:aws:eks:...:cluster/<name>

不想切来切去，就别新建集群，直接把 KServe 装进第 06 篇那个集群——本节后面的步骤原样可用。

先起集群：

kind create cluster --name kserve-lab
kubectl config current-context     # 应显示 kind-kserve-lab
kubectl get nodes

KServe 的 webhook 需要证书组件，先装 cert-manager。本地演示用 v1.20.2：

helm install cert-manager oci://quay.io/jetstack/charts/cert-manager \
  --version v1.20.2 \
  --namespace cert-manager --create-namespace \
  --set crds.enabled=true
kubectl get pods -n cert-manager

再准备入口。生产是附录 D 的 Traefik，本地用 Istio 作 ingress controller 同样可行——KServe Standard mode 只创建一个普通 Ingress 对象，用哪个 IngressClass 由集群决定，与 serving 数据路径无关：

helm repo add istio https://istio-release.storage.googleapis.com/charts
helm repo update
helm install istio-base istio/base -n istio-system --create-namespace \
  --set defaultRevision=default
helm install istiod istio/istiod -n istio-system --wait
helm install istio-ingressgateway istio/gateway -n istio-system
kubectl get pods -n istio-system

声明对应的 IngressClass，让 KServe 生成的 Ingress 有 controller 认领：

apiVersion: networking.k8s.io/v1
kind: IngressClass
metadata:
  name: istio
spec:
  controller: istio.io/ingress-controller

最后装 KServe 本体。CRD 与 controller/runtime 分成两个 chart，先 CRD 后 resources，并显式指定 Standard 部署模式：

helm install kserve-crd oci://ghcr.io/kserve/charts/kserve-crd \
  --version v0.18.0 \
  --namespace kserve --create-namespace --wait
helm install kserve oci://ghcr.io/kserve/charts/kserve-resources \
  --version v0.18.0 \
  --namespace kserve --wait \
  --set kserve.controller.deploymentMode=Standard
kubectl apply -f https://github.com/kserve/kserve/releases/download/v0.18.0/kserve-cluster-resources.yaml

两条 helm install 都要显式带 --namespace kserve。省掉它会装进 default，下面那条 kubectl get pods -n kserve 就会返回空，看起来像装失败。最后一条把内置的 ClusterServingRuntime 装进来——sklearn、XGBoost、TensorFlow 等运行时就是在这里注册的。确认控制面就绪：

kubectl get pods -n kserve
kubectl get clusterservingruntime
kubectl get crd inferenceservices.serving.kserve.io

看到 kserve-controller-manager 就绪、ClusterServingRuntime 列表里有 kserve-sklearnserver 一类条目，才能进入下一步。

生产别照抄本地这套一次性 helm install 加 kubectl apply -f <release URL> 的装法。附录 D 的硬规则是：下载固定 release、验证 checksum/签名、在非生产集群渲染后再由 GitOps 推进，不用 latest。本地 KinD 只是为了在提交清单前把行为看清楚。

3. 声明 InferenceService 并验证

控制面就绪后，部署我们的意图分类模型。清单与仓库里的 example/deploy/kserve/inferenceservice.yaml 一致：绑定最小权限的 intent-api ServiceAccount、sklearn 格式、指向不可变版本前缀的 storageUri、显式资源请求与上限。命名空间沿用附录 D 的 intent-mlops：

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: intent-classifier
  namespace: intent-mlops
spec:
  predictor:
    serviceAccountName: intent-api
    model:
      modelFormat:
        name: sklearn
      # 这个不可变前缀里必须放着 runtime 期望的 model.joblib
      storageUri: s3://REPLACE_BUCKET/intent-classifier/REPLACE_VERSION/
      resources:
        requests:
          cpu: 250m
          memory: 512Mi
        limits:
          cpu: "1"
          memory: 1Gi

这一份声明替代了原生路径里的 Deployment、Service、Ingress、HPA 以及模型下载逻辑。KServe controller 读到它以后，会拉起一个带 storage-initializer init 容器的 Predictor Pod：init 容器把 storageUri 前缀同步进来，主容器用 sklearn runtime 加载 model.joblib，再挂上 Service 与 Ingress。

源教程为了图快，把 storageUri 直接指向一个 GitHub release 上的 .pkl 单文件。能跑，但违反本系列的治理约定——发布目录必须是不可变版本前缀、文件名是 runtime 期望的 model.joblib、且带 checksum 与 run ID 审计（见第 6 节与第 1 节）。演示可以用单文件，进 CI/CD 必须走版本化前缀。

提交与验证：

cd example        # 本篇后续所有相对路径都以 example/ 为根
kubectl apply -f deploy/kserve/inferenceservice.yaml
kubectl get inferenceservice -n intent-mlops
kubectl describe inferenceservice intent-classifier -n intent-mlops
kubectl get all -n intent-mlops
kubectl get ingress -n intent-mlops

kubectl get inferenceservice 的 READY 列是第一判据。URL 就绪、READY=True 才算成功。若 READY=False，kubectl describe 的 Status.Conditions 和 Pod 事件会指出卡点：多数是 storageUri 权限不足、前缀里没有 model.joblib、或 serving 端与训练端的 scikit-learn/joblib 版本不兼容——这些都不是清单字段写错，别去改 YAML。

4. 调用推理端点

KServe 给每个模型暴露统一的推理契约 /v1/models/<name>:predict，多框架、多团队共用同一个协议——这正是它相对手写 Service 的价值之一。本地验证时不必经过 ingress，直接 port-forward 到 Predictor Service（名字是 <inferenceservice 名>-predictor）：

kubectl port-forward -n intent-mlops \
  svc/intent-classifier-predictor 8080:80

再发推理请求。sklearn runtime 的 V1 协议接受 instances 数组，每个元素是一条待分类文本：

curl -s -X POST http://localhost:8080/v1/models/intent-classifier:predict \
  -H "Content-Type: application/json" \
  -d '{"instances":["企业版订阅每个月多少钱？"]}' | jq

curl -s -X POST http://localhost:8080/v1/models/intent-classifier:predict \
  -H "Content-Type: application/json" \
  -d '{"instances":["我上传文件时应用一直崩溃"]}' | jq

curl -s -X POST http://localhost:8080/v1/models/intent-classifier:predict \
  -H "Content-Type: application/json" \
  -d '{"instances":["我忘了密码，登不进账号了"]}' | jq

一次可以批量传多条：

curl -s -X POST http://localhost:8080/v1/models/intent-classifier:predict \
  -H "Content-Type: application/json" \
  -d '{"instances":["你们的客服响应很快，谢谢","怎么申请退款？"]}' | jq

返回体是与输入一一对应的 predictions 数组。下面这几段 JSON 是响应结构示意，不是承诺：仓库里那份模型只用 30 行数据训出来，它对这几个句子给不给出这些标签，取决于你手上的制品版本。要看结构，别看结论——真正该核对的是”predictions 是个数组、长度和 instances 一致、元素是标签字符串”。

{"predictions": ["billing"]}
{"predictions": ["technical_support"]}
{"predictions": ["account"]}

批量那条传了两个样本，就返回两个元素：

{"predictions": ["account", "billing"]}

predictions 的长度永远等于 instances 的长度，靠下标对应，响应体里不带原文——批量调用时调用方必须自己保住顺序。

验收同样不能只看 Pod 为 Running：要确认 READY=True、每条已知样本被分到预期意图、kubectl top pods 下资源占用在 requests/limits 区间内。Standard mode 的 Predictor 挂 HPA 按 CPU 扩缩；如果 TARGETS 长期 <unknown>，是 Metrics Server 没装，HPA 拿不到 CPU 数据（见附录 D）。

5. 自定义预处理怎么办

我们的 TF-IDF 已封装在 sklearn Pipeline 中，适合一起加载。如果模型前还有数据库查询、复杂特征服务或业务规则，可以：

  • 构建自定义 ServingRuntime；
  • 使用 transformer 组件处理前后置逻辑；
  • 将在线特征查询拆成独立受治理服务。

不要为了迁就平台而把不可测试的复杂逻辑塞进启动脚本。

6. 模型存储与权限

storageUri 必须指向不可变版本目录。KServe 工作负载通过 Kubernetes ServiceAccount 获取最小 S3 读取权限，模型上传流水线使用另一套写权限。

还应保存 checksum、来源 run ID 和模型签名，下载后先验证再加载。

7. Standard 与 Knative 模式

不同 KServe 安装模式的扩缩容和网络行为不同：

  • Standard/Raw Deployment 更接近原生 Deployment、Service、HPA，延迟可预测；
  • Knative 模式支持 scale-to-zero 和 revision 流量能力，但可能产生冷启动。

Standard mode 仍需证书组件以及 KServe 的 CRD、controller 和 ClusterServingRuntime。部署前先确认控制面已就绪：

kubectl get pods -n kserve
kubectl get crd inferenceservices.serving.kserve.io
kubectl get clusterservingruntime
kubectl explain inferenceservice.spec.predictor \
  --api-version=serving.kserve.io/v1beta1

如果出现 no matches for kind "InferenceService"，说明 CRD 未安装或 kubeconfig 指向错误集群；如果对象存在但 READY=False，再检查 controller、runtime、S3 权限、模型格式和事件。

实时客服路由通常更重视稳定延迟，不应只为节省少量资源默认 scale-to-zero。批量、低频模型则可能适合。

8. KServe 与原生 Deployment 的选择

一个团队只有少数带复杂业务逻辑的 API，原生 Deployment 可能更直观。当平台需要支持多框架、多团队、统一推理协议、标准模型存储和生命周期时，KServe 的抽象价值才明显。

KServe 不是完整 MLOps 平台。它不取代：

  • DVC 的数据版本；
  • MLflow 的实验跟踪和模型注册；
  • 训练工作流编排；
  • 模型审批和业务质量门禁；
  • 漂移检测和真实标签反馈。

9. 一条完整交付链

这样 KServe 处在最擅长的位置：把已批准的模型稳定变成在线端点。

01—11 小结：可部署链路已经打通

我们从数据、特征、标签开始，训练并保存模型；用 Flask 和 Docker 建立服务契约；用 DVC 与 MLflow 获得可追溯性；依次在本地、AWS VM 和 EKS 中验证运行方式；最后用 KServe 把重复的模型服务基础设施抽象为平台能力。到这里，”把一个模型稳定地送上线”这件事已经完整了。

但 MLOps 的终点不是装完某个工具，而是任何一次线上预测都能回答：它使用哪个模型、模型来自哪个实验、实验使用哪份数据、由谁批准、如何监控，以及出现问题怎样安全回滚。对照这份清单，前 11 篇答出了”哪个模型、来自哪个实验、用了哪份数据”，剩下的批准、监控、回滚还都空着。

准确地说，缺的不是”什么都没有”，而是”有教学级的，没有生产级的”：第 03 篇已经交付了 validate 数据校验、固定随机种子的训练划分，以及把两者挂进 CI 的 workflow——门禁是存在的，训练也是可重复的。但它只跑在 CI 的 runner 上、只校验仓库里那份 30 行 CSV，没有独立的数据基线（谁定义”合格”、基线怎么随业务演进）、没有编排层的硬依赖（validate 和 train 是两条 CI step，不是集群执行的 DAG）、也没有身份与资源隔离。晋级靠人工判断，上线后没人盯着漂移。
