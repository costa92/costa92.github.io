第 6 / 25 节 · 训练、数据与实验

Git 很擅长管理代码差异，却不适合频繁存储大型数据集。原因不止一条：

  • CSV、图片、音频、视频这类文件一旦提交，仓库体积会迅速膨胀，历史记录再也无法收缩；
  • Git 是按行做文本差异（diff）的，面对二进制大文件只能整份重存，越提交越慢；
  • 每个人 clone / pull / push 都要搬动全量历史，团队一多就变成瓶颈；
  • 托管平台按仓库体积计费，把训练数据塞进去等于持续付费；
  • 数据还有敏感性和生命周期诉求，Git 无法表达”这份数据谁能看、什么时候该删”。

DVC（Data Version Control，数据版本控制）的思路很直接：让 Git 只保管一个小型指针文件，真实字节交给本地缓存（cache）和对象存储（object storage）去管。 于是每一次代码提交，都精确对应一份确定的数据版本，而仓库本身几乎不增重。

1. 安装 DVC 与 S3 插件

DVC 的对象存储后端是按需拆分成插件的。用 S3 当 remote 就要额外装 dvc-s3：

python3 -m pip install 'dvc[s3]'

dvc[s3] 这个 extra 等价于 dvc + dvc-s3，一条命令装完，也是 example 工程 pyproject.toml 里的写法（dvc[s3]>=3.60,<4）——依赖声明只留一处，别让文档和工程各写一套。dvc-s3 会把 boto3 一并带进来，负责和 S3 API 打交道。如果后端换成 GCS 或 Azure，只是把插件换成 dvc-gs / dvc-azure，命令层完全一样。

2. 初始化和跟踪数据

在已经是 Git 仓库的目录里初始化 DVC：

git init
dvc init
dvc add data/intents.csv

如果 .git 不在当前目录（比如项目是某个大仓库的子目录），改用 dvc init --subdir，让 DVC 把自己的元数据挂在子目录而不是去找上层的 .git。

在本系列的 example/ 里照做，用的正是这一条：example/ 是本 vault 的子目录，上层已有 .git，直接 dvc init 会报 you are not inside of a DVC repository 或把元数据挂到错误的层级。完整序列是：

cd example
pip install -e '.[mlops]'     # dvc[s3] 在 mlops extra 里
dvc init --subdir             # 仅首次
dvc repro                     # 跑 dvc.yaml 定义的 validate → train

另外注意：example/ 刻意没有对 data/intents.csv 执行 dvc add。30 行的教学数据集留在 Git 里更方便阅读和 diff，它是被 dvc.yaml 当作 stage 依赖消费的，而不是被 DVC 托管的数据。下面讲的 dvc add 流程是给真实数据集用的——真跑一遍会让 .gitignore 把这份 CSV 排除掉，与仓库现状冲突。

dvc init 会生成 .dvc/ 目录和 .dvcignore；dvc add data/intents.csv 则做三件事：

  1. 计算这份文件的内容摘要（默认 md5），把真实字节拷进本地缓存 .dvc/cache/；
  2. 生成指针文件 data/intents.csv.dvc，里面记着摘要、大小和路径；
  3. 自动往 .gitignore 追加一行，把真实的 data/intents.csv 排除掉，避免它被误提交进 Git。

看一眼生成的指针文件 data/intents.csv.dvc，它就是一份极小的 YAML：

outs:
  - md5: 826701fcfb3b5fd8872924ec429dc8c3
    size: 1102
    hash: md5
    path: intents.csv

md5 是数据的内容指纹，size 是字节数，path 指向被跟踪的真实文件。只要数据内容变一个字节，md5 就会变，DVC 据此判断数据是否更新，也据此在存储里唯一定位一份数据。

跟踪住之后，把指针和配置交给 Git：

git add .dvc .dvcignore data/intents.csv.dvc
git commit -m "track intent dataset with dvc"

注意进 Git 的是 .dvc 指针，不是几百 KB 甚至几个 G 的原始数据。这样”哪个代码提交用了哪份数据”就被钉死了：checkout 到某个历史 commit，data/intents.csv.dvc 里的 md5 也回到当时的值，指向的正是当时那份数据。

本系列的 example 工程为了让读者克隆即用，把这份仅 1 KB 的 intents.csv 直接留在了 Git 里，并由 §4 的 dvc.yaml 流水线把它当依赖消费——小到这种程度的教学数据，不 dvc add 也无妨。上面的 dvc add 流程针对的是真实项目里那种几百 MB 到几十 GB、不该塞进 Git 的数据集。两种用法（dvc add 追踪单个大文件、dvc.yaml 定义可复现流水线）DVC 都支持，按数据规模选用即可。

想确认工作区和缓存是否一致，用 dvc status：它会报告哪些被跟踪的输出发生了变化、哪些还没同步到 remote。

3. 配置 S3 Remote

指针有了，真实字节还得有个团队共享的落脚点。把一个 S3 bucket 配成默认 remote：

dvc remote add -d storage s3://example-dvc-bucket/intent-service
dvc remote modify storage region ap-southeast-1
dvc remote list
  • -d 表示 default（默认 remote），之后 dvc push / dvc pull 不指定名字就走它；
  • storage 是这个 remote 的别名，s3://... 是 bucket 加可选前缀；
  • dvc remote modify 用来补充区域等参数；
  • dvc remote list 核对配置是否写对。

这些配置落在 .dvc/config 里（remote 地址、是否 autostage 等），它是要进 Git 的普通文本：

git add .dvc/config
git commit -m "configure dvc remote"
dvc push

dvc push 把本地缓存里、Git 当前 commit 引用到的那些数据版本，按内容摘要上传到 S3——bucket 里的对象是以 md5 命名的，相同内容天然去重。

凭证绝不写进 .dvc/config。 .dvc/config 会进 Git，写死密钥等于泄露。让 dvc-s3（底层 boto3）按标准链路取凭证即可：本地用 AWS profile，CI 用短期 OIDC 凭证，训练/推理环境用挂在实例上的 IAM Role。换句话说，配置文件只描述”数据在哪个 bucket”，”谁有权访问”由运行环境的身份决定。

新成员或新机器恢复环境时，代码和数据两步走：

git clone <repository>
cd <repository>
dvc pull

git clone 拿到代码和 .dvc 指针，dvc pull 再照着指针里的 md5 从 S3 把真实数据拉回本地。想复现某次实验，先 git checkout <历史 commit> 让指针回到当时的值，再 dvc pull，就能拿回那一刻的确切数据。

4. 把处理步骤写成 Pipeline

只版本化原始文件还不够，从原始数据到训练输入的处理过程也必须可重复，否则”数据版本”只锁住了输入、锁不住加工。DVC 用 dvc.yaml 把这些步骤声明成有依赖关系的阶段（stage）：

# dvc.yaml
stages:
  validate:
    cmd: python -m intent_mlops.validate > artifacts/validation.json
    deps:
      - data/intents.csv
      - src/intent_mlops/validate.py
    outs:
      - artifacts/validation.json
  train:
    cmd: python -m intent_mlops.train
    deps:
      - data/intents.csv
      - params.yaml
      - src/intent_mlops/train.py
      - src/intent_mlops/validate.py
    params:
      - train
    outs:
      - artifacts/intent-model.joblib
      - artifacts/metadata.json
    metrics:
      - artifacts/metrics.json

deps 里既有数据（data/intents.csv）又有代码，params 引用 params.yaml 里的超参数分组，outs / metrics 是产物。执行 dvc repro 时，DVC 会对每个 stage 的依赖重新算摘要：只要数据、代码、参数任何一项的摘要没变，就直接复用上次结果，一项变了才重跑对应阶段。 这让数据版本、代码版本、参数版本共同决定了产物版本，复现不再靠记忆。

这条链路只有在训练代码真的读 params.yaml 时才成立。仓库里的 train.py 用 load_params() 从 params.yaml 取 test_size / ngram_range / C / max_iter，并把最终生效的参数写进 metadata.json——改一行 params.yaml，产物摘要就会变。如果超参还硬编码在代码里，params 声明只会制造”改了参数也重跑了”的假象，产物字节其实一模一样，这是自建流水线里很常见的一种自欺。

5. 数据版本不等于数据质量

DVC 能证明”用了哪份数据”，不能证明数据本身正确。进入训练前仍需要检查：

  • 必需列及数据类型；
  • 空值、重复行和非法标签；
  • 类别数量与比例；
  • 文本长度和语言分布；
  • 是否包含个人信息；
  • train/test 是否发生同源泄漏。

上面的 validate 阶段就是干这个的——让验证失败直接使 dvc repro 中断，并把统计报告 artifacts/validation.json 作为 artifact 留档，坏数据就进不了训练。

6. 分支、合并与安全

.dvc 指针文件是纯文本，可以像代码一样在分支间合并，但数据的语义冲突 Git 判断不了。两个分支各自改了标注，Git 只会看到两个不同的 md5，它没法替你决定哪份标注对——需要人重新生成一份经过审核的统一数据集，再让指针指向它。

S3 侧的加固建议：开启 bucket 版本控制（versioning）、静态加密、最小权限策略、访问日志和生命周期规则。还要记住一点：删掉 Git 里的指针，不等于远端对象立刻消失；跑 dvc gc（垃圾回收）清理无引用数据前，必须确认没有别的分支、tag 或项目还在引用同一份缓存，否则会误删别人还需要的历史数据。

小结

Git 管”意图”（哪个提交用了什么），DVC 管”内容映射”（指针到摘要），S3 管”真实字节”（按摘要寻址存储）。三者组合后，每一个代码版本都能精确恢复到对应的数据版本，为实验复现、模型审计和团队协作建立了共同的地基。
