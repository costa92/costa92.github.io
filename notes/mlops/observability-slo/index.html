第 20 / 25 节 · 治理与运营

上一篇用反馈闭环和受控重训练回答了”模型失效之后怎么把它修回来”，而这条闭环成立的前提是这套服务仍被可靠值守——你得先知道它现在到底是什么状态。这一篇把模型服务当作需要长期值守的生产产品：平台上线的标准不是”端点可以访问”，而是团队知道正常意味着什么、异常如何定位、报警在什么时候该把人叫醒。

1. Metrics、Logs、Traces

  • Metrics：请求率、状态码、延迟直方图、并发、模型加载和预测分布；
  • Logs：结构化记录 request ID、模型版本、错误类别，不泄露原始敏感输入；
  • Traces：连接入口、特征查询、推理和下游调用，定位长尾延迟。

推荐使用 OpenTelemetry 统一埋点语义，以 Prometheus/Grafana 展示指标。model_version 是关键维度，但用户 ID 等高基数字段不能直接成为指标 label。

1.1 示例服务暴露了什么

不要凭空写 PromQL。example/src/intent_mlops/app.py 暴露三个业务指标：

REQUESTS = Counter(
    "intent_api_requests_total", "Prediction requests", ["status", "model_version"]
)
LATENCY = Histogram(
    "intent_api_prediction_seconds", "Prediction latency", ["model_version"]
)
PREDICTIONS = Counter(
    "intent_api_predictions_total", "Predictions by label", ["label", "model_version"]
)

四条硬事实决定了后面所有查询：status 只有 success / not_ready / invalid / too_long 四个枚举值（低基数 label 该有的样子）；label 只有 billing / technical_support / account 三个取值，同样是安全的低基数维度——它按预测类别计数，用来观测预测分布漂移（第 17 篇的在线对照）；只有 /predict 被计数，探针流量不会稀释错误率；observe() 与 PREDICTIONS 都只写在成功分支，所以分位数天然是”成功请求的延迟”、类别计数天然只含真正出了结果的预测——恰好符合 SLI 惯例，但你得知道它是这么来的。

抓取由 example/monitoring/servicemonitor.yaml 声明，interval: 30s 打在名为 http 的端口的 /metrics。它靠 matchLabels: {app: intent-api} 选中 Service，而 Prometheus 实例的 serviceMonitorSelector 又要能选中它——只装 CRD 不会自动开始抓取，这是最常见的”指标怎么是空的”。

1.2 三条基础查询

# 请求率，按模型版本切开
sum by (model_version) (rate(intent_api_requests_total[5m]))

# 错误率，与 prometheusrule.yaml 里的告警同源
sum(rate(intent_api_requests_total{status!="success"}[5m]))
/
clamp_min(sum(rate(intent_api_requests_total[5m])), 0.001)

# p95 延迟
histogram_quantile(0.95,
  sum by (le) (rate(intent_api_prediction_seconds_bucket[5m])))

# 预测类别配比，突变即预测漂移的早期信号
sum by (label) (rate(intent_api_predictions_total[5m]))

rate() 而非 increase()，量纲直接是 RPS，Pod 重启导致的 Counter 归零也会被自动处理。

clamp_min 不是装饰：零流量时分母为 0，PromQL 得到 NaN，告警既不触发也不恢复。夹到极小正值后行为可预测，代价是低流量时比率被压小——所以低流量服务要额外带绝对量条件（and sum(rate(...[5m])) > 0.1），否则一天三个请求错两个也不会响。

分位数有三个坑：必须用 _bucket 序列（_sum/_count 只能算均值）；sum by (le) 必须保留 le；上面把所有版本聚成一条线，灰度期要写 sum by (le, model_version)。还要接受它是分桶线性插值估计——prometheus-client 默认边界在 150 ms 附近只有 .1 和 .25，误差可达数十毫秒。既然 150 ms 要写进 SLO，就该自定义 bucket 在这一段加密。

1.3 Recording rule：为什么要预聚合

错误率表达式会在仪表盘出现一次、告警一次、多窗口告警再四次，每次都是一遍跨全量序列的除法。固化它：

groups:
  - name: intent-api-sli
    interval: 30s
    rules:
      - record: intent_api:request_error_ratio:rate5m
        expr: |
          sum(rate(intent_api_requests_total{status!="success"}[5m]))
          /
          clamp_min(sum(rate(intent_api_requests_total[5m])), 0.001)

完整清单在 example/monitoring/recordingrule.yaml：除了 5m 窗，它还落了 rate30m / rate1h / rate6h 三个窗口和 intent_api:prediction_seconds:p95_5m——2.3 节的双窗燃烧率告警需要不同时间窗的同口径错误率，序列必须先存在，告警才不是空表达式。

预聚合买到三样东西：查询成本（每 30s 算一次落成新序列，仪表盘不再重算原始数据）、口径唯一（SLI 定义只存在一处，仪表盘和告警不可能算出两个数）、长期可查（原始高基数序列可设短保留期，聚合后的 SLI 留一年也不贵，季度复盘才有数据）。命名遵循 level:metric:operations——冒号是 recording rule 的专属标记。

1.4 label 的价值与禁忌

model_version 值得做 label，因为它低基数、且是排查时的第一个切分维度。有了它，”错误率涨了”立刻变成”是不是新版本涨的”——这一条查询就是金丝雀放量与回滚的决策依据。

反过来，用户 ID、request ID、原始文本、完整 URL 路径绝不能做 label：每个 label 值组合都是一条独立时间序列，加一个百万级用户 ID 等于让序列数乘以一百万，结果通常不是”变慢”而是 Prometheus 直接 OOM——恰好在你最需要它的时候。分界线是指标回答”有多少、多快、多少比例”，日志回答”具体是哪一个”：app.py 已把 request_id、model_version、label、confidence、latency_ms 写成一行 JSON，高基数信息该待在那里；跨服务的单请求归因交给 Traces。

2. 定义 SLO

示例：

  • 28 天可用性 ≥ 99.9%；
  • 成功请求 p95 推理延迟 ≤ 150 ms（口径见下）；
  • 技术支持类线上 recall ≥ 80%（标签延迟一周）；
  • 在线特征新鲜度：P95 特征年龄 < 20 分钟，30 天达标率 ≥ 99%。

系统 SLO 可以实时计算，模型质量 SLO 受标签延迟影响，应分开设置错误预算和处理流程。

两条与其他篇有关联的说明。recall ≥ 80% 这个 SLO 目标，高于第 15 篇离线门禁的 0.78 下限——这不是笔误：门禁是”允许上线的最低线”，SLO 是”承诺给业务的水平”，中间那 2pp 就是留给线上退化的缓冲。两个数字如果相等，任何一次轻微退化都会立刻烧穿错误预算。特征新鲜度那一条对本项目其实不适用——第 16 篇说明了本项目的特征封装在 sklearn Pipeline 里，不存在在线特征存储；这里列出来是因为一旦引入 Feature Store 它就必须进 SLO，口径与阈值的推导见第 16 篇。

写 SLO 数值之前先把口径钉死。 仓库里的告警规则用的是 intent_api_prediction_seconds 这个直方图，而它在 app.py 里只包住了 predict_proba 调用——不含 HTTP 解析、JSON 序列化和网络往返。也就是说它度量的是”模型推理耗时”，不是用户感受到的”请求延迟”，后者通常还要再高几十毫秒。两种口径都可以拿来定 SLO，但必须说清是哪一种：拿模型侧的直方图去承诺端到端延迟，是最容易在事后复盘时被推翻的一类 SLO。若要面向用户承诺，就得在入口（Ingress/Traefik 或 Istio）那一层取指标。

2.1 错误预算怎么算

SLO 不是”必须永远 99.9%”，而是”允许不达标 0.1%”。这 0.1% 是一笔可以花的额度，不是不能碰的红线：错误预算 = 窗口内总请求数 × (1 - SLO 目标)。

日均 100 万请求、28 天窗口、99.9% 目标，预算是 28000 个失败请求；一次持续 20 分钟、错误率 100% 的故障约烧掉 14000 个。这个换算本身就是最好的稳定性说服工具：它把”我们挂了 20 分钟”翻译成”接下来 26 天不能再挂”。剩余预算（1 = 未动，0 = 刚好烧完，负 = 超支）：

1 - (
  sum(increase(intent_api_requests_total{status!="success"}[28d]))
  /
  clamp_min(sum(increase(intent_api_requests_total[28d])), 1)
) / 0.001

一处需要澄清：invalid 和 too_long 是客户端送错了东西，服务侧行为完全正确，严格的 SLI 不该算作失败，而仓库的 status!="success" 算进去了——这是示例的简化。生产里分子只放服务端过错（status="not_ready"），同时给这两类单独建告警：它们突涨不代表服务坏了，但很可能代表上游客户端发版发错了。

2.2 预算烧尽了该做什么

错误预算的意义是把”该不该继续发版”从一场辩论变成一条事先约定的规则：

剩余预算决策
> 50%正常节奏，可放量，可做有风险的实验
25%~50%继续发布，金丝雀观察期加倍，禁止同时上线两个变更
< 25%只允许发稳定性修复，新功能与新模型版本排队
≤ 0冻结发布，重心切到可靠性，直到滚动窗口自然恢复预算

反方向同样重要：预算长期用不完，说明跑得太保守。 季末还剩 90% 不是荣誉而是信号——要么 SLO 太松该收紧，要么发布太慢、超配太多，该提速该省钱。错误预算是双向油门，不是单向刹车。

模型质量 SLO 走另一套流程。”recall ≥ 80%”依赖一周后才到的标签，预算无法实时计算，烧尽后的动作也不是冻结发布而是触发重训练评审（见第 18 篇）。两种预算混进一张表，两边都会失去可执行性。

2.3 多窗口多燃烧率告警

单一阈值只有两种失败方式：紧了被日常抖动吵醒，松了漏掉”每小时多错一点、一周悄悄烧光预算”的慢性问题。燃烧率（burn rate） 衡量你正在以多少倍于预算的速度消耗：

intent_api:request_error_ratio:rate5m / 0.001

分母就是 SLO 允许的错误率。燃烧率 1 表示恰好在窗口末尾用完，14.4 表示 2 天烧光。据此配快慢两组：

  • 快窗：1h 燃烧率 > 14.4 且 5m > 14.4 → 立即 page，正在发生的事故；
  • 慢窗：6h 燃烧率 > 6 且 30m > 6 → 开工单不叫醒人，慢性退化白天处理。

两窗口取 and 是关键：长窗判断”够严重”，短窗判断”还在发生”。 只有长窗，故障恢复后告警要拖很久才消除；只有短窗，一次抖动就把人叫醒。

这两条规则落在 example/monitoring/prometheusrule-burnrate.yaml：快窗 severity: critical（page），慢窗 severity: warning（ticket），两条都额外 and intent_api:request:rate5m > 0.1 —— 就是 1.2 节说的绝对量守卫，防止零流量时比率失真。表达式一律引用 recording rule 而非原始指标，所以 recordingrule.yaml 必须先 apply，否则告警会安静地永远 Inactive。

prometheusrule.yaml 的固定阈值 + for: 10m 仍然留在仓库里，但它属于”能看见”，是展示 PromQL 写法用的；燃烧率那份才是”能值守”的生产用法。两者同时启用会重复告警，生产环境二选一——最直接的一对是 burnrate 文件里的 IntentApiP95LatencyDegraded 与固定阈值文件里的 IntentApiHighP95Latency，阈值同为 0.15，同时开就是同一件事响两次。（prometheusrule.yaml 的第三条 IntentApiPredictionSkew 不在这组取舍里：它监控预测分布倾斜，不是服务 SLI，两种方案下都该留着。）

3. 事故响应与演练

Runbook 应覆盖：错误率上升、延迟退化、模型加载失败、预测分布突变、标签质量下降、S3/Registry 不可用和错误模型发布。定期演练模型回滚、数据库恢复和区域故障，确认文档真的可执行。

not_ready 值得单列一节：它意味着 Pod 起来了但模型没加载上。/readyz 返回 503 会把它挡在流量外，但若所有副本同时如此（模型文件被误删、IRSA 权限过期），服务就是全挂。

但这里有个必须点破的盲区：全挂的时候，not_ready 计数器很可能是零。 readiness 失败会把 Pod 从 Service 的 endpoint 列表里摘掉，请求根本到不了应用进程——503 由 Ingress 或 kube-proxy 返回，应用没有机会给任何计数器 +1。更普遍地说：本节到目前为止所有 SLI 都建立在”应用还活着并且能被抓取”这个前提上，而这个前提恰恰在最严重的故障里不成立。序列消失时，错误率、燃烧率这些比率表达式得到的是空向量，不是 100%——于是 100% 故障反而一片安静。

所以监控必须有一层不依赖应用自身产生的信号。仓库里的 availability-rules.yaml 就是这一层：

告警表达式核心它捕捉什么
IntentApiTargetDownup{job="intent-api"} == 0抓取失败。up 由 Prometheus 自己产生，应用挂了它仍在
IntentApiNoMetricsabsent(up{job="intent-api"})连 up 都没有——ServiceMonitor 没被选中、namespace 写错、Service 消失
IntentApiNoReadyReplicaskube_deployment_status_replicas_available == 0全部副本未就绪，流量到不了应用
IntentApiReplicasBelowPDB... < 2可用副本跌破 PDB 下界，节点维护会被卡住

判断一条告警属于哪一层，有个简单的问法：这个指标是谁产生的？ 应用自己产生的指标（intent_api_*）只能告诉你”应用认为自己怎么样”；up 来自 Prometheus、kube_* 来自 kube-state-metrics，它们能在应用失语时继续说话。只有前者的监控体系，天然对最严重的故障失明。 再往外一层是黑盒探测（从集群外定期打真实端点），本系列没有展开，但生产上值得有。

小结

可观测性的产出不是”接了 Prometheus”，而是三个问题有确定答案：正常长什么样（SLI 口径写死、recording rule 是唯一定义处）、什么时候该叫醒人（燃烧率而非固定阈值，快慢双窗决定 page 还是工单）、预算花完了做什么（发布决策由剩余预算档位驱动，不靠临场辩论）。

这一篇也留下了一条明确的债：仓库的 SLI 取自进程内直方图，度量的是模型推理耗时。要承诺面向用户的端到端延迟，得换成入口或 sidecar 的指标——第 12 篇 §3.3 给了具体写法，但两套口径至今没有合并。下一篇收束整个系列：把风险关住，把账算清。
