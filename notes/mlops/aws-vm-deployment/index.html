第 10 / 25 节 · 服务与部署

这一阶段仍采用虚拟机，但不再把 python app.py 留在 SSH 会话中运行。目标是建立可重复创建、可健康检查、可水平扩展的服务。上一篇我们在本地把意图分类（intent classification）服务跑通，这一篇把同一个 Flask 应用搬到 AWS，用一条完整的请求链路和一套可复制的实例引导脚本，让它像真正的线上服务那样存活。

动手前先看两件事。

一、这一篇和下一篇是架构讲解，不是可照抄的工程。文中的 infra-tf/ / infra-eks-terraform/ 目录不在 example/ 里——完整的 Terraform 要连带 VPC、子网、路由、安全组、IAM、启动模板、Listener、日志，那是另一个仓库的体量，塞进来会淹没本系列的主线。请把这两篇的命令当作动作序列的说明，真正落地时用你们组织已有的网络与 IAM 模块。example/ 里能直接跑的是第 10 篇之后的 Kubernetes 清单。

二、这里开始花钱了。按文中架构起一套（ALB + 2×t3.small + NAT Gateway）大约 $1.5–2/天，其中 NAT Gateway 约 $0.045/小时且按流量另计——它是最容易被忘掉的一项，因为控制台上看不见它在工作。第 10 篇的 EKS 再加 $0.10/小时控制面费。实验完请务必 terraform destroy，并手工确认这些不会被一起销毁的残留：ELB、未挂载的 EBS 卷、Elastic IP、CloudWatch log group、ECR 镜像、S3 里的 MLflow artifact。第 20 篇第 2 节会讲成本治理，但那时账单已经产生了。

1. 请求链路：为什么需要四段而不是一段

本地开发时我们直接 flask run 或 python app.py，那是内置的开发服务器，单进程、无并发保护、遇到异常就退出，官方文档也明确写着”不要用于生产”。生产链路要把职责拆开，每一段只做一件事：

  • NGINX 是 HTTP 服务器与反向代理。它听懂 HTTP，但它不会执行 Python 代码，所以它不能直接把请求交给 Flask，而是把请求转发给后端的 Gunicorn。它顺带负责连接管理、请求限流、超时控制和访问日志。
  • Gunicorn 是这条链路的关键中间层，也就是 WSGI（Web Server Gateway Interface，Python Web 网关接口） 服务器。NGINX 与 Python 应用之间语言不通，WSGI 就是双方约定好的翻译协议：Gunicorn 一边接住 NGINX 转发过来的 HTTP 请求，一边按 WSGI 规范调用 Flask 应用对象。它还负责派生多个 worker 进程来并发处理请求、回收异常 worker。
  • Flask 是承载业务的 Web 框架，路由 /predict 收到文本后调用模型推理，/healthz 返回存活状态。
  • Model 是训练好的意图分类模型（joblib 制品），在进程启动时一次性加载进内存，之后每个请求复用同一份模型对象。

一句话概括这条链路的分工：NGINX 面向公网收发 HTTP，Gunicorn 把 HTTP 翻译成 Python 调用并管理并发，Flask 承载路由，模型承载推理。任何一段单独拿出来都不足以撑起生产。

WSGI 入口

Gunicorn 需要一个明确的入口对象。约定俗成的做法是写一个 wsgi.py，把 Flask 应用暴露成一个可被 WSGI 服务器加载的顶层对象：

# wsgi.py
from intent_mlops.app import create_app

app = create_app()

Gunicorn 通过 模块:变量 的形式定位它，例如 wsgi:app 表示”加载 wsgi 模块里的 app 对象”。有了这个入口，Gunicorn 才知道该把请求交给谁。

这个 wsgi.py 是 EC2 路径下的约定，仓库的 example/ 里没有它——容器路径直接用工厂函数 intent_mlops.app:create_app()（见 Dockerfile 与 Makefile），少一层文件。两种写法都对，本篇沿用 wsgi:app 是因为 systemd unit 里写模块名比写工厂调用更常见。

启动 Gunicorn

在实例上手动验证时，一条命令就能把 WSGI 服务拉起来：

gunicorn --workers 2 --bind 127.0.0.1:8080 --timeout 30 wsgi:app

三个参数决定了这一层的行为：

  • --workers 2：派生 2 个 worker 进程并发处理请求。worker 数量要和实例 vCPU、单请求推理耗时、模型内存占用一起权衡——不是越多越好，每个 worker 都会独立加载一份模型，进程数翻倍意味着内存占用翻倍。
  • --bind 127.0.0.1:8080：只监听本机回环地址。这一点很重要：Gunicorn 不直接对公网暴露，只接受来自本机 NGINX 的连接。
  • --timeout 30：单请求超时保护，卡死的 worker 会被回收重启。

手动跑通只是为了验证，真正的生产运行要交给 Systemd 托管（见第 3 节）。

2. NGINX 反向代理

NGINX 只做一件事：把公网/ALB 进来的请求原样转发给本机 Gunicorn。配置文件放在 /etc/nginx/conf.d/intent_app.conf：

server {
    listen 80;
    server_name _;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_connect_timeout 60s;
        proxy_read_timeout 120s;
    }
}

几个要点：

  • listen 80 + server_name _：监听 80 端口、匹配任意 Host，因为实例前面还有 ALB，真正的域名与 TLS 由 ALB 处理。
  • proxy_pass http://127.0.0.1:8080：转发到本机 Gunicorn 的回环地址，与上一节 --bind 严格对应。
  • 三个 proxy_set_header：把真实客户端信息透传给后端。X-Forwarded-For 让 Flask 侧能还原原始客户端 IP，否则应用只会看到 NGINX 的地址。
  • 两个超时：连接超时 60s、读取超时 120s。模型推理偶尔较慢时，proxy_read_timeout 要留够余量，否则 NGINX 会在 Gunicorn 返回前就切断连接。

配合安全组，实例端口只允许 ALB 访问，Gunicorn 只绑回环，NGINX 只向本机代理——实例本身不需要任何一个端口直接暴露公网。

3. Systemd 托管服务

把 gunicorn ... 留在 SSH 会话里，会话一断进程就没了；重启实例也不会自动拉起。生产运行要交给 Systemd，让它负责开机自启、崩溃重启和日志接入。unit 文件放在 /etc/systemd/system/intent_gunicorn.service：

[Unit]
Description=Gunicorn instance for Intent Classifier
After=network-online.target

[Service]
User=intent-api
Group=intent-api
WorkingDirectory=/opt/intent-api
Environment="PATH=/opt/intent-api/venv/bin"
EnvironmentFile=-/etc/intent-api.env
ExecStart=/opt/intent-api/venv/bin/gunicorn \
  --workers 2 --bind 127.0.0.1:8080 --timeout 30 wsgi:app
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target

逐段看它解决了什么：

  • After=network-online.target：等网络就绪再启动，避免绑定端口时网络还没起来。
  • User / Group：用非特权账户运行，而不是 root。
  • WorkingDirectory + Environment=PATH：指定应用目录和虚拟环境路径，ExecStart 里用绝对路径调用 venv 内的 gunicorn，不依赖任何 shell 的 PATH 状态。
  • EnvironmentFile：把配置和密钥从 unit 文件里分离出去，/etc/intent-api.env 单独管理（Secret 不进代码、不进 AMI）。路径前的 - 表示”文件不存在也照常启动”；不加这个前缀，缺文件会让 unit 直接启动失败。
  • Restart=always + RestartSec=5：这是”故障自愈”的核心。worker 全部崩溃、进程被 OOM kill、异常退出，Systemd 都会在 5 秒后重新拉起，不需要人工介入。
  • WantedBy=multi-user.target：enable 后开机自动启动。

启用和管理的命令序列：

systemctl daemon-reload            # 重新加载 unit 定义
systemctl enable intent_gunicorn   # 设为开机自启
systemctl start intent_gunicorn    # 立即启动
systemctl enable nginx
systemctl restart nginx

之后用 systemctl status intent_gunicorn 看运行状态，用 journalctl -u intent_gunicorn 看聚合日志。

4. EC2 实例引导（user data）

上面这一整套——装依赖、建虚拟环境、训练/放置模型、写 systemd unit、写 NGINX 配置、开机启动——不应该靠 SSH 手工敲，而是写进 EC2 的 user data 引导脚本，让每个新实例开机时自动完成。这样 ASG 换出的新实例才能自我组装成一台可服务的机器。引导脚本的动作序列：

运行时依赖至少包含 Flask、scikit-learn、pandas、joblib、PyYAML、prometheus-client、gunicorn。但别为 EC2 路径单独维护一份 requirements.txt——那会和 pyproject.toml 里的版本约束分叉，出现”本地测的版本和机器上跑的版本不是一个”的经典事故。引导脚本里直接装项目本身即可：

/opt/intent-api/venv/bin/pip install /opt/intent-api

pytest 属于开发依赖（pyproject.toml 的 dev extra），不进运行时环境。

关键在于幂等和可重复：同一份 user data 在任意一台空白 EC2 上执行，都应该得到一台配置一致、服务已起的实例。这正是把”一台手工调好的机器”变成”可批量复制的启动模板”的分界线。

5. Terraform：声明式创建基础设施

有了会自我组装的实例，还需要把它前面的网络、负载均衡和自动伸缩用 Terraform（基础设施即代码）声明出来，而不是在控制台点鼠标。核心资源之间的关系：启动模板描述”一台实例长什么样”，ASG 用它维持一组实例，Target Group 收集这些实例并做健康检查，ALB 把外部流量分到健康的目标上。

下面是最能体现这层关系的两段（Target Group 的健康检查、ASG 的容量与目标组绑定）：

resource "aws_lb_target_group" "intent" {
  port     = 80
  protocol = "HTTP"
  vpc_id   = var.vpc_id

  health_check {
    path                = "/healthz"
    healthy_threshold   = 2
    unhealthy_threshold = 3
  }
}

resource "aws_autoscaling_group" "intent" {
  min_size            = 2
  desired_capacity    = 2
  max_size            = 6
  target_group_arns   = [aws_lb_target_group.intent.arn]
  vpc_zone_identifier = var.private_subnet_ids
}
  • 健康检查打到 NGINX 的 80 端口、探测 /healthz。连续 2 次成功才算 healthy、连续 3 次失败才算 unhealthy——阈值留出抖动容忍，避免一次偶发失败就把实例摘掉。
  • ASG 以 2 台为期望容量、下限 2、上限 6，实例落在私有子网。它把自己拉起的实例自动注册进 Target Group；某台实例健康检查持续失败时，ASG 会终止并替换它，维持期望容量。这就是”自动替换不健康节点”的来源。

上面只是示意，省略了启动模板、Listener、IAM、日志与完整网络资源。生产代码应使用远端 state、锁、模块版本和环境隔离，并在 CI 中执行 fmt、validate、安全扫描和 plan 审批。

标准的 Terraform 工作流：

cd infra-tf
terraform init                                      # 初始化 provider 与后端
terraform validate                                  # 语法与引用校验
terraform apply -auto-approve -var-file=variables.tfvars

apply 完成后，控制台会出现创建好的 ALB、Target Group（显示两个 healthy target）和由 ASG 拉起的 EC2 实例。ALB 会给出一个 DNS 端点，形如 intent-classifier-alb-xxxxxxxxxx.ap-southeast-1.elb.amazonaws.com，用它验证整条链路：

curl http://<alb-dns-name>/healthz
curl -X POST http://<alb-dns-name>/predict \
  -H "Content-Type: application/json" \
  -d '{"text":"这个月为什么被扣了两次款"}'

请求路径是 ALB → 某台 EC2 的 NGINX:80 → 本机 Gunicorn:8080 → Flask → 模型，返回意图分类结果即说明四段链路全部打通。实验结束记得销毁，避免持续计费：

terraform destroy -auto-approve -var-file=variables.tfvars

6. 发布与回滚

不要在运行中的实例上 SSH 更新文件。构建新的 AMI 或不可变启动模板版本，然后执行 instance refresh。模型版本、应用版本和镜像/AMI ID 应一起记录。

发布顺序：

只依赖 ALB /healthz 不足以判断新模型可用，还应运行一组不含敏感信息的 smoke inference。

7. 扩缩容指标

CPU 对轻量模型可能有效，但对推理服务更有意义的指标还包括 ALB 每目标请求数、并发、队列长度和 p95 延迟。模型加载较慢时必须设置足够的 warm-up 和健康检查宽限期，否则实例还没把模型加载进内存就被健康检查判死、被 ASG 换掉，陷入反复重建。

8. 安全与可观测性

  • ALB 使用 ACM 证书和 TLS，实例侧只跑明文 HTTP；
  • EC2 位于私有子网，通过 IAM Role 访问 S3；
  • 模型和配置校验摘要，Secret 通过 EnvironmentFile 注入、不进 AMI；
  • 统一采集 NGINX、Gunicorn 和应用日志；
  • 告警覆盖 5xx、目标不健康、延迟、容量和模型版本异常。

小结

VM 架构完全可以可靠服务模型，前提是采用不可变发布、负载均衡、自动替换和基础设施即代码。这一篇搭出的是一条能存活的传统生产链路，但它止步于”活着”：systemd 保证进程不死，ASG 保证实例被换掉，NGINX 保证流量进得来——而这些都只回答了运行时存活与横向扩展。真正没被回答的是换版本：新模型怎么灰度、旧版本怎么保留、放量中途指标变坏怎么退回去。在这套架构里，这三件事都得靠自己写脚本和约定，而且每加一个服务就要重写一遍。Kubernetes 不是生产化的唯一答案，它主要在服务数量和发布频率增长、上述这些环节的统一管理成本变高时才显出价值。下一篇我们把同一个模型交给容器与 Kubernetes 来编排。
