第 23 / 25 节 · 附录

这份附录按流水线顺序排列：先训练、再打包成服务、再接实验跟踪和数据版本、再上 Kubernetes，最后是监控。排查时有一条通用原则——从离症状最近的一层开始，一层层往外推，每推一层先确认上一层确实正常，不要跳过中间环节去改配置。下文的命令默认使用系列里的命名：namespace intent-mlops、Deployment / Service intent-api、InferenceService intent-classifier，替换成你自己的即可。

训练阶段

分层切分报错

train_test_split(..., stratify=y) 抛出 “The least populated class in y has only 1 member” 一类的错误，原因通常是某个标签样本太少，分层抽样没法在训练集和测试集里各放至少一条。

先看类别分布：

make validate

摘要里会列出每个标签的样本数。处理方式是补数据、合并语义相近的标签，或者明确把这个标签排除出本次训练，并在 metadata.json 里留下记录。不要通过关闭 stratify 掩盖数据问题：关掉之后报错消失了，但小类别可能整个落进训练集，测试集里一条都没有，macro F1 看起来反而更好看。数据门禁的设计见第 13 篇。

离线指标突然提高

一次改动让 macro F1 从 0.82 跳到 0.95，第一反应应该是怀疑，而不是庆祝。按出现频率依次检查：

  1. 重复样本：同一句话同时出现在训练集和测试集，模型等于在背答案。对文本做规范化（去空格、统一大小写）后再去重，比较去重前后的样本数。
  2. 同一会话跨集合：同一用户、同一会话的多条消息被随机拆到两边，表述高度相似。应该按会话或用户分组切分。
  3. 未来数据泄漏：特征里用到了预测时刻拿不到的信息，比如事后才写入的处理结果。第 16 篇讲的 point-in-time join 就是为了防这个。
  4. 测试集参与调参：反复看测试集分数挑超参数，测试集就变成了验证集。应该用交叉验证选参，测试集只在最后看一次，见第 07 篇。

确认没有以上问题之后，再把提升记录成一个可复现的 MLflow run，而不是直接宣布模型变好了。

本地可加载，容器无法加载

典型报错是 ModuleNotFoundError、AttributeError: Can't get attribute ...，或者 scikit-learn 的 InconsistentVersionWarning。joblib 文件本质是 pickle，反序列化依赖训练时的类定义和库版本，并不保证跨任意版本兼容。

按顺序比对三样东西：

# 1. 训练时记录的版本
jq '{sklearn_version, model_sha256}' artifacts/metadata.json

# 2. 镜像里的实际版本
docker run --rm intent-api:dev python -c "import sklearn, joblib, sys; print(sys.version, sklearn.__version__, joblib.__version__)"

# 3. 镜像里的模型文件是不是同一个
docker run --rm intent-api:dev sha256sum /app/artifacts/intent-model.joblib

版本不一致，就统一用同一份依赖锁文件构建训练环境和服务镜像；哈希不一致，说明打包进去的不是你以为的那个模型，回头查构建上下文和 .dockerignore。

API 与容器

/healthz 正常但 /readyz 返回 503

这正是两个探针分开设计的意义：/healthz 只说明进程活着，/readyz 要求模型已经加载成功。503 说明进程起来了但模型没加载上。

kubectl -n intent-mlops logs deploy/intent-api | grep -iE 'model|error|traceback' | head
kubectl -n intent-mlops exec deploy/intent-api -- sh -c 'echo $MODEL_PATH; ls -l "$MODEL_PATH"'

常见原因依次是：MODEL_PATH 指向了不存在的路径（相对路径在不同工作目录下解析结果不同）、文件属主是 root 而容器以非 root 用户运行导致无权读取、文件 checksum 与 metadata.json 不符被启动校验拒绝。本地复现的方法见第 08 篇。

Gunicorn worker 不断重启

日志里反复出现 WORKER TIMEOUT 或 Worker ... was sent SIGKILL! Perhaps out of memory?。

  • 被 OOM 杀掉：每个 worker 都独立加载一份模型，worker 数翻倍，内存占用接近翻倍。用 kubectl -n intent-mlops describe pod <pod> 看上次退出原因是否为 OOMKilled，再对比 memory limit。
  • 超时：单次推理耗时超过 --timeout，或者模型加载太慢，在 worker 启动阶段就超时了。

不要盲目增加 worker。先用 --workers 1 测出单进程的常驻内存和单请求耗时，再按 limit ÷ 单进程内存 算出安全的 worker 上限。并发不够时，优先考虑 --threads 或者横向扩 Pod。

只读文件系统下启动失败

开启 readOnlyRootFilesystem: true 后报 OSError: [Errno 30] Read-only file system，说明应用在往工作目录或家目录写文件，常见的有 Gunicorn worker 心跳文件、Python 的 __pycache__、日志文件和临时上传文件。

修复方式是精确开一个可写目录，而不是关掉只读：把 /tmp 挂成内存型 emptyDir（系列清单里给的是 64Mi），让临时文件都写到那里；日志打到 stdout；模型和配置保持只读。Docker 本地调试时对应的参数是 --read-only --tmpfs /tmp。

MLflow 与 DVC

MLflow 里有 run，但 artifact 丢失

UI 能看到 run 和指标，点开 artifact 却是空的或者报错。MLflow 的元数据（run、参数、指标）存在后端数据库里，artifact 文件存在对象存储里，两边是分开写的，任何一边配置错了都会出现这种「半条记录」。

  1. 看 run 记录的 artifact URI 指向哪个 bucket 和 prefix；
  2. 用同样的身份执行 aws s3 ls <artifact_uri>/，确认文件是否真的存在；
  3. 如果是 Tracking Server 代理上传（--serve-artifacts），检查服务端 Pod 的 IAM 权限；如果是客户端直传，检查训练环境的凭证。

另外，数据库备份不能替代 S3 备份：只恢复数据库，得到的是一堆指向空文件的 run。搭建细节见第 06 篇。

dvc pull 返回权限错误

dvc remote list -v                 # remote 的 URL 是否正确
aws sts get-caller-identity        # 当前到底是哪个身份
aws s3 ls s3://<bucket>/<prefix>/  # 这个身份能否列出目录

依次排除 remote URL 写错、region 不一致、凭证来源不是预期的那个（环境变量、profile 和实例角色的优先级不同），以及 bucket 使用了 KMS 加密而当前身份缺少 kms:Decrypt 权限。CI 中优先用 OIDC 换取临时凭证，EKS 中用 Pod Identity 或 IRSA，不要把长期 AccessKey 写进流水线变量。见第 05 篇。

Kubernetes 与 KServe

Pod 是 Running，但请求进不来

沿着流量路径从里往外查，每一步确认通过再往下：

kubectl -n intent-mlops get pods -l app=intent-api          # READY 是否 1/1
kubectl -n intent-mlops get endpoints intent-api            # 是否有 Pod IP
kubectl -n intent-mlops get svc intent-api -o yaml | grep -A3 selector
kubectl -n intent-mlops get ingress
kubectl -n traefik logs deploy/traefik | tail

READY 是 0/1，回到上面的 /readyz 一节；Endpoints 为空，多半是 Service selector 和 Pod label 对不上；Endpoints 正常但外部不通，再检查 IngressClass 是否被 Traefik 认领、路由规则的 host/path，以及外部负载均衡的健康检查。

HPA 不扩容

kubectl -n intent-mlops describe hpa intent-api
kubectl top pods -n intent-mlops

describe 输出里的 Conditions 和 Events 一般会直接给出原因：<unknown>/70% 表示拿不到指标，先确认 Metrics Server 正常；提示 missing request，说明容器没设 resources.requests.cpu，按百分比计算的利用率无从算起；使用自定义指标时，还要确认指标适配器能查到这个指标。如果以上都正常，那就是指标确实没超过 target——压测时注意流量是否真的打到了这组 Pod 上。

KServe InferenceService 一直 Not Ready

kubectl -n intent-mlops get inferenceservice intent-classifier
kubectl -n intent-mlops describe inferenceservice intent-classifier
kubectl -n intent-mlops logs <predictor-pod> -c storage-initializer
kubectl -n intent-mlops logs <predictor-pod> -c kserve-container

先看 condition 卡在哪一步，再看对应容器的日志。storage-initializer 报错通常是 storageUri 写错或者缺少 S3 权限；kserve-container 报错通常是模型格式与 runtime 不匹配。这里有个容易踩的坑：文件名对上了，不代表 runtime 读得懂文件。内置 sklearn runtime 的 scikit-learn 版本可能与训练端不同，系列的做法是构建与训练使用同一依赖锁的自定义 ServingRuntime，理由见第 11 篇。资源不足时 Pod 会停在 Pending，describe pod 的 Events 里能看到。

新版本 Canary 指标恶化

处理顺序是：先止血，再保留现场，最后才是分析。

  1. 冻结放量，把流量权重调回旧版本；
  2. revert 对应的 GitOps 提交，让集群状态回到 Git 里的上一个版本，而不是在集群上手工修改；
  3. 保留新旧两个版本的预测事件，按切片对比错误率、延迟和预测分布。

不要原地覆盖模型 URI，即把新模型上传到旧版本的 S3 前缀：这样回滚会回到一个已经被改掉的文件，事后也无法复盘当时线上跑的是什么。每个版本使用独立前缀，见第 15 篇。

监控

Prometheus 没有抓到指标

先确认是没抓到，还是抓到了但查错了：在 Prometheus 的 Targets 页面搜 intent-api。

  • Targets 里没有：ServiceMonitor 没被选中。检查三处匹配关系——ServiceMonitor 的 selector.matchLabels 是否匹配 Service 的 label（app: intent-api）；endpoints.port 写的是端口名称 http，而 Service 的端口必须真的叫这个名字；Prometheus 实例的 serviceMonitorSelector 和 serviceMonitorNamespaceSelector 能否选中这个 ServiceMonitor 和它所在的 namespace。只装 CRD 不会自动开始抓取。
  • Targets 里有但状态是 down：在集群内执行 curl http://intent-api.intent-mlops/metrics，确认应用确实暴露了指标；如果是跨 namespace 抓取，还要检查 NetworkPolicy 是否放行。

建议给这个服务配一条 absent(up{job="intent-api"}) 告警，「指标突然没了」本身就是故障信号。见第 19 篇。

漂移告警频繁误报

PSI 超过阈值不一定代表出了问题，先排除四种常见的统计假象：

  • 样本量太小：窗口内只有几十条请求时，PSI 波动很大。设置最小样本量，不够就不出结论。
  • 季节性：周末和工作日、白天和深夜的输入分布本来就不同，应该和同期基线比较，而不是和一个固定窗口比较。
  • 基线选得不好：基线如果取自一段异常时期，之后的正常流量反而会被判为漂移。
  • 没有按切片看：整体分布稳定，可能掩盖了某个渠道的剧烈变化；反过来，某个小切片的抖动也可能拉高整体指标。

漂移是需要调查的信号，不等于模型质量下降。确认质量需要真实标签回流，再决定是否重训练，见第 17 篇和第 18 篇。
