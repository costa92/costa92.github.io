第 2 / 25 节 · 基础

很多 DevOps 工程师第一次接触 MLOps，会自然地把模型看成一种新的应用包：构建、部署、扩容、监控，似乎把熟悉的流水线再跑一遍就够了。

真正的差别在于，普通应用的主要行为由代码决定，机器学习系统的行为还取决于数据和训练过程。相同代码使用不同数据训练，可能得到完全不同的模型；服务即使返回 HTTP 200，预测质量也可能已经下降。

0. 传统程序和机器学习的分界

把用户意图分类这件事交给传统程序，你会写一堆规则：消息里出现”扣款””退款”就归到账单，出现”登录””报错”就归到技术支持。这套 if-else 一开始能跑，但客服话术千变万化，规则越加越多、越加越难维护，遇到没预料过的说法就直接失效。

机器学习换了一条路：不再由人把规则一条条写死，而是把大量”消息 → 正确分类”的历史样本喂给算法，让它自己从数据里学习出模式（learn patterns from data）。数据越多、越贴近真实分布，模型的判断通常越准。用一句话概括这个范式的骨架就是：

  • 数据（data）：原始输入，可能是日志、数值、文本或图像，是构造特征的原料；
  • 模型（model）：一个在数据上训练出来的数学函数，负责给出判断；
  • 预测（prediction）：模型对新输入产出的结果或决策。

对 DevOps 读者来说，这个转变的含义是：系统的”业务逻辑”不再完全躺在代码仓库里，有一部分被编码进了数据和训练出来的模型制品。这也是后面所有 MLOps 工程实践的起点。

1. 一个 ML 系统究竟包含什么

以用户意图分类为例，我们希望把客服消息分为三类：

  • billing：账单、退款、扣费问题；
  • technical_support：登录失败、页面异常等技术问题；
  • account：账户资料、注销或权限问题。

训练数据可以写成：

text,label
为什么重复扣款,billing
我无法登录账号,technical_support
怎样注销账户,account

这里有五个基础概念：

  • 样本：一行历史数据；
  • 特征：模型实际使用的输入表示，例如文本经过 TF-IDF 后的向量；
  • 标签：希望模型预测的答案；
  • 训练：从样本中学习参数；
  • 推理：使用训练好的模型预测新输入。

其中”特征”这一条需要展开一句，因为它是后面十几篇反复出现的东西。模型不认识文字，只认识数字向量，所以必须先把”为什么重复扣款”这样一句话变成一串数。本系列全程用的方法叫 TF-IDF（词频—逆文档频率，Term Frequency–Inverse Document Frequency）。要理解它，先接受一个中性概念：token（切分单位）——把一段文本按某种规则切开之后得到的最小片段。怎么切由你选：可以按词切（英文按空格、中文要上分词器），也可以按固定长度的字符片段切。本系列全程用的是后者：token 就是 2–4 个连续字符的片段（如”扣款””重复扣””么重复扣”），不涉及任何中文分词器，理由见第 03 篇。

TF-IDF 把每段文本变成一个很长的向量，每一维对应词表里的一个 token，维上的数值由两部分相乘得到：

  • TF（词频）——这个 token 在当前这句话里出现了几次。出现得多，说明它对这句话重要。
  • IDF（逆文档频率）——这个 token 在整个语料里有多罕见。”的””了”这类片段几乎每句都有，区分能力为零，IDF 就把它们的权重压到很低；”扣款”只在账单类问题里出现，IDF 高，权重就大。

两者相乘的效果是：一个 token 只有既在这句话里常出现、又在整体语料里少见，才会得到高权重。于是”为什么重复扣款”这句话的向量里，”扣款”那一维数值很大，”为什么”那几维很小——模型正是靠这种差异把它判成 billing。

这里有一个 MLOps 视角的关键事实，第 16 篇会用到：IDF 是从训练语料统计出来的，属于模型的一部分。换句话说”哪些 token 稀有”这件事被固化进了模型文件，推理时必须用训练时那一份 IDF，否则同一句话在训练和线上会被算成两个不同的向量。这类”特征算错了但程序不报错”的问题，是 ML 系统区别于普通应用的典型故障。

“相同的特征转换”非常重要。如果训练时做了小写化、分词和 TF-IDF，推理时却使用另一套逻辑，即使模型文件没有损坏，输出也不可信。因此实践中常把预处理器和模型封装成一个 Pipeline 一起保存。

这里的 Pipeline（流水线）在 MLOps 语境下还有一层更大的含义：它指从数据摄取（data ingestion）、预处理、训练、评估到部署的一整套自动化步骤序列。上面把预处理器和模型打包在一起，只是这条流水线里”特征转换 → 训练”这一小段的落地方式；后续文章会把整条链路补全。

2. 训练集、验证集和测试集

不能用模型见过的数据证明模型有效。常见划分是：

  • 训练集：拟合模型参数；
  • 验证集：比较方案、调整超参数；
  • 测试集：在最终选择后做一次独立评估。

验证集和测试集不是一回事，这一点后面几篇会反复用到。 验证集是可以反复看的——你就是靠它挑 n-gram 范围、挑正则化强度，看多少次都行，代价是它给出的分数会随着你挑的次数越来越乐观，所以它衡量的是”哪个方案更好”，不是”这个方案有多好”。测试集则是只能看一次的：在所有选择都锁定之后评一次，用来估计上线后的真实水平。数据量不够单独切一份验证集时，正确做法是在训练集内部做交叉验证（cross-validation），而不是把测试集拿来当验证集用。

如果先观察测试集结果，再反复修改模型，测试集事实上也参与了决策，指标会变得过于乐观。这个陷阱有个更准确的名字：测试集污染（test set contamination），或者叫 data snooping（数据窥探）。它和”数据泄漏”常被混为一谈，但机制不同：数据泄漏是特征里混进了预测时刻拿不到的信息，测试集污染是人在决策过程中反复消费了那份本应只用一次的数据。两者的后果一样——离线分数虚高，上线打回原形。

之所以要用没见过的数据来验证，是因为模型有两种典型的”学偏”方式：

  • 过拟合（overfitting）：模型把训练数据背了下来，连噪声和偶然细节都记住了，在训练集上分数很漂亮，一遇到新输入就露馅；
  • 欠拟合（underfitting）：模型连训练数据里的基本模式都没学到，在训练集和新数据上都表现平平。

好的模型要在两者之间取得平衡——既学到规律，又不死记硬背。测试集的作用，正是把这种”对没见过的数据是否还有效”量化出来。

分类模型常见指标包括：

  • Accuracy：总体预测正确的比例；
  • Precision：预测为某类的样本中，有多少真的属于该类；
  • Recall：真实属于某类的样本中，有多少被找出来；
  • F1：Precision 和 Recall 的调和平均。

客服路由不能只看 Accuracy。如果 technical_support 只占 5%，模型全部预测成其他类别仍可能得到很高准确率，却漏掉所有技术故障。

3. 参数、超参数和模型制品

参数是训练过程学到的数值，例如线性模型的权重。超参数是在训练前配置的选择，例如正则化强度、树的数量或最大深度。

训练结束后保存的文件称为 model artifact（模型制品）。它至少需要关联：

  • 训练代码版本；
  • 数据版本；
  • 超参数；
  • 评估指标；
  • Python 与依赖版本；
  • 创建时间和模型版本。

只保存一个 model.pkl，几周后通常无法回答“它是用哪批数据训练的”。这正是后续需要 DVC 和 MLflow 的原因。

4. 模型为什么会在生产中变差

代码没有变化，现实世界却一直在变化：新增产品会带来新词汇，促销活动会改变问题分布，用户表达方式也会变化。

  • 数据漂移（data drift）：线上输入分布与训练数据不同；
  • 概念漂移（concept drift）：输入与正确答案之间的关系发生变化；
  • 标签漂移（label drift）：不同类别出现的比例发生变化。

要分清两件事：分布变化和性能退化。上面三条讲的都是分布变化——某个统计量和训练时不一样了。它不必然导致效果变差：新增的表达方式可能落在模型早就学会的模式里，类别比例的变化也可能与模型的判别边界无关，某些情况下线上效果甚至会变好。反过来，性能退化也不一定是渐进的——上游把字段口径改了、某个渠道的文本被截断了，效果可能一夜之间掉下来。

模型漂移（model drift）指的是后一件事：模型的真实效果确实变差了。而只有带标签的评估才能确认它。分布变化是”值得去查”的线索，不是”已经变差”的结论——这个区分在第 17 篇会展开成一条硬规则。真正棘手的地方在于它和进程崩溃不一样：服务照常返回结果，只是结果越来越不准，很难靠传统告警发现。这类”沉默的退化”正是 ML 系统需要一层额外监控的根本原因。

因此 ML 监控有两层：

系统健康：延迟、吞吐量、错误率、CPU、内存
模型健康：输入分布、置信度、漂移、真实效果

只有第一层，最多能证明服务活着，不能证明模型仍然有用。

5. DevOps 工程师需要掌握到什么程度

不必先成为算法专家，但至少应该能回答：模型的输入输出是什么、训练数据来自哪里、如何评估、制品如何生成、线上预处理是否一致、什么条件触发重训练、如何回滚到上一个模型。

这些问题决定了后面的流水线、存储、部署和监控应该怎样设计。

小结

机器学习系统不是“代码加一个模型文件”，而是代码、数据、模型和运行环境共同组成的系统。MLOps 的目标，是让这四部分能够被追踪、复现、验证、发布和持续运营。
