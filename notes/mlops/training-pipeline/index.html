第 15 / 25 节 · 数据与训练流水线

上一篇把数据质量门禁定义成了一份可执行契约：什么样的数据允许进入训练。但契约只有真正挡在训练前面才有意义——如果验证是人手动跑一遍、训练是另一个人在自己机器上跑，门禁随时可以被绕过。这一篇把”验证 → 训练”固化成一条声明式的 DAG，让顺序、身份、镜像和参数都由集群执行，而不是由习惯保证。

GitHub Actions 适合代码集成和触发流程，长时间训练、步骤缓存、失败重试和资源调度更适合由 Argo Workflows、Kubeflow Pipelines 或 Airflow 管理。

0. 先确认你在哪个集群

这一篇有一条容易踩空的前置条件，先说清楚：本篇假定 MLflow 与 Argo Workflows 装在同一个集群里。清单里 train 步骤的 MLFLOW_TRACKING_URI 写的是集群内 DNS http://mlflow.mlflow.svc.cluster.local:80，跨集群解析不出来——现象是训练容器起来了、日志里一个 Python 报错、MLflowException 或 connection refused，而不是任何 Argo 层面的错。

如果你是从第 11 篇一路读下来的，此刻 kubeconfig 的 current-context 大概率还停在那篇新建的 KinD 集群 kind-kserve-lab，那里既没有 Argo 也没有 MLflow。先切回去：

kubectl config get-contexts
kubectl config use-context <装了 MLflow 的那个集群>   # 第 06 / 10 篇的集群
kubectl get svc -n mlflow          # 应该能看到名为 mlflow 的 Service

如果你想就在 kserve-lab 上跑这一篇，那就在这个集群里补装 MLflow（第 06 篇第 3 节的 Helm 步骤原样可用），别指望它跨集群连过去。两种做法都行，不能不选。

本文的 Argo 示例以 Kubernetes 1.34.x、Argo Workflows 4.0.5 为基线。Workflow 仍使用 argoproj.io/v1alpha1，它来自 Argo CRD，而不是 Kubernetes 内置 API。生产安装必须固定 release；Argo 4.0 的完整 CRD 应使用 server-side apply。

1. CI 与训练编排的边界

CI 不应持有长期云凭证，也不应把数小时训练绑在短生命周期 runner 上。这条边界在实践里的表现是：GitHub Actions 负责 lint、单元测试、构建镜像并推到 ECR，拿到一个 @sha256: digest；然后由它提交一个 Workflow，把 digest 作为参数传进集群。训练本身跑在集群里，用集群的身份、集群的资源配额、集群的重试策略。

2. 仓库里那份 Workflow 逐字段讲解

仓库里的 example/workflows/train-workflow.yaml 是一份能直接提交的最小可用清单——只有 validate 和 train 两步。先看全文，再逐字段拆：

apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata:
  generateName: intent-training-
  annotations:
    intent-mlops.example.com/tested-with: argo-workflows-v4.0.5_kubernetes-v1.34
spec:
  entrypoint: pipeline
  # Created by serviceaccount.yaml in this directory; apply that first.
  serviceAccountName: intent-training
  arguments:
    parameters:
      - {name: image, value: "REGISTRY/intent-trainer@sha256:REPLACE_WITH_DIGEST"}
      # The teaching image contains this file. Replace with an Argo artifact
      # input or DVC pull for immutable S3 datasets in a real environment.
      - {name: data-path, value: data/intents.csv}
  templates:
    - name: pipeline
      dag:
        tasks:
          - {name: validate, template: validate}
          - name: train
            dependencies: [validate]
            template: train
    - name: validate
      container:
        image: "{{workflow.parameters.image}}"
        command: [python, -m, intent_mlops.validate]
        env:
          - {name: DATA_PATH, value: "{{workflow.parameters.data-path}}"}
    - name: train
      container:
        image: "{{workflow.parameters.image}}"
        command: [python, -m, intent_mlops.train_mlflow]
        env:
          - {name: DATA_PATH, value: "{{workflow.parameters.data-path}}"}
          # Matches the chart install in chapter 06: namespace mlflow, Service port 80.
          - {name: MLFLOW_TRACKING_URI, value: "http://mlflow.mlflow.svc.cluster.local:80"}

generateName: intent-training-：用 generateName 而不是 name，每次 argo submit 生成一个带随机后缀的新对象（intent-training-abc12）。训练是”每次都是新的一次运行”，不是”收敛到期望状态”——这一点和第 10 篇的 Deployment 正相反，不要给 Workflow 起固定名字，否则重复提交会直接冲突。

entrypoint: pipeline：templates 是一个平铺的列表，Argo 不会猜哪个是起点，必须显式指出。这里指向 pipeline 这个 dag 模板；validate 和 train 是被它调用的容器模板，本身不是入口。

serviceAccountName: intent-training：Workflow 级别声明，所有步骤 Pod 都用这个身份运行。不写就落到命名空间的 default SA——这是新手最常踩的坑，见下一节。

arguments.parameters：两个工作流级参数，模板里用 {{workflow.parameters.<name>}} 引用。

  • image 写成 REGISTRY/intent-trainer@sha256:REPLACE_WITH_DIGEST。占位符要在提交时替换成 CI 刚推上去的真实 digest。用 digest 不用 tag，理由和第 10 篇一致：这条 Workflow 记录下来的”训练用的是哪份代码”必须是不可变的，否则半年后复现实验时 :latest 早就指向别的东西了。
  • data-path 默认 data/intents.csv。注意这个默认值只在教学镜像里成立——镜像构建时把 data/ 一起 COPY 进去了，所以容器里直接有这个文件。清单里的注释已经把话说明白：真实环境应换成 Argo artifact 输入或 DVC pull 拉不可变的 S3 数据集。

DAG 依赖：train 声明 dependencies: [validate]，validate 失败则 train 根本不会启动。这就是第 13 篇那道门禁的执行机制——不是”训练脚本里顺手调一下校验”，而是编排层面的硬依赖，任何人提交这条 Workflow 都绕不过去。

两个 container 模板：都用同一个 image（同一份代码、同一套依赖锁），只是 command 不同——python -m intent_mlops.validate 与 python -m intent_mlops.train_mlflow。两个模块都读 DATA_PATH 环境变量（os.getenv("DATA_PATH", ...)），所以参数注入靠 env 而不是命令行参数。

MLFLOW_TRACKING_URI 只在 train 步骤注入，指向 http://mlflow.mlflow.svc.cluster.local:80——正是第 06 篇用 Helm chart 装进 mlflow 命名空间的那个 Service，集群内 DNS 直连，不走 ingress。train_mlflow.py 会 mlflow.start_run()、记录 git_sha / dataset_sha256 / 超参、记录 macro_f1，并把 artifacts/ 目录整个 log_artifacts 上去。这一条 env 是把”训练跑过”和”训练可追溯”连起来的唯一一根线；漏掉它，脚本会退回默认的 http://localhost:5000，容器里没有那个服务，运行直接失败。

3. 为什么必须配 ServiceAccount 和 workflowtaskresults 权限

同目录的 example/workflows/serviceaccount.yaml 要先于 Workflow apply。它只做三件事：建一个 intent-training SA、一个 Role、一个 RoleBinding。Role 的规则只有一条：

rules:
  - apiGroups: ["argoproj.io"]
    resources: ["workflowtaskresults"]
    verbs: ["create", "patch"]

这条权限值得单独解释，因为它导致的故障现象非常有迷惑性。Argo 的 executor 跑在每个步骤 Pod 里，步骤结束后它要把退出码、输出参数等结果写回集群——写成一个 WorkflowTaskResult 对象，controller 再读它来推进 DAG。用的是 Pod 自己的 ServiceAccount。所以少了这条 Role：

  • 容器里的 Python 脚本正常跑完、日志里一切正常、退出码 0；
  • 但 executor 创建 workflowtaskresults 被 RBAC 拒绝；
  • controller 拿不到结果，把这一步标成 Failed。

“日志全绿但步骤失败”——看到这个组合，先查 RBAC，别去改训练代码。

SA 上还留了一句注释：在 EKS 上应该在这里绑 IRSA / Pod Identity 角色，让训练 Pod 拿到读 S3 数据集、写 MLflow artifact bucket 的权限，而不是挂静态 AWS key。这与第 10 篇给推理 Pod 授权的做法是同一套机制，只是权限方向相反：推理只读，训练可写（第 11 篇第 6 节那张图讲的就是这个分工）。

4. 一个必须承认的差距：artifact 还留在容器里

第 2 节开头那条原则——每一步用不可变镜像，输入输出通过明确参数或 artifact URI 传递，不要依赖上一步容器遗留的本地文件——仓库里这份清单其实并没有完全做到。

具体地说：train 步骤把 intent-model.joblib、metadata.json、metrics.json 写进容器本地的 artifacts/ 目录，Workflow 里没有任何 outputs.artifacts 声明。Pod 一结束，容器文件系统就没了。

这里有一半是被 MLflow 兜住的：train_mlflow.py 调了 mlflow.log_artifacts(str(ARTIFACTS), artifact_path="intent-model")，制品其实被推到了 MLflow 的 artifact store，带着 run ID 可以追溯。所以示例不是”制品彻底丢失”，而是”制品的流转绕过了编排层”。代价是：Argo 自己不知道这一步产出了什么，下游步骤（比如后续要加的 evaluate、register）没法用 inputs.artifacts 声明式地拿到它，只能靠”再去 MLflow 查一次 run”这种隐式约定。

保留这个简化是为了让示例在没有配置 artifact repository 的集群上也能一把跑通。但生产上应该补齐，有三条路：

  1. 配置 Argo artifact repository（S3/MinIO），在模板里声明 outputs.artifacts，由 Argo 负责打包上传和下游注入；
  2. 训练步骤直接写不可变 S3 版本前缀，把 URI 作为 outputs.parameters 传下去——和第 11 篇 storageUri 的约定对齐；
  3. 数据侧用 DVC：validate 之前 dvc pull 拉指定版本的数据，训练后 dvc push 推制品，数据版本由 dvc.lock 而不是容器镜像携带。

第一条的写法示意（只是补上 outputs，其他字段不变）：

- name: train
  container:
    image: "{{workflow.parameters.image}}"
    command: [python, -m, intent_mlops.train_mlflow]
    env:
      - {name: DATA_PATH, value: "{{workflow.parameters.data-path}}"}
      - {name: MLFLOW_TRACKING_URI, value: "http://mlflow.mlflow.svc.cluster.local:80"}
  outputs:
    artifacts:
      - name: model
        path: /app/artifacts
        archive: {none: {}}
        s3:
          key: "intent-classifier/{{workflow.name}}/"

s3.key 用 {{workflow.name}} 做前缀，每次运行落到独立的不可变目录——这样第 11 篇要求的”storageUri 指向不可变版本前缀”才有东西可指。bucket、endpoint、凭证来自集群级的 artifact repository 配置（workflow-controller-configmap），不写死在 Workflow 里。

示例和原则不一致就直说，比事后被读者发现要好。

5. 提交与验证

5.1 先把 intent-trainer 镜像构建出来

image 参数里那个 REGISTRY/intent-trainer@sha256:... 不是仓库里已有的镜像，得先构建。它和第 04/10 篇的服务镜像不是同一个，这一点必须说清楚：

Dockerfile（服务）Dockerfile.trainer（训练）
装什么pip install .pip install '.[mlops]'，多了 mlflow 和 dvc[s3]
构建期做什么校验 + 训练，把模型固化进镜像什么都不做，训练发生在运行期
入口gunicorn 起 HTTP 服务python -m intent_mlops.train_mlflow
运行期约束只读根文件系统、需要可写 /tmp需要可写 artifacts/，不需要 Flask/gunicorn 那套
身份非 root，10001:10001同样非 root，10001:10001

第一行是最关键的差别。服务镜像里没有 mlflow——pip install . 只装 [project.dependencies]，mlops 是 optional extra。拿服务镜像去跑这条 Workflow，validate 那步会过，train 那步一启动就 ModuleNotFoundError: No module named 'mlflow'。日志里只有这一行，看不出和 Argo 有任何关系。

构建并推送（以 ECR 为例）：

cd example        # 本篇后续所有相对路径都以 example/ 为根

REGISTRY=123456789012.dkr.ecr.ap-southeast-1.amazonaws.com
aws ecr get-login-password --region ap-southeast-1 \
  | docker login --username AWS --password-stdin "$REGISTRY"

docker buildx build \
  -f Dockerfile.trainer \
  -t "$REGISTRY/intent-trainer:$(git rev-parse --short HEAD)" \
  --push .

推完之后要拿到 digest，因为 Workflow 里用的是 @sha256:，不是 tag：

DIGEST=$(aws ecr describe-images \
  --repository-name intent-trainer \
  --image-ids imageTag=$(git rev-parse --short HEAD) \
  --query 'imageDetails[0].imageDigest' --output text)
echo "$DIGEST"      # sha256:xxxx...

这个值不要手改进 YAML 文件。清单里的 REPLACE_WITH_DIGEST 是个故意留着不能跑的占位符——提交时用 -p 覆盖，让”这次训练用的是哪份镜像”由 CI 的输出决定，而不是靠谁记得改文件：

argo submit -n intent-mlops workflows/train-workflow.yaml \
  -p image="$REGISTRY/intent-trainer@$DIGEST"

（完整的提交命令见下面 5.2，这里先把 digest 怎么来的说清楚。）

5.2 提交流程

先确认 CRD、controller 和 RBAC 都到位——这三样任何一个缺失，报错信息都长得不像同一类问题：

kubectl get crd workflows.argoproj.io
kubectl get deployment -n argo
kubectl auth can-i create workflows.argoproj.io -n intent-mlops

然后按顺序 apply 身份、再对 Workflow 做服务端干跑：

kubectl apply -f workflows/serviceaccount.yaml
kubectl apply --server-side --dry-run=server \
  -n intent-mlops -f workflows/train-workflow.yaml

--dry-run=server 走完整的 API Server 校验（含 CRD schema 和 webhook），比客户端干跑能多抓一类字段错误。真正提交时把镜像 digest 换成 CI 刚推的那一份：

argo submit -n intent-mlops workflows/train-workflow.yaml \
  -p image="$REGISTRY/intent-trainer@$DIGEST" \
  --watch

--watch 会把 DAG 进度打在终端上。也可以不带它，之后再查：

argo list -n intent-mlops
argo get -n intent-mlops @latest
argo logs -n intent-mlops @latest --follow
argo logs -n intent-mlops @latest train      # 只看某一步

成功判据不止一条，缺一条都不算通过：

  • argo get 里 Status: Succeeded，validate 和 train 两个节点都是 Succeeded；
  • argo logs ... train 末尾能看到 train_mlflow.py 打出的 {"run_id": "..."}；
  • 到 MLflow UI 里能找到这个 run，macro_f1 指标和 intent-model artifact 都在，git_sha / dataset_sha256 参数已记录。

只有第一条满足、后两条不满足，说明训练跑了但没连上 tracking server——问题在 MLFLOW_TRACKING_URI 或网络策略，不在训练代码。

失败时先看什么，按这个顺序：

  1. argo get @latest 的节点树，确认是哪一步、什么阶段挂的；
  2. kubectl describe pod 看事件——ImagePullBackOff 是 digest 或 ECR 拉取权限，CreateContainerConfigError 是 env / secret 引用；
  3. argo logs 看容器实际输出——validate 挂在数据不合格，日志里会有明确的校验失败项，这是门禁生效，不该重试；
  4. 日志正常但步骤 Failed，回到第 3 节查 workflowtaskresults 权限；
  5. train 步骤报 ModuleNotFoundError: No module named 'mlflow'，说明 image 传成了服务镜像而不是 Dockerfile.trainer 构建的训练镜像——见 5.1。

6. 这份清单还缺什么：重试、超时、资源

必须说清楚：仓库里那份是最小可用清单，没有 retryStrategy、没有 activeDeadlineSeconds、没有 resources。放到生产上这三样都要补。

- name: train
  retryStrategy:
    limit: "2"
    retryPolicy: OnTransientError     # 只重试瞬时错误，不重试业务失败
    backoff: {duration: "30s", factor: "2", maxDuration: "5m"}
  activeDeadlineSeconds: 3600         # 超过一小时判失败，防止卡死占资源
  container:
    image: "{{workflow.parameters.image}}"
    command: [python, -m, intent_mlops.train_mlflow]
    resources:
      requests: {cpu: "1", memory: 2Gi}
      limits: {cpu: "2", memory: 4Gi}

三点判断：

  • 重试策略要分步骤设，不能全局一刀切。train 里的网络下载、tracking server 短暂不可用值得重试；validate 是确定性的数据校验，同一份数据重试一百次结果一样，重试只会掩盖问题、拖长反馈。所以 validate 那步应该完全不配 retryStrategy。
  • activeDeadlineSeconds 既可以写在 spec 层（整个 Workflow 的墙钟上限），也可以写在模板层。训练任务最好两层都有：模板层防单步卡死，Workflow 层防整体拖尾。没有它，一个 hang 住的训练能占着 GPU 节点一整晚。
  • resources 不写就是 BestEffort，会被优先驱逐，也无法被调度器正确放置。requests 决定调度，limits 决定被 OOMKill 的边界——这个值必须实测得出。GPU OOM 属于”应该失败并要求改配置或改模型”的那一类，不该进重试循环。

另外两个生产上迟早要加的：podGC（跑完自动清理 Pod，否则命名空间会堆满 Completed）和 ttlStrategy（Workflow 对象本身的保留期）。

7. 幂等、缓存和重试

同一代码、数据、参数组合应生成唯一执行键。重跑任务不能覆盖已经批准的 artifact——这也是上面第 4 节里 s3.key 用 {{workflow.name}} 而不是固定路径的原因。网络下载可以重试，确定性数据验证失败不应重试；GPU OOM 则应失败并要求修改资源或模型，而不是无限循环。

8. 触发策略

  • 代码触发：训练逻辑或依赖变化；
  • 数据触发：新的已验证数据快照；
  • 定时触发：业务定义的训练窗口（Argo 用 CronWorkflow，它内嵌的就是同一份 workflowSpec）；
  • 监控触发：漂移或质量退化；
  • 人工触发：紧急修复和受控回放。

所有触发最终进入同一参数化 Workflow，避免五套不同训练脚本。这正是把 image 和 data-path 提成 spec.arguments.parameters 的价值——换数据、换代码版本都只是换参数，DAG 结构一行不动。

9. 运行元数据

Workflow ID、Git SHA、DVC 数据版本、MLflow Run ID、镜像 digest、资源规格和触发原因必须关联起来。这样才能区分”模型算法退化”与”训练基础设施变化”。

示例里这条链是这么串的：generateName 生成的 Workflow 名是这次运行的 ID；image 参数是镜像 digest；train_mlflow.py 把 git_sha 和 dataset_sha256 记进 MLflow params，把 run ID 打到 stdout（也就进了 argo logs）。缺的一环是反向索引——MLflow run 里没有记 Workflow 名。补法很简单：在 train 模板里多注一个 {name: WORKFLOW_NAME, value: "{{workflow.name}}"}，训练脚本一并 log_param。

10. Argo / Kubeflow Pipelines / Airflow 怎么选

一句话边界：Argo Workflows 是通用的 Kubernetes 原生 DAG 引擎，清单就是 CRD，和集群 RBAC、调度、GitOps 天然一致，适合团队已经在 K8s 上、且训练之外还有别的批处理要编排；Kubeflow Pipelines 底层就跑在 Argo 上，额外给了 Python SDK、组件复用和实验/运行的 UI 追踪，代价是一整套 Kubeflow 组件的运维负担，适合有多个团队反复搭相似 ML 流水线的场景；Airflow 强在时间驱动的调度、丰富的 operator 生态和跨系统编排（数仓、ETL、外部 API），如果训练只是既有数据管道末端的一个节点，用 Airflow 拉起 K8s Pod 往往比再引入一套编排器更实际。三者不是替代关系，选错的代价主要是运维面积，不是能力缺失。

小结

编排系统把训练从一个命令升级为有依赖、有状态、有重试策略且可审计的 DAG；CI 负责代码质量与触发，两者职责互补。仓库里那份两步清单已经能跑通”验证挡住训练、训练写回 MLflow”这条主干，但它离生产还差 artifact 输出、重试、超时和资源声明——这些差距本文都点名了，不要照抄进生产。
