第 7 / 25 节 · 训练、数据与实验

本地运行 mlflow ui 很适合学习，却不适合团队共享。生产式跟踪服务至少要把计算、元数据和大型制品分开。

这一篇搭出来的 Tracking Server，就是下一篇里训练脚本通过 MLFLOW_TRACKING_URI 连接的那个地址。先把服务立起来，第 07 篇再谈怎么往里记实验、怎么比较。

先说清楚本篇的范围：第 1—5 节讲的是架构设计——存储怎么分层、为什么 PostgreSQL 和 S3 各管一半、Helm 装进 Kubernetes 的顺序是什么、入口和权限该怎么收。这部分不是一份能照抄执行的清单，因为 chart 的 values.yaml 字段取决于你的数据库地址、Secret 引用和桶名，给死值只会误导。

如果你现在就想让第 07 篇跑起来，直接跳到第 3 节末尾的”最小可跑通路径”——三条命令，本机 sqlite，五分钟见到 UI。跑通之后再回来读架构部分，你会更清楚它在解决什么问题。

两条路的关系是：最小路径让你现在有个能连的地址；架构部分告诉你为什么那条路不能带进团队。

1. 先看清楚要摆脱的起点

单机跟踪最省事的形态，是让 MLflow 直接把元数据写进本地 SQLite、把 artifacts（制品）落在本地磁盘：

mlflow ui \
  --backend-store-uri sqlite:///mlflow.db \
  --host 0.0.0.0 \
  --port 5000

如果这个 UI 要给别的机器访问（例如挂在一台云主机上让同事打开），还得放开来源限制。这时候换用 mlflow server——--allowed-hosts / --cors-allowed-origins 是挂在 server 子命令下的，且只在默认的 FastAPI/uvicorn 后端生效：

mlflow server \
  --backend-store-uri sqlite:///mlflow.db \
  --host 0.0.0.0 \
  --port 5000 \
  --allowed-hosts "203.0.113.10:5000" \
  --cors-allowed-origins "*"

--cors-allowed-origins "*" 放开所有跨域来源，只适合本机试跑，别带进真实环境。这套起点的问题不在命令本身，而在存储形态：SQLite 文件和本地磁盘绑死在这一台机器上，进程一挂、盘一坏，历史就没了，也没法多副本。下面要做的，就是把这两块存储从计算里拆出去。

2. 为什么要拆分存储

PostgreSQL 适合查询结构化关系，例如某个 experiment 下有哪些 runs、某个 run 记了哪些 metric；S3 适合保存容量较大的不可变文件，比如模型权重、图表、报告。两者职责不同：

  • PostgreSQL（元数据）：experiment、run、parameter、metric，量小但要频繁按关系查询。
  • S3（artifacts / 制品）：模型和大文件，写一次读多次，按对象键取用。

拆开之后，MLflow Server 本身尽量做到无状态——所有持久数据都在库和桶里，Pod 重建、扩容、滚动升级都不影响历史记录。这正是从 SQLite 单机形态往集群形态迁移的核心动作。

关键配置示意：

mlflow server \
  --host 0.0.0.0 \
  --port 5000 \
  --backend-store-uri postgresql://USER:PASSWORD@postgres:5432/mlflow \
  --artifacts-destination s3://example-mlflow-artifacts

注意命令从 mlflow ui 换成了 mlflow server：--backend-store-uri 指向 PostgreSQL，--artifacts-destination 指向 S3 桶。不要把密码直接放进命令或 Helm values。使用 Kubernetes Secret，并优先通过 External Secrets 对接云 Secret Manager。

3. 用 Helm 把它装进 Kubernetes

真正把服务立起来时，与其手写全套 manifest，不如直接用社区维护的 MLflow Helm chart。整体顺序是：准备集群 → 建库 → 建命名空间和 Secret → Helm 安装 → 打通访问。

准备一个集群。生产上是 EKS 之类的托管集群；本地验证可以用 KinD 起一个临时集群：

kind create cluster --name mlops-labs
kubectl config current-context     # 应显示 kind-mlops-labs

这个集群会被后面的篇章用到，记住它的 context 名。 kind create cluster 会把 kubeconfig 的 current-context 切成 kind-mlops-labs。第 10 篇会切到 EKS、第 11 篇会新建一个 kind-kserve-lab——而第 14 篇的训练 Workflow 要求 Argo 与 MLflow 在同一个集群，靠集群内 DNS mlflow.mlflow.svc.cluster.local 连过来。所以要么这里就装在你打算长期用的那个集群上（生产路径是 EKS），要么到第 14 篇时用 kubectl config use-context 切回来。三个集群的对照表见第 10 篇第 2 节。

添加 chart 仓库。使用 community-charts 提供的 MLflow chart：

helm repo add community-charts https://community-charts.github.io/helm-charts
helm repo update

chart 的参数说明在 https://community-charts.github.io/docs/charts/mlflow/usage，具体有哪些 values 以那份文档为准。

建命名空间，把 MLflow 相关资源隔在一起：

kubectl create namespace mlflow

准备 AWS 凭据 Secret，让 Server 能读写 S3 桶：

kubectl create secret generic mlflow-aws-secret \
  --namespace mlflow \
  --from-literal=AWS_ACCESS_KEY_ID=YOUR_KEY \
  --from-literal=AWS_SECRET_ACCESS_KEY=YOUR_SECRET

这里用静态 AWS Key 是为了把链路先跑通。在 EKS 里更推荐让 ServiceAccount 通过 Pod Identity 或 IRSA 拿到指定 S3 路径的权限，彻底不落地静态密钥——见第 5 节。

用 values 文件安装。chart 的所有环境差异（数据库地址、凭据引用、S3 桶、认证方式等）都收敛到一个 values.yaml 里，再交给 Helm：

helm install mlflow community-charts/mlflow \
  --namespace mlflow \
  -f values.yaml

values.yaml 的具体字段取决于 chart 版本和你的环境，需要照官方 usage 文档填自己的数据库 host、Secret 引用和桶名，这里不给死值以免误导。要点只有一个：敏感信息用上一步的 Secret 引用，不要把明文密码写进 values 文件。

只想让第 07 篇跑起来？用这条最小路径

上面这套（Kubernetes + RDS + S3）是”生产形态”，需要真实云资源，而且 chart values 因环境而异。如果你的目的只是让下一篇的实验跟踪有个能连的 server，不必先把这套搭起来——本机起一个就够：

cd example                         # 本篇的相对路径一律以 example/ 为根
pip install -e '.[mlops]'          # 装 mlflow 与 dvc[s3]
mlflow server \
  --backend-store-uri sqlite:///mlflow.db \
  --default-artifact-root ./mlruns \
  --host 127.0.0.1 --port 5000

这条命令会占住当前终端（前台运行），别等它返回。另开一个终端，同样 cd example，先探活再把地址交给训练脚本：

cd example
curl -fsS http://localhost:5000/health          # 返回 OK
MLFLOW_TRACKING_URI=http://localhost:5000 make train-mlflow

成功判据有四条，缺一条就说明没真正跑通：

  1. curl .../health 返回 OK。连不上先看第一个终端的日志——端口被占是最常见的原因（macOS 上 5000 常被 AirPlay 占用，换 --port 5001 即可）。
  2. make train-mlflow 的输出末尾有一行 JSON：{"run_id": "..."}。没有它说明训练根本没起来，问题在数据或依赖，不在 MLflow。
  3. 同时打印出一行 🏃 View run ... at: http://localhost:5000/#/experiments/1/runs/<run_id>。这一行是关键：它证明 run 是写进了 server，而不是退回本地 ./mlruns 目录。如果地址是 file:// 开头，说明 MLFLOW_TRACKING_URI 没生效。
  4. 浏览器打开 http://localhost:5000，intent-classifier 实验下有这条 run，点进去 Metrics 里有 macro_f1、Parameters 里有 git_sha 和 dataset_sha256、Artifacts 里有 intent-model 目录。

第 4 条是和第 07 篇的接口：那一篇要做的实验对比，比的就是这些 metric 和 param。只满足前三条、第 4 条里 artifacts 是空的，第 07 篇会走不下去。

（附录 A 第 4 节用的正是这条路径。）

这条路径不是本篇要教的东西，恰恰是本篇要否定的起点：SQLite 文件和本地磁盘绑死在这台机器上，进程一挂、盘一坏历史就没了，也没法多副本。把它当脚手架——先让第 07 篇的实验对比跑起来，等真的需要多人共享和长期留存时，再回到上面的分层存储方案。别把它带进团队环境。

4. PostgreSQL 不是一个附属容器

教学环境可以把 PostgreSQL 装进集群，生产环境更适合使用 RDS 等托管数据库。以 RDS 为例，Server 连上去之前，库要先建好。装一个 psql 客户端：

sudo apt install postgresql-client -y

连到实例、建出 MLflow 专用的库：

psql -h mlopsdatabase.example.us-east-1.rds.amazonaws.com -U postgres -d postgres
CREATE DATABASE mlflow;

库名 mlflow 要和第 3 节 values 里配的 --backend-store-uri 对上。除了建库，托管数据库还要配好：

  • 自动备份和时间点恢复；
  • Multi-AZ 或明确的可用性目标；
  • TLS 连接；
  • 连接数与连接池；
  • Schema migration 前的备份与兼容性验证。

MLflow Pod 多副本并不等于整个系统高可用，数据库和对象存储同样属于可用性链路。

5. 入口、认证和隔离

装完之后先把访问打通。最直接的方式是端口转发到本地验证：

kubectl port-forward svc/mlflow 5000:80 -n mlflow --address 0.0.0.0

注意 Service 对外暴露的是 80 端口，转发到本地 5000。但 port-forward 只是调试手段，不是对外入口。 MLflow UI 包含实验参数和模型文件，不能裸露到公网。生产上常见方案是在 Ingress 前接入企业 SSO/OIDC 代理，并限制网络来源。

在 EKS 中，让 Server 访问 S3 也不必依赖第 3 节那份静态 Key：给 ServiceAccount 绑定 Pod Identity 或 IRSA，就能拿到指定 S3 路径的权限，避免静态 AWS Key 落地到 Secret 里。

团队规模扩大后还要考虑：

  • experiment 命名规范；
  • 不同团队的 artifact prefix；
  • 删除和保留策略；
  • 审计日志；
  • 开发、测试、生产环境隔离。

6. 可观测性和灾难恢复

基础指标包括请求率、5xx、延迟、Pod 重启、数据库连接、S3 错误和磁盘/备份状态。恢复演练必须验证：数据库恢复后，run 记录引用的 S3 artifact（制品）仍然存在且可读取。元数据和制品分处两套存储，任何一套单独恢复都不够，二者要能对得上。

7. “生产式”不等于“已经生产就绪”

这一点值得说透。用 Helm 把 MLflow 装进 Kubernetes、把元数据放进 PostgreSQL、把制品放进 S3——这套架构已经解决了单机 SQLite 的根本问题：存储职责分离 + 容器化部署，也就是本篇标题里“生产式”真正指的东西。

但它仍然只是一个简化的生产雏形。下面这些，本篇的最小链路里一个都没自动带上：

  • 高可用与冗余；
  • 传输层 TLS/加密；
  • 认证与授权；
  • 备份策略；
  • 监控与可观测性；
  • 生产级 Ingress 配置；
  • 数据库连接池与调优。

镜像升级、认证、备份、Secret、资源限制、监控和恢复演练——缺少任何一项，都会在真实运行中暴露风险。把“架构正确”当成“已经生产就绪”，是这一步最容易踩的坑。

小结

MLflow Tracking Server 是控制入口，PostgreSQL 保存可查询元数据，S3 保存大型制品。搭建顺序是：起集群 → 建库 → 建命名空间和 Secret → Helm 装 chart（配 values）→ 打通访问。先把状态边界设计清楚，再谈副本数量、认证和高可用——这些恰恰是“生产式”雏形还没覆盖的部分。
