第 9 / 25 节 · 训练、数据与实验

Kubernetes 能解决调度和运行问题，却不能修复错误的 API 契约、预处理不一致或损坏的模型。越早在简单环境验证这些问题，排查成本越低。

第 04 篇已经把意图分类模型包成了一个 Flask API 并打进镜像。这一篇不重复”怎么做成 API”，而是回答一个更前置的问题：在把它交给 Kubernetes 或云上弹性 VM 之前，凭什么相信它是对的？ 答案是先在自己的机器上把推理流程和服务契约跑穿——本地环境变量最少、反馈最快，一个 curl 就能定位问题，而不必等镜像推到 registry、Pod 起来、再去翻一堆 controller 日志。

0. 本地跑通推理的最短路径

在讨论”四层验证”之前，先建立一条能反复重放的最短链路。example 仓库里这条链路就是三个 make 目标加一条 curl：

# 1. 装依赖（含 dev 工具）
make install

# 2. 校验数据 → 训练 → 落地 artifact
make train

# 3. 用 gunicorn 在 8080 起服务（与生产同一个 WSGI server）
make serve

make train 会先跑 intent_mlops.validate 校验训练数据，再产出 artifacts/intent-model.joblib 和 artifacts/metadata.json；make serve 背后是 gunicorn --bind 0.0.0.0:8080 --workers 1 --threads 4 'intent_mlops.app:create_app()'——刻意用与线上一致的 WSGI server 而不是 flask run，避免”本地能跑、生产不行”的假验证。

服务起来后，先看两个探针再打推理：

curl -s http://localhost:8080/healthz   # {"status":"alive"}
curl -s http://localhost:8080/readyz    # {"status":"ready","model_version":"..."}

/readyz 返回 ready 才说明模型已经加载进内存；如果模型没找到，它会返回 503 {"status":"not_ready"}，这时打 /predict 也会拿到 503。这一步就把”模型没加载”和”推理逻辑错”两类问题分开了。

一次完整的推理往返：

curl -s -X POST http://localhost:8080/predict \
  -H 'Content-Type: application/json' \
  -d '{"text":"为什么重复扣款"}'

返回体是这一篇要盯住的服务契约：

{
  "label": "billing",
  "confidence": 0.83,
  "model_version": "intent-v1",
  "latency_ms": 4.12
}

多打几条不同意图，确认标签、置信度、模型版本三个字段稳定成形，再决定要不要进容器：

curl -s -X POST http://localhost:8080/predict -H 'Content-Type: application/json' -d '{"text":"我无法登录"}'
curl -s -X POST http://localhost:8080/predict -H 'Content-Type: application/json' -d '{"text":"退款什么时候到账"}'

这条链路能在本地重放，就意味着”训练产物 → 加载 → 契约”这段逻辑已经和基础设施解耦。后面的四层验证，都是在这条链路上加压力、加约束。

1. 四层本地验证

模型层

直接加载 artifact，使用固定样本测试标签、类型和确定性。这里不经过 HTTP，用于区分模型问题与服务问题。

API 契约层

契约不只是”能返回结果”，而是每种输入都返回一个可预测的状态码和结构。用 curl -i 连响应头一起看，逐一验证 /predict 的正常与异常分支：

# 200：合法输入，返回 label / confidence / model_version / latency_ms
curl -i -X POST http://localhost:8080/predict \
  -H 'Content-Type: application/json' \
  -d '{"text":"我无法登录"}'

# 400：缺 text 字段或空字符串
curl -i -X POST http://localhost:8080/predict \
  -H 'Content-Type: application/json' \
  -d '{}'

# 413：text 超长（example 中上限 2000 字符）
curl -i -X POST http://localhost:8080/predict \
  -H 'Content-Type: application/json' \
  -d "{\"text\":\"$(head -c 3000 </dev/zero | tr '\0' 'a')\"}"

对应 example 里 app.py 的分支，至少覆盖这几种状态码：

状态码触发条件返回体
200text 为非空字符串{"label","confidence","model_version","latency_ms"}
400缺字段 / 空串 / 非字符串{"error":"text must be a non-empty string"}
413text 超过 2000 字符{"error":"text is too long"}
503模型尚未加载{"error":"model is not loaded"}
405对 /predict 发 GETFlask 默认 405

这些边界不是靠人肉 curl 一次性验证完就算数，而应该固化成测试。example 的 tests/test_app.py 就把契约钉死了：test_prediction_contract 断言 label ∈ {billing, technical_support, account}、0 ≤ confidence ≤ 1；test_invalid_prediction_input 断言空 JSON 返回 400。推荐进一步用 JSON Schema 或 OpenAPI 把字段类型显式声明出来，而不是让调用方猜测——契约一旦写成机器可校验的，进 K8s 后任何回归都会在测试阶段就暴露。

容器层

docker run --rm --read-only \
  --tmpfs /tmp \
  --memory 512m --cpus 1 \
  -p 8080:8080 intent-api:v1

--tmpfs /tmp 不能省。Gunicorn 的 worker heartbeat 走 tempfile，只读根文件系统下没有可写的 /tmp，进程会直接以 No usable temporary directory found 退出（见附录 B）。K8s 侧的等价写法是给 Pod 挂一个 emptyDir 到 /tmp，仓库的 deployment.yaml 已经这么做了。

验证只读文件系统、非 root 用户和资源限制下仍能启动。确认收到 SIGTERM 后 Gunicorn 能停止接收新请求并完成在途请求。

性能层

用 hey、wrk 或 k6 做小规模基线测试，记录吞吐、p50/p95/p99 延迟、错误率和内存。目的不是证明本机能承担生产流量，而是为后续部署提供对比基线。

2. 健康检查的含义

  • liveness：进程是否卡死，需要重启；
  • readiness：当前实例是否已经加载模型、可以接收流量；
  • startup：大模型启动较慢时，避免 liveness 过早杀死进程。

不要让 liveness 检查数据库、S3 等外部依赖，否则短暂网络故障会触发所有实例同时重启。readiness 可以更严格，但必须设置合理超时。

3. 模型随镜像还是外部加载

方案优点缺点
模型打入镜像原子化、离线启动、回滚直接大镜像、每次模型变化都需构建
启动时下载模型运行时复用、模型更新独立依赖存储、启动慢、需要校验和缓存
挂载共享存储多实例共享一致性、性能和挂载运维复杂

无论哪种方案，都必须固定不可变版本并校验 SHA-256，不能让生产实例下载一个会被覆盖的 latest/model.pkl。

4. 何时选择哪种部署方式

  • 本地进程：开发调试；
  • 单台 VM：低流量内部服务或快速验证；
  • VM + Load Balancer + Auto Scaling：已有成熟 VM 平台的团队；
  • Kubernetes：多服务、频繁发布、统一调度与自愈；
  • KServe / SageMaker：需要标准化管理许多模型及其推理运行时。

这条阶梯的起点——本地进程——只适合验证，不适合承载流量，原因要说清楚，才知道后面每一级到底在补什么：

  • 单机架构：一台机器宕了服务就没了，没有故障转移；
  • 无横向扩展：并发一上来只能靠单进程扛，没有自动扩容；
  • 无负载均衡：所有请求打到同一个端口，没法把流量摊开；
  • 无高可用：没有多副本，没有滚动发布，一次重启就是一次中断。

VM + LB + Auto Scaling 补的是扩展和容错，Kubernetes 在此之上再补统一调度与自愈，KServe 再补模型/推理运行时的标准化——每上一级都是在为上一级没解决的问题买单，而不是”更高级所以更好”。平台复杂度必须匹配实际需求：一个每天几十次请求的小模型，并不会因为进入 Kubernetes 自动变得更可靠，反而多背了一整套需要运维的抽象。本地验证的意义正在于此——先在最便宜的一级把应用本身证明清楚，再按真实流量决定要爬到阶梯的哪一格。

小结

先证明模型、契约、镜像和资源行为正确，再更换运行平台。这样进入 AWS 或 Kubernetes 后，新增变量主要来自基础设施，而不是把应用错误与平台错误混在一起。
