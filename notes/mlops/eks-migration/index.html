第 11 / 25 节 · 服务与部署

迁移到 Kubernetes 时，应用接口和模型逻辑不应同时大改。保持第 04 篇的镜像不变，先改变运行和流量管理方式，才能清楚判断问题来自哪里。

这一步的意义不是让模型更准，而是让发布和运行更标准化：同一个容器在任何节点上以同样方式启动、探活、扩缩容和被路由，团队不再为”某台机器上环境不一样”买单。

为什么离开 EC2 逐台管理

先把上一篇的成果说公道：第 09 篇已经用 user data、Auto Scaling Group（自动扩缩容组）和 systemd 消掉了逐台 SSH——新实例开机自己拉镜像、自己起服务，扩容和替换都不需要人登录。那套方案已经是自动化的，不是手工的。

所以离开它的理由不是”还在手工登录”，而是四个更具体的边界：

  • 发布粒度。ASG 换镜像的最小单位是一台实例：滚动发布靠实例轮替，回滚靠换回旧 launch template 再走一遍轮替，一次几分钟起步。Kubernetes 的最小单位是 Pod，滚动和回滚都是秒级、且 kubectl rollout undo 就是一条命令。
  • 调度密度。EC2 上一台实例通常只跑一个服务，剩余 CPU/内存闲置；Kubernetes 按 requests 把多个工作负载装箱到同一批节点上。服务少的时候这点浪费无所谓，服务多了就是真金白银。
  • 平台统一性。EC2 路径里，推理服务、训练任务、批处理作业各有各的部署方式（ASG、EC2 一次性实例、Lambda 或 cron）。Kubernetes 让它们共用同一套原语和同一套 RBAC——后面第 14 篇的训练 Workflow、第 11 篇的 InferenceService 能落在同一个集群里，正是靠这一点。
  • 服务数量。一两个服务时，ASG + LB 的心智负担明显低于一个 Kubernetes 集群。服务数量是这个决策的主变量：数量少就别迁，迁了是净亏。

Kubernetes 把同样的事情换成**声明式（declarative）**表达——你描述”想要 3 个健康副本、按这个镜像跑、这样对外暴露”，控制面负责把现状收敛到期望状态。由此获得的能力可以归成几类：

  • 声明式部署：期望状态写在清单里，kubectl apply 幂等收敛，回滚只是换回上一版清单；
  • 滚动更新（rolling update）：新旧副本按策略逐步替换，发布不需要停服；
  • 自愈（self-healing）：Pod 崩溃、探活失败或节点丢失时自动重建，无需人工介入；
  • 资源调度：按 requests/limits 把 Pod 放到有容量的节点上；
  • 服务发现（service discovery）：Service 提供稳定的集群内名字和虚拟 IP，副本 IP 变化对调用方透明；
  • 弹性伸缩：副本数随负载增减，而不是靠手动加机器；
  • 统一的容器管理：所有工作负载用同一套原语（Pod / Deployment / Service）描述和运维。

迁移买到的是这套通用控制面，而不是更好的模型。模型质量、数据版本、漂移检测这些问题，Kubernetes 一个都不负责（见下文第 7 节）。

版本基线与前置条件

本系列以 Amazon EKS/Kubernetes 1.34.x 为目标，CI 推荐 kubectl 1.34.x；本地使用 kubectl 1.35.0 和其内置 Kustomize 5.7.1 验证清单。官方允许 kubectl 与 API Server 相差一个 minor，但 CI 固定相同 minor 更容易复现。

EKS 的实时支持版本不要从文章硬编码，应在创建集群前查询：

aws eks describe-cluster-versions --output table
kubectl version --output=yaml

示例还要求 Metrics Server、名为 traefik 的 IngressClass，以及可用的 ECR 拉取权限。Kubernetes/EKS、KServe、Argo 和监控组件的完整矩阵见附录 D。

整条请求路径不变，只是把”EC2 + ALB”换成”托管负载均衡 + Traefik + Service”：

1. 复用第 04 篇的镜像

迁移的前提是镜像不动。第 04 篇已经把 Intent API 打成一个自包含的容器：以 python:3.12-slim 起步，pip install . 装好依赖后在构建期先校验数据、再训练、把模型固化进镜像，最后以非 root 用户用 gunicorn 对外提供 HTTP 服务。要点只有两条——运行期不再联网装东西，容器一启动就能对外服务：

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    MODEL_PATH=/app/artifacts/intent-model.joblib \
    MODEL_METADATA_PATH=/app/artifacts/metadata.json

WORKDIR /app
COPY pyproject.toml README.md ./
COPY src/ ./src/
COPY data/ ./data/
RUN pip install --no-cache-dir . && \
    python -m intent_mlops.validate && \
    python -m intent_mlops.train && \
    useradd --create-home --uid 10001 appuser

USER 10001:10001
# 容器对外监听 8080，与下文 Deployment 的 containerPort 一致
EXPOSE 8080
CMD ["gunicorn", "--bind", "0.0.0.0:8080", "--workers", "1", "--threads", "4", "intent_mlops.app:create_app()"]

构建产物推到 ECR，供集群按 digest 拉取（docker buildx build 出镜像后 tag 成 ECR 仓库地址并 push）。到 Kubernetes 这一层，我们引用的是不可变的 @sha256:...，而不是会漂移的 :latest 标签——这是保证”每个副本跑的是同一份代码”的关键。

2. 创建托管的 EKS 集群

EKS 的价值在于控制面托管：API Server、etcd、调度器由 AWS 跨可用区运行和升级，你只管理数据面的节点组。集群本身用 Terraform 声明（基础设施即代码，Infrastructure as Code），而不是手点控制台：

cd infra-eks-terraform
terraform init
terraform validate
terraform apply -auto-approve -var-file=variables.tfvars

集群就绪后，把访问凭据写进本地 kubeconfig，kubectl 才能对接这个集群：

aws eks update-kubeconfig --name <cluster-name> --region ap-southeast-1
kubectl config current-context     # 应显示 arn:aws:eks:...:cluster/<cluster-name>
kubectl get nodes

这条命令会把 kubeconfig 的 current-context 切到 EKS。如果你按第 06 篇在 KinD 上装过 MLflow（context kind-mlops-labs），从这一篇起当前集群就不再是它了。整个系列会碰到三个集群，kubectl config get-contexts 随时能看清自己在哪一个：

篇章目标集群切换命令
06（MLflow）KinD mlops-labs 或你的 EKSkubectl config use-context kind-mlops-labs
10（本篇）、14（Argo 训练）EKSkubectl config use-context arn:aws:eks:...:cluster/<name>
11（KServe 实验）KinD kserve-labkubectl config use-context kind-kserve-lab

第 14 篇的训练 Workflow 要求 Argo 与 MLflow 在同一个集群（它按集群内 DNS mlflow.mlflow.svc.cluster.local 连 tracking server）。所以真正要跑通那一篇时，MLflow 和 Argo 都得装在这里的 EKS 上，第 11 篇那个 kserve-lab 只是个用完即弃的旁支。

aws eks describe-cluster-versions 查到的可用版本，决定 Terraform 变量里该填哪个 K8s minor——版本从查询结果来，不从教程硬编码。

3. Deployment 与 Service

Deployment 声明期望副本数与 Pod 模板，Service 给这组 Pod 一个稳定的集群内入口。下面是简化后的核心字段，与 example/deploy/base 的完整清单对齐（完整清单还带 serviceAccountName、terminationGracePeriodSeconds、securityContext 等生产必需项）：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: intent-api
  labels: {app: intent-api}
spec:
  replicas: 3
  strategy:
    rollingUpdate: {maxSurge: 1, maxUnavailable: 0}
  selector:
    matchLabels: {app: intent-api}
  template:
    metadata:
      labels: {app: intent-api}
    spec:
      serviceAccountName: intent-api          # 绑定 IRSA/Pod Identity，见第 6 节
      terminationGracePeriodSeconds: 30
      securityContext:
        seccompProfile: {type: RuntimeDefault}  # restricted 策略强制要求
      volumes:
        - name: tmp                             # 只读根文件系统下 gunicorn 需要可写 /tmp
          emptyDir: {medium: Memory, sizeLimit: 64Mi}
      containers:
        - name: api
          image: 123456789012.dkr.ecr.ap-southeast-1.amazonaws.com/intent-api@sha256:...
          ports:
            - {name: http, containerPort: 8080}
          readinessProbe:
            httpGet: {path: /readyz, port: http}   # 就绪才接流量
            periodSeconds: 5
          livenessProbe:
            httpGet: {path: /healthz, port: http}  # 卡死才重启
            periodSeconds: 10
          volumeMounts:
            - {name: tmp, mountPath: /tmp}
          resources:
            requests: {cpu: 250m, memory: 256Mi}
            limits: {cpu: "1", memory: 512Mi}
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            runAsNonRoot: true
            capabilities: {drop: ["ALL"]}
---
apiVersion: v1
kind: Service
metadata:
  name: intent-api
  labels: {app: intent-api}
spec:
  selector: {app: intent-api}
  ports:
    - {name: http, port: 80, targetPort: http}

几个容易踩坑的点：

  • readiness 和 liveness 分工不同。示例用 /readyz 做就绪探针（未就绪就不进流量），/healthz 做存活探针（真卡死才重启）；两者混用会让”启动慢”被误判成”进程死了”而反复重启。
  • 镜像用 digest 固定，不用可变 tag，保证每个副本一致。
  • requests 影响调度和 HPA 计算，limits 必须通过压测确定，不能随意复制模板值。
  • Service 靠 selector 匹配 label 找到后端 Pod，用命名端口 http 而不是写死数字——这就是”服务发现”：调用方只认 intent-api 这个名字，副本怎么增删漂移都无感。

用 Kustomize 组织清单，一条命令渲染并下发整组资源：

cd example        # 本篇的相对路径一律以 example/ 为根
kubectl apply -k deploy/base
kubectl get all -n intent-mlops

kustomization.yaml 汇总了 serviceaccount / deployment / service / ingress / hpa / pdb 六份资源，作为一个整体版本化和发布。它里面写了 namespace: intent-mlops，所以每份清单不必各自重复 metadata.namespace，apply -k 也不用再带 -n——命名空间归属由这一处统一决定。

4. Traefik 入口

集群内路由由 Traefik 承担。先用 Helm 把 Traefik 作为 Ingress 控制器装进集群，它会在 AWS 上自动申请一个负载均衡器作为对外入口：

helm repo add traefik https://traefik.github.io/charts
helm repo update
helm install traefik traefik/traefik --namespace traefik --create-namespace
kubectl get pods -n traefik        # 确认控制器 Running
kubectl get svc  -n traefik        # 看它拿到的 LoadBalancer 地址

然后用一份标准 Ingress 把域名和路径绑到 intent-api Service 上，ingressClassName: traefik 指定由 Traefik 处理：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: intent-api
spec:
  ingressClassName: traefik
  rules:
    - host: intent-api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: intent-api
                port: {number: 80}

分工要拎清：AWS Load Balancer 负责把外部流量送进集群的入口控制器，Traefik 负责集群内按 host/path 把请求路由到对应 Service。示例统一走 Kubernetes 原生 Ingress（而非 Traefik 私有的 IngressRoute CRD），可移植性更好。生产环境还要在这一层补上 TLS、认证、超时、请求体大小限制和 rate limit（限流）。

5. 滚动发布与自愈

滚动更新策略写在 Deployment 里，配合就绪探针实现”先起新、再撤旧”的零停机替换：

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1

maxUnavailable: 0 保证替换过程中可用副本不掉；maxSurge: 1 允许临时多起一个新 Pod。新 Pod 通过 readiness 后才接流量，旧 Pod 配合 preStop 和 terminationGracePeriodSeconds: 30 优雅退出。模型启动时间较长时，加 startupProbe 把”慢启动”和”卡死”区分开，避免启动期被 liveness 误杀。

自愈是另一条独立于发布的保障：Pod 进程退出、liveness 连续失败、或节点整个丢失时，控制器都会按期望副本数自动重建，无需人工登录处理——这正是 EC2 时代要靠人盯的部分。

需要强调：滚动成功只说明 Pod 健康，不说明新模型业务指标更好。 更安全的方式是 Canary（金丝雀发布）：少量流量进入新版本，验证错误率、延迟和预测分布后再放量。

6. 自动扩缩容

HPA（Horizontal Pod Autoscaler，水平 Pod 自动扩缩容）可以基于 CPU/内存或 Prometheus 自定义指标扩容。对推理服务，更贴切的信号是每 Pod 并发、请求率或队列深度。示例先用最通用的 CPU 版本：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: intent-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: intent-api
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: {type: Utilization, averageUtilization: 65}

CPU 目标为 requests 的 65%，所以容器必须设置 CPU requests，集群也必须提供 metrics.k8s.io（Metrics Server）。验证方式：

kubectl get --raw /apis/metrics.k8s.io/v1beta1/nodes >/dev/null   # 有 Metrics Server 才有返回
kubectl get hpa -n intent-mlops

扩容速度还受节点容量制约：Pod 想扩但没有可调度的节点时，得靠 Cluster Autoscaler 或 Karpenter 补节点。如果模型占用大量内存，新 Pod 在模型下载和加载完成前无法接收请求，应预留容量并考虑预热，不要把 scale-to-zero 当作默认答案。

7. EKS 运行边界

  • ECR 保存镜像，按 digest 拉取；
  • Pod Identity/IRSA 通过 serviceAccountName 给 Pod 授予 AWS 权限，避免塞长期密钥；
  • Secret Manager/External Secrets 管理凭证；
  • NetworkPolicy 限制东西向访问；
  • PodDisruptionBudget（对应清单里的 pdb.yaml）避免节点维护时同时中断所有副本；
  • 多可用区节点分布提升容错；
  • Prometheus、日志平台与 tracing 形成可观测性。

8. Kubernetes 没有自动解决的问题

它不负责判断模型好坏、管理数据版本、审批模型、检测概念漂移，也不会自动建立反馈闭环。它提供的是可靠运行工作负载的通用控制面。

小结

EKS 将逐台服务器管理转化为声明式工作负载管理，并提供自愈、服务发现和滚动发布。迁移的意义不在于模型更准，而在于发布和运行更标准化。但团队仍需自己设计镜像不可变性、模型版本、容量、渐进发布和模型质量监控。
