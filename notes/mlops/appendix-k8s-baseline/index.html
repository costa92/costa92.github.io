Kubernetes 清单能被 YAML 解析，并不代表它一定能被目标集群接受。内置 API、CRD、控制器、云厂商插件和客户端都有独立的版本边界。本附录给出本系列的可复现基线，以及部署前必须确认的运行条件。

1. 本系列使用的版本

下表是本文档与示例清单的教学、验收基线，不表示所有组件永远只能使用这些版本。

组件本系列基线说明
Kubernetes API Server / Amazon EKS1.34.x目标集群 minor；patch 与 EKS eks.<n> platform version 由 AWS 持续更新
kubectlCI 推荐 1.34.x；本地验证为 1.35.0官方支持与 API Server 相差不超过一个 minor，生产 CI 仍建议使用相同 minor
Kustomizekubectl v1.35.0 内置 v5.7.1本系列使用 kubectl kustomize，避免独立版本产生差异
KServev0.18.0，Standard modeKServe 0.18 要求 Kubernetes 1.32+；传统分类模型不需要 Knative scale-to-zero
Argo Workflowsv4.0.5Workflow CR 使用 argoproj.io/v1alpha1；4.0 的完整 CRD 使用 server-side apply
Prometheus Operatorv0.90.1示例 CR 使用 monitoring.coreos.com/v1；0.84+ 要求 Kubernetes 1.25+
Ingress ControllerTraefik 3.xIngress 仅声明路由，集群必须已有名为 traefik 的 IngressClass；Middleware CRD 见第 12 篇（v3 的字段是 ipAllowList，v2 叫 ipWhiteList）
cert-managerv1.20.2KServe webhook 与入口 TLS 共用一套；本地演示与生产同版本
Istio（可选）1.22+仅在需要服务网格时安装；networking.istio.io/v1 与 security.istio.io/v1 自 1.22 起为稳定版本，更早版本用 v1beta1（字段结构不变）。sidecar 注入状态必须纳入 GitOps，见下方说明
Argo CD（可选）2.xGitOps 收敛，Application 使用 argoproj.io/v1alpha1；见第 15 篇
Metrics Server与 EKS 1.34 兼容的受支持版本CPU HPA 依赖 metrics.k8s.io，未安装时 HPA 不会获得 CPU 数据

选择 1.34 的原因是它处于 2026-07-15 的上游和 EKS 标准支持范围内，同时满足 KServe 0.18 的最低版本。EKS 支持窗口会变化，新建集群前必须以 AWS 返回结果为准：

aws eks describe-cluster-versions \
  --query 'clusterVersions[].{version:clusterVersion,status:status,end:endOfStandardSupportDate}' \
  --output table

不要只记录 1.34。EKS platform version、CoreDNS、VPC CNI、kube-proxy、节点 AMI 和操作系统也必须进入集群版本清单。

Istio：注入状态必须和网格清单一起进 GitOps

这一条单独拎出来，因为它的失败方式特别安静。PeerAuthentication、AuthorizationPolicy、DestinationRule、VirtualService 这些网格清单，全部依赖 Pod 里有 sidecar 才生效。没有 sidecar，它们不会报错、不会被拒绝、kubectl get 一切正常——它们只是什么都不做。于是一条 PeerAuthentication: {mtls: {mode: STRICT}} 看起来已经强制了 mTLS，实际流量还是明文；一条限制调用方的 AuthorizationPolicy 看起来已经生效，实际谁都能调。你会得到一份读起来很安全的 Git 仓库，和一个完全没有这些保护的集群。

注入由两处状态共同决定：命名空间上的 istio-injection=enabled（或 istio.io/rev=<revision>）标签，以及 Pod 模板上的 sidecar.istio.io/inject 注解。这两处必须和网格清单在同一个 Git 仓库、由同一次 GitOps 同步推进，而不是靠谁在终端里敲一条 kubectl label namespace。手工打的标签不在任何清单里，集群重建、命名空间重造、或换一个环境部署时不会被带上，网格策略就静默失效了。

具体要求三条：

  • 命名空间的注入标签写进 Kustomize/Helm 的 Namespace 清单，纳入版本控制；

  • 部署后验证注入真的发生了，而不是只验证策略对象存在：

    # READY 列应是 2/2（业务容器 + istio-proxy），不是 1/1
kubectl get pods -n intent-mlops
kubectl get pods -n intent-mlops -o jsonpath='{.items[*].spec.containers[*].name}'

  • 升级 Istio 用 revision 标签（istio.io/rev）而不是原地改 istio-injection，且改完 revision 必须重启工作负载——sidecar 只在 Pod 创建时注入，已经在跑的 Pod 不会自动换版本。

第 11 篇本地演示里的 Istio 只当 ingress controller 用，不启用注入，因此不受这条约束；一旦真的启用服务网格（第 12 篇），这条就是硬要求。

KServe 内置 sklearn runtime 的版本约束

KServe v0.18.0 的 sklearnserver 镜像把 scikit-learn 钉在 ~=1.5.1（>=1.5.1,<1.6），joblib 为 >=1.4,<2。而本系列示例工程 example/pyproject.toml 声明的是 scikit-learn>=1.6,<2——两者不兼容，joblib 制品不保证跨 sklearn 大版本反序列化。

因此本系列的选择是：走 KServe 路径时必须构建使用同一依赖锁的自定义 ServingRuntime，不使用内置的 kserve-sklearnserver。 只把制品改名成 model.joblib 放进 storageUri 是不够的——文件名对上只说明 runtime 找得到文件，说明不了它读得懂文件。理由与替代方案（把训练端降到 1.5.x）见第 11 篇第 1 节。

升级 KServe 前必须重新核对这个版本：

# 从内置 runtime 的镜像里直接读，别信文档
kubectl get clusterservingruntime kserve-sklearnserver -o jsonpath='{.spec.containers[0].image}'
docker run --rm --entrypoint python <上面那个镜像> -c "import sklearn; print(sklearn.__version__)"

kubectl api-resources | grep -E 'InferenceService|Workflow|ServiceMonitor|PrometheusRule'
kubectl explain inferenceservice.spec.predictor --api-version=serving.kserve.io/v1beta1
kubectl get crd \
  inferenceservices.serving.kserve.io \
  workflows.argoproj.io \
  servicemonitors.monitoring.coreos.com \
  prometheusrules.monitoring.coreos.com

3. 集群前置条件

原生 Deployment 路径需要：

  • 至少三个可调度工作节点，或能容纳三个 Pod 的多可用区节点组；
  • ECR 拉取权限、VPC CNI、CoreDNS 和 kube-proxy 正常；
  • Metrics Server，否则 CPU HPA 的 TARGETS 会显示 <unknown>；
  • Traefik 3.x 及 traefik IngressClass，或把清单改成集群实际的 class；
  • IRSA 或 EKS Pod Identity。示例 ServiceAccount 注解是 IRSA 写法，Pod Identity 应创建 association；
  • 日志、指标后端，以及限制工作负载权限的 Pod Security / NetworkPolicy 策略。

KServe 路径另外需要 KServe CRD、controller、ClusterServingRuntime 和证书组件。本文选择 Standard mode，它创建普通 Deployment、Service、Ingress 和 HPA；只有明确需要 scale-to-zero、Knative revision 或其流量能力时才选择 Knative mode。

Argo 与监控清单不会自行安装控制器。必须先安装固定版本的 Argo Workflows 和 Prometheus Operator，再提交 Workflow、ServiceMonitor 与 PrometheusRule。

4. 推荐安装顺序

CRD 和 controller 必须先就绪。直接对没有 CRD 的集群执行 dry-run，会得到 “no matches for kind”，这不是业务清单字段错误。

生产环境不要执行未经审阅的 curl | bash，也不要使用 latest。下载固定 release，验证 checksum/签名，在非生产集群安装并导出最终渲染结果，再通过 GitOps 推进。

5. 部署前检查

# 客户端、服务端及内置 Kustomize
kubectl version --output=yaml
kubectl config current-context

# 节点、核心 add-on 和资源指标
kubectl get nodes -o wide
kubectl get pods -n kube-system
kubectl get --raw /apis/metrics.k8s.io/v1beta1/nodes >/dev/null

# 入口、CRD 与权限
kubectl get ingressclass
kubectl get crd | grep -E 'kserve|argoproj|monitoring.coreos.com'
kubectl auth can-i create deployments -n intent-mlops
kubectl auth can-i create inferenceservices.serving.kserve.io -n intent-mlops

建议单独创建命名空间，不把教学服务放进 default：

kubectl create namespace intent-mlops --dry-run=client -o yaml | kubectl apply -f -
kubectl label namespace intent-mlops \
  pod-security.kubernetes.io/enforce=restricted --overwrite

应用示例前替换镜像 digest、域名、AWS Account/Role 和模型 S3 URI：

cd example
kubectl kustomize deploy/base > /tmp/intent-api.yaml
kubectl apply --server-side --dry-run=server \
  -n intent-mlops -f /tmp/intent-api.yaml
kubectl apply -n intent-mlops -f /tmp/intent-api.yaml

6. 部署后验收

kubectl rollout status deployment/intent-api -n intent-mlops --timeout=5m
kubectl get pod,svc,ingress,hpa,pdb -n intent-mlops
kubectl get events -n intent-mlops --sort-by=.lastTimestamp
kubectl top pods -n intent-mlops
kubectl port-forward -n intent-mlops service/intent-api 8080:80
curl -fsS http://localhost:8080/readyz
curl -fsS http://localhost:8080/metrics | grep intent_api

验收不能只看 Pod 为 Running：

  • Deployment 的 available replicas 等于期望副本；
  • readiness 返回模型版本，滚动期间无不可用副本；
  • HPA 能显示 CPU 数据，不能长期为 <unknown>；
  • IngressClass、DNS、TLS 和负载均衡健康检查一致；
  • PDB 不阻止计划内节点维护，也不会允许一次驱逐全部副本；
  • ServiceMonitor 被 Prometheus 选中，PrometheusRule 成功加载；
  • 模型 S3 URI 与镜像均不可变，可从 Git 提交定位到实际运行版本。

7. EKS 与组件升级

Kubernetes minor 不应跨级升级，EKS 也不能原地降级。推荐顺序：

  1. 把当前 minor 更新到最新 patch，备份 GitOps 状态和重要数据；
  2. 检查 API 弃用、admission webhook、CRD stored versions 和 controller 兼容矩阵；
  3. 在预生产环境执行 server-side dry-run 和端到端回归；
  4. 升级 EKS control plane 一个 minor；
  5. 升级 VPC CNI、CoreDNS、kube-proxy 和 CSI 等 add-on；
  6. 逐节点组 drain、升级 AMI/kubelet，确认 PDB 和容量允许驱逐；
  7. 按官方顺序升级 Argo、KServe、Prometheus Operator 及 CRD；
  8. 重跑推理契约、HPA、Ingress、监控、Canary 和回滚演练。

升级前至少执行：

kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis || true
kubectl api-resources >/tmp/api-resources-before.txt
kubectl get crd -o yaml >/tmp/crds-before.yaml

官方参考：Kubernetes version skew、EKS 版本生命周期、KServe 0.18 Quickstart、Argo Workflows 安装、Prometheus Operator 兼容性。
