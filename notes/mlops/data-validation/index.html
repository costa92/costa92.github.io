第 14 / 25 节 · 数据与训练流水线

前两篇把管道修好了：第 11 篇用 KServe 标准化了模型服务，上一篇又补齐了入口网关与东西向流量。但管道再规整，也只保证这个模型能被正确地端出去，对”端出去的是不是一个用垃圾数据训出来的模型”没有意见。往上游走一层问题就换了个样子——DVC 能恢复某一版数据，却不能判断这版数据是否值得训练。数据质量门禁要在昂贵训练开始前，拒绝结构错误、分布异常或存在泄漏的数据。

训练是整条链路里最贵的一步，它前面必须站一道会说”不”的门。 门禁不需要复杂，需要的是确定性——同一份数据今天拦下来、明天也拦下来；同一条规则，本地跑和 CI 跑给出同一个答案。

1. 四层验证

拆成四层，是为了让每一条失败都能归到明确的责任人：

文件层：文件存在、格式可读、编码正确
Schema 层：字段、类型、非空、枚举、长度
统计层：类别比例、分位数、异常值、重复率
语义层：标签定义、泄漏、时间边界、隐私

前两层失败通常是工程问题（导出脚本挂了、列名改了），统计层是数据问题，语义层是业务问题（标签定义被人悄悄改了）。四层由浅入深，也由便宜到昂贵。

本系列的示例验证器覆盖前三层，语义层留给评审。它只有一个函数 validate_dataset(path)。

下面先按最初的硬编码版本逐段讲——先看清每条规则在挡什么，再谈把阈值抽出去（第 5 节）。仓库里的当前版本已经改从 thresholds.yaml 读，默认值与这里一字不差：

# src/intent_mlops/validate.py（初版：阈值硬编码，便于逐条讲解）
EXPECTED_LABELS = {"billing", "technical_support", "account"}
DEFAULT_DATA_PATH = Path("data/intents.csv")


def validate_dataset(path: Path) -> dict:
    if not path.exists():
        raise ValueError(f"dataset does not exist: {path}")

    data = pd.read_csv(path)
    if list(data.columns) != ["text", "label"]:
        raise ValueError("dataset columns must be exactly: text,label")
    if data.empty:
        raise ValueError("dataset must not be empty")
    if data"text", "label".isna().any().any():
        raise ValueError("text and label must not contain null values")

文件层 + Schema 层，四个检查各对应一类真实故障：path.exists() 挡住”DVC 没 pull 就直接训练”；data.empty 挡住”导出脚本成功但结果零行”——最阴险的一类，因为文件存在、格式合法；isna() 挡住空值，它进 TF-IDF 会变成字符串 "nan"，训练不报错、模型学到一个假类别。

值得单说的是列名比较用了顺序敏感的相等而不是 set(...) 包含关系。这是有意的严格：多一列 source、或写成 label,text 都会被拦下。宽松版本更友好，但会让”列变了”这种契约变更静默通过。

data["text"] = data["text"].astype(str).str.strip()
data["label"] = data["label"].astype(str).str.strip()
if (data["text"].str.len() < 2).any():
    raise ValueError("every text value must contain at least two characters")
if data["text"].duplicated().any():
    raise ValueError("duplicate text samples are not allowed")

统计层，先 strip() 再检查——真实数据里”看起来非空、其实是几个空格”的行大量存在，不去空白则长度检查形同虚设。

  • 最小长度 2：单字符对字符级 n-gram（第 03 篇的 analyzer="char", ngram_range=(2, 4)）没有信息量。这个阈值跟着特征工程走——换成词级 n-gram，合理下限就变成”至少一个词”。
  • 重复文本直接失败：这是最接近”防泄漏”的一条。同一条文本出现两次，train_test_split 有相当概率把它一份放训练、一份放测试，指标凭空虚高；30 行的数据集上一条重复就能把 macro-F1 抬起一大截。这只是泄漏防护的最弱一环，见第 3 节。
labels = set(data["label"].unique())
if labels != EXPECTED_LABELS:
    raise ValueError(f"expected labels {sorted(EXPECTED_LABELS)}, got {sorted(labels)}")

counts = data["label"].value_counts().to_dict()
if min(counts.values()) < 5:
    raise ValueError("each label must contain at least five samples")

return {
    "rows": int(len(data)),
    "labels": {key: int(value) for key, value in sorted(counts.items())},
    "max_text_length": int(data["text"].str.len().max()),
}

语义层的入口，也是最该被讨论的两行。

标签集合用双向相等（!=）而不是子集判断，两种情况都会红：出现没见过的标签（拼错 techincal_support、上游新增类别），以及某个已知标签一条都没有了。后一种是子集检查会漏掉的——数据只剩两类，训练照样跑出一个二分类模型，线上收到 technical_support 的请求它永远不会预测，而指标看起来都正常。

每类最少 5 条，只是为了让第 03 篇的 train_test_split(test_size=0.3, stratify=...) 在技术上跑得起来：分层切分要求每个类别在两侧都至少落到 1 条，少于 5 条时 sklearn 会直接抛错或把某个类别整个划到一侧。

必须说清它换不来什么。 测试集里有 1 条样本，不等于这个类别的 recall 有意义——单条样本的 recall 只能取 0 或 1，它衡量的是运气而不是模型。哪怕按当前数据集每类 10 条、测试集落到 3 条，recall 的取值也只有 0 / 0.33 / 0.67 / 1 四档，换个 random_state 就能抖动三分之一。所以第 03 篇那个 macro-F1 验证的是流水线形状（数据读得进、Pipeline fit 得了、指标算得出、文件落得下），不验证模型质量，更不能拿去和另一个模型比高低。

真实项目的样本量门槛不该这样倒推，而应该反过来问：我要在多大的置信区间内检出多大的效果差异？ 从这里推出每类需要多少条评估样本，再加上交叉验证（第 07 篇）来降低单次切分的方差。5 这个数字在这里的全部作用，是让示例仓库的命令能跑通。

返回值也不是装饰：这份摘要会被 train() 整体塞进 metadata.json 的 validation 字段，门禁的副产品成了模型的溯源证据。

跑一次

make validate 背后就是 python -m intent_mlops.validate，读 DATA_PATH、默认 data/intents.csv，摘要打到 stdout。当前这份 30 行、三个标签各 10 条的数据集：

$ cd example && make validate
python -m intent_mlops.validate
{
  "rows": 30,
  "labels": {
    "account": 10,
    "billing": 10,
    "technical_support": 10
  },
  "max_text_length": 11
}

（max_text_length 为 11，来自”如何恢复已经停用的账户”这类最长样本。）

故意把一条 billing 改成 bulling 再跑，就是门禁生效的样子：

$ make validate
python -m intent_mlops.validate
ValueError: expected labels ['account', 'billing', 'technical_support'], got ['account', 'billing', 'bulling', 'technical_support']
make: *** [Makefile:11: validate] Error 1

注意 Makefile 里 train: validate 这条依赖——训练目标以校验为前置条件，校验非零退出，训练根本不会启动。门禁不靠自觉调用，靠依赖关系强制。

验证输出要落盘

打印到日志的摘要，下次构建就冲掉了。dvc.yaml 把它固化成了真正的 pipeline 产物：

stages:
  validate:
    cmd: python -m intent_mlops.validate > artifacts/validation.json.tmp &&
      mv artifacts/validation.json.tmp artifacts/validation.json
    deps:
      - data/intents.csv
      - src/intent_mlops/validate.py
      - thresholds.yaml
    outs:
      - artifacts/validation.json
  train:
    deps:
      - artifacts/validation.json      # 这一行才让 train 成为下游节点
      - thresholds.yaml

三个好处：validation.json 进了 DVC 产物追踪，可按版本回溯；deps 同时列了数据、验证代码和阈值配置，改任意一个 DVC 都知道要重跑（很多人只列数据，结果改了规则却复用旧结果）；train 把 artifacts/validation.json 列进 deps，于是”校验没通过就没有这个文件、train 就跑不了”成为 DAG 事实。

中间那两点很容易写错，值得单说。

一是共享输入不等于上下游依赖。如果 train 只列了 data/intents.csv 和 validate.py（很常见的写法），它和 validate 只是碰巧读同一批文件，DAG 上根本没有连边——dvc repro train 会直接跳过校验去训练。要让”校验是训练的前置条件”成立，train 必须依赖 validate 的产物。

二是先重定向再执行会先把文件截断。cmd: ... > artifacts/validation.json 的 shell 语义是”先建/清空文件，再跑命令”，所以校验失败时留下的是一个空文件，而不是”文件不产生”。写成先输出到 .tmp 再 mv，才能拿到”要么是完整的旧版本、要么是完整的新版本”这个原子语义。

为什么不用 Great Expectations 或 pandera

两个都是成熟方案。Great Expectations（数据质量框架）提供表达力很强的期望套件（Expectation Suite）和自动生成的数据文档；pandera（DataFrame 校验库）用声明式 schema 装饰 pandas 函数，几行就能写完上面大半个文件。规则涨到上百条、需要多人维护、需要给非工程角色看报告时，它们明显比手写强。

本系列坚持手写是两个取舍：依赖最小——训练闭环只依赖 joblib / pandas / scikit-learn / PyYAML，Great Expectations 会带来一个不小的依赖树和自己的配置目录（context、datasource、checkpoint），对一个 30 行 CSV 是过度设计；门禁逻辑可读——40 行 Python 能逐行讲清每条规则的动机，YAML 期望套件读出来的是”有哪些规则”，读不出”为什么是这个数”。

切换标准也给出来：规则超过二三十条、需要跨表一致性检查、或要把质量报告给数据团队之外的人看时，就该换现成框架。

2. 基线与变化检查

Schema 正确不代表分布正常。上面的验证器有个根本局限：它只看当前这一份数据，不看它和上一版的关系。

所以第二道门是对比门：新数据要和一份”已批准基线”比较。基线就是上一个通过评审、并训出了在线模型的那版数据摘要——冻结成 artifacts/validation.baseline.json，也可以直接取线上模型 metadata.json 里的 validation 字段。逐个指标说清怎么算、超了怎么办：

指标怎么算建议阈值超了怎么办
总样本量变化固定抽取窗口内、去重后的有效样本量，与基线求 (new - base) / base增长 > 50% 警告；缩减 > 10% 失败（示例起始值，见下方推导说明）两个方向都要求给出解释：对上已知变更事件（去重规则调整、合规删除、时间窗口变化、渠道上下线）就放行并更新基线，对不上就查管道
类别比例变化每个标签的 count / rows，与基线求绝对差的最大值（max|p_new - p_base|）> 0.05 警告；> 0.15 失败警告时人工确认是真实业务变化还是采样偏差；失败时挂起，要求提供变化说明后再放行
文本长度分布p50 / p95 / max 字符数，与基线比相对变化p95 变化 > 30% 警告通常意味着来源换了（客服工单 vs App 反馈），要重新评估特征是否还合适
重复率1 - nunique(text) / len(text)（本系列要求为 0）> 0 失败去重后重跑；若重复来自上游 join 放大，修 join 而不是简单 drop_duplicates
空文本占比(text.str.len() < 2).mean()> 0 失败先定位是采集端截断还是清洗规则漏了
新词率（OOV）切 n-gram 后不在基线词表中的 token 占比> 20% 警告（示例值）词表老化，模型对新表达无感知，是”该重训了”的早期信号
来源覆盖率按 source 分组计数，检查每个已知来源是否都有样本任一来源为 0 则失败某个渠道整体缺失，几乎必然是采集任务挂了

OOV（Out-Of-Vocabulary，未登录词率） 这一行值得解释一句：模型训练时会固化一份词表（本系列是第 01 篇讲的那些 2–4 字符 token），推理时不在这份词表里的 token 会被直接丢弃——它们对预测毫无贡献，模型等于没看见。OOV 率就是新数据里被丢弃的 token 占比。它只适用于基于固定词表的文本特征（TF-IDF、词袋），对数值特征或用子词编码的模型（BERT 一类）不是这个含义。局限也很直白：它衡量的是”模型看不懂多少”，不是”模型会答错多少”——新词可能全是无关紧要的语气词，也可能正好是新业务的关键词，光看比例分不出来。

（示例数据集只有 text,label 两列，来源覆盖率在本仓库没有对应字段，列在这里是因为真实项目几乎一定会有。）

这张表的前三行在 example 仓库里已经落成了 baseline.py 的 compare_to_baseline(current, baseline)：读 artifacts/validation.json 和一份基线快照（默认 artifacts/validation.baseline.json，可用 BASELINE_PATH 指定），阈值同样来自 thresholds.yaml，结果用退出码分档——0 通过、1 warning、2 fail，正好对上下面第一条经验。

基线文件不会凭空出现：它是你主动冻结的一份”已批准”快照，冻结这个动作本身就是评审的产物。第一次用先把当前摘要复制过去：

python -m intent_mlops.validate > artifacts/validation.json
cp artifacts/validation.json artifacts/validation.baseline.json

没有这一步，make baseline 会输出 {"status": "skipped"} 并以 0 退出——无从对比要明说，不能假装比过了。有了基线之后，假设数据从 60 行缩到 30 行：

$ make baseline
{
  "status": "fail",
  "warnings": [],
  "failures": [
    "rows shrank 50.0% (60 -> 30), fail threshold 10%"
  ],
  "metrics": {
    "rows_change_pct": -50.0,
    "max_class_ratio_delta": 0.0,
    "max_text_length_change_pct": 0.0
  }
}

表格后四行还没实现：文本长度那行现在只能拿验证摘要里的 max_text_length 近似（真实项目应落 p50/p95），OOV、来源覆盖率则要求验证摘要和数据集本身带上更多字段。

两条经验：

一、阈值分 hard fail 和 warning 两档。 未知标签、样本量骤降、重复率非零几乎不存在”合理的意外”，直接失败；类别比例漂了 15%、文本变长可能是真实业务变化（做了一次营销活动，账单类问题激增），发警告要求人工审核比一刀切更实用。门禁全是 hard fail 的结果，一定是有人去改阈值。

二、样本量阈值不对称，但”增长是好事、缩减是故障”这个说法要打折。 两个方向都可能是真实变化，也都可能是故障：

  • 增长未必是好事。上游 join 写错会把样本放大若干倍，采样口径从”每用户一条”改成”每会话一条”也会凭空多出几万行——这类增长带来的全是冗余，还会悄悄改变类别比例。所以那一行的算法特意写成”去重后的有效样本量“，而不是原始行数。
  • 缩减也未必是故障。去重规则收紧、合规删除请求执行、时间窗口从 90 天缩到 30 天、某个渠道正常下线，都会让数据变少，而且都是对的。

真正可靠的判据不是方向和百分比，而是这四条：是否按固定抽取窗口统计（窗口不固定，任何对比都无意义）、去重后的有效样本量、来源覆盖率（总量没变但某个渠道归零，比总量掉 10% 严重得多）、以及能否对上一个已知变更事件。对得上就放行并更新基线，对不上才是待查故障。

阈值仍然设成不对称的（增长 50% 警告、缩减 10% 失败），因为经验上缩减类故障的检出价值更高。但这两个数字是示例起始值，没有普适依据。正确的推导方式是：拿过去若干周期的样本量变化序列，算出它的历史波动分位数，把 warning 设在 p95、fail 设在 p99 附近，再按误报成本调整。业务本身有周期性（周末低谷、大促尖峰）时，还要先按周期归一化再算分位。照抄 10% / 50% 的结果通常是：要么天天误报被人调宽到形同虚设，要么松到真出事也不响。

3. 防止数据泄漏

随机划分可能让同一用户、同一会话或近似重复文本同时进入训练和测试集。第 1 节的 duplicated() 只拦得住逐字完全相同的文本，拦不住”我无法登录账号”和”我无法登陆账号”这类近似重复——它们对字符级 n-gram 几乎是同一个样本。

更可靠的方式是分组划分：按用户、会话或时间分组，让同一组样本只出现在一侧。scikit-learn 的 GroupShuffleSplit / StratifiedGroupKFold 就是为此准备的，代价是数据里要带分组键——这也是为什么真实项目的训练数据不该只有 text,label 两列，至少还要留 user_id 和事件时间戳。

时间维度上还有一类更隐蔽的泄漏：特征计算用了预测时刻尚未发生的信息。”该用户历史工单数”如果按全量数据统计，训练样本就偷看到了未来。正确做法是 point-in-time join（时点对齐关联），每条样本只用它自己发生时刻之前的数据算特征。手工做极易出错，这正是第 16 篇 Feature Store 要解决的问题之一。

对本系列示例，能落地的最低标准是三条：去重在划分之前做、划分固定 random_state、测试集绝不参与任何统计量计算（包括 TF-IDF 词表——第 03 篇把向量化器放进 Pipeline、由 fit 只在训练集上拟合，正是为了这个）。

4. 隐私和治理

训练前识别手机号、邮箱、身份证等个人信息，决定删除、脱敏或限制访问。用户输入的自由文本是重灾区——语料里出现”我的手机号 138xxxx 收不到验证码”完全正常，而这条文本一旦进训练集，就同时进了模型权重、DVC 远端和 CI artifact。

验证报告应记录数据所有者、用途、保留周期和授权依据，回答审计时必然被问的四个问题：归谁管、为什么可以拿来训练、能留多久、到期谁负责删。

质量合格与合规可用是两个不同门禁，不要合并。质量门禁由工程实现、每次提交自动跑；合规门禁通常是一次性审批 + 定期复核，由法务或数据治理角色签字。混在一起的结果是：要么工程师被迫做合规判断，要么合规审批被 CI 红灯绑架。

5. 放入流水线

门禁进流水线只有一个硬要求：失败必须中断，而不是记一条日志继续跑。 本仓库靠两处依赖保证——Makefile 里的 train: validate，和 dvc.yaml 里 train stage 对 data/intents.csv 与 validate.py 的依赖。CI 侧是第 03 篇 ci.yml 里 validate 排在 train 之前，任一步非零退出整个 job 就红。

质量门禁配置本身也要版本化。阈值一旦变多、需要按环境区分，写死在 validate.py 里就不合适了，所以 example 仓库把它们抽成了一份 thresholds.yaml：

# thresholds.yaml —— 数据质量门禁阈值
schema:
  required_columns: [text, label]
  expected_labels: [account, billing, technical_support]
  min_text_length: 2
  allow_duplicates: false

volume:
  min_samples_per_label: 5
  # 不对称阈值：缩减比增长危险
  total_rows_shrink_fail_pct: 10
  total_rows_growth_warn_pct: 50

drift:
  # 与已批准基线（artifacts/validation.baseline.json）比较
  class_ratio_warn: 0.05
  class_ratio_fail: 0.15
  p95_text_length_warn_pct: 30
  oov_rate_warn: 0.20

governance:
  owner: platform-ml
  purpose: intent-classification
  retention_days: 365

validate.py 通过一个 load_thresholds() 读这份配置（写法和 train.py 的 load_params() 对齐：YAML 是唯一声明处），dvc.yaml 的 validate stage 把 thresholds.yaml 加进了 deps——改阈值就是改依赖，DVC 强制重跑校验，不会出现”偷偷放宽标准却复用了旧的通过结果”。

抽配置之后可以直接验证它不是摆设：把 min_samples_per_label 从 5 改成 11，make validate 立刻红：

$ make validate
python -m intent_mlops.validate
ValueError: each label must contain at least 11 samples
make: *** [Makefile:11: validate] Error 1

阈值进代码 vs 进配置

这是个真实取舍，不是”配置化总是更好”：

写进代码写进 thresholds.yaml
修改成本改代码走 PR，必然被认真 review也走 PR，但容易被当作”配置微调”放过
可读性规则和动机（注释）在一起规则一眼看全，但动机容易丢失
多环境需要 if/else 分支，很快变脏天然支持 dev/staging/prod 多份
类型安全由 Python 保证要额外做 schema 校验，否则拼错 key 会被静默忽略
适用规模规则 < 10 条规则多、或需要非工程角色参与调整

一条实践判断：结构性契约留在代码里，数值阈值放进配置。 “必须恰好是 text,label 两列”、”标签集合必须完全相等”是契约，变了就是接口变更；”每类至少 5 条”、”漂移警告线 0.05”是可调参数，放配置更合适。

还有一个必须挑明的取舍：配置文件缺失时怎么办。 example 仓库的 load_thresholds() 在 thresholds.yaml 读不到时会回落到一组内置默认值，这样新读者 clone 下来直接 make validate 就能跑，不用先配环境。但这个行为和本篇通篇主张的 fail-closed 是反的——它意味着”有人误删了阈值文件”、”容器里 ConfigMap 挂载失败”、”路径写错了”这三种事故，全都会以”校验通过”的形式静默溜过去，而且日志上看不出任何异常。最讽刺的情形是：你刚把 fail 阈值从 10% 收紧到 5%，部署时挂载路径写错，实际生效的是内置的宽松默认值，门禁看起来绿着，标准却悄悄退回去了。

所以这条要分场景：教学和本地开发用默认值兜底，生产必须 fail-closed——找不到阈值文件就直接非零退出，而不是猜一组值继续跑。生产版本大概是这样：

def load_thresholds(path: Path) -> dict:
    if not path.exists():
        # 生产环境：配置缺失是事故，不是可以推断的情况
        raise FileNotFoundError(f"thresholds file not found: {path}")
    return yaml.safe_load(path.read_text(encoding="utf-8"))

同样的道理适用于所有”读不到就用默认值”的门禁配置。判据很简单：这份配置缺失时，系统是变得更严还是更松？ 变松就必须 fail-closed。

无论放哪都要守住同一条底线：阈值修改必须经过评审，理由写进 PR 描述。 否则团队迟早会通过降低标准来”修复”失败任务——这是数据门禁最常见的死法，比技术缺陷致命。防御手段很朴素：给 thresholds.yaml 加 CODEOWNERS。example 仓库里就有一份 .github/CODEOWNERS，把 thresholds.yaml、validate.py、baseline.py 和 data/ 都挂到数据负责人名下（文件里的 @data-team 是占位团队名，落地要换成组织里真实存在的 team，并在仓库设置里打开 “Require review from Code Owners”，否则它只是一份注释）。

6. 仍然缺少什么

这一篇把”训练前的数据门禁”做成了可执行的东西：make validate 能跑、失败会中断 make train、结果落成 artifacts/validation.json 并进了模型元数据。但离生产级还差几层：

  • 基线对比只覆盖了指标表的前三行。样本量、类别比例、文本长度已经在 baseline.py 里，OOV 和来源覆盖率还缺——它们要求验证摘要落更多字段、数据集带 source 列。”哪份是已批准基线”目前也只是一个文件约定（artifacts/validation.baseline.json），谁有权更新它需要流程来定。
  • 泄漏防护只有去重。分组划分和 point-in-time join 都需要 user_id 和时间戳，示例数据集没有。
  • 只管训练入口，不管线上入口。线上请求分布是否还和训练数据一致是第 17 篇的问题——同一套统计指标，一头用在训练前，一头用在推理后，这是数据质量工作最有杠杆的复用点。

小结

数据验证把隐性假设变成可执行契约。”标签只有这三个”、”每条文本至少两个字”、”不允许重复”——这些假设本来只在某个人脑子里，写成 validate_dataset() 之后就成了每次提交都被机器检查的事实。模型效果问题越早在数据入口被发现，修复成本越低：Schema 层的错误几毫秒内被拦下，同样的错误溜到线上，代价是一次回滚加一次事故复盘。
