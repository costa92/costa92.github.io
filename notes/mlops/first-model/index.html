第 4 / 25 节 · 训练、数据与实验

上一篇画清了 MLOps 与 DevOps 的边界。这一篇把边界里那条”模型交付链路”落到能跑的代码上：读取用户意图数据，先做数据校验，再训练一个 TF-IDF + Logistic Regression 的 Pipeline，评估后把模型、指标和溯源元数据一起保存成制品，最后用 GitHub Actions 证明这套流程在干净环境里可以重复。

目标很朴素——把”notebook 里跑通一次”变成”任何人拉下仓库、一条命令就能复现”。区别不在算法，而在工程约束：可复现的数据划分、可校验的输入、可加载的制品、可追溯的元数据。

1. 项目结构

我们把训练脚本做成一个可安装的 Python 包（intent_mlops），而不是散落的脚本，这样测试和 CI 都能用 python -m intent_mlops.train 稳定地调用它。

intent-mlops/
├── data/intents.csv                 # 训练数据（text,label 两列）
├── src/intent_mlops/
│   ├── __init__.py
│   ├── validate.py                  # 训练前的数据校验
│   └── train.py                     # 训练 + 保存制品
├── tests/
│   ├── test_validate.py
│   └── test_train.py
├── artifacts/                       # 训练产物落地目录
├── params.yaml                      # 训练超参数记录
├── pyproject.toml                   # 依赖与打包配置
└── .github/workflows/ci.yml         # 校验 → 训练 → 测试 → 打包

依赖用 pyproject.toml 声明，训练阶段真正用到的是三个库，测试放进可选依赖 dev：

[project]
dependencies = [
  "joblib>=1.4,<2",
  "pandas>=2.2,<4",
  "scikit-learn>=1.6,<2",
]

[project.optional-dependencies]
dev = ["pytest>=8,<10"]

[tool.setuptools.packages.find]
where = ["src"]

安装用可编辑模式，一并装上测试依赖（CI 里也是这一条）：

pip install -e '.[dev]'

后面几篇会往 pyproject.toml 里追加 Flask、gunicorn（在线推理）和 dvc、mlflow（数据与实验追踪），这里先只保留训练闭环需要的部分。

2. 训练前先校验数据

很多”训练成功但线上翻车”的事故，根子在数据而不在模型：标签拼错、类别缺失、样本重复、空文本。所以在 fit 之前先立一道数据门禁 validate.py，任何一条不满足就直接抛错、让流水线红掉。

# src/intent_mlops/validate.py
from pathlib import Path
import pandas as pd

EXPECTED_LABELS = {"billing", "technical_support", "account"}
DEFAULT_DATA_PATH = Path("data/intents.csv")


def validate_dataset(path: Path) -> dict:
    if not path.exists():
        raise ValueError(f"dataset does not exist: {path}")

    data = pd.read_csv(path)
    if list(data.columns) != ["text", "label"]:
        raise ValueError("dataset columns must be exactly: text,label")
    if data.empty:
        raise ValueError("dataset must not be empty")
    if data"text", "label".isna().any().any():
        raise ValueError("text and label must not contain null values")

    data["text"] = data["text"].astype(str).str.strip()
    data["label"] = data["label"].astype(str).str.strip()
    if (data["text"].str.len() < 2).any():
        raise ValueError("every text value must contain at least two characters")
    if data["text"].duplicated().any():
        raise ValueError("duplicate text samples are not allowed")

    labels = set(data["label"].unique())
    if labels != EXPECTED_LABELS:
        raise ValueError(f"expected labels {sorted(EXPECTED_LABELS)}, got {sorted(labels)}")

    counts = data["label"].value_counts().to_dict()
    if min(counts.values()) < 5:
        raise ValueError("each label must contain at least five samples")

    return {
        "rows": int(len(data)),
        "labels": {key: int(value) for key, value in sorted(counts.items())},
        "max_text_length": int(data["text"].str.len().max()),
    }

数据是三分类的用户意图：billing（账单）、technical_support（技术支持）、account（账户），CSV 只有 text,label 两列，例如：

text,label
为什么重复扣款,billing
我需要修改账户资料,account

校验函数除了”挡住坏数据”，还顺手返回一份数据摘要（行数、每个标签的样本数、最长文本长度）。这份摘要后面会被写进模型元数据，成为”这个模型是用什么数据训出来的”的第一条证据。它自己也能独立运行，方便本地或 CI 单独体检：

python -m intent_mlops.validate

3. 训练脚本

训练脚本做四件事：校验数据 → 划分训练/测试集 → 训练 Pipeline → 保存制品与元数据。

# src/intent_mlops/train.py
from __future__ import annotations
import hashlib
import json
import os
from datetime import datetime, timezone
from pathlib import Path

import joblib
import pandas as pd
import sklearn
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import classification_report, f1_score
from sklearn.model_selection import train_test_split
from sklearn.pipeline import Pipeline

from intent_mlops.validate import DEFAULT_DATA_PATH, validate_dataset

ARTIFACTS = Path("artifacts")


def sha256(path: Path) -> str:
    digest = hashlib.sha256()
    with path.open("rb") as source:
        for chunk in iter(lambda: source.read(65536), b""):
            digest.update(chunk)
    return digest.hexdigest()


def train(data_path: Path, output_dir: Path) -> dict:
    validation = validate_dataset(data_path)
    data = pd.read_csv(data_path)
    x_train, x_test, y_train, y_test = train_test_split(
        data["text"],
        data["label"],
        test_size=0.3,
        random_state=42,
        stratify=data["label"],
    )
    model = Pipeline(
        [
            ("tfidf", TfidfVectorizer(analyzer="char", ngram_range=(2, 4))),
            ("classifier", LogisticRegression(max_iter=1000, random_state=42)),
        ]
    )
    model.fit(x_train, y_train)
    prediction = model.predict(x_test)
    macro_f1 = float(f1_score(y_test, prediction, average="macro"))

    output_dir.mkdir(parents=True, exist_ok=True)
    model_path = output_dir / "intent-model.joblib"
    joblib.dump(model, model_path)
    metrics = {
        "macro_f1": macro_f1,
        "report": classification_report(y_test, prediction, output_dict=True),
    }
    (output_dir / "metrics.json").write_text(
        json.dumps(metrics, ensure_ascii=False, indent=2), encoding="utf-8"
    )
    metadata = {
        "model_version": os.getenv("MODEL_VERSION", "local-dev"),
        "created_at": datetime.now(timezone.utc).isoformat(),
        "dataset_sha256": sha256(data_path),
        "model_sha256": sha256(model_path),
        "sklearn_version": sklearn.__version__,
        "validation": validation,
    }
    (output_dir / "metadata.json").write_text(
        json.dumps(metadata, ensure_ascii=False, indent=2), encoding="utf-8"
    )
    return {"metrics": metrics, "metadata": metadata}


def main() -> None:
    data_path = Path(os.getenv("DATA_PATH", str(DEFAULT_DATA_PATH)))
    result = train(data_path, ARTIFACTS)
    print(json.dumps(result, ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()

跑一次训练：

python -m intent_mlops.train

几个工程上的关键决定，值得逐条说清楚：

  • Pipeline 打包预处理与分类器。把 TfidfVectorizer 和 LogisticRegression 放进同一个 Pipeline，序列化时它们作为一个整体存进 intent-model.joblib。这样线上加载后 model.predict(["..."]) 直接吃原始文本，不可能出现”训练时做了 TF-IDF、上线却忘了做”的经典事故。
  • 字符级 n-gram 而非词级。这里用 analyzer="char", ngram_range=(2, 4)，对中文文本按 2~4 个字符切 n-gram，不依赖分词器，短句意图分类下鲁棒且零外部依赖。（若换成英文语料，改回词级 ngram_range=(1, 2) 更自然。）
  • Logistic Regression 名字叫回归，干的是分类。它是一个线性分类器：给每个特征维度学一个权重，把输入向量加权求和，再压成 0–1 之间的数。名字里的”回归”是历史包袱（它拟合的是对数几率），实际输出是每个类别的概率——这正是第 04 篇 /predict 接口里 confidence 的来源。超参 C 控制正则化强度，而且方向是反的：C 越小，正则化越强，权重被压得越平、模型越保守、越不容易过拟合；C 越大约束越松，越容易把训练集里的偶然细节也学进去。默认 C=1.0，第 07 篇会把它当成主要的调参旋钮。
  • 可复现的数据划分。test_size=0.3 留三成做测试，random_state=42 + stratify=data["label"] 保证每次划分一致、且各类别在训练/测试集里按比例分层，避免小样本类别被划光。分类器也固定 random_state=42，让整条链路可复现。
  • 但这只是一次 train/test 切分，它验证的是流水线形状，不是模型质量。这里没有验证集：30 行数据、每类测试集只落到 3 条，任何一条判错都会让该类 recall 抖动 33 个百分点。这个数字能证明的只有”数据能读进来、Pipeline 能 fit、模型能预测、指标能算出来并落盘”——它不能证明模型好用，更不能拿来比较两套超参数。真实项目必须用交叉验证（cross-validation）选参、把测试集留到最后评一次，第 07 篇会把这件事补上。本系列示例保持单次切分，是因为它让后面十几篇讲的版本化、门禁、发布、监控更容易看清楚，不是因为它在方法论上够用。
  • 用 macro-F1 而不是 accuracy。三分类样本可能不均衡，f1_score(..., average="macro") 对每个类别一视同仁，比”整体正确率”更能暴露少数类被牺牲的情况。这是意图分类这类多分类任务比源教程的鸢尾花 accuracy 更该采用的指标。

params.yaml 把这些超参数单独记一份，和脚本里的取值保持一致，也为下一篇接入 DVC 参数化训练埋好接口：

train:
  test_size: 0.3
  random_state: 42
  analyzer: char
  ngram_min: 2
  ngram_max: 4
  max_iter: 1000
  c: 1.0

这一版是”两份真值”，下一篇会消掉它。 上面的 train() 把 test_size=0.3、ngram_range=(2, 4) 直接写死在代码里，params.yaml 只是抄了一份同样的数字——改 YAML 不会影响训练结果。仓库里的 train.py 已经进了下一步：用 load_params() 从 params.yaml 读，同名环境变量可临时覆盖，生效的参数还会写进 metadata.json。

之所以先给硬编码版本，是因为它更容易一眼看懂每个超参在哪起作用。但如果你打算继续跟着第 05 篇做 DVC、第 07 篇做实验对比，请现在就换成仓库版本（example/src/intent_mlops/train.py）——那两篇都依赖”改参数能真正改变产物”这件事，拿硬编码版本会得到”重跑了但产物字节没变”的假象，第 05 篇第 4 节专门讲了这个坑。

4. 制品与元数据

训练结束后 artifacts/ 目录里会落下三个文件，它们各司其职：

文件内容作用
intent-model.joblib序列化后的整条 Pipeline线上加载即用的模型本体
metrics.jsonmacro_f1 + 每类 precision/recall/f1 的 classification_report评估结果，供人和门禁检查
metadata.json版本、时间、数据/模型哈希、sklearn 版本、数据摘要溯源（lineage）证据

metadata.json 是这一版相比”只存模型 + accuracy”最实质的升级。它回答的是审计问题——“这个模型是谁、用哪份数据、在什么环境训出来的”：

{
  "model_version": "local-dev",
  "created_at": "2026-07-16T08:00:00+00:00",
  "dataset_sha256": "…",
  "model_sha256": "…",
  "sklearn_version": "1.6.x",
  "validation": {
    "rows": 30,
    "labels": {"account": 10, "billing": 10, "technical_support": 10},
    "max_text_length": 11
  }
}

其中 dataset_sha256 和 model_sha256 分别是数据文件和模型文件的 SHA-256 指纹：数据只要改一个字节、哈希就变，这为”数据变了没有”提供了免费的判据；model_version 从环境变量 MODEL_VERSION 读取，本地默认 local-dev，在 CI 里可以注入 commit SHA 或语义化版本号；sklearn_version 记录训练时的库版本，防止未来加载时因版本漂移而静默出错。这些字段是后面 DVC / MLflow 做完整血缘追踪之前，最轻量的一版”溯源锚点”。

5. 制品加载测试

只测试训练函数还不够。模型最常见的交付故障之一，是训练成功但保存的文件无法在新进程或新环境里加载——序列化版本不兼容、路径写死、依赖缺失，都会在这一步暴露。所以测试要真正把制品从磁盘 joblib.load 回来、跑一次预测：

# tests/test_train.py
from pathlib import Path
import joblib
from intent_mlops.train import train


def test_training_writes_loadable_artifacts(tmp_path):
    result = train(Path("data/intents.csv"), tmp_path)
    model = joblib.load(tmp_path / "intent-model.joblib")
    prediction = model.predict(["我需要修改账户资料"])
    assert prediction[0] in {"billing", "technical_support", "account"}
    assert (tmp_path / "metadata.json").exists()
    assert result["metrics"]["macro_f1"] >= 0

这个测试同时验证了三件事：训练能把制品写到指定目录、写出的模型能被独立加载并预测出合法标签、元数据文件确实生成。用 tmp_path（pytest 提供的临时目录）而不是固定路径，保证测试之间互不污染。

数据校验也配一份对应测试（tests/test_validate.py），覆盖标签缺失、样本过少、重复文本等违规输入应当抛错的场景。

pytest -q

6. GitHub Actions 自动化

有了”校验 + 训练 + 测试”三个可独立执行的入口，就能把它们串成一条 CI 流水线，证明整套流程在一台干净的 runner 上可以从零重复：

# .github/workflows/ci.yml
name: intent-mlops-ci

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  validate-test-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - run: python -m pip install -e '.[dev]'
      - run: python -m intent_mlops.validate
      - run: python -m intent_mlops.train
      - run: pytest -q
      - uses: actions/upload-artifact@v4
        with:
          name: intent-model-${{ github.sha }}
          path: artifacts/
          retention-days: 7
      - run: docker build -t intent-api:${{ github.sha }} .

几个要点：

  • 触发条件：pull_request 和推送到 main 都会跑，让”改数据/改代码”在合并前就得到验证。
  • 最小权限：permissions: contents: read，CI 只需要读代码，不给多余权限，符合最小权限原则。
  • 步骤顺序即质量门禁：先 validate（数据不合格就红），再 train（校验里内嵌的数据门禁 + 训练本身），再 pytest（制品能否加载），任何一步失败流水线即中止。这就是这一版的”质量门禁”——它由数据校验和可加载测试共同构成，而不是脚本里硬编码一个 F1 阈值。
  • 产物留存：upload-artifact 把整个 artifacts/ 目录（模型 + 指标 + 元数据）上传，命名带上 github.sha 便于对应到具体 commit，retention-days: 7 控制保留期。
  • 顺带构建镜像：最后 docker build 打出 intent-api:${{ github.sha }}，为下一篇的容器化推理服务做铺垫。跟着本篇手写的话这一步现在还跑不通——Dockerfile 要到第 04 篇才写出来，先把这行注释掉，第 04 篇建好后再启用。（仓库 example/.github/workflows/ci.yml 里它是启用状态，因为仓库是全系列跑完的最终形态，Dockerfile 早已存在。）

这条流水线证明了训练在干净环境能重复，并保留了可检查的制品。但要诚实地划边界：CI 的临时 artifact 不是正式的 Model Registry，upload-artifact 只是短期留存、不做版本治理和审批；真实项目也不该把大型或敏感数据直接塞进 Git。

7. 仍然缺少什么

相比”只存模型 + accuracy”，这一版已经补上了数据校验、可复现划分、macro-F1、可加载测试、以及带哈希和版本的元数据。但离生产级还差几层：

  • 数据版本化：dataset_sha256 能发现数据变了，却没有真正把数据的历史版本管起来——这是下一篇 DVC 的活。
  • 实验追踪：现在每次训练的指标只落在一个 metrics.json 里，多次实验无法横向对比、无法回溯参数与结果的对应关系——这是 MLflow 要解决的：run ID、参数、指标、混淆矩阵的系统化记录。
  • 模型注册与审批：从”CI 产物”到”被批准上线的模型版本”之间，还缺一个 Model Registry 和审批流程。
  • 量化质量门禁：目前门禁是”数据合格 + 制品可加载”，尚未在 CI 里对 macro_f1 设硬阈值。等有了稳定的评估基线，这是一个自然的加固点。

再往后是容器化、编排与线上监控——也就是这个系列接下来几篇的主线。

小结

“可交付模型”至少应能在干净环境训练、通过数据与制品层面的门禁、连同溯源元数据一起保存为制品、并被重新加载验证。只有 notebook 里的一次成功运行，还进不了工程交付链路。这一篇把这条最小闭环用 scikit-learn 和 GitHub Actions 完整跑通，剩下的，是给它逐层加上版本、追踪与治理。
