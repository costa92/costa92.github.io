第 21 / 25 节 · 治理与运营

上一篇把”正常长什么样、异常怎么报警”钉死成了 SLI、SLO 和燃烧率告警。知道这些之后，还剩两件长期的事：把风险关住，把账算清。这两件事没有告警会替你提醒——安全问题在被利用之前是静默的，成本问题在账单来之前是静默的，它们只能靠工程约定和定期复核压住。最后这一篇讲安全控制面、容量与成本模型，并给出一条从”能重复”到”平台化”的成熟度路线，收束整个系列。

1. 安全控制面

1.1 容器与 Pod 层：每一项各自防什么

example/deploy/base/deployment.yaml 的 securityContext 五项各有明确假想敌：

  • runAsNonRoot: true —— 防”容器内 root 等于宿主机 root”。相当一部分容器逃逸路径依赖容器内的 root 身份（挂载、设备访问、部分内核接口），非 root 能显著降低这类利用的成功概率，并缩小得手后的影响面。但它不是保证：不依赖 root 的内核漏洞照样存在，配错的挂载、过宽的 ServiceAccount token、宿主机 socket 暴露，都能绕过这一层。把它当作”少一个常见起点”而不是”逃逸被阻断”。Dockerfile 那句 useradd --uid 10001 appuser 是它的前提，否则 kubelet 直接拒绝启动。
  • readOnlyRootFilesystem: true —— 防”往容器里落文件”：写不进 webshell 和挖矿二进制，也改不掉已加载的模型。代价是真正要写的目录必须显式声明，所以清单挂了个 64Mi 内存 emptyDir 到 /tmp（gunicorn worker 心跳要写）。这是”最小豁免”的样板：不是关掉只读，而是精确开一个洞。
  • capabilities: {drop: ["ALL"]} —— 防”用不到的内核能力被拿去用”。默认带的 NET_RAW 能伪造 ARP 做中间人、CHOWN 能改文件属主，而一个只监听 8080 的 Flask 应用一个都不需要。
  • allowPrivilegeEscalation: false —— 防”运行中把自己提权回去”。它设 no_new_privs 位让 setuid 二进制失效；没有它，前三项都可能被一个残留的 setuid 程序绕过。
  • seccompProfile: {type: RuntimeDefault} —— 屏蔽数十个高危 syscall，收窄内核攻击面。seccomp profile 实际作用在容器进程上，每个容器各自加载一份过滤器；写在 Pod 级 securityContext 里只是设了个默认值，由该 Pod 的所有容器继承，容器级 securityContext 可以单独覆盖它。写在 Pod 级是为了”少写一处就少漏一个容器”，不是因为它们共享同一份 profile。

这五项合起来恰好满足 附录 D 那条 pod-security.kubernetes.io/enforce=restricted 的要求。区别在执行者：securityContext 是应用自己的自觉，写清单的人随时能删掉；restricted 由准入控制器在 API Server 层强制，不满足就拒绝创建 Pod，且对该命名空间所有工作负载生效。前者是自律，后者是护栏，生产两个都要有。

1.2 模型服务特有的攻击面

制品来源验证。 传统应用的信任链止于镜像，模型服务多了一环——从 S3 拉下来的那个 .joblib。而 joblib/pickle 反序列化会执行任意代码：joblib.load() 一个被污染的文件，等同于在 Pod 里执行攻击者的代码，还是在任何请求到达之前。防线是镜像按 digest 拉取（@sha256:... 而非 :latest）、模型制品记录并校验哈希、只从写权限受控的 bucket 读取，再加 cosign 签名配合准入策略。模型是可执行代码，不是数据文件——这是从 DevOps 迁过来的人最容易漏的一条。

推理输入的滥用与注入。 app.py 做对了两件事：非字符串和空串 400、超过 2000 字符 413。长度上限同时是成本护栏（阻止用超长文本拉高推理耗时和账单）和可用性护栏（阻止单请求把 worker 占死）。生产还要补入口层的认证与 rate limit，以及防高频探测反推模型边界——注意 /predict 返回了 confidence，这恰恰是模型窃取最有价值的泄露维度，对外接口可考虑只返回标签或分桶后的置信度。

PII 不进日志与指标。 用户文本几乎必然含个人信息。app.py 的日志事件里 request_id / model_version / label / confidence / latency_ms 都在，唯独原始 text 不在，这是刻意的：要复现某次预测就用 request_id 关联另一套访问受控、保留期更短、有审计的存储，而不是让原文躺在所有人都能 grep 的日志平台。指标侧同理——把用户输入做成 label，一次同时犯下高基数事故和 PII 泄露两个错。

安全测试（依赖与镜像扫描、清单策略校验）应进入发布门禁，而不是上线后的附录。

2. 容量与成本模型

先用压测得到单 Pod 在目标延迟下的安全吞吐：

required_replicas ≈ peak_requests_per_second
                    ÷ safe_rps_per_replica
                    × headroom

总成本包括计算、GPU 空闲、模型存储、跨区流量、ALB、NAT Gateway、日志和监控保留。scale-to-zero 节省空闲成本但引入冷启动；多模型共享提高利用率但增加隔离和故障半径。

2.1 超配是最大的浪费源

先把机制说准，因为”超配 = 浪费”这个结论对，但常见的解释是错的。云账单实际上按节点/实例（或 serverless Pod 的计费规格）收钱，不看你的 requests 填了多少；而且 requests 是调度预留不是运行时独占——一个 Pod 申请了 250m 只用 40m，剩下那 210m 的 CPU 时间片其他容器照样能用，CPU 是可压缩资源。

超配推高账单走的是另一条更长的传导链：requests 定得过高 → 调度器按声明值算容量，每个节点塞不下几个 Pod → 装箱密度下降 → 同样的实际负载需要更多节点 → 账单上升。节点上真实的 CPU 利用率可能只有 15%，但调度器认为它”满了”。示例请求 cpu: 250m、3 副本起步；若实际只用 40m，每副本多占 210m 的调度容量，乘以副本数再乘以服务数，最终体现为一堆跑得很闲却删不掉的节点——这通常是集群账单里最大的一块虚胖。内存是不可压缩资源，超配的浪费更直接：申请了就锁死，别的容器一点都用不到。

查它（需 kube-state-metrics 与 cAdvisor）：

sum by (namespace, pod) (
  rate(container_cpu_usage_seconds_total{container="api"}[7d])
)
/
sum by (namespace, pod) (
  kube_pod_container_resource_requests{resource="cpu", container="api"}
)

用 7 天窗口而非 5 分钟——要看长期稳态，短窗口会被一次尖峰误导。判读：比值持续 < 0.2，requests 至少能砍一半。

但比值 > 0.9 不代表被限流，也和 OOM 没有关系——这个查询里根本没有 limits。CPU 限流由 limit（cgroup CFS quota）决定，用量超过 requests 只意味着”用得比声明的多”，在节点还有空闲时完全正常，调度器也不会因此惩罚它。OOMKill 更是纯内存问题，和 CPU 无关。要判断这两件事，得查各自正确的指标：

# CPU 是否真的被限流：被限流的调度周期占比
sum by (namespace, pod) (rate(container_cpu_cfs_throttled_periods_total{container="api"}[7d]))
/
sum by (namespace, pod) (rate(container_cpu_cfs_periods_total{container="api"}[7d]))

这个比值持续超过 5%–10%（示例起始值，按你的延迟 SLO 反推）就说明 limit 定低了，Pod 在被真实地掐住。

# 内存 OOM 风险：working set 相对 limit 的水位
max by (namespace, pod) (container_memory_working_set_bytes{container="api"})
/
max by (namespace, pod) (kube_pod_container_resource_limits{resource="memory", container="api"})

水位长期贴近 1 就是 OOMKill 的前夜。再配一条事后确认，因为被 OOM 杀掉的容器不会留下任何 CPU 或内存曲线上的痕迹：

kube_pod_container_status_last_terminated_reason{reason="OOMKilled"}

这条一旦非零，就是板上钉钉发生过，不需要再推测。记住这条分工：CPU 超了是变慢（限流），内存超了是进程被杀（OOMKill），所以内存 requests 要只看峰值不看均值。调整按 P99 用量留一倍余量，且必须配合 Cluster Autoscaler / Karpenter，否则只是把闲置从 Pod 层转移到节点层——节点还在那儿，账单也还在那儿。

2.2 其他抓手

  • HPA 与副本下限。 hpa.yaml 是 minReplicas: 3，pdb.yaml 是 minAvailable: 2。下限 3 不是随手定的：要同时满足多可用区分布和 PDB，降到 2 会让节点维护时无法驱逐任何 Pod。”把 min 调成 1 省钱”的代价是可用性和可维护性；夜间低谷可定时缩容，但同样要保住 PDB 的下界。
  • GPU vs CPU 的决策点。 这个 scikit-learn 分类器在 CPU 上是毫秒级的，上 GPU 纯属浪费。决策点是吞吐密度而非”是不是深度学习”：模型足够大（CPU 上单次推理超过百毫秒）、批处理能填满 GPU、流量稳定到利用率能维持 50% 以上，三者同时成立才划算。一块空转的 GPU 比一整排空转的 CPU 节点还贵，低流量场景的答案通常是 CPU 加副本，或把模型蒸馏/量化到能跑在 CPU 上。
  • artifact 与日志的保留期。 MLflow 每次 run、DVC 每次 push 都在 S3 留副本，只增不减。定策略：Registry 里标记 Production/Staging 的版本永久保留，实验性 run 的制品 90 天清理；预测日志热 30 天、温 90 天、冷 1 年；Prometheus 原始指标 15 天、recording rule 产出的 SLI 序列 400 天（正好覆盖同比）——这是第 19 篇 1.3 节预聚合的另一个理由。
  • 对象存储生命周期策略。 这些不该靠人记得去删，写成 S3 Lifecycle：30 天转 Standard-IA、90 天转 Glacier IR、按前缀设过期。务必开 AbortIncompleteMultipartUpload——失败的分片上传永久计费且在控制台完全不可见，最经典的隐形账单。跨区流量和 NAT Gateway 同属”看不见但一直计费”，把 ECR 与 S3 的 VPC Endpoint 配上，能省掉相当一部分镜像拉取和模型下载的 NAT 费用。

3. 成熟度路线

L1 可重复：代码、数据、模型有版本
L2 可交付：自动测试、Registry、声明式部署
L3 可运营：监控、SLO、回滚、反馈闭环
L4 平台化：自助工作流、统一策略、成本与治理

不要为了追求 L4 一次性搭建所有工具。先解决当前最昂贵的人工步骤和最危险的不可见风险。

系列总结

完整 MLOps 不是从 notebook 到 Kubernetes 的单向管道，而是数据、训练、审批、部署、监控和反馈组成的闭环。每一个模型版本都应可复现、可解释其来源、可安全发布、可持续衡量，也能在出错时快速回滚。

回望 01→20，我们围绕同一个意图分类器，依次交出了 ML 基础与生命周期边界（01-02）、可交付的训练与打包（03-04）、数据与实验版本化（05-07）、从本地到 EC2 再到 EKS 的部署演进（08-10）、KServe 标准化服务（11）、入口网关与服务网格（12）、质量门禁与流水线编排（13-14）、Registry 审批与 GitOps 发布（15）、特征一致性（16）、模型监控与漂移检测（17）、反馈闭环与受控重训练（18）、可观测性与 SLO（19），以及这一篇的安全、成本与治理。没有一步是锦上添花——每一步都在回答前一步暴露的问题：手工 SSH 发布不可重复，所以要 IaC；镜像不可变解决不了模型版本追溯，所以要 Registry；服务活着不代表模型有效，所以要漂移监控；知道模型退化了还得有条受控的路把它修回去，所以要反馈闭环。

但这条链路是教学级的，不是生产级的。诚实列出被简化的环节，比假装它完备更有价值：

  • 示例数据集只有 30 行。 够跑通流水线，但基于它的准确率、混淆矩阵和阈值都没有统计意义，第 17 篇讲的最小样本量、切片分析、PSI 阈值在 30 行上没法真正演示。
  • 训练制品的流转绕过了编排层。 示例 Workflow 的 train 步骤没有 outputs.artifacts 声明，产物靠 mlflow.log_artifacts 直接推到 MLflow，下游只能隐式回查 run（见第 14 篇）。真实 Pipeline 应该由 artifact repository 在步骤间显式传递，步骤才能落在不同节点、才能重试和独立复用。
  • 单体 Pipeline，特征逻辑封在模型里。 第 16 篇讲了训练/服务一致性的原理，并说明本项目的 sklearn Pipeline 已在源头消除了 skew。仓库提供了 Feast 参考定义和 as-of join 可运行演示，但它们不参与主工程构建——特征真的成为独立资产时才需要它们。
  • 单模型、单区域、无多租户，没有涉及资源隔离、跨区容灾和平台化后必然遇到的配额与计费分摊。
  • 监控只覆盖了服务侧 SLI：仓库里有 recording rule、快慢双窗燃烧率告警和五面板仪表盘（第 19 篇），但 SLI 口径取自 app.py 的进程内直方图，度量的是模型推理耗时而非用户感知的端到端延迟。第 12 篇 §3.3 已经给出了用 sidecar 指标重算这条 SLI 的写法，但仓库的 recording rule 和燃烧率告警仍然基于进程内直方图，两套口径尚未合并。错误预算目标也是写死的 99.9%，没有按业务线分级。

这些不是遗漏，是取舍：每个环节都做到生产强度，读者会淹没在配置里而看不见主线。真正要带走的不是这些 YAML，而是判断力——知道每个组件在解决什么问题、边界在哪里、自己团队当下最痛的是哪一环。工具三年一换，这套判断不会。
