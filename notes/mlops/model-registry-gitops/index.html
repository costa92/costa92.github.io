第 16 / 25 节 · 治理与运营

第 14 篇把训练从一条命令升级成了有依赖、有重试、有运行元数据的 DAG。但编排系统跑完只产出一个”候选”——Workflow 成功不等于这个模型该上线。这一篇处理交接：Model Registry 保存候选模型及其证据，GitOps 仓库保存环境应该运行哪个版本，中间是明确的审批。把这两件事混在一起，就会出现”训练脚本自己 kubectl apply“这种把质量决策藏进 CI 日志的做法。

1. 候选模型必须携带什么

一个可被审批的候选模型必须自带这些字段。缺任何一项，审批者都只能凭信任签字：

  • 来源 MLflow Run（run_id）；
  • Git commit 与训练镜像 digest；
  • 数据版本（DVC 指纹 / dataset_sha256）及验证报告；
  • 离线指标、性能测试和公平性检查；
  • 模型格式、签名、制品 SHA-256；
  • 所有者、风险级别和审批记录。

这些字段在第 07 篇已被 log_params / log_metric / log_artifacts 写进 run。注册不是重新收集，而是把它们冻结到一个版本号上。

2. 用 MLflow Model Registry 做晋级

本项目 pyproject.toml 锁的是 mlflow>=3,<4。MLflow 3 有一个必须先讲清楚的变化：Stage（None / Staging / Production / Archived）已经被移除，生命周期改用 alias（别名）和 tag 表达。client.transition_model_version_stage(...) 与 stage= 过滤在 3.x 已不可用，老教程里的写法照抄会直接报错。

alias 的语义比 stage 好：它是一个指向某个版本号的可移动指针，一个模型可以有任意多个（staging、production、champion、shadow），而 stage 只有固定四档。加载时用 models:/<name>@<alias>。

2.1 从 run 注册出一个版本

第 07 篇提到两条路：log_artifacts 存复现所需的原始文件目录，mlflow.sklearn.log_model 存可被统一加载的 flavored model。要用 models:/ URI 加载必须有后者；example 的 train_mlflow.py 目前只做了前者，所以晋级脚本要么在训练里补一行 log_model，要么直接把 artifact 目录当 source 注册。

下面这条链路已经落成 example/src/intent_mlops/promote.py，提供 register / staging / production / rollback / current 五个子命令（python -m intent_mlops.promote register --run-id <RUN_ID>）。mlflow 在 pyproject.toml 里属于 mlops 这个 optional extra，脚本延迟导入，未安装时提示 pip install '.[mlops]' 而不是让整个包炸掉。

事后注册（推荐，因为”训练成功”和”决定注册”是两个决策）：

import os
import mlflow
from mlflow import MlflowClient

mlflow.set_tracking_uri(os.environ["MLFLOW_TRACKING_URI"])
client = MlflowClient()

MODEL_NAME = "intent-classifier"
run_id = os.environ["RUN_ID"]

# 模型注册表条目本身只需创建一次；已存在时不要让脚本崩掉
try:
    client.create_registered_model(MODEL_NAME)
except mlflow.exceptions.MlflowException:
    pass  # RESOURCE_ALREADY_EXISTS

version = client.create_model_version(
    name=MODEL_NAME,
    source=f"runs:/{run_id}/intent-model",   # 与 log_artifacts 的 artifact_path 一致
    run_id=run_id,
    description="第 14 篇编排产出的候选，待离线门禁",
)
print(version.version)   # "1", "2", ...

mlflow.register_model(model_uri=..., name=...) 是同一件事的简写，会自动创建注册表条目，脚本里两者选一即可。

注册的同时把审计字段写成 model version tag。tag 是审批记录的载体——它跟着版本号走，不会因为有人改了 Git 分支或删了 CI 日志而消失：

run = client.get_run(run_id)
tags = {
    "git_sha": run.data.params.get("git_sha", "unknown"),
    "dataset_sha256": run.data.params["dataset_sha256"],
    "training_image": os.environ["TRAINING_IMAGE_DIGEST"],
    "workflow_id": os.environ["ARGO_WORKFLOW_NAME"],
    "artifact_sha256": artifact_sha256,   # 见第 4 节
    "owner": "customer-platform",
    "risk_level": "medium",
}
for key, value in tags.items():
    client.set_model_version_tag(MODEL_NAME, version.version, key, value)

2.2 打 staging alias

注册完只是”存在”，还不是”可被测试”。离线门禁通过后再打 staging——这一步应该由代码判定，不是由人在 UI 上点：

metrics = run.data.metrics
gate = (
    # 缺省值一律朝"拒绝"方向倒：指标没打上来等同于没通过。
    # 下限类指标缺省用 0.0，上限类用 inf——写反一个就是自动放行。
    metrics.get("macro_f1", 0.0) >= 0.82
    and metrics.get("technical_support_recall", 0.0) >= 0.78
    and metrics.get("p95_inference_ms", float("inf")) <= 50
)
if not gate:
    raise SystemExit(f"offline gate failed: {metrics}")

client.set_registered_model_alias(MODEL_NAME, "staging", version.version)
client.set_model_version_tag(
    MODEL_NAME, version.version, "offline_gate", "passed"
)

门禁阈值写在 git 里，谁改了标准、什么时候改的，git log 说了算。这是”审批可审计”的第一层。

这里的 .get() 缺省值不是防御性编程的样板，是门禁的核心语义。 写成 metrics["macro_f1"] 会在指标缺失时抛 KeyError——看起来也是”失败”，但异常和”门禁未通过”在 CI 里往往走不同的分支，前者可能被 || true 之类的写法吞掉。更糟的是 metrics.get("p95_inference_ms", 0)：缺省 0 恒满足 <= 50，指标没打就等于自动放行，而这种放行不会留下任何痕迹。门禁类代码的每一个缺省值都要问一句：这个值让它更容易通过，还是更容易被拦？

上面这段是示意。仓库里 promote.py 的 offline_gate() 与它逻辑一致，但环境变量统一用 os.getenv(..., default) 而非 os.environ[...]——脚本要能在缺少可选变量（如 ARTIFACT_SHA256）时正常降级，而不是启动即崩。

2.3 通过人工审批后打 production alias

第二层是人。离线指标能自动判，但”这个模型现在能不能承接真实客服流量”是业务决定：这周在做大促吗？客服排班够不够接住误分类？这些不在指标里。所以晋级 production 需要一个显式的、带身份的操作，且这个动作本身要留下机器可读的痕迹。

approver = os.environ["APPROVER"]            # 来自 CI 的 OIDC 身份，不是手填
ticket = os.environ["APPROVAL_TICKET"]       # 变更单 / PR 编号

staging = client.get_model_version_by_alias(MODEL_NAME, "staging")

# 记录"上一任 production 是谁"，回滚时就不用翻历史
try:
    previous = client.get_model_version_by_alias(MODEL_NAME, "production")
    client.set_registered_model_alias(
        MODEL_NAME, "previous-production", previous.version
    )
except mlflow.exceptions.MlflowException:
    previous = None

client.set_model_version_tag(
    MODEL_NAME, staging.version, "approved_by", approver
)
client.set_model_version_tag(
    MODEL_NAME, staging.version, "approval_ticket", ticket
)
client.set_registered_model_alias(MODEL_NAME, "production", staging.version)

回滚就是把 alias 挪回去，不需要重训、也不需要找回旧文件；”生产在跑哪个版本”则是一次查询：

# 回滚
client.set_registered_model_alias(MODEL_NAME, "production", previous.version)

# 查询当前生产事实
mv = client.get_model_version_by_alias(MODEL_NAME, "production")
print(mv.version, mv.run_id, mv.tags["approved_by"], mv.tags["artifact_sha256"])

谁批准、批准什么、记录留在哪。 谁：CI 通过 OIDC 拿到的真实身份，不是 APPROVER=me 这种环境变量手填；批准什么：一个具体的版本号 + 制品 checksum，不是”这个模型”这种模糊对象；记录留在哪：model version tag（不可绕过的注册表事实）+ GitOps 仓库的 commit（谁 merge 的、什么时候）。两处互为佐证。如果只有 Slack 里一句”可以上了”，那不是审批，是口头承诺。

3. 发布状态机

用 alias 表达就是 (无 alias) → staging → production，回滚是 production 指针后移。状态改变必须追加审计记录，不能通过改文件名表达——看到 model_final_v7.joblib，说明状态机根本不存在。

4. 不可变前缀与 checksum：从注册贯穿到发布

第 11 篇定下了 serving 侧的约定：storageUri 必须指向不可变版本前缀，前缀里放着 runtime 期望的 model.joblib。批准后由发布任务把制品复制到该位置，路径里的数字就是 model version：

s3://models/intent-classifier/17/model.joblib
s3://models/intent-classifier/17/metadata.json

metadata.json 是这个前缀的自述，内容直接来自 model version tag：

{
  "model_name": "intent-classifier",
  "model_version": "17",
  "mlflow_run_id": "3f9c1a2b4d5e6f708192a3b4c5d6e7f8",
  "git_sha": "a1b2c3d4",
  "dataset_sha256": "9e107d9d372bb6826bd81d3542a419d6...",
  "artifact_sha256": "e3b0c44298fc1c149afbf4c8996fb924...",
  "training_image": "REGISTRY/intent-train@sha256:...",
  "approved_by": "ci-oidc:customer-platform/release-bot",
  "approval_ticket": "CHG-2841",
  "feature_contract_version": "3"
}

checksum 在三个点上被用到，缺一环这条链就断：

  1. 注册时计算：晋级脚本从 run artifact 下载文件，算出 artifact_sha256，写进 model version tag；
  2. 上传后校验：复制到 S3 前缀后立刻回读比对，防止传输截断；
  3. 加载前校验：serving 侧（或 storage-initializer 之后的启动钩子）下载完先比对 metadata.json 里的 artifact_sha256，不匹配就拒绝启动。
VERSION=17
PREFIX="s3://models/intent-classifier/${VERSION}"

# 上传前先算，作为唯一真值
EXPECTED=$(sha256sum artifacts/model.joblib | cut -d' ' -f1)

aws s3 cp artifacts/model.joblib "${PREFIX}/model.joblib"
aws s3 cp metadata.json          "${PREFIX}/metadata.json"

# 回读校验：不比对就上线，等于相信网络
ACTUAL=$(aws s3 cp "${PREFIX}/model.joblib" - | sha256sum | cut -d' ' -f1)
test "$EXPECTED" = "$ACTUAL" || { echo "checksum mismatch"; exit 1; }

前缀不可变意味着 17/ 一旦写完就永不覆写，要改模型就发 18/。于是同一个 storageUri 在任何时刻拉下来的字节都一样，”回滚到 17”是确定行为。反过来，发布流程里一旦出现 s3://models/intent-classifier/latest/，Pod 重启就可能悄悄换模型——latest 是这条链上最常见的破口。

5. Argo CD Application：集群状态由 Git 决定

GitOps 的核心不是”用工具部署”，而是一条约束：集群里跑什么，由 Git 仓库里的清单决定；人和 CI 都不直接改集群。 差异由 controller 持续检测并收敛。

于是发布动作变成了一次提交。发布任务改的是仓库里的 storageUri：

spec:
  predictor:
    model:
      modelFormat: {name: sklearn}
      storageUri: s3://models/intent-classifier/17/

这里有个容易踩空的地方：改 storageUri 只有在被某个 Application 纳管时才会生效。仓库里因此有两份互斥的 Application——application.yaml 指向 example/deploy/base（原生 Deployment + Service + Ingress + HPA + PDB 那条路径），application-kserve.yaml 指向 example/deploy/kserve（InferenceService 那条路径，上面这段 storageUri 就在它里面）。两者服务的是同一个模型，同时启用会在一个命名空间里跑起两套服务栈，按第 11 篇的选择留一个。

下面以 base 那份为例（repoURL 是占位符，应用前先换成自己的仓库）：

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: intent-api
  namespace: argocd
  finalizers:
    # 删除 Application 时级联清理它创建的资源，避免留下孤儿
    - resources-finalizer.argocd.argoproj.io
spec:
  project: intent-mlops
  source:
    repoURL: https://github.com/example/intent-mlops.git
    # 只跟受保护分支；不要写 HEAD 或可移动 tag
    targetRevision: main
    path: example/deploy/base
  destination:
    server: https://kubernetes.default.svc
    namespace: intent-mlops
  syncPolicy:
    automated:
      # 集群里被手工改动的字段会被拉回 Git 声明的值
      selfHeal: true
      # Git 里删掉的资源，集群里也删掉
      prune: true
    syncOptions:
      - CreateNamespace=false
      - ServerSideApply=true
    retry:
      limit: 5
      backoff: {duration: 10s, factor: 2, maxDuration: 3m}

selfHeal: true 是这套约束真正生效的开关。没有它，有人 kubectl edit 改了副本数或镜像，Argo CD 只会显示 OutOfSync 而不纠正——集群状态就又变回”看谁最后动过手”。

syncPolicy 自动同步与人工审批的取舍，本质是”把人放在哪一道门”：

automated 自动同步去掉 automated（手工 Sync）
人的位置PR review 阶段PR review + 点 Sync 两道
merge 到生效秒级，无人值守需要有人在场
半夜发布会发生不会发生
适合已有 canary 门禁自动兜底的环境高风险变更、无自动回滚能力的环境
风险一个错误 merge 立刻进生产集群长期偏离 Git，且值班的人成为瓶颈

推荐组合是：保留 automated，把人的审批前移到分支保护规则——生产分支要求 CODEOWNERS 审批和状态检查通过。这样”谁批准的”落在 PR 的 approve 记录上，是平台强制、不可事后编辑的凭据；而”点 Sync 的那个人”通常只是当时在线的运维，签的不是同一件事。

生产集群不允许 CI 直接 kubectl apply：CI 的权限只到”提 PR”，集群凭据只有 Argo CD 持有。这条隔离让”CI 被攻破”不等于”集群被攻破”。

6. Canary、Shadow 与 A/B

  • Canary（金丝雀）：少量真实流量走新模型，逐步放量，检验”新模型在真实流量下是否会坏”；
  • Shadow（影子）：复制请求给新模型但结果不影响用户，零风险，只能看预测差异、看不到业务后果；
  • A/B：按实验设计稳定分组比较业务结果，观察周期长得多；
  • Blue/Green（蓝绿）：两套完整版本切换，回滚快但资源成本翻倍。

务实顺序：Shadow 跑一天看预测分布对不对得上 → Canary 分档放量 → 有余力再上 A/B。

7. Canary 放量门禁的具体判据

“放量看指标”是句废话，除非写出阈值、观察窗口和动作。下面这张表是意图分类服务的一套起始值——数字要按你的业务错误成本调，但结构不变：

判据观察窗口继续放量暂停自动回滚
HTTP 5xx 率10 min 滚动< 0.5%0.5%–2%≥ 2% 持续 5 min
p95 推理延迟10 min 滚动≤ baseline × 1.21.2–1.5×> 1.5× 持续 5 min
预测分布偏移（对 baseline 的 PSI）30 min 累积< 0.10≥ 0.10（含 ≥ 0.25）不单独回滚，见下
低置信度比例（max_prob < 0.6）30 min 累积≤ baseline + 3pp> +3pp（含 > +8pp）不单独回滚，见下
人工纠正率（客服改单）4 h 累积≤ baseline + 2pp+2pp–+5pp> +5pp
单类别 recall（technical_support）4 h 累积≥ 0.780.72–0.78< 0.72

PSI（Population Stability Index，总体稳定性指数） 在这里第一次出现：它衡量两个分布差多远——把新旧版本的预测标签占比按同样的分箱切开，逐箱比较占比差异，汇总成一个数。0 表示完全一致，越大差异越明显。常用判读是 < 0.1 稳定、0.1–0.25 需观察、> 0.25 需调查，上表就是按这个刻度定的。完整公式、可运行实现和它的四条局限（分箱敏感、小样本不稳、只看边缘分布、没有方向性）在第 17 篇第 4 节。这里只需要知道：它衡量”变了多少”，不衡量”变差了没有”——所以 PSI 高只触发暂停和调查，不单独作为回滚依据。

分布类判据那两行的”自动回滚”列是空的，这是刻意的。 PSI 和低置信度比例都只证明”输出变了”，不证明”变差了”——一次营销活动、一次上游文案调整、一次真实的用户结构变化，都能把 PSI 推过 0.25，而模型可能完全正常（第 17 篇第 4 节列了 PSI 的四条局限）。把它接上自动回滚，等于让一个无标签的代理信号去做需要标签才能下的判断，结果是频繁误回滚，然后团队开始调高阈值直到它再也不响。

正确的用法是升级为暂停 + 调查：分布剧变时停止放量、拉人来看，只有当它同时伴随带标签的质量退化（recall 掉、人工纠正率涨）时才回滚——那时候真正触发回滚的是后者，PSI 只是提供了”为什么变差”的线索。gate.py 里就是这么实现的：系统红线（5xx、延迟）单独成立即回滚，业务判据单独成立即回滚，分布信号单独出现一律 hold。

放量档位 5% → 25% → 50% → 100%，每档至少驻留 30 分钟。这里只定义了”该不该放量”，没说流量怎么切——执行侧在第 12 篇：Istio 的 VirtualService 按权重把这几档流量导给新版本 subset，本节的判据就是驱动那个权重变化的输入。没有网格时，退而求其次的做法是按副本比例近似（新旧 Deployment 各起若干副本，靠 Service 轮询分流），代价是档位粒度受副本数限制、5% 这一档基本做不到。5% 档跳过 4 小时窗口的业务判据是合理的（样本量不够），但那两条必须在 25% 及以后强制评估——很多事故就出在”前两档飞快通过，业务指标从没被看过”。

写成可执行的判据表达式，让它能被 CI 或渐进式交付控制器直接求值——这张表和下面的函数就是 example/deploy/canary/gate.py，阈值都提成了文件顶部的常量，python deploy/canary/gate.py 会跑几组样例输入把三档决策打出来：

def decide(m: dict, baseline: dict, stage_pct: int) -> str:
    """返回 rollback / hold / promote。任一红线触发即回滚。"""
    if (
        m["error_rate_10m"] >= ROLLBACK_ERROR_RATE            # 0.02
        or m["p95_ms_10m"] > baseline["p95_ms"] * ROLLBACK_P95_FACTOR   # 1.5x
        or m["psi_30m"] >= ROLLBACK_PSI                       # 0.25
        or m["low_conf_ratio_30m"]
        > baseline["low_conf_ratio"] + ROLLBACK_LOW_CONF_DELTA  # +8pp
    ):
        return "rollback"

    # 业务判据只在样本量足够的档位评估
    business_gate = stage_pct >= BUSINESS_GATE_FROM_PCT       # 25%
    if business_gate and (
        m["correction_rate_4h"]
        > baseline["correction_rate"] + ROLLBACK_CORRECTION_DELTA  # +5pp
        or m["recall_technical_support_4h"] < ROLLBACK_MIN_RECALL  # 0.72
    ):
        return "rollback"

    if (
        m["error_rate_10m"] >= HOLD_ERROR_RATE                # 0.005
        or m["p95_ms_10m"] > baseline["p95_ms"] * HOLD_P95_FACTOR   # 1.2x
        or m["psi_30m"] >= HOLD_PSI                           # 0.10
        or m["low_conf_ratio_30m"] > baseline["low_conf_ratio"] + HOLD_LOW_CONF_DELTA  # +3pp
    ):
        return "hold"

    # 业务判据的中间档：没坏到要回滚，但不能继续放量
    if business_gate and (
        m["correction_rate_4h"] > baseline["correction_rate"] + HOLD_CORRECTION_DELTA  # +2pp
        or m["recall_technical_support_4h"] < HOLD_MIN_RECALL  # 0.78
    ):
        return "hold"

    return "promote" if m["stage_minutes"] >= MIN_STAGE_MINUTES else "hold"

注意判据的排列顺序：所有 rollback 条件必须排在所有 hold 条件之前。写反了会出现”低置信度涨了 9pp（该回滚）却先命中 +3pp 的 hold 分支”，把一次该回滚的发布拖成无限期暂停。表格里的六个判据在这里都有三档，唯一没实现的是”持续 5 min”这个时间条件——decide() 是单次求值的纯函数，持续时长应该由调用方（CI 或渐进式交付控制器）在采样窗口上保证。

三个细节：系统指标和模型指标必须同时看——5xx 和延迟正常、PSI 却飙到 0.4，说明模型在安静地预测错，没有任何告警会响；hold 不是终态，连续 3 次应升级为 rollback 或呼人，否则 canary 会永远卡在 25%；baseline 要来自当前 production 的同期数据，周一早高峰和周日凌晨的 p95 本来就不一样，拿错 baseline 会让门禁在正常波动时误触发。

回滚动作是两件事一起做：GitOps 仓库 revert 那次 storageUri 提交（集群收敛回旧前缀），MLflow 把 production alias 指回 previous-production（注册表事实同步）。只做前者，注册表就开始撒谎。

8. 回滚单位

模型、预处理、API Schema 和特征定义可能存在耦合。回滚不能只替换模型文件，而要使用经过验证的兼容组合。部署清单应记录：

application_digest + model_version + feature_contract_version

三元组一起进 Git、一起回滚。典型翻车场景：新模型要求特征表多一列，API 镜像也跟着改了，出问题时只把 storageUri 退回 16/——旧模型拿到新 schema 的输入，报的错和模型本身毫无关系，排查方向从第一分钟就是错的。如果回滚需要人思考”还要一起退什么”，这个回滚单位就定错了。

小结

Registry 管模型事实与审批，Git 管环境期望状态，GitOps Controller 负责收敛实际状态。把三者分开，发布才可审计、可回滚。

三条硬约束贯穿全篇：alias 而非文件名表达生命周期（MLflow 3 已无 stage）；不可变前缀加 checksum 让”版本 17”在任何时刻都是同一批字节；canary 判据写成表达式进 git，而不是留在某个人的经验里。审批不是点个按钮，而是一条从 run_id 到 approver 到 commit SHA 都可查的记录链。
