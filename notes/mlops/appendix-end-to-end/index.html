第 22 / 25 节 · 附录

本附录把 20 篇中的关键动作串成一条可验证路径。所有本地命令在示例工程目录执行——也就是说，先 cd example，本附录之后所有相对路径都以它为根。

0. 集群 context：先想清楚在哪跑

第 5 节起的命令都对着一个 Kubernetes 集群。正文里不同篇章会建不同集群（第 06 篇的 KinD mlops-labs、第 10 篇的 EKS、第 11 篇的 KinD kserve-lab），从头到尾照做会切三次 context，然后在第 14 篇撞上”MLflow 不在当前集群里”。

本附录只用一个集群，把第 5—6 节的所有组件装在这里。选哪个都行，选定后固定下来：

kubectl config get-contexts
kubectl config use-context <你选定的那个>
export KUBECTL_CTX=$(kubectl config current-context)

之后每次跨越较长时间回来继续，先确认没跑偏：

[ "$(kubectl config current-context)" = "$KUBECTL_CTX" ] && echo OK || echo "context 已被切走"

这个集群里需要装齐：MLflow（第 06 篇）、KServe（第 11 篇）、Argo Workflows（第 14 篇）、Prometheus Operator（第 19 篇）。其中 Argo 和 MLflow 必须同集群——训练 Workflow 通过集群内 DNS mlflow.mlflow.svc.cluster.local 连 tracking server，跨集群直接 DNS 解析失败。

第 1—4 节全在本机跑，不碰集群，可以先做完。

1. 本地环境

cd example
python3 -m venv .venv
source .venv/bin/activate
make install
make validate
make train
make test

验收标准：

  • 验证输出包含 30 行及三个标签；
  • artifacts/ 生成 model、metrics、metadata；
  • metadata 包含数据和模型 SHA-256；
  • 所有 pytest 通过。

2. API 验收

make serve

新终端执行：

curl -fsS http://localhost:8080/healthz
curl -fsS http://localhost:8080/readyz
curl -fsS -X POST http://localhost:8080/predict \
  -H 'Content-Type: application/json' \
  -H 'X-Request-ID: acceptance-001' \
  -d '{"text":"为什么重复扣款"}'
curl -fsS http://localhost:8080/metrics | grep intent_api

验证响应有 label、confidence、model_version 和 latency_ms，错误输入返回 400。

3. 容器验收

docker compose up --build -d
docker compose ps
docker compose logs intent-api
docker compose down

验收容器以非 root、只读文件系统运行，健康检查最终为 healthy。

4. 可选 MLOps 工具

这一节有两个前置条件，缺一步就会失败：

  • example/ 不是独立的 git 仓库根，dvc repro 之前必须先在这个子目录初始化（见第 05 篇）；
  • train-mlflow 需要一个已经在跑的 MLflow Server，本地最简做法是第 06 篇里的 mlflow server 或对集群内服务做 port-forward。
make install-mlops
dvc init --subdir            # 仅首次；已有 .dvc/ 时跳过
dvc repro
# 另开终端：mlflow server --host 127.0.0.1 --port 5000
MLFLOW_TRACKING_URI=http://localhost:5000 make train-mlflow

DVC 应复用未变化的阶段（改一行 params.yaml 再跑，train 阶段应重新执行且产物摘要变化）；MLflow UI 中应出现 run、macro F1 和 artifacts。

5. Kubernetes 清单

目标版本为 Kubernetes/EKS 1.34.x。完整组件矩阵与集群前置条件见附录 D。从这一节起开始碰集群，先按第 0 节确认 context，再核对服务端版本、Metrics Server 和 IngressClass，最后替换镜像 digest、域名和 IAM Role：

kubectl config current-context     # 应等于第 0 节选定的那个
kubectl version --output=yaml
kubectl get --raw /apis/metrics.k8s.io/v1beta1/nodes >/dev/null
kubectl get ingressclass
kubectl create namespace intent-mlops --dry-run=client -o yaml | kubectl apply -f -
kubectl kustomize deploy/base > /tmp/intent-api.yaml
kubectl apply --server-side --dry-run=server -n intent-mlops -f /tmp/intent-api.yaml

部署后检查：

kubectl rollout status deployment/intent-api -n intent-mlops --timeout=5m
kubectl get pod,svc,ingress,hpa,pdb -n intent-mlops
kubectl get events -n intent-mlops --sort-by=.lastTimestamp
kubectl port-forward -n intent-mlops service/intent-api 8080:80

6. KServe 与监控

KServe 0.18.0、Prometheus Operator 0.90.1 及对应 CRD 必须预先安装：

kubectl apply --server-side --dry-run=server -n intent-mlops -f deploy/kserve/inferenceservice.yaml
kubectl apply --server-side --dry-run=server -n intent-mlops -f monitoring/servicemonitor.yaml
kubectl apply --server-side --dry-run=server -n intent-mlops -f monitoring/prometheusrule.yaml

7. 训练流水线

这一节对应第 14 篇，是最容易在环境上卡住的一环，两个前置条件：

  • 当前 context 就是第 0 节那个集群，且里面同时有 Argo Workflows 和 MLflow。只装了 Argo 没装 MLflow，train 步骤会因为 DNS 解析不到 mlflow.mlflow.svc.cluster.local 而失败。
  • 训练镜像已经构建并推上去。它是 Dockerfile.trainer 而不是服务用的 Dockerfile——后者不装 mlflow，train 步骤会直接 ModuleNotFoundError: No module named 'mlflow'。
kubectl config current-context                 # 第 0 节那个
kubectl get svc -n mlflow                      # 应有名为 mlflow 的 Service
kubectl get crd workflows.argoproj.io

docker buildx build -f Dockerfile.trainer -t "$REGISTRY/intent-trainer:$(git rev-parse --short HEAD)" --push .
DIGEST=<上一步推上去的 sha256:...>

kubectl apply -f workflows/serviceaccount.yaml
argo submit -n intent-mlops workflows/train-workflow.yaml \
  -p image="$REGISTRY/intent-trainer@$DIGEST" --watch

验收标准（缺一条不算通过）：

  • argo get -n intent-mlops @latest 显示 Succeeded，validate 和 train 两个节点都是 Succeeded；
  • argo logs -n intent-mlops @latest train 末尾有 {"run_id": "..."}；
  • MLflow UI 里能找到这个 run，macro_f1、git_sha、dataset_sha256 和 intent-model artifact 都在。

只有第一条通过、后两条不通过，说明训练跑了但没连上 tracking server——查 MLFLOW_TRACKING_URI 和网络策略，不要改训练代码。

8. 发布验收矩阵

层必须通过失败动作
数据Schema、分布、隐私门禁停止训练
模型离线质量和性能门禁拒绝注册
制品checksum、来源、兼容性阻止发布
服务契约、健康、压测停止放量
Canary错误率、延迟、预测分布自动回滚
生产SLO、漂移、真实质量调查或触发重训练
