第 18 / 25 节 · 治理与运营

第 16 篇讲清了训练—服务偏斜的根因，结论是本项目的 sklearn Pipeline 把特征逻辑和模型权重打包进同一个 joblib，从源头消灭了这个问题——不需要 Feature Store。但”两端算得一样”只保证模型不会因工程失误而算错，它不保证世界不变：用户会换说法、业务会上新品类、上游会悄悄改字段。这一篇要回答的是：模型上线之后，凭什么持续相信它还是对的？

部署成功只是模型生命周期的中点。没有真实标签反馈，团队只能看到服务是否可用，却无法知道预测是否仍然正确。一个 500 错误率为 0、p95 延迟 20ms 的服务，完全可能正在稳定地、快速地、全都答错。

1. 三层监控

三层信号的性质完全不同：服务层（QPS、错误率、p95 延迟、内存）秒级可得，走 Prometheus 实时告警；数据/预测层（输入特征分布、预测标签分布、置信度分布）分钟到小时级，靠窗口任务加阈值；模型质量层（准确率、类别 recall、业务转化）要等标签，小时到数周，只能出离线报告交人工评审。

服务指标实时告警；数据和模型指标通常按窗口异步计算，避免在请求链路执行昂贵统计。在 /predict 里同步算 PSI 是一个典型的错误设计——它会把一个 4ms 的推理拖成 40ms，还会因为窗口不足而算出噪声。

2. 三种漂移的区别

“漂移”这个词经常被当成一个整体使用，但生产上要处理的是三件性质完全不同的事。

数据漂移（data drift / covariate shift）——输入分布变了。 训练时用户写”为什么重复扣款”，现在大量涌入”自动续费怎么关”：词频、长度、语言分布都变了，但”这句话属于 billing”这个映射关系没变。检测手段是把当前窗口的输入特征分布和基线做统计对比。不需要标签就能发现。

常用的三个工具，各有适用范围和局限：

  • PSI（Population Stability Index，总体稳定性指数）——把两份数据切成相同的分箱，逐箱比较占比差异，加总成一个数。适用于单个连续数值或有序分箱后的特征（置信度、文本长度），也可以直接用在类别特征上（每个类别当一个箱）。优点是好算、好解释、有一套行业沿用的判读区间；局限是强依赖分箱方式且只看单个特征，下面第 4 节会展开。
  • KS 检验（Kolmogorov–Smirnov test）——比较两份样本的累积分布函数，取最大垂直距离作为统计量。只适用于连续数值特征，类别特征用不了。它输出 p 值，看起来很”科学”，局限恰恰在这里：样本量一大，任何微不足道的差异都会显著。线上日均几十万条预测时，p 值几乎永远小于 0.05，所以实践中要看统计量本身（距离有多大）而不是 p 值是否显著。
  • Jensen-Shannon 散度（JS divergence）——衡量两个概率分布的差异，值域固定在 0–1（以 2 为底时），对称且有界，这是它比 KL 散度好用的地方。适用于离散分布或分箱后的分布，本系列的预测标签占比就是典型场景。局限和 PSI 一样：对分箱敏感、只看边缘分布，而且它给出的是一个抽象距离，没有直接的业务含义——0.15 是大是小，只能靠历史基线比出来。

选哪个不重要，重要的是分箱规则和基线窗口必须固定并版本化，否则三个工具算出来的都是噪声。本系列后面只落地 PSI，因为它一个就够撑起”发现异常 → 立案调查”这条链路。

概念漂移（concept drift）——输入和标签的关系变了。 同样一句”账号被限制了”，产品改版前该判为 account，改版后风控接管，正确答案变成 technical_support。输入分布纹丝不动，模型却已系统性地答错。这类漂移无法从输入侧检测，必须要有真实标签——所有分布类监控都是绿的，这正是它最危险的地方。

预测漂移（prediction drift）——输出分布变了。 标签占比从 billing 40% / technical_support 35% / account 25% 变成 billing 65%，或平均置信度从 0.83 掉到 0.61。同样不需要标签就能发现。

这里要拆掉一个流行的错误说法：预测漂移不是前两者的必然投影。两个方向都不成立——

  • 概念漂移可以完全不引起预测漂移。 模型是固定的函数，输入分布不变时，它吐出的预测分布就一定不变。产品改版后”账号被限制了”的正确答案从 account 变成了 technical_support，模型照旧稳稳地预测 account，预测分布纹丝不动，置信度也纹丝不动——它错得非常自信，且非常稳定。这正是概念漂移最危险的形态：所有无标签监控全绿。
  • 预测漂移也可以在没有任何漂移的情况下发生。 输入只是正常波动（大促期间账单类咨询变多），预测分布跟着变，模型本身完全健康。

所以三者的正确关系是：数据漂移和预测漂移是同一类东西——无标签的代理信号，便宜、及时、每个请求都有，但它们衡量的是”有东西变了”，不是”效果变差了”。概念漂移、以及带标签评估出来的真实性能下降，才是另一类。

为什么生产上最先看到的往往是预测漂移？因为标签要等。 真实标签来自人工标注、工单闭环或用户行为，快则几小时慢则几周；而预测分布是模型自己吐出来的，零延迟、零成本、每个请求都有。所以现实的优先级是：预测漂移当哨兵（最快最便宜）→ 数据漂移定位”输入侧发生了什么”→ 带标签的质量评估最慢但最权威。

一句话立规矩：数据漂移和预测漂移是调查信号，只能触发排查；带标签的真实效果下降才是决策信号，才能触发回滚或重训。 把预测漂移告警直接接上自动回滚，是这一章最常见的踩坑方式——大促当天流量结构一变，你的模型就被一个完全健康的分布变化自动回滚掉了。反过来，也别指望这两个代理信号能替你发现概念漂移，它们结构上就发现不了。

3. 记录什么

推理事件至少包含时间、请求 ID、模型版本、经过隐私处理的特征摘要、预测标签、置信度和延迟。不要默认保存原始用户文本。真实标签到达后，通过 request ID 或业务实体关联。

example 里的 app.py 已经在每次成功预测后写了一条结构化日志，这就是事件契约的雏形：

event = {
    "event": "prediction",
    "request_id": request.headers.get("X-Request-ID", "unknown"),
    "model_version": model_version,
    "label": str(state["model"].classes_[best]),
    "confidence": round(float(probabilities[best]), 6),
    "latency_ms": round(elapsed * 1000, 3),
}
logging.getLogger("intent_mlops.prediction").info(json.dumps(event))

它被采集进日志系统或数仓后就是离线漂移分析的原料。反馈到达时再补一条关联记录：

prediction_id: p-123
model_version: 17
predicted_label: billing
event_time: ...

稍后反馈：
prediction_id: p-123
actual_label: account
label_source: agent_correction

注意 request_id 必须由上游注入（网关生成 X-Request-ID），否则全都是 unknown，预测和标签就再也接不上了。这是反馈闭环里最容易在半年后才被发现的断点。

4. PSI：最常用的分布漂移量

PSI（Population Stability Index，总体稳定性指数）是风控和 ML 监控里用得最多的分布对比指标。思路很朴素：把基线和当前样本按同样的分箱切开，逐箱比较占比差异。

$$\mathrm{PSI} = \sum_i (a_i - e_i) \times \ln \frac{a_i}{e_i}$$

其中 $e_i$ 是基线（expected）第 $i$ 箱的占比，$a_i$ 是当前（actual）的占比。下面这段实现就是 example 里的 monitoring/psi.py，可以直接 python monitoring/psi.py 跑：

"""psi.py — 连续特征与离散标签的总体稳定性指数。"""
from __future__ import annotations

import numpy as np
import pandas as pd


def psi_numeric(expected, actual, bins: int = 10, eps: float = 1e-6) -> float:
    """连续特征 PSI：用基线的分位数定义分箱，再比较两侧占比。"""
    expected = np.asarray(expected, dtype=float)
    actual = np.asarray(actual, dtype=float)

    # 关键：分箱边界只由基线决定，否则两次分箱不可比
    quantiles = np.linspace(0, 100, bins + 1)
    edges = np.unique(np.percentile(expected, quantiles))
    if len(edges) < 3:                      # 基线几乎是常数，PSI 无意义
        return 0.0
    edges[0], edges[-1] = -np.inf, np.inf

    e_cnt, _ = np.histogram(expected, bins=edges)
    a_cnt, _ = np.histogram(actual, bins=edges)
    e_pct = np.clip(e_cnt / max(e_cnt.sum(), 1), eps, None)
    a_pct = np.clip(a_cnt / max(a_cnt.sum(), 1), eps, None)
    return float(np.sum((a_pct - e_pct) * np.log(a_pct / e_pct)))


def psi_categorical(expected, actual, eps: float = 1e-6) -> float:
    """离散分布 PSI：适用于预测标签占比这类天然分箱的数据。"""
    e = pd.Series(expected).value_counts(normalize=True)
    a = pd.Series(actual).value_counts(normalize=True)
    categories = e.index.union(a.index)
    e_pct = np.clip(e.reindex(categories, fill_value=0.0).to_numpy(), eps, None)
    a_pct = np.clip(a.reindex(categories, fill_value=0.0).to_numpy(), eps, None)
    return float(np.sum((a_pct - e_pct) * np.log(a_pct / e_pct)))


if __name__ == "__main__":
    rng = np.random.default_rng(42)
    base_conf = rng.beta(6, 2, 5000)     # 基线置信度分布
    print("confidence 无漂移 PSI =",
          round(psi_numeric(base_conf, rng.beta(6, 2, 5000)), 4))
    print("confidence 有漂移 PSI =",
          round(psi_numeric(base_conf, rng.beta(3, 3, 5000)), 4))

    labels = ["billing", "technical_support", "account"]
    print("label 分布 PSI =", round(psi_categorical(
        rng.choice(labels, 5000, p=[0.40, 0.35, 0.25]),
        rng.choice(labels, 5000, p=[0.65, 0.20, 0.15])), 4))

跑一次的输出（default_rng(42) 固定了随机种子，可复现）：

confidence 无漂移 PSI = 0.0033
confidence 有漂移 PSI = 1.8993
label 分布 PSI = 0.2758

同分布的两份样本 PSI 只有 0.003，噪声底很低；置信度分布换成 Beta(3,3) 后冲到 1.9，这种量级通常意味着”模型换了”或”上游数据源换了”，而不是渐进演化。标签那一例 0.276 刚过线，更接近真实生产的形态：需要立案调查，但不足以下结论。

常用判读区间（源自信用风控实践，不是数学定理）：

PSI通常解读建议动作
< 0.1稳定无需动作
0.1 – 0.25中度变化记录、观察趋势、看是否持续
> 0.25显著变化立案调查，先查数据管道再查模型

必须知道的局限，否则很容易被 PSI 误导：

  • 分箱敏感。 同一份数据，分 5 箱和分 20 箱能差出一倍以上。所以分箱规则必须固定并版本化——上面代码刻意让边界只由基线决定，而不是每次重新按当前数据分位。

  • 小样本不稳。 样本少的时候，两份来自同一分布的数据算出来的 PSI 也可能超过 0.1——这个”噪声底”完全由样本量决定，和有没有真漂移无关。所以必须设一个最小样本门槛，窗口内不够时跳过计算而不是照算，否则夜间低峰期会天天误报。

    代码里的 1000 是一个示例经验值，不是推导结果。有一种常见的说法是”10 箱 × 每箱 30 条 = 300，再乘 3 倍余量”——这个推导站不住：按基线分位数切箱时，各箱在基线上本来就是近似等频的，不存在”尾部箱天然稀疏”这回事（等宽分箱才有这个问题，而上面的代码用的是分位分箱）。

    正确的做法是测出来，而且不难：从你的基线数据里有放回地重复抽样两份大小为 N 的样本（自助法 / bootstrap），算 PSI，重复上千次，得到”同分布下 PSI 的分布”。看它的 p99 落在哪里——如果 N=500 时 p99 已经压到 0.05 以下，500 就够用；如果 N=1000 时 p99 还在 0.12，那 0.1 这条告警线在这个样本量下就是纯噪声，要么加大窗口，要么把阈值抬到噪声底之上。这套模拟顺带还给你另一个更有用的东西：这个数据分布下、这个样本量下的实际误报率。半小时的活，换掉一个抄来的数字。

  • 只看边缘分布。 每个特征单独看都没漂移，联合分布可能已经面目全非。PSI 检测不到特征之间相关性的变化。

  • 没有方向性和业务含义。 PSI = 0.3 只说”变了”，不说”变差了”。它是调查的起点，不是结论。

5. Evidently：离线深度诊断

PSI 适合放进定时任务算几个数，但要回答”到底哪个特征、往哪个方向漂了”，需要更完整的报告。Evidently 就是干这个的：给它基线和当前两个 DataFrame，它自动挑检验方法、算统计量、画分布对比图。

example 里的 monitoring/drift_report.py 就是这样一份骨架（Evidently 是离线分析依赖，不进推理镜像，所以没写进 pyproject.toml，缺依赖时脚本会直接提示安装命令并退出）：

"""drift_report.py — 每日离线漂移报告。"""
import pandas as pd
from evidently import Report
from evidently.presets import DataDriftPreset, TargetDriftPreset

# reference：训练集或上一个稳定周期的采样
reference = pd.read_parquet("data/reference_window.parquet")
# current：过去 24h 的推理事件（从日志/数仓回捞）
current = pd.read_parquet("data/current_window.parquet")

# 两份 DataFrame 至少包含：text_length / char_diversity 等特征摘要，
# 以及 prediction（预测标签）、confidence，有标签时再加 target
report = Report(metrics=[
    DataDriftPreset(),      # 输入特征分布漂移
    TargetDriftPreset(),    # 预测/标签分布漂移
])
snapshot = report.run(reference_data=reference, current_data=current)
snapshot.save_html("reports/drift-2026-07-27.html")

result = snapshot.dict()
print(result["metrics"][0])   # 供 CI 做门禁判断

把 HTML 产物挂到对象存储，再用 snapshot.dict() 的结构化结果驱动自动化——比如漂移特征数超阈值就开一张工单，而不是发一条会被无视的告警。

Evidently 的 API 在 0.4 → 0.7 之间有过较大调整（Report 从 evidently.report 移到顶层，metric preset 改名）。升级前对照当时的官方文档，不要照抄旧博客。

Evidently 和 Prometheus 的分工要说清楚，这是很多团队混用两套工具却都没用好的原因：

Prometheus / GrafanaEvidently
定位在线实时告警离线深度诊断
数据时序聚合值（counter / histogram）明细样本 DataFrame
延迟秒级小时 / 天级
回答的问题“现在有没有出事”“到底出了什么事”
保留期通常 15–30 天，降采样报告归档，可长期回溯

一句话：Prometheus 负责把你叫醒，Evidently 负责让你在被叫醒后 10 分钟内知道该看哪。 不要试图用 PromQL 做特征级分布诊断——你会写出一堆无法维护的 recording rule；也不要指望 Evidently 报告能在 5 分钟内触达 on-call。

6. 真实的告警规则

example 仓库的 monitoring/prometheusrule.yaml 里有三条规则，配合 servicemonitor.yaml（每 30s 抓一次 /metrics）工作。先看第一条：

- alert: IntentApiHighErrorRatio
  expr: |
    sum(rate(intent_api_requests_total{status!="success"}[5m]))
    /
    clamp_min(sum(rate(intent_api_requests_total[5m])), 0.001)
    > 0.02
  for: 10m
  labels: {severity: warning}
  annotations:
    summary: Intent API non-success ratio exceeds 2%

它在防什么： 非成功请求占比超过 2%。intent_api_requests_total 的 status 标签在 app.py 里取四个值——success / invalid（400）/ too_long（413）/ not_ready（503），所以这条规则同时覆盖三类故障：模型没加载（not_ready 突增，通常是新版本 artifact 路径错了）、上游改了请求格式（invalid 突增）、有人开始灌超长文本（too_long 突增）。

两个工程细节值得学：clamp_min(..., 0.001) 防的是零流量时分母为 0 产生 NaN，低峰期没有请求时不该告警；for: 10m 防的是瞬时抖动。

第二条：

- alert: IntentApiHighP95Latency
  expr: |
    histogram_quantile(0.95,
      sum by (le) (rate(intent_api_prediction_seconds_bucket[5m])))
    > 0.15
  for: 10m
  labels: {severity: warning}
  annotations:
    summary: Intent API p95 prediction latency exceeds 150 ms

它在防什么： 推理变慢。常见诱因是换了更大的模型、输入文本变长、或者 Pod 被压到了 CPU limit。

这里有一个必须记住的口径问题：intent_api_prediction_seconds 在 app.py 里只包住了 predict_proba 那一行，不含 JSON 反序列化、Flask 路由、Gunicorn 排队和网络往返。所以当用户抱怨”接口慢”而这条告警安静如鸡时，不要怀疑 Prometheus 坏了——是这个指标本来就不测那一段。真实的用户侧延迟要靠 ingress 或 service mesh 的 RED 指标来看，第 19 篇会展开”指标口径与 SLO 对不齐”这条线。

monitoring/README.md 里的另一条提醒同样重要：示例镜像是单 Gunicorn 进程 + 多线程，进程内计数天然一致。若在一个 Pod 里开多个 worker，必须配 PROMETHEUS_MULTIPROC_DIR 和 multiprocess collector，否则每次抓取只采到随机一个 worker 的计数，指标会忽高忽低。更省事的做法是保持单进程，靠 HPA 横向扩。

第三条针对的正是本篇的主题：预测标签分布。intent_api_requests_total 只按 status 和 model_version 打标签，没有 label 维度，在线就看不到预测漂移，所以 app.py 里单独加了一个计数器：

PREDICTIONS = Counter(
    "intent_api_predictions_total", "Predictions by label", ["label", "model_version"]
)
# 在 predict() 成功分支里：
PREDICTIONS.labels(label, model_version).inc()

对应的告警按”某一类占比持续过高”来写：

- alert: IntentApiPredictionSkew
  expr: |
    max(
      sum by (label) (rate(intent_api_predictions_total[30m]))
      / on() group_left()
      clamp_min(sum(rate(intent_api_predictions_total[30m])), 0.001)
    )
    > 0.6
  for: 30m
  labels: {severity: info}
  annotations:
    summary: One intent label exceeds 60% of predictions over 30m

/ on() group_left() 不能省。分子 sum by (label) 带着 label 标签、分母 sum() 把标签全丢光了，而 PromQL 的二元运算默认按全部标签匹配——两侧标签集不同，匹配不上，结果是空向量，max() 空、告警永远 Inactive。on() 表示”按空标签集匹配”，group_left() 声明左侧是多对一里的”多”并保留它的 label。这类”规则语法合法、YAML 校验通过、上线后安静得像没事发生”的错误，只能靠在真实数据上跑一次 promtool test rules 或手工推演标签集来发现。

注意它只标 severity: info——它是调查信号，不是决策信号，不该半夜叫醒 on-call，更不该接自动回滚。标签基数也要控住：三类意图没问题，但绝不要把 request_id、用户 ID 或原始文本放进 label，那是把 Prometheus 打爆的最快方式。

7. 基线与窗口

比较对象应是已批准训练集、上一稳定周期或季节性对应窗口。“上周同一时段”通常比”昨天”更好——很多业务的周内节律比趋势变化更强，拿周一比周日必然报漂移。另外三点：窗口内样本不足就跳过计算并标记 insufficient_data，别算出一个数就告警；按语言、地区、渠道分片看，”整体 PSI 0.08”完全可能是”英语 0.02 + 西语 0.41”的平均；基线要版本化并定期重设，通常每次重训练上线后切到新训练集，否则监控会一直拿远古数据当真理。

小结

模型监控把”服务活着”升级为”模型持续创造正确结果”。三种漂移要分开看：数据漂移不需要标签、概念漂移必须要标签、预测漂移最快到达因而最适合当哨兵。PSI 便宜好用但对分箱和样本量敏感，只能当调查起点；Evidently 做离线深度诊断，Prometheus 做在线实时告警，两者分工而非替代。基线要版本化，窗口要分片看，样本不足就别算。

到这里，你已经能看见漂移了——但看见只是第一步。分布变了不等于模型变差了，告警响了也不等于该重训练。真实标签什么时候回来、回来之后怎么用、什么条件下才允许换掉线上模型，这些才是把监控变成闭环的部分，也是下一篇的主题。
