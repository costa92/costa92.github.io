第 5 / 25 节 · 训练、数据与实验

上一篇训练出的 intent-model.joblib 只是磁盘上的一个文件，前端、客服系统或其他微服务没法直接 import 它。要让它对外服务，需要三件事：一份稳定的请求协议、一个把模型包成 HTTP 接口的进程、一个能在任何机器上原样跑起来的容器。这一篇把意图分类模型做成一个最小可用的在线推理服务。

1. API 契约

先定协议，再写代码。契约稳定了，前后端才能并行开发，模型内部怎么换都不影响调用方。

请求：只接受一个字段 text。

{"text": "为什么我这个月被重复扣款了"}

响应：返回标签、置信度、模型版本，以及本次推理耗时。

{
  "label": "billing",
  "confidence": 0.913204,
  "model_version": "intent-v1",
  "latency_ms": 2.317
}

几个约定要在契约阶段就写死：

  • 调用方只依赖标签名（billing / technical_support / account），不依赖类别数组的内部下标顺序——model.classes_ 的顺序会随重训变化。
  • model_version 同时进响应体和日志。线上出问题时，第一件事就是确认”到底是哪个版本在服务”。
  • confidence 是 predict_proba 的最大概率，不是校准后的真实概率，业务侧不能未经验证就当风险分数用。

2. Flask 应用

先补依赖——第 03 篇的 pyproject.toml 只装了训练闭环需要的三个包，这一篇要用的 Flask、Prometheus 客户端和 gunicorn 都还没有：

[project]
dependencies = [
  "Flask>=3.1,<4",
  "gunicorn>=23,<24",
  "joblib>=1.4,<2",
  "pandas>=2.2,<4",
  "prometheus-client>=0.21,<1",
  "PyYAML>=6,<7",
  "scikit-learn>=1.6,<2",
]
pip install -e '.[dev]'

（PyYAML 是训练侧读 params.yaml 用的，见第 03 篇末尾那条注记。）

用工厂函数 create_app() 构建应用，而不是在模块顶层直接建全局 app。工厂模式的好处是测试时能注入不同的模型路径，各测试用例互不污染。

# intent_mlops/app.py
from __future__ import annotations

import json
import logging
import os
import time
from pathlib import Path

import joblib
from flask import Flask, jsonify, request
from prometheus_client import CONTENT_TYPE_LATEST, Counter, Histogram, generate_latest

DEFAULT_MODEL = Path("artifacts/intent-model.joblib")
DEFAULT_METADATA = Path("artifacts/metadata.json")

REQUESTS = Counter(
    "intent_api_requests_total", "Prediction requests", ["status", "model_version"]
)
LATENCY = Histogram(
    "intent_api_prediction_seconds", "Prediction latency", ["model_version"]
)


def create_app(model_path: Path | None = None, metadata_path: Path | None = None) -> Flask:
    app = Flask(__name__)
    selected_model = model_path or Path(os.getenv("MODEL_PATH", str(DEFAULT_MODEL)))
    selected_metadata = metadata_path or Path(
        os.getenv("MODEL_METADATA_PATH", str(DEFAULT_METADATA))
    )

    state: dict = {"model": None, "metadata": {}}
    if selected_model.exists():
        state["model"] = joblib.load(selected_model)
    if selected_metadata.exists():
        state["metadata"] = json.loads(selected_metadata.read_text(encoding="utf-8"))

    @app.get("/healthz")
    def healthz():
        return {"status": "alive"}

    @app.get("/readyz")
    def readyz():
        if state["model"] is None:
            return {"status": "not_ready"}, 503
        return {
            "status": "ready",
            "model_version": state["metadata"].get("model_version", "unknown"),
        }

    @app.get("/metrics")
    def metrics():
        return generate_latest(), 200, {"Content-Type": CONTENT_TYPE_LATEST}

    @app.post("/predict")
    def predict():
        if state["model"] is None:
            REQUESTS.labels("not_ready", "unknown").inc()
            return jsonify({"error": "model is not loaded"}), 503

        payload = request.get_json(silent=True) or {}
        text = payload.get("text")
        if not isinstance(text, str) or not text.strip():
            REQUESTS.labels("invalid", "unknown").inc()
            return jsonify({"error": "text must be a non-empty string"}), 400
        if len(text) > 2000:
            REQUESTS.labels("too_long", "unknown").inc()
            return jsonify({"error": "text is too long"}), 413

        started = time.perf_counter()
        probabilities = state["model"].predict_proba([text])[0]
        best = int(probabilities.argmax())
        model_version = state["metadata"].get("model_version", "unknown")
        elapsed = time.perf_counter() - started

        REQUESTS.labels("success", model_version).inc()
        LATENCY.labels(model_version).observe(elapsed)

        event = {
            "event": "prediction",
            "request_id": request.headers.get("X-Request-ID", "unknown"),
            "model_version": model_version,
            "label": str(state["model"].classes_[best]),
            "confidence": round(float(probabilities[best]), 6),
            "latency_ms": round(elapsed * 1000, 3),
        }
        logging.getLogger("intent_mlops.prediction").info(json.dumps(event))

        return jsonify(
            {
                "label": str(state["model"].classes_[best]),
                "confidence": round(float(probabilities[best]), 6),
                "model_version": model_version,
                "latency_ms": round(elapsed * 1000, 3),
            }
        )

    return app


app = create_app()

这段代码有几个刻意的设计：

  • 模型只加载一次。create_app() 在启动时 joblib.load 一次，放进 state，之后每个请求复用，不在请求里重复读盘。
  • 健康检查拆成两个。/healthz（liveness，存活探针）只回 {"status": "alive"}，证明进程没死；/readyz（readiness，就绪探针）会检查模型是否真加载了，没加载就返回 503 not_ready。存活和就绪是两回事：进程活着但模型没就绪时，不该往它发流量。
  • 输入校验在推理之前。非字符串、空串、超长（>2000 字符）分别返回 400 和 413，而不是让脏输入进到 predict_proba 里抛一个笼统的 500。模型没加载时 /predict 直接回 503，与就绪探针语义一致。
  • 可观测性内建。/metrics 暴露 Prometheus 指标：intent_api_requests_total（按 status 和 model_version 打标签的请求计数）和 intent_api_prediction_seconds（推理延迟直方图）。仓库里的 app.py 还有第三个指标 intent_api_predictions_total{label, model_version}——它是第 17 篇为了在线观测预测分布漂移加上的，这里先不引入，以免把”服务可观测性”和”模型可观测性”混成一团。对照仓库时不必怀疑自己抄漏了。每次成功推理还打一条结构化 JSON 日志，带 request_id、model_version、label、confidence、latency_ms——注意日志里记的是结果概要，不落原始文本。

model_version 来自训练阶段产出的 artifacts/metadata.json，缺失时降级为 "unknown"，服务不会因为读不到元数据就崩。

3. 本地验证

开发期可以用 Flask 自带服务器快速起，生产用 Gunicorn（下一节容器里用的就是它）：

# 开发服务器（仅本地调试）
flask --app intent_mlops.app run --host 0.0.0.0 --port 8080

# 或直接用生产同款启动方式
gunicorn --bind 0.0.0.0:8080 --workers 1 --threads 4 "intent_mlops.app:create_app()"

逐个探针和接口打一遍：

# 存活探针
curl -s http://localhost:8080/healthz
# {"status":"alive"}

# 就绪探针（模型已加载时）
curl -s http://localhost:8080/readyz
# {"status":"ready","model_version":"intent-v1"}

# Prometheus 指标
curl -s http://localhost:8080/metrics | grep intent_api

# 正常预测
curl -s -X POST http://localhost:8080/predict \
  -H 'Content-Type: application/json' \
  -d '{"text":"我的账单这个月为什么变多了"}'
# {"label":"billing","confidence":0.91...,"model_version":"intent-v1","latency_ms":2.3...}

别只测 happy path。下面这些异常路径也要验证，它们才是接口稳定性的分水岭：

# 空 JSON → 400
curl -s -X POST http://localhost:8080/predict \
  -H 'Content-Type: application/json' -d '{}'

# 字段类型错误 → 400
curl -s -X POST http://localhost:8080/predict \
  -H 'Content-Type: application/json' -d '{"text":123}'

# 不支持的方法 → 405（GET 打到只允许 POST 的 /predict）
curl -s http://localhost:8080/predict

接口测试不只看状态码，还要看字段类型和标签集合是否在约定范围内。对应的 pytest 用例长这样：

# tests/test_app.py
from pathlib import Path

from intent_mlops.app import create_app
from intent_mlops.train import train


def make_client(tmp_path):
    train(Path("data/intents.csv"), tmp_path)
    app = create_app(tmp_path / "intent-model.joblib", tmp_path / "metadata.json")
    app.config.update(TESTING=True)
    return app.test_client()


def test_health_and_readiness(tmp_path):
    client = make_client(tmp_path)
    assert client.get("/healthz").status_code == 200
    assert client.get("/readyz").status_code == 200
    metrics = client.get("/metrics")
    assert metrics.status_code == 200
    assert b"intent_api_requests_total" in metrics.data


def test_prediction_contract(tmp_path):
    client = make_client(tmp_path)
    response = client.post("/predict", json={"text": "我无法登录"})
    body = response.get_json()
    assert response.status_code == 200
    assert body["label"] in {"billing", "technical_support", "account"}
    assert 0 <= body["confidence"] <= 1
    assert body["latency_ms"] >= 0


def test_invalid_prediction_input(tmp_path):
    client = make_client(tmp_path)
    assert client.post("/predict", json={}).status_code == 400

make_client 用 create_app 的参数注入到 tmp_path 下的临时模型，这正是工厂模式换来的可测性——每个用例拿到一份干净的、隔离的服务实例。

4. Dockerfile

容器解决的是”在我机器上能跑”的问题。把 Python 版本、依赖、模型、启动命令全固定进镜像，交付物就变成一个可复现的单元。

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    MODEL_PATH=/app/artifacts/intent-model.joblib \
    MODEL_METADATA_PATH=/app/artifacts/metadata.json

WORKDIR /app
COPY pyproject.toml README.md ./
COPY src/ ./src/
COPY data/ ./data/
RUN pip install --no-cache-dir . && \
    python -m intent_mlops.validate && \
    python -m intent_mlops.train && \
    useradd --create-home --uid 10001 appuser

USER appuser
EXPOSE 8080
CMD ["gunicorn", "--bind", "0.0.0.0:8080", "--workers", "1", "--threads", "4", "intent_mlops.app:create_app()"]

几个关键点：

  • 构建期先校验再训练。python -m intent_mlops.validate 先做数据体检，python -m intent_mlops.train 在镜像里现训一份模型落到 artifacts/。数据不合格就让 docker build 直接失败，坏模型不会被打进镜像。
  • 非 root 运行。建一个 uid 10001 的 appuser 并 USER appuser，容器进程不以 root 身份跑，缩小被攻破后的影响面。
  • Gunicorn 而非开发服务器。启动命令用 gunicorn ... "intent_mlops.app:create_app()"——注意这里传的是工厂函数调用字符串，Gunicorn 会自己调 create_app() 拿到 app。--workers 1 --threads 4 只是一个起点配置，不是推荐值。这里要破除一个常见误判：TF-IDF 向量化 + 逻辑回归的推理是纯 CPU 计算，不是 I/O 等待——请求进来之后没有任何网络调用或磁盘读写，全程在算矩阵乘法。所以”加线程就能提并发”这个 Web 服务的直觉在这里不成立：多线程能不能真的并行，取决于底层库在计算时是否释放 GIL。numpy / scipy 的 BLAS 运算通常会释放，纯 Python 层的代码不会，实际能吃到多少并行度只能压测出来。真实的调参顺序是：先压测出单进程的 CPU 饱和点和 p95 延迟曲线，再决定加 worker（进程，能真正吃满多核，代价是每个进程一份模型内存）还是加 thread。还要注意 worker 数和 BLAS 自身的线程数会相乘打架，CPU 核数少时通常要显式设 OMP_NUM_THREADS=1 把底层线程关掉，让并发交给 worker 管。

构建和运行：

docker build -t intent-api:v1 .
docker run -d -p 8080:8080 --name intent-api intent-api:v1
docker ps

# 起来后同样打一遍探针
curl -s http://localhost:8080/readyz
curl -s -X POST http://localhost:8080/predict \
  -H 'Content-Type: application/json' \
  -d '{"text":"账号被锁了怎么解封"}'

这里把模型直接烤进镜像，镜像和模型天然原子化：一次 docker run 就是一个确定的”代码 + 模型”组合，回滚只需切回上一个 tag。代价是模型大或更新频繁时，构建和分发成本高。另一条路是启动时从对象存储（S3 / MinIO）按 MODEL_PATH 下载指定模型，镜像只装代码。两种模式的取舍会在 KServe 篇里展开对比。

5. Compose 编排与安全加固

单机跑或本地联调，用 Compose 比手敲 docker run 参数更省事，也顺手把安全基线固定下来：

# compose.yaml
services:
  intent-api:
    build: .
    ports:
      - "8080:8080"
    read_only: true
    tmpfs:
      - /tmp
    security_opt:
      - no-new-privileges:true
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8080/readyz')"]
      interval: 10s
      timeout: 3s
      retries: 5
docker compose up --build

这份配置做了三层收敛：

  • read_only: true + tmpfs: /tmp——根文件系统只读，只给 /tmp 留一块可写的内存盘。推理服务本来就不该在运行时改自己的文件，只读能挡住一大类被写入 webshell 的路子。
  • no-new-privileges:true——禁止容器内进程通过 setuid 提权。
  • healthcheck 打的是 /readyz 而不是 /healthz。编排系统关心的是”能不能接流量”，模型没就绪就该判定不健康，这跟上面探针的语义是一致的。

6. 生产注意事项

这套东西是最小可用闭环，能跑通”请求进、预测出”，但离生产级还差不少，认证、限流、监控告警、版本治理都得另外补：

  • WSGI 服务器。Flask 开发服务器（app.run）单线程、无并发保护，官方明确说了不能用于生产，所以镜像里用 Gunicorn。worker/thread 数得根据压测结果和实例规格调，不是拍脑袋填 1 和 4。

  • 反序列化风险。joblib.load 底层是 pickle，加载不可信文件可能执行任意代码。模型来源必须受控，最好校验摘要（如 SHA256）后再加载。

  • 日志脱敏。不落完整敏感文本；日志只留 request_id、model_version、延迟和结果概要，方便排查又不泄漏用户内容。

  • 置信度不等于概率。confidence 没经过校准（calibration），业务拿它当阈值前要先在真实数据上验证它的可靠性。怎么验证：把线上预测按置信度分箱（如 0.5–0.6、0.6–0.7…），等真实标签回来后统计每箱的实际正确率，再和箱的中值比——如果 0.9 那一箱实际只对了 70%，这个模型就是”过度自信”的，confidence > 0.9 就自动放行这类规则会系统性地放错。画出来的那张图叫可靠性曲线（reliability diagram），理想情况是一条 45° 直线。sklearn 的 CalibratedClassifierCV（Platt scaling / isotonic regression）可以做后处理校准。校准分两次做，别把它整个推迟到上线之后：

  • 预上线校准：只要你手里的训练数据带标签，上线前就能做——从训练集里再切一份独立的校准集，或者直接用 CalibratedClassifierCV(cv=5) 做交叉验证式校准（它在内部折上拟合校准曲线，不需要额外留数据）。这一步能拿到一个”在训练分布下大致可信”的概率，足以支撑上线初期的阈值设定。硬约束只有一条：校准数据不能和最终测试集有任何重叠——用测试集拟合校准曲线，再用同一份测试集报告校准效果，得到的可靠性曲线必然好看，且毫无意义。

  • 上线后再校准：预上线校准的前提是线上分布和训练分布一致，而这个前提会随时间失效。所以真实标签通过第 18 篇的反馈闭环回流之后，要用线上数据重新画一次可靠性曲线、重新拟合校准，并把它纳入常规复核。

在拿到第一版校准之前，confidence 只适合用来排序（挑出最不确定的样本送人工），不适合当绝对阈值。

  • 探针语义。readiness 必须验证模型已加载（/readyz 已经这么做）；liveness 不要依赖外部慢服务，否则下游一抖，你的实例会被误杀重启。
  • 认证与限流。当前接口对任何人开放且不限速，上线前至少要加 API key/网关鉴权和基本的速率限制。

小结

模型服务的核心是稳定的契约加上围绕它的工程，而不是随手加一个 /predict 路由。容器解决环境一致性；工厂模式换来可测性；存活/就绪探针、输入校验、指标与结构化日志、非 root 与只读文件系统，这些才决定了它上线之后能不能可靠地活着。下一篇开始，我们把注意力从”服务模型”转向”管住数据”，用 DVC 给数据集上版本。
