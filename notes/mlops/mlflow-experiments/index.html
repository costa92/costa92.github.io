第 8 / 25 节 · 训练、数据与实验

第 06 篇搭好了 MLflow 服务，这一篇让训练代码真正使用它。一次 run（运行记录）应把输入版本、参数、指标和输出制品联系起来，而不是只记录一个最终分数。做实验跟踪（experiment tracking）不是为了留下漂亮的曲线，而是让”哪个模型、用什么数据、跑出什么结果”这件事在几个月后仍然说得清楚。

1. Experiment 与 Run

MLflow 用两级结构组织训练历史：

  • Experiment（实验） 是一组相关尝试的逻辑分组，相当于一个项目，例如 intent-classifier。同一个意图分类任务的所有调参、换模型、换数据的尝试都归到这一个 experiment 下，才能横向比较。
  • Run（运行记录） 是一次具体训练。每个 run 独立保存自己的参数（params）、指标（metrics）、标签（tags）和制品（artifacts），并拥有一个全局唯一的 run_id。

最小骨架就是”设置 tracking 地址 → 选 experiment → 在 start_run() 上下文里记录一切”：

import os
import mlflow
import mlflow.sklearn

mlflow.set_tracking_uri(os.environ["MLFLOW_TRACKING_URI"])
mlflow.set_experiment("intent-classifier")

with mlflow.start_run() as run:
    mlflow.log_params({
        "vectorizer": "tfidf",
        "ngram_max": 2,
        "classifier": "logistic_regression",
        "C": 1.0,
    })
    mlflow.set_tags({
        "git_commit": os.getenv("GIT_SHA", "local"),
        "dataset_version": os.getenv("DATA_VERSION", "unknown"),
        "owner": "customer-platform",
    })

    model.fit(x_train, y_train)
    prediction = model.predict(x_test)
    macro_f1 = f1_score(y_test, prediction, average="macro")
    mlflow.log_metric("macro_f1", macro_f1)

    mlflow.log_artifacts("artifacts", artifact_path="intent-model")
    print(run.info.run_id)

with mlflow.start_run() 是关键：进入时开一条 run，正常退出时自动标记为 FINISHED，抛异常时标记为 FAILED。你几乎不需要手动 end_run()。run.info.run_id 是这次训练的身份证，后面注册模型、追溯问题都靠它。

dataset_version 可以使用 DVC 文件摘要或数据快照 ID。没有这个字段，实验仍不能完整复现——同样的代码在两份不同的数据上会得到不同的模型，而 UI 里看不出区别。

本系列 example 工程里的 train_mlflow.py 就是这个骨架的落地版：它从环境变量读 MLFLOW_TRACKING_URI 和 experiment 名，调用真实的 train() 得到模型与指标，用 log_params 记录 algorithm / git_sha / dataset_sha256 以及本次生效的全部超参，用 log_metrics 一次记录 macro/weighted F1、三个类别各自的 recall 和粗测的 p95_inference_ms（后两类正是第 15 篇离线门禁要读的，只记一个总分会让门禁永远拿不到数据），再用 log_artifacts(...) 把整个制品目录上传，最后打印 run_id。下面各小节的 API 都以它为准。

从命令行批量产出 run

实验跟踪的价值在”多次”。前提是训练脚本真的可参数化——example 里的 train.py 用 load_params() 从 params.yaml 读超参，并允许同名环境变量临时覆盖（NGRAM_MAX、C、MAX_ITER 等），train_mlflow.py 再把最终生效的这组参数原样 log_params 上去。于是不同超参各跑一次，就自然积累出可比较的 run：

# 基线：完全按 params.yaml
python -m intent_mlops.train_mlflow

# 换更小的 n-gram 上界与更强的正则，各产出一个 run
NGRAM_MAX=3 C=0.5 python -m intent_mlops.train_mlflow
NGRAM_MAX=2 C=2.0 python -m intent_mlops.train_mlflow

它们共享同一个 experiment（intent-classifier），于是 MLflow UI 里会出现一张可排序、可对比的 run 列表。这正是”实验跟踪”取代 Excel 手记的地方。

如果超参还硬编码在 train() 里，这三条命令会产出三个参数完全相同的 run——UI 上看着像 MLflow 坏了，其实是脚本没接参数。先确认参数进得去，再谈对比。 另外示例数据集只有 30 行，三次 run 的 macro_f1 很可能一模一样；这不影响演示，但提醒一件事：样本量不足时，指标差异不具备可比性。

2. 记录什么：params、metrics、artifacts

MLflow 只提供四类原语，用对它们比写多少代码更重要。

Params（参数）——一次 run 固定不变的输入。 单个用 log_param，一批用 log_params：

mlflow.log_param("ngram_max", 2)
mlflow.log_params({
    "algorithm": "tfidf-logistic-regression",
    "git_sha": os.getenv("GIT_SHA", "local"),
    "dataset_sha256": dataset_sha256,   # 数据指纹，复现的前提
})

params 记的是”你决定了什么”：算法、超参、数据版本、特征方案。它们在一次 run 内不变，所以适合当作比较不同 run 的 X 轴。

Metrics（指标）——训练/评估过程中测出来的数。 单个用 log_metric，一批用 log_metrics：

mlflow.log_metric("macro_f1", macro_f1)
mlflow.log_metrics({
    "weighted_f1": weighted_f1,
    "billing_recall": billing_recall,
    "technical_support_recall": ts_recall,
    "p95_inference_ms": p95_latency,
})

metric 支持 step 参数，可以记录随 epoch 或迭代变化的序列，MLflow UI 会画成曲线：

for epoch, val_f1 in enumerate(history):
    mlflow.log_metric("val_macro_f1", val_f1, step=epoch)

Artifacts（制品）——落到磁盘的任何文件。 单个文件用 log_artifact，整目录用 log_artifacts：

# 单个文件：一份评估报告
mlflow.log_artifact("artifacts/metrics.json")

# 整个目录：把 vectorizer、模型、混淆矩阵图一起归档到 intent-model/ 下
mlflow.log_artifacts("artifacts", artifact_path="intent-model")

example 工程用的是后者——log_artifacts(ARTIFACTS, artifact_path="intent-model") 一次把整个制品目录传上去，因为意图分类的模型不是单个 .pkl，而是 TF-IDF 向量器 + 分类器 + 标签映射的组合，必须打包在一起才能复原。

flavored model（带风味的模型）——可选的第五种。 如果想让 MLflow 记住”这是个 sklearn 模型”、以后能用统一接口加载和上线，可以用 flavor API：

mlflow.sklearn.log_model(model, name="model")
# 之后任意 run 都能：mlflow.pyfunc.load_model(f"runs:/{run_id}/model")

它和 log_artifacts 不冲突：前者存”可直接加载的标准模型对象”，后者存”复现和审计需要的全套原始文件”。两条路都记，上线与追溯就都不缺东西。

不要只记录最好看的指标

意图分类应至少记录：

  • macro F1 和 weighted F1（前者每类等权，小类别退化藏不住；后者按样本量加权，更贴近整体体验。两个一起记：只看 weighted 会漏掉小类别崩塌，只看 macro 会把一个占比 1% 的类别的波动放大成全局警报）；
  • 每个类别的 precision、recall、F1；
  • confusion matrix（混淆矩阵）；
  • 训练和推理耗时（尤其 p95 延迟）；
  • 数据量及类别分布；
  • 模型文件大小。

平均指标可能掩盖关键类别退化。例如账单类提高 2%，技术故障类 recall 却下降 20%，整体 macro F1 看着还涨了——是否上线要由业务错误成本来判断，而不是一个总分。把这些都作为 metric 记进 run，比较时才能一眼看穿”平均值陷阱”。

3. 比较 Runs 与选择候选模型

积累出多个 run 后，比较有两种方式。

在 UI 里比较。 打开 MLflow UI，选中同一 experiment 下的多个 run，点 Compare，就能得到并排的参数-指标表和散点/平行坐标图。如果 MLflow 按第 06 篇那样跑在 Kubernetes 上，先把服务转发到本地再用浏览器访问：

kubectl port-forward svc/mlflow 5000:80 -n mlflow --address 0.0.0.0
# 浏览器打开 http://localhost:5000

在代码里比较。 UI 适合人看，自动化流程要用 MlflowClient 或 mlflow.search_runs 按指标排序、按条件过滤：

import mlflow

runs = mlflow.search_runs(
    experiment_names=["intent-classifier"],
    order_by=["metrics.macro_f1 DESC"],
)
best = runs.iloc[0]
print(best["run_id"], best["metrics.macro_f1"])

这就把”谁是最好的 run”从人工翻 UI 变成了可复现、可审计的查询。

入门级超参搜索

改变 TF-IDF 的 n-gram、正则化参数或分类器，为每个组合创建一个 run，是最朴素也最够用的超参调优（hyperparameter tuning）。但有一条不能省的纪律：搜索过程中绝对不许碰测试集。

先说清楚为什么。如果每个组合都在 x_test 上评一次、再按分数挑冠军，那么”哪套参数最好”这个决策就是测试集参与做出的，最后报出来的分数必然偏乐观——你挑的既是真实优势，也是这一次切分上的运气。这个陷阱叫 测试集污染（test set contamination），也叫 data snooping（数据窥探）。它比”数据泄漏”更准确地描述了这里发生的事：特征里没混进未来信息，是人在选择过程中反复消费了那份本应只用一次的数据。搜索的组合越多，虚高越明显——10 个组合里挑最高分，本身就是在挑噪声。

正确的做法是把选参和最终评估彻底分开：选参只在训练集内部做交叉验证，测试集留到最后评一次。

import numpy as np
from sklearn.model_selection import StratifiedKFold, cross_val_score

grid = [
    {"ngram_max": 1, "C": 1.0},
    {"ngram_max": 2, "C": 1.0},
    {"ngram_max": 2, "C": 0.5},
    {"ngram_max": 3, "C": 2.0},
]

# 分层 K 折：每一折都保持各类别比例，小类别不会被整折划走
cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)

for params in grid:
    with mlflow.start_run(run_name=f"ngram{params['ngram_max']}-C{params['C']}"):
        mlflow.log_params(params)
        scores = cross_val_score(
            build_pipeline(params),        # 注意传的是未 fit 的 Pipeline
            x_train, y_train,              # 只用训练集
            cv=cv,
            scoring="f1_macro",
        )
        # 均值是选参依据，标准差是"这个差距是不是噪声"的判据
        mlflow.log_metric("cv_macro_f1_mean", float(scores.mean()))
        mlflow.log_metric("cv_macro_f1_std", float(scores.std()))

这里有两个细节值得单说。一是传给 cross_val_score 的必须是未 fit 的整条 Pipeline，而不是已经 fit 好的模型或提前算好的 TF-IDF 矩阵——否则每一折的验证部分都参与了词表和 IDF 的统计，交叉验证本身就被污染了，第 03 篇把向量化器塞进 Pipeline 在这里再次派上用场。二是要同时记录均值和标准差：cv_macro_f1_mean 差 0.01、而标准差有 0.05 时，这两套参数在统计上没有区别，按均值排序挑出来的”冠军”只是噪声的胜利。这种情况下选更简单的那套（更小的 ngram_max、更小的 C）。

选定之后才动测试集，而且只动一次：

best_params = max(grid, key=lambda p: cv_mean[str(p)])   # 决策已经锁定

with mlflow.start_run(run_name="final"):
    mlflow.log_params(best_params)
    final_model = build_pipeline(best_params).fit(x_train, y_train)
    # 整个流程中 x_test 第一次、也是唯一一次出现
    mlflow.log_metric("test_macro_f1", evaluate(final_model, x_test, y_test))

这个 test_macro_f1 才是能对外报的数字，前面那些 cv_* 指标只用于内部比较。如果拿到测试分数后你不满意，回头再改参数重挑，测试集就作废了——它已经进了决策循环。真到了这一步，诚实的做法是承认这一轮的测试分数不可信，另切一份数据出来。

跑完一次循环，experiment 里就多了一批可排序的 run，用上面的 search_runs 直接挑冠军——注意排序字段要用 cv_macro_f1_mean 而不是 test_macro_f1。等这套流程稳定了，再换成 Optuna、Hyperopt 这类带搜索策略的库也只是替换循环体，记录方式和”测试集只用一次”这条纪律都不变。

本仓库的示例代码是单次 train/test 切分，没有交叉验证。 那是为了让第 03 篇能用最少的行数讲清楚”训练→制品→元数据”这条链路，30 行数据也撑不起 5 折。真实项目请按上面这套来：交叉验证选参、测试集只评一次。仓库里那个 macro-F1 数字验证的是流水线跑通了，不是模型有多好。

选择不能只看单一指标

选择模型时不能简单按 macro F1 排序，还要检查稳定性、延迟、容量和可解释性。建议把选择条件写成代码，而不是靠工程师在 UI 里手动挑：

eligible = (
    metrics["macro_f1"] >= 0.82
    and metrics["technical_support_recall"] >= 0.78
    and metrics["p95_inference_ms"] <= 50
)

这比 UI 手选更可审计——门禁条件进了 git，谁改了标准、什么时候改的都有据可查。

4. 从 Tracking 到 Registry

Tracking 记录”发生过什么”；Model Registry（模型注册表）管理”准备交付的模型版本及其生命周期”。二者职责不同：一个 experiment 里可能有几百个 run，但只有极少数值得晋升为受管理的模型版本。

把某个 run 的模型注册出来，可以在训练时直接注册，也可以事后按 run_id 注册：

# 方式一：训练时顺手注册
mlflow.sklearn.log_model(
    model,
    name="model",
    registered_model_name="intent-classifier",
)

# 方式二：事后把已有 run 的制品注册为一个新版本
result = mlflow.register_model(
    model_uri=f"runs:/{run_id}/model",
    name="intent-classifier",
)
print(result.version)   # v1, v2, ...

注册后用 MlflowClient 推进生命周期阶段（现代 MLflow 推荐用 alias 或 tag，老版本用 stage）：

from mlflow import MlflowClient

client = MlflowClient()
client.set_registered_model_alias("intent-classifier", "staging", version="3")
# 验证通过后再提升：
client.set_registered_model_alias("intent-classifier", "production", version="3")

常见流程是：

注册模型时应保留源 run、代码 commit、数据版本和评估报告——它们通过 run_id 已经串在一起了。不要下载一个模型后手工改名为 final_v7_really_final.pkl：那一刻你就丢掉了它从哪个 run、哪份数据、哪次 commit 来的全部线索。

5. 常见反模式

  • 开启 mlflow.autolog() 后以为所有业务语义都已记录——autolog 只抓框架层面的参数和指标，类别级 recall、延迟、数据版本这些业务关键项它不知道，仍要你手动 log_metric；
  • 把密码、用户原始文本等敏感信息写进 params 或 artifact——它们会被永久存进 tracking 后端和对象存储；
  • 每次运行创建新 experiment，导致 run 散落各处无法横向比较；
  • 只保存模型，不保存评估报告和环境信息；
  • 只比较离线指标，不做部署前的接口和性能验证。

小结

一个高质量 run 是模型的出生证明：它把代码、数据、参数、指标和制品连接起来。四类原语——params 记你的决定、metrics 记测出的结果、artifacts 存复现所需的文件、flavored model 存可直接上线的对象——用对了，比较、注册、部署和审计就都有了结构化事实可依。MLflow 的价值不是漂亮 UI，而是把”哪个模型好、为什么好”从口头记忆变成可查询、可复现的工程记录。
