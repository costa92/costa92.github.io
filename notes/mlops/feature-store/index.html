第 17 / 25 节 · 治理与运营

第 15 篇解决了”哪个模型版本被批准上线”，让模型制品的流转有了审批与 GitOps 痕迹。但制品对了，不代表预测就对——模型吃进去的是特征，如果线上算出来的特征和训练时算出来的不是同一回事，一个通过了所有门禁的模型照样会在生产里悄悄失灵。

这类失灵有个专门的名字：训练—服务偏斜（training-serving skew）。它不报错、不崩溃、不触发任何告警，只是把离线 0.92 的 macro F1 在线上兑现成 0.7 出头，而你在 Grafana 上看到的一切指标都是绿的。

1. 偏斜从哪里产生

偏斜的本质是：同一个特征，在训练路径和推理路径上由两份不同的代码算出来。 只要存在两份实现，它们就一定会在某个时间点漂开。常见来源：

  • 双份实现。 训练用 SQL 在数仓里算”用户过去 30 天下单数”，线上用 Go 查 Redis 再累加。两边对”30 天”的定义、退款是否计入、时区如何处理，几乎不可能长期一致。
  • 时间穿越。 训练时读数据库的当前状态给历史样本打特征，模型于是看到了样本发生之后才出现的信息。这是标签泄漏（label leakage）最常见的形态，也是 §3 的主题。
  • 新鲜度不对称。 离线算的是”截止昨晚 24:00 的完整聚合”，在线存储里的值可能已滞后 20 分钟。模型学的是完整数据下的语义，线上拿到的是半成品。
  • 边界细节不一致。 默认值填 0 还是 -1、窗口左闭右开还是双闭、是否小写归一化、类别编码用哪一版映射表。单条都不起眼，叠加起来足以让分布明显偏移。

偏斜是怎么被发现的

它不会自己冒出来，得主动去找。按成本从低到高：

  1. 离线 / 线上指标对不上。 上线后真实指标显著低于离线评估，而用同一批线上样本重跑离线评估又恢复正常——这是偏斜的典型指纹。
  2. 影子比对（shadow scoring）。 把线上请求实际用到的特征向量原样打日志，隔天用离线管线对同一批实体、同一时间点重算一遍，逐字段 diff，不一致的字段就是偏斜源。
  3. 特征分布监控。 线上特征和训练集特征分别统计均值 / 分位数 / 缺失率再比较。这和第 17 篇的漂移监控共用一套设施，区别只在比较对象：漂移比”今天 vs 训练时”，偏斜比”线上 vs 离线，同一时刻”。

2. 本项目为什么天然不会偏斜

看一眼 example 工程的训练代码，模型其实是一条 sklearn Pipeline：

model = Pipeline(
    [
        ("tfidf", TfidfVectorizer(
            analyzer=params["analyzer"],
            ngram_range=(params["ngram_min"], params["ngram_max"]),
        )),
        ("classifier", LogisticRegression(
            C=params["c"], max_iter=params["max_iter"],
        )),
    ]
)
model.fit(x_train, y_train)
joblib.dump(model, model_path)

关键在最后一行：joblib.dump 序列化的不只是逻辑回归的系数，还包括 TfidfVectorizer 拟合后的完整状态——词表、每个 n-gram 对应的列索引、IDF 权重向量。也就是说，特征工程逻辑和模型权重被打包进了同一个 .joblib 文件。

推理侧于是可以什么都不做——app.py 里只有 joblib.load(...) 和 state["model"].predict_proba([text])[0] 两句。predict_proba 内部会先跑 TfidfVectorizer.transform，用的正是训练时那份词表和 IDF。没有第二份特征实现，也就没有偏斜的容身之处。 服务代码里连”TF-IDF”这四个字母都不需要出现。

附带的好处：特征版本和模型版本天然绑定，metadata.json 的 model_sha256 一并覆盖了特征逻辑；换 ngram_range 只改 params.yaml，推理侧零改动。唯一隐患是 joblib 跨 sklearn 大版本不保证兼容，所以 metadata 里记了 sklearn_version。

结论说直白些：本系列的意图分类项目不需要 Feature Store，引入它是纯粹的过度设计。 特征全部来自请求体那一个 text 字段，计算无状态、纯函数式，一致性问题已在源头消灭。

这个办法什么时候失效

Pipeline 打包法有一个隐含前提：特征的全部输入都在请求体里，且计算不依赖任何外部状态。 一旦下面任一条成立，它就不够用了：

  • 特征来自数据库。 要用”用户注册时长””历史工单数”，而请求体里只有 user_id，服务必须去外部查——查询逻辑就是第二份实现。
  • 特征来自实时行为流。 “最近 5 分钟点击次数”需要流式作业持续维护，训练时则要从事件日志回放。两条链路，两套代码。
  • 特征需要跨请求聚合。 单条请求算不出”过去 7 天平均会话时长”，必须依赖跨时间窗口的状态。
  • 多个模型共用同一特征。 各自 Pipeline 一份，就有 N 份实现在各自漂移。

一旦踩中，特征就从”模型的一部分”变成”独立的数据资产”，需要独立的定义、存储、版本和 SLO。这正是 Feature Store 的定位。

3. Point-in-time correctness 与 as-of join

假设要给意图模型加一个特征 open_tickets（用户在提问时刻的未结工单数）。手上两张表：samples 是训练样本（user_id、prediction_time、label），user_stats 是用户特征快照（user_id、event_time、open_tickets，同一用户多行历史）。

最自然、也最错的写法是先取每个用户的最新快照，再按 user_id join：

# ❌ 泄漏未来信息：把"今天的状态"贴给"三个月前的样本"
latest = user_stats.sort_values("event_time").groupby("user_id").tail(1)
train = samples.merge(latest, on="user_id", how="left")

这两行干净得让人放松警惕，但它把用户现在的未结工单数当作了他三个月前提问时的特征。而”现在工单多”往往正是”当时那次提问是个投诉”的结果——特征里混进了标签的下游产物。离线 F1 会漂亮得不真实，上线后一分不剩，因为推理时刻根本拿不到未来。（直接 merge(user_stats, on="user_id") 更糟：多行快照笛卡尔展开，样本数凭空膨胀。）

正确的做法是 as-of join（时间点对齐）：对每条样本，只取 event_time <= prediction_time 的快照中最新的一条。pandas 有专门的 merge_asof：

import pandas as pd

# merge_asof 要求两侧都按时间键排序
samples = samples.sort_values("prediction_time")
user_stats = user_stats.sort_values("event_time")

train = pd.merge_asof(
    samples,
    user_stats,
    left_on="prediction_time",
    right_on="event_time",
    by="user_id",              # 实体键：先分组，再在组内做时间对齐
    direction="backward",      # 只向过去找，这一项就是 point-in-time 的保证
    tolerance=pd.Timedelta("7D"),  # 超过 7 天的陈旧快照视为缺失
)

三个参数是重点：direction="backward" 只允许匹配 event_time <= prediction_time 的行，这是真正防泄漏的部分，写成 "nearest" 就前功尽弃；by="user_id" 保证时间对齐在同一用户内部做；tolerance 是特征有效期，没有它，一条半年前的快照也会被当成有效特征贴上去，而线上永远不会给模型这么陈旧的值。

数仓侧的等价 SQL：

SELECT s.user_id, s.prediction_time, s.label,
       f.open_tickets, f.event_time AS feature_event_time
FROM samples s
LEFT JOIN LATERAL (
    SELECT open_tickets, event_time FROM user_stats u
    WHERE u.user_id = s.user_id
      AND u.event_time <= s.prediction_time                      -- 不看未来
      AND u.event_time >  s.prediction_time - INTERVAL '7 days'  -- 不看太旧
    ORDER BY u.event_time DESC LIMIT 1
) f ON TRUE;

u.event_time <= s.prediction_time 这一行是 point-in-time correctness 的入门版。它简单到容易被当成可有可无的过滤条件删掉——而代价是一个离线指标虚高、上线即打回的模型。

但只有这一行是不够的，因为它假设了一件很少成立的事：事件发生的那一刻，数据就已经能被查到了。

真实系统里有两个不同的时间：

  • event time（事件时间）：这件事在业务上发生的时刻。工单是 10:00 创建的。
  • availability time / created time（可用时间）：这条记录真正落进你的特征表、能被查询到的时刻。ETL 每小时跑一次，于是 10:00 那条工单可能 11:05 才可查。

线上推理只能读到”此刻已经落库的数据”。所以正确的判据不是”事件时间早于预测时间”，而是**”这条记录在预测时刻已经可查”**——即 u.created_at <= s.prediction_time。只筛 event_time 而不筛 created_at，10:30 那次预测就会用上一条 11:05 才可查的记录，这仍然是泄漏，只是比 direction="nearest" 那种隐蔽得多：它不会让你在数据里看到任何”未来的时间戳”。

三类情况会把这个差距放大：

  • 晚到数据（late-arriving data）。移动端离线缓存、跨时区批量回传、上游重试补数，event time 和 created time 差几小时到几天都算正常。
  • 修订记录（restatement）。同一个 (user_id, event_time) 被上游修正过一次——退款冲销、人工订正、口径重算。训练要用的是”预测时刻那一版的值”，不是”今天回头看最准的那一版”。所以特征表应该是 append-only、带 created_at 的多版本表，而不是原地 UPDATE 的当前值表。原地更新的表在物理上就已经丢掉了历史，任何 join 都救不回来。
  • 回填（backfill）。补跑历史分区会给老 event time 打上今天的 created time。这本身没错，但意味着用回填后的表构造训练集，永远无法还原当时的真实可见性。要么在回填时保留原始 created time，要么明确承认这批样本的 point-in-time 语义已经失真。

带上可用时间的版本长这样——两个条件都要，缺一个都不成立：

LEFT JOIN LATERAL (
    SELECT open_tickets, event_time FROM user_stats u
    WHERE u.user_id = s.user_id
      AND u.event_time <= s.prediction_time                      -- 不看未来发生的事
      AND u.created_at <= s.prediction_time                      -- 也不看当时还查不到的记录
      AND u.event_time >  s.prediction_time - INTERVAL '7 days'  -- 不看太旧
    ORDER BY u.event_time DESC, u.created_at DESC LIMIT 1        -- 同一事件时间取当时最新的那一版
) f ON TRUE;

第 4 节 Feast 的 FileSource 里那个 created_timestamp_column="created_at" 参数，管的正是这件事——它不只是”同一事件时间下的去重依据”，更是可用时间这一维的载体。定义 source 时漏掉它，Feast 也只能退回到单时间轴的入门版。

一句话记法：event time 决定”这条数据说的是什么时候的事”，availability time 决定”这条数据当时能不能被看见”。训练只能使用预测时刻真正可获得的那个数据版本。

实操建议：把 feature_event_time 留在训练集里，统计 prediction_time - feature_event_time 的分布。这个”特征滞后时长”若中位数是 2 分钟，你的在线存储就必须做到相近的新鲜度，否则即便 join 写对了，训练和线上依然是两个世界。

跑一遍看看差多少

上面两种写法的差距不是理论问题。example 工程里有一个只依赖 pandas 的可运行演示 scripts/asof_join_demo.py：40 个用户，每人 8 条带时间戳的工单快照，其中”投诉类”样本（label=1）之后工单数会明显上涨——也就是说”现在工单多”正是”当时那次提问是投诉”的结果。

cd example        # 本篇的相对路径一律以 example/ 为根
python scripts/asof_join_demo.py

真实输出：

=== 数据规模 ===
样本数              : 40
特征快照数          : 320

=== ❌ 泄漏写法 groupby().tail(1) + merge ===
取到未来快照的行数  : 40 / 40 (100%)
open_tickets 均值   : 9.07

=== ✅ 正确写法 pd.merge_asof(direction='backward') ===

用泄漏特征的离线 F1 : 0.806

两个数字值得盯着看。一是 open_tickets 均值从 9.07 掉到 1.20——泄漏写法喂给模型的根本不是同一个特征。二是离线 F1 从 0.286 被抬到 0.806：一个实际几乎没有预测力的特征，因为一个写错的 join，在离线评估里看起来像个好特征。上线后它当然一分不剩，因为推理时刻拿到的只会是 1.20 那一版。

这个 0.52 的差距，全部来自 direction="backward" 这一个参数。

4. Feast：特征定义、离线存储与在线存储

如果确实需要，Feast 是开源方案里最轻的一个。它的核心是把特征定义写成 Python 声明，然后由同一份定义分别驱动离线取数和在线取数。

# feature_repo/definitions.py
from datetime import timedelta

from feast import Entity, FeatureView, Field, FileSource, ValueType
from feast.types import Float32, Int64

# Entity：特征挂在哪个业务主键上
user = Entity(name="user", join_keys=["user_id"], value_type=ValueType.STRING)

# Source：原始数据在哪，以及哪一列是事件时间
user_stats_source = FileSource(
    name="user_stats_source",
    path="data/user_stats.parquet",         # 仓库里用本地 parquet，无需云资源
    timestamp_field="event_time",           # point-in-time join 的时间轴
    created_timestamp_column="created_at",  # 同一事件时间下的到达顺序，用于去重
)

# FeatureView：一组共享实体、来源和 TTL 的特征
user_stats_view = FeatureView(
    name="user_stats",
    entities=[user],
    ttl=timedelta(days=7),                  # 等价于 §3 里的 tolerance
    schema=[
        Field(name="open_tickets", dtype=Int64),
        Field(name="avg_resolution_hours", dtype=Float32),
    ],
    source=user_stats_source,
    online=True,                            # 允许物化到在线存储
    tags={"owner": "customer-platform", "version": "v2"},
)

两条读取路径共用这一份定义。离线（训练） 的 get_historical_features 内部做的就是 §3 那个 as-of join，只是不用你手写；在线（推理） 的 get_online_features 从在线存储按主键点查最新值：

from feast import FeatureStore

store = FeatureStore(repo_path="feature_repo")

# 训练：entity_df 需含 user_id 和 event_timestamp 两列
training_df = store.get_historical_features(
    entity_df=samples,
    features=["user_stats:open_tickets"],
).to_df()

# 推理：毫秒级点查
online = store.get_online_features(
    features=["user_stats:open_tickets"],
    entity_rows=[{"user_id": request_user_id}],
).to_dict()

离线存储与在线存储的分工

离线存储在线存储
典型实现S3 + Parquet、BigQueryRedis、DynamoDB
存什么特征全部历史，带 event_time每个实体键的最新一份值
访问模式 / 延迟大范围扫描 + as-of join，秒到分钟主键点查，个位数毫秒

两者由 feast materialize 定期把离线数据推到在线存储来衔接：

feast apply                                          # 注册 / 更新特征定义
feast materialize-incremental $(date -u +%Y-%m-%dT%H:%M:%S)

关键在于：一份 FeatureView 定义，两条路径。 这才是 Feature Store 的核心价值——它不是”又一个键值数据库”，而是消除了那份会漂移的第二实现。

上面这份定义在 example 工程里落成了可查的文件：feature_repo/definitions.py 与 feature_repo/feature_store.yaml（offline store 用本地 file、online store 用本地 sqlite，不需要任何云资源）。但它是一份参考定义，不参与本工程的构建：feast 没有进 pyproject.toml，make train、pytest、CI 都不会碰它。理由和本文的结论一致——这个项目用不上 Feature Store，为一份示例给主工程引入一个重依赖，正是本系列一直在反对的事。想实际跑 feast apply / materialize-incremental，在独立虚拟环境里单独 pip install feast，步骤见 feature_repo/README.md。

在线特征新鲜度必须进 SLO

materialize-incremental 通常挂在定时任务上。假设每 15 分钟跑一次，在线特征最坏滞后 15 分钟；而训练集里的滞后中位数可能只有 2 分钟。这个差距本身就是一种偏斜，而且最容易被忽略——它不是逻辑错误，是运维状态。

所以特征新鲜度必须当成服务等级目标（SLO）来管，和第 19 篇的延迟、可用性 SLO 放在同一张仪表盘上：

别把 SLI 定义成 now() - max(feature.event_time)。 这是个很自然但完全无效的写法：它取的是全局最新的那一条记录，只要有任意一个活跃实体刚被物化，指标就显示”很新鲜”，而剩下 99% 的用户可能已经陈旧了一整天。这个指标最擅长的事就是在真出问题的时候保持绿色——因为出问题的往往正是物化作业只跑完了一部分分区。

正确的做法是按实体（或按线上实际发生的查询事件）逐条算 feature age，再看它的分布：

feature_age = 该次在线取数的时刻 - 取到的那条记录的 event_time

在推理服务里，每次 get_online_features 返回后就地算一次，作为直方图指标暴露（和第 19 篇的延迟直方图同一套做法）。按查询事件而不是按实体全表扫，还有个额外好处：它天然按真实流量加权——没人查的僵尸实体陈旧了不该触发告警，热门实体陈旧了必须立刻响。

然后至少盯三组数：

  • 分位数：feature age 的 p50 / p95 / p99，按 FeatureView 分别统计。p50 反映物化周期是否正常，p99 才反映”最差的那批用户经历了什么”。只看均值或最大值都会漏掉分片故障——均值被大量新鲜实体拉低，最大值被单个僵尸实体带偏。
  • 覆盖率：在线取数返回非空的比例。物化作业部分失败时，典型现象不是”值旧了”，而是”某些实体压根查不到”。这个数掉下来，比 age 变大更紧急。
  • 训练/线上分布对比：训练集里 prediction_time - feature_event_time 的分位数，和线上 feature age 的同一分位数放在一起看。§3 提到中位数 76.5 小时——如果线上 p50 是 15 分钟，两边根本不是同一个特征，这个偏斜不会体现在任何一个单侧指标上。

对应的 SLO 和告警：

  • SLO：user_stats 的 feature age p95 < 20 分钟且覆盖率 ≥ 99.9%，30 天达标率 ≥ 99%；耗尽错误预算时暂停依赖该特征的模型发版；
  • 告警：物化任务失败、p99 age 超过 ttl、或覆盖率跌破阈值。后两条比第一条更重要——物化任务”成功退出”但只写了一半分区，是这类系统最常见的失败形态。特征年龄超过 ttl 时在线取数会大面积返回空值，而模型往往把空值当成”这个用户很正常”，静默劣化。

顺带强调：特征拿不到时的降级行为必须显式设计。 默认填 0 意味着”该用户零工单”，是一个有强语义的错误答案。更稳妥的是关键特征缺失时返回低置信度结果或走规则兜底，并把缺失率作为独立指标暴露。

5. 特征契约

不管用不用 Feast，每个进入模型的特征都应该有一份可查的契约：名称与版本（user_stats:open_tickets@v2，改语义必须升版本而不是原地改）、数据类型与取值范围、实体键（决定 join 和在线点查的粒度）、事件时间列（缺了它就不可能做对 as-of join）、TTL 与新鲜度目标、缺失值策略及降级行为、所有者、上游来源。

模型侧则在 metadata 里记下依赖的 feature service 版本——example 工程已经在记 dataset_sha256 和 params，多加一个 feature_service_version 是同一思路的延伸。部署前做一次 schema 兼容性校验（线上 Store 的字段是否覆盖模型所需、类型是否一致），放进第 15 篇的发布门禁，成本极低，能挡掉一整类”特征字段被上游悄悄改名”的事故。

6. 什么时候该上 Feature Store

Feature Store 是一套要长期运维的基础设施：注册中心、离线存储、在线存储、物化作业，外加各自的监控告警。对”一个模型、一份 Pipeline”的项目，运维负担远超它解决的问题。下面几条满足两条以上再考虑引入：

  • 多模型共享特征。 三五个模型都要”用户活跃度”时，复用收益才开始压过运维成本。
  • 特征来源是实时流。 需要毫秒级点查最新聚合值，而不是请求体里现算。
  • 多团队协作。 生产方和消费方不是同一拨人，需要有 owner、有版本的契约层解耦。
  • 需要特征血缘审计。 金融、医疗场景要能回答”这个拒贷决策用了哪些特征、值是多少、从哪来”，靠翻代码答不上来。
  • 训练集回填是常态。 手写 as-of join 已成重复劳动和 bug 来源。

还有个中间地带：不上完整 Feature Store，只把特征计算抽成被训练和推理共同 import 的 Python 包，靠单一实现保证一致性。这能解决双份实现问题，代价是 point-in-time 和在线点查要自己处理。对多数从”一个模型”走向”几个模型”的团队，这一步比直接上 Feast 更务实。

小结

训练—服务偏斜的根因只有一个：同一个特征存在两份实现。sklearn Pipeline 把特征逻辑和模型权重一起序列化，在源头消灭了这个问题——这才是本系列示例项目不需要 Feature Store 的真实原因，不是”我们还没做到”。

当特征开始依赖数据库、实时流或跨请求聚合，这层保护就失效了。此时要补三件事：一份被离线和在线共用的特征定义、一个写对了 event_time <= prediction_time 的 as-of join、一个把在线特征新鲜度纳入 SLO 的运维闭环。Feature Store 提供的正是这三件事的成品实现——但只有当你确实需要它们时，它才值那份运维成本。
