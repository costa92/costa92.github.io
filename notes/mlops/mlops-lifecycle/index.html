第 3 / 25 节 · 基础

DevOps 解决的是软件如何快速、可靠地从提交进入生产。MLOps 继承这些原则，但管理对象从代码扩展到了数据、实验和模型。

1. 两种系统的变化来源

传统服务通常在代码或配置变化时重新发布。ML 系统还有第三种变化来源：数据。即使代码不变，新数据也可能触发训练并产生新模型。换句话说，DevOps 的输入是代码，输出是应用；MLOps 的输入是代码加数据，输出是模型加预测结果。

维度DevOpsMLOps
输入代码代码 + 数据
输出可运行的应用模型 + 预测
核心制品应用包、镜像镜像、数据版本、模型制品
验证单元/集成/端到端测试再加数据验证、离线指标、偏差与漂移检查
测试性质断言可穷举：期望输出能一条条写死单样本可断言，整体质量只能统计估计
触发器代码提交代码、数据、定时任务、质量告警
版本管理Git 管代码Git + 数据版本 + 模型版本
生产监控可用性和性能再加预测质量和数据分布
失败模式崩溃、报错、5xx——通常很吵静默错误预测（silent wrong predictions）——服务照常返回，只是越来越不准
回滚回滚代码/镜像代码、模型、特征逻辑可能需要一起回滚

“测试性质”那一行容易被误读，先说清楚。 常见的说法是”ML 是概率性的、同样输入可能得到不同输出”——对本系列这套东西来说这是错的。固定模型文件、固定预处理、固定输入，model.predict() 是确定性的，跑一万次结果一样。所以”输入 我无法登录账号 必须返回 technical_support“这种契约测试完全可以写死，而且应该写死，它守的是”模型文件没换错、预处理没漂移”。

真正的概率性在另一个层面：你关心的从来不是某一条样本对不对，而是模型在没见过的数据上的整体表现。这个量无法直接观测，只能用一批有代表性的样本去估计，而估计就自带不确定性——样本换一批，macro-F1 就会抖。所以 ML 的质量门禁必须同时回答两个问题：单样本契约有没有破（确定性断言），以及总体指标的变化是不是超出了样本噪声（统计判断）。把后者当成前者，会得到一个天天误报的门禁。

另一个值得强调的是失败模式的差异。DevOps 的故障往往是“吵”的：进程挂了、接口返回 500、健康检查变红，监控立刻能报出来。ML 系统的典型故障却是“静默”的——模型服务一切正常，延迟、成功率都达标，只是预测悄悄开始偏离真相。没有针对预测质量和数据分布的专门监控，这类退化可能几周都无人察觉。这也是为什么把 DevOps 那套原封不动搬过来并不够。

2. CI、CD 与 CT

CI：持续集成

ML 项目的 CI 不止运行代码测试，还应验证：

  • 数据 Schema 是否符合预期；
  • 特征转换是否稳定；
  • 训练脚本能否在干净环境运行；
  • 新模型是否超过最低质量门槛；
  • 模型序列化后能否重新加载并推理。

CD：持续交付或持续部署

部署对象可能是内含模型的镜像，也可能是“固定运行时 + 外部模型 URI”。流水线需要记录哪个环境正在使用哪个模型版本，并支持渐进式发布和回滚。

CT：持续训练

CT（Continuous Training，持续训练）是 MLOps 相对 DevOps 多出来的那一环，也是 CI/CD/CT 三件套里最容易被忽略的一件。但 CT 的”持续”讲的是能力，不是频率。 准确的定义是：训练流程本身可重复、可审计、可被条件触发——任何人在任何时间点按一下，都能用指定的数据和参数训出可比较的模型。至于要不要真的重训、多久重训一次，是另一个决策，由效果、数据、风险和成本共同决定。

所以”MLOps 就得不停重训”是个误解。规则稳定的领域（会计科目分类）、漂移极慢的领域、以及每次模型变更都要走合规审批的高监管场景，完全可能一年只重训一两次，甚至长期不重训——只要监控证明效果没退化，不动就是正确选择。重训本身也有代价：算力、标注、评审、发布窗口、以及每次换模型带来的行为变化风险。CT 的价值是让”要重训”这件事从三天的手工作业变成一次流水线触发，而不是逼你每天都跑。

持续训练不是盲目地每天重跑任务，而是把训练变成可重复、可审计的过程。触发条件可以是新标注数据达到阈值、漂移超过限制、定期训练窗口，或业务方确认规则变化。

那什么时候确实需要重训？ 当模型开始衰减（model decay）的时候。训练时模型学到的是历史数据的分布，而线上世界可能一直在变——用户行为迁移、季节变化、新词新梗、上游数据口径调整，都会让线上数据偏离训练时的假设。偏离累积到影响效果时，模型的准确率会缓慢下滑，却不会抛出任何异常。CT 的意义是：这一天到来时，你有一条随时可以按下去的流水线，而不是临时拼一个训练脚本。

可以打个临场调整的比方。一支球队赛前会根据对手数据、场地情况做一套完整战术，这相当于一次“训练”。但比赛真正开始后，场地比预期更慢、对方换了打法、己方体力下降——这些都是“数据漂移”。聪明的球队不会死守赛前那一套，而是不断“观察当前局势 → 调整策略 → 执行 → 再观察”。ML 系统的监控与重训练闭环，本质上就是把这套“观察—调整—执行—重复”固化成工程流程。

3. 一个完整闭环

标准生命周期的几个阶段

把闭环拆开，一条相对标准的 ML 生命周期通常包含这些阶段，前后相接：

  1. 问题定义：先厘清业务目标和期望结果，决定“模型要预测什么、判对判错的代价是什么”。这一步不产出代码，却决定后面所有阶段的方向。
  2. 数据采集：获取原始训练数据。数据质量直接决定模型上限，垃圾进则垃圾出。
  3. 数据清洗与预处理：去重、纠错、消除不一致，统一数据格式，让数据可用。
  4. 探索性数据分析（EDA）：在清洗后观察数据分布、找规律、发现隐藏问题，进一步打磨数据集。
  5. 特征工程与选择：构造或变换特征，并挑出对预测最有价值的特征，提升模型表现。
  6. 模型训练与评估：在处理好的数据上训练，再用留出数据测试，用指标衡量准确度。
  7. 模型打包与部署：把模型封装成 API（如 FastAPI）或容器（如 Docker），部署到虚拟机、Kubernetes 或 Serverless 平台。
  8. 监控与重训练：上线后持续盯预测质量、监测数据漂移，按需触发动态重训练。

最容易被忽略的是反馈。意图分类服务返回预测后，真实答案可能来自人工客服最终选择的队列。没有把这些结果回流，团队就无法计算线上效果，更无法有依据地重训练。

每个阶段常见的工具

为了让这条闭环不停留在抽象层面，下面给出各阶段业界常见的工具，方便对照理解（本系列后续篇章会逐一动手实践，这里只做地图）：

阶段常见工具
数据采集S3、Kafka、日志、数据库
预处理Pandas、Spark

值得注意的是，前半段（采集、预处理、训练）多是数据科学家熟悉的工具，后半段（编排、部署、监控）几乎全是 DevOps 世界的老面孔。MLOps 的工程量，很大程度上就落在“把这两半工具链缝合成一条自动流水线”上。

4. 各角色如何协作

  • 数据工程师负责可靠的数据获取、清洗和数据契约；
  • 数据科学家负责实验、特征和模型质量；
  • ML 工程师负责把实验代码工程化，定义训练和推理接口；
  • MLOps/平台工程师提供流水线、制品库、训练环境、部署平台与可观测性；
  • 业务专家定义错误代价、标签含义和上线门槛。

边界不是固定组织架构，关键是每个阶段有明确输入、输出和责任人。

6. 最小落地顺序

对刚进入 MLOps 的团队，更实际的顺序是：

  1. 先让训练脚本可重复运行；
  2. 保存指标和模型制品；
  3. 版本化训练数据；
  4. 建立统一在线推理接口；
  5. 自动测试和构建；
  6. 再引入模型注册、渐进发布和漂移监控。

一开始就部署庞大的 ML 平台，往往只会得到昂贵但无人使用的基础设施。

小结

MLOps 的核心不是工具清单，而是把数据到模型再到反馈的循环变成可重复、可验证、可运营的系统。DevOps 提供交付基础，数据和模型则增加了新的状态、风险和触发机制。
