Go 报 unknown time zone Asia/Calcutta：Ubuntu 24.04/26.04 镜像缺 tzdata-legacy 的排查与修复

 costalong  2026-11-16  linux 故障排查 Docker Linux 运维 Go
故障排查 Docker Linux 运维 Go
linux golang
文章字数:   4.3k
阅读次数:  
   阅读模式

文中的打卡服务、接口、请求头、业务代码和线上数字是改编的，tzdata 拆包、Go 和 glibc 的行为以及镜像里的测试结果是真实跑出来的，用的是官方 ubuntu:22.04、ubuntu:24.04、ubuntu:26.04 镜像。文中时刻都是北京时间。

场景

我维护一个 Go 写的打卡服务，用 Go 1.27 编译，跑在容器里。用户每天学完打一次卡，服务按用户当地日期累计连续天数，同一个当地日期只认一次打卡。

客户端上报两份时区信息。心跳请求带 X-Timezone，是 Asia/Calcutta 这样的地区名，服务端记下它，用户提交打卡时用它换算当地日期，决定这次打卡记到哪一天。提交打卡的请求本身带 X-Utc-Offset，是 +5.5、+1 这样的数字偏移，用来和前者对一下。提交接口先算两边的日期并比对，再判断是否重复打卡；两边日期不一样，就记一条 tz_mismatch 日志并计数，平时这个数基本是 0。

解析地区名的代码大致如下：

func parseTimezone(h http.Header) (offset float64, ok bool) {
	name := h.Get("X-Timezone")
	if name == "" {
		return 0, false
	}
	loc, err := time.LoadLocation(name)
	if err != nil {
		log.Errorw("parse timezone failed", "tz", name, "err", err)
		return 0, false // 调用方拿到 0，按 UTC 处理
	}
	_, sec := time.Now().In(loc).Zone()
	return float64(sec) / 3600, true
}

服务的基础镜像是 2023 年打的 Ubuntu 22.04，tzdata 一直没升级，停在 2023c。前阵子摩洛哥用户反馈打卡时间显示快了一小时。摩洛哥从 2026-09-20 起改成全年 +00，2023c 里没有这条规则，还按 +01 算：

# tzdata 2023c
$ TZ=Africa/Casablanca date -d "2026-11-16 03:00 UTC" "+%Z %z"
+01 +0100
# tzdata 2026e
$ TZ=Africa/Casablanca date -d "2026-11-16 03:00 UTC" "+%Z %z"
+00 +0000

错误日志里还有一类 unknown time zone America/Coyhaique，每小时几十条。这是 tzdata 后来才加的时区，2023c 里同样没有。

22.04 的标准支持 2027 年 4 月到期，我决定不在旧镜像上单独升 tzdata，直接把基础镜像换成 ubuntu:26.04。新镜像在 Dockerfile 里装了 tzdata，凌晨 3 点在变更窗口里分批发布。

出现问题：上线后大量 unknown time zone

03:00 发出第一批 Pod，03:01 开始出现 parse timezone failed，03:05 告警响了。十分钟不到报了三千多条，平时是每小时几十条，tz_mismatch 一起往上走。我停了后面的批次，03:10 把第一批回滚到旧镜像，报错随即停止。

按报错里的时区名统计，Asia/Calcutta 约占 60%，Asia/Saigon 约 18%，America/Buenos_Aires 约 6%，Asia/Rangoon 和 Asia/Katmandu 各 3% 到 4%，剩下的是 US/Pacific、US/Eastern、Europe/Kiev 等。这些全是改过名的旧写法，Asia/Calcutta 现在叫 Asia/Kolkata，Asia/Saigon 现在叫 Asia/Ho_Chi_Minh。不少老版本客户端直接把系统给的旧名报上来。

分析问题：时区加载失败后按 UTC 记日期

LoadLocation 失败后偏移取 0，打卡日期按 UTC 算。凌晨 3 点是 UTC 前一天 19 点，印度当地是 0 点半，越南是 2 点，两边当地已经是新的一天，按 UTC 却还在前一天，打卡就记到了前一天。如果前一天已经打过卡，这次会被当成重复打卡拒掉。美洲这时还是前一天白天，按 UTC 算日期不变，没受影响。

数字偏移那条路不查 tzdata，照常工作，两边日期对不上，tz_mismatch 就涨了。

测试环境也换了新镜像，没发现问题，是因为测试账号和自动化用例报的都是 Asia/Shanghai、Asia/Kolkata 这类标准名，没有旧名。我在开发机上自测也没问题，原因在 Go 查时区数据的顺序：time.LoadLocation 先看 ZONEINFO 环境变量，再查 /usr/share/zoneinfo 等系统目录，然后是程序内嵌的数据（引入 time/tzdata 才有），最后是 $GOROOT/lib/time/zoneinfo.zip。我的开发机也是 Ubuntu 26.04，系统目录里同样没有旧名，但装了 Go，最后这个 zip 里有。同样的代码用 go build -trimpath 编译，再以 GOROOT=/nonexistent 运行，就报 unknown time zone 了。macOS 的系统目录里本来就有旧名，到不了 zip 这一步。

发现问题：旧时区名被拆进了 tzdata-legacy

进新镜像看：

$ docker run --rm <新镜像> sh -c '
dpkg -l tzdata tzdata-legacy | tail -n +6
for z in Asia/Calcutta Asia/Kolkata PRC US/Eastern EST5EDT; do
  [ -e /usr/share/zoneinfo/$z ] && echo "OK   $z" || echo "MISS $z"
done'
ii  tzdata         2026e-0ubuntu0.26.04.1 all  time zone and daylight-saving time data
un  tzdata-legacy  <none>                 <none> (no description available)
MISS Asia/Calcutta
OK   Asia/Kolkata
MISS PRC
MISS US/Eastern
MISS EST5EDT

旧名的文件没了，挪到了 tzdata-legacy 包里，而这个包没装。

tzdata 的 changelog.Debian.gz 和 NEWS.Debian.gz 里有记录。Debian 2023c-8（2023 年 8 月）把 IANA backward 文件里的旧名、合并名移进 tzdata-legacy，US/* 也在内，Ubuntu 23.10 跟进，24.04 LTS 已经是这样。2023c-10 又把 UTC、CET 这类顶层名挪了回来。2024b-3 再把 CET、EST5EDT 等 System V 名移走，Ubuntu 从 25.04 开始，26.04 LTS 也包含。

这个包也不会被顺带装上。apt-cache depends tzdata 显示 tzdata 对 tzdata-legacy 只有 Breaks 和 Replaces，没有 Depends 或 Recommends；反过来是 tzdata-legacy 依赖 tzdata。

旧名和标准名的对应关系在 tzdata 自带的 /usr/share/zoneinfo/tzdata.zi 里，L 标准名 旧名 这样的行就是别名表，旧名的文件拆走了，这个文件还在。我拿官方镜像补装 tzdata，把 tzdata-legacy 里除 right/* 外的 113 个旧名挨个查了一遍：

基础镜像tzdata113 个旧名中缺失
ubuntu:22.042026e-0ubuntu0.22.04.10
ubuntu:24.042026e-0ubuntu0.24.04.1101
ubuntu:26.042026e-0ubuntu0.26.04.1113

24.04 已经缺了大半，26.04 又少了 CET、EST5EDT 这批 System V 名和 Asia/Choibalsan。我从 22.04 直接跳到 26.04，两次拆分是一起碰上的。

Asia/Calcutta 在 Go 的四个数据来源里都没找到，偏移按 0 兜底，打卡日期落到了前一天；装上 tzdata-legacy 后在第 3 步就能找到。

分析解决方法：几种修复方式的取舍

能想到的做法有下面这些：

方案做法好处代价
Amain 包加 import _ "time/tzdata"改一行代码，不依赖镜像只对 Go 进程有效，数据版本跟着 Go 走
BDockerfile 里装 tzdata-legacy旧名用系统数据，随系统更新镜像多约 1.2MB，带了整套 right/*
C服务端把旧名转成标准名老版本客户端报旧名也能处理，下游统一用标准名要改代码，要维护对照表（可以从 tzdata.zi 生成）

另外，地区名解析失败时直接按 UTC 处理本身就不合理，同一个请求里明明带着 X-Utc-Offset。

B 只改 Dockerfile 一行，不动业务代码。A 我在测试分支的 main 包里加了这一行来测，在 ubuntu:26.04 里 113 个旧名确实全部能加载。设了 TZ=Asia/Calcutta 时，Go 程序里的 time.Local 也从 UTC 变回了 +0530，系统的 date 不受影响，还是 UTC。

/etc/localtime 要是链接到一个不存在的旧名，比如 PRC，又没设 TZ，内嵌了数据结果也还是 UTC。看源码，不设 TZ 时 Go 拿 localtime 这个名字去 /etc 下找，退到内嵌数据时查的还是 localtime，内嵌数据里没有这个名字。

退回 UTC 时不会有任何报错。glibc 遇到不认识的 TZ 也是这样：

$ TZ=Asia/Calcutta date '+%Z %z'
UTC +0000

Go 的 time.Local 加载不了 TZ=PRC 同样退回 UTC，不打日志。我的服务从请求头读时区，好歹有报错；靠 TZ 环境变量设时区的服务，时间错了也看不出来。

光能加载还不够。我把附录里的 tz-verify 加上 import _ "time/tzdata" 编译，拿内嵌数据加载的旧名和系统数据加载的标准名，比对 1970 到 2037 年的偏移。113 个里有一个对不上：

FAIL Canada/Central vs America/Winnipeg @ 2026-11-05: CST-21600 vs EST-18000

镜像里的 tzdata 是 2026e，changelog 写着 Manitoba 从 2026-10-31 起全年 -05。Go 1.27.4 内嵌的是 2026c，还会在 11 月 1 日回拨到 -06。同一个地方，写 America/Winnipeg 时间是对的，写 Canada/Central 就慢一小时。

镜像里有 /usr/share/zoneinfo 时，只有系统里缺的名字才会用到内嵌数据，缺的正是这些旧名。哪里改了夏令时，它的旧名就会算错，要等 Go 下个版本更新内嵌数据才能好。所以 A 我没用。

确定方案：安装 tzdata-legacy

B 保留。装 tzdata-legacy 之后，旧名和标准名读的是同一份系统数据，不会出现 Canada/Central 那样的偏差。

地区名解析失败时，改成用同一请求里的 X-Utc-Offset 算日期，并照常记 parse timezone failed。数字偏移管不了夏令时，只当兜底用，不替代地区名。

C 分两步做。服务入口先把旧名转成标准名再往下传，这一步老版本客户端也能受益；新版客户端再改成直接报标准名。这样数据库和日志分析这些 Go 以外的环节也统一了。

测试分支上加的那行 time/tzdata 撤掉了，否则测试环境的二进制比生产多一份内嵌数据，测出来的结果对不上线上。

执行方案：Dockerfile 加装 tzdata-legacy

修复版的 Dockerfile 和第一批的镜像相比，只在安装那一行多了 tzdata-legacy：

FROM ubuntu:26.04
ENV DEBIAN_FRONTEND=noninteractive
RUN apt-get update \
 && apt-get install -y --no-install-recommends tzdata tzdata-legacy \
 && ln -sf /usr/share/zoneinfo/Asia/Shanghai /etc/localtime \
 && rm -rf /var/lib/apt/lists/*

COPY checkin-server /usr/local/bin/
CMD ["checkin-server"]

解析失败时退回数字偏移的改动跟这个版本一起发。CI 里另外加了一步构建期校验 tz-verify，换基础镜像时它会先拦一道，代码见最后一节「附：构建期校验 tz-verify」。

验证方案：在 Ubuntu 22.04/24.04/26.04 镜像里逐个加载旧名

装了 tzdata-legacy 的 ubuntu:26.04 里：

$ dpkg-query -W -f='${Package} ${Version}\n' tzdata tzdata-legacy
tzdata 2026e-0ubuntu0.26.04.1
tzdata-legacy 2026e-0ubuntu0.26.04.1
$ TZ=Asia/Calcutta date '+%Z %z'
IST +0530
$ TZ=PRC date '+%Z %z'
CST +0800

113 个旧名的文件都在，没内嵌 tzdata 的 Go 程序也能全部加载。

上线前在预发环境用老版本客户端回放了一批带旧名的请求，parse timezone failed 和 tz_mismatch 都是 0。

tz-verify 和服务一样不内嵌 tzdata，只用系统数据，检查 tzdata.zi 里的全部别名能否加载、是否和标准名一致。在几个镜像上的结果：

镜像别名总数系统缺失问题构建
ubuntu:22.04，只装 tzdata15100通过
ubuntu:24.04，只装 tzdata151101101 个 unknown time zone失败
ubuntu:24.04，装了 legacy15100通过
ubuntu:26.04，只装 tzdata162113113 个 unknown time zone失败
ubuntu:26.04，装了 legacy16200通过

三个镜像都是 2026e，别名数却不一样。22.04 和 24.04 的稳定更新为了不改变行为，把 CET、EST5EDT 等 11 个 System V 名留成独立时区，tzdata.zi 里是 Z 行；26.04 里它们成了 L 行的别名。

不内嵌时别名和标准名读同一份系统数据，表里的问题全是加载失败，比对这一项没报过。比对是给用了方案 A 的服务准备的：服务加了 time/tzdata，tz-verify 也加上同一行再编译，就能比出 Canada/Central 这种偏差。

上线部署

04:30 开始发布修复版，还是分批滚动，每批看 5 分钟再放下一批，05:10 全部替换完。再出问题就退回 22.04 的旧镜像。

观察日志与数据

修复版上线后 parse timezone failed 没有再涨，tz_mismatch 一直在 0 附近。全部替换完之后，摩洛哥的时间对了，America/Coyhaique 的报错也没了，这两处靠的是新 tzdata。

出错的时间是 03:01 到 03:10，不到十分钟。被拒掉的打卡也有记录：比对在判重之前，每一条日期不一致的请求都留了 tz_mismatch 日志，里面有用户、地区名、数字偏移和提交时间。我按这份日志用数字偏移重新算当地日期。被记到前一天的改回当天；因为“前一天已打卡”被拒掉的补录到当天。补录前按用户和当地日期去重，当天已经有记录的不再重复写，最后重算连续天数。受影响的多是印度和越南用户。

总结

IANA 早把这些名字降成别名，Debian 和 Ubuntu 又把别名拆进一个不会自动安装的包，而服务的二进制没有内嵌 tzdata，容器里也没有 GOROOT，只能查系统目录。

升级 tzdata 两个方向都可能出错。太旧会认不得新时区，算不对新规则，比如 Africa/Casablanca 和 America/Coyhaique；太新又可能缺旧名，比如 Asia/Calcutta。

现在镜像装了 tzdata-legacy，地区名解析失败时退回数字偏移，CI 跑 tz-verify。服务启动时会把 time.Now().Format("-0700") 打进日志，time.Local 要是悄悄退回了 UTC，日志里会是 +0000 而不是 +0800。服务端的旧名转换还在做。

自己排查的话，先进镜像跑 dpkg -l tzdata-legacy，看 /usr/share/zoneinfo/Asia/Calcutta 在不在。再用 grep '^L ' /usr/share/zoneinfo/tzdata.zi 取出旧名清单，grep 配置、Dockerfile 和连接串（比如 Go DSN 的 loc=）。客户端上报的时区 grep 不到，得从日志里统计。开发机上别直接 go run，编译后放进目标镜像里跑。

附：构建期校验 tz-verify

它从镜像的 /usr/share/zoneinfo/tzdata.zi 读出所有“别名 → 标准名”，逐个加载后和标准名比对 1970 到 2037 年每两周一个时间点的偏移与缩写。两次切换相隔不到两周的规则差异可能被漏掉。它不引入 time/tzdata，和服务一样只用系统数据。有别名加载失败或和标准名不一致、必需别名有一个不在清单里，或者一个别名都没读到，就以退出码 1 结束，让构建失败。必需别名是 15 个 Asia/Europe 旧名加上这次事故里出现过的三个美洲旧名，用来确认 tzdata.zi 确实读全了。

// tz-verify 在目标镜像内校验：tzdata.zi 中的每个时区别名都能加载，
// 且与其标准名在 1970–2037 的偏移、缩写一致。不引入 time/tzdata，和服务一样只用系统数据。
// 任一失败退出码为 1，用于让 docker build 失败。
package main

import (
	"bufio"
	"fmt"
	"os"
	"path/filepath"
	"strings"
	"time"
)

const zoneDir = "/usr/share/zoneinfo"

// 必须出现在 tzdata.zi 中的别名，防止清单读漏：15 个 Asia/Europe 旧名和事故里出现过的美洲旧名。
var required = []string{
	"Asia/Ashkhabad", "Asia/Calcutta", "Asia/Choibalsan", "Asia/Chungking",
	"Asia/Dacca", "Asia/Katmandu", "Asia/Macao", "Asia/Rangoon", "Asia/Saigon",
	"Asia/Thimbu", "Asia/Ujung_Pandang", "Asia/Ulan_Bator",
	"Europe/Kiev", "Europe/Uzhgorod", "Europe/Zaporozhye",
	"America/Buenos_Aires", "US/Eastern", "US/Pacific",
}

func main() {
	links, err := readLinks(filepath.Join(zoneDir, "tzdata.zi"))
	if err != nil {
		fail("读取 tzdata.zi: %v", err)
	}

	var problems []string
	missing := 0
	for alias, target := range links {
		if !exists(alias) {
			missing++
		}
		if p := compare(alias, target); p != "" {
			problems = append(problems, p)
		}
	}
	for _, alias := range required {
		if _, ok := links[alias]; !ok {
			problems = append(problems, "必需别名不在 tzdata.zi 中: "+alias)
		}
	}

	fmt.Printf("tz-verify: 别名 %d 个已校验（系统缺失 %d 个），问题 %d 个\n", len(links), missing, len(problems))
	for _, p := range problems {
		fmt.Println("  FAIL", p)
	}
	if len(problems) > 0 || len(links) == 0 {
		os.Exit(1)
	}
}

// readLinks 解析 tzdata.zi 中的 "L 目标 别名" 行。
func readLinks(path string) (map[string]string, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close()
	links := map[string]string{}
	sc := bufio.NewScanner(f)
	for sc.Scan() {
		if fs := strings.Fields(sc.Text()); len(fs) == 3 && fs[0] == "L" {
			links[fs[2]] = fs[1]
		}
	}
	return links, sc.Err()
}

func exists(name string) bool {
	_, err := os.Stat(filepath.Join(zoneDir, name))
	return err == nil
}

func compare(alias, target string) string {
	a, err := time.LoadLocation(alias)
	if err != nil {
		return fmt.Sprintf("%s: %v", alias, err)
	}
	b, err := time.LoadLocation(target)
	if err != nil {
		return fmt.Sprintf("%s -> %s: 目标加载失败: %v", alias, target, err)
	}
	for t := time.Date(1970, 1, 1, 12, 0, 0, 0, time.UTC); t.Year() <= 2037; t = t.AddDate(0, 0, 14) {
		an, ao := t.In(a).Zone()
		bn, bo := t.In(b).Zone()
		if an != bn || ao != bo {
			return fmt.Sprintf("%s vs %s @ %s: %s%+d vs %s%+d", alias, target, t.Format("2006-01-02"), an, ao, bn, bo)
		}
	}
	return ""
}

func fail(format string, args ...any) {
	fmt.Fprintf(os.Stderr, "tz-verify: "+format+"\n", args...)
	os.Exit(1)
}

两段式 Dockerfile，第二段换成你自己的基础镜像。构建目录里放 main.go 和 go.mod，go.mod 用 go mod init tzverify 生成即可，程序只用标准库。TZ_PKGS 默认装 tzdata tzdata-legacy，传 --build-arg TZ_PKGS=tzdata 可以复现上表里的失败；ubuntu:22.04 没有 tzdata-legacy 这个包，也要这样传。

ARG BASE_IMAGE=ubuntu:26.04
ARG GO_IMAGE=golang:1.27

FROM ${GO_IMAGE} AS build
WORKDIR /src
COPY go.mod main.go ./
RUN CGO_ENABLED=0 go build -trimpath -o /tz-verify .

FROM ${BASE_IMAGE}
ARG TZ_PKGS="tzdata tzdata-legacy"
ENV DEBIAN_FRONTEND=noninteractive
RUN apt-get update && apt-get install -y --no-install-recommends ${TZ_PKGS} \
 && ln -sf /usr/share/zoneinfo/Asia/Shanghai /etc/localtime \
 && rm -rf /var/lib/apt/lists/*
