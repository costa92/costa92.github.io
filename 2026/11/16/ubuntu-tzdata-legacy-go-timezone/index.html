Go 报 unknown time zone Asia/Calcutta：Ubuntu 24.04/26.04 镜像缺 tzdata-legacy 的排查与修复

 costalong  2026-11-16  更新于 2026-11-24  linux Go 故障排查 Docker Linux 运维

Go 程序在 ubuntu:24.04、ubuntu:26.04 容器里调用 time.LoadLocation("Asia/Calcutta")，返回 unknown time zone Asia/Calcutta；同一段代码在 ubuntu:22.04 里正常。下面的结果都是我在官方 ubuntu:22.04、ubuntu:24.04、ubuntu:26.04 镜像里补装 tzdata 后跑出来的，Go 用的是 golang:1.27 镜像。

24.04 缺 101 个旧时区名，26.04 缺 113 个

进 26.04 镜像看：

$ docker run --rm <镜像> sh -c '
dpkg -l tzdata tzdata-legacy | tail -n +6
for z in Asia/Calcutta Asia/Kolkata PRC US/Eastern EST5EDT; do
  [ -e /usr/share/zoneinfo/$z ] && echo "OK   $z" || echo "MISS $z"
done'
ii  tzdata         2026e-0ubuntu0.26.04.1 all  time zone and daylight-saving time data
un  tzdata-legacy  <none>                 <none> (no description available)
MISS Asia/Calcutta
OK   Asia/Kolkata
MISS PRC
MISS US/Eastern
MISS EST5EDT

旧名的文件挪到了 tzdata-legacy 包里，而这个包没装。旧名和标准名的对应关系还留在 /usr/share/zoneinfo/tzdata.zi 里，L 标准名 旧名 这样的行就是别名表。我把 tzdata-legacy 里除 right/* 外的 113 个旧名在三个镜像里挨个查了一遍：

基础镜像tzdata113 个旧名中缺失
ubuntu:22.042026e-0ubuntu0.22.04.10
ubuntu:24.042026e-0ubuntu0.24.04.1101
ubuntu:26.042026e-0ubuntu0.26.04.1113

11 月 24 日复查时 26.04 的 tzdata 已经更新到 2026f，162 个别名里缺 113 个，结果没变。24.04 已经缺了大半，26.04 又少了 CET、EST5EDT 这批 System V 名和 Asia/Choibalsan。从 22.04 直接升到 26.04，两次拆分会一起碰上。

拆分的来历在 tzdata 的 changelog.Debian.gz 和 NEWS.Debian.gz 里。Debian 2023c-8（2023 年 8 月）把 IANA backward 文件里的旧名、合并名移进 tzdata-legacy，US/* 也在内，Ubuntu 23.10 跟进，24.04 LTS 已经是这样。2023c-10 又把 UTC、CET 这类顶层名挪了回来。2024b-3 再把 CET、EST5EDT 等 System V 名移走，Ubuntu 从 25.04 开始，26.04 LTS 也包含。这个包也不会被顺带装上：apt-cache depends tzdata 显示 tzdata 对 tzdata-legacy 只有 Breaks 和 Replaces，没有 Depends 或 Recommends。

Asia/Calcutta 在 Go 的四个数据来源里都没找到；装上 tzdata-legacy 后在系统目录这一步就能找到。

内嵌 time/tzdata 能加载，但 Canada/Central 慢一小时

最省事的修法看起来是在 main 包加一行 import _ "time/tzdata"。我在 ubuntu:26.04 里试过，113 个旧名确实全部能加载；设了 TZ=Asia/Calcutta 时，Go 程序里的 time.Local 也从 UTC 变回了 +0530，系统的 date 不受影响，还是 UTC。

光能加载还不够。我把附录里的 tz-verify 加上 import _ "time/tzdata" 编译，拿内嵌数据加载的旧名和系统数据加载的标准名，比对 1970 到 2037 年的偏移。113 个里有一个对不上：

FAIL Canada/Central vs America/Winnipeg @ 2026-11-05: CST-21600 vs EST-18000

镜像里的 tzdata 是 2026e，changelog 写着 Manitoba 从 2026-10-31 起全年 -05。Go 1.27.4 内嵌的是 2026c，还会在 11 月 1 日回拨到 -06。同一个地方，写 America/Winnipeg 时间是对的，写 Canada/Central 就慢一小时。

镜像里有 /usr/share/zoneinfo 时，只有系统里缺的名字才会用到内嵌数据，缺的正是这些旧名。哪里改了夏令时，它的旧名就会算错，要等 Go 下个版本更新内嵌数据才能好。

内嵌数据还有一处管不到：/etc/localtime 链接到一个不存在的旧名（比如 PRC）又没设 TZ 时，结果仍是 UTC。看源码，不设 TZ 时 Go 拿 localtime 这个名字去 /etc 下找，退到内嵌数据时查的还是 localtime，内嵌数据里没有这个名字。

装 tzdata-legacy，再用 tz-verify 在构建期拦住

我最后选的是在 Dockerfile 里装 tzdata-legacy，镜像多约 1.2MB（带了整套 right/*），换来旧名和标准名读同一份系统数据，不会出现 Canada/Central 那样的偏差：

FROM ubuntu:26.04
ENV DEBIAN_FRONTEND=noninteractive
RUN apt-get update \
 && apt-get install -y --no-install-recommends tzdata tzdata-legacy \
 && ln -sf /usr/share/zoneinfo/Asia/Shanghai /etc/localtime \
 && rm -rf /var/lib/apt/lists/*

装好之后：

$ dpkg-query -W -f='${Package} ${Version}\n' tzdata tzdata-legacy
tzdata 2026e-0ubuntu0.26.04.1
tzdata-legacy 2026e-0ubuntu0.26.04.1
$ TZ=Asia/Calcutta date '+%Z %z'
IST +0530
$ TZ=PRC date '+%Z %z'
CST +0800

113 个旧名的文件都在，没内嵌 tzdata 的 Go 程序也能全部加载。

换基础镜像时容易忘装这个包，所以我写了一个构建期校验 tz-verify（代码见最后一节，也放在 blog-go-example/tzverify，可以照着 README 复现）。它和普通服务一样不内嵌 tzdata，只用系统数据，检查 tzdata.zi 里的全部别名能否加载、是否和标准名一致。在几个镜像上的结果：

镜像别名总数系统缺失问题构建
ubuntu:22.04，只装 tzdata15100通过
ubuntu:24.04，只装 tzdata151101101 个 unknown time zone失败
ubuntu:24.04，装了 legacy15100通过
ubuntu:26.04，只装 tzdata162113113 个 unknown time zone失败
ubuntu:26.04，装了 legacy16200通过

三个镜像都是 2026e，别名数却不一样。22.04 和 24.04 的稳定更新为了不改变行为，把 CET、EST5EDT 等 11 个 System V 名留成独立时区，tzdata.zi 里是 Z 行；26.04 里它们成了 L 行的别名。

不内嵌时别名和标准名读同一份系统数据，表里的问题全是加载失败，比对这一项没报过。比对是给内嵌了 time/tzdata 的服务准备的：服务加了那一行，tz-verify 也加上同一行再编译，就能比出 Canada/Central 这种偏差。

怎么复现：加载失败后悄悄按 UTC 算

问题最容易藏在“解析失败就按 UTC 兜底”的代码里。下面是一段示例，从请求头读客户端上报的时区名：

func parseTimezone(h http.Header) (offset float64, ok bool) {
	name := h.Get("X-Timezone")
	if name == "" {
		return 0, false
	}
	loc, err := time.LoadLocation(name)
	if err != nil {
		log.Errorw("parse timezone failed", "tz", name, "err", err)
		return 0, false // 调用方拿到 0，按 UTC 处理
	}
	_, sec := time.Now().In(loc).Zone()
	return float64(sec) / 3600, true
}

客户端上报的如果是 Asia/Calcutta、Asia/Saigon 这类旧名，在 26.04 镜像里偏移会变成 0：北京时间凌晨 3 点是 UTC 前一天 19 点，印度当地已是 0 点半，按 UTC 算出来的日期却还是前一天。凡是按用户当地日期分桶的逻辑都会算错。

靠 TZ 环境变量设时区的程序更难发现，出错时什么也不打印。glibc 遇到不认识的 TZ 直接退回 UTC：

$ TZ=Asia/Calcutta date '+%Z %z'
UTC +0000

Go 的 time.Local 加载不了 TZ=PRC 同样退回 UTC，不打日志。启动时把 time.Now().Format("-0700") 打进日志能兜住这一点，悄悄退回 UTC 时日志里会是 +0000。

在开发机上可能复现不出来，原因在 Go 查时区数据的顺序：time.LoadLocation 先看 ZONEINFO 环境变量，再查 /usr/share/zoneinfo 等系统目录，然后是程序内嵌的数据（引入 time/tzdata 才有），最后是 $GOROOT/lib/time/zoneinfo.zip。我的开发机也是 Ubuntu 26.04，系统目录里同样没有旧名，但装了 Go，最后这个 zip 里有。同样的代码用 go build -trimpath 编译，再以 GOROOT=/nonexistent 运行，就报 unknown time zone 了。macOS 的系统目录里本来就有旧名，到不了 zip 这一步。所以别直接 go run，编译后放进目标镜像里跑。

tzdata 太旧也会错：Casablanca 快一小时

反方向同样会出错。tzdata 停在 2023c 的镜像不知道摩洛哥从 2026-09-20 起改成全年 +00，还按 +01 算；也不认识 America/Coyhaique 这种后来才加的时区：

# tzdata 2023c
$ TZ=Africa/Casablanca date -d "2026-11-16 03:00 UTC" "+%Z %z"
+01 +0100
# tzdata 2026e
$ TZ=Africa/Casablanca date -d "2026-11-16 03:00 UTC" "+%Z %z"
+00 +0000

升级 tzdata 两头都要查：太旧算不对新规则，太新又可能缺旧名。自己排查时，先进镜像跑 dpkg -l tzdata-legacy，看 /usr/share/zoneinfo/Asia/Calcutta 在不在；再用 grep '^L ' /usr/share/zoneinfo/tzdata.zi 取出旧名清单，grep 配置、Dockerfile 和连接串（比如 Go DSN 的 loc=）。客户端上报的时区 grep 不到，得从日志里统计。

附：构建期校验 tz-verify

它从镜像的 /usr/share/zoneinfo/tzdata.zi 读出所有“别名 → 标准名”，逐个加载后和标准名比对 1970 到 2037 年每两周一个时间点的偏移与缩写。两次切换相隔不到两周的规则差异可能被漏掉。它不引入 time/tzdata，和服务一样只用系统数据。有别名加载失败或和标准名不一致、必需别名有一个不在清单里，或者一个别名都没读到，就以退出码 1 结束，让构建失败。必需别名是 15 个 Asia/Europe 旧名加上三个常见的美洲旧名，用来确认 tzdata.zi 确实读全了。

// tz-verify 在目标镜像内校验：tzdata.zi 中的每个时区别名都能加载，
// 且与其标准名在 1970–2037 的偏移、缩写一致。不引入 time/tzdata，和服务一样只用系统数据。
// 任一失败退出码为 1，用于让 docker build 失败。
package main

import (
	"bufio"
	"fmt"
	"os"
	"path/filepath"
	"strings"
	"time"
)

const zoneDir = "/usr/share/zoneinfo"

// 必须出现在 tzdata.zi 中的别名，防止清单读漏：15 个 Asia/Europe 旧名和三个常见的美洲旧名。
var required = []string{
	"Asia/Ashkhabad", "Asia/Calcutta", "Asia/Choibalsan", "Asia/Chungking",
	"Asia/Dacca", "Asia/Katmandu", "Asia/Macao", "Asia/Rangoon", "Asia/Saigon",
	"Asia/Thimbu", "Asia/Ujung_Pandang", "Asia/Ulan_Bator",
	"Europe/Kiev", "Europe/Uzhgorod", "Europe/Zaporozhye",
	"America/Buenos_Aires", "US/Eastern", "US/Pacific",
}

func main() {
	links, err := readLinks(filepath.Join(zoneDir, "tzdata.zi"))
	if err != nil {
		fail("读取 tzdata.zi: %v", err)
	}

	var problems []string
	missing := 0
	for alias, target := range links {
		if !exists(alias) {
			missing++
		}
		if p := compare(alias, target); p != "" {
			problems = append(problems, p)
		}
	}
	for _, alias := range required {
		if _, ok := links[alias]; !ok {
			problems = append(problems, "必需别名不在 tzdata.zi 中: "+alias)
		}
	}

	fmt.Printf("tz-verify: 别名 %d 个已校验（系统缺失 %d 个），问题 %d 个\n", len(links), missing, len(problems))
	for _, p := range problems {
		fmt.Println("  FAIL", p)
	}
	if len(problems) > 0 || len(links) == 0 {
		os.Exit(1)
	}
}

// readLinks 解析 tzdata.zi 中的 "L 目标 别名" 行。
func readLinks(path string) (map[string]string, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close()
	links := map[string]string{}
	sc := bufio.NewScanner(f)
	for sc.Scan() {
		if fs := strings.Fields(sc.Text()); len(fs) == 3 && fs[0] == "L" {
			links[fs[2]] = fs[1]
		}
	}
	return links, sc.Err()
}

func exists(name string) bool {
	_, err := os.Stat(filepath.Join(zoneDir, name))
	return err == nil
}

func compare(alias, target string) string {
	a, err := time.LoadLocation(alias)
	if err != nil {
		return fmt.Sprintf("%s: %v", alias, err)
	}
	b, err := time.LoadLocation(target)
	if err != nil {
		return fmt.Sprintf("%s -> %s: 目标加载失败: %v", alias, target, err)
	}
	for t := time.Date(1970, 1, 1, 12, 0, 0, 0, time.UTC); t.Year() <= 2037; t = t.AddDate(0, 0, 14) {
		an, ao := t.In(a).Zone()
		bn, bo := t.In(b).Zone()
		if an != bn || ao != bo {
			return fmt.Sprintf("%s vs %s @ %s: %s%+d vs %s%+d", alias, target, t.Format("2006-01-02"), an, ao, bn, bo)
		}
	}
	return ""
}

func fail(format string, args ...any) {
	fmt.Fprintf(os.Stderr, "tz-verify: "+format+"\n", args...)
	os.Exit(1)
}

两段式 Dockerfile，第二段换成你自己的基础镜像。构建目录里放 main.go 和 go.mod，go.mod 用 go mod init tzverify 生成即可，程序只用标准库。TZ_PKGS 默认装 tzdata tzdata-legacy，传 --build-arg TZ_PKGS=tzdata 可以复现上表里的失败；ubuntu:22.04 没有 tzdata-legacy 这个包，也要这样传。

ARG BASE_IMAGE=ubuntu:26.04
ARG GO_IMAGE=golang:1.27

FROM ${GO_IMAGE} AS build
WORKDIR /src
COPY go.mod main.go ./
RUN CGO_ENABLED=0 go build -trimpath -o /tz-verify .

FROM ${BASE_IMAGE}
ARG TZ_PKGS="tzdata tzdata-legacy"
ENV DEBIAN_FRONTEND=noninteractive
RUN apt-get update && apt-get install -y --no-install-recommends ${TZ_PKGS} \
 && ln -sf /usr/share/zoneinfo/Asia/Shanghai /etc/localtime \
 && rm -rf /var/lib/apt/lists/*
COPY --from=build /tz-verify /usr/local/bin/tz-verify
# 构建期校验：系统时区数据里每个别名都能加载且与标准名一致，否则构建失败
RUN /usr/local/bin/tz-verify
