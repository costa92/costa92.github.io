DeepSeek Super-agent：谁来管理多个 Agent 的任务

 2026-11-01  AI DeepSeek Agent DeepSeek Harness 多智能体
DeepSeek Agent DeepSeek Harness 多智能体

让一个编程 Agent 修 Bug，通常不难开始：交代问题，等它读代码、跑测试，再检查结果。

同时推进几件事后，麻烦出现在窗口外面。一个任务的评审意见到了 GitHub，另一个任务在群里改了需求，还有一个测试跑完了，等你回去接着处理。代码有人写了，消息仍要你搬，进度仍要你记。

DeepSeek 的 Super-agent 原型尝试接过这部分协调工作。沿着一项修复任务看下去，可以看清它增加了哪些系统机制，再判断自己的工作流是否需要它。

本文依据官方开源原型的固定提交 6337fc8，截至 2026 年 11 月 1 日。它是 DeepSeek Harness 的插件套件，围绕一个 GitHub 仓库工作，可选接入飞书；属于研究代码，与内部版本和更广泛的设计探索有差别。下面的导出 Bug 是解释流程的假设案例，没有部署官方原型；配套 Go 案例的本地与真实模型验证在后文单独说明。

截图来自官方仓库的 README 页面，对应本文分析的提交 6337fc8，截取于 2026 年 11 月 1 日。

把群聊和 GitHub 接进一个会话，还不够吗

假设你交给 Agent 一个问题：明明查到了数据，导出的 CSV 却是空的，请修复并补上回归测试。

它开始排查时，群里又来了另一项需求。与此同时，另一个 PR 下有人要求补测试。如果把这些消息全部塞进正在修导出问题的会话，Agent 就要一边保留当前的执行细节，一边分辨新消息属于哪项工作。耗时命令还可能让它迟迟接不到下一条输入。

多开几个会话能把工作分散开，但又会回到开头的问题：由谁记住每个窗口负责什么，把后续意见送过去？

Super-agent 增加了任务管理层。它接收协作平台的消息，判断是否开展工作，为任务安排执行会话，并把后续讨论关联回来。这里说的“普通 Agent”是常见的单会话编程用法，其他工具也可能已有类似能力，不能把两种用法当成整个行业的代际划分。

发生的事情人管理多个会话Super-agent 原型的安排
新工作到来人选择会话、交代背景检查来源与请求，决定是否接单
多项工作并行人记住各窗口进展分配执行器，并限制并发数量
PR 出现后续意见人转述到对应会话通过任务与讨论的订阅关系送达
需要判断或验收人逐个查看窗口集中呈现待回答、待评审和受阻事项

这层系统增加了部署和维护成本。只有一项明确的小修复时，直接开一个会话往往更省事；消息持续到来、任务反复接续时，协调负担才更值得单独处理。

谁负责接单，谁负责把代码改完

导出 Bug 可能要跑一轮较慢的测试。等待期间，接收新工作的入口不应该也跟着停住。原型把这两件事放到不同会话中：

  • 主 Session 是协调会话，负责接单判断、路由和交接。
  • Worker 是执行会话，在自己的上下文和任务目录里处理具体工作。需要时，它还可以调用 Subagent 分担子任务。

主 Session 不必亲自复现每个 Bug，Worker 也不必理解团队收到的全部消息。这是协调与执行分离的设计取舍：各自需要记住的内容变少了，系统却多了派工、输入投递和跨会话同步的责任。

还有一部分责任由程序承担。模型能判断一段话是什么意思，任务记录和状态变化则由 Engine 维护。下面是按开源架构文档整理的逻辑关系图，连线不表示独立服务器。文中技术图均可点击查看原尺寸。

图里的存储与队列让任务记录留在会话之外：SQLite 保存系统状态，Effects 保存待执行动作，Outbox 记录对外消息的发送情况。它们支撑任务的接续和恢复，后面会用一次通知失败说明。

协调器带多个执行器已有公开实践，例如 Anthropic 2025 年介绍的多智能体研究系统。这份原型值得具体检查的，是怎样把请求、授权、后续讨论与执行状态串起来。

新评论来了，怎样知道该交给谁

回到导出 Bug。假设一个有权限的开发者在 Issue 中 @ Agent，请它修复。系统检查请求来源，主 Session 决定接受后，创建一项 Ticket，并为它记录 Mandate。

可以把 Ticket 理解为一项持续跟踪的工作，Mandate 则记录为什么获准开展这项工作、允许做到哪里。它们由任务持有，不必随着执行会话的一次暂停就消失。相关定义见领域模型。

Worker 提交修复 PR 后，评审者说还要覆盖空输入。人通常希望这条意见继续交给原来处理问题的 Agent，不必重新描述整个故障。原型用订阅建立这种联系：任务关联了某个讨论线程，后续消息就能作为上下文送进来。

这时，如果评审者又提出重写认证模块，消息虽然也在同一条 PR 下，却已经超出了修复导出问题的范围。执行器应把它交回重新路由，判断是否另接任务。信息送达和任务授权需要分别处理。

下面画的是事件处理路径。Eval 指接单评估；订阅投递后，机器人事件仍可能独立进入评估，因此不能简单理解成“已有订阅就全部绕过评估”。

订阅省下的是重复识别任务、搬运背景的劳动，但消息归属和范围判断仍可能出错。Mandate 也不等于安全沙箱：是否超范围，还依赖执行器判断并按约定交回。具体规则见授权文档。

还有一种入口：群里有人提到故障，却没有向 Agent 发出明确请求。此时系统需要决定是否值得主动投入工作。原型先用确定性条件检查来源和请求强度，再让模型研判候选内容；主动接受需要匹配相应规则。

为避免一开始就在群里误接任务，可以先用默认的 observe 模式，看它原本打算接什么，再考虑切换到 auto。观察模式影响的是推断候选的主动接受，明确请求在各模式下仍可处理。观察记录也只能说明它怎样判断，不能当作修复成功的证据。

PR 提交了，这项工作就算结束了吗

Worker 把导出问题修好、检查通过，报告 ready。对于带 PR 的任务，这表示交来了可评审结果；是否满足原本要求，还要经过验收。

把整条路径放在一起，人的工作发生在哪里会更清楚。下表的阶段是阅读说明，不是一组新的内部状态码。

过程系统怎样接续人负责什么
Issue 提出修复要求检查来源，接单并记录范围给出复现条件与预期行为
等待资源、复现和修改安排 Worker；耗时命令可转入后台遇到缺失信息或必要决策时介入
提交 PR，报告 ready带 PR 的任务进入待评审阶段看改动、测试证据和风险
PR 要求补回归测试订阅送达原任务，范围内继续处理给出评审意见
讨论扩大到认证重写超范围要求交回重新判断决定是否另做这项工作
修复验收通过，PR 合并在本例只有一条相关 PR、且无未完成后续工作的条件下，任务可随 PR 结果结束按仓库规则验收与合并

任务结束后还会保留历史。未被人工停止的已结束任务，在授权重新校验通过后，可以因自身讨论线程上的人类后续消息恢复；机器人和 CI 消息不会以同样方式唤醒它。详见执行文档。

不过，人若还要不停打开面板确认“现在要不要管”，协调负担仍然存在。原型的面板设计先展示待回答、待评审和受阻的事项，再提供健康状态和历史。

这里需要节省的是人的注意力。每个 Worker 都播报内部进展，会把省下的切换时间变成阅读通知的时间。项目的设计原则因此强调，人在此时需要行动，或者结果对人有用，才值得发消息。

对交接质量，我还会多看一件事：它有没有说清已经完成什么、还缺什么、当前需要人决定什么。比如回归测试未能运行，交接时就应给出缺失条件和影响，让评审者知道接下来要核对哪里。

如果通知失败，或者进程中断，会怎样

假设 PR 已经创建，结果通知却因网络超时没发出去。如果系统只记“还没交付”，恢复后可能把整个修复再做一次；只记“已经完成”，又可能永远漏掉这条通知。

所以要分别保存修复工作的进展和消息的投递情况。原型在事务中记录状态变化，提交后再执行相关动作；Outbox 保留发送记录，动作队列在失败后延长等待再重试。这让系统有条件重试发送环节，而不必把修复任务从头再跑。

下面沿这个假设案例画出通知重试的逻辑时序。“任务与通知管理”合并表示状态存储、Outbox 和发送队列，省略内部调用；图中的超时表示尚未确认送达，远端也可能已经收到。

但远端操作成功、本地尚未记下结果时，进程也可能退出。因此，持久化不能保证每个外部动作都恰好发生一次。恢复时仍要核对 GitHub、工作目录和已有结果，防止重复推送或评论。

进程本身停了，又是另一层问题。数据库保存状态，不能自行启动服务。部署文档提供了在另一个 Harness 配置实例中设置定时检查的方案，避免检查器随被监控服务一起停掉，并要求尊重人工停止的意图。

这几处安排把长期运行拆成了可检查的问题：任务有没有留记录、动作有没有待办、恢复后是否核对远端、服务退出由谁发现。它们都需要验证，不能仅凭有数据库和重试就推导出可靠性。

用 GoAgent 与 Harness 把案例跑起来

只看关系图，任务记录与模型会话还是容易混在一起。我用 kart-io/goagent v0.33.0 补了一个可运行的 Go 案例，再接入 GoAgent Harness 的编码工具，让 Worker 能在教学工作区里实际修改代码、运行测试。

协调 Agent 判断是否存在可开展的工作；程序检查授权、观察模式、范围和订阅，再创建或接续 Ticket。GoAgent 负责模型与工具循环、持久化工作流和恢复；Harness 提供工作区、文件编辑、命令工具与权限装配。任务结果和待发通知共同写入应用快照，Outbox 单独负责投递。

下图对照案例代码 811698b 的默认 Docker 编码模式。宿主先验证修复结果，再由 Engine 核对任务版本并保存应用快照；框架检查点与调用日志分记录保存。文件工具受限访问宿主工作区，测试命令交给断网容器。

默认方案模式仍只生成修复建议。编码模式下，每个任务版本拥有独立工作区，Worker 使用 preset.Configure 把 Harness 装配接入 GoAgent。下面摘出执行节点的核心代码，外围错误处理和预算配置见完整实现：

agent, err := preset.Configure(builder.NewSimpleBuilder(client), asm).
    WithAgentID("csv-worker").
    WithSessionID(id).
    WithDurableScope("csv-worker").
    WithMaxIterations(10).
    WithTimeout(3 * time.Minute).
    Build()
if err != nil {
    return s, err
}
result, err := agent.AsRunnable().Invoke(ctx, s.Prompt)

外层持久图绑定稳定运行 ID，装配清单与模型配置参与版本校验。框架提供执行和恢复机制，订阅、任务范围、人工验收和通知队列由案例程序实现。

为了把开场的假设故障变成可重复的练习，模板故意漏掉 csv.Writer.Flush()：行还留在编码器缓冲区，函数就返回了底层 Buffer，所以小数据导出为空。脚本 Worker 通过 Harness 先运行失败测试、读取代码，再作出这一处修改：

+ writer.Flush()
  return buf.String(), writer.Error()

修改后重跑原有测试，覆盖普通多行、空输入，以及带引号、逗号和换行的 Unicode 内容。Worker 汇报完成后，宿主还会独立检查测试文件没有变化、重跑测试，并生成 diff 和源码哈希。模型只说“已经修好”不能让 Ticket 进入 ready。

下面展开新建 CSV 任务的主路径，省略已有订阅与中断恢复。接单只记录 pending，work 或演示命令显式触发执行；版本已更新时不发布旧结果。review 只读且不是强制前置，accept 才会复核并更新验收状态。通知也要调用 Deliver 才处理到期项，失败记录退避，不在后台自行轮询。

案例需要 Go 1.25 或更新版本、Git 和 Docker。准备好 golang:1.26.6-alpine 镜像后，在仓库根目录运行：

git clone https://github.com/costa92/blog-go-example.git
cd blog-go-example
git checkout 0a60245
mkdir -p .superagent
coding_state="$(mktemp -d "$PWD/.superagent/csv.XXXXXX")"
go run ./superagent/cmd/superagent -mode coding-demo -state-dir "$coding_state"
# 从输出中找到 Ticket ID，查看原始失败、独立测试结果和 diff：
go run ./superagent/cmd/superagent -mode review -ticket TICKET_ID -state-dir "$coding_state"
# 人工审阅后再确认；该命令会重新校验源码和测试：
go run ./superagent/cmd/superagent -mode accept -coding -ticket TICKET_ID -state-dir "$coding_state"

命令默认不需要 API Key。固定脚本通过真实的 Agent 工具循环修改文件、运行测试，命令在断网容器中执行。Docker 必须能读取状态目录；本机 Colima 不共享系统临时目录，因此示例把工作区放在已共享的项目目录，而不假定 /tmp 一定可用。更多命令、镜像选择和真实模型配置见编码 Worker 说明。

本地验证中，缺陷被复现，补上 Flush 后测试通过；完成图重放没有重复请求模型。测试还检查虚报成功被拒绝、范围外命令被拒绝、测试文件和过期证据不能用于验收，以及原有的并发调度和通知恢复。竞态检查、go vet、容器演示和验收命令均通过。

脚本测试验证的是工具与执行流程，不能直接证明模型会定位故障。随后我在 2026 年 11 月 1 日使用 -live 接入真实的 DeepSeek deepseek-flash，另建工作区运行同一个练习。模型读取源码和测试后，实际补上 Flush() 并检查刷新错误；原有三个测试与宿主独立容器验证均通过，Ticket 保持在 ready 等待人工评审。

真实调用还暴露了一个工具反馈问题：模型想用 ls/find 查找文件，或给测试命令加上 2>&1，都超出了宿主允许的命令。适配层现在提供只读 glob，不允许的命令继续拒绝，并把原因交回模型，让它改用允许的工具。第二轮真实运行中，这种纠正已经发生，被拒绝的命令没有执行；越界文件操作仍会中止本次执行。

这证明的是一次固定 CSV 案例的完整执行，并不是任意仓库的修复能力评测。Worker 仍只处理这份模板，没有创建 PR，也没有把 ready 自动变成人工验收。

案例使用文件快照而非官方原型的 SQLite，范围用可信宿主提供的标签比较。文件修改、命令执行、测试证据和人工验收都有各自的边界；即使测试通过，仍要阅读 diff，不能把它当成任意代码正确或安全的证明。

什么情况下值得试，应该怎样算收益

如果你每天都在把 PR 意见复制回 Agent、重新解释任务背景，这层系统有明确的试验对象。如果当前主要问题是模型修不对代码，增加任务管理层并没有直接解决那个问题。

试用前还要检查运行权限。原型为任务提供独立会话和目录，也可通过准备命令建立 Git worktree；这些能减少工作目录冲突。部署文档同时说明，执行器使用部署者的操作系统身份和 danger-full-access，账号包装器选择凭据，不提供进程隔离。独立目录并不限制它读取该系统用户的其他文件。

因此，第一轮可选择低影响仓库，使用只放 Agent 凭据的专用系统账号，限定一类可复现的任务。指定验收人，主动接单先留在 observe，再对选中的明确请求观察完整执行。这是本文的试点建议。

用一张共享表就能开始，由协调者从任务历史、面板和 PR 补录，每位参与者记下自己的介入时间：

要记录什么用来回答什么
请求到达、接单、Worker 开始执行的时间时间花在判断还是等待资源
首个可评审结果、验收通过的时间与结论结果提交和真正完成各要多久
人工介入的分钟数与原因是否少了搬消息，却多了评审或处理异常
主动候选的判断及人工回看结果哪些该接、哪些误接，约定候选事件中漏了哪些
所有尝试的模型支出、返工与维护时间包含失败以后，总账是否划算

两种工作方式要用一致的验收标准，控制模型、工具权限和预算。相同测试任务从相同代码快照、隔离环境开始，交错顺序，避免第二次继承第一次的答案；真实任务可以按复杂度配对分组。

最后同时看成功、失败、放弃和尚未验收的任务。全部尝试的模型支出除以验收通过数，人工小时按同一范围另算；未约定折算单价前，不把小时与金额相加。若没有任务通过验收，只报告总消耗。

我会先用这个试点回答一个具体问题：原来需要人搬运和跟进的工作，究竟少了多少？再把增加的维护、评审和异常处理算进去，才有依据决定是否扩大使用。
