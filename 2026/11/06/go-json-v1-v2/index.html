Go encoding/json v1 与 v2：行为差异、迁移方式与实测性能

 2026-11-06  golang Go JSON 标准库
Go JSON 标准库
golang
文章字数:   5.8k
阅读次数:  
   阅读模式

encoding/json 是 Go 里用得最多的标准库之一，它有不少早年定下、因为兼容性又无法修改的默认行为：字段名大小写不敏感、nil 切片编码成 null、默认转义 HTML 字符、非法 UTF-8 被替换成 U+FFFD 而不报错。

encoding/json/v2 就是为了解决这些问题而来的。它在 Go 1.25 以实验特性（GOEXPERIMENT=jsonv2）的形式进入标准库，到 Go 1.27 默认开启。本文所有输出都来自 Go 1.27.3 / linux amd64 上的实际运行结果。每一项差异都写成了测试，放在 blog-go-example/jsonv2，执行 go test -v ./jsonv2/ 即可在你自己的 Go 版本上复核。

一、版本时间线与包结构

先看清楚各版本的状态，我对本机装的几个版本逐一查了 src/internal/buildcfg/exp.go 里 JSONv2 的默认值：

Go 版本encoding/json/v2默认是否启用启用/关闭方式
1.24 及以前不存在—只能用 github.com/go-json-experiment/json
1.25 / 1.26存在否GOEXPERIMENT=jsonv2 开启
1.27存在是GOEXPERIMENT=nojsonv2 关闭

v2 由三个包组成：

  • encoding/json/jsontext：纯语法层，负责 JSON 的词法和格式，提供 Encoder / Decoder / Token / Value，完全不涉及 Go 类型反射。
  • encoding/json/v2：语义层，负责 Go 值和 JSON 之间的转换（Marshal / Unmarshal / MarshalWrite / UnmarshalRead 等），建立在 jsontext 之上。
  • encoding/json（v1）：API 不变。启用 jsonv2 后，v1 的内部实现改为“v2 + 一组兼容选项”，对外行为保持 v1 语义。

因此，升级到 Go 1.27 后，不改代码的 v1 调用也会由 v2 实现执行。我用同一段 v1 代码在默认和 GOEXPERIMENT=nojsonv2 下各跑一次，输出完全一致：

b, _ := json.Marshal(struct{ Tags []string }{})
var u User // UserName string `json:"user_name"`
err := json.Unmarshal([]byte("{\"USER_NAME\":\"a\xffb\",\"user_name\":\"c\"}"), &u)
fmt.Printf("%s %q %v\n", b, u.UserName, err)
h, _ := json.Marshal("<&>")
fmt.Printf("%s\n", h)
{"Tags":null} "c" <nil>
"<&>"

所以升级本身不会改变 v1 的语义；真正的行为变化只发生在你显式 import "encoding/json/v2" 的地方。

二、默认行为差异逐项实测

下面的示例用别名同时导入两个版本：

import (
	jsonv1 "encoding/json"
	"encoding/json/jsontext"
	jsonv2 "encoding/json/v2"
)

2.1 nil 切片和 nil map

type Nil struct {
	Tags  []string
	Attrs map[string]int
}
jsonv1.Marshal(Nil{})
jsonv2.Marshal(Nil{})
v1: {"Tags":null,"Attrs":null}
v2: {"Tags":[],"Attrs":{}}

v1 把 Go 的 nil 语义泄漏到了 JSON 里：同样是“没有元素”，nil 切片是 null，空切片是 []，前端经常因此多写一层判空。v2 统一编码成 [] / {}。如果下游确实依赖 null，可以用选项恢复：

jsonv2.Marshal(v, jsonv2.FormatNilSliceAsNull(true), jsonv2.FormatNilMapAsNull(true))
// {"Tags":null,"Attrs":null}

2.2 字段名匹配：大小写敏感

type User struct {
	UserName string `json:"user_name"`
	Age      int    `json:"age"`
}
in := []byte(`{"USER_NAME":"alice","Age":30}`)
v1: {UserName:alice Age:30}
v2: {UserName: Age:0}

v1 解码时对字段名做大小写不敏感匹配，USER_NAME、Age 都能对上。这个默认值既让人意外，也有性能代价：遇到未知字段时要额外做一次折叠比较。v2 改为精确匹配，对不上的键当成未知字段直接忽略，不报错。迁移后如果请求方用的字段名大小写和 tag 不一致，这些字段会变成零值，也不会有任何错误提示。

需要宽松匹配时有两种方式，一个是全局选项，一个是字段级 tag：

jsonv2.Unmarshal(in, &u, jsonv2.MatchCaseInsensitiveNames(true))
// {UserName:alice Age:30}

type Login struct {
	UserName string `json:"user_name,case:ignore"`
}
// {"UserName":"carol"} -> {UserName:carol}

注意 v2 的“不敏感”比 v1 更宽：它同时忽略 - 和 _，所以 userName、user_name、USER-NAME 都能匹配到 user_name。实测 {"userName":"bob"} 在开启选项后能正确填进 user_name 字段。

2.3 重复键

dup := []byte(`{"user_name":"a","user_name":"b"}`)
v1: {UserName:b}  err=<nil>
v2: {UserName:a}  err=jsontext: duplicate object member name "user_name"

v1 取最后一个值且不报错。RFC 8259 并没有规定重复键的语义，不同解析器有的取第一个、有的取最后一个，这种分歧曾经被用来绕过安全校验（网关看到的是 A，后端拿到的是 B）。v2 直接拒绝。确实需要兼容时用 jsontext.AllowDuplicateNames(true)。

2.4 非法 UTF-8

bad := []byte("{\"user_name\":\"a\xffb\"}")
v1: "a�b"  err=<nil>
v2: ""          err=jsontext: invalid UTF-8 within "/user_name" after offset 15

v1 会把非法字节替换成 U+FFFD，数据就这样悄悄被改了；v2 报错，并告诉你出错位置的 JSON Pointer 和字节偏移。兼容选项是 jsontext.AllowInvalidUTF8(true)。

2.5 HTML 字符转义

h := map[string]string{"html": `<a href="x">&</a>`}
v1: {"html":"\u003ca href=\"x\"\u003e\u0026\u003c/a\u003e"}
v2: {"html":"<a href=\"x\">&</a>"}

v1 默认把 <、>、& 转义成 \u00XX，防的是 JSON 被直接塞进 HTML 时的注入。Go 团队认为这是“层次错误”：JSON 库不该假设输出一定嵌进 HTML。v2 默认不转义，输出更短也更好读。如果你的 JSON 确实会内联进 <script>，显式打开 jsontext.EscapeForHTML(true) 和 jsontext.EscapeForJS(true)。

2.6 omitempty 的语义变了，新增 omitzero

type Omit struct {
	Name  string    `json:"name,omitempty"`
	Count int       `json:"count,omitempty"`
	Ptr   *string   `json:"ptr,omitempty"`
	When  time.Time `json:"when,omitempty"`
	Zero  time.Time `json:"zero,omitzero"`
	Obj   struct{}  `json:"obj,omitempty"`
}
v1: {"when":"0001-01-01T00:00:00Z","obj":{}}
v2: {"count":0,"when":"0001-01-01T00:00:00Z"}

两个版本对 omitempty 的判断依据不同：

  • v1 的 omitempty 按 Go 类型判断：false、0、nil 指针、nil 接口、长度为 0 的数组/切片/map/字符串会被省略。所以 count:0 被省略，而空结构体 obj:{} 不会，time.Time 零值也不会。
  • v2 的 omitempty 按 JSON 结果判断：编码结果是 null、""、{}、[] 才省略。所以 count:0 保留（0 不是空 JSON 值），obj:{} 被省略。
  • omitzero 按 Go 零值判断，有 IsZero() bool 方法时调用它。time.Time 零值靠它才能省掉。omitzero 在 Go 1.24 已经加入 v1，两个版本都能用。

迁移建议：原来 v1 里 int、bool 字段上的 omitempty，到 v2 改成 omitzero 才是原来的意思；time.Time、netip.Addr 这类有明确零值的类型也用 omitzero。

2.7 time.Duration 没有默认表示

type Job struct {
	Timeout time.Duration `json:"timeout"`
}
v1: {"timeout":1500000000}
v2: err=json: cannot marshal from Go time.Duration within "/timeout": no default representation

v1 把 Duration 当成普通 int64 输出纳秒数，对端很难看出单位。v2 在 1.27 里干脆不给默认值，直接报错，逼你做出选择。目前有两条路：

// 1. 沿用 v1 的纳秒整数
jsonv2.Marshal(j, jsonv1.FormatDurationAsNano(true))
// {"timeout":1500000000}

// 2. 自定义编码器，比如输出 "1.5s"
durStr := jsonv2.MarshalToFunc(func(enc *jsontext.Encoder, d time.Duration) error {
	return enc.WriteToken(jsontext.String(d.String()))
})
jsonv2.Marshal(j, jsonv2.WithMarshalers(durStr))
// {"timeout":"1.5s"}

版本差异提醒
Go 1.25/1.26 的实验版 v2 支持 json:"d,format:units" 这样的 format tag。到了 1.27，它已经从文档中移除，同样的写法会报 has unsupported `format` tag option。网上不少 v2 教程基于早期版本，照抄前请先确认自己的 Go 版本。

2.8 [N]byte 与数组长度

type Hash struct{ Sum [4]byte `json:"sum"` }
v1: {"sum":[1,2,3,4]}
v2: {"sum":"AQIDBA=="}

v1 里 []byte 编码成 base64 字符串，[N]byte 却是数字数组，两者不一致。v2 统一为 base64（兼容选项 jsonv1.FormatByteArrayAsArray）。

数组长度也变严格了：

type Arr struct{ A [2]int `json:"a"` }
// 输入 {"a":[1,2,3]}
v1: {[1 2]} err=<nil>
v2: {[1 2]} err=json: cannot unmarshal JSON array into Go [2]int within "/a": too many array elements

v1 静默丢掉多余元素，v2 要求长度严格相等。

2.9 map 键的顺序

m := map[string]int{"b": 2, "a": 1, "c": 3, "d": 4, "e": 5}
v1:               {"a":1,"b":2,"c":3,"d":4,"e":5}
v2:               {"b":2,"a":1,"c":3,"d":4,"e":5}
v2+Deterministic: {"a":1,"b":2,"c":3,"d":4,"e":5}

v1 总是按键排序，v2 为了流式编码和性能不排序。依赖输出稳定性的场景（签名、缓存键、golden 测试）要加 jsonv2.Deterministic(true)，或者对已有 JSON 调用 jsontext.Value.Canonicalize()。

2.10 指针接收者的 MarshalJSON

type ID struct{ v int64 }
func (i *ID) MarshalJSON() ([]byte, error) { return []byte(fmt.Sprintf(`"id-%d"`, i.v)), nil }

type Wrap struct{ I ID }
jsonv1.Marshal(Wrap{I: ID{42}})
jsonv2.Marshal(Wrap{I: ID{42}})
v1: {"I":{}}
v2: {"I":"id-42"}

这是 v1 的一个老坑：值不可寻址时（这里是按值传入的结构体），v1 不会调用定义在指针接收者上的 MarshalJSON，退化成反射编码；ID 没有导出字段，于是输出了 {}。v2 会在需要时取地址，统一调用方法。

2.11 string 选项

type Str struct{ N int64 `json:"n,string"` }
// 输入 {"n":123}
v1: err=json: cannot unmarshal number into Go struct field Str.n of type int64
v2: err=json: cannot unmarshal JSON number into Go int64 within "/n"

两者都要求带 ,string 的字段在 JSON 里是带引号的数字 "123"。区别在于 v2 把它限定为只能用于数字类型，用在其他类型上直接报错；v1 则静默忽略。

三、错误信息：带 JSON Pointer 的 SemanticError

同一个类型错误，看看两边的报错：

var v struct {
	Items []struct {
		Price int `json:"price"`
	} `json:"items"`
}
in := []byte(`{"items":[{"price":1},{"price":"9"}]}`)
v1: json: cannot unmarshal string into Go struct field .items.1.price of type int
v2: json: cannot unmarshal JSON string into Go int within "/items/1/price"

v2 的路径是标准 JSON Pointer（RFC 6901），可以直接拿去定位。而且错误是结构化的：

var se *jsonv2.SemanticError
if errors.As(err, &se) {
	fmt.Println(se.JSONPointer, se.JSONKind, se.GoType, se.ByteOffset)
}
// /items/1/price string int 31

写 API 网关或配置校验时，可以把 JSONPointer 直接返回给调用方，不用再从字符串里解析字段路径。

四、v2 的新能力

4.1 embed：内联结构体与“兜底”字段

v1 只能通过 Go 匿名嵌入来“摊平”字段，也没有办法保留未知字段。v2 用一个 embed 选项同时解决这两件事（1.25/1.26 里分别叫 inline 和 unknown，1.27 合并成了 embed）：

type Meta struct {
	Env string `json:"env"`
}
type Svc struct {
	ID   int  `json:"id"`
	Meta Meta `json:",embed"`
}
// {"id":1,"env":"prod"}

当 embed 字段的类型是 jsontext.Value 或 map[string]T 时，它就成了“兜底字段”，所有没被其他字段认领的键都收进来，编码时再原样写回：

type Cfg struct {
	Name  string         `json:"name"`
	Extra jsontext.Value `json:",embed"`
}
var c Cfg
jsonv2.Unmarshal([]byte(`{"name":"svc","timeout":30,"debug":true}`), &c)
// c.Extra = {"timeout":30,"debug":true}
jsonv2.Marshal(c)
// {"name":"svc","timeout":30,"debug":true}

这对“只改其中几个字段、其余原样透传”的场景很有用，比如代理修改配置、中间件补字段。反过来，如果想严格拒绝未知字段：

jsonv2.Unmarshal(data, &u, jsonv2.RejectUnknownMembers(true))
// json: cannot unmarshal JSON string into Go main.User: unknown object member name "nick"

v1 对应的是 Decoder.DisallowUnknownFields()，只能在 Decoder 上用，json.Unmarshal 没有这个选项。

4.2 流式接口：MarshalJSONTo / UnmarshalJSONFrom

v1 的 MarshalJSON() ([]byte, error) 必须先生成一段完整的 []byte，库再校验一遍、拷贝进输出，嵌套层数一多就有大量重复分配。v2 新增了直接操作编码器的接口：

type Celsius float64

func (c Celsius) MarshalJSONTo(enc *jsontext.Encoder) error {
	return enc.WriteToken(jsontext.String(fmt.Sprintf("%.1f°C", float64(c))))
}
// map[string]Celsius{"bj": 21.5} -> {"bj":"21.5°C"}

对应的解码接口是 UnmarshalJSONFrom(*jsontext.Decoder) error。原有的 MarshalJSON / UnmarshalJSON 在 v2 中仍然被识别，不需要为迁移重写。

4.3 调用方指定的编解码函数

除了在类型上定义方法，v2 还能在调用时为某个类型临时指定编解码逻辑，这在 v1 里做不到。前面的 Duration 例子用的就是这个：MarshalToFunc / UnmarshalFromFunc 生成 Marshalers，再通过 WithMarshalers 传进去。适合以下场景：

  • 第三方类型，你没法给它加方法；
  • 同一个类型在不同接口里需要不同表示（例如对外接口输出 "1.5s"、内部存储输出纳秒）。

4.4 jsontext：按 token 流式处理

jsontext.Decoder 可以逐个读 token，不需要把整个文档反序列化成 Go 值。下面统计日志里 lvl 为 error 的条目数：

dec := jsontext.NewDecoder(strings.NewReader(
	`{"logs":[{"lvl":"info"},{"lvl":"error"},{"lvl":"error"}]}`))
n := 0
for {
	tok, err := dec.ReadToken()
	if err != nil {
		break // io.EOF 或语法错误
	}
	if tok.Kind() == '"' && tok.String() == "lvl" {
		val, _ := dec.ReadToken()
		if val.String() == "error" {
			n++
		}
	}
}
// n = 2

v1 也有 Decoder.Token()，但每个 token 都装箱成 interface{}，分配多、速度慢。jsontext.Token 是值类型，配合 ReadValue / SkipValue 可以跳过不关心的子树。

jsontext.Value 还自带格式化工具：

raw := jsontext.Value(`{"b":1,"a":[1, 2 ]}`)
raw.Canonicalize() // {"a":[1,2],"b":1}，按 RFC 8785 规范化，可用于签名
raw.Indent()       // 美化输出

五、迁移策略

5.1 不迁移也能吃到一部分红利

如前所述，Go 1.27 下 v1 已经跑在 v2 引擎上，语义不变、解码更快（见第六节数据）。对大多数项目来说，升级 Go 版本本身就是第一步。如果升级后发现兼容问题，可以先用 GOEXPERIMENT=nojsonv2 回退到旧实现，同时向上游报告问题。

5.2 用 DefaultOptionsV1 渐进切换

v1 包里导出了 DefaultOptionsV1()，把它传给 v2 的函数，就能得到 v1 语义：

in := []byte(`{"USER_NAME":"alice"}`)
jsonv2.Unmarshal(in, &a)                            // {UserName:}
jsonv2.Unmarshal(in, &b, jsonv1.DefaultOptionsV1()) // {UserName:alice}

选项可以叠加，后面的覆盖前面的。于是可以先整体套上 v1 语义，再逐条关掉不想要的旧行为：

jsonv2.Marshal(User{}, jsonv1.DefaultOptionsV1())
// {"user_name":"","tags":null}
jsonv2.Marshal(User{}, jsonv1.DefaultOptionsV1(), jsonv2.FormatNilSliceAsNull(false))
// {"user_name":"","tags":[]}

v1 包里还有一组更细的开关（MatchCaseSensitiveDelimiter、OmitEmptyWithLegacySemantics、CallMethodsWithLegacySemantics、UnmarshalArrayFromAnyLength 等），每个对应一项历史行为，便于逐项排查。

5.3 迁移检查清单

把 import "encoding/json" 换成 v2 之前，逐项确认：

检查项v1 → v2 的变化处理方式
请求体字段大小写不一致匹配不上的字段被静默忽略case:ignore 或 MatchCaseInsensitiveNames
前端依赖 nullnil 切片/map 变为 []/{}FormatNilSliceAsNull / FormatNilMapAsNull
数值字段用了 omitempty0/false 不再被省略改为 omitzero
time.Duration 字段直接报错FormatDurationAsNano 或自定义 MarshalToFunc
[N]byte 字段改为 base64FormatByteArrayAsArray
输出要求稳定map 键不再排序Deterministic(true)
JSON 内嵌进 HTML不再转义 <>&EscapeForHTML / EscapeForJS
上游可能有脏数据重复键、非法 UTF-8 报错AllowDuplicateNames / AllowInvalidUTF8，或修数据源
解析错误字符串的代码错误文本格式变了改用 errors.As 拿 *SemanticError

前两项最危险，因为它们不报错，只是结果不同。迁移时最好准备一组真实请求样本，分别用 v1 和 v2 解码，再逐个比较结果。

六、性能实测

测试数据：1000 个对象组成的数组（约 98KB），每个对象含 int64、string、float64、[]string 和 map[string]string 字段。环境为 Intel i7-14700KF、Go 1.27.3，-count 3 取中位数。“经典 v1”使用 GOEXPERIMENT=nojsonv2。

基准代码如下（bench_test.go）。解码和编码各一组，v1 与 v2 用同一份数据：

type Item struct {
	ID    int64             `json:"id"`
	Name  string            `json:"name"`
	Price float64           `json:"price"`
	Tags  []string          `json:"tags"`
	Attrs map[string]string `json:"attrs"`
}

// 1000 个对象，约 98KB。
var benchData = func() []byte {
	var sb strings.Builder
	sb.WriteString("[")
	for i := range 1000 {
		if i > 0 {
			sb.WriteString(",")
		}
		fmt.Fprintf(&sb, `{"id":%d,"name":"item-%d","price":%d.5,"tags":["a","b","c"],"attrs":{"color":"red","size":"L"}}`, i, i, i)
	}
	sb.WriteString("]")
	return []byte(sb.String())
}()

func BenchmarkV1Unmarshal(b *testing.B) {
	b.SetBytes(int64(len(benchData)))
	for b.Loop() {
		var v []Item
		if err := jsonv1.Unmarshal(benchData, &v); err != nil {
			b.Fatal(err)
		}
	}
}

func BenchmarkV2Marshal(b *testing.B) {
	var v []Item
	jsonv2.Unmarshal(benchData, &v)
	b.SetBytes(int64(len(benchData)))
	for b.Loop() {
		if _, err := jsonv2.Marshal(v); err != nil {
			b.Fatal(err)
		}
	}
}

// BenchmarkV2Unmarshal、BenchmarkV1Marshal 结构相同，只换调用的包。

b.Loop() 是 Go 1.24 新增的基准循环写法，会自动排除循环外的准备代码。运行方式：

# v1 跑在 v2 引擎上（1.27 默认）与 v2
go test ./jsonv2/ -run '^$' -bench . -benchmem -count 3

“经典 v1”那一行需要 GOEXPERIMENT=nojsonv2。但关掉实验后，本目录会因为构建约束被整个跳过（见第七节），所以要把两个 BenchmarkV1* 复制到一个不引用 v2、也不带该约束的文件里单独运行。结果汇总：

v1（v2 引擎）0.94 ms（105 MB/s）80120.53 ms（186 MB/s）4003
v20.84 ms（118 MB/s）80120.47 ms（211 MB/s）2003

从这组数据可以看出：

  • 解码提升明显：v2 比经典 v1 快约 37%，分配次数少三分之一。即使继续用 v1 API，也有约 30% 的提升。
  • 编码在这个负载下反而更慢：v2 比经典 v1 慢约 37%，v1 跑在 v2 引擎上慢约 55%，虽然分配次数更少。性能差异和数据形状关系很大（这里每个对象都带一个小 map 和一个字符串切片），不要把官方或别人的数字直接套到自己的服务上。

如果服务以编码为主（比如大量序列化响应体），升级到 1.27 后建议用自己的真实数据跑一遍基准；编码确实成为瓶颈时，可以先用 GOEXPERIMENT=nojsonv2 回退，再观察后续版本的优化。

七、用测试复核这些差异

前面每一项输出都写成了断言，放在 blog-go-example/jsonv2 的 diff_test.go 里。在自己的 Go 版本上运行一条命令就能复核文中结论；Go 升级后如果 v2 的行为有变化，对应的测试会失败。迁移业务代码时，也可以照这个思路，把关心的样本固定成测试。

7.1 构建约束

//go:build goexperiment.jsonv2 && go1.27

package jsonv2

两个条件缺一不可：goexperiment.jsonv2 保证 v2 包存在；go1.27 把 1.25/1.26 排除在外，因为那两个版本的实验版用的是 inline、unknown、format 这些旧 tag，本案例的断言在那里不成立。满足不了条件时，整个目录会被跳过，不影响仓库里的其他案例。

7.2 辅助函数

import (
	jsonv1 "encoding/json"
	"encoding/json/jsontext"
	jsonv2 "encoding/json/v2"
	"errors"
	"fmt"
	"strings"
	"testing"
	"time"
)

type User struct {
	UserName string `json:"user_name"`
	Age      int    `json:"age"`
}

// marshalBoth 用两个版本编码同一个值，任何一边出错都直接让测试失败。
func marshalBoth(t *testing.T, v any) (string, string) {
	t.Helper()
	b1, err := jsonv1.Marshal(v)
	if err != nil {
		t.Fatalf("v1: %v", err)
	}
	b2, err := jsonv2.Marshal(v)
	if err != nil {
		t.Fatalf("v2: %v", err)
	}
	return string(b1), string(b2)
}

func expect(t *testing.T, name, got, want string) {
	t.Helper()
	if got != want {
		t.Errorf("%s = %s, want %s", name, got, want)
	}
}

// expectErr 只匹配错误文本的关键片段，避免把整条错误信息写死。
func expectErr(t *testing.T, err error, substr string) {
	t.Helper()
	if err == nil || !strings.Contains(err.Error(), substr) {
		t.Errorf("err = %v, want containing %q", err, substr)
	}
}

t.Helper() 让失败信息指向调用处的行号，而不是辅助函数内部。

7.3 编码差异：nil 切片与 omitempty

func TestNilSliceAndMap(t *testing.T) {
	type Nil struct {
		Tags  []string
		Attrs map[string]int
	}
	v1, v2 := marshalBoth(t, Nil{})
	expect(t, "v1", v1, `{"Tags":null,"Attrs":null}`)
	expect(t, "v2", v2, `{"Tags":[],"Attrs":{}}`)

	b, _ := jsonv2.Marshal(Nil{}, jsonv2.FormatNilSliceAsNull(true), jsonv2.FormatNilMapAsNull(true))
	expect(t, "v2+FormatNil*AsNull", string(b), `{"Tags":null,"Attrs":null}`)
}

func TestOmitEmptyAndOmitZero(t *testing.T) {
	type Omit struct {
		Name  string    `json:"name,omitempty"`
		Count int       `json:"count,omitempty"`
		Ptr   *string   `json:"ptr,omitempty"`
		When  time.Time `json:"when,omitempty"`
		Zero  time.Time `json:"zero,omitzero"`
		Obj   struct{}  `json:"obj,omitempty"`
	}
	v1, v2 := marshalBoth(t, Omit{})
	expect(t, "v1", v1, `{"when":"0001-01-01T00:00:00Z","obj":{}}`)
	expect(t, "v2", v2, `{"count":0,"when":"0001-01-01T00:00:00Z"}`)
}

7.4 解码差异：大小写与重复键

v2 的大小写差异不报错，只表现为字段没被填上，所以这里比较的是解码后的结构体，而不是错误：

func TestCaseSensitiveNames(t *testing.T) {
	in := []byte(`{"USER_NAME":"alice","Age":30}`)
	var u1, u2, u3 User
	if err := jsonv1.Unmarshal(in, &u1); err != nil {
		t.Fatal(err)
	}
	if err := jsonv2.Unmarshal(in, &u2); err != nil {
		t.Fatal(err)
	}
	if u1 != (User{"alice", 30}) || u2 != (User{}) {
		t.Errorf("v1=%+v v2=%+v", u1, u2)
	}
	if err := jsonv2.Unmarshal(in, &u3, jsonv2.MatchCaseInsensitiveNames(true)); err != nil || u3 != (User{"alice", 30}) {
		t.Errorf("MatchCaseInsensitiveNames: %+v %v", u3, err)
	}

	// v2 的不敏感匹配还忽略 - 和 _
	var u4 User
	jsonv2.Unmarshal([]byte(`{"userName":"bob"}`), &u4, jsonv2.MatchCaseInsensitiveNames(true))
	expect(t, "camelCase", u4.UserName, "bob")

	var l struct {
		UserName string `json:"user_name,case:ignore"`
	}
	jsonv2.Unmarshal([]byte(`{"UserName":"carol"}`), &l)
	expect(t, "case:ignore", l.UserName, "carol")
}

func TestDuplicateNames(t *testing.T) {
	in := []byte(`{"user_name":"a","user_name":"b"}`)
	var u1, u2, u3 User
	if err := jsonv1.Unmarshal(in, &u1); err != nil || u1.UserName != "b" {
		t.Errorf("v1: %+v %v", u1, err)
	}
	expectErr(t, jsonv2.Unmarshal(in, &u2), `duplicate object member name "user_name"`)
	if err := jsonv2.Unmarshal(in, &u3, jsontext.AllowDuplicateNames(true)); err != nil {
		t.Errorf("AllowDuplicateNames: %v", err)
	}
}

7.5 time.Duration：把版本变化也固定下来

最后一段断言检查 format tag 在 1.27 中已不受支持。Go 1.25/1.26 的教程大多用这个写法，如果后续版本恢复了它，这条断言会失败。

func TestDuration(t *testing.T) {
	type Job struct {
		Timeout time.Duration `json:"timeout"`
	}
	j := Job{Timeout: 1500 * time.Millisecond}

	b, _ := jsonv1.Marshal(j)
	expect(t, "v1", string(b), `{"timeout":1500000000}`)

	_, err := jsonv2.Marshal(j)
	expectErr(t, err, "no default representation")

	b, _ = jsonv2.Marshal(j, jsonv1.FormatDurationAsNano(true))
	expect(t, "FormatDurationAsNano", string(b), `{"timeout":1500000000}`)

	durStr := jsonv2.MarshalToFunc(func(enc *jsontext.Encoder, d time.Duration) error {
		return enc.WriteToken(jsontext.String(d.String()))
	})
	b, _ = jsonv2.Marshal(j, jsonv2.WithMarshalers(durStr))
	expect(t, "MarshalToFunc", string(b), `{"timeout":"1.5s"}`)

	// Go 1.25/1.26 的 format tag 在 1.27 已移除
	type Old struct {
		D time.Duration `json:"d,format:units"`
	}
	_, err = jsonv2.Marshal(Old{})
	expectErr(t, err, "unsupported `format` tag option")
}

7.6 embed 与结构化错误

func TestEmbed(t *testing.T) {
	type Meta struct {
		Env string `json:"env"`
	}
	type Svc struct {
		ID   int  `json:"id"`
		Meta Meta `json:",embed"`
	}
	b, _ := jsonv2.Marshal(Svc{ID: 1, Meta: Meta{Env: "prod"}})
	expect(t, "embed struct", string(b), `{"id":1,"env":"prod"}`)

	type Cfg struct {
		Name  string         `json:"name"`
		Extra jsontext.Value `json:",embed"`
	}
	in := `{"name":"svc","timeout":30,"debug":true}`
	var c Cfg
	if err := jsonv2.Unmarshal([]byte(in), &c); err != nil {
		t.Fatal(err)
	}
	expect(t, "fallback", string(c.Extra), `{"timeout":30,"debug":true}`)
	b, _ = jsonv2.Marshal(c)
	expect(t, "roundtrip", string(b), in) // 未知字段原样写回

	var u User
	expectErr(t, jsonv2.Unmarshal([]byte(`{"user_name":"a","nick":"x"}`), &u, jsonv2.RejectUnknownMembers(true)),
		`unknown object member name "nick"`)
}

func TestSemanticError(t *testing.T) {
	var v struct {
		Items []struct {
			Price int `json:"price"`
		} `json:"items"`
	}
	in := []byte(`{"items":[{"price":1},{"price":"9"}]}`)
	expectErr(t, jsonv1.Unmarshal(in, &v), "Go struct field .items.1.price of type int")

	err := jsonv2.Unmarshal(in, &v)
	var se *jsonv2.SemanticError
	if !errors.As(err, &se) {
		t.Fatalf("want *SemanticError, got %T", err)
	}
	expect(t, "JSONPointer", string(se.JSONPointer), "/items/1/price")
	if se.ByteOffset != 31 {
		t.Errorf("ByteOffset = %d", se.ByteOffset)
	}
}

八、小结

v2 的默认行为更严格，也更贴近 JSON 本身的语义，宽松行为需要通过选项显式打开。重复键、非法 UTF-8、数组元素过多、Duration 没有指定格式，这些情况 v1 不报错，v2 都会报错。

实际落地可以分三步：

  1. 升级到 Go 1.27，v1 代码不改，先拿到解码性能提升，同时验证编码路径没有变慢；
  2. 新代码直接用 v2，按第五节的清单设置 tag 和选项；
  3. 老代码用 DefaultOptionsV1() 平移到 v2，再逐项去掉兼容选项，每去一项都用真实样本做对比测试。

另外要注意，v2 的细节仍在变化：从 1.26 到 1.27，inline/unknown 合并成了 embed，format tag 被移除，Duration 也没有了默认表示。写代码和查资料时，都以你所用 Go 版本自带的 go doc encoding/json/v2 为准。
