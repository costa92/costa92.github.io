审核后补了 3 行代码，内容摘要让旧批准失效，摘要之外的改动要靠树比较拦住

 costalong  2026-11-23  更新于 2026-11-24  AI AI Agent 软件工程 测试
AI Agent 软件工程 测试
AI
文章字数:   3.4k
阅读次数:

多个 Agent 接力开发时，我最常遇到的交接是这样的：实现者写完，复核者说“通过”，准备合并前实现者又补了一个错误分支，顺手加了一条测试。聊天记录里那句“通过”还在，可它说的是改动之前的代码。

我想知道把审核结论绑到内容摘要上，到底能拦住哪些情况、拦不住哪些情况，于是写了一个约 430 行的 Go 命令行 gate，在一个小 Go 项目上把这次交接完整走了一遍，又用变异测试检查了示例项目的测试和 gate 自己的测试。代码、场景脚本和原始输出都在 blog-go-example/review-gates，下文的终端输出来自 2026-11-24 在 Linux x86_64、Go 1.27.4、git 2.53.0 上的运行（results/scenario.txt、results/go-test-v.txt）。

被审核的示例：把 current 切到恢复出来的副本

示例项目只有一个 promote 包，约 110 行。它把服务入口 current 这个符号链接切到 replicas/<name>，规格 SPEC.md 写了 8 条验收条件，比较关键的几条：

  • old.lock 存在（旧实例还在跑）时拒绝，current 不动；
  • 读取旧目录遇到“不存在”以外的错误，比如权限错误，拒绝；
  • 副本的 STATUS 不是 ready 时拒绝；
  • intent 文件记着另一个副本的未完成切换时拒绝；
  • 先写 intent 再切 current，切完后进程中断，intent 必须还在，Resume 能按它补完。

我选这个例子，是因为它的错误大多不体现在返回值上：先把 current 切过去、再检查副本状态并返回错误，调用方照样拿到一个 error，但入口已经被改坏了。后面的变异测试会用到这一点。

三个摘要各算什么

gate 读仓库根目录的 review-gates.json，示例里是这样配的：

{
  "base": "main",
  "design": ["SPEC.md"],
  "tests": ["promote/*_test.go"],
  "test_cmd": ["go", "test", "-count=1", "./..."],
  "code": ["promote/", ":(exclude)promote/*_test.go"]
}

每个关卡的摘要由若干组成部分合成，批准记录里把组成部分也存下来，这样失效时能说出是哪一部分变了：

关卡组成部分不包含
design每个规格文件内容的 SHA-256代码、测试
tests每个测试文件内容的 SHA-256，加上 go test -json 逐用例 pass/fail/skip 列表（排序、去掉耗时）的 SHA-256被测代码本身
code合并基点的提交号，加上 code 路径下每个文件 merge-base..HEAD diff 的 SHA-256未提交的改动（有就直接报错，不计算）

gate approve code --by reviewer-b 写出的 .review/code.json 长这样，这是场景里第一次批准时的真实文件：

{
  "gate": "code",
  "digest": "21390bde8a00a961f80ff30882ec4e410a1208c0e1993b81cdf12b405d625f34",
  "parts": {
    "base": "9b338ae418e648233949b2a240d0044a36d4a74a",
    "diff:promote/promote.go": "873b5a61aadbeb9a3e9b289852742888204c27a6496bb1bc0a832249ba06db7e"
  },
  "approved_by": "reviewer-b",
  "approved_at": "2026-11-24T08:24:49Z",
  "head": "b2ef1049d430f3fce4950b0f8a04b90d019485cb",
  "tree": "d714908eea56423a65fc9074d7eea18da9063118"
}

tree 是批准时 HEAD 的树对象，merge-check 要用它。.review/ 在 .gitignore 里，批准记录不进提交树，否则每写一条记录树就变一次。

补了 3 行之后，check 指出两项失效、一项仍有效

场景脚本 scenario/run.sh 在临时目录建仓库：main 上只有规格和配置，实现者在 promote 分支提交实现，复核者批准三个关卡，merge-check 通过：

$ gate merge-check
design OK       a5c6836afd16 approved by reviewer-b
tests  OK       9f90635f1d5b approved by reviewer-b
code   OK       21390bde8a00 approved by reviewer-b
tree   OK       squash candidate d714908eea56 == reviewed tree
merge-check: OK

然后实现者补了一个错误分支：副本目录里没有 STATUS 文件时，原来会把 os.ReadFile 的原始错误抛出去，现在归为“副本未就绪”。同时在表驱动测试里加了一条用例。改动是 promote.go 加 3 行、promote_test.go 加 7 行：

b, err := os.ReadFile(filepath.Join(root, "replicas", name, "STATUS"))
if os.IsNotExist(err) {
	return fmt.Errorf("%w: %s has no STATUS", ErrBlocked, name)
}

提交后再跑 check 和 merge-check：

$ gate check
design OK       a5c6836afd16 approved by reviewer-b
tests  STALE    approved 9f90635f1d5b by reviewer-b, now 65f2ce816854
         ~ file:promote/promote_test.go 8f5bd9d36d79 -> 53511da09f0e
         ~ go test result 56502927452e -> 52dfd2926c85
code   STALE    approved 21390bde8a00 by reviewer-b, now 5033581a9b59
         ~ diff:promote/promote.go 873b5a61aadb -> 56d6d709713e
check: FAIL
[exit 1]
$ gate merge-check
...（三行关卡状态同上）
tree   FAIL     squash candidate b135566fed12 != reviewed tree d714908eea56
         M	promote/promote.go
         M	promote/promote_test.go
merge-check: FAIL
[exit 1]

这份输出回答了交接时最需要的三个问题。规格没动，design 的批准继续有效，不用重做设计复核。测试记录失效有两个原因：测试文件变了，go test 的用例列表也多了一条。代码复核失效只因为 promote.go 的 diff 变了，复核者要看的就是这 3 行，而不是整个功能。

merge-check 在临时 worktree 里从 main 做 git merge --squash，提交出候选，再拿候选的树和 code 批准时记下的树比较。这里两边的差异正好是那两个文件。

复核者看完 git diff HEAD~1 -- promote/promote.go，重新批准 tests 和 code，merge-check 通过，候选树 b135566fed12 和新批准的树一致。整个场景脚本（含后面两段）跑一遍约 2 秒，大头是每次 check 都会重跑 go test。

只改 README：三项摘要全过，树比较拦下

接着实现者只改了 README.md，这个文件不在任何关卡的范围里：

$ gate check
design OK       a5c6836afd16 approved by reviewer-b
tests  OK       65f2ce816854 approved by reviewer-b
code   OK       5033581a9b59 approved by reviewer-b
check: OK
$ gate merge-check
...（三行 OK）
tree   FAIL     squash candidate cb9e7a9c2bb1 != reviewed tree b135566fed12
         M	README.md
merge-check: FAIL
[exit 1]

摘要只覆盖配置里列出的路径。真实项目里，go.mod、生成代码、配置文件、CI 脚本都可能改变行为，却很容易没被列进 code。树比较不关心范围，只要候选里有任何一个文件和复核时不同就拒绝。代价也在这里：改个错别字也得让复核者重新批准一次 code。重新批准后 code 的摘要还是 5033581a9b59，只有记录里的 tree 换成了新树。

我的取舍是两样都留：摘要负责告诉复核者“哪部分变了、要看什么”，树比较负责保证合并进去的正是被看过的那棵树。只有摘要，会放过范围外的改动；只有树比较，只知道“变了”，不知道该重审哪一项。

主分支前进以后

场景最后在 main 上提交一个无关的 HOTFIX.md，回到功能分支跑 merge-check：

base   FAIL     main is not an ancestor of HEAD; rebase and re-review

变基到新的 main 之后，check 显示只有 code 失效，且只有合并基点一项变了，diff 本身没变：

code   STALE    approved 5033581a9b59 by reviewer-b, now 408e38081975
         ~ base 9b338ae418e6 -> 168d9d91238c

把合并基点算进 code 摘要是我有意的选择：变基后代码和新的主分支组合在一起，复核者至少该确认一次。输出里能看出 diff 没变，这次确认可以很快。如果嫌每次变基都要批准太频繁，可以把 base 从摘要里去掉，靠 merge-check 的祖先检查和树比较兜底。下面的变异测试 G1 正是这个改法，它会让“变基后旧批准仍然有效”。

（results/scenario.txt 里的提交号和含合并基点的 code 摘要每次运行都不同，因为提交带时间戳；文件摘要和树对象每次一致。）

测试能不能认出错误实现：9 个变异

check 能保证测试记录对应当前的测试文件，但测试本身能不能发现错误实现，是另一回事。我给 promote 写了两套测试：完整测试每条用例都断言返回的错误类型、current 的指向和 intent 的内容，并模拟“切换后崩溃”“写完 intent 后崩溃”；弱测试覆盖同样的拒绝场景，但只断言“有没有返回错误”，也没有崩溃模拟。

mutation/mutation_test.go 把整个目录复制到临时目录，每次改一处源码，再跑测试，测试失败就算发现了这个变异。前 4 个对应规格里最容易被写错的拒绝条件，后 5 个是我在写实现时觉得最可能出错的地方：

变异完整测试弱测试
M1 取不到旧实例的锁仍继续发现（AC1、AC7 锁）发现
M2 权限错误当作旧目录不存在发现（AC2）发现
M3 忽略副本的阻塞状态发现（AC3、AC7 阻塞）发现
M4 有别的副本的未完成切换仍放行发现（AC4）发现
M5 先切 current 再写 intent发现（两个崩溃用例、切换失败用例）存活
M6 成功后不删 intent发现（AC6、AC7 补完、崩溃用例）存活
M7 Resume 绕过锁和状态检查发现（AC7 锁、AC7 阻塞）发现
M8 吞掉切换失败的错误发现（仅切换失败用例）发现
M9 切换之后才检查副本状态发现（AC3、AC7 阻塞）存活

完整测试 9/9，弱测试 6/9。弱测试漏掉的三个都有一个共同点：返回值没错，错的是磁盘上的状态。M9 最典型，阻塞的副本照样被切成了 current，函数随后返回 ErrBlocked，只看错误的测试认为一切正常。M5 只有在崩溃那一刻才暴露，没有崩溃模拟就测不到。

M2 没被弱测试漏掉，原因有点偶然：变异后代码不再拒绝，后续检查都通过，切换成功，函数不返回错误，弱测试恰好能发现。如果权限错误让后面某一步也失败，返回的就是另一个错误，弱测试会把它当成“正确拒绝”。完整测试用 errors.Is(err, ErrOldUnreadable) 断言错误类型，才不依赖这种巧合。

M8 在完整测试里只被一个用例发现。哪天有人觉得“切换失败”这个用例难构造（它靠把 current 换成非空目录让 rename 失败）把它删了，这个变异就没人管了。这类“只有一条用例守着”的变异，值得在测试名或规格里标出来。

给 gate 自己做变异：第一次 G3 存活

检查工具本身也可能有缺陷，所以我对 gate.go 做了 6 个变异，用 gate_test.go 的 10 种情形（无改动、改规格、改测试文件、改代码、改代码导致测试失败、未提交的改动、只改 README、主分支前进、变基，以及后来补的一种）来判：

变异结果
G1 code 摘要不含合并基点发现（变基）
G2 merge-check 跳过树比较发现（7 种情形）
G3 tests 摘要不含 go test 结果第一次存活，补用例后发现
G4 不拒绝未提交的代码改动发现（未提交的改动）
G5 测试失败时仍允许批准发现
G6 不检查主分支是否为祖先发现（主分支前进）

第一次运行 G3 存活（results/mutation-run1-before-fix.txt）。原因是已有的 9 种情形里，测试结果变化总伴随着别的信号：要么测试文件内容变了，要么测试失败，check 本来就因为“测试未通过”判定失效。结果列表这一项在这些情形下是多余的。

它真正起作用的场景，是 test_cmd 跑的范围比 tests 列出的文件更宽：配置里测试文件只列了 promote/*_test.go，命令却是 go test ./...。在别的目录新增一个测试包，测试文件摘要不变，测试全过，只有逐用例结果多出一行。我把这个情形补进 gate_test.go 后，G3 被发现，6 个变异全部发现。全部测试（含 15 个变异）跑一遍约 12.5 秒。

这次存活让我改了一个看法：摘要范围和实际跑的测试范围不一致，本身就是一类漏洞。要么让 tests 的文件列表和 test_cmd 的包范围一致，要么像现在这样把执行结果也算进摘要。

这套检查管不到的地方

  • 摘要相同只说明范围内的内容没变，不说明代码对。上面 M8 那种只靠一条用例守着的情况，摘要帮不上忙。
  • --by reviewer-b 是自报的名字，.review/ 是本地文件，能写工作区的人都能改，也就谈不上防篡改。它也不随分支传给别人，多人或多机协作时要把批准放到服务端。
  • tests 摘要不含被测代码。只改代码、测试照样全过时，tests 保持有效，这次变化由 code 关卡负责。
  • 权限错误的用例靠 chmod 000 构造，用 root 跑时不成立；我只在普通用户下运行过。

服务端已经有现成的同类机制：GitHub 分支保护可以在推送新提交时让旧的 PR 批准失效，Merge Queue 在合入前用最新的目标分支重新跑必需检查，分别对应这里的 code 失效和 merge-check。Spec Kit 和 OpenSpec 管的是规格、计划、任务文件怎样组织，和批准之后内容有没有变是两件事，可以叠加使用；这两个工具我没有在本文的场景里实跑过。

在自己的流程里试的话，最省事的一步是：复核通过后故意改一行行为相关的代码，看现有工具会不会拒绝合并；再只改一个不在复核范围里的文件，看它是否仍然拒绝。前者测摘要，后者测树比较，本文的场景两种都覆盖了。
