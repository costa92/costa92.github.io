多个 Agent 接力开发，怎样让审核结论跟上代码变化

设想一次开发交接：实现 Agent 写完功能，另一个 Agent 复核后给出“通过”。准备合并时，实现者又补了一处错误处理，顺手调整了测试。代码已经变了，聊天记录里却仍然只有修改前的审核结论。

把整个功能重审一遍有成本，直接沿用旧结论又会漏过刚补的分支。接手的人需要知道：改动有没有影响已批准的设计，哪些测试需要重跑，复核者还要看哪些差异。

一个 Go 运维项目把这些要求写进了开发工具，让设计批准、测试记录和代码审核都对应到具体版本。以其中的恢复放行功能为例，可以看到这套流程怎样处理审核后的修改，又怎样检查最终要合并的代码。

先把“要做什么”和“现在做到了什么”分开

恢复放行处理从备份恢复出的副本：检查副本，确认旧实例停止，再把服务入口切过去（从备份恢复本身是另一个切片的事）。如果命令中途退出，下次执行还要能按原来的切换意图继续完成。

只在聊天里交代这些要求，换一个会话就可能换一种理解。“旧目录不可达”是指路径不存在，还是也包括权限错误？交付前只需跑通测试，还是必须在真实环境里验证重启？这些差别会直接影响实现和验收，需要有明确的文档供各个会话查阅。

项目把这些内容分别写在四类材料中：

材料保存什么使用时要注意
需求规格行为、边界、失败处理与验收条件写进规格的要求，还要检查代码是否实现
功能设计当前采用的流程、模块契约和测试安排设计要遵守需求，不能自行改动需求含义
本次任务记录范围、批准、复核、偏差和遗留问题长期采用的方案仍需写回设计文档
使用说明当前能运行的能力及验证程度未来规划要与已有能力区分

例如，“旧实例未停止时必须拒绝”属于需求；在哪里取锁、持有到什么时候，属于设计；测试或人工验收则记录实现是否在相应条件下做到了这些要求。

开发时，项目把一次任务称为一个“切片”。每个切片声明涉及的需求、允许修改的路径和对应设计文档，在独立分支与工作区中推进。如果实现者发现方案做不到，就要记录卡在哪里。若需要改变需求的含义，则交由用户裁决，后续实现按裁决继续。

设计复核先检查失败以后发生什么

恢复放行的正常路径并不复杂，难点在于操作可能只完成一半：入口已经切到新目录，最后的完成标记还没写入，进程就退出了。

项目的设计复核曾指出一个问题：从同一份备份恢复出副本 A 和 B，先对 A 放行，在入口切到 A 后中断。此时再对 B 发起放行，最初的设计可能把 A 当成普通旧目录，继续切到 B，而 A 的切换还没有完成。

修订后的设计会先检查原目录的切换意图和恢复状态。只要还有未完成的切换，就拒绝新的放行，要求先处理原来的操作。

要发现这个问题，复核者得知道入口何时改变、状态写在哪里、写入按什么顺序发生。因此，设计需要写清跨模块调用、持久写入、提交点和中断后的恢复方式，并安排对应测试。仅有一张从开始连到成功的流程图，看不出切换到 A 之后还留下了什么。

对有持久化或外部副作用的功能，可以沿着流程图的每个节点检查：此时哪些操作已经完成，下一步失败后，重试会从哪里继续。目录切换、重复通知和审批执行都值得这样分析；只改一行展示文案，就没有必要把整套恢复分析再做一遍。

复核通过，要记录通过的是哪一份内容

项目由实现者维护代码与设计，另一独立会话负责复核，集成者负责批准、推进任务状态和合并。主会话有时也写代码，这时仍需把复核交给另一会话。

批准和复核记录主要绑定三类内容摘要，用来检查审核后的变化（工具里还有代码冻结和验收用的摘要，这里不展开）。摘要类似文件指纹，不过三者计算的内容不同：

摘要计算范围用在什么地方
规格摘要本任务涉及的需求，以及按规则展开的登记项、裁决等检查批准时的要求是否变化
设计摘要设计中需要批准的部分区分方案变化与实现阶段的信息回填
交付摘要本任务代码改动与完整设计文档核对代码复核针对的是哪一份交付内容

例如，实现时会在设计文档里补上代码符号和测试列。设计摘要排除了这些回填字段，因此补全它们不会改变设计摘要；交付摘要包含完整设计文档，会把这些内容一起算进去。规格摘要也只按规定的范围展开，更深的间接依赖是否受影响，仍需复核者判断。

只有处于开发状态，才能修改切片范围内的代码。进入代码复核前，工具检查工作区、文档同步情况与测试证据，并记录交付摘要。独立复核通过后，再核对复核记录中的摘要与当前内容是否一致。

flowchart TD
    A[设计复核与批准] --> B[开发并提交代码]
    B --> C[检查与测试取证]
    C --> D[独立代码复核]
    D --> E{结论通过且摘要一致}
    E -->|是| F[进入待合并状态]
    E -->|否| G[修正或重新复核]
    G --> B

这张图展示处理顺序，返工时还要区分两种状态。复核不通过，可以直接退回开发；已经通过后再返工，要先退回设计阶段，再获准进入开发。即使规格和设计没变，也要走这一步；如果方案变了，还要重新完成相应的设计复核与批准。

回到开场的修改，假设恢复放行通过审核后，实现者又补了一个错误分支，并调整了测试。此时交付摘要变了，旧审核结论就不能用来让任务进入完成状态。任务要按上述返工步骤重新进入开发，验证修改，再请复核者检查相关差异。规格和设计没有变化时，已经成立的设计结论仍可保留。

摘要相同，只说明所计算的内容没变。代码是否正确，还得看复核和验证。即使换了独立会话，也可能沿用实现者的错误假设，所以复核记录要写清看了哪些内容、测试检查了哪些行为，让接手的人能判断是否有遗漏。

测试除了通过，还要能识别错误实现

每条验收条件都要有有效的测试或人工验收证据。采用人工验收时，需要记录结果和说明，并匹配相应验收条件的摘要。采用自动测试时，要把需求编号和验收序号写进测试名，工具再从运行事件中找出通过的用例。仅在注释里写了编号，或者测试已写好却没有执行，都不能算作自动测试覆盖。

把编号对上，还不够。假如恢复放行的测试只检查命令退出码，不检查失败前有没有改写旧目录，那么实现即使先写坏数据、再返回错误，也可能通过测试。

为此，设计阶段就要说明：实现出现哪种错误时，哪个测试应该失败。项目把这称为反向证据。恢复放行的既有代码复核记录里一共检查了 9 个变异，下面是其中 4 个：

人为引入的错误行为应当发现它的测试
取不到旧目录锁仍继续放行旧实例持锁时拒绝，并检查没有发生切换
把权限错误当作目录不存在原目录访问失败时拒绝
忽略副本的阻塞状态副本未通过检查时拒绝放行
原目录还有未完成的切换意图时仍然放行原目录有未完成意图时拒绝的检查，以及中断后补完的用例

按既有复核记录，这些变异都使相应测试失败。例如，持锁场景的用例确实能发现“取不到锁却继续放行”的错误。它检查的是这一行为；换成不同文件系统、真实后端或部署环境后是否仍按预期工作，还要在对应环境中验收。

合并前，检查真正准备进入主分支的内容

切片完成后，主分支可能已经前进。即使切片本身没有再改，把它与新的主分支组合起来，也可能得到一份没有审过、测过的代码。

项目的合并命令会在临时工作区生成 squash 候选提交，先核对候选与已审核的切片源提交是否具有相同的文件树，再检查候选是否满足交付要求。合并命令要求当前主分支是源提交的祖先，否则直接拒绝；快进之前还会再确认主分支没有变化。主分支前进后，切片要先变基到最新主分支，摘要因此变化的，退回重新批准，再尝试合并。

flowchart TD
    A[已审核的切片源提交] --> B[临时工作区生成候选]
    B --> C{候选文件树与源提交相同}
    C -->|否| X[停止合并并处理差异]
    C -->|是| D[核对证据与批准摘要]
    D --> E[检查当前主分支基线]
    E --> F[以快进方式合入]

候选需要重新检查，但测试不一定全部重跑。工具允许复用符合条件的成功测试记录：测试输入摘要、记录有效性、工具链环境和工作区状态都要通过核对。覆盖、文档同步和批准摘要等检查则重新计算。

审核记录也会随流程增加。为了避免每补一条记录就触发全量测试，测试缓存的输入排除了过程卡目录。这样做的前提是测试不读取过程卡作为实际输入；一旦新增这种依赖，缓存规则就要跟着修改。环境核对也受记录字段的限制，白名单以外的环境变化不会被自动发现。

合并前的主分支检查和 Git 快进合并可以发现常见的并发变化，操作者的身份则是另一个问题。摘要不能证明是谁审核或批准的，这套本地工具也没有提供身份认证或防范恶意篡改记录的安全隔离。由集成者执行合并、由独立会话复核，这些角色分工仍要靠协作纪律或额外的权限机制落实。

类似工具已经解决了哪些部分

GitHub Spec Kit 把规格、计划和任务分开，提供实现前的一致性检查，以及实现后的遗漏检查。用它组织好开发材料后，还需要检查：代码变化时，先前的审核是否会失效，合并时又是否核对了审核对应的版本。执行过开发步骤本身并不能保证这些约束成立。

OpenSpec 的自定义流程文档 列出了社区的 anvil schema，在设计后安排独立复核，再进入测试计划和实现。不过，文档在介绍 anvil 时也提醒：OpenSpec 只检查这些文件是否存在，并不会强制执行其中的审核结论。要在审核不通过时阻止后续操作，还需自行接入 CI 或 hook。

到了合并环节，GitHub 分支保护 可以让受变更影响的旧批准失效；Merge Queue 则把最新目标分支、队列中排在前面的变更一起纳入必需检查。多人协作时，可以评估如何将这些服务端检查与本地流程配合使用。

选工具时，不妨用开场那次修改逐步核对：补过代码后，工具是否拒绝旧批准；读取审核记录时，是否核对对应内容；到了合并环节，限制由本地工具还是服务端执行。这样更容易找到现有流程还缺哪一步。

复用时保留机制，把项目规则交给配置

如果把这套流程抽成模板，可以让模板负责状态推进、审核记录和验证命令的执行，把恢复目录、旧实例锁、放行状态等业务规则留在各项目中。各项目再提供自己的验证命令，按需求配置：

模板可以提供各项目需要确定
角色、任务状态、审核记录格式谁负责批准，哪些变化必须交用户裁决
版本与证据的关联方式哪些文件参与摘要，哪些依赖影响结论
验证命令执行及结果记录Go 测试、前端构建、接口测试或页面检查
失败后的退回与复核规则风险等级、必须验证的行为与允许的遗留项

摘要范围和缓存条件尤其需要重新检查。排除一个目录，可以减少重复执行，也可能漏掉测试或审核实际依赖的输入。设计模板时，可以要求项目说明每项排除的依据，以及依赖变化后怎样让旧记录失效。

采用这套流程也要付出维护成本：设计要随代码更新，独立复核者要理解上下文，检查工具自身也可能有缺陷。是否值得继续投入，可以看它发现了哪些行为问题、修过的问题是否复发，以及真实运行中的问题多久能反馈到开发中。单看审核轮次，无法知道这些工作是否有用。

任务开始时就应按风险确定检查要求。小改动可以保留明确范围、实际验证和独立检查；涉及持久化、授权或外部副作用时，再增加设计批准和失败恢复分析。检查失败后临时降低要求，会让原先约定的验收条件失去作用。

在自己的项目里尝试时，可以先记录一次审核的范围和对应版本，再有意修改一个影响行为的分支，检查旧批准是否仍能用于合并。如果还能通过，就沿这次交接查下去：是没有记录对应版本，修改后缺少验证，还是合并工具没有检查批准是否过期。
