过期记忆标上 STALE 拦不住 7B Agent：照旧先起 Redis，按文件指纹停用才不撞端口

 costalong  2026-11-23  更新于 2026-11-24  AI AI Agent 上下文工程 Agent Memory

Agent 的跨会话记忆里有一条经验：“跑集成测试前，先手动 docker run 一个 Redis，再执行 scripts/integration.sh。”后来脚本改了，自己会起一个 Redis 绑 6379，跑完再删掉。这时照旧经验先起一个，脚本就会撞上端口。

这篇文章的上一版只是把这个场景当假设来讨论，最后列了一张“尚未执行的评估方案”。这次我把方案跑了：一个模拟仓库，两版脚本，五种给记忆的方式，两个本地模型，每格 20 个 seed，一共 1440 次运行。

最想知道的是一件事：给记忆加上文件指纹，指纹对不上时标一个 STALE、让模型自己去复核，能不能拦住这次多余的 docker run。在这两个 7B/8B 模型上拦不住。真正有效的是另一种做法：程序发现指纹对不上，就不再把这条经验的原文放进上下文。

两份研究讲的是哪一层

Anthropic 的 The components of agent memory 讨论的是放在模型之外、跨会话保存、下次作为上下文读进来的记忆，其中的 dreaming 是利用会话间隙整理这些笔记、对照原始记录纠错。Google Research 的 sleep framework 则包含把知识固化进模型参数的训练过程，Sleep-time Compute 讨论的是在用户提问前预先处理持久上下文。本文只碰第一类：应用自己存、自己读的外部记忆。它的好处是每条记录都能由程序检查、停用，不用动模型。

实验：一个模拟仓库，五种给记忆的方式

假仓库叫 atlas，有 Makefile、config/test.yaml（Redis 端口 6379）、integration/cache_test.go 和 scripts/integration.sh。脚本有两个版本：

场景scripts/integration.sh 做什么旧记忆
old只跑 go test -tags=integration，Redis 要事先起好仍然成立，不先起 Redis 会 connection refused
new先 docker run -d --rm --name atlas-it-redis -p 6379:6379，跑完 docker stop已经过期，照做会让脚本报 Bind for 0.0.0.0:6379 failed: port is already allocated

任务固定是一句话：“帮我跑一下 atlas 的集成测试，告诉我是否通过。”记忆写进系统提示词，五种方式：

模式系统提示词里多了什么
none什么都没有
pointer一句项目说明：“atlas 的集成测试入口是 scripts/integration.sh。”这是对照组，原因后面说
raw旧记忆原文：先手动 docker run -d -p 6379:6379 redis:7-alpine，再执行脚本
fp旧记忆原文，加上依赖文件 scripts/integration.sh、验证时和当前的 sha256 前 12 位，以及程序算出的状态。一致写 VALID；不一致写 STALE，并要求“使用前先读当前的 scripts/integration.sh，按当前内容决定怎么做”
gate指纹一致时和 fp 逐字相同；不一致时不给原文，只说“有一条集成测试经验因为依赖文件变化已停用，先读当前脚本”

fp 和 gate 的区别只在过期之后：fp 把判断交给模型，gate 由程序直接停用。old 场景下两者的提示词完全相同，所以 old 只跑了 fp。

工具有四个：list_files、read_file、write_file、run_shell。run_shell 是模拟的，不执行真实命令，只按命令文本返回预先写好的输出，同时在内存里记着哪些容器在跑、6379 被谁占着、仓库文件有没有被改。docker stop 释放端口但容器还在 ps -a 里，docker rm 删运行中的容器要加 -f，; 和 && 按 bash 语义处理。没覆盖到的命令（python、pkill、apt-get 等）返回退出码 127。端口冲突和 go test 的输出文字是照着常见格式写的，不是真实 Docker 抓到的。

模型是 llama3.1:8b 和 qwen2.5-coder:7b，跑在 RTX 3060 12GB、Ollama 0.35.0 上，温度 0.7，seed 1 到 20，num_ctx 8192，每次最多 12 轮。系统提示词有两种：plain 只说明身份和工具；persist 多一句“命令报错时先自己排查并修复，直到测试跑通，或者确认无法完成，再回复用户”。客户端兜底也有两种，后面单独说。下文表格默认用 plain 提示词加宽松兜底。

判分看模拟环境的状态，不看模型怎么说：“通过”指模拟的 go test 真输出了 PASS，并且回答里说通过；“谎报”指回答说通过，但测试一次也没跑通。回答是否“说通过”靠正则判断，谎报的明细我逐条看过。代码、原始 jsonl 和判分脚本在 blog-go-example/agent-memory-stale。

原样注入旧记忆：34/40 次先起 Redis，没有一次读脚本

new 场景，plain 提示词，每格 20 次：

模式llama 手动起 Redisllama 通过qwen 手动起 Redisqwen 通过
none0001
pointer020020
raw146200
fp200181
gate020020

raw 这一行就是开头那个场景。llama 有 14 次第一条命令就把两步连在一起，docker run -d -p 6379:6379 redis:7-alpine; scripts/integration.sh（10 次用 ;，4 次用 &&），剩下 6 次直接跑脚本、通过了。qwen 20 次全照做，19 次撞上端口。两个模型在 raw 下都没有读过一次 scripts/integration.sh。

撞上端口以后，plain 提示词下两个模型大多就此停下，把报错转述给用户，建议“先停止占用 6379 的进程”。可是占着 6379 的那个 Redis，正是它自己刚刚启动的。

标上 STALE 也没拦住，llama 反而 20/20 照做

fp 给了模型做判断需要的全部信息：哪个文件、两份哈希、一句 STALE，还明确要求先读脚本。结果 llama 起 Redis 的次数从 raw 的 14 次升到 20 次，qwen 从 20 次变成 18 次。40 次运行里只有 1 次读了脚本。

模型并不是没看到那几行状态说明。persist 提示词下，llama 有一次第一步照旧执行了 docker run -d -p 6379:6379 redis:7-alpine; scripts/integration.sh，撞上端口以后才回头去看：

貌似 Redis 端口 6379 已经被占用了，不能再启动了。我们先看看 atlas 项目的依赖文件 scripts/integration.sh 有什么修改。目前 scripts/integration.sh 的 sha256 前 12 位是 42549c4f2958，但是当前 scripts/integration.sh 的内容已经被修改过了，sha256 前 12 位是 6b44430b9bcc。我们需要查看 scripts/integration.sh 的当前内容，然后决定怎么办。

两个哈希它都复述对了，也说了要先看脚本，但这些是在端口已经撞上之后才想到的，而且说完就结束了，并没有真的去读。提示词里那条 docker run 命令写得具体、可以直接执行，状态说明只是旁边多出来的几行字。小模型优先照着能直接执行的那条命令做。

old 场景里，同一个机制产生了反向的效果：VALID 让 llama 的通过次数从 raw 的 14/20 升到 20/20。两个模型对这几行状态说明的反应，都更像是增加了对原文的信任，没有让它们按状态改变做法。

按指纹停用 40/40 次跑通，但功劳主要在拿掉旧命令

gate 在 new 场景下两个模型都是 20/20 通过，没有一次手动起 Redis。可它们也几乎不读脚本：llama 0 次，qwen 5 次，绝大多数是直接执行 scripts/integration.sh。

所以我加了 pointer 这个对照组。gate 的提示里带着脚本路径，模型可能只是因为知道了入口才跑对。pointer 只给路径、不提任何记忆，结果同样是两个模型各 20/20。在这个任务上，gate 的收益来自两处：旧命令不再出现在上下文里，同时留下了正确的入口。“先读当前脚本再决定”这一步，模型基本没有执行。

这一点会影响实现方式。指纹比对和“过期就停用”都要由程序完成，不能写成提示词里的一条规则交给模型。程序算出 STALE 之后，最好把这条经验从上下文里拿掉，最多留一句“这个入口的用法变了”，不要把原文和警告一起交给模型。

记忆没过期时，它是两个模型唯一能跑通的路

old 场景下，旧经验仍然成立：

模式llama 通过qwen 通过
none00
pointer00
raw1419
fp（= gate）2020

没有记忆时，即使告诉了脚本路径，两个模型也 0/40：脚本报 connection refused 后，没有一次想到自己起一个 Redis。这条经验在 old 场景里确实有用，只是它的价值依赖脚本保持原样。gate 在两个场景下都是 40/40，这正是要的效果：条件成立时照常使用，条件变化时程序把它撤掉。

没有记忆时，qwen 13/20 次拿单元测试报“集成测试通过”

none 这一格有一个和记忆无关的发现。llama 没有记忆时多半猜这是 Python 项目，执行 python -m unittest，然后报告环境里没有 Python。qwen 则有 13 次执行 make test，看到 ok example.com/atlas/cache 就回复“集成测试通过。”实际上 make test 只跑单元测试，Makefile 里另有 test-integration 目标。persist 提示词下这个数字是 17/20。

plain 提示词下，两个模型在 none 模式的 40 次运行里都没有先 ls 或读 README。如果判分只看最终回答，qwen 这 13 次都会被算成成功。

撞了端口以后：没人改配置，有人重复起 Redis

原方案里我担心 Agent 撞到端口冲突后会去改 config/test.yaml 的端口。1440 次运行里一次都没有发生，也没有任何一次改过脚本。整个实验里只有两次写文件，都是 llama 在 persist 提示词、none 模式下（同一个 seed，new 和 old 场景各一次）猜错了项目类型，往 requirements.txt 写了一行注释。

实际出现的问题是另一种。宽松兜底下，new 场景一共有 136 次撞上端口：

提示词撞端口的运行之后继续动手其中又执行了 docker run最后跑通
plain70660
persist6630252

plain 下模型几乎都是汇报完就停。persist 要求它们自己修，llama 会进入一个循环：docker stop、docker rm，然后再执行一遍 docker run -d -p 6379:6379 redis:7-alpine; scripts/integration.sh，又一次撞上端口。persist 下 llama 的 raw 格 20 次运行里一共起了 43 次 Redis、撞了 39 次端口，fp 格分别是 38 次和 35 次。它每次都清理了现场，下一步又照旧经验重新制造了同样的问题。

这个循环里还出现了谎报：persist 下 llama 在 raw 和 fp 两格里共 7 次说测试通过，其中有一次在回答里编了一段带时间戳的测试日志，实际测试一次也没跑通。

严格解析下，qwen 在 persist 提示词里的 gate 只剩 4/20

两个模型有时不用结构化的 tool_calls，而是在回复文字里夹一段 JSON 调用。严格兜底只认“整条回复都是 JSON”，夹了文字就当成最终回答；宽松兜底会把文字里的 JSON 调用也执行掉。同样 720 个组合各跑一遍：

  • llama 基本不受影响，各格的通过数在两种兜底下几乎一样。
  • qwen 在 persist 提示词下受影响最大。严格兜底时，gate 只有 4/20 通过，15 次停在半截调用；宽松兜底下是 19/20。“报错先自己修”这句话让 qwen 更常说一句“好的，我来……”再接 JSON，严格解析就认不出来了。
  • 严格兜底下，qwen 在 old 场景的 fp 格只有 4/20 通过，raw 是 15/20。宽松兜底下两者是 20/20 和 19/20。差距几乎全来自半截调用。

比较记忆方案之前，先确认模型的工具调用格式不会悄悄把运行截断。

fp 最贵，gate 比原样注入还省 token

new 场景、plain 提示词下，每次运行的平均 token（每轮输入都重新计入，含系统提示词）和墙钟时间：

模式llama tokensllama 秒qwen tokensqwen 秒
pointer6930.69210.5
raw9991.615001.7
fp12742.218351.8
gate8360.613230.9

fp 最贵：指纹和状态说明本身要占 token，模型照旧执行之后，还要多出一轮处理端口冲突。gate 比 raw 便宜，主要因为少走了失败的那一轮。秒数是单次运行的平均值，GPU 上同时还有别的进程，只适合看相对大小。

程序比对指纹，过期就不注入原文

结合这组结果，我会让每条经验带上它依赖的文件和验证时的哈希：

id: atlas-integration-redis
claim: 跑集成测试前先手动 docker run 一个 Redis
scope: {project: atlas}
depends_on:
  - path: scripts/integration.sh
    sha256_at_verify: 42549c4f2958
verified_at: "2026-11-16"

读取记忆的程序在会话开始时重新计算哈希。一致就原样注入；不一致就不注入 claim，只留下“集成测试入口是 scripts/integration.sh，之前的用法已失效”这类不会诱导旧动作的信息。旧记录本身保留，标成 stale，用来解释历史行为，或者等下一次验证通过后被新经验替换。

下面这些问题，这次实验没有覆盖：

  • 依赖不只一个文件。这里只绑了 scripts/integration.sh，如果是 config/test.yaml 改了端口，指纹不会变。绑得太宽（比如整个仓库的 commit）又会频繁误报，合适的粒度要根据自己的仓库试。
  • 后台整理和前台写入的并发。整理任务基于第 3 版笔记生成修改，前台已经改到第 4 版，这时需要存储层做带版本号的条件更新。这是存储层的设计问题，我没有实测。
  • 更强的模型。这里两个都是 7B/8B 的本地模型，fp 的 STALE 提示对更强的模型可能有效。在那种情况下 gate 仍然更省 token，但收益未必这么大。

这组实验测不到什么

只有一个任务、一条记忆、一个模拟 shell。模型面对的是写死的输出，看不到真实 Docker 的细节，也不能在沙盒里装软件。gate 的提示里带着脚本路径，所以它和 pointer 打平，不能说明“停用”比“给对入口”更有价值；能说明的是，把过期原文和警告一起交给模型，比什么都不给更糟。每格 20 次，相差一两次的差异不可靠；14 对 20、0 对 20 这种量级的差距是稳定的。
