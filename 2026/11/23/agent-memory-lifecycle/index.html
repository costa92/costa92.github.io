Agent 记住的经验过期了怎么办：从近期记忆研究看验证与失效

假设一个编程 Agent 上周修好了项目的集成测试。它发现，当时应该启动测试用的 Redis，再执行测试命令，于是留下了一条记忆：“跑集成测试前，先启动 Redis。”

这周项目把测试环境迁到了临时容器，启动脚本已经负责准备依赖。Agent 接到一个新任务，读到旧记忆，又额外启动了一份 Redis。端口冲突后，它开始修改配置，试图修复一个由自己的经验制造出来的问题。

这条记忆留下了动作，却丢掉了动作成立的条件。它与新任务仍然相关，检索程序很容易找回它，却无法仅凭相关性判断今天是否还该执行。

2026 年 11 月 6 日，Anthropic 发布了 The components of agent memory。其中的 dreaming 指利用会话之间的时间整理外部记忆，并对照原始记录纠正笔记。本文沿着纠错的问题继续讨论：项目条件变了，应用怎样发现旧经验已经不适用，并停止沿用？

下文依据截至 2026 年 11 月 23 日可查的官方资料分析设计，不是模型效果实测。项目迁移案例、数据结构和验证方案均是本文提出的设计建议。

外部记忆与参数学习，修改的对象不同

最近两份研究都借用了睡眠的比喻，但修改的对象不同。

Anthropic 这篇讨论跨会话保存、以后作为上下文读取的外部记忆，不把修改模型权重算在这个定义里。Google Research 在 2026 年 10 月 27 日介绍的 sleep framework，则包含把信息固化到参数、更新数值权重的训练过程。两者不能因为都叫 dreaming，就当成同一种可直接接入应用的能力。

设计方向主要改变什么对应用开发者意味着什么
外部记忆整理笔记、索引、下次读取的内容可以在应用层记录来源、审阅差异、停用某条经验
参数层持续学习模型参数及其承载的知识需要相应训练机制与评估，不能用“保存一份 Markdown”替代

Sleep-time Compute 在 2025 年提出提前处理持久上下文，把部分计算放到用户提问之前，也提供了利用空闲时间处理信息的思路。不过，后台总结是否节省成本，仍取决于后续任务能否复用这些工作。

开场里的编程 Agent 需要查明测试经验的来源、检查适用条件，并能撤回错误条目。外部记忆允许应用逐条处理这些记录，无需更新模型参数，因此本文的方案从这里展开。

一条成功记录，怎样变成了一条错误规则

在项目 atlas 的旧测试配置下，首次执行集成测试失败。日志显示依赖连接失败；启动测试 Redis 后，同一组测试通过。

记录能说明的是，那次执行在补齐依赖后通过了测试。要把它用于下一次任务，还得确认环境和配置是否相同；仅凭这次成功，无法得出“所有集成测试都要手工启动 Redis”的规则。

总结器若将它压成“测试前先启动 Redis”，就会丢掉项目、版本、环境，以及失败到成功之间的执行过程。另一个 Agent 再把这句话搬进全局规则，原本只在旧配置下验证过的经验，就可能被用于其他环境。

记录时可以把观察、解释和经验分开，分别决定下次怎样使用：

内容在案例里是什么下次怎样使用
一次观察某次测试连接 Redis 失败定位历史事件，不直接指导当前操作
待验证解释可能缺少外部 Redis作为排查假设，继续检查当前配置
有条件的经验旧配置需要外部 Redis，且当时已验证条件仍成立时，才作为执行参考

即使模型给出“置信度 0.9”，读取方仍然不知道该检查什么。保留测试记录和依赖文件后，读取方才能核对证据。“已验证”也只对验证时的条件成立。

把验证时的条件存下来

为了在下次读取时核对条件，可以把这条经验存成下面的结构。这是本文设计的应用层数据示意，不对应某个 SDK 接口或官方统一格式。

id: atlas-integration-redis
revision: 3
scope:
  project: atlas
  environment: local-test
claim: 旧测试配置需要外部 Redis
status: verified
evidence:
  - run: test-run-017
    observation: 补齐依赖后，同一组集成测试通过
dependencies:
  - path: scripts/integration.sh
    fingerprint: recorded-at-verification
  - path: compose.test.yaml
    fingerprint: recorded-at-verification
verified_at: "2026-11-16"
on_dependency_change: mark_stale

fingerprint 的示意值在实现时要换成实际内容哈希或其他可比较的版本标识。读取记忆的程序负责计算并比较，不能让模型凭印象判断文件“应该没变”。

依赖范围越大，触发复核的次数就越多。如果绑定整个仓库的 commit，改一段无关文案也会让测试经验失效。可以先绑定直接相关的脚本和配置，发现漏记后再扩大范围。依赖关系还不清楚的小规模试点，则可以先绑定整个 commit，接受更多重复验证，以减少漏掉变化的机会。

测试脚本更新以后，旧记录可以进入 stale，表示“暂不能作为现行规则使用”。原始证据仍然保留，方便解释历史行为。新 Agent 读取当前脚本，发现容器已自动准备依赖，再生成新的候选经验。验证通过后，新条目替代旧条目。

过了一周并不能单独说明旧经验有误。时间戳可以触发复核，脚本和配置的变化则直接影响这个案例中的操作。不过，外部 API、权限、部署环境可能在本地文件不变时发生变化，还需要额外的版本检查或时效策略；文件哈希覆盖不了这些情况。

后台整理要能纠错，也要避免把猜测写成事实

LangChain 的记忆文档 区分了实时写入和后台整理：前者让新信息及时可用，但增加响应路径的工作；后者把整理移出主流程，却可能让其他会话暂时读不到最新信息。

在案例里，可以当场记下“哪条命令失败、后来做了什么、测试结果是什么”，把合并重复笔记、检查冲突等较重的工作放到后台。后台会同时读到不同阶段的记录，需要处理它们之间的差异。

比如，“启动 Redis 后测试通过”和“Redis 端口冲突”可能分别发生在迁移前后，不能简单合并成一条启动规则。可以让整理器输出变更提案，列出两次事件的条件差异和支持修改的证据，再决定是否更新现有结论。

如果现有记录不足以解释冲突，就保留两个事件，标记为 needs_review，等待补充证据。

提案生成期间，原笔记也可能变化。整理任务读取了第 3 版笔记，前台随后将它改到第 4 版；后台此时直接提交，就可能覆盖刚发生的纠正。提案应携带读取时的版本号，由存储层执行原子条件更新：只有当前版本仍与该版本号一致，才写入内容并递增版本。比较与写入不能分成两次独立操作，否则两者之间仍可能插入其他更新。版本不符时，整理器重新读取并生成差异；提示词可以帮助解释冲突，无法代替这项存储约束。

对于低风险的格式整理，可以自动合并；把一次失败推广成长期规则，则需要更强的证据。验证也要看动作本身：读取项目配置通常成本很低，启动服务、执行迁移或调用付费接口则应遵守原有执行权限。记忆维护不能额外获得这些权限。

找到相关记忆后，先判断它还能不能用

保存了条件和状态，还需要在读取时使用它们。否则，检索到的旧规则仍会原样进入上下文。读取流程可以按下面的顺序处理：

  1. 根据当前用户、项目和任务，限定允许读取的范围。
  2. 找出相关候选，过滤已经撤回或被替代的条目。
  3. 检查版本、依赖和时效；过期条目作为历史线索，不作为现行规则。
  4. 将少量可用经验及其条件交给模型，必要时再打开原始证据。

范围限制必须在检索和存储访问层落实。把其他项目或其他用户的内容先取出来，再要求模型“不要使用”，既浪费上下文，也无法形成可靠的访问边界。

对 atlas 项目，第三步应当发现脚本已经改变，让 Agent 先读取新配置，再决定是否启动 Redis。

Claude Code 的记忆文档 也明确区分了提供上下文的指令文件、自动记忆与强制执行的控制。在本文方案中，历史笔记即使写着“以后可以直接操作”，执行层仍须检查当前调用者权限和本次任务授权。外部文档里的操作建议，也不能经过一次总结就变成高优先级指令。

有些内容可以在读取时直接查询，无需维护一份记忆。例如，当前容器是否运行，查询环境比读取旧笔记更合适。项目为什么曾经选择某种测试方式，却未必能从当前配置中还原；如果没有决策记录，可以通过记忆保留当时的依据，减少后续重复调查。

用变化后的环境检验记忆

只让 Agent 回答“上周怎么修的”，测不出它能否停用旧经验。需要让测试脚本发生变化，再交给它一个新的集成测试任务，观察它是否仍会重复启动 Redis。

可以围绕这个案例准备一组小型回放任务，固定模型与工具条件，比较三种模式：不读跨会话记忆、直接注入历史摘要、读取带条件和失效状态的记忆。以下是尚未执行的评估方案：

回放条件应观察的行为
配置与上周一致是否复用经验，减少重复查找
脚本已负责启动依赖是否先确认新配置，避免重复启动 Redis
换成另一个项目是否避免套用 atlas 的专用经验
旧笔记与新测试结果冲突是否保留冲突并重新检查，而不是挑一句相信
新旧两个整理任务同时完成旧提案是否会覆盖较新的纠正
原始证据已不可访问是否停止声称“可以验证”，并按风险降级处理

Agent 可能先制造端口冲突，修复后仍然完成任务。因此，除了任务是否成功，还应记录过期记忆实际影响决策的次数、错误动作次数、额外读取和验证次数，以及端到端耗时。

计算总成本时，还要计入任务开始前的后台整理：

总成本 = 后台整理 + 记忆读取 + 条件复核 + 当前任务执行

只有复用节省的工作超过这些新增支出，记忆才在成本上划算。高度重复的项目任务可能适合整理经验；一次性问题、频繁变化且便宜可查的状态，未必值得预先维护。这个判断需要用自己的任务分布验证，不能从一篇研究里的收益直接换算。

落到自己的项目，可以先挑一条常用规则，补上来源、适用范围和一个明确的失效条件，再有意改变这个条件。对于本文的 Redis 案例，要观察的是：Agent 能否发现脚本变化，停用手工启动的旧规则，并根据新配置执行测试。
