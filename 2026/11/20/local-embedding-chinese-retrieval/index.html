nomic-embed-text 看不见 79% 的汉字

 costalong  2026-11-20  AI 本地大模型 RAG
本地大模型 RAG
AI
文章字数:   4.5k
阅读次数:  
   阅读模式

本地搭 RAG，nomic-embed-text 常被拿来做本地嵌入：Ollama 一条命令就能拉下来，274 MB。我手上的资料大半是中文，就想知道它对中文到底行不行。于是手写了一套小语料，同样的内容中英文各一份，用同一批问题去检索，比较排名。

结果差得比预想多：同一批问题，英文检索第一名命中 92.5%，中文只有 45%。原因不在模型「中文语义理解弱」这种模糊的层面，而在更底层的地方，它的词表里几乎没有汉字。

评测怎么搭的

语料和问题

语料是我自己写的 48 段技术短文，覆盖 Kubernetes（8 段）、Go（8）、Linux（8）、Docker（6）、网络（6）、Git（4）、数据库（4）、大模型（4）。每段一到两句话，中文平均 65 个字符，最长 103 个字符；然后我逐段写了对应的英文版，平均 29 个词。

同一主题下故意放了容易混的段落：存活探针、就绪探针、启动探针各一段；GOMEMLIMIT 和 GOGC 各一段；内核 OOM killer 和容器 OOMKilled 各一段。检索要分清这些，才算真的理解了问题。

问题 40 条，每条只标注 1 个正确段落，也是中英文各一份。问题尽量用使用者的说法，不抄段落里的关键词。比如正确段落写的是「存活探针连续失败……数据库一抖，所有 Pod 会一起重启」，问题写的是「为什么数据库抖一下，所有 Pod 都被重启了？」。

指标

每条问题对 48 段算余弦相似度，从高到低排序，记下正确段落的名次 r。

指标定义读法
recall@1r = 1 的问题占比只取第一名时答对的比例
recall@5r ≤ 5 的问题占比RAG 取前 5 段喂给模型时，正确段落在里面的比例
MRR1/r 的平均值第 1 名记 1，第 2 名记 0.5，第 10 名记 0.1，对排名靠前更敏感

因为每条问题只有一个正确段落，这里的 recall@k 就是常说的 hit@k。

几个需要先说清的局限：

  • 语料和问题都是我一个人写的，中英文也是我自己对照着写的，难免带着我的措辞习惯。英文版不是专业译文。
  • 48 段、40 条问题是很小的集合。recall@1 差 1 条问题就是 2.5 个百分点，几个点以内的差别不要当真。
  • 嵌入是确定性计算，同一输入重复调用向量不变，所以每个组合我只跑了一次，没有重复取平均。

环境

项目值
Ollama0.35.0，systemd 服务，调用 /api/embed
硬件RTX 3060 12 GiB，i7-14700KF，61 GiB 内存
模型nomic-embed-text:latest（GGUF 元数据里的名字是 nomic-embed-text-v1.5，F16，137M 参数，768 维）
对照模型bge-m3:latest（567M 参数，1024 维，F16，1.2 GB；测完已删除）

Ollama 返回的向量已经做过 L2 归一化（server/routes.go 的 embed 处理里有 normalize），所以余弦相似度直接用点积算。

语料、问题和评测脚本放在 blog-go-example/local-embedding-chinese-retrieval，可以照着 README 复现。

中文比英文低一半

不加任何前缀时，四种组合的结果：

查询 → 文档recall@1recall@5MRR
中文 → 中文0.4500.8000.563
英文 → 英文0.9251.0000.958
中文 → 英文0.3500.5750.467
英文 → 中文0.4000.5500.495

英文那一行几乎满分，40 条问题里 37 条第一名就对，前 5 名全部命中。说明问题和段落本身没有出错，同样的语义用英文表达，这个模型分得清。

中文这一行的 recall@5 是 0.8，看起来还能用，但 recall@1 只有 0.45。更说明问题的是最后两列：正确段落与问题的平均余弦是 0.700，而每条问题里「得分最高的错误段落」平均是 0.714。错误答案的分数平均比正确答案还高，排序几乎是在噪声里挑。英文这两个数是 0.715 和 0.609，中间有一段清楚的间隔。

词表里只有 244 个汉字

最先让我起疑的是两个相似度。我随手比了几对短语：

cos('存活探针失败', '就绪探针失败') = 1.000
cos('容器被杀掉', '镜像被删除') = 1.000
cos('磁盘满了', '内存满了') = 0.747
cos('磁盘满了', '天气很好') = 0.824
cos('the disk is full', 'the weather is nice') = 0.446

「存活探针失败」和「就绪探针失败」余弦 1.000，向量完全相同。「磁盘满了」和「天气很好」的相似度，比和「内存满了」还高。这不是语义理解弱能解释的，更像是这些字在模型眼里根本是同一个东西。

token 数也对得上这个猜测：「秋天」返回的 prompt_eval_count 是 4，「秋天的傍晚」是 7，正好是字数加 2（BERT 的开头和结尾标记），每个汉字一个 token。

于是我把语料和问题里出现过的 541 个不同汉字逐个送去嵌入，和一个生僻字「龘」的向量比较：

541 个汉字里有 470 个的向量和「龘」完全相同。按出现次数算，语料和问题里 78.8% 的汉字都变成了同一个 token。

为了确认这是词表本身的问题，而不是 Ollama 分词的实现问题，我用 gguf 这个 Python 包直接读了模型文件里的分词器元数据：

tokenizer.ggml.model = bert
general.name = nomic-embed-text-v1.5
nomic-bert.context_length = [2048]
词表大小 30522 ；其中单个汉字的 token 244
语料里 541 个不同汉字中，在词表里的 71 个

词表 30522 个 token，单个汉字只有 244 个。我的 541 个汉字里，71 个在词表中，正好就是上面那 71 个「能区分」的字，两种方法的结果完全吻合。「的」「一」「不」在词表里，「存」「活」「就」「绪」「容」「镜」都不在。30522 这个大小和 BERT 英文版词表一样，推测 nomic-embed-text 沿用了英文 BERT 的分词器，没有为中文扩充（我没有去核对它的训练代码，这一点是推测）。

这样再回头看中文 0.45 的 recall@1，就不奇怪它为什么不是 0 了：段落里的英文术语还在。我按问题里有没有英文字母把中文 → 中文的 40 条拆开：

中文问题条数recall@1recall@5MRR
含英文字母（如 Pod、Go、HTTP、reset –hard）180.6670.9440.762
纯中文220.2730.6820.401

纯中文问题第一名只对 27%。排名最差的几条全是纯中文：「怎么让服务崩溃后自动重启，又不会无限重启？」正确段落排到第 46 名（一共 48 段），第一名是启动探针那段；「改了配置，容器里的环境变量为什么还是旧的？」排第 35 名，第一名是多阶段构建。「怎」「么」「了」本身也是未知 token，推测模型实际上在用「不」「的」这类词表里有的常用字和标点去匹配。

前缀有一点用，但救不了中文

nomic-embed-text 的模型说明要求给查询加 search_query: 、给文档加 search_document: 前缀。我加上前缀重跑了一遍：

查询 → 文档recall@1 无前缀 → 有前缀recall@5MRR
中文 → 中文0.450 → 0.4750.800 → 0.7750.563 → 0.596
英文 → 英文0.925 → 0.9251.000 → 0.9750.958 → 0.948
中文 → 英文0.350 → 0.3000.575 → 0.5500.467 → 0.431
英文 → 中文0.400 → 0.3750.550 → 0.5250.495 → 0.458

所有变化都在 1 到 2 条问题以内，有升有降，在这个样本量下分不出好坏。英文本来就接近满分，没有提升空间；中文的瓶颈在词表，前缀改变不了「存」和「就」是同一个 token 这件事。

前缀还有一个容易忽略的成本：它本身占 token。48 段中文文档的 prompt_eval_count 合计从 2448 变成 2640，多了 192 个，正好每段 4 个。对 2048 token 上限的模型来说不算多，但长文档切块时要算进去。

跨语言检索比中文对中文还差

如果中文问题去检索英文文档呢？思路是：既然英文这么好，能不能把知识库翻成英文，问题保持中文？

结果是 recall@1 0.350，比中文对中文的 0.450 还低。推测原因和上面一样：中文问题这一端已经变成了大量相同的未知 token，再好的英文文档也接不住。反过来英文问题查中文文档是 0.400，瓶颈换到了文档一端。

所以「文档翻成英文」只有在问题也翻成英文时才有意义，那时实际上就变成了英文对英文。

长文档在 2048 token 处被截掉

第二个担心是长文档。nomic-embed-text 的 Modelfile 里写着 PARAMETER num_ctx 8192，但模型元数据里的上下文长度是 2048。Ollama 嵌入时取两者较小的那个，源码在 server/routes.go 的 embed 处理函数里：

ctxLen := int(m.metadata.Int("context_length"))
if opts.NumCtx > 0 {
    ctxLen = min(opts.NumCtx, ctxLen)
}

超出部分的处理和聊天接口不同。聊天接口截掉中间、保留结尾；嵌入接口是 tokens[:ctxLen]，保留开头、直接丢掉结尾。

我构造了一个测试：一句英文事实「The nightly backup job for the billing service runs at 03:17 and uploads its archives to the storage bucket named kestrel-archive.」，前面或后面拼上不同数量的填充句（用语料里其他英文段落循环拼接），问题是「When does the billing backup run, and which bucket does it upload to?」。

几个读数：

  • 问题和事实句本身的余弦是 0.778，和 40 句纯填充文字是 0.523，这是两个参照点。
  • 填充到 60 句以后，prompt_eval_count 停在 2048 不再增长。60、80、120、200 句的结果一字不差：事实在开头时余弦 0.640，在末尾时 0.528，后者和纯填充文字的 0.523 几乎一样，事实句已经被截掉了。
  • 默认请求返回 200，没有任何提示。加 "truncate": false 后，同样的输入返回 400：the input length exceeds the context length。
  • 同一时段的服务日志里没有 WARN。llama-server 每次请求都打一行 stop processing: n_tokens = 2048, truncated = 0，因为截断在 Ollama 这一层已经做完了，后端收到的输入本来就不超长。看到 truncated = 0 不能说明没被截。脚本按 truncat 或 WARN 统计到的 23 行，全是这种 slot release 行。

prompt_eval_count 能告诉你「到顶了」，但不会告诉你原文有多长。60 句的原文大约多长，我只能按 20 句 801 token、40 句 1564 token 的增量线性估，大约 2300 token 左右（估算，没有精确分词）。

还有一个比截断更早出现的效应。40 句填充时文档是 1564 token，没有被截断，但事实在末尾时余弦只有 0.544，在开头时是 0.635。我推测这和 nomic-bert 的平均池化有关：一句话的信息被 1500 多个 token 平均掉了，事实放在开头时略占优势的原因我没有深究。不管是哪种原因，在这组测试里，单个事实对整块向量的贡献很小，切块看起来比依赖长上下文更稳妥。

换成 bge-m3 之后

对照模型我选了 bge-m3，同样是 BERT 架构，但词表是为多语言训练的。同一套语料、同一批问题、同一个脚本，不加前缀：

查询 → 文档recall@1recall@5MRR正确段落平均余弦最高错误段落平均余弦
中文 → 中文0.9500.9750.9600.6990.604
英文 → 英文0.9000.9750.9350.6550.552
中文 → 英文0.8250.9750.9020.6180.553
英文 → 中文0.8750.9750.9180.6230.554

中文对中文从 0.450 到 0.950，跨语言从 0.350 到 0.825。正确段落和最高错误段落之间重新出现了间隔（单语约 0.1，跨语言约 0.07），和 nomic-embed-text 在英文上的表现差不多。英文对英文 0.900 比 nomic 的 0.925 低一条问题，在这个样本量下算持平。

按问题里有没有英文字母拆开，bge-m3 的纯中文问题 recall@1 是 0.955（22 条），含英文字母的是 0.944（18 条），两类没有差别了。排名最差的一条是「排空节点时卡住不动，一直在等什么？」，正确段落（PodDisruptionBudget）排第 12，第一名是数据库连接池那段，两段都在讲「等待」。这种错误至少是语义上能理解的。

之前那几对短语也换 bge-m3 算了一遍：

bge-m3 cos('存活探针失败', '就绪探针失败') = 0.836
bge-m3 cos('容器被杀掉', '镜像被删除') = 0.555
bge-m3 cos('磁盘满了', '内存满了') = 0.851
bge-m3 cos('磁盘满了', '天气很好') = 0.532

「磁盘满了」终于离「内存满了」比离「天气很好」更近。分词也不再是逐字：「秋天的傍晚」是 6 个 token（含首尾标记），比 nomic 少 1 个；48 段中文文档的 token 合计 2048，比 nomic 的 2448 少 16%。

代价在体积上。ollama list 里 bge-m3 是 1.2 GB（567M 参数，F16，1024 维），nomic-embed-text 是 274 MB。按默认参数加载后，ollama ps 显示 bge-m3 占 664 MB（CONTEXT 4096），nomic 占 323 MB（CONTEXT 2048），都在 GPU 上；后面把 bge-m3 的 num_ctx 提到 8192 时变成 940 MB。速度反而没拉开：48 段中文一次批量嵌入，nomic 三次分别是 366、238、193 ms，bge-m3 是 337、334、334 ms。每种各 3 次计时，GPU 上的批量很小，换成 CPU 或大批量结论可能不同。

8192 上下文，默认也只用 2048

bge-m3 的元数据里上下文长度是 8192，我本以为长文档问题就此解决。用同一个长文档脚本跑了一遍，prompt_eval_count 还是停在 2048，事实在末尾时余弦 0.537，和纯填充文字的 0.514 只差一点。区别在日志里，这次有错误了：

srv    send_error: task id = 792, error: input (2653 tokens) is too large to process. increase the physical batch size (current batch size: 2048)
...
srv    send_error: task id = 824, error: input (4096 tokens) is too large to process. increase the physical batch size (current batch size: 2048)

这几行对着源码能拼出完整过程。Ollama 默认 num_ctx 是 4096，先按 min(4096, 8192) 截到 4096 以内；llama-server 的物理批大小是 2048，按错误信息，超过批大小的输入不能做嵌入，于是拒绝；Ollama 收到 400 后并不报错，而是用 num_batch 再截一次重试：

truncated, ok, err := truncateInputToLimit(text, opts.NumBatch)

嵌入模型的 num_batch 默认值在 llm/llama_server.go 里写死为 DefaultEmbeddingNumBatch = 2048（请求和模型都没指定时生效）。所以不管模型声称多长的上下文，默认配置下实际生效的上限都是 2048 token，接口照样返回 200。

只在请求里加 "options": {"num_ctx": 8192} 不够，结果还是 2048；同时加 "num_batch": 8192 才真正吃进全文：

事实在末尾的长文档默认num_ctx 8192num_ctx 8192 + num_batch 8192
60 句填充2048 token，余弦 0.5372048，0.5372653 token，0.568
120 句填充2048 token，余弦 0.5372048，0.5375251 token，0.592

"truncate": false 在两种长度下都返回 400，和 nomic 一样，这是这次测过的选项里唯一能让超长输入显式失败的开关。即便吃进了全文，5251 token 里那一句事实对余弦的贡献也只把 0.537 推到 0.592，离事实句单独嵌入的 0.771 还很远，在这组测试里，切块对 bge-m3 看起来同样更稳妥。

这次的局限

  • 语料只有 48 段、40 条问题，全部出自我一人之手；领域集中在运维和后端开发。换成长篇、口语化或者专业领域的中文，数字会不一样。
  • 只比较了 nomic-embed-text 和 bge-m3 两个模型，没有测其他中文嵌入模型。
  • 长文档实验只用了英文填充文字和一个事实句，每个长度一次；速度只计了三次，都是单次运行的读数。
  • 「词表里只有 244 个汉字」是 Ollama 发布的这个 GGUF 文件的情况，我没有核对其他来源或其他格式的 nomic-embed-text 权重。

中文知识库选嵌入模型前的三个小测试

下面几个小测试一分钟就能跑完，换任何嵌入模型都可以先过一遍。

第一个是「生僻字测试」。拿语料里出现过的汉字逐个嵌入，和一个肯定不在词表里的字（我用的是「龘」）比较，向量完全相同的比例就是落进未知 token 的比例。nomic-embed-text 是 470/541。再加两三对「意思不同但字数相同」的短语，余弦接近 1 就该警惕。

第二个是看 prompt_eval_count。它比字数更直接地告诉你模型怎么切中文：每个汉字一个 token 说明词表没有中文词，同时它也是判断截断的唯一读数，等于 2048 这种整数时，多半是被截了。

第三个是在入库脚本里固定写 "truncate": false。默认的静默截断对检索的伤害是看不见的，宁可让超长的块报 400，再回去改切块大小；真的需要长上下文，就同时设 num_ctx 和 num_batch，并在日志里确认没有 too large to process。

至于 nomic-embed-text，它在英文上的成绩我没有任何意见，40 条问题 37 条第一名命中。只是在一个以中文为主的知识库里，它的大部分汉字是同一个 token，用上面的词表检查就能提前发现。
