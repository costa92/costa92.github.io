写新主机初始化脚本踩的坑：幂等、卸载与 SSH 防锁死

新买一台 Ubuntu 云主机，我要做的事情几乎每次都一样：装 Docker、配 swap、开 UFW、加固 SSH、起一个网关，再按需加 Redis、Postgres、VictoriaMetrics 这些组件。手敲两三次之后，我把它写成了 hostkit：一个纯 shell 的初始化工具，每个步骤一个文件，都提供 install / uninstall / purge 三种动作，用 make swap、make uninstall-ssh 这样的命令驱动。

从建仓到提交 af94e70 一共 40 个提交（含 GitHub 自动生成的初始提交和 1 个 merge），其中 12 个的标题带 fix 或”修复”。这篇不复述 README，只讲写这种脚本必须回答的几个问题，以及这个项目实际撞上的 bug。所有安装和卸载我都放在一次性的 systemd 容器里跑，没有碰宿主机。几个结论先放前面：

问题hostkit 的做法本机实测
重跑会不会乱重启写文件前先比较，内容不变就不重载docker + dockerconf 重跑 1.15 秒，Docker 启动时间不变；单独重跑 dockerconf 前后 dockerd PID 都是 5257
卸载会不会误伤/var/lib/hostkit 记录自己做过什么，首次修改前备份原文件卸载后 cmp 与安装前 daemon.json 一致
改 SSH 会不会锁死先放行端口再改、sshd -t 失败即回滚、兼容 socket 激活端口写成 70000 时配置被自动撤销，22 端口照常监听
Docker 网段撞内网按宿主机路由挑地址池容器 IP 在 172.17.0.0/16，脚本自动选了 10.200.0.0/16
网关 404return 404 + error_page，404 页标 internal；兜底路由的优先级显式写成数字旧配置对不存在的路径返回 200

重跑不重启：写文件前先比较

初始化脚本最常见的用法不是跑一次，而是改一行配置再跑一次。如果每次都无条件覆盖文件、重启服务，第二次运行就会把正在跑的容器全部打断。

hostkit 所有写配置的地方都走同一个函数，lib/common.sh:104-113：

# 内容不变返回 1，调用方据此决定是否重载服务
write_if_changed() {
  local dst=$1 mode=${2:-0644} tmp
  tmp=$(mktemp)
  cat >"$tmp"
  if [[ -f $dst ]] && cmp -s "$tmp" "$dst"; then rm -f "$tmp"; return 1; fi
  install -D -m "$mode" "$tmp" "$dst"
  rm -f "$tmp"
  log "已写入 $dst"
}

关键在返回值：有变化返回 0，没变化返回 1，调用方用 if write_if_changed ...; then systemctl restart ... 决定要不要重载。容器组件也一样，lib/components.sh:62-66 里 compose 文件、.env、渲染出的配置任意一个变了才加 --force-recreate，否则 docker compose up -d 什么也不做。

我在容器里连跑两次 dockerconf。第一次 daemon.json 从安装前的 {"debug": true} 改成合并后的内容，第二次什么都不改：

PID 和启动时间都没变，文件的修改时间还停在第一次写入的 05:52:16。更早还有一轮 docker 和 dockerconf 两步一起重跑，time 记下的是 1.154 秒，Docker 的启动时间前后都是 05:47:51；第一次装 Docker 是 3 分 54 秒。SSH 步骤同理，第二次运行输出 SSH 配置无变化，没有重启 ssh.socket。

也有不完全幂等的地方。UFW 步骤每次都会重新执行 ufw allow 和 ufw --force enable，第二次运行这一步花了 4 秒。ufw 遇到已存在的规则会跳过，结果应当一致（这次没有用 ufw status numbered 逐条核对），只是它没有做”先比较再动手”。写自己的脚本时，我的建议是把”结果一致”和”什么都不碰”分开对待：前者是底线，后者对会重启服务的步骤才是必须的。

还有一个细节值得抄：判断包是否已装，lib/common.sh:115-116 特意不用 dpkg -s：

# dpkg -s 对 remove 后残留配置（rc 状态）的包也返回 0，不能用
pkg_installed() { [[ $(dpkg-query -W -f='${db:Status-Status}' "$1" 2>/dev/null) == installed ]]; }

我在 ubuntu:24.04 容器里装上 ufw 再 apt remove，验证了这条注释：

$ dpkg -l ufw | tail -1
rc  ufw            0.36.2-6     all          program for managing a Netfilter firewall
$ dpkg -s ufw >/dev/null; echo $?
0
$ dpkg-query -W -f="${db:Status-Status}" ufw
config-files

包已经卸了，dpkg -s 仍然返回 0。用它判断”已安装就跳过”，被卸载过一次的主机就再也装不回来。

卸载只撤销自己做过的事

卸载比安装难。新主机上可能已经有云厂商建好的 swap、用户自己写的 daemon.json、早就启用的 UFW。卸载如果把这些一起删了，比不提供卸载更糟。

hostkit 的办法是在 /var/lib/hostkit 记账，lib/common.sh:40-67：

# 记录本脚本做过什么，卸载时只撤销自己的改动
STATE_DIR=/var/lib/$PROJECT
state_set() { install -d -m 0700 "$STATE_DIR"; printf '%s\n' "${2:-1}" >"$STATE_DIR/$1"; }
...
# 首次修改前保存原文件（或记下原本不存在），restore_backup 据此还原
backup_once() {
  local key="backup${1//\//_}"
  state_has "$key" && return 0
  install -d -m 0700 "$STATE_DIR"
  if [[ -e $1 ]]; then cp -a "$1" "$STATE_DIR/$key.orig"; state_set "$key" present
  else state_set "$key" absent
  fi
}

backup_once 的”once”很重要：只在第一次修改前备份，之后重跑不会把自己改过的版本当成”原始文件”覆盖掉备份。原文件不存在也要记下来（absent），否则卸载时不知道该删还是该留。

各步骤按同一个思路记账：swap 步骤只有自己创建了 /swapfile 才写 swapfile-created，卸载时没有这个标记就输出 swap 不是本脚本创建的，保留；docker 步骤没有 docker-installed 标记时拒绝卸载 Docker；UFW 记下安装前是否已启用。

改 SSH 时不把自己锁在外面

远程主机上改 SSH 是整个脚本风险最高的一步。hostkit 叠了四层保护。

第一层是顺序。install.sh:16 的注释写着”ufw 必须在 ssh 前：改端口时先放行新端口”，而 UFW 放行的端口来自配置的端口加上 sshd 当前实际在听的端口（steps/ufw.sh:7），所以即使 sshd 原本跑在非 22 端口，开防火墙时也不会漏掉。改端口时默认新旧端口同时监听：

$ SSH_PORT=2222 ./install.sh install ufw ssh   # 第 1 次
[05:43:49] UFW 已启用，放行 TCP: 2222 22 80 443
[WARN] Docker 发布的端口（-p）会绕过 UFW，只发布确实需要对外的端口
[05:43:49] 已写入 /etc/ssh/sshd_config.d/00-hostkit.conf
[05:43:50] SSH 已加固（端口: 2222 22，密码登录: yes）
[WARN] 仍同时监听 22；用新端口 2222 登录验证后，设 SSH_CLOSE_OLD_PORT=1 再跑 ssh 步骤

第二层是写完先校验，失败就撤销，steps/ssh.sh:45-48：

if ! sshd_check -t; then
  rm -f "$conf"
  die "sshd 配置校验失败，已撤销 $conf"
fi

我故意把端口写成 70000：

配置被删掉，ssh.socket 没有被重启，22 端口的 IPv4、IPv6 两个监听都还在。最后那行 步骤 [ssh] 失败 来自 install.sh 里的 EXIT trap，set -e 退出时默认什么都不说，这个 trap 补上了失败的步骤名。

第三层是 Ubuntu 22.10 之后的 socket 激活。新版本里监听 22 端口的是 systemd 的 ssh.socket，sshd 要等第一个连接进来才启动，/run/sshd 这个目录也是那时才创建。在刚开机、还没人连过的机器上直接跑 sshd -t，结果是这样的：

$ systemctl is-active ssh.socket ssh.service
active
inactive
$ ls -ld /run/sshd
ls: cannot access '/run/sshd': No such file or directory
$ sshd -t
Missing privilege separation directory: /run/sshd
exit=255

配置本身没问题，校验却失败。如果脚本照搬”校验失败就回滚”，在这种机器上永远改不了 SSH。hostkit 的处理是在调用前把目录建好，lib/common.sh:186-188：

# socket 激活模式下 /run/sshd 要等首个连接才创建，没有它 sshd -t/-T 直接失败
sshd_check() { install -d -m 0755 /run/sshd; sshd "$@"; }
current_ssh_ports() { sshd_check -T | awk '$1=="port" {print $2}'; }

生效方式也不同：socket 激活时端口由 systemd generator 从 sshd_config 生成，要 daemon-reload 再重启 ssh.socket，systemctl reload ssh 不会让新端口生效（steps/ssh.sh:5-12）。改端口后看监听进程，22 和 2222 都是 systemd,pid=1，说明新端口确实是 socket 在听：

$ ss -ltnp
LISTEN 0      4096         0.0.0.0:22        0.0.0.0:*    users:(("systemd",pid=1,fd=45))
LISTEN 0      4096         0.0.0.0:2222      0.0.0.0:*    users:(("systemd",pid=1,fd=48))

第四层是密码登录。只有 root 或 SUDO_USER 的 authorized_keys 里有可用公钥，才关闭 PasswordAuthentication。我的测试容器里没放公钥，所以输出是 保留密码登录。顺带一个小瑕疵：以 root 直接运行时 SUDO_USER 为空，这条警告显示成 root 没有可用的 authorized_keys，中间多了一个空格，不影响逻辑。配置文件名用 00- 前缀，是因为 sshd 对同一选项取第一次出现的值，要排在云镜像自带的 50-cloud-init.conf 前面；写完后脚本还会用 sshd -T 读实际生效值，被别的文件覆盖时给出警告。

Docker 地址池要避开宿主机的路由

Docker 默认从 172.17.0.0/16 起分配网段。云主机的 VPC 如果恰好在 172.16.0.0/12 里，或者机器要通过专线访问 10.x 的内网，新建的 compose 网络就可能和真实路由重叠，表现是容器里访问某些内网地址不通，很难第一时间想到是网段冲突。

hostkit 的做法是先收集宿主机已用的网段，排除 Docker 自己的接口，lib/common.sh:178-184：

# 宿主机已占用的网段（排除 docker 自身接口）
host_cidrs() {
  ip -4 -o route show table all 2>/dev/null \
    | awk '$1 ~ /\// && $0 !~ / dev (docker[0-9]*|br-[0-9a-f]+|veth[^ ]*) / {print $1}'
  ip -4 -o addr show 2>/dev/null \
    | awk '$2 !~ /^(docker[0-9]*|br-[0-9a-f]+|veth.*)$/ {print $4}'
}

再在三个候选（172.17.0.0/16 10.200.0.0/16 192.168.128.0/18）里用 Python 的 ipaddress.overlaps 挑第一个不冲突的，用户还可以用 AVOID_CIDRS 补充路由表里看不到的网段（比如对端 VPN 的网段）。

测试容器正好提供了一个真实场景：它跑在宿主机默认 bridge 上，eth0 是 172.17.0.3/16，也就是第一个候选已经被占：

$ ip -4 -o addr show eth0
2: eth0    inet 172.17.0.3/16 brd 172.17.255.255 scope global eth0
...
[05:47:49] Docker 地址池: 10.200.0.0/16
...
$ docker network create t1 && docker network inspect -f '{{range .IPAM.Config}}{{.Subnet}}{{end}}' t1
10.200.1.0/24
$ ip -4 -o addr show docker0
docker0 10.200.0.1/24

脚本跳过了 172.17.0.0/16，docker0 和新网络都落在 10.200.0.0/16 里。另一个值得注意的选择在 steps/dockerconf.sh:65-66：daemon.json 里已经有 default-address-pools 就不再改。已有的网络不会因为地址池变了而迁移，重跑时换池只会造成新旧网络不一致。重跑 dockerconf 时输出里没有”Docker 地址池”这一行，就是走了这个分支。

make uninstall swap 实际会做什么

这个坑和 shell 无关，是 make 的语义。用户很自然地会敲 make uninstall swap，意思是”卸载 swap”。但对 make 来说这是两个目标：uninstall（STEPS 默认是 all）和 swap（安装 swap）。我把 Makefile 拷出来，删掉保护块，用 make -n 只打印不执行：

--- 去掉保护后: make -n uninstall swap
sudo ./install.sh uninstall all 
sudo ./install.sh install swap
exit=0

先卸载全部组件，再装一遍 swap。如果加了 CONFIRM=yes，这一下就把整台机器的 Docker 和组件都卸掉了。hostkit 在 Makefile:9-14 里直接拒绝这种组合：

# `make uninstall swap` 会被 make 拆成「卸载全部」+「安装 swap」，直接拒绝
ifneq ($(filter uninstall purge,$(MAKECMDGOALS)),)
ifneq ($(filter install stage1 stage2 stage3 $(STEP_NAMES),$(MAKECMDGOALS)),)
$(error 卸载/清除指定步骤请用 STEPS="swap ssh" 或 uninstall-<步骤>/purge-<步骤>)
endif
endif

当前版本的实际效果：

$ make -n uninstall swap
Makefile:12: *** 卸载/清除指定步骤请用 STEPS="swap ssh" 或 uninstall-<步骤>/purge-<步骤>。 停止。
$ make -n uninstall-swap
sudo ./install.sh uninstall swap
$ make -n uninstall STEPS=swap
sudo ./install.sh uninstall swap

用 make 包装破坏性命令时，MAKECMDGOALS 检查值得每个项目都加上。

自定义 404 的三个坑：状态码、自动路由、优先级

网关这一层在 git 历史里改得最密：先在 nginx 上给未匹配的路由返回自定义 404，再整体换成 Traefik，404 页面也换了好几种实现。其中三个问题值得单独拿出来，前两个我做了复现，写网关配置时很容易再踩一遍。

第一个是状态码。f0bdafc 里 error-pages 的配置是：

location / {
    try_files $uri $uri.html /404.html =404;
}

我用同一个 nginx:1.30.7-alpine 镜像分别加载这一版和 e07ffc3 修复后的版本：

== old.conf
GET /nope -> 200
GET /404.html -> 200
<h1>页面不存在</h1>
== new.conf
GET /nope -> 404
GET /404.html -> 404
<h1>页面不存在</h1>

页面内容一样，状态码差别很大。try_files 回落到一个存在的 URI 时，是一次内部跳转去正常服务那个文件，状态码就是 200；只有最后一个参数写成 =404 才会返回 404。浏览器里看不出区别，搜索引擎和监控会把所有不存在的路径当成正常页面。修复版改成 return 404 加 error_page 404 /404.html，并把 /404.html 标成 internal。

第二个是 Traefik 的 Docker provider。f0bdafc 给 error-pages 容器加了 traefik.enable=true 和服务端口 label，本意只是让 Traefik 知道这个服务。我起了一个 Traefik 3.7.19（用 constraints 只让它看到实验容器），给一个容器加同样的两个 label，查 API：

{"entryPoints":["web"],"service":"error-pages","rule":"Host(`hk-ep`)","priority":13,...,"name":"hk-ep@docker","provider":"docker"}
  HTTP/1.1 200 OK
  HTTP/1.1 404 Not Found

Traefik 按默认规则 Host(容器名) 给它自动建了一条路由，带 Host: hk-ep 请求就能直接访问到这个容器。53cc3fd 的修复是去掉 label，在 file provider 里声明一个静态服务 http://error-pages:80，这样它只作为中间件的后端存在，不会自己长出路由。Traefik 文档里对这个行为的描述是 defaultRule，只要容器被 enable 又没有显式写 router，就会套用它。

再往后我干脆把辅助容器删了，改成 Traefik 本地插件直接写 404：一个 PathPrefix(/)、优先级 1 的兜底路由，挂上插件中间件，后端只是一个指向 http://127.0.0.1:9 的占位服务 dummy-404，请求在中间件这一层就被写回 404。

第三个问题出在优先级上。demo 测试页的路由也是 PathPrefix(/)，没有限定 Host，优先级又比兜底路由高，结果所有没匹配上的路径都被 demo 接走，自定义 404 根本轮不到。5407096 的做法是把优先级写成表：兜底 404 是 1，SITES 的 main 站点 2，demo 3，内置服务站点 4，容器名:端口站点和根路径跳转 1000，组件路径路由用 Traefik 默认的规则长度。Traefik 默认按规则字符串长度排优先级，PathPrefix(/) 这种短规则之间谁先谁后不直观，显式写数字比靠长度推算可靠。

同一个提交还暴露了另一件事：切到 Traefik 后，nginx 和 tls 步骤已经不在步骤表里，但 otel、alert 两个步骤还在调用 tls_on，证书监控就这样静默失效了。测试脚本当时把 steps/*.sh 全部 source 进来，函数都在，所以没报错。改完后测试只加载步骤表里的步骤，和 install.sh 一致。回头看，网关这一层换方案的成本远高于 swap、SSH 这些步骤：它同时牵动配置渲染、状态输出、监控和测试。

被删掉的 bind mount 目录

最后一个坑出现在 nginx 时代的证书清除逻辑里（这部分代码已随 nginx 在 5407096 删除，但坑对任何挂载证书目录的容器都成立），提交 d2a5b31 的说明写得很清楚：certbot 的证书目录是运行中 nginx 容器的 bind mount，purge-tls 用 rm -rf 删掉目录、重签时再建一个同名目录，容器里看不到新证书，nginx -t 报找不到证书。

我用一个临时目录复现：

$ rm -rf conf && mkdir conf && echo new > conf/fullchain.pem   # 旧版 purge-tls + 重签
$ docker exec hk-bind ls -la /etc/letsencrypt
total 0
--- 只清空内容（d2a5b31 的做法）
new

bind mount 绑定的是挂载那一刻的目录 inode，不是路径。目录被删后容器手里拿着的是一个已删除的空目录，宿主机上同名的新目录与它无关。

修复分两步：d2a5b31 把删除改成 find "$d" -mindepth 1 -maxdepth 1 -exec rm -rf -- {} +，只清空内容；07171ae 再加一个自愈检查，签发后在容器里 test -s 证书文件，看不到就 --force-recreate 重建容器，这样已经被旧版本弄坏的主机 git pull 后重跑一次 make tls 就能恢复。lib/common.sh 里的 safe_rm_dir 对挂载点也做了同样处理：mountpoint -q 为真时只清空内容。

写自己的初始化脚本时可以照抄的清单

按这次实测的结果整理：

  1. 所有配置写入都经过一个”比较后再写”的函数，用返回值决定是否重载服务；重跑一次，确认服务 PID 不变。
  2. 判断包是否已安装用 dpkg-query -W -f='${db:Status-Status}'，等于 installed 才算，不要用 dpkg -s。
  3. 首次修改前备份原文件，原本不存在也要记录；状态放在固定目录，卸载只按记录撤销。卸载后用 cmp 验证。
  4. 先放行防火墙端口再改 SSH，新旧端口并行一段时间；写完 sshd -t，失败就删掉自己的配置。
  5. 兼容 socket 激活：调用 sshd -t/-T 前 install -d /run/sshd，生效用 daemon-reload + 重启 ssh.socket。
  6. Docker 地址池按 ip route show table all 挑不冲突的网段，已配置过就别改。
  7. make 包装的卸载命令检查 MAKECMDGOALS，拒绝 make uninstall <步骤> 这种会被拆成两个目标的写法。
  8. 自定义错误页先用 curl 看状态码；Traefik 里只做后端的容器不要 enable，放到 file provider 的静态服务里。
  9. 运行中容器的 bind mount 目录只清空内容，不要删掉重建。
  10. 换掉大组件时，测试要和生产按同一张步骤表加载，不然删掉的组件还会在测试里”活着”，掩盖真实调用关系。
