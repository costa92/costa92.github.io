Ollama 静默截断长提示词：上下文 4096 时，4184 token 只剩 2050

 costalong  2026-11-20  AI 本地大模型 AI 工程实践

阅读次数:

给本地模型塞一份长资料再提问，回答文不对题，我第一反应是模型太小。这次在 Ollama 0.35.0 上把这件事拆开测了一遍，原因不在模型，在 Ollama 替你做的截断。几个结论先放前面：

  • 截断不是「超多少砍多少」。上下文 4096 时，3998 token 的提示词原样送进模型，4184 token 的提示词只剩 2050。公式在源码里：limit = num_ctx - (num_ctx - num_keep) / 2，和 num_predict 无关。
  • 砍的是中间，保留开头 4 个 token 和结尾。任务说明写在开头时 qwen2.5-coder:7b 6 次全错，写在末尾 6 次全对；把 num_keep 设成 64，开头的说明也能保住。
  • 多轮对话还有第二层截断：放不下时整条旧消息被扔掉，服务端日志里一行 WARN 都没有。
  • /api/chat、/api/generate、/v1/chat/completions 截得一模一样，响应里唯一的线索是输入 token 数。OpenAI 兼容接口在请求里改不了上下文，只能靠 Modelfile 或环境变量。
  • 上下文从 4096 加到 32768，7b 模型多占 1.6 GiB 显存，生成速度基本不变；llama3.1:8b 开到 32768 就放不下显存，生成速度从 61 token/s 掉到 24。

起因：温度实验里的一个异常

这个问题是我测本地模型温度时顺手撞上的。当时构造了一个 9051 token 的提示词：开头一句要求写 checksum_v7(data: bytes)，返回字节和模 251，后面接 300 行变更日志当参考资料。默认上下文下模型回了一段占位注释，日志里有一条 WARN：

当时我猜「只留一半，另一半给生成预留」，没有去源码里确认。这篇把当时没弄清的几件事补齐：limit 到底怎么算、和 num_predict 有没有关系、换接口会不会不一样、上下文在哪里设才生效、设大了要付出什么。

测试环境

项目值
GPURTX 3060 12 GiB，测量时桌面程序约占 4.1 GiB，留给模型约 7.4 GiB
Ollama0.35.0，systemd 服务，后端是它自带的 llama-server
模型qwen2.5-coder:7b（主力）、llama3.1:8b（测显存溢出），放在机械硬盘上

采样温度 0，num_predict 128，其他参数默认

提示词沿用温度实验的结构：任务说明一句，加 N 行形如 - release 1.2.3: fixed a minor issue in module util_123 ... 的变更日志，最后一句「只回代码」。改变行数就能得到不同长度：105 行是 3006 token，170 行 5021，300 行 9051，663 行 20304。判断对错不看字面，我把模型返回的函数拿出来，在子进程里跑两个断言。

脚本、原始输出和日志都留在实验目录里，下面贴出的数字都是从那里抄的。每个组合大多只跑了 1 次；温度 0 下同一输入的输出在这几轮里没有变过，但这仍然是小样本。

实验脚本放在 blog-go-example/ollama-context-truncation，可以照着 README 复现。

一过线就砍掉一半

先把 4 种提示词长度和 4 种上下文排列组合跑了一遍。默认上下文和显式写 num_ctx=4096 的结果完全相同，表里合成一列：

表里是响应中的 prompt_eval_count，也就是模型真正读到的 token 数。被截断的格子里，函数全部写错或者干脆没写。

最反直觉的是 4096 那一列。我又在 4000 附近补了两个点：137 行的提示词是 3998 token，原样送进模型，答对；143 行是 4184 token，只多了 186 个，送进模型的却只有 2050，答错。超出 88 个 token，结果丢掉了 2134 个。

把这些点画到一张图上，每个上下文都是一条「先沿对角线走，到 num_ctx−1 处直接跳水」的折线：

这意味着一个很实际的坑：如果你的提示词长度在上下文附近浮动，有时候它完整进去，有时候只剩一半，两次请求的回答质量会差得很远，而你看到的只是「模型时好时坏」。

源码里的公式：limit 和 num_predict 无关

日志里那条 WARN 来自 llm/llama_server.go 第 320 行。我把 v0.35.0 这个 tag 克隆下来，截断逻辑在 completionPromptForRequest 里，关键几行是：

fullPromptLimit := s.options.NumCtx - 1
if len(tokens) <= fullPromptLimit {
    return prompt, nil
}
// ...
nKeep := req.Options.NumKeep
// ...
limit := contextShiftPromptLimit(s.options.NumCtx, nKeep)
discard := len(tokens) - limit
truncated = append(truncated, tokens[:nKeep]...)
truncated = append(truncated, tokens[nKeep+discard:]...)

contextShiftPromptLimit 在第 324 到 333 行：

// Match the old runners' first context shift: preserve num_keep, then free
// roughly half of the remaining context before generation needs the slot.
return numCtx - max((numCtx-numKeep)/2, 1)

代入默认值：4096 − (4096 − 4) / 2 = 2050，8192 时是 4098，2048 时是 1026，和实测完全对上。同目录的 llama_server_test.go 第 139 行还有一个测试用例，名字就叫 issue 16618 context preserves generation headroom，期望值正是 2050。所以「留一半给生成」这个猜测方向是对的，但它是一个固定比例，而不是按 num_predict 算出来的预留。

为什么是一半？函数上方的注释说，这是在模仿旧版 runner 第一次做「上下文平移」（context shift）时的行为。llama.cpp 的上下文平移是这样工作的：生成过程中窗口写满了，就保留开头 n_keep 个 token，把剩下部分的前一半扔掉，腾出空间继续生成。Ollama 在提示词进门时就提前做了一次同样的操作，所以结果是开头一小段加后一半。我的理解是：这样做保证了生成刚开始时窗口里还有大约一半的空位，不会一开口就触发平移；代价是提示词只要超出一点点，就要丢掉一半（这是我读代码后的推测，没有找到官方文档专门解释这个取舍）。

保留结尾而不是开头，对聊天场景是合理的：最新的那条用户消息总在最后。问题在于很多人写长提示词的习惯正好相反，先写「请帮我做 X」，再贴资料。

num_keep 的默认值 4 写在 api/types.go 第 1130 行的 DefaultOptions() 里。Ollama 启动 llama-server 时，命令行里也能看到 --context-shift --keep 4。代码里还有一段：如果分词器会自动加 BOS，keep 再加 1。qwen2.5-coder 的日志里 keep 一直是 4，说明它不走这条分支。

为了确认和 num_predict 无关，我固定上下文 4096、提示词 9051 token，把 num_predict 分别设成 16、1024 和 −1（不限）。三次的 WARN 一字不差，都是 limit=2050 prompt=9051 keep=4 new=2050。

再往上追一层：这段截断只有在两个开关都是默认值时才会发生。请求里的 truncate 默认为真；shift（上下文平移）默认也为真，server/sched.go 第 134 行起只对 deepseek2 系列默认关掉。这两个开关后面还会用到。

砍掉的是中间：任务说明写在哪里决定生死

截断保留的是开头 num_keep 个 token 和结尾的 limit − num_keep 个，中间整段扔掉。下面这张示意图画的是 9051 token 的提示词在默认上下文下丢了 7001 个：

4 个 token 能装下什么？经过聊天模板渲染后，提示词最前面是 <|im_start|>system 这样的模板标记，接着才是 system 提示词和用户消息。4 个 token 连 system 提示词都装不下，更别说后面的任务说明。

于是我把同一句任务说明分别放在变更日志前面和后面，默认上下文、温度 0，9051 和 20304 token 两种长度各跑 3 次：

位置9051 token20304 token
任务在开头0/30/3
任务在末尾3/33/3

任务在开头时，模型 6 次都回了类似这样的东西：

# This is a placeholder for the actual code that would be executed based on the provided text.
# The text describes a series of releases where each release fixes a minor issue in a module named 'util_XXX' and updates the documentation for a helper named 'helper_XXX'.

它只看到了一堆变更日志，就照着变更日志的内容去「写代码」。任务在末尾时 6 次都是同一段正确的 return sum(data) % 251。温度 0 下，4 组里有 3 组的三次输出逐字相同，另一组（9051 token、任务在开头）出现了两种措辞，但都是占位注释。所以这里的「3 次」更接近确认可复现，而不是 3 个独立样本。

但「任务放末尾」只能保住任务本身，保不住资料。我又让问题放在末尾，分别问变更日志里第 4 行和第 299 行的内容，提示词都是 9030 token 左右：

问题默认上下文num_ctx=16384
release 1.0.3 修了哪个模块（第 4 行）module_03（编的）util_3
release 1.29.8 修了哪个模块（第 299 行）util_298未测

第 4 行早就被截掉了，模型没有说「找不到」，而是编了一个看起来很像的名字。这类错误比占位注释更难发现。每格只跑了 1 次，我只把它当作一个演示：截断之后，模型对被删掉的那部分内容没有任何感知。

num_keep 能把开头钉住

既然 num_keep 决定开头保留多少，那就把它设大到能盖住任务说明。我先测了一个零行变更日志的提示词，模板、system 和任务说明加起来一共 71 token，任务说明在其中靠前的位置。然后在 9051 token 的提示词上加 num_keep：

num_ctxnum_keep送进模型结果
40964（默认）2050写错
4096642080写对
40961002098写对
81921004146写对

limit 也跟着公式变了：4096 − (4096 − 64) / 2 = 2080。代价是中间被丢掉的资料多了几十个 token，但任务说明和 system 提示词都留住了。

num_keep 数的是渲染后提示词的 token，包括模板标记和 system 提示词，不是用户消息本身。设多大要按自己的提示词量一下：用一个空资料的请求看 prompt_eval_count，再留点余量。这个参数不解决资料丢失，只保证「我要你做什么」这句话不丢。

多轮对话还有一层更安静的截断

上面说的是单条提示词太长。多轮对话走的是另一段代码：server/prompt.go 的 chatPrompt，它在拼提示词之前就会从最早的消息开始整条丢弃，直到放得下为止，只保证 system 消息和最后一条消息还在。丢消息时打的是 Debug 级别日志（第 77 行），默认的 INFO 级别下看不到。

我造了一个两轮对话：第一轮用户消息里定规则「函数名都加 cv_ 前缀」，后面跟 100 行变更日志，助手回「OK」；第二轮再给 70 行变更日志，要求写求字节和模 251 的函数。总长约 4822 token。

上下文 4096 时，prompt_eval_count 只有 2002：第一轮的用户消息和助手的「OK」整条没了，模型写出 sum_of_bytes_mod_251，规则被忘掉。换成 8192，4822 个 token 全部进去，函数名变成 cv_checksum。我又去服务端日志里数了这段时间的 truncating，结果是 0。

这比单条截断更麻烦。单条截断至少还有一条 WARN 可以 grep；整条丢消息时，日志、响应状态、done_reason 都和正常请求一样。做聊天类应用时，如果用户说「你忘了我一开始说的」，先去看 prompt_eval_count 有没有掉下来。

三个接口截得一样，只有 token 数能看出来

同一个 9051 token 的提示词，默认上下文，分别走三个接口：

接口输入 token 字段值结束原因
/api/chatprompt_eval_count2050done_reason: stop
/api/generate（system + prompt）prompt_eval_count2050done_reason: stop
/v1/chat/completionsusage.prompt_tokens2050finish_reason: stop

三次的 WARN 都是 limit=2050 prompt=9051，三次都回了同样的占位注释。响应里没有任何「已截断」字段，结束原因也是正常的 stop。唯一能看出问题的，是输入 token 数比你预期的少了一大截。

OpenAI 兼容接口还有一个额外的限制：请求里改不了上下文。我试了两种写法，在 body 里加 "options": {"num_ctx": 16384}，以及在顶层加 "num_ctx": 16384，usage.prompt_tokens 都还是 2050。翻 openai/openai.go 第 711 到 752 行，兼容层只把 stop、max_tokens、temperature、seed、两个 penalty 和 top_p 翻译成 Ollama 的 options，没有 num_ctx 这一项。用 OpenAI SDK、各种「兼容 OpenAI」的客户端连 Ollama 时，上下文长度只能在服务端定。

不想被静默截断，可以让它直接报错

前面提到的两个开关，在原生接口里可以显式关掉。同样是 4096 上下文、9051 token：

  • 请求里加 "shift": false，返回 HTTP 400：the prompt is longer than the context length currently available to the model; shorten the prompt, adjust the context length in settings, or use a model with a longer context length。
  • 请求里加 "truncate": false，同样 400，错误体来自 llama-server：request (9051 tokens) exceeds the available context size (4096 tokens), try increasing it，还带着 n_prompt_tokens 和 n_ctx 两个数字。

两种我都只在 /api/chat 上测了。对批处理、RAG 这类「宁可失败也不要静默变差」的场景，我更愿意加上 truncate: false，失败了再决定是切块还是加大上下文。

三种设置方式，请求优先

上下文可以在三个地方设：请求的 options.num_ctx、Modelfile 里的 PARAMETER num_ctx、服务端环境变量 OLLAMA_CONTEXT_LENGTH。为了不动正在跑的 systemd 服务，我另起了一个临时实例来测环境变量：

OLLAMA_HOST=127.0.0.1:11435 OLLAMA_MODELS=/path/to/models OLLAMA_NOPRUNE=1 \
  OLLAMA_CONTEXT_LENGTH=8192 ollama serve

OLLAMA_NOPRUNE=1 是为了避免第二个实例启动时清理共用的模型目录。Modelfile 则建了一个临时模型：

FROM qwen2.5-coder:7b
PARAMETER num_ctx 16384

同一个 9051 token 的提示词，结果如下（ollama ps 的 CONTEXT 列和送进模型的 token 数一致）：

优先级是：请求 > Modelfile > 环境变量 > 按显存给的默认值。源码里也是这个顺序，server/routes.go 第 126 到 150 行先取 DefaultOptions()（其中 NumCtx 来自环境变量，为 0 时用显存档位的默认值），再依次用模型自带的默认参数、Modelfile 参数、请求参数覆盖。

显存档位在同一个文件第 2199 到 2209 行：总显存不少于 47 GiB 默认 262144，不少于 23 GiB 默认 32768，其余 4096。我这张 12 GiB 的卡（日志里是 total_vram="11.6 GiB"）落在最低档。有个容易误导的细节：临时实例设了 OLLAMA_CONTEXT_LENGTH=8192，启动日志里仍然打印 vram-based default context ... default_num_ctx=4096，实际生效的却是 8192。看日志判断上下文时，要看加载模型时 llama-server 命令行里的 -c 参数，或者 ollama ps 的 CONTEXT 列。

对 OpenAI 兼容客户端来说，能用的只有后两种：给模型做一个 Modelfile 变体，或者改服务端环境变量。前者只影响这一个模型名，后者影响所有没在 Modelfile 里写死上下文的模型。

上下文开大的代价

最后看看把 num_ctx 开大要付出什么。每个上下文先卸载模型再重新加载，用 nvidia-smi 每秒采样显存，同时记录 llama-server 启动时打印的显存分项。速度用 3018 token（llama3.1 分词后为 2807）的提示词测预填充、用一段约 400 token 的生成测输出，各跑 2 次：

num_ctxollama ps显存分项（MiB）nvidia-smi 峰值预填充 token/s生成 token/s
40964.7 GB，100% GPU4528（KV 224）88422245 / 222966.8 / 66.9
81925.1 GB，100% GPU4896（KV 448）92202266 / 218566.3 / 66.2
163845.5 GB，100% GPU5212（KV 896）95252207 / 215665.7 / 66.1
327686.4 GB，100% GPU6124（KV 1792）104382194 / 220266.5 / 63.4

nvidia-smi 峰值包含桌面程序常驻的约 4.1 GiB。KV 缓存严格按上下文线性增长，每 1024 个位置 56 MiB；权重始终是 4168 MiB。只要还在显存里，上下文开大几乎不影响速度。32768 时再塞一个 20316 token 的真实长提示词，预填充降到 1655 token/s，生成 55 token/s（只生成了 27 个 token，这个数参考价值有限）。

我还试了 num_ctx=65536，日志里出现 requested context size too large for model num_ctx=65536 n_ctx_train=32768，ollama ps 显示的上下文是 32768。超过模型训练长度的请求会被压回去，这一次至少有 WARN。

qwen2.5-coder:7b 开到 32768 也放得下，没能看到溢出。于是换 llama3.1:8b 再测，它的 KV 缓存每个位置的占用是 qwen 7b 的两倍多：

num_ctxollama psGPU 上的层预填充 token/s生成 token/s
81925.8 GB，100% GPU33/331972 / 200060.5 / 62.0
327689.5 GB，32%/68% CPU/GPU23/331347 / 129824.0 / 24.6
6553614 GB，54%/46% CPU/GPU15/331016 / 102310.4 / 17.4

日志里能看到 llama-server 的估算：32768 时需要 8639 MiB，可用只有 7275 MiB，于是把 10 层放到了 CPU。生成速度掉到原来的四成；65536 时两次测量差距很大（10.4 和 17.4），我没有追原因，推测和系统内存紧张、换页有关，这台机器测试时可用内存只有 14 GiB 左右，交换分区几乎用满。

所以在 12 GiB 的卡上，上下文不是越大越好。合适的做法是按实际最长的提示词再加生成长度来定，然后用 ollama ps 确认 PROCESSOR 列还是 100% GPU。

这组实验的局限

  • 主要只测了 qwen2.5-coder:7b 一个模型。截断公式在 Ollama 代码里，与模型无关；但截断后模型怎么反应（写占位注释、编模块名）是这个模型的表现，换模型可能不同。
  • 判对错的任务极简单，每个组合只有 1 到 3 次。它能说明「任务说明被截掉就做不对」，不能说明截断对一般任务的平均影响有多大。
  • truncate、shift 两个开关只在 /api/chat 上测过；num_keep 只测了请求参数，没有测写进 Modelfile。
  • 只测了 Ollama 0.35.0 在 CUDA 上走自带 llama-server 的这条路径。测试用例名里引用了 issue 16618，推测这段逻辑近期改过，其他版本的数字可能不同，升级后值得用同样的方法复测一次。

我现在的做法

  • 塞长资料前先估长度。中文、代码、日志的 token 密度差别很大，不要凭字数猜。最省事的办法是发一次请求看 prompt_eval_count。
  • 每个请求都核对 prompt_eval_count（或 usage.prompt_tokens）。它明显小于预期，就是被截了，这是响应里唯一的信号。
  • 批处理和 RAG 里加 "truncate": false，让超长请求直接 400，而不是返回一个看起来正常的错答案。
  • 必须容忍截断时，把任务说明放在末尾，或者把 num_keep 设到能盖住 system 提示词和任务说明。
  • 走 OpenAI 兼容接口的客户端，用 Modelfile 做一个写死 num_ctx 的模型变体，别指望请求参数。
  • 多轮对话自己管理历史长度，别把「保留旧消息」交给 Ollama，它丢消息时连 WARN 都不打。
  • 上下文按需开，开完看一眼 ollama ps 的 PROCESSOR 列。一旦出现 CPU，生成速度可能只剩一半不到。
