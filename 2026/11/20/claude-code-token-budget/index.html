Claude Code 无头调用的 token 账：首轮 45k 从哪来

 costalong  2026-11-20  更新于 2026-11-24  Coding-Agent Claude Code MCP AI 工程实践

用 claude -p 在脚本里跑小任务时，一个只回答 “OK” 的调用，在我平时的配置下按标价估算要 $0.269。上一篇让 Claude Code 排查 K8s 故障里顺手测过一次：在已有 --setting-sources project 的基础上再加 --strict-mcp-config，两轮对话的缓存读写合计从约 25.6k 降到约 10.4k。这次我想把这笔账拆细：一次无头调用的 token 到底花在哪几块上，哪些开关真能省钱，哪些其实没用。

我在本机前后跑了 54 次 claude -p，按估算价合计花了 $2.70。我平时的配置下，一句 “Reply with exactly: OK” 的首轮上下文是 45096 token，关掉用户级设置、MCP 和内置工具后只剩 3035。但上下文大小本身不是最贵的部分，贵的是缓存写入：Claude Code 按 1 小时 TTL 写缓存，单价是普通输入的 2 倍，而命中缓存的读取只要输入价的 5%。同一份 1.1 万 token 的上下文，命中时一次 $0.0023，改了 CLAUDE.md 里一行再跑是 $0.072，差 31 倍。

环境和测量方法

项目值
Claude Code2.1.329，默认模型 claude-opus-5-5
登录方式订阅账号 OAuth（apiKeySource: none）
输出格式--output-format stream-json --verbose
宿主机Ubuntu，命令都在本机执行

调用时直接执行 claude 二进制，只传 HOME、PATH、LANG、TERM、USER 五个环境变量，避免当前 shell 里的变量混进子进程。

每次调用的 stream-json 里，assistant 消息带着这一次请求的 usage，最后的 result 消息带 total_cost_usd 和按模型汇总的 modelUsage。我把一次请求的”上下文”定义为三项之和：

context = input_tokens + cache_creation_input_tokens + cache_read_input_tokens

total_cost_usd 在订阅登录下是 Claude Code 按标价算出来的估算值，不是真扣款。我用第一次探测调用核对了它的算法，Opus 5.5 的标价是输入 $4、输出 $20 每百万 token，缓存读取 $0.20：

req1: input=2 cache_create=2384 (5m=0,1h=2384) cache_read=649 output=4 context=3035
result: turns=1 cost=$0.0192898 is_error=False text='OK'

2×4 + 2384×8 + 649×0.2 + 4×20 = 19289.8，单位是百万分之一美元，正好是 $0.0192898。缓存写入按 $8 算，也就是 1 小时 TTL 的 2 倍价（usage.cache_creation 里也写明全部是 ephemeral_1h_input_tokens）。后面所有的费用都可以用这个公式复算。

为了看清每一块的成本，我写了三个小东西：一个不依赖任何库的 stdio MCP 服务器 tinyops（10 个运维类工具，描述照真实工具的长度写，tools/list 返回 5393 字节）；一个生成 CLAUDE.md 的脚本，内容是一个虚构的 Go 订单服务 orderhub 的约定、目录、错误码和模块说明；还有一个包装脚本，负责跑一次调用、按请求去重 usage、记账。保存原始输出时，我把初始化消息里不属于这次实验的 MCP、技能、插件名字都替换成了计数。

这几个脚本和虚构项目放在 blog-go-example/claude-code-token-budget，可以照着 README 复现。

一句 OK 的首轮上下文：从 3035 到 45096

先看同一个提示词在不同配置下的首轮上下文。除了最后两行，都加了 --setting-sources project --strict-mcp-config。

配置首轮上下文（token）
--tools ""，不加载任何内置工具3035
--tools Read4126
--tools "Bash,Read,Edit,Write"6308
默认内置工具（24 个）18531
默认内置工具，工作目录换到 home 下21806
不限制设置来源，只加 --strict-mcp-config39994
我平时的完整配置45096

我平时的配置是：12 个 MCP 服务器共 81 个工具、18 个插件、254 个技能、77 个 agent、6 个 SessionStart hook。完整配置第一次跑花了 $0.269，紧接着再跑一次全部命中缓存，只要 $0.0091。

把这些差值叠起来，45096 大致分成这几块：

  • 系统提示词和必需部分：3035。
  • 24 个内置工具的定义：15496，是单项最大的一块。
  • 工作目录在 home 下时加载的用户级 CLAUDE.md：3275（下面单独说为什么要强调”在 home 下”）。
  • 用户级设置带进来的技能、插件、agent 和 hook：18188。
  • 12 个 MCP 服务器：5102。

18188 这块我没有逐项拆。下文测到一个项目级技能只占 58 token，按这个量级估算，254 个技能大约 1.5 万，和这块的大小对得上，但这只是推测。

内置工具占得最多，按需裁剪最直接

24 个内置工具一共 15496 token，平均每个 600 多。--tools 只留 Read 时首轮是 4126，留 Bash,Read,Edit,Write 四个是 6308。脚本任务通常只用得到两三个工具，用 --tools 显式列出来，首轮能少一万多 token。

注意 --tools 和 --allowedTools 不是一回事：--allowedTools 管的是哪些调用不用询问，属于权限；上面这些数字变化都来自 --tools，它决定哪些工具出现在上下文里。

MCP 工具：有 ToolSearch 时只占一个名字

MCP 的结果和我预想的不一样。我用 tinyops 分别暴露 1、3、10 个工具：

配置10 个 MCP 工具带来的增量
--tools ""，MCP 工具全量加载+2336
--tools Read，没有 ToolSearch+1957
--tools "Read,ToolSearch"+766
默认内置工具（含 ToolSearch）+151

--tools "" 下 1 个、3 个、10 个工具的首轮分别是 3724、4096、5371。可一旦内置工具里有 ToolSearch，10 个 MCP 工具只多了 151 token：初始化消息里 10 个工具照样列出来，但从 token 数看，完整的定义没有进上下文，我的理解是模型需要时先用 ToolSearch 搜出定义再调用。--tools "Read,ToolSearch" 的 +766 里，推测大部分是 ToolSearch 这个工具自身的定义，我没有单独测不带 MCP 时它占多少。

这也解释了为什么我平时 81 个 MCP 工具只占 5102 token。反过来有一个坑：如果为了省 token 用 --tools 只留了几个内置工具，又没把 ToolSearch 列进去，MCP 工具会退回全量加载。我的 10 个工具只有 2 千多 token，换成几十个描述很长的工具就不是小数目了。

CLAUDE.md：每行约 29 token，中文比英文贵 11%

CLAUDE.md 这组实验一开始全部白跑了。我把 50、200、800 行的 CLAUDE.md 依次放进工作目录，首轮上下文纹丝不动，都是 3035。问模型”上下文里有没有项目 CLAUDE.md”，回答是 NONE。

原因在工作目录：我把实验目录放在了会话的临时目录下，路径在 /tmp/claude-<uid>/ 里面。上一篇的 K8s 实验也遇到过，把工作目录移到 $HOME/.cache 下面以后才加载。为什么这个目录会被跳过我没有查到文档，推测是 Claude Code 不读它自己临时目录里的 CLAUDE.md。换到 /home/user/.cache/cc-tokens-proj 后，同样的问题模型直接引用出了第三行。

换目录后又发现第二件事：没放项目 CLAUDE.md 时，首轮也从 3035 变成了 6311。多出来的是我的用户级 ~/.claude/CLAUDE.md（连同它引用的文件约 7.6KB）。也就是说 --setting-sources project 只限制 settings 文件，不会挡住用户级 CLAUDE.md；--safe-mode 能挡住，同样条件下首轮是 2344。

在 home 下的目录里，项目 CLAUDE.md 的边际成本如下（--tools ""，以 6311 为基线）：

文件行数字符数增加的 token
中文5024911424
中文20076125007
中文8003359323498
中文，模块说明部分20085466156
英文，同样的模块说明200155935526

800 行的 CLAUDE.md 每行约 29.4 token，单这一项就比 24 个内置工具还大。按 Opus 5.5 的价格，第一次写缓存要 $0.188，之后每次命中读取约 $0.0047。

最后两行是同一份内容的中英文版本。中文每个字符约 0.72 token，英文约 0.35 token，中文字符数少一半，token 反而多 11%。11% 不算大，我不会为了它把 CLAUDE.md 改成英文，删掉 200 行用不上的内容效果大得多。

技能和 agent：只占一行描述

在 home 下另一个目录里，我加了一个项目级技能 deploy-check（SKILL.md 7521 字节，正文 60 步）和一个 agent pg-reviewer（5531 字节）。基线是 21806，加了技能后 21864，再加 agent 后 21931。一个技能 +58，一个 agent +67，进上下文的只有 front-matter 里的名字和描述，正文要等调用时才读。

所以单个技能、agent 写多长都无所谓，真正累积起来的是数量：上面那一万八千多 token，推测主要就是几百个技能和 agent 的描述叠出来的。

缓存：命中便宜 31 倍，改一行就重写整块

接下来看缓存。工作目录里放 200 行中文 CLAUDE.md，--tools ""，依次做四件事：原样再跑一次，改最后一行，改第三行，再原样跑一次。下面是从保存的 stream-json 里重新打印的摘要：

== g1_same_again  duration_ms=2593
req1: input=2 cache_create=0 (5m=0,1h=0) cache_read=11288 output=4 context=11290
result: turns=1 cost=$0.0023455999999999998 is_error=False text='OK'
== g2_edit_last_line  duration_ms=3291
req1: input=2 cache_create=8963 (5m=0,1h=8963) cache_read=2386 output=4 context=11351
result: turns=2 cost=$0.1442944 is_error=False text='OK'
== g3_edit_line3  duration_ms=1773
req1: input=2 cache_create=8935 (5m=0,1h=8935) cache_read=2386 output=4 context=11323
result: turns=1 cost=$0.0720452 is_error=False text='OK'
== g4_again_after_edit  duration_ms=2471
req1: input=2 cache_create=0 (5m=0,1h=0) cache_read=11321 output=4 context=11323
result: turns=1 cost=$0.0023522 is_error=False text='OK'

缓存是按前缀匹配的。这四次里，前 2386 token（系统提示词）一直命中；CLAUDE.md 不管改第 3 行还是第 200 行，后面约 8.9k token 都要重新写入。命中时 $0.0023，重写时 $0.072，差 31 倍。

g2 的费用还翻了一倍，因为这一次模型第一次回复没有可见文字，Claude Code 自动追加了一条 [Your previous response had no visible output. Please continue and produce a user-visible response.]，又发了一次请求，而第二次请求也重新写了一遍缓存。这个现象在 54 次调用里出现了两次，都是 200 行中文 CLAUDE.md 的场景，原因我没有查清。

缓存能活多久也测了一下。10 个 MCP 工具那次调用跑完 8 到 9 分钟后，用同样的参数再跑，5369 token 全部命中，只花 $0.0012。这和 1 小时 TTL 的写入记录一致，超过 5 分钟的间隔也能吃到缓存。代价是写入单价是输入价的 2 倍，按官方文档的算法，1 小时 TTL 下同一个前缀至少要用 3 次才比不缓存便宜。

还有一个开关我以为有用，实测没效果：--exclude-dynamic-system-prompt-sections。帮助里说它把工作目录、git 状态这类每台机器不同的段落从系统提示词挪到第一条用户消息里，提升跨用户的缓存复用。我用两个不同的空目录 A、B 先后跑，不加这个参数时 B 能复用 17622 token、新写 4182；加了以后 B 复用 17375、新写还是 4182。在这个版本的 -p 模式下，目录相关的内容看起来本来就排在可共享的前缀之后。

多步任务：钱主要花在写缓存上

一次调用里如果有工具调用，就会发多次请求。我在 src/ 下放了 5 个 Go 文件（合计 10380 字节），让它逐个 Read，最后列出每个文件的导出函数：

== k_agentic  wall=17.7s rc=0
init: tools=2 mcp_servers=0 slash_commands=55 skills=19 agents=6 plugins=4 model=claude-opus-5-5
req1: input=2 cache_create=2509 (5m=0,1h=2509) cache_read=1947 output=8 context=4458
req2: input=2 cache_create=118 (5m=0,1h=118) cache_read=4456 output=16 context=4576
req3: input=2 cache_create=1269 (5m=0,1h=1269) cache_read=4574 output=16 context=5845
req4: input=2 cache_create=1284 (5m=0,1h=1284) cache_read=5843 output=16 context=7129
req5: input=2 cache_create=1299 (5m=0,1h=1299) cache_read=7127 output=16 context=8428
req6: input=2 cache_create=1330 (5m=0,1h=1330) cache_read=8426 output=59 context=9758
req7: input=2 cache_create=1346 (5m=0,1h=1346) cache_read=9756 output=367 context=11104
result: turns=7 cost=$0.1038018 is_error=False text='5 个文件已按顺序逐个读完。...'
  modelUsage claude-opus-5-5: in=14 out=1104 cr=42129 cc=9155 cost=0.1038018

每一次请求都把前面的全部内容重发一遍，前缀命中缓存，只有新读进来的文件内容（每个约 1.3k token）写入缓存。7 次请求累计计费的输入是 51298 token，而最后的上下文只有 11104。

按单价拆开这 $0.1038：缓存写入 9155 × $8 = $0.0732，占 70.5%；输出 1104 × $20 = $0.0221，占 21.3%；缓存读取 42129 × $0.2 = $0.0084，只占 8.1%。累计读了 4 万多 token，却是最便宜的一项。同样的任务在缓存已热的情况下又跑了 4 次（本来是想换参数，结果是我的 zsh 循环没把参数拆开），费用在 $0.0831 到 $0.0839 之间，很稳定。

多轮对话也是同一个规律。我在一个进程里通过 --input-format stream-json 一轮一轮地发 6 个问题（要等上一轮的 result 回来再发下一条；一次性把 4 条消息全塞进 stdin，后 3 条会被合并成一轮）：

轮次问题本轮费用
1读 order.go$0.0231
2再读 payment.go$0.0189
3再读 inventory.go$0.0191
4CancelOrder 的超时是多少$0.0036
5validateOrder 检查了什么$0.0041
6合成三行清单$0.0074

第 4 到 6 轮的上下文已经有 8500 token，比第 1 轮大一倍，费用却只有前三轮的约六分之一到五分之二。决定单轮费用的是这一轮新进来多少内容（要写缓存）和输出多少，而不是上下文总长度，前提是前缀一直命中。

换模型、降 effort、限轮数

还是读 5 个文件那个任务，每种配置各跑一次。只有默认 Opus 那次是冷缓存；--effort low 和 --max-turns 3 是在它之后跑的，读到了前面留下的缓存，所以要拿它们和缓存已热时的 $0.0831～$0.0839 比：

配置费用耗时结果
Opus 5.5（默认）$0.103816.9s正确
--model sonnet（claude-sonnet-5-5）$0.051011.0s正确
--model haiku（claude-haiku-5-5）$0.00319.3s正确
--effort low$0.087617.2s正确
--max-turns 3$0.02016.2serror_max_turns，没有结果

Haiku 5.5 的标价是每百万 token 输入 $0.10、输出 $0.50，按这个价算出来正好是 $0.0031，只有冷启动那次 Opus 的 3%。5 个文件的 20 个函数一个不差，后面还多补了一句观察：”每个文件里的 4 个函数函数体完全相同”，Get、Cancel、List 并没有做名字说的事。Haiku 的首轮上下文是 5210，比 Opus 的 4458 多 17%，可能是分词更碎，也可能是系统提示词或工具集不同，这次没有拆开看；但单价低得多，完全抵消。这种读文件、提取字段的活，用小模型足够。

--effort low 在这个任务上基本没有省钱：输出 1139 token，和默认的 1104 差不多；$0.0876 比冷启动的 $0.1038 低，但比缓存已热时的 $0.083 左右还略高。任务太简单，本来就没多少思考可省，effort 的效果要在更难的任务上才看得出来。

--max-turns 3 是个负面例子。它在第 4 轮被截停，result 为空，errors 是 Reached maximum number of turns (3)，已经花掉的 $0.0201 什么也没换来。把它当成本上限用不合适，它只是让失控的循环少烧一点。帮助里另有一个 --max-budget-usd，我这次没测。

意外和坑

  • 工作目录在 /tmp/claude-<uid>/ 下面时，项目级 CLAUDE.md 不加载；加了 --setting-sources project 时用户级的也没进上下文，换到 home 下才正常（上一篇用默认设置来源在同一类目录里跑，用户级的是加载了的）。在 CI 或脚本里拿临时目录做工作目录时，最好先问一句模型确认 CLAUDE.md 进没进上下文。
  • --setting-sources project 挡不住 ~/.claude/CLAUDE.md，我的用户级指令照样进了每一次无头调用；要完全隔离得用 --safe-mode。
  • 用 --tools 精简内置工具时漏掉 ToolSearch，MCP 工具会从”只占名字”变回全量加载。
  • 模型偶尔第一次回复没有可见文字，Claude Code 会自动补一次请求，那一次调用费用翻倍。
  • 往 --input-format stream-json 的 stdin 一次塞多条消息，排队的消息会被合并成一轮，想测逐轮成本必须等上一轮 result 回来再发。

落到脚本里

根据这些数字，我给自己的脚本定了几条规矩：

  1. 无头调用一律加 --strict-mcp-config，需要哪个 MCP 用 --mcp-config 单独给；用户级设置不需要时加 --setting-sources project，需要彻底干净时用 --safe-mode。我的配置下前两步就把首轮从 45096 降到 21806。
  2. 用 --tools 只列真正要用的内置工具，要用 MCP 就把 ToolSearch 也列上。24 个内置工具占 15496 token，留 4 个只要 3273。
  3. CLAUDE.md 按每行约 30 token 估算，800 行就是 2.3 万。写给人看的长文档放到别的文件里，让模型需要时去读。
  4. 批量跑同一类任务时，把会变的东西放进提示词，不要放进 CLAUDE.md 或系统提示词，让前缀保持不变，后续调用才能按 5% 的价格读缓存。
  5. 读文件、抽字段这类任务直接 --model haiku，这次同样的结果费用只有冷启动 Opus 的 3%，和缓存已热的 Opus 比也不到 4%。
  6. 不要靠 --max-turns 控成本，它截停时已经花掉的钱不退，也拿不到结果。
  7. 看费用时直接读 usage.cache_creation_input_tokens，它比上下文总长度更能说明这次调用为什么贵。
