把 Ollama 放进 Kubernetes：Pod 已 Ready，模型还没到

 costalong  2026-11-20  AI 本地大模型 Kubernetes Ollama
本地大模型 Kubernetes Ollama
AI
文章字数:   4.2k
阅读次数:  
   阅读模式

在单节点 kind 集群里用纯 CPU 跑 Ollama，把冷启动、就绪探针、keep_alive、CPU limit、memory limit 和滚动重启各测了一遍。每个结论都来自一次单独的运行，日志原样保留，截图里的终端输出直接从日志里截取。

最先踩到的坑是就绪探针：探针打在 / 上，Pod 3 秒就 Ready，但模型要 6 分钟后才拉完，这期间 Service 把 349 个请求转给它，全部返回 404 model not found。另外两个坑和资源限制有关：limits.cpu: 1 时 Ollama 照样按宿主机物理核数开 20 个线程，生成 128 个 token 要两分半；limits.memory: 512Mi 时 Ollama 自己算出只有 394 MiB 可用，却没有拒绝加载，结果是容器被 OOMKill。

测试环境

  • 集群：kind v0.24.0，单节点，节点镜像 kindest/node:v1.31.0，kube-proxy 为 iptables 模式，StorageClass 用 kind 自带的 local-path。
  • 宿主机：Intel i7-14700KF，llama.cpp 日志里显示 28 个逻辑核，61 GiB 内存，cgroup v2，没有 GPU 参与。
  • Ollama：镜像 ollama/ollama:0.40.16，模型 qwen2.5-coder:0.5b（约 400 MB）。选 0.5b 是为了让每轮实验在几分钟内跑完；换成更大的模型，绝对数字都会变，下面讲的现象我只在 0.5b 上看到过。
  • 客户端：集群里一个 curl Pod，按固定间隔请求 http://ollama:11434/api/chat，每行记录 HTTP 状态码、耗时和响应体。
  • 服务端：一个 Deployment 加一个 ClusterIP Service。容器命令是 sh -c 包装的一段脚本：先 ollama serve &，等它能应答后按需 ollama pull 和 ollama run 预热，最后 wait。

每种配置只跑了一次。在同一台机器上，偶尔会有单个请求慢出一个数量级（prompt 掉到个位数或十几 token/s，eval 掉到 0.6 到 2 token/s），原因没查清，下文遇到时会标出来，不把它当成配置的效果。

生成清单、客户端和跑实验的 kind 脚本放在 blog-go-example/ollama-on-kubernetes，可以照着 README 复现。

镜像本身就是一道门槛

ollama/ollama:0.40.16 的 amd64 镜像约 3.4 GB（kubelet 报告 3397620864 字节）。在镜像里跑 du -sh /usr/lib/ollama/*，大头是 GPU 运行库：mlx_cuda_v13 2.0G、cuda_v12 1.3G、cuda_v13 1.1G。在只有 CPU 的节点上，这些全是白拉。

这次拉取很慢：在节点里由 kubelet 拉，事件里记的是 Successfully pulled image ... in 48m1.386s；后来在宿主机上 docker pull 同一个 digest，也用了 48 分钟。第一个 Pod 在这 48 分钟里一直卡在 ContainerCreating，kubectl get pod 上看不到任何进度。

用 kind load docker-image 把宿主机的镜像导进节点时直接报错：

ctr: content digest sha256:125793ec...: not found

从报错推断，原因是宿主机的 Docker 开着 containerd image store，docker pull 留下的是多平台的索引，但只下载了 amd64 那一份内容；kind 用 ctr images import --all-platforms 导入时，去找其他平台的层就找不到。绕过办法是只导出一个平台，再直接交给节点里的 ctr：

docker save --platform linux/amd64 ollama/ollama:0.40.16 \
  | docker exec -i ok8s-control-plane ctr -n k8s.io images import --snapshotter=overlayfs -

导入耗时 2 分 45 秒。生产集群里的对应做法是让节点提前把镜像拉好（比如用 DaemonSet 预拉，或者放进节点镜像），不要等第一个 Ollama Pod 调度上来才开始拉。

冷启动：Ready 和“模型可用”是两回事

四次冷启动，每次客户端都在 kubectl apply 的同一时刻开始每秒发一个请求：

编号模型存放启动时做什么就绪探针Ready首个 200期间的失败
c1emptyDirpullGET /3 秒361.3 秒349 个 404
c2PVC，首次pull + 预热test -f /tmp/ready340 秒340.4 秒333 个连接失败
c3PVC，已有模型pull + 预热同上约 5 秒6.0 秒4 个连接失败
c4PVC，已有模型只预热同上3～4 秒3.9 秒2 个连接失败

c1 是最常见的写法：容器启动时 ollama pull，就绪探针用 HTTP 打 /。ollama serve 起来后 / 立刻返回 200，所以 Pod 在 3 秒时就 Ready 了，Service 把流量转过来；而模型拉了将近 6 分钟，这段时间每个请求都是 404：

c2 到 c4 把就绪条件改成“模型已经加载过一次”：拉完以后用 ollama run 发一个请求把模型装进内存，然后 touch /tmp/ready，就绪探针检查这个文件。

command: [sh, -c, 'ollama serve & pid=$!;
  until ollama list >/dev/null 2>&1; do sleep 0.2; done;
  ollama run qwen2.5-coder:0.5b hi >/dev/null 2>&1; touch /tmp/ready;
  wait $pid']
readinessProbe:
  exec: {command: [test, -f, /tmp/ready]}
  periodSeconds: 1

这样 Pod 没准备好时就不在 Service 的端点里，客户端拿到的是连接失败而不是 404。连接失败更容易让上游重试，或者在前面挂一个等待逻辑；404 往往会被当成“模型名写错了”，直接报给用户。

PVC 解决的是另一件事：模型只拉一次。c2 第一次挂空 PVC 时照样要拉 5 分多钟，c3 和 c4 重建 Pod 时模型已经在卷上，不到 5 秒就 Ready。c3 演示的是启动脚本里保留 ollama pull 的情况：模型已存在时 pull 只做一次远端校验，这次花了 1.2 秒，但它要求每次启动都能连上模型仓库，不如去掉。PVC 本身的细节在 存储笔记 里。

c4 预热完后的第一个请求 load_duration 几乎为 0（0.5 毫秒），总耗时 0.08 秒。没预热的 c1，第一个 200 里有 1.18 秒花在加载模型上。

还有一个数字值得留意：第一次启动的 Pod 在 discovering available GPUs... 这一步停了近 14 秒，之后的 Pod 这一步只要 0.2 秒左右。第一次慢的原因我没有确认。

keep_alive 过期后，下一个请求要重新加载

Ollama 默认在模型闲置 5 分钟后把它从内存里卸掉，这个时长由 OLLAMA_KEEP_ALIVE 控制。这里设成 30 秒，看间隔超过它时会怎样：

请求间隔load_duration单次总耗时
45 秒（k1）0.52 到 0.78 秒，每次都有0.64 到 0.92 秒（第一个 1.92 秒）
15 秒（k2）只有第一个 0.53 秒，之后为 00.08 秒（第一个 0.64 秒，第三个慢请求 1.19 秒）

k1 的第一个请求 eval 只有 5.9 token/s，k2 的第三个请求 prompt 只有 26.7 token/s，都是前面说的偶发慢请求。

0.5b 模型重新加载只要半秒多，放大到 7b 或更大的模型，这个时间会长得多（本文没测）。如果服务要求延迟稳定，有两种做法：把 OLLAMA_KEEP_ALIVE 设得比最长空闲间隔还长，或者设成 -1 让模型常驻。常驻的代价是内存一直被占着，而这部分内存要算进下面的 memory limit 里。

CPU limit：线程数不看 limit

测法：同一个 prompt（让模型写一个反转单链表的 Go 函数并解释），temperature 0、seed 1、生成 128 个 token，每种配置发 2 个请求。requests 和 limits 设成相同的值，memory 统一给 4Gi。

CPU默认线程数（20）num_thread = limit节流周期占比（默认 → num_thread）
不设 limit106.7 token/s，1.2 秒不适用没有 cpu.max
417.9 token/s，7.2 秒100.1 token/s，1.6 秒91% → 37%
27.6 token/s，17.3 秒63.5 token/s，2.4 秒97% → 36%
10.9 token/s，146.0 秒35.8 token/s，4.1 秒99.9% → 32%

表中是 2 个请求的平均 eval 速度和平均总耗时；节流周期占比取自容器 cgroup 的 cpu.stat，只统计客户端发请求的这段时间。

不设 limit 时，0.5b 模型在这台机器上每秒能生成 100 多个 token。设了 limit 之后，默认配置下慢得不成比例：limits.cpu: 4 只剩 17.9 token/s，不到不设 limit 时的五分之一；limits.cpu: 1 只有 0.9 token/s，一个请求要 146 秒。

原因在服务端日志里。不管 limit 是多少，llama.cpp 都按宿主机的物理核数（20，逻辑核 28）开线程，不看 cgroup 的 cpu.max：

system_info: n_threads = 20 (n_threads_batch = 20) / 28

我的理解是：20 个线程去抢 1 个核的 CFS 配额，每个调度周期的配额很快用完，剩下的时间全部线程一起被节流；矩阵乘法又要求线程之间同步，一个线程被挂起，其余线程只能等着。cgroup 里的 cpu.stat 能看到这一点：limits.cpu: 1 默认线程数的那一轮，2974 个调度周期里有 2972 个被节流。

请求里把 num_thread 设成和 limit 一样，日志里的线程数就变了，速度也回来了：

curl http://ollama:11434/api/chat -d '{
  "model": "qwen2.5-coder:0.5b",
  "messages": [{"role": "user", "content": "..."}],
  "options": {"num_thread": 1}
}'

limits.cpu: 1 加上 num_thread: 1 后是 35.8 token/s，是默认线程数时的 40 倍；limits.cpu: 4 配 4 个线程时到了 100.1 token/s，和不设 limit 的 106.7 token/s 差不多。线程数改变会让 Ollama 重新加载一次模型，所以这三组的第一个请求里都有 0.54 到 0.56 秒的 load。

默认线程数下的耗时在两轮之间也不稳定：limits.cpu: 1 这组在早先的一轮里（那轮客户端没留下完整的统计字段，没有计入上表）单个请求是 110 到 120 秒，这一轮是 144 到 148 秒。

这个参数是逐请求设置的，要求所有调用方都带上。也可以写进 Modelfile（PARAMETER num_thread 2）做成一个专用模型，这条我没测。另一个办法是不设 CPU limit，只设 requests，让 Ollama 在节点空闲时用满所有核；代价是它会和同节点的其他 Pod 抢 CPU。requests 和 limits 怎么搭配会影响 Pod 的 QoS 等级，见 QoS 笔记。

memory limit：Ollama 看到了上限，但不会拒绝

八种组合，每种跑一次：memory limit 取 256Mi、512Mi、768Mi、1Gi，num_ctx 取默认的 4096 和 32768。这一组用的是 HTTP / 就绪探针，第一个请求负责把模型加载进内存。

先看 llama.cpp 自己报的账（0.5b 模型）：

部分num_ctx 4096num_ctx 32768
模型权重345.65 MiB + 28.05 MiB（CPU_REPACK）同左
KV cache48 MiB384 MiB
计算缓冲区41.27 MiB138.54 MiB
合计约 463 MiB约 896 MiB

在 4096 下实际测到的 Pod 峰值约 611 MiB，比上表多出 150 MiB 左右，这部分是 ollama serve 进程本身和 Go 运行时的开销。按这个开销粗算，32768 会超过 1 GiB，但 1Gi 那格实际跑完了，峰值 948 MiB；我推测是计算缓冲区没有全部被写到，所以没有全占上。不管怎样，余量只剩 76 MiB。

512Mi 这格最能说明问题。Ollama 的调度器在日志里明确写出了 cgroup 给的上限和剩余量，接下来负责加载的 llama-server 却按整台机器的内存来估算，认为空间绰绰有余：

结果是容器在加载权重时被内核杀掉，退出码 137，原因 OOMKilled。Pod 级 cgroup 的 memory.events 里 oom_kill 是 8，说明每次 OOM 被杀的不止一个进程（oom_group_kill 是 2，kubelet 给容器开了 cgroup 级的整组 OOM kill）。768Mi 加 32768 上下文那格的权重加载完了，日志最后几行是 llama_context: n_ctx = 32768 和 output buffer，下一步就是分配 384 MiB 的 KV cache。

256Mi 更早：日志停在 discovering available GPUs...，还没轮到模型。我推测是 Ollama 在探测 GPU 时会加载各个 GPU 后端的库，这一步就超过了 256 MiB，但没有逐个验证。这个组合重启了 4 次，进入 CrashLoopBackOff，从头到尾没有返回过一个 200。

在 Kubernetes 里，512Mi 和 768Mi 表现为请求到一半连接断开（客户端看到状态码 000）；256Mi 的 Pod 一直不 Ready，请求直接连接失败。两种情况下 Pod 的重启计数都在涨，不会收到“内存不够”之类的报错。估算 memory limit 时，可以用模型文件大小加上目标 num_ctx 下的 KV cache 和计算缓冲区，再加 150 到 250 MiB 给服务进程。如果要支持多个并发请求（OLLAMA_NUM_PARALLEL）或常驻多个模型，KV cache 要按倍数算；这两种情况本文都没测。资源和探针的基础用法见 探针与资源笔记。上下文开小了还有另一种后果：超出部分会被静默截断，见 Ollama 静默截断长提示词。

滚动重启：Recreate 断流，RollingUpdate 不断

最后一组看 kubectl rollout restart。客户端每秒发一个请求、共 150 个，第 20 秒触发重启；模型都放在同一个 PVC 上，不用重新拉取。

编号策略就绪探针结果
r1RecreateGET /，不预热146 个 200，4 个连接失败；新 Pod 第一个请求加载模型 0.53 秒
r2Recreate预热后写文件148 个 200，1 个连接失败，1 个请求挂了 133 秒后失败
r3RollingUpdateGET /，不预热150 个 200；新 Pod 第一个请求加载模型 0.53 秒
r4RollingUpdate预热后写文件150 个 200，没有看到加载

Recreate 先删旧 Pod 再建新 Pod，中间必然有空窗，单副本时这个空窗就是服务中断。RollingUpdate 先等新 Pod Ready 再删旧的，配合预热探针（r4），150 个请求全部 200，但新 Pod 预热的那 11 秒里有一个请求耗时 10.2 秒，是切换期间抢 CPU 还是前面说的偶发慢请求，没有区分；只用 GET /（r3）时不丢请求，但切换后第一个请求要多等一次模型加载。

r1 和 r2 里有两个现象和 Ollama 关系不大，但部署时会遇到：

一是旧 Pod 花了整整 30 秒才退出。容器的 1 号进程是 sh -c，它不会把 SIGTERM 转发给 ollama serve，所以 Ollama 一直跑到宽限期结束被 SIGKILL。这 30 秒里，r1 的请求仍然由旧 Pod 返回 200；我推测是 kube-proxy 在没有就绪端点时，会回落到仍在 serving 的终止中端点，这一点没有单独验证。新 Pod 要等旧 Pod 彻底消失才创建，所以整个 Recreate 被拖长了 30 秒。修法是让 SIGTERM 传到 Ollama。我在启动脚本开头加了一行 trap "kill -TERM $pid; wait $pid" TERM，同样的 Deployment 各跑一次 kubectl delete pod --wait：不加时 33.3 秒，加了以后 4.0 秒。优雅退出的完整流程见 优雅终止笔记。

二是 r2 里有一个请求在旧 Pod 被杀后发出，挂了 133.45 秒才以连接失败告终。我推测这个连接被 DNAT 到了已经消失的旧 Pod IP，SYN 一直重传到超时；之后的请求都正常。不管原因是什么，结论是调用 Ollama 的客户端一定要设连接超时，别依赖默认值。

还有一点没测：模型放在 ReadWriteOnce 的 PVC 上时，RollingUpdate 能成功，是因为这次只有一个节点，新旧 Pod 挂的是同一个节点上的卷。多节点集群里，新 Pod 被调度到别的节点时，卷挂不上去，滚动会卡住。

合起来的一份 Deployment

把上面几项改进合在一起，大致是下面这样（数值按 0.5b 模型、4 核 limit、4096 上下文估算，换模型要重新算内存）：

apiVersion: apps/v1
kind: Deployment
metadata: {name: ollama}
spec:
  replicas: 1
  strategy: {type: RollingUpdate}          # 单节点或 RWX 卷；RWO 跨节点会卡住
  selector: {matchLabels: {app: ollama}}
  template:
    metadata: {labels: {app: ollama}}
    spec:
      containers:
      - name: ollama
        image: ollama/ollama:0.40.16       # 节点上预拉好
        command: [sh, -c, 'ollama serve & pid=$!;
          trap "kill -TERM $pid; wait $pid" TERM;
          until ollama list >/dev/null 2>&1; do sleep 0.2; done;
          ollama run qwen2.5-coder:0.5b hi >/dev/null 2>&1; touch /tmp/ready;
          wait $pid']
        env:
        - {name: OLLAMA_HOST, value: "0.0.0.0:11434"}
        - {name: OLLAMA_KEEP_ALIVE, value: "-1"}
        resources:
          requests: {cpu: "4", memory: 1Gi}
          limits: {cpu: "4", memory: 1Gi}   # 调用方请求里带 num_thread: 4
        readinessProbe:
          exec: {command: [test, -f, /tmp/ready]}
          periodSeconds: 2
        volumeMounts: [{name: models, mountPath: /root/.ollama}]
      volumes:
      - name: models
        persistentVolumeClaim: {claimName: ollama-models}   # 预先 ollama pull 进去

这份清单是按上面的结论组合出来的，没有作为整体再跑一遍；其中每一项都对应上文的某一次运行。

这次没有覆盖的

  • 所有数字都来自单次运行，只用了 0.5b 一个模型，没有 GPU，没有多节点。
  • 偶发的慢请求（eval 掉到 0.6 到 2 token/s）在几组实验里都出现过，原因没查清，表格里能看出来的地方我都标了。
  • 256Mi 下 GPU 探测为什么就能超出内存、r1 旧 Pod 在终止期间为什么还能收到流量、r2 那个请求为什么挂了 133 秒，都是推测，没有单独验证。
  • 并发请求（OLLAMA_NUM_PARALLEL）、多模型常驻、HPA 扩缩容都没有测。
