Ollama /v1 兼容接口的 7 处静默差异

把一个用 OpenAI SDK 写的小工具指向本机 Ollama，只需要改 base_url，代码一行不动就能跑。问题是「能跑」和「行为一致」是两回事：同一句话、同一个模型，走 /v1/chat/completions 和走原生 /api/chat，模型实际拿到的采样参数、上下文长度、输出约束都可能不一样，而且两边都返回 200。

Ollama 0.35.0 的 /v1 兼容层，我把能想到的请求字段和原生接口挨个对照了一遍。最意外的一条：不传 temperature 时，/v1 会主动把温度设成 1.0、top_p 设成 1.0，比原生接口的默认值 0.8 和 0.9 更发散。其余几条是请求里写了却不生效、也不报错的字段。

测试环境和对照方法

项目值
Ollama0.35.0，systemd 服务，监听 127.0.0.1:11434，服务配置没有改动
硬件RTX 3060 12 GiB，i7-14700KF，61 GiB 内存，模型放在机械硬盘上
默认上下文4096（服务没设 OLLAMA_CONTEXT_LENGTH，按显存取的默认值）
模型qwen2.5-coder:7b（Modelfile 里没有任何 PARAMETER）、llama3.1:8b（只有 stop）
客户端Python urllib 直接发 JSON；最后用 openai 3.57.0 SDK 复核一遍

对照方法很朴素：同一个请求体分别发给两个端点，比较响应和服务端日志。这台机器上的 Ollama 服务日志级别比较高，journalctl -u ollama 里每次推理都会打出 llama-server 的采样参数行，所以「模型实际用了什么参数」可以直接看到，不用靠输出去猜。源码对照用的是 v0.35.0 tag，兼容层的转换逻辑在 openai/openai.go 的 FromChatRequest。

对照脚本放在 blog-go-example/ollama-openai-compat，可以照着 README 复现。

下文每个结论后面都注明了跑了几次。大部分是单次运行，仍然是小样本。

温度：不传就是 1.0

源码里这一段写得很直白：

if r.Temperature != nil {
    options["temperature"] = *r.Temperature
} else {
    options["temperature"] = 1.0
}
// ...
if r.TopP != nil {
    options["top_p"] = *r.TopP
} else {
    options["top_p"] = 1.0
}

也就是说兼容层不是「没传就用模型默认值」，而是「没传就按 OpenAI 的默认值填上 1.0」。原生接口的默认值在 api/types.go 的 DefaultOptions() 里，是 Temperature: 0.8、TopP: 0.9。qwen2.5-coder:7b 的 Modelfile 没有覆盖这两项，所以原生接口用的就是 0.8 和 0.9。

先看日志。我发了四个请求，每次请求前记下 journal 的游标，请求后只取游标之后的采样参数行：

== /v1 不设 temperature/top_p
top_k = 40, top_p = 1.000, ... temp = 1.000
== /api/chat 不设 options
top_k = 40, top_p = 0.900, ... temp = 0.800
== /v1 只设 temperature=0.2
top_k = 40, top_p = 1.000, ... temp = 0.200
== /v1 temperature=0.8 top_p=0.9
top_k = 40, top_p = 0.900, ... temp = 0.800

第三组值得单独说：只传 temperature、不传 top_p 时，top_p 依然被填成 1.0。原生接口的 top_p 0.9 会砍掉概率尾部的候选，/v1 不会，所以即使两边温度一样，/v1 也更容易采到低概率的词。

日志里的参数是一层证据，我又用 seed 做了一次交叉验证。固定 seed=7、max_tokens=60，让 qwen2.5-coder:7b「用一句话描述秋天的傍晚」，四种写法各发两次：

写法输出
A：/v1，只设 seed秋天的傍晚，天边云卷云舒，夕阳西下，万物宁静，满天金黄。
B：/api/chat，只设 seed秋天的傍晚，天边云卷云舒，夕阳西下，景致宁静而美丽。
C：/api/chat，seed + temperature 1.0 + top_p 1.0秋天的傍晚，天边云卷云舒，夕阳西下，万物宁静，满天金黄。
D：/v1，seed + temperature 0.8 + top_p 0.9秋天的傍晚，天边云卷云舒，夕阳西下，景致宁静而美丽。

A 和 C 逐字相同，B 和 D 逐字相同。也就是说，/v1 不传温度的效果，等价于原生接口显式传 1.0 和 1.0；反过来，想让 /v1 复现原生接口的默认行为，得把 0.8 和 0.9 都写上。

有一个小插曲：A 的第一次请求输出是「……万物染上了金黄。」，和后面几次不同。我推测那次请求触发了模型加载（当时没有记录加载耗时，无法确认），之后我又连发了 4 次 A、2 次 C，6 次全是「万物宁静，满天金黄」。如果确实如此，可能是首次加载时的计算顺序和之后不完全一样，导致同 seed 也没对上，但没有深究。用 seed 做回归测试时，最好先发一次预热请求。

不设 seed 时差异有多大？两边各发 10 次，10 次输出全都互不相同，平均长度分别是 27.1 和 29.4 个字符。这个样本太小，看不出分布上的差别，我只拿它说明一件事：两边都在随机采样，光看几条输出分辨不出温度是 0.8 还是 1.0，只有日志和 seed 对照能说清楚。

温度对代码生成的影响，我在本地模型温度实验里测过。那篇末尾假设过一种情形：「通过 OpenAI 兼容接口只传 temperature、截断参数用的是另一套默认值」。这里证实 Ollama 的 /v1 正是这样：截断参数指的就是被填成 1.0 的 top_p。

上下文：options 字段被整个丢掉

OpenAI 的请求格式里没有上下文长度这个概念，Ollama 的 ChatCompletionRequest 结构体也就没有对应字段，连原生接口的 options 都没有。gin 解析 JSON 时，结构体里没有的字段会直接丢弃，不报错。

我用一个 13857 token 的提示词试了三种写法：开头一句「暗号是蓝鲸-4729」，中间 450 行服务端口记录，末尾问暗号是什么。

请求HTTPprompt_tokens回答ollama ps 的 CONTEXT
/v1，不带额外字段2002050暗号是 “服务 svc-386 监听端口 62824096
/v1，"options": {"num_ctx": 16384}2002050同上4096
/v1，顶层 "num_ctx": 163842002050同上4096
/api/chat，options.num_ctx=1638420013857蓝鲸-472916384

三种 /v1 写法的结果完全一样：提示词被截到 2050 个 token，开头的暗号被砍掉，模型从剩下的记录里随手编了一个答案。服务端日志里每次都有一条 level=WARN ... msg="truncating input prompt" limit=2050 prompt=13857 keep=4 new=2050，但客户端什么都收不到。为什么是 2050 而不是 4096，我在上一篇讲截断的文章里从源码推过，这里不重复。

用官方 SDK 时更容易踩到这个坑。openai 3.57.0 的 create() 不接受未知参数，直接写 num_ctx=16384 会抛 TypeError: Completions.create() got an unexpected keyword argument 'num_ctx'；于是很自然地改成 extra_body={'options': {'num_ctx': 16384}}。这一次 SDK 不报错了，请求也确实带上了 options，结果 prompt_tokens 还是 2050，回答还是错的，报错消失了，截断照旧。

官方文档给的办法是用 Modelfile 做一个写死上下文的模型变体：

printf 'FROM qwen2.5-coder:7b\nPARAMETER num_ctx 16384\n' > Modelfile.16k
ollama create qwen-coder-16k -f Modelfile.16k

ollama create 复用已有的权重层，只写了一个新 manifest，耗时 0.62 秒。之后 /v1 请求把 model 换成 qwen-coder-16k，prompt_tokens 变成 13857，答出了「蓝鲸-4729」，ollama ps 显示 CONTEXT 16384。实验结束后我用 ollama rm 删掉了这个变体。

还有一个代价是混用两个端点时才会暴露的。原生 16k 请求让模型以 16384 的上下文重新加载，这次重载花了 32.86 秒（原因没查，推测和 16k 的 KV 缓存分配有关），整个请求 42.76 秒；紧接着的一个 /v1 请求又按默认的 4096 重新加载了一次，用了 1.30 秒。同一个模型被不同上下文的请求交替调用时，会来回重载。都是单次计时，具体秒数和磁盘、缓存状态关系很大，只说明重载确实会发生。

keep_alive 是唯一透传的扩展字段

keep_alive 不是 OpenAI 的字段，Ollama 在 ChatCompletionRequest 里专门加了它，源码注释说没有它，OpenAI 客户端就没法让模型释放显存。实测四种取值都按预期生效：

/v1 请求里的 keep_alive请求后 1 秒的 ollama ps
不传UNTIL：4 minutes from now
"30s"UNTIL：28 seconds from now
0列表为空，模型已卸载
-1UNTIL：Forever

SDK 里同样要走 extra_body={'keep_alive': 0}，复测时模型也立刻卸载了。所以 /v1 并不是完全不认扩展字段，只认它结构体里声明过的那几个；options、num_ctx、truncate、shift 都不在其中。

response_format：写错就退化成自由文本

兼容层对 response_format 的处理只有两个分支：json_object 转成原生的 format: "json"；json_schema 取 json_schema.schema 当作原生的 format。只要没命中这两条路径，就等于没传，不报错。

我让模型回答「Go 语言叫什么、哪一年首次公开发布」，温度 0，每种写法跑一次：

写法结果
标准写法 {"type":"json_schema","json_schema":{"name":"lang","schema":{...},"strict":true}}合法 JSON，含 name 和 year
json_schema 里只有 name，没有 schema 对象一段中文自由文本
schema 写在 response_format.schema（少了一层）一段中文自由文本
type 拼成 json-schema一段中文自由文本
{"type":"json_object"}合法 JSON，但字段是模型自己起的 {"text": "..."}
原生 format 传同一个 schema和标准写法输出逐字相同
原生 format: "json"和 json_object 输出逐字相同

三种写错的情况全都返回 200，内容是一段普通的介绍文字。如果下游代码直接 json.loads，异常会出现在离真正原因很远的地方。

这组数据还顺带暴露了另一件事：两次 schema 约束的输出都是 {"name":"Go语言","year":2007}，而同一个模型在自由文本里写的是「Go 语言在 2009 年首次公开发布」，2007 是它说的开发起始年份。约束保证了 JSON 的形状，没有保证内容对。我在 JSON 输出那篇里讨论过约束解码的代价，这只是一次运行，不能说明约束让答案变差，只能说明形状合法和内容正确是两件事，都要校验。

流式响应：usage 要单独开

不加 stream_options 时，/v1 的流式响应里没有 token 统计。最后一个数据块只有 finish_reason: "stop"，然后是 data: [DONE]，整个响应 8 行 SSE。加上 "stream_options": {"include_usage": true} 之后多出一行，共 9 行：

data: {"id":"chatcmpl-78",...,"choices":[],"usage":{"prompt_tokens":37,"prompt_tokens_details":{"cached_tokens":36},"completion_tokens":7,"total_tokens":44},"timings":{"prompt_n":37,"prompt_ms":14,...,"predicted_per_second":76.08695652173913}}
data: [DONE]

这行有三个要注意的地方。第一，choices 是空数组，按 OpenAI 的约定写的客户端没问题，但如果代码里无条件取 choices[0]，这一行会直接越界。第二，prompt_tokens 37 里有 36 个命中了提示词缓存，cached_tokens 是兼容层从原生的 prompt_eval_cached_count 映射过来的，可以用来确认缓存是否生效。第三，timings 是 Ollama 自己加的字段，OpenAI 没有，严格校验响应结构的客户端可能会因此报错（推测，我没有找到这样做的客户端来验证）。

原生 /api/chat 的流式响应没有这个开关，最后一行 done: true 里固定带着 prompt_eval_count、eval_count 和各段耗时。

工具调用：看模型，也看兼容层

这一节的差异最多，而且有一半不是兼容层造成的。同一个 get_weather 工具、同一句「杭州现在天气怎么样？」，温度 0：

qwen2.5-coder:7b 两个端点都没有产生结构化的工具调用。它把 {"name": "get_weather", "arguments": {"city": "杭州"}} 当成正文写了出来，tool_calls 是 null，finish_reason 是 stop。我推测是模型输出格式和 Ollama 的工具解析没对上，换哪个端点都一样。ollama show 里它的 Capabilities 明明列着 tools，所以「声明支持工具」不等于「工具调用能被解析出来」。

llama3.1:8b 能正常调用，两个端点的响应形状却不一样：

字段/v1/chat/completions/api/chat
结束原因finish_reason: "tool_calls"done_reason: "stop"
arguments字符串 "{\"city\":\"杭州\"}"对象 {"city": "杭州"}
idcall_2mvjii9scall_d69mj8q9
index在 tool_call 顶层在 function 里面

把工具结果用 role: "tool" 和对应的 tool_call_id 发回 /v1，第二轮回答是「杭州现在天气较为阴雨，气温约为14摄氏度。」，往返是通的。

兼容层自己的问题在 tool_choice。官方文档的字段列表里把它标成不支持，实测确实被忽略：tool_choice: "none" 时 llama3.1:8b 依然调用了工具，finish_reason 依然是 tool_calls。OpenAI 的语义是 none 表示禁止调用工具，如果某个框架靠 none 结束工具循环（推测，未验证具体框架），在 Ollama 上这一轮会再收到一个工具调用，循环就会多跑一轮。三种 tool_choice 写法各跑了一次。

错误：有的报，有的不报

能报错的场景，/v1 的错误格式和 OpenAI 一致，SDK 能正确映射成异常：

场景/v1/api/chat
未知模型404，{"error":{"message":"model 'gpt-4o-mini' not found","type":"not_found_error",...}}404，{"error":"model 'gpt-4o-mini' not found"}
messages 为空400，[] is too short - 'messages'200，done_reason: "load"，内容为空
temperature 传成字符串400，json: cannot unmarshal string into Go struct field ...未测
JSON 不完整400，unexpected EOF400，{"error":"unexpected EOF"}
role 写成 robot200，照常回答未测

SDK 里未知模型抛的是 NotFoundError，status_code 404，body 里的 type 是 not_found_error，和用 OpenAI 时的处理代码可以共用。

messages 为空这一行很有意思：原生接口把它当成「只加载模型」的请求，返回 200 和空内容；兼容层在中间件里先拦了一道，返回 400。同一个空请求，两边的语义完全不同。

真正麻烦的是超长提示词。13857 token 的提示词发给上下文 4096 的模型：

/v1 返回 200，prompt_tokens 2050，finish_reason 是 length（因为 max_tokens 只给了 10）。我试着在 /v1 请求里加 "truncate": false, "shift": false，结果一模一样，这两个字段同样不在兼容层的结构体里。原生接口加 truncate: false 就会拒绝请求：

{"error":"{\"error\":{\"code\":400,\"message\":\"request (13857 tokens) exceeds the available context size (4096 tokens), try increasing it\",\"type\":\"exceed_context_size_error\",\"n_prompt_tokens\":13857,\"n_ctx\":4096}}"}

注意这个错误是双层的：外层 error 的值是一个字符串，里面又是一段 JSON，是 llama-server 的原始错误被原样塞了进去。要取出 n_prompt_tokens 得解析两次。只设 shift: false 则是另一段纯文字的 400：the prompt is longer than the context length currently available to the model; ...。

所以在 /v1 上，超长提示词没有任何报错路径。客户端能做的只有一件事：每次都拿 usage.prompt_tokens 和自己估算的长度比，明显偏小就是被截了。

两个没人会注意的字段：id 和 n

兼容层生成响应 id 的代码是 fmt.Sprintf("chatcmpl-%d", rand.Intn(999))，只有 999 种取值。我连发 100 个请求，得到 94 个不同的 id，有 6 个各出现了两次（chatcmpl-941、chatcmpl-185、chatcmpl-688、chatcmpl-423、chatcmpl-700、chatcmpl-396）。按生日问题估算，从 999 个值里抽 100 次，期望的重复对数约是 100×99÷2÷999 ≈ 5，实测 6 对，量级吻合。拿 id 当日志主键或者去重键的系统，在 Ollama 上会把两次不相关的请求当成同一次。

n=3 返回 200，但 choices 只有 1 个元素；logit_bias 也是 200，看不出有没有生效。文档里这两个字段都标了不支持；实测 n 被静默忽略，logit_bias 只能确认返回 200、没有报错。

用 SDK 复核了一遍

前面的实验都是手写 JSON。为了确认用户真实会遇到的情况，我在临时虚拟环境里装了 openai 3.57.0，把关键几条重跑了一遍，结果和手写 JSON 完全一致：

openai 3.57.0
extra_body options.num_ctx=16384 -> prompt_tokens 2050 answer '暗号是 "服务 svc-386 监听端口 6282'
直接传 num_ctx=16384 -> TypeError Completions.create() got an unexpected keyword argument 'num_ctx'
extra_body keep_alive=0 -> '你好！有什么我可以帮忙'
NAME    ID    SIZE    PROCESSOR    CONTEXT    UNTIL
未知模型 -> NotFoundError 404 {'message': "model 'gpt-4o-mini' not found", 'type': 'not_found_error', 'param': None, 'code': None}

七处差异汇总

差异/v1 的行为原生 /api/chat依据
默认采样temperature 1.0、top_p 1.00.8、0.9日志各 1 次，seed 对照各 2 次
上下文请求里改不了，options 被丢弃options.num_ctx3 种写法各 1 次
超长提示词只能静默截断，200可用 truncate:false 拿到 400各 1 次
response_format 写错退化成自由文本，200不适用3 种错法各 1 次
tool_choice忽略，none 也会调用工具没有这个字段3 种写法各 1 次
n忽略，只返回 1 个 choice没有这个字段1 次
响应 id只有 999 种，100 次撞 6 对没有 id100 次

另外几处形状上的差别不算「静默」，但写解析代码时要知道：工具参数一边是字符串一边是对象；流式 usage 那一行 choices 为空；空 messages 一边 400 一边 200。

客户端指向 Ollama 前要补的几行参数

  • 每个请求都显式写 temperature 和 top_p。想和原生接口行为一致，就写 0.8 和 0.9；想要确定性输出，写 0。不写就是 1.0 和 1.0。
  • 需要长上下文的模型，用 Modelfile 建一个变体，客户端只改 model 名。不要写 extra_body={'options': ...}，它不报错也不生效。
  • 每次响应都检查 usage.prompt_tokens，它小于你估算的提示词长度就说明被截了。/v1 不会用错误告诉你。
  • 结构化输出用标准的 json_schema 写法，并且在客户端解析失败时打印原始响应，而不是只抛 JSONDecodeError。
  • 用工具调用前，先用目标模型跑一次，看 tool_calls 是否真的非空。qwen2.5-coder:7b 在这台机器上两个端点都只会把调用写成正文。
  • 别依赖 tool_choice: "none" 来结束工具循环，改成在那一轮不传 tools。
  • 响应 id 不能当唯一键，需要的话自己生成。
  • 批处理或测试脚本结束时发一个 keep_alive: 0，显存立刻释放，不用等 5 分钟。

这次没覆盖到的

  • 只测了 Ollama 0.35.0 和两个模型。兼容层代码近几个版本改动频繁（文档里 Responses API 标着 v0.13.3 才加入），其他版本的结论需要复测。
  • /v1/completions、/v1/embeddings、/v1/responses 都没测，它们的默认值不一定相同。源码里 /v1/completions 对应的转换函数也有一段温度缺省填 1.0 的逻辑，但我没有实际发请求验证。
  • 温度那一节说明了默认值不同，没有测这个差异对具体任务的质量影响有多大。
  • logit_bias 只确认了不报错，没有设计实验去看它是否被忽略；按文档的不支持列表，推测是被丢弃了。
  • OpenAI 官方接口在超长提示词时的行为我没有在本机验证，文中只对比了 Ollama 两个端点之间的差异。
