Go 存活堆 150MiB 为何撑爆 256Mi 容器

 costalong  2026-11-20  golang 故障排查 Kubernetes Go
故障排查 Kubernetes Go
golang
文章字数:   5k
阅读次数:  
   阅读模式

设想一个 Go 服务：pprof 看存活堆一直在 150MiB 上下，容器的内存上限是 256Mi，按理说还有 100MiB 的余量。实际跑起来却会反复重启，kubectl describe 里写着 OOMKilled，退出码 137。

我在本机用 kind 起了一个一次性集群，写了一个能精确控制存活堆、垃圾产生速度和堆外内存的小程序，把这个场景复现出来，再逐个测 GOMEMLIMIT、GOGC、downward API 和 GOMAXPROCS。结论先放这里：默认 GOGC=100 时堆目标约等于存活堆的 2 倍，150MiB 存活堆对应 293MiB 的目标，256Mi 的上限根本装不下；GOMEMLIMIT=230MiB 能让它活下来，代价是 GC 占用的 CPU 从 7% 涨到 23%（这个指标含空闲时段做的标记，偏高，算上限），而且它是软上限，存活堆继续涨时进程照样会死，只是死前先把 CPU 耗在 GC 上。

实验环境与测试程序

项目版本
Gogo1.27.4 linux/amd64（另用 golang:1.24-alpine 构建对照镜像，得到 go1.24.13）
kindv0.24.0，节点镜像 kindest/node:v1.31.0
kubectlv1.31.0
容器运行时containerd 1.7.18，Docker 29.9.2
主机26 个逻辑 CPU，cgroup v2，内核 7.0.0-42

集群只为这次实验创建，kubeconfig 写在实验目录里，所有 kubectl 都显式带 --kubeconfig，结束后整个集群删掉。

测试程序叫 memload，FROM scratch 打包，镜像 2.5MB 左右。源码、Dockerfile 和跑实验的 kind 脚本放在 blog-go-example/gomemlimit，可以照着 README 复现。它启动时打印运行环境，然后按以下环境变量制造内存压力：

变量作用
LIVE_MIB一直保持可达的存活集大小，默认 150
LIVE_PTR存活集用 64 字节节点串成的链表，GC 必须逐个扫描
CHURN_MIB_S每秒分配多少 MiB 短命对象（每个 64KiB），0 表示不限速
GROW_MIB_S存活集每秒额外增长多少 MiB，用来模拟泄漏
OFFHEAP_MIB用 syscall.Mmap 申请并写满的堆外内存

默认每秒输出一行（部分实验把间隔调到 200ms、100ms 或 50ms，表里的速率都已折算成每秒），数据来自 runtime/metrics 和容器自己的 cgroup 文件：

t= 1.11s live= 164MiB goal= 209MiB runtime= 224MiB gc=    10 (+   6/s) gcCPU= 20.0% churn=  300MiB/s cg.cur=221MiB cg.peak=222MiB

live 是 /gc/heap/live:bytes，goal 是 /gc/heap/goal:bytes，runtime 是 /memory/classes/total:bytes 减去已归还给系统的部分，也就是 GOMEMLIMIT 实际管控的那部分内存。gcCPU 是两次采样之间 /cpu/classes/gc/total 的增量除以 /cpu/classes/total 的增量，后者约等于 GOMAXPROCS × 墙钟时间。注意 /cpu/classes/gc/total 包含 /gc/mark/idle，也就是 P 空闲时顺手做的标记；runtime/metrics 文档说要减掉它才是 GC 必须占用的 CPU。主实验的分配被限速在 300MiB/s，2 个 P 常有空闲，所以文中的 GC CPU 都偏高，应当看成上限，比较同一组内的相对变化更可靠。cg.cur 和 cg.peak 读的是容器内的 memory.current 和 memory.peak。

早期版本的存活集用 1MiB 的 []byte，这种对象不含指针，GC 不需要扫描内容，GC CPU 一直在 1% 左右，跟真实服务差得太远。后面的主实验都开了 LIVE_PTR，并把垃圾产生速度限制在 300MiB/s。不限速时短命对象来得太快，浮动垃圾会把测到的存活堆从 120MiB 抬到 200MiB，干扰判断，那组数据我单独拿来测吞吐。

所有 Pod 的内存上限都是 256Mi（memory.max=268435456），CPU 上限 2 核。requests 的内存与 limit 相同，CPU request 只给 100m，所以 Pod 属于 Burstable。

容器被杀之后，容器自己的 cgroup 也跟着消失，程序里读到的 memory.peak 来不及打印。我改成在 kind 节点上读 Pod 级的 cgroup，路径形如 /sys/fs/cgroup/kubelet.slice/kubelet-kubepods.slice/kubelet-kubepods-burstable.slice/kubelet-kubepods-burstable-pod<uid>.slice，只要 Pod 对象还在，这一层的 memory.events、memory.peak 和 cpu.stat 就会保留，重启多次的计数也会累加。另外 kubectl logs --previous 在连续重启后只能拿到上一次的日志，我把节点上 /var/log/pods 下每次运行的日志文件也一起拷了出来，后面需要单次结果的实验则改用 restartPolicy: Never。

默认 GOGC 下，存活堆 150MiB 撑不过 1 秒

第一个实验什么都不设，只给 150MiB 的存活集：

start go=go1.27.4 NumCPU=26 GOMAXPROCS=2 GOGC="" GOMEMLIMIT="" memlimit=8796093022207MiB cpu.max="200000 100000" memory.max="268435456"
live set of 150 MiB (ptr=true) ready at t=0.11s
t= 0.31s live= 147MiB goal= 293MiB runtime= 224MiB gc=     4 (+   0/s) gcCPU=  0.0% churn=  299MiB/s cg.cur=221MiB cg.peak=221MiB

只打出一行采样，进程就没了。memlimit=8796093022207MiB 是 math.MaxInt64 换算成 MiB，表示没有设置内存上限。堆目标 293MiB，已经超过了 256Mi 的上限。

下面是 describe 的结果、Pod 级 cgroup 的 memory.events，以及打开 GODEBUG=gctrace=1 后的一次复现：

几个数字可以对上：

  • 第 5 次 GC 结束时存活堆 166MB，按 GOGC=100 算下一次目标应是 332MB 左右，采样里的 goal= 333MiB 正是这个值。
  • runtime= 256MiB，cg.cur=255MiB，Go 管理的内存和 cgroup 看到的几乎一致，已经顶到上限。
  • Pod 级 memory.events 里 max 115 表示内存触碰上限 115 次，oom 3 表示这个 Pod 的 3 次运行都被 OOM 杀掉（Restart Count 是 2），memory.peak 精确等于 memory.max。

退出码 137 和 OOMKilled 的基本排查方法在 探针与资源限制 那篇笔记里写过，这里不重复，重点是 Go 这一侧为什么会走到这一步。

我接着把存活集从 60MiB 到 100MiB 逐档调，看默认 GOGC 下到底能放多大的存活堆：

规律很直接：goal 稳定在 live 的 2 倍（存活集配置是 150MiB，加上运行时自身的结构，实测 live 在 164 至 172MiB 之间），Pod 峰值基本等于 goal。存活堆 113MiB 时峰值已经到 230MiB，离上限只剩 26MiB。如果只看 pprof 的 inuse 数据，150MiB 远低于 256Mi，可真正决定峰值的是堆目标，不是存活堆。

GOMEMLIMIT=230MiB 让它活下来，GC CPU 涨到 23%

同样 150MiB 的存活集，加上 GOMEMLIMIT=230MiB：

GOGC=100，上限 1Gi（对照）1723443462.17.4%353.0MiB存活
GOMEMLIMIT=230MiB1702082286.523.0%240.7MiB存活 60 秒，oom_kill 0

表里除最后两列外单位都是 MiB，取的是 5 秒以后各采样的平均值。

设置 GOMEMLIMIT=230MiB 后，goal 从 344 压到 208，runtime 稳定在 228MiB 左右，Pod 峰值 240.7MiB，在 256Mi 以内。代价是 GC 次数从每秒 2.1 次升到 6.5 次，GC CPU 从 7.4% 升到 23.0%（两者都含空闲标记时间），换句话说是在用 CPU 换内存。

GOMEMLIMIT=400MiB 比容器上限还大，等于没设，结果和默认情况一样。

GOGC=off 加 GOMEMLIMIT 是官方 GC 指南里提到的组合：只在接近上限时才回收。当上限本身已经低于 2 倍存活堆时，它和 GOGC=100 加同样的上限表现几乎一样，因为 goal 本来就是被上限卡住的。存活堆小一些时差别才出来：

配置（存活集 60MiB）goalGC 次数/秒GC CPUPod 峰值
GOGC=100，不设上限135MiB5.56.5%136.6MiB
GOGC=off + GOMEMLIMIT=230MiB215MiB2.22.6%224.8MiB

GOGC=off 让堆一直涨到接近 230MiB 才回收，GC 次数少了六成，代价是常驻内存从 137MiB 涨到 225MiB。在内存配额按 limit 计费、而 CPU 紧张的场景，这笔交易是划算的；反过来就不划算。存活集 100MiB、都设 230MiB 上限时，GOGC=100 和 GOGC=off 的 goal 都是 212MiB，GC CPU 8.4% 和 8.7%，没有区别，因为两者算出的目标本来就差不多。

软上限：存活堆继续涨时，GC CPU 卡在 47% 然后被杀

GOMEMLIMIT 是软上限。文档写得很清楚：为了不让程序完全卡在 GC 上，运行时会把 GC 的 CPU 占用限制在大约 50%，超过之后宁可让内存越过上限。这意味着存活堆真的逼近上限时，它保不住进程。

我用 GOMEMLIMIT=230MiB、存活集 150MiB 起步、每秒再泄漏 1MiB 来模拟这个过程：

过程分三段：

时间livegoalGC 次数/秒GC CPU
1 至 4 秒164 至 166MiB209MiB6 至 7约 20%
16 至 28 秒184 至 199MiB198 至 208MiB9 至 1329% 至 42%
31 至 37 秒201 至 208MiB比 live 高 0 至 6MiB，35 秒起相等13 至 1447.0% 至 47.5%

存活堆越接近上限，goal 和 live 之间的空间越小，每分配一点就要触发一次 GC。从第 31 秒起，GC CPU 停在 47% 左右不再往上。我推测这是 CPU 限制器在起作用（文档说它把 GC 限制在约 50%）：GC 不能再快了，堆只能往上漫。不过这个 47% 含空闲标记时间，限制器是否按同一口径计算，我没有在文档里找到说明，所以这一条标为「推测」。第 37 秒最后一行日志之后，Pod 以 OOMKilled 137 结束（08:36:06 启动，08:36:43 结束）。

这次实验里垃圾产生速度是限速的 300MiB/s，CPU 上限 2 核还有余量，所以业务吞吐没有掉下来，表现为 GC CPU 一路上涨。如果不限速，同样的配置在第一次采样之前就被杀了。线上服务大多是后一种情况：请求不会因为 GC 忙就变少。

为了看清 GC 抢 CPU 对业务的影响，我另做了一组不限速的吞吐测试：存活集 120MiB，容器上限放宽到 1Gi，只改 GOMEMLIMIT：

两点值得注意。第一，上限从“不设”收到 230MiB，分配吞吐掉了 64%，而 GC CPU 只从 39% 升到 45%。这个指标已经包含辅助标记（mark assist）的时间，所以吞吐掉得比 GC CPU 涨得多的原因我没有拆开测，推测是 GC 周期变密后写屏障一直开着、分配更多走慢路径，这一条标为「推测」。第二，230MiB 及以下时 runtime 稳定在 255 至 275MiB，全都超过了设定值，软上限在这里看得很清楚。这组跑在 1Gi 的容器里，所以没有被杀；换成 256Mi 就是 OOMKilled。

堆外内存不在 GOMEMLIMIT 的账上

GOMEMLIMIT 只管 Go 运行时自己分配的内存。runtime/debug.SetMemoryLimit 的文档列出了不计入的部分：二进制文件本身的映射、其他语言（cgo）管理的内存、操作系统代程序持有的内存。我用 syscall.Mmap 申请 60MiB 并写满，模拟 cgo 库或 mmap 文件缓存：

start go=go1.27.4 NumCPU=26 GOMAXPROCS=2 GOGC="" GOMEMLIMIT="230MiB" memlimit=230MiB cpu.max="200000 100000" memory.max="268435456"
live set of 150 MiB (ptr=true) ready at t=0.13s
t= 0.23s live= 153MiB goal= 210MiB runtime= 194MiB gc=     4 (+  10/s) gcCPU= 31.2% churn=  298MiB/s cg.cur=254MiB cg.peak=254MiB
t= 0.34s live= 153MiB goal= 210MiB runtime= 196MiB gc=     4 (+   0/s) gcCPU=  0.0% churn=   28MiB/s cg.cur=255MiB cg.peak=255MiB
t= 1.03s live= 153MiB goal= 210MiB runtime= 197MiB gc=     4 (+   0/s) gcCPU=  0.0% churn=    9MiB/s cg.cur=255MiB cg.peak=255MiB

Go 运行时认为自己只用了 197MiB，离 230MiB 还很远，所以不会加紧回收；cgroup 看到的是 255MiB。这时分配速度从 298MiB/s 掉到 9MiB/s，连采样本身也停了：1.03 秒那行之后的约 9 秒里程序一行都没打出来，所以 9MiB/s 是按被拉长的间隔算的。我推测进程被内核的直接回收拖住了，但没有采 memory.stat 或 PSI，这一条标为「推测」。大约 10 秒后 OOMKilled。

如果服务里有 cgo、大块 mmap 或者依赖库自带的内存池，GOMEMLIMIT 要从容器上限里先扣掉这部分，再留余量。

用 downward API 注入 GOMEMLIMIT，divisor 写错会让 GC 空转

把 GOMEMLIMIT 写死在镜像或 Deployment 里，改 limit 时容易忘记同步。常见做法是用 downward API 从容器自己的 limits.memory 读出来。这里有个容易踩的坑。

Downward API 那篇笔记提到过 divisor 的取整规则。对内存来说：

写法注入的值Go 解析结果实测
不写 divisor268435456256MiB（纯数字按字节）存活 60 秒，峰值 249.5MiB
divisor: 1Mi256256 字节GC 每秒 14 至 17 轮、CPU 46%，约 8 秒后 OOMKilled
divisor: 1Mi 存进 MEM_MIB，再写 GOMEMLIMIT: $(MEM_MIB)MiB256MiB256MiB约 19 秒后 OOMKilled

divisor: 1Mi 是最自然的写法，因为人习惯以 MiB 为单位。可 GOMEMLIMIT 接受的格式是“数字加可选单位后缀”，没有后缀就按字节解释，于是上限变成了 256 字节：

截图下半部分就是这个场景：GOMEMLIMIT="256"，memlimit=0MiB。程序启动 0.89 秒时已经做了 771 轮 GC，到 7.71 秒是 864 轮，平均每秒约 14 轮（另一次 1 秒采样的运行是每秒 16、17 轮），GC CPU 一直在 46% 左右。它并没有立刻崩，存活堆 167MiB 时 runtime 只有 182 至 197MiB，看起来比正常配置还省内存。但第 7.71 秒的最后一行里 runtime 突然到了 235MiB，同一行分配速度是 1099MiB/s，随后 Pod 被杀。

1099MiB/s 是我的限速器补偿造成的：GC 忙的时候分配被拖慢，限速器发现落后于 300MiB/s 的目标，就会连续补分配。我推测真实服务里请求积压后的突发也是类似效果，而 GC 已经满负荷，没有能力再收紧。这一点没有进一步验证，标为「推测」。

第三行同样是 256MiB，却在 19 秒左右被杀（Pod 级 oom_kill 2），而不写 divisor 的那次活过了 60 秒。两次的上限完全相同，cg.peak 都到过 249MiB 左右，一次被杀，一次没有。两次的差别我认为只是时机不同，但能确定的是 GOMEMLIMIT 设成和 limit 一样大没有余量。我推测把它推过线的是 Go 运行时之外的那点内存，比如二进制映射和内核代程序持有的内存，这一条没有单独测量。

我最后选的写法是先取 MiB，再乘一个比例。Kubernetes 的环境变量展开不支持算术，所以比例要么在启动脚本里算，要么在程序 main 开头用 debug.SetMemoryLimit 按 memory.max 设置。我这次没有测 automemlimit 之类的库。

GOMAXPROCS：决定行为的是 go.mod 的 go 版本，不是工具链

Go 1.25 起，GOMAXPROCS 默认会参考 cgroup 的 CPU 上限，此前它只看主机的逻辑 CPU 数。这次我想确认的是：用新工具链编译老项目，会不会自动生效。

我构建了三种镜像，在 CPU limit 为 500m、1、1.5、2、4 核的 Pod 里各启动一次，只打印启动信息：

镜像500m11.524
go1.24.13 构建2626262626
go1.27.4 构建，go.mod 写 go 1.242626262626
go1.27.4 构建，go.mod 写 go 1.2522224

在 Docker 里用 --cpus 测了 1、1.5、2、4 核（没有测 0.5 核），结果一致。

原因在 GODEBUG 文档 里：新行为由 containermaxprocs 和 updatemaxprocs 两个 GODEBUG 开关控制，主模块 go.mod 的 go 行低于 1.25 时，它们的默认值是 0，也就是保持旧行为。所以只升级 CI 里的 Go 版本没有用，go.mod 的那一行才算数。

另外两个细节：

  • 500m 得到的是 2 而不是 1。runtime 文档写明按 ceil(quota/period) 取整，且在 CPU 数不少于 2 时下限是 2。
  • 1.5 核得到 2，向上取整。

GOMAXPROCS 也会影响内存。我在 CPU limit 2、内存 limit 1Gi 的 Pod 里跑不限速的负载（存活集 120MiB）：

配置GOMAXPROCS结果Pod 峰值
go.mod 1.2426约 4 秒 OOMKilled，3.11 秒时 live 346MiB、runtime 924MiB1024MiB
go.mod 1.25，环境变量 GOMAXPROCS=2626约 3 秒 OOMKilled
go.mod 1.252存活 30 秒970.6MiB
go.mod 1.24，GODEBUG=containermaxprocs=12存活 30 秒892.3MiB

GOMAXPROCS=26 的两组 GC CPU 只有 3.1% 左右（按 26 个 P 算），但存活堆在 3 秒内从 172MiB 跳到 346MiB 左右，堆目标随之翻倍，1Gi 都不够用。几组数字排除了两个直觉上的解释。一是 CPU 限流：Pod 级 cpu.stat 里 nr_throttled 0，usage_usec 约 4.27 秒，跑了约 4 秒，平均只用了 1 个核左右，2 核的配额没有用满。二是 GC 周期被拉长：26 个 P 时每秒 14、15 轮 GC，和 2 个 P 时差不多；GC 占用的绝对 CPU 也接近，3.1% × 26 和 40% 左右 × 2 都约是 0.8 个核。存活堆为什么在第 3 秒突然翻倍，我没有查清楚。能确定的是 GODEBUG=containermaxprocs=1 可以让 go.mod 还停在 1.24 的项目用上新行为，效果和升级 go.mod 一样。

这组实验每种配置只跑了一次，而且 GOMAXPROCS=2 的两次峰值也到了上限的 87% 至 95%，余量并不大。能说的是：在这组单次实验里，GOMAXPROCS 偏大的配置更早 OOM。go.mod 停在 1.24 的服务，即使 CPU limit 只有 2 核，运行时也会按 26 个 P 来安排 GC。

CPU 限流本身的现象在 探针与资源限制 里写过，Pod 的 QoS 等级对 OOM 时谁先被杀的影响见 QoS。

几个让我意外的地方

  • 默认 GOGC 下真正决定峰值的是堆目标。存活 113MiB 时 Pod 峰值已是 230MiB，监控里只看 inuse 会严重低估。
  • GOMEMLIMIT 设成和容器 limit 一样大，同样的值一次活过 60 秒，一次 19 秒被杀，没有稳定的结果。
  • 在 GOMEMLIMIT 卡住的区间里，GC CPU 数字涨得不多（39% 到 45%），分配吞吐却掉了 64%，只看 GC CPU 指标会以为影响不大。
  • downward API 加 divisor: 1Mi 的错误不会让程序立刻崩，反而让内存曲线看起来更低，只有 GC 次数（每秒 14 至 17 轮）和 CPU 能暴露它。
  • 升级工具链不会自动启用容器感知的 GOMAXPROCS，要改 go.mod。

落地清单

根据这些数据，我现在给 Go 服务配内存时按这个顺序检查：

  1. 先量存活堆，按 存活堆 × (1 + GOGC/100) 估算默认峰值。超过 limit 的 80% 左右就该设 GOMEMLIMIT 或者加 limit。80% 是经验值，这次没有逐档测；存活 113MiB 那次峰值到了 limit 的 90%，也活了下来。
  2. GOMEMLIMIT 留出余量，比如 limit 的 90%。这次只测了两档：256Mi 下 230MiB（90%）可以长期运行，256MiB（100%）不稳定。
  3. 有 cgo、mmap 这类 Go 堆之外的内存时，先从 limit 里扣掉，再算比例。
  4. 用 downward API 注入时不要单独用 divisor: 1Mi。要么不写 divisor 拿字节数，要么拼上 MiB 后缀，要么在程序里读 memory.max 自己设置。
  5. 设了 GOMEMLIMIT 后监控 /gc/cycles/total:gc-cycles 的增速和 GC CPU。GC 次数持续上涨、GC CPU 接近 50%，说明存活堆已经逼近上限，该扩容或查泄漏，不要指望它自己恢复。
  6. 想少做 GC、内存又有富余时，可以试 GOGC=off 加 GOMEMLIMIT，但它只在存活堆远小于上限时才有区别。
  7. 检查 go.mod 的 go 行。低于 1.25 时，要么升级它，要么加 GODEBUG=containermaxprocs=1，否则 GOMAXPROCS 还是主机核数。
