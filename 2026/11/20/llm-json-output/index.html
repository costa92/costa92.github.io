Ollama 结构化输出实测：schema 管得住格式，管不住对错

 costalong  2026-11-20  AI 本地大模型 AI 工程实践

阅读次数:

让模型返回程序能直接用的 JSON，常见的做法有三种：只在提示词里要求、给 Ollama 传 format: "json"、传一份 JSON Schema 做结构化输出。一般认为第三种最稳，约束了就不会错。这次在自己的 RTX 3060 上，用 36 条手写的客服消息、四个本地模型和 MiniMax 的托管接口跑了 2200 多次抽取，结果有几处和这个说法对不上：

  • schema 约束保证的是「能解析、结构对」，不是「内容对」。提示词里已经写清字段时，温度 0 下 format: "json" 和 format: <schema> 的输出在四个本地模型上 36 条全部逐字相同，字段准确率 95.8% 到 97.7%，一个点都没变。只靠提示词的那组，解析失败全是因为模型套了一层 ```json 代码块，剥掉以后同样 100% 能解析。
  • 约束会把模型逼成编造。我把 schema 里的 null 去掉（days_waiting 只允许整数），qwen2.5-coder:7b 在 25 个本该为空的位置全部填了 0，14 个没有署名的消息把顾客名填成字符串 "null"。四个本地模型的 6 字段全对率从 75%～86% 掉到 17%～22%，而 schema 校验依然 100% 通过。
  • MiniMax-M3 接受 response_format: json_schema，会校验 schema 本身的写法，但不按它约束输出：提示词里不写字段时，36 次回答没有一次符合 schema。默认返回的 content 里还带着 <think> 段，直接 json.loads 36 次只成功 1 次。

任务：36 条客服消息抽成 7 个字段

我自己写了 36 条短消息，中英文都有，形式包括客服邮件、聊天记录和两行日志。每条要抽成下面这个对象：

SCHEMA = {
    "type": "object",
    "properties": {
        "order_id": {"type": ["string", "null"]},
        "customer": {"type": ["string", "null"]},
        "intent": {"type": "string", "enum": ["refund", "exchange", "cancel", "shipping", "other"]},
        "items": {"type": "array", "items": {
            "type": "object",
            "properties": {"sku": {"type": "string"}, "qty": {"type": "integer"}},
            "required": ["sku", "qty"], "additionalProperties": False}},
        "urgent": {"type": "boolean"},
        "days_waiting": {"type": ["integer", "null"]},
        "summary": {"type": "string"},
    },
    "required": ["order_id", "customer", "intent", "items", "urgent", "days_waiting", "summary"],
    "additionalProperties": False,
}

前 6 个字段有人工标注，summary 是自由文本，不计分，只用来考察转义：好几条消息里带双引号，比如 The box was labeled "FRAGILE - this side up"。故意埋了几类难点：

  • 数字写成单词：three KB-204、twelve SOCK-5、two weeks（应为 14）、十天了、二十天前到的货。
  • 该为空的字段：没有订单号、没有署名、没提等了几天。
  • 关键词陷阱：Please don't cancel my order 40500 的意图不是 cancel。
  • 嵌套数组：一条消息里有 3 个 SKU，各自带数量。
  • 两条日志行，例如 order=73318 user="R. Gupta" action=cancel items=[MUG-12:1,CBL-3:4] priority=high。

提示词逐条说明了每个字段的含义，包括「没有就填 null」「数量没写就是 1」「只有明确要求才算 urgent」。打分分四层，每层比上一层严格：

指标含义
直接解析json.loads(content) 成功，什么都不处理
清理后解析去掉 <think> 段和 ``` 代码块，再取第一个 { 到最后一个 }
schema 合规用 jsonschema 按上面的 SCHEMA 校验
字段准确率 / 全对率6 个字段和标注逐个比对；全对率是 6 个字段都对的比例

比对规则很宽松：订单号去掉 #，名字不分大小写，SKU 转大写。两条有歧义的样本我标了多个可接受答案，比如 Dr. Helen Ward 和 Helen Ward 都算对。

请求 Ollama 时只改 format，其余参数相同，温度 0，num_predict 512：

body = {"model": model, "stream": False,
        "options": {"temperature": temp, "num_predict": num_predict},
        "messages": [{"role": "system", "content": SYSTEM},
                     {"role": "user", "content": build_prompt(arm, text)}]}
if fmt == "json":
    body["format"] = "json"
elif fmt == "schema":
    body["format"] = schema

每个模型依次加载，跑完卸载，GPU 上同一时间只有一个模型。

只靠提示词时，qwen2.5-coder:7b 和 gemma4 每一次都把 JSON 包在 ```json 代码块里，3b 是 36 次里 32 次，llama3.1:8b 一次都没有。这是格式问题，不是能力问题：剥掉代码块以后四个模型都是 100% 可解析、100% 符合 schema。

更关键的是后两组的关系。我逐条比对了原始文本：四个本地模型的 format: "json" 和 format: <schema> 输出 36 条全部逐字相同。提示词已经把字段讲清楚时，模型本来就会按这个结构写，schema 约束在温度 0 下一个 token 都没改。只靠提示词那组和前两组的 6 个计分字段，7b、llama3.1:8b 也是 36 条全同；3b 有 2 条的 intent 不一样，一条变对一条变错，准确率相同。推测是因为开头多了一段 ```json，后面的上下文跟着变了。

剩下的错误全是内容错误，换哪种 format 都一样：

  • Please don't cancel my order 40500：四个本地模型在不思考的情况下都判成 cancel。
  • Cancel!!! Wrong address on 55120：两个 qwen 模型把订单号填成 null，大概是没认出光秃秃的 55120 是订单号。
  • Do you ship to Iceland? 和 你们周末发货吗？：所有模型（包括 MiniMax-M3）都判成 shipping，我标的是 other。我给 shipping 的定义是「delivery status or shipping changes」，这两句确实可以算进去，算标注和提示词的歧义，不算模型错。每个模型的 intent 错误里都有这两条。

gemma4 的输出 token 少了三成，原因很直接。只靠提示词时它按多行缩进格式写，加了 format 后变成单行紧凑 JSON：

model=gemma4:latest arm=prompt tag=main case=7 temp=0.0 rep=0 done_reason=stop eval_count=110
model=gemma4:latest arm=json tag=main case=7 temp=0.0 rep=0 done_reason=stop eval_count=76
content="{\"order_id\": \"45510\", \"customer\": \"Mike O'Neil\", \"intent\": \"refund\", ...

所以对 gemma4 来说，加约束反而让中位耗时从 2.25 s 降到 1.12 s。其余三个模型输出几乎一样，生成速度差别在 3% 以内（3b 约 120 到 123 tok/s，7b 约 64 tok/s，llama3.1:8b 约 62 tok/s）。在这个规模的 schema 上，约束本身没有可见的开销。

温度 0.8：约 4% 的结构错误被 schema 全部挡住，准确率没变

只靠提示词时，3b 有 4 次结构不合规：一次把 intent 写成枚举之外的 delivery，三次 intent 直接是 null；llama3.1:8b 有 5 次，主要是 summary 写成了 null。schema 把这 9 次都挡住了。可准确率没跟着涨，3b 加约束后全对率反而低了 5.6 个百分点。每格 108 个样本，这个差距在噪声范围内，我不把它解读成「约束让 3b 变差」，能确定的只是「约束没让它变好」。

不在提示词里描述字段：结构全对，内容大半是错的

Ollama 文档里写着「It is ideal to also pass the JSON schema as a string in the prompt to ground the model’s response」。我想知道不这么做会怎样，就把提示词换成一句话「Extract the order information from this customer message as JSON.」，分别配 format: "json" 和 format: <schema>：

模型方式schema 合规字段准确率全对率
qwen2.5-coder:3bformat: json0%12.0%0%
format: schema100%75.9%13.9%
qwen2.5-coder:7bformat: json0%11.1%0%
format: schema100%72.2%8.3%
llama3.1:8bformat: json0%4.6%0%
format: schema100%71.3%2.8%
gemma4（think=false）format: schema100%84.3%22.2%

format: "json" 只保证是合法 JSON，键名由模型自己取。同一条消息，7b 给出的是 order_number、product、customer_name、request，程序一个字段都读不到。

加上 schema 后，键名和类型都对了，内容却错得很多。schema 只告诉模型「days_waiting 是整数或 null」，没说什么时候该填 null，没提等待天数的 25 条消息里，7b 有 19 条填成 0、只有 5 条填了 null；urgent 没有定义，它把 36 条里的 24 条判成 true（标注里只有 7 条是）；customer 填了 "unknown"、"未提供"、"Refund me"、"I"。同一条台灯消息，提示词描述了字段时 7b 填的是 "days_waiting": null，只靠 schema 时变成 "days_waiting": 0。

字段名本身就是一种提示，它能让模型写出 order_id 而不是 order_number；字段的语义（什么时候为空、什么算紧急、两周等于几天）只能靠提示词说清楚。

去掉 null 之后，模型开始编

这组是我最想验证的。很多人写 schema 时习惯把字段都设成必填、单一类型，比如 days_waiting: {"type": "integer"}。我把 order_id、customer、days_waiting 三个字段的 null 去掉，提示词保持不变，里面仍然写着「没有就填 null」：

模型全对率（可为 null）全对率（不可为 null）days_waiting 准确率customer 准确率
qwen2.5-coder:3b75.0%19.4%100% → 30.6%97.2% → 61.1%
qwen2.5-coder:7b75.0%16.7%100% → 30.6%100% → 61.1%
llama3.1:8b83.3%22.2%100% → 30.6%94.4% → 58.3%
gemma4（think=false）86.1%22.2%100% → 30.6%100% → 61.1%

36 条消息里，标注为 null 的位置一共 44 个（days_waiting 25 个、customer 14 个、order_id 5 个）。模型在这些位置填了什么：

== qwen2.5-coder:3b  null slots=44
   24  days_waiting=0
    4  customer="null"
    3  order_id=""
...
    1  customer="Just wanted to say the mug is lovely, thanks!"
...
== qwen2.5-coder:7b  null slots=44
   25  days_waiting=0
   14  customer="null"
    5  order_id="null"
...
== gemma4:latest  null slots=44
   21  days_waiting=0
   14  customer="null"
    5  order_id="null"
    4  days_waiting=-1

7b 和 gemma4 的做法算是有迹可循：数字填 0 或 -1，字符串填 "null"。3b 更糟，把整句消息当成顾客名，还有 "Customer Name"、"收件人"、"Hi"。最直观的是那条只有一句夸奖的消息：

这些输出全部通过 schema 校验。程序拿到 "customer": "null" 至少还能做个字符串判断，"days_waiting": 0 就分不清是「当天」还是「没提」。约束把模型想写的 null 屏蔽掉之后，它只能挑一个合法的值，代价是错误从「解析失败」这种显眼的形式，变成了「看起来正常的错值」。

让模型先写理由：多花近一半 token，没换来准确率

还有一种流行做法：在 schema 第一个位置放一个 reasoning 字段，让模型先写几句分析再填答案。Ollama 的约束会按 properties 的顺序生成，我对比了 reasoning 放最前和放最后：

模型无 reasoningreasoning 在前reasoning 在后平均输出 token（无 / 在前）
qwen2.5-coder:3b75.0%69.4%69.4%89 / 147
qwen2.5-coder:7b75.0%80.6%77.8%86 / 127
llama3.1:8b83.3%86.1%83.3%74 / 109

表里是全对率。差距最多两条样本，在 36 个样本上说明不了什么。理由的内容也多是在复述题目，7b 对第一条写的是「The message contains an order number, customer name, intent for a refund, and a product code. No urgency or waiting time is mentioned.」，这些信息模型不写出来也知道。真正有效的是把「思考」交给模型自己的思考模式，见下一节 gemma4 的结果。

截断：约束救不了写到一半的 JSON

num_predict 设成 40 个 token（正常输出 70 到 90 个），三种方式、三个模型（gemma4 没跑这组）的可解析率都是 0：

model=qwen2.5-coder:7b arm=prompt tag=trunc case=7 temp=0.0 rep=0 done_reason=length eval_count=40
content="```json\n{\n  \"order_id\": \"45510\",\n  \"customer\": \"Mike O'Neil\",\n  \"intent\": \"refund\",\n  \"items\": [\n    {\n"
model=qwen2.5-coder:7b arm=schema tag=trunc case=7 temp=0.0 rep=0 done_reason=length eval_count=40
content="{\n  \"order_id\": \"45510\",\n  \"customer\": \"Mike O'Neil\",\n  \"intent\": \"refund\",\n  \"items\": [\n    {\n      \"sku"

约束决定的是「下一个 token 可以是什么」，不管还剩多少 token 预算，到了上限就直接停。gemma4 在这一点上更容易出事：它默认开启思考，思考内容也计入 num_predict。我在 8 条消息上用 format: <schema> 加默认思考、num_predict 512 跑了一遍，6 条的 content 是空字符串，2 条是写到一半的 JSON，done_reason 全是 length。HTTP 返回 200，没有任何报错。

把 num_predict 提到 4096 后，8 条全部正常结束，平均输出 685 个 token（思考加答案），8 条 6 个字段全对，包括关闭思考时判错的 Please don't cancel 那条。代价是中位耗时从 1.1 s 涨到约 10 s。8 个样本太少，我只能说思考修好了这一条，不能说它在全部 36 条上都更准。

程序里要检查 done_reason（OpenAI 兼容接口是 finish_reason），等于 length 时，不管有没有约束，输出都不可信。

MiniMax-M3：参数照收，约束不执行

MiniMax 的 OpenAI 兼容接口文档 参数表里没有 response_format，也没有把它列进「不生效」的参数。它的原生文本接口文档 写着 response_format「当前仅 MiniMax-Text-01 支持此参数」，而同一页的模型枚举里只有 MiniMax-M3.1-Flash 和 MiniMax-M3。文档说不清楚，我就直接测。

第一个请求就碰了壁：同一份 SCHEMA 原样传过去，返回 400：

它不接受 "type": ["integer", "null"] 这种 JSON Schema 标准写法。我写了个函数把类型数组改成 anyOf，之后请求都能返回 200。为了判断它到底有没有按 schema 约束输出，我用了和本地模型一样的方法：提示词里不写字段，只靠 schema。36 次回答里没有一次符合 schema，键名五花八门（order_number、customer_name、requested_action……），同一条消息还会出现嵌套的 item 和 issue 对象。在 Ollama 上，同样的写法 schema 合规率是 100%。

提示词写清字段时，MiniMax-M3 的内容准确率是这次最高的：

MiniMax-M3直接解析清理后解析schema 合规字段准确率全对率中位耗时
只靠提示词2.8%100%100%98.6%91.7%3.16 s
json_object0.0%100%97.2%98.1%88.9%3.38 s
json_schema（anyOf 写法）2.8%100%100%98.1%88.9%3.51 s
json_schema + reasoning_split100%100%100%98.6%91.7%3.47 s

两个现象：

  • 直接解析几乎全失败，原因是 content 开头是一段 <think>…</think>。文档里有个 reasoning_split 参数，设为 true 后思考内容挪到 reasoning_content 字段，content 只剩 JSON，36 次直接解析全部成功。
  • json_object 模式下有一次键名写坏了："days-ings":14。它的思考里写着「days-ings spelling key requested」，模型自己把字段名看错了。

MiniMax 这部分一共调用了 186 次。

这组数据的边界

样本量不大，主实验每格 36 条，温度 0.8 每格 108 条。相差一两条样本（3 到 6 个百分点）的差别我都没当成结论，比如 reasoning 字段的影响、温度 0.8 下 3b 加约束后全对率略降。站得住的结论是几处差距很大、而且在四个模型上方向一致的地方：去掉 null 后全对率掉 56～64 个百分点、不描述字段时全对率只剩 2.8%～22.2%、温度 0 下约束不改变任何输出。

schema 很小，7 个字段，嵌套只有一层。更复杂的 schema（几十个字段、深层嵌套、递归）下约束的速度开销和对模型的干扰可能完全不同，这次没测。生成速度上我看到的唯一差异是「不描述字段 + schema」那组每秒 token 数低了 10% 到 20%（7b 从 66.6 降到 57.7），推测是模型想写的 token 频繁被约束拒绝，采样器要多做几轮筛选，但两组的输出内容也不同，我没法把这两个因素分开。

标注是我一个人做的，shipping 和 other 的边界前面已经说过有歧义。MiniMax 的结论只针对 MiniMax-M3 这一个模型、2026 年 11 月 20 日的接口行为。

接进程序时的几条做法

  • 提示词里把每个字段的含义写清楚，尤其是「什么时候为空」。这是准确率的主要来源，约束替代不了它。
  • 用 Ollama 时加 format: <schema>。温度 0 下它不改内容，代价几乎为零，但能挡住升温后 4% 左右的结构错误，也省掉剥代码块的代码。
  • 允许为空的字段在 schema 里显式写成可为 null。不确定的字段宁可可空，必填加单一类型等于逼模型编一个值。
  • 拿到结果先看 done_reason / finish_reason，是 length 就当失败处理。思考模型要么关掉思考，要么给足输出上限：这次 gemma4 开着思考时单条最多用了 803 个 token，我设的上限是 4096。
  • 解析之后再用 jsonschema 或 Pydantic 校验一遍。托管接口上 response_format 收下了不代表生效，MiniMax-M3 就是例子；它的思考段要用 reasoning_split 分出去。
  • 结构对了不等于内容对。准确率要靠带标注的样本去测，schema 校验通过率不能当准确率用。
