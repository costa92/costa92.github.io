qwen2.5-coder:7b 写代码，温度 0 通过率反而最低：1200 次带测试的生成实测

 costalong  2026-11-20  AI 本地大模型 AI 工程实践

写代码时把温度调成 0，常见的理由是三条：最稳、可复现、通过率最高。这次在自己的 RTX 3060 上用 Ollama 跑了三个本地模型、再加 MiniMax 的托管接口，一共跑了近 1800 次生成，代码题都用隐藏单元测试判对错。结果和这三条理由各有一处对不上：

  • qwen2.5-coder:7b 在温度 0 时通过率 60%，是五档里最低的，温度 1.2 时 72.5%。差距几乎全来自两道题：温度 0 把模型锁在同一个错误答案上，8 次全错。另外两个本地模型没有这个规律，所以这不是「温度 0 普遍更差」，而是「温度 0 会把个别固定错误放大成必错」。
  • 温度 1.6 在本地看起来很安全，那是因为 Ollama 默认带着 top_k=40、top_p=0.9，而且截断发生在温度之前。把截断关掉，同样的 1.6 让 qwen2.5-coder:7b 的语法错误率从 1.2% 变成 92.5%。
  • 温度 0 在 Ollama 上大多数时候可复现，但 qwen2.5-coder:3b 对同一个提示词的第一次回答会和之后的回答不同；MiniMax-M3 在温度 0、固定 seed 下连续 5 次输出全都不一样，官方文档写明 temperature 传了也不生效。

MiniMax 我先试了几个模型名：MiniMax-M2 和 MiniMax-M2.1 返回 404，原文是 The model "MiniMax-M2.1" is no longer available. (2069)；MiniMax-M2.5、M2.7、M3 都能用。官方 OpenAI SDK 文档页只列了 MiniMax-M3.1-Flash 和 MiniMax-M3，所以主实验用 M3。

题目、判题和跑批脚本放在 blog-go-example/local-model-temperature，可以照着 README 复现。

判题脚手架：10 道题，隐藏测试，AST 去重

题目是我自己写的 10 个自包含函数：罗马数字、区间合并、括号匹配、RLE 解码、Top-K 词频、LRU 缓存、时长解析、螺旋矩阵、按宽度折行、版本号比较。每题有一组 assert，模型看不到。为了确认测试本身没写错，我先给每题写了参考实现跑一遍，10 题全部通过。

提示词统一是题面加一句英文要求：只回复一个 python 代码块，不要解释、示例和测试。请求 Ollama 时只改温度，其它参数保持默认，另外把 num_predict 限制在 1024：

def gen_ollama(model, prompt, temp, seed=None, extra=None):
    opts = {"temperature": temp, "num_predict": 1024}
    if seed is not None:
        opts["seed"] = seed
    opts.update(extra or {})
    r = post(OLLAMA, {"model": model, "stream": False, "options": opts,
                      "messages": [{"role": "system", "content": SYSTEM},
                                   {"role": "user", "content": prompt}]})

判题分三步：先剥掉 <think> 段，取第一个代码块；再用 ast.parse 判语法，同时把 AST dump 当作「规范化代码」，这样注释、空白和引号风格不同都算同一种解法；最后把代码和测试拼在一起，放进子进程跑。

def extract(text):
    text = re.sub(r"<think>.*?</think>", "", text, flags=re.S)
    m = re.findall(r"```(?:python|py)?\s*\n(.*?)```", text, flags=re.S)
    return m[0] if m else text

def run_tests(code, tests):
    with tempfile.NamedTemporaryFile("w", suffix=".py", delete=False) as f:
        f.write(code + "\n\n" + tests)
        path = f.name
    try:
        p = subprocess.run([sys.executable, "-I", path], capture_output=True, text=True, timeout=5)
        return p.returncode == 0, p.stderr.strip().splitlines()[-1:] if p.returncode else []
    except subprocess.TimeoutExpired:
        return False, ["timeout"]
    finally:
        os.unlink(path)

本地模型每个温度（0、0.4、0.8、1.2、1.6）每题跑 8 次，每个模型 400 次，三个模型依次加载，同一时间 GPU 上只有一个模型。MiniMax 每个温度（0、0.8、1.6）每题跑 5 次，共 150 次。整个实验调用 MiniMax 不到 200 次。

本地每格 80 个样本，标准误差在 5 个百分点左右，所以 3b 在 1.2 掉到 33.8%、1.6 又回到 50% 这种起伏，我不打算解读成规律。7b 那一行也要换个角度看：温度 0 下每题 8 次输出几乎一样，这 80 个样本实际上只相当于 10 道题各答一次。所以能站住的不是「60% 比 72.5% 低」这个百分比，而是逐题的证据：intervals 和 wrap 两题在温度 0 下 8 次全错，升温后每档都能做对一部分。

温度 0 相当于对每道题只做一次决定。intervals 这题，7b 的贪心答案是这样的：

def merge_intervals(intervals: list[list[int]]) -> list[list[int]]:
    if not intervals:
        return []
    
    intervals.sort()
    merged = [intervals[0]]

题面写了「不要修改输入列表」，它用了原地 intervals.sort()，8 次都一样，于是 8 次全错。温度一升，有些采样改用 sorted(intervals)。升温后的 32 个样本里有 23 个通过，全都用了 sorted(；没通过的 9 个都没用它。wrap 题也是同样的情况：贪心解在长度累加时多算了一个空格，行宽实际被限制在 width-1；1.2 下的采样换了写法，8 次里过了 7 次。

代价落在原本就会做的题上。semver 在温度 0 时 8/8，升温后掉到 4 到 6 次，其中有 9 次是语法错误，典型的一处是少了一个右括号：

a_parts = list(map(int, a.split('.')))
b_parts = list(map(int, b.split('.'))

所以温度是在两件事之间换：会做的题偶尔做坏，不会做的题偶尔做对。我把「8 次里至少过一次」的题数也统计了，这相当于 pass@8：

qwen2.5-coder:7b69999
llama3.1:8b68898

温度 0 下多跑几次没有意义，6 题就是 6 题。只要有测试能自动挑出对的那一份，多采样加一点温度明显更划算。

有两道题需要单独说明。duration（时长解析）三个本地模型 0/120，失败原因五花八门，比如 '5' 没有报错、'1m1h' 没有判成顺序错误；rle 里有一条测试把空格当作字符（'1 2!' 解码成 ' !!'），不少模型把它判为非法。这两题的边界条件比较多，但 MiniMax-M3 两题都是 15 次里过 14 到 15 次，说明题目可解。

3b 的括号题：换多少温度都绕不开同一个错

qwen2.5-coder:3b 有 10% 的语法错误率，五档温度都是 10%，几乎全部来自 brackets 这一题。我把 40 个样本里定义映射表的那一行抽出来统计：

12 bracket_map = {') : '(', '}': '{', ']': '['}
5 bracket_pairs = {') : '(', '}': '{', ']': '['}
4 matching_brackets = {') : '(', '}': '{', ']': '['}
3 mapping = {') : '(', '}': '{', ']': '['}
2 brackets = {'):'(', '}':'{', ']':'['}
...

变量名随温度变了七八种，')' 后面那个引号却几乎每次都丢，40 次里只有 1.6 那档的 1 次通过。这类错误不靠温度修。推测原因跟分词有关，') 加冒号这段字符串可能落在一个模型很少见到的 token 组合上，贪心和采样都偏向同一个错误续写；我没有去查 tokenizer 验证。7b 和 llama3.1:8b 这题都是 40/40。

多样性和速度

「不同解法数」是每题 8 个样本里 AST 不同的份数，取 10 题平均：

到 0.4 已经有五六种写法，0.8 以后基本每次都不一样，再往上加温度也换不来更多多样性。生成速度和温度无关，3b 在五档之间只差 1.5 tok/s。

MiniMax-M3 不管传什么温度，每题 5 次的原始输出都是 5 种，规范化后平均 3.7 到 3.8 种。三档温度的结果放在一起分不出差别。

显存是用 nvidia-smi 每秒采样取峰值，基线是桌面程序占的约 3.9 GiB：

加载耗时取的是每轮第一个请求返回的 load_duration。模型放在机械硬盘上，冷加载慢得很明显；3b 第二次加载时文件已经在页缓存里，只用了 1.25 s。7b 比体积更大的 llama 慢一倍多，我推测是 llama 的文件在页缓存里还留着一部分，没有清缓存复测。

MiniMax-M3 这边，单次请求墙钟时间中位 5.1 s、P90 10.2 s。它是推理模型，平均 501 个输出 token 里有 369 个是思考过程，而且 150 次回复的 content 里全部带着 <think> 段，不剥掉就没法直接执行。

高温为什么没崩：截断发生在温度之前

qwen2.5-coder:7b 在 1.6 还有 71% 的通过率，这和「温度高了就胡言乱语」的印象不符。我去 Ollama 的服务日志里看每个请求的采样参数：

我没有设置过 top_k 和 top_p，日志里是 40 和 0.9，和 Modelfile 文档 列的默认值一致。关键在顺序：top-k、top-p 先把候选砍到前 40 个、累计概率 0.9 以内，temp-ext 排在后面。温度只是在剩下的候选里把概率拉平，那些概率极低的乱码 token 早在截断时就去掉了。

验证方法很直接：传 top_k=0, top_p=1.0 关掉截断，num_predict 降到 512，每题跑 4 次：

qwen2.5-coder:3b默认截断33.8%10.0%50.0%10.0%
qwen2.5-coder:3b关闭截断50.0%27.5%0.0%95.0%

qwen2.5-coder:7b关闭截断52.5%12.5%7.5%92.5%

关掉截断后，1.6 基本全军覆没。3b 和 7b 写罗马数字（两者各自的第 1 次采样），写到一半是这样的：

所以「Ollama 上温度 1.6 也能写代码」只在默认 top_k/top_p 下成立。换到别的推理后端，或者通过 OpenAI 兼容接口只传 temperature、截断参数用的是另一套默认值，同一个温度可能就是另一种结果。比较不同平台的温度表现之前，要先确认截断参数是否一致。

温度 0 的可复现性：本地基本可靠，3b 对每个提示词的第一次回答例外

三个本地模型在温度 0 下每题 8 次，7b 和 llama3.1:8b 全部 10 题都是 8 次逐字相同。3b 有 3 题是这个模式（字母表示第几种不同的原始输出，按运行顺序排列）：

qwen2.5-coder:3b     roman      raw=ABBBBBBB pass=PPPPPPPP
qwen2.5-coder:3b     brackets   raw=ABBBBBBB pass=........
qwen2.5-coder:3b     spiral     raw=ABBBBBBB pass=PPPPPPPP

只有第一次不一样。日志里能看到 Ollama 0.35 带了提示词缓存（prompt cache is enabled, size limit: 8192 MiB），同一个提示词第二次进来时只重算最后一个 token：

slot   operator(): id  0 | task 15559 | cached n_tokens = 138, memory_seq_rm [138, end)

为了确认跟缓存有关，我重新加载 3b，每题分两组跑：连续发 6 次同一题；再把这一题和另一道题交替发 6 次。结果：

roman repeat ABBBBB interleave AAAAAA repeat[0]==interleave[0] False
brackets repeat ABBBBB interleave AAAAAA repeat[0]==interleave[0] False
spiral repeat ABBBBB interleave AAAAAA repeat[0]==interleave[0] False
wrap repeat AAAAAA interleave AAAAAA repeat[0]==interleave[0] True

交替组 6 次一致，并且和连续组的第 2 次以后完全相同。所以分界点是「这个提示词是不是第一次被完整计算」，不是前一个请求是什么。差异也不只是改个变量名，roman 题第一次用 for 循环逐位加减，之后改成 while 循环，遇到减法组合时一次跳两位，算法写法变了，只是两种都能通过测试。推测原因：第一次是整段提示词批量前向计算，之后是单 token 前向，两条路径的浮点累加顺序不同，logits 有微小差别，在两个 token 概率几乎相等的位置上贪心选择就翻了。7b 同样的实验 4 题全部 AAAAAA，没有复现这个现象。

seed 的作用也测了，每组 6 次：

roman seed None temp 0.0 AAAAAA
roman seed None temp 0.8 ABCDEF
roman seed 42 temp 0.0 AAAAAA
roman seed 42 temp 0.8 AAAAAA

7b 和 3b 结果相同。在 Ollama 上，温度 0.8 加固定 seed 可以完全复现，这在做 A/B 对比时很好用：既保留采样，又能重放某一次结果。

MiniMax：temperature 和 seed 都不起作用

MiniMax 的接口对 temperature 不做校验，我用 MiniMax-M2.5 传 0、1.2、1.6、2.0 都返回 200。但输出看不出任何区别，温度 0 下同一题连续 5 次：

MiniMax-M3 roman temp 0.0 seed 42 raw ABCDE code ABCDE
MiniMax-M3 wrap temp 0.0 seed 42 raw ABCDE code ABBCB
MiniMax-M2.5 roman temp 0.0 seed None raw ABCDE code ABCDE
MiniMax-M2.5 wrap temp 0.0 seed None raw ABCDE code ABCDE

加了 seed=42 也是 5 种输出。查 MiniMax 的 OpenAI SDK 文档，temperature 那一行写的是「暂不支持指定，传入的值不会生效。MiniMax-M3.1-Flash 和 MiniMax-M3 固定使用 1」，top_p 固定 0.95，seed 文档里没有提到。也就是说，接口不报错，参数却被静默忽略了。好在 M3 本身够强，150 次里 148 次通过，温度固定在 1 也不影响结果。

还有一件跟温度无关、但实际踩到的事：MiniMax-M2.5 有一次请求超过了我设的 300 秒读超时（The read operation timed out），其余 M2.5 请求的中位耗时只有 3.7 s。生产环境调用要设超时和重试。

一个跟温度无关的坑

做实验时还撞上了另一个问题：超过上下文长度的提示词会被 Ollama 静默截断，HTTP 不报错，写在开头的任务说明被砍掉，模型只能瞎答。这件事影响面比温度大，我单独补了实验写成另一篇。

这组数据能说明什么，不能说明什么

样本量不大。本地每个模型、每档温度 80 个样本，相差 5 个百分点以内的变化都可能只是噪声；关闭截断那组每格只有 40 个样本。我敢下结论的只有几处差距明显的地方：7b 从温度 0 到升温后差了 7.5 到 12.5 个百分点，而且集中在 intervals、wrap 两题；关闭截断后 1.6 档的语法错误率从个位数跳到九成以上。

题目全是单函数、几十行以内的小题，提示词也只有一种写法。多文件修改、需要读上下文的真实任务里，温度的影响会不会更大，这次没有测。量化版本用的是 Ollama 拉取时的默认 tag，没有对比不同量化精度。

MiniMax 这边只跑了 150 次主实验，而且文档已经说明温度不生效，所以它在表里只是作为参照：一个温度被固定在 1 的强模型。它每题 5 次、本地每题 8 次，多样性数字不能直接横向比较。

另外，「温度 0 不是最准」主要对 7b 成立。llama3.1:8b 只在 0.4 时比温度 0 高 7.5 个百分点，0.8 以上就持平或略低；3b 起伏很大（33.8%～50%），看不出单调的规律。如果拿不到测试、只能信第一次输出，升温带来的是另一种风险：7b 在 1.2 时 semver 只有 4/8，原本稳定做对的题变成了掷硬币。

落到参数上

  • 只生成一次、没有测试兜底：用温度 0。会做的题稳定做对，semver 这类题升温后出现的低级语法错误也不会有；代价是 intervals 这类题会稳定做错。0.2 这样的低温这次没有测，它能不能两头兼顾只是推测。
  • 有单元测试或能自动验证：升温到 0.4～0.8 采样 5 到 8 份，挑能过测试的那份。7b 的「至少过一次」从 6 题升到 9 题。
  • 头脑风暴、要多种写法：0.8 已经接近每次都不同，再往上加温度换不来更多多样性。
  • 温度超过 1 时先确认 top_k/top_p 有没有生效。Ollama 默认值替你兜着底，关掉后 1.6 基本只剩乱码。
  • 要可复现，温度 0 之外再固定 seed，并记下模型版本。小模型对每个提示词的第一次回答可能和之后不同（实验显示和提示词缓存有关），回归测试里每个提示词先跑一次再比对。
  • 托管接口先查文档，看 temperature 是否真的生效。MiniMax-M3 静默忽略 temperature 和 seed，靠它做确定性输出是做不到的。
  • 往本地模型塞长提示词前，先看上下文截断那篇。
