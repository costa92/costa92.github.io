系统提示词开头加个时间戳，Ollama 首字延迟从 37ms 涨到 3 秒

 costalong  2026-11-20  AI 本地大模型 AI 工程实践

文章字数:   4k
阅读次数:

一份 6269 token 的系统提示词，在 RTX 3060 上用 qwen2.5-coder:7b 处理一遍要 2.9 秒。连续发两次一模一样的请求，第二次的提示词处理只要 16ms，首字延迟 37ms：Ollama 把上一次请求算好的 KV 缓存留着，下一次请求只要开头的 token 对得上，就直接复用。

这件事 Ollama 不需要任何配置就会做，缓存失效时接口也不会给任何提示。在系统提示词开头写一句”当前时间：…”，首字延迟就从 37ms 变成 3.1 秒。下面是我在本机挨个试出来的几种写法，以及它们各自的代价。

测试环境和测法

项目值
Ollama0.35.0，systemd 服务，OLLAMA_NUM_PARALLEL=1，OLLAMA_KEEP_ALIVE=5m，没开 Flash Attention
推理后端Ollama 自带的 llama-server，llama.cpp 版本 b11081（v0.35.0 源码里的 LLAMA_CPP_VERSION）
硬件RTX 3060 12 GiB（驱动 580.178.04），i7-14700KF，61 GiB 内存
模型qwen2.5-coder:7b 为主，关键场景用 llama3.1:8b 复测
上下文请求里 num_ctx: 8192，/v1 那组除外

系统提示词是一份程序生成的”值班手册”：80 条格式相同、内容随机的处置规则，qwen2.5-coder 分词后 6269 个 token，llama3.1 是 6733 个。用户问题固定为一句话。每次请求 temperature: 0、seed: 1、num_predict: 24，只生成 24 个 token，让时间主要花在提示词上；多轮和工具循环两组为 60。

客户端用 Python 直接发流式请求，记录四个数：

  • prompt_eval_count 和 prompt_eval_cached_count：提示词总 token 数和其中命中缓存的数量。
  • prompt_eval_duration：提示词处理耗时。
  • load_duration：加载模型的耗时。
  • 首字延迟（TTFT）：从发出请求到收到第一段正文的时间，在客户端测量。

除特别说明，每种情况连续跑 5 次（个别 6～7 次），下文给中位数，括号里是范围。测试期间这台机器的 CPU 上还跑着另一个实验，负载在 12～15 左右，GPU 上没有别的推理任务，每批测试前用 nvidia-smi 确认过。提示词处理本身在 GPU 上，受影响应该不大，但首字延迟里的几毫秒抖动不必当真。

测试脚本放在 blog-go-example/ollama-prefix-cache，可以照着 README 复现。

先说一个读数上的坑：prompt_eval_count 不能用来判断有没有命中缓存。命中时它照样报 6269，因为 Ollama 把缓存命中数和实际计算数加在一起返回（v0.35.0 的 llm/llama_server.go 里 promptEvalCount() 返回 CacheN + PromptN）。要看的是 0.35.0 响应里多出来的 prompt_eval_cached_count，或者 prompt_eval_duration。/v1 接口对应的是 usage.prompt_tokens_details.cached_tokens。

缓存命中和没命中差多少

情况（qwen2.5-coder:7b，6269 token）命中 token提示词处理加载首字延迟
完全相同的请求再发一次626816ms（16～16）1ms37ms（36～43）
模型刚加载，缓存为空02941ms（2930～2959）1819ms（1797～1916）4775ms（4761～4904）

命中时最多是 6268，比总数少 1：最后一个 token 总要重新算一次，才能拿到生成第一个字所需的输出。缓存为空时，提示词处理按每秒约 2130 个 token 算，6269 个就是 2.9 秒。模型文件已经在系统页缓存里，加载只要 1.8 秒；第一次从磁盘读时要久得多，后面会说到。

在一个槽位内，规则只有一条：llama-server 拿新请求的 token 序列和缓存里的序列从头比较，取最长公共前缀，前缀以内直接复用，从第一个不同的 token 起全部重算。所以要问的不是”改了什么”，而是”第一处改动离开头有多远”。

时间戳放在哪：开头 3.1 秒，结尾 69ms

很多程序会往系统提示词里塞当前时间、请求编号或用户名，好让模型”知道现在几点”。我在每次请求里生成一个精确到微秒的时间和一个随机请求号，分别放在三个位置：

时间戳位置（qwen2.5-coder:7b，6312 token）命中 token提示词处理首字延迟
系统提示词开头24（3～24）2914ms（2912～2926）3099ms（3054～3108）
系统提示词结尾6255（6233～6257）44ms（43～51）69ms（62～75）
用户消息开头6262（6239～6262）42ms（42～52）65ms（60～73）

放在开头时只能命中 3～24 个 token，也就是模板开头的标记，加上时间字符串里相邻两次请求恰好相同的那一小段。剩下 6000 多个 token 每次都要重算，首字延迟是完全命中时的 80 多倍。放到结尾或用户消息里，变化的只有最后几十个 token，比完全命中多 30ms 左右。

llama3.1:8b 上结果一样：开头 3547ms（3543～3558），结尾 45ms（44～53），用户消息里 44ms（43～55）。

时间戳只是最常见的一种。凡是每次请求都会变的东西，比如会话 ID、用户名、”今天是星期几”、随机挑选的示例，只要写在系统提示词前面，效果都一样。

工具定义：顺序变了要重算近 800 个 token，llama3.1 每轮都要

给请求加上 8 个工具定义后，提示词变成 7084 个 token。每次请求把工具列表随机打乱一下：

工具列表（qwen 7084 / llama3.1 7584 token）命中 token提示词处理
qwen2.5-coder:7b，顺序固定708317ms（17～17）
qwen2.5-coder:7b，每次打乱6277459ms（451～461）
llama3.1:8b，顺序固定758319ms（19～19）
llama3.1:8b，每次打乱6806481ms（480～491）

工具这一组我只看提示词处理时间，不看首字延迟：模型返回的是工具调用，正文要等调用解析完才有，首字延迟测出来没有意义。

qwen2.5-coder 的模板把工具定义放在系统提示词后面，所以前面 6277 个 token 还能复用，只重算工具那 800 来个 token。按 Python dict 遍历顺序、或者按插件注册顺序拼工具列表的程序，顺序通常是稳定的；从集合里取、或者按”相关度”动态挑选工具的程序就不一定了。

真正的坑在 llama3.1:8b 的模板里。ollama show llama3.1:8b --template 能看到，它不把工具放进系统提示词，而是放在最后一条用户消息里（模板里的 {{- if and $.Tools $last }}）。多轮对话时，上一轮的用户消息不再是”最后一条”，工具定义就从那里消失，挪到新的用户消息后面。结果是工具定义永远在提示词末尾，永远进不了缓存。

我用同一组工具跑了一个 5 轮的工具调用循环（用户提问、模型调用工具、程序回填一条工具结果、模型回答）：

每轮用户提问后的那次请求提示词总量命中 token提示词处理
llama3.1:8b（第 2～5 轮）7720～81326876～7289510～514ms
qwen2.5-coder:7b（第 2～5 轮）7145～73327111～729738～39ms

llama3.1 每轮都要重算 840 多个 token，提示词处理比 qwen 多约 470ms；工具结果回填后的那次请求，工具定义不渲染，只要 62～65ms。qwen2.5-coder:7b 这组需要说明一下：它把工具调用当成正文 JSON 输出，Ollama 没解析成 tool_calls（上一篇遇到过同样的情况），所以循环里没有工具结果这一步，只是普通的多轮追加。但 qwen 的模板里工具在系统提示词后面，位置不随轮次变化，这一点和有没有解析出工具调用无关。

多轮对话：追加没问题，从头裁历史就有代价

多轮对话最自然的写法是每轮把新的用户消息和模型回答追加到消息列表末尾，前面的内容不变，缓存一直有效：

多轮写法（qwen2.5-coder:7b，第 4～7 轮）命中 token提示词处理首字延迟
一直追加比总量少 34～3637～41ms64～88ms
只保留最近 5 条消息（滑动窗口）6239124～127ms150～155ms

每轮没命中的 34～36 个 token 就是新的用户问题。模型上一轮生成的回答，下一轮作为 assistant 消息重新分词后，和缓存里的 token 对得上，这一点在 qwen2.5-coder 上是成立的。

滑动窗口是为了控制上下文长度：消息超过 5 条以后，每轮从最前面丢掉旧的。丢的位置紧跟在系统提示词后面，于是缓存只能命中系统提示词那 6239 个 token，整段保留下来的历史每轮都要重算。我这组的回答只有 60 个 token，历史很短，代价是每轮多 85ms 左右；历史越长，这个数越大。按 2130 token/s 粗算，保留 4000 token 的历史，每轮要多花近 2 秒（推测，没有实测这个长度）。

想要控制长度又不想每轮都失效，可以攒到一定长度再一次性裁掉一大段，让缓存在两次裁剪之间保持有效。这是从机制推出来的做法，我没有单独测。

改采样参数没事，改 num_ctx 等于重新加载

相邻两次请求的差别（qwen2.5-coder:7b）命中 token提示词处理加载首字延迟
temperature 在 0 和 0.8 之间交替626817ms1～5ms36～81ms
num_ctx 在 8192 和 16384 之间交替02929～3017ms2206～3049ms5170～6015ms

温度、top_p 这类采样参数只影响生成阶段，缓存照常命中。num_ctx 不同就是另一回事：Ollama 的调度器发现运行参数变了，会把模型卸载再按新参数加载一遍，缓存跟着进程一起没了。v0.35.0 的 server/sched.go 里 needsReload 比较的是 api.Runner 这组参数，包括 num_ctx、num_batch、num_gpu、main_gpu、use_mmap、num_thread，任何一个和已加载的模型不同都会触发重载。

一个应用里不同功能用不同的 num_ctx（比如聊天用 8192，总结长文用 32768）时，两类请求交替到来，每次切换都要付 5 秒多。

/v1 和原生接口混用：上下文对不上就每次重载

/v1/chat/completions 不认 num_ctx（上一篇测过，options 整个被丢掉），总是用服务的默认上下文，这台机器上是 4096。所以这组换成一份 2780 token 的短提示词：

交替方式（2780 token）命中 token首字延迟
原生不传 num_ctx ↔ /v1两边都是 2779原生 28ms，/v1 28ms
原生 num_ctx: 8192 ↔ /v1两边都是 0原生 3693ms，/v1 3746ms

上下文一致时，两个接口渲染出来的提示词完全相同，互相命中对方留下的缓存。原生接口带了 num_ctx: 8192 后，每次从 /v1 切回原生都要按 8192 重载，从原生切到 /v1 又要按 4096 重载。原生侧测到每次加载约 2.4 秒，/v1 侧首字延迟 3.7～4.2 秒，量级相同。同一个服务里一部分代码用 OpenAI SDK、一部分直接调原生接口，就会碰到这个情况。解决办法是把上下文长度定在一处：用 OLLAMA_CONTEXT_LENGTH 或 Modelfile 的 PARAMETER num_ctx，两边都不在请求里传（这个做法我没有实测）。

/api/generate（system + prompt）和 /api/chat 也能互相命中，5 组交替请求里每次都命中 6268 个 token。

别的模型、keep_alive 和多份提示词

加载另一个模型。 中间穿插一次 qwen2.5-coder:0.5b 的请求，两个模型能同时放进显存，7b 的缓存不受影响，下一次请求照样 16ms。换成 llama3.1:8b 就放不下了，Ollama 把 7b 卸掉，切回来时要重新加载再重算：后 4 次加载 2.4 秒（2.38～2.68），提示词处理 2.9 秒，首字延迟 5.4 秒。这组的第一次加载花了 129 秒，模型放在机械硬盘上，我推测是模型文件当时不在页缓存里。

keep_alive 过期。 请求里设 keep_alive: "5s"，等 8 秒后再发，模型已经被卸载，5 次都要从头来过，首字延迟 4.7 秒（4.5～4.8）。服务默认的 5 分钟在交互场景下一般够用；如果是间隔几分钟才来一次的定时任务，第一次请求总要付加载加重算的钱。

两三份提示词轮流用。 这是唯一让我意外的结果。OLLAMA_NUM_PARALLEL=1 时 llama-server 只有一个槽位，我以为两份不同的系统提示词交替使用会互相挤掉缓存。实测并没有：P1、P2 交替 6 轮，三份 P1、P2、P3 轮流 5 轮，除了每份提示词第一次出现那一次，其余全部命中，prompt_eval_duration 都在 16～19ms。

但首字延迟是 210ms 左右，不是 37ms：

服务端日志说明了原因。llama.cpp 的服务端有一个放在内存里的提示词缓存（PR #16391）：切换提示词时，先把当前槽位的 KV 状态整份存进内存，这次是 344 MiB；再从已存的几份里找公共前缀最长的那份，拷回显存。这一存一取花了 135～229ms，中位数约 170ms，而且不算在 prompt_eval_duration 里，只有在客户端测首字延迟才看得到。

这个缓存默认上限 8192 MiB（llama.cpp b11081 的 common/common.h 里 cache_ram_mib = 8192），Ollama 0.35.0 启动 llama-server 时没有改这个参数。按日志里 149764 est 的估算，这样大小的提示词能存二十多份，超出后从最旧的开始丢，这个上限我没有测到。这块内存占的是系统内存，不是显存；内存紧张的机器上要算进去。

判断缓存有没有被打掉

回到开头的问题，按这次的数据，下面几种写法会让 Ollama 的前缀缓存失效，代价从小到大：

写法这次测到的额外耗时
时间戳、请求号放在用户消息或系统提示词末尾约 30ms
多份系统提示词轮流使用约 170ms，统计里看不到
滑动窗口从前面裁历史随保留的历史长度增加，60 token 的回答时约 85ms
工具列表顺序不固定；llama3.1 这类把工具放在末尾的模板约 450ms
时间戳、会话 ID 放在系统提示词开头约 2.9 秒，等于没有缓存
交替使用不同的 num_ctx，或 /v1 与带 num_ctx 的原生请求混用加载约 2.4 秒，再加整段重算
模型被别的模型挤出显存，或 keep_alive 过期同上，冷盘时加载能到 2 分钟

排查时先看 prompt_eval_cached_count 和 prompt_eval_count 的比例，接近 1 就是命中；再看 load_duration，超过几十毫秒说明模型被重新加载了。两项都正常、首字延迟却明显偏高时，去 journalctl -u ollama 里搜 prompt cache update took，看是不是在内存缓存里换来换去。

模板的差别值得单独看一眼：ollama show <模型> --template，找 .Tools 出现的位置。它在系统提示词里，工具定义就能被缓存；在最后一条消息里，就每轮都要重算。

这次没测的

  • OLLAMA_NUM_PARALLEL 大于 1 时，多个槽位各有自己的缓存，请求被分到哪个槽位会影响命中率。
  • 开启 Flash Attention 或量化 KV 缓存（OLLAMA_KV_CACHE_TYPE）后，重算速度和内存缓存每份的大小都会变。
  • 提示词只测了 2780 和 6000～8000 token 两档；更长的提示词，重算和内存缓存存取的绝对耗时都会更大。
  • 每种情况只在一个下午里连续跑了 5 次左右，不同硬件上的绝对数字会不一样，但在 llama-server 默认配置下，”第一个不同的 token 之后全部重算”这条规则不变。

上下文本身被截断的问题见 Ollama 静默截断提示词。
