同是 8B，多步工具调用 25 比 0：本地模型在第二步断开

上一篇对照 Ollama /v1 兼容接口 时顺手发现，qwen2.5-coder:7b 带上工具定义后不会产生结构化的 tool_calls，只会把 {"name": ..., "arguments": ...} 当正文打印出来。那次只发了一轮请求。真正的 agent 要连着调好几次工具，后一步的参数来自前一步的结果，单轮能调通不代表整条链能走完。

这次我搭了一个假的工单系统，6 个工具、5 个任务，每个任务要连续调用 2 到 4 次工具才能答对。4 个本地模型各跑 5 个 seed，再试了改工具描述、加系统规则、在客户端兜底解析文本调用这几种补救办法。结果差得比预想大：同样是 8B、同样 Q4_K_M，gemma4 25 次全对，llama3.1:8b 一次都没对，而且换了三种提示词写法还是 0。

测试环境

项目值

显卡RTX 3060 12 GiB，驱动 580.178.04，桌面占用约 4 GiB

gemma4 是唯一默认带思考的模型，所以它多跑了一组 think: false。

假工单系统、工具循环和判分脚本放在 blog-go-example/local-model-tool-calling，可以照着 README 复现。

一个假的工单系统

工具都是本地的 Python 函数，数据写死在脚本里：

工具作用
search_tickets(query)按标题关键词搜工单，返回 id、标题、状态
get_ticket(ticket_id)工单详情，含负责人 assignee（如 U-07）和客户 customer（如 C-315）
get_user(user_id)员工姓名、邮箱、团队
list_orders(customer_id)客户的全部订单，故意不按日期排序
update_ticket(ticket_id, status, note)改状态，status 只接受 open、pending、closed
calc(expression)算术

五个任务，问法都是普通用户会说的话：

任务用户的问题至少要走的链正确答案
t1工单 TK-1042 的负责人叫什么名字？get_ticket → get_user李娜
t2标题里带”发票”的工单中，还没关闭的那张，负责人的邮箱是什么？search → get_ticket → get_userzhaomin@example.com
t3工单 TK-1077 对应客户最近三笔订单的总金额是多少？get_ticket → list_orders（→ calc）3840.25
t4把标题里有”登录失败”的工单状态改成 resolved，备注写”已修复”。search → update状态不存在，要么改成 closed 并说明，要么如实告诉用户改不了
t5TK-1042 和 TK-1090 这两张工单的负责人分别在哪个团队？2 次 get_ticket → 2 次 get_user支付组、账号组

t3 的订单列表是 10-15、09-12、11-02、09-30、10-28 这个顺序，最近三笔是 11-02、10-28、10-15，金额 1280.50 + 349.00 + 2210.75 = 3840.25。按列表前三笔加就是错的。t4 要求的 resolved 不在允许值里，用来看模型拿到错误之后会不会照样说”已修改”。

循环本身是最朴素的写法：模型返回 tool_calls 就逐个执行，把结果作为 role: "tool" 消息追加回去，再请求下一轮；不返回 tool_calls 时把 content 当最终回答。

for turn in range(max_turns):
    m = chat(model, msgs, tools, seed, think)["message"]
    msgs.append(m)
    tcs = m.get("tool_calls") or []
    if not tcs:
        final = m.get("content", "")
        break
    for tc in tcs:
        f = tc["function"]
        res = run_tool(f["name"], f["arguments"], state)
        msgs.append({"role": "tool", "tool_name": f["name"],
                     "content": json.dumps(res, ensure_ascii=False)})

评分只看最终回答对不对。答错的运行按第一处出错的地方归类：调用写成了文本、根本没调工具、查到一半就回答、回答里出现工具结果中没有的邮箱或数字（算编造）、参数里用了没见过的 ID 或缺参数、循环或者选错了数据。答案对、但跳过了任务必需的读取调用（比如直接拿描述里的示例 ID 去查）不算对。t4 里改了一张真实存在、之前结果里出现过的其他工单，记为改错工单；ID 没在问题或之前的工具结果里出现过，一律记为编造 ID。归类脚本先跑一遍，再逐条读原始轨迹核对，t4 的判定规则就是在核对时改过两次的。

模型 / 配置答对中位耗时主要问题

每组只有 25 次，比例本身的误差不小。但 25 和 0 之间的差别不需要统计检验。

llama3.1:8b：第一轮就把整条链发出去

llama3.1 的工具调用大多数时候是结构化的 tool_calls，格式上问题不大。问题出在顺序上：它经常在第一轮就把后面几步一起发出来，而后面几步需要的 ID 它还没拿到，只好现编。

seed 3 那次最典型：搜索、读工单、读用户三个调用在同一轮发出，ticket_id 填的是”获取到的 id”，user_id 填的是”获取到的负责人 id”。两个调用都返回 not found，可它的最终回答写得有模有样：”通过获取该工单的详细信息，我们发现负责人是用户“Alice”。因此，负责人的邮箱是alice@example.com。”工具结果里根本没有 Alice。

我统计了”第一轮就发出依赖前一步结果的调用”的次数，比如 t1 第一轮就调 get_user、t4 第一轮就调 update_ticket。默认提示词下 25 次里有 13 次。占位参数五花八门：

  • 自然语言：获取到的 id、找出标题里有"登录失败"的工单id、调用 search_tickets 后获得的 id
  • 伪造的引用：[result of search_tickets with query='登录失败']、[ticket_id]、...
  • 看起来像真 ID：12345、ID-123、U-001、user123；改描述的两组里还会照抄描述里的格式示例，去改 TK-0000、TK-0001，查客户 C-000

没有占位符的那几次也好不到哪去。t1 五次全部停在第一步，回答”负责人是 U-07”，把用户 ID 当成了名字。t2 编了三个邮箱，除了 alice@example.com，还有一个 yourcompany.com 下的客服邮箱和一个 company.com 下的个人邮箱（company.com 是真实域名，这里不写出完整地址）；t5 编了”开发””运维””IT 支持””客户端开发”这几个团队。t4 的备注参数里出现了”发认已源到””取觀做”这类乱码，原文明明是”已修复”三个字。

文档里的 Parallel tool calling 指的是一轮里发出多个互不依赖的调用，gemma4 在 t5 里就是这么做的：先同时读两张工单，再同时读两个负责人。llama3.1 是把有依赖的调用也塞进同一轮。为什么会这样我没有查到确切原因，推测和 Llama 3.1 的工具调用微调数据以单步调用为主有关，模型没学会”等结果回来再走下一步”。

加规则只是把错误换了个样子

我试了两种补救，组合起来一共四种写法：

  • 改描述：在工具描述里写清 ID 的格式和出处，比如”user_id 形如 U-00，取自 get_ticket 返回的 assignee”，注明订单不按日期排序，给 status 加上 enum。
  • 加规则：系统提示词里加四条，一次只做一步、ID 只能来自问题或之前的结果、报错时不能声称成功、数据齐了再回答。

第一版描述里的格式示例写的是 TK-1042、U-07、C-208，恰好是假系统里真实存在的 ID，U-07 还是 t1 的答案。复核轨迹时发现，qwen2.5-coder:3b 当时的 3 次”答对”都是跳过 get_ticket 直接拿 U-07 去查，llama3.1 有 4 次去改了 TK-1042。我把示例换成 TK-0000、U-00、C-000 这类不存在的 ID，用同样的 seed 重跑了所有用到改描述的组合，文中这几组的数字都是重跑后的。llama3.1 照样照抄示例：两组里各有 5 个调用填的是 TK-0000、TK-0001、C-000、U-00 这类 ID，只是现在它们查不到任何东西。

四种写法全是 0/25。变化在错误分布上：

写法第一轮就发依赖调用查一半就停编造
默认13/2574
改描述19/2551
加规则3/25109
改描述 + 加规则15/2552

单加规则时，”一次只做一步”确实起作用了，第一轮抢跑从 13 次降到 3 次。可它接着就不走第二步了：t1 五次都是读完工单就回答”U-07”，t2 有两次在回答里用文字写出根本不存在的工具，search_ticket_responsible 和 search_ticket_assignee，循环把这段文字当成最终回答收下了。改描述反而让抢跑更多，推测是描述里”取自 get_ticket 返回的 assignee”这类话被模型理解成了”可以直接调用 get_user”。

llama3.1 这种写一半的文本调用不止出现在 t2。t4 的 20 次运行里，有 9 次的最终回答结尾是一段工具调用 JSON，比如”由于状态 resolved 不在允许的状态中，改为 closed”后面跟着一段 update_ticket 的 JSON，但它没有真的发起调用。

qwen2.5-coder：先把文本里的调用捞回来

qwen2.5-coder 7b 和 3b 在 50 次运行里一次都没有产生结构化调用，第一轮直接输出 {"name": "get_ticket", "arguments": {"ticket_id": "TK-1042"}} 这样的正文。它的模板要求把调用包在 <tool_call></tool_call> 里，模型输出的却是不带标签的裸 JSON，结果被当成普通回答。推测 Ollama 是靠这对标签识别调用的，这一点我没有读源码确认。推测是 coder 版本的指令微调里这对标签出现得少，这一点我没有验证。

很多 agent 框架遇到这种情况会做兜底：在客户端解析正文里的 JSON，转换成工具调用再执行。我也写了一个，支持一条回复里有多个 JSON 对象、代码块和 <tool_call> 标签，只要正文里除了调用还有别的文字就不解析。解析出来的调用会全部执行，和框架常见的做法一样。

兜底之后调用确实能执行了，7b 有 21 次、3b 有 22 次至少解析到一个调用，可答对的只有 7b 的 1 次。原因和 llama3.1 类似，换了个形式：

  • 7b 的 t1 五次全部在读完工单后停下，四次回答”U-07”，一次干脆回答”张三”。
  • 它会在一条回复里把整条链写完，后面的参数是 <ticket_id>、<search_results.ticket_id> 这样的模板占位符。兜底解析把它们全部执行，自然全是 not found。
  • 有一次拿到搜索结果后，它自己写了一段 <tool_response> 标签，把搜索结果又抄了一遍，然后结束。它在替工具说话。
  • 3b 的典型错误是把 ID 填错位置，比如把 TK-1042 当成 user_id 传给 get_user。加上改描述和规则后它还是 0/25，有 7 个调用照抄了描述里的示例 ID。

gemma4：思考换来的是第二步

gemma4 是这组里唯一能稳定走完整条链的模型。t5 里它先在一轮里同时调用两次 get_ticket，等结果回来，再同时调用两次 get_user，这是并行调用该有的样子。t4 拿到”invalid status”之后，5 次里 4 次把错误转述给用户，问改成哪个状态；1 次自己改成 closed 重试成功，回答里写的是”已关闭”而不是”已解决”。

代价是时间。默认思考时中位耗时 15.4 秒，think: false 只要 1.4 秒，答对率从 25/25 掉到 16/25。掉下来的 9 次里，最整齐的是 t3：

关掉思考后，t3 五次都把订单列表的前三笔加起来，得到 4051.25。调用链完全对，get_ticket、list_orders、calc 一步不差，错在”最近三笔”需要先按日期排序，它跳过了。开着思考时五次都选对了 11-02、10-28、10-15 三笔：四次调用 calc 算 1280.5 + 349.0 + 2210.75，一次没调 calc 直接给出 3840.25。

另外 4 次是在 t2 和 t4 里不调工具，先反问用户，比如”请问您是否需要我先执行搜索操作？”。这在交互式助手里不算错，放进无人值守的流程就是卡住。

改描述 + 加规则的组合下，gemma4 还是 25/25，中位耗时 14.7 秒。t4 的行为变了：工具定义里有了 enum，它一次都没有尝试 resolved，5 次里 4 次直接改成 closed 并在回答里说明系统不支持 resolved，1 次先问用户改成哪个状态。我没有测 think: false 加改描述的组合，所以不知道”订单不按日期排序”这句描述能不能救回 t3。

提示词救不回来，思考救回了一部分

  • 提示词对 llama3.1 的答对率没有任何帮助。四种写法 100 次全是 0，每种写法只是换了一种错法。
  • 补救之后最常见的错误变成”查一半就停”。llama3.1 单加规则后、qwen2.5-coder:7b 加兜底后，都是这一类最多：模型拿到第一步的结果就觉得够了，把 U-07 当名字回答。
  • 思考解释的是 gemma4 自己掉的那 9 次。关掉思考后它 t3 五次全错，样子和 llama3.1 一样是”没想就做”；但即便关掉思考，它仍比 llama3.1 多对 16 次，两个模型之间的差距不能都算在思考头上。
  • 编造的东西都很像真的。alice@example.com、”支付组”之外的”开发””运维”，单看回答完全看不出问题，只有对照工具结果才发现。

把本地模型接进工具循环前要做的检查

  • 先用目标模型跑一遍多步任务，看结构化调用、第二步和最终回答三处。只测单轮工具调用会漏掉这里绝大多数错误。
  • 校验参数里的 ID。工具执行前检查 ID 是否在问题或之前的结果里出现过，llama3.1 那 13 次抢跑就能在执行前被拦下，并把错误回给模型。这一步我没有实测效果，回给模型之后它能不能改对是另一回事。
  • 排序、筛选、”最近 N 笔”这种逻辑放进工具里。list_orders 如果直接返回按日期倒序的结果或接受 limit 参数，t3 就不需要模型自己排序。
  • 能用 enum 就用 enum。gemma4 在 t4 里看到 enum 后就不再试错，比依赖错误信息更省一轮。
  • 文本调用兜底能让调用跑起来，但救不回答对率。qwen2.5-coder 加兜底的四组共 100 次只对了 1 次，不如换一个原生支持工具调用的模型。
  • 多步任务优先开思考，时间预算按 10 秒以上估。gemma4 关掉思考快了 10 倍，答对率掉了三分之一多。
