Gemini 4 Neon 对 Claude Opus 5.5 实测：答对率几乎打平，Neon 默认思考慢 3 到 8 倍

 costalong  2026-11-26  AI AI 工程实践 Go LLM 评测 Gemini

Google 在 2026 年 11 月 18 日发布了 Gemini 4 Neon，API 标价每百万 token 输入 3 美元、输出 15 美元，比 Claude Opus 5.5 的 4 美元、20 美元便宜四分之一。两家都给了一长串基准分数，但几乎没有同一个版本的同一个基准：Neon 报的是 Terminal-Bench 4.1（65.2%），Opus 5.5 报的是 Terminal-Bench 4.0（66.4%）；Neon 报 FrontierCode 2.0，Opus 5.5 报 v1.1。数字放在一起看不出谁强。

所以我自己出了三套能自动判分的题，在同一天把两个模型都跑了一遍：10 道 Go 编程题，用隐藏测试判分；30 道推理与数学题，答案由程序算出；3 份 10 万到 60 万 token 的长上下文检索题。两个模型都用 high 思考强度（Neon 的默认值），另外用 Neon 的 low 强度跑了一遍编程和推理作对照。

结论先放这里：

  • 答对率几乎打平。 编程题按「三遍隐藏测试全过」算，两边都是 29/30；推理题 Neon 60/60，Opus 58/60；长上下文两边 12 次全对，也都没有被干扰记录骗到。
  • Neon 在 high 强度下想得非常多。 编程题每次输出 token 的中位数 Neon 是 13,133（其中思考 11,850），Opus 是 1,650。延迟中位数编程题 101 秒对 12 秒，推理题 37 秒对 11 秒，长上下文冷启动 25 秒对 4 秒。
  • 单价便宜不等于每次便宜。 按官方标价折算，编程题 Neon 每次 0.257 美元，Opus 0.046 美元；推理题 0.108 对 0.041。只有长上下文这种输入远多于输出的任务，Neon 才更便宜（每次 1.08 对 1.83 美元）。
  • Neon 降到 low 强度，这几套题照样全对，延迟和成本降到接近 Opus 的水平（编程 28 秒、0.058 美元）。

实验怎么搭的

两个模型的调用方式：

  • Gemini 4 Neon：模型 id gemini-4-neon，走 Gemini API 的 REST 接口（标准层），thinkingConfig.thinkingLevel 设为 high 或 low。
  • Claude Opus 5.5：模型 id claude-opus-5-5，通过 Claude Code CLI 的 claude -p 调用，--effort high。为了让它尽量接近一次裸 API 调用，替换了系统提示、关闭全部工具和 MCP、不读任何 settings，在空目录里运行；这样除了提示词，只多出约 600 个缓存前缀 token。

两边的系统提示都是同一句 You are a helpful assistant.。

三套题：

套题内容判分轮数
编程10 道 Go 题：工作日计数、严格 CSV 解析、表达式求值、整数区间集合、带 TTL 的 LRU、限并发有序并行 map、令牌桶限流、语义化版本比较、确定性拓扑排序、中英文混排按显示宽度折行取回答里第一个 Go 代码块，配隐藏测试跑 go test -race -count=3，每个测试三遍都过才算过Neon high 和 Opus 各 3 轮，Neon low 1 轮
推理5 类各 6 题：带障碍的网格路径数、带条件的数位计数、6 人排座（唯一解）、骰子点数和的精确概率、跨节假日的工作日推算只看最后一行「答案：」，分数按分数值比较Neon high 和 Opus 各 2 轮，Neon low 1 轮
长上下文Go 标准库源码当干草堆，埋 8 条 // NOTE(ops-ledger) 真配额记录和 4 条 // NOTE(test-fixture) 干扰记录（同名服务、不同数字），要求输出全部真配额、总和和最大者JSON 里 8 个配额、总和、最大者全对才算对两边各 2 轮

编程题都只用标准库，题面写清了导出的函数签名和边界行为，每题 7 到 9 个测试。出题后先用参考实现过一遍全部测试，再故意改坏参考实现，确认测试能抓住常见错误。

成本按 2026-11-26 官方价目页的标价算，输入一律按基础价计，不算缓存。Claude CLI 会自动给提示词写 1 小时缓存（每百万 token 8 美元），如果把这个算进去，长上下文第一轮的 Opus 账单会翻倍，两边就没法比了。原始日志里另外记了按价目表折算的实际金额。

Neon 唯一没过的一次是 expr 第 3 轮：它把 65,536 个输出 token 的上限全部花在思考上，以 MAX_TOKENS 结束，一行代码都没给。这一次调用耗时 438 秒，按标价算 0.99 美元。我没有重试，按 0 分算。另外两轮 expr 它都写对了，说明不是不会，而是 high 强度下偶尔停不下来。

Opus 没过的是 parmap 第 3 轮。这道题要求实现一个限并发、保序的并行 map：任一调用出错就取消其余调用，父 context 取消时尽快返回，返回之后不能再有新的调用。Opus 这份代码用一个带缓冲的 channel 当信号量，出错后的清理逻辑里写了：

select {
case <-sem:
default:
}

意图是「释放一个名额」，但当前 goroutine 并没有拿到过名额。这一下会偷走另一个正在运行的 goroutine 的名额，那个 goroutine 退出时 defer 里的 <-sem 就永远阻塞，wg.Wait() 跟着死锁。父 context 取消和「返回后不再调用」两个测试每次都挂，「首个错误取消在途调用」那个测试时过时不过，我反复判分时它在 6/9 和 7/9 之间跳。这类并发错误普通单测跑一遍很容易漏过去，-race -count=3 才把它稳定地抓出来。

另外两轮 Opus 的 parmap 都是对的。所以两个模型在这 10 道题上都是「偶尔失手一次」，看不出谁写 Go 更强。差别在花的 token：Neon 每道题都多想 5 到 10 倍，最多的 toposort 中位数 28,704 个输出 token，Opus 是 4,169。

Opus 的两次错误都只在一轮出现，另一轮同一道题是对的：

  • dice-3 第 2 轮答 43/144，正确答案是 1/3。看推理过程，它列点数和的分布表时把 17 和 19 两行的组合数抄错了，后面的算法本身没问题。
  • digits-4 第 1 轮答 105519，正确答案是 106779。它用生成函数展开计数，中间一步系数乘错了。

两次都是「思路对、算术错」。Opus 在推理题上每次的思考 token 中位数只有 568，Neon high 是 3,556，Neon low 也有 2,119。想得多的一方没有出这种低级错误，这和直觉一致；但 2/60 的差距太小，换一套题很可能就反过来了。

长上下文：都全对，Neon 冷启动慢、价格便宜

同一份文本，两边的分词器给出的 token 数差得不少，Claude 那边多约 35%：

两边 12 次回答全对：8 个配额、总和、最大者都对，没有一次把 test-fixture 的假数据报进来。在这个难度下，1M 上下文的两个模型都还没到检索能力的极限，没有分出高下。

成本上 Neon 每次便宜约 40%。原因有两个：输入单价 3 对 4 美元，同一段 Go 源码 Gemini 少计 25% 的 token。两边的输出都只有几百 token，基本不影响账单。延迟上 Opus 快得多。Opus 的延迟用的是 CLI 报告的 API 耗时，加上进程启动大约再多 1.5 秒（100k 时总共 4.4 秒）。第二轮两边都命中了缓存，延迟只看第一轮。

Gemini 的思考 token 按输出价计费，每百万 15 美元。编程题上 Neon 每次多输出约 11,000 个 token，比 Opus 每次的全部开销还贵。官方说 Neon「每个任务的成本比主流前沿模型低 50% 到 80%」，在这几套题、high 强度下我没看到这个结果；只有长上下文这种以输入为主的任务符合。

延迟的长尾也值得看。编程题 Neon high 的 p10 / p50 / p90 是 71 / 106 / 226 秒，最长 438 秒；Opus 是 9 / 13 / 33 秒，最长 41 秒。如果把模型放在交互式的工具里，Neon high 的 p90 已经超出大多数人愿意干等的时间。

把三套题加起来，按标价计 Neon high 一共 20.63 美元，Opus 14.86 美元，Neon low 2.40 美元（只跑了编程和推理各一轮）。

Neon 降到 low：这几套题上没有掉分

low 强度的 Neon 编程 10/10、推理 30/30，全对。和 high 相比，编程题延迟中位数从 101 秒降到 28 秒，每次成本从 0.257 降到 0.058 美元；推理题从 37 秒、0.108 美元降到 22 秒、0.060 美元。

low 只跑了一轮，样本比 high 少，「全对」不能说明 low 和 high 一样强，只能说明这几套题用不着 high。但它说明了一件实际的事：Neon 默认的 high 强度对中等难度的任务明显过量，先试 low，比直接拿默认值去和别的模型比价更合理。即使降到 low，Neon 在编程题上仍比 Opus 慢一倍、每次贵约 25%。

怎么选

  • 对话式写代码、需要快速来回：在这几套题上 Opus 5.5 的延迟和成本都占优，答对率不输。
  • 用 Neon：先把 thinkingLevel 设为 low 或中间档，确认答对率够用再往上调；默认的 high 对中等难度任务想得太多，偶尔还会把输出上限全花在思考上，最后什么都不交。调用方要处理 MAX_TOKENS 这种结束原因，别把空回答当成功。
  • 大段输入、少量输出的批处理（读长文档、在大代码库里查东西）：Neon 输入单价低、分词更省，每次能便宜约 40%，延迟不敏感时值得用。
  • 并发代码：两个模型都可能写出偶发死锁，-race 加多次重复运行的测试仍然是必须的。

哪些结论不能外推

  • 题目是自己出的，编程 10 道、推理 30 道、长上下文 3 份，每题只跑 2 到 3 轮。29/30 对 29/30、60/60 对 58/60 这种差距在统计上都不显著。
  • 只比了 high 强度的 Opus 和 high / low 强度的 Neon。Opus 官方基准用的是 max effort，Neon 宣传的分数有一部分是 xhigh，这里都没测。
  • Claude 通过 CLI 订阅登录调用，Gemini 走公开 API 标准层，两边的网络路径、排队和服务器负载都不同，而且只测了一天。延迟只能当量级看。
  • 长上下文题只考「找出若干条格式固定的记录并求和」，不涉及跨段落推理，不能代表长文档理解能力。
  • 编程题都是单文件、只用标准库的小题，不涉及读已有代码库或多轮修改，和 Agent 场景下的编程能力不是一回事。
  • 价格是 2026-11-26 的标价，不含批处理折扣和缓存优惠。
