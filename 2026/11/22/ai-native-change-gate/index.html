AI-Native 进阶：批准之后，变更怎样安全执行

上一篇 AI-Native把 Agent 的终点定在 L3：提交 PR，由人审查，再走既有交付链路。这里沿用这个权限边界，继续看获批变更交给执行器后会发生什么。执行器可以由交付系统承担，不需要把生产写权限交给 Agent。

下面用一次假设的回滚说明。

时间发生了什么
09:00checkout 的 v17 出现错误，Agent 提议回到 v16
09:02值班人员看过证据，批准 v17 → v16
09:04另一位开发者上线了 v18 热修复
09:05排队的 Agent 请求终于开始执行，准备把镜像改成 v16

提案没改，审批人也确实点过同意。但此时执行回滚，会覆盖后来上线的热修复。

上一篇用“四小时没人处理就自动关闭”清理未处理的提案。这里人已经批准，五分钟内状态却变了。即使批准另有有效期，也得在执行时检查它是否还适用。

批准的是哪份内容

“同意修复 checkout”太宽。Agent 在收到批准后，如果重新生成一遍命令，把目标从 v16 换成 v15，执行端不能只检查提案上的 approved=true。

批准前应当形成一份确定的执行内容。下面是配套案例中的数据结构，v17、v16 是便于阅读的示例版本名；真实部署应绑定不可变的镜像标识。

{
  "id": "rollback-001",
  "actor": "agent-a",
  "service": "checkout",
  "uid": "deployment-1",
  "expected_version": 41,
  "before": "v17",
  "after": "v16",
  "policy_revision": 1,
  "expires_at": 1800000300
}

id 标识这一次操作，actor 限定发起者。资源 UID 用来区分同名但已经删除重建的资源。预期修订号与 before 记录起点，after 固定目标；政策版本和到期时间决定这份批准还能不能用。

本例只管理一个资源。接入多集群环境时，还要把租户、集群、命名空间与动作类型写进提案，不能依赖执行器的当前默认配置。

批准时保存这些字段的摘要和审批身份，执行器再核对收到的内容。目标、环境、有效期或执行者变了，就必须重新提案，旧批准不能沿用。

摘要只负责发现内容变没变。谁能批准、批准的是哪个环境、记录是否来自可信服务，仍要由身份系统和审批服务保证。让 Agent 自己提交一段 JSON，再附上它自己算出的摘要，并不能产生权限。

审批页面也要从这份内容生成。如果人看到的是“回到 v16”，执行器收到的却是一段仍由模型补全的脚本，人批过的内容就约束不了实际执行。

有效期没到，批准也可能失效

09:05 的请求内容与批准完全相同，却已经不适合执行。检查摘要只能防止提案被改，发现不了提案之外的变化。

执行端要核对：是不是原来的资源，镜像是否仍为 v17，修订是否与批准时相同。相关条件变了，就拒绝旧请求。Agent 可以重新读取状态、重新判断，但不能替换旧批准里的修订号后继续重试。

不过，先读再写仍会遇到这种顺序：

执行器读取：当前还是 v17
另一个发布：写入 v18
执行器写入：改成 v16

把读操作放在执行前一毫秒，也没有消除这个窗口。比较和写入需要由持有状态的一方作为一个条件操作处理。

Kubernetes 的更新接口允许客户端携带读到的 resourceVersion；更新时版本已变化，API Server 会拒绝陈旧写入。JSON Patch 也可以通过 test 设置条件，并在同一个请求里执行修改。RFC 6902说明了 test 失败时整份 HTTP PATCH 不应留下部分修改。

只比较镜像，可能漏掉 v17 → v18 → v17 这样的中间变更；比较整个对象的版本，又可能因无关的状态更新而频繁冲突。刚开放生产动作时，可以先规定状态有变就退回重审，再根据冲突记录缩小检查范围。会影响批准结论的条件必须保留。

这次条件更新只保护被修改的 Kubernetes 对象，不会检查指标是否过时、审批人的权限是否变化，或其他服务是否又发了版。涉及这些条件时，还要约定可接受的观察窗口与失败处理，一次对象写入无法把整个环境锁住。

超时后，先找回这次操作

再看没有 v18 热修复插入的另一条分支：资源仍是批准时的 v17，执行端把它改成了 v16，但返回结果时连接断了。

Agent 只看到了超时。重新提交一个新操作号，可能再次触发发布；如果它改用别的修复办法，还可能叠加第二种变更。之前的 Go 超时实验已经展示过，客户端停止等待和服务端工作停止是两回事。对于写操作，还要考虑工作已经完成、只是回执没送到的情况。

第一次发送前就要确定操作号，重试时沿用它。同一执行者拿相同操作号、相同内容重试，执行端返回原操作的状态或回执；同号换了目标，则拒绝。AWS 的幂等 API 设计说明也专门区分了重复请求与“同一请求号、不同意图”。

假设请求要求修订号为 41，执行后变成 42。重试时若先比较修订号，执行端会报“状态变了”，第一次是否成功反而查不清。应当先确认调用者有权读取这次操作，再按操作号查找相同内容的回执。尚未执行的新操作，才继续检查到期时间、政策和资源状态。

旧回执也不能当成现状。它记录那次操作把资源改成了 v16，后来仍可能有发布把它改成 v18。要知道当前版本和健康情况，还得另查。

批准过期后可以停止新执行，但不能直接删掉幂等记录。记录至少要覆盖允许重试与对账的窗口，否则晚到请求只查到“无此操作”，第一次执行的结果就没了依据。

图里画的是后面的单进程 Go 示例，省略了字段格式校验。完整函数从入口持锁；这个临界区不包含远程 API。

用 Go 验证执行与重试

配套案例只实现一项固定能力：修改一个模拟资源的镜像。没有任意命令工具，没有调用模型，也没有连接 Kubernetes。审批服务和认证后的调用者被视为可信输入，案例没有实现登录、审批人角色管理或生产凭证。

Gate 在服务端保存批准内容的摘要与执行回执。Execute 从入口持锁，先检查字段和调用者，再找这次操作是否已有回执。下面按原函数的顺序摘录，省略函数签名和注释：

g.mu.Lock()
defer g.mu.Unlock()
if !valid(p) {
    return Receipt{}, false, ErrInvalid
}
if caller != p.Actor {
    return Receipt{}, false, ErrActor
}
h := digest(p)
if r, ok := g.receipts[p.ID]; ok {
    if r.PlanHash != h {
        return Receipt{}, false, ErrKeyReuse
    }
    return r, true, nil
}

第一次执行把修订从 41 改到 42，保存了回执。第二次仍携带原来的 ExpectedVersion=41，但会在上面返回，不再拿它与当前的 42 比较。true 表示读到历史回执；调用者不匹配或同号换了内容，都不能走这条返回路径。

只有没找到回执，原函数才继续检查批准摘要、执行开关、有效期和政策修订。省略这几项检查后，资源比较与写入部分如下；此时仍持有同一把锁：

if g.resource.Service != p.Service || g.resource.UID != p.UID ||
    g.resource.Version != p.ExpectedVersion || g.resource.Image != p.Before {
    return Receipt{}, false, ErrStale
}
// Execute 在进入检查前已经持有 g.mu，直到保存回执后才释放。
g.resource.Image = p.After
g.resource.Version++
r := Receipt{
    OperationID: p.ID,
    PlanHash:    h,
    Image:       p.After,
    Version:     g.resource.Version,
}
g.receipts[p.ID] = r

这里的 Version 是教学模型自己的递增计数，不能直接当成 Kubernetes resourceVersion 的实现。锁也只保护这个进程里的对象。policy_revision 也只比较政策版本，没有实现生产策略引擎；真实执行端还要按当前规则检查调用者、动作与资源范围。

在案例目录执行，要求 Go 1.25 及以上，没有第三方依赖：

cd blog-go-example/ai-native-change-gate
go test -race -count=1 ./...
go vet ./...
go run .

在 macOS arm64、Go 1.27.2 上运行后，测试和竞态检查通过，go vet 无报错。命令与输出保存在运行记录，下图为该记录的浏览器截图：

示例为这两条分支分别创建初始状态。stale approval 一组先插入 v18，随后旧请求被拒绝，v18 保留下来；lost reply 一组没有插入新发布，先执行一次，再故意丢弃返回值来模拟回复丢失。重试拿到原回执，变更计数仍是 1。这里没有制造真实网络故障。并发组的 32 次调用拿的是同一份批准，只有一次产生修改，另外 31 次读取回执。

测试还覆盖了到期、执行权限关闭、换调用者、同名资源重建，以及两份不同提案竞争同一修订号，并检查被拒绝的请求没有改动资源。两份提案即使都获批，也只允许一个成功，另一个必须基于新状态重做决定。

内存锁之外，还有“执行了但没记下来”的空档

案例中的资源、批准和回执都在内存里，进程退出就会丢失。如果把执行记录放进数据库，资源变更改为调用另一个 API，就会遇到下面这段过程。配套案例没有实现这里的远程调用和崩溃恢复：

数据库：记录操作开始
Kubernetes：接受变更
进程崩溃
数据库：还没记下结果

把 mu 换成分布式锁，崩溃后的这个空档仍然存在。写数据库的事务也管不到已经发出的远程请求。

恢复程序读到“操作开始”，还不能据此决定再执行一次。执行器需要在发出请求前持久保存操作意图，让重启后的进程能找到这次尚未核对的操作。Outbox 可以防止待执行意图随着进程退出而消失；但上面的崩溃仍可能发生，消息重送到下游时，第一次变更可能已经完成。AWS 的 Outbox 说明同样要求消费方处理重复消息，Outbox 本身不保证下游副作用只发生一次。

接下来怎样恢复，要看目标 API 能提供什么。支持幂等请求号，就沿用原号；只支持条件更新，就需要保存足够的目标身份、前置条件与执行关联信息，供恢复程序查询。

查到“当前镜像等于 v16”还不够。它可能是另一位操作者改成的，也可能已经经历过多次发布。无法确认是不是这次操作的效果，就记为结果未知，保留证据交给恢复流程或人工核对，不能换号重试。

执行端能确认的事实后续动作
尚未发出请求，前置条件已变拒绝旧提案，重新观察和审批
同一操作已有匹配回执返回原回执，再按需查询当前状态
请求已发出，目标提供原操作的可信结果核对结果后补全执行记录
请求已发出，无法确认是否产生效果标记结果未知，暂停可能冲突的后续写入并对账

在本文只有一个 checkout 资源的场景里，先暂停可能与这次未决操作冲突的后续写入，再由负责人在限定的查询预算和处置时限内核对，不能把“结果未知”留成无人接手的记录。实际暂停范围要按资源及依赖之间的冲突确定；案例没有实现这类调度或暂停机制。

如果核对期间批准或执行权限被撤回，已经发出的请求仍要继续查。执行开关能拦截尚未派发的动作，不能保证收回远端已经接受的请求。派发前要限制单次动作的范围并记录派发位置，撤权后继续核对在途操作；把开关关掉后连对账进程也停掉，会让这些结果无人处理。

仍然走 GitOps，检查应该放在哪里

沿用上一篇的 PR 路径，需要区分两种变化。PR 获批后又追加修改，变的是被批准的内容，对应前面的摘要核对。旧批准是否继续有效，要由服务端规则约束。GitHub 的分支保护说明提供了变更差异后撤销陈旧批准、要求最近一次可审查推送获批等选项；这些都需要显式配置，不能把一个绿色审批标记视为永久有效。

开场的 v18 热修复属于另一种变化：即使回滚 PR 一字未改，目标资源也已经离开了批准时的状态。内容核对通过，仍要在真正修改资源时检查前置条件。PR 自身的审批记录不能替代这次条件写入。

接入既有交付链路时，可以由审批入口保存获批修订与审批身份，由执行入口核对待执行内容；持有写权限的部署执行端携带资源条件，交给目标服务比较并修改；操作记录与恢复模块在派发前保存操作号与操作意图，随后保存结果，供重试和结果核对时查询。这是接入时建议安排的分工，现有工具是否满足，需要逐项核对。

原文提到的私有仓库免费计划缺少服务端保护，这个限制仍需处理。检查脚本可以发现不合规，却挡不住有足够权限的人绕过入口。放权前必须核对写凭证和服务端规则能否拦住这些路径。

查执行结果时，也不能停在“PR 已合并”。Git 记录预期配置，控制器还要把它同步到集群；OpenGitOps 的原则将期望状态与持续协调分开。若此时集群仍是另一个版本，先识别是不是紧急变更、同步延迟或配置漂移，不能让 Agent 直接写集群去“补平”，否则控制器下一次协调时可能又覆盖回去。

因此，要从这次获批内容查到合并后的修订，再查控制器实际观察到了哪个修订：

被批准的内容 → 合并后的修订 → 控制器观察到的修订
             → 目标工作负载完成更新 → 业务验收结果

查到目标工作负载完成更新，还不能说明 checkout 的请求已经恢复。Kubernetes 的 rollout 完成条件关注副本更新与可用状态，不能证明某个业务接口的错误率已经恢复；只检查进程是否存活的就绪探针，也无法证明付款、查询或消息消费正常。

生产方案中的目标版本、业务信号与观察窗口，也应纳入被批准的执行内容；若验收规则单独存放，提案应绑定它的不可变版本。后续用这份批准中的条件验收，不能执行失败后由 Agent 换掉条件再宣布完成。前面的教学 Plan 只用 after 表示目标镜像，没有业务信号和观察窗口字段，也没有实现验收流程。

观察窗口结束仍不达标，也不等于获得了回滚权限：数据和依赖可能已变化，回滚要有单独授权的条件，或者重新提案。案例没有运行实际部署和业务验收。

回到 09:05

09:05，那份旧回滚应当被拒绝，保留 v18。案例测试把这次拒绝记为通过，不代表故障已经解决。Agent 接下来要读取 v18 的状态，再判断是否还需要修复。如需继续变更，就重新提案，不能沿用基于 v17 的批准。
