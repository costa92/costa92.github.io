个人开发者接入 Waffo 支付：从申请到付款后到账

 月影  2026-11-22  独立开发 Waffo 支付 独立开发

上一篇写了支付宝 Vibe Pay 和微信个人虚拟支付。还是那个图片处理工具，如果要卖给海外用户，网站还需要一条银行卡收款的路径。

Waffo 有面向个人开发者的产品，叫 Waffo Pancake。它采用 Merchant of Record（MoR）模式，由平台作为面向买家的法律销售主体，承接支付和相应交易税务；开发者继续负责产品交付。个人可以申请，不要求先注册公司，但正式收款仍要通过店铺审核。个人申请条件、MoR 的职责分别有说明。

下面为海外版设一个“10 美元、30 次处理”的一次性套餐，从申请一直写到用户拿到次数。资料核对日期为 2026 年 11 月 22 日，已完成测试店铺和测试商品的创建，尚未提交正式商户审核，也未进行平台测试付款或真实资金交易。代码使用官方 TypeScript SDK，价格和套餐均为示例。

注册账号，进入个人建店流程

从 Waffo Pancake 官网进入商户后台。注册和登录使用同一个入口，可以选 Google、GitHub，或填写邮箱后接收登录链接。页面底部写明，新用户直接登录就会创建账户，不用再找一个单独的“注册”按钮。

首次登录后会进入建店引导，依次是“关于你”“店铺和商品”“开始使用”。第一步先选择“个人”，按真实情况填写所在国家或地区、产品业务类型和了解渠道；计费模式为选填。图中展示的是尚未填写的表单。

产品还没确定，可以在这一步点“暂时跳过”。接下来的页面支持输入网站地址自动导入，也有“还没有网站？手动创建”入口，不必为了继续而编造一个产品网址。

手动创建分两步：先填写店铺和第一个商品的名称，再设置计费类型、价格、币种及商品类别。这里显示的是测试模式，不处理真实支付。这次用“开发测试店铺”和“支付接入测试商品”完成引导，测试价格设为一次性 1 美元，返回 URL 留空；下文的 10 美元次数包仍是用于解释业务逻辑的示例。

创建成功后，页面会显示店铺已就绪，并标注测试模式。下图英文界面显示 is ready · test mode，点击 Go to Dashboard 打开后台。这个引导页与后文的 Business Details 业务审核是两个阶段，完成建店不代表已经获准正式收款。

本文使用 docs.waffo.ai 下的 Pancake 文档和 @waffo/pancake-ts，后面的接口、费率都按这套产品说明。不要把 Waffo 企业支付网关的配置直接搬进来。

对这个次数包，平台负责收钱、维护支付订单，自己的服务负责把购买对应到业务账号，再给账号增加 30 次。接入前有三件事要分别确认：

想完成的事要准备什么
在测试环境创建商品、打开收银台账号、店铺、测试商品和测试密钥
接受真实付款店铺业务资料通过审核，商品发布到正式环境
把余额提到自己的账户完善个人身份资料，添加本人名下且渠道支持的收款账户，等待资金可提现

测试环境可以先接，不必等业务审核。店铺审核与提现身份资料也不是同一个步骤，不能因为测试订单创建成功，就认为已经具备正式收款和提现资格。审核范围与身份资料要求可以分开核对。

提交申请前，把产品页面补完整

到店铺的 Settings → Business Details，从 Start Setup 进入业务资料流程，按官方业务资料说明选择 Individual / Solo developer，填写产品说明、网站地址、联系邮箱和业务现状。本文实际查看到审核入口，后面的资料要求按官方文档整理，尚未完成提交。

对图片工具，网站至少得让第一次来的人看懂这些内容：

  • 工具能处理什么图片，怎样得到处理结果。
  • 10 美元买的是 30 次处理，是否过期，处理失败怎样处理。
  • 这是一次性购买，是否存在自动续费。
  • 怎样申请退款、怎样联系支持。

价格页应当无需登录就能查看。服务条款、隐私政策要有完整内容，并在页脚提供能正常打开的链接；提交审核的联系邮箱，应与网站上的支持邮箱一致。不能只放一个登录入口，让审核人员猜产品是做什么的。官方店铺审核说明列出了这些检查项；如果做的是 AI 图片或视频生成，还要另看 AIGC 要求。

提交前还要完成邮箱和域名验证。在 Contact Email 步骤接收验证码，先验证自己能使用这个支持邮箱；Website URL 步骤则验证产品域名归属。提交按钮会等这两项完成后才开放。邮箱验证、域名验证各有对应说明。

已验证邮箱与产品网站同域时，可以按页面提示一键验证域名。否则可选 DNS TXT：把后台生成的记录名称和值添加到自己的 DNS，等公开查询能查到，再回 Pancake 确认。也支持 HTML meta 和 .well-known 文件；选一种即可，记录值和文件路径以本次后台生成的内容为准。

文档给出的通常审核时间是 1～3 个工作日，具体看后台结果。资料被退回，就按反馈修改同一家店铺后重新提交。

先建测试商品，再拿密钥

在后台切到 Test Mode，进入 Products → Create Product，创建一次性商品，设置名称、USD 价格和适用税务分类。这个例子把商品设为 10 美元，业务系统里的套餐则记录“该商品对应 30 次处理”。Waffo 的商品是计费对象，并不会自动变成图片工具里的次数余额。

先用后台复制的商品链接检查名称和价格是否正确，暂时不用接业务发货。要让登录用户付款后自动到账，再由服务端创建专属于这次购买的 Checkout Session。商品创建和托管链接见官方快速开始。

服务端需要的配置如下，变量名可按项目习惯调整：

配置从哪里取得用在哪里
WAFFO_MERCHANT_ID后台 API & Development 的 API Key 创建区域确定商户身份
WAFFO_PRIVATE_KEY创建 Test API Key 时按后台指引取得并保存的私钥SDK 对 API 请求签名，只保存在服务端
WAFFO_STORE_ID当前店铺资料通知到达后核对店铺
商品 ID，形如 PROD_…测试商品详情服务端把本地套餐映射到 Waffo 商品

API Key 按测试、正式环境分别创建。使用 API Key 时，平台从密钥识别环境，不能只把浏览器后台切成 Test Mode，就认为程序也在调用测试环境。环境隔离说明里写明了这点。

下单时，把购买和业务账号绑在一起

一个公开商品链接可以收钱，但图片工具已经有用户账号。付款邮箱不一定等于登录邮箱，后续不能靠邮箱猜这 30 次该发给谁。

因此这里采用官方 SDK 的已登录买家模式：业务服务从登录态取得用户 ID，先保存待支付购买记录，再创建收银台会话。浏览器只提交套餐代号，商品 ID、价格、次数和用户归属都由服务端确定。

示例基于 Node.js 20 及以上，SDK 固定为本次核对的版本：

npm install --save-exact @waffo/pancake-ts@0.28.0

下面是服务端创建会话的片段。purchase 必须来自已经落库的购买记录，不能直接使用浏览器传来的同名字段；id 使用服务端生成的 UUID。

import { WaffoPancake } from "@waffo/pancake-ts";

const merchantId = process.env.WAFFO_MERCHANT_ID!;
const client = new WaffoPancake({
  merchantId,
  privateKey: process.env.WAFFO_PRIVATE_KEY!, // Test API Key 的私钥
});

type Purchase = {
  id: string;
  userId: string;
  productId: string;
};

export async function createCreditCheckout(purchase: Purchase) {
  const session = await client.checkout.authenticated.create({
    productId: purchase.productId,
    currency: "USD",
    buyerIdentity: purchase.userId,
    orderMerchantExternalId: purchase.id,
    successUrl: "https://app.example.com/payments/return",
  }, {
    idempotencyKey: `${merchantId}_checkout_${purchase.id}`,
  });

  return {
    sessionId: session.sessionId,
    checkoutUrl: session.checkoutUrl,
    expiresAt: session.expiresAt,
  };
}

域名换成自己的 HTTPS 地址。把返回的会话 ID 和过期时间保存到购买记录，完整的 checkoutUrl 返回给当前登录用户，再跳转。这个模式返回的链接带有买家会话令牌片段，不要裁掉，也不要发到公开日志或分享给其他用户。

这里有两个用途不同的标识：buyerIdentity 关联业务用户，orderMerchantExternalId 关联这一次购买。后者会出现在支付通知中，服务端据此找到原来保存的用户、商品和 30 次权益快照。创建会话接口说明了外部订单号的传递规则。

如果创建请求超时，用原购买记录和相同参数重试，沿用原幂等键。SDK 不会自动生成这个键；平台的幂等缓存有效期为 24 小时，不能把它当成永久防重机制。键只使用字母、数字、连字符和下划线，不要用带冒号的自定义格式。幂等规则有更完整的约束。

用户付完钱，30 次怎样到账

收银台支付完成后，用户点击 Done 才会进入 successUrl，当前并非自动跳回。也有人付完就关掉页面。所以返回页只调用自己的服务端查询购买状态，显示“正在确认”或“已到账”，不能凭页面被打开就增加次数。

付款确认走服务端通知。到 Settings → Webhooks 添加测试环境的 HTTP 通知，格式选 Raw JSON，填写自己的 HTTPS 地址，例如 https://api.example.com/webhooks/waffo。先为下面的付款处理函数订阅 order.completed，配置步骤见Webhook 指南。

通知入口需要接收原始请求体。不要先执行 request.json() 再序列化，那样可能改变签名对应的内容。下面的处理函数使用标准 Request、Response；commitCreditPurchase 是应用需要接入的数据库事务，下一段说明它必须完成什么。

import { verifyWebhook, type WebhookEvent } from "@waffo/pancake-ts";

export async function receivePayment(
  request: Request,
  commitCreditPurchase: (event: WebhookEvent) => Promise<void>,
) {
  const body = await request.text();
  let event: WebhookEvent;
  try {
    event = verifyWebhook(body, request.headers.get("x-waffo-signature"), {
      environment: "test", // 这段示例只接测试通知
    });
  } catch {
    return new Response("Invalid signature", { status: 401 });
  }

  if (event.mode !== "test" || event.storeId !== process.env.WAFFO_STORE_ID) {
    return new Response("Wrong environment or store", { status: 403 });
  }
  if (event.eventType !== "order.completed") {
    return new Response("Ignored", { status: 200 });
  }

  try {
    await commitCreditPurchase(event);
  } catch {
    return new Response("Not committed", { status: 500 });
  }
  return new Response("OK", { status: 200 });
}

SDK 提供通知验签和内置环境公钥，但这不替代店铺核对和业务处理。示例明确限定测试环境，正式部署时要一起切换密钥、通知配置、验签环境和业务数据，不能让测试事件增加正式余额。验签契约见通知 API 文档。

业务侧怎样保证只发一次

commitCreditPurchase 不只是一次 balance += 30。下面是应用需要实现的事务要求，示例代码尚未实现。它应当在同一个数据库事务中：

  1. 按 data.orderMerchantExternalId 找到并锁定本地购买记录，确认用户、套餐和环境；未知订单不能凭通知临时创建。
  2. 核对 orderStatus=completed、paymentStatus=succeeded、币种，以及平台订单和付款标识，必要时查平台订单确认商品。金额核对要区分套餐原价、税额和实际收取金额；本例不启用优惠券和动态价格，不要把所有金额字段都当成同一个数。
  3. 对通知建立唯一键，例如 (mode, storeId, eventType, eventId)。order.completed 的 eventId 对应付款 ID；还要对购买记录的发放状态和权益流水做唯一约束，防止另一笔付款或主动补单再次给同一次购买加次数。
  4. 检查这次购买已记录的成功退款及累计退款范围，按公示规则计算仍可发放的次数。全额退款后不再发放；部分退款只影响对应购买批次，不能直接作废整包，也不能把已退权益重新加回来。
  5. 写入付款记录和权益流水，按计算结果增加次数；没有退款时，本例增加 30 次。同步更新购买记录的发放状态，事务提交成功，或确认同一事件已处理完，才让通知入口返回 200。

上面的唯一约束和发放事务属于自己的业务实现。单纯在内存里记住通知 ID，进程重启后就失效；先标记“处理过”再写余额，写库失败时则可能永远少发一次。数据库故障返回 500，应与验签失败分开处理，不能统一报成“签名错误”。

若同一购买关联到了另一笔成功付款，应记录异常并进入核对或退款处理，而不是默默吞掉这笔钱。通知没到时，返回页可以请求自己的服务端补查，由服务端通过平台的订单与付款查询确认付款与退款结果，再复用上述事务处理。定时补单也走同一条路径，不能绕过退款检查直接补发 30 次。

退款也要锁定同一笔购买

退款要另接 refund.succeeded，不能用上面忽略其他事件的分支代替退款处理。退款申请已受理也不等于退款成功，流程见退款指南。

应用处理退款时，应与付款发放锁定同一条购买记录，在事务中按退款 ID 防重，记录成功退款事实、原购买与付款的关联，以及本次金额和累计退款范围。即使退款通知先到、权益流水还没创建，也必须先保存这些事实，供后续付款通知和补单检查；找不到本地购买的退款应保留待核对，不能凭通知新建购买。不能把每次退款通知都当成新的扣减，也不能把一笔部分退款直接标成整包失效。

已发放的次数按购买批次、已用次数和公示规则处理，退款与消费也要保持该批次余额一致。用户已经用掉 8 次时，直接从总余额扣 30，可能把另一笔购买的次数也扣掉。无论退款先到、付款先到，还是两者并发处理，已经退掉的权益都不能被后续发放或补单恢复。这些同样是应用需要实现的要求。

测试时，要故意让通知来两次

先用后台的 Send Test Event 检查通知地址和验签；它是样例事件，不代表有一笔真实购买，也不应凭空生成业务订单。之后在平台测试收银台走一次完整购买，才能核对账号、商品、外部订单号和次数是否串在了一起。

官方测试卡中，4576 7500 0000 0110 用于成功付款，4576 7500 0000 0220 用于失败付款，配未来有效期和任意三位 CVC，仅用于测试环境。至少检查这些结果：

操作业务系统应有的结果
一次成功付款原购买记录变为已发放，余额增加 30 次
失败付款，或未付款时只访问返回页不增加次数
重复投递同一事件返回成功，余额不再增加
修改通知内容，保留原签名验签失败，不修改业务记录
让发放事务失败后再重投失败时不确认；恢复后只发一次
付款后关闭浏览器服务端仍能确认并发放，重新登录可查到结果
全额退款通知先到，再补到付款通知先记录退款事实，之后不发放已退款的次数
部分退款通知先到，再处理发放按累计退款范围和公示规则，只发本批次仍应交付的次数
重复投递同一笔退款通知退款只记一次，不重复扣减本批次权益
退款与发放或消费并发锁定同一购买并保持批次余额一致，不超发、不重复扣减、不恢复已退权益

本文两段 TypeScript 片段做了类型检查，并用本地模拟请求核对 SDK 参数传递和通知入口的错误分支。这些检查没有调用 Waffo 测试收银台，也没有实现上面的数据库事务。表中的付款、退款、并发和补单场景仍是待执行的业务验证与平台联调要求，并非已通过的测试结果。

小额订单，先把费用算进去

按查阅时的 Pancake 费用说明，银行卡和数字钱包的成功交易费为 3.9% + 0.50 美元；微信支付为 3.9%，没有这笔固定费。具体可用支付方式仍取决于产品、币种和收银台，不能拿 Waffo 整个平台的渠道数量当作个人账号都能使用的清单。

只按卡支付手续费计算，卖 10 美元扣 0.89 美元，剩 9.11 美元，尚未计入税务、退款、提现、汇兑及收款行等因素。如果拆成十笔 1 美元，固定费累计就要 5 美元。这也是次数包需要单独考虑定价的原因。

退款和提现也要一起看：卡及数字钱包每次退款处理费为 1 美元，原交易手续费不退；提现费为金额的 1%，每次至少 10 美元。费用页另列出了特定失败交易和拒付的收费，不能只按“成功时扣费”估计全部成本。比如提取 500 美元，1% 本来是 5 美元，但按最低费用要扣 10 美元，汇兑与银行费用还需另核对。

收到付款，不等于已经到银行卡

在头像菜单的 Profile 完善个人身份资料，再进入 Payout Accounts 添加收款账户。法定姓名须与证件一致，账户持有人使用该身份资料。当前文档列有中国内地银行卡、个人支付宝等提现方式，支持的银行以实际列表为准；这里的支付宝是开发者的提现去向，不等于买家已经能用支付宝付款。身份填写和收款账户说明给出了具体字段。

按提现流程描述的常规路径，销售款先在店铺侧等待约 10 个工作日，再自动转入商户余额，工作日按香港节假日日历计算。可提现金额超过 10 美元后，到 Finance 手动申请提现；银行卡通常在申请后还需要 1～3 个工作日到账。Finance 读取真实资金数据，提现不能在 Test Mode 中模拟。

开发者服务条款还规定，可提现余额取决于平台或支付渠道是否已实际收到资金，以及费用、退款、拒付等扣减；身份资料未通过核验、风险准备金或资金扣留也会影响提现。实际能否提现，以后台可提现余额为准，到账时间、汇率和限制还需看申请页及渠道结果。

MoR 承接的是协议范围内的交易税务，不会自动免掉开发者自己的所得税、申报和产品合规责任，这些分工见开发者服务条款。

准备上线时，先等店铺审核通过，将测试商品发布到正式环境，再配置正式 API Key 和正式 Webhook，核对商品价格与退款规则。对这个图片工具，接入完成的标志是：一笔属于指定账号的付款，能在关闭浏览器、重复通知和写库重试后，仍然准确发放那 30 次处理；之后再单独核对第一笔真实资金的结算与提现。
