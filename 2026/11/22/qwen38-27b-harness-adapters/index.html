Qwen3.8-27B Harness 适配器实测：Pi、DSH 与验收漏测

 月影  2026-11-22  AI Agent Qwen LoRA Hugging Face
Agent Qwen LoRA Hugging Face

阅读次数:

本地首轮测试只有三道 Go 修复题。在 Pi 里，Qwen3.8-27B 加载 LoRA 后，三份答案都通过了原验收。复查其中的退避函数，才发现一个大数输入本该返回上限，实际却算出了 4ns。

Hugging Face 在 11 月 20 日发布了 Harness Adapters 的训练方案：冻结 Qwen3.8-27B 的基座权重，让它在 Pi、OpenCode 和 Hermes Agent 内执行任务，用强化学习分别训练 LoRA，产物可直接下载。

本文依据截至 2026 年 11 月 22 日的公开资料，先说明适配器怎样工作，再看本地 Pi 和 DeepSeek Harness 的执行结果。实测使用 GGUF 和三道公开教学题，没有复跑训练或官方 BF16 基准，业务自动化、视觉任务及其他工具环境尚未测试。

适配器改的是模型，工具仍由 Agent 执行

这里的 Harness 就是围绕模型运行的 Agent 程序：把任务、系统提示和工具说明交给模型，执行工具调用，再送回文件内容、命令输出或错误。上下文何时压缩、任务何时结束，也有它参与控制。

工具名称相同，反馈也未必一样。读文件可能一次返回全文，也可能分段；命令超时可能留下部分输出，也可能直接报错。模型下一步怎么做，取决于它实际收到的内容。

Hugging Face 保留 Pi、OpenCode 和 Hermes 各自的执行流程，让模型在真实 Agent 内完成任务，再根据验证器给出的奖励更新 LoRA。博客里的 DeepSeek Harness 专栏主要拆宿主的任务管理；这里改变的是模型如何使用宿主提供的工具。

适配器装在模型侧。以 Pi 适配器的配置文件为例，下面只摘录几个字段：

{
  "base_model_name_or_path": "Qwen/Qwen3.8-27B",
  "peft_type": "LORA",
  "r": 32,
  "lora_alpha": 64,
  "peft_version": "0.21.2"
}

按 PEFT 的 LoRA 机制，权重更新表示为两个较小矩阵的乘积，原权重冻结，训练只更新这部分参数。推理时可以同时加载基座和适配器，也可以把更新合并进基座，得到独立模型。配置里的 peft_version 记录产物使用的版本。本例分开加载适配器权重和原来的 27B 基座；适配器不能单独推理，内存要按整套模型估算。

在 Pi 里修三道 Go 题

配套代码放在案例仓库的 qwen38-harness 目录。它用 Go 准备任务、采集数据和判分，分别调用真实的 Pi 1.5.2 与 DSH 0.2.2-rc.1，工具循环和原生工具由各自 CLI 提供。

三道题分别修复字节大小解析、带上限的指数退避、CSV 记录编码。每次都从相同的错误实现、任务说明和可见测试开始，只允许修改 solution.go。Agent 退出后，再把答案交给外部 Go 测试判分。这组公开小题用来观察执行过程。

本机是 48 GB 内存的 M4 Pro，实际使用 llama.cpp 0.6.0、Metal、Qwen3.8-27B 的 Q4_K_M 基座，以及官方 F16 Pi LoRA。两个文件下载后，完整 SHA-256 均与 Hugging Face 公布值一致。

两组共用这一份基座，请求里的 LoRA scale 分别为 0／1。两次短推理探针返回了对应 scale，token 概率输出也发生变化。Pi 和 Go 判分器放在独立容器里，没有向 shell 挂载博客和案例源码。

上下文为 16384，thinking off，温度 0.8，每次 Agent 最多运行 5 分钟。先各跑一轮，再用相同参数追加两轮，共 18 个计分试次。首轮结果如下，完整参数和文件哈希见首轮实测记录。

首轮六个试次按原验收 V1 判分，截图由保存的运行记录导出。这时还没发现验收里的漏测。

字节解析题的基座反复修改代码、补边界测试，300 秒到时留下了一个未使用变量，外部编译失败。退避题正常结束了，却把 Delay(2, time.Nanosecond, 10*time.Nanosecond) 算成 10ns，正确值是 2ns。它自己跑过的可见测试没有检出这个错误。

按 V1 验收，首轮 LoRA 通过三题，基座通过一题。双方都通过的只有 CSV 一对：基座约 81.3 秒，LoRA 约 69.9 秒。字节解析基座的 token 用量保留为缺失，没有拿中断前的部分计数充当完整用量。

追加两轮的结果

首轮每题只跑了一次，又按预定计划补了两轮，共 12 个试次。任务、提示、权重、采样参数和预算沿用首轮，两组继续交替执行，中途没有按成绩增删试次。追加时用 -runs 2 -run-offset 1 承接已完成的首轮，从第 2 轮编号，保留首轮文件。

三轮共 18 个计分试次，V1 下基座通过 4/9，LoRA 通过 9/9。18 次均可评分，逐次结果见三轮实测记录。

基座的字节解析题在第 2 轮通过，第 3 轮却把合法输入 12B 当成非法数字。退避题后两轮都正常结束，但在大数输入下返回了溢出的负时长。可见测试每题只有一个简单输入，跑绿并不能覆盖题目要求；外部验收采用整题通过制，一个边界错误就会让整次失败。

通过验收的代码，算出了 4ns

开头的 4ns 就出在首轮 LoRA 的退避代码里。它在移位后检查 d <= 0，能拦住部分溢出，却漏掉了溢出后仍为正数的情况：

attempt = 3
base    = 4611686018427387905 ns
limit   = 9223372036854775807 ns

预期：返回 limit
实际：返回 4 ns

V1 没有这个输入，给了这份错误答案一个“通过”。V2 扩充到字节解析 58 个用例、退避 40 个、CSV 26 个，保留 V1 的输入，再加入非法前缀、单位乘法边界、正数回绕、符号位溢出和 CSV 转义等情况。周围空白仍按原参考实现的 strings.TrimSpace 处理，检查换页符、纵向制表符和不换行空格等字符。

参考答案全部通过 V2、已知错误被检出后，再重判保存的 18 份原答案，没有改答案或重新调用模型。V2 补测记录保留了逐用例结果、测试文件哈希和原始输出哈希。

同一份 Pi LoRA，换到 DeepSeek Harness

DeepSeek Harness（DSH）是另一套 Agent 宿主。它用 Cordis 插件装配模型适配层、工具、会话和执行循环，也能通过 OpenAI 兼容接口接本地模型。这里的 DeepSeek 指宿主项目，下面仍然使用同一份 Qwen 权重。

这次继续使用 Pi 专用 LoRA，观察它离开训练宿主后的表现。提示、工具和会话由 DSH 提供，装配方式见官方架构文档。

要检查的变化保持什么相同更换什么

DSH 内的迁移效果DSH、题目与运行预算基座／启用同一份 Pi LoRA

两边都有 read、write、edit、bash，参数却不同：DSH 文件路径用 file_path，命令还要求 description。

驱动器通过 -harness deepseek-harness 选择官方 headless 入口和原生四工具，完整安装与容器命令在案例说明里。llm-pi-ai 插件复用了模型协议库，执行循环、文件和命令工具仍是 DSH 自己的。

DSH 容器使用 Node 24.9.0、Go 1.27.2，继续连接本机 Metal 模型服务。Go 网关只转发模型请求，固定温度、top_p、4096 输出上限、thinking off 和 LoRA scale；DSH 生成的提示、历史及工具定义保留不动，完整请求也会保存。

这次三题、两组各跑一次，共六个试次。V2 在开始前已经固定，结束后直接用它验收原答案。DSH 真实运行和 V2 判分记录了原始执行和验收结果。

LoRA 的字节解析漏了不换行空格和 em space，退避题把 attempt=2, base=5ns, limit=11ns 算成 11ns，正确值应为 10ns。CSV 的错误更直接：标准库输出已经带 LF，代码又追加一次 LF，24 项用例因此失败。这些都是运行结束时留下的原答案。

还有四次运行停在 300 秒上限，两组各只有一次正常结束。基座虽然是 3/3，其中两次验收的是超时时留下的代码，Agent 尚未完成整轮执行。超时 token 总量记为未知；双方都通过且正常结束的配对一个也没有，效率中位数只能留空。

在这六个试次里，Pi LoRA 组的 V2 通过数低于基座组。但 DSH 每题每组只跑一次，Pi 已跑三轮；原生提示里的模型别名、临时目录，以及 Node 版本和运行时段也不同。这批初测记录了迁移后的失败，尚不足以说明差异能否重复，也不能给 Harness 排名。

官方方案补充：适配器怎样训练

以下训练流程与评测数据来自 Hugging Face 的公开资料，本地未复跑。4ns 的漏测也关系到训练：错误补丁一旦通过验证，就可能拿到奖励。Hugging Face 把已安装的 Agent 放进任务环境，采集实际操作，而非只让模型学习工具调用的文本格式。

Hermes 适配器的训练配置中，每个任务采集 8 次尝试，奖励由验证器正确性和权重为 0.1 的工具效率奖励组成。GRPO 比较同一任务的多次尝试；每次奖励都一样，这一组就没有相对优势可比较。

公开的任务数据集保留了验证、难度筛选和拒绝记录，也包含未验证候选。使用时要检查配置和 split，整库下载不等于拿到一份全部合格的训练集。

TRL 的 Harbor 示例通过 OpenEnv 运行任务，推理引擎记录 token ID、概率和训练掩码，用于更新模型。掩码区分提示、工具反馈与模型生成内容，事后将聊天文本重新分词不能替代这些记录。AsyncGRPOTrainer让采样与更新重叠，部分采样仍用较早的参数，因此还要限制样本的陈旧程度。

执行环境另装了 safeagents 的任务插件，检查工具调用规则，并处理正常调试被误拦的情况。这些插件与规则需部署在执行链路中，加载 LoRA 不会自动带入。

数据分别来自 Pi、OpenCode和 Hermes Agent模型卡。Terminal-Bench 2.1 共 89 题，部分环境或验证器故障使成对题数少于总数。模型卡还提供了另一张四种配置的汇总表，按四者共同可评分的任务取交集；这里采用的是基座与对应适配器的成对结果，不能混着取数。

Pi 第一行的增幅是 25.5 个百分点，比较的是同一评估设置下的基座和适配器。不同宿主的工具、历史处理和失败条件都不同，基座分数也不一样；这些行各自回答“加载适配器后怎样变化”，没有提供三个 Harness 的同条件排名。

发布检查点的选择还看过 SWE-bench Pro 分数和 Terminal-Bench 的 18 题子集，这部分数据参与过挑选，不能算完全独立的盲测。OpenCode 模型卡另列了 66 道未用于挑选检查点的 Terminal-Bench 任务，结果为 45.5% → 59.1%；完整 84 题的增益为 6.0 个百分点，统计区间包含零，仍有较大不确定性。

共同成功的任务，少用了多少 token 和工具

Pi 模型卡还统计了基座和适配器都解出的 32 道 Terminal-Bench 任务：生成 token 数中位数从 2.9k 降到 1.5k，交互轮数中位数从 18 降到 8。先限定双方都成功，再比较用量，就不会把提前放弃算成省 token。

这里的中位数描述共同成功的任务，不是全部任务的平均用量，也不是账单折扣。模型生成、提示预填充、工具执行、缓存和失败重试都会影响成本。

Hermes 的共同成功集有 31 道 Terminal-Bench 任务，工具调用次数中位数是基座 23 次、适配器 7 次。

thinking 模式也要单独看。Pi 模型卡记录，适配器关闭 thinking 后，工具调用之间仍会生成更多简短解释文字；关闭这个模式不等于不再推理。若拿它与开启 thinking 的基座比较，必须列明两边的模式和预算，额外的推理预算不能省略。

多个宿主共用 Super-adapter

如果只用 Pi，可以直接评估 Pi 的专用适配器。要为多个 Agent 维护模型服务，Hugging Face 还提供了 Super-adapter。

合并方法是把三个专用 LoRA 的权重更新各乘以 1/2 后相加，通过矩阵拼接得到 rank 96 的适配器，合并时没有再次训练。推理时将这个适配器与基座一起加载，无需跑三个模型投票；分别平均 A、B 矩阵也得不到同样的结果。

部署一个产物更方便，但专用版的收益没有全部保留下来。模型卡因此建议，单个 Harness、关闭 thinking 时优先试专用版；跨多个 Harness，或准备开启 thinking 时再评估 Super-adapter。

合并权重的选择用过 Terminal-Bench 数据，该部分结果可能偏乐观，不同模式和题目交集的分数也要分开看。本地 DSH 初测用的是 Pi 专用版，未测试 Super-adapter。

复现入口

先检查判分器。在 Go 1.25 及以上、macOS 或 Linux 环境执行：

cd blog-go-example/qwen38-harness
go test ./...
go run . selfcheck

自检输出：

bytesize: buggy=rejected reference=accepted
retry-delay: buggy=rejected reference=accepted
csv-record: buggy=rejected reference=accepted
selfcheck passed: 3 graders checked; no Pi or model invoked

自检只检查已知答案，没有调用模型。正式运行时，判分放在 Agent 退出之后：只把最终答案文件复制到外部临时目录，放入固定的 go.mod 和验收测试，再执行：

cmd := ownedCommand(ctx, "go", "test", "-json", "-count=1", "-timeout=10s", ".")
cmd.Dir = dir

完整判分函数在案例的 grader.go。ownedCommand 会在超时后终止子进程组，判分还会检查 JSON 中的 TestAcceptance 和包级通过事件，退出码为零不够。Agent 对可见测试的修改不会复制进验收目录。临时目录并不隔离系统权限，实际执行 bash 仍应放在专用测试环境中。

Mac 实测与 BF16 部署入口

上文 Mac 实测使用 llama.cpp，启动参数与容器命令见案例说明。案例另外提供了 serve-vllm.sh，按固定修订的 BF16 基座和 Pi LoRA 本地快照，在同一个 vLLM 服务暴露 qwen-base、qwen-pi 两个名称。这条 GPU 部署路径尚未在本机执行，下面的命令使用它的接口地址：

go run . run \
  -pi /tmp/qwen38-pi-runtime/node_modules/.bin/pi \
  -url http://127.0.0.1:8000/v1 \
  -base-model qwen-base -adapter-model qwen-pi \
  -runs 3 -timeout 5m -out results/qwen38-first

这条命令一次跑完三题、两个条件、每题三次，共 18 次 Agent 运行。两组工具相同，temperature 0.8、top_p 1、thinking off，每次生成最多 4096 token，先后顺序交替。预算没有照搬官方的 100 步。前文本地实测采用先跑首轮、再追加两轮的采样顺序，无需在这条三轮命令后再追加。

results.json 保存判分、工具次数、时间和任务哈希，events.jsonl 保存执行过程。工具次数和耗时只统计双方都通过、且正常结束的配对；token 还要求两边 usage 完整，缺数记为 null。API 或事件格式故障另记为不可评分，实验命令也会报错。

接模型前，用脚本服务检查过 Pi 的读写、测试和统计流程。那一组只验证接口，前文的实测数据来自实际加载 Qwen 权重的运行。

首轮曾遇到容器结果存储问题，四个已完成结果保留，一次主动中止的 CSV 基座尝试单列，不计入这 18 个试次。追加批次前重启过模型服务，之后没有逐次清缓存，随机种子也未控制。原始轨迹、答案和外部验收输出均已保留。

先补验收，再判断适配器的收益

补上正数回绕用例后，开头那份算出 4ns 的代码才被拒绝。LoRA 组同一批答案从 9/9 变成 6/9，模型没有重跑，改变的是验收测试。后续可以沿用 V2 检查新答案；跨宿主的收益是否稳定、实际能否提速，还要重新采样验证。
