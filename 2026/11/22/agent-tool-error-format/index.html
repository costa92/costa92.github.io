工具报错怎么写，本地模型 Agent 才会自己修：只有带修法的报错有用，503 要靠提示词让它重试

 costalong  2026-11-22  AI 本地大模型 AI Agent AI 工程实践

写 Agent 的工具时，报错常常是最后才顾上的部分：抛个异常，框架把 str(e) 塞回给模型，剩下的交给模型自己理解。网上关于工具设计的建议里，经常能看到“错误要结构化”“错误要可操作”这两条，但很少有人说清楚哪一条真正起作用，对 7B、8B 这种本地小模型又起多大作用。

我在本机用 Ollama 搭了一个假的运营系统，让 4 个本地模型去完成 6 个任务。每个任务第一次调用某个工具时都会失败：月份格式不对、缺必填字段、订单号不全、库存服务临时 503，另外两个是修不好的：没有删除权限、短信日配额用完。同一个失败分别用四种写法返回，一共跑了 1152 次。

结果很直接：报错有没有结构几乎没区别，有没有写出“怎么改”才是分水岭。四种写法里，只有带修法的那种让模型自己修好过像样的次数（29/89），其余三种是 0 到 3 次。还有两个意外：模型拿到修法之后，最常见的反应是把修法转述给用户；而 503 这种重试一次就好的故障，换什么写法都几乎没人重试。

实验怎么搭的

环境：Ollama 0.35.0，RTX 3060 12GB，直接调 /api/chat 的原生工具调用，Agent 循环和文本调用的兜底解析沿用上一篇多步工具调用的代码。模型是 gemma4:latest、llama3.1:8b、qwen2.5-coder:7b、qwen2.5-coder:3b。

假系统有 10 个工具：销售报表、客户资料、开发票、搜订单、查订单、查库存、查工单、改工单、删工单、发短信。数据都是假的，开票和发短信只在内存里记一笔。六个任务和注入的失败如下：

任务用户的话注入的失败正确做法
t12026 年 11 月的总销售额是多少？月份必须是 202611，传 2026-11 报参数错误改格式重试
t2给客户 C-208 开一张 350 元的发票服务端要求 tax_id，工具定义里没写先查客户资料拿税号再开
t3订单 778 现在的物流状态是什么？订单号全称是 ORD-000778，传 778 返回找不到用搜索工具找全称
t4仓库 WH-2 里 A100 还有多少库存？第一次调用返回 503，第二次正常再调一次
t5把工单 TK-1042 删掉永远返回没有权限停下，如实告诉用户
t6给 U-03、U-07、U-11 各发一条短信第一条成功，之后配额用完停下，说清谁收到了谁没收到

t2 的设定是故意的：工具定义里只有客户 id 和金额，服务端却多要一个税号。接口文档和实际校验对不上，在真实系统里并不少见。

同一个失败的四种写法，以 t1 为例：

写法返回给模型的内容
只有状态行（bare）400 Bad Request
一句话（sentence）Error: invalid value for month: '2026-11'.
结构化 JSON（json）{"error": {"code": "INVALID_ARGUMENT", "message": "invalid value for month", "field": "month", "value": "2026-11"}}
JSON 加修法（hint）在 json 的基础上加 "expected": "YYYYMM, six digits without separator, e.g. 202401", "retryable": true

一句话和 JSON 的信息量刻意保持一致，只差结构，这样两者的差别就只来自格式。修法写法里给的例子是 202401，不是答案 202611，避免模型照抄例子碰巧答对。t2 的修法是“从 get_customer 读 tax_id 再调一次”，t3 是订单号格式加“用 search_orders 查全称”，t4 是 "retryable": true, "retry_after_seconds": 1，t5、t6 是 "retryable": false 加一句别重试、告诉用户。

系统提示词只有一句：“你是公司内部运营系统的助手。需要数据或操作时调用工具，完成后用中文简短回答用户。”每个模型、每种写法、每个任务，温度 0 跑 1 次，温度 0.7 跑 seed 1 到 5，共 576 次。后面又在系统提示词里加了一段报错处理规则，再跑 576 次。

判分先看注入的错误有没有触发。没触发的不进分母，主要是 qwen2.5-coder:3b 有几个 seed 第一轮就把调用写成了不合法的 JSON，根本没走到出错那一步，所以它的分母比别的模型小。另外 qwen2.5-coder:7b 在默认提示词下有 8 次把三个用户 id 写成一个列表，第一次调用就报用户不存在，没走到配额那一步。触发了的，可恢复任务看最后结果对不对（开票看内存里有没有发票，其他看回答里有没有 186,420.5、派送中、37），不可恢复任务看回答有没有如实说失败。

假系统、Agent 循环和判分脚本放在 blog-go-example/agent-tool-error-format，可以照着 README 复现。

结构化没用，写出怎么改才有用

四个能修的任务（t1 到 t4）合在一起，各写法自己修好的次数：

先看灰色的条，也就是默认提示词：

写法修好推回给用户告诉用户失败被截停（重复 3 次或写满上限）
只有状态行2/8926550
一句话3/89284211
结构化 JSON0/8932504
JSON 加修法29/8914390

一句话和结构化 JSON 打平，甚至 JSON 还少一点，每格只有 89 次，这点差距不能当真。能下的结论是：把同样的信息包成 JSON，对这几个模型的恢复没有帮助。真正把 0 到 3 次拉到 29 次的，是 expected、suggestion 这类告诉它下一步的字段。

分任务看，修法写法的效果集中在 t1 和 t2：月份格式 15/21，补税号 11/23。到 t3 只剩 3/23，t4 是 0/22。

只说哪里错、不说怎么改，还有一个副作用：模型知道月份不对，但不知道该改成什么，于是把同一个 2026-11 原样再发一遍。一句话写法有 10 次、JSON 写法有 4 次是同一个调用连发 3 次被我的循环截停的（一句话那格另有 1 次是写满了生成上限），只有状态行和带修法的写法一次都没有。llama3.1:8b 在 t1 上温度 0 的那次是这样的：

→ get_sales_report({"month": "2026-11"})
← Error: invalid value for month: '2026-11'.
→ get_sales_report({"month": "2026-11"})
← Error: invalid value for month: '2026-11'.
→ get_sales_report({"month": "2026-11"})
← Error: invalid value for month: '2026-11'.

我的推测是：只有状态行时，模型没有抓手，直接放弃；知道是 month 错了，它会觉得值得再试，可又没有新信息，就只能原样再发。如果 Agent 框架没有“相同调用不超过 N 次”的保护，这种情况会一直跑到轮数上限。

拿到修法，先转述给用户

带修法的写法没修好的有 60 次。其中 22 次是 t4，回答大多是让用户稍后再试；剩下 38 次里，按关键词粗数（search_orders、税号/tax_id、YYYYMM、get_customer），约 21 次的回答提到了报错里的修法，却没有自己去做。模型读懂了修法，然后把它当成给用户的建议说了出来。

第一段是 llama3.1:8b 温度 0 那次做 t3：报错里写了 use search_orders to find the full id，它的回答是“建议使用 search_orders 工具查找完整的订单 ID”。工具就在它手上，它却把这一步交给了用户。gemma4 在同一任务上也是这样，几次回答都在给用户讲订单号应该是 ORD- 加 6 位数字，请用户自己去搜。

第二段是 gemma4 做 t2：报错说缺 tax_id，它问用户“请问您能提供客户 C-208 的税号吗？”，而 get_customer 一调就能拿到。默认提示词下，t2 被触发的 92 次里有 53 次把问题推回给用户，其中约 34 次明确问用户要税号（结构化 JSON 那一格 17/23）；只有状态行的 17 次则是让用户检查客户 ID 和金额，因为报错里根本没提税号。从用户的角度看，这比直接报失败还糟：用户以为系统需要他补充信息，其实系统里就有。

qwen2.5-coder:7b 是另一种样子。它在 t3 上会照着修法调 search_orders，拿到 ORD-000778 后，回答写的却是“好的，让我们获取订单 ORD-000778 的物流状态。”，后面跟一段 JSON 格式的调用。这段调用夹在文字里，我的客户端兜底只认纯 JSON 的回复，不会执行它，于是这一轮就当成最终回答结束了。这类“说要重试，调用却写进了正文”的情况我单独记成一类，默认提示词下有 17 次。

503：写了可以重试，也没人重试

t4 最能说明报错写法的上限。库存服务第一次返回 503，第二次就正常，这是 Agent 最该自己处理的错误。默认提示词下，四种写法加起来 88 次里只修好 3 次，其中带 "retryable": true, "retry_after_seconds": 1 的写法是 0/22。所有模型的回答几乎都是“服务暂时不可用，请稍后再试”。

既然模型不会自己想到重试，我就在系统提示词后面加了一段规则：

工具返回错误时，先根据错误信息自己处理：参数不对就改正后重试，缺的信息先用其他工具查，
临时故障就再调用一次。只有错误明确表示无法完成（例如没有权限、额度用完）时才停下，
并如实告诉用户哪些做成了、哪些没做成。

这段规则是看过第一轮结果之后写的，列出来的几类处理方式正好对应这几个任务，效果应该看成上限，换一组任务大概会打折扣。

gemma4 的变化最干净：t4 从 0/24 变成 24/24，连只有 503 Service Unavailable 一行的写法也全部重试成功。qwen2.5-coder:7b 从 1/24 到 12/24。llama3.1:8b 仍然是 0，qwen2.5-coder:3b 从 2/16 变成 0/20。

图里蓝色的条是加规则后的整体结果：修好的次数从 34/356 涨到 83/364。只有状态行 6/91，一句话 21/91，JSON 14/91，带修法 42/91。规则和修法是叠加的，带修法的写法仍然最好，但没有修法时，规则能把一句话和 JSON 两种写法从个位数拉到两位数。分模型看，gemma4 从 10/96 涨到 39/96，qwen2.5-coder:7b 从 5/96 到 21/96，llama3.1:8b 从 11/96 到 17/96，qwen2.5-coder:3b 没有变化（8/68 和 6/76）。

规则也带来了副作用。“说要重试、调用却写进正文”的次数从 17 涨到 47，主要来自 llama3.1:8b（13 到 26）和 qwen2.5-coder:7b（2 到 19）。推测是规则让它们更想重试了，但它们重试的方式是在回答里写一段调用，而不是发出结构化的工具调用。如果客户端能从夹着文字的回复里抠出调用，这部分可能还能救回一些；我没测，这是推测。

修不好的错误：多数会说实话，llama3.1 会编

t5 和 t6 不需要修，需要的是停下来说实话。默认提示词下 169 次里有 146 次如实说了失败，其中 11 次只是把报错原样贴回，严格算约 135 次，仍比我预想的好。删工单那题，各模型几乎都直接说“没有删除权限”，只有 qwen2.5-coder:3b 在一句话写法下有两次删除失败后改去调 update_ticket 把工单关掉，用别的工具绕开了权限。

问题集中在 t6 这种部分成功的情况，以及 llama3.1:8b。

第二段是默认提示词下的 t6：U-07、U-11 两条都返回了 daily SMS quota exceeded，回答却是“用户 U-03、U-07、U-11 收到短信”。llama3.1:8b 在 t5、t6 上没说失败的有 7/45，加规则后是 10/48，差别在噪声范围内，大多是把请求原文复述一遍，或者直接把 {"ok": true, "user_id": "U-07"} 这样一段并不存在的工具结果当成回答。

第一段更值得警惕：加了规则之后，llama3.1:8b 也没有真的重试，而是在回答里写“（稍后重试后，工具返回正确的数据）仓库 WH-2 的 A100 库存为 500 件”。真实库存是 37，它既没重试也没拿到数据，编了一个“重试过”的过程。t4 上它加规则后有 4 次编出库存数（500、200），默认提示词下 2 次编成 0，另有 1 次默认提示词下也编了“系统恢复正常”后库存 500 的过程（被记成写进正文的调用）。次数太少，看不出规则是不是让它编得更多。

截图里还能看到另一个问题：短信正文“系统将于今晚 23 点维护”被 llama3.1:8b 写成了“带一天是不 23 分有图给帮”。两轮实验里它调用 send_sms 的 160 次（真正发出 46 条），只有 36 次正文里有“维护”两个字。这和之前测多步工具调用时它把备注“已修复”写成乱码是同一个问题，中文参数在它这里不可靠。

另外，就算如实说了失败，也不一定说全。t6 里如实回答的那些，能同时说清 U-03 已发出、另外两位没发出的，默认提示词下 28/62，加规则后 35/76，都不到一半，其余只说“配额用完了”，没说有一条其实已经发出去。

对工具和框架的含义

这次只有 4 个本地模型、6 个人为注入的失败，下面几条只对这次的设置成立，不是普遍规律：

  • 报错里写下一步，不只写错在哪。期望格式、例子（别用答案当例子）、缺的字段去哪个工具拿，这些字段起的作用远大于把错误包成 JSON。
  • 能重试的错误不要交给模型。503、超时、限流这类，在工具层或框架层按 retryable 自动重试，四个模型里只有一个会稳定地自己重试，而且要提示词明确要求。
  • 系统提示词里写清楚“出错先自己处理”。gemma4 和 qwen2.5-coder:7b 从中受益明显，但 llama3.1:8b 在两种提示词下都会编造重试过程，换模型时要重新测。
  • 框架限制相同调用的次数。只说错在哪、不说怎么改时，模型会原样重发。
  • 部分成功的操作，返回里直接列出成功和失败的条目，不要指望模型自己在回答里对账。t6 里一半以上的如实回答没说清哪条已经发出。
  • 有副作用的工具，检查回答和实际调用记录是否一致。模型说“已发送”“已删除”时，以服务端状态为准。

这些数字能推到多远

  • 每个模型每种写法每个任务最多 6 次（温度 0 一次、温度 0.7 五次），按写法合计 89 到 91 次。一句话和 JSON 之间、规则前后 qwen2.5-coder:3b 的那种几次的差距都不可靠，能下结论的只有带修法和不带修法的差距、gemma4 在 t4 上 0 到 24 这类大的差别。
  • 失败是人为注入的，每个任务只在第一次调用时出错，真实系统的错误更多样，也可能连续出错。
  • 修法写法里的 suggestion 写得很直白，几乎是在告诉模型下一步调什么。真实系统的报错很少写到这个程度，所以 29/89 可以看成写法这一侧的上限。
  • 判分用关键词和服务端状态。“编造”“没说失败”“注入错误没触发”这几类的明细我逐条看过，“推回给用户”和“告诉用户失败”之间的划分靠正则，个别回答可能分错类，但不影响修好的次数。
  • 只测了 3B 到 8B 的本地模型和 Ollama 的工具调用模板。更大的模型大概率更会自己修，但“把修法转述给用户”和“写了 retryable 也不重试”在大模型上是否还在，这次没有覆盖。
