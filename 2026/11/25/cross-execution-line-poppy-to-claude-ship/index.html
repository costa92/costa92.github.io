跨过执行线：从 Poppy 协议到 Claude Ship，AI Agent 如何接管真实工作流？

 costalong  2026-11-25  AI AI Agent MCP AI 工程实践 Poppy 协议

2026 年 11 月的十天里，出了两套专门处理“AI 真正改状态”的方案。11 月 13 日，Sierra 和 Meta 联合发布 Poppy 协议（Personal Agent Protocol）1.0，Shopify 给平台商家默认打开了支持，Meta 的个人智能体 Muse 访问网站时默认先查 Poppy 入口；11 月 23 日，Anthropic 发布面向 GitHub 的 Claude Ship，把自动审查、自动修 PR 和基于策略的自动审批拆成三个独立组件。

这两件事碰的是同一条线：读网页、写草稿、生成代码出错最多浪费一点 token，但替人在电商网站取消一笔未发货订单，或者把 PR 修完冲突并批准合入主干，每一次动作都会改掉真实系统的状态。不给写权限，Agent 只能停在建议阶段；直接放全量权限，外部网站防不住越权和风控，内部仓库也不敢让模型自己写代码又自己点 Approve。

本文根据 2026 年 11 月公开的 Poppy 1.0 规范资料、Sierra/Meta 及 Anthropic 官方发布信息整理，不含私有生产环境的实测数据。文中用来串起链路的“电商退单”和“PR 修冲突审批”是假设案例，引用的内部效率数字均标明官方出处；文末附了一套离线单进程 Go 代码，只验证签名、双层鉴权和策略求值，不连外部云服务。

Poppy 1.0：外部网站的请求怎么一步步升级权限

以前个人智能体想替人操作外部网站，基本只有两条路：模拟浏览器点击，容易触发 WAF 和验证码，页面一改版脚本就失效；或者让用户把账号密码、完整 Cookie 交给代理，等于交出整个账户，既没法限制它只查订单不改支付方式，网站服务端也分不清对面是恶意爬虫还是合法用户的个人助手。

Poppy 1.0 没有另起一套传输层，而是叠在 HTTPS、OAuth 2.1、JWT、OpenAPI 和 MCP 之上。用一个假设案例串一遍它的请求顺序：用户让个人智能体（比如 Meta Muse）先问某家电商“显示器支不支持七天无理由退货”，再查自己刚买的那单有没有发货，没发就取消。

商家先在 /.well-known/poppy.json 声明入口

Agent 进站先拉取 https://{domain}/.well-known/poppy.json。文件写清商家信息、鉴权服务地址、对外开放哪些 Scope，以及商家希望 Agent 走哪条通道——可以是 OpenAPI、基于 Streamable HTTP 的远端 MCP 服务，也可以是商家自己的客服 Agent 或受控 Web 会话端点。

{
  "protocol_version": "1.0",
  "organization": {
    "name": "Example Commerce",
    "domain": "example.com"
  },
  "auth": {
    "issuer": "https://auth.example.com",
    "scopes": {
      "orders:read": "查看订单历史与物流状态",
      "orders:write": "经用户授权后修改或取消待发货订单"
    }
  },
  "apis": [
    {
      "type": "mcp",
      "url": "https://mcp.example.com/v1",
      "description": "订单与售后远端 MCP 服务"
    }
  ]
}

拿到这份文件，Agent 不用去解析页面 DOM 或猜私有接口，商家也能把代理流量直接引到结构化通道上。

查退货政策：未登录态加 Poppy-Session JWT

按这个案例，第一步只是查退货政策，不需要登录用户账号。Poppy 规定会话默认处于未登录（signed-out）且隔离的状态，但每次请求都要带签名的 Poppy-Session HTTP 头，让商家验明代理身份。

全网成千上万个商家不可能提前给每家个人智能体手工注册 OAuth client_id。Poppy 用 CIMD（Client ID Metadata Document） 跳过预注册：代理的 client_id 本身是一个 HTTPS URL，指向自己的元数据文档（里面带 jwks_uri 公钥集）。商家按 URL 拉公钥即可验签。

Poppy-Session 的固定字段如下：

  • Header 声明 typ: "poppy-session+jwt" 和 alg: "ES256"，由短期委派密钥（poppy_dlg）签名。
  • Payload 包含代理的 client_id、会话标识 sid、目标商家域名 aud，以及一个成对用户标识（pairwise sub）。sub 由个人智能体针对单个商家生成，稳定但不透明，不同商家之间拿它拼不出跨站用户画像。
// Poppy-Session JWT Header
{
  "alg": "ES256",
  "typ": "poppy-session+jwt",
  "kid": "poppy_dlg_20261125"
}

// Poppy-Session JWT Payload（示例字段）
{
  "client_id": "https://muse.example.net/cimd.json",
  "sub": "pairwise-shop-9f8e7d",
  "sid": "sess-001",
  "aud": "shop.example.com",
  "iat": 1795612800,
  "exp": 1795613100
}

到这一步，Agent 带着签名头就能以访客态查完退货政策，全程不碰用户账号凭据；商家拿到 ES256 签名后，可以把合规个人代理和匿名爬虫分开限流。

取消订单：OAuth 2.1 提权与远端 MCP 双层请求头

接着查个人订单并取消，未登录态不够用了。Agent 按 poppy.json 里的 auth.issuer 发起带 PKCE 的 OAuth 2.1 授权码流程，跳到商家原生页面让用户登录，明确勾选 orders:read 和 orders:write。权限随时可以在商家侧撤销。

MCP 管的是模型怎么发现和调用工具，但协议本身不定义“这个 Agent 代表哪个自然人、拿了商家哪几项授权”。在 Poppy 1.0 里，远端 MCP 是官方支持的执行通道，写操作请求会同时带两个头：

POST /v1/orders/ORD-1001/cancel HTTP/1.1
Host: mcp.shop.example.com
Poppy-Session: eyJhbGciOiJFUzI1NiIsInR5cCI6InBvcHB5LXNlc3Npb24rand0In0...
Authorization: Bearer <resource-bound-oauth-access-token>

Authorization: Bearer 绑定目标资源 URL 和细粒度 Scope，管用户授权；Poppy-Session 管代理身份和无状态会话，防止令牌被转发到别的服务引发混淆代理人（confused deputy）问题。Poppy 还支持把 OAuth Scope 对应到 MCP 工具的 readOnlyHint、destructiveHint 标注，没拿到写权限的调用在协议层直接被挡掉。规范同时要求把远端返回内容严格当作数据处理，不作指令执行，用来压低间接提示词注入风险。

这套做法的成本在服务端。Shopify 给平台商家默认生成 poppy.json 解决了电商长尾，但自建系统和老 SaaS 仍要自己拆细 OAuth Scope、补接口幂等。另外协议只管权限边界，不管模型有没有理解错意思——就算权限卡死在 orders:write，模型如果把用户的口语听岔、取消了另一笔订单，协议层拦不住，高风险写操作在应用层还是得留二次确认。

Claude Ship：把 PR 合入前的活拆给三个独立角色

研发仓库里的问题反过来。编码 Agent 把写代码的速度提上去以后，时间主要耗在 PR 打开到合入之间：CI 挂了、主干有冲突、Review 提了几处修改、等同事抽空点批准。如果只挂一个全权 Agent 进仓库，写代码、修分支、审批、合并全由它做，模型在边界逻辑上判错时既没法拦，也不好追责。

假设开发者用编程 Agent 提了一个改了 12 个文件的 PR，刚推上去就撞上两件事：CI 里的 lint 和一条单测挂了，主干同时合进新提交导致两行冲突。Anthropic 11 月 23 日发布的 Claude Ship 把后续动作拆给了三个权责分开的组件。

Code Review（GA）

Code Review 结合仓库上下文从多个角度审 diff，并对自己初步找出的问题做一轮对抗式验证（adversarial verification）筛掉误报，再按严重程度分级发成行内评论。仓库可以按重要度选 Quick、Standard、Deep 三档深度。

Anthropic 官方披露了内部使用数据：Claude Code 团队启用后，6 月到 9 月合入的 PR 数量翻倍，代码回滚（revert）比例下降超过 40%。这是 Anthropic 自身重度依赖 AI 编码团队的数据，不能直接外推到普通业务仓库，但它反映了一个实际变化：代码产出变快后，先用自动化过滤一轮低级问题，人工审稿的噪音负担会明显下降。

PR Steward（Public Beta）

Review 意见和 CI 报错出来后，PR Steward 接管修分支的机械活：读失败的 CI 日志、解合并冲突、按 Code Review 或同事评论改代码，直接往当前分支推修复 commit。

它能往分支推代码，但权限被卡死了三处：

  • 每次 push 后都在 PR 下留评论，写明改了什么以及怎么回滚。
  • 开发者评论 @claude [指令] 可以纠偏，发 @claude stop 立即停掉它在当前 PR 上的后续动作。
  • PR Steward 被显式禁止执行 approve 和 merge，只负责把分支修绿。

Claude Approvals（Public Beta）

Claude Approvals 允许 Agent 给符合条件的 PR 点 Approve。团队在仓库默认分支放一份 .claude/approvals.yml，写法接近带条件判断的 CODEOWNERS：

mode: observe # 建议先用 observe 跑审计，确认误判率后再改 enforce

rules:
  - name: Routine Code
    paths:
      - "src/**"
      - "docs/**"
    if:
      - "claude/code_review"
    allow_claude_approval: true

  - name: Sensitive Paths (Billing/Security)
    paths:
      - "billing/**"
      - "security/**"
    seats:
      - count: 1
        from: [humans, "!pr/author"] # 至少 1 名非作者本人的人类工程师批准

配置时有三个细节不能漏：

  1. mode 省略时默认是 enforce（通过 GitHub Check 实际阻断合入）。官方建议先用 mode: observe 跑一段时间，只记录它会批哪些、拦哪些，拿真实 PR 对照人类审批再切 enforce。
  2. 要在 GitHub 分支保护规则（Branch Protection Rules）里把 Claude Approvals 设为必需检查项，策略才会真正挡住合入；最终能否 Merge 依然受 GitHub 原生分支保护约束，Claude Approvals 绕不过去。
  3. 根据公开文档，.claude/approvals.yml 的条件不能直接读取底层 CI 测试结果。哪怕常规代码过了 Claude Approvals，单测、构建和静态扫描依然要作为独立的 GitHub 必需状态检查挂在分支保护里。

计费和合规方面，Claude Ship 面向使用 GitHub 的 Claude Team 与 Enterprise 组织，按云端 Token 计费，当前不兼容 Zero Data Retention（零数据保留）、HIPAA 合规配置以及客户自管加密密钥（CMEK）。策略文件本身也要跟着目录结构维护，规则写松了会漏风险，写碎了维护成本高。

放一起看：两套方案共用的控制面

把 Poppy 1.0 和 Claude Ship 并排对照，两边的工程边界基本落在同一张表里：

维度Poppy 1.0（跨组织个人代理）Claude Ship（内部研发流水线）共同做法
边界文件/.well-known/poppy.json 声明入口与 Scope.claude/approvals.yml 声明路径分级与审批席位边界写进配置文件，不写在 Prompt 里
权责切分默认未登录浏览 → OAuth 显式提权写操作Review（查）/ Steward（修）/ Approvals（批）分开读、写、批拆开，同一角色不既改又批
底层门禁ES256 Poppy-Session + 资源绑定 OAuth TokenGitHub Branch Protection + 独立 CI Status Checks兜底放在确定性系统，模型改不了
人工干预用户随时撤销 OAuth 授权、无状态会话隔离每次 push 附回滚说明、@claude stop 急停留痕、随时能停、能回滚
上线节奏未登录态起步，按需触发细粒度授权先跑 mode: observe，验证后再切 enforce先低权限或只读观察，再放开写/批权限

请求或事件从触发到落地的控制面路径：

flowchart LR
    A["用户 / 事件触发"] --> B["读取声明式契约
(poppy.json / approvals.yml)"]
    B --> C["只读与低风险执行
(未登录查询 / Code Review)"]
    C --> D{"是否跨过执行线?
(状态变更 / 审批签发)"}
    D -- "否" --> E["直接返回结果与审计记录"]
    D -- "是" --> F["确定性策略与权限校验
(OAuth Scope / 分支保护 + CI)"]
    F -- "超出边界" --> G["拦截并升级给人类处理"]
    F -- "符合策略" --> H["受限执行 + 留痕
(可急停 / 可回滚)"]
    H --> I["持续观测与策略迭代
(Observe Mode / 撤销权限)"]

最关键的分界在 F 这一步：OAuth 授权服务器校验 Scope、GitHub 校验分支保护和 CI 状态，都不经过模型。就算模型出现幻觉或碰到间接提示词注入，也改不动这层检查。模型负责非结构化的理解和修补，确定性系统守住写操作的闸门。

用 Go 把控制面跑一遍

配套仓库 blog-go-example/execution-line-control-plane 里有一个无外部依赖的单进程 Go 模型（只用标准库 crypto/ecdsa、net/http 和 gopkg.in/yaml.v3），把上面几条拦截规则跑通了：

  • poppy/：起内存 HTTP 服务托管 /.well-known/poppy.json，实现 ES256 + typ: "poppy-session+jwt" 签发与验签。测试覆盖了未登录访客只读放行，以及 POST /v1/orders/{id}/cancel 在缺 Poppy-Session、仅有 orders:read、或 Bearer Token 资源 URL 不匹配时返回 401/403。
  • approvals/：解析 .claude/approvals.yml 风格配置，测试 observe 与 enforce 差异、billing/** 强制要求 !pr/author 人类席位、Approvals 通过但 CI 失败时依然拦住合入，以及 ValidateStewardAction 拒绝 approve_pr、merge_pr 和 @claude stop 状态。

在案例仓库根目录运行：

go test -v ./execution-line-control-plane/...
go run ./execution-line-control-plane/cmd/demo

边界再明确一下：这是离线单进程模型，用来核对字段、签名和策略拦截，不做真实 OAuth 浏览器跳转，也不调 Meta Muse、Shopify、GitHub 或 Anthropic 云端接口。

准备让 Agent 动手前，先查三件事

如果打算把某段内部流程交给 Agent 执行，动工前可以按下面三条筛一遍：

  • 挑等待多、出错能回滚的环节。修 CI、解合并冲突、文档或测试夹具审批、未发货订单查询取消，出错后都能退回；删库、资金划转、核心鉴权修改这类不可逆动作，现阶段留在人工审批一侧。
  • 先写边界文件，再接 Agent。开通写权限前，试着把允许动的目录、接口、Scope 和红线写成一份版本可控的配置（类似 poppy.json 或 approvals.yml）。连哪些路径算低风险都列不出来时，先别给写权限。
  • 先跑一两周观察模式。不管是现成套件还是自建运维 Agent，第一步先只记决定、不真执行，拿真实历史事件对比 Agent 判断和人工结果，摸清误报和漏放比例后再按模块放权。
