拆解 MCP 2026 架构重构：会话没了，状态搬去了哪里（附 Claude Code 实测）

2026 年 7 月 28 日，MCP 发布了第五个规范版本 2026-07-28。官方博客把这次改动概括为一句话：MCP 从双向、有状态的协议，改成了请求/响应式的无状态协议。initialize 握手没了，Mcp-Session-Id 没了，服务端主动向客户端发起的请求（elicitation、sampling、roots）也换成了另一种机制。

规范的 changelog 分主要变更和次要变更列了一长串，一条条读下来很难看出它们是在解决同一个问题。所以我把它当成一次架构重构来拆：旧架构卡在哪里，新架构把状态挪到了哪里，挪过去之后谁要接手。

光读规范不够，我用官方 Go SDK v1.8.0 在本机起了 3 个 MCP 副本，前面放一个轮询的反向代理，分别用新旧两个协议版本去连，记下代理看到的每一个 HTTP 请求。之后又把同一个服务端接给 Claude Code 2.1.332，看 Claude 这边实际发了什么。

结论先放前面：

  • 旧协议放在普通负载均衡后面根本连不上。 initialize 落在副本 0，下一个请求落到副本 1，直接 404 session not found。要么开会话保持，要么只部署一个副本。
  • 新协议去掉的是协议层的状态，不是你的状态。 普通调用在轮询下 30/30 全通。但如果把 MRTR 的待确认状态放在副本内存里，确认类调用 0/30；如果句柄背后的数据放在副本内存里，0/10。
  • Claude Code 已经在用新协议。 抓到的请求依次是 server/discover → tools/list → tools/call → 带 inputResponses 的重试 → subscriptions/listen，每个请求都带 MCP-Protocol-Version: 2026-07-28。

旧架构卡在哪：会话绑在一台机器的内存里

2025-11-25 及以前，一个 MCP 连接是这样建起来的：

  1. 客户端 POST initialize，带上协议版本和客户端能力。
  2. 服务端返回自己的能力，同时在响应头里发一个 Mcp-Session-Id。
  3. 客户端 POST notifications/initialized，之后每个请求都带这个会话 ID。
  4. 客户端另开一个 GET 长连接，接收服务端主动推来的消息。

会话 ID 对应的状态（协商好的版本、客户端声明的能力、打开着的 SSE 流）只存在创建它的那个进程里。我把 3 个副本放在轮询代理后面，旧协议的客户端走到第三个请求就挂了：

序号请求落到状态码
1POST initialize副本 0200，拿到会话 ID
2GET（开推送流）副本 1404
3POST notifications/initialized副本 2404

SDK 报的错是 sending "notifications/initialized": failed to connect (session ID: …): session not found。连接都没建起来，后面的工具调用一次也没执行。

把代理改成会话保持（记下哪个副本发出了这个会话 ID，后续带这个 ID 的请求都送回去），一切正常：whoami 调了 30 次，30 次都落在副本 0。也就是说，旧协议能跑，代价是：

  • 负载均衡器必须认识 Mcp-Session-Id，普通的四层或轮询七层负载均衡都不行。
  • 一个会话的所有流量压在一台机器上。这台机器重启或缩容，会话就断了。
  • 服务端要向客户端发请求（比如弹确认框）时，只能通过一条一直开着的 SSE 流。在实验里，确认类工具每次调用都是两个 POST：工具调用本身的那个 POST 在等用户答复期间一直不能结束；用户的答复作为另一个 POST 发回来，而且必须落到同一台机器上。

这三点放在 serverless 和边缘部署上都是硬伤：函数实例随时会被回收，也不会有会话保持。

新架构把状态挪到了哪里

2026-07-28 的主要变更可以归成四组，每组都是把一份原来由协议层持有的状态，搬到别的地方去。

原来的状态现在放在哪对应的规范变更
握手时协商好的版本、客户端能力每个请求的 _meta 里自带删除 initialize，新增可选的 server/discover（SEP-2575）
Mcp-Session-Id 对应的会话服务端铸造的句柄，作为工具参数传来传去删除会话（SEP-2567）
等待用户答复时挂着的 SSE 流客户端带着答复重发原请求，服务端的中间状态放在 requestState 里MRTR（SEP-2322）
网关要拆开 JSON 才知道是什么请求HTTP 头 Mcp-Method、Mcp-Name；列表结果带 ttlMs 和 cacheScopeSEP-2243、SEP-2549

握手：每个请求自己说清楚

新协议下，代理看到的第一个请求是 server/discover，然后直接是 tools/list 和 tools/call，中间没有任何握手。每个请求的 _meta 里都带三个键：

"_meta": {
  "io.modelcontextprotocol/protocolVersion": "2026-07-28",
  "io.modelcontextprotocol/clientCapabilities": { ... },
  "io.modelcontextprotocol/clientInfo": { "name": "lab-client", "version": "v1" }
}

HTTP 头里同时有 MCP-Protocol-Version: 2026-07-28、Mcp-Method: tools/call、Mcp-Name: whoami。这样任何一个副本拿到任何一个请求，都不需要查任何上下文就能处理。实验里 30 次 whoami 被均匀分到 3 个副本，每台 10 次，没有一次失败。

server/discover 是可选的，规范说客户端「可以」先调用它来了解服务端支持哪些版本和能力。Go SDK 的客户端在建连时会先调一次，发现服务端不支持新协议就退回 initialize 握手。用 2025-11-25 建连的客户端则直接发 initialize，不会调 server/discover。

这样做的代价是每个请求都变大了。同一个不带参数的 whoami 调用，旧协议的请求体平均 89 字节，新协议 330 字节，多出来的部分基本都是 _meta。对工具调用来说这点开销可以忽略，但如果你的网关按请求体大小限流，要把它算进去。

会话：换成模型看得见的句柄

规范对跨调用状态的建议是：由服务端铸造一个句柄，作为工具结果返回，模型在下一次调用时把它当参数传回来。官方博客的说法是，去掉协议层的会话，并不强迫你的应用也变成无状态。

我写了一个 cart_add 工具：第一次调用时返回 cart_xxx 这样的句柄，之后每次带着句柄往里加一件商品。连加 3 件，检查购物车里是不是 3 件。

  • 句柄背后的数据放在共享存储里（实验里用进程内的 map 代替 Redis）：10/10。
  • 放在各副本自己的内存里：0/10。轮询把 3 次调用分到了 3 台副本，每台只看到 1 件，报错是 cart lost items: got [c] on replica 0。

句柄只是把「这次调用属于哪份状态」从 HTTP 头挪到了工具参数里。状态本身该放共享存储，还是得放共享存储。区别在于，现在这件事完全由应用自己负责，负载均衡器不用再知道它。

反向请求：MRTR 让服务端不用等

旧协议里，工具执行到一半需要用户确认时，服务端在当前请求的 SSE 流上发一个 elicitation/create 请求，然后挂着等答复。新协议改成多轮往返（Multi Round-Trip Request，MRTR）：

  1. 客户端调 tools/call。
  2. 服务端不执行，直接返回 resultType: "input_required"，inputRequests 里写明要问用户什么，requestState 里放一段不透明的状态。
  3. 客户端问完用户，带着 inputResponses 和原样的 requestState 重发同一个 tools/call。
  4. 服务端核对 requestState，执行。

每一轮都是一个完整的请求/响应，中间不挂任何连接。实验里确认类工具每次调用是两个 tools/call，第二个落在另一台副本上。

这里有个很容易踩的坑：第 4 步落在哪台副本是不确定的。我先写了一个偷懒的版本：第 2 步生成一个随机 ID 当 requestState，把「要删哪个分支」存在本副本的内存里，第 4 步再按 ID 查。结果 30 次确认全部失败，错误是 replica 2: unknown or expired requestState。

改成把状态签进 requestState 本身，任何持有同一个密钥的副本都能独立验证，就 30/30 了：

// 把分支名和过期时间签进 requestState，不需要查表
func sign(branch string, exp time.Time) string {
	body := fmt.Sprintf("%s|%d", branch, exp.Unix())
	m := hmac.New(sha256.New, secret)
	m.Write([]byte(body))
	return b64(body) + "." + b64(m.Sum(nil))
}

requestState 会经过客户端再回来，所以必须签名，不能直接信任里面的内容；要加过期时间，防止旧的确认被重放；里面的东西客户端看得到，敏感数据不要放明文。

网关友好：头里带方法名，列表可以缓存

另外两项改动是给网关和客户端减负的：

  • Mcp-Method 和 Mcp-Name 头让网关不解析 JSON 就能按工具路由、限流、计费。
  • tools/list 等列表结果可以带 ttlMs 和 cacheScope，告诉客户端和网关能缓存多久、能不能跨用户共享。我让服务端返回 ttlMs: 60000，客户端连续调 3 次 tools/list，实际只发出 1 次请求，另外 2 次命中 Go SDK 客户端的缓存。不设 TTL 时 3 次都会发出。

原来的 GET 推送流和 resources/subscribe 合并成一个 subscriptions/listen 请求，客户端在里面声明要订阅哪几类变更通知。SSE 断线续传（Last-Event-ID）删掉了，流断了就由客户端用新的请求 ID 重发。

一起被移出核心的东西

  • Roots、Sampling、Logging 标记为弃用（SEP-2577），至少还能用 12 个月。替代办法：路径作为工具参数传，服务端需要模型就直接调模型 API，日志写 stderr 或 OpenTelemetry。
  • 旧的 HTTP+SSE 传输、OAuth 动态客户端注册（DCR）也标记为弃用，后者改用 Client ID Metadata Documents。
  • 实验性的 Tasks 移到扩展 io.modelcontextprotocol/tasks，和 MCP Apps 一样走新的扩展框架。
  • 新增弃用政策：任何弃用功能至少保留 12 个月才能移除。

新旧混跑：旧客户端连新服务端，确认类工具会失败

升级不可能一夜完成，所以我又测了一个组合：用 2025-11-25 的客户端去连无状态模式的服务端，前面还是轮询代理。

建连、tools/list、普通调用、句柄都正常：服务端处于无状态模式时不发会话 ID，旧客户端也就不带，请求照样可以落到任意副本。开推送流的 GET 收到 405，客户端没有报错，继续往下走。

只有确认类工具 0/30。错误是 multi-round-trip: fulfilling input request "confirm": client does not support elicitation。原因是：同一份工具代码返回 inputRequests 时，Go SDK 会判断客户端的协议版本，旧客户端不认识 input_required，SDK 就替你退回到老办法，由服务端发 elicitation/create；但无状态模式下服务端既不保留旧客户端在 initialize 时声明的能力，也没有一条能把这个请求送回去的流，于是 SDK 判定它不支持确认。

所以过渡期有两个选择：

  • 给旧客户端保留一套有状态部署，配会话保持。
  • 确认类工具在客户端不支持时给出降级结果，比如只返回「将要删除哪些分支」的预览，不真的执行。

另外，Go SDK 的文档写明，流式 HTTP 传输只有在 Stateless = true 时才接受 2026-07-28 的请求，有状态的 handler 收到新协议请求会直接拒绝。也就是说，用 Go SDK 想同时服务新旧客户端，得开无状态模式。

Claude 这一侧：Claude Code 已经在说新协议

Anthropic 在规范发布当天发了博客 Bringing MCP 2026-07-28 to Claude，只说支持正在各个 Claude 产品中陆续上线，没有列出具体产品和时间。同一篇里提到的还有：

  • MCP Apps：服务端可以直接在对话里渲染交互界面。
  • 企业托管授权：管理员授权一次连接器，用户通过已有的身份提供商分组继承权限。
  • MCP tunnels（研究预览）：让 Claude 连到私有网络里的服务端，源站不用开入站端口，也不用加 IP 白名单。
  • 连接器目录里已有超过 950 个 MCP 服务端。

我用 claude -p --mcp-config 把 Claude Code 2.1.332 接到同一个服务端（单副本、无状态模式），让它先调 whoami，再调 delete_branch。服务端记下的请求是：

序号请求说明
1server/discover先探测服务端支持的版本
2tools/list
3tools/call whoami_meta 里多了一个 claudecode/toolUseId
4tools/call delete_branch服务端返回 input_required
5tools/call delete_branch带着 inputResponses 重发，答复是 cancel（第二次运行记下的）
6subscriptions/listen订阅变更通知

全部请求都带 MCP-Protocol-Version: 2026-07-28、Mcp-Method 和 Mcp-Name 头，User-Agent 是 claude-code/2.1.332 (sdk-cli)，没有一个带会话 ID。Claude Code 在 _meta 里声明的能力是：

{"roots":{"listChanged":true},"elicitation":{"form":{},"url":{}},"extensions":{"io.modelcontextprotocol/tasks":{}}}

几个值得注意的地方：

  • 它确实实现了 MRTR：收到 input_required 后按协议重发，而不是把它当成错误交给模型。
  • -p 是非交互模式，没有人能点确认，所以答复是 cancel，工具返回 deleted: false，Claude 也如实转述了这个结果。交互模式下会怎么提示用户，这次没有测。
  • 它仍然声明了 roots 能力，而 roots 在这一版已经弃用。弃用期内功能照常可用，这不算问题，但说明客户端这边也还在过渡。
  • extensions 里的 Tasks 扩展只在 server/discover、tools/list 和 subscriptions/listen 上声明，tools/call 的 _meta 里没有带。

对 MCP 服务端作者来说，这意味着 Claude Code 用户已经在以新协议连你的服务。服务端如果只认 initialize，Go SDK 客户端会退回旧握手；Claude Code 是否同样退回，这次没有测。

服务端迁移清单

  1. 找出所有读会话 ID 的地方。 包括日志里按会话 ID 聚合、按会话缓存用户信息、按会话做限流。新协议下这些都拿不到了，客户端身份要从 _meta 里的 clientInfo 或认证令牌里取。
  2. 跨调用状态改成显式句柄，背后放共享存储。 句柄只解决「找到哪份状态」，不解决「状态存在哪」。
  3. 需要用户确认的工具改成 MRTR，requestState 签名加过期时间。 不要把待确认状态只存在副本内存里。
  4. 列表结果设置合理的 ttlMs。 工具列表很少变的服务，给几十秒到几分钟，能省掉大部分 tools/list 请求。
  5. 决定旧客户端怎么办。 保留有状态部署，或者让确认类工具在旧客户端上降级。
  6. Roots、Sampling、Logging 开始准备替代方案。 至少 12 个月后才会移除，但新代码不要再依赖它们。

这些结论的边界

  • 3 个副本在同一个进程里，代理严格轮询、请求串行，所以 MRTR 的重试和句柄的下一次调用必然落到另一台，失败率是 100%。生产环境里随机分发、并发请求时失败率会低一些，但不会是 0，而且会表现为偶发故障，更难排查。
  • 「旧客户端连无状态服务端时确认类工具失败」是 go-sdk v1.8.0 的行为，TypeScript、Python、C# SDK 怎么处理没有测。
  • Claude Code 只测了 -p 非交互模式下的一个版本（2.1.332）。Claude.ai、Claude Desktop 和 API 的 MCP 连接器没有测，官方也没有公布它们的支持时间。
  • 没有测延迟。本机回环上的毫秒数对真实部署没有参考价值。

实验代码、每个场景的结果和代理记下的全部请求都在 blog-go-example/mcp-2026-stateless，go run ./lab 约 2 秒跑完，python3 report.py 从日志打印文中的全部数字。
