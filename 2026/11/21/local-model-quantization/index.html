qwen2.5:3b 六个量化版本实测：Q4_K_M 和 FP16 打平，Q3_K_M 掉到 49/165，Q2_K 只会输出 4333

在 Ollama 上拉模型，同一个名字后面通常挂着一串标签：fp16、q8_0、q4_K_M、q3_K_M、q2_K。常见的说法是 Q4_K_M 够用，再往下就要掉质量，但掉多少、掉在哪类任务上，很少有人在中文任务上给出具体数字。

这次在一张 RTX 3060 12GB 上，对 qwen2.5:3b-instruct 的六个官方量化版本做了一轮对比，任务全部是能自动判对错的中文题，温度 0。结论先列出来：

  • Q8_0 和 Q4_K_M 与 FP16 在 165 道题上的差距只有几道，Q4_K_M 甚至多对了 1 道，这个差距在单次运行里不能当真。
  • Q3_K_M 是一道悬崖：总分从 153 掉到 49，JSON 抽取 40 道全错，代码题 20 道只对 1 道。Q3_K_L 也只有 54。
  • Q2_K 一道都没对，输出是一串 4333333…。在 llama.cpp 的 CPU 构建上测困惑度同样崩掉，自己从 FP16 量化一份也是这样。
  • 用 llama.cpp 的 imatrix（重要性矩阵）重新量化，Q3_K_M 回到 128/165，Q2_K 从 0 变成 92。悬崖主要来自量化方法，不完全来自位数。
  • 速度上 Q4_K_M 生成最快，每秒 124 token，是 FP16 的 2.6 倍；Q3_K_M 反而只有 96。

环境和测量方法

  • 硬件：RTX 3060 12GB。桌面程序常驻占用约 4.1GB 显存，下面的显存数字都是减掉这部分之后的增量。
  • 软件：Ollama 0.35.0；KL 散度和重新量化用 llama.cpp b12596 的 CPU 构建（llama-perplexity、llama-quantize、llama-imatrix）。
  • 模型：qwen2.5:3b-instruct-fp16、-q8_0、-q4_K_M、-q3_K_L、-q3_K_M、-q2_K，全部来自 Ollama 官方库，模板和系统提示词一致，只有权重文件不同。
  • 调用：/api/chat，temperature 0、seed 1、num_ctx 4096，每题只跑一次。生成上限按题型设：常识 64、应用题 512、JSON 160、代码 512 token。Q3_K_M 有 11 条输出写到上限被截断，Q2_K 有 137 条。

题库、判分、量化和测速脚本，以及原始结果放在 blog-go-example/local-model-quantization，可以照着 README 复现。

题目共 165 道，分四类，每类都用程序判分，不靠人工或模型打分：

类别题数判分方式
常识问答45首都、诗句、作者、成语填空等，输出里包含任一可接受答案即算对
应用题606 个模板加固定随机种子生成数字，要求最后一行写「答案：数字」，取最后一个答案行比对
JSON 抽取40从一句订单描述里抽 name、city、order_id、qty、total，total 需要自己算数量乘单价，逐字段比对
Python 函数20要求写指定名字的函数，取代码块在隔离的 Python 进程里跑断言，超时 5 秒

常识题的判分比较宽松：只要输出里含有答案就算对，后面会看到这会让一些明显有毛病的回答也拿分。所以下面的常识题分数是偏乐观的。例如问光速“每秒多少万公里”，FP16 答 300000、几个低位版本答 300，单位都不对，都被判对。

Q4_K_M 只有一半题的输出和 FP16 相同，但另一半里有对有错，丢 5 道、多对 6 道，相互抵消。Q8_0 的输出和 FP16 一样的有 125 道，丢的 4 道全是应用题。温度 0 下没有采样随机性，差异来自少数临界题被量化误差扰动后翻转。按逐题配对看，Q8_0 是 0 得 4 丢、Q4_K_M 是 6 得 5 丢，配对检验都不显著（Q8_0 的 McNemar 精确检验 p≈0.13），这几道的差距都在误差范围之内，我不会据此说 Q4_K_M 比 FP16 好，或者 Q8_0 比 Q4_K_M 差，只能说在这套题上看不出区别。

有几道题连 FP16 都错，和量化无关：

  • 「长方形四周每隔 1 米种树，四个角都种」这一类应用题，60 道里有 10 道。正确答案就是周长，模型常常把四个角再减掉一次。FP16 在这 10 道里错了 7 道，占了它 8 道应用题错题中的 7 道；Q8_0 这 10 道全错，Q4_K_M 和 imatrix Q4_K_M 各错 7 道。
  • 「对牛弹_」，FP16、Q8_0、Q4_K_M 都填「歌」。

Q3_K_M：格式先坏，内容跟着坏

Q3_K_M 掉分最多的是 JSON 和代码，这两类恰好都要求严格的输出格式。看同一道抽取题三个版本的原始输出：

Q3_K_M 没有输出 JSON，而是一行一个 key: value，判分在解析这一步就失败了。就算放宽成按文本比对，里面也有三处错：城市写成「杭」，订单号丢了 SO 前缀，总价 6×41 算成 126。它还多输出了题目没要的 price 和 date。40 道 JSON 题它全是这种格式。

代码题也是类似的情况：题目指定了函数名，FP16、Q8_0、Q4_K_M 都是 20 道全按名字写，Q3_K_M 只有 3 道写对了名字，20 道里有 6 道连代码块都没有。Q3_K_M 失败的 19 道里，名字写错导致 NameError 的有 11 道，另有 6 道是语法或缩进错误，1 道断言失败，1 道超时。

常识题看上去还好，29/45，但这里面有宽松判分的功劳。比如问澳大利亚首都，Q3_K_M 回答「堪培拉克 ☀️」，包含「堪培拉」，算对。

Q3_K_L 比 Q3_K_M 多用了一些位数，总分只多 5 分，JSON 同样是 0/40，说明问题不在 L 和 M 这点差别上。

Q2_K 为什么只会输出 4333

Q2_K 的 165 道题全错。其中 28 道被 Ollama 中途终止，返回 HTTP 500 和 token repeat limit reached，剩下的输出都是数字串或乱码：

第一反应是文件下载坏了，或者是 GPU 上的某个算子有问题。我按下面的顺序排除：

  1. 用 llama.cpp 的 CPU 构建对 Ollama 存储目录里的同一个 GGUF 文件跑 llama-perplexity：困惑度 11235，首选 token 和 FP16 相同的只有 0.8%。不经过 Ollama、不用 GPU 也一样坏，所以不是 GPU 算子的问题。
  2. 用 llama-quantize 从 FP16 文件自己量化一份 Q2_K，不加 imatrix。它在评测语料上的困惑度是 11222，Ollama 那份是 11235，几乎相同。

第 2 步说明文件没坏：这个模型按不带 imatrix 的方式量化到 Q2_K，结果就是这样。Q2_K 这个名字并不保证能用，至少对 3B 这种小模型不保证。

用 KL 散度看每个 token 偏了多少

165 道题的总分比较粗，Q4_K_M 和 FP16 之间那几道的差距分不清是量化本身造成的，还是少数临界题碰巧翻转。所以我又用 llama.cpp 测了 KL 散度：先让 FP16 在一段文本上逐 token 算出概率分布并存下来，再让每个量化版本在同一段文本上算，比较两者的分布差了多少，同时统计每个位置上概率最高的 token 和 FP16 是否相同。

评测文本是我自己博客的 4 篇文章正文，去掉代码块、表格和链接后约 2.9 万字符（其中汉字约 1.3 万），上下文 512，共 33 段。

这张表和任务分数对得上：

  • Q8_0 几乎和 FP16 一样，97% 的位置首选 token 相同。
  • Q4_K_M 有 14.5% 的位置首选 token 变了，这解释了为什么它只有一半题的输出和 FP16 一字不差。但这些变化大多不影响答案对错。
  • 从 Q4_K_M 到 Q3_K_M，KL 散度涨了 10 倍，困惑度翻倍，正好对应任务分数的悬崖。

另一个现象是，「不加 imatrix 自己量化」的三个版本，和 Ollama 官方库的同名版本几乎一样：Q4_K_M 是 0.076 对 0.075，Q3_K_M 是 0.813 对 0.781，Q2_K 是 6.587 对 6.591。（推测）Ollama 库里这几个文件是不带 imatrix 量化的。我没有找到官方对此的说明，这是根据数值接近得出的推断。

imatrix 重新量化

imatrix 的做法是：先让 FP16 模型跑一段校准文本，统计每个输入通道上激活值的平方均值，量化时按它给误差加权，让重要通道上的权重误差更小。llama-quantize 支持传入这个矩阵。

校准文本也用我自己的博客，但特意选了另外 5 篇，和评测 KL 散度用的 4 篇不重合，约 3.6 万字符（其中汉字约 1.4 万），避免拿测试数据去校准：

llama-imatrix -m qwen2.5-3b-fp16.gguf -f calib.txt -o imatrix.gguf
llama-quantize --imatrix imatrix.gguf qwen2.5-3b-fp16.gguf imat-q3_K_M.gguf Q3_K_M

量化后的文件大小和不加 imatrix 时一样：Q4_K_M 约 1835 MiB（每权重 4.99 位），Q3_K_M 约 1511 MiB（4.11 位），Q2_K 约 1210 MiB（3.29 位）。imatrix 不改变位数，只改变每一组权重怎么取舍。

导入 Ollama 时沿用官方版本的模板和系统提示词，只换权重文件，然后跑同样的 165 道题：

  • Q3_K_M：49 → 128。JSON 从 0/40 回到 35/40，上面那道订单题抽出的字段和 FP16 一样。
  • Q2_K：0 → 92。不再输出数字串，能正常回答，但错得多：问澳大利亚首都它答「悉尼」，JSON 里 total 算错 17 道。
  • Q4_K_M：154 → 149。KL 散度从 0.075 降到 0.038，任务分数反而少了 5 道。逐题看，它比 FP16 丢了 9 道（4 道应用题、3 道常识、1 道 JSON、1 道代码），又多对了 5 道，两边都是零散的单题，配对检验不显著（p≈0.42），我不认为这说明 imatrix 让 Q4_K_M 变差了。

所以 imatrix 对 Q4 这档是锦上添花，对 Q3 和 Q2 是能不能用的区别。Q3_K_M 加 imatrix 之后的 128/165 仍然比 FP16 少 25 道，悬崖没有填平，只是变成了一个斜坡。

速度和显存

速度测试只做了 FP16、Q8_0、Q4_K_M、Q3_K_M 四个官方版本。每个版本先卸载所有模型，加载后记录显存，再发 5 次约 2020 token 的长提示词（每次前缀不同，避免命中提示词缓存），生成上限 256 token，取中位数。速度来自 Ollama 返回的 prompt_eval_duration 和 eval_duration，首 token 时间用流式接口在客户端计时。

FP1647.643910.50 s6215 MiB6.41 GB

几点观察：

  • 生成速度基本跟着文件大小走：3060 生成阶段受显存带宽限制，每生成一个 token 都要把权重读一遍，文件越小越快。FP16 到 Q4_K_M 占用小了约 3 倍，速度快了 2.6 倍。
  • 提示词处理是计算受限的，四个版本都在每秒 4000 token 上下（约 3980 到 4540），首 token 时间都在半秒左右。2000 token 的提示词，量化对首 token 时间几乎没影响。
  • Q3_K_M 占用比 Q4_K_M 小约 16%，生成速度却慢了 23%，提示词处理也最慢。（推测）Q3_K 的权重解包比 Q4_K 更复杂，在这张卡上解包的计算开销盖过了少读的那点带宽。我没有拆到 kernel 层面去验证。
  • 显存方面，3B 模型的 KV 缓存在 4096 上下文下不大，显存增量基本就是权重大小。12GB 的卡跑 3B，哪个版本都放得下。

加载时间我也记了：文件已在页缓存里时，重新加载 1.2 到 1.9 秒。第一次冷加载的数字从 20 多秒到 70 多秒不等，但那几次正赶上磁盘上在删别的模型文件，读盘被干扰，数字不可靠，这里不列。

该选哪个标签

按这次的结果，对 qwen2.5:3b 这个量级的模型：

  • 默认用 Q4_K_M。质量和 FP16 看不出差别，速度最快，显存只要 2GB 出头。
  • 显存宽裕、想要最接近原模型的输出，用 Q8_0。它和 FP16 的输出 76% 一字不差，速度也有 FP16 的 1.8 倍。
  • 不要用 Ollama 官方库里 3B 模型的 Q3_K_M、Q3_K_L 和 Q2_K。省下的那几百 MB 不值得：Q3 连格式都守不住，Q2_K 完全不可用，而且 Q3_K_M 还比 Q4_K_M 慢。
  • 如果确实需要更小的文件，用 llama.cpp 加 imatrix 自己量化，或者找明确标注了 imatrix 的第三方 GGUF。即便如此，Q3 也会比 FP16 少不少分，要拿自己的任务测过再用。

格式类任务（JSON、指定函数名）是量化损伤最先暴露的地方。如果业务里有结构化输出，测量化版本时应该优先测这类题，常识问答的分数会掩盖问题。

这次测试的局限

  • 每个版本每道题只跑了一次。温度 0 加固定 seed 在 Ollama 上大多可复现，但不保证完全确定，几道题的差距不能当作结论。
  • 只测了一个模型、一个尺寸。一般认为小模型对量化比 7B 及以上更敏感，大模型的 Q3 不一定掉这么多，这次没有测。
  • 165 道题只覆盖四类任务，常识题的判分偏宽松。
  • KL 散度只用了 4 篇博客正文，约 2.9 万字，语料偏技术类中文。
  • imatrix 的校准文本也是我自己的技术博客，换成更通用的校准语料，结果可能不同。
  • 速度只在一张 RTX 3060 上测过。不同显卡上各量化格式的 kernel 效率不同，Q3_K_M 比 Q4_K_M 慢这一点不一定能推广。
