CPU 只用一半，Go 服务 p99 为何按 100ms 往上跳

 costalong  2026-11-21  golang 故障排查 Kubernetes Go
故障排查 Kubernetes Go

阅读次数:

监控面板上 CPU 使用率只有 limit 的一半，接口的 p99 却时不时跳到一两百毫秒，而且数值很整齐，像是 100ms 的倍数。这类问题在 Kubernetes 里很常见，原因也常被一句「CPU 被 throttle 了」带过。我想知道具体是哪一步把延迟切成了 100ms 的台阶，平均利用率为什么看不出来，以及 GOMAXPROCS、GC、cpu.max.burst 和去掉 limit 这几种办法各自有多大用。

于是在本机 kind 集群里写了一个每个请求固定消耗 5ms CPU 的 Go HTTP 服务，用开环压测器按固定的平均速率打它，改变 CPU limit、请求到达方式和 Go 运行时参数，同时读取容器 cgroup 的 cpu.stat。最极端的一组：1 核 limit，平均 CPU 0.57 核，请求每 400ms 一次来 40 个，p99 是 190ms；同样的负载只设 request 不设 limit，p99 是 22ms。

实验环境与测试程序

项目版本
Gogo1.27.4 linux/amd64，go.mod 写 go 1.27
kindv0.24.0，节点镜像 kindest/node:v1.31.0
容器运行时containerd v1.7.18，Docker 29.9.2
主机26 个逻辑 CPU（大小核混合），cgroup v2，内核 7.0.0-42，sched_cfs_bandwidth_slice_us 为 5000

集群只为这次实验创建，kubeconfig 写在实验目录里，所有 kubectl 都显式带 --kubeconfig，做完整个集群删掉。源码和脚本整理在 blog-go-example/cpulimit。

服务端只有标准库，/work 每个请求做两件事：分配 256KiB 垃圾（给 GC 找点活），然后锁定当前线程做 sha256，直到这个线程的 CPU 时间（getrusage(RUSAGE_THREAD)）涨够 5ms。按线程 CPU 时间计量而不是按墙上时间，是因为这台机器大小核混合，同样的循环在不同核上耗时不同；按 CPU 时间算，每个请求花掉的额度是固定的 5ms。/cpustat 返回容器自己的 /sys/fs/cgroup/cpu.stat，外加当前 GOMAXPROCS 和 GC 次数。

压测器是开环的：第 i 批请求的计划发送时刻是固定的，不管前面的请求回没回来都按时发出，延迟从计划时刻算起。闭环压测器（发完一个等回复再发下一个）在服务卡住时会跟着停下来，卡顿期间本该到达的请求根本没被发出，统计出来的尾延迟偏低，这就是常说的 coordinated omission。到达方式有三种，平均速率都一样：

方式含义
均匀100 rps 就每 10ms 发 1 个
泊松间隔服从指数分布，固定随机种子，每次运行的到达序列相同
突发 n每 n/100 秒一次性发 n 个，比如 n=40 就是每 400ms 来 40 个

每组配置新建一个服务端 Pod，跑 3 次，每次预热 5 秒、测 30 秒，测量窗口前后各读一次 cpu.stat 取差值。下文表格里的 p99 是 3 次的中位数，括号里是 3 次的范围。服务端 Pod 设 memory limit 256Mi，CPU request 等于 limit（不设 limit 的组 request 写 1 核或对应核数），QoS 都是 Burstable。

平均 CPU 一样，突发越集中 p99 越高

先把 CPU limit 固定在 1 核，平均 100 rps，也就是每秒需要 0.5 核的纯计算，加上 GC 和网络开销，cpu.stat 量到的平均使用率在 0.51 到 0.60 核之间。只改变请求是均匀来还是一批批来：

17.27.17.1未测0 / 0

单位都是毫秒。几件事从这张表里就能看出来：

  • 均匀到达时，三种 GOMAXPROCS 的 p99 都是 7ms 左右，一个周期都没被限流。0.57 核对 1 核的 limit 来说确实宽裕。
  • 每次 40 个时，平均使用率没变，p99 涨到 180～210ms。40 个请求要 200ms 的 CPU，而 1 核的 limit 每 100ms 只给 100ms 的额度，这批请求无论怎么调度，至少要跨两个周期才能做完。
  • 不设 limit 时同样的突发只要 22ms：26 个核同时开工，200ms 的活几毫秒就分完了。

决定尾延迟的不是一秒内的平均值，而是任意一个 100ms 窗口里的需求有没有超过额度。监控上常见的 CPU 使用率曲线是按 15 秒、30 秒甚至 1 分钟平均出来的，突发在里面被摊平，看不出来。

100ms 周期怎么把延迟切成台阶

CFS 带宽控制的规则写在内核文档 CFS Bandwidth Control 里：每个周期给一个 cgroup 分配 quota 微秒的 CPU 时间，quota 按 slice 分给各个 CPU 的运行队列，额度分完以后再要 CPU 的线程会被 throttle，并且「直到下一个周期补充额度前都不能再运行」。cgroup v2 里这两个数写在 cpu.max，格式是 $MAX $PERIOD，默认 max 100000，即周期 100ms（cgroup v2 文档）。Kubernetes 的 CPU limit 1 对应 cpu.max 为 100000 100000。

用 GOMAXPROCS=26 跑突发 40 的那组，cpu.stat 的差值是这样的：

30 秒 296 个周期，148 个被限流。每 400ms 一批突发，30 秒只有 75 批，平均每批被挂起两次：一批要 200ms 的 CPU，跨 3 个周期才做完，其中 2 次撞上限流，正好对应后面直方图里的三簇。throttled_ms 是 135 秒，比测量窗口的 30 秒还长。cgroup v2 文档只列出了 throttled_usec 这个键名，没有解释它怎么累加；从数字看，它应该是按 CPU 运行队列分别计时再相加的，135 秒折合整个窗口平均约 4.5 个运行队列处于被限流状态（推测）。所以排查时看 nr_throttled / nr_periods 比看 throttled_usec 的绝对值直观。

只看 p99 还看不出台阶。我按同样的配置另跑了一批，让压测器把每个请求的延迟都打出来，取每组第 1 次运行的 3000 个请求，5ms 一格画分布。这批运行的 p99 和上表略有不同（GOMAXPROCS=26 是 165.9ms，不设 limit 是 17.0ms）：

三种跑法的 p99 差不多，形状完全不同：

  • GOMAXPROCS=1 时同一时刻只有一个线程在跑，CPU 使用率基本不超过 1 核，几乎不被限流（3 次运行分别是 9、5、5 个周期），40 个请求排成一队一个接一个做完，延迟从 5ms 均匀铺到 210ms 左右，再往后逐渐变少，最慢 235ms。这是 Go 调度器里的排队，不是内核限流。
  • GOMAXPROCS=26 时 40 个请求几乎同时开工，几毫秒内就把本周期剩下的额度用光，整组线程一起被挂起，等下一个周期再跑几毫秒，再被挂起。延迟于是挤成三簇：5～10ms、60～70ms、160～170ms。后两簇相隔正好 100ms，第一簇和第二簇之间的距离取决于突发落在周期里的哪个位置。
  • 不设 limit 时 99% 在 17ms 以内，最慢 19ms。

开头说的「p99 是 100ms 的倍数」就是第三种形状：线程多、额度少，每个周期只能干几毫秒活，剩下的时间全在等周期边界。

GOMAXPROCS：默认值不被限流，但会让请求在 Go 里排队

Go 1.25 起，Linux 上的默认 GOMAXPROCS 会参考 cgroup 的 CPU 带宽限制（Go 1.25 Release Notes），运行时每秒最多检查一次 limit 有没有变化。go doc runtime.GOMAXPROCS 里写了具体规则：取逻辑 CPU 数、亲和掩码和 quota/period 三者的最小值，非整数向上取整，并且不低于 2（逻辑 CPU 数或亲和掩码本身小于 2 时除外）。这次实测的默认值：

0.5 核和 1 核的 limit 拿到的都是 2。之前写 Go 存活堆 150MiB 为何撑爆 256Mi 容器 时测过，go.mod 的 go 行低于 1.25 时这套逻辑不生效，默认值仍是主机的 26。

按理说 GOMAXPROCS 等于 limit 时，Go 同时最多跑 limit 个线程执行 Go 代码，很难在一个周期里用超额度。泊松到达、平均使用率为 limit 的 56%～60% 时，结果是这样的：

2 核和 4 核两行，默认值确实一个周期都没被限流，可 p99 比 GOMAXPROCS=26 和不设 limit 都高。我的解释是泊松到达本身就有小的扎堆：同一个 10ms 里来了 4 个请求，GOMAXPROCS=2 只能先做 2 个，另外 2 个在 Go 的运行队列里等 5ms；而 26 个 P 可以全部同时开工，短时间超过 2 核也没关系，100ms 周期内的总额度还够。GC 的后台标记也要占 P，P 越少挤占越明显。这两点都是推测，这次没有测排队时间，也没有把 GC 拆开测。

0.5 核这一行两种设置都被限流：quota 只有 50ms，两个线程并行 25ms 就能用完，默认的 2 本身就超过了 limit。但 GOMAXPROCS=26 被限流更多（28 对 23），GOMAXPROCS=1 这次没测，所以不能说限流就是「不低于 2」这条规则造成的，它最多是原因之一（推测）。

突发场景里，GOMAXPROCS 的作用正好反过来。突发 10 时 26 比默认的 2 快（13.0 对 30.0），因为 50ms 的活在 100ms 额度内，并行越多做得越快；突发 20 和 40 时默认和 26 两档差不多，因为需求超过了额度，并行再多也只是更早撞上限流。GOMAXPROCS=1 在所有突发场景里都最慢。

所以调 GOMAXPROCS 改变的是「在 Go 里排队」还是「在内核里排队」，两边都有代价。负载平稳、额度充足时，把它调高到超过 limit 反而降低了 p99；负载有突发、需求接近额度时，它救不了延迟。

GC 关掉也没用，偶发的几百毫秒停顿还没抓到原因

每个请求分配 256KiB，默认 GOGC 下 30 秒里有 122～293 次 GC。我用 GOGC=off 配合 GOMEMLIMIT=180MiB 把 GC 压到 30 秒 4～5 次（256Mi 的内存 limit 下不能完全关掉），对比 1 核 limit 下的突发 10 和突发 20：

GC 次数从几百降到个位数，p99 没有变好。在这个负载里，决定尾延迟的是突发需求和额度的比例，GC 只是其中很小的一部分。

表里最怪的是突发 10、GOMAXPROCS=26、GC 几乎关闭那格：3 次里有 2 次 p99 冲到 162ms 和 321ms，最大值 356ms 和 818ms，每次只有 5、6 个周期被限流。平时这个配置一个周期都不被限流。这两次虽然有限流，但只有 5、6 个周期，最慢的请求却等了 818ms，比 6 个周期加起来的 600ms 还长，单靠限流解释不通。

我想用 GODEBUG=gctrace=1 把慢请求的时刻和 GC 对上，于是让压测器把超过 100ms 的请求连同计划时刻一起打印，又跑了 13 次（默认 GOGC 5 次，GC 几乎关闭 3 次加 5 次），一次都没复现，p99 全部在 6～16ms。把所有 GOMAXPROCS=26、突发 10 的运行算在一起，20 次里出现 3 次：最早一次 20 秒的探测（默认 GOGC，p99 197ms，max 499ms，4 个周期被限流）和上面那 2 次，都在实验的前一个小时。其中一次压测器自己的发送也晚了 208ms（maxlag=207.8），压测器 Pod 不受 CPU limit 约束，说明那一刻整台主机可能都卡过一下（推测）。但也有反例：别的配置在实验开始约 1.5 小时后也出过一次 max 370ms 的离群（cburst-40-def 第 2 次），还有一次 p99 469ms 的运行（burst-40-p1 第 2 次）压测器的发送延迟只有 1.3ms，说明那次压测器并没有被拖慢。这个现象我没有查清，只在这里记下数据。

cpu.max.burst 能吸收突发，但 Kubernetes 没有暴露它

cgroup v2 的 cpu.max.burst 允许 cgroup 把之前周期没用完的额度攒下来，在之后的周期里超额使用，上限由这个文件指定，范围是 0 到 quota，默认 0（cgroup v2 文档）。内核文档对这个功能的描述是先借用额度、以后用空闲的时间还上，换来的是对其他 cgroup 的干扰变大（CFS Bandwidth Control）。

Kubernetes v1.31（本次测试版本）的 Pod spec 里没有对应字段，kubelet 也不会去设它。我直接在 kind 节点的 cgroupfs 里，把 Pod 那一层和业务容器那一层的 cpu.max.burst 都写成 100000（等于 quota），然后跑同样的突发：

突发 20，GOMAXPROCS=2662.511.0（10.9～24.6）22.9

突发 20 加 GOMAXPROCS=26，100ms 的需求刚好等于攒下的额度，限流降到 0，p99 从 62ms 降到 11ms，反而比不设 limit 的 22.9ms 还低，原因没有查（不设 limit 的结果本身波动也大）。突发 40 需要 200ms，超过了「本周期 100ms 加攒下的 100ms」，仍然被限流，p99 只降到 67ms。注意设了 burst 以后 30 秒的 nr_periods 从约 297 降到 222～225，被限流的 74 个周期占约三分之一。

默认 GOMAXPROCS=2 的两行说明了另一件事：设了 burst 以后它们也一个周期都没被限流，突发 20 的 p99 却几乎没变（60.6 对 56.0），突发 40 只降到 111ms。100ms 的活分给 2 个线程要 50ms，200ms 的活要 100ms，排队发生在 Go 的运行队列里，内核放不放行都一样。

这个设置在 Pod 重建后就没了，生产上要在节点侧或运行时层面设置（OCI runtime spec 有 linux.resources.cpu.burst 字段），这次没有测试这类方案。

从限流比例到 limit 怎么设

把 CPU limit 和延迟放在一起看时，我会按这个顺序：

  1. 先看限流比例，不看平均使用率。cpu.stat 的 nr_throttled / nr_periods，或者 cAdvisor 导出的 container_cpu_cfs_throttled_periods_total 和 container_cpu_cfs_periods_total。但限流为 0 不代表没问题：这次 GOMAXPROCS=1 的突发 20、40，以及加了 cpu.max.burst 后默认 GOMAXPROCS 的突发 40，p99 都过了 100ms，限流却几乎为 0，请求是在 Go 里排队。两类都要看延迟分布，台阶状是内核限流，平铺是线程不够。
  2. 估算 100ms 窗口内的峰值需求：一批突发的请求数乘以单个请求的 CPU 时间，再和 limit × 100ms 比。超过额度的部分，最少要多等一个周期。
  3. 对延迟敏感、负载有突发的服务，只设 request 不设 limit 是这次数据里最有效的办法，突发 40 从 190ms 降到 22ms。代价是 Pod 会占用节点上的空闲 CPU，可能影响邻居；QoS 等级也会随之变化，见 QoS 和 探针与资源限制 两篇笔记。
  4. 一定要设 limit 时，按峰值需求设，而不是按平均值留一倍余量。
  5. GOMAXPROCS 先用 Go 1.25+ 的默认值，确认 go.mod 的 go 行不低于 1.25。负载平稳时可以试着调高，这次 2 核和 4 核的 limit 下 p99 从 19ms 和 13ms 降到 7ms；有明显突发时调它没用。
  6. 0.5 核这类小于 1 的 limit，默认 GOMAXPROCS 也是 2，并行两个线程 25ms 就能用完 50ms 的额度，这次 p99 是不设 limit 的 4 倍。能给到 1 核以上就尽量别给小数，不过这条只来自一组数据，GOMAXPROCS=1 在 0.5 核下没测（推测）。

这次测试的边界

  • 每组 3 次运行，单个 Pod，单节点 kind 集群。压测器和服务端在同一台主机上，主机还在跑其他负载，个别运行的最大值有明显离群（例如 GOMAXPROCS=1、突发 40 的第 2 次运行 p99 469ms，另外两次是 209ms），原因没有查清。cburst-20-def 的第 3 次运行 bursts=0、限流也是 0，而同配置不加 burst 时限流 144 个周期，这个反常也没有解释。
  • 服务端的工作量是纯 CPU 计算。真实服务里有 I/O 等待，线程会主动让出 CPU，突发需求的形状不同，结论的数字不能直接套用。
  • cpu.max.burst 只在 kind 节点上手工设置，没有测试它对同节点其他 Pod 的影响。
  • 内核 7.0、Go 1.27，其他版本的调度和 GC 细节可能不同。
