本地 8B 模型当裁判：错答案加长，llama3.1 判对率从 84% 掉到 61%

 costalong  2026-11-21  AI 本地大模型 AI 工程实践 LLM 评测

前几篇测温度、JSON 输出和多步工具调用时，判对错都靠脚本：JSON 能不能解析、工具参数对不对、最后的数字等不等于标准答案。开放式回答写不出这种规则，常见做法是再找一个模型当裁判，给两个回答，问它哪个更好。

如果裁判也想用本地模型，先要知道它判得准不准，以及它会被什么带偏。这次我手写了 32 道题，每道一个正确回答、一个埋了一处事实错误的回答，再把错的那份加长、换格式、调换顺序，看三个本地模型的判决怎么变。一共 5000 多次调用。

题目怎么出

32 道题覆盖 Go、Kubernetes、Linux、Git、HTTP、SQL、Python、网络。每道题我写两个回答，错的那份只围绕一个能查文档核实的知识点出错，长度相近。例如：

问题：Kubernetes 里 readinessProbe 连续失败会发生什么？

正确：Pod 会被标记为未就绪，从 Service 的端点里摘掉，不再接收新流量。容器不会被重启，探针恢复成功后 Pod 会重新加入端点。重启容器是 livenessProbe 失败时的行为。

错误：kubelet 会杀掉容器并按 restartPolicy 重启它。重启后 Pod 会被重新加入 Service 端点。所以 readinessProbe 的阈值要设得宽松一些，避免反复重启。

在这对基础上做了 3 种变体，内容层面的对错不变：

变体怎么改
原始一对正确平均 90 字，错误平均 70 字
错的加长错误回答前面加一句“这是一个非常好的问题……”，后面补一条和问题相关但不回答问题的真实细节，再加一句总结客套，平均 229 字
错的改 markdown错误回答改成“要点”加列表，文字一字不改
同一份内容两边都是正确回答，一边纯文本，一边 markdown

每一对都按 A/B 两个顺序各问一次，提示词只有一句“哪个回答更好？只输出 A 或 B”。标签是我自己定的：错的那份有明确的事实错误，正确的那份就是标准答案。跑完后我回头查了被判错最多的题，没有哪道被三个裁判一致判反，最多是 6 次里错 3 次（硬链接、git reset --soft）；又人工读了十几条带分析的判决，没发现标签本身有问题。

先看总数

gemma4 在三种变体下都稳定在 94% 以上，不太受长度和格式影响。llama3.1:8b 和 qwen2.5-coder:7b 在原始一对上有八成多，但只要错的那份变长或者变好看，判对率就明显下降。llama 遇到“错的改 markdown”时 64 次里只对 32 次，和抛硬币一样。

灰条最显眼：两份内容完全相同，三个裁判都几乎一边倒地选 markdown 版。

位置：交换顺序后改口

一对回答只看一个顺序时，“选对率”掩盖了位置偏差。把两个顺序放在一起看：

裁判原始一对选 A 的比例两个顺序结论一致的题
gemma453%30/32
llama3.1:8b66%22/32
qwen2.5-coder:7b66%22/32

llama 和 qwen 各有 10 道题，换个顺序就换了答案，而且全都是两个顺序都选 A。两个回答本来就有明确对错，它们还有三成题被位置左右。

两个回答都没错时更严重。我让三个模型各回答 12 道开放题（“解释 Kubernetes Service 是做什么的”这类），再两两配对给三个裁判判。qwen 在这 72 次判决里选了 69 次 A，基本只看位置。

长度：几句客套和一条无关的真话

“错的加长”只加了客套话和一条与问题沾边的真实细节，错误那句一字没动。llama 从 54/64 掉到 39/64，qwen 从 52/64 掉到 42/64。按两个顺序都选对才算对来数，llama 只剩 13 道，另有 6 道在两个顺序下都选了加长的错答案。

改成打分也躲不开。qwen 给原始错误回答平均 4.97 分，加长后同样的错误平均 6.38 分。

格式：同一份内容，markdown 赢

两边内容相同，合理的结果是五五开，或者两个顺序给出相反答案。实际上 gemma4 64 次里 62 次选 markdown，llama 54 次，qwen 57 次。gemma4 不怎么受位置影响，所以它的格式偏好最干净：A/B 换了，它跟着 markdown 走。

这个偏好会直接盖过事实。llama 在“错的改 markdown”变体里只对一半；gemma4 在同一变体里还有 60/64，说明它更看重事实，但当两边事实相同时，格式就成了决定因素。

提示词里加一句“篇幅和格式不加分”的效果有限：gemma4 选 markdown 从 62 次降到 47 次，但选 A 的比例从 50% 升到 67%，格式偏好换成了位置偏好。llama 和 qwen 几乎没变。

自我偏好：这组数据下不了结论

gemma4 在包含自己答案的对局里选自己 45/48 次，看上去偏袒自己。但 llama 在“gemma4 vs qwen”的对局里也选 gemma4 18/24 次，而 gemma4 的 12 个回答全都用了 markdown，另外两个模型各只有 4 个。llama 选自己只有 7/48。

开放题没有标准答案，12 道题又太少，自我偏好、格式偏好和回答本身的好坏混在一起，分不开。我不把它算作结论。

几种补救办法

下面按“两个顺序都选对才算对、两个顺序不一致算平”统计，每格是 32 道题里的 对/平/错：

做法gemma4 原始llama 原始qwen 原始gemma4 加长llama 加长qwen 加长
只问 A 或 B，交换顺序30/2/022/10/021/10/129/3/013/13/615/12/5
加一句评分标准27/5/025/5/220/12/028/4/010/15/716/13/3

“加一句评分标准”和“先分析再结论”用的是同一句标准（事实最重要，篇幅和格式不加分），区别只在要不要先写分析。前者对长度偏差没有帮助，llama 反而从 13 降到 10；后者把 llama 和 qwen 在加长变体上都拉到 22。从这组单次运行的数据看，起作用的更像是让模型先逐条检查，而不是那句标准。

先分析再下结论：结论变准了，理由不可信

qwen 在分析里写出了正确事实“硬链接不能跨越文件系统”，却据此判正确回答“不正确”，最后选了错的那个。llama 在 CPU limit 那题两个顺序都判对，分析里却把 CFS 写成“Container Fair Scheduler”。如果打算把裁判的分析当成反馈给人看，这些理由要单独核对。

这种方式每次判决要输出几百个 token，gemma4 有 4 条写到 700 token 上限被截断，其中 1 条在截断前已经写出“选择 B”，另外 3 条没给出结论，按未解析计。gemma4 本身在原始一对上的结果也从 30 题降到 28 题，对本来就准的裁判，多写分析不一定加分。

打分制：llama 给 134/160 个回答打了 8 分

分别打分天然没有位置问题，但 llama 几乎不区分好坏：160 个回答里 134 个是 8 分，正确和错误回答平均分是 8.25 和 7.66，32 道题里 21 道打了平分。gemma4 打分最好用，正确回答平均 9.91，错误回答 4.22。

两个顺序的概率取平均

Ollama 0.35 的 /api/chat 可以返回第一个生成 token 的对数概率。只生成 1 个 token，取 A 和 B 的概率，再把两个顺序下“正确回答一侧”的概率平均，大于 0.5 就算判对：

body = {"model": judge, "messages": [{"role": "user", "content": prompt}], "stream": False,
        "logprobs": True, "top_logprobs": 10,
        "options": {"temperature": 0, "num_predict": 1}}
top = {x["token"]: x["logprob"] for x in resp["logprobs"][0]["top_logprobs"]}
pa = 1 / (1 + math.exp(top.get("B", -50) - top.get("A", -50)))   # 只在 A、B 之间归一化

A、B 两项合计占第一个 token 概率的比例，llama 和 qwen 每次都在 99.5% 以上，gemma4 平均 99% 以上（个别调用低到 71%），取这两项基本没有丢掉什么。在原始一对上它是最好的办法：llama 从 22 对 10 平变成 29 对，qwen 从 21 对变成 30 对，gemma4 32 题全对。成本和交换顺序一样，每对两次调用，每次一个 token。

它解决的是位置偏差。原始一对里，llama 和 qwen 两个顺序结论不一致的 20 道题，多数是一个顺序下明显偏向正确回答（概率多在 0.8 以上），另一个顺序下只是略偏向错的那份（多在 0.3 到 0.5 之间），平均后 20 道里有 16 道正确的一边胜出；llama 有 3 道、qwen 有 1 道，偏错的那一侧偏得太多，平均后仍判错。长度偏差它解决不了：llama 和 qwen 在加长变体上仍然有 11 道两边平均后选了错的。

温度 0.7 和 seed：三个 seed 不是三次独立重复

我原本的设计是 temperature 0.7 下跑 seed 1、2、3，看判决随机翻转多少。结果 seed 2 和 3 的统计在三个模型上完全相同，seed 1 却把 llama 的判对率从 86% 拉到 39%。

按对数概率换算，第一行在温度 0.7 下选 A 的概率是 0.957，seed 1 两次都选了 B，seed 2、3 都选 A。用 logprob 回算全部 192 次调用：seed 1 有 82 次选了概率较小的那个 token，llama 和 qwen 的分界在约 0.96：多数 token 概率不高于 0.957 时都翻了，不低于 0.959 时都没翻；gemma4 在 0.985 时也翻了一次。seed 2、3 的 192 次调用逐条完全一致，各只有 2 次选了少数 token，都在接近五五开的题上。截图是另一次运行，BG 那行的 logprob 和主实验不同：接近五五开的题，跨次运行连概率最大的 token 都可能变。

推测：Ollama 用 seed 初始化采样器，每次请求的第一个随机数都一样，所以 seed 1 相当于一个固定落在 0.96 附近的分位数。我没读采样器源码，这个机制没有验证，llama 和 qwen 的数据符合这个规律，gemma4 有一个例外。对裁判来说结论很直接：固定 seed 跑三遍得到的是三个固定分位数，三次结果之间高度相关，不能当成三次独立采样，也不能用来估计判决的稳定性。

要估计温度的影响，用概率算期望更干净。按 logprob 换算，温度 0.7 下每次判决选对的期望次数：gemma4 61.5/64（温度 0 是 62），llama 49.0/64（温度 0 是 54），qwen 52.3/64（温度 0 是 52）。裁判没有理由开温度，开了只会让 llama 更差。

裁判自己拿不准的事实

Go 1.22 起 for 循环变量每轮一个新变量，这道题 gemma4 在原始一对上两个顺序都判对了。但在先分析再下结论的模式下，它两个顺序给出了相反的“事实核查”：一次写“Go 1.22 确实对循环变量的捕获机制进行了改进”，另一次写“Go 1.22 并没有在 for 循环变量捕获方面做出这种改变”，后者一直写到 token 上限也没给出结论。加长变体里，它打开思考后两个顺序都选了错的那份。

推测：裁判能可靠判断的，只有它自己掌握得很牢的事实（这里的依据只有这一道题）。较新的版本变化、冷门参数，它可能只是被包装和顺序推着走。

接进评测前先跑的几项检查

  1. 准备一小组有明确对错的题，像本文一样埋错误，先测裁判在这组题上的判对率，不要直接用在开放题上。
  2. 每对回答至少问两个顺序。能拿到 logprob 就把两个顺序的概率平均，拿不到就把两次结论不一致的记成平局，不要只问一次。
  3. 被评的回答长度和格式差别大时，把错答案加长、加 markdown 的变体放进校准集。本文里 llama 在这两种变体上掉了 23 和 34 个百分点，qwen 掉了 15 和 6 个百分点，加一句“格式不加分”基本没用。
  4. 需要更准的结论时用“先逐条分析，最后一行写结论”，但把分析当作参考，不当作证据。
  5. 裁判用温度 0。想看稳定性就看 logprob，不要靠换几个 seed 重跑。

以上数字大多是每个配置跑一次（温度 0，每对两个顺序），题目只有 32 道，相差一两道题的差异不要当成结论。
