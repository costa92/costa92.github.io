Go 请求已经超时，为什么后台还在消耗 CPU

 costalong  2026-11-21  golang Go 故障排查 HTTP gRPC
Go 故障排查 HTTP gRPC context
golang

阅读次数:

上一篇 CPU 限流实验里，CPU 配额用完后，请求需要等到下个周期。给客户端加上 100ms 超时，还要看服务端的计算何时结束。如果旧任务继续运行，重试只会增加同时计算的任务数。

这次用 Go HTTP 服务做对照，8 个客户端都收到了超时错误，服务端却继续算完了全部工作。客户端结束后，进程又消耗了约 3 秒 CPU。服务端 context 已经取消，计算循环没有检查它。

客户端超时后，8 个 handler 仍在计算

服务只做 SHA-256 计算。8 个请求全部进入业务 handler 后统一开始计算，比较三种写法：前两组忽略取消信号，第三组让计算循环检查 r.Context()。

实验运行在 macOS arm64 本机，Go 1.27.2，主机有 14 个逻辑 CPU，程序固定 GOMAXPROCS=2。客户端和服务端在同一个进程，通过 httptest.NewServer 建立真实 HTTP/1.1 连接，没有代理或 Kubernetes CPU limit。

先用单 goroutine 校准约 400ms CPU 时间的工作量，这次得到每个任务 9,454,592 次 SHA-256。三组都用这个固定次数，没有写成“循环到墙钟过去 400ms”：否则调度一慢，任务反而少干活，就无法比较取消掉了多少计算。

场景超时设在哪里计算如何处理取消
客户端超时，忽略取消http.Client.Timeout=100ms不检查 context
服务端超时包装器，忽略取消http.TimeoutHandler(..., 100ms, ...)；客户端兜底 20s不检查 context
客户端超时，业务协作取消http.Client.Timeout=100ms每 1024 次哈希检查一次

三组各跑 3 轮。客户端超时从发起调用开始计时，TimeoutHandler 从进入包装器开始计时，都早于统一放行计算的时刻。下表的“客户端全部结束”从放行计算起算；“额外等待”接着量到业务完成信号全部到达。每列单独取 3 轮中位数：

场景客户端全部结束额外等待业务结束总 CPU客户端结束后 CPU
客户端超时，忽略取消148ms1503ms3.298s3.000s
TimeoutHandler，忽略取消293ms1362ms3.302s2.718s
客户端超时，业务协作取消159ms93ms0.505s0.187s

CPU 取 getrusage(RUSAGE_SELF) 的 user 与 system 时间差，包含同进程客户端、服务端和 Go 运行时。总 CPU 从发出请求前量到业务完成信号全部到达；最后一列只量客户端全部结束之后的部分。两个 P 可以并行，累计 CPU 时间会大于墙钟时间；GOMAXPROCS=2 也不能当成容器的 2 核配额。

第一组的 8 个任务最后全部完成，总哈希次数仍是 75,636,736。客户端全部结束时，业务 handler 的活跃数还是 8。

Client.Timeout会限制连接、重定向、读取响应体等请求过程，并取消底层 Transport 的请求。这里的直连 HTTP/1.1 服务端已经收到取消，计算函数却没有读取 ctx.Err() 或监听 ctx.Done()，因此没有提前退出。

TimeoutHandler 返回 503，内层继续计算

第二组把超时放到服务端：

handler := http.TimeoutHandler(
    workHandler,
    100*time.Millisecond,
    "deadline\n",
)

3 轮里，客户端每轮收到 8 个 HTTP 503，业务仍完整做完 8 个任务。计算结束后再写响应，8 次写入全都得到 http.ErrHandlerTimeout。

Go 的 timeoutHandler.ServeHTTP 实现会派生带超时的 context，另起 goroutine 执行业务 handler。外层超时后返回 503，内层 goroutine 是否退出取决于业务代码。这里仍是不检查 context 的哈希循环，所以计算全部完成，最后写响应时才得到错误。

http.Server.WriteTimeout 限制写响应的时间，也不会终止业务计算。另需注意，TimeoutHandler不支持 Flusher 和 Hijacker，依赖 Flush 的 SSE 或分块响应接口不能直接套用。

让工作函数响应取消

第三组的客户端超时不变，计算循环改为每 1024 次哈希检查一次 context。省略对照开关后的代码如下：

func hashWork(ctx context.Context, rounds int) ([32]byte, error) {
    var sum [32]byte
    for done := 0; done < rounds; {
        if err := ctx.Err(); err != nil {
            return sum, err
        }
        end := min(done+1024, rounds)
        for ; done < end; done++ {
            sum = sha256.Sum256(sum[:])
        }
    }
    return sum, nil
}

handler 传入 r.Context()。3 轮里，每轮 8 个任务都因取消提前退出，完整完成数为 0，整批 CPU 从约 3.30 秒降到约 0.51 秒。

下图对应请求已进入业务函数、客户端触发取消的情况。TimeoutHandler 改由包装器派生的 context 触发取消，工作函数仍需响应。

第三组客户端全部结束时，8 个业务 handler 也仍然活跃，91～119ms 后才收到全部完成信号。这段延迟包含取消传播、goroutine 调度和等待下一个检查点的时间，没有分别测量，不能全归因于检查间隔。

实际返回时间也超过了配置的 100ms。从放行计算到客户端全部返回，三轮中客户端超时组用了 123～180ms，包装器组用了 281～315ms，协作取消组用了 129～161ms。同进程里的计时器和网络处理也要获得调度。这组实验比较的是取消前后的计算量，不能用于推算生产 QPS。

HTTP 传递取消，gRPC 还传递 deadline

协议实验分别使用 HTTP/1.1、HTTP/2、gRPC 的真实连接，每轮发一个请求，记录服务端收到的 context 和完成步数。任务共 20 步，每步设置 10ms 等待，模拟可以中断的慢操作。这组等待任务没有计入前面的 CPU 统计。

连接先预热，请求进入业务函数后才纳入观察。

只停止本地等待，没有取消底层请求

先给外层等待设置 50ms 超时，RPC 继续使用 Background：

result := make(chan error, 1)
go func() {
    _, err := client.Run(context.Background(), req)
    result <- err
}()

select {
case err := <-result:
    return err
case <-time.After(50 * time.Millisecond):
    return errors.New("local wait timeout")
}

50ms 后退出的是外层 select，context.Background() 没有被取消，RPC 仍在执行。用同样的方式等待 client.Do，也不会取消底层 HTTP 请求。

案例将这一组记为 wait-only。三种协议的协作取消任务都做完了 20 步，底层调用正常成功。容量为 1 的结果通道用于接收迟到结果，避免发送 goroutine 阻塞，不负责取消请求。

把 deadline 传给实际请求

把 50ms 的 context deadline 传给实际请求，每种协议分别运行忽略取消和协作取消两种任务。以下是单次运行结果，完成步数受调度影响：

协议服务端请求有 deadline忽略取消完成步数协作取消完成步数
HTTP/1.1无20/204/20
HTTP/2无20/204/20
gRPC有20/204/20

HTTP/1.1 使用本机 TCP，HTTP/2 使用启用 HTTP/2 的 TLS 测试服务器，协议由服务端 r.Proto 确认。gRPC 使用 grpc-go v1.76.0、标准 protobuf 和真实 TCP。连同原生 Client.Timeout、主动 cancel() 和独立后台任务，程序共保存了 33 组直接调用结果。

表中的 deadline 来自服务端业务函数的 ctx.Deadline()。原生 HTTP 不会自动把客户端的 Go deadline 编码进请求，因此前两行都是“无”。请求取消后，两种 HTTP 服务端都记录到了 context.Canceled。原生 Client.Timeout 和主动 cancel() 的对照也收到了取消。

gRPC 会把时限编码进 grpc-timeout 元数据，接收方据此建立 deadline，格式见 gRPC over HTTP/2 协议。调用时要把 context 传给这次 RPC：

ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
defer cancel()

_, err := client.Run(ctx, &api.WorkRequest{Mode: "cooperate"})
code := status.Code(err) // 本次超时调用记录为 codes.DeadlineExceeded

client 由 api.NewWorkerClient(conn) 创建，接口与生成文件在案例的 api/ 目录中。超时设置在这次 Run 上；只限制建连时间，不会给后续使用 context.Background() 的 RPC 设置业务时限。

服务端把入站 context 传给 doSteps，省略实验记录字段后如下：

func (s *worker) Run(ctx context.Context, req *api.WorkRequest) (*api.WorkReply, error) {
    _, err := doSteps(ctx, s.cfg, false) // 内部 select ctx.Done()，取消后提前返回
    if err != nil {
        return nil, status.FromContextError(err).Err()
    }
    return &api.WorkReply{Outcome: "completed"}, nil
}

ignore 模式不监听 ctx.Done()，到期后仍然做完了 20 步。gRPC 的取消说明要求应用停止自己启动的工作，框架负责通知取消。CancelFunc也不会等待工作退出。

两端记录的错误名并不总是相同。这次 gRPC 客户端 deadline 到期得到 codes.DeadlineExceeded，主动取消得到 codes.Canceled；几组 deadline 调用的服务端记录到的却是 context.Canceled。客户端发来的取消和服务端本地 deadline 可能以不同顺序触发，服务端应按实际错误用 status.FromContextError转换。

这些请求都已经进入业务函数，客户端和服务端也是直连。如果在等连接或建连时就超时，服务端可能根本没收到请求。经过代理、网关，或者遇到网络故障时，还要逐跳检查取消能否及时传过去。

A 调 B 时，Background 切断了取消关系

转发实验增加服务 A，由 A 调用 gRPC 服务 B。B 始终响应取消，A 分别传入原请求 context 和 context.Background()：

outgoing := ctx
if !passParent { // 对照开关：故意切断父请求的 deadline 和取消关系
    outgoing = context.Background()
}
return backend.Run(outgoing, req)

客户端总时限仍为 50ms，A 先模拟处理 20ms，再调用 B。三种入站协议，各跑沿用 context 和改用 Background 两种情况，共 6 组：

客户端到 A沿用请求 context：B 的 deadline沿用请求 context：B 完成步数改用 Background：B 完成步数
HTTP/1.1无，但收到取消2/2020/20
HTTP/2无，但收到取消2/2020/20
gRPC有，剩余约 29.8ms2/2020/20

使用 context.Background() 的三组，B 都没有收到原请求的 deadline 或取消，最终做完 20 步。gRPC 入站且沿用 context 时，B 的剩余时限约为 29.8ms，已经扣除了 A 的处理时间。Go 的 deadline 传播需要把入站 context 继续传给下游调用。

HTTP → A → gRPC B 虽然没有数值 deadline，沿用 context 时 B 也只做了 2 步。客户端取消 HTTP 请求，A 的 context 随之取消，接着取消 A 发出的 RPC，B 才得以提前退出。

需要单独限制 B 的调用时间时，可用 context.WithTimeout(ctx, ...) 派生子 context，结束时调用返回的 cancel。它保留父请求的取消关系，deadline 取父子中较早的一个。

下游是 HTTP 或数据库时

调用 HTTP 服务也可以把同一个 context 交给请求对象：

req, err := http.NewRequestWithContext(ctx, http.MethodGet, upstreamURL, nil)
if err != nil {
    return err
}
resp, err := client.Do(req)
if err != nil {
    return err
}
defer resp.Body.Close()

原 context 取消会取消这个 HTTP 请求，对方的业务仍需响应自己的请求 context。HTTP/2 可以取消单个请求而保留 TCP 连接，连接是否断开不能用来判断业务是否退出。

数据库调用可以把原请求 context 或它派生的 context 传给 QueryContext、ExecContext，写法见官方的数据库取消示例。这次没有测试数据库，具体驱动能否取消、数据库多久停止执行，需要另测。

后台任务使用独立的时限

如果任务需要在客户端离开后继续执行，就不能继续依赖请求 context。HTTP 的请求 context 在 ServeHTTP 返回时也会取消；即使改成 go work(ctx)，响应取消的工作函数仍会退出。

案例里的 detached 先用 context.WithoutCancel解除父 context 的取消和 deadline，再为任务设置独立上限：

taskCtx, taskCancel := context.WithTimeout(context.WithoutCancel(requestCtx), time.Second)
done := make(chan error, 1)
go func() {
    defer taskCancel() // 在实际工作结束时释放，不在 HTTP handler 返回时取消
    done <- work(taskCtx)
}()

handler 监听 requestCtx.Done()，请求取消后返回；后台 goroutine 使用 taskCtx 继续执行。案例中的测试程序负责等待后台任务、收集结果，最后退出。

独立时限为 1 秒时，客户端在约 50ms 取消，任务仍做完 20 步。将 gRPC 独立任务的时限缩到 80ms 后，任务完成 7 步，以 DeadlineExceeded 结束；客户端此前已收到 Canceled。

这个任务只保存在当前进程内，不支持重启恢复。需要保证最终执行时，应先可靠地保存任务，再由 Worker 控制并发、记录结果和处理重试，不能依赖 WithoutCancel。若需要响应服务关闭，可以从服务级 context 派生任务。后台应只保留必要输入，handler 返回后不再使用 ResponseWriter 或请求体。

重试之前，先确认旧任务有没有退出

前两组客户端结束等待时，8 个旧任务都还在计算。此时重试，会让新旧请求一起占用 CPU。

限制并发时，等待名额的请求也应能响应取消：

func withSlot(ctx context.Context, slots chan struct{}, work func(context.Context) error) error {
    select {
    case slots <- struct{}{}:
        defer func() { <-slots }()
    case <-ctx.Done():
        return ctx.Err()
    }
    if err := ctx.Err(); err != nil {
        return err
    }
    return work(ctx)
}

slots 必须是容量大于 0 的缓冲通道，例如 make(chan struct{}, maxInFlight)。容量需按服务承受能力确定，这里仅给出写法，没有做容量测试。名额应由实际工作持有到退出；若在 TimeoutHandler 外层获取、返回 503 时释放，内层计算尚未结束就能放入新请求，实际工作数仍可能超限。

外部写操作还涉及结果确认：客户端收到超时时，写入可能已经成功，取消不会撤销写入。重试前需要核对结果，或用幂等设计避免重复执行。不支持取消的阻塞库函数，也无法靠外层 context 强行终止。

排查时，把活跃任务数记在实际业务函数里，同时记录客户端结束和业务结束的时间。取消一批慢请求后，检查任务数、CPU 和下游调用是否回落。仍有任务运行，再检查请求取消、context 传递和工作函数的检查点；客户端的超时日志本身不能说明任务已经退出。

复现实验

配套代码和保存的结果位于 blog-go-example/http-timeout-cancellation，使用独立 go.mod。根目录 CPU 程序本身只依赖标准库；协议示例固定使用 grpc-go v1.76.0、protobuf v1.36.10，接口生成文件已包含在 api/ 中。

进入目录后，先运行测试和 CPU 对照：

go test ./...
go test -race ./...
go run . -runs 3 -requests 8 -deadline 100ms -work 400ms -procs 2
python3 summarize.py results.json

go run . 会重新校准哈希次数，再运行实验；summarize.py 读取的是随文保存的 3 轮 results.json。换台机器，重新校准出的哈希次数和耗时可能不同。

协议和转发实验由另一个入口运行：

# HTTP/1.1、HTTP/2、gRPC：33 组直接调用
go run ./cmd/protocols

# 对比 gRPC deadline 下忽略取消和协作取消的业务
go run ./cmd/protocols -protocol grpc -trigger deadline -mode ignore
go run ./cmd/protocols -protocol grpc -trigger deadline -mode cooperate

# A 先处理 20ms，再调用 gRPC B
go run ./cmd/protocols -chain

# 独立任务的 80ms 上限
go run ./cmd/protocols -protocol grpc -trigger cancel -mode detached -background-limit 80ms

# 校验保存的协议观察
python3 summarize_protocols.py protocol_results.json

protocol_results.json 保存 33 组直接调用、6 组转发和 1 组独立时限结果。测试覆盖取消能否传到服务端、HTTP/2 是否实际协商、下游是否保留 context，以及独立任务是否受自己的上限控制。各文件的职责、结果字段和 protobuf 生成命令见案例 README。

终端截图为同参数另一次运行的字段节选，表格和统计图仍使用随文保存的数据。views/*.jq 位于案例仓库，筛选方法见 README。env -u GOROOT 用来避开本机 GOROOT 与 Go 工具链版本冲突；Go 环境正常时不需要此前缀。

实验均在本机 loopback 上运行，gRPC 为 unary RPC。协议对照使用等待步骤模拟慢操作，不能替代流式 RPC、真实数据库、第三方 API 或生产代理的取消验证；CPU 统计支持 Linux 和 macOS，本文数据来自 macOS。
