检查会假绿：kind v0.23 的 kindnetd 放行了 default-deny，契约检查漏掉 9 个新破坏里的 8 个

我说的 AI-Native，是系统从设计起就假设会有一个 AI 读它的状态、据此提出改动。这样一来，系统报告的”成功””通过””已生效”必须能直接当证据用。人看到绿灯还会结合经验起疑，读命令输出的 AI 不会。所以在给 AI 开任何接口之前，我更关心另一件事：我手上的检查，什么情况下会假绿。

这篇文章的旧版本里有两句话没给证据。一句是”kind 默认的 kindnetd 不执行 NetworkPolicy，apply 成功但流量照样通”；另一句是”服务契约检查做了 36 次故意破坏，全部拦下”。这次我把两件事都重跑了一遍，结果和我原来写的都不完全一样。

同一条 default-deny，四个集群的结果

实验很小：一个单节点 kind 集群，np-demo 命名空间里放一个 nginx 当 server，一个带 curl 的 Pod 当 client。client 直接 curl server 的 Pod IP，超时 5 秒。每个集群测三次：

  1. 不加任何策略，应该是 200，不通说明网络本身坏了。
  2. 加一条选中全部 Pod、同时禁止 Ingress 和 Egress 的 default-deny，应该超时。
  3. 再加两条显式放行 client 到 server:80 的策略，应该恢复 200，证明前一步是策略生效，不是网络断了。

探测打 Pod IP 而不是 Service 名，是因为 default-deny 连 Egress 一起禁了，走 Service 名会先卡在 DNS 上，那样第二步的失败分不清是哪条规则造成的。

我在四个集群上跑了同一个脚本：

集群网络插件无策略default-deny显式放行
kind v0.23.0，Kubernetes v1.30.0kindnetd v20240202-8f1494ea200200200
kind v0.24.0，Kubernetes v1.31.0kindnetd v20240813-c6f155d6200超时200
kind v0.33.0，Kubernetes v1.37.0kindnetd v20260820-69b56db7200超时200
kind v0.33.0，Kubernetes v1.37.0Calico v3.32.1200超时200

kind v0.23.0 那一次就是我旧文里描述的假绿，完整输出是这样的：

--- no policy
$ kubectl exec -n np-demo client -- curl -sS -o /dev/null -m 5 -w %{http_code}\n http://10.244.0.5/
200
$ kubectl apply -f manifests/default-deny.yaml
networkpolicy.networking.k8s.io/default-deny created
$ kubectl get networkpolicy -n np-demo
NAME           POD-SELECTOR   AGE
default-deny   <none>         0s
--- default-deny
$ kubectl exec -n np-demo client -- curl -sS -o /dev/null -m 5 -w %{http_code}\n http://10.244.0.5/
200

策略创建成功，查得到，流量照样通。同样的步骤换到 kind v0.33.0 默认的 kindnetd 上，第二步变成了：

--- default-deny
$ kubectl exec -n np-demo client -- curl -sS -o /dev/null -m 5 -w %{http_code}\n http://10.244.0.5/
curl: (28) Connection timed out after 5001 milliseconds
000
command terminated with exit code 28

kind v0.24.0 的 kindnetd 启动日志里有一行 Starting controller kube-network-policies，之后是 Syncing nftables rules，它已经带了一个 NetworkPolicy 控制器。我只测了 v0.23.0、v0.24.0 和 v0.33.0 三个 kind 版本，所以能确定的是：v0.23.0 自带的 kindnetd 不执行策略，v0.24.0 和 v0.33.0 的会执行。

这对我的练习项目有直接影响。项目锁定的 kind 是 v0.32.0，集群一直禁用 kindnetd、改装 Calico，理由就是”kindnetd 不执行 NetworkPolicy”。项目的已知缺口清单里还挂着一个故障实验：”NetworkPolicy 创建成功但 CNI 未执行”，计划是起一个默认 kindnetd 的临时集群来复现，一直没跑。按这次的结果，在项目实际用的 kind 版本上，这个实验按原计划复现不出来，得固定一个 v0.23.0 或更早的 kind 才行。我旧文里那句话，用的是一个没有在当前版本上验证过的前提。

四个集群有一点完全一样：kubectl apply 都返回 created，kubectl get networkpolicy 都列出了 default-deny。命令层面的输出没有任何区别，能分出真假的只有那一次 curl。所以”策略已生效”这个结论只能来自流量探测，不能来自 apply 的返回值。

Calico 集群第一次跑在节点 Ready 之后卡住

Calico 集群用 disableDefaultCNI: true、podSubnet 设成 192.168.0.0/16，然后 apply 官方 v3.32.1 的 calico.yaml。脚本最初的写法是等节点 Ready 后就部署测试 Pod，结果两个 Pod 在 ContainerCreating 停了 3 分钟，事件里是：

Failed to create pod sandbox: ... plugin type="calico" failed (add):
stat /var/lib/calico/nodename: no such file or directory:
check that the calico/node container is running and has mounted /var/lib/calico/

节点已经 Ready，calico-node 还没起来。我在脚本里加了一步 kubectl -n kube-system rollout status ds/calico-node，第二次就正常了。”节点 Ready”和”Pod 网络可用”是两件事，前者也会让人以为可以往下走。

另外这台机器当时负载很高（load average 一度到 45），有两次 kind create cluster 在 kubeadm init 阶段超时失败，删掉重建才过。这和 CNI 无关，只说明这类实验在共享机器上要留重试的余地。

契约检查：225 个内置破坏全部被拒

第二件事是练习项目里的服务模板契约。新服务从模板生成，生成后的仓库里有一个 check-golden-path.mjs，按构建、运行时、交付、安全、可观测性、归属六个方面检查渲染后的 Helm 清单和 CI 配置。旧文里的”36 次故意破坏”出自 10 月 13 日的模板 0.3.0：一个无依赖的单环境服务 17 次，一个带 PostgreSQL 和 Redis、三环境、公开路由的服务 19 次。每次只改坏一处，要求检查非零退出，并且失败原因要匹配预期。

到现在这份破坏清单已经长到两个服务分别 98 和 127 项。原来的测试遇到第一个不符合预期的用例就中断，我在项目副本里加了一个只记录不中断的模式，把每一项的退出码和失败原因都写下来，然后完整跑了一遍。生成、vet、race 测试加上全部破坏，两个服务一共 435 秒，单次契约检查的中位数是 1.58 秒。

结果：225 项全部被拒绝，失败原因全部和预期匹配。最初那 36 项，名字都还在清单里，也都被拒绝了。它们改的是这些地方：build 目标留空、Make 依赖写坏、镜像名改错、/version 路由挪走、运行时测试加 t.Skip、CI 里删掉契约检查、Catalog 负责人改掉、删 CODEOWNERS、删 runbook 里的值班方式、删就绪探针、关掉只读根文件系统、打开 ServiceAccount token 自动挂载、删 NetworkPolicy、删 ServiceMonitor、删 dashboard、忽略镜像 digest、改告警接收方，三环境的服务另外多两项：给 prod 打开自动同步、把 prod 标成 dev。

我另写的 9 个破坏，8 个通过了

225 项全过，说明检查和它自己的清单对得上。清单是写检查的人写的，它测的是作者想到的那些破法。所以我又写了 9 个清单里没有的破坏，标准是渲染后的 YAML 仍然合法，但部署之后服务会坏掉或者变弱。两个服务各跑一遍，结果一致。表里”部署后的后果”一列是按 Kubernetes 的行为推测的，这几个破坏我没有真的部署：

破坏部署后的后果检查结果
就绪探针端口改成 9090Pod 永远不 Ready通过
存活探针端口改成 9090容器被反复重启通过
Service 的 targetPort 改成 9090Service 转发到空端口通过
容器 command 改成 sleep infinity服务根本不启动通过
放行 Prometheus 的 Pod 标签打错一个字指标抓不到通过
删掉放行规则里的 Prometheus podSelector监控命名空间里任何 Pod 都能访问服务通过
用 projected 卷挂 ServiceAccount token自动挂载关了，token 照样进了容器通过
就绪探针周期改成 300 秒摘流量延迟到 5 分钟通过
内存 request 改成 1Mi调度严重低估拒绝

看检查代码就知道为什么。探针只比对了 path 是不是 /ready 和 /health，没比端口；Service 只比对了 selector；NetworkPolicy 的放行来源只要求标签非空，不要求标签能对上真实的 Pod；token 只检查了 automountServiceAccountToken: false 这个字段。资源配置那一项把 request 和 limit 都钉死了，所以内存那一条被拦下。运行时测试启动的是 Go 进程本身，不是 Helm 里写的容器命令，所以 command 被换掉它看不到。

这 8 条和 kindnetd 那个假绿是同一类问题：检查读的是声明，后果发生在运行时。kubectl apply 成功不代表流量被拦，readinessProbe.path 写对也不代表探针打得到。静态检查能补，比如给探针加端口比对、给放行规则的标签加一份已知 Pod 的对照，但”能不能真的连上”这一类，只有把服务部署起来探一次才算数，做法和上面的三态 curl 一样。

契约文件本身其实写了一条它证明不了的事：Catalog 里的团队和代码平台上的审查人属于两个系统，检查只能证明两边写得一致，证明不了这个人真在这个团队。按这次的结果，端口、容器命令和放行标签是否对得上真实 Pod，也该写进这份”证明不了”的清单。

还没测的部分

练习项目里给 AI 设计的部分，包括只能以 PR 形式提交改动、按准确率分级放权，目前只是设计，AI 还没接进来，准确率和人推翻 AI 结论的比例都没有实测数据，这篇不展开。

本文的脚本、清单、kind 配置、四个集群的完整输出，以及 243 次契约破坏的逐条结果，都在 blog-go-example/ai-native-false-green。被测的契约检查在我的私有练习仓库里，那里只放了记录模式的补丁和 9 个额外破坏的定义，读者没法直接复跑这一部分。NetworkPolicy 实验只依赖 Docker、kind 和 kubectl，可以原样复现。
