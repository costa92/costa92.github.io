让 Cloudflare 缓存 GitHub Pages 的 HTML：难的是部署后什么时候清

 2026-11-05  linux Cloudflare GitHub Pages CDN GitHub Actions
Cloudflare GitHub Pages CDN GitHub Actions Hexo
linux Network
文章字数:   3.7k
阅读次数:  
   阅读模式

这个博客是 Hexo 生成的静态站，放在 GitHub Pages 上，域名接入了 Cloudflare。我一直以为页面已经由 Cloudflare 缓存着，直到看了一眼首页的响应头：

cache-control: max-age=600
cf-cache-status: DYNAMIC

DYNAMIC 表示 Cloudflare 没有缓存这个响应，每次请求都转回 GitHub Pages。用 Lighthouse 测，首页 HTML 的服务器响应时间在 160 到 520 毫秒之间跳动；从我这台机器用 curl 请求，首字节时间在 0.5 到 0.65 秒左右。CSS、JS 和图片早已在边缘缓存，偏偏所有页面都要先拿到的 HTML 每次都要回源。

下面记录让 HTML 进入边缘缓存的过程。规则本身只要几分钟，真正花时间的是两个上线后才暴露的问题：浏览器缓存时间被改掉了，部署后清缓存的时机不对就会把旧页面再缓存一天。

为什么 HTML 默认不缓存

Cloudflare 的默认缓存只认文件扩展名：css、js、图片、字体这类静态资源会缓存，HTML 不在列表里。它不知道你的 HTML 是静态生成的还是每次由程序拼出来的，保守起见当成动态内容。对 WordPress 这类站点这是合理的默认值，对 Hexo 这种纯静态站就只剩损失。

要改变这个行为，在区域的「缓存 → Cache Rules」里加一条规则，把 HTML 标记为「符合缓存条件」，免费套餐就能用。我的站点之前已经有两条：带 ?v= 版本号的 CSS/JS 缓存一年，/images/ 下的图片缓存 7 天。新规则放在最后，加完后列表如下：

匹配条件用表达式写：

(http.host eq "costalong.com"
 and not starts_with(http.request.uri.path, "/cdn-cgi/")
 and (ends_with(http.request.uri.path, "/")
      or http.request.uri.path.extension in {"html" "xml" "json"}))

Hexo 的固定链接以 / 结尾，index.html 实际上是 /2026/11/05/xxx/ 这样的路径，所以必须匹配结尾的斜杠，只写 html 扩展名会漏掉几乎所有文章页。xml 和 json 覆盖 atom.xml、sitemap.xml、站内搜索用的 search.xml，它们和 HTML 一样随每次构建变化。/cdn-cgi/ 是 Cloudflare 自己的路径，排除掉以防万一。

在规则编辑页选「自定义筛选表达式」，点「编辑表达式」直接粘贴：

操作部分设置两项：

设置取值原因
缓存资格符合缓存条件让 HTML 可以被缓存
边缘 TTL忽略缓存控制标头，使用 1 天源站给的 max-age=600 只有 10 分钟，边缘按它走的话缓存很快过期

边缘 TTL 定为 1 天，前提是每次部署后会主动清缓存，后面单独讲。部署后第二次请求首页，响应头变成了 cf-cache-status: HIT。

第一个坑：浏览器缓存时间被改成 4 小时

同一个响应头里还有一行变化我差点没注意：

cf-cache-status: HIT
cache-control: max-age=14400

源站给的是 600 秒，经过 Cloudflare 变成了 14400 秒，也就是 4 小时。规则里我只设置了边缘 TTL，没有动浏览器 TTL。对照发现，没有被新规则匹配的 build-id.txt（后文会用到）仍是 max-age=600、DYNAMIC，只有被规则标记为可缓存的响应变成了 4 小时。看起来，响应一旦变为可缓存，区域级的默认浏览器缓存 TTL（4 小时）就接管了 cache-control。

这比边缘缓存过期更麻烦。Cloudflare 的清缓存只作用于它自己的边缘节点，管不到访客浏览器里存着的副本。访客早上看过首页，中午我发布了新文章，他在 4 小时内再打开首页，浏览器直接用本地缓存，连请求都不会发出去。

修法是在同一条规则里显式加上浏览器 TTL，选「接受源服务器 TTL」。保存后响应头回到 cache-control: max-age=600，cf-cache-status 仍是 HIT：边缘缓存 1 天，浏览器只缓存 10 分钟。规则最终的缓存设置如下，浏览器 TTL 那一栏的说明也写明了「Cloudflare 缓存清除不会清除客户端浏览器上缓存的内容」：

如果你的站点也在源站设置了较短的 max-age，加完缓存规则后值得核对一次这个头。

缓存 1 天，部署后谁来清

边缘 TTL 有两种取法：

方案部署后多久生效代价
边缘 TTL 设短，比如 2 小时，不清缓存最长 2 小时不用任何密钥；但缓存命中率低，新文章发布后要等
边缘 TTL 设长（1 天），部署后调用 API 清缓存部署完立即生效需要一个 API Token，部署流程多一步

我选了第二种，因为这个站点的部署本来就走 GitHub Actions：推送到 master 后构建，再用 peaceiris/actions-gh-pages 把 public/ 推到 GitHub Pages 仓库。在最后加一步调用 Cloudflare 的清缓存接口，看起来只是几行 curl。

第二个坑：清早了，旧页面会再缓存一天

最直接的写法是推送完成后马上清缓存。问题在于，actions-gh-pages 那一步结束，只代表新文件已经推到了 GitHub Pages 仓库。Pages 之后还要自己构建、发布，这个过程是异步的，我实测从推送完成到线上换成新版本大约需要一分钟。

如果在这一分钟里清缓存，会发生这样的事：

sequenceDiagram
    participant CI as GitHub Actions
    participant Pages as GitHub Pages
    participant CF as Cloudflare 边缘
    participant U as 访客
    CI->>Pages: 推送新版 public/
    Note over Pages: 异步发布，约 1 分钟
    CI->>CF: 立即清缓存
    U->>CF: 请求首页
    CF->>Pages: 缓存已空，回源
    Pages-->>CF: 返回的仍是旧页面
    Note over CF: 旧页面按边缘 TTL 再缓存 1 天

清缓存本身成功了，但下一个访客把旧页面重新带回边缘，并且一存就是一天。边缘 TTL 越长，清早了的后果越重；之前边缘不缓存 HTML 时，这个时序问题根本不存在。

所以清缓存之前必须确认 GitHub Pages 已经在提供新版本。我考虑过两种判断方式：

  • 查 GitHub Pages 的构建状态接口。需要对 Pages 仓库有读权限的 Token，而且构建显示完成后，GitHub 自己的 CDN 也可能还没更新。
  • 直接从线上读一个每次构建都会变的文件，读到新内容就说明源站已经更新。

第二种测的正是我们关心的结果，不依赖 GitHub 的内部状态，我用的就是它。整个部署流程如下：

每次构建生成一个编号

Hexo 会自动加载 scripts/ 下的脚本。加一个生成器，每次构建输出 /build-id.txt，内容是随机编号：

// scripts/build_id.js
var id = Date.now().toString(36) + Math.random().toString(36).slice(2, 8);

hexo.extend.generator.register('build_id', function () {
  return { path: 'build-id.txt', data: id + '\n' };
});

不用 Git 提交号，是因为手动部署未提交的改动时，提交号不变，等待会立刻错误地通过。

等线上编号对上，再清缓存

#!/usr/bin/env bash
# tools/purge-cloudflare.sh
set -euo pipefail
: "${CLOUDFLARE_API_TOKEN:?需要只含 Zone.Cache Purge 权限的 API Token}"
: "${CLOUDFLARE_ZONE_ID:?需要区域的 Zone ID}"

want=$(cat "$(dirname "$0")/../public/build-id.txt")
# 随机查询参数让请求穿过 Cloudflare 缓存，拿到源站当前版本
for i in $(seq 60); do
  got=$(curl -fsS "https://costalong.com/build-id.txt?nc=$RANDOM$RANDOM" || true)
  [ "$got" = "$want" ] && break
  if [ "$i" -eq 60 ]; then echo "GitHub Pages 10 分钟内仍未上线构建 $want（线上为 $got）" >&2; exit 1; fi
  sleep 10
done
echo "GitHub Pages 已上线构建 $want"

curl -fsS -X POST "https://api.cloudflare.com/client/v4/zones/$CLOUDFLARE_ZONE_ID/purge_cache" \
  -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" -H "Content-Type: application/json" \
  --data '{"purge_everything":true}' | grep -q '"success":true'
echo "Cloudflare 缓存已清除"

几个细节：

  • 查询参数 nc 每次都不同。Cloudflare 默认把查询字符串算进缓存键，每次请求都是新的键，必然回源，读到的是 GitHub Pages 当前提供的内容。
  • build-id.txt 扩展名是 txt，不在缓存规则的匹配范围内。
  • 最多等 10 分钟，超时就让任务失败。线上迟迟不更新本身就值得有人去看，比静默跳过清缓存好。
  • grep -q '"success":true' 检查接口返回，Token 无效或权限不够时这一步会失败，而不是假装成功。

接进 GitHub Actions

在部署步骤后面加一步：

# HTML 在 Cloudflare 边缘缓存 1 天，部署后要清掉才能立即生效
- name: Purge Cloudflare cache
  run: bash tools/purge-cloudflare.sh
  env:
    CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
    CLOUDFLARE_ZONE_ID: ${{ vars.CLOUDFLARE_ZONE_ID }}

Zone ID 在区域的概览页上能找到，不是机密，放在仓库变量里；Token 放 Secret。两个值具体存在哪、怎么填，见下一节。工作流原本就配了 concurrency 并取消进行中的旧运行，连续推送时旧任务可能在等待中被取消，没关系，最后一次运行会清缓存。

第一次跑通时，部署步骤用了 26 秒，清缓存这一步用了 1 分 12 秒，几乎都花在等待上：

前 7 次请求都是 404，因为线上还没有 build-id.txt 这个文件；之后的部署里，等待期间读到的会是上一次构建的编号。大约 70 秒后编号对上，随即清缓存成功。这 70 秒正是如果不等待就会出错的窗口。

Token 只给清缓存的权限

这个 Token 会长期放在 CI 里，权限越小越好。在「我的个人资料 → API 令牌 → 创建自定义令牌」里：

  • 权限：区域 → 清除缓存 → 清除
  • 区域资源：包括 → 特定区域 → 你的域名
  • 其他保持默认

泄露了最多能让人清你的缓存，改不了 DNS，也碰不到别的域名。创建后 Cloudflare 只显示一次 Token，可以先用 GET /client/v4/user/tokens/verify 确认状态是 active，再存进 GitHub Secret。

存进 GitHub

Secret 和变量都在部署工作流所在的仓库里配置（这里是放博客源码的仓库，不是 GitHub Pages 仓库）。打开仓库的 Settings，左侧栏找到 Secrets and variables → Actions：

在 Secrets 标签点 New repository secret，Name 填 CLOUDFLARE_API_TOKEN，Secret 粘贴刚才复制的 Token，点 Add secret。名称必须和工作流里 secrets.CLOUDFLARE_API_TOKEN 一致：

保存后 GitHub 只显示名称和更新时间，值再也看不到，只能覆盖。日志里引用它的地方会显示成 ***，前面的日志里能看到。

Zone ID 切到旁边的 Variables 标签，点 New repository variable，Name 填 CLOUDFLARE_ZONE_ID，值填 Zone ID。变量是明文的，列表里直接显示值（下图已打码），工作流里用 vars.CLOUDFLARE_ZONE_ID 读取：

习惯命令行的话，用 GitHub CLI 也行。gh secret set 不带 --body 时会提示输入，Token 不会留在 shell 历史里：

gh secret set CLOUDFLARE_API_TOKEN          # 回车后粘贴 Token
gh variable set CLOUDFLARE_ZONE_ID --body <你的 Zone ID>

效果

规则和流程都上线后，从同一台机器再测：

请求建立连接首字节
边缘未命中（MISS）约 0.31 秒约 0.62 秒
边缘命中（HIT）约 0.27 秒约 0.43 秒

扣掉建立连接的时间，服务器部分从约 0.31 秒降到约 0.16 秒，每个页面省下约 150 毫秒回源时间。Lighthouse 报告的 HTML 响应时间稳定在 160 到 190 毫秒，不再出现 500 毫秒以上的情况。

坦白说，Lighthouse 的性能分数几乎没变。它用模拟的慢速 4G 网络，分数主要被阻塞渲染的 CSS 和大图左右，150 毫秒的首字节差距在模拟里不明显。真正受益的是离源站远的访客，以及搜索引擎爬虫，HTML 是它们拿到的第一个资源。

偶尔还会看到 MISS，连接时间也和其他请求不同。这是请求落到了另一个 Cloudflare 节点，每个节点的缓存是各自的，冷门页面在每个节点上第一次被访问时都要回源一次。

还要记住的约束

手动部署不会自动清缓存。 CI 以外的部署，比如本地执行 hexo deploy，不会运行清缓存脚本，线上会保持旧页面一天。Token 存进 GitHub Secret 后读不出来，本地没有。最省事的做法是手动部署后，等线上 build-id.txt 变成新编号，再到 Cloudflare 后台的缓存配置页清除全部缓存（Purge Everything）。

如果经常手动部署，也可以在本地直接运行同一个脚本。按前面的步骤再建一个 Token，权限同样只给 Zone.Cache Purge，本地和 CI 各用一个，哪个泄露就单独撤销哪个。然后：

npm run build                   # 生成 public/，其中有本次的 build-id.txt
npm run deploy                  # hexo deploy 直接推送已有的 public/，不会重新生成
read -rs CLOUDFLARE_API_TOKEN   # 粘贴本地用的 Token，不回显，也不进 shell 历史
export CLOUDFLARE_API_TOKEN
export CLOUDFLARE_ZONE_ID=<你的 Zone ID>
bash tools/purge-cloudflare.sh

脚本拿 public/build-id.txt 和线上比对，所以部署和清缓存之间不要再执行 hexo generate 或 npm run build。重新生成会换一个新编号，线上永远等不到它，脚本会在 10 分钟后超时失败。

每次部署都会清掉全部缓存。 purge_everything 也会清掉一年期的 CSS/JS 和 7 天期的图片，部署后的第一批访客会让它们重新回源一次。对个人博客的部署频率来说可以忽略；如果站点很大、部署很频繁，可以改成按 URL 清除，只清 HTML、xml、json。

边缘 TTL 是兜底。 清缓存流程哪天坏了，最多一天后边缘缓存自然过期。如果站点不能接受一天的旧内容，就把边缘 TTL 设短一些，在命中率和兜底时间之间取舍。

要做的事，按顺序

  1. 用 curl -sI 看首页的 cf-cache-status，是 DYNAMIC 就说明 HTML 没有被缓存。
  2. 先把清缓存接进部署流程：生成构建编号，部署后等线上编号对上再清。用一次实际部署确认这一步成功。
  3. 再加缓存规则：匹配以 / 结尾的路径和 html/xml/json，边缘 TTL 设长，浏览器 TTL 显式选「接受源服务器 TTL」。
  4. 第二次请求确认 HIT，同时确认 cache-control 还是源站给的值。

第 2、3 步的顺序不能反。规则先上线而清缓存还没接通，之后每次部署都要等一天才生效。
