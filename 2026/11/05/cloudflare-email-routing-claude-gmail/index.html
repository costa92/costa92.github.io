用自己的域名接收 Claude 验证邮件：Cloudflare Email Routing 转发到 Gmail

 2026-11-05  linux Claude Cloudflare DNS Gmail
Claude Cloudflare DNS Gmail
linux Network
文章字数:   3.8k
阅读次数:  
   阅读模式

准备注册 Claude 时，我想用自己域名下的地址接收验证邮件，日常仍然只打开 Gmail。域名已经托管在 Cloudflare，博客也能正常访问，但这并不代表域名已经具备收信能力。

打开 Cloudflare 的邮件路由后台，最初看到的是：DNS 记录未配置，路由规则 0 条，目标地址 0 个。网站能访问，只说明网站的解析正常；发信服务器还不知道这个域名的邮件应该交给谁。

本文记录 2026 年 11 月 5 日的配置过程。已实际完成目标地址验证、邮件 DNS 配置和路由规则启用。Claude 的登录验证邮件最初到达 Gmail 的垃圾邮件目录，补上收信过滤器后，新邮件直接进入了收件箱。新账号的后续注册步骤不在此次完成范围内。下面统一使用 example.com 和 your-name@gmail.com 作为占位示例，操作时换成自己的地址。

配置截图取自本次实际后台，域名与邮箱已替换为上述示例，配置状态保持原样；DNS 图中的 DKIM 长公钥已明确省略。原理图为根据这次配置绘制的示意图。

先分清两个地址

这次要建立的关系是：Claude 把邮件发往域名地址，Cloudflare 按规则转发，最后由 Gmail 接收并分类。

原理示意：MX、转发规则和 Gmail 分类分别决定不同环节。点击图片可放大。

claude@example.com 是填写在注册页面上的地址。your-name@gmail.com 是实际收信的目标邮箱。前者的 claude 只是我选的名称，也可以换成 account 或其他容易辨认的名字。

这里配置的是转发：不需要为这个域名地址再维护一个独立收件箱，也没有给它设置邮箱密码。在 Gmail 收到邮件后，从 Gmail 直接回复，也不会因为配置了转发就自动获得以域名地址发信的能力。

Cloudflare 当前把相关功能放在 Email Service 下，其中 Email Routing 负责入站邮件路由，Email Sending 是另一套发信功能。本文只用前者。官方价格页列明 Email Routing 免费，但域名本身仍需续费。Cloudflare Email Service 价格说明

第一步：确认域名目前由谁收邮件

在添加记录前，先检查这个域名有没有接入其他邮箱服务。在 Cloudflare 的 DNS 记录列表中筛选 MX，也可以运行：

dig +short MX example.com
dig +short TXT example.com

MX 指定接收这个域名邮件的服务器。TXT 中可能包含以 v=spf1 开头的 SPF 记录，用来声明允许使用的发信来源。

这次查询没有返回 MX，后台也提示邮件 DNS 未配置，因此没有现有邮件服务需要迁移。如果你的域名已经使用 Google Workspace、Microsoft 365 或其他企业邮箱，就不能照着教程直接替换 MX。改变 MX 会改变这个域名邮件的投递去向，应先确定旧邮箱如何迁移，或者另行配置用于收信的子域名。

同样，不要看到教程里的 SPF 就额外添加第二条 v=spf1。同一个名称下有多条 SPF 会造成认证问题；已有配置需要结合现有发信服务合并。Cloudflare 邮件故障排查

第二步：添加真正接收邮件的 Gmail

当前后台的入口是：

计算 → 电子邮件服务 → 电子邮件路由
Compute → Email Service → Email Routing

进入自己的域名后，打开「目标地址」，填写 your-name@gmail.com，点击「添加地址」。它表示 Cloudflare 最后把邮件送到哪里。

这次添加后，列表直接显示「已验证」。这个观察不能套用到所有账户：如果你的地址显示待验证，需要打开 Gmail，找到 Cloudflare 的验证邮件，点击其中的验证入口，再回后台核对状态。官方文档明确说明，目标地址没有验证时，指向它的规则不会启用。目标地址与路由规则说明

目标地址列表：这里核对的是最终接收邮件的 Gmail。截图已脱敏。

注意这封邮件验证的是“你控制这个 Gmail”，还没有检验“外部邮件能经过域名转发到 Gmail”。因为此时域名的邮件记录和地址规则可能还没建好。

第三步：让邮件先到达 Cloudflare

在邮件路由的「设置」中找到 DNS 记录区域。我的后台列出了 5 条缺失记录：3 条 MX、1 条 SPF TXT、1 条 DKIM TXT。点击「添加缺失记录」后，由 Cloudflare 补齐。

记录这次配置中的作用应怎样填写
MX把域名的入站邮件交给 Cloudflare使用后台为当前域名列出的服务器和优先级
SPF TXT为转发邮件提供相关授权声明没有旧 SPF 时按后台要求添加；有旧配置先核对并合并
DKIM TXT为转发邮件提供签名验证所需的公钥使用当前域名生成的选择器和完整公钥

这次 MX 的服务器是 route1.mx.cloudflare.net、route2.mx.cloudflare.net、route3.mx.cloudflare.net，但优先级不是网上教程常见的固定顺序。实际查询结果如下，数字是本次域名的值，不是读者需要照抄的模板：

17 route3.mx.cloudflare.net.
21 route2.mx.cloudflare.net.
98 route1.mx.cloudflare.net.

SPF 为：

v=spf1 include:_spf.mx.cloudflare.net ~all

DKIM 的名称和长公钥直接以后台为准。不要复制另一篇文章里其他域名的公钥，也不要把带省略号的示例当成完整记录。Cloudflare 的域名配置文档说明了这些记录的职责，以及自动配置方式。邮件域名与 DNS 配置

添加后，后台的 MX 和 DKIM 显示「已锁定」，SPF 显示「未锁定」。这里的锁定描述记录是否受服务管理；「未锁定」不等于「缺失」。本次进一步查询公共解析器，确认 MX 和 SPF 已经可以解析：

dig @1.1.1.1 +short MX example.com
dig @1.1.1.1 +short TXT example.com

实际 DNS 配置：三条 MX 的优先级来自本次后台；DKIM 公钥省略部分不能照抄。

本机默认解析器一度还没有返回新记录，而指定公共解析器已经能查到。遇到这种差异，先考虑 DNS 缓存，不要反复删除再添加记录。官方说明 DNS 更新通常需要一定传播时间；检查时应同时看后台状态和查询结果。Email Routing 配置流程

第四步：给 Claude 建一条明确的规则

DNS 解决的是“这个域名的邮件交给 Cloudflare”，规则才决定“交给 Cloudflare 以后转发到哪里”。

打开「路由规则」，点击「创建路由规则」，按下面填写：

表单字段示例值
电子邮件匹配模式claude
域名example.com
操作发送到电子邮件
目标已验证的 your-name@gmail.com

保存后，列表应出现 claude@example.com，目标是 Gmail，状态为「活跃」。本次已经在后台确认了这三个字段。

路由规则列表：专用地址活跃，全收规则保持禁用。截图已脱敏。

我保留了「全收」规则的禁用状态。全收也叫 Catch-all，会接住其他未匹配地址的来信；目前只需要一个注册地址，用明确规则更容易发现输入错误，也避免无意接收大量随意拼写地址的邮件。需要多个服务地址时，再分别建规则即可。

这里很容易出现一个填反的错误：把 Gmail 当成匹配地址，把域名邮箱当成目标。记住方向是“域名地址收到邮件，再转给 Gmail”，就不容易混淆。

第五步：验证收信，再继续注册 Claude

配置保存成功后，还缺少一次真正的收信验证。可以先用另一个邮箱给 claude@example.com 发一封普通测试邮件，主题带上便于识别的时间，再同时检查 Gmail 和 Cloudflare 的「活动日志」。

当前后台活动日志提示，指标和日志可能需要最多 2 分钟显示。不要在刚发信后看到空列表就立即判定转发失败；等日志出现后，结合收件人、时间和结果定位这一封邮件。Cloudflare 活动日志说明

用于 Claude 注册时，打开 Claude，输入域名邮箱，选择 Continue with email。然后去 Gmail 查看对应邮件，按邮件中的链接或验证码继续页面流程。Claude 的帮助文档也区分了邮箱入口与 Google 登录入口。Claude 官方注册入口说明

如果你的目的是用域名邮箱作为账号地址，就在邮箱输入框里填域名地址。Gmail 负责接收转发邮件，并不会把域名邮箱变成 Google 账号；点击「Continue with Google」是另一条登录路径。

实际检查时，新会话在提交邮箱后先出现浏览器安全验证页面，等待检查通过后，Claude 提示登录链接已发送到域名地址。随后，Cloudflare 活动日志出现了这封邮件，结果为「已转发」。

但 Gmail 收件箱里并没有它。用 in:anywhere 加收件地址搜索，才发现邮件进了垃圾邮件目录，主题是 Your secure link to Claude is here，附带发送时间。至此才真正确认：发信方已发出、Cloudflare 已转发、目标 Gmail 已收到。只盯着收件箱，会把一次成功投递误判成转发失败。

如果你也遇到这种情况，先核对邮件确实来自自己刚发起的登录操作，再在 Gmail 中将它标记为「非垃圾邮件」。这次观察只能说明该邮件被分到了垃圾邮件，不能仅凭这一封就断言具体的过滤原因。邮件中的登录链接有有效期，过期后回 Claude 页面重新发起，不要反复尝试旧链接。

只移出这一封还不够，给后续邮件设置规则

把当前邮件移回收件箱，只能直接证明这封邮件的位置已改变。若要为后续登录邮件明确设置处理方式，可以在 Gmail 建一个范围较小的过滤器。

点击搜索框右侧的「显示搜索选项」，填写：

条件示例值
发件人@mail.anthropic.com
收件人claude@example.com

这是根据本次实际来信的发件地址设置的：它的域名是 mail.anthropic.com，no-reply- 后还带有一段字符，所以没有把整串地址固定在规则中。设置前先搜索，确认结果确实是预期的 Claude 邮件；如果将来发信域改变，需要重新核对。

点击「创建过滤器」，勾选 不要将其发送至“垃圾邮件”，可同时应用于匹配的已有会话，再保存。不要勾选「跳过收件箱」或「删除」。两个条件同时使用，处理范围比仅按域名收件地址放行所有邮件更小。Google 官方说明了过滤器的创建、修改和删除入口。Gmail 过滤器设置

本次保存时，Google 还要求验证“是本人正在创建新的过滤器”，通过已登录手机确认。遇到这种提示，点击保存不代表设置已经完成；验证后应在「设置 → 过滤器和屏蔽的地址」中看到匹配条件和“不发送至垃圾邮件”的操作，再请求一封新的登录邮件检验。

已保存的 Gmail 过滤器：核对条件与动作，不能只看创建时的勾选状态。截图已脱敏。

完成验证后，我在设置页确认了这条规则，再重新请求登录邮件。14:50 发出的新邮件直接带着「收件箱」标签出现，没有手动移动这封新邮件。此前进入垃圾邮件的测试邮件则单独移回收件箱，避免把人工移动的结果当成规则生效的证明。

在过滤器完成验证前的复测中，有一封新邮件仍被分到了垃圾邮件。打开邮件，Gmail 给出的原因是「此邮件与我们过去识别的垃圾邮件很相似」。在「更多邮件选项 → 显示原始邮件」中检查，Google 接收端的 SPF、DKIM、ARC 均为 pass，Cloudflare 接收端也记录了原始发件域的 DMARC 通过。认证通过与进入收件箱是两回事，这些结果不足以确定 Gmail 的具体评分原因，但没有显示需要通过补 DNS 来修复的认证失败。

这是当前 Gmail 账户内的收信规则，不代表修复了发件域信誉，也不会改变其他人的 Gmail 如何分类这些邮件。排查时先检查实际邮件的认证结果，不要因为进入垃圾邮件就盲目添加或重复修改域名 DNS。

即使收到验证邮件，也还要继续完成 Claude 页面要求的注册步骤。官方手机号验证说明要求受支持地区的手机号，并列出了号码限制；自定义域名邮箱不会替代这些要求。Claude 手机号验证说明

邮件没来，按它经过的顺序排查

出现“收不到验证码”时，先判断邮件走到了哪一步，再改对应配置：

观察到的情况优先检查
Claude 仍停留在安全检查或提交报错页页面是否真的完成了邮件请求
公共 DNS 查不到 Cloudflare MX记录是否添加到了正确域名，以及 DNS 缓存是否更新
目标邮箱显示待验证完成 Cloudflare 发给目标邮箱的验证
MX 正常，但规则没匹配注册地址拼写、域名、规则状态和操作类型
Cloudflare 日志没有这封邮件时间范围、日志延迟，以及发件方是否实际发出
日志已有转发结果，Gmail 收件箱没看到查看垃圾邮件、所有邮件及过滤器；用收件地址和时间搜索
Gmail 收到邮件，Claude 仍要求后续验证按注册页面继续，不再把它当成 DNS 问题

例如，可以在 Gmail 搜索：

in:anywhere to:claude@example.com newer_than:1d

不要把“目标 Gmail 已验证”“规则活跃”“邮件送达”“账号注册完成”当成同一个状态。前两项可以在 Cloudflare 检查；第三项需要真实邮件；最后一项只能由 Claude 的注册结果确认。

后续使用这个地址登录时，域名续费、Cloudflare 规则和目标 Gmail 都要继续可用。换 Gmail 前先验证新目标，再修改转发规则并重新试收；让注册时用过的地址在几个月后仍能收到登录邮件，才是这套配置真正需要维持的结果。
