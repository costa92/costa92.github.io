Go AI Agent 框架实战：用 GoAgent 实现工具调用、人工审批与中断恢复

自动化 AI Agent Go
AI golang
文章字数:   5.3k
阅读次数:

假设要给现有的 Go 服务加一个退款助手。用户说“帮我查一下订单，看看能不能退款”，助手需要查询订单、读取退款规则，必要时请人审批，再执行操作并返回结果。

调用一次模型 API，只解决了其中的语言理解和回答生成。接下来还有不少程序要写：模型选择工具后怎样执行，结果怎样交回模型，审批等待怎样保存，服务重启后怎样接着跑，以及一次失败重试会不会重复退款。

GoAgent 为这些步骤提供了可嵌入 Go 服务的执行内核。模型调用、工具和业务流程可以在服务里组合起来，订单查询、权限检查和数据库访问则继续使用已有的 Go 代码。

GitHub 项目地址：github.com/kart-io/goagent。

以下示例使用 v0.53.0，实现说明依据 2026 年 11 月 15 日的源码。退款流程是用来解释设计的假设案例，代码演示的是订单查询和文本审批。

GoAgent 主要解决哪些问题

退款助手接上模型后，还需要处理下面这些执行问题：

实际遇到的问题GoAgent 提供的机制业务仍需完成的部分
模型请求调用工具，应用要持续接收、执行并反馈结果原生工具循环、函数工具、统一 Runnable 入口实现查询或操作函数，校验参数和权限
退款流程必须经过审批，服务还可能重启类型化图、持久检查点、人工输入与恢复提供稳定运行标识、存储、审批身份与流程版本
调用已经发出，崩溃后却不知道是否成功操作日志、完成结果回放、中断结果核对接口外部系统幂等、查询与补偿策略
子 Agent 和重试各算各的，整项任务不断消耗资源共享根预算、工具准入、期限与并发限制配置预算存储、Token 估计和业务额度
最终答案出错，却看不清执行到了哪一步会话日志、步骤事件、OpenTelemetry 与运行诊断保存业务回执，接入观测后端并定义告警

下面先接订单查询工具，再加入审批和持久恢复。接上工具以后，还需要检查模型是否读对了订单数据、是否按退款规则作答。

从一次模型调用到工具循环（Tool Calling）

退款助手首先要查订单。模型本身并不知道订单是否存在，需要宿主程序提供一个查询工具。

工具向模型声明名称、用途和参数结构。模型返回工具调用后，GoAgent 执行对应的 Go 函数，把结果放回对话，再请求模型继续。下一步可能是调用另一个工具，也可能是给用户最终答复。

图里的 Dispatcher 校验工具调用，并执行宿主配置的授权检查；预算和日志也由宿主接入。下面先给出直接注册函数工具的写法，接到业务服务时再补上这些组件。

在这个订单查询示例里，模型发起查询，工具返回订单事实。参数来自模型，进入业务服务前仍要检查参数和调用者权限。

GoAgent 用 builder.NewSimpleBuilder 装配 Agent，通过 agent.AsRunnable() 调用：Invoke 等待完整结果，Stream 接收过程事件。完整接入步骤见 Quickstart。

先接一个只读的订单查询工具

先让助手完成“查订单并解释状态”，便于观察模型什么时候调用工具。订单数据先写在内存里，后面再替换成真实查询。

当前项目要求 Go 1.27 或更高版本。新建目录后安装依赖：

mkdir goagent-demo
cd goagent-demo
go mod init example.com/goagent-demo
go get github.com/kart-io/goagent@v0.53.0

export OPENAI_API_KEY='替换为你的 API Key'
export OPENAI_MODEL='替换为支持工具调用的模型 ID'

保存为 main.go：

package main

import (
	"context"
	"fmt"
	"log"
	"strings"
	"time"

	"github.com/kart-io/goagent/builder"
	"github.com/kart-io/goagent/llm/providers"
	"github.com/kart-io/goagent/tools"
)

func main() {
	client, err := providers.NewOpenAIWithOptions()
	if err != nil {
		log.Fatal(err)
	}

	lookup := tools.NewFunctionTool(
		"lookup_order",
		"按订单号查询订单状态；返回的是演示数据",
		`{"type":"object","properties":{"order_id":{"type":"string"}},"required":["order_id"],"additionalProperties":false}`,
		func(ctx context.Context, args map[string]interface{}) (interface{}, error) {
			if err := ctx.Err(); err != nil {
				return nil, err
			}
			id, ok := args["order_id"].(string)
			if !ok || strings.TrimSpace(id) == "" {
				return nil, fmt.Errorf("订单号不能为空")
			}
			if id != "demo-1001" {
				return nil, fmt.Errorf("演示订单不存在")
			}
			return map[string]interface{}{
				"order_id":     id,
				"status":       "已支付，未发货",
				"amount_cents": 9900,
				"currency":     "CNY",
			}, nil
		},
	)

	agent, err := builder.NewSimpleBuilder(client).
		WithSystemPrompt("你是订单查询助手。订单事实必须来自工具；不能办理退款，也不能承诺退款结果。").
		WithTools(lookup).
		WithMaxIterations(6).
		WithTimeout(30 * time.Second).
		Build()
	if err != nil {
		log.Fatal(err)
	}

	out, err := agent.AsRunnable().Invoke(
		context.Background(), "查询订单 demo-1001 的状态和金额。",
	)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println(out.Result)
}
go run .

运行时会请求你配置的模型。这个工具只认识 demo-1001，返回“已支付，未发货”；amount_cents 的单位是分，9900 对应人民币 99 元。可以检查模型是否调用了工具，以及回答中的订单状态和金额是否与返回值一致。

WithMaxIterations(6) 包含最终回答所需的模型请求，查一次工具后再回答通常已经需要两次请求。WithTimeout 限制执行时间，实际数据库和 HTTP 调用也需要传递并响应 context；取消无法强行停止忽略上下文的第三方代码。

接入真实订单服务时，把函数体换成已有的查询方法，并从可信的请求上下文取得用户身份和租户范围。不能让模型传一个任意 user_id，就据此读取那个用户的订单。

内置 Provider 包括 OpenAI、DeepSeek、Gemini 和 Anthropic，也有面向 Kimi、SiliconFlow、Ollama 的 OpenAI 兼容预设。兼容端点最终能否完成工具调用，仍取决于服务和模型的支持情况。使用上面的 OpenAI 客户端时，也可以通过 OPENAI_BASE_URL 指向兼容服务，并配套设置它接受的模型 ID。

退款有固定步骤时，把流程写成图

查到订单后，用户可能接着要求退款。核对订单、生成申请、等待审批、执行退款和记录回执有固定的业务顺序，其中的审批步骤需要由程序保证执行。

这时可以用 workflow.Graph[S] 把流程写出来。S 保存订单事实、审查决定和回执，节点接收并更新状态，边决定先后顺序。审查通过就进入退款节点，拒绝则记录原因。状态字段由哪个节点读取、由哪个节点更新，都能沿着 Go 代码查看。

需要理解用户文字或解释结果的节点仍可调用 Agent；反过来，子 Agent 或持久图也可以包装成工具。模型选择下一步查什么，业务代码控制退款要经过哪些步骤，接法见原生编排指南。

图还支持并行汇合和有界循环。异构节点用 Adapt 转换输入输出，并行分支则要提供 Clone 和 Merge，明确数据怎样复制与合并；普通指针、map 和 slice 不会自动获得深复制或事务隔离。接口细节见工作流文档。

人明天才审批，服务不用一直等着（Human-in-the-loop）

退款申请送审后，审批人可能几个小时都没空处理。原 HTTP 请求需要先返回，进度也得离开内存保存下来，否则服务一重启就不知道该从哪里继续。

用 CompileDurable 编译图，并在 ApprovalNodes 指定人工审查节点，运行就会在该节点前保存检查点、返回等待。宿主为这项申请提供稳定的 RunID。审批到来后，以同一 RunID 和当前等待键调用 Resume，程序便能读回保存的状态，校验人工输入后继续。

等待键用于定位本次暂停，审批人是谁、有没有权限仍由宿主检查。接入时，用 WithResumeHandler 解析和校验输入，再在 WithBeforeApprove 中复核订单事实、权限或期限。人工修改与放行标记保存成功后，程序才执行暂停的节点。接入方法见人工介入指南。

虚线连接的是等待与恢复两次调用，通知审批人和触发恢复都由宿主负责。图中的“是否有效”检查输入和权限；审批人选择拒绝退款也是合法决定，程序保存后会走拒绝分支。

可以先跑仓库已有的离线示例，观察跨进程恢复。它审查一段文本，无需 API Key：

git clone https://github.com/kart-io/goagent.git
cd goagent
git checkout v0.53.0

GOAGENT_REVIEW_DIR=$(mktemp -d)
go run ./examples/human-in-the-loop \
  -dir "$GOAGENT_REVIEW_DIR" -text '待审查的退款说明'

第一次运行返回 Waiting: true、Done: false 和一个 Key，随后进程退出。用同一目录可以读取状态，再把输出的 Key 填入恢复命令：

go run ./examples/human-in-the-loop \
  -dir "$GOAGENT_REVIEW_DIR" -action status

go run ./examples/human-in-the-loop \
  -dir "$GOAGENT_REVIEW_DIR" -action resume \
  -key '替换为输出中的 Key' -reviewer demo-reviewer \
  -decision approve -text '人工修订后的退款说明'

这三条命令在本地分别启动了三个 Go 进程。运行 status 时，最初的进程已经退出，但读到的仍是原来的 Key 和等待状态；恢复命令返回 Done: true，业务状态变为 accepted，文本也换成了“人工修订后的退款说明”。等待期间不需要保留原进程。

示例用 demo-reviewer 作为审批身份规则，生产入口要接入自己的登录和授权系统。把文本审查换成退款申请后，还要在放行前复核订单是否发生变化、审批是否过期。

检查点保存的是业务状态和执行位置，不是 Go 调用栈。它还绑定图的结构和流程版本；节点行为或状态结构改变时，需要提升流程版本，并检查原有检查点能否继续使用。

如果要在节点内部等人补充信息，可以使用 durable.AwaitInput。续跑会重新进入相应执行逻辑，函数此前做过的操作仍可能重做。

能恢复执行，还要解决重复退款（Durable Execution）

再考虑一个故障：支付系统已经受理退款，当前进程却在保存本地结果前退出。重启后，单看本地检查点，可能无法判断远端是否成功。

继续对话要读回历史消息，处理这次故障还得知道支付调用是否已经生效。GoAgent 用操作记录保存调用结果，恢复时回放已完成的记录，也提供核对中断结果的机制。记录按宿主提供的运行标识和派生的子操作标识关联，处理规则见持久操作契约。

这仍然需要按至少一次执行来设计。Dispatcher 默认允许重跑中断的工具，业务必须提供幂等或结果核对策略，不能把“恢复成功”理解为“支付只发生一次”。

退款接口应使用稳定的业务幂等键；如果结果未知，就用相同标识查询或重试，按支付方的协议对账。workflow.DurableKey(ctx) 可以提供执行位置相关的键，但怎样映射到支付方的业务请求，仍要由接入方决定。

项目中的 workflow/refund 提供了申请去重、审批事实复核、累计退款额度检查等可复用保护。不过它实现的是本地事务效果账本，演示回执也不是支付机构回单。接入真实支付时，还需要支付方的幂等、查询和补偿协议。

这也影响最终回答的生成。只有保存了可信回执，才能告诉用户“已完成退款”；模型说出这句话本身，不能作为业务成功的证据。

把整项退款任务的消耗记下来

前面的 WithMaxIterations 限制了一个 Agent 的请求次数。如果它把审查交给子 Agent，或者失败后再次尝试，整项退款任务还会发生更多调用。只给每个 Agent 单独设限，容易漏掉这些累计消耗。

core/budget 把模型请求次数、工具调用次数和期限绑定到根任务，再随上下文传给子调用。需要跨进程恢复时，预算控制器也要持久化，续跑才能沿用原账本。工具计数以经过 Dispatcher 的实际调用为准，绕过它的宿主函数不会自动计入。

Token 准入上限依赖宿主提供估计函数，限制的是累计预留量，实际账单仍要依据真实用量和费率。取消或崩溃不会退还已经预留的额度，缺少 usage 证据的用量保留为未知。页面收到的 usage 事件也是累计快照，不能把每个事件重复相加。执行治理指南说明了计数、重试和未知用量的处理规则。

排查时，core/observe 提供只读执行事件，observability 提供 OpenTelemetry 集成。业务回执、检查点和持久账本保存执行事实，追踪与指标帮助定位在哪一轮、哪个工具或哪个节点耗时、出错。异步观测队列可能丢事件，不能拿它替代持久审计。

GoAgent 的设计思想

业务规则留在宿主服务里

退款申请能否通过，最终取决于订单事实、权限和退款规则。GoAgent 的工具循环与工作流控制执行顺序，这些业务判断则继续调用宿主已有的代码。execution.Scope 将宿主提供的运行标识、会话、日志、预算和观察者接到请求上下文中，资源也由宿主管理。装配方法见宿主接入指南。

计划模式、编码工具和具体业务流程都放在上层，由它们调用内核，内核不反向依赖这些模块。退款助手怎样校验订单归属、生成支付幂等键、通知审批人和触发续跑，仍按宿主的规则接入。包之间的关系见架构概述。

换一种调用方式，仍然执行同一套逻辑

后台任务等完整结果，聊天页面需要边执行边显示，图节点还可能把 Agent 作为一步来调用。GoAgent 用同一执行源支撑 Invoke、Stream、批处理和组合，让这些入口沿用相同的工具、回调与错误处理。缺失或重复终态、迟到错误和取消都按同一执行契约处理。

页面可以转发 Stream 的文本增量，但模型可能先说一句说明，再调用工具。显示出文字不表示退款已经完成；持久图的一次调用结束，也可能只是进入审批等待，业务是否完成要检查快照中的 Done。工作流的步骤流展示节点过程，Pipe 会等上游最终输出再调用下游，不做跨节点的逐 Token 转换。

与 LangGraph、Eino、Google ADK 相比，优势在哪里

几种框架都提供工具调用、编排和人工介入。放到退款助手里，可以比较订单方法怎样接入、审批状态怎样保存，以及需要额外维护哪些组件。下表依据 2026 年 11 月 15 日可查的官方文档整理。

框架官方提供的相关能力与 GoAgent 比较时的选型重点
GoAgentGo 原生工具循环、类型化图、持久操作记录、审批、根预算和 OTel 接口适合希望在现有 Go 服务内组合执行、恢复和治理的场景；存储、身份、业务幂等与调度仍需接入
LangGraph状态图、持久执行、流式输出、人工介入，可结合 LangChain 和 LangSmith已使用 Python 或 JavaScript 技术栈时有直接的衔接路径；Go 服务若选择独立运行这些 Agent，需要另外设计跨进程调用和上下文传播
EinoGo 组件抽象、Chain/Graph/Workflow、ADK、流处理与开发工具；也支持检查点和中断恢复需要通用组件组合和流式编排时可以考虑；与 GoAgent 对比时，可重点试接预算、审批和恢复接口
Google ADK for GoGo Agent、工具、多 Agent 工作流与运行组件；当前 Go 2.0 文档也包含图工作流和人工确认已采用 ADK 的 Runner、会话和 Gemini 接入方式时值得沿用；选择 GoAgent 时，比较其执行键、操作账本、根预算能否更直接对接自己的业务

复用已有 Go 代码，接入执行治理

如果现有订单逻辑、权限检查和数据库访问都在 Go 中，GoAgent 可以直接调用这些函数，继续传递 context、错误和业务状态。相较于另开 Python 或 JavaScript Agent 服务的方案，这能省去一层 RPC 协议、部署单元和跨服务身份传递。Eino 与 ADK Go 也有同语言集成的便利。

GoAgent 是否更合适，还要看它的审批、操作记录和根预算怎样接上自己的存储与授权代码。可以用同一笔退款申请做一个小接入，比较需要维护多少适配代码。

小图与工具循环的框架开销

仓库保留了一份 2026 年 10 月 27 日的框架性能对测。它使用 Apple M4 Pro、Go 1.27.2、GOMAXPROCS=4，对比当时的 GoAgent 与 Eino v0.9.22；模型响应和工具数据在本地即时产生，排除了构建与编译时间，没有启用持久化。

下表单位是微秒，P50 为五个独立进程各自 P50 的中位数：

在这套负载里，GoAgent 的小图和工具循环有较低的框架执行开销；64 段流的总完成时间则是 Eino 更低。GoAgent 的首段到达 P50 为 10.333 微秒，Eino 为 21.979 微秒，说明首段响应与整体完成也需要分开评价。

表中数据对应上述测试日期和配置，不能直接换算成当前版本或真实退款业务的加速倍数。测试不包含网络推理、数据库、持久化和业务工具耗时，也没有逐项验证两个框架入口的功能是否等价；ADK Go 未参与测量。接入自己的业务后，还需要打开实际使用的检查点、预算和观测，再测一次。

接入时怎样选择组件

前面的查询助手只需要 builder、llm/providers 和 tools。接到真实订单服务时，先补上可信身份与工具授权，用 Dispatcher 和 Pipeline 控制工具准入；退款顺序和审批再放进持久图。若业务只有一次文本生成，直接用模型 SDK 就能完成。

要保留多轮历史，可以接入 core/session 的会话日志。后面如果遇到上下文过长，再按来源处理：Compaction 压缩较早消息，Offload 把长工具结果换成引用、需要时分页读取；RAG 用于检索外部资料。外部 MCP 工具可以通过 mcp 接入，这些能力都可以按实际需要逐项增加。

扩展也分在几个相关仓库中：goagent-contrib 放检索器、文档加载和 Postgres 持久存储等集成；goagent-harness 放计划、技能装配、上下文压缩和编码工具等组件；goagent-examples 提供业务案例。只想给服务加一个查询助手，可以先保留很小的装配范围。

同一个 ConfigurableAgent 实例会串行执行会话轮次。要让不同会话并发运行，应分别建立实例，并限制它们共用的模型、存储和工具资源。

管理服务当前支持单个活动 Worker 并发执行不同会话。跨主机分片和心跳超时后的自动接管需要另外接入调度方案，单独换成共享 Postgres 存储还不够。使用长期记忆时，也要配置命名空间、存储以及抽取或维护任务。部署前可以对照运行能力文档检查自己的配置。

开放真实退款前，应在自己的存储和支付接口上测试重复提交、进程退出和远端结果未知，检查回执、检查点与已用额度能否对上。文中的离线审批示例可以先验证恢复接法，支付效果还要通过支付方的幂等和查询协议核对。
