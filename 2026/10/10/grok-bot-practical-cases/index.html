Grok Bot 实用案例：6 个可改写的任务模板与审批边界

前两篇记录了 Grok Bot 的公开文档整理，以及 Skill 复用与跨 Bot 调用测试。接下来把适合尝试的工作整理成案例模板。

下面 6 个案例中，案例二到六根据官方 Use cases、文件交付和审批文档改写；官方列出的 8 个角色里没有整理更新日志这一类，案例一是补充的。我们用 Grok Bot 做了一次安全演示：只读取官方 Use cases 页面；其余五项使用本次请求中明确标注的虚构数据。这验证的是任务模板、基础计算和边界表达，不是报销、监控、浏览器、日历或广告平台连接器的实测。

一次任务演示六个案例

我们要求 Bot 生成一份 Markdown 笔记，并明确限制为只读一个官方网页、其余使用虚构输入，不接入连接器、不读本地文件、不发送或发布内容，也不创建任务或 Routine。下面两张图分别是实际输入和客户端返回的摘要与文件卡片；数据都是演示数据，不能当作业务结论。

Bot 交付了 grok-bot-case-examples-demo.md 和一段摘要。各案例的计算结果放在下文对应小节；缺少人数、会议日期等输入时，Bot 标为待确认或未提供，没有自行推断。有一处错误值得注意：摘要最后说 Use cases 页面没写更新日期，但页脚标注了 Last updated: August 11, 2026，Bot 漏读了。和上一篇第一次读取没拿到日期一样，页面日期这类信息仍要人工复核。

先把任务写成可检查的交付

交给 Bot 的任务，先说明四件事：从哪里取资料、希望它做什么、要交付什么、哪些操作必须停下。文件任务还要说清每个附件的用途。官方建议为重要工作分别列出事实、推断、已完成操作、等待批准事项和未解决问题。Files and results介绍附件与结果卡片，Approvals, security, and privacy说明审批与敏感操作边界。

案例一：整理项目更新与迁移影响

适合：每周发布频繁、需要快速判断哪些变更影响团队的项目。只给官方更新日志或发布说明链接，能从公开资料开始，不必先接入私有系统。本次演示用官方 Use cases 页面代替更新日志，Bot 整理出页面列出的 8 个工作角色及建议的渐进启用顺序。这只验证了“只读一个公开官方页面并按要求汇总”这一部分，更新日志与迁移分析的模板没有实测。

只阅读以下官方发布说明：[官方 URL]
整理最近一个版本周期的新增功能、破坏性变更、弃用项目和迁移要求。
每项结论附原文链接；没有明确写出的影响请标为待确认。
输出一页 Markdown：先给摘要，再列版本、变更、受影响模块、建议检查项。
不要根据其他网站补写版本信息，不要修改代码或创建任务。
如果来源无法访问或日期不清楚，说明问题后停止推断。

验收时看链接是否落到具体条目、版本日期是否读对，以及“建议检查”有没有被写成官方已要求的操作。稳定后再保存为 Skill；自动检查更新前，先定义发布周期与失败时的报告方式。

案例二：核对费用与报销政策

适合：把收据和费用表与公司政策逐项比对。它需要你有权处理的文件和政策版本；涉及员工或供应商信息时，先检查组织允许使用的资料与连接器。本次演示的虚构输入是：政策规定团队餐每人上限 USD 50、酒店 USD 200/晚；E01 团队餐申报 64、收据 64，E02 出租车 28/28，E03 酒店 180/180。Bot 算出申报与收据合计都是 USD 272；E01 是否超出每人 USD 50 的上限取决于就餐人数，因人数缺失只标待确认，没有贸然判定违规。

附件说明：费用表是本周申报，收据是原始凭证，政策文件是本次核对依据。
逐行核对金额、币种、日期、分类与收据；只按附件中的政策判断例外。
交付：对账表（申报行、凭证金额、政策条款、差异、证据链接）和简短摘要。
总金额须能回算到原表；找不到凭证或条款时标注“待人工核实”。
不要修改原件、批准报销、联系申报人或发送邮件。

抽查几条记录，确认总数能回算、政策条款链接正确、金额与币种没有混淆。若 Bot 只能给出结论却没有证据，不应直接把对账结果当作审批依据。官方案例也建议在每个例外旁附政策条款，并让汇总数能够回到来源核对。文件附件文档列出了常见可读文件种类与桌面附件限制；上传前确认单个文件符合当前上限。

案例三：分析发布后的性能回归

适合：新版本发布后，某个接口或页面变慢，需要先整理证据再决定是否升级处理。此任务需要授权的仪表板、trace 或分析系统；没有这些来源时，只能分析用户提供的材料。本次演示的虚构输入是发布前后各 10,000 次请求：p50 从 210 到 230 毫秒，p95 从 480 到 730 毫秒，错误率从 0.4% 到 0.9%。Bot 算出 p50 增加约 9.5%、p95 增加约 52.1%、错误率增加 0.5 个百分点，并说明这些数字不能说明根因。

调查 [功能/接口] 从 [发布时间] 起的延迟变化。
只读查看这些已授权来源：[仪表板、trace、性能报告链接]。
列出对比时间窗、样本量、变化幅度、可复现的热点与直接证据链接。
把观测到的事实和推测原因分开，并标注置信度与缺少的数据。
交付一页排查摘要及必要截图。
不要改告警、扩缩容、生产配置或代码；需要操作时先给出方案并等待批准。

重点检查 Bot 有没有拿不同时间窗作比较、是否把相关性直接说成原因，以及截图能否回到原仪表板。官方 Product Performance 案例同样强调截图、直接链接、事实与假设分开，并明确不改告警和生产设置，Routine 只用于周期性的健康报告。审批指南建议针对具体操作写窄范围规则，避免“允许浏览器做任何事”一类宽泛规则。

案例四：在测试环境复现 Bug

适合：把模糊的错误报告整理成工程师可复现的步骤。提前准备干净的测试账号、测试环境地址和不含真实客户资料的样例。

请在 [staging URL] 使用新建的测试账号复现以下问题：[Bug 报告链接或文本]。
记录前置状态、逐步操作、预期与实际结果、浏览器和系统版本。
若失败，附页面截图、相关控制台或网络现象，以及无法继续的步骤。
交付最小复现说明；不要尝试生产环境，不要使用客户数据，不要改代码。
如果页面要求密码或验证码，暂停并请求我接管，不要让我在聊天里发送凭据。

上图只是任务输入（虚构问题：在 Linux 上的 Chromium 中点击“保存草稿”后按钮转圈，刷新后内容消失），本次没有访问 staging 或启动浏览器。复现包应让其他人从同一个测试状态得到相同现象。账号失效、环境不可达和问题未出现，都要记录成结果，而不是继续猜原因。官方 Bug Reproduction 案例要求用 staging、新测试账号，并通过安全接管提供测试凭据；敏感输入不要放进普通聊天消息。人工接管步骤说明用户如何亲自完成登录等步骤。

案例五：汇总日程与会议行动项

适合：上班前把已授权日历和会议纪要整理成待办简报。要先确认连接器权限和时间范围，并避免把“Bot 能访问”误当作“应该纳入”。本次演示的虚构纪要是：决定由林检查付款接口延迟，陈在周四前准备对账方案；纪要没写会议日期，也没指定林的截止时间。Bot 把这两项标为“未提供”，没有自行推测。

整理过去 24 小时 [已批准的日历与会议纪要] 中与 [本周目标] 相关的内容。
每项列出来源链接、时间、决定、负责人、截止时间和待我确认的问题。
没有明确负责人或日期时写“未指定”，不要自行补全。
只返回简报和待办草稿，不创建、改期或取消会议，不发送消息。
来源不可访问时列出缺失来源，不用旧记录代替。

检查时重点看会议时间与时区、行动项的原始表述，以及是否把讨论意见误记成最终决定。若之后要让 Bot 创建任务或修改日历，应把具体操作、对象和审批要求单独写入新请求。官方 Chief of Staff 案例建议每条摘要都给出来源、重要性、下一步和需要用户决定的事项，并避免自动修改会议或发送消息。

案例六：分析广告投放并准备预算建议

适合：先汇总各广告系列花费和效果，提出调整建议，再由负责人决定是否改预算。需要获准访问的广告后台、分析数据和预算表；没有连接器或可靠导出时，不要让 Bot 编造指标。本次演示的虚构输入是：月预算 USD 1,200，目标 CAC 不高于 USD 50；A 花费 400、10 次转化、营收 800，B 花费 600、10 次转化、营收 900。Bot 算出 A 的 CAC 为 USD 40、ROAS 为 2.0，B 分别为 USD 60 和 1.5，合计 CAC 正好是 USD 50；但没有边际效率信息，所以没有据此建议转移多少预算。需要注意，这里 Bot 把“每次转化成本”直接当成了 CAC：输入里没有新增客户数，转化也可能包含重复购买，真实 CAC 是否达标仍待确认。实际使用这个模板时，应在输入里写明新增客户数和去重口径。

根据 [广告后台报告]、[分析报表] 和 [月度预算表]，按 campaign 汇总当前花费和效果。
与预算及目标 CAC 对比，列出计算口径、数据日期、偏差和建议重新分配的金额。
交付可核对的表格，以及一份给团队看的 Slack 消息草稿。
草稿不得发送；不要更改任何预算或广告设置。
缺少字段、口径不一致或来源过期时，先列出缺口，不给确定的金额建议。

复核每个计算的分子、分母、币种和时间范围。即使建议看起来合理，调预算和发布消息仍属于外部操作，应留给人工确认。官方 Paid Media 案例也要求不改预算、不发送消息，即使做成 Routine，广告活动的修改仍要先经审批。

什么时候保存为 Skill 或 Routine

一个案例成功一次，还不足以自动运行。官方 Use cases 推荐的顺序是：先完成一次任务、修正到可检查的结果、保存 Skill，然后用第二份输入再测；定义好失败处理和重试行为后，再考虑 Routine。按 Skills and routines，Routine 的 Test run 会真实执行任务，不只是预览计划。

可以把每类案例的检查结果记成一张小表：

检查项通过条件
输入范围Bot 只用了指定链接、文件或获准连接器
事实准确数字、日期、对象和原始记录能对回来源
交付完整文件或摘要符合格式，并包含足够的来源链接
不确定性缺失、冲突、失败和假设都单独标出
行动边界发送、发布、付款、删除及生产改动停在审批之前

如果这些条件还不稳定，先缩小任务或补充 Skill 说明。
