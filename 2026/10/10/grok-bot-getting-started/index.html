Grok Bot 实测：整理公开文档、保存 Skill，并在另一个 Bot 中复用

 2026-10-10  AI AI Agent Grok Bot Skill 自动化

让 AI 整理资料时，难点往往在对话框之外：需要打开网页、查文件、在不同工具之间搬运信息，最后把结果放到能继续使用的位置。Grok Bot 面向的就是这类跨应用任务。

本文介绍的是 Grok Bot 官方产品。它让 Bot 使用云电脑完成工作，不是接入 Grok API 的第三方聊天机器人。下面按“确认资格 → 创建 Bot → 完成一次任务 → 保存 Skill → 换来源复用 → 换 Bot 调用”的顺序整理。

测试环境：2026 年 10 月 10 日，Linux 桌面客户端 0.68.1。实测了新建 Bot、网页整理、文件下载、保存 Skill，以及在同一 Bot 和新建 Bot 中复用 Skill；安装、账号关联和 Routine 部分依据官方文档。两次复用都是在消息中点名调用 Skill，未使用 / 菜单；Skill 是否被读取，依据是界面中的 Skill 标签和 Bot 的回复。

Grok Bot 如何工作

每个 Bot 有自己的名字、职责和上下文，执行任务时使用云端电脑上的浏览器、文件系统和终端，也能通过连接器访问外部工具。同一账号下的多个 Bot 共享同一台云电脑的文件与登录状态，所以分工只用来组织工作，不能拿来隔离敏感账号，见官方概览。下文用到的几个概念：Bot 是”谁来做”，云电脑是”在哪做”，Skill 是”怎么重复做一类事”，Routine 是”什么时候再做”。

账号、订阅与安装

使用资格（Cursor 付费计划、可关联的 SuperGrok / X Premium+ 订阅、Grok Business 席位等，SuperGrok Lite 不含）和每周用量、On-demand 计费规则见 Plans and billing；下载、登录、关联订阅和数据设置要求（不支持 Legacy Privacy Mode）见 Get started。我用的是 Linux 桌面客户端，从 x.ai/bot 下载。桌面端只是入口，默认工作环境仍是云电脑。

创建第一个 Bot

在引导页选择建议的角色，或使用 Create your own。初次尝试可以创建一个“技术资料整理员”，用下面的描述限定工作方式：

你负责整理我指定的技术资料。
优先阅读官方文档，保存原始链接，区分事实、推断和待确认信息。
输出中文 Markdown，保留关键版本号与日期。
遇到来源无法访问或资料冲突时直接说明，不补写不存在的结论。
未经我明确要求，不发送消息、不发布内容、不修改外部系统。

这是一份可修改的角色模板。职责越具体，越容易判断交付结果是否符合预期。

实测：读取两篇公开文档，交付 Markdown 文件

本次从已安装、已登录的客户端开始。点击左上角的 ＋，应用创建了“新建 Bot”对话，并询问要处理什么任务。我们没有使用它推荐的选项，而是直接指定两个公开网址。

1. 输入任务，并指定交付物

下面是本次提交的任务内容，为方便阅读调整了换行：

这次是公开资料整理测试。请将你的名称设为“技术资料整理员”。
请仅访问 https://docs.x.ai/grok-bot/overview 和
https://docs.x.ai/grok-bot/skills-routines-and-automations，
整理一份中文 Grok Bot 阅读笔记。
输出内容：
1. Bot、云电脑、Skill、Routine 的区别；
2. 从一次任务保存为 Skill 再创建 Routine 的步骤；
3. 三项适用限制。
关键结论附原文链接，并记录网页标注的更新日期。
请生成 Markdown 文件 grok-bot-reading-note.md，
并返回可下载文件及简短摘要。
不要读取 Gmail、Notion、私有 GitHub 或本地文件，
不发送消息，不发布内容，不创建定时任务。
来源无法访问时直接说明。

发送后，Bot 回复将只读取指定页面，将名称改为“技术资料整理员”，并显示正在处理。这个案例没有让 Bot 登录新的服务，也没有上传私人资料。

2. 查看摘要和文件卡片

任务完成后，对话中出现 grok-bot-reading-note.md 文件卡片，界面显示 9.3 kB。摘要包含四个概念的区别、流程步骤与限制，并列出概览页的更新日期为 2026 年 10 月 7 日，Skills 页面为 10 月 6 日。

这里可以确认它交付了文件和摘要。Bot 还说明只访问了指定页面、没有读取其他连接，这一点是它的自述。

3. 预览、下载并检查内容

点击文件卡片的名称，可打开 Markdown 预览。预览窗口右上角和文件卡片右侧都有下载图标；本次点击卡片上的图标后，文件保存到了系统下载目录。

下载文件实际为 9,489 字节。打开后可以看到来源表、概念对比、流程步骤和限制说明。抽查发现，页面更新日期、Skill 跨 Bot 共享、Routine 归属单个 Bot 等内容与前文核对的官方文档一致。

也有需要编辑的地方：笔记额外讨论了提示词并未要求的 box 术语，并在一些段落中重复粘贴英文原句。这不影响文件交付，但如果要作为文章使用，应先删掉无关内容、精简重复引用，而不是直接发布整份生成结果。

本次实测说明，Grok Bot 能在一个任务里读取指定网页、整理内容并返回可下载文件；报告是否适合发布，仍需要检查来源和编辑质量。

补充：需要登录时如何接管（官方说明）

本次公开网页任务没有触发登录接管。根据官方说明，Bot 遇到认证步骤时，可以让你打开 Agent Computer 并接管。登录、完成验证后，再把控制权交回。密码和一次性验证码由你在接管界面输入，不放进普通聊天消息。

这台电脑上的会话会保留，其他 Bot 也可能使用相同登录状态。具体接管方式见 官方入门步骤，凭据与权限说明见 Approvals, security, and privacy。

把这次任务保存为 Skill

官方文档把 Skill 和 Routine 分开：Skill 保存做法，Routine 指定执行时间或受支持的事件触发条件。建议先完成一次任务、纠正输出，再保存 Skill。

下载并核对报告后，我们继续发送了保存请求：

请把本次“读取指定公开文档并生成带来源的中文 Markdown 笔记”
流程保存成一个 Skill，名称“公开文档阅读笔记”。
包含输入网址、检查网页日期、区分原文事实与未知内容、
输出文件及摘要、来源不可访问时报告失败。
仅允许访问任务中明确指定的公开页面。
不读取私人连接或本地资料、不发送消息、不发布、不创建 Routine。
完成后告知如何在界面中找到该 Skill。
只保存 Skill，不创建定时或事件任务。

Bot 返回“公开文档阅读笔记”的可点击标签。本次使用这个标签打开详情；根据官方 Skills 文档，已保存的 Skill 可在桌面输入框中用 / 引用，@ 则用于 Bot、群组、Routine 和连接器。Bot 的回复把 / 和 @ 都列为入口，这一点与文档不符，以文档为准。

点击标签后，客户端打开 Skill 详情，显示“私有技能”、名称、描述和指令。指令中包含网址输入、输出文件名以及仅访问指定来源的约束。可见 Skill 确实已保存，不只是 Bot 口头确认。

保存时没有点击“发布”。到这一步验证的是创建与查看；Skill 能不能真正复用，要换一个来源再跑一次。

复用 Skill：换一篇文档再跑一次

Skill 名称和“已保存”的回复还不够。开始前，我们重新打开上一条对话中的 Skill 链接，确认详情页仍显示“私有技能”，并保留了输入、指令和访问边界。

若 Skill 没有出现在 / 菜单，可到 Marketplace → Your plugins → Manage plugins and skills 检查 Private skills。本次输入 /公开 没有匹配结果，我们改为在消息中点名 Skill，并要求找不到时直接报告失败。

1. 换一个来源，保留交付要求

这次只指定官方 Files and results 文档，目标文件为 grok-bot-files-note.md。它与前面的概念介绍不同，重点是文件输入与结果交付。

下面是完整提示词，为方便阅读调整了换行：

请调用账号中已经保存的私有 Skill“公开文档阅读笔记”，
不要重新创建 Skill。
把本次新建 Bot 的名字设为“文档复用验证员”。
输入网址只有 https://docs.x.ai/grok-bot/files-and-results 。
请按该 Skill 已保存的流程整理这篇新文档，
交付中文 Markdown 文件 grok-bot-files-note.md。
报告需要包含来源日期、附件数量与大小限制、
预览下载交付物的步骤、事实与推断及未知项，
并逐项给出来源链接。
只读取指定公开网页，不访问私人连接器或本地文件，
不发送消息、不发布、不创建 Routine。
请说明是否实际找到并读取了保存的 Skill；
若无法读取，直接报告失败，不用自行编造技能内容。

这一轮我本来要新建一个 Bot，提示词里也写的是“本次新建 Bot”，但从截图看，这条消息落在了上一轮的对话里，客户端没有新建，只是按提示把当前 Bot 改名为“文档复用验证员”（截图里那行“已重命名为 文档复用验证员”）。所以实际是同一会话中的第二次任务。光在提示词里写“新建”不会开出新 Bot；第一轮是点左上角的 ＋ 才建出来的。

Bot 随后回复已经找到并读取“公开文档阅读笔记”，没有重新创建 Skill，并返回了可点击的 Skill 标签。

2. 检查文件，而不只看完成回复

任务结束后，对话出现 grok-bot-files-note.md 卡片，界面显示约 8 kB。打开卡片可以预览，再通过下载按钮保存。我们实际下载的文件为 8,202 字节，并读取了 Markdown 正文。

文件包含来源与日期、附件限制、结果预览步骤、事实/推断/未知项，以及访问范围说明。下面是人工核对结果：

验收项下载文件中的表现核对结论
来源正确指向本次指定的 Files and results 页面未混入第一次任务的概览内容
日期可查记录页面更新日期 2026-10-03与官方页面页脚一致
关键数字准确桌面一次最多 6 个附件；文档、图片、音频每个最多 25 MB；视频每个最多 200 MB与官方 Attach files 小节一致；本次没有上传临界大小文件测试
引用可定位多项结论附 #attach-files、#preview-generated-work 等章节链接下载文件保留了可核对的来源
未知信息单列列出总大小上限、超限处理、具体预览格式等未说明事项没有把这些事项写成确定规则
交付物可用预览可打开，下载后是可读取的 Markdown文件交付完成

附件规则与页面日期依据官方原文。

3. 日期补查与未知项值得保留

下载报告解释：首次读取正文时没有获得更新日期，随后抓取同一个 URL 的原始 HTML 补查页脚和元数据。我们独立查看官方页面，确认更新日期为 2026 年 10 月 3 日；报告所述的 WebFetch 与 curl 执行过程则属于 Bot 自述。

报告没有自行确定文件超限后会被拒绝、截断还是提示错误，也没有给出所有可预览格式的清单。这种留白有实际价值：当来源没有回答问题时，报告应把问题留给后续验证。

报告声明只读取了指定网址，没有读取私人连接器、发送消息或创建 Routine。

4. 结果仍有三处需要改进

英文引文重复较多。 附件限制在正文与事实清单中重复出现，中文说明后还附了长英文原句，前面第一次任务的笔记也有同样的问题。核对时有帮助，但阅读成本偏高。适合把 Skill 的输出规则改成“以中文转述为主，每项结论保留来源链接，仅在术语有歧义时保留短引文”。本文没有全文转载生成报告。

预览表格较拥挤。 来源表同时放了长网址、访问说明、日期与时区，预览中出现较碎的换行。只有一个来源时，可以改成纵向信息块：来源名称、链接、页面日期、核对时间各占一行。

这次不能单独证明 Skill 的贡献。 我们沿用了旧对话，提示词又重复了若干交付要求。即使结果合格，也不能区分其中多少来自已保存的指令、旧上下文或本次提示。更严格的做法是换一个独立 Bot，只提供新网址和必要参数。

以下是可追加到 Skill 的改进建议，本次尚未修改保存的指令：

中文转述为主，避免在多个章节重复同一结论或长段英文。
单个来源使用纵向信息块，不使用五列表格。
每项结论附章节链接，页面日期缺失时说明如何补查。
不要把页面未说明的行为写成已验证结论。
最终摘要列出：文件名、来源、已核对事项、仍需实测的问题。

换一个 Bot 再调用

同一会话里的复用，分不清结果来自 Skill、旧上下文还是提示词。所以我们又新建了一个“跨 Bot 复用验证员”，只给它官方审批、隐私与安全文档的网址，要求使用已保存的“公开文档阅读笔记”，不重新创建或修改，找不到就先报告、不要照着提示词仿做，并交付 grok-bot-approvals-note.md。任务同样禁止访问私人连接器、本地文件，或发送、发布、创建 Routine 与修改设置。

按操作记录，这是一个新建的 Bot，消息气泡也从前一个 Bot 的橙色变成了玫红色。不过截图没有拍到侧边栏的 Bot 列表，单看截图只能确认改名提示。

新 Bot 回复找到了这个 Skill，返回同名 Skill 标签，随后交付了约 8.7 kB 的文件卡片和摘要，摘要给出的页面更新日期为 2026 年 10 月 6 日，内容涉及自动审查（Auto Review）规则和人工接管步骤。

我们对照官方页面核对了摘要中的要点：

摘要要点官方文档说明核对结果
页面更新日期页脚标注 October 6, 2026一致
Ask first匹配时始终暂停，等用户处理一致
Allow automatically自动审查没有发现其他停止理由时，匹配操作才继续一致
两类规则同时匹配Ask first 优先一致
密码和验证码打开 Agent Computer 接管，自己完成敏感步骤，再交还控制权一致

这一轮只核对了卡片和摘要，没有下载文件正文，因此对文件内部的完整性、引用是否逐项可点击，不作保证。能确认的是：同一账号下新建的 Bot 能找到这个私有 Skill，并在引用它后交付了新页面的笔记。这与官方 Skills 文档的说法一致：Private skills 是所有 Bot 共用的一个库。提示词仍重复了部分交付要求，所以和上一轮一样，测不出 Skill 单独的贡献；这次也没走 / 菜单。

换一个 Bot 只改变任务角色与会话，开头说过，Bot 之间共享同一台云电脑，官方文档也提醒不要把单独创建的 Bot 当作安全边界。本次没有执行 Routine，没有访问连接器或本地文件，也没有修改 Auto Review 设置；访问范围来自请求限制和 Bot 对话中的说明，我们没有独立审计后台的全部工具调用。

再复用时如何验收

可以先换来源，再逐步加入更难的情况。每次都检查实际文件和引用，而不是仅检查 Bot 是否回复完成。

  • 独立 Bot：上一节已验证新 Bot 能找到该 Skill；下次还应下载文件，按上面的验收表逐项核对。
  • 来源失败：指定无法访问的测试网址，检查是否明确停止或标注失败。
  • 日期缺失：确认报告写“未找到”，而不是沿用之前的日期。
  • 内容冲突：给出两份存在差异的公开来源，检查是否分别列出依据。

后三项尚未测试，/ 菜单路径和多次运行的稳定性也还没有验证。Skill 对输出质量的贡献还需要更干净的对照测试；下一步先按上面的建议修改指令，再只给网址重跑一次。

Routine 和审批规则：只读了文档

这两部分我没有实测。流程稳定后可以把 Skill 配成 Routine 定时执行，做法见官方 Skills 与 Routines 文档，其中 Test run 会执行真实工作。涉及邮件、发布或修改外部系统的任务，我会把完成条件写成”先给出待执行的结果，等我确认”，例如：

读取指定邮件，按主题归类并生成回复草稿。
每份草稿附上原始邮件链接，列出需要我确认的事实。
不要发送，完成后给我检查列表。

Auto Review 的 Ask first / Allow automatically 规则，以及删除 Bot 不会清掉共享云电脑上的文件和浏览器会话这一点，见权限与数据说明。

如何判断这次尝试有没有价值

本次验证了入门流程，以及 Skill 在同一 Bot 和新建 Bot 中被找到并交付了文件卡片；跨 Bot 那一轮只看了卡片和摘要，没有下载正文，跨应用联动、Routine 和后台执行也还没有测试。

建议从一个固定流程开始，记录人工原本需要的时间，再比较 Bot 交付后的检查与修正时间。可以连续观察三次：

  • 是否能找到正确、最新的来源？
  • 是否按约定格式交付，而不是只给一段概述？
  • 中途失败时是否说明已经完成和仍未完成的部分？
  • 你是否能直接接着结果工作？

如果每次都要重新解释需求，先改角色描述和 Skill；如果来源频繁不可访问，先检查登录状态与工作环境。适合自动化的流程，应该先有清楚的输入、交付物和验收方式。
