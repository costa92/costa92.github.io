Grok Bot 进阶实测：复用 Skill 处理新文档，并在另一个 Bot 中调用

 2026-10-10  AI AI Agent Grok Bot 自动化 Skill
AI Agent Grok Bot 自动化 Skill
AI
文章字数:   2.6k
阅读次数:  
   阅读模式

上一篇入门实测完成了公开网页整理、Markdown 下载，以及私有 Skill“公开文档阅读笔记”的保存。接下来要验证两件事：换一个来源后，能否继续得到可检查的文件？换一个 Bot，还能不能找到这个 Skill？

这次在同一个 Bot 对话中，明确要求使用已保存的 Skill，读取新的官方文档 Files and results。Bot 回复称找到了并读取该 Skill，随后交付了新的 Markdown 文件。下载后的内容满足主要格式要求，但仍需要人工整理。

测试环境同上一篇。两次都是在消息中点名调用 Skill，未使用 / 菜单；Skill 是否被读取，依据是界面中的 Skill 标签和 Bot 的回复。

先检查保存的 Skill

Skill 名称和“已保存”的回复还不够。开始前，我们重新打开上一条对话中的 Skill 链接，确认详情页仍显示“私有技能”，并保留了输入、指令和访问边界（详情页截图见上一篇）。

这份 Skill 的用途是读取用户明确指定的公开网页，返回中文 Markdown 文件和摘要。输入包括网址、整理要点与输出文件名；规则要求记录来源日期，区分事实和未知信息，来源失败时明确报告。

按官方 Skills 文档，桌面输入框的 / 用于引用保存的 Skill，@ 用于 Bot、群组、Routine 与连接器。若 Skill 没有出现在 / 菜单，可到 Marketplace → Your plugins → Manage plugins and skills 检查 Private skills。

本次输入 /公开 没有匹配结果，我们改为在消息中点名 Skill，并要求找不到时直接报告失败。

换一个来源，保留交付要求

这次只指定官方 Files and results 文档，目标文件为 grok-bot-files-note.md。它与上一篇的概念介绍不同，重点是文件输入与结果交付。

下面是任务主体，为方便阅读调整了换行，省略了重命名请求：

请调用账号中已经保存的私有 Skill“公开文档阅读笔记”，
不要重新创建 Skill。
输入网址只有 https://docs.x.ai/grok-bot/files-and-results 。
请按该 Skill 已保存的流程整理这篇新文档，
交付中文 Markdown 文件 grok-bot-files-note.md。
报告需要包含来源日期、附件数量与大小限制、
预览下载交付物的步骤、事实与推断及未知项，
并逐项给出来源链接。
只读取指定公开网页，不访问私人连接器或本地文件，
不发送消息、不发布、不创建 Routine。
请说明是否实际找到并读取了保存的 Skill；
若无法读取，直接报告失败，不用自行编造技能内容。

提示词里把 Bot 称为“本次新建”，但客户端沿用了上一篇的对话，只是把 Bot 改名为“文档复用验证员”，所以这次属于同一会话中的第二次任务。

Bot 随后回复已经找到并读取“公开文档阅读笔记”，没有重新创建 Skill，并返回了可点击的 Skill 标签。

检查文件，而不只看完成回复

任务结束后，对话出现 grok-bot-files-note.md 卡片，界面显示约 8 kB。打开卡片可以预览，再通过下载按钮保存。我们实际下载的文件为 8,202 字节，并读取了 Markdown 正文。

文件包含来源与日期、附件限制、结果预览步骤、事实/推断/未知项，以及访问范围说明。下面是人工核对结果：

验收项下载文件中的表现核对结论
来源正确指向本次指定的 Files and results 页面未混入上一篇的概览内容
日期可查记录页面更新日期 2026-10-03与官方页面页脚一致
关键数字准确桌面一次最多 6 个附件；文档、图片、音频每个最多 25 MB；视频每个最多 200 MB与官方 Attach files 小节一致；本次没有上传临界大小文件测试
引用可定位多项结论附 #attach-files、#preview-generated-work 等章节链接下载文件保留了可核对的来源
未知信息单列列出总大小上限、超限处理、具体预览格式等未说明事项没有把这些事项写成确定规则
交付物可用预览可打开，下载后是可读取的 Markdown文件交付完成

附件规则与页面日期依据官方原文。

日期补查与未知项值得保留

下载报告解释：首次读取正文时没有获得更新日期，随后抓取同一个 URL 的原始 HTML 补查页脚和元数据。我们独立查看官方页面，确认更新日期为 2026 年 10 月 3 日；报告所述的 WebFetch 与 curl 执行过程则属于 Bot 自述。

报告没有自行确定文件超限后会被拒绝、截断还是提示错误，也没有给出所有可预览格式的清单。这种留白有实际价值：当来源没有回答问题时，报告应把问题留给后续验证。

报告声明只读取了指定网址，没有读取私人连接器、发送消息或创建 Routine。

结果仍有三处需要改进

英文引文重复较多。 附件限制在正文与事实清单中重复出现，中文说明后还附了长英文原句。核对时有帮助，但阅读成本偏高。适合把 Skill 的输出规则改成“以中文转述为主，每项结论保留来源链接，仅在术语有歧义时保留短引文”。本文没有全文转载生成报告。

预览表格较拥挤。 来源表同时放了长网址、访问说明、日期与时区，预览中出现较碎的换行。只有一个来源时，可以改成纵向信息块：来源名称、链接、页面日期、核对时间各占一行。

这次不能单独证明 Skill 的贡献。 我们沿用了旧对话，提示词又重复了若干交付要求。即使结果合格，也不能区分其中多少来自已保存的指令、旧上下文或本次提示。更严格的做法是换一个独立 Bot，只提供新网址和必要参数。下一节换了 Bot，验证的是跨 Bot 能否找到并引用 Skill；不过那次的提示词仍重复了部分交付要求，同样不能单独衡量 Skill 对输出的贡献。

以下是可追加到 Skill 的改进建议，本次尚未修改保存的指令：

中文转述为主，避免在多个章节重复同一结论或长段英文。
单个来源使用纵向信息块，不使用五列表格。
每项结论附章节链接，页面日期缺失时说明如何补查。
不要把页面未说明的行为写成已验证结论。
最终摘要列出：文件名、来源、已核对事项、仍需实测的问题。

换一个 Bot 再调用

同一会话里的复用，分不清结果来自 Skill、旧上下文还是提示词。所以我们又新建了一个“跨 Bot 复用验证员”，只给它官方审批、隐私与安全文档的网址，要求使用已保存的“公开文档阅读笔记”，找不到就先报告、不要照着提示词仿做，并交付 grok-bot-approvals-note.md。

按操作记录，这是一个新建的 Bot，消息气泡也从前一个 Bot 的橙色变成了玫红色。不过截图没有拍到侧边栏的 Bot 列表，单看截图只能确认改名提示。

新 Bot 回复找到了这个 Skill，返回同名 Skill 标签，随后交付了约 8.7 kB 的文件卡片和摘要，摘要给出的页面更新日期为 2026 年 10 月 6 日。

我们对照官方页面核对了摘要中的要点：

摘要要点官方文档说明核对结果
页面更新日期页脚标注 October 6, 2026一致
Ask first匹配时始终暂停，等用户处理一致
Allow automatically自动审查没有发现其他停止理由时，匹配操作才继续一致
两类规则同时匹配Ask first 优先一致
密码和验证码打开 Agent Computer 接管，自己完成敏感步骤，再交还控制权一致

这一轮只核对了卡片和摘要，没有下载文件正文。能确认的是：同一账号下新建的 Bot 能找到这个私有 Skill，并在引用它后交付了新页面的笔记。这与官方 Skills 文档的说法一致：Private skills 是所有 Bot 共用的一个库。

再复用时如何验收

可以先换来源，再逐步加入更难的情况。每次都检查实际文件和引用，而不是仅检查 Bot 是否回复完成。

  • 独立 Bot：上一节已验证新 Bot 能找到该 Skill；下次还应下载文件，按上面的验收表逐项核对。
  • 来源失败：指定无法访问的测试网址，检查是否明确停止或标注失败。
  • 日期缺失：确认报告写“未找到”，而不是沿用上一篇日期。
  • 内容冲突：给出两份存在差异的公开来源，检查是否分别列出依据。

后三项尚未测试。结论是：同账号下新建的 Bot 能找到这个私有 Skill，并在引用它后返回交付卡片。Skill 对输出质量的贡献还需要更干净的对照测试；下一步先按上面的建议修改指令，再只给网址重跑一次。
