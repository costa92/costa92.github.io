Go、Rust 写的 CLI 为什么用 npm 分发：拆开飞书 lark-cli 和 Codex 看整套设计

 2026-10-10  Tool 开发工具 Go Rust npm

Tool
文章字数:   9.6k
阅读次数:

第一次装飞书官方 CLI 时，我以为看错了文档：一个 Go 写的命令行工具，安装命令是

npx @larksuite/cli@latest install

Go 的卖点之一就是「编译出一个静态二进制，扔到哪都能跑」，按理说 GitHub Releases 挂几个压缩包、再给个 Homebrew formula 就够了，为什么要绕道 Node.js 的包管理器？

而且这不是飞书独有的。OpenAI 的 Codex CLI 用 Rust 写，安装命令是 npm install -g @openai/codex；Rust 写的代码检查工具 Biome 是 npm install @biomejs/biome。语言不同，分发渠道却都选了 npm。

带着这个疑问，我把本机全局安装的 @larksuite/cli@1.0.63 拆开看了一遍，又下载了 @openai/codex@0.162.1 和 @biomejs/biome@2.5.15 做对照。结论先放在这里：npm 在这里不是运行时，而是分发渠道。Go 或 Rust 负责「把程序做好」，npm 负责「把程序送到用户手上」，两件事分开选最合适的工具。而且只要把这层外壳设计好，里面装的是什么语言编译出来的二进制，npm 并不关心。

拆开 npm 包：里面其实没有 Go 代码

先看 package.json，关键字段只有这几个：

{
  "name": "@larksuite/cli",
  "version": "1.0.63",
  "bin": { "lark-cli": "scripts/run.js" },
  "scripts": { "postinstall": "node scripts/install.js" },
  "os": ["darwin", "linux", "win32"],
  "cpu": ["x64", "arm64", "riscv64"],
  "files": [
    "scripts/install.js",
    "scripts/install-wizard.js",
    "scripts/run.js",
    "checksums.txt",
    "CHANGELOG.md"
  ]
}

files 里没有任何二进制文件，除了 README、CHANGELOG 这类文档，发布到 npm 的只有三个 JS 脚本和一份 checksums.txt，npm view 显示整个包解压后约 112 kB（unpackedSize 为 111534 字节）。而装完以后，node_modules/@larksuite/cli/bin/ 下多出一个 39.7MB 的文件：

$ file bin/lark-cli
bin/lark-cli: ELF 64-bit LSB executable, x86-64, version 1 (SYSV),
statically linked, Go BuildID=..., stripped

这才是真正的 lark-cli，一个静态链接的 Go 程序。它不在 npm 包里，是安装时现下载的。整个过程分三步。

第一步：postinstall 按平台下载二进制

npm install 结束时会执行 postinstall，也就是 scripts/install.js。它先把 Node 的平台标识映射成 Go 的 GOOS/GOARCH 命名：

const PLATFORM_MAP = { darwin: "darwin", linux: "linux", win32: "windows" };
const ARCH_MAP = { x64: "amd64", arm64: "arm64", riscv64: "riscv64" };

const archiveName = `${NAME}-${VERSION}-${platform}-${arch}${ext}`;
const GITHUB_URL =
  `https://github.com/${REPO}/releases/download/v${VERSION}/${archiveName}`;

拼出来的就是 GoReleaser 风格的文件名，比如 lark-cli-1.0.63-linux-amd64.tar.gz。注意 VERSION 直接取自 package.json，所以 npm 包的版本号和 GitHub Release 的 tag 是一一绑定的，不会出现「npm 装了 1.0.63，下载到的却是别的版本」。

下载地址不止一个，按顺序尝试：

  1. GitHub Releases；
  2. 如果用户配置了非默认的 npm_config_registry（公司内部的 Verdaccio、Artifactory 等），尝试 <registry>/-/binary/lark-cli/v<版本>/<文件名>；
  3. 最后回退到 registry.npmmirror.com 的二进制镜像。

第 3 条对国内用户很关键：GitHub Releases 在国内经常下载失败，而 npmmirror 本来就同步了大量这类二进制文件。用户执行 npm install 时已经配置好的镜像，顺手也被拿来下载 Go 二进制了。

第二步：用 checksums.txt 校验

下载完不会直接用。npm 包里随附的 checksums.txt 列出了 7 个平台压缩包的 SHA-256：

d0cdc776...  lark-cli-1.0.63-linux-amd64.tar.gz
e24c3e44...  lark-cli-1.0.63-linux-arm64.tar.gz
5c6f3d88...  lark-cli-1.0.63-windows-amd64.zip
...

install.js 流式计算下载文件的哈希，不一致就抛出 [SECURITY] Checksum mismatch。这一步的意义在于：二进制可能来自 GitHub，也可能来自某个镜像，但校验值来自 npm 包本身。只要你信任 npm 上这个包的发布者，就不必再额外信任每一个镜像站。脚本里还有一个下载域名白名单，注释写得很直白：白名单只是纵深防御，主要的完整性保障是 checksum。

校验通过后解压（Windows 上依次尝试 .NET ZipFile、Expand-Archive、tar 三种方式），把二进制拷到包内的 bin/ 目录并 chmod 755。

第三步：run.js 转发命令

bin 字段指向的不是 Go 二进制，而是 scripts/run.js。npm 会在全局 bin 目录生成一个叫 lark-cli 的链接指向它，你每次敲 lark-cli，实际执行的是：

const bin = path.join(__dirname, "..", "bin", "lark-cli" + ext);
execFileSync(bin, args, { stdio: "inherit" });

stdio: "inherit" 让 Go 程序直接继承终端的标准输入输出，交互、颜色、管道都正常；退出码通过 process.exit(e.status) 原样传回。

除了转发，run.js 还兜了两个底：

  • 二进制不存在时自动补装。安装时加了 --ignore-scripts、或者包管理器默认不执行依赖的生命周期脚本（pnpm 10 就是这样），postinstall 不会跑；用 npx 临时运行时脚本会执行，但 install.js 检测到 npm_command 为 exec 就主动跳过下载。这几种情况下，run.js 发现 bin/lark-cli 不存在，会先调一次 install.js 再执行。
  • 拦截 install 子命令。npx @larksuite/cli install 不会转发给当前包里的 Go 二进制，而是先进入一个 JS 写的安装向导：它用 npm install -g 安装或升级全局的 lark-cli，再调用全局命令的 config init、auth login 完成应用配置和授权，最后调用 npx skills add larksuite/cli 给 AI 编程工具装上配套的 Skills。

为什么偏偏是 npm

理解了机制，再回到最初的问题。Go 程序的分发方式其实很多，逐个看一下它们各自缺什么。

方式用户需要什么主要问题
go installGo 工具链绝大多数用户没装 Go；从源码编译，慢
GitHub Releases 手动下载浏览器要自己选平台、解压、放进 PATH，升级全靠手动
curl ... | sh 安装脚本curl、shWindows 不友好；国内访问 GitHub 不稳定
Homebrewbrew基本只覆盖 macOS，Linux 用户少，Windows 没有
Scoop / winget / apt / yum各自的包管理器每个平台单独维护一套发布流程
npmNode.js需要 Node；二进制要另外处理（本文的做法）

npm 能胜出，靠的是下面几点。

1. 目标用户的机器上大概率已经有 Node

飞书 CLI 的 README 第一句话是「让人类和 AI Agent 都能在终端中操作飞书」。它的主要用户是两类：前端/全栈开发者，以及 Claude Code、Codex 这类 AI 编程工具的使用者。前者天天用 npm；后者的工具本身很多就是通过 npm 安装的，Node 早就在机器上了。

对这些人来说，「装一个 npm 包」是零学习成本的操作，而「去 GitHub 选对 linux-arm64 的压缩包」反而是门槛。分发渠道选的是用户已经在用的那个，而不是开发语言对应的那个。

2. 一条命令覆盖三大系统

npm 在 macOS、Linux、Windows 上用法完全一致，npm install -g 之后命令自动进 PATH。lark-cli 的包声明了 3 种操作系统 × 3 种 CPU 架构，对应 7 个预编译产物，用户不需要知道自己是 amd64 还是 arm64，install.js 用 process.platform 和 process.arch 判断。

同样的效果，用系统包管理器要分别维护 Homebrew formula、Scoop manifest、deb/rpm 仓库，工作量和出错面都大得多。

3. 版本、升级、卸载都是现成的

npm 自带语义化版本、npm update -g、npm uninstall -g、npm outdated。项目内还可以把它写进 devDependencies 锁定版本，团队成员 npm ci 后拿到的是完全相同的 CLI，CI 里也一样。Go 二进制自己实现这一整套（检查更新、替换自身、回滚）不是做不到，但要花不少功夫。

4. npx 让「先试试」变成一行命令

npx @larksuite/cli@latest install

这条命令本身不要求用户先全局安装，向导会替用户完成全局安装、配置和授权。这对 AI Agent 尤其友好：文档里写一行 npx 命令，Agent 就能自己完成安装，不必判断操作系统、处理解压路径。只想临时试用、不想留下全局安装，可以用 npx @larksuite/cli@1.0.63 --help 这类不带 install 的命令。README 里甚至专门给 AI 助手留了一段「请直接跳转到快速开始（AI Agent）」的提示。

5. 现成的镜像基础设施

国内开发者普遍已经配置了 npm 镜像。lark-cli 复用 npm_config_registry 推导二进制下载地址，并以 npmmirror 兜底。等于借用了 npm 生态多年积累的镜像网络，不用自己搭 CDN。

6. 生态里已经有成熟先例

这种「原生程序 + npm 外壳」的模式并不是飞书首创。前端工具链和开发者工具里早就大量使用：

  • esbuild（Go 编写）
  • Biome、Sentry CLI、Deno（Rust 编写）
  • Turborepo（早期 Go，后迁到 Rust）
  • Bun（Zig 编写）

用户执行 npm install esbuild 时，大多根本没意识到自己装的是一个 Go 程序。

换成 Rust：Codex 和 Biome 怎么做

lark-cli 是「npm 包里不放二进制，安装时去外面下载」。两个 Rust 项目走的是另一条路：二进制本身就发布在 npm 上。

Biome：每个平台一个子包

@biomejs/biome 主包把 8 个平台子包列为 optionalDependencies：

$ npm view @biomejs/biome optionalDependencies
{
  "@biomejs/cli-linux-x64": "2.5.15",
  "@biomejs/cli-linux-x64-musl": "2.5.15",
  "@biomejs/cli-darwin-arm64": "2.5.15",
  "@biomejs/cli-win32-x64": "2.5.15",
  ...
}

$ npm view @biomejs/cli-linux-x64 os cpu libc
{ "os": ["linux"], "cpu": ["x64"], "libc": ["glibc"] }

每个子包用 os / cpu 声明自己只适用于哪个平台，包管理器安装时会跳过不匹配的可选依赖，最后只落地当前平台那一个子包，里面就是 Rust 编译出的 biome 可执行文件。esbuild（Go）用的也是这个方案，子包叫 @esbuild/linux-x64 之类。

主包的 bin/biome 是启动器，核心逻辑只有几行：

const binPath = env.BIOME_BINARY ||
  (platform === "linux" && isMusl()
    ? PLATFORMS["linux-musl"][arch]
    : PLATFORMS[platform][arch]);

spawnSync(require.resolve(binPath), process.argv.slice(2), {
  stdio: "inherit",
  env: { ...env, BIOME_DISTRIBUTION: "npm", ... },
});

子包型的安装过程完全由包管理器完成，不需要任何安装脚本：

和 lark-cli 比，多了两个细节：Linux 上要用 ldd --version 判断是 glibc 还是 musl（Alpine 容器是 musl），再选对应子包；还允许用环境变量 BIOME_BINARY 指定一个自己的二进制，绕过 npm 里的版本。

Codex：同一个包名，用版本号区分平台

@openai/codex 的主包只有约 13KB，optionalDependencies 写得很特别：

{
  "@openai/codex-linux-x64":   "npm:@openai/codex@0.162.1-linux-x64",
  "@openai/codex-darwin-arm64": "npm:@openai/codex@0.162.1-darwin-arm64",
  "@openai/codex-win32-x64":   "npm:@openai/codex@0.162.1-win32-x64",
  ...
}

npm: 前缀是 npm 的别名语法。Codex 没有注册 6 个独立的子包名，而是把各平台二进制作为同一个包 @openai/codex 的预发布版本发布，比如 0.162.1-linux-x64，再在主包里用别名引用。npm view @openai/codex@0.162.1-linux-x64 os cpu 能看到它同样声明了 "os": ["linux"], "cpu": ["x64"]。好处是 npm 上只多出几个版本号，不多出包名，发布权限和包页面都只有一份。

启动器 bin/codex.js 先把 Node 的平台标识映射成 Rust 的 target triple：

const PLATFORM_PACKAGE_BY_TARGET = {
  "x86_64-unknown-linux-musl": "@openai/codex-linux-x64",
  "aarch64-unknown-linux-musl": "@openai/codex-linux-arm64",
  "x86_64-apple-darwin": "@openai/codex-darwin-x64",
  "aarch64-apple-darwin": "@openai/codex-darwin-arm64",
  "x86_64-pc-windows-msvc": "@openai/codex-win32-x64",
  "aarch64-pc-windows-msvc": "@openai/codex-win32-arm64",
};

注意 Linux 只有 musl 版本。Codex 把 Linux 二进制统一编译成 musl 静态链接，于是不用像 Biome 那样区分 glibc 和 musl，一个产物同时跑在 Ubuntu 和 Alpine 上。

找不到子包时，它会判断你是用 npm、pnpm、bun 还是 Vite+ 装的，给出对应的重装命令。启动时用的是异步 spawn，并把 SIGINT、SIGTERM、SIGHUP 转发给子进程；子进程如果是被信号杀掉的，代码的本意是父进程用同一个信号结束自己，让外层脚本看到正确的退出状态。但 0.162.1 重发信号前没有移除自己注册的监听器，信号会被再次拦截：我按同样的写法做了最小复现，子进程被 SIGTERM 结束后，父进程的退出码是 0。后文示例在重发前先调用 process.removeAllListeners(signal)，就是为了避开这个问题。

cargo-dist：Rust 版的下载型

Rust 社区的发布工具 cargo-dist（现名 dist）可以自动生成 npm 安装包，思路和 lark-cli 一样。以它的作者 axo 自家的 @axodotdev/oranda 为例：

{
  "bin": { "oranda": "run-oranda.js" },
  "scripts": { "postinstall": "node ./install.js" },
  "dependencies": { "axios": "...", "tar": "...", "detect-libc": "...", ... }
}

postinstall 下载 GitHub Release 里的压缩包，run-oranda.js 负责启动。也就是说，Go 和 Rust 两边都存在「下载型」和「子包型」两种实现，选哪种跟语言无关。

更多案例：十几个真实 npm 包的做法

三个包还不足以说明这是一种普遍做法。我又用 npm view 查了一批常见的原生 CLI，并把其中几个下载下来读了安装脚本（版本是 2026-10-10 查询时的最新版，表中列出了实际查看的版本）：

@bufbuild/buf1.73.0Go子包型 + 兜底一个包提供 3 个命令；子包缺失时再跑一次 npm install

几点在前面三个包里没看到的设计，单独说一下。

第三种模式：安装时把 Node 外壳拿掉

后文「这么做的代价」一节会提到，每次执行命令都要先启动一个 Node 进程，这是 npm 分发常见的开销。Claude Code、Bun、opencode 把它去掉了。以 Claude Code 为例，它的 package.json 里 bin 直接指向 bin/claude.exe，而 npm 包里的这个文件只有 500 字节，是一段 shell 脚本：

echo "Error: claude native binary not installed." >&2
echo "Either postinstall did not run (--ignore-scripts, some pnpm configs)" >&2
...

真正的二进制在 @anthropic-ai/claude-code-linux-x64 这类子包里。postinstall 找到匹配的子包后，用硬链接把它放到 bin/claude.exe 的位置（失败再退回复制）。之后执行 claude，系统直接运行原生程序，不经过 Node。脚本注释里写明了用硬链接的原因：二进制约 500MB，硬链接不占额外磁盘、瞬间完成。

这个脚本里还有两处细节值得借鉴：

  • 判断 musl 不调用 ldd，而是看 process.report.getReport().header.glibcVersionRuntime 是否存在。注释说明了理由：更快，而且最小化容器里可能根本没有 ldd，命令找不到会被误判成 musl。
  • 在 Apple Silicon 上，如果用户装的是 x64 版 Node（经 Rosetta 转译运行），os.arch() 会返回 x64。脚本用 sysctl -n sysctl.proc_translated 识别这种情况，改装 arm64 二进制。

Bun 的做法类似，bin/bun.exe 同样是一个占位脚本。它的兜底链条更长：子包不在就自己执行一次 npm install @oven/bun-linux-x64，还不行就直接从 registry.npmjs.org 下载这个子包的 tgz 并解压。Deno 走的是另一条路，postinstall 不替换包内文件，而是改写 npm 在全局 bin 目录生成的链接，让 deno 命令直接指向原生二进制；改写失败时仍然保留 bin.cjs 这个 JS 启动器。

代价是重新依赖 postinstall。对 Claude Code、Bun、opencode 这类替换占位文件的包，脚本没跑，用户得到的就是那个报错的占位文件，所以它们的占位文件都会明确提示原因和修复命令。Deno 不受这个影响：改写入口失败或脚本没跑时，bin.cjs 仍能作为 JS 启动器运行，二进制缺失时还会调用 runInstall() 从平台子包里找到它。

子包为主，下载兜底

Sentry CLI 和 buf 走的是另一种折中：正常情况下用子包，postinstall 只检查子包是否已经存在，存在就直接退出。

子包缺失通常是因为用户加了 --no-optional 或 --omit=optional。这时 Sentry CLI 会从自家 CDN 下载对应平台的二进制，校验 checksums.txt 里的哈希，再执行 --version 确认版本号和 npm 包一致。buf 的安装脚本基于 esbuild 的实现（注释里直接引用了 esbuild 的 issue），兜底方式是在包目录里临时再执行一次 npm install <平台子包>@<版本>，这样依然走 npm 仓库，也能用上公司的 npm 代理。

buf 的另一个细节是 bin 字段里有 3 个命令：buf、protoc-gen-buf-lint 和 protoc-gen-buf-breaking。一个 npm 包可以同时分发多个原生程序。

postinstall 不一定用来下载

lefthook 是 Go 写的 Git hooks 管理器，二进制同样来自子包，但它的 postinstall 做的是另一件事：在用户项目目录（INIT_CWD）里执行 lefthook install，把 Git hooks 装好；检测到 CI 环境变量时跳过。

这类工具通常作为项目的 devDependencies 安装，团队成员 npm install 之后 hooks 就自动生效，也不用再单独装 Go 工具链。这也是 Go / Rust 写的前端工具（esbuild、Biome、turbo、buf）都发 npm 包的主要原因：它们属于某个 JS 项目，版本应该写在这个项目的 package.json 里，跟着 lockfile 一起锁定。

lefthook 的启动器也是一个反面例子：子进程退出码不为 0 时，它一律 process.exit(1)，原始退出码丢了，也没有转发信号。对 Git hooks 来说这无关紧要，但如果你的 CLI 用不同的退出码表示不同错误，这样写就不行。

换实现语言，安装命令不变

turbo 早期用 Go 编写，那时的平台子包叫 turbo-linux-64 之类（npm 上至今还能查到 turbo-linux-64@1.0.0）。后来改用 Rust 重写，子包也改名为 @turbo/linux-64，但用户执行的始终是 npm install turbo。它的启动器里专门有一段兼容逻辑，注释写着子包从 turbo-<os>-<arch> 改名成了 @turbo/<os>-<arch>，两种名字都会尝试。

Railway CLI 的情况类似。它现在是 Rust 写的，安装脚本的 URL 模板用的是 Rust target triple，但旁边的注释还写着「{{arch}} is one of the Golang architectures」，看起来是早期版本留下的。

这正是本文的核心观点：npm 包只是一层壳，壳里换了语言，用户不需要知道。

平台映射表出错的真实事故

前面说过，Node、Go、Rust 三套平台命名之间的映射表写错一项，那个平台的用户就装不上。Railway CLI 的 postinstall.js 里就记着这样一次事故：他们之前用 @napi-rs/triples 自动推导 target triple，Linux 一律得到 *-unknown-linux-gnu；可是他们除了 x86_64 以外不发布 gnu 版本，于是 arm64 等 Linux 平台上 npm i -g @railway/cli 全部失败，报错 Failed fetching the binary: Not Found。

修复方式是把映射表改成手写，并要求「每一项都必须对应 release 流水线实际产出的文件」，Linux 统一用 musl 静态版本。这和 Codex 只发 musl 的选择是同一个思路。

顺带一提，我在 Railway 的这两个安装脚本里没有找到 checksum 校验逻辑，而同为下载型的 lark-cli 和 go-task 都有。如果你采用下载型，这一步不要省。

整体设计：一套与语言无关的分发架构

把这些包放在一起看，可以抽象出一个通用结构。不管二进制是 Go、Rust、Zig 还是 C++ 编出来的，要通过 npm 分发，都得回答下面六个问题。

图中的编号对应下面六个小节。图里校验 ⑤ 画在启动器 ④ 之前，因为实际流程是先校验、再启动。

1. 构建矩阵：产出哪些平台的二进制

这是 Go 和 Rust 差异最大的地方。

Go 交叉编译几乎零成本：CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build 就能在任何机器上编出别的平台的二进制，默认静态链接，不依赖目标机器的 libc。lark-cli 的 7 个产物（3 系统 × 3 架构中的有效组合，包括 linux-riscv64）用 GoReleaser 一次生成，Linux 只需要一个版本。

Rust 每个 target triple 需要对应的标准库和链接器，macOS、Windows 目标通常要在对应系统的 CI runner 上编译，或借助 cross、cargo-zigbuild 之类的工具。Linux 上还要选 libc：

  • 链接 glibc（x86_64-unknown-linux-gnu）：兼容主流发行版，但在 Alpine 上跑不了，而且对 glibc 的最低版本有要求；
  • 链接 musl（x86_64-unknown-linux-musl）：可以完全静态，到处能跑，代价是 musl 自带的内存分配器在多线程场景下偏慢，不少项目会换成 jemalloc 或 mimalloc。

Biome 两种都发，所以有 8 个子包；Codex 只发 musl，所以只有 6 个。这个选择会直接影响下一步的平台匹配逻辑。

2. 产物托管：二进制放在哪里

下载型（lark-cli、cargo-dist）子包型（Biome、esbuild、Codex）
二进制位置GitHub Releases / 镜像npm 仓库本身
npm 主包体积很小（lark-cli 约 112 kB）很小，但子包大（Biome linux-x64 子包约 67MB）
是否依赖 postinstall是可以不依赖，取决于启动方案
内网 npm 代理 / 离线缓存需要额外处理自动生效
lockfile 完整性只覆盖 JS 外壳覆盖二进制
每次发版要发布1 个 npm 包 + 1 个 ReleaseN+1 个 npm 包（或 N+1 个版本）

子包型的优势在于「二进制也是 npm 包」，于是 npm 的一切基础设施都自动适用：公司的 Artifactory 代理、npm ci 的离线缓存、package-lock.json 里的 integrity 哈希。下载型则把这些都绕开了，所以 lark-cli 必须自己做 checksum、自己支持从 npm_config_registry 推导地址、自己处理脚本被禁用的情况。

实际项目里两者经常混用：Sentry CLI、buf 以子包为主、下载兜底；Claude Code、Bun 用子包分发二进制，再用 postinstall 把它放到 bin 的位置。详见上一节的案例。

3. 平台匹配：装哪一个

两种做法：

  • 声明式：子包写 os、cpu（以及 libc）字段，由包管理器在安装时过滤。Biome、Codex、esbuild 都是这样。不同包管理器对 libc 字段的支持程度不一，所以 Biome 在启动器里还会用 ldd 再判断一次，不完全依赖包管理器。
  • 命令式：安装脚本里读 process.platform / process.arch 自己拼文件名。lark-cli、cargo-dist 都是这样，cargo-dist 还额外依赖 detect-libc 判断 glibc / musl。

不管哪种，都绕不开一张映射表：Node 的 x64 对应 Go 的 amd64、Rust 的 x86_64；Node 的 win32 对应 Go 的 windows、Rust 的 pc-windows-msvc。这张表写错一项，那个平台的用户就装不上。

4. 启动器：那几十行 JS 要做什么

package.json 的 bin 通常指向一个 JS 文件，而不是二进制本身（上一节「替换占位文件」是例外）。原因是 npm 的 bin 需要一个跨平台的入口：在 Windows 上 npm 会为它生成 .cmd 包装，在 Unix 上生成符号链接，而二进制的真实路径在安装前并不确定。

一个合格的启动器要做到：

  1. 定位二进制：子包型用 require.resolve('<子包>/package.json')，下载型用固定的相对路径；
  2. 透传参数和标准输入输出：stdio: "inherit"，否则交互式界面、颜色和管道都会出问题；
  3. 原样返回退出码：CI 和 shell 脚本靠它判断成败；
  4. 转发信号：lark-cli 和 Biome 用同步的 execFileSync / spawnSync，在终端里按 Ctrl-C 没问题（同一进程组都会收到 SIGINT），但如果是外部程序只给 Node 父进程发 SIGTERM，子进程收不到。Codex 用异步 spawn 加信号转发，处理得更完整，只是被信号结束时的退出状态有前面说的问题；
  5. 缺失时给出可操作的提示：lark-cli 选择自动补装，Codex 选择报错并给出对应包管理器的重装命令。

5. 完整性与供应链

  • 子包型的二进制随 npm 包一起受 lockfile 的 integrity 字段保护，还可以用 npm 的 provenance 证明它来自哪个 CI 流水线；
  • 下载型必须自带校验：lark-cli 把 checksums.txt 打进 npm 包，校验值和二进制来自不同渠道，镜像被篡改也能发现。

另外，子包型可以做到完全不依赖安装脚本，比如 Biome 和 Codex，在 --ignore-scripts 已经成为不少团队默认配置的今天，这是一个实打实的优势。不过 Claude Code、Bun 这类替换入口的方案，以及需要校验或兜底下载的包，仍然会用到 postinstall。

6. 升级：谁说了算

原生 CLI 常常自带「检查更新」甚至「自我更新」功能。一旦通过 npm 安装，版本就应该由包管理器管理，二进制自己替换自己会让 node_modules 里的版本和 lockfile 对不上。

所以启动器会通过环境变量告诉二进制「你是被谁装的」：Biome 注入 BIOME_DISTRIBUTION=npm 和 NODE_PACKAGE_MANAGER，Codex 注入 CODEX_MANAGED_BY_NPM（或 _PNPM、_BUN）和包的根目录。二进制可以据此决定是自己更新，还是提示用户用包管理器升级（比如 npm install -g @openai/codex@latest）。

别和 napi-rs 搞混

Rust 进入 npm 还有一条路：用 napi-rs 把 Rust 编译成 Node 原生扩展（.node 文件），比如 Rspack 的 @rspack/binding。它的子包分发方式和 Biome 很像，但本质不同：原生扩展被 require 进 Node 进程，给 JS 调用，是库；本文讨论的是独立进程运行的命令行程序，Node 只负责启动它。如果你的产品是 CLI，不需要 napi-rs。

同样的模式在 Python 生态也有：uv、ruff 都是 Rust 写的，却通过 PyPI 分发，每个平台一个 wheel，pip install uv 装上的就是原生二进制。npm 和 PyPI 在这里扮演的是同一个角色。

const PLATFORMS = {
  "linux-x64":    { go: "linux-amd64",   rust: "x86_64-unknown-linux-musl" },
  "linux-arm64":  { go: "linux-arm64",   rust: "aarch64-unknown-linux-musl" },
  "darwin-x64":   { go: "darwin-amd64",  rust: "x86_64-apple-darwin" },
  "darwin-arm64": { go: "darwin-arm64",  rust: "aarch64-apple-darwin" },
  "win32-x64":    { go: "windows-amd64", rust: "x86_64-pc-windows-msvc" },
  "win32-arm64":  { go: "windows-arm64", rust: "aarch64-pc-windows-msvc" },

第二个是启动器 npm/shared/launch.js，按前面「启动器」一节的要求实现，写法参考了 Codex：

function launch(bin, args, extraEnv) {
  // 异步 spawn：事件循环不被阻塞，才能接收并转发信号
  const child = spawn(bin, args, { stdio: "inherit", env: { ...process.env, ...extraEnv } });

  for (const sig of ["SIGINT", "SIGTERM", "SIGHUP"]) {
    process.on(sig, () => {
      if (child.exitCode === null && child.signalCode === null) child.kill(sig);
    });
  }

  child.on("exit", (code, signal) => {
    if (signal) {
      // 子进程被信号结束：父进程用同一个信号结束自己，调用方看到的退出状态才一致
      process.removeAllListeners(signal);
      try { process.kill(process.pid, signal); return; } catch {}
    }
    process.exit(code ?? 1);
  });
}

// bin 字段只能写一个路径，Windows 上它必须以 .exe 结尾，所以各平台统一用这个文件名
const dest = path.join(__dirname, "bin", "native-demo-rs-direct.exe");

  fs.linkSync(src, dest);     // 硬链接：不占额外磁盘，瞬间完成

  fs.copyFileSync(src, dest); // 跨文件系统或没有权限时退回复制

写的过程中踩到的坑

有几处是读别人的代码时没注意到、自己写才撞上的：

  • 全局安装会忽略 --omit=optional（npm 10.9.4 下观察到）。我本来用 npm install -g --omit=optional 测试「子包缺失」，结果子包照样装上了。改成在普通项目里安装才复现出来。所以「用户跳过可选依赖」主要发生在项目依赖里，全局安装反而不太会遇到。
  • 占位文件不能写 shebang。 Windows 上 npm 生成命令包装（cmd-shim）时会读取 bin 文件的 shebang。按 cmd-shim 的逻辑，如果占位脚本写了 #!/bin/sh，生成的包装就会用 sh 去调用它；postinstall 把它换成 .exe 之后，这个包装应该就不能用了。这一点是推断，我只实测了不带 shebang 的版本在 Windows 上能正常运行。Claude Code 的占位文件以 echo 开头、没有 shebang，我猜是同样的原因。Unix shell 遇到没有 shebang 的可执行文件会按 sh 脚本执行，所以在 Linux、macOS 上照样能输出提示。
  • Windows 上要写全 tar.exe 的路径。 Windows 10 起自带的 tar 是 bsdtar，能解 zip；但在 Git Bash 里，PATH 上排在前面的是 GNU tar，它解不了 zip。下载型解压时用 %SystemRoot%\System32\tar.exe 才稳。
  • 测试环境里的 IPv4 / IPv6。 本地测试都通过，到 CI 上却连不上 verdaccio：原因应该是 runner 上 localhost 解析成了 ::1，而脚本访问的是 127.0.0.1；macOS 上用 Python 的 http.server 模拟下载源也出现了同样的连接失败。两处都改成显式绑定 127.0.0.1 后，CI 就通过了。

这么做的代价

npm 分发不是没有成本，选型时需要心里有数。

多一层 Node 进程。 每次执行 lark-cli，先启动 Node 跑 run.js，再由它启动原生二进制。Biome、Codex 也一样。我在本机各跑 5 次 --version 对比：经过 npm 外壳共 0.26 秒，直接调用二进制 0.13 秒，每次多出约 25ms。对交互式使用无感，但如果在脚本里循环调用几千次，这部分开销会被放大。需要时可以直接调用 node_modules/@larksuite/cli/bin/lark-cli，绕过外壳。如果你是发布者，也可以学 Claude Code、Bun，在 postinstall 里把原生二进制放到 bin 指向的位置，彻底去掉这层开销，代价是更依赖安装脚本。

对 Node 版本有要求。 lark-cli 的包里声明了 "engines": { "node": ">=16" }。只想用 CLI 的运维人员，可能要为此专门装一个 Node。对这类用户，直接下载 GitHub Release 或 go install 反而更简单，lark-cli 也保留了从源码 make install 的方式。

供应链风险集中在 postinstall。 postinstall 能执行任意代码，这是近年 npm 投毒事件的常见入口之一，所以很多团队会默认 --ignore-scripts。lark-cli 的应对是 checksum 校验 + 域名白名单 + run.js 补装，让「禁用脚本」也能正常使用。如果你自己要采用这种模式，校验值必须随 npm 包一起发布，不能从下载源同一处获取，否则校验就失去了意义。

两个版本号要保持同步。 npm 包版本和 GitHub Release tag 必须一致，发布流水线里任何一步失败（例如 Release 产物还没上传完，npm 包已经发出去了），用户就会装到一个下载 404 的版本。

什么时候值得这样做

如果你在用 Go 或 Rust 写 CLI，先按目标用户判断要不要上 npm：

  • 用户主要是前端、全栈开发者，或者 AI 编程工具的使用者：值得发一个 npm 包，npx 一行命令的体验很难被替代。
  • 用户主要是运维、SRE、服务端开发者：GitHub Releases + 安装脚本 + Homebrew 通常就够了，再加 npm 收益不大。
  • 两类用户都有：像 lark-cli 一样，npm 作为推荐方式，同时保留 Release 下载和源码编译。

决定要上之后，再按团队情况选实现。先看一张简化的决策图：

  • 想省事、已经有 GitHub Release 流程：用下载型。Go 项目学 lark-cli，GoReleaser 产出多平台压缩包和 checksums.txt，npm 包里放下载、校验、转发三个脚本；Rust 项目直接用 cargo-dist 生成。
  • 用户在企业内网、或团队默认禁用 install 脚本：用子包型，学 Biome / esbuild；想少管几个包名，学 Codex 的别名版本。
  • Rust 项目的 Linux 产物：没有特殊理由就编译成 musl 静态版本，像 Codex 一样省掉 glibc / musl 的判断。
  • 启动器：照着 Codex 的写法处理信号转发和退出状态，并通过环境变量告诉二进制它由 npm 管理，关掉自我更新。

回到开头的问题：Go、Rust 写的 CLI 用 npm 分发，并不是因为 npm 在技术上更合适，而是因为用户已经在那里了。npm 包在这里只是一层壳，壳里装哪种语言的二进制都可以。语言决定程序怎么写，分发渠道应该看用户怎么装。
