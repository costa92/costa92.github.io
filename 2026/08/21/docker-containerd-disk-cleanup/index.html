根分区 98%：Docker/containerd 排查复盘

 2026-08-21  linux Docker containerd BuildKit 磁盘管理
Docker containerd BuildKit 磁盘管理 故障排查 Linux 运维

环境

项值
系统Ubuntu 24.04（GLIBC 2.39，内核 6.8）
根分区/dev/nvme0n1p5，468G，已用 434G，可用 11G（98%）
数据盘/dev/sda，916G，挂载在 /mnt/data

起因不是磁盘告警，而是一个装不上的 npm 包。

一、引子：codex 装不上，顺手发现磁盘要满

第一次报错发生在运行时：

Error: Missing optional dependency @openai/codex-linux-x64

optional dependency 缺失，通常意味着安装阶段就没装上。重装时才看到真正的错误：

npm error ENOTEMPTY: directory not empty, rename
'.../node_modules/@openai/codex' -> '.../node_modules/@openai/.codex-m3xzPeyC'

npm 更新一个包时的做法是：先把旧目录 rename 成 .<name>-<随机串> 作为临时备份，装好新的再删备份。上一次安装被中断，备份目录 .codex-m3xzPeyC 留在了那里，此后每一次安装的 rename 都会撞上这个非空目录而失败——于是那个 323MB 的平台二进制包永远装不上，而外层的 @openai/codex 看起来”装好了”，只是跑起来才报缺依赖。

修复很直接：rm -rf 掉残留目录后重装，13 分钟（下载 323MB），codex --version 输出 codex-cli 0.149.0。

这个小插曲本身不重要，重要的是下载 323MB 的过程让我顺手看了一眼 df：根分区只剩 11G。

二、第一课：你的 du 可能在骗你

开始做容量分析，第一条命令是常规的：

du -x -d1 /home/username

输出看起来很正常，只是——加不起来。/home 顶层统计是 242G，而列出来的子目录加总只有约 57G。差了 185G。

这个信号必须停下来。 一个目录的总量和它子项之和对不上，只有几种可能：

  1. 有子目录因权限读不到（会有 stderr 报错，且通常伴随 Permission denied）
  2. 硬链接被去重（du 默认行为，但一般不会造成如此巨大的偏差）
  3. 挂载点跨越（已经用 -x 排除）
  4. 你看到的不是 du 的真实输出

答案是第 4 种。这台机器上装了一个叫 rtk 的 CLI 代理，通过 Claude Code 的 hook 自动重写命令以节省 token——它会对输出做过滤和压缩。结果是 ~/code(50G)、~/.config(42G)、~/.local(32G)、~/.nvm、~/onedrive(10G) 这些几十 G 的行全部被吃掉了，只留下零碎小目录。

如果没注意到加总对不上，接下来的每一个判断都会建立在一份被删了大半的数据上。

绕过方式是让命令不经过重写层：

# 方式一：绝对路径直接调用真实二进制
/usr/bin/du -x -d1 /home/username | /usr/bin/sort -rh

# 方式二：rtk 自带的透传（注意它不接受 shell 管道）
rtk proxy du -x -d1 /home/username

教训：做容量分析时，任何会改写命令的中间层——别名、包装脚本、shell hook、AI 工具链——都可能让你看到一个失真的世界。而校验方法是免费的：总量必须等于子项之和。

到这里第一名已经很清楚：BuildKit 构建缓存 51.49GB，可回收 47GB。这是典型的”没人管的增长项”——每次 docker build 都往里加。Docker 内置的 builder 默认开着 GC，当前文档给的默认上限是 defaultKeepStorage: 20GB（旧版本的默认值按磁盘容量比例计算），但这台机器的缓存还是涨到了 51GB，说明不能指望默认策略。要让它自己管住，得在 daemon.json 的 builder.gc 里显式配置上限；否则就得靠人定期 prune。

清理执行：

下面的 prune 会删除当前 daemon/builder 认为“不再使用”的资源；-a 会扩大删除范围，执行前先用 docker system df -v 和 docker volume ls -qf dangling=true 逐项确认。缓存和无引用镜像删除后通常无法恢复，只在确认不需要它们时执行。

docker builder prune -af          # 删除当前 builder 的全部未使用构建缓存
docker image prune -af            # 删除全部未使用镜像；确认不需要回滚镜像后再执行
# 仅删除已确认不再需要的匿名卷；不要把具名卷直接交给 volume prune
sudo apt-get clean                # /var/cache/apt
sudo rm -rf /var/crash/*
sudo journalctl --vacuum-size=500M   # 释放 3.4G
rm -rf ~/.cache/{uv,go-build,pip,puppeteer,ms-playwright}  # 确认这些缓存可重建

刻意保留的东西：两个具名卷 docker_app_data 和 docker_collab_outbox。它们当时处于 dangling 状态（没有容器引用）。Docker 23.0 起 docker volume prune 默认只删匿名卷，加 -a/--all 才会连具名卷一起删；但旧版本的 Docker 和顺手加上的 -a 都会把它们带走。具名卷之所以被人为命名，通常就是因为它承载真实业务数据；匿名卷是运行时副产品，具名卷不是。dangling 只说明此刻没容器挂着它，不说明数据没用。

原则：批量清理时，匿名资源可以按规则删，具名资源必须逐个确认。

结果：11G → 84G 可用，98% → 82%。

四、核心谜题：明明配了 data-root，根分区为什么还是满的

清理完毕，但真正让我在意的是 /var/lib/containerd 那 60G。因为这台机器早就把 Docker 数据盘搬走了：

// /etc/docker/daemon.json
{
  "runtimes": { "nvidia": { "args": [], "path": "nvidia-container-runtime" } },
  "data-root": "/mnt/data/docker-data"
}

而且配置确实生效——docker info 显示 Docker Root Dir: /mnt/data/docker-data，实测该目录 35G。既然搬走了，为什么根分区还被吃掉 60G？

答案在于这台机器上的 dockerd / containerd / BuildKit 可以看成三层，而 data-root 只覆盖其中一层。镜像和构建缓存落在哪一层，取决于 Docker 是否启用了 containerd image store（containerd snapshotter）。

dockerd                              ← data-root 管这一层
  │  镜像元数据、容器读写层、卷
  │  （/mnt/data/docker-data）
  │
  └─ 委托给 → containerd (systemd 独立服务)   ← 自己的 root，data-root 管不着
                │  content store / snapshotter
                │  （/var/lib/containerd）
                │
                └─ 本次环境的 BuildKit 构建缓存落在这里

关键点：dockerd 自己不管理底层运行时。现代 Docker 安装把容器生命周期委托给一个独立的 systemd 服务 containerd，两者通过 socket 通信：

$ ps -eo pid,args | grep containerd
... dockerd -H fd:// --containerd=/run/containerd/containerd.sock

这个 containerd 是独立进程、独立配置、独立数据目录。它的 root 由 /etc/containerd/config.toml 决定，跟 daemon.json 里的 data-root 毫无关系。你把 dockerd 的家搬到数据盘，containerd 依然待在 /var/lib/containerd。

在本次环境中，BuildKit 的构建缓存确实存在 containerd 的存储层里：

路径实测
/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots7568M
/var/lib/containerd/io.containerd.content.v1.content/blobs2171M

（以上为清理之后的数据。）

所以本次 47G 的可回收构建缓存从头到尾就躺在根分区上，data-root 搬不走它。

这正是 containerd image store 的行为。Docker 官方文档写明，启用它之后镜像内容和快照由 containerd 存在自己的数据目录里，data-root 不会作用到这部分，需要单独配置 containerd 的目录；而 Docker Engine 29.0 起，新安装默认就启用 containerd image store。确认方法：

docker info -f '{{ .DriverStatus }}'
# [[driver-type io.containerd.snapshotter.v1]] 表示已启用

如果用的是传统的 overlay2 存储驱动，镜像和构建缓存仍在 data-root 下，本文的结论不适用。排查时以 docker info、builder 配置和实际目录占用为准。

五、最小改动迁移 containerd

清理只是把水位降下来，构建缓存会重新长回去。要根治，得把 containerd 的 root 也挪到数据盘。

先读配置，不要先动手

第一步是看 /etc/containerd/config.toml 现状。我用 grep 找 root / snapshotter 关键字，没有匹配，于是一度认为”这台机器没有 containerd 配置文件”。

这是错的。文件存在，886 字节，是 Docker 官方包附带的。grep 没命中只是因为相关行被注释了，而我的模式没考虑前导 #。

小教训：grep 没命中不等于文件不存在。判断文件是否存在用 ls / test -f，不要用内容匹配的结果去反推。

实际内容的关键部分：

disabled_plugins = ["cri"]

#root = "/var/lib/containerd"
#state = "/run/containerd"

即：root 被注释掉，走编译内置的默认值 /var/lib/containerd。

关键决策：不要用 containerd config default

网上常见做法是 containerd config default > /etc/containerd/config.toml 然后改 root。这里不能这么做。

那条命令会生成一份 296 行的完整配置，其中包含当前明确被 disabled_plugins = ["cri"] 关掉的 CRI 插件及一大堆默认参数。用它覆盖现有的 886 字节配置，等于凭空引入几百行你没审过的配置项，把一次单参数变更变成一次全量配置替换。风险面无谓地扩大了。

最小改动只需一行：

 disabled_plugins = ["cri"]
 
-#root = "/var/lib/containerd"
+root = "/mnt/data/containerd"
 #state = "/run/containerd"

state = /run/containerd 保持不动——那是 tmpfs，重启即空，不占磁盘，没有迁移的必要。

执行步骤

先确认目标盘已经挂载、空间足够，并确认当前 containerd 服务确实使用这份配置；如果目标文件系统不支持 ACL 或 xattr，需要相应调整 rsync 参数。

# 1. 先备份配置
sudo cp /etc/containerd/config.toml /etc/containerd/config.toml.bak-20260821

# 1.5 确认目标盘和目标目录可用
findmnt /mnt/data
df -h /mnt/data /var/lib/containerd
sudo systemctl cat containerd | grep -E -- '--config|ExecStart'

# 2. 单行替换
sudo sed -i 's|^#root = "/var/lib/containerd"$|root = "/mnt/data/containerd"|' \
  /etc/containerd/config.toml

# 3. 停服务（注意 docker.socket 也要停，否则会被 socket 激活拉起）
sudo systemctl stop docker.socket docker containerd

# 4. 同步数据，保留硬链接/ACL/xattr
sudo mkdir -p /mnt/data/containerd
sudo rsync -aHAX /var/lib/containerd/ /mnt/data/containerd/
sudo rsync -aHAXni --delete /var/lib/containerd/ /mnt/data/containerd/  # -n 只演练，-i 逐项列出差异；应无输出

# 5. 启动
sudo systemctl start containerd
sudo systemctl start docker

# 6. 验证通过后再删旧目录 —— 不要立刻删

几个实测细节：

  • 停 docker 耗时较长，因为要优雅关闭 10 个容器，其中含 3 个 kind 节点。
  • rsync 9.6G 约 2 分钟。
  • rsync 的 -aHAX 中 -H 尤其重要：containerd 的 content store 里存在大量硬链接，丢掉硬链接会让占用凭空膨胀。

旧目录先不删是这里最重要的一条纪律。迁移完成后 /var/lib/containerd 仍然原样存在，一旦新目录有问题，可执行下面的回滚步骤：停止 Docker/containerd，把 root 改回 /var/lib/containerd，再启动 containerd 和 Docker。确认新目录运行稳定、进程不再打开旧目录后，再执行 sudo rm -rf /var/lib/containerd 释放那 9.6G。多占一段时间磁盘，换来随时可用的回滚路径。

回滚示例（把配置中的 root 改回旧路径后执行）：

sudo systemctl stop docker.socket docker containerd
sudo systemctl start containerd
sudo systemctl start docker

六、我在这次排查里犯的三个错误

错误一：把 /var/lib/containerd 判定为 k3s 的镜像层

最初看到 60G，我的第一反应是”这是 k3s 的镜像层”。这个判断有两处错误。

归属错了。 这台机器上确实跑着 k8s 相关的东西，所以”containerd = k8s 的运行时”这个联想很自然，但它只是联想，不是证据。查证只用了两步：

# 第一步：这个 containerd 是谁在用？
$ ps -eo pid,args | grep containerd
... dockerd -H fd:// --containerd=/run/containerd/containerd.sock

dockerd 显式指向了系统的 /run/containerd/containerd.sock，说明 /usr/bin/containerd 服务的是 Docker。

# 第二步：更硬的证据 —— 看 namespace
$ ctr namespace ls
moby
moby_history

containerd 用 namespace 隔离不同调用方：Docker 用 moby，Kubernetes 用 k8s.io。这里只有 moby 和 moby_history，没有 k8s.io。结论很明确：这份数据属于 Docker，跟 k8s 无关。

补充事实：这台机器上确实存在第二个 containerd 二进制 /usr/local/bin/containerd，服务于 kubelet 的 k8s.io namespace，与前者互不影响。而我猜测的 k3s 数据目录 /var/lib/rancher 实际只有 4K。

数量也过时了。 60G 是清理之前的数字，我却拿它去做清理之后的决策。重新测量：/var/lib/containerd 只剩 9.6G。

而这个数字反过来成了最好的交叉验证：

60G  −  49.81G（docker builder prune 报告的释放量）  ≈  10G
实测剩余：9.6G

两者基本吻合，说明那 60G 的绝大部分就是 BuildKit 构建缓存。

方法论：当你有两条独立路径能算出同一个数字时，一定要算一遍。 数字对上了，你的因果模型才算被验证过；对不上，说明模型里有你没看见的东西。

错误二：认定 restart=on-failure 的容器不会自动拉起

迁移前我记录了所有容器的重启策略，并判断：restart=on-failure 的容器在 daemon 重启后不会自动启动，需要手动 docker start。

实测证明这是错的。 docker 恢复后，10 个容器全部自动恢复，包括那 4 个 on-failure 的。

这类”我记得规则是这样”的判断成本极低、验证成本也极低，却经常不验证就写进计划。这次的代价只是多准备了一份没用上的手动启动清单，但同类错误在反方向上（以为会自动起、结果没起）就是一次静默的服务中断。

错误三：grep 没命中就断定文件不存在

已在第五节说明。归纳一下这三个错误的共同点：都是用间接信号去推断事实，而没有去直接观测事实。

我用的间接信号应该直接观测的
目录名像 k8s 的ctr namespace ls / ps 看进程参数
记忆中的 restart 策略语义重启后 docker ps 实际看一眼
grep 有没有命中ls -l 文件是否存在

七、重启暴露的定时炸弹：migration 版本漂移

迁移完成后开始验证，出现两件事。

一件是虚惊

kind 集群的 kubectl get nodes 报错：

couldn't get current server API group list: unknown

看起来很吓人，但这只是 apiserver 还没起来。稍等片刻，3 个节点全部 Ready。

教训：重启后立刻判断”坏了”往往为时过早。 分布式组件有启动顺序和就绪时间，在收敛窗口内的报错不是故障信号。急着”修”一个还在启动的系统，很容易把真问题制造出来。

一件是真问题

容器 wechat-account-app-1 陷入重启循环。日志里有两个阶段，必须分开看：

阶段一（噪音）：

dial tcp 172.18.0.3:5432: connect: connection refused
FATAL: the database system is starting up (SQLSTATE 57P03)

这是应用比 postgres 先起来的启动竞态，postgres 就绪后会自愈，不是根因。

阶段二（根因，在日志最后）：

Error: 数据库迁移失败: no migration found for version 193:
read down for version 193 .: file does not exist

查证两边的状态：

-- 数据库侧
select * from schema_migrations;
-- version = 193, dirty = f
# 镜像侧
/app/migrations 下最高只到 000192_*

结论清楚了：数据库已经被某个更新版本的应用升级到了 193，而当前镜像只带到 192。golang-migrate 启动时发现数据库版本高于自己已知的最高版本，试图 down 回滚到 192，却找不到 000193_*.down.sql 这个文件——于是启动失败。

（golang-migrate 的机制：它用 schema_migrations 表记录当前版本和 dirty 标志，迁移文件成对存在 up/down。版本落后于数据库时它需要 down 文件才能回退，缺文件就是硬失败。）

它和磁盘迁移无关

问题本身先前就存在，只是那个容器已经连续运行了 4 个小时没重启，被”进程还活着”的假象掩盖着。停 Docker 才把它暴露出来。

长期不重启的容器会掩盖配置和版本漂移。 一个在运行中的进程只证明它”启动过一次时是好的”，不证明它”现在还能启动”。镜像回滚、迁移文件缺失、配置文件被改坏、依赖的 secret 过期——这些问题都只在下一次启动时才现形。

一次计划内的重启，往往是发现这类定时炸弹的唯一机会。而如果等到机器宕机、被迫重启时才发现，你要在故障压力下同时处理宕机和一堆起不来的服务，代价完全不是一个量级。

顺带的建议：如果你的服务栈里有那种”跑了几个月没重启”的容器，主动挑一个低峰期把它重启一遍。这不是折腾，这是演练。

处置：不擅自决定

问题定位清楚了，但我没有动数据库。可选方案有两条：

  1. 补回 000193_* 迁移文件，重建镜像；
  2. 确认 193 这次变更应当废弃，手工回退 schema 到 192。

选哪条取决于 193 那次变更的业务含义，而这不是执行磁盘清理的人能判断的。所以把两个选项和证据交给业务负责人。

原则：涉及真实业务数据的修复，不由执行清理的人擅自决定。 这和前面保留具名卷是同一条原则的两个侧面——清理者的职责边界止于”可再生的数据”。

八、完整决策流程

把前面七节压缩成两条可执行流程。每个需要判断的步骤，都先核对证据再进入下一步。

阶段一：定位与清理

  1. 用 df -h 确认根分区水位。
  2. 用未被改写的 du 重测；总量和子项对不上时，先排查命令重写层。
  3. 逐层下钻，再用 docker system df 区分镜像、容器、卷和构建缓存。
  4. 只在确认影响范围后清理构建缓存和无引用镜像；匿名卷可按规则处理，具名卷逐个确认。
  5. 再清理 journal、apt 缓存、崩溃转储和可重建的用户缓存。
  6. 根分区已恢复就结束；仍紧张则进入 containerd 迁移。

阶段二：迁移与验证

  1. 用进程参数和 ctr namespace ls 确认 containerd 的归属。
  2. 只改 root 一行，停 docker.socket、Docker 和 containerd。
  3. 用 rsync -aHAX 复制数据，做一次 dry-run 校验无差异。
  4. 先启动 containerd，再启动 Docker，等待组件完成收敛。
  5. 如果有服务起不来，区分启动竞态噪音和日志末尾的真实根因；涉及业务数据时交给负责人决定。
  6. 全部恢复后，用 lsof 等证据确认进程不再持有旧目录，最后才删除旧目录。

两条支线值得单独强调：

  • 阶段一第 2 步（du 对不上 → 排查重写层 → 重测）是整件事的前提。数据不可信，后面的判断都站不住。
  • 阶段二第 5 步（起不来的服务 → 是否涉及业务数据 → 交给负责人）划出了清理者的职责边界：可再生的数据可以删，业务数据只负责定位和上报。

九、结果与可复用的原则

最终：根分区可用空间从 11G（98%）变为 93G（80%），累计释放 82G。

旧目录 /var/lib/containerd 是最后删的。在删之前，用四项证据确认了 containerd 已完全切换到新目录：

检查结果
grep ^root /etc/containerd/config.toml/mnt/data/containerd
lsof -p $(pgrep -x containerd)只打开新目录，未持有旧目录任何文件
两边 meta.db 的 mtime旧目录停在迁移时刻，新目录持续更新
systemctl is-active + docker ps服务 active，10 个容器正常

其中 lsof 那条是最硬的证据：配置写了什么是意图，进程实际打开了什么才是事实。

删除前还做了两项防呆确认——readlink -f 确保新目录不是指回旧目录的符号链接，stat -c %d 对比设备号（2048 vs 66307）确认两者在不同文件系统上、是真实独立副本。否则一条 rm -rf 会把刚迁移好的数据一起带走。

沉淀下来的几条原则：

原则来自哪个坑
父目录总量 ≠ 子项之和 → 先怀疑工具链，不要怀疑文件系统rtk 过滤掉 du 输出
任何改写命令的中间层都可能让你看到失真的数据同上
用间接信号推断，不如直接观测一次containerd 归属 / restart 策略 / grep
grep 没命中 ≠ 文件不存在containerd config.toml
有两条独立路径能算出同一个数，就都算一遍做交叉验证60 − 49.81 ≈ 10，实测 9.6
配置变更取最小 diff，不要用 config default 全量覆盖containerd 迁移
迁移后旧数据先留着，验证通过再删rsync 迁移
批量清理只删匿名资源，具名资源逐个确认两个具名卷
重启后立刻判定”坏了”往往为时过早kind apiserver
长期不重启的容器会掩盖版本漂移，计划内重启是发现它们的唯一机会migration 193
涉及业务数据的修复交给负责人，不擅自决定migration 193

关于 Docker 磁盘占用的一条结构性结论，值得单独记住：

daemon.json 里的 data-root 只搬走 dockerd 自己那一层。启用 containerd image store 时，底层 containerd 是独立服务、独立配置、独立数据目录，镜像和 BuildKit 构建缓存都落在 containerd 的 snapshotter 和 content store 里。要把本机 Docker 相关数据彻底挪出根分区，需要同时核对并迁移两处；用 overlay2 存储驱动的环境不适用这条结论。

附：可复用速查表

容量定位

# 绕过可能存在的命令重写层，用绝对路径
/usr/bin/du -x -d1 / | /usr/bin/sort -rh | head -20
/usr/bin/du -x -d1 /var/lib | /usr/bin/sort -rh | head -20

df -h                        # 分区水位
du -x -d1 ~/.cache | sort -rh    # 开发机的重灾区

校验：顶层数字必须约等于子项之和，对不上就是数据有问题。

Docker / containerd 归属确认

docker system df                 # 分类型占用与可回收量
docker system df -v              # 逐镜像/卷/缓存明细
docker info | grep "Docker Root Dir"
docker info -f '{{ .DriverStatus }}'   # 是否启用 containerd image store

ps -eo pid,args | grep containerd   # dockerd 委托给哪个 containerd
ctr namespace ls                    # moby = Docker，k8s.io = Kubernetes
which -a containerd                 # 可能存在多个二进制

清理

docker builder prune -af         # 构建缓存，通常是最大头
docker image prune -af           # 无引用镜像
docker volume ls -qf dangling=true   # 先列出来看；volume prune 不加 -a 时只删匿名卷（Docker 23.0+）

sudo apt-get clean
sudo journalctl --vacuum-size=500M
sudo rm -rf /var/crash/*
rm -rf ~/.cache/{uv,go-build,pip,puppeteer,ms-playwright}

containerd 迁移

ls -l /etc/containerd/config.toml     # 先确认文件是否存在（别用 grep 判断）
cat /etc/containerd/config.toml       # 注意被注释掉的 root/state

sudo cp /etc/containerd/config.toml /etc/containerd/config.toml.bak-$(date +%Y%m%d)
# 只改 root 一行，state 在 tmpfs 上不用动

sudo systemctl stop docker.socket docker containerd
sudo rsync -aHAX /var/lib/containerd/ /mnt/data/containerd/
sudo rsync -aHAXni --delete /var/lib/containerd/ /mnt/data/containerd/   # 无输出才算一致
sudo systemctl start containerd && sudo systemctl start docker

docker ps -a                          # 验证容器全部恢复
kubectl get nodes                     # 若有 k8s，给它一点启动时间再判断
# 验证无误后才 rm -rf 旧目录

容器起不来时的排查顺序

docker logs <container> --tail 200    # 根因通常在日志最后，不在最前
docker inspect -f '{{.RestartCount}} {{.State.Error}}' <container>

读日志时区分两类信息：连接被拒、”system is starting up” 这类是启动竞态噪音；Error: / FATAL 且不再重试的那条才是根因。
