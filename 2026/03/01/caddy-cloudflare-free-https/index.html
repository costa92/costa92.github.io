Caddy + Cloudflare：免费 HTTPS 与 Tunnel 方案

 2026-03-01  linux Caddy Cloudflare HTTPS Let's Encrypt

导读
给网站上 HTTPS 不需要买证书。Caddy 自带自动 HTTPS，配合 Cloudflare 的免费 DNS，就能拿到免费、自动续期的 TLS 证书。后半部分介绍 cloudflared Tunnel：服务器没有公网 IP、或者不想开放任何入站端口时用它。

为什么选 Caddy 而不是 Nginx

我之前给好几个项目配过 Nginx + Let’s Encrypt，每次都得装 Certbot、配定时续期、处理续期失败，再往配置里塞一堆 ssl 指令。

Caddy 把这些都省了。它的设计是 HTTPS 默认开启——配置里写一个域名，Caddy 就会自动：

  1. 向 Let’s Encrypt 申请证书，失败时改用 ZeroSSL
  2. 配置 TLS
  3. 把 HTTP 80 端口的请求重定向到 HTTPS 443
  4. 在证书剩余约 1/3 有效期时自动续期（90 天的证书大约是到期前 30 天）

这些都不需要额外配置。

对比项Nginx + CertbotCaddy
HTTPS 配置手动安装 Certbot + 定时续期自动，零配置
证书续期需要自己维护定时任务内置自动续期
配置文件复杂度较高（ssl_certificate 等指令）低（写域名就行）
反向代理配置10+ 行3 行

什么时候需要 Cloudflare DNS 验证

默认情况下，Caddy 用 HTTP-01（以及 TLS-ALPN-01）验证——Let’s Encrypt 会访问你服务器的 80（或 443）端口，确认你拥有这个域名。

有两种场景这行不通：

  • 80 端口被封（比如国内部分家宽运营商）
  • 需要通配符证书（*.example.com）——HTTP-01 不支持通配符

这时候就需要 DNS-01 验证：Caddy 通过 Cloudflare API 在 DNS 里写一条临时 TXT 记录，Let’s Encrypt 查询这条记录来确认域名所有权，验证完成后 TXT 记录自动删除。

整个过程不需要开放 80 端口，也支持通配符证书。

准备工作

开始之前，确认你有：

  • 一台 Linux 服务器（Ubuntu/Debian/CentOS 均可）
  • 一个域名，DNS 托管在 Cloudflare（免费计划就够）
  • 域名的 A 记录已指向服务器 IP

💡 关于 Cloudflare 免费计划
免费计划够用。把域名的 Nameserver 改成 Cloudflare 提供的地址后，DNS 管理和 API 就都可以用了。

第一步：创建 Cloudflare API Token

Caddy 需要一个 Cloudflare API Token 来操作 DNS 记录。这里用的是 API Token（权限可限定），不是 Global API Key（权限太大）。

  1. 登录 Cloudflare Dashboard
  2. 点击右上角头像 → My Profile
  3. 左侧选择 API Tokens（也可以直接打开 API Tokens 页面）
  4. 点击 Create Token
  5. 选择 Create Custom Token
  6. 按以下配置填写：
配置项值
Token 名称caddy-dns-challenge（随便起）
PermissionsZone → Zone → Read；Zone → DNS → Edit
Zone ResourcesInclude → Specific zone → 选择你的域名
  1. 点 Continue to summary → Create Token
  2. 立即复制 Token——它只显示一次

权限按 caddy-dns/cloudflare 插件 README 的要求：Zone 读 + DNS 编辑两项。

第二步：安装带 Cloudflare 插件的 Caddy

标准的 Caddy 不包含 Cloudflare DNS 模块，需要一个带插件的版本。

先说一个前提：后面用到的 systemctl ... caddy 依赖 caddy.service 和 caddy 系统用户。最省事的做法是先按官方安装文档用 apt/yum 装好官方包（它会带上 service 文件和 /etc/caddy/Caddyfile），再把二进制换成带插件的版本。

方式 A：官网下载页（推荐新手）

  1. 打开 Caddy 下载页
  2. 选择操作系统和架构（比如 Linux amd64）
  3. 在插件搜索栏搜索 cloudflare
  4. 勾选 dns.providers.cloudflare
  5. 点击 Download 下载

下载下来就是编译好的二进制文件。

方式 B：xcaddy 命令行构建

服务器上需要有 Go 环境。xcaddy 默认构建最新版 Caddy，Go 版本要满足 Caddy go.mod 的声明（写作时 v2.11.x 声明的是 go 1.26）；Go 1.21 以上在默认的 GOTOOLCHAIN=auto 下会自动下载所需工具链。

# 安装 xcaddy
go install github.com/caddyserver/xcaddy/cmd/xcaddy@latest

# 构建带 Cloudflare 插件的 Caddy
xcaddy build --with github.com/caddy-dns/cloudflare

# 验证构建结果
./caddy version
./caddy list-modules | grep cloudflare
# 应该输出: dns.providers.cloudflare

替换官方包里的二进制

如果是通过 Debian/Ubuntu 官方包安装的 Caddy，官方文档推荐用 dpkg-divert + update-alternatives 替换，避免下次 apt upgrade 把自定义二进制覆盖掉：

sudo dpkg-divert --divert /usr/bin/caddy.default --rename /usr/bin/caddy
sudo mv ./caddy /usr/bin/caddy.custom
sudo update-alternatives --install /usr/bin/caddy caddy /usr/bin/caddy.default 10
sudo update-alternatives --install /usr/bin/caddy caddy /usr/bin/caddy.custom 50
sudo systemctl restart caddy

第三步：编写 Caddyfile

场景一：单域名反向代理

假设有一个跑在本地 8080 端口的 Web 应用，想通过 app.example.com 用 HTTPS 访问：

app.example.com {
    tls {
        dns cloudflare {env.CLOUDFLARE_API_TOKEN}
    }
    reverse_proxy localhost:8080
}

Caddy 会用 Cloudflare DNS 验证申请证书，然后反向代理到你的服务。

场景二：通配符证书

有多个子域名时，可以用一张通配符证书覆盖：

*.example.com {
    tls {
        dns cloudflare {env.CLOUDFLARE_API_TOKEN}
    }

    @app host app.example.com
    handle @app {
        reverse_proxy localhost:8080
    }

    @api host api.example.com
    handle @api {
        reverse_proxy localhost:3000
    }

    handle {
        respond "Not Found" 404
    }
}

把 Caddyfile 保存到 /etc/caddy/Caddyfile。

第四步：设置环境变量并启动

Token 要以环境变量的形式交给 Caddy 进程。手动跑 caddy run 测试时可以直接 export：

export CLOUDFLARE_API_TOKEN="你的Token"

以 systemd 服务运行时，用 drop-in 文件写进服务环境：

sudo systemctl edit caddy

在打开的编辑器中添加：

[Service]
Environment="CLOUDFLARE_API_TOKEN=你的Token"

然后启动 Caddy：

sudo systemctl daemon-reload
sudo systemctl enable --now caddy

# 检查状态
sudo systemctl status caddy

# 查看日志（启动失败时）
sudo journalctl -u caddy --no-pager -n 50

⚠️ 首次启动可能需要等一会儿
Caddy 首次启动时要向 Let’s Encrypt 申请证书，DNS 记录传播也需要时间。日志里出现 obtaining certificate 就说明流程在走，耐心等待即可。

启动成功后，浏览器访问 https://app.example.com，查看证书信息，签发者应该是 Let’s Encrypt（或 ZeroSSL）。

之后修改了 Caddyfile 不需要重启，热加载即可：

sudo systemctl reload caddy
# 或者：sudo caddy reload --config /etc/caddy/Caddyfile

常见问题排查

证书申请失败

# 检查 Cloudflare Token 是否有效
curl -X GET "https://api.cloudflare.com/client/v4/user/tokens/verify" \
    -H "Authorization: Bearer 你的Token" \
    -H "Content-Type: application/json"
# 返回 "status": "active" 说明 Token 有效

Token 有效但仍然失败时，检查权限是否同时包含 Zone Read 和 DNS Edit，以及 Zone Resources 是否选中了对应域名。

端口冲突

# 检查 80 和 443 端口是否被占用
sudo ss -tlnp | grep -E ':80|:443'
# 如果有其他服务占用，先停掉它

DNS 未指向服务器

# 确认 A 记录是否正确
dig app.example.com +short
# DNS 记录为"仅 DNS"（灰色云朵）时，应返回服务器公网 IP

如果 DNS 记录开了 Cloudflare 代理（橙色云朵），这里返回的是 Cloudflare 的 IP，属于正常现象。

浏览器提示”重定向次数过多”

DNS 记录开了 Cloudflare 代理、而 Cloudflare 的 SSL/TLS 加密模式是 Flexible 时，Cloudflare 用 HTTP 回源，Caddy 又把 HTTP 重定向回 HTTPS，就会循环。源站已经有有效证书，把加密模式改成 Full (strict) 即可。

完整配置文件参考

替换域名和端口号后保存为 /etc/caddy/Caddyfile：

# 全局配置
{
    email your-email@example.com
}

# 主站
example.com {
    tls {
        dns cloudflare {env.CLOUDFLARE_API_TOKEN}
    }
    root * /var/www/html
    file_server
}

# 应用反向代理
app.example.com {
    tls {
        dns cloudflare {env.CLOUDFLARE_API_TOKEN}
    }
    reverse_proxy localhost:8080
}

关于 email 配置
email 是 ACME 账户的联系邮箱。注意 Let’s Encrypt 已在 2025 年 6 月停止发送证书到期提醒邮件，不能再把它当续期失败的兜底；续期是否正常要看 Caddy 日志，或者另外做证书到期监控。

进阶：用 cloudflared Tunnel 摆脱公网 IP

前面的方案有一个前提：服务器有公网 IP，且 443 端口可访问。但很多场景不满足——家里的 NAS、公司内网的测试机、80/443 被封的家宽……

这时候可以用 Cloudflare 的另一个免费服务：cloudflared Tunnel。frp 和 ngrok 干的是类似的事，文末有三者的对比。

它解决了什么问题

传统方案的流量路径：

用户 → 你的公网 IP:443 → Caddy → 你的应用

cloudflared Tunnel 把连接方向反过来：

用户 → Cloudflare 边缘节点 → cloudflared 出站隧道 → Caddy → 你的应用

cloudflared 从你的服务器主动向外建立加密连接（类似 SSH 反向隧道），Cloudflare 再把用户请求通过这条隧道转进来。服务器不需要公网 IP，防火墙也不需要开任何入站端口。

安装 cloudflared

Debian / Ubuntu：

curl -L https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64.deb \
  -o cloudflared.deb
sudo dpkg -i cloudflared.deb

CentOS / RHEL：

curl -L https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-x86_64.rpm \
  -o cloudflared.rpm
sudo rpm -ivh cloudflared.rpm

安装完成后验证：

cloudflared --version

创建 Tunnel

一共四步：登录认证 → 创建隧道 → 配置 DNS 路由 → 运行。下面是用命令行管理的本地隧道（locally-managed tunnel），也可以在 Cloudflare Zero Trust 控制台里图形化创建。

# 1. 登录认证（会弹出浏览器让你授权）
# 无图形界面的服务器会输出一个 URL，复制到本地浏览器打开即可
cloudflared tunnel login

# 2. 创建 Tunnel（会输出一个 UUID，记住它）
cloudflared tunnel create my-tunnel

# 3. 把域名指向这条 Tunnel（会自动创建一条 CNAME 记录）
cloudflared tunnel route dns my-tunnel app.example.com

# 4. 运行 Tunnel
cloudflared tunnel run my-tunnel

第 1 步执行后，认证证书保存在 ~/.cloudflared/cert.pem；第 2 步创建的隧道凭证在 ~/.cloudflared/<TUNNEL_UUID>.json。

编写 cloudflared 配置文件

创建 ~/.cloudflared/config.yml：

tunnel: <你的TUNNEL_UUID>
credentials-file: /root/.cloudflared/<你的TUNNEL_UUID>.json  # 换成实际的 home 目录

ingress:
  - hostname: app.example.com
    service: http://localhost:80
  - hostname: api.example.com
    service: http://localhost:80
  # 兜底规则（必须有）
  - service: http_status:404

关于兜底规则
ingress 的最后一条必须是不带 hostname 的兜底规则，否则 cloudflared 会拒绝启动，通常设为返回 404。

api.example.com 也要像第 3 步那样执行一次 cloudflared tunnel route dns。写好配置后，先验证语法：

cloudflared tunnel ingress validate

Caddy + cloudflared 的配合方式

分工：

  • cloudflared：负责与 Cloudflare 网络之间的加密隧道
  • Caddy：负责本地的反向代理和路由

访客看到的 HTTPS 由 Cloudflare 在边缘终结，Caddy 在本地只需要监听 HTTP。Caddyfile 可以简化成：

http://app.example.com {
    reverse_proxy localhost:8080
}

http://api.example.com {
    reverse_proxy localhost:3000
}

地址前的 http:// 不能省。Caddy 对带域名的站点地址默认使用 HTTPS 和 443 端口；只写全局的 auto_https off 并不会改变这一点，只会关掉证书申请和跳转，结果是 443 上没有可用证书。显式写 http:// 后，Caddy 只在 80 端口提供 HTTP，也不会为这两个站点申请证书——正好对应上面 ingress 里的 http://localhost:80。cloudflared 回源时会保留原始的 Host，所以按域名区分站点照常工作。

这样既没有 tls 块，也不需要 DNS 插件。

设为系统服务（开机自启）

# 用 sudo 安装时 $HOME 是 /root，配置不在 /root 下就要用 --config 显式指定
sudo cloudflared --config /home/<USER>/.cloudflared/config.yml service install

# 启动并设为开机自启
sudo systemctl enable --now cloudflared

# 查看日志
sudo journalctl -u cloudflared -f

两种方案怎么选

对比项Caddy + DNS 验证Caddy + cloudflared Tunnel
是否需要公网 IP需要不需要
是否需要开端口需要 443（和可选的 80）不需要任何入站端口
TLS 证书管理Caddy 自动申请和续期Cloudflare 边缘自动处理
额外安装Caddy + Cloudflare 插件Caddy + cloudflared
服务器 IP 暴露不开代理时 DNS 记录中可见不暴露
适合场景有公网 IP 的 VPS/云服务器家庭宽带、NAT 后面、内网服务器

我的建议：服务器有固定公网 IP，用前面的 DNS 验证方案更直接；在家里搞 homelab 或者服务器在内网，用 cloudflared Tunnel。

cloudflared vs frp vs ngrok

做内网穿透的工具不止 cloudflared 一个，frp 和 ngrok 是另外两个常见选择。我三个都用过，说说实际体感。

frp 是国人开发的开源项目（Apache 2.0 协议，GitHub 上十万以上 star），功能最全——TCP、UDP、HTTP、HTTPS 甚至 P2P 都支持。代价是得自己准备一台有公网 IP 的 VPS 跑 frps 服务端，配置也比较多。适合需要穿透 UDP 流量（比如游戏服务器）或者想完全掌控数据链路的人。

ngrok 上手最快，一行命令就能跑起来，还自带请求审查面板，调试 webhook 很好用。但免费版限制不少：每月 1GB 出站流量、2 万次 HTTP 请求、1 个静态域名，浏览器访问时还会先弹一个警告页。正式使用要上付费计划（Hobbyist 计划年付 $8/月，月付 $10）。

cloudflared Tunnel 在 Web 场景下最合适：Tunnel 本身免费、不按流量计费，自带 Cloudflare 的 DDoS 防护，源站 IP 不暴露。前提是域名托管在 Cloudflare，且流量仍受 Cloudflare 服务条款约束——经它的 CDN 大量分发视频等大文件是受限的。

对比项cloudflared Tunnelfrpngrok
费用免费，不按流量计费开源免费，但需自备 VPS（~$5/月起）免费版 1GB/月，付费 $8/月起
是否需要中转服务器不需要（Cloudflare 托管）需要（自建 frps）不需要（ngrok 托管）
安全防护Cloudflare DDoS 防护，可叠加 WAF 和 Accesstoken 认证、TLS，其余需自行加固OAuth / IP 白名单等（部分为付费功能）
支持的协议HTTP/HTTPS；TCP、SSH、RDP 需访问端也装 cloudflared 或 WARPHTTP/HTTPS、TCP、UDP、KCP、P2PHTTP/HTTPS、TCP（不支持 UDP）
上手难度中等（需配置域名和 DNS）较高（需自建服务端 + 写配置文件）最低（一行命令启动）
源站 IP 隐藏不暴露暴露中转 VPS 的 IP隐藏在 ngrok 域名后
适合场景长期运行的 Web 服务游戏服务器、UDP 穿透、完全自主可控本地调试、临时演示、webhook 测试

我的选择：长期运行的 Web 服务用 cloudflared，需要 UDP 或完全自主可控用 frp，临时调试用 ngrok。
