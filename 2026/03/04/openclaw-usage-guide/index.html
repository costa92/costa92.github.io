OpenClaw 接本地 Ollama 小模型：一句 pong 先付 1.6 万 token，qwen2.5-coder 80 次没调成一次工具

 costalong  2026-03-04  更新于 2026-11-24  Coding-Agent 自动化 AI Agent OpenClaw

这篇原来是一份 OpenClaw 的命令手册，内容基本是把官方文档按使用顺序重排了一遍。手册类的东西官方文档写得更全，我留着它意义不大。这次我换了个问题来测：把 OpenClaw 接到本机 Ollama 上的小模型，它到底能不能干活。具体量三件事：每次请求在用户消息之前固定塞了多少 token；在几道固定的小任务上，几个 7B/8B 级本地模型的成功率是多少；tools.profile、allow、alsoAllow 几种写法组合起来，最后模型手里到底剩哪些工具。

全部数据来自 2026-11-25 这一天在我自己桌面机上的运行，脚本和原始结果放在 blog-go-example/openclaw-local-ollama。

测试环境和观测方法

项目配置
OpenClaw2026.11.9（0032b1d），npm install openclaw@2026.11.9 装在一个临时目录里，HOME 也指向那里，没有全局安装
Node24.22.2
Ollama0.35.0，systemd 服务，服务端参数没改
模型qwen2.5-coder:3b、qwen2.5-coder:7b、llama3.1:8b、gemma4（8B），都是 Ollama 库里的 Q4_K_M
显卡RTX 3060 12GB，驱动 580.178.04，桌面程序常驻占 3G 左右
系统Ubuntu 26.04.1

初始化用的是非交互 onboard，只连本机 Ollama，不起网关服务、不连任何聊天渠道：

openclaw onboard --non-interactive --accept-risk --mode local --auth-choice ollama \
  --skip-channels --skip-daemon --no-install-daemon --skip-health \
  --skip-hooks --skip-search --skip-skills --skip-ui

它扫了一遍本机已拉取的模型写进 models.providers.ollama.models，每个模型的 contextTokens 都是 32768，tools.profile 写的是 full，默认模型挑了最小的 qwen2.5-coder:0.5b。我把默认模型改成 3b，所有测试都用 openclaw agent --local 跑嵌入式单轮，每次一个新的 --session-id。

装好之后第一个 config set 就报错了：No safe OpenClaw temp root is available，原因是我的临时目录是组可写的。OpenClaw 2026.11.9 会检查状态目录的每一级父目录，组或其他人可写又没有粘滞位就拒绝读配置。chmod go-w 之后正常。onboard 那一步没有这个检查，所以是装完才撞上。

要知道 OpenClaw 发给模型的到底是什么，光看它的日志不够。我写了一个只用 Python 标准库的反向代理，监听 11435 端口转发到 Ollama，把 models.providers.ollama.baseUrl 指过去。代理记录每个 /api/chat 请求里的工具名单、系统提示词字符数、num_ctx，以及 Ollama 返回的 prompt_eval_count 和模型发出的原生 tool_calls。OpenClaw 的 --json 输出里还有一份 systemPromptReport，列了注入了哪些工作区文件、多少个 skill、工具 schema 多长，两边对着看。

用 prompt_eval_count 计数之前我先确认了一件事：同一个请求连发两次，第二次命中 Ollama 的前缀缓存，预填充耗时从 4.58 秒降到 0.03 秒，但 prompt_eval_count 两次都是 15,943。这个字段报的是完整提示词长度，不受缓存影响，可以直接当开销用。

一句 pong 之前已经有 15,956 个 token

测试消息是 Reply with the single word: pong，用户这边只有几个 token。默认配置第一次会话，qwen2.5-coder:3b 收到的提示词是 15,956 个 token，构成如下：

  • 系统提示词 47,066 个字符，其中工作区文件 19,711 个字符：AGENTS.md 7,144、BOOTSTRAP.md 7,475、SOUL.md 1,526、IDENTITY.md 1,453、USER.md 1,136；
  • 23 个 bundled skill 的说明，7,750 个字符；
  • 直接发给模型的 16 个工具 schema，序列化后 20,371 个字符：read、write、edit、apply_patch、exec、process、openclaw_ls、message、web_fetch、memory_search、memory_get、sessions_yield、openclaw，外加 tool_search、tool_describe、dispatch_action 三个调度工具；
  • 另有 51 个工具（browser、canvas、sessions_spawn、image_generate 等）标为 deferred，schema 不进请求，模型要用时先通过 tool_search 找。

我按顺序一项项砍掉，看每一项值多少 token（qwen2.5 的分词器）：

配置发给模型的工具数系统提示词字符prompt token
onboard 默认（full，23 个 skill，含 BOOTSTRAP.md）1647,06615,956

skills.allowBundled: [] 关掉 bundled skill 后还剩 2 个 skill 条目，941 个字符；到 minimal 时变成 0。最后一行的 3,352 个 token 是 OpenClaw 自己的系统提示词加三个调度工具，工作区和 skill 都砍光之后剩下的就是这些。

BOOTSTRAP.md 是首次运行的引导文件，OpenClaw 只在引导完成之前注入它。我在消融里删过一次，后来把整个工作区从备份拷回来，文件就在磁盘上，systemPromptReport 里却不再列它，系统提示词 39,123 个字符，prompt 14,140 个 token。所以正常用了一段时间之后，默认配置的固定开销是 1.4 万左右，第一次会话是 1.6 万。

换模型之后数字不一样，因为分词器不同，工具名单也不同：

模型首轮 prompt token发给模型的工具数
qwen2.5-coder:3b15,95616
qwen2.5-coder:7b15,95616
llama3.1:8b15,42616

gemma4 在 onboard 写出的配置里标了 input: ["text", "image"]，OpenClaw 多给了它 computer 和 view_image 两个工具，工具 schema 涨到 27,503 个字符。

llama3.1:8b 那一轮回 pong 时先调了一次 message 工具，所以有三次请求：15,426、11,481、11,584。后两次消息更多，token 反而少了 4 千。我把第二次请求原样重放给 Ollama，还是 11,481，日志里 truncated = 0，不是截断。原因在 llama3.1 的 Ollama 模板里：{{- if and $.Tools $last }}，工具定义只渲染进最后一条 user 消息。工具调用之后最后一条是 tool 结果，工具定义整段不出现在提示词里，模型在第二步看不到 schema。这是模型模板的行为，换任何 Agent 框架都一样。

这么大的固定开销，单次请求的耗时没有想象中糟。OpenClaw 把当前时间写在用户消息开头（[Wed 2026-11-25 09:35 GMT+8] ...），系统提示词和工具定义本身不变，前缀缓存能命中：模型已在显存里时，同样的 pong 第二次只用了 1.8 秒，冷启动那次是 25 秒，其中预填充 4.58 秒。缓存命中的条件见 系统提示词开头加个时间戳，Ollama 首字延迟从 37ms 涨到 3 秒。

12G 显卡上，上下文窗口两头都不够

OpenClaw 给每个 Ollama 模型写的 contextTokens 是 32768，请求里的 num_ctx 也就是 32768。它自己在发请求前会估一次提示词长度，结果记在 contextBudgetStatus 里。qwen2.5-coder:3b 那次估的是 21,985 个 token，比实际的 15,943 多估了 38%；预算按 32768 减去 8192 的输出预留算，剩 2,591。

llama3.1:8b 每个 token 的 KV 缓存比 qwen2.5-coder:7b 大一倍多，在 12G 卡上最紧。我只改它的 contextTokens，三档各跑一次 pong，同时看 ollama ps 的显存：

contextTokensOpenClaw 预算判断超出估算模型总占用在 GPU 上
16384compact_only，shouldCompact: true7,3156.89 GB全部
24576compact_only，shouldCompact: true1,1717.98 GB全部
32768fits09.52 GB8.08 GB

32768 时有 1.4G 被挤到 CPU，这台机器上 llama3.1 开 32K 上下文被挤出 6 层时的速度我在 12G 显卡跑 Ollama 里量过，长提示词下生成从 29 掉到 9.7 token/s；这次 OpenClaw 任务里我没有单独测生成速度。往下调到 24576 能全放进显存，OpenClaw 又在第一轮还没开始时就判定要压缩。三档的这一轮 pong 都发出去了，回复也正常。多轮对话里 compact_only 会怎样触发压缩、压缩后小模型还能不能接着干活，我这次没有测。

5 道小任务，qwen2.5-coder 一次原生工具调用都没有

任务都在 OpenClaw 的工作区里，每次运行前重置 task/ 目录，答案由检查函数判，不看模型自己说成没成：

任务判对条件
write_filetask/hello.txt 的内容正好是 hello openclaw
sum_numbers读 task/numbers.txt 里 12 个三位数，回复里出现正确的和 5961
count_errors用 shell 数 task/app.log 200 行里含 ERROR 的行，回复里出现 42
edit_jsontask/config.json 的 port 从 8080 改成 9090，其他字段不变
index_notes把 task/notes/ 下 4 个 .md 文件名按字母序写进 task/index.txt，目录里另有一个 README.txt 干扰

两组配置：default 是 onboard 写出的配置（full，23 个 skill，引导已完成）；slim 是 coding 加 skills.allowBundled: []。每个模型每组 5 题 × 4 轮，一共 160 次 OpenClaw 运行，温度用的是 Ollama 默认值。

qwen2.5-coder 把工具调用写成了文字

qwen2.5-coder 两个尺寸 80 次运行里，代理没记到一次原生 tool_calls。失败的样子分三种：40 次在回复里写了一段工具调用 JSON，比如 {"name": "read", "arguments": {"path": "numbers.txt"}}；17 次把要跑的命令放进代码块交给我，比如 grep -c 'ERROR' .../task/app.log；23 次没调工具直接作答，有说 “The file task/hello.txt has been created” 但文件不存在的，有说和是 123 的。

OpenClaw 能识别一部分文字版工具调用。这类运行它会再请求一次模型，还不行就返回 ⚠️ The model wrote a tool call as text instead of calling the tool. No tool ran for that call. Please try again or use a model with native tool calling.，进程退出码 1。80 次里有 18 次走到了这一步，其余的文字 JSON 和编造结果都被当成正常回复交了出去，退出码 0。

为了确认这是不是 OpenClaw 那 1.6 万 token 的提示词把模型压垮了，我绕开 OpenClaw 直连 Ollama 做了对照，5 道题的原话各发 2 次，只看第一轮有没有原生工具调用：

请求prompt tokenqwen2.5-coder:3bqwen2.5-coder:7bllama3.1:8b
OpenClaw 的系统提示词和 16 个工具，用户消息只放任务原文15,6130/100/1010/10
系统提示词换成一句话，16 个工具不变4,1260/100/109/10
一句话系统提示词，只留 read/write/edit/exec1,0910/100/1010/10

提示词缩到 1 千 token、工具只剩 4 个，qwen2.5-coder 还是 0/10，问题出在这个模型在 Ollama 上的工具调用输出，跟 OpenClaw 无关。同样是 8B，不同模型多步工具调用的差距我在 同是 8B，多步工具调用 25 比 0 里测过，这里的结论方向一致：选本地模型接 Agent，先单独测它能不能发原生工具调用。

llama3.1 和 gemma4 调了工具，错在结果上

llama3.1:8b 40 次里 14 次也是把工具调用写成文字（”Here is the function call with its proper arguments…”），这类 OpenClaw 没拦，退出码 0。我把 OpenClaw 原样的消息（带时间戳的用户消息、末尾那条 runtime 上下文消息）直接发给 Ollama，第一轮原生调用是 8/10，去掉末尾那条也是 8/10，比上表第一行（同样的系统提示词，用户消息只放任务原文）的 10/10 略低。每组只有 10 次，这点差别我不当结论。另外 10 次 llama 调了工具但结果错，4 次没调工具直接作答。

两个模型共同的失败在 sum_numbers 上，两个模型两组配置 16 次全错。它们都用 read 读了文件，然后心算：llama 给出过 6781、6231、6681，gemma4 给出过 4741、4991、4961、5361，正确答案是 5961。手里有 exec，没有一次想到用 shell 去算。count_errors 题目明说用 shell，gemma4 8/8 都对，llama 有两次 grep 跑完回了 0。

gemma4 的 index_notes 8 次全错。按它回复里自己报的路径，5 次写到了 task/notes/index.txt，题目要的是 task/index.txt，有一次还写着 “written to task/notes/index.txt as requested”；另外 3 次自称写进了 task/index.txt，内容没通过检查，其中一次把 README.txt 也列了进去。每一次回复都说任务完成了，这种错只有按文件检查才看得出来。

tools.allow 只在 profile 已有的工具里筛

OpenClaw 的工具权限分几层：tools.profile 先定一个基础集合（minimal、coding、messaging、full），alsoAllow 往上加，allow 和 deny 再筛。我把 13 种写法逐个用 openclaw config set tools '<json>' --strict-json 写进去，跑 openclaw config validate --json，再跑一轮 pong，从代理看实际发给模型的工具。下表省略了每次都在的 tool_search、tool_describe、dispatch_action：

exec 和 read 都是真实存在的工具名。messaging 的基础集合里没有它们，allow 在这个集合里再筛一遍，交集是空的。config set 和 config validate 都放行，错误要到运行时才出来，openclaw agent 退出码 1：

No callable tools remain after resolving explicit tool allowlist (tools.allow: exec, read);
no registered tools matched. Fix the allowlist or enable the plugin that registers the requested tool.

报错说的是 “no registered tools matched”，看上去像工具名写错了，实际是 profile 和 allow 的交集为空。第二个例子里 discord 和 fs 确实不是工具名（渠道消息工具叫 message，文件工具组叫 group:fs），报的是同一句话，两种原因从报错上分不出来。

想在 messaging 的基础上加 shell 和文件工具，要用 alsoAllow。allow 和 alsoAllow 写在同一层时，config set 直接拒绝写入：tools cannot set both allow and alsoAllow in the same scope (merge alsoAllow into allow, or remove allow and use profile + alsoAllow)，这一条倒是在写入时就拦住了。

full 和不写 profile 发出的工具完全一样，都是 16 个。被 allow 收窄之后，deferred 工具也从 51 个变成只剩 skills_read 1 个，tool_search 能找到的范围跟着缩小。

我现在给本地小模型的配置

这次测下来，我在 12G 卡上给 OpenClaw 配本地模型时会这样写：

{
  tools: { profile: "coding" },        // 不需要渠道消息时不用 full，少 1,300 token 左右
  skills: { allowBundled: [] },        // 23 个 bundled skill 每次 2,500 token，按需再打开
}

模型用 gemma4，qwen2.5-coder 不接 OpenClaw。要收窄工具就在 coding 或 full 上写 allow，在 messaging 上加工具用 alsoAllow，改完配置跑一轮 openclaw agent --local ... --json，看 systemPromptReport.tools.entries 里列出的工具，不能只看 config validate 的结果。

这几条只覆盖我测过的范围：OpenClaw 2026.11.9 的 agent --local 单轮运行，网关模式、渠道消息、多轮对话里的上下文压缩都没有测；任务只有 5 道，每个组合 4 轮，gemma4 的 12/20 和 llama3.1 的 6/20 之间差距够大，同一模型两组配置之间一两次的差别说明不了什么。
