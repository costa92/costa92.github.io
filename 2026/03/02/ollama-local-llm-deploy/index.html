12G 显卡跑 Ollama：llama3.1 开 32K 上下文只剩 10 token/s，KV 缓存改 q8_0 回到 29

我这台机器是一张 RTX 3060 12G，同时也是日常用的桌面机。Ollama 装好、ollama run 能出字之后，真正决定好不好用的是几个服务端参数：上下文开多大、Flash Attention 和 KV 缓存怎么设、要不要让一个模型同时处理多个请求。网上的说法大多是”开 q8_0 省显存””调大 NUM_PARALLEL 提吞吐”，没说在 12G 卡上具体换来什么、丢了什么。这次我把这几个参数挨个在本机测了一遍，主要用 llama3.1:8b，因为它每个上下文位置占的 KV 缓存是 qwen2.5-coder:7b 的两倍多，12G 卡上最先撞到上限。

测试环境

项目配置
Ollamaollama --version 输出 0.35.0，systemd 服务 ollama.service，以 ollama 用户运行，模型目录用 drop-in 指到数据盘
显卡RTX 3060 12GB，驱动 580.178.04，CUDA 13.0
主机28 核 CPU，61G 内存，Ubuntu，桌面在跑
模型llama3.1:8b、qwen2.5-coder:7b，都是 Q4_K_M
日期2026-11-24

服务端参数要改环境变量、重启服务，这台机器上的 Ollama 服务还有别的程序在用，我没去动它，而是用同一个二进制另起一个服务，端口换掉，模型目录共用：

OLLAMA_HOST=127.0.0.1:11500 \
OLLAMA_MODELS=/mnt/data/ollama/models \
OLLAMA_NOPRUNE=1 \
OLLAMA_KV_CACHE_TYPE=q8_0 OLLAMA_FLASH_ATTENTION=1 \
ollama serve

OLLAMA_NOPRUNE=1 让临时服务启动时不去清理模型目录。每组参数起一次、测完杀掉，系统服务的配置从头到尾没改。测速脚本只用 Python 标准库，调 /api/generate，在请求的 options 里传 num_ctx、temperature: 0 和固定 seed，从返回的 prompt_eval_count / prompt_eval_duration 和 eval_count / eval_duration 算预填充和生成速度；CPU/GPU 比例取 /api/ps 的 size_vram / size，也就是 ollama ps 里 PROCESSOR 那一列的来源；GPU 层数、KV 缓存大小从服务日志里 llama-server 的加载输出摘。脚本和原始结果放在 blog-go-example/ollama-12gb-tuning。

12G 的卡，模型能用的只有 7G 出头

没加载任何模型时，nvidia-smi 显示已经用了 3.3 到 3.8 GiB，是浏览器、编辑器、远程桌面这些桌面程序占的。Ollama 0.35.0 背后跑的是 llama-server，它加载前会先估算要多少显存，再给显卡留 1024 MiB 余量（日志里叫 free memory target，对应 LLAMA_ARG_FIT_TARGET），放不下就把一部分层挪到 CPU。llama3.1:8b 开 32K 上下文时的日志：

common_params_fit_impl: projected to use 8639 MiB of device memory vs. 8401 MiB of free device memory
common_params_fit_impl: cannot meet free memory target of 1024 MiB, need to reduce device memory by 1261 MiB
common_params_fit_impl:   - CUDA0 (NVIDIA GeForce RTX 3060): 27 layers,   7215 MiB used,   1186 MiB free

可用的 8.4 GiB 再减掉 1 GiB 余量，留给权重、KV 缓存和计算缓冲区的大约 7.2 GiB。llama3.1:8b 的权重 4.7GB，剩下的空间决定了上下文能开多大。下面所有”放得下、放不下”的结论都是在这个余量下得出的，没开桌面的服务器会宽松一些。

Flash Attention 在 0.35.0 里已经默认开了

ollama serve 启动时打印的配置里写着 OLLAMA_FLASH_ATTENTION:false，我一开始以为没开。翻 llama-server 的启动命令，不设这个变量时传的是 --flash-attn auto，日志随后打出 Flash Attention enabled；设成 0 才变成 --flash-attn off。设 OLLAMA_KV_CACHE_TYPE=q8_0 并设 OLLAMA_FLASH_ATTENTION=1 时，命令行是 --cache-type-k q8_0 --cache-type-v q8_0 --flash-attn on。

把它显式关掉对比一下。提示词约 3.6K token，生成 128 个 token，每档 3 次取中位数：

40965.5 GB，100% GPU，33/331258 / 47.15.3 GB，100% GPU，33/331738 / 49.1

6553616.2 GB，56%/44%，11/33303 / 9.814.1 GB，45%/55%，18/33952 / 15.5

两边的 KV 缓存一样大（都是 f16，4096 时 512 MiB，按上下文线性翻倍），差在计算缓冲区：16K 时 llama-server 估算关 FA 要 7543 MiB、开 FA 要 6575 MiB，这将近 1 GiB 让关 FA 的 16K 就开始掉层。即使全在 GPU 上，开 FA 的预填充也快了约四成。所以在 0.35.0 上不用专门去设 OLLAMA_FLASH_ATTENTION=1，要防的是别人在配置里把它写成 0。

表里还能看到上下文开大本身的代价：开着 FA，16K 以内都在 GPU 上，速度几乎不变；到 32K 有 6 层被挤到 CPU，同样 3.6K 的提示词生成速度从 51 掉到 21 token/s。qwen2.5-coder:7b 的 KV 缓存小一半，32K 也放得下，那组数据在Ollama 静默截断长提示词里，这里不重复。

KV 缓存改 q8_0，32K 重新全部放进 GPU

OLLAMA_KV_CACHE_TYPE 把 KV 缓存从 f16 量化成 q8_0 或 q4_0，体积分别是 f16 的约 53% 和 28%（llama-server 报的 32K 大小：f16 4096 MiB，q8_0 2176 MiB，q4_0 1152 MiB）。除了 3.6K 的短提示词，32K 档再喂一个 22.6K token 的长提示词（生成 64 个 token），64K 档喂 45.1K token 的，都是 3 次取中位数：

32K 是这张卡上差别最大的一档。f16 时 22.6K 的长提示词生成只有 9.7 token/s，生成 300 个 token 要等半分钟；q8_0 全回 GPU 后是 29.2 token/s，三倍。64K 时只有 q4_0 能全放进 GPU，q8_0 仍有 9 层在 CPU 上，长提示词生成 5.5 token/s，基本没法用。

量化本身也有开销。在 f16 本来就放得下的 4K 到 16K，q8_0 和 q4_0 的短提示词生成在 44.6 到 48.2 token/s，f16 是 49.1 到 51.2，慢 5% 左右；18K token 的提示词全在 GPU 上预填充，f16 中位数 1418 token/s，q8_0 1345，q4_0 1339。上下文用不到 16K 的话，改 KV 类型没有好处。

精度代价：llama3.1 测不出来，qwen2.5-coder 配 q4_0 直接坏掉

省显存的代价是精度，我用一个长上下文检索题去量。程序生成一份”项目登记表”，每条记录写着项目代号、负责人、预算和一个五位数的机房门禁码，代号故意做得很像（HIDDEN-QUARRY-5 和 HIDDEN-QUARRY-x 这种）。从头到尾按均匀深度挑 30 条，每次问”代号 X 的门禁码是多少，只回五位数字”，温度 0，回答里第一个五位数和标准答案完全一致才算对。登记表在同一组配置里是同一份，只有末尾的问题在变，前缀缓存会接住前面的部分，所以 30 题跑得很快。

先看全部在 GPU 上的对比。llama3.1:8b，num_ctx 20480，登记表 400 条约 18.1K token，三份不同随机种子的登记表各 30 题：

KV 类型种子 7种子 11种子 23合计
f1627292884/90
q8_027293086/90
q4_027282984/90

三者差一两题，在这个题量下分不出高低。错的题多数是把相似代号的门禁码张冠李戴，比如问第 17 条答成了第 370 条的码。

更长的上下文我只跑了一份登记表：

模型 / num_ctx / 提示词f16q8_0q4_0
llama3.1:8b / 32768 / 22.6K token21/30（82% GPU）29/3026/30
llama3.1:8b / 65536 / 45.1K token13/30（55% GPU）24/30（75% GPU）23/30

f16 在 32K 和 64K 都是最低分，这和”量化掉精度”的直觉相反。我怀疑过是部分层在 CPU 上算导致的，于是在 20K 下用请求参数 num_gpu: 27 强行只放 27 层到 GPU，f16 拿了 28/30，q8_0 27/30，和全在 GPU 上一样，这个解释不成立。原因我没查出来，只有一份登记表，我不拿它当”f16 更差”的证据，能确定的是 q8_0 和 q4_0 在 llama3.1 上没有表现出可测的精度损失。

qwen2.5-coder:7b 就是另一回事了。num_ctx 32768，登记表 500 条约 26K token，三份登记表：

KV 类型种子 7种子 11种子 23合计
f1620222365/90
q8_021202364/90
q4_00000/90

q4_0 的回答不是答错，而是乱码，长这样：1 1 1、1 1 11 1 1、en 1 1 1 1。我以为是长上下文才出问题，又在 8K 上下文、60 条记录（约 2.8K token）上试，q4_0 仍是 0/30，q8_0 29/30。最后直接问短问题：

q4_0  "What is 2+3? Answer with the number only."  ->  '2'
q4_0  "Write a Go function that reverses a string." ->  '...a simple Go program that reversverses a string: ... //// reverseString ...'
q8_0  同样两个问题                                  ->  '5'，代码正常

短对话里也会算错、吞字，只是不像长上下文那样完全崩掉，乍一看还像正常输出，这比报错更危险。同样设置下 llama3.1:8b 一切正常，所以问题出在模型和 q4_0 KV 缓存的组合上，具体原因我没追。OLLAMA_KV_CACHE_TYPE 是服务端全局设置，对这个服务上的所有模型生效，只要服务上有 qwen2.5 系列，就别用 q4_0。

OLLAMA_NUM_PARALLEL：每多一个槽位，KV 缓存多一份

0.35.0 的 OLLAMA_NUM_PARALLEL 默认是 1，同一时间一个模型只处理一个请求，其余排队。设成 N 时 llama-server 以 -np N 启动，日志里是 n_slots = N, n_ctx_slot = 8192，每个槽位都有完整的 num_ctx，KV 缓存跟着乘以 N：num_ctx 8192 时 np=1 是 1024 MiB，np=2 是 2048 MiB，np=4 是 4096 MiB，等于开了一个 32K 的上下文。

测法：llama3.1:8b，num_ctx 8192，每个请求是一段约 570 token 的不同内容（互相没有公共前缀），固定生成 200 个 token；1、2、4、8 个客户端同时发，每档跑 3 轮取中位数。吞吐是所有请求生成的 token 总数除以整轮耗时，延迟是单个请求从发出到返回的时间。

配置ollama ps1 个客户端 吞吐 / 延迟2 个4 个8 个（中位延迟 / 最长）
np=1，f165.9 GB，100% GPU46.5 / 4.3s49.0 / 6.2s49.2 / 10.2s48.8 / 18.3s / 32.8s
np=2，f166.9 GB，100% GPU46.8 / 4.3s80.4 / 5.0s81.7 / 7.4s82.9 / 12.1s / 19.3s
np=4，f169.4 GB，20%/80%26.3 / 7.6s42.6 / 9.4s66.4 / 12.0s66.1 / 18.4s / 24.2s
np=4，q8_07.1 GB，100% GPU49.3 / 4.1s83.9 / 4.8s110.3 / 7.2s109.8 / 11.3s / 14.6s

np=1 时总吞吐卡在 49 token/s 左右，来几个请求都一样，排在后面的人干等：8 个并发时最后一个要 33 秒。np=2 吞吐涨到 81 token/s，单个请求的生成速度只从 52 降到 48 左右，8 个并发的最长等待缩到 19 秒。

np=4 配 f16 是这次最反直觉的一组。KV 缓存涨到 4 GiB 放不下，6 层被挪到 CPU，结果只有一个请求时也只剩 26 token/s，比 np=1 慢了将近一半，并发时总吞吐 66 token/s，还不如 np=2。槽位开多了，单人用的时候也在付代价。同样 np=4 换成 q8_0 KV 缓存，KV 回到 2176 MiB、全在 GPU 上，单请求 49 token/s 不受影响，4 个并发总吞吐 110 token/s，是 np=1 的 2.2 倍。

加载时间：页缓存在就是两三秒

同一个 llama3.1:8b，换 num_ctx 或换服务端参数都要重新加载。模型文件在系统页缓存里时，load_duration 大多在 1.9 到 3.5 秒。校准脚本第一次加载 llama3.1:8b 用了 57 秒，我推测当时模型文件不在页缓存里，这只碰到一次。另外有两次 14 秒和 19 秒，都紧跟在关 FA、64K 上下文那一组之后，那一组有 9GB 左右的权重和 KV 缓存放在内存里，我推测是把模型文件挤出了页缓存，没有进一步验证。

num_ctx 是按请求传的，同一个模型被不同 num_ctx 的请求轮流调用就会反复重载，这个现象在系统提示词开头加个时间戳，Ollama 首字延迟从 37ms 涨到 3 秒里测过。

按这些数，我会这样配这台机器

如果要改系统服务，写法是 drop-in：

sudo systemctl edit ollama.service
[Service]
Environment="OLLAMA_FLASH_ATTENTION=1"
Environment="OLLAMA_KV_CACHE_TYPE=q8_0"
Environment="OLLAMA_NUM_PARALLEL=2"

然后 sudo systemctl restart ollama。这几个值我是在临时服务上用环境变量验证的，系统服务因为还有别的程序在用，没有真的重启去改，以上配置只按测得的结果推荐。

选这几个值的理由都来自上面的表：

  • OLLAMA_KV_CACHE_TYPE=q8_0：llama3.1:8b 的 32K 上下文从 79% GPU 回到 100%，长提示词生成快三倍，检索题不掉分；短上下文时慢 5% 左右，可以接受。qwen2.5-coder 在 q8_0 下也正常。
  • 不用 q4_0：它在 llama3.1 上能把 64K 全塞进 GPU，但同一个服务上的 qwen2.5-coder:7b 会输出乱码。只跑 llama 系列、又真要 64K 时可以单独起一个 q4_0 的服务。
  • OLLAMA_FLASH_ATTENTION=1：0.35.0 默认就是开的，写上它是因为我测 q8_0 时一直是两个一起设的，只设 KV 类型不设 FA 的组合我没测。
  • OLLAMA_NUM_PARALLEL=2：8K 上下文时多付 1 GiB 显存，并发时吞吐多六成多。在这台机器上设 4 必须配 q8_0，并且只在经常有 3 个以上并发时才值得。

不管怎么设，加载后都用 ollama ps 看一眼 PROCESSOR 列。只要出现 CPU 的百分比，就要预期生成速度掉一半甚至更多。

这次没测的

  • 只测了两个 Q4_K_M 的 7B/8B 模型和一张 RTX 3060。更大的模型、别的量化版本、别的显卡，”放得下”的分界会变。
  • 检索题是合成数据，30 题一组，32K 以上只有一份登记表。它只测”从长文里找回一个数字”，不代表推理或写代码的质量。
  • llama3.1 在 32K、64K 下 f16 得分最低的原因没查出来。
  • qwen2.5-coder 配 q4_0 KV 缓存出乱码的原因没追，也没测 qwen2.5 的其他尺寸或 qwen3 系列。
  • 只设 OLLAMA_KV_CACHE_TYPE、不设 OLLAMA_FLASH_ATTENTION 的组合，以及 np=2 配 q8_0，没有测。
  • 并发测试的请求都很短（约 570 token 输入、200 token 输出），长提示词并发时预填充会互相抢 GPU，结果会不一样。
