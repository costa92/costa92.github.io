用 mitmproxy 抓包 Claude Code：一次真实走代理的请求记录

 2026-03-23  Coding-Agent Claude Code mitmproxy 网络抓包 调试
Claude Code mitmproxy 网络抓包 调试
Coding-Agent
文章字数:   3.5k
阅读次数:

Claude Code 读文件、改代码、跑命令，但它和 Anthropic API 之间说了什么，你在终端里看不到。想弄清楚，最直接的办法是抓包：在中间插一个 HTTPS 代理，把请求一条条记下来。

这篇先在 Linux 上把 mitmproxy 的代理链路完整跑一遍（证书在哪生成、不信任 CA 会怎样、Node 程序要额外设什么），再给出 macOS / Windows 的证书配置，然后让 Claude Code 真的走一次代理，看它发了哪些请求、/v1/messages 里装了什么。

原理：中间人代理

Claude Code 不直接连 API，而是先经过 mitmproxy，mitmproxy 记录请求后再转发。

前提是客户端信任 mitmproxy 的 CA 证书。mitmproxy 会给每个目标站点现签一张证书，客户端信任了它的根证书，它就能在中间解密、记录、再加密，两端都不报错。

先在 Linux 上把代理链路跑通

先不碰 Claude Code，用 curl 和一段 Node 脚本访问 example.com，验证链路本身。以下是 2026-10-30 在 Ubuntu 26.04 + mitmproxy 12.3.1 + curl 8.18.0 + Node 22.22.0 上实测的结果。

安装：用 uv 装进独立环境

uv venv .venv
uv pip install --python .venv/bin/python mitmproxy
.venv/bin/mitmdump --version
Mitmproxy: 12.3.1
Python:    3.12.11
OpenSSL:   OpenSSL 4.0.3 29 Sep 2026
Platform:  Linux-7.0.0-38-generic-x86_64-with-glibc2.43

mitmproxy 依赖不少，放进独立虚拟环境（uv、pipx 都行）可以避免和其他 Python 项目打架。macOS 用 brew install mitmproxy，Windows 用 pip install mitmproxy 或 pipx。

证书在第一次启动时生成

证书目录由 confdir 选项决定，默认值可以这样查：

mitmweb --options | grep -E '^(confdir|web_port):'
confdir: ~/.mitmproxy
web_port: 8081

我实测时用 --set confdir=<实验目录>/conf 把证书放在实验目录里，免得往家目录写东西。第一次启动后目录里会出现这些文件：

mitmproxy-ca-cert.cer
mitmproxy-ca-cert.p12
mitmproxy-ca-cert.pem      # 给客户端信任用的公钥证书
mitmproxy-ca.p12
mitmproxy-ca.pem           # 含私钥，权限是 600，别外传
mitmproxy-dhparam.pem

后面所有”信任证书”的步骤用的都是 mitmproxy-ca-cert.pem。

启动：端口被占会直接退出

mitmweb --listen-port 8080    # 代理在 8080，网页界面在 8081
# 或者无界面版，配合脚本用
mitmdump -p 8080

我第一次用的端口恰好被本机别的服务占了，mitmdump 没有换端口，而是直接退出。后来我故意用 python3 -m http.server 先占住一个端口再起 mitmdump，复现了一遍：

Error logged during startup, exiting...
[Errno 98] HTTP(S) proxy failed to listen on 127.0.0.1:28092 with [Errno 98] error while attempting to bind on address ('127.0.0.1', 28092): [errno 98] address already in use
Try specifying a different port by using `--mode regular@28094`.
mitmdump exit=1
$ curl -sS -o /dev/null -x http://127.0.0.1:28092 https://example.com
curl: (7) CONNECT tunnel failed, response 501

更坑的是，此时 curl 连上的是那个占端口的服务，报 CONNECT tunnel failed，后面的状态码取决于占端口的是什么（我第一次遇到的是 404，这次 Python 自带的 http.server 回的是 501），看上去像代理配置错了。遇到这种报错先看 mitmproxy 自己有没有起来。另外它默认监听 0.0.0.0，只在本机抓包时加上 --listen-host 127.0.0.1 更稳妥。

不信任 CA 时会怎样

换了空闲端口后，分别用 curl 不带 CA、带 CA、用环境变量指定代理访问 example.com：

P=http://127.0.0.1:28087
CA=conf/mitmproxy-ca-cert.pem
curl -sS -o /dev/null -x $P https://example.com
curl -sS -o /dev/null -w "withcert: %{http_code}\n" -x $P --cacert $CA https://example.com
HTTPS_PROXY=$P curl -sS -o /dev/null -w "envproxy: %{http_code}\n" --cacert $CA https://example.com
curl -sS -v -o /dev/null -x $P --cacert $CA https://example.com 2>&1 | grep -E "subject:|issuer:"
curl: (60) SSL certificate OpenSSL verify result: unable to get local issuer certificate (20)
More details here: https://curl.se/docs/sslcerts.html
withcert: 200
envproxy: 200
*   subject: CN=example.com
*   issuer: CN=mitmproxy; O=mitmproxy

不信任 CA 时客户端直接拒绝握手，mitmproxy 这边的日志会写 “Client TLS handshake failed … this may indicate that the client does not trust the proxy’s certificate”。信任之后，证书的签发者变成了 CN=mitmproxy，这就是中间人在工作。

Node 程序：光设 HTTPS_PROXY 不够

Claude Code 官方文档说它会读取 HTTPS_PROXY。但 Claude Code 拉起的子进程不一定，比如用 Node 写的 stdio MCP 服务器。我用一段最简单的 Node 脚本（https.get('https://example.com/')）试了三种组合：

HTTPS_PROXY=...                                         -> node status 200 SSL Corporation
HTTPS_PROXY=... NODE_USE_ENV_PROXY=1                    -> node error UNABLE_TO_VERIFY_LEAF_SIGNATURE
HTTPS_PROXY=... NODE_USE_ENV_PROXY=1 NODE_EXTRA_CA_CERTS=conf/mitmproxy-ca-cert.pem
                                                        -> node status 200 mitmproxy

脚本打印的最后一列是证书签发者的 O 字段。Node 22.22.0 的 https 模块默认不读 HTTPS_PROXY，第一种组合绕过代理直连：拿到的是 example.com 的真实证书（签发者 SSL Corporation），mitmproxy 里什么都没有。直连能不能通看网络环境，我第一次跑时这一步是 ETIMEDOUT，重跑这次直连成功了，两种结果都说明它没走代理；加上 NODE_USE_ENV_PROXY=1 才走代理，但又不信任 mitmproxy 的证书；三个变量都设上才拿到 200，证书签发者是 mitmproxy。

结论：抓 Claude Code 本体，HTTPS_PROXY 加 NODE_EXTRA_CA_CERTS 就够；想连它拉起的 Node 子进程一起抓，还要看那个进程用的 HTTP 库认不认代理变量。

信任证书：macOS 和 Windows

macOS

# 将 mitmproxy CA 证书导入系统钥匙串并设为信任
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain \
  ~/.mitmproxy/mitmproxy-ca-cert.pem

在「钥匙串访问」→「系统」里能找到一个叫 mitmproxy 的证书，状态应该是「始终信任」。

Windows

证书路径：C:\Users\你的用户名\.mitmproxy\mitmproxy-ca-cert.pem

  1. 双击 .pem 文件
  2. 选择「安装证书」→「本地计算机」
  3. 将证书放入「受信任的根证书颁发机构」

安全提醒
这个 CA 让 mitmproxy 可以解密所有 HTTPS 流量。抓包结束后移除它：macOS 在钥匙串访问中删除，Windows 在证书管理器中删除。

让 Claude Code 走代理

在同一个终端窗口设置环境变量，然后启动 Claude Code：

# macOS / Linux
export HTTPS_PROXY=http://127.0.0.1:8080
export NODE_EXTRA_CA_CERTS=~/.mitmproxy/mitmproxy-ca-cert.pem
claude
# Windows (PowerShell)
$env:HTTPS_PROXY = "http://127.0.0.1:8080"
$env:NODE_EXTRA_CA_CERTS = "C:\Users\你的用户名\.mitmproxy\mitmproxy-ca-cert.pem"
claude

HTTPS_PROXY 让 Claude Code 把 HTTPS 请求发给代理（按官方网络配置文档，它不支持 SOCKS 代理）。NODE_EXTRA_CA_CERTS 把 mitmproxy 的 CA 追加到信任列表。

按同一份文档，Claude Code 默认同时信任自带的 Mozilla CA 和操作系统证书库（CLAUDE_CODE_CERT_STORE 默认是 bundled,system），原生安装版总能读系统证书库，npm 安装需要 Node 22.15 及以上。所以证书已经导入系统的话，较新的版本不设 NODE_EXTRA_CA_CERTS 也能工作。显式设上最稳妥。

想确认证书真的加载了，用 claude --debug 启动，日志（~/.claude/debug/<session-id>.txt）里会有一行 CA certs: Appended extra certificates from NODE_EXTRA_CA_CERTS (...)，这句原文在 2.1.314 的程序里能搜到；会话里跑 /status 也能看到代理一行。

每次都设变量太麻烦，可以存成脚本，比如 ~/.local/bin/claude-debug：

#!/bin/bash
export HTTPS_PROXY=http://127.0.0.1:8080
export NODE_EXTRA_CA_CERTS=~/.mitmproxy/mitmproxy-ca-cert.pem
claude "$@"

抓到的请求在 http://127.0.0.1:8081 的 Flow List 里，点开能看到完整的 Request / Response。对话请求（/v1/messages）是 SSE 流式响应，要看 Response 的 Raw 标签页，默认视图可能显示不全。截图或导出前记得打码，请求头里就是你的凭据。

实测：Claude Code 走一次代理

为了不让 Claude Code 读到本机真实的登录态，我用 env -i 清空环境变量，把 HOME 和 CLAUDE_CONFIG_DIR 都指到实验目录里的空目录，API key 给一个假值。预期结果是 401，但请求会完整地经过代理：

env -i HOME=$LAB/home CLAUDE_CONFIG_DIR=$LAB/cfg PATH=/usr/bin:/bin \
  ANTHROPIC_API_KEY=sk-ant-dummy \
  HTTPS_PROXY=http://127.0.0.1:28091 \
  NODE_EXTRA_CA_CERTS=$LAB/conf/mitmproxy-ca-cert.pem \
  claude -p hi
Invalid API key · Fix external API key
exit=1

mitmdump 这边挂了一个脚本，把每个请求的方法、路径、状态码记下来，/v1/messages 的 body 只统计字段名和字节数，x-api-key 打码。2026-10-30 在 Ubuntu 26.04 + Claude Code 2.1.314（原生安装版）+ mitmproxy 12.3.1 上，一次 claude -p hi 一共 13 个请求，全部发往 api.anthropic.com：

GET  /api/claude_code/policy_limits                  401
GET  /api/claude_code/settings                       401
POST /api/eval/sdk-<id>                              200
POST /api/event_logging/v2/batch                     200
GET  /mcp-registry/v0/servers                        200
GET  /api/claude_cli/bootstrap                       401
GET  /api/claude_code_penguin_mode                   401
GET  /mcp-registry/v0/servers                        200
POST /v1/messages                                    401
GET  /mcp-registry/v0/servers                        200
GET  /api/claude_code/organizations/metrics_enabled  401
GET  /mcp-registry/v0/servers                        200
POST /api/event_logging/v2/batch                     200

需要认证的接口都是 401，遥测、MCP 注册表这类不校验 key 的接口照样 200。也就是说，key 无效时遥测仍然发出去了。

/v1/messages 这一条的结构：

请求头（节选）:
  User-Agent: claude-cli/2.1.314 (external, sdk-cli)
  anthropic-version: 2023-06-01
  anthropic-beta: claude-code-20250219,interleaved-thinking-2025-05-14,context-management-2025-06-27,...（共 15 项）
  x-api-key: <redacted>
  x-app: cli
  X-Claude-Code-Session-Id / x-claude-code-prompt-id / x-client-request-id: <uuid>
  x-claude-code-request-class: main
  X-Stainless-*: SDK 版本 0.128.0、运行时 node v26.12.1 等
body 顶层字段: model, messages, system, tools, metadata, max_tokens, thinking,
               context_management, output_config, thread, diagnostics, stream
body 总大小: 48162 字节
system: 4 个 block，7481 字节
tools: 13 个工具定义，30577 字节
messages: 2 条
stream: true
响应: {"type":"error","error":{"type":"authentication_error","message":"invalid x-api-key"}}

我只输入了一个 “hi”，请求体已经有 48KB，其中六成多是工具定义，system 提示只占 7KB。这还是空配置目录、没装任何 MCP server 和 skill 的情况，平时的请求只会更大。

程序里能搜到的其他请求

上面那次是假 key、空配置，登录态、托管设置、MCP 连接都没走到。下表是我在本机 2.1.314（原生安装版）的程序文本里按字符串搜到的接口路径，不是抓包记录；标了「已抓到」的是上面那次实际出现过的。这些大多是内部接口，路径会随版本变化，具体会出现哪些取决于安装方式和登录方式：

#请求地址说明发送时机
1版本检查：原生安装查 downloads.claude.ai，Homebrew 安装查 formulae.brew.sh，npm 安装查 npm registry检查是否有新版本启动时
2MCP Server URL（如 mcp.slack.com/mcp）连接配置的远程 MCP 服务器启动时
3api.anthropic.com/api/claude_cli_profile 或 /api/oauth/profile获取账号基本信息（假 key 那次没出现，出现的是 /api/claude_cli/bootstrap）启动时
4api.anthropic.com/api/claude_code/settings拉取组织下发的托管设置（已抓到）启动时
5api.anthropic.com/api/claude_code_penguin_mode查询组织是否允许 Fast mode（已抓到）启动时
6api.anthropic.com/v1/messages发送对话请求（已抓到）用户发消息时
7api.anthropic.com/api/event_logging/v2/batch上报使用遥测数据（已抓到）周期性

一个例外：原生安装版的程序里搜不到 registry.npmjs.org/@anthropic-ai/claude-code 这个字面量，npm 版走的是另一套更新逻辑，我没装 npm 版去对照。

版本检查

Claude Code 启动时检查最新版本号。npm / bun 安装查 npm registry，原生安装查 downloads.claude.ai（程序里还能搜到 storage.googleapis.com/claude-code-dist-… 的地址，2.1.314 里出现在插件相关路径上），Homebrew 安装查 formulae.brew.sh。原生安装会自动更新，也可以手动跑 claude update。

MCP 服务器连接

~/.claude.json 或项目 .mcp.json 里配置的 MCP 服务器，Claude Code 会逐个连接：

POST https://mcp.slack.com/mcp         (HTTP 类型)
GET  https://your-server.example/sse   (SSE 类型)

HTTP / SSE 类型在 mitmweb 里能看到；stdio 类型走本地进程通信，抓不到包，它自己发出的网络请求是否走代理，就是上面 Node 实验说明的问题。用 claude.ai 账号登录时，从 claude.ai 添加的连接器会经由 mcp-proxy.anthropic.com 转发。

账号信息和托管设置

GET https://api.anthropic.com/api/claude_cli_profile
GET https://api.anthropic.com/api/oauth/profile
GET https://api.anthropic.com/api/claude_code/settings

用 Console API key 登录走 claude_cli_profile（请求头带 x-api-key），用 claude.ai 订阅账号登录走 oauth/profile（带 Authorization: Bearer）。claude_code/settings 拉的是组织管理员配置的托管设置，个人账号通常返回空配置。

Fast mode 可用性

GET https://api.anthropic.com/api/claude_code_penguin_mode

penguin_mode 是 Fast mode 的内部代号。从程序里的调用方式看，它查询组织是否开启了 Fast mode。官方网络文档也提到，即便通过 ANTHROPIC_BASE_URL 走 LLM 网关，这个检查仍然会请求 api.anthropic.com。真正的 feature flags 是另外的请求拉取的。

对话请求

POST https://api.anthropic.com/v1/messages
Content-Type: application/json

核心请求：指令、系统提示、工具定义、对话历史全部打包发给 API，Request Body 里分别是 system、tools、messages 三个字段，外加 thinking、context_management 等十来个控制字段（见上面的实测）。Response 是 text/event-stream，每个 chunk 是一段文本或一次工具调用。

遥测

POST https://api.anthropic.com/api/event_logging/v2/batch

批量上报使用事件；直连 Anthropic API 时还会向 Datadog（http-intake.logs.us5.datadoghq.com，这个域名程序里也能搜到）发运维遥测。介意的话设 DISABLE_TELEMETRY=1，或用 CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 一并关掉非必要流量，详见官方 Data usage。关掉后再抓一次，就能看到哪些请求消失了。

过滤和脚本化

mitmweb 搜索框输入 ~d api.anthropic.com 只显示 Anthropic 的请求。选中一条请求可以通过 Flow 菜单的 Export 复制为 curl 命令，重放前先删掉里面的 key 或 token。

想自动化分析，用 mitmdump 加 Python 脚本。下面这个脚本我实测时把域名换成了 example.com：

# save as filter_host.py
def response(flow):
    if "example.com" in flow.request.pretty_host:
        print(f"{flow.request.method} {flow.request.path}")
        print(f"  Status: {flow.response.status_code}")
        print(f"  Size: {len(flow.response.content)} bytes")
mitmdump -s filter_host.py -p 8080

每经过一次请求，mitmdump 输出（2026-10-30，mitmproxy 12.3.1）：

GET /
  Status: 200
  Size: 577 bytes
127.0.0.1:35610: GET https://example.com/ HTTP/2.0
     << HTTP/2.0 200 OK 577b

抓 Claude Code 时把判断条件换回 api.anthropic.com 即可。用完记得关掉 mitmproxy，并从系统里移除它的 CA 证书。
