OpenClaw 进阶实战：12 个使用技巧与必装 Skills 清单

前置说明
本文假设你已完成 OpenClaw 的安装和渠道接入，还没做的话先看 OpenClaw 完整使用指南。内容最初基于 v2026.3.2，运行环境是 Discord 渠道 + DeepSeek-V3.2 模型；2026-10 按 2026.9.9 和 ClawHub 的当前状态复核过一遍，有变化的地方就近标注。

装好 OpenClaw、接通 Discord、发几条消息确认能回复，很多人到这一步就停了。但真正影响日常体验的，是 Skills 生态、Agent 架构和一些不写在首页的配置细节。这篇整理我实际用下来觉得有用的东西：12 个技巧、6 个值得装的 Skill、3 种 Agent 架构，外加两个踩过的坑。

效率技巧

1. 脚本里用 openclaw agent，不用开聊天界面

在 Discord 里一条条发消息等回复，不适合批量操作。openclaw agent 跑一轮对话就退出，适合写进脚本或 CI：

# 单条指令
openclaw agent --agent main --message "列出 ~/projects 下所有 Git 仓库的最近一次提交"

# 长指令写进文件
openclaw agent --agent main --message-file ./task.md

# 要机器可读的结果
openclaw agent --agent main --message "检查 package.json 里有没有过期依赖" --json

需要续接某个会话的上下文（避免重复解释背景）时，用 --session-key 指定会话：

openclaw agent --session-key agent:main:main --message "接着刚才的话题，给出升级顺序"

2. 给长模型 ID 设别名

siliconflow/Pro/deepseek-ai/DeepSeek-V3.2 每次手打太长，用 models aliases 起个短名：

openclaw models aliases add ds siliconflow/Pro/deepseek-ai/DeepSeek-V3.2

# 之后切换模型只需
openclaw models set ds

3. 用 –dry-run 预演不可逆操作

reset、update 这类改动大的命令，先加 --dry-run：

# reset 需要同时指定 --scope，否则仍会进入交互式提示
openclaw reset --dry-run --scope config --non-interactive --yes
# 输出将要删除的文件列表，不实际执行

openclaw update --dry-run
# 显示安装方式、通道、当前版本和目标版本，不实际升级

reset --scope 有三个值：config（只清配置）、config+creds+sessions（配置、凭据和会话）、full（完全重置）。

我有一次手滑执行了 openclaw reset --scope config+creds+sessions --yes，API Key 全清了。之后的习惯是：任何带 --yes 或 --force 的命令，先换成 --dry-run 看一眼影响范围，再去掉 --dry-run 重跑。

4. Shell 补全

装一次，后续子命令和参数都能 Tab 补全：

openclaw completion --install
# 重启终端后生效，支持 zsh / bash / fish / powershell

OpenClaw 的子命令和参数很多，补全省下的主要是查文档确认参数名的时间。

安全技巧：别让 Agent 变成攻击入口

5. 装完先跑一次安全审计

openclaw security audit
openclaw security audit --deep   # 额外探测运行中的网关

我第一次跑时有两条 CRITICAL：

  • Discord 的 groupPolicy 是 open：服务器里任何人 @ 你的 Bot 都能触发工具调用，存在 prompt injection 风险。修复方法是切换为 allowlist，并用 allowFrom 限定允许触发的用户：
// ~/.openclaw/openclaw.json
{
  channels: {
    discord: {
      enabled: true,
      token: "${DISCORD_BOT_TOKEN}",
      groupPolicy: "allowlist",   // open | allowlist | disabled
      dmPolicy: "pairing",        // pairing | allowlist | open | disabled
      allowFrom: ["123456789012345678"],   // 你的 Discord 用户 ID（纯数字）
      guilds: {}                  // 服务器、频道级规则，见使用指南
    }
  }
}

2026.9.9 的默认值已经是 groupPolicy: "allowlist"、dmPolicy: "pairing"，但早期版本装出来的配置可能还是 open，值得检查一遍。

怎么拿到自己的 Discord 用户 ID：

# 方式一：从已有会话里找（前提是已经和 Bot 私聊过）
openclaw sessions --json | python3 -c \
  "import json,sys; [print(s['key']) for s in json.load(sys.stdin).get('sessions',[]) if ':direct:' in s['key']]"
# → agent:main:discord:direct:123456789012345678
#                              ↑ 末段数字就是你的用户 ID

# 方式二：通过用户名查
openclaw channels resolve "你的Discord用户名" --channel discord --kind user

# 方式三：Discord 客户端「用户设置 → 高级 → 开发者模式」打开后，右键自己的头像 → 复制用户 ID

allowFrom 只填数字 ID，不要填用户名：用户名能改，ID 不会变。

  • credentials 目录权限过宽：同机其他用户能读到你的 API Key。修复：
chmod 700 ~/.openclaw/credentials
# 或者让审计命令自动修复文件权限类问题
openclaw security audit --fix

6. 按 Provider 收窄工具权限

主力模型可以开 coding 全量工具，但便宜的备用模型更容易被 prompt injection 牵着走，应该收窄：

{
  tools: {
    profile: "coding",
    byProvider: {
      "ollama/llama3.2-vision:latest": { profile: "messaging" },
      "google-antigravity": { profile: "minimal" }
    }
  }
}

键可以是 Provider 名，也可以精确到某个 provider/model。

7. 装第三方 Skill 之前先看审计结果

2026 年 2 月，Koi Security 审计了 ClawHub 上的 2857 个 Skill，发现 341 个恶意 Skill，其中 335 个属于同一个代号 ClawHavoc 的攻击活动：它们在 SKILL.md 里写一段”前置条件”，诱导用户执行安装脚本，最终投放 macOS 窃密木马 Atomic Stealer（Koi Security 原文、The Hacker News 报道）。

截至 2026-10，ClawHub 的每个 Skill 页面都会显示安全审计状态、风险等级和具体发现，命令行也能直接查：

# 安装前查看 ClawHub 的审计结论
openclaw skills verify @owner/skill-name

# 不安装，只看元数据、审核状态和文件
npx clawhub@latest inspect @owner/skill-name

我自己的规则：

  • 只装能看懂 SKILL.md 的 Skill，尤其警惕要求你先执行一段 curl | sh 的”前置步骤”；
  • 同名 slug 有多个作者时，用 @作者/slug 指定，优先选下载量高、审计状态干净的；
  • 需要凭据的 Skill，先确认它要哪些环境变量、会把数据发到哪里。

写作时我装过一个叫 agentverus-scanner 的社区扫描 Skill，2026-10 复核时它已经从 ClawHub 下架，所以不再推荐。

关于 ClawHub 限流
ClawHub API 对匿名请求按 IP 限流，登录后按账号计，额度更高（截至 2026-10 的文档：下载类请求匿名 1200 次/分钟/IP，登录 6000 次/分钟/账号）。多人共用一个出口 IP 时容易碰到 Rate limit exceeded，登录即可缓解：

npx clawhub@latest login    # 浏览器里用 GitHub 账号授权
npx clawhub@latest whoami   # 确认登录状态

登录信息在 Linux 上保存在 ~/.config/clawhub/config.json。被限流时按返回的 Retry-After 等待后重试即可。

调试技巧

8. 三步定位法：doctor → status → logs

出问题别乱猜，按顺序跑：

# 第一步：全面检查并应用推荐修复
openclaw doctor --fix

# 第二步：看全局状态
openclaw status --all     # 只读的完整诊断报告，可以直接贴给别人
openclaw status --deep    # 主动探测各渠道连通性（WhatsApp / Telegram / Discord / Slack / Signal）
openclaw status --usage   # 各 Provider 的用量和配额快照

# 第三步：实时跟踪日志，定位具体错误
openclaw logs --follow

--all 和 --deep 是两个维度：前者汇总一份完整报告，适合排查原因不明的故障；后者真的去拨测渠道，适合确认某个渠道到底通没通。升级大版本后配置字段改名、服务定义过期这类问题，doctor --fix 一般都能处理。

9. 改配置后先跑 config validate

v2026.3.2 新增的命令，在修改配置之后、重启网关之前跑一次：

openclaw config validate --json
# {"valid":true,"path":"/home/user/.openclaw/openclaw.json"}

配置有问题时会返回 "valid": false 和出错的字段路径，比重启网关后从日志里找报错快得多。

10. 回复变慢，先看上下文占用

openclaw sessions
# Tokens 一列显示每个会话的上下文占用，例如：
# 7.0k/128k (5%)    — 正常
# 120k/128k (94%)   — 该压缩了

上下文占用超过 80% 时，在聊天里执行 /compact 压缩上下文，或者 /new 开新会话。

11. BOOTSTRAP.md 被跳过

第一次启动时如果直接问业务问题，workspace 里的 BOOTSTRAP.md（身份初始化引导）可能没有走完，Agent 就没有设置好名字和人格，回复风格很”原始”。手动补一次即可：

openclaw agent --agent main --message "读取 BOOTSTRAP.md 并执行其中的设置步骤"

新建 Agent 后，第一条消息就让它执行 BOOTSTRAP.md，可以省掉这个问题。

12. Cron 任务的投递目标

--channel discord 只选平台，还需要 --to 指定接收目标，否则报 Discord recipient is required。Discord 的目标写法（截至 2026.9.9 文档）：

发送目标--to 写法ID 从哪来
服务器频道channel:<频道ID>会话 key 里 discord:channel: 后面的数字
私信（DM）user:<用户ID>会话 key 里 discord:direct: 后面的数字

只写一串数字时会被当作频道 ID，所以发私信一定要带 user: 前缀。

三种获取 ID 的方式：

# 方式一：从已有会话提取
openclaw sessions --json | python3 -c \
  "import json,sys; [print(s['kind'],'|',s['key']) for s in json.load(sys.stdin).get('sessions',[])]"
# group  | agent:main:discord:channel:111111111111111111
# direct | agent:main:discord:direct:123456789012345678

# 方式二：列出 Bot 能看到的群组 / 频道
openclaw directory groups list --channel discord

# 方式三：按名称查 ID
openclaw channels resolve "频道名称" --channel discord --kind channel
openclaw channels resolve "用户名" --channel discord --kind user
# 发到频道
openclaw cron add --name "daily-report" \
  --cron "0 8 * * *" --tz "Asia/Shanghai" \
  --message "生成日报" \
  --channel discord --to "channel:111111111111111111" \
  --announce

# 发到私信
openclaw cron add --name "daily-dm-report" \
  --cron "0 8 * * *" --tz "Asia/Shanghai" \
  --message "生成日报" \
  --channel discord --to "user:123456789012345678" \
  --announce

已经建好但缺 --to 的任务不用删，openclaw cron edit <job-id> --to "channel:<ID>" 直接补上。

值得装的 6 个 Skills

ClawHub 上的 Skill 很多，但相当一部分是简单的 API 包装或功能重复。下面是我实际留下来的，2026-10 逐个在 ClawHub 上核对过：同一个 slug 往往有多位作者发布，所以都写成 @作者/slug 的形式。安装命令用 2026.9.9 内置的 openclaw skills install；旧版本可以用 npx clawhub@latest install，它会装到当前目录的 skills/ 下。

第一梯队：装完立刻有用

GitHub —— 开发者日常刚需

GitHub Skill 已经随 OpenClaw 内置，不用另装，只要本机的 gh 已登录就会变成 ready。之后在 Discord 里就能查 PR 状态、看 Issue、创建 Issue。配合每天早上的 cron 任务，可以让 Agent 汇总所有 open PR。

Summarize —— 长文快速决策

summarize 也是内置 Skill，但依赖一个叫 summarize 的命令行工具：

# macOS / Linuxbrew
brew install steipete/tap/summarize
# 或者用 npm（注意包名带作用域，npm 上不带作用域的 summarize 是另一个无关的包）
npm install -g @steipete/summarize

openclaw skills check | grep summarize

我最常用的场景是在 Discord 里丢一个链接，让 Agent 把一篇长技术文章压成三句话，再决定要不要细读。PDF、YouTube 视频、本地文件也支持。

Agent Browser —— 无头浏览器自动化

需要抓取登录后才能看的页面、填表单、或者验证前端功能时用，在聊天里描述要做什么，Agent 去操作浏览器并返回截图和数据。ClawHub 上叫这个名字的 Skill 有好几个，例如：

openclaw skills install @rez0/agent-browser

浏览器自动化类 Skill 天然包含执行外部命令、访问网络的代码，审计里出现提示是常态，装之前一定看一遍具体发现。

第二梯队：按需安装

AgentMail —— 给 Agent 一个邮箱

openclaw skills install @adboio/agentmail

基于 AgentMail 这个面向 Agent 的邮件 API 服务，Agent 可以有独立的收件箱，处理注册验证码、邮件分类和自动回复。需要先在 AgentMail 控制台生成 API Key，配置为 AGENTMAIL_API_KEY 环境变量。

2nd Brain —— 结构化的个人知识库

openclaw skills install @coderaven/2nd-brain

在原生记忆系统之上加一层按人物、地点、项目、想法分类的知识库，比单纯往 MEMORY.md 里追加更有条理。注意它在 skills check 里显示的名字是 brain（SKILL.md 里的 name 和 slug 不同）。

Agent Step Sequencer —— 多步骤任务编排

openclaw skills install @gostlightai/agent-step-sequencer

请求包含三步以上、步骤之间有依赖时，它会先给出分步计划等你确认，再把状态持久化下来逐步执行，网关中途重启也能接着跑。它依赖 python3 和环境变量 STEP_AGENT_CMD，没设置时 skills check 会显示缺依赖：

# 写进网关进程能读到的环境（例如 ~/.zshrc，或 systemd / launchd 服务的环境变量）
export STEP_AGENT_CMD="openclaw agent --message"

验证安装结果

openclaw skills check
openclaw skills list --eligible
openclaw skills info summarize

显示 missing 的 Skill 多半是缺命令行工具或环境变量，skills info <name> 会列出它具体要求什么。

三种 Agent 架构

多 Agent 不只是”多建几个 Bot”，下面三种模式按复杂度递增。

模式 1：按渠道隔离（入门）

Discord 归 main Agent，Telegram 归 work Agent，上下文完全隔离：

openclaw agents add work --workspace ~/.openclaw/workspace-work --non-interactive
openclaw agents bind --agent work --bind telegram
openclaw agents set-identity --agent work --name "工作助手" --emoji 💼

适合工作和个人事务分开，避免 Agent 把周末计划混进工作日报。

模式 2：按能力分权（进阶）

不同 Agent 配不同的模型和工具权限：

{
  agents: {
    entries: {
      dev: {
        model: { primary: "anthropic/<模型 ID>" },
        tools: { profile: "coding" }
      },
      reader: {
        model: { primary: "siliconflow/Pro/deepseek-ai/DeepSeek-V3.2" },
        tools: { profile: "messaging", allow: ["browser"] }
      }
    }
  }
}

dev 有完整编码权限，用最强的模型；reader 只能浏览网页和收发消息，用便宜的模型。即使 reader 被 prompt injection，也执行不了 shell 命令。（v2026.3.x 的写法是数组 agents.list: [{ id: "dev", ... }]，2026.9.9 规范为 agents.entries，旧写法仍兼容。）

模式 3：主 Agent + 子 Agent（高级）

主 Agent 可以 spawn 子 Agent 并行处理独立的子任务。并发上限在配置里设：

{
  agents: {
    defaults: {
      maxConcurrent: 4,
      subagents: { maxConcurrent: 8 }
    }
  }
}

典型场景是”调研这三个竞品”：主 Agent 拆出三个子 Agent 分头去查，结果汇总后整合回复。子 Agent 的生命周期由主 Agent 管理。每个子 Agent 都会占用一份模型调用和工具进程，内存小的机器上把并发设低一些。

从简单开始
只接了一个渠道时，模式 1 就够了。等场景复杂到需要权限隔离，再升级到模式 2。不要一上来就搭三层架构。

配置速查：从装好到可用

# 1. 安全加固
openclaw security audit --deep
openclaw security audit --fix      # 自动修复文件权限等问题
# 再手动确认 channels.discord.groupPolicy 为 "allowlist"，并设置 allowFrom

# 2. 效率配置
openclaw completion --install
openclaw models aliases add ds siliconflow/Pro/deepseek-ai/DeepSeek-V3.2

# 3. Skills
npm install -g @steipete/summarize           # summarize 的命令行依赖
openclaw skills install @rez0/agent-browser
openclaw skills install @adboio/agentmail
openclaw skills install @coderaven/2nd-brain
openclaw skills install @gostlightai/agent-step-sequencer

# 4. Hooks
openclaw hooks enable session-memory
openclaw hooks enable command-logger

# 5. 验证
openclaw doctor --fix
openclaw skills check
openclaw health

跑完这一轮，OpenClaw 就从”能聊天”变成”能干活”了。

常见问题：Discord 收到 <tool_call> 原始 XML

用 openrouter/free 当默认模型时容易碰到：你在 Discord 里问 Agent 状态，它回的不是正常文本，而是：

<tool_call><function=session_status></function></tool_call>

原因

openrouter/free 是动态路由，每次请求被转发到 OpenRouter 当时可用的某个免费模型。部分免费模型（例如 Hermes 系列）训练时用的是 XML 形式的工具调用（<tool_call> 标签），而不是 OpenClaw 能解析的 OpenAI tool_calls JSON。OpenClaw 拿到的只是一段文本，就原样转发给了 Discord。

models scan --no-probe 可以列出当前的免费候选模型：

openclaw models scan --no-probe --no-input

加了 --no-probe 不会真的测试，工具支持一列只是元数据默认值，不代表真实能力。要确认哪些模型真的支持工具调用，需要去掉 --no-probe 让它逐个探测，耗时几分钟。

修复

方法 1：换成确定支持工具调用的模型（立即生效）

openclaw models set ds      # 前面设的 DeepSeek-V3.2 别名
openclaw models status
# Default: siliconflow/Pro/deepseek-ai/DeepSeek-V3.2

DeepSeek-V3.2 使用标准的 OpenAI tool_calls 格式，不会出现 XML 泄漏。

方法 2：在免费模型里自动挑一个能用的

想保持零成本的话，让 models scan 实际探测，并把第一个通过的设为默认：

openclaw models scan --yes --set-default
# 对每个候选模型发一次简单的工具调用请求，检查返回的是不是标准 toolCall

方法 3：确认 fallback 链里有靠谱的模型

openclaw models fallbacks list
openclaw models fallbacks add siliconflow/Pro/deepseek-ai/DeepSeek-V3.2

主模型出问题时会按 fallback 顺序切换，链上至少放一个确定支持工具调用的模型。

改完默认模型后重启网关让配置生效：

openclaw gateway restart

然后在 Discord 里发一条会触发工具调用的消息（例如”你的会话 ID 是什么？”），正常情况下会得到一句文本回复，而不是 XML。

常见问题：国内网络下 Discord Bot 在线但不回复

Bot 显示在线，发消息后也有”正在输入”，但就是没有回复。日志里是这样的：

[discord] rest proxy enabled
[discord] gateway proxy enabled
[discord] logged in to discord as <bot-id> (小龙虾)
[tools] message failed: fetch failed
[discord] final reply failed: TypeError: fetch failed

原因

这是我在 v2026.3.x 的 macOS 环境里碰到的情况。channels.discord.proxy 只覆盖了两条路径：

路径是否走 channels.discord.proxy
Gateway WebSocket（收消息）和启动时的少量 REST 查询是
发消息、部署命令等常规 REST 请求否，走 Node.js 进程全局的 fetch

所以 Bot 能登录、能收消息，但回复时直连 Discord API 失败。2026.9.9 的文档对 channels.discord.proxy 的描述仍然是”Gateway WebSocket 和启动时的 REST 查询”，并且明确说 WebSocket 不继承进程的代理环境变量，所以下面”两处都配”的做法依然适用。

修复

第一步：确认本地代理能访问 Discord API

curl -s -o /dev/null -w "HTTP Status: %{http_code}\n" \
  --proxy http://127.0.0.1:7890 \
  --connect-timeout 10 \
  https://discord.com/api/v10/gateway
# HTTP Status: 200 表示代理可用

第二步：配置渠道级代理（解决 WebSocket）

{
  channels: {
    discord: {
      proxy: "http://127.0.0.1:7890"
      // 其余配置不变
    }
  }
}

第三步：给网关进程加全局代理环境变量（解决 REST）

macOS 上网关以 launchd 服务运行，编辑 ~/Library/LaunchAgents/ai.openclaw.gateway.plist，在 EnvironmentVariables 的 <dict> 里加：

<key>HTTPS_PROXY</key>
<string>http://127.0.0.1:7890</string>
<key>HTTP_PROXY</key>
<string>http://127.0.0.1:7890</string>

Linux 上对应的是 systemd 服务的 Environment= 配置。

第四步：重载服务

launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/ai.openclaw.gateway.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/ai.openclaw.gateway.plist

验证

tail -20 ~/.openclaw/logs/gateway.err.log   # 不应再有 fetch failed
tail -20 ~/.openclaw/logs/gateway.log       # 能看到 proxy enabled 和 logged in

之后在 Discord 发消息能正常收到回复，日志里也不再出现 failed to deploy native commands: fetch failed。

为什么两处都要配？
channels.discord.proxy 管的是 OpenClaw 自己建立的 Gateway 连接；HTTPS_PROXY 环境变量管的是进程里其余走全局 fetch 的请求。只配前者能登录但发不出消息，只配后者可能在 Gateway 连接阶段就失败。
