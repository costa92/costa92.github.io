MemPalace 从零上手：给 Claude Code 装本地 AI 记忆（零 API）

 2026-04-16  Coding-Agent MCP RAG Claude-Code 本地优先
MCP RAG Claude-Code 本地优先 记忆系统
Coding-Agent
文章字数:   2.7k
阅读次数:  
   阅读模式

每次新开 Claude Code 会话，上下文从零开始。前一天讨论的技术选型、踩过的坑、字段命名，全部要重新喂一遍——长对话被压缩成几百字摘要，重要的取舍过程已经丢了。

MemPalace 的解法是逐字存储原文，用本地语义检索找回来，核心流程不需要任何 API key。这篇从安装到接入 Claude Code MCP 和自动保存 hook 全流程走一遍。命令和输出按 2026-10 的 3.10.0 版核对过，项目迭代很快，早期教程里的不少命令已经变了。

核心要点

  • 本地优先：默认 ChromaDB 后端，embedding 用 ChromaDB 自带的 all-MiniLM-L6-v2（首次运行下载约 80 MB），检索不走网络
  • 原文保留：wings（人/项目）→ rooms（话题）→ drawers（原文片段）三级结构
  • 接入 Claude Code：截至 3.10.0 有 45 个 MCP 工具，另有 Stop / SessionEnd / PreCompact 三个自动保存 hook
  • Benchmark 可复现：LongMemEval raw 模式 96.6% R@5，held-out 450 题 98.4%

MemPalace 是什么，为什么它反直觉

业界做 AI 记忆的主流路线是”让 LLM 提取事实”——Mem0、Supermemory、Mastra 都走这条路。缺点是：LLM 只留下”用户偏好 PostgreSQL”，原始对话里讨论过的 SQLite、MongoDB、为什么不选的理由全部丢失。

MemPalace 的做法更朴素：原文切块、ChromaDB 默认 embedding、语义检索（新版本还叠加了 BM25 关键词分）。

看一眼它的自描述：

$ pip show mempalace | head -3
Name: mempalace
Version: 3.10.0
Summary: Give your AI a memory — mine projects and conversations into a searchable palace. No API key required.

mempalace --help 里的子命令已经有二十多个，日常用到的主要是这几个：

init       Detect rooms from your folder structure
mine       Mine files into the palace
search     Find anything, exact words
wake-up    Show L0 + L1 wake-up context (~600-900 tokens)
hook       Run hook logic (reads JSON from stdin, outputs JSON to stdout)
mcp        Show MCP setup command for connecting MemPalace to your AI client

反直觉的地方在于：跳过”让 LLM 决定记什么”这一步后，recall 反而更高。项目把这个结论的依据——每道题的原始结果文件——都提交到了仓库里，后面专门讲。

几分钟跑通第一条记忆

Python 要求 3.9 以上。官方推荐用 uv tool install 装到隔离环境，pip 也行：

uv tool install mempalace   # 或 pip install mempalace
mempalace init ~/projects/myapp

init 会扫描项目目录，识别人名、项目名，并按目录结构建 room。注意 3.x 后期 init 默认会尝试用本地 Ollama 做实体识别的辅助判断，没有 Ollama 时会退回纯启发式；不想要这一步就加 --no-llm。它默认是交互式的，加 --yes 自动接受识别结果，加 --auto-mine 初始化完直接开挖。

接下来把项目文件和历史对话挖进去：

# 挖项目代码与文档（默认 --mode projects）
mempalace mine ~/projects/myapp

# 挖对话导出（Claude、ChatGPT、Slack 等导出格式）
mempalace mine ~/chats/ --mode convos

两种模式走的是不同的切分策略：--mode convos 按一问一答切，项目模式按文件切块。第一次 mine 时会下载 embedding 模型。挖完就可以用自然语言搜了，--wing 限定项目、--results 控制条数。下面是我用两份示例文档建的小 palace 的真实输出：

$ mempalace search "why did we switch to GraphQL" --wing myapp --results 2

  [1] myapp / documentation
      Source: adr-graphql.md
      Match:  cosine_sim=0.574  bm25=2.874

      # ADR 003: Switch from REST to GraphQL
      The frontend needed five REST requests to render the dashboard page. We decided to move to GraphQL with Apollo Server.
      ...

  [2] myapp / documentation
      Source: db.md
      Match:  cosine_sim=0.386  bm25=0.304
      ...

开新 session 时，wake-up 输出一段精简的背景上下文（身份 + 关键记忆，官方估计 600–900 token），可以直接贴给模型：

mempalace wake-up --wing myapp

Palace 数据模型：Wings、Rooms、Drawers

Palace 不是扁平的 vector store。它把索引切成三层，让检索可以带作用域跑，而不是每次都在全库里捞：

层级存的是什么例子
Wings 翼人、项目（entity）myapp、alice
Rooms 房间话题，项目模式下通常来自目录结构documentation、graphql-migration
Drawers 抽屉原文片段某个文件或某轮对话的一段原文

这样”在 myapp 项目下找 graphql 迁移相关的对话”可以精确限制到一个 wing + 一个 room，避免把隔壁项目的 GraphQL 讨论也拉进来：

mempalace search "why we rejected federation" \
  --wing myapp --room graphql-migration

命令行之外也有 Python API，适合写到自己的脚本里。注意官方 Python API 文档 的示例漏了 palace 路径参数，3.10.0 里照抄会报 missing 1 required positional argument: 'palace_path'，下面是实际能跑的写法：

from mempalace.config import MempalaceConfig
from mempalace.searcher import search_memories

palace = MempalaceConfig().palace_path  # 默认 palace 位置
res = search_memories(
    "why we switched to GraphQL",
    palace,
    wing="myapp",
    n_results=5,
)
for hit in res["results"]:
    print(hit["room"], hit["source_file"], hit["text"][:80])

存储后端是可替换的：截至 3.10.0，仓库 mempalace/backends/ 下除了默认的 ChromaDB，还有 Qdrant、pgvector、Milvus 和基于 SQLite 的实现，init / mine / search 都接受 --backend 参数。

另外还有个基于本地 SQLite 的时序知识图谱，给每条”实体 A 与实体 B 的关系”带上有效期窗口。这一块单开一篇更合适，这里只提一句：它主要通过 MCP 工具使用（mempalace_kg_add、mempalace_kg_query、mempalace_kg_timeline 等），Python 里对应 mempalace.knowledge_graph.KnowledgeGraph。

接入 Claude Code：MCP 工具 + 自动保存 hook

真正让 MemPalace 发挥价值的是自动化——人手动 mine 和 wake-up 几次就会忘。

最省事的方式是装官方 Claude Code 插件，它会同时注册 MCP server 和自动保存 hook：

claude plugin marketplace add MemPalace/mempalace
claude plugin install --scope user mempalace
# 重启 Claude Code 后在会话里跑 /mempalace:init 完成初始化

只想要 MCP 的话手动加一条。mempalace mcp 会直接打印适合你环境的命令：

claude mcp add mempalace -- mempalace-mcp
# 自定义 palace 路径：claude mcp add mempalace -- mempalace-mcp --palace /path/to/palace

MCP 工具数量在不同版本差别很大：3.3.0 的 README 写的是 29 个，官方文档站有段时间还挂着更早的 19 个，而我用 3.10.0 的 mempalace-mcp 实际列出来是 45 个，覆盖读写抽屉、知识图谱、跨 wing 的 tunnel 导航、agent 日记和任务协调等场景。工具一多，每次会话光工具 schema 就要占不少上下文，所以新版本还提供了一个只有 3 个合并工具的轻量版 mempalace-light-mcp，官方说可以省约 92% 的 schema token。

配好之后对话里直接说”搜一下之前讨论 GraphQL 的那次”，Claude 就会调 mempalace_search；说”把刚才这段存到 myapp 项目下”，会走 mempalace_add_drawer。

自动保存 hook 解决的是”忘了存”的问题：Stop hook 每隔 15 条用户消息让 Claude 把要点存进 palace，PreCompact hook 在上下文压缩之前强制抢救一次，SessionEnd hook 在正常退出时再补存一次。不装插件、手动配置的话，要按 Claude Code 的 hooks 格式写——每个事件是一个数组，里面是带 hooks 列表的匹配组，每条 hook 是 type: "command" 加 command。写在 ~/.claude/settings.json（全局）或项目的 .claude/settings.local.json：

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "mempalace hook run --hook stop --harness claude-code",
            "timeout": 30
          }
        ]
      }
    ],
    "PreCompact": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "mempalace hook run --hook precompact --harness claude-code",
            "timeout": 90
          }
        ]
      }
    ],
    "SessionEnd": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "mempalace hook run --hook session-end --harness claude-code",
            "timeout": 10
          }
        ]
      }
    ]
  }
}

这和官方插件 hooks.json 里注册的三个事件、超时设置一致，只是把插件的 wrapper 脚本换成了直接调 CLI（需要 mempalace 在 PATH 上）。仓库 hooks/ 目录下也有可以直接引用的 mempal_save_hook.sh / mempal_precompact_hook.sh，保存间隔 SAVE_INTERVAL 在脚本里改。网上流传的 "PreCompact": "mempalace save ..." 这种把命令直接写成字符串的配置，Claude Code 不认，mempalace save 这个子命令也不存在。

性能可信吗？96.6% R@5 与团队的纠错记录

项目自己公布的 benchmark 是一回事，能不能在自己机器上跑出来同样的数是另一回事。MemPalace 把每个 benchmark 的逐题结果文件都提交到了 benchmarks/ 下，复现步骤写在 benchmarks/README.md：

git clone https://github.com/MemPalace/mempalace.git
cd mempalace
uv sync --extra dev   # 或 pip install -e ".[dev]"

mkdir -p /tmp/longmemeval-data
curl -fsSL -o /tmp/longmemeval-data/longmemeval_s_cleaned.json \
  https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned/resolve/main/longmemeval_s_cleaned.json

# raw 模式，即 96.6% 那个数；先加 --limit 20 试跑一小段
python benchmarks/longmemeval_bench.py /tmp/longmemeval-data/longmemeval_s_cleaned.json

文档给出的预期输出是 Recall@5: 0.966、Recall@10: 0.982，在 Apple Silicon 上全量 500 题约 5 分钟。

README 里的几个关键数字（截至 2026-10）：

模式数据集指标得分
Raw（纯语义检索，无 LLM）LongMemEval 500 题R@596.6%
Hybrid v4 held-outLongMemEval 450 题R@598.4%
Hybrid v4 + LLM rerankLongMemEval 500 题R@5≥99%
Hybrid v5（无 rerank）LoCoMo 1,986 题R@1088.9%

Hybrid v4 是在 50 道开发题上调参的，held-out 98.4% 是在另外 450 道没参与调参的题上测出来的，所以比全量的 98.6% 更能代表泛化能力。另外要注意，这些都是检索召回率（正确答案所在的会话有没有被捞进前 5 / 前 10），不是最终问答准确率，不能直接和别家公布的 QA accuracy 比。

让我多放一分信任的是团队的 CHANGELOG.md——公开记录撤回和修正。3.3.0（2026-04-13）这一版就改了一批说法：删掉把 retrieval recall 和竞品 QA accuracy 混在同一列的对比表，撤回”+34% palace boost”，把”Haiku rerank 100%”的标题数字换成 held-out 98.4%（最后那 0.6% 是对着具体错题调出来的，项目自己承认属于”teaching to the test”），删掉 LoCoMo top-50 下的 100% 这一行。更正和公告集中记录在仓库的 docs/HISTORY.md 里。这种主动认错的做法，比任何一次 README 里的 benchmark 截图都更有说服力。

装之前：认准官方源，远离仿冒域名

README 顶部挂着一条仿冒站点警告：mempalace.tech 等域名与项目无关，可能分发恶意软件，社区在 issue #267、#326、#506 里多次报告过。官方只有这三个入口：

GitHub:  https://github.com/MemPalace/mempalace
PyPI:    https://pypi.org/project/mempalace/
Docs:    https://mempalaceofficial.com

装完之后可以顺手验证一下来源，避免装到同名包：

pip show mempalace | grep -E "^(Name|Version|Home-page)"
# 项目主页应指向 github.com/MemPalace/mempalace

不要执行任何三方博客里的 curl | sh 安装脚本，官方安装方式只有 uv / pip 和 Claude Code 插件市场。

装完、挖完、接上 MCP 和 hook 之后，日常基本不用再手动敲 mempalace 命令：Claude 会在需要时自己去 palace 里查，hook 负责定期存档。剩下要做的，是隔一段时间用 mempalace status 看看各个 wing 里存了些什么，删掉不该进去的内容。
