Superpowers 写计划、GSD 导入执行实跑：11 次花 4.42 美元，导入被 BLOCKER 拦了两次

 costalong  2026-04-14  更新于 2026-11-24  Coding-Agent Claude Code AI 工程实践

这篇的旧版本里，”ROADMAP 里没有的 phase 会被拒绝”这句话是我读 GSD 的 workflows/import.md 得出来的，没真跑过。这次我在一个小 Go 项目上把整条链路跑了一遍：Superpowers 的 brainstorming 和 writing-plans 写计划，GSD 的 /gsd-import --from 在三种状态下导入，再把同一份需求分别交给 /gsd-execute-phase 和 Superpowers 的 executing-plans 去实现。下面的输出、耗时和费用都来自 2026-11-24 这一轮运行。

环境：Claude Code 2.1.331，全部用 claude -p --model sonnet --output-format stream-json --verbose 非交互调用，每次加 --max-budget-usd 3 兜底；Superpowers 7.0.2（官方插件市场），GSD 是 npm 包 get-shit-done-cc 1.42.3，Go 1.27.4。11 次运行一共花了 4.42 美元。项目、脚本和汇总数据在 blog-go-example/superpowers-gsd-workflow。

靶子：一个只会数行数和词数的 tally

tally 从 stdin 读文本，打印 lines=N words=M，一个 Count 函数加一个表驱动测试，总共 30 多行。要加的功能是 -top N：在计数之后按出现次数输出前 N 个词，大小写不敏感，次数相同按字母序，N=0 时输出不变。

这个需求小到一个人十分钟能写完，但有几处需要拿主意：负数 N 怎么办、标点算不算词的一部分、要不要改 Counts 结构体。正好用来看 brainstorming 会怎么处理这些选择。

brainstorming 和 writing-plans 一次跑完：48 秒，0.27 美元

-p 模式下没人回答问题，brainstorming 一提问会话就结束了。所以我在提示词里写明”我在非交互运行，不能回答问题，需要问我的地方取你推荐的选项，写进设计文档后继续”，然后点名先用 superpowers:brainstorming 再用 superpowers:writing-plans，写完计划就停。

这次运行 8 轮、48 秒、0.27 美元，没有调用 AskUserQuestion。产物是两个文件、两次提交：

060fd84 docs: tally -top N 实现计划
3ec25a4 docs: tally -top N 设计
c179858 init tally

docs/superpowers/specs/2026-11-24-top-flag-design.md   34 行
docs/superpowers/plans/2026-11-24-top-flag.md          83 行

设计文档里有一段”我的决定（供复核）”，把它替我拿的主意集中列了出来：负数 N 报 tally: -top must be >= 0 并以退出码 2 退出；N 大于不同词数时全部输出；分词沿用 strings.Fields，不剥标点，所以 a, 和 a 是两个词。方案比较了三种，选的是新增内部函数 scan 一遍扫描、Count 保持原签名，理由是”Counts 加 map 字段会让结构体不可比较，现有测试用 == 要改”。这条理由是它读了现有测试才得出的，不是模板话。

计划分两个任务，每个任务先写失败测试再实现，开头一行写着 “REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans”。计划里没有 phase: 这类字段，这一点后面导入时会用到。

没有 ROADMAP 时，/gsd-import 直接拦下

先在没有 .planning/ 目录的副本上跑 /gsd-import --from docs/superpowers/plans/2026-11-24-top-flag.md。3 轮、16 秒、0.20 美元，输出（节选）：

GSD > 注意：没有找到 PROJECT.md、REQUIREMENTS.md 和 CONTEXT.md，对应的约束检查已跳过。

### BLOCKER
- [BLOCKER] 这个仓库没有 `.planning/` 目录，也就没有 ROADMAP.md。导入需要计划所属的阶段，
  而 `docs/superpowers/plans/2026-11-24-top-flag.md` 是自由格式的 superpowers 计划，
  没有 `phase:` 和 `plan:` 的 frontmatter。导入流程把"目标阶段在 ROADMAP.md 中不存在"判为阻塞项。

安全门已触发，**没有写入任何文件**，包括 PLAN.md、ROADMAP.md 和提交。

## 解除阻塞的办法
1. 先初始化 GSD：运行 `/gsd-new-project` ……
2. 不用 GSD 编排：直接用 `superpowers:executing-plans` 或 `superpowers:subagent-driven-development` ……
3. 小改动走轻量流程：用 `/gsd-quick` 或 `/gsd-fast` ……

跑完 git status 是干净的，确实什么都没写。第二条建议挺实在：这么小的需求，它自己就建议别走 GSD。

有 ROADMAP、不指定 phase：它推断出 Phase 2

接着我手写了一个最小的 .planning/，没有走 /gsd-new-project（那一步要深度提问，非交互跑不动，也不是这次要测的）。里面有 PROJECT.md（约束：只用标准库、默认输出不能变）、STATE.md、mode 改成 yolo 的 config.json，以及三个 phase 的 ROADMAP：

- [x] **Phase 1: Line and word counts** - Count lines and words from stdin
- [ ] **Phase 2: Frequent words report** - Optional report of the most frequent words
- [ ] **Phase 3: JSON output** - Machine-readable output mode

Phase 2 的成功标准写的是”A flag selects how many top words to print / Default output is unchanged”，故意没提 -top 这个名字。导入命令和上面一字不差，不指定 phase。

10 轮、67 秒、0.43 美元。冲突检测结果是 0 个阻塞、0 个警告、2 条提示，目标定在 Phase 2，文件写到 .planning/phases/02-frequent-words-report/02-01-PLAN.md。推断是对的，它用 gsd-tools.cjs init phase-op 2 拿到了目录名。

但导入没有走完。写完 PLAN.md 后它派了 gsd-plan-checker 子代理校验，报了 2 个阻塞、4 个警告：

### Blockers
1. [task_completeness] Malformed XML: a stray `</output>` closes nothing.
   - Line 87 has `</output>` after `</tasks>`, and no `<output>` is ever opened.
2. [verification_derivation] Frontmatter has no `requirements` field.

### Warnings
1. Both tasks use `type="auto" tdd="true"`. The convention is `type="tdd"` ……
2. `must_haves` has no `key_links`.
3. There is no `<objective>`, `<verification>`, `<success_criteria>` or `<context>` XML ……
4. ROADMAP.md still shows `Plans: TBD` for Phase 2.

第一个阻塞是误报：文件只有 86 行，里面根本没有 <output>，主会话自己 grep 了一下就指出来了。第二个是实打实的，我的 ROADMAP 没给 Phase 2 编需求 ID。结果是 PLAN.md 只 git add 了，没有提交，ROADMAP 也没动，最后一句是”需求 ID 也请你定：用 [TOP-01, TOP-02]，还是留空？”

第一次导入写出的 frontmatter 是这样的，type: "feature" 和 plan: "02-01" 都不是 GSD 自己的写法，checker 第一条警告说的就是它：

---
phase: "02-frequent-words-report"
plan: "02-01"
type: "feature"
wave: 1
depends_on: []
files_modified:
  - main.go
  - main_test.go
  - README.md
autonomous: true
must_haves:
  truths:
    - "`-top N` prints the N most frequent words after the `lines=N words=M` line"
    - "Default output (`-top 0` or no flag) is byte-identical: `lines=%d words=%d\\n`"
    - "Negative N: stderr `tally: -top must be >= 0`, exit code 2, empty stdout"
    ...
---

指定一个不存在的 phase：同样拦下，还建议改回 Phase 2

旧文里那句”推断出 ROADMAP 里没有的编号就会撞上 BLOCKER”，这次直接测：同一份 ROADMAP，命令后面加一句”导入到 Phase 5”。5 轮、20 秒、0.22 美元：

[BLOCKER] 目标阶段不存在
  Found: 你指定导入到 Phase 5。`.planning/ROADMAP.md` 只有 Phase 1 到 3，没有 Phase 4 和 5。
  Expected: 导入目标必须是 ROADMAP 里已有的阶段。
  → 二选一：
    1. 导入到 Phase 2「Frequent words report」。……我推荐这个。
    2. 先用 `/gsd-phase` 在 ROADMAP 里新增 Phase 4 和 5，再回来导入。

GSD > BLOCKED: 1 blocker must be resolved before import can proceed.
我没有写任何文件。

到这里，”ROADMAP 里没有的 phase 会被拒绝”算是跑出来了：没有 ROADMAP、指定不存在的编号，两种情况都在写文件之前停下。有 ROADMAP 的两次导入，它都把计划对到了 Phase 2。

补完导入：又一轮 93 秒、0.46 美元

-p 会话结束后问题就悬在那里。我开了一个新会话，把 checker 的问题列表贴进去，回答”需求 ID 用 [TOP-01, TOP-02]，在 ROADMAP 的 Phase 2 加 Requirements 行”，要求按 import 工作流修正、重跑 checker、提交。11 轮、93 秒、0.46 美元。checker 第二次是 0 阻塞 0 警告，提交信息和 import.md 里规定的格式一致：

178ceba docs(02-frequent-words-report): import plan from 2026-11-24-top-flag.md
 .planning/ROADMAP.md                               |   6 +-
 .planning/STATE.md                                 |   2 +-
 .../phases/02-frequent-words-report/02-01-PLAN.md  | 150 +++++++++++++++++++++

最终 frontmatter 多了 requirements 和 key_links，type 改成 execute，正文补齐了 <objective>、<context>、<verification> 等 XML 段，每个任务的 <verify> 变成可以直接运行的命令。它还把 checker 一条提示落实成了新要求：flag 的用法输出必须写到 stderr，并加了一个 -bogus 参数的测试用例。

type: execute
requirements: [TOP-01, TOP-02]
must_haves:
  key_links:
    - from: "main.go (Count)"
      to: "main.go (scan)"
      via: "Count calls scan and discards the frequency map"
    - from: "main.go (run)"
      to: "main.go (scan, Top)"
      via: "run scans stdin once, then prints Top(freq, n) when n > 0"

有一处不顺：这个版本的 GSD 工作流到处调用 gsd-sdk 命令，而我这边 GSD 是装进 ~/.claude 的，gsd-sdk 不在 PATH 上。导入时模型退回到 node ~/.claude/get-shit-done/bin/gsd-tools.cjs，提交那一步说 gsd-sdk query commit 的输出前后矛盾，最后改用普通 git commit。功能上没出错，但这是模型临场绕过去的，不是工作流设计好的路径。

把导入的四次运行加起来，从 Superpowers 计划到一份能执行的 GSD 计划，有效的两次（第一次导入加补完）花了 160 秒、0.89 美元，比写计划本身还贵。

执行：两条路都把测试跑通了

导入提交后的仓库复制成几份跑 /gsd-execute-phase 2，写完计划、还没有 .planning/ 的仓库复制成几份跑 superpowers:executing-plans。两边提示词都附了同一句”不能回答问题，按推荐项继续，不要推送和开 PR”。跑完后我自己在每份副本里跑 go test -count=1 ./...，再用 printf 'b a B c\n' | go run . -top 2 和 -top -1 的退出码核对行为。

运行墙钟轮次费用提交go test备注
execute-phase，无 gsd-sdk59 秒100.43 美元3通过主会话内联，没派子代理
execute-phase #181 秒100.57 美元6通过派了 1 个 gsd-executor
execute-phase #261 秒120.40 美元3通过主会话内联
execute-phase #360 秒130.48 美元4通过主会话内联
executing-plans #143 秒90.29 美元2通过新建分支 feature/top-flag
executing-plans #2100 秒120.68 美元2通过新建分支，多派了一个 opus 审查子代理

费用是 stream-json 最后一个 result 事件的 total_cost_usd，包含子代理；主会话等后台子代理时会产生两个 result 事件，轮次按两者相加。GSD 的提交数包括它自己更新 SUMMARY、ROADMAP、STATE 的那一两次。

六份结果的行为完全一致：-top 2 输出 lines=1 words=4、b 2、a 1，不带参数时输出和改动前一样，-top -1 退出码是 2，gofmt -l 为空。

几个跑之前没想到的地方：

GSD 的”编排者不亲自干活”没有每次兑现。 execute-phase.md 开头写着 “Orchestrator coordinates, not executes”。第一次 gsd-sdk 不在 PATH 上，模型说”gsd-sdk 不在 PATH 上，我改为直接读 .planning 文件，并内联执行这一个计划”。我把 get-shit-done-cc@1.42.3 装到一个临时目录、把它的 node_modules/.bin 加进 PATH 后又跑了三次，gsd-sdk query init.execute-phase 2 能正常返回 executor_model: sonnet，可只有一次真的派了 gsd-executor，另外两次都以”只有一个计划、一个 wave”为由在主会话里写完了。三次都没有派 gsd-verifier，第 2 次自己写了一份 02-VERIFICATION.md。只有一个计划时，wave 并行本来也没东西可并行。

派了子代理的那次最慢也最贵（81 秒、0.57 美元），但它的提交最规整：测试和实现分开提交，test(02-01): add failing tests for scan and Top 后面跟 feat(02-01): add scan, Top and WordFreq，一共 6 个。内联执行的几次把测试和实现合在一个 feat 提交里。

executing-plans 两次的花费差了一倍多。 第 1 次 43 秒、0.29 美元，做完就停；第 2 次在结尾派了一个审查子代理，子代理指定了 model: "opus"，这一项单独花了 0.35 美元，结论是”没有 Critical 或 Important 级别的问题”。同一个技能、同一份计划、同样的提示词，有没有这一步全看那一次模型怎么走。两次它都先从 main 切出新分支再动手，GSD 的四次都直接提交在 main 上。

只看执行，两边差不多：execute-phase 带 gsd-sdk 的三次平均 0.48 美元，executing-plans 两次平均 0.49 美元。把导入的 0.89 美元算进去，GSD 这条路在这个需求上的总花费是后者的近三倍。换来的是 .planning/ 里多了 SUMMARY、更新过的 ROADMAP 和 STATE：Phase 2 打了勾，下一步提示 /gsd-plan-phase 3。这些东西的价值要到第二、第三个 phase 才看得出来，这次没有跑。

这次没测到的

  • 计划只有两个任务、一个 PLAN.md，GSD 按 wave 并行多个计划的能力完全没用上，上面的耗时对比不能外推到多计划的 phase。
  • .planning/ 是我手写的最小版本，没有 REQUIREMENTS.md 和 CONTEXT.md，导入时”和锁定决策矛盾””和已有需求矛盾”这两类 BLOCKER 没机会触发。
  • 每种执行方式只跑了 2 到 3 次，表里的数字只能看量级，executing-plans 两次就差出一倍。
  • 全程非交互。交互使用时，brainstorming 会真的问问题，导入在 checker 不通过时会停下来等人，耗时主要取决于人。
  • GSD 已经以 GSD Core（open-gsd/gsd-core，npm 包 @opengsd/gsd-core，今天查到的最新版是 1.23.0）的名义继续开发，原仓库 gsd-build/get-shit-done 已归档，get-shit-done-cc 在 npm 上被标为不再维护。我测的是旧包 1.42.3，GSD Core 的 /gsd-import 有没有变化我没有测。

按这次的结果，我会这样接

# 0. 先有 ROADMAP，并给要导入的 phase 写上 Requirements 行（这次少了它，checker 不通过）
/gsd-new-project            # 已有代码库在 1.42.3 里先 /gsd-map-codebase

# 1. 设计和计划
/superpowers:brainstorming
/superpowers:writing-plans

# 2. 导入，不指定 phase 也能推断，但写明更省一轮来回
/gsd-import --from docs/superpowers/plans/<计划文件>.md
#    checker 报问题时会停下，只暂存不提交；回答完它才提交

# 3. 执行
/gsd-execute-phase <N>

如果像这次一样只有一个两三步的小需求，/gsd-import 在第一次被拦时给的建议是对的：直接用 executing-plans 跑 Superpowers 的计划，最快的一次 43 秒、0.29 美元，比单是导入的花费还少。gsd-sdk 要在 PATH 上，否则 GSD 的工作流每一步都要靠模型临场找替代办法。
