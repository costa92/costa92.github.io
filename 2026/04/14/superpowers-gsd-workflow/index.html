Superpowers + GSD：Claude Code 两套工作流怎么分工和衔接

 2026-04-14  Coding-Agent Claude Code 工作流 Superpowers GSD
Claude Code 工作流 Superpowers GSD Agent
Coding-Agent

阅读次数:  
   阅读模式

Superpowers 管”想清楚、写对”：brainstorming、writing-plans、执行与 review，产物是设计文档和实现计划。GSD 管”按阶段推进、可追踪”：ROADMAP 里的 phase、按 wave 执行的 PLAN.md、验证与交付。两者的计划格式不同，衔接点是 /gsd-import --from。

下文的命令名、参数和产物路径，我在 2026-10-30 对照本机已安装的 skill 文件逐个核对过：Superpowers 7.0.0（官方插件市场）和 GSD 1.42.3（旧 npm 包 get-shit-done-cc），GSD Core 的差异另外对照了它的命令文档。

单独用哪一种都差一块

只用 Superpowers：brainstorming 很好用，计划也写得细，但项目一长就缺全局视角，哪些阶段做完了、当前在第几步，全靠自己记。

只用 GSD：ROADMAP 和 PLAN.md 很规整，但前期讨论不充分的话，计划方向本身可能就是错的，GSD 只会把错的方向执行得很有节奏。

我的做法是组合：Superpowers 负责”做什么、怎么设计”，GSD 负责”按什么节奏做、做到哪了”。

安装：两个渠道选一个，别像我一样都装

Superpowers

obra/superpowers 是一套 Claude Code 技能库：先澄清需求、再写计划、再按计划执行和审查。在会话里二选一：

# 方式一：Anthropic 官方插件市场
/plugin install superpowers@claude-plugins-official

# 方式二：作者自己的插件市场
/plugin marketplace add obra/superpowers-marketplace
/plugin install superpowers@superpowers-marketplace

两个渠道同时装会出现两份同名技能。我本机就是这样，查 ~/.claude/plugins/installed_plugins.json 才发现：

superpowers@superpowers-marketplace 6.3.0
superpowers@claude-plugins-official 7.0.0

两个版本差了一个大版本。7.0.0（2026-10-09）重写了 brainstorming，release notes 里说它会先问你想要什么、为什么，复述给你确认，再”matches the process to the work, from just doing it to writing a full design”；6.3.0 还是旧的提问流程。两份同时在，同一个场景可能重复触发两份技能，提示也会互相打架。留官方市场那份，把另一个卸掉。

验证：新开会话输入 /superpowers:，补全列表里应该有 brainstorming、writing-plans 等技能。在 Claude Code 里，Superpowers 通过插件自带的 session-start hook 加载 using-superpowers，不需要手动初始化。

早期的 /brainstorm、/write-plan、/execute-plan 斜杠命令已经没了。release notes 写得很清楚：v5.1.0（2026-04-30）”Legacy slash commands removed”。现在用全名调用 /superpowers:brainstorming，或者用自然语言描述需求让它自动触发。

GSD

GSD（Get Shit Done）是一个规格驱动开发框架。原仓库 gsd-build/get-shit-done 已经归档，npm 包 get-shit-done-cc 的 latest 停在 1.42.3；项目以 GSD Core 的名义在 open-gsd/gsd-core 继续开发。2026-10-30 查 GitHub 和 npm 的公开接口：

gsd-build/get-shit-done  archived=True   last push 2026-05-31
open-gsd/gsd-core        archived=False  last push 2026-10-30
npm get-shit-done-cc     latest 1.42.3
npm @opengsd/gsd-core    latest 1.19.0

新装用（命令来自 GSD Core 仓库的 README 和 docs/how-to/install-on-your-runtime.md，我没有实际装过 GSD Core）：

npx @opengsd/gsd-core@latest

按文档的说法，交互式安装程序会让你选目标运行时和安装范围，也可以用 --claude 加 --global 或 --local 做非交互安装。装完在会话里跑 /gsd-help（1.42.3 里有这个命令），能看到命令列表就算成功。

我本机还是旧的 1.42.3（~/.claude/get-shit-done/VERSION），命令名基本一致，都是 /gsd-*，但有个差别会影响上手：接入已有代码库，GSD Core 用 /gsd-onboard，1.42.3 里没有这个 skill，要先 /gsd-map-codebase 生成 .planning/codebase/ 下的分析文档，再 /gsd-new-project。

Superpowers：先想后做

技能在合适的时机自动触发，也可以用 /superpowers:<技能名> 手动调用。下表的产物路径来自 7.0.0 的 SKILL.md：

技能作用产物
brainstorming通过提问澄清需求、比较方案，分段确认设计docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md，并提交
using-git-worktrees开工前确保有隔离的工作区隔离的 worktree
writing-plans把设计拆成小任务，写明文件路径、代码和验证步骤docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md
subagent-driven-development / executing-plans前者每个任务派一个子代理执行；后者由当前会话自己实现代码和提交
test-driven-development实现时强制 RED-GREEN-REFACTOR测试先行的代码
requesting-code-review完成任务或合并前对照需求做 reviewreview 结论
finishing-a-development-branch测试全过后决定怎么合入合并或 PR

executing-plans 在 6.4.1 被重写成”Native execution”，release notes 的说法是 “a cheaper alternative to subagent-driven development”；7.0.0 的描述是在当前会话里由你自己当实现者，适合你选了 inline 执行或者没有子代理工具的情况。

brainstorming 的设计文档是 writing-plans 的输入，writing-plans 的计划是执行阶段的蓝图。计划写完，自己读一遍再让它执行，这是控制 AI 行为成本最低的时机。我还习惯在 brainstorming 收尾时追问一句：”如果按推荐方案做，第一步是什么？”

GSD：按 phase 推进，按 wave 并行

GSD 把工作拆成 phase，每个 phase 有目标、依赖和成功标准，规划文件都放在项目的 .planning/ 目录。核心命令（参数来自 1.42.3 各 SKILL.md 的 argument-hint）：

# 新项目：深度提问 → 调研 → 需求 → ROADMAP
/gsd-new-project

# 已有代码库：1.42.3 先跑这个；GSD Core 可以用 /gsd-onboard
/gsd-map-codebase

# 规划前先讨论某个 phase 的实现决策（可选）
/gsd-discuss-phase 1

# 为 phase 1 做调研、写计划并校验计划
/gsd-plan-phase 1

# 执行 phase 1 的所有计划（按 wave 并行；--wave N 只跑某一批）
/gsd-execute-phase 1

# 对 phase 1 的交付做对话式验收
/gsd-verify-work 1

# 查看进度，--next 直接推进到下一步
/gsd-progress
/gsd-progress --next

phase 定义在 .planning/ROADMAP.md 里，大致是这样的结构：

### Phase 3: MVP 实现

**Goal**: 完成核心功能可运行的最小版本
**Depends on**: Phase 2
**Success Criteria** (what must be TRUE):
  1. 用户可以完成一次完整操作流程
  2. 核心模块有单元测试覆盖

Depends on 和 Success Criteria 让”做完了吗”变成一个可以对照检查的问题。

/gsd-plan-phase 在 .planning/phases/<phase 目录>/ 下生成一个或多个 PLAN.md，文件名形如 03-01-PLAN.md，frontmatter 里的 wave 是执行批次、depends_on 是依赖的其他计划。/gsd-execute-phase 把同一 wave 里互不依赖的计划交给新上下文的子代理并行执行，一个 wave 完成再进下一个。重活放到干净的子代理上下文里，主会话保持精简，这是 GSD 对付上下文腐烂的办法。

用 /gsd-import 把计划接过去

这张图是示意，画得不精确：图里”PLAN.md 在两层之间传递”是简化画法，两者的计划不是同一个文件。Superpowers 的计划在 docs/superpowers/plans/，GSD 读的是 .planning/phases/ 下带 phase:、plan:、type: 等 frontmatter 的 PLAN.md，直接让 /gsd-execute-phase 去执行 Superpowers 的计划行不通。

/gsd-import 的参数只有两种形式：--from <filepath> 导入外部计划，--from-gsd2 把 GSD-2 的 .gsd/ 项目反向迁回 .planning/。我读了 1.42.3 的 workflows/import.md，--from 的流程是：冲突检测 → 写成 GSD 格式的 PLAN.md → 交给 gsd-plan-checker 校验 → 提交。冲突分三级：

[BLOCKER]  任一出现就不写任何文件：
           计划指向 ROADMAP.md 里不存在的 phase
           技术栈和 PROJECT.md 的约束矛盾
           和某个 CONTEXT.md 里锁定的决策矛盾
           和 REQUIREMENTS.md 里的已有需求矛盾
[WARNING]  需要你确认：和未完成的计划改同一批文件、depends_on 指向未完成的计划、
           phase 编号和 ROADMAP 冲突、需求部分重叠
[INFO]     只提示：用到了技术栈之外的新库、会往 ROADMAP 里加新 phase

第一条 BLOCKER 决定了顺序：没有 ROADMAP 就没有 phase，导入会被直接拒绝，所以必须先 /gsd-new-project（已有代码库先 map），再导入。另外它会把计划改名成 {NN}-{MM}-PLAN.md 的形式，写完后自动提交，提交信息是 docs({phase}): import plan from <文件名>。

还有一个容易忽略的点：Superpowers 的计划没有 phase: 字段。import.md 对这类非 GSD 格式的文档只写了 phase 目标 “from frontmatter or inferred from content”，也就是由模型从正文里推断；推断出一个 ROADMAP 里没有的编号，就会撞上第一条 BLOCKER。所以导入前在计划开头写明目标 phase（比如一行”目标 phase：Phase 3 MVP 实现”），或者在调用 /gsd-import 的同一条消息里说清楚要导入到哪个 phase。

完整顺序：

# 0. 先建 GSD 项目，拿到 ROADMAP（已有代码库先 /gsd-map-codebase）
/gsd-new-project

# 1. 探索方向，产出设计文档（docs/superpowers/specs/）
/superpowers:brainstorming

# 2. 写实现计划（docs/superpowers/plans/），写完自己通读一遍，并在开头写明目标 phase
/superpowers:writing-plans

# 3. 导入 GSD，冲突在这一步列出来
/gsd-import --from docs/superpowers/plans/<计划文件>.md

# 4. 执行并验收
/gsd-execute-phase 1
/gsd-verify-work 1

# 5. 合并前对照需求做一次 review
/superpowers:requesting-code-review

# 6. 推进到下一步
/gsd-progress --next

需求很小的话不需要走完整套，让 Superpowers 的 subagent-driven-development 或 executing-plans 执行它自己的计划就够了。GSD 的价值在多阶段、跨好几天的项目里才明显。

两者的分工对照

维度单独用 Superpowers单独用 GSDSuperpowers + GSD
方向探索brainstormingdiscuss-phasebrainstorming
任务拆解writing-plansplan-phasewriting-plans → gsd-import
执行节奏按计划逐任务执行phase + wavephase + wave
跨会话进度追踪弱强（STATE / ROADMAP）强
代码质量把关requesting-code-reviewverify-work两者都有

GSD 本身也有 discuss-phase 和 plan-phase，单用 GSD 并不是没有前期探索。我更习惯 Superpowers 的 brainstorming 节奏，所以把探索和设计交给它；一套工具够用的话，只用其中一个完全可以。第一轮会慢一些，从第二个 phase 开始，之前的设计文档、ROADMAP 和决策记录都能复用。
