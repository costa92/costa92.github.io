Superpowers + GSD：Claude Code 的双模式工作流实战

 2026-04-14  Coding-Agent Claude Code 工作流 Superpowers GSD
Claude Code 工作流 Superpowers GSD Agent
Coding-Agent
文章字数:   2.8k
阅读次数:  
   阅读模式

核心要点

  • Superpowers 管”想清楚、写对”：brainstorming → writing-plans → 执行与 review，产物是设计文档和实现计划
  • GSD 管”按阶段推进、可追踪”：ROADMAP 里的 phase、按 wave 执行的 PLAN.md、验证与交付
  • 两者的产物格式不同，衔接点是 /gsd-import --from，不是”自动读同一个 PLAN.md”
  • 版本说明：命令以 2026-10 的 Superpowers 6.4.x 和 GSD Core 为准

痛点：单独用哪一种都不够

用 Claude Code 一段时间后，你可能会遇到两类困境。

只用 Superpowers 技能：brainstorming 很好用，计划也写得细，但计划一多、项目一长，就缺一个全局视角：哪些阶段做完了、哪些还欠着、当前在第几步，全靠你自己记。

只用 GSD 工作流：ROADMAP 和 PLAN.md 很规整，但如果前期讨论不充分，计划本身的方向可能就是错的，GSD 只会把错的方向执行得很有节奏。

我自己的做法是把两者组合起来：Superpowers 负责”做什么、怎么设计”的探索和判断，GSD 负责”按什么节奏做、做到哪了”的推进和追踪。

前置准备：安装两个系统

安装 Superpowers

Superpowers 是 obra/superpowers 提供的一套 Claude Code 技能库，本质上是一套结构化的开发方法论：先澄清需求、再写计划、再按计划执行和审查。它在 Claude Code 里有两个安装渠道，在 Claude Code 会话里输入：

方式一：Anthropic 官方插件市场（推荐）

/plugin install superpowers@claude-plugins-official

方式二：作者自己的插件市场

/plugin marketplace add obra/superpowers-marketplace
/plugin install superpowers@superpowers-marketplace

安装需要访问 GitHub，网络超时的话先检查终端的代理设置。两个渠道二选一即可，同时装会出现两份同名技能。

验证是否装好：新开一个会话，输入 /superpowers: 看补全列表里有没有 brainstorming、writing-plans 等技能；或者直接说一句”帮我规划一下这个功能”，Agent 会自动触发 brainstorming 技能。Superpowers 通过会话启动 hook 加载 using-superpowers，不需要手动初始化。

命令名的变化：早期版本提供过 /brainstorm、/write-plan、/execute-plan 这类斜杠命令（也有教程写成 /superpowers:brainstorm），它们在 v5.1.0（2026-04-30）被移除了。现在只有技能，用全名调用，例如 /superpowers:brainstorming，或者直接用自然语言描述需求让它自动触发。

安装 GSD

GSD（Get Shit Done）是一个面向 Claude Code 等编码 Agent 的规格驱动开发框架。它的原仓库 gsd-build/get-shit-done 已在 2026-06 归档，npm 包 get-shit-done-cc 也已停止维护（最后版本 1.42.3）；项目现在以 GSD Core 的名义在 open-gsd/gsd-core 继续开发。新装请用：

npx @opengsd/gsd-core@latest

交互式安装程序会让你选择目标运行时（Claude Code、OpenCode、Cursor 等）和安装范围。也可以用 --claude 加 --global（所有项目可用）或 --local（仅当前项目）做非交互安装。

已经装了旧版 get-shit-done-cc 的话，命令名基本一致（/gsd-*），可以继续用，但新功能只会出现在 GSD Core 里，建议按官方迁移说明切过去。

验证安装成功

/gsd-help

能看到 GSD 的命令列表（/gsd-new-project、/gsd-plan-phase、/gsd-execute-phase 等）即安装成功。

第一层：Superpowers 技能系统

Superpowers 的技能覆盖开发全流程。官方 README 给出的基本工作流是这样的顺序，每个技能在合适的时机自动触发，也可以手动用 /superpowers:<技能名> 调用：

技能作用产物
brainstorming通过提问澄清需求、比较方案，分段确认设计docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md
using-git-worktrees设计确认后，在新分支的独立 worktree 里开工隔离的工作区
writing-plans把设计拆成 2–5 分钟粒度的小任务，写明文件路径、代码和验证步骤docs/superpowers/plans/YYYY-MM-DD-<feature>.md
subagent-driven-development / executing-plans按计划执行：前者每个任务派一个新子代理并逐个 review，后者在当前会话内执行、最后统一 review代码和提交
test-driven-development实现过程中强制 RED-GREEN-REFACTOR测试先行的代码
requesting-code-review任务之间对照计划做 review，按严重程度报告问题review 结论
finishing-a-development-branch全部完成后跑测试，给出合并 / PR / 保留 / 丢弃的选项合并或 PR

这些技能的价值是强制先想后做：brainstorming 产出的设计文档是 writing-plans 的输入，writing-plans 产出的计划是执行阶段的蓝图。写计划之后，务必自己读一遍再让它执行——这是你控制 AI 行为成本最低的时机。

执行一次 brainstorming

/superpowers:brainstorming

它会一轮一轮地问你问题背景、约束条件和期望结果，列出几种方案并分析利弊，最后分段给出设计让你确认，确认后写入 docs/superpowers/specs/ 并提交。

我自己的习惯是在 brainstorming 收尾时追问一句：”如果按推荐方案做，第一步是什么？”——这能把探索结论直接转成计划的起点。

第二层：GSD 工作流

GSD 的核心思想是：把工作拆成 phase（阶段），每个 phase 有明确的目标、依赖和成功标准，所有规划文件放在项目的 .planning/ 目录里。

GSD 的核心命令

# 新项目：深度提问 → 调研 → 需求 → ROADMAP
/gsd-new-project

# 已有代码库：首次接入 GSD
/gsd-onboard

# 规划前先讨论某个 phase 的实现决策（可选）
/gsd-discuss-phase 1

# 为 phase 1 做调研、写计划并校验计划
/gsd-plan-phase 1

# 执行 phase 1 的所有计划（按 wave 并行）
/gsd-execute-phase 1

# 对 phase 1 的交付做验收测试
/gsd-verify-work 1

# 查看进度，--next 自动推进到下一步
/gsd-progress
/gsd-progress --next

GSD 的 phase 不局限于”开发阶段”，它可以是”技术调研”、”MVP 实现”、”Beta 测试”。phase 的边界由你定义，GSD 负责追踪状态和依赖。

ROADMAP 里的 phase 依赖

phase 定义在 .planning/ROADMAP.md 里，每个 phase 都写明依赖和成功标准，大致是这样的结构：

### Phase 3: MVP 实现

**Goal**: 完成核心功能可运行的最小版本
**Depends on**: Phase 2
**Success Criteria** (what must be TRUE):
  1. 用户可以完成一次完整操作流程
  2. 核心模块有单元测试覆盖

Depends on 和 Success Criteria 让”做完了吗”变成一个可以对照检查的问题，而不是凭感觉判断。

PLAN.md 和 wave

/gsd-plan-phase 会在 .planning/phases/<phase 目录>/ 下生成一个或多个 PLAN.md（文件名形如 03-01-PLAN.md）。每个计划的 frontmatter 里有两个关键字段：

  • wave：执行批次，规划时就算好了
  • depends_on：这个计划依赖哪些其他计划

/gsd-execute-phase 会把同一 wave 里互不依赖的计划交给新上下文的子代理并行执行，一个 wave 完成后再进入下一个；也可以用 --wave N 只跑某一批。这正是 GSD 对付”上下文腐烂”的办法：重活都放到干净的子代理上下文里，主会话保持精简。

两者如何衔接

上面两张示意图里画的”PLAN.md 在两层之间传递”需要说得更精确一点：两者的计划不是同一个文件。Superpowers 的计划写在 docs/superpowers/plans/ 下，格式是给它自己的执行技能用的；GSD 读的是 .planning/phases/ 下带 wave / depends_on frontmatter 的 PLAN.md。直接让 /gsd-execute-phase 去执行 Superpowers 的计划文件是行不通的。

真正的衔接点是 GSD 的 /gsd-import：它读入一份外部计划，先和项目里已经确定的决策（PROJECT.md 等）做冲突检测，再改写成 GSD 格式的 PLAN.md，并交给计划校验器检查。

具体流程

第一步：brainstorming 探索方向

/superpowers:brainstorming
> 我们的内部工具需要从单体拆成微服务，怎么拆？什么时候拆？

确认设计后，它会把设计文档写进 docs/superpowers/specs/。

第二步：writing-plans 生成实现计划

/superpowers:writing-plans
> 基于刚确认的设计，写第一阶段的实现计划

计划写进 docs/superpowers/plans/。到这一步先停下，自己通读一遍计划。

第三步：导入 GSD，交给 phase 管理

/gsd-import --from docs/superpowers/plans/<计划文件>.md

导入时如果计划和项目已有决策冲突，GSD 会先列出来让你决定，而不是直接写入。导入完成后，用 GSD 的命令推进：

/gsd-execute-phase 1
/gsd-verify-work 1

第四步：用 Superpowers 的 review 把关质量

/superpowers:requesting-code-review

在每个 phase 收尾、准备合并之前调用，对照计划检查实现，按严重程度列出问题。

如果你的需求很小，其实不需要走完整套：直接让 Superpowers 的 subagent-driven-development 或 executing-plans 执行它自己的计划就够了。GSD 的价值在多阶段、跨好几天的项目里才明显。

为什么这个组合值得用

Superpowers 解决”想清楚”的问题。 brainstorming 的连续提问逼你在动手前审视方向，writing-plans 把模糊的想法翻译成带验证步骤的任务列表。

GSD 解决”做完整”的问题。 phase 的依赖和成功标准让进度可见，wave 机制让大任务分批交付、分批验证，STATE 和 ROADMAP 让你隔几天回来也知道做到哪了。

两者叠加后，Claude Code 的行为更可预测。 每个阶段有明确的输入和退出标准，Agent 在每个节点都知道该做什么、不该做什么。

维度单独用 Superpowers单独用 GSDSuperpowers + GSD
方向探索brainstormingdiscuss-phasebrainstorming
任务拆解writing-plansplan-phasewriting-plans → gsd-import
执行节奏按计划逐任务执行phase + wavephase + wave
跨会话进度追踪弱强（STATE / ROADMAP）强
代码质量把关requesting-code-reviewverify-work两者都有

需要说明的是，GSD 本身也有 discuss-phase 和 plan-phase，单用 GSD 并不是”没有前期探索”。我更习惯 Superpowers 的 brainstorming 节奏，所以把探索和设计交给它；如果你觉得一套工具就够，完全可以只用其中一个。

快速上手：第一次组合调用

# 0. 初始化 GSD 项目（已有代码库用 /gsd-onboard）
/gsd-new-project

# 1. 探索方向，产出设计文档
/superpowers:brainstorming

# 2. 写实现计划
/superpowers:writing-plans

# 3. 把计划导入 GSD
/gsd-import --from docs/superpowers/plans/<计划文件>.md

# 4. 执行并验收
/gsd-execute-phase 1
/gsd-verify-work 1

# 5. 收尾前做一次 review
/superpowers:requesting-code-review

# 6. 推进到下一步
/gsd-progress --next

第一轮会慢一些（brainstorming 和写计划都要求你先想清楚），但从第二个 phase 开始，之前的设计文档、ROADMAP 和决策记录都能复用，节奏会明显顺起来。
