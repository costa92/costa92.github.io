Karpathy 的 LLM Wiki：三层架构搭建持久化的个人 AI 大脑

 2026-04-27  AI RAG Karpathy LLM-Wiki Claude-Code
RAG Karpathy LLM-Wiki Claude-Code Obsidian AI知识库
AI
文章字数:   6.2k
阅读次数:  
   阅读模式

Karpathy 在 X 上分享的一份 gist 给”个人 AI 知识库”提了一种新组织方式——比 RAG 更轻、可累积、不绑厂商。

核心要点

  • RAG 在每次提问时把知识从 chunks 重新拼起来，没有累积、不会跨文档收敛、矛盾难以标记
  • Karpathy 的 LLM Wiki 把检索对象换成 LLM 维护的”持久化、可复利的知识资产”——markdown 文件 + cross-link + index
  • 三层架构：Raw Sources（不可变原始文件）+ Wiki 层（LLM 生成的概念页/实体页）+ Schema（CLAUDE.md 这类约束文件）
  • 三个操作：Ingest（吸收新源）/ Query（带引用回答）/ Lint（体检——清理矛盾、过期、孤儿页）
  • 落地组合：Claude Code（或 Codex 等 agent）按 schema 维护 wiki，Obsidian 浏览本地文件

OpenAI 创始成员、特斯拉前 AI 总监 Andrej Karpathy 在 X 上贴出的这份 gist，引发了”个人 AI 知识库”圈一次明显的范式校准。全文不到两千词，Karpathy 自己说它是一份”idea file”，本意就是让你直接贴给自己的 agent 去落地。里面提出的几个术语——Raw sources、the wiki、the schema、Ingest / Query / Lint——每一个都可以直接对应到一份目录结构。

YouTube 频道 HC AI 说人话 的视频《3 层架构打造个人 AI 大脑》做过一次实战演示，用 Claude Code + NotebookLM + Obsidian 搭了”墨尔本旅游指南”和”交易策略库”两套 wiki。这篇文章把 Karpathy 的原文逐层拆开，和 RAG 做对比，再给出落地路径。引号里的英文都摘自 gist 原文。

为什么 RAG 不够？

Karpathy 一句话本质
“the LLM is rediscovering knowledge from scratch on every question. There’s no accumulation.” —— “在每次提问时让 LLM 从零重新发现知识，没有累积。”

把 RAG 的痛点拆开，有四条比较致命的。

第一条是跨文档拼凑。同一个概念散落在 50 份原始文件里，每次 query 都要重新切 chunk、重新 embedding、重新 top-k 排序——同一个问题第二次问，依然走完整条管线，而且因为 embedding 模型对长尾相似度的判断带噪声，两次给出的答案常常不一样。这种不一致在面向用户的产品里尤其麻烦：今天能答对、明天答错的”幻觉漂移”很难做回归。

第二条是矛盾标记困难。假设知识库里有一份”A 餐厅好吃”的旧文档，又被加进来一份”A 餐厅食安事件”的新文档。RAG 的标准做法是寄希望于 top-k 同时命中两份并由 LLM 现场判断；如果 embedding 离得不够近，新事件会被悄悄漏掉。Karpathy 的思路是把这件事前置到写入阶段：新 source 进来时，LLM 更新相关的实体页，并且 “noting where new data contradicts old claims”——“A 餐厅”那一页在 ingest 新文档的那一刻就会被改写、标出前后矛盾。检索对象从”原始 chunks 的相似度排序”换成”已经过 LLM 判断的概念页”，这是认知上的一次升级。

第三条是平台锁定。RAG 的本质是把知识压成某个特定 embedding 模型的向量空间。换 embedding，索引几乎要重建；换厂商，工程成本立即可见。Wiki 派的反向论点：把知识落地为 markdown 文件，OpenAI / Anthropic / Qwen / MiniMax / GLM 任何一家都能直接读，不需要二次工程。这件事在 LLM 厂商竞争白热化的当下特别有意义——你不希望自己的知识库今年用 OpenAI、明年用 Anthropic 时还要重做一遍向量化。

第四条是Token 经济差。每次 query 都要把 top-k chunks 灌进 context，每条 chunk 几百到几千 token，光检索就吃掉几 K token；如果还要 rerank、加引用、做 citation 解析，token 用量翻倍。Wiki 派把”昂贵的综合”前置到 ingest 阶段——一次写入，多次读取——平均到每次 query 上的 token 成本明显更低。我的判断是这条是 wiki 派最被低估的优势——前期写 schema 多花的几小时，会在后续每次 query 上回本。

project/
  raw/                          # 不可变 source 层
    karpathy-llm-wiki.txt
    youtube-hc-ai.md
  wiki/                         # LLM 维护层
    concepts/
      llm-wiki.md
      rag-vs-wiki.md
    entities/
      andrej-karpathy.md
    index.md
    log.md
  CLAUDE.md                     # schema
# RAG 的典型 query 路径：每次都重来
embed(question) -> ANN search -> top_k chunks -> rerank -> context -> LLM

# Wiki 的 query 路径：先看 index 再读页
read(index.md) -> resolve_relevant_pages() -> read(N pages) -> LLM

注意第二条管线里没有 embedding 这一步——LLM 自己读 index 就能定位文件。Karpathy 原文给的经验规模是”~100 sources, ~hundreds of pages”，在这个量级上光靠 index 就够用，不需要 embedding 那一套基础设施。

三层架构详解

Raw Sources：不可变的原始来源

Karpathy 原文：“your curated collection of source documents. Articles, papers, images, data files. These are immutable — the LLM reads from them but never modifies them.”

第一层是 Raw Sources——你 curate 来的原始资料。文章、论文、PDF、网页存档、屏幕截图都行。关键约束是不可变（immutable）。 一旦放进 raw/ 目录，LLM 在后续工作中只读不写。这是整个体系的”事实地基”——如果地基会被随手编辑，上面的 wiki 页就失去了可追溯性。

什么算”好的 raw 源”？三个判断标准：可定位（有 stable URL 或本地文件路径）、可注明时间（知道是哪一天的快照）、可去重（不要把同一篇文章存三份不同标题的副本）。一个实用的做法是给每份 raw 文件取一个稳定 id（内容 hash 或时间戳），让 wiki 层用 id 引用，而不是用人类标题——标题会改，id 不会。网页文章可以用 gist 里推荐的 Obsidian Web Clipper 浏览器插件直接存成 markdown。

# 一个简单的 ingest 入口：把 PDF 抽成文本存到 raw/，文件名用 sha1 前 8 位
# pdftotext 来自 poppler-utils；pandoc 不能读 PDF，别用它做这一步
mkdir -p raw/
HASH=$(sha1sum paper.pdf | cut -c1-8)
pdftotext -layout paper.pdf "raw/${HASH}.md"
# raw/<hash>.md 的 frontmatter 约定，给 wiki 层做来源引用用
---
source_id: a1b2c3d4
title: 原文标题
captured_at: 2026-04-27
url: https://example.com/paper
hash_algo: sha1
---

Wiki 层：LLM 完全拥有

Karpathy 原文：“a directory of LLM-generated markdown files. Summaries, entity pages, concept pages, comparisons, an overview, a synthesis. The LLM owns this layer entirely.”

第二层是 Wiki 层。所有页面由 LLM 生成、由 LLM 维护——原文的说法是 “You never (or rarely) write the wiki yourself”。Karpathy 给出了几种页面类型：summary（一份 source 的浓缩）、entity（一个具体对象，比如某家餐厅或某个人）、concept（一个抽象概念，比如”风险管理”)、comparison（横向对比）、overview / synthesis（跨多个 entity/concept 的综述）。

每页一定包含两类 link：指向 raw 的引用（当前页的事实来源）和指向其他 wiki 页的 cross-link（建立知识网络）。后者是和 RAG 最大的差异——RAG 切完 chunk 后，跨文档关系就丢了；wiki 层把这层关系重新显式建出来。一旦 cross-link 成网，LLM 在 query 时就可以从一个入口页”游走”到相关页，比单纯按语义相似度捞 chunk 更有方向性。Karpathy 描述自己的用法是一边开着 LLM agent、一边开着 Obsidian 实时看它改了什么，并打了个比方：“Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase.”

人类要不要直接改 wiki 页？按原文的分工，人负责挑选来源、提问和判断，记账式的维护都交给 LLM。发现某页有事实错误时，我更倾向于把更正作为新的 source 放进 raw/（raw 本身不改），再让 LLM ingest，这样更正本身也会在 log 里留下记录；直接手改 wiki 页虽然快，但下次 LLM 更新这一页时，它不一定知道为什么那里被改过。

Schema：LLM 的操作手册

Karpathy 原文：“a document (e.g. CLAUDE.md for Claude Code or AGENTS.md for Codex) that tells the LLM how the wiki is structured, what the conventions are, and what workflows to follow.”

第三层是 Schema——一份给 LLM 看的”项目说明书”。Claude Code 用 CLAUDE.md，OpenAI Codex 用 AGENTS.md，本质都是把”这个 wiki 的命名规则、目录结构、ingest/query/lint 各自怎么跑”写成 markdown 给 LLM 当系统提示。

Schema 的存在让 wiki 与具体厂商解绑：你换一家 LLM 服务，schema 文件原样可用；你给同一份 wiki 加另一个 agent（比如 Codex），只需要复制 schema 改个文件名。原文还特别强调 schema 不是一次写死的——“You and the LLM co-evolve this over time as you figure out what works for your domain.”

什么该写进 schema？经验法则：能用一句话描述的”硬规则”都进 schema，依赖判断的部分留给 LLM。比如”raw/ 文件名是 sha1 hash”是硬规则，应该写进 schema；”判断哪些 takeaways 值得进 wiki”是软判断，留给 LLM 在 ingest 时和人类协商。把硬规则前置到 schema 能极大降低后续每次操作的 token 开销。

# CLAUDE.md（一个 schema 的最小骨架）

## 目录约定
- raw/ 只读，文件名是源的 sha1 hash 前 8 位
- wiki/concepts/ 抽象概念，每页 < 800 字
- wiki/entities/ 具体实体，每页含字段表
- wiki/index.md 自动维护，按 concepts / entities 分组
- wiki/log.md append-only，禁止删改历史行

## 工作流
- ingest <source>: 读源 -> 与人确认 takeaways -> 写 summary -> 更新 entities -> 更新 concepts -> 写 log
- query <q>: 先读 index -> 取相关页 -> 综合回答（带引用） -> 写 log
- lint: 找矛盾、过期、孤儿页 -> 报告 -> 写 log（不直接修改 wiki 页）

三个核心操作：Ingest / Query / Lint

一个容易误解的词
有些中文介绍把第三个操作理解成”连结”或”链接”，Karpathy 原文 用的词是 Lint——软件工程里”代码体检”的隐喻。Linter 不写新代码，只挑出有问题的旧代码；Wiki 的 Lint 同理，做的是健康检查而不是建立连接。这个误译会让人以为这一步是”加链接”，方向就跑偏了。

Ingest：把一份 source 变成多个 wiki 页

“the LLM reads the source, discusses key takeaways with you, writes a summary page in the wiki, updates the index, updates relevant entity and concept pages across the wiki, and appends an entry to the log.”

Ingest 不是简单”把文件丢进数据库”。Karpathy 给出的标准动作里有一步关键的中间环节——discusses key takeaways with you——LLM 读完源以后先和人确认要点，再决定哪些进 wiki、用什么 frame。这样 wiki 是带人类判断进去的，而不是机器一刀切。原文估计一份 source 可能会牵动 10–15 个 wiki 页；Karpathy 自己偏好一次 ingest 一份、全程参与，但也承认可以批量 ingest、少盯一点。

边界情况：如果新源和现存 wiki 内容矛盾怎么办？gist 只说要标出矛盾，没规定格式。我的做法是让 LLM 在更新现有 concept 页时，同时引用旧来源和新来源，并在页面顶部注明”某日更新，取代 raw/xxx 中的旧说法”，完整的变更历史交给 log.md。

# 在 Claude Code 里跑 ingest（带初始提示词启动交互会话）
claude "ingest raw/a1b2c3d4.md"

# LLM 会按顺序做：
#   1. 读 source
#   2. 列出 takeaways 让你确认/调整
#   3. 写 wiki/concepts/<topic>.md
#   4. 更新 wiki/entities/<对应实体>.md
#   5. 在 index.md 加一行
#   6. 在 log.md 追加 ingest 记录（含来源 hash + 时间戳）

Query：带引用的回答，而不是自由发挥

“You ask questions against the wiki. The LLM searches for relevant pages, reads them, and synthesizes an answer with citations.”

Query 路径的特点是先读 index 再定位页，而不是上来就把整个 wiki 灌进 context。这件事在 token 经济上意义很大——一份几百页的 wiki，光 index.md 可能也就几 KB，LLM 看 index 就能精确选出 3-5 页深读，剩下的 token 留给回答本身。

如果 index 里没有相关条目怎么办？更好的反应不是”直接回答”，而是让 LLM 承认知识缺失、询问要不要去 raw/ 里临时搜索——这条可以直接写进 schema。这是 wiki 派和 RAG 派的另一个分野：RAG 总会返回”top-k 里最像的 chunks”，哪怕完全不相关；wiki 派可以诚实地说”我这里没有”。

原文在 Query 这一节还有一个很关键的点：“good answers can be filed back into the wiki as new pages.” 你让 LLM 做的一次对比、一份分析，不应该消失在聊天记录里，而是写回 wiki 成为新页面——这样提问本身也会让知识库变厚。

claude "query 苹果股票交易策略，10 万美金本金，要看风险管理"

# 路径：read(wiki/index.md)
#       -> 选中 [risk-management.md, position-sizing.md, apple-stock.md]
#       -> 读这 3 页 -> 综合并标注引用
#       -> 把本次 query 写入 log.md（query 内容 + 引用页 + 时间）

Lint：维护 wiki 长期健康的关键

“ask the LLM to health-check the wiki. Look for: contradictions between pages, stale claims that newer sources have superseded, orphan pages with no inbound links, important concepts mentioned but lacking their own page, missing cross-references, data gaps that could be filled with a web search.”

Lint 是这套架构里最被低估的一步。Karpathy 列出的检查项——页面间矛盾、被新来源取代的过期说法、没有入链的孤儿页、被提到却没有独立页面的重要概念、缺失的交叉引用、可以联网补上的数据空白——在纯 RAG 里基本没有对应的环节。在我的 schema 里，lint 只出报告、不直接改页面，对存量做”质量回归”，修不修由人决定。

实操中可以把 lint 设成 cron——每周一早上由 agent 自动跑一次，把报告 append 到 log.md，人类在周会上扫一眼就行。频率取决于 wiki 写入速度：每天有 ingest 的快速 wiki 适合每天 lint 一次；只是偶尔补充的研究 wiki 可以放宽到每月。

# 一个 lint 报告的样子（log.md 里的一段）

## 2026-04-27 lint pass
- contradiction: concepts/risk.md 说"6% 单笔上限"，entities/apple.md 说"10% 单笔上限"
- stale: entities/apple.md 价格数据 captured 2024-01，距今 > 90 天
- orphan: concepts/option-spreads.md 没有任何页 link 进来
- missing-xref: concepts/risk.md 提到 stop-loss 但没 link 到 entities/stop-loss.md
- cross-ref ok 38 条

Index 与 Log：让 wiki 可被 LLM 高效消费

Karpathy 原文：index 是 “content-oriented… a catalog of everything in the wiki”；log 是 “append-only record of what happened and when — ingests, queries, lint passes.”

Index 和 Log 是 wiki 的两条独立轨道，职责完全不重叠。

Index 负责 “现在 wiki 里有什么”——它是一份内容目录，每页一行：链接 + 一句摘要，可选附上日期、来源数等元数据，按 entities / concepts / sources 分组。LLM 在每次 query 时先读 index，靠这一句摘要决定要不要去读全文。一个良好维护的 index 是 wiki 性能上限的决定因素——摘要写得越精准，LLM 命中相关页的概率越高、误读其他页的浪费越少。

# wiki/index.md
## concepts
- [llm-wiki.md] Karpathy 提出的三层个人知识库架构
- [rag-vs-wiki.md] 五维对比，wiki 在累积性和跨文档精度上胜出
- [ingest.md] 把 source 转化为 wiki 页的标准流程
- [lint.md] 检查矛盾、过期、孤儿、缺失交叉引用

## entities
- [andrej-karpathy.md] OpenAI 创始成员，提出 LLM Wiki 概念
- [obsidian.md] 本地优先的 markdown 编辑器
- [notebook-lm.md] Google 提供的 source 整理工具

Log 负责 “过去发生了什么”——append-only，记录每一次 ingest / query / lint。它主要帮 LLM 了解最近做过什么，也方便人做审计。原文给了个小技巧：每条记录用统一前缀开头（如 ## [2026-04-02] ingest | Article Title），就能用 grep "^## \[" log.md | tail -5 直接取最近 5 条。当某条 wiki 内容存疑时，可以回 log 找到它最初是哪份 source、什么时候被 ingest 的。这件事在合规或审计场景下尤其重要——你需要能证明”某条结论是基于某份特定来源在某个时间点做出的”。

# wiki/log.md
- 2026-04-15 09:12  ingest  raw/a1b2c3d4.md -> concepts/llm-wiki.md, entities/karpathy.md
- 2026-04-15 14:33  query   "三层架构是什么" -> 引用 [llm-wiki.md, ingest.md]
- 2026-04-22 09:00  lint    pass: 1 contradiction, 1 stale, 1 orphan
- 2026-04-27 10:08  ingest  raw/c8f9e2a1.md -> 更新 concepts/llm-wiki.md

把这两个文件想成数据库里的”目录索引”和”binlog”——前者优化读路径，后者保留可回溯的事件流。

vs RAG：五维硬碰硬对比

维度传统 RAGKarpathy 的 LLM Wiki
累积性每次 query 重新检索，知识不沉淀wiki 页持续更新，是”持久化、可复利的资产”
跨文档精度top-k chunks 拼凑，受 embedding 噪声影响概念页已显式做过综合，cross-link 把跨文档关系固化
矛盾处理寄希望 top-k 同时命中新旧文档lint 主动捞出矛盾；新事实直接 supersede 旧页
平台锁定绑定 embedding 模型与向量库纯 markdown，换厂商成本接近零
Token 成本每次都要灌 N 个 chunk 进 context先读小 index，再精读 3-5 页，token 用量稳定

RAG 仍然占优的场景是规模。Karpathy 说 index 方案在”~100 sources, ~hundreds of pages”这个量级上效果出奇地好；再往上，他建议给 wiki 加一个真正的搜索引擎，点名推荐了 qmd——一个本地运行的 markdown 搜索工具，BM25 + 向量混合检索再加 LLM rerank，既有 CLI 也有 MCP server。也就是说，规模上去之后不是在 wiki 和检索之间二选一，而是 wiki 负责上层综合、检索负责定位。

# 大规模时的混合架构
query -> wiki/index.md（先看摘要层）
      -> 命中？读 wiki 页综合回答
      -> 不命中？落到 RAG 检索 raw/ 里的 chunks
# 小到中等规模时的纯 wiki 架构（绝大多数个人/团队场景）
query -> wiki/index.md -> 读 3-5 个 wiki 页 -> 回答

大多数个人知识库在起步阶段都没到第一种规模，先走纯 wiki 路径就够了，把精力花在 schema 和 lint 上。等到 vault 里的笔记多到 index 覆盖不过来，再接一层检索。我在《给 Obsidian 知识库接一层本地检索：一次踩坑实录》里记录了给一个 660 篇 markdown 的 vault 接 qmd 的完整过程和遇到的问题，可以作为这一步的参考。

落地路径：Claude Code + Obsidian

Karpathy 自己的组合很简单：一边是 LLM agent，一边是 Obsidian。分工大致是：

  • Claude Code（或 Codex、OpenCode 等 agent）按 schema 执行 ingest / query / lint，是整个体系的执行者
  • Obsidian 提供本地文件浏览、双向链接和 graph view，让人能直观看到 wiki 的形状——哪些页是枢纽、哪些是孤儿
  • raw/ 目录存放原始资料。HC 的视频里用 NotebookLM 管理 source；不过值得注意，Karpathy 在 gist 开头恰恰把 NotebookLM 列为”每次提问都重新检索”的 RAG 式工具，把它当 raw 层的容器可以，但别把它当 wiki 本身
# 1. 在项目根目录写好 CLAUDE.md（schema，见下一节的骨架）
# 2. 在 Claude Code 里让它按 schema 处理一份 source
claude "按 CLAUDE.md 的 ingest 流程处理 raw/a1b2c3d4.md"
# 3. 在 Obsidian 里用"打开文件夹作为仓库"打开这个项目目录，看生成的 wiki 页和 graph view

网上也有人把这套流程打包成现成的 Claude Code skill 或付费模板。它们适合快速体验，但 Karpathy 原文的态度很明确：这份文档 “is intentionally abstract”，目录结构、schema 约定、页面格式都应该由你和自己的 agent 一起定出来。一页 CLAUDE.md 就是一份 schema，写一次就归你了。

工具替代上也很灵活：Claude Code 不是必选，OpenAI Codex 加 AGENTS.md 同样能跑；Obsidian 可以换 VS Code 加任意 markdown viewer。原文还提醒，wiki 本身就是一个 markdown 文件组成的 git 仓库，版本历史、分支和协作都是现成的。这套架构对工具的依赖远低于对约定的依赖。

我的偏好是一开始就自己写 CLAUDE.md：一来 schema 写不到 100 行，自建成本极低；二来出问题时知道每条规则是为什么加的，调试快得多。

七步落地清单

要想把上面的架构跑起来，第一周大致按这个顺序：

  1. 挑一个具体场景——投资策略 / 旅游计划 / 读书笔记任一，目标越具体越好；通用知识库一开始很难维护
  2. 收集 5-10 份 raw 源——存到 raw/ 目录，文件名用源的 hash 前 8 位
  3. 写一份 CLAUDE.md——目录约定 + ingest/query/lint 三个工作流，控制在 100 行以内
  4. 跑第一次 ingest——让 Claude Code 处理一份 source，看 wiki 页结构是否符合预期，不符合就调 schema
  5. 跑两到三次 query——问真实问题，看回答的引用准确性，引用错位说明 index 摘要写得不够好
  6. 设置 cron lint——每周一早上 9 点跑一次，结果 append 到 log.md
  7. 第一个月只用 Obsidian 看 wiki——不要急着接 Telegram / 自动总结之类的下游消费，先把 wiki 本身养稳
# 最小可跑的脚手架，10 秒搭出来
mkdir -p raw wiki/{concepts,entities}
touch CLAUDE.md wiki/index.md wiki/log.md
cat > CLAUDE.md <<'EOF'
## 目录约定
- raw/ 只读，文件名是源的 sha1 hash 前 8 位
- wiki/concepts/ 抽象概念
- wiki/entities/ 具体实体
- wiki/index.md 自动维护
- wiki/log.md append-only

## 工作流
- ingest <source>: 读 -> 确认 takeaways -> 写 wiki -> 更新 index -> 写 log
- query <q>: 读 index -> 选 3-5 页 -> 回答带引用 -> 写 log
- lint: 找矛盾 / 过期 / 孤儿 / 缺失 xref -> 写 log
EOF

什么时候 Wiki 不够用

规模的边界
不是所有场景都该上纯 wiki。原文给的舒适区是约 100 份 source、几百个页面；文档量再大几个数量级（比如整个公司的知识库），只靠 LLM 读 index 和逐页维护，成本会迅速失控。

两个常见的边界场景：

# 场景 1：raw 文件 > 数千份
# 解：wiki 当作摘要层，下面落 RAG 处理 chunks
# 检索路径：query -> wiki -> 命中则返回；不命中则回退 RAG
# 场景 2：单页内容超过 LLM context window
# 解：拆 sub-wiki，每个 sub-wiki 独立维护一份 schema
# wiki/
#   trading-strategy/{index, log, concepts/, ...}
#   travel-melbourne/{index, log, concepts/, ...}

第一种场景里 wiki 退化为传统知识管理系统的”摘要 + 全文”两层；第二种是把 wiki 自己再做一次模块化。至于团队场景，gist 里只把”由 Slack、会议记录、项目文档喂养、人工审核更新的内部 wiki”列为一种可能的用途，没有展开多人协作怎么解决冲突——这部分还得自己摸索。

小结

LLM Wiki 的想法并不新——Karpathy 自己在文末把它和 Vannevar Bush 1945 年设想的 Memex 联系起来：一个私人的、精心整理的、文档之间有关联路径的知识库。Bush 没解决的是”谁来维护”，而 LLM 让维护的边际成本接近零。RAG 只是 LLM × 知识库的第一种工程化形态；Wiki 是 Karpathy 给出的第二种，更轻量、更可累积、对厂商依赖更低。

这周可以试一次：

  • 把最近一周读的 5 篇文章做成 raw/，让 Claude Code 跑一次 ingest，看生成的 wiki 页能不能复述你想留下的判断
  • 给某个具体场景（健身、读书、投资任一）写一份 100 行的 CLAUDE.md schema，跑一周看维护成本
  • 把已有的 RAG 项目做一次 audit：哪些跨文档查询其实可以靠一份”已经写好的概念页”省掉
# 一周后自评：wiki 是否健康？
# - 能不能用一句话说清每页是干什么的？(index 摘要质量)
# - lint 报告里 contradiction / stale / orphan 各几条？
# - 同一个问题问两次，回答的引用页是否一致？

至于”持久化、可复利的知识资产”这件事——它的复利效应只在你坚持养 wiki 几个月之后才看得到。前面几周没什么明显感觉，越往后越值钱，这是这套架构最反直觉、也最值得投入的部分。
