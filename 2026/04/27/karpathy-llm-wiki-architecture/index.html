Karpathy 的 LLM Wiki：三层架构、三个操作，以及它和 RAG 的分界

LLM Wiki 系列

  1. 架构：Karpathy 原文的三层和三个操作（本篇）
  2. 给 Obsidian 知识库接一层本地检索：一次踩坑实录：vault 变大后怎么补检索层
  3. LLM Wiki 知识库实战：从资料入库到可追溯问答：两个案例、示例仓库和本地小模型的实测

Andrej Karpathy 发过一份叫 LLM Wiki 的 gist，不到两千词。他自己称之为 “idea file”，用法是把整份贴给自己的 agent，由 agent 和你一起把它落成具体实现。

这篇是我读 gist 和 HC AI說人話 的视频《3 層架構打造個人 AI 大腦》之后的整理。视频用 Claude Code + NotebookLM + Obsidian 搭了”墨尔本旅游指南”和”交易策略库”两套 wiki。

写法约定：引号里的英文都是 gist 原话，2026-10-30 我又对照原文核了一遍；标”我的判断”或”我的做法”的段落是我自己的看法和用法，gist 里没有。

Karpathy 对 RAG 只批评了一点：没有累积

原话是：”the LLM is rediscovering knowledge from scratch on every question. There’s no accumulation.” 他举的例子是一个需要综合五份文档的问题：每问一次，LLM 都要重新找碎片、重新拼。他点名 NotebookLM、ChatGPT 文件上传和多数 RAG 系统都这样工作。

他的替代方案是让 LLM “incrementally builds and maintains a persistent wiki”。新资料进来时，LLM 读完把信息并入已有页面：更新实体页，修订主题摘要，并且 “noting where new data contradicts old claims”。他的概括是 “the wiki is a persistent, compounding artifact”。

下面三点是我的判断，gist 没有展开：

  • 矛盾在写入时处理。知识库里有一份”A 餐厅好吃”的旧文档，又加进一份”A 餐厅食安事件”，RAG 要发现冲突，得指望 top-k 同时召回这两份；wiki 在 ingest 新文档时就会改写”A 餐厅”那一页，并标出前后矛盾。
  • 不绑 embedding。知识落成 markdown，换哪家模型都能直接读；RAG 换 embedding 模型通常要重建索引。
  • 综合成本前移。跨文档综合在 ingest 时做一次，之后每次查询读的是已经综合好的页面。我觉得这是最被低估的一点，不过我没做过 token 用量对比，这只是推断。

目录骨架和两种查询路径对比如下：

project/
  raw/                          # 原始资料，只读
    karpathy-llm-wiki.txt
    youtube-hc-ai.md
  wiki/                         # LLM 维护
    concepts/
      llm-wiki.md
      rag-vs-wiki.md
    entities/
      andrej-karpathy.md
    index.md
    log.md
  CLAUDE.md                     # schema

# RAG：每次都重来
embed(question) -> ANN search -> top_k chunks -> rerank -> context -> LLM
# Wiki：先看 index 再读页
read(index.md) -> resolve_relevant_pages() -> read(N pages) -> LLM

第二条路径里没有 embedding，LLM 读 index 就能定位文件。原文说这种做法在 “~100 sources, ~hundreds of pages” 的规模上 “works surprisingly well”，用不着 embedding 检索那套基础设施。

三层：raw 只读，wiki 归 LLM，schema 是操作手册

Raw sources：原始资料不可改

原话：”your curated collection of source documents. Articles, papers, images, data files. These are immutable — the LLM reads from them but never modifies them. This is your source of truth.”

我的做法：raw 文件要能定位（有 URL 或固定路径）、有抓取日期、不重复存。给每份资料一个稳定 id，比如内容哈希前 8 位，wiki 用 id 引用，标题改了链接也不断。网页可以用 gist 推荐的 Obsidian Web Clipper 存成 markdown；PDF 我用 pdftotext 抽文本：

# pdftotext 来自 poppler-utils；pandoc 读不了 PDF
mkdir -p raw/
HASH=$(sha1sum paper.pdf | cut -c1-8)
pdftotext -layout paper.pdf "raw/${HASH}.md"
# raw/<hash>.md 的 frontmatter，供 wiki 层引用
---
source_id: a1b2c3d4
title: 原文标题
captured_at: 2026-04-27
url: https://example.com/paper
hash_algo: sha1
---

Wiki：LLM 写，人读

原话：”a directory of LLM-generated markdown files. Summaries, entity pages, concept pages, comparisons, an overview, a synthesis. The LLM owns this layer entirely.” 他还说 “You never (or rarely) write the wiki yourself”，人负责 “sourcing, exploration, and asking the right questions”。他自己的用法是一边开 agent、一边开 Obsidian 实时看改动：”Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase.”

我的做法：每页至少有两类链接，一类指向 raw 里的来源，一类指向其他 wiki 页。后一类正是 RAG 切 chunk 时丢掉的跨文档关系。发现某页有事实错误时，我把更正作为新资料放进 raw/ 再 ingest，不直接手改 wiki 页。这样更正会在 log 里留下记录，下次 LLM 更新这一页时也知道那里为什么变了。

# wiki/concepts/llm-wiki.md（一个 wiki 页的样子）

> Karpathy 提出的"个人知识库"架构。

## 核心要点
- 三层：[原始来源](../entities/raw-sources.md)、本页、[Schema](./schema.md)
- 三操作：[Ingest](./ingest.md)、[Query](./query.md)、[Lint](./lint.md)
- 与 RAG 的对比见 [rag-vs-wiki.md](./rag-vs-wiki.md)

## 来源
- raw/a1b2c3d4.md  -- Karpathy gist 原文
- raw/c8f9e2a1.md  -- HC AI 视频转录

## 最近更新
- 2026-04-27 ingest c8f9e2a1（HC 视频）后补充了"实战工具栈"小节

Schema：告诉 LLM 怎么维护

原话：”a document (e.g. CLAUDE.md for Claude Code or AGENTS.md for Codex) that tells the LLM how the wiki is structured, what the conventions are, and what workflows to follow”。他特别说明 schema 会变：”You and the LLM co-evolve this over time as you figure out what works for your domain.”

我的经验法则：能一句话写清的硬规则进 schema，比如”raw/ 文件名是 sha1 前 8 位”；”哪些要点值得进 wiki”这类软判断，留到 ingest 时和 LLM 商量。下面是我用的最小骨架，不到 20 行：

# CLAUDE.md（一个 schema 的最小骨架）

## 目录约定
- raw/ 只读，文件名是源的 sha1 hash 前 8 位
- wiki/concepts/ 抽象概念，每页 < 800 字
- wiki/entities/ 具体实体，每页含字段表
- wiki/index.md 自动维护，按 concepts / entities 分组
- wiki/log.md append-only，禁止删改历史行

## 工作流
- ingest <source>: 读源 -> 与人确认 takeaways -> 写 summary -> 更新 entities -> 更新 concepts -> 写 log
- query <q>: 先读 index -> 取相关页 -> 综合回答（带引用） -> 写 log
- lint: 找矛盾、过期、孤儿页 -> 报告 -> 写 log（不直接修改 wiki 页）

三个操作：Ingest、Query、Lint

有些中文介绍把第三个操作译成”连结”，原文用的是 Lint，借的是代码检查工具的意思：不写新内容，只挑旧内容的毛病。理解成”加链接”，方向就偏了。

Ingest：一份资料可能改动十几页

原话：”the LLM reads the source, discusses key takeaways with you, writes a summary page in the wiki, updates the index, updates relevant entity and concept pages across the wiki, and appends an entry to the log.”

中间的 “discusses key takeaways with you” 容易被跳过：LLM 读完先和人确认要点，再决定写什么。原文估计一份资料 “might touch 10-15 wiki pages”。Karpathy 自己 “prefer to ingest sources one at a time and stay involved”，也承认可以批量 ingest、少盯一些。

gist 只说要标出矛盾，没规定格式。我的做法是更新概念页时同时引用新旧来源，在页面顶部注明”某日更新，取代 raw/xxx 中的旧说法”，完整的变更历史留给 log.md。

这条做法在第 3 篇实战里有反面例子。我用本地 qwen2.5-coder:3b 按同样的流程入库，加入”10 月 12 日新决定”那一步，模型回复说已更新来源摘要、索引和日志，实际只写回了一个文件，新决定根本没进决策页；换 qwen2.5:3b 重跑也一样。之后五个验收问题结论全对，但涉及新决定的两题都是拿旧材料推出来的，依据错了。新旧来源不同时写在页面上，入库漏没漏一眼就能看出来。

# 在 Claude Code 里跑 ingest（带初始提示词启动交互会话）
claude "ingest raw/a1b2c3d4.md"
# 按 schema，它应该：读 source -> 列 takeaways 让你确认 -> 写或更新 concepts/entities
#                    -> 在 index.md 加一行 -> 在 log.md 追加记录

Query：好答案写回 wiki

原话：”You ask questions against the wiki. The LLM searches for relevant pages, reads them, and synthesizes an answer with citations.” 这一节最重要的一句是 “good answers can be filed back into the wiki as new pages.”：一次对比、一份分析，不该消失在聊天记录里。

我的做法：查询先读 index，挑出三五页再细读，不把整个 wiki 塞进上下文。index 里没有相关条目时，让 LLM 先承认缺失，再问要不要去 raw/ 里搜，这条直接写进 schema。RAG 总会返回最像的几个 chunk，哪怕都不相关；wiki 可以老实说”这里没有”。同一次实测里，3B 模型的五个回答没有一题按要求附上正确来源，所以验收时我看引用，不只看结论。

claude "query 苹果股票交易策略，10 万美金本金，要看风险管理"
# read(wiki/index.md) -> 选中 risk-management.md、position-sizing.md、apple-stock.md
# -> 读这 3 页 -> 带引用回答 -> 在 log.md 记下问题和引用页

Lint：定期体检

原话：”ask the LLM to health-check the wiki. Look for: contradictions between pages, stale claims that newer sources have superseded, orphan pages with no inbound links, important concepts mentioned but lacking their own page, missing cross-references, data gaps that could be filled with a web search.” 他还说 LLM “is good at suggesting new questions to investigate and new sources to look for”。

这些检查项在纯 RAG 里基本没有对应环节。我的做法是 lint 只出报告、不改页面，修不修由人决定。频率看写入速度：每天都有 ingest 的 wiki 每天跑一次，偶尔补充的研究 wiki 一个月一次就够。

## [2026-04-27] lint | weekly
- contradiction: concepts/risk.md 说"6% 单笔上限"，entities/apple.md 说"10% 单笔上限"
- stale: entities/apple.md 价格数据 captured 2024-01，距今 > 90 天
- orphan: concepts/option-spreads.md 没有任何页 link 进来
- missing-xref: concepts/risk.md 提到 stop-loss 但没 link 到 entities/stop-loss.md

index 管”现在有什么”，log 管”发生过什么”

原文对两者的定义：index 是 “content-oriented”，”a catalog of everything in the wiki”，每页一行链接加一句摘要，可选日期、来源数等元数据，按类别分组，”The LLM updates it on every ingest”；log 是 “an append-only record of what happened and when — ingests, queries, lint passes”。

log 有个小技巧：每条记录用统一前缀开头，比如 ## [2026-04-02] ingest | Article Title，然后 grep "^## \[" log.md | tail -5 就能取出最近 5 条。

# wiki/index.md
## concepts
- [llm-wiki.md] Karpathy 提出的三层个人知识库架构
- [rag-vs-wiki.md] wiki 与 RAG 在累积、矛盾处理和规模上的取舍
- [lint.md] 检查矛盾、过期、孤儿、缺失交叉引用

## entities
- [andrej-karpathy.md] 提出 LLM Wiki 的 gist 作者
- [obsidian.md] 本地优先的 markdown 编辑器

# wiki/log.md
## [2026-04-15] ingest | raw/a1b2c3d4.md -> concepts/llm-wiki.md, entities/andrej-karpathy.md
## [2026-04-15] query | "三层架构是什么" -> llm-wiki.md, ingest.md
## [2026-04-22] lint | 1 contradiction, 1 stale, 1 orphan

我的判断：index 的一句话摘要写得准不准，基本决定了 LLM 能不能找对页面。log 的价值在追溯：某条结论存疑时，能查到它来自哪份资料、什么时候进来。

和 RAG 的分界在规模

下表是我的归纳，不是原文内容：

维度传统 RAGLLM Wiki
累积性每次查询重新检索，知识不沉淀页面随新资料持续更新
跨文档综合查询时用 top-k chunks 现场拼ingest 时已写进概念页，交叉链接固定下来
矛盾处理依赖新旧文档同时被召回ingest 时标出，lint 定期再查
迁移成本绑定 embedding 模型和向量库纯 markdown，换模型直接读
规模资料越多越有优势原文说约 100 份资料、几百页时 index 够用

规模再往上，Karpathy 建议给 wiki 加搜索引擎，点名 qmd：”a local search engine for markdown files with hybrid BM25/vector search and LLM re-ranking, all on-device”，CLI 和 MCP server 都有。他也说可以让 LLM 帮你 “vibe-code a naive search script”。

我的判断：规模上去后两者是叠加关系，wiki 负责综合，检索负责定位：

query -> wiki/index.md -> 命中：读 3-5 个 wiki 页回答
                       -> 不命中：检索 raw/ 或全部页面，再决定要不要 ingest

多数个人知识库起步时到不了这个规模，先走纯 index，把精力花在 schema 和 lint 上。我在给 Obsidian 知识库接一层本地检索里记录了给 660 篇 markdown 的 vault 接 qmd 的过程和问题。

落地：agent 维护，Obsidian 浏览

gist 开头第一段列的 agent 是 OpenAI Codex、Claude Code、OpenCode / Pi。分工大致是：

  • Claude Code（或 Codex 等）按 schema 执行 ingest、query、lint。
  • Obsidian 浏览本地文件。原文说 graph view 是看 wiki 形状最好的方式：”which pages are hubs, which are orphans”；Marp 插件可以出幻灯片，Dataview 可以按 frontmatter 生成表格。
  • raw/ 存原始资料。视频里用 NotebookLM 管 source，可 gist 讲核心思路的那一段恰好把 NotebookLM 列为每次重新检索的 RAG 式工具，拿它当 raw 层的容器可以，别把它当 wiki 本身。
mkdir -p raw wiki/{concepts,entities} && touch CLAUDE.md wiki/index.md wiki/log.md
# 写好 CLAUDE.md 后，让 Claude Code 按 schema 处理一份 source
claude "按 CLAUDE.md 的 ingest 流程处理 raw/a1b2c3d4.md"
# 在 Obsidian 里"打开文件夹作为仓库"，看生成的页面和 graph view

网上有人把这套流程打包成现成的 skill 或付费模板，适合快速体验。原文的态度是 “This document is intentionally abstract”，目录、schema 和页面格式都应该由你和自己的 agent 一起定。工具也可以换：Codex 加 AGENTS.md 一样能跑，Obsidian 可以换成任意 markdown 编辑器。原文还提醒 “The wiki is just a git repo of markdown files”，版本历史和协作是现成的。

我倾向于一开始就自己写 CLAUDE.md：不到 100 行，出问题时知道每条规则为什么加。

第一周怎么起步

这是我建议的顺序，不是原文内容：

  1. 挑一个具体场景，比如投资策略、旅游计划或读书笔记。通用知识库一开始很难维护。
  2. 收集 5 到 10 份资料放进 raw/。
  3. 写 CLAUDE.md：目录约定加三个工作流，控制在 100 行以内。
  4. 跑第一次 ingest，看页面结构是否符合预期，不符合就改 schema。
  5. 问两三个真实问题，看引用对不对。引用错位，多半是 index 摘要写得不够好。
  6. 定一个固定的 lint 时间，比如每周一，报告追加到 log.md。
  7. 第一个月只用 Obsidian 看 wiki，先别接 Telegram、自动摘要之类的下游。

纯 wiki 撑不住的两种情况

下面两种情况和应对是我的判断，gist 里没有，我也还没有把 wiki 做到这个规模。

一是 raw 文件到了数千份，只靠 LLM 读 index 和逐页维护，成本会很快失控。这时 wiki 退成摘要层，底下接检索，查询先看 wiki，没命中再搜原文。

二是单个主题的内容多到一次读不完。这时按主题拆成多个子 wiki，比如 wiki/trading-strategy/ 和 wiki/travel-melbourne/，各自维护 index 和 log。

团队场景 gist 只提了一句：一个 “internal wiki maintained by LLMs, fed by Slack threads, meeting transcripts, project documents, customer calls”，”Possibly with humans in the loop reviewing updates”。多人同时改怎么解决冲突，原文没说，得自己摸索。

Memex 的维护问题

Karpathy 在文末把这个想法和 Vannevar Bush 1945 年设想的 Memex 联系起来：私人的、精心整理的、文档之间有关联路径的知识库。他的原话是 “The part he couldn’t solve was who does the maintenance. The LLM handles that.”

维护成本降下来以后，剩下要判断的是 wiki 有没有养好。我会在一周后问自己三个问题：

- 每一页能不能用一句话说清它是干什么的？（index 摘要质量）
- lint 报告里 contradiction / stale / orphan 各有几条？
- 同一个问题问两次，引用的页面是否一致？
