传统 RAG vs 树形 RAG：RAPTOR、MCTS-RAG 与父子块检索

核心要点
在处理海量长文本时，传统 RAG 依赖向量相似度检索，往往只能命中”表层相似”，却难以捕捉跨段落、跨层级的逻辑结构。树形 RAG 正是为解决这一问题而生。

两种范式的本质区别

传统扁平 RAG

核心机制
基于向量相似度的平面检索，将文档切分为等长 chunks 后进行独立编码和检索。

核心特点

  • 机制：语义相似度匹配 (KNN/ANN 检索)
  • 视野：局部视角，仅看碎片块
  • 数据结构：线性列表，无层级关系
  • 检索方式：Top-K 向量相似度排序

优势

  • 部署快，检索延迟低（一次向量检索）
  • 成本低，只需切块和向量化，不需要 LLM 预处理
  • 技术成熟，生态工具丰富
  • 适合简单的事实查询

短板

  • 容易出现”盲人摸象”：每个块单独看都相关，拼不出全貌
  • 难以回答全局总结类问题
  • 跨段落、跨章节的逻辑推理能力弱
  • 块与块之间的上下文关联在切分时就丢了

典型失效场景：

问题："这本书的主要论点是什么？"
传统 RAG：返回若干相似段落，但无法提供整体论述
树形 RAG：从顶层摘要节点直接回答，涵盖全局结构

树形层级 RAG

核心创新
通过递归摘要 + 层级索引，构建具有抽象能力的知识树，支持从宏观到微观的多粒度检索。

核心特点

  • 机制：递归摘要 + 路径规划
  • 视野：全局视角，具备多层级抽象
  • 数据结构：树形结构，叶节点到根节点逐层抽象
  • 检索方式：树搜索 + 路径优化

优势

  • 缓解长文档的信息碎片化问题
  • 更适合需要综合多处信息的多跳问题
  • 全局总结能力强
  • 能利用文档的层次结构

短板

  • 预处理开销大（要调用 LLM 做递归摘要）
  • 检索链路更长，延迟更高
  • 多层级索引带来额外存储
  • 文档更新时需要重建受影响的子树，工程复杂度高

核心优势场景：

问题："作者在第3章和第7章的观点有什么矛盾？"
传统 RAG：难以建立跨章节的逻辑关联
树形 RAG：通过章节级摘要节点，快速定位并对比论点

核心研究文献

RAPTOR (递归摘要树)

Recursive Abstractive Processing for Tree-Organized Retrieval
通过递归聚类并生成高层级摘要节点，构建一棵”知识树”，让模型能够从宏观视角回答问题。

论文信息：

  • 标题：RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval
  • 作者：Parth Sarthi 等（Stanford），ICLR 2024
  • 发布日期：2024-01-31
  • 论文地址：https://arxiv.org/abs/2401.18059
  • 核心贡献：自底向上递归地”嵌入—聚类—摘要”，构建多层摘要树，检索时可以同时命中细节块和高层摘要

RAPTOR 工作流程

  1. 文档切分：将长文档切分为约 100 token 的短块（叶节点），论文用 SBERT（multi-qa-mpnet-base-cos-v1）做向量化
  2. 递归聚类：先用 UMAP 降维，再用 GMM（高斯混合模型）软聚类，簇的数量用 BIC 选择；一个节点可以属于多个簇
  3. 摘要生成：用 LLM（论文中是 gpt-3.5-turbo）为每个簇生成摘要，作为上一层节点
  4. 层级构建：重复步骤 2-3，直到无法再聚类
  5. 检索：论文比较了两种方式——逐层向下的树遍历（tree traversal），以及把所有层的节点摊平后一起做相似度检索（collapsed tree）；后者效果更好

关键技术点

下面是示意代码，省略了 create_leaf_nodes、assign_to_clusters 等辅助方法：

# RAPTOR 核心：软聚类 + 递归摘要（示意）
class RAPTORTree:
    def __init__(self, documents: List[str], llm, embedding_model):
        self.llm = llm
        self.embedding_model = embedding_model
        self.layers = []  # 存储每一层的节点

    def build_tree(self, documents):
        # 第一层：原始文档块
        leaf_nodes = self.create_leaf_nodes(documents)
        self.layers.append(leaf_nodes)

        current_layer = leaf_nodes
        while len(current_layer) > 1:
            # 软聚类：允许节点属于多个簇
            clusters = self.soft_cluster(current_layer)

            # 为每个簇生成摘要
            summaries = []
            for cluster in clusters:
                summary = self.llm.summarize(cluster)
                summaries.append(summary)

            self.layers.append(summaries)
            current_layer = summaries

    def soft_cluster(self, nodes, n_clusters=None):
        """使用 GMM 进行软聚类，允许重叠"""
        from sklearn.mixture import GaussianMixture

        embeddings = [self.embedding_model(n.text) for n in nodes]
        gmm = GaussianMixture(n_components=n_clusters or max(1, len(nodes) // 10))
        gmm.fit(embeddings)

        # 根据概率分配节点到多个簇
        probs = gmm.predict_proba(embeddings)
        return self.assign_to_clusters(nodes, probs)

MCTS-RAG (蒙特卡洛树搜索)

Enhancing Retrieval-Augmented Generation with Monte Carlo Tree Search
把”什么时候检索、检索什么、怎么推理”看成一个搜索决策过程，用 MCTS 在推理步骤构成的树上寻找最可靠的答案路径。

论文信息：

  • 标题：MCTS-RAG: Enhancing Retrieval-Augmented Generation with Monte Carlo Tree Search
  • 作者：Yunhai Hu、Yilun Zhao、Chen Zhao、Arman Cohan
  • 发布日期：2025-03-26
  • 论文地址：https://arxiv.org/abs/2503.20757
  • 核心贡献：把检索动作嵌进 MCTS 推理搜索，让 7B/8B 级小模型通过增加推理时计算，在知识密集型任务上接近 GPT-4o

注意它和 RAPTOR 的”树”不是一回事：RAPTOR 的树是文档索引，MCTS-RAG 的树是推理过程，每个节点是一步推理或检索动作。论文定义了六种动作：直接回答、快速推理、拆解问题、检索后推理、检索后拆解、汇总回答。

MCTS-RAG 工作流程

  1. 选择 (Selection)：从根节点开始，按 UCT 分数选择最有潜力的子节点
  2. 扩展 (Expansion)：在叶节点上尝试上述动作，其中检索类动作会生成查询、取回外部知识
  3. 模拟 (Simulation)：沿当前路径推演到给出答案，评估其可靠性
  4. 回传 (Backpropagation)：更新路径上所有节点的价值

最终答案由多条推理路径投票决定：路径上节点奖励的乘积作为权重。论文设置为 4 次 rollout、最大深度 5，同一节点的不同动作并行展开以降低延迟。

关键技术点

下面是 MCTS 骨架的示意代码（expand、simulate 等方法省略），实际实现中节点内容是推理步骤而非文档：

import math

# MCTS 骨架：搜索树 + UCB 策略（示意）
class MCTSNode:
    def __init__(self, content, parent=None):
        self.content = content
        self.parent = parent
        self.children = []
        self.visits = 0
        self.value = 0.0

    def ucb_score(self, exploration_weight=1.414):
        """UCB1 公式：平衡探索与利用"""
        if self.visits == 0:
            return float('inf')

        exploitation = self.value / self.visits
        exploration = exploration_weight * math.sqrt(
            math.log(self.parent.visits) / self.visits
        )
        return exploitation + exploration

class MCTSRetriever:
    def __init__(self, llm, max_iterations=100):
        self.llm = llm
        self.max_iterations = max_iterations

    def search(self, query, retriever):
        root = MCTSNode(content=None)

        for _ in range(self.max_iterations):
            # 1. Selection: 选择最佳路径
            node = self.select(root)

            # 2. Expansion: 扩展候选节点
            if not node.is_terminal():
                node = self.expand(node, query, retriever)

            # 3. Simulation: 评估路径质量
            reward = self.simulate(node, query)

            # 4. Backpropagation: 更新路径价值
            self.backpropagate(node, reward)

        # 返回最佳路径
        return self.best_path(root)

    def select(self, node):
        """选择 UCB 分数最高的子节点"""
        while node.children:
            node = max(node.children, key=lambda n: n.ucb_score())
        return node

父子块策略 (Parent-Child Retriever)

Parent-Child Document Chunking Strategy
一种轻量级的层级检索方案，通过”小块检索、大块召回”的策略，在保持检索精度的同时提供更丰富的上下文。

核心理念：

  • Child Chunks（子块）：用于向量检索的小粒度块（精确匹配）
  • Parent Chunks（父块）：用于 LLM 生成的大粒度块（完整上下文）

工作原理

两层存储结构：

  1. 检索层（Child）：存储小块（例如 128-256 tokens）及其向量
  2. 召回层（Parent）：存储大块（例如 1024-2048 tokens）的原始文本

检索流程：

用户查询 → 在 Child 层检索 → 定位到匹配的小块 → 返回其对应的 Parent 块

核心优势

相比传统 RAG 的改进

传统 RAG 的困境：

  • 小块：检索准确，但上下文不足（容易断章取义）
  • 大块：上下文丰富，但检索噪声大（相似度下降）

Parent-Child 的解决方案：

  • 检索用小块 → 保证精确度
  • 生成用大块 → 保证上下文完整性

代码实现

from typing import List

# 父子块策略核心实现（按空格分词近似 token，仅作演示）
class ParentChildRetriever:
    def __init__(self, documents: List[str], embedding_model):
        self.embedding_model = embedding_model

        # 存储结构
        self.child_chunks = []      # 小块（用于检索）
        self.parent_chunks = []     # 大块（用于召回）
        self.child_embeddings = []  # 小块的向量
        self.child_to_parent = {}   # 映射关系：child_id -> parent_id

        self.build_index(documents)

    def build_index(self, documents: List[str]):
        """构建父子索引"""
        parent_id = 0
        child_id = 0

        for doc in documents:
            # 1. 切分为父块（大块）
            parent_chunks = self.split_document(
                doc,
                chunk_size=1024,   # 父块：1024 tokens
                overlap=100
            )

            for parent_chunk in parent_chunks:
                # 存储父块
                self.parent_chunks.append(parent_chunk)

                # 2. 将父块进一步切分为子块（小块）
                child_chunks = self.split_document(
                    parent_chunk,
                    chunk_size=256,   # 子块：256 tokens
                    overlap=50
                )

                for child_chunk in child_chunks:
                    # 存储子块
                    self.child_chunks.append(child_chunk)

                    # 建立映射关系
                    self.child_to_parent[child_id] = parent_id

                    # 计算子块向量（仅对小块编码）
                    embedding = self.embedding_model.encode([child_chunk])[0]
                    self.child_embeddings.append(embedding)

                    child_id += 1

                parent_id += 1

    def retrieve(self, query: str, top_k: int = 5):
        """检索：在子块中搜索，返回父块"""
        # 1. 对查询编码
        query_embedding = self.embedding_model.encode([query])[0]

        # 2. 在子块中检索（精确匹配）
        from sklearn.metrics.pairwise import cosine_similarity
        similarities = cosine_similarity(
            [query_embedding],
            self.child_embeddings
        )[0]

        # 3. 获取 Top-K 子块
        top_child_indices = similarities.argsort()[-top_k:][::-1]

        # 4. 映射到父块（去重，保持相似度顺序）
        parent_ids = []
        for child_id in top_child_indices:
            parent_id = self.child_to_parent[child_id]
            if parent_id not in parent_ids:
                parent_ids.append(parent_id)

        # 5. 返回父块（完整上下文）
        return [
            {
                'text': self.parent_chunks[pid],
                'parent_id': pid,
                'source': 'parent_chunk'
            }
            for pid in parent_ids
        ]

    def split_document(self, doc: str, chunk_size: int, overlap: int):
        """文档切分（带重叠）"""
        words = doc.split()
        chunks = []

        for i in range(0, len(words), chunk_size - overlap):
            chunk = ' '.join(words[i:i + chunk_size])
            if chunk:
                chunks.append(chunk)

        return chunks

实际应用场景

法律文档检索

场景：检索合同条款

问题：”违约金的计算方式是什么？”

传统 RAG（单一块大小）：

  • 小块（256 tokens）：检索到”违约金按日计算”，但缺少具体公式
  • 大块（1024 tokens）：包含完整公式，但可能没检索到（被其他相似内容干扰）

Parent-Child 策略：

  • 子块检索：”违约金按日计算”（精确命中）
  • 父块召回：整个条款段落，包含完整计算公式、生效条件、上限说明
  • 结果：既准确又完整

配置建议

参数调优

块大小没有通用最优值，下面是常见的起点，需要在自己的评测集上调：

文档类型子块大小父块大小
技术文档128-256 tokens1024-1536 tokens
法律合同256-384 tokens1536-2048 tokens
新闻文章128-192 tokens512-1024 tokens

经验法则：

  • 子块：包含 1-2 个完整句子
  • 父块：包含 1-2 个完整段落
  • 重叠：确保关键信息不被切断

与其他方法的对比

父子块 vs 传统 RAG：

# 传统 RAG：一种块大小
chunks = split(doc, size=512)  # 中等大小，检索精度和上下文都要妥协

# 父子块：两种块大小
child_chunks = split(doc, size=256)   # 检索用：小而准
parent_chunks = split(doc, size=1024) # 生成用：大而全

父子块 vs 树形 RAG：

  • 复杂度：父子块更简单，无需递归摘要
  • 成本：父子块更低，不需要 LLM 生成摘要
  • 延迟：父子块更快，无树遍历开销
  • 适用性：父子块是树形 RAG 的轻量替代，但没有跨段落的摘要节点，回答不了全局总结类问题

高级变体

多层级父子结构：

class MultiLevelParentChild:
    """三层结构：孙 → 子 → 父"""
    def __init__(self):
        self.grandchild_chunks = []  # 64 tokens (检索层)
        self.child_chunks = []       # 256 tokens (中间层)
        self.parent_chunks = []      # 1024 tokens (召回层)

        # 映射关系
        self.gc_to_child = {}   # grandchild → child
        self.child_to_parent = {} # child → parent

    def retrieve(self, query: str, return_level='parent'):
        """可选择返回不同层级的块"""
        # 1. 在孙块中检索
        top_gc_ids = self.search_grandchild(query)

        # 2. 根据需求返回不同层级
        if return_level == 'grandchild':
            return [self.grandchild_chunks[i] for i in top_gc_ids]
        elif return_level == 'child':
            child_ids = [self.gc_to_child[i] for i in top_gc_ids]
            return [self.child_chunks[i] for i in child_ids]
        else:  # parent
            parent_ids = [
                self.child_to_parent[self.gc_to_child[i]]
                for i in top_gc_ids
            ]
            return [self.parent_chunks[i] for i in parent_ids]

常见陷阱

1. 映射关系丢失

# 错误：没有保存映射关系
child_chunks = split_small(doc)
parent_chunks = split_large(doc)
# 问题：无法知道哪个 child 属于哪个 parent

# 正确：先切父块，再切子块
for parent in split_large(doc):
    for child in split_small(parent):
        child_to_parent[child_id] = parent_id

2. 重复召回

# 多个子块可能属于同一父块，需要去重
parent_ids = set([child_to_parent[cid] for cid in top_children])

3. 存储冗余

# 优化：只存储父块和映射关系，子块可以动态生成
class EfficientParentChild:
    def __init__(self):
        self.parent_chunks = []  # 只存储父块
        self.child_ranges = []   # 子块在父块中的位置 [(start, end), ...]

LangChain 实现

LangChain 自带 ParentDocumentRetriever。LangChain 1.0（2025-10）之后它被移到了 langchain-classic 包，下面按新的包结构写（需要 pip install langchain-classic langchain-chroma langchain-openai langchain-text-splitters）：

from langchain_classic.retrievers import ParentDocumentRetriever
from langchain_core.stores import InMemoryStore
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

# 注意：RecursiveCharacterTextSplitter 的 chunk_size 默认按字符数计
parent_splitter = RecursiveCharacterTextSplitter(
    chunk_size=2000,
    chunk_overlap=200
)

child_splitter = RecursiveCharacterTextSplitter(
    chunk_size=400,
    chunk_overlap=50
)

# 父块存储（键值对）
store = InMemoryStore()

# 子块向量库
vectorstore = Chroma(
    collection_name="child_chunks",
    embedding_function=embeddings
)

# 组装检索器
retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=store,
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,
)

# 添加文档（documents 为 langchain_core.documents.Document 列表）
retriever.add_documents(documents)

# 检索：返回的是父块
results = retriever.invoke("查询内容")

关键能力对比

定性对比表

维度传统 RAGRAPTOR（树形索引）MCTS-RAG（推理搜索）
擅长的问题简单事实查找长文档总结、跨章节综合需要多步推理和多次检索的问题
长文本处理只看局部块摘要节点提供全局视角取决于底层检索
多跳推理弱较强（摘要节点聚合了多处信息）强（显式拆解问题、多轮检索）
离线成本只做向量化需要 LLM 递归摘要只做向量化
在线成本一次检索 + 一次生成一次检索 + 一次生成多轮 LLM 调用，延迟和 token 都明显增加
工程复杂度低中（树构建与增量更新）高（搜索与打分）

两者也不冲突：RAPTOR 改进的是”索引长什么样”，MCTS-RAG 改进的是”怎么用检索来推理”，理论上可以把 RAPTOR 树作为 MCTS-RAG 的检索后端。

场景示例

一个假设的例子

问题：”这份300页的技术报告中，关于成本优化的建议分布在哪几章？主要观点是什么？”

传统 RAG：

  • 检索到若干包含”成本优化”的段落
  • 无法确定分布位置（第几章）
  • 难以提炼主要观点（缺乏全局视角）

RAPTOR：

  • 从章节级摘要定位相关章节：第3、7、12章
  • 提取各章核心观点并总结
  • 给出结构化答案：
    • 第3章：基础设施成本优化（云资源右配）
    • 第7章：人力成本优化（自动化流程）
    • 第12章：长期成本优化（架构重构）

MCTS-RAG：

  • 先把问题拆成”哪些章节谈成本优化””各章观点是什么”等子问题
  • 对每个子问题分别检索、推理，多条推理路径投票得出答案
  • 准确率可能更高，但调用次数和延迟也成倍增加

核心代码实现对比

传统 RAG 实现

以下两段是便于对照的示意实现，embedding_model.encode 假定接口与 sentence-transformers 一致，llm.summarize 需要自行实现。

from typing import List

# 传统 RAG：扁平化检索
class FlatRAG:
    def __init__(self, documents: List[str], embedding_model):
        self.embedding_model = embedding_model
        self.chunks = []
        self.embeddings = []

        # 1. 文档切分
        for doc in documents:
            chunks = self.split_document(doc, chunk_size=512)
            self.chunks.extend(chunks)

        # 2. 向量化
        self.embeddings = self.embedding_model.encode(self.chunks)

    def retrieve(self, query: str, top_k: int = 5):
        # 3. 向量检索
        query_embedding = self.embedding_model.encode([query])[0]

        # 4. 计算相似度
        from sklearn.metrics.pairwise import cosine_similarity
        similarities = cosine_similarity(
            [query_embedding],
            self.embeddings
        )[0]

        # 5. Top-K 排序
        top_indices = similarities.argsort()[-top_k:][::-1]
        return [self.chunks[i] for i in top_indices]

    def split_document(self, doc: str, chunk_size: int):
        """简单的固定窗口切分"""
        words = doc.split()
        return [
            ' '.join(words[i:i+chunk_size])
            for i in range(0, len(words), chunk_size)
        ]

树形 RAG 实现 (RAPTOR 风格)

from typing import List

# 树形 RAG：层级化检索（collapsed tree 风格）
class TreeRAG:
    def __init__(self, documents: List[str], llm, embedding_model):
        self.llm = llm
        self.embedding_model = embedding_model
        self.tree_layers = []

        # 构建层级树
        self.build_hierarchy(documents)

    def build_hierarchy(self, documents: List[str]):
        """递归构建摘要层级"""
        # 1. 叶节点层：原始 chunks
        leaf_chunks = []
        for doc in documents:
            chunks = self.split_document(doc, chunk_size=512)
            leaf_chunks.extend(chunks)

        self.tree_layers.append({
            'level': 0,
            'nodes': leaf_chunks,
            'embeddings': self.embedding_model.encode(leaf_chunks)
        })

        # 2. 递归构建上层摘要
        current_nodes = leaf_chunks
        level = 1

        while len(current_nodes) > 1:
            # 聚类
            clusters = self.cluster_nodes(current_nodes, n_clusters=max(1, len(current_nodes) // 5))

            # 生成摘要
            summaries = []
            for cluster in clusters:
                summary = self.llm.summarize(cluster)
                summaries.append(summary)

            # 存储当前层
            self.tree_layers.append({
                'level': level,
                'nodes': summaries,
                'embeddings': self.embedding_model.encode(summaries)
            })

            current_nodes = summaries
            level += 1

    def retrieve(self, query: str, top_k_per_layer: int = 3):
        """跨层级混合检索"""
        query_embedding = self.embedding_model.encode([query])[0]

        from sklearn.metrics.pairwise import cosine_similarity
        all_candidates = []

        # 在每一层都检索
        for layer in self.tree_layers:
            similarities = cosine_similarity(
                [query_embedding],
                layer['embeddings']
            )[0]

            top_indices = similarities.argsort()[-top_k_per_layer:][::-1]

            for idx in top_indices:
                all_candidates.append({
                    'text': layer['nodes'][idx],
                    'level': layer['level'],
                    'score': similarities[idx]
                })

        # 按分数排序，返回混合结果
        all_candidates.sort(key=lambda x: x['score'], reverse=True)
        return all_candidates[:top_k_per_layer * 2]

    def cluster_nodes(self, nodes: List[str], n_clusters: int):
        """用 GMM 聚类（这里取最可能的簇，即硬分配；RAPTOR 原文是按概率阈值软分配）"""
        from sklearn.mixture import GaussianMixture

        embeddings = self.embedding_model.encode(nodes)
        gmm = GaussianMixture(n_components=n_clusters, random_state=42)
        labels = gmm.fit_predict(embeddings)

        # 按簇分组
        clusters = [[] for _ in range(n_clusters)]
        for i, label in enumerate(labels):
            clusters[label].append(nodes[i])

        return [c for c in clusters if c]  # 过滤空簇

实践建议

何时使用传统 RAG

适用场景

  • 文档较短，或者问题的答案通常集中在一两段里
  • 查询类型：简单事实查找
  • 对延迟敏感
  • 预算有限，无法承担 LLM 预处理成本

何时使用树形 RAG

适用场景

  • 长文档（书籍、长报告、合同汇编）
  • 查询类型：总结、对比、多跳推理
  • 对准确性要求高于延迟
  • 文档相对稳定，不需要频繁重建索引

混合策略

最佳实践

双路检索架构：

  1. 快速路径：传统 RAG 处理简单查询
  2. 深度路径：树形 RAG 处理总结、对比类复杂查询
  3. 路由：用规则、小分类器或 LLM 判断查询复杂度

两条路径各占多少流量取决于业务，建议先打日志统计真实查询分布再决定。

class HybridRAG:
    def __init__(self, documents, llm, embedding_model, query_classifier):
        self.flat_rag = FlatRAG(documents, embedding_model)
        self.tree_rag = TreeRAG(documents, llm, embedding_model)
        self.query_classifier = query_classifier

    def retrieve(self, query: str):
        # 判断查询复杂度
        if self.query_classifier.is_simple(query):
            return self.flat_rag.retrieve(query)
        else:
            return self.tree_rag.retrieve(query)

聚类数量选择：

def adaptive_clustering(nodes, max_cluster_size=10):
    """自适应聚类数量"""
    n_nodes = len(nodes)
    n_clusters = max(1, n_nodes // max_cluster_size)
    return n_clusters
