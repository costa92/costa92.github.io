CLAUDE.md 别写成许愿墙：200 行是红线

 2026-07-06  Coding-Agent Claude Code AI编程 CLAUDE.md 上下文工程
Claude Code AI编程 CLAUDE.md 上下文工程 配置实战
Coding-Agent
文章字数:   4.5k
阅读次数:  
   阅读模式

同一个仓库，昨天 Claude 写得挺好，今天开个新会话，它又开始瞎猜包管理器、把上周纠正过的错再犯一遍。原因很简单：每次会话都从白纸开始。

CLAUDE.md 就是补这张白纸的文件，它把项目规则、命令、约定塞进每一次会话的开场。最容易被误解的一点先摆在前面：官方 memory 文档原文是 “Claude treats them as context, not enforced configuration”。你写的其实是一份交接文档，读者是一个很能干、但每次上班都失忆的新队友。

下文的事实以官方 memory 和 hooks 文档为准；文中提到的设置键和环境变量（autoMemoryEnabled、claudeMdExcludes、CLAUDE_CODE_DISABLE_AUTO_MEMORY、CLAUDE_CODE_NEW_INIT），我在 2026-10-30 用本机 Claude Code 2.1.314 的程序文本逐个搜过，都还在。

CLAUDE.md 只能引导，强制要靠 hook 和 settings

大多数人的 CLAUDE.md 都写成了许愿墙：塞满 Claude 本来就会做的事，真正重要的三条规则淹没在噪声里。

- 写干净、可维护、高性能的代码
- 遵循最佳实践
- 注意错误处理，保持一致性

这三条对 Claude 等于没说，只是白占 token，还把该被看见的规则往下挤。

官方排障小节说，CLAUDE.md 的内容是 “delivered as a user message after the system prompt”，也就是 system prompt 之后的一条 user message。Claude 读到了、会尽量遵守，但没有强制力，规则一模糊、一互相打架，它就随机挑一个。

所以”每次 commit 前必须跑 lint”这种不容商量的动作，别写成 bullet，去写 hook：

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git commit *)",
            "command": "make lint >&2 || exit 2"
          }
        ]
      }
    ]
  }
}

两个细节容易写错：matcher 只匹配工具名（Bash、Edit|Write），git commit 这种参数条件要写进 if 字段（权限规则语法）；hook 只有以退出码 2 结束才会拦下这次工具调用，其他非零退出码只算非阻塞错误，所以上面用 || exit 2 把 lint 失败转成拦截。

hook 由客户端在固定生命周期节点执行，不管 Claude 怎么想；CLAUDE.md 只塑形，不兜底。”永远用 pnpm，不要用 npm”如果要硬拦，正确位置是 settings 里的 permissions.deny（比如 "Bash(npm *)"）。

要引导，写 CLAUDE.md；要强制，写 hook 或 settings。分不清这两者，是我见过的配置翻车里占比最高的一类。

五层文件全部拼接，谁也不覆盖谁

CLAUDE.md 按作用域分 5 层，加载顺序从广到窄，离启动目录越近的指令越后被读到。

作用域位置共享给谁
Managed policymacOS: /Library/Application Support/ClaudeCode/CLAUDE.md；Linux/WSL: /etc/claude-code/CLAUDE.md；Windows: C:\Program Files\ClaudeCode\CLAUDE.md组织内所有人
User instructions~/.claude/CLAUDE.md你，所有项目
Project instructions./CLAUDE.md 或 ./.claude/CLAUDE.md团队（走版本控制）
Local instructions./CLAUDE.local.md（记得进 .gitignore）你，当前项目
Nested子目录里的 CLAUDE.md读到该目录文件时才载入

很多人以为项目级会盖掉用户级，其实所有被发现的文件全部 concatenate 进上下文。Claude 从当前工作目录向上走目录树，逐层收集 CLAUDE.md 和 CLAUDE.local.md，按文件系统根到工作目录的顺序拼起来。在 foo/bar/ 里启动时：

foo/CLAUDE.md            先进场（离根更近）
foo/bar/CLAUDE.md        后进场（离启动目录更近）
foo/bar/CLAUDE.local.md  同目录内，local 永远排在 CLAUDE.md 之后

所以 user 层的个人偏好和 project 层的项目规则同时在场。两层写了互相打架的规则，Claude 不会帮你仲裁。我踩过一次：user 层写了默认 pnpm，某个老项目的 project 层又写了用 npm，结果每开一个会话，Claude 挑的还不一样。

nested 这层不在启动时载入，只有 Claude 真去读那个子目录里的文件时才纳入。monorepo 能用一棵 CLAUDE.md 树就是靠这个：根目录放通用约定，各子包放各自的规则。

仓库里已经有给其他编码工具写的 AGENTS.md 的话，较新版本的 Claude Code 也会读取它，不必再复制一份。2.1.314 的程序里，AGENTS.md 和 CLAUDE.md、CLAUDE.local.md 出现在同一份待加载文件名列表里。

想确认哪些文件被载入了，用 /memory（程序里的描述是 “Edit CLAUDE.md files and memory settings”），它会列出当前载入的 CLAUDE.md、CLAUDE.local.md 和 rules 文件。某个文件不在列表里，Claude 就是看不见它。我排查”Claude 怎么不听我 CLAUDE.md”，第一步永远是 /memory，有一半的”不听话”其实是”根本没读到”。

@ 导入只帮你组织，不帮你省 token

CLAUDE.md 可以用 @path/to/file 把别的文件拉进上下文：

See @README for project overview and @package.json for available commands.

- git workflow @docs/git-instructions.md
- 跨 worktree 共享个人偏好 @~/.claude/my-project-instructions.md

四条约束，踩中任何一条都白折腾：

  1. 最多 4 跳。被导入的文件可以再导入别的文件，官方 memory 文档的原话是 “a maximum depth of four hops”：从 CLAUDE.md 算起，最多再往下嵌套 4 层 import。
  2. 相对路径相对于包含这行 import 的文件，跟启动目录无关。我把 import 从根 CLAUDE.md 挪进子目录后路径全断了，就是因为参照系跟着文件走。
  3. 代码块里的 @ 不解析。import 解析会跳过 code span 和 fenced code block，想提一嘴某个路径而不导入，用反引号包起来。
  4. import 不省 token。被导入的文件在启动时一样展开、一样进上下文窗口。拆了半天文件以为省了上下文，其实一个 token 没省下；真要减负，靠后面的 path-scoped rules。
写带反引号的 @README（外面有一对反引号）只是字面文本，不会导入；
写不带反引号的 @README 才会把 README 拉进上下文。

另外，第一次遇到外部 import（比如指向 ~/.claude/ 或仓库外的文件），Claude Code 会弹一个批准对话框。点了拒绝，imports 就此停用，对话框也不再出现，想反悔得自己去设置里找。

200 行红线背后是两笔成本

官方给了明确数字：”target under 200 lines per CLAUDE.md file”。

第一笔是 token 成本：CLAUDE.md 每次会话开场全量载入，从第一个字就开始吃工作上下文。第二笔是注意力成本，官方原话 “Longer files consume more context and reduce adherence”，文件越长遵守率越低。这把”文件太长”从审美问题变成了能观察到的行为退化。

拿我自己的博客仓库当例子。它的 CLAUDE.md 进了 git，可以直接看历史：

for c in $(git log --format=%h --reverse -- CLAUDE.md); do
  echo "$c $(git log -1 --format=%cs $c) $(git show $c:CLAUDE.md | wc -l) lines"
done
c23912e 2026-06-23 50 lines
b39765b 2026-06-25 90 lines
3b3f89e 2026-10-04 91 lines
2d31ea2 2026-10-08 94 lines
03fee99 2026-10-08 96 lines
1a94fa5 2026-10-09 120 lines

（2026-10-30 实测，11 次提交里截取 6 行，当前 120 行、10351 字节。）四个月里它一次都没变短过。两次大跳都是新增整段：06-25 加了 CSS 分层、front-matter、数据注入和 UI 审计四节，+39 行；10-09 加了内容规则和导入流程，+24 行。离 200 行还远，但增长曲线只有一个方向。

回头审这份文件，最该下沉的是”Custom Hexo scripts”一节：12 行、约 1.9 KB，逐个解释 scripts/ 下每个文件做什么，只有改这些脚本时才用得上，却每次会话都全量载入。按下文的办法，它适合挪进 .claude/rules/ 并加上 paths: ["scripts/**"]。

砍不动的时候，按这四招分流：

删：Claude 已经稳定做对的规则 → 直接删
移进 skill：多步操作流程（比如"发版流程 8 步"）→ 按需加载，不常驻
移进 path-scoped rule：只对某类文件生效的规则 → 碰到匹配文件时才载入
移进 hook：必须在固定时机跑的（每次 commit 前）→ 强制执行，且不吃上下文

判断一条该不该留，我问自己：这条规则，Claude 上次是不是已经做对了？是的话就删。我给自己定的硬线是 150 行，留 50 行 buffer，一超就坐下来砍。文件半年只增不减，多半是垃圾在堆积。

每条规则都要具体到能判断做没做到

200 行以内放什么？一份项目 CLAUDE.md 大致是这几个区块：

# Project: 一句话说清这是什么

## Stack        —— 技术栈 + 明确写死包管理器（pnpm, never npm）
## Commands     —— build / test / lint / typecheck 的确切命令
## Code style   —— 可验证的规则：缩进、命名、格式化工具
## Architecture —— 具体位置：API handlers 放 src/api/handlers/
## Do / Don't   —— 硬偏好和已知的坑
## Data model   —— 数据密集型项目才需要

决定 Claude 听不听话的是每一条够不够具体。官方给了三组对照：

模糊（Claude 没法照做）具体（Claude 能验证）
“Format code properly”“Use 2-space indentation”
“Test your changes”“Run npm test before committing”
“Keep files organized”“API handlers live in src/api/handlers/“

“格式化好代码”是个态度，”用 2 个空格缩进”是个能照做、能检验的动作。每一条规则都该能被一句”做到了没有”直接判定，做不到的删掉。

一个很少有人用的小技巧：块级 HTML 注释会在注入上下文前被剥离，可以给人类维护者留话，不花 Claude 的 token：

<!-- 维护者注意：下面这条是 2026-07 加的，等 CI 迁移完就删 -->
- 临时规则：跳过 e2e 测试直到 CI 修好

代码块内部的注释会保留，用 Read 工具直接打开文件时注释也可见，只有注入模型上下文那一刻才被剥掉。

用 .claude/rules 按路径分流

瘦身的主力是 .claude/rules/：一个文件一个主题，Claude 会递归发现目录下所有 .md。

your-project/
  .claude/
    CLAUDE.md          主项目指令
    rules/
      code-style.md    代码风格
      testing.md       测试约定
      security.md      安全要求

不带 paths 的 rule 跟 .claude/CLAUDE.md 同优先级、启动即载入。真正省上下文的是带 paths frontmatter 的路径作用域规则，只有 Claude 碰到匹配的文件时才载入：

---
paths:
  - "src/api/**/*.ts"
---

# API Development Rules
- All API endpoints must include input validation
- Use the standard error response format
- Include OpenAPI documentation comments
模式匹配
**/*.ts任意目录下所有 TS 文件
src/**/*src/ 下所有文件
*.md项目根目录的 Markdown
src/**/*.{ts,tsx}brace 展开，一条顶两条

两个进阶点。一是用户级 ~/.claude/rules/ 对你机器上所有项目生效，先于项目级载入；官方说得明白，两者谁也不覆盖谁，冲突时 Claude 可能遵循任意一条。二是 .claude/rules/ 支持 symlink，可以维护一套团队公共规则软链进每个项目：

ln -s ~/team-standards/security.md .claude/rules/security.md

链接目标在工作目录之外时，Claude Code 会把它当成外部 import 处理，要先批准外部导入才会载入，而且批准后也只载入不带 paths 的规则。

稍有规模的项目，我建议一上来就建 .claude/rules/。等主文件超了 200 行再拆，规则之间往往已经开始互相打架了。

三份可以直接改的模板

下面三份是示例：项目名和细节都是虚构的，结构参考社区里常见的写法，不是哪个真实项目的文件。照着填自己的栈就行。

Web 应用（Next.js / TypeScript）：

# Project: Acme Dashboard
Customer-facing analytics dashboard. Next.js + TypeScript + Tailwind.

## Stack
- Next.js 15 (App Router), React 19, TypeScript (strict)
- Package manager: pnpm (never npm or yarn)

## Commands
- Dev: pnpm dev   Build: pnpm build   Test: pnpm test
- Lint + typecheck: pnpm lint && pnpm typecheck

## Architecture
- Never call DB from client components; use server actions in app/**/actions.ts

## Do / Don't
- DO run pnpm lint && pnpm typecheck before declaring done
- DON'T edit generated files in lib/generated/

移动端（Expo / React Native），平台特有约定是 Claude 最容易猜错的地方：

# Project: Trailhead (Expo / React Native)
Cross-platform hiking companion app. Expo + Expo Router.

## Commands
- Start: pnpm expo start   iOS: pnpm expo run:ios
- Typecheck: pnpm tsc --noEmit

## Architecture
- Platform-specific: *.ios.tsx / *.android.tsx

## Do / Don't
- DO use expo-image, not the RN Image component
- DON'T import Node-only modules; runs in Hermes

数据 / Python 项目（uv），一定要写死哪些目录只读、哪些绝不提交：

# Project: churn-model
ML pipeline for customer churn prediction. Python 3.12 + uv.

## Commands
- Install: uv sync   Test: uv run pytest
- Lint + format: uv run ruff check . && uv run ruff format .

## Architecture
- Notebooks exploratory only—never import from them
- Raw data in data/raw/ is read-only

## Do / Don't
- DO keep data loading deterministic (set random_state)
- DON'T commit anything from data/ or models/artifacts/

三份的共同点是每一条都指向一个具体位置或一个确切命令，没有一句”写好代码”。

不想从零写，直接 /init，Claude 会分析代码库生成初稿；已经有 CLAUDE.md 的话，它给改进建议而不是覆盖。想要交互式的多阶段流程：

# 启用交互式多阶段 /init（设好后在会话里运行 /init）
CLAUDE_CODE_NEW_INIT=1 claude

2.1.314 的程序里，设了这个变量后 /init 的描述会变成 “Initialize new CLAUDE.md file(s) and optional skills/hooks with codebase documentation”，也就是除了 CLAUDE.md 还会顺带建议 skill 和 hook。/init 给的是草稿，它只能发现代码库里明面上的东西，团队的隐性规矩、踩过的坑还得手动补。

Auto memory 是另一套系统，由 Claude 自己写

官方文档把标题叫 “How Claude remembers your project”，并明确框成两套互补的记忆系统：

CLAUDE.md filesAuto memory
谁写你Claude 自己
装什么指令和规则学到的经验和模式
载入每次会话，全量每次会话（MEMORY.md 前 200 行或 25KB）
用于编码标准、工作流、架构构建命令、调试洞察、它发现的偏好

auto memory 在工作时自动记下构建命令、调试心得、偏好，按”未来会话是否用得上”决定存不存。存储位置按项目分：

~/.claude/projects/<project>/memory/
  MEMORY.md          索引入口，每次会话载入（前 200 行 / 25KB）
  debugging.md       详细调试笔记，按需读
  api-conventions.md API 设计决策

前 200 行 / 25KB 的限制只对 MEMORY.md，它是索引，超出部分不在开场载入；CLAUDE.md 不论多长都全量载入，只是短的遵守率更好。一个是记忆索引的载入上限，一个是手写指令的建议上限，别混。2.1.314 的程序里，整理记忆的提示词原文是 so it stays under ${EL} lines AND under ~25KB. It's an **index**, not a dump，${EL} 是程序里的行数变量，大写的 AND 和加粗的 index 都是原文自带的强调，不是我加的。

auto memory 在本地会话里默认开启，可以在 /memory 里切换（写入 ~/.claude/settings.json 的 autoMemoryEnabled），也可以在项目 settings 里单独关掉：

{ "autoMemoryEnabled": false }
# 或者用环境变量整机关闭
export CLAUDE_CODE_DISABLE_AUTO_MEMORY=1

auto memory 是机器本地的，<project> 路径从 git 仓库推导，同一个仓库的所有 worktree 和子目录共享同一个 memory 目录，但不跨机器、不跨云环境同步。换台机器、进 CI 就没了。

我把 auto memory 当草稿本：定期在 /memory 里扫一眼，有用的提升进 CLAUDE.md，剩下的删掉。在会话里说”以后用 pnpm 不用 npm”，Claude 默认存进 auto memory；想让它进 CLAUDE.md 给团队共享，得明说”加到 CLAUDE.md 里”。不然规则明明写了，同事却拿不到。

出问题时对着查的表

症状根因修法
Claude 不听 CLAUDE.md规则模糊或互相矛盾；它是 user message/memory 确认载入；把规则改具体；查跨文件矛盾
规则太虚“格式化好” 没法照做换成 “用 2 空格缩进” 这种可验证的
多文件打架主文件、nested、rules 之间冲突定期审所有 CLAUDE.md；monorepo 用 claudeMdExcludes 跳无关的
有条规则必须每次都跑CLAUDE.md 只引导不强制写成 hook
/compact 后指令像丢了nested 文件不自动重注入项目根 CLAUDE.md 会从磁盘重读；nested 下次读到才重载

/compact 最容易被误判成”配置失效”：项目根 CLAUDE.md 压缩后会从磁盘重读、重新注入；会”消失”的是子目录里的 nested 文件，要等 Claude 下次读到那个目录才重载。如果某条指令 compact 后像是丢了，先想想它是不是只在对话里说过、根本没落进任何 CLAUDE.md。

monorepo 里被别的团队的 CLAUDE.md 污染，用 claudeMdExcludes 按绝对路径的 glob 跳过，放 .claude/settings.local.json 只在本机生效：

{
  "claudeMdExcludes": [
    "**/monorepo/CLAUDE.md",
    "/home/user/monorepo/other-team/.claude/rules/**"
  ]
}

组织级还有一招：claudeMd key 能把 managed CLAUDE.md 内容直接塞进 managed-settings.json（只在 managed/policy 设置里生效）。和 managed CLAUDE.md 文件一样，它不能被 claudeMdExcludes 排除：

{
  "claudeMd": "Always run `make lint` before committing.\nNever push directly to main."
}

新项目的 10 分钟清单

1. 跑 /init 生成初稿
2. 砍到 200 行以内，每条规则改到"可验证"
3. 只对某类文件生效的 → 下沉到 .claude/rules/ 带 paths
4. 分层：~/.claude/CLAUDE.md 放跨项目个人偏好，项目 CLAUDE.md 放团队规则
5. /memory 确认全部载入
6. 提交到版本控制
7. 同一个纠正说第二次就写进去，过期的立刻删

最常被跳过的是第 5 步和第 7 步。Claude 第二次犯同样的错、code review 抓到它本该知道的常识、你又一次把同样的纠正打进聊天框，这些都是该加一条的信号；稳定做对的、过期的规则，该删就删。我自己那份 120 行的文件，下一步就是把 scripts 那一节挪进 rules。

周末写个小脚本，犯不着套这套仪式；复杂的团队仓库才值得认真分层。配置的规模跟着项目的规模走。
