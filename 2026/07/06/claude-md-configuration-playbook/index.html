CLAUDE.md 别写成许愿墙：200 行是红线

 2026-07-06  Coding-Agent Claude Code AI编程 CLAUDE.md 上下文工程
Claude Code AI编程 CLAUDE.md 上下文工程 配置实战
Coding-Agent
文章字数:   5.9k
阅读次数:  
   阅读模式

同一个仓库，昨天 Claude 写得挺好，今天开个新会话，它又开始瞎猜你的包管理器、把上周纠正过的错再犯一遍。不是模型变笨了，是它每次都从白纸开始，上一轮记忆全丢了。

CLAUDE.md 就是用来补这张白纸的那份文件，它把项目规则、命令、约定塞进每一次会话的开场。我先把最容易被误解的一句话摆在前面：CLAUDE.md 是上下文，不是强制配置。官方文档（code.claude.com/docs/en/memory）原文写得很直白——“Claude treats them as context, not enforced configuration”。你不是在给机器写规则，你是在给一个很能干、但每次上班都失忆的新队友写交接文档。想清楚这一点，后面所有的取舍都顺了。

这篇讲什么

  • CLAUDE.md 的 5 层加载顺序，以及”拼接不覆盖”到底怎么拼
  • @-imports 的四条硬约束（最坑的是”不省 token”）
  • 200 行红线背后的两笔成本，以及瘦身的四招
  • 最优结构的 7 个区块 + path-scoped rules
  • 官方现在把”记忆”框成了两套系统，大多数人只知道一半

一、它到底是什么：上下文，不是开关

先说我的暴论：大多数人的 CLAUDE.md 都写成了许愿墙——塞满一堆 Claude 本来就会做的事，真正重要的三条规则淹没在噪声里。许愿墙长这样：

- 写干净、可维护、高性能的代码
- 遵循最佳实践
- 注意错误处理，保持一致性

这三条对 Claude 等于没说。它本来就在”尽量写干净的代码”，你把这几行堆在 ## Code style 底下，只是白占 token，还顺手把真正该被看见的规则往下挤。这种文件越长，Claude 越不听话。

为什么？因为 CLAUDE.md 的内容不是以 system prompt 的身份进场的。官方排障小节说得很清楚：它是 “delivered as a user message after the system prompt”——system prompt 之后的一条 user message。Claude 读到了、会尽量遵守，但没有强制力，规则一模糊、一互相打架，它就随机挑一个。

所以当你真的需要”每次 commit 前必须跑 lint”这种不容商量的动作，别写进 CLAUDE.md 的 bullet 里，那只是许愿。去写 hook：

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git commit *)",
            "command": "make lint >&2 || exit 2"
          }
        ]
      }
    ]
  }
}

两个细节容易写错：matcher 只匹配工具名（Bash、Edit|Write），git commit 这种参数条件要写进 if 字段（权限规则语法）；hook 只有以退出码 2 结束才会拦下这次工具调用，其他非零退出码只算非阻塞错误，所以上面用 || exit 2 把 lint 失败转成拦截。

区别在于：hook 由客户端在固定生命周期节点强制执行，不管 Claude 怎么想；CLAUDE.md 只塑形，不兜底。同样是许愿墙里最常见的一条——“永远用 pnpm，不要用 npm”——如果你要的是硬拦截，正确位置是 settings 里的 permissions.deny（比如 "Bash(npm *)"），而不是一句 markdown。

一句话记住这条边界：要引导，写 CLAUDE.md；要强制，写 hook 或 settings。 分不清这两者，是我见过的配置翻车里占比最高的一类。

二、Claude 怎么加载它：5 层，拼接不覆盖

CLAUDE.md 不止一个文件。它按作用域分 5 层，从最广到最窄，加载顺序也是从广到窄——广的先进场，窄的后进场，所以离你启动目录越近的指令越”后被读到”。

作用域位置共享给谁
Managed policymacOS: /Library/Application Support/ClaudeCode/CLAUDE.md；Linux/WSL: /etc/claude-code/CLAUDE.md；Windows: C:\Program Files\ClaudeCode\CLAUDE.md组织内所有人
User instructions~/.claude/CLAUDE.md你，所有项目
Project instructions./CLAUDE.md 或 ./.claude/CLAUDE.md团队（走版本控制）
Local instructions./CLAUDE.local.md（记得进 .gitignore）你，当前项目
Nested子目录里的 CLAUDE.md按需，读到该目录文件时才载入

这里最反直觉的是拼接不覆盖。很多人以为项目级会”盖掉”用户级，其实不会——所有被发现的文件全部 concatenate 进上下文。Claude 从当前工作目录向上走目录树，逐层收集 CLAUDE.md 和 CLAUDE.local.md，然后按文件系统根 → 工作目录的顺序拼起来。假设你在 foo/bar/ 里启动：

foo/CLAUDE.md            先进场（离根更近）
foo/bar/CLAUDE.md        后进场（离启动目录更近）
foo/bar/CLAUDE.local.md  同目录内，local 永远排在 CLAUDE.md 之后

因为是”拼接”，所以你的个人偏好（user 层）和项目规则（project 层）会同时在场、同时生效——它们不是二选一。这也意味着两层写了互相打架的规则时，Claude 不会自动帮你仲裁，它只会挑一个，这是后面”多文件打架”那个坑的根子。我踩过一次：user 层写了默认 pnpm，某个老项目的 project 层又写了用 npm，结果我每开一个会话，Claude 挑的还不一样。

nested（子目录）这层单独说一句：它不在启动时载入，只有当 Claude 真的去读那个子目录里的文件时才纳入上下文。这也是为什么 monorepo 能用一棵 CLAUDE.md 树——根目录放通用约定，各子包放各自的规则，Claude 走到哪读到哪。

如果仓库里已经有给其他编码工具写的 AGENTS.md，v2.1.277 起的 Claude Code 也能直接读取它，不必再复制一份成 CLAUDE.md。

想确认到底哪些文件被载入了？别猜，用 /memory：

# 会话里直接敲，列出当前载入的所有 CLAUDE.md / CLAUDE.local.md / rules 文件
/memory

如果某个文件没出现在列表里，Claude 就是看不见它，十有八九是位置放错了。我排”Claude 怎么不听我 CLAUDE.md”的问题，第一步永远是 /memory 确认它真被载入了，而不是急着改措辞。我发现有一半的”不听话”其实是”根本没读到”。

三、@-imports 的四条硬约束

CLAUDE.md 可以用 @path/to/file 把别的文件拉进上下文，方便你把长指令拆成模块。语法很简单，但有四条硬约束，踩中任何一条都白折腾：

See @README for project overview and @package.json for available commands.

- git workflow @docs/git-instructions.md
- 跨 worktree 共享个人偏好 @~/.claude/my-project-instructions.md

第一条，最多 4 跳（four hops）。 被导入的文件可以再导入别的文件，但递归深度上限是 4。超过就断，别指望搭一座七层塔。

第二条，相对路径相对于”文件本身”，不是工作目录。 @docs/git-instructions.md 是相对于包含这行 import 的那个文件去找，不是相对于你启动 Claude 的目录。这条我踩过——我在把 import 从根 CLAUDE.md 挪进子目录后，路径全断了，就是因为参照系跟着文件走了。

第三条，代码块里的 @ 不解析。 import 解析会跳过 markdown 的 code span 和 fenced code block。所以你想在文里”提一嘴”某个路径而不真的导入它，用反引号包起来就行：

写带反引号的 @README（外面有一对反引号）只是字面文本，不会导入；
写不带反引号的 @README 才会把 README 拉进上下文。

第四条，也是最反直觉的一条：import 不省 token。 很多人拆 import 是为了”减小主文件、省上下文”——省不了。被导入的文件在启动时一样会展开、一样进上下文窗口。import 只帮你组织，不帮你减负。真要减 token，得靠后面讲的 path-scoped rules 和瘦身，不是靠 import。这是对 import 最常见的误会，拆了半天文件以为省了上下文，其实一个 token 没省下。

补一个安全提示：第一次遇到外部 import（比如指向 ~/.claude/ 或仓库外的文件），Claude Code 会弹一个批准对话框列出这些文件。你要是点了拒绝，imports 就此停用，而且对话框不再出现——想反悔得自己去设置里找。

四、200 行红线：两笔成本

官方给了一个明确数字：target under 200 lines per CLAUDE.md file——每个 CLAUDE.md 控制在 200 行以内。这不是洁癖，是两笔实打实的成本叠加。

第一笔是 token 成本。CLAUDE.md 每次会话开场都全量载入，一份 300 行的文件，占的 token 从第一个字就开始吃你的工作上下文。第二笔更隐蔽，是注意力成本：文件越长，真正重要的规则越容易被埋在中间，模型对”上下文正中间”的内容处理得最不稳。官方原话——“Longer files consume more context and reduce adherence”，长文件降低遵守率。这句话的分量在于，它把”文件太长”从”不够优雅”升级成了”直接掉遵守率”，是能被观察到的行为退化。

所以红线的正解不是”写到 199 行为止”，而是主动砍。我给一个能立刻上手的判断顺序，砍不动的时候按这四招分流：

删：Claude 已经稳定做对的规则 → 直接删，别留着占地方
移进 skill：多步操作流程（比如"发版流程 8 步"）→ 按需加载，不常驻
移进 path-scoped rule：只对某类文件生效的规则 → 只在碰到匹配文件时载入
移进 hook：必须在固定时机跑的（每次 commit 前）→ 强制执行，且不吃上下文

判断”这条该不该留”的时候，我会用一个反问：这条规则，Claude 上次是不是已经做对了？ 是的话就删——留着它唯一的作用是稀释真正需要提醒的那几条。想量化就直接数行数：

# 超过 200 行就该动手瘦身了
wc -l CLAUDE.md

超过 200 行的 CLAUDE.md，回头看很少是”必须这么长”——多半是懒得删攒出来的。该删的是 Claude 早就做对的通用规矩，该留的是几条它真会猜错的项目约定。好的 CLAUDE.md 随时间是越写越短的。我会给自己定一条硬线：150 行，留 50 行 buffer，一超就逼自己坐下来砍。如果你的文件半年只增不减，那不是配置在进化，是垃圾在堆积。

五、最优结构：7 个区块 + 具体压倒模糊

200 行以内该放什么？一份好用的项目 CLAUDE.md，大致就这 7 个区块，多一个都要问自己”真需要吗”：

# Project: 一句话说清这是什么

## Stack        —— 技术栈 + 明确写死包管理器（pnpm, never npm）
## Commands     —— build / test / lint / typecheck 的确切命令
## Code style   —— 可验证的规则：缩进、命名、格式化工具
## Architecture —— 具体位置：API handlers 放 src/api/handlers/
## Do / Don't   —— 硬偏好和已知的坑
## Data model   —— 数据密集型项目才需要

真正决定 Claude 听不听话的，不是区块多全，而是每一条够不够具体到可验证。官方给了三组对照，我会建议你逐条对照自己的文件：

模糊（Claude 没法照做）具体（Claude 能验证）
“Format code properly”“Use 2-space indentation”
“Test your changes”“Run npm test before committing”
“Keep files organized”“API handlers live in src/api/handlers/“

差别在哪？”格式化好代码”是个态度，Claude 无从下手；”用 2 个空格缩进”是个可以照做、可以检验的动作。你写的每一条规则，都该能被一句”做到了没有”直接判定。做不到这一点的规则，删了它，它只是在凑字数。我在对照这 7 个区块删自己文件时，第一个下手的永远是 Code style 里那几行正确的废话。

还有一个几乎没人用的小技巧：块级 HTML 注释会在注入上下文前被剥离。也就是说你可以在 CLAUDE.md 里给人类维护者留话，而不花 Claude 一个 token：

<!-- 维护者注意：下面这条是 2026-07 加的，等 CI 迁移完就删 -->
- 临时规则：跳过 e2e 测试直到 CI 修好

代码块内部的注释会保留，用 Read 工具直接打开文件时注释也可见——只有注入模型上下文那一刻才被剥掉。拿它写”给人看、不给模型看”的维护笔记，很顺手。

六、path-scoped rules：让规则只在需要时出现

瘦身的主力工具是 .claude/rules/。把指令拆成一个文件一个主题，放进这个目录，Claude 会递归发现所有 .md：

your-project/
  .claude/
    CLAUDE.md          主项目指令
    rules/
      code-style.md    代码风格
      testing.md       测试约定
      security.md      安全要求

不带 paths 的 rule 跟 .claude/CLAUDE.md 同优先级、启动即载入。真正省上下文的是带 paths frontmatter 的路径作用域规则——只有当 Claude 碰到匹配的文件时才载入：

---
paths:
  - "src/api/**/*.ts"
---

# API Development Rules
- All API endpoints must include input validation
- Use the standard error response format
- Include OpenAPI documentation comments

这条规则平时不占任何上下文，只有 Claude 真去改 src/api/ 下的 TypeScript 时才浮现。glob 支持得挺全，够覆盖绝大多数分流需求：

模式匹配
**/*.ts任意目录下所有 TS 文件
src/**/*src/ 下所有文件
*.md项目根目录的 Markdown
src/**/*.{ts,tsx}brace 展开，一条顶两条

再补两个进阶点。一是用户级 ~/.claude/rules/ 对你机器上所有项目生效，适合放跟项目无关的个人偏好；用户级先于项目级载入，所以项目规则出现在上下文更靠后的位置。但官方说得很清楚：两者谁也不覆盖谁，冲突时 Claude 可能遵循任意一条，所以要保持一致。二是 .claude/rules/ 支持 symlink，你可以维护一套团队公共规则，软链进每个项目：

ln -s ~/team-standards/security.md .claude/rules/security.md

注意：链接目标在工作目录之外时，Claude Code 会把它当成外部 import 处理，要先在项目里批准外部导入才会载入，而且批准后也只载入不带 paths 的那些规则。

我推荐稍有规模的项目一上来就建 .claude/rules/，因为主文件迟早会膨胀，晚拆不如早拆——等它超了 200 行再来救火，规则之间往往已经开始互相打架了。做法是：CLAUDE.md 只留”每次都要知道”的通用约定，一切”只在改某类文件时才相关”的规则全下沉到 path-scoped rules。这一招是把 200 行红线真正落地的关键。

七、三个可复制模板

光讲规则太虚，给三份能直接抄的骨架。这是社区里流传的常见结构，我拿来当范例——照着填你自己的栈就行。

Web 应用（Next.js / TypeScript）：

# Project: Acme Dashboard
Customer-facing analytics dashboard. Next.js + TypeScript + Tailwind.

## Stack
- Next.js 15 (App Router), React 19, TypeScript (strict)
- Package manager: pnpm (never npm or yarn)

## Commands
- Dev: pnpm dev   Build: pnpm build   Test: pnpm test
- Lint + typecheck: pnpm lint && pnpm typecheck

## Architecture
- Never call DB from client components; use server actions in app/**/actions.ts

## Do / Don't
- DO run pnpm lint && pnpm typecheck before declaring done
- DON'T edit generated files in lib/generated/

移动端（Expo / React Native）——注意它把”平台特有约定”写死了，这正是 Claude 最容易猜错的地方：

# Project: Trailhead (Expo / React Native)
Cross-platform hiking companion app. Expo + Expo Router.

## Commands
- Start: pnpm expo start   iOS: pnpm expo run:ios
- Typecheck: pnpm tsc --noEmit

## Architecture
- Platform-specific: *.ios.tsx / *.android.tsx

## Do / Don't
- DO use expo-image, not the RN Image component
- DON'T import Node-only modules; runs in Hermes

数据 / Python 项目（uv）——数据类项目一定要写死”哪些目录只读、哪些绝不提交”：

# Project: churn-model
ML pipeline for customer churn prediction. Python 3.12 + uv.

## Commands
- Install: uv sync   Test: uv run pytest
- Lint + format: uv run ruff check . && uv run ruff format .

## Architecture
- Notebooks exploratory only—never import from them
- Raw data in data/raw/ is read-only

## Do / Don't
- DO keep data loading deterministic (set random_state)
- DON'T commit anything from data/ or models/artifacts/

三份模板的共同点，不是区块一样，而是每一条都指向一个具体位置或一个确切命令——没有一句”写好代码”。这就是能用的 CLAUDE.md 和许愿墙的区别。新项目抄一份改栈名就能出第一版，剩下的靠后面几次纠正慢慢长。

不想从零写？直接 /init，Claude 会分析代码库、把发现的构建命令、测试指令、项目约定生成一份初稿。已经有 CLAUDE.md 的话，/init 是给改进建议而不是覆盖。想要更细的交互流程，开这个环境变量：

# 启用交互式多阶段 /init（设好后在会话里运行 /init）
CLAUDE_CODE_NEW_INIT=1 claude

但记住 /init 给的是草稿不是成品。它能发现的只是代码库里明面上的东西，那些 Claude 自己猜不到的约定——你团队的隐性规矩、踩过的坑——还得你手动补。用 /init 起草后，记得按上一节的标准删掉 Claude 本来就会做的那部分。

八、Auto memory：官方现在讲的是”两套记忆系统”

这一节是很多 CLAUDE.md 教程没提、但值得知道的。官方文档现在把标题就叫 “How Claude remembers your project”，并且明确框成两套互补的记忆系统：

CLAUDE.md filesAuto memory
谁写你Claude 自己
装什么指令和规则学到的经验和模式
载入每次会话，全量每次会话（MEMORY.md 前 200 行或 25KB）
用于编码标准、工作流、架构构建命令、调试洞察、它发现的偏好

CLAUDE.md 是你写给 Claude 的；auto memory 是 Claude 写给自己的。它在工作时自动记下构建命令、调试心得、代码风格偏好这类东西，按”未来会话是否用得上”决定存不存——不是每次都存。存储位置按项目分：

~/.claude/projects/<project>/memory/
  MEMORY.md          索引入口，每次会话载入（前 200 行 / 25KB）
  debugging.md       详细调试笔记，按需读
  api-conventions.md API 设计决策

有个关键细节容易搞混：前 200 行 / 25KB 的限制只对 MEMORY.md——它是索引，Claude 靠它知道详细内容存在哪个主题文件里，超出部分不在开场载入。而 CLAUDE.md 不论多长都全量载入（只是短的遵守率更好）。两个”200”含义完全不同，别混：一个是”记忆索引的载入上限”，一个是”你手写指令的建议上限”。

auto memory 在本地会话里默认开启，可以在 /memory 里切换开关（会写入 ~/.claude/settings.json 的 autoMemoryEnabled），也可以在项目 settings 里单独关掉：

{ "autoMemoryEnabled": false }
# 或者用环境变量整机关闭
export CLAUDE_CODE_DISABLE_AUTO_MEMORY=1

还有一点值得先知道，免得踩坑：auto memory 是机器本地的，<project> 路径从 git 仓库推导，所以同一个仓库的所有 worktree 和子目录共享同一个 memory 目录，但它不跨机器、不跨云环境同步。换句话说，你本机让 Claude 记住的东西，换台机器、进 CI 就没了。真正要团队共享、要跨环境生效的规则，还是得写进进版本控制的 CLAUDE.md，别指望 auto memory 帮你带过去。

我的用法是把 auto memory 当草稿本：定期在 /memory 里扫一眼，有用的提升进 CLAUDE.md，剩下的删掉。分工上，auto memory 适合让 Claude 沉淀”它自己摸索出来的东西”（比如”这个测试要先起本地 Redis”），而 CLAUDE.md 适合放”团队共识、要进版本控制”的规则。当你在会话里说”记住以后用 pnpm 不用 npm”，Claude 默认会存进 auto memory；你要是想让它进 CLAUDE.md（团队共享），得明说”加到 CLAUDE.md 里”。搞清楚这个分工，才不会把该共享的规则丢进只有自己机器可见的 auto memory——那是团队协作里很隐蔽的一个漏点，规则明明写了，同事却拿不到。

九、常见失败模式 + 10 分钟行动清单

把最高频的几个坑和对应修法列一张表，出问题时对着查：

症状根因修法
Claude 不听 CLAUDE.md规则模糊或互相矛盾；它是 user message 不是 system prompt/memory 确认载入；把规则改具体；查跨文件矛盾
规则太虚“格式化好” 没法照做换成 “用 2 空格缩进” 这种可验证的
多文件打架主文件、nested、rules 之间冲突定期审所有 CLAUDE.md；monorepo 用 claudeMdExcludes 跳无关的
有条规则必须每次都跑CLAUDE.md 只引导不强制写成 hook
/compact 后指令像丢了nested 文件不自动重注入项目根 CLAUDE.md 会从磁盘重读续存；nested 下次读到才重载

这里补一句 /compact 的细节，因为它最容易被误判成”配置失效”：项目根 CLAUDE.md 在压缩后会从磁盘重读、重新注入，所以它是稳的；真正会”消失”的是子目录里的 nested 文件，它们要等 Claude 下次读到那个目录的文件才重载。如果某条指令 compact 后像是丢了，先想想它是不是只在对话里说过、根本没落进任何 CLAUDE.md——那种才是真的没了。

monorepo 里被别的团队的 CLAUDE.md 污染，是大仓最烦的一类。claudeMdExcludes 按绝对路径的 glob 跳过这些文件，放 .claude/settings.local.json 可以让排除只在你本机生效：

{
  "claudeMdExcludes": [
    "**/monorepo/CLAUDE.md",
    "/home/user/monorepo/other-team/.claude/rules/**"
  ]
}

组织级还有一招：claudeMd key 能把 managed CLAUDE.md 内容直接塞进 managed-settings.json（只在 managed/policy 设置里生效，写在用户或项目设置里无效）。和 managed CLAUDE.md 文件一样，它不能被 claudeMdExcludes 排除：

{
  "claudeMd": "Always run `make lint` before committing.\nNever push directly to main."
}

最后给一份我自己在用的 10 分钟清单，新项目照着走一遍就有一份能用的配置：

1. 跑 /init 生成初稿
2. 砍到 200 行以内，每条规则改到"可验证"
3. 只对某类文件生效的 → 下沉到 .claude/rules/ 带 paths
4. 分层：~/.claude/CLAUDE.md 放跨项目个人偏好，项目 CLAUDE.md 放团队规则
5. /memory 确认全部载入
6. 提交到版本控制（团队一起受益）
7. 养成习惯：同一个纠正说第二次就写进去，过期的立刻删

最常被跳过的是第 5 步和第 7 步，而第 7 条恰恰最重要，也最难坚持。CLAUDE.md 不是写一次就锁死的配置，它是一份跟着项目长的活文档：Claude 第二次犯同样的错、code review 抓到它本该知道的常识、你又一次把同样的纠正打进聊天框——这些都是该往里加一条的信号。同样，Claude 已经稳定做对的、过期的规则，该删就删。

配 CLAUDE.md 别上来就追求大而全。周末写个小脚本，犯不着套 200 行的仪式；真正复杂的团队仓库，才值得你认真分层。把功夫花在配置的规模匹配项目的规模上——这比任何模板都管用。装好之后别忘了做那件最容易被跳过的事：/memory 打开看一眼，确认 Claude 真的读到了你写的东西，而不是又在白纸上瞎猜。
