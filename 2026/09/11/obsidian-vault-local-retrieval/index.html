给 Obsidian 知识库接一层本地检索：一次踩坑实录

 2026-09-11  AI Claude Code Obsidian LLM Wiki qmd
Claude Code Obsidian LLM Wiki qmd 本地 RAG
AI
文章字数:   2.5k
阅读次数:  
   阅读模式

起点

我的 Obsidian vault 有 660 篇 markdown，其中 wiki/ 目录是按 Karpathy 的 LLM Wiki 范式由 LLM 维护的累积层，三个 sub-wiki 共 66 个内容页，lint 报告矛盾、孤儿、死链全部为零。看起来很健康。

但让 AI 用它回答问题时暴露了一个结构性缺口：query 操作靠”先读 index.md 再挑几页深读”，只覆盖 wiki 层那几十页。02-技术/ 里 370 多篇亲手写的文章不在任何 index 里，AI 根本不知道它们存在。

wiki/local-rag-kb/ 这个 sub-wiki 恰好早就把答案研究好了：vault 页数在 150 到 2000 之间，该上 qmd（BM25 + 向量 + LLM rerank 的本地混合检索，Karpathy 在 LLM Wiki 那篇 gist 里点名提到的搜索工具）。这篇文章记录的是从”结论已知”到”跑起来”之间的距离。

问题一：Schema 说自己是 git 仓库，其实不是

顶层 CLAUDE.md 里写着设计哲学第四条：”Wiki 是 git repo，版本历史本身就是隐式的 log”。实际目录下没有 .git，只有 OneDrive 在同步。

这是典型的”schema 与现实脱节”。规则写进文档不等于生效，lint 只检查 wiki 页之间的一致性，不检查 schema 自己的承诺有没有兑现。

处理很简单：git init，写 .gitignore 排除 .DS_Store、__pycache__、.bak 备份和可重建的索引目录，做初始提交。一个意外是 url-shortener/ 自带 .git，被当作嵌入仓库只记了一个 commit 指针，后续要么删掉内层 .git，要么转 submodule。

真正的风险在 OneDrive 上。同步工具对 .git 目录里高频变动的小文件并不友好，我之前就记录过 OneDrive 回滚本目录脚本改动、剥掉执行位的案例。这次先把 .git 留在同步目录里，隔天核对。更稳的做法是把 .git 移到同步范围之外，用 git --git-dir 指过去。

问题二：安装”卡住”其实是我等得不够久

bun install -g @tobilu/qmd 跑了 5 分钟没有任何输出，超时被挪到后台。我判断它卡死了，另开一个 npm install 重装，结果两个安装进程并行往同一个全局目录写，互相踩。

后来 bun 那次安静地完成了，qmd 好端端地装在 ~/.bun/bin/ 下。

教训是：判断一个进程”卡住”之前，先看它有没有网络连接、有没有子进程、目标目录有没有在变大。没输出不等于没进展。qmd 依赖 node-llama-cpp，后者要拉十几个平台的预编译二进制，每个 20 到 40MB，在慢网络下就是十几分钟的静默。

问题三：HuggingFace 直连 0 字节

qmd 首次 embed 会从 HuggingFace 下载三个 GGUF 模型。实测这台机器的网络状况：

源速度
huggingface.co0 B/s，连接建立后无数据
hf-mirror.com302 跳回 huggingface.co，等于没用
modelscope.cn21 KB/s
registry.npmjs.org约 100 KB/s
registry.ollama.ai约 140 KB/s

qmd embed 进程挂着，没有报错，也没有任何 socket。这是第二种”卡住”，和问题二的区别是这次真的卡了。

处理方式是绕开 HuggingFace：Ollama 仓库里有同一个 Qwen3-Embedding-0.6B Q8_0 和 Qwen3-Reranker-0.6B，Ollama 的 blob 本身就是 GGUF 文件。qmd 定位缓存模型的逻辑是在 ~/.cache/qmd/models/ 下按文件名做 includes 匹配，所以把 Ollama 的 blob 用符号链接挂成 qmd 期望的文件名就能跳过下载。我把这个操作写成了一个十几行的脚本放在 ~/.config/qmd/。

这个方案不优雅，但它把”模型分发”从一个不可控的 CDN 换到了一个可控的。在这台机器的网络环境下，Ollama 仓库是最稳的 GGUF 来源。

问题四：默认 embedding 模型不认中文

qmd 默认用 embeddinggemma-300M，README 明说它是 English-optimized，对 CJK 覆盖有限。vault 是中文为主的，这个默认值直接决定了向量召回的质量。

有意思的是，wiki/local-rag-kb/entities/qwen3-embedding.md 早在两个月前就写好了结论：Qwen3-Embedding 支持 119 种语言，是 BGE-M3 最强的开源挑战者。qmd 的 README 也建议中文等 CJK 内容换成 Qwen3-Embedding。wiki 层研究过的东西，在动手时要记得回去查。我在 index.yml 的 models.embed 里显式指定了它，避免依赖环境变量。

顺带发现一个能省下 1.1GB 下载的细节：qmd 的第三个模型是查询扩展用的微调小模型，只在 CLI 的 qmd query 路径上用。MCP 路径的 query 工具要求调用方自己传 lex / vec / hyde 三类子查询，扩展由调用它的大模型完成。既然目标是让 Claude Code 通过 MCP 调用，这个模型可以不装。

问题五：BM25 先跑起来，向量层是增量

模型下载要两三个小时。在这段时间里，BM25 索引已经建好了：463 篇文档，wiki 层 99 篇（排除 raw/ 和 log.md），02-技术/ 364 篇。

用中文查”Claude Code 源码泄露”，直接命中对应文章。查”pgvector HNSW”，第一条是 wiki 的 pgvector 页，附带 collection 的 context 描述。qmd 的 context 树是它比一般向量库好用的地方：给 /local-rag-kb 这个路径前缀配一句”本地 RAG 知识库体系：向量库、embedding 模型”，每条命中结果都会带上这句话，LLM 拿到结果时就知道这页在知识库里的位置。

这说明检索层的价值不是等所有组件到位才兑现的。关键词层先上线，向量层和 rerank 层作为增量补上，每一步都能单独验证。

问题六：embed 跑了 42 分钟，嵌入了 0 个 chunk

模型就位后第一次 qmd embed，进度条走到 100%，输出是”Embedded 0 chunks from 459 documents in 42m 49s”，中间夹着一行”Session expired”。

原因有两层。qmd 给 embed 会话设了 30 分钟的默认上限，到点就跳过剩余批次。而默认批次是按 64MB 切的，02-技术/ 里有 MLOps 教程那种带完整示例代码的长文，一个批次装下去，第一批还没跑完就到期了，于是一个 chunk 都没落盘。

把批次压到 8MB、会话上限设为不限，wiki 层 99 篇 44 秒完成，02-技术/ 360 篇 5 分 50 秒完成，总共 3448 个向量。GPU 全程 94% 利用率，说明模型本身没问题，问题只在批次策略。

问题七：符号链接骗过了 qmd，没骗过 node-llama-cpp

问题三里用符号链接把 Ollama 的 blob 挂成 qmd 期望的文件名，embed 阶段确实生效了。但后来跑 qmd pull，它又把同一个 embedding 模型完整下了一遍，命名是 hf_Qwen_Qwen3-Embedding-0.6B-Q8_0.gguf。我以为是重复文件，删掉。结果下一次 qmd vsearch 花了 4 分钟，其中 3 分多钟在静默地把它再下回来。

qmd 自己的缓存检查用文件名做子串匹配，符号链接的名字能过。但真正加载模型的是 node-llama-cpp，它按 hf_<用户>_<文件名> 的固定规则找文件，找不到就下载，而且不报任何提示。一个工具的两层分别用两套命名规则找同一个文件，链接只满足了外面那层。

链接脚本改成直接生成 hf_ 前缀的名字之后，语义检索 3.7 秒，混合检索加 rerank 19.7 秒。

问题八：agent 环境自己的坑

这次全程是在 Claude Code 里让 agent 操作的，有几个和任务无关、纯粹是环境层面的问题，也值得记一笔：

  • 命令重写 hook 把 echo ====== 这种分隔符当成了命令名，报”not found”。用 shell 里的特殊字符做视觉分隔要小心。
  • pkill -f 'qmd embed' 和 pgrep -f 'qmd.js query' 的模式都匹配到了执行它们的那个 shell 本身，整条命令以 144 退出，后面的步骤全没跑。这个错我在同一个会话里犯了两次。用 ps -eo pid,comm,args 按 comm 字段过滤再取 PID，才是安全的写法。
  • 后台任务的”杀掉”只杀到了外层 shell，内层 bun 进程又活了 20 分钟，一直在抢带宽。杀进程之后要回头看进程树，不能只看命令返回值。
  • 用 Claude Code 的 run_in_background 跑带 > 重定向的命令，日志文件一直是空的。改用 nohup sh -c "..." & 才正常。
  • 两个进程共用同一个 .ipull 临时文件，先退出的那个把文件清了，后退出的在最后 rename 时报 ENOENT，1.2GB 白下。

这五个都不是 qmd 的问题，但每一个都消耗了一轮排查。agent 操作真实系统时，工具链本身的行为是需要被验证的对象，不能当作透明的。

最终状态

  • git 仓库建好，两次提交。
  • qmd 装好，463 篇文档、3448 个向量，三个模型全部就位，CUDA 加速正常。
  • 项目根 .mcp.json 注册了 MCP server，Claude Code 进目录自动加载 query / get / multi_get。
  • CLAUDE.md 加了”检索层”一节，写明 query 的新顺序和 embed 的批次参数。
  • 实测：查”K8s 集群里 GPU 调度怎么做”，第一条是 K8s 进阶系列第 21 篇 GPU 调度，第二条是 wiki 的 device-plugin 概念页，分别来自创作层和 wiki 层。查”怎么让 agent 记住之前的对话”，命中 hindsight 记忆系统、hermes 持久记忆和 harness 系列的记忆章节。

回头看

八个问题里，真正和 qmd 有关的只有三个：默认模型的语言偏向、embed 的批次上限、两层不一致的模型命名。其余五个分别来自：文档与现实脱节、对”静默”的误判、网络环境、组件间的隐含依赖、agent 工具链自身。

搭一个”AI 第二大脑”的技术选型早就在 wiki 里做完了。难的从来不是选什么，而是把它在一台具体的、网络不好的、被 OneDrive 同步着的机器上跑起来。
