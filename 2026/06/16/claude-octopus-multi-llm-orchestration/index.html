单模型 review 的死穴：Claude Octopus 怎么让多个 LLM 投票

 2026-06-16  Coding-Agent Claude Code AI编程 多模型编排 LLM共识
Claude Code AI编程 多模型编排 LLM共识 Agent工程
Coding-Agent
文章字数:   4.5k
阅读次数:  
   阅读模式

让一个大模型写代码、再让同一个大模型审代码，是当下几乎所有 AI 编程工具的默认做法。问题是：写的时候”想错了”的地方，审的时候往往会因为同样的理由再”想错”一遍。

Claude Octopus 这个 Claude Code 插件给出的答案很直接——别让一个模型自己审自己，把 Codex、Antigravity CLI、Perplexity、Copilot、Qwen、Ollama 等外部 provider 拉进来，和宿主 Claude 互相挑错。下面拆三层：它要解决的根本问题、核心机制怎么实现、以及这套复杂度到底值不值。

版本说明
本文最初按 2026-06 的 v9.45.0 写成，当时 README 写的是”最多 9 个模型”（Claude + Codex、Gemini、Antigravity CLI、Copilot、Qwen、Ollama、Perplexity、OpenRouter）。截至 2026-10-09，仓库已到 v11.13.1、约 4.2k star，变化不小：Gemini CLI 已被标为退役，外部 provider 扩到 12 个（新增 OrcaRouter、OpenCode、Cursor CLI、Grok、Kimi Code 等），命令 / skill / persona 变成 54 / 63 / 31，默认模型路由也换了一轮。下文的数字凡是两个版本不同的，都标了”截至”时间；四阶段流程、75% 共识门、反应引擎、worktree 隔离这些核心机制在 v11 里仍然存在。

先说结论：它的价值不在”多个模型一起干活”这种朴素直觉，而在用工程手段隔离了不同模型的训练偏差。代价是 token 成本和复杂度都成倍上升。

自相关偏差：模型审不出自己的 bug

有个词很贴切地概括了单模型 review 的死穴——autocorrelation（自相关）。意思是：审查模型和生成模型共享同一套训练数据、同一套失败模式，所以”在生成阶段说得通”的逻辑错误，”在审查阶段也会同样说得通”。

举个具体的：模型写了一段订单查询，循环里逐条查数据库。

def get_order_totals(order_ids):
    totals = {}
    for oid in order_ids:
        # 每个 id 单独查一次库——经典 N+1
        order = db.query("SELECT * FROM orders WHERE id = ?", oid)
        totals[oid] = order.amount
    return totals

这段代码功能上完全正确，测试也能过。N+1 查询是性能问题，不是功能 bug。当你把它丢回给同一个模型问”这段代码有什么问题”，它大概率回答”看起来没问题”——因为当初让它写出这种循环的那套”习惯”,同样会让它觉得这种循环很自然。

生成模型：写出 N+1 循环（觉得自然）
        ↓ 换审查 prompt，但还是同一个模型
审查模型：判定"没问题"（同样的偏差，同样的盲区）

要打破这个死循环，最直接的办法是引入一个训练分布不同的审查者。按 README 给的角色分工，OpenAI 的 Codex 系模型负责边界情况挖掘和实现、Perplexity 负责联网检索，和 Claude 的强项并不重叠——可以合理推测它们的盲区也错开了。这就是 Octopus 整个设计的出发点：不是”人多力量大”，是”盲区要错开”。

三层架构与 provider 的懒检测

Octopus 把自己分成三层：最上面是 /octo:* 命令和 skill 组成的用户界面（截至 2026-10：54 个命令、63 个 skill）；中间是一组 shell 脚本构成的编排核心，主脚本 scripts/orchestrate.sh 约 3400 行，scripts/ 下 190 多个 .sh 合计约 8 万行；最下面是各个执行环境（宿主 Claude 必需，其余外部 provider 按需激活）。

最值得看的是它怎么”发现”可用的 provider——不需要你提前配置，每次调用现场探测。下面是简化后的逻辑（真实实现在 scripts/lib/providers.sh 的 detect_providers()，还会区分 OAuth 和 API key 两种认证）：

# 简化示意
detect_providers() {
  PROVIDERS=""
  command -v codex >/dev/null 2>&1 && PROVIDERS="${PROVIDERS} codex"
  command -v agy >/dev/null 2>&1 && PROVIDERS="${PROVIDERS} agy"
  [ -n "$PERPLEXITY_API_KEY" ] && PROVIDERS="${PROVIDERS} perplexity"
  PROVIDERS="${PROVIDERS} claude"
  echo "${PROVIDERS}"
}

逻辑朴素到有点反高潮：CLI 在 PATH 里就算一个，API key 设了就算一个，Claude 永远兜底。这种”懒检测”带来一个很实际的好处——你装了 Codex 就自动多一票，没装也不报错，整套工作流照常跑，只是参与投票的模型少一个。

安装本身走 Claude Code 的插件市场，要求 Claude Code v2.1.14 以上：

claude plugin marketplace add https://github.com/nyldn/plugins.git
claude plugin install octo@nyldn-plugins
# 装完在会话里跑 /octo:setup 配置 provider；诊断用 shell 里的 octopus doctor 或会话内 /octo:skill-doctor

第一个坑是仓库找错地方：nyldn/plugins 只是个 marketplace 目录（0 star），真正的代码在 nyldn/claude-octopus。它迭代极快：2026-06 我看的时候是 v9.45.0、约 3.6k star、49 命令 / 54 skill / 32 persona；到 2026-10-09 已经是 v11.13.1、约 4.2k star、300 个左右的 release。外面一些介绍说 orchestrate.sh 有 8600 行，单看这个主脚本对不上（2026-06 约 3100 行，2026-10 约 3400 行），那个数字大概是把 scripts/ 下多个脚本加在一起算的。下面讲机制时，能在仓库里找到对应代码的会注明文件，其余的标”据 README”。

四个阶段：每个阶段配不同的编排策略

Octopus 不是把这一圈模型一股脑全程并行，而是把一次完整工作流切成四个阶段——这套流程改编自英国设计委员会（UK Design Council）的 Double Diamond 双钻设计框架，每个阶段用不同的编排模式，这是它比”开几个 agent 一起跑”更讲究的地方。

阶段命令编排模式解决什么
Discover/octo:discover并行广撒网找信息，越多视角越好
Define/octo:define顺序共识收敛需求，要的是一致
Develop/octo:develop质量门控实现，边写边卡质量
Deliver/octo:deliver对抗式交付前红队挑刺、go/no-go 打分

按 README 的说法，provider 在研究阶段并行跑、在问题界定阶段顺序跑、在审查阶段对抗式跑。发现阶段要的是覆盖面，所以并行——让模型各查各的，互相看不见，反而能捞出更全的信息；到了定义需求阶段恰恰相反，要的是收敛，所以走顺序共识。这个”按任务性质换编排策略”的思路，比一刀切高明。

最省事的用法是一条命令走完四个阶段（默认 supervised 档位下每个阶段都要人工确认）：

/octo:embrace build stripe integration

想要逐阶段控制，就拆开调：

/octo:discover stripe integration patterns
/octo:define   requirements from discovery
/octo:develop  implement the integration
/octo:deliver  adversarial review before PR

除了这条主线，它还有几个针对性模式。议会模式（council，v9.41 起升为一等公民）让 3/5/7 个 persona 围绕一个决策做结构化辩论，带配额和关键否决（critical-veto）门；--goal 选目标（advice/decision/plan/implement/review），--style 选风格（balanced/adversarial/red-team 等）：

/octo:council --goal decision --style adversarial "Should this service stay monolithic?"
/octo:council --goal review --style red-team "Evaluate auth security assumptions"

并行模式把一个大任务拆成多个工作包同时开干，暗工厂模式（factory）则是 spec 进、软件出的全自动流水线：

/octo:parallel implement full e-commerce checkout system
/octo:factory "REST API with JWT auth, Postgres, OpenAPI, 90% test coverage"

暗工厂听着很美，但后面讲限制时我会泼冷水——它会把含糊的规格放大成含糊的产出。

共识门：用 75% 投票替代单模型自评

光把这一圈模型拉来还不够，关键是怎么把它们的意见收敛成一个决策。Octopus 的做法叫共识门（consensus gate），默认阈值 75%（README 与对比表都写明 “75% agreement threshold”）——在两个工作阶段之间，统计所有活跃 provider 的意见，达不到 75% 同意就不放行。

# 审批节奏由 autonomy 档位控制
export OCTOPUS_AUTONOMY="semi-autonomous"  # supervised | semi-autonomous | autonomous

（说明一下：网上有的说法提到一个 OCTOPUS_CONSENSUS_THRESHOLD 环境变量可以调阈值，但 README 和插件文档里都没有这个开关，别照搬那条 export。）

这里有个容易被忽略的设计点：它没有让任何单个模型来判断”意见够不够”。如果让 Claude 来裁决”大家是不是达成共识了”，等于又把自相关偏差请回来了。共识门是纯计票——投票这个动作本身在编排脚本里完成，不经过任何一个模型的主观判断。

更有意思的是分歧时的行为。它不会把冲突藏起来取个平均，而是把具体的分歧点摊到你面前。举个设想的场景（示意，不是真实输出）：

Claude 和 Copilot 批准了这个实现。
Codex 标记了一处潜在的 N+1 查询。

注意这正好接上了第一节那个 N+1 的例子——单模型审不出来，换一个分布不同的审查者就有机会抓到。这种”把不同意见显式化”的处理，比强行投出一个多数票更有价值，因为真正值钱的往往是那一票反对。

每个阶段的产出都会作为独立的 synthesis 文件落盘，可追溯；v10 起又加了一层持久化的执行契约和”贡献校验”——某个 provider 的结果不合格就直接判失败，而不是混进最终结论（细节见仓库 docs/ARCHITECTURE.md）。

对抗式审查与并行 worktree 隔离

共识投票管的是”对不对”，最后交付阶段还有一套更狠的机制——对抗式审查。它给模型换了个提问方式：不问”这段代码正确吗”，改问”如果你是攻击者，你会怎么利用这段代码”。

视角一换，模型的注意力完全不同。问”对不对”时模型倾向于确认；问”怎么攻破”时模型才会主动去找认证绕过、注入点、边界溢出。其中 Perplexity 负责联网做实时 CVE 检索、查依赖和最新文档，把外部已知漏洞拉进来一起挑战。多 provider 跑完还会写一张 agent 状态台账（octopus agent-summary 可查），记录哪个 provider 真出力了、哪个降级跑、哪个在合成前就挂了——每条结论可回溯到具体模型。

并行执行靠的是 git worktree 隔离。多个 agent 各自在独立的 worktree 里干活，互不踩踏：

# 每个并行 agent 一个独立 worktree + 独立分支
git worktree add ../wt-auth   feature/auth-wt1
git worktree add ../wt-pay    feature/pay-wt2
# 跨 worktree 的共享记忆挂在统一目录下
~/.claude/projects/<repo>/memory/

worktree 之间共享底层 object database 所以不浪费磁盘，但各自的 plan mode、hooks、权限是隔离的。这对应一个经典的工程模式——舱壁（bulkhead）：一个 agent 崩了不会顺着并行流把别人也带塌。

还有一个独立运转的反应引擎（reaction engine），它在 agent 对话之外单独盯着一个 13 状态的生命周期：CI 挂了把失败日志收进 agent 收件箱、最多重试 3 次、超过 30 分钟升级给人；agent 15 分钟没进展也会升级。默认值可以用项目里的 .octo/reactions.conf 覆盖：

# 生命周期状态流转（scripts/reactions.sh；默认 ci_failed 重试 3 次、30 分钟升级）
# running → pr_open → ci_pending → [ci_failed | review_pending]
# 反应引擎状态持久化在 ~/.claude-octopus/agents/reactions 下
ls ~/.claude-octopus/agents/reactions

这是典型的带外监工（out-of-band supervisor）——监控逻辑不混在被监控的对话里，agent 自己卡死了也有人在外面看着。

persona、原生 agent 与省 token 的小心思

光有 provider 还不够，Octopus 在上面又架了一层角色系统。它内置一批 persona（2026-06 是 32 个，2026-10 是 31 个），分为软件工程、专项开发、文档与沟通、研究与战略、商业与合规、创意与设计六类。安全审查那一票，就是由专门的 security-auditor persona 去投，而不是让通用模型临时客串。

persona 和执行偏好的映射集中写在 agents/config.yaml 里——每个 persona 用哪个 CLI、在哪些阶段（probe / grasp / tangle / ink，分别对应四个阶段）激活、属于哪个档位、权限模式是只读还是可写，必要时还能声明 isolation: worktree。另外 agents/droids/ 下有 10 个原生 agent（octo-backend-architect、octo-security-auditor、octo-code-reviewer 等），是带 frontmatter 的 markdown 文件。

# agents/config.yaml 中一个 persona 条目（节选）
ai-engineer:
  file: personas/ai-engineer.md
  cli: agy
  phases: [probe, tangle]
  tier: premium
  permissionMode: plan

这种声明式配置的好处是，编排核心不用把”谁该在什么时候上场”硬编码进脚本，agent 自己带着这张名片。

跑这么多模型，上下文开销是绕不开的问题。Octopus 的对策叫 bin/octo-compress，挂在 PostToolUse hook 上压缩工具输出（项目文档自称每个会话省约 7300 token）。截至 2026-10 它是显式开启的：

export OCTOPUS_COMPRESS_ENABLED=true   # PostToolUse 输出压缩

它还处理了一个 Claude Code 用户很熟的痛点——上下文压缩（compaction）。hooks/pre-compact.sh 在有 agent 正在跑的阶段会尝试拦下压缩（需要 Claude Code v2.1.105+），post-compact.sh 则在压缩后把工作流的执行约束重新注入，不至于一压缩就”金鱼脑”。这些细节单看不起眼，但正是它们让多模型编排在长会话里不至于失控。

成本、复杂度，与什么时候真该用它

讲完机制，得冷静算账。它有几条很实在的限制，我把最关键的挑出来。

成本上，多模型工作流的 token 用量是单模型的好几倍。 README 给了一张示意性的估算（按 2026-09-22 的 API 价格）：单 provider 的一次快速提问 5–20K token，多轮辩论 30–80K，council 60–150K，完整的四阶段 /octo:embrace 要 150–400K token、折合 1–6 美元以上。README 写明有五个 provider”不额外花钱”（截至 2026-10）：Codex、Antigravity CLI、Copilot、Cursor CLI 复用你已有的订阅或本地认证，Ollama 在本地跑。要注意一个时效坑——早先流传的”Qwen 每天 1000–2000 次免费”已经过期了，README 明确写 Qwen 的免费 OAuth 档在 2026-04-15 结束，现在得用 API key 或 Coding-Plan。按量付费的典型是 Perplexity，Sonar Pro 是 $3/$15 每百万 token 输入/输出，另按检索请求收 $6–14 每千次。跑之前可以用 /octo:costs 看预估，跑完用 /octo:usage 看实际花费。

# 项目档位提示：不硬性拦截，只影响 setup / doctor / 工作流推荐的验证强度和 provider 开销
export OCTO_TIER="production"   # prototype | mvp | production

多花的 token 换来的不只是”多几票”。Octopus 的路由是有依据的分工——让擅长的模型干擅长的事，而不是平均主义地都跑一遍。这套分工 README 写得很具体，但模型名几乎每个大版本都在换。截至 2026-10（v11.13.1）的默认映射是：

架构 / 策略 / 安全审查 → Opus 5.5（Claude Code v2.1.280+；更老的宿主依次回退到 Opus 5、4.8/4.7/4.6）
代码审查 / 实现       → GPT-5.6 Sol（经 Codex，负责边界情况挖掘）
综合汇总             → Sonnet 5.5（老版本宿主回退到 Sonnet 5 / 4.6）
实时联网 / CVE 检索   → Perplexity

（2026-06 的 v9.45 时，这张表还是 Opus 4.8 + GPT-5.4 + Gemini 的组合。）也就是说，前面对抗式审查里 edge-case 挖掘交给 OpenAI 系不是随手分的，是按各家强项分的；高风险的架构和安全审查默认走最强的 Opus（想退回 v9.29 之前的旧映射可以 export OCTOPUS_LEGACY_ROLES=1）。至于各种 benchmark 分数，月月在变，这里只讲分工逻辑、不把单个分数当硬数据。

复杂度上，worktree 一旦超过 4–6 个并行 agent 就开始难管——合并冲突、磁盘占用都要操心。还有那个 /octo:factory（spec 进、软件出的全自动模式），它会把模糊的需求顺着流水线放大：规格写得含糊，产出就是规模化的含糊（README 自己也提醒，这个模式你审的是产出、不是每一步）。

所以我的判断是，它不是用来替代日常 Claude Code 的。该用它的场景很窄但很明确：

值得用 Octopus：
  - 有长期后果的架构决策
  - 安全攸关的审查（认证 / 加密 / 支付）
  - 真正不确定、需要多方求证的调研
  - 要发给真实用户的生产级交付

用普通 Claude Code 就够：
  - 快速、无歧义的小任务
  - 探索期的紧凑迭代循环
  - 个人工具、低风险自动化

这套设计真正聪明的地方，是把分布式系统里那几个成熟模式——熔断、舱壁、带外监工、共识校验——平移到了多模型编排上。orchestrate.sh 那三千多行、加上 scripts/ 整体数万行的 shell 不是堆出来的复杂度，而是这些机制本身要求的协调基础设施。

我自己的取舍很简单：架构评审和支付、认证相关的安全审查值得用它，直接 /octo:deliver 上一轮对抗式审查，因为那种地方一个盲区就是一次线上事故，多花几倍 token 换几个分布不同的审查视角很划算；但写脚本、改配置这种日常活我不用它，开 4–6 个 worktree 再处理合并冲突的成本，远超它能帮我省下的时间。

但”机制成熟”不等于”你需要”。如果你的任务一个模型 30 秒就能搞定，那套 /octo:embrace 的四阶段流水线就是纯仪式感，还要多烧几倍 token。先想清楚你要解决的是不是”自相关偏差”这个具体问题，再决定要不要请这只八爪鱼上桌。想深挖的话，官方仓库的 README 和 docs/ARCHITECTURE.md 把 provider 流转和执行模型讲得很细。
