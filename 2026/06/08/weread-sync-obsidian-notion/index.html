用微信读书官方 Skill 把书架和笔记同步到 Obsidian 与 Notion

 2026-06-08  Tool Obsidian 微信读书 Notion Dataview
Obsidian 微信读书 Notion Dataview 知识管理

微信读书里划了几百条线、读完几十本书，这些数据一直躺在 App 里，想拿出来二次整理基本没辙。以前靠第三方插件抓 cookie 同步，但 cookie 三天两头失效，移动端的授权方式也早就变了。

2026 年 5 月微信读书上了官方 Skill，事情就简单了：Skill 负责把数据读出来，一个会跑命令的 AI Agent 负责把数据写到你想要的地方。我把同一套数据分别同步进了 Notion 和 Obsidian，两条路都跑通了，过程差别不小——同步到 Obsidian 反而比 Notion 更省事。这篇把两条路放在一起讲，最后给出怎么选。

共同的底座：官方 Skill + 执行类 Agent

不管目的地是哪个，数据来源都一样：

  • 微信读书官方 Skill：把书架、阅读时长、划线和想法读出来；
  • 一个执行类 AI Agent：Claude Code、Codex、Cursor 都行，只要它能装 skill、能跑命令行、能读写本地文件。

Agent 在中间当胶水：从 Skill 取数据，再写进 Notion 或 Obsidian。

安装 Skill、拿 API Key

去微信读书官方 Skill 页扫码登录，拿到属于你自己的 API Key（wrk- 开头），数据只有你自己可见。然后让 Agent 装上 skill：

# 让 Agent 安装微信读书官方 Skill
npx skills add Tencent/WeChatReading -g

也可以直接对 Agent 说”下载 https://cdn.weread.qq.com/skills/weread-skills.zip 安装 skill”，效果一样。

这个 Skill 是只读的，官方页面列了六类能力：

- 书架：最近在读 / 已读 / 收藏
- 统计：阅读时长、天数、偏好分析
- 笔记：导出某本书的划线与想法
- 搜索：按书名、作者搜书，看评分等信息
- 详情：书籍简介、章节目录、阅读进度
- 推荐：基于阅读偏好推荐新书

它不会反向往微信读书写任何东西。Agent 读数据时统一调一个网关，用你的 Key 鉴权，下面是 Skill 内部调用的大致形态（skill_version 随 Skill 版本变化）：

curl -X POST "https://i.weread.qq.com/api/agent/gateway" \
  -H "Authorization: Bearer $WEREAD_API_KEY" \
  -d '{"api_name":"/shelf/sync","skill_version":"1.0.3"}'

返回的是结构化 JSON：书名、作者、封面、阅读状态、划线、想法都在里面。接下来要做的，就是把这些 JSON 落成 Notion 记录或 Obsidian 认得的 markdown。

两边的差别从这里开始：

同步到 Notion：
  装官方 Skill → 装 ntn CLI → ntn login (OAuth) → Agent 用 ntn api 写库

同步到 Obsidian：
  装官方 Skill → Agent 直接把 .md 写进 vault

路线一：同步到 Notion

Notion 是云端服务，要写进去得先把 Agent 接上它的 API。

准备书架模板

你得先有一个”书架”数据库来放书，列至少包括书名、作者、分类、阅读状态、笔记数、链接。关键是让 Agent 在导入时能看懂这些属性，否则它不知道该把数据塞到哪个字段。

划线怎么存有两种选法：一种是记在每本书页面的正文里，看单本时方便，但没有汇总入口；另一种是单独建一个”摘抄本”数据库，每条划线一行，再关联回书架。我推荐后者，原因在后面的坑二里。

装好并登录 Notion CLI

Notion 官方 CLI 叫 ntn，它让 Agent 精确读写 Notion，而不是猜页面结构：

# 安装 Notion 官方 CLI
curl -fsSL https://ntn.dev | bash
ntn --version

# 浏览器授权，凭证存进系统 keychain，不落明文
ntn login

# 拉一下当前用户，能返回就说明打通了
ntn api v1/users

Agent 往 Notion 写数据，本质就是在拼 ntn api 调用，比如在某个页面下建记录：

# page_id 换成你书架页的 ID
ntn api v1/pages parent[page_id]=abc123

完整用法见 Notion CLI 官方文档，日常基本不用手敲。

首次同步

把同步逻辑讲清楚后，Agent 会先自检：Skill 装了没、ntn 通不通。然后它会问几件事，提前想好答案能省不少来回：

1. 书架页面：把 Notion 书架数据库的链接贴给它
2. 摘录去哪：页面正文，还是独立的"摘抄本"数据库
3. 阅读状态：默认"在读 / 读完"两个值
4. 同步范围：第一次建议只同步书单，不带摘录，量大时快很多
5. 封面：同步到 Notion 的封面位
6. 是否允许新增字段：允许（有些字段用来去重）
7. 微信读书 Key 放哪：本地安全存储

第 7 项别把 Key 明文塞进配置文件，存进系统 keychain：

# macOS 示例
security add-generic-password -s "weread-api" -a "$USER" -w "你的_API_KEY"

中途报错很正常，照着 Agent 的提示改就行。列表刷出来后第一时间去 Notion 里抽查几本：书名、作者、状态对不对，封面有没有图。哪项不对就告诉它，别等全跑完再返工。

结果：170 本 + 摘抄本

我把整个书架搬了一遍：170 本书（其中 2 本在归档区，主书架 168 本），每本都带封面、作者、分类和阅读状态。

书目元数据几乎一把过，真正费事的是”笔记在 Notion 里怎么好用”——这部分结构得自己设计，Agent 不会替你想。

路线二：同步到 Obsidian

很多人以为 Obsidian 是本地软件、没有云 API，同步起来更麻烦。恰恰相反：Obsidian 的 vault 就是一个装满 .md 文件的本地文件夹，没有专有数据库，也没有需要授权的 API。Agent 要”写进 Obsidian”，就是往这个文件夹里写 markdown，这是任何能读写本地文件的 Agent 天生就会的事。所以 ntn、OAuth、token 这三样在这边全都不需要，Obsidian 本体也不用装任何同步插件。

另一个好处是产物就是普通文件，多设备同步和这套流程完全解耦：原本用 iCloud、Obsidian Sync 还是 git 同步 vault，照旧就行。我的 vault 是 git 跟踪的，这批书目笔记顺带进了版本历史，哪天 Agent 写错了，git checkout 一下就回滚。

让 Agent 把每本书写成一个 .md

不用先搭数据库、不用想”这个属性是 select 还是 rich_text”。直接告诉 Agent：一本书一个 markdown 文件，元数据放 frontmatter，笔记放正文。 同步出来的一篇，frontmatter 长这样：

书名: "深入理解Istio：云原生服务网格进阶实战"
作者: "云原生社区"
分类: "计算机-计算机综合"
阅读状态: 在读
笔记数: 1
bookId: "3300020615"
封面: "https://cdn.weread.qq.com/.../t6_3300020615.jpg"
链接: "https://weread.qq.com/web/reader/0a7329e0813ab6e8dg01585d"
tags: [微信读书, 读书笔记]

正文是一个书名标题，下面一个”划线”小节，每条划线用 > 引用块排开；有想法的再加一个”想法”小节。

书名、作者、状态之所以要放 frontmatter，是因为下一步的 Dataview 靠读这些字段来聚合——frontmatter 就是 Obsidian 体系里的”数据库列”。另外书名里的 / : ? * 等字符不能直接当文件名，要让 Agent 先清洗。我书架里有本导入的 Word 文档，原标题是一长串十六进制乱码，这类边角最好在提示里提前交代。

用 Dataview 当书架数据库

Notion 里得有一个数据库来汇总书；Obsidian 不用，散落在文件夹里的 .md 靠 Dataview 插件一段查询就能实时拼成表。在 微信读书书架.md 总览页里写：

TABLE 作者, 分类, 阅读状态, 笔记数
FROM "微信读书/书库"
SORT 笔记数 DESC

它会扫 微信读书/书库 下所有笔记，把 frontmatter 拼成表格，新同步一本，表里自动多一行：

同步之后的玩法

数据进了 vault，就能吃到 Obsidian 全套能力：全局搜索能搜到每一条划线，#微信读书 标签能聚合所有书，Dataview 还能切出各种看板，比如只看在读且有笔记的书：

TABLE 笔记数, 分类
FROM "微信读书/书库"
WHERE 阅读状态 = "在读" AND 笔记数 > 0

写读后感时可以用双链把几本书关联起来，时间长了会织成一张自己的知识网。我的用法是：同步只负责灌原始划线，我在每篇笔记下面接着写自己的消化和延伸。前提是在提示里讲明”已存在的笔记不要整篇重写”，Agent 就只补新书、不覆盖手写部分。

两边都会踩的坑

坑一：书籍链接不能拿 bookId 直接拼。 我一开始把链接写成 weread.qq.com/web/bookDetail/{数字bookId}，点开全是 404。网页版用的是编码后的 ID，要用 Skill 返回的 reader 链接：

❌ https://weread.qq.com/web/bookDetail/510672              → 404
✅ https://weread.qq.com/web/reader/a563285057cad0a565ce031 → 正常打开

坑二：Notion 表格视图里看不到笔记。 Agent 默认把划线写进每本书的页面正文，而数据库表格只显示列，列表里压根看不到笔记。解法就是上面的独立「摘抄本」数据库，把笔记拍平成一条条记录。Obsidian 没有这个问题，笔记本来就在正文里，全局搜索直接命中。

坑三：”笔记没同步”多半是源头就没有。 我这个账号 168 本书里只有 9 本有笔记，其中 3 本还是单字符或纯书签，没有可导出的正文，所以摘抄本最后只有 12 条；Obsidian 那边前 20 本里也只有 1 本有划线。不是漏抓，是微信读书里本来就这么多。

另外，封面有时第一遍抓不全，要补一句”封面没同步，请处理”让 Agent 再跑一遍——这是”人盯着、报错就改”的半自动流程，不是一键全自动。

还要记住官方 Skill 是只读单向的，同步只是某个时刻的快照。之后又划了新线、读完新书，得再让 Agent 跑一次。一个省事的做法是把这次和 Agent 的会话改名叫”微信读书”，下次进去说一句”同步一下”，它还记得书架页、字段映射，不用从头再问。

Obsidian 还是 Notion

维度NotionObsidian
额外依赖ntn CLI + OAuth 登录无，直接写 md
汇总方式数据库 + relationDataview 查询
笔记可见性需单独建摘抄本数据库正文即笔记，全局可搜
数据在哪云端本地纯文件
多人协作原生支持需自己解决
换工具绑定 Notionmd 谁都能打开
选 Obsidian：想数据在本地、纯 md、长期不被某个 App 锁住
选 Notion  ：要多人协作、要关系数据库视图、本来就在 Notion 里管理信息

我自己最后留在 Obsidian：读书笔记是要长期攒的资产，落在本地、是纯 markdown 才安心，换编辑器、换平台都不丢。如果你的信息管理本来就在 Notion，那走 Notion 这条路也完全没问题，多出来的只是装 CLI 和登录这一步。

两条路的起点都一样：去微信读书官方 Skill 页拿到 Key，然后告诉 Agent 你要把书架写到哪里。

本文 Notion 部分的流程参考了 Shiki 的视频教程，命令已对照微信读书 Skill 页和 Notion CLI 官方文档核对。
